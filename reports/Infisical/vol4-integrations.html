16.1　Docker / Docker Compose 注入

三種模式 開發者

Docker 環境中把 secret 注入容器有三種主流方法：

方式適用優點缺點
CLI 在 entrypoint 注入本機開發、簡單部署setup 最簡單image 內含 CLI
SDK 在應用程式內取多數 productioncleanest，無外部依賴啟動延遲增加
Sidecar Agent多 replica、需共享 secret 檔主應用無需 SDK多容器要協調

方式 1：CLI 在 entrypoint 開發者

# Dockerfile
FROM node:20-alpine AS app

# 安裝 CLI（鎖版本）
ARG INFISICAL_CLI_VERSION=v0.43.78
RUN apk add --no-cache bash sudo wget \
 && wget -qO- https://artifacts-cli.infisical.com/setup.apk.sh | sh \
 && apk add infisical=${INFISICAL_CLI_VERSION#v}-r0

WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .

# 用 infisical run 注入再啟動 node
ENTRYPOINT ["infisical", "run", "--"]
CMD ["node", "server.js"]
# docker-compose.yml
services:
  app:
    build: .
    environment:
      INFISICAL_TOKEN: ${INFISICAL_TOKEN}
      INFISICAL_PROJECT_ID: ${INFISICAL_PROJECT_ID}
      INFISICAL_ENV: production
      INFISICAL_DOMAIN: https://app.infisical.com
    ports: ["3000:3000"]

啟動前要把 INFISICAL_TOKEN 準備好。在 host 上：

export INFISICAL_TOKEN=$(infisical login \
  --method=universal-auth \
  --client-id=$CID --client-secret=$CSECRET \
  --silent --plain)

docker compose up -d

方式 2：SDK 在應用程式內取

第三卷第 14 章有完整六語言範例，這裡不重複。Docker 端只需把 INFISICAL_CLIENT_ID / INFISICAL_CLIENT_SECRET 透過 env 傳進去。

16.3　Kubernetes Operator：CRD、自動 reload

三個 CRD 各自的角色

  • InfisicalSecret：從 Infisical 拉 secret，建立成 K8s Secret 或 ConfigMap。最常用。
  • InfisicalPushSecret：反方向——把 K8s Secret 推回 Infisical 中央化管理。
  • InfisicalDynamicSecret：拿 dynamic secret lease，自動更新到 K8s Secret，並在過期前自動 renew。

安裝

# 加 Helm repo
helm repo add infisical-helm-charts \
  'https://dl.cloudsmith.io/public/infisical/helm-charts/helm/charts/'
helm repo update

# 安裝 operator（v3.0+）
helm install infisical-secrets-operator \
  infisical-helm-charts/secrets-operator \
  --namespace infisical-operator-system \
  --create-namespace

InfisicalSecret 範例：用 Kubernetes Auth

# 1. SA + ClusterRoleBinding（給 Infisical 驗證 SA token）
apiVersion: v1
kind: ServiceAccount
metadata:
  name: infisical-token-reviewer
  namespace: infisical-operator-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: infisical-auth-delegator
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: system:auth-delegator
subjects:
  - kind: ServiceAccount
    name: infisical-token-reviewer
    namespace: infisical-operator-system
---
# 2. 應用 SA（pod 用這個身分認證）
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
  namespace: production
---
# 3. InfisicalSecret CRD
apiVersion: secrets.infisical.com/v1alpha1
kind: InfisicalSecret
metadata:
  name: my-app-secrets
  namespace: production
spec:
  hostAPI: https://app.infisical.com/api
  resyncInterval: 60     # 每 60 秒從 Infisical 拉一次
  authentication:
    kubernetesAuth:
      identityId: 5f1a2b3c-4d5e-6f7a-8b9c-0d1e2f3a4b5c
      serviceAccountRef:
        name: my-app-sa
        namespace: production
  managedSecretReference:
    secretName: my-app-secret      # 產出的 K8s Secret 名
    secretNamespace: production
    creationPolicy: "Orphan"        # 刪 CRD 時保留 Secret
  managedKubeConfigMapReferences:   # （選用）也 sync 到 ConfigMap
    - configMapName: my-app-config
      configMapNamespace: production
  scope:
    secretsScope:
      projectSlug: my-project
      envSlug: prod
      secretsPath: "/services/api"
      recursive: true

自動 reload pod：殺手級功能

Infisical Operator 最強的差異化：secret 變更時自動重啟 deployment。在 deployment 加 annotation：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: production
  annotations:
    secrets.infisical.com/auto-reload: "true"
spec:
  template:
    spec:
      containers:
        - name: app
          image: my-app:latest
          envFrom:
            - secretRef:
                name: my-app-secret  # 對映上面 Operator 產出的 Secret

之後在 Infisical UI 改 secret 值 → Operator 偵測到 → 更新 K8s Secret → Deployment 觸發 rolling restart → pod 啟動拿到新值。整套無人工介入。

InfisicalDynamicSecret：DB 動態憑證自動 lease

apiVersion: secrets.infisical.com/v1alpha1
kind: InfisicalDynamicSecret
metadata:
  name: postgres-readonly
  namespace: production
spec:
  hostAPI: https://app.infisical.com/api
  authentication:
    kubernetesAuth:
      identityId: ...
      serviceAccountRef:
        name: my-app-sa
        namespace: production
  dynamicSecret:
    secretName: postgres-readonly  # 對應 Infisical UI 上的 dynamic secret slug
    projectId: ...
    environmentSlug: prod
    secretsPath: "/db"
  leaseTTL: "1h"
  leaseRevocationPolicy: "Revoke"  # CRD 刪除時自動 revoke
  managedSecretReference:
    secretName: postgres-readonly-creds
    secretNamespace: production

Operator 會在 lease 過期前自動 renew 或重新發 lease，K8s Secret 內的帳密永遠是有效的短效 credential。

16.4　CSI Provider：mount 為檔案，徹底跳過 K8s Secret

為什麼要用 CSI DevOps/SRE

K8s 原生 Secret 物件有個尷尬問題：它存在 etcd 裡，預設只是 base64 編碼（不是加密）。即使啟用 etcd encryption-at-rest，K8s admin 透過 API 仍可直接讀。CSI provider 的設計繞過這層：secret 從來不變成 K8s Secret 物件，直接 mount 為 pod 內檔案。

安裝兩件元件

# 1. Secrets Store CSI Driver（K8s SIG 維護的通用 driver）
helm repo add secrets-store-csi-driver \
  https://kubernetes-sigs.github.io/secrets-store-csi-driver/charts
helm install csi secrets-store-csi-driver/secrets-store-csi-driver \
  --namespace kube-system \
  --set enableSecretRotation=true \
  --set rotationPollInterval=2m \
  --set "tokenRequests[0].audience=infisical"

# 2. Infisical CSI Provider（解析 Infisical 認證 + secret）
helm install infisical-csi-provider \
  infisical-helm-charts/infisical-csi-provider \
  --namespace kube-system
EKS 注意事項

AWS EKS 不支援 custom audience，安裝時請不要設 tokenRequests[0].audience。對應地，Infisical 端 K8s Auth identity 的「Allowed Audience」也留空。其他多數 K8s 發行版兩邊一致設 infisical 即可。

SecretProviderClass + Pod 掛載

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: my-app-spc
  namespace: production
spec:
  provider: infisical
  parameters:
    hostAPI: https://app.infisical.com/api
    authMethod: "kubernetes"
    identityId: "5f1a2b3c-..."
    projectSlug: "my-project"
    envSlug: "prod"
    secretsPath: "/services/api"
    fileNames: |
      - secretName: DATABASE_URL
        fileName: db_url
      - secretName: STRIPE_KEY
        fileName: stripe_key
---
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: production
spec:
  serviceAccountName: my-app-sa
  containers:
    - name: app
      image: my-app:latest
      volumeMounts:
        - name: secrets-store
          mountPath: "/mnt/secrets"
          readOnly: true
  volumes:
    - name: secrets-store
      csi:
        driver: secrets-store.csi.k8s.io
        readOnly: true
        volumeAttributes:
          secretProviderClass: my-app-spc

應用程式從 /mnt/secrets/db_url 讀取——secret 從來沒變成 K8s Secret 物件，etcd 裡也沒有。

16.5　Agent Injector：Mutating Webhook 模式

Agent Injector 是仿 Vault Agent Sidecar Injector 的設計：在 pod 啟動時透過 mutating admission webhook 自動加上 sidecar container（裝著 Infisical Agent），由 sidecar 取 secret 寫到 shared volume，主容器讀檔即可。

# 安裝 injector（含 webhook 與 cert-manager 自簽憑證）
helm install infisical-agent-injector \
  infisical-helm-charts/infisical-agent-injector \
  --namespace infisical-system \
  --create-namespace
# Pod 透過 annotation 觸發注入
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: production
  annotations:
    agent.infisical.com/inject: "true"
    agent.infisical.com/inject-template-app-config: |
      {{- with secret "PROJECT_ID" "prod" "/services/api" }}
      DATABASE_URL={{ .Data.DATABASE_URL }}
      STRIPE_KEY={{ .Data.STRIPE_KEY }}
      {{- end }}
    agent.infisical.com/sa-namespace: "production"
spec:
  serviceAccountName: my-app-sa
  containers:
    - name: app
      image: my-app:latest
      command: ["/bin/sh", "-c"]
      args: ["source /vault/secrets/app-config && node server.js"]

Injector 自動加上 sidecar，Agent 把 template 渲染寫入 /vault/secrets/app-config。

16.6　Helm Chart 部署與 ArgoCD GitOps

純 GitOps 模式 DevOps/SRE

InfisicalSecret CRD 本身就是聲明式 K8s 資源，可以放進 Git，ArgoCD 自動 sync。但 credential 不能放進 Git——所以採取「secret zero in cluster」模式：

  1. cluster 內部署一個 Bootstrap Secret，內含 Universal Auth 的 client ID + secret（或更好：用 K8s Auth 的 SA，連 Bootstrap Secret 都不需要）。
  2. InfisicalSecret CRD 引用這個 Bootstrap，從 Infisical 拉所有應用程式 secret。
  3. ArgoCD sync 整個 stack 進 cluster，無 secret 進 Git。

建議架構：

本章重點回顧
  • Docker 用 CLI in entrypoint 最簡單，Production 多用 SDK in app。
  • K8s 三種模式：Operator（多數最佳，含自動 reload）、CSI（避 K8s Secret）、Agent Injector（仿 Vault 風格）。
  • Infisical Operator 三個 CRD 對應三種需求；自動 reload pod 是 ESO 沒有的殺手級功能。
  • 2025 ESO 暫停發布，新採用建議用 Infisical 原生 Operator。
  • GitOps 用 K8s Auth + InfisicalSecret CRD 進 Git，達到 secret zero。

17.1　GitHub Actions（OIDC，無 secret zero）

GitHub Actions 是現代 CI 的代表，務必使用 OIDC Auth 而非 Universal Auth。差別：UA 要把 Client Secret 放進 GitHub Secrets（這就是另一個 secret），OIDC 完全不需要——GitHub 動態簽 token，Infisical 用 GitHub 公鑰驗。

步驟 1：在 Infisical 建立 OIDC Auth identity

  1. Org Settings → Access Control → Identities → Create。
  2. 選 OIDC Auth，配置：
    • OIDC Discovery URL: https://token.actions.githubusercontent.com
    • Issuer: 同上
    • Subject（限制）: repo:acme/myapp:ref:refs/heads/main
    • Audiences: infisical（自訂）
  3. 記下 Identity ID。

步驟 2：在 GitHub Actions 用 secrets-action

name: deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write   # 必要，授權 GitHub 簽 OIDC
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Fetch secrets from Infisical
        uses: Infisical/secrets-action@v1.0.7
        with:
          method: "oidc"
          identity-id: ${{ vars.INFISICAL_IDENTITY_ID }}
          project-slug: "my-proj"
          env-slug: "prod"
          secret-path: "/ci"
          # 可選：指定不同 audience
          oidc-audience: "infisical"

      # 之後 step 可直接讀 env
      - name: Deploy
        run: |
          echo "AWS key: ${AWS_ACCESS_KEY_ID:0:8}..."
          ./deploy.sh

secrets-action 的 secret 會寫進 $GITHUB_ENV,後續 step 直接 $VAR_NAME 取用。GitHub 也會自動 mask 這些值,在 log 裡顯示 ***。

步驟 3:Subject 限制範例

OIDC subject 字串有完整 GitHub claim 結構,可以非常精細地限制誰能取 secret:

# 只允許 main 分支 push 觸發
repo:acme/myapp:ref:refs/heads/main

# 只允許 release tag
repo:acme/myapp:ref:refs/tags/v*

# 只允許特定環境（GitHub Environment Protection 配合）
repo:acme/myapp:environment:production

# 只允許 PR (pull_request 事件)
repo:acme/myapp:pull_request
為什麼 OIDC 是 CI 的最佳解

傳統做法:在 GitHub Secrets 存 INFISICAL_CLIENT_SECRET,但這個 secret 本身就是要被保護的東西——而且 GitHub Secrets 一旦設了就無法輪替（只能整個換掉）。OIDC 完全消除這層:GitHub 簽的 token 只在那次 workflow 執行時有效,過期即廢,且綁定到 commit + branch + actor,blast radius 從「無限期」縮成「單次 workflow run」。

17.2　GitLab CI

GitLab 也支援 OIDC。原理與 GitHub Actions 類似,Infisical 端 OIDC config:

  • OIDC Discovery URL: https://gitlab.com (SaaS) 或自家 GitLab URL
  • Subject: project_path:acme/myapp:ref_type:branch:ref:main
# .gitlab-ci.yml
deploy:
  image: alpine:latest
  id_tokens:
    INFISICAL_JWT:
      aud: infisical
  before_script:
    - apk add --no-cache curl jq bash
    - wget -qO- https://artifacts-cli.infisical.com/setup.apk.sh | sh
    - apk add infisical
  script:
    # 用 OIDC token 換 Infisical access token
    - export INFISICAL_TOKEN=$(infisical login --method=oidc-auth
        --identity-id=$INFISICAL_IDENTITY_ID
        --jwt=$INFISICAL_JWT --silent --plain)
    # 用 secret 跑部署
    - infisical run --env=prod --projectId=$PROJECT_ID -- ./deploy.sh
  only: [main]

17.3　Jenkins

Jenkins 沒有原生 OIDC ID token 簽發機制（除非你自己架 Jenkins-OIDC bridge）。多數 Jenkins 部署用 Universal Auth + Credentials Binding plugin 模式:

// Jenkinsfile
pipeline {
  agent any
  environment {
    INFISICAL_TOKEN = credentials('infisical-universal-auth-creds')
    // credentials() 是 Jenkins Credentials plugin 的 binding
    // 把 Username + Password 形式的 credential 注入成
    // INFISICAL_TOKEN_USR 與 INFISICAL_TOKEN_PSW
  }
  stages {
    stage('Login') {
      steps {
        sh '''
          export INFISICAL_TOKEN=$(infisical login \
            --method=universal-auth \
            --client-id=$INFISICAL_TOKEN_USR \
            --client-secret=$INFISICAL_TOKEN_PSW \
            --silent --plain)
          echo "INFISICAL_TOKEN=$INFISICAL_TOKEN" > infisical.env
        '''
      }
    }
    stage('Deploy') {
      steps {
        sh '''
          set -a; source infisical.env; set +a
          infisical run --env=prod --projectId=$PROJECT_ID -- ./deploy.sh
        '''
      }
    }
  }
  post {
    always {
      sh 'rm -f infisical.env'
    }
  }
}

17.4　CircleCI / Bitbucket Pipelines / Azure DevOps

三者都支援 OIDC,設定原則一致——在 CI 平台啟用 OIDC、在 Infisical 配置對應 issuer 與 subject。

CI 平台OIDC Issuer URLSubject 範例
CircleCIhttps://oidc.circleci.com/org/<org-id>org/<org-id>/project/<proj-id>

17.5　Pipeline 安全最佳實務

七條鐵則 DevOps/SRE

  1. 能用 OIDC 就不要用 long-lived token。
  2. Subject 限制要嚴:精確到 branch / tag / environment,不要用 wildcard 接受任何 ref。
  3. 每個 pipeline 一個 identity:不要共用,blast radius 才能限縮。
  4. Identity 採最小權限:只給該 pipeline 需要的 environment + path,不給 admin。
  5. 不要 echo secret:即使 GitHub 會 mask,也要避免不必要的 print。
  6. artifact 不含 secret:build 出來的 artifact (image / package) 不要 baked in secret。
  7. Audit log 必接 SIEM:CI 是 secret 取用最頻繁的源頭,異常存取最容易在這裡被發現。

18.1　Secret Syncs 概念

有些目標平台不能直接呼叫 Infisical API——例如 Vercel、Netlify 上跑的 serverless function 不會在 build / runtime 主動去拉。對這些平台,Infisical 採「Secret Sync」模式:把 secret 單向推送到目標平台的 native secret store,後續用該平台原生機制取用。

flowchart LR
  INF[(Infisical

這個模式重要的取捨:

  • 優點:應用程式無需改動,使用該平台原生 SDK 即可。
  • 缺點:secret 同時存在 Infisical 與目的地兩處,有同步延遲(預設約幾分鐘)。
  • 因此能直接呼叫 Infisical API 的場景就不要用 sync(例如 EKS pod 用 Kubernetes Auth 拉,不要 sync 到 K8s Secret 再讀)。

18.2　AWS:Secrets Manager / Parameter Store / IAM

Secret Sync 到 AWS Secrets Manager

  1. 在 AWS IAM 建立 IAM Role,信任 Infisical 的 AssumeRole(用 External ID 防 confused deputy)。
  2. 授權該 Role secretsmanager:CreateSecret / UpdateSecret / GetSecretValue。
  3. Infisical UI → Project → Integrations → AWS Secrets Manager → Create Sync,填 Role ARN + External ID + Region + Path Prefix。
  4. 選同步來源 environment + path。
  5. 儲存後 Infisical 立即同步,之後每次 source 變更自動推。

同步到 SSM Parameter Store

流程相似但 IAM Action 改為 ssm:PutParameter 等。Parameter Store 比 Secrets Manager 便宜很多,但有 4KB 大小限制,適合配置型(非超機敏)的 secret。

AWS IAM Dynamic Secret

另一個方向:Infisical 動態簽發 AWS IAM 短效 access key 給應用程式用。第二卷 4.4 節已介紹。

18.3　GCP:Secret Manager

原理一樣:在 GCP IAM 建立 Service Account,授予 secretmanager.admin role,把 SA Key 給 Infisical(或更好——用 Workload Identity Federation)。

# 用 gcloud 建 SA
gcloud iam service-accounts create infisical-sync \
  --display-name="Infisical Sync"

gcloud projects add-iam-policy-binding $PROJECT_ID \
  --member="serviceAccount:infisical-sync@$PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/secretmanager.admin"

# 建 SA key (傳統方式)
gcloud iam service-accounts keys create infisical-key.json \
  --iam-account=infisical-sync@$PROJECT_ID.iam.gserviceaccount.com
# 把 infisical-key.json 內容貼到 Infisical UI

# 推薦:Workload Identity Federation
# 完整步驟見官方文件,可避免 SA Key 外洩風險

18.4　Azure:Key Vault / App Configuration

對 Azure-centric 環境,常見需求是把 Infisical secret sync 到 Azure Key Vault,讓 App Service / Function 透過 Managed Identity 直接取用。

  1. 在 Azure 建立 Key Vault。
  2. 建立 Service Principal 或 App Registration,授權 Vault get / set / list。
  3. 把 Tenant ID + Client ID + Client Secret(或 Certificate)填到 Infisical sync 設定。

18.5　Vercel / Netlify / Heroku / Cloudflare

這四個平台的 secret 都用 OAuth + 平台原生 API:

  • Vercel:Project → Integrations → Vercel,授權後選 Vercel Project + Environment(Preview/Production)即可。Build 時 Vercel 把 secret 注入成 env var。
  • Netlify:同上,授權後選 Site。
  • Heroku:走 Heroku API token,sync 到 Heroku Config Vars。
  • Cloudflare Workers:Cloudflare API token,sync 到 Worker secrets/variables。
Vercel 等 PaaS 的 build cache

Vercel build 時會把 env var bake 進 build artifact 並 cache。意思是:secret 改了,要等下次 deploy 才會生效——而且 Vercel 的 preview deployment cache 可能保留舊 secret。Production 重大變更建議手動觸發 redeploy。

18.6　Databricks / Supabase 等

還有一系列「資料平台」整合,如 Databricks Secrets、Supabase Secrets、Render、Fly.io、Railway。流程一致:在目標平台拿 API token → Infisical UI 建 sync。

19.1　Terraform Provider

基本資料來源 DevOps/SRE

# versions.tf
terraform {
  required_providers {
    infisical = {
      source  = "infisical/infisical"
      version = "~> 0.15"
    }
  }
}

# provider.tf
provider "infisical" {
  host = "https://app.infisical.com"
  auth {
    universal {
      client_id     = var.infisical_client_id
      client_secret = var.infisical_client_secret
    }
  }
}

# main.tf - 取單一 secret
data "infisical_secrets" "all" {
  workspace_id = var.workspace_id
  env_slug     = "prod"
  folder_path  = "/"
}

resource "aws_db_instance" "primary" {
  password = data.infisical_secrets.all.secrets["DATABASE_PASSWORD"]
  # ... 其他欄位
}
使用 data source 的合規問題

用 data "infisical_secrets" 取出來的值會寫進 Terraform state 檔!即使設了 sensitive = true,state 檔內仍是明文。如果 state 存在 S3、Terraform Cloud、Git,等於 secret 在那邊也存了一份。解法:用下面的 ephemeral resource。

Ephemeral Resource:secret 不進 state（重要）

Terraform 1.10+ 支援 ephemeral resource,值只在 plan/apply 期間存在,不寫入 state、不出現在 plan output。Infisical Provider 從 0.15+ 支援:

# 不會寫進 state 的 ephemeral secret
ephemeral "infisical_secret" "db_creds" {
  name         = "DB_PASSWORD"
  env_slug     = "prod"
  workspace_id = var.workspace_id
  folder_path  = "/db"
}

resource "aws_db_instance" "primary" {
  password = ephemeral.infisical_secret.db_creds.value
  # plan/apply 結束後 password 不會留在 state
}

Production Terraform 操作 secret 強烈建議全用 ephemeral resource。這是 2024 後 Terraform 對 secret-in-state 問題的官方解。

Terraform 用 OIDC Auth（CI 內最佳實踐）

# GitHub Actions 內 export OIDC token
TOKEN=$(curl -s -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
  "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=infisical" | jq -r .value)
export INFISICAL_AUTH_JWT=$TOKEN

# Terraform Provider 自動讀 INFISICAL_AUTH_JWT
provider "infisical" {
  auth {
    oidc {
      identity_id = var.identity_id
      # 不需傳 jwt,自動從 env var 讀
    }
  }
}

19.2　Pulumi

Pulumi 沒有官方 Infisical Provider,但可以透過Pulumi ESC(Environments, Secrets and Configuration)的 dynamic provider 機制接入,或在 Pulumi 程式裡直接用 Infisical SDK 取 secret:

// Pulumi TypeScript
import * as pulumi from "@pulumi/pulumi";
import * as aws from "@pulumi/aws";
import { InfisicalSDK } from "@infisical/sdk";

async function main() {
  const inf = new InfisicalSDK({ siteUrl: "https://app.infisical.com" });
  await inf.auth().universalAuth.login({
    clientId: process.env.INFISICAL_CLIENT_ID!,
    clientSecret: process.env.INFISICAL_CLIENT_SECRET!,
  });

  const dbSecret = await inf.secrets().getSecretByName({
    secretName: "DATABASE_PASSWORD",
    projectId: process.env.INFISICAL_PROJECT_ID!,
    environment: "prod",
    secretPath: "/db",
  });

  // 用 pulumi.secret 包裝確保 Pulumi 也視為 secret
  const password = pulumi.secret(dbSecret.secretValue);

  new aws.rds.Instance("primary", {
    password,
    // ...
  });
}

main();

19.3　Ansible Lookup Plugin

Infisical 有官方 Ansible Collection(infisical.vault),提供 lookup plugin 與 modules:

# 安裝
ansible-galaxy collection install infisical.vault

# playbook.yml
- name: Deploy app with Infisical secrets
  hosts: webservers
  tasks:
    - name: Login to Infisical
      infisical.vault.login:
        url: "https://app.infisical.com"
        auth_method: universal_auth
        universal_auth_client_id: "{{ lookup('env', 'INFISICAL_CLIENT_ID') }}"
        universal_auth_client_secret: "{{ lookup('env', 'INFISICAL_CLIENT_SECRET') }}"
      register: inf_login

    - name: Read all secrets
      infisical.vault.read_secrets:
        login_data: "{{ inf_login.login_data }}"
        project_id: "{{ project_id }}"
        env_slug: "prod"
        path: "/services/web"
        as_dict: true
      register: secrets

    - name: Configure app
      template:
        src: app.conf.j2
        dest: /etc/myapp/app.conf
      vars:
        db_url: "{{ secrets.secrets.DATABASE_URL }}"
        api_key: "{{ secrets.secrets.API_KEY }}"

Ansible Collection 也支援 dynamic secret lease 操作(create_dynamic_secret_lease、renew_dynamic_secret_lease、delete_dynamic_secret_lease),適合「playbook 跑完 lease 自動 revoke」這種情境。

19.4　Chef / Puppet 整合模式

Chef / Puppet 沒有官方 Infisical Provider,但可以在 recipe / manifest 內呼叫 CLI 或 SDK:

# Chef recipe 範例
execute 'fetch infisical secrets' do
  environment ({
    'INFISICAL_CLIENT_ID'     => node['infisical']['client_id'],
    'INFISICAL_CLIENT_SECRET' => node['infisical']['client_secret']
  })
  command 'infisical export --env=prod --format=dotenv > /etc/myapp/.env.runtime'
  not_if  'test -s /etc/myapp/.env.runtime'
  notifies :restart, 'service[myapp]', :delayed
end

file '/etc/myapp/.env.runtime' do
  owner 'myapp'
  group 'myapp'
  mode '0600'
end

注意 export 出來的 .env 檔權限 600,並由 service user 擁有。

20.1　Agent 架構與 Template 機制

Agent 是什麼 DevOps/SRE

Infisical Agent 是一支獨立的 daemon(其實就是 CLI 的 infisical agent 子命令),它的職責:

  1. 啟動時用配置檔指定的 Auth method 登入 Infisical
  2. 把 access token 與 / 或 secret 寫到 sink(檔案 / stdout)
  3. 持續 watch,當 secret 變更時重新渲染 template

適合「應用程式不能改、不想加 SDK、又需要動態 secret reload」的場景。

典型 agent-config.yaml

infisical:
  address: https://app.infisical.com
  exit-after-auth: false       # false = 持續執行,自動 reload

auth:
  type: universal-auth           # 也可以 aws-iam / kubernetes / azure 等
  config:
    client-id-path: /etc/infisical/client-id
    client-secret-path: /etc/infisical/client-secret
    remove-client-secret-on-read: false

sinks:
  - type: file
    config:
      path: /var/run/infisical/access-token

templates:
  - source-path: /etc/infisical/templates/app.env.tpl
    destination-path: /etc/myapp/.env.runtime
    config:
      polling-interval: 60s
      execute:
        command: systemctl reload myapp   # secret 變更時執行

Template 語法

template 用 Go template 引擎,有專屬函式 secret 取 Infisical secret:

# app.env.tpl
{{- with secret "PROJECT_ID" "prod" "/services/api" }}
DATABASE_URL={{ .Data.DATABASE_URL }}
STRIPE_KEY={{ .Data.STRIPE_KEY }}
JWT_SECRET={{ .Data.JWT_SECRET }}
APP_VERSION={{ .Data.APP_VERSION | default "1.0.0" }}
{{- end }}

每次 polling 偵測到 secret 變化,Agent 重新渲染檔案,然後執行 execute.command(例如 reload nginx、kill -HUP 給 worker)。

20.3　Gateway:讓 Cloud 反向連回內網

解決什麼問題 DevOps/SRE

常見場景:你用 Infisical Cloud,但需要 Cloud 連回你內網的 PostgreSQL 做 dynamic secret——可是內網 DB 沒對外開放。傳統解法:開個 NAT 或 VPN 給 Infisical Cloud 的 IP——但這破壞了「外部服務不該主動進你內網」的安全原則。

Gateway 把這個方向反過來:你在內網部署一個 Gateway,Gateway 主動向外建立 SSH 反向 tunnel 到 Infisical Cloud(或 Org-level Relay)。Cloud 端要連你內網時,流量經過這個既有 tunnel,不需要 inbound firewall rule。

flowchart LR
  subgraph CLOUD[Infisical Cloud]
    BACK[Backend]
    RELAY[Relay
SSH Bastion]
  end

  subgraph CORP[公司網段]
    GW[Gateway
反向 SSH client]
    DB[(內網 PostgreSQL)]
    APP[內網應用 API]
  end

  GW -- 主動發起 SSH
反向 tunnel --> RELAY
  BACK -- 透過 tunnel
連回內網 --> RELAY -.-> GW --> DB
  GW --> APP

Gateway V2 架構重點

  • Relay:在 Cloud / Self-Host 端的中介。Instance-level Relay 由 Infisical 公司託管(US/EU 多區);Org-level Relay 你自己部署降低延遲。
  • Gateway:在你內網的 client。用 Infisical 簽發的 SSH 憑證身份認證(短效)。
  • 連線方向:Gateway 主動發起,只需要對 Relay 的 outbound 連線(443 或 22)。
  • 支援的下游資源:資料庫(用於 dynamic secret)、HTTP API(用於 App Connections)、PAM Resource(用於 PAM session proxy)。

Gateway 部署

# 1. 在 Infisical UI 啟用 Gateway,產生一次性 enrollment token
#    Org Settings → Gateways → Create Gateway

# 2. 在內網主機部署 Gateway
docker run -d --name infisical-gateway \
  --restart=always \
  -e INFISICAL_HOST=https://app.infisical.com \
  -e ENROLLMENT_TOKEN=$ONE_TIME_TOKEN \
  -e GATEWAY_NAME=corp-network-gw \
  infisical/gateway:v2-latest

# 3. UI 上會顯示 Gateway "已連線"
# 4. 之後在 Dynamic Secret 配置時,選 "Use Gateway: corp-network-gw"
Gateway V1 將被淘汰

舊版 Gateway V1 用 QUIC 協定,新版 V2 用 SSH 反向 tunnel。V2 不是 V1 的 in-place 升級——需要重新建立 Gateway 並把所有 dynamic secret / app connection 指向新 gatewayId。建議盡早遷移,V1 仍支援但無新功能。

本卷重點回顧
  • Docker / K8s 三種注入模式各有取捨;K8s 多數團隊選 Operator + 自動 reload。
  • CI 全面用 OIDC,徹底消除 long-lived token。
  • Cloud Platform 用 Secret Sync 模式單向推送,但能直連 Infisical 的場景不要用 sync。
  • Terraform 一律用 ephemeral resource 避免 secret 進 state。
  • Agent 解決「應用程式無法改、又要動態 reload」;Gateway 解決「Cloud 要連回你內網但不能開 inbound」。
