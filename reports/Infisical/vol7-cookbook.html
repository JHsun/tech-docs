31.1　Web App + DB 完整 secret 流（Local → CI → K8s）

場景描述 開發者

典型 SaaS 後端：Node.js + Express + PostgreSQL，部署在 K8s。需要管理的 secret 有 DATABASE_URL、JWT_SECRET、STRIPE_SECRET_KEY、SENDGRID_API_KEY 等。目標：開發者本機開發、PR 觸發 CI 跑測試、merge 到 main 自動部署到 K8s production。整套流程不存任何長期 token。

步驟 1：Infisical 端 Project 結構

# Project: my-saas-app
# Environments:
#   - development
#   - staging
#   - production
# Folder structure:
#   /app           （應用程式 secret）
#   /ci            （CI 專用 secret，例如測試用 fixture）
#   /db            （DB 連線資訊）
#
# 建立 4 個 Identity:
#   1. dev-team-readonly       （給開發者本機, UA + IP allowlist）
#   2. github-actions-ci       （給 CI, OIDC Auth）
#   3. k8s-prod-operator        （給 Operator, K8s Auth）
#   4. github-actions-deploy    （部署用, OIDC Auth + 限 main 分支）

步驟 2：本機開發體驗

# 開發者第一次設定（一次性）
brew install infisical/get-cli/infisical
infisical login                                # 瀏覽器 SSO
cd ~/projects/my-saas-app
infisical init                                 # 產生 .infisical.json

# 平常開發
infisical run --env=dev -- npm run dev
# secrets 自動注入，code 內 process.env.DATABASE_URL 即可用

步驟 3：GitHub Actions CI（OIDC 無 secret zero）

# .github/workflows/ci.yml
name: CI
on: [pull_request]

permissions:
  id-token: write
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: Infisical/secrets-action@v1.0.7
        with:
          method: "oidc"
          identity-id: ${{ vars.INFISICAL_CI_IDENTITY }}
          project-slug: my-saas-app
          env-slug: development
          secret-path: /ci

      - uses: actions/setup-node@v4
        with: { node-version: 20 }

      - run: npm ci
      - run: npm test
      # process.env 已含所有 ci secret

步驟 4：CD（merge to main → K8s deploy）

# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: registry.acme.com/my-saas-app:${{ github.sha }}
      # K8s 部署：用 sealed kubeconfig + kubectl set image
      - run: |
          kubectl set image deployment/my-saas-app \
            app=registry.acme.com/my-saas-app:${{ github.sha }} \
            -n production
          kubectl rollout status deployment/my-saas-app -n production

步驟 5：K8s production manifest

# 1. SA + 認證對映
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-saas-app
  namespace: production
---
# 2. InfisicalSecret CRD：拉 production secret
apiVersion: secrets.infisical.com/v1alpha1
kind: InfisicalSecret
metadata:
  name: my-saas-app-secrets
  namespace: production
spec:
  hostAPI: https://app.infisical.com/api
  resyncInterval: 60
  authentication:
    kubernetesAuth:
      identityId: <k8s-prod-operator id>
      serviceAccountRef:
        name: my-saas-app
        namespace: production
  managedSecretReference:
    secretName: my-saas-app-env
    secretNamespace: production
    creationPolicy: Orphan
  scope:
    secretsScope:
      projectSlug: my-saas-app
      envSlug: production
      secretsPath: /app
      recursive: false
---
# 3. Deployment + 自動 reload
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-saas-app
  namespace: production
  annotations:
    secrets.infisical.com/auto-reload: "true"
spec:
  replicas: 3
  selector:
    matchLabels: { app: my-saas-app }
  template:
    metadata:
      labels: { app: my-saas-app }
    spec:
      serviceAccountName: my-saas-app
      containers:
        - name: app
          image: registry.acme.com/my-saas-app:latest
          envFrom:
            - secretRef:
                name: my-saas-app-env

結果：

  • 開發者本機：瀏覽器 SSO 一次，之後 infisical run 即可
  • CI：OIDC，零長期 token
  • Production：Operator 自動同步、secret 變更自動 rolling restart
  • 整條鏈不存任何 long-lived secret

31.2　微服務環境的 dynamic DB credentials

場景 DevOps/SRE

10 個微服務都要連同一個 PostgreSQL。傳統做法：每個服務都拿同一組 DB credential，Vault/Infisical 內存一筆 secret。問題：

  • credential 永遠有效，外洩 blast radius 是「永遠」
  • 10 個服務都用同一帳號，資料庫端無法分辨誰下了那個慢查
  • 輪替時 10 個服務同時要 reload

用 Dynamic Secret 改寫：每個服務啟動時拿一份專屬 + 短效的 DB credential，用 1 小時即廢，過期前自動 renew。

實作

步驟 1：在 Infisical UI 建立 PostgreSQL Dynamic Secret 設定：

  • 連線資訊：用一個有 CREATE ROLE 權限的 admin 帳號
  • 建立 user 的 SQL（範本）：CREATE ROLE "{{username}}" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT readonly TO "{{username}}";
  • 銷毀 user 的 SQL：DROP ROLE "{{username}}"
  • Default TTL：1h，Max TTL：24h

步驟 2：每個微服務的 K8s manifest 用 InfisicalDynamicSecret：

apiVersion: secrets.infisical.com/v1alpha1
kind: InfisicalDynamicSecret
metadata:
  name: order-service-db
  namespace: production
spec:
  hostAPI: https://app.infisical.com/api
  authentication:
    kubernetesAuth:
      identityId: <order-service identity>
      serviceAccountRef:
        name: order-service
        namespace: production
  dynamicSecret:
    secretName: postgres-readonly
    projectId: my-saas-app
    environmentSlug: production
    secretsPath: /db
  leaseTTL: "1h"
  leaseRevocationPolicy: Revoke
  managedSecretReference:
    secretName: order-service-db-creds
    secretNamespace: production

步驟 3：應用程式啟動時讀 order-service-db-creds 的 username/password 連 DB；Operator 在 lease 到期前自動 renew/重發 lease，更新 K8s secret，pod 自動 reload。

結果驗證

# 在 PostgreSQL 端查當前 active role
psql -c "SELECT rolname, rolvaliduntil FROM pg_roles WHERE rolname LIKE 'dyn_%';"

# 預期看到 10 個 dyn_xxx 帳號，每個 valid until 不同
# 各自對應一個微服務的當前 lease
這個設計帶來的安全價值

萬一 order-service 被入侵，攻擊者拿到的 DB credential 最長活 1 小時，且只能 readonly（依 SQL 範本控制權限）。其他 9 個微服務的 credential 攻擊者拿不到。事故 blast radius 從「全 DB 寫入權限 + 永久」縮成「order-service 範圍 + 1 小時」。

31.3　內部 PKI 簽發 mTLS 憑證自動續發

場景 DevOps/SRE

內部 50 個微服務之間走 mTLS（client cert 認證 server cert）。每個服務需要自己的 cert，90 天到期。手動管理是地獄；要的是：

  • 新服務 deploy 時自動拿 cert
  • Cert 到期前自動續發、不需 ops 介入
  • Cert 撤銷時要立即生效

架構：Internal CA + cert-manager + ACME

實作步驟

步驟 1：在 Infisical 建立 PKI Project，建 Root CA + Intermediate CA（第二卷 8.2 節）。

步驟 2：建 Certificate Profile k8s-services：

  • Issuing CA：Intermediate CA
  • Policy：CN 必須 *.svc.acme.local、TTL 90 天、SAN 允許 DNS
  • Enrollment Method：ACME
  • 輸出 ACME directory URL 與 EAB credentials

步驟 3：K8s 安裝 cert-manager，建 ClusterIssuer：

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: infisical-internal
spec:
  acme:
    server: https://app.infisical.com/api/v1/pki/acme/<profile-id>/directory
    email: pki@acme.com
    privateKeySecretRef:
      name: infisical-acme-account
    externalAccountBinding:
      keyID: ${EAB_KID}
      keySecretRef:
        name: infisical-eab
        key: secret
    solvers:
      - http01:
          ingress:
            class: nginx

步驟 4：每個服務在自己 namespace 建 Certificate CR：

apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: order-service-tls
  namespace: production
spec:
  secretName: order-service-tls
  duration: 2160h        # 90d
  renewBefore: 360h      # 15d 前 renew
  issuerRef:
    name: infisical-internal
    kind: ClusterIssuer
  commonName: order.svc.acme.local
  dnsNames:
    - order.svc.acme.local
    - order.production.svc.cluster.local

步驟 5：Pod 掛載 cert：

volumes:
  - name: tls
    secret:
      secretName: order-service-tls
volumeMounts:
  - name: tls
    mountPath: /etc/tls
    readOnly: true

cert-manager 在 75 天時自動續發，新 cert 寫進同 K8s Secret，pod 透過 reloader 重啟。整套流程零 ops 介入。

撤銷流程

當服務被汰除或私鑰外洩：在 Infisical UI Certificates 頁找到該 cert，按 Revoke。Infisical 立即更新 CRL，其他服務下次驗證時會拒絕該 cert。

31.4　跨團隊 Approval Workflow 設計

場景 DevOps/SRE

三個團隊（backend / data / platform）共用 production secret。希望任何 production secret 變更：

  • 必須有申請者所屬團隊以外的 reviewer 簽核（避免 self-review）
  • 2 人核准才生效
  • Slack 即時通知所有 reviewer
  • 緊急情況可由 platform admin break-glass，但所有 break-glass 進獨立 audit

實作

步驟 1：建 Custom Project Role 區分團隊：

  • backend-engineer：對 /services/* 有 read/create/update（除 /services/data/*）
  • data-engineer：對 /services/data/* 有 read/create/update
  • platform-admin：所有 path read，有 break-glass approve 權限

步驟 2：在 Project Settings → Approval Workflows 建 Policy：

Policy 1: Production Backend
  Environment: production
  Folder Path: /services/*  (排除 /services/data/*)
  Required Approvals: 2
  Reviewer Group:
    - data-engineer 角色全員
    - platform-admin 角色全員
  Self-Approval: 禁止

Policy 2: Production Data
  Environment: production
  Folder Path: /services/data/*
  Required Approvals: 2
  Reviewer Group:
    - backend-engineer 角色全員
    - platform-admin 角色全員
  Self-Approval: 禁止

Policy 3: Break-Glass (Production)
  Environment: production
  Folder Path: /
  Required Approvals: 1
  Reviewer Group: platform-admin only
  Self-Approval: 禁止
  Tag: break-glass

步驟 3：Workflow Integration → Slack，把通知 push 到 #secret-approvals。

步驟 4：Audit Log Stream → Datadog / SIEM，特別 alert：

  • 所有 break-glass 標記的 approval（標記 high severity）
  • 同一 reviewer 在短時間內核准多個申請（疑似橡皮圖章）
  • policy 本身被修改的事件

實際使用 walkthrough

  1. backend 工程師 Alice 提交 production /services/api/STRIPE_KEY 變更。
  2. 系統依 Policy 1 標記為待審，通知 #secret-approvals。
  3. data 團隊 Bob、platform-admin Carol 收到通知。
  4. Bob 在 UI 查看 diff，按 Approve。
  5. Carol 同樣按 Approve。
  6. 達到 2 核准，變更立即生效，建立新 secret version。
  7. 整段流程進 audit log，Datadog dashboard 顯示。

32.1　常見錯誤與解法

CLI / SDK 錯誤

「Failed to load Infisical Token... no authentication method provided」

症狀：CLI 或 K8s Operator 啟動時 panic 無法登入。

根因：Identity 已建立但未配置任何 Auth method，或 credentialsRef 指向的 K8s Secret 缺少欄位。

解法：

  • UI 確認 Identity → Auth → 至少有一個 method 已啟用（Universal / Kubernetes / OIDC 等）
  • K8s Secret 內 key 名拼寫對：clientId、clientSecret（注意大小寫）
  • Operator log：kubectl logs -n infisical-operator-system deploy/infisical-secrets-operator

「Missing environment or workspace id」

症狀：Operator 拉 secret 失敗，日誌出現 statusCode 400。

根因：InfisicalSecret CRD 內 projectSlug 拼錯、envSlug 不對、或 Identity 沒被加入該 Project。

解法：

  • UI 內找到 Project，URL 上的 slug 跟 CRD 對齊
  • environment slug 是「dev」「prod」這種短代號，不是顯示名稱
  • UI → Project Settings → Access Control → Machine Identities，確認 Identity 已加入並有 viewer 以上權限

「Forbidden: insufficient permission」

症狀：API 回 403，但 Identity 看起來權限沒問題。

可能根因 1：Identity 被加入 Project 但沒給 role（預設 no-access）。

可能根因 2：ABAC policy 拒絕（例如 IP 不在 allowlist）。

可能根因 3：Folder-level 權限設定阻擋。

解法：UI → Audit Log 查那次 forbidden 事件，metadata 會說明哪條規則拒絕的。

「jwt malformed」或「invalid token」

根因：access token 過期，或 AUTH_SECRET 在 Self-Host 重啟過程中被換掉，舊 token 全部失效。

解法：重新登入；Self-Host 維護要維持 AUTH_SECRET 不變。

Self-Host 部署錯誤

啟動後 secret 都是亂碼

根因：ENCRYPTION_KEY 跟原本不同——例如備份還原後忘了用同一把。

解法：找回原 ENCRYPTION_KEY 並重啟。沒備份就完全救不回來，只能砍掉重建。

K8s Helm 安裝後 pod CrashLoopBackOff

常見原因排查順序：

  1. kubectl logs 看真實錯誤訊息
  2. 確認 infisical-secrets K8s Secret 存在且 5 個必要 key（ENCRYPTION_KEY / AUTH_SECRET / DB_CONNECTION_URI / REDIS_URL / SITE_URL）齊全
  3. 從 pod exec 進去 nslookup <db host>，確認 DNS 解得到
  4. 確認 PG 已啟動且接受連線（kubectl exec -it pod -- nc -zv db-host 5432）
  5. schema migration 需要 PG superuser-ish 權限（CREATE 等），確認 DB user 權限足夠

升級後出現「relation "..." does not exist」

根因：DB schema 比 image code 版本舊（migration 沒跑成功）或新（rollback 但 migration 不可逆）。

解法：

  • 升級時：確認 autoDatabaseSchemaMigration: true，看 init container log
  • 降版時：必須同時還原 PG 到升級前的 backup

整合相關錯誤

GitHub Actions OIDC「could not authenticate」

排查：

  1. Workflow 是否有 permissions: id-token: write？沒有則 GitHub 不簽 token。
  2. Identity OIDC config 的 Issuer 是否正確：https://token.actions.githubusercontent.com
  3. Subject 限制是否與當前 workflow 對得上？例如 repo:org/repo:ref:refs/heads/main，PR 觸發的 ref 不同
  4. Audience 是否一致？（在 Identity 設 infisical，secrets-action 預設也是 infisical）

K8s Operator「token reviewer JWT verification failed」

根因：通常是 system:auth-delegator ClusterRoleBinding 沒設好，或 EKS audience 不匹配。

解法：第四卷 16.3 節範例有完整 RBAC YAML；EKS 用戶看 16.4 節 audience 注意事項。

32.2　效能問題排查

API latency 突然飆高

從慢的那一層開始查：

  1. 網路：LB → API pod 是否有 packet drop？AZ 之間的延遲？
  2. API：Prometheus http_request_duration_seconds p99 對哪個 endpoint？
  3. Node.js event loop：nodejs_eventloop_lag_seconds > 0.1 = CPU 飽和或同步阻塞
  4. PG：慢查（pg_stat_statements）、connection pool 排隊（pg_pool_waiting）
  5. Redis：SLOWLOG 看慢命令；OOM 會把 lru 用掉拖慢 cache hit

secret get 慢

單筆 secret get 應該 < 50ms。慢的常見原因：

  • 用了 External KMS（CMK）→ 每次都打外部 KMS API，這是設計上的代價
  • Secret referencing 鏈太長（${dev.A} 引用 ${shared.B} 引用 ${global.C}）→ 每層都要 fetch
  • Audit log 寫入阻塞主流程 → 確認 audit log 走 BullMQ 異步

K8s Operator 同步太慢

Operator 預設 resyncInterval: 60，秒級延遲。降低延遲：

  • 調 resyncInterval 到 10 秒（成本：API 呼叫變多）
  • 啟用 secrets.infisical.com/auto-reload: "true" annotation，secret 變更立即重啟 pod
  • 對極時延敏感場景，考慮 Agent Injector 替代 Operator

32.3　Self-Host 常見坑

用了 Helm 內建 PG/Redis 上 production

後果：升級時 PVC 設定錯誤導致資料遺失、無 HA、無備份。

修正：第五卷 22.2 節範例配置外部 managed PG/Redis。

環境變數寫進 ConfigMap 而非 Secret

後果：ENCRYPTION_KEY、AUTH_SECRET 在 K8s 中被當 plain config 看待，etcd 內可被任何 namespace 的 admin 讀到。

修正：必須用 K8s Secret，並啟用 etcd encryption-at-rest。

SITE_URL 設錯

症狀：登入後 redirect 到錯誤網址；OAuth callback 失敗；email 連結點不開。

修正：SITE_URL 必須是使用者瀏覽器看到的對外 URL，含 https:// 與正確 domain。改完要重啟 pod。

備份只跑而沒驗證

後果：DR 那天才發現 dump 檔損毀或缺欄。

修正：每月固定還原到隔離環境並登入驗證（第五卷 24.2 節）。

沒同步保留 ENCRYPTION_KEY 與 PG 備份

後果：兩者拆散儲存看似分權安全，但必須同時取得才能還原——某次 DR 時找不到 KEY 就完蛋。

修正：把 ENCRYPTION_KEY 視為「保險箱鑰匙」，DR 流程文件要把「去哪裡取 KEY」清楚寫明，且至少 2 人知道。

33.2　本地開發環境

Dev 環境若登出後再登入失敗（500 error），通常是 dev DB 內 user 記錄與 cookie 不同步。解法：docker compose -f docker-compose.dev.yml down -v 砍掉 volume 重來。

33.3　Contributing 流程與 PR 規範

提 PR 前的 checklist

  • 已開 Issue 或 Discussion 討論過設計（大功能）
  • 分支從最新 main rebase
  • 程式碼通過 npm run lint 與 npm test
  • 新增功能附測試（單元 + 整合）
  • 更新對應 docs（docs/ 內 mdx）
  • commit message 用 conventional commits（feat: / fix: / chore:）
  • PR 描述含「為什麼」「做了什麼」「怎麼測」

EE 程式碼的注意事項

backend/src/ee/ 內是 EE License 程式碼，貢獻 PR 要：

  • 簽 CLA（首次貢獻時 PR bot 會引導）
  • 重大 EE 功能建議先聯絡 maintainer 對齊
  • OSS 貢獻不會被綁進 EE 條款，但 EE 區的修改授權方式不同

  • Slack：官方 Infisical Users 工作區（從 infisical.com/slack 申請邀請）

  • GitHub Issues：bug、明確的功能 issue

APPENDIX D

詞彙表 (Glossary)

詞彙說明
ABAC (Attribute-Based Access Control)依使用者 / 資源屬性決定存取權的模型；對 RBAC 的補強。
ACME (RFC 8555)自動憑證簽發協定，cert-manager / Let's Encrypt 等用。
Approval Workflow對 secret 變更或 access 申請設定多人審批的流程。
Audit Log Stream把 audit log 即時推送到外部 SIEM。
Break-glass緊急情況下繞過正常流程的特殊管道，所有 break-glass 必入 audit。
CMK (Customer-Managed Key)由客戶自管 root key（外部 KMS）。
CRD (Custom Resource Definition)K8s 自訂資源類型；Infisical Operator 提供 InfisicalSecret 等 CRD。
CRL (Certificate Revocation List)已撤銷憑證清單。
CSI (Container Storage Interface)K8s 標準介面；Infisical CSI Provider 把 secret 直掛 pod 不經 K8s Secret。
Dynamic Secret每次申請都產生新的、短效 credential。
EAB (External Account Binding)ACME 的客戶端綁定機制。
EE (Enterprise Edition)Infisical 商業授權版本。
EST (RFC 7030)面向 IoT 的憑證註冊協定。
FolderProject 內的 secret 分組單位，是真實的權限邊界。
Gateway部署在內網、用反向 SSH tunnel 讓 Cloud 連回私網資源。
Identity身分抽象，分 User Identity（人）與 Machine Identity（機器）。
LeaseDynamic Secret 的一次發放 + TTL。
Lockout連續失敗認證後鎖定機制（防 brute-force）。
Machine Identity機器身分，配多種 Auth method 取代舊式 Service Token。
OIDC (OpenID Connect)基於 OAuth 2.0 的身分協定，可用於 user SSO 或 machine OIDC Auth。
PAM (Privileged Access Management)對特權帳號的存取管理 + session 錄製。
PIT (Point-in-Time Recovery)把 environment 還原到歷史快照的時間點。
PKI (Public Key Infrastructure)憑證簽發、續發、撤銷的整套基礎設施。
RBAC (Role-Based Access Control)角色式存取控制。
RelayGateway tunnel 的中介伺服器，可由 Cloud 提供或 Org 自建。
Rotation把同一支長期 credential 換新值。
SCEP面向網路設備的憑證註冊協定。
SCIM跨系統使用者生命週期同步協定。
Secret Reference用 ${env.NAME} 在一個 secret 內引用另一個 secret 的值。
Secret Sync單向把 Infisical secret 推到外部平台（AWS / Vercel 等）。
Secret Zero「為了拿 secret 而需要的另一個 secret」這個矛盾，OIDC 是解法。
Service Token舊式機器認證 token，已 deprecated。
SPIFFECNCF 雲原生工作負載身分標準。
Universal AuthMachine Identity 的通用認證法（client ID + secret）。
