卷首語

密碼、API 金鑰、資料庫連線字串、TLS 憑證、SSH 私鑰——這些 secret 是整個資訊系統最敏感的資產，也是攻擊者最想拿到的東西。但在多數團隊裡，它們散落在 .env 檔、Slack 訊息、Vault、Jenkins 變數、Kubernetes Secret、雲端控制台之間。當組織規模擴張、CI/CD pipeline 複雜化、AI agent 開始自動化操作後，「secret sprawl（祕密蔓延）」就成了治理的死角。

Infisical 是一個開源、一站式的 secret 管理平台，把 Secrets Management、Secrets Scanning、Certificate Management（PKI）、Key Management（KMS）、Privileged Access Management（PAM）、SSH 整合在同一個產品裡。它的設計目標是：讓開發者像使用一般工具一樣輕鬆，又同時讓 DevOps、SRE、安全團隊能用統一的方式做治理、稽核、輪替與回收。

這份《Infisical 完整教學手冊》共分為七卷，依「由淺入深、由開發到維運」的順序展開。第一卷是入門篇，假設讀者完全沒接觸過 Infisical。讀完之後，你應該能：

  • 清楚說出 Infisical 是什麼、解決哪些問題、和傳統做法的差異
  • 分辨 Infisical Cloud 與 Self-Host 的取捨點，做出對自己團隊正確的決策
  • 在本機 5 分鐘啟動一個可以操作的 Infisical 實例
  • 掌握 Organization、Project、Environment、Folder、Secret、Identity、Role 等核心名詞，後續所有章節將以這些術語為基礎

1.1　什麼是 Infisical：定位與五大產品線

一句話定位 初學者

Infisical 是開源的「機敏資料治理平台」，把 secret、憑證、特權存取的整套管理流程整合進同一個產品。它定位的對象是整個工程組織——不只給安全團隊用，也給每天寫程式的開發者、跑 pipeline 的 DevOps、扛 production 的 SRE。

類比一下：如果說 GitHub 是「程式碼的中央交換台」、Docker Hub 是「容器映像的中央交換台」，那麼 Infisical 想做的，就是「機敏資料的中央交換台」。

五大產品線一覽

Infisical 並不是單一功能的工具，而是由以下五個緊密整合的產品線組成。它們可以選用，但底層共用同一套 Identity、權限、稽核機制：

產品線 解決什麼問題 典型使用者
Secrets Management 集中存放、版本控管、輪替、動態簽發應用程式 secret（API key、DB credentials 等），並把它們同步到任何需要的地方。 幾乎所有人
Secrets Scanning 掃描程式碼、CI pipeline、檔案系統中是否有硬編碼 secret，預防外洩；超過 140 種 secret 類型可辨識。 開發者、Security
Certificate Management（PKI） 內部 CA 階層建置、外部 CA（Let's Encrypt、DigiCert、Microsoft AD CS、Venafi TPP 等）整合、X.509 憑證生命週期、ACME / EST API 自動簽發、CRL 與告警。 SRE、Security、平台工程
KMS（Key Management Service） 集中管理對稱金鑰，提供 encrypt / decrypt API 給應用程式使用，並可作為 Infisical 自身的後端加密金鑰來源（CMK）。 後端工程、Security
PAM（Privileged Access Management） 管理對資料庫、伺服器、特權帳號的存取，提供以政策驅動的批准流程、session 錄製、命令攔截。 DevOps、SRE、Security

除了這五條產品線之外，平台還有一條相對獨立的延伸：Infisical SSH——以憑證式短效 credential 取代靜態 SSH key 來管理基礎設施登入。這條線在第二卷會專章說明。

對開發者來說，最直觀的價值 開發者

對開發者而言，Infisical 最直接的好處是「不再把 .env 提交到 Git」。本機開發時用 infisical run -- npm start 把 secret 注入到應用程式環境變數；CI/CD 上用同一個 CLI 或 GitHub Action / GitLab Component 取得；上線到 Kubernetes 用 Operator 同步成 Secret 物件。整套流程不需要為每個環境寫不同的設定碼。

對 DevOps/SRE 來說，治理面的價值 DevOps/SRE

對維運與安全團隊而言，價值在於「把分散的治理面收攏到單一平台」：

  • 輪替（Rotation）：DB 密碼、雲端 IAM credential 排程自動換發，不再有「全公司都用同一組永久 root 金鑰」這種事。
  • 動態簽發（Dynamic Secrets）：應用程式或 pipeline 啟動時才生出短效 credential，用完即廢。
  • 稽核（Audit Logs）：誰、何時、從哪、做了什麼，全部入帳，可以匯流到 Datadog、Splunk、S3。
  • 多重審批（Approval Workflows）：production 環境的 secret 變更需要 reviewer 簽核才生效。
  • Identity 統一：CI、Kubernetes pod、AWS lambda、developer 都走同一套 RBAC，不用每個入口寫一份權限。

1.2　為何需要它：Secret Sprawl 問題與工具對比

Secret Sprawl 是什麼 初學者

「Secret sprawl」字面意義是「secret 的蔓延」。隨著一家公司產品成長，secret 會以一種非常難以察覺的方式擴散：

  • 第一年：放在開發者本機的 .env，順手寄到 Slack 給同事。
  • 第二年：放進 GitHub repo 的 secret、CI 的 variable、Kubernetes Secret、各種雲端服務的環境變數。
  • 第三年：跨多雲、多區域、多 cluster；某些 secret 過期了沒人知道，某些 secret 被 commit 到舊 commit 還沒清掉。
  • 第四年：發生事故，調查時發現「我們有幾百個地方需要輪替這支金鑰，沒人說得出全貌」。

這個失控過程就是 secret sprawl。它不只是技術問題——更是治理問題。Infisical 想處理的核心痛點，就是把這條失控的擴散曲線壓回來。

Infisical 與其他常見方案的對比

下表整理開發團隊常見的選項，讓你判斷自己現在處於哪一格、要不要往 Infisical 這格走：

不適用的情境 DevOps/SRE

Infisical 不是萬靈丹，下面幾個情境要謹慎評估：

  • 嚴格 air-gapped、零外網連線且必須 FIPS-validated 全鏈路：可走 Self-Host + FIPS image，但要評估維運能量。
  • 需要 HSM 後端：目前 KMS 對 HSM 的整合主要透過 EE 提供，需要與商務團隊談授權。
  • 主用情境是「使用者個人密碼管理」：那是 1Password / Bitwarden 的領域，Infisical 不是給人記網路銀行密碼用的。

1.3　開源授權與 EE 商業版差異

授權架構 初學者

Infisical 採用「open core」模式：repo 主體以 MIT License 開源，可以自由修改、商用、再散佈；但 repo 內 ee/ 目錄下是企業功能，使用需要商業授權（Infisical 的 EE License）。

哪些功能屬於 EE、哪些已下放到 OSS，是會隨版本演進的。實際採購或部署前，請以 infisical.com/pricing 與 Self-Host EE 文件 為準，並考慮直接寄信至 sales@infisical.com 確認。

授權的實務影響 DevOps/SRE

對 SRE 而言，授權差異會影響三件事，採購前要先確認：

  1. SSO 整合方式：OAuth 是 OSS，但 SAML / SCIM / OIDC group sync 多屬 EE。如果公司已強制 SSO，這條會直接決定能不能落地。
  2. Approval Workflow：production secret 變更需要簽核、access request 流程，這些通常是合規必備，但屬於 EE。
  3. Audit Log 保留與輸出：OSS 提供基本 audit log，但要長期保留、串到 SIEM（Datadog / Splunk / S3）多屬 EE。

1.4　Cloud vs Self-Host：部署模型如何選

兩種模式 初學者

Infisical 提供兩種使用形態：

  • Infisical Cloud：托管服務，網址 app.infisical.com。註冊即用，由 Infisical 公司負責升級、可用性、底層安全。
  • Self-Hosted：把 Infisical 部署到自己的基礎設施（VM、Kubernetes、雲端、地端），完全掌握資料與運維，但相對地，升級、監控、補丁、災難復原也都是自己的責任。

兩者使用同一份開源核心程式碼，核心功能完全一樣。差別只在運維責任歸誰，以及 EE 功能授權形式。

Self-Host 看起來「免費」，但實際 TCO（Total Cost of Ownership）要算進：高可用 PostgreSQL、Redis、TLS 憑證、監控、告警、災難演練、版本跟版的人力。一個 production-grade Self-Host 通常需要至少 0.3～0.5 FTE。如果這份人力比訂閱費貴，Cloud 反而是經濟選擇。

本手冊涵蓋哪一種

本手冊兩種都會教。本卷後續第 2 章先用 Self-Host（Docker Compose）讓你 5 分鐘啟動實例做實驗——因為它不用註冊、不會用掉 Cloud 的免費額度，又能直接看清楚平台的全貌。等你熟悉之後，第五卷會專門討論 production-grade 的 Self-Host 部署方式（Kubernetes、Helm、Reference Architecture、災難復原），第二、三、四卷的功能與整合則 Cloud 與 Self-Host 通用。

本章重點回顧
  • Infisical 是開源、五大產品線（Secrets、Scanning、PKI、KMS、PAM）的一站式機敏資料治理平台。
  • 它要解的核心痛點是 secret sprawl——把分散的 secret 治理收攏到單一平台。
  • 授權採 open core 模式：MIT 開源核心 + EE 企業功能。
  • 使用形態有三種：Cloud、Self-Host OSS、Self-Host EE，並可組合 Cloud + Gateway。
  • 選擇 Cloud vs Self-Host 的關鍵問題是：合規 / 主權需求、團隊維運能力、內網整合需求。

2.1　註冊 Infisical Cloud 帳號

為什麼從 Cloud 開始 初學者

第一次接觸 Infisical 建議直接從 Cloud 開始：

  • 不用裝任何東西，瀏覽器即可體驗。
  • 免費方案就能完整玩到 secret 管理的核心功能。
  • 之後若要轉成 Self-Host，組織與專案的概念是共通的，學習不會浪費。

註冊步驟

  1. 瀏覽器開啟 https://app.infisical.com/signup。
  2. 用 Email + 密碼註冊，或選 Google / GitHub / GitLab SSO 登入。
  3. 第一次登入時會引導你建立 Organization（公司或團隊名稱）。
  4. 系統會提示下載一份「Emergency Kit / Recovery PDF」——務必下載並妥善保管。萬一忘記密碼又沒設 SSO，這份 PDF 是唯一的恢復方式。
Recovery Kit 是真的很重要

Infisical 採用端到端加密，密碼是金鑰派生的種子。如果你忘了密碼又遺失 Recovery Kit，技術上 Infisical 也無法替你解開資料——這是設計的安全特性。團隊使用時，建議所有成員都把 Recovery PDF 存到自己的密碼管理器或加密金鑰庫。

Infisical 的資料以五層樹狀結構組織。理解這張圖之後，後續所有功能都是「在這層做某件事」：

各層的職責

層級 對應現實概念 典型內容 邊界意義
Organization 公司、事業群 會員、帳單、SSO 設定、Machine Identity 身分與計費的最大邊界
Project 產品、團隊、應用程式組合 該產品線的 secret / 憑證 / 金鑰 / 政策 權限與工作隔離的主要單位
Environment 部署階段（dev / staging / prod） 同一組 secret name 在不同環境的不同值 讓同一支 key 在不同階段安全切換

Secret 單一鍵值對 name、value、metadata、tag、comment、版本 實際被 CLI / SDK / Operator 取用的資料

幾個常被誤解的點 開發者

1. Project 類型一旦選定就不能換。建立時選了 Secrets Management，後續就只能管 secret，不能在同一個 Project 內又管 PKI。要管 PKI 就建立另一個 Project（這是設計上有意的隔離）。

2. Environment 之間互相看不到對方的 secret。在 development 改了一個 secret 不會自動影響 production。但你可以用「Secret Referencing」在 production 引用其他 environment 的值（例如 ${dev.SHARED_KEY}），這個進階功能第二卷詳述。

3. Folder 不只是 UI 美化。Folder 是真正的權限邊界——可以對 /services/api 給某個 identity 讀寫、對 /services/billing 完全不允許。當 Project 變大時，folder 是切權限細粒度的關鍵手段。

4. Secret 的 name 必須是有效的環境變數名稱。實務上請守住 [A-Z][A-Z0-9_]* 慣例（全大寫底線分隔），因為大部分使用情境最終會被注入成環境變數，不規範的命名在 shell 會出錯。

給 SRE 的容量規劃 DevOps/SRE

要規劃自己的命名與切割策略，可以參考下面的常見原則：

  • 每個事業單位一個 Organization：當你有多個獨立計費或合規邊界的單位時。
  • 每個 microservice 一個 Project：給最強的權限隔離。缺點是 SRE 要管很多 Project。
  • 每個團隊一個 Project，內部用 folder 切 service：折衷做法，多數中型團隊採此。
  • 所有產品共用一個 Project，用 tag + folder 區分：適合很小的團隊（< 10 人）。
沒有絕對正確的切法

但「切錯不會丟資料」——Project 之間的 secret 可以匯出再匯入。建議從中間方案開始，等實際用了 1～2 個月再依摩擦點調整。

3.2　User Identity vs Machine Identity

兩種身分 初學者

Infisical 把所有「能登入並對平台做事」的東西都抽象成「Identity（身分）」。Identity 分兩種：

  • User Identity：代表一個真實人類（開發者、SRE、Security 工程師）。透過瀏覽器登入，可以走 Email + 密碼、Google / GitHub OAuth、SAML、OIDC、LDAP 等方式。
  • Machine Identity：代表一個系統角色（CI runner、K8s pod、AWS Lambda、應用程式）。透過 API 呼叫平台，使用各種雲原生或平台無關的認證方式（Universal Auth / AWS / GCP / Azure / K8s / OIDC / JWT 等）。

對照表

面向 User Identity Machine Identity
典型使用者 真實人類 CI、Pod、Function、應用程式
登入方式 瀏覽器 + 密碼 / SSO API + 認證憑證
典型認證方法 Email-Password、SAML、OIDC、LDAP Universal Auth、AWS、GCP、Azure、Kubernetes、OIDC、JWT
MFA 支援（TOTP / WebAuthn） 不適用
Token 壽命 JWT（短）+ Refresh Token 可設 TTL（短至幾分鐘、長至無限）
權限載體 個人 + 群組 role Identity 自身的 role
是否可入口稽核 有（含 IP、UA、device） 有（含 IP、Auth method、token id）

七大 Machine Identity Auth 方法總覽 開發者 DevOps/SRE

Machine Identity 為什麼有這麼多種 Auth 方法？因為「不同執行環境天生有不同的可信憑據」。下表是七種方法的速覽：

Auth 方法 底層機制 適用情境 優勢
Universal Auth Client ID + Client Secret 任何環境、最通用 不依賴雲廠商，地端 / 跨雲皆可
Token Auth 長壽命 token 低風險、簡單情境 最簡單，但 token 外洩風險最高
Kubernetes Auth Pod 的 ServiceAccount JWT K8s pod 內 無需配發 secret，pod 自帶身分
AWS Auth IAM 簽名請求（sts:GetCallerIdentity） EC2、Lambda、ECS 無需配發 secret，IAM Role 即身分
GCP Auth GCE / GKE / Cloud Run 的 ID Token GCP 任意服務 同 AWS Auth，原生 GCP IAM
Azure Auth Managed Identity Access Token Azure 任意服務 同 AWS Auth，原生 Azure AD
OIDC Auth OIDC ID Token GitHub Actions、GitLab CI、CircleCI 等支援 OIDC 的平台 無需配發 secret，pipeline 自帶身分
JWT Auth 自訂 JWT issuer 內部 IdP、自架 OIDC provider 最大彈性，但需自管 IdP

本卷只先建立印象，第二卷第 5 章會逐一示範實作。選擇原則：能用雲原生（K8s/AWS/GCP/Azure/OIDC）就不要用 Universal Auth；能用 Universal Auth 就不要用長壽 Token Auth——以「不需自己管 secret 來換取 secret」為最佳。

Service Token 是舊式機制

你可能在舊文件、舊程式碼或舊版本看到「Service Token」這個名詞。它是 Machine Identity 的前身，目前仍然支援但不建議在新專案使用。新專案請一律用 Machine Identity + Universal Auth（或更好的雲原生方法）。第六卷第 28 章會說明兩者差異。

3.3　Role / Permission / Policy 三層權限模型

三個動作面 初學者

Infisical 的權限設計分三層，從「最一般」到「最特定」：

  1. Role（角色）：把一組 permission 包起來、命名，方便指派給多個 identity。
  2. Permission（權限）：對某個資源（secret、folder、environment、project 設定等）能做什麼動作（read / create / update / delete）。
  3. Policy（政策）：對特定情境的補強規則——核准流程（Approval）、ABAC 屬性條件、臨時授權（Temporary Access）、額外特權（Additional Privileges）。
flowchart LR
  IDENT["Identity
User / Machine"] --> ROLE["Role
Admin / Developer / Custom"]
  ROLE --> PERM["Permission
secrets:read on /api"]
  IDENT -.補強.-> POL1["Approval Policy
prod 變更需 2 人核准"]
  IDENT -.補強.-> POL2["ABAC Policy
僅辦公室 IP 可讀"]
  IDENT -.補強.-> POL3["Temporary Access
3 小時臨時 admin"]
  IDENT -.補強.-> POL4["Additional Privilege
單次允許某操作"]

兩個層級的存取控制

Role 與權限可以掛在兩個層級：

  • Organization-level Access Control：管帳單、邀請成員、SSO 設定、Machine Identity 全域設定等。組織管理員需要這層的 admin role。
  • Project-level Access Control：管 secret、folder、environment、PKI 憑證等專案級資源。一個 user 可以在 ProjectA 是 admin、在 ProjectB 是 viewer，互不影響。

內建 Project Role 速覽

內建角色 典型權限 適用對象
admin 專案全部權限（含設定、成員、policy） Tech Lead、Platform 團隊
member 大部分讀寫，但無法改 policy / 成員 一般開發者
viewer 僅讀取（不能看 secret 值） 稽核、PM
no-access 無 已被加進專案但暫時禁用
Custom Role 自訂組合 需要 fine-grained 控制時

進階：ABAC 與其他補強政策 DevOps/SRE

RBAC 解決「誰能做什麼」，但有時候需要「在什麼條件下才能做」。這時 ABAC（Attribute-Based Access Control）登場：

  • 「只有從辦公室 IP 範圍才能讀 production」
  • 「只有 metadata.team=backend 的 identity 才能寫 /services/api 的 secret」
  • 「PROD 環境的變更，需要兩位以上不同 reviewer 簽核」

這些是平台層、跟 Role 正交的另一種規則，第二卷第 6 章會專章說明。

設計原則：先 RBAC，再加 ABAC

對多數團隊建議先把 RBAC 做好（Custom Role + Group），用 6～12 個月後再評估是否需要 ABAC。過早引入 ABAC 會讓權限模型變得難以調試（「我為什麼讀不到？」）。

3.4　端到端加密與 KMS 模式概念

Infisical 怎麼保護你的 secret 不外洩 初學者

對使用者而言，最關心的問題是「就算 Infisical 自己被駭，我的 secret 是不是仍然安全？」答案是：採取「多層金鑰階層 + AES-256-GCM 認證加密」設計，即使資料庫被偷，沒有 Root Encryption Key 也無法解密。

核心想法是：把資料加密分成「實際資料的金鑰」與「包裝那把金鑰的金鑰」，後者再被另一把更外層的金鑰包起來。要解密 secret 必須一路解到最外層、而最外層的 Root Key 只存在於伺服器啟動時提供的環境變數（或外部 HSM），不寫進資料庫。

四層金鑰各自的角色

金鑰 大小 來源 儲存位置 負責加密誰
Root Encryption Key 256-bit AES Operator 提供的環境變數，或 HSM 取得 環境變數 / HSM（永不存 DB） Internal KMS Root Key
Internal KMS Root Key 256-bit AES 實例首次啟動隨機生成 DB（被 Root Key 加密） Organization / Project Data Keys
Organization Data Key 256-bit AES 建立 Org 時隨機生成 DB（被 Internal KMS Key 加密） Org 級敏感資料（SSO/SAML/SCIM/Identity）
Project Data Key 256-bit AES 建立 Project 時隨機生成 DB（被 Internal KMS Key 或 External KMS 加密） 實際 secret、憑證、私鑰

為什麼這樣設計

這套階層的好處：

  • 資料庫被偷沒用：所有 Data Key 都是被加密狀態，沒有 Root Key 就解不開。
  • 租戶隔離：每個 Project 有自己的 Data Key，即使一個 Project 的金鑰外洩也不影響其他 Project。
  • 可換鎖：可以把某個 Project 的加密轉交給 External KMS（AWS KMS、GCP KMS、AWS CloudHSM），讓 root of trust 落在你自己的雲帳號裡。
  • FIPS 相容性：可選 FIPS 140-3 驗證的密碼學模組與 HSM-backed root key，符合金融、政府要求。

傳輸與認證 DevOps/SRE

除了 at-rest 加密，Infisical 也在傳輸與身分上有保護：

  • 傳輸加密：Infisical Cloud 全流量過 Cloudflare，最低 TLS 1.2。Self-Host 建議至少 TLS 1.3。
  • 每個請求都需驗證：所有 API 端點（除少數刻意公開的登入端點）都必須帶有效的 token。
  • JWT 儲存：Web UI 把 access token 放在記憶體，refresh token 放 HttpOnly cookie，搭配嚴格 CSP 防 XSS。
  • Machine Identity 限制：可設 TTL、IP 白名單、使用次數上限。
  • 速率限制：對 read / write / secrets 操作有可設定的 rate limit，防 abuse。

Zero-knowledge 與員工存取 DevOps/SRE

這是 Cloud 用戶常問的問題：「Infisical 員工能看到我的 secret 嗎？」

官方說明的精確版本：在你沒有明示授予 Infisical 存取權的前提下，Infisical 員工物理上無法看到 secret 的明文值——因為 Project Data Key 在伺服器運行時才解開、用完即棄，員工沒有 Root Key 環境變數的存取權。對 Self-Host 而言，這個信任邊界完全在你手上。

威脅模型不涵蓋的事

Infisical 的安全保證對以下情境不適用，這些是部署方必須自己處理的：

  • 對儲存後端的不受控存取（攻擊者直接拿到 DB shell）
  • 運行記憶體探測（DRAM dump 攻擊）
  • 客戶端被入侵（CI runner 中木馬導致認證憑據外洩）
  • 內部管理員濫權變更設定
  • 實體存取（伺服器被搬走）
  • 對員工的社交工程

本章重點回顧

這份心智地圖請隨手帶著
  • 資料階層五層：Organization → Project → Environment → Folder → Secret。
  • 身分有兩種：User Identity（人類）與 Machine Identity（系統），後者支援七種主流 Auth 方法。
  • 權限模型三層：Role 包 Permission，再用 Policy（Approval / ABAC / Temporary / Additional Privilege）補強。
  • 加密用四層金鑰階層 + AES-256-GCM，Root Key 不入 DB；可選 External KMS / HSM 改變信任根。
