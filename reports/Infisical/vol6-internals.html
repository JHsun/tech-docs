四個元件各自的職責

對比 HashiCorp Vault：Vault 內建 Raft 一致性協定 + 自家儲存後端，運維時要會調 Raft、處理 quorum loss。Infisical 不走這條路——直接用 PostgreSQL（誰都會運維）+ Redis。這也是為什麼 Infisical 的 production setup 比 Vault 簡單得多。

28.2　一次 secret get 的完整資料流

把整本書串起來最有效的方法：跟著一次「GET /api/v3/secrets/raw/DATABASE_URL」請求，看資料怎麼流動。

sequenceDiagram
  autonumber
  participant CL as Client (CLI/SDK)
  participant LB as Load Balancer + TLS
  participant API as Backend API
  participant PE as Permission Engine
  participant KE as KMS Engine
  participant PG as PostgreSQL
  participant RD as Redis (cache)
  participant AL as Audit Logger

  CL->>LB: HTTPS + Bearer access_token
  LB->>API: 內部 HTTP /api/v3/secrets/raw/DATABASE_URL
  API->>API: 解析 JWT, 驗證簽名 (用 AUTH_SECRET)
  API->>PE: 檢查 actor 對 project/env/path 是否有 secrets:read
  PE->>PG: 查 role + permission + ABAC condition
  PE-->>API: ALLOWED / DENIED

  alt DENIED
    API->>AL: 記錄 forbidden 事件
    API-->>CL: 403
  else ALLOWED
    API->>RD: 查 cache: secrets:proj:env:path:DATABASE_URL
    alt cache hit
      RD-->>API: ciphertext
    else cache miss
      API->>PG: SELECT ciphertext FROM secrets ...
      PG-->>API: ciphertext (AES-256-GCM)
      API->>RD: SET cache (TTL)
    end

    API->>KE: decrypt(ciphertext, project_data_key_id)
    KE->>KE: 取 ProjectDataKey
(被 Internal KMS Key 加密)
    KE->>KE: 用 Root Encryption Key 解 Internal KMS Key
    KE->>KE: 用 Internal KMS Key 解 ProjectDataKey
    KE->>KE: 用 ProjectDataKey 解 secret ciphertext
    KE-->>API: plaintext
    API->>AL: 記錄 get-secret 事件 (含 actor/IP/UA)
    API-->>LB: JSON {secretValue: "..."}
    LB-->>CL: HTTPS response
  end

幾個值得注意的設計細節 DevOps/SRE

  • Token 驗證走 AUTH_SECRET：JWT 簽名驗證是 stateless 的（不查 DB），這也是為什麼 token 撤銷需要把 token id 加進 deny list（存 Redis）才能即時生效。
  • Permission 檢查在解密之前：權限不過直接拒絕，不會無謂浪費 KMS 解密成本。
  • Redis cache 存的是 ciphertext，不是 plaintext。Redis 被入侵也只拿到密文。Cache TTL 通常很短（秒級），主要是減少 PG 壓力。
  • 解密在 server 內存發生：plaintext 在記憶體中存在，這就是為什麼 runtime memory intrusion 是官方 out-of-scope 的威脅。
  • Audit log 異步寫：先回應 client，audit log 走 background queue 寫入。這代表突發大量請求時 audit 會稍微延遲，但不會拖慢主要請求。

28.3　加密引擎細節

對稱加密原語 DevOps/SRE

Infisical 的所有對稱加密採用同一組原語：

  • 演算法：AES-256-GCM
  • Nonce 長度：96 bit（12 bytes）
  • Tag 長度：128 bit（GCM 認證標籤）
  • Nonce 來源：每次加密用 CSPRNG 產生新 nonce（避免 reuse）

每筆密文儲存的格式（簡化）：

+----------+------------+------------------+--------+
| KeyId    | Nonce(12B) | Ciphertext(N)    | Tag(16B)|
+----------+------------+------------------+--------+

其中 KeyId 指向用哪把 ProjectDataKey 加密

External KMS 模式（CMK）

啟用 Project-level CMK 後，那個 Project 的 ProjectDataKey 不被 Internal KMS 包，而是被你指定的 External KMS（AWS KMS / GCP KMS / Azure Key Vault）包。每次需要解 secret，Infisical server 會呼叫你的 External KMS 解出 ProjectDataKey，再用它解 secret。

這的設計含義：

  • External KMS 的所有 decrypt 呼叫都會留在你自己的 cloud audit log，提供額外可觀測性
  • 停用 External KMS key 等於凍結整個 project
  • Infisical Cloud 的員工從來無法解這個 project 的 secret，因為他們沒有你 KMS 的權限
  • 代價：每次解 secret 都打外部 KMS，延遲與成本要納入評估

28.4　Permission Engine 實作

權限解析的兩階段

每次操作會走兩階段：

  1. RBAC 階段：actor 的 role 是否有對應 resource + action 的允許？
  2. ABAC 階段（如果有 policy）：actor / resource 的 attributes 是否符合條件？

兩階段都通過才允許，任一階段拒絕即拒絕。

Permission 內部表達 DevOps/SRE

內部用類似 CASL.js 的「who-can-do-what-on-what」三元組表達：

{
  "subject": { "type": "user", "id": "u_xxx", "metadata": { "team": "backend" } },
  "action":  "secrets:read",
  "object":  { "type": "secret", "projectId": "p_xxx", "envSlug": "prod", "path": "/api" },
  "condition": [
    { "field": "subject.metadata.team", "operator": "eq", "value": "backend" },
    { "field": "context.ip", "operator": "in_cidr", "value": "10.0.0.0/8" }
  ]
}

條件評估全在 server 完成，不會把 condition 邏輯傳給 client。Client 只看到 ALLOWED / DENIED。

Service Token 與 Machine Identity 的差異深入

第一卷 3.2 節已介紹 Service Token vs Machine Identity 的選擇。從架構角度看，差異更明顯：

面向Service Token（舊）Machine Identity（新）
儲存形式單一 token string，hashed 存 DBIdentity 物件 + 多種 Auth method 設定 + Auth-issued JWT
權限模型固定 read/write，scope 寫死在 token完整 RBAC + ABAC，可隨時調權限不換 token
登入流程Token = JWT，直接帶用先用 Auth method（UA/K8s/AWS/...）登入，換得短效 access_token
撤銷整個 token 砍掉可撤 client_secret、單個 access_token、整個 identity
多 project一 token 對一 project + env一 identity 可加入多 project，各自不同 role

架構上 Service Token 是「一張長期票券」；Machine Identity 是「有不同登入方式的虛擬帳號」。後者更接近現代 IAM 設計，前者只保留以維持向後相容。

29.1　加密金鑰階層回顧

第一卷 3.4 與第六卷 28.3 已詳述四層金鑰階層。這裡濃縮成一張「責任邊界」表：

金鑰層誰負責外洩後果
Root Encryption Key Self-Host 由你管理；Cloud 由 Infisical 公司 + Cloud KMS 所有 secret 解密門戶開啟，但仍需要 DB 才能取出密文
Internal KMS Root Key 由 Infisical 自動管理，存在 PG 加密欄位 單獨外洩無用，需配合 Root Key
Org / Project Data Keys 同上 單獨外洩無用
Secret Plaintext 取出時短暫存在於 server 記憶體 取決於攻擊者進到 server 記憶體的能力

29.2　威脅模型 in-scope（平台保證的）

官方明確列為 in-scope 的威脅，Infisical 提供具體緩解：

威脅緩解機制
Eavesdropping（傳輸竊聽） Cloud 全流量過 Cloudflare TLS 1.2+；Self-Host 建議 TLS 1.3。Server ↔ PG / Redis 也都應啟用 TLS。
Tampering（資料竄改，at rest 或 in transit） AES-256-GCM 自帶認證標籤，每次解密都驗 integrity；不一致直接失敗並告警。
Unauthorized Access（無 auth/authz 的存取） 所有 endpoint（除少數登入）強制 token；MFA、IP allowlist、RBAC、ABAC、policy 多層把關。
Actions without Accountability（無稽核的操作） 每個 mutating 操作都進 audit log，含 actor、IP、UA、timestamp、event metadata。
Brute-force Authentication Lockout（3 次失敗鎖 5 分鐘）+ rate limit。WebAuthn 抗釣魚。
Insider Privilege Abuse（管理員濫權） Approval Workflow + Access Request + 完整 audit；EE 提供更細顆粒度的 separation of duties。
Unidentified Vulnerabilities 每年兩次第三方 pentest + 漏洞獎勵計畫；security@infisical.com 接收通報。

29.3　威脅模型 out-of-scope（使用者要自己處理）

同樣重要——以下是官方明確說「Infisical 不對這些情境提供保證」的威脅。誤以為平台會擋這些，是 production 事故的常見根因。

out-of-scope 威脅使用者該如何補
Uncontrolled Storage Access
攻擊者直接拿到 PG 資料		 PG 部署在私網、強制 TLS、minimal IAM、加密磁碟、定期 audit DBA 操作。Self-Host 不要把 PG 暴露公網。
Disclosure of Secret Presence
看到 secret 名稱即洩漏 metadata		 避免在 secret name 內含敏感資訊（例如 STRIPE_LIVE_KEY_PRODUCTION_2026）；用 generic 命名 + comment。
Runtime Memory Intrusion
探測 server 記憶體		 容器 / VM 隔離；不允許 host shell 接觸 production process；考慮使用 confidential compute (AMD SEV / Intel TDX)；FIPS 部署用 HSM 縮短記憶體中明文存在的時間。
Side-Channel Attacks
透過 timing / cache 推測金鑰		 硬體層補強：用支援 AES-NI 的 CPU；container 不要與不可信工作負載共宿主。
Compromised Client
CI runner / 開發者本機被入侵		 Identity 設嚴格 IP / TTL / Subject 限制；OIDC 取代長期 token；EDR 與 host hardening；MFA。
Internal Configuration Abuse
有 admin 權限的人惡意改設定		 強制 Approval Workflow 變更高敏感設定；Server Admin Console 操作必入 audit；定期 access review。
Physical Access
實體取走伺服器		 機房門禁；磁碟全盤加密；Cloud 用戶仰賴 cloud provider 的實體控制。
Social Engineering
釣魚、假冒、社交工程		 員工教育訓練；WebAuthn / hardware key MFA；通訊管道驗證流程；事故演練。
最常被誤解的一條：「Infisical Cloud 員工能不能看我 secret？」

正確答案：沒有授權的情況下，物理上做不到，但威脅模型上不算 zero-trust。Cloud 員工 ↔ Root Encryption Key 的存取受 Infisical 公司內部 SOC 2 / 流程控制保護。如果你需要的保證強度高於這個——例如金融、醫療對「永遠不能讓供應商看到」的硬要求——請走 Self-Host + External KMS（CMK）路線。

29.4　安全部署 Checklist

針對 Self-Host 的 production 部署，以下是實戰過的 checklist。每一項都是可勾選的具體動作：

金鑰與 secret

  • ENCRYPTION_KEY 是 32 字元 hex 隨機值（openssl rand -hex 16），非範本預設值
  • ENCRYPTION_KEY 至少有 3 份備份：HSM/Cloud KMS、離線冷儲存、主管 password manager
  • AUTH_SECRET 同樣為隨機 32B base64
  • SMTP password、DB password 全為隨機產生，不跟其他系統共用
  • 啟用 External KMS (CMK) 或 HSM 為 root key 後端（金融 / 醫療）

網路

  • Infisical pod / container 不直接對外，全走 LB
  • 強制 TLS 1.2+（Self-Host 建議 1.3）
  • PG / Redis 在私網，TLS 啟用
  • 對外 outbound 加白名單（SMTP、IdP、KMS、Sync 目的）
  • 啟用 CORS 限制（在 SITE_URL 控制）

身份與存取

  • 所有人類使用者強制 MFA（建議 WebAuthn）
  • SSO 走 SAML / OIDC，並啟用 SCIM 自動 deprovisioning
  • Instance admin 為 break-glass 帳號，日常不登入
  • CI 一律 OIDC Auth，不用長期 token
  • 所有 Identity 設嚴格 IP allowlist 與短 TTL
  • 內建 admin role 不被廣泛分配，多用 Custom Role

稽核與監控

  • Audit Log Stream 串到 SIEM（Datadog / Splunk / S3）
  • Prometheus metrics 採集，告警設置
  • OpenTelemetry tracing 啟用
  • 異常事件（admin 操作、policy 變更、large bulk delete）即時通知 Security Slack channel

備份與災難復原

  • 每日 PG full dump + WAL archive 至異地對象儲存
  • 備份每月測試還原（不只是「跑備份」，要驗證能還原）
  • 季度 DR drill
  • RTO / RPO 文件化

升級與漏洞

  • 每月跟版升級，先 staging 後 production
  • 訂閱 GitHub releases 與 security advisory
  • 有發現問題的內部回報流程，不在 GitHub 公開 issue 通報安全漏洞

29.5　漏洞回報流程

Infisical 有官方安全聯絡管道：

  • Email：security@infisical.com
  • 內容：問題描述、重現步驟、影響範圍、是否願意被列入 hall of fame
  • 不要做：不在 GitHub 公開 issue、不在 Slack / Discord 公開討論細節

遇到疑似 0-day 而你又是 production 用戶，建議同時：

  3. 觀察 audit log 是否已被利用
  4. 等官方 CVE / patch 公告

30.1　共通遷移策略

四階段法 DevOps/SRE

無論從哪個來源遷移，建議遵循「並行→驗證→切換→淘汰」四階段：

flowchart LR
  S0[T0
原平台
運作中]
  S1[T1
並行
secrets 同步進 Infisical]
  S2[T2
驗證
應用程式 dual read]
  S3[T3
切換
應用程式只讀 Infisical]
  S4[T4
淘汰
原平台關閉]
  S0 --> S1 --> S2 --> S3 --> S4

每階段建議至少維持 1 週，大型組織可能需要 1 季——絕對不要週五下班前一刀切。

遷移期共通注意事項

  • secret 名稱規範化：原平台命名可能很亂，遷入時是統一規約的好機會（如全大寫 + 底線）
  • 環境對映：原平台的 environment 名稱可能不同（development / dev / local），遷入時統一
  • 歷史版本：多數來源不能保留版本歷史，遷入後從 v1 重新累積
  • 靜態 vs Dynamic：原平台的 dynamic secret 不能直接搬，需要在 Infisical 重建設定

30.2　從 HashiCorp Vault 遷移

Vault 的不同

Vault 與 Infisical 有幾個概念差異要先對齊：

Vault 概念對應 Infisical
Mount path（如 kv/）Project + folder
Secret path（如 kv/data/myapp/db）Folder + secret name
Policy（HCL 語言）Custom Role + ABAC
Token / AppRoleMachine Identity（Universal Auth）
KV v2 版本歷史Infisical Versioning
Database Engine（dynamic）Dynamic Secrets（重建設定）
Transit EngineInfisical KMS
PKI EngineInfisical PKI

遷移腳本範例

#!/bin/bash
# vault-to-infisical.sh
# 從 Vault KV v2 mount 把所有 secret 搬進 Infisical

set -euo pipefail

VAULT_ADDR="https://vault.example.com"
VAULT_TOKEN="..."
VAULT_MOUNT="kv"

INFISICAL_PROJECT_ID="..."
INFISICAL_ENV="prod"
INFISICAL_CLIENT_ID="..."
INFISICAL_CLIENT_SECRET="..."

# 登入 Infisical
export INFISICAL_TOKEN=$(infisical login \
  --method=universal-auth \
  --client-id="$INFISICAL_CLIENT_ID" \
  --client-secret="$INFISICAL_CLIENT_SECRET" \
  --silent --plain)

# 列出 Vault 內所有 secret path
list_paths() {
  local path="$1"
  vault kv list -format=json "${VAULT_MOUNT}/${path}" 2>/dev/null | \
    jq -r '.[]' | while read -r entry; do
    if [[ "$entry" == */ ]]; then
      list_paths "${path}${entry}"
    else
      echo "${path}${entry}"
    fi
  done
}

# 對每個 path 取出 secret 並寫入 Infisical
list_paths "" | while read -r path; do
  echo "Migrating: $path"
  vault kv get -format=json "${VAULT_MOUNT}/${path}" | \
    jq -r '.data.data | to_entries[] | "\(.key)=\(.value)"' | \
    while IFS='=' read -r key value; do
      infisical secrets set "${key}=${value}" \
        --env="${INFISICAL_ENV}" \
        --path="/${path%/}" \
        --projectId="${INFISICAL_PROJECT_ID}"
    done
done

echo "Migration complete. Verify in Infisical UI."
Dynamic Secret 不能 1:1 搬

Vault 的 Database Engine、AWS Engine 等動態 secret 設定不能直接匯出。要在 Infisical 端按第二卷 4.4 節步驟重建對應 dynamic secret 設定，並讓應用程式逐步切過去。整個遷移期間舊 lease 照跑、新 lease 從 Infisical 拿。

30.3　從 AWS Secrets Manager 遷移

#!/bin/bash
# asm-to-infisical.sh

INFISICAL_PROJECT_ID="..."
INFISICAL_ENV="prod"
PREFIX="prod/"

aws secretsmanager list-secrets \
  --filter Key=name,Values="${PREFIX}" \
  --query 'SecretList[].Name' \
  --output text | tr '\t' '\n' | while read -r name; do
    value=$(aws secretsmanager get-secret-value \
      --secret-id "$name" \
      --query SecretString --output text)
    # 把斜線轉成 folder path
    short_name=$(echo "$name" | sed "s|^${PREFIX}||" | tr '/' '_' | \
      tr '[:lower:]' '[:upper:]' | tr -c 'A-Z0-9_' '_')
    infisical secrets set "${short_name}=${value}" \
      --env="${INFISICAL_ENV}" \
      --projectId="${INFISICAL_PROJECT_ID}"
done

注意 ASM 的 secret 經常是 JSON object，需要先 jq 拆成 key=value：

# JSON secret 拆解
value_json=$(aws secretsmanager get-secret-value --secret-id "$name" \
  --query SecretString --output text)
echo "$value_json" | jq -r 'to_entries[] | "\(.key)=\(.value)"' | \
  while IFS='=' read -r k v; do
    infisical secrets set "${k}=${v}" --env=prod
  done

30.4　從 Azure Key Vault 遷移

#!/bin/bash
# akv-to-infisical.sh

VAULT_NAME="acme-prod-kv"

az keyvault secret list --vault-name "$VAULT_NAME" \
  --query '[].name' -o tsv | while read -r name; do
    value=$(az keyvault secret show --vault-name "$VAULT_NAME" \
      --name "$name" --query value -o tsv)
    # AKV name 用 dash，Infisical 慣用底線
    inf_name=$(echo "$name" | tr '-' '_' | tr '[:lower:]' '[:upper:]')
    infisical secrets set "${inf_name}=${value}" --env=prod
done

30.5　從 Doppler / 1Password / .env 遷移

Doppler

# 用 Doppler CLI 匯出
doppler secrets download --no-file --format=json > doppler.json

# 轉成 .env 再用 infisical secrets set --file
jq -r 'to_entries[] | "\(.key)=\(.value.computed)"' doppler.json > .env.import
infisical secrets set --file=.env.import --env=prod
shred -u .env.import

1Password CLI

# 1Password CLI 取出 vault 內所有 item
op item list --vault Production --format=json | \
  jq -r '.[].id' | while read -r id; do
    op item get "$id" --format=json | \
      jq -r '.fields[] | select(.value != null) | "\(.label)=\(.value)"' >> .env.import
done
infisical secrets set --file=.env.import --env=prod
shred -u .env.import

純 .env 檔

最簡單的場景。直接：

infisical secrets set --file=.env.production --env=prod --projectId=$PID

# 完成後 shred 原檔，並從 git 歷史移除
git filter-repo --path .env --invert-paths
shred -u .env.production
本卷重點回顧
  • Infisical 由 Server / Clients / PostgreSQL / Redis 四元件組成；沒有自家 Raft，PG + Redis 是底層基石。
  • 一次 secret get 走 LB → API → 權限引擎 → cache/PG → KMS engine → audit。
  • 加密用 AES-256-GCM (96-bit nonce) + 四層金鑰階層；Root Key 不入 DB。
  • Permission 雙階段：RBAC 過了再走 ABAC condition。
  • 威脅模型 in-scope 與 out-of-scope 必須分清楚——平台保證的是 7 條，剩下 8 條要使用者自己處理。
  • 外部遷移走「並行→驗證→切換→淘汰」四階段，dynamic secret 不能直接搬。
