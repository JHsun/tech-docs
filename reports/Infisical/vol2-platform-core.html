4.1　Dashboard 操作：建立、引用、tag、註解

四種建立 secret 的方式 開發者

進到 Project 之後，建立 secret 有四種介面：UI、CLI、API、SDK。本節聚焦 UI 與 CLI，API 與 SDK 在第三卷。

UI 單筆建立：在 Secrets 頁籤點 Add Secret，輸入 key + value。

UI 批次匯入：點 ... 選 Import Secrets，可上傳 .env 檔，平台會把 key=value 解析後一次寫入。這是從舊專案遷移最快的路徑。

CLI 寫入：

# 設定單個 secret
infisical secrets set DATABASE_URL "postgres://user:pwd@host:5432/db"

# 批次設定
infisical secrets set KEY1=val1 KEY2=val2 KEY3=val3

# 從 .env 匯入
infisical secrets set --file=.env

API 寫入：

curl -X POST 'https://app.infisical.com/api/v3/secrets/raw/STRIPE_KEY' \
  -H "Authorization: Bearer $INFISICAL_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "workspaceId": "PROJECT_ID",
    "environment": "dev",
    "secretValue": "sk_test_xxx",
    "secretPath": "/services/billing"
  }'

Secret Referencing（secret 引用）

同一份 secret 經常需要在多個地方出現——例如 SHARED_DB_HOST 在 dev、staging、prod 都是同樣的值。直接複製貼上會違反「單一資料源」原則，這時用 secret referencing：

# 在 production 環境的 DATABASE_URL 內引用 dev 的 SHARED_DB_HOST
DATABASE_URL=postgres://app:secret@${dev.SHARED_DB_HOST}:5432/prod

# 引用同 environment 但不同 folder 的 secret
JWT_SIGNER=${shared.JWT_SECRET}

# 巢狀引用（最多 5 層）
FULL_URL=${dev.PROTOCOL}://${dev.HOST}:${dev.PORT}/${dev.PATH}

引用語法：${<environment-slug>.<secret-name>} 或 ${<folder-path>.<secret-name>}。引用會在 讀取時展開（fetch-time resolution），不是寫入時——所以被引用的 secret 改了，引用方下次讀就會拿到新值。

引用會增加可觀測性的複雜度

當稽核日誌顯示「get-secret DATABASE_URL」時，引用內的 SHARED_DB_HOST 也會出現在「dependent secret resolution」事件裡。除錯時要記得展開鏈條。建議引用層數控制在 2 層以內、避免跨太多 environment。

Tag、Comment、Metadata DevOps/SRE

除了 key 與 value，每個 secret 還能掛三種附加資訊：

欄位用途建議用法
Tag 分類標籤，可在 UI 過濾、寫 ABAC 政策時當條件 用 service:billing、severity:critical、owner:platform-team 等結構化 key:value
Comment 給人讀的備註 說明 secret 的用途、申請的工單號、輪替頻率、失效時的緊急聯絡人
Metadata 給機器讀的結構化資料 用於與外部系統同步時的對映欄位（例如 AWS Tag）

實務經驗：tag 一致化是大型團隊治理的關鍵。建議組織層級先定義 tag 規範（schema），全 Project 共用，例如：

# 推薦的 tag schema（公司層級規約）
service:<name>        # 屬於哪個服務
team:<name>            # 哪個團隊負責
severity:critical|high|medium|low
rotation:auto|manual|none
expires:YYYY-MM-DD     # 預期失效日（手動 secret 用）

Folder 與 Path

當 Project 內 secret 超過 30 個，UI 會變得難以瀏覽。Folder 解決這個問題，並且是真正的權限邊界：

# 在 dev 環境建立 folder 結構
infisical secrets folders create --path /services
infisical secrets folders create --path /services/api
infisical secrets folders create --path /services/billing
infisical secrets folders create --path /shared

# 把 secret 放到指定 folder
infisical secrets set DATABASE_URL "..." --path /services/api

# 列出某 folder 的所有 secret
infisical secrets --path /services/api

所有 path 從 /（root）開始算。Folder 之間的 secret 名稱可以相同（不同 path 是不同 namespace），但 同一 folder 內 secret 名稱必須唯一。

4.2　Secret Versioning 與 Point-in-Time Recovery

每次變更都自動存檔 開發者

每次修改 secret，Infisical 都會自動建立一個新版本。歷史版本永久保留（除非你手動清理）。在 UI 點任何 secret 的側欄，可以看到完整歷史時間軸：誰、何時、改了什麼、舊值是什麼。

用 API 取得指定版本：

# 取目前版本
infisical secrets get DATABASE_URL

# 取舊版本（version=3 表示第 3 個版本）
curl 'https://app.infisical.com/api/v3/secrets/raw/DATABASE_URL?\
workspaceSlug=my-proj&environment=prod&version=3' \
  -H "Authorization: Bearer $TOKEN"

Point-in-Time Recovery（PIT）DevOps/SRE

事故場景：開發者誤把 prod 的 50 個 secret 一鍵清空。怎麼救？

PIT Recovery 不是「還原單個 secret」，而是「把整個 environment 還原到某時間點的快照」。在 Project Settings → Snapshots 可以看到所有歷史快照，每個快照對應一個時間戳，按 Rollback to this snapshot 即可。

flowchart LR
  T1[T0
建立 secret A,B,C] --> T2[T1
修改 B]
  T2 --> T3[T2
新增 D]
  T3 --> T4[T3
誤刪 A,B,C,D]
  T4 -.PIT Recovery.-> T3
  T3 -.還原快照.-> R[T4
狀態 = T2]

PIT 還原會建立一筆新 commit（不是覆蓋歷史），所以還原本身也有 audit log，可再被回溯。

PIT 不是備份的替代

PIT 只在 Infisical 自身資料庫內運作。如果 PostgreSQL 整顆掛了或被刪庫，PIT 救不了你。Production 的 Self-Host 一定要做：定期 PG dump → 異地備份 → 演練還原。Cloud 用戶 Infisical 已負責這層備份。

4.3　Secret Rotation：自動輪替靜態 credential

Rotation 解決什麼 開發者

「每三個月輪替一次資料庫密碼」這種規定，靠人手做幾乎沒人會做。Secret Rotation 讓 Infisical 排程自動輪替密碼，新密碼直接寫回 secret，下游應用程式（透過 Operator / Agent / SDK）下次讀就拿到新值。

支援的輪替目標 DevOps/SRE

截至 v0.158，內建 rotator 支援：

Rotator輪替對象備註
PostgreSQL CredentialsDB user 密碼用 dual-user 機制無感切換
MySQL CredentialsDB user 密碼同上
MSSQL CredentialsDB user 密碼同上
Oracle DB CredentialsDB user 密碼同上
AWS IAM UserAccess Key同時刪除舊 key
Azure Client SecretApp Registration secret
LDAP PasswordLDAP user 密碼
Auth0 Client SecretAuth0 App secret

Dual-User 切換機制

大多數 DB rotator 採取 dual-user 設計，避免「輪替當下應用程式拿到舊密碼導致連線失敗」這個經典問題：

sequenceDiagram
  participant App as 應用程式
  participant Inf as Infisical
  participant DB as 資料庫
  Note over Inf: 輪替時刻 T1
  Inf->>DB: 建立 user_B + 設新密碼
  Inf->>Inf: 把 secret 更新為 user_B 的密碼
  App->>Inf: 讀 secret（拿到 user_B）
  App->>DB: 用 user_B 連線 ✓
  Note over Inf: 確認過渡期穩定
  Inf->>DB: 撤銷 user_A 密碼

這樣設計的好處：應用程式無論用快取的舊 secret 或新讀取的 secret，過渡期內都能正確連線。

實作：建立一個 PostgreSQL Rotation

  1. 左側選 Secret Rotations → Create New Rotation。
  2. 選 PostgreSQL Credentials，填入：
    • Connection：DB host、port、admin 帳密（用來建立 / 刪除 user）
    • Username Template：例如 app_user_{{random_suffix}}
    • Rotation Interval：60 天
    • Output Secret：要把新密碼寫到哪個 secret name（例如 DB_PASSWORD）
  3. 儲存後，下一次到期時 Infisical 自動執行；UI 顯示下次輪替時間與最近一次的執行紀錄。
輪替前先做這件事

啟用 rotation 前，先確認應用程式的「reload secret」行為。最佳做法：用 Infisical Agent 或 K8s Operator 接收 webhook 重啟 / reload；最差做法：應用程式啟動時讀一次就快取整個生命週期——這時 rotation 會直接斷服務。

4.4　Dynamic Secrets：即用即發的短效 credential

Dynamic Secret 與 Rotation 的差別 開發者

Rotation 是「把同一個長期 credential 換新」；Dynamic Secret 是「每次申請都生一組新的、用完即廢」。兩者解決不同層次的問題：

面向Static + RotationDynamic Secret
credential 數量一組長期每次請求一組
壽命數十天～數月數分鐘～數小時
失效後回收下一次輪替到期自動 revoke
典型情境application config（DB pool）job、CI、agent、人工臨時查詢
對下游的衝擊需 reload 機制每次 lease 都新建連線

支援的 Dynamic Secret 類型

  • 資料庫：PostgreSQL、MySQL、MSSQL、Oracle、MongoDB、Redis、Cassandra、Elasticsearch
  • 訊息中介：RabbitMQ
  • 雲端 IAM：AWS IAM、GCP IAM、Azure（透過 Service Principal）
  • SaaS：GitHub App、Snowflake、Atlas（MongoDB Cloud）
  • 金鑰：AWS KMS data key、SSH Key Pair

Lease 生命週期

sequenceDiagram
  participant Client as Client (App / CI)
  participant Inf as Infisical
  participant Target as 目標系統 (DB / Cloud IAM)
  Client->>Inf: 申請 dynamic secret (lease)
  Inf->>Target: 即時建立短效帳號 / token
  Target-->>Inf: 回傳 credential
  Inf-->>Client: 發出 credential (附 lease ID, TTL)
  Note over Client: 在 TTL 內使用
  alt TTL 到期前
    Client->>Inf: 主動 revoke / renew
    Inf->>Target: 撤銷 / 延長
  else TTL 到期
    Inf->>Target: 自動撤銷
  end

實作範例：PostgreSQL Dynamic Secret

# 1. 在 UI 建立 dynamic secret 設定
#    Project → Dynamic Secrets → Create
#    - Type: PostgreSQL
#    - Connection: 提供 admin 連線字串
#    - SQL Statements: 申請時要跑的 SQL（例如 CREATE USER ...）
#    - Default TTL: 1h
#    - Max TTL: 24h
#    - Username Template: dyn_user_{{random}}

# 2. 從 CLI 申請一個 lease
infisical dynamic-secrets lease create \
  --slug=postgres-readonly \
  --ttl=1h

# 輸出範例:
# Lease ID: dl_xxx
# Username: dyn_user_a1b2c3
# Password: tmpPass!8s7Hk
# TTL: 3600s

# 3. 用完 revoke
infisical dynamic-secrets lease revoke --id=dl_xxx
為什麼這是 secret 管理的最佳實踐

當你能用 dynamic secret 時，就不要用 static secret。即使有人複製了 credential 或 commit 到 repo，TTL 一過就無效，blast radius 從「永遠」縮成「幾小時」。Vault 把這項功能變成業界共識，Infisical 把它做得更好用。

Access Request：JIT 取得 prod 權限

場景：on-call SRE 平時沒有 prod read 權限，凌晨故障要排查時才需要。

  1. SRE 在 UI 點 Request Access，選環境 / folder / 期限（例如 4 hours）。
  2. 系統依 Approval Policy 通知 reviewer。
  3. 核准後，SRE 暫時獲得指定權限（內部以 Additional Privilege 實作）。
  4. 到期自動失效——不需要事後手動回收。

4.6　Secret Sharing：對外分享一次性連結

適用情境 開發者

偶爾你需要把一個 secret 傳給 Infisical 帳號之外的人——例如外部廠商、客戶、新進員工首次設定密碼。傳統做法是 Slack / Email 直接貼，非常糟糕（聊天紀錄永久保留、被搜尋、被同事看到）。

Secret Sharing 的設計：產生一個一次性連結，對方點開看到 secret 後連結即失效；同時可設過期時間、最大查看次數、是否需要密碼解鎖。

實作步驟

  1. UI 上方選單 → Secret Sharing → New Shared Secret。
  2. 填入：
    • Secret Value：要分享的內容
    • Expires In：過期時間（5 分鐘 ~ 30 天）
    • Max Views：最多被查看幾次（建議 1）
    • Password：是否需要密碼才能解（額外用其他管道告知對方）
  3. 產生連結，傳給對方。

背後加密設計

共享 secret 在伺服器是用獨立金鑰加密儲存（不是 Project KMS），且加密金鑰嵌在 URL 的 fragment（# 之後）裡。fragment 不會送到伺服器，所以 Infisical 自身的 log 也只看得到加密 ciphertext，看不到分享的明文。

本章重點回顧
  • UI / CLI / API / SDK 都能寫 secret，UI 適合試，CLI / API 適合自動化。
  • Secret referencing 用 ${env.NAME} 語法，但層數要克制。
  • Folder + Tag 是大型 Project 的治理骨幹。
  • Versioning 永久保留，PIT Recovery 還原整個 environment 到時間點，但不取代 PG 備份。
  • Rotation 是「換同一支」，Dynamic Secret 是「每次新發」。能用 Dynamic 就用。
  • Approval Workflows、Change Request、Access Request 三件事關係要分清楚，是合規的核心。
  • Secret Sharing 用 fragment-only key 設計，連 Infisical 自身也看不到明文。

SAML SSO 實作（以 Okta 為例）DevOps/SRE

  1. Infisical Organization Settings → Authentication → SAML → Set up SAML SSO，選 Okta。
  2. 把 Infisical 提供的 ACS URL 與 Audience URI（SP Entity ID） 填進 Okta 的 SAML App。
  3. 把 Okta 的 IdP Metadata XML 上傳回 Infisical（或填入 Issuer URL、SSO URL、X.509 Certificate）。
  4. Attribute Mapping：email、firstName、lastName 對映到 Okta 的對應 attribute。
  5. 啟用後，強制 SAML SSO 之前先用一個 Okta 帳號完整登入測試。
  6. 都通過後再 toggle Enforce SAML SSO——強制後所有使用者必須走 IdP，否則被踢出。
Lockout 救命門

強制 SSO 後若 IdP 設定錯誤，所有人會被鎖在外面。Infisical 提供 Admin Login Portal 在 /login/admin 路徑（例如 https://app.infisical.com/login/admin），允許 instance admin 用密碼登入處理。Self-Host 一定要記住這個救命門。

}

// Infisical 對映規則：
//   IdP group "platform-admin" → Infisical Org role "admin"
//   IdP group "engineering"    → Infisical Org role "member"

這讓 IdP 端的 group 異動能直接驅動 Infisical 權限變化，是大型企業的標準做法。

SCIM：自動帳號生命週期

SCIM（System for Cross-domain Identity Management）讓 IdP 端可以在以下時刻自動同步到 Infisical：

  • 新員工加入 IdP group → 自動在 Infisical 建立帳號並加入對應 Org role
  • 員工離職 IdP 停權 → 自動 deprovision Infisical 帳號（撤所有 token）
  • 部門調動 → 自動更新 Org role / Group membership

對於 100 人以上組織、合規需求高的場景，SCIM 幾乎是必備——它讓「離職後 secret 仍可被前員工取得」這種事故不可能發生。

5.2　Machine Identity 總覽

Identity 與 Service Token：用新的，不用舊的 開發者

歷史上 Infisical 有兩種機器認證：Service Token（已 deprecated）與 Machine Identity（現行標準）。差異：

Lockout 防 brute-force無支援的 Auth 方法預設啟用

新專案一律用 Machine Identity。 舊有 Service Token 仍可運作以保相容性，但官方已停止新功能投入並建議遷移。

Identity 數量規劃

常見問題：「我該為每個微服務建立一個 Identity 嗎？」

原則：以「blast radius（爆炸半徑）」決定，不是以服務數量決定。可以共用 Identity 的條件：

  • 所有共用者讀取的 secret 範圍相同
  • 運行在相同的信任邊界（同一個 K8s namespace / 同一個 cloud account）
  • 合規上不要求個別審計

反過來，必須分開的情境：

  • 不同 team 擁有的服務（即使讀取相同 secret）
  • 跨信任邊界（dev cluster 與 prod cluster）
  • 合規要求個別追蹤（PCI、HIPAA scope 內外）

Lockout（防 brute-force）

2026 新增功能：當某 Identity 在 30 秒內登入失敗 3 次，該 Auth method 會被鎖定 5 分鐘。預設啟用於 Universal Auth 與 LDAP Auth。可在 UI 關閉或調整。

5.3　11 種 Machine Identity Auth 方法逐一實作

選擇優先順序 DevOps/SRE

面對 11 種 Auth 方法不要慌，原則就一句：「能用工作負載原生的身分，就不要用人工配發的 secret」。優先順序：

  1. K8s pod → Kubernetes Auth
  2. EC2 / Lambda / ECS → AWS Auth
  3. GCE / GKE / Cloud Run → GCP Auth
  4. Azure VM / Function → Azure Auth
  5. Oracle Cloud → OCI Auth
  6. SPIRE / Workload Identity 框架 → SPIFFE Auth
  7. GitHub Actions / GitLab CI / 任何支援 OIDC 的 CI → OIDC Auth
  8. 地端 / VM / 自架服務 → Universal Auth
  9. 內部自架 IdP → JWT Auth
  10. 地端 LDAP user 重用 → LDAP Auth
  11. 最簡單但風險最高 → Token Auth

5.3.1　Universal Auth（地端 / 跨雲萬用）

UA 是最通用的方法。一組 Client ID + Client Secret，類似傳統 OAuth 2.0 client credentials flow。

# 步驟 1: 建立 identity 並啟用 UA（UI 預設就是 UA）

# 步驟 2: 拿 Client ID + Client Secret

# 步驟 3: 應用程式登入
curl -X POST 'https://app.infisical.com/api/v1/auth/universal-auth/login' \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "xxx-yyy-zzz",
    "clientSecret": "secret-value"
  }'
# 回傳 { "accessToken": "...", "expiresIn": 7200, "tokenType": "Bearer" }

# 步驟 4: 用 accessToken 呼叫 API
curl 'https://app.infisical.com/api/v3/secrets/raw?...' \
  -H "Authorization: Bearer $ACCESS_TOKEN"

UA 可設四個重要參數：

  • Access Token TTL（預設 30 天）：簽發的 access token 壽命
  • Access Token Max TTL：含 renew 的最大壽命
  • Access Token Max Number of Uses：access token 可被使用的次數
  • Token Period：周期性 token，可無限延長但每次只到 period——這是解 secret zero 的關鍵

5.3.2　Token Auth（最簡單但最危險）

就是一支長壽 token。配置最簡單：在 UI 直接產生，貼到應用程式。缺點明顯：token 一旦外洩等於 root 級別曝光。只在低風險、無法用更好方法的場景使用，TTL 越短越好。

5.3.3　Kubernetes Auth（K8s pod 用 ServiceAccount）

原理：每個 pod 都有 ServiceAccount JWT，K8s API server 可驗證它。Infisical 透過 TokenReview API 驗證 pod 提交的 SA token，驗證通過後就接受認證。

# 1. 在 K8s 集群建立 ClusterRoleBinding，給 Infisical 訪問 TokenReview API
kubectl create clusterrolebinding infisical-auth-delegator \
  --clusterrole=system:auth-delegator \
  --serviceaccount=infisical:infisical-reviewer

# 2. 在 Infisical UI 建立 K8s Auth identity，填：
#    - Kubernetes Host: K8s API server URL
#    - Token Reviewer JWT: 上一步 SA 的 token
#    - Allowed Service Account Names: my-app
#    - Allowed Namespaces: production
#    - Allowed Audience: 必填，例如 "infisical"

# 3. Pod 內讀取自己的 SA token，登入 Infisical
TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
curl -X POST 'https://app.infisical.com/api/v1/auth/kubernetes-auth/login' \
  -H "Content-Type: application/json" \
  -d "{ \"identityId\": \"...\", \"jwt\": \"$TOKEN\" }"

實務上你不會手寫這段——K8s Operator 會自動處理。

5.3.4　AWS Auth（EC2 / Lambda / ECS 用 IAM Role）

原理：AWS SDK 在 EC2 / Lambda 內可以呼叫 sts:GetCallerIdentity，回傳目前 IAM Role。Infisical 重簽這個請求驗證來源真實。

# 在 Infisical 配置：
# - Allowed Principal ARNs: arn:aws:iam::123456789:role/MyAppRole
# - STS Endpoint: 預設 sts.amazonaws.com（中國區改 cn）

# Lambda 內：
import requests, boto3
session = boto3.Session()
creds = session.get_credentials()
# Infisical SDK 自動帶上簽名請求
import infisical_sdk
client = infisical_sdk.InfisicalClient()
client.auth.aws_iam.login(identity_id="...")
# 之後 client.secrets.get_secret(...) 即可

5.3.5　GCP Auth（GCE / GKE / Cloud Run）

原理：GCE metadata server 可以為 VM / Pod 簽發 ID Token，Infisical 用 GCP 公鑰驗證。

# Pod 內取 ID token
ID_TOKEN=$(curl -H "Metadata-Flavor: Google" \
  "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=infisical")

# 登入 Infisical
curl -X POST 'https://app.infisical.com/api/v1/auth/gcp-auth/login' \
  -d "{ \"identityId\": \"...\", \"jwt\": \"$ID_TOKEN\" }"

5.3.6　Azure Auth（Managed Identity）

原理：Azure 的 Managed Identity 透過 IMDS endpoint 為資源簽發 token。

# Azure VM / Function 內
TOKEN=$(curl -s "http://169.254.169.254/metadata/identity/oauth2/token?\
api-version=2018-02-01&resource=https://management.azure.com/" \
  -H "Metadata: true" | jq -r '.access_token')

curl -X POST 'https://app.infisical.com/api/v1/auth/azure-auth/login' \
  -d "{ \"identityId\": \"...\", \"jwt\": \"$TOKEN\" }"

5.3.7　OCI Auth（Oracle Cloud）

2026 新增。原理類似 AWS Auth，用 OCI 簽名請求驗證來源。實作流程：在 Infisical 建立 OCI Auth identity，配置 allowed Tenancy / User OCID / Group，OCI 工作負載用 OCI SDK 自動簽名後送出。

5.3.8　OIDC Auth（最重要的 CI 認證方式）

OIDC Auth 是現代 CI/CD 的標配。GitHub Actions、GitLab CI、CircleCI 都會在 pipeline 啟動時自動簽發 OIDC ID Token，Infisical 驗證後即接受。無需在 secret manager 配發任何 secret 給 CI——這是 secret zero 的根本解。

GitHub Actions 範例：

name: deploy
on: [push]

permissions:
  id-token: write   # 必要，授權 GitHub 簽 OIDC token
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: Infisical/secrets-action@v1.0.7
        with:
          method: "oidc"
          identity-id: "abc-def-123"
          project-slug: "my-proj"
          env-slug: "prod"
      # 之後 step 可直接讀環境變數
      - run: ./deploy.sh   # secret 已在 env 內

在 Infisical 端 OIDC config 重點：

  • OIDC Discovery URL：例如 GitHub https://token.actions.githubusercontent.com
  • Subject 限制：例如 repo:acme/myapp:ref:refs/heads/main 只允許 main 分支
  • Audiences：自訂 audience 字串增加額外保護
  • Claims 限制：可加任意 OIDC claim 條件
為什麼 OIDC 是 CI 的最佳選擇

傳統 CI 需要在 GitHub Secrets / GitLab Variables 內存一支 long-lived token——這 token 本身就是要被保護的 secret，等於「為了拿 secret 而存了另一個 secret」（secret zero 問題）。OIDC 完全消除這個問題：CI 啟動時 GitHub 動態簽 token，Infisical 用 GitHub 公鑰驗證。

5.3.9　JWT Auth（自家 IdP）

OIDC 是 JWT 的特例（要走 OIDC Discovery）。如果你的 IdP 不支援 OIDC Discovery（例如自架簽 JWT），用 JWT Auth：直接配置 issuer URL、JWKS URL、subject、audience 規則。

5.3.10　LDAP Auth（地端 AD 重用）

讓 Identity 用 LDAP / AD 帳號登入。適合純地端環境，已有 AD 服務。

# 配置：bind DN、base DN、search filter
# 應用程式登入：
curl -X POST 'https://infisical/api/v1/auth/ldap-auth/login' \
  -d '{
    "identityId": "...",
    "username": "ldap-user",
    "password": "ldap-pwd"
  }'

5.3.11　SPIFFE Auth（雲原生身分標準）

2026 新增。SPIFFE 是 CNCF 的 workload identity 標準，SPIRE 是其參考實作。SPIFFE Auth 接受 SPIRE 簽發的 JWT-SVID，Infisical 用 SPIRE bundle 公鑰驗證。

適合已採用 SPIRE 做跨叢集 / 跨雲身分的進階組織。一般 K8s 工作負載直接用 Kubernetes Auth 即可，不必引入 SPIRE。

5.4　Auth Templates 套用最佳實務

讓配置可重用 DevOps/SRE

當你有 50 個 K8s 叢集都需要 K8s Auth identity，每次手動配置都要填一樣的 host、reviewer JWT、namespace policy。Machine Identity Auth Templates 讓你把常用配置存成模板，建立 identity 時一鍵套用。

建立模板：Org Settings → Auth Templates → Create Template。模板可包含 default TTL、max uses、IP allowlist、auth method 預設值。

建議的模板設計

  • k8s-prod-strict：K8s Auth、TTL 1h、IP 限制 prod cluster CIDR、強制 audience 字串
  • ci-github-readonly：OIDC Auth、限制 main 分支、TTL 30min、僅 read
  • local-dev-developer：UA、TTL 7 天、無 IP 限制

5.5　MFA 與 GitHub Team Sync

MFA：人類使用者必開 DevOps/SRE

Org admin 在 Settings → Authentication → MFA 可強制開啟。支援：

  • TOTP（Google Authenticator、Authy 等）：基本款，建議全員啟用
  • WebAuthn / Passkey：硬體 key（YubiKey）或 platform passkey（Touch ID、Windows Hello）。釣魚抗性最強
  • Email OTP：備援用，避免主要 MFA 失效時無法登入

GitHub Team Sync

對 GitHub 為主的組織，可以用 GitHub Team Sync：把 Infisical Org member 的 role 對映到 GitHub Org / Team membership。當員工從 GitHub Org 移除，Infisical 自動踢除——這是輕量版的 SCIM。

本章重點回顧
  • 人類用 SSO（SAML / OIDC / LDAP），全員強制 MFA。
  • 機器用 Machine Identity，11 種 Auth 方法選最貼合工作負載原生身分的。
  • Service Token 是舊機制，新專案不要用。
  • CI/CD 一律走 OIDC Auth，徹底解決 secret zero。
  • Lockout 預設 3 失敗鎖 5 分鐘。
  • 大型部署用 Auth Templates 統一配置。

6.2　Custom Role 與 Additional Privileges

當內建角色不夠用

實務上經常需要更細粒度的角色。例如「只能讀 dev/staging，不能讀 prod；可以提交 prod 的 change request 但不能直接寫」。這時用 Custom Role：

  1. Project Settings → Access Control → Project Roles → New Role。
  2. 命名（例：dev-engineer）。
  3. 對每個 resource（secrets、folders、environments、members、settings、integrations、approvals、policies 等）勾選允許的動作（read / create / edit / delete）。
  4. 對 secrets 可以額外限定 environment + path 範圍（例：只允許 dev + /services/api/*）。

Additional Privileges：在 role 之外給單次特權

場景：alice 是 member role，但今天需要臨時刪除一個 prod 內舊的 secret。直接升 admin 太重；改 role 之後又忘了改回來。

用 Additional Privileges：在 alice 個人頁面授予「secrets:delete on /legacy in prod」單次特權，可加 TTL（24 小時自動到期）。處理完即釋放。

6.3　Temporary Access（臨時授權）

Additional Privileges 的特化：給「臨時 admin / 臨時 member」這種粗粒度但有時限的授權。在成員列表點該成員 → Grant Temporary Access，選 role + 期限。

典型用途：

  • 外部稽核員在期間內取得 viewer 權限
  • 合作廠商開發期間給 dev member
  • 新進員工 onboarding 觀察期內限縮權限

6.4　Access Requests 流程

已在 4.5 節說明。重申關鍵點：

  • 申請者主動要求 → reviewer 審核 → 過了就拿到「指定範圍 + 指定時長」的 Additional Privilege
  • 過期自動回收，不需手動清理
  • 所有環節都有 Audit Log

Access Request 適合「例外情況」，不該被當成日常授權手段。如果某類權限被頻繁申請，應該重新檢視 base role 設計。

6.5　PR / Approval Workflows

4.5 節已涵蓋。本節補充政策設計建議：

  • 分層審批：dev 不需審批；staging 1 人；prod 2 人。降低開發摩擦同時保障 prod 嚴格。
  • 避免 self-approval：永遠關掉「申請者可自己核准」。
  • Reviewer 群要包含 on-call：避免假日唯一 reviewer 度假時所有變更卡住。
  • Bypass 機制：對緊急修補 production 的場景設計「破玻璃」流程——可由特定 admin 強制核准但所有 bypass 都進 audit。

6.6　IP Allowlist 與 ABAC

Project-level IP Allowlist

Project Settings → Trusted IPs。配置後，所有對該 project 的存取（含 user、identity、CLI）都必須來自白名單 IP。

注意：

  • 支援 IPv4 / IPv6 + CIDR
  • 應用前一定要把 自己當下的 IP加進去，否則自己會被鎖在外面
  • 對全雲端 CI（IP 飄忽）不適用，那種情境用 OIDC + claim 限制更佳

Identity-level IP 限制

個別 Identity 也可以單獨設 IP allowlist（在 client secret 或 access token 兩層），即使整個 Project 沒設 trusted IPs，特定 identity 仍可被限縮。粒度比 Project-level 更細。

ABAC：屬性式存取控制

RBAC 解「誰能做什麼」，ABAC 解「在什麼條件下才能做」。Infisical 的 ABAC 用 metadata + rule expression 實作：

// 假設 identity 有 metadata: { team: "backend", env_access: ["dev", "staging"] }
// 政策: 只有 team == "backend" 的 identity 才能寫 /services/api 下的 secret

{
  "rule": {
    "effect": "allow",
    "actions": ["secrets:create", "secrets:update"],
    "resources": ["secret:/services/api/*"],
    "conditions": {
      "identity.metadata.team": "backend"
    }
  }
}

常見用法：

  • 限制特定 team 才能讀指定 folder
  • 限制 identity metadata 含 compliance:pci 才能讀 payment 相關 secret
  • 結合 OIDC claim：CI 拿到的 token 要含 environment: production 才能讀 prod
ABAC 是進階功能，先把 RBAC 做好

ABAC 強大但會讓「為什麼讀不到 secret」的排查變難。建議組織先用 RBAC 6 個月以上、確定 RBAC 的能力邊界後再引入 ABAC，並且每條 ABAC 政策都要寫文件說明「為什麼這條規則存在」。

7.3　Event Subscriptions（事件驅動整合）

Audit Log Stream 是「所有事件全推」；Event Subscriptions 是「特定事件選擇性推」並可路由到不同目的地。設計上更貼近「事件總線」。

典型訂閱：

  • secret-updated in /services/billing of prod → push 到 PagerDuty 觸發 on-call
  • identity-created with admin role → push 到 Security Slack channel
  • access-request-granted → push 到稽核專用 webhook 落 immutable storage

7.4　Workflow Integrations：Slack / Microsoft Teams 通知

不需要 SIEM，只想把關鍵事件推到團隊聊天工具？用 Workflow Integrations。

Org Settings → Workflow Integrations → Create → Slack。OAuth 一次後選 channel，再到 Approval Policy 設定「核准請求自動 ping 此 channel」。

這是 Approval Workflow 真正可用的關鍵——沒有人會主動回 UI 看待審清單，但 Slack 通知會被看到。

8.1　PKI 基礎與使用情境

PKI（Public Key Infrastructure）的核心需求：誰能信任誰簽出來的憑證、怎麼撤銷、怎麼自動續發。Infisical PKI 把這套完整流程內建到平台：

  • Internal CA：完全在 Infisical 內建立 root CA、intermediate CA 階層，用於內部服務 mTLS、IoT 裝置、員工 client cert。
  • External CA：把外部 CA（Let's Encrypt / DigiCert / Microsoft AD CS / Venafi TLS Protect Cloud / AWS Private CA / 任何 ACME-compatible CA）接入，由 Infisical 統一 orchestrate 簽發與續發。
  • 四種 enrollment 方法：API、ACME、EST、SCEP。讓不同類型的 client（K8s cert-manager、IoT 裝置、Apache、Nginx、自家服務）都有合適的接入方式。

8.2　Internal CA：建立 Root + Intermediate 階層

為什麼要分 Root + Intermediate

標準做法：root CA 簽 intermediate CA，由 intermediate 簽出實際 leaf cert。Root CA 的 private key 簽完 intermediate 之後就離線存放（offline），幾年才用一次。日常簽發都用 intermediate——萬一 intermediate 被入侵，撤銷它即可，不必動到 root（換 root 等於整個信任鏈崩潰）。

實作步驟

  1. 建立 Certificate Management Project（第一卷 2.3 節）。
  2. 左側 Certificate Authorities → Create CA → 選 Internal CA。
  3. 填 root CA 的設定：
    • CA Type: Root
    • Common Name: Acme Root CA
    • Key Algorithm: RSA 4096 / ECDSA P-384
    • NotAfter: 10 年
  4. 建立 Intermediate CA：
    • CA Type: Intermediate
    • Parent CA: 選剛剛的 root
    • NotAfter: 5 年（必須短於 parent）
  5. 把 Root CA 的 private key 匯出，離線冷儲存（YubiKey / HSM / 加密硬碟保險箱）。
Root CA 私鑰外洩 = 災難

如果 Root CA 私鑰外洩，攻擊者可以隨意簽發看似合法的內部憑證冒充任何服務。一旦發生，必須撤銷 Root CA、所有 intermediate、所有 leaf cert，重建整套階層。建議：(1) 簽 intermediate 後立即匯出 root 私鑰、(2) 平台內 root CA 設為 disabled、(3) 私鑰存於 HSM 或多人保管的離線媒介。

8.5　四種 Enrollment Methods

API Enrollment

最直接：呼叫 REST API 帶 CSR，取回簽好的 cert。適合應用程式自己控制密鑰生成的場景，或 Infisical Agent / 內部工具串接。

# 申請憑證
curl -X POST 'https://app.infisical.com/api/v1/pki/profiles/{profile-id}/issue' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "commonName": "api.acme.local",
    "altNames": ["api-v2.acme.local"],
    "ttl": "90d"
  }'

# 回傳 cert + private key（若 server-side keygen）或只 cert（若帶 CSR）

ACME Enrollment

RFC 8555 標準。優點：cert-manager、certbot、Apache 內建支援，零自寫程式碼。Infisical 的 ACME 實作支援 HTTP-01 / DNS-01 兩種 challenge，並支援 EAB（External Account Binding）做客戶端綁定。

K8s cert-manager 整合：

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: infisical-acme
spec:
  acme:
    server: https://app.infisical.com/api/v1/pki/acme/{profile-id}/directory
    email: ops@acme.com
    privateKeySecretRef:
      name: infisical-acme-key
    externalAccountBinding:
      keyID: ${EAB_KID}
      keySecretRef:
        name: infisical-eab
        key: secret
    solvers:
      - http01:
          ingress:
            class: nginx

EST Enrollment

RFC 7030。適合 IoT 裝置、企業網路設備。Infisical 實作了 cacerts、simpleenroll、simplereenroll 三個關鍵端點。

SCEP Enrollment

適合舊型網路設備（Cisco IOS、Juniper）。配置 challenge password 後，設備可以透過 SCEP 自動註冊與續發。

8.6　憑證生命週期：簽發、續發、撤銷

Client-driven 與 Server-driven 續發

  • Client-driven：client 監測自己的 cert，到期前向 Infisical 申請續發。最常見，cert-manager / certbot 都是這種。
  • Server-driven：Infisical 主動在 cert 到期 N 天前簽好新 cert，並 push 到 destination（例如 cert sync 到 AWS ACM）。適合 cert 不在 client 手上、由平台統一管理的場景。

撤銷與 CRL

cert 撤銷後，Infisical 自動更新 CRL（Certificate Revocation List）。CRL 可以透過固定 URL 對外發布，client 端定期下載比對。

# CRL 端點範例
https://app.infisical.com/api/v1/pki/ca/{ca-id}/crl

# 用 openssl 驗證 cert 是否被撤銷
openssl crl -in crl.pem -noout -text | grep "Serial Number"

8.7　Certificate Syncs

把 Infisical 簽好的 cert 自動推到 AWS ACM、Azure Key Vault、Heroku、Cloudflare 等外部平台，就像 Secret Syncs 對 secret 那樣。配合 server-driven renewal，整個 cert 生命週期完全自動化。

8.8　Alerting：過期告警

Project → Certificates → Alerts。可設：

  • CA 憑證在到期前 X 天告警
  • Leaf 憑證到期前 X 天告警
  • 告警目的地：Email、Slack、PagerDuty webhook

Cert 過期是 production 大事故的常見原因（Slack、Spotify、LinkedIn 都曾因此短暫掛掉）。Alerting 是必設。

KMS：金鑰管理服務

本章學什麼
Infisical KMS 的兩種角色——「應用程式 KMS」（讓你的服務 encrypt/decrypt 資料）與「平台 KMS」（用 External KMS 接管 Infisical 自身加密的 root key）。
適合誰讀
開發者DevOps/SRE

9.1　KMS 概念與適用場景

KMS 解決的問題：「我的應用程式需要加密一些資料儲存到 DB（例如使用者個資），但密鑰要放哪？」答案不該是「跟 secret 一起塞進環境變數」——那等於把保險箱鑰匙放在保險箱裡。

正確做法：把金鑰本身放在 KMS（金鑰永不離開 KMS），應用程式呼叫 KMS 的 encrypt / decrypt API。即使應用程式被入侵，攻擊者拿到 ciphertext 也解不開（除非他能繼續呼叫 KMS API，那時 KMS audit log 會看到異常）。

9.2　建立對稱金鑰、Encrypt / Decrypt API

建立 KMS Project → KMS → Keys → Create Key。選對稱（AES-256-GCM）或非對稱（RSA / ECDSA）。

# 加密
curl -X POST 'https://app.infisical.com/api/v1/kms/keys/{key-id}/encrypt' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{ "plaintext": "Sensitive PII data" }'
# 回傳 { "ciphertext": "AQID..." }

# 解密
curl -X POST 'https://app.infisical.com/api/v1/kms/keys/{key-id}/decrypt' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{ "ciphertext": "AQID..." }'
# 回傳 { "plaintext": "Sensitive PII data" }

Envelope Encryption

對大資料（檔案、影音），不要直接呼叫 KMS encrypt（KMS 通常有 4KB 大小限制）。改用 envelope encryption：

  1. 應用程式產生隨機 DEK（Data Encryption Key）
  2. 用 DEK 加密實際大資料
  3. 把 DEK 用 KMS 加密（這個操作 KMS 可勝任）
  4. 儲存「加密後的 DEK + 加密後的資料」

9.3　Project-level KMS 與 Customer-Managed Keys（CMK）

第一卷 3.4 節提到 Infisical 用四層金鑰階層加密 secret。預設情況下最外層 root key 由 Infisical 提供（Cloud）或在環境變數（Self-Host）。

CMK 模式：把 Project Data Key 改用「你自己的 External KMS」加密。例如指向你的 AWS KMS CMK。一旦切換：

  • 每次 Infisical 解 secret 都需呼叫你的 AWS KMS
  • 你可以在 AWS 端 audit 所有解密請求
  • 萬一你想「凍結」這個 project，停掉 AWS KMS key 即可，Infisical 從此解不出 secret

這是合規上「root of trust 在我自己」的解。對金融、醫療客戶常見要求。

9.4　與 Secrets Management 後端整合

除了 Project-level CMK，整個 Instance 的 root key 也可以用 External KMS 託管（HSM-backed root），這部份會在第五卷 27 章 EE 設定詳述。

SSH 憑證式存取

本章學什麼
用 SSH CA 取代靜態 SSH key、簽發短效 SSH 憑證、與 Bastion / Jump Host 整合。
適合誰讀
DevOps/SRE

10.1　為何用 SSH CA 取代靜態 Key

傳統 SSH 用 ~/.ssh/authorized_keys 維護白名單：誰的 public key 在裡面，誰就能進。問題：

  • 員工離職時，要去每台主機刪除他的 public key——通常會漏
  • 新進員工要加入，得改所有主機的 authorized_keys
  • 沒有時效——key 一加上去，永遠有效
  • 沒有 audit——誰在何時用哪把 key 進來，主機 log 裡資訊有限

SSH 憑證模式徹底翻轉這個流程：主機只信任「由 CA 簽過的憑證」，不再維護個別 user 的 key。要進主機？跟 CA 申請一張短效憑證（例如 15 分鐘有效），用完即廢。

10.2　設定 SSH CA 與 Host

步驟 1：建立 SSH CA

  1. 建立 SSH Project（第一卷 2.3 節）。
  2. SSH Certificate Authorities → Create CA。
  3. 選 ECDSA 或 Ed25519，輸出 CA public key。

步驟 2：在每台主機信任 CA

# 把 CA public key 寫入 sshd config
echo "TrustedUserCAKeys /etc/ssh/infisical_ca.pub" | sudo tee -a /etc/ssh/sshd_config
sudo cp infisical_ca.pub /etc/ssh/infisical_ca.pub
sudo systemctl restart sshd

步驟 3：建立 SSH Certificate Template

類似 PKI Profile：定義 user principal 規則、TTL、是否可 forward agent / pty / X11。

10.3　簽發短效 SSH 憑證

# 用 Infisical CLI 申請憑證
infisical ssh issue-credentials \
  --templateName=engineers \
  --principals=alice,bob \
  --keyAlgorithm=ED25519 \
  --ttl=15m

# 輸出範例：
# Private Key: -----BEGIN OPENSSH PRIVATE KEY-----
# Certificate: ssh-ed25519-cert-v01@openssh.com AAAAH...
# 自動寫入 ~/.ssh/

# 直接 ssh
ssh -o IdentityFile=~/.ssh/id_infisical \
    -o CertificateFile=~/.ssh/id_infisical-cert.pub \
    user@target-host

更佳做法：用 infisical ssh connect 一鍵申請+連線。

10.4　與 Bastion / Jump Host 整合

大型環境通常有 Bastion 跳板機。Infisical SSH CA 與 Bastion 是相輔相成：

  • Bastion 信任 Infisical SSH CA 的 user CA
  • 內網主機也信任同一張 CA
  • 使用者：拿到一張短效憑證，能跳到 Bastion 也能從 Bastion 跳到內網
  • 個別主機不需各自管 user 名單
