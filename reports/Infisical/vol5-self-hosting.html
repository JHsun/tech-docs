當你決定 Self-Host Infisical 之後，問題從「會不會用」轉變成「如何讓它穩定、可被信任地承載 production 機敏資料」。第五卷把整套維運主題從零展開：從選擇部署平台、設計 production-grade 架構，到備份還原、監控告警、版本升級，乃至於 Enterprise 功能與合規模式（FIPS / HSM）。

本卷的隱性假設

本卷假設你已熟悉 Linux 系統管理、PostgreSQL 操作、TLS 配置、Kubernetes 基礎與 GitOps 流程。如果這些觀念不熟，建議先補齊再讀本卷——否則內容會變成抄寫範例，缺少「為什麼這樣做」的脈絡，遇到 production 故障無法判斷。

最重要的一句話

ENCRYPTION_KEY 一旦遺失，所有 secret 變成密文垃圾，永遠無法解密。第 22 章與第 24 章會反覆強調，但這個觀念是 Self-Host Infisical 的第一準則：把 ENCRYPTION_KEY 當成你公司最重要的金鑰之一，存在 HSM 或冷儲存，並準備災難復原計畫。

實務建議：

  • Production 第一推薦 K8s + Helm。HA、滾動升級、健康檢查、autoscale 都原生支援。

  • 單機原型 / 內網實驗：Docker Compose 最快。
  • 嚴格 air-gapped 環境：Linux 套件 + 自行架 HA。

實際規劃時的關鍵指標

  • API Request rate：每秒讀 secret 次數是主要 sizing factor。Pod 多少並發 secret fetch + CI 觸發頻率合計算。
  • PostgreSQL 大小：secret + audit log + version history 累積增長。1000 個 secret 跑 1 年大約 5–10 GB（含 audit）。
  • Redis：用作 session、rate limit、訊息 broker。記憶體大小依使用者數估算。

關鍵設計原則：

  • 跨 AZ：API pod 與 PG / Redis 都要跨可用區，防單區掛掉。
  • PostgreSQL HA：Zalando postgres-operator 或 Crunchy Data 是常見選擇。不要用 Helm 內建 PG（單副本、無備份策略，僅供 PoC）。
  • Redis HA：Sentinel 或 Cluster 模式。Infisical 對 Redis 不算重度依賴，但故障時影響 session 與 rate limit。
  • 對外只暴露 LB：API 容器直接對外是漏洞，務必走 LB。
  • 備份：自動每日 PG dump + WAL archive 到對象儲存，第 24 章詳述。

22.1　Docker Compose Production

關鍵差異 vs sandbox DevOps/SRE

第一卷 2.2 節跑過 Docker Compose 的 sandbox 模式。Production 版本有幾個關鍵差異：

  1. 每個 secret 用隨機產生的值（範本檔的預設密碼是公開的，絕對不可上線）
  2. PostgreSQL 與 Redis 改用外部 managed service（RDS、ElastiCache）
  3. 前面架 nginx / Traefik 處理 TLS
  4. 定期備份 + 監控

產生隨機 secret

# 產生 ENCRYPTION_KEY（32 字元 hex）
openssl rand -hex 16

# 產生 AUTH_SECRET（base64）
openssl rand -base64 32

# 把產出的值填進 .env，再保存到外部 secret 管理（HSM / Cloud KMS）
# 永遠不要把 .env 進 Git

production .env 範本

# 必要參數
ENCRYPTION_KEY=<openssl rand -hex 16>
AUTH_SECRET=<openssl rand -base64 32>
SITE_URL=https://infisical.acme.com

# 外部 PG
DB_CONNECTION_URI=postgres://infisical:****@rds.example.com:5432/infisical?sslmode=require
DB_ROOT_CERT=/etc/infisical/rds-ca.pem    # AWS RDS SSL 用

# 外部 Redis
REDIS_URL=rediss://default:****@elasticache.example.com:6379

# SMTP（密碼重設、邀請通知）
SMTP_HOST=smtp.sendgrid.net
SMTP_PORT=587
SMTP_USERNAME=apikey
SMTP_PASSWORD=SG.****
SMTP_FROM_ADDRESS=infisical@acme.com
SMTP_FROM_NAME=Infisical

# 可選但建議
TELEMETRY_ENABLED=false        # 關閉 Infisical 自家 telemetry
NODE_ENV=production
永遠保留 ENCRYPTION_KEY 的多重副本

ENCRYPTION_KEY 是整個 instance 解密所有 secret 的根金鑰。如果遺失，所有 secret 變成無法復原的密文，PG 備份也救不了你。建議：

  • 主要副本：Cloud KMS / HSM 加密儲存
  • 第二副本：離線冷儲存（保險箱、加密硬碟）
  • 第三副本：主管階層或安全團隊個人 password manager
  • 絕不可只存在容器 env 或 .env 檔內

nginx 反向代理 + TLS

# /etc/nginx/sites-available/infisical
upstream infisical_backend {
    server 127.0.0.1:8080;
}

server {
    listen 443 ssl http2;
    server_name infisical.acme.com;

    ssl_certificate     /etc/letsencrypt/live/infisical.acme.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/infisical.acme.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE+AESGCM:ECDHE+CHACHA20:DHE+AESGCM:!aNULL:!MD5;
    ssl_prefer_server_ciphers on;
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;

    client_max_body_size 50M;

    location / {
        proxy_pass http://infisical_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}

server {
    listen 80;
    server_name infisical.acme.com;
    return 301 https://$host$request_uri;
}

22.2　Kubernetes + Helm 完整部署

步驟 1：建立 namespace 與機敏資料

kubectl create namespace infisical

# 建立 ENCRYPTION_KEY 與所有 production credentials

  --from-literal=SMTP_PASSWORD="SG.xxx" \

# 把 ENCRYPTION_KEY 同步備份到 cluster 外部

  'https://dl.cloudsmith.io/public/infisical/helm-charts/helm/charts/'

不要在 production 用 Helm 內建 PG

Helm 預設啟用內建 Postgres + Redis 給 PoC 方便。Production 一定關掉，改用外部 managed service。內建 PG 用的是 bitnamilegacy/postgresql image，沒有 HA、沒有自動備份、persistent volume 容易設錯導致升級時遺失資料。

22.3　PostgreSQL / Redis 外部化與備份

PostgreSQL 推薦設定

  • 版本：PG 14+
  • HA：AWS RDS / Cloud SQL / Crunchy Data / Zalando postgres-operator 三選一
  • SSL：強制 TLS（sslmode=require 至少，理想 verify-full）
  • 備份：每日 full backup + WAL archive 持續，至少保留 30 天
  • 監控：connection 數、磁碟使用、replication lag、慢查詢

Redis 推薦設定

  • HA 模式：Sentinel（簡單）或 Cluster（高吞吐）
  • 持久化：開 AOF（appendonly），但對 Infisical 不是強需求（資料丟失只影響 session）
  • TLS：對外連線必開
  • memory limit：設 maxmemory-policy allkeys-lru，防 OOM

22.4　TLS 終止與 Ingress 設定

K8s 部署的 TLS 通常用 cert-manager + Let's Encrypt 自動簽發：

23.2　Infisical Gateway：自家內網的 dynamic secret

第四卷 20.3 節介紹 Gateway。本節重點是 Self-Host 環境的 Gateway 部署考量。

Self-Host 場景下，Gateway 的價值依然存在，但情境不同：

  • 當 Infisical 自身在你 DMZ / Cloud 區段，需要連回更內層的私網 DB（多層 zone 設計）
  • 當 Infisical 跨區部署，要連一個只在某區可達的資源
  • 當你不希望「Infisical 主應用程式直接持有 production DB admin credential」

Org-level Relay 部署

Self-Host 想要降低 Gateway tunnel 延遲，可以部署 Org-level Relay（替代 Infisical Cloud 的 Relay）：

# Helm 安裝 Relay（EE 功能）
helm install infisical-relay \
  infisical-helm-charts/infisical-relay \
  --namespace infisical \
  --set relay.licenseKey=<EE-LICENSE> \
  --set relay.publicAddress=relay.acme.com

之後在 Gateway 配置時指定 Relay = relay.acme.com，整條 tunnel 就走你自家的 Relay。

23.3　Private Resource（內部 DB）接入

實作流程：

  1. 在內網部署 Gateway（容器或裸機），用 enrollment token 註冊到 Infisical。
  2. Infisical UI → Org Settings → Gateways → 確認「online」狀態。
  3. 建立 Dynamic Secret 配置時，「Connection Method」選 Through Gateway，指定剛剛的 gateway。
  4. Connection 內填的 host 用內網 DNS / IP（例如 db.internal.acme.local）——這個位址只有 Gateway 解析得到，Infisical 主應用反而看不到。

24.1　版本升級流程

升級節奏 DevOps/SRE

Infisical 演進極快（每月數個版本）。建議節奏：

  • 每月跟版：取最新 stable 版（避開 release candidate）
  • 升級前讀 release notes：尤其檢查 breaking changes 與 DB migration
  • 先升級 staging 一週，確認穩定再升 production
  • 備份 + 維護視窗：升級前一定先做完整 PG dump

K8s Helm 升級實作

# 1. 升級前完整備份
kubectl exec -n infisical postgresql-0 -- \
  pg_dump -U infisical infisicalDB | \
  gzip > backup-$(date +%Y%m%d-%H%M).sql.gz

# 2. 把備份上傳到外部對象儲存
aws s3 cp backup-*.sql.gz s3://acme-infisical-backup/

# 3. 升級 Helm chart
helm repo update
helm upgrade infisical \
  infisical-helm-charts/infisical-standalone \
  --namespace infisical \
  --values values-prod.yaml \
  --set infisical.image.tag=v0.159.0    # 新版本

# 4. 觀察 rollout
kubectl rollout status deployment/infisical -n infisical -w

# 5. 驗證
curl https://infisical.acme.com/api/status

# 6. 故障時 rollback
helm rollback infisical 0 -n infisical
DB schema migration 是不可逆的

autoDatabaseSchemaMigration: true 會在啟動時自動跑 PG schema 遷移。如果新版有 schema 變更，降版（rollback）會壞——舊版的 code 跑不了新 schema。Production 升版前一定先做 pg_dump，rollback 時還原 DB + 切回舊 image，二者一起來。

24.2　PostgreSQL 備份與還原

三層備份策略

層級方式RPORTO
每日 full backupcron job 跑 pg_dump，上傳 S324h~30 分
WAL archive連續推送 WAL 到對象儲存~1 分~30 分
跨區 replicastreaming replication 到異地秒級分鐘

RDS / Cloud SQL 用戶可開 PITR + 自動 snapshot；自架 PG 用戶推薦 pgbackrest 或 wal-g。

還原流程演練

備份只有「能還原」才有用。建議季度演練：

# 1. 開新 PG instance（測試用，不要碰 production）
# 2. 從 S3 下載最新 backup
aws s3 cp s3://acme-infisical-backup/backup-20260506-0300.sql.gz .
gunzip backup-20260506-0300.sql.gz

# 3. 還原到測試 instance
psql -h test-pg.example.com -U postgres -c "CREATE DATABASE infisical_restore;"
psql -h test-pg.example.com -U postgres -d infisical_restore -f backup-20260506-0300.sql

# 4. 起一個 Infisical 容器指向這個 DB（用同樣的 ENCRYPTION_KEY!!）
docker run -d \
  -e DB_CONNECTION_URI="postgres://...test-pg.../infisical_restore" \
  -e ENCRYPTION_KEY=<原 KEY> \
  -e AUTH_SECRET=<原 SECRET> \
  -p 8080:8080 \
  infisical/infisical:v0.158.2

# 5. 登入驗證 secret 都還在
沒 ENCRYPTION_KEY，PG 備份等於沒用

備份還原時必須同時提供原本的 ENCRYPTION_KEY，否則連到 DB 後 secret 是密文垃圾。這就是為什麼第 22 章強調 ENCRYPTION_KEY 要多重備份——把它跟 PG dump 想成「鑰匙」與「保險箱」，缺一不可。

24.3　PIT Recovery 與資料庫快照的差別

第二卷 4.2 節介紹過 Infisical 的 PIT Recovery。這裡澄清它的真實能力：

場景用什麼救
誤刪幾個 secret / 改錯值Infisical PIT 還原 environment 快照
整個 Project 結構亂了Infisical PIT 還原
誤刪整個 ProjectPG 備份還原（PIT 救不了已刪 Project）
整個 Org 被刪PG 備份還原
PostgreSQL 整顆掛掉PG 備份 + WAL archive 還原
整個 DC 失效跨區 replica 切換

24.4　多區 Replication 配置

Production-grade 部署應考慮跨區 PG replica：

  • 主區（primary）：寫 + 讀
  • 異區（standby）：streaming replication，唯讀，可讀分流（Infisical 目前不對 read replica 自動分流，主要作為 DR）
  • 切換策略：主區故障 →promote standby，更新 DB_CONNECTION_URI，rolling restart

24.5　災難復原演練

把上面所有東西串起來，每季度跑一次完整 DR drill：

  1. 在隔離環境模擬「production cluster 全毀」
  2. 從備份還原 PG 與 Redis
  3. 取出冷儲存 ENCRYPTION_KEY
  4. 部署新 Infisical instance 指到還原的 DB
  5. 登入驗證所有關鍵 secret 仍然能解
  6. 記錄 RTO 實際值，與 SLO 對比
演練的真正價值

大多數 DR 失敗的真正原因不是備份壞掉，而是：沒人知道完整流程、ENCRYPTION_KEY 找不到、步驟細節在 Wiki 但 Wiki 也在 production。每季度演練讓這些問題在 lower stake 環境被發現。

25.2　Prometheus metrics 與 Grafana

Infisical 暴露 Prometheus metrics 在 /api/v1/metrics。在 K8s 用 ServiceMonitor 採集：

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: infisical
  namespace: infisical
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: infisical
  endpoints:
    - port: http
      path: /api/v1/metrics

關鍵 metric

  • http_request_duration_seconds：API latency 分位數
  • http_requests_total：總請求數，依 status / method 拆解
  • nodejs_eventloop_lag_seconds：Node.js event loop 延遲，> 0.1s 是警訊
  • pg_pool_size、pg_pool_waiting：DB 連線池狀況

26.1　Instance 層管理介面

第一位註冊的 user 自動成為 instance admin。Instance admin 可進入 Server Admin Console（路徑 /admin），這是凌駕於所有 Org 之上的管理層。

能做的事：

  • 檢視所有 Organization 與 user 列表
  • 停權違規 Organization 或 user
  • 配置 instance-wide 預設值（例如所有 Org 都強制 MFA）
  • 管理 EE License
  • 調整 rate limit 與 telemetry
Admin 權限的存在的價值與風險

Instance admin 是 Self-Host 唯一能在「忘記密碼且 SSO 配壞」時救自己的角色——但反過來也是最大攻擊面。建議：

  • Instance admin 帳號要強制 WebAuthn / hardware MFA
  • Admin 帳號最好是專用 break-glass 帳號，不日常登入使用
  • Admin 操作全部進 audit，串到 SIEM
  • 定期審視 admin 帳號清單

26.2　全站 SSO / SCIM 設定

第二卷 5.1 節介紹的 SSO 是每個 Organization 各自配。Server Admin Console 還有一層更上層的 SSO 設定，影響整個 instance：

  • 所有 Org 共用的預設 IdP（多租戶 instance 用）
  • 新建 Org 時自動套用的 SCIM provisioning 規則
  • Lockout policy（連續失敗次數、鎖定時長）

多數情境下你只有一個 Org，這層用不到。但若你 Self-Host 給多個事業單位用，instance-level SSO 是治理的關鍵。

26.3　Rate Limit 與速率控制

Self-Host 預設的 rate limit 與 Cloud 相當。可在 Server Admin → Configuration 調整：

設定預設建議調整時機
Public API rate limit每 IP / token 每分鐘 600 次大型 CI 群觸發 429 時提高
Login attempt rate limit每 IP 每分鐘 30 次調低降低 brute-force 機會
Secret operation rate limit每 token 每分鐘 60 次寫入批次匯入大量 secret 時暫時提高

26.4　License 管理

EE 使用者可在 Server Admin → License 上傳授權檔，啟用 EE 功能。授權檔過期或無效時 EE 功能自動鎖回 OSS 等級——OSS 功能不受影響。

27.3　FIPS 模式部署

FIPS 140-3 是美國聯邦政府要求的密碼學模組驗證。對金融、醫療、政府部門經常是合規硬性條件。

FIPS image

Infisical 提供 FIPS-validated Docker image（EE only）：

# Helm values
infisical:
  image:
    repository: infisical/infisical-fips
    tag: "v0.158.2"

FIPS image 內的 Node.js / OpenSSL 用 FIPS-validated cryptographic module，且強制以 FIPS mode 執行。

HSM-backed Root Key

FIPS 部署的另一個關鍵組件：把 ENCRYPTION_KEY 從環境變數移到 HSM（例如 AWS CloudHSM、Azure Dedicated HSM、Thales Luna），由 HSM 完成根加密操作。配置在 Server Admin → KMS Configuration → HSM。

啟用後，ENCRYPTION_KEY 環境變數可以移除——所有 root-level 解密都委由 HSM 執行。HSM 故障時 instance 完全無法解密 secret，這是 FIPS 設計的一部分。

本卷重點回顧
  • Production 首選 K8s + Helm，不要用 Helm 內建 PG/Redis。
  • ENCRYPTION_KEY 三重備份（HSM + 冷儲存 + 主管 password manager），與 PG 備份分開存。
  • 每月跟版升級，升級前 PG dump，schema migration 不可逆。
  • 三層備份策略：每日 full + WAL archive + 跨區 replica。
  • 季度 DR 演練，目的是發現流程缺陷而不是測試備份能用。
  • 監控四個關鍵 metric：API latency、event loop lag、PG connection、replication lag。
  • EE 主要解 SSO / Approval Workflows / Audit Streams / FIPS / HSM。
