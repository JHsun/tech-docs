Argo CD Image Updater
自動偵測新 image 並寫回 Git

CI 把新版 image 推到 registry 後——誰來更新 Application 的 image tag？Image Updater 是 argoproj-labs 的獨立 controller，週期性掃描 registry，偵測新 tag（依 semver / newest-build / alphabetical / digest 策略），自動更新 Application 的 image 參數，或更好地：直接 commit 推回 Git 維持 GitOps single source of truth。本章涵蓋兩種 write-back 模式、五種 update strategies、Helm vs Kustomize 整合、registry 認證、與 ApplicationSet 配合（ignoreApplicationDifferences）、實務最佳實踐。

📋

前置：已完成 Vol 1-5 與 Ch.26（ignoreApplicationDifferences）。理解 Helm parameters 與 Kustomize image transformer（Ch.05）。理解 SemVer 版本規則。對 container registry（Docker Hub / GHCR / ECR / GCR）有基本概念。

🎯 學習目標

  • 理解 Image Updater 解決的核心問題：將「image tag 變更」從 CI 解耦，讓 image 更新成為獨立流程
  • 了解 Image Updater 的關鍵限制：只支援 Helm / Kustomize（不支援 plain YAML / Jsonnet）
  • 安裝獨立的 argocd-image-updater controller（與 Argo CD 主元件分離）
  • 掌握核心 annotations：image-list（含 alias）、write-back-method、update-strategy、allow-tags、ignore-tags、helm.image-name/tag
  • 區分兩種 write-back：① argocd（imperative，直接改 Application spec）vs ② git（declarative，commit 回 Git，推薦生產用）
  • 理解 git write-back 的預設機制：寫到 .argocd-source-<appName>.yaml（Argo CD 自動識別此特殊檔案）
  • 掌握 5 種 update strategies：semver（預設）、newest-build（舊名 latest）、alphabetical（舊名 name）、digest、自訂正則
  • 實作 Helm 整合（image-name + image-tag parameter）與 Kustomize 整合（kustomization write-back-target）
  • 處理 Docker Hub rate limit、private registry 認證（GHCR / ECR / GCR）
  • 與 ApplicationSet 整合：用 Ch.26 學的 ignoreApplicationDifferences 讓 Image Updater 的修改不被 controller 覆蓋

1為什麼需要 Image Updater

1.1 CI 推 image 後誰更新 manifest？

傳統 CI/CD 流程：

1
Dev push code 到 main branch
2
CI 跑測試 → build image → push 到 registry（tag: v1.2.3）
3
? 誰把 Application / Helm values 中的 image tag 從 v1.2.2 更新為 v1.2.3？
4
Argo CD sync 部署新版本

第 3 步通常有三種解法：

方案做法缺點
A. CI 中直接 commit Git CI build image 後再 commit 到 GitOps repo 更新 tag CI 需 Git 寫權限；CI 失敗會留下半完成狀態；多個 CI 同時 push 衝突
B. 手動更新 Dev push code 後手動修改 GitOps repo 容易忘記；無自動化 CD；延遲
C. Image Updater 獨立 controller 掃描 registry，自動更新 多一個 controller 要維護；CI ↔ CD 解耦但偵測有延遲（預設 2 分鐘）
💡

Image Updater 的核心價值

① CI / CD 完全解耦：CI 只需 push image，不需碰 Git；② 單一更新邏輯：所有 Application 用相同策略（semver、newest-build）；③ GitOps 純粹：image 變更也是 Git commit，保有完整 audit；④ 適合多 cluster / 多環境：不需要為每個環境寫 CI 規則。

1.2 重要限制

⚠️

Image Updater 只支援 Helm 與 Kustomize

不支援：① plain YAML（用 directory source 的 Application）；② Jsonnet；③ Config Management Plugins。原因：Image Updater 依賴 Argo CD 對這兩個工具的parameter override 機制。如果你的 Application 用 plain YAML，要嘛改寫成 Kustomize，要嘛用其他方案（如 Flux 的 image-automation）。

3核心 Annotations

Image Updater 全靠 Application metadata.annotations 設定。最重要的是 image-list：

3.1 image-list 與 alias

YAML — image-list 完整語法
metadata:
  annotations:
    # 1) 最簡單：單一 image，無 alias
    argocd-image-updater.argoproj.io/image-list: myregistry.io/myapp

    # 2) 含 alias（推薦）——讓後續 annotation 可引用
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp

    # 3) 多 image
    argocd-image-updater.argoproj.io/image-list: |
      frontend=myregistry.io/frontend,
      backend=myregistry.io/backend,
      worker=myregistry.io/worker

    # 4) 限定版本範圍（semver constraint）
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp:~1.2
    # ~1.2  → 只更新 1.2.x（不會跳到 1.3）
    # ^1.2  → 只更新 1.x（不會跳到 2.0）
    # >1.0  → 只取 1.0 之後的版本

  # 引用 alias 在後續 annotation：
  argocd-image-updater.argoproj.io/myapp.update-strategy: semver
  argocd-image-updater.argoproj.io/myapp.allow-tags: 'regexp:^v[0-9]+\.[0-9]+\.[0-9]+$'

3.2 五種 Update Strategies

Strategy邏輯適合
semver（預設） 按 SemVer 規則找最新版本（依 constraint） 生產推薦——release 嚴格 SemVer 的應用
newest-build（舊名 latest） 按 image push 時間找最新（不管 tag 名） dev / staging 環境——追隨最新 build
alphabetical（舊名 name） 按 tag 字母順序排序，取最後 有特殊命名規則（如 20260105-153）的 tag
digest 追蹤特定 tag（如 latest），偵測 digest 變化 使用 latest 或 main 但仍要 GitOps 留痕
(預先 v0.10) 自訂正則 用 allow-tags: regexp:^xxx 過濾後再套用上述 複雜命名（PR-{n}、release-{date} 等）
YAML — update-strategy 範例
annotations:
  # 多個 image 各用不同策略
  argocd-image-updater.argoproj.io/image-list: |
    api=myregistry.io/api,
    web=myregistry.io/web,
    sidecar=docker.io/library/redis

  # api：嚴格 SemVer（適合穩定的 backend service）
  argocd-image-updater.argoproj.io/api.update-strategy: semver

  # web：用 newest-build 追最新（dev 環境）
  argocd-image-updater.argoproj.io/web.update-strategy: newest-build

  # sidecar：固定 tag 追 digest 變化（如 redis:7-alpine 的 patch）
  argocd-image-updater.argoproj.io/sidecar.update-strategy: digest

3.3 allow-tags / ignore-tags

YAML — tag 過濾
annotations:
  argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp

  # allow-tags：只接受符合正則的 tag
  argocd-image-updater.argoproj.io/myapp.allow-tags: 'regexp:^v[0-9]+\.[0-9]+\.[0-9]+$'
  # 例如 v1.2.3 通過；v1.2.3-rc1 / latest 被擋

  # ignore-tags：明確排除特定 tag
  argocd-image-updater.argoproj.io/myapp.ignore-tags: "latest, develop, *-rc*, *-beta*"

  # platforms：限定特定平台（多架構 image）
  argocd-image-updater.argoproj.io/myapp.platforms: "linux/amd64,linux/arm64"

  # pull-secret：private registry 認證（見第 7 節）
  argocd-image-updater.argoproj.io/myapp.pull-secret: pullsecret:argocd/myregistry-creds

4Write-back：argocd vs git

4.1 兩種模式對比

面向argocd 方法（imperative）git 方法（declarative）
更新位置Application spec（K8s API）Git repo
Git 留痕❌ 沒有 commit✅ 完整 commit history
需要 Git 寫權限❌ 不需✅ 需 dedicated bot credentials
App-of-Apps 相容❌ 衝突（Git 中的 Application spec 覆蓋）✅ 完全相容
適合實驗 / PoC / 不用 GitOps 管 Application 的場景生產環境主流，符合 GitOps 哲學
Argo CD 衝突風險需要 ignoreApplicationDifferences（Ch.26）無——image 變更也是 Git commit
💡

生產環境永遠用 git write-back

argocd write-back 違反 GitOps 原則——Application spec 由 controller 直接修改，Git 中的 manifest 與實際 cluster 狀態不一致。下次有人從 Git 重建環境，image 就退回舊版本。git write-back 是唯一符合 GitOps 哲學的選擇。

4.2 git write-back 完整設定

YAML — git write-back 完整 annotations
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  annotations:
    # 必要：image list
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp

    # 必要：啟用 git write-back
    argocd-image-updater.argoproj.io/write-back-method: git

    # 可選：明確指定 branch（若 spec.source.targetRevision 不是 branch）
    argocd-image-updater.argoproj.io/git-branch: main

    # 可選：自訂 commit user / email
    argocd-image-updater.argoproj.io/git-commit-user: argocd-image-updater
    argocd-image-updater.argoproj.io/git-commit-email: image-updater@example.com

    # 可選：自訂 commit message template（Go template）
    argocd-image-updater.argoproj.io/git-commit-message: |
      chore: update {{range .Updated}}{{.Name}}={{.NewTag}} {{end}}

      Signed-off-by: ArgoCD Image Updater <image-updater@example.com>
      Updated by argocd-image-updater for {{.AppName}}

    # 可選：write-back-target（見下方）
spec:
  source:
    repoURL: https://github.com/myorg/gitops.git
    path: apps/my-app
    # targetRevision 必須是 branch（不要 HEAD / tag / commit sha）
    targetRevision: main

4.3 預設行為：寫到 .argocd-source-<appName>.yaml

預設情況下，git write-back 不會直接修改你的 values.yaml 或 kustomization.yaml。它建立 / 更新一個特殊檔案 .argocd-source-<appName>.yaml 在 Application 的 source path：

YAML — 自動產生的 .argocd-source-my-app.yaml
# Argo CD 會自動讀取此特殊檔案，作為 source override
# 不需要在 Application spec 中明確引用
helm:
  parameters:
    - name: image.name
      value: myregistry.io/myapp
      forceString: true
    - name: image.tag
      value: v1.2.3
      forceString: true
ℹ️

為什麼用 .argocd-source-<app>.yaml 而不直接改 values.yaml？

① 避免 merge conflict：Image Updater 與人類 commit 改不同檔案，不衝突；② 清晰分離：人類 commit 改 chart / values；機器 commit 改 image tag；③ 容易稽核：所有 image-updater 的 commit 都只改 .argocd-source-* 檔案。缺點：Helm template / kustomize build 本地執行時看不到 image 變更（必須透過 Argo CD reconcile）。

4.4 write-back-target：直接改 values 或 kustomization

若希望直接改 values.yaml 或 kustomization.yaml（讓 helm/kustomize 本地執行也能看到變更），用 write-back-target：

YAML — write-back-target 三種選擇
annotations:
  # 預設（不設定）：寫到 .argocd-source-<appName>.yaml

  # 選項 1：寫到指定的 helm values 檔案
  argocd-image-updater.argoproj.io/write-back-target: "helmvalues:./values-prod.yaml"

  # 選項 2：寫到 kustomization（如同 kustomize edit set image）
  argocd-image-updater.argoproj.io/write-back-target: kustomization

  # 選項 3：指定 kustomization 的路徑（相對於 source path）
  argocd-image-updater.argoproj.io/write-back-target: "kustomization:../../base"

  # 選項 4：絕對路徑（從 repo root 開始，必須以 / 開頭）
  argocd-image-updater.argoproj.io/write-back-target: "kustomization:/config/overlays/bar"

5Helm 整合

Helm chart 用 parameter override 機制。Image Updater 預設更新 image.name 與 image.tag 兩個 parameter，但實際 chart 可能用不同的 parameter 名（如 image.repository）：

YAML — Helm 整合完整範例
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-helm-app
  namespace: argocd
  annotations:
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp
    argocd-image-updater.argoproj.io/write-back-method: git

    # 指定 Helm parameter 名稱（如果 chart 用 image.repository 而非 image.name）
    argocd-image-updater.argoproj.io/myapp.helm.image-name: image.repository
    argocd-image-updater.argoproj.io/myapp.helm.image-tag: image.tag

    # 進階：nested key（如 frontend.image.tag）
    # argocd-image-updater.argoproj.io/frontend.helm.image-name: frontend.image.repository
    # argocd-image-updater.argoproj.io/frontend.helm.image-tag: frontend.image.tag

    # 更新策略：semver 1.x
    argocd-image-updater.argoproj.io/myapp.update-strategy: semver
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp:^1.0

    # 排除 RC / beta tag
    argocd-image-updater.argoproj.io/myapp.allow-tags: 'regexp:^v?[0-9]+\.[0-9]+\.[0-9]+$'
spec:
  source:
    repoURL: https://github.com/myorg/charts.git
    path: my-app
    targetRevision: main
    helm:
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: production
⚠️

Multi-image Helm chart 的 alias 限制

多個 image 都用 image-name / image-tag 結尾的 annotation，但不同 alias 必須對應到 chart 中不同的 parameter 路徑。例如 chart 有 frontend.image.tag 與 backend.image.tag，必須各自 annotation。常見錯誤：複製 annotation 但忘了改 helm path，造成多個 alias 都更新到同一個 parameter。

6Kustomize 整合

Kustomize 用 images field（kustomization.yaml 中的 image transformer）。Image Updater 直接更新該 field：

YAML — Kustomize 整合完整範例
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-kustomize-app
  namespace: argocd
  annotations:
    argocd-image-updater.argoproj.io/image-list: myapp=myregistry.io/myapp
    argocd-image-updater.argoproj.io/write-back-method: git

    # 用 kustomization write-back-target（直接改 kustomization.yaml）
    argocd-image-updater.argoproj.io/write-back-target: kustomization

    # 或指定其他位置的 kustomization（如改 base 而非 overlay）
    # argocd-image-updater.argoproj.io/write-back-target: "kustomization:../../base"

    argocd-image-updater.argoproj.io/myapp.update-strategy: semver
spec:
  source:
    repoURL: https://github.com/myorg/k8s-config.git
    path: overlays/production
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: production

## kustomization.yaml 在 overlays/production/ 變化為：
## apiVersion: kustomize.config.k8s.io/v1beta1
## kind: Kustomization
## resources:
##   - ../../base
## images:
##   - name: myregistry.io/myapp
##     newTag: v1.2.3      # <- image-updater 自動更新此行
💡

Kustomize image override 技巧

Kustomize 允許用一個 image 名稱「override」另一個。例如 base 用 quay.io/argoproj/argocd，overlay 可以 override 為 ghcr.io/argoproj/argocd（不同 registry）。Image Updater 用 manifestTargets.kustomize.name 指定要 override 的原始名稱。對於切換 registry 場景非常有用。

7Registry 認證

7.1 Docker Hub rate limit 問題

⚠️

Docker Hub 匿名帳號自 2020 年起有 pull limit

未認證 IP 每 6 小時 100 次 image pull。Image Updater 預設未認證——大量 Application 都用 Docker Hub image 時容易被擋。必設認證（即使是免費 Docker Hub 帳號也有 200 次/6h）。

7.2 在 ConfigMap 註冊 registry 認證

YAML — argocd-image-updater-config 含多 registry
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-image-updater-config
  namespace: argocd
data:
  registries.conf: |
    registries:
      # 1) Docker Hub（用認證避免 rate limit）
      - name: Docker Hub
        api_url: https://registry-1.docker.io
        prefix: docker.io
        ping: yes
        credentials: pullsecret:argocd/dockerhub-secret
        default: true       # 預設 registry（image-list 沒 prefix 時）

      # 2) GitHub Container Registry (GHCR)
      - name: GitHub Container Registry
        api_url: https://ghcr.io
        prefix: ghcr.io
        ping: yes
        credentials: pullsecret:argocd/ghcr-secret
        credsexpire: 12h

      # 3) AWS ECR（用 ecr-login helper 自動 refresh token）
      - name: AWS ECR
        api_url: https://ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com
        prefix: ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com
        ping: yes
        credentials: ext:/scripts/ecr-login.sh    # 外部腳本動態取得 token
        credsexpire: 10h

      # 4) Google Container Registry (GCR)
      - name: Google Container Registry
        api_url: https://gcr.io
        prefix: gcr.io
        ping: yes
        credentials: pullsecret:argocd/gcr-secret
        credsexpire: 1h

8與 ApplicationSet 整合

當 Application 由 ApplicationSet 產生時，controller 會把 Application spec 覆蓋回 template 定義的內容——Image Updater 的修改會被覆蓋。解法：用 Ch.26 學的 ignoreApplicationDifferences：

YAML — ApplicationSet + Image Updater
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: microservices
spec:
  goTemplate: true

  # 關鍵：讓 Image Updater 的修改不被 controller 覆蓋
  ignoreApplicationDifferences:
    - jsonPointers:
        # argocd write-back：忽略 spec.source.helm.parameters
        - /spec/source/helm/parameters
        # git write-back：忽略 .argocd-source-*.yaml 已自動處理（不需此設定）
        # 但若用 write-back-target=kustomization，可能需要

  generators:
    - list:
        elements:
          - name: api
            image: myregistry.io/api
          - name: web
            image: myregistry.io/web

  template:
    metadata:
      name: '{{.name}}-prod'
      annotations:
        # Image Updater annotation 也可以在 template 中
        argocd-image-updater.argoproj.io/image-list: '{{.name}}={{.image}}'
        argocd-image-updater.argoproj.io/write-back-method: git
        argocd-image-updater.argoproj.io/{{.name}}.update-strategy: semver
    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/charts.git
        path: '{{.name}}'
        targetRevision: main
      destination:
        server: https://kubernetes.default.svc
        namespace: production

  # 推薦：用 create-update 避免 generator 故障時刪除 production Application
  syncPolicy:
    applicationsSync: create-update
💡

git write-back + ApplicationSet 是最佳組合

git write-back 把 image 變更寫到 Git 中的 .argocd-source-<app>.yaml——這不是 Application spec 的一部分，不會與 ApplicationSet template 衝突。所以 git write-back 模式下，通常不需要 ignoreApplicationDifferences。這是 git write-back 比 argocd write-back 更適合大規模 GitOps 的另一個原因。

Image Updater 生產 Checklist

① 永遠用 git write-back（符合 GitOps，不需 ignoreApplicationDifferences）；② 用 dedicated bot account（不要用個人 PAT）；③ 所有 Application 都用 alias（image-list: myapp=registry/image）；④ 明確的 update-strategy（prod 用 semver，dev 用 newest-build）；⑤ allow-tags 限制 release pattern（避免 rc/beta tag 意外進 prod）；⑥ 必設 Docker Hub / GHCR 認證避免 rate limit；⑦ 單副本 deployment（避免 git push race）；⑧ 監控 controller log並 alert 在持續 error；⑨ git-commit-message template 包含 dry source ref方便追溯；⑩ 定期 review .argocd-source-*.yaml 移除已刪除 Application 的孤兒檔案。

📌 Key Takeaways

  • 🔄Image Updater 解決 CI 推 image 後誰更新 manifest 的問題：獨立 controller 週期性掃描 registry，自動更新 Application image。CI / CD 完全解耦，CI 只需 push image，更新邏輯集中。關鍵限制：只支援 Helm 與 Kustomize（不支援 plain YAML / Jsonnet）。
  • 📦核心 annotations 三必設：① image-list（含 alias：myapp=registry/image）；② write-back-method（git/argocd）；③ <alias>.update-strategy（5 種策略）。所有後續 annotation 都用 alias 引用，沒設 alias 後續引用會非常麻煩。
  • 🎯5 種 update strategies：① semver（預設，按 SemVer constraint）；② newest-build（舊名 latest，按 push 時間）；③ alphabetical（舊名 name，字母順序）；④ digest（追蹤特定 tag 的 digest 變化）；⑤ 配 allow-tags: regexp:... 自訂過濾。prod 用 semver，dev 用 newest-build。
  • 📝git write-back 是生產唯一選擇：argocd write-back 違反 GitOps（直接改 Application spec，與 Git 不一致）。git write-back 預設寫到 .argocd-source-<appName>.yaml——Argo CD 自動識別此特殊檔案。不會與人類 commit 的 values.yaml 衝突，且與 ApplicationSet 完全相容。
  • 🎚️write-back-target 控制寫入位置：① 不設（預設）：.argocd-source-*.yaml；② helmvalues:./values.yaml：直接改 values 檔；③ kustomization 或 kustomization:../../base：改 kustomization.yaml 的 images field。選 helmvalues / kustomization 的好處：本地 helm template 也能看到變更（適合不完全用 Argo CD 的環境）。
  • 🐳Helm 整合用 helm.image-name + helm.image-tag：預設更新 image.name + image.tag，多數 chart 用不同 path（如 image.repository），必須明確設定。Multi-image chart 每個 alias 各自 annotation，常見錯誤：複製 annotation 忘改 path 造成多 alias 寫到同一 parameter。
  • 🧱Kustomize 整合用 write-back-target=kustomization：直接更新 kustomization.yaml 的 images field（如同 kustomize edit set image）。可指定其他位置的 kustomization（如改 base 而非 overlay）。支援跨 registry override（base 用 quay.io，overlay override 為 ghcr.io）。
  • 🔑Docker Hub rate limit 是常見坑：匿名 100/6h，認證後 200/6h。必設認證。Registry 認證在 argocd-image-updater-config ConfigMap 統一管理，支援 prefix 自動 match registry（docker.io / ghcr.io / ECR / GCR）。ECR 用 credentials: ext:/scripts/ecr-login.sh 動態 refresh token。
  • 🔁ApplicationSet 整合首選 git write-back：因為 git write-back 寫到 .argocd-source-*.yaml（非 Application spec），不需要 ignoreApplicationDifferences。若用 argocd write-back 或 write-back-target=kustomization，需在 ApplicationSet spec 加 ignoreApplicationDifferences 讓 controller 忽略對應欄位。
  • 🛠️除錯三利器：① 看 controller log（findall errors）；② argocd-image-updater test CLI（在 pod 內測試 image 偵測）；③ port-forward metrics endpoint（:8081/metrics）。常見錯誤：alias 拼錯、helm.image-name 對應不上 chart、Git push 衝突（多副本）、Docker Hub rate limit。
