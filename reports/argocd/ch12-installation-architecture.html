Argo CD 安裝架構
與部署模式選型

Vol 3 進入 Argo CD 運維視角。本章是 Vol 3 的開篇——介紹四種官方安裝 manifest（install / namespace-install / ha / core）、四種主流安裝方式（manifest / Helm / Operator / autopilot），以及四種部署拓撲（standalone / hub-spoke / per-cluster / control-plane）的選型決策。為後續的 HA、安全、升級、DR 章節打好基礎。

📋

前置：已完成 Vol 1（GitOps 入門）與 Vol 2（應用程式管理）。理解 Argo CD 五大元件（Ch.03）。

🎯 學習目標

  • 理解四種官方 manifest（install / namespace-install / ha / core）的差異與使用場景
  • 能比較四種安裝方式（manifest / Helm / Operator / autopilot）的優缺點
  • 掌握四種部署拓撲（standalone / hub-spoke / per-cluster / control-plane），並能依組織規模選擇
  • 了解 self-managed Argo CD 的工作原理與設定方式
  • 能設計 App-of-Apps 啟動模式，實現「一鍵 bootstrap 整個叢集」
  • 使用決策樹快速判斷組織該選用哪種部署模式

1四種官方 Manifest 套件

Argo CD 在 GitHub Releases 提供四種預先打包的 manifest 套件，對應不同的部署需求。選錯 manifest 是新手最常見的踩坑點：例如想要 HA 卻用了單副本的 install.yaml，或想要 namespace 隔離卻使用了需要 cluster-admin 的標準版。

install.yaml
cluster-scoped
標準完整安裝。需要 cluster-admin 權限，可部署應用至任何 namespace（含安裝叢集本身）。最常用的選項。
namespace-install.yaml
namespace-scoped
只需 namespace 級權限。無 ClusterRole，本叢集只能部署到 Argo CD 自己的 namespace；外部叢集需提供 credentials。多 Argo CD 並存時使用。
ha/install.yaml
cluster-scoped + HA
與 install.yaml 相同元件，但所有元件多副本（含 Redis Sentinel）+ 反親和性。生產環境推薦。
core-install.yaml
無 UI / 無 server
只有 application-controller / repo-server / redis 三個核心元件。沒有 Web UI 或 API server，純 GitOps 操作（kubectl apply Application CRD）。極簡部署。

1.1 install.yaml 完整安裝

Bash — install.yaml 安裝
# 標準安裝（含所有元件、需要 cluster-admin）
$ kubectl create namespace argocd
$ kubectl apply -n argocd \
    --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.4.0/manifests/install.yaml

# 包含的元件：
# - argocd-server (1 replica)
# - argocd-application-controller (StatefulSet, 1 replica)
# - argocd-repo-server (1 replica)
# - argocd-applicationset-controller (1 replica)
# - argocd-notifications-controller (1 replica)
# - argocd-dex-server (1 replica)
# - argocd-redis (1 replica，無 HA)
# 加上：CRDs、ClusterRole、ClusterRoleBinding、ConfigMap、Secret、Service

1.2 namespace-install.yaml（多租戶 Argo CD）

當組織需要多個獨立的 Argo CD 實例（例如每個 BU 一個），namespace-install.yaml 是理想選擇——只需 namespace 級權限，無 ClusterRole 衝突：

Bash — namespace-install 安裝
# 1. 安裝 CRD（CRD 仍為 cluster-scoped，需要 cluster-admin 一次性執行）
$ kubectl apply --server-side --force-conflicts \
    -k https://github.com/argoproj/argo-cd/manifests/crds?ref=v3.4.0

# 2. 安裝 namespace-scoped Argo CD
$ kubectl create namespace team-a-argocd
$ kubectl apply -n team-a-argocd \
    --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.4.0/manifests/namespace-install.yaml

# 限制：
# - 本叢集只能部署到 team-a-argocd namespace
# - 部署到其他叢集需要 cluster credentials
# - 部署到本叢集其他 namespace：argocd cluster add <CONTEXT> --in-cluster --namespace <TARGET>

1.3 ha/install.yaml（生產推薦）

Bash — HA 安裝
# HA 安裝（生產環境推薦，含多副本 + Redis Sentinel）
$ kubectl apply -n argocd \
    --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.4.0/manifests/ha/install.yaml

# 與 install.yaml 的差異：
# - argocd-server: 3 replicas
# - argocd-applicationset-controller: 2 replicas
# - argocd-repo-server: 2 replicas
# - argocd-redis-ha: StatefulSet 3 replicas + Sentinel
# - argocd-redis-ha-haproxy: 3 replicas
# - 加入 PodAntiAffinity（避免同 Node）
# - argocd-application-controller 仍為 1 replica（StatefulSet，需手動調整 sharding）

1.4 core-install.yaml（極簡 GitOps）

Argo CD Core 是 v2.5 之後的選項，移除所有對外服務（UI、API server、Dex、Notifications、ApplicationSet），只保留純 GitOps 引擎。適合：

  • 已有外部 GitOps tooling（如自己的儀表板、CI 整合）的組織
  • 不需要 Web UI 的純自動化環境（如 GitOps「機器人」）
  • 資源極度受限的 edge 環境
⚠️

Core 模式無法使用 argocd CLI 大部分指令

Core 沒有 argocd-server，因此 argocd login、argocd app create、argocd app sync 等指令都無法使用。所有操作必須透過 kubectl apply Application CRD 完成。如果需要 CLI / UI，請選擇其他 manifest。

2四種安裝方式比較

官方 Manifest（kubectl apply）
優點最直接、無第三方依賴；官方推薦的入門方式
缺點客製化困難（要自己維護 patch 或 Kustomize overlay）；升級需手動操作
適合學習、demo、簡單 production；不需要客製化的場景
Helm Chart（argo-cd）
優點透過 values.yaml 集中管理所有客製化；社群維護活躍；可納入 GitOps
缺點需要對 Helm 熟悉；values 結構複雜；升級時要關注 values schema 變化
適合大多數生產部署，特別是需要客製化（HA / Resources / SSO / TLS）
Argo CD Operator
優點透過 ArgoCD CRD 宣告式管理；OpenShift GitOps 內建；多實例管理便利
缺點不如 Helm 社群活躍；版本可能落後上游；額外 Operator 元件
適合OpenShift 環境（GitOps Operator）；需要管理多個 Argo CD 實例

2.1 Helm Chart 完整 values 範例

YAML — argocd-values.yaml 生產等級配置
global:
  image:
    tag: "v3.4.0"           # 固定版本，不使用 latest
  domain: argocd.example.com

configs:
  params:
    server.insecure: true      # Ingress 終止 TLS 時設為 true
    controller.repo.server.timeout.seconds: "180"
  cm:
    timeout.reconciliation: "600s"    # 600s + Webhook 設定
    timeout.reconciliation.jitter: "120s"
    application.resourceTrackingMethod: annotation+label

server:
  replicas: 3                 # HA：3 replicas
  autoscaling:
    enabled: true
    minReplicas: 3
    maxReplicas: 10
  resources:
    requests: {cpu: "250m", memory: "256Mi"}
    limits: {cpu: "1000m", memory: "1Gi"}
  ingress:
    enabled: true
    ingressClassName: nginx
    hosts: [argocd.example.com]
    tls:
      - hosts: [argocd.example.com]
        secretName: argocd-tls

controller:
  replicas: 2                 # StatefulSet sharding
  env:
    - name: ARGOCD_CONTROLLER_REPLICAS
      value: "2"
  resources:
    requests: {cpu: "500m", memory: "1Gi"}
    limits: {cpu: "2000m", memory: "4Gi"}
  args:
    - --sharding-method=consistent-hashing

repoServer:
  replicas: 3                 # 多副本分散 manifest 生成負載
  resources:
    requests: {cpu: "500m", memory: "512Mi"}
    limits: {cpu: "2000m", memory: "2Gi"}

applicationSet:
  replicas: 2

redis-ha:
  enabled: true                # 啟用 Redis HA（Sentinel 模式）
redis:
  enabled: false               # 停用單副本 Redis

# 安裝/升級命令：
# helm repo add argo https://argoproj.github.io/argo-helm
# helm upgrade --install argocd argo/argo-cd \
#   --namespace argocd --create-namespace \
#   --version 7.x.x --values argocd-values.yaml

2.2 argocd-autopilot：開箱即用的 GitOps 結構

argocd-autopilot 是 argoproj-labs 提供的 CLI 工具，採用「opinionated」（有意見的）方式，一鍵建立完整的 self-managed Argo CD 設定，包含：

  • 部署 Argo CD 到目標叢集（含 ApplicationSet controller）
  • 建立私有 Git repo（或使用既有 repo）作為 GitOps single source of truth
  • 在 repo 建立標準化目錄結構（projects/、apps/、bootstrap/）
  • 建立 Application 讓 Argo CD 自我管理（self-managed）
Bash — argocd-autopilot bootstrap
# 1. 安裝 autopilot CLI（macOS）
$ brew install argocd-autopilot

# 2. 設定 git 認證
$ export GIT_TOKEN=ghp_xxxxxxxxxxxx
$ export GIT_REPO=https://github.com/myorg/argocd-gitops

# 3. 一鍵 bootstrap（自動建立 repo 並安裝 self-managed Argo CD）
$ argocd-autopilot repo bootstrap

# 完成後，Git repo 結構：
# argocd-gitops/
# ├── bootstrap/
# │   ├── argo-cd.yaml             # Self-managed Argo CD Application
# │   ├── cluster-resources/       # ClusterRoleBinding 等
# │   └── root.yaml                # Root App-of-Apps
# ├── projects/                    # AppProject 定義
# └── apps/                        # Application 定義

# 4. 建立第一個 project
$ argocd-autopilot project create my-team

# 5. 加入 Application 到 project
$ argocd-autopilot app create my-app \
    --app github.com/argoproj-labs/argocd-autopilot/examples/demo-app/ \
    --project my-team
💡

autopilot 的最大價值：建立 GitOps 結構慣例

新團隊面對 Argo CD 經常困惑「該如何組織 Git repo？專案目錄結構怎麼設計？如何讓 Argo CD 管理自己？」autopilot 提供了一套經過實戰驗證的開箱即用結構。即使日後不繼續用 autopilot CLI，這套結構也是很好的範本。

3部署拓撲模式

3.1 模式一：Standalone 單叢集

Argo CD 與目標應用在同一個叢集，沒有跨叢集管理。最簡單的部署模式，適合單一叢集的團隊或學習環境。

📊 Standalone 拓撲（同叢集自我管理）
Cluster A
Argo CD 管理控制台
→
Apps（同叢集） argocd ns + 其他 ns

3.2 模式二：Hub-and-Spoke（最常見的多叢集模式）

單一 Argo CD「Hub」管理多個 spoke 叢集。Hub 透過 cluster credentials 連接到 spoke 的 K8s API，將 manifest push 到各 spoke。spoke 不需要安裝 Argo CD，只需要服務帳戶。

🌐 Hub-and-Spoke 拓撲
🎯 Hub Cluster
Argo CD 控制中心
(管理叢集)
→
📦 Spoke: dev-cluster
📦 Spoke: staging-cluster
📦 Spoke: prod-us-east
📦 Spoke: prod-eu-west
面向Hub-and-Spoke 特性
優點單一管理介面、統一 RBAC、簡化跨叢集運維、適合中小規模團隊（~5-30 個叢集）
缺點Hub 是 SPOF；Hub 故障時無法部署任何 spoke；網路延遲影響 sync 效能；超大規模時 controller 負擔大
規模上限建議 30 個 spoke 以下；超過時建議啟用 Sharding（Ch.13）
網路需求Hub 需要能存取所有 spoke 的 K8s API（VPC peering、private link 或公開 API endpoint）

3.3 模式三：Per-Cluster Argo CD（每叢集獨立）

每個叢集都安裝自己的 Argo CD 實例，各自管理。沒有跨叢集集中管理，但提供完全的故障隔離與獨立性。

📊 Per-Cluster 拓撲
Cluster A
Argo CD A 獨立
— 無連線 —
Apps A 本地
Cluster B
Argo CD B 獨立
— 無連線 —
Apps B 本地
Cluster C
Argo CD C 獨立
— 無連線 —
Apps C 本地
面向Per-Cluster 特性
優點故障完全隔離（一個 Argo CD 掛掉不影響其他）；可獨立升級；網路延遲小（local API call）
缺點沒有統一管理介面；多 RBAC 設定要重複維護；管理成本高（N 個 Argo CD）
適合監管嚴格（每個叢集需獨立、不允許跨叢集存取）；超大規模（100+ 叢集）；混合雲且網路斷裂

3.4 模式四：Control Plane（多 Argo CD + 統一控制台）

結合 Per-Cluster 的隔離性與 Hub-and-Spoke 的統一管理。每個叢集有獨立 Argo CD，但有一個 control plane（如 Codefresh GitOps、ArgoCD Agent）提供統一儀表板。

ℹ️

ArgoCD Agent（v3.x）：原生 Control Plane 解決方案

Argo CD v3.x 開始引入 ArgoCD Agent 架構：每個 spoke 叢集執行獨立的 Argo CD 實例（pull 模式），但由中央 hub 集中管理 Application 定義。提供「per-cluster 隔離 + 中央可視」的雙重優勢。目前在 Red Hat OpenShift GitOps 1.19 已包含此功能，社群版仍在演進中。

4Self-Managed Argo CD

Self-Managed（自我管理）是 GitOps 哲學的極致實踐：讓 Argo CD 管理自己的部署。這意味著 Argo CD 的安裝 manifest（或 Helm values）也是 Git repo 中的一個 Application，未來升級或設定變更只需要 git push。

YAML — Self-Managed Argo CD Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: argocd
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: platform
  source:
    # Argo CD 自己的 Helm chart
    repoURL: https://argoproj.github.io/argo-helm
    chart: argo-cd
    targetRevision: 7.6.12          # 固定 chart 版本
    helm:
      valueFiles:
        - $values/argocd/values.yaml     # 從 values repo 讀取
  # Multiple Sources：chart 與 values 分開
  sources:
    - repoURL: https://argoproj.github.io/argo-helm
      chart: argo-cd
      targetRevision: 7.6.12
      helm:
        releaseName: argocd
        valueFiles:
          - $values/argocd/values.yaml
    - repoURL: https://github.com/myorg/argocd-config.git
      targetRevision: main
      ref: values
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: false     # ⚠️ 不要對 self-managed Argo CD 啟用 prune
      selfHeal: true
    syncOptions:
      - ServerSideApply=true
      - CreateNamespace=true
  # 忽略 Argo CD 自己的某些動態欄位
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas     # HPA 管理 replicas
⚠️

Self-Managed 的「雞生蛋」問題

第一次安裝 Argo CD 時，叢集還沒有 Argo CD，無法用 GitOps 方式部署。解決方案：第一次手動安裝（kubectl apply 或 helm install），然後立即建立 self-managed Application 讓 Argo CD 接管自己。後續所有升級和設定變更，都透過 Git push 完成。

⚠️

絕對不要對 self-managed Argo CD 啟用 prune

如果 Git 中的 values.yaml 意外清空或被誤刪，prune: true 會讓 Argo CD 把自己刪除！設定 prune: false（手動 prune），或加 argocd.argoproj.io/sync-options: Prune=false annotation 在所有 Argo CD 自身資源上。

5App-of-Apps 啟動模式（Cluster Bootstrapping）

App-of-Apps 是用於「一個 Application 管理一群 Applications」的設計模式。最常見的用法是 cluster bootstrapping——新叢集只需要部署一個 root App，這個 root App 會自動建立所有其他 platform Applications（cert-manager、ingress-nginx、Prometheus 等）。

Tree + YAML — App-of-Apps 結構
## Git Repo 結構
# argocd-bootstrap/
# ├── root-app.yaml              # 第一個建立的 App（指向下方目錄）
# └── apps/                      # 內含所有 platform Applications
#     ├── cert-manager.yaml
#     ├── ingress-nginx.yaml
#     ├── external-secrets.yaml
#     ├── monitoring-stack.yaml
#     └── ... （數十個 App）

## root-app.yaml：「一個 App 管理所有 Apps」
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://github.com/myorg/argocd-bootstrap.git
    targetRevision: main
    path: apps            # 指向 apps/ 目錄
    directory:
      recurse: true     # 遞迴讀取所有 .yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

## apps/cert-manager.yaml：被 root 管理的 Application
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cert-manager
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://charts.jetstack.io
    chart: cert-manager
    targetRevision: v1.14.0
    helm:
      valuesObject:
        installCRDs: true
  destination:
    server: https://kubernetes.default.svc
    namespace: cert-manager
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    syncOptions: [CreateNamespace=true]

## 啟動流程：
# 1. 第一次安裝 Argo CD（kubectl apply 或 helm install）
# 2. kubectl apply -f root-app.yaml
# 3. Argo CD 偵測到 root App，sync 後讀取 apps/ 目錄
# 4. 自動建立 apps/ 中所有 Application
# 5. 每個 child App 開始 sync 自己的 source（Helm chart / Git repo）
# 6. 整個叢集 platform 部署完成
💡

App-of-Apps + ApplicationSet 的進化

App-of-Apps 是經典模式，但在大量重複的 child App（如「為 5 個叢集各部署 cert-manager」）時很冗長。ApplicationSet（Vol 5）以 generators（list / cluster / git directory 等）動態生成 Application，更適合大規模場景。新部署建議直接用 ApplicationSet。

├── 生產環境 single-tenant  → ✅ ha/install.yaml
└── 學習 / 開發             → ✅ install.yaml

建議部署模式組合

📌 Key Takeaways

  • 📦四種官方 manifest：install（標準 cluster-admin）、namespace-install（多租戶 Argo CD）、ha/install（生產 HA）、core-install（無 UI 純 GitOps）。生產環境用 ha/install.yaml；CRD 對 namespace-install 仍需單獨安裝（cluster-admin 一次性）。
  • ⚙️四種安裝方式：Manifest（簡單）、Helm（最靈活，推薦生產）、Operator（OpenShift 內建）、autopilot（一鍵 GitOps 結構）。Helm 透過 values.yaml 集中管理客製化，是最常見的選擇。
  • 🌐四種部署拓撲：Standalone（單叢集）、Hub-and-Spoke（5-30 叢集主流）、Per-Cluster（隔離 / 監管）、Control Plane（30+ 叢集 / ArgoCD Agent）。Hub-and-Spoke 是中型組織的甜蜜點。
  • 🔄Self-Managed Argo CD 是 GitOps 極致：讓 Argo CD 管理自己的部署。第一次手動安裝後，立即建立 self-managed Application 接管。絕對不要對 self-managed Argo CD 啟用 prune（防止意外刪除自己）。
  • 🚀App-of-Apps 是經典 bootstrap 模式：root App 透過 directory recurse 自動建立所有 child App，實現「一鍵 bootstrap 整個叢集」。新部署可考慮直接用 ApplicationSet（Vol 5），對大規模場景更適合。
  • 🎯選型決策樹的核心問題：① 叢集數量；② 是否需要跨叢集統一管理；③ 是否監管限制；④ 是否需要 UI；⑤ 是否使用 OpenShift。先回答這 5 個問題，部署模式自然浮現。
