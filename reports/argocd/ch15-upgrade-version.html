升級流程與
版本管理（v2 → v3 完整指南）

Argo CD 升級看似簡單（kubectl apply 即可），但生產環境下一次失敗的升級會中斷整個 GitOps pipeline——所有 Application 停止調和、自動修復停擺、新部署無法進行。本章從版本策略開始，深入 v2 → v3 重大變更（含 RBAC、health status、CMP plugin），介紹三種升級策略，並提供完整 rollback 流程。

📋

前置：已閱讀 Ch.12（安裝架構）、Ch.13（HA）、Ch.14（安全）。理解 Helm chart upgrade、CRD lifecycle、Server-Side Apply。

🎯 學習目標

  • 掌握 Argo CD 的 SemVer 規則、跳版升級限制（必須逐個 minor 版本）、支援週期
  • 熟悉五階段升級流程：閱讀 release notes → 備份 → 測試 → 升級 → 驗證
  • 能識別 v2.x → v3.0 的 6 個重大變更，並完成所需的 pre-upgrade 修改
  • 理解 v3.3+ 必須使用 SSA（--server-side --force-conflicts）的原因
  • 能依環境特性選擇 In-place / Blue-Green / Self-Managed 升級策略
  • 處理 CRD 升級的特殊情境（serve 多版本、conversion webhook、storage migration）
  • 執行升級後完整的驗證 checklist，與必要時的 rollback 程序

1版本策略與支援週期

1.1 Argo CD 的 SemVer 規則

Argo CD 採用 semver-like 版本：MAJOR.MINOR.PATCH（例如 v3.4.0）。每種版本變動的意義：

變動類型範例意義
Patchv3.4.0 → v3.4.5純 bug fix，無 breaking change，可直接升級
Minorv3.3.x → v3.4.0新功能 + 部分 deprecation；通常向後相容，但需閱讀 release notes
Majorv2.14.x → v3.0.0重大 breaking changes、API 變更、預設值變更；必須做 pre-upgrade migration

1.2 支援週期與升級路徑

Argo CD 維護「最新兩個 minor 版本」的 patch release。例如：v3.4 發布後，v3.3 仍會收到 patch；v3.5 發布後，v3.3 停止維護。

⚠️

不能跨多個 minor 版本直接升級！

從 v2.10 跳到 v3.0 會錯過 v2.11、v2.12、v2.13、v2.14 期間累積的 deprecation warnings 和 migration 機會。正確路徑：v2.10 → v2.11 → ... → v2.14（最新 v2.x） → v3.0 → ... 每個 minor 都升級並等待穩定。生產環境建議停留在 minor 版本後一個 patch（如 v3.4.1 而非 v3.4.0）。

當前版本下個必經版本升級路徑
v2.10.xv2.14.x（最新 v2）v2.10 → v2.11 → v2.12 → v2.13 → v2.14
v2.14.xv3.0.x（major 升級）需執行 pre-upgrade migration（見第 3 節）
v3.0.xv3.4.x（最新）v3.0 → v3.1 → v3.2 → v3.3 → v3.4（v3.3 起需 SSA）
v3.4.xv3.4 patch直接 v3.4.0 → v3.4.5（無 breaking changes）

2五階段升級流程

PHASE 1
閱讀 Release Notes
逐版本檢視 breaking changes、deprecations、CRD 變更
PHASE 2
備份
CRD、ConfigMap、Secret、Application、AppProject 全備份
PHASE 3
Staging 測試
在非生產環境完整演練，含 rollback
PHASE 4
執行升級
維護窗口內執行，監控 controller 狀態
PHASE 5
驗證
所有 App 健康、sync、CLI/UI 正常

Phase 2 — 完整備份

Bash — 升級前備份腳本
#!/bin/bash
# 升級前備份腳本

BACKUP_DIR="argocd-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p $BACKUP_DIR

# 1. 備份所有 CRDs（必要！）
kubectl get crd applications.argoproj.io -o yaml > $BACKUP_DIR/crd-application.yaml
kubectl get crd appprojects.argoproj.io -o yaml > $BACKUP_DIR/crd-appproject.yaml
kubectl get crd applicationsets.argoproj.io -o yaml > $BACKUP_DIR/crd-applicationset.yaml

# 2. 備份所有 Application / AppProject / ApplicationSet
kubectl get applications -A -o yaml > $BACKUP_DIR/applications.yaml
kubectl get appprojects -A -o yaml > $BACKUP_DIR/appprojects.yaml
kubectl get applicationsets -A -o yaml > $BACKUP_DIR/applicationsets.yaml

# 3. 備份所有 ConfigMap（含設定）
kubectl get cm -n argocd -o yaml > $BACKUP_DIR/configmaps.yaml

# 4. 備份所有 Secret（cluster credentials、repo credentials、admin secret）
kubectl get secret -n argocd -o yaml > $BACKUP_DIR/secrets.yaml

# 5. 備份目前的 Argo CD manifest（用於 rollback）
ARGOCD_VERSION=$(kubectl -n argocd get deployment argocd-server -o jsonpath='{.spec.template.spec.containers[0].image}' | cut -d: -f2)
echo "Current version: $ARGOCD_VERSION" > $BACKUP_DIR/version.txt

curl -L -o $BACKUP_DIR/install.yaml \
  https://raw.githubusercontent.com/argoproj/argo-cd/$ARGOCD_VERSION/manifests/ha/install.yaml

# 6. 上傳到 S3 / off-cluster 儲存
tar -czf argocd-backup-$(date +%Y%m%d).tar.gz $BACKUP_DIR
aws s3 cp argocd-backup-$(date +%Y%m%d).tar.gz s3://my-backup-bucket/argocd/

echo "Backup completed: $BACKUP_DIR"

3v2.14 → v3.0 六大重大變更

Argo CD 3.0 是 low-risk major 升級，但仍含 6 個必須處理的 breaking changes：

⚠️1. RBAC fine-grained 變更
變更
v2 中 applications, update/delete, * 同時控制 App 本身與其管理的 K8s 資源；v3 起 update/delete 只控制 App，要操作管理資源需新增 update/* 或 delete/* 規則。
緩解
設定 server.rbac.disableApplicationFineGrainedRBACInheritance: false 維持 v2 行為，或 audit 並更新 RBAC policy。
⚠️2. logs RBAC 強制執行
變更
v2 預設 applications, get 自動含 logs 存取；v3 起 logs 必須明確授權。沒有 logs, get 規則的 user 在 UI 看不到 Pod 日誌。
緩解
為每個有 applications, get 的 role 新增對應的 logs, get, */*, allow 規則。
⚠️3. Health Status 不再持久化
變更
v3 預設 controller.resource.health.persist: false，Application CR 的 status.resources[].health 改為從 appTree 即時讀取（節省 etcd 空間）。某些舊版 GitOps tooling（如自製儀表板）讀取這個欄位會失效。
緩解
設定 controller.resource.health.persist: true 維持 v2 行為；或更新 tooling 改讀 status.health.status（這個仍持久化）。
⚠️4. CMP inline plugin 移除
變更
v3 完全移除 configManagementPlugins（在 argocd-cm 內定義 plugin）的支援。所有 CMP 必須改用 sidecar plugin（見 Ch.11）。
緩解
在 v2.x 期間就遷移到 sidecar plugin 並驗證可用，再升級。inline plugin 不會自動遷移。
⚠️5. tracking method 預設 annotation
變更
v3 預設 application.resourceTrackingMethod: annotation+label。仍使用 label tracking 的環境會發現所有 Application 顯示 OutOfSync（因為 annotation 還沒加入）。
緩解
v2.x 期間先切到 annotation+label 並逐個 sync 所有 App（--prune=false）。詳見 Ch.10。
⚠️6. 預設 Resource Exclusion 擴大
變更
v3 在 argocd-cm 加入大量預設 resource.exclusions（Endpoints, EndpointSlice, Lease, TokenReview 等高頻資源）。這降低 K8s API 負載，但若原本依賴觀察這些資源的 Application 會看不到它們。
緩解
大多數環境受益此變更。少數情境（觀察 ServiceMesh 端點）需手動移除特定排除項目。

3.1 Dex sub claim 變更（影響 SSO + RBAC）

v3 起，使用 Dex 的 SSO 認證從原本的 sub claim（不穩定的 base64 編碼字串）改用 federated_claims.user_id。原本 RBAC policy 中以 sub claim 寫的 user mapping 必須更新：

YAML — Dex sub claim 遷移
# 識別影響的 policy（base64-encoded sub claims 通常很長）
$ kubectl get cm argocd-rbac-cm -n argocd -o jsonpath='{.data.policy\.csv}' | grep -E "^g, [A-Za-z0-9+/=]{20,}"

# Decode 看看是哪個使用者
$ echo "ChdleGFtcGxlQGFyZ29wcm9qLmlvEgJkZXhfY29ubl9pZA" | base64 -d
# 輸出：example@argoproj.iodex_conn_id

# 更新 policy.csv：
data:
  policy.csv: |
    # 舊（v2 行為）：
    # g, ChdleGFtcGxlQGFyZ29wcm9qLmlvEgJkZXhfY29ubl9pZA, role:example
    # 新（v3 行為）：
    g, example@argoproj.io, role:example

4Server-Side Apply 必要性（v3.3+）

從 v3.3 起，Argo CD manifest 安裝必須使用 Server-Side Apply。原因是 ApplicationSet CRD 的 size 超過 client-side apply 的 256KB last-applied-configuration annotation 上限，會觸發以下錯誤：

Error — client-side apply 失敗訊息
The CustomResourceDefinition "applicationsets.argoproj.io" is invalid:
  metadata.annotations: Too long: may not be more than 262144 bytes
Bash — 正確使用 SSA 升級
# ✅ 正確（v3.3+ 必要）
$ kubectl apply -n argocd \
    --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.4.0/manifests/ha/install.yaml

# ❌ 錯誤（v3.3+ 會失敗）
$ kubectl apply -n argocd -f <url>

# --server-side：使用 SSA 機制（managedFields 取代 last-applied annotation）
# --force-conflicts：接管之前由其他工具（如 Helm、舊 kubectl apply）管理的欄位

# Helm 用戶不受影響：
# helm upgrade argocd argo/argo-cd --version 7.x.x 內部使用 SSA
⚠️

--force-conflicts 會覆蓋客製化欄位

--force-conflicts 接管之前由其他工具管理的欄位。若你之前用 kubectl apply 編輯過 Argo CD 元件（如修改 affinity、env、resources），這些客製化會被官方 manifest 覆蓋。建議改用 Helm 或 Kustomize overlay 管理客製化，不要直接 kubectl edit Argo CD 資源。

5三種升級策略

In-place（同地）
原理直接在現有 Argo CD 上 apply 新版 manifest
優點最簡單、無額外資源、HA 部署可滾動升級
缺點升級失敗時 Argo CD 自身受影響，rollback 較複雜
適合minor / patch 升級，HA 部署
Blue-Green（並行）
原理新 namespace 部署新版本，驗證後切換流量並刪除舊版
優點完全隔離、rollback 即時（切回舊 namespace）
缺點需要兩倍資源、需處理 Application/Project 遷移、cluster credentials 需複製
適合Major 升級（v2 → v3）、高度敏感環境
Self-Managed (GitOps)
原理Argo CD 透過 Application 管理自己，更新 Git 中的 chart 版本即升級
優點符合 GitOps、版本記錄在 Git、可自動化
缺點「self-update 失敗時無法自我修復」的雞生蛋問題
適合已實作 self-managed 架構的環境（見 Ch.12）

5.1 In-place 升級（最常用）

Bash — In-place 升級流程（Helm）
## 1. 更新 Helm repo
$ helm repo update argo

## 2. 檢查可用版本
$ helm search repo argo/argo-cd --versions | head -20

## 3. Diff（dry-run 看會變更什麼）
$ helm diff upgrade argocd argo/argo-cd \
    --version 7.5.0 \
    --namespace argocd \
    --values argocd-values.yaml

## 4. 升級（HA 部署可滾動）
$ helm upgrade argocd argo/argo-cd \
    --version 7.5.0 \
    --namespace argocd \
    --values argocd-values.yaml \
    --wait \
    --timeout 10m

## 5. 監控 rollout 狀態
$ kubectl rollout status -n argocd deployment/argocd-server
$ kubectl rollout status -n argocd statefulset/argocd-application-controller
$ kubectl get pods -n argocd

5.2 Blue-Green 升級（major 版本推薦）

Bash — Blue-Green 升級流程
## 1. 在新 namespace 部署新版（不影響原本 argocd ns）
$ kubectl create namespace argocd-v3

$ helm install argocd-v3 argo/argo-cd \
    --version 7.5.0 \
    --namespace argocd-v3 \
    --values argocd-values.yaml

## 2. 從舊 namespace 複製 cluster credentials / repo credentials
$ kubectl get secrets -n argocd \
    -l argocd.argoproj.io/secret-type=cluster \
    -o yaml | sed 's/namespace: argocd/namespace: argocd-v3/' | \
    kubectl apply -f -

$ kubectl get secrets -n argocd \
    -l argocd.argoproj.io/secret-type=repository \
    -o yaml | sed 's/namespace: argocd/namespace: argocd-v3/' | \
    kubectl apply -f -

## 3. 用 GitOps 在新 instance 重新註冊所有 Application（從 Git 讀取）
## 若使用 self-managed 架構，只需 apply root Application 即可

## 4. 驗證新 instance：
$ argocd login argocd-v3.example.com  # 新 ingress
$ argocd app list                      # 確認所有 App 在新 instance 可見
$ argocd app sync test-app --dry-run  # 測試 sync

## 5. 切換流量（Ingress / DNS）
$ kubectl patch ingress argocd-server -n argocd \
    --type merge -p '{"spec":{"rules":[{"host":"argocd.example.com","http":{"paths":[{"backend":{"service":{"name":"argocd-server","namespace":"argocd-v3"}}}]}}]}}'

## 6. 確認穩定後（1-2 週），刪除舊 namespace
$ kubectl delete namespace argocd
$ kubectl create namespace argocd  # 重新建立（為了下次 blue-green）

5.3 Self-Managed GitOps 升級

若已建立 self-managed Argo CD（見 Ch.12 第 4 節），升級就是修改 Git 中的 chart 版本：

Bash + YAML — Self-Managed 升級
## Git 中的 self-managed Argo CD Application：
spec:
  source:
    repoURL: https://argoproj.github.io/argo-helm
    chart: argo-cd
    targetRevision: 7.5.0      # ← 修改這裡（從 7.4.x 改為 7.5.0）
    helm:
      valueFiles:
        - $values/argocd/values.yaml

## 流程：
# 1. 修改 Git 中的 targetRevision
$ git checkout -b upgrade/argocd-7.5.0
$ vim argocd/values.yaml  # 順便處理 breaking changes
$ git commit -am "Upgrade Argo CD to 7.5.0"
$ git push origin upgrade/argocd-7.5.0

# 2. 建立 PR、code review、merge

# 3. Argo CD 偵測到變更，自動 sync 自己（升級）
# 4. application-controller 重啟期間，sync queue 暫停（最多 2-3 分鐘）
# 5. 升級完成後，自動恢復所有 App 的 reconciliation

## ⚠️ 重要：自我升級的限制
# 若新版本有嚴重 bug，Argo CD 自我修復失效，需要手動介入：
$ helm rollback argocd -n argocd  # 或 kubectl apply 舊 manifest

6CRD 升級特殊處理

Argo CD 自身的 CRD（Application、AppProject、ApplicationSet）由 Argo CD 升級腳本處理。但使用者管理的 CRD（透過 Application 部署的 cert-manager CRD、Argo Rollouts CRD 等）若有版本變更（如 v1 → v2），需要特別處理。

CRD 版本升級安全流程

YAML — CRD 多版本 serve 期間設定
## 階段 1：CRD 同時 serve v1 與 v2，仍以 v1 為 storage
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: myresources.example.com
spec:
  group: example.com
  versions:
    - name: v1
      served: true
      storage: true     # 仍是 storage version
    - name: v2
      served: true     # 開始 serve v2
      storage: false
  # conversion webhook（v1 ↔ v2 互轉）
  conversion:
    strategy: Webhook
    webhook:
      clientConfig:
        service:
          name: crd-converter
          namespace: my-operator

## 階段 2：所有 custom resources 改用 v2 API（手動 + Argo CD ignoreDifferences）
ignoreDifferences:
  - group: example.com
    kind: MyResource
    jsonPointers:
      - /apiVersion      # 過渡期忽略 apiVersion 差異

## 階段 3：切換 storage 為 v2
versions:
  - name: v1
    served: true     # 仍 serve（向後相容）
    storage: false
  - name: v2
    served: true
    storage: true     # 改為 storage version

## 階段 4：PostSync hook 觸發 storage migration
apiVersion: batch/v1
kind: Job
metadata:
  name: migrate-myresources-to-v2
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrator
          image: bitnami/kubectl:latest
          command: ["sh", "-c"]
          args:
            - |
              # 讀寫所有 v1 資源以觸發 v2 storage 寫入
              kubectl get myresources -A -o json | \
                jq -c '.items[]' | \
                while read item; do
                  echo "$item" | kubectl apply -f -
                done
ℹ️

kube-storage-version-migrator 自動化 storage migration

K8s 官方提供的 kube-storage-version-migrator 可自動偵測並重寫所有 storage 不一致的物件，比 PostSync hook 更可靠。生產環境推薦同時部署這個 controller。

7驗證 Checklist 與 Rollback

升級後驗證 Checklist

Bash — 完整驗證腳本
## 1. 確認版本
$ argocd version
$ kubectl get pods -n argocd -o jsonpath='{.items[*].spec.containers[*].image}' | tr ' ' '\n' | sort -u

## 2. 確認所有 pod 健康
$ kubectl get pods -n argocd
## 預期：所有 Pod Ready 1/1，沒有 CrashLoopBackOff / ImagePullBackOff

## 3. 確認 CRD 正確
$ kubectl get crd applications.argoproj.io -o jsonpath='{.spec.versions[*].name}'
$ kubectl get crd appprojects.argoproj.io -o jsonpath='{.spec.versions[*].name}'
$ kubectl get crd applicationsets.argoproj.io -o jsonpath='{.spec.versions[*].name}'

## 4. 確認所有 Application 仍可見
$ argocd app list | wc -l   # 確認與升級前數量相同

## 5. 確認所有 Application 為 Synced + Healthy
$ argocd app list -o json | jq -r '.[] | select(.status.sync.status != "Synced" or .status.health.status != "Healthy") | .metadata.name'
## 預期：空輸出（所有 App 健康）

## 6. 測試 sync 操作
$ argocd app sync test-app

## 7. 測試 SSO 登入
$ argocd login argocd.example.com --sso

## 8. 確認 RBAC 仍正常
$ argocd account can-i sync application '*/*'

## 9. 檢查 controller log 無 ERROR / FATAL

Rollback 程序

Bash — 升級失敗 Rollback
## 情境：升級到 v3.x 後發現嚴重 bug，回滾到 v2.14

## 方式 A：Helm rollback（最簡單）
$ helm history argocd -n argocd
# REVISION  STATUS    CHART       APP VERSION  DESCRIPTION
# 5         deployed  argo-cd-7.5  v3.4.0       Upgrade complete
# 4         superseded argo-cd-6.x v2.14.0      Upgrade complete

$ helm rollback argocd 4 -n argocd
# 注意：rollback 不會還原 CRD changes！

## 方式 B：從備份還原 CRD（必要！）
$ kubectl apply --server-side --force-conflicts \
    -f $BACKUP_DIR/crd-application.yaml \
    -f $BACKUP_DIR/crd-appproject.yaml \
    -f $BACKUP_DIR/crd-applicationset.yaml

## 方式 C：完整 manifest 重新 apply
$ kubectl apply -n argocd \
    --server-side --force-conflicts \
    -f $BACKUP_DIR/install.yaml

## 方式 D：Blue-Green 切換回舊 instance（最快，無中斷）
$ kubectl patch ingress argocd-server -n argocd \
    --type merge -p '{"spec":{"rules":[{"host":"argocd.example.com","http":{"paths":[{"backend":{"service":{"name":"argocd-server","namespace":"argocd"}}}]}}]}}'

## Rollback 後驗證
$ argocd version
$ argocd app list  # 確認 Application 數量正確
⚠️

CRD downgrade 是危險操作

新版 CRD 中加入的欄位若已被 Application 使用，downgrade 後這些欄位會被 K8s 視為「無效」並可能丟失。建議：① 升級前完整備份 Application；② major 升級用 Blue-Green 策略避免直接 CRD downgrade；③ rollback 後立即從備份還原 Application（kubectl apply -f $BACKUP_DIR/applications.yaml）。

📌 Key Takeaways

  • 📅不可跳版升級：必須逐個 minor 版本（v2.10 → v2.11 → ... → v2.14 → v3.0）。Argo CD 只維護「最新兩個 minor」的 patch release，超過版本就無法獲得 bug fix。生產環境停留在「最新 minor 的後一個 patch」最穩定。
  • 🔍v2 → v3 六大 breaking changes：① RBAC fine-grained 變更（update/delete 不再繼承）；② logs 強制獨立 RBAC；③ Health status 不持久化；④ CMP inline plugin 移除；⑤ tracking method 預設 annotation；⑥ resource exclusion 預設值擴大。每個都需 pre-upgrade migration。
  • ⚙️v3.3+ 必須使用 SSA：kubectl apply --server-side --force-conflicts。原因是 ApplicationSet CRD 超過 256KB annotation 上限。Helm 用戶不受影響（內部已用 SSA）。
  • 🔄三種升級策略選擇：① In-place 適合 minor / patch 升級；② Blue-Green 適合 major 升級或高度敏感環境（兩倍資源代價，但 rollback 即時）；③ Self-Managed 是 GitOps 哲學的極致，但有 self-update 失敗的雞生蛋風險。
  • 📦使用者 CRD 升級需要四階段：serve 多版本 → custom resource 改用新版 → 切換 storage → PostSync hook 觸發 storage migration（或用 kube-storage-version-migrator）。
  • 🛡️升級前完整備份是底線：CRD、所有 Application/AppProject、ConfigMap、Secret 必須完整備份到 off-cluster 儲存。Helm rollback 不會還原 CRD changes，必須手動還原。Major 升級強烈建議用 Blue-Green 策略。
