Sync 策略精細控制：
Automated Sync、Sync Options、Sync Windows

Ch.02 建立了 syncPolicy 的基礎認識。本章深入所有 Sync 控制機制：Automated Sync 的全部選項（含 v3.x 新增的 enabled 旗標）、完整的 syncOptions 參考、三種 apply 方法的比較、ignoreDifferences 全欄位說明，以及 Sync Windows 時間窗口設計。

📋

前置：已閱讀 Ch.02（Application CRD 與 Sync Status 基礎）。本章為進階深入，建議已有 Application 部署實作經驗。

🎯 學習目標

  • 掌握 Automated Sync 的 prune / selfHeal / allowEmpty / enabled 四個旗標的精確行為
  • 熟悉 retry backoff 的指數退避計算公式，避免無限重試風暴
  • 能從完整的 syncOptions 清單中，為不同場景選擇適當的選項組合
  • 理解 kubectl apply / Server-Side Apply / Replace 三種 apply 方法的本質差異與適用場景
  • 精通 ignoreDifferences 的三種 path 類型（jsonPointers / jqPathExpressions / managedFieldsManagers）
  • 設計符合組織需求的 Sync Windows（allow + deny 組合），並理解 deny 優先的運作邏輯
  • 能組合出生產環境推薦的完整 syncPolicy 配置

1Automated Sync 深度說明

Automated Sync 讓 Argo CD 自動偵測並套用 Git 變更，是 GitOps 自動化的核心。但它不是一個「全或無」的開關——每個子選項都有重要的行為差異，必須謹慎設計。

1.1 prune / selfHeal / allowEmpty 精確行為

旗標預設行為說明安全注意
prune false Git 中刪除的資源，是否自動從叢集中刪除。false 時，刪除的資源會變成 OutOfSync 但不會被刪除，需手動 sync（並勾選 prune）才能清除。 生產環境建議謹慎啟用。搭配 PruneLast=true 與 PrunePropagationPolicy=foreground 更安全
selfHeal false 叢集狀態偏離 Git（drift）時，5 秒後自動 sync 修復。啟用後，任何直接對叢集的手動修改都會被還原。 啟用後無法手動 rollback（rollback 按鈕灰色）；除非先暫停 selfHeal 或改用 git revert
allowEmpty false 允許 source 為零個資源時仍執行 sync。預設 false 是安全護欄：若 Git repo 意外清空，不會刪除叢集中所有資源。 幾乎不應設為 true。只有確實需要「空的 Application」的特殊情境才考慮
YAML — automated sync 四個旗標完整說明
syncPolicy:
  automated:
    # 安全護欄順序：建議先開 selfHeal，確認穩定後再開 prune
    prune: true      # Git 刪除的資源自動從叢集刪除（謹慎！）
    selfHeal: true   # drift 5 秒後自動修復
    allowEmpty: false # 不允許空資源（安全護欄，通常保持 false）

    # v3.x 新增：明確啟用/停用 automated sync 而不移除整個 automated 區塊
    # enabled: true  # 省略（或 null）等同 true
    # enabled: false # 停用 automated sync，但保留 prune/selfHeal 設定

1.2 automated.enabled 旗標（v3.x）

v3.x 新增 automated.enabled 旗標，解決了一個長期痛點：以前若要臨時停用 automated sync，必須刪除整個 automated: 區塊，再次啟用時要重新設定 prune / selfHeal 等選項。現在只需切換 enabled: false/true：

YAML — enabled 旗標的用途
## 場景：臨時凍結 automated sync（例如緊急維護期間）
syncPolicy:
  automated:
    enabled: false    # 停用 automated sync
    prune: true      # 設定保留，恢復時不需重新設定
    selfHeal: true   # 同上

## 注意事項：
# - enabled 省略或設為 null，等同於 true（向後相容）
# - enabled: false 時，prune/selfHeal/allowEmpty 的值被保留但不生效
# - ApplicationSet 管理的 App：直接修改 App 的 automated 欄位無效
#   需透過 ApplicationSet 的 Controlling Resource Modification 機制

1.3 retry 指數退避策略

當 sync 失敗時，retry 機制避免立即重試（會加重問題），改用指數退避（exponential backoff）逐漸拉長等待時間：

YAML — retry 完整設定與計算說明
syncPolicy:
  retry:
    limit: 5        # 最多重試 5 次（-1 = 無限次，慎用）
    backoff:
      duration: 5s  # 初始等待時間（第一次重試前等 5 秒）
      factor: 2    # 每次重試後，等待時間乘以此係數
      maxDuration: 3m  # 等待時間上限（不超過 3 分鐘）

## 退避計算範例（factor=2, duration=5s, maxDuration=3m）
# 失敗 1 → 等 5s → 重試
# 失敗 2 → 等 10s → 重試
# 失敗 3 → 等 20s → 重試
# 失敗 4 → 等 40s → 重試
# 失敗 5 → 等 80s → 重試（未超過 3m 上限）
# 超過 limit（5次）→ 停止重試，標記 SyncFailed

## 重要行為：
# - 同一 commit SHA 的 sync 失敗後，不會自動重試（需 git push 新 commit 或手動觸發）
# - retry 只適用於暫時性失敗（如 CRD race condition），不適用於配置錯誤
⚠️

重要行為：相同 commit SHA 不自動重試

Argo CD 不會對「同一 commit SHA + 相同參數」的失敗 sync 自動重試。這防止了無限重試風暴，但也意味著：若 sync 因為 CRD 尚未就緒而失敗，等 CRD 就緒後並不會自動觸發新的 sync——需要有新的 Git commit 或手動觸發 sync。

2Sync Options 完整參考

Sync Options 設定在 spec.syncPolicy.syncOptions（Application 層級），或以 annotation argocd.argoproj.io/sync-options 設定在個別資源上。資源層級的設定會覆蓋 Application 層級的同名設定。

2.1 Apply 行為類

ServerSideApply=true
Server-Side Apply
使用 kubectl apply --server-side。Kubernetes API server 負責 merge 邏輯與欄位所有權追蹤。大型 CRD（>262KB）必須使用；多工具共同管理同一資源時建議使用。
App / 資源 兩層
ApplyOutOfSyncOnly=true
只 Apply OutOfSync 資源
跳過所有 Synced 的資源，只 apply 實際 OutOfSync 的資源。對有數千個資源的大型 Application 可大幅降低 API server 負載與 sync 時間。Sync Hooks 仍會執行（與 Selective Sync 的差異）。
App 層級
Replace=true
強制 Replace（刪除重建）
使用 kubectl replace 取代 apply：先刪除資源再重建。適合某些不支援 patch 的資源類型（如 Kubernetes admission webhook），但會造成短暫服務中斷。謹慎使用。
App / 資源 兩層
Validate=false
跳過 Schema 驗證
等同 kubectl apply --validate=false。用於使用 RawExtension 的資源（如 ServiceCatalog），這類資源的 schema 無法被 kubectl 正確驗證。
App / 資源 兩層
SkipDryRunOnMissingResource=true
跳過缺失資源的 Dry Run
CRD 與其 CR 在同一個 Application 時，Argo CD 在 CRD 尚未安裝的情況下會 dry-run 失敗。此選項跳過 dry-run，讓 CRD 先安裝後 CR 再建立。搭配 Sync Waves 效果更好。
App / 資源 兩層
RespectIgnoreDifferences=true
Sync 時也尊重 ignoreDifferences
預設情況下，ignoreDifferences 只影響 diff 計算（不影響 sync 操作）。設定此選項後，sync 時也不會覆蓋 ignoreDifferences 中定義的欄位，讓 HPA 管理的 replicas 在 sync 後不被還原。
App 層級

2.2 Prune 行為類

PruneLast=true
最後才執行 Prune
資源的刪除（prune）在所有資源 apply 完成且 healthy 後才執行，作為 sync 的最後一個隱式 wave。避免「先刪除 ConfigMap，導致依賴它的 Deployment 在新 ConfigMap 建立前 crash」的情境。
App / 資源 兩層
Prune=false
保護特定資源不被刪除
在資源 annotation 上設定，防止該資源被 prune。常用於 PVC、Namespace 等需要手動管理生命週期的資源。即使 Application 層級啟用了 prune，加此 annotation 的資源也不會被刪除。
資源層級 annotation
Prune=confirm
刪除前需人工確認
資源即將被 prune 時，sync 操作暫停並在 UI 顯示「Confirm Pruning」按鈕，需人工確認後才繼續刪除。適用於 Namespace、PersistentVolume 等高風險資源。
App / 資源 兩層
PrunePropagationPolicy=foreground
刪除級聯策略
foreground（預設）：等待所有子資源刪除後才刪除父資源；background：立即刪除父資源，子資源非同步刪除；orphan：只刪除父資源，子資源保留（成為孤立資源）。
App 層級

2.3 Namespace 管理類

CreateNamespace=true
自動建立目標 Namespace
若目標 namespace 不存在，自動建立。啟用後 namespace 由 Argo CD 管理（含 cascade delete 可能性）。搭配 managedNamespaceMetadata 可為自動建立的 namespace 加上 labels / annotations。
App 層級
Delete=confirm
刪除 Application 前需確認
刪除 Application 時需人工確認（在 UI 點擊或加入 argocd.argoproj.io/deletion-approved annotation）。適合生產環境防止意外刪除整個 Application 及其所有資源。
App / 資源 兩層

2.4 安全防護類

FailOnSharedResource=true
共用資源時 Sync 失敗
當發現一個 Kubernetes 資源被多個 Application 追蹤時，sync 失敗（預設情況是繼續執行，可能造成多個 App 互相覆蓋同一資源）。用於嚴格防止多個 App 管理同一資源的衝突。
App 層級

2.5 資源層級 annotation 用法

部分 Sync Options 可以在個別資源的 annotation 上設定，覆蓋 Application 層級的設定。多個 option 用逗號分隔：

YAML — 資源層級 annotation 範例
## 範例一：PVC 保護不被 prune，且刪除前需確認
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: database-pvc
  annotations:
    # 多個 option 用逗號分隔（去除空白）
    argocd.argoproj.io/sync-options: Prune=false,Delete=confirm

---
## 範例二：大型 CRD 跳過 validation
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: largecrds.example.com
  annotations:
    argocd.argoproj.io/sync-options: ServerSideApply=true,SkipDryRunOnMissingResource=true

---
## 範例三：Namespace 保留（即使 App 被刪除）
apiVersion: v1
kind: Namespace
metadata:
  name: my-important-namespace
  annotations:
    argocd.argoproj.io/sync-options: Prune=false

3Apply 方法：kubectl apply vs Server-Side Apply vs Replace

Argo CD 支援三種 apply 方法，選擇正確的方法對於避免欄位衝突和確保資源正確套用至關重要：

kubectl apply（預設）
Client-Side Apply。將 last-applied-configuration annotation 存在資源上，下次 apply 時與之比較。簡單可靠，但有 annotation 大小限制（256KB），大型 CRD 會失敗。
✓ 簡單、廣泛支援
✓ 無需額外設定
✗ 256KB annotation 限制
✗ 多工具共管時欄位覆蓋問題
Server-Side Apply（SSA）
由 Kubernetes API server 執行 merge 邏輯，以 managedFields 追蹤欄位所有權。無大小限制，多工具共管時各自追蹤自己的欄位，不互相覆蓋。
✓ 無大小限制
✓ 欄位所有權追蹤，多工具共存
✓ 更精確的 conflict detection
✗ 初次啟用可能出現所有權衝突
✗ 需搭配 --force-conflicts 處理遷移
Replace（替換）
先刪除資源再重建（kubectl replace）。適用於不支援 patch 的特殊資源（如某些 admission webhooks）。會造成短暫不可用，謹慎在生產環境使用。
✓ 確保完全替換，無遺留欄位
✗ 刪除再重建，有短暫中斷
✗ 只在特殊情況使用
💡

生產環境推薦：ServerSideApply

新部署的 Argo CD Application 建議直接使用 ServerSideApply=true。對於已有 Application 的遷移，先加上 --force-conflicts 進行一次強制 sync 以轉移欄位所有權，之後就能穩定使用 SSA。這也是官方安裝文件建議使用 --server-side --force-conflicts 的原因。

YAML — managedNamespaceMetadata（CreateNamespace 配合使用）
syncPolicy:
  syncOptions:
    - CreateNamespace=true
  # 為自動建立的 Namespace 加上 labels / annotations
  managedNamespaceMetadata:
    labels:
      team: backend
      environment: production
      pod-security.kubernetes.io/enforce: baseline
    annotations:
      contact: backend-team@example.com
      cost-center: "CC-1234"

4Compare Options 與 ignoreDifferences

ignoreDifferences 讓 Argo CD 在計算 diff 時忽略特定欄位，防止動態管理的欄位（如 HPA 調整的 replicas）不斷觸發 OutOfSync。

4.1 ignoreDifferences 三種 path 類型

YAML — ignoreDifferences 完整三種類型
ignoreDifferences:

  ## 類型一：jsonPointers（RFC 6901 JSON Pointer 語法）
  ## 最常用，語法簡單直觀
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas           # HPA 管理 replicas
      - /metadata/resourceVersion # 系統自動更新欄位

  ## 類型二：jqPathExpressions（jq 查詢語法，更強大）
  ## 支援條件過濾、陣列操作
  - group: apps
    kind: Deployment
    jqPathExpressions:
      # 忽略所有 container 的 image（admission webhook 可能注入 digest）
      - .spec.template.spec.containers[]?.image
      # 忽略特定 annotation
      - .metadata.annotations["kubectl.kubernetes.io/last-applied-configuration"]

  ## 類型三：managedFieldsManagers（Server-Side Apply 欄位所有權）
  ## 忽略由特定 manager 管理的欄位
  - group: apps
    kind: Deployment
    managedFieldsManagers:
      - kube-controller-manager  # 忽略 controller manager 管理的欄位
      - helm                      # 忽略 helm 管理的欄位

  ## glob 通配：適用所有 group / kind
  - group: "*"
    kind: "*"
    jsonPointers:
      - /metadata/generation  # 對所有資源忽略 generation

  ## 指定特定資源名稱（非通配，精確匹配）
  - group: apps
    kind: Deployment
    name: my-specific-deployment  # 只對這個 Deployment 生效
    namespace: production
    jsonPointers:
      - /spec/replicas

4.2 RespectIgnoreDifferences：讓 Sync 也尊重忽略設定

預設情況，ignoreDifferences 只影響 diff 計算（決定 Sync Status），但 sync 操作仍然會 apply 完整的 manifest（可能覆蓋被忽略的欄位）。

設定 RespectIgnoreDifferences=true 後，sync 時也不會觸碰 ignoreDifferences 中定義的欄位，讓 HPA 設定的 replicas 在 sync 後不被還原：

YAML — RespectIgnoreDifferences 完整範例
spec:
  syncPolicy:
    syncOptions:
      # 讓 sync 也尊重 ignoreDifferences（防止 HPA replicas 被覆蓋）
      - RespectIgnoreDifferences=true
      - ServerSideApply=true  # 搭配 SSA 效果最佳

  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
        # Argo CD sync 時不會 apply replicas 欄位
        # HPA 設定的值不被覆蓋
ℹ️

全域 ignoreDifferences（系統層級）

除了在 Application spec 中設定 ignoreDifferences，還可以在 argocd-cm 中設定 resource.customizations.ignoreDifferences，對特定 group/kind 的所有 Application 全域生效。例如：對所有 Deployment 都忽略 replicas 差異，無需在每個 Application 重複設定。

5Sync Windows：時間窗口控制

Sync Windows 是在 AppProject 中定義的部署時間窗口，控制 Application 的 sync 是否被允許。這是跨越 Application 層面的時間管理機制，讓 SRE / DevOps 可以設定「維護窗口」與「變更凍結期」。

5.1 allow vs deny 的運作邏輯

📊 Sync Window 評估邏輯

以下展示「只允許每天凌晨 02:00–06:00 部署（allow window），且週五 18:00–隔天 08:00 凍結（deny window）」的時間軸：

🚫 Fri 18:00–Sat
✅ Sat 02:00–06:00
🚫 Sat 06:00–Mon
✅ Mon 02:00–06:00
🚫 Mon 06:00–
Allow window 有效 → 可 sync（但 deny 優先）
Deny window 有效 → 禁止 sync（優先級最高）
無 allow window 匹配 → 禁止 sync（有 allow window 定義時）
情境是否有 allow window是否在 deny window結果
情境 A無（未設定）否✅ 允許（完全開放）
情境 B無是🚫 禁止（deny window 生效）
情境 C有，但不在窗口內否🚫 禁止（有 allow window = 窗口外禁止）
情境 D有，在窗口內否✅ 允許
情境 E有，在窗口內是🚫 禁止（deny 優先）
⚠️

關鍵規則：deny 永遠優先

即使在 allow window 有效的時段，若同時有 deny window 匹配該 Application，deny 永遠優先。這讓「週期性維護窗口 + 臨時變更凍結」的組合設計非常靈活。

5.2 AppProject 完整 Sync Windows 設定

YAML — AppProject syncWindows 完整範例
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production
  namespace: argocd
spec:
  syncWindows:

    ## Allow window 1：每天凌晨 02:00–06:00（維護窗口）
    - kind: allow
      schedule: '0 2 * * *'       # cron: 每天 02:00 開始
      duration: 4h              # 持續 4 小時（02:00–06:00）
      applications:
        - '*'                    # 所有 Application（支援 glob）
      manualSync: true          # allow window 外仍允許手動 sync（緊急修復）
      timeZone: "Asia/Taipei"  # 時區（ArgoCD v2.7+，建議明確指定）

    ## Allow window 2：每週三 14:00–16:00（額外的 patch 窗口）
    - kind: allow
      schedule: '0 14 * * 3'     # 週三（0=Sun, 1=Mon, ..., 3=Wed）
      duration: 2h
      namespaces:
        - production           # 只針對 production namespace 的 App
      manualSync: true
      timeZone: "Asia/Taipei"

    ## Deny window：週五 18:00 到週一 09:00（週末變更凍結）
    ## 注意：無法用單一 window 表達跨天，需要兩個 window
    - kind: deny
      schedule: '0 18 * * 5'     # 週五 18:00
      duration: 63h             # 63 小時 = 到週一 09:00
      applications:
        - 'prod-*'              # 只針對 prod- 開頭的 Application
      manualSync: false         # 連手動 sync 也禁止（嚴格凍結）
      timeZone: "Asia/Taipei"

    ## Deny window：季末財務結帳期凍結（finance 相關 App）
    - kind: deny
      schedule: '0 0 25 3,6,9,12 *' # 每季最後一個月 25 號
      duration: 168h           # 7 天
      applications:
        - 'finance-*'
        - 'billing-*'
      manualSync: true          # 財務人員可手動緊急修復
      timeZone: "Asia/Taipei"

# 查看 project 的所有 Sync Windows 及當前狀態
$ argocd proj windows list production
# ID  STATUS    KIND   SCHEDULE      DURATION  APPLICATIONS  MANUALSYNC
# 0   Active    allow  0 2 * * *    4h        *             Enabled
# 1   Inactive  allow  0 14 * * 3  2h        *             Enabled
# 2   Inactive  deny   0 18 * * 5  63h       prod-*        Disabled

# 查看特定 App 目前是否可 sync
$ argocd app get prod-backend
# 若被 window 封鎖會顯示 SyncWindow: Sync Denied

# 緊急時臨時啟用特定 window 的手動 sync
$ argocd proj windows enable-manual-sync production 2  # window ID 2

# 用 CLI 新增 deny window
$ argocd proj windows add production \
  --kind deny \
  --schedule "0 20 * * 5" \
  --duration 48h \
  --applications "prod-*" \
  --timezone "Asia/Taipei"

6Skip Application Reconcile

有時需要暫時停止 Argo CD 對特定 Application 的調和（例如進行手動操作或除錯），可以在 Application 上加入 annotation：

Bash / YAML — 暫停與恢復 Application Reconcile
## 方式一：kubectl patch 加入 annotation（暫停調和）
$ kubectl patch application my-app -n argocd \
  --type=merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/skip-reconcile":"true"}}}'

## 方式二：在 Application YAML 中設定
metadata:
  annotations:
    # 加入此 annotation 後，Argo CD 停止對此 Application 的 Reconcile
    argocd.argoproj.io/skip-reconcile: "true"

## 恢復：移除 annotation
$ kubectl annotate application my-app -n argocd \
  argocd.argoproj.io/skip-reconcile-
# （annotation name 後加 - 表示刪除）

## v3.4 新增：Cluster 層級暫停
## 對整個叢集的所有 Application 暫停 Reconcile
$ kubectl annotate secret -n argocd \
  "cluster-https://prod-cluster.example.com" \
  argocd.argoproj.io/skip-reconcile="true"
⚠️

skip-reconcile 的影響

加入 skip-reconcile: "true" 後，Argo CD 完全停止計算 Sync Status 與 Health Status，Application 在 UI 中的狀態不再更新。這是一個暫時性操作，完成後務必移除 annotation，否則 Application 將永遠不會被調和。

7生產環境最佳 syncPolicy 配置

整合本章所有知識，以下是針對不同環境的推薦 syncPolicy 配置：

YAML — 生產環境推薦 syncPolicy（完整版）
spec:
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false     # 保持預設，防止意外清空
    syncOptions:
      - ServerSideApply=true          # 推薦：無大小限制，欄位所有權管理
      - CreateNamespace=true          # 自動建立 namespace
      - ApplyOutOfSyncOnly=true       # 效能：只 apply 有差異的資源
      - PruneLast=true                # 安全：最後才刪除，避免服務中斷
      - PrunePropagationPolicy=foreground  # 等待子資源刪除
      - RespectIgnoreDifferences=true # sync 時也尊重 ignoreDifferences
    retry:
      limit: 3                         # 有限次數，防止無限重試
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 3m
    managedNamespaceMetadata:
      labels:
        managed-by: argocd
        environment: production

  ## 為 HPA 管理的資源設定 ignoreDifferences
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas

## 針對需要保護的資源（在資源 YAML 中加入）
# metadata:
#   annotations:
#     argocd.argoproj.io/sync-options: Prune=false  # PVC、Namespace 等
環境automatedpruneselfHeal重點 syncOptions
開發（dev）✅ 啟用✅ true✅ trueCreateNamespace，快速迭代
測試（staging）✅ 啟用✅ true✅ trueServerSideApply, PruneLast
生產（production）✅ 啟用（配合 Sync Windows）✅ true✅ trueServerSideApply, PruneLast, PrunePropagationPolicy=foreground, ApplyOutOfSyncOnly
關鍵系統（critical）✅ 啟用（narrow Sync Windows）⚠️ 謹慎（Prune=confirm）✅ true所有保護選項 + Delete=confirm + Prune=confirm

📌 Key Takeaways

  • 🔄Automated Sync 三個旗標：prune（刪除 Git 移除的資源）、selfHeal（修復 drift，5 秒後重試）、allowEmpty（允許零資源，保持 false）。v3.x 新增 enabled 旗標，可臨時停用 automated 而不清除設定。
  • ⚙️關鍵 Sync Options 組合：生產環境推薦 ServerSideApply + ApplyOutOfSyncOnly + PruneLast + PrunePropagationPolicy=foreground + RespectIgnoreDifferences。這個組合兼顧效能、安全與正確性。
  • 🔒資源保護 annotation：在 PVC、Namespace 等重要資源上加 argocd.argoproj.io/sync-options: Prune=false，防止被 prune 誤刪。對高風險資源加 Prune=confirm 要求人工確認。
  • 📊ignoreDifferences 三種類型：jsonPointers（RFC 6901）、jqPathExpressions（jq 語法）、managedFieldsManagers（SSA 欄位所有權）。搭配 RespectIgnoreDifferences=true 可讓 sync 也不覆蓋被忽略的欄位。
  • 🪟Sync Windows 的 deny 優先規則：deny window 永遠優先；有 allow window 定義時，窗口外禁止 sync；manualSync: true 可讓窗口外仍允許手動 sync。時區必須明確指定（timeZone 欄位）。
  • ⏸️Skip Reconcile annotation：argocd.argoproj.io/skip-reconcile: "true" 讓 Argo CD 完全停止調和特定 Application，用於緊急維護。v3.4 起支援 Cluster 層級暫停。記得完成後移除 annotation。
