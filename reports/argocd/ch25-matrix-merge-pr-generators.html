Matrix / Merge / Pull Request
Generators 實戰精通

本章深入三個進階 generator：Matrix（兩 generator 笛卡爾積）、Merge（mergeKey 左 join + 覆蓋）、Pull Request（PR 預覽環境動態建立）。Pull Request generator 是最受開發者歡迎的功能——每個 PR 都有自己的 live 環境，merge / close 後自動清理。完整 GitHub / GitLab / Bitbucket 設定 + 真實的 preview environment 架構範例。

📋

前置：已完整理解 Ch.24（List / Cluster / Git generators）。理解 GitHub PAT / GitHub App、PR 生命週期。對 ephemeral environments / preview environments 有基本概念。

🎯 學習目標

  • 理解 Matrix（笛卡爾積）與 Merge（左 join + 覆蓋）的數學差異與選用準則
  • 用 Matrix 組合 Cluster + Git File 實現「N cluster × M tenant」自動部署
  • 用 Merge 實現「base 設定 + 例外覆蓋」模式（一個 cluster 啟用 Kafka，其他不啟用）
  • 掌握 Pull Request generator 對 GitHub / GitLab / Bitbucket / Gitea 各自的設定差異
  • 建立完整的 PR preview environment（含 namespace 隔離、unique URL、自動 cleanup、CI 整合）
  • 了解 SCM Provider generator 在組織級 repo 自動發現的應用
  • 處理 ephemeral environments 的資源管理（quota、定期清理 stale preview）

1Matrix vs Merge 概念解析

1.1 笛卡爾積 vs 左 Join

⚙️ Matrix（笛卡爾積）
數學概念：兩個集合所有可能組合
A × B = {(a,b) | a∈A, b∈B} 結果數：|A| × |B|
例：Cluster generator 產生 3 個 cluster + Git generator 產生 5 個 app → 產生 15 個 Application（每 cluster 都有每個 app）
🔀 Merge（左 Join + Override）
數學概念：以 base generator 為主，後 generator 用 mergeKey 匹配並覆蓋欄位
A ⨝ B on mergeKey, B 覆蓋 A 結果數：|A|（與 base 一樣）
例：Cluster generator 產生 5 個 cluster + List generator 提供 1 個 cluster 的覆蓋 → 產生 5 個 Application，其中一個有覆蓋的設定

1.2 何時用哪個

情境選擇原因
「N 個 App 部署到 M 個 cluster」Matrix需要所有組合（fan-out）
「同一個 App 部到 N cluster，但其中一個要特殊設定」Mergebase 維持，特例覆蓋
「每個 cluster 用 Helm chart 但 values 不同」Matrix（cluster + Git File）用 Git File 提供 per-cluster values
「prod cluster 啟用 Kafka，dev 不啟用」Merge（cluster + cluster）base + label-based override
「monorepo N 個 App 部署到 prod 與 staging」Matrix（Git Directory + List）App × env 組合
ℹ️

Matrix 與 Merge 都只能組合「兩個」generator

原版限制只能組合 2 個 generator。要組合 3 個以上需要嵌套（Matrix of Matrix）。從 v2.6+ 起 Merge 支援更多 generator。實務上 2 個已能滿足絕大多數需求；嵌套會讓 ApplicationSet 難以理解，建議拆成多個 ApplicationSet。

2Matrix Generator 實戰

2.1 基本語法

YAML — Matrix 基本結構
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-addons
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    # Matrix 是「parent」，內含兩個「child」generators
    - matrix:
        generators:
          # Child 1：Git Directory（產生 5 個 addon）
          - git:
              repoURL: https://github.com/myorg/cluster-addons.git
              revision: main
              directories:
                - path: addons/*
          # Child 2：Cluster generator（產生 3 個 cluster）
          - clusters:
              selector:
                matchLabels:
                  argocd.argoproj.io/secret-type: cluster
  # 結果：5 addons × 3 clusters = 15 Applications
  template:
    metadata:
      name: '{{.path.basename}}-{{.name}}'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/cluster-addons.git
        targetRevision: main
        path: '{{.path.path}}'
      destination:
        server: '{{.server}}'
        namespace: '{{.path.basename}}'

2.2 Cluster + Git File 模式（最強組合）

Matrix 最強大的應用是「Cluster + Git File」——cluster 列表自動發現、每個 cluster 有自己的 config 檔：

YAML — Cluster + Git File Matrix
spec:
  goTemplate: true
  generators:
    - matrix:
        generators:
          - clusters:
              selector:
                matchLabels:
                  monitoring: "true"
          - git:
              repoURL: https://github.com/myorg/cluster-configs.git
              revision: main
              files:
                # Git File path 引用 cluster generator 的 {{.name}}
                - path: 'clusters/{{.name}}/monitoring.json'
  template:
    metadata:
      name: 'monitoring-{{.name}}'
    spec:
      source:
        helm:
          parameters:
            - name: prometheus.retention
              value: '{{.retention}}'     # 來自 Git File config
            - name: prometheus.storage
              value: '{{.storage}}'
      destination:
        server: '{{.server}}'
        namespace: monitoring

2.3 參數依賴規則

⚠️

循環依賴是禁止的

Matrix 的兩個 child generator 可以引用彼此參數，但不能雙向依賴。例如 Git File 用 {{.name}}（cluster generator 的參數）OK；但 Cluster generator 同時用 {{.path.basename}}（Git generator 的參數）就會 circular dependency 錯誤。

3Merge Generator 實戰

3.1 基本語法

Merge 用 mergeKeys 將後續 generator 的結果覆蓋到第一個 generator 的結果上：

YAML — Merge 基本結構
spec:
  goTemplate: true
  generators:
    - merge:
        mergeKeys:
          - server           # 用 server URL 匹配 cluster
        generators:
          # Generator 1（base）：所有 production cluster
          - clusters:
              selector:
                matchLabels:
                  environment: production
              values:
                replicas: "3"           # 預設 3 個 replica
                storage: "50Gi"
          # Generator 2（override）：特定 cluster 的覆蓋
          - list:
              elements:
                # 對 prod-us-east 覆蓋 replicas + storage
                - server: https://prod-us-east.example.com
                  values.replicas: "10"
                  values.storage: "500Gi"
  template:
    metadata:
      name: 'app-{{.name}}'
    spec:
      source:
        helm:
          parameters:
            - name: replicas
              value: '{{.values.replicas}}'
            - name: storage
              value: '{{.values.storage}}'

3.2 cluster + list 啟用特定 feature

YAML — 啟用 Kafka / Redis 範例
spec:
  goTemplate: true
  generators:
    - merge:
        mergeKeys: [server]
        generators:
          # Base：所有 cluster 預設不啟用 Kafka 與 Redis
          - clusters:
              values:
                kafka: 'false'
                redis: 'false'
          # Override 1：use-kafka label 為 true 的 cluster 啟用 Kafka
          - clusters:
              selector:
                matchLabels:
                  use-kafka: 'true'
              values:
                kafka: 'true'
          # Override 2：特定 cluster 啟用 Redis
          - list:
              elements:
                - server: https://prod-us-east.example.com
                  values.redis: 'true'
  template:
    spec:
      source:
        helm:
          parameters:
            - name: kafka.enabled
              value: '{{.values.kafka}}'
            - name: redis.enabled
              value: '{{.values.redis}}'
ℹ️

Generator 順序的覆蓋優先級

Merge 中後 generator 的值覆蓋前 generator 的值。在 mergeKey 匹配時，下面的 generator value 贏。第一個（base）generator 必須產生所有可能的結果（其他 generator 結果若 mergeKey 匹配不到 base 中的記錄會被丟棄）。

4Pull Request Generator

4.1 產生的 Parameters

Pull Request generator 透過 GitHub / GitLab / Bitbucket / Gitea API 取得 open PR 列表，為每個 PR 產生以下 parameters：

Parameter說明範例
{{.number}}PR 編號123
{{.branch}}PR source branchfeature/new-api
{{.branch_slug}}branch 的 K8s-safe 版本feature-new-api
{{.target_branch}}PR target branchmain
{{.head_sha}}PR HEAD commit SHA（推薦 pin 到此）abc123def456...
{{.head_short_sha}}SHA 前 8 字元abc123de
{{.labels}}PR labels（陣列）[preview, feature]
{{.author}}PR author（GitHub username）alice
{{.title}}PR title"feat: add new feature"

4.2 GitHub 完整設定

YAML — Pull Request Generator (GitHub)
## ── Step 1：建立 GitHub PAT 並儲存於 Secret ──────────────
apiVersion: v1
kind: Secret
metadata:
  name: github-pr-token
  namespace: argocd
stringData:
  # Fine-grained PAT 需求：
  # - Repository access: Selected repositories
  # - Permissions: Pull requests (Read), Contents (Read)
  token: "github_pat_xxxxxxxxxxxxxxxxxxxx"

--- ## ── Step 2：ApplicationSet with Pull Request generator ──
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: myapp-pr-preview
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - pullRequest:
        github:
          owner: myorg
          repo: myapp
          # Self-hosted GitHub Enterprise（可選）
          # api: https://github.example.com/api/v3
          tokenRef:
            secretName: github-pr-token
            key: token
          # 強烈建議：只匹配特定 label 的 PR
          labels:
            - preview
        requeueAfterSeconds: 60
        # 過濾條件（可選）
        filters:
          - branchMatch: "^feature/.*"
          - targetBranchMatch: "main"

  template:
    metadata:
      name: 'preview-pr-{{.number}}'
      labels:
        preview: "true"
        pr-number: '{{.number}}'
    spec:
      project: previews
      source:
        repoURL: https://github.com/myorg/myapp.git
        # 用 head_sha 鎖定到 PR 當前 commit（推薦）
        targetRevision: '{{.head_sha}}'
        path: deploy/preview
        helm:
          parameters:
            - name: image.tag
              value: 'pr-{{.number}}'
            - name: ingress.host
              value: 'pr-{{.number}}.preview.example.com'
            - name: banner.text
              value: 'Preview for PR #{{.number}}: {{.title}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'preview-pr-{{.number}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
        retry:
          limit: 5
          backoff:
            duration: 30s
            factor: 2
            maxDuration: 5m

4.3 GitLab / Bitbucket / Gitea 差異

YAML — 多平台 Pull Request 設定差異
## ── GitLab Merge Request ─────────────────────────────────
generators:
  - pullRequest:
      gitlab:
        # GitLab 用 project ID（不是 owner/repo）
        project: "12341234"
        api: https://gitlab.example.com/
        tokenRef:
          secretName: gitlab-token
          key: token
        labels:
          - preview
        pullRequestState: opened

## ── Bitbucket Cloud ──────────────────────────────────────
generators:
  - pullRequest:
      bitbucket:
        owner: myproject
        repo: myrepository
        basicAuth:
          username: myuser
          passwordRef:
            secretName: bitbucket-password
            key: password
        # Bitbucket Cloud 不支援 label 過濾
        filters:
          - branchMatch: "feature/.*"

## ── Gitea ────────────────────────────────────────────────
generators:
  - pullRequest:
      gitea:
        owner: myorg
        repo: myrepository
        api: https://gitea.mydomain.com/
        tokenRef:
          secretName: gitea-token
          key: token
        insecure: true      # 自簽憑證

5PR 預覽環境完整方案

實務上完整的 PR preview environment 需要多個元件配合：

1
Developer 開 PR，加上 preview label
2
CI 執行：build container image，tag 為 pr-{number}，push 到 registry
3
ApplicationSet PR generator polling（或 webhook 觸發）發現新 PR
4
Argo CD 自動建立 Application preview-pr-{number}，部署到 namespace preview-pr-{number}
5
CI 取得 preview URL https://pr-{number}.preview.example.com，留言到 PR
6
Reviewer / PM 點開 URL 測試實際變更，留言或 approve
7
PR merge 或 close：generator 偵測到 PR 不再 open
8
Argo CD 自動刪除 Application（preserveResourcesOnDeletion: false）+ namespace cascade 刪除
YAML — GitHub Actions 在 PR 留言 preview URL
# .github/workflows/pr-preview.yml
name: PR Preview
on:
  pull_request:
    types: [opened, labeled]

jobs:
  build-and-comment:
    if: contains(github.event.pull_request.labels.*.name, 'preview')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # Build + push image
      - name: Build & Push
        run: |
          docker build -t ghcr.io/myorg/myapp:pr-${{ github.event.pull_request.number }} .
          docker push ghcr.io/myorg/myapp:pr-${{ github.event.pull_request.number }}
      # 留言到 PR 標明 preview URL
      - name: Comment PR with preview URL
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `🚀 Preview environment is being created!

              **URL**: https://pr-${{ github.event.pull_request.number }}.preview.example.com
              **Argo CD**: https://argocd.example.com/applications/preview-pr-${{ github.event.pull_request.number }}

              Wait ~2 minutes for the deployment to complete.`
            })

6SCM Provider Generator（簡介）

SCM Provider generator 用 SCM API（GitHub / GitLab / Bitbucket）掃描整個 organization 的 repo，自動發現符合條件的（如有特定 label、含特定檔案）。適合大型組織的「自動納管所有 repo」場景：

YAML — SCM Provider Generator 範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: org-wide-apps
spec:
  goTemplate: true
  generators:
    - scmProvider:
        github:
          organization: myorg
          tokenRef:
            secretName: github-token
            key: token
        # 過濾：只納管含特定條件的 repo
        filters:
          - repositoryMatch: "^myorg/svc-.*"      # Repo 命名規則
          - pathsExist:
              - argocd/Application.yaml            # 必須有此檔
          - labelMatch: "argocd-managed"          # 必須有 label
        requeueAfterSeconds: 300
  template:
    metadata:
      name: '{{.repository}}'
    spec:
      source:
        repoURL: '{{.url}}'
        targetRevision: '{{.branch}}'     # 預設 branch
        path: manifests
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.repository}}'

## SCM Provider 產生的 parameters：
## {{.organization}}    GitHub org name
## {{.repository}}      Repo name
## {{.url}}             Clone URL
## {{.branch}}          Default branch
## {{.sha}}             Commit SHA at default branch
## {{.short_sha}}       SHA 前 8 字元
## {{.labels}}          Repo labels
ℹ️

SCM Provider 是雙刃劍

強大但風險高：① 意外納管——某 repo 加上 argocd-managed label 立刻被 Argo CD 部署，可能不安全；② API rate limit——大型 org 掃描很耗 GitHub API 配額。建議：① 嚴格過濾條件（命名規則 + label + pathsExist 三重）；② 用 GitHub App 提高 rate limit；③ requeueAfterSeconds 設長（300+）。

7資源管理與 Cleanup

ResourceQuota / LimitRange 防止 PR 環境吃光資源

YAML — 為 preview namespace 自動建立 quota
## 在 PR Application 的 source manifests 中包含：
apiVersion: v1
kind: ResourceQuota
metadata:
  name: preview-quota
spec:
  hard:
    requests.cpu: "4"
    requests.memory: "8Gi"
    limits.cpu: "8"
    limits.memory: "16Gi"
    persistentvolumeclaims: "5"
    pods: "20"

---
apiVersion: v1
kind: LimitRange
metadata:
  name: preview-limits
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"

定期清理 stale preview（外部 cron）

Bash — 清理超過 72 小時的 stale preview
#!/bin/bash
# cleanup-stale-previews.sh - 由 K8s CronJob 每天執行

# 列出所有 preview Application 與其建立時間
kubectl get applications -n argocd -l preview=true \
  -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.metadata.creationTimestamp}{"\n"}{end}' | \
  while read name ts; do
    age_hours=$(( ($(date +%s) - $(date -d "$ts" +%s)) / 3600 ))
    if [ "$age_hours" -gt 72 ]; then
      echo "Deleting stale preview: $name (age: ${age_hours}h)"
      kubectl delete application "$name" -n argocd
    fi
  done

# 為何需要外部 cleanup？
# PR generator 只在 PR close 時刪除。但有些「忘了 close」的 stale PR
# 會一直存活；此腳本作為保險，刪除超過 72 小時的環境

故障排查

問題診斷指令解法
PR 已開但沒建 Applicationkubectl describe applicationset 看 status檢查 token 權限、label match、filter 過嚴
token API 失敗kubectl logs -n argocd deploy/argocd-applicationset-controllertoken 過期、rate limit、權限不足
image pull error（CI 還沒推完）argocd app get preview-pr-N調 retry.limit 與 backoff
PR close 但 Application 沒刪看 ApplicationSet syncPolicy確認 preserveResourcesOnDeletion: false（v3.0 預設）
多個 PR 互相影響檢查 namespace 是否獨立確認 namespace name 含 PR number；NetworkPolicy 隔離

✓本章重點回顧

📌 Key Takeaways

  • 🧮Matrix vs Merge 數學差異：Matrix 是笛卡爾積（|A| × |B|），用於 fan-out（N App × M cluster）；Merge 是左 join + 覆蓋（保持 |A|），用於 base + 例外（多數預設、少數覆蓋）。兩者都只能組合 2 個 generator。
  • ⚙️Matrix 最強組合：Cluster + Git File。cluster 自動發現 + 每 cluster 自己的 config 檔。子 generator 可引用兄弟 generator 參數（如 Git File path 用 {{.name}}），但不能循環依賴。
  • 🔀Merge 用 mergeKeys 匹配：通常用 server（cluster URL）。後 generator 的 value 覆蓋前 generator。第一個是 base 必須產生所有結果；後續 generator 只匹配 base 中已有的記錄。
  • 🎫Pull Request generator 是開發者最愛功能：每個 PR 獨立環境 + 自動 cleanup。產生 11 個 parameters（number / branch / branch_slug / head_sha / labels / author / title）。GitHub / GitLab / Bitbucket / Gitea 各有設定差異。強烈建議用 label 過濾（不是每個 PR 都需要環境）。
  • 🚀完整 PR preview 流程：① CI build image with PR tag；② ApplicationSet generator 偵測；③ Argo CD 部署到專屬 namespace；④ CI 留言 preview URL；⑤ PR merge / close 自動 cleanup。用 head_sha 鎖定 commit（不要用 branch，避免 race condition）。
  • 🔍SCM Provider 強大但風險高：自動掃描 org 內 repo。必設嚴格過濾（命名規則 + label + pathsExist 三重）。用 GitHub App 取代 PAT 提高 rate limit。requeueAfterSeconds 設長（300+）避免 API 壓力。
  • 🛡️preview namespace 必設資源限制：ResourceQuota + LimitRange 防止 PR 環境失控吃光叢集資源。外部 cron 定期清理 stale preview（72 小時自動刪除），保險 PR generator 沒偵測到的孤兒環境。
