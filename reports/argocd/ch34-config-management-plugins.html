Config Management Plugins
(CMP) v2 sidecar 架構與實戰

Argo CD 內建支援 Helm / Kustomize / Jsonnet / plain YAML 四種 manifest 來源。但實務上你可能需要 Helmfile、CDK8s、Cue、Tanka、Pulumi——這些都需要 Config Management Plugin（CMP）。v2.8 起 ConfigMap 方式完全移除，必須用 sidecar 架構。本章涵蓋 sidecar 通訊機制（gRPC over Unix socket）、plugin.yaml 完整規範（init / generate / discover）、自訂 plugin 從 Dockerfile 到部署、三個生產級實戰範例（Helmfile / CDK8s / Cue）、與 ApplicationSet 整合、除錯流程。

📋

前置：已完成 Vol 1-6 與 Ch.32-33。理解 Ch.05（manifest tools 內建）。Docker / containerization 基本概念。理解 K8s sidecar pattern（多容器共享 volume）。對 Helmfile / CDK8s / Cue 等工具有基本認識（本章是 CMP 整合，不教這些工具）。

🎯 學習目標

  • 理解 CMP v1（ConfigMap）與 v2（sidecar）的差異與 v2.8 起 v1 完全移除的事實
  • 掌握 sidecar 架構：cmp-server 作為 sidecar 在 repo-server pod 中，透過 Unix socket（/home/argocd/cmp-server/plugins/*.sock）與 repo-server gRPC 通訊
  • 撰寫 plugin.yaml：init（初始化）、generate（產生 YAML）、discover（自動發現）三大命令；parameters 收集動態參數
  • 理解環境變數三層：① 系統內建（ARGOCD_APP_NAME / ARGOCD_APP_NAMESPACE / ARGOCD_APP_SOURCE_PATH 等）；② 系統 + build 變數；③ 使用者自訂（自動加 ARGOCD_ENV_ 前綴防注入）
  • 從零建立 CMP：① Dockerfile（含 argocd-cmp-server binary + tool）；② plugin.yaml；③ patch argocd-repo-server Deployment 加 sidecar；④ Application spec 指定 plugin
  • 實作三個生產級 CMP：① Helmfile（多 chart 編排）；② CDK8s（TypeScript / Python 寫 manifest）；③ Cue（強型別 schema validation）
  • 掌握 discovery 兩種方式：① find.glob（檔案 pattern match）；② find.command（執行命令判斷）；以及為什麼 plugin 名稱明確指定更可靠
  • 與 ApplicationSet 整合：在 template 中用 spec.source.plugin 引用 CMP，並傳入動態參數
  • 除錯利器：cmp-server logs、socket 是否建立、Hard Refresh 清除 Redis cache、ARGOCD_EXEC_TIMEOUT 調整
  • 避開常見陷阱：discovery 過於寬鬆造成誤觸發、忘記 Hard Refresh、image cache 問題、ConfigMap 變更需重啟 repo-server

1為什麼需要 CMP

1.1 v1（ConfigMap）vs v2（sidecar）

CMP 的演進顯示 Argo CD 對「extensibility 與 security 並重」的態度：

面向v1（argocd-cm，已移除）v2（sidecar）
設定位置argocd-cm ConfigMapargocd-repo-server 的 sidecar 容器
執行環境repo-server 主容器內獨立 sidecar 容器
安全性plugin 命令可存取 repo-server 全部檔案filesystem 隔離（含 /tmp 不共用）
套件依賴必須建自訂 argocd-repo-server image（混亂）plugin 自帶 image（乾淨）
多 plugin 衝突所有 plugin 共用同一 image 容易版本衝突每個 plugin 獨立 sidecar 互不影響
v2.4deprecatedintroduced
v2.8完全移除唯一支援方式
⚠️

v2.8 起 ConfigMap 方式完全移除

如果你還在用 configManagementPlugins in argocd-cm，升級到 v2.8+ 會立刻失效。必須先遷移到 sidecar 架構。遷移流程：① 把 plugin spec 從 argocd-cm 抽出到獨立 ConfigMap；② patch argocd-repo-server Deployment 加 sidecar；③ Application 的 spec.source.plugin.name 移除（讓 discovery 自動偵測）或改為新名稱（<name>-<version>）。本章專注 v2 sidecar 架構。

1.2 何時需要 CMP？

Argo CD 內建工具已涵蓋 90% 場景。CMP 用於剩下的 10%：

需求原因常見 CMP
多 Helm chart 編排內建 Helm 不支援跨 chart 依賴Helmfile
程式碼寫 manifest（TS / Python / Go）YAML 不足以表達複雜邏輯CDK8s, Pulumi
強型別 schema validationYAML 弱型別容易出錯Cue
Grafana Labs jsonnet 工具內建 jsonnet 不支援 jsonnet-bundlerTanka, jkcfg
Secret 解密（pre-render）內建工具不解密argocd-vault-plugin（Ch.35）, Helm Secrets
YAML 後處理（validation / lint / patch）渲染後再加工kpt, OPA Conftest
未來的新工具（YTT、Pkl）主流工具更新快YTT, Apple Pkl
💡

先確認內建方案不夠才用 CMP

CMP 是強大但有運維成本的功能：要維護 plugin image、處理 socket / discovery 問題、debug 比內建工具更複雜。建議優先嘗試：① Helm + Kustomize 組合（Argo CD v2.4+ 內建 kustomize.buildOptions，可在 kustomization 中引用 helm chart）；② 用 Source Hydrator（Ch.27）預渲染再 commit；③ ApplicationSet 的 templating 解決動態化需求。確認內建工具真的不夠才考慮 CMP。

2.2 完整流程

1
Pod startup：init container 把 argocd-cmp-server binary 複製到共用 volume /var/run/argocd
2
Sidecar 啟動：以 argocd-cmp-server 為 entrypoint，讀取 /home/argocd/cmp-server/config/plugin.yaml
3
註冊 plugin：sidecar 在 /home/argocd/cmp-server/plugins/ 建立 socket（my-plugin-v1.0.sock）
4
Application sync 觸發：repo-server 收到請求，clone Git repo 到臨時目錄
5
Discovery：repo-server 列出 plugins 目錄，對每個 plugin 執行 discover.find 命令——第一個回 true 的 plugin 被選中（或 Application 明確指定 plugin name）
6
gRPC 呼叫：repo-server 透過 socket 對 cmp-server 發 GenerateManifests(path) RPC
7
執行 generate：sidecar 執行 init.command（若有）→ generate.command，輸出 YAML 到 stdout
8
回傳 manifest：repo-server 接收 stdout 內容，傳給 application-controller 進行 sync
⚠️

filesystem 隔離（v2.4+ 安全強化）

v2.4 起，sidecar 不能與 repo-server 共用 /tmp——每個 sidecar 必須有自己的 cmp-tmp emptyDir。這是為了防止 path traversal 攻擊：惡意 plugin 不能透過 .. 路徑存取 repo-server 的其他 repo 內容。如果你的 plugin.yaml 範例還在共用 /tmp，必須改，否則 v2.4+ 會運作異常。

3plugin.yaml 規範

3.1 init / generate / discover

YAML — plugin.yaml 完整骨架
apiVersion: argoproj.io/v1alpha1
kind: ConfigManagementPlugin
metadata:
  name: my-plugin           # plugin 名稱（必須）
spec:
  version: v1.0           # 版本（可選，用於 socket naming）

  # Plugin 名稱完整格式：
  # - 有 version: <name>-<version> (e.g. my-plugin-v1.0)
  # - 無 version: <name>          (e.g. my-plugin)

  # ── init: 初始化（每次 generate 前都跑）─────────
  init:
    command: [sh, -c]
    args:
      - |
        # 例：安裝依賴、下載資源
        npm install 2>/dev/null || true
        helmfile deps

  # ── generate: 產生 manifests（必須）─────────────
  generate:
    command: [sh, -c]
    args:
      - |
        # 必須輸出 valid YAML 到 stdout
        helmfile template --quiet --namespace $ARGOCD_APP_NAMESPACE

  # ── discover: 自動發現（可選但建議）─────────────
  discover:
    # 方法 1：用 glob pattern
    find:
      glob: "**/helmfile.yaml"

    # 方法 2：用 command（更彈性）
    # find:
    #   command: [sh, -c, "find . -name helmfile.yaml | head -1 | grep -q ."]

    # 方法 3：用 fileName（單一檔案 match）
    # fileName: "helmfile.yaml"

  # ── 行為控制 ─────────────────────────────────
  allowConcurrency: true      # 允許多個 application 同時用此 plugin
  lockRepo: false            # true: plugin 執行時 lock repo（避免多 plugin 同時修改）

  # ── Git credentials（可選，謹慎使用）────────
  provideGitCreds: false     # true: plugin 取得 repo-server 的 Git 認證
                            # （只信任的 plugin 才開啟）

  # ── parameters（v2.5+，UI 顯示參數）─────────
  parameters:
    static:
      - name: environment
        title: Environment
        required: true
        itemType: string
    dynamic:
      command: [sh, -c, "ls envs/"]
      # 動態列出所有環境（envs/ 下的子目錄）

3.2 環境變數三層

層級變數來源範例
1系統環境（sidecar 容器的 env）PATH, 自訂 VAULT_ADDR
2Argo CD 內建變數（automatic）ARGOCD_APP_NAME, ARGOCD_APP_NAMESPACE, ARGOCD_APP_SOURCE_PATH, ARGOCD_APP_REVISION, KUBE_VERSION, KUBE_API_VERSIONS
3使用者自訂（Application spec.source.plugin.env）會自動加 ARGOCD_ENV_ 前綴（防注入）
YAML — Application 傳遞自訂變數
apiVersion: argoproj.io/v1alpha1
kind: Application
spec:
  source:
    repoURL: https://github.com/myorg/configs.git
    path: apps/my-app
    plugin:
      name: helmfile-v1.0      # 明確指定 plugin（推薦）
      env:
        - name: FOO
          value: bar
          # Plugin 內看到的是 ARGOCD_ENV_FOO=bar（自動加前綴）
        - name: REVISION
          value: test-$ARGOCD_APP_REVISION
          # 支援系統變數插值，最終值為 test-abc1234

3.3 Parameters（v2.5+ UI 顯示）

YAML — parameters static + dynamic
spec:
  parameters:
    # Static：固定的參數（UI 顯示輸入欄位）
    static:
      - name: replicas
        title: Replica count
        required: true
        itemType: number
        collectionType: value      # value | array | map

      - name: image
        required: true
        tooltip: "Container image URL"

    # Dynamic：執行命令動態取得選項
    dynamic:
      command: [sh, -c]
      args:
        - |
          # 輸出 JSON 陣列：UI 顯示為下拉選單
          echo '[
            {"name": "env", "title": "Environment",
             "itemType": "string", "collectionType": "value",
             "string": "dev"},
            {"name": "env", "title": "Environment",
             "itemType": "string", "collectionType": "value",
             "string": "prod"}
          ]'

4建立第一個 CMP

4.1 Dockerfile

Dockerfile — Helmfile CMP image
# Dockerfile
FROM alpine:3.19

# 安裝必要工具：helmfile + helm + helm plugins
RUN apk add --no-cache curl bash git \
    && curl -fsSL https://get.helm.sh/helm-v3.14.0-linux-amd64.tar.gz | tar -xz \
    && mv linux-amd64/helm /usr/local/bin/ \
    && rm -rf linux-amd64

# Helmfile
RUN curl -fsSL -o /usr/local/bin/helmfile \
    https://github.com/helmfile/helmfile/releases/download/v0.166.0/helmfile_0.166.0_linux_amd64.tar.gz \
    && chmod +x /usr/local/bin/helmfile

# Helm plugins（helmfile 依賴）
RUN helm plugin install https://github.com/databus23/helm-diff \
    && helm plugin install https://github.com/jkroepke/helm-secrets

# 建立 argocd user（cmp-server 需 non-root）
RUN adduser -D -u 999 argocd

# 必須：使用 argocd user
USER 999

# 對應 sidecar 中 argocd-cmp-server 的 entrypoint
ENTRYPOINT ["/var/run/argocd/argocd-cmp-server"]
YAML — plugin.yaml + ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: cmp-helmfile
  namespace: argocd
data:
  plugin.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: helmfile
    spec:
      version: v1.0
      init:
        command: [sh, -c]
        args:
          - |
            helmfile deps 2>&1 | head -50

      generate:
        command: [sh, -c]
        args:
          - |
            helmfile template \
              --quiet \
              --namespace $ARGOCD_APP_NAMESPACE

      discover:
        find:
          glob: "**/helmfile.yaml"

      allowConcurrency: true
      lockRepo: false

4.2 Patch argocd-repo-server 加 sidecar

YAML — argocd-repo-server sidecar patch
apiVersion: apps/v1
kind: Deployment
metadata:
  name: argocd-repo-server
  namespace: argocd
spec:
  template:
    spec:
      containers:
        - name: helmfile
          command: [/var/run/argocd/argocd-cmp-server]
          image: myregistry.io/cmp-helmfile:v1.0.0
          imagePullPolicy: IfNotPresent
          securityContext:
            runAsNonRoot: true
            runAsUser: 999

          volumeMounts:
            # 1) argocd-cmp-server binary（由 init container 填入）
            - mountPath: /var/run/argocd
              name: var-files

            # 2) Plugin socket 註冊位置
            - mountPath: /home/argocd/cmp-server/plugins
              name: plugins

            # 3) Plugin 設定檔（從 ConfigMap mount）
            - mountPath: /home/argocd/cmp-server/config/plugin.yaml
              subPath: plugin.yaml
              name: cmp-helmfile-config

            # 4) cmp-tmp（v2.4+ 必須與 repo-server /tmp 分離）
            - mountPath: /tmp
              name: cmp-tmp

      volumes:
        - name: cmp-helmfile-config
          configMap:
            name: cmp-helmfile
        - name: cmp-tmp
          emptyDir: {}
        # var-files 與 plugins volume 在原 Deployment 已存在
Bash — 套用 + 驗證
## 1) 套用 ConfigMap 與 Deployment patch
$ kubectl apply -f cmp-helmfile-cm.yaml
$ kubectl patch deploy argocd-repo-server -n argocd --patch-file repo-server-patch.yaml

## 2) 重啟 repo-server 載入 sidecar
$ kubectl rollout restart deploy argocd-repo-server -n argocd

## 3) 確認 sidecar 啟動
$ kubectl get pods -n argocd -l app.kubernetes.io/name=argocd-repo-server \
    -o jsonpath='{.items[*].spec.containers[*].name}'
# argocd-repo-server helmfile

## 4) 看 sidecar log 確認 socket 註冊
$ kubectl logs -n argocd deploy/argocd-repo-server -c helmfile --tail=20
# argocd-cmp-server v3.4.0 serving on /home/argocd/cmp-server/plugins/helmfile-v1.0.sock

## 5) 建立測試 Application
$ cat << EOF | kubectl apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-helmfile-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/configs.git
    path: apps/my-app
    plugin:
      name: helmfile-v1.0      # 明確指定 plugin（含 version）
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app
EOF

5三個生產實戰 CMP

5.1 Helmfile（多 chart 編排）

使用情境：Application 需要部署多個 chart（如 monitoring stack: prometheus + grafana + alertmanager），且彼此有依賴關係：

YAML — Helmfile 多 chart 範例
# Git repo 結構：apps/monitoring/helmfile.yaml
repositories:
  - name: prometheus-community
    url: https://prometheus-community.github.io/helm-charts
  - name: grafana
    url: https://grafana.github.io/helm-charts

releases:
  - name: prometheus
    chart: prometheus-community/prometheus
    version: 25.8.0
    values:
      - server:
          retention: "30d"

  - name: grafana
    chart: grafana/grafana
    version: 7.3.0
    # 依賴 prometheus：先部署 prometheus 才部署 grafana
    needs:
      - prometheus
    values:
      - datasources:
          datasources.yaml:
            apiVersion: 1
            datasources:
              - name: Prometheus
                url: http://prometheus-server

  - name: alertmanager
    chart: prometheus-community/alertmanager
    version: 1.5.0
    needs:
      - prometheus

# Argo CD 透過 Helmfile CMP 一次部署三個 chart，依賴順序由 helmfile 處理

5.2 CDK8s（程式碼寫 manifest）

YAML — CDK8s plugin.yaml
data:
  plugin.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: cdk8s
    spec:
      version: v1.0
      init:
        command: [sh, -c]
        args:
          - |
            # Install dependencies
            npm install --silent
      generate:
        command: [sh, -c]
        args:
          - |
            # Run CDK8s synth 產生 manifests
            npm run synth --silent >/dev/null
            # Combine 所有產出的 YAML
            cat dist/*.yaml
      discover:
        find:
          glob: "**/cdk8s.yaml"
      allowConcurrency: true
TypeScript — CDK8s 範例
// main.ts (in app repo)
import { App, Chart } from 'cdk8s';
import { KubeDeployment, KubeService } from './imports/k8s';

class MyAppChart extends Chart {
  constructor(scope: App, name: string) {
    super(scope, name);

    const labels = { app: 'my-app' };
    const replicas = parseInt(process.env.ARGOCD_ENV_REPLICAS || '3');

    new KubeDeployment(this, 'deployment', {
      spec: {
        replicas,
        selector: { matchLabels: labels },
        template: {
          metadata: { labels },
          spec: {
            containers: [{
              name: 'app',
              image: process.env.ARGOCD_ENV_IMAGE || 'my-app:latest',
              ports: [{ containerPort: 8080 }],
            }],
          },
        },
      },
    });

    new KubeService(this, 'service', {
      spec: { selector: labels, ports: [{ port: 80, targetPort: 8080 as any }] },
    });
  }
}

const app = new App();
new MyAppChart(app, 'my-app');
app.synth();

5.3 Cue（強型別 schema validation）

YAML — Cue plugin.yaml
data:
  plugin.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: cue
    spec:
      version: v1.0
      init:
        command: [sh, -c]
        args: ["cue mod tidy"]
      generate:
        command: [sh, -c]
        args:
          - |
            # 用 cue export 輸出 K8s manifest
            cue export ./... --out yaml \
              --inject env=$ARGOCD_ENV_ENVIRONMENT
      discover:
        find:
          glob: "**/*.cue"
      allowConcurrency: true
Cue — 強型別 schema 範例
// app.cue: 用 Cue 定義強型別 schema
package myapp

// 1) 定義 schema（含 validation）
#AppConfig: {
    name:     string & =~"^[a-z][a-z0-9-]*$"     // regex 驗證
    replicas: int & >=1 & <=100                   // 範圍驗證
    image:    string                              // 必填
    env:      "dev" | "staging" | "prod"          // enum 驗證
    resources: {
        cpu:    string & =~"^[0-9]+m?$"
        memory: string & =~"^[0-9]+(Mi|Gi)$"
    }
}

// 2) 注入環境（cue export 時 --inject env=prod）
env: *"dev" | "staging" | "prod" @tag(env)

// 3) 環境特定 config（自動切換）
config: #AppConfig & {
    name: "my-app"
    env:  env
    if env == "prod" {
        replicas: 10
        resources: cpu: "1000m"
    }
    if env != "prod" {
        replicas: 2
        resources: cpu: "500m"
    }
    image:     "myregistry.io/my-app:v1.2.3"
    resources: memory: "512Mi"
}

// 4) 輸出 K8s manifest（cue export 自動產生）
deployment: {
    apiVersion: "apps/v1"
    kind:       "Deployment"
    metadata: name: config.name
    spec: {
        replicas: config.replicas
        selector: matchLabels: app: config.name
        template: {
            metadata: labels: app: config.name
            spec: containers: [{
                name:  config.name
                image: config.image
                resources: requests: config.resources
            }]
        }
    }
}
💡

三個 CMP 的差異

① Helmfile——適合「已用 Helm，需要多 chart 編排」團隊；② CDK8s——適合「想用熟悉語言（TS/Python）寫 manifest，避免 YAML 複雜邏輯」團隊；③ Cue——適合「嚴格 schema validation、平台工程團隊」場景。都比直接寫 YAML 更安全，但學習曲線各異——選擇取決於團隊背景。

6Discovery 與選擇邏輯

Discovery 決定「哪個 plugin 處理這個 Application 的 source」。有兩種方式：

6.1 自動 discovery（用 find）

YAML — 三種 discovery 寫法
# 方法 1：glob pattern（最簡單）
discover:
  find:
    glob: "**/helmfile.yaml"
    # 在 source path 下任何深度找 helmfile.yaml 都 match

# 方法 2：fileName（單一檔名 match）
discover:
  fileName: "helmfile.yaml"

# 方法 3：command（最彈性）
discover:
  find:
    command: [sh, -c]
    args:
      - |
        # 任何輸出非空就視為 match
        if [ -f "$ARGOCD_APP_SOURCE_PATH/helmfile.yaml" ] && \
           [ ! -f "$ARGOCD_APP_SOURCE_PATH/Chart.yaml" ]; then
          echo "match"
        fi
        # 條件：有 helmfile.yaml 但沒 Chart.yaml（避免 helm chart 誤觸發）

6.2 明確指定 plugin（推薦）

Argo CD discussion #13870 等 issue 顯示自動 discovery 在多 plugin 環境容易出錯——多個 plugin 都可能 match 同一個 source，且 race condition 造成不一致。生產環境建議明確指定 plugin name：

YAML — 明確指定 plugin（生產推薦）
apiVersion: argoproj.io/v1alpha1
kind: Application
spec:
  source:
    repoURL: https://github.com/myorg/configs.git
    path: apps/monitoring
    plugin:
      # 完整 plugin name 格式：<name>-<version>
      # 來自 plugin.yaml 的 metadata.name 與 spec.version
      name: helmfile-v1.0

      # 可選：傳入自訂 env
      env:
        - name: ENVIRONMENT
          value: production

      # 可選：傳入 parameters（v2.5+）
      parameters:
        - name: replicas
          string: "10"
⚠️

Plugin name 格式必須完全匹配

① plugin.yaml metadata.name: helmfile + spec.version: v1.0 → 完整名稱是 helmfile-v1.0；② 沒 version → 完整名稱是 helmfile。Application 的 plugin.name 必須完全匹配，否則報「plugin sidecar failed. couldn't find cmp-server plugin with name」錯誤（discussion #8216）。升級 plugin 時要同步更新所有 Application 的 plugin.name。

7與 ApplicationSet 整合

CMP 可以在 ApplicationSet template 中使用，配合 generator 動態建立多個 Application：

YAML — ApplicationSet + Helmfile CMP
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-env-monitoring
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - list:
        elements:
          - env: dev
            cluster: https://dev-cluster.example.com
            retention: "7d"
          - env: staging
            cluster: https://staging-cluster.example.com
            retention: "14d"
          - env: prod
            cluster: https://prod-cluster.example.com
            retention: "30d"

  template:
    metadata:
      name: 'monitoring-{{.env}}'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/monitoring.git
        path: helmfile
        targetRevision: main

        # 引用 CMP
        plugin:
          name: helmfile-v1.0
          # Generator 變數透過 env 傳給 plugin
          env:
            - name: ENVIRONMENT
              value: '{{.env}}'
            - name: RETENTION
              value: '{{.retention}}'

      destination:
        server: '{{.cluster}}'
        namespace: monitoring
      syncPolicy:
        automated: {prune: true, selfHeal: true}

helmfile.yaml 中可以引用環境變數（Go template syntax）：

YAML — helmfile.yaml 使用環境變數
# helmfile/helmfile.yaml in monitoring repo
releases:
  - name: prometheus
    chart: prometheus-community/prometheus
    version: 25.8.0
    values:
      - server:
          # 注意：是 ARGOCD_ENV_RETENTION（前綴自動加）
          retention: "{{ env "ARGOCD_ENV_RETENTION" | default "7d" }}"
        global:
          external_labels:
            environment: "{{ env "ARGOCD_ENV_ENVIRONMENT" }}"
            cluster: "{{ env "ARGOCD_APP_NAME" }}"

8除錯與最佳實踐

常用除錯指令

Bash — CMP 除錯工具集
## 1. 確認 sidecar 正常啟動
$ kubectl get pods -n argocd -l app.kubernetes.io/name=argocd-repo-server
$ kubectl logs -n argocd deploy/argocd-repo-server -c helmfile --tail=50
# 看到 "argocd-cmp-server v3.4.0 serving on .../helmfile-v1.0.sock" 就是 OK

## 2. 確認 socket 已建立
$ kubectl exec -n argocd deploy/argocd-repo-server -c helmfile -- \
    ls -la /home/argocd/cmp-server/plugins/
# helmfile-v1.0.sock

## 3. 確認 plugin.yaml 內容
$ kubectl exec -n argocd deploy/argocd-repo-server -c helmfile -- \
    cat /home/argocd/cmp-server/config/plugin.yaml

## 4. 看 repo-server 主容器 log（plugin selection logic）
$ kubectl logs -n argocd deploy/argocd-repo-server -c argocd-repo-server \
    --tail=200 | grep -i plugin
# 找：plugin "helmfile-v1.0" matched / not found / errors

## 5. Application 報錯：強制 Hard Refresh（清 Redis cache）
# 在 UI 點 "Refresh" 旁邊的下拉 → "Hard Refresh"
# 或 CLI：
$ argocd app get my-app --refresh hard

## 6. 手動執行 plugin 命令測試（在 sidecar 內）
$ kubectl exec -n argocd deploy/argocd-repo-server -c helmfile -- sh
$ cd /tmp/test-source-path     # 模擬 Argo CD 的 source path
$ export ARGOCD_APP_NAMESPACE=my-app
$ helmfile template --quiet --namespace $ARGOCD_APP_NAMESPACE

## 7. 修改 plugin.yaml ConfigMap 後必重啟 repo-server
$ kubectl rollout restart deploy/argocd-repo-server -n argocd

## 8. 調整 timeout（plugin 執行慢時）
$ kubectl set env deploy/argocd-repo-server -n argocd \
    -c helmfile ARGOCD_EXEC_TIMEOUT=300s

錯誤訊息原因解法

最佳實踐

✅

CMP 上線 Checklist

① plugin.yaml 用 ConfigMap 管理（不要 bake 到 image，更新方便）；② Application 明確 plugin.name不要依賴 discovery（多 plugin 環境容易亂）；③ 必設 spec.version方便管理多版本並存；④ Dockerfile 用 distroless / alpine降低 attack surface；⑤ USER 999且 securityContext.runAsNonRoot;⑥ cmp-tmp 用獨立 emptyDir（v2.4+ 強制隔離）；⑦ 修改 plugin 必 rollout restart repo-server；⑧ plugin 升級用新 version（v1.0 → v1.1）並同步更新 Application；⑨ 監控 sidecar resources（CPU/memory limit 適當）；⑩ 不要把 generate 命令做太複雜（複雜邏輯放 application repo 中的腳本）。

✓本章重點回顧

📌 Key Takeaways

  • 🔌CMP v2 sidecar 是唯一支援方式：v2.4 deprecated v1（ConfigMap），v2.8 完全移除。如果還在用 argocd-cm configManagementPlugins 必須先遷移。sidecar 架構帶來 filesystem 隔離（v2.4+ /tmp 不共用）、plugin 自帶 image、多 plugin 互不影響的好處。
  • ⚙️架構核心：cmp-server 是 sidecar，repo-server 透過 Unix socket 用 gRPC 通訊。init container 把 argocd-cmp-server binary 複製到共用 volume /var/run/argocd。Sidecar 以此為 entrypoint，註冊 socket 到 /home/argocd/cmp-server/plugins/<name>-<version>.sock。
  • 📄plugin.yaml 三大命令：① init（每次 generate 前跑，可裝依賴）；② generate（產出 YAML 到 stdout，必須）；③ discover（自動發現，可選但建議）。allowConcurrency: true多數情況需要（否則 plugin 序列化執行）；provideGitCreds 只給信任 plugin（會把 Git 認證傳給 plugin）。
  • 🔑環境變數三層：① 系統（sidecar 容器 env）；② Argo CD 內建（ARGOCD_APP_NAME / ARGOCD_APP_SOURCE_PATH / ARGOCD_APP_REVISION / KUBE_VERSION）；③ 使用者自訂（Application spec.source.plugin.env，自動加 ARGOCD_ENV_ 前綴防注入）。Plugin 內存取自訂變數記得用前綴名。
  • 🏗️建立 CMP 四步驟：① Dockerfile（installs tool + USER 999 + entrypoint argocd-cmp-server）；② plugin.yaml（在 ConfigMap）；③ patch argocd-repo-server Deployment 加 sidecar（含 var-files / plugins / config / cmp-tmp 四個 volume mount）；④ Application 用 spec.source.plugin.name: <name>-<version> 引用。
  • 📦三個生產 CMP 範例：① Helmfile（多 chart 依賴編排，needs: 控制順序）；② CDK8s（TS/Python 寫 manifest，process.env 讀 Argo CD env）；③ Cue（強型別 schema validation，cue export --inject 注入環境參數）。選 CMP 取決於團隊背景，不是哪個更好。
  • 🔍Discovery 兩種：glob 與 command。生產推薦明確 spec.source.plugin.name不依賴 discovery（多 plugin 環境容易 race condition 選錯 plugin，discussion #13870）。Plugin name 格式必須完全匹配 <name>-<version>（如有 version）或 <name>（無 version），否則報 plugin not found（#8216）。
  • 🎫與 ApplicationSet 整合：在 template 的 spec.source.plugin 引用 CMP，generator 變數透過 env 傳給 plugin（自動加 ARGOCD_ENV_ 前綴）。Plugin 內可在 helmfile / cue / cdk8s 程式中讀取這些 env。實現「N 個環境 × M 個 CMP」的動態組合。
  • 🐛除錯起點：① 看 sidecar log 確認 socket 註冊；② kubectl exec 進 sidecar 手動執行 generate；③ Hard Refresh 清 Redis cache（修改 plugin 後 manifest 還是舊版的常見原因）；④ ARGOCD_EXEC_TIMEOUT 調整 plugin 執行 timeout（預設 90s）；⑤ 修改 plugin.yaml ConfigMap 後 必 rollout restart repo-server。
  • ✅10 項上線 Checklist：① plugin.yaml 用 ConfigMap（更新方便）；② Application 明確 plugin.name；③ 必設 spec.version；④ Dockerfile 用 distroless/alpine；⑤ USER 999 + runAsNonRoot；⑥ cmp-tmp 獨立 emptyDir；⑦ 修改 plugin 必 rollout restart；⑧ 升級用新 version 並同步 Application；⑨ 監控 sidecar resources；⑩ generate 命令簡單（複雜邏輯放 app repo 腳本）。
