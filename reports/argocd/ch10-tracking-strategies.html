Tracking 策略、Resource Tracking
與供應鏈安全（GnuPG）

本章涵蓋兩個獨立但相關的 tracking 概念：一是 Application 追蹤 Git 中哪個版本（targetRevision 的五種策略）；二是 Argo CD 如何追蹤 Kubernetes 叢集中的資源屬於哪個 Application（三種 Resource Tracking Method）。最後介紹 GnuPG 簽名驗證，確保供應鏈安全。

📋

前置：已完成 Vol 2 Ch.05–Ch.09 的基礎學習。了解 Git tag、branch、commit SHA 的基本概念。

🎯 學習目標

  • 理解 targetRevision 五種策略（branch / tag / commit SHA / HEAD / semver）的行為差異與適用場景
  • 掌握三種 Resource Tracking Method（label / annotation / annotation+label）的差異，以及各自的優缺點
  • 能設定 annotation+label 作為全域 tracking method，並安全地從 label 遷移
  • 理解 annotation tracking-id 的格式（app-name:group/kind:namespace/name）
  • 了解 GnuPG 簽名驗證的工作原理，並在 AppProject 中設定強制驗證
  • 能診斷常見的 tracking 問題（資源不在 App 樹中、phantom OutOfSync 等）

1Tracking 策略（targetRevision）

spec.source.targetRevision 決定 Argo CD 追蹤 Git 中的哪個版本。選擇錯誤的策略會導致生產環境不穩定（branch 追蹤意外部署未測試的程式碼）或失去靈活性（過度釘定 commit SHA）。

🌿
Branch 追蹤
targetRevision: main
追蹤 branch 最新的 commit。每次 push 到該 branch 都可能觸發 sync。適合開發、CI 驗證環境，不適合生產（無法精確控制版本）。
🌱 適合：dev / feature branches
🏷️
Tag 追蹤
targetRevision: v1.2.3
追蹤特定 Git tag 指向的 commit。Tag 通常不變（除非 force-push），提供比 branch 更確定性的版本控制。適合 staging / production 發佈流程。
🚀 適合：staging / production release
🔒
Commit SHA 釘定
targetRevision: a1b2c3d4e5f6
釘定到特定 commit（不可變）。最嚴格、最確定的版本控制——commit SHA 的含義絕不改變。要更改部署版本，必須修改 Application 的 targetRevision。
🔒 適合：production（嚴格版本管控）
⬆️
HEAD 符號參考
targetRevision: HEAD
追蹤 Git repo 的 default branch 最新 commit。等同追蹤 default branch（通常是 main 或 master），是不填 targetRevision 時的預設行為。適合入門，不適合多環境管理。
📖 適合：入門學習 / 單一環境 demo
📦
Semver 約束
targetRevision: ">=1.2.0 <1.3.0"
僅適用於 Helm chart repo（非 Git）。自動追蹤符合語意化版本約束的最新 chart 版本，例如 1.2.* 追蹤 1.2.x 系列最新 patch，^1.0.0 追蹤相容版本。
⎈ 適合：Helm chart repo 版本管理

1.1 Branch 追蹤詳解

YAML — Branch 追蹤（含 fully-qualified 格式）
source:
  repoURL: https://github.com/myorg/k8s-manifests.git
  # 一般 branch 名稱
  targetRevision: main

  # 若 branch 與 tag 同名（ambiguous reference），使用 fully-qualified 格式
  # 避免 Argo CD 無法確定要追蹤哪個 ref 而出現 constant reconciliation loop
  targetRevision: refs/heads/release-1.0    # 明確指定 branch
  # targetRevision: refs/tags/release-1.0      # 明確指定 tag
⚠️

Branch 與 Tag 同名的陷阱

若 Git repo 中有 branch 和 tag 都叫做 release-1.0，Argo CD 可能無法確定要追蹤哪個，導致 reconciliation loop。解決方法：使用 fully-qualified 參考格式 refs/heads/release-1.0（branch）或 refs/tags/release-1.0（tag）明確區分。

1.2 Tag 追蹤詳解

YAML — Tag 追蹤（含 annotated tag 說明）
source:
  repoURL: https://github.com/myorg/k8s-manifests.git
  # Lightweight tag（指向 commit）
  targetRevision: v1.2.3

  # Annotated tag（Git tag object，指向 commit）
  # 建議使用：含有 tagger 名稱、日期、描述訊息，有利稽核
  # git tag -a v1.2.3 -m "Release 1.2.3: Bug fixes"
  targetRevision: v1.2.3  # 格式相同，但 GPG 驗證行為不同（見 3.4 節）

## CI/CD 自動化更新 tag（宣告式方式）
## CI pipeline 建立新 tag 後，更新 Application YAML 中的 targetRevision
## 並 commit 回 GitOps repo → Argo CD 偵測到變更後自動 sync

## argocd CLI 更新（臨時，不推薦生產使用）
## argocd app set my-app --revision v1.2.4

1.3 Commit SHA 釘定

YAML — Commit SHA 釘定（最嚴格版本控制）
source:
  repoURL: https://github.com/myorg/k8s-manifests.git
  # 完整 40 位 commit SHA（最精確）
  targetRevision: a1b2c3d4e5f67890abcdef1234567890abcdef12
  # 或短縮版（8-12 位通常足以唯一識別）
  # targetRevision: a1b2c3d4

## 從 tag 遷移至 commit SHA（鎖定當前部署版本）
## 步驟：
## 1. 取得目前部署的 commit SHA
##    argocd app get my-app -o json | jq -r '.status.sync.revision'
## 2. 更新 targetRevision 為該 SHA
## 適用於緊急凍結（incident 處理期間，防止任何新程式碼被部署）

1.4 Semver 約束（Helm chart repo）

YAML — Semver 約束（僅 Helm chart repo）
## Semver 約束只適用於 Helm chart repository（非 Git）
source:
  repoURL: https://prometheus-community.github.io/helm-charts
  chart: kube-prometheus-stack

  # Semver 約束範例
  targetRevision: "58.*"          # 任何 58.x.x 版本（追蹤最新 patch）
  targetRevision: ">=58.0.0 <59.0.0"  # 等同 58.*（明確範圍）
  targetRevision: "^58.3.0"       # 相容版本：>=58.3.0 <59.0.0
  targetRevision: "~58.3.0"       # 更新 patch：>=58.3.0 <58.4.0

## Semver 約束使用注意：
## - 生產環境建議用精確版本（如 58.3.3）而非約束，避免意外升級
## - 開發/測試環境可用約束追蹤最新版

1.5 環境對應最佳實踐

環境推薦策略理由範例
開發（dev）Branch 追蹤（feature branch）每次 push 自動部署，快速迭代targetRevision: feature/my-feature
整合（integration）Branch 追蹤（main / develop）持續驗證 main branch 的健康targetRevision: main
預發（staging）Tag 追蹤只部署有 tag 的版本，模擬生產流程targetRevision: v1.2.3
生產（production）Tag 追蹤 or Commit SHA 釘定確定性版本，可重現部署狀態targetRevision: v1.2.3
緊急凍結Commit SHA 釘定防止任何新 commit 被部署，絕對確定targetRevision: a1b2c3d4（完整 SHA）

2Resource Tracking Method

這裡的「tracking」是另一個層面的概念：Argo CD 如何在 Kubernetes 叢集中識別「哪些資源屬於哪個 Application」。這是 Argo CD 建立 App 資源樹、計算 Sync Status 的基礎機制。

label（原始預設）
識別方式app.kubernetes.io/instance: <app-name> label
優點可用 kubectl label selector 查詢；最簡單
缺點與 Helm 的 app.kubernetes.io/instance label 衝突；app 名稱超過 63 字元時截斷；多個 App 管理同一資源時無法精確識別
設定值application.resourceTrackingMethod: label
annotation（新預設）
識別方式argocd.argoproj.io/tracking-id: <app>:<group>/<kind>:<ns>/<name>
優點不與任何 label 衝突；含完整資源 ID，精確識別；支援超長 app 名稱；annotation 不影響 selector
缺點無法用 kubectl label selector 查詢（需用 Argo CD CLI）
設定值application.resourceTrackingMethod: annotation
annotation+label（推薦）
識別方式使用 annotation 追蹤（精確）+ 同時保留 label（相容性）
優點annotation 負責精確追蹤；label 維持向後相容；可用 kubectl label selector 查詢；Helm label 不被覆蓋
缺點label 仍有 63 字元限制（但不影響 tracking 精確度）
設定值application.resourceTrackingMethod: annotation+label

2.1 annotation tracking-id 格式解析

annotation 追蹤使用 argocd.argoproj.io/tracking-id，格式為：

Format — tracking-id 格式解析
## tracking-id 格式：
## <app-name>:<group>/<kind>:<namespace>/<name>

## 範例一：Deployment（apps group）
argocd.argoproj.io/tracking-id: "my-app:apps/Deployment:production/api-server"

## 範例二：Service（core group，group 為空字串）
argocd.argoproj.io/tracking-id: "my-app:/Service:production/api-service"

## 範例三：cluster-scoped 資源（無 namespace）
argocd.argoproj.io/tracking-id: "my-app:rbac.authorization.k8s.io/ClusterRole:/my-cluster-role"

## 驗證方式
## kubectl get deployment api-server -n production \
##   -o jsonpath='{.metadata.annotations.argocd\.argoproj\.io/tracking-id}'

2.2 設定與安全遷移步驟

YAML + Bash — 設定 annotation+label 並安全遷移
## Step 1：修改 argocd-cm
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 設定 annotation+label（推薦）
  application.resourceTrackingMethod: annotation+label

## Step 2：重啟 application-controller 使設定生效
## kubectl rollout restart statefulset argocd-application-controller -n argocd

## Step 3：逐一 sync 所有 Application（加入 --prune=false 防止誤刪）
## 使用 --prune=false 很重要：遷移期間舊 label 消失，
## Argo CD 可能誤判資源為「不在 App 中」而嘗試 prune
## for app in $(argocd app list -o name); do
##   argocd app sync "$app" --prune=false
##   sleep 3
## done

## Step 4：驗證 annotation 已加入資源
## kubectl get deployment -n production \
##   -o jsonpath='{.items[*].metadata.annotations.argocd\.argoproj\.io/tracking-id}'
⚠️

遷移時必須使用 --prune=false

從 label 遷移到 annotation 時，遷移途中資源暫時失去 label tracking，Argo CD 可能將它們視為「不屬於此 App」而嘗試 prune（刪除）。使用 --prune=false 的 sync 確保遷移期間不會誤刪資源。等所有 App sync 完成後，annotation 已加入所有資源，才恢復正常 prune 行為。

2.3 自定義 Label Key

若不想使用預設的 app.kubernetes.io/instance label（可能與現有監控系統衝突），可以自定義 label key：

YAML — 自定義 label key
data:
  # 預設：app.kubernetes.io/instance
  # 自定義（使用 Argo CD 專有的 annotation 風格 label）
  application.instanceLabelKey: argocd.argoproj.io/instance

  ## 注意：修改 instanceLabelKey 需要重新 sync 所有 Application，
  ## 讓新 label key 被加入所有資源（原有 label key 的資源將變為 orphaned）

3供應鏈安全：GnuPG 簽名驗證

想像一個攻擊者取得了你 Git repo 的寫入權限，悄悄修改 manifest 檔案，將惡意的 image tag 或環境變數注入。如果 Argo CD 不加驗證就同步，生產環境就會執行惡意程式碼。GnuPG 簽名驗證讓 Argo CD 只接受由你信任的 GPG key 簽署的 commit 或 tag，從根源阻擋供應鏈攻擊。

3.1 GPG 驗證原理

步驟說明
開發者簽署 commit開發者使用私鑰（Private Key）對 commit 或 tag 進行 GPG 簽名：git commit -S -m "Deploy v1.2.3"（-S 表示 sign）
公鑰匯入 Argo CD平台團隊將開發者的公鑰（Public Key）匯入 Argo CD，存放在 argocd-gpg-keys-cm ConfigMap
Project 設定強制驗證在 AppProject 中設定 signatureKeys，要求關聯的 Application 只能 sync 已簽署的 commit
Argo CD 驗證簽名每次 sync 前，Argo CD 驗證 commit 或 tag 的 GPG 簽名，若簽名無效或 key 不在允許清單中，拒絕 sync 並回傳 ResourceComparison error

3.2 設定流程

Bash — GPG 驗證完整設定流程
## ── Step 1：匯入公鑰到 Argo CD ──────────────────────────────

# 方式一：argocd CLI（需要 ASCII armored 格式）
$ argocd gpg add --from /path/to/developer-public.asc

# 方式二：宣告式（ConfigMap）
# argocd-gpg-keys-cm 中，key 為 GPG key fingerprint，value 為 ASCII armored 公鑰

# 列出已匯入的 GPG keys
$ argocd gpg list
# KEY ID          FINGEPRINT  OWNER          TRUST
# F7B123ABC456   ...          Developer1     fully

# 取得 GPG key fingerprint（用於 Project 設定）
$ gpg --list-keys --keyid-format LONG developer@example.com
# pub   rsa4096/ABCDEF123456789 2023-01-01

## ── Step 2：開發者簽署 commit ──────────────────────────────

# 設定 GPG 簽署 key
$ git config user.signingkey ABCDEF123456789
$ git config commit.gpgsign true  # 自動簽署所有 commit

# 手動簽署 commit
$ git commit -S -m "feat: update API image to v3.2.1"

# 簽署 tag（annotated tag 需要 -s）
$ git tag -s v1.2.3 -m "Release 1.2.3: Security fixes"
$ git push origin v1.2.3

# 驗證 commit 是否已簽署
$ git verify-commit HEAD
$ git log --show-signature -1

3.3 AppProject 強制驗證設定

YAML — AppProject 強制 GPG 簽名驗證
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production
  namespace: argocd
spec:
  description: "生產環境 Project：強制 GPG 簽名驗證"
  sourceRepos:
    - https://github.com/myorg/k8s-manifests.git
  destinations:
    - server: https://kubernetes.default.svc
      namespace: production

  # 強制 GPG 簽名驗證
  # 只允許由以下 key fingerprint 簽署的 commit/tag
  signatureKeys:
    - keyID: ABCDEF123456789  # Developer1 的 GPG key fingerprint
    - keyID: 123456789ABCDEF  # Developer2（可允許多個 key）

## 驗證失敗時的表現：
## Application 顯示 ComparisonError 狀態
## 錯誤訊息：
## "signature verification failed: commit is not signed,
##  or is signed by an unknown or not allowed public key"

## 啟用/停用全域 GPG 功能
## 在 argocd-server / argocd-repo-server / argocd-application-controller
## / argocd-applicationset-controller 的 deployment 中設定：
## env:
##   - name: ARGOCD_GPG_ENABLED
##     value: "true"   # 預設 true（啟用但不強制）
##     value: "false"  # 完全停用 GPG 功能

3.4 Annotated Tag 的特殊行為

targetRevision 類型驗證對象簽署方式
Branch 名稱（如 main）Branch tip 的 commit 對象git commit -S
Lightweight tagTag 指向的 commit 對象git commit -S
Annotated tag（如 v1.2.3）Tag 對象本身（非 commit）git tag -s v1.2.3（必須用 -s 簽署 tag）
Commit SHA指定的 commit 對象git commit -S
⚠️

Annotated Tag 必須簽署 tag 本身（而非 commit）

若 targetRevision 是 annotated tag，Argo CD 驗證的是 tag 對象，而非 tag 指向的 commit。這意味著即使 commit 有 GPG 簽名，若 tag 本身沒有用 git tag -s 簽署，GPG 驗證仍會失敗。確保 CI/CD pipeline 在建立 annotated tag 時使用 -s 旗標。

4Tracking 診斷工具

Bash — Tracking 常見問題診斷
## ── 診斷一：確認目前 tracking method ────────────────────
$ kubectl get cm argocd-cm -n argocd \
  -o jsonpath='{.data.application\.resourceTrackingMethod}'
# 空字串 = 使用預設 label 方式（v3.x 預設已改為 annotation）

## ── 診斷二：確認資源的 tracking metadata ─────────────────
$ kubectl get deployment api-server -n production -o yaml | \
  grep -E "app.kubernetes.io/instance|argocd.argoproj.io/tracking-id"
# 應看到 tracking-id annotation（annotation 模式）
# 或 app.kubernetes.io/instance label（label 模式）

## ── 診斷三：尋找 orphaned resources（刪除 App 後殘留）────
# Label 模式：
$ kubectl get all --all-namespaces \
  -l app.kubernetes.io/instance=my-deleted-app

# Annotation 模式：
$ kubectl get all --all-namespaces -o json | \
  jq -r '.items[] | select(.metadata.annotations["argocd.argoproj.io/tracking-id"] | startswith("my-app:")) | "\(.metadata.namespace)/\(.kind)/\(.metadata.name)"'

## ── 診斷四：App 資源不出現在 resource tree ─────────────
$ argocd app resources my-app
# 若資源應在 App 中但不出現，可能：
# 1. tracking label/annotation 不匹配（手動修改過）
# 2. 資源在不同 namespace（App 追蹤的 namespace 不匹配）
# 解決：argocd app sync my-app --force

## ── 診斷五：GPG 驗證失敗 ────────────────────────────────
$ argocd app get my-app
# 若顯示 ComparisonError + GPG 訊息：
# 1. 確認 commit 是否有簽署：git verify-commit HEAD
# 2. 確認公鑰是否匯入：argocd gpg list
# 3. 確認 key fingerprint 是否在 Project signatureKeys 中
# 4. 等待 key propagation（可能需要幾分鐘）

## ── 診斷六：目前 App 的 targetRevision 與實際同步 SHA ──
$ argocd app get my-app -o json | \
  jq '{targetRevision: .spec.source.targetRevision, syncedSHA: .status.sync.revision}'

📌 Key Takeaways

  • 🎯targetRevision 五種策略：Branch（持續追蹤）→ Tag（版本釘定）→ Commit SHA（絕對釘定）→ HEAD（default branch）→ Semver 約束（Helm chart repo 限定）。生產環境推薦 Tag 或 Commit SHA，開發環境用 Branch。
  • ⚠️Branch 與 Tag 同名的陷阱：使用 refs/heads/branch-name 或 refs/tags/tag-name fully-qualified 格式可避免 ambiguous reference 導致的 reconciliation loop。
  • 🏷️Resource Tracking Method 推薦使用 annotation+label：annotation 負責精確追蹤（含完整 group/kind/namespace/name），label 維持 kubectl selector 相容性。避免使用純 label 模式（與 Helm label 衝突）。
  • 🔄tracking method 遷移必須使用 --prune=false：遷移途中資源暫時失去舊 tracking metadata，若此時執行 prune 可能意外刪除資源。逐一 sync 所有 App 時加上 --prune=false。
  • 🔐GnuPG 驗證是供應鏈安全的關鍵：在 AppProject.spec.signatureKeys 設定後，Argo CD 拒絕 sync 未簽署或簽署者不在允許清單的 commit/tag。Annotated tag 必須用 git tag -s 簽署 tag 本身（非 commit）。
  • 🔍tracking-id annotation 格式：<app-name>:<group>/<kind>:<namespace>/<name>。核心 API group（如 Service）的 group 部分為空字串，格式為 my-app:/Service:production/api-svc。
