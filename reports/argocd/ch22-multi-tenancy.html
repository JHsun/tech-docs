1多租戶概念與目標

1.1 什麼是 Argo CD 中的「租戶」？

多租戶（Multi-Tenancy）是讓多個獨立團隊（tenant）安全共用同一個 Argo CD 平台的設計。一個典型的「租戶」具備以下特徵：

面向租戶擁有租戶不能存取
Git Repos自己 team 的 Git 儲存庫其他 team 的 repo
K8s Namespaces自己擁有的 namespace（如 team-a-*）kube-system 與其他 team 的 namespace
K8s Clusters所屬環境的 cluster（如 dev/staging）其他環境（如 prod，需審核）
K8s 資源類型Deployment、Service、ConfigMap 等應用層ClusterRole、CRD、Namespace（平台層）
Argo CD UI 視野只看到自己的 Application其他 team 的 App 不可見
Sync 時段自定義部署時段（如 prod 限工時外）跨越組織政策禁止時段

1.2 隔離的四大維度

👁️
可見性
UI / API 中只看得到自己的 Application、Project、Cluster、Repo
📦
部署範圍
能 sync 到哪些 namespace / cluster；能用哪些 Git repos
🛡️
資源類型
能管理哪些 K8s kind（namespace-scoped allow，cluster-scoped 限定）
⏰
Sync 時段
什麼時間可以 / 不可以 sync（如 prod 維護時段、freeze period）

2三大多租戶策略對比

A. Single Instance + RBAC
架構
一個 Argo CD 服務所有 team。透過 AppProject + RBAC + namespace 隔離
優點
  • 運維成本最低
  • 統一升級 / 設定
  • 跨 team 視野容易
  • 資源使用最佳
缺點
  • 單點故障：壞了所有 team 都受影響
  • 嘈雜鄰居：大 App 拖累所有人
  • RBAC 隨團隊數複雜化
  • 無法各 team 獨立升級
適合
2-30 個 team、信任度高、單一組織
B. Multi Instance（每 team 一個）
架構
每個 team 自己的 Argo CD（不同 namespace 或 cluster）
優點
  • 真實隔離（不只 policy）
  • 各 team 獨立升級
  • 故障局部影響
  • 不需要跨 team RBAC
缺點
  • 運維成本 N 倍
  • 無集中視野
  • SSO / cluster credentials 重複設定
  • 資源使用較高
適合
監管嚴格、競爭關係 team、SaaS 平台、超大規模 (100+ team)

2.3 策略 C：Hybrid（推薦中大型組織）

Architecture — Hybrid 拓撲
┌──────────────────────────────────────────────────────────────────┐
│  Layer 1: Platform Argo CD（管理員 instance）                    │
│  ──────────────────────────────────────                          │
│  • 由平台團隊運維                                                │
│  • 部署各租戶的 Argo CD instance（self-management）              │
│  • 部署 platform 元件：cert-manager、ingress、monitoring         │
│  • 部署各 tenant 的 namespace + RoleBinding                      │
└────────┬─────────────────────────────────────────────────────────┘
         │ 部署 + 管理
         ▼
┌────────────────┬────────────────┬────────────────┬───────────────┐
│ Tenant Argo CD │ Tenant Argo CD │ Tenant Argo CD │ ...           │
│  Team Alpha    │  Team Beta     │  Team Gamma    │               │
│ (in alpha-     │ (in beta-      │ (in gamma-     │               │
│  argocd ns)    │  argocd ns)    │  argocd ns)    │               │
│  namespace-    │  namespace-    │  namespace-    │               │
│  install.yaml  │  install.yaml  │  install.yaml  │               │
└────────────────┴────────────────┴────────────────┴───────────────┘
         │                │                │
         ▼                ▼                ▼
┌──────────────────────────────────────────────────────────────────┐
│  Tenant 各自的 K8s Namespaces（alpha-*、beta-*、gamma-*）         │
└──────────────────────────────────────────────────────────────────┘

Hybrid 模式結合兩者優點：① 平台團隊用 platform Argo CD 管理基礎設施與各 tenant 的 Argo CD instance（GitOps 部署）；② 各 tenant 在自己的 instance 上自治；③ 故障隔離（platform 故障不影響 tenant 已運行的 sync）。大型組織首選。

3AppProject：Single Instance 多租戶基石

選擇 Single Instance 策略時，AppProject 是隔離的核心。一個完整的 tenant AppProject 必須涵蓋四大限制：

YAML — 完整 tenant AppProject 範例
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-alpha
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io     # 防止意外刪除
spec:
  description: Team Alpha applications

  # ─── 1. Source Repos：限制 Git 來源 ─────────────────────
  sourceRepos:
    - 'https://github.com/myorg/team-alpha-*'   # 自己的 repo
    - 'https://github.com/myorg/shared-charts'   # 公司共享 chart
    # 不允許 - '*'（會破壞租戶隔離）

  # ─── 2. Destinations：限制部署目的地 ─────────────────────
  destinations:
    # 本叢集，限定 namespace 前綴
    - namespace: 'alpha-*'
      server: https://kubernetes.default.svc
    # Production cluster，限定特定 namespace
    - namespace: 'alpha-prod'
      server: https://prod.k8s.example.com
    # 限定 destination 中 Application 物件可在哪個 namespace
    # （用於 Apps in Any Namespace 功能，見第 4 節）
  sourceNamespaces:
    - alpha-argocd      # 只接受來自 alpha-argocd ns 的 Application

  # ─── 3. Cluster Resources：限制 cluster-scoped 資源 ─────
  # 預設 deny all，只允許白名單
  clusterResourceWhitelist:
    # 不允許 ClusterRole、ClusterRoleBinding、CRD、Namespace（給 platform 管）
    # （空 list = 全 deny）

  # 黑名單：明確禁止特定 namespace-scoped 資源
  namespaceResourceBlacklist:
    - group: ''
      kind: ResourceQuota      # 由 platform 設定
    - group: ''
      kind: LimitRange
    - group: 'networking.k8s.io'
      kind: NetworkPolicy      # 由 platform 設定

  # ─── 4. Sync Windows：限制 sync 時段 ──────────────────────
  syncWindows:
    # 平日上班時間禁止 sync prod（避免人為失誤）
    - kind: deny
      schedule: '0 9 * * 1-5'      # 週一至週五 09:00
      duration: 9h                 # 持續 9 小時（到 18:00）
      applications:
        - '*-prod'
      manualSync: false          # 連手動 sync 都禁止
      timeZone: Asia/Taipei

  # ─── 5. Project-level Roles（見 Ch.21）─────────────────
  roles:
    - name: admin
      policies:
        - p, proj:team-alpha:admin, applications, *, team-alpha/*, allow
      groups:
        - team-alpha-leads

    - name: deployer
      policies:
        - p, proj:team-alpha:deployer, applications, get,    team-alpha/*, allow
        - p, proj:team-alpha:deployer, applications, sync,   team-alpha/*, allow
        - p, proj:team-alpha:deployer, applications, action/*, team-alpha/*, allow
      groups:
        - team-alpha-developers

  # ─── 6. Orphaned Resources：通知未管理資源 ──────────────
  orphanedResources:
    warn: true          # UI 顯示警告但不刪除
    ignore:
      - kind: Secret
        name: 'default-token-*'      # 系統自動建立的 token
⚠️

關鍵安全陷阱：sourceRepos: ['*']

許多教學範例為了簡化，把 sourceRepos 設為 '*'——這完全破壞 multi-tenancy！tenant 可以指定任何 Git repo（包含 platform 的 secret repo），規避所有限制。絕對不要在生產環境使用 sourceRepos: ['*']，永遠列出明確的 repo 模式。

4Apps in Any Namespace（v2.5+，租戶自治關鍵）

傳統 Argo CD 中，所有 Application 物件必須在 argocd namespace。這意味著 tenant 想新增 App 必須有 argocd ns 的 write 權限——而那相當於 super-admin。v2.5+ 引入 Apps in Any Namespace：tenant 可以在自己擁有的 namespace 中建立 Application 物件，實現真正的 declarative 自治：

4.1 啟用設定

YAML — 啟用 Apps in Any Namespace
## ── Step 1：在 argocd-cmd-params-cm 設定 namespace 模式 ────
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  # 允許 controller 與 server watch 哪些 namespace 的 Application
  # 支援 glob 模式
  application.namespaces: "argocd,*-argocd"
  # 範例匹配：argocd, alpha-argocd, beta-argocd, gamma-argocd
  # 不匹配：alpha, kube-system, default

## ── Step 2：在 AppProject 中限定 sourceNamespaces ──────────
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-alpha
  namespace: argocd
spec:
  sourceNamespaces:
    - alpha-argocd      # 只接受來自 alpha-argocd ns 的 Application
  # 其他 spec 同前

## ── Step 3：在 tenant 自己的 namespace 建立 Application ────
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: alpha-argocd      # tenant 擁有的 namespace
spec:
  project: team-alpha            # 必須對應 sourceNamespaces 設定
  source:
    repoURL: https://github.com/myorg/team-alpha-app1
    path: k8s
  destination:
    server: https://kubernetes.default.svc
    namespace: alpha-prod

## ── Step 4：UI 中的顯示 ─────────────────────────────────────
# Application 在 UI 顯示為「alpha-argocd/my-app」格式
# 與 argocd ns 的 App 區分（避免命名衝突）

4.2 命名衝突防護

ℹ️

v2.5+ 命名規則：<namespace>/<app-name>

同一個 cluster 內，alpha-argocd 與 beta-argocd 中可以同時有名為 my-app 的 Application（K8s 層級唯一）。Argo CD 內部用 <namespace>/<app-name> 區分，避免命名衝突。但 argocd ns 中的 App 仍只用 my-app（向後相容）。

YAML — RBAC 對 Apps in Any Namespace 的設定
data:
  policy.csv: |
    # 對 Apps in Any Namespace，object 格式為 <app-namespace>/<app-name>
    # 注意：不是 project 名稱，是 K8s namespace 名稱！

    # Allow team-alpha 操作 alpha-argocd ns 中的 App
    p, role:team-alpha-deployer, applications, *, alpha-argocd/*, allow

    # 對 argocd ns 中的 App（傳統模式）
    p, role:team-alpha-deployer, applications, *, team-alpha/*, allow

    # 二者並存：兼容傳統 + 新模式
💡

App-of-Apps + Apps in Any Namespace = 完美自治

tenant 在自己的 namespace 建立一個 root Application（指向 tenant 自己的 GitOps repo），root Application 透過 directory.recurse 讀取 tenant 自己 repo 中的所有 child Application。tenant 增加新 App = git push（無需 platform 介入）。真正的 declarative GitOps 自治。

5ApplicationSet 多租戶 Generators

ApplicationSet（深入細節見 Vol 5）讓 platform team 自動為 tenant 產生 Application，無需手動逐個建立。多租戶場景常用三種 generator：

YAML — 三種 ApplicationSet 多租戶範例
## ────────────────────────────────────────────────────────
## 範例 1：List generator（手動列表）
## 為 4 個 tenant 自動建立 monitoring stack
## ────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: tenant-monitoring
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - tenant: alpha
            project: team-alpha
          - tenant: beta
            project: team-beta
          - tenant: gamma
            project: team-gamma
          - tenant: delta
            project: team-delta
  template:
    metadata:
      name: 'monitoring-{{tenant}}'
    spec:
      project: '{{project}}'
      source:
        repoURL: https://github.com/myorg/platform-monitoring.git
        path: 'tenants/{{tenant}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{tenant}}-monitoring'

---
## ────────────────────────────────────────────────────────
## 範例 2：Cluster generator（依 cluster 自動 fan-out）
## ────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: platform-cert-manager
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            platform-managed: "true"      # 對應 cluster Secret label
  template:
    metadata:
      name: 'cert-manager-{{name}}'      # cluster name
    spec:
      project: platform
      source:
        repoURL: https://charts.jetstack.io
        chart: cert-manager
        targetRevision: v1.14.0
      destination:
        server: '{{server}}'           # 從 cluster Secret
        namespace: cert-manager

---
## ────────────────────────────────────────────────────────
## 範例 3：Git generator（從 Git directory 自動產生）
## tenant 在自己 repo 建立目錄即自動部署
## ────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-alpha-apps
spec:
  generators:
    - git:
        repoURL: https://github.com/myorg/team-alpha-apps
        revision: main
        directories:
          - path: 'apps/*'          # 每個子目錄產生一個 App
  template:
    metadata:
      name: 'alpha-{{path.basename}}'
    spec:
      project: team-alpha
      source:
        repoURL: https://github.com/myorg/team-alpha-apps
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: 'alpha-{{path.basename}}'

6租戶完全自治：namespace-install + Hybrid

對需要極致隔離的租戶（如金融部門、合規嚴格 team），可以為其部署獨立的 namespace-install Argo CD instance。tenant 在自己的 namespace 完全擁有 Argo CD：

YAML — Hybrid：platform 部署 tenant Argo CD
## platform Argo CD 用 ApplicationSet 自動為每個 tenant
## 部署一個獨立的 namespace-install Argo CD instance

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: tenant-argocd-instances
  namespace: argocd      # platform argocd ns
spec:
  generators:
    - list:
        elements:
          - tenant: alpha
          - tenant: beta
          - tenant: gamma
  template:
    metadata:
      name: 'argocd-{{tenant}}'
    spec:
      project: platform
      source:
        repoURL: https://argoproj.github.io/argo-helm
        chart: argo-cd
        targetRevision: 7.6.12
        helm:
          releaseName: 'argocd-{{tenant}}'
          valuesObject:
            global:
              domain: 'argocd-{{tenant}}.example.com'
            configs:
              cm:
                application.namespaces: '{{tenant}}-*'
              params:
                # 用 namespace-install 模式
                application.namespaces: '{{tenant}}-*'
            crds:
              install: false      # CRD 由 platform 統一安裝
            controller:
              resources:
                requests: {cpu: "500m", memory: "1Gi"}
            server:
              replicas: 2
              ingress:
                enabled: true
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{tenant}}-argocd'
      syncPolicy:
        automated: {prune: true, selfHeal: true}
        syncOptions: [CreateNamespace=true]

## 效果：
# platform Argo CD 為每個 tenant 部署一個獨立的 namespace-scoped Argo CD
# tenant Argo CD 只能管理 {{tenant}}-* namespace（namespace-install 限制）
# 各 tenant 各自獨立升級、設定、SSO
# 故障局部影響

7完整實作：4 個團隊的 Single Instance 多租戶

整合本章所有概念，以下是中型組織（4 個產品 team + platform team）的完整 Single Instance 多租戶配置：

YAML — 完整多租戶實作（platform-managed）
## ────────────────────────────────────────────────────────
## 1) Platform AppProject（管理員，部署 platform 元件）
## ────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform
  namespace: argocd
spec:
  description: Platform infrastructure
  sourceRepos:
    - 'https://github.com/myorg/platform-*'
    - 'https://argoproj.github.io/argo-helm'     # 為了 self-management
    - 'https://charts.jetstack.io'               # cert-manager
  destinations:
    - namespace: '*'
      server: '*'           # platform 可部署到任何地方
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'            # 允許所有 cluster 資源
  roles:
    - name: admin
      policies:
        - p, proj:platform:admin, applications, *, platform/*, allow
      groups:
        - platform-team-leads

---
## ────────────────────────────────────────────────────────
## 2) Tenant Template AppProject（範本，由 platform 維護）
## 4 個 tenant project（team-alpha / team-beta / team-gamma / team-delta）
## ────────────────────────────────────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-alpha
  namespace: argocd
spec:
  sourceRepos:
    - 'https://github.com/myorg/team-alpha-*'
    - 'https://github.com/myorg/shared-charts'
  destinations:
    - namespace: 'alpha-*'
      server: '*'
  sourceNamespaces:
    - alpha-argocd      # Apps in Any Namespace 隔離
  clusterResourceWhitelist: []     # 不允許 cluster-scoped
  namespaceResourceBlacklist:
    - group: ''
      kind: ResourceQuota
    - group: 'networking.k8s.io'
      kind: NetworkPolicy
  roles:
    - name: admin
      policies:
        - p, proj:team-alpha:admin, applications, *, alpha-argocd/*, allow
      groups:
        - team-alpha-leads
    - name: deployer
      policies:
        - p, proj:team-alpha:deployer, applications, get,    alpha-argocd/*, allow
        - p, proj:team-alpha:deployer, applications, sync,   alpha-argocd/*, allow
      groups:
        - team-alpha-developers

---
## ────────────────────────────────────────────────────────
## 3) Tenant Namespace + RoleBinding（由 platform 透過 GitOps 管理）
## 自動為 alpha-argocd ns 設定 tenant 可寫入 Application 的權限
## ────────────────────────────────────────────────────────
apiVersion: v1
kind: Namespace
metadata:
  name: alpha-argocd
  labels:
    tenant: alpha
    # Pod Security restricted
    pod-security.kubernetes.io/enforce: restricted
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alpha-tenant-argocd-write
  namespace: alpha-argocd
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit           # K8s 內建 edit role
subjects:
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: team-alpha-leads
  - kind: Group
    apiGroup: rbac.authorization.k8s.io
    name: team-alpha-developers

---
## ────────────────────────────────────────────────────────
## 4) Global RBAC（argocd-rbac-cm）
## ────────────────────────────────────────────────────────
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: ''
  scopes: '[groups,email]'
  policy.csv: |
    # 所有人可看到 platform / app projects（透明性）
    p, role:org-readonly, projects, get, *, allow
    p, role:org-readonly, applications, get, */*, allow

    g, "okta-all-employees", role:org-readonly

8選型決策矩陣

場景策略關鍵設定
小團隊（1-3 team）
5-50 App		 Single Instance + AppProject + RBAC 所有 Application 在 argocd ns；簡單 Project 隔離
中型組織（4-30 team）
100-1000 App		 Single Instance + Apps in Any Namespace + ApplicationSet tenant 自治在 alpha-argocd ns；platform 用 ApplicationSet 自動產生 base Apps
大型組織（30+ team）
含監管嚴格部門		 Hybrid：platform Argo CD + 監管部門獨立 instance 大部分用 Single + Apps in Any Namespace；金融/合規部門用 namespace-install
SaaS 平台（為客戶提供 Argo CD）
競爭關係 tenant		 Multi Instance（每客戶一個） 每客戶獨立 namespace-install + 獨立 cluster credentials
超大規模（100+ team / 50+ cluster） Per-Cluster Argo CD（見 Ch.12）+ ArgoCD Agent 每 cluster 一個 Argo CD + 中央 control plane 統一視野
💡

選型核心問題清單

① 監管限制：tenant 是否要求完全獨立 instance？
② 故障容忍度：一個 tenant 影響其他 tenant 是否可接受？
③ 升級節奏：tenant 是否需要獨立決定升級時機？
④ RBAC 複雜度：是否願意維護跨 tenant 的 policy？
⑤ 運維能力：能否負擔多 instance 的管理成本？
前三題若有一題回答「是」，考慮 Multi Instance 或 Hybrid。

✓本章重點回顧

📌 Key Takeaways

  • 🏢多租戶 = 隔離 + 自治：tenant 應在四大維度被隔離（可見性、部署範圍、資源類型、Sync 時段）。Single Instance 用 RBAC 實現「邏輯隔離」；Multi Instance 用獨立 instance 實現「物理隔離」。
  • ⚖️三大策略各有適用場景：① Single Instance（運維簡單但故障域大，2-30 team）；② Multi Instance（強隔離但 N 倍成本，監管嚴格 / SaaS 多客戶）；③ Hybrid 是中大型組織首選（platform + tenant instance）。
  • 🛡️AppProject 是 Single Instance 隔離核心：四大限制必設——sourceRepos（明確列舉，絕不用 *）、destinations（限定 namespace + cluster）、clusterResourceWhitelist（預設空 = 全 deny）、namespaceResourceBlacklist（禁 ResourceQuota / NetworkPolicy 等 platform 資源）。再加 syncWindows + Project Roles。
  • 📂Apps in Any Namespace 是真正自治的關鍵（v2.5+）：在 argocd-cmd-params-cm 設定 application.namespaces；AppProject 配 sourceNamespaces；tenant 在自己 ns 建立 Application = git push 即部署，無需 argocd ns 寫入權限。對應 RBAC 的 object 是 <app-namespace>/<app-name>。
  • 🔁ApplicationSet 三大 generator 對應多租戶：① List：手動為固定 tenant 列表產生 App；② Cluster：依 cluster Secret label 自動 fan-out；③ Git：tenant 在自己 repo 建目錄即自動產 App。大幅減少 platform team 手動工作量。
  • 🏗️Hybrid 模式下的 platform 角色：platform Argo CD 透過 ApplicationSet 自動為每個 tenant 部署 namespace-install Argo CD instance + 建立 namespace + RoleBinding + cluster credentials。tenant 完全自治於自己的 instance，platform 只負責 bootstrap。
  • 📋選型決策五問：監管限制？故障容忍度？升級節奏？RBAC 複雜度？運維能力？前三題若有「是」考慮 Multi/Hybrid。中型組織建議：Single Instance + Apps in Any Namespace 起步，部分監管嚴格 team 改用 Hybrid namespace-install。
