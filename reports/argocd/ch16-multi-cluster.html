多叢集連線
與管理（IRSA、SA Token、mTLS）

Hub-and-Spoke 拓撲下，Argo CD 必須安全地連接所有 spoke 叢集。本章解析 cluster Secret 的結構、五種認證方式（SA Token、Client Certificate、EKS IRSA、GKE Workload Identity、Exec-based）的選擇依據，以及完整的 IRSA 跨帳號設定。最後涵蓋宣告式 GitOps 註冊、外部 Secret 管理整合、連線診斷與 token 輪替。

📋

前置：已閱讀 Ch.12（Hub-and-Spoke 拓撲）、Ch.14（最小權限 ClusterRole）。理解 Kubernetes ServiceAccount、ClusterRoleBinding、AWS IAM 基本概念。

🎯 學習目標

  • 理解 cluster Secret 的結構（labels、name、server、config JSON）
  • 能比較五種認證方式的優缺點，依雲平台選擇正確方案
  • 使用 argocd cluster add 命令快速註冊新叢集
  • 以宣告式 GitOps 方式管理所有 cluster credentials（versioned + reproducible）
  • 完成 EKS IRSA 跨帳號設定（OIDC provider、IAM role、aws-auth ConfigMap）
  • 設計 cluster RBAC 最小權限（取代預設的 cluster-admin）
  • 整合 External Secrets Operator + Vault / AWS Secrets Manager 自動輪替
  • 診斷常見連線問題（連接失敗、token 過期、權限不足）

1Cluster Secret 結構

1.1 in-cluster 自動連線（不需 Secret）

Argo CD 安裝所在的叢集稱為 in-cluster，server URL 為 https://kubernetes.default.svc。Argo CD 自動使用所在 pod 的 ServiceAccount token（透過 ClusterRoleBinding 提供 cluster-admin 級權限），不需要額外建立 cluster Secret。

Application 部署到 in-cluster 的方式：

YAML — in-cluster destination
apiVersion: argoproj.io/v1alpha1
kind: Application
spec:
  destination:
    # 方式 A：使用 server URL（永遠可用）
    server: https://kubernetes.default.svc

    # 方式 B：使用 cluster name "in-cluster"（需 namespace-install 模式可能不存在）
    # name: in-cluster

    namespace: production

1.2 Cluster Secret 完整格式

外部叢集的連線資訊以 Secret 形式存放在 argocd namespace。每個 Secret 必須有 argocd.argoproj.io/secret-type: cluster 標籤，Argo CD 才會將其識別為 cluster credentials：

YAML — Cluster Secret 完整結構
apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod-us-east
  namespace: argocd      # 必須在 argocd namespace
  labels:
    # 必要標籤：Argo CD 透過此 label 識別 cluster Secret
    argocd.argoproj.io/secret-type: cluster
    # 自定義標籤（可用於 ApplicationSet generators）
    environment: production
    region: us-east-1
    cloud: aws
    type: workload
type: Opaque
stringData:
  # 三大必要欄位
  name: prod-us-east          # UI 顯示名稱（人類可讀）
  server: https://k8s.prod.example.com  # K8s API server URL
  config: |
    {
      "bearerToken": "eyJhbGciOiJSUzI1NiIs...",
      "tlsClientConfig": {
        "insecure": false,
        "caData": "LS0tLS1CRUdJTi..."
      }
    }

  # 進階欄位（可選）
  # namespaces 限定可部署的 namespace（cluster-scoped 限制）
  # namespaces: "ns-a,ns-b,ns-c"

  # clusterResources 是否允許 cluster-scoped 資源
  # clusterResources: "false"   # 若為 false，不允許部署 cluster-scoped 資源

  # shard 強制指派給特定 application-controller shard（見 Ch.13）
  # shard: "0"

  # project 限定此 cluster 只能被特定 AppProject 使用
  # project: "team-backend"

1.3 利用 labels 進行分群

cluster Secret 的 labels 是 ApplicationSet（Vol 5）cluster generator 的關鍵——可以根據 labels 動態為符合條件的 cluster 部署 Application。

YAML — labels 應用範例（搭配 ApplicationSet）
## cluster-prod-us-east labels: environment=production, region=us-east-1
## cluster-prod-eu-west labels: environment=production, region=eu-west-1
## cluster-dev          labels: environment=dev, region=us-east-1

## ApplicationSet 用 cluster generator 自動產生 Application：
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            environment: production   # 只匹配 production cluster
  template:
    metadata:
      name: 'monitoring-{{name}}'     # 為每個 prod cluster 產生 Application
    spec:
      destination:
        server: '{{server}}'          # 從 cluster Secret 取得
        namespace: monitoring
      project: platform
      source:
        repoURL: https://github.com/myorg/platform-monitoring.git
        path: 'environments/{{metadata.labels.region}}'  # 根據 region 選 path

2五種認證方式比較

🎫
1. Bearer Token (SA)
通用
使用遠端叢集的 ServiceAccount token。最簡單、最廣泛支援。需要在遠端叢集建立 SA + ClusterRoleBinding。
通用 簡單 長期 token 需手動輪替
🔐
2. Client Certificate
自管 K8s
用 X509 client certificate 進行 mTLS 認證。憑證由 cluster CA 簽發，會過期需要更新。適合自管 K8s 叢集的高安全環境。
mTLS 會過期 需要 CA 簽發
🟧
3. EKS / IRSA
AWS EKS
使用 IAM role 認證，無靜態 token。AWS STS 自動輪替短期 token。CloudTrail 記錄所有操作。EKS 生產環境最佳選擇。
無靜態 token 自動輪替 CloudTrail 跨帳號
🟦
4. GKE / Workload Identity
GCP GKE
類似 IRSA，使用 GCP Service Account 認證。Argo CD SA 對應到 GCP SA，透過 Workload Identity Federation 取得 access token。
無靜態 token Cloud Audit Logs 設定複雜
🛠️
5. Exec-based
Cloud / 自定義
透過外部命令（如 aws-iam-authenticator、gke-gcloud-auth-plugin）取得 token。設定彈性最高，可整合任何認證系統。
最彈性 可自訂 需安裝 binary

2.1 Bearer Token (ServiceAccount) 設定

Bash + YAML — Bearer Token 完整流程
## ── Step 1：在遠端叢集建立 ServiceAccount + ClusterRoleBinding ──
--- # 在遠端叢集執行
apiVersion: v1
kind: ServiceAccount
metadata:
  name: argocd-manager
  namespace: kube-system
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-manager-role
rules:
  # 完整 cluster-admin 權限（後續用 Ch.14 的最小權限取代）
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["*"]
  - nonResourceURLs: ["*"]
    verbs: ["*"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: argocd-manager-role-binding
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: argocd-manager-role
subjects:
  - kind: ServiceAccount
    name: argocd-manager
    namespace: kube-system
---
## ── Step 2：建立 ServiceAccount Token（K8s 1.24+ 必要）──
## K8s 1.24+ 預設不再自動為 SA 建立 token Secret，需要手動建立
apiVersion: v1
kind: Secret
metadata:
  name: argocd-manager-token
  namespace: kube-system
  annotations:
    kubernetes.io/service-account.name: argocd-manager
type: kubernetes.io/service-account-token

## ── Step 3：取得 token 與 CA cert（在遠端叢集執行）──
$ TOKEN=$(kubectl get secret argocd-manager-token -n kube-system -o jsonpath='{.data.token}' | base64 -d)
$ CA=$(kubectl get secret argocd-manager-token -n kube-system -o jsonpath='{.data.ca\.crt}')
$ SERVER=$(kubectl config view --minify -o jsonpath='{.clusters[].cluster.server}')

## ── Step 4：在 Argo CD 叢集建立 cluster Secret ──
--- # 在 Argo CD 叢集執行
apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
stringData:
  name: prod
  server: $SERVER
  config: |
    {
      "bearerToken": "$TOKEN",
      "tlsClientConfig": {
        "insecure": false,
        "caData": "$CA"
      }
    }

2.2 Client Certificate (mTLS)

Bash — Client Certificate 簽發與設定
# 1. 生成 private key
$ openssl genrsa -out argocd-client.key 2048

# 2. 建立 CSR（CN=user, O=group）
$ openssl req -new -key argocd-client.key \
    -out argocd-client.csr \
    -subj "/CN=argocd-manager/O=system:masters"
# 注意：O=system:masters 給予 cluster-admin 權限（生產應改為自訂 group + ClusterRoleBinding）

# 3. 用 cluster CA 簽發（在 control plane node 執行，需要 CA key）
$ sudo openssl x509 -req \
    -in argocd-client.csr \
    -CA /etc/kubernetes/pki/ca.crt \
    -CAkey /etc/kubernetes/pki/ca.key \
    -CAcreateserial \
    -out argocd-client.crt \
    -days 365

# 4. 編碼為 base64 並組成 cluster Secret config
$ CERT_DATA=$(cat argocd-client.crt | base64 -w 0)
$ KEY_DATA=$(cat argocd-client.key | base64 -w 0)
$ CA_DATA=$(cat /etc/kubernetes/pki/ca.crt | base64 -w 0)

stringData:
  config: |
    {
      "tlsClientConfig": {
        "insecure": false,
        "caData": "$CA_DATA",
        "certData": "$CERT_DATA",
        "keyData": "$KEY_DATA"
      }
    }
# 注意：沒有 bearerToken，純 mTLS
⚠️

argocd cluster add 用 cert 認證的限制

實測中當 kubeconfig 使用 client-cert 認證（client-certificate-data + client-key-data），argocd cluster add 會建立 SA，但仍以 cert 而非 SA token 連線（GitHub issue #13175）。憑證過期後 Argo CD 會無法連線。建議：手動建立 SA 並取得 token 後，再以宣告式建立 cluster Secret。

3CLI 註冊：argocd cluster add

argocd cluster add 是最快的註冊方式：自動在遠端叢集建立 argocd-manager SA、ClusterRoleBinding，並在 Argo CD 叢集建立 cluster Secret。

Bash — argocd cluster add 完整流程
## Step 1：取得遠端叢集 context
$ kubectl config get-contexts
# CURRENT  NAME         CLUSTER          AUTHINFO   NAMESPACE
#          prod-us-east arn:aws:eks:...  user@prod  default
#          dev-cluster  dev.example.com  dev-admin  default

## Step 2：登入 Argo CD
$ argocd login argocd.example.com --sso

## Step 3：新增 cluster
$ argocd cluster add prod-us-east --name prod-us
# 自動：
#   1. 在 prod-us-east 建立 ServiceAccount: argocd-manager (kube-system)
#   2. 建立 ClusterRoleBinding: argocd-manager-role-binding
#   3. 建立 ServiceAccountToken Secret（K8s 1.24+）
#   4. 在 Argo CD 叢集建立 cluster Secret

## Step 4：驗證
$ argocd cluster list
# SERVER                          NAME             STATUS      MESSAGE
# https://kubernetes.default.svc  in-cluster       Successful  
# https://prod.example.com        prod-us          Successful  

## Step 5：限定 namespace（選填，安全強化）
$ argocd cluster add prod-us-east \
    --name prod-us \
    --namespace argocd-managed-1 \
    --namespace argocd-managed-2
# 此 cluster 只能部署到指定 namespace

## Step 6：使用自訂 SA 名稱（避開預設 argocd-manager）
$ argocd cluster add prod-us-east \
    --name prod-us \
    --service-account my-custom-sa \
    --system-namespace my-argocd-ns
ℹ️

argocd cluster add 不適合 GitOps 工作流程

CLI 註冊建立的 cluster Secret 不在 Git 中，無法版本控制、code review、disaster recovery。生產環境建議：用 CLI 一次註冊取得 token + CA，再轉為宣告式 cluster Secret 提交到 Git（見下節）。

4宣告式註冊（GitOps 模式）

把所有 cluster Secret 放入 Git repo，由 Argo CD 自己管理（self-managed），實現完整的 GitOps 工作流：

Bash + YAML — 宣告式 cluster 管理
## Git Repo 結構：
# argocd-config/
# └── clusters/
#     ├── prod-us-east.yaml         # SealedSecret 或 ExternalSecret
#     ├── prod-eu-west.yaml
#     ├── staging.yaml
#     └── dev.yaml

## clusters/prod-us-east.yaml（用 SealedSecrets 加密）
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: cluster-prod-us-east
  namespace: argocd
spec:
  template:
    metadata:
      labels:
        argocd.argoproj.io/secret-type: cluster
        environment: production
        region: us-east-1
  encryptedData:
    name: AgB...
    server: AgB...
    config: AgB...

## 建立 SealedSecret 流程
# 1. 建立明文 Secret（不要 commit）
$ kubectl create secret generic cluster-prod-us-east \
    --namespace argocd \
    --from-literal=name=prod-us-east \
    --from-literal=server=https://prod.example.com \
    --from-literal=config='{"bearerToken":"...","tlsClientConfig":{"caData":"..."}}' \
    --dry-run=client -o yaml > /tmp/cluster-prod-us-east.yaml

# 2. 加上 label（kubeseal 會保留 metadata）
$ kubectl label --local -f /tmp/cluster-prod-us-east.yaml \
    argocd.argoproj.io/secret-type=cluster \
    --dry-run=client -o yaml > /tmp/cluster-prod-labeled.yaml

# 3. 加密為 SealedSecret
$ kubeseal --format yaml < /tmp/cluster-prod-labeled.yaml \
    > clusters/prod-us-east.yaml

# 4. Commit 到 Git，由 Argo CD root App 管理 clusters/ 目錄

--- # root-clusters.yaml（在 Git 中）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: argocd-clusters
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://github.com/myorg/argocd-config.git
    targetRevision: main
    path: clusters
    directory:
      recurse: true
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: false      # ⚠️ 重要：絕不自動 prune cluster Secret（避免誤刪導致全部 App OutOfSync）
      selfHeal: true

5EKS IRSA 完整跨帳號設定

IRSA（IAM Roles for Service Accounts）是 EKS 環境最推薦的方式：無靜態 token、自動輪替、完整 CloudTrail 稽核、原生支援跨 AWS 帳號。設定流程較複雜，但生產環境值得投入。

架構：Argo CD 叢集（Account A）→ Spoke 叢集（Account B）

Bash — Step 1：在 Argo CD Account 建立 OIDC provider
# 確認 OIDC provider 已關聯
$ aws eks describe-cluster \
    --name argocd-management-cluster \
    --region us-east-1 \
    --query "cluster.identity.oidc.issuer" --output text

# 若未關聯，使用 eksctl 建立
$ eksctl utils associate-iam-oidc-provider \
    --cluster argocd-management-cluster \
    --region us-east-1 \
    --approve
JSON — Step 2：IAM Role Trust Policy（Account A）
## ArgoCD-IRSA-Controller 角色，只允許 Argo CD pod 透過 OIDC 取得
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        # OIDC provider ARN（Account A 的 management cluster）
        "Federated": "arn:aws:iam::ACCOUNT_A:oidc-provider/oidc.eks.us-east-1.amazonaws.com/id/XXXXX"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "oidc.eks.us-east-1.amazonaws.com/id/XXXXX:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          # 限定哪些 SA 可以 assume：argocd ns 中以 argocd- 開頭的 SA
          "oidc.eks.us-east-1.amazonaws.com/id/XXXXX:sub": "system:serviceaccount:argocd:argocd-*"
        }
      }
    }
  ]
}
YAML — Step 3：annotate Argo CD ServiceAccount（Account A）
## Helm values：annotate argocd-application-controller 與 argocd-server SA
controller:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT_A:role/ArgoCD-IRSA-Controller
    automountServiceAccountToken: true

server:
  serviceAccount:
    create: true
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT_A:role/ArgoCD-IRSA-Controller

# Argo CD pod 重啟後驗證：
$ kubectl exec -n argocd deploy/argocd-application-controller -- env | grep AWS
# AWS_ROLE_ARN=arn:aws:iam::ACCOUNT_A:role/ArgoCD-IRSA-Controller
# AWS_WEB_IDENTITY_TOKEN_FILE=/var/run/secrets/eks.amazonaws.com/serviceaccount/token
JSON — Step 4：跨帳號 Role（Account B）
## 在 Account B（target cluster）建立角色，trust policy 允許 Account A 的角色 assume
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        # Account A 的 Argo CD 管理角色
        "AWS": "arn:aws:iam::ACCOUNT_A:role/ArgoCD-IRSA-Controller"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
# 注意：此角色不需要任何權限（policies 為空）
# 它的存在只是為了讓 Argo CD assume 後再透過 aws-auth ConfigMap 對應到 K8s RBAC
YAML + JSON — Step 5：aws-auth + cluster Secret
## 在 spoke 叢集（Account B）的 aws-auth ConfigMap 加入對應
apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  mapRoles: |
    - rolearn: arn:aws:iam::ACCOUNT_B:role/ArgoCD-Spoke-Role
      username: argocd-controller
      groups:
        - system:masters     # 或自訂 group + ClusterRoleBinding（最小權限）

## 建立 cluster Secret（在 Argo CD 叢集）
apiVersion: v1
kind: Secret
metadata:
  name: cluster-account-b-prod
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
stringData:
  name: account-b-prod
  server: https://XYZ.gr7.us-east-1.eks.amazonaws.com
  config: |
    {
      "awsAuthConfig": {
        "clusterName": "spoke-cluster-b",
        "roleARN": "arn:aws:iam::ACCOUNT_B:role/ArgoCD-Spoke-Role"
      },
      "tlsClientConfig": {
        "insecure": false,
        "caData": "LS0tLS1CRUdJTi..."
      }
    }
## 注意：
# 1. 沒有 bearerToken（用 IRSA 動態取得）
# 2. awsAuthConfig.roleARN 指向 Account B 的 spoke role
# 3. Argo CD pod 用 Account A 的 IRSA assume Account B 的 role，再交換 K8s token
✅

IRSA 流程總覽

① Argo CD pod 啟動時，K8s 注入 OIDC token（projected SA token）
② Argo CD 用此 token 呼叫 STS:AssumeRoleWithWebIdentity → 取得 Account A IAM 短期 credentials
③ 用 Account A credentials 呼叫 STS:AssumeRole → 取得 Account B 短期 credentials
④ 用 Account B credentials 呼叫 EKS GetToken API → 取得 spoke cluster 的 K8s API token
⑤ 用此 token 連接 spoke cluster 並執行 manifest sync
整個流程沒有任何靜態長期 token，所有 token 自動由 STS 輪替。

6Cluster RBAC 最小權限（取代 cluster-admin）

第 2 節示範的 ClusterRole 是 cluster-admin（"*" verbs on "*" resources）。生產環境應參考 Ch.14 的最小權限模式：

YAML — 遠端叢集最小權限 ClusterRole
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-manager-restricted
rules:
  # 1. 全 cluster 讀取（diff 比對需要）
  - apiGroups: ["*"]
    resources: ["*"]
    verbs: ["get", "list", "watch"]

  # 2. 限定可寫的資源類型
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets", "daemonsets"]
    verbs: ["create", "update", "patch", "delete"]
  - apiGroups: [""]
    resources: ["services", "configmaps", "secrets", "serviceaccounts", "persistentvolumeclaims", "namespaces"]
    verbs: ["create", "update", "patch", "delete"]
  - apiGroups: ["networking.k8s.io"]
    resources: ["ingresses", "networkpolicies"]
    verbs: ["create", "update", "patch", "delete"]
  - apiGroups: ["autoscaling"]
    resources: ["horizontalpodautoscalers"]
    verbs: ["create", "update", "patch", "delete"]
  - apiGroups: ["batch"]
    resources: ["jobs", "cronjobs"]
    verbs: ["create", "update", "patch", "delete"]

  # 3. 應用層 events
  - apiGroups: ["", "events.k8s.io"]
    resources: ["events"]
    verbs: ["create", "patch"]

  # ❌ 預設不允許：ClusterRole / ClusterRoleBinding（避免提權）
  # ❌ 預設不允許：CRD（限定平台 cluster 才有此能力）
  # ❌ 預設不允許：MutatingWebhookConfiguration（避免劫持）

# 若 Application 需要管理這些資源（如 cert-manager），
# 用一個獨立的「Platform AppProject」搭配額外的 ClusterRole：
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-manager-platform      # 給 platform team 用

  - apiGroups: ["apiextensions.k8s.io"]

7外部 Secret 管理（自動 Token 輪替）

對於使用 bearer token 的非 EKS 環境，最佳實踐是用 External Secrets Operator + Vault / AWS Secrets Manager 自動同步並輪替 token：

YAML — ExternalSecret 動態取得 cluster credentials
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: cluster-prod-us-east
  namespace: argocd
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore

  target:
    name: cluster-prod-us-east      # 產生的 K8s Secret 名稱
    template:
      metadata:
        labels:
          argocd.argoproj.io/secret-type: cluster
          environment: production
          region: us-east-1
      data:
        name: prod-us-east
        server: https://prod.example.com
        config: |
          {
            "bearerToken": "{{ .token }}",
            "tlsClientConfig": {
              "insecure": false,
              "caData": "{{ .ca }}"
            }
          }

  data:
    - secretKey: token
      remoteRef:
        key: argocd/clusters/prod-us-east/token
    - secretKey: ca
      remoteRef:
        key: argocd/clusters/prod-us-east/ca

## 效果：
# Vault 中存放真實 token + CA
# Vault 自動每 24h 輪替 token（Vault dynamic secrets 功能）
# ESO 每 1h 重新拉取 → 更新 K8s Secret
# Argo CD 自動使用最新 token，無人工介入

# 1. 在遠端叢集刪除舊 token Secret
$ kubectl delete secret argocd-manager-token -n kube-system  --kubeconfig=remote-cluster.yaml

# 2. 重新建立 token Secret
$ kubectl apply --kubeconfig=remote-cluster.yaml -f - <<EOF
apiVersion: v1
kind: Secret
metadata:
  name: argocd-manager-token
  namespace: kube-system
  annotations:
    kubernetes.io/service-account.name: argocd-manager
type: kubernetes.io/service-account-token
EOF

$ NEW_TOKEN=$(kubectl get secret argocd-manager-token -n kube-system \
    --kubeconfig=remote-cluster.yaml \

📌 Key Takeaways

  • 📋cluster Secret 結構固定：argocd ns + argocd.argoproj.io/secret-type: cluster 標籤；三大欄位 name / server / config；config 是 JSON 字串。labels 是 ApplicationSet cluster generator 的關鍵分群依據。in-cluster 自動連線，不需 Secret。
  • 🎫五種認證方式選擇：① Bearer Token：通用、簡單但需手動輪替；② Client Certificate：mTLS，會過期；③ EKS IRSA：生產推薦，無靜態 token + CloudTrail；④ GKE Workload Identity：類似 IRSA 的 GCP 版本；⑤ Exec-based：最彈性，可自訂。
  • ⚙️K8s 1.24+ 必須手動建立 SA Token Secret：自動 token 機制已移除。需要建立 kubernetes.io/service-account-token 類型 Secret 並 annotate kubernetes.io/service-account.name。
  • 🚀argocd cluster add 用於初次註冊，但生產應用 GitOps：CLI 註冊不會建立 Git 中的 Secret，無法版本控制。建議：CLI 取得 token → 轉為宣告式 Secret（SealedSecret 或 ExternalSecret）→ commit 到 Git。
  • 🔐EKS IRSA 跨帳號流程：① OIDC provider；② Account A IAM role（trust SA）；③ annotate Argo CD SA；④ Account B 跨帳號 role；⑤ aws-auth 對應；⑥ cluster Secret 用 awsAuthConfig 而非 bearerToken。整個流程無靜態 token。
  • 🛡️cluster RBAC 應該最小權限：cluster-admin 是預設但不安全。生產環境用最小 ClusterRole 取代（read all + write 限定資源類型）。Platform team 用獨立 AppProject + 額外 ClusterRole 處理 ClusterRole / CRD 等高權限資源。
