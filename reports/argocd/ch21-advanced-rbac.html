進階 RBAC
與 Casbin 規則精通

RBAC 是 Argo CD 多租戶架構的核心。本章從 Casbin 政策模型出發，深入語法細節（policy / group / 萬用字元 / deny 優先）、Resource × Action 矩陣、sub-resource fine-grained 控制、Project Roles + JWT Tokens 的去中心化授權，並提供完整的 argocd admin settings rbac 除錯流程。

📋

前置：已閱讀 Ch.11（Projects 概覽）、Ch.14（policy.default 嚴格設定）、Ch.20（SSO Groups Claim）。理解 OIDC token 中 groups claim 的傳遞流程。

🎯 學習目標

  • 理解 Argo CD RBAC 的三層架構：global RBAC（argocd-rbac-cm）、project RBAC（AppProject roles）、SSO group bindings
  • 精通 Casbin policy 與 group 兩種規則的語法、優先順序、glob 比對
  • 掌握所有 9 種 resource type 與其支援的 action（applications / clusters / repositories / projects / accounts / certificates / gpgkeys / logs / exec / extensions / applicationsets）
  • 使用 sub-resource fine-grained RBAC 限制 application 內的特定 K8s 資源（如禁止刪除 PV）
  • 建立 Project Roles 並產生 JWT tokens 給 CI/CD 使用
  • 了解 Resource Actions（如重啟 Deployment）的 RBAC 控制
  • 使用 argocd admin settings rbac validate / can 驗證政策正確性
  • 處理 v3.x SAML/AWS SSO 的 group binding 已知問題
  • 設計企業級 RBAC 結構：admin / platform / sre / dev / readonly + project-scoped 隔離

1RBAC 完整模型

1.1 三層權限架構

Argo CD RBAC 是分層的——一個 user 的最終權限，是三層的聯集（任一層 allow 即可，但 explicit deny 永遠贏）：

Diagram — RBAC 三層架構
┌──────────────────────────────────────────────────────────────────┐
│  Layer 1: argocd-rbac-cm（Global RBAC）                          │
│  ──────────────────────────────────────                          │
│  • 跨所有 project 的全局規則                                      │
│  • 內建角色：role:admin、role:readonly                            │
│  • 自訂 role: + group binding                                    │
│  • policy.default 設定預設行為（永遠應為 ''）                    │
└──────────────────┬───────────────────────────────────────────────┘
                   │
                   │ 聯集
                   ▼
┌──────────────────────────────────────────────────────────────────┐
│  Layer 2: AppProject.spec.roles（Project RBAC）                  │
│  ──────────────────────────────────────                          │
│  • 限定於該 Project 內的應用                                     │
│  • 由 project owner 自行管理（無需 cluster admin）               │
│  • 可綁定 SSO group 或產生 JWT token                             │
│  • subject 格式：proj:<project>:<role>                          │
└──────────────────┬───────────────────────────────────────────────┘
                   │
                   │ 聯集
                   ▼
┌──────────────────────────────────────────────────────────────────┐
│  Layer 3: 個別使用者直接權限（user-scoped）                      │
│  ──────────────────────────────────────                          │
│  • 直接以 email 或 SSO sub 對應 role                             │
│  • 通常用於管理員例外、CI 服務帳戶                              │
└──────────────────┬───────────────────────────────────────────────┘
                   │
                   ▼
        最終權限 = (L1 ∪ L2 ∪ L3) ∩ ¬(任一層的 deny)
                   ↑
                   deny 永遠 trumps allow

1.2 內建角色

角色權限範圍用途
role:admin所有 resource × 所有 action × 所有 object（含 exec、override）平台管理員。嚴格限制人數，建議只給平台團隊負責人
role:readonly所有 resource 的 get；applications 與 logs 的 get（含 logs 子資源）QA、外包、observability tooling 的最小權限
role:unauthenticated無權限（空）啟用匿名存取時的預設角色（不建議啟用匿名）
⚠️

role:admin 的 exec 權限要特別注意

role:admin 預設包含 p, role:admin, exec, create, */*, allow——可以直接 argocd app exec 進入任意 pod。生產環境建議建立自訂 admin role 排除 exec：p, role:custom-admin, exec, create, */*, deny。需要 exec 時走另一條 break-glass 流程（如 PIM）。

2Casbin 規則語法詳解

2.1 policy + group 兩種規則

p p, <subject>, <resource>, <action>, <object>, <effect>
g g, <user/group>, <role-or-group>
欄位說明範例
subject誰擁有此權限：role:xxx、user 名稱、group 名稱、emailrole:developer、alice@example.com
resource資源類型（見第 3 節 11 種）applications、clusters
action操作（get / create / update / delete / sync / override / action / *）sync、delete、*
object目標物件，applications 用 <project>/<app>，其他通常用 *team-a/*、frontend/web-*
effectallow 或 denyallow
YAML — Casbin 完整語法範例
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: ''      # 永遠 deny by default
  scopes: '[groups,email]'     # 從 token 取出 group + email

  policy.csv: |
    # ─── Policy 規則（p）─────────────────────────────────

    # 1) role:developer：可看 + sync 所有 App，但不能 delete
    p, role:developer, applications, get,    */*, allow
    p, role:developer, applications, sync,   */*, allow
    p, role:developer, applications, action/*, */*, allow
    p, role:developer, logs, get, */*, allow
    p, role:developer, projects, get, *, allow

    # 2) role:team-a-deployer：限定 team-a project
    p, role:team-a-deployer, applications, *, team-a/*, allow
    p, role:team-a-deployer, applications, *, !team-a/*, deny    # 否定通配
    p, role:team-a-deployer, logs, get, team-a/*, allow

    # 3) role:sre：除了 production 都可以 delete
    p, role:sre, applications, *, */*, allow
    p, role:sre, applications, delete, */prod-*, deny    # deny 永遠贏
    p, role:sre, applications, override, */prod-*, deny

    # ─── Group 規則（g）─────────────────────────────────

    # SSO group → role 對應
    g, "platform-admins", role:admin
    g, "frontend-developers", role:team-a-deployer
    g, "sre-team", role:sre
    g, "all-developers", role:developer

    # 個別 user 直接給角色（緊急例外）
    g, "alice@example.com", role:admin

    # 巢狀群組（developer 自動繼承 readonly 權限）
    g, role:developer, role:readonly

    # 為 CI 服務帳戶的 Project Token 對應角色
    g, "proj:team-a:ci-token", role:team-a-deployer

2.2 deny 優先順序與 glob 比對規則

ℹ️

RBAC 評估順序

① 收集 user 的所有 role（透過 g 規則的傳遞 closure）；② 對每個 role，找符合的 p 規則；③ 任一規則 explicit deny → 拒絕；④ 任一規則 allow → 通過；⑤ 都沒匹配 → 用 policy.default。deny 永遠贏，這是 Casbin 的設計，不可更改。

Glob 模式（*、?、!）使用方式：

Patterns — Argo CD object/action glob 範例
# Wildcard *（匹配任意字串）
p, role:dev, applications, get, */*,        allow   # 所有 project / 所有 app
p, role:dev, applications, get, team-a/*,   allow   # team-a project 下所有 app
p, role:dev, applications, get, */api-*,    allow   # 任 project 下名稱以 api- 開頭的 app

# Question mark ?（匹配單一字元）
p, role:dev, applications, get, env-?/*, allow      # env-1, env-2, ... 但非 env-prod

# Negation !（否定匹配，常用於 deny）
p, role:dev, applications, *, !*/prod-*, deny       # 拒絕所有非 prod 以外的（雙否定，謹慎使用）

# Action 通配
p, role:dev, applications, *,    */*, allow         # 所有 action（包含 delete!）
p, role:dev, applications, get,  */*, allow         # 只有 get

# 對 Resource Actions 用 action/* （見第 6 節）
p, role:dev, applications, action/apps/Deployment/restart, */*, allow

3Resource × Action 矩陣

Argo CD 共有 11 種 RBAC resource type。每種支援的 action 不同：

applications
get, create, update, delete, sync, override, action/*
applicationsets
get, create, update, delete
clusters
get, create, update, delete
repositories
get, create, update, delete
projects
get, create, update, delete
accounts
get, update, action（如 update-password）
certificates
get, create, update, delete
gpgkeys
get, create, delete
logs
get（看 pod 日誌）
exec
create（進入 pod，極危險）
extensions
invoke（呼叫 UI extension）
⚠️

logs 與 exec 的 RBAC 變更（v3.0 起）

v2.x 中 applications, get 自動包含 logs 存取；v3.0 起 logs 必須明確授權。沒有 p, role:xxx, logs, get, */*, allow 的 user 在 UI 看不到 pod 日誌。同樣，exec 永遠是獨立 RBAC（從未繼承自 application），需單獨設定。

應用層 action 的詳細語意

Action意義常見場景
get讀取 Application 資訊（含 status、tree）所有 user 都需要
create建立新 Applicationlimited（只給 lead / admin）
update修改 Application spec（source、destination）limited（修改 deployment 設定）
delete刪除 Application（不一定 cascade 到 K8s 資源）嚴格控制；避免誤刪
sync觸發 manual syncdeployer 角色核心動作
override修改 Application 的 sync source（如 set image tag）慎用，繞過 GitOps 真理
action/*呼叫 Resource Actions（重啟 Deployment 等）operator 角色

4Sub-resource Fine-grained RBAC

v2.x 後新增的精細權限控制——可以限制 application 內特定類型 K8s 資源的操作。例如「可以 sync 整個 App 但不能 delete PersistentVolume」：

YAML — Sub-resource fine-grained 範例
data:
  policy.csv: |
    # Sub-resource 語法：<action>/<group>/<kind>/<namespace>/<name>
    # 也可以用 <action>/<group>/<kind>/<name> 簡化（match 任意 namespace）

    # 1) 允許 dev role 對所有 App 進行所有操作
    p, role:dev, applications, *, team-a/*, allow

    # 2) 但 explicit deny 刪除 PersistentVolume / PersistentVolumeClaim
    p, role:dev, applications, delete/*/PersistentVolume/*/*,      team-a/*, deny
    p, role:dev, applications, delete/*/PersistentVolumeClaim/*/*, team-a/*, deny

    # 3) 拒絕修改 RBAC 資源（即使 dev 是 owner）
    p, role:dev, applications, update/rbac.authorization.k8s.io/*, team-a/*, deny
    p, role:dev, applications, delete/rbac.authorization.k8s.io/*, team-a/*, deny

    # 4) 允許 sre 重啟 Pod，但不能 delete
    p, role:sre, applications, action/*/Pod/*, */*, allow
    p, role:sre, applications, delete/*/Pod/*, */*, deny

    # 5) 對特定 namespace（kube-system）的所有資源拒絕修改
    p, role:dev, applications, */*/*/kube-system/*, */*, deny
ℹ️

fine-grained RBAC 繼承行為（v3.0 變更）

v2.x：對 application 整體的 allow 自動繼承到所有 sub-resource。v3.0 起預設關閉繼承——必須分別授權。要保留 v2.x 行為，設定 server.rbac.disableApplicationFineGrainedRBACInheritance: false（在 argocd-cm）。預設關閉繼承的好處：可以用 explicit deny 排除特定 sub-resource（如上方 PV 範例）。

5Project Roles + JWT Token（去中心化授權）

5.1 Project Role 結構

Project Role 讓 project owner 自行管理該 project 的權限——不需要修改 cluster-wide 的 argocd-rbac-cm。權限自動 scoped 到該 project：

YAML — AppProject 含 Project Roles
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: payments
  namespace: argocd
spec:
  description: Payment service applications
  sourceRepos:
    - 'https://github.com/myorg/payments-service'
  destinations:
    - namespace: payments-*
      server: '*'
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'

  # Project Roles（核心區塊）
  roles:
    # Role 1：管理員（限定 payments project）
    - name: admin
      description: Full access to payments apps
      policies:
        - p, proj:payments:admin, applications, *, payments/*, allow
        - p, proj:payments:admin, logs, get, payments/*, allow
        - p, proj:payments:admin, exec, create, payments/*, allow
      groups:
        - payments-leads      # SSO group binding
        - payments-on-call

    # Role 2：Deployer（CI 用、無 exec / delete）
    - name: deployer
      description: Sync access for CI
      policies:
        - p, proj:payments:deployer, applications, get,    payments/*, allow
        - p, proj:payments:deployer, applications, sync,   payments/*, allow
        - p, proj:payments:deployer, applications, action/*, payments/*, allow
        - p, proj:payments:deployer, logs, get, payments/*, allow
      groups:
        - payments-developers

    # Role 3：Viewer（QA 唯讀）
    - name: viewer
      description: Read-only access
      policies:
        - p, proj:payments:viewer, applications, get, payments/*, allow
        - p, proj:payments:viewer, logs, get, payments/*, allow
      groups:
        - payments-qa
        - payments-product
⚠️

Project Role policy subject 必須是 proj:<name>:<role>

Project Role 的 subject 格式必須是 proj:<project-name>:<role-name>（冒號分隔），否則 RBAC enforcer 不會識別為 project role。其他格式（如 role:payments-admin）會被當成 global role 處理但不會生效。

5.2 JWT Token 生成與使用（CI/CD 整合）

對 CI/CD 等自動化系統，不適合用 SSO（無 web 互動）。Project Token 是 long-lived JWT，綁定特定 Project Role，可放入 CI secret：

Bash — 完整 JWT token 流程
## ── 設定環境變數 ─────────────────────────────────────
$ PROJECT=payments
$ ROLE=deployer

## ── 1) 在 AppProject 中先建立 role + policies（見上方 YAML）─

## ── 2) 產生 JWT token（指定過期時間）──────────────────
$ TOKEN=$(argocd proj role create-token $PROJECT $ROLE \
    --expires-in 720h \    # 30 天
    --token-only)
## 注意：產出後立即顯示，無法再取回，需妥善保存

## ── 3) 列出 token（看 ID + iat + expiry）──────────────
$ argocd proj role list-tokens $PROJECT $ROLE
# ID                          ISSUED-AT              EXPIRES-AT
# 1738000000                  2026-05-08T00:00:00Z   2026-06-07T00:00:00Z

## ── 4) CI 系統使用 token ─────────────────────────────
## GitHub Actions 範例：
## - name: Sync ArgoCD App
##   env:
##     ARGOCD_AUTH_TOKEN: ${{ secrets.ARGOCD_TOKEN }}
##     ARGOCD_SERVER: argocd.example.com
##   run: |
##     argocd app sync payments-api --auth-token $ARGOCD_AUTH_TOKEN

## ── 5) 撤銷 token（離職 / 洩漏時立即執行）─────────────
$ argocd proj role delete-token $PROJECT $ROLE 1738000000  # 用 ID

## ── 6) 解碼 JWT 看內容 ────────────────────────────────
$ echo $TOKEN | cut -d. -f2 | base64 -d | jq
# {
#   "iss": "argocd",
#   "sub": "proj:payments:deployer",     # ← role 對應的 subject
#   "iat": 1738000000,
#   "exp": 1740592000,
#   "jti": "1738000000"                  # token 唯一 ID
# }
💡

JWT Token 安全最佳實踐

① 永遠設定 expires-in（30 天為宜，CI 用 token 不需要長效）；② 存放在 K8s Secret 或 Vault，不要寫死 in CI YAML；③ 定期 audit（argocd proj role list-tokens）找未使用的 token 撤銷；④ 用 ExternalSecret 自動輪替（每月重新產生 + 更新 GitHub secret）；⑤ 重要操作（如 prod sync）改用短期 token + JIT。

6Resource Actions（自訂操作）的 RBAC

Resource Actions 是 Argo CD 對 K8s 資源的「按鈕」操作（在 UI 上點擊執行），如：重啟 Deployment、暫停 Rollout、回滾 StatefulSet。這些操作有獨立的 RBAC 路徑：

YAML — Resource Actions RBAC 設定
data:
  policy.csv: |
    # Resource Action 格式：
    # action/<group>/<kind>/<action-name>

    # 允許所有 resource action（萬用）
    p, role:operator, applications, action/*, */*, allow

    # 細粒度：只允許重啟 Deployment
    p, role:dev, applications, action/apps/Deployment/restart, team-a/*, allow

    # 細粒度：只允許暫停 Argo Rollouts
    p, role:dev, applications, action/argoproj.io/Rollout/pause,  team-a/*, allow
    p, role:dev, applications, action/argoproj.io/Rollout/resume, team-a/*, allow
    p, role:dev, applications, action/argoproj.io/Rollout/abort,  team-a/*, allow

    # 拒絕：StatefulSet 的 restart（避免誤操作 db）
    p, role:dev, applications, action/apps/StatefulSet/restart, team-a/*, deny

## 內建的 Resource Actions（部分清單）：
# action/apps/Deployment/restart     重啟 Deployment
# action/apps/StatefulSet/restart    重啟 StatefulSet（謹慎）
# action/apps/DaemonSet/restart      重啟 DaemonSet
# action/argoproj.io/Rollout/pause   暫停 Rollout
# action/argoproj.io/Rollout/resume  恢復 Rollout
# action/argoproj.io/Rollout/abort   中止 Rollout
# action/batch/CronJob/create-job    手動觸發 CronJob

## Custom Resource Actions：
# 在 argocd-cm 的 resource.customizations 自訂 Lua script，
# 設定後也用同樣 RBAC 路徑控制

7RBAC 除錯與驗證

7.1 argocd admin settings rbac 工具

Argo CD CLI 內建 RBAC 驗證指令，可在套用前測試：

Bash — RBAC 驗證指令
## ── 驗證 policy.csv 語法 ─────────────────────────────
# 從本地檔案
$ argocd admin settings rbac validate --policy-file policy.csv
# Validating policy file...
# Policy is valid.

# 從 live ConfigMap
$ argocd admin settings rbac validate -n argocd

## ── 測試特定 user 是否能執行特定操作 ──────────────────
## 語法：argocd admin settings rbac can <subject> <action> <resource> [object]

# 測試 alice@example.com 是否能 sync
$ argocd admin settings rbac can alice@example.com sync applications 'team-a/web' \
    --policy-file policy.csv
# Yes

# 測試 group 是否能 delete prod App
$ argocd admin settings rbac can platform-admins delete applications '*/prod-*' \
    --policy-file policy.csv
# No (denied by explicit rule)

# 測試 role:developer 的權限
$ argocd admin settings rbac can role:developer get applications '*/*' \
    -n argocd

# 用 default role 測試（policy.default 設定值）
$ argocd admin settings rbac can someone@example.com get applications '*/*' \
    --use-builtin-policy=false \
    --default-role role:readonly \
    -n argocd

## ── 從使用者視角驗證 ─────────────────────────────────
# 以當前登入身份測試
$ argocd account can-i sync application 'team-a/*'
# yes

$ argocd account can-i delete application '*/prod-app'
# no

## ── 看自己的所有權限 ─────────────────────────────────
$ argocd account get-user-info
## 顯示：JWT iss / sub / groups + 對應的 roles

7.2 v3.x SAML/AWS SSO Group Binding 已知問題

⚠️

v3.x 已知 issue：AWS IAM Identity Center SAML groups 無法匹配（GitHub #24869）

v3.1.5 至 v3.x 某些版本中，Casbin enforcer 在處理 SAML 來源的 groups claim 時不會迭代 group array，導致 g, <group-name>, role:admin 不生效。debug log 顯示「enforce failed」即使 token 中有正確的 groups。

workaround：① 改用 OIDC（如果 IdP 支援）；② 改用 email 對應（g, alice@example.com, role:admin）；③ 用 Project Role + group binding（在 AppProject 內，未受此 bug 影響）；④ 等 upstream 修復後升級。不要使用 policy.default: role:admin 當 workaround（嚴重安全風險）。

Bash — 診斷 group binding 是否生效
## ── Step 1：確認 groups 在 token 中 ──────────────────
$ TOKEN=$(yq '.users[0].auth-token' ~/.config/argocd/config)
$ echo $TOKEN | cut -d. -f2 | base64 -d | jq '.groups'
# ["argocd-admins", "platform-team"]   ← 確認有 groups

## ── Step 2：啟用 server debug log ────────────────────
$ kubectl set env -n argocd deploy/argocd-server ARGOCD_LOG_LEVEL=debug

## ── Step 3：登入 + 操作，看 log ──────────────────────
$ kubectl logs -n argocd deploy/argocd-server -f | grep -i "rbac\|enforce"

# 健康狀態：
# level=debug msg="enforce ok" subject="argocd-admins" action="get" resource="applications"

# 異常狀態（v3 已知 bug）：
# level=debug msg="enforce failed" subject="user@example.com" action="get"
## 注意 subject 是 user 而非 group ← 表示 group 沒被處理

## ── Step 4：恢復正常 log level ───────────────────────
$ kubectl set env -n argocd deploy/argocd-server ARGOCD_LOG_LEVEL=info

8企業級 RBAC 範例（中型組織）

結合本章所有概念，以下是一個 500-1000 App 中型組織的完整 RBAC 設計：

YAML — 企業級 argocd-rbac-cm
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: ''          # 永遠 deny
  scopes: '[groups,email]'

  policy.csv: |
    # ════════════════════════════════════════════════════════
    # 內建 admin 排除 exec（生產環境慣例）
    # ════════════════════════════════════════════════════════
    p, role:org-admin, applications, *, */*, allow
    p, role:org-admin, clusters, *, *, allow
    p, role:org-admin, repositories, *, *, allow
    p, role:org-admin, projects, *, *, allow
    p, role:org-admin, accounts, *, *, allow
    p, role:org-admin, certificates, *, *, allow
    p, role:org-admin, gpgkeys, *, *, allow
    p, role:org-admin, logs, get, */*, allow
    # 顯式拒絕 exec（即使 admin）
    p, role:org-admin, exec, create, */*, deny

    # ════════════════════════════════════════════════════════
    # Platform Team：管 platform 類 App（cert-manager、ingress 等）
    # ════════════════════════════════════════════════════════
    p, role:platform, applications, *, platform/*, allow
    p, role:platform, applications, get, */*, allow      # 看其他 project
    p, role:platform, clusters, *, *, allow
    p, role:platform, repositories, *, *, allow
    p, role:platform, projects, *, *, allow
    p, role:platform, certificates, *, *, allow
    p, role:platform, logs, get, */*, allow

    # ════════════════════════════════════════════════════════
    # SRE Team：跨 project 但拒絕 prod delete
    # ════════════════════════════════════════════════════════
    p, role:sre, applications, *, */*, allow
    p, role:sre, applications, delete, */prod-*, deny
    p, role:sre, applications, override, */prod-*, deny
    p, role:sre, logs, get, */*, allow
    p, role:sre, exec, create, */*, allow                # SRE 緊急除錯
    p, role:sre, projects, get, *, allow

    # ════════════════════════════════════════════════════════
    # 全公司 readonly（含管理階層）
    # ════════════════════════════════════════════════════════
    p, role:org-readonly, applications, get, */*, allow
    p, role:org-readonly, projects, get, *, allow
    p, role:org-readonly, repositories, get, *, allow
    p, role:org-readonly, clusters, get, *, allow
    p, role:org-readonly, logs, get, */*, allow

    # ════════════════════════════════════════════════════════
    # SSO Group → Role 對應
    # ════════════════════════════════════════════════════════
    g, "okta-argocd-admins", role:org-admin
    g, "okta-platform-team", role:platform
    g, "okta-sre-team", role:sre
    g, "okta-all-employees", role:org-readonly

    # Project-specific roles 寫在各 AppProject 內（見 S5 範例）
    # 透過 AppProject roles + groups bindings 實現
    # 例：team-a-leads → proj:team-a:admin

    # 緊急例外（個別 user）
    g, "emergency-admin@example.com", role:org-admin

📌 Key Takeaways

  • 📊RBAC 三層架構：Global RBAC（argocd-rbac-cm）+ Project RBAC（AppProject roles）+ User-scoped。三層權限是聯集；deny 永遠 trumps allow。
  • 📝Casbin 兩種規則：p（policy）定義「subject 對 resource 的 action 在 object 上的 allow/deny」；g（group）定義「user/group 屬於哪個 role」。glob 比對支援 *、?、! 萬用字元。RBAC 有 11 種 resource type，每種支援的 action 不同。
  • ⚠️v3.0 RBAC 變更要記住：① logs, get 必須明確授權（不再從 applications 繼承）；② exec 永遠是獨立 RBAC；③ Sub-resource fine-grained 預設不繼承（可用 disableApplicationFineGrainedRBACInheritance 還原 v2 行為）。
  • 🎯Project Roles 是去中心化授權的關鍵：subject 必須是 proj:<project>:<role>。讓 project owner 自管權限，無需 cluster admin 介入。同時支援 SSO group binding 與 JWT token，CI/CD 整合便利。
  • 🎫JWT Token 用於自動化：argocd proj role create-token 產生，必設過期時間（建議 30 天）+ 妥善存放 + 定期 audit + 用 ExternalSecret 自動輪替。離職 / 洩漏立即用 ID 撤銷。
  • 🔍RBAC 除錯黃金組合：① argocd admin settings rbac validate 驗證語法；② argocd admin settings rbac can 測試特定 subject 的權限；③ argocd account can-i 從 user 視角驗證；④ argocd-server debug log 看 enforce 結果。
  • 🐛v3.x SAML group binding 已知問題（GitHub #24869）：AWS IAM Identity Center 等 SAML 來源的 groups 可能無法匹配。workaround 用 email 對應或 Project Role binding，絕對不要用 policy.default: role:admin 當 workaround。
  • 🏢企業 RBAC 設計範式：org-admin（含 exec deny 例外）+ platform（管 platform 類 App）+ sre（跨 project 但 prod delete deny）+ org-readonly（全員看）+ Project-specific roles（在各 AppProject 內）。最小權限 + 集中政策 + 去中心化專案管理。
