自訂 Health Checks
Lua 腳本與 Resource Customizations 實戰

Vol 7 第一章。「我的 CRD 出問題但 Argo CD 顯示 Healthy」——這是因為 Argo CD 對自訂資源預設「存在 = Healthy」。本章深入 Lua-based health checks：obj / hs 物件、resource.customizations.health.<group>_<kind> naming、6 種 health 狀態、沙盒環境限制、5 個生產級實戰範例（PostgreSQL Operator、Argo Rollouts、Prometheus、External Secrets、SealedSecret）。另涵蓋 resource customizations 三大欄位（health / ignoreDifferences / actions）、argocd admin 測試工具、Lua 單元測試框架。讓 Argo CD UI 真正反映完整應用狀態。

📋

前置：已完成 Vol 1-6。理解 K8s CRD 與 Operator 模式。對 status conditions（lastTransitionTime、reason、message）熟悉。Lua 基本語法（if/else、table、return）——本章會教，但有基礎更快上手。

1為什麼需要自訂 Health Checks

1.1 內建 vs 自訂的判定流程

Argo CD 對標準 K8s 資源（Deployment / StatefulSet / Service / Ingress / Pod / Job / DaemonSet 等）有 hardcoded 健康判定邏輯。對 CRD / 自訂資源，預設的 fallback 是「存在 = Healthy」——這對 production 是嚴重問題：

Mermaid — Argo CD health 判定流程
Resource Synced
       │
       ▼
┌─────────────────────────────┐
│ Built-in health check 存在? │
└──────┬──────────────────────┘
       │
   ┌───┴─── Yes ──┐
   │              │
  No              ▼
   │       Execute built-in logic
   ▼              │
┌─────────────────────────┐
│ Custom Lua script 存在? │
└──────┬──────────────────┘
       │
   ┌───┴─── Yes ──┐
   │              │
  No              ▼
   │       Execute Lua script
   ▼              │
Return "Healthy"  │
（fallback）      │
   │              │
   └─────────────┴────► Return hs.status + hs.message
                                 │
                                 ▼
                         ArgoCD UI 顯示

關鍵問題：

  • ① DatabaseCluster 建立失敗（status: Failed）→ Argo CD 顯示 Healthy（因為物件存在）；
  • ② Certificate 還在等 CA 簽署（status: Issuing）→ Argo CD 顯示 Healthy（部署完成但實際還不能用）；
  • ③ Argo CD UI 不再是「single pane of glass」，運維者必須再去個別 Operator 查狀態。

1.2 6 種 Health 狀態

狀態意義典型情境
Healthy資源完全正常運作Deployment 所有 replica Ready
Progressing資源正在更新或啟動中（暫時狀態）Deployment 滾動更新中、Certificate 簽署中
Degraded資源有問題，需要關注Pod CrashLoopBackOff、Cert 簽署失敗
Suspended資源暫停（等外部事件恢復）暫停的 CronJob、paused Deployment
Missing資源應存在但未找到Application 已 sync 但物件被外部刪除
Unknown無法判定（如 Lua 腳本錯誤）nil pointer、unknown structure
💡

預設應該回 Progressing 而非 Healthy

撰寫 Lua check 時，遇到「不確定狀態」（status field 還沒出現、condition 還沒設定）應該回 Progressing 而非 Healthy。Progressing 表示「正在處理中，請耐心等待」；Healthy 表示「100% 確認沒問題」。錯誤回 Healthy 會讓 CI/CD pipeline 在 argocd app wait --health 立刻通過，但實際資源還沒就緒——可能造成下游 stage 失敗。

2Lua 腳本基礎

2.1 obj 與 hs 結構

每個 Lua health check 都遵循相同的 contract：

Lua — 最小可行 health check 範例
-- obj：global 變數，含完整的 K8s resource 物件（從 etcd 取得的 unstructured object）
-- 可以存取 obj.apiVersion / obj.kind / obj.metadata / obj.spec / obj.status

-- 必須 return 一個 table（Lua 中 table 是字典結構）
hs = {}
hs.status = "Progressing"      -- 6 種狀態之一
hs.message = "Waiting for resource to be ready..."

-- 主邏輯：檢查 status field
if obj.status ~= nil then
  if obj.status.phase == "Running" then
    hs.status = "Healthy"
    hs.message = "Resource is running"
  elseif obj.status.phase == "Failed" then
    hs.status = "Degraded"
    hs.message = obj.status.message or "Resource failed"
  end
end

return hs

2.2 Naming Convention

Health check 儲存在 argocd-cm ConfigMap 的 data field，key 遵循特定格式：

YAML — Naming convention 範例
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 格式：resource.customizations.health.<group>_<kind>
  # 注意：group 中的 . 保留，group 與 kind 之間用 _ 分隔

  # 範例 1：cert-manager.io group 的 Certificate kind
  resource.customizations.health.cert-manager.io_Certificate: |
    hs = { status = "Progressing", message = "..." }
    -- 完整 Lua 腳本
    return hs

  # 範例 2：core group 的 ConfigMap（empty group）
  resource.customizations.health._ConfigMap: |
    -- 注意：core group 是空字串，所以 key 是 "._ConfigMap"
    return { status = "Healthy" }

  # 範例 3：argoproj.io group 的 Application（自訂自己）
  resource.customizations.health.argoproj.io_Application: |
    hs = {}
    if obj.status ~= nil and obj.status.health ~= nil then
      hs.status = obj.status.health.status
      hs.message = obj.status.health.message
    end
    return hs

  # 範例 4：使用 wildcard 寫法（key 結構不同！）
  resource.customizations: |
    cert-manager.io/Certificate:
      health.lua: |
        -- Lua 腳本
⚠️

Wildcard 只在 resource.customizations 鍵下支援

K8s ConfigMap key 不允許 *，所以 resource.customizations.health.<group>_<kind> 寫法不能用 wildcard。如果要 match 多個 kind（如 cert-manager.io/*），必須改用第二種寫法：把所有 customizations 放在單一 resource.customizations key 下，用 YAML 結構表達——這樣就可以用 wildcard：cert-manager.io/*: { health.lua: ... }。

2.3 沙盒環境限制

為了安全，Argo CD 的 Lua 環境是嚴格沙盒：

不允許原因替代方案
require()不能載入外部 module所有邏輯寫在單一腳本
os.execute() / os.exit()不能執行 shell 命令—
io.* 全部不能讀寫檔案—
load() / loadfile() / dofile()不能執行動態 code—
網路存取不能 HTTP request 等只能用 obj 中的資料
collectgarbage()不能控制 GC不需要

可以使用：基本 Lua 語法（if/else/while/for）、table 操作、string 操作（string.find / string.match / string.format 等）、math 函數、tostring / tonumber。對於 health check 來說完全足夠。

3第一個 Health Check：cert-manager Certificate

從一個實際範例開始——cert-manager 的 Certificate CRD：

YAML — cert-manager Certificate Custom Resource 結構
# 一個典型的 Certificate 物件，status 部分由 cert-manager controller 填入
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: example-com-tls
spec:
  secretName: example-com-tls
  issuerRef:
    name: letsencrypt-prod
  dnsNames:
    - example.com
status:
  conditions:
    - type: Ready
      status: "True"          # or "False" / "Unknown"
      reason: Ready
      message: "Certificate is up to date and has not expired"
      lastTransitionTime: "2026-05-09T14:32:00Z"
YAML — Certificate health check 完整實作
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  resource.customizations.health.cert-manager.io_Certificate: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Initializing certificate..."

    -- 1) 防禦性：先檢查 status 是否存在
    if obj.status ~= nil and obj.status.conditions ~= nil then

      -- 2) 遍歷 conditions 找 Ready type
      for i, condition in ipairs(obj.status.conditions) do
        if condition.type == "Ready" then

          -- 3) 依 condition status 判斷
          if condition.status == "True" then
            hs.status = "Healthy"
            hs.message = condition.message
            return hs
          elseif condition.status == "False" then
            hs.status = "Degraded"
            hs.message = condition.message
            return hs
          end
        end
      end

      -- 4) 沒找到 Ready condition 或 status=Unknown
      hs.message = "Waiting for Ready condition"
    end

    return hs
Bash — 套用並驗證
# 套用 ConfigMap 變更
$ kubectl apply -f argocd-cm.yaml

# 重啟 application-controller 套用變更（不需 server restart）
$ kubectl rollout restart statefulset \
    argocd-application-controller -n argocd

# 等 controller ready
$ kubectl rollout status statefulset \
    argocd-application-controller -n argocd

# 在 UI 中：Certificate 物件現在會顯示真實 health 狀態
# - Issuing 中: Progressing
# - Ready: Healthy + condition message
# - 簽署失敗: Degraded + error message
ℹ️

cert-manager 已內建在 Argo CD

實務上 cert-manager 等主流 Operator 的 health check 已內建在 Argo CD 主 repo 的 resource_customizations/ 目錄。如果你用最新版 Argo CD，不需要自己寫——這個範例只是教學。但如果你用客製 Operator 或內部 CRD，就必須自己撰寫。可以參考 resource_customizations/cert-manager.io/Certificate/health.lua 學習 best practice。

45 個生產實戰範例

4.1 Zalando PostgreSQL Operator

YAML — postgresql.acid.zalan.do/postgresql health check
data:
  resource.customizations.health.acid.zalan.do_postgresql: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Initializing PostgreSQL cluster..."

    if obj.status ~= nil and obj.status.PostgresClusterStatus ~= nil then
      local clusterStatus = obj.status.PostgresClusterStatus

      -- Running 是預期的最終狀態
      if clusterStatus == "Running" then
        hs.status = "Healthy"
        hs.message = "Cluster is running"

      -- Creating / Updating 都是進行中
      elseif clusterStatus == "Creating" or
             clusterStatus == "Updating" or
             clusterStatus == "Synchronizing" then
        hs.status = "Progressing"
        hs.message = "Cluster status: " .. clusterStatus

      -- Invalid / CreateFailed 都是失敗
      elseif clusterStatus == "Invalid" or
             clusterStatus == "CreateFailed" or
             clusterStatus == "UpdateFailed" or
             clusterStatus == "SyncFailed" then
        hs.status = "Degraded"
        hs.message = "Cluster failed: " .. clusterStatus
      end
    end

    return hs

4.2 Argo Rollouts

YAML — Argo Rollouts health check
data:
  resource.customizations.health.argoproj.io_Rollout: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Initializing rollout..."

    if obj.status == nil then
      return hs
    end

    -- Argo Rollouts 有自己的 phase 欄位
    if obj.status.phase == "Healthy" then
      hs.status = "Healthy"
      hs.message = obj.status.message or "Rollout is healthy"

    elseif obj.status.phase == "Paused" then
      -- Canary 在 step 之間暫停（等待手動 promotion）
      hs.status = "Suspended"
      hs.message = obj.status.message or "Rollout is paused"

    elseif obj.status.phase == "Progressing" then
      hs.status = "Progressing"
      hs.message = obj.status.message or "Rolling out new version"

    elseif obj.status.phase == "Degraded" then
      hs.status = "Degraded"
      hs.message = obj.status.message or "Rollout degraded"
    end

    return hs
💡

Paused 對應到 Suspended 狀態

Argo Rollouts canary 在 step 之間暫停等待 manual promotion 時，是「等待外部事件」的設計性暫停，不應視為 Degraded。用 Suspended 狀態，UI 會顯示特殊圖示讓運維者知道需要互動。同樣適用 paused Deployment、suspended CronJob。

4.3 Prometheus Operator（複雜：檢查多個 replica）

YAML — Prometheus health check
data:
  resource.customizations.health.monitoring.coreos.com_Prometheus: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Waiting for Prometheus to start..."

    if obj.status == nil then return hs end

    -- Prometheus 有 availableReplicas / unavailableReplicas
    local available = obj.status.availableReplicas or 0
    local unavailable = obj.status.unavailableReplicas or 0
    local desired = obj.spec.replicas or 1

    if available == desired and unavailable == 0 then
      hs.status = "Healthy"
      hs.message = "All " .. desired .. " Prometheus replicas are available"

    elseif unavailable > 0 and available == 0 then
      hs.status = "Degraded"
      hs.message = unavailable .. " replicas unavailable, 0 available"

    elseif available < desired then
      hs.status = "Progressing"
      hs.message = available .. "/" .. desired .. " replicas available"
    end

    return hs

  # 同樣用於 Alertmanager（結構相同）
  resource.customizations.health.monitoring.coreos.com_Alertmanager: |
    # （同上邏輯）

4.4 External Secrets Operator

YAML — ExternalSecret health check
data:
  resource.customizations.health.external-secrets.io_ExternalSecret: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Syncing from secret store..."

    if obj.status ~= nil and obj.status.conditions ~= nil then
      -- ExternalSecret 用 conditions 表達狀態
      for i, c in ipairs(obj.status.conditions) do

        -- Ready: True = 成功從外部 secret store 同步
        if c.type == "Ready" then
          if c.status == "True" then
            hs.status = "Healthy"
            hs.message = "Secret synced: " .. (c.message or "")
            return hs

          elseif c.status == "False" then
            hs.status = "Degraded"
            hs.message = c.message or "Failed to sync secret"
            -- 常見原因：AWS IAM 權限不足、Vault token 過期、secret path 錯誤
            return hs
          end
        end
      end
    end

    return hs

4.5 SealedSecret

YAML — SealedSecret health check
data:
  resource.customizations.health.bitnami.com_SealedSecret: |
    hs = {}
    hs.status = "Progressing"
    hs.message = "Waiting for SealedSecret to be unsealed..."

    if obj.status ~= nil and obj.status.conditions ~= nil then
      for i, c in ipairs(obj.status.conditions) do

        if c.type == "Synced" then
          if c.status == "True" then
            hs.status = "Healthy"
            hs.message = "Secret unsealed and synced"
            return hs

          elseif c.status == "False" then
            -- 常見失敗：用錯 controller 的 public key 加密、Secret 已被外部修改
            hs.status = "Degraded"
            hs.message = c.message or "Failed to unseal SealedSecret"
            return hs
          end
        end
      end
    end

    return hs

5Resource Customizations 全覽

除了 health，resource.customizations 還有兩個重要欄位：

5.1 ignoreDifferences（忽略 diff）

有些 controller 會自動修改 K8s 物件（如 HPA 修改 Deployment replicas、Operator 加 finalizer）——Argo CD 看到 diff 會反覆 sync 造成 fight。用 ignoreDifferences 排除特定欄位的 diff 偵測：

YAML — 全域 ignoreDifferences 範例
data:
  # 全域：所有 Deployment 都忽略 replicas（讓 HPA 自由調整）
  resource.customizations.ignoreDifferences.apps_Deployment: |
    jsonPointers:
      - /spec/replicas

  # 對所有 group/kind 共通：忽略 Operator 自動加的 finalizer
  resource.customizations.ignoreDifferences.all: |
    jsonPointers:
      - /metadata/finalizers

  # 用 managedFieldsManagers（v2.5+）：忽略特定 controller 修改的欄位
  resource.customizations.ignoreDifferences.apps_Deployment: |
    managedFieldsManagers:
      - "kube-controller-manager"    # 忽略 HPA controller 的修改
    jsonPointers:
      - /spec/replicas

  # 用 jqPathExpressions（v2.6+）：複雜過濾
  resource.customizations.ignoreDifferences.batch_CronJob: |
    jqPathExpressions:
      - '.spec.jobTemplate.spec.template.spec.containers[].image'    # 忽略 image 變更（外部更新）
⚠️

全域 ignoreDifferences vs Application 級

全域設定影響所有 Application，要謹慎使用。如果只想對特定 Application 忽略 diff，用 Application spec 的 spec.ignoreDifferences 欄位（per-app 設定）。建議：① cluster-scoped 共通行為（如 HPA / Operator finalizer）→ 全域；② 應用特定的 patch（如 SealedSecret 解密後的 secret data）→ per-app。

5.2 Actions（UI 自訂操作按鈕）

Argo CD UI 對 K8s 資源提供「Actions」按鈕（如 Deployment 的 restart）。用 Lua 可以加自訂 action：

YAML — 自訂 action：暫停 / 恢復 Rollout
data:
  # 列出此資源類型支援的 actions（discovery）
  resource.customizations.actions.argoproj.io_Rollout: |
    discovery.lua: |
      actions = {}

      -- 只在 Healthy 狀態才能 restart
      actions["restart"] = {
        disabled = obj.status.phase ~= "Healthy"
      }

      -- 只在 Paused 狀態才能 resume
      actions["resume"] = {
        disabled = obj.status.phase ~= "Paused"
      }

      -- 暫停按鈕（Healthy 時可用）
      actions["pause"] = {
        disabled = obj.status.phase ~= "Healthy"
      }

      return actions

    definitions:
      # 各 action 的具體實作
      - name: restart
        action.lua: |
          -- 重啟所有 ReplicaSet pod（透過 annotation）
          obj.spec.restartAt = os.date("!%Y-%m-%dT%H:%M:%SZ")
          return obj

      - name: pause
        action.lua: |
          obj.spec.paused = true
          return obj

      - name: resume
        action.lua: |
          obj.spec.paused = false
          return obj

# 套用後 UI 上點擊 Rollout 物件會看到三個按鈕：
# [Restart] [Pause] [Resume]

data:

6測試與除錯

6.1 argocd admin settings 命令

本機測試 Lua 腳本是否會在 Argo CD 環境正確執行：

Bash — argocd admin settings 測試
## 1. 驗證 argocd-cm 整體設定合法性
$ argocd admin settings validate --argocd-cm-path argocd-cm.yaml \
    --argocd-secret-path argocd-secret.yaml
# 輸出：✓ Application overrides settings is valid
#       ✓ Resource overrides settings is valid
#       ...

## 2. 列出所有可用 health check（內建 + 自訂）
$ argocd admin settings resource-overrides list-actions \
    --argocd-cm-path argocd-cm.yaml
# 列出所有 group/kind 與其 action / health 狀態

## 3. 對特定 resource 執行 health check
$ cat my-certificate.yaml | argocd admin settings resource-overrides health \
    --argocd-cm-path argocd-cm.yaml -
# 輸出：
# STATUS: Healthy
# MESSAGE: Certificate is up to date and has not expired

## 4. 對特定 resource 列出可執行的 actions
$ cat my-rollout.yaml | argocd admin settings resource-overrides list-actions \
    --argocd-cm-path argocd-cm.yaml -
# 輸出：
# NAME      DISABLED
# restart   false
# pause     false
# resume    true

## 5. 對特定 resource 執行 action（dry-run 看修改後的物件）
$ cat my-rollout.yaml | argocd admin settings resource-overrides run-action \
    --argocd-cm-path argocd-cm.yaml - pause
# 輸出修改後的 YAML（spec.paused: true）

6.2 撰寫 Lua 單元測試

Argo CD 主 repo 的 resource_customizations/ 目錄使用內建測試框架，同樣可以在自己的 repo 用：

Tree — 標準目錄結構
resource_customizations/
└── cert-manager.io/
    └── Certificate/
        ├── health.lua              # Lua health check 腳本
        ├── health_test.yaml        # 測試案例
        └── testdata/
            ├── ready.yaml          # Test case 1：Healthy 狀態
            ├── issuing.yaml        # Test case 2：Progressing
            └── failed.yaml         # Test case 3：Degraded
YAML — health_test.yaml 範例
# resource_customizations/cert-manager.io/Certificate/health_test.yaml
tests:
  - healthStatus:
      status: Healthy
      message: "Certificate is up to date and has not expired"
    inputPath: testdata/ready.yaml

  - healthStatus:
      status: Progressing
      message: "Issuing certificate..."
    inputPath: testdata/issuing.yaml

  - healthStatus:
      status: Degraded
      message: "Failed to validate ACME order"
    inputPath: testdata/failed.yaml
Bash — 執行測試
# Clone argocd repo（用於測試框架）
$ git clone https://github.com/argoproj/argo-cd.git
$ cd argo-cd

# 把自己的 customization 放到 resource_customizations/ 對應目錄
$ cp -r my-customizations/* resource_customizations/

# 執行測試（Go test）
$ go test ./resource_customizations/... -v
# === RUN   TestLuaHealthScript
# === RUN   TestLuaHealthScript/cert-manager.io/Certificate
# === RUN   TestLuaHealthScript/cert-manager.io/Certificate/Healthy
# --- PASS: TestLuaHealthScript/cert-manager.io/Certificate/Healthy (0.00s)
# ...
💡

CI 中自動跑 Lua 測試

把 Lua 腳本與測試 commit 到自己的 GitOps repo，CI 中跑這些測試確保改動不破壞 health check。當 Operator 升級造成 status 結構變化時，能立刻發現 Lua 腳本失效（測試 fail），避免上 production 才發現。這比 production 出包後才除錯快十倍。

最佳實踐 Checklist

✅

Lua Health Check 撰寫 10 原則

① 先檢查 Argo CD 內建（resource_customizations/）是否已有，不要重複造輪；② 預設 Progressing，找到正向證據才 Healthy；③ 嚴格 nil 檢查（status / conditions / each field）；④ 提供有用的 message（運維者一眼看出問題）；⑤ 處理多個 condition（不是只看第一個）；⑥ 區分 Suspended 與 Progressing（暫停的 Rollout、CronJob 用 Suspended）；⑦ commit 完整 testdata + health_test.yaml；⑧ CI 跑 go test ./resource_customizations/；⑨ Operator 升級時重跑測試；⑩ 修改後 rollout restart application-controller。

Lua pattern 速查

Lua pattern類比 PCRE說明
%d\\d任一數字
%a[a-zA-Z]任一英文字母
%w[a-zA-Z0-9]字母或數字
%s\\s空白字元
++1 或多
-*（lazy）0 或多（最短匹配）
**（greedy）0 或多（最長匹配）

📌 Key Takeaways

  • 🎯Argo CD 對 CRD 預設「存在 = Healthy」——這是 production GitOps 的隱形 bug。Certificate 簽署失敗、DatabaseCluster 建立失敗、Operator 卡在 reconcile loop——全部顯示 Healthy。自訂 health check 是 production 必備，不是 nice-to-have。
  • 📊6 種 Health 狀態各有定位：Healthy（正常）/ Progressing（進行中，預設）/ Degraded（有問題）/ Suspended（等外部事件）/ Missing（應存在但找不到）/ Unknown（無法判定）。暫停的 Rollout / paused Deployment 用 Suspended（不是 Degraded），UI 會顯示特殊圖示提示運維者互動。
  • 📝Lua 腳本 contract：global 變數 obj 是完整 K8s resource（含 spec/status），return 一個含 status + message 的 table（hs 變數）。沙盒環境禁用 require / io / os.execute / 網路——但 health check 用基本 Lua + table + string 完全夠用。
  • 🔑ConfigMap key 命名：resource.customizations.health.<group>_<kind>。core group 是空字串（._ConfigMap）；group dots 保留。K8s ConfigMap key 不允許 *——要 wildcard 必須改用 resource.customizations: 整體鍵 + 巢狀 YAML 結構。
  • 💎5 大實戰 health check 範例：① cert-manager Certificate（檢查 Ready condition）；② Zalando PostgreSQL（檢查 PostgresClusterStatus）；③ Argo Rollouts（含 Suspended 處理）；④ Prometheus Operator（檢查 availableReplicas vs spec.replicas）；⑤ ExternalSecret / SealedSecret（檢查 conditions）。這 5 個範例覆蓋 80% 生產場景的撰寫模式。
  • ⚙️resource.customizations 三大欄位：① health（健康判定，本章主題）；② ignoreDifferences（忽略 HPA / Operator 自動修改）；③ actions（UI 自訂按鈕，如 Rollout pause/resume/restart）。v2.6+ 新增 knownTypeFields 處理 CRD Strategic Merge Patch 推導問題。
  • 🧪argocd admin settings 是本地測試利器：resource-overrides health（測 health check）、list-actions（測 action discovery）、run-action（測 action 執行，輸出修改後 YAML）、validate（驗證整體合法性）。每次改 Lua 前先 local test，避免 prod 上 controller 拋 Lua 錯誤。
  • 📂用 health_test.yaml 做單元測試：Argo CD repo 的 resource_customizations/ 標準結構（health.lua + health_test.yaml + testdata/）。go test 跑所有 test case。CI 中自動跑這些測試——Operator 升級造成 status 變化時立刻發現，比 production 出包早十倍。
  • ⚠️七大常見陷阱：未做 nil 檢查（最常見）、預設回 Healthy 而非 Progressing、wildcard 用錯位置、Operator 升級後失效、Lua pattern 不是 PCRE、condition 順序處理、修改後沒 rollout restart。10 項撰寫原則避免絕大多數問題。
