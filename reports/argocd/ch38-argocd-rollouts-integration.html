Argo CD + Argo Rollouts 整合
Istio、Gateway API、生產實踐

Vol 8 最後一章。Ch.36-37 介紹了 Argo Rollouts 與 AnalysisTemplate，本章專注 Argo CD 與 Argo Rollouts 的協同整合：Argo CD UI 對 Rollout 的內建 health check（v2.0+）、Actions 按鈕（promote/abort/restart）、回滾策略（Git revert vs argo rollouts abort）、與 Service Mesh / Gateway API 的完整 traffic routing 整合（Istio VirtualService + DestinationRule、Gateway API HTTPRoute、NGINX、SMI、ALB、AppMesh）、Istio 物件的 health check 補完、argocd-notifications 整合 Rollouts events、生產級完整 stack 範例。完成本章後你具備設計、部署、運維 GitOps + Progressive Delivery 完整 platform 的能力。

1內建整合機制

1.1 Rollout Health Check（v2.0+ 內建）

Argo CD 從 v2.0 起內建 Rollout 的 health check——不需要自己寫 Lua（雖然 Ch.37 範例展示了如何寫，那是 fallback 教學）。當 Argo CD 看到 Rollout CR，自動依照 status.phase 判斷 health：

Rollout phaseArgo CD healthUI 顯示
HealthyHealthy綠色心跳 + step 100% / 100%
ProgressingProgressing藍色旋轉 + 當前 step / setWeight
PausedSuspended橘色暫停 icon + pause reason
DegradedDegraded紅色驚嘆 + abort reason
AbortedDegraded紅色 + "Rollout aborted"
ℹ️

「Paused = Suspended」是設計上的重要決策

當 Rollout 在 pause: {}（無限等待 manual promote），Argo CD 顯示 Suspended 而非 Degraded——告訴運維者「這不是錯誤，是等你互動」。Suspended 也不會觸發 Notifications 的 on-health-degraded trigger（Ch.29），避免半夜 paging。但 sync wave 會卡住——Rollout 沒到 Healthy，下個 wave 不會推進，所以 Suspended 仍然影響整體部署流程。

                                      │ 4. promote / abort  │

關鍵理解：

  • ① Argo CD 管 spec：Rollout / AnalysisTemplate / VirtualService 等 CRD 的 spec 由 Git 控制；
  • ② Argo Rollouts 管實體：ReplicaSet 數量、VirtualService 的 weight、AnalysisRun 結果由 Rollouts controller 動態管理；
  • ③ 兩者透過 K8s API 解耦：Argo CD 不需要知道 Rollouts 存在（就是個 CRD），Rollouts 也不依賴 Argo CD。

2UI Actions for Rollout

2.1 promote / abort / restart 按鈕

Argo CD UI 在 Rollout 物件提供四個 action 按鈕——直接從 Argo CD UI 操作，不需切換到 kubectl 或 Argo Rollouts Dashboard：

UI Action對應 CLI使用情境
promotekubectl argo rollouts promote從 pause:{} 推進到下一個 step
promote-fullpromote --full跳過剩餘 step 直接 100%
abortabort放棄這次 rollout，流量切回 stable
restartrestart滾動重啟所有 pod（不換版本）
retryretry rolloutabort 後重新觸發
resume--unpause從 manual pause 恢復

使用流程：

1
Argo CD UI → 點開 Application → 找到 Rollout 物件
2
右鍵或點選 Rollout → 看到 "ACTIONS" 下拉選單
3
選擇 promote / abort / restart 等 action
4
Argo CD 透過 Rollout subresource API 觸發對應動作
5
Argo Rollouts controller 偵測到變更，執行實際邏輯

2.2 CSP / Cluster RBAC 設定

YAML — RBAC: 允許 dev 看 / SRE 操作 Rollout
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.csv: |
    # ── Role: developer（只能看，不能操作 Rollout）─────
    p, role:developer, applications, get, */*, allow
    p, role:developer, applications, sync, */*, allow
    # 不允許 application action（包含 Rollout actions）

    # ── Role: sre（可操作 Rollout actions）──────────
    p, role:sre, applications, get, */*, allow
    p, role:sre, applications, sync, */*, allow
    # 關鍵：允許 application action（promote / abort / restart）
    p, role:sre, applications, action/*, */*, allow

    # ── Role: emergency-on-call（緊急可用）──────────
    p, role:emergency, applications, action/argoproj.io/Rollout/*, */*, allow
    # 只給 Rollout actions（不能改其他資源）

    # ── 用戶分組 ──────────────────────────────────
    g, dev-team, role:developer
    g, sre-team, role:sre
    g, on-call-bot, role:emergency
💡

細粒度 RBAC：只允許特定 Rollout action

除了 action/* 通用權限，還可以細分到特定 action：① action/argoproj.io/Rollout/restart（只允許 restart）；② action/argoproj.io/Rollout/abort（只允許 abort）。實務：dev role 給 restart（重啟 pod 不換版本，影響小）；SRE role 才給 promote / abort（會影響流量切換）。on-call bot 給 abort 緊急回滾。

3回滾策略：Git revert vs argo rollouts abort

3.1 兩種回滾路徑

面向argo rollouts abort（imperative）git revert（declarative，GitOps-pure）
觸發方式Argo CD UI Actions / CLIGit 中 revert commit
速度立即（< 10 秒）Git push → Argo CD sync（通常 1-3 分鐘）
Git 留痕❌ 沒 commit✅ 完整 audit trail
Argo CD 認知Synced（spec 仍指向新版）OutOfSync → Synced（spec 改回舊版）
下次 sync 行為⚠️ 自動 sync 可能再次觸發 rollout✅ 一切正常
適合緊急止血確定回滾的長期決定

3.2 abort 的 Out-of-sync 陷阱

⚠️

argo rollouts abort 後 Argo CD 不會顯示 OutOfSync

關鍵問題：abort 把流量切回 stable，但 Rollout spec.image 仍指向 v2.0.0（新版）——Git 與 cluster 的 spec 完全一致，Argo CD 視為 Synced。後果：① 啟用 auto-sync + selfHeal 的話，Argo CD 看到 spec 一致就不會做任何事，但 Argo Rollouts 可能會再次嘗試 rollout（被 abort 後 status 是 Degraded）；② 重新觸發 sync（如修改 unrelated 物件）可能讓 Rollouts 再試一次 v2.0.0；③ 沒有 Git audit trail 記錄回滾決定。所以 abort 是 quick stop，正式 rollback 必須跟 git revert。

正確的 production rollback 流程

1
發現問題：metric alert / customer report / AnalysisRun 顯示 Failed
2
立即止血：Argo CD UI 點 Rollout abort（< 10 秒切回 stable）
3
確認流量切回：看 Prometheus / Grafana 確認 error rate 下降
4
Git revert：git revert <commit> push 到 GitOps repo
5
Argo CD 偵測到 spec 變更：自動 sync 或手動觸發
6
Rollout 重新進入 Healthy：spec 與 cluster 一致（都是舊版）
7
事後分析：retrospective / postmortem，準備 fix 後再 deploy

4Istio 整合

Istio 是 Argo Rollouts 最成熟的 traffic routing integration——支援精細的流量分配（不限於 replica ratio）：

4.1 VirtualService + Canary 流量切換

YAML — Istio 整合完整範例
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  strategy:
    canary:
      canaryService: my-app-canary      # 指向 canary ReplicaSet
      stableService: my-app-stable      # 指向 stable ReplicaSet

      trafficRouting:
        istio:
          # 支援多 VirtualService（v1.0+）
          virtualServices:
            - name: my-app-vsvc
              # 多個 route 時必須指定 route name
              routes:
                - http-primary
              # 若有 HTTPS/TLS route：
              # tlsRoutes:
              #   - port: 443
              #     sniHosts:
              #       - my-app.example.com

          # DestinationRule subset（v0.10+，更精細控制）
          destinationRule:
            name: my-app-dr
            canarySubsetName: canary
            stableSubsetName: stable

      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - analysis:
            templates:
              - templateName: success-rate
        - setWeight: 50
        - pause: {duration: 5m}
        - setWeight: 100

---
## VirtualService — Argo Rollouts 會自動更新 weight
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app-vsvc
spec:
  hosts:
    - my-app.example.com
  gateways:
    - my-app-gateway
  http:
    - name: http-primary      # 對應 rollout.trafficRouting.istio.virtualServices.routes
      route:
        - destination:
            host: my-app-stable    # 指向 stableService
          weight: 100                 # 初始 100，Rollouts 動態更新
        - destination:
            host: my-app-canary    # 指向 canaryService
          weight: 0                   # 初始 0，Rollouts 動態更新

4.2 DestinationRule + Subset（進階）

DestinationRule subset 提供更精細的流量控制（如 retry policy、circuit breaker、mTLS 設定可以各 subset 不同）：

YAML — DestinationRule + subset
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: my-app-dr
spec:
  host: my-app      # 共同的 base service（非 canary/stable）
  subsets:
    # Argo Rollouts 動態更新 labels 切換 subset
    - name: stable
      labels:
        app: my-app
        # Rollouts 自動加 rollouts-pod-template-hash label
    - name: canary
      labels:
        app: my-app

  # Subset 共用的 traffic policy
  trafficPolicy:
    connectionPool:
      http:
        http1MaxPendingRequests: 10
        http2MaxRequests: 100
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s

4.3 Istio 物件的 Health Checks（Ch.32 補完）

Argo CD 預設不知道 Istio CRD 是否「健康」——預設「存在 = Healthy」（Ch.32 講過）。實務上應該補上 Istio 5 大物件的 health checks：

YAML — argocd-cm 補完 Istio 物件 health checks
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # VirtualService — 多數情境直接視為 Healthy（無 status conditions）
  resource.customizations.health.networking.istio.io_VirtualService: |
    hs = {}
    hs.status = "Healthy"
    hs.message = "VirtualService is configured"
    return hs

  # DestinationRule
  resource.customizations.health.networking.istio.io_DestinationRule: |
    hs = {}
    hs.status = "Healthy"
    hs.message = "DestinationRule is configured"
    return hs

  # Gateway
  resource.customizations.health.networking.istio.io_Gateway: |
    hs = {}
    hs.status = "Healthy"
    hs.message = "Gateway is configured"
    return hs

  # AuthorizationPolicy
  resource.customizations.health.security.istio.io_AuthorizationPolicy: |
    hs = {}
    hs.status = "Healthy"
    hs.message = "AuthorizationPolicy is configured"
    return hs

  # PeerAuthentication
  resource.customizations.health.security.istio.io_PeerAuthentication: |
    hs = {}
    hs.status = "Healthy"
    hs.message = "PeerAuthentication is configured"
    return hs
⚠️

避免 ignoreDifferences 把 VirtualService 整個 spec.http 忽略

常見錯誤：因為 Argo Rollouts 動態更新 VirtualService 的 weight，新手會在 Argo CD 加 ignoreDifferences 忽略整個 spec.http——這會造成 Argo CD 完全看不到 VirtualService 的變更。正確做法：只忽略 weight 欄位：

jsonPointers: ["/spec/http/0/route/0/weight", "/spec/http/0/route/1/weight"]

5Gateway API 整合（v1.4+）

Gateway API 是 K8s 官方逐步取代 Ingress 的新標準（v1.0 GA 2023-10）。Argo Rollouts v1.4+ 透過 traffic router plugin 支援：

5.1 HTTPRoute Backend 配 Canary

YAML — Gateway API HTTPRoute 範例
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app-route
spec:
  parentRefs:
    - name: my-gateway
      namespace: istio-system
  hostnames:
    - my-app.example.com
  rules:
    - matches:
        - path: {type: PathPrefix, value: /}
      # Argo Rollouts 動態更新兩個 backend weight
      backendRefs:
        - name: my-app-stable
          port: 80
          weight: 100          # 初始值，Rollouts 動態更新
        - name: my-app-canary
          port: 80
          weight: 0            # 初始值

5.2 trafficRouting plugin 設定

YAML — Rollout 配 Gateway API plugin
## Step 1: 在 Argo Rollouts controller 啟用 Gateway API plugin
apiVersion: v1
kind: ConfigMap
metadata:
  name: argo-rollouts-config
  namespace: argo-rollouts
data:
  trafficRouterPlugins: |
    - name: "argoproj-labs/gatewayAPI"
      location: "https://github.com/argoproj-labs/rollouts-plugin-trafficrouter-gatewayapi/releases/download/v0.6.0/gateway-api-plugin-linux-amd64"

---
## Step 2: 套用後 restart controller 載入 plugin
## $ kubectl rollout restart deploy/argo-rollouts -n argo-rollouts

---
## Step 3: 在 Rollout 使用 plugin
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  strategy:
    canary:
      canaryService: my-app-canary
      stableService: my-app-stable

      trafficRouting:
        plugins:
          argoproj-labs/gatewayAPI:
            httpRoute: my-app-route
            namespace: my-app

      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - setWeight: 50
        - pause: {duration: 5m}
        - setWeight: 100
💡

Gateway API 取代 Istio VirtualService 的方向

Istio 從 v1.20 開始原生支援 Gateway API（不只是 plugin），未來方向是用 Gateway API 取代 VirtualService 作為 ingress 標準。優勢：① cross-vendor 標準（Istio、Linkerd、Cilium、NGINX 全支援）；② 更明確的 role separation（GatewayClass / Gateway / HTTPRoute）。新專案直接用 Gateway API + Argo Rollouts plugin，舊專案漸進遷移。

6NGINX / SMI / ALB / AppMesh 整合

YAML — 多種 traffic router 範例
## ── NGINX Ingress (most common with non-mesh) ─────
trafficRouting:
  nginx:
    stableIngress: my-app-ingress
    # Argo Rollouts 自動建立 my-app-ingress-canary Ingress（含 canary annotation）
    # NGINX 看兩個 Ingress + weight 路由

    # 可選：自訂 annotation prefix
    annotationPrefix: nginx.ingress.kubernetes.io

    # 可選：額外的 canary annotations
    additionalIngressAnnotations:
      canary-by-header: X-Canary
      canary-by-header-value: always
      # 含 X-Canary: always header 的 request 強制走 canary

## ── SMI (Service Mesh Interface) ──────────────────
trafficRouting:
  smi:
    rootService: my-app
    trafficSplitName: my-app-split
    # 用 TrafficSplit CRD（Linkerd / Open Service Mesh 支援）

## ── AWS ALB (Application Load Balancer) ────────────
trafficRouting:
  alb:
    ingress: my-app-ingress
    servicePort: 80
    # 用 AWS ALB target groups + weighted target group action

## ── AWS AppMesh ────────────────────────────────────
trafficRouting:
  appMesh:
    virtualService:
      name: my-app-virtual-service
    virtualNodeGroup:
      canaryVirtualNodeRef:
        name: my-app-canary
      stableVirtualNodeRef:
        name: my-app-stable

## ── Traefik ────────────────────────────────────────
trafficRouting:
  traefik:
    weightedTraefikServiceName: my-app-traefik
💡

Traffic router 選擇建議

① 已用 Istio → 用 Istio integration（最成熟）；② 新專案 + Istio → 直接用 Gateway API plugin；③ 無 service mesh + AWS → ALB（與 IRSA / Workload Identity 整合好）；④ 無 service mesh + 簡單需求 → NGINX Ingress（最普及）；⑤ 多家 vendor 共存 → SMI（標準介面但 vendor 支援不一）。

7argocd-notifications + Rollouts 事件整合

Argo CD 把 Rollout 物件視為一般 K8s 資源——Rollout 的 status 變化可以觸發 argocd-notifications（Ch.29）：

YAML — Rollouts events 整合 Notifications
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-notifications-cm
  namespace: argocd
data:
  # ── Trigger：Rollout aborted ─────────────────────
  trigger.on-rollout-aborted: |
    - description: Rollout aborted (canary failed)
      send: [slack-rollout-aborted]
      when: |
        app.status.health.status == 'Degraded' &&
        app.status.resources.any(r =>
          r.kind == 'Rollout' &&
          r.health.message contains 'aborted'
        )

  # ── Trigger：Rollout paused (manual promotion needed) ──
  trigger.on-rollout-paused: |
    - description: Rollout paused, manual promotion needed
      send: [slack-rollout-pause]
      oncePer: app.status.sync.revision
      when: |
        app.status.health.status == 'Suspended' &&
        app.status.resources.any(r =>
          r.kind == 'Rollout' &&
          r.health.status == 'Suspended'
        )

  # ── Template：含 promote / abort 連結 ─────────────
  template.slack-rollout-pause: |
    message: |
      ⏸ *Rollout paused — manual promotion needed*
      App: {{.app.metadata.name}}
      Revision: {{.app.status.sync.revision | slice 7}}
      Action:
        • Promote: kubectl argo rollouts promote {{.app.metadata.name}} -n {{.app.spec.destination.namespace}}
        • Abort: kubectl argo rollouts abort {{.app.metadata.name}} -n {{.app.spec.destination.namespace}}
        • UI: https://argocd.example.com/applications/{{.app.metadata.name}}
    slack:
      attachments: |
        [{
          "title": "{{.app.metadata.name}} paused",
          "color": "#FFA500",
          "fields": [
            {"title": "Step", "value": "{{(index .app.status.resources 0).health.message}}"},
            {"title": "Revision", "value": "{{.app.status.sync.revision | slice 7}}"}
          ]

ℹ️

Argo Rollouts 也有自己的 notifications

除了 argocd-notifications，Argo Rollouts 本身有 notification controller（v1.0+），可以針對 Rollout 事件直接通知（不經過 Argo CD）：① on-rollout-completed；② on-rollout-step-completed；③ on-rollout-paused；④ on-analysis-run-error。實務：① Argo CD Notifications 通知「sync / 整體 health」；② Argo Rollouts Notifications 通知「step / analysis 細節」——兩者互補。

8完整 Production Stack 範例

整合 Argo CD + Argo Rollouts + Istio + Prometheus + AnalysisTemplate + argocd-notifications 的完整 production deployment：

YAML — Production-grade complete stack
# Git repo: gitops/apps/my-app/
## ── 1) Application (Argo CD) ──────────────────────
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app-prod
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/myorg/gitops.git
    path: apps/my-app/overlays/production
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: my-app-prod
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    # 重要：ignoreDifferences 排除 Rollouts 動態管理的欄位
  ignoreDifferences:
    - group: networking.istio.io
      kind: VirtualService
      jsonPointers:
        - /spec/http/0/route/0/weight
        - /spec/http/0/route/1/weight

---
## ── 2) Rollout（Argo Rollouts）────────────────────
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
  namespace: my-app-prod
spec:
  replicas: 10
  selector: {matchLabels: {app: my-app}}
  template:
    metadata:
      labels: {app: my-app}
    spec:
      containers:
        - name: my-app
          image: myorg/my-app:v2.0.0
          readinessProbe:
            httpGet: {path: /health, port: 8080}
          resources:
            requests: {cpu: "200m", memory: "256Mi"}
            limits: {cpu: "1000m", memory: "512Mi"}

  strategy:
    canary:
      canaryService: my-app-canary
      stableService: my-app-stable
      trafficRouting:
        istio:
          virtualServices:
            - name: my-app-vsvc
              routes: [http-primary]

      # Background analysis：rollout 全程 safety net
      analysis:
        templates:
          - templateName: slo-burn-rate
        args:
          - name: service-name
            value: my-app-canary.my-app-prod.svc
        startingStep: 2

      steps:
        # 10% 流量觀察 5 分鐘
        - setWeight: 10
        - pause: {duration: 5m}

        # 跑 inline analysis：success rate + latency
        - analysis:
            templates:
              - templateName: success-rate-slo
              - templateName: latency-slo
            args:
              - name: service-name
                value: my-app-canary.my-app-prod.svc

        # 50% 流量觀察 5 分鐘
        - setWeight: 50
        - pause: {duration: 5m}

        # 再跑 analysis
        - analysis:
            templates:
              - templateName: success-rate-slo
            args:
              - name: service-name
                value: my-app-canary.my-app-prod.svc

        # 100% 流量（手動 promote）
        - pause: {}
        - setWeight: 100

---
## ── 3) Service x2 (stable / canary) ────────────────
apiVersion: v1
kind: Service
metadata:
  name: my-app-stable
spec:
  selector: {app: my-app}
  ports:
    - port: 80

---
apiVersion: v1
kind: Service
metadata:
  name: my-app-canary
spec:
  selector: {app: my-app}
  ports:
    - port: 80

---
## ── 4) Istio VirtualService ────────────────────────
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app-vsvc
spec:
  hosts:
    - my-app.example.com
  gateways:
    - istio-system/default-gateway
  http:
    - name: http-primary
      route:
        - destination: {host: my-app-stable}
          weight: 100
        - destination: {host: my-app-canary}
          weight: 0

---
## ── 5) AnalysisTemplate (success rate SLO) ─────────
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate-slo
spec:
  args:
    - name: service-name
  metrics:
    - name: success-rate
      initialDelay: 60s
      interval: 1m
      count: 5
      successCondition: "len(result) == 0 || result[0] >= 0.995"
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(istio_requests_total{
              destination_service=~"{{args.service-name}}",
              response_code!~"5.."
            }[5m]))
            /
            sum(rate(istio_requests_total{
              destination_service=~"{{args.service-name}}"
            }[5m]))

Issue #22772：Istio Gateway + AWS ALB HTTP/2 認證失敗（v2.14.9）

當 Argo CD 暴露在 Istio Gateway → AWS ALB（HTTP/2 listener） 的環境，argocd login CLI 失敗（HTTP 404 / 307）。workaround：① ALB listener 改用 HTTP/1.1（移除 alb.ingress.kubernetes.io/backend-protocol-version: HTTP2）；② 用 Ingress 直接連 ALB（不經 Istio）；③ 在 cluster 內部直接連 argocd-server service（不經 Gateway）。UI 正常運作不受影響，只有 gRPC CLI 受影響。

問題症狀解法
abort 後 Argo CD 顯示 Synced spec 一致但 cluster 是舊版 必跟 git revert 才完整 rollback
VirtualService 一直 OutOfSync Rollouts 改 weight，Argo CD 偵測差異 用 ignoreDifferences 排除 weight jsonPointers
Rollout selector 與舊 Deployment 衝突 遷移時兩者管同一個 ReplicaSet 遷移前先刪除舊 Deployment
auto-sync 重複觸發 Rollout Rollouts 更新 weight 後 Argo CD selfHeal 改回去 必設 ignoreDifferences
Istio 物件顯示 Unknown Argo CD 沒內建 Istio health check 補上 5 個 Istio 物件的 health check
Gateway API plugin 載入失敗 controller 沒重啟 修改 trafficRouterPlugins ConfigMap 後 rollout restart controller

Production 最佳實踐

✅

Argo CD + Rollouts 整合 12 項 Checklist

① 用 v2.0+ 內建 Rollout health check（不需自訂 Lua）；② 必設 VirtualService weight 的 ignoreDifferences避免 Argo CD selfHeal 與 Rollouts 衝突；③ 補上 Istio 5 大物件的 health check（VS/DR/GW/AuthPol/PeerAuth）；④ UI Actions 細粒度 RBAC（dev: restart only；SRE: all）；⑤ 緊急 rollback 流程：abort 立即止血 + git revert 永久回滾；⑥ auto-sync 啟用 selfHeal: true 但搭配 ignoreDifferences；⑦ Background analysis 永遠跑（safety net），加 inline analysis 做 milestone gate；⑧ argocd-notifications 訂閱 on-rollout-paused提醒手動 promote；⑨ 遷移舊 Deployment 必先刪避免 selector 衝突；⑩ service mesh 選擇：新專案優先 Gateway API plugin；⑪ 定期 chaos test：故意 abort 確認流量切回 stable 流程通；⑫ monitor Rollout metrics：Prometheus 抓 Argo Rollouts 的 /metrics endpoint（port 8090）。

✓本章重點回顧

📌 Key Takeaways

  • 🤝Argo CD 與 Argo Rollouts 完美互補但獨立：① Argo CD = Git → cluster spec 同步；② Argo Rollouts = ReplicaSet + 流量切換實際操作。兩者透過 K8s API（CRD spec）解耦，v2.0+ Argo CD 內建 Rollout health check，UI 自動顯示 step / setWeight / stable/canary 進度。
  • ⚖️Rollout phase 對應 Argo CD health 5 種狀態：Healthy → Healthy（綠）；Progressing → Progressing（藍）；Paused → Suspended（橘，非 Degraded，避免半夜誤觸發 alert）；Degraded → Degraded（紅）；Aborted → Degraded（紅）。Suspended 仍會卡 sync wave 推進。
  • 🎮UI Actions：promote / abort / restart / retry / resume / promote-full。從 Argo CD UI 直接操作 Rollout，不需切換到 kubectl 或 Argo Rollouts Dashboard。細粒度 RBAC：action/argoproj.io/Rollout/restart（dev role）；action/argoproj.io/Rollout/abort（SRE / on-call role）。
  • ↩️回滾兩種路徑必須並用：① argo rollouts abort（imperative）：立即止血（< 10s），但 Argo CD 不會顯示 OutOfSync（spec 與 cluster 一致），auto-sync 可能再次觸發 rollout；② git revert（declarative）：完整 audit trail。標準流程：abort 立即止血 → git revert 永久回滾。
  • 🕸️Istio 整合 4 個關鍵設定：① trafficRouting.istio.virtualServices（支援多 VS）；② routes（多 route 時必填）；③ destinationRule.canarySubsetName / stableSubsetName（DR subset 進階控制）；④ ignoreDifferences 排除 VS weight 欄位避免 selfHeal 衝突。Istio 5 大物件 health check 必補（VS/DR/GW/AuthPol/PeerAuth）。
  • 🚪Gateway API 是未來方向（v1.4+ Argo Rollouts 支援）：透過 argoproj-labs/gatewayAPI plugin，HTTPRoute backend 配 stable/canary service。K8s 官方標準（vs Istio VirtualService 是 Istio-specific），跨 vendor 通用。新專案直接用 Gateway API，舊專案漸進遷移。
  • 🚦5 種 traffic router 各有適用：① Istio（最成熟，已有 mesh）；② Gateway API（新標準，未來方向）；③ NGINX Ingress（無 mesh 最普及，支援 header-based canary）；④ AWS ALB（target groups）；⑤ SMI（vendor 中立但支援不全）。traffic-based canary 必選一種。
  • 📢argocd-notifications + Rollouts 雙層通知：① Argo CD Notifications：on-rollout-aborted、on-rollout-paused 等 trigger 看 app.status.resources；② Argo Rollouts Notifications：直接 on-step-completed、on-analysis-run-error 等細節事件。實務：Argo CD 通知整體 health；Rollouts 通知 step 細節。
  • 🏭Production stack 完整組合：Application（Argo CD）+ Rollout（Argo Rollouts）+ 2 個 Service（stable/canary）+ VirtualService（Istio）+ AnalysisTemplate（SLO-driven）+ Notifications。ignoreDifferences 排除 VirtualService weight 是 critical 設定，否則 Argo CD selfHeal 會與 Argo Rollouts 動態調整衝突。
  • ⚠️已知問題：① Issue #22772（Istio Gateway + ALB HTTP/2 造成 argocd CLI 失敗，UI 正常）；② abort 後 Argo CD 不顯示 OutOfSync（必跟 git revert）；③ VirtualService 一直 OutOfSync（必設 ignoreDifferences）；④ Rollout selector 與舊 Deployment 衝突（遷移前必刪舊物件）；⑤ Istio 物件預設 Unknown（補 health check）。12 項 Checklist 解決絕大多數整合問題。
