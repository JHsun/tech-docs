Manifest 來源工具：
Helm、Kustomize、OCI、Jsonnet、Directory

Argo CD 不在乎 manifest 是如何產生的，它支援業界主流的所有生成方式。本章深入每一種工具的 Application spec 寫法、進階參數設定，以及 v3.1 起的 OCI 原生 Source 與 Multiple Sources 多倉庫組合模式。

📋

前置：已完成 Vol 1（Ch.01–Ch.04），理解 Application CRD 的基本結構，並對 Helm / Kustomize 有基本認識。

🎯 學習目標

  • 理解 Tool Detection 的五步驟優先順序，以及如何強制指定工具類型
  • 掌握 Helm 三種來源（Git / chart repo / OCI）的完整 spec 寫法與差異
  • 熟悉 Helm values 五層優先順序（parameters > valuesObject > values > valueFiles > 預設值）
  • 能使用 Kustomize overlay 模式管理多環境部署，並配合 inline patches
  • 了解 OCI 原生 Source（oci:// scheme）的 v3.1 特性與與 Helm OCI 的差異
  • 掌握 Multiple Sources（spec.sources）的 ref 參考機制，實現 chart 與 values 分倉管理
  • 能根據團隊現況選擇最合適的 manifest 工具，理解各工具的優缺點

1Tool Detection：自動識別機制

建立 Application 時，如果 spec 中沒有明確指定工具設定（如 helm: 或 kustomize:），Argo CD 的 repo-server 會掃描 source path 內的檔案，依照固定的優先順序自動判斷應使用哪種工具。

1.1 偵測優先順序（硬編碼，不可更改）

🔍 Tool Detection 決策流程（Helm > Kustomize > Jsonnet > CMP > Directory）
P1 Chart.yaml Helm 最高優先。即使是空的 Chart.yaml 也會觸發 Helm 模式。大小寫敏感（chart.yaml 不觸發）
P2 kustomization.yaml / kustomization.yml / Kustomization Kustomize 三個檔名均有效；Kustomization（無副檔名）也算
P3 *.jsonnet / *.libsonnet Jsonnet 在 source path 根目錄（非遞迴）找到任一 .jsonnet 或 .libsonnet 檔案即觸發
P4 CMP Plugin discovery rules Plugin 各 sidecar CMP plugin 的 discover 規則決定；sidecar 順序即優先順序
P5 （無符合） Directory fallback：將目錄內所有 .yaml / .yml / .json 檔案作為純 YAML manifest 套用
⚠️

最常見的 Tool Detection 陷阱

從 Helm 遷移至 Kustomize 後忘記刪除 Chart.yaml，導致 Argo CD 仍以 Helm 處理，出現 Chart.yaml file is missing 等令人困惑的錯誤。遇到工具判定異常，先執行：argocd app get MY_APP -o json | jq '.status.sourceType' 確認 Argo CD 實際判定的工具類型。

1.2 強制指定工具（繞過 Auto-Detection）

在 Application spec 中明確加入工具設定區塊，即可強制使用該工具，無論目錄中有無其他 marker file：

YAML — 強制指定工具（四種方式）
# 方式一：強制 Helm（即使目錄中有 kustomization.yaml）
source:
  path: apps/my-app
  helm:
    releaseName: my-app

# 方式二：強制 Kustomize（即使目錄中有 Chart.yaml）
source:
  path: apps/my-app
  kustomize:
    namePrefix: prod-

# 方式三：強制 Directory（即使有 Chart.yaml 或 kustomization.yaml）
source:
  path: apps/my-app
  directory:
    recurse: false

# 方式四：強制 CMP Plugin
source:
  path: apps/my-app
  plugin:
    name: my-cmp-plugin

1.3 停用特定工具（安全強化）

若組織不使用某些工具（如 Jsonnet），可在 argocd-cm 中停用，降低潛在攻擊面：

YAML — argocd-cm 停用不使用的工具
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 停用 Jsonnet（若組織不使用）
  jsonnet.enable: "false"
  # 停用 Helm（不常見，但可行）
  # helm.enable: "false"
  # 停用 Kustomize
  # kustomize.enable: "false"

2Helm

⎈
Helm
Kubernetes 的套件管理器。Argo CD 以 helm template（非 helm install）執行，生成 manifest 後直接以 kubectl apply 套用，不維護 Helm release state。
觸發檔：Chart.yaml 三種來源：Git / Helm repo / OCI
ℹ️

Argo CD 使用 helm template，不使用 helm install

這意味著：helm list 不會顯示 Argo CD 管理的 release；helm rollback 無法使用（回滾應透過 Argo CD 的 Rollback 或 git revert）；Helm hooks（helm.sh/hook annotation）不被 Argo CD 執行，應改用 Argo CD 原生的 Resource hooks。

2.1 來源一：Git repo 中的 Helm chart

chart 存在自己或外部 Git repo 中，使用 path 指定 chart 根目錄（含 Chart.yaml 的目錄）：

YAML — Helm from Git（完整欄位說明）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-helm-app
  namespace: argocd
spec:
  source:
    repoURL: https://github.com/myorg/helm-charts.git
    targetRevision: main
    path: charts/my-app  # 含 Chart.yaml 的目錄
    helm:
      # Release 名稱（預設為 Application 名稱）
      releaseName: my-app-prod
      # Values 檔案（相對於 chart 根目錄，後者優先）
      valueFiles:
        - values.yaml           # 基礎值
        - values-production.yaml # 環境特定值（後者覆蓋前者）
      # Inline values（格式同 values.yaml，比 valueFiles 優先）
      values: |
        replicaCount: 3
        resources:
          limits:
            cpu: 500m
            memory: 512Mi
      # valuesObject（結構化 values，等同 values 但更易閱讀，v2.6+）
      valuesObject:
        ingress:
          enabled: true
          host: myapp.example.com
      # 個別參數 override（最高優先）
      parameters:
        - name: image.tag
          value: v3.2.1
        - name: replicaCount
          value: "5"  # 注意：parameters 的 value 是字串類型
      # 指定 Helm 版本（預設自動偵測 Chart.yaml 中的 apiVersion）
      version: v3
      # 跳過 CRD 安裝（當另有 App 管理 CRD 時）
      skipCrds: false
      # 傳遞 Helm 認證至子 chart 的 repo（跨 domain 拉取）
      passCredentials: false
  destination:
    server: https://kubernetes.default.svc
    namespace: production

2.2 來源二：Helm chart repository

chart 存放在標準 Helm HTTP(S) chart repo（如 ArtifactHub 上的 chart），使用 chart 欄位取代 path：

YAML — Helm from chart repo（Sealed Secrets 範例）
spec:
  source:
    # chart repo URL（不是 Git URL）
    repoURL: https://bitnami-labs.github.io/sealed-secrets
    # 使用 chart 欄位（非 path）
    chart: sealed-secrets
    # targetRevision = chart 版本號
    targetRevision: 2.15.0
    helm:
      releaseName: sealed-secrets
      valuesObject:
        serviceAccount:
          create: true
          name: sealed-secrets-controller
  destination:
    server: https://kubernetes.default.svc
    namespace: kube-system
💡

私有 Helm repo 認證

在 Argo CD Settings → Repositories 中加入私有 repo，或以 argocd CLI：argocd repo add https://private-charts.example.com --type helm --name private --username user --password pass。宣告式方式見 Vol 3 Ch.17（Repository Secret）。

2.3 來源三：OCI Registry（Helm chart 儲存於 OCI）

Helm 3 起可將 chart 以 OCI artifact 形式儲存於 container registry（Docker Hub、GHCR、ECR、GAR 等）。Argo CD 支援兩種 OCI Helm 的 URL 格式：

YAML — Helm from OCI（兩種 URL 格式）
## 格式一：直接指定 chart 路徑（不含 oci:// 前綴）
## 適合：已在 Settings → Repositories 設定了 OCI repo 認證
source:
  repoURL: registry-1.docker.io/bitnamicharts  # 不含 oci://
  chart: nginx
  targetRevision: 18.1.7
  helm:
    valuesObject:
      replicaCount: 2

## 格式二：oci:// 前綴（用於非 Helm OCI artifact，如純 YAML 打包成 OCI）
## 適合：儲存 Kubernetes YAML manifest 的 OCI image（非 Helm chart）
source:
  repoURL: oci://ghcr.io/myorg/charts/myapp  # 含 oci://
  targetRevision: 1.2.3
  path: .

## 加入私有 OCI Helm repo（CLI）
# argocd repo add registry-1.docker.io/bitnamicharts \
#   --type helm --name bitnami-oci \
#   --username myuser --password mypass \
#   --enable-oci
格式用途repoURL 範例chart 欄位
不含 oci://OCI Helm chart repo（類似 Helm HTTP repo 但在 OCI）registry-1.docker.io/bitnamicharts必填（chart 名稱）
含 oci://OCI artifact source（非 Helm chart，純 YAML / Helm chart 均可）oci://ghcr.io/myorg/charts/myapp不填（用 path 指定）

2.4 Helm values 五層優先順序

當多種 values 設定同時存在時，優先順序從高到低為：

P1 spec.source.helm.parameters 最高優先。每個 name=value 鍵值對，等同 helm 的 --set 旗標
P2 spec.source.helm.valuesObject 結構化 YAML object，等同 --set-json，比 values 字串更易閱讀（v2.6+）
P3 spec.source.helm.values（inline） 多行字串格式的 YAML values，等同 --values -（stdin）
P4 spec.source.helm.valueFiles 陣列中後者優先（等同 helm --values 旗標的順序）
P5 chart 內的 values.yaml 最低優先。chart 預設值，所有 override 都基於此
ℹ️

實踐建議

不建議在 parameters 中存放環境特定值（這會讓值分散在 YAML spec 與 values 檔中）。建議以 valueFiles 的多層次 values 檔案（base → env-specific → cluster-specific）管理所有值，並利用 Multiple Sources 將 chart 與 values 分開儲存。

2.5 valueFiles Glob 與 Build Environment 變數

Argo CD 支援在 valueFiles 中使用 glob pattern，讓多個 values 檔案自動被匹配，以及使用 Build Environment 變數：

YAML — valueFiles glob 與 Build Environment 變數
helm:
  valueFiles:
    # Glob：匹配 envs/ 目錄下所有 .yaml，依字母順序展開
    - 'envs/*.yaml'

    # Build Environment 變數（Argo CD 自動注入）
    # ARGOCD_APP_NAME, ARGOCD_APP_NAMESPACE, ARGOCD_ENV_* 等
    - envs/$ARGOCD_APP_NAME/values.yaml

    # 跨 source 的 values 檔案（Multiple Sources 的 $ref 用法）
    - $values/environments/production/values.yaml

## 常用 Build Environment 變數
# ARGOCD_APP_NAME      = Application 名稱
# ARGOCD_APP_NAMESPACE = Application 所在 namespace
# ARGOCD_ENV_*         = 來自 Parameters 的自定義環境變數

2.6 Helm 使用注意事項

注意點說明
helm install 不執行Argo CD 只執行 helm template，Helm hooks（helm.sh/hook annotation）不生效，改用 Argo CD resource hooks（argocd.argoproj.io/hook）
helm list 看不到Argo CD 不維護 Helm release state，helm list、helm rollback、helm history 均無效
CRD 安裝注意Helm 會安裝 crds/ 目錄的 CRD（如果 CRD 尚未存在）。若要跳過，設定 skipCrds: true，另以獨立 App 管理 CRD
parameters 類型parameters.value 永遠是字串類型。傳遞數字須注意 YAML 解析，也可使用 valuesObject 避免類型問題
cross-domain 認證Helm v3.6.1+ 不自動傳遞 credentials 至不同 domain 的 chart。若子 chart 在不同 domain，設定 passCredentials: true
v3.0 Helm 並行生成v3.0 起，相同 repo 的多個 Helm Application 預設並行生成 manifest（舊版為串行）。改善效能，但可能增加短暫 CPU 峰值

3Kustomize

🔧
Kustomize
「無模板的模板化」。以 base + overlay 結構管理多環境配置，不 fork 原始 YAML，透過 patch 機制客製化。Argo CD 執行 kustomize build 生成最終 manifest。
觸發檔：kustomization.yaml / .yml / Kustomization 多版本並存支援

3.1 基本用法：base + overlay

Kustomize 的核心概念是 base（共用配置）+ overlay（環境特定 patch）。Argo CD 的 path 指向 overlay 目錄即可：

YAML — Kustomize Application spec
source:
  repoURL: https://github.com/myorg/k8s-manifests.git
  targetRevision: HEAD
  # 指向 overlay 目錄（包含 kustomization.yaml）
  path: overlays/production
  kustomize:
    # 指定 Kustomize 版本（需在 argocd-cm 中預先設定路徑）
    version: v5.2.1
    # 為所有資源加上名稱前綴
    namePrefix: prod-
    # 為所有資源加上名稱後綴
    nameSuffix: -v2
    # 設定 namespace（覆蓋 kustomization.yaml 中的設定）
    namespace: production
    # 為所有資源加上 common labels
    commonLabels:
      app.kubernetes.io/managed-by: argocd
      environment: production
    # 為所有資源加上 common annotations
    commonAnnotations:
      team: platform
    # 覆寫特定 image 版本（無需修改 kustomization.yaml）
    images:
      - name: myapp
        newTag: v3.2.1
      - name: nginx
        newName: custom-nginx
        newTag: 1.25-alpine

典型 Kustomize 目錄結構

Tree — 典型 base + overlay 結構
k8s-manifests/
├── base/
│   ├── kustomization.yaml    # resources: [deployment.yaml, service.yaml]
│   ├── deployment.yaml
│   └── service.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml  # resources: [../../base], patches: [...]
    │   └── patch-replicas.yaml # replicas: 1
    ├── staging/
    │   └── kustomization.yaml  # resources: [../../base], patches: [...]
    └── production/             # ← Argo CD path 指向這裡
        ├── kustomization.yaml  # resources: [../../base], patches: [...]
        └── patch-replicas.yaml # replicas: 3

多版本 Kustomize 並存設定

若不同 Application 需要不同版本的 Kustomize，可在 argocd-cm 中登記多個版本：

YAML — argocd-cm 多版本 Kustomize
data:
  # 全域 build options
  kustomize.buildOptions: --load-restrictor LoadRestrictionsNone
  # 登記額外版本路徑（需先將二進位安裝至 repo-server container）
  kustomize.path.v4.5.7: /custom-tools/kustomize-4.5.7
  kustomize.path.v5.2.1: /custom-tools/kustomize-5.2.1

3.2 spec.source.kustomize.patches（Inline Patches）

從 Argo CD v2.10 起，可以在 Application spec 中直接定義 Kustomize patch，無需修改 Git repo 中的 kustomization.yaml，特別適合 ApplicationSet 中為不同叢集套用不同 patch：

YAML — Inline Kustomize Patches（在 spec 中定義）
source:
  repoURL: https://github.com/argoproj/argocd-example-apps.git
  targetRevision: HEAD
  path: kustomize-guestbook
  kustomize:
    patches:
      # JSON Patch：修改 Deployment 的容器 port
      - target:
          kind: Deployment
          name: guestbook-ui
        patch: |
          - op: replace
            path: /spec/template/spec/containers/0/ports/0/containerPort
            value: 8443
      # Strategic Merge Patch：修改 replicas
      - target:
          kind: Deployment
          name: guestbook-ui
        patch: |
          apiVersion: apps/v1
          kind: Deployment
          metadata:
            name: guestbook-ui
          spec:
            replicas: 3

3.3 kustomized-helm 模式

在 Kustomize 的 kustomization.yaml 中透過 helmCharts 欄位引用 Helm chart，讓 Kustomize 先執行 helm template 再套用 Kustomize patch。這在需要同時享受 Helm 的打包能力與 Kustomize 的 patch 能力時非常有用：

YAML — kustomization.yaml（helmCharts 模式）
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
helmCharts:
  - name: cert-manager
    repo: https://charts.jetstack.io
    version: v1.14.0
    releaseName: cert-manager
    namespace: cert-manager
    valuesFile: cert-manager-values.yaml
    includeCRDs: true
patches:
  # 在 Helm output 上再套用 patch
  - target:
      kind: Deployment
      name: cert-manager
    patch: |
      - op: add
        path: /spec/template/spec/containers/0/args/-
        value: --dns01-recursive-nameservers=8.8.8.8:53
⚠️

kustomized-helm 需要 --enable-helm 旗標

在 argocd-cm 中加入：kustomize.buildOptions: --enable-helm。沒有此設定，Kustomize 會忽略 helmCharts 區塊。同時，Argo CD 必須能存取指定的 Helm repo（需在 Settings → Repositories 中登記）。

4OCI 原生 Source（v3.1）

📦
OCI Source
v3.1 新增：直接以 oci:// scheme 指定 OCI registry 中的 artifact 作為 manifest 來源。支援儲存純 YAML manifest 或 Helm chart 的 OCI artifact，統一使用 OCI registry 管理所有 artifact。
v3.1 原生支援 觸發：repoURL 含 oci://

OCI Source 讓 manifest 的發佈流程與 container image 對齊：CI pipeline 建置完 image 後，可同時 push 一份 manifest OCI artifact，讓 Argo CD 直接從 registry 拉取，不需要提交到 Git repo。

YAML — OCI Source 完整範例
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-oci-app
  namespace: argocd
spec:
  source:
    # oci:// 前綴：指定 OCI image（含 manifest YAML）
    repoURL: oci://ghcr.io/myorg/manifests/my-app
    # targetRevision = OCI image tag 或 digest
    targetRevision: v1.2.3
    # 或使用 digest（更精確，推薦生產環境）
    # targetRevision: sha256:abc123...
    # path 指定 OCI artifact 解壓後的子目錄
    path: .
    # 若 OCI artifact 內含 Helm chart，可加入 helm: 設定
    # helm:
    #   valuesObject: ...

## 加入私有 OCI registry 認證
## argocd repo add oci://ghcr.io/myorg/manifests \
##   --type oci \
##   --username myuser \
##   --password $GITHUB_TOKEN

## CI pipeline：打包並 push manifest 為 OCI artifact
## helm package ./charts/my-app
## helm push my-app-1.2.3.tgz oci://ghcr.io/myorg/manifests

5Jsonnet

🔢
Jsonnet
函數式資料模板語言，可生成 JSON（Kubernetes YAML 的超集）。適合需要複雜邏輯、迴圈、函式封裝的 manifest 生成場景。Argo CD 執行 jsonnet 工具生成 manifest。
觸發檔：*.jsonnet / *.libsonnet 適合複雜生成邏輯
YAML — Jsonnet Application spec
source:
  repoURL: https://github.com/myorg/jsonnet-configs.git
  targetRevision: HEAD
  path: apps/my-app
  directory:
    jsonnet:
      # Jsonnet 外部變數（--ext-str）
      extVars:
        - name: env
          value: production
        - name: replicas
          value: "3"
      # Jsonnet TLA（Top Level Arguments，--tla-str）
      tlas:
        - name: namespace
          value: production
      # 額外的 jsonnet 函式庫搜尋路徑（-J）
      libs:
        - vendor
        - lib
💡

Jsonnet 適用場景

Jsonnet 適合有豐富 Jsonnet 經驗的團隊（如 Google 內部工具文化），特別是需要複雜函式封裝、迴圈生成大量相似資源的情境。對大多數團隊而言，Helm 或 Kustomize 更常見，且有更豐富的社群資源。

6Directory（純 YAML）

📂
Directory
最簡單的 manifest 來源。Argo CD 直接讀取目錄中的所有 .yaml / .yml / .json 檔案，不執行任何模板化工具。適合靜態 manifest 或自定義工具生成的 manifest。
fallback：無觸發檔時 最簡單，無生成邏輯
YAML — Directory spec 完整選項
source:
  repoURL: https://github.com/myorg/k8s-manifests.git
  targetRevision: HEAD
  path: apps/static-configs
  directory:
    # 遞迴讀取子目錄（預設 false）
    recurse: true
    # 包含符合 glob 的檔案
    include: '*.yaml'
    # 排除符合 glob 的檔案（優先於 include）
    exclude: '**/test*.yaml'
    # Jsonnet 設定（當目錄中有 .jsonnet 檔時）
    jsonnet:
      extVars:
        - name: env
          value: prod
ℹ️

Directory 與 recurse

預設 recurse: false——Argo CD 只讀取 path 指定的根目錄中的 YAML，不遞迴進入子目錄。若要管理有子目錄結構的 manifest，設定 recurse: true，但要注意可能意外包含不該套用的檔案，建議搭配 exclude 過濾。

7Multiple Sources：多 Source 組合

Multiple Sources（spec.sources 複數）是 v2.6 正式穩定的功能，允許一個 Application 同時引用多個 Git repo 或 Helm chart，最常見的使用場景是：chart 來自一個 repo（或 chart registry），values 來自另一個 repo。

ℹ️

spec.source 與 spec.sources 二擇一

source（單數）與 sources（複數）不可同時出現。使用 sources 時，每個 source 均為完整的 source 定義（含 repoURL / path 或 chart / targetRevision），且各自獨立進行 Tool Detection。

7.1 ref：跨 Source 參考機制

ref 欄位讓一個 source 成為「參考來源」，其他 source 可以用 $ref_name/path 的格式引用它的檔案：

📊
Source 1（Chart）
Helm chart repo 或 Git
chart: kube-prometheus-stack
無 ref 欄位
+
📁
Source 2（Values）
Git repo 存放 values
ref: values
本身不部署任何資源
YAML — Multiple Sources：chart + values 分倉（完整範例）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prometheus-stack
  namespace: argocd
spec:
  project: platform
  sources:
    ## Source 1：Helm chart（來自 Helm repo）
    - repoURL: https://prometheus-community.github.io/helm-charts
      chart: kube-prometheus-stack
      targetRevision: 58.3.3
      helm:
        releaseName: prometheus
        valueFiles:
          # $values 對應下方 ref: values 的 Source
          - $values/monitoring/prometheus/base-values.yaml
          - $values/monitoring/prometheus/production-values.yaml

    ## Source 2：Values Git repo（ref 定義）
    - repoURL: https://github.com/myorg/platform-values.git
      targetRevision: main
      # ref: 讓此 source 成為「參考來源」，值為 $values 中 $ 後的名稱
      ref: values
      # 有 ref 的 source 本身不部署任何資源，僅提供檔案參考

  destination:
    server: https://kubernetes.default.svc
    namespace: monitoring
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true

7.2 常見 Multiple Sources 模式

模式Source 1Source 2適用場景
chart + values 分倉Helm chart repo / OCIGit values repo（ref）chart 由平台提供，各環境 values 各自管理
base + overlay 跨 repoKustomize base（共用）Kustomize overlay（環境特定）base 在共用 repo，overlay 在各團隊 repo
manifest + 額外資源主 App manifest額外 ConfigMap / Secret主 App 不修改，但需注入外部配置
OCI chart + Git valuesOCI Helm chartGit values repo（ref）統一用 OCI 存 chart，Git 存環境特定 values

8工具選型指南

沒有絕對最好的工具，選擇應基於團隊現況、應用程式複雜度與維護成本：

工具最適場景優點缺點 / 注意
Helm（Git chart）自建 chart，多環境用 values 差異化模板強大、子 chart、生態豐富模板語法複雜；helm install 與 Argo CD 語義不同
Helm（chart repo / OCI）使用第三方 chart（cert-manager、prometheus 等）直接用官方 chart，版本鎖定清楚values 過多時難管理，建議搭配 Multiple Sources
Kustomizebase + overlay 多環境部署，不需模板邏輯純 YAML、無模板語言、學習成本低複雜邏輯能力弱於 Helm；overlay 巢狀深時難以追蹤
OCI SourceCI 自動 push manifest artifact，不提交 Gitmanifest 與 image 統一管理於 registryv3.1 新特性，工具鏈支援需自行驗證
JsonnetGoogle 風格的大規模 manifest 生成函式式語言、高度可複用學習曲線陡、生態相對 Helm/Kustomize 小
Directory靜態 manifest、CI 生成後直接存 Git最簡單、無需任何工具知識無法模板化，多環境維護困難
Multiple Sourceschart 與 values 分倉管理，分離關注點chart 由平台維護，values 由各團隊維護spec 較複雜；兩個 repo 的 sync 需注意協調
💡

最佳實踐：保持一致性

在同一個 Argo CD 實例中，不建議混用過多工具。選定一到兩種主要工具後，在全組織統一使用，能顯著降低維護與 onboarding 成本。若使用第三方 chart（如 Bitnami、Prometheus），搭配 Multiple Sources 將 values 管理在自己的 Git repo，是業界常見且推薦的模式。

📌 Key Takeaways

  • 🔍Tool Detection 五步驟優先順序（不可改變）：Helm（Chart.yaml）→ Kustomize（kustomization.yaml）→ Jsonnet（*.jsonnet）→ CMP Plugin → Directory（fallback）。遇到工具判定異常，用 argocd app get --output json | jq '.status.sourceType' 確認。
  • ⎈Helm 三種來源：Git repo（用 path）、Helm chart repo（用 chart 欄位）、OCI registry（repoURL 不含 oci:// 前綴）。Argo CD 只執行 helm template，不維護 Helm release state，helm list 看不到。
  • 📊Helm values 五層優先順序：parameters（最高）> valuesObject > values（inline）> valueFiles（後者優先）> chart 預設值（最低）。使用 valuesObject 比 parameters 更易閱讀，避免字串類型轉換問題。
  • 🔧Kustomize overlay 模式：path 指向 overlay 目錄，Argo CD 自動執行 kustomize build。spec 中的 kustomize.patches 支援 inline patch，無需修改 Git repo 中的 kustomization.yaml，特別適合 ApplicationSet 場景。
  • 📦Multiple Sources 的 ref 機制：設定 ref: values 的 source 成為「參考來源」，其他 source 的 valueFiles 可用 $values/path/to/file.yaml 引用其檔案，實現 chart 與 values 分倉管理。
  • 🆕OCI 原生 Source（v3.1）：oci:// 前綴的 repoURL 直接使用 OCI artifact 作為 manifest 來源，統一 manifest 與 container image 的發佈流程至 registry。
