Sync Hooks 與 Resource Hooks
5 階段 hook 完整指南

Hooks 讓 Argo CD 從「apply manifest」升級為「orchestrate deployment」——在 sync 前後執行 DB migration、smoke test、cleanup、notification 等動作。本章完整講解 5 個 hook 階段（PreSync / Sync / PostSync / SyncFail / PostDelete）的執行時機、HookDeletePolicy 三策略、與 sync waves 的整合、6 個生產實戰範例。同時揭露 issue #13429（hook 物件隨機被刪除）等已知問題的成因與 workaround。

📋

前置：已完成 Vol 1-6 與 Ch.32。理解 Ch.06 (sync policy)、Ch.08 (resource hooks 基礎)、Ch.09 (sync waves)。理解 K8s Job 物件、ttlSecondsAfterFinished、backoffLimit。本章是基礎章的進階版本，深入實戰場景與已知問題。

🎯 學習目標

  • 理解 hooks 與一般 K8s 資源的差異（lifecycle attached to sync operation）以及與 Argo Workflows 的職責分工
  • 精通 5 個 hook 階段：PreSync（早於應用資源）、Sync（與應用資源同時）、PostSync（應用 Healthy 後）、SyncFail（失敗時）、PostDelete（Application 刪除後）
  • 掌握 6 個生產實戰範例：① DB migration；② backup & validation；③ smoke test；④ cache warming；⑤ Slack notification；⑥ external resource cleanup
  • 區分 HookDeletePolicy 三策略：HookSucceeded / HookFailed / BeforeHookCreation，並了解組合策略的應用
  • 理解 sync waves 與 hooks 的互動：waves 排序資源（含 hook），每 wave 間 2 秒 delay 可調（ARGOCD_SYNC_WAVE_DELAY）
  • 避開已知問題：① #13429（hook 物件被隨機刪除）；② selective sync 不會跑 hooks；③ PreSync 失敗整個 sync 停止；④ 單一 PreSync job 無法多步驟（需 Argo Workflows）
  • 掌握重要設計原則：① SyncFail 不放關鍵 logic（degraded context）；② notification 用 Argo CD Notifications 而非 SyncFail；③ hooks 必須先在 staging 驗證再上 prod
  • 實作正確的 hook job naming：generateName（防衝突）+ BeforeHookCreation（看最新一次）+ ttlSecondsAfterFinished（保險清理）

1為什麼需要 Hooks

1.1 Hooks vs 一般 K8s 資源

同樣是 Job，加上 argocd.argoproj.io/hook annotation 就變成 hook——但有什麼差別？

面向一般 K8s Job（manifest）Argo CD Hook（含 annotation）
套用時機與其他資源一起 apply由 hook phase 決定（PreSync / PostSync 等）
失敗影響sync 仍標記成功（Job 失敗只影響該物件 health）PreSync/Sync 失敗 → 整個 sync 失敗，後續資源不被 apply
生命週期持續存在直到手動刪除由 HookDeletePolicy 自動清理
每次 sync 行為同名 Job 已存在會報 immutable 錯誤用 generateName 每次建新 Job（或 BeforeHookCreation 清舊建新）
適合場景應用內部的 batch job（如每日報表）deployment lifecycle 操作（migration、test、notification）

1.2 Hooks vs Argo Workflows

⚠️

單一 PreSync job 不能有多步驟

Argo CD hook 的本質是「一個 K8s Job/Pod」——只有一個步驟。如果需要「先 backup → 再 migrate → 再 validation」三步驟且需要 dependency 控制，單一 hook job 做不到，必須：① 拆成多個 hook 用 sync-wave 控制順序（最簡單）；② 用 Argo Workflows 作為 hook resource（kind: Workflow）取得完整 DAG 控制。本章專注 hook 本身，Argo Workflows 整合屬於進階主題。

💡

實務分工：Hooks vs Workflows vs Notifications

① 單一動作 + sync lifecycle 綁定 → Hook（最常用，本章主題）；② 多步驟有 DAG / fan-out → Argo Workflows（用 kind: Workflow 作為 hook）；③ 失敗通知 → 不要用 SyncFail hook，用 Argo CD Notifications（Ch.29）——SyncFail 在 degraded 環境中執行，本身可能失敗，不適合作為告警唯一來源。

2.2 5 個階段對照表

Hook 階段觸發時機失敗後果典型用途
PreSync 應用資源 apply 之前 整個 sync 停止，應用資源不被 apply DB migration、backup、validation
Sync 與應用資源同時 apply 該物件失敗，可能影響整個 sync 複雜編排（不常用，多數情況改用 sync-wave）
PostSync 應用資源全部 Healthy 後 整個 sync 標記為 failed smoke test、cache warming、success notification
SyncFail sync 失敗時觸發 標記 failed 但不會做特殊處理 cleanup（不建議：notification 應用 Notifications）
PostDelete Application 被刪除後 標記 failed 外部資源清理（如 cloud DNS、IAM role）
⚠️

Selective sync 不會跑 hooks

如果用 UI 或 CLI 觸發 selective sync（只 sync 部分資源），hooks 不會執行。這設計是為了避免 selective sync 意外觸發 DB migration 等危險操作。要跑 hooks 必須完整 sync。對於需要 hook 但只想 sync 部分資源的場景，需要重新設計流程或考慮 Argo Workflows。

3PreSync 實戰

3.1 Database Migration（最經典用例）

YAML — PreSync DB migration job
apiVersion: batch/v1
kind: Job
metadata:
  # 用 generateName（不是 name）讓每次 sync 建立獨立 job
  generateName: db-migrate-
  namespace: my-app
  annotations:
    argocd.argoproj.io/hook: PreSync
    # 失敗保留供除錯，成功自動刪除
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
    # 早於應用資源（負 wave）—— wave 0 是預設
    argocd.argoproj.io/sync-wave: "-1"
spec:
  ttlSecondsAfterFinished: 3600     # 保險清理：1 小時後 K8s GC
  backoffLimit: 2                  # 最多重試 2 次
  activeDeadlineSeconds: 600         # 最多執行 10 分鐘
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myorg/api:v1.2.3      # 通常與應用同 image
          command: ["python", "manage.py", "migrate"]
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: url
          resources:
            requests: {cpu: "100m", memory: "256Mi"}
            limits: {cpu: "500m", memory: "512Mi"}
ℹ️

generateName + HookSucceeded 是黃金組合

① generateName：K8s 自動產生唯一名稱（db-migrate-abc123），同名衝突問題不存在；② HookSucceeded：成功後自動刪除，失敗保留供除錯；③ ttlSecondsAfterFinished：保險清理（即使 HookSucceeded 沒生效，K8s 自己會 GC）；④ backoffLimit + activeDeadlineSeconds：限制失敗與超時行為。

3.2 Backup & Validation（DB migration 前的保險）

YAML — PreSync DB backup + validation
## 第一階段：先 backup（wave -10）
apiVersion: batch/v1
kind: Job
metadata:
  generateName: db-backup-
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
    argocd.argoproj.io/sync-wave: "-10"     # 最先執行
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: backup
          image: postgres:16-alpine
          command:
            - /bin/sh
            - -c
            - |
              TS=$(date +%Y%m%d-%H%M%S)
              pg_dump $DATABASE_URL | gzip > /backup/pre-deploy-$TS.sql.gz
              aws s3 cp /backup/pre-deploy-$TS.sql.gz \
                s3://my-backups/pre-deploy/

---
## 第二階段：migration（wave -1，等 backup 完成才執行）
apiVersion: batch/v1
kind: Job
metadata:
  generateName: db-migrate-
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
    argocd.argoproj.io/sync-wave: "-1"      # backup 之後、應用之前
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myorg/api:v1.2.3
          command: ["./migrate", "up"]
💡

用 sync-wave 串接多個 PreSync hooks

單一 PreSync hook 是一個 Pod，沒有多步驟。但多個 PreSync hooks 配 sync-wave 就能達到順序控制：backup（-10）→ migrate（-1）→ 應用資源（wave 0）。Argo CD 會等 wave -10 全部 Healthy 才執行 wave -1，達到「先 backup 再 migrate」的依賴順序，不需動用 Argo Workflows。

4Sync & PostSync 實戰

4.1 PostSync Smoke Test（最常用）

YAML — PostSync smoke test
apiVersion: batch/v1
kind: Job
metadata:
  generateName: smoke-test-
  namespace: my-app
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation
    # 保留最近一次結果供除錯，下次 sync 前清理
spec:
  ttlSecondsAfterFinished: 86400     # 保留 24 小時
  backoffLimit: 1
  activeDeadlineSeconds: 120         # 2 分鐘 timeout
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: smoke-test
          image: curlimages/curl:latest
          command:
            - /bin/sh
            - -c
            - |
              # 等 service / pod 真的 ready（PostSync 觸發後可能還沒立刻可用）
              sleep 10

              # 1) Health endpoint check
              HEALTH=$(curl -s -o /dev/null -w "%{http_code}" \
                http://my-app.my-app.svc:8080/health)
              if [ "$HEALTH" != "200" ]; then
                echo "❌ Health check failed: HTTP $HEALTH"
                exit 1
              fi

              # 2) Critical API path check
              API=$(curl -s http://my-app.my-app.svc:8080/api/version)
              echo "Version: $API"

              # 3) DB connectivity check
              curl -fsS http://my-app.my-app.svc:8080/api/db-check || {
                echo "❌ DB connectivity failed"
                exit 1
              }

              echo "✅ All smoke tests passed"

4.2 Cache Warming（PostSync）

YAML — PostSync cache warming
apiVersion: batch/v1
kind: Job
metadata:
  generateName: cache-warmup-
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed
    argocd.argoproj.io/sync-wave: "10"      # smoke test 之後
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: warmup
          image: curlimages/curl:latest
          command:
            - /bin/sh
            - -c
            - |
              # 對熱門 endpoint 發 request 預熱 cache
              for path in / /products /categories /featured; do
                for i in 1 2 3 4 5; do
                  curl -s -o /dev/null \
                    http://my-app.my-app.svc:8080$path
                done
              done
              echo "✅ Cache warmed"

4.3 Slack Notification（PostSync 通知部署成功）

YAML — PostSync Slack notification
apiVersion: batch/v1
kind: Job
metadata:
  generateName: notify-deployed-
  annotations:
    argocd.argoproj.io/hook: PostSync
    # notification 是 fire-and-forget——成功失敗都刪除
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed
spec:
  backoffLimit: 0     # 不重試（避免重複通知）
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: notify
          image: curlimages/curl:latest
          env:
            - name: SLACK_WEBHOOK
              valueFrom:
                secretKeyRef: {name: slack, key: webhook}
          command:
            - /bin/sh
            - -c
            - |
              curl -X POST $SLACK_WEBHOOK --data-urlencode \
                'payload={"channel":"#deployments","text":"✅ my-app deployed"}'
💡

但更建議用 argocd-notifications（Ch.29）

PostSync notification hook 是傳統做法，但 argocd-notifications 提供更多優勢：① 不需建 Job（純 Slack API 呼叫，更輕量）；② 內建 trigger / template / subscription 機制；③ oncePer 防重複；④ 支援 Slack / Teams / Email / Webhook 多通道。新專案用 argocd-notifications 取代 PostSync notification hook，hook 只用於確實需要 Job 執行邏輯的場景（如 smoke test）。

5SyncFail & PostDelete

5.1 SyncFail（失敗時清理）

YAML — SyncFail rollback signal
apiVersion: batch/v1
kind: Job
metadata:
  generateName: syncfail-rollback-signal-
  annotations:
    argocd.argoproj.io/hook: SyncFail
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: rollback-signal
          image: curlimages/curl:latest
          command:
            - /bin/sh
            - -c
            - |
              # 通知外部系統 sync 失敗（觸發回滾、開 ticket 等）
              curl -X POST https://incident-api.example.com/v1/sync-failed \
                -H "Authorization: Bearer $INCIDENT_TOKEN" \
                -d '{"app":"my-app","ts":"'$(date -u +%FT%TZ)'"}'
⚠️

SyncFail 不適合放關鍵邏輯

SyncFail hook 在 degraded sync 環境中執行——可能本身也失敗（image pull 失敗、namespace 已壞、secret 還沒就緒）。關鍵的 alerting 用 Argo CD Notifications / Prometheus Alerts，不要依賴 SyncFail。SyncFail 適合「best-effort cleanup」如刪除 partial 建立的資源、發 informational signal——失敗也不會造成更大問題的場景。

5.2 PostDelete（外部資源清理）

YAML — PostDelete cleanup external resources
apiVersion: batch/v1
kind: Job
metadata:
  generateName: cleanup-cloud-resources-
  annotations:
    argocd.argoproj.io/hook: PostDelete
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: OnFailure
      serviceAccountName: cleanup-bot      # IRSA / Workload Identity
      containers:
        - name: cleanup
          image: amazon/aws-cli:2
          command:
            - /bin/sh
            - -c
            - |
              # 1) 刪除應用建立的 S3 bucket
              aws s3 rb s3://my-app-prod-data --force

              # 2) 刪除應用註冊的 Route53 records
              aws route53 change-resource-record-sets ...

              # 3) 刪除 IAM Role
              aws iam delete-role --role-name my-app-prod-role

              echo "✅ External resources cleaned"
ℹ️

PostDelete 的限制與替代方案

PostDelete 在 Application 被刪除後執行——但有時 Application 已經被刪、Job 卻找不到 namespace。實務上更穩健的做法：① 用 K8s Finalizer（如 Crossplane 提供的 cloud resource finalizer）；② 用 OperatorPattern（自製 controller 接管刪除流程）；③ PostDelete 作為「最終保險」清理一些不關鍵的 metadata。關鍵資源（資料庫、PV 等）不要依賴 PostDelete 唯一清理。

6HookDeletePolicy 三策略

每次 sync hook 都會建一個 Job——沒設 delete policy 累積到 50 次部署就是 50 個 Job 在 namespace。argocd.argoproj.io/hook-delete-policy 控制清理時機：

策略觸發時機典型用途
HookSucceeded Hook 成功完成後立刻刪除 DB migration（失敗保留供除錯）
HookFailed Hook 失敗後刪除 少用——失敗通常想保留
BeforeHookCreation（預設） 下次 sync 建新 hook 前刪除舊的 保留最近一次結果供除錯

組合策略（用逗號分隔）

YAML — 5 種常見組合策略
## 1) DB migration（最常見組合）
# 成功後刪除，失敗保留供除錯，下次 sync 前清理失敗的
annotations:
  argocd.argoproj.io/hook: PreSync
  argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation

## 2) Smoke test（保留最近一次結果）
annotations:
  argocd.argoproj.io/hook: PostSync
  argocd.argoproj.io/hook-delete-policy: BeforeHookCreation

## 3) Notification（fire and forget）
# 成功失敗都刪除，不留紀錄
annotations:
  argocd.argoproj.io/hook: PostSync
  argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed

## 4) Audit log（不刪除，保留歷史）
# 配合 unique name（含 version）避免衝突
metadata:
  name: audit-deploy-v1.2.3-20260509     # unique name 而非 generateName
  annotations:
    argocd.argoproj.io/hook: PostSync
    # 沒 hook-delete-policy = 永遠保留

## 5) SyncFail alert（成功後刪除，下次失敗時清舊建新）
annotations:
  argocd.argoproj.io/hook: SyncFail
  argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
💡

選擇策略的決策樹

① 需要除錯失敗的 hook? → 是：HookSucceeded（失敗保留）；否：HookSucceeded,HookFailed（全刪）；② 需要看最近一次結果? → 是：BeforeHookCreation；否：HookSucceeded；③ 需要長期 audit log? → 不設 policy + 用 unique name；④ 大多數場景：HookSucceeded,BeforeHookCreation（成功刪、失敗留、下次清舊）。

7與 Sync Waves 整合

Sync waves（Ch.09 介紹過）控制 phase 內的順序，hooks 同樣支援 sync-wave annotation：

YAML — Hook + sync-wave 完整時序範例
## 假設一次 sync 涉及以下資源（按 phase + wave 排序）：

## ━━━━━━━━━━━ PreSync phase ━━━━━━━━━━━
# 1. PreSync wave -10：DB backup（最先）
# 2. PreSync wave -1：DB migration（backup 完成後）

## ━━━━━━━━━━━ Sync phase ━━━━━━━━━━━
# 3. Sync wave 0（預設）：Namespace、ServiceAccount、ConfigMap、Secret
# 4. Sync wave 1：PersistentVolumeClaim、Database StatefulSet
# 5. Sync wave 2：Backend Deployment
# 6. Sync wave 3：Frontend Deployment、Ingress

## ━━━━━━━━━━━ PostSync phase ━━━━━━━━━━━
# 7. PostSync wave 0：Smoke test（等所有 Sync 資源 Healthy 才執行）
# 8. PostSync wave 10：Cache warming（smoke test 完才執行）
# 9. PostSync wave 100：Slack notification（最後）
⚠️

每 wave 之間有 2 秒 delay

Argo CD 在每個 sync wave 結束後等 2 秒才開始下一個 wave——讓 K8s controllers（如 deployment-controller）有時間處理 spec 變更，避免 hooks 在「資源還是舊狀態」時就被觸發。可調整環境變數 ARGOCD_SYNC_WAVE_DELAY（預設 2 秒）。如果你有 50 個 wave，每個 delay 2 秒就是 100 秒額外時間——大型部署可以考慮加長 delay 確保穩定，或調短加速但風險更高。

等 Healthy 的判定

YAML — Argo CD wave progression 規則
# Argo CD 推進到下一個 wave 的條件：
#
# 1. 當前 wave 的所有資源都 apply 完成
# 2. 當前 wave 的所有資源都 Healthy（依 health check）
# 3. 等待 ARGOCD_SYNC_WAVE_DELAY 秒（預設 2）
# 4. 進入下一個 wave
#
# 對於 hook 而言：
# - Job 的 Healthy = Job complete 成功
# - Job 的 Degraded = Job failed
# - Argo CD 等 hook 達到 Healthy 才進下一 wave
#
# 如果 hook 永遠不 complete（如 wait condition 一直 false）：
# - sync 會 stuck 在該 wave 直到 sync timeout
# - 必設 activeDeadlineSeconds 限制 Job 執行時間

8已知問題與限制

Issue #13429：Hook 物件隨機被刪除

⚠️

已知 issue #13429（v2.5+ 至今未完全修復）

當 hook 是非 Job 物件（ConfigMap、SecretProviderClass、ExternalSecret 等）且用 hook-delete-policy: BeforeHookCreation，偶發性的在 PreSync hook 結束後該物件被刪除。原因：Argo CD 將「BeforeHookCreation」誤套用到該物件本身。workaround：① 把 ConfigMap / Secret 改為一般 K8s 資源（不加 hook annotation），讓它跟隨應用週期；② 改用 hook-delete-policy: HookSucceeded 明確指示刪除時機；③ 升級到最新版本確認是否修復。

限制總覽

限制影響解法
單 PreSync 不能多步驟 無法在單一 Pod 內做 backup → migrate → validate 序列依賴 拆多個 hook 用 sync-wave；或用 Argo Workflows 作 hook
Selective sync 不跑 hooks UI / CLI 點 sync 個別資源時 hook 不會執行 完整 sync 才會觸發 hooks（這是設計使然，保護 DB migration 等危險操作）
PreSync 失敗整個停止 一個 hook 卡住 = 整個 sync 失敗 ① 設 activeDeadlineSeconds 限制時間；② backoffLimit 限制重試；③ hook script 內加 timeout
SyncFail 在 degraded 環境 SyncFail hook 本身可能失敗（image pull / namespace 問題） 不放關鍵邏輯；alerting 用 Notifications 取代
沒有跨 Application 的 hook 無法在「App A sync 完才 sync App B」 用 App-of-Apps + sync-wave；或外部 orchestrator（Argo Workflows、Kargo）
Hook resource 不受 ignoreDifferences 影響 hook job 不會被 diff，每次 sync 都重新建 這是設計使然——hook 本意就是每次 sync 重建

9最佳實踐 Checklist

✅

Hooks 撰寫 11 原則

① 用 generateName 而非 name（避免命名衝突）；② 必設 hook-delete-policy（避免 namespace 累積垃圾）；③ 必設 activeDeadlineSeconds（防止無窮等待卡死 sync）；④ 必設 backoffLimit（限制重試次數）；⑤ 用 ttlSecondsAfterFinished 作為保險（即使 hook-delete-policy 失效，K8s 自己會清）；⑥ restartPolicy: Never（migration 不應該重複執行）；⑦ PreSync 失敗的 logic 設計：確保安全 abort 不留 partial state；⑧ 不要在 SyncFail 放關鍵邏輯（用 Notifications）；⑨ 多步驟依賴用 sync-wave 串接而非單一 hook；⑩ hooks 先在 staging 驗證再上 prod（broken hook 阻擋所有 sync）；⑪ 用 argocd-notifications 取代 PostSync notification hook（更輕量、更可靠）。

除錯指令

Bash — Hook 除錯工具集
## 1. 看 Application 的 hook 執行歷史
$ argocd app get my-app --show-operation
# 輸出 hooks 的 phase / status / message

## 2. 看 hook Job 的 logs（最近一次）
$ kubectl logs -n my-app -l app.kubernetes.io/managed-by=argocd \
    -l argocd.argoproj.io/hook=PreSync --tail=200

## 3. 看 controller log 找 hook 相關訊息
$ kubectl logs -n argocd statefulset/argocd-application-controller \
    --tail=500 | grep -i hook

## 4. 列出所有 hook resources
$ kubectl get jobs -n my-app -l argocd.argoproj.io/hook=PreSync
$ kubectl get jobs -n my-app -l argocd.argoproj.io/hook=PostSync

## 5. 強制清理卡住的 hook Job
$ kubectl delete jobs -n my-app -l argocd.argoproj.io/hook=PreSync

## 6. 看 Job 為何失敗
$ kubectl describe job -n my-app db-migrate-abc123
# Events 區段會顯示 ImagePullBackOff / OOMKilled / DeadlineExceeded 等

## 7. 修改 ARGOCD_SYNC_WAVE_DELAY（調慢或調快）
$ kubectl set env statefulset/argocd-application-controller \
    -n argocd ARGOCD_SYNC_WAVE_DELAY=5
# 改為 5 秒（適合大型 wave-heavy 部署）

📌 Key Takeaways

  • 🎯Hooks 讓 Argo CD 從「apply manifest」升級為「orchestrate deployment」：5 個階段（PreSync / Sync / PostSync / SyncFail / PostDelete）覆蓋 deployment 完整 lifecycle。Hook 是含 argocd.argoproj.io/hook annotation 的 K8s 資源（通常是 Job），失敗會中斷 sync（與一般資源不同）。
  • ⚡PreSync 是最重要的階段：在應用資源 apply 之前執行，失敗則整個 sync 停止（保護機制）。經典用例：DB migration、backup、validation。多個 PreSync hook 用 sync-wave 串接達成順序依賴（backup -10 → migrate -1 → 應用 wave 0）。
  • 📦Sync 階段不常單獨用（直接用 sync-wave 控制資源順序更直觀）。PostSync 在應用全部 Healthy 後執行，最常用於 smoke test、cache warming、deployment notification。注意：建議用 argocd-notifications 取代 PostSync notification hook（更輕量、有 oncePer 防重複）。
  • ⚠️SyncFail 不適合放關鍵邏輯：在 degraded sync 環境執行，本身可能失敗。alerting / paging 用 Prometheus Alerts，notification 用 argocd-notifications。SyncFail 適合 best-effort cleanup（如刪除 partial 建立的資源、發 informational signal）。
  • 🗑️PostDelete 外部資源清理：Application 刪除後執行，用於清理 S3 bucket、Route53 records、IAM Role 等外部資源。但有時 namespace 已刪 Job 跑不起來——關鍵資源（資料庫、PV 等）應該用 Finalizer 或 Operator pattern 而非 PostDelete。
  • 🧹HookDeletePolicy 三策略：① HookSucceeded（成功刪、失敗留供除錯）；② HookFailed（少用）；③ BeforeHookCreation（預設，保留最近一次）。實務最常用組合 HookSucceeded,BeforeHookCreation：成功刪、失敗留、下次清舊。notification 用 HookSucceeded,HookFailed（fire and forget）。
  • 🌊Sync waves 串接 hooks 達成多步驟：單一 hook 是一個 Pod（無多步驟），但多個 hook + sync-wave 可達成 backup → migrate → 應用 → smoke test → notification 完整流程。每 wave 間有 2 秒 delay（ARGOCD_SYNC_WAVE_DELAY），大型部署可調長更穩或調短加速。
  • 🐛已知 issue #13429（v2.5+ 偶發）：非 Job hook（ConfigMap / SecretProviderClass）配 BeforeHookCreation policy 時 randomly 被刪除。workaround：① 改回一般 K8s 資源（不加 hook annotation）；② 改用 HookSucceeded 明確指示；③ 升級最新版確認修復。
  • 🚧核心限制：① 單 PreSync 不能多步驟（用 sync-wave 拆多 hook 或 Argo Workflows）；② Selective sync 不跑 hooks（設計使然保護 DB migration）；③ 無跨 Application hook（用 App-of-Apps + sync-wave 或外部 orchestrator）；④ Hook 不受 ignoreDifferences（每次 sync 都重建）。
  • ✅11 項撰寫原則：① generateName 避免命名衝突；② 必設 hook-delete-policy；③ 必設 activeDeadlineSeconds；④ 必設 backoffLimit；⑤ ttlSecondsAfterFinished 保險清理；⑥ restartPolicy: Never；⑦ PreSync 設計安全 abort；⑧ 不在 SyncFail 放關鍵邏輯；⑨ 多步驟用 sync-wave；⑩ 先在 staging 驗證；⑪ 用 argocd-notifications 取代 PostSync notification。
