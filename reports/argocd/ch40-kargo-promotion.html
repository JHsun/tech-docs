Kargo
Multi-Stage Promotion 跨環境推進

Vol 9 第二章。Argo CD 擅長「Git → Cluster」單一同步，但「從 dev → staging → prod 跨環境推進」呢？傳統做法依賴 CI script、手動修改 GitOps repo、或 ApplicationSet 配 manual sync——都缺乏 first-class 的 promotion 抽象。Kargo（由 Argo / Akuity 團隊打造）是一個 GitOps-native 的multi-stage promotion engine，引入 Warehouse（監聽 artifact 來源）、Freight（可推進的版本快照）、Stage（環境抽象 + 推進邏輯）三大 CRD。本章涵蓋 Kargo 完整概念、實作、與 Argo CD 整合、與 Image Updater + ApplicationSet 的對比、生產實踐。

📋

前置：已完成 Vol 1-8。理解 Ch.30（Image Updater）與 Ch.31（CI/CD 整合 + image promotion 痛點）。理解 ApplicationSet（Ch.23-26）。對 finite state machine 與 DAG 概念有基本認識。

🎯 學習目標

  • 理解 Argo CD 在「跨環境 promotion」的功能缺口：每個 Application 各自 sync，無 first-class 的 dev → staging → prod 推進抽象
  • 掌握 Kargo 三大核心 CRD：Warehouse（artifact source watcher）、Freight（versioned bundle of artifacts）、Stage（environment + promotion logic）
  • 理解 Freight 的不可變特性：一個 Freight = container image + Git commit + Helm chart 的確定組合 snapshot，promotion 推的是 Freight 而非單一 artifact
  • 實作 Warehouse：監聽 container registry（SemVer / Newest-build / digest）、Git repo（branch / tag）、Helm chart repo
  • 撰寫 Stage 的 promotionTemplate.steps：git-clone、yaml-update、kustomize-set-image、helm-update-image、git-commit、git-push、argocd-update、analysis-run
  • 掌握 expression 語法：${{ vars.xxx }} 變數引用、${{ imageFrom(repo, warehouse(name)).Tag }} 從 Freight 取值、${{ ctx.stage }} 取得 Stage 名
  • 用 PromotionTask 抽象提取通用邏輯（避免每個 Stage 重複大段步驟）
  • 整合 Verification + AnalysisRun（Ch.37 的 AnalysisTemplate）：每個 Stage promotion 後自動 verify metrics 才允許下個 Stage 取此 Freight
  • 與 Argo CD 整合：① argocd-update step 觸發 sync；② Application 必須加 kargo.akuity.io/authorized-stage 註解才能被 Stage 操作；③ Stage health 反映 Argo CD Application health
  • 對比三種 promotion 方案：① Kargo；② Image Updater + ApplicationSet；③ CI script + git commit。理解各自適用場景
  • 避開常見陷阱：① Warehouse repoURL 錯誤 → Freight nil；② Stage path 與 git-clone 不一致；③ Git push 認證缺失；④ Argo CD Application 未加 authorized-stage 註解；⑤ Helm tag 沒 quote() 造成 SemVer 解析錯誤

1為什麼需要 Kargo

1.1 Argo CD 的 Promotion 缺口

Argo CD 的核心是「Git → Cluster 同步」——一個 Application 對應一個 Git path + 一個 cluster destination。但「相同 image 從 dev → staging → prod 推進」不是 Argo CD 的職責：

需求Argo CDKargo
Git → Cluster 同步✅ 核心功能❌ 不負責（呼叫 Argo CD 做）
多 Application 同 source✅ ApplicationSet—
跨環境 promotion（dev → staging → prod）❌ 無 first-class 抽象✅ Stage CRD 核心
確定 image / Helm / Git 組合一起推進❌ 各自獨立✅ Freight = 不可變組合 snapshot
跨 Stage verification gate❌ 無✅ AnalysisRun 整合
UI 顯示推進進度❌（每 App 獨立）✅ 跨 Stage pipeline 視覺化
Manual approval gate❌ 用 sync 暫停 hack✅ 內建 approve 機制
💡

Kargo 不取代 Argo CD，是補上 promotion 層

① Argo CD：reconciliation engine（同步 Git → K8s）；② Kargo：promotion engine（把 Freight 從 Stage A 推到 Stage B）。Kargo 透過 Argo CD 完成實際部署——Kargo 修改 GitOps repo（image tag、Helm value），Argo CD 偵測到變更 sync 到 cluster。兩者完美互補，不是替代關係。

1.2 vs ApplicationSet 的差異

ApplicationSet 可以「dev/staging/prod 各建一個 Application」，但不提供 promotion 邏輯：

  • ① ApplicationSet 把多個 Application 模板化，但每個 Application 各自獨立 sync——image tag 變更必須手動 push 到對應 overlay；
  • ② ApplicationSet 沒有「先 dev → 觀察 → 再 staging」的順序推進概念；
  • ③ 沒有「dev、staging、prod 用同一 image+config 組合」的不可變 snapshot；
  • ④ Kargo + ApplicationSet 可以並用：ApplicationSet 建立各環境 Application，Kargo 管理它們之間的 promotion。

2三大核心 CRD

2.1 Warehouse（artifact source watcher）

Warehouse 是「artifact source 的訂閱者」——監視 container registry、Git repo、Helm chart repo 的變化，產生 Freight：

YAML — Warehouse 完整範例
apiVersion: kargo.akuity.io/v1alpha1
kind: Warehouse
metadata:
  name: myapp-warehouse
  namespace: myteam-project
spec:
  # Freight 建立策略：Automatic（自動）/ Manual（需 approve）
  freightCreationPolicy: Automatic

  # 多久檢查一次
  interval: 5m0s

  # 訂閱多種 artifact source（單一 Freight 含三者組合）
  subscriptions:
    # 1) Container image
    - image:
        repoURL: public.ecr.aws/myorg/myapp
        # 選擇策略：SemVer / NewestBuild / Alphabetical / Digest / Lexical
        imageSelectionStrategy: SemVer
        strictSemvers: true          # 嚴格 SemVer（如 v1.2.3）
        semverConstraint: ">=1.0.0"
        discoveryLimit: 20             # 最多保留 20 個歷史 image 給 selection
        platforms:
          - linux/amd64
          - linux/arm64

    # 2) Git repo（manifest / Helm chart sources）
    - git:
        repoURL: https://github.com/myorg/gitops.git
        branch: main
        # 或 tags / commits
        # commitSelectionStrategy: Lexical / NewestFromBranch / SemVer

    # 3) Helm chart repo
    - chart:
        repoURL: https://charts.example.com
        name: myapp
        semverConstraint: "^2.0.0"

2.2 Freight（不可變的 artifact bundle）

💡

Freight = container image + Git commit + Helm chart 的確定組合 snapshot

Freight 是 Kargo 的核心 idea。傳統 promotion 只推 image tag，但實務上「v1.2.3 image」可能需要「v1.2.3 的 Helm chart」與「commit abc123 的 manifest patch」一起部署——Kargo 用 Freight 把三者捆綁為一個不可變 snapshot。

Promotion 推的是整個 Freight——dev 跑的 image+chart+manifest 與 staging、prod 跑的完全相同，避免「dev 用 image v1.2.3 + chart v2.0；prod 卻意外用 image v1.2.3 + chart v1.9」的版本錯配。

Freight 由 Warehouse 自動產生，不需手動建立——你只需 build image 並 push 到 registry，Warehouse 偵測到後就 emit 一個新 Freight 物件。每個 Freight 有唯一 id（hash of contents）。

2.3 Stage（environment + promotion logic）

YAML — Stage 完整骨架
apiVersion: kargo.akuity.io/v1alpha1
kind: Stage
metadata:
  name: dev
  namespace: myteam-project
  annotations:
    # UI 視覺化顏色（lime / cyan / yellow / orange / red）
    kargo.akuity.io/color: lime
spec:
  # 從哪取 Freight
  requestedFreight:
    - origin:
        kind: Warehouse
        name: myapp-warehouse
      sources:
        # direct: true 表示從 Warehouse 直接取（dev stage）
        direct: true
        # 或從上游 Stage 取（staging / prod stage）
        # stages: [dev]   # 表示從 dev stage promote 過來

  # Promotion 邏輯：當有 Freight 要推進到此 Stage 時執行
  promotionTemplate:
    spec:
      vars:
        - name: gitopsRepo
          value: https://github.com/myorg/gitops.git
        - name: imageRepo
          value: public.ecr.aws/myorg/myapp
      steps:
        # Step 1：clone GitOps repo
        - uses: git-clone
          config:
            repoURL: ${{ vars.gitopsRepo }}
            checkout:
              - branch: main
                path: ./out

        # Step 2：用 kustomize 更新 image
        - uses: kustomize-set-image
          as: update-image
          config:
            path: ./out/overlays/dev
            images:
              - image: ${{ vars.imageRepo }}

        # Step 3：commit + push
        - uses: git-commit
          as: commit
          config:
            path: ./out
            message: ${{ outputs['update-image'].commitMessage }}
        - uses: git-push
          config:
            path: ./out

        # Step 4：等 Argo CD sync 完成（同 Ch.31 的 argocd app wait）
        - uses: argocd-update
          config:
            apps:
              - name: myapp-dev
                sources:
                  - desiredRevision: ${{ outputs.commit.commit }}
                    repoURL: ${{ vars.gitopsRepo }}

  # Promotion 完成後跑 verification（可選，第 6 節詳述）
  verification:
    analysisTemplates:
      - name: smoke-test

3安裝與基礎設定

$ kubectl apply -f \

## 2. 安裝 Kargo controller + API server + Web UI
$ helm install kargo \
    oci://ghcr.io/akuity/kargo-charts/kargo \
    --namespace kargo \
    --create-namespace \

## 3. 驗證
$ kubectl get pods -n kargo
# kargo-controller-xxx
# kargo-api-xxx

$ curl -L -o kargo \
    "https://github.com/akuity/kargo/releases/latest/download/kargo-darwin-amd64"

## 5. 登入
$ kubectl port-forward -n kargo svc/kargo-api 8080:443 &
$ kargo login https://localhost:8080 \
    --admin --insecure-skip-tls-verify --password admin

## 6. 建立 Project（namespace）
$ kargo create project myteam-project
ℹ️

Kargo Project = K8s Namespace

Kargo 用 K8s namespace 作為 Project 邊界——每個 team / 應用一個 Project（namespace），其中包含 Warehouse、Stage、Freight 等資源。跨 Project 不能直接 promote。RBAC 也是 namespace-scoped，方便多團隊隔離。

4完整 Promotion Pipeline

實作「dev → staging → prod」三 Stage pipeline，含 Argo CD Application 整合：

4.1 Warehouse 監聽 image registry

YAML — Warehouse 監聽 GHCR
apiVersion: kargo.akuity.io/v1alpha1
kind: Warehouse
metadata:
  name: guestbook
  namespace: guestbook-project
spec:
  freightCreationPolicy: Automatic
  interval: 5m0s
  subscriptions:
    - image:
        repoURL: ghcr.io/myorg/guestbook
        imageSelectionStrategy: SemVer
        strictSemvers: true
        discoveryLimit: 20

4.2 dev Stage：從 Warehouse 取 Freight

YAML — dev Stage（direct from Warehouse）
apiVersion: kargo.akuity.io/v1alpha1
kind: Stage
metadata:
  name: dev
  namespace: guestbook-project
  annotations:
    kargo.akuity.io/color: lime
spec:
  requestedFreight:
    - origin:
        kind: Warehouse
        name: guestbook
      sources:
        direct: true          # 直接從 Warehouse（dev 是 pipeline 第一個 Stage）

  promotionTemplate:
    spec:
      vars:
        - name: gitopsRepo
          value: https://github.com/myorg/gitops.git
        - name: imageRepo
          value: ghcr.io/myorg/guestbook
      steps:
        - uses: git-clone
          config:
            repoURL: ${{ vars.gitopsRepo }}
            checkout:
              - branch: main
                path: ./out

        # 用 kustomize-set-image step
        - uses: kustomize-set-image
          as: update-image
          config:
            path: ./out/overlays/dev
            images:
              - image: ${{ vars.imageRepo }}
                # 自動從 Freight 取 image tag

        - uses: git-commit
          as: commit
          config:
            path: ./out
            message: ${{ outputs['update-image'].commitMessage }}

        - uses: git-push
          config:
            path: ./out

        # 觸發 Argo CD sync + 等完成
        - uses: argocd-update
          config:
            apps:
              - name: guestbook-dev
                sources:
                  - desiredRevision: ${{ outputs.commit.commit }}
                    repoURL: ${{ vars.gitopsRepo }}

4.3 staging / prod Stage：從上游 Stage 取 Freight

YAML — staging 與 prod Stage
apiVersion: kargo.akuity.io/v1alpha1
kind: Stage
metadata:
  name: staging
  namespace: guestbook-project
spec:
  requestedFreight:
    - origin:
        kind: Warehouse
        name: guestbook
      sources:
        # 從 dev stage 推進過來
        stages:
          - dev
      # 重要：staging 不允許跳過 dev 直接從 Warehouse 取

  promotionTemplate:
    spec:
      vars:
        - name: gitopsRepo
          value: https://github.com/myorg/gitops.git
        - name: imageRepo
          value: ghcr.io/myorg/guestbook
      steps:
        - uses: git-clone
          config:
            repoURL: ${{ vars.gitopsRepo }}
            checkout:
              - branch: main
                path: ./out
        - uses: kustomize-set-image
          as: update-image
          config:
            path: ./out/overlays/staging
            images:
              - image: ${{ vars.imageRepo }}
        - uses: git-commit
          as: commit
          config:
            path: ./out
            message: ${{ outputs['update-image'].commitMessage }}
        - uses: git-push
          config:
            path: ./out
        - uses: argocd-update
          config:
            apps:
              - name: guestbook-staging
                sources:
                  - desiredRevision: ${{ outputs.commit.commit }}
                    repoURL: ${{ vars.gitopsRepo }}

結果是一個跨 Stage 的DAG pipeline：

Diagram — Pipeline DAG
┌──────────────┐
│ Warehouse    │ ←─── ghcr.io/myorg/guestbook（監聽新 SemVer image）
│ (guestbook)  │
└──────┬───────┘
       │ emit Freight (v1.2.3, commit abc, chart v2.0)
       ▼
┌──────────────┐
│ Stage: dev   │ direct: true（從 Warehouse 取）
│              │ kustomize-set-image → git-commit → argocd-update
└──────┬───────┘
       │ Freight 在 dev 部署完成（且 verification 通過）
       │ 才能 promote 到 staging
       ▼
┌──────────────┐
│ Stage:staging│ stages: [dev]
│              │ 同樣的 promotion steps，path 改為 overlays/staging
└──────┬───────┘
       │ 通過 staging 的 verification 才能 promote 到 prod
       │（通常還需 manual approval）
       ▼
┌──────────────┐
│ Stage: prod  │ stages: [staging]
│              │ path: overlays/prod
└──────────────┘

# 重點：dev/staging/prod 部署的是同一個 Freight
#       → image / chart / manifest 完全一致
#       → 不可能「dev 用 v1.2.3 但 prod 不小心用 v1.2.2」

5PromotionTask 模組化

上面每個 Stage 都有大段重複的 promotion steps（git-clone → kustomize-set-image → commit → push → argocd-update）。PromotionTask 把這段邏輯抽出來重用：

YAML — PromotionTask + 簡化版 Stage
apiVersion: kargo.akuity.io/v1alpha1
kind: PromotionTask
metadata:
  name: standard-promotion
  namespace: guestbook-project
spec:
  vars:
    - name: stage           # 由 Stage 傳入
    - name: argocdApp       # 由 Stage 傳入
    - name: gitopsRepo
      value: https://github.com/myorg/gitops.git
    - name: imageRepo
      value: ghcr.io/myorg/guestbook
  steps:
    - uses: git-clone
      config:
        repoURL: ${{ vars.gitopsRepo }}
        checkout:
          - branch: main
            path: ./out
    - uses: kustomize-set-image
      as: update-image
      config:
        path: ./out/overlays/${{ vars.stage }}
        images:
          - image: ${{ vars.imageRepo }}
    - uses: git-commit
      as: commit
      config:
        path: ./out
        message: ${{ outputs['update-image'].commitMessage }}
    - uses: git-push
      config:
        path: ./out
    - uses: argocd-update
      config:
        apps:
          - name: ${{ vars.argocdApp }}
            sources:
              - desiredRevision: ${{ outputs.commit.commit }}
                repoURL: ${{ vars.gitopsRepo }}

---
## Stage 變得非常精簡
apiVersion: kargo.akuity.io/v1alpha1
kind: Stage
metadata:
  name: staging
spec:
  requestedFreight:
    - origin:
        kind: Warehouse
        name: guestbook
      sources:
        stages: [dev]
  promotionTemplate:
    spec:
      steps:
        # 引用 PromotionTask 並傳參數
        - task:
            name: standard-promotion
            kind: PromotionTask
          vars:
            - name: stage
              value: staging
            - name: argocdApp
              value: guestbook-staging
💡

PromotionTask 帶來的好處

① DRY：promotion 邏輯寫一次，多 Stage / 多服務共用；② 變更集中：要改 promotion 流程（如加 Slack 通知 step）只改 PromotionTask；③ 跨服務統一：全公司用同一 PromotionTask 確保一致性；④ 可測試：PromotionTask 在 dev environment 驗證後再套用 prod。實務上 PromotionTask 應該由 platform team 維護，dev team 只填 Stage 的 vars。

6Verification 與 AnalysisRun

Stage 可以加 verification——promotion 完成後自動跑 AnalysisTemplate（Ch.37），通過才能讓 Freight 進入「可被下游 Stage 取用」狀態：

YAML — Stage with verification
apiVersion: kargo.akuity.io/v1alpha1
kind: Stage
metadata:
  name: staging
spec:
  requestedFreight:
    - origin:
        kind: Warehouse
        name: guestbook
      sources:
        stages: [dev]

  promotionTemplate:
    ## ... promotion steps（同上）

  # 關鍵：promotion 完成後跑 verification
  verification:
    analysisTemplates:
      - name: smoke-test           # 必須是同 namespace 的 AnalysisTemplate
      - name: success-rate-slo     # 多個 template 都要通過

    # 可選：AnalysisRun 的額外 args
    analysisRunMetadata:
      labels:
        stage: staging
ℹ️

Kargo 重用 Argo Rollouts 的 AnalysisTemplate（Ch.37）

Kargo 並不重新發明 verification 機制——直接重用 Argo Rollouts 的 AnalysisTemplate CRD。意思是 Ch.37 學的 Prometheus / Datadog / Web / Job 等 metric providers 通通可用。Kargo verification 創建 AnalysisRun，等結果 Successful 才標記此 Freight 在這個 Stage 已 verified（下游 Stage 才能取用）。實務：用相同的 AnalysisTemplate 同時服務 Argo Rollouts canary 與 Kargo Stage verification。

Verification 失敗的處理

Bash — Verification 失敗時的操作
## 1. 查看 Stage 狀態（含 verification history）
$ kargo get stage staging --project guestbook-project -o yaml | yq .status

## 範例輸出（含 verification 結果）：
# verificationHistory:
#   - analysisRun:
#       name: staging.01j2w7aknhf3.101bca5
#       namespace: guestbook-project
#       phase: Failed
#     phase: Failed
#     finishTime: "2026-05-09T22:13:57Z"

## 2. 看 AnalysisRun 詳細失敗原因
$ kubectl describe analysisrun staging.01j2w7aknhf3.101bca5 \
    -n guestbook-project

## 3. Verification 失敗時，Stage 維持 Unhealthy 狀態
##    Freight 不會被標記為 verified-in-this-stage
##    下游 Stage 看不到此 Freight 為「可推進」

## 4. 解決後重新 verify（不需重做 promotion）
$ kargo verify stage staging --project guestbook-project

7與 Argo CD 整合細節

7.1 authorized-stage 註解（必設）

Kargo 透過 argocd-update step 操作 Argo CD Application——但Argo CD Application 必須明確授權給特定 Stage 才能被操作，避免任何 Stage 都能改任何 Application：

YAML — Application 加 authorized-stage 註解
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook-staging
  namespace: argocd
  annotations:
    # 關鍵註解：允許哪個 Project 的哪個 Stage 操作此 Application
    # 格式：<project-namespace>:<stage-name>
    kargo.akuity.io/authorized-stage: guestbook-project:staging
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/gitops.git
    path: overlays/staging
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: staging
  syncPolicy:
    automated: {prune: true, selfHeal: true}
⚠️

缺 authorized-stage 註解會報「argocd-update unauthorized」

這是 Kargo 入門最常見的錯誤之一。每個 Application 必須明確聲明被哪個 Stage 授權操作，是 Kargo 的安全模型核心——防止某個 team 的 Stage 意外影響另一個 team 的 Application。多 Stage 對應一個 App：用逗號分隔，如 guestbook-project:staging,guestbook-project:dev。

7.2 Health Check：Stage 反映 Application 狀態

Stage 的 status.health 反映其引用的 Argo CD Application 的 health：

YAML — Stage status 範例
status:
  health:
    # 整體 health（依所有 Application 而定）
    status: Healthy
    argoCDApps:
      - healthStatus:
          status: Healthy
        name: guestbook-staging
        namespace: argocd
        syncStatus:
          revision: 111eaf55aa41f21bb9bb707ba1baa748b83ec51e
          status: Synced

        Warehouse/guestbook:
          images:

💡

Stage health 是 Application health 的聚合

Stage 可能引用多個 Argo CD Application（如「staging」包含 frontend + backend + worker 三個 Application）——Stage health 是所有 Application health 的最差狀態。任何一個 Application Degraded → Stage 整體 Degraded → Freight 在此 Stage 不能 verify 成功。

最佳實踐 Checklist

✅

Kargo 上線 12 項 Checklist

① 從單一 Stage 開始（先驗證 dev Stage 跑通，再加 staging / prod）；② 用 PromotionTask 抽出通用邏輯避免每 Stage 重複；③ 必設 Application 的 authorized-stage 註解（最常見錯誤）；④ Git credentials 用 Secret + 注入 token不要硬編碼 PAT；⑤ verification 用 ClusterAnalysisTemplate（與 Argo Rollouts 共用）；⑥ prod Stage 不設 automatic promotion（用 kargo approve CLI 或 UI 手動）；⑦ 每個服務獨立 Warehouse（避免無關 image 干擾）；⑧ discoveryLimit 設合理值（如 20，避免 Warehouse 載入過多歷史）；⑨ interval 至少 5m避免 image registry rate limit；⑩ monitor Promotion CR（用 metrics + alert 卡住的 promotion）；⑪ 用 UI 視覺化 pipeline讓 dev team 自助操作；⑫ RBAC 限定 Project namespace（每團隊一個 Project）。

📌 Key Takeaways

  • 🎯Kargo 補上 Argo CD 的 promotion 缺口：Argo CD 擅長「Git → Cluster 同步」，但缺乏 first-class 的「跨 Stage 推進」抽象。Kargo 由 Akuity / Argo 團隊打造，引入 promotion engine 概念。不取代 Argo CD，是補上 promotion 層——Kargo 改 GitOps repo，Argo CD 同步到 cluster。
  • 📦三大核心 CRD：① Warehouse（artifact source watcher，監視 registry / Git / Helm chart）；② Freight（不可變的 artifact bundle = image + git commit + chart 組合 snapshot）；③ Stage（environment + promotion logic）。Freight 是 Kargo 最重要的 idea——確保 dev/staging/prod 部署完全一致的版本組合。
  • 🔄Stage 兩種 Freight source：① sources.direct: true（直接從 Warehouse，通常是 pipeline 第一個 Stage 如 dev）；② sources.stages: [dev]（從上游 Stage promote 過來，如 staging 從 dev、prod 從 staging）。形成 DAG pipeline，UI 視覺化跨 Stage 進度。
  • ⚙️promotionTemplate.steps 是 promotion 邏輯核心：內建 step 包含 git-clone / git-clear / kustomize-set-image / helm-update-image / yaml-update / git-commit / git-push / argocd-update。expression 語法：${{ vars.xxx }}、${{ outputs.step_name.output }}、${{ imageFrom(repo, warehouse(name)).Tag }}、${{ ctx.stage }}。
  • 🧩PromotionTask 模組化：把重複的 promotion steps 抽成可重用 Task，Stage 只引用 task.name: standard-promotion 並傳 vars。多 Stage / 多服務共用，platform team 維護 PromotionTask，dev team 只填 Stage vars。變更 promotion 流程改一處即可。
  • ✅Verification 重用 Argo Rollouts 的 AnalysisTemplate（Ch.37）：Kargo 不重新發明 verification，直接用同一 CRD。Ch.37 學的 Prometheus / Datadog / Web / Job providers 通通可用。Verification 失敗 → Freight 在此 Stage 不被標記 verified → 下游 Stage 看不到此 Freight 為可推進。
  • 🔐authorized-stage 註解是 Kargo 安全模型核心：Argo CD Application 必須加 kargo.akuity.io/authorized-stage: <project>:<stage> 才能被 Stage 的 argocd-update step 操作。最常見入門錯誤就是漏設此註解。多 Stage 用逗號分隔。
  • 📊Stage health 是 Application health 的聚合：Stage 可引用多個 Application（如 staging 包含 frontend + backend + worker），任一 Application Degraded → Stage 整體 Degraded → Freight 不能 verify。Stage status 顯示：current freight、verification history、argoCDApps health、freightHistory。
  • ⚖️三方案對比：① Image Updater + 手動（簡單，無 multi-stage 抽象）；② ApplicationSet（模板化建 Application，但無 promotion 順序）；③ Kargo（first-class promotion engine + verification gate + manual approval）。並不互斥——Kargo + ApplicationSet 並用是進階做法。Kargo 目前 Beta，謹慎評估是否 production-ready。
  • ✅12 項 Checklist：從單一 Stage 開始、用 PromotionTask 抽通用邏輯、必設 authorized-stage 註解、Git creds 注入 token、verification 用 ClusterAnalysisTemplate、prod 不設 automatic、每服務獨立 Warehouse、discoveryLimit 設 20、interval ≥ 5m、monitor Promotion CR、UI 視覺化、RBAC 用 namespace。
