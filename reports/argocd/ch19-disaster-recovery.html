災難復原（DR）
與備份還原策略

Vol 3 最後一章。Argo CD 沒有傳統資料庫——所有狀態都是 K8s CRD + ConfigMap + Secret。看似簡單，誤刪 namespace 卻會讓 150+ Application 在數秒內消失。本章建立完整 DR 體系：六大狀態資產盤點、三種備份策略（admin export / Velero / GitOps）、災難情境劇本、跨叢集 DR 部署、Game Day 演練。

📋

前置：已完成 Vol 3 前 7 章。理解 Argo CD CRD 結構（Ch.03）、Self-Managed 架構（Ch.12）、cluster credentials 管理（Ch.16）。

🎯 學習目標

  • 盤點 Argo CD 的六大狀態資產：CRD、Application、AppProject、ConfigMap、Secret、cluster cache
  • 定義組織的 RTO（恢復目標時間）與 RPO（恢復目標點），選擇對應 DR 等級
  • 掌握三種備份策略的優缺點與組合方式：argocd admin export（快）、Velero（全）、GitOps（理想）
  • 建立 argocd admin export 自動化排程腳本
  • 使用 Velero Helm chart 部署完整備份基礎設施（S3 / GCS / Azure Blob backend）
  • 處理三種典型災難情境：誤刪 Application / 誤刪 namespace / 整 cluster 故障
  • 實作主備（active-passive）跨叢集 DR 部署
  • 規劃並執行 DR Game Day 演練（每季一次）

1Argo CD 狀態盤點

Argo CD 不像傳統 CI/CD 工具有 PostgreSQL 或 MongoDB——所有狀態都儲存為 Kubernetes 資源。這是優勢（無外部依賴），也是危險（K8s namespace 一旦消失，所有狀態瞬間蒸發）。先理解什麼需要備份：

1.1 六大狀態資產

📦
CRD 定義
cluster-scoped
applications / appprojects / applicationsets。CRD 一旦刪除，所有 instance 也消失（cascading）。一般升級時自動覆蓋，但意外刪除會清空所有 App。
📋
Application CR
argocd ns
每個 Application 的完整定義（source、destination、syncPolicy）。刪除後，K8s 資源仍在但 Argo CD 失去管理。
🛡️
AppProject CR
argocd ns
RBAC 邊界、source/destination 限制、roles + tokens。失去後安全邊界全消失，所有 App 將無 project 而 sync 失敗。
⚙️
ConfigMaps
argocd ns
argocd-cm（OIDC、tracking）、argocd-rbac-cm（policies）、argocd-cmd-params-cm（performance tuning）、argocd-ssh-known-hosts-cm、argocd-tls-certs-cm。
🔐
Secrets
argocd ns
argocd-secret（admin password、webhook secret、Dex client secret）、cluster credentials、repository credentials。失去後最痛的部分，需重新建立所有外部連線。
💾
Redis Cache
argocd-redis
manifest cache、cluster state cache。不需要備份——揮發性資料，重啟後會自動重建（首次 sync 較慢）。
⚠️

真實案例：3 AM 的 ArgoCD namespace 蒸發

有家公司的新工程師執行清理腳本，誤將 production 的 argocd namespace 一鍵刪除。150+ Application 在數秒內消失。所幸 K8s 中已部署的應用仍在運行（沒有 cascade delete），但 Argo CD 失去了所有「我管的是什麼」的記憶。從備份還原 + GitOps 重建花了 6 小時。如果有自動化備份，這應該是 15 分鐘的事情。

1.2 RTO / RPO 與 DR 等級

名詞定義典型目標值
RTO（Recovery Time Objective）從災難發生到完全恢復服務的最長時間關鍵業務：< 1 小時；一般：4-8 小時
RPO（Recovery Point Objective）可接受的資料遺失時間範圍（最近一次備份後的資料）關鍵業務：< 1 小時；一般：24 小時
MTTR（Mean Time To Recovery）實際平均恢復時間（包含偵測 + 響應 + 恢復）應 ≤ RTO 的 70%
Tier 1 入門級
RTO8-24 小時
RPO24 小時
策略每日 admin export 到 S3 + GitOps 為主
適合學習、demo、單叢集小團隊
Tier 2 標準級
RTO2-4 小時
RPO1-6 小時
策略Velero 排程備份 + 多副本 admin export + GitOps
適合中型生產（500-2000 App）
Tier 3 企業級
RTO< 30 分鐘
RPO< 1 小時
策略主備跨 region + Velero hourly + 自動 failover
適合關鍵業務、金融、多 region 部署

2三種備份策略

2.1 argocd admin export（簡單快速）

面向argocd admin export 特性
原理由 argocd CLI 執行，產出單一 YAML 包含所有 Application、AppProject、ConfigMap、Secret
優點最快設定（5 分鐘）；單一檔案易管理；可整合 cron 排程；版本支援好
缺點單一巨大檔案（生產環境可能 50+ MB）；無增量備份；無自動化保留策略；不含 Redis（不重要）
RPO取決於 cron 頻率，通常 1-24 小時
RTO10-15 分鐘（重新部署 Argo CD + import）

2.2 Velero 整合（全面）

面向Velero 特性
原理K8s 原生備份工具，將 namespace 中的所有資源（含 PV）快照到 S3 / GCS / Azure Blob
優點原子性備份（point-in-time）；增量 / 全量；自動保留策略；跨叢集還原（Argo CD DR 標準做法）
缺點需額外部署 Velero（增加維運複雜度）；需 object storage；恢復速度依資料量
RPO1-6 小時（依排程而定）
RTO30-60 分鐘（依資料量與網路速度）

2.3 GitOps 純宣告式（最理想）

面向GitOps 純宣告式特性
原理所有 Argo CD 設定（Application、Project、ConfigMap、Secret）都在 Git；Self-Managed Argo CD 自動 reconcile
優點Git 天然就是備份；版本控制；無需額外工具；災難時 kubectl apply 一個 root App 即可恢復一切
缺點需 Sealed Secrets / External Secrets 處理敏感資料；初期投入較多時間設計
RPO0（永遠等於 Git 最新狀態）
RTO15-30 分鐘（部署 Argo CD + apply root App）
💡

生產環境推薦組合

主要靠 GitOps（所有設定在 Git，含 SealedSecret 加密的 cluster credentials）+ Velero hourly 備份（保險網，避免 Git 故障時無法恢復）+ argocd admin export 每日（額外副本，存放 off-cluster 儲存）。三層備份大幅降低單點故障。

3argocd admin export 實作

Bash — 自動化備份腳本（CronJob）
#!/bin/bash
# argocd-backup.sh - 每日 02:00 透過 K8s CronJob 執行
set -euo pipefail

# 變數
NAMESPACE="argocd"
DATE=$(date +%Y%m%d-%H%M%S)
BACKUP_NAME="argocd-${DATE}"
BUCKET="s3://my-backups/argocd"

# 1. 取得目前 Argo CD 版本（重要：用同版本還原才不會出錯）
ARGOCD_VERSION=$(kubectl -n $NAMESPACE get deployment argocd-server \
  -o jsonpath='{.spec.template.spec.containers[0].image}' | cut -d: -f2)

# 2. 用對應版本的 Argo CD container 執行 admin export
docker run --rm \
  -v ~/.kube:/home/argocd/.kube \
  quay.io/argoproj/argocd:$ARGOCD_VERSION \
  argocd admin export -n $NAMESPACE \
  > /tmp/${BACKUP_NAME}.yaml

# 3. 額外個別備份關鍵 ConfigMap / Secret（更精細）
kubectl get cm -n $NAMESPACE -o yaml > /tmp/configmaps-${DATE}.yaml
kubectl get secret -n $NAMESPACE -o yaml > /tmp/secrets-${DATE}.yaml
kubectl get crd applications.argoproj.io -o yaml > /tmp/crd-applications-${DATE}.yaml
kubectl get crd appprojects.argoproj.io -o yaml > /tmp/crd-appprojects-${DATE}.yaml

# 4. 打包並加密（敏感資料）
tar -czf /tmp/${BACKUP_NAME}.tar.gz -C /tmp \
  ${BACKUP_NAME}.yaml configmaps-${DATE}.yaml secrets-${DATE}.yaml \
  crd-applications-${DATE}.yaml crd-appprojects-${DATE}.yaml

# 5. SOPS 加密（推薦）或 GPG
sops --encrypt --in-place /tmp/${BACKUP_NAME}.tar.gz

# 6. 上傳到 object storage（保留 90 天）
aws s3 cp /tmp/${BACKUP_NAME}.tar.gz $BUCKET/${BACKUP_NAME}.tar.gz \
  --storage-class STANDARD_IA \
  --metadata "argocd-version=$ARGOCD_VERSION"

# 7. 清理本地暫存
rm /tmp/${BACKUP_NAME}.* /tmp/*-${DATE}.yaml

# 8. 通知（成功 / 失敗）
curl -X POST $SLACK_WEBHOOK -d "{\"text\":\"✅ Argo CD backup completed: ${BACKUP_NAME}\"}"
YAML — K8s CronJob 排程備份
apiVersion: batch/v1
kind: CronJob
metadata:
  name: argocd-backup
  namespace: argocd
spec:
  schedule: "0 2 * * *"      # 每日 02:00 UTC
  timeZone: "Asia/Taipei"      # 1.27+ 支援
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 600   # 10 分鐘超時
      template:
        spec:
          restartPolicy: OnFailure
          serviceAccountName: argocd-backup-sa  # IRSA 設定
          containers:
            - name: backup
              image: quay.io/argoproj/argocd:v3.4.0
              command: ["/bin/sh", "/scripts/argocd-backup.sh"]
              env:
                - name: AWS_REGION
                  value: us-east-1
              volumeMounts:
                - name: backup-script
                  mountPath: /scripts
          volumes:
            - name: backup-script
              configMap:
                name: argocd-backup-script
                defaultMode: 0755

4Velero 完整整合

4.1 Velero Helm 部署

YAML — 透過 Argo CD 部署 Velero
## 把 Velero 也納入 GitOps 管理
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: velero
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://vmware-tanzu.github.io/helm-charts
    chart: velero
    targetRevision: 8.x.x
    helm:
      values: |
        configuration:
          backupStorageLocation:
            - name: default
              provider: aws
              bucket: my-velero-backups
              config:
                region: us-east-1
          volumeSnapshotLocation:
            - name: default
              provider: aws
              config:
                region: us-east-1

        credentials:
          useSecret: false            # 用 IRSA（推薦）

        serviceAccount:
          server:
            annotations:
              eks.amazonaws.com/role-arn: arn:aws:iam::123:role/velero

        initContainers:
          - name: velero-plugin-for-aws
            image: velero/velero-plugin-for-aws:v1.10.0
            volumeMounts:
              - name: plugins
                mountPath: /target

        # 排程備份（透過 Velero 自身 schedules）
        schedules:
          argocd-hourly:
            disabled: false
            schedule: "0 * * * *"     # 每小時
            template:
              ttl: "168h"            # 保留 7 天
              includedNamespaces:
                - argocd
              defaultVolumesToFsBackup: false

          argocd-daily:
            disabled: false
            schedule: "0 3 * * *"     # 每日 03:00
            template:
              ttl: "720h"            # 保留 30 天
              includedNamespaces:
                - argocd

  destination:
    server: https://kubernetes.default.svc
    namespace: velero
  syncPolicy:
    automated: {prune: true, selfHeal: true}
    syncOptions: [CreateNamespace=true]

4.2 手動備份與還原

Bash — Velero 備份還原指令集
## ── 列出所有備份 ────────────────────────────────────
$ velero backup get

## ── 立即備份（手動）─────────────────────────────────
$ velero backup create argocd-pre-upgrade-$(date +%Y%m%d) \
    --include-namespaces argocd \
    --ttl 720h

## ── 檢查備份內容 ────────────────────────────────────
$ velero backup describe argocd-daily-20260509-030000 --details

## ── 還原整個 argocd namespace ───────────────────────
$ velero restore create argocd-restore-$(date +%s) \
    --from-backup argocd-daily-20260509-030000 \
    --include-namespaces argocd

## ── 只還原特定 Application（精細）──────────────────
$ velero restore create my-app-restore \
    --from-backup argocd-daily-20260509-030000 \
    --include-namespaces argocd \
    --include-resources applications.argoproj.io \
    --selector "metadata.name=my-app"

## ── 跨叢集還原（DR 主備切換）──────────────────────
## 1. 在 DR cluster 部署 Velero（指向同 S3 bucket）
## 2. Velero 自動同步 BackupStorageLocation
## 3. 在 DR cluster 執行 restore：
$ velero restore create argocd-dr-failover \
    --from-backup argocd-hourly-20260509-100000 \
    --include-namespaces argocd
⚠️

Velero 備份不含 PVC 預設行為

Argo CD 不使用 PVC（Redis 為揮發性 cache），所以這不是問題。但若部署了 PVC（如 backup of own GitLab），需設定 defaultVolumesToFsBackup: true 或對該 PVC 加 annotation backup.velero.io/backup-volumes。Argo CD 自身設定不需要。

5三種典型災難情境劇本

5.1 情境 1：Application 誤刪

情境：開發者 kubectl delete app my-app -n argocd 後才發現是 production App。

影響：Argo CD 從此不管理該 App，但已部署的 K8s 資源仍在運行（除非有 finalizer + cascade delete）。

🔴 復原步驟（5-10 分鐘）
1
從 Git 還原（最簡單）：若 Application 是宣告式定義在 Git，直接 kubectl apply -f apps/my-app.yaml -n argocd。Argo CD 重新建立後會偵測到已存在的 K8s 資源並 adopt。
2
從 Velero 還原：velero restore create my-app-restore --from-backup argocd-hourly-20260509-100000 --selector metadata.name=my-app --include-resources applications.argoproj.io
3
從 admin export 還原：用 jq 從備份 yaml 抽出指定 App，jq '.items[] | select(.kind == "Application" and .metadata.name == "my-app")' < backup.yaml | kubectl apply -f -
4
觸發 sync 確認：argocd app sync my-app。Argo CD 偵測到 K8s 中的 Service / Deployment 已存在，會 adopt 並繼續管理。

5.2 情境 2：argocd namespace 整個誤刪

情境：清理腳本誤刪 argocd ns，所有 Application、AppProject、ConfigMap、Secret 一併消失。

影響：Argo CD 全面停止運作，所有 GitOps 中斷。已部署的應用仍在運行，但無法觀察、sync 或自動修復。

🔴🔴 復原步驟（30-60 分鐘）
1
重新建立 namespace + 安裝 Argo CD：kubectl create namespace argocd; helm install argocd argo/argo-cd ...（用既有 helm values）
2
從 Velero 還原（推薦）：velero restore create argocd-disaster-recovery --from-backup argocd-hourly-LATEST --include-namespaces argocd。Velero 會還原所有 ConfigMap、Secret、Application 等。注意：必須等 Argo CD 元件 Ready 後再 restore，否則 CRD 物件無法被處理。
3
或從 admin export 還原：argocd admin import - < backup.yaml。會將 Application、AppProject、ConfigMap、Secret 全部寫回。
4
純 GitOps 還原（最理想）：若有 self-managed Argo CD，只需 kubectl apply -f bootstrap/root-app.yaml，root App 自動拉取所有 Application + Project + Config 到 Git 中的最新狀態。
5
驗證：所有 Application 從 OutOfSync 變回 Synced（K8s 中的舊資源被 adopt）。argocd app list | grep -v "Synced.*Healthy" 應為空。

5.3 情境 3：整個 Cluster 故障（region 級災難）

情境：AWS us-east-1 全 region 故障，Argo CD management cluster 無法存取。所有 spoke cluster 失去管控。

🔴🔴🔴 復原步驟（< 30 分鐘 with active-passive）
1
確認災難範圍：是 Argo CD 故障 vs spoke cluster 故障 vs 整 region 故障。若只是 Argo CD 故障，spoke 上的應用仍在跑（但 GitOps 暫停）。
2
啟用 DR cluster：在備援 region 已預先部署 passive Argo CD（見第 6 節）。透過 Velero restore 從共享 S3 bucket 取得最新備份。
3
切換 DNS：將 argocd.example.com 從 us-east-1 切到 us-west-2。Route53 health check + failover routing policy 可自動化。
4
停用 active 端避免雙寫：DR Argo CD 接管後，原 cluster 一旦恢復，必須先停用其 application-controller（scale to 0），避免兩個 Argo CD 同時操作同 spoke cluster。
5
反向還原（事故結束後）：將 DR cluster 的最新備份還原回原 region，再切換 DNS 回去。

6主備（Active-Passive）跨叢集 DR 部署

關鍵業務環境（Tier 3）建議部署主備架構：

Architecture — Active-Passive DR 拓撲
┌─────────────────────────────────────────────────────────┐
│  Region A: us-east-1 (Active)                            │
│  ┌──────────────────────────────────────────────────┐    │
│  │  Argo CD (Active)                                │    │
│  │  - 完整功能運作                                  │    │
│  │  - Velero hourly backup → S3                     │    │
│  └──────────────────────────────────────────────────┘    │
│        ▼                                                  │
│  ┌──────────────────────────────────────────────────┐    │
│  │  Spoke Clusters (us-east-1, eu-west-1, ...)     │    │
│  │  目前由 Region A 的 Argo CD 管理                │    │
│  └──────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────┘
                       │
                       │ Velero 備份共享 S3 bucket
                       │ (Cross-region replication)
                       ▼
┌─────────────────────────────────────────────────────────┐
│  Region B: us-west-2 (Passive / Standby)                 │
│  ┌──────────────────────────────────────────────────┐    │
│  │  Argo CD (Passive, deployed but not managing)   │    │
│  │  - 已部署但 application-controller scale=0      │    │
│  │  - AppProject 設定 sync-window deny（防誤啟動） │    │
│  │  - 持續從 S3 拉取 Velero backup                 │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  災難發生時：                                            │
│  ① velero restore from latest backup                     │
│  ② kubectl scale --replicas=2 application-controller     │
│  ③ 移除 AppProject 的 sync-window deny                   │
│  ④ 切換 Route53 DNS                                      │
└─────────────────────────────────────────────────────────┘
YAML — Passive cluster 防雙寫設定
## 在 passive cluster 的 AppProject 加入 deny syncWindow
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: default
  namespace: argocd
spec:
  # 永久 deny window，防止 passive controller 誤啟動 sync
  syncWindows:
    - kind: deny
      schedule: "* * * * *"      # 每分鐘都 deny
      duration: 24h
      applications: ['*']
      manualSync: false
      timeZone: UTC

## DR failover 時，刪除這個 syncWindow 即啟用 sync 能力
ℹ️

Red Hat ACM + OADP 是企業級方案

Red Hat Advanced Cluster Management（ACM）提供類似 Argo CD 的多 cluster 管理能力，搭配 OADP（OpenShift API for Data Protection）+ Velero 提供完整的 DR 解決方案。OpenShift GitOps 場景推薦此組合。社群版 K8s 用戶可參考其架構，自行用 Velero + ExternalDNS + Route53 health check 實現類似機制。

7DR 演練（Game Day）— 每季一次

沒有演練過的 DR 計畫等於沒有 DR。建議每季執行一次完整演練（在 staging cluster），模擬災難並計時 RTO：

Bash — Game Day 演練腳本
## ═══════════════════════════════════════════════
## DR Game Day Playbook (在 staging cluster 執行)
## ═══════════════════════════════════════════════

## ── Phase 1: 演練前準備（30 分鐘前）─────────────────
# 1. 通知所有相關團隊（避免誤判為真實事故）
# 2. 記錄當前狀態（基準線）
$ argocd app list | wc -l    # 紀錄 Application 數量
$ kubectl get crd applications.argoproj.io -o yaml > pre-disaster-snapshot.yaml

## ── Phase 2: 模擬災難（記錄 T0）──────────────────────
$ T0=$(date +%s)

# 災難場景：刪除整個 argocd namespace（最嚴重）
$ kubectl delete namespace argocd --grace-period=0 --force

# 確認災難（所有 App 應該消失）
$ kubectl get applications -A 2>&1 | head
# Error: applications.argoproj.io not found（CRD 也被刪除）

## ── Phase 3: 復原（記錄 T1, T2, T3）─────────────────
# 3a. 重新建立 namespace
$ kubectl create namespace argocd
$ T1=$(date +%s)

# 3b. 重新部署 Argo CD（用既有 helm values）
$ helm upgrade --install argocd argo/argo-cd \
    --version 7.5.0 -n argocd \
    --values argocd-values.yaml --wait
$ T2=$(date +%s)

# 3c. 從 Velero 還原
$ velero restore create gameday-$(date +%s) \
    --from-backup argocd-hourly-LATEST \
    --include-namespaces argocd \
    --wait
$ T3=$(date +%s)

# 3d. 等待所有 Application 變 Healthy
$ while [ $(argocd app list -o json | jq '[.[] | select(.status.health.status != "Healthy")] | length') -gt 0 ]; do
    sleep 10
  done
$ T4=$(date +%s)

## ── Phase 4: 計算 RTO 與驗證 ──────────────────────────
$ echo "=== DR Game Day Results ==="
$ echo "Namespace recreation: $((T1-T0))s"
$ echo "Argo CD redeployment: $((T2-T1))s"
$ echo "Velero restore: $((T3-T2))s"
$ echo "All apps Healthy: $((T4-T3))s"
$ echo "Total RTO: $((T4-T0))s"

# 驗證：Application 數量應該與災難前相同
$ argocd app list | wc -l    # 比對基準線

## ── Phase 5: 演練覆盤 ─────────────────────────────────
# 1. RTO 是否符合 SLA？（target: < 30 minutes for Tier 3）
# 2. 哪一步最慢？是否可以優化？
# 3. 過程中有沒有發現備份遺漏的資源？
# 4. runbook 文件是否完整正確？
# 5. 通知機制是否運作？
💡

Game Day 的關鍵指標

① RTO 達標率：實測恢復時間 vs SLA 目標；② 資料完整性：恢復後 Application 數量 / Project 數量是否與災難前一致；③ 意外發現：每次演練都會發現一些備份遺漏（如新加的 ConfigMap 沒被備份），更新備份清單；④ Runbook 改進：將實際遇到的問題寫進 runbook，下次更快。

📌 Key Takeaways

  • 📦六大狀態資產：CRD、Application、AppProject、ConfigMap、Secret 必須備份；Redis 不需要（揮發性 cache）。Secret 是失去後最痛的部分（含 cluster credentials、repo credentials）。
  • 🎯定義 RTO / RPO 才能規劃 DR 等級：Tier 1（24h RTO）每日 admin export；Tier 2（4h RTO）Velero hourly；Tier 3（30min RTO）主備跨 region。先談清楚預期，再選擇對應方案。
  • 🛡️三種策略應該疊加，不是擇一：① GitOps 是主要（Git 永遠最新）；② Velero hourly 是保險網（Git 故障時的後援）；③ admin export 每日存 off-cluster（額外副本）。三層備份大幅降低單點故障風險。
  • ⚠️誤刪 namespace 是真實風險：清理腳本 + 過寬 RBAC 已導致多家公司 6+ 小時 outage。argocd ns 應該設定為禁刪（finalizer 或 admission webhook），所有 cleanup 腳本都要 dry-run + namespace allow-list。
  • 🔄Active-Passive 跨叢集 DR 是 Tier 3 標配：passive cluster 預先部署 + scale=0 + AppProject deny syncWindow，避免雙寫。Velero cross-region replication 共享 S3，DR failover 為「scale up + 移除 syncWindow + DNS 切換」。
  • 🧪每季 Game Day 演練：沒有演練過的 DR 計畫等於沒有。在 staging 模擬災難，計時 RTO，驗證資料完整性。每次演練都會發現備份遺漏 / runbook 缺漏，持續改進。
