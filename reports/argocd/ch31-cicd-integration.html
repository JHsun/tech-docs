與 CI/CD 整合
GitHub Actions、GitLab CI、image promotion

Vol 6 最後一章。Argo CD 是 CD 元件，但完整的 CI/CD pipeline 需要 CI（build、test、push image）與 CD（Argo CD sync）的整合。本章涵蓋三種整合模式（GitOps push、API trigger、Image Updater）、CI service account 建立、GitHub Actions / GitLab CI 完整範例、image promotion 跨環境（dev → staging → prod）含手動 approval、PR preview environment 整合、十大常見反模式。完成本章後你會有可立即用於生產的 CI/CD pipeline 範本。

📋

前置：已完成 Vol 1-5 + Ch.28-30。理解 GitHub Actions 或 GitLab CI 基本語法。理解 Application + AppProject + Project Role（Ch.21）。理解 Image Updater（Ch.30）作為替代方案。

🎯 學習目標

  • 理解 CI 與 CD 的職責分離原則：CI 負責 build/test/push image + 更新 Git；CD（Argo CD）負責從 Git sync 到 K8s
  • 掌握三種整合模式：① GitOps push（最 GitOps）；② argocd CLI API trigger；③ Image Updater（自動偵測）
  • 遵循 App repo 與 GitOps repo 分離原則（two-repo pattern），理解單 repo 反模式的問題
  • 建立 dedicated CI service account（local user 或 SSO），用 Project Role 限制最小權限，產生 token
  • 實作完整 GitHub Actions workflow：build image → push GHCR → update GitOps repo → argocd app wait
  • 實作完整 GitLab CI .gitlab-ci.yml：四階段 pipeline（build / push / deploy / verify）
  • 建立 image promotion pipeline：dev 自動 → staging 自動 → prod 手動 approval
  • 用 PR-based workflow 為每個 PR 建立 preview environment（含 cleanup）
  • 避開十大反模式：CI 直接 kubectl apply、用 admin token、不 wait health、token 過寬等
  • 掌握 argocd app wait --sync --health 的關鍵性（光 sync 完成不代表健康）

1CI vs CD 職責分離

1.1 三種整合模式

模式誰更新 image tag誰觸發 sync純度
1. GitOps push CI commit 到 GitOps repo Argo CD 自動偵測（auto-sync） ★★★ 最 GitOps
2. argocd CLI trigger CI commit + argocd CLI CI 中 argocd app sync 主動觸發 ★★ 折衷
3. Image Updater Image Updater controller Argo CD 自動偵測 ★★★ CI / CD 完全解耦
💡

選用建議

① 純 GitOps + Helm/Kustomize → Image Updater（CI 完全不碰 Git）；② 純 GitOps + 想自己控制流程 → 模式 1（CI 用 PAT push GitOps repo，Argo CD auto-sync）；③ 想 CI 知道部署完成才結束 → 模式 2（用 argocd CLI 主動 sync + wait）；④ App 與 GitOps 在同一 repo → 不推薦（見下節）。

1.2 App repo + GitOps repo 分離（two-repo pattern）

Tree — 兩個獨立 repo
## App Repo: myorg/my-app（程式碼）
my-app/
├── src/                     # 應用程式碼
├── Dockerfile
├── tests/
└── .github/workflows/
    ├── ci.yml               # 觸發：push to main
    └── update-gitops.yml    # 觸發：ci.yml 完成後

## GitOps Repo: myorg/k8s-gitops（K8s manifest）
k8s-gitops/
├── apps/
│   └── my-app/
│       ├── base/            # Kustomize base
│       └── overlays/
│           ├── dev/
│           │   └── kustomization.yaml    # images: 由 CI 自動更新
│           ├── staging/
│           │   └── kustomization.yaml
│           └── production/
│               └── kustomization.yaml
└── argocd/
    └── applications.yaml    # Argo CD Application 定義
⚠️

反模式：app 與 GitOps 在同一 repo

常見的「monorepo 把 manifest 跟程式碼放一起」做法，會造成：① CI 修改 GitOps 部分觸發 Argo CD 重新偵測 + 觸發另一次 CI（無限迴圈）；② 無法區分 dev / DevOps 權限（兩種變更權限混在一起）；③ Pipeline 複雜（要區分到底是程式碼變更還是 manifest 變更）。用 [skip ci] 在 commit message 是 hack，不是解法——two-repo 是長期穩定的設計。

2準備：CI Service Account

讓 CI 安全地呼叫 argocd API，需要 dedicated service account（不是個人 admin token）：

2.1 建立 ci-bot local account

YAML — 建立 local CI account
## argocd-cm 加入新 account
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 建立 ci-bot account，只能透過 apiKey（不能登入 UI）
  accounts.ci-bot: apiKey
  # 可選：standby disable
  accounts.ci-bot.enabled: "true"

## 套用後產生 token：
## $ argocd account generate-token --account ci-bot --id ci-bot-prod-2026
## eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
## 將 token 存到 CI 系統的 secret（GITHUB_SECRETS / GitLab CI variables）

2.2 用 Project Role 限制最小權限

YAML — Project Role 限定 sync 權限
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: my-team
spec:
  roles:
    # CI bot 只能 sync 本 project 的 application（不能修改 spec）
    - name: ci-deploy
      policies:
        - p, proj:my-team:ci-deploy, applications, get, my-team/*, allow
        - p, proj:my-team:ci-deploy, applications, sync, my-team/*, allow
        - p, proj:my-team:ci-deploy, applications, action/*, my-team/*, allow
        # 不允許 update / delete / override
      groups:
        - ci-bot      # 對應到上面的 local account

## 產生 project-scope token（推薦——權限更細）
## $ argocd proj role create-token my-team ci-deploy --id ci-deploy-prod-2026
##
## Project-scope token 只對該 project 的 application 有效
## 即使 token 洩漏，blast radius 限定在這個 project
💡

Project Role token vs Local account token

① Project Role token（推薦）：權限限定在單一 project；token id 在 token 中明確記錄；可在 UI 一鍵 revoke；② Local account token：用全域 RBAC（argocd-rbac-cm）控制權限；適合需要跨 project 操作的 CI。多數情況用 Project Role token——對單一 team / project 的 CI 最安全。

3GitHub Actions 完整範例

3.1 App repo：build + push image

YAML — .github/workflows/ci.yml（app repo）
name: CI
on:
  push:
    branches: [main]
env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write      # GHCR 需要
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
      image-sha: ${{ steps.short-sha.outputs.sha }}
    steps:
      - uses: actions/checkout@v4

      # 用前 7 碼 SHA 當 image tag（immutable）
      - name: Get short SHA
        id: short-sha
        run: echo "sha=${GITHUB_SHA::7}" >> $GITHUB_OUTPUT

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Build & Push（含 cache 加速）
      - name: Build and push
        id: meta
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ steps.short-sha.outputs.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

      # 觸發下一個 workflow 更新 GitOps repo
      - name: Trigger GitOps update
        uses: peter-evans/repository-dispatch@v3
        with:
          token: ${{ secrets.GITOPS_TOKEN }}
          repository: myorg/k8s-gitops
          event-type: update-image
          client-payload: |
            {
              "app": "my-app",
              "env": "dev",
              "image_tag": "${{ steps.short-sha.outputs.sha }}",
              "repo": "${{ github.repository }}",
              "sha": "${{ github.sha }}"
            }

3.2 GitOps repo：接收 dispatch + 更新 manifest

YAML — .github/workflows/update-image.yml（GitOps repo）
name: Update Image
on:
  repository_dispatch:
    types: [update-image]

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          token: ${{ secrets.GITOPS_TOKEN }}

      - name: Install kustomize
        run: |
          curl -sLO https://github.com/kubernetes-sigs/kustomize/releases/download/kustomize%2Fv5.3.0/kustomize_v5.3.0_linux_amd64.tar.gz
          tar -xzf kustomize_v5.3.0_linux_amd64.tar.gz
          sudo mv kustomize /usr/local/bin/

      # 更新 dev 環境的 image tag
      - name: Update image tag
        run: |
          cd apps/${{ github.event.client_payload.app }}/overlays/${{ github.event.client_payload.env }}
          kustomize edit set image \
            ghcr.io/${{ github.event.client_payload.repo }}=\
            ghcr.io/${{ github.event.client_payload.repo }}:${{ github.event.client_payload.image_tag }}

      # Commit + push
      - name: Commit and push
        run: |
          git config user.name "argocd-ci-bot"
          git config user.email "ci-bot@example.com"
          git add .
          git diff --staged --quiet || \
            git commit -m "chore(${{ github.event.client_payload.env }}): deploy ${{ github.event.client_payload.app }} ${{ github.event.client_payload.image_tag }}

          Triggered by: ${{ github.event.client_payload.repo }}@${{ github.event.client_payload.sha }}"
          git push

3.3 等待 sync + health（關鍵！）

YAML — 加入 argocd app wait（CI 知道部署完成）
## 在 update-image.yml 末尾加入：
      - name: Install ArgoCD CLI
        run: |
          curl -sL https://github.com/argoproj/argo-cd/releases/latest/download/argocd-linux-amd64 \
            -o /usr/local/bin/argocd
          chmod +x /usr/local/bin/argocd

      - name: Wait for Argo CD sync & health
        env:
          ARGOCD_SERVER: argocd.example.com
          ARGOCD_AUTH_TOKEN: ${{ secrets.ARGOCD_TOKEN }}      # Project Role token
        run: |
          # 觸發 refresh（讓 Argo CD 立刻偵測新 commit）
          argocd app get my-team/my-app-dev --refresh --grpc-web

          # 等待 sync 完成 AND health 通過（300 秒 timeout）
          argocd app wait my-team/my-app-dev \
            --sync --health --timeout 300 --grpc-web

          # 如果 wait 失敗，dump diagnostic info
          if [ $? -ne 0 ]; then
            echo "::error::Deployment failed"
            argocd app get my-team/my-app-dev --grpc-web
            exit 1
          fi

      - name: Notify success
        if: success()
        run: echo "✅ Deployed ${{ github.event.client_payload.app }} to dev"
⚠️

必設 --sync --health（不只 --sync）

argocd app wait --sync 只等 sync 完成（manifest 已 apply）——但 Pod 可能 ImagePullBackOff、Service 還在等 endpoint。必加 --health 等待 Healthy 才能確認真正部署成功。生產 CI 都應該用 --sync --health --timeout 300 三者並用。

4GitLab CI 完整範例

YAML — .gitlab-ci.yml 四階段 pipeline
stages:
  - test
  - build
  - deploy-dev
  - verify

variables:
  IMAGE_NAME: "$CI_REGISTRY_IMAGE"
  IMAGE_TAG: "$CI_COMMIT_SHORT_SHA"
  ARGOCD_SERVER: "argocd.example.com"
  APP_NAME: "my-team/my-app-dev"

## ─── 1. Test ─────────────────────────────────────────────
test:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

## ─── 2. Build & Push to GitLab Registry ─────────────────
build:
  stage: build
  image: docker:24
  services: [docker:24-dind]
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG -t $IMAGE_NAME:latest .
    - docker push $IMAGE_NAME:$IMAGE_TAG
    - docker push $IMAGE_NAME:latest
  only:
    - main

## ─── 3. Update GitOps repo + trigger sync ───────────────
deploy-dev:
  stage: deploy-dev
  image: alpine:3.19
  environment:
    name: dev
    url: https://dev.example.com
  before_script:
    # 安裝必要工具
    - apk add --no-cache git curl
    - curl -sSL -o /usr/local/bin/kustomize https://github.com/kubernetes-sigs/kustomize/releases/latest/download/kustomize_linux_amd64
    - chmod +x /usr/local/bin/kustomize
    - curl -sSL -o /usr/local/bin/argocd https://github.com/argoproj/argo-cd/releases/latest/download/argocd-linux-amd64
    - chmod +x /usr/local/bin/argocd
  script:
    # Clone GitOps repo（用 dedicated bot account 的 token）
    - git config --global user.email "ci-bot@example.com"
    - git config --global user.name "GitLab CI Bot"
    - git clone https://oauth2:$GITOPS_TOKEN@gitlab.com/myorg/k8s-gitops.git
    - cd k8s-gitops/apps/my-app/overlays/dev

    # Update image tag
    - kustomize edit set image $IMAGE_NAME=$IMAGE_NAME:$IMAGE_TAG

    # Commit + push（[skip ci] 避免無限迴圈）
    - git add .
    - git diff --staged --quiet || git commit -m "Deploy $CI_COMMIT_SHORT_SHA to dev [skip ci]"
    - git push

    # 觸發 Argo CD 立刻偵測（不等 polling）
    - argocd login $ARGOCD_SERVER --auth-token $ARGOCD_TOKEN --grpc-web
    - argocd app get $APP_NAME --refresh --grpc-web

    # 等待 sync + health
    - argocd app wait $APP_NAME --sync --health --timeout 300 --grpc-web
  only:
    - main

## ─── 4. Verify（smoke test）─────────────────────────────
verify:
  stage: verify
  image: alpine:3.19
  before_script: [apk add --no-cache curl]
  script:
    # Smoke test：確認 endpoint 回 200
    - curl -fsSL https://dev.example.com/health || exit 1
    - echo "✅ Dev deployment verified"
  only:
    - main
ℹ️

[skip ci] 與 only/except 配合

GitOps repo 與 App repo 分離時，CI bot push 到 GitOps repo 不應該再觸發 GitOps repo 的 pipeline——避免無限迴圈。commit message 加 [skip ci]（GitLab）或 [skip actions]（GitHub）。也可以用 GitLab Push Rules + GitHub Path filters 精準控制觸發條件。

5Image Promotion 跨環境

從 dev → staging → prod 推進是真實 CI/CD 的核心場景。完整 pipeline：

5.1 dev 自動 → staging 自動 → prod 手動

YAML — GitHub Actions promotion workflow
# .github/workflows/promote.yml
name: Promote
on:
  workflow_dispatch:
    inputs:
      from_env:
        description: "Source environment"
        required: true
        type: choice
        options: [dev, staging]
      to_env:
        description: "Target environment"
        required: true
        type: choice
        options: [staging, production]
      app:
        description: "Application name"
        required: true

jobs:
  promote:
    runs-on: ubuntu-latest
    # 重點：production 需要 manual approval（GitHub Environment 設定）
    environment: ${{ github.event.inputs.to_env }}
    steps:
      - uses: actions/checkout@v4
        with:
          repository: myorg/k8s-gitops
          token: ${{ secrets.GITOPS_TOKEN }}

      # 從 source env 抓當前 image tag
      - name: Get current image tag
        id: current
        run: |
          cd apps/${{ github.event.inputs.app }}/overlays/${{ github.event.inputs.from_env }}
          TAG=$(grep -A1 "newTag" kustomization.yaml | tail -1 | awk '{print $2}')
          echo "tag=$TAG" >> $GITHUB_OUTPUT

      # Promote 到 target env
      - name: Promote image tag
        run: |
          cd apps/${{ github.event.inputs.app }}/overlays/${{ github.event.inputs.to_env }}
          kustomize edit set image ghcr.io/myorg/${{ github.event.inputs.app }}=ghcr.io/myorg/${{ github.event.inputs.app }}:${{ steps.current.outputs.tag }}

      - name: Commit and push
        run: |
          git config user.name "argocd-promote-bot"
          git config user.email "promote-bot@example.com"
          git add .
          git commit -m "promote: ${{ github.event.inputs.app }} ${{ steps.current.outputs.tag }} to ${{ github.event.inputs.to_env }}"
          git push

      - name: Wait for Argo CD
        run: |
          argocd login $ARGOCD_SERVER --auth-token $TOKEN --grpc-web
          argocd app wait my-team/${{ github.event.inputs.app }}-${{ github.event.inputs.to_env }} \
            --sync --health --timeout 600 --grpc-web
        env:
          ARGOCD_SERVER: argocd.example.com
          TOKEN: ${{ secrets.ARGOCD_TOKEN }}

5.2 GitHub Environment + Required Reviewers（手動 approval）

Settings — GitHub Environment 設定
## 在 GitHub repo Settings → Environments 建立 environment：
##
## Environment: production
##   ✓ Required reviewers: @platform-team, @security-team（兩位 approver）
##   ✓ Wait timer: 5 min（避免太快點下去）
##   ✓ Deployment branches: main only
##
## Environment: staging
##   ✓ Required reviewers: @team-leads（一位即可）
##   ✓ Deployment branches: main only
##
## Environment: dev
##   不需 review（自動推進）

## 觸發後流程：
## 1. dev → staging：自動，CI 完成即推進到 staging
## 2. staging → production：
##    a. 工程師在 GitHub Actions 點 Run workflow 選 production
##    b. GitHub 通知 @platform-team @security-team
##    c. Approver 在 GitHub UI 點 "Approve"
##    d. Wait timer 5 min 結束後
##    e. Workflow 執行 promote + argocd sync
💡

用 GitHub Environment 取代自製 approval flow

GitHub Environment 提供成熟的 manual approval 機制：required reviewers、wait timer、deployment branches limit、environment secrets。不要自己寫 if/else 等 approval（如查詢 Slack message、自製 webhook）——GitHub Environment 直接整合 audit log、SAML SSO、required reviewer 規則。GitLab 也有對應的 manual job 與 protected environments。

6PR Preview Environment

Ch.25 介紹過 Pull Request generator，這裡示範整合 GitHub Actions CI 與 ApplicationSet PR generator 的完整流程：

YAML — GitHub Actions PR Preview workflow
name: PR Preview
on:
  pull_request:
    types: [opened, synchronize, reopened, labeled]

jobs:
  build-preview:
    # 只有加上 "preview" label 的 PR 才執行
    if: contains(github.event.pull_request.labels.*.name, 'preview')
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      pull-requests: write      # 為了留言 preview URL
    steps:
      - uses: actions/checkout@v4

      # Build image with PR-{number} tag
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build & Push PR image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:pr-${{ github.event.pull_request.number }}

      # 留言到 PR：preview URL（ApplicationSet PR generator 已自動建環境）
      - name: Comment PR with preview URL
        uses: actions/github-script@v7
        with:
          script: |
            const prNumber = context.issue.number;
            const previewUrl = `https://pr-${prNumber}.preview.example.com`;
            const argocdUrl = `https://argocd.example.com/applications/preview-pr-${prNumber}`;

            // 找之前的 preview comment（更新而非重複留言）
            const comments = await github.rest.issues.listComments({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: prNumber
            });
            const existing = comments.data.find(c =>
              c.user.login === 'github-actions[bot]' &&
              c.body.includes('🚀 Preview environment')
            );

            const body = `🚀 **Preview environment is being prepared!**

            | | |
            |---|---|
            | 🌐 URL | [${previewUrl}](${previewUrl}) |
            | 🛠️ Argo CD | [${argocdUrl}](${argocdUrl}) |
            | 📦 Image | \`pr-${prNumber}\` |
            | ⏱️ ETA | ~2 min |

            Updated at ${new Date().toISOString()}`;

            if (existing) {
              await github.rest.issues.updateComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                comment_id: existing.id,
                body
              });
            } else {
              await github.rest.issues.createComment({
                owner: context.repo.owner,
                repo: context.repo.repo,
                issue_number: prNumber,
                body
              });
            }

配合 Ch.25 的 ApplicationSet PR generator（labels: [preview]），完整流程：

1
Dev 開 PR，加上 preview label
2
CI 偵測 label，build image with tag pr-123，push 到 GHCR
3
ApplicationSet PR generator 每 60 秒 polling，發現新 PR
4
Argo CD 自動建立 Application preview-pr-123 → namespace preview-pr-123
5
CI 在 PR 留言含 preview URL 與 Argo CD link
6
Reviewer 點開測試 → approve 或 request changes
7
PR merge / close → ApplicationSet 自動刪除 Application + namespace cascade 清理

8十大常見反模式

反模式問題正確做法
1. CI 直接 kubectl apply 跳過 Argo CD，Git 與 cluster 不一致；無 audit trail CI 只 commit Git，Argo CD 負責 apply
2. CI 用 admin token blast radius 過大，token 洩漏災難性 用 Project Role token（限定單一 project + 只允許 sync）
3. 不 wait health argocd app sync 完成不代表 healthy；image pull 失敗也算 sync 完成 必加 argocd app wait --sync --health --timeout 300
4. CI sync + Application 也 auto-sync 兩邊競爭，可能 race condition + double sync 選一個：CI sync 時 disable auto-sync，或全部用 auto-sync
5. App 與 GitOps 同 repo 無限迴圈、權限混淆、pipeline 複雜 two-repo pattern（app repo + GitOps repo）
6. CI 用 argocd app set 改 spec 偏離 GitOps（spec 從 CI 改而非 Git） 只 commit Git，argocd app set 只允許 image tag 例外（最好不用）
7. 用 latest tag 無 immutability，相同 latest 在不同時間是不同 image 用 short SHA / SemVer tag
8. token 儲存在 app repo repo 公開化或洩漏時 token 也洩漏 用 GitHub Secrets / GitLab CI variables / Vault
9. sync 時跳過 sync window 違反 AppProject 的時段限制（如 prod 禁止上班時段 sync） CI 先檢查 sync window：argocd app get --output json | jq .syncWindows
10. 用 Argo CD rollback 而非 git revert cluster 與 Git 不一致，下次 sync 又會被覆蓋回去 用 git revert 在 GitOps repo 推進回滾
⚠️

反模式 #4 細節：CI sync vs auto-sync 衝突

常見情境：CI 用 argocd app sync 觸發，但 Application 也設定 automated: {prune: true, selfHeal: true}——兩邊可能同時 sync 造成 race。建議：① 純 GitOps Push 模式：用 auto-sync，CI 不 sync；② argocd CLI Trigger 模式：CI sync 時禁用 auto-sync（避免雙重 trigger）；③ 折衷：auto-sync 但 CI 加 wait 等 Argo CD 自己處理（不主動觸發 sync）。

📌 Key Takeaways

  • ⚖️CI / CD 職責分離：CI 負責 build/test/push image + 更新 Git；CD（Argo CD）負責從 Git sync 到 K8s。CI 永遠不直接 kubectl apply——這是 GitOps 的核心原則。
  • 🔀三種整合模式：① GitOps Push（CI commit Git，Argo CD auto-sync，最純 GitOps）；② argocd CLI Trigger（CI 主動 sync + wait，最強控制）；③ Image Updater（完全解耦，僅限 Helm/Kustomize）。實務常組合：dev 用 Image Updater、staging 用 GitOps Push、prod 用 CLI Trigger + manual approval。
  • 📦Two-repo pattern 是長期穩定的設計：app repo（程式碼）與 GitOps repo（K8s manifest）分離。同 repo 會造成無限迴圈、權限混淆、pipeline 複雜——[skip ci] 是 hack 不是解。
  • 🔐CI service account 用 Project Role token：建立 dedicated ci-bot account + Project Role 限定權限（只允許 sync 本 project 的 Application）。不要用 admin token，blast radius 過大。Project Role token 在 UI 一鍵 revoke，比 local account token 更易管理。
  • ⏳必設 argocd app wait --sync --health：光 sync 完成不代表健康。Pod ImagePullBackOff、Service 無 endpoint 都算 sync 完成。生產 CI 必用 --sync --health --timeout 300 三者並用。失敗時 dump diagnostic info（argocd app get）方便除錯。
  • 🚀Image promotion pipeline 設計：dev 自動 → staging 自動（CI 完成即推進）→ production 手動 approval。用 GitHub Environment / GitLab Protected Environment取代自製 approval flow——提供 required reviewers、wait timer、deployment branches limit、environment secrets 等成熟功能。
  • 🎫PR Preview 完整流程：① PR 加 preview label；② CI build pr-{number} image；③ ApplicationSet PR generator polling 偵測；④ Argo CD 建 preview-pr-{number}；⑤ CI 在 PR 留言 preview URL；⑥ PR close → 自動清理。留言用 actions/github-script 更新既有 comment而非重複留言（避免 PR 充滿 bot 訊息）。
  • ⚡Git webhook + argocd refresh 加速偵測：① 設定 Git provider webhook 到 https://argocd.example.com/api/webhook（一勞永逸）；② CI 中 argocd app get --refresh（即時觸發，保險）。兩者並用：webhook 是日常路徑，refresh 是 CI 觸發時的明確 trigger。
  • 🚫十大反模式：CI kubectl apply、admin token、不 wait health、CI sync 與 auto-sync 並存、app 與 GitOps 同 repo、CI 用 argocd app set、用 latest tag、token 在 app repo、跳過 sync window、Argo CD rollback 取代 git revert。避免這十項就能解決 80% CI/CD 整合問題。
  • 🔄回滾用 git revert 而非 Argo CD rollback：Argo CD rollback 把 cluster 改回舊 manifest，但 Git 中還是新版本——下次 sync 會被覆蓋回去。git revert 推進 GitOps repo才是 GitOps-pure 的回滾方式，Argo CD 自然把 cluster sync 回舊版本。
