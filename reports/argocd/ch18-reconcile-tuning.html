Reconcile 效能調優：
大規模 Argo CD 的瓶頸與對策

當 Application 數量從 100 成長到 1000+，預設配置會碰到各種瓶頸：UI 載入緩慢、sync 排隊、controller OOM、Git 平台 rate limit。本章拆解 reconcile 六階段流程、三大效能瓶頸（controller / repo-server / cluster cache），逐一給出調優公式與設定，最後提供效能 Playbook 與監控指標。

📋

前置：已閱讀 Ch.13（HA + Sharding）。理解 application-controller 與 repo-server 的角色（Ch.03）、Prometheus 監控基本概念。

🎯 學習目標

  • 理解 reconcile 六階段流程：取 manifest → 比對 → 排隊 → sync → 寫入 → 更新狀態
  • 能依症狀定位三大瓶頸：controller queue 堆積 / repo-server CPU 飆高 / cluster cache 過時
  • 掌握 application-controller 調優：status-processors、operation-processors、kubectl-parallelism-limit、workqueue rate limiter
  • 掌握 repo-server 調優：parallelism.limit、shallow clone、manifest cache、--allow-concurrency 標記
  • 正確設定 timeout.reconciliation + jitter，搭配 Webhook 達成「快速感知 + 低 polling 負載」
  • 使用 ignoreResourceUpdates 與 manifest-generate-paths 大幅減少不必要的 reconcile
  • 大型 cluster 的 cache 調優（ARGOCD_CLUSTER_CACHE_LIST_PAGE_BUFFER_SIZE）
  • 建立關鍵效能指標的 Prometheus alert 與 Grafana dashboard

1Reconcile 流程拆解

1.1 六階段管線

每次 Application reconcile 都經過六個階段。理解這個流程才能定位效能瓶頸：

Pipeline — Reconcile 六階段
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 1: Detect Trigger                                            │
│  - timer fires (timeout.reconciliation, default 180s + 60s jitter)  │
│  - webhook arrives (Git push)                                       │
│  - resource update (Kubernetes watch event)                         │
│  - manual refresh (UI / CLI / API)                                  │
└──────────┬──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 2: Manifest Generation (repo-server)                         │
│  - git clone / fetch (cache hit if same commit SHA)                 │
│  - helm template / kustomize build / cmp generate                   │
│  - return rendered manifests                                        │
└──────────┬──────────────────────────────────────────────────────────┘  ← 通常最慢
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 3: Live State Read (controller cluster cache)                │
│  - 從 cache 讀取目前 cluster 狀態（避免每次都打 K8s API）            │
│  - cache 由 watch APIs 持續更新                                     │
└──────────┬──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 4: Diff & Status Update                                      │
│  - 比對 desired vs live                                             │
│  - 計算 sync status (Synced/OutOfSync) + health status              │
│  - 更新 Application CR 的 status                                    │
└──────────┬──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 5: Sync (only if OutOfSync + auto-sync enabled)              │
│  - 透過 kubectl apply / SSA 寫入 K8s（消耗 operation-processors）   │
└──────────┬──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Stage 6: Status Update                                             │
│  - 更新 Application CR 的 status.sync.status / health.status         │
│  - 更新 Application Set 的彙總狀態                                  │
└─────────────────────────────────────────────────────────────────────┘

1.2 三大瓶頸定位

📦
瓶頸 1：repo-server 慢
"Context deadline exceeded"
repo-server CPU 飆 80%+
queued requests 持續增加
最常見的瓶頸。Helm template / Kustomize build / git clone 太慢。對策：parallelism limit、shallow clone、manifest cache、horizontal scale。
⚙️
瓶頸 2：controller queue 堆積
UI status 過時
新 commit 數分鐘後才 OutOfSync
controller CPU 飆高
application 太多但 processors 太少。對策：status/operation processors 增加、Sharding（多個 controller）、reduce reconcile 頻率。
💾
瓶頸 3：cluster cache 過大
controller OOM
"continue parameter is too old"
cache initial sync 超時
受管 cluster 中資源太多。對策：resource.exclusions 排除高頻資源、ARGOCD_CLUSTER_CACHE_LIST_PAGE_BUFFER_SIZE 調高、增加 controller memory。
🌐
瓶頸 4：Git 平台 rate limit
"rate limit exceeded"
repo-server 與 Git 連線失敗
許多 OutOfSync 但無法 detect
許多 App 同時 polling 同 repo。對策：repo-server.git.request.timeout 加長、用 GitHub App（5000 RPS）、webhook 取代 polling。

2application-controller 調優

2.1 Status / Operation Processors

controller 內部有兩個 worker pool：status processors 處理 reconciliation（diff 計算），operation processors 處理實際 sync 操作。預設 20 / 10，1000+ Application 環境必須調高：

YAML — controller processors 設定
## 方式：argocd-cmd-params-cm（推薦，宣告式）
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  # Status processors（reconciliation 並發數）
  # 預設 20。1000 App 用 50，3000+ App 用 100
  controller.status.processors: "50"

  # Operation processors（sync 操作並發數）
  # 預設 10。1000 App 用 25，3000+ App 用 50
  controller.operation.processors: "25"

  # 注意：increase processors 會線性增加 CPU + memory
  # 50/25 配置：~2 CPU + 2 GB memory（單 controller）
  # 100/50 配置：~4 CPU + 4 GB memory
ℹ️

Processors 增加的時機

當 UI 顯示某 App 已經 OutOfSync 但 Argo CD 「沒在做事」時，通常是 status processors 不夠用，App 還在 queue 中等待。觀察 argocd_workqueue_depth 指標，若持續 > 0 且 status processors 全忙，就要增加。

2.2 kubectl-parallelism-limit

controller 用 kubectl fork/exec 將 manifest 寫入 K8s 與轉換 resource version。沒有限制時，大量並發 fork 會造成 controller pod OOM：

YAML — kubectl-parallelism-limit
data:
  # kubectl 並發 fork/exec 限制（防止 controller OOM）
  # 預設無限制；建議 20
  controller.kubectl.parallelism.limit: "20"

  # 每個 sync 內部的 K8s API 並發數（Argo CD v2.10+）
  controller.sync.timeout.seconds: "180"

2.3 Workqueue Rate Limiter

當異常 Application（例如 manifest 一直生成失敗）持續觸發 reconcile，會造成 sync loop 與其他 App 排隊。Rate limiter 限制單一 Application 的重試頻率：

YAML — Workqueue Rate Limiter（環境變數）
## 在 argocd-application-controller StatefulSet 設定 env
env:
  ## ── Per-item rate limiter（exponential backoff）─────────
  - name: WORKQUEUE_FAILURE_COOLDOWN
    value: "10s"     # 失敗後最短重試間隔
  - name: WORKQUEUE_BASE_DELAY
    value: "5ms"
  - name: WORKQUEUE_MAX_DELAY
    value: "1000s"   # 失敗多次後最長間隔（指數成長）

  ## ── Global rate limiter（防止 burst）──────────────────
  - name: WORKQUEUE_BUCKET_SIZE
    value: "500"     # 單秒最多入 queue 的項目數
  - name: WORKQUEUE_BUCKET_QPS
    value: "50"      # 平均 QPS（fill rate）

## 效果：
# 失敗的 App 自動退避，不會佔用 worker
# 突發大量 webhook 不會把其他 App 擠出 queue

3repo-server 調優（最常見瓶頸）

3.1 parallelism.limit

單一 repo-server replica 的並發 manifest 生成上限。預設無限制，500+ Application 同時 reconcile 時會 OOM：

YAML — repo-server parallelism limit
data:
  # 公式：limit = (CPU cores × 2)
  # 4 CPU → 8
  # 2 CPU → 4-5
  reposerver.parallelism.limit: "10"

  # Git 連線並發限制（保護 Git 平台）
  # 0 = 無限制；超過 200 App 用同 repo 時必須設定
  reposerver.git.requests.concurrency.limit: "20"

# 公式說明：
# Total parallelism = replicas × per-replica limit
# 3 replica × 10 limit = 30 並發 manifest 生成
# 30 是個合理的中型生產環境配置（管理 500-1000 App）

3.2 Manifest Cache + Shallow Clone

YAML — repo-server 快取與 clone 優化
data:
  # Shallow clone（只取最新 commit，不取歷史）
  # 大型 mono-repo（10000+ commits）效益顯著：
  # - 50MB clone 取代 500MB
  # - 5 秒取代 30 秒
  reposerver.git.shallow.clone: "true"

  # Manifest cache TTL（Argo CD 內部 cache，存於 Redis）
  # 預設 24h；對 immutable 的 commit SHA 已足夠
  # 對追蹤 branch 的場景，配合 webhook 可大幅減少 helm template 次數

  # Helm template timeout
  reposerver.git.request.timeout: "60s"

  # 標記允許並發的 chart（建立 .argocd-allow-concurrency 檔案）
  # 在 chart 目錄根新增空檔案 .argocd-allow-concurrency
  # 表示此 chart 不修改本地檔案，可並發處理

Mono-repo 場景的 .argocd-allow-concurrency 標記示範：

Bash — 為所有 chart 標記允許並發
# 在 mono-repo 中為每個 chart 目錄建立 .argocd-allow-concurrency
$ find . -name "Chart.yaml" -exec dirname {} \; | \
    xargs -I {} touch {}/.argocd-allow-concurrency

# 同樣為 kustomize overlay：
$ find . -name "kustomization.yaml" -exec dirname {} \; | \
    xargs -I {} touch {}/.argocd-allow-concurrency

# commit 進 Git，repo-server 重啟後生效
# 效果：同 repo 多個 chart 可並發 template，大幅縮短大批量 reconcile 時間

4Reconciliation 間隔調優

4.1 timeout.reconciliation

controller 預設每 180 秒 + 60 秒 jitter 對所有 Application 重新 reconcile。500+ App 環境，預設值會造成持續高負載：

YAML — timeout.reconciliation 調優
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 預設 180s + 60s jitter，總 polling 間隔 ~3 分鐘
  # 配合 webhook 後，可拉長到 600s（10 分鐘）甚至 1800s（30 分鐘）
  timeout.reconciliation: 600s
  timeout.reconciliation.jitter: 120s
  # 設為 0 完全停用 polling（純 webhook 模式）
  # timeout.reconciliation: 0s
⚠️

jitter 不是可選

若 jitter = 0，所有 Application 會在啟動後同一時間點同時 reconcile（雪崩效應）。永遠保留至少 timeout 的 30-50% 作為 jitter。例如 timeout = 600s，jitter = 120-180s。

4.2 Webhook 即時觸發

Webhook 讓 Argo CD 在 Git push 後 ~10 秒內感知變更，不需要等下次 polling。這是最關鍵的效能優化——可以將 timeout.reconciliation 拉長到 30 分鐘而仍維持快速 sync：

YAML + Bash — Git Webhook 完整設定
## ── Step 1：取得 webhook secret ────────────────────────
## 在 argocd-secret 中設定（用於驗證 webhook 真實性）
apiVersion: v1
kind: Secret
metadata:
  name: argocd-secret
  namespace: argocd
stringData:
  # GitHub
  webhook.github.secret: my-github-webhook-secret
  # GitLab
  webhook.gitlab.secret: my-gitlab-webhook-secret
  # Bitbucket
  # webhook.bitbucketserver.secret: ...

## ── Step 2：在 GitHub repo 設定 webhook ────────────────
## Repo Settings → Webhooks → Add webhook
# Payload URL:    https://argocd.example.com/api/webhook
# Content type:   application/json
# Secret:         my-github-webhook-secret（與上方 secret 相同）
# Events:         Just the push event（精確比 "Send everything" 好）

## ── Step 3：使用 manifest-generate-paths 進一步優化 ─────
## 在 Application 加入 annotation，告訴 Argo CD：
## 「只有當這些 path 變更時才重新生成 manifest」
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  annotations:
    # 多 path 用分號分隔
    argocd.argoproj.io/manifest-generate-paths: .;../shared-libs
spec:
  source:
    path: apps/my-app

## 效果：
# Mono-repo 收到 webhook 時：
# Argo CD 解析 webhook payload 中的 changed files
# 若沒有任何檔案在 my-app/ 或 shared-libs/，跳過 reconcile
# 大幅減少不必要的 manifest 生成
💡

典型優化組合

500 App + Mono-repo：① timeout.reconciliation = 1800s；② jitter = 600s；③ Webhook + manifest-generate-paths；④ .argocd-allow-concurrency 標記。實測效果：repo-server CPU 從 80% 降至 15%，Git push 後感知時間從 2-5 分鐘降至 5-10 秒。

5減少不必要的 Reconcile

5.1 ignoreResourceUpdates（v2.10+）

許多 K8s controller 會週期性更新 resource status（如 ExternalSecret 的 status.refreshTime、cert-manager 的 conditions）。每次更新觸發 Argo CD 重新 reconcile，但實際上沒有 sync 需求。ignoreResourceUpdates 讓 Argo CD 忽略這些變更：

YAML — ignoreResourceUpdates 設定
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 全域：忽略所有 resource 的 .status 變更
  resource.customizations.ignoreResourceUpdates.all: |
    jsonPointers:
      - /status

  # 針對特定資源：忽略 ExternalSecret 的 refreshTime
  resource.customizations.ignoreResourceUpdates.external-secrets.io_ExternalSecret: |
    jsonPointers:
      - /status/refreshTime
      - /status/conditions

  # 針對 Certificate（cert-manager）：忽略 renewal time 變更
  resource.customizations.ignoreResourceUpdates.cert-manager.io_Certificate: |
    jsonPointers:
      - /status/renewalTime
      - /status/conditions

  # 預設啟用（v2.10+）：
  resource.ignoreResourceUpdatesEnabled: "true"

對於不在 Application 管理範圍但仍會觸發 watch 的 untracked resources，可在 manifest 加 annotation：

YAML — untracked resource annotation
## 在依賴資源加上 annotation（如 cert-manager 自建的 Secret）
metadata:
  annotations:
    argocd.argoproj.io/ignore-resource-updates: "true"
ℹ️

找出高 churn 資源類型

把 controller log level 設為 debug，搜尋 "Requesting app refresh caused by object update"。按 api-version/kind 計數，找到頻繁觸發的資源類型，再針對性加入 ignoreResourceUpdates。

5.2 resource.exclusions（v3.0 預設已強化）

排除高頻 / 高 churn 但不需要 GitOps 管理的 K8s 資源類型，避免 cluster cache 過大與 watch event 過多：

YAML — resource.exclusions（v3.0 預設值）
data:
  # v3.0 起預設排除以下資源（無需手動設定）：
  resource.exclusions: |
    # 高頻更新（performance critical）
    - apiGroups: [""]
      kinds: [Endpoints]
      clusters: ["*"]
    - apiGroups: ["discovery.k8s.io"]
      kinds: [EndpointSlice]
      clusters: ["*"]
    - apiGroups: ["coordination.k8s.io"]
      kinds: [Lease]
      clusters: ["*"]
    # Token / Review 類（暫時性 + 高頻）
    - apiGroups: ["authentication.k8s.io"]
      kinds: [SelfSubjectReview, TokenReview]
    - apiGroups: ["authorization.k8s.io"]
      kinds: [LocalSubjectAccessReview, SelfSubjectAccessReview, SelfSubjectRulesReview, SubjectAccessReview]
    - apiGroups: ["certificates.k8s.io"]
      kinds: [CertificateSigningRequest]
    # PolicyReport（OPA Gatekeeper / Kyverno）
    - apiGroups: ["wgpolicyk8s.io"]
      kinds: [PolicyReport, ClusterPolicyReport]

  # 自定義排除：服務網格的高頻資源
  # （在預設值之外擴充，注意不要覆蓋預設）

5.3 manifest-generate-paths（mono-repo 必備）

Mono-repo 中，App A 在 apps/a/，App B 在 apps/b/。若沒有 manifest-generate-paths annotation，任何一個 commit 都會觸發 A 和 B 都重新 reconcile（每次都 helm template）。設定後只有對應 path 變更才觸發：

YAML — manifest-generate-paths 範例
## App A：只在 apps/a/ 或共享 lib/ 變更時 reconcile
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-a
  annotations:
    # 多 path 用分號分隔；. 表示 source.path 本身
    # ../shared-lib 表示 path 的相對路徑
    argocd.argoproj.io/manifest-generate-paths: ".;../shared-lib"
spec:
  source:
    repoURL: https://github.com/myorg/mono-repo.git
    path: apps/a

# 注意：此功能只在 webhook 模式下生效
# Polling 模式下（webhook 未設定），仍會所有 App reconcile

6大型 Cluster Cache 調優

controller 透過 K8s watch API 維護 cluster 快取（avoid query K8s API 每次 reconcile）。當 cluster 中資源數量極多（10000+）時，初次 cache sync 可能超時：

YAML — Cluster cache 環境變數
## 在 argocd-application-controller StatefulSet 設定
env:
  # 單次 list page size（K8s API 分頁讀取）
  # 預設 500，大 cluster 可調至 2000
  - name: ARGOCD_CLUSTER_CACHE_LIST_PAGE_SIZE
    value: "500"

  # Page buffer 數（並發處理多少 page）
  # 預設 1，大 cluster 調至 5-10
  # 防止 etcd compaction 期間「continue parameter is too old」錯誤
  - name: ARGOCD_CLUSTER_CACHE_LIST_PAGE_BUFFER_SIZE
    value: "5"

  # 公式：PAGE_SIZE × BUFFER_SIZE 應大於最大資源類型總數
  # 例：cluster 中 10000 個 Pod → 500 × 20 = 10000 OK

  # Cache 重新同步間隔（預設 24h）
  - name: ARGOCD_CLUSTER_CACHE_RESYNC_DURATION
    value: "24h"

  # Watch retry 間隔
  - name: ARGOCD_CLUSTER_CACHE_WATCH_RESYNC_DURATION
    value: "60s"
⚠️

controller OOM 的真兇通常是 cache

Argo CD controller 記憶體用量主要來自 cluster cache。10000+ resources 的 cluster 可能需要 2-4 GB memory。觀察 argocd_cluster_cache_resources 指標，依此調整 controller resources.limits.memory。Sharding 是進一步分擔 cache 負載的方案（每 shard 只 cache 部分 cluster）。

7效能監控指標

沒有監控就沒有調優。以下是必須監控的關鍵指標：

argocd_app_reconcile_bucket
Application reconciliation 持續時間 histogram。99th percentile > 120s 表示有效能問題。
⚠ Alert: p99 > 120s for 10m
argocd_app_k8s_request_total
每 Application 對 K8s API 的請求數。某 App 異常高表示其資源使用了 non-preferred version（cache miss）。
⚠ 找出 outlier App 並修復 manifest
argocd_repo_pending_request_total
repo-server 中等待處理的請求數。持續 > 0 代表 parallelism limit 太低或 repo-server 過載。
⚠ Alert: > 0 for 5m
argocd_workqueue_depth
controller queue 深度。持續 > 0 + status processors 全忙 = 需要增加 processors。
⚠ Alert: > 50 for 5m
argocd_cluster_cache_resources
cache 中的資源數量。極端大表示 resource.exclusions 不足或 cluster 過大需 sharding。
⚠ Alert: > 50000 per cluster
argocd_git_request_duration_seconds
Git operation 持續時間。> 30s 表示 Git 平台慢、network 問題、或 repo 過大需 shallow clone。
⚠ Alert: p95 > 30s
YAML — Prometheus Alert Rules 範例
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: argocd-performance
  namespace: argocd
spec:
  groups:
    - name: argocd-performance
      rules:
        - alert: ArgoCDSlowReconciliation
          expr: |
            histogram_quantile(0.99,
              rate(argocd_app_reconcile_bucket[5m])
            ) > 120
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "Argo CD reconciliation taking too long"

        - alert: ArgoCDRepoServerOverloaded
          expr: argocd_repo_pending_request_total > 5
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "repo-server has pending requests"
            description: "Increase replicas or parallelism limit"

        - alert: ArgoCDControllerQueueDepthHigh
          expr: argocd_workqueue_depth > 50
          for: 5m
          labels:
            severity: warning

調優順序建議

① 啟用 Webhook（最大效益，幾乎免費）；② shallow clone（5 分鐘設定）；③ ignoreResourceUpdates（找 high-churn 資源）；④ 調 processors / parallelism（依 metrics 決定）；⑤ Sharding（>30 cluster 才需要）；⑥ cluster cache 調優（>10000 resource 才需要）。先省力且有大效益的優化，後針對性調參。

✓本章重點回顧

📌 Key Takeaways

  • 📊Reconcile 六階段瓶頸定位：① repo-server 慢（最常見，CPU/OOM）；② controller queue 堆積（processors 不夠）；③ cluster cache 過大（OOM）；④ Git rate limit。先看 metrics 找瓶頸，不要盲目調參。
  • ⚙️controller processors 公式：1000 App → status:50 / op:25；3000+ App → status:100 / op:50。kubectl-parallelism-limit:20 必設（防 OOM）。Workqueue rate limiter 處理 sync loop。
  • 📦repo-server 調優三件套：① parallelism.limit = CPU × 2；② shallow.clone: true（mono-repo 效益巨大）；③ 在 chart 目錄放 .argocd-allow-concurrency 標記允許並發。
  • 🌐Webhook 是最大投資報酬比的優化：設定後 timeout.reconciliation 可拉長到 1800s，repo-server CPU 降 3x，Git push 後感知時間從分鐘級降到秒級。配合 manifest-generate-paths 在 mono-repo 進一步避免不必要的 reconcile。
  • 🔇ignoreResourceUpdates 大幅降低無效 reconcile：對 ExternalSecret / Certificate / 任何高 churn 資源類型設定。debug log 找 "Requesting app refresh caused by object update" 找出兇手。v3.0 預設啟用。
  • 📈必須監控的關鍵指標：argocd_app_reconcile（duration p99）、argocd_repo_pending_request_total（> 0 即警告）、argocd_workqueue_depth、argocd_cluster_cache_resources。沒有監控就無法判斷調優是否有效。
