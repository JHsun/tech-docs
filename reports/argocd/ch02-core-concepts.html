核心概念全解：
Application、Project、Sync 狀態

Argo CD 的一切操作都建立在幾個核心概念之上：Application CRD、AppProject、Sync Status 與 Health Status。徹底理解這四個概念，是掌握後續所有進階功能的基礎。本章以完整 YAML 解析、狀態機圖解、以及實際情境對照，帶你建立清晰的心智模型。

📋

前置：已閱讀 Ch.01，了解 GitOps 四大原則與 Push vs Pull 架構差異。具備 Kubernetes 基礎（YAML、CRD 概念）。

🎯 學習目標

  • 能獨立撰寫完整的 Application CRD YAML，理解每個欄位的用途與必填/選填性質
  • 精確區分 Sync Status（Synced / OutOfSync）與 Health Status（六種）的語義差異
  • 理解 Application 的 Health 聚合邏輯（worst-case 原則）
  • 掌握「Synced but Degraded」等四象限狀態的實際含義與對應動作
  • 了解 AppProject 的邊界管理功能與 default project 的使用限制
  • 熟悉手動 sync 與自動 sync 的適用時機與關鍵差異

1Application CRD 完整解析

Application 是 Argo CD 最核心的 Kubernetes Custom Resource。每一個 Application 代表「一個部署單元的聲明合約」：告訴 Argo CD 去哪裡取得 manifest（source）、部署到哪裡（destination），並指定如何保持兩者同步（syncPolicy）。

📖

官方定義

「Application CRD 是 Kubernetes resource object，代表一個在特定環境中已部署的應用程式實例。它由兩個關鍵資訊定義：source（Git 中 desired state 的參考位置）與 destination（目標叢集與 namespace）。」— 官方文件

1.1 完整的生產等級 Application YAML

先看一個完整範例，再逐段解析各欄位：

YAML — Application（生產等級完整範例）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: backend-api            # 在同一 Argo CD 實例中必須唯一
  namespace: argocd
  labels:
    team: backend
    env: production
  annotations:
    notifications.argoproj.io/subscribe.on-sync-succeeded.slack: backend-deploys
    notifications.argoproj.io/subscribe.on-health-degraded.pagerduty: backend-oncall
  finalizers:
    - resources-finalizer.argocd.argoproj.io  # 刪除 App 時 cascade 清除叢集資源
spec:
  project: backend-team       # 所屬 AppProject（預設 "default"）

  source:                      # manifest 來源
    repoURL: https://github.com/myorg/backend-api.git
    targetRevision: main
    path: charts/backend
    helm:
      valueFiles:
        - values.yaml
        - values-production.yaml
      parameters:
        - name: image.tag
          value: v3.2.1

  destination:               # 部署目標
    server: https://kubernetes.default.svc
    namespace: backend-production

  syncPolicy:                # 同步策略
    automated:
      prune: true             # Git 刪除的資源，叢集也刪除
      selfHeal: true          # 自動修復 drift（5 秒後重試）
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true
      - ApplyOutOfSyncOnly=true
      - PruneLast=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

  ignoreDifferences:         # 忽略預期內差異
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas  # HPA 動態管理，忽略
  revisionHistoryLimit: 10

1.2 source 欄位詳解

📁 spec.source — manifest 來源定義
repoURL
倉庫 URL 必填
Git repo URL（HTTPS 或 SSH）或 Helm chart repo URL。OCI registry 格式為 oci://registry/repo（v3.1 起原生支援）。
targetRevision
目標修訂版本 必填
可填 HEAD（追蹤 default branch 最新）、branch 名稱、tag（v1.2.3）、完整 commit SHA。Helm chart 填版本號（1.5.0）。
path
Git 路徑 Git 必填
Git repo 內 manifest 所在目錄路徑。Helm chart repo 不使用此欄位，改用 chart。支援 . 表示根目錄。
chart
Helm Chart 名稱 Helm repo 必填
當 repoURL 是 Helm chart repository 時使用，填 chart 名稱（如 nginx）。此時 targetRevision 填 chart 版本。
helm / kustomize / directory / plugin
工具特定設定 選填
依 manifest 類型選填一種。Argo CD 自動偵測（Tool Detection）：有 Chart.yaml 用 Helm，有 kustomization.yaml 用 Kustomize，否則用 Directory。詳見 Vol 2 Ch.05。
💡

Multiple Sources（多 Source）

Application 支援 spec.sources（複數）欄位，可同時引用多個 Git repo 或 Helm chart（例如 chart 來自一個 repo，values 來自另一個 repo）。source 與 sources 二擇一，不可同時使用。詳見 Vol 2 Ch.05。

1.3 destination 欄位詳解

🎯 spec.destination — 部署目標定義
server
叢集 API Server URL server 或 name 二擇一
目標叢集的 API server URL。本地叢集固定用 https://kubernetes.default.svc。外部叢集需先以 argocd cluster add 或宣告式 Secret 方式註冊。
name
叢集別名 server 或 name 二擇一
使用叢集的友善名稱（如 in-cluster、prod-us-east）代替 URL，可讀性更高。在 ApplicationSet 中特別常用。注意：server 與 name 不可同時填寫，否則報錯。
namespace
目標 Namespace 選填
manifest 中未指定 namespace 的資源，預設部署到此 namespace。搭配 CreateNamespace=true sync option 可自動建立，無需預先 kubectl create namespace。

1.4 syncPolicy 詳解

syncPolicy 決定 Argo CD 如何（以及何時）將 Git 的 desired state 套用到叢集，是日常運維中最需要謹慎設計的欄位。

欄位預設值說明注意事項
automated.prunefalseGit 中刪除的資源，叢集中也自動刪除建議配合 PruneLast=true 更安全
automated.selfHealfalse偵測到 drift 時（5 秒後）自動重新 sync 修復啟用後無法手動 rollback（需先停用 automated）
automated.allowEmptyfalse允許 source 為空（零資源）時仍執行 sync預設 false 是安全保護，防止意外清空叢集
syncOptions: CreateNamespace=true—自動建立目標 namespace啟用後 namespace 由 Argo CD 管理，可能被刪除
syncOptions: ServerSideApply=true—使用 server-side apply推薦用於 CRD 或大型資源；大型 CRD 必須使用
syncOptions: ApplyOutOfSyncOnly=true—只 apply 狀態為 OutOfSync 的資源（v3.4 改善）大型 Application 可顯著降低 API server 壓力
syncOptions: Prune=confirm—資源刪除前需人工確認生產環境安全防護，避免意外刪除
retry.limit0（不重試）sync 失敗時最大重試次數（-1 為無限次）建議設定合理上限，配合 backoff 避免 thundering herd

1.5 ignoreDifferences：處理預期內差異

某些情況下，叢集中的資源會與 Git 定義出現預期內的差異。例如 HPA（Horizontal Pod Autoscaler）會動態調整 replicas 數量，導致 Argo CD 不斷偵測到 spec.replicas 不同步而標記為 OutOfSync。ignoreDifferences 讓你告訴 Argo CD：「這些欄位的差異不算 drift，請忽略。」

YAML — ignoreDifferences 常見範例
ignoreDifferences:
  # 情境 1：HPA 動態管理 replicas，忽略差異
  - group: apps
    kind: Deployment
    jsonPointers:
      - /spec/replicas

  # 情境 2：admission webhook 自動注入欄位（jqPathExpressions）
  - group: apps
    kind: Deployment
    jqPathExpressions:
      - .spec.template.spec.containers[]?.image

  # 情境 3：忽略特定 manager 的 managedFields
  - group: "*"
    kind: "*"
    managedFieldsManagers:
      - kube-controller-manager

2Sync Status 深度解析

Sync Status 回答的問題是：「叢集中的實際狀態，是否與 Git 中定義的 desired state 一致？」這是一個純粹的 diff 比較結果，與應用程式是否正常運行無關。

📊 Sync Status 狀態機
stateDiagram-v2 [*] --> Unknown : Application 剛建立 Unknown --> Synced : 首次 sync 成功 Unknown --> OutOfSync : 初始 diff 偵測到差異 Synced --> OutOfSync : Git 新提交 / 叢集被手動修改 OutOfSync --> Synced : sync 操作完成 OutOfSync --> OutOfSync : sync 失敗（retry） Synced --> Synced : selfHeal 持續監控中

2.1 三種 Sync Status 詳解

狀態含義常見原因對應動作
Synced ✅ 叢集狀態與 Git desired state 完全一致 sync 成功完成；selfHeal 已修復 drift 無需動作
OutOfSync ⚠️ 叢集狀態與 Git desired state 存在差異 Git 有新 commit；有人直接 kubectl edit；資源未部署 觸發 sync（手動或等待自動）
Unknown ❓ Argo CD 無法完成 diff 計算 repo server 連線失敗；manifest 解析錯誤；CRD 尚未安裝 排查 repo server 日誌與 Application 事件

2.2 手動 Sync vs 自動 Sync

⚠️

重要限制：啟用 automated sync 後不支援 Rollback

當 spec.syncPolicy.automated 設定後，Argo CD UI 的 Rollback 按鈕會被禁用。若需要回滾，必須先停用 automated sync，或透過 Git revert 更改版本。這個設計是刻意的：回滾應透過 Git 操作，而非繞過 Git。

面向手動 Sync自動 Sync（automated）
觸發方式UI 點擊 / argocd app sync / API偵測到 OutOfSync 後自動執行（最長 3 分鐘輪詢）
Rollback✅ 支援任意歷史 revision❌ 不支援（需先停用 automated）
Drift 修復需手動觸發✅ selfHeal=true 時自動修復（5 秒後重試）
適用場景生產環境需人工審核；GitOps 導入過渡期充分信任 Git 流程；staging / dev 環境
同步間隔由人工決定由 timeout.reconciliation（預設 120s + 60s jitter）控制
💡

透過 Git Webhook 消除延遲

設定 Git Webhook（GitHub / GitLab / Bitbucket 均支援）後，push 事件可即時觸發 Argo CD 重新計算 diff，幾乎消除最長 3 分鐘的輪詢延遲。詳見 Vol 6 Ch.30。

3Health Status 完整說明

Health Status 回答的問題是：「已部署的資源，實際上是否正常運作？」這與 Sync Status 完全獨立——應用程式可以 Synced（與 Git 一致）但仍然 Degraded（Pod 在 CrashLoopBackOff）。

3.1 六種 Health Status 詳解

✅
Healthy
最佳狀態
所有資源均正常運作。Deployment：所有 replica 就緒且更新到最新版。Pod：所有 container 運行中且通過 readiness probe。Service（LoadBalancer）：已取得 external IP。
readyReplicas == replicas
🔄
Progressing
過渡狀態
資源正在建立或更新中，尚未達到穩定狀態。Rolling update 進行中、Pod 正在啟動、PVC 正在 provision、LoadBalancer 等待 IP 分配。
Deployment rolling update in progress
🔴
Degraded
需要關注
資源遇到錯誤或無法達到健康狀態。Pod CrashLoopBackOff / OOMKilled / ImagePullBackOff；Deployment progressDeadlineExceeded（預設 10 分鐘）；Job 達到 backoffLimit。
Pod: CrashLoopBackOff
⏸️
Suspended
人為暫停
資源被刻意暫停，等待外部事件觸發。已 pause 的 Deployment（spec.paused: true）、已 suspend 的 CronJob、replicas 設為 0 的 Deployment。
spec.paused == true
❓
Missing
資源不存在
Git 中定義的資源在叢集中完全不存在。通常是 sync 尚未執行，或資源被手動 kubectl delete 後 selfHeal 尚未運行。這是 sync 問題，非 health check 問題。
Resource in Git, not in cluster
🔘
Unknown
無法評估
Argo CD 無法判斷資源的健康狀態。通常發生在自定義 CRD 沒有對應的 health check 設定時（對陌生資源類型預設返回 Unknown）。需要在 argocd-cm 加入自定義 Lua health check。
Custom CRD without health check

3.2 Application Health 聚合邏輯

Application 的 Health Status 是所有直接子資源健康狀態的聚合結果。聚合原則是 worst-case（最差狀態優先），優先順序從最差到最佳：

📊 Health 聚合優先順序（左為最差、右為最佳）
graph LR D["🔴 Degraded（最高優先）"] --> M["❓ Missing"] M --> P["🔄 Progressing"] P --> S["⏸️ Suspended"] S --> H["✅ Healthy（最低優先）"] style D fill:#fee2e2,stroke:#dc2626,color:#dc2626 style M fill:#f3e8ff,stroke:#7c3aed,color:#7c3aed style P fill:#cffafe,stroke:#0891b2,color:#0891b2 style S fill:#fef3c7,stroke:#d97706,color:#d97706 style H fill:#dcfce7,stroke:#16a34a,color:#16a34a
ℹ️

實際含義

只要有任何一個子資源是 Degraded，整個 Application 就顯示 Degraded；若沒有 Degraded 但有 Missing，則為 Missing；以此類推。只有所有資源都 Healthy，Application 才顯示 Healthy。

⚠️

Health 不繼承自孫資源

Application 的 health 只考慮直接子資源的 health，不遞迴聚合孫資源。例如：Application 直接管理 Deployment，Argo CD 評估 Deployment 的 health；而 Deployment 管理的 Pod 的 health 只有在 Deployment 本身的 health check 邏輯中才被間接考慮。這是設計上的刻意決策，避免過度複雜。

4Sync vs Health：四象限矩陣

初學者最常混淆的是：Sync Status 與 Health Status 是完全獨立的兩個維度。理解兩者的組合，是正確判讀 Argo CD Dashboard 的關鍵。

✅ Synced + ✅ Healthy
理想狀態（Ideal）
叢集與 Git 完全一致，且應用程式正常運作。所有 Application 的目標狀態。
動作：無需任何操作
⚠️ OutOfSync + ✅ Healthy
待更新狀態（Pending）
Git 有新提交尚未套用，但當前運行版本仍然健康。常見於手動 sync 模式等待部署中。
動作：適時觸發 sync（無緊迫性）
✅ Synced + 🔴 Degraded
執行期問題（Runtime Issue）
manifest 已正確套用（Synced），但應用程式本身出現問題。GitOps 本身沒問題，問題在應用層。最需立即排查的情況。
動作：查 Pod logs / kubectl describe / 應用程式監控
⚠️ OutOfSync + 🔴 Degraded
複合問題（Compound Issue）
叢集與 Git 不一致，且當前狀態也有問題。可能是 drift 導致配置錯誤，或 sync 失敗加上既有問題。
動作：先確認 diff 原因，排查 Degraded 根因，考慮 rollback
💡

CLI 快速查詢

argocd app list 可一次看到所有 Application 的兩種狀態。透過 --sync-status OutOfSync 或 --health-status Degraded 旗標篩選，快速定位問題 Application。

5AppProject：邊界管理與多租戶隔離

AppProject（簡稱 Project）是 Argo CD 的多租戶隔離機制。它定義了一組 Application 的邊界：哪些 Git repo 可以作為 source、哪些叢集與 namespace 可以作為 destination、哪些 Kubernetes 資源類型被允許操作。這讓平台團隊可以安全地將 Argo CD 使用權下放給各業務團隊，而不擔心越界操作。

🏢 backend-team Project
backend-api (Healthy)
backend-worker (Healthy)
backend-cron (Progressing)
✅ source: github.com/myorg/backend-*
✅ dest: prod-cluster / backend-*
❌ 禁止：ClusterRole、CRD
🏢 platform-team Project
monitoring-stack (Healthy)
cert-manager (Healthy)
ingress-nginx (Progressing)
✅ source: github.com/myorg/platform-*
✅ dest: all clusters / kube-system, monitoring
✅ 允許：ClusterRole、CRD

5.1 AppProject 完整 YAML 範例

YAML — AppProject 完整範例
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: backend-team
  namespace: argocd
spec:
  description: "Backend 團隊的 GitOps project"

  ## 允許作為 source 的 Git repo（白名單）
  sourceRepos:
    - https://github.com/myorg/backend-api.git
    - https://github.com/myorg/backend-worker.git
    # - '*'  # 允許所有 repo（生產環境不建議）

  ## 允許的部署目標（叢集 + namespace）
  destinations:
    - server: https://kubernetes.default.svc
      namespace: backend-*  # 支援 glob pattern
    - server: https://prod-cluster.example.com
      namespace: backend-production

  ## 允許操作的 cluster-scoped 資源
  clusterResourceWhitelist:
    - group: ""
      kind: Namespace
    # v3.3 起可限定具體資源名稱
    - group: apiextensions.k8s.io
      kind: CustomResourceDefinition
      name: mycrds.example.com  # v3.3 新增

  ## namespace-scoped 資源黑名單（預設全部允許）
  namespaceResourceBlacklist:
    - group: ""
      kind: ResourceQuota  # 不允許 backend 團隊修改 quota

  ## Project 內的 RBAC 角色
  roles:
    - name: developer
      description: 可讀取，只能 sync dev 環境
      policies:
        - p, proj:backend-team:developer, applications, get, backend-team/*, allow
        - p, proj:backend-team:developer, applications, sync, backend-team/backend-dev, allow
      groups:
        - github-org:backend-developers  # SSO group 對應

  ## 偵測不受 Argo CD 管理的「孤立資源」
  orphanedResources:
    warn: true

5.2 default Project 的特殊性

⚠️

default Project：方便但需謹慎

Argo CD 安裝後自動建立 default project，sourceRepos 與 destinations 均設為 *（無任何限制）。這讓入門非常方便，但在多團隊或生產環境中，強烈建議不要將生產環境的 Application 放在 default project。應為每個團隊建立獨立 Project 並明確設定邊界，避免誤操作越界。

Project 邊界能力v2.xv3.3+
sourceRepos 限制✅ glob pattern✅ glob pattern
destinations 限制✅ glob pattern✅ glob pattern
clusterResourceWhitelist只能限定 group / kind✅ 可進一步限定具體資源 name
namespaceResourceBlacklist / Whitelist✅✅
Project 層級 RBAC roles✅✅（配合 v3.0 Fine-Grained RBAC）

📌 Key Takeaways

  • 📄Application CRD 的四大區塊：project（所屬 Project）、source（repoURL + targetRevision + path/chart）、destination（叢集 + namespace）、syncPolicy（自動化行為）。每個 Application 名稱在同一 Argo CD 實例中必須唯一。
  • 🔄Sync Status ≠ Health Status：Sync 回答「叢集是否與 Git 一致？」；Health 回答「應用程式是否正常運作？」。兩者完全獨立，Synced 的應用可能同時是 Degraded 的（runtime 問題）。
  • 🏥六種 Health Status：Healthy、Progressing、Degraded、Suspended、Missing、Unknown。Application 的 Health 採用 worst-case 聚合：Degraded > Missing > Progressing > Suspended > Healthy。
  • 🎮自動 Sync 的重要限制：啟用 automated 後不支援 UI Rollback；selfHeal=true 會自動還原手動的叢集修改。生產環境初期建議使用手動 Sync，充分測試後再啟用自動化。
  • 🏢AppProject 是多租戶的核心：透過 sourceRepos、destinations、clusterResourceWhitelist 三道邊界，確保不同團隊的 Application 不會互相越界。v3.3 起可對 CRD 白名單精確到具體資源名稱。
  • 🏷️ignoreDifferences 的用途：排除 HPA 管理的 replicas、admission webhook 注入欄位等「預期內差異」，防止 Argo CD 因正常的動態變化而不斷報告 OutOfSync。
