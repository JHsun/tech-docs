ApplicationSet 概念
與 Generators 全覽

當你需要部署「同一個 App 到 30 個 cluster」、「同一 mono-repo 中 50 個微服務各有自己的 Application」、「為每個 PR 自動建立預覽環境」——逐個寫 Application 不切實際。ApplicationSet 是 Argo CD 的「Application 工廠」，透過 generators 自動產生 Application。本章涵蓋核心概念、CRD 結構、8 種 generators 全覽、兩種模板語法、Post Selector，以及與單一 Application、App-of-Apps 的差異比較。

📋

前置：已完整閱讀 Vol 1-2（Application 概念、syncPolicy、Hooks、Tracking）。理解 Vol 4 Ch.22 的多租戶 ApplicationSet 範例。理解 Helm template 與 Go template 基本語法（用於 templating 章節）。

🎯 學習目標

  • 理解 ApplicationSet 解決哪三類規模化部署問題：multi-cluster fan-out、mono-repo 自動化、多租戶自治
  • 掌握 ApplicationSet CRD 完整結構：generators / template / strategy / syncPolicy / goTemplate
  • 能列出 8 種 generators 並說明各自適用場景：List / Cluster / Git / Matrix / Merge / SCM Provider / Pull Request / Cluster Decision Resource / Plugin
  • 理解 generator → template → Application 的六階段渲染流程
  • 能比較 fasttemplate 與 goTemplate 的差異，並選擇正確語法（v3.x 強烈推薦 goTemplate）
  • 使用 Post Selector 對 generator 產生的參數做後過濾
  • 能比較 ApplicationSet vs 單一 Application vs App-of-Apps 三者的取捨
  • 掌握 ApplicationSet controller 的 HA 限制（leader election，單 active replica）

1為什麼需要 ApplicationSet

1.1 三大解決問題

當組織從「幾個 App」成長為「數十、數百個 App」，傳統的「逐一建立 Application 物件」會碰到三種困境：

問題傳統做法ApplicationSet 解法
1. Multi-cluster fan-out：同一個 App 要部署到 N 個 cluster 為每個 cluster 寫一個 Application（30 cluster = 30 個 YAML），每次升級要全部修改 一個 ApplicationSet + Cluster generator 自動為所有匹配的 cluster 產生 Application
2. Mono-repo 自動化：repo 中每個目錄都是獨立 App 每新增一個目錄就要手動 commit 一個 Application YAML Git Directory generator 自動掃描 repo 目錄，每個目錄產生一個 Application
3. 多租戶 / PR 預覽：每個 tenant 或每個 PR 需自己的環境 tenant 增加要 platform 介入；PR 預覽環境完全手動 List / SCM Provider / Pull Request generator 動態產生

1.2 與 App-of-Apps 的差異

許多人混淆 ApplicationSet 與 App-of-Apps（Vol 1 Ch.04 介紹過的 root Application 模式）。兩者各有適用場景：

面向App-of-AppsApplicationSet
本質普通 Application 的 syncPolicy 自動 apply 子 Application 物件專用 CRD + 控制器，動態 generate Application
來源必須是 Git 中的靜態 Application YAML動態 generators（Git / cluster / API / list）
適合開機啟動（bootstrap）、固定一組 Application大規模 fan-out、自動化、多租戶
運作application-controller 處理applicationset-controller（獨立元件）
HA受 controller sharding 影響（Ch.13）Leader election，單 active replica
💡

實務上常常混合使用

典型的企業架構：① Bootstrap Application（單一靜態 Application，由 platform 手動 apply）；② Bootstrap App 的 source 包含多個 ApplicationSet（管 platform 元件、管 tenant、管 monitoring 等）；③ ApplicationSet 動態產生具體的 Application。三層結構：1 個 root → N 個 ApplicationSet → 數百個 Application。

2CRD 結構與渲染流程

2.1 完整結構

YAML — ApplicationSet 完整 spec
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: my-appset
  namespace: argocd
spec:
  # 1. 模板語法（v2.6+ 推薦 goTemplate: true）
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]    # 缺少 key 時報錯（推薦）

  # 2. Generators（必填，至少一個）
  generators:
    - list:                                    # List generator
        elements:
          - cluster: prod-us-east
            url: https://prod-us-east.example.com

  # 3. 模板（必填）—— 渲染為 Application
  template:
    metadata:
      name: 'my-app-{{.cluster}}'
      labels:
        tenant: '{{.cluster}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/app.git
        path: manifests
        targetRevision: main
      destination:
        server: '{{.url}}'
        namespace: my-app
      syncPolicy:
        automated: {prune: true, selfHeal: true}

  # 4. 同步策略（影響 ApplicationSet 對 Application 的更新行為）
  syncPolicy:
    # 是否在 ApplicationSet 刪除時保留 Application（v3.0 預設 false）
    preserveResourcesOnDeletion: false

    # 應用層 syncPolicy（控制 controller 是否能 prune / 自動 sync ApplicationSet 變更）
    applicationsSync: create-update     # 不允許 controller 刪除 Application
    # 可選值：sync（預設，可建/改/刪）、create-only、create-update、create-delete

  # 5. Strategy（可選）—— 控制大量 update 的滾動方式（見 Ch.26）
  # strategy:
  #   type: RollingSync
  #   rollingSync:
  #     steps:
  #       - matchExpressions: ...

  # 6. Templated patch（可選）—— 局部 patch（見 Ch.26）
  # templatePatch: |
  #   metadata:
  #     annotations:
  #       custom: '{{.value}}'

2.2 渲染六階段流程

📊 ApplicationSet 渲染流程
1
Generator 執行：每個 generator 從其資料來源（List 元素 / cluster Secret / Git repo / GitHub API / ...）讀取資料，產生parameter sets（每組是一個 dict）。
2
Post Selector 過濾（可選）：用 label selector 進一步過濾 parameter sets。例如 cluster generator 取得所有 cluster 後，只保留 environment=prod 的。
3
Template 渲染：對每組 parameter set，用 {{.key}}（goTemplate）或 {{key}}（fasttemplate）取代 template 中的 placeholder，產出一個完整的 Application YAML。
4
Diff 比對：與上次渲染結果比對，計算需要 create / update / delete 哪些 Application 物件。
5
套用 syncPolicy 限制：依 applicationsSync 決定是否實際 create / update / delete。例如 create-only 模式下，update / delete 都被忽略。
6
套用 strategy（如有）：若設定 RollingSync，會分批執行，等前一批 Healthy 才繼續下一批。
ℹ️

ApplicationSet controller 不直接 sync K8s 資源

ApplicationSet controller 只負責 建立 / 更新 / 刪除 Application 物件。實際的 K8s 資源 sync 仍由 application-controller 處理。所以 ApplicationSet controller 跟 application-controller 是兩個獨立元件，各自有獨立的 reconciliation loop。

38 種 Generators 全覽

ApplicationSet 提供 8 種內建 generators（v3.4），各自適用不同情境：

📋
List
手動列舉
從靜態 key/value 列表產生 parameters。最簡單、最容易理解。
適合：小規模固定列表（5-10 個 cluster / tenant）、教學起點
🌐
Cluster
自動發現 cluster
讀取 Argo CD 已註冊的 cluster Secret（含 in-cluster），可用 label selector 過濾。cluster 增減時自動響應。
適合：multi-cluster fan-out（platform 元件如 cert-manager、monitoring agent）
📂
Git Directory
掃描 repo 目錄
在 Git repo 中掃描 directory glob（如 apps/*），每個目錄產生一組 parameters（含 path、basename）。
適合：mono-repo 自動化（每個目錄 = 一個 App）
📄
Git File
讀取 config 檔案
在 Git repo 中讀取 YAML / JSON 檔案，每個檔案的內容作為 parameter set。適合 per-instance config。
適合：每個 cluster 有自己的 config.json（含 region、tier 等資訊）
⚙️
Matrix
兩個 generator 笛卡爾積
組合兩個子 generator，所有可能組合都產生 parameters。例如 3 cluster × 5 region = 15 個 Application。
適合：多維度 fan-out（cluster × app、environment × tenant）
🔀
Merge
多 generator 合併
用 mergeKey 對多個 generator 結果做左 join。後 generator 的 value 覆蓋前者。適合 override 模式。
適合：基底 cluster 列表 + 特定 cluster 的自訂 override
🔍
SCM Provider
掃描 GitHub org
透過 GitHub / GitLab / Bitbucket / Gitea API 掃描整個 org，自動發現符合條件的 repo（如有 argocd.yaml）。
適合：大型組織的自動化（新 repo 自動納管）
🎫
Pull Request
PR 預覽環境
透過 GitHub / GitLab API 取得 open PR 列表，為每個 PR 產生 Application（用 PR 的 branch 作為 source）。
適合：PR preview environment、ephemeral 測試環境
🤖
Cluster Decision Resource
外部 CR 提供 cluster
讀取 K8s CR（如 OCM Placement、Karmada）取得 cluster 列表。外部 controller 決定要部署到哪些 cluster。
適合：跟 OCM、Karmada 整合
🔌
Plugin
自訂 HTTP API
向使用者自訂的 HTTP 服務發送 RPC 請求取得 parameters。無限延伸性，可整合任何資料來源。
適合：CMDB、自訂租戶系統、特殊整合
⚠️

從哪個 generator 開始？

新手建議從 List → Cluster → Git Directory 順序學習，這三個 generator 涵蓋 80% 場景。Matrix / Merge 是組合性的，理解前三個再學。SCM Provider / Pull Request 適合特定使用情境。Plugin / Cluster Decision Resource 是進階整合。

4Template 與兩種模板語法

4.1 fasttemplate vs goTemplate

ApplicationSet 支援兩種模板語法。v2.6+ 推薦使用 goTemplate，提供更強大的功能與更好的錯誤檢測：

面向fasttemplate（舊）goTemplate（推薦）
啟用預設（不設定 goTemplate）spec.goTemplate: true
語法{{name}}、{{path.basename}}（無 dot）{{.name}}、{{.path.basename}}（有 dot，如 Helm）
條件邏輯不支援支援 {{if}}、{{range}}、{{with}}
函數不支援支援 sprig 函數（{{.name | upper}}、{{contains .branch "release"}}）
missing key 處理silently render as empty用 goTemplateOptions: ["missingkey=error"] 強制報錯
nested 字典存取用 dotted key（{{path.basename}}）標準 Go template（{{.path.basename}} 或 {{index .metadata.labels "key"}}）
YAML — fasttemplate vs goTemplate 對比
## ── 範例 1：fasttemplate（舊語法，不建議新專案使用）─────
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: old-style
spec:
  # 不設定 goTemplate（預設 false = fasttemplate）
  generators:
    - clusters: {}
  template:
    metadata:
      name: 'app-{{name}}'          # 無 dot
    spec:
      destination:
        server: '{{server}}'
        # nested label：用 dotted key
        namespace: '{{metadata.labels.tenant}}'

--- ## ── 範例 2：goTemplate（推薦）──────────────────────────
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: go-style
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]    # 缺 key 時失敗

  generators:
    - clusters: {}
  template:
    metadata:
      name: 'app-{{.name}}'          # 有 dot（標準 Go template）
    spec:
      destination:
        server: '{{.server}}'
        # nested label：用 index 或直接 dot 存取
        namespace: '{{index .metadata.labels "tenant"}}'

      # goTemplate 才支援的條件邏輯
      syncPolicy:
        automated:
          prune: '{{if eq (index .metadata.labels "env") "prod"}}false{{else}}true{{end}}'

4.2 遷移到 goTemplate

遷移時主要調整：① 加上 goTemplate: true；② 所有 placeholder 加 dot（{{name}} → {{.name}}）；③ nested label 改用 {{index .x.y "z"}} 語法（key 含 hyphen 等特殊字元時）。

✅

新專案永遠用 goTemplate + missingkey=error

fasttemplate 在 missing key 時會 silently render 為空字串，導致不易發現的 bug（如 name: 'app-'）。goTemplateOptions: ["missingkey=error"] 會在缺 key 時直接 fail，立即發現問題。v3.x 強烈建議所有 ApplicationSet 都用此設定。

5Post Selector：過濾 generator 結果

有時候 generator 產生的 parameter sets 太多，需要進一步過濾。Post Selector 用 K8s 標準的 label selector 語法對結果做後過濾：

YAML — Post Selector 範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: prod-only-monitoring
spec:
  goTemplate: true
  generators:
    - clusters:
        # 第一階段：用 selector 在 generator 層過濾（cluster Secret label）
        selector:
          matchLabels:
            argocd.argoproj.io/secret-type: cluster

      # 第二階段：Post Selector（generator 產生 parameter 後再過濾）
      selector:
        matchExpressions:
          # 只保留 environment 為 prod 或 staging 的 cluster
          - key: environment
            operator: In
            values: [prod, staging]
          # 排除有 skip-monitoring label 的 cluster
          - key: skip-monitoring
            operator: DoesNotExist

  template:
    metadata:
      name: 'monitoring-{{.name}}'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/monitoring.git
        path: 'manifests/{{index .metadata.labels "environment"}}'
      destination:
        server: '{{.server}}'
        namespace: monitoring
ℹ️

Selector 兩階段執行

① Generator selector（generator 內部）：在資料源層過濾，可大幅減少 generator 處理量；② Post Selector（generator 外部）：在 parameter 已經產生後過濾。實務上推薦：能在 generator 內部過濾就不要等到 Post Selector，效能較佳。Post Selector 適合跨多個 generator 過濾（如 Matrix / Merge 結果）。

6ApplicationSet vs 單一 Application 比較

面向單一 ApplicationApplicationSet
關係「我」就是部署單位「我」產生 N 個 Application（不直接部署）
適合規模1-10 個固定 App10+ 個 App 或動態 App
運維複雜度每 App 獨立管理統一模板，但需要理解 generator
變更影響只影響此 App影響所有 generated Application
UI 顯示單一卡片ApplicationSet 卡片 + 多個子 Application 卡片
HA 模型受 application-controller sharding單 active replica（leader election）
適合場景核心關鍵 App、特殊個案fan-out、模板化、多租戶
⚠️

ApplicationSet 變更影響範圍很大

修改 ApplicationSet 的 template 會影響所有由它產生的 Application。例如改 source.path，所有 30 個 cluster 的 App 都會切換 source。生產環境應：① 先在 staging 驗證；② 用 syncPolicy 的 create-only 或 create-update 限制；③ 用 strategy.RollingSync（見 Ch.26）分批滾動。

7動手做：第一個 ApplicationSet

讓我們從最簡單的 List generator 開始，實際動手部署：

YAML — Hello-World ApplicationSet
## hello-appset.yaml — 為三個假想 cluster 部署 guestbook 範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: hello-world
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - list:
        elements:
          - cluster: in-cluster
            url: https://kubernetes.default.svc
            env: dev
          # 真實使用時，可以加上 staging / prod cluster URL 與 namespace
          # - cluster: staging
          #   url: https://staging.example.com
          #   env: staging

  template:
    metadata:
      name: 'guestbook-{{.cluster}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps.git
        targetRevision: HEAD
        path: guestbook
      destination:
        server: '{{.url}}'
        namespace: 'guestbook-{{.env}}'
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true

8運維注意事項

HA 限制

ApplicationSet controller 使用 K8s leader election——同時只有一個 replica 在 active 處理事件，其他 replica 是 standby。不像 application-controller 可以 sharding。實務影響：

場景影響對策
Leader pod 故障新 leader 接手前（~10 秒）暫停處理多 replica + leader election，Helm chart 預設啟用
大量 ApplicationSet（數百個）單 active replica 處理可能慢v3.x 增加 worker 數；考慮拆分成多個 ApplicationSet
SCM Provider / Plugin generator 慢慢的 generator 影響整體 reconcile 速度調 requeueAfterSeconds；Plugin 用 cache

RBAC 與安全考量

⚠️

ApplicationSet 是 super-power CRD

ApplicationSet 可以自動產生數百個 Application 物件。誰能寫入 ApplicationSet 就能繞過 AppProject 限制（透過自訂 generator + template）。argocd-rbac-cm 必須對 applicationsets resource 嚴格授權：只給 platform admin（不要授權給一般 tenant developer）。

YAML — ApplicationSet RBAC 範例
data:
  policy.csv: |
    # 預設只給 admin 寫入 ApplicationSet
    p, role:platform-admin, applicationsets, *, *, allow

    # 一般 user 唯讀
    p, role:org-readonly, applicationsets, get, */*, allow

    # 對 tenant 不開放 ApplicationSet 寫入（避免繞過 AppProject 限制）
    # （不寫 allow 即為 deny）

ApplicationSet in Any Namespace（v2.8+）

類似 Apps in Any Namespace（Ch.22），ApplicationSet 也支援放在 argocd 以外的 namespace。設定 applicationsetcontroller.namespaces 並在 AppProject 加入 sourceNamespaces。讓 tenant 在自己的 namespace 管理 ApplicationSet：

YAML — ApplicationSet in Any Namespace 設定
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  applicationsetcontroller.namespaces: "argocd,*-argocd"
  application.namespaces: "argocd,*-argocd"            # 兩者通常一起設

📌 Key Takeaways

  • 🏭ApplicationSet 是 Application 工廠：解決三類規模化部署——multi-cluster fan-out（同 App 部到 N cluster）、mono-repo 自動化（每目錄一個 App）、多租戶 / PR 預覽。與 App-of-Apps 互補：root App 啟動 → 多個 ApplicationSet → 數百 Application。
  • 🔄渲染六階段流程：Generator 執行 → Post Selector 過濾 → Template 渲染 → Diff 比對 → 套用 syncPolicy → Strategy 滾動。controller 只管 Application 物件，不直接 sync K8s 資源，實際 sync 仍由 application-controller 處理。
  • 📋8 種 generators 各有定位：① List：簡單列表；② Cluster：cluster 自動發現；③ Git Directory / File：repo 為 source；④ Matrix：兩 generator 笛卡爾積；⑤ Merge：mergeKey 合併；⑥ SCM Provider：org 掃描；⑦ Pull Request：PR 預覽；⑧ Cluster Decision Resource / Plugin：外部整合。從 List + Cluster + Git Directory 學起。
  • 📝v3.x 永遠用 goTemplate + missingkey=error：fasttemplate 在缺 key 時 silently render 為空字串造成隱藏 bug；goTemplate 提供條件邏輯、sprig 函數，搭配 missingkey=error 立即發現問題。語法差別：{{name}}（fast）→ {{.name}}（go），nested 用 {{index .x.y "z"}}。
  • 🔍Post Selector 兩階段過濾：generator 內部 selector 在資料源過濾（效能佳）；Post Selector 在 generator 外部過濾（適合跨 generator 結果）。能在 generator 內過濾就不要等到 Post Selector。
  • ⚖️ApplicationSet vs Application 取捨：1-10 個固定 App 用 Application 即可；10+ 個或動態 App 用 ApplicationSet。注意：ApplicationSet 變更影響範圍大（一改全改），生產環境用 syncPolicy 限制 + RollingSync 分批滾動。
  • 🔒HA 限制與安全：ApplicationSet controller 是 leader election（不像 application-controller 可 sharding）。ApplicationSet 是 super-power CRD——能寫入即可繞過 AppProject，RBAC 必須嚴格限定（只給 platform admin）。v2.8+ 支援 ApplicationSet in Any Namespace 給 tenant 自治。
