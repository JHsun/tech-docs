未來展望與 Argo 2.x → 3.x 遷移
完整 Argo 生態總覽

本書終章。Argo CD 從 2018 年發布至今走過 7 年，從一個小工具成長為 CNCF Graduated 專案、GitOps 事實標準。2025-05-06 GA 的 Argo CD v3.0 是繼 v2.0（2021）後第一個 major version——標榜 "Small but Mighty"，意指低風險升級但帶來重要的結構性改進。本章涵蓋 Argo CD 3.0 設計哲學、六大 breaking changes、完整遷移步驟、v3.x 後續 minor 重要變更（v3.1-v3.5）、整個 Argo 生態系（Workflows / Events / Rollouts / Kargo / Autopilot）的未來方向、給讀者的學習路徑建議。完成本章後，你已具備 Argo CD 從入門到精通的完整知識體系。

1Argo CD 3.0 設計哲學

1.1 "Small but Mighty"

Argo CD 維護團隊在 2025 年初公開 v3.0 提案時，明確設定低風險升級目標：

💡

v3.0 不是大改寫，是「清理 anti-patterns」

官方原話：「upgrading to 3.0 is almost as easy as upgrading between 2.x minor versions」。v3.0 的目標不是引入新功能，而是把幾年累積下來的不良預設值、安全 anti-patterns、過時設定全部清理掉：

① 移除 legacy 設定（argocd-cm 中的 legacy repository config，CMP v1）；② 修正不安全的 default（RBAC 過寬、tracking method 過時）；③ 解決已知 ApplicationSet bug（matrix/merge generator 預設選擇不一致）。這為 v3.x 後續的 5+ 年發展奠定乾淨的基礎。

1.2 時間表與支援政策

版本狀態 / 日期支援情況
v2.14v3 發布時最後一個 v2.xv3 GA 後支援 1 年
v3.02025-05-06 GAStable
v3.12025-08（約）Stable
v3.22025-11（約）Stable
v3.32026-02（約）Stable
v3.42026-04（約）本書基準版本
ℹ️

Argo CD 支援政策：N + 2 minor versions

官方同時支援最新 minor 與前兩個 minor。例如 v3.4 發布時，v3.4 / v3.3 / v3.2 都會收到 patch fix；v3.1 開始只接 critical security fix。實務：① 升級不要拖超過 3 個 minor 版本；② 大版本升級（如 v2 → v3）建議在 v2 最後 minor 升到最新後再 jump；③ 看 release notes 不只當前版本，要讀從你的版本到目標版本之間所有 minor 的 notes。

2六大 Breaking Changes

2.1 Fine-grained update/delete RBAC enforcement

影響：v2.x 中，applications, update, */* 權限隱含包含對 Application 所有 managed resources 的 update。v3.0 起必須明確聲明對 managed resources 的權限。

YAML — RBAC policy v2.x → v3.0 遷移
## v2.x 中以下 policy 可以更新所有 managed resources（如 Deployment、Service）
p, role:developer, applications, update, */*, allow

## v3.0 起，update 只作用在 Application 物件本身
## 要更新 managed resources 必須另外聲明：
p, role:developer, applications, update, */*, allow
p, role:developer, applications, update/*, */*, allow   # 新增此行
p, role:developer, applications, delete/*, */*, allow   # 對 delete 同樣

## 還原 v2.x 行為的 escape hatch：
# argocd-cm:
#   server.rbac.disableApplicationFineGrainedRBACInheritance: "false"
Bash — 影響評估指令
## 檢查現有 RBAC policy 是否使用 update / delete
$ kubectl get cm argocd-rbac-cm -n argocd -o jsonpath='{.data.policy\.csv}' | \
    grep -E "applications,\s*(update|delete),"
# 如有匹配，需要在這些 policy 旁邊加 update/* 或 delete/*

2.2 Logs RBAC enforced by default

影響：v2.4 引入了 logs RBAC，但預設關閉。v3.0 預設開啟——users 必須有 applications, get + logs, get 才能看 Pod 日誌。

YAML — Logs RBAC 設定
## v2.x：logs 自動跟著 applications get 一起給
p, role:developer, applications, get, */*, allow

## v3.0：必須明確加 logs 權限
p, role:developer, applications, get, */*, allow
p, role:developer, logs, get, */*, allow     # 新增

## 還原 v2.x 行為（不建議）：
# 移除 argocd-cm 中的 server.rbac.log.enforce.enable（v3 已不支援此 flag）
# 改為 policy.default 設為 role:readonly（含 logs）

2.3 Health Status 不再 persist 在 Application CR

影響：v2.x 中，application.status.health 包含 resources 陣列的詳細 health。v3.0 起resources health 從 appTree 動態計算，不再 persist 在 CR。

YAML — Application 物件 health 差異
## v2.x：Application CR 含 resources health 細節
status:
  health:
    status: Healthy
    lastTransitionTime: '2025-01-01T00:00:00Z'
    resources:            # ← persist 在 CR
      - group: apps
        health: {status: Healthy}
        kind: Deployment
        name: my-app

## v3.0：只有 top-level health，resources 從 appTree 取
status:
  health:
    status: Healthy
    lastTransitionTime: '2025-01-01T00:00:00Z'
  resourceHealthSource: appTree   # ← 新增此欄位

## 還原 v2.x 行為：
# argocd-cmd-params-cm:
#   controller.resource.health.persist: "true"
⚠️

第三方工具相依 Application CR 的 resources health 會壞

例如某些 dashboard 或 GitOps 監控工具讀 app.status.health.resources[]——v3 後此陣列為空。遷移前檢查所有 reading Application CR 的工具，必要時開啟 escape hatch controller.resource.health.persist: "true" 保持相容性。

2.4 Annotation-based Tracking 成為預設

影響：Ch.10 介紹的 tracking method——v3.0 起 annotation-based tracking 是預設（v2.x 預設是 label-based）。

YAML / Bash — Tracking method 遷移
## 1. 檢查現在用哪種 tracking method
$ kubectl get cm argocd-cm -n argocd -o jsonpath='{.data.application\.resourceTrackingMethod}'
# 空值 → v2.x 預設 = label
# "annotation" → 已使用 annotation-based

## 2. v2.x 中切換到 annotation（v3 升級前完成）
$ kubectl patch cm argocd-cm -n argocd --type merge \
    -p '{"data":{"application.resourceTrackingMethod":"annotation"}}'

## 3. Argo CD 會逐步把 label-tracked resources 改成 annotation-tracked
## 但這個 transition 需要每個 resource 被 sync 一次才完成

## 4. 對所有 application 強制 re-sync
$ for app in $(argocd app list -o name); do
    argocd app sync $app --force
  done

2.5 ApplicationSet applyNestedSelectors 強制 true

影響：Ch.26 的 matrix / merge generator——v2.x 中 applyNestedSelectors 預設 false，造成 selector 行為不一致。v3.0 強制 true 並移除這個欄位。

YAML — ApplicationSet matrix selector v3 行為
## v2.x：預設 applyNestedSelectors: false
## 子 generator 的 selector 不會 applied
spec:
  generators:
    - matrix:
        generators:
          - clusters:
              selector:      # ⚠️ v2.x 中此 selector 預設被忽略
                matchLabels: {env: prod}
        # applyNestedSelectors: true   ← 必須加才會生效

## v3.0：applyNestedSelectors 強制 true，selector 一律生效
# 結果：原本生 100 個 Application 的 ApplicationSet
# 可能突然只生 10 個（被 selector 篩掉）

## 影響評估：
## 1. 搜尋所有 ApplicationSet 找 matrix / merge generator
$ kubectl get appset -A -o yaml | grep -E "matrix|merge"

## 2. 檢查每個 nested generator 是否有 selector
## 3. 確認 selector 是否符合預期

2.6 argocd-cm legacy repository config 移除

影響：v2.x 支援在 argocd-cm 直接配置 repositories—— v3.0 已完全移除，必須用 Secret 形式。

YAML — Repository config 遷移
## ❌ v2.x legacy（v3 不再支援）
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
data:
  repositories: |
    - url: https://github.com/myorg/repo
      passwordSecret:
        name: repo-secret
        key: password

## ✅ v3.x 標準（Secret-based）
apiVersion: v1
kind: Secret
metadata:
  name: repo-myorg
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  url: https://github.com/myorg/repo
  username: myuser
  password: ghp_xxxxxx
Bash — 自動偵測 legacy repository config
## 檢查 argocd-cm 是否還有 legacy repositories
$ kubectl get cm argocd-cm -n argocd -o yaml | grep -A 5 "repositories:"
# 有任何輸出表示需要遷移

## 檢查既有 repo Secret 數量
$ kubectl get secrets -n argocd -l argocd.argoproj.io/secret-type=repository | wc -l

3遷移完整步驟

3.1 Pre-upgrade Health Check

Bash — Pre-upgrade Checklist 自動化
#!/bin/bash
## argo-v3-preupgrade-check.sh
## 升級前必跑：偵測所有可能 break 的設定

## 1. 確認所有 Application 處於 Synced + Healthy
echo "== Unhealthy / OutOfSync Apps =="
argocd app list --output json | jq -r '.[] | select(.status.sync.status != "Synced" or .status.health.status != "Healthy") | .metadata.name'

## 2. 檢查 legacy argocd-cm repository config（B6）
echo "== Legacy repository in argocd-cm =="
kubectl get cm argocd-cm -n argocd -o yaml | grep -A 3 "^[[:space:]]*repositories:"

## 3. 檢查 tracking method（B4）
echo "== Tracking method =="
kubectl get cm argocd-cm -n argocd -o jsonpath='{.data.application\.resourceTrackingMethod}'
# 空字串或 "label" → 升級前先切到 annotation

## 4. 檢查 RBAC 是否依賴 v2.x update/delete inheritance（B1）
echo "== RBAC update/delete usage =="
kubectl get cm argocd-rbac-cm -n argocd -o jsonpath='{.data.policy\.csv}' | grep -E "applications,\s*(update|delete),"

## 5. 檢查 ApplicationSet matrix/merge（B5）
echo "== ApplicationSet matrix / merge =="
kubectl get appset -A -o yaml | grep -B 2 -E "matrix:|merge:" | head -30

## 6. 確認 Argo CD 版本至少在 v2.13+
echo "== Current Argo CD version =="
argocd version --client --short

3.2 執行遷移步驟

1
讀完所有 minor release notes：從你目前的 v2.x 到 v3.0 之間每個 minor 的 upgrading 文件都要讀
2
升到 v2 最後 minor（v2.14）：先在 v2.x 內升到最新，確認 stable 後再 jump 到 v3
3
跑 pre-upgrade check 腳本：偵測所有需要 remediation 的點
4
逐項 remediation：B1 RBAC、B2 logs RBAC、B4 tracking method 等都在 v2.x 中完成（避免 v3 升級 + 多項變更同時發生）
5
在 staging 環境先升 v3：kubectl apply --server-side --force-conflicts -f .../v3.0.0/manifests/install.yaml
6
Post-upgrade 驗證：所有 Application Sync + Healthy、log 沒 error、CLI 連線正常
7
觀察 1-2 週：staging 穩定後再升 prod
8
升 prod：同步驟 5-6

3.3 Rollback 計畫

⚠️

Argo CD CRD 變更後 rollback 有風險

v3 升級會更新 CRD schema。降版回 v2.x 後：① 既有 Application 物件可能含 v3-only 欄位（v2 controller 看不懂但不會壞）；② resourceHealthSource: appTree 等新欄位被 v2 忽略；③ ApplicationSet 已展開的 Application 不會自動還原。實務建議：① 升級前 kubectl get applications.argoproj.io -A -o yaml > backup.yaml；② Argo CD secret 與 ConfigMap 全 backup；③ 嚴重狀況：刪除 v3 + apply v2 manifest + restore Application 物件（但 status 可能要重新建立）。

Bash — Rollback 應急流程
## 升級前 backup
$ kubectl get applications.argoproj.io -A -o yaml > apps-backup.yaml
$ kubectl get appprojects.argoproj.io -A -o yaml > projects-backup.yaml
$ kubectl get cm -n argocd -o yaml > argocd-cm-backup.yaml
$ kubectl get secret -n argocd -o yaml > argocd-secret-backup.yaml

## 如需 rollback：
## 1. 重新 apply v2.14 manifests（CRD 會更新回 v2 schema）
$ kubectl apply --server-side --force-conflicts -n argocd -f \
    https://raw.githubusercontent.com/argoproj/argo-cd/v2.14.0/manifests/install.yaml

## 2. 觀察 Application 物件是否正常運作
$ argocd app list

## 3. 如有問題：restore Application backup
$ kubectl apply -f apps-backup.yaml

ℹ️

v3.x 後續 minor 都遵守「向下相容」原則

v3.0 釋出後，後續 minor（v3.1 / v3.2 / v3.3 / v3.4）的變更都是 additive——新增功能但不破壞既有設定。意義：在 v3.x 內升級小心翼翼但風險低；下一個 major（推測 v4.0）會是 3-4 年後，且可能再次「Small but Mighty」。Argo CD 已進入穩定演進期。

💡

Argo CD vs Flux：兩者選擇

① Argo CD：UI 友善、多租戶 RBAC 強、ApplicationSet 模板化、生態系豐富（Rollouts/Workflows/Kargo）；② Flux：lightweight、與 Helm 整合最緊、社群風格較貼近 Kubernetes 原生 API。2026 年趨勢：大組織選 Argo CD（功能完整 + 多團隊治理）；小團隊 / Helm-heavy 選 Flux（簡潔 + 原生）。兩者皆 CNCF Graduated，都是長期 stable 選擇。

📌 本章 Key Takeaways

  • 🎯Argo CD 3.0 "Small but Mighty"（2025-05-06 GA）：不是大改寫，是清理 anti-patterns——移除 legacy 設定、修正不安全 default、解決已知 bug。目標是「升級 v3 跟 minor 升級一樣容易」，為後續 5+ 年發展奠定乾淨基礎。
  • 🔄六大 Breaking Changes：① Fine-grained update/delete RBAC（需明確 update/* delete/* policy）；② Logs RBAC enforced by default（需明確 logs, get）；③ Health 不再 persist 在 Application CR（resources health 改從 appTree 計算，第三方工具可能受影響）；④ Annotation-based tracking 成為預設（v2.x 預設是 label，遷移前手動切換）；⑤ ApplicationSet matrix/merge applyNestedSelectors 強制 true（原本被忽略的 nested selector 現在會生效）；⑥ argocd-cm legacy repository config 移除（必須用 Secret-based）。
  • 🛡️每個 breaking change 都有 escape hatch（除了 #6 完全移除）——還原 v2.x 行為的 flag 可以爭取遷移時間，但官方不建議長期保留（會在 v4 完全移除）。策略：先升 v3 + 開啟 escape hatch 保持相容，再逐步移除依賴。
  • 📋遷移 8 步驟：① 讀完所有 minor release notes；② 升到 v2 最後 minor（v2.14）；③ 跑 pre-upgrade check 腳本（6 項自動檢查）；④ 逐項 remediation 在 v2.x 完成；⑤ staging 環境先升 v3；⑥ post-upgrade 驗證；⑦ 觀察 1-2 週；⑧ 升 prod。降版有 CRD 風險，必須先 backup applications.yaml + projects.yaml + configmaps。
  • 🚀v3.x 後續 minor：v3.1（Notifications + SSO group）、v3.2（PR generator + Source Hydrator GA）、v3.3（性能優化 + Sharding）、v3.4（GitOps Server Architecture + UI 重構，本書基準）。遵守 additive 原則——v3.x 內升級小心翼翼但風險低。
  • 🌍Argo 生態系全圖：Argo CD（Graduated）+ Argo Rollouts（Incubating）+ Argo Workflows（Graduated）+ Argo Events（Graduated）+ Kargo（Akuity, Beta）+ Autopilot（argoproj-labs, Beta）。Argo CD vs Flux：大組織選 Argo CD（功能完整 + 多團隊治理），小團隊選 Flux（簡潔 + 原生），兩者皆 CNCF Graduated。
  • 🔮2026-2027 預期方向：① Argo CD：Source Hydrator GA + 大規模性能優化 + UI 重構；② Argo Rollouts：Gateway API 主流化 + Experiment 增強；③ Kargo：Beta → GA（預計 2026）；④ Autopilot：Helm 支援 + Kargo 整合；⑤ 整體進入穩定演進期，下一個 major version（v4）3-4 年後。
  • 📚三種讀者的下一步：① 剛入門 Developer：動手做 Vol 1-2 lab + 部署自己小專案 + 加入 Slack 社群；② DevOps / Platform Engineer：試 Source Hydrator + 設計 ApplicationSet pattern + 整合 Argo Rollouts；③ SRE / 深入：研究 source code + 貢獻 PR + 設計大規模 architecture。
  • 📅30 / 60 / 90 天計畫：① 30 天部署 Argo CD + sample app + ApplicationSet + RBAC；② 60 天實作 progressive delivery + secrets 整合 + Notifications + Monitoring；③ 90 天選擇進階方案——Source Hydrator / Kargo / Autopilot 擇其一深入。不要全部都用，選最匹配的。
  • ⚠️遷移 5 大陷阱：① 未升到最新 v2.x 就跳 v3；② 沒讀完所有 minor release notes 漏掉變更；③ 多 cluster 環境一次升所有 cluster（應該分批）；④ 沒先在 staging 測試；⑤ ApplicationSet matrix 隱含 selector 變更（applyNestedSelectors）未察覺造成 Application 突然消失。
