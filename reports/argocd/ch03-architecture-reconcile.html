架構深度解析：
五大元件與 Reconcile Loop

Argo CD 的設計以「關注點分離」為核心哲學，五個元件各司其職。真正理解每個元件的職責、通訊方式、以及 Reconcile Loop 的完整流程，是進行生產環境除錯、效能調優與高可用規劃的必要基礎。

📋

前置：已閱讀 Ch.01（GitOps 概念）與 Ch.02（Application CRD、Sync / Health Status）。具備 Kubernetes 基礎（Pod、Deployment、StatefulSet）。

🎯 學習目標

  • 說明 Argo CD 五大元件的職責、部署類型（Deployment / StatefulSet）與通訊埠號
  • 描述從使用者 git push 到叢集狀態更新的完整資料流（十個步驟）
  • 理解 Reconcile Loop 的觸發條件、時間參數與 jitter 的用途
  • 區分 Argo CD 哪些資料存在 Redis（暫存）、哪些存在 Kubernetes etcd（持久）
  • 能根據元件特性快速定位問題日誌位置，進行初步故障排查
  • 了解 repo-server 的 manifest 快取機制與 parallelism 控制

1架構全覽：設計哲學與資料流

1.1 設計哲學：關注點分離

Argo CD 的架構刻意保持簡單。相較於其他 CD 平台動輒十幾個微服務，Argo CD 只有五個核心元件，每個元件有明確的單一職責：

💡

架構設計原則

「API server 處理使用者互動，repo server 處理 manifest 生成，application controller 處理調和，Redis 透過快取串聯一切。這種有意的簡單性是特性，不是限制——更少的移動部件，代表更少可能出錯的地方。」

Argo CD 的所有持久資料都以 Kubernetes 原生物件的形式存在（ConfigMap、Secret、CRD），Redis 只是效能快取，即使 Redis 失效，資料也不會遺失。這個設計讓災難復原（DR）極為簡單：備份 argocd namespace 即備份全部狀態。

2五大元件詳解

以下逐一深入說明每個元件的職責、部署特性、關鍵配置，以及在故障排查時應關注的面向。

🖥️
argocd-server
Deployment · 可水平擴展
API Gateway：所有外部請求的入口。服務 Web UI、CLI（argocd）、第三方 CI/CD 系統。同時負責 RBAC 執行、Session 管理、通知觸發協調。
Port :8080 gRPC+REST API · :8083 Prometheus metrics
⚙️
argocd-application-controller
StatefulSet · 支援 Sharding
Argo CD 的大腦。持續執行 Reconcile Loop：比對 desired state（Git）與 live state（K8s），觸發 sync 操作，計算 Sync Status 與 Health Status。
Port :8082 Prometheus metrics · 無對外 HTTP
📦
argocd-repo-server
Deployment · 可水平擴展
Manifest 工廠。Clone Git repo、執行 Helm template / Kustomize build / Jsonnet eval 等工具，生成最終 Kubernetes manifest，並快取結果到 Redis。
Port :8081 gRPC（僅內部） · :8084 metrics
🔑
argocd-dex-server
Deployment · 選配（可用外部 OIDC）
SSO 橋接器。作為 OIDC broker，連接外部 IdP（GitHub、Okta、LDAP、SAML 等）。若直接設定外部 OIDC provider，可跳過 Dex。
Port :5556 OIDC / HTTP · :5557 gRPC · :5558 metrics
🔴
argocd-redis
Deployment（標準）/ StatefulSet（HA Sentinel）
快取層（非持久儲存）。快取 manifest 生成結果、叢集資源狀態、Session token 等。Redis 資料可隨時丟棄並重建，不影響持久配置。
Port :6379 Redis · HA 模式加 Sentinel :26379

2.1 argocd-server 深入解析

argocd-server 同時提供 gRPC（argocd CLI 使用）與 REST/HTTP（Web UI 使用）兩種協定，由同一個 process 處理。它是 Argo CD 中唯一需要對外暴露的元件（透過 Ingress 或 LoadBalancer Service）。

在 authn（身份驗證）流程上：使用者透過 SSO 登入時，argocd-server 將請求導向 argocd-dex-server，Dex 完成與外部 IdP 的 OAuth2/OIDC 交換，並回傳 JWT token。argocd-server 解析 JWT 中的 claims（user、groups）作為後續 RBAC 的主體（subject）。

在 authz（授權）流程上：argocd-server 使用 Casbin 作為 RBAC engine，讀取 argocd-rbac-cm ConfigMap 中的 policy 定義，對每個 API 請求進行 resource / action / subject 三維度的權限驗算。v3.0 起強制使用 Fine-Grained RBAC，子資源操作需獨立授權。

⚠️

argocd-server 重新啟動的影響

argocd-server 是 stateless 的（所有狀態在 Kubernetes 或 Redis 中），可安全地滾動重啟或水平擴展。但重啟期間，UI 與 CLI 請求會暫時中斷，在生產環境中建議設定 2+ 副本（HA 模式）。

2.2 argocd-application-controller 深入解析

Application Controller 是整個 Argo CD 的核心。它以 StatefulSet 而非 Deployment 的形式部署，原因是每個副本（shard）需要維護穩定的身份，負責固定的叢集子集（Sharding）。

內部工作佇列

Application Controller 內部維護兩個佇列：

佇列類型預設 Worker 數設定方式職責
status processors20controller.status.processors計算 Application 的 Sync Status 與 Health Status
operation processors10controller.operation.processors執行實際的 sync 操作（呼叫 K8s API apply manifest）

selfHeal 的指數退避機制

當 selfHeal: true 且偵測到 drift 時，Controller 不會立即 sync，而是等待 --self-heal-timeout-seconds（預設 5 秒）。若 sync 失敗，使用指數退避（exponential backoff）策略，初始等待 2 秒，每次乘以 3，上限 300 秒：

YAML — argocd-cmd-params-cm：self-heal 退避調優
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  # selfHeal 初始等待（秒）
  controller.self.heal.timeout.seconds: "5"
  # selfHeal 退避基底（秒）
  controller.self.heal.backoff.timeout.seconds: "2"
  # 退避乘數
  controller.self.heal.backoff.factor: "3"
  # 退避上限（秒）
  controller.self.heal.backoff.cap.seconds: "300"
  # Status 計算 workers
  controller.status.processors: "20"
  # Sync operation workers
  controller.operation.processors: "10"

Sharding（叢集分片）

當 Argo CD 管理大量叢集（通常超過 20–30 個）時，單一 Application Controller 的記憶體與 CPU 負擔會顯著上升。Sharding 讓多個 Controller 副本各自負責一部分叢集，實現水平擴展：

YAML — StatefulSet 啟用 Sharding（2 replicas 範例）
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: argocd-application-controller
  namespace: argocd
spec:
  replicas: 2  # 增加副本數即啟用 Sharding
  template:
    spec:
      containers:
      - name: argocd-application-controller
        env:
        - name: ARGOCD_CONTROLLER_REPLICAS
          value: "2"  # 必須與 replicas 數量一致
        args:
        - --sharding-method=consistent-hashing  # 推薦：均勻分佈且減少重新分配
ℹ️

三種 Sharding 演算法

legacy（預設）：基於 UID 的非均勻分佈；round-robin：均勻輪詢分配；consistent-hashing（推薦）：一致性雜湊，在新增或移除叢集時最小化重新分配。v3.x 中 Dynamic Cluster Distribution 功能已正式穩定，可讓 shard 數量動態調整。

2.3 argocd-repo-server 深入解析

argocd-repo-server 是效能瓶頸最常發生的地方，因為它負責所有昂貴的 manifest 生成操作。每次生成 manifest 時，它會 fork/exec 對應的工具（helm template、kustomize build、jsonnet），這些操作會消耗大量 CPU 與記憶體。

快取機制（commit SHA 為 key）

Repo server 使用 Git commit SHA 作為快取 key，將生成的 manifest 快取到 Redis。只有當 commit SHA 改變時（或快取過期），才重新執行 manifest 生成工具。這讓大多數 Reconcile Loop 不需要重複 fork/exec，效能得以保持。

場景是否重新生成 manifest說明
Git 無新 commit，叢集有 drift否（使用快取）Reconcile 只需取得快取 manifest 與 live state 比對即可
Git 有新 commit是commit SHA 改變，快取失效，重新執行 helm/kustomize
Parameters override（UI/CLI）是參數改變視同不同的 cache key
Redis 重啟後是（第一次）快取消失，但資料可從 Git 重建，無資料遺失

並發控制

大量 Application 同時需要生成 manifest 時，repo-server 可能因 OOM（記憶體不足）而崩潰。透過 reposerver.parallelism.limit 限制並發數，避免資源耗盡：

YAML — argocd-cmd-params-cm：repo-server 效能調優
data:
  # 限制同時進行 manifest 生成的並發數（0 = 無限制）
  reposerver.parallelism.limit: "10"
  # 啟用 shallow clone（減少 git clone 流量與時間）
  reposerver.git.shallow.clone: "true"
  # repo cache 過期時間
  reposerver.repo.cache.expiration: "24h"

2.4 argocd-dex-server 深入解析

argocd-dex-server 是選配元件。若組織已有 OIDC-compliant IdP（如 Okta、Auth0、Azure AD），可以在 argocd-cm 中直接設定外部 OIDC provider，完全繞過 Dex。但 Dex 的優勢在於支援不原生支援 OIDC 的協定，例如 LDAP、SAML 2.0——Dex 可作為協定橋接器，將這些協定轉換為 OIDC 格式供 argocd-server 使用。

ℹ️

v3.0 Dex 認證主體變更

v3.0 將 RBAC 中的使用者主體從 JWT 的 sub claim 改為 federated_claims.user_id。若從 v2.x 升級且使用 Dex SSO，必須更新 argocd-rbac-cm 中的 policy 主體定義，否則所有 SSO 使用者的權限將失效。完整升級指南見 Vol 3 Ch.19。

2.5 argocd-redis 深入解析

Redis 在 Argo CD 中的定位是純快取，而非持久儲存。官方明確指出：「Redis 是快取層，可以隨時丟棄並重建，不影響任何配置資料。」這個設計決策讓 Argo CD 的災難復原非常簡單。

Redis 中儲存的內容來源失效後影響
manifest 生成結果（commit SHA → manifest）repo-server 生成後寫入下次 Reconcile 重新生成（效能短暫下降）
叢集資源 live state 快照controller 從 K8s watch 後快取下次 Reconcile 重新從 K8s API 取得
應用程式狀態快取（app-state）controller 計算後存入UI 可能暫時顯示 stale 狀態，下次 Reconcile 後恢復
Session token（使用者登入）argocd-server 登入時寫入所有使用者被登出，需重新登入（非資料遺失）
Repo 索引與 ref 快取repo-server 查詢 Git 後快取下次操作重新查詢 Git

3Reconcile Loop 深度解析

Reconcile Loop 是 Argo CD 實現「持續調和」原則的核心機制。理解這個循環的每個步驟，才能在生產環境中精確定位問題：「是 Git 拉取失敗？是 manifest 生成錯誤？還是 K8s apply 被拒絕？」

3.1 完整 Reconcile 流程（十步）

1
觸發條件滿足 application-controller
輪詢定時器到期（預設 120s + jitter 60s）、Git Webhook 通知到達、或偵測到叢集資源變化事件（Watch event）。Application 被加入「待調和」佇列。
2
請求 manifest 生成 application-controller → repo-server
Application Controller 向 Repo Server 發送 gRPC 請求，指定 repoURL、targetRevision、path 及所有參數。Repo Server 先查詢 Redis 快取。
3
取得 desired state manifest repo-server
快取命中：直接從 Redis 取得快取 manifest（μs 等級）。快取未命中：Clone / pull Git repo → 執行 helm template / kustomize build → 將結果存入 Redis 快取 → 回傳 manifest。
4
取得 live state（叢集現況） application-controller → K8s API
Controller 透過 Kubernetes Watch 機制維護所有 tracked 資源的本地快照（存於 Redis）。此步驟通常從 Redis 快照讀取，避免每次都呼叫 K8s API。
5
計算 Diff（desired vs live） application-controller
比對 desired state manifest 與 live state，考慮 ignoreDifferences 規則。若有差異，標記為 OutOfSync 並記錄具體的 diff 清單（可在 UI 的 App Diff 頁面查看）。
6
計算 Health Status application-controller
對每個 tracked 資源執行 health check（內建或自定義 Lua script），聚合得出 Application 整體 Health Status（worst-case 原則）。
7
更新 Application 狀態 application-controller → K8s API
將 Sync Status、Health Status、Resource List 等寫入 Application CRD 的 status 欄位（存於 etcd）。這是 UI 與 CLI 讀取到的「最新狀態」的來源。
8
判斷是否需要 Sync application-controller
若 Application 設定了 automated sync 且狀態為 OutOfSync，進入 Sync 流程。若為手動模式，等待使用者觸發。若 Synced，回到步驟 1 等待下次觸發。
9
執行 Sync 操作 application-controller → K8s API
依照 Sync Waves 順序（由低到高），對每個 OutOfSync 資源執行 kubectl apply（或 server-side apply）。先執行 PreSync hooks，完成後執行 PostSync hooks。
10
Reconcile 完成，等待下次觸發 application-controller
所有資源 apply 完成後，Controller 重新評估 Health Status（等待 Progressing → Healthy），更新 Operation Result，並回到步驟 1 等待下一次 Reconcile 週期。

3.2 Reconcile 觸發條件

觸發類型機制延遲設定位置
定期輪詢（預設）timeout.reconciliation 計時器到期最長 180s（120s + 60s jitter）argocd-cm: timeout.reconciliation
Git WebhookGitHub/GitLab push event → argocd-server → controller幾乎即時（<1s）Ingress + Git 倉庫 Webhook 設定
叢集資源變化Kubernetes Watch event 觸發幾乎即時內建，無需設定
手動 RefreshUI 點擊 Refresh / argocd app get --refresh即時使用者操作
Hard Refresh清除快取並重新生成 manifest即時（+git pull 時間）app get --hard-refresh

3.3 時間參數調優：解決 Thundering Herd

當 Argo CD 管理數百個 Application 時，預設的 120s 輪詢間隔會導致所有 Application 在相同時間點同時觸發 Reconcile，對 repo-server 和 K8s API server 造成瞬間高峰（Thundering Herd 問題）。透過 jitter 可以將負載分散：

📊 Jitter 效果：無 jitter vs 有 jitter（500 個 Application）
gantt title Reconcile 負載分佈比較（3 分鐘週期） dateFormat mm:ss section 無 Jitter（突波） 500 apps 同時 Reconcile :crit, t1, 00:00, 30s 閒置期 :t2, after t1, 150s 下次突波 :crit, t3, 03:00, 30s section 有 Jitter（60s） 分散式 Reconcile :active, j1, 00:00, 3m
YAML — argocd-cm：Reconcile 時間調優
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 輪詢間隔（預設 120s）。使用 Webhook 的環境可調高至 600s
  timeout.reconciliation: "120s"

  # Jitter 上限（預設 60s）。每個 App 的實際間隔 = 120s + random(0, 60s)
  # 大型部署（500+ apps）建議調高至 120s 以更好地分散負載
  timeout.reconciliation.jitter: "60s"

  # 設為 0 可完全停用定期輪詢（僅依賴 Webhook）
  # timeout.reconciliation: "0"
💡

最佳實踐：結合 Webhook + 加長輪詢間隔

生產環境建議：設定 Git Webhook（消除延遲）+ 將 timeout.reconciliation 調高至 600s（減少不必要的輪詢）+ 設定足夠的 jitter（分散殘餘輪詢負載）。這三招組合可讓 repo-server 的負載降低 80% 以上。

4持久化儲存：etcd vs Redis vs Git

理解 Argo CD 的資料儲存層次，是規劃備份與 DR 策略的基礎。Argo CD 沒有自己的資料庫，而是巧妙地利用 Kubernetes 本身作為持久化後端：

資料類型儲存位置持久性備份需求
Application / AppProject CRDetcd（Kubernetes objects）永久持久備份 argocd namespace 即可
argocd-cm（UI/behavior 設定）etcd（ConfigMap）永久持久同上
argocd-rbac-cm（RBAC policy）etcd（ConfigMap）永久持久同上
argocd-secret（admin 密碼、token）etcd（Secret）永久持久同上（加密備份）
Cluster / Repo 憑證etcd（Secret）永久持久同上（加密備份）
Manifest 快取Redis揮發性（可重建）不需要
Live state 快照Redis揮發性（可重建）不需要
Session tokenRedis揮發性（重啟後登出）不需要
Application desired state（Git）Git repo永久（版本控制）Git 本身負責
💡

備份只需一個指令

使用 argocd admin export 可將所有 Argo CD 設定（Application、AppProject、ClusterSecret、RepositorySecret、ConfigMap）匯出為 YAML 格式，用於備份或遷移。還原時使用 argocd admin import 即可。完整 DR 流程見 Vol 3 Ch.19。

5元件故障排查：快速定位問題

根據問題現象，可以快速判斷應查看哪個元件的日誌：

問題現象可能元件查看方向
UI 無法登入 / 無法存取argocd-serverserver pod logs、Ingress 設定、TLS 憑證
SSO 登入失敗argocd-dex-serverdex logs、argocd-cm OIDC 設定、IdP 回調 URL
App 一直顯示 Unknown（無法計算 diff）argocd-repo-serverrepo-server logs（git clone 失敗？manifest 解析錯誤？）
App Sync 失敗（manifest 生成錯誤）argocd-repo-serverrepo-server logs、argocd app logs --repo-server
App Sync 失敗（K8s apply 被拒絕）application-controllercontroller logs、K8s events（kubectl get events -n target-ns）

📌 Key Takeaways

  • 🏗️五大元件各司其職：argocd-server（API Gateway + authn/authz）、application-controller（Reconcile Loop 核心，StatefulSet）、repo-server（manifest 生成工廠，Deployment）、dex（SSO 橋接器，選配）、redis（純快取，可隨時重建）。
  • 🔄Reconcile Loop 的十個步驟：觸發 → 請求 manifest → 取得快取或重新生成 → 取得 live state → 計算 diff → 計算 health → 更新 Application status → 判斷是否需要 sync → 執行 sync（按 Wave 順序）→ 完成後等待下次觸發。
  • ⏱️Reconcile 時間調優三要素：timeout.reconciliation（輪詢間隔）+ timeout.reconciliation.jitter（分散負載的隨機延遲）+ Git Webhook（消除輪詢延遲）。三者結合可大幅降低 repo-server 負載。
  • 💾持久資料在 etcd，快取在 Redis：Application CRD、ConfigMap、Secret 均持久存在 Kubernetes etcd 中，Redis 失效後無資料遺失。備份 argocd namespace 即完整備份 Argo CD 設定。
  • ⚙️application-controller 是 StatefulSet：原因是支援 Sharding（每個 replica 負責固定叢集子集）。管理 20+ 叢集時考慮啟用 Sharding，演算法推薦 consistent-hashing。
  • 🔍問題定位公式：UI/登入問題 → argocd-server；SSO 失敗 → dex；manifest 生成失敗 / Unknown 狀態 → repo-server；sync 失敗 / Reconcile 停滯 → application-controller；全員登出 → redis 重啟。
