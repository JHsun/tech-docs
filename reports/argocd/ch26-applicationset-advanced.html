ApplicationSet 進階
Templating、Strategy 與 Sync 控制

前三章涵蓋 generators 全部基礎與進階用法。本章深入ApplicationSet 的真正威力來源：goTemplate 進階（sprig 函數、條件邏輯、迴圈）、templatePatch 局部覆蓋（同一 ApplicationSet 中部分 App 與其他不同）、syncPolicy 三層控制（applicationsSync / preserveResourcesOnDeletion）、ignoreApplicationDifferences（允許 image-updater 修改不被覆蓋）、Strategy.RollingSync 分批滾動（生產環境變更的安全保險）、Progressive Sync 完整模式。

📋

前置：已完整理解 Ch.23-25（ApplicationSet 概念、List/Cluster/Git generators、Matrix/Merge/PR generators）。理解 Helm goTemplate / sprig 基本用法。理解 Kubernetes deletion finalizer 概念。

🎯 學習目標

  • 精通 goTemplate 進階：sprig 函數（upper / contains / default / quote / fromJson）、條件邏輯（if/else/end）、迴圈（range）、變數（$x := .y）
  • 使用 templatePatch 為部分 generated Application 套用差異化設定（如 prod 不開 auto-sync、cilium 加 ServerSideApply）
  • 理解 syncPolicy 三層：① applicationsSync（controller 對 Application 的操作權限）；② preserveResourcesOnDeletion（刪除 ApplicationSet 時是否保留 Application）；③ Application 自身的 syncPolicy（控制 K8s 資源 sync）
  • 用 ignoreApplicationDifferences 配合 Image Updater / 手動 override 場景，避免 controller 不斷把改動覆蓋回去
  • 掌握 Strategy.RollingSync 的 steps + matchExpressions + maxUpdate，實現「先 dev 再 staging 再 prod」的安全部署
  • 理解 deletionOrder（Reverse 用於 dependent service 的反向拆除）
  • 用 argocd appset create --dry-run 預覽 ApplicationSet 將產生的 Application，避免破壞性變更
  • 避開 v3.x 已知 bug：templatePatch 對 syncPolicy 部分欄位無效（issue #26592）、ignoreApplicationDifferences 對 list 限制（MergePatch 全替換）

1goTemplate 進階：sprig 函數與邏輯

1.1 sprig 函數庫

啟用 goTemplate: true 後，所有 sprig 函數都可用。最常用的字串、條件、轉換函數：

類別函數用途範例
字串upper / lower / title{{ upper .name }}
字串trim / trimPrefix / trimSuffix{{ trimPrefix "team-" .project }}
字串replace / contains / hasPrefix / hasSuffix{{ if hasPrefix "prod-" .cluster }}...{{ end }}
條件default{{ default "us-east-1" .region }}
條件eq / ne / gt / lt{{ if eq .env "prod" }}...{{ end }}
編碼quote / squote / b64enc / b64dec{{ .image | quote }} 產生 "image"
轉換toJson / fromJson / toYaml{{ .config | fromJson }}
數學add / sub / mul / div{{ mul .replicas 2 }}
列表list / first / last / contains{{ if has "prod" .labels }}...{{ end }}
字典index / hasKey / get{{ index .metadata.labels "team" }}
⚠️

含 hyphen 的 key 必須用 index 存取

K8s label 常用 hyphen（如 team-name），但 Go template 的 dot 語法把 hyphen 當減號。必須用 index 函數：{{ index .metadata.labels "team-name" }}。同樣適用 annotation 中常見的 dot key（如 kubernetes.io/managed-by）。

1.2 條件邏輯與迴圈

YAML — goTemplate 條件、迴圈、變數綜合範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-env-deploy
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - list:
        elements:
          - name: api
            env: prod
            replicas: "5"
            tags: "backend,critical"
          - name: web
            env: staging
            replicas: "2"
            tags: "frontend"

  template:
    metadata:
      # 1) default 函數：region 沒提供時用預設
      name: '{{.name}}-{{.env}}-{{ default "us" .region }}'

      labels:
        app: '{{.name}}'
        # 2) trimPrefix + upper：env 大寫，去除可能的 "env-" 前綴
        env: '{{ .env | trimPrefix "env-" | upper }}'

      annotations:
        # 3) 條件：if/else 視 env 加 critical annotation
        priority: '{{ if eq .env "prod" }}P0{{ else }}P2{{ end }}'
        # 4) hasPrefix 判斷
        tier: '{{ if hasPrefix "api" .name }}backend{{ else }}frontend{{ end }}'

    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/{{.name}}.git
        targetRevision: '{{ if eq .env "prod" }}main{{ else }}develop{{ end }}'
        path: manifests
        helm:
          parameters:
            # 5) 變數：先計算再使用
            # {{- $totalReplicas := mul .replicas 2 -}}（在 templatePatch 中可用）
            - name: replicas
              value: '{{.replicas}}'
            - name: env
              value: '{{.env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.name}}-{{.env}}'
ℹ️

template 與 templatePatch 的差異

template 區塊本身是結構化 YAML，goTemplate 只能用在 string value 中（如 name、value 欄位）；templatePatch 是純文字 YAML，整段都被當 template 處理，可以用 range、{{- if -}} 動態產生整段 YAML 結構（甚至條件性插入整個 syncPolicy 區塊）。複雜邏輯應放在 templatePatch。

2templatePatch 局部覆蓋

2.1 基本用法

templatePatch 是「strategic merge patch」字串，在 template 渲染後再對結果套用 patch。最大優勢：整段都是 template，可以用 range / if-else 動態產生整個區塊：

YAML — templatePatch 為 cilium 加特殊設定
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-addons
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - git:
        repoURL: https://github.com/myorg/addons.git
        directories:
          - path: addons/*

  template:
    metadata:
      name: '{{.path.basename}}'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/addons.git
        path: '{{.path.path}}'
        helm:
          valueFiles:
            - values.yaml
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.path.basename}}'
      syncPolicy:
        automated: {prune: true, selfHeal: true}
        syncOptions:
          - CreateNamespace=true

  # templatePatch 對特定 App 套用額外設定
  templatePatch: |
    {{- if eq .path.basename "cilium" }}
    spec:
      ignoreDifferences:
        - group: monitoring.coreos.com
          kind: ServiceMonitor
          name: ""
          jsonPointers:
            - /spec
      syncPolicy:
        syncOptions:
          - ServerSideApply=true   # 避免 annotations too long
          - CreateNamespace=true
    {{- end }}

    {{- if hasPrefix "cert-manager" .path.basename }}
    spec:
      syncPolicy:
        syncOptions:
          - ServerSideApply=true
          - CreateNamespace=true
          - Replace=true             # cert-manager CRD 用 Replace
    {{- end }}

2.2 條件式 syncPolicy（dev 自動、prod 手動）

YAML — 依環境條件啟用 auto-sync
spec:
  goTemplate: true
  generators:
    - list:
        elements:
          - env: dev
            namespace: dev-apps
          - env: test
            namespace: test-apps
          - env: prod
            namespace: prod-apps

  template:
    metadata:
      name: 'my-app-{{.env}}'
    spec:
      project: apps
      source:
        repoURL: https://github.com/myorg/gitops.git
        path: 'apps/my-app/overlays/{{.env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.namespace}}'

  templatePatch: |
    # prod 環境不啟用 auto-sync（必須手動審核）
    {{- if ne .env "prod" }}
    spec:
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
    {{- end }}

2.3 已知 bug：templatePatch 對 syncPolicy 部分欄位無效

⚠️

v3.1.x 已知 issue #26592

當 ApplicationSet 同時使用 strategy.RollingSync + templatePatch 時，templatePatch 對 spec.syncPolicy.automated 與 spec.syncPolicy.preserveResourcesOnDeletion 的修改不會套用到 generated Application。workaround：① 不要在 templatePatch 中修改 syncPolicy.automated，改在 template 主體寫死；② 或暫時拿掉 RollingSync，改用 AllAtOnce（會犧牲分批安全部署）；③ 等待 upstream 修復。

3syncPolicy 三層：誰能對 Application 做什麼？

ApplicationSet 中有三個層級的 syncPolicy，職責完全不同，極易混淆：

層級位置控制什麼？
1. ApplicationSet syncPolicy spec.syncPolicy ApplicationSet controller 對 Application 物件的操作（create/update/delete）
2. Application syncPolicy（template 內） spec.template.spec.syncPolicy application-controller 對 K8s 資源的 sync（auto-sync、prune、selfHeal）
3. preserveResourcesOnDeletion spec.syncPolicy.preserveResourcesOnDeletion ApplicationSet 被刪除時，generated Application 是否保留

3.1 applicationsSync：controller 操作權限

YAML — applicationsSync 四種模式
spec:
  syncPolicy:
    # 控制 ApplicationSet controller 能對 Application 物件做什麼
    applicationsSync: create-update
    # 可選值：
    # - sync          (預設) controller 可建立、更新、刪除 Application
    # - create-only   只建立，不更新（手動修改 Application 不會被覆蓋）
    # - create-update 建立 + 更新，但不刪除（Application 從 generator 結果消失也保留）
    # - create-delete 建立 + 刪除，但不更新
applicationsSynccreateupdatedelete適用
sync（預設）✅✅✅標準場景
create-only✅❌❌讓 tenant 自由修改 generated Application 不被 controller 覆蓋
create-update✅✅❌避免誤刪 production Application（generator 故障時不會大量 delete）
create-delete✅❌✅少見，避免 controller 改動 Application spec
💡

生產環境推薦 create-update

避免 generator 故障（如 cluster Secret label 被誤改）造成大量 production Application 被自動刪除。create-update 模式下，generator 結果消失只會在 ApplicationSet status 顯示 stale，不會 cascade 刪除 Application，給運維人員時間調查。

3.2 preserveResourcesOnDeletion

YAML — preserveResourcesOnDeletion 行為
spec:
  syncPolicy:
    # 預設 false（v3.0+）：刪除 ApplicationSet 時 cascade 刪除所有 generated Application
    preserveResourcesOnDeletion: true     # 設為 true 保留

## true 的使用場景：
## 1. 生產環境保險：意外刪除 ApplicationSet 不會造成大規模 outage
## 2. 重構：拿掉舊 ApplicationSet 改用新的，但維持 Application 不重建（避免 sync 中斷）
## 3. 遷移過程：從 ApplicationSet 改回手動管理 Application

## false 的使用場景：
## 1. ephemeral 環境：刪 ApplicationSet 自動清理 Application 與 K8s 資源
## 2. 測試環境：快速 reset
## 3. PR preview：PR generator 偵測 PR 關閉就清理
⚠️

preserveResourcesOnDeletion: true 必須加 finalizer

v3.x 起，啟用 preserveResourcesOnDeletion: true 時，ApplicationSet controller 會自動為 ApplicationSet 加上 resources-finalizer.argocd.argoproj.io finalizer，確保正確處理刪除流程。如果是手動管理的舊 ApplicationSet 沒有此 finalizer，建議手動加上。

4ignoreApplicationDifferences：允許外部修改

當 Image Updater、CI/CD pipeline、或人類運維者直接修改 Application（如更新 image tag），ApplicationSet controller 預設會把改動覆蓋回去（因為 generator 重新渲染後不含這些改動）。ignoreApplicationDifferences 讓 controller 忽略特定欄位的差異：

YAML — ignoreApplicationDifferences 完整範例
spec:
  ignoreApplicationDifferences:
    # Rule 1：對所有 generated Application 套用
    # 用 jsonPointer（RFC 6901）指定欄位
    - jsonPointers:
        - /spec/source/targetRevision      # 允許 UI/CLI 修改 image tag
        - /spec/source/helm/parameters      # 允許 Image Updater 改 helm values

    # Rule 2：對特定 Application 套用（用 name 過濾）
    - name: my-app-prod
      jqPathExpressions:
        - .spec.syncPolicy.automated      # 允許手動暫停 prod auto-sync

    # Rule 3：用 jq 進行進階過濾（v2.10+）
    - jqPathExpressions:
        # 允許某個 Helm source 的 valuesObject 被修改
        - .spec.sources[]?|select(.repoURL == "https://mycharts.github.io").helm.valuesObject

## ── 常見使用場景 ──────────────────────────────────────
# 1. 配合 Argo CD Image Updater：
#    - jsonPointers: [/spec/source/helm/parameters]
# 2. 暫時 pin 特定 commit：
#    - jsonPointers: [/spec/source/targetRevision]
# 3. 暫時關閉某 App auto-sync：
#    - name: my-app-prod, jsonPointers: [/spec/syncPolicy/automated]
# 4. Progressive Sync 中個別 Application 跳過：
#    - jsonPointers: [/metadata/labels/sync]
⚠️

MergePatch list 限制（重要！）

ApplicationSet controller 用 MergePatch（不是 StrategicMergePatch），這意味著「list 一旦變更整個被替換」。例如有多個 sources 的 Application，即使 ignoreApplicationDifferences 標記了 source[0].targetRevision，只要 source[1] 改變，整個 sources list 會被替換，source[0].targetRevision 也會被覆蓋。workaround：① 拆成多個 ApplicationSet；② 用 jqPathExpressions 更精確；③ Issue #21909 追蹤 templatePatch 增強。

5Strategy.RollingSync：分批滾動部署

5.1 基本範例

當 ApplicationSet 修改影響數十、數百個 Application（如 image tag 升級），同時 sync 全部的風險巨大。strategy.RollingSync 將 update 分批執行，等前一批 Healthy 才執行下一批：

YAML — RollingSync 三階段環境推進
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: multi-env
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  # Strategy 區塊：定義部署策略
  strategy:
    type: RollingSync
    rollingSync:
      steps:
        # Step 1：先所有 dev cluster
        - matchExpressions:
            - key: env
              operator: In
              values: [dev]
          # 不設 maxUpdate = 全部同時更新

        # Step 2：staging（等 dev 全部 Healthy 才開始）
        - matchExpressions:
            - key: env
              operator: In
              values: [staging]

        # Step 3：prod（等 staging 全 Healthy 才開始）
        - matchExpressions:
            - key: env
              operator: In
              values: [prod]
          maxUpdate: 1     # prod 一次只更新 1 個（最謹慎）

  generators:
    - clusters:
        selector:
          matchLabels:
            argocd.argoproj.io/secret-type: cluster

  template:
    metadata:
      name: 'app-{{.name}}'
      labels:
        # 重要！label 必須對應 strategy 的 matchExpressions
        env: '{{ index .metadata.labels "environment" }}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/app.git
        targetRevision: main
        path: manifests
      destination:
        server: '{{.server}}'
        namespace: my-app

5.2 maxUpdate 控制併發

maxUpdate 值意義適合
不設定預設 100%（無限制併發）非關鍵環境（dev / staging）
1一次只更新 1 個 Application關鍵 prod 部署
3一次最多更新 3 個中等規模、有限併發容量
"50%"百分比表示大規模部署（10 個 cluster 一次更新 5 個）
0暫停此步驟緊急停止滾動的方法（修改 maxUpdate=0 寫入 Git）

5.3 deletionOrder（v3.x 新功能）

YAML — Reverse 反向刪除順序
spec:
  strategy:
    type: RollingSync
    # 控制刪除順序（v3.0+）
    deletionOrder: Reverse      # Reverse | AllAtOnce（預設）
    rollingSync:
      steps:
        # Step 1：dev 先建立，最後刪除
        - matchExpressions:
            - key: env
              operator: In
              values: [dev]

        # Step 2：prod 後建立，先刪除
        - matchExpressions:
            - key: env
              operator: In
              values: [prod]

## 適用：依賴關係明確的服務（frontend 依賴 backend）
## 部署：先 backend → 後 frontend
## 拆除：先 frontend → 後 backend（避免 backend 被刪後 frontend 報錯）

5.4 RollingSync 的重要警告

⚠️

RollingSync 強制關閉 generated Application 的 auto-sync

當 ApplicationSet 啟用 strategy.RollingSync，所有 generated Application 的 syncPolicy.automated 會被強制 disable（即使你在 template 中寫了 automated: {prune: true}）。RollingSync controller 會在每個 step 主動 trigger sync，類似 UI 點 Sync 按鈕。這是設計使然：避免 auto-sync 與 RollingSync 互相競爭。

applicationset-controller log 會印警告：warn: Application has automated syncPolicy enabled, but RollingSync requires it disabled。實務上：① 重要環境用 RollingSync 取代 auto-sync；② 非關鍵環境改用 AllAtOnce + auto-sync。

6Progressive Sync 完整模式

結合 RollingSync + ignoreApplicationDifferences + Manual Approval，實現完整的 Progressive Sync workflow——逐個環境推進，每階段需手動確認才繼續：

YAML — Progressive Sync：dev → qa(manual) → prod
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: progressive-deploy
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  syncPolicy:
    applicationsSync: create-update     # 不允許 cascade delete
    preserveResourcesOnDeletion: true      # 刪除 ApplicationSet 不影響 Application

    # 允許手動加 sync=false label 跳過 Progressive Sync
  ignoreApplicationDifferences:
    - jsonPointers:
        - /metadata/labels/sync          # 允許手動加 sync=false 略過

  strategy:
    type: RollingSync
    rollingSync:
      steps:
        # Step 1：自動部署所有 dev（除非 sync=false）
        - matchExpressions:
            - key: env
              operator: In
              values: [dev]
            - key: sync
              operator: NotIn
              values: ["false"]
          maxUpdate: "100%"

        # Step 2：QA（手動觸發！matchExpressions 不匹配，需 CLI 介入）
        - matchExpressions:
            - key: env
              operator: In
              values: [qa-manual-approval]    # 不會自動匹配任何 App
          maxUpdate: "0%"     # 0% 表示停在這一步

        # 觸發後續：argocd app sync <app-name> 手動推進
        # 或修改 Git 把 maxUpdate 改成 100% commit 觸發

        # Step 3：所有 prod（一次只 1 個）
        - matchExpressions:
            - key: env
              operator: In
              values: [prod]
            - key: sync
              operator: NotIn
              values: ["false"]
          maxUpdate: 1      # prod 一次 1 個，最謹慎

  generators:
    - clusters:
        selector:
          matchLabels:
            argocd.argoproj.io/secret-type: cluster

  template:
    metadata:
      name: 'app-{{.name}}'
      labels:
        env: '{{ index .metadata.labels "environment" }}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myorg/app.git
        targetRevision: main
        path: manifests
      destination:
        server: '{{.server}}'
        namespace: my-app
💡

手動推進 Progressive Sync 的兩種方式

① argocd CLI：argocd app sync <app-name> 直接觸發特定 Application 的 sync（即使在 RollingSync 等待中也會推進）；② UI 按鈕：在 Application 卡片點擊 "SYNC" 按鈕，效果相同；③ Git commit：修改 ApplicationSet 中 maxUpdate 從 0% → 100% 並 commit，整個 step 變成自動執行。

用 sync=false label 暫時排除特定 Application

Bash — 緊急排除某個 Application 的 RollingSync
# 場景：production 中 app-prod-eu-west 出問題，
# 想升級其他 prod 但不要碰這個

# 給該 Application 打 label sync=false
$ kubectl label application app-prod-eu-west sync=false -n argocd

# 因為 ApplicationSet 的 step 中 matchExpressions 排除 sync=false，
# 此 App 會被 RollingSync 跳過，其他 prod 繼續更新

# 因為 ignoreApplicationDifferences 包含 /metadata/labels/sync，
# controller 不會把這個 label 改回去

# 修復後移除 label，下次 RollingSync 會包含這個 App
$ kubectl label application app-prod-eu-west sync- -n argocd

7dry-run 與除錯

ApplicationSet 變更影響範圍大（一改全改），生產環境部署前必須 dry-run 預覽：

Bash — dry-run 預覽 Application
# 1. CLI dry-run（推薦）
$ argocd appset create --dry-run ./appset.yaml -o json | \
    jq -r '.status.resources[].name'
# app-cluster-1
# app-cluster-2
# app-cluster-3

# 2. 預覽完整 spec（不只 name）
$ argocd appset create --dry-run ./appset.yaml -o yaml

# 3. 比較變更前後（先取得目前狀態，再 dry-run，diff）

📌 Key Takeaways

  • 📝goTemplate + sprig 是 ApplicationSet 的真實威力：upper / trimPrefix / hasPrefix / contains / default / index / quote / fromJson 涵蓋 90% 場景。含 hyphen 的 key 必用 index 函數（如 K8s label）。template 主體只能用在 string value，複雜邏輯放 templatePatch。
  • 🩹templatePatch 是局部覆蓋的最強工具：整段是 template，可用 if / range / with 動態產生整個區塊。常見場景：cilium 加 ServerSideApply、cert-manager 加 Replace、prod 不啟用 auto-sync。v3.1.x 有 bug（issue #26592）：templatePatch 對 syncPolicy.automated 在 RollingSync 模式下無效。
  • 📊syncPolicy 三層職責不同：① applicationsSync（controller 對 Application 物件的 CRUD 權限）；② Application template 內的 syncPolicy（K8s 資源 sync）；③ preserveResourcesOnDeletion（刪 ApplicationSet 時的行為）。生產環境推薦 applicationsSync: create-update + preserveResourcesOnDeletion: true，避免 generator 故障造成大量 Application 被刪。
  • 🚫ignoreApplicationDifferences 用於外部修改：用 jsonPointer 或 jqPathExpressions 指定欄位讓 controller 忽略。常見搭配 Argo CD Image Updater（忽略 helm.parameters）、暫停 prod auto-sync（忽略 syncPolicy.automated）、Progressive Sync 排除特定 App（忽略 sync label）。注意 MergePatch list 限制——多 source 場景會整個 list 替換。
  • 🔄Strategy.RollingSync 是生產變更的安全保險：steps + matchExpressions + maxUpdate 三維度控制。dev (100%) → staging (100%) → prod (1) 的標準漏斗。RollingSync 強制關閉 generated Application 的 auto-sync（設計使然），controller 主動觸發 sync 類似手動點 Sync 按鈕。
  • 🎚️maxUpdate 0% 是緊急剎車：commit ApplicationSet YAML 把 maxUpdate 設為 0% 暫停滾動。也可用 "50%" 等百分比。配合 deletionOrder: Reverse（v3.x）實現 frontend 先刪 backend 後刪的依賴順序拆除。
  • ✋Progressive Sync 完整模式：RollingSync + ignoreApplicationDifferences + manual approval step（matchExpressions 不匹配 + maxUpdate 0%）+ sync=false label 排除機制。每階段需 CLI 或 UI 手動推進，最高安全性。用 label 機制可緊急隔離特定 Application不被升級。
  • 🔍變更前必 dry-run：argocd appset create --dry-run -o json | jq '.status.resources[].name' 列出將產生的 Application。配合 diff 比對新舊清單。生產 SOP：dry-run → staging 驗證 → RollingSync → 監控 log → maxUpdate=0% 緊急停止。
