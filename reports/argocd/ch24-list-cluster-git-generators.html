List / Cluster / Git
Generators 實戰精通

Ch.23 概述了 8 種 generators，本章深入三個最常用的 generator——這三個涵蓋 80% 的真實使用場景。每個 generator 完整介紹欄位、產生的 parameters、selector 過濾、最佳實踐與常見坑。最後提供整合三者的真實範例：mono-repo + multi-cluster + per-tenant config。

📋

前置：已閱讀 Ch.23（ApplicationSet 概念與 8 種 generators 全覽）。理解 Vol 3 Ch.16 的 cluster Secret 結構（labels + name + server + config）。理解 goTemplate 語法。

🎯 學習目標

  • 精通 List generator：基本元素、elementsYaml 動態載入、適用場景
  • 精通 Cluster generator：產生的 parameters（name / server / metadata.labels / metadata.annotations / values）、selector / matchExpressions 過濾、in-cluster 的 secret 陷阱
  • 精通 Git Directory generator：path glob、exclude 過濾、pathParamPrefix（避免 Matrix 衝突）
  • 精通 Git File generator：讀取 JSON / YAML config 檔案，將內容作為 parameters
  • 用 Git webhook 大幅縮短 Git generator 的偵測延遲（從 3 分鐘到 10 秒）
  • 能設計三 generator 整合的真實架構（mono-repo + multi-cluster + per-tenant config）
  • 避開常見坑：cluster generator 不匹配 in-cluster、Git glob 太寬、未啟用 webhook 導致延遲

1List Generator 實戰

1.1 基本用法

List 是最簡單的 generator——直接列出 key/value 對，作為 parameters 餵給 template：

YAML — List Generator 基本範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-list
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - list:
        elements:
          # 每個元素是一組 parameters，可任意 key
          - cluster: engineering-dev
            url: https://kubernetes.default.svc
            env: dev
            replicas: "1"      # 注意：值必須是字串
          - cluster: engineering-prod
            url: https://prod.example.com
            env: prod
            replicas: "3"

  template:
    metadata:
      name: '{{.cluster}}-guestbook'
      labels:
        env: '{{.env}}'
    spec:
      project: my-project
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps.git
        targetRevision: HEAD
        path: 'guestbook'
        helm:
          parameters:
            - name: replicas
              value: '{{.replicas}}'
      destination:
        server: '{{.url}}'
        namespace: 'guestbook-{{.env}}'

產生的 Application 數量：等於 elements 列表長度（此例 = 2）。每個 element 的所有 key 都可在 template 中以 {{.key}} 引用。

⚠️

YAML 中所有 value 都必須是 string

List generator 的 element values 只能是字串。replicas: 3 會報錯，必須寫 replicas: "3"。即使是布林值也要用字串：enabled: "true"。在 template 中需要時可用 sprig 函數轉換（如 {{ atoi .replicas }}）。

1.2 elementsYaml 動態載入（v2.10+）

傳統 List generator 是靜態硬編碼。v2.10+ 新增 elementsYaml 欄位，可從 Matrix 的前一個 generator 載入動態 YAML 字串作為列表，極大提升彈性：

YAML — List + elementsYaml 動態載入
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: elements-yaml
  namespace: argocd
spec:
  goTemplate: true
  generators:
    - matrix:
        generators:
          # 第一階段：Git generator 取得 file 內容
          - git:
              repoURL: https://github.com/myorg/configs.git
              revision: HEAD
              files:
                - path: "tenants/tenants.yaml"

          # 第二階段：List generator 用 Git 取得的內容
          - list:
              elementsYaml: "{{ .tenants | toYaml }}"
              # 取 tenants.yaml 中 .tenants 欄位（陣列）作為 elements

  template:
    metadata:
      name: 'tenant-{{.name}}'
    spec:
      source:
        repoURL: https://github.com/myorg/team-{{.name}}.git
      destination:
        server: '{{.server}}'
        namespace: '{{.namespace}}'
YAML — 對應的 tenants.yaml（在 Git）
# tenants/tenants.yaml
tenants:
  - name: alpha
    server: https://kubernetes.default.svc
    namespace: alpha-prod
  - name: beta
    server: https://staging.example.com
    namespace: beta-staging
  - name: gamma
    server: https://prod.example.com
    namespace: gamma-prod

效益：tenant 增減只需修改 Git 中的 tenants.yaml，無需修改 ApplicationSet 物件本身——更符合 GitOps 哲學。

1.3 List Generator 適用場景

場景適合？說明
3-10 個固定 cluster✅最直觀
每個 element 有獨特設定✅parameter 直接定義在 element 內
動態元素清單（從 Git 讀）✅用 elementsYaml + Matrix

tenant 自治（不希望 platform 改 ApplicationSet）⚠️用 elementsYaml 從 Git 讀；或用 Git generator

2Cluster Generator 實戰（最重要！）

Cluster generator 從 Argo CD 已註冊的 cluster Secret 動態取得 cluster 列表（Vol 3 Ch.16 介紹過 cluster Secret 結構）。cluster 增減時 controller 自動響應——這是 multi-cluster 場景最常用的 generator。

2.1 產生的 Parameters

Cluster generator 為每個匹配的 cluster 產生以下 parameters（goTemplate 語法）：

Parameter來源範例
{{.name}}cluster Secret 的 data.nameprod-us-east
{{.server}}cluster Secret 的 data.serverhttps://prod.example.com
{{.metadata.labels}}cluster Secret 的 metadata.labels（含自訂 label）{environment: prod, region: us-east}
{{.metadata.annotations}}cluster Secret 的 metadata.annotations{platform: eks, ...}
{{.nameNormalized}}name 經過 normalize（去除特殊字元，符合 K8s 名稱規範）prod-us-east
{{.values.xxx}}從 generator 的 values 區塊（自訂額外資料）see §2.4
{{.project}}cluster Secret 的 data.project（如有）platform

2.2 selector 與 matchExpressions 過濾

YAML — Cluster generator selector 完整範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: monitoring-prod
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - clusters:
        selector:
          # 1. matchLabels（精確匹配）
          matchLabels:
            argocd.argoproj.io/secret-type: cluster     # 必要 label
            environment: production

          # 2. matchExpressions（複雜邏輯）
          matchExpressions:
            # 範圍匹配
            - key: region
              operator: In
              values: [us-east-1, us-west-2, eu-west-1]

            # 排除特定 cluster
            - key: disable-monitoring
              operator: DoesNotExist

            # 必須有此 label（任何值）
            - key: tier
              operator: Exists

  template:
    metadata:
      name: 'monitoring-{{.name}}'
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/monitoring.git
        path: 'environments/{{index .metadata.labels "environment"}}'
      destination:
        server: '{{.server}}'
        namespace: monitoring

2.3 in-cluster 的 secret 陷阱

⚠️

cluster selector 預設不會匹配 in-cluster！

Argo CD 安裝所在的 in-cluster 沒有對應的 cluster Secret（用 SA 自動連線）。Cluster generator 的 selector 依賴 Secret 上的 label——所以 in-cluster 永遠不被匹配。解法：

YAML — 為 in-cluster 建立 Secret（讓 selector 能匹配）
apiVersion: v1
kind: Secret
metadata:
  name: in-cluster-config
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster     # 必要
    # 自訂 label（讓 generator 能匹配）
    environment: production
    platform-managed: "true"
type: Opaque
stringData:
  name: in-cluster
  server: https://kubernetes.default.svc
  # 不需要 config 欄位（in-cluster 用 SA 連線）

## 替代方案：用 List generator 顯式包含 in-cluster
## generators:
##   - clusters: { selector: { matchLabels: ... } }
##   - list:
##       elements:
##         - name: in-cluster
##           server: https://kubernetes.default.svc

2.4 values 自訂欄位（per-cluster 自訂）

Cluster Secret 上的 label 是 K8s label（受字元限制）。對於更複雜的 per-cluster 設定，用 generator 的 values 區塊：

YAML — Cluster generator values 範例
generators:
  - clusters:
      selector:
        matchLabels:
          environment: production
      # 為每個匹配的 cluster 額外注入 values
      values:
        # 可使用其他 parameter 動態組合
        replicas: '{{ if eq (index .metadata.labels "tier") "premium" }}5{{ else }}2{{ end }}'
        monitoringEndpoint: 'https://prom.{{index .metadata.labels "region"}}.example.com'
        slackChannel: '#alerts-{{index .metadata.labels "team"}}'

template:
  metadata:
    name: 'app-{{.name}}'
  spec:
    source:
      helm:
        parameters:
          - name: replicas
            value: '{{.values.replicas}}'
          - name: monitoring.endpoint
            value: '{{.values.monitoringEndpoint}}'

3Git Directory Generator 實戰

Git Directory generator 掃描 Git repo 中符合 path glob 的目錄，每個目錄產生一組 parameters。適合 mono-repo 自動化：

3.1 基本用法

YAML — Git Directory 基本範例
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: cluster-addons
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - git:
        repoURL: https://github.com/myorg/platform-addons.git
        revision: main
        directories:
          # 對 cluster-addons/ 下每個子目錄產生一個 Application
          - path: cluster-addons/*
          # * 只匹配一層；** 匹配多層

  template:
    metadata:
      name: '{{.path.basename}}'     # 用目錄名稱作為 App 名
    spec:
      project: platform
      source:
        repoURL: https://github.com/myorg/platform-addons.git
        targetRevision: main
        path: '{{.path.path}}'           # 完整 path
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{.path.basename}}'
      syncPolicy:
        syncOptions:
          - CreateNamespace=true

產生的 parameters：

Parameter說明範例（path = cluster-addons/cert-manager）
{{.path.path}}完整路徑cluster-addons/cert-manager
{{.path.basename}}最後一段（檔名）cert-manager
{{.path.basenameNormalized}}basename 經 normalizecert-manager
{{.path.segments}}路徑切分後的陣列["cluster-addons", "cert-manager"]
{{.path.filename}}（File generator 才有）檔名—

3.2 exclude 過濾

YAML — Git Directory exclude
generators:
  - git:
      repoURL: https://github.com/myorg/apps.git
      revision: main
      directories:
        # 包含所有 apps/ 下的子目錄
        - path: apps/*
        # 但排除 apps/_template（範本）和 apps/.archive（已封存）
        - path: apps/_template
          exclude: true
        - path: apps/.archive
          exclude: true

      # 注意：exclude 路徑也支援 glob
      # - path: apps/*-deprecated
      #   exclude: true

3.3 pathParamPrefix（Matrix 中防衝突）

當 ApplicationSet 在 Matrix 中組合兩個 Git generator，兩者都產生 {{.path.basename}} 等 parameter，會衝突。用 pathParamPrefix 為其中一個加 prefix：

YAML — pathParamPrefix 範例
generators:
  - matrix:
      generators:
        # 第一個 git generator
        - git:
            repoURL: https://github.com/myorg/apps.git
            directories:
              - path: apps/*
            # 加 prefix：產生 {{.app.path.path}}、{{.app.path.basename}}
            pathParamPrefix: app

        # 第二個 git generator
        - git:
            repoURL: https://github.com/myorg/configs.git
            directories:
              - path: environments/*
            # 加另一個 prefix：產生 {{.env.path.path}}、{{.env.path.basename}}
            pathParamPrefix: env

template:
  metadata:
    name: '{{.app.path.basename}}-{{.env.path.basename}}'

4Git File Generator 實戰

Git File generator 不掃描目錄，而是讀取 YAML / JSON 檔案內容，將檔案內容作為 parameters。適合「每個 cluster / tenant 有自己的 config 檔」場景：

4.1 基本用法

YAML — Git File generator
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-cluster-config
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    - git:
        repoURL: https://github.com/myorg/cluster-configs.git
        revision: main
        files:
          # 讀取 clusters/ 下每個 config.json 檔案
          - path: "clusters/**/config.json"

  template:
    metadata:
      name: 'guestbook-{{.cluster.name}}'
    spec:
      project: '{{.cluster.project}}'
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps.git
        path: guestbook
      destination:
        server: '{{.cluster.address}}'
        namespace: '{{.cluster.namespace}}'
      syncPolicy:
        syncOptions:
          - 'CreateNamespace={{.cluster.createNamespace}}'

4.2 對應的 config 檔案結構（JSON 與 YAML 皆可）

JSON — clusters/engineering-prod/config.json
{
  "cluster": {
    "name": "engineering-prod",
    "address": "https://prod.example.com",
    "project": "engineering",
    "namespace": "guestbook",
    "createNamespace": "true"
  }
}
YAML — clusters/engineering-dev/config.yaml（v2.5+ 也支援）
cluster:
  name: engineering-dev
  address: https://kubernetes.default.svc
  project: engineering
  namespace: guestbook-dev
  createNamespace: "true"

檔案結構建議：每個 cluster / tenant 一個目錄，內含 config.json/yaml。檔案頂層為 dict（不要是 list），方便 template 用 {{.cluster.xxx}} 引用。

產生的特殊 parameters：

Parameter說明範例（檔案路徑 = clusters/engineering-prod/config.json）
{{.path.path}}檔案目錄clusters/engineering-prod
{{.path.basename}}目錄名engineering-prod
{{.path.filename}}檔案名config.json
{{.path.filenameNormalized}}檔名 normalizeconfig.json
檔案內容的所有頂層 key檔案內容直接展開為 parameters{{.cluster.name}}、{{.cluster.address}}

5Git Webhook 加速（必設！）

Git generator 預設每 3 分鐘 polling 一次 Git repo——對於頻繁更新的環境（每天數十次 commit）會造成感知延遲。強烈建議啟用 webhook，將延遲從 3 分鐘降至 ~10 秒：

YAML + Steps — Webhook 設定
## ── Step 1：在 argocd-secret 加入 webhook secret ─────────
apiVersion: v1
kind: Secret
metadata:
  name: argocd-secret
  namespace: argocd
stringData:
  webhook.github.secret: my-shared-secret

## ── Step 2：在 GitHub repo 設定 webhook ──────────────────
## Repo Settings → Webhooks → Add webhook
##   - Payload URL:    https://argocd.example.com/api/webhook
##   - Content type:   application/json
##   - Secret:         my-shared-secret（同上）
##   - Events:         Just the push event

## ── Step 3：減少 Git generator polling（webhook 啟用後可拉長）─
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  # Git generator 預設 3min；webhook 啟用後可拉長到 30min
  applicationsetcontroller.policy: sync
  # 對 ApplicationSet 個別調整 requeueAfterSeconds：

## 在 ApplicationSet spec 加入 generator 級別的 requeue：
spec:
  generators:
    - git:
        repoURL: ...
        requeueAfterSeconds: 1800     # 30 分鐘（webhook 是主要更新源）
💡

Webhook + 長 requeue = 最佳組合

Webhook 提供「即時」的更新（push 後 ~10 秒）；長 requeue 提供「保險」的定期重新檢查（防止 webhook 失敗）。生產環境推薦：webhook + requeueAfterSeconds 30 分鐘。

6三 generator 整合範例（真實場景）

結合本章三個 generator，以下是中型組織的真實使用案例：

需求：① 把 mono-repo 中 apps/ 下每個目錄當一個 App；② 部署到所有 production cluster；③ 每個 cluster 有自己的 helm values 檔案（在另一個 config repo）。

YAML — Git Directory + Cluster + Git File 整合
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: microservices-prod
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]

  generators:
    # Matrix 組合三個 generator
    - matrix:
        generators:
          # 第一個：Git Directory 掃描 mono-repo 中的 apps/
          - git:
              repoURL: https://github.com/myorg/microservices.git
              revision: main
              directories:
                - path: apps/*
              requeueAfterSeconds: 1800
              pathParamPrefix: app

          # 第二個：Cluster 取所有 production cluster
          - clusters:
              selector:
                matchLabels:
                  argocd.argoproj.io/secret-type: cluster
                  environment: production

  template:
    metadata:
      name: '{{.app.path.basename}}-{{.name}}'     # app 名 + cluster 名
      labels:
        app: '{{.app.path.basename}}'
        cluster: '{{.name}}'
        env: production
    spec:
      project: microservices

      # 多 source（v2.6+）：app manifests + cluster-specific values
      sources:
        # Source 1：Helm chart in mono-repo
        - repoURL: https://github.com/myorg/microservices.git
          targetRevision: main
          path: '{{.app.path.path}}'
          helm:
            valueFiles:
              # 從 ref source 引用 cluster-specific values
              - '$values/{{.app.path.basename}}/{{.name}}/values.yaml'

        # Source 2：Cluster-specific values（不渲染，僅作為 ref）
        - repoURL: https://github.com/myorg/cluster-configs.git
          targetRevision: main
          ref: values

      destination:
        server: '{{.server}}'
        namespace: '{{.app.path.basename}}'

      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
          - ApplyOutOfSyncOnly=true

  # Strategy：分批滾動（見 Ch.26）
  strategy:
    type: RollingSync
    rollingSync:
      steps:
        - matchExpressions:
            - key: cluster
              operator: In
              values: [prod-canary]      # 先部 canary
        - matchExpressions:
            - key: cluster
              operator: NotIn
              values: [prod-canary]      # 再部其他 prod

結果：假設 mono-repo 有 12 個 apps、3 個 production cluster，這個 ApplicationSet 會自動產生 12 × 3 = 36 個 Application，並先部署到 canary cluster 再滾動到其他 cluster。

7常見坑與最佳實踐

坑症狀解法
cluster generator 不匹配 in-cluster 所有 selector 結果都漏掉 in-cluster 為 in-cluster 建立 Secret + label，或用 List generator 補上
List generator value 寫成 number kubectl apply 報錯：cannot unmarshal number into string 所有 value 加引號："3"、"true"
Git Directory glob 太寬，意外納管 新增非 App 的目錄（如 docs/）後，被誤產生 Application 用 specific path（apps/*）；加 exclude rule；或在目錄內放 sentinel 檔案 + Git File generator
未啟用 Git webhook Git push 後 3 分鐘才感知變更 啟用 webhook + 拉長 requeueAfterSeconds 到 1800s
Matrix 中兩個 git generator 衝突 {{.path.basename}} 不知是哪個 generator 的 用 pathParamPrefix 為兩者加不同 prefix
Cluster generator 的 selector 拼寫錯誤 產生 0 個 Application（沒明顯錯誤訊息） kubectl get applicationset -o json 看 status；UI 看 generator 結果；先用空 selector 確認 cluster 可見
Git File 中 JSON 格式錯誤 ApplicationSet 卡住不產生 Application kubectl describe applicationset 看 status condition；JSON 改 YAML 較不易出錯

最佳實踐 Checklist

✅

Generator 設計十項原則

① 永遠用 goTemplate: true + missingkey=error；② cluster generator 必設 selector，至少 argocd.argoproj.io/secret-type: cluster；③ Git generator 必設 webhook；④ Git Directory glob 永遠用 specific path（不要用 */*）；⑤ Git File 結構頂層為 dict 不為 list；⑥ Cluster Secret 設計時就規劃好 label schema（environment、region、tier、team）；⑦ List generator 動態列表用 elementsYaml；⑧ Matrix 中兩個 git 用 pathParamPrefix；⑨ values 區塊用於 cluster 的衍生計算（label 條件式）；⑩ 大型部署用 strategy.RollingSync 分批滾動。

📌 Key Takeaways

  • 📋List generator 三大用途：① 固定小列表（3-10 個）；② 動態列表用 elementsYaml（v2.10+）從 Matrix 上游取得；③ 為現有 generator 結果補充元素（如為 cluster generator 補 in-cluster）。所有 value 必須是字串。
  • 🌐Cluster generator 是 multi-cluster 主力：產生 7 個 parameters（name / server / metadata.labels / metadata.annotations / nameNormalized / values / project）。selector 用 matchLabels + matchExpressions。cluster 增減 controller 自動響應。
  • ⚠️in-cluster 不被 selector 匹配：因為沒有 cluster Secret。解法：① 為 in-cluster 建立帶 label 的 Secret（推薦）；② 用 List generator 顯式補上；③ 改用 List + name=in-cluster（不用 selector）。設計時就要考慮這點。
  • 📂Git Directory 適合 mono-repo：產生 path.path / path.basename / path.basenameNormalized / path.segments。用 exclude: true 過濾 _template / archive 等特殊目錄。Matrix 中兩個 git 必用 pathParamPrefix 區分。
  • 📄Git File 適合 per-instance config：讀取 JSON / YAML 檔案內容作為 parameters。檔案結構頂層為 dict（如 {cluster: {...}}），方便用 {{.cluster.xxx}} 引用。常見模式：每個 cluster / tenant 一個目錄，內含 config.json/yaml。
  • 🌐Git webhook 必設：將 Git generator 偵測延遲從 3 分鐘降至 ~10 秒。設定後 requeueAfterSeconds 可拉長到 1800s（webhook + 長 polling = 即時 + 保險）。
  • 🏗️三 generator 整合常見模式：Matrix(Git Directory + Cluster) + 多 source 用 ref values。實現「mono-repo 中 N 個 App × M 個 cluster」的 N×M 自動部署 + per-cluster Helm values。配 RollingSync 分批安全部署。
