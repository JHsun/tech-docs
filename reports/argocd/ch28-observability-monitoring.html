可觀測性與監控基礎
Prometheus + Grafana + SLO

Argo CD 開箱即用支援 Prometheus metrics——但沒有監控的 Argo CD 像是飛機沒有儀表板。本章涵蓋 6 個 metrics endpoints、ServiceMonitor 設定、application labels 自訂 metrics、官方與社群 Grafana dashboards（14584 與 argo-cd-mixin）、關鍵 PromQL 查詢、SLI / SLO 設計（sync 成功率、reconcile latency）、Prometheus alerting rules。完成本章後你會有完整的 Argo CD 可觀測性 stack。

📋

前置：已完成 Vol 1-5，理解 Argo CD 架構（Ch.03）、HA 元件（Ch.13）、reconcile 機制（Ch.18）。理解 Prometheus 基本概念（scrape、ServiceMonitor、recording rules、alerting rules）。Grafana dashboard 操作經驗。

  • 啟用所有元件的 metrics（controller / server / repoServer / applicationSet / notifications / dex / redis）與設定 ServiceMonitor
  • 用 --metrics-application-labels 將 Application 的 label（team、env、tier）暴露為 Prometheus metric 標籤，實現 per-team alerting

  • 建立 8 條核心 Prometheus alerting rules（unhealthy app、sync failure spike、controller down、repo server slow 等）

1可觀測性三支柱在 Argo CD

可觀測性的標準三支柱（Metrics / Logs / Traces）在 Argo CD 環境中各有定位：

支柱Argo CD 中的對應用途本章涵蓋
Metrics Prometheus metrics（6 endpoints） 長期趨勢、SLO 計算、alerting、capacity planning ✅ 完整涵蓋
Logs kubectl logs / Loki / ELK 除錯特定錯誤、追溯 reconcile 細節 Ch.18 已涵蓋部分；本章補充
Traces OpenTelemetry（v2.10+ 實驗性） 追蹤 reconcile 各階段延遲、跨元件 request flow 簡略提及（仍實驗階段）
💡

Argo CD 觀測優先順序

① 先做 Metrics + Dashboards（90% 問題從這裡解決，最高 ROI）；② Logs centralization（Loki / Splunk，方便跨元件查 reconcile 細節）；③ Alerting（Prometheus + Alertmanager）；④ Traces 仍是 nice-to-have。先把前三個做好，比急著上 OpenTelemetry 更實用。

3啟用 Metrics 與 ServiceMonitor

3.1 Helm chart 啟用所有元件 metrics

YAML — argo-cd Helm values 完整 metrics 啟用
# values.yaml for argo-cd Helm chart
controller:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true           # 建立 ServiceMonitor CR（推薦）
      interval: 30s
      scrapeTimeout: 10s
      additionalLabels:
        release: prometheus     # 必須對應 Prometheus operator selector
      metricRelabelings:
        # 過濾掉高 cardinality（如 deleted applications）
        - action: drop
          sourceLabels: [__name__]
          regex: 'go_.*|process_.*'       # 視需求

server:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true
      additionalLabels: {release: prometheus}

repoServer:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true
      additionalLabels: {release: prometheus}

applicationSet:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true
      additionalLabels: {release: prometheus}

notifications:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true
      additionalLabels: {release: prometheus}

dex:
  metrics: {enabled: true}      # Dex SSO 元件

redis:
  metrics: {enabled: true}      # Redis cache 元件

commitServer:     # v2.13+ Source Hydrator
  metrics:
    enabled: true

      enabled: true

3.2 手動建立 ServiceMonitor（不用 Helm 時）

YAML — 手動 ServiceMonitor 範例
# 為 argocd-metrics service 建立 ServiceMonitor
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: argocd-metrics
  namespace: argocd
  labels:
    release: prometheus          # 必須對應 Prometheus operator
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: argocd-metrics
  endpoints:
    - port: metrics
      interval: 30s
      path: /metrics

# 同樣為 argocd-server-metrics / argocd-repo-server 等建立

3.3 application labels 自訂 metrics（強力功能！）

預設情況下，argocd_app_info metric 不包含 Application 的 label（如 team-name、tier）。啟用 --metrics-application-labels 可將特定 label 暴露為 Prometheus label，實現 per-team / per-tier 的 alerting 與 dashboard：

YAML — 啟用 --metrics-application-labels
# 透過 Helm values 的 extraArgs
controller:
  extraArgs:
    - --metrics-application-labels
    - team-name
    - --metrics-application-labels
    - business-unit
    - --metrics-application-labels
    - tier

# 或直接在 Deployment 中加 args
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: argocd-application-controller
spec:
  template:
    spec:
      containers:
        - name: argocd-application-controller
          command:
            - argocd-application-controller
            - --metrics-application-labels
            - team-name
            - --metrics-application-labels
            - tier

# 效果：argocd_app_info metric 新增 label_team_name 與 label_tier 標籤
# argocd_app_info{name="my-app", label_team_name="platform", label_tier="critical"} 1
⚠️

Cardinality 控制：metrics-cache-expiration

application 與 project 的建立 / 刪除歷史會累積在 metrics cache，cardinality 暴增可能讓 Prometheus 記憶體飆升。必設 --metrics-cache-expiration="24h0m0s" 定期清空已刪除 application 的 metrics history。生產環境推薦 24h；極大規模可用 6h。

4關鍵 Metrics 詳解

4.1 Application 層 metrics

Metric類型意義 / 用法
argocd_app_info Gauge 每個 Application 一個 sample，包含 sync_status、health_status、autosync_enabled 等 label。最常用 metric，dashboard / alerting 都靠它。
argocd_app_sync_total Counter 累計 sync 次數（含 phase=Succeeded/Failed/Error）。用於 sync 成功率 SLO。
argocd_app_reconcile Histogram 每次 reconcile 的耗時分布（bucket）。用於 p95 / p99 reconcile latency。
argocd_app_condition Gauge Application condition（如 SharedResourceWarning、OrphanedResourceWarning）。偵測警告。
argocd_app_orphaned_resources_count Gauge orphaned resources 數量（AppProject 設定 orphanedResources.warn）。
argocd_app_k8s_request_total Counter 對 K8s API 的 request 數，按 response_code 分。偵測 API call 異常。

4.2 Controller 效能 metrics

Metric意義警告閾值參考
argocd_cluster_api_resources_count 每個 cluster 的 K8s 資源類型數 —（看 cluster 規模）
argocd_cluster_api_resource_objects 每個 cluster 的物件總數 單 cluster > 100k 時考慮 sharding
argocd_cluster_cache_age_seconds cluster cache 上次更新後經過時間 持續 > 300s 表示 watch 斷線
argocd_kubectl_exec_pending 等待中的 kubectl exec 數 持續 > 5 表示 throttle 不足
process_resident_memory_bytes controller 記憶體用量 接近 limit 80% 需擴容
workqueue_depth 等待 reconcile 的 work queue 深度 持續 > 100 表示 controller 飽和

4.3 Repo Server metrics

Metric意義關注重點
argocd_git_request_total Git 操作次數（fetch / ls-remote / clone） 異常增加 = 可能是 webhook 故障導致 polling 增多
argocd_git_request_duration_seconds Git 操作耗時 histogram p95 > 30s 表示 Git server 慢
argocd_repo_pending_request_total 等待中的 repo request 持續高 = repo-server 不足，考慮擴容
argocd_redis_request_total{initiator="argocd-repo-server"} repo-server 對 Redis 的 request cache hit/miss 比例

6關鍵 PromQL 查詢

PromQL — 12 個必備查詢
## 1) Application 總數（按 project / health 分類）
count by (project, health_status) (argocd_app_info)

## 2) Unhealthy applications（不是 Healthy 也不是 Missing）
count(argocd_app_info{health_status!~"Healthy|Missing"})

## 3) Sync 成功率（過去 24 小時）
sum(rate(argocd_app_sync_total{phase="Succeeded"}[24h]))
  /
sum(rate(argocd_app_sync_total[24h]))

## 4) Sync failure 速率（每分鐘）
sum(rate(argocd_app_sync_total{phase="Failed"}[5m])) by (name, project)

## 5) Reconcile p99 latency（per cluster）
histogram_quantile(0.99,
  sum(rate(argocd_app_reconcile_bucket[5m])) by (dest_server, le)
)

## 6) Git 操作 p95 latency
histogram_quantile(0.95,
  sum(rate(argocd_git_request_duration_seconds_bucket[5m])) by (repo, request_type, le)
)

## 7) 待處理的 reconcile queue（workqueue depth）
sum(workqueue_depth{name="application-controller-app_reconciler"})

## 8) Controller 記憶體用量（含 limit 比例）
sum by (pod) (process_resident_memory_bytes{namespace="argocd"})
  /
sum by (pod) (kube_pod_container_resource_limits{resource="memory", namespace="argocd"})

## 9) OutOfSync apps（per team——需要 metrics-application-labels）
count by (label_team_name) (
  argocd_app_info{sync_status="OutOfSync"}
)

## 10) Apps with autosync disabled（潛在風險）
count(argocd_app_info{autosync_enabled="false"})

## 11) Cluster cache 過舊（> 5 分鐘沒更新表示 watch 斷線）
argocd_cluster_cache_age_seconds > 300

## 12) ApplicationSet reconcile 失敗率
sum(rate(argocd_appset_reconcile_count{status="error"}[5m]))
  /
sum(rate(argocd_appset_reconcile_count[5m]))

7SLI / SLO 設計

對於 Argo CD 這個「平台元件」，建議建立明確的 SLI / SLO，作為與 stakeholder 對話的依據：

建議 SLI 與目標 SLO

SLI定義SLO 目標PromQL
Sync 成功率 過去 28 天，sync attempts 中成功的比例 ≥ 99% sum(rate(...phase="Succeeded"[28d])) / sum(rate(...[28d]))
Reconcile p95 延遲 單次 reconcile 從觸發到完成的時間 p95 < 30s histogram_quantile(0.95, ...reconcile_bucket[5m])
API availability argocd-server API 5xx error rate error rate < 0.1% sum(rate(grpc_server_handled_total{grpc_code!~"OK|Canceled"}[5m])) / sum(rate(grpc_server_handled_total[5m]))
Application health 處於 Healthy 的 Application 比例 ≥ 95%（24 小時平均） count(argocd_app_info{health_status="Healthy"}) / count(argocd_app_info)
Git 操作 p95 延遲 git fetch / ls-remote 的耗時 p95 < 10s histogram_quantile(0.95, ...git_request_duration...)
YAML — SLO Recording Rules
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: argocd-slo-rules
  namespace: argocd
spec:
  groups:
    - name: argocd-slo
      interval: 1m
      rules:
        # SLI 1：Sync 成功率（28 天滾動）
        - record: argocd:slo:sync_success_rate_28d
          expr: |
            sum(rate(argocd_app_sync_total{phase="Succeeded"}[28d]))
              /
            sum(rate(argocd_app_sync_total[28d]))

        # SLI 2：Reconcile p95 latency
        - record: argocd:slo:reconcile_p95_seconds
          expr: |
            histogram_quantile(0.95,
              sum(rate(argocd_app_reconcile_bucket[5m])) by (le)
            )

        # SLI 3：Application Healthy 比例
        - record: argocd:slo:app_healthy_ratio
          expr: |
            count(argocd_app_info{health_status="Healthy"})
              /
            count(argocd_app_info)

        # SLO budget（剩餘 error budget）
        - record: argocd:slo:sync_error_budget_remaining
          expr: |
            (argocd:slo:sync_success_rate_28d - 0.99) / (1 - 0.99)
          # 0 表示用完，1 表示沒消耗
💡

SLO 不是越嚴格越好

① SLO 應該稍微低於實際表現（給 controller 升級、Git 故障等容錯空間）；② 用 error budget 觸發行動：剩餘 budget < 20% 暫停非緊急變更；③ 每季 review SLO：上一季都在 99.9% 但 SLO 是 99% 表示 SLO 太鬆；④ Per-tier 不同 SLO：platform 元件 99.9%、tenant Application 99%。

8核心 Prometheus Alerts

以下 8 條 alerting rules 涵蓋 Argo CD 運維 95% 場景：

YAML — 8 條核心 Alerting Rules
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: argocd-alerts
  namespace: argocd
spec:
  groups:
    - name: argocd
      rules:

        # Alert 1：Application 不健康（持續 15 分鐘）
        - alert: ArgoCDAppUnhealthy
          expr: |
            argocd_app_info{health_status!~"Healthy|Missing"} == 1
          for: 15m
          labels:
            severity: warning
          annotations:
            summary: "Application {{ $labels.name }} unhealthy"
            description: "App {{ $labels.name }} in project {{ $labels.project }} is {{ $labels.health_status }} for 15+ min"

        # Alert 2：Sync 失敗激增（5 分鐘內 > 5 次失敗）
        - alert: ArgoCDSyncFailureSpike
          expr: |
            sum(increase(argocd_app_sync_total{phase=~"Failed|Error"}[5m])) by (name) > 5
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Argo CD app {{ $labels.name }} repeatedly failing to sync"

        # Alert 3：Controller down
        - alert: ArgoCDControllerDown
          expr: |
            up{job="argocd-metrics"} == 0
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "argocd-application-controller is down"

        # Alert 4：Repo Server 慢（p95 > 30s）
        - alert: ArgoCDRepoServerSlow
          expr: |
            histogram_quantile(0.95,
              sum(rate(argocd_git_request_duration_seconds_bucket[5m])) by (le)
            ) > 30
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "argocd-repo-server p95 Git latency > 30s"

        # Alert 5：Reconcile queue 積壓
        - alert: ArgoCDReconcileQueueBacklog
          expr: |
            workqueue_depth{name=~".*reconciler.*", namespace="argocd"} > 100
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "Reconcile queue depth > 100, controller might be saturated"

        # Alert 6：Cluster cache 斷線
        - alert: ArgoCDClusterCacheStale
          expr: |
            argocd_cluster_cache_age_seconds > 300
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Cluster {{ $labels.server }} cache hasn't updated for 5+ min"
            description: "Watch connection lost; reconnect needed"

        # Alert 7：SLO error budget 即將用完
        - alert: ArgoCDSyncSLOBudgetLow
          expr: |
            argocd:slo:sync_error_budget_remaining < 0.20
          for: 30m
          labels:
            severity: warning
          annotations:
            summary: "Sync SLO error budget < 20% remaining"

        # Alert 8：太多 OutOfSync app（可能配置問題）
        - alert: ArgoCDManyOutOfSync
          expr: |
            count(argocd_app_info{sync_status="OutOfSync"}) > 20
          for: 30m
          labels:
            severity: warning
          annotations:
            summary: "More than 20 applications stuck OutOfSync"
⚠️

Alert fatigue 是真實問題

Argo CD 預設的 notification triggers（如 on-sync-failed）在網路抖動時可能每幾秒一次告警。這就是為什麼 Adin Hodovic 改用 Prometheus 的 for: 5m / 10m 機制——確保是持續性問題才告警。建議：① 都用 Prometheus alerts 取代 Argo CD notifications 的 alerting；② for 至少 5m；③ 用 inhibition rules 避免相關 alerts 同時觸發。

📌 Key Takeaways

  • 📊三支柱優先順序：Metrics（90% 問題從這裡解決）> Logs（除錯用）> Traces（仍實驗階段）。先把 Metrics + Grafana + Alerting 做好，比急著上 OpenTelemetry 更實用。
  • 🔌6 個 metrics endpoints：application-controller (8082)、server (8083)、repo-server (8084)、applicationset-controller (8085)、notifications (9001)、commit-server (8087)。application-controller 最重要，包含所有 Application、reconcile、cluster cache metrics。Helm chart 全部啟用 metrics.enabled + serviceMonitor.enabled。
  • 🏷️--metrics-application-labels 是 enterprise 必設：將 Application label（team / tier / business-unit）暴露為 Prometheus label，實現 per-team alerting。必設 --metrics-cache-expiration=24h 防止已刪除 app 的 cardinality 爆炸。
  • 📈最常用 metric：argocd_app_info（gauge）含 sync_status / health_status / autosync_enabled 等所有 dashboard / alert 必需 label。argocd_app_sync_total（counter）用於 sync 成功率 SLO。argocd_app_reconcile（histogram）用於 p95 latency。
  • 📉Dashboard 兩階段：① 起步用官方 dashboard 14584（5 分鐘上線）；② 進階用 argo-cd-mixin（Operational + Application + Notifications 三個 dashboard + 完整 alerts）。Mixin 用 jsonnet bundler 編譯，產 ConfigMap + PrometheusRule。
  • 🎯5 個建議 SLI：① Sync 成功率 ≥ 99%；② Reconcile p95 < 30s；③ API 5xx rate < 0.1%；④ App Healthy 比例 ≥ 95%；⑤ Git p95 < 10s。用 recording rules 預先計算（28 天滾動需要重計算量大）。用 error budget 觸發行動，剩餘 < 20% 暫停非緊急變更。
  • 🚨8 條核心 alerts：① UnhealthyApp（15m）；② SyncFailureSpike（5/5m）；③ ControllerDown；④ RepoServerSlow（p95 > 30s）；⑤ ReconcileQueueBacklog（> 100）；⑥ ClusterCacheStale（> 300s）；⑦ SLOBudgetLow（< 20%）；⑧ ManyOutOfSync（> 20）。
  • ⏳用 Prometheus alerts 取代 Argo CD notifications 的 alerting：Argo CD notifications 在網路抖動時容易 noisy（每幾秒一次）。Prometheus 的 for: 5m 機制確保持續性問題才告警，大幅減少 alert fatigue。Argo CD notifications 保留給 deployment success / new image deployed 等正面通知。
