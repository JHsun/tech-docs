ArgoCD Autopilot 與 App-of-Apps
自管 GitOps 結構與一鍵 DR

Vol 9 第三章。Argo CD 安裝完後，新手最常問的問題：「GitOps repo 該怎麼組織？Application 該放哪？跨環境怎麼分？Argo CD 自己怎麼 GitOps？」傳統做法是手動實作 app-of-apps 模式——root Application 指向 apps 目錄，目錄中每個 Application 又是另一個 Application 的目錄。argocd-autopilot（Codefresh 開發後捐給 Argo 社群）把這套模式自動化，提供 opinionated 目錄結構 + CLI workflow + 自管 Argo CD + 一鍵 DR recovery。本章涵蓋手動 app-of-apps、Autopilot 完整工作流、目錄結構解析、多 cluster 多 project 跨環境部署、DR 流程、與 ApplicationSet / app-of-apps / Autopilot 三方案對比。

📋

前置：已完成 Vol 1-8。理解 Argo CD Application / AppProject CRD（Ch.02、Ch.11）。理解 ApplicationSet（Ch.23-26）。理解 Kustomize overlay 結構。對 Disaster Recovery 概念有基本認識（Ch.19）。

🎯 學習目標

  • 理解 app-of-apps 模式：用一個 root Application 管理多個 child Application，達到「Argo CD 自管 + GitOps 全部設定」的效果
  • 掌握 app-of-apps 的限制：手動寫 YAML、無強加目錄結構、跨環境推進需自己設計、無 DR 流程
  • 理解 Autopilot 的定位：argocd-autopilot 是 argoproj-labs 的 opinionated CLI 工具（Codefresh 開發後捐給社群），自動化 app-of-apps 模式 + 強加目錄結構規範
  • 使用 4 種安裝方式：brew / scoop / choco / yay；理解 GIT_TOKEN 與 GIT_REPO 環境變數
  • 執行 argocd-autopilot repo bootstrap：① 安裝 Argo CD + ApplicationSet 到 cluster；② 在 Git repo 建立 bootstrap 目錄含三個關鍵 Application（autopilot-bootstrap / argo-cd / root）
  • 理解三個關鍵 Application：① autopilot-bootstrap（管 bootstrap 目錄本身）；② argo-cd（管 Argo CD 自身 + ApplicationSet）；③ root（管 projects 目錄）
  • 掌握目錄結構：/bootstrap（autopilot 自管，勿動）+ /projects（每 project 一個 yaml）+ /apps（每 app 一個 dir，含 base + overlays/<project>）
  • 使用 argocd-autopilot project create 與 app create 命令——CLI 自動產生 Kustomize 結構並 commit 到 Git
  • 實作多 cluster 跨環境部署：prod cluster 裝 Argo CD、staging cluster 用 --dest-kube-context 加入
  • 實作 Disaster Recovery：argocd-autopilot repo bootstrap --recover 在新 cluster 用既有 GitOps repo 一鍵還原所有應用
  • 對比三方案：① 手動 app-of-apps；② ApplicationSet；③ Autopilot——理解各自適用場景與並用方式
  • 避開常見陷阱：① 只支援 Raw YAML + Kustomize（Helm 在 roadmap）；② Beta 階段謹慎用於 production；③ 修改 /bootstrap 會被覆蓋；④ GIT_TOKEN 權限不足；⑤ Argo CD 版本與 Autopilot 不相容

1App-of-Apps 模式（手動版本）

1.1 手動實作 app-of-apps

app-of-apps 是 Argo CD 社群最早期就推廣的模式——用一個 Application 物件管理一堆 Application 物件。核心 idea：

Mermaid — App-of-Apps 架構
┌──────────────────────────┐
│ Git Repo                 │
│  /apps                   │
│    ├── app1.yaml         │  ← 各個 Application YAML
│    ├── app2.yaml         │
│    ├── app3.yaml         │
│    └── ...               │
└────────────┬─────────────┘
             │
             │ 一個 root Application 指向 /apps directory
             ▼
┌──────────────────────────┐
│ root Application         │
│ (kind: Application)      │
│ path: apps               │
│ recurse: true            │
└────────────┬─────────────┘
             │ Argo CD sync /apps
             │ apply 所有 Application YAML
             ▼
┌──────────────────────────────────────────┐
│ Argo CD 自動建立：                         │
│  - Application: app1                     │
│  - Application: app2                     │
│  - Application: app3                     │
│                                          │
│ 每個 child Application 又獨立 sync 自己的    │
│ source repo / path                       │
└──────────────────────────────────────────┘
YAML — 手動 root Application 範例
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/gitops.git
    path: apps             # 指向 apps 目錄
    targetRevision: HEAD
    directory:
      recurse: true          # 遞迴載入子目錄
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd     # Application 物件放在 argocd namespace
  syncPolicy:
    automated:
      prune: true            # 刪除 git 中移除的 Application
      selfHeal: true

## /apps 目錄下每個檔案是另一個 Application
## apps/guestbook.yaml:
## apiVersion: argoproj.io/v1alpha1
## kind: Application
## metadata: { name: guestbook }
## spec: { project: default, source: ..., destination: ... }

1.2 手動 app-of-apps 的問題

問題說明
無強加目錄結構 新手不知道該怎麼組織：apps/ vs projects/？dev/staging/prod 該怎麼分？
每個 app 寫一份 YAML 多 cluster / 多 env 時大量重複（後來才有 ApplicationSet 解決）
Argo CD 不自管 升級 Argo CD 自己要手動 kubectl apply，不在 GitOps 流程
跨環境推進無範本 image tag 怎麼推 dev → prod？沒明確規範
無 DR 流程 cluster 重建怎麼還原？需自己寫 script
Application 命名混亂 沒命名規範，team A、team B 命名衝突

2為什麼需要 Autopilot

2.1 Autopilot 解決的核心問題

💡

Autopilot = opinionated app-of-apps + Argo CD 自管 + CLI workflow

① 強加目錄結構：明確規範 /bootstrap、/projects、/apps 三層，新手不再迷茫；② Argo CD 自管：bootstrap 後 Argo CD 透過自己管自己（更新 Argo CD 變成 git push）；③ CLI 自動化：argocd-autopilot app create 自動產生 Kustomize 結構 + commit Git，不必手寫 YAML；④ DR 流程內建：--recover flag 一鍵還原 cluster 上所有應用；⑤ 多 cluster 友善：--dest-kube-context 指定不同 cluster。

2.2 與 app-of-apps 的關係

Autopilot 底層仍是 app-of-apps + ApplicationSet，但加上：

  • ① 三個 root Application（autopilot-bootstrap / argo-cd / root）形成多層 app-of-apps；
  • ② 每個 Project 自帶 ApplicationSet，git generator 監聽 /apps 子目錄自動建立 Application；
  • ③ Kustomize overlay 結構強加：apps/<app-name>/base + apps/<app-name>/overlays/<project>；
  • ④ CLI 隱藏複雜度：使用者不需手寫這些 YAML。
ℹ️

Autopilot 仍是 Beta 階段

2026 年初 Autopilot 仍在積極開發中，官方 README 明確標注「currently under active development」。限制：① 目前只支援 Raw YAML 與 Kustomize（Helm 在 roadmap）；② API 仍可能變更；③ 處理 Secret 功能尚未完善。建議：在 dev / staging 試用，production 使用前評估自己的 use case 是否觸及限制。

3.1 CLI 安裝

Bash — 4 種安裝方式
## macOS
$ brew install argocd-autopilot

## Windows (Scoop)
$ scoop update
$ scoop install argocd-autopilot

## Windows (Chocolatey)
$ choco install argocd-autopilot

## Arch Linux (AUR)
$ yay -S argocd-autopilot-bin

## Docker（CI 環境用）
$ docker run \
    -v ~/.kube:/home/autopilot/.kube \
    -v ~/.gitconfig:/home/autopilot/.gitconfig \
    -it quay.io/argoprojlabs/argocd-autopilot <cmd> <flags>

## 驗證安裝
$ argocd-autopilot version

3.2 repo bootstrap 命令

Bash — 一鍵 bootstrap Argo CD + GitOps repo
## Step 1：設環境變數（Git PAT 與 repo URL）
$ export GIT_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
$ export GIT_REPO=https://github.com/myorg/argocd-autopilot-gitops.git
# GIT_TOKEN 需要 repo 權限（讀寫）
# GIT_REPO 不存在會自動建立 private repo（如有 token 權限）

## Step 2：執行 bootstrap
$ argocd-autopilot repo bootstrap

# 輸出範例：
# INFO cloning git repository: https://github.com/myorg/argocd-autopilot-gitops.git
# INFO empty repository, initializing new one with main as default branch
# INFO using revision: "", installation path: "/"
# INFO pushing bootstrap manifests to repo
# INFO applying bootstrap manifests to cluster...
# INFO bootstrap completed successfully
# INFO argocd initialized. password: pfrDVRJZtHYZKzBv
# INFO run: kubectl port-forward -n argocd svc/argocd-server 8080:80

## Step 3：port-forward 到 Argo CD UI
$ kubectl port-forward -n argocd svc/argocd-server 8080:80
# 開 http://localhost:8080 用 admin / pfrDVRJZtHYZKzBv 登入

## 進階選項：
# 安裝到特定 path 而非 root：
$ argocd-autopilot repo bootstrap \
    --repo https://github.com/example/repo/path/to/installation_root

# 指定 cluster context：
$ argocd-autopilot repo bootstrap --kubecontext prod-cluster

# --recover 模式（DR）：
$ argocd-autopilot repo bootstrap --recover
# 使用既有 GitOps repo 在新 cluster 一鍵還原
⚠️

Bootstrap 只與 cluster 直接互動一次

Autopilot 只在 bootstrap 階段直接操作 cluster（kubectl apply Argo CD manifest）。之後所有命令（project create / app create / repo recover）只與 Git repo 互動——透過 Argo CD 同步到 cluster。意義：① CI/CD 中執行 Autopilot 不需 kubeconfig（只需 GIT_TOKEN）；② 多 cluster 場景下，從本機執行不需切 kubecontext；③ 整體更貼近 GitOps 純粹度。

4產生的目錄結構解析

Diagram — Bootstrap 後的目錄結構
argocd-autopilot-gitops/
├── bootstrap/                          ← autopilot 自管，請勿手動編輯
│   ├── argo-cd.yaml                   ← Application: argo-cd（管 Argo CD 自身）
│   ├── cluster-resources.yaml         ← Application: cluster-resources
│   ├── root.yaml                      ← Application: root（管 projects/）
│   └── argo-cd/                       ← Argo CD 的 Kustomize manifest
│       ├── kustomization.yaml
│       └── ...
├── projects/                           ← 每個 project 一個 file
│   └── DUMMY                          ← 初始 placeholder
└── apps/                               ← 每個 app 一個 directory
    └── (空，等 app create 命令填入)

# Bootstrap 後 Argo CD 中應該看到三個 Application：
# 1. autopilot-bootstrap  ← 管 bootstrap 目錄本身
# 2. argo-cd              ← 管 bootstrap/argo-cd folder
# 3. root                 ← 管 projects/ 目錄

4.1 /bootstrap 目錄（autopilot 自管）

三個關鍵 Application 物件：

Application路徑職責
autopilot-bootstrap /bootstrap watch /bootstrap 目錄本身，是 root-of-roots
argo-cd /bootstrap/argo-cd 管 Argo CD 自己的 deployment + ApplicationSet controller
root /projects watch /projects 目錄，自動建立各 project 的 ApplicationSet
cluster-resources /bootstrap/cluster-resources 管 cluster-wide 資源（如 RBAC、CRD）
⚠️

勿手動編輯 /bootstrap 目錄

這個目錄由 Autopilot 維護，手動編輯可能被後續命令覆蓋。需要修改 Argo CD 設定時：① 升級版本：等 Autopilot 新版（會自動更新 bootstrap manifests）；② 自訂 Argo CD ConfigMap（如 RBAC、SSO）：改用 cluster-resources 目錄管理；③ 緊急 hotfix 必須手動改：改完立刻提 PR 給 Autopilot，避免 drift。

4.2 /projects 目錄

Diagram — projects 目錄結構
projects/
├── DUMMY                              ← 初始 placeholder（無 project 時保留）
├── production.yaml                    ← project: production 的設定 + ApplicationSet
├── staging.yaml                       ← project: staging
└── dev.yaml                           ← project: dev

# 每個 yaml 包含兩個資源：
# 1. AppProject（Argo CD AppProject CRD）
# 2. ApplicationSet（監聽 /apps/*/overlays/<project>）

每個 project file 內容：

YAML — production.yaml 結構
## 1) AppProject 定義
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production
  namespace: argocd
spec:
  description: production
  destinations:
    - namespace: '*'
      server: '*'
  sourceRepos:
    - '*'

---
## 2) ApplicationSet（自動建立此 project 的所有 Application）
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: production
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: https://github.com/myorg/gitops.git
        # 監聽 apps/*/overlays/production/config.json
        files:
          - path: "apps/**/overlays/production/config.json"
        requeueAfterSeconds: 20
  template:
    metadata:
      name: '{{userGivenName}}-production'
      labels:
        app.kubernetes.io/managed-by: argocd-autopilot
    spec:
      project: production
      source:
        repoURL: https://github.com/myorg/gitops.git
        path: 'apps/{{userGivenName}}/overlays/production'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{destNamespace}}'
      syncPolicy:
        automated: {prune: true, selfHeal: true}

5Project 與 Application 命令

Bash — Project 與 Application 完整工作流
## 1) 建立 Project（自動 commit 到 /projects）
$ argocd-autopilot project create production
# INFO cloning git repository...
# INFO pushing new project manifest to repo
# INFO project created: 'production'

# Argo CD 同步後，UI 中會看到 production AppProject + ApplicationSet

## 2) 建立第二個 Project
$ argocd-autopilot project create staging

## 3) 從 public repo 建立 application
$ argocd-autopilot app create guestbook \
    --app github.com/argoproj-labs/argocd-autopilot/examples/demo-app/ \
    -p production
# INFO cloning git repository...
# INFO created kustomization at: apps/guestbook/base/kustomization.yaml
# INFO created config at: apps/guestbook/overlays/production/config.json
# INFO pushing application manifests to repo
# INFO application created: 'guestbook' in project 'production'

## --app 接受多種格式：
# 1) github.com/...     ← public repo
# 2) https://github.com/...   ← HTTPS URL
# 3) ./local/path      ← 本機 directory（autopilot 會把內容 commit）

## 4) 把同一 app 加到 staging project（跨 project 共用 base）
$ argocd-autopilot app create guestbook \
    --app github.com/argoproj-labs/argocd-autopilot/examples/demo-app/ \
    -p staging

## 5) 列出 Applications
$ argocd-autopilot app list -p production

## 6) 刪除 Application
$ argocd-autopilot app delete guestbook -p production
# 自動移除 apps/guestbook/overlays/production，
# 不影響 staging 的 overlay

## 7) 刪除整個 Project
$ argocd-autopilot project delete production
💡

app create 兩種儲存模式：kustomization vs flat

① Kustomization mode（預設）：在 apps/<name>/base/kustomization.yaml 用 resources 引用 public repo URL——保持與上游同步、適合「我只是要部署這個 chart」場景；② Flat mode（--type dir）：把 manifest 完整拷貝到 apps/<name>/base/——適合需要修改原始 manifest 的場景。多數情況用 Kustomization mode——保持 GitOps 純粹（image tag 等變更靠 overlay 即可）。

6多 Cluster 多 Project 部署

Autopilot 支援用單一 Argo CD 管理多 cluster——把 Argo CD 裝在 prod cluster，staging cluster 用 --dest-kube-context 加入：

Bash — 多 Cluster 完整工作流
## Step 1：切到 prod cluster bootstrap Argo CD
$ kubectl config use-context prod-cluster
$ export GIT_TOKEN=ghp_xxxx
$ export GIT_REPO=https://github.com/myorg/gitops.git
$ argocd-autopilot repo bootstrap

## Step 2：建立 prod 與 staging 兩個 project
$ argocd-autopilot project create prod
$ argocd-autopilot project create staging \
    --dest-kube-context staging-cluster

# staging project 預設指向 staging cluster
# （Argo CD 透過 cluster credentials 連到外部 cluster）

## Step 3：app create 預設用 project 的 default cluster
$ argocd-autopilot app create myapp \
    --app github.com/myorg/myapp \
    -p prod
# 部署到 prod-cluster（project 預設）

$ argocd-autopilot app create myapp \
    --app github.com/myorg/myapp \
    -p staging
# 部署到 staging-cluster

## Step 4：跨 project 不同 cluster 的特殊情境
# 例如 dev project 預設指 staging cluster，但這個 app 要部到 dev cluster：
$ argocd-autopilot app create special-app \
    --app github.com/myorg/special-app \
    -p dev \
    --dest-server https://dev-cluster.example.com
ℹ️

多 cluster 需先註冊 cluster credentials

在 Autopilot 之外，Argo CD 必須先有 staging cluster 的 credentials（如 Ch.16 介紹的 argocd cluster add）。Autopilot 不負責加 cluster；它假設你已經把目標 cluster 加進 Argo CD。實務流程：① bootstrap Argo CD；② argocd cluster add staging-cluster（Ch.16）；③ argocd-autopilot project create staging --dest-kube-context staging-cluster。

7Disaster Recovery 流程

Autopilot 的「殺手級功能」——一鍵 DR：

Bash — DR Recovery 完整流程
## 情境：原 cluster 完全爆炸，所有東西都沒了
##       但你的 GitOps repo 還在

## Step 1：provision 新 K8s cluster（如 EKS / GKE / AKS）
$ eksctl create cluster --name recovery-cluster --region us-east-1

## Step 2：switch context 到新 cluster
$ aws eks update-kubeconfig --name recovery-cluster
$ kubectl cluster-info

## Step 3：執行 recover 命令
$ export GIT_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx
$ export GIT_REPO=https://github.com/myorg/gitops.git
$ argocd-autopilot repo bootstrap --recover

# INFO cloning git repository from existing GitOps repo...
# INFO installing argo-cd to new cluster...
# INFO bootstrap completed successfully

## Step 4：等 Argo CD 開始 sync 既有 manifest
$ kubectl port-forward -n argocd svc/argocd-server 8080:80

# 在 UI 你會看到：
# 1. autopilot-bootstrap / argo-cd / root 三個 root Application 自動建立
# 2. ApplicationSet 從 /projects 自動發現所有 project
# 3. 每個 project 的 ApplicationSet 從 /apps 發現所有 Application
# 4. 每個 Application 自動 sync
# 全部完成後，cluster 上的所有應用都還原了

## Step 5：恢復時間估計
# 取決於應用數量與 image pull 速度：
# - 10 個 Application: ~5-10 分鐘
# - 100 個 Application: ~30-60 分鐘
# - 1000+ Application: 數小時（受 image registry 與 etcd 影響）
💡

DR 流程 vs Ch.19 Disaster Recovery 章節

Ch.19 介紹了 Argo CD 整體 DR 策略（etcd backup、Argo CD secrets backup、cluster certificate 等）。Autopilot 的 --recover 只負責還原「應用程式定義」（Application / AppProject）——不還原 Secrets / CRD 中的 data / image registry credentials 等。完整 DR 策略：Autopilot --recover + Velero（cluster-wide state）+ external secret store（Ch.35 ESO）+ cluster bootstrap script（Terraform / Crossplane）。

三方案的並用組合

① 新團隊 / 新專案：從 Autopilot 開始，省去結構設計時間（前提：只用 Raw YAML / Kustomize）；② 大規模 / 已有完整 GitOps repo：手動 app-of-apps 配 ApplicationSet（靈活度高，可用 Helm）；③ Helm-heavy 環境：避免 Autopilot，用 ApplicationSet 的 Helm support；④ 需要 multi-stage promotion：用 Kargo（Ch.40）取代 Autopilot 的環境推進邏輯。不是非此即彼——Autopilot 底層仍用 ApplicationSet，可以混搭。

📌 Key Takeaways

  • 🌳App-of-Apps 是 Argo CD 社群最早的「Argo CD 自管」模式：root Application 指向 /apps directory + recurse: true，自動 apply 所有 child Application。缺點：無強加目錄結構、無 Argo CD 自管、跨環境推進需自行設計、無 DR 流程。ApplicationSet（Vol 5）部分解決了多 cluster / 模板化問題，但仍是社群自由發揮。
  • 🛠️argocd-autopilot 是 argoproj-labs 的 opinionated CLI 工具（Codefresh 開發後捐給 Argo 社群）。5 大價值：① 強加目錄結構規範；② Argo CD 自管（GitOps 純粹）；③ CLI workflow 隱藏 YAML 複雜度；④ 多 cluster 友善；⑤ 內建一鍵 DR recovery（殺手級功能）。底層仍用 app-of-apps + ApplicationSet。
  • ⚙️核心命令三個：① argocd-autopilot repo bootstrap（安裝 Argo CD + 初始化 GitOps repo 結構）；② argocd-autopilot project create <name>（建 Project，自動產生 AppProject + ApplicationSet）；③ argocd-autopilot app create <name> --app <source> -p <project>（建 Application，自動產生 Kustomize 結構）。所有變更都自動 commit到 GitOps repo。
  • 📁三層強加目錄結構：① /bootstrap（autopilot 自管，含三個關鍵 Application：autopilot-bootstrap / argo-cd / root；勿手動編輯）；② /projects（每 project 一個 yaml，含 AppProject + ApplicationSet）；③ /apps（每 app 一個 dir，含 base/ + overlays/<project>）。
  • 🔑Bootstrap 只與 cluster 直接互動一次。之後所有命令（project create / app create / repo recover）只與 Git repo 互動，透過 Argo CD 同步到 cluster。意義：CI/CD 中執行 Autopilot 不需 kubeconfig；多 cluster 場景從本機執行不需切 context；整體更貼近 GitOps 純粹度。
  • 🌐多 Cluster 支援：用 --dest-kube-context 指定 project 的目標 cluster；或 app-level --dest-server 覆蓋。前提：cluster 必須先用 argocd cluster add（Ch.16）加入 Argo CD——Autopilot 不負責 cluster 註冊。
  • 🆘Disaster Recovery 是 Autopilot 的殺手級功能：argocd-autopilot repo bootstrap --recover 在新 cluster 用既有 GitOps repo 一鍵還原所有應用。原理：① 新 cluster 安裝 Argo CD；② Argo CD 從 GitOps repo 還原所有 Application 定義；③ 每個 Application sync 還原實際 workload。但只還原應用定義——Secrets / CRD data / image credentials 需配合 ESO + Velero + external state。
  • ⚖️三方案對比：① 手動 app-of-apps（靈活但無規範）；② ApplicationSet（多 cluster / 多 env 自動化但無 Argo CD 自管）；③ Autopilot（強加結構 + DR + CLI）。三者不互斥：Autopilot 底層用 app-of-apps + ApplicationSet，可混搭。
  • ⚠️主要限制：① 目前只支援 Raw YAML 與 Kustomize，Helm 在 roadmap——Helm-heavy 環境不適合；② Beta 階段，API 可能變更；③ 修改 /bootstrap 會被覆蓋；④ Secret 管理尚未完善（用 ESO 補強）；⑤ ApplicationSet 進階 generator（如 PR generator）需手動加。
  • ✅10 項 Checklist：固定 Autopilot 版本、private GitOps repo、最小權限 PAT、勿改 /bootstrap、Argo CD 自訂用 cluster-resources、Secret 用 ESO、每環境一 Project、Kustomization mode、multi-stage promotion 用 Kargo、每季測試 DR。定期測試 --recover 是 production-readiness 的關鍵——確保真的需要時 DR 流程確實能用。
