高可用部署：
HA 架構、Sharding、Redis HA

每個 Argo CD 元件的 HA 策略各不相同——server 是 stateless 可水平擴展，application-controller 需要 Sharding，repo-server 受限於本地 Git clone，Redis 需要 Sentinel 才能高可用，Dex 卻只能用 in-memory 資料。本章逐個拆解，給出每個元件的精確 HA 配方。

📋

前置：已閱讀 Ch.03（五大元件架構）、Ch.12（安裝架構）。理解 StatefulSet、Deployment、PodAntiAffinity 的基本概念。

🎯 學習目標

  • 掌握 Argo CD 五大元件各自的 HA 策略，建立完整的 HA 設計矩陣
  • 理解 argocd-server、repo-server、ApplicationSet 是 stateless 的 Deployment，可水平擴展
  • 精通 application-controller 的三種 Sharding 演算法（legacy / round-robin / consistent-hashing）
  • 了解 Dynamic Cluster Distribution 的工作原理（v3.x alpha）：以 Deployment + heartbeat ConfigMap 取代 StatefulSet
  • 掌握 argocd-redis HA：Sentinel + HAProxy 架構及其運作
  • 理解 argocd-dex-server 的 in-memory 限制及應對策略
  • 能撰寫完整生產等級的 HA Helm values，並執行 HA 故障演練

1HA 設計原則：五大元件不同對策

Argo CD 是「largely stateless」（基本無狀態）：所有持久資料都存在 Kubernetes etcd 中，Redis 只是揮發性快取。但這並不代表所有元件都能簡單地水平擴展——每個元件的擴展策略受其架構特性限制。

1.1 五大元件 HA 矩陣

argocd-server
水平擴展（stateless）
Deployment + 3+ replicas + HPA
完全 stateless，所有狀態在 K8s 與 Redis。建議 3+ replicas 起步，搭配 HPA 依 CPU 自動擴展。最不容易出問題的元件。
argocd-repo-server
水平擴展（受限於並發）
Deployment + 2-5 replicas + parallelism limit
每個 replica 維護自己的 Git clone。某些 manifest 工具（Kustomize、CMP）需要修改本地檔案，限制單實例並發。多 replica 是橫向擴展，配合 parallelism limit 避免 OOM。
application-controller
Sharding（每 shard 處理一組 cluster）
StatefulSet + replicas = shard 數量
不是傳統水平擴展！每個 replica 是一個 shard，負責固定的 cluster 子集。增加 replica 不會分擔同一 cluster 的負載，而是分擔不同 cluster。<30 cluster 不需要 sharding。
argocd-redis
Sentinel HA
StatefulSet 3 replicas + Sentinel + HAProxy
Redis 本身是單 master，需要 Sentinel 監控並在 master 故障時自動 failover。HAProxy 為用戶端提供穩定的入口（無需用戶端感知 master 變化）。
argocd-dex-server
不能水平擴展（in-memory DB）
Deployment 1 replica（保留以等待重啟）
使用 in-memory database 儲存 OIDC state。多 replica 會有資料不一致問題。維持單副本，依賴 Kubernetes 的 Pod 重啟機制提供恢復。或考慮直接用外部 OIDC provider 跳過 Dex。
applicationset-controller
Leader Election（單 active）
Deployment 2 replicas + leader election
v2.7+ 支援 leader election，多 replica 但只有一個 active。Leader 故障時其他 replica 自動接管。配合 ARGOCD_APPLICATIONSET_CONTROLLER_LEADER_ELECTION_LEASE_DURATION 調整 failover 延遲。
notifications-controller
Leader Election（單 active）
Deployment 1-2 replicas + leader election
與 applicationset-controller 類似，只有 leader 處理通知。多 replica 提供 failover 能力，不分擔負載。

1.2 PodAntiAffinity 與 PodDisruptionBudget（PDB）

HA 不只是多 replica——還需要確保 replica 不會在同一個 Node上（避免單 Node 故障同時影響所有副本），以及在 K8s 滾動升級時至少保留多少副本（PDB）。

YAML — PodAntiAffinity + PDB（Helm values 範例）
global:
  # 對所有 Argo CD pod 設定 PodAntiAffinity
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app.kubernetes.io/part-of: argocd
            topologyKey: kubernetes.io/hostname  # 不同 Node

server:
  replicas: 3
  # PDB：滾動升級時至少保留 2 個 replica
  pdb:
    enabled: true
    minAvailable: 2

repoServer:
  replicas: 3
  pdb:
    enabled: true
    minAvailable: 2
⚠️

HA 安裝至少需要 3 個不同的 Node

官方 ha/install.yaml 中的 PodAntiAffinity 是 requiredDuringScheduling（強制）規則。這意味著 Redis HA（3 replica）需要 3 個不同 Node 才能全部排程成功。單 Node 叢集無法使用 HA 模式。Helm chart 預設改為 preferred（盡力而為），但仍建議至少 3 個 Node 以發揮 HA 效益。

2argocd-server HA：水平擴展最簡單

argocd-server 是 Argo CD 中最容易擴展的元件，因為它是純 stateless：所有 session 透過 JWT token 自帶（無 server-side session），Application 狀態從 K8s API 讀取。

YAML — argocd-server HA + HPA
server:
  replicas: 3             # 起步 3 replica（生產最低）

  # HPA 自動擴展（根據 CPU 與 memory）
  autoscaling:
    enabled: true
    minReplicas: 3
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70
    targetMemoryUtilizationPercentage: 75

  resources:
    requests:
      cpu: "250m"
      memory: "256Mi"
    limits:
      cpu: "1000m"
      memory: "1Gi"

  pdb:
    enabled: true
    minAvailable: 2
ℹ️

argocd-server 何時需要更多 replica？

典型負載：100 個並發 UI 使用者 + CI 系統 API 呼叫。3 replica 通常足夠處理 500 個 Application 的環境。需要更多 replica 的訊號：UI 載入緩慢、API 請求延遲增加、CPU 持續超過 70%。可以透過 argocd_redis_request_total 與 grpc_server_handled_total metrics 觀察。

3argocd-repo-server HA：受限於本地 Git clone

repo-server 的擴展不像 server 那樣直接。它的限制在於：每個 replica 維護自己本地的 Git repo clone，部分 manifest 工具（Kustomize、某些 plugin）執行時會修改 clone 中的檔案，因此單一 replica 內部的並發是受限的。

3.1 parallelism 與並發控制

YAML — repo-server 並發調優
repoServer:
  replicas: 3          # 多 replica 分散負載

  env:
    # 限制單個 repo-server 同時處理的 manifest 生成數
    # 公式參考：(memory_limit_MB - 200) / per_request_memory_MB
    - name: PARALLELISM_LIMIT
      value: "10"

    # Mono-repo 跳過深度 git clone（顯著加快效能）
    - name: ARGOCD_GIT_ATTEMPTS_COUNT
      value: "3"

  resources:
    requests:
      cpu: "500m"
      memory: "512Mi"
    limits:
      cpu: "2000m"
      memory: "2Gi"      # OOM 是 repo-server 最常見的問題

  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 8
    targetMemoryUtilizationPercentage: 75

3.2 Mono-repo 效能調優

當組織使用 mono-repo（一個 Git repo 包含 50+ Application）時，repo-server 的負擔特別大。以下是必須的調優：

調優項目設定方式效果
Helm 並行生成v3.0+ 預設啟用同 repo 多 Helm App 並行 template，無需特殊設定
標記 chart 允許並發在 chart 目錄建立 .argocd-allow-concurrency 空檔案repo-server 信任此 chart 不會修改本地檔案，允許並發處理
使用 fully-qualified Git refsrefs/heads/main 取代 main大型 repo 的 ref 解析效能顯著提升
提高 repo-server timeoutcontroller.repo.server.timeout.seconds: "180"避免 manifest 生成超時導致 sync 失敗
啟用 sidecar plugin（CMP）使用 sidecar 而非舊式 plugin每個 App 用 repo 的暫時複本處理，原生支援並發

4application-controller Sharding

application-controller 是 Argo CD 中唯一不能簡單水平擴展的元件。它的擴展機制是 Sharding：每個 replica 負責一組固定的 cluster，總體上分擔 reconcile 的負擔。單 cluster（in-cluster only）的部署不需要 Sharding，1 replica 即可。

4.1 三種 Sharding 演算法比較

legacy（預設）
穩定
原理基於 cluster UID hash 分配 shard
優點簡單、長期使用、行為可預測
缺點分配不均，某些 shard 可能 cluster 集中
適用少量 cluster（<10）或不需均衡
round-robin
實驗
原理cluster 依序輪詢分配到 shard
優點完美均勻分布
缺點移除 rank-0 cluster 時觸發大規模 reshuffling
適用cluster 數量穩定的環境
consistent-hashing
實驗
原理一致性雜湊環，每個 shard 負責環上一段
優點新增/移除 cluster 只影響少量重新分配；分布合理
缺點分布不如 round-robin 完全均勻；alpha 階段
適用cluster 數量會變動的大型環境（推薦）
YAML — Sharding 啟用設定
## 方式一：argocd-cmd-params-cm（推薦）
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  controller.sharding.algorithm: consistent-hashing

## 方式二：StatefulSet env var（直接）
spec:
  replicas: 3           # 必須與 ARGOCD_CONTROLLER_REPLICAS 一致
  template:
    spec:
      containers:
        - name: argocd-application-controller
          env:
            - name: ARGOCD_CONTROLLER_REPLICAS
              value: "3"
            - name: ARGOCD_CONTROLLER_SHARDING_ALGORITHM
              value: consistent-hashing

## 設定後，套用變更（StatefulSet 必須 rollout restart）
# kubectl rollout restart -n argocd statefulset argocd-application-controller

## 驗證 sharding 結果
# argocd admin cluster stats
# 輸出：每個 cluster 屬於哪個 shard，以及該 shard 的負載

4.2 Dynamic Cluster Distribution（v3.x alpha）

傳統 Sharding 的痛點：增加 replica 數量需要修改 ARGOCD_CONTROLLER_REPLICAS env var，並重啟所有 controller pod，造成短暫的 sync 中斷。Dynamic Cluster Distribution 解決這個問題——將 application-controller 從 StatefulSet 改為 Deployment，使用 ConfigMap 心跳機制動態分配 shard。

Bash + YAML — 啟用 Dynamic Cluster Distribution
## Step 1：套用 Deployment overlay（取代 StatefulSet）
$ kubectl apply -k https://github.com/argoproj/argo-cd/manifests/ha/base/controller-deployment/?ref=v3.4.0

## Step 2：在 Deployment env 中啟用
env:
  - name: ARGOCD_ENABLE_DYNAMIC_CLUSTER_DISTRIBUTION
    value: "true"
  # Heartbeat 間隔（預設 10 秒）
  - name: ARGOCD_CONTROLLER_HEARTBEAT_TIME
    value: "10"
  # 必須使用 consistent-hashing
  - name: ARGOCD_CONTROLLER_SHARDING_ALGORITHM
    value: "consistent-hashing"

## Step 3：擴展 replica 不需要 restart
$ kubectl scale deployment argocd-application-controller --replicas=5 -n argocd
# Controller 自動偵測 replica 變化，重新分配 shard

## 工作原理：
# Controller 建立 argocd-app-controller-shard-cm ConfigMap
# 每個 controller pod 在 readiness probe 中更新自己的 heartbeat
# 若 3*HeartbeatDuration 沒更新 → readiness 變 unhealthy → 重新分配 shard
⚠️

v3.0.6 的 Dynamic Distribution 已知問題

截至 v3.0.6，當 controller replica 從 3 縮減到 2 時，可能出現「部分 cluster 沒有任何 controller 處理」的 race condition（GitHub issue #24147）。建議在 production 中目前先使用 StatefulSet + 手動指定 ARGOCD_CONTROLLER_REPLICAS，等 Dynamic Distribution 從 alpha 進入 stable 後再採用。

4.3 手動 shard 指派

當需要將特定 cluster 強制分配到指定 shard（例如：把高負載的 prod cluster 與低負載的 dev cluster 分開到不同 controller），可以在 cluster Secret 上加入 shard 欄位：

YAML — 手動 shard 指派
apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod-us-east
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
stringData:
  name: prod-us-east
  server: https://prod-us-east.example.com
  # 強制此 cluster 由 shard 0 處理
  shard: "0"
  config: |
    {
      "bearerToken": "xxxxx",
      "tlsClientConfig": {...}
    }

5argocd-redis HA：Sentinel + HAProxy

Redis 本身是單 master 架構，要實現 HA 必須：① Sentinel 監控 master，並在故障時自動將 replica 提升為新 master；② HAProxy 為用戶端提供穩定入口（用戶端不需要感知 master 變化）。

5.1 Sentinel 架構

📊 argocd-redis HA 架構（3 Redis + 3 Sentinel + 3 HAProxy）
Redis Master
redis-ha-server-0
⇄
Redis Replica
redis-ha-server-1
⇄
Redis Replica
redis-ha-server-2
↑ 同 pod 內含 Sentinel sidecar，互相監控 ↑
HAProxy
haproxy-0
HAProxy
haproxy-1
HAProxy
haproxy-2
↑ 用戶端（controller / server / repo-server）連接 HAProxy，由 HAProxy 路由到當前 master ↑

5.2 HAProxy 用戶端負載平衡

所有 Argo CD 元件都不直接連接 Redis，而是透過 argocd-redis-ha-haproxy Service。HAProxy 透過查詢 Sentinel 取得當前 master，動態路由所有寫入到 master，所有讀取到 replica（或 master）。

YAML — Helm values 啟用 Redis HA
redis-ha:
  enabled: true            # 啟用 Redis HA（3 replica + Sentinel + HAProxy）
  redis:
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
  haproxy:
    enabled: true
    replicas: 3
    resources:
      requests:
        cpu: "100m"
        memory: "64Mi"

# 同時停用單副本 Redis（避免衝突）
redis:
  enabled: false           # 重要！

# 控制元件透過 sentinel 連線（部分元件需要設定）
controller:
  env:
    - name: ARGOCD_APPLICATION_CONTROLLER_REDIS_USE_TLS
      value: "false"
ℹ️

argocd-redis 預設只支援 3 個 sentinel

官方文件明確說明：argocd-redis is pre-configured with the understanding of only three total redis servers/sentinels。修改 redis-ha replica 數量需要對應修改 Argo CD 元件的 sentinel 連線設定，建議維持 3 replica 即可——這已足夠提供 quorum-based failover 能力。

6argocd-dex-server / applicationset-controller HA

argocd-dex-server：無法水平擴展

Dex 使用 in-memory database 儲存 OIDC state（OAuth2 callback URL、authorization code、refresh token 等）。多 replica 之間沒有同步機制，會造成「使用者在 replica 1 開始 OAuth 流程，回調卻被路由到 replica 2 而失敗」的問題。

應對策略：

策略說明
維持單副本Dex 重啟很快（< 5 秒），對使用者影響小。設定足夠的 readiness probe + restart policy
跳過 Dex（推薦）若組織有 OIDC-compliant IdP（Okta / Auth0 / Azure AD），直接在 argocd-cm 設定外部 OIDC，繞過 Dex
使用 OAuth2 Proxy用 oauth2-proxy 取代 Dex 處理 SSO，再以 header 或 token 認證至 Argo CD

applicationset-controller：Leader Election HA

v2.7+ 起，applicationset-controller 支援 Kubernetes 的 leader election。多 replica 透過 Lease 物件選出 leader，只有 leader 處理 ApplicationSet 的 reconciliation。其他 replica 是 standby，leader 故障時自動接管。

YAML — applicationset-controller HA（leader election）
applicationSet:
  replicas: 2          # 2 replica：1 leader + 1 standby
  env:
    # Leader election 設定（預設值通常足夠）
    - name: ARGOCD_APPLICATIONSET_CONTROLLER_LEADER_ELECTION_LEASE_DURATION
      value: "15s"     # Lease 持續時間
    - name: ARGOCD_APPLICATIONSET_CONTROLLER_LEADER_ELECTION_RETRY_PERIOD
      value: "5s"      # 重試間隔
    - name: ARGOCD_APPLICATIONSET_CONTROLLER_LEADER_ELECTION_RENEW_DEADLINE
      value: "10s"     # 續租截止
  # Failover 時間 ≈ Lease - Renew = 15s - 10s = 5s 上下

7完整 HA 配置 Helm values

整合本章所有設定，以下是生產等級 HA 部署的完整 Helm values：

YAML — argocd-ha-values.yaml（生產完整版）
global:
  image:
    tag: "v3.4.0"
  domain: argocd.example.com
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app.kubernetes.io/part-of: argocd
            topologyKey: kubernetes.io/hostname

configs:
  params:
    controller.sharding.algorithm: consistent-hashing
    controller.repo.server.timeout.seconds: "180"
    reposerver.parallelism.limit: "10"

server:
  replicas: 3
  autoscaling:
    enabled: true
    minReplicas: 3
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70
  resources:
    requests: {cpu: "250m", memory: "256Mi"}
    limits: {cpu: "1000m", memory: "1Gi"}
  pdb:
    enabled: true
    minAvailable: 2

controller:
  # StatefulSet sharding（穩定方式）
  replicas: 2
  env:
    - name: ARGOCD_CONTROLLER_REPLICAS
      value: "2"
  resources:
    requests: {cpu: "500m", memory: "1Gi"}
    limits: {cpu: "2000m", memory: "4Gi"}

repoServer:
  replicas: 3
  autoscaling:
    enabled: true
    minReplicas: 3
    maxReplicas: 8
    targetMemoryUtilizationPercentage: 75
  resources:
    requests: {cpu: "500m", memory: "512Mi"}
    limits: {cpu: "2000m", memory: "2Gi"}
  pdb:
    enabled: true
    minAvailable: 2

applicationSet:
  replicas: 2
  resources:
    requests: {cpu: "100m", memory: "128Mi"}
    limits: {cpu: "500m", memory: "512Mi"}

notifications:
  replicas: 2

dex:
  replicas: 1           # Dex 維持單副本
  # 或 enabled: false 完全停用 Dex（使用外部 OIDC）

redis-ha:
  enabled: true          # 啟用 Redis HA
redis:
  enabled: false         # 停用單副本 Redis（必須）

8HA 故障演練（Game Day）

HA 配置必須定期演練驗證。以下是針對每個元件的故障演練腳本：

Bash — HA 故障演練腳本
## ── Test 1：argocd-server failover ─────────────────────
## 預期：刪除 1 個 server replica，UI 仍可存取

$ POD=$(kubectl get pods -n argocd -l app.kubernetes.io/name=argocd-server -o name | head -1)
$ kubectl delete -n argocd $POD --wait=false
$ curl -k https://argocd.example.com/api/version
# 應立即得到回應（其他 replica 接手）

## ── Test 2：Redis master failover ──────────────────────
## 預期：殺死 Redis master，Sentinel 自動將 replica 提升為新 master

$ MASTER_POD=$(kubectl exec -n argocd argocd-redis-ha-server-0 -c redis -- \
    redis-cli -p 6379 info replication | grep "role:master")

$ kubectl delete pod -n argocd argocd-redis-ha-server-0
# 等 30 秒讓 Sentinel 完成選舉
$ sleep 30

# 驗證 Argo CD 仍可運作
$ argocd app list
# 應正常顯示 App 清單

## ── Test 3：application-controller shard failover ───────
## 預期：殺死 controller 0，其他 shard 暫時接管 cluster
$ kubectl delete pod -n argocd argocd-application-controller-0

# 觀察 sync 狀態（應持續運作，可能短暫延遲）
$ argocd app get my-app -w

## ── Test 4：repo-server pod 故障 ────────────────────────
$ kubectl delete pods -n argocd -l app.kubernetes.io/name=argocd-repo-server
# 由於有多個 replica，整體 manifest 生成不中斷

## ── Test 5：完整 Node 故障模擬 ───────────────────────────
## 將整個 Node cordon + drain，模擬 Node 故障
$ NODE=$(kubectl get pods -n argocd -l app.kubernetes.io/name=argocd-server \
    -o jsonpath='{.items[0].spec.nodeName}')
$ kubectl cordon $NODE
$ kubectl drain $NODE --ignore-daemonsets --delete-emptydir-data
# 由於 PodAntiAffinity，其他 Node 應已有副本，UI 持續可用

## ── 演練後驗證 ────────────────────────────────────────
$ argocd app list                       # 列出所有 App，應正常
$ kubectl get pods -n argocd            # 觀察 Pod 是否回到 Running
$ argocd app sync test-app               # 嘗試手動 sync 一個 App

📌 Key Takeaways

  • 📊HA 不是「全部多副本」：不同元件有不同擴展機制——server / repo-server / ApplicationSet 是水平擴展；application-controller 是 Sharding；Redis 是 Sentinel HA；Dex 不能水平擴展（in-memory DB）。
  • 🌐argocd-server 最簡單：純 stateless，3+ replicas + HPA 即可。100 個並發使用者用 3 replica 通常足夠。觀察 CPU 與 grpc metrics 決定是否擴展。
  • ⚙️Sharding 不是同 cluster 分擔負載：Sharding 是讓不同 shard 處理不同 cluster。<30 cluster 不需要 sharding（1 controller 即可）。consistent-hashing 是新增/移除 cluster 時最穩定的演算法（推薦）。
  • 🔴Redis HA = Sentinel + HAProxy：3 個 Redis（1 master + 2 replica）+ 同 pod 內的 Sentinel 互相監控 + HAProxy 為用戶端提供穩定入口。argocd-redis 預設只支援 3 個 sentinel，不要修改。
  • 🔑Dex 不能水平擴展，建議跳過：使用 in-memory DB，多 replica 會有 OAuth state 不一致。生產環境推薦：直接設定外部 OIDC provider（Okta / Auth0 / Azure AD），完全繞過 Dex。
  • 🧪HA 配置必須定期演練：每季執行一次 Game Day——刪除 server pod、殺死 Redis master、drain Node、模擬 controller failover。沒有演練過的 HA 不能算 HA。
