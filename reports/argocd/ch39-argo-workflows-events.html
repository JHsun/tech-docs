Argo Workflows 與 Events
事件驅動的 CI/CD pipeline

Vol 9 第一章。Argo 不只是 CD——整個 Argo 家族包含 Argo CD（CD）、Argo Rollouts（progressive delivery）、Argo Workflows（DAG-based job orchestration）、Argo Events（event-driven automation）。本章介紹 Workflows 與 Events 兩個專案、與 Argo CD 的關係（互補不重疊）、典型整合場景（GitHub push → CI pipeline → Argo CD sync）、四大 Argo 元件協作的完整 stack。完成本章後你會掌握用 Argo 家族打造 end-to-end DevOps platform 的能力。

📋

前置：已完成 Vol 1-8。理解 K8s Job / CronJob 概念。理解 webhook 機制（GitHub / Bitbucket）。理解 message bus 概念（NATS / Kafka）。對 DAG（Directed Acyclic Graph）有基本認識。

🎯 學習目標

  • 理解 Argo 全家桶四大專案的職責分工：Argo CD（CD / GitOps）、Argo Workflows（job orchestration）、Argo Events（event automation）、Argo Rollouts（progressive delivery）
  • 掌握 Argo Workflows 核心 CRD：Workflow（一次性執行）、WorkflowTemplate（可重用範本）、CronWorkflow（排程）、ClusterWorkflowTemplate（跨 namespace）
  • 區分 DAG 與 Steps 兩種寫法：DAG 用於並行任務 + 依賴控制；Steps 用於明確線性流程
  • 使用 artifacts 與 outputs 在 step 間傳遞檔案 / 變數（含 S3 / GCS / OSS / artifact repository 設定）
  • 掌握 Argo Events 四大元件：EventSource（事件來源 20+）、EventBus（傳輸層，NATS-based）、Sensor（dependency + trigger 邏輯）、Trigger（執行動作 10+）
  • 實作典型整合：GitHub webhook → EventSource → Sensor → Argo Workflows pipeline → Argo CD sync
  • 理解 Argo CD 與 Workflows 的協同：① Workflows 跑 CI（build/test/push image）→ Argo CD 跑 CD（apply manifest）；② Argo CD 管 Workflows manifest（GitOps）；③ Sensor 觸發 Argo CD sync 取代輪詢
  • 實作 5 種典型 EventSource：GitHub webhook、Cron schedule、SQS / Kafka、S3 drop、generic webhook
  • 掌握 Workflows trigger 進階：parameterization（dataKey 傳事件內容到 Workflow input）、conditions（多個 dependency 都滿足才觸發）、policies（依結果決定後續）
  • 避開常見陷阱：① Workflows 在錯誤 namespace 看不到；② Sensor SA 權限不足；③ EventBus NATS 單副本造成 SPOF；④ webhook 沒過濾任何 push 都觸發；⑤ EventSource 暴露在 public（必須有認證）

apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: hello-world-
  namespace: argo

  entrypoint: whalesay            # 從哪個 template 開始
  serviceAccountName: argo-workflow

2.2 DAG vs Steps

YAML — DAG 範例（並行 + 依賴）
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: ci-pipeline-
spec:
  entrypoint: main
  templates:
    # 主 DAG
    - name: main
      dag:
        tasks:
          - name: checkout
            template: git-clone

          # 三個 task 並行（都依賴 checkout）
          - name: unit-test
            template: test
            dependencies: [checkout]
            arguments:
              parameters:
                - name: type
                  value: unit

          - name: lint
            template: test
            dependencies: [checkout]
            arguments:
              parameters:
                - name: type
                  value: lint

          - name: security-scan
            template: test
            dependencies: [checkout]
            arguments:
              parameters:
                - name: type
                  value: trivy

          # build 等三個 test 都成功
          - name: build-image
            template: kaniko-build
            dependencies: [unit-test, lint, security-scan]

          # 部署：等 build 完成
          - name: deploy
            template: argocd-sync
            dependencies: [build-image]
            # When 條件：只有 main branch 才部署
            when: "{{workflow.parameters.branch}} == 'main'"

    # 子 templates
    - name: git-clone
      container:
        image: alpine/git
        command: [git, clone, "{{workflow.parameters.repo}}", /src]

    - name: test
      inputs:
        parameters:
          - name: type
      container:
        image: my-test-runner:v1
        command: [sh, -c]
        args: ["run-tests --type={{inputs.parameters.type}}"]

2.3 Artifacts 與 Outputs（step 間傳資料）

YAML — Artifact 與 Output 範例
spec:
  templates:
    # 1) Build：產生 image tag artifact
    - name: build
      container:
        image: gcr.io/kaniko-project/executor
        command: [/kaniko/executor]
        args: ["--destination=myorg/myapp:{{workflow.uid}}"]
      # Output：把 image tag 寫到 file，下游 step 可讀
      outputs:
        parameters:
          - name: image-tag
            valueFrom:
              path: /tmp/image-tag.txt
        # 或：artifact（檔案 / 目錄）to S3 / GCS
        artifacts:
          - name: test-results
            path: /results
            s3:                                # 自動上傳到 S3
              bucket: my-artifacts
              key: "results/{{workflow.name}}.tar.gz"

    # 2) Deploy：讀 build step 的 output
    - name: deploy
      inputs:
        parameters:
          - name: image-tag
      container:
        image: argoproj/argocd:v2.14
        command: [argocd, app, set, my-app]
        args: ["--helm-set", "image.tag={{inputs.parameters.image-tag}}"]

3.3 Sensor 與 Trigger

YAML — 簡單 webhook → Workflow 範例
## 1) EventSource：webhook listener
apiVersion: argoproj.io/v1alpha1
kind: EventSource
metadata:
  name: webhook
  namespace: argo-events
spec:
  service:
    ports:
      - port: 12000
        targetPort: 12000
  webhook:
    example:
      port: "12000"
      endpoint: /trigger
      method: POST

---
## 2) Sensor：訂閱事件 + 觸發 Workflow
apiVersion: argoproj.io/v1alpha1
kind: Sensor
metadata:
  name: webhook
  namespace: argo-events
spec:
  template:
    serviceAccountName: operate-workflow-sa

  # Dependency：訂閱哪個事件
  dependencies:
    - name: webhook-dep
      eventSourceName: webhook
      eventName: example
      # 可選：filter 過濾事件內容
      filters:
        data:
          - path: body.action
            type: string
            value:
              - deploy

  # Triggers：觸發什麼動作
  triggers:
    - template:
        name: trigger-workflow
        argoWorkflow:
          operation: submit
          source:
            resource:
              apiVersion: argoproj.io/v1alpha1
              kind: Workflow
              metadata:
                generateName: webhook-triggered-
              spec:
                entrypoint: main
                arguments:
                  parameters:
                    - name: message
                      value: default     # 預設值（會被 parameters 覆蓋）
                templates:
                  - name: main
                    inputs:
                      parameters:
                        - name: message
                    container:
                      image: docker/whalesay
                      command: [cowsay]
                      args: ["{{inputs.parameters.message}}"]

          # 把 event body 內容傳給 Workflow input
          parameters:
            - src:
                dependencyName: webhook-dep
                dataKey: body.message
              dest: spec.arguments.parameters.0.value

4Events + Workflows 完整 CI Pipeline

4.1 GitHub webhook 觸發完整 CI

YAML — GitHub EventSource
apiVersion: argoproj.io/v1alpha1
kind: EventSource
metadata:
  name: github-webhook
  namespace: argo-events
spec:
  service:
    ports:
      - port: 12000
        targetPort: 12000

  github:
    myapp-repo:
      owner: myorg
      repository: myapp
      events:
        - "*"      # 監聽所有 event（或具體：push、pull_request）
      webhook:
        endpoint: /push
        port: "12000"
        method: POST
        url: "https://argo-events.example.com"      # 外部可達 URL
      # GitHub PAT 用於自動建立 webhook（可選）
      apiToken:
        name: github-access
        key: token
      # Webhook secret 驗證簽章
      webhookSecret:
        name: github-access
        key: secret
      insecure: false
YAML — Sensor 觸發完整 CI Workflow
apiVersion: argoproj.io/v1alpha1
kind: Sensor
metadata:
  name: github-ci
  namespace: argo-events
spec:
  template:
    serviceAccountName: operate-workflow-sa

  dependencies:
    - name: github-push
      eventSourceName: github-webhook
      eventName: myapp-repo
      # Filter：只接 main branch 的 push
      filters:
        data:
          - path: body.ref
            type: string
            value:
              - "refs/heads/main"
          - path: headers.X-Github-Event
            type: string
            value:
              - push

  triggers:
    - template:
        name: ci-pipeline
        argoWorkflow:
          operation: submit
          source:
            resource:
              apiVersion: argoproj.io/v1alpha1
              kind: Workflow
              metadata:
                generateName: ci-
                namespace: argo
              spec:
                entrypoint: main
                arguments:
                  parameters:
                    - name: repo
                      value: ""
                    - name: commit
                      value: ""
                workflowTemplateRef:
                  name: ci-template   # 引用獨立的 WorkflowTemplate

          # 從 GitHub event 傳資料到 Workflow parameters
          parameters:
            - src:
                dependencyName: github-push
                dataKey: body.repository.clone_url
              dest: spec.arguments.parameters.0.value
            - src:
                dependencyName: github-push
                dataKey: body.after
              dest: spec.arguments.parameters.1.value

4.2 完整 DAG Pipeline（WorkflowTemplate）

YAML — 可重用的 CI WorkflowTemplate
apiVersion: argoproj.io/v1alpha1
kind: WorkflowTemplate
metadata:
  name: ci-template
  namespace: argo
spec:
  entrypoint: main
  arguments:
    parameters:
      - name: repo
      - name: commit

  templates:
    - name: main
      dag:
        tasks:
          - name: clone
            template: git-clone
          - name: test
            template: run-tests
            dependencies: [clone]
          - name: build
            template: kaniko-build
            dependencies: [test]
          - name: update-gitops
            template: commit-image-tag
            dependencies: [build]

    - name: git-clone
      container:
        image: alpine/git
        command: [sh, -c]
        args:
          - |
            git clone {{workflow.parameters.repo}} /src
            cd /src
            git checkout {{workflow.parameters.commit}}

    - name: run-tests
      container:
        image: node:20
        command: [sh, -c, "npm ci && npm test"]

    - name: kaniko-build
      container:
        image: gcr.io/kaniko-project/executor:latest
        args:
          - "--destination=myregistry.io/myapp:{{workflow.parameters.commit}}"

    - name: commit-image-tag
      container:
        image: alpine/git
        command: [sh, -c]
        args:
          - |
            git clone https://github.com/myorg/gitops.git /gitops
            cd /gitops/apps/myapp/overlays/dev
            kustomize edit set image myorg/myapp:{{workflow.parameters.commit}}
            git commit -am "Deploy {{workflow.parameters.commit}} to dev"
            git push

5與 Argo CD 整合

5.1 用 Argo CD 管 Workflows（GitOps）

把 WorkflowTemplate / CronWorkflow / EventSource / Sensor 全部 commit 到 Git，由 Argo CD 統一部署：

YAML — Argo CD Application 管 Workflows + Events
## 1) Argo CD 管 Workflows templates
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: workflows-templates
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://github.com/myorg/argo-templates.git
    path: workflows/templates
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: argo
  syncPolicy:
    automated: {prune: true, selfHeal: true}

---
## 2) Argo CD 管 Events EventSources + Sensors
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: argo-events-config
  namespace: argocd
spec:
  project: platform
  source:
    repoURL: https://github.com/myorg/argo-templates.git
    path: events
    targetRevision: main
  destination:
    server: https://kubernetes.default.svc
    namespace: argo-events
  syncPolicy:
    automated: {prune: true, selfHeal: true}

5.2 Sensor 觸發 Argo CD sync（取代 polling）

Argo CD 預設用 polling（3 分鐘檢查 Git 一次）。透過 Argo Events 可以做到 event-driven sync——push 後立即觸發：

YAML — Sensor 觸發 ArgoCD sync
apiVersion: argoproj.io/v1alpha1
kind: Sensor
metadata:
  name: argocd-sync-trigger
  namespace: argo-events
spec:
  template:
    serviceAccountName: argo-events-sa

  dependencies:
    - name: github-push
      eventSourceName: github-webhook
      eventName: gitops-repo
      filters:
        data:
          - path: body.ref
            type: string
            value: ["refs/heads/main"]

  triggers:
    - template:
        name: argocd-sync
        # Trigger 1：Workflow 跑 argocd CLI
        argoWorkflow:
          operation: submit
          source:
            resource:
              apiVersion: argoproj.io/v1alpha1
              kind: Workflow
              metadata:
                generateName: argocd-sync-
              spec:
                entrypoint: sync
                templates:
                  - name: sync
                    container:
                      image: argoproj/argocd:v2.14
                      command: [sh, -c]
                      args:
                        - |
                          argocd login argocd-server.argocd.svc:443 \
                            --auth-token $ARGOCD_TOKEN --grpc-web --insecure
                          argocd app get my-app --refresh
                          argocd app wait my-app --sync --health --timeout 300

---
## 另一種：Argo CD 內建的 Git webhook（更輕量）
## 在 GitHub Settings → Webhooks：
##   Payload URL: https://argocd.example.com/api/webhook
## 不需要 Argo Events 也能 event-driven
## Argo Events 適合的是「複雜 dependency / 多 source 整合」
💡

Argo Events vs Argo CD webhook 何時用哪個

① 單純 Git push 觸發 sync：用 Argo CD 內建 webhook（/api/webhook），設定簡單；② 複雜流程：CI build + image push + sync + smoke test + notify：用 Argo Events + Workflows + Argo CD；③ 多 source 整合（Git + Docker registry + Slack）：必用 Argo Events；④ 純 CronJob 取代：用 Argo Workflows CronWorkflow（比 K8s CronJob 強大很多）。

6典型使用情境組合

情境使用元件流程
純 Git → Deploy（簡單） Argo CD 內建 webhook Git push → Argo CD webhook → auto-sync
CI + CD 完整流程 Events + Workflows + CD Git push → EventSource → Sensor → Workflow（build/test/push）→ commit gitops repo → Argo CD sync
ML training pipeline Workflows + S3 EventSource S3 新檔案 drop → trigger Workflow（preprocess → train → eval）
Cron-based 排程 CronWorkflow 每日 02:00 跑 backup workflow
Slack ChatOps Events webhook + Workflow Slack slash command → Sensor → Workflow（執行操作）→ 回 Slack message
多 source 觸發 Events（多 dependency） 等 GitHub PR + CI green + manual approval 三者都到位才觸發 deploy
Event 路由 Events + Trigger conditions 同一個 push event 依檔案路徑路由到不同 workflow
跨 cluster sync Events resource trigger cluster A 的 ConfigMap 改變 → Sensor → 在 cluster B 建對應資源

7最佳實踐與陷阱

常見陷阱

陷阱症狀解法
Workflow 在錯誤 namespace Sensor 觸發但 Workflow controller 看不到 確認 namespace 一致；或部署 controller 為 cluster-wide scope
Sensor SA 權限不足 Sensor 嘗試建 Workflow 失敗 RBAC denied operate-workflow-sa 需 workflows.argoproj.io create / get 權限
EventBus 單 replica NATS pod crash → 所有 sensor 失效 EventBus replicas: 3（生產必設）
EventSource 暴露 public 無認證 任何人都能 trigger workflow 用 webhookSecret 驗證簽章；或加 Ingress + auth proxy
webhook 沒過濾 任何 PR / push 都觸發 CI 用 filters.data 限定 branch / event type
Workflow artifacts 過大 Workflow 變慢、storage 滿 用 archive workflow + S3 artifact repository；過期清理
Workflow 卡住不 complete activeDeadlineSeconds 沒設 必設 spec.activeDeadlineSeconds（如 3600 = 1h）
大量 Workflows 累積 etcd 過載 設 workflowDefaults.spec.ttlStrategy.secondsAfterCompletion

最佳實踐 Checklist

✅

Workflows + Events 上線 12 項 Checklist

① 用 WorkflowTemplate（不要每次寫完整 Workflow，可重用）；② 必設 activeDeadlineSeconds（避免無限等待）；③ ttlStrategy 自動清理已完成的 Workflow（避免 etcd 壅塞）；④ artifact repository 用 S3 / GCS（不要存 etcd）；⑤ EventBus 至少 3 replicas（生產 HA）；⑥ EventSource 必認證（webhookSecret / mTLS）；⑦ Sensor 必過濾（filters.data 限定 branch / event type）；⑧ RBAC 最小權限（operate-workflow-sa 只給必要 verbs）；⑨ WorkflowTemplate + Argo CD 管理（GitOps 一致性）；⑩ monitor Workflow metrics（Prometheus 抓 /metrics 端點）；⑪ CronWorkflow 設 concurrencyPolicy: Forbid避免同時多 instance；⑫ 用 Argo Events 取代 polling 大規模監聽（CronJob 多到一定程度應改 Events）。

📌 Key Takeaways

  • 🌳Argo 是四個獨立專案的傘狀名稱：① Argo CD（GitOps CD）；② Argo Workflows（job orchestration）；③ Argo Events（event automation）；④ Argo Rollouts（progressive delivery）。不需要全裝，按需組合。本書 Vol 1-8 專注 Argo CD + Rollouts，Ch.39 補上 Workflows + Events。
  • 🔄Argo Workflows 核心 CRD 四種：① Workflow（一次性執行）；② WorkflowTemplate（可重用範本，推薦做法）；③ CronWorkflow（排程，比 K8s CronJob 強大）；④ ClusterWorkflowTemplate（跨 namespace 共用）。實務：每個 pipeline 寫成 WorkflowTemplate，Workflow 物件只引用 template + 傳參數。
  • 🕸️DAG vs Steps：① DAG（推薦）：用 dependencies: [task1, task2] 明確表達依賴，支援並行任務；② Steps：線性流程（每個 step 等前一個完成）。多數 CI/CD 場景用 DAG——測試/lint/security-scan 可並行，再 build → deploy 等三者完成。
  • 📦Artifacts 與 Outputs：① outputs.parameters 從 file 讀字串（傳 image tag）；② outputs.artifacts 上傳檔案/目錄到 S3 / GCS（傳 test results / build artifacts）；③ 下游 step 用 inputs.parameters 引用。artifact repository 必設（S3/GCS/MinIO），不要存 etcd。
  • ⚡Argo Events 四大元件：① EventSource（20+ 種：github、kafka、s3、slack...）；② EventBus（NATS-based 傳輸層，必設 3 replicas HA）；③ Sensor（訂閱 + filter + trigger）；④ Trigger（10+ 動作：K8s resource、Argo Workflow、HTTP webhook、AWS Lambda、Slack message...）。
  • 🔔Sensor 是 Events 的核心：dependencies 定義要等什麼事件（可多個，conditions 控制組合邏輯）；filters.data 過濾事件內容（如 branch、event type）；triggers 觸發動作；parameters 把 event body 內容傳給 trigger（如 git commit SHA → Workflow input）。
  • 🔗典型整合：GitHub webhook → Events → Workflows → Argo CD sync。流程：① GitHub push 觸發 EventSource；② Sensor 過濾 main branch；③ 觸發 Workflow 跑 clone/test/build/push image；④ commit image tag 到 GitOps repo；⑤ Argo CD 偵測變更 sync 到 cluster。完整 CI/CD 端到端 GitOps-pure。
  • ⚖️Argo Events vs Argo CD webhook：① 單純 Git push → sync：用 Argo CD 內建 /api/webhook（最輕量）；② 複雜 CI/CD pipeline：Argo Events + Workflows；③ 多 source 整合（Git + Docker push + Slack approval）：必用 Argo Events 的 multi-dependency。
  • 🏗️用 Argo CD 管 Workflows + Events：把 WorkflowTemplate / CronWorkflow / EventSource / Sensor 全部 commit Git，由 Argo CD GitOps 管理。「Argo CD 管 Argo」是 Argo 全家桶的標準做法——一切都是 declarative + Git-driven。
  • ✅12 項生產 Checklist：WorkflowTemplate（不要寫死 Workflow）、必設 activeDeadlineSeconds 與 ttlStrategy、artifact repository S3/GCS、EventBus 3 replicas HA、EventSource 必認證 webhookSecret、Sensor 必 filter、RBAC 最小權限、Argo CD 統一管理、monitor Workflow metrics、CronWorkflow concurrencyPolicy Forbid、大規模監聽用 Events 取代 polling。
