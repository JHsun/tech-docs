argocd-notifications
訂閱事件、模板、多通道整合

Ch.28 提到「用 Prometheus alerts 取代 Argo CD notifications 做 alerting」——所以 argocd-notifications 用來做什麼？事件通知：deployment succeeded、new image deployed、PR preview ready，這些正面通知類訊息進 Slack / Teams。本章完整講解 trigger / template / service / subscription 四大角色、官方 notifications-catalog、Slack 進階（attachments、thread grouping）、Teams / Email / Webhook 多通道整合、namespace-level 與 project-level 訂閱、常見除錯場景。

📋

前置：已完成 Vol 1-5 與 Ch.28。理解 Argo CD Application 的 sync / health phase。Slack workspace admin 權限（建立 Slack App）。對 Go template 語法（與 Helm 同）有基本概念。

1argocd-notifications vs Prometheus alerting

許多人混淆兩者用途，這是 Argo CD 觀測架構的關鍵分工：

用途argocd-notificationsPrometheus alerts
觸發機制事件驅動（Application status 變化即觸發）條件持續達標（for: 5m）才觸發
適合場景單一事件通知：「成功部署」「新 image」「PR preview ready」持續性問題：「sync 失敗率高」「reconcile 慢」「SLO 用完」
正/負面訊息主要正面（informational）主要負面（alerting）
抖動敏感度容易 noisy（網路抖動造成多次觸發）抖動不會觸發（必須持續達標）
典型通道Slack 一般 channel / Teams generalSlack #alerts / PagerDuty / Opsgenie
💡

實務分工建議

① argocd-notifications 用於：deployment succeeded → 通知 dev team；new image deployed → 通知 PM；PR preview ready → 留言到 PR；security CRD warning → 通知 platform。② Prometheus alerts 用於：5xx 錯誤率 / sync failure rate / SLO budget / controller down 等 SRE 警報。兩者並存才完整。

2架構與核心概念

2.1 四大角色

角色用途設定位置
Service通知通道（Slack / Email / Webhook）argocd-notifications-cm 的 service.<name>
Trigger觸發條件（用 expr-lang 寫條件）argocd-notifications-cm 的 trigger.<name>
Template訊息內容（用 Go template）argocd-notifications-cm 的 template.<name>
Subscription訂閱：誰要 trigger 在哪個 service 收到什麼 templateApplication annotation / Project annotation / Global

2.2 事件流程

1
application-controller 完成 reconcile，更新 Application status（如 sync.status: Succeeded）
2
notifications-controller 監聽 Application 變化，對每個 Application 套用所有 trigger
3
trigger 的 when 條件求值（如 app.status.sync.status == 'Succeeded'）→ 若為 true 且 oncePer 通過 → 標記為「該發通知」
4
檢查 Application 的 annotation 看哪些 service 訂閱了此 trigger，例如 notifications.argoproj.io/subscribe.on-deployed.slack: my-channel
5
渲染 template：trigger 的 send 列出 template 名稱，notifications-controller 用 Go template 渲染 message
6
送到 Service：呼叫對應 service 的 API（如 Slack chat.postMessage），帶 token + channel + message
7
記錄 metrics：argocd-notifications-controller-metrics:9001 記錄 delivery success / failure 計數

3安裝與啟用

3.1 安裝 notifications-catalog（預設 trigger + template）

Argo CD v2.x 起，notifications-controller 已整合進 argocd 主元件（不再需要 argocd-notifications 子專案）。但預設 trigger 與 template 需要單獨安裝，從官方 catalog 取得：

Bash — 安裝 notifications-catalog

$ kubectl apply -n argocd --server-side --force-conflicts \
    -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/notifications_catalog/install.yaml

# 驗證 ConfigMap 內容
$ kubectl get cm argocd-notifications-cm -n argocd -o yaml | head -50

# 包含的預設 triggers：
# - on-created                建立時
# - on-deleted                刪除時
# - on-deployed               成功部署
# - on-health-degraded        健康狀態變差
# - on-sync-failed            sync 失敗
# - on-sync-running           sync 進行中
# - on-sync-status-unknown    sync 狀態未知
# - on-sync-succeeded         sync 成功（與 deployed 不同）

# 對應的 templates：
# - app-created
# - app-deleted
# - app-deployed
# - app-health-degraded
# - app-sync-failed
# ... 與 trigger 對應
ℹ️

on-deployed vs on-sync-succeeded 的細微差別

① on-sync-succeeded：sync 完成（Argo CD 把 manifest apply 到 cluster）；② on-deployed：sync 成功且 health 變 Healthy。實務上 on-deployed 更有意義——「真的好了」而不只是「apply 完了」。生產通知建議用 on-deployed。

4Triggers 撰寫

4.1 expr-lang 條件語法

Trigger 的 when 條件用 expr-lang 寫（不是 Go template），這是專為「布林條件」設計的小語言：

YAML — 自訂 Trigger 範例
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-notifications-cm
  namespace: argocd
data:
  # 1) 基本：sync 成功
  trigger.on-sync-succeeded: |
    - when: app.status.operationState.phase in ['Succeeded']
      send: [app-sync-succeeded]

  # 2) 進階：production app 第一次部署到新 cluster
  trigger.on-first-deploy-to-prod: |
    - when: |
        app.metadata.labels.tier == 'production' &&
        app.status.sync.status == 'Synced' &&
        app.status.health.status == 'Healthy' &&
        app.status.operationState.operation.sync != nil &&
        app.status.history != nil &&
        len(app.status.history) == 1
      send: [first-deploy-celebration]

  # 3) 條件式：image tag 變更（CI/CD 整合）
  trigger.on-new-image: |
    - when: |
        app.status.sync.revision != app.status.history[0].revision &&
        app.status.sync.status == 'Synced' &&
        app.status.health.status == 'Healthy'
      send: [new-image-deployed]
      # oncePer：同一個 revision 只通知一次
      oncePer: app.status.sync.revision

  # 4) 多條件：health degraded 且不是 progressing
  trigger.on-health-degraded: |
    - when: |
        app.status.health.status == 'Degraded' &&
        app.status.sync.status != 'OutOfSync'
      send: [app-health-degraded]
      # 5 分鐘內只通知一次（避免狀態抖動）
      oncePer: app.status.health.status

  # 5) 字串包含：commit message 含 [breaking]
  trigger.on-breaking-change: |
    - when: |
        app.status.operationState.operation.sync.revision != '' &&
        'breaking' in (app.status.operationState.operation.initiatedBy.username ?? '')
      send: [breaking-change-alert]

4.2 oncePer 防重複通知（最重要！）

oncePer 是 expr-lang 表達式——對相同的 oncePer 值只通知一次。實務上是避免 noisy 通知的關鍵：

oncePer 表達式意義適用場景
app.status.sync.revision同一個 commit revision 只通知一次on-deployed（避免 selfHeal 反覆觸發）
app.status.health.statushealth status 不變則不重複通知on-health-degraded（避免 Degraded 持續觸發）
app.status.operationState.startedAt同一次 sync operation 只通知一次on-sync-running（避免每次 reconcile 都通知）
不設定每次條件達標都通知（容易 spam）不建議用於生產

4.3 官方 catalog 預設 trigger 完整列表

Trigger觸發時機建議用途
on-createdApplication 物件建立新 App 通知 platform team
on-deletedApplication 刪除稽核 / 安全
on-sync-runningsync 開始長時間 sync 才有用（一般略過）
on-sync-succeededsync 成功（manifest 已 apply）CI 觸發後續測試
on-sync-failedsync 失敗通知 dev / DevOps（容易 noisy）
on-sync-status-unknownsync 狀態變未知用 oncePer，否則 noisy
on-health-degradedhealth 變差通知 on-call（用 oncePer + Prometheus 雙保險）
on-deployedsync 成功且 Healthy最常用——真實部署成功

5Templates 撰寫

5.1 基本 message 與 Slack 進階

YAML — Template 基本與進階範例
data:
  # 1) 最簡單：純文字 message
  template.app-sync-succeeded: |
    message: |
      ✅ Application {{.app.metadata.name}} synced at {{.app.status.operationState.finishedAt}}.
      Revision: {{.app.status.sync.revision}}
      View: {{.context.argocdUrl}}/applications/{{.app.metadata.name}}

  # 2) Slack 進階：用 attachments 提供豐富格式
  template.app-deployed: |
    message: |
      🚀 Application {{.app.metadata.name}} successfully deployed!
    slack:
      attachments: |
        [{
          "title": "{{.app.metadata.name}}",
          "title_link": "{{.context.argocdUrl}}/applications/{{.app.metadata.name}}",
          "color": "#18be52",
          "fields": [
            {
              "title": "Sync Status",
              "value": "{{.app.status.sync.status}}",
              "short": true
            },
            {
              "title": "Health Status",
              "value": "{{.app.status.health.status}}",
              "short": true
            },
            {
              "title": "Repository",
              "value": "{{.app.spec.source.repoURL}}",
              "short": false
            },
            {
              "title": "Revision",
              "value": "{{.app.status.sync.revision | slice 0 7}}",
              "short": true
            },
            {
              "title": "Environment",
              "value": "{{index .app.metadata.labels \"env\"}}",
              "short": true
            }
          ]
        }]

  # 3) 失敗通知（紅色 color）
  template.app-sync-failed: |
    message: |
      ❌ Application {{.app.metadata.name}} sync failed.
      Reason: {{.app.status.operationState.message}}
    slack:
      attachments: |
        [{
          "title": "{{.app.metadata.name}}",
          "color": "#E96D76",
          "fields": [
            {
              "title": "Error",
              "value": "{{.app.status.operationState.message}}",
              "short": false
            }
          ]
        }]

5.2 groupingKey 聚合 Slack thread（大規模部署必設）

當 GitOps push 同時觸發 30 個 Application sync，預設會在 channel 連發 30 條訊息——使用者體驗極差。groupingKey 把相同 key 的訊息聚合到同一個 thread：

YAML — groupingKey 聚合範例
template.app-deployed: |
  message: |
    🚀 Application {{.app.metadata.name}} deployed
  slack:
    attachments: |
      [{
        "title": "{{.app.metadata.name}}",
        "color": "#18be52",
        "fields": [
          {"title": "Revision", "value": "{{.app.status.sync.revision | slice 0 7}}"}
        ]
      }]
    # 用 git commit hash 聚合 thread
    # 同一次 commit 觸發的多個 Application 部署訊息聚合到同一個 thread
    groupingKey: "{{.app.status.sync.revision}}"
    # 是否同時發 channel 訊息（除了 thread reply）
    notifyBroadcast: false

# 效果：
#   #deployments channel:
#     🚀 app-1 deployed
#       └ 🚀 app-2 deployed (thread reply)
#       └ 🚀 app-3 deployed (thread reply)
#       └ ... 27 more in thread
# 大幅減少 channel 雜訊
💡

常用 groupingKey 策略

① {{.app.status.sync.revision}}：同 commit 部署聚合（最常用）；② {{index .app.metadata.labels "release"}}：同 release 聚合（適合 release train）；③ {{.app.spec.project}}：同 project 聚合（per-team channel 已分流，再聚合更乾淨）。不設 groupingKey 會在大規模部署造成 alert fatigue。

6Subscription 三層

三層 subscription，從細到粗：

6.1 Application-level annotation（最細）

YAML — Application annotation 訂閱
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  annotations:
    # 格式：notifications.argoproj.io/subscribe.<trigger>.<service>: <recipient>
    # 多個 recipient 用 ; 分隔
    notifications.argoproj.io/subscribe.on-deployed.slack: deployments;engineering
    notifications.argoproj.io/subscribe.on-sync-failed.slack: urgent-alerts
    notifications.argoproj.io/subscribe.on-sync-failed.email: oncall@example.com
    notifications.argoproj.io/subscribe.on-health-degraded.slack: health-alerts

6.2 Project-level annotation（per-team）

在 AppProject 設定 annotation，所有屬於該 project 的 Application 自動繼承：

YAML — Project annotation 訂閱
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-alpha
  namespace: argocd
  annotations:
    # 所有 team-alpha 的 Application 都會把 on-deployed 送到 alpha-deployments channel
    notifications.argoproj.io/subscribe.on-deployed.slack: alpha-deployments
    notifications.argoproj.io/subscribe.on-sync-failed.slack: alpha-alerts
spec:
  description: Team Alpha applications
  # ... 其他 spec

6.3 Global subscriptions（all apps）

在 argocd-notifications-cm 設定 subscriptions 欄位，可用 selector 過濾：

YAML — Global subscriptions
data:
  subscriptions: |
    # 所有 app 的 sync-status-unknown 都送到 monitoring channel
    - recipients:
        - slack:monitoring
        - email:platform-team@example.com
      triggers:
        - on-sync-status-unknown

    # 只 label tier=critical 的 app 的 health-degraded 送到 on-call
    - recipients:
        - slack:oncall
      selector: tier=critical
      triggers:
        - on-health-degraded

    # 所有 production 環境的 sync-failed 送到 webhook（PagerDuty）
    - recipients:
        - webhook:pagerduty
      selector: env=production
      triggers:
        - on-sync-failed
ℹ️

三層 subscription 是「並集」

App annotation + Project annotation + Global subscription 三層的訂閱都會生效——同一個 trigger 可能同時送到 app-level 的 channel + project-level 的 channel + global 的 webhook。實務建議：① global 設組織級訊息（如所有 sync-failure 進 #all-deployments）；② project 設 team 訊息；③ app annotation 只用於特殊例外。

7多通道：Teams / Email / Webhook

7.1 Microsoft Teams（Webhook）

YAML — Microsoft Teams 整合
## Step 1：在 Teams channel 加入 "Incoming Webhook" connector
## Teams channel → ... → Connectors → Incoming Webhook → Configure
## 取得 Webhook URL：https://outlook.office.com/webhook/...

## Step 2：argocd-notifications-secret 儲存 URL
apiVersion: v1

metadata:
  name: argocd-notifications-secret
stringData:
  teams-webhook: https://outlook.office.com/webhook/...

## Step 3：argocd-notifications-cm 設定 service.teams
data:
  service.teams: |
    recipientUrls:
      argocd-team: $teams-webhook        # key 是 recipient 名稱
      platform-team: $teams-webhook-platform

  # Teams template（用 MessageCard schema）
  template.app-deployed-teams: |
    teams:
      title: "🚀 Application Deployed"
      themeColor: "0078D7"
      facts: |
        [
          {"name": "Application", "value": "{{.app.metadata.name}}"},
          {"name": "Revision", "value": "{{.app.status.sync.revision | slice 0 7}}"},
          {"name": "Environment", "value": "{{index .app.metadata.labels \"env\"}}"}
        ]

## Step 4：訂閱（app annotation 中 service 寫 teams）
# notifications.argoproj.io/subscribe.on-deployed.teams: argocd-team

7.2 Email（SMTP / Gmail）

YAML — Email SMTP 設定
## Secret
stringData:
  email-username: noreply@example.com
  email-password: app-specific-password      # Gmail 需用 App Password

## ConfigMap
data:
  service.email.gmail: |
    username: $email-username
    password: $email-password
    host: smtp.gmail.com
    port: 465
    from: $email-username

  # 多個 email service（用於不同寄件人）
  service.email.alerts: |
    username: $email-username
    password: $email-password
    host: smtp.gmail.com
    port: 465
    from: argocd-alerts@example.com

  template.app-sync-failed-email: |
    email:
      subject: "🚨 [{{.app.spec.project}}] Sync failed for {{.app.metadata.name}}"
    message: |
      Application {{.app.metadata.name}} failed to sync.

      Error: {{.app.status.operationState.message}}

      View: {{.context.argocdUrl}}/applications/{{.app.metadata.name}}

## 訂閱：notifications.argoproj.io/subscribe.on-sync-failed.email: oncall@example.com
## 或指定 service 名稱：subscribe.on-sync-failed.alerts: oncall@example.com

7.3 Custom Webhook（PagerDuty / OpsGenie / 自製整合）

YAML — Custom Webhook（PagerDuty 範例）
data:
  service.webhook.pagerduty: |
    url: https://events.pagerduty.com/v2/enqueue
    headers:
      - name: Content-Type
        value: application/json

  template.pagerduty-trigger: |
    webhook:
      pagerduty:
        method: POST
        body: |
          {
            "routing_key": "{{.context.pagerduty_routing_key}}",
            "event_action": "trigger",
            "dedup_key": "{{.app.metadata.name}}",
            "payload": {
              "summary": "ArgoCD app {{.app.metadata.name}} failed",
              "severity": "error",
              "source": "argocd",
              "custom_details": {
                "app": "{{.app.metadata.name}}",
                "error": "{{.app.status.operationState.message}}"
              }
            }
          }

## 訂閱：subscribe.on-sync-failed.webhook: pagerduty
⚠️

PagerDuty / Opsgenie 用 Prometheus alerts 而非 notifications

雖然 notifications 支援 PagerDuty webhook，但正確做法仍是 Prometheus alerts → Alertmanager → PagerDuty。原因：① Prometheus alerts 有 inhibition、grouping、silence；② 抖動不會觸發 page；③ Alertmanager 是 industry standard。notifications 適合 informational 訊息（Slack / Teams / Email），不適合 paging。

8除錯與最佳實踐

常用除錯指令

Bash — Notifications 除錯
## 1. 看 controller log（最重要的除錯起點）
$ kubectl logs -n argocd deploy/argocd-notifications-controller -f --tail=100

## 2. 看 metrics（成功 / 失敗統計）
$ kubectl port-forward -n argocd \
    svc/argocd-notifications-controller-metrics 9001:9001
$ curl http://localhost:9001/metrics | grep -E 'notification|trigger'

## 3. 手動觸發測試（patch app 加 annotation）

    "op": "replace",

argocd-notifications 上線 Checklist

① 從 catalog 安裝預設 trigger/template（不要從零寫）；② 用 on-deployed 而非 on-sync-succeeded（真實部署完成）；③ 所有 trigger 必設 oncePer；④ 大規模部署用 groupingKey聚合 thread；⑤ 三層 subscription 分工：global 組織訊息、project per-team、app 例外；⑥ Slack App 用 dedicated bot（不要用個人 user token）；⑦ 監控 controller metrics（notification_delivered_total / notification_dropped_total）；⑧ 分流 channel：deployments / alerts / health 不同 channel，避免單 channel 過載；⑨ 不用於 paging（PagerDuty 等用 Prometheus + Alertmanager）；⑩ 定期 review 訂閱，移除離職人員的 email 與不再使用的 channel。

✓本章重點回顧

📌 Key Takeaways

  • 🔔argocd-notifications vs Prometheus alerts 是分工：notifications 用於事件通知（deployment succeeded、new image、PR ready），Prometheus 用於持續性 alerting（sync failure rate、SLO budget）。兩者並存才完整。不要用 notifications 做 paging（用 Prometheus + Alertmanager + PagerDuty）。
  • 🎭四大角色：Service（通道）+ Trigger（條件）+ Template（內容）+ Subscription（訂閱）。Service 與 Trigger / Template 都在 argocd-notifications-cm 設定；Subscription 在 Application / AppProject annotation 或全域 subscriptions 欄位。
  • 📦先安裝官方 notifications-catalog（8 個預設 trigger + 對應 template，5 分鐘啟動）：on-created / on-deleted / on-sync-running / on-sync-succeeded / on-sync-failed / on-sync-status-unknown / on-health-degraded / on-deployed。on-deployed 最常用（sync 成功且 Healthy），on-sync-succeeded 只是 apply 完未必健康。
  • 💬Slack 5 步驟設定：① 建立 Slack App；② 設定 chat:write / chat:write.public scopes；③ Install to Workspace 取得 Bot Token；④ /invite @Argo CD Notifications 加 App 到 channel；⑤ 設定 secret（token）+ cm（service.slack）。常見錯誤："not_in_channel"——忘了第 4 步。
  • 🧮Trigger 用 expr-lang，Template 用 Go template：兩種不同語言！① expr-lang 是布林條件（app.status.sync.status == 'Synced'）；② Go template 是字串渲染（{{.app.metadata.name}}）。oncePer 是 expr-lang（如 oncePer: app.status.sync.revision）——同樣的 oncePer 值只通知一次，避免 spam。
  • 🧵groupingKey 是大規模部署必設：GitOps 一次 push 觸發 30 個 app sync，沒 groupingKey 會在 Slack channel 連發 30 條訊息；有 groupingKey 後聚合到同一個 thread（用 {{.app.status.sync.revision}} 聚合同 commit）。同時設 notifyBroadcast: false 避免 thread reply 也廣播到 channel。
  • 📋三層 subscription 是並集：① App annotation（最細，只此 app）；② Project annotation（per-team 預設）；③ Global subscriptions（all apps，可用 selector 過濾）。實務建議：global 設組織級訊息、project 設 team 訊息、app annotation 只用於特殊例外。
  • 🔌多通道整合：Slack（最常用）、Teams（webhook + MessageCard）、Email（SMTP / Gmail App Password）、Custom Webhook（PagerDuty / OpsGenie / 自製）。Gmail 必用 App Password（一般密碼會被拒絕）。在 secret 用 $name 引用，cm 中用 $name。
  • 🔍除錯利器：argocd admin notifications：trigger run on-deployed my-app 看條件求值；template notify app-deployed my-app --recipient slack:test 直接送測試訊息；controller log 看 delivery failure；metrics endpoint :9001 看成功/失敗統計。Template 含 hyphen key（如 team-name label）必用 {{index .x.y "z"}}。
