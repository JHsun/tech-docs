Argo Rollouts 基礎
Rollout CRD、Canary、Blue-Green

Vol 8 第一章。K8s 原生 Deployment 只有 RollingUpdate，缺乏「先讓 10% 流量試試、觀察 5 分鐘、metrics 正常才推 50%」的精細控制——這正是 Argo Rollouts 解決的問題。本章涵蓋 Argo Rollouts 的核心 CRD（Rollout）、與 Deployment 的差異、Canary strategy（setWeight + pause）、Blue-Green strategy（active/preview service）、kubectl plugin CLI（promote/abort/retry）、Web Dashboard、與 Argo CD 的關係（Argo Rollouts 不依賴 Argo CD，但兩者完美互補）。下一章 Ch.37 將進入 AnalysisTemplate 自動化決策。

📋

前置：已完成 Vol 1-7。理解 K8s Deployment / ReplicaSet 機制（Ch.05）、Service 與 Endpoint。理解 rolling update strategy（maxSurge/maxUnavailable）。理解 readiness probe。對 canary / blue-green deployment 概念有基礎認識。

🎯 學習目標

  • 理解 K8s 原生 Deployment 的 5 大限制：無法控制流量比例、無 metric-based 決策、不能 pause、回滾慢、難以實作 canary
  • 掌握 Progressive Delivery 的核心概念：在 Continuous Delivery 基礎上加入「逐步擴大用戶曝光 + metric-driven 決策」
  • 安裝 Argo Rollouts controller、kubectl-argo-rollouts plugin、Web Dashboard
  • 從現有 Deployment 遷移到 Rollout：只需改 apiVersion + kind + 加 strategy，pod template 不變
  • 掌握 Rollout CRD 完整結構：spec（與 Deployment 99% 相同）+ strategy（canary 或 blueGreen）
  • 實作 Canary strategy：setWeight（流量比例）+ pause（duration 等待或無限等待）+ analysis（指向 AnalysisTemplate，Ch.37 詳細介紹）
  • 區分 replica-based canary（不需 service mesh）vs traffic-based canary（精細流量控制，需 Istio/SMI/NGINX/Gateway API）
  • 實作 Blue-Green strategy：activeService + previewService + autoPromotionEnabled + scaleDownDelaySeconds
  • 掌握 kubectl-argo-rollouts CLI：get / promote / abort / restart / retry / set image / watch
  • 使用 Argo Rollouts Web Dashboard（不需 Argo CD）獨立查看 rollout 進度
  • 選擇正確的策略：何時用 canary、何時用 blue-green、何時 traffic-based vs replica-based

1Deployment 的限制

1.1 為什麼需要 Argo Rollouts？

K8s 原生 Deployment 提供 RollingUpdate 策略，但有明顯限制：

限制原生 DeploymentArgo Rollouts
流量比例控制 ❌ 只能控制 pod 數量（maxSurge/maxUnavailable），實際流量不精確 ✅ setWeight 精確控制流量百分比（搭配 service mesh）
Metric-based 決策 ❌ 無法依 error rate / latency 決定是否繼續 ✅ AnalysisTemplate 整合 Prometheus / Datadog / New Relic 自動判斷
暫停 (Pause) ❌ 不能暫停 rollout ✅ 在任何 step 可手動或自動暫停
回滾速度 慢（要 scale down 新 ReplicaSet、scale up 舊的） ✅ 立即（保留 stable ReplicaSet，只需切換流量）
Blue-Green ❌ 必須自行寫 script 切換 Service selector ✅ 原生支援，activeService + previewService 自動切換
實驗 (Experiment) ❌ 無 ✅ Experiment CRD 可同時跑多版本 A/B test

1.2 Progressive Delivery 概念

💡

Progressive Delivery = CD + 漸進式曝光 + 自動決策

① Continuous Delivery：自動部署到 production（但是 all-or-nothing）；② Progressive Delivery：在 CD 之上，加入逐步擴大用戶曝光（10% → 30% → 50% → 100%）+ metric-driven 決策（error rate > 1% 自動 abort）。blast radius 限制在小範圍，問題在 10% 流量就被偵測並回滾，而不是影響全部用戶。

典型的 Progressive Delivery 場景：

  • ① 新版本逐步擴大：10% 流量 5 分鐘 → 30% 5 分鐘 → 50% → 100%
  • ② Header-based testing：特定 header（如 internal users）流量到新版，其他用戶看舊版
  • ③ Blue-green with smoke test：新版本部署到 preview service，跑完 smoke test 才切換 active
  • ④ A/B test：50/50 流量分到兩版本，依商業指標（轉換率）決定保留哪個
  • ⑤ 自動 abort：error rate / latency 超過閾值自動回滾，不需人工介入

ℹ️

Argo Rollouts 與 Argo CD 是獨立專案

Argo Rollouts 是 Argo project 旗下獨立的 controller，不依賴 Argo CD 也能用。但兩者搭配是 GitOps + Progressive Delivery 的完美組合：① Argo CD 負責 Git → cluster 同步；② Argo Rollouts 接管 Rollout CR 的實際 deployment 邏輯。Argo CD 從 v2.0 起內建 Rollouts 的 health check，UI 自動顯示 rollout 進度（Ch.38 詳細介紹）。

2.2 從 Deployment 遷移

YAML — Deployment → Rollout 對比
## ── BEFORE: K8s Deployment ───────────────────────────
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 5
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: myorg/my-app:v1.0.0
          ports:
            - containerPort: 8080
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 25%

## ── AFTER: Argo Rollout（只改三處）──────────────────
apiVersion: argoproj.io/v1alpha1  # ① 變
kind: Rollout                       # ② 變
metadata:
  name: my-app
spec:
  replicas: 5
  selector:
    matchLabels:
      app: my-app
  template:                          # Pod template 完全一樣
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: myorg/my-app:v1.0.0
          ports:
            - containerPort: 8080
  strategy:                          # ③ 換成 canary / blueGreen
    canary:
      steps:
        - setWeight: 25
        - pause: { duration: 5m }
        - setWeight: 50
        - pause: { duration: 5m }
        - setWeight: 100
⚠️

遷移時必須刪除舊 Deployment

Rollout 與 Deployment 是不同 CRD——遷移時不能直接 kubectl apply -f rollout.yaml 就完事，必須先 kubectl delete deployment my-app 再 apply Rollout。否則會有兩個 controller 同時管 ReplicaSet，造成混亂。GitOps repo 中也要把 deployment.yaml 改成 rollout.yaml，Argo CD sync 時會偵測到變更。Ch.38 會講解 Argo CD 整合的細節。

3Rollout CRD 結構

3.1 與 Deployment 99% 相同

YAML — Rollout 完整 spec 結構
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  # ── 與 Deployment 共同欄位 ──────────
  replicas: 5
  selector: {matchLabels: {app: my-app}}
  template:
    metadata:
      labels: {app: my-app}
    spec:
      containers:
        - name: my-app
          image: myorg/my-app:v1.0.0
          readinessProbe:
            httpGet: {path: /health, port: 8080}

  minReadySeconds: 30          # pod 至少 ready 多久才算 healthy
  revisionHistoryLimit: 10     # 保留多少舊 ReplicaSet
  progressDeadlineSeconds: 600  # 10 分鐘沒進展視為失敗

  # ── Rollouts 特有 ──────────────────

  # 1) Strategy（canary 或 blueGreen，二選一）
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - setWeight: 50
        - pause: {}                  # 無限等待手動 promote
      # 流量管理（traffic-based canary 必須）
      canaryService: my-app-canary
      stableService: my-app-stable
      trafficRouting:
        nginx:
          stableIngress: my-app-ingress

  # 2) Workload reference（v1.0+ 可選）
  # 對既有 Deployment 直接 wrap，無需改 Deployment
  # workloadRef:
  #   apiVersion: apps/v1
  #   kind: Deployment
  #   name: existing-deployment

4Canary Strategy

4.1 setWeight + pause 基本範例

YAML — 5 步驟 canary 完整範例
spec:
  replicas: 10
  strategy:
    canary:
      steps:
        # Step 1：10% 流量 → 1 個 canary pod
        - setWeight: 10

        # Step 2：等待 5 分鐘觀察
        - pause: {duration: 5m}

        # Step 3：30% 流量 → 3 個 canary pod
        - setWeight: 30
        - pause: {duration: 5m}

        # Step 4：50% 流量
        - setWeight: 50
        - pause: {}                  # 無限等待 manual promote

        # Step 5：100% 流量（manual promote 後執行）
        - setWeight: 100

Pause 兩種模式

寫法行為適合
pause: {duration: 5m} 等待 5 分鐘自動推進 低風險變更、自動化 pipeline
pause: {} 無限等待，必須手動 argo rollouts promote 才繼續 重要環境、需 reviewer 批准
pause: {duration: 24h} 長時間 canary（觀察一整天） 需大量真實流量驗證

4.2 Replica-based vs Traffic-based Canary

沒有 service mesh 時，Argo Rollouts 用 replica ratio 近似流量比例：

Mermaid — Replica-based vs Traffic-based
## Replica-based canary（無 service mesh）
## - setWeight: 25 + 10 replicas → 2 canary + 8 stable（K8s service 隨機路由）
## - 流量 ≈ replica ratio，但不精確（service 是隨機輪詢）

  ┌───────────────────────┐
  │ K8s Service           │
  │ (random load balance) │
  └────┬─────────────┬────┘
       │             │
  ┌────▼─────┐  ┌────▼─────┐
  │ 2 canary │  │ 8 stable │   ratio = 2:8 ≈ 20:80
  │ pods     │  │ pods     │
  └──────────┘  └──────────┘

## Traffic-based canary（with NGINX / Istio / SMI / Gateway API）
## - setWeight: 25 + 10 replicas → 可以是 1 canary + 9 stable
## - 流量精確 25%（service mesh 控制）

  ┌──────────────────────────┐
  │ NGINX / Istio Gateway    │
  │ (precise weight: 25/75)  │
  └────┬─────────────┬───────┘
       │ 25%         │ 75%
  ┌────▼─────┐  ┌────▼──────┐
  │ 1 canary │  │ 9 stable  │  流量精確控制
  │ pod      │  │ pods      │
  └──────────┘  └───────────┘
YAML — Traffic-based canary（NGINX Ingress）
spec:
  strategy:
    canary:
      # 流量管理必要欄位
      canaryService: my-app-canary      # 指向 canary ReplicaSet
      stableService: my-app-stable      # 指向 stable ReplicaSet

      trafficRouting:
        # 選擇一種：nginx / istio / smi / alb / appmesh / gatewayAPI / traefik
        nginx:
          stableIngress: my-app-ingress   # NGINX Ingress 名稱

      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - setWeight: 50

  # Argo Rollouts 自動建立 my-app-canary Ingress（含 canary annotations）
  # NGINX 看到兩個 Ingress（stable + canary），按 weight 路由流量

---
apiVersion: v1
kind: Service
metadata:
  name: my-app-stable
spec:
  selector:
    app: my-app            # controller 自動加 rollouts-pod-template-hash label
  ports:
    - port: 80
      targetPort: 8080

---
apiVersion: v1
kind: Service
metadata:
  name: my-app-canary
spec:
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
💡

選用 replica-based 或 traffic-based？

① replica-based（無 service mesh）：設定簡單，適合大 replica 數（如 100+）。缺點：流量比例不精確，setWeight: 5% 對 10 replicas 沒意義（最少 1 個 pod = 10%）；② traffic-based（需 ingress / service mesh）：精確流量控制，可設 setWeight: 5%。缺點：需 Istio / NGINX 等基礎設施。多數情況推薦 traffic-based——尤其搭配 AnalysisTemplate（Ch.37）需要精確流量做 metric-based 決策。

4.3 Promote / Abort 操作

Bash — Canary 控制命令
## 1) Promote：推進到下一個 step
$ kubectl argo rollouts promote my-app
# 從 pause:{} 推進到 setWeight: 100

## 2) Promote --full：直接跳到最後
$ kubectl argo rollouts promote my-app --full
# 跳過剩餘 step 直接 setWeight: 100（緊急情況用）

## 3) Abort：放棄這次 rollout（流量切回 stable）
$ kubectl argo rollouts abort my-app
# 立即把流量切回 stable，但 canary ReplicaSet 留著（不會 scale down）

## 4) Retry：abort 後重新觸發
$ kubectl argo rollouts retry rollout my-app

## 5) Set image：直接改 image（觸發新 rollout）
$ kubectl argo rollouts set image my-app my-app=myorg/my-app:v2.1.0

## 6) Pause / Unpause（無 step 的 pause）
$ kubectl argo rollouts pause my-app
$ kubectl argo rollouts pause my-app --unpause

## 7) Restart：rolling restart pod（不換版本）
$ kubectl argo rollouts restart my-app

## 8) Watch：即時看進度
$ kubectl argo rollouts get rollout my-app --watch

5Blue-Green Strategy

5.1 Active vs Preview Service

Blue-Green 是另一種 progressive delivery 模式——同時運行兩個完整版本，瞬間切換流量：

Mermaid — Blue-Green 架構
## 部署前：
   ┌──────────────────┐
   │ activeService    │ ─────► Blue ReplicaSet (v1)
   │ (live traffic)   │
   └──────────────────┘
   
## 更新觸發：建立 Green ReplicaSet
   ┌──────────────────┐
   │ activeService    │ ─────► Blue (v1)   ← live traffic
   └──────────────────┘
   ┌──────────────────┐
   │ previewService   │ ─────► Green (v2)  ← internal testing
   │ (smoke test)     │
   └──────────────────┘

## Promote 後：瞬間切換
   ┌──────────────────┐
   │ activeService    │ ─────► Green (v2)  ← live traffic
   └──────────────────┘
   ┌──────────────────┐
   │ previewService   │ ─────► Green (v2)
   └──────────────────┘
   Blue (v1) ← 留著 scaleDownDelaySeconds 秒供 quick rollback

## 等待結束：Blue 被 scale down
   Blue (v1) deleted
   Green (v2) → only version
YAML — Blue-Green 完整範例
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  replicas: 5
  selector: {matchLabels: {app: my-app}}
  template:
    # ... 同上

  strategy:
    blueGreen:
      # 必要：active service（line traffic）
      activeService: my-app-active

      # 可選：preview service（給 smoke test 用）
      previewService: my-app-preview

      # 自動 promotion 設定
      autoPromotionEnabled: false      # true: 新版 ready 後自動切；false: 需手動 promote
      autoPromotionSeconds: 300          # 新版 ready 後等 5 分鐘自動 promote

      # 舊版留多久供 rollback
      scaleDownDelaySeconds: 600         # 切換後 10 分鐘才 scale down 舊版

      # Pre-promotion analysis（切流前先驗證）
      prePromotionAnalysis:
        templates:
          - templateName: smoke-test     # Ch.37 介紹

      # Post-promotion analysis（切流後 validate）
      postPromotionAnalysis:
        templates:
          - templateName: error-rate-check

      # Anti-affinity：強制 canary 與 stable 在不同 node
      antiAffinity:
        requiredDuringSchedulingIgnoredDuringExecution: {}

---
# Active service（live traffic）
apiVersion: v1
kind: Service
metadata:
  name: my-app-active
spec:
  selector:
    app: my-app    # controller 自動加 hash label 切換
  ports:
    - port: 80

---
# Preview service（internal testing）
apiVersion: v1
kind: Service
metadata:
  name: my-app-preview
spec:
  selector:
    app: my-app
  ports:
    - port: 80

5.2 autoPromotionEnabled 兩種模式

autoPromotionEnabled行為適合
true（預設） 新版 ReplicaSet 全部 ready 後立即切換 active service 低風險變更
false 新版 ready 後無限等待，必須 manual argo rollouts promote 需 QA 在 preview 跑完測試才切換
false + autoPromotionSeconds: N 新版 ready 後等 N 秒自動 promote（給 prePromotionAnalysis 跑） 有 automated smoke test 的場景
💡

Canary vs Blue-Green 選擇

① Canary：漸進式擴大（10% → 50% → 100%），適合需 metric-driven 決策、想觀察真實流量行為的場景。缺點：需要應用支援版本共存（API 向下相容）；② Blue-Green：瞬間切換，適合不能版本共存（如 DB schema 變更）、需明確 cutover 時間點的場景。缺點：需要 2x 資源（兩版本同時運行）。實務組合：dev/staging 用 canary 觀察 metrics，prod 用 blue-green 配合 prePromotionAnalysis（smoke test 通過才切換）。

動態 Stable 縮放（dynamicStableScale）

YAML — 節省資源的 traffic-based canary
spec:
  strategy:
    canary:
      canaryService: my-app-canary
      stableService: my-app-stable
      trafficRouting:
        nginx:
          stableIngress: my-app-ingress

      # 預設 false：traffic-based 模式下 stable 永遠 100% replicas
      # （安全但耗 2x 資源）
      # 設 true：stable 隨 canary weight 反向縮放
      dynamicStableScale: true

      steps:
        - setWeight: 25
        # dynamicStableScale: true → stable 從 100% 降到 75%
        # 總 replicas 不變（節省資源）
        - pause: {duration: 5m}
        - setWeight: 75
        # stable 降到 25%
        - pause: {duration: 5m}
        - setWeight: 100
        # stable scale 為 0
⚠️

dynamicStableScale 的 trade-off

① 優點：節省資源（不需 2x replicas）；② 缺點：abort 時 stable 需重新 scale up 才能接流量，rollback 變慢（從 secs 變成 minutes）。適合大 replica 數 + 資源緊張 + abort 不那麼緊急的場景。Critical service 寧可花資源也要保留 stable 100% 以便瞬間 rollback。

Rollout 上線 Checklist

① 從 simple canary 開始（2-3 step + duration pause）熟悉後再加 analysis；② 必設 progressDeadlineSeconds（10 分鐘沒進展視為失敗，避免卡住）；③ 必設 readinessProbe（rollout 用此判斷 pod ready）；④ minReadySeconds > 30 避免 false positive；⑤ traffic-based 用 service mesh 取得精確流量；⑥ scaleDownDelaySeconds >= 600（blue-green 留 10 分鐘以上 rollback）；⑦ monitor pausing condition（卡 pause 太久應自動 alert）；⑧ CI integrate argo rollouts status 等待完成；⑨ Argo CD UI 整合（Ch.38）讓 sync 顯示 rollout 進度；⑩ 準備 abort runbook（什麼情況該 abort、怎麼 git revert）。

📌 Key Takeaways

  • 🚀Argo Rollouts 補足 K8s Deployment 的 5 大限制：① 無精確流量控制；② 無 metric-based 決策；③ 不能 pause；④ 回滾慢；⑤ 不支援 blue-green。Rollouts 透過 CRD + controller + service mesh 整合提供 progressive delivery。與 Argo CD 是獨立但完美搭配的兩個 Argo project。
  • 📦三大元件：① argo-rollouts-controller（必要）；② kubectl-argo-rollouts CLI plugin（建議）；③ argo-rollouts-dashboard（選用，不需 Argo CD 也能用）。Rollout 與 Argo CD 完全解耦，可獨立部署使用。
  • 🔄從 Deployment 遷移只改三處：① apiVersion: argoproj.io/v1alpha1；② kind: Rollout；③ 加 strategy: canary 或 blueGreen。Pod template 完全不變。或用 workloadRef wrap 既有 Deployment 不刪除原物件。⚠️ GitOps repo 必須同步改，否則 Argo CD sync 會衝突。
  • 📊Canary strategy：setWeight + pause 黃金組合。setWeight: N 設定流量百分比，pause: {duration: 5m} 自動推進或 pause: {} 無限等待手動 promote。經典 5 step：10% → pause 5m → 30% → pause 5m → 50% → pause {} → 100%。
  • 🚦Replica-based vs Traffic-based canary：① replica-based（無 service mesh）：用 replica ratio 近似流量比例，簡單但不精確；② traffic-based（需 NGINX/Istio/SMI/Gateway API/Traefik/ALB/AppMesh）：精確控制流量。多數場景推薦 traffic-based，尤其搭配 AnalysisTemplate 需要精確流量。
  • 🔵🟢Blue-Green strategy：activeService + previewService。瞬間切換（vs canary 漸進），適合不能版本共存（DB schema 變更）的場景。autoPromotionEnabled: false + autoPromotionSeconds: N 提供 pre-promotion 驗證時間；scaleDownDelaySeconds: 600 留舊版 10 分鐘供 quick rollback。
  • 🎮10 個 CLI 必備命令：get rollout --watch、promote（含 --full）、abort、retry、set image、pause/unpause、restart、undo、list rollouts、status --watch --timeout。CI 中用 argo rollouts status 等待完成（與 argocd app wait 搭配）。
  • 🖥️Web Dashboard 獨立運作：本機用 kubectl argo rollouts dashboard port-forward；生產用 cluster 部署 + Ingress。提供：所有 Rollout 清單、即時 step 進度、Promote/Abort 按鈕、Analysis Run 結果（Ch.37）。不需 Argo CD。
  • ⚖️Canary vs Blue-Green 選擇：① canary 適合 API 向下相容、需 metric 觀察、節省資源；② blue-green 適合 DB schema 變更、需明確 cutover、可承受 2x 資源。實務組合：dev/staging canary 觀察；prod blue-green + prePromotionAnalysis。
  • 💰dynamicStableScale 節省資源：traffic-based 預設 stable 永遠 100%（耗 2x），設 true 後 stable 隨 canary weight 反向縮放（總 replicas 不變）。trade-off：節省資源 vs rollback 變慢（stable 需 scale up 才能接流量）。critical service 寧可耗資源也要保留即時 rollback 能力。
