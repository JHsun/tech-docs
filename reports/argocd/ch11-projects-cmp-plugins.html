與 Config Management Plugins

1AppProject 多租戶邊界

AppProject 是 Argo CD 的安全與治理核心。每個 Application 必須屬於一個 AppProject，Project 定義了「這個團隊可以從哪裡 pull manifest、可以部署到哪裡、可以建立哪些 K8s 資源」的完整邊界。預設的 default project 沒有任何限制，生產環境絕不應使用 default project，而是為每個團隊或環境建立獨立 Project。

1.1 AppProject 完整 Spec

YAML — 生產等級 AppProject 完整範例
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-backend
  namespace: argocd
  # Finalizer：確保 Project 不會在仍有 Application 引用時被刪除
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  description: "Backend team applications - production and staging"

  # ── 邊界 1：允許的 Source Repos ────────────────────────────
  sourceRepos:
    - 'https://github.com/myorg/backend-*'          # 萬用字元
    - 'https://github.com/myorg/shared-libs'          # 精確 repo
    - 'https://charts.bitnami.com/bitnami'            # Helm chart repo
    - '!https://github.com/myorg/secrets-*'           # 拒絕（! 前綴）

  # ── 邊界 2：允許的 Destinations（cluster + namespace）─────
  destinations:
    # 允許部署到 backend-* namespace
    - server: https://kubernetes.default.svc
      namespace: backend-*
    # 允許部署到 production cluster 的 backend namespace
    - name: prod-cluster           # 用 cluster name 而非 server URL
      namespace: backend
    # 拒絕部署到 kube-system（防止意外操作）
    - server: '*'
      namespace: '!kube-system'     # namespace 拒絕規則

  # ── 邊界 3：允許建立的 cluster-scoped 資源 ────────────────
  # 預設拒絕所有 cluster-scoped 資源（whitelist 模式）
  clusterResourceWhitelist:
    - group: ''
      kind: Namespace
    - group: 'rbac.authorization.k8s.io'
      kind: ClusterRole
      name: 'backend-team-*'     # 限定特定名稱模式

  # ── 邊界 4：拒絕建立的 namespace-scoped 資源 ──────────────
  # 預設允許所有 namespace-scoped 資源（blacklist 模式）
  namespaceResourceBlacklist:
    - group: ''
      kind: ResourceQuota          # 不允許 team 建立自己的 ResourceQuota
    - group: ''
      kind: LimitRange
    - group: 'networking.k8s.io'
      kind: NetworkPolicy

  # ── 邊界 5：強制 GnuPG 簽名驗證（見 Ch.10）────────────────
  signatureKeys:
    - keyID: ABCDEF123456789

  # ── 邊界 6：Sync Windows（部署時間窗口，見 Ch.06）─────────
  syncWindows:
    - kind: deny
      schedule: '0 18 * * 5'      # 週五 18:00
      duration: 63h             # 到週一 09:00
      applications:
        - 'prod-*'
      manualSync: false          # 連手動 sync 也禁止
      timeZone: "Asia/Taipei"

  # ── 邊界 7：Roles & Policies（細粒度權限，下節詳述）──────
  roles:
    - name: developer
      description: "Read + sync own apps"
      policies:
        - p, proj:team-backend:developer, applications, get, team-backend/*, allow
        - p, proj:team-backend:developer, applications, sync, team-backend/*, allow
      groups:
        - backend-developers      # 來自 SSO 的 group claim

  # ── 進階：Orphaned Resources 偵測 ──────────────────────────
  orphanedResources:
    warn: true                  # 發現孤立資源時警告（不刪除）
    ignore:                       # 忽略這些資源不視為孤立
      - group: ''
        kind: Secret
        name: my-shared-secret

1.2 六大邊界控制視覺化

📁
sourceRepos
允許從哪些 Git / Helm repo 拉取 manifest。支援 glob，! 前綴拒絕。
🎯
destinations
允許部署到哪些 cluster + namespace。同樣支援 glob 與拒絕語法。
🌐
clusterResourceWhitelist
允許建立的 cluster-scoped 資源（白名單模式，預設拒絕）。
📦
namespaceResourceBlacklist
禁止建立的 namespace-scoped 資源（黑名單模式，預設允許）。
🔐
signatureKeys
強制 GnuPG 簽名驗證的允許 key 清單。
⏰
syncWindows
部署時間窗口控制（allow / deny + cron schedule）。
⚠️

clusterResourceWhitelist: [] 不等於「拒絕所有」

過去版本中曾有此 bug：設定空的 whitelist clusterResourceWhitelist: [] 並未拒絕所有 cluster-scoped 資源。要明確拒絕，請完全省略 clusterResourceWhitelist 欄位（預設拒絕），或使用 clusterResourceBlacklist 明確列出禁止項目。

1.3 允許 / 拒絕規則語法

語法意義範例
'*'萬用字元，匹配任何字串'*' 允許所有
'prefix-*'前綴匹配'team-a-*' 匹配 team-a-dev、team-a-prod
'!XXX'拒絕規則（必須有對應的允許規則）'!kube-system' 拒絕此 namespace
精確值完全匹配'production' 只匹配 production
YAML — 拒絕規則的應用範例
spec:
  destinations:
    # 允許所有 namespace，但拒絕 kube-system 與 argocd
    - namespace: '*'
      server: '*'
    - namespace: '!kube-system'
      server: '*'
    - namespace: '!argocd'
      server: '*'

## 規則判定邏輯（皆需滿足）：
## 1. 至少有一條 allow 規則匹配
## 2. 沒有任何 deny 規則匹配（! 前綴）
## 注意：!* 是無效的（不能拒絕全部）

1.4 Project Roles 與 JWT Token

Project Roles 為 CI 整合等場景提供細粒度的 token-based 認證。每個 role 有自己的 policy 清單，policy 採用 Casbin 格式（與 argocd-rbac-cm 相同語法）。

YAML + Bash — Project Role 設定與 Token 生成
## ── YAML：在 AppProject 中定義多個 role ────────────────────
spec:
  roles:
    # Role 1：CI deployer（給 GitOps CI pipeline 用）
    - name: deployer
      description: "CI/CD sync access only"
      policies:
        # Policy 格式：p, <subject>, <resource>, <action>, <object>, <effect>
        - p, proj:team-backend:deployer, applications, sync, team-backend/*, allow
        - p, proj:team-backend:deployer, applications, get, team-backend/*, allow
      groups: []         # 不關聯 SSO group（純 token 使用）

    # Role 2：Developer（SSO 使用者）
    - name: developer
      description: "Developers can sync own apps"
      policies:
        - p, proj:team-backend:developer, applications, *, team-backend/*, allow
        # 排除危險操作
        - p, proj:team-backend:developer, applications, delete, team-backend/*, deny
        - p, proj:team-backend:developer, applications, override, team-backend/*, deny
      groups:
        - backend-developers    # SSO group claim
        - platform-admins

    # Role 3：Read-only（稽核 / 監控）
    - name: readonly
      policies:
        - p, proj:team-backend:readonly, applications, get, team-backend/*, allow
        - p, proj:team-backend:readonly, applications, action/*, team-backend/*, deny

## ── Bash：產生 JWT Token 給 CI 使用 ────────────────────────

# 1. 為 deployer role 生成 token（30 天有效期）
$ argocd proj role create-token team-backend deployer --expires-in 720h
# 輸出：eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

# 2. 列出所有 token（id 用於後續撤銷）
$ argocd proj role list-tokens team-backend deployer

# 3. 在 CI 中使用 token
$ argocd app sync my-app --auth-token "$ARGOCD_TOKEN"
$ argocd app get my-app --auth-token "$ARGOCD_TOKEN"

# 4. 撤銷 token
$ argocd proj role delete-token team-backend deployer <token-id>

# 5. 驗證 role 權限
$ argocd proj role can-i team-backend deployer get applications 'team-backend/*'
# 輸出：yes
ℹ️

Token 與 SSO User 的關係

Project Token 適合機器使用（CI/CD 系統）；SSO 群組關聯適合人類使用。Token 可以隨時撤銷，但無法限制使用次數或 IP。建議：CI 用 token，人類用 SSO + group。Project Roles 中設定的 policy 只能授予權限——若要從 system 層級限制（如禁止某 role 操作），需在 argocd-rbac-cm 設定。

2Private Repositories

大部分組織的 Git repo 是私有的，需要設定認證讓 Argo CD 能 clone。Argo CD 支援多種認證方式，存放在 argocd namespace 的 Secret 中。生產環境推薦使用宣告式設定（Secret YAML），便於版本控制與自動化。

SSH Key
  • 使用 deploy key（每個 repo 獨立）
  • repoURL 格式為 git@github.com:org/repo.git
  • 不需 token rotation，但需管理 SSH key
  • Private repo 標準做法
HTTPS Token (PAT)
  • 使用 Personal Access Token / Deploy Token
  • repoURL 格式為 https://github.com/org/repo.git
  • 可細粒度權限（GitHub fine-grained PAT）
  • 需定期 rotation，但設定最簡單
GitHub App（推薦）
  • 更高的 API rate limit（vs PAT）
  • 不綁定個人帳號（不會因離職失效）
  • 細粒度權限（per-repo 授權）
  • token 自動 rotation（私鑰不變）

2.1 SSH Key 認證

YAML — SSH Key Repository Secret
# Step 1：生成 SSH key pair（不加密碼）
## ssh-keygen -t ed25519 -C "argocd@example.com" -f ./argocd-deploy-key -N ""

# Step 2：將公鑰（argocd-deploy-key.pub）加入 Git repo 的 deploy keys
## GitHub: Settings → Deploy keys → Add deploy key

# Step 3：將私鑰建立為 Argo CD Repository Secret
apiVersion: v1
kind: Secret
metadata:
  name: repo-backend-private
  namespace: argocd
  labels:
    # 必須有此 label，Argo CD 才會識別
    argocd.argoproj.io/secret-type: repository
stringData:
  # SSH 格式 URL（注意：使用 git@ 而非 https://）
  url: git@github.com:myorg/backend-private.git
  type: git
  name: backend-private             # UI 顯示名稱
  # SSH 私鑰（多行字串，注意縮排）
  sshPrivateKey: |
    -----BEGIN OPENSSH PRIVATE KEY-----
    b3BlbnNzaC1rZXktdjEAAAAABG5vbmUAAAAEbm9uZQAAAAAAAAABAAAAMwAAAAtzc2gtZW
    ...（私鑰內容）
    -----END OPENSSH PRIVATE KEY-----

## CLI 方式（互動式新增）
## argocd repo add git@github.com:myorg/backend-private.git \
##   --ssh-private-key-path ./argocd-deploy-key

2.2 HTTPS Token 認證

YAML — HTTPS Token Repository Secret
apiVersion: v1
kind: Secret
metadata:
  name: repo-backend-https
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  url: https://github.com/myorg/backend-private.git
  type: git

  # 方式 A：Username + Token（推薦）
  username: argocd-bot     # Git 平台的 user（GitHub: 任意值即可）
  password: ghp_xxxxxxxxxxxxxxxxxxxx  # Personal Access Token

## GitHub Fine-Grained PAT 設定（推薦，比 classic PAT 更安全）：
## 1. Settings → Developer settings → Personal access tokens → Fine-grained
## 2. Repository access：選擇特定 repo（最小權限原則）
## 3. Permissions：Contents = Read-only
## 4. 設定有效期（建議 90 天）並加入 calendar 提醒 rotation

## CLI 方式
## argocd repo add https://github.com/myorg/backend-private.git \
##   --username argocd-bot --password ghp_xxxxxxxxxxxxxxxxxxxx

2.3 GitHub App 認證（生產推薦）

YAML — GitHub App Repository Secret
# Step 1：在 GitHub Organization 建立 GitHub App
## 1. Settings → Developer settings → GitHub Apps → New GitHub App
## 2. 設定 permissions：Contents = Read-only, Metadata = Read-only
## 3. 安裝到 organization 的特定 repo
## 4. 取得：App ID、Installation ID、Private Key (.pem)

apiVersion: v1
kind: Secret
metadata:
  name: repo-backend-github-app
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: repository
stringData:
  url: https://github.com/myorg/backend-private.git
  type: git

  # GitHub App 認證（取代 username/password）
  githubAppID: "123456"             # App ID
  githubAppInstallationID: "789012" # 安裝到 org 的 ID
  githubAppPrivateKey: |
    -----BEGIN RSA PRIVATE KEY-----
    MIIEpAIBAAKCAQEA1234567890...
    ...（GitHub App 的私鑰 .pem 內容）
    -----END RSA PRIVATE KEY-----

  # 若使用 GitHub Enterprise Server
  # githubAppEnterpriseBaseUrl: https://github.example.com/api/v3

2.4 Repository Credential Templates（多 repo 共享認證）

當有大量同一組織的 repo 需要相同認證時，逐個設定 Repository Secret 既煩人又難維護。Repository Credential Templates 讓你以 URL 前綴匹配，所有匹配的 repo 自動使用相同認證：

YAML — Repository Credential Template（萬用 GitHub 認證）
apiVersion: v1
kind: Secret
metadata:
  name: github-myorg-creds
  namespace: argocd
  labels:
    # 注意：是 repo-creds（template）不是 repository
    argocd.argoproj.io/secret-type: repo-creds
stringData:
  # URL 前綴匹配：所有 https://github.com/myorg/* 的 repo 都用此認證
  url: https://github.com/myorg
  type: git

  # 使用 GitHub App（推薦）或 username + token
  githubAppID: "123456"
  githubAppInstallationID: "789012"
  githubAppPrivateKey: |
    -----BEGIN RSA PRIVATE KEY-----
    ...
    -----END RSA PRIVATE KEY-----

## 效果：
## https://github.com/myorg/repo-1 ✅ 自動使用此認證
## https://github.com/myorg/repo-2 ✅ 自動使用此認證
## https://github.com/myorg/.../sub ✅ 自動使用此認證
## https://github.com/otherorg/...   ❌ 不匹配，需要獨立認證

## 不需要為每個 repo 建立 Repository Secret，
## 在 AppProject 的 sourceRepos 中直接寫 URL 即可。
💡

repo-creds vs repository

repo-creds（Credential Template）：URL 前綴匹配，多 repo 共享。repository（Repository Secret）：精確 URL 匹配，單一 repo。可以混用：先用 repo-creds 設定組織級預設，特殊 repo 再用 repository 覆寫。

3Config Management Plugin（CMP）

Argo CD 內建支援 Helm、Kustomize、Jsonnet、Directory 四種 manifest 工具（見 Ch.05）。但組織可能使用其他工具——如 cdk8s（用 TypeScript 寫 K8s manifest）、kapitan（template + secret 管理）、tanka（Grafana 的 Jsonnet wrapper）、ytt（Carvel 工具鏈）等。Config Management Plugin（CMP）讓你以 sidecar 容器的形式為 Argo CD 加入這些工具的支援。

3.1 Sidecar Plugin 架構

CMP 以 sidecar container 部署在 argocd-repo-server Pod 中，透過 Unix socket 與 repo-server 主程序通訊。每個 sidecar 都有獨立的 plugin.yaml 設定檔，定義 discover 規則（何時觸發此 plugin）和 generate 命令（如何生成 manifest）。

YAML — argocd-repo-server Deployment 加入 CMP sidecar
apiVersion: apps/v1
kind: Deployment
metadata:
  name: argocd-repo-server
  namespace: argocd
spec:
  template:
    spec:
      containers:
        # ── 主 container：argocd-repo-server（Argo CD 提供）──────
        - name: argocd-repo-server
          image: quay.io/argoproj/argocd:v3.4.0
          volumeMounts:
            # 共享 socket（與所有 sidecar 通訊）
            - name: var-files
              mountPath: /var/run/argocd
            # CMP server library（plugin discover 程式）
            - name: plugins
              mountPath: /home/argocd/cmp-server/plugins

        # ── Sidecar：cdk8s plugin（範例）─────────────────────────
        - name: cdk8s-plugin
          image: myregistry/cdk8s-cmp:1.0.0
          command: [/var/run/argocd/argocd-cmp-server]
          securityContext:
            runAsNonRoot: true
            runAsUser: 999
          volumeMounts:
            # Plugin 設定檔（plugin.yaml）
            - name: cdk8s-plugin-config
              mountPath: /home/argocd/cmp-server/config/plugin.yaml
              subPath: plugin.yaml
            # 共享 socket（與 repo-server 通訊）
            - name: var-files
              mountPath: /var/run/argocd
            # cmp-server 二進位（從 repo-server 共享）
            - name: plugins
              mountPath: /home/argocd/cmp-server/plugins

      volumes:
        - name: var-files
          emptyDir: {}
        - name: plugins
          emptyDir: {}
        - name: cdk8s-plugin-config
          configMap:
            name: cdk8s-plugin-config

3.2 完整 CMP 實作：cdk8s plugin

以下示範一個完整的 cdk8s plugin。cdk8s 是用 TypeScript / Python 寫 Kubernetes manifest 的工具，透過 cdk8s synth 命令生成 YAML。

YAML — plugin.yaml（CMP 設定）
apiVersion: argoproj.io/v1alpha1
kind: ConfigManagementPlugin
metadata:
  name: cdk8s          # Plugin 名稱（用於 Application spec.source.plugin.name）
spec:
  # 這個 plugin 支援的版本（資訊用）
  version: v1.0

  # Init 命令：在 generate 之前執行（如安裝 dependencies）
  init:
    command: ["sh", "-c"]
    args: ["npm install --silent"]

  # Generate 命令：實際生成 manifest 並輸出到 stdout
  generate:
    command: ["sh", "-c"]
    args:
      - |
        # cdk8s synth 生成 manifest 到 dist/ 目錄
        cdk8s synth --output dist
        # 將所有 .k8s.yaml 檔案合併輸出到 stdout
        cat dist/*.k8s.yaml

  # Discover 規則：repo-server 自動偵測何時使用此 plugin
  discover:
    # 方式 A：fileName glob
    fileName: "cdk8s.yaml"     # 在 source path 中找到此檔案就觸發

    # 方式 B：find 命令（更彈性）
    # find:
    #   command: [sh, -c, "find . -name 'cdk8s.yaml'"]

    # 方式 C：glob pattern（多檔案匹配）
    # glob: "**/cdk8s.yaml"

  # Parameters：UI 中可設定的 plugin 參數
  parameters:
    static:
      - name: target-environment
        title: "Target Environment"
        collectionType: string
        required: false
        itemType: string
YAML — Application 使用 CMP plugin
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-cdk8s-app
  namespace: argocd
spec:
  source:
    repoURL: https://github.com/myorg/cdk8s-app.git
    targetRevision: main
    path: .
    # 方式 A：自動偵測（cdk8s.yaml 存在於 path 中）
    # 不需 plugin 設定區塊

    # 方式 B：明確指定 plugin（強制使用）
    plugin:
      name: cdk8s            # 必須與 plugin.yaml 中的 name 匹配
      env:
        - name: TARGET_ENV
          value: production

3.3 Discover 規則三種方式

Discover 方式用法適用場景
fileNamefileName: "cdk8s.yaml"單一指示性檔案存在即觸發（最常見）
find commandfind: { command: [sh, -c, "find . -name '*.jsonnet'"] }需要更複雜的判斷邏輯（如檔案內容、組合）
glob patternglob: "**/Tanka.libsonnet"遞迴匹配深層目錄結構
ℹ️

Plugin 偵測順序與內建工具的關係

內建工具（Helm、Kustomize、Jsonnet）的偵測優先級高於 CMP plugin（見 Ch.05 1.1 節）。若你的 source path 同時有 Chart.yaml 與 cdk8s.yaml，Argo CD 會優先選擇 Helm。要強制使用 CMP plugin，在 Application spec 中明確指定 plugin.name。

4綜合實戰：完整 Multi-Tenant 配置

整合 Project + Private Repo + CMP，建立一個完整的 multi-tenant 配置：

YAML — 完整 Multi-Tenant 配置（三個 team + 共享 platform）
## ═══════════════════════════════════════════════
## Repository 認證（組織共享）
## ═══════════════════════════════════════════════
apiVersion: v1
kind: Secret
metadata:
  name: github-myorg-creds
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: repo-creds
stringData:
  url: https://github.com/myorg
  type: git
  githubAppID: "123456"
  githubAppInstallationID: "789012"
  githubAppPrivateKey: |
    -----BEGIN RSA PRIVATE KEY-----
    ...
    -----END RSA PRIVATE KEY-----
---
## ═══════════════════════════════════════════════
## Platform Project（管理基礎設施）
## ═══════════════════════════════════════════════
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform
  namespace: argocd
  finalizers: [resources-finalizer.argocd.argoproj.io]
spec:
  description: "Platform team - cluster infrastructure"
  sourceRepos:
    - 'https://github.com/myorg/platform-*'
  destinations:
    - server: '*'
      namespace: '*'      # Platform 可部署到所有 namespace
  # Platform team 可建立任何 cluster-scoped 資源
  clusterResourceWhitelist:
    - group: '*'
      kind: '*'
  roles:
    - name: admin
      policies:
        - p, proj:platform:admin, applications, *, platform/*, allow
      groups: [platform-admins]
---
## ═══════════════════════════════════════════════
## Backend Team Project
## ═══════════════════════════════════════════════
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-backend
  namespace: argocd
  finalizers: [resources-finalizer.argocd.argoproj.io]
spec:
  description: "Backend team applications"
  sourceRepos:
    - 'https://github.com/myorg/backend-*'
    - 'https://github.com/myorg/shared-helm-values'
  destinations:
    - server: https://kubernetes.default.svc
      namespace: backend-*
  # 不允許 cluster-scoped 資源（最小權限）
  clusterResourceWhitelist: []
  # 禁止建立 ResourceQuota（由 platform 統一管理）
  namespaceResourceBlacklist:
    - group: ''
      kind: ResourceQuota
    - group: ''
      kind: LimitRange
  # 強制 GnuPG 簽名
  signatureKeys:
    - keyID: BACKEND_TEAM_GPG_KEY
  syncWindows:
    - kind: deny
      schedule: '0 18 * * 5'
      duration: 63h
      applications: ['prod-*']
      manualSync: false
      timeZone: "Asia/Taipei"
  roles:
    - name: developer
      policies:
        - p, proj:team-backend:developer, applications, get, team-backend/*, allow
        - p, proj:team-backend:developer, applications, sync, team-backend/*, allow
        - p, proj:team-backend:developer, applications, delete, team-backend/*, deny
      groups: [backend-developers]
    - name: ci
      description: "CI pipeline (token-based)"
      policies:
        - p, proj:team-backend:ci, applications, sync, team-backend/*, allow
        - p, proj:team-backend:ci, applications, get, team-backend/*, allow
---
## ═══════════════════════════════════════════════
## Application 範例（屬於 team-backend project）
## ═══════════════════════════════════════════════
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: prod-api-server
  namespace: argocd
spec:
  project: team-backend     # 必須屬於某個 Project
  source:
    # Repo URL 必須符合 sourceRepos 規則
    repoURL: https://github.com/myorg/backend-api.git
    targetRevision: v3.2.1  # Tag 追蹤（GnuPG 已簽署）
    path: deploy/production
  destination:
    # 必須符合 destinations 規則（namespace: backend-*）
    server: https://kubernetes.default.svc
    namespace: backend-prod
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
✅

這個配置實現的安全保證

① Backend team 無法部署到 frontend namespace（destinations 限制）
② 無法建立 cluster-scoped 資源（clusterResourceWhitelist 為空）
③ 無法建立 ResourceQuota / LimitRange（namespaceResourceBlacklist）
④ 無法 sync 未簽署的 commit（signatureKeys）
⑤ 無法在週末部署 prod-* 應用（syncWindows）
⑥ Developers 無法刪除 Application（policy deny）
⑦ 所有 backend-* repo 自動使用 GitHub App 認證（repo-creds 模板）

📌 Key Takeaways

  • 🛡️AppProject 是多租戶安全核心：六大邊界（sourceRepos / destinations / clusterResource* / namespaceResource* / signatureKeys / syncWindows）共同構成完整的隔離保證。生產環境絕不使用 default project。
  • 🚫拒絕規則使用 ! 前綴：'!kube-system' 拒絕該 namespace。判定邏輯需同時滿足：至少一條 allow 匹配 AND 沒有 deny 規則匹配。!* 是無效的。
  • 🎫Project Roles 適合 CI 整合：每個 role 有獨立 token，policy 採用 Casbin 格式。argocd proj role create-token 產生 JWT token，可隨時撤銷。CI 用 token，人類用 SSO + group。
  • 🔑Private Repo 認證選擇：開發環境 PAT 最快；生產環境推薦 GitHub App（更高 rate limit、不綁帳號、自動 token rotation）。SSH Deploy Key 適合需要避開 token 管理的環境。
  • 📋repo-creds（Credential Template）省去重複設定：URL 前綴匹配，所有匹配的 repo 共享認證。設定一次，整個組織的 repo 都能用。配合 Repository Secret 的精確匹配可分層管理。
  • 🔌CMP Plugin 擴充非原生工具：以 sidecar 容器加入 cdk8s、kapitan、tanka 等工具支援。三大要素：discover 規則（何時觸發）、generate 命令（如何生成 manifest）、parameters（UI 可調參數）。內建工具偵測優先於 CMP plugin。
