Secrets 管理
AVP、External Secrets Operator、SealedSecrets

Vol 7 最後一章。「明文 Secret 不能進 Git，但 GitOps 需要一切都在 Git」——這是 Argo CD 從業者最常遇到的矛盾。本章完整剖析三大主流方案：① External Secrets Operator (ESO)——拉模型，現代首選；② argocd-vault-plugin (AVP)——推模型，CMP 整合；③ Sealed Secrets——加密 Git 模型，輕量但有限制。深入分析優缺點、適用場景、生產級設定（AWS Secrets Manager / HashiCorp Vault / Azure Key Vault / GCP Secret Manager）、secret rotation 策略。

📋

前置：已完成 Vol 1-6 與 Ch.32-34。理解 Ch.34（CMP sidecar 架構，AVP 用此部署）。理解 K8s Secret 物件、IRSA（AWS IAM Roles for Service Accounts）、Workload Identity（GCP）、Azure AD Workload Identity。對 HashiCorp Vault / AWS Secrets Manager / Azure Key Vault 有基本認識。

🎯 學習目標

  • 理解 GitOps 與 Secrets 的核心矛盾，以及 Argo CD 官方明確不推薦 AVP 模式的三個理由
  • 掌握三大方案的核心差異：① ESO（拉模型，CRD-based）；② AVP（推模型，CMP 整合）；③ SealedSecrets（Git 加密）
  • 實作 ESO：安裝 controller + 配置 SecretStore / ClusterSecretStore + ExternalSecret CR + IRSA / Workload Identity 認證
  • 連接 4 大 secret stores：AWS Secrets Manager、HashiCorp Vault、Azure Key Vault、GCP Secret Manager
  • 實作 AVP：CMP sidecar 部署（沿用 Ch.34 架構）+ <path:secret/data/db#password> placeholder + auth 認證流程
  • 實作 SealedSecrets：sealed-secrets-controller 安裝 + kubeseal CLI + 加密 Secret → commit Git → controller 解密為 Secret
  • 了解 ESO 進階：refreshInterval 動態 rotation、PushSecret（反向同步）、generators（Password generator / ECRAuthorizationToken）、Template 自訂 Secret 結構
  • 掌握 secret rotation 策略：① 應用程式自動 reload（restartedAt annotation + reloader）；② Deployment annotation hash 觸發重啟；③ 主動 rolling restart
  • 避開五大陷阱：① ESO 過短 refreshInterval 撞 API rate limit；② AVP 把 secret 寫入 Redis cache；③ SealedSecrets controller 換證書遺失既有 sealed；④ 環境變數 vs file mount 的 rotation 行為差異；⑤ K8s Secret 不是加密儲存（etcd encryption 必設）

1GitOps 與 Secrets 的矛盾

1.1 三大方案對比

方案核心理念Secret 儲存位置Argo CD 看到的
1. ESO（拉模型） Git 只放引用，secret 留在外部 store；K8s controller 自動拉 AWS Secrets Manager / Vault / Azure Key Vault / GCP Secret Manager ExternalSecret CR（無敏感資訊）
2. AVP（推模型） Git 放含 placeholder 的 Secret manifest，Argo CD 渲染時注入真值 同上（外部 store） 已注入 secret 的明文 manifest（在 Redis cache）
3. SealedSecrets（加密模型） 用 controller public key 加密 Secret，密文進 Git；controller 用 private key 解密 Git（加密後） SealedSecret CR（密文）

1.2 Argo CD 官方為何不推薦 AVP？

⚠️

Argo CD 官方文件明確警告 AVP 模式

Argo CD 官方 secret-management 文件對 AVP「strongly cautions against」，三大理由：

① 安全：Argo CD 必須有 secret store 的存取權限，增加洩漏風險；② Redis cache：Argo CD 把渲染後的 manifest（含明文 secret）存 Redis cache；③ Rendered Manifests pattern 不相容（Ch.27 Source Hydrator）——hydrated branch 會 commit 明文 secret 到 Git。

這就是為什麼新專案優先選 ESO，AVP 是 Legacy 或特殊情境（如要 secret 進 ConfigMap / Deployment 而非 Secret 物件）才用。

選用決策矩陣

情境推薦方案原因
已有 Vault / AWS Secrets Manager / Azure Key Vault ESO 原生 K8s 模式、refresh interval rotation、PushSecret 反向同步
多 cluster + 中央化 secret store ESO（ClusterSecretStore） 單一 secret store 服務多 cluster，rotation 一處改動
小團隊 / 簡單場景 / 沒外部 secret store SealedSecrets 輕量、僅需 controller，無外部依賴
需要把 secret 注入 ConfigMap / Deployment 環境變數（非 Secret 物件） AVP ESO 只能產生 Secret，AVP 可注入任何資源
已用 Source Hydrator（Ch.27） ESO 或 SealedSecrets AVP 不相容（hydrated branch 會 commit 明文）
需要 secret 自動 rotation ESO refreshInterval 自動同步，AVP 需重新 sync 才更新
合規要求「secret 不能離開 vault」 ESO（with auto rotation） secret 在 K8s 中是短期快取，rotation 立即生效

2External Secrets Operator (ESO)

2.1 架構與 CRD

Mermaid — ESO 架構
┌──────────────┐
│ Git Repo     │
│              │
│ ExternalSec- │    Argo CD sync
│ ret manifest │ ─────────────►  ┌─────────────┐
│ (no secret)  │                 │ K8s API     │
└──────────────┘                 │ - SecretStore│
                                 │ - ExternalS. │
                                 └──────┬──────┘
                                        │ watch
                                        ▼
                                 ┌─────────────────┐
                                 │ ESO Controller  │ ─────► AWS/Vault/Azure
                                 │ (in cluster)    │   fetch secret
                                 │                 │ ◄─────

                                        │ creates
                                        ▼

ESO 的三大核心 CRD：

CRD用途Scope
SecretStore定義 secret store 連線（URL、auth）Namespaced
ClusterSecretStore同 SecretStore 但 cluster-scoped（多 namespace 共用）Cluster
ExternalSecret聲明：從哪個 store 取哪個 secret，目標 K8s Secret 名稱Namespaced
PushSecret（v0.9+）反向：K8s Secret → 外部 store（少用）Namespaced
ClusterExternalSecret單一 ES 定義產生多 namespace 的 SecretCluster

2.3 ExternalSecret 完整範例

YAML — ExternalSecret with Template
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secrets
  namespace: my-app
spec:
  refreshInterval: 1h      # 每小時從 store 同步一次

  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore

  target:
    name: app-secrets            # 產生的 K8s Secret 名稱
    creationPolicy: Owner         # Owner | Orphan | Merge | None
    deletionPolicy: Retain        # Retain | Delete | Merge

    # Template：自訂 Secret 結構（非 1:1 mapping）
    template:
      type: kubernetes.io/dockerconfigjson   # 或 Opaque / tls 等
      metadata:
        labels:
          app: my-app
      data:
        # 用 Go template 組合多個 secret value
        DATABASE_URL: "postgresql://{{ .username }}:{{ .password }}@db.example.com/{{ .dbname }}"
        API_KEY: "{{ .api_key }}"

  # 從外部 store 取得哪些值
  data:
    - secretKey: username     # template 中的變數名
      remoteRef:
        key: prod/database    # AWS Secrets Manager 的 secret name
        property: username     # JSON key（若 secret 是 JSON）
    - secretKey: password
      remoteRef:
        key: prod/database
        property: password
    - secretKey: dbname
      remoteRef:
        key: prod/database
        property: dbname
    - secretKey: api_key
      remoteRef:
        key: prod/api-keys
        property: stripe

  # 或用 dataFrom：取整個 secret 為 JSON
  # dataFrom:
  #   - extract:
  #       key: prod/database     # 整個 JSON 展開為 K8s Secret keys

2.4 與 Argo CD 整合（health check + sync-wave）

YAML — Argo CD + ExternalSecret 整合
# 1) 用 Ch.32 的自訂 health check 讓 Argo CD 知道 ExternalSecret 是否 ready
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
data:
  resource.customizations.health.external-secrets.io_ExternalSecret: |
    hs = { status = "Progressing", message = "Syncing from store..." }
    if obj.status ~= nil and obj.status.conditions ~= nil then
      for i, c in ipairs(obj.status.conditions) do
        if c.type == "Ready" then
          if c.status == "True" then
            hs.status = "Healthy"
            hs.message = "Secret synced"
          elseif c.status == "False" then
            hs.status = "Degraded"
            hs.message = c.message or "Failed to sync"
          end
        end
      end
    end
    return hs

# 2) 用 sync-wave 確保 ExternalSecret 先於 Deployment 部署
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: app-secrets
  annotations:
    argocd.argoproj.io/sync-wave: "-1"     # 早於 wave 0

---
apiVersion: apps/v1
kind: Deployment
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "1"      # 等 ES Healthy 才部署

3ArgoCD Vault Plugin (AVP)

3.1 AVP 如何運作

AVP 是 CMP（Ch.34）的特殊應用——在 manifest 渲染階段把 placeholder 替換為真實 secret 值：

Mermaid — AVP 工作流程
┌──────────────────────────┐
│ Git Repo                 │
│ Secret manifest 含       │
│ <path:db#password>       │
│ placeholder              │
└────────┬─────────────────┘
         │ git fetch
         ▼
┌──────────────────────────┐
│ argocd-repo-server       │
│ + AVP CMP sidecar        │
└────────┬─────────────────┘
         │ generate command
         ▼
┌──────────────────────────┐
│ AVP CLI                  │ ─────► HashiCorp Vault
│ 1. parse placeholder     │   fetch secret
│ 2. fetch from store      │ ◄─────
│ 3. replace in manifest   │
└────────┬─────────────────┘
         │ rendered manifest（含明文）
         ▼
┌──────────────────────────┐
│ Argo CD application-     │
│ controller apply         │
└────────┬─────────────────┘
         │
         ▼
   K8s cluster

⚠️ 注意：渲染後的 manifest 含明文 secret，會被存到 Redis cache

3.2 CMP sidecar 部署

YAML — AVP plugin.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cmp-plugin-avp
  namespace: argocd
data:
  avp.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: argocd-vault-plugin
    spec:
      # 對 kustomize manifest 套用 AVP
      allowConcurrency: true
      lockRepo: false

      generate:
        command: [sh, -c]
        args:
          - |
            # 1) 用 kustomize / helm 先渲染
            kustomize build . | \
            # 2) Pipe 給 argocd-vault-plugin 替換 placeholder
            argocd-vault-plugin generate -

      discover:
        find:
          command:
            - sh
            - -c
            - |
              # 只有 kustomization.yaml 含 avp 標記才 match
              if [ -f "$ARGOCD_APP_SOURCE_PATH/kustomization.yaml" ] && \
                 grep -q "avp.kubernetes.io/path" \
                 "$ARGOCD_APP_SOURCE_PATH"/*.yaml; then
                echo "argocd-vault-plugin"
              fi

## Sidecar 容器（同 Ch.34 模式）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: argocd-repo-server
spec:
  template:
    spec:
      serviceAccountName: avp-bot      # IRSA / Workload Identity
      containers:
        - name: avp
          command: [/var/run/argocd/argocd-cmp-server]
          image: quay.io/argoproj-labs/argocd-vault-plugin:v1.18.1
          env:
            - name: AVP_TYPE
              value: "vault"             # vault / awssecretsmanager / gcpsecretmanager / azurekeyvault
            - name: VAULT_ADDR
              value: "https://vault.example.com:8200"
            - name: AVP_AUTH_TYPE
              value: "k8s"               # k8s 認證方法
            - name: AVP_K8S_ROLE
              value: "argocd"
          volumeMounts:
            - mountPath: /var/run/argocd
              name: var-files
            - mountPath: /home/argocd/cmp-server/plugins
              name: plugins
            - mountPath: /home/argocd/cmp-server/config/plugin.yaml
              subPath: avp.yaml
              name: cmp-plugin-avp
            - mountPath: /tmp
              name: cmp-tmp

3.3 Placeholder 語法

YAML — AVP placeholder 使用範例
# Secret manifest in Git（注意：placeholder 不是真值）
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: my-app
  annotations:
    # 1) 必設：標記此 manifest 需要 AVP 處理
    avp.kubernetes.io/path: "secret/data/prod/database"
type: Opaque
stringData:
  # 2) Placeholder 語法：<key>
  # 從 secret/data/prod/database 取 username
  username: "<username>"
  password: "<password>"

  # 3) 跨 path 引用：<path:>
  api_key: "<path:secret/data/prod/api-keys#stripe>"

  # 4) 含版本：<path:#>
  # AWS Secrets Manager：取特定 version
  prev_key: "<path:prod/api-keys#stripe#AWSPREVIOUS>"

---
# AVP 也可以注入非 Secret 物件（這是 ESO 做不到的）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  annotations:
    avp.kubernetes.io/path: "secret/data/prod/database"
spec:
  template:
    spec:
      containers:
        - name: app
          env:
            # 直接注入到環境變數（非透過 Secret）
            - name: DB_PASSWORD
              value: "<password>"
            - name: DB_HOST
              value: "<path:secret/data/prod/database#host>"
⚠️

AVP 的 manifest 進 Redis cache（含明文 secret）

Argo CD 把渲染後的 manifest 存 Redis 加速 reconcile——AVP 渲染後 manifest 含明文 secret，所以 Redis cache 也含明文。降低風險：① 啟用 Redis password（默認沒有）；② 啟用 Redis TLS（cluster 內也加密）；③ 用 redis-secret-init 自動產生強密碼；④ etcd encryption at rest（K8s Secret 本身也需加密）。這些都做了還是有風險——這就是 Argo CD 官方不推薦 AVP 的原因。

4.2 kubeseal 工作流程

Bash — SealedSecrets 完整工作流程
## Step 1：安裝 sealed-secrets controller
$ helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
$ helm install sealed-secrets sealed-secrets/sealed-secrets \
    -n kube-system

## Step 2：安裝 kubeseal CLI（本機）
$ KUBESEAL_VERSION=0.27.1
$ wget https://github.com/bitnami-labs/sealed-secrets/releases/download/v$KUBESEAL_VERSION/kubeseal-$KUBESEAL_VERSION-linux-amd64.tar.gz
$ tar -xvzf kubeseal-$KUBESEAL_VERSION-linux-amd64.tar.gz kubeseal
$ sudo install -m 755 kubeseal /usr/local/bin/kubeseal

## Step 3：建立明文 Secret manifest（不要 commit！）
$ cat > secret.yaml << EOF
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: my-app
type: Opaque
stringData:
  username: admin
  password: SuperSecret123!
EOF

## Step 4：用 kubeseal 加密
$ kubeseal --controller-name=sealed-secrets \
    --controller-namespace=kube-system \
    --format yaml \
    < secret.yaml > sealed-secret.yaml

## Step 5：刪除明文檔案，commit 加密版到 Git
$ rm secret.yaml
$ git add sealed-secret.yaml && git commit -m "feat: add db credentials"
$ git push

## Step 6：Argo CD sync 後，controller 自動解密為 K8s Secret
$ kubectl get secrets -n my-app
# db-credentials   Opaque   2  5s   ← 由 controller 建立
YAML — SealedSecret 範例（密文）
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-credentials
  namespace: my-app
spec:
  encryptedData:
    # 加密後的內容（每個 value 都用 controller public key 加密）
    username: AgB7y8w...大段 base64...x9Ka==
    password: AgCxYz12...大段 base64...mPq3==
  template:
    metadata:
      name: db-credentials
      namespace: my-app
    type: Opaque
⚠️

SealedSecrets 兩大陷阱

① controller private key 遺失 = 所有 sealed secret 變廢紙：sealed-secrets controller 的 private key 必須定期 backup（建議到外部 secret store）。如果 cluster 重建沒 restore key，所有 SealedSecret 都解不開，必須重新加密所有 secret。

② Scope 嚴格：SealedSecret 加密時綁定 name + namespace（預設）。把 SealedSecret 改名或搬 namespace 會解密失敗。workaround：① 用 --scope namespace-wide 解除 name 綁定；② 用 --scope cluster-wide 完全無 scope（安全性降低）。

6Secret Rotation 策略

取得 secret 只是第一步——更難的是 rotation（如何讓應用程式接收新的 secret 而不需手動重啟）。三種策略：

6.1 應用程式自動 reload（最理想）

YAML — 用 file mount 讓 secret 自動更新
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
        - name: app
          image: my-app:v1
          # ❌ env 注入：secret 變更後不會自動更新（必須重啟 Pod）
          # env:
          #   - name: DB_PASSWORD
          #     valueFrom:
          #       secretKeyRef:
          #         name: db-credentials
          #         key: password

          # ✅ 用 file mount：kubelet 會自動更新檔案內容
          volumeMounts:
            - name: db-creds
              mountPath: /etc/secrets
              readOnly: true
      volumes:
        - name: db-creds
          secret:
            secretName: db-credentials

# 應用程式讀取 /etc/secrets/password 並支援 hot reload
# （或定期重讀檔案）
⚠️

env vs file mount 的關鍵差異

① env (envFrom / valueFrom)：Pod 啟動時注入，之後 Secret 變更不會反映到 env，必須 rolling restart Pod；② file mount (volume)：kubelet 每分鐘檢查一次（kubeletConfiguration.syncFrequency 預設 1m），自動更新檔案內容。支援動態 reload 的應用必用 file mount。

6.2 Deployment annotation hash（自動 rolling restart）

YAML — Kustomize secretGenerator + hash 觸發重啟
# kustomization.yaml
configMapGenerator:
  - name: app-config
    files: [config.yaml]
  # Kustomize 自動加 hash suffix（如 app-config-abc123）
  # Secret/ConfigMap 變更 → hash 變 → Deployment 環境變數變 → 自動重啟

# 或對既有 Secret 手動加 hash annotation
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    metadata:
      annotations:
        # 手動更新此 hash 觸發 rolling restart
        checksum/config: "{{ sha256sum (printf "%v" .Values.config) }}"

6.3 Reloader（自動偵測 + restart）

YAML — Stakater Reloader 整合
# 安裝 Stakater Reloader（watch Secret 變更觸發 rolling restart）
## $ helm repo add stakater https://stakater.github.io/stakater-charts
## $ helm install reloader stakater/reloader -n kube-system

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  annotations:
    # 監視特定 Secret 變更觸發 rolling restart
    secret.reloader.stakater.com/reload: "db-credentials,api-keys"
    # 監視特定 ConfigMap
    # configmap.reloader.stakater.com/reload: "app-config"

    # 或 auto-reload 所有 Reference 的 Secret / ConfigMap
    # reloader.stakater.com/auto: "true"
💡

選擇 rotation 策略的決策樹

① 應用支援動態 reload + 用 file mount → 自動更新（最理想，零中斷）；② 應用用 env 變數 → 用 Reloader 自動 rolling restart；③ 應用需要明確的 restart trigger → Kustomize secretGenerator + hash；④ Critical 應用需要謹慎 rotation → 手動 kubectl rollout restart（搭配 Argo Rollouts 進階 canary）。

📌 Key Takeaways

  • 🔐GitOps + Secret 三大方案：① ESO（拉模型）Git 只放引用，controller 從外部 store 拉；② AVP（推模型）Git 含 placeholder，Argo CD 渲染時注入；③ SealedSecrets（加密模型）Git 放加密密文。Argo CD 官方明確不推薦 AVP（Redis cache 含明文、與 Source Hydrator 不相容、增加 Argo CD 的 secret 存取權限）。
  • ⭐ESO 是新專案首選：原生 K8s CRD（SecretStore / ClusterSecretStore / ExternalSecret）、refreshInterval auto rotation、與 IRSA / Workload Identity 完美整合、不需 CMP sidecar、與 Source Hydrator 100% 相容。2026 年 GitOps secret 管理的事實標準。
  • 🛠️ESO 連接 4 大 secret stores：AWS Secrets Manager（IRSA via serviceAccountRef）、HashiCorp Vault（K8s auth method）、Azure Key Vault（Workload Identity）、GCP Secret Manager（Workload Identity）。都用 ServiceAccount-based auth避免 static credentials。
  • 🎯ExternalSecret 三大用法：① data array明確 mapping（remoteRef.property 取 JSON key）；② dataFrom整個 secret 展開為 K8s Secret 多 key；③ target.template自訂結構（可組合多 secret 為單一字串，如 DATABASE_URL）。用 sync-wave: -1 確保 ES 早於 Deployment 部署。
  • 📌AVP 仍有特殊用途：注入 secret 到非 Secret 物件（ConfigMap / Deployment env / Ingress annotation）——這是 ESO 做不到的。但 Redis cache 含明文+不相容 Source Hydrator 是嚴重缺點，必須啟用 Redis password / TLS / etcd encryption 降低風險。
  • 🔒SealedSecrets 是輕量替代：非對稱加密、密文進 Git、controller 解密。適合無外部 store 的場景。兩大陷阱：① controller private key 必 backup（遺失等於所有 secret 廢紙）；② scope 預設綁 name+namespace（改名/搬 namespace 解密失敗，用 --scope 控制）。
  • 🔄Secret rotation 三策略：① file mount + hot reload（最理想，kubelet 每分鐘自動更新檔案，應用支援 reload）；② Reloader（自動 watch Secret 變更觸發 rolling restart，適合 env-based 應用）；③ Kustomize secretGenerator + hash（hash 變→Deployment annotation 變→自動 rolling restart）。env-mounted Secret 不會自動更新。
  • 🧪三方案差異 11 維度：是否需外部 store、Secret 是否在 Git、auto rotation、注入非 Secret 物件、多 cluster 共享、Redis cache 含明文、Source Hydrator 相容性、學習曲線、運維複雜度等。選擇取決於組織現況——已有 Vault → ESO；無外部 store → SealedSecrets；特殊注入需求 → AVP。
  • ⚠️K8s Secret 本身不是加密儲存：etcd 中 Secret 只是 base64 編碼。必設 etcd encryption at rest（用 KMS key），否則任何 secret 方案都白費。這是 baseline，三大方案的安全性都建立在此基礎之上。
  • ✅10 項生產 Checklist：etcd encryption、ESO 主方案、ClusterSecretStore + IRSA、secret store audit log、自動 rotation、file-mount + hot reload、Reloader for env-based、SealedSecrets 必 backup key、Argo CD 自訂 health check、季度 chaos test rotation。
