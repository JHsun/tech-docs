Source Hydrator
(v2.13+) 渲染後推回 Git

Vol 5 最後一章。Source Hydrator 是 Argo CD 自 v2.13 推出的原生 rendered manifests 模式——將 Helm / Kustomize 的渲染結果自動 commit 推回 Git 分支，作為實際 sync 來源。這解決了「Git history 中只看到 values.yaml 改了一行，但不知道實際對 K8s 產生了什麼影響」的痛點。本章涵蓋 dry / hydrated / sync 三層概念、commit server 元件啟用、repository-push secret 設定、與 hydrateTo 進階用法。

📋

前置：已完整理解 Vol 5 前四章（ApplicationSet 全套）。理解 Helm / Kustomize 的渲染流程（Ch.05）。對 GitOps 「rendered manifests pattern」有基本概念。本章內容為 Beta feature，生產環境前請評估風險。

🎯 學習目標

  • 理解傳統 GitOps 中只儲存 dry source 的三大痛點：① diff 不直觀；② 升級回滾困難；③ 審計困難
  • 掌握 dry source / hydrated source / sync source 三層概念與它們的 Git branch 對應關係
  • 啟用 Source Hydrator：在 argocd-cmd-params-cm 設 hydrator.enabled: "true" + 部署 commit server 元件
  • 設定 repository-push Secret 提供推送權限（與 repository 拉取 Secret 分離，原則最小權限）
  • 建立第一個 spec.sourceHydrator Application：drySource + syncSource 雙來源
  • 用 hydrateTo 引入 staging branch：先推 staging，人工 review 後 merge 到 production branch
  • 實作 Helm 與 Kustomize 的 sourceHydrator 範例
  • 了解 Git trailer 機制：commit 中包含上游 dry commit 的 author / sha / message，實現完整追溯
  • 避開 v2.x 與 v3.x 已知問題（hydrateTo 高頻 trigger、Git notes 競爭、tracking-id 缺失）

1為什麼需要 Source Hydrator

1.1 傳統 GitOps 中只儲存 dry source 的痛點

傳統 Argo CD 工作流程中，Git 中儲存的是 dry source（Helm chart + values.yaml、Kustomize base + overlays）。Argo CD 在 reconcile 時即時渲染為 K8s manifests，然後 sync。這個模式有三大痛點：

痛點具體情境影響
1. Diff 不直觀 PR 中只看到 values.yaml 的 image.tag: v1.2 → v1.3，看不到實際多少 Deployment / ConfigMap / Service 被影響 Reviewer 難以判斷風險，可能漏看引發連鎖反應的變更
2. Chart 升級風險 更新 chart: nginx-1.0 → 2.0 一行，背後可能改了 50 個 K8s 物件，但 PR 中看不出 誤升級造成 outage 但 Git history 看起來只是一行小改動
3. 審計與回滾困難 需要回到「2 週前的實際 K8s 狀態」，但 chart 已升級，當時 values + chart 渲染出的 manifest 不易重建 Incident response 慢、SOC 2 / FedRAMP 等合規審計困難

1.2 rendered manifests pattern 的演進

社群早就發展出「rendered manifests pattern」解決上述痛點：用 CI（如 GitHub Actions）在 PR merge 後自動執行 helm template / kustomize build，把渲染結果 commit 到另一個 branch，Argo CD 從該 branch sync。每次變更的「全部 K8s 影響」都顯式 commit 到 Git。

但這種 DIY 方案有問題：

  • ① 每個團隊各自實作 CI，難維護；
  • ② CI 環境的 Helm / Kustomize 版本可能與 Argo CD 不同，渲染結果有差異；
  • ③ 推送權限管理複雜，常見 CI 用過寬的 GitHub PAT；
  • ④ 沒有官方追溯機制連結 dry commit 與 hydrated commit。

Source Hydrator 把這個模式變成 Argo CD 的原生功能——argocd-controller 直接渲染，commit-server 元件推回 Git，使用同一份 Helm / Kustomize 二進位（與 sync 時一致）。

💡

Source Hydrator 的核心價值

① PR review 看到實際 K8s 影響：reviewer 在 hydrated branch 的 PR 中看到完整 manifest diff；② 歷史可重現：任何時間點的 hydrated branch HEAD 就是當時的實際 K8s 狀態；③ chart 升級風險視覺化：升級 chart 一行，hydrated diff 卻是 1000 行——立刻意識到風險；④ 審計合規：所有變更都在 Git 中有完整記錄，含 author / time / dry source 追溯。

2Dry vs Hydrated vs Sync 三層概念

Source Hydrator 引入三個獨立的 Git 來源，初看複雜，但理解後非常清晰：

層級內容誰寫入角色
1. Dry Source 原始 Helm chart + values.yaml / Kustomize base + overlays 開發者 commit 真實意圖（intent）
2. Hydrated Source 渲染後的純 K8s YAML（Deployment / Service / ConfigMap 完整展開） Argo CD commit-server 自動寫入 實際的 K8s 影響（rendered）
3. Sync Source Argo CD application-controller 實際從哪裡 sync —（指向 hydrated branch） 實際部署來源

2.1 Dry Source 範例（開發者寫的）

YAML — dry source: environments/prod/values.yaml
# dry source（在 main branch 的 environments/prod/values.yaml）
# 開發者只需編輯這個小檔案
replicaCount: 5
image:
  tag: v1.2.3
resources:
  limits:
    memory: "1Gi"
    cpu: "500m"

2.2 Hydrated Source 範例（Argo CD 寫的）

YAML — hydrated source: environments/prod/manifest.yaml
# hydrated source（在 environments/prod branch 的 manifest.yaml）
# 由 Argo CD 自動產生並 commit
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  labels:
    app.kubernetes.io/name: my-app
    app.kubernetes.io/version: v1.2.3
spec:
  replicas: 5          # 來自 values.yaml 的 replicaCount
  selector:
    matchLabels:
      app.kubernetes.io/name: my-app
  template:
    metadata:
      labels:
        app.kubernetes.io/name: my-app
    spec:
      containers:
        - name: my-app
          image: my-app:v1.2.3     # Tag 從 values.yaml 注入
          resources:
            limits:
              memory: "1Gi"
              cpu: "500m"
          ports:
            - containerPort: 8080

---
apiVersion: v1
kind: Service
# ... 完整的 Service 定義（從 Helm chart 模板渲染出來）

關鍵價值：開發者 PR 修改 values.yaml 的一行 replicaCount: 3 → 5，CI 後 hydrated branch 的 PR 顯示 Deployment 的 replicas: 3 → 5——意圖與影響都在 Git 中。

2.3 Sync Source 是 hydrated branch

Argo CD application-controller 不再從 dry source（main branch）sync，而是從 hydrated source（如 environments/prod branch）sync。這意味著：

  • ① Sync 速度更快：不需要每次 reconcile 都跑 helm template；
  • ② Sync 結果可預測：hydrated YAML 就是要 apply 的內容；
  • ③ Manifest cache 利用率高：hydrated branch HEAD 不變則 cache 命中。

3啟用與部署

3.1 啟用 hydrator.enabled 與 commit server 元件

YAML — 啟用 Source Hydrator
## ── Step 1：啟用 hydrator.enabled flag ───────────────────
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cmd-params-cm
  namespace: argocd
data:
  hydrator.enabled: "true"

## 重啟 controller 與 server 套用變更
## $ kubectl rollout restart deploy argocd-server -n argocd
## $ kubectl rollout restart statefulset argocd-application-controller -n argocd

## ── Step 2：部署 commit server 元件 ─────────────────────
## 方法 A：使用官方 install-with-hydrator.yaml（一次到位）
## $ kubectl apply -n argocd \
##     -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install-with-hydrator.yaml

## 方法 B：Helm chart 中啟用 commitServer
## values.yaml
commitServer:
  enabled: true
  replicas: 1          # 單副本（避免並行 commit 衝突）
  resources:
    requests: {cpu: "100m", memory: "128Mi"}
    limits: {cpu: "500m", memory: "512Mi"}

## 驗證部署
## $ kubectl get pods -n argocd | grep commit-server
## argocd-commit-server-xxxxxxxxx-yyyyy   1/1     Running
⚠️

commit-server 必須單副本

Source Hydrator 的 commit-server 元件無法水平擴展——多副本會造成同時 push 到 Git 的競爭條件（race condition），出現 Git notes conflict 等錯誤（issue #25727）。生產環境保持 replicas: 1 + K8s Deployment 自動重啟即可。流量極大時 commit-server 可能是瓶頸，這是已知限制。

3.2 設定 repository-push Secret

傳統 Argo CD 的 repository Secret 只有讀取權限（pull）。Source Hydrator 需要推送權限（push），用獨立的 repository-push Secret 管理——遵循最小權限原則：

YAML — repository-push Secret 設定
apiVersion: v1
kind: Secret
metadata:
  name: argocd-example-apps-push
  namespace: argocd
  labels:
    # 注意是 repository-push 不是 repository！
    argocd.argoproj.io/secret-type: repository-push
type: Opaque
stringData:
  url: https://github.com/argoproj/argocd-example-apps.git
  # 方法 1：HTTPS + PAT
  username: argocd-bot
  password: ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxx
  # 方法 2：SSH
  # sshPrivateKey: |
  #   -----BEGIN OPENSSH PRIVATE KEY-----
  #   ...
  #   -----END OPENSSH PRIVATE KEY-----

## ── 安全建議 ────────────────────────────────────────────
## 1. 為 Argo CD bot 建立專屬 GitHub user (argocd-bot)
## 2. 該 user 只有 hydrated branch 的 push 權限
## 3. 用 GitHub branch protection rules 防止人類直接 push hydrated branch
## 4. PAT 設定 90 天過期 + 自動輪替（External Secrets Operator）
## 5. SSH key 用 deploy key + write 權限
ℹ️

repository-push 與 repository 是分離的

同一個 repo 可能同時存在 repository（pull 用，連接到原始 source）與 repository-push（push 用，給 hydrator 推 hydrated branch）。不要在同一個 Secret 同時設兩種 secret-type；分開設定是設計原則，提供細粒度權限控制。

4第一個 sourceHydrator Application

建立 Application 時用 spec.sourceHydrator 取代 spec.source / spec.sources：

YAML — Application with sourceHydrator
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app-prod
  namespace: argocd
spec:
  project: default

  # sourceHydrator 與 source / sources 互斥（v3.x 報錯）
  sourceHydrator:
    # Dry source：原始 chart / kustomize
    drySource:
      repoURL: https://github.com/myorg/gitops.git
      targetRevision: main            # 開發者 commit 到 main
      path: environments/prod          # 含 Chart.yaml + values.yaml

    # Sync source：實際 sync 來源 = hydrated branch
    syncSource:
      targetBranch: environments/prod  # hydrator 寫入此 branch
      path: .                          # branch 內的 path（通常 .）

  destination:
    server: https://kubernetes.default.svc
    namespace: my-app

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

運作流程

1
開發者修改 main branch 的 environments/prod/values.yaml（如 image.tag: v1.3）並 commit
2
application-controller 偵測到 dry source（main）有變化，觸發 hydration
3
repo-server 渲染 Helm / Kustomize，產生 manifest.yaml
4
commit-server 將 manifest.yaml commit 到 environments/prod branch，並 push 到 Git（用 repository-push Secret）
5
application-controller 偵測到 syncSource（environments/prod branch）有新 commit
6
automated sync 觸發，從 hydrated branch apply 純 K8s manifests 到 cluster
💡

Hydrator 不需要 CI！

這個流程完全不需要 GitHub Actions / GitLab CI——argocd-controller 即時偵測 dry source 變化並驅動整個流程。CI 仍然可以做其他事（測試、image build、policy check），但「渲染 + push」由 Argo CD 原生處理。

5hydrateTo：staging branch 機制

進階用法：用 hydrateTo 引入中間 staging branch，hydrator 不直接寫入 syncSource branch，而是寫到 staging。人類 PR review 確認 hydrated diff 後 merge 到 syncSource branch，application-controller 才 sync——多一層人工把關：

YAML — hydrateTo 進階用法
spec:
  sourceHydrator:
    drySource:
      repoURL: https://github.com/myorg/gitops.git
      targetRevision: main
      path: environments/prod

    # hydrator 先寫到 staging branch
    hydrateTo:
      targetBranch: environments/prod-staging

    # 但 syncSource 還是讀 production branch
    syncSource:
      targetBranch: environments/prod
      path: .

hydrateTo 工作流程

1
Dev 修改 main 的 values.yaml → commit
2
hydrator 渲染並寫入 prod-staging branch（自動 commit）
3
CI / GitHub Action 自動開啟 PR：prod-staging → prod，PR description 含 hydrated diff
4
Reviewer 在 PR 中審視實際 K8s 影響（Deployment 改了什麼、Service 新增了什麼）
5
通過 → merge PR → prod branch 更新
6
argocd-controller 偵測 syncSource 變化 → automated sync 觸發
💡

hydrateTo 是 production change-management 的關鍵

金融 / 醫療 / 政府等嚴格 change-management 場景必備：① 機器渲染（hydrator 自動）；② 人工把關（PR review）；③ 完整 audit trail（hydrated diff 留在 PR history）；④ branch protection rule 確保只能 PR merge 不能直接 push。同時保留 GitOps 自動化與企業審計需求。

⚠️

v2.14 已知 bug：hydrateTo 高頻 trigger（#22506）

v2.14.x 中設定 hydrateTo 可能造成 hydrator 每 5 秒重新觸發一次（看似永無止盡）。workaround：① 升級到 v3.x（已修復）；② 暫時不用 hydrateTo，直接寫到 syncSource。生產環境採用前先測試此功能在你的版本是否穩定。

6完整使用案例

6.1 Helm 範例（典型 multi-env Chart）

YAML — Helm Application + sourceHydrator
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webapp-prod
  namespace: argocd
spec:
  project: default
  sourceHydrator:
    drySource:
      repoURL: https://github.com/myorg/webapp-config.git
      targetRevision: main
      path: charts/webapp           # 含 Chart.yaml + values-prod.yaml
    syncSource:
      targetBranch: environments/prod
      path: .

  destination:
    server: https://kubernetes.default.svc
    namespace: webapp

  syncPolicy:
    automated: {prune: true, selfHeal: true}

Repo 結構（同一個 repo，多個 branch）：

Tree — webapp-config repo 結構
## main branch（dry source）
charts/
  webapp/
    Chart.yaml
    values-prod.yaml
    templates/
      deployment.yaml
      service.yaml
      ingress.yaml
      configmap.yaml

## environments/prod branch（hydrated source，自動產生）
manifest.yaml          # 全部 K8s 物件渲染後的純 YAML
README.md              # hydrator 自動產生（含 dry source 來源資訊）

7Git Trailer 追溯來源

Source Hydrator 在 commit hydrated branch 時，會在 commit message 加入 Git trailers（類似 RFC 2822 標準）標明這次 hydration 對應的 dry commit：

Bash — hydrated commit 範例（含 trailer）
$ git log environments/prod -1
commit 8f3a5b2c... (HEAD -> environments/prod)
Author: argocd-bot <argocd@example.com>
Date:   Thu May 9 14:32:18 2026 +0000

    Hydrate manifests for prod environment

    Argocd-reference-commit-author: Alice <alice@example.com>
    Argocd-reference-commit-sha: a1b2c3d4e5f6...
    Argocd-reference-commit-subject: bump nginx to v1.27
    Argocd-reference-commit-repourl: https://github.com/myorg/gitops.git
    Argocd-reference-commit-date: 2026-05-09T14:31:45+00:00

## 從 hydrated commit 反查 dry commit 的指令
$ git log environments/prod -1 --format='%(trailers:key=Argocd-reference-commit-sha,valueonly=true)'
## a1b2c3d4e5f6...

## 直接 checkout 對應的 dry commit
$ DRY_SHA=$(git log environments/prod -1 \
    --format='%(trailers:key=Argocd-reference-commit-sha,valueonly=true)')
$ git checkout main $DRY_SHA

實務應用：

  • ① UI 顯示：Argo CD UI 從 trailer 解析 dry commit info，在 Application 卡片顯示「實際是哪個 dev 改了什麼」（非 argocd-bot 的渲染 commit）；
  • ② Incident 追溯：發現某次 sync 造成 outage，從 hydrated commit 一步到位看到 dry commit author + message + URL；
  • ③ SOC 2 審計：「為什麼 production 在 2026-05-09 14:32 做了這個變更？」答：因為 Alice 在 14:31 推了這個 dry commit。

8已知問題與最佳實踐

v2.x / v3.x 已知 Issues

Issue影響版本症狀解法
#25727 Git notes conflict v3.3.0-rc2+ 多個 Application 同時 hydrate 時，push refs/notes/hydrator.metadata 衝突失敗 降低並行度；commit-server replicas=1；等修復
#22506 hydrateTo 高頻 trigger v2.14.8 設 hydrateTo 後每 5 秒觸發 hydration，UI 不斷出錯 升級到 v3.x；或不用 hydrateTo
#24371 tracking-id 缺失 v2.14+ hydrated manifest 沒有 argocd.argoproj.io/tracking-id annotation，影響觀測性 在 hydrator 後做 post-process（CI 工具補 annotation）

運維最佳實踐

✅

Source Hydrator 上線 Checklist

① commit-server 用單副本（避免 race condition）；② repository-push Secret 用 dedicated bot account（不要用個人 PAT）；③ GitHub branch protection 啟用：argocd 用戶 push hydrated branch；人類 PR 才能改 main；④ 關鍵 prod 啟用 hydrateTo：人工 review hydrated diff；⑤ PAT 自動輪替（External Secrets Operator + 90 天輪替）；⑥ 監控 commit-server（log + restart count）；⑦ 初期僅在 staging 測試，確認 Helm / Kustomize 版本相容性後再推到 prod；⑧ 關注 Argo CD release notes，Source Hydrator 仍是 Beta，每版本有變動。

遷移建議：從傳統 source 遷移到 sourceHydrator

Bash — 遷移流程
## Step 1：在 dev 環境啟用 hydrator，建立第一個 sourceHydrator Application
## 跑 1-2 週確認穩定性、效能、團隊習慣

## Step 2：手動驗證 hydrated branch 內容正確
$ git checkout environments/dev
$ helm template ../charts/webapp -f ../charts/webapp/values-dev.yaml \
    > expected.yaml
$ diff manifest.yaml expected.yaml      # 應該為空（或只差 hydrator 加的 metadata）

## Step 3：對既有 Application 漸進改造
## 不要一次性把所有 prod Application 改成 sourceHydrator
## 每週改 5-10 個，觀察效能與 commit-server 負載

## Step 4：監控指標
$ kubectl logs -n argocd deploy/argocd-commit-server --tail=100 | \
    grep -i "error\|fail"
# 看是否有 push 失敗、Git conflict 等

## Step 5：建立 runbook
## - 當 hydrator 失敗時如何手動 push hydrated branch（emergency）
## - 當 commit-server crash 時如何重啟
## - 當 hydrated branch 不一致時如何強制重建（force re-hydrate）

📌 Key Takeaways

  • 🚿Source Hydrator 是原生的 rendered manifests pattern（v2.13+）：Argo CD 自動把 Helm / Kustomize 渲染後 commit 推回 Git 分支，作為 sync 來源。解決三大痛點：① diff 顯示真實 K8s 影響；② chart 升級風險視覺化；③ 完整審計與回滾。
  • 📚三層概念分離：① Dry source（開發者寫的 chart + values）；② Hydrated source（Argo CD 寫的渲染結果）；③ Sync source（指向 hydrated branch）。意圖與影響都在 Git 中，dry commit 一行小改 → hydrated PR 顯示 1000 行 K8s diff。
  • 🔧啟用三件事：① argocd-cmd-params-cm 設 hydrator.enabled: "true"；② 部署 commit-server 元件（單副本）；③ 設定 repository-push Secret（與 repository pull 分開，最小權限）。重啟 controller + server 套用變更。
  • ⚙️commit-server 必須單副本：多副本造成 push race condition + Git notes conflict（#25727）。生產環境保持 replicas=1 + K8s 自動重啟即可。流量極大時 commit-server 是已知瓶頸。
  • 📝spec.sourceHydrator 取代 source/sources：三者互斥。drySource + syncSource 兩個必填區塊。流程：dev push main → hydrator 偵測 → 渲染 → commit-server push 到 syncSource branch → application-controller sync。完全不需要外部 CI。
  • ✋hydrateTo 進入 staging 機制（金融/合規場景必備）：hydrator 寫到 prod-staging branch，CI 自動開 PR 到 prod，人工 review hydrated diff 後 merge，argocd-controller 才 sync。同時保留 GitOps 自動化 + 企業審計需求。注意 v2.14 已知 bug（#22506）。
  • 🔗Git trailer 提供完整追溯：hydrated commit 含 Argocd-reference-commit-{author,sha,subject,repourl,date}。從 hydrated commit 一步到位看到 dry commit info。UI 顯示 dev 真名而非 argocd-bot；incident 追溯與 SOC 2 審計輕鬆完成。
  • ⚠️仍是 Beta，謹慎上線：v2.14 / v3.x 有多個已知 issues（hydrateTo 高頻、Git notes conflict、tracking-id 缺失）。建議：① 先在 dev 環境跑 1-2 週；② 漸進改造既有 Application（每週 5-10 個）；③ 監控 commit-server log；④ 建立 emergency runbook；⑤ 關注 release notes（每版本有變動）。
