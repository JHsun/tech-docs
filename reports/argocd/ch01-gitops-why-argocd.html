GitOps 是什麼？
為什麼選 Argo CD

在深入 Argo CD 的技術細節之前，我們先建立最重要的觀念基礎： GitOps 要解決的是什麼問題？它的核心哲學為何？ 以及在眾多 GitOps 工具中，Argo CD 憑什麼成為業界首選？

1傳統部署的痛點

在 GitOps 出現以前，Kubernetes 應用程式的部署方式幾乎清一色是 Push-based：由 CI/CD pipeline（Jenkins、GitLab CI、GitHub Actions 等） 在 pipeline 執行階段直接呼叫 kubectl apply 或 helm upgrade， 將 manifest 推送至叢集。 這個模式在小規模環境運作尚稱順暢，但隨著叢集數量增加、團隊規模擴大， 問題便接踵而至。

1.1 Push-based 的根本問題

Push-based 架構有一個結構性的安全盲點：CI/CD 系統必須持有 Kubernetes 叢集的存取憑證。這意味著：

⚠️ Push-based 的問題
CI server 需持有 kubeconfig 或 service account token，且往往是 cluster-admin 等級
憑證暴露在多個系統（Jenkins、GitHub Secrets、環境變數）中，攻擊面廣
Pipeline 失敗時，叢集狀態可能介於「舊版」與「新版」之間，難以回溯
若有人直接 kubectl apply 了某個 hotfix，Git 與叢集立即產生 drift
無法從 Git 歷史完整重建某時刻的叢集狀態
多叢集時，每個叢集都需要一套憑證管理，維護成本倍增
✅ GitOps Pull-based 解法
叢集內的 agent 主動從 Git 拉取，CI server 不需要任何叢集憑證
憑證集中在叢集內部管理，外部系統無法直接存取叢集
Agent 持續確保叢集狀態與 Git 一致，失敗自動重試
任何 drift 都會被偵測並告警，可選擇自動修復
Git commit 歷史即部署歷史，任意時刻狀態均可重現
Rollback = git revert，操作直覺且可稽核

1.2 Configuration Drift：靜默的系統殺手

Configuration Drift 是指叢集的實際狀態（actual state） 與預期狀態（desired state）之間出現無聲無息的偏離。 它通常源自以下場景：

  • 🔧 SRE 在凌晨三點為了緊急修復而直接 kubectl edit，事後忘記同步回 Git
  • 📦 有人手動調整了 replicas 數量，過幾天 pipeline 重新部署時被覆蓋
  • 🔒 ConfigMap 或 Secret 被直接修改，沒有任何人知道
  • 🏷️ Node label、Namespace annotation 在多次手動操作後與文件不符
⚠️

Drift 的危險性

Drift 本身不會立即造成問題，但它讓系統進入一種「你以為你了解它，其實你不了解它」的狀態。當事故發生時，工程師面對的是一個與文件不符的環境，除錯時間成本倍增，且往往無法重現問題。

GitOps 透過持續調和（continuous reconciliation）機制， 讓 agent 每隔一段時間（或接收到事件時）比對 Git 與叢集狀態， 一旦偵測到 drift，即可告警甚至自動修復， 從根本上消滅 drift 存在的空間。

2GitOps 的誕生與核心原則

2.1 誰發明了 GitOps？

GitOps 一詞由 Weaveworks 創辦人 Alexis Richardson 於 2017 年首次提出。 Weaveworks 在構建自家 Weave Cloud 平台時，發展出一套以 Git 為中心的基礎設施管理方法， 效果卓越，因此在 2019 年正式對外分享這套方法論，「GitOps」這個詞就此誕生。

隨著 GitOps 概念迅速普及，社群意識到需要有一套中立、標準化的定義， 因此在 Amazon、Azure、GitHub、Red Hat、Codefresh、Weaveworks 等公司的共同推動下， 成立了 OpenGitOps 工作組（CNCF Sandbox 計畫）， 並於 2021 年發布 GitOps Principles v1.0， 成為目前業界公認的標準定義。

📖

OpenGitOps 官方定義

「GitOps 是一套操作和管理軟體系統的原則。當使用 GitOps 時，系統或子系統的 Desired State 被宣告式地定義為版本控制的不可變資料，且運行中系統的配置持續地從這份資料衍生出來。」

2.2 GitOps 四大原則

OpenGitOps 定義了四個核心原則，任何符合 GitOps 的系統都必須滿足這四條：

原則 1 / PRINCIPLE 1

宣告式（Declarative）

系統的 Desired State 必須以宣告式方式表達。描述「要達到什麼」而非「如何一步步做到」。Kubernetes YAML manifest 是最典型的宣告式配置。

Declarative
原則 2 / PRINCIPLE 2

版本控制與不可變（Versioned & Immutable）

Desired State 必須儲存在版本控制系統中（通常是 Git），且歷史記錄不可竄改。每次變更都有完整的稽核軌跡：誰、何時、改了什麼、為何而改。

Versioned & Immutable
原則 3 / PRINCIPLE 3

自動拉取（Pulled Automatically）

Software agent 自動從 Git 拉取（pull）Desired State 並套用，而非由外部系統推送（push）。這讓叢集不需要對外部 CI server 開放存取權限，大幅縮減攻擊面。

Pulled Automatically
原則 4 / PRINCIPLE 4

持續調和（Continuously Reconciled）

Software agent 持續觀察實際系統狀態，並嘗試讓它符合 Desired State。若發現 drift（偏差），agent 會自動嘗試修復，確保系統自我修復（self-healing）。

Continuously Reconciled
💡

記憶口訣

四個原則可以記成 D·V·P·C：Declarative（宣告式）→ Versioned（版本化）→ Pulled（自動拉取）→ Continuously reconciled（持續調和）。後續讀到 Argo CD 的各種功能時，都可以回頭對照這四條原則，理解它解決的是哪個層次的問題。

3.1 全面比較

比較維度 Push-based（傳統） Pull-based（GitOps）
憑證存放 CI server / CI secret store 持有叢集憑證 憑證僅存在叢集內部，外部系統無需存取

Rollback 方式 重新觸發舊版 pipeline，操作複雜 git revert / git checkout，立即生效
稽核軌跡 分散在 CI 日誌與 kubectl history，難以整合 Git commit 歷史即完整稽核記錄
多叢集管理 每個叢集需個別配置 pipeline 與憑證 單一 Argo CD 實例可管理數百個叢集
離線能力 CI server 無法連線時，部署中止 Agent 在叢集內，網路隔離環境下仍可運作
Desired State 可見性 需查閱 CI pipeline 定義才能了解部署內容 Git repo 即全部真相，任何人隨時可查閱
ℹ️

Pull-based 不代表放棄 CI

GitOps 重新定義的是 CD（Continuous Delivery） 的部分。CI（測試、建置映像、產生 manifest）仍由 GitHub Actions 等工具負責，只是 CI 的最後一步不再是 kubectl apply，而是將新的 manifest 或映像 tag 提交回 Git repo，再由 Argo CD 偵測並完成部署。

4.3 CNCF 定位與 Argo CD vs Flux 選型

Argo CD 與 Flux 都是 CNCF Graduated 等級的 GitOps 工具，兩者在目標上高度重疊， 但設計哲學有根本差異：

面向Argo CDFlux CD
核心模型 集中式（Centralized）：單一 Argo CD 實例管理多叢集 分散式（Decentralized）：每個叢集安裝自己的 Flux controller
UI 內建完整 Web UI，視覺化 Application 拓撲 無內建 UI，需使用 Weave GitOps 等外部工具
多叢集管理 從單一 Argo CD 控制多個叢集，視覺化清晰 每叢集獨立管理，需搭配 Fleet 等工具
學習曲線 較平緩，UI 直觀，概念清晰 較陡，需理解多個 CRD（Kustomization / HelmRelease…）
RBAC 精細度 v3.0 起支援 resource-level Fine-Grained RBAC 依賴 Kubernetes RBAC，無 UI 層 RBAC
適用場景 需要集中管理、可視性高、多團隊、複雜 RBAC 偏好分散控制、GitOps 純粹主義、無 UI 偏好
ℹ️

沒有絕對的最佳選擇

Argo CD 與 Flux 均是優秀工具。本手冊選擇 Argo CD 是因為其 UI、集中式管理模型、豐富的生態工具（Rollouts、Image Updater 等）使其在大多數企業場景中擁有更平緩的學習曲線，且 2025 年 CNCF 調查顯示它是 Kubernetes 叢集中最廣泛採用的 GitOps 解決方案。

5Argo CD v3.x 的架構演進

若你曾使用過 Argo CD v2.x，以下是 v3.x 系列最需要注意的架構層面改變。 即使是第一次接觸 Argo CD 的讀者，理解這些設計決策背後的動機， 也有助於日後理解各項配置選項的意義。

5.1 主要 Breaking Changes（v2.x → v3.0）

變更項目v2.x 行為v3.0 新行為影響評估
RBAC Fine-Grained applications, update, * 自動涵蓋子資源 子資源需獨立授權（update/*） ⚠️ 高影響，需審查所有 RBAC policy
Logs RBAC 持有 applications, get 即可查看 logs 需明確授予 logs, get 權限 中影響，更新 role 定義即可
resource.exclusions 需手動配置排除高 churn 資源 預設排除 Endpoints、Lease、TokenReview 等高 churn 資源 正面影響，效能提升
Dex 認證主體 使用 sub claim 作為 RBAC 主體 改用 federated_claims.user_id 若使用 Dex SSO，需更新 RBAC policy
💡

v2.x 遷移保留選項

若需要暫時保留 v2.x 的 RBAC 行為，可在 argocd-cm 中設定 server.rbac.disableApplicationFineGrainedRBACInheritance: "false"。但這只是遷移過渡期的暫時措施，最終仍需按 v3.x 新模型重新設計 policy。完整升級指南見 Vol 3 Ch.19。

📌 Key Takeaways

  • 🔴 傳統 Push-based 的核心問題：CI server 持有叢集憑證（安全風險）、Configuration Drift 無人知曉（穩定性風險）、跨叢集管理成本高（可擴展性問題）。
  • 📖 GitOps 四大原則（D·V·P·C）：Declarative（宣告式）、Versioned & Immutable（版本控制不可變）、Pulled Automatically（自動拉取）、Continuously Reconciled（持續調和）。這四條是判斷任何工具是否符合 GitOps 精神的標準。
  • 🔒 Pull-based 的安全優勢：外部系統（CI server）完全不需要持有叢集憑證，攻擊面大幅縮減。Argo CD agent 在叢集內部以 Kubernetes API 完成所有操作。
  • 📊 Argo CD 業界地位：CNCF Graduated（2022）、近 60% Kubernetes 叢集採用（2025 CNCF 調查）、NPS 79，是目前最廣泛使用的 GitOps 工具。
  • 🔑 v3.0 最重要的 Breaking Change：RBAC 從粗粒度改為 Fine-Grained，子資源操作需獨立授權。所有從 v2.x 升級的環境都必須審查並更新 RBAC policy。
