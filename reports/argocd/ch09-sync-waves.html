PreDelete Hook 與
Sync Waves 深度實踐

Sync Waves 讓你在 GitOps 宣告式框架內，精確控制數百個資源的部署順序，並透過 Health Gate 確保每個 wave 完全就緒後才推進下一個。本章深入 wave 的三層排序規則、Health Gate 機制、prune 的逆向 wave，以及複雜 DB 部署和 Blue/Green 切換的完整實戰場景。

📋

前置：已閱讀 Ch.08（Resource Hooks 基礎）。了解 Kubernetes Deployment / StatefulSet / Job 的 Health 判斷邏輯。

🎯 學習目標

  • 理解 Sync Wave 的三層排序規則（Phase → Wave → Kind），以及各層的優先順序
  • 掌握 Health Gate 機制：Argo CD 如何判斷一個 wave「完成」，才推進下一個
  • 了解 ARGOCD_SYNC_WAVE_DELAY 的作用與調整時機
  • 理解 Prune 操作的逆向 wave 排序（從高到低刪除）
  • 設計完整的 Wave 命名慣例，並為常見資源類型分配適當 wave
  • 撰寫複雜 DB 部署場景（7 個 wave）的完整 YAML
  • 實作 Blue/Green 部署的 wave 切換序列

1Sync Wave 核心機制

Sync Wave 透過 argocd.argoproj.io/sync-wave annotation 指定一個整數值（可為負數）。Argo CD 按照從最小值到最大值的順序，分批 apply 資源，每批之間等待前一批全部達到 Healthy 狀態。

1.1 三層排序規則

Argo CD 在排列資源的 apply 順序時，依照以下三層優先順序（最高優先在前）：

優先順序排序依據說明
第一層（最高） Phase（Hook 類型） PreSync（所有資源之前）→ Sync（主資源）→ PostSync（所有資源之後）。PreSync hook 永遠在 Sync 資源之前，不論 wave 數值。
第二層 Wave 數值（由小到大） 同一 Phase 內，wave -5 在 wave 0 之前，wave 0 在 wave 5 之前。預設值為 0。
第三層（最低） Kind（資源類型） 同一 wave 內，Namespace 最先，其次 Service，然後 Deployment 等。這是 Argo CD 的硬編碼排序，確保基礎設施資源先建立。
YAML — Wave Annotation 基本語法
metadata:
  annotations:
    # 值必須是字串（非數字）！
    # 錯誤：argocd.argoproj.io/sync-wave: 1
    # 正確：
    argocd.argoproj.io/sync-wave: "-5"   # 最早執行的 wave
    argocd.argoproj.io/sync-wave: "0"    # 預設（與不加 annotation 相同）
    argocd.argoproj.io/sync-wave: "10"   # 較晚執行的 wave

    # Wave 可與 Hook 結合使用，控制同 Phase 內的順序
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/sync-wave: "-1"  # 在其他 PreSync hook 之前

1.2 Wave 間的 Health Gate

Health Gate 是 Sync Wave 能夠實現「先等資料庫健康，再部署 API」的關鍵機制。Argo CD 在推進到下一個 wave 之前，會等待當前 wave 中的所有資源都達到 Healthy 狀態：

📊 Wave 推進流程（含 Health Gate）
Wave -2
Namespace: production
ServiceAccount: app-sa
⏳ Health Gate：等待 Namespace 建立完成（Healthy）
Wave -1
ConfigMap: app-config
Secret: db-credentials
⏳ Health Gate：等待 ConfigMap / Secret 套用完成（Healthy）
Wave 0
StatefulSet: postgres
Service: postgres
⏳ Health Gate：等待 postgres StatefulSet Healthy（所有 Pod 就緒 + readinessProbe 通過）
Wave 1
Job: db-migrate（Sync hook, wave 1）
⏳ Health Gate：等待 migration Job 完成（Completed）
Wave 2
Deployment: api-server
Service: api-service
⏳ Health Gate：等待 api-server Deployment Healthy（所有 replica 就緒）
Wave 3
HorizontalPodAutoscaler
Ingress: api-ingress
⚠️

Health Gate 失敗會停止整個 sync

若某 wave 中的任何資源在 sync timeout 前無法達到 Healthy 狀態，整個 sync 失敗，後續 wave 不會執行。這確保了「資料庫未就緒時，不部署 API」，但也意味著單個資源 Healthy 問題會阻擋所有後續資源。務必為每個資源設計正確的 readinessProbe / livenessProbe。

1.3 Wave 間延遲（ARGOCD_SYNC_WAVE_DELAY）

每個 wave 之間，Argo CD 預設等待 2 秒再推進，讓其他 controller 有時間對剛 apply 的資源作出反應，避免 health check 讀到過時的 resource version：

YAML — 調整 Wave 間延遲（argocd-application-controller）
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: argocd-application-controller
  namespace: argocd
spec:
  template:
    spec:
      containers:
        - name: argocd-application-controller
          env:
            # 預設 2 秒，可依環境調整
            # 大型叢集或 controller 反應慢的環境可調高（5-10s）
            # 追求快速的 CI/CD 環境可調低（0-1s），但有 race condition 風險
            - name: ARGOCD_SYNC_WAVE_DELAY
              value: "2"  # 單位：秒

2Wave 與 Hook 的協作

2.1 同 Phase 內 Wave 的排序

Hook 和一般資源都可以指定 wave，在同一 Phase 內按 wave 順序執行。Phase 的優先順序永遠高於 wave：即使 PreSync hook 的 wave 是 999，它也一定在 Sync Phase 的 wave -999 之前執行。

YAML — 同 Phase 內 Hook 的 Wave 排序
## 場景：多個 PreSync hook 需要有序執行
## 1. 先備份資料庫（wave -2）
## 2. 再執行 migration（wave -1）
## 3. 最後驗證 schema（wave 0）

--- # Step 1: 備份
apiVersion: batch/v1
kind: Job
metadata:
  name: db-backup
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/sync-wave: "-2"   # 最先執行
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: backup
          image: postgres:15
          command: ["pg_dump", "-h", "postgres", "-U", "admin", "mydb", "-f", "/backup/pre-deploy.sql"]

--- # Step 2: Migration
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/sync-wave: "-1"   # 備份成功後執行
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myorg/api:latest
          command: ["python", "manage.py", "migrate"]

--- # Step 3: 驗證
apiVersion: batch/v1
kind: Job
metadata:
  name: schema-validate
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/sync-wave: "0"    # migration 成功後驗證
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: validate
          image: myorg/api:latest
          command: ["python", "manage.py", "check", "--database", "default"]

2.2 Prune 的逆向 Wave

當 Argo CD 執行 prune（刪除在 Git 中移除的資源）時，順序是逆向的——從最高 wave 開始刪除，逐步到最低 wave。這確保「先刪除依賴者，再刪除被依賴者」：

操作類型Wave 處理順序原因
Apply（部署）Wave -N → … → 0 → … → Wave +N（由小到大）先建立依賴，再建立依賴者
Prune（刪除）Wave +N → … → 0 → … → Wave -N（由大到小）先刪除依賴者，再刪除依賴（逆向）
ℹ️

Prune 逆向 Wave 的實際意義

例如：Ingress（wave 3）依賴 Service（wave 2），Service 依賴 Deployment（wave 0）。刪除時，Argo CD 先刪 Ingress（wave 3），再刪 Service（wave 2），最後刪 Deployment（wave 0）——永遠不會出現「Service 已刪但 Ingress 仍在指向它」的破碎狀態。

3Wave 設計模式與命名慣例

為組織建立統一的 wave 命名慣例，讓所有人一眼就能理解資源的部署順序：

Wave 範圍類別典型資源說明
-10 ~ -6平台基礎設施CRD、ClusterRole、ClusterRoleBinding、StorageClassCluster-scoped 資源，必須在所有 namespace-scoped 資源之前
-5 ~ -3Namespace 與 RBACNamespace、ServiceAccount、Role、RoleBindingNamespace 必須在其中的資源之前建立
-2 ~ -1配置資源ConfigMap、Secret、PersistentVolumeClaimApp 啟動前需要的配置和資料卷
0核心資料層StatefulSet（DB）、Service（DB）資料庫等核心依賴服務，Health Gate 確保就緒
1中間層 / 遷移Job（DB migration）、其他依賴 DB 的初始化任務資料庫就緒後才執行
2應用主體Deployment、Service（API）、Service（Frontend）DB 就緒且 migration 完成後部署
3流量管理Ingress、HorizontalPodAutoscaler、ServiceMonitorApp 健康後才開放流量和監控
4+驗收 / 通知Job（integration test）、ConfigMap（feature flags）完整部署後的驗收工作
💡

Wave 設計原則

① 只在有真實依賴時才分 wave——不需要為每種資源類型都分不同 wave。
② 同一 wave 內的資源並行執行——沒有依賴關係的資源放同一 wave 可加快部署。
③ Wave 數量越少越好——每個 wave 之間至少等待 Health Gate，太多 wave 會顯著拉長部署時間。
④ 使用跳號（-10, -5, -2, 0, 2, 5）——為未來插入新 wave 預留空間，避免大規模重新編號。
⑤ 在 YAML 中加入說明 annotation（如 # Wave 2: 需要 DB 就緒才部署）。

4實戰場景：複雜 DB 部署（含 Migration + Schema 驗證）

以下是一個生產等級的 API + PostgreSQL 部署，涵蓋 7 個 wave，從 Namespace 建立到最終 Ingress 開放流量：

4.1 完整 YAML（7 個 Wave）

YAML — 生產等級 API + DB 部署（7 個 Wave）
## ═══════════════════════════════════════════════
## Wave -5：Namespace 與 RBAC
## ═══════════════════════════════════════════════
apiVersion: v1
kind: Namespace
metadata:
  name: production
  annotations:
    argocd.argoproj.io/sync-wave: "-5"
    team: platform
---
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api-sa
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "-5"
    # IRSA（AWS）或 Workload Identity（GCP）設定
    eks.amazonaws.com/role-arn: arn:aws:iam::123:role/api-role
---
## ═══════════════════════════════════════════════
## Wave -2：ConfigMap / Secret / PVC
## ═══════════════════════════════════════════════
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "-2"
data:
  LOG_LEVEL: "info"
  DB_HOST: "postgres.production.svc.cluster.local"
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "-2"
    # PVC 不應被 prune 刪除（防止資料遺失）
    argocd.argoproj.io/sync-options: Prune=false
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 20Gi
---
## ═══════════════════════════════════════════════
## Wave 0：資料庫 StatefulSet + Service
## Health Gate：等待 postgres Pod readinessProbe 通過
## ═══════════════════════════════════════════════
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "0"
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:15-alpine
          # readinessProbe 是 Health Gate 的關鍵！沒有它，Argo CD 無法判斷 DB 是否就緒
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "admin", "-d", "myapp"]
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 6
---
apiVersion: v1
kind: Service
metadata:
  name: postgres
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "0"
---
## ═══════════════════════════════════════════════
## Wave 1：DB Migration Job（Sync Phase hook + wave）
## 在 Sync Phase（非 PreSync），使用 wave 確保 DB 就緒後執行
## ═══════════════════════════════════════════════
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  namespace: production
  annotations:
    argocd.argoproj.io/hook: Sync
    argocd.argoproj.io/sync-wave: "1"   # postgres（wave 0）就緒後才執行
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  backoffLimit: 3
  activeDeadlineSeconds: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: myorg/api:v3.2.1
          command: ["python", "manage.py", "migrate", "--no-input"]
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: db-credentials
---
## ═══════════════════════════════════════════════
## Wave 2：API Application
## DB 就緒 + Migration 完成後才部署
## ═══════════════════════════════════════════════
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "2"   # migration（wave 1）完成後才部署
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-server
  template:
    metadata:
      labels:
        app: api-server
    spec:
      serviceAccountName: api-sa
      containers:
        - name: api
          image: myorg/api:v3.2.1
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: api-service
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "2"
---
## ═══════════════════════════════════════════════
## Wave 3：流量管理（Ingress + HPA）
## API 健康後才開放流量
## ═══════════════════════════════════════════════
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "3"
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "3"
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 10

5實戰場景：Blue/Green 部署切換（Sync Waves）

使用 Sync Wave 實現 Blue/Green 部署：先部署 Green 版本並測試，確認通過後再切換流量，最後縮減 Blue 版本。注意：此為純 Argo CD 的 wave-based Blue/Green，生產環境建議搭配 Argo Rollouts（Vol 8）實現更完整的 Progressive Delivery。

YAML — Blue/Green 切換（4 個 Wave）
## Wave 0：部署 Green 版本（新版）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-green
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "0"
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
      version: green
  template:
    metadata:
      labels:
        app: myapp
        version: green
    spec:
      containers:
        - name: app
          image: myorg/app:v2.0.0  # 新版本
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
---
## Wave 1：Green 版本的 Service（測試用，不對外）
apiVersion: v1
kind: Service
metadata:
  name: app-green-svc
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "1"
spec:
  selector:
    app: myapp
    version: green
---
## Wave 2：Green 版本測試 Job（Green 就緒後執行）
apiVersion: batch/v1
kind: Job
metadata:
  name: test-green
  namespace: production
  annotations:
    argocd.argoproj.io/hook: Sync
    argocd.argoproj.io/sync-wave: "2"  # Green 就緒後才測試
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: test
          image: curlimages/curl:latest
          command:
            - sh
            - -c
            - |
              curl -f http://app-green-svc:8080/health || exit 1
              curl -f http://app-green-svc:8080/api/v1/status || exit 1
              echo "Green version tests PASSED"
---
## Wave 3：切換主 Service 到 Green，縮減 Blue
apiVersion: v1
kind: Service
metadata:
  name: app-service  # 主 Service（對外流量）
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "3"  # 測試通過後才切流量
spec:
  selector:
    app: myapp
    version: green  # 切換到 Green
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-blue  # 縮減舊版本
  namespace: production
  annotations:
    argocd.argoproj.io/sync-wave: "3"
spec:
  replicas: 0  # 縮為 0（流量已切走）
  selector:
    matchLabels:
      app: myapp
      version: blue

6PreDelete Hook 深度：複雜清理場景

6.1 多步驟 PreDelete（Wave 排序）

PreDelete hook 也支援 wave 排序，實現「先通知，再備份，最後清理 external resources」的多步驟刪除流程：

YAML — 多步驟 PreDelete（3 個 Wave）
## PreDelete Wave -1：先發送下線通知
apiVersion: batch/v1
kind: Job
metadata:
  name: pre-delete-notify
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PreDelete
    argocd.argoproj.io/sync-wave: "-1"  # 最先執行
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: notify
          image: curlimages/curl:latest
          command: ["sh", "-c", "curl -X POST $SLACK_URL -d '{\"text\":\"🗑️ production/my-app 正在刪除中...\"}'"]
---
## PreDelete Wave 0：備份資料庫（通知後才備份）
apiVersion: batch/v1
kind: Job
metadata:
  name: pre-delete-backup
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PreDelete
    argocd.argoproj.io/sync-wave: "0"
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  activeDeadlineSeconds: 600  # 備份最多 10 分鐘
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: backup
          image: postgres:15
          command:
            - sh
            - -c
            - |
              TIMESTAMP=$(date +%Y%m%d-%H%M%S)
              pg_dump -h postgres -U admin myapp | \
                aws s3 cp - "s3://backups/final-${TIMESTAMP}.sql"
              echo "Final backup completed: final-${TIMESTAMP}.sql"
---
## PreDelete Wave 1：清理 External Resources
apiVersion: batch/v1
kind: Job
metadata:
  name: pre-delete-cleanup
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PreDelete
    argocd.argoproj.io/sync-wave: "1"  # 備份成功後才清理
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: cleanup
          image: bitnami/kubectl:latest
          command:
            - sh
            - -c
            - |
              # 刪除 ExternalDNS record
              kubectl delete dnsendpoint my-app-dns -n production --ignore-not-found
              # 刪除 ExternalSecret（避免遺留）
              kubectl delete externalsecret my-app-secret -n production --ignore-not-found
              echo "External resources cleaned up"

6.2 PreDelete 失敗處理

場景結果處理方式
PreDelete hook Job 失敗（backoffLimit 耗盡）Application 停留在「刪除中」狀態，資源不被刪除修復 hook 的問題（更新 Git → 推送 → Argo CD 重建 Job）
強制刪除（跳過 hook）可使用 kubectl delete application MY_APP --cascade=foreground --grace-period=0緊急情況才使用，會跳過 PreDelete hook
Hook 超時（activeDeadlineSeconds）Job 標記失敗 → 刪除流程被阻擋調整 activeDeadlineSeconds 或排查超時原因

8最佳實踐

實踐項目說明
Wave 值使用跳號使用 -10, -5, -2, 0, 2, 5, 10 等跳號，為未來插入新 wave 預留空間，避免大規模重新編號
每個資源加說明 comment在 YAML 中加入 # Wave N: 需要 XXX 就緒 的說明，讓接手者理解 wave 設計意圖
readinessProbe 是必要的Health Gate 依賴 readinessProbe 判斷資源就緒。沒有 readinessProbe 的 Deployment，Argo CD 只能判斷 Pod 是否 Running，無法確認 app 是否真正可用
避免 wave 過多每個 wave 之間至少有 Health Gate 等待時間。5 個 wave 的部署比 1 個 wave 可能慢 2–5 分鐘。只在有真實依賴時才拆分 wave
同 wave 內資源並行無依賴關係的資源放同一 wave，可以並行部署加快速度
設定 activeDeadlineSeconds所有 hook Job 都應設定超時，避免一個掛起的 Job 永遠阻擋後續部署
PreDelete hook 的 idempotent 設計PreDelete hook 可能因 Job 失敗而被多次建立（修復後重試），必須設計為冪等的（如 --ignore-not-found）

📌 Key Takeaways

  • 🌊三層排序規則：Phase（最高）→ Wave 數值 → Kind（最低）。同一 Phase 內的 Hook 和資源都按 wave 排序，Phase 邊界不可逾越。
  • 🚦Health Gate 是關鍵：每個 wave 完全達到 Healthy 後才推進下一個。必須為資料庫等核心依賴服務設計正確的 readinessProbe，否則 Health Gate 無法正確工作。
  • ⏱️ARGOCD_SYNC_WAVE_DELAY 預設 2 秒：讓 controller 有時間反應，避免讀到過時狀態。大型叢集可調高，追求速度的 CI 環境可調低（但有 race condition 風險）。
  • 🔄Prune 是逆向 Wave：刪除時從最高 wave 到最低 wave，確保先刪依賴者（Ingress）再刪被依賴者（Service → Deployment），不出現破碎狀態。
  • 🗑️PreDelete 也支援 Wave：多步驟清理（通知 → 備份 → 清理 external resources）可用 wave 排序，確保每步驟完成後才進行下一步。PreDelete hook 失敗會阻擋 Application 刪除。
  • 📐Wave 設計原則：使用跳號（-5, -2, 0, 2, 5）、加入說明 comment、只在有真實依賴時才拆分 wave、無依賴的資源放同一 wave 並行執行、所有 hook Job 設定 activeDeadlineSeconds。
