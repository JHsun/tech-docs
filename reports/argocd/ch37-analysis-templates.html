AnalysisTemplate 與 Metric Providers
自動化決策的核心

Ch.36 介紹的 Canary 中所有 step 都是手動或 duration-based——但「等 5 分鐘」不能告訴你「真的沒問題」。本章進入 Progressive Delivery 的精華：AnalysisTemplate 自動查詢 Prometheus / Datadog / New Relic / CloudWatch 等 metric 來源，依 successCondition / failureCondition 做出 promote / abort / pause 決策。完整涵蓋 5 大 Metric Provider、Inline / Background / Pre/Post-promotion 三種 analysis 模式、SLO-driven rollouts、AnalysisRun 除錯、production 最佳實踐。

📋

前置：已完成 Ch.36 (Argo Rollouts 基礎)、Ch.28 (Prometheus 觀測)。理解 Prometheus PromQL / Datadog Metric Query Language 基本語法。理解 K8s Job 物件、Secret reference。理解 SLO / Error Budget 概念（Ch.28 涵蓋）。

🎯 學習目標

  • 理解為什麼手動 pause 不足以保證生產安全：「等 5 分鐘」≠「驗證沒問題」，需 metric-based 決策
  • 掌握 Argo Rollouts analysis 三大角色：AnalysisTemplate（範本定義）、ClusterAnalysisTemplate（跨 namespace 共用）、AnalysisRun（範本實例化執行）
  • 撰寫 AnalysisTemplate：metrics 陣列、args 參數、provider 來源、successCondition / failureCondition expression、count / interval / failureLimit
  • 整合 5 大 Metric Provider：Prometheus（最常用）、Datadog、New Relic、CloudWatch、Web/Job（自訂腳本）
  • 區分三種 analysis 模式：① Inline analysis（step 中作為一個 step，阻塞推進）；② Background analysis（rollout 全程運行）；③ Pre/Post-promotion analysis（Blue-Green 切換前後）
  • 實作 SLO-driven rollouts：用「99.9% 成功率」「p95 latency < 500ms」等 SLI 自動判斷是否 promote
  • 用 kubectl argo rollouts get analysisrun、kubectl describe 除錯失敗的 analysis
  • 避開常見陷阱：① empty array 處理（query 沒資料）；② initialDelay 避免新版剛起來 metric 不準；③ failureLimit 過嚴造成 false positive；④ provider secret 在錯誤 namespace；⑤ ClusterAnalysisTemplate 與 AnalysisTemplate 同名衝突

1為什麼需要自動化決策

1.1 手動 pause 的限制

Ch.36 介紹的純 setWeight + pause 模式有明顯限制：

限制後果
等 5 分鐘自動推進5 分鐘沒收到 5xx 不代表沒問題（可能流量太少、metrics 未到）
等待手動 promote需要 on-call 工程師盯著 Grafana 看 metrics，無法自動化
無 abort 邏輯error rate 飆升必須有人手動 abort，3am 出問題沒人理
無客觀標準「看起來沒問題」是主觀的，不同人標準不同
💡

AnalysisTemplate 的核心價值

① 客觀標準：用 metric 數值判斷（success rate ≥ 99.5%），不是主觀感覺；② 24/7 自動化：3am 部署也能自動 promote 或 abort；③ 多指標複合判斷：error rate + latency + saturation 三者同時要 OK；④ SLO-aligned：直接用 SLO 作為 promotion gate，與 reliability 目標對齊；⑤ 歷史可追溯：AnalysisRun 物件保存決策依據，事後可分析。

2AnalysisTemplate 結構

2.1 完整結構

YAML — AnalysisTemplate 完整骨架
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
  namespace: my-app
spec:
  # 1) Args：可從 Rollout 傳入的參數
  args:
    - name: service-name          # 必填參數（無 value）
    - name: prometheus-port
      value: "9090"             # 預設值，可被 Rollout 覆蓋
    - name: api-token
      valueFrom:                    # 從 Secret 取得
        secretKeyRef:
          name: api-credentials
          key: token

  # 2) Metrics：要查詢的指標陣列
  metrics:
    - name: success-rate          # 指標名稱

      # Sampling 設定
      initialDelay: 30s           # 啟動延遲（等新版 ready）
      interval: 1m                # 每分鐘採樣一次
      count: 5                     # 總共採樣 5 次（不設則 indefinite）

      # 條件判斷
      successCondition: "result[0] >= 0.95"     # Expr expression
      # failureCondition: "result[0] < 0.50"             # 兩者擇一或並用

      # 失敗容忍度
      failureLimit: 3             # 允許 3 次失敗（超過視為 Failed）
      inconclusiveLimit: 5        # 允許 5 次 inconclusive（暫停手動）
      consecutiveErrorLimit: 4    # 允許 4 次連續 provider error（如 prom 暫時不可用）

      # Provider（必填，本章節 3 詳述）
      provider:
        prometheus:
          address: "http://prometheus.example.com:{{args.prometheus-port}}"
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",status!~"5.."}[5m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[5m]))

2.2 successCondition vs failureCondition

欄位意義缺一行為
successCondition true 視為 Successful sample 無此欄位則永遠不算 Successful，必須有 failureCondition
failureCondition true 視為 Failed sample 無此欄位則只看 successCondition（非 success 即視為 inconclusive）
兩者並用 明確區分 success / failure / inconclusive 三狀態 推薦做法
ℹ️

Expression 語言（Expr）

successCondition / failureCondition 用 Expr（與 ApplicationSet 同款）。常用語法：

result[0] >= 0.95（陣列第一個 ≥ 95%）；len(result) == 0 || result[0] >= 0.95（empty array 也算成功）；default(result, 0) < 10（無資料時用 0）；asFloat(result) < 100（轉 float 比較）；result =~ "success"（regex match，web provider 用）。

2.3 count / interval / failureLimit 行為

YAML — 三種採樣模式
## 模式 1：單次採樣（不設 interval，預設 count: 1）
metrics:
  - name: smoke-test
    successCondition: "result == 'ok'"
    # 一次性測試，跑完就結束

## 模式 2：固定次數採樣（count + interval）
metrics:
  - name: latency-check
    count: 5            # 採樣 5 次
    interval: 1m       # 每 1 分鐘一次
    failureLimit: 2    # 5 次中允許 2 次失敗
    successCondition: "result[0] < 500"
    # 5 分鐘內持續驗證 latency

## 模式 3：持續採樣（只設 interval，無 count）
metrics:
  - name: error-rate
    interval: 30s      # 每 30 秒一次
    failureLimit: 3    # 連續 3 次失敗才 abort
    successCondition: "result[0] >= 0.99"
    # 無 end time：背景持續監控直到 rollout 完成或 abort
⚠️

failureLimit 設太嚴會造成 false positive

① failureLimit: 0：任何一次失敗就 abort——太敏感，網路抖動就 rollback；② failureLimit: 3：允許 3 次失敗（推薦預設）；③ consecutiveErrorLimit：provider 本身錯誤（如 prometheus 連不上）的容忍次數，不要與 failureLimit 混淆。實務：interval 30s + failureLimit 3 = 至少 90 秒持續錯誤才 abort，平衡敏感度與穩定。

3五大 Metric Providers

3.1 Prometheus（最常用）

YAML — Prometheus AnalysisTemplate
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: success-rate
      initialDelay: 30s
      interval: 2m
      count: 5
      # 處理 empty array（流量太少 query 沒結果）
      successCondition: "len(result) == 0 || result[0] >= 0.95"
      failureLimit: 3
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(irate(
              istio_requests_total{
                reporter="source",
                destination_service=~"{{args.service-name}}",
                response_code!~"5.*"
              }[5m]
            ))
            /
            sum(irate(
              istio_requests_total{
                reporter="source",
                destination_service=~"{{args.service-name}}"
              }[5m]
            ))

          # 進階：自訂 HTTP headers（如認證）
          # headers:
          #   - key: Authorization
          #     value: "Bearer xxx"

          # 進階：自訂 timeout
          # timeout: 30

3.2 Datadog

YAML — Datadog AnalysisTemplate (v2 API)
## 1) Datadog credentials Secret（與 argo-rollouts controller 同 namespace）
apiVersion: v1
kind: Secret
metadata:
  name: datadog           # 名稱固定為 datadog
  namespace: argo-rollouts
stringData:
  address: https://api.datadoghq.com
  api-key: <datadog-api-key>
  app-key: <datadog-app-key>

---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate
spec:
  args:
    - name: service-name
  metrics:
    - name: error-rate
      interval: 30s
      successCondition: "default(result, 0) < 0.01"
      failureLimit: 3
      provider:
        datadog:
          apiVersion: v2            # v1 / v2（v2 支援 formula）
          interval: 5m              # DD 查詢的時間範圍（看過去 5 分鐘）
          # v2 支援多 query + formula
          queries:
            errors: "sum:requests.errors{service:{{args.service-name}}}.as_count()"
            total: "sum:requests{service:{{args.service-name}}}.as_count()"
          formula: "errors / total"

3.3 New Relic / CloudWatch / Wavefront

YAML — New Relic 與 CloudWatch 範例
## ── New Relic ──────────────────────
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: nr-error-rate
spec:
  metrics:
    - name: error-rate
      successCondition: "result.errorRate < 0.01"
      provider:
        newRelic:
          profile: my-newrelic-secret     # 同 namespace 的 Secret
          query: |
            SELECT percentage(count(*), WHERE error IS true) as errorRate
            FROM Transaction WHERE appName = 'my-app' SINCE 5 minutes ago

---
## ── CloudWatch (AWS) ──────────────
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: alb-5xx-rate
spec:
  metrics:
    - name: 5xx-count
      interval: 30s
      successCondition: "result[0] < 10"

          metricDataQueries:

3.4 Web Provider 與 Kubernetes Job

YAML — Web / Job providers（自訂測試）
## ── Web Provider：HTTP request 自訂 endpoint ─────
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: api-smoke-test
spec:
  metrics:
    - name: smoke-test
      # JSON path 解析 response
      successCondition: "result.healthy == true && result.version == 'v2'"
      provider:
        web:
          url: "http://my-app-canary.my-app.svc/health"
          timeoutSeconds: 10
          jsonPath: "{$}"          # 取整個 JSON
          # 認證 headers
          # headers:
          #   - key: Authorization
          #     value: "Bearer xxx"

---
## ── Job Provider：執行自訂 K8s Job ─────────────
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: integration-test
spec:
  metrics:
    - name: integration-test
      # Job exit code 0 = success；非 0 = failure
      # 不需 successCondition（Job 內建邏輯）
      provider:
        job:
          spec:
            backoffLimit: 0
            template:
              spec:
                restartPolicy: Never
                containers:
                  - name: test
                    image: myorg/integration-tests:v1
                    command:
                      - /bin/sh
                      - -c
                      - |
                        # 跑完整 integration test suite
                        pytest tests/ --canary-url http://my-app-canary.my-app.svc
                        # exit 0 = success；exit 1 = failure

4與 Canary 整合：3 種 Analysis 模式

4.1 Inline Analysis（作為 step）

Analysis 作為一個 step，阻塞推進到下一個 step——success 才繼續，failed 則 abort。最直觀的 metric-based gate：

YAML — Inline analysis 完整範例
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  strategy:
    canary:
      steps:
        # Step 1：10% 流量
        - setWeight: 10
        - pause: {duration: 2m}    # 等待 metric 穩定

        # Step 2：跑 analysis（阻塞，必須 success 才繼續）
        - analysis:
            templates:
              - templateName: success-rate
              - templateName: latency-check    # 可以多個 template 同時跑
            args:
              - name: service-name
                value: my-app-canary.my-app.svc
              # 用 valueFrom 動態取得 canary hash（v2.10+）
              - name: canary-hash
                valueFrom:
                  podTemplateHashValue: Latest

        # Step 3：50% 流量（前面 analysis 成功才到這）
        - setWeight: 50
        - pause: {duration: 2m}

        # Step 4：再跑 analysis（50% 流量下的 metric）
        - analysis:
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: my-app-canary.my-app.svc

        # Step 5：100% 流量
        - setWeight: 100

4.2 Background Analysis（rollout 全程運行）

Analysis 在 rollout 開始時觸發，全程在背景監控。一旦 failureCondition 達標立即 abort，不等到下一個 step：

YAML — Background analysis
spec:
  strategy:
    canary:
      # Background analysis（與 steps 平行運行）
      analysis:
        templates:
          - templateName: error-rate-monitor
        startingStep: 2           # 從第 2 個 step 開始監控
        args:
          - name: service-name
            value: my-app-canary.my-app.svc

      steps:
        - setWeight: 10
        - pause: {duration: 5m}    # Background analysis 持續監控
        - setWeight: 30
        - pause: {duration: 5m}
        - setWeight: 100
        # 全程都被 background analysis 監控
        # 任何一秒 error rate 飆升 → 立即 abort

---
## 對應的 AnalysisTemplate（無 count，持續採樣）
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate-monitor
spec:
  args:
    - name: service-name
  metrics:
    - name: error-rate
      # 不設 count → 持續採樣直到 rollout 完成
      interval: 30s
      failureCondition: "result[0] > 0.05"  # error rate > 5% 視為 fail
      failureLimit: 3                       # 連續 3 次（90 秒）才 abort
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_errors_total{service="{{args.service-name}}"}[1m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[1m]))

4.3 Pre/Post-promotion Analysis（Blue-Green）

YAML — Blue-Green 配 pre/post analysis
spec:
  strategy:
    blueGreen:
      activeService: my-app-active
      previewService: my-app-preview
      autoPromotionEnabled: false

      # Pre-promotion：切換 active 服務前驗證
      # 對 preview service 跑測試，通過才 promote
      prePromotionAnalysis:
        templates:
          - templateName: smoke-test
          - templateName: integration-test
        args:
          - name: service-name
            # 對 preview service 跑（live traffic 未切換）
            value: my-app-preview.my-app.svc

      # Post-promotion：active 切到新版後驗證
      # 確認 live traffic 沒問題，否則自動 rollback
      postPromotionAnalysis:
        templates:
          - templateName: error-rate-monitor
        args:
          - name: service-name
            value: my-app-active.my-app.svc

## 流程：
# 1. 新版 ReplicaSet 建立（preview service 指向新版）
# 2. prePromotionAnalysis 觸發（對 preview 跑）
# 3. 全部 success → active service 切到新版（瞬間切換）
# 4. postPromotionAnalysis 觸發（持續監控 live traffic）
# 5. 持續 OK → scaleDownDelaySeconds 後刪除舊版
# 6. failure → 自動切回舊版（active service 改回指向舊版）
💡

三種 analysis 的使用情境

① Inline：明確的「gate」——這個 step 沒通過就不能繼續。適合明確 milestone（10% 後驗證、50% 後驗證）；② Background：「safety net」——全程監控，任何時候失敗立即 abort。適合 critical metric（error rate、availability）；③ Pre/Post-promotion：Blue-Green 專用——切換前 smoke test、切換後 monitoring。三者可組合用：inline 做 milestone gate + background 做 safety net。

5SLO-Driven Rollouts

把 Ch.28 學的 SLI / SLO 直接用於 rollout 決策——「不允許這次 rollout 燒掉 5% 的 monthly error budget」：

YAML — SLO-driven AnalysisTemplate
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: slo-burn-rate
spec:
  args:
    - name: service-name
  metrics:
    # ── Metric 1：Error rate SLI（success rate ≥ 99.5%）─────
    - name: success-rate-slo
      initialDelay: 60s
      interval: 1m
      count: 5
      successCondition: "result[0] >= 0.995"
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            sum(rate(http_requests_total{service="{{args.service-name}}",status!~"5.."}[5m]))
            /
            sum(rate(http_requests_total{service="{{args.service-name}}"}[5m]))

    # ── Metric 2：Latency SLI（p95 < 500ms）─────────────
    - name: latency-slo
      initialDelay: 60s
      interval: 1m
      count: 5
      successCondition: "result[0] < 500"      # < 500ms
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            histogram_quantile(0.95,
              sum(rate(http_request_duration_seconds_bucket{
                service="{{args.service-name}}"
              }[5m])) by (le)
            ) * 1000

    # ── Metric 3：Burn rate（multi-window，SRE Workbook 推薦）──
    # 1 hour burn rate > 14.4 = 在 1 小時內燒掉 2% monthly budget
    # 6 hour burn rate > 6 = 在 6 小時內燒掉 5% monthly budget
    - name: slo-burn-rate-1h
      interval: 5m
      failureCondition: "result[0] > 14.4"
      failureLimit: 1
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            (
              sum(rate(http_requests_total{service="{{args.service-name}}",status=~"5.."}[1h]))
              /
              sum(rate(http_requests_total{service="{{args.service-name}}"}[1h]))
            ) / 0.005    # SLO target: 99.5% (允許 0.5% 錯誤)
💡

SLO-driven 的進階模式

Multi-window, multi-burn-rate alerts（SRE Workbook 推薦）：① 1 小時內 burn rate > 14.4：燒得太快（立即 abort）；② 6 小時內 burn rate > 6：燒得快（abort）；③ 24 小時內 burn rate > 3：警示（pause 等手動）。把 alerting strategy 直接套用到 rollout decision——確保 progressive delivery 不會耗光 monthly error budget。

6除錯 AnalysisRun

Bash — AnalysisRun 除錯命令
## 1. 列出 Rollout 的所有 AnalysisRun
$ kubectl argo rollouts get rollout my-app
# 找到 α icon 標記的 AnalysisRun 名稱

$ kubectl get analysisrun -n my-app
# NAME                               PHASE        AGE
# my-app-6c8c79b696-2-error-rate     Successful   5m
# my-app-6c8c79b696-3-error-rate     Failed       3m

## 2. 查看 AnalysisRun 詳細狀態
$ kubectl describe analysisrun my-app-6c8c79b696-3-error-rate -n my-app
# 重要欄位：
# - Status.Phase: Pending | Running | Successful | Failed | Inconclusive | Error
# - Status.Message: 失敗原因
# - Status.MetricResults[].Measurements: 每次採樣的結果
# - Status.MetricResults[].FailureCount: 失敗次數
# - Events: 完整 timeline

常見錯誤對照

症狀原因解法
Phase: Error（不是 Failed） Provider 本身錯誤（prometheus 連不上、認證失敗） 看 controller log；確認 address / Secret 正確
失敗：value = "[]"（empty array） Query 沒結果（流量太少 / metric 名稱錯） condition 加 len(result) == 0 || 或調整 query
失敗：value 是 null JSON path 不正確（web provider） 用 default(result, 0)
Datadog 401 unauthorized Secret 在錯誤 namespace Secret 名稱必須是 datadog 且在 argo-rollouts namespace
連續 false positive initialDelay 不足，新版剛起來 metric 不準 調 initialDelay 30s → 60s 或更長
Rollout 卡 Inconclusive 達 inconclusiveLimit，需手動處理 argo rollouts promote 或 abort

7最佳實踐

✅

AnalysisTemplate 撰寫 Checklist（10 項）

① 必設 initialDelay（≥ 30s，讓新版 ready + metrics 累積）；② condition 處理 empty array（len(result) == 0 || 或 default(result, 0)）；③ failureLimit ≥ 3（網路抖動容忍）；④ 用 ClusterAnalysisTemplate 跨 namespace 共用（如 generic success-rate）；⑤ args 提供合理 default，要求參數設為無 value；⑥ 結合 inline + background（gate + safety net）；⑦ 用 SLI/SLO 而非 hardcoded 數字；⑧ Web/Job provider 設 timeout避免無限等；⑨ monitor AnalysisRun 數量（多 rollout 同時跑 analysis 可能耗 Prometheus 資源）；⑩ 先在 dev/staging 跑通再上 prod。

✓本章重點回顧

📌 Key Takeaways

  • 🎯AnalysisTemplate 是 Progressive Delivery 的精華：用客觀 metric 取代主觀 pause，自動判斷 promote / abort。三角色：① AnalysisTemplate（範本定義）；② ClusterAnalysisTemplate（跨 namespace 共用）；③ AnalysisRun（每次 rollout 的 runtime 實例）。
  • 📊核心結構：args + metrics + provider + conditions。args 從 Rollout 傳入（支援 Secret valueFrom）；metrics 陣列定義多個指標；provider 選擇 metric 來源；successCondition + failureCondition 用 Expr 語言判斷。採樣設定：count（次數）+ interval（間隔）+ initialDelay（等待）+ failureLimit（容忍）。
  • 🔌5 大 Metric Providers：① Prometheus（最常用，PromQL 查詢）；② Datadog（v2 API 支援 formula）；③ New Relic（NRQL）；④ CloudWatch（AWS metric data queries）；⑤ Web / Job（自訂 HTTP request 或 K8s Job 跑 integration test）。Datadog Secret 必須在 argo-rollouts namespace 名稱固定為 datadog。
  • ⚙️處理 empty array 的兩種模式：① len(result) == 0 || result[0] >= 0.95（empty 視為成功）；② len(result) > 0 && result[0] >= 0.95（empty 視為失敗）；③ default(result, 0) < 10（empty 視為 0）。必須明確處理——預設行為可能不是你想的。
  • 🚦3 種 Analysis 整合模式：① Inline（作為 step，阻塞推進）：明確 milestone gate；② Background（rollout 全程持續監控）：critical metric safety net；③ Pre/Post-promotion（Blue-Green 切換前後）：pre 對 preview service 跑、post 對 active service 監控。實務組合 inline + background。
  • 📈SLO-driven Rollouts：把 Ch.28 學的 SLI 直接用於 rollout 決策。Multi-window, multi-burn-rate（SRE Workbook 推薦）：① 1h burn rate > 14.4 立即 abort；② 6h burn rate > 6 abort；③ 24h burn rate > 3 pause。確保 rollout 不耗光 monthly error budget。
  • 🔬failureLimit vs consecutiveErrorLimit 不同：① failureLimit：condition 為 failure 的累計次數；② consecutiveErrorLimit：provider 本身錯誤（連不上）的容忍次數。預設 4 次 consecutive error 視為 Error phase（不是 Failed）。網路抖動造成的失敗是 consecutive error 不是 failure。
  • 🐛AnalysisRun 5 種 phase：Pending → Running → Successful / Failed / Inconclusive / Error。除錯：① kubectl describe analysisrun 看 Status.MetricResults；② controller log grep -i analysis；③ 手動執行 query 驗證；④ UI Dashboard 視覺化；⑤ initialDelay 太短是最常見 false positive 原因。
  • ⚠️常見陷阱：① empty array 沒處理（流量太少時）；② initialDelay 不足（metrics 還沒累積）；③ failureLimit 太嚴（0 或 1 太敏感）；④ Datadog secret namespace 錯誤；⑤ Prometheus query 在 controller pod 內無法 resolve（service name vs full FQDN）。
  • ✅10 項 Checklist：initialDelay ≥ 30s、condition 處理 empty array、failureLimit ≥ 3、ClusterAnalysisTemplate 共用、args 合理 default、inline + background 組合、用 SLI/SLO、Web/Job 設 timeout、monitor AnalysisRun 數量、先 dev/staging 驗證。AnalysisTemplate 是 production rollout 的最重要 safety net，不要省略此功能。
