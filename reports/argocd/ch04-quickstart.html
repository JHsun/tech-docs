快速上手：
安裝、UI 巡覽與第一個 Application

前三章建立了完整的觀念基礎。本章進入實作：從零開始安裝 Argo CD、巡覽 Web UI 各功能區域、熟悉 argocd CLI，並完成第一個 Application（guestbook）的完整部署與驗證流程。

📋

前置：已閱讀 Ch.01–Ch.03。需要一個可用的 Kubernetes 叢集（minikube / kind / k3s / EKS / GKE / AKS 均可）以及 kubectl 工具。

🎯 學習目標

  • 使用 kubectl apply（server-side apply）成功安裝 Argo CD 並驗證所有 Pod 正常運行
  • 理解 --server-side 旗標的必要性（CRD 大小限制）
  • 設定 Port-forward 在本機存取 Web UI 與 API server
  • 完成初次登入、修改 admin 密碼、刪除初始 admin secret
  • 熟悉 Web UI 的 Applications 儀表板與 Application 詳情頁各功能區域
  • 使用 argocd CLI 完成 login / app create / app sync / app get 等核心操作
  • 以 YAML 宣告式方式建立 guestbook Application 並完成驗證

1前置需求確認

在安裝 Argo CD 之前，先確認環境符合最低需求：

✅ 安裝前確認清單

  • ✓Kubernetes 版本：1.24 或以上（Argo CD v3.x 要求）。執行 kubectl version 確認。
  • ✓kubectl 工具：已安裝且 kubeconfig 指向目標叢集。執行 kubectl cluster-info 確認可連線。
  • ✓叢集權限：安裝者需有 cluster-admin 或等效權限（用於建立 CRD、ClusterRole 等 cluster-scoped 資源）。
  • ✓資源容量：至少 2 vCPU + 4 GB RAM 可用（生產環境建議更高）。執行 kubectl top nodes 確認（需安裝 metrics-server）。
  • ✓外網存取：叢集需能拉取 quay.io/argoproj 的映像（或設定 image pull secret / mirror）。
  • ✓Git 倉庫：需要一個 Argo CD 可存取的 Git repo（本章使用官方公開範例 repo，無需認證）。
ℹ️

本機開發推薦：minikube 或 kind

若沒有現成叢集，推薦使用 minikube start --cpus=4 --memory=8192 或 kind create cluster 快速建立本機叢集。兩者均支援完整的 Argo CD 功能，適合學習與測試。

2安裝 Argo CD

Argo CD 提供兩種主要安裝方式：官方 manifest（適合學習與快速部署）和 Helm chart（適合生產環境客製化）。

2.1 方式一：官方 manifest（kubectl apply）

這是官方文件的入門方法，直接套用上游 manifest。必須使用 --server-side 旗標，因為部分 CRD（如 ApplicationSet）超過 kubectl apply 的 client-side 模式 262 KB annotation 大小限制：

Bash — 安裝 Argo CD（官方 stable manifest）
# Step 1：建立 argocd namespace
$ kubectl create namespace argocd
namespace/argocd created

# Step 2：使用 server-side apply 安裝
# stable = 當前最新穩定版（v3.4.x）
# 生產環境建議固定版本：改用 v3.4.0 取代 stable
$ kubectl apply -n argocd \
  --server-side --force-conflicts \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# --server-side：繞過 client-side 262KB annotation 限制（CRD 必須）
# --force-conflicts：允許覆蓋其他工具（如 Helm）先前管理的欄位

# Step 3：等待所有 Pod 就緒（約 2-3 分鐘）
$ kubectl wait pod \
  --all -n argocd \
  --for=condition=Ready \
  --timeout=300s
pod/argocd-application-controller-0 condition met
pod/argocd-applicationset-controller-xxx condition met
pod/argocd-dex-server-xxx condition met
pod/argocd-notifications-controller-xxx condition met
pod/argocd-redis-xxx condition met
pod/argocd-repo-server-xxx condition met
pod/argocd-server-xxx condition met
⚠️

生產環境：固定版本而非 stable

學習時使用 stable branch 方便，但生產環境應固定到具體版本（如 v3.4.0），避免安裝時版本隨時間漂移。具體 release URL 格式：https://github.com/argoproj/argo-cd/releases/download/v3.4.0/install.yaml

2.2 方式二：Helm chart（生產環境推薦）

Helm chart 方式允許透過 values.yaml 集中管理所有配置，便於 GitOps 管理 Argo CD 本身（Self-managed Argo CD）：

Bash — Helm 安裝
# 加入官方 Helm repo
$ helm repo add argo https://argoproj.github.io/argo-helm
$ helm repo update

# 使用 values.yaml 安裝（客製化配置）
$ helm install argocd argo/argo-cd \
  --create-namespace \
  --namespace argocd \
  --version 7.x.x \  # 固定 chart 版本
  --values argocd-values.yaml

# argocd-values.yaml 最小化範例
YAML — argocd-values.yaml 生產環境最小配置
global:
  image:
    tag: "v3.4.0"  # 固定版本

configs:
  params:
    # 若 Ingress 已終止 TLS，設為 true 避免 redirect loop
    server.insecure: false
  cm:
    timeout.reconciliation: "120s"
    timeout.reconciliation.jitter: "60s"

server:
  replicas: 2  # HA：2+ 副本

repoServer:
  replicas: 2  # HA：多副本分散 manifest 生成負載

applicationSet:
  replicas: 2

redis-ha:
  enabled: true  # 啟用 Redis HA（Sentinel 模式）

3存取 Argo CD

3.1 Port-forward（本機開發最快速）

Port-forward 不需要修改任何 Service 設定，是本機開發最快速的存取方式。開啟一個獨立 terminal 視窗執行，保持前景運行：

Bash — Port-forward 存取
# 開啟 port-forward（保持此 terminal 前景運行）
$ kubectl port-forward svc/argocd-server -n argocd 8080:443
Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080

# 在瀏覽器開啟（自簽憑證需接受警告）
# https://localhost:8080

# 或設定環境變數讓 CLI 自動使用 port-forward
$ export ARGOCD_OPTS='--port-forward-namespace argocd'

3.2 LoadBalancer / Ingress（長期存取）

Bash — 轉換為 LoadBalancer Service
# 將 argocd-server Service 改為 LoadBalancer 類型
$ kubectl patch svc argocd-server -n argocd \
  -p '{"spec": {"type": "LoadBalancer"}}'

# 等待 EXTERNAL-IP 分配
$ kubectl get svc argocd-server -n argocd -w
NAME            TYPE           CLUSTER-IP     EXTERNAL-IP    PORT(S)
argocd-server   LoadBalancer   10.96.87.147   35.123.45.67   80:30080/TCP,443:30443/TCP

# 取得 IP
$ kubectl get svc argocd-server -n argocd \
  -o jsonpath='{.status.loadBalancer.ingress[0].ip}'
35.123.45.67
YAML — Nginx Ingress（含 TLS）
# 先設定 argocd-server 為 insecure 模式（讓 Ingress 終止 TLS）
$ kubectl patch cm argocd-cmd-params-cm -n argocd \
  --type=merge -p '{"data":{"server.insecure":"true"}}'
kubectl rollout restart deployment argocd-server -n argocd
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: argocd-ingress
  namespace: argocd
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
  - hosts: [argocd.example.com]
    secretName: argocd-tls
  rules:
  - host: argocd.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: argocd-server
            port:
              number: 80

3.3 取得初始 admin 密碼並登入

安裝後 Argo CD 自動生成一組隨機的初始 admin 密碼，存放在 argocd-initial-admin-secret Secret 中：

Bash — 取得初始密碼（三種方式）
# 方式 1：使用 argocd CLI（v2.4+ 支援，最簡單）
$ argocd admin initial-password -n argocd
CH5hFPo5q1TcHi9-
This password must be only used for first time login.
We strongly recommend you update the password using
`argocd account update-password`.

# 方式 2：直接讀取 Secret（kubectl）
$ kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d; echo

# 方式 3：PowerShell（Windows）
> kubectl -n argocd get secret argocd-initial-admin-secret `
  -o jsonpath="{.data.password}" | `
  ForEach-Object { [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($_)) }
🔒

安全提醒：登入後立即執行以下兩個動作

1. 修改密碼：argocd account update-password（或在 UI 的 User Info 頁面修改）。2. 刪除初始 secret：kubectl -n argocd delete secret argocd-initial-admin-secret——此 secret 存放明文密碼，刪除後 Argo CD 不會再讀取它，不影響運作。

4Web UI 巡覽

Argo CD 的 Web UI 設計直觀，是日常操作的主要介面。以下逐一介紹各功能區域：

4.1 Applications 儀表板

區域 1
頂部導覽列
左側有 Applications / Settings / User Info 三個主要入口。右上角有通知鈴（Notification Center）、深色模式切換，以及使用者選單（登出 / 修改密碼）。
區域 2
過濾側欄
左側可依 Sync Status（Synced / OutOfSync）、Health Status（Healthy / Degraded 等）、Project、叢集、Namespace 篩選 Application，快速聚焦問題應用。
區域 3
Application 卡片 / 清單視圖
每張卡片顯示 App 名稱、Health 狀態（圖示 + 文字）、Sync Status、目標叢集與 namespace、最後 sync 時間。右上角切換卡片視圖（Cards）或清單視圖（List）。
區域 4
Settings（設定）
包含：Repositories（倉庫設定 / 測試連線）、Clusters（管理外部叢集）、Projects（AppProject CRUD）、Accounts（本地帳號）、GPG Keys（commit 簽名驗證）。
區域 5
+ New App 按鈕
點擊後開啟 Application 建立表單。支援欄位填寫或直接貼入 YAML（右上角 Edit as YAML 切換），是新手第一次建立 Application 的引導介面。
區域 6
全域 Sync / Refresh All
頂部的 Sync Apps 按鈕可批次觸發多個 Application 的 sync。Refresh All 強制重新計算所有 Application 的 diff（不使用快取，類似 --hard-refresh）。

4.2 Application 詳情頁（點擊卡片後）

資源拓撲圖
Resource Tree（中央視覺化）
樹狀圖顯示 Application 下所有資源的階層關係（Deployment → ReplicaSet → Pod）及其 Health 狀態（顏色圖示）。點擊節點可查看資源的詳細資訊、YAML、日誌或 Events。
Summary 頁
概覽資訊
顯示 App 的 source（repoURL / path / targetRevision）、destination（server / namespace）、Sync Status 與最新 commit message。操作按鈕：Sync / Refresh / Delete / Edit。
Parameters 頁
參數 Override
Helm Application 可在此查看並臨時覆寫 values（不提交 Git）。是 Parameter Overrides 功能的 UI 介面，適合緊急調整（如臨時修改 image tag）。
Diff 頁
Git vs 叢集差異
OutOfSync 時顯示 desired state（Git）與 live state（叢集）的完整 diff，語法高亮標示新增/修改/刪除的欄位。是理解「為什麼 OutOfSync」的主要工具。
History 頁
同步歷史記錄
列出所有 Sync Operation 的歷史（成功/失敗、時間、操作者、commit SHA）。點擊任意歷史記錄可觸發 Rollback（手動 sync 模式下）。
Events 頁
Kubernetes Events
彙整 Application 下所有資源的 Kubernetes Events，等同於 kubectl get events -n namespace，是排查 Pod 失敗原因的第一站。

6部署第一個 Application：guestbook

使用 Argo CD 官方範例倉庫（argoproj/argocd-example-apps）的 guestbook 應用程式，完成從建立到驗證的完整流程。guestbook 是一個簡單的 Redis + PHP 留言板，manifest 包含 Deployment 與 Service。

6.1 方式一：使用 CLI 建立

1
建立 Application
Bash — argocd app create
$ argocd app create guestbook \
  --repo https://github.com/argoproj/argocd-example-apps.git \
  --path guestbook \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace default \
  --project default \
  --sync-policy automated \
  --auto-prune \
  --self-heal \
  --sync-option CreateNamespace=true
application 'guestbook' created

重要旗標說明：--repo 指定 Git repo；--path 指定 repo 內的目錄；--dest-server 指定目標叢集（本地叢集固定用 https://kubernetes.default.svc）；--sync-policy automated 啟用自動 sync；--auto-prune 啟用 prune；--self-heal 啟用 selfHeal。

2
觀察 sync 狀態

6.2 方式二：YAML 宣告式建立（推薦）

在 GitOps 精神下，Application 本身也應以 YAML 形式納入版本控制。以下是等效的宣告式 YAML：

YAML — guestbook-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
Bash — 套用 YAML
$ kubectl apply -f guestbook-application.yaml
application.argoproj.io/guestbook created

# 等待 sync 完成
$ argocd app wait guestbook --sync --health --timeout 120
TIMESTAMP                  GROUP        KIND   NAMESPACE                  NAME    STATUS   HEALTH            HOOK  MESSAGE
2026-05-08T10:00:00+08:00   apps  Deployment    default          guestbook-ui  Synced  Healthy
Application 'guestbook' sync was successful

6.3 驗證部署並體驗 drift 修復

最後，透過一個小實驗，親身體驗 selfHeal 的運作方式——手動修改叢集狀態，觀察 Argo CD 自動還原：

Bash — drift 體驗實驗
## 實驗：手動修改 replicas，觀察 Argo CD 自動還原

# Step 1：直接修改叢集中的 Deployment（製造 drift）
$ kubectl scale deployment guestbook-ui -n default --replicas=3
deployment.apps/guestbook-ui scaled

# Step 2：立即查看 sync 狀態（應變為 OutOfSync）
$ argocd app get guestbook --refresh
Sync Status:  OutOfSync from HEAD (6bed858)
             (replicas: 3 != 1)

$ kubectl get deployment guestbook-ui -n default -w

guestbook-ui   3/3     3            3   # drift 狀態

Health Status: Healthy

恭喜！你已完成第一個 GitOps 工作流

你剛才親眼見證了 GitOps 的核心原則：Git 是 single source of truth，任何對叢集的直接修改都會被偵測並自動修復。這就是 selfHeal + 持續調和（Continuously Reconciled）的實際運作。

1
修改 admin 密碼並刪除初始 secret

$ argocd account generate-token \
  --account ci \

3
設定 TLS 憑證（生產環境使用信任的 CA）

自簽憑證在本機開發可接受，但生產環境應配置 cert-manager + Let's Encrypt，或掛載組織 CA 憑證。詳見 Vol 3 Ch.14。

5

為各團隊建立獨立 AppProject，設定 sourceRepos、destinations、clusterResourceWhitelist 邊界，避免越界操作。詳見 Ch.02 Section 5 與 Vol 4 Ch.22。

📌 Key Takeaways

  • 📦安裝必須使用 --server-side：kubectl apply --server-side --force-conflicts 是正確的安裝方式，避開 CRD annotation 大小限制。生產環境應固定版本（如 v3.4.0）而非使用 stable。
  • 🔑初始密碼安全流程：登入後立即修改密碼（argocd account update-password），然後刪除 argocd-initial-admin-secret。該 secret 存放明文密碼，是安全風險。
  • 🖥️Web UI 四個關鍵頁面：Applications 儀表板（全局概覽）、App Summary（基本資訊 + 操作按鈕）、App Diff（排查 OutOfSync 原因）、App History（Rollback 入口）。
  • ⌨️最常用 CLI 指令：argocd app list（概覽）、argocd app get --refresh（強制刷新）、argocd app sync --dry-run（預覽 sync）、argocd app diff（終端查看 diff）。
  • 📄YAML 宣告式優於 CLI 建立：在 GitOps 精神下，Application 本身也應以 YAML 形式納入版本控制，而非依賴 CLI 指令建立。這讓 Argo CD 的設定也符合 GitOps 原則。
  • 🔄selfHeal 實驗：任何直接 kubectl 修改叢集狀態的操作，都會在 5 秒後（selfHeal timeout）被 Argo CD 偵測並自動還原。這是「Git 為 single source of truth」的直接體現。
