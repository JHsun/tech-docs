SSO 整合
與 OIDC 設定（Direct vs Dex）

SSO 是企業使用 Argo CD 的必要前提。本章從 OIDC 認證流程開始，比較 Direct OIDC（推薦）與 Dex（用於非 OIDC IdP）兩種路徑。提供 Okta、Azure AD/Entra ID、Google Workspace、SAML、GitHub OAuth、LDAP 各自的完整設定範例，並深入 groups claim 取得、IdP 端常見陷阱與故障排查。

📋

前置：已閱讀 Ch.14（安全強化）。理解 OAuth2 / OIDC 基本概念（Authorization Code Flow、ID Token、claims）、以及 SAML 的基本流程（如選用 Dex SAML）。

🎯 學習目標

  • 理解 Argo CD SSO 兩種路徑：Direct OIDC（IdP 原生支援 OIDC 時推薦）vs Dex（IdP 只支援 SAML / LDAP / GitHub OAuth 時必要）
  • 掌握 OIDC Authorization Code Flow 在 Argo CD 中的完整時序
  • 能為 Okta、Azure AD/Entra ID、Google Workspace 設定完整 SSO（含 groups claim）
  • 使用 Dex 整合 SAML（Okta SAML / ADFS）、GitHub OAuth、LDAP（Active Directory）
  • 正確設定 scopes 與 requestedIDTokenClaims 確保 groups 資訊進入 token
  • 使用 argocd account can-i 與 JWT decode 工具診斷 SSO 問題
  • 理解 policy.default 與 scopes 的關係，避免常見的 RBAC 設定陷阱

1SSO 兩種路徑：Direct OIDC vs Dex

Argo CD 提供兩種 SSO 整合路徑。理解兩者差異是設計 SSO 架構的第一步：

⚡
Direct OIDC（推薦）
argocd-server 直接連 IdP
IdP 原生支援 OIDC 時的最佳選擇。設定在 argocd-cm 的 oidc.config，argocd-server 直接呼叫 IdP，不經過 Dex。更簡單、更穩定、可水平擴展（無 Dex HA 限制）。
🌐
Dex（必要時使用）
argocd-server → Dex → IdP
當 IdP 不支援 OIDC（只支援 SAML / LDAP / GitHub OAuth），或需要聚合多個 IdP（同時讓 Okta + GitHub 使用者登入）時使用。Dex 作為協議轉換器，把各種協議轉成 OIDC 給 argocd-server。

1.1 Direct OIDC vs Dex 詳細對比

面向Direct OIDCDex
適用 IdPOkta（OIDC）、Azure AD、Auth0、Keycloak、Google（無 groups）Okta SAML、Azure AD SAML、ADFS、GitHub OAuth、LDAP/AD、Google + Groups
HA支援水平擴展（argocd-server 多 replica 即可）單副本（in-memory DB），重啟期間使用者需重新登入
設定位置argocd-cm 的 oidc.configargocd-cm 的 dex.config + connectors
callback URL/auth/callback/api/dex/callback
除錯難度較簡單（直接連 IdP）需檢查 Dex log + IdP log（雙層）
跳過 Dex—可在 Helm 中 dex.enabled: false 完全停用 Dex 元件
💡

Vol 3 Ch.13 已建議：能用 Direct OIDC 就不用 Dex

Dex 是 Argo CD 唯一無法水平擴展的元件（in-memory database）。若 IdP 支援 OIDC（Okta、Azure AD、Auth0、Keycloak），優先使用 Direct OIDC 並停用 Dex（dex.enabled: false）。只在必須整合 SAML / LDAP / GitHub OAuth 時才保留 Dex。

1.2 OIDC 認證流程（Direct OIDC）

📊 OIDC Authorization Code Flow（Argo CD + Direct OIDC）
1
使用者打開 Argo CD UI（https://argocd.example.com）→ 點選 "Log in via OIDC"
2
argocd-server 重定向至 IdP（如 https://myorg.okta.com/oauth2/default/v1/authorize?...）
帶上 client_id、redirect_uri、scope=openid profile email groups、response_type=code
3
使用者在 IdP 登入（輸入帳號密碼 + MFA）
4
IdP 重定向回 Argo CD callback（https://argocd.example.com/auth/callback?code=AUTHORIZATION_CODE）
5
argocd-server 用 code 向 IdP 換 token（後端 POST 至 IdP /token endpoint，帶 client_secret）→ 取得 ID Token（JWT）+ access_token
6
argocd-server 驗證 ID Token（用 IdP 的 JWKS 公鑰）→ 取出 sub（user ID）、email、groups claims
7
argocd-server 產生自己的 JWT（簽名用 argocd-secret 中的 server.secretkey）→ 寫入瀏覽器 cookie
8
後續所有 API 請求都附帶此 JWT。argocd-server 解 JWT 取得 user / groups → 對照 RBAC policy 決定權限

2Direct OIDC 通用設定範本

所有支援 OIDC 的 IdP 都使用同一份設定模板，只需修改 issuer URL、clientID、scopes 等參數：

YAML — argocd-cm + argocd-secret 通用 OIDC 設定
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  # 必須設定 url（OIDC 重定向需要）
  url: https://argocd.example.com

  oidc.config: |
    # 顯示在 UI 登入按鈕的名稱
    name: Okta
    # IdP 的 OIDC issuer URL（不含 /.well-known/openid-configuration）
    issuer: https://myorg.okta.com/oauth2/default
    # OIDC client ID（在 IdP 的 application 設定中取得）
    clientID: 0oa1b2c3d4e5f6g7h8i9
    # Client secret 從 argocd-secret 動態讀取（$ 表示 reference）
    clientSecret: $oidc.okta.clientSecret

    # 要求的 scopes（取得 group 與 email 必須）
    requestedScopes:
      - openid
      - profile
      - email
      - groups       # 必須請求 groups scope

    # 強制要求 IdP 在 ID token 中放入 groups claim（即使 token 較大）
    requestedIDTokenClaims:
      groups:
        essential: true

    # 可選：限定可登入的 group（在 token 驗證階段過濾）
    # allowedGroups:
    #   - argocd-users
    #   - platform-team

    # 可選：CLI 使用的 client（PKCE flow，無 client secret）
    cliClientID: 0oa-cli-client-id

  # RBAC 必須對應 group claim（見 Ch.14）
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  # 永遠 deny by default
  policy.default: ''
  # 從 token 哪個 claim 取出 group 資訊（預設為 groups）
  scopes: '[groups]'

  policy.csv: |
    g, "platform-admins", role:admin
    g, "developers",      role:readonly
---
apiVersion: v1
kind: Secret
metadata:
  name: argocd-secret
  namespace: argocd
stringData:
  # OIDC client secret（從 IdP 取得）
  oidc.okta.clientSecret: "abc123..."
ℹ️

scopes 與 RBAC scopes 是兩個不同概念

① oidc.config.requestedScopes 是向 IdP 請求的 OAuth scopes（決定 IdP 在 token 中放入哪些 claims）；② argocd-rbac-cm.scopes 是從 token 中讀取哪個 claim 作為 group。前者是 OIDC 概念（OAuth scope），後者是 RBAC 概念（claim mapping）。設定時都要正確！

3Okta 完整設定（最常見場景）

3.1 Step 1：在 Okta 建立應用

Bash + Steps — Okta Application 建立流程
## ── Okta Admin Console 操作步驟 ───────────────────────

# 1. 登入 Okta Admin Console
$ open https://myorg-admin.okta.com

# 2. Applications → Applications → Create App Integration
#    - Sign-in method: OIDC - OpenID Connect
#    - Application type: Web Application

# 3. 設定 Application（重要參數）：
#    - App name: Argo CD
#    - Grant type: ☑ Authorization Code（必選）
#                  ☑ Refresh Token（建議勾選，延長 session）
#    - Sign-in redirect URIs:
#        https://argocd.example.com/auth/callback
#    - Sign-out redirect URIs:
#        https://argocd.example.com
#    - Assignments: Allow everyone OR Limited to groups

# 4. 取得設定值（套用到 argocd-cm）：
#    - Client ID:     從 General 頁面複製
#    - Client secret: 從 General 頁面複製（一次性顯示）
#    - Issuer URL:    Security → API → Authorization Servers → default
#                     範例：https://myorg.okta.com/oauth2/default

# 5. 建立 CLI client（可選，給 argocd CLI 使用）
#    - 同樣建立 OIDC App，但選 Native Application
#    - Grant type: ☑ Authorization Code, ☑ Refresh Token
#    - Sign-in redirect URIs:
#        http://localhost:8085/auth/callback
#    - PKCE: Required（CLI 用 PKCE 而非 client secret）

3.2 Step 2：設定 Groups Claim（關鍵！）

Okta 預設不會在 OIDC token 中包含 groups。必須手動設定 groups claim：

Steps — Okta Groups Claim 設定
## ── 在 Okta 設定 Groups Claim ─────────────────────────

# 1. Security → API → Authorization Servers → default
# 2. 選 Claims 分頁 → Add Claim
#    - Name: groups
#    - Include in token type: ID Token, Always
#    - Value type: Groups
#    - Filter: Matches regex .* （所有 groups）
#       OR    Starts with argocd- （只回傳 argocd- 前綴的 group）
#    - Include in: Any scope（或限定 groups scope）

# 3. 建立 Groups（如果還沒有）：
#    Directory → Groups → Add Group
#    例：argocd-platform-admins, argocd-developers

# 4. 將 user 加入 group：
#    Directory → People → 選 user → Groups → Edit

# 5. 將 group 指派給 Argo CD application：
#    Applications → Argo CD → Assignments → Assign → Assign to Groups

# 6. 驗證：用 Postman 或 curl 測試 token endpoint
#    JWT decode 後應看到 "groups": ["argocd-platform-admins", ...]
YAML — Argo CD 對應的 Okta 設定
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  url: https://argocd.example.com
  oidc.config: |
    name: Okta
    issuer: https://myorg.okta.com/oauth2/default
    clientID: 0oa1b2c3d4e5f6g7h8i9
    clientSecret: $oidc.okta.clientSecret
    cliClientID: 0oa-cli-client-id          # Native CLI client
    requestedScopes:
      - openid
      - profile
      - email
      - groups
    requestedIDTokenClaims:
      groups:
        essential: true

---
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-rbac-cm
  namespace: argocd
data:
  policy.default: ''
  scopes: '[groups,email]'      # 同時支援 group 與 email 對應
  policy.csv: |
    # Group 對應
    g, "argocd-platform-admins", role:admin
    g, "argocd-developers",      role:readonly
    # 個別 user（用 email 對應）
    g, "alice@example.com",      role:admin

4Azure AD / Microsoft Entra ID

Azure AD（現名 Microsoft Entra ID）原生支援 OIDC，使用 Direct OIDC 即可：

Steps — Azure AD App Registration
## ── Azure Portal 設定步驟 ─────────────────────────────

# 1. Azure Portal → Microsoft Entra ID → App registrations → New registration
#    - Name: Argo CD
#    - Supported account types: Single tenant（單一組織）
#    - Redirect URI: Web → https://argocd.example.com/auth/callback

# 2. 取得 IDs：
#    - Application (client) ID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
#    - Directory (tenant) ID:   yyyyyyyy-yyyy-yyyy-yyyy-yyyyyyyyyyyy
#    - Issuer URL:              https://login.microsoftonline.com/{tenant_id}/v2.0

# 3. Certificates & secrets → New client secret
#    - Description: Argo CD secret
#    - Expires: 24 months（最長 2 年；建議短期 + auto rotation）

# 4. 設定 groups claim（重要）：
#    Token configuration → Add groups claim
#    - Which groups to include: Security groups（推薦）
#                              OR All groups
#    - Customize token properties:
#        ID: ☑ Group ID 或 ☑ sAMAccountName
#        Access: ☑ Group ID
#        SAML:  不用設

# 5. API permissions：
#    - Microsoft Graph → User.Read (預設已有)
#    - Microsoft Graph → GroupMember.Read.All（讓 token 含 groups）
#    - Grant admin consent（管理員同意）
YAML — Azure AD argocd-cm 設定
data:
  url: https://argocd.example.com
  oidc.config: |
    name: Microsoft
    issuer: https://login.microsoftonline.com/{TENANT_ID}/v2.0
    clientID: {CLIENT_ID}
    clientSecret: $oidc.azure.clientSecret
    requestedScopes:
      - openid
      - profile
      - email
      # Azure AD 用 https://graph.microsoft.com/.default scope 取代 groups
    requestedIDTokenClaims:
      groups:
        essential: true
⚠️

Azure AD groups claim 是 GUID 不是名稱

Azure AD 預設在 token 中放入 group 的 Object ID（GUID），而非名稱。RBAC policy 必須使用 GUID：g, "12345678-1234-1234-1234-123456789012", role:admin。若要用名稱，需在 App registration → Token configuration 中啟用 onpremises_sam_account_name（需 hybrid AD 同步）或使用 Azure AD Premium 的 Group Display Name 功能。

5Google Workspace（不含 Groups 的 OIDC）

Google 的 OIDC 不會在 token 中包含 group 資訊。如果不需要 group-based RBAC（只用 email 或網域過濾），可以用 Direct OIDC；若需要 Google Groups 整合，必須使用 Dex + 額外的 service account（見下節）。

YAML — Google Direct OIDC（無 groups）
## 在 Google Cloud Console 建立 OAuth 2.0 Client ID
##   APIs & Services → Credentials → Create Credentials → OAuth client ID
##   - Application type: Web application
##   - Authorized redirect URIs: https://argocd.example.com/auth/callback

data:
  url: https://argocd.example.com
  oidc.config: |
    name: Google
    issuer: https://accounts.google.com
    clientID: xxxxxxxxxxxx-xxxxxxxxxxxxxxxxxxxxx.apps.googleusercontent.com
    clientSecret: $oidc.google.clientSecret
    requestedScopes:
      - openid
      - profile
      - email
      # Google 沒有 groups scope

---
data:
  policy.default: ''
  scopes: '[email]'          # 用 email 對應（沒有 groups）
  policy.csv: |
    g, "alice@example.com", role:admin
    g, "bob@example.com",   role:readonly

若需要 Google Groups 整合，使用 Dex + Google connector + service account（Dex 會以 service account 呼叫 Admin SDK 查詢使用者的 group 列表）：

YAML — Dex + Google Groups（需 GSuite super admin）
data:
  url: https://argocd.example.com
  dex.config: |
    connectors:
      - type: google
        id: google
        name: Google
        config:
          clientID: $dex.google.clientID
          clientSecret: $dex.google.clientSecret
          redirectURI: https://argocd.example.com/api/dex/callback
          # 限定網域（只允許 example.com 的使用者）
          hostedDomains:
            - example.com
          # Service account JSON（Dex 用此呼叫 Admin SDK）
          serviceAccountFilePath: /tmp/google-service-account.json
          # 要 impersonate 的 admin user（需要 Domain-wide delegation）
          adminEmail: admin@example.com

6Dex 進階設定（SAML / GitHub / LDAP）

6.1 SAML connector（Okta SAML / ADFS）

YAML — Dex SAML connector（Okta SAML）
data:
  url: https://argocd.example.com
  dex.config: |
    connectors:
      - type: saml
        id: okta-saml
        name: Okta SAML
        config:
          # 從 Okta SAML application 設定中取得
          ssoURL: https://myorg.okta.com/app/xxx/sso/saml
          # Okta 提供的 CA certificate（驗證 SAML response）
          caData: |
            LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t...
          redirectURI: https://argocd.example.com/api/dex/callback
          # 必須匹配 Okta 中的 Audience URI（SP Entity ID）
          entityIssuer: https://argocd.example.com/api/dex/callback

          # SAML attribute 對應
          usernameAttr: email
          emailAttr: email
          groupsAttr: groups       # SAML assertion 中的 group 屬性名

          # 可選：filter group by prefix
          ## groupsDelim: ","

## ── Okta SAML 端設定 ─────────────────────────────────
# 1. Applications → Create App Integration → SAML 2.0
# 2. Single sign-on URL: https://argocd.example.com/api/dex/callback
# 3. Audience URI (SP Entity ID): https://argocd.example.com/api/dex/callback
# 4. Attribute Statements:
#    - email = user.email
# 5. Group Attribute Statements:
#    - groups = Matches regex .* (or specific filter)

6.2 GitHub OAuth（小團隊或 OSS 專案）

YAML — Dex GitHub OAuth connector
data:
  url: https://argocd.example.com
  dex.config: |
    connectors:
      - type: github
        id: github
        name: GitHub
        config:
          clientID: $dex.github.clientID

# 1. GitHub → Settings → Developer settings → OAuth Apps → New
# 2. Homepage URL: https://argocd.example.com
# 3. Authorization callback URL:
#    https://argocd.example.com/api/dex/callback
# 4. 取得 Client ID 與 Client Secret 寫入 argocd-secret

## ── RBAC：使用 GitHub team 名稱 ─────────────────────
# groups 的格式為：<org-name>:<team-slug>
# g, "my-github-org:argocd-admins", role:admin

6.3 LDAP connector（企業內部 Active Directory）

YAML — Dex LDAP connector（Active Directory）
data:
  url: https://argocd.example.com
  dex.config: |
    connectors:
      - type: ldap
        id: ldap
        name: Active Directory
        config:
          # LDAP/AD server
          host: ldap.example.com:636
          # 啟用 LDAPS（TLS）
          insecureNoSSL: false
          insecureSkipVerify: false
          # Service account（Dex 用此 bind 後查詢）
          bindDN: cn=argocd-readonly,ou=service-accounts,dc=example,dc=com
          bindPW: $dex.ldap.bindPW

          # User search
          userSearch:
            baseDN: ou=Users,dc=example,dc=com
            filter: "(objectClass=person)"
            username: sAMAccountName        # AD 中的 username 屬性
            idAttr: objectGUID
            emailAttr: mail
            nameAttr: displayName

          # Group search
          groupSearch:
            baseDN: ou=Groups,dc=example,dc=com
            filter: "(objectClass=group)"
            # 連結 user 與 group 的屬性
            userMatchers:
              - userAttr: distinguishedName
                groupAttr: member
            # Group 顯示名稱屬性
            nameAttr: cn

## ── RBAC：使用 LDAP/AD group CN ─────────────────────
# groups 的格式為 group 的 nameAttr（如 cn）
# g, "ArgoCD-Admins", role:admin

7Groups Claim 驗證與除錯

SSO 設定完成後，最常見的問題是「登入成功但所有 App 看不到」。這通常是 group claim 沒有正確進入 token，或 RBAC 沒有正確對應。診斷步驟：

Bash — Groups Claim 診斷流程
## ── 步驟 1：取得當前 user 的 token ───────────────────
$ argocd login argocd.example.com --sso
# 完成 OIDC 登入後

$ TOKEN=$(argocd account get-user-info --output json | jq -r '.iss')
# 或從 ~/.argocd/config 讀取
$ TOKEN=$(yq '.users[0].auth-token' ~/.config/argocd/config)

## ── 步驟 2：解碼 JWT 看 claims ───────────────────────
$ echo $TOKEN | cut -d. -f2 | base64 -d | jq
## 範例輸出：
# {
#   "iss": "https://argocd.example.com/api/dex",
#   "sub": "Cg5...",
#   "email": "alice@example.com",
#   "groups": [
#     "argocd-platform-admins",   # ← 確認此處有 group
#     "argocd-developers"
#   ],
#   "name": "Alice",
#   "exp": 1738000000
# }

## ── 步驟 3：驗證 RBAC 規則 ───────────────────────────
$ argocd account can-i sync application '*/*'
# yes / no

# 詳細權限
$ argocd account get-user-info

## ── 步驟 4：檢查 user info（透過 API）─────────────────
$ curl -H "Authorization: Bearer $TOKEN" \
    https://argocd.example.com/api/v1/account/can-i/applications/sync/*/*
## 回傳 {"value": "yes"} 或 {"value": "no"}

## ── 步驟 5：在 Argo CD UI 直接看 user info ───────────
## 點選右上角 user icon → User Info
## 顯示 ID Token 解碼後的所有 claims
⚠️

常見陷阱：scopes 設定不完整

① oidc.config.requestedScopes 沒包含 groups：IdP 不會在 token 中放入 group 資訊。② argocd-rbac-cm.scopes 寫成 '[email]' 卻在 policy.csv 用 group 名稱：永遠 deny。③ Okta 沒設定 groups claim：即使 scopes 對也沒用。三者必須一致。

8SSO 故障排查

錯誤訊息原因解法
redirect_uri_mismatchIdP 設定的 redirect URI 與 Argo CD 不符確認 IdP application 中的 redirect URI 是 https://argocd.example.com/auth/callback（Direct OIDC）或 /api/dex/callback（Dex）
invalid_clientclientID / clientSecret 錯誤檢查 argocd-cm 的 clientID 與 argocd-secret 中的 clientSecret 是否與 IdP 一致
登入後仍看不到任何 Appgroups claim 未進入 token，或 RBAC 不匹配① JWT decode 看是否有 groups；② 檢查 scopes；③ 用 argocd account can-i 驗證

📌 Key Takeaways

  • ⚡能用 Direct OIDC 就不用 Dex：Direct OIDC 設定簡單、可水平擴展、除錯容易。Dex 只在 IdP 不支援 OIDC（SAML / LDAP / GitHub OAuth）或需聚合多 IdP 時使用。Dex 是 Argo CD 唯一無法 HA 的元件。
  • 🔄OIDC 流程關鍵：argocd-server → IdP authorize → 使用者登入 → callback 帶 code → 後端換 token → 驗證 JWT 取 claims → 產生 Argo CD 自己的 JWT 寫入 cookie。後續所有 API 都帶此 cookie。
  • 🎯Okta 設定四要素：① Web Application + Authorization Code grant；② Sign-in redirect URI 是 /auth/callback；③ Authorization Server → Claims 中加入 groups claim（Always、ID Token）；④ Group 加入 Argo CD application 的 Assignments。
  • 🪟Azure AD 的 GUID 陷阱：預設 groups claim 是 GUID 而非名稱，RBAC policy 必須用 GUID。或在 Token configuration 中設定 onpremises_sam_account_name 取得名稱（需 hybrid AD 同步）。
  • 🌐Google 不支援 OIDC groups：需 Dex + Google Service Account + Domain-wide Delegation 才能取得 Google Groups。沒有 group 需求時可用 Direct OIDC + email 對應。
  • 🔍SSO 除錯三步驟：① JWT decode 看 token 是否含 groups；② argocd account can-i 驗證權限；③ argocd-server / dex log 看 OIDC 錯誤。最常見的陷阱是 scopes / claims / RBAC 設定不一致。
  • 🔐OIDC scopes 與 RBAC scopes 不同概念：① oidc.config.requestedScopes 是向 IdP 請求；② argocd-rbac-cm.scopes 是從 token 取出哪個 claim。前者必含 groups（讓 IdP 放入 token），後者必設 '[groups]'（讓 RBAC 讀取）。
