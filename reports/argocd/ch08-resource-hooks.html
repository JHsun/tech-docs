Resource Hooks：
PreSync / Sync / PostSync / SyncFail

Resource Hooks 讓你在部署的各個階段插入自定義邏輯——部署前執行 DB migration、部署後執行 smoke test、失敗時發送告警、刪除前執行清理。本章深入六種 Hook 類型、三種 Delete Policy，以及實際生產場景的完整 YAML 範例。

📋

前置：已閱讀 Ch.06（syncPolicy 與 Sync 流程）。了解 Kubernetes Job / Pod 的基本結構。

🎯 學習目標

  • 理解 Hook 在 Sync 生命週期中的執行順序，以及各 Phase 的失敗行為
  • 掌握六種 Hook 類型（PreSync / Sync / PostSync / SyncFail / PreDelete / Skip）的適用場景
  • 理解三種 Hook Delete Policy（HookSucceeded / HookFailed / BeforeHookCreation）的行為差異與組合方式
  • 能撰寫 DB migration PreSync hook、PostSync smoke test、SyncFail 告警通知等完整 Job YAML
  • 理解 PreDelete hook（v3.3）的運作機制與 Application 刪除流程
  • 了解 Argo CD Hook 與 Helm hook 的差異，以及 Selective Sync 對 hook 的影響

1Hook 概念與 Sync 生命週期

Resource Hook 是用特定 annotation 標記的 Kubernetes 資源，告訴 Argo CD 在 sync 的哪個階段執行它。Hook 與一般資源的根本差異在於：Hook 有明確的生命週期——執行完成後，Argo CD 可以根據 Delete Policy 自動清理。

1.1 Sync 生命週期完整圖

Phase 1
PreSync
在所有應用資源 apply 之前執行。例如 DB migration、前置備份。
❌ 失敗 → 整個 sync 停止，應用資源不受影響
Phase 2
Sync
與應用資源同時 apply（按 sync wave 順序）。複雜部署編排邏輯。
❌ 失敗 → 標記 SyncFail，同時觸發 SyncFail hooks
Phase 3
PostSync
所有 Sync Phase 資源 Healthy 後執行。Smoke test、通知、cache warming。
❌ 失敗 → 整個操作標記為失敗
Phase 4（條件）
SyncFail
只在 sync 失敗時執行（Phase 2 或 3 失敗）。清理、回滾、告警。
⚠️ SyncFail hook 本身失敗時僅標記操作失敗，不再遞迴
ℹ️

PreDelete 與 PostDelete 在獨立的生命週期

PreDelete 與 PostDelete（實驗性）hook 不在 sync 生命週期中執行，而是在 Application 刪除流程中執行。PreDelete 在資源刪除前，PostDelete 在所有資源刪除後。詳見 2.5 節。

1.2 Hook vs 一般資源的差異

面向一般資源（非 Hook）Hook 資源
執行時機在 Sync Phase（wave 順序）在指定 Phase（PreSync / PostSync 等）
執行完後的資源狀態持續在叢集中（受 Argo CD 管理）由 Delete Policy 決定是否清理
Health 判定由 Argo CD 持續 reconcilePod/Job 完成（Completed）= Hook 成功
Selective Sync 影響在 Selective Sync 時可能被跳過Hook 不受 Selective Sync 影響（不會被跳過）
Git 中的位置在 source path 中也在 source path 中，以 annotation 區分
Prune 行為啟用 prune 時，從 Git 刪除後會從叢集刪除由 Delete Policy 獨立控制，不受 prune 影響

2六種 Hook 類型詳解

⚡
PreSync
在所有應用資源 apply 之前執行
最常使用的 hook。若 PreSync hook 失敗，整個 sync 停止，應用資源完全不受影響，可確保「先遷移資料庫，再部署新程式碼」的安全順序。
典型用途
• DB Schema migration
• 部署前備份
• 前置驗證（如 config lint）
• 建立依賴資源（ConfigMap、Secret）
🔄
Sync
與應用資源同時 apply（按 sync wave 排序）
較少使用。與一般應用資源在同一 Phase，但受 wave 控制順序。適合需要在部署過程中插入特定操作，且需要與其他資源交錯執行的情境。
典型用途
• 複雜部署編排中的中間步驟
• 需要在特定 wave 執行的初始化工作
• 資料種子（data seeding）
✅
PostSync
所有 Sync Phase 資源 Healthy 後執行
在 Sync Phase 的所有資源（含 Sync hooks）都達到 Healthy 後才觸發。適合執行驗證、通知等需要確認部署成功才能進行的工作。PostSync hook 失敗會讓整個操作標記失敗。
典型用途
• Smoke test / Integration test
• Slack / PagerDuty 成功通知
• Cache warming
• 觸發下游 CD pipeline
🚨
SyncFail
只在 sync 失敗時執行
當 Sync Phase 或 PostSync Phase 失敗時觸發（PreSync 失敗不觸發）。SyncFail hook 本身失敗，不會進一步遞迴觸發更多 hook，只標記操作為失敗。注意：Selective Sync 不執行 SyncFail hook。
典型用途
• 失敗告警通知
• DB Schema rollback
• 清理部分建立的資源
• 更新外部狀態系統（ITSM ticket）
🗑️
PreDelete v3.3
Application 刪除前執行（非 sync 生命週期）
在 Application 被刪除（kubectl delete / argocd app delete）時，先執行清理工作再刪除資源。Argo CD 等待 PreDelete hook 達到 Healthy 後，才繼續刪除 Application 資源。若 hook 失敗，刪除流程被阻擋。
典型用途
• 服務下線通知
• 清理 external resources（DNS、LB）
• 資料備份後再刪除
• 通知相關系統
⏭️
Skip
告訴 Argo CD 忽略此資源
標記為 Skip 的資源存在於 Git repo 中，但 Argo CD 在 sync 時會完全忽略它（不 apply、不追蹤、不計入 Sync Status）。適合文件用的 manifest 或由其他 controller 管理的資源。
典型用途
• 文件性 manifest
• 由另一個 Argo CD App 管理的共用資源
• 暫時停用的資源

2.1 基本 Hook Annotation 語法

YAML — Hook Annotation 基本語法
metadata:
  annotations:
    # 指定 hook 類型（必填）
    argocd.argoproj.io/hook: PreSync

    # 指定 hook 刪除策略（選填，預設 BeforeHookCreation）
    argocd.argoproj.io/hook-delete-policy: HookSucceeded

    # 指定 sync wave（在同一 Phase 中的執行順序，預設 0）
    argocd.argoproj.io/sync-wave: "1"

    # 多個 hook 類型：同時在多個 Phase 執行（逗號分隔）
    # argocd.argoproj.io/hook: PreSync,SyncFail

2.2 PreDelete Hook 深度說明（v3.3）

PreDelete hook 是 v3.3 新增的功能，解決了「刪除 Application 前需要執行清理作業」的需求。它的執行流程如下：

YAML — PreDelete Hook 完整範例
apiVersion: batch/v1
kind: Job
metadata:
  name: pre-delete-cleanup
  namespace: production
  annotations:
    # 在 Application 刪除前執行
    argocd.argoproj.io/hook: PreDelete
    # HookSucceeded：清理成功後刪除此 Job
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: cleanup
          image: bitnami/kubectl:latest
          command:
            - sh
            - -c
            - |
              # 發送服務下線通知
              curl -X POST "$SLACK_WEBHOOK" \
                -d '{"text":"⚠️ production/my-app 即將刪除，請注意"}'
              # 清理 external DNS record
              kubectl delete externaldns my-app-record --ignore-not-found
              echo "PreDelete cleanup completed"
          env:
            - name: SLACK_WEBHOOK
              valueFrom:
                secretKeyRef:
                  name: slack-webhook
                  key: url
PreDelete 行為說明
觸發條件執行 argocd app delete 或 kubectl delete application 時
不觸發條件正常 sync 操作，即使啟用了 prune；只有「刪除 Application」才觸發
失敗時行為刪除操作被阻擋，Application 保持在「刪除中」狀態，需修復 hook 才能繼續
等待條件Argo CD 等待 PreDelete hook 的 Pod/Job 達到 Healthy（Completed）狀態
與 cascade delete 的關係PreDelete hook 執行完畢後，才開始 cascade 刪除應用資源

3Hook Delete Policy：生命週期管理

若不設定 Delete Policy，每次 sync 都會累積一個完成的 Job 在叢集中。50 次 sync 後，叢集中就有 50 個 completed migration Job，造成資源混亂。Delete Policy 讓 Argo CD 自動清理 hook 資源。

3.1 三種 Delete Policy 詳解

Policy觸發時機行為適用場景
BeforeHookCreation
（預設）		 下次 sync 開始時，在建立新 hook 之前 刪除同名的舊 hook 資源，再建立新的。上次 hook 的結果（成功或失敗）都保留到下次 sync 前。 DB migration、任何需要查看最後一次執行結果的 hook；預設行為，無需特別設定
HookSucceeded hook 執行成功後立即刪除 hook Job/Pod 成功完成後，Argo CD 自動刪除。失敗時保留，便於除錯。 Smoke test、通知、任何成功就不需要保留的 hook；最常用的清理策略
HookFailed hook 執行失敗後立即刪除 hook 失敗後立即刪除，成功時保留。較少使用。 需要保留成功執行記錄供稽核，但失敗的不重要的 hook

3.2 組合策略（最佳實踐）

YAML — 常用組合策略
## 組合一：成功清理 + 新 sync 前清理（最通用）
## 效果：成功後刪除；失敗時保留（便於除錯）；下次 sync 時清理舊的
argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation

## 組合二：無論成敗都清理（通知類 hook）
## 效果：Job 完成後立即刪除，不需要除錯
argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed

## 不設定（僅 BeforeHookCreation 效果）
## 適合：每次 sync 都想保留最後結果供查看
## 但注意：失敗的 Job 若名稱相同，下次 sync 才會被清理

## generateName 與固定 name 的選擇：
## generateName：每次建立不同名稱的 Job（適合 audit trail）
## name：固定名稱（配合 BeforeHookCreation 自動清理舊 Job）
Hook 類型推薦 Delete Policy原因
PreSync DB migrationHookSucceeded,BeforeHookCreation成功後清理；失敗保留除錯；下次 sync 前重置
PostSync smoke testHookSucceeded,BeforeHookCreation同上；失敗時需要查看 log 排查原因
PostSync Slack 通知HookSucceeded,HookFailed通知 fire-and-forget，無需保留
SyncFail 告警HookSucceeded,BeforeHookCreation成功告警後清理；新 sync 時清理舊告警
PreDelete 清理HookSucceeded成功執行後清理，失敗保留（阻擋刪除直到修復）

4Hook 可支援的資源類型

任何 Kubernetes 資源都可以加上 hook annotation，但 Argo CD 判斷 hook「成功」的邏輯因資源類型而異：

資源類型成功條件常見使用方式
Job（最常用）Job.status.succeeded >= 1（至少一個 Pod 成功完成）DB migration、smoke test、通知
PodPod.status.phase == Succeeded簡單的一次性任務
Argo WorkflowWorkflow.status.phase == Succeeded複雜多步驟工作流（需安裝 Argo Workflows）
DeploymentDeployment Healthy（所有 replica 就緒）在特定 Phase 部署輔助服務
ConfigMap / Secret套用即成功（不等待）預先建立配置資源
⚠️

Job 必須設定 restartPolicy: Never

Hook Job 的 Pod template 必須設定 restartPolicy: Never（或 OnFailure）。使用 Never 時，Pod 失敗後不會自動重啟，Job 的 backoffLimit 控制最大重試次數。不設定 restartPolicy 會導致 Job 在 Pod 失敗後無法正確計算成功/失敗狀態。

5實戰場景完整範例

5.1 DB Schema Migration（PreSync）

🗄️ 場景：Django DB Migration（部署新版本前自動執行） PreSync
YAML — DB Migration PreSync Job
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PreSync
    # 成功後清理；失敗時保留（除錯）；下次 sync 前刪舊的
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
    # wave -1：確保在其他 PreSync hook 之前執行
    argocd.argoproj.io/sync-wave: "-1"
spec:
  backoffLimit: 3  # 失敗最多重試 3 次
  activeDeadlineSeconds: 300  # 5 分鐘超時
  template:
    spec:
      restartPolicy: Never
      serviceAccountName: my-app-sa  # 確保有 DB 連線權限
      containers:
        - name: migrate
          # 使用與 App 相同的 image，確保 migration 與 code 版本一致
          image: myregistry/my-api:v3.2.1
          command: ["python", "manage.py", "migrate", "--no-input"]
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: db-credentials
                  key: url

5.2 PostSync Smoke Test

🧪 場景：部署後 HTTP 健康檢查（失敗則標記 sync 失敗） PostSync
YAML — PostSync Smoke Test Job
apiVersion: batch/v1
kind: Job
metadata:
  name: smoke-test
  namespace: production
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,BeforeHookCreation
spec:
  backoffLimit: 0  # smoke test 不重試，失敗就是失敗
  activeDeadlineSeconds: 120
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: smoke-test
          image: curlimages/curl:latest
          command:
            - sh
            - -c
            - |
              # 等待服務完全就緒
              sleep 10
              # 健康檢查
              STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
                http://my-api-service:8080/health)
              if [ "$STATUS" != "200" ]; then
                echo "Smoke test FAILED: /health returned $STATUS"
                exit 1
              fi
              # API 功能測試
              STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
                -H "Authorization: Bearer $TEST_TOKEN" \
                http://my-api-service:8080/api/v1/users)
              if [ "$STATUS" != "200" ]; then
                echo "Smoke test FAILED: /api/v1/users returned $STATUS"
                exit 1
              fi
              echo "All smoke tests PASSED"
          env:
            - name: TEST_TOKEN
              valueFrom:
                secretKeyRef:
                  name: test-credentials
                  key: token

5.3 SyncFail 告警通知

🚨 場景：Sync 失敗時發送 Slack 告警 SyncFail
YAML — SyncFail Slack 告警
apiVersion: batch/v1
kind: Job
metadata:
  generateName: sync-fail-alert-  # 每次失敗建立不同名稱
  namespace: production
  annotations:
    argocd.argoproj.io/hook: SyncFail
    # 通知 fire-and-forget，無論成敗都清理
    argocd.argoproj.io/hook-delete-policy: HookSucceeded,HookFailed
spec:
  backoffLimit: 2
  activeDeadlineSeconds: 60
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: slack-alert
          image: curlimages/curl:latest
          command:
            - sh
            - -c
            - |
              curl -X POST "$SLACK_WEBHOOK_URL" \
                -H 'Content-type: application/json' \
                -d "{
                  \"text\": \"🚨 *ArgoCD Sync 失敗*\",
                  \"attachments\": [{
                    \"color\": \"danger\",
                    \"fields\": [
                      {\"title\": \"Application\", \"value\": \"$ARGOCD_APP_NAME\", \"short\": true},
                      {\"title\": \"Namespace\", \"value\": \"$ARGOCD_APP_NAMESPACE\", \"short\": true}
                    ]
                  }]
                }"
          env:
            - name: ARGOCD_APP_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.labels['app.kubernetes.io/name']
            - name: ARGOCD_APP_NAMESPACE
              valueFrom:
                fieldRef:
                  fieldPath: metadata.namespace
            - name: SLACK_WEBHOOK_URL
              valueFrom:
                secretKeyRef:
                  name: slack-webhook
                  key: url
ℹ️

SyncFail 告警：建議改用 Argo CD Notifications

雖然 SyncFail hook 可以發送告警，但 Argo CD Notifications（Vol 6 Ch.29）是更好的選擇：Notifications 是 Application 層級的設定，無需修改 manifest；支援更多服務（Slack / PagerDuty / Email / Webhook）；不占用 namespace 資源；發送失敗不影響 sync 狀態。SyncFail hook 更適合複雜的清理邏輯（如 DB rollback），而非單純通知。

5.4 完整的 DB Migration + Smoke Test + SyncFail 組合

YAML — 完整 Hook 組合（三個 Job 放在同一 YAML 或同一目錄）
## 目錄結構
## k8s/
## ├── deployment.yaml
## ├── service.yaml
## ├── hooks/
##     ├── presync-migrate.yaml    ← 本節 5.1
##     ├── postsync-smoke.yaml     ← 本節 5.2
##     └── syncfail-alert.yaml     ← 本節 5.3

## 執行順序（成功路徑）：
## 1. PreSync: db-migrate Job → 等待完成
## 2. Sync:    deployment.yaml + service.yaml apply（wave 0）
## 3. PostSync: smoke-test Job → 等待完成
##    ✅ 成功 → sync 完成，兩個 Job 被 HookSucceeded 清理

## 執行順序（失敗路徑 - smoke test 失敗）：
## 1. PreSync: db-migrate → 成功（Job 被清理）
## 2. Sync:    Deployment + Service apply → 成功
## 3. PostSync: smoke-test → 失敗（Job 保留供除錯）
## 4. SyncFail: sync-fail-alert Job 執行 → 發送告警
##    🚨 整體操作標記 SyncFail

6Hook 的限制與最佳實踐

限制 / 注意點說明
Selective Sync 不執行 Hook使用 Selective Sync 時，所有 hook（PreSync / PostSync 等）都不執行，只 apply 選定的資源。若需要 hook，需使用完整 sync。
Helm hook annotation 不相容Argo CD 不執行 Helm 原生 hook（helm.sh/hook）。若 chart 使用 Helm hook，需要轉換為 Argo CD hook annotation，或使用 skipHooks: true 跳過。
SyncFail hook 不遞迴SyncFail hook 本身失敗，不會觸發新的 SyncFail hook。只標記操作失敗。
PreSync 失敗不觸發 SyncFailPreSync hook 失敗時，sync 停止且不觸發 SyncFail hook——因為 Sync Phase 根本沒有開始。
Hook 不適合長時間任務Hook 執行時間過長會阻擋整個 sync。建議設定 activeDeadlineSeconds 超時，並考慮用 Argo Workflows 處理複雜長時間任務。
RBAC 權限Hook Job 執行時使用的 ServiceAccount 需要有執行其任務所需的 RBAC 權限。避免使用 default ServiceAccount（通常沒有 API 存取權限）。
💡

最佳實踐總結

① 一定要設定 Delete Policy，避免 Job 累積。
② 設定 activeDeadlineSeconds 超時，防止 hook 永遠等待。
③ PreSync hook 必須設計為冪等的（idempotent）——因為 retry 可能多次執行。
④ SyncFail hook 用於清理，通知改用 Argo CD Notifications。
⑤ 用 sync-wave 控制同 Phase 內 hook 的順序（如先備份再 migration）。
⑥ 測試 hook 時先在 staging 環境驗證，錯誤的 PreSync hook 會阻擋所有 sync。

✓本章重點回顧

📌 Key Takeaways

  • ⚡六種 Hook 類型的時機：PreSync（最早，所有資源之前）→ Sync（與資源同時，按 wave）→ PostSync（所有資源 Healthy 後）→ SyncFail（sync 失敗時）。PreDelete（v3.3，Application 刪除前）與 Skip（完全忽略）是特殊類型。
  • ❌失敗行為：PreSync 失敗 → sync 停止（不觸發 SyncFail）；Sync/PostSync 失敗 → 觸發 SyncFail hook；SyncFail hook 本身失敗 → 只標記失敗，不遞迴。
  • 🗑️Delete Policy 必須設定：不設定會讓 hook Job 無限累積。推薦組合：DB migration / smoke test 使用 HookSucceeded,BeforeHookCreation；通知類使用 HookSucceeded,HookFailed。
  • 🔁PreSync hook 必須是 idempotent 的（冪等）：因為 retry 機制可能導致同一 hook 被多次執行。DB migration 工具（如 Flyway、Alembic、Django migrate）通常已內建冪等設計。
  • ⏭️Selective Sync 不執行 Hook：這是常見的踩坑點。若你手動選擇特定資源做 Selective Sync，PreSync / PostSync 都不會執行。需要 hook 的情境應使用完整 sync。
  • 📢通知建議改用 Argo CD Notifications（Vol 6 Ch.29）：比 SyncFail hook 更靈活、不占用 namespace 資源、支援更多服務。SyncFail hook 適合的是複雜清理邏輯，而非單純通知。
