Hibernate ORM with Panache

Panache 是 Quarkus 為 Hibernate ORM 量身打造的「糖衣層」── 同樣的 entity、同樣的 query， 但程式碼少 50–70%。它提供兩種風格：Active Record（entity 自帶 CRUD 方法） 與 Repository（DDD 派的傳統做法）。本章告訴你怎麼選、怎麼用，以及何時該退回原生 Hibernate。

為什麼用 Panache：50 行 vs 5 行

Java · 純 Hibernate 的 CRUD repository
@ApplicationScoped
public class ProductRepository {
    @Inject EntityManager em;

    public Product findById(Long id) {
        return em.find(Product.class, id);
    }

    public List<Product> findAll() {
        return em.createQuery("SELECT p FROM Product p", Product.class).getResultList();
    }

    public List<Product> findByName(String name) {
        return em.createQuery("SELECT p FROM Product p WHERE p.name = :n", Product.class)
            .setParameter("n", name).getResultList();
    }

    @Transactional
    public Product persist(Product p) { em.persist(p); return p; }

    @Transactional
    public boolean deleteById(Long id) {
        Product p = em.find(Product.class, id);
        if (p == null) return false;
        em.remove(p); return true;
    }

    public long count() {
        return em.createQuery("SELECT COUNT(p) FROM Product p", Long.class).getSingleResult();
    }
}
Java · Panache Active Record
@Entity
public class Product extends PanacheEntity {
    public String name;
    public BigDecimal price;

    public static List<Product> findByName(String name) {
        return list("name", name);
    }
}

// 用法
Product.findById(42L);
Product.listAll();
Product.findByName("Widget");
Product.count();
new Product().persist();          // 寫法 1
Product.deleteById(42L);
少寫的程式碼 = 少出 bug、少審 review、少維護成本。

加擴充

bash
quarkus extension add hibernate-orm-panache jdbc-postgresql

Panache 是 ORM 之上的 thin layer，所以 datasource、schema、二級快取等配置與第 15 章完全相同。

Active Record 模式

讓 entity 繼承 PanacheEntity，立刻獲得一堆 static 與 instance 方法：

Java · Product extends PanacheEntity
import io.quarkus.hibernate.orm.panache.PanacheEntity;
import jakarta.persistence.*;

@Entity
@Table(name = "products")
public class Product extends PanacheEntity {

    public String name;
    public String sku;
    public BigDecimal price;

    @Column(name = "created_at")
    public Instant createdAt = Instant.now();
}
✓
Panache 的兩個爭議特性
  1. 沒有 @Id ── PanacheEntity 已經提供 public Long id，自動 IDENTITY 生成。要客製 ID 策略則繼承 PanacheEntityBase。
  2. 使用 public field ── 不需 getter / setter。Quarkus 在 build time 自動產生 accessor 並改寫外部呼叫，行為與原本 Hibernate 一致。需要客製邏輯時可以加 setter，會自動被使用。
這在團隊接受度上常引發討論。喜歡 DDD / encapsulation 的人可用 Repository 模式（下一節）。

Active Record 內建操作

建立與儲存

Java
@Transactional
public Product create(String name, BigDecimal price) {
    Product p = new Product();
    p.name = name;
    p.price = price;
    p.persist();        // INSERT
    return p;           // p.id 已填回
}

// 批次
Product.persist(productA, productB, productC);    // varargs
Product.persist(myList);                          // Iterable

查詢

Java · 查詢 API 一覽
// 依 ID
Product p = Product.findById(42L);
Optional<Product> op = Product.findByIdOptional(42L);

// 全部
List<Product> all = Product.listAll();
Stream<Product> stream = Product.streamAll();      // 大量資料時省記憶體

// 簡化欄位查詢（Panache 偵測「單欄位 = 值」格式）
List<Product> widgets = Product.list("name", "Widget");
List<Product> expensive = Product.list("price > ?1", new BigDecimal("100"));

// 多參數
List<Product> r = Product.list("name = ?1 and price > ?2", "Widget", new BigDecimal("50"));

// 具名參數
List<Product> r2 = Product.list("name = :n and price > :p",
    Parameters.with("n", "Widget").and("p", new BigDecimal("50")));

// 排序
List<Product> sorted = Product.list("price > ?1", Sort.by("name").and("price", Sort.Direction.Descending), new BigDecimal("100"));

// 數量
long count = Product.count();
long expensiveCount = Product.count("price > ?1", new BigDecimal("100"));

// 存在判斷
boolean exists = Product.find("sku", "WID-001").firstResultOptional().isPresent();
ℹ︎
Panache 簡化 query 的「魔法」
Product.list("name", "Widget") 並不是 JPQL ── Panache 偵測到「一個 query 一個 value」就自動補成 SELECT p FROM Product p WHERE name = ?1。 當你給的是完整 JPQL（含 SELECT、FROM 或運算子），Panache 就照原樣用。 這個彈性是 Panache 的核心生產力來源。

分頁：PanacheQuery

find() 回傳 PanacheQuery<T>，可以鏈接分頁、排序、page count：

Java · 分頁
PanacheQuery<Product> query = Product.find("price > ?1", new BigDecimal("100"));

// 取第 1 頁，每頁 20 筆
List<Product> page = query.page(Page.of(0, 20)).list();

// 下一頁
query.nextPage();
List<Product> nextPage = query.list();

// 總筆數與總頁數
long total = query.count();
int pageCount = query.pageCount();

// 一次取所有
List<Product> allMatching = query.list();

更新

Java
// 取出後改 ── 跟純 Hibernate 一樣，managed entity 自動 dirty check
@Transactional
public void increasePrice(Long id, BigDecimal delta) {
    Product p = Product.findById(id);
    p.price = p.price.add(delta);
    // 不需呼叫 .update()！
}

// 批次 UPDATE（直接發 SQL，不走 entity load）
@Transactional
public long markExpensive() {
    return Product.update("name = ?1 where price > ?2",
        "[Premium] " + " (expensive)", new BigDecimal("1000"));
}

刪除

Java
@Transactional
public void deleteCheap() {
    Product.delete("price < ?1", new BigDecimal("10"));   // 批次 DELETE
}

@Transactional
public void deleteOne(Long id) {
    boolean deleted = Product.deleteById(id);
}

@Transactional
public void deleteAll() {
    long deleted = Product.deleteAll();        // 清空表
}

自訂 static 查詢方法

業界最佳實踐：把 query 邏輯放在 entity 內，讓資料存取與 entity「住在一起」：

Java · 把 query 放 entity
@Entity
public class Product extends PanacheEntity {
    public String name;
    public String sku;
    public BigDecimal price;
    public Boolean active;

    // ── 自訂查詢 ──
    public static Optional<Product> findBySku(String sku) {
        return find("sku", sku).firstResultOptional();
    }

    public static List<Product> findActiveInPriceRange(BigDecimal min, BigDecimal max) {
        return list("active = true and price between ?1 and ?2", min, max);
    }

    public static PanacheQuery<Product> search(String keyword) {
        return find("lower(name) like ?1", "%" + keyword.toLowerCase() + "%");
    }
}

// 業務層用起來像這樣
List<Product> results = Product.findActiveInPriceRange(min, max);
Product p = Product.findBySku("WID-001").orElseThrow(NotFoundException::new);

Repository 模式

如果你的團隊偏好「entity 是純資料、CRUD 操作獨立成 class」（典型 DDD / Hexagonal Architecture），用 Repository 模式：

Java · 純 JPA entity + Repository
// Entity 是「乾淨」的 JPA entity（用 private + getter/setter）
@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private BigDecimal price;
    // getters/setters
}

// Repository 提供 CRUD
import io.quarkus.hibernate.orm.panache.PanacheRepository;

@ApplicationScoped
public class ProductRepository implements PanacheRepository<Product> {

    public Optional<Product> findBySku(String sku) {
        return find("sku", sku).firstResultOptional();
    }

    public List<Product> findActiveInPriceRange(BigDecimal min, BigDecimal max) {
        return list("active = true and price between ?1 and ?2", min, max);
    }
}

使用：

Java
@ApplicationScoped
public class CatalogService {

    @Inject ProductRepository repository;

    @Transactional
    public Product create(Product p) {
        repository.persist(p);
        return p;
    }

    public Product findById(Long id) {
        return repository.findById(id);
    }
}
ℹ︎
兩種模式如何選
  • Active Record：簡單 CRUD、中小型專案、追求最少程式碼
  • Repository：團隊有 DDD 共識、需要與其他 ORM 共存、entity 是 immutable 或要 expose 給 client side（不想暴露 persistence 方法）
  • 同一個專案可以混用，但建議統一風格

客製 ID：PanacheEntityBase

PanacheEntity 預設用 Long id + IDENTITY。要用 UUID、複合 ID 或 sequence？繼承 PanacheEntityBase 自己管 ID：

Java · UUID 主鍵
import io.quarkus.hibernate.orm.panache.PanacheEntityBase;

@Entity
public class Order extends PanacheEntityBase {

    @Id @GeneratedValue
    public UUID id;

    public String customerId;
    public BigDecimal total;
}

// 因為 ID 型別不是 Long，findById 也支援 UUID：
Order o = Order.findById(UUID.fromString("..."));

Projection：只取需要的欄位

列表 API 常常只需要部分欄位。抓整顆 entity 是浪費。Panache 有 @RegisterForReflection + project()：

Java · DTO projection
import io.quarkus.hibernate.orm.panache.common.ProjectedFieldName;
import io.quarkus.runtime.annotations.RegisterForReflection;

@RegisterForReflection
public record ProductSummary(
    Long id,
    String name,
    @ProjectedFieldName("price") BigDecimal cost
) {}

// 直接用 project()
List<ProductSummary> summaries = Product.findAll().project(ProductSummary.class).list();

// 帶條件
List<ProductSummary> cheap = Product.find("price < ?1", new BigDecimal("10"))
    .project(ProductSummary.class)
    .list();
✓
效能提示
Projection 不只是省記憶體 ── 它也跳過 entity 載入到 persistence context 的開銷。 回傳的 record 是 immutable DTO，沒有 dirty checking、沒有 lazy proxy。對列表 API 性能提升 2-5 倍。

大量資料：streamAll / stream

批次處理百萬筆資料？listAll() 會 OOM。改用 stream：

Java · 串流處理
@Transactional
public void exportAll(OutputStream out) {
    try (Stream<Product> stream = Product.streamAll()) {
        stream.forEach(p -> {
            writeToCSV(out, p);
            // Hibernate 還是把 entity 留在 persistence context
            // 大量資料建議定期 em.flush() + em.clear()
        });
    }
}
⚠
stream 不是萬靈丹
Hibernate 預設仍會把每個 entity 加入 persistence context，最後還是吃光記憶體。 真正的 batch 場景考慮：
  • 定期 em.flush(); em.clear() 釋放 context
  • 用 StatelessSession（純 SQL、無 dirty check）
  • 分批查詢（依 ID 範圍切片）

關聯與 LAZY

Panache 不改變 JPA 關聯規則 ── @ManyToOne、@OneToMany 寫法相同，預設都是 LAZY：

Java · 關聯
@Entity
public class Product extends PanacheEntity {
    public String name;

    @ManyToOne(fetch = FetchType.LAZY)
    public Category category;

    @OneToMany(mappedBy = "product", cascade = CascadeType.ALL)
    public List<Review> reviews = new ArrayList<>();
}

// JOIN FETCH 仍是好朋友
List<Product> products = Product.find("from Product p join fetch p.category").list();

貫穿專案進度：catalog-service 用 Panache 重寫

Java · Active Record 完整版
@Entity
@Table(name = "products")
public class Product extends PanacheEntity {

    @Column(nullable = false, length = 100)
    public String name;

    @Column(unique = true, length = 20)
    public String sku;

    @Column(nullable = false, precision = 10, scale = 2)
    public BigDecimal price;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "category_id")
    public Category category;

    @Column(name = "created_at", updatable = false)
    public Instant createdAt;

    @Version
    public Long version;

    @PrePersist
    void onCreate() { this.createdAt = Instant.now(); }

    // 查詢方法
    public static Optional<Product> findBySku(String sku) {
        return find("sku", sku).firstResultOptional();
    }

    public static PanacheQuery<Product> search(String q) {
        return find("lower(name) like ?1 or sku = ?2",
            "%" + q.toLowerCase() + "%", q);
    }
}

// REST endpoint 變得超簡潔
@Path("/api/v1/products")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class ProductResource {

    @GET
    public List<Product> list(
            @QueryParam("page") @DefaultValue("0") int page,
            @QueryParam("size") @DefaultValue("20") int size) {
        return Product.findAll().page(page, size).list();
    }

    @GET @Path("/{id}")
    public Product get(@PathParam("id") Long id) {
        return Product.<Product>findByIdOptional(id)
            .orElseThrow(NotFoundException::new);
    }

    @POST @Transactional
    public Response create(@Valid Product p) {
        p.persist();
        return Response.created(URI.create("/api/v1/products/" + p.id)).entity(p).build();
    }

    @DELETE @Path("/{id}") @Transactional
    public Response delete(@PathParam("id") Long id) {
        return Product.deleteById(id)
            ? Response.noContent().build()
            : Response.status(404).build();
    }
}

跟第 15 章純 ORM 的版本比，這份程式碼短了一半，意圖更清楚。

什麼時候不該用 Panache

⚠
Panache 不是萬靈丹
以下情境建議退回原生 Hibernate 或考慮其他工具：
  • 查詢字串太複雜 ── 動態組合多條件，Criteria API 仍更清楚
  • 需要 read-only 高效查詢 ── 考慮 StatelessSession 或 raw JDBC
  • 非典型 entity 模型 ── 例如多 entity hierarchy、複雜 inheritance
  • 團隊熟悉 Spring Data JPA ── Quarkus 有 spring-data-jpa 擴充，可直接用 Spring 風格
  • 已有大量 native SQL 工具 ── 直接用 EntityManager 與 native query 即可
Panache 是工具，不是宗教。

常見陷阱

症狀原因解法
findById(id) 回傳 Object 泛型推斷失敗（static method 限制） Product.<Product>findById(id) 或加變數型別
persist 沒寫入 沒包在 @Transactional 內 方法加 @Transactional
Public field 違反團隊 code style Panache 預設要求 改 Repository 模式或自己寫 getter/setter
List 回傳整個 entity 太慢 缺 projection 用 .project(SummaryDTO.class)
批次更新後 entity state 不對 Product.update(...) 直接發 SQL，不通知 persistence context 批次後呼叫 em.clear() 或重新查詢
跨包 entity 找不到 多 PU 配置遺漏 packages 設 quarkus.hibernate-orm.packages

本章小結

  • Panache 是 Quarkus 為 Hibernate ORM 打造的糖衣層，減少 50–70% 程式碼。
  • 兩種風格：Active Record（extends PanacheEntity，方法在 entity 上）vs Repository（implements PanacheRepository<T>，分離 entity 與操作）。
  • 查詢 API 偵測簡化格式：Product.list("name", "Widget") 自動補成完整 JPQL。
  • 分頁用 PanacheQuery 鏈式 API：.page(Page.of(0,20)).list()。
  • 批次更新／刪除：Product.update(...) / Product.delete(...)。
  • Projection：.project(DTO.class) 只取需要的欄位，列表 API 大幅提速。
  • 客製 ID 用 PanacheEntityBase；混用 Active Record + Repository 也可。
  • 不要在所有場景用 Panache ── 複雜動態查詢、批次大資料、高度客製 entity 可退回原生 Hibernate。
