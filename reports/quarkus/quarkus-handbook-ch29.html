JWT 與 OIDC

Basic auth 是地基 ── 但雲原生世界的 API 不可能要使用者每個 request 都送密碼。 解法是 token-based authentication：登入一次取得 token，之後 request 帶 token 即可。 JWT（JSON Web Token）是 token 格式標準；OIDC（OpenID Connect）是「怎麼安全發 token」的協定。 Quarkus 用 quarkus-oidc 把這套技術變成「加擴充 + 寫 4 行配置」的事。

JWT 結構：三段式信封

JWT 是一段 xxxxx.yyyyy.zzzzz 三段式字串，用 . 分隔。

eyJhbGciOiJSUzI1NiIsInR5cCIgOiAiSldUIn0 ← Header（演算法、token 類型） .eyJzdWIiOiJhbGljZSIsInJvbGVzIjpbInVzZXIiXX0 ← Payload（claims：使用者資料） .QFLrFvkvOFqYx9PqJYJ-IXP2_BcRf1JyJ7hMmPbRgs ← Signature（用 issuer 私鑰簽名）
json · Header 與 Payload 解碼後
// Header
{ "alg": "RS256", "typ": "JWT", "kid": "key-2026-01" }

// Payload
{
  "iss": "https://auth.example.com/realms/catalog",    // issuer：誰發的
  "sub": "alice",                                        // subject：誰
  "aud": "catalog-service",                              // audience：要給誰用
  "exp": 1748707200,                                     // expiration：到期時間
  "iat": 1748703600,                                     // issued at：發出時間
  "groups": ["user", "premium"],                         // 自訂 claim（roles）
  "email": "alice@example.com",
  "preferred_username": "alice"
}
⚠
JWT 是「簽章」不是「加密」
Payload 只是 base64 編碼，任何人都能解碼讀取。
  • 絕對不要把密碼、信用卡、SSN 等敏感資料放進 JWT payload
  • JWT 防的是偽造（簽章驗證），不是偷看
  • 真的需要加密：用 JWE（JSON Web Encryption），但較複雜

OIDC vs JWT：協定 vs 格式

概念角色類比
JWTToken 的格式類似「PDF」── 一種檔案格式
OAuth 2.0「授權」流程的協定類似「快遞流程」── 怎麼把東西安全送達
OIDCOAuth 2.0 上加「身份」層類似「快遞 + 簽收 + 驗身份」

實際關係：OIDC 在 OAuth 2.0 流程結束時，多回傳一個 ID Token（一個 JWT），代表「這就是已驗證的使用者」。

兩個擴充，差別何在

擴充用途典型場景
quarkus-smallrye-jwt本地驗 JWT（public key 寫死在配置）輕量、無 IdP 通訊、單獨 microservice
quarkus-oidcOIDC 客戶端（從 IdP 動態取 JWK）雲原生標準、配 Keycloak/Auth0/Okta
✓
直接用 quarkus-oidc
99% 的場景都該用 quarkus-oidc ── 它支援 token 驗證、自動拿 JWK、refresh、introspection。 smallrye-jwt 只在確定沒有 IdP、token 由你自己簽時才用。本章主要走 OIDC 路線。

Bearer Token 流程

sequenceDiagram
  participant U as User / SPA
  participant API as Quarkus catalog-service
  participant IDP as OIDC Provider
Keycloak

  Note over API,IDP: 啟動時：取 JWK 公鑰
  API->>IDP: GET /.well-known/jwks
  IDP-->>API: { keys: [public keys...] }

  Note over U,IDP: 使用者流程
  U->>IDP: 登入（password / SSO / MFA）
  IDP-->>U: access_token (JWT) + id_token + refresh_token

  U->>API: GET /api/orders
Authorization: Bearer xxx.yyy.zzz
  API->>API: 用 JWK 驗 token 簽章 expiry audience
  API-->>U: 200 OK + 業務資料

圖 29-1 ─ Bearer Token 流程：IdP 簽發 token，Quarkus 用 IdP 的公鑰本地驗證

ℹ︎
為什麼這套設計優雅
  • 無狀態驗證：API 不必呼叫 IdP，本地用公鑰驗即可（除非主動 introspect）
  • 橫向擴展：每個 Pod 都有公鑰，無 session sticky 需求
  • 跨服務：token 可在 catalog-service → inventory-service 透傳
  • JWK 自動 rotation：IdP 換 key 時 Quarkus 自動取新 JWK

Dev Services for Keycloak 自動啟動
dev 模式下，Quarkus 偵測到 quarkus-oidc 但沒設 auth-server-url，自動：
  1. 啟一個 Keycloak 容器
  2. 建一個 realm quarkus

  4. 把 auth-server-url、client-id 等屬性自動注入
本機開發零配置，馬上能跑。

受保護的 endpoint

Java
import jakarta.annotation.security.RolesAllowed;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import org.eclipse.microprofile.jwt.JsonWebToken;

@Path("/api/users")
public class UserResource {

    @Inject JsonWebToken jwt;                    // 注入 JWT 自己

    @GET @Path("/me")
    @RolesAllowed("user")                        // 限 user 角色
    public Map<String, Object> me() {
        return Map.of(
            "username", jwt.getName(),
            "subject", jwt.getSubject(),
            "issuer", jwt.getIssuer(),
            "email", jwt.getClaim("email"),
            "roles", jwt.getGroups(),
            "expiresAt", Instant.ofEpochSecond(jwt.getExpirationTime())
        );
    }
}

實測（dev 模式）

$ # 1. 從 dev 模式啟動的 Keycloak 取 token $ TOKEN=$(curl -s -X POST http://localhost:<keycloak-port>/realms/quarkus/protocol/openid-connect/token \ -d 'grant_type=password&client_id=quarkus-app&username=alice&password=alice' \ | jq -r .access_token) $ # 2. 帶 token 訪問 $ curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/users/me {"username":"alice","subject":"...","email":"alice@example.com","roles":["user"]}

生產配置

application.properties
# 連到正式 IdP
quarkus.oidc.auth-server-url=https://keycloak.example.com/realms/catalog
quarkus.oidc.client-id=catalog-service

# Service mode = 純 API（無 web UI、不做 redirect）
quarkus.oidc.application-type=service

# Roles 來自哪：access token / id token / userinfo
quarkus.oidc.roles.source=accesstoken

# Audience 驗證（防 token 跨服務誤用）
quarkus.oidc.token.audience=catalog-service

# JWK 快取時間（IdP 換 key 後最久幾分鐘才生效）
quarkus.oidc.jwks.cache-size=10
quarkus.oidc.jwks.refresh-internal=30M

JsonWebToken：讀 claims

OIDC extension 自動把驗證後的 token 包成 JsonWebToken，可以注入並讀取所有 claim：

Java · 各種 claim 存取方式
@Inject JsonWebToken jwt;

// 標準 claims（RFC 7519）
String username = jwt.getName();         // sub claim 或 preferred_username
String subject = jwt.getSubject();       // sub
String issuer = jwt.getIssuer();         // iss
Set<String> aud = jwt.getAudience();    // aud
long exp = jwt.getExpirationTime();      // exp（epoch seconds）
Set<String> groups = jwt.getGroups();   // groups（roles）

// 自訂 claim
String email = jwt.getClaim("email");
String tenant = jwt.getClaim("tenant_id");
List<String> perms = jwt.getClaim("permissions");

// 用 ClaimValue 取得（注入 vs 取值）
@Inject @Claim(standard = Claims.email) ClaimValue<String> emailClaim;

roles.source：roles 從哪來

OIDC token 可能把 roles 放在不同地方。Quarkus 預設按以下順序找：

  1. groups claim（MicroProfile JWT 規範）
  2. Keycloak 的 realm_access.roles（realm 全域 roles）
  3. Keycloak 的 resource_access.<client-id>.roles（client 特定 roles）
application.properties · 自訂 roles 來源
# 從 access token 而非 id token 取（預設 service mode 已是 accesstoken）
quarkus.oidc.roles.source=accesstoken

# 自訂 claim 路徑（JSON pointer）
quarkus.oidc.roles.role-claim-path=realm_access/roles

# 或從 userinfo endpoint
# quarkus.oidc.roles.source=userinfo

Authorization Code Flow（Web App）

API 用 Bearer，但傳統 server-rendered web app怎麼整合？用 Authorization Code Flow ── 把使用者導向 IdP 登入，登入完帶 code 回來，Quarkus 自動換成 token。

sequenceDiagram
  participant U as Browser
  participant Q as Quarkus web-app
  participant IDP as Keycloak

  U->>Q: GET /dashboard
  Q-->>U: 302 Redirect to Keycloak login
  U->>IDP: 顯示登入頁
  IDP-->>U: 302 Redirect to /callback?code=abc
  U->>Q: GET /callback?code=abc
  Q->>IDP: POST /token  code abc + secret
  IDP-->>Q: access_token + id_token + refresh_token
  Q->>Q: 存 token 到 encrypted cookie
  Q-->>U: 302 Redirect to /dashboard 帶 session

圖 29-2 ─ Authorization Code Flow：Quarkus 處理整個 redirect 與 token 交換

application.properties
quarkus.oidc.auth-server-url=https://keycloak.example.com/realms/catalog
quarkus.oidc.client-id=catalog-webapp
quarkus.oidc.credentials.secret=${OIDC_CLIENT_SECRET}

# Web app 模式 = 主動處理 redirect、發 cookie
quarkus.oidc.application-type=web-app

# Roles 從 id token 取（預設 web-app mode）
quarkus.oidc.roles.source=idtoken

# 登入後預設跳轉
quarkus.oidc.authentication.redirect-path=/dashboard

# 登出
quarkus.oidc.logout.path=/logout
quarkus.oidc.logout.post-logout-path=/

就這樣。寫的程式碼跟 Bearer mode 完全一樣（注入 JsonWebToken、@RolesAllowed），機制由配置決定。

Token Propagation：服務間轉遞

catalog-service 收到 user 的 token 後要呼叫 inventory-service，怎麼把 token 帶過去？

bash · 加 token 傳播擴充
quarkus extension add oidc-client-reactive-filter
Java · REST Client 自動帶 token
import io.quarkus.oidc.token.propagation.AccessToken;
import org.eclipse.microprofile.rest.client.inject.RegisterRestClient;

@RegisterRestClient(configKey = "inventory-api")
@AccessToken                    // 自動把當前 SecurityIdentity 的 access_token 加到 Authorization header
public interface InventoryClient {
    @GET @Path("/stock/{sku}")
    StockInfo getStock(@PathParam("sku") String sku);
}

原來的 token 自動透傳給下游服務 ── 下游也用 quarkus-oidc，自動驗證並建 SecurityIdentity。整條 chain 都知道是 alice 在操作。

Token Exchange：服務自己取 token

有時下游服務不該收使用者 token，而是想知道「這是 catalog-service 在呼叫」。用 OIDC Client 拿 service token：

bash
quarkus extension add oidc-client
application.properties · Client Credentials Flow
quarkus.oidc-client.auth-server-url=${quarkus.oidc.auth-server-url}
quarkus.oidc-client.client-id=catalog-service-machine
quarkus.oidc-client.credentials.secret=${SERVICE_CLIENT_SECRET}
quarkus.oidc-client.grant.type=client
Java · 注入 OidcClient 主動取 token
@Inject OidcClient oidcClient;

public void callBackgroundJob() {
    Tokens tokens = oidcClient.getTokens().await().indefinitely();
    String accessToken = tokens.getAccessToken();
    // 用這個 token 呼叫下游（背景排程、Webhook 等無使用者場景）
}

測試

不需要起 Keycloak 也能測：用 quarkus-test-oidc-server：

Java · 測試帶 Bearer Token
import io.quarkus.test.common.QuarkusTestResource;
import io.quarkus.test.oidc.server.OidcWiremockTestResource;
import io.smallrye.jwt.build.Jwt;

@QuarkusTest
@QuarkusTestResource(OidcWiremockTestResource.class)
class UserResourceTest {

    @Test
    void me_returnsCurrentUser() {
        String token = Jwt.preferredUserName("alice")
                          .groups(Set.of("user"))
                          .issuer("https://server.example.com")
                          .sign();          // 用測試私鑰簽

        given().auth().oauth2(token)
            .when().get("/api/users/me")
            .then()
                .statusCode(200)
                .body("username", equalTo("alice"));
    }
}

貫穿專案進度：catalog-service 全面 OIDC 化

把第 28 章的 Basic auth 升級成完整 OIDC：

  • 對外 API：bearer token，由 Keycloak 簽發
  • 內部管理 endpoint：仍用 Basic auth（第 28 章），用不同路徑隔離
  • 下游呼叫：InventoryClient + @AccessToken 透傳
  • 背景排程：OidcClient + client credentials flow 取 service token
  • 測試：OidcWiremockTestResource 簽假 token，不依賴 Keycloak

DevOps / SRE 視角

✓
生產上線 checklist
  1. 強制 HTTPS（OIDC 流程中 token 從 query/header 流通）
  2. 設 token.audience：確保 token 是給「這個服務」用的，防 token 跨服務誤用
  3. 短 token expiry（5-15 分鐘）+ refresh token；JWT revoke 困難，短期是補償
  4. JWK rotation 容忍度：jwks.refresh-internal 設 10-30 分鐘
  5. connection-delay：啟動時 IdP 還沒就緒會失敗，設 connection-delay=15S 容忍
  6. 監控 401 / 403 rate：突然飆升可能是 IdP 異常或 attack
  7. client_secret 用 K8s Secret 管理，不要進 image
  8. 每個 service 一個 client，最小權限（不要全 microservice 共用一個 client_id）

常見陷阱

症狀原因解法
啟動報「無法連到 IdP」 K8s 啟動順序：app 比 IdP 早起 設 quarkus.oidc.connection-delay=30S 與 readiness probe
JWT 驗證 401：JWS signature is invalid JWK key 已 rotate、cache 過時 調短 jwks.refresh-internal 或重啟
角色 @RolesAllowed 失效 roles 在 token 中不在預期 claim 設 roles.source 或 role-claim-path
下游服務拒絕 token (invalid audience) 下游驗 aud 失敗 IdP 配置 audience 包含所有微服務 client_id
token 過大 (8KB+) roles 太多塞進 JWT 改用 access token + 服務端查角色，或精簡 roles
code flow 在 K8s 後 redirect URL 是 internal Keycloak 看到的是 internal hostname 啟動 Keycloak 時設 KEYCLOAK_FRONTEND_URL 為對外網址
JWT clock skew 失敗 (token expired) Pod 與 IdP 時間不同步 K8s 開 NTP；設 token.lifespan-grace=30 容忍 30 秒誤差

本章小結

  • JWT 是 token 格式（header.payload.signature）；OAuth 2.0 是授權協定；OIDC 是 OAuth + 身份。
  • JWT 是簽章不是加密 ── 敏感資料禁放 payload。
  • quarkus-oidc vs quarkus-smallrye-jwt：99% 場景用 OIDC。
  • Bearer Token 流程：IdP 簽 token → Quarkus 用 IdP 的 JWK 公鑰本地驗證，無狀態、易橫擴。
  • Dev Services for Keycloak：dev 模式零配置，自動啟 Keycloak 與測試使用者。
  • JsonWebToken 注入後可讀所有 claim：getName()、getGroups()、getClaim("email") 等。
  • roles.source 決定 roles 從哪取（accesstoken / idtoken / userinfo），role-claim-path 可指定 JSON 路徑。
  • Authorization Code Flow（web-app mode）：Quarkus 處理 redirect、token 交換、encrypted cookie 全自動。
  • Token Propagation 用 @AccessToken annotation，REST Client 自動帶 token 給下游。
  • 背景任務用 OidcClient + client credentials 拿 service token。
  • 測試用 OidcWiremockTestResource 簽假 token，不依賴真 Keycloak。
  • SRE 重點：強制 HTTPS、設 audience、短 expiry、JWK rotation、connection-delay、最小權限的 client。
