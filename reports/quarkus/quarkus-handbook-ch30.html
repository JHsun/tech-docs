角色與權限 RBAC

前兩章解決「你是誰」── 本章解決「你能做什麼」。從 Jakarta 標準的 @RolesAllowed 起步， 到 Quarkus 獨有的 @PermissionsAllowed + @PermissionChecker 機制做細粒度授權（如「使用者只能編輯自己的訂單」）， 再到 SecurityIdentityAugmentor 把資料庫的權限動態加進 SecurityIdentity。 本章是 Part VI 的核心 ── 把「拿到 token」變成「真的能保護資料」。

RBAC vs ABAC：兩種授權模型

面向RBAC（角色為本）ABAC（屬性為本）
核心判斷「你的角色能做什麼」「考慮所有屬性後能做什麼」
典型問題admin 能刪所有訂單嗎？使用者能刪自己的訂單嗎？
靜態/動態大致靜態，roles 由 IdP 配置每次判斷，需資源屬性
實作複雜度低 ── annotation 即可中 ── 需 PermissionChecker
Quarkus 實作@RolesAllowed@PermissionsAllowed + @PermissionChecker
✓
兩者通常並用
生產系統幾乎都是 RBAC + ABAC 混合：
  • RBAC 控制粗粒度（admin 才能進 /admin）
  • ABAC 控制細粒度（user 只能改自己的 order）
本章兩個都要會。

Jakarta 標準註解

這四個註解來自 jakarta.annotation.security.*，是 Jakarta EE 標準，Quarkus 完全支援：

註解效果
@PermitAll任何人都能訪問（含匿名）
@DenyAll任何人都不能訪問
@RolesAllowed({"user"})登入且具有任一指定 role 才能訪問
@Authenticated（Quarkus）登入即可，role 不拘
Java · 完整範例
import jakarta.annotation.security.*;
import io.quarkus.security.Authenticated;

@Path("/orders")
public class OrderResource {

    @GET @Path("/public-stats")
    @PermitAll                          // 任何人
    public Stats publicStats() { /* ... */ }

    @GET
    @Authenticated                      // 登入即可
    public List<Order> listOrders() { /* ... */ }

    @POST
    @RolesAllowed({"user", "admin"})    // user 或 admin
    public Order createOrder(...) { /* ... */ }

    @DELETE @Path("/{id}")
    @RolesAllowed("admin")              // 只有 admin
    public Response delete(@PathParam("id") Long id) { /* ... */ }

    @POST @Path("/dangerous-debug")
    @DenyAll                            // 暫時完全禁止
    public void debug() { /* ... */ }
}

類別層級套用

Java · 類別預設 + 方法覆寫
@Path("/admin")
@RolesAllowed("admin")                  // 整個 class 預設限 admin
public class AdminResource {

    @GET public List<User> listUsers() { /* admin only */ }

    @GET @Path("/ping")
    @PermitAll                          // 此方法覆寫，公開
    public String ping() { return "pong"; }
}

Role 從哪來？

第 29 章說過 quarkus.oidc.roles.source。除此之外還有兩個地方可以加 role：

1. 配置層映射

application.properties · 角色屬性表達式
# 把 IdP 的 role 對應到應用內 role
quarkus.oidc.roles.role-claim-path=realm_access/roles

# 用 property expression 讓 dev / prod 不同
%dev.role.user=admin
%prod.role.user=user
# 在 Java 用：@RolesAllowed("${role.user}")

2. SecurityIdentityAugmentor：程式化動態加 role

常見場景：JWT 只有 user role，但你的應用需要更細的「該 user 是否為 premium 會員」── 查 DB 後動態加 role：

Java · SecurityIdentityAugmentor
import io.quarkus.security.identity.SecurityIdentity;
import io.quarkus.security.identity.SecurityIdentityAugmentor;
import io.quarkus.security.identity.AuthenticationRequestContext;
import io.quarkus.security.runtime.QuarkusSecurityIdentity;
import io.smallrye.mutiny.Uni;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class PremiumRoleAugmentor implements SecurityIdentityAugmentor {

    @Inject UserRepository userRepo;

    @Override
    public Uni<SecurityIdentity> augment(SecurityIdentity identity,
                                          AuthenticationRequestContext context) {
        if (identity.isAnonymous()) return Uni.createFrom().item(identity);

        // 查 DB 看是否 premium 會員
        return Uni.createFrom().item(() -> {
            String username = identity.getPrincipal().getName();
            User user = userRepo.findByUsername(username);
            return QuarkusSecurityIdentity.builder(identity)
                .addRoles(user.isPremium() ? Set.of("premium") : Set.of())
                .addAttribute("tenantId", user.getTenantId())
                .build();
        });
    }
}

這個 bean 會被自動發現，每次 authentication 後都會跑。後續 @RolesAllowed("premium") 就能用了。

⚠
Augmentor 是每個 request 都跑
DB 查詢結果記得用 cache（第 20 章 Redis 或 Caffeine）。否則每個 request 都打 DB，效能崩潰。

細粒度授權：@PermissionsAllowed

RBAC 解決不了的問題：「使用者只能編輯自己的訂單」。 這要看 當前使用者與目標資源的關係 ── ABAC 場景。 Quarkus 用 @PermissionsAllowed + @PermissionChecker 解決：

Java · 細粒度授權
import io.quarkus.security.PermissionsAllowed;
import io.quarkus.security.PermissionChecker;
import io.quarkus.security.identity.SecurityIdentity;

@Path("/orders")
public class OrderResource {

    @PUT @Path("/{orderId}")
    @PermissionsAllowed("order:edit")              // 標記需要這個 permission
    public Order update(@PathParam("orderId") Long orderId, OrderDto dto) {
        return orderService.update(orderId, dto);
    }
}

@ApplicationScoped
public class OrderPermissionChecker {

    @Inject OrderRepository orderRepo;

    @PermissionChecker("order:edit")               // 對應上面的 permission 名
    public boolean canEditOrder(SecurityIdentity identity, Long orderId) {
        //  ↑ Quarkus 自動把 @PathParam 名稱對應的引數注入
        String username = identity.getPrincipal().getName();
        Order order = orderRepo.findById(orderId);
        return order != null && order.getOwnerUsername().equals(username);
    }
}
✓
這套設計很優雅的地方
  • 宣告式：endpoint 只寫 @PermissionsAllowed("order:edit")
  • 編譯期綁定：build time 把 permission 字串對應到 method（無 reflection）
  • 自動參數注入：checker 方法的參數名與 endpoint 參數名一致即可
  • 集中化：所有授權邏輯在 PermissionChecker 內，endpoint 保持乾淨
  • 可測試：PermissionChecker 是普通 bean，可直接 unit test

OR vs AND：多個 permission

Java
// 預設 OR：任一 permission 通過即可
@PermissionsAllowed({ "order:edit", "order:admin" })
public Order update(...) { /* ... */ }

// AND：所有 permission 都要通過
@PermissionsAllowed(value = { "order:edit", "tenant:active" }, inclusive = true)
public Order update(...) { /* ... */ }

從 Roles 映射 Permissions

有時 token 帶的是 role 不是 permission，可在配置層映射：

application.properties
# role-policy 把 role 映射成一組 permissions
quarkus.http.auth.policy.role-policy1.roles-allowed=user,admin
quarkus.http.auth.policy.role-policy1.permissions.user=order:read
quarkus.http.auth.policy.role-policy1.permissions.admin=order:read,order:edit,order:delete

# 適用此 policy 的路徑
quarkus.http.auth.permission.orders.paths=/orders/*
quarkus.http.auth.permission.orders.policy=role-policy1

這樣 @PermissionsAllowed("order:edit") 對 admin 自動通過，對 user 自動失敗 ── 不必每個 endpoint 重複寫 role 清單。

HTTP Security Policy：配置式中央授權

第 28 章已介紹過 HTTP Security Policy 的基本用法。這裡完整看一遍授權配置能做什麼：

application.properties · 完整 policy 範例
# 規則 1：所有 /api/* 都要登入
quarkus.http.auth.permission.api.paths=/api/*
quarkus.http.auth.permission.api.policy=authenticated

# 規則 2：/api/admin/* 限 admin role
quarkus.http.auth.policy.admin-only.roles-allowed=admin
quarkus.http.auth.permission.admin.paths=/api/admin/*
quarkus.http.auth.permission.admin.policy=admin-only

# 規則 3：只有 POST / DELETE 限 admin，GET 大家都行
quarkus.http.auth.permission.write-api.paths=/api/products/*
quarkus.http.auth.permission.write-api.policy=admin-only
quarkus.http.auth.permission.write-api.methods=POST,PUT,DELETE

# 規則 4：HealthCheck 完全放行（不論 proactive auth 設定）
quarkus.http.auth.permission.health.paths=/q/health/*
quarkus.http.auth.permission.health.policy=permit
quarkus.http.auth.permission.health.methods=GET

# 規則 5：開發環境的特定 endpoint 放行（生產自動失效）
%dev.quarkus.http.auth.permission.dev-only.paths=/dev/*
%dev.quarkus.http.auth.permission.dev-only.policy=permit
ℹ︎
Policy vs Annotation 的職責分工
  • HTTP Security Policy：粗粒度、配置層、路徑為單位 ── 適合「整個 admin 區段限 admin」
  • @RolesAllowed：細粒度、程式碼層、方法為單位 ── 適合「個別 endpoint 特殊規則」
  • @PermissionsAllowed：超細粒度、需 PermissionChecker ── 適合 ABAC
三者疊加，無衝突。

自訂 HttpSecurityPolicy

需要更動態的授權判斷？實作 HttpSecurityPolicy bean：

Java · 自訂 IP 白名單 policy
import io.quarkus.vertx.http.runtime.security.HttpSecurityPolicy;
import io.smallrye.mutiny.Uni;
import io.vertx.ext.web.RoutingContext;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class IpAllowlistPolicy implements HttpSecurityPolicy {

    private static final Set<String> ALLOWED_IPS = Set.of(
        "10.0.0.0/8", "192.168.0.0/16"
    );

    @Override
    public String name() { return "ip-allowlist"; }

    @Override
    public Uni<CheckResult> checkPermission(RoutingContext request,
                                              Uni<SecurityIdentity> identity,
                                              AuthorizationRequestContext ctx) {
        String clientIp = request.request().remoteAddress().host();
        return matches(clientIp, ALLOWED_IPS)
            ? Uni.createFrom().item(CheckResult.PERMIT)
            : Uni.createFrom().item(CheckResult.DENY);
    }
}
application.properties · 啟用 policy
quarkus.http.auth.permission.internal-only.paths=/internal/*
quarkus.http.auth.permission.internal-only.policy=ip-allowlist

import io.quarkus.test.security.TestSecurity;

@QuarkusTest
class OrderResourceAuthTest {

    @Test

            .when().post("/orders")
            .then().statusCode(200);
    }

    @Test
    @TestSecurity(user = "alice", roles = {"user"})
    void user_cannotDeleteOrder() {
        given().when().delete("/orders/1")
            .then().statusCode(403);
    }

    @Test
    @TestSecurity(user = "admin-bob", roles = {"admin"})
    void admin_canDeleteOrder() {
        given().when().delete("/orders/1")
            .then().statusCode(204);
    }

    @Test

        given().when().get("/orders")
            .then().statusCode(401);
    }
}

貫穿專案進度：catalog-service 完整授權設計

第 28 章 + 第 29 章已搞定 AuthN。現在補完整 AuthZ：

角色定義

角色可做
anonymous瀏覽公開商品、查公開 API
user登入、下訂單、查／改自己的訂單
premium(自動加) 看 premium 商品、優先客服
seller管理自己上架的商品
admin所有商品、所有訂單、系統管理

關鍵 endpoint 授權設計

Java
@Path("/api")
public class CatalogResource {

    // ----- 公開 -----
    @GET @Path("/products")
    @PermitAll
    public List<Product> listProducts() { /* ... */ }

    // ----- 任何登入者 -----
    @POST @Path("/orders")
    @RolesAllowed({"user", "premium"})
    public Order placeOrder(...) { /* ... */ }

    // ----- 細粒度：只能改自己的 -----
    @PUT @Path("/orders/{orderId}")
    @PermissionsAllowed("order:edit")
    public Order updateOrder(@PathParam("orderId") Long orderId, OrderDto dto) {
        return orderService.update(orderId, dto);
    }

    // ----- Seller：只能改自己的商品 -----
    @PUT @Path("/products/{productId}")
    @PermissionsAllowed("product:edit")
    public Product updateProduct(@PathParam("productId") Long productId, ProductDto dto) {
        return productService.update(productId, dto);
    }

    // ----- Admin -----
    @DELETE @Path("/orders/{orderId}")
    @RolesAllowed("admin")
    public Response deleteOrder(@PathParam("orderId") Long orderId) { /* ... */ }
}

@ApplicationScoped
public class CatalogPermissionChecker {

    @Inject OrderRepository orderRepo;
    @Inject ProductRepository productRepo;

    @PermissionChecker("order:edit")
    public boolean canEditOrder(SecurityIdentity id, Long orderId) {
        if (id.hasRole("admin")) return true;        // admin 跳過細粒度
        Order o = orderRepo.findById(orderId);
        return o != null && o.getOwnerUsername().equals(id.getPrincipal().getName());
    }

    @PermissionChecker("product:edit")
    public boolean canEditProduct(SecurityIdentity id, Long productId) {
        if (id.hasRole("admin")) return true;
        if (!id.hasRole("seller")) return false;
        Product p = productRepo.findById(productId);
        return p != null && p.getSellerUsername().equals(id.getPrincipal().getName());
    }
}

這就是「RBAC（admin/seller/user）+ ABAC（ownerUsername 比對）」的標準模式。

DevOps / SRE 視角

✓
授權上線 checklist
  1. 預設拒絕：所有 endpoint 都要明確標 @PermitAll / @RolesAllowed，沒標的視為私密
  2. HTTP Security Policy 鋪底：用路徑前綴擋住未標註的失誤（如 /api/* 一律要登入）
  3. 細粒度比對：永遠用 SecurityIdentity，不要用 request body 裡的 userId（用戶可竄改）
  4. 403 vs 404：未授權應回 404（不洩漏資源存在），不是 403
  5. 稽核 log：所有失敗的授權都記 log，含 username、endpoint、resource ID、IP
  6. 監控 403 飆升：可能是攻擊或權限配置錯誤
  7. Augmentor 加快取：每個 request 都跑 augmentor 會打爆 DB
  8. 定期審視 role 表：權限漸增是 anti-pattern，定期清理
⚠
三個 OWASP Top 10 級別錯誤
  1. IDOR (Insecure Direct Object Reference)：/orders/{id} 只查資料庫，不檢查 ownership ── 任何登入者可看任何訂單
  2. Privilege Escalation：request body 裡帶 role=admin，後端竟然信任
  3. Missing Function Level Access Control：刪除 endpoint 忘記加 @RolesAllowed
都用 PermissionChecker 與預設拒絕原則防範。

常見陷阱

症狀原因解法
@RolesAllowed 標了但仍可匿名訪問 同 class 內部呼叫（CDI proxy 限制） 拆到別的 bean，或用 HTTP Security Policy
JWT 有 role 但 @RolesAllowed 失效 roles 在 token 不在預期 claim 第 29 章設 roles.source 或 role-claim-path
PermissionChecker 沒被呼叫 permission 字串拼錯 嚴格用常數或 enum，避免 typo
PermissionChecker 參數名不匹配 endpoint 用 id，checker 用 orderId 參數名要一致；或用 @PermissionsAllowed(params="orderId") 明確映射
Augmentor 跑了每個 request，DB 打爆 沒加 cache 用 Caffeine 或 Redis cache
測試 @TestSecurity 沒生效 沒裝 quarkus-test-security 加 dependency
HTTP Policy 與 annotation 規則衝突 Policy 先 deny、annotation 想 permit 兩者都要過；統一邏輯方向（policy 寬、annotation 嚴）
使用者可看別人訂單（IDOR） 沒檢查 ownership 用 @PermissionsAllowed + PermissionChecker 強制比對

本章小結

  • RBAC（角色）+ ABAC（屬性） 雙軌是生產系統的標準。
  • Jakarta 標準註解：@PermitAll / @DenyAll / @RolesAllowed / @Authenticated ── 多數場景已夠用。
  • SecurityIdentityAugmentor 在 authentication 後動態加 role/attribute（記得加 cache）。
  • @PermissionsAllowed + @PermissionChecker 是 Quarkus 獨有的細粒度 ABAC 機制 ── build-time 綁定、自動參數注入、集中管理。
  • HTTP Security Policy：配置層中央化授權，適合路徑前綴規則；可映射 role → permissions。
  • 自訂 HttpSecurityPolicy bean 處理動態判斷（IP 白名單、tenant 隔離等）。
  • 測試用 @TestSecurity 跳過 OIDC，直接注入身份。
  • SRE 重點：預設拒絕、永遠用 SecurityIdentity 比對、稽核 log、防 IDOR/privilege escalation。
