Schema 演進

Entity 改了，DB 怎麼跟上？答案不是「generation=update 讓 Hibernate 自動處理」── 那會讓你失去控制、無法 review、無法回滾。 本章介紹兩大主流工具 Flyway 與 Liquibase，並建立一套 「分階段、向後相容、零停機」的 schema 演進方法論。

為什麼不用 Hibernate auto-update

第 15 章已點到，這裡再次重申──

⚠
Hibernate generation 在生產的問題
  • 不可預測：你看不到實際 DDL，只能祈禱 Hibernate 解析正確
  • 不能 review：team 無法 PR review schema 變更
  • 無法回滾：沒有版本紀錄
  • 權限風險：應用帳號需要 DDL 權限，違反最小權限原則
  • 順序依賴：多 Pod 同時啟動可能造成 race condition
  • 不能加註解：comment、partition、index 細節都丟失
生產規則：schema 變更必須是顯式、版本化、可 review、可回滾。

Flyway vs Liquibase 怎麼選

面向FlywayLiquibase
主要語言原生 SQL（每 DB 各寫一份）XML / YAML / JSON（DB 中性抽象）
學習曲線低（會 SQL 就會）中（需熟 changeLog DSL）
跨 DB 支援需各寫一份大部分操作自動跨 DB
內建回滾付費版才有免費內建 rollback 標籤
變更比對無diffChangeLog 自動產生
社群大小大大
典型選擇單一 DB、團隊熟 SQL多 DB 支援、需要回滾
ℹ︎
決策建議
  • 新專案、單一 DB、團隊熟 SQL → 用 Flyway（90% 場景）
  • 遺留專案已用 Liquibase → 繼續用
  • 真的需要跨 DB（PostgreSQL + Oracle） → Liquibase
本章先講 Flyway 詳細、Liquibase 概念為主。

Flyway 起步

bash
quarkus extension add flyway
application.properties · 必要配置
# Hibernate 不再 auto-create，由 Flyway 管 schema
quarkus.hibernate-orm.database.generation=validate

# 應用啟動時自動跑 Flyway migrate
quarkus.flyway.migrate-at-start=true

# 既有 DB 第一次接管（已有 table，但沒有 flyway_schema_history）
quarkus.flyway.baseline-on-migrate=true
quarkus.flyway.baseline-version=1.0.0
quarkus.flyway.baseline-description=Initial baseline

# K8s 環境多 Pod 同時啟動：等 DB 可用
quarkus.flyway.connect-retries=10

# Migration 檔案位置（預設就是這個）
quarkus.flyway.locations=db/migration

第一個 migration 檔

SQL · src/main/resources/db/migration/V1.0.0__init.sql
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    sku         VARCHAR(20) UNIQUE,
    price       NUMERIC(10, 2) NOT NULL,
    category_id BIGINT,
    created_at  TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMP,
    version     BIGINT NOT NULL DEFAULT 0
);

CREATE INDEX idx_products_sku ON products(sku);
CREATE INDEX idx_products_category ON products(category_id);

CREATE TABLE categories (
    id   BIGSERIAL PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL
);

ALTER TABLE products
    ADD CONSTRAINT fk_products_category
    FOREIGN KEY (category_id) REFERENCES categories(id);

命名規則

檔名格式類型用途
V1.0.0__init.sqlVersioned有版本號，只跑一次
V2024.05.15.1__add_status.sqlVersioned（時間戳格式）多分支合併友善
R__create_or_replace_view.sqlRepeatable檔案內容改變就重跑（views、stored procs）
U1.0.0__rollback.sqlUndo（付費版）回滾腳本

核心規則：檔名格式 V<版本>__<描述>.sql，兩個底線分隔。版本號可以用 1、1.0、1.0.0、20240515.1 等任何 dotted 格式，Flyway 按照字典序排序執行。

⚠
命名最常見錯誤
  • 用一個底線（V1_init.sql）→ 解析失敗
  • 檔名有空白（V1__add column.sql）→ 解析失敗
  • 版本號重複（V1__a.sql、V1__b.sql）→ build 拒絕
  • 已部署的 migration 修改檔案內容 → checksum 不符，啟動失敗

Flyway 歷史表

第一次啟動會在 DB 建一張 flyway_schema_history：

db=# SELECT version, description, type, success, installed_on FROM flyway_schema_history; version | description | type | success | installed_on ---------+----------------------+---------+---------+--------------------- 1.0.0 | init | SQL | t | 2026-05-14 10:00:00 1.0.1 | add status column | SQL | t | 2026-05-14 14:30:00 1.1.0 | add review table | SQL | t | 2026-05-15 09:15:00

每筆紀錄包含 checksum；下次啟動會驗證歷史檔案沒被改過。

零停機部署：三階段法

真正的挑戰：新舊版本應用同時運作時，schema 變更不能讓任一邊崩潰。經典策略叫 Expand-Migrate-Contract（也叫 Parallel Change 或 Blue/Green Schema）。

flowchart LR
  classDef phase fill:__SOFT_INFO__,stroke:__INFO__,color:__TXT__,font-weight:bold
  classDef both fill:__SOFT_OK__,stroke:__OK__,color:__TXT__

  E["1. Expand
加新結構

  C["4. Contract
移除舊結構"]:::phase

  E --> D --> M --> C

圖 19-1 ─ Expand-Migrate-Contract 四階段：每個階段新舊版本都能正常運作

實例：把 products.name 拆成 title + subtitle

SQL · V2.0.0__expand_name.sql
-- 加新欄位，允許 NULL（先別 not null）
ALTER TABLE products ADD COLUMN title    VARCHAR(80);
ALTER TABLE products ADD COLUMN subtitle VARCHAR(80);

-- 加 trigger：寫舊 name 自動同步到 title
CREATE OR REPLACE FUNCTION sync_product_name() RETURNS trigger AS $$
BEGIN
    IF NEW.title IS NULL AND NEW.name IS NOT NULL THEN
        NEW.title := NEW.name;
    END IF;
    IF NEW.name IS NULL AND NEW.title IS NOT NULL THEN
        NEW.name := NEW.title;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER products_name_sync
    BEFORE INSERT OR UPDATE ON products
    FOR EACH ROW EXECUTE FUNCTION sync_product_name();

舊應用照常讀寫 name；新欄位空著、由 trigger 維持同步。

Java · 新版本 entity
@Entity
public class Product extends PanacheEntity {
    // 過渡期：兩個都對映
    public String name;       // legacy
    public String title;      // new
    public String subtitle;

    // 寫入時兩邊都填，trigger 也會幫忙
    public void setName(String n) {
        this.name = n;
        if (this.title == null) this.title = n;
    }
}

新版本部署。讀寫雙寫，舊應用仍能繼續跑。

SQL · V2.1.0__backfill_title.sql
-- 把 name 全部 copy 到 title
UPDATE products
   SET title = name
 WHERE title IS NULL;

-- 設 NOT NULL
ALTER TABLE products ALTER COLUMN title SET NOT NULL;

背景作業填資料、確認新欄位完整。應用切換到只讀 title。

SQL · V3.0.0__drop_name.sql
-- 確認沒有應用還用 name 了
DROP TRIGGER products_name_sync ON products;
DROP FUNCTION sync_product_name();
ALTER TABLE products DROP COLUMN name;

所有舊版本下線後，最後一步：移除 name 欄位。

✓
為什麼這麼複雜
K8s rolling update 期間，新舊 Pod 同時存活。若你「直接重命名 column」，舊 Pod 找不到欄位會崩潰。 Expand-Migrate-Contract 雖然分四個 deploy 週期，但保證零停機。 對於小團隊 + 可容忍短暫停機的場景，可以走捷徑：dB 維護視窗內一次 ALTER。

Liquibase 概覽

bash
quarkus extension add liquibase
application.properties
quarkus.liquibase.migrate-at-start=true
quarkus.liquibase.change-log=db/changeLog.xml
XML · db/changeLog.xml
<?xml version="1.0" encoding="UTF-8"?>
<databaseChangeLog
    xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
      http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-4.20.xsd">

  <include file="db/changes/v1.0.0-init.xml"/>
  <include file="db/changes/v1.0.1-add-status.xml"/>
</databaseChangeLog>
XML · v1.0.0-init.xml
<databaseChangeLog ...>
  <changeSet id="1" author="alice">
    <createTable tableName="products">
      <column name="id" type="BIGINT" autoIncrement="true">
        <constraints primaryKey="true" nullable="false"/>
      </column>
      <column name="name" type="VARCHAR(100)">
        <constraints nullable="false"/>
      </column>
      <column name="price" type="DECIMAL(10,2)"/>
    </createTable>

    <rollback>
      <dropTable tableName="products"/>
    </rollback>
  </changeSet>
</databaseChangeLog>

Liquibase 的優勢：

  • 內建 <rollback> 標籤，免費就支援回滾
  • DB 中性：上面這份 changeSet 在 PostgreSQL / MySQL / Oracle 都能跑
  • 豐富 preCondition：「只在 column 不存在時才加」

CI/CD 整合策略

策略 A：應用啟動時 migrate（最簡單）

就是預設的 migrate-at-start=true。應用 Pod 啟動 → 跑 migration → 提供服務。

⚠
適用 / 不適用
  • ✓ 適用：單 Pod、小團隊、簡單應用
  • ✗ 風險：多 Pod 同時啟動會競爭 lock（Flyway 自帶 lock 機制，但有 timeout）
  • ✗ 風險：應用帳號需要 DDL 權限
  • ✗ 風險：migration 慢就拖延啟動 readiness

策略 B：獨立 Migration Job

K8s Job 或 CI pipeline 階段獨立執行 migration，應用本身只 validate：

yaml · K8s pre-deploy migration Job
apiVersion: batch/v1
kind: Job
metadata:
  name: catalog-migrate-v2.0.0
spec:
  template:
    spec:
      containers:
      - name: flyway
        image: flyway/flyway:10
        args: ["migrate"]
        envFrom:
        - secretRef:
            name: flyway-config       # 含 FLYWAY_URL/USER/PASSWORD
        volumeMounts:
        - name: migrations
          mountPath: /flyway/sql
      restartPolicy: OnFailure
application.properties · 應用只做 validation
quarkus.flyway.migrate-at-start=false
quarkus.flyway.validate-at-start=true
quarkus.hibernate-orm.database.generation=validate
✓
為什麼推薦獨立 Job
  • 權限分離：應用帳號只需要 DML，DDL 用獨立 migration 帳號
  • 明確時機：CD pipeline 知道何時 migration 完成才 deploy 應用
  • 無啟動 race：應用 Pod 啟動時 schema 已就緒
  • 失敗顯式：migration 失敗就停在 Job，不會被當成「應用 crashloop」

策略 C：手動執行（高度受控環境）

金融、醫療等高合規場景：

$ mvn flyway:info -Dflyway.configFiles=prod.conf $ mvn flyway:migrate -Dflyway.configFiles=prod.conf Successfully applied 1 migration to schema "public" (execution time 00:00.521s): V2.0.0 - add reviews

DBA 在 maintenance window 親手執行，留下 audit log。

回滾策略

⚠
嚴酷現實：DB 回滾很危險
DDL 大多不可逆（DROP COLUMN 後資料消失）。真正的「回滾」是前進到修正版本，不是真的退回。 建議：
  • 每個 migration 向後相容，部署後監察一段時間再 commit 下一步
  • 對於 DROP，永遠走 Expand-Contract 兩步走
  • Liquibase 的 rollback 標籤只對簡單 DDL 有效，業務資料還是要備份
  • 真的緊急 → 從 DB backup 還原（接受資料丟失）

DevOps / SRE 視角

✓
生產 Schema 演進 Checklist
  1. Hibernate 設 validate，不要 update / create
  2. Migration 獨立 Job 跑（推薦），或 migrate-at-start 但配 lock timeout
  3. 應用帳號最小權限：只 DML，DDL 另立帳號
  4. 所有變更走 Expand-Contract：DROP 前先讓所有應用版本都不再用
  5. 慎用 transaction-heavy DDL：PostgreSQL 中 ALTER TABLE 取大 lock
  6. 大表加欄位：先 NULL 允許 + DEFAULT NULL 快、之後再加 NOT NULL
  7. 大表加 index：用 CREATE INDEX CONCURRENTLY（PostgreSQL）
  8. 監控 migration 時間：CI 報警長於 10 秒的 migration
  9. 失敗策略：migration 失敗時 K8s Job 顯示在 dashboard、不要被當作應用問題
  10. 回滾以「前進」為主，DB 真正 rollback 是最後手段

常見陷阱

症狀原因解法
啟動失敗：checksum mismatch 已部署的 migration 檔案被改動 建新版本檔案；緊急 flyway:repair
多 Pod 啟動失敗 同時跑 Flyway lock 競爭 用獨立 Job、或設 quarkus.flyway.connect-retries
Migration 「跳過」 檔名格式錯（單底線、空白） 檢查命名 V<ver>__<desc>.sql
既有 DB 無法接管 沒有 flyway_schema_history 設 baseline-on-migrate=true
新欄位 default 跑很慢 大表 ALTER 全表掃描 分兩步：先 ADD COLUMN NULL；UPDATE; ALTER SET NOT NULL
應用報「unknown column」 新版部署但 migration 沒跑 檢查 Job 順序：先 migration 再 deploy

本章小結

  • 生產 schema 不要靠 Hibernate auto-update；用 Flyway 或 Liquibase 顯式版本化。
  • Hibernate 設 generation=validate，schema 由 migration 工具管。
  • Flyway 命名規則：V<version>__<description>.sql，兩個底線。
  • Repeatable migration（R__...）適合 views、stored procs、dev seed data。
  • 既有 DB 接管：baseline-on-migrate=true + baseline-version。
  • 零停機部署：Expand-Migrate-Contract 四階段，每階段新舊版本都能運作。
  • Liquibase 優勢：XML / YAML 跨 DB、內建 <rollback>；Flyway 優勢：原生 SQL 簡單。
  • 多 datasource migration：屬性插入 datasource 名稱（quarkus.flyway.analytics.locations）。
  • CI/CD 策略：應用啟動 migrate（小團隊）vs 獨立 K8s Job（推薦）。
  • 「回滾」實務上是「前進到修正版本」，DDL 不可逆。
  • 大表 ALTER：分階段（先 NULL 允許 → 填資料 → NOT NULL），index 用 CONCURRENTLY。
