Quarkus REST

Quarkus REST（前身 RESTEasy Reactive）是 Quarkus 預設的 Jakarta REST 實作， 建立在 Vert.x 與 Mutiny 之上，同時支援命令式與響應式寫法。 它不是「只給響應式專案用」的工具 ── 90% 的命令式 REST API 也都應該用它。

Quarkus REST 是什麼

從 Quarkus 3.9 起，原本叫 RESTEasy Reactive 的擴充正式改名為 Quarkus REST。 改名原因：太多人誤以為它只能用於響應式工作負載，實際上它對命令式同樣優秀，甚至更省資源。

ℹ︎
artifact 變化
  • 舊：quarkus-resteasy-reactive、quarkus-resteasy-reactive-jackson
  • 新：quarkus-rest、quarkus-rest-jackson
Maven relocation 已就位，quarkus update 會自動處理。

三套 REST 實作的選擇

實作artifact建議使用情境
Quarkus REST（推薦）quarkus-rest所有新專案，命令式 + 響應式都優秀
RESTEasy Classic（舊）quarkus-resteasy從舊版升級且暫時無法重構的情境
純 Vert.x Webquarkus-vertx-web需極致效能，且能接受 Vert.x 風格 API

你的第一個 REST endpoint

專案要加擴充：

bash
quarkus extension add rest rest-jackson
Java · 基本 GET endpoint
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/products")
public class ProductResource {

    @GET
    @Produces(MediaType.APPLICATION_JSON)
    public List<Product> listAll() {
        return List.of(
            new Product(1L, "Widget", new BigDecimal("9.99")),
            new Product(2L, "Gadget", new BigDecimal("19.99"))
        );
    }
}

啟動後測試：

$ curl http://localhost:8080/products [{"id":1,"name":"Widget","price":9.99},{"id":2,"name":"Gadget","price":19.99}]
✓
三件事自動發生了
  1. Quarkus 在編譯期掃到 @Path，註冊路由
  2. 看到 @Produces(JSON)，自動裝配 Jackson 序列化
  3. 看到回傳型別 List<Product>，自動序列化為 JSON 陣列
沒有任何 reflection、沒有任何 runtime 解析，所有路由在 mvn package 階段就決定好了。

Jakarta REST 核心註解

註解用途
@Path定義 URL 路徑（class 或 method）
@GET @POST @PUT @DELETE @PATCH @HEADHTTP 方法
@Produces回應的 Content-Type
@Consumes接受的 Content-Type
@PathParam從 URL 路徑取參數：/products/{id}
@QueryParam從 query string 取參數：?page=1
@HeaderParam從 HTTP header 取值
@CookieParam從 cookie 取值
@FormParam從 form 取值
@RestForm ⭐Quarkus REST 專屬，更彈性的 form binding
@DefaultValue當參數缺失時的預設值
@Context注入 UriInfo、HttpHeaders、SecurityContext 等

完整 CRUD 範例

Java · 完整 CRUD ProductResource
@Path("/products")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class ProductResource {

    private final ProductService service;

    public ProductResource(ProductService service) {
        this.service = service;
    }

    @GET
    public List<Product> list(
            @QueryParam("page") @DefaultValue("0") int page,
            @QueryParam("size") @DefaultValue("20") int size) {
        return service.list(page, size);
    }

    @GET
    @Path("/{id}")
    public Product get(@PathParam("id") Long id) {
        return service.findById(id)
            .orElseThrow(() -> new NotFoundException("產品不存在：" + id));
    }

    @POST
    public Response create(@Valid Product product, @Context UriInfo uri) {
        Product created = service.create(product);
        URI location = uri.getAbsolutePathBuilder()
            .path(String.valueOf(created.id()))
            .build();
        return Response.created(location).entity(created).build();
    }

    @PUT
    @Path("/{id}")
    public Product update(@PathParam("id") Long id, @Valid Product product) {
        return service.update(id, product);
    }

    @DELETE
    @Path("/{id}")
    public Response delete(@PathParam("id") Long id) {
        service.delete(id);
        return Response.noContent().build();
    }
}

注意幾個設計細節：

  • 類別層級的 @Produces / @Consumes 套用到所有方法，省去重複
  • Constructor 注入 service（不是 @Inject 欄位）
  • POST 回傳 Response：可加 Location header 符合 REST 慣例
  • @Valid 自動觸發 Bean Validation（第 11 章詳述）

執行緒模型：本章最關鍵的部分

Quarkus REST 預設執行在 Vert.x event-loop thread，這帶來極高 throughput，但有個鐵律：

⚠
不能在 event-loop 阻塞
JDBC、Thread.sleep()、阻塞式 HTTP client ── 這些都會卡住 event-loop， 導致應用整體 throughput 崩潰。Quarkus REST 提供三種方式跳出這個限制。

方式 A：Reactive 回傳型別（首選）

回傳 Uni<T> 或 Multi<T>，Quarkus REST 知道你在做非阻塞操作：

Java · Reactive 寫法
@GET
@Path("/{id}")
public Uni<Product> get(@PathParam("id") Long id) {
    return service.findById(id);     // 回傳 Uni<Product>
}

@GET
public Multi<Product> stream() {
    return service.streamAll();      // 多筆，可做 Server-Sent Events
}

方式 B：@Blocking 註解

明確告訴 Quarkus「這個方法會阻塞，幫我 dispatch 到 worker thread」：

Java · @Blocking
import io.smallrye.common.annotation.Blocking;

@GET
@Path("/{id}")
@Blocking
public Product get(@PathParam("id") Long id) {
    return service.findById(id);     // JDBC 阻塞操作，安全
}

方式 C：@RunOnVirtualThread（JDK 21 最佳實踐）

JDK 21 的虛擬執行緒解決了「阻塞代碼也能高 throughput」的兩難。Quarkus 完整支援：

Java · @RunOnVirtualThread
import io.smallrye.common.annotation.RunOnVirtualThread;

@GET
@Path("/{id}")
@RunOnVirtualThread
public Product get(@PathParam("id") Long id) {
    return service.findById(id);     // 在 virtual thread 跑，阻塞無代價
}

三種方式對照

方式所在執行緒容量適用
預設（event-loop）少量 event-loop thread幾萬 req/s純 reactive、純 CPU 計算
@Blocking有限的 worker pool~幾百 req/s少量阻塞呼叫，JDBC 等
@RunOnVirtualThread幾乎無限的 virtual thread幾千 req/s阻塞操作為主、JDK 21+
Uni / Multievent-loop幾萬 req/sI/O 密集的響應式工作

JSON 處理：Jackson vs JSON-B

Quarkus REST 支援兩種 JSON 序列化器：

bash · 加擴充
quarkus extension add rest-jackson
Java · Jackson DTO
import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.annotation.JsonIgnore;

public record Product(
    Long id,
    String name,
    @JsonProperty("unit_price") BigDecimal price,
    @JsonIgnore String internalCode
) {}
bash
quarkus extension add rest-jsonb
Java · JSON-B DTO
import jakarta.json.bind.annotation.JsonbProperty;
import jakarta.json.bind.annotation.JsonbTransient;

public record Product(
    Long id,
    String name,
    @JsonbProperty("unit_price") BigDecimal price,
    @JsonbTransient String internalCode
) {}
ℹ︎
該選哪個？
Jackson：生態最廣（Spring Boot 預設）、功能最完整、社群最大。
JSON-B：Jakarta EE 標準、設定更簡單。
新專案建議 Jackson，遷移舊 Jakarta EE 系統可考慮 JSON-B。

客製化 Jackson

application.properties
quarkus.jackson.fail-on-unknown-properties=false
quarkus.jackson.write-dates-as-timestamps=false
quarkus.jackson.serialization-inclusion=non-null
quarkus.jackson.timezone=Asia/Taipei

或在程式中提供客製 ObjectMapper：

Java · 客製 ObjectMapper
import io.quarkus.jackson.ObjectMapperCustomizer;

@Singleton
public class CustomObjectMapper implements ObjectMapperCustomizer {
    @Override
    public void customize(ObjectMapper mapper) {
        mapper.registerModule(new JavaTimeModule());
        mapper.setPropertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE);
    }
}

例外處理

傳統做法是用 ExceptionMapper，Quarkus REST 提供更簡潔的 @ServerExceptionMapper：

Java · @ServerExceptionMapper
import org.jboss.resteasy.reactive.server.ServerExceptionMapper;

public class ProductExceptionMappers {

    @ServerExceptionMapper
    public RestResponse<ErrorResponse> productNotFound(ProductNotFoundException ex) {
        return RestResponse.status(Response.Status.NOT_FOUND,
            new ErrorResponse("PRODUCT_NOT_FOUND", ex.getMessage()));
    }

    @ServerExceptionMapper
    public Response constraintViolation(ConstraintViolationException ex) {
        Map<String, String> errors = ex.getConstraintViolations().stream()
            .collect(Collectors.toMap(
                v -> v.getPropertyPath().toString(),
                ConstraintViolation::getMessage));
        return Response.status(400).entity(errors).build();
    }
}

public record ErrorResponse(String code, String message) {}
✓
為什麼 @ServerExceptionMapper 比較好
  • 不需實作 ExceptionMapper<T> 介面
  • 可放在 Resource class 內，作用域只限該 class
  • 可注入其他 Bean（透過 method 參數）
  • 支援回傳 Uni<Response>，非阻塞處理錯誤

Request / Response Filters

需要在所有請求前後做事（鑑權、log、CORS）？用 @ServerRequestFilter / @ServerResponseFilter：

Java · 攔截器
import org.jboss.resteasy.reactive.server.ServerRequestFilter;
import org.jboss.resteasy.reactive.server.ServerResponseFilter;

@ApplicationScoped
public class LoggingFilters {

    @ServerRequestFilter
    public void logRequest(ContainerRequestContext ctx) {
        Log.infof("→ %s %s", ctx.getMethod(), ctx.getUriInfo().getPath());
    }

    @ServerResponseFilter
    public void logResponse(ContainerRequestContext req, ContainerResponseContext res) {
        Log.infof("← %s %s : %d", req.getMethod(), req.getUriInfo().getPath(), res.getStatus());
    }
}

Multipart 與檔案上傳

Quarkus REST 的 multipart 處理與 RESTEasy Classic 完全不同，更現代：

Java · 接收上傳
import org.jboss.resteasy.reactive.RestForm;
import org.jboss.resteasy.reactive.multipart.FileUpload;

@POST
@Path("/upload")
@Consumes(MediaType.MULTIPART_FORM_DATA)
public Response upload(
        @RestForm("file") FileUpload file,
        @RestForm("description") String description) {

    Log.infof("收到 %s (%d bytes) - %s",
        file.fileName(), file.size(), description);

    Path saved = Paths.get("/uploads", file.fileName());
    Files.copy(file.uploadedFile(), saved, StandardCopyOption.REPLACE_EXISTING);

    return Response.ok().build();
}

Server-Sent Events（SSE）

用 Multi<T> 自然支援串流：

Java · SSE 串流
@GET
@Path("/events")
@Produces(MediaType.SERVER_SENT_EVENTS)
public Multi<PriceUpdate> streamPrices() {
    return Multi.createFrom().ticks().every(Duration.ofSeconds(1))
        .map(tick -> new PriceUpdate("BTC", randomPrice()));
}

客戶端用 JavaScript 接收：

JavaScript
const es = new EventSource('/events');
es.onmessage = (e) => console.log(JSON.parse(e.data));

從 RESTEasy Classic 遷移

若你有舊的 RESTEasy Classic 專案要遷移，幾個關鍵點：

項目RESTEasy ClassicQuarkus REST
artifactquarkus-resteasyquarkus-rest
JSONquarkus-resteasy-jacksonquarkus-rest-jackson
Clientquarkus-resteasy-clientquarkus-rest-client
多型 @Path 優先順序依宣告順序更嚴格的 spec-compliant 比對
自訂 annotation支援 org.jboss.resteasy.annotations.*不支援，改用 org.jboss.resteasy.reactive.*
Multipart APIMultipartFormDataInput@RestForm + FileUpload
預設執行緒worker thread（阻塞）event-loop（非阻塞）
⚠
遷移後檢查清單
  1. 所有 JDBC、JPA、舊版 HTTP client 呼叫加 @Blocking 或 @RunOnVirtualThread
  2. 檢查自訂 ExceptionMapper 是否仍生效
  3. 跑整套整合測試，特別注意 path 匹配的差異
  4. 把 multipart endpoint 改用新 API

貫穿專案進度：catalog-service REST 完整版

把累積的 Service、Repository、ConfigMapping 接上 REST 層：

Java · 完整 ProductResource（含三種執行緒模式）
@Path("/products")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class ProductResource {

    private final ProductService service;

    public ProductResource(ProductService service) {
        this.service = service;
    }

    // 版本 1：阻塞，傳統寫法
    @GET
    @Path("/blocking/{id}")
    @Blocking
    public Product getBlocking(@PathParam("id") Long id) {
        return service.findById(id);
    }

    // 版本 2：虛擬執行緒（JDK 21）
    @GET
    @Path("/{id}")
    @RunOnVirtualThread
    public Product get(@PathParam("id") Long id) {
        return service.findById(id);
    }

    // 版本 3：響應式
    @GET
    @Path("/reactive/{id}")
    public Uni<Product> getReactive(@PathParam("id") Long id) {
        return service.findByIdReactive(id);
    }

    @ServerExceptionMapper
    public RestResponse<ErrorResponse> notFound(ProductNotFoundException ex) {
        return RestResponse.status(Response.Status.NOT_FOUND,
            new ErrorResponse("PRODUCT_NOT_FOUND", ex.getMessage()));
    }
}

DevOps / SRE 視角

選對執行緒模型 = 省一半 Pod

實際案例：某 catalog API，5,000 req/s 流量。

執行緒模型需要 Pod 數P99 延遲
RESTEasy Classic（worker pool）10 個180ms
Quarkus REST + @Blocking10 個150ms
Quarkus REST + @RunOnVirtualThread（JDK 21）4 個50ms
Quarkus REST + Uni（完全 reactive）3 個30ms
ℹ︎
SRE 行動項目
  1. 盤點現有 endpoint 的執行緒模型，找出仍走 @Blocking 的部分
  2. 用 JDK 21 + @RunOnVirtualThread 替換高流量阻塞 endpoint
  3. I/O 密集且能完全非阻塞的，改 Reactive（最高效）
  4. 定期看 metrics：event-loop 佔用率、worker pool 隊列長度

常見陷阱

症狀原因解法
warn：blocked event loop 在預設模式做了阻塞操作 加 @Blocking 或改為響應式
JSON 欄位名稱不對 Jackson 命名策略未配置 用 @JsonProperty 或全域命名策略
404 但路徑看起來對 方法上 @Path 與 class 重複 class @Path("/products") + method @Path("/{id}")
POST 收不到 body 缺 @Consumes 類別或方法加 @Consumes(MediaType.APPLICATION_JSON)
遷移後 ExceptionMapper 沒生效 用了 RESTEasy Classic 的舊 annotation 改用 @ServerExceptionMapper
SSE 客戶端立刻斷線 缺 @Produces(SERVER_SENT_EVENTS) 或回傳型別不是 Multi 檢查兩者皆正確

本章小結

  • Quarkus REST（前身 RESTEasy Reactive）是 Quarkus 預設的 REST 實作，命令式與響應式同樣強。
  • 使用 Jakarta REST 標準註解，與 Spring Web 截然不同的設計理念。
  • 預設執行在 event-loop thread，阻塞操作需用 @Blocking 或 @RunOnVirtualThread。
  • JSON 處理：Jackson（推薦）或 JSON-B，透過 quarkus.jackson.* 配置或 ObjectMapperCustomizer 客製。
  • 例外處理用 @ServerExceptionMapper 取代傳統 ExceptionMapper<T>。
  • Multipart 用全新的 @RestForm + FileUpload API，更簡潔。
  • SSE 透過 Multi<T> 自然支援，搭配 @Produces(SERVER_SENT_EVENTS)。
  • 從 RESTEasy Classic 遷移：artifact 改名、執行緒模型變更、Multipart 與 ExceptionMapper API 不同。
