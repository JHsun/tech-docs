Chapter 31 · Part VI

Keycloak 整合

第 29 章已經跑通 OIDC，但 IdP 一直是黑盒。本章把 Keycloak 攤開來看 ── CNCF 級的開源 IdP， 懂它的 realm / client / role / user 治理結構、知道怎麼用 Realm JSON 把配置版本化、 用 quarkus-keycloak-admin-client-reactive 程式化建立使用者， 再進階到 quarkus-keycloak-authorization 把授權完全外包給 Keycloak。 一個 Keycloak 集群可以承載一個公司的所有 microservice 認證 ── 這就是「centralized identity」的力量。

為什麼 Keycloak 而非 Auth0 / Okta

面向Keycloak（OSS）Auth0 / Okta（SaaS）
授權Apache 2.0，CNCF Incubating商業，按使用者數計費
部署自我託管（K8s / Docker / bare metal）SaaS，免維護
客製化完整源碼可改，extension API限制在 SaaS 提供的功能內
資料主權使用者資料在自己 DB使用者資料在廠商雲端
成本授權 0，但要付 SRE 維運License 費隨使用者數線性成長
合規場景HIPAA / 金融 / 政府最常用多數 SaaS 場景
✓
Keycloak 的兩個甜蜜點
  1. 規模化省錢：一萬以上使用者，自我託管 TCO 明顯低於 SaaS
  2. 合規/資料主權：法規或客戶要求「使用者資料不離開境內」
若無這兩個誘因，初創公司用 Auth0 / Okta 更省心。

Realm Roles vs Client Roles

Keycloak 有兩層 role：

  • Realm role：整個 realm 通用（如 user、admin）
  • Client role：只在特定 client 內有效（如 catalog-backend.seller）

Quarkus 預設讀 realm role 與當前 client 的 client role。第 29 章的 roles.source 設定就是控制這個。

Dev Services 帶你一站到位

第 29 章已用過 Dev Services for Keycloak。回顧它預設做什麼：

  • 啟動 Keycloak 26.x 容器（隨機 port）
  • 建立 quarkus realm
  • 建立 quarkus-app client（secret secret）
  • 建立兩個使用者：alice（user role）、bob（user role）、admin（admin role）
  • 注入 OIDC 配置屬性

匯入自訂 Realm

真實專案不滿足於預設使用者。把你的 realm.json 放到 src/main/resources/ 並指向它：

application.properties
%dev.quarkus.keycloak.devservices.realm-path=catalog-realm.json
%dev.quarkus.keycloak.devservices.create-realm=false

# 也可固定 port，方便 SPA 端寫死 redirect URL
%dev.quarkus.keycloak.devservices.port=8180

產生 realm.json

從現有 Keycloak 匯出：

bash · 用 kc.sh 匯出
# 進入容器
kubectl exec -it keycloak-0 -- /bin/bash

# 匯出（含 users）
/opt/keycloak/bin/kc.sh export \
  --dir /tmp/export \
  --realm catalog \
  --users realm_file

# 從容器拷出來
kubectl cp keycloak-0:/tmp/export/catalog-realm.json ./catalog-realm.json
⚠
Realm JSON 是配置的 single source of truth
把 catalog-realm.json commit 到 Git ── 它包含 realm 結構、所有 client、所有 role、（可選）測試使用者。 生產環境用 CI/CD 自動匯入，禁止在生產 Keycloak 手動改，避免 drift。 敏感資訊（client secret、user 密碼）用 placeholder，由 K8s Secret 注入。

Client 類型：選對才安全

類型有 client secret適用
Confidential有後端服務、server-side web app（catalog-backend）
Public無SPA、行動 app（任何人都能看到 client_id）
Bearer-only無純驗 token 的 API（不主動發起 login）
⚠
SPA 必須是 Public client + PKCE
SPA / 行動 app 不能存 secret（任何人 view source 都能看到）。
用 Public client + PKCE（Proof Key for Code Exchange）── code 換 token 時用一次性 verifier 保護，無 secret 也安全。
Quarkus OIDC 自動處理 PKCE，不需額外配置（前提：client 端啟用）。

Keycloak Admin Client：程式化管理

常見場景：新使用者註冊時，業務邏輯要在 Keycloak 建一個 user。用 quarkus-keycloak-admin-client-reactive：

bash
quarkus extension add keycloak-admin-client-reactive
application.properties
quarkus.keycloak.admin-client.server-url=https://keycloak.example.com
quarkus.keycloak.admin-client.realm=catalog
quarkus.keycloak.admin-client.client-id=catalog-backend
quarkus.keycloak.admin-client.client-secret=${KC_ADMIN_SECRET}
quarkus.keycloak.admin-client.grant-type=CLIENT_CREDENTIALS
Java · 建立使用者
import org.keycloak.admin.client.Keycloak;
import org.keycloak.representations.idm.UserRepresentation;
import org.keycloak.representations.idm.CredentialRepresentation;

@ApplicationScoped
public class UserProvisioningService {

    @Inject Keycloak keycloak;        // Quarkus 自動注入已認證的 client

    public String createUser(SignupRequest req) {
        UserRepresentation user = new UserRepresentation();
        user.setUsername(req.username());
        user.setEmail(req.email());
        user.setEmailVerified(false);
        user.setEnabled(true);

        CredentialRepresentation cred = new CredentialRepresentation();
        cred.setType(CredentialRepresentation.PASSWORD);
        cred.setValue(req.password());
        cred.setTemporary(true);      // 首次登入強制改密碼
        user.setCredentials(List.of(cred));

        Response response = keycloak.realm("catalog").users().create(user);
        if (response.getStatus() != 201) {
            throw new WebApplicationException(response);
        }
        // 回傳新 user 的 ID（從 Location header 抓）
        String location = response.getHeaderString("Location");
        return location.substring(location.lastIndexOf('/') + 1);
    }

    public void assignRole(String userId, String roleName) {
        RoleRepresentation role = keycloak.realm("catalog").roles().get(roleName).toRepresentation();
        keycloak.realm("catalog").users().get(userId).roles().realmLevel().add(List.of(role));
    }
}
⚠
Service Account 需要 realm-management roles
用 client_credentials 呼叫 admin API，client 的 Service Account 必須被指派 realm-management client 的對應 role：
  • view-users ── 只讀
  • manage-users ── 建立／修改 user
  • view-realm ── 讀 realm 設定
  • manage-realm ── 改 realm 設定（很危險，少用）
最小權限原則 ── 只給需要的，不要直接給 realm-admin。

quarkus-keycloak-authorization：把授權完全外包

前兩章用 @RolesAllowed / @PermissionsAllowed 把授權邏輯寫在 Quarkus 程式碼。 但有些場景要授權規則由非開發者管理（如業務 admin 介面動態配置「哪個產品線只給哪個區域」）。 quarkus-keycloak-authorization 把整套 RBAC/ABAC 邏輯外包給 Keycloak Authorization Services。

圖 31-2 ─ Quarkus 啟用 policy enforcer，每個 request 委派 Keycloak 做授權判斷

啟用

bash
quarkus extension add keycloak-authorization
Java · 完全不需要 @RolesAllowed
@Path("/api/products")
public class ProductResource {

    @GET @Path("/{id}")
    public Product get(@PathParam("id") Long id) {
        // 沒有 annotation！授權由 Keycloak 動態決定
        return productService.findById(id);
    }

    @DELETE @Path("/{id}")
    public Response delete(@PathParam("id") Long id) {
        productService.delete(id);
        return Response.noContent().build();
    }
}

Keycloak 端配置：

  1. Client → Authorization 分頁（啟用後出現）
  2. 定義 Resources：/api/products/* ＝ "products"
  3. 定義 Scopes：read / write / delete
  4. 定義 Policies：「user role 的 policy」、「admin role 的 policy」、「JS-based policy」（ABAC）
  5. 定義 Permissions：「products + delete scope 要 admin policy」
✓
這套設計的最大好處
  • 授權規則改變不需要重部署業務應用
  • 非開發者（業務 admin）可在 Keycloak UI 改 policy
  • 多服務共享同一套授權策略
  • 稽核集中（誰改了 policy 都有 log）
代價：每個 request 都要查 Keycloak（多一次網路往返）。生產用 token cache 與 policy enforcer 內建快取緩解。

生產 HA 部署

✓
Keycloak 生產 checklist
  1. 外部 DB：用 PostgreSQL，絕不用內建 H2（生產失敗保證）
  2. HA cluster：3+ replica，用 K8s Operator（keycloak-operator）或 Helm chart
  3. Infinispan distributed cache：跨 node 共享 session（K8s 內網用 JGroups）
  4. External cache（remote Infinispan）給多 region
  5. Frontend URL：KC_HOSTNAME 設成對外 URL，避免 token 內 issuer 不正確
  6. TLS 終端：通常在 Ingress / Service Mesh，內部 Keycloak 跑 HTTP
  7. 每日備份：PostgreSQL dump，realm.json export 雙軌
  8. Admin Console 隔離：用 KC_HTTP_RELATIVE_PATH=/auth，admin endpoint 限內網訪問
  9. 監控：JVM metrics、login success/fail rate、session count、cache hit rate
  10. 升級節奏：跟 Keycloak 主要版本（每年），先在 staging 跑兩週

進階：PAR（Pushed Authorization Requests）

標準 OIDC code flow 把所有授權參數放在瀏覽器 URL ── 可能被 log / 第三方截獲。 PAR（RFC 9126）改成：client 先把參數從後端 push 給 IdP，拿一個短期 request_uri，再用這個 URI 啟動瀏覽器流程。

application.properties · 啟用 PAR
quarkus.oidc.authentication.pushed-authorization-requests=true

Keycloak 26+ 預設支援。Quarkus 自動從 OIDC discovery 偵測 pushed_authorization_request_endpoint 並使用。

ℹ︎
PAR 適合的場景
  • 金融、健保、政府等高合規環境
  • FAPI（Financial-grade API）規範要求
  • 實作 SSO，多個 client 共用 IdP，需減少瀏覽器歷史記錄敏感資料
一般電商 / SaaS 應用，標準 code flow + PKCE 已足夠。

常見陷阱

症狀原因解法
Token issuer 不對 / 驗證失敗 K8s 內部 hostname 與對外 URL 不同 設 KC_HOSTNAME 為對外 URL
Admin Client 403 forbidden Service Account 沒被指派 realm-management role 到 Client → Service Account Roles 加上 manage-users 等
Realm JSON 匯入失敗 已存在同名 realm 用 --override 或先刪掉
升 Keycloak 大版本後 session 全清 Infinispan cache 不相容 滾動升級用 Operator；或接受 session reset 並通知使用者
SPA 登入後 CORS 報錯 Web Origins 沒設 Client → Settings → Web Origins 加 SPA 網域
quarkus-keycloak-authorization 每 request 慢 沒啟用 token cache 設 quarkus.keycloak.policy-enforcer.lazy-load-paths=true
JS policy 在 Keycloak 27+ 報「disabled by default」 Keycloak 27 起 JS policies 安全考量預設關閉 啟動 --features=scripts，或改用其他 policy 類型

本章小結

  • Keycloak 是 CNCF Incubating 開源 IdP，與 Auth0/Okta 競爭，甜蜜點在大規模 + 合規場景。
  • 四層治理：Realm → Client → Role → User；realm 是完全隔離單位。
  • 兩層 role：realm role（全 realm 通用）vs client role（只在特定 client 內）。
  • Dev Services for Keycloak 自動啟容器、建預設 realm／users，零配置上手。
  • Realm JSON 是配置的 single source of truth：commit 到 Git、CI/CD 匯入、secret 用 placeholder。
  • Client 類型三選：Confidential（後端）、Public + PKCE（SPA／行動）、Bearer-only（純驗 API）。
  • Keycloak Admin Client 程式化建 user / 指派 role；Service Account 需要 realm-management roles（最小權限）。
  • quarkus-keycloak-authorization：授權邏輯完全外包給 Keycloak，業務應用無 @RolesAllowed。代價：每 request 多一次驗證往返（可 cache 緩解）。
  • PAR（Pushed Authorization Requests）為高合規場景進一步硬化 OIDC 流程。
  • SRE 重點：外部 PostgreSQL、HA cluster + Operator、設正確 KC_HOSTNAME、每日備份、policy 升級節奏。
