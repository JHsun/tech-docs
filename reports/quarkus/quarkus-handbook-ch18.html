幕後英雄：Narayana

當你寫 @Transactional 時，背後是 Narayana 交易管理器在運作。它由 quarkus-narayana-jta 擴充提供，Hibernate ORM 已自動引入，多數情況不需手動加。

bash · 不用 Hibernate 時才需手動加
quarkus extension add narayana-jta
ℹ︎
Narayana 是誰
紅帽（Red Hat）開源的 Jakarta Transactions（前身 JTA）實作，數十年戰場驗證， 也是 WildFly / JBoss EAP 內建的交易管理器。Quarkus 把它輕量化、build-time 初始化， 讓它能在雲端原生環境（K8s、native image）運作。

JTA 交易完整生命週期

sequenceDiagram
  participant C as Client
  participant M as 業務方法
  participant TM as Narayana TM
  participant DS as Agroal Datasource
  participant DB as Database

  C->>M: 呼叫 @Transactional 方法
  M->>TM: begin
  TM->>DS: 取得 Connection
  DS-->>TM: Connection
  TM->>DB: SET AUTOCOMMIT false
  Note over M: 執行業務邏輯
  M->>DB: INSERT / UPDATE

    M->>TM: commit
    TM->>DB: COMMIT
    TM->>DS: 歸還 Connection
  else 拋出 RuntimeException
    M->>TM: rollback
    TM->>DB: ROLLBACK
    TM->>DS: 歸還 Connection
  end
  TM-->>M: 完成
  M-->>C: 結果

六種傳播屬性

@Transactional 的 value 屬性控制當前已有交易時的行為：

屬性已有交易時無交易時典型使用
REQUIRED（預設）加入現有建立新絕大多數業務方法
REQUIRES_NEW暫停現有、開新建立新審計日誌、外部回呼
MANDATORY加入現有拋例外強制呼叫端管理交易
SUPPORTS加入現有無交易執行純讀取且不在乎交易
NOT_SUPPORTED暫停現有無交易執行長查詢、read-only 加速
NEVER拋例外無交易執行絕對禁止交易的方法

REQUIRES_NEW 的經典場景

主交易失敗也要寫入的「審計記錄」：

Java · 審計獨立交易
@ApplicationScoped
public class OrderService {

    @Inject AuditService audit;

    @Transactional        // 主交易 ── 失敗會 rollback
    public Order placeOrder(CreateOrderRequest req) {
        Order order = new Order(req);
        order.persist();
        audit.logOrderAttempt(req);    // 即使下面 fail，這筆 audit 也要留
        if (order.total.compareTo(BigDecimal.valueOf(10000)) > 0) {
            throw new RiskCheckException("Too high");   // 主交易 rollback
        }
        return order;
    }
}

@ApplicationScoped
public class AuditService {

    @Transactional(Transactional.TxType.REQUIRES_NEW)
    public void logOrderAttempt(CreateOrderRequest req) {
        AuditLog log = new AuditLog("ORDER_ATTEMPT", req);
        log.persist();      // 獨立交易、立刻 commit
    }
}
⚠
CDI 自呼叫陷阱
上述 OrderService 不能在自己內部呼叫另一個 @Transactional(REQUIRES_NEW) 方法 ── CDI 攔截器只攔截「外部呼叫」。 若要在同一個 class 內切換交易，必須把方法拆到另一個 bean（如上 AuditService），透過 @Inject 呼叫。

Rollback 規則：unchecked 預設、checked 要設定

Java · 三種 rollback 控制
// 1. 預設：RuntimeException 與 Error → rollback；Checked exception → commit
@Transactional
public void payDefault() throws IOException {
    em.persist(payment);
    throw new IOException("network");    // ❌ 主交易仍 COMMIT！
}

// 2. 指定 checked exception 也要 rollback
@Transactional(rollbackOn = IOException.class)
public void payCustomRollback() throws IOException {
    em.persist(payment);
    throw new IOException("network");    // ✓ 現在會 rollback
}

// 3. 反向：某些 RuntimeException 不要 rollback
@Transactional(dontRollbackOn = OptimisticLockException.class)
public void payNoRollback() {
    em.persist(payment);
    throw new OptimisticLockException(); // ✓ 仍 commit（適合 retry 上層處理）
}

// 4. 程式內手動標記 rollback
@Inject TransactionManager tm;

@Transactional
public void manualRollback() throws SystemException {
    em.persist(payment);
    if (someCondition) {
        tm.setRollbackOnly();      // 標記後即使正常返回也會 rollback
    }
}
⚠
最大坑：checked exception 不 rollback
throws IOException 看似讓呼叫端知道「失敗了」，但預設 commit。 這違反多數開發者直覺。建議：業務錯誤永遠用自定義的 RuntimeException（如 InsufficientStockException）， 避免依賴 rollbackOn 機制。

QuarkusTransaction：現代的程式化 API

聲明式 @Transactional 不夠用時（動態決定交易邊界、複雜流程控制），Quarkus 2.8+ 提供 QuarkusTransaction：

Lambda 風格（推薦）

Java · Lambda 交易
import io.quarkus.narayana.jta.QuarkusTransaction;
import io.quarkus.narayana.jta.TransactionExceptionResult;

// 開新交易執行（等價 REQUIRES_NEW）
QuarkusTransaction.requiringNew().run(() -> {
    payment.persist();
});

// 加入現有交易（等價 REQUIRED）
Order o = QuarkusTransaction.joiningExisting().call(() -> {
    return Order.findById(id);
});

// 暫停現有交易（等價 NOT_SUPPORTED）
QuarkusTransaction.suspendingExisting().run(() -> {
    longRunningReadOnlyReport();
});

// 完整配置：自訂 timeout、客製例外處理
int result = QuarkusTransaction.requiringNew()
    .timeout(10)                          // 10 秒
    .exceptionHandler(throwable -> {
        if (throwable instanceof BusinessException) {
            return TransactionExceptionResult.COMMIT;   // 業務例外仍 commit
        }
        return TransactionExceptionResult.ROLLBACK;
    })
    .call(() -> {
        // 業務邏輯
        return computeResult();
    });

顯式 begin / commit / rollback

Java · 命令式交易
QuarkusTransaction.begin();
try {
    em.persist(entity);
    if (validate(entity)) {
        QuarkusTransaction.commit();
    } else {
        QuarkusTransaction.rollback();
    }
} catch (Exception e) {
    QuarkusTransaction.rollback();
    throw e;
}

// 帶選項
QuarkusTransaction.begin(QuarkusTransaction.beginOptions().timeout(30));
// ... 業務邏輯
✓
QuarkusTransaction 比 UserTransaction 好用
  • 無 checked exception：底層例外包裝為 QuarkusTransactionException
  • 無交易洩漏：綁定 request scope，scope 結束未 commit 自動 rollback
  • per-transaction timeout：不汙染全域 timeout 設定
  • Lambda 風格：減少樣板程式
舊版 @Inject UserTransaction 寫法仍可用，但新專案優先用 QuarkusTransaction。

交易 Timeout

全域預設

application.properties
# 預設 60 秒
quarkus.transaction-manager.default-transaction-timeout=120

方法層級覆寫

Java
import io.quarkus.narayana.jta.runtime.TransactionConfiguration;

@Transactional
@TransactionConfiguration(timeout = 300)    // 5 分鐘
public void heavyBatchJob() {
    // 大量處理
}
⚠
短交易就是好交易
交易期間連線被「鎖住」── 同時也持有 row-level locks。在交易內呼叫外部 HTTP／其他服務是大忌（外部慢，連線池就枯竭）。 SRE 上線檢查重點：
  • 單筆業務交易應 < 5 秒
  • 批次作業拆 chunk（如每 100 筆一個交易）
  • 絕不在交易內呼叫外部 API、發送 email、發 message broker（用 outbox pattern）

樂觀鎖 vs 悲觀鎖

樂觀鎖：@Version

假設衝突很少。每次 UPDATE 帶 version 條件，衝突時拋例外讓上層 retry：

Java · 樂觀鎖
@Entity
public class Product extends PanacheEntity {
    public String name;
    public BigDecimal price;
    public Integer stock;

    @Version
    public Long version;       // Hibernate 自動帶到 WHERE
}

// Hibernate 產生的 SQL：
// UPDATE products SET name = ?, price = ?, stock = ?, version = version + 1
//   WHERE id = ? AND version = ?
// 若 0 rows affected → OptimisticLockException

悲觀鎖：LockModeType

衝突頻繁時，直接在 DB 層上鎖：

Java · 悲觀鎖
@Transactional
public void deductStock(Long id, int quantity) {
    Product p = em.find(Product.class, id, LockModeType.PESSIMISTIC_WRITE);
    //                                     ↑ SELECT ... FOR UPDATE
    if (p.stock < quantity) {
        throw new InsufficientStockException();
    }
    p.stock -= quantity;
    // commit 時釋放 lock
}
樂觀鎖悲觀鎖
對 DB 壓力低（無 lock）高（FOR UPDATE 阻塞）
衝突頻率假設低高
處理衝突retry 機制（上層）序列化（等待）
scalability高低
典型場景編輯個人資料、文章金融轉帳、扣庫存

樂觀鎖 retry 模式

Java · retry 包裝
import io.smallrye.faulttolerance.api.RetryWhen;

@ApplicationScoped
public class OrderService {

    @Transactional
    @org.eclipse.microprofile.faulttolerance.Retry(
        maxRetries = 3,
        delay = 100,
        retryOn = OptimisticLockException.class)
    public void deductStock(Long id, int qty) {
        Product p = Product.findById(id);
        if (p.stock < qty) throw new InsufficientStockException();
        p.stock -= qty;
        // commit 時若 version 衝突 → retry
    }
}

XA：跨多 datasource 的單一交易

同個 JVM 內需要在同一交易裡寫兩個資料庫（如 PostgreSQL + MSSQL）？用 XA 兩階段提交。

sequenceDiagram
  participant App as 應用
  participant TM as Narayana
  participant PG as PostgreSQL
  participant MS as MS SQL

  App->>TM: begin XA
  App->>PG: INSERT order
  App->>MS: INSERT audit

  Note over TM,MS: Phase 1 Prepare
  TM->>PG: prepare
  PG-->>TM: ok
  TM->>MS: prepare
  MS-->>TM: ok

  Note over TM,MS: Phase 2 Commit
  TM->>PG: commit
  TM->>MS: commit
  TM-->>App: 完成

圖 18-2 ─ XA 兩階段提交：先 prepare、全 OK 後再 commit；任一階段 fail 全部 rollback

application.properties · 多 datasource XA
# 預設 datasource：訂單庫
quarkus.datasource.db-kind=postgresql
quarkus.datasource.jdbc.url=jdbc:postgresql://orders-db:5432/orders
quarkus.datasource.jdbc.transactions=xa            # ← 啟用 XA
quarkus.datasource.username=app
quarkus.datasource.password=${ORDERS_PW}

# 第二個 datasource：審計庫
quarkus.datasource.audit.db-kind=mssql
quarkus.datasource.audit.jdbc.url=jdbc:sqlserver://audit-db:1433;databaseName=audit
quarkus.datasource.audit.jdbc.transactions=xa      # ← 啟用 XA
quarkus.datasource.audit.username=app
quarkus.datasource.audit.password=${AUDIT_PW}
Java · 同一交易內寫兩個 DB
@ApplicationScoped
public class TransferService {

    @Inject EntityManager primaryEm;          // 預設 PU

    @Inject @PersistenceUnit("audit")
    EntityManager auditEm;

    @Transactional       // 兩個 PU 在同一個 XA 交易
    public void transfer(TransferRequest req) {
        primaryEm.persist(new Order(req));
        auditEm.persist(new AuditLog(req));
        // 兩邊都成功才 commit，任一邊失敗都 rollback
    }
}
⚠
XA 的隱性成本
  • 效能下降：每筆交易至少 2 倍 round trip（prepare + commit）
  • 恢復複雜：crash 後 in-doubt 交易需要人工介入
  • Heuristic outcome：少數情況下 phase 2 可能部分失敗，造成資料不一致
  • 不是分散式交易：只能跨同 JVM 內的多個資源，不能跨服務
雲端原生世界傾向避免 XA，改用 Saga / Outbox / 事件最終一致。

為什麼 Quarkus 不支援傳統分散式交易

⚠
官方明確聲明
Quarkus 的 narayana-jta 不支援跨服務的分散式交易協定，包括：
  • JTS（Java Transaction Service）── 基於 CORBA，雲時代已過時
  • REST-AT（REST Atomic Transaction）── 在多個 REST 服務間做 2PC
  • WS-AtomicTransaction── SOAP 時代的 2PC
原因：這些協定需要長時間持鎖、可靠雙向通訊，與雲端原生「故障是常態」哲學衝突。

Saga 與 LRA：雲時代的「分散式交易」

傳統 2PC：「全部成功才 commit」。Saga 模式：「每步驟立刻 commit，失敗就執行補償」。

sequenceDiagram
  participant C as 訂購流程
  participant O as Order Service
  participant P as Payment Service
  participant I as Inventory Service

  Note over C: 正向路徑
  C->>O: 建立訂單
  O-->>C: ok
  C->>P: 扣款
  P-->>C: ok
  C->>I: 扣庫存
  I-->>C: FAIL

  Note over C: 補償路徑
  C->>P: 退款
  C->>O: 取消訂單

LRA 擴充

bash
quarkus extension add narayana-lra
Java · LRA 風格的服務
import org.eclipse.microprofile.lra.annotation.*;
import org.eclipse.microprofile.lra.annotation.ws.rs.LRA;

@Path("/payment")
@ApplicationScoped
public class PaymentService {

    @POST @Path("/charge")
    @LRA(value = LRA.Type.MANDATORY)     // 必須在 LRA context 內
    public Response charge(PaymentRequest req,
                           @HeaderParam(LRA.LRA_HTTP_CONTEXT_HEADER) URI lraId) {
        Payment p = doCharge(req, lraId.toString());
        return Response.ok(p).build();
    }

    @PUT @Path("/compensate")
    @Compensate
    public Response compensate(@HeaderParam(LRA.LRA_HTTP_CONTEXT_HEADER) URI lraId) {
        // LRA 失敗時呼叫 ── 退款
        refund(lraId.toString());
        return Response.ok(ParticipantStatus.Compensated.name()).build();
    }

    @PUT @Path("/complete")
    @Complete
    public Response complete(@HeaderParam(LRA.LRA_HTTP_CONTEXT_HEADER) URI lraId) {
        // LRA 成功時呼叫 ── 標記為已確認
        confirm(lraId.toString());
        return Response.ok(ParticipantStatus.Completed.name()).build();
    }
}
ℹ︎
LRA 的限制與優勢
  • ✓ Atomicity：所有步驟或全成功、或全補償
  • ✗ Isolation：補償執行前，部分結果已可見（其他人可能讀到「半成品」）
  • ✗ 不是 ACID：補償是業務層的「語意倒退」，不是 DB rollback
  • 適用：跨服務、長時間業務流程（如旅遊預訂：訂機票 + 飯店 + 租車）

替代方案：Outbox Pattern

實務上更常用：把「狀態變更」與「事件發布」放在同一個 DB 交易，由背景 polling／CDC 投遞事件。

Java · Outbox 寫入
@Transactional
public Order placeOrder(CreateOrderRequest req) {
    Order order = new Order(req);
    order.persist();

    // 把事件寫到 outbox 表（同一交易！）
    OutboxEvent ev = new OutboxEvent(
        "ORDER_CREATED",
        order.id,
        JsonObject.of("orderId", order.id, "total", order.total).encode());
    ev.persist();

    return order;
}
// 另一個 worker 定期掃 outbox → 發 Kafka → 標記已發送

Narayana Object Store：交易日誌儲存

Narayana 為了 crash recovery，會把交易狀態寫入「object store」。預設是檔案系統，雲端原生環境建議改用 JDBC：

application.properties · JDBC object store
# 預設：檔案系統（單 Pod 重啟尚可、K8s ephemeral storage 就會丟）
quarkus.transaction-manager.object-store.type=jdbc

# 用獨立 datasource（避免汙染業務 DB）
quarkus.transaction-manager.object-store.datasource=transactions
quarkus.datasource.transactions.db-kind=postgresql
quarkus.datasource.transactions.jdbc.url=jdbc:postgresql://tx-db:5432/transactions
⚠
K8s 部署 Narayana 的紅線
Narayana recovery 需要三件事：
  • 穩定的儲存：用 JDBC object store 或 PVC，不要用 emptyDir
  • 唯一可重用的 Node ID：StatefulSet 的 ordinal index（pod-0、pod-1）
  • 穩定的 IP：StatefulSet headless service
若你不需要 XA、也不在乎極端崩潰恢復，避免 XA 並用單 DB 交易是最省事的選擇。

貫穿專案進度：catalog-service 完整交易設計

Java · 訂單服務完整版
@ApplicationScoped
public class OrderService {

    @Inject AuditService audit;
    @Inject OutboxService outbox;

    @Transactional
    @TransactionConfiguration(timeout = 10)     // 業務交易必須短
    @org.eclipse.microprofile.faulttolerance.Retry(
        maxRetries = 3, delay = 50,
        retryOn = OptimisticLockException.class)
    public Order placeOrder(CreateOrderRequest req) {
        // 1. 鎖庫存（悲觀鎖避免超賣）
        Product p = em.find(Product.class, req.productId(),
            LockModeType.PESSIMISTIC_WRITE);
        if (p.stock < req.quantity()) {
            throw new InsufficientStockException();
        }
        p.stock -= req.quantity();

        // 2. 建立訂單
        Order order = new Order(p, req.quantity());
        order.persist();

        // 3. 寫 outbox（事件最終會推到 Kafka）
        outbox.publish("ORDER_CREATED", order);

        // 4. 審計：失敗也要記（獨立交易）
        audit.logSuccess(order);    // REQUIRES_NEW

        return order;
        // commit 時釋放 lock + 發布事件
    }
}

DevOps / SRE 視角

✓
生產交易設計 Checklist
  1. 業務交易 < 5 秒：超過代表設計問題
  2. 絕不在交易內呼叫外部服務：用 outbox / 事件
  3. 明確 timeout：每個業務方法設 @TransactionConfiguration
  4. 樂觀鎖預設、悲觀鎖例外：只在金融類關鍵資源用 PESSIMISTIC_WRITE
  5. 避免 XA：除非真的需要跨多 DB；改 outbox 或拆服務
  6. 監控指標：交易數量、平均時長、rollback 率、optimistic lock failure 率
  7. 慢交易報告：log slow query > 500ms
  8. K8s：用 JDBC object store + StatefulSet

常見陷阱

症狀原因解法
@Transactional(REQUIRES_NEW) 沒生效 同 class 內自呼叫（CDI 不攔截） 拆到另一個 bean 用 @Inject 呼叫
Checked exception 沒 rollback JTA 預設只對 unchecked rollback 業務錯用 RuntimeException 或設 rollbackOn
Transaction timed out 交易內混入慢操作 調 timeout、或把慢操作移交易外
Connection pool 耗盡 長交易持有連線太久 切短交易、不在交易內等 I/O
OptimisticLockException 頻繁 競爭資源高、@Version 衝突 加 retry，或改悲觀鎖
XA in-doubt 交易 phase 2 中間 crash 手動介入 Narayana CLI 或 DB tool
Reactive 環境用 @Transactional 失敗 JTA 是阻塞 API 改用 @WithTransaction（第 17 章）

本章小結

  • Quarkus 用 Narayana JTA 管理交易；Hibernate ORM 自動引入。
  • 六種傳播屬性：REQUIRED（預設）、REQUIRES_NEW、MANDATORY、SUPPORTS、NOT_SUPPORTED、NEVER。
  • Rollback 預設只對 unchecked exception；checked 要 rollbackOn。
  • QuarkusTransaction lambda 風格（requiringNew().run()）優於舊 UserTransaction。
  • per-method timeout：@TransactionConfiguration(timeout = N)。
  • 樂觀鎖 @Version 預設、悲觀鎖 LockModeType.PESSIMISTIC_WRITE 用於高競爭資源。
  • XA 跨多 datasource：jdbc.transactions=xa；謹慎使用、成本不低。
  • Quarkus 不支援傳統分散式交易（JTS / REST-AT / WS-AT）。
  • 跨服務用 Saga / LRA（補償模式）或 Outbox + 事件。
  • K8s 部署 Narayana 用 JDBC object store + StatefulSet。
  • SRE 紅線：業務交易 < 5 秒、絕不在交易內 I/O 等待外部服務。
