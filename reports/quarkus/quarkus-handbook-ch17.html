Chapter 17 · Part IV

Reactive Persistence

若你的 REST 層用 Uni／Multi 寫成非阻塞，但 DB 層還在阻塞 JDBC，整個鏈路一樣會卡 ── 瓶頸從應用 thread 移到了 DB 操作。Hibernate Reactive 用 Vert.x 反應式 SQL client 取代 JDBC， 搭配 Reactive Panache，整條 request 鏈路完全在 event-loop 上跑，省 Pod、降延遲。 但反應式不是免費午餐 ── 本章告訴你什麼時候該用、什麼時候堅持用阻塞 JDBC。

為什麼要反應式持久層

回顧第 9 章的執行緒模型 ── 整條鏈路只要有一段阻塞，throughput 就被那段拖住：

  end

圖 17-1 ─ 全反應式（A）整條鏈路非阻塞；半反應式（B）DB 層仍阻塞，事倍功半

面向JDBC（Agroal）Reactive SQL Client
連線使用模式每 query 佔用整個連線直到回應連線可服務多個並發 query（pipelining）
執行緒佔用每 query 佔一個 thread少量 event-loop thread 共服所有 query
容量（5000 RPS）~ 10 Pod~ 3–4 Pod
程式碼複雜度低（同步）中（Uni / Multi 思維）
JDK 21 虛擬執行緒大幅改善容量仍最佳，但差距縮小
⚠
JDK 21 改變了取捨
JDK 21 之前，反應式幾乎是高吞吐唯一解。JDK 21+ 的虛擬執行緒（@RunOnVirtualThread）讓阻塞 JDBC 也能達到接近反應式的容量，且程式碼更直覺。 現在的選擇變成：I/O 密集、長連接（streaming）→ 反應式；傳統 CRUD、團隊熟悉同步寫法 → 阻塞 + virtual thread。

關鍵限制：與 Hibernate ORM 互斥

⚠
同一個應用只能擇一
Quarkus 的 quarkus-hibernate-orm 與 quarkus-hibernate-reactive 兩個擴充不能共存。 它們使用相同的 entity scanning 與 PU 配置，build time 會衝突。 從 Quarkus 3.31+ 開始的 Panache Next（experimental）試圖統一這個分裂，但本章仍以穩定版為主。 要混用阻塞與反應式請走 Panache Next 或拆服務。

原生 API：Mutiny.SessionFactory

最底層的 API：注入 Mutiny.SessionFactory，用 withTransaction 或 withSession 包裹邏輯：

Java · SessionFactory 直接用
import org.hibernate.reactive.mutiny.Mutiny;
import io.smallrye.mutiny.Uni;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class ProductService {

    @Inject Mutiny.SessionFactory sf;

    public Uni<Product> create(Product p) {
        return sf.withTransaction(session -> session.persist(p))
                 .replaceWith(p);          // persist 回 Void，換回 entity
    }

    public Uni<Product> findById(Long id) {
        return sf.withSession(session -> session.find(Product.class, id));
    }

    public Uni<List<Product>> listAll() {
        return sf.withSession(session -> session
            .createQuery("FROM Product", Product.class).getResultList());
    }

    public Uni<Integer> deleteById(Long id) {
        return sf.withTransaction(session -> session
            .createQuery("DELETE FROM Product WHERE id = :id")
            .setParameter("id", id)
            .executeUpdate());
    }
}

withSession vs withTransaction

方法行為用於
withSession建立 session，不開交易純讀取
withTransaction建立 session + 開交易，自動 commit / rollback寫入操作
openSession手動管理 session 生命週期進階場景
openStatelessSession無 dirty checking，純 SQL批次讀寫

Reactive Panache：糖衣再一層

跟阻塞版相同的概念，但所有方法回傳 Uni / Multi：

Java · Reactive Active Record
import io.quarkus.hibernate.reactive.panache.PanacheEntity;   // ← 反應式版本的包
import io.smallrye.mutiny.Uni;
import io.smallrye.mutiny.Multi;
import jakarta.persistence.Entity;

@Entity
public class Product extends PanacheEntity {

    public String name;
    public String sku;
    public java.math.BigDecimal price;

    public static Uni<Product> findBySku(String sku) {
        return find("sku", sku).firstResult();
    }
}
Java · 反應式查詢 API
Uni<Product> p = Product.findById(42L);
Uni<List<Product>> all = Product.listAll();
Multi<Product> stream = Product.streamAll();
Uni<Long> count = Product.count();
Uni<Boolean> deleted = Product.deleteById(42L);
⚠
Import package 不同
第 16 章阻塞 Panache 是 io.quarkus.hibernate.orm.panache.PanacheEntity，
本章反應式版本是 io.quarkus.hibernate.reactive.panache.PanacheEntity（中間多 reactive）。 Entity class 在兩個版本之間不可共用，因為繼承的基類提供不同的方法簽章（Uni vs 直接回傳）。

@WithSession 與 @WithTransaction

Reactive Panache 的 endpoint 不能用 @Transactional（那是 JTA 阻塞 API）。改用 Quarkus 的反應式版本：

Java · 反應式 REST + Panache
import io.quarkus.hibernate.reactive.panache.common.WithSession;
import io.quarkus.hibernate.reactive.panache.common.WithTransaction;
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.*;

@Path("/api/v1/products")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class ProductResource {

    @GET
    @WithSession
    public Uni<List<Product>> list() {
        return Product.listAll();
    }

    @GET @Path("/{id}")
    @WithSession
    public Uni<Product> get(@PathParam("id") Long id) {
        return Product.<Product>findById(id)
            .onItem().ifNull().failWith(NotFoundException::new);
    }

    @POST
    @WithTransaction
    public Uni<Response> create(@Valid Product p) {
        return p.<Product>persist()
            .map(saved -> Response
                .created(URI.create("/api/v1/products/" + saved.id))
                .entity(saved).build());
    }

    @DELETE @Path("/{id}")
    @WithTransaction
    public Uni<Response> delete(@PathParam("id") Long id) {
        return Product.deleteById(id)
            .map(ok -> ok
                ? Response.noContent().build()
                : Response.status(404).build());
    }
}
⚠
忘了加 @WithSession 是頭號錯誤
錯誤訊息：No current Mutiny.Session found。
原因：Panache 方法需要 reactive session，但你沒在 endpoint 上標 @WithSession（讀）或 @WithTransaction（寫）。
第三條規則：寫入操作必須用 @WithTransaction，@WithSession 不會自動 commit。

Service 層的選擇

實務上把 @WithSession／@WithTransaction 放在 endpoint 層（接近邊界），service 接收已啟動的 session：

Java · service 層保持純粹
@ApplicationScoped
public class ProductService {
    // 不標 @WithTransaction ── 由呼叫方決定
    public Uni<Product> create(Product p) {
        return p.<Product>persist();
    }
}

@Path("/api/v1/products")
public class ProductResource {
    @Inject ProductService service;

    @POST
    @WithTransaction          // 在邊界開交易
    public Uni<Response> create(@Valid Product p) {
        return service.create(p).map(saved -> /* ... */);
    }
}

組合多個 Uni：反應式的真正威力

反應式真正強的地方是並行組合。比較兩種寫法：

Java · 依序執行
// 取得產品 + 計算庫存 + 取得評論：依序 3 次 round trip
@GET @Path("/{id}/detail")
@Blocking
public ProductDetail detail(@PathParam("id") Long id) {
    Product product = productRepo.findById(id);            // 50ms
    Integer stock = stockService.getStock(id);              // 80ms
    List<Review> reviews = reviewRepo.findByProduct(id);    // 60ms
    return new ProductDetail(product, stock, reviews);
    // 總時間：190ms
}
Java · 並行
// 三個查詢同時發出，最長那個決定總時間
@GET @Path("/{id}/detail")
@WithSession
public Uni<ProductDetail> detail(@PathParam("id") Long id) {
    return Uni.combine().all().unis(
        Product.findById(id),
        stockService.getStockReactive(id),
        Review.list("product.id", id)
    ).asTuple().map(t -> new ProductDetail(
        (Product) t.getItem1(),
        (Integer) t.getItem2(),
        (List<Review>) t.getItem3()));
    // 總時間：80ms（取決於最慢那個）
}
✓
並行是反應式的殺手鐧
這個例子節省 110ms，等於延遲降低 58%。當一個 endpoint 需要呼叫多個下游時，反應式可以所有依賴並行， 阻塞版即使用 CompletableFuture 拼接也比反應式繁瑣得多。

串流大資料：Multi

批次匯出、報表生成、SSE：用 Multi 邊查邊回傳，不需把整個結果集載入記憶體。

Java · 串流匯出 CSV
@GET @Path("/export")
@Produces(MediaType.TEXT_PLAIN)
@WithSession
public Multi<String> exportCSV() {
    return Product.<Product>streamAll()
        .map(p -> "%s,%s,%s%n".formatted(p.id, p.name, p.price));
}

// SSE 也是 Multi
@GET @Path("/events")
@Produces(MediaType.SERVER_SENT_EVENTS)
@WithSession
public Multi<Product> stream() {
    return Product.streamAll();
}

什麼時候該用反應式持久層

✓
適合反應式
  • I/O 密集：一個 request 內要呼叫多個 DB + 外部服務，能並行組合
  • 長連接 / 串流：SSE、WebSocket 推送 DB 變更
  • 極高吞吐：每秒數萬請求、希望 Pod 數最少
  • 已有反應式生態：團隊熟悉 Mutiny、Vert.x、Reactive Messaging
⚠
堅持用阻塞 + Panache 的場景
  • 傳統 CRUD：每個 request 一個 query，順序執行即可
  • 團隊不熟反應式：debug Uni / Multi 鏈是初學者的惡夢
  • 已大量現有 JPA 程式碼：遷移成本高
  • JDK 21 + virtual thread 可用：阻塞 + @RunOnVirtualThread 通常足夠
  • 需要 second-level cache：Hibernate Reactive 對 L2 快取的支援較弱

測試反應式 Panache

Hibernate Reactive 的測試比阻塞版麻煩，因為所有操作必須在 Vert.x event loop 上跑：

Java · 測試 reactive Panache
import io.quarkus.test.junit.QuarkusTest;
import io.quarkus.test.vertx.RunOnVertxContext;
import io.quarkus.test.vertx.UniAsserter;
import org.junit.jupiter.api.Test;

@QuarkusTest
class ProductRepositoryTest {

    @Test
    @RunOnVertxContext
    void shouldFindBySku(UniAsserter asserter) {
        asserter.execute(() -> {
            Product p = new Product();
            p.name = "Widget";
            p.sku = "WID-001";
            return p.persist();
        });
        asserter.assertThat(
            () -> Product.findBySku("WID-001"),
            p -> assertEquals("Widget", ((Product) p).name)
        );
    }
}

關鍵：@RunOnVertxContext 確保測試方法跑在 event-loop，UniAsserter 提供 chain 起來的斷言。

DevOps / SRE 視角

連線池大小：與 JDBC 不同

ℹ︎
反應式連線可以小但精
JDBC 慣例 vCPU × 2（如 4 核 → 8 連線）。反應式因為 pipelining，更少連線就能服務更多請求。 起點建議：reactive.max-size = vCPU × 2，但實測通常即使 4–8 也夠用。
監控指標：等待 connection 的時間（connection_acquired latency），若上升就增加 pool。

EventLoop 阻塞偵測

Quarkus 預設會偵測 event-loop 上的阻塞呼叫並 warn：

WARN Thread Vert.x EventLoop has been blocked for 2345 ms, time limit is 2000 ms at java.lang.Thread.sleep(Native Method) at com.example.ProductService.doSomething(ProductService.java:42)

看到這個就代表反應式鏈路中混進了阻塞呼叫（例如不小心呼叫 JDBC 或 Thread.sleep）。要把它包成 Uni：

Java · 包裝阻塞呼叫
// ❌ 在 event-loop 阻塞
return Product.findById(id).map(p -> {
    String result = legacyBlockingClient.call(p);   // 卡 event-loop
    return result;
});

// ✓ runSubscriptionOn 把阻塞操作 dispatch 到 worker pool
return Product.findById(id)
    .onItem().transformToUni(p ->
        Uni.createFrom().item(() -> legacyBlockingClient.call(p))
            .runSubscriptionOn(Infrastructure.getDefaultWorkerPool()));

觀測指標

  • 啟用 quarkus.datasource.metrics.enabled=true 暴露反應式 pool 指標
  • 監控 vertx.pool.queue.delay（等連線時間）與 vertx.pool.usage
  • 注意 event-loop 占用率 ── 持續 > 80% 表示需要橫向擴展

常見陷阱

症狀原因解法
No current Mutiny.Session found endpoint 沒加 @WithSession / @WithTransaction 讀加 @WithSession，寫加 @WithTransaction
HR000068: must run on Vert.x EventLoop 在 worker thread 呼叫 reactive session 用 @RunOnVertxContext 測試、生產代碼確保鏈路完整
連線一直被佔住 長交易內混入慢的外部呼叫 把外部呼叫移到交易外、或拆短交易
build 失敗：hibernate-orm 與 hibernate-reactive 不能共存 兩個擴充都加了 移除其中一個或拆分服務
遷移後 URL 解析失敗 用了 jdbc: 前綴 反應式 URL 不含 jdbc:
第三方 library 阻塞 event-loop 呼叫了同步 client 包裝成 Uni 並 runSubscriptionOn 到 worker pool
L2 cache 不生效 Hibernate Reactive 對 L2 支援有限 應用層自行用 Caffeine / Redis 快取

本章小結

  • 反應式持久層用 Vert.x reactive SQL client 取代 JDBC，整條鏈路非阻塞，省 Pod、降延遲。
  • JDK 21+ 虛擬執行緒讓阻塞 JDBC 也能高吞吐，反應式不再是唯一解。
  • Quarkus 中 hibernate-orm 與 hibernate-reactive 不能共存於同一個應用。
  • URL 屬性用 quarkus.datasource.reactive.url，不含 jdbc: 前綴。
  • 原生 API：Mutiny.SessionFactory + withSession / withTransaction。
  • 反應式 Panache import package 是 io.quarkus.hibernate.reactive.panache.PanacheEntity。
  • endpoint 用 @WithSession（讀）或 @WithTransaction（寫），不能用 @Transactional。
  • 反應式最大價值：並行組合多個 I/O 操作（Uni.combine）。
  • 串流大資料用 Multi + streamAll。
  • 測試用 @RunOnVertxContext + UniAsserter。
  • SRE 警訊：event-loop blocked warn = 反應式鏈路被阻塞汙染，要包成 Uni 並 dispatch 到 worker pool。
