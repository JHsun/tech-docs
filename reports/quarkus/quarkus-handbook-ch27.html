Funqy / Serverless 訊息

前面六章的訊息處理都是長駐服務：應用啟動後 24×7 監聽。但雲端時代有另一條路 ── Serverless function： 沒有事件就完全不存在，事件來就被叫醒、處理完就消失。Quarkus 的 Funqy 讓你用一個 @Funq 註解寫一份函式， 部署到 AWS Lambda、Azure Functions、Google Cloud Functions、Knative Events 任一平台。本章是 Part V 的收尾， 讓你看清楚什麼時候該選 Funqy、什麼時候不該。

為什麼要 Serverless

來看一個常見痛點：

⚠
傳統長駐服務的「閒置成本」
一個訂單事件平均 5 分鐘才來一次，但你的 consumer service 24×7 跑著：
  • 3 個 replica × 512MB memory = 1.5GB 永遠占著
  • 多數時間 CPU 接近零、處理量稀少
  • 但你還是付雲端帳單
Serverless 的承諾：沒事件就 scale to zero，有事件才付費。

Funqy 的核心：portable function API

Funqy 的設計理念不是又一個 FaaS 框架，而是一層可攜性：

  classDef fn fill:__SOFT_OK__,stroke:__OK__,color:__TXT__,font-weight:bold
  classDef target fill:__SOFT_INFO__,stroke:__INFO__,color:__TXT__

  CODE["@Funq
public Output myFunc"]:::fn

  CODE --> LAMBDA[AWS Lambda]:::target
  CODE --> AZURE[Azure Functions]:::target
  CODE --> GCP[Google Cloud Functions]:::target
  CODE --> KN[Knative Events]:::target
  CODE --> HTTP[Standalone HTTP]:::target

圖 27-1 ─ Funqy：一份 @Funq 函式，五種部署目標，不改一行業務碼

✓
Funqy 的價值主張
  • 避免 vendor lock-in：不被 AWS Lambda SDK 鎖住
  • 本機開發體驗：dev mode + 普通 HTTP 測試
  • 原生 GraalVM 支援：cold-start < 100ms，正是 Lambda 的痛點
  • CDI 注入：仍可用 @Inject、配置屬性、interceptor
Funqy 不是「比 Lambda SDK 強」的框架，是「把同一份程式碼跑在任何 FaaS」的框架。

第一個 Funqy 函式

bash · 標準 HTTP 版（最簡單）
quarkus extension add funqy-http
Java
import io.quarkus.funqy.Funq;

public class Greeting {

    @Funq
    public String greet(String name) {
        return "Hello " + name;
    }
}

就這樣。@Funq 自動暴露為 HTTP endpoint POST /greet，request body 反序列化成 String，response body 是回傳值。

$ curl -X POST http://localhost:8080/greet -H "Content-Type: application/json" -d '"Alice"' "Hello Alice"

五種 binding：同一份程式碼、不同目標

擴充部署到適用
quarkus-funqy-httpStandalone HTTP server本機開發、長駐部署
quarkus-funqy-amazon-lambdaAWS LambdaAWS 生態
quarkus-azure-functionsAzure FunctionsAzure 生態（透過 Azure Functions HTTP trigger）
quarkus-google-cloud-functionsGoogle Cloud FunctionsGCP 生態

同一專案只能裝一個 binding
五個擴充是互斥的 ── 同個專案不要同時裝兩個。
要部署到多個平台？建議用 Maven profile 切換擴充，或維護多個 module。

主菜：Funqy + Knative Events

Knative Events 是 K8s 上的 CloudEvents 事件總線，本章重點放在這條路 ── 因為它自我託管、開源、與 Part V 主題最契合。

加擴充

bash
quarkus extension add funqy-knative-events

圖 27-2 ─ Knative Events：事件源送進 Broker，Trigger 依 CloudEvent type 路由到對應 function

  • Event Source：產生事件的來源（KafkaSource、CronJobSource、PingSource、SinkBinding…）
  • Broker：事件總線，接收所有事件、緩衝、路由
  • Trigger：訂閱規則（依 CloudEvent type／source 過濾）
  • Subscriber：Quarkus Funqy function（K8s Service）

寫 Funqy function 接收 CloudEvent

Java · 直接接 POJO（推薦）
import io.quarkus.funqy.Funq;

public class OrderFunctions {

    @Funq
    public void processOrder(Order order) {
        // 自動解析 CloudEvent data 為 Order
        Log.infof("處理訂單 %s", order.id());
        // ... 業務邏輯
    }
}

沒設 trigger annotation 時，任何 CloudEvent type 都會路由到此函式（前提：同類別只有這一個 @Funq）。

明確 trigger：@CloudEventMapping

Java · 多個函式各自綁不同 event type
import io.quarkus.funqy.Funq;
import io.quarkus.funqy.knative.events.CloudEventMapping;

public class OrderFunctions {

    @Funq
    @CloudEventMapping(trigger = "com.example.order.created")
    public void onOrderCreated(Order order) { /* ... */ }

    @Funq
    @CloudEventMapping(trigger = "com.example.order.paid")
    public void onOrderPaid(Order order) { /* ... */ }

    @Funq
    @CloudEventMapping(trigger = "com.example.order.cancelled")
    public void onOrderCancelled(Order order) { /* ... */ }
}

取得 CloudEvent metadata

Java · 用 @Context 注入
import io.quarkus.funqy.Context;
import io.quarkus.funqy.knative.events.CloudEvent;

@Funq
public void processOrder(Order order, @Context CloudEvent ce) {
    Log.infof("CloudEvent id=%s source=%s type=%s subject=%s",
              ce.id(), ce.source(), ce.type(), ce.subject());
    // 用 metadata 做 idempotency 檢查、tracing 等
}

函式鏈：output → 下一個 trigger

Knative Events 強大之處：function 回傳的 CloudEvent 自動成為新事件，可觸發下一個 function。

Java · 三段式處理鏈
public class OrderPipeline {

    @Funq
    @CloudEventMapping(
        trigger = "order.created",
        responseType = "order.validated",      // 回傳 → 新事件 type
        responseSource = "order-validator")
    public ValidatedOrder validate(Order order) {
        // 驗證邏輯
        return new ValidatedOrder(order);
    }

    @Funq
    @CloudEventMapping(
        trigger = "order.validated",
        responseType = "order.priced",
        responseSource = "pricing-engine")
    public PricedOrder price(ValidatedOrder order) {
        return new PricedOrder(order, calculatePrice(order));
    }

    @Funq
    @CloudEventMapping(trigger = "order.priced")
    public void persist(PricedOrder order) {
        // 終點：寫 DB，不回傳事件
        orderRepository.save(order);
    }
}

三個 function 各自獨立部署，沒有任何直接呼叫。Broker 與 Trigger 把它們串起來。新增第四段只要再加一個 Trigger，原 function 不動。

Funqy on AWS Lambda

若要部署到 AWS Lambda 而非 Knative：

bash
# 移除 funqy-knative-events，改裝 funqy-amazon-lambda
quarkus extension remove funqy-knative-events
quarkus extension add funqy-amazon-lambda
application.properties · 指定函式名稱
quarkus.funqy.export=processOrder
quarkus.lambda.handler=processOrder

程式碼一行不改，mvn package -Dnative 產出 Lambda runtime 用的 native binary（zip 形式），cold-start < 100ms。

Funqy vs Reactive Messaging：怎麼選

面向Funqy（Knative）Reactive Messaging（Kafka）
啟動模式事件來才啟動，閒置 → scale to zero24×7 長駐
程式碼風格單一函式同一個應用多 @Incoming
事件路由外部（Trigger 配置）內部（程式碼）
狀態無狀態（function 每次新建）有狀態（in-memory cache、connection pool）
啟動延遲有 cold start（native < 100ms，JVM 2-3s）無（已在跑）
適合事件量低～中（每分鐘幾筆～幾百筆）高（每秒幾百~幾萬筆）
底層 brokerKnative Broker（內部用 Kafka／RabbitMQ／in-memory）直接連 Kafka
連線管理每次重建（DB pool 也重建）持久連線
⚠
高吞吐用 Funqy 的成本陷阱
Function 每次冷啟都要：建 JVM／native 程式、建 DB connection pool、初始化 CDI ── 即便 native 也要 100ms。
每秒 100 個事件 → 100 個 cold start／秒 → DB 連線數爆炸、延遲不穩定。
高吞吐場景請用 Reactive Messaging。Funqy 適合低頻、突發、批次型事件（每日報表、檔案上傳處理、定時觸發）。

三種觸發模式並存

Funqy Knative Events 同時支援三種呼叫方式（同一個 function）：

bash · 1. 普通 HTTP（測試最方便）
curl -X POST http://localhost:8080/processOrder \
  -H "Content-Type: application/json" \
  -d '{"id":"o-1","total":99.99}'
bash · 2. CloudEvent binary mode（生產）
curl -X POST http://localhost:8080/ \
  -H "Content-Type: application/json" \
  -H "Ce-Id: 1" \
  -H "Ce-Source: order-api" \
  -H "Ce-Type: com.example.order.created" \
  -H "Ce-Specversion: 1.0" \
  -d '{"id":"o-1","total":99.99}'
bash · 3. CloudEvent structured mode
curl -X POST http://localhost:8080/ \
  -H "Content-Type: application/cloudevents+json" \
  -d '{
    "id":"1","source":"order-api","type":"com.example.order.created",
    "specversion":"1.0",
    "data":{"id":"o-1","total":99.99}
  }'

本機開發隨便用一種；Knative 部署後 Broker 預設用 binary mode 送過來。

貫穿專案進度：catalog-service 補上排程批次

catalog-service 主要邏輯是長駐服務（Kafka 消費 + REST API）。但有些低頻、可冷啟動的任務適合 Funqy：

  • 每日報表產生：凌晨 2 點觸發、跑完就結束
  • 檔案上傳處理：使用者上傳 CSV → S3 → 觸發 function 處理
  • 外部 webhook 接收：第三方系統不定期推送，沒事件就不該占資源
Java · 每日報表 function
@ApplicationScoped
public class DailyReportFunction {

    @Inject ReportService service;

    @Funq
    @CloudEventMapping(trigger = "dev.knative.sources.ping")  // PingSource 觸發
    public void generateDailyReport(@Context CloudEvent ce) {
        LocalDate yesterday = LocalDate.now().minusDays(1);
        Log.infof("產生 %s 的報表", yesterday);
        service.generateAndUpload(yesterday);
    }
}

配合 Knative PingSource 每天 02:00 發 CloudEvent → 觸發 function → 跑 30 秒 → scale to zero。比起長駐服務省下 24 小時的 idle cost。

DevOps / SRE 視角

Cold start 的真實影響

啟動模式Cold start適用場景
JVM mode2-5 秒不在乎冷啟動，scale to zero 後第一筆事件可慢
Native image50-150 msHTTP API 風格 Function，使用者等回應
min-scale=10（恆有 1 個 instance）關鍵業務，不能容忍 cold start
✓
生產配置 checklist
  1. 用 native build：Funqy 的最大優勢就在這 ── cold start < 100ms
  2. min-scale=1 用於關鍵 function；其他 min-scale=0
  3. max-scale 控制突發流量上限，避免下游被打爆
  4. DB connection pool 設小（max=2）── function 多 instance 並行不可開 100 連線
  5. idempotency：CloudEvent id 當去重 key（Knative 重試會送同 id）
  6. 監控 cold-start latency：Knative 內建 metrics 含 queue_proxy_request_count
  7. 避免在 function 內初始化重資源（如 NLP 模型）── 用 lazy + min-scale=1

常見陷阱

症狀原因解法
Function 收不到事件 Trigger filter type 不匹配 檢查 Broker 收到的 CloudEvent type 與 Trigger 設定一致
多個 @Funq 都沒設 @CloudEventMapping Funqy 無法決定路由 顯式加 trigger annotation，或拆成多個應用
Cold start 慢得不能接受 JVM mode 改用 native；或 min-scale=1
同事件處理多次 Function 處理超過 timeout，Knative 重試 處理 idempotent；或調長 Knative timeout（預設 60s）
DB 連線數爆炸 每個 function instance 開了大 pool 把 max-pool-size 設小（2-3）
Function 回傳的事件沒觸發下一段 沒設 responseType 或 Broker 沒設定對應 Trigger 顯式 @CloudEventMapping(responseType=...) + Trigger
本機測試正常，部署後 404 Funqy URL 路徑與 Knative Broker 預期不符 確認 K8s Service 名稱與 Trigger subscriber 一致

本章小結

  • Funqy 是 Quarkus 的 portable function API：一份 @Funq 程式碼，部署到 AWS Lambda、Azure Functions、Google Cloud、Knative、HTTP。
  • 本章重點放在 Knative Events ── 自我託管、開源、與 CloudEvents 標準完美整合。
  • Knative 架構：Event Source → Broker → Trigger → Function，依 CloudEvent type 路由。
  • 函式鏈：function 回傳的 CloudEvent 可觸發下一個 function，沒有直接呼叫。
  • 三種觸發模式並存：HTTP POST、CloudEvent binary mode、CloudEvent structured mode。
  • Funqy 適合低頻、突發、批次型事件；高吞吐用 Reactive Messaging（cold start 與 connection pool 的代價）。
  • Native build 是 Funqy 的關鍵：cold start < 100ms 才是 serverless 真實體驗。
  • SRE 重點：min-scale、max-scale、connection pool 小、idempotency、cold-start 監控。
