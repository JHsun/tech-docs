Serverless：Knative 與 Funqy

Quarkus 的超短啟動時間（<100ms native）讓它成為 serverless 的天然候選 ── 傳統 JVM 語言的幾秒冷啟動讓 scale-to-zero 難以實用，Quarkus native 完全解決這個問題。 本章涵蓋兩條 serverless 路：Knative Serving（把任何 Quarkus 服務變 scale-to-zero） 和 Funqy（函數式 API，一個 function 跑在 HTTP / AWS Lambda / Azure Functions 上）。 最後整合 Knative Eventing 建立事件驅動架構。

Knative Serving：把 Quarkus 服務 scale-to-zero

Knative Serving 讓任何 HTTP 服務享有自動伸縮 ── 包含縮到零個副本（scale-to-zero）。 沒有流量就完全不佔資源；第一個請求進來才喚醒。搭配 Quarkus native，冷啟動幾乎察覺不到。

bash · 加擴充
quarkus extension add kubernetes knative
application.properties · 生成 Knative Service
# 切換到 Knative 部署目標
quarkus.kubernetes.deployment-target=knative

# image
quarkus.container-image.registry=ghcr.io
quarkus.container-image.group=example-org
quarkus.container-image.name=catalog-function
quarkus.container-image.tag=${quarkus.application.version}

# Knative 自動伸縮設定
quarkus.knative.scale-to-zero-pod-retention-period=1m  # 閒置 1 分鐘後縮到零
quarkus.knative.autoscaling.target=100                 # 每個 pod 最多 100 並發請求
quarkus.knative.autoscaling.window=60s                 # 取過去 60s 的平均計算
quarkus.knative.min-scale=0                            # 允許縮到 0
quarkus.knative.max-scale=50                           # 最多 50 個副本

# 資源限制
quarkus.knative.resources.requests.cpu=100m
quarkus.knative.resources.requests.memory=128Mi
quarkus.knative.resources.limits.cpu=1000m
quarkus.knative.resources.limits.memory=256Mi

build 後 target/kubernetes/knative.yml 包含 Knative Service（不是 K8s Service）：

yaml · 生成的 Knative Service
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: catalog-function
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "0"
        autoscaling.knative.dev/maxScale: "50"
        autoscaling.knative.dev/target: "100"
    spec:
      containers:
      - image: ghcr.io/example-org/catalog-function:1.0.0
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits: { cpu: "1000m", memory: "256Mi" }
        readinessProbe:
          httpGet: { path: /q/health/ready, port: 8080 }
✓
Knative + Native = 最佳 serverless 體驗
Knative 冷啟動（scale 0 → 1）直接影響第一個請求的 latency：
・JVM mode：啟動 1–3s → 冷啟動明顯（用 min-scale=1 消除）
・Native mode：啟動 <100ms → 冷啟動幾乎無感
對 latency 敏感的場景必選 native + Knative。

Funqy：一個函數，多雲執行

Funqy 是 Quarkus 的函數式 API ── 一段 Java 程式碼，加注解後可以部署到： HTTP endpoint、AWS Lambda、Azure Functions、Google Cloud Functions、Knative。 不需要改程式碼，只換擴充。

Java · Funqy 函數定義
import io.quarkus.funqy.Funq;
import io.quarkus.funqy.Context;
import jakarta.inject.Inject;

public class GreetingFunction {

    @Inject
    GreetingService greetingService;

    // 函數名 = endpoint 路徑
    @Funq
    public Greeting greet(GreetInput input) {
        return greetingService.greet(input.name());
    }

    // 支援 Uni（reactive）
    @Funq
    public Uni<PriceResult> getPrice(PriceRequest req, @Context FunqyContext ctx) {
        return pricingService.calculate(req.sku());
    }
}

public record GreetInput(String name) {}
public record Greeting(String message) {}

HTTP 模式測試

bash · Funqy HTTP 呼叫
# 函數名 = endpoint 路徑
curl -X POST http://localhost:8080/greet \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice"}'

# 回傳
{"message":"Hello, Alice!"}

AWS Lambda 部署

bash · 部署到 Lambda
# 加 Lambda 擴充
quarkus extension add funqy-amazon-lambda

# 打 Lambda 部署包（含 bootstrap 腳本）
./mvnw package -Pnative -Dquarkus.native.container-build=true

# Lambda 部署包在 target/function.zip
aws lambda create-function \
  --function-name catalog-greet \
  --zip-file fileb://target/function.zip \
  --runtime provided.al2 \
  --handler unused \
  --role arn:aws:iam::123456789:role/lambda-role

# 更新
aws lambda update-function-code \
  --function-name catalog-greet \
  --zip-file fileb://target/function.zip
ℹ︎
Lambda 冷啟動：native 的關鍵價值
・JVM Lambda 冷啟動：2–10s（無法接受的 P99）
・Quarkus native Lambda 冷啟動：<100ms
AWS Lambda 用 provided.al2 runtime 直接跑 native binary， 啟動時間從秒縮到毫秒。這是 Quarkus 在 serverless 場景的決定性優勢。

Knative Eventing：事件驅動架構

Knative Eventing 讓 Quarkus 函數被 CloudEvents 觸發 ── 來自 Kafka、HTTP、計時器等：

bash · 加 Knative Events 擴充
quarkus extension add funqy-knative-events
Java · CloudEvents 觸發的函數
import io.quarkus.funqy.Funq;
import io.quarkus.funqy.knative.events.CloudEvent;
import io.quarkus.funqy.knative.events.CloudEventMapping;

public class OrderProcessor {

    // 訂閱 "order.placed" 類型的 CloudEvent
    @Funq
    @CloudEventMapping(trigger = "order.placed",
                       responseType = "order.processed")
    public OrderResult processOrder(OrderEvent event) {
        // event 從 CloudEvent payload 自動反序列化
        return orderService.process(event);
    }
}
yaml · Knative Trigger 綁定事件
apiVersion: eventing.knative.dev/v1
kind: Trigger
metadata:
  name: order-processor-trigger
spec:
  broker: default
  filter:
    attributes:
      type: order.placed    # 只收這個類型的事件
  subscriber:
    ref:
      apiVersion: serving.knative.dev/v1
      kind: Service
      name: order-processor  # 你的 Quarkus Funqy 服務

何時選 Serverless

適合 Serverless不適合 Serverless
流量不均勻、有明顯低峰持續高 QPS（一直滿載）
短時間爆發需求（黑五、促銷）長連線（WebSocket、SSE）
成本要按實際用量計費需要本地狀態（session、cache）
事件觸發的背景任務對冷啟動 latency 不容許任何容差

本章小結

  • Knative Serving：把任何 Quarkus 服務變 scale-to-zero；搭配 native <100ms 冷啟動幾乎無感。
  • 設定 quarkus.kubernetes.deployment-target=knative，build 生成 Knative Service YAML。
  • 自動伸縮：minScale/maxScale/target 並發數控制 Knative 伸縮節奏。
  • Funqy：一個函數，多雲執行 ── 換擴充不改程式碼就能跑在 HTTP / Lambda / Azure / GCP / Knative。
  • AWS Lambda：funqy-amazon-lambda + native build → target/function.zip，冷啟動 <100ms。
  • Knative Eventing：CloudEvents 觸發函數，@CloudEventMapping 綁定事件類型，Trigger 路由。
  • Serverless 適合：流量不均勻、爆發需求、按用量計費、事件驅動背景任務。
