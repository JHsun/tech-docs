JMS

Jakarta Messaging（JMS）是 Java EE 時代的訊息標準，至今仍是企業整合的官方語言。 當你要對接 IBM MQ、WebSphere、JBoss EAP、TIBCO 或既有 Java EE 應用時，JMS 比 Reactive Messaging 更貼合。 本章帶你用 Quarkus Artemis JMS（Quarkiverse）整合， 搭配 quarkus-pooled-jms 處理連線池與 XA 交易，並說明何時該用 JMS、何時該避開。

什麼時候該用 JMS

ℹ︎
三大場景
  1. 對接既有 Java EE / Jakarta EE 系統：JBoss EAP、WebSphere、WildFly 都用 JMS
  2. 對接非開源 MQ：IBM MQ、TIBCO EMS、Solace 通常只提供 JMS 客戶端
  3. 需要 JMS 2.0+ 標準 API：跨組織共用、訓練教材皆以 JMS 為主
⚠
否則優先用 Reactive Messaging
若你是新專案、不需相容舊系統，第 21 章的 Reactive Messaging + AMQP connector 通常更好：
  • JMS 是阻塞式 API，自己管 thread；Reactive 整合 Vert.x event-loop
  • JMS 沒有原生 reactive operator 鏈
  • JMS 配置與 CDI 整合需多花心思（pool、XA、scope）
JMS 是「相容性的代價」，不是「現代性的選擇」。

加擴充

bash · Quarkiverse 擴充
quarkus extension add io.quarkiverse.artemis:quarkus-artemis-jms
quarkus extension add io.quarkiverse.messaginghub:quarkus-pooled-jms
✓
為什麼一定要加 pooled-jms
JMS ConnectionFactory.createContext() 每呼叫一次都建立新 TCP 連線。 若每個 REST 請求都建一個，broker 很快就連線爆表。
quarkus-pooled-jms 包裝成 JmsPoolConnectionFactory，連線重用、效能可用。 實務上必加。

Producer：送訊息

Java · JMSContext API
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import jakarta.jms.ConnectionFactory;
import jakarta.jms.JMSContext;
import jakarta.jms.JMSProducer;
import jakarta.jms.Queue;

@ApplicationScoped
public class OrderJmsPublisher {

    @Inject
    ConnectionFactory connectionFactory;     // 自動是 pooled

    public void publish(String orderId) {
        try (JMSContext ctx = connectionFactory.createContext(JMSContext.AUTO_ACKNOWLEDGE)) {
            Queue queue = ctx.createQueue("orders");
            JMSProducer producer = ctx.createProducer();
            producer.send(queue, orderId);
        }
    }
}
⚠
try-with-resources 非常重要
JMSContext 是 AutoCloseable。沒關閉就漏連線、漏 session。 所有 JMSContext 用 try-with-resources 包起來。

Consumer：JMS 是阻塞 API

JMS 本身沒有「@Incoming 自動觸發」這種事。要持續消費，得自己起 thread：

Java · 阻塞式 listener
import io.quarkus.runtime.ShutdownEvent;
import io.quarkus.runtime.StartupEvent;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Observes;
import jakarta.inject.Inject;
import jakarta.jms.*;
import java.util.concurrent.*;

@ApplicationScoped
public class OrderJmsConsumer implements Runnable {

    @Inject ConnectionFactory connectionFactory;
    private final ExecutorService executor = Executors.newSingleThreadExecutor();
    private volatile boolean running = true;

    void onStart(@Observes StartupEvent ev) {
        executor.submit(this);
    }

    void onStop(@Observes ShutdownEvent ev) {
        running = false;
        executor.shutdown();
    }

    @Override
    public void run() {
        try (JMSContext ctx = connectionFactory.createContext(JMSContext.AUTO_ACKNOWLEDGE)) {
            JMSConsumer consumer = ctx.createConsumer(ctx.createQueue("orders"));
            while (running) {
                Message msg = consumer.receive(1000);       // 阻塞 1 秒
                if (msg != null) {
                    processOrder(msg.getBody(String.class));
                }
            }
        } catch (JMSException e) {
            Log.error("JMS consumer error", e);
        }
    }

    void processOrder(String orderId) { /* ... */ }
}
⚠
手動 thread = 自己管所有後果
  • 失敗 retry、shutdown、metrics 都要自己寫
  • 沒有自動 reconnect
  • 異常 thread 死掉 → 不再消費，要自己監控
  • 用 setMessageListener() 改 push 風格也只是把問題搬家
這就是為什麼若無相容性需求，Reactive Messaging 更好用。或下節介紹的 Resource Adapter。

與 @Transactional 整合

業務常常需要「資料庫寫入 + JMS 送訊息」同個交易內：

Java · 本地交易（單一資源管理）
@ApplicationScoped
public class OrderService {

    @Inject EntityManager em;
    @Inject ConnectionFactory connectionFactory;

    @Transactional
    public Order placeOrder(CreateOrderRequest req) {
        Order order = new Order(req);
        em.persist(order);                            // 寫資料庫

        try (JMSContext ctx = connectionFactory.createContext(JMSContext.SESSION_TRANSACTED)) {
            ctx.createProducer().send(
                ctx.createQueue("orders"), order.id());
            // ctx 內的 send 在 commit 前不會真的進 broker
        }
        return order;
    }
}

XA：DB + JMS 真正 atomic

上面的寫法仍有極小 race window：DB commit 完才 close ctx，期間若 JVM 掛掉，DB 寫入了但訊息沒送。要消除：用 XA 交易整合 Narayana JTA（第 18 章）。

application.properties · 啟用 XA
quarkus.pooled-jms.transaction=xa
quarkus.datasource.jdbc.transactions=xa

啟用後 JMS 與 JDBC 都註冊到 Narayana 的 transaction manager，2PC 保證 atomic。代價是效能下降、object store 持久化負擔（第 18 章詳述）。

多個命名 ConnectionFactory

大型系統常常要連到多個 broker（主 + DR、orders queue + analytics queue）：

application.properties
# 預設 connection factory
quarkus.artemis.url=tcp://primary:61616
quarkus.artemis.username=app
quarkus.artemis.password=${PRIMARY_PASSWORD}

# 命名 "orders"
quarkus.artemis."orders".url=tcp://orders-broker:61616
quarkus.artemis."orders".username=orders-app
quarkus.artemis."orders".password=${ORDERS_PASSWORD}

# 命名 "analytics"（用 XA）
quarkus.artemis."analytics".url=tcp://analytics-broker:61616
quarkus.pooled-jms."analytics".transaction=xa
quarkus.pooled-jms."analytics".max-connections=20
Java · 用 @Identifier 注入命名 CF
import io.smallrye.common.annotation.Identifier;
import jakarta.jms.ConnectionFactory;

@ApplicationScoped
public class MultiBrokerPublisher {

    @Inject
    @Identifier("orders")
    ConnectionFactory ordersFactory;

    @Inject
    @Identifier("analytics")
    ConnectionFactory analyticsFactory;

    public void publish(String orderId, String analyticsEvent) {
        try (JMSContext ctx = ordersFactory.createContext()) {
            ctx.createProducer().send(ctx.createQueue("orders"), orderId);
        }
        try (JMSContext ctx = analyticsFactory.createContext()) {
            ctx.createProducer().send(ctx.createTopic("events"), analyticsEvent);
        }
    }
}

Resource Adapter：真正的 MDB 體驗

上面手寫 thread 那段不夠優雅。quarkus-artemis-jms-ra 提供 Resource Adapter 風格的 Message-Driven Bean：自動 thread、自動交易、自動 retry。

bash
quarkus extension add io.quarkiverse.artemis:quarkus-artemis-jms-ra
application.properties
quarkus.ironjacamar.ra.kind=artemis
quarkus.ironjacamar.ra.config.connection-parameters=host=artemis;port=61616
quarkus.ironjacamar.ra.config.user=app
quarkus.ironjacamar.ra.config.password=${ARTEMIS_PASSWORD}

# Activation spec：訂閱 orders queue
quarkus.ironjacamar.activation-spec.orders.config.destination-type=jakarta.jms.Queue
quarkus.ironjacamar.activation-spec.orders.config.destination=jms.queue.orders
quarkus.ironjacamar.activation-spec.orders.config.max-session=4    # 並行 4 個 listener
quarkus.ironjacamar.activation-spec.orders.config.rebalance-connections=true
Java · 像 EJB MDB 一樣的 listener
import io.quarkiverse.ironjacamar.ResourceEndpoint;
import io.smallrye.common.annotation.Identifier;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.transaction.Transactional;

@ResourceEndpoint(activationSpecConfigKey = "orders")
public class OrderMessageListener implements MessageListener {

    @Override
    @Transactional      // 自動加入 XA 交易
    public void onMessage(Message message) {
        try {
            String orderId = message.getBody(String.class);
            // 處理訂單；若拋例外，broker 端會 redeliver
            processOrder(orderId);
        } catch (Exception e) {
            throw new RuntimeException(e);
        }
    }

    void processOrder(String orderId) { /* ... */ }
}
✓
RA 是 JMS 在 Quarkus 上的「現代版」
若你必須用 JMS 又想要好的開發體驗，artemis-jms-ra 是首選：
  • 不必自己起 thread
  • 自動加入 JTA / XA 交易
  • broker 連線異常自動 reconnect
  • 並行 listener（多 session）
  • 業務 code 像寫 EJB MDB 一樣簡潔

替代方案：Apache Qpid JMS（AMQP 1.0 client）

除了 Artemis 原生 client，Quarkus 也支援 Apache Qpid JMS，這是純 AMQP 1.0 的 JMS client。差異：

面向Artemis JMS ClientQpid JMS Client
傳輸協定Artemis Core / HornetQ / OpenWireAMQP 1.0
Broker 支援主要 ActiveMQ Artemis任何 AMQP 1.0 broker（Artemis、Azure Service Bus、Solace、Qpid Broker-J）
Quarkus 擴充quarkus-artemis-jmsquarkus-qpid-jms
JMS SpecJMS 2.0JMS 2.0

用 Azure Service Bus 透過 JMS API？用 Qpid JMS。連 IBM MQ？用 IBM 自家 client（手動配 ConnectionFactory bean）。

JMS vs smallrye-amqp：選哪個

ℹ︎
兩條路徑都連 ActiveMQ Artemis 怎麼選？
選 JMS（artemis-jms-ra）選 smallrye-amqp
需相容既有 JMS 程式碼新專案、無歷史包袱
要 XA 與 JTA 緊密整合at-least-once + idempotent 已夠用
偏好 EJB MDB 風格偏好 Reactive 風格
需要 JMS 2.0 的 selector / temporary queue需要 Multi 串流、@Blocking 切換
對接 JBoss EAP / WildFly跨 broker 切換頻繁（Kafka/AMQP/MQTT）

貫穿專案進度：catalog-service 接 legacy ERP

實際企業場景：catalog-service 主流程用 Kafka（第 22 章），但對接舊 ERP 系統的訂單同步必須走 JMS（ERP 只開放 JMS 介面）。架構：

  • Kafka：內部事件總線
  • JMS（Artemis）：與 ERP 雙向同步
  • 用 artemis-jms-ra 寫 ERP listener
  • 用 pooled-jms transaction=xa 確保「ERP 通知 → DB 寫入 → Kafka 通知」原子

DevOps / SRE 視角

連線池調校

參數意義建議
max-connections同時連 broker 的 TCP 連線數10-20（看併發）
max-sessions-per-connection每連線上的 session 上限50-500
connection-idle-timeout閒置連線回收時間30s 起跳
use-anonymous-producers同 session 用一個 producer 送多 destinationtrue（省資源）

Health Check

啟用 smallrye-health 後，所有 ConnectionFactory 自動加入 /q/health/ready。可關閉：

application.properties
quarkus.artemis.health.enabled=false        # 關閉所有
quarkus.artemis."orders".health.enabled=false  # 只關 orders

監控指標

  • Pool 飽和率（active / max-connections）
  • Send 延遲、receive 延遲
  • Broker 端 queue depth、consumer 數
  • Redelivery 次數（暗示處理失敗）
  • XA recovery log 大小（XA 模式）

常見陷阱

症狀原因解法
broker 連線爆表 沒加 pooled-jms，每呼叫一次建一個連線 必加 quarkus-pooled-jms
JMSContext 漏連線 沒用 try-with-resources 所有 ctx 用 try-with-resources 包
XA recovery 失敗 node-name 不穩定（Pod 重啟改變） StatefulSet + 穩定 quarkus.transaction-manager.node-name
handwritten consumer 偶爾停掉 broker 斷線後 thread 死 改用 artemis-jms-ra 自動 reconnect
多個 CF 注入失敗 沒用 @Identifier 區分 命名 CF 必須用 @Identifier("name")
RabbitMQ 連不上 artemis-jms 是 Artemis 專用協定 用 quarkus-qpid-jms + AMQP 1.0 plugin
原生映像啟動失敗 JMS client 有 reflection 缺類 用 Artemis 擴充（自動處理 native）；自寫 CF 要加 reflection config

本章小結

  • JMS 是相容性優先的選擇：對接 IBM MQ、JBoss EAP、舊 Java EE 應用首選。
  • 新專案無相容需求 → 優先 Reactive Messaging（第 21、24 章）。
  • Quarkus 主要靠 Quarkiverse 擴充：quarkus-artemis-jms（client）+ quarkus-pooled-jms（必加）。
  • JMS 2.0 用 JMSContext 簡化（Connection + Session 合一），務必 try-with-resources。
  • JMS 是阻塞 API，consumer 要自己起 thread；或用 artemis-jms-ra 享受 MDB 自動化體驗。
  • 本地交易 transaction=enabled；DB + JMS 真正 atomic 需 transaction=xa + JTA（第 18 章）。
  • 多 broker 用 quarkus.artemis."name" 命名 + @Identifier 注入。
  • Apache Qpid JMS 是 AMQP 1.0 純 client，連 Azure Service Bus 首選。
  • SRE：必加 pooled-jms、調 max-connections、XA 環境穩定 node-name、監控 redelivery。
