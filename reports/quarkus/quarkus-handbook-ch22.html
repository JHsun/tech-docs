Apache Kafka 基礎

上一章的 in-memory channel 適合單體應用的內部解耦，但要跨服務、跨機器、保留可重播性，就需要真正的分散式 log ── Apache Kafka。本章從 Kafka 的核心概念（topic、partition、offset、consumer group）開始， 示範 Quarkus 怎麼用 SmallRye Kafka connector 透明取代 in-memory，並深入 serializer、offset commit、auto offset reset 這些決定可靠性的關鍵設定。

關鍵概念

概念意義
Topic邏輯訊息類別（如 order-events、user-signups）
PartitionTopic 的並行單位 ── 一個 partition 就是一個 append-only log
Offsetpartition 內訊息的編號（單調遞增）；Kafka 不刪訊息，靠 retention 規則過期
Record Key決定訊息進哪個 partition（同 key 永遠在同 partition，保序的關鍵）
Consumer Group多個 consumer 形成一組共同消費 topic；每個 partition 在組內只指派給一個 consumer
Replicationpartition 在多個 broker 上複製，防止單點故障
ℹ︎
Partition 是並行與保序的取捨核心
  • Partition 越多 → 並行度越高（更多 consumer 可以分擔）
  • 但 partition 數量是 Topic 的準終身決定 ── 後改會打亂 key 雜湊與排序
  • 同 key 永遠在同一 partition：用 userId 當 key，同使用者的事件保證有序
  • 跨 partition 不保證順序
起始建議：partition 數 ≥ 預期 consumer 數 × 2，預留擴展空間。

第一個 Kafka 範例

定義 payload

Java
public record OrderEvent(String orderId, String type, BigDecimal total, Instant at) {}

Producer

Java · 用 Emitter 送 Kafka
@Path("/orders")
public class OrderResource {

    @Channel("order-events")
    Emitter<OrderEvent> emitter;

    @POST @Transactional
    public Response create(CreateOrderRequest req) {
        Order o = orderRepo.create(req);
        emitter.send(new OrderEvent(o.id(), "ORDER_CREATED", o.total(), Instant.now()));
        return Response.accepted().entity(o).build();
    }
}

Consumer

Java · 收 Kafka
@ApplicationScoped
public class InventoryListener {

    @Incoming("order-events")
    @Blocking @Transactional
    public void onOrder(OrderEvent ev) {
        if ("ORDER_CREATED".equals(ev.type())) {
            inventoryService.reserve(ev.orderId());
        }
    }
}

application.properties

✓
Serializer 自動偵測
Quarkus 看到 channel 的 payload 是 OrderEvent record，在 build time 自動產生 Jackson serializer/deserializer。 你不用手動設 value.serializer。常見內建型別（String、Integer、Long、Double、JSON）也都自動處理。

控制 partition：Record Key

沒指定 key 時，訊息會 round-robin 分散到所有 partition。要保序就必須用 key：

Java · 用 Record 類型
import io.smallrye.reactive.messaging.kafka.Record;

@Channel("order-events")
Emitter<Record<String, OrderEvent>> emitter;

@POST
public void create(CreateOrderRequest req) {
    Order o = orderRepo.create(req);
    // 同 orderId 的所有事件保證有序處理
    emitter.send(Record.of(o.id(), new OrderEvent(o.id(), "CREATED", o.total(), Instant.now())));
}

用 metadata 設更多細節

Java · OutgoingKafkaRecordMetadata
import io.smallrye.reactive.messaging.kafka.OutgoingKafkaRecordMetadata;
import org.apache.kafka.common.header.internals.RecordHeaders;

Message<OrderEvent> msg = Message.of(event)
    .addMetadata(OutgoingKafkaRecordMetadata.<String>builder()
        .withKey(order.id())
        .withTopic("order-events")            // 覆寫預設 topic
        .withTimestamp(Instant.now())
        .withHeaders(new RecordHeaders()
            .add("source", "order-api".getBytes())
            .add("trace-id", traceId.getBytes()))
        .build());

emitter.send(msg);

Offset 與 auto.offset.reset

Consumer group 第一次連上 topic 時（或之前的 offset 已過期），從哪裡開始讀？這由 auto.offset.reset 決定：

值行為適用
latest（預設）從最新一筆之後開始，不讀舊資料即時通知、不在乎歷史
earliest從 topic 起始讀全量重建、事件溯源、新服務初始化
none找不到 offset 就拋例外嚴格驗證；需手動處理
⚠
latest 與 earliest 的選擇影響上線
新部署一個 consumer service 時：
  • latest：上線前累積的事件會被跳過。風險：上線前一筆訂單漏掉
  • earliest：從頭讀起，但可能讀到幾百萬筆已過時資料
生產實務：先用 earliest 上線一次（補追資料），確認穩定後再切 latest。 或設計成 idempotent，反正重讀也無妨。

Offset Commit 策略

Consumer 處理完訊息要「commit offset」告訴 broker：「這之前我都處理完了」。Quarkus 支援三種策略：

application.properties
mp.messaging.incoming.order-events.commit-strategy=throttled
策略行為適用
throttled（預設）定期 commit 已 ack 訊息的最高 offset多數場景，平衡可靠性與效能
checkpoint每處理 N 筆才 commit，跨重啟用 state store需 exactly-once
latest每筆訊息 ack 時立即 commit最安全但最慢
ignore不自動 commit（你自己管）自訂 offset 管理
⚠
at-least-once 是預設，不是 exactly-once
Kafka 預設 at-least-once：consumer 處理完還沒 commit 就掛了，下次重啟會重讀。
  • 對策：consumer 邏輯必須 idempotent（重複處理結果相同）
  • 用 DB unique key（事件 ID）擋重複
  • 真要 exactly-once，搭 checkpoint + transactional producer（複雜，慎用）

Consumer Group 與水平擴展

同一個 group.id 的多個 instance 共同消費 topic ── 自動分擔 partition：

flowchart LR
  classDef p fill:__SOFT_INFO__,stroke:__INFO__,color:__TXT__
  classDef c fill:__SOFT_OK__,stroke:__OK__,color:__TXT__,font-weight:bold

  P0[Partition 0]:::p --> C1[Pod 1]:::c
  P1[Partition 1]:::p --> C1
  P2[Partition 2]:::p --> C2[Pod 2]:::c
  P3[Partition 3]:::p --> C2
  P4[Partition 4]:::p --> C3[Pod 3]:::c
  P5[Partition 5]:::p --> C3

圖 22-2 ─ 6 partition + 3 Pod consumer group：每個 Pod 拿 2 個 partition

ℹ︎
擴展上限是 partition 數
  • Pod 數 ≤ partition 數：多餘 Pod 會閒置（無 partition 可拿）
  • K8s HPA 設 max replicas 不應超過 partition 數
  • 規劃時：partition 數 = 預期高峰 Pod 數 × 安全邊際（2x）

Rebalance：好與壞

當 consumer 加入或離開（部署、scale、Pod 重啟），Kafka 觸發 rebalance 重新分配 partition。期間：

  • 所有 consumer 暫停處理（stop-the-world）
  • 新分配生效後再恢復
  • 滾動部署可能引發多次 rebalance，造成延遲

緩解：

application.properties
# 使用 cooperative rebalance（partition 不全部釋放）
mp.messaging.incoming.order-events.partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# 給滾動部署足夠時間（45s vs 預設 10s）
mp.messaging.incoming.order-events.session.timeout.ms=45000

# 拉長 max.poll.interval，避免長處理被誤判失聯
mp.messaging.incoming.order-events.max.poll.interval.ms=600000

JSON 序列化的細節

Quarkus 自動產生的 Jackson serializer 處理多數情況。如果你想自訂：

application.properties · 顯式指定
# Producer
mp.messaging.outgoing.order-events.value.serializer=io.quarkus.kafka.client.serialization.ObjectMapperSerializer

# Consumer
mp.messaging.incoming.order-events.value.deserializer=io.quarkus.kafka.client.serialization.ObjectMapperDeserializer
mp.messaging.incoming.order-events.json.deserializer.class=com.example.OrderEvent

# Key 默認 String
mp.messaging.outgoing.order-events.key.serializer=org.apache.kafka.common.serialization.StringSerializer
mp.messaging.incoming.order-events.key.deserializer=org.apache.kafka.common.serialization.StringDeserializer
⚠
JSON 不是長期生產的最佳選擇
JSON 簡單但有問題：無 schema、欄位重命名不向後相容、效能不如二進位。
生產級的 event-driven 系統推薦 Avro + Schema Registry 或 Protobuf，下一章（第 23 章）詳述。

Dead Letter Queue：失敗處理

第 21 章提過：失敗策略生產用 DLQ。Kafka 的 DLQ 就是另一個 topic：

application.properties
mp.messaging.incoming.order-events.failure-strategy=dead-letter-queue

# DLQ topic 名稱（預設 dead-letter-topic-$channel）
mp.messaging.incoming.order-events.dead-letter-queue.topic=order-events-dlq

# DLQ 訊息會附加額外 headers：
# - dead-letter-reason
# - dead-letter-cause
# - dead-letter-topic（原 topic）
# - dead-letter-partition
# - dead-letter-offset

後續用 admin tool 或另寫一個 service 監聽 DLQ 處理、人工介入、reprocess。

處理層 retry：@Retry

暫時性錯誤（網路抖、DB 重啟）可以用 SmallRye Fault Tolerance（第 38 章詳述）做 retry：

Java · 結合 @Retry
import org.eclipse.microprofile.faulttolerance.Retry;

@Incoming("order-events")
@Blocking
@Retry(maxRetries = 3, delay = 500)
public void process(OrderEvent ev) {
    inventoryService.reserve(ev.orderId());     // 失敗自動重試 3 次
}

retry 都失敗才會走 failure-strategy，所以 retry + DLQ 是經典組合。

直接用 Kafka Client（非 Reactive Messaging）

有些場景（管理工具、特殊 transactional producer）需要直接用原生 Kafka Client：

Java · 注入原生 Producer/Consumer
import org.apache.kafka.clients.producer.*;

@Inject
@Identifier("default-kafka-broker")
Map<String, Object> kafkaConfig;

public void rawSend() {
    var config = new HashMap<>(kafkaConfig);
    config.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
    config.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

    try (var producer = new KafkaProducer<String, String>(config)) {
        producer.send(new ProducerRecord<>("admin-topic", "key", "value")).get();
    }
}

多數情況 Reactive Messaging 已足夠，這條路只在特殊需求時走。

貫穿專案進度：catalog-service 跨服務事件

把第 21 章的 in-memory channel 換成 Kafka，程式碼不變，只改 properties：

application.properties · 生產配置
%prod.kafka.bootstrap.servers=kafka-bootstrap.kafka.svc:9092

# 全部 channel 都用 smallrye-kafka
mp.messaging.outgoing.order-events.connector=smallrye-kafka
mp.messaging.outgoing.order-events.topic=catalog.order-events
mp.messaging.outgoing.order-events.acks=all
mp.messaging.outgoing.order-events.enable.idempotence=true

mp.messaging.incoming.order-events.connector=smallrye-kafka
mp.messaging.incoming.order-events.topic=catalog.order-events
mp.messaging.incoming.order-events.group.id=catalog-service
mp.messaging.incoming.order-events.failure-strategy=dead-letter-queue
mp.messaging.incoming.order-events.dead-letter-queue.topic=catalog.order-events.dlq
mp.messaging.incoming.order-events.auto.offset.reset=earliest
✓
生產 Producer 三大標準設定
  • acks=all ── 等所有 in-sync replica 確認，最高可靠性
  • enable.idempotence=true ── Kafka 端去重，避免 retry 造成重複
  • max.in.flight.requests.per.connection 預設 5；要嚴格保序設 1（犧牲吞吐）

DevOps / SRE 視角

容量規劃

✓
起步配置建議
  • Cluster：3 broker 起跳（容忍 1 broker 故障）
  • Replication factor：3
  • min.insync.replicas：2（搭配 acks=all）
  • Retention：時間或大小，依業務需求（7 天、30 天）
  • Partition 數：依預期吞吐 + consumer 數規劃，至少 3-6 起步
  • Compression：compression.type=lz4（producer 端）

監控指標

  • Consumer Lag：consumer 落後 broker 最新 offset 多少筆。持續上升 = 處理跟不上
  • Rebalance 頻率：頻繁 rebalance 表示 consumer 不穩
  • Producer batch size：太小代表 producer 過於急著送出
  • Under-replicated partitions：broker 健康狀態
  • Quarkus 啟用 quarkus.kafka.health.enabled=true 把 Kafka 接到 health endpoint

常見陷阱

症狀原因解法
Consumer 重啟後重複處理 at-least-once 預設行為 業務邏輯做 idempotent；用事件 ID 去重
新 service 上線完全沒收到歷史事件 auto.offset.reset=latest 改 earliest 或啟動前先 reset offset 到指定點
同 user 事件處理順序錯亂 沒設 record key，分散到多 partition 用 userId 或 orderId 當 key
頻繁 rebalance 處理慢 + 預設 timeout 過短 拉長 max.poll.interval.ms、改 cooperative assignor
DLQ 啟用後啟動爆炸 已知 issue #51521（auto-generated serializer 在 DLQ 載不到） 顯式設 dead-letter-queue.value.serializer
Producer block broker 連線問題、buffer 滿 檢查 buffer.memory、max.block.ms、broker 狀態

本章小結

  • Kafka 核心：Topic → Partition → Offset；Consumer Group 內每個 partition 只給一個 consumer。
  • Quarkus 整合用 quarkus-messaging-kafka，dev 模式有 Dev Services 零配置。
  • Record key 決定 partition，同 key 保序；沒 key 則 round-robin。
  • Serializer/Deserializer 自動偵測（Jackson JSON、內建型別）。
  • auto.offset.reset：earliest（重建）vs latest（只看新）── 上線時的關鍵決策。
  • Commit 策略預設 throttled；生產上 at-least-once 是常態，consumer 必須 idempotent。
  • Consumer Group：Pod 數 ≤ partition 數，HPA 上限要受限。
  • Rebalance 是壽命中必有，用 cooperative assignor 與較長 timeout 緩解。
  • 失敗用 DLQ；暫時性錯誤可結合 @Retry。
  • 生產 Producer 三件套：acks=all + enable.idempotence=true + 適當 max.in.flight。
