Chapter 35 · Part VII

Tracing（OpenTelemetry）

使用者按下「下單」， 4.8 秒後才看到回應 ── 慢在哪？資料庫？inventory-service？payment gateway？Kafka？ Distributed Tracing 把一次 request 在所有服務的每一步攤開，視覺化成一棵調用樹（span tree）。 Quarkus 用 OpenTelemetry（CNCF 標準，取代 OpenTracing/Jaeger client）── 一行 extension 就自動 instrument REST、JDBC、Kafka、Redis、HTTP Client， 需要自訂 span 時用 @WithSpan 註解。本章把這套技術從看一張 trace 圖到產生那張圖背後的所有細節講透。

術語意義
Trace一次 request 從進入到完成的完整路徑。有唯一 traceId。
SpanTrace 中的一個工作單元（一個方法、一次 DB 查詢、一次 HTTP 呼叫）。有 spanId、parentSpanId。
AttributeSpan 上的 key-value 標籤（http.method=POST、db.statement=SELECT ...）
EventSpan 內某個時間點發生的事（如 retry、error）
ContexttraceId + spanId + sampling decision，跨服務傳遞用的資訊

OpenTelemetry：統一觀測標準

✓
為什麼是 OTel
2019 年前：OpenTracing（API）+ Jaeger / Zipkin（後端各自不同 client）。
OpenCensus（Google）：另一套，分裂。
2019：OpenTracing + OpenCensus 合併成 OpenTelemetry，CNCF graduated。
現在：所有主流後端（Jaeger / Tempo / Datadog / New Relic / Dynatrace）都接 OTLP 協定。
結論：應用端用 OTel API、後端隨便換，這就是 vendor-neutral 的核心。

啟動後免費獲得

裝完擴充重啟 ── 不必改任何業務碼，已自動 instrument：

類型自動產生的 span
HTTP server每個 REST request 一個 root span（method + path）
JDBC每個 SQL 查詢一個 span（statement 截斷）
Hibernate ORM / Panache透過 JDBC 自動取得
REST Client每個 outbound HTTP call 一個 span（含下游 traceId）
Kafka clientproducer.send / consumer poll 各一個 span
Redis client每個 command 一個 span
@Scheduled 方法每次執行一個 span
ℹ︎
Quarkus build-time 注入
傳統 Java agent 在啟動時注入 instrumentation（性能差、native 不支援）。 Quarkus 用建構時靜態注入，所有 instrumentation 在 build 時就接好 ── native image 完整支援，無 cold start 成本。

自訂 Span：@WithSpan

自動 instrumentation 只看到 REST / DB / HTTP 邊界，不知道你方法裡面在幹嘛。要看清業務邏輯的某個重要步驟，用 @WithSpan：

Java · 基本用法
import io.opentelemetry.instrumentation.annotations.WithSpan;
import io.opentelemetry.instrumentation.annotations.SpanAttribute;

@ApplicationScoped
public class OrderService {

    @WithSpan("place-order")             // span 名稱（不寫則用方法名）
    public Order place(@SpanAttribute("order.user") String userId,
                       @SpanAttribute("order.items") int itemCount,
                       Cart cart) {
        // 自動建立 span，方法結束時自動結束 span
        validateInventory(cart);
        BigDecimal total = calculatePrice(cart);
        Order order = persist(userId, total);
        return order;
    }

    @WithSpan
    private void validateInventory(Cart cart) {
        // 又一個子 span
    }
}

結果：POST /orders（自動）→ place-order（@WithSpan）→ validateInventory（@WithSpan）→ JDBC query（自動），形成完整調用樹。

從程式碼直接拿 Span

Java · 加 event 與 attribute
import io.opentelemetry.api.trace.Span;

@WithSpan
public void processPayment(Payment p) {
    Span span = Span.current();
    span.setAttribute("payment.method", p.method().name());
    span.setAttribute("payment.amount", p.amount().doubleValue());

    try {
        gateway.charge(p);
        span.addEvent("payment.charged");
    } catch (PaymentException e) {
        span.recordException(e);          // span 自動標 error
        span.setStatus(StatusCode.ERROR, e.getMessage());
        throw e;
    }
}
⚠
不要把敏感資料放 attribute
Span 與 log 一樣是合規地雷：信用卡號、SSN、密碼絕對不能放 attribute。 Tempo / Jaeger 預設無加密儲存，看 trace 的人可能比看 log 的人更多。

Context Propagation：跨服務串起來

OTel 自動把 trace context 透過 HTTP header 跨服務傳遞 ── 名稱叫 traceparent（W3C Trace Context 標準）：

GET /stock/ABC-123 HTTP/1.1 Host: inventory:8080 traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 │ │ │ │ │ └ traceId (32 hex) │ └ flags └ version └ spanId

下游服務的 OTel 自動解析這個 header，把自己的 span 標為「父 span = inventory client span」── 整條鏈就串起來了。

sequenceDiagram
  participant U as User
  participant C as catalog-service
  participant I as inventory-service
  participant D as Database

  U->>C: POST /orders
無 traceparent
  Note over C: 建立新 traceId
spanId=s1
  C->>I: GET /stock
traceparent=t1/s1
  Note over I: 解析 traceparent
parent=s1 自己=s2
  I->>D: SELECT
  Note over D: span s3 parent=s2
  D-->>I: result
  I-->>C: response
  C-->>U: 201 Created

圖 35-2 ─ Context 透過 traceparent header 在服務間傳遞，所有 span 共享 traceId

支援的 Quarkus 元件（自動傳遞）

  • REST Client：outbound HTTP 自動加 traceparent
  • Vert.x HTTP Client：同上
  • Reactive Messaging Kafka：header traceparent 自動加入 Kafka message
  • gRPC：自動處理 metadata

手動傳遞（非標準 client）

如果你用某個沒被 OTel instrument 的 library（如自寫的 HTTP client），手動注入：

Java · 手動 inject context
import io.opentelemetry.api.OpenTelemetry;
import io.opentelemetry.context.Context;
import io.opentelemetry.context.propagation.TextMapSetter;

@Inject OpenTelemetry openTelemetry;

void sendToLegacy(Request req) {
    Map<String, String> headers = new HashMap<>();
    openTelemetry.getPropagators().getTextMapPropagator()
        .inject(Context.current(), headers, Map::put);
    // 此時 headers 已含 traceparent
    legacyClient.send(req, headers);
}

Reactive 場景：context 千萬不要丟

傳統 Java thread-local context 在 reactive code 跨 thread 切換時會消失。Quarkus 用 duplicated context 解決：每個 request 一個隔離區，OTel context 跟著走。

⚠
@WithSpan 在 reactive 方法的坑
@WithSpan 套在回 Uni<T> / Multi<T> 的方法上 ── span 預設在方法 return 時就結束， 不是在 Uni 真正 resolve 時。結果：duration 看起來是 0ms，子 span 全跑外面。
Quarkus OTel 已對 Uni / Multi 做了正確處理，但若有疑惑可手動： 
return Uni.createFrom().item(...)
    .invoke(item -> Span.current().setAttribute("...", ...));

Sampling：trace 不能全收

每筆 request 都記 trace 太貴 ── 一個服務每秒 10000 req × 30 個下游 spans = 30 萬 spans / 秒。Sampling 決定哪些 trace 該留。

Head-based sampling（最常見）

在 trace 開始之前決定要不要採樣，整條 trace 一致：

application.properties
# 採樣 10% 的 trace
quarkus.otel.traces.sampler=traceidratio
quarkus.otel.traces.sampler.arg=0.1

# 或永遠採樣（dev）
%dev.quarkus.otel.traces.sampler=always_on

# 或全關（極端流量）
# quarkus.otel.traces.sampler=always_off
⚠
Head-based 的缺點
決定採樣太早 ── 你還不知道這個 request 會不會失敗、會不會慢。等發現問題時，trace 早已被丟掉。 對於「我想看所有慢請求 / 錯誤請求」的場景，head-based 不夠用。

Tail-based sampling（OTel Collector 端）

應用端全部送出，OTel Collector 在記憶體緩衝整條 trace，等 trace 結束（含所有子 span）才決定要不要存：

yaml · otel-collector.yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: errors-policy
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow-policy
        type: latency
        latency: { threshold_ms: 1000 }
      - name: random-10pct
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }

這配置：所有 error + 所有 >1 秒 + 10% 隨機。應用端不必做決定，全送出，Collector 智慧過濾。

✓
生產建議
  • 小規模（< 1k req/s）：head-based always_on 即可
  • 中規模：head-based 1-10%
  • 大規模：tail-based + Collector，能保留所有「壞」trace

✓
Collector 的價值
  • 後端解耦：應用永遠送 OTLP 到 Collector，後端從 Tempo 換到 Datadog 不用改應用
  • 批次與重試：應用送 Collector 是本機（快），Collector 負責上傳遠端後端（穩）
  • Tail-based sampling：跨服務看完整 trace 才決定
  • 過濾與轉換：去敏感資料、改 attribute、降採樣
  • 多後端 fan-out：同一份 trace 送多個後端
生產一定要有 Collector，不要應用直接送遠端後端。

後端選型：Jaeger vs Tempo vs SaaS

後端類型適用
JaegerOSS，CNCF graduated中小規模、自我託管、最熟悉的工具
Grafana TempoOSS大規模、跟 Grafana / Loki / Prometheus 整合好
Datadog APM商業 SaaS無維護需求、預算夠
New Relic / Dynatrace商業 SaaS企業合約、合規場景
Honeycomb商業 SaaS，event-based需高基數 query、結構化分析
ℹ︎
Tempo 的特殊優勢
Tempo 設計用 S3 / GCS 當儲存 ── 每 1TB 月成本 < $30，遠低於其他後端。 搭配 Grafana 已有 stack 的團隊，幾乎是首選。代價：query 慢，要靠 traceId 跳轉（需 metrics / logs 先定位）。

Log + Trace 雙向跳轉

第 33 章說過 OTel Logging 讓 log 自動帶 traceId。完整循環：

  1. Grafana 看到 P99 latency 飆升（metric）
  2. 查 logs 看到一筆 error，含 traceId（log → trace）
  3. 點 traceId 跳到 Tempo，看完整調用樹（trace）
  4. 從 trace 的某個 span 點 logs 圖示，看那段時間該服務的所有 log（trace → log）
✓
這就是「可觀測性」的真實價值
當三大訊號（metric / log / trace）能互相跳轉，debug 從「猜」變「順著線索走」。 這需要 OTel 把三者用同一個 SDK、同一個協定、同一個 traceId 串起來。 這是 OTel 出現的真正動機。

貫穿專案進度：catalog 完整 trace 視角

把 catalog-service 的 placeOrder 流程加上有意義的 span：

Java
@Path("/api/orders")
public class OrderResource {

    @POST
    public Order place(OrderRequest req) {
        // 自動 span: POST /api/orders
        return orderService.placeOrder(req);
    }
}

@ApplicationScoped
public class OrderService {

    @Inject InventoryClient inventory;
    @Inject PaymentClient payment;
    @Inject Emitter<OrderEvent> eventEmitter;

    @WithSpan("order.place")
    @Transactional
    public Order placeOrder(@SpanAttribute("order.user") String userId,
                             OrderRequest req) {
        Span span = Span.current();
        span.setAttribute("order.itemCount", req.items().size());

        // 1. 庫存驗證（會看到 inventory-service 的 spans）
        inventory.reserve(req.items());

        // 2. 計價（業務邏輯，明確標 span）
        BigDecimal total = priceOrder(req);
        span.setAttribute("order.total", total.doubleValue());

        // 3. 付款
        PaymentResult pr = payment.charge(userId, total);
        span.addEvent("payment.success",
                       Attributes.of(AttributeKey.stringKey("payment.id"), pr.id()));

        // 4. 寫 DB（自動 JDBC span）
        Order order = persist(userId, req, total, pr);

        // 5. 發 Kafka 事件（自動 Kafka span，traceparent 透過 header 傳到下游 consumer）
        eventEmitter.send(new OrderEvent(order.getId(), userId, total));

        return order;
    }

    @WithSpan
    private BigDecimal priceOrder(OrderRequest req) {
        // 計價邏輯
    }
}

結果：POST /api/orders → order.place → reserve (inventory-service 整個 trace 樹) → priceOrder → charge (payment-service 整個 trace 樹) → INSERT (JDBC) → Kafka send 形成完整視覺化。當任何一步慢，Tempo 圖一眼看出。

DevOps / SRE 視角

✓
Tracing 上線 checklist
  1. 裝 OTel Collector（DaemonSet 或 Deployment），應用送 Collector 不送遠端
  2. 應用 OTel endpoint 用 K8s Service（otel-collector.observability.svc:4317）
  3. Sampling 策略：小規模 head 100%、中規模 head 10%、大規模 tail-based
  4. 每個服務設 service.name + service.version
  5. 禁敏感資料當 attribute：與 log mask 同等對待
  6. Native build 驗證 OTel：reachability metadata 已內建，但自訂 instrumentation 要驗
  7. Trace retention 分層：高解析度 24-48 小時、降採樣 7 天
  8. 監控 trace dropped rate：Collector 滿載會丟，需告警
  9. 跨 Kafka 邊界傳遞：確認 reactive messaging 配置 OK
  10. 建立 trace 模板 dashboard：service map、top slowest、error trace 列表

常見陷阱

症狀原因解法
Trace 斷掉（一個 request 兩棵 trace 樹） 某個中間環節沒傳 traceparent 檢查那個 hop 用什麼 client；非 Quarkus 的 client 手動 inject
@WithSpan 不生效 同 class 內部呼叫（CDI proxy 限制） 拆到別的 bean
reactive 方法 span duration 是 0 span 在 Uni return 時結束、不在 resolve 時 3.x 已修正；若仍有問題改用 Uni.invoke 手動操作 span
@Scheduled 方法的 trace 無 parent 排程任務本來就無 parent，是 root span 正常行為；想串連請手動傳 context
看不到任何 span Collector 連不到 / sampling=always_off 檢查 endpoint 與 sampler 配置
Trace 量爆炸，後端 OOM 採樣率太高 + 沒批次發送 降採樣率，或加 Collector 與 batch processor
Native build 後 trace 缺失 某 library 動態反射未註冊 多數常用 lib 已支援；自訂 lib 加 @RegisterForReflection

本章小結

  • Trace 由多個 Span 組成樹，每個 span 有 service、operation、duration、attributes。
  • OpenTelemetry 是 CNCF 統一標準（合併自 OpenTracing + OpenCensus），所有主流後端支援 OTLP。
  • Quarkus build-time 注入 OTel ── native image 完整支援、無 cold start 成本。
  • 自動 instrumentation：REST、JDBC、Kafka、Redis、REST Client、@Scheduled 全免費。
  • 業務 span 用 @WithSpan，重要參數用 @SpanAttribute。
  • Span.current() 可取得當前 span，加 attribute / event / recordException。
  • 跨服務透過 W3C traceparent header 自動傳遞 context（REST Client / Kafka 全自動）。
  • Reactive 場景 Quarkus 用 duplicated context 保留 OTel context，跨 thread 不丟。
  • Sampling 兩種：head-based（簡單但盲）、tail-based（保留壞 trace、需 Collector）。
  • OTel Collector 是生產必備：後端解耦、批次、tail sampling、過濾敏感資料、多後端 fan-out。
  • 後端選型：Tempo + Grafana（OSS、便宜）、Jaeger（自我託管熟悉）、Datadog（SaaS 無維護）。
  • Log + Trace 雙向跳轉 是 OTel 的真正價值 ── 三大訊號用同一 traceId 串起。
  • SRE 重點：sampling 策略、retention 分層、敏感資料治理、native build 驗證、Collector 高可用。
