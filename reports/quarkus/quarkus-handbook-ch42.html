Chapter 42 · Part IX

進階測試：Testcontainers、WireMock 與 Native

@QuarkusTest 覆蓋了大多數測試需求，但有些場景需要更真實的環境 ── @QuarkusIntegrationTest 測試打包後的 artifact（JAR 或 Native binary）， Testcontainers 用 Docker 起真實 DB / Kafka， WireMock 精確模擬外部 HTTP API 的各種失敗場景。 最後 ── Quarkus 的 Continuous Testing， 讓測試像 hot reload 一樣在後台自動跑，改完程式碼幾秒內就知道測試結果。

@QuarkusIntegrationTest：測試真實 Artifact

@QuarkusTest 在 test JVM 內啟動應用；@QuarkusIntegrationTest 對已打包的 artifact 做黑盒測試 ── 可以測 JAR 或 Native binary：

Java · 把 @QuarkusTest 變成 IT
import io.quarkus.test.junit.QuarkusIntegrationTest;

// ① 繼承 @QuarkusTest 的測試類別（共用測試邏輯）
@QuarkusIntegrationTest
class ProductResourceIT extends ProductResourceTest {
    // 不需要額外程式碼
    // 相同 test 方法，但跑在打包後的應用上
}
bash · 分別執行
# 只跑 @QuarkusTest（快）
./mvnw test

# 打包後跑 @QuarkusIntegrationTest（慢，但測真實 JAR）
./mvnw verify

# 測 Native binary（最慢，CI 才跑）
./mvnw verify -Pnative
⚠
@QuarkusIntegrationTest 的限制
應用跑在獨立 process 中，test 在另一個 JVM ── 因此：
  • @Inject 無效（兩個 JVM）── 只能用 HTTP 測試
  • @InjectMock 無效── 無法 mock CDI bean
  • Dev Services 仍然有效（在外部 container 中）
所以 IT 適合黑盒 REST API 測試，不適合細粒度 unit 測試。

Testcontainers：自訂外部依賴

Dev Services 已能自動啟 PostgreSQL、Kafka、Redis。 但如果你用了 Dev Services 尚不支援的服務（如 CockroachDB、Couchbase、特定版本的 Oracle）， 用 QuarkusTestResourceLifecycleManager + Testcontainers：

pom.xml
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-test-common</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
</dependency>
Java · 自訂 QuarkusTestResourceLifecycleManager
import io.quarkus.test.common.QuarkusTestResourceLifecycleManager;
import org.testcontainers.containers.PostgreSQLContainer;
import java.util.Map;

public class PostgresTestResource implements QuarkusTestResourceLifecycleManager {

    // 使用 Testcontainers 靜態容器（跨 test class 共用，避免重複起容器）
    static final PostgreSQLContainer<?> DB =
        new PostgreSQLContainer<>("postgres:16-alpine")
            .withDatabaseName("catalog_test")
            .withUsername("test")
            .withPassword("test");

    @Override
    public Map<String, String> start() {
        DB.start();
        return Map.of(
            "quarkus.datasource.jdbc.url", DB.getJdbcUrl(),
            "quarkus.datasource.username", DB.getUsername(),
            "quarkus.datasource.password", DB.getPassword()
        );
    }

    @Override
    public void stop() {
        // Testcontainers 靜態容器自動管理生命週期
        // DB.stop();  // 不需要，Ryuk 自動清理
    }
}
Java · 使用自訂 resource
import io.quarkus.test.common.QuarkusTestResource;

@QuarkusTest
@QuarkusTestResource(PostgresTestResource.class)
class OrderRepositoryIntegrationTest {

    @Inject OrderRepository repo;

    @Test
    @Transactional
    void persistAndFind() {
        var order = new Order("cust-1");
        repo.persist(order);

        var found = repo.findById(order.id);
        Assertions.assertNotNull(found);
    }
}

@QuarkusTestResource 選項

Java · restrictToAnnotatedClass
// 只為這個 test class 啟動，不影響其他 test
@QuarkusTestResource(
    value = PostgresTestResource.class,
    restrictToAnnotatedClass = true       // ← 隔離到這個 class
)
class IsolatedDbTest { ... }

WireMock：模擬外部 HTTP API

測試需要呼叫外部 API（payment gateway、匯率 API）時，WireMock 可以：

  • 模擬各種 HTTP 回應（200、429、503、超時）
  • 驗證你的服務發出了正確的請求
  • 測試容錯邏輯（@Retry、@CircuitBreaker 是否正確觸發）
pom.xml
<dependency>
    <groupId>io.quarkiverse.wiremock</groupId>
    <artifactId>quarkus-wiremock</artifactId>
    <version>1.4.0</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>io.quarkiverse.wiremock</groupId>
    <artifactId>quarkus-wiremock-test</artifactId>
    <version>1.4.0</version>
    <scope>test</scope>
</dependency>
application.properties · 指向 WireMock
# WireMock 啟動後 port 透過 ${quarkus.wiremock.server-port} 取得
%test.payment.gateway.url=http://localhost:${quarkus.wiremock.server-port}/
%test.inventory.service.url=http://localhost:${quarkus.wiremock.server-port}/
Java · WireMock stub 各種場景
import com.github.tomakehurst.wiremock.WireMockServer;
import com.github.tomakehurst.wiremock.client.WireMock.*;
import io.quarkus.test.common.QuarkusTestResource;
import io.quarkiverse.wiremock.devservice.ConnectWireMock;

@QuarkusTest
@ConnectWireMock           // ← 注入 WireMockServer
class PaymentServiceTest {

    WireMockServer wireMock;  // 自動注入

    @Test
    void charge_success_shouldReturnApproved() {
        wireMock.stubFor(
            post(urlEqualTo("/api/charge"))
                .withRequestBody(matchingJsonPath("$.amount"))
                .willReturn(aResponse()
                    .withStatus(200)
                    .withHeader("Content-Type", "application/json")
                    .withBody("""
                        {"result":"APPROVED","transactionId":"txn-123"}
                        """))
        );

        given()
            .body(new ChargeRequest("prod-1", 100))
            .when().post("/api/orders")
            .then()
                .statusCode(201)
                .body("payment.status", equalTo("APPROVED"));

        // 驗證 payment client 確實呼叫了 gateway
        wireMock.verify(1, postRequestedFor(urlEqualTo("/api/charge")));
    }

    @Test
    void charge_gatewayDown_shouldReturnFallback() {
        wireMock.stubFor(
            post(urlEqualTo("/api/charge"))
                .willReturn(aResponse()
                    .withStatus(503)
                    .withFixedDelay(2000))   // 模擬 2s 超時
        );

        // CircuitBreaker + Fallback 觸發，應回傳降級結果
        given()
            .body(new ChargeRequest("prod-1", 100))
            .when().post("/api/orders")
            .then()
                .statusCode(202)
                .body("payment.status", equalTo("PENDING"));  // fallback

        wireMock.verify(moreThan(1), postRequestedFor(urlEqualTo("/api/charge")));
    }

    @Test
    void charge_rateLimit_shouldRetry() {
        // 前兩次 429，第三次成功
        wireMock.stubFor(
            post(urlEqualTo("/api/charge"))
                .inScenario("rate-limit")
                .whenScenarioStateIs("Started")
                .willReturn(aResponse().withStatus(429))
                .willSetStateTo("first-fail")
        );
        wireMock.stubFor(
            post(urlEqualTo("/api/charge"))
                .inScenario("rate-limit")
                .whenScenarioStateIs("first-fail")
                .willReturn(aResponse().withStatus(200)
                    .withBody("""{"result":"APPROVED"}"""))
        );

        given()
            .body(new ChargeRequest("prod-1", 100))
            .when().post("/api/orders")
            .then().statusCode(201);
    }
}

Continuous Testing：測試像 hot reload 一樣

Quarkus dev 模式內建 Continuous Testing ── 你改完程式碼，幾秒後自動跑受影響的 test：

bash · 啟動 Continuous Testing
quarkus dev

# 在 dev console 輸入：
# r → 跑所有測試（run tests）
# o → 切換 continuous testing on/off
# f → 切換 fail-focused（只顯示失敗）
# d → 切換 debugger attach
# s → 強制重新掃描
✓
Continuous Testing 改變開發體驗
傳統流程：改程式碼 → 手動執行 mvn test → 等 30 秒 → 看結果
Quarkus CT：改程式碼 → 幾秒後自動跑受影響 test → 直接看結果
Quarkus 只跑「與修改相關」的 test（類似 Jest 的 watch mode），極快。

Native Binary 測試

bash · CI pipeline：build native + 跑 IT
# 1. 打 Native image（container build，不需本地 GraalVM）
./mvnw package -Pnative \
  -Dquarkus.native.container-build=true \
  -Dquarkus.native.builder-image=quay.io/quarkus/ubi-quarkus-mandrel-builder-image:23.1-java21

# 2. 跑 @QuarkusIntegrationTest（自動測試剛建的 native binary）
./mvnw verify -Pnative -DskipTests=false
yaml · GitHub Actions CI
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - uses: actions/setup-java@v4
      with:
        java-version: '21'
        distribution: 'temurin'

    # 快：JVM 測試（每次 PR）
    - name: Run JVM tests
      run: ./mvnw test

    # 慢：Native 測試（只在 main branch 合併後）
    - name: Build and test native
      if: github.ref == 'refs/heads/main'
      run: ./mvnw verify -Pnative -Dquarkus.native.container-build=true

Kafka 整合測試

Java · 測試 Kafka consumer
import io.quarkus.test.junit.QuarkusTest;
import io.quarkus.test.common.DevServicesContext;
import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.junit.jupiter.api.*;

@QuarkusTest
class OrderConsumerTest {

    @Inject DevServicesContext devServicesContext;  // 取 Dev Service 資訊

    KafkaProducer<String, String> producer;

    @BeforeEach
    void setUp() {
        // 從 Dev Services 取 Kafka bootstrap server 位址
        String bootstrapServers = devServicesContext
            .devServicesProperties()
            .get("kafka.bootstrap.servers");

        producer = new KafkaProducer<>(Map.of(
            "bootstrap.servers", bootstrapServers,
            "key.serializer", "org.apache.kafka.common.serialization.StringSerializer",
            "value.serializer", "org.apache.kafka.common.serialization.StringSerializer"
        ));
    }

    @Test
    void sendOrder_shouldBeConsumedAndPersisted() throws Exception {
        String orderJson = """{"orderId":"ord-1","customerId":"cust-1","amount":99.99}""";

        producer.send(new ProducerRecord<>("orders", "ord-1", orderJson)).get();

        // 等待 consumer 處理
        Thread.sleep(2000);

        // 驗證 DB 中有資料
        given()
            .when().get("/api/orders/ord-1")
            .then().statusCode(200)
            .body("orderId", equalTo("ord-1"));
    }
}

測試策略建議

✓
Part IX 測試策略 Checklist
  1. Unit test 覆蓋業務邏輯── 無需 CDI，純 Mockito，最快
  2. @QuarkusTest 覆蓋 API 路徑── 每個 endpoint 至少 1 個 happy path + 1 個 error case
  3. WireMock 覆蓋容錯場景── 503、429、超時、fallback 是否正確觸發
  4. Testcontainers 覆蓋 DB schema── Migration、constraint、index
  5. @QuarkusIntegrationTest 覆蓋打包後── 少量，主要路徑
  6. Native 測試只在 CI/CD main branch── build 太慢，PR 不等
  7. Continuous Testing 開發時常開── 儘早發現回歸
  8. 同一 @TestProfile 的 test 合併── 減少 Quarkus 啟動次數
  9. @BeforeEach 清測試資料── 避免 test 互相影響
  10. 測試命名：given_when_then── createProduct_validInput_shouldReturn201

常見陷阱

症狀原因解法
@QuarkusIntegrationTest 無法 @Inject應用跑在獨立 process只用 HTTP / RestAssured 測試，不用 CDI injection
Testcontainers 啟動失敗沒有 Docker daemonCI 確保 Docker 可用；本地用 Rancher Desktop / Podman
WireMock 不接收請求application URL 指向錯誤的 port確認 %test.*.url=http://localhost:${quarkus.wiremock.server-port}/
Continuous Testing 改了 A 但沒跑 A 的 testQuarkus 依賴分析不完整按 r 強制跑所有 test
@QuarkusTestResource 影響了其他 test預設是 global加 restrictToAnnotatedClass = true
Native IT 比 JVM IT 慢 10 倍Native build 3–15 分鐘CI 把 native test 移到 nightly 或 main branch merge 後

本章小結

  • @QuarkusIntegrationTest：對打包後的 JAR 或 Native binary 做黑盒測試；不能用 @Inject，只能用 HTTP。
  • Testcontainers：透過 QuarkusTestResourceLifecycleManager 啟動自訂容器（DB、Kafka 等），並把連線資訊注入 Quarkus config。
  • 靜態容器（static final）跨 test class 共用，避免重複啟動。
  • WireMock：精確模擬外部 HTTP API 的成功、失敗、超時、rate limit 等場景；可驗證請求次數與內容。
  • Kafka 整合測試：透過 DevServicesContext 取 bootstrap server，用 KafkaProducer 發送測試訊息，驗證 consumer 處理結果。
  • Continuous Testing：dev 模式內建，改完程式碼幾秒後自動跑受影響 test，根本改變開發體驗。
  • Native 測試：./mvnw verify -Pnative；Build 慢，建議只在 main branch CI 跑。
  • 測試策略：Unit（多）→ @QuarkusTest（中）→ @QuarkusIntegrationTest（少）；WireMock 覆蓋容錯；CT 開發時常開。
