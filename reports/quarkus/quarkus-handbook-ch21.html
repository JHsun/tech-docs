Chapter 21 · Part V

Reactive Messaging 基礎

REST 是「請求／回應」── 但分散式系統還需要另一條軸線：事件驅動。 使用者下單後，要通知庫存、通知物流、寫審計日誌、寄 email；這些下游不該卡住下單回應。 Quarkus 用 SmallRye 實作 MicroProfile Reactive Messaging， 讓你用 @Incoming / @Outgoing 註解組合非同步管線， 並透過 connector 無痛切換 Kafka、AMQP、MQTT、JMS 等底層協定。本章是 Part V 的地基。

為什麼需要事件驅動架構

看一個經典痛點：下單流程同步寫法。

Java · ❌ 同步呼叫的問題
@POST @Transactional
public Order placeOrder(CreateOrderRequest req) {
    Order order = orderRepo.create(req);

    inventoryService.reserve(order);       // 80ms
    emailService.sendConfirmation(order);  // 200ms（外網）
    auditService.log(order);               // 30ms
    shippingService.notify(order);         // 150ms

    return order;                          // 總共 460ms 才回應使用者
}

四個問題層層疊加：

  1. 延遲長：使用者等到所有下游都跑完才看到回應
  2. 耦合緊：email 服務掛了，整個下單就失敗
  3. 擴展受限：流量尖峰所有下游一起壓力爆表
  4. 邏輯臃腫：placeOrder 知道太多其他服務的事

事件驅動的解法：

Java · ✓ 事件驅動寫法
@POST @Transactional
public Order placeOrder(CreateOrderRequest req) {
    Order order = orderRepo.create(req);
    orderEvents.send(new OrderCreated(order));    // 幾毫秒，立即回應
    return order;
}
// 其他服務各自監聽 OrderCreated 事件，獨立處理、獨立失敗、獨立重試

圖 21-1 ─ Reactive Messaging 三層模型：Message → Channel → Connector

1. Message：訊息信封

Message<T> 包裝 payload + metadata + ack/nack 動作。多數時候你只需要 payload，但需要時可拆封：

Java
// 簡單版：直接收 payload
@Incoming("orders")
public void process(Order order) { /* ... */ }

// 完整版：收 Message，能存取 metadata 與 ack
@Incoming("orders")
public CompletionStage<Void> process(Message<Order> msg) {
    Order order = msg.getPayload();
    // ... 處理
    return msg.ack();      // 顯式 ack
}

2. Channel：邏輯通道

Channel 是程式碼裡的名稱（如 "orders"），對應到 connector 的實體（Kafka topic、AMQP queue）。 若沒對應 connector，就是 in-memory channel（同一個 JVM 內傳遞）。

3. Connector：傳輸層

Connector 名稱對應技術常見場景
smallrye-kafkaApache Kafka事件溯源、log streaming、大量 throughput
smallrye-amqpAMQP 1.0（ActiveMQ Artemis、Azure Service Bus）企業 messaging、佇列
smallrye-mqttMQTTIoT、低頻寬
smallrye-rabbitmqRabbitMQ（AMQP 0.9.1）傳統 RabbitMQ 部署
smallrye-pulsarApache Pulsar多租戶、地理複製
smallrye-in-memory無外部依賴單體應用內、測試
✓
同樣的程式碼、不同的 transport
Reactive Messaging 最大的魅力：業務 code 不變，改 application.properties 就能換底層。 開發時用 in-memory，測試用 Testcontainers Kafka，生產用真的 Kafka cluster。

Producer：使用 Emitter

Java · REST endpoint 發送訊息
import org.eclipse.microprofile.reactive.messaging.Channel;
import org.eclipse.microprofile.reactive.messaging.Emitter;

@Path("/orders")
public class OrderResource {

    @Channel("orders")             // 對應 channel 名稱
    Emitter<Order> emitter;

    @POST
    public Response create(Order order) {
        emitter.send(order);       // 非阻塞發送
        return Response.accepted().entity(order).build();
    }
}

Processor：@Incoming + @Outgoing

Java · 中間處理階段
import org.eclipse.microprofile.reactive.messaging.Incoming;
import org.eclipse.microprofile.reactive.messaging.Outgoing;

@ApplicationScoped
public class KitchenService {

    @Incoming("orders")
    @Outgoing("kitchen-ready")
    public KitchenTicket prepare(Order order) {
        Log.infof("廚房正在準備：%s", order.item());
        return new KitchenTicket(order.id(), order.item(), "PREPARED", order.price());
    }
}

Consumer：@Incoming only

Java · 終端消費者
@ApplicationScoped
public class NotificationService {

    @Incoming("kitchen-ready")
    public void notify(KitchenTicket ticket) {
        Log.infof("通知客人：%s 已備好", ticket.item());
    }
}
ℹ︎
完全不用配置 connector？
這個範例用內部 channel（同 JVM 記憶體傳遞）。Quarkus 啟動時掃描所有 @Incoming / @Outgoing， 若 channel 兩端都在同一個應用內、沒對應 connector，就自動用 in-memory 連起來。 這讓「decouple 服務內部模組」極為輕量。

Emitter 進階用法

有回呼的 send

Java · 等送達確認
@Channel("orders")
Emitter<Order> emitter;

public Uni<Void> sendAndWait(Order order) {
    return Uni.createFrom().completionStage(
        emitter.send(order)        // 回 CompletionStage<Void>
    );
}

送出 Message 物件（附 metadata）

Java · 帶 metadata
import org.eclipse.microprofile.reactive.messaging.Message;
import org.eclipse.microprofile.reactive.messaging.Metadata;

emitter.send(Message.of(order)

背壓策略

Emitter 預設 buffer 256 個訊息，超過就拋例外。可以調整或改策略：

application.properties
# Emitter 緩衝大小
mp.messaging.outgoing.orders.merge=true
mp.messaging.outgoing.orders.overflow-strategy=BUFFER
mp.messaging.outgoing.orders.buffer-size=512

# 策略選項：BUFFER（預設）、DROP、FAIL、LATEST、NONE

Ack/Nack：可靠性的關鍵

訊息系統的核心問題：怎麼確認訊息已成功處理？解法：acknowledgement。

sequenceDiagram
  participant B as Broker
  participant C as Consumer

  B->>C: 送訊息
  alt 成功處理
    C-->>B: ack
    Note over B: 標記為已處理，不再送
  else 處理失敗
    C-->>B: nack
    Note over B: 視策略 retry / dead-letter
  end

圖 21-2 ─ Ack/Nack 訊息確認流程

三種 ack 模式

方法簽章Ack 時機
public void process(Payload p)方法成功回傳時自動 ack（拋例外則 nack）
public Uni<Void> process(Payload p)Uni 完成時 ack（失敗 nack）
public CompletionStage<Void> process(Message<P> m)你顯式呼叫 m.ack() 或 m.nack(t)
⚠
@Acknowledgment 改變預設
可以顯式控制：
  • POST_PROCESSING（預設）── 方法成功才 ack
  • PRE_PROCESSING ── 一收到就 ack（at-most-once）
  • MANUAL ── 你自己呼叫 m.ack()
  • NONE ── 不管，由連接器決定

失敗策略

application.properties
# Kafka 連接器的失敗策略
mp.messaging.incoming.orders.failure-strategy=fail
# 選項：
#   fail   ── 整個 channel 停止（預設，最嚴格）
#   ignore ── 紀錄 log 後繼續
#   dead-letter-queue ── 送到 DLQ topic（生產推薦）
mp.messaging.incoming.orders.dead-letter-queue.topic=orders-dlq

處理阻塞工作：@Blocking

Reactive Messaging 預設方法跑在 Vert.x event-loop。若你的處理函式會做阻塞 I/O（JDBC、傳統 client），必須加 @Blocking：

Java · @Blocking 處理
import io.smallrye.reactive.messaging.annotations.Blocking;

@Incoming("orders")
@Blocking      // dispatch 到 worker thread
@Transactional // 阻塞交易 OK
public void persistOrder(Order order) {
    orderRepo.persist(order);     // 阻塞 JDBC
}

// JDK 21+ 也可以用虛擬執行緒
@Incoming("orders")
@RunOnVirtualThread
@Transactional
public void persistOrderVT(Order order) {
    orderRepo.persist(order);
}
⚠
不加 @Blocking 是頭號 bug 來源
若你在沒標 @Blocking 的方法內做 JDBC / 大計算 / Thread.sleep，會看到：
WARN Thread Vert.x EventLoop has been blocked for XXX ms
然後整個應用停滯。第 17 章也提過：反應式鏈路被阻塞汙染等於毀掉所有並行優勢。

回傳 Multi：一進多出

Java · 一個 order 拆成多個 lineItem 事件
import io.smallrye.mutiny.Multi;

@Incoming("orders")
@Outgoing("line-items")
public Multi<LineItem> explode(Order order) {
    return Multi.createFrom().iterable(order.items());
}

多 @Incoming 合流

Java · 兩個來源合到同一個處理
@Incoming("orders-online")
@Incoming("orders-pos")
@Outgoing("orders-merged")
public Order merge(Order o) { return o; }   // 兩個來源統一進 orders-merged

PausableChannel：暫停與恢復

遇到下游壅塞、維護視窗時，可以動態暫停 channel：

Java · 動態暫停消費
import io.smallrye.reactive.messaging.ChannelRegistry;
import io.smallrye.reactive.messaging.PausableChannel;

@ApplicationScoped
public class IngestionController {

    @Inject ChannelRegistry registry;

    public void pause(String channel) {
        PausableChannel p = registry.getPausable(channel);
        if (p != null) p.pause();
    }

    public void resume(String channel) {
        PausableChannel p = registry.getPausable(channel);
        if (p != null) p.resume();
    }
}

啟用：

application.properties
mp.messaging.incoming.orders.pausable=true
# 啟動時初始狀態
mp.messaging.incoming.orders.initially-paused=false

測試

Reactive Messaging 提供 InMemoryConnector 在測試替換真實 broker：

bash
quarkus extension add smallrye-reactive-messaging-in-memory
Java · 測試
import io.quarkus.test.junit.QuarkusTest;
import io.smallrye.reactive.messaging.memory.InMemoryConnector;
import io.smallrye.reactive.messaging.memory.InMemorySink;
import io.smallrye.reactive.messaging.memory.InMemorySource;

@QuarkusTest
class OrderFlowTest {

    @Inject @Connector("smallrye-in-memory") InMemoryConnector connector;

    @Test
    void shouldProduceKitchenTicket() {
        InMemorySource<Order> orders = connector.source("orders");
        InMemorySink<KitchenTicket> tickets = connector.sink("kitchen-ready");

        orders.send(new Order("o-1", "Pizza", new BigDecimal("12.50")));

        await().atMost(2, SECONDS).until(() -> tickets.received().size() == 1);
        assertThat(tickets.received().get(0).getPayload().item()).isEqualTo("Pizza");
    }
}

貫穿專案進度：catalog-service 引入訂單事件

Java · 下單流程改用事件驅動
@ApplicationScoped
public class OrderService {

    @Inject EntityManager em;

    @Channel("order-events")
    Emitter<OrderEvent> emitter;

    @Transactional
    public Order placeOrder(CreateOrderRequest req) {
        Order order = new Order(req);
        em.persist(order);

        // 交易內 send：Kafka connector 預設等 commit 後才送
        emitter.send(new OrderEvent("ORDER_CREATED", order.id(), order.total()));

        return order;
    }
}

// 下游 1：庫存服務監聽
@ApplicationScoped
public class InventoryListener {
    @Incoming("order-events")
    @Blocking @Transactional
    public void onOrder(OrderEvent ev) {
        if ("ORDER_CREATED".equals(ev.type())) {
            inventoryService.reserve(ev.orderId());
        }
    }
}

// 下游 2：審計
@ApplicationScoped
public class AuditListener {
    @Incoming("order-events")
    @Blocking
    public void onOrder(OrderEvent ev) {
        auditLog.write(ev);
    }
}
⚠
Transactional Outbox 是更穩的做法
上面範例「交易內 send」實際上有 race ── 若 Kafka 在 commit 之間掛了，資料庫提交了但事件未送。 生產推薦用 Transactional Outbox pattern（第 26 章詳述）：先寫 outbox 表， CDC（如 Debezium）再讀表發到 Kafka。第 22 章還會介紹 Kafka 端的 idempotent producer。

DevOps / SRE 視角

✓
生產級 checklist
  1. 所有 incoming channel 設 dead-letter-queue，不要用預設 fail
  2. 啟用 smallrye-health，channel 異常時 K8s readiness 會自動處理
  3. 監控 Emitter buffer 使用率（接近 max 代表上游壓力大）
  4. 觀察 ack rate / nack rate / lag（Kafka）
  5. Pausable channel 給 SRE 一個維護視窗工具
  6. 避免單一 channel 訂閱多個 incoming（如 issue #25650 的 Azure Event Hub 問題）
  7. Tracing：OpenTelemetry 自動補上 trace context，事件流可追蹤端到端

常見陷阱

症狀原因解法
啟動失敗：No subscriber for channel X 有 @Outgoing 但無 @Incoming 對應，且 channel 不在 connector 配置內 加 connector 配置，或補上 @Incoming 處理者
event-loop blocked warn 處理方法做了阻塞操作 加 @Blocking 或 @RunOnVirtualThread
訊息消失但沒錯誤 預設 failure-strategy=fail 在 Kafka 上會卡住 partition 改 dead-letter-queue
Emitter buffer 滿、拋 OverflowException 下游處理速度跟不上發送 調大 buffer-size 或改背壓策略；根本是下游瓶頸
同 channel 不能同時用 @Outgoing 與 Emitter SmallRye 限制 拆成兩個 channel 對應同一個 Kafka topic
測試卡住 沒切換到 in-memory connector %test. 前綴覆寫 connector 配置

本章小結

  • 事件驅動解耦同步呼叫鏈路：低延遲、低耦合、獨立擴展。
  • Reactive Messaging 三層：Message（信封）→ Channel（邏輯通道）→ Connector（傳輸層）。
  • Producer 用 @Channel + Emitter；Processor/Consumer 用 @Incoming / @Outgoing。
  • 無配置 connector → 自動用 in-memory channel，方便應用內部解耦。
  • Message<T> 提供 payload + metadata + ack/nack；payload-only 寫法是糖衣。
  • 失敗策略：生產用 dead-letter-queue，不要用預設 fail。
  • 阻塞處理必須加 @Blocking 或 @RunOnVirtualThread，否則拖垮 event-loop。
  • PausableChannel 給 SRE 動態暫停的能力。
  • 測試用 InMemoryConnector + %test. 配置切換，不需起 Kafka。
  • 「交易內 send」有風險，生產推薦 Transactional Outbox（第 26 章）。
