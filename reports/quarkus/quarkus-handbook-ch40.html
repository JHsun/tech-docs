效能調校：Native、GC、Connection Pool

Quarkus 預設就很快 ── 但「快」不代表不需要調校。本章從最有效益的幾個維度切入： Native vs JVM 模式選型（啟動、記憶體、吞吐量三角取捨）、 GC 選型與 Heap 配置（容器環境的陷阱）、 Connection Pool 調校（被忽視最久的效能瓶頸），最後涵蓋 Caching、反序列化優化、AOT JAR。 每個調校點都附有可直接貼進 application.properties 的配置模板。

建 Native Image

bash
# 本地環境需要安裝 GraalVM 或 Mandrel
./mvnw package -Pnative

# 或：用 Docker 建（CI 推薦，不用本地裝 GraalVM）
./mvnw package -Pnative -Dquarkus.native.container-build=true \
               -Dquarkus.native.builder-image=quay.io/quarkus/ubi-quarkus-mandrel-builder-image:23.1-java21

AOT JAR（介於 JVM 和 Native 之間）

Quarkus 3.32+ 推出 AOT JAR，在 JVM 上執行但預先做 ahead-of-time class initialization， 啟動時間約減少 50%（實測從 380ms 降到 190ms），同時保留 JVM 的所有診斷能力：

application.properties
# 使用 AOT JAR 打包方式（Quarkus 3.32+）
quarkus.package.jar.type=aot-jar
bash
./mvnw package -Dquarkus.package.jar.type=aot-jar

GC 選型與 Heap 配置

GC 選型

GC特性適合
G1GC（預設）通用，低 pause多數情況，Heap 4GB 以上效果好
ZGC亞毫秒 pause，大 Heap對 latency 極敏感，Heap 8GB+
Shenandoah亞毫秒 pause，中等 HeapOpenJDK（非 Oracle），latency 優先
SerialGC單 thread，記憶體最省極小型容器（<256MB）
Dockerfile / JVM flags
# 一般生產（G1GC，512MB limit）
java -XX:+UseG1GC \
     -Xmx384m -Xms128m \
     -XX:MaxRAMPercentage=75 \
     -jar quarkus-run.jar

# Latency 優先（ZGC，4GB limit）
java -XX:+UseZGC \
     -Xmx3g -Xms512m \
     -jar quarkus-run.jar

# 超小容器（128MB limit）
java -XX:+UseSerialGC \
     -Xmx96m -Xms32m \
     -XX:MaxRAMPercentage=75 \
     -jar quarkus-run.jar

容器 Heap 最重要的陷阱

⚠
不設 -Xmx 的容器 = Heap 等於機器記憶體
JVM 預設 Heap = 物理記憶體 / 4。容器 limit 是 512MB，但你的 Kubernetes 節點有 64GB， JVM 以為自己有 16GB Heap ── 超出 limit 後 Pod 被 OOMKilled。

解法：用 MaxRAMPercentage（推薦）： -XX:MaxRAMPercentage=75 ── JVM 讀 cgroup 限制，自動設 75%。
或：明確設 -Xmx（精確但需每個 Pod 算一次）。
Kubernetes · 推薦的 JVM 容器 flags
env:
- name: JAVA_OPTS
  value: >-
    -XX:+UseG1GC
    -XX:MaxRAMPercentage=75
    -XX:+ExitOnOutOfMemoryError
    -XX:+HeapDumpOnOutOfMemoryError
    -XX:HeapDumpPath=/tmp/heapdump.hprof
    -Djava.util.logging.manager=org.jboss.logmanager.LogManager
    -XX:+UseContainerSupport
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"
    cpu: "1000m"

Connection Pool：被忽視的效能瓶頸

Connection Pool 配置錯誤是最常見的 Quarkus 效能問題來源之一。 太小 → 請求排隊等 connection；太大 → DB 端 connection overhead 超出負荷。

Pool Size 公式

一個常用的起點（HikariCP / Agroal 作者建議）：

ℹ︎
Pool Size = 核心數 × 2 + 磁碟數（通常是 1）
範例：8 核心機器 → pool size = 8 × 2 + 1 = 17
這是 DB 端 thread 利用率的最佳點，不是「越大越好」。
過大的 pool 反而讓 DB 端 context switch 更多，整體吞吐量下降。
application.properties · Agroal 配置
# JDBC Connection Pool（Agroal）
quarkus.datasource.jdbc.min-size=5          # 維持最小連線數
quarkus.datasource.jdbc.max-size=20         # 根據上述公式調整
quarkus.datasource.jdbc.acquisition-timeout=30S   # 拿不到 connection 多久後 fail
quarkus.datasource.jdbc.idle-removal-interval=5M  # 閒置連線回收間隔
quarkus.datasource.jdbc.max-lifetime=8M           # 連線最大壽命（防 DB 斷開）
quarkus.datasource.jdbc.validation-query-sql=SELECT 1

# 開啟連線池 metrics（Micrometer 自動偵測）
quarkus.datasource.jdbc.telemetry=true

Connection Pool Metrics 監控

✓
關鍵 Metrics
  • agroal_active_count：目前使用中的連線數
  • agroal_awaiting_count：等待連線的請求數 ── 這個 >0 代表 pool 不夠大
  • agroal_max_used_count：歷史峰值 ── 評估 max-size 是否夠用
  • agroal_acquisition_time：拿 connection 的 latency ── 上升代表 pool 壓力
Grafana alert：agroal_awaiting_count > 0 超過 30s → 增大 pool 或優化 query。

Caching：最有效益的效能加速

在正確的地方加 cache 可以讓 P99 latency 降低一個數量級。Quarkus 提供 quarkus-cache 基於 Caffeine：

Java · @CacheResult
import io.quarkus.cache.CacheResult;
import io.quarkus.cache.CacheInvalidate;
import io.quarkus.cache.CacheInvalidateAll;

@ApplicationScoped
public class ProductService {

    // 回傳值自動 cache，key = productId
    @CacheResult(cacheName = "products")
    public Product findById(Long productId) {
        return productRepo.findById(productId);
    }

    // 更新後讓 cache 失效
    @CacheInvalidate(cacheName = "products")
    public void update(@CacheKey Long productId, Product updated) {
        productRepo.save(updated);
    }

    // 清空整個 cache（如批量更新後）
    @CacheInvalidateAll(cacheName = "products")
    public void importAll(List<Product> products) {
        productRepo.saveAll(products);
    }
}
application.properties · Cache 配置
quarkus.cache.caffeine."products".maximum-size=1000
quarkus.cache.caffeine."products".expire-after-write=5M      # 5 分鐘失效
quarkus.cache.caffeine."products".metrics-enabled=true        # 輸出 hit rate 到 Micrometer
⚠
Cache 什麼不能快取
  • 用戶特定資料（個人購物車）── 用 Redis，Caffeine 是 process-level cache
  • 金流 / 庫存等強一致性資料── cache 可能 stale 導致超賣
  • 大型物件（PDF、圖片）── 很快把 Heap 吃完
Caffeine 最適合：參考資料（商品分類、匯率）、高頻讀低頻寫、短暫 stale 可接受。

Jackson Reflection-free 序列化（Quarkus 3.20+）

傳統 Jackson 用 reflection 序列化物件 ── 慢、不 native-friendly。 Quarkus 3.20+ 在 build-time 生成靜態 serializer，無需 reflection：

application.properties
# 啟用 reflection-free Jackson serialization（Quarkus 3.20+）
quarkus.rest.jackson.optimization.enable-reflection-free-serializers=true

效果：序列化更快、Native build 更穩定（減少 reflection 配置）。

生產 JVM Flags Checklist

bash · 完整生產 JVM flags
java \
  # GC
  -XX:+UseG1GC \
  -XX:MaxRAMPercentage=75 \          # 讀 cgroup，不超過容器 limit 的 75%
  -XX:+UseContainerSupport \          # 讓 JVM 知道自己在容器裡
  # 故障時自動 dump
  -XX:+ExitOnOutOfMemoryError \       # OOM 時立即退出（讓 K8s 重啟）
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/tmp/oom.hprof \
  # JFR 常態收集
  -XX:StartFlightRecording=settings=default,disk=true,maxsize=256M \
  # Quarkus 必要
  -Djava.util.logging.manager=org.jboss.logmanager.LogManager \
  # Virtual Thread（JDK 21）
  -Djdk.tracePinnedThreads=short \    # 偵測 pinning（staging 用，prod 可關）
  -jar quarkus-run.jar

Extension Audit：刪除不用的擴充

每個 Quarkus 擴充都會增加 build-time 掃描量與 runtime 記憶體。 不用的擴充要刪掉：

bash · 查看目前擴充
quarkus extension list --installed

# 移除不需要的
quarkus extension remove hibernate-search-orm-elasticsearch
application.properties · 關閉 Hibernate 用不到的功能
# 不用 2nd level cache → 關掉省記憶體
quarkus.hibernate-orm.second-level-caching-enabled=false

# 不用 Hibernate statistics
quarkus.hibernate-orm.statistics=false

# 不要自動 validate schema（交給 Flyway 管理）
quarkus.hibernate-orm.database.generation=none

# 開啟 Hibernate batch insert（大批量操作效能提升 10x）
quarkus.hibernate-orm.jdbc.statement-batch-size=50

DevOps / SRE 視角

✓
效能調校優先順序
  1. 先量測，再優化── 用 Micrometer 確認瓶頸在哪，不要猜
  2. Connection Pool 先設對── 多數效能問題在這
  3. Heap sizing 用 MaxRAMPercentage── 容器環境避免 OOMKill
  4. 適當 Caching── 把熱點查詢的 DB 壓力降 90%
  5. GC 選對── latency 敏感用 ZGC；一般用 G1GC
  6. Native 不是一定要── 高 QPS 穩定服務 JVM mode throughput 更高
  7. 刪不用的 extension── 減少 build time 和 runtime 開銷
  8. Reactor（Event Loop）不阻塞── @RunOnVirtualThread 或 @Blocking
  9. 壓測在 staging── -XX:ActiveProcessorCount=2 模擬生產 CPU limit
  10. 逐步調校── 每次改一個參數，觀察 3 個 Golden Signals

常見陷阱

症狀原因解法
Container OOMKilledHeap 超過 cgroup limit-XX:MaxRAMPercentage=75 + 設合理 limit
Connection pool 排隊、P99 spikemax-size 太小監控 agroal_awaiting_count，增大 pool 或優化慢 query
Native build 報 reflection 錯誤某個 library 用了動態 reflection加 reflect-config.json 或換不用 reflection 的 library
JVM warmup 後 P50 好但 P99 高偶發 GC pause（G1GC full GC）增大 Heap 避免 Full GC，或換 ZGC
Caffeine cache hit rate 低TTL 太短或 key 差異太大延長 expire-after-write，或換更粗粒度的 key
AOT JAR 沒有速度提升JDK 版本不支援確認 JDK 21+，特定 JDK 版本有效（IBM Semeru 效果最明顯）

本章小結

  • Native vs JVM：Scale-to-zero、記憶體嚴格 → Native；高吞吐持續服務 → JVM；兩者中間 → AOT JAR。
  • AOT JAR（Quarkus 3.32+）：JVM 上的 ahead-of-time class init，啟動時間減半，保留 JVM 診斷能力。
  • Heap sizing：容器必用 -XX:MaxRAMPercentage=75 -XX:+UseContainerSupport，避免 OOMKill。
  • GC 選型：G1GC 通用；ZGC / Shenandoah 給 latency 敏感場景。
  • Connection Pool：公式 = 核心數 × 2 + 1；監控 agroal_awaiting_count；設合理 max-lifetime。
  • Caching（Caffeine）：最高 ROI 的調校；適合參考資料、高讀低寫；監控 hit rate。
  • Jackson reflection-free（Quarkus 3.20+）：build-time serializer，快且 native-friendly。
  • 生產 JVM flags：MaxRAMPercentage、ExitOnOutOfMemoryError、HeapDumpOnOOM、JFR 常態開啟。
  • Extension audit：不用的擴充、Hibernate 功能都刪掉，減少 build time 與 runtime 記憶體。
  • 調校原則：量測 → 找瓶頸 → 一次改一個 → 觀察 Golden Signals。
