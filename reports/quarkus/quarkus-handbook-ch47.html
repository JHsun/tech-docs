Quarkus Update 與版本管理

Quarkus 的快速發版節奏（每 4–6 週一個 minor）是雙刃劍 ── 功能進步快，但跟不上就積累技術債。 本章解析 Quarkus 的 版本命名規則（LTS vs non-LTS）、quarkus update 工具的工作原理、 Dependabot 自動 PR 設定，以及跨 major 版本遷移的策略。 最後用整個 Part X 的全景圖做收尾 ── 從源碼到 production container image 的完整 pipeline。

Quarkus 版本命名與 LTS

版本類型特點適合
LTS（Long Term Support）每年發布，支援 3 年；Red Hat 商業支援可選企業生產環境、合規要求、穩定優先
non-LTS每 4–6 週發布，只維護 4 週（下一版出就停）跟上最新功能、實驗性專案
ℹ︎
本書版本：Quarkus 3.33 LTS
Quarkus 3.20 起為 LTS，支援至 2027 年 3 月。
LTS 仍然收 bug fix 和安全更新，但不加新功能。
生產建議：用 LTS。新功能實驗：可跟 non-LTS，但不要上生產。

quarkus update 深入解析

quarkus update 底層用 OpenRewrite（現代 Java 代碼遷移框架）做：

它做了什麼例子
更新 BOM 版本3.8.x → 3.33.0
更新廢棄的 API@QuarkusTest 搭配舊 annotation → 新 annotation
更新設定 key已重命名的 properties key
更新 importjavax.* → jakarta.*（2.x → 3.x 跨版本）
更新 pom.xmlplugin 版本、dependency 版本
bash · 完整升版流程
# 0. 確保 git 沒有未提交的改動（保護現場）
git status

# 1. 看有哪些更新
quarkus update --dry-run

# 2. 執行更新
quarkus update

# 3. 看 git diff，確認改動符合預期
git diff

# 4. 跑測試
./mvnw verify

# 5. 如果測試過了就提交
git add -A && git commit -m "Upgrade Quarkus to 3.33.0"

# 跨 stream 升（如 3.8 LTS → 3.20 LTS）
quarkus update --stream 3.20

# 從 2.x 升到 3.x（大版本跨越）
quarkus update --stream 3
# 注意：2.x → 3.x 會自動把 javax.* 換成 jakarta.*

它不做什麼

⚠
quarkus update 的局限
  • 不處理 quarkiverse（社群擴充）的版本更新
  • 不處理你自己的 third-party library（如 Jackson、Guava）
  • OpenRewrite recipe 不涵蓋 100% 的 breaking change
  • 不能保證功能行為不變 ── 測試是必要的
仍需要人工 review RELEASE_NOTES.md 和 migration guide。

Dependabot：自動 PR 跟進版本

yaml · .github/dependabot.yml
version: 2
updates:
  # Maven 依賴
  - package-ecosystem: maven
    directory: /
    schedule:
      interval: weekly
      day: monday
      time: "09:00"
    groups:
      # 把 Quarkus 相關依賴 group 成一個 PR
      quarkus:
        patterns:
          - "io.quarkus*"
          - "io.quarkus.platform*"
    # 限制最多幾個 open PR
    open-pull-requests-limit: 5
    reviewers:
      - platform-team
    labels:
      - dependencies
      - java

  # GitHub Actions
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
✓
Dependabot + quarkus update 組合策略
  1. Dependabot 每週開 PR 更新 BOM 版本（機械性工作自動化）
  2. CI 跑 test，綠燈後 merge
  3. quarkus update 處理需要 code 遷移的大版本升級（手動啟動）
  4. 保持「每次只升一個版本」── 多版本跳升 debug 困難

跨 Major 版本遷移策略

從 Quarkus 2.x 到 3.x 是最後一次大遷移（jakarta namespace）。以後的 major 版本跨越應該更平滑。 但如果你還在 2.x，以下步驟：

bash · 2.x → 3.x 完整流程
# 1. 確認現在 2.x 的最高版本（先升到最新 2.x）
quarkus update --stream 2

# 2. 建 branch
git checkout -b upgrade/quarkus-3

# 3. 升到 3.x（這一步自動做 javax → jakarta）
quarkus update --stream 3

# 4. 確認 import 都改好了
grep -r "javax\." src/main/java/ | grep -v ".class"

# 5. 修正殘留問題（通常是 third-party library 的 javax import）
# 找出問題 library → 換 jakarta 相容版本

# 6. 測試
./mvnw verify

# 7. 升到目標 LTS
quarkus update --stream 3.20

Part X 全景圖

本章（第 47 章）是 Part X 建構打包的最後一章。回顧整個 Part X 的完整 pipeline：

✓
從源碼到 Production 的完整路徑
  1. 開發：quarkus dev（hot reload）
  2. 建構工具：Maven / Gradle / Quarkus CLI（ch43）
  3. 打包格式：fast-jar（K8s 優化）→ target/quarkus-app/
  4. Container Image：Jib（CI 無 daemon）或 Docker（自訂 Dockerfile）（ch44）
  5. Native：Mandrel container build → ubi9-micro base（ch45）
  6. CI/CD：PR → 快速 test → main → build image → push → GitOps → ArgoCD（ch46）
  7. 版本維護：Dependabot weekly PR + quarkus update 大版本遷移（ch47）

本章小結

  • Quarkus LTS（每年）適合生產；non-LTS（每 4–6 週）適合實驗。
  • quarkus update：OpenRewrite 自動升 BOM 版本、更新廢棄 API、遷移 namespace。不做 third-party library、不保證 100% 無縫。
  • 跨 major 版本（2.x → 3.x）：quarkus update 自動處理 javax.* → jakarta.*；仍需測試。
  • Dependabot：每週自動 PR 更新 BOM；Quarkus group 合為一個 PR 降低噪音。
  • 升版原則：每次只升一個版本、先跑測試、再提交；多版本跳升 debug 困難。
  • Part X 完整鏈：dev → Maven/Gradle → fast-jar → Jib/Docker → Native(可選) → CI/CD → GitOps → prod。
