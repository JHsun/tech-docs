Apache Camel 整合

前面五章看的都是「訊息」── 但企業整合的世界遠不止於此：FTP 檔案、HTTP API、SOAP、SAP、Salesforce、SFTP、Twitter、SAP RFC、SQL 排程、Excel 報表… Apache Camel 是 20 年資歷的整合框架，提供 300+ component 和 80+ 種 Enterprise Integration Patterns（EIP）， 透過 camel-quarkus 在 Quarkus 上以 native 速度啟動。本章還會用 Camel 實作貫穿 Part V 的Transactional Outbox模式。

Camel 是什麼，又不是什麼

ℹ︎
Camel 不是 ESB
Camel 不是獨立部署的中介伺服器（不像 MuleSoft、TIBCO BusinessWorks）。它是嵌入式的整合 library， 被嵌進你的 Quarkus / Spring Boot 應用內運行。這代表：
  • 沒有「Camel server」要部署
  • 每個服務獨立打包整合邏輯（與微服務理念一致）
  • 降低 vendor lock-in
  • 仍享有 300+ 個現成 connector

  • Route：一個整合流程 ── from(source).process(...).to(target)
  • Exchange：流經 route 的訊息信封，含 in/out message、headers、properties、屬性、例外
  • Component：協定／系統的接頭。jms:、kafka:、file:、http:、aws-s3:… 300+ 種，URI 風格
  • EIP：80+ 種預製模式 ── Splitter、Aggregator、Content-Based Router、Wire Tap、Dead Letter Channel…

第一條 Route

Camel 在 Quarkus 上最常用 Java DSL。繼承 RouteBuilder，在 configure() 內寫 route：

Java · 簡單 file → log
import org.apache.camel.builder.RouteBuilder;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class FileToLogRoute extends RouteBuilder {

    @Override
    public void configure() {
        from("file:input?delete=true&noop=false")
            .routeId("file-watcher")
            .log("讀到檔案 ${header.CamelFileName}, 內容 ${body}")
            .to("file:output");
    }
}

應用啟動後，Camel 自動每秒掃描 input/ 目錄，找到檔案 → log → 搬到 output/。不用一行 main 函數。

幾個常用 EIP

Content-Based Router（基於內容路由）

Java
from("jms:queue:incoming")
    .choice()
        .when(header("region").isEqualTo("US"))
            .to("kafka:us-orders")
        .when(header("region").isEqualTo("EU"))
            .to("kafka:eu-orders")
        .otherwise()
            .to("kafka:other-orders");

Splitter（拆分）

Java · 一份訂單拆成多個 lineItem
from("direct:order")
    .split(jsonpath("$.items[*]"))    // 用 JsonPath 拆 items 陣列
        .to("kafka:line-items");

Aggregator（聚合）

Java · 把 5 秒內同一個 userId 的事件批次發送
from("kafka:user-events")
    .aggregate(header("userId"), AggregationStrategies.groupedBody())
        .completionTimeout(5000)
        .completionSize(100)
    .to("http://batch-processor/api/v1/events");

Wire Tap（旁路複製）

Java · 主流程繼續，同時送一份到稽核
from("kafka:transactions")
    .wireTap("kafka:audit-log")      // 旁路複製，不影響主流程
    .to("direct:process-transaction");

Dead Letter Channel（失敗訊息處理）

Java
errorHandler(deadLetterChannel("kafka:dlq")
    .maximumRedeliveries(3)
    .redeliveryDelay(1000)
    .useExponentialBackOff());

from("kafka:orders")
    .to("http://payment-service/charge");      // 失敗 3 次後送 DLQ

經典場景：橋接不同協定

Camel 的最大魅力是極低成本連接異質系統。看一個複雜但常見的範例 ── FTP 拉檔 → JSON 轉換 → JMS 廣播 → 同時寫 S3 備份：

Java · FTP → JSON → JMS + S3
@ApplicationScoped
public class PartnerFeedRoute extends RouteBuilder {

    @Override
    public void configure() {
        from("ftp://partner@ftp.partner.com/orders?password={{partner.ftp.password}}"
              + "&delete=true&include=order-.*\\.csv&delay=60000")
            .routeId("partner-feed")
            .log("收到合作夥伴檔案 ${header.CamelFileName}")
            .unmarshal().csv()                           // CSV 解析
            .split(body())                                // 每筆 row 拆開
                .process(this::enrichOrder)              // 補欄位
                .marshal().json(JsonLibrary.Jackson)     // 轉 JSON
                .multicast().parallelProcessing()
                    .to("jms:queue:orders-incoming")     // 廣播到 JMS
                    .to("aws2-s3://orders-archive?keyName=${exchangeId}.json"
                       + "&region=us-east-1");
    }

    void enrichOrder(Exchange exchange) {
        Map<String, String> row = exchange.getMessage().getBody(Map.class);
        row.put("ingested-at", Instant.now().toString());
        row.put("source", "partner-ftp");
    }
}

核心邏輯 30 行 ── 同樣功能用 raw client（Apache Commons FTPClient、Jackson、Artemis JMS client、AWS S3 SDK）寫，至少 300 行而且要自己處理錯誤、retry、並行、resource lifecycle。這是 Camel 最划算的場景。

何時用 Camel，何時不要

✓
用 Camel 的時機
  • 需要連接 3 個以上不同協定／系統（FTP + DB + JMS + HTTP + S3 …）
  • 要實作 EIP 模式（splitter、aggregator、content-based router）
  • 處理批次／檔案／排程／scheduled job
  • 整合沒有 Reactive Messaging connector 的系統（Salesforce、SAP、Twitter、ServiceNow 等）
  • 需要強大的 data transformation（CSV ↔ JSON ↔ XML ↔ Avro）
⚠
不用 Camel 的時機
  • 純 REST API 服務 ── 用 Quarkus REST 就好
  • 單一 Kafka 應用 ── 用 Reactive Messaging（前面章節）更輕量
  • 團隊不熟 Camel DSL ── 學習曲線真實存在
  • 業務邏輯比整合邏輯多得多 ── 不要為了用 hammer 找釘子
Camel 與 Reactive Messaging 不衝突，同一應用可同時用，按職責劃分。

壓軸大菜：Transactional Outbox 解決 dual-write

第 21 章預告的問題：DB 寫入與 Kafka send 無法原子。看個失敗場景：

Java · ❌ 危險寫法
@Transactional
public void placeOrder(Order order) {
    em.persist(order);                  // ① 寫 DB
    emitter.send(orderEvent(order));    // ② 送 Kafka
}                                       // ③ DB commit

四種失敗組合：

失敗點結果
① 之前掛OK：什麼都沒發生
① 與 ② 之間掛OK：DB 還沒 commit，整個 rollback
② 之後 ③ 之前掛❌：Kafka 收到事件但 DB rollback → 下游處理一筆不存在的訂單
③ commit 後但 Kafka send 還在飛❌：DB 寫了但 Kafka 從沒收到 → 下游錯過事件

圖 26-2 ─ Outbox 模式：應用只寫 DB（業務表 + outbox 表）一個交易，Debezium CDC 把 outbox 變化送 Kafka

✓
為什麼這解決了 dual-write
  • 應用只與 DB 互動，無 dual-write 問題
  • 業務表 + outbox 表在同一個 transaction，原子性由 DB 保證
  • Debezium 讀 transaction log（WAL）── DB commit 後才會出現的內容
  • Debezium 自身有 offset 持久化 + retry，至少保證 at-least-once
  • 下游消費 idempotent 即可達到 effectively-once

方法 A：Debezium Quarkus Outbox Extension

最快上手的方式：用官方 Debezium 出的 Quarkus 擴充。

xml · pom.xml
<dependency>
  <groupId>io.debezium</groupId>
  <artifactId>debezium-quarkus-outbox</artifactId>
  <version>3.4.2.Final</version>
</dependency>
Java · 定義事件
import io.debezium.outbox.quarkus.ExportedEvent;

public class OrderCreatedEvent implements ExportedEvent<String, JsonNode> {
    private final String orderId;
    private final JsonNode payload;
    private final Instant timestamp;

    @Override public String getAggregateId() { return orderId; }
    @Override public String getAggregateType() { return "Order"; }
    @Override public String getType() { return "OrderCreated"; }
    @Override public JsonNode getPayload() { return payload; }
    @Override public Instant getTimestamp() { return timestamp; }
}
Java · 發送事件
import jakarta.enterprise.event.Event;
import io.debezium.outbox.quarkus.ExportedEvent;

@ApplicationScoped
public class OrderService {

    @Inject EntityManager em;
    @Inject Event<ExportedEvent<?, ?>> eventBus;

    @Transactional
    public Order placeOrder(CreateOrderRequest req) {
        Order order = new Order(req);
        em.persist(order);                                    // 寫業務表

        eventBus.fire(new OrderCreatedEvent(order));          // 觸發 CDI event
        // ↑ Outbox 擴充攔截：在同一交易內把事件寫進 outbox 表
        return order;
    }
}

剩下的事：部署 Debezium Connector（Kafka Connect 或 Debezium Server）監看 PostgreSQL 的 outbox 表，把變更發到 Kafka。應用一行 Kafka 程式碼都不必寫。

方法 B：用 Camel 實作（適合 outbox 表已存在）

有時 outbox 表是 legacy schema、不能改，這時用 Camel 自己做 CDC：

Java · Camel + Debezium PostgreSQL component
from("debezium-postgres:my-cdc"
      + "?databaseHostname=postgres"
      + "&databaseUser=cdc_user"
      + "&databasePassword={{cdc.password}}"
      + "&databaseDbname=catalog"
      + "&databaseServerName=catalog-db"
      + "&tableIncludeList=public.outbox"
      + "&pluginName=pgoutput")
    .routeId("outbox-relay")
    .filter(header("aggregate_type").isEqualTo("Order"))
    .process(this::convertToCloudEvent)
    .toD("kafka:catalog.${header.aggregate_type}");

同樣達成原子性，且程式碼仍在 Quarkus 應用內運行，不需獨立部署 Kafka Connect。

貫穿專案進度：catalog-service 補上 Outbox

把 ch21 提到的「交易內 emitter.send()」風險徹底解決：

  1. 用 Debezium Quarkus Outbox 擴充（方法 A）
  2. 所有業務代碼從 emitter.send 改成 eventBus.fire
  3. 部署 Debezium Server（單獨 deployment）監看 outbox 表，發到 Kafka
  4. 下游消費（如第 22 章的 InventoryListener）程式碼完全不變，繼續從 Kafka 收

這個架構同時兼顧了：

  • 原子性（單一 DB 交易）
  • 可重播（Kafka log retention）
  • 可觀測（outbox 表可直接 SELECT 查歷史）
  • 低耦合（業務代碼不知道 Kafka 存在）

DevOps / SRE 視角

✓
Camel + Outbox 上線 checklist
  1. PostgreSQL WAL 設定：wal_level=logical、max_replication_slots 適當調整
  2. Debezium Server 用 K8s Deployment 部署，PVC 存 offset
  3. outbox 表清理：Debezium 提供 SMT 「after-commit delete」，或用 cron 定期 truncate
  4. 監控 replication slot lag：未消費的 WAL 堆積會塞滿磁碟
  5. Camel route 監控：每個 route 啟用 metrics（camel.management.statistics-enabled=true），暴露到 Micrometer
  6. Native build：camel-quarkus 各 component 標榜支援 GraalVM native，啟動 < 100ms

Native build 注意事項

  • 大部分 camel-quarkus component 已支援 native（檢查 component 文件的 ✓ 標記）
  • 少數動態反射（如某些 SOAP、Salesforce client）需要顯式 reflection 配置
  • 啟動時間：native binary 約 50-100ms vs JVM 約 2-3 秒

常見陷阱

症狀原因解法
Route 跑不起來，沒任何錯誤 configure() 沒被呼叫 / Bean 沒被掃描 確認 RouteBuilder 子類有 @ApplicationScoped
JMS component 連不上 沒裝 quarkus-artemis-jms 或 pooled-jms 同時裝 camel-jms + artemis-jms + pooled-jms（第 25 章）
Outbox 表越來越大 Debezium 沒設清理 SMT 加 EventRouter SMT 或 cron 清理
Camel route 處理慢拖垮整個 app route 沒用 threads() 或 parallelProcessing 顯式加並行處理；或用 seda: 解耦
Debezium replication slot lag 持續上升 下游消費跟不上、或 Debezium connector 掛了 檢查 Debezium 健康、擴大 Kafka consumer
Native build 失敗：missing reflection config 動態反射 class 沒註冊 加 @RegisterForReflection 或 reflect-config.json
Outbox 寫了但 Kafka 沒收到 PostgreSQL wal_level 不是 logical 改 postgresql.conf 並重啟 PG

本章小結

  • Camel 是嵌入式整合 library，不是 ESB；300+ component、80+ EIP。
  • Quarkus 整合用 camel-quarkus，每個 component 一個獨立擴充，按需安裝。
  • 三個核心：Route（整合流程）、Exchange（訊息信封）、Component（協定接頭）。
  • Java DSL 是主流：from(source).process(...).to(target)。
  • 常用 EIP：Content-Based Router、Splitter、Aggregator、Wire Tap、Dead Letter Channel。
  • Camel 最划算的場景：連接 3+ 異質協定（FTP + JMS + HTTP + S3 …）。
  • 純 Kafka 應用、純 REST 服務不需要用 Camel；與 Reactive Messaging 可共存。
  • Transactional Outbox 是解決 dual-write 的標準模式：應用單一 DB 交易、Debezium CDC 將 outbox 變更發到 Kafka。
  • 方法 A 用 Debezium Quarkus Outbox 擴充，最簡單；方法 B 用 Camel + Debezium component，更靈活。
  • SRE 重點：PostgreSQL wal_level=logical、replication slot lag 監控、outbox 表清理、native build 反射配置。
