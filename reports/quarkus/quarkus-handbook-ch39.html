Chapter 39 · Part VIII

Reactive 效能：Mutiny、Virtual Thread 與事件迴圈

Quarkus 底層建立在 Vert.x 的事件迴圈上 ── 這給了它驚人的吞吐量，但也埋下了一個陷阱： 在事件迴圈上執行阻塞程式碼，等同於讓整個服務停擺。 本章從三種並發模型（Blocking Worker / Reactive Event Loop / Virtual Thread）的根本差異講起， 釐清 @Blocking、@NonBlocking、@RunOnVirtualThread 的適用時機， 並給出 Mutiny 的核心操作模式（Uni、Multi）與生產最佳實踐。 2026 年的答案是：Virtual Thread 讓你寫阻塞風格卻有 Reactive 效能 ── 但有一些坑要知道。

最危險的陷阱：阻塞事件迴圈

⚠
在 Event Loop Thread 上阻塞 = 整個服務停擺
Quarkus REST（Reactive）預設在事件迴圈 thread 上執行 endpoint。如果你在裡面做了：
  • 傳統 JDBC 查詢（connection.createStatement()）
  • Thread.sleep()
  • 讀檔案（blocking File I/O）
  • 呼叫同步 REST client
── 你把那個 event loop thread 阻塞了。少數幾個 event loop thread 被阻塞，整個服務吞吐量暴跌。

偵測：Vert.x 自動告警

WARN [io.ver.cor.imp.BlockedThreadChecker] Thread Thread[vert.x-eventloop-thread-0,...] has been blocked for 3048 ms, time limit is 2000 ms
application.properties · 降低偵測門檻（開發用）
# 預設 2s 才警告，開發時降低到 500ms 讓問題更容易被發現
quarkus.vertx.warning-exception-time=500ms

@Blocking：最簡單的解法

告訴 Quarkus「我知道這個方法會阻塞，請丟到 worker thread pool」：

Java · @Blocking 保護 event loop
import io.smallrye.common.annotation.Blocking;

@GET
@Path("/report")
@Blocking                              // ← 丟到 worker thread
public Report generateReport() {
    // 這裡可以安心做 JDBC、Thread.sleep、同步 I/O
    return reportService.generate();
}

// 同理：Messaging consumer
@Incoming("orders")
@Blocking
public void processOrder(Order order) {
    orderService.process(order);       // JDBC 事務，需要 blocking
}
ℹ︎
Quarkus REST 的自動判斷
用 quarkus-rest（Reactive REST）時：
・回傳 Uni<T> 或 Multi<T> → 自動 non-blocking，在 event loop 執行
・回傳一般型別（String、Response）→ 自動 blocking，在 worker thread 執行
所以大多數情況不需要手動加 @Blocking。
但 Messaging（Kafka consumer）預設是 event loop ── 有 blocking 操作才需加 @Blocking。

@RunOnVirtualThread：JDK 21 的最佳選擇

Virtual Thread（Project Loom）讓你寫傳統阻塞風格，JVM 在底層用 carrier thread + park/unpark 實現高並發。 Quarkus 整合方式極簡：

Java · @RunOnVirtualThread
import io.smallrye.common.annotation.RunOnVirtualThread;

@GET
@Path("/products/{id}")
@RunOnVirtualThread                    // ← 在虛擬執行緒上執行
public Product getProduct(Long id) {
    // 可以安心呼叫阻塞式 JDBC、REST Client
    Product p = productRepo.findByIdBlocking(id);     // JDBC
    Stock s = inventoryClient.checkStockBlocking(id); // 同步 HTTP
    return p.withStock(s);
}

// Kafka consumer 也可以
@Incoming("orders")
@RunOnVirtualThread
public void processOrder(Order order) {
    orderService.process(order);
}

三種端點寫法對照

Java · 三種模型在同一個 Resource
@Path("")
public class FortuneResource {

    @Inject FortuneRepository repo;

    @GET @Path("/blocking")
    // 在 worker thread 執行（傳統阻塞 JDBC）
    public Fortune blocking() {
        return repo.findAllBlocking().get(0);
    }

    @GET @Path("/reactive")
    // 在 event loop 執行（Reactive JDBC / Hibernate Reactive）
    public Uni<Fortune> reactive() {
        return repo.findAllReactive()
            .map(list -> list.get(0));
    }

    @GET @Path("/virtual")
    @RunOnVirtualThread
    // 在 virtual thread 執行（寫阻塞，但有高並發）
    public Fortune virtual() {
        return repo.findAllBlocking().get(0);
    }
}

Virtual Thread 的坑：Pinning

Pinning（釘住）指 virtual thread 被卡在 carrier OS thread 上，無法 park/unpark。 這讓 virtual thread 退化成 platform thread，高並發下 carrier threads 耗盡：

原因現象JDK 24 後狀態
在 synchronized block 內阻塞carrier thread 被鎖住JEP 491（JDK 24）已大幅改善
Native method 阻塞同上未完全解決
ThreadLocal 大量使用不是 pinning，但每個 VT 都建 object，記憶體爆炸ScopedValue 是解法方向
✓
2026 年的實務建議
JDK 21 pinning 是真實風險，但 JDK 24（JEP 491）已大幅改善。
Quarkus 的 JDBC driver、Hibernate ORM 等都已更新到不用 synchronized。
大部分 Quarkus 場景 @RunOnVirtualThread 是安全的，但要：
  • 確認 JDK 21+（21 最低，24 最佳）
  • 第三方 library 有無 pinning 要自行測試（開 -Djdk.tracePinnedThreads=full 偵測）
  • CPU-bound 的長時間計算不適合 VT（用 worker thread pool 避免 monopolization）

偵測 Pinning

Mutiny 核心操作

Mutiny 是 Quarkus 的 Reactive 函式庫。兩個核心型別：

型別意義類比
Uni<T>0 或 1 個值（或失敗）非同步的 Optional<T>
Multi<T>0 到 N 個值的串流非同步的 Stream<T>，帶 backpressure

Uni 常用操作

Java · Uni 操作模式
// 建立 Uni
Uni.createFrom().item(42)
Uni.createFrom().failure(new RuntimeException("oops"))
Uni.createFrom().emitter(em -> { em.complete(result); })

// 轉換（不阻塞 thread）
Uni<String> name = repo.findById(id)
    .onItem().transform(p -> p.name());              // sync transform
    .onItem().transformToUni(p -> client.enrich(p)); // async flatMap

// 組合多個 Uni（平行執行）
Uni.combine().all().unis(userUni, stockUni)
    .asTuple()
    .map(tuple -> new Response(tuple.getItem1(), tuple.getItem2()));

// 錯誤處理
Uni<Product> result = repo.findById(id)
    .onFailure(NotFoundException.class).recoverWithItem(Product.empty())
    .onFailure().invoke(e -> Log.error("Failed", e))
    .onFailure().recoverWithUni(e -> fallbackRepo.findById(id));

// 等價的阻塞取值（不要在 event loop 用！）
Product p = repo.findById(id).await().indefinitely();

阻塞部分程式碼：runSubscriptionOn

Java · 只把阻塞部分丟到 worker
import io.smallrye.mutiny.infrastructure.Infrastructure;

public Uni<Report> processOrder(Order order) {
    return orderRepo.save(order)                       // reactive JDBC
        .onItem().transformToUni(saved ->
            // 這段呼叫了舊的同步 report service，丟到 worker thread
            Uni.createFrom().item(() -> legacyReport.generate(saved))
               .runSubscriptionOn(Infrastructure.getDefaultWorkerPool())
        );
}

Multi 與 Backpressure

Java · Kafka consumer backpressure
@Incoming("orders")
public Uni<Void> processOrder(Order order) {
    // 回傳 Uni → SmallRye Messaging 自動 backpressure：
    // 處理完才拉下一筆（pull-based loop）
    return orderService.handle(order)
        .invoke(() -> Log.infof("processed order %s", order.id()))
        .replaceWithVoid();
}

// 若不回傳 Uni（void method）→ fire-and-forget，沒有 backpressure
// @Incoming("orders")
// public void processOrderNoBackpressure(Order order) { ... }  // 慎用
⚠
Kafka Consumer backpressure 決策
@Incoming 方法回傳 Uni<Void> → 處理完才拉下一筆（背壓，推薦）
回傳 void → fire-and-forget，Kafka 持續推送（消費能力不足時會 OOM）
高吞吐量場景但有複雜業務邏輯，建議 Uni + @RunOnVirtualThread。

DevOps / SRE 視角

✓
生產 Reactive 效能 Checklist
  1. Vert.x blocked thread 告警監控── Prometheus metric vertx_pool_rejected_total 異常就告警
  2. 降低 blocking 偵測門檻── staging 設 500ms，prod 維持 2s，讓問題早點暴露
  3. Kafka consumer 用 Uni<Void> 回傳── 啟用 backpressure，防 OOM
  4. Reactive 方法絕不 .await().indefinitely()── 永遠阻塞 event loop
  5. Virtual Thread 用 JDK 21+── 不要在 JDK 17 上跑
  6. CPU-bound 長計算用 worker thread── VT monopolization 導致 carrier thread 耗盡
  7. 壓測 + 受限 CPU── -XX:ActiveProcessorCount=2 測試 event loop 敏感度
  8. 同一 app 三種模型可並存── 不需要全部統一，按需選最適合的

常見陷阱

症狀原因解法
Vert.x blocked thread 警告在 event loop 上做了阻塞操作加 @Blocking 或 @RunOnVirtualThread 或改 Reactive
Kafka consumer 消費越來越慢最終 OOMvoid method 沒有 backpressure，訊息堆積在記憶體改 Uni<Void> 回傳啟用 backpressure
Virtual Thread 高負載下效能退化有 pinning（synchronized block）加 -Djdk.tracePinnedThreads=full 找出並更新 library
CPU-bound 任務 VT 後更慢VT monopolization，carrier thread 不夠改用 worker thread pool 或 ManagedExecutor
Uni 鏈中 TransactionScoped 丟失Reactive 跨 thread 事務 scope 丟失用 Panache 或 Hibernate Reactive 的 Uni 事務 API
await().indefinitely() 導致 event loop 卡死在 event loop 上等待非同步結果只在 worker thread / VT 上 await，或保持 Uni 鏈

本章小結

  • Quarkus 底層是 Vert.x 事件迴圈 ── 在 event loop thread 阻塞是最危險的錯誤。
  • 三種模型：Blocking Worker（簡單）/ Reactive Event Loop（最高效）/ Virtual Thread（簡單且高效）。
  • @Blocking：最簡單的修復，讓 Quarkus 把方法丟到 worker thread pool。
  • @RunOnVirtualThread：JDK 21+ 最佳選擇 ── 寫阻塞程式碼，JVM 自動高並發。
  • Virtual Thread 的坑：Pinning（synchronized block 內阻塞）、CPU-bound monopolization、ThreadLocal 記憶體爆炸。JDK 24 大幅改善。
  • Mutiny Uni：非同步 0/1 值；transform / transformToUni / combine / 錯誤處理。絕不在 event loop 上 await()。
  • Kafka consumer 回傳 Uni<Void> 啟用 backpressure，防止消費端 OOM。
  • 選型原則：低並發 → 阻塞；I/O bound 高並發 → VT；極高吞吐 + 有 Reactive 能力 → Event Loop；CPU bound → Worker Thread。
  • 三種模型可在同一應用並存 ── 按 endpoint 特性分別選擇。
