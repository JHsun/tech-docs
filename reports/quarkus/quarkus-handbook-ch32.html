⚠
Level 0-1 是 OWASP A02 (Cryptographic Failures)
  • Level 0：硬編在 .java 檔；git push 一次 secret 永遠在 history（即使 force push 也可能被快取）
  • Level 1：commit 在 properties；任何讀 repo 的人都看得到
這兩種方式絕對禁止，用 git-secrets / pre-commit hook 自動擋。

Level 3：Kubernetes Secret + ConfigMap

多數 Quarkus 應用第一步是這個 ── K8s 內建、零成本。

傳統方式：mount 為檔案或 env var

yaml · Deployment 注入 Secret 為 env var
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-service
spec:
  template:
    spec:
      containers:
        - name: catalog
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: catalog-db-credentials
                  key: password
            - name: OIDC_CLIENT_SECRET
              valueFrom:
                secretKeyRef:
                  name: catalog-oidc
                  key: client-secret
application.properties
quarkus.datasource.password=${DB_PASSWORD}
quarkus.oidc.credentials.secret=${OIDC_CLIENT_SECRET}

進階方式：quarkus-kubernetes-config 直接讀

避免每個 secret 都要寫一段 Deployment yaml，用 quarkus-kubernetes-config 讓應用啟動時直接呼叫 K8s API：

bash
quarkus extension add kubernetes-config
application.properties
%prod.quarkus.kubernetes-config.enabled=true
%prod.quarkus.kubernetes-config.config-maps=catalog-config
%prod.quarkus.kubernetes-config.secrets.enabled=true
%prod.quarkus.kubernetes-config.secrets=catalog-db,catalog-oidc

# 設定的優先序：application.properties < ConfigMap < Secret < env var

應用啟動時自動讀指定 Secret/ConfigMap 的所有 key-value，當作 MicroProfile Config 來源。Service Account 需要 view 角色：

yaml · RBAC 配置
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: catalog-config-reader
  namespace: catalog
rules:
  - apiGroups: [""]
    resources: ["configmaps", "secrets"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: catalog-config-reader
subjects:
  - kind: ServiceAccount
    name: catalog
roleBinding:
  kind: Role
  name: catalog-config-reader
⚠
K8s Secret 並非「加密」儲存
K8s Secret 預設只是 base64 編碼，存在 etcd。要真正加密：
  • 啟用 etcd encryption at rest（雲廠商 managed cluster 通常已開）
  • 限制 namespace 內的 get secret RBAC
  • 敏感等級高 → 用 Vault（下一節）

Level 4：HashiCorp Vault

Vault 把機密管理升級成專門服務，提供 K8s Secret 給不到的能力：

能力K8s SecretHashiCorp Vault
靜態 secret✓✓
動態 secret（每次取都不同）✗✓（PostgreSQL、AWS IAM 等）
自動 rotation✗（要自己 K8s Operator）✓（內建 TTL）
稽核 log（誰讀了什麼）K8s audit log 粗粒度每個 secret 精確記錄
PKI（簽憑證）✗✓（mTLS 場景關鍵）
Transit 加解密服務✗✓（資料層加密）
動態存取控制K8s RBAC細粒度 policy + 多種 auth method

加擴充

bash
quarkus extension add vault

Dev Services for Vault 自動啟一個 Vault 容器、配置好 token、注入連線屬性 ── 與第 29 章的 Dev Services for Keycloak 一樣的體驗。

KV：靜態 secret 當 config 來源

application.properties
quarkus.vault.url=https://vault.example.com:8200
quarkus.vault.authentication.kubernetes.role=catalog
quarkus.vault.kv-secret-engine-mount-path=secret
quarkus.vault.kv-secret-engine-version=2

# 之後在 application.properties 直接用：
quarkus.datasource.password=${db.password}
# ↑ db.password 來自 Vault 的 secret/catalog/config，無感取得

Kubernetes Auth Method：無需密碼登入 Vault

圖 32-2 ─ Kubernetes Auth Method：用 Pod 的 ServiceAccount token 換 Vault token，免存密碼

這就是 Vault 在 K8s 內最常見的部署模式 ── 應用永遠不需要存 Vault credential，連接 Vault 用的 token 來自 K8s ServiceAccount，由 Vault 透過 K8s API 驗證。

動態 DB credentials

更進階的玩法：每次取得 DB 密碼都是不同的、短效的，Vault 動態建 PostgreSQL user：

application.properties
quarkus.datasource.credentials-provider=vault-kv-credentials-provider
quarkus.datasource.credentials-provider-name=vault-credentials

# Vault 動態 DB engine 配置
quarkus.vault.credentials-provider.vault-credentials.database-credentials-role=catalog-rw
quarkus.vault.credentials-provider.vault-credentials.kv-path=database/creds/catalog-rw
✓
動態 credential 解決什麼問題
  • 洩漏快速失效：每個密碼 TTL 1 小時，洩漏窗口短
  • 稽核精細：每個 Pod 用不同密碼，DB 端可看到哪個 Pod 連
  • 免手動 rotation：Vault 自動換
代價：DB 必須允許 Vault 建/刪 user（給 Vault 一個高權限 admin user）。

Transit 加密：把 Vault 當加密服務

應用要加密儲存某欄位（如使用者敏感欄位）── 又不想自己管 key？用 Vault Transit：

Java
import io.quarkus.vault.VaultTransitSecretEngine;

@ApplicationScoped
public class PiiService {

    @Inject VaultTransitSecretEngine transit;

    public String encryptSSN(String ssn) {
        return transit.encrypt("user-pii", ssn);
        // 回傳 vault:v1:abc123...  ← 可直接存 DB
    }

    public String decryptSSN(String ciphertext) {
        return transit.decrypt("user-pii", ciphertext).asString();
    }
}

Key 永遠不出 Vault，應用只送 plain/ciphertext 來回。Key rotation 透明（舊 ciphertext 仍能解，新加密用新 key）。

mTLS：服務間相互驗證

HTTP（即使用 TLS）只驗證伺服器身份。mTLS 同時驗證客戶端身份 ── 每個服務都有自己的憑證，連線時雙向出示。

  C->>C: 用 CA 驗 server cert

Quarkus 3.x 用 TLS Registry 配置

Quarkus 3.x 起引入 TLS Registry，把 TLS 配置中央化，多個元件（HTTP server、REST Client、Kafka、Vault）共用：

application.properties · 完整 mTLS 配置
# 定義一個 TLS configuration "mtls-config"
quarkus.tls.mtls-config.key-store.p12.path=/deployments/tls/keystore.p12
quarkus.tls.mtls-config.key-store.p12.password=${KEYSTORE_PWD}
quarkus.tls.mtls-config.trust-store.p12.path=/deployments/tls/truststore.p12
quarkus.tls.mtls-config.trust-store.p12.password=${TRUSTSTORE_PWD}

# HTTP server 用此 TLS config，並強制 client auth
quarkus.http.tls-configuration-name=mtls-config
quarkus.http.ssl.client-auth=required          # required / request / none

# REST Client 連下游服務時也用此 TLS config
quarkus.rest-client.inventory-api.tls-configuration-name=mtls-config
quarkus.rest-client.inventory-api.url=https://inventory.catalog.svc:8443

取得 client cert 資訊

Server 收到 mTLS 連線後，client cert 自動變成 SecurityIdentity：

Java
import io.quarkus.security.credential.CertificateCredential;
import java.security.cert.X509Certificate;

@Inject SecurityIdentity identity;

@GET @Path("/who")
public String whoAreYou() {
    // CN 自動變成 principal name
    String cn = identity.getPrincipal().getName();

    // 完整 X509 憑證可取得
    CertificateCredential cert = identity.getCredential(CertificateCredential.class);
    X509Certificate x509 = cert.getCertificate();

    return "Connected as %s, cert expires %s".formatted(cn, x509.getNotAfter());
}

把憑證 CN 對應到 role

application.properties · CN → roles 映射
# 啟用 cert→role 映射
quarkus.http.auth.certificate-role-properties=cert-roles.properties
cert-roles.properties
catalog=service,internal
billing=service,billing
admin-tool=admin

後續就能用 @RolesAllowed("service") 控制只有特定 service cert 能訪問。

圖 32-4 ─ cert-manager + Vault PKI：宣告式憑證、到期自動續期、無人工干預

yaml · Certificate CRD
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: catalog-mtls
  namespace: catalog
spec:
  secretName: catalog-mtls-cert          # 產出的 K8s Secret 名稱
  duration: 2160h                        # 90 天
  renewBefore: 720h                      # 到期前 30 天續

  commonName: catalog.catalog.svc
  dnsNames:
    - catalog.catalog.svc
    - catalog.catalog.svc.cluster.local

  issuerRef:
    name: vault-pki-issuer
    kind: ClusterIssuer

  keystores:
    pkcs12:
      create: true                       # 直接產 keystore.p12 (Java 友善)
      passwordSecretRef:
        name: keystore-password
        key: password

Pod 啟動時 mount 這個 Secret 為 volume，Quarkus 從 mount 路徑讀 keystore ── 整個生命週期無人工干預。

替代方案：Service Mesh

ℹ︎
Service Mesh 把 mTLS 變成基礎設施
上面 mTLS 的所有配置（憑證、TLS Registry、cert-manager）── Istio / Linkerd 等 Service Mesh 全包了：
  • Sidecar 代理（Envoy）攔截所有流量，自動加 mTLS
  • 憑證由 mesh 內部 CA 自動簽發、輪轉
  • 應用代碼完全不知道 mTLS 存在
  • SPIFFE/SPIRE 提供標準身份框架
有 Service Mesh 環境，本章的 mTLS 段就略過 ── 讓 mesh 處理。
沒 Service Mesh（小團隊、邊緣場景），Quarkus 內建 mTLS 是最務實的解。

Quarkus 與 Service Mesh 的關係

  • Istio / Linkerd：sidecar 透明處理 mTLS、流量管理、observability
  • Quarkus 端：應用層用 HTTP（無 TLS），mesh 接管網路層
  • 仍需 Quarkus 處理：使用者層認證（OIDC）、業務授權（@RolesAllowed）

分工：mesh 管「服務 A → 服務 B 安不安全」，Quarkus 管「使用者 alice 能不能做這件事」。

DevOps / SRE 視角

✓
生產 checklist
  1. git-secrets / pre-commit hook：擋住 secret commit 到 repo
  2. etcd encryption at rest：K8s 層基本要求
  3. Vault HA：3+ node Raft cluster，PostgreSQL 或 Integrated Storage 後端
  4. Vault unseal：用 auto-unseal（AWS KMS、Azure Key Vault、GCP KMS）避免人工輸入 key
  5. Vault audit log：寫到 SIEM（Splunk / ELK）
  6. Vault backup：snapshot 每天
  7. policy 最小權限：每個 service 一個 role，只能讀自己的 secret
  8. 禁止用 root token：Vault 初始化後立即註銷
  9. K8s NetworkPolicy：限制 Pod 只能呼叫 Vault Service，不能直連網路
  10. cert-manager 監控：憑證快過期警報（30/7/1 天）
  11. 定期 secret scan：trivy、TruffleHog 掃 image 與 git history

常見陷阱

症狀原因解法
git history 留有 secret 已 commit 過 用 BFG Repo-Cleaner 清除；secret 視為已洩漏，立即輪換
K8s Secret 顯示明文（kubectl get -o yaml） base64 不是加密 啟用 etcd encryption；RBAC 限制讀權限；改用 Vault
Vault Pod 重啟後所有 secret 取不到 Vault 預設啟動是 sealed 狀態 用 auto-unseal（KMS）
動態 DB credentials 用一陣子失效 Vault token / lease 過期未 renew Quarkus extension 自動 renew，檢查 logs；或設較長 TTL
mTLS 連線 SSL handshake failure truststore 不含對方 CA 檢查 truststore 內容；確保 CA cert 正確
cert-manager 不續期 controller 沒跑、Issuer 配置錯 kubectl describe certificate 看 events；檢查 Issuer 狀態
K8s ingress 終止 TLS 後 client cert 不見 L7 ingress 通常 terminate TLS 用 SSL passthrough 或在 ingress 後另起 mTLS proxy
Service Mesh 與 quarkus mTLS 衝突 應用層 + mesh 層雙重 TLS 選一個就好；通常選 mesh，Quarkus 走 HTTP

本章小結

  • 機密管理階梯：硬編 → 配置檔 → env var → K8s Secret → 外部 Vault，每階解決前一階的問題。
  • K8s Secret 是 base64 不是加密；用 quarkus-kubernetes-config 直接讀，搭配 RBAC 與 etcd encryption。
  • HashiCorp Vault 是專業機密管理：動態 secret、自動 rotation、稽核、PKI、Transit 加密。
  • Kubernetes Auth Method：Pod 用 ServiceAccount token 換 Vault token，應用內零 Vault credential。
  • 動態 DB credentials：每小時換密碼、洩漏窗口最小化、審計精細。
  • Vault Transit：加密服務化，key 永遠不出 Vault。
  • mTLS 提供機器身份驗證 ── server 也驗證 client。
  • Quarkus 3.x 用 TLS Registry 集中管理 TLS 配置，多元件共用。
  • CN 自動成為 SecurityIdentity 的 principal，可用 cert-role properties 映射 role。
  • cert-manager + Vault PKI 自動續期憑證 ── 解決手動管理憑證的地獄。
  • Service Mesh（Istio / Linkerd）把 mTLS 變透明基礎設施；有 mesh 就讓它做。
  • 分工：mesh 管服務間，Quarkus 管使用者層。
