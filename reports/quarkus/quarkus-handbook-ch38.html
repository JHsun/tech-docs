容錯彈性：SmallRye Fault Tolerance

分散式系統中失敗不是例外，而是常態。網路會抖動、DB 會短暫過載、第三方 API 會莫名其妙慢下來。 沒有容錯設計的 microservice 就像沒有安全帶的跑車 ── 平時沒問題，出事就全毀。 SmallRye Fault Tolerance 用五個注解解決五類問題： @Retry 消化瞬間抖動、@Timeout 切斷無窮等待、 @CircuitBreaker 阻止 cascading failure、@Bulkhead 隔離艙壁防鄰居拖垮、 @Fallback 讓降級有個樣子。本章把五者的使用場景、堆疊順序與調校邏輯講清楚。

@Retry：重試瞬間失敗

最常用的模式。DB 連線瞬間斷、第三方 API 503 一秒後恢復 ── retry 可以無痛吸收。

Java · 基本 retry
import org.eclipse.microprofile.faulttolerance.Retry;
import java.time.temporal.ChronoUnit;

@ApplicationScoped
public class InventoryClient {

    @Retry(
        maxRetries = 3,          // 最多重試 3 次（共 4 次呼叫）
        delay = 200,             // 每次間隔 200ms
        delayUnit = ChronoUnit.MILLIS,
        maxDuration = 2000,      // 整個 retry 流程最多 2s
        jitter = 50,             // 加隨機 ±50ms 防 thundering herd
        retryOn = {IOException.class, TimeoutException.class},  // 只對特定例外 retry
        abortOn = {ValidationException.class}  // 這種不要 retry（業務錯誤）
    )
    public Stock checkStock(String sku) {
        return restClient.get(sku);
    }
}

Exponential Backoff（SmallRye 擴充）

固定 delay 在 thundering herd（所有 retry 同時打爆剛恢復的服務）場景很危險。 用 Exponential Backoff 加上 jitter，讓 retry 分散：

Java · Exponential backoff
import io.smallrye.faulttolerance.api.ExponentialBackoff;

@Retry(maxRetries = 4, maxDuration = 10000)
@ExponentialBackoff(
    factor = 2,         // 每次翻倍：100ms → 200ms → 400ms → 800ms
    initialDelay = 100,
    maxDelay = 2000,
    jitter = 0.25       // ±25% 隨機
)
public Order placeOrder(CreateOrderRequest req) { ... }
✓
Exponential + Jitter 是生產的正確選擇
固定 delay → 所有 thread 同時醒來打爆服務。
Exponential + jitter → 自然分散，給服務恢復時間。
AWS、Google SRE 手冊都推薦 exponential backoff with jitter 作為 retry 標準模式。

@RetryWhen：結果判斷

有時候不是例外，而是回傳值表達失敗（如 HTTP 503）。用 @RetryWhen：

Java · 用回傳值決定是否 retry
import io.smallrye.faulttolerance.api.RetryWhen;

@Retry(maxRetries = 3)
@RetryWhen(result = IsServiceUnavailable.class)
public StockResponse checkStockHttp(String sku) {
    return restClient.check(sku);
}

// 判斷邏輯
public class IsServiceUnavailable implements Predicate<Object> {
    @Override
    public boolean test(Object result) {
        return result instanceof StockResponse r && r.statusCode() == 503;
    }
}

@Timeout：切斷無窮等待

沒有 timeout 的呼叫 = 線程可能永遠掛住。DB deadlock、網路中斷都可能造成呼叫永遠不回來。

Java
import org.eclipse.microprofile.faulttolerance.Timeout;

@Timeout(value = 2, unit = ChronoUnit.SECONDS)
public Payment charge(Order order) {
    return paymentGateway.charge(order);  // 超過 2s 就丟 TimeoutException
}

// 組合 @Retry：2s timeout、每次重試也有自己的 timeout
@Timeout(value = 2, unit = ChronoUnit.SECONDS)
@Retry(maxRetries = 2)
public Payment chargeWithRetry(Order order) {
    return paymentGateway.charge(order);
}
⚠
@Timeout 是 interrupt 機制，不保證立即停止
SmallRye FT 用獨立 thread + interrupt signal 實作 timeout。若下游 library 忽略 interrupt（某些阻塞 I/O），timeout 不會立即生效。
Reactive（Uni）場景應在 Uni 本身加 .ifNoItem().after(Duration).fail()，比 @Timeout 更可靠。

@Fallback：降級策略

所有 retry 失敗後、或 circuit breaker 開路後，用 fallback 給使用者一個還算合理的回應。

Java · 方式 A：fallback method
import org.eclipse.microprofile.faulttolerance.Fallback;

@ApplicationScoped
public class PricingService {

    @Retry(maxRetries = 2)
    @Fallback(fallbackMethod = "cachedPrice")
    public Price getPrice(String sku) {
        return externalPricer.price(sku);
    }

    // 簽名必須與 getPrice 一致（相同參數與回傳型別）
    public Price cachedPrice(String sku) {
        return cache.get(sku).orElse(Price.defaultPrice());
    }
}
Java · 方式 B：FallbackHandler 類別
import org.eclipse.microprofile.faulttolerance.ExecutionContext;
import org.eclipse.microprofile.faulttolerance.FallbackHandler;

@Fallback(value = PriceFallbackHandler.class)
public Price getPrice(String sku) { ... }

public class PriceFallbackHandler implements FallbackHandler<Price> {
    @Override
    public Price handle(ExecutionContext ctx) {
        // ctx.getFailure() 取到最後的例外
        // ctx.getParameters() 取到原始參數
        Log.warnf("Pricing service unavailable for sku=%s: %s",
            ctx.getParameters()[0], ctx.getFailure().getMessage());
        return Price.defaultPrice();
    }
}

@CircuitBreaker：阻止 Cascading Failure

Circuit Breaker（斷路器）是容錯模式中最複雜、也最重要的一個。它有三個狀態：

stateDiagram-v2
  [*] --> CLOSED: 初始（正常運作）
  CLOSED --> OPEN: 失敗率超過閾值
  OPEN --> HALF_OPEN: delay 後自動探測
  HALF_OPEN --> CLOSED: successThreshold 連續成功
  HALF_OPEN --> OPEN: 探測失敗

  note right of CLOSED: 所有請求正常通過
計算失敗率
  note right of OPEN: 所有請求立即失敗
丟 CircuitBreakerOpenException
  note right of HALF_OPEN: 只放少量請求
測試服務是否恢復

圖 38-2 ─ Circuit Breaker 三個狀態的轉換邏輯

Java · @CircuitBreaker
import org.eclipse.microprofile.faulttolerance.CircuitBreaker;

@CircuitBreaker(
    requestVolumeThreshold = 20,  // 滾動視窗大小（最近 20 次請求）
    failureRatio = 0.5,           // 50% 失敗率 → 開路
    delay = 5000,                 // 開路後 5s 才進 HALF_OPEN
    delayUnit = ChronoUnit.MILLIS,
    successThreshold = 3,         // HALF_OPEN 連續 3 次成功 → 關路
    failOn = {IOException.class, TimeoutException.class},
    skipOn = {ValidationException.class}  // 業務錯誤不算失敗
)
@Fallback(fallbackMethod = "stockFallback")
public Stock checkStock(String sku) {
    return inventoryService.check(sku);
}

public Stock stockFallback(String sku) {
    // CircuitBreakerOpenException 觸發
    return Stock.unknown(sku);
}

Circuit Breaker 調校指南

參數意義調校方向
requestVolumeThreshold滾動視窗大小太小 → 一兩次失敗就開路（誤判）；太大 → 失敗太多才觸發（反應慢）。生產建議 20–50
failureRatio觸發開路的失敗率0.5（50%）是通用起點；核心依賴可降到 0.3；非核心可提高到 0.7
delay開路後多久進 HALF_OPEN對應下游恢復時間。DB restart 約 30s；外部 API 可短一點 5–10s
successThresholdHALF_OPEN 連續成功幾次才關路2–5 次，防止瞬間恢復但不穩定又立刻開路

@Bulkhead：艙壁隔離

Bulkhead（艙壁）來自船艦設計：把船隔成多個艙，一個艙漏水不會讓整艘船沉。在 microservice 中，它限制同時執行的呼叫數量，防止一個慢的端點耗盡所有 thread。

Java · @Bulkhead
import org.eclipse.microprofile.faulttolerance.Bulkhead;

@Bulkhead(
    value = 10,          // 最多同時 10 個並發呼叫
    waitingTaskQueue = 5 // 超過 10 個時，最多排隊 5 個（同步才有）
)
@Fallback(fallbackMethod = "queueFull")
public Report generateReport(ReportRequest req) {
    return reportService.generate(req);   // 慢操作
}

public Report queueFull(ReportRequest req) {
    throw new ServiceUnavailableException("Too many concurrent reports");
}

Bulkhead vs Rate Limit

機制控制什麼典型場景
@Bulkhead同時並發數慢操作（DB export、PDF 生成）── 防並發過多
@RateLimit時間視窗內呼叫次數外部 API 有 QPS 限制（第三方 rate limit）
Java · @RateLimit（SmallRye 擴充）
import io.smallrye.faulttolerance.api.RateLimit;
import java.time.temporal.ChronoUnit;

@RateLimit(
    value = 100,          // 每時間窗口最多 100 次
    window = 1,
    windowUnit = ChronoUnit.SECONDS,
    minSpacing = 10,      // 最小間隔 10ms（防 burst）
    minSpacingUnit = ChronoUnit.MILLIS
)
public Quote getExchangeRate(String pair) {
    return forexProvider.quote(pair);    // 外部 API 有 100 QPS 限制
}

注解堆疊順序

多個注解同時用時，執行順序是固定的（由外到內）：

ℹ︎
執行順序（固定，不可改）
@Fallback → @CircuitBreaker → @RateLimit → @Timeout → @Bulkhead → @Retry → 實際方法

意思是：
1. Retry 包住實際呼叫（每次 retry 都有 timeout）
2. Bulkhead 在 retry 之外（只限制進入的並發，retry 不額外消耗 slot）
3. CircuitBreaker 在 Retry 之外（retry 的每次結果都被 CB 記錄）
4. Fallback 在最外層（CB 開路拋的 exception 也能被 fallback 處理）
Java · 完整堆疊範例
@Timeout(value = 1500, unit = ChronoUnit.MILLIS)      // 每次呼叫最多 1.5s
@Retry(maxRetries = 2)                                  // 最多重試 2 次
@ExponentialBackoff(initialDelay = 100, factor = 2)    // 100ms → 200ms
@CircuitBreaker(requestVolumeThreshold = 20, failureRatio = 0.5, delay = 10000)
@Bulkhead(value = 20)                                   // 最多 20 並發
@Fallback(fallbackMethod = "cachedInventory")
public Stock checkInventory(String sku) {
    return inventoryService.check(sku);
}

public Stock cachedInventory(String sku) {
    return cache.get(sku).orElse(Stock.unknown(sku));
}

Reactive 整合

SmallRye FT 原生支援 Mutiny Uni。回傳 Uni 的方法可以直接加所有 FT 注解：

Java · Reactive 方法
@Retry(maxRetries = 3)
@Timeout(value = 2, unit = ChronoUnit.SECONDS)
@CircuitBreaker(requestVolumeThreshold = 10, failureRatio = 0.5, delay = 5000)
@Fallback(fallbackMethod = "stockFallback")
public Uni<Stock> checkStockReactive(String sku) {
    return inventoryClient.check(sku);    // 回傳 Uni
}

public Uni<Stock> stockFallback(String sku) {
    return Uni.createFrom().item(Stock.unknown(sku));
}
⚠
Reactive + @Timeout 的注意事項
Reactive 方法的 @Timeout 只計算 Uni 訂閱到完成的時間，不是方法返回 Uni 的時間。
但更推薦在 Uni 鏈上用 .ifNoItem().after(Duration).failWith(...)，語意更清晰且不依賴 FT 的 timer thread。

Config Override：property 覆寫注解

不同 profile 可能需要不同的 timeout（dev 放寬、prod 嚴格）。用 properties 覆寫：

application.properties
# 全域調整所有 @Retry
Retry/maxRetries=3

# 只調整特定 class 的 method
com.example.catalog.InventoryClient/checkInventory/Retry/maxRetries=5
com.example.catalog.InventoryClient/checkInventory/Timeout/value=3000

# 在 dev 模式完全關閉 fault tolerance（測試用）
%dev.MP_Fault_Tolerance_NonFallback_Enabled=false

Fault Tolerance Metrics

SmallRye FT 自動曝露 Micrometer / MicroProfile Metrics 指標：

Metric意義
ft.invocations.totalFT 方法總呼叫次數（含 result、fallbackApplied 標籤）
ft.retry.retries.totalRetry 次數
ft.timeout.calls.totalTimeout 觸發次數
ft.circuitbreaker.state.totalCircuit Breaker 在各狀態的時間
ft.bulkhead.concurrent.executionsBulkhead 目前並發數（Gauge）
✓
Grafana 告警建議
  • CB 開路持續 > 30s：下游服務可能嚴重故障 → PagerDuty
  • Retry 率 > 20%：下游不穩定 → 先告警再觀察
  • Bulkhead 拒絕率 > 5%：並發配置可能太低或下游太慢
  • Fallback 使用率突增：某個依賴開始劣化

貫穿專案進度：catalog-service 完整容錯配置

Java · catalog-service InventoryClient
@ApplicationScoped
public class InventoryClient {

    @Inject @RestClient InventoryRestClient restClient;
    @Inject InventoryCache cache;

    @Timeout(value = 1500, unit = ChronoUnit.MILLIS)
    @Retry(maxRetries = 2)
    @ExponentialBackoff(initialDelay = 100, factor = 2, jitter = 0.3)
    @CircuitBreaker(
        requestVolumeThreshold = 20,
        failureRatio = 0.5,
        delay = 10000,
        successThreshold = 3,
        failOn = {IOException.class, TimeoutException.class}
    )
    @Bulkhead(value = 30, waitingTaskQueue = 10)
    @Fallback(fallbackMethod = "cachedStock")
    public Stock checkStock(String sku) {
        return restClient.stock(sku);
    }

    public Stock cachedStock(String sku) {
        Log.warnf("Inventory unavailable for sku=%s, using cache", sku);
        return cache.get(sku).orElse(Stock.unknown(sku));
    }
}

DevOps / SRE 視角

✓
容錯設計 Checklist
  1. 所有對外呼叫都要 @Timeout── 沒有 timeout = 沒有 SLA
  2. @Retry 只對 idempotent 操作── POST 建立訂單不能無腦 retry
  3. Retry 要 Exponential Backoff + Jitter── 固定 delay 會 thundering herd
  4. @CircuitBreaker 核心依賴必加── DB、Kafka、payment gateway
  5. Fallback 要有實質意義── 不能只是 throw 同樣的 exception
  6. @Bulkhead 保護慢端點── report 生成、大型 export
  7. 用 Metrics 監控 CB 狀態── CB 開路告警，不要等用戶回報
  8. 非核心依賴失敗不影響核心流程── audit log 失敗不能讓 order 失敗
  9. Config override 跨環境調整── dev 放寬 timeout、prod 嚴格

常見陷阱

症狀原因解法
@Retry 對 POST 重複建立業務操作非 idempotent只對 GET、查詢、idempotent 操作 retry；POST 不 retry 或加 idempotency key
@Timeout 在 Reactive 不生效Uni 回傳後 FT 不再管用 Uni.ifNoItem().after(Duration).failWith()
CB 開路後 retry 仍繼續@Retry 在 @CircuitBreaker 內層正常行為：每次 retry 都被 CB 記錄。CB 開路後 retry 直接收 CircuitBreakerOpenException
Fallback method 簽名不符參數型別或回傳型別不一致fallback method 參數必須與原方法完全一致
@Bulkhead 沒效果同步模式沒設 waitingTaskQueue同步：@Bulkhead(value=10, waitingTaskQueue=5)
CB 反應太慢requestVolumeThreshold 設太大降低 threshold 讓 CB 更敏感；或縮短 sliding window
Dev 模式 FT 干擾測試Timeout 太短打斷 debugger%dev.MP_Fault_Tolerance_NonFallback_Enabled=false

本章小結

  • 分散式系統失敗是常態，容錯設計是必要 ── 不是 nice to have。
  • @Retry：消化瞬間失敗；搭配 @ExponentialBackoff + jitter 防 thundering herd；只用於 idempotent 操作。
  • @Timeout：切斷無窮等待；每個對外呼叫必加。Reactive 場景改用 Mutiny 鏈的 timeout 操作。
  • @Fallback：降級策略；method 或 FallbackHandler 兩種；fallback 要有實質意義。
  • @CircuitBreaker：三個狀態（CLOSED / OPEN / HALF_OPEN）防止 cascading failure；核心依賴必加。
  • @Bulkhead：隔離慢端點防止耗盡所有 thread；@RateLimit 用於時間視窗控制。
  • 執行順序：Fallback → CB → RateLimit → Timeout → Bulkhead → Retry → 實際方法（固定）。
  • Reactive 方法直接加注解即可；@AsynchronousNonBlocking 處理 non-blocking 場景。
  • Config override：property file 可覆寫注解參數，跨環境調整不改程式碼。
  • Metrics：FT 自動曝露 CB 狀態、retry 率、fallback 次數 ── 接進 Grafana 做告警。
