Chapter 37 · Part VII

Profiling 與診斷

Logs 說「發生了什麼」、Metrics 說「多嚴重」、Traces 說「哪段慢」── 但有一類問題三者都答不了： CPU Hotspot 在哪裡？是哪個 method 在 allocate 大量 object？記憶體洩漏的根源是哪個 class？ 這是 Profiling 的領域。本章從 JFR（Java Flight Recorder） 與 async-profiler 開始， 涵蓋 Flame Graph 判讀、Heap dump 分析、Thread dump 死鎖偵測， 最後收尾在 連續 profiling（Pyroscope） ── 讓 profiling 像 metrics 一樣常態運行。 本章是 Part VII 可觀測性的完結篇，也是三大信號向下延伸到「JVM 內部」的補完。

Java Flight Recorder（JFR）

JFR 是 JDK 內建（JDK 11+，JDK 17+ 開放商業限制）的低開銷 profiling 框架。 它以 ring buffer 的方式持續記錄 JVM 事件（GC、class loading、thread state、I/O、lock 等）， 生產可常態開啟（overhead 通常 <2%）。

開啟方式

bash · JVM 參數開啟 JFR
# 啟動時開 JFR，固定錄 60 秒後輸出（用於排查特定問題）
java -XX:StartFlightRecording=filename=recording.jfr,duration=60s,settings=profile \
     -XX:FlightRecorderOptions=stackdepth=128 \
     -jar target/quarkus-app/quarkus-run.jar

# 或：持續錄（circular buffer），任何時間手動 dump
java -XX:StartFlightRecording=name=continuous,settings=default,disk=true \
     -XX:FlightRecorderOptions=maxsize=500M \
     -jar target/quarkus-app/quarkus-run.jar

# 觸發 dump（用 jcmd）
jcmd <PID> JFR.dump recording=continuous filename=/tmp/snapshot.jfr
bash · quarkus dev 模式也可加
quarkus dev -Djvm.args="-XX:StartFlightRecording=filename=dev-profile.jfr,settings=profile"

分析工具

工具特點
JDK Mission Control（JMC）官方 GUI，最完整。免費（OpenJDK 版本）。看 GC、thread、method profiling、I/O 一應俱全。
IntelliJ ProfilerIDEA 內建，能直接跳到程式碼。開發者首選。
async-profiler jfr2flame把 JFR 轉成 flame graph HTML。輕量好用。

async-profiler：低開銷 Flame Graph

async-profiler 是使用 AsyncGetCallTrace API（繞過 safepoint 偏差，更準確）+ perf_events 的 sampling profiler。 生產環境 overhead 通常 <5%，是目前最主流的 Java profiler。

安裝與基本使用

bash · 下載並 profile
# Linux x64
curl -LO https://github.com/async-profiler/async-profiler/releases/latest/download/async-profiler-linux-x64.tar.gz
tar xf async-profiler-linux-x64.tar.gz

# 取得 Quarkus 程序 PID
PID=$(pgrep -f quarkus-run.jar)

# CPU profiling 30 秒，輸出 flame graph HTML
./asprof -d 30 -e cpu -o flamegraph -f cpu-flamegraph.html $PID

# Allocation profiling（找誰在 allocate 大量 object）
./asprof -d 30 -e alloc -o flamegraph -f alloc-flamegraph.html $PID

# Wall-clock profiling（包含 I/O 等待，比 CPU profile 更全面）
./asprof -d 30 -e wall -o flamegraph -f wall-flamegraph.html $PID

在 Quarkus 啟動時掛上 async-profiler

bash · agent 方式（適合分析啟動時間）
AP_LIB=/path/to/async-profiler/lib/libasyncProfiler.so

# CPU 啟動 profile
java -agentpath:${AP_LIB}=start,event=cpu,file=startup-cpu.html,interval=1000000,simple \
     -jar target/quarkus-app/quarkus-run.jar

# Ctrl+C 停止後自動輸出 startup-cpu.html

Flame Graph 判讀

ℹ︎
Flame Graph 怎麼看
  • X 軸：在 sample 中出現的比例（不是時間順序）── 寬 = 花的時間多
  • Y 軸：call stack，底部是 root（main / reactor-loop），越往上越深層
  • 平頂（plateau）：那個 method 本身花了時間（不是只 call 子 method），就是 hotspot
  • 找「最寬的平頂」── 那就是你要優化的 method

K8s 容器內 Profiling

容器環境有限制：perf_events 需要 CAP_PERFMON（Linux 5.8+）或 SYS_ADMIN capability。 兩種策略：

方案 A：從容器內 profile

bash · kubectl exec 進 Pod 執行
# 把 async-profiler 複製進 Pod
kubectl cp ./async-profiler-linux-x64.tar.gz catalog-pod:/tmp/
kubectl exec -it catalog-pod -- bash
cd /tmp && tar xf async-profiler-linux-x64.tar.gz
PID=$(pgrep -f quarkus-run)
./asprof -d 30 -e cpu -o flamegraph -f /tmp/cpu.html $PID

# 複製出來
kubectl cp catalog-pod:/tmp/cpu.html ./cpu-$(date +%Y%m%d-%H%M%S).html

方案 B：以 JVM flag 從啟動就掛（需要在 Dockerfile 準備）

Dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
# 把 async-profiler 打包進 image（staging / debug 版本）
COPY --from=async-profiler:latest /async-profiler /opt/ap
COPY target/quarkus-app/ .
ENV AP_LIB=/opt/ap/lib/libasyncProfiler.so
CMD ["java", "-jar", "quarkus-run.jar"]

連續 Profiling：Pyroscope

傳統 profiling 是「出事後再去抓」── 但那個時候問題可能已經不可重現。連續 profiling 讓 profiler 像 metrics 一樣常態運行，數據推到 Pyroscope（Grafana Labs 開源），隨時可回看。

✓
為什麼連續 profiling 是 2026 趨勢
CPU flame graph 是 point-in-time。
但如果 CPU spike 只在凌晨 3 點發生、持續 30 秒，你在 9 點才發現，傳統做法就 GG。
Pyroscope 常態保存過去 30 天的 profiling data，事後拉出來看。
bash · Pyroscope Java agent
wget https://github.com/grafana/pyroscope/releases/download/v1.5.0/pyroscope-agent-1.5.0.jar

java -javaagent:pyroscope-agent.jar \
     -Dpyroscope.application.name=catalog-service \
     -Dpyroscope.server.address=http://pyroscope:4040 \
     -Dpyroscope.profiling.interval=10ms \
     -jar quarkus-run.jar
yaml · K8s Deployment Pyroscope 加注
spec:
  template:
    metadata:
      annotations:
        # Grafana Pyroscope auto-instrumentation（operator 模式）
        pyroscope.grafana.com/scrape: "true"
        pyroscope.grafana.com/application-name: "catalog-service"
        pyroscope.grafana.com/port: "6060"
    spec:
      containers:
      - name: catalog-service
        env:
        - name: JAVA_TOOL_OPTIONS
          value: >-
            -javaagent:/opt/pyroscope/pyroscope-agent.jar
            -Dpyroscope.application.name=catalog-service
            -Dpyroscope.server.address=http://pyroscope.monitoring:4040

Heap Dump：找記憶體洩漏

記憶體緩慢增長、最終 OOM ── 需要 heap dump 找出誰在佔記憶體：

bash · 觸發 heap dump
# 方式 A：jcmd（JDK 內建，不中斷服務）
jcmd <PID> GC.heap_info
jcmd <PID> VM.native_memory
jcmd <PID> GC.heap_dump /tmp/heapdump.hprof

# 方式 B：OOM 時自動 dump
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/tmp/oom-dump.hprof \
     -jar quarkus-run.jar

# 方式 C：async-profiler allocation flamegraph（比 heap dump 更快）
./asprof -d 60 -e alloc -o flamegraph -f alloc.html <PID>

分析工具

工具特點
Eclipse MAT開源、最功能完整。Dominator tree（誰在 hold 最多記憶體）、leak suspects 報告。
JDK Mission Control（JMC）也能開 .hprof，與 JFR 同一工具。
IntelliJ ProfilerIDEA 直接 drag & drop .hprof，最低摩擦力。
async-profiler alloc不 pause，直接 flame graph 看誰在 allocate，比 heap dump 更快定位。
⚠
Heap dump 在生產需謹慎
取 heap dump 時 JVM 會 全力 GC + STW（Stop-The-World），服務會短暫中斷數秒。 生產上建議：先從 pod 取出一個 replica、從 Service 移除，再取 dump，取完後恢復。

Thread Dump：死鎖與 Blocking 分析

bash · 觸發 thread dump
# jcmd（不中斷服務）
jcmd <PID> Thread.print > /tmp/threads.txt

# 或用 kill -3（輸出到 stdout）
kill -3 <PID>

# 或從 K8s
kubectl exec <pod> -- jcmd 1 Thread.print > threads-$(date +%Y%m%d-%H%M%S).txt

判讀要點

  • BLOCKED 狀態的 thread 多 ── 有鎖競爭（檢查 locked / waiting to lock）
  • WAITING / TIMED_WAITING 在同一個 method 超多 ── 可能是 connection pool 耗盡
  • Deadlock detected 字樣 ── JVM 自動偵測死鎖，thread dump 末段會列出
  • 連續取兩次 dump（間隔 5 秒），比對哪些 thread 動了、哪些一直在同一個 stack frame
bash · 快速找 BLOCKED thread
grep -A 5 'BLOCKED' /tmp/threads.txt | head -60

# 找 deadlock 直接看最後幾行
tail -50 /tmp/threads.txt | grep -A 20 'deadlock'

Native Image 診斷

Native build 的診斷比 JVM 困難：沒有 JIT、沒有 JFR（部分支援）、沒有 jcmd。但也有對應工具：

工具Native 支援
Micrometer / OTel metrics✅ 完整，application-level metrics 不受影響
OpenTelemetry traces✅ 完整，Quarkus build-time instrumentation
Heap dump✅ GraalVM native 支援 --enable-heap-dump
JFR⚠ 部分支援（GraalVM Enterprise 21+）
async-profiler CPU⚠ 有限，需要 debug info
Linux perf / gdb✅ native 程式用系統工具即可
bash · Native heap dump
# 編譯時加入 heap dump 支援
./mvnw package -Pnative -Dquarkus.native.enable-heap-dump=true

# 執行時觸發
kill -SIGUSR1 <PID>   # 或用 REST admin endpoint

Quarkus Dev Console 診斷

開發模式下 http://localhost:8080/q/dev-ui/ 提供豐富的診斷工具：

  • Configuration：所有設定值（含 profile overrides）
  • CDI Beans：全部 bean 實例、scope、inject 關係
  • REST Endpoints：所有路由列表
  • Health UI：即時 health check 狀態
  • OpenAPI / Swagger：一鍵試 API
  • Continuous Testing：測試結果即時更新
  • Kafka UI / DB Console：接了對應擴充後自動出現
ℹ︎
Dev Console 在 prod 一定要關
quarkus.dev-ui.enabled=false（預設）。
若不小心在 prod 開了，等於把 CDI bean tree、設定值、API 路由都暴露出去。

DevOps / SRE 視角

✓
生產 Profiling 策略
  1. JFR 常態開啟（overhead <2%）── -XX:StartFlightRecording=settings=default,disk=true,maxsize=500M
  2. 連續 profiling Pyroscope ── 跟 metrics 一樣常態，事後可查
  3. OOM 自動 heap dump ── -XX:+HeapDumpOnOutOfMemoryError 必加
  4. Profiling 用 Staging 先確認 ── 某些 profiler 需要 kernel 權限，生產環境不一定有
  5. 取 heap dump 時先移出 LB ── STW 期間服務中斷，不要讓 LB 繼續送請求
  6. Thread dump 連取兩次（間隔 5–10s）── 比較靜態的才是真問題
  7. Native build 問題先排 JVM 模式 ── 確認 JVM 沒問題再懷疑 native
  8. CPU spike ≠ 程式 bug ── 先看 GC pause time、thread count、外部 I/O wait

常見陷阱

症狀原因解法
async-profiler 沒法 attachContainer 沒有 CAP_PERFMONSecurityContext 加 capabilities.add: ["PERFMON"] 或用 JFR 替代
Flame graph 全是 unknownJIT 最佳化去掉 frame info加 -XX:+PreserveFramePointer 啟動 JVM
Heap dump 後 Pod 沒回來STW 期間 Liveness probe 失敗觸發重啟暫時調高 failureThreshold，或移出 LB 再取 dump
Native build 找不到記憶體洩漏native 不能用 heap dump 分析 Java heap在 JVM 模式重現問題，再 profile
Pyroscope 數據不連續Pod 重啟後 agent 重新計時用 Pyroscope label（env、pod）聚合；接受 restart gap
CPU 100% 但 flame graph 沒 hotspotGC 佔主因（GC thread 不一定在 user code frame）看 JFR GC events，調 heap size 或 GC 策略

本章小結

  • Profiling 是 Logs / Metrics / Traces 之外的第四層 ── 回答「根源是哪行程式碼」。
  • JFR：JDK 內建，overhead <2%，生產可常態開啟；JMC 或 async-profiler jfr2flame 分析。
  • async-profiler：CPU / alloc / wall-clock profile，輸出互動式 flame graph。找 hotspot 首選。
  • Flame graph 判讀：X 軸寬 = 花時間多；找「最寬的平頂」就是 hotspot。
  • Heap dump：用 jcmd GC.heap_dump 或 -XX:+HeapDumpOnOutOfMemoryError；Eclipse MAT 分析。取 dump 需先移出 LB。
  • Thread dump：連取兩次比較；找 BLOCKED 大量 thread 或 deadlock。
  • 連續 profiling（Pyroscope）：像 metrics 一樣常態保存，事後可查歷史 flame graph。
  • Native image：metrics / traces 完整；JFR 部分支援；heap dump 需編譯期開啟；複雜問題先在 JVM 模式重現。
  • Dev Console：dev 模式診斷利器，prod 必須關閉。
  • Part VII 完整收尾：Logs（細節）+ Metrics（趨勢）+ Traces（因果）+ Health（存活）+ Profiling（根源）── 五個維度讓系統透明可觀測。
