認識 Quarkus

在 Cloud Native 時代，Java 不必再是體積臃腫、啟動緩慢的代名詞。 Quarkus 把 Build-Time Augmentation、Container-First、Reactive Core 寫進框架基因，讓 Supersonic Subatomic Java 不只是口號。

Quarkus 是什麼？

Quarkus 是一個專為 Java 設計、原生支援 Kubernetes 與 GraalVM 的應用框架。 它從 2019 年由 Red Hat 開源以來，定位自身為「Supersonic Subatomic Java」── 超音速啟動、次原子級的記憶體佔用。

Quarkus 不是另一個 Web 框架，而是一個建立在 Vert.x 響應式核心上、 以 Build-Time Augmentation（建構時期增強）為核心理念的應用平台。 它支援的標準涵蓋 Jakarta EE、MicroProfile、Reactive Streams、Reactive Messaging， 並提供一個龐大的擴充（extension）生態系。

圖 1-1 ─ Quarkus 三大設計支柱與其衍生特性

① Build-Time First（建構時期優先）

傳統 Java 框架（如 Spring）大量依賴 Runtime Reflection：應用啟動時要掃描 classpath、 讀取 annotation、產生 proxy bean。這在 JVM 上是慢的；在 Native Image 編譯成 靜態執行檔時，更是個惡夢，因為 reflection 必須額外註冊。

Quarkus 翻轉這個模式：所有能在編譯期決定的事（DI 圖、ORM mapping、REST 路由註冊）， 都在 mvn package 階段就由 Quarkus 的 Extension Processor 完成。應用啟動時，只剩 「載入這份預先計算好的結構」這件事，所以啟動時間從秒級降到毫秒級。

② Container First（容器優先）

Quarkus 從設計第一天就鎖定 Kubernetes 為主要部署目標。預設整合健康檢查（Liveness / Readiness / Startup Probe）、Micrometer Metrics、OpenTelemetry Tracing，且擴充提供 Kubernetes Manifest 自動產生、Native Image 容器建構、Dev Services 自動拉測試環境。

③ Developer Joy（開發者愉悅感）

這是 Quarkus 在開發者社群迅速壯大的關鍵。Live Reload（一改檔案，下一個 HTTP request 就生效）、 Dev Services（不寫 docker-compose，Quarkus 自動幫你啟動 PostgreSQL / Kafka / Keycloak）、 Dev UI（瀏覽器上看 routes、config、cache、scheduler 全景）、 Continuous Testing（檔案改動時自動跑相關測試）。 這些功能組合起來，把 Java 的開發體驗推到接近 Node.js / Python 的即時感。

命令式 vs 響應式：你都會用到

Quarkus 的核心是響應式的（基於 Eclipse Vert.x），但允許你以兩種方式撰寫業務邏輯： 命令式（Imperative / Blocking）與響應式（Reactive / Non-blocking）。 本手冊每章關鍵範例都會兩種寫法並陳。先看一個 REST endpoint 的最小對照：

Java · Imperative 
@Path("/greet")
public class GreetResource {

    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public String hello() {
        return "Hello, Quarkus!";
    }
}
Java · Reactive (Mutiny) 
@Path("/greet")
public class GreetResource {

    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public Uni<String> hello() {
        return Uni.createFrom().item("Hello, Quarkus!");
    }
}

注意關鍵字：命令式直接回傳 String，響應式回傳 Uni<String>。 Quarkus 看到回傳型別就知道要在 worker thread（命令式，可阻塞）還是 event-loop thread（響應式，不能阻塞）執行。

⚠
三條規則
  1. 命令式不能在 @RunOnVirtualThread 或預設情境下阻塞 event-loop（Quarkus 會幫你 dispatch 到 worker）。
  2. 響應式回傳 Uni（單一結果）或 Multi（串流）；裡面不能呼叫阻塞 API（例如 JDBC、Thread.sleep）。
  3. JDK 21 之後可選擇 Virtual Threads（虛擬執行緒）來寫看似命令式、但行為類似響應式的程式。詳見第 40 章。

DevOps / SRE 視角

本節是 🟠 SRE 必讀。Quarkus 對營運帶來的差異不只是「啟動快」這麼簡單， 而是整個成本結構的位移。

啟動時間 → 擴縮容彈性

HPA（Horizontal Pod Autoscaler）的反應速度受限於 Pod 啟動時間。 Spring Boot 3~10 秒的啟動意味著「突發流量到達」與「新 Pod ready」之間有可觀的延遲視窗， 常見補救是過度配置 baseline replica。Quarkus Native 應用 50ms 內就 ready， 能用更激進的 HPA 設定（甚至 scale-to-zero），把每月雲端帳單砍掉 30 ~ 60% 是業界常見的案例。

記憶體 → 部署密度

典型 Spring Boot 應用 idle 時佔 200 MB+，Quarkus JVM 模式 70 MB，Native 模式 20 MB。 同一個 16 GB Node，能塞下的 Pod 數量差異可達 3 ~ 10 倍。對於業務尖峰時段大量短期任務（例如報表產生、批次處理）特別關鍵。

Native Image → 可預測性

Native 應用沒有 JIT 暖機曲線，效能從第一個 request 開始就是穩定的；沒有 GC 大停頓， P99 延遲分布顯著收斂；映像檔小（典型 80 MB vs Spring Boot 250 MB）， CI/CD 推送、Pull 與啟動都快。

⚠
Native 不是萬靈丹
Native 編譯時間長（5 ~ 15 分鐘）、記憶體需 8 GB+、reflection 須事先註冊。 對於開發迭代週期短、且 JVM 啟動成本可接受的內部工具，JVM 模式可能更合適。 第 44 章會深入討論抉擇。

本章小結

  • Quarkus 用 Build-Time Augmentation 翻轉傳統 Java 框架的執行時期反射模型，換來啟動與記憶體優勢。
  • 三大設計支柱：Build-Time First、Container First、Developer Joy。
  • 命令式與響應式雙軌並重；JDK 21 提供 Virtual Threads 作為第三條路。
  • 生態系包含 Core / Platform / Quarkiverse / RHBQ 四個層次。
  • 對 SRE 而言，Quarkus 帶來的不只是「快」，而是擴縮容、部署密度、延遲可預測性的整體位移。
