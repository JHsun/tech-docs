Chapter 62 · Part XIII

多模型供應商、MCP 與 AI Observability

Part XIII 最後一章補完 AI 應用的「營運面」：按場景混用多個 LLM 供應商（便宜 vs 精準）、2025 年廣泛採用的 Model Context Protocol（MCP）讓 AI 連接任意外部工具、以及透過 OpenTelemetry 追蹤每次 LLM 呼叫的 latency 與 token 用量 ── AI Observability 與一般服務同等重要。

版本 Quarkus LangChain4j 0.24+
更新 2026-05-16

按場景混用多個模型

任務類型推薦模型理由
FAQ 回答、分類GPT-4o-mini / Llama 3.2便宜（GPT-4o 1/15 價格），效果夠用
複雜推理、程式碼GPT-4o / Claude 3.5 Sonnet準確度高
長文件分析Claude 3.5 / Gemini 1.5 Pro128K+ context window
隱私/離線Ollama（Llama 3.2 本地）資料不離境
Java · Named 模型配置
// 不同 AI Service 用不同模型
@RegisterAiService(modelName = "cheap")    // FAQ：便宜模型
public interface FaqAssistant {
    String answer(@UserMessage String question);
}

@RegisterAiService(modelName = "powerful") // 分析：高品質模型
public interface DocumentAnalyzer {
    AnalysisResult analyze(@UserMessage String document);
}

MCP：Model Context Protocol

MCP 是 Anthropic 2024 年推出、2025 年廣泛採用的開放協議 ── 標準化 LLM 連接外部工具的方式。 與 Function Calling（Tools）相比，MCP 工具可跨應用共享，且有豐富的現成服務（GitHub、Slack、Notion 等）：

application.properties · 連接 MCP 服務
# 連接 GitHub MCP Server
quarkus.langchain4j.mcp.github.transport-type=http
quarkus.langchain4j.mcp.github.url=https://api.githubcopilot.com/mcp/v1
quarkus.langchain4j.mcp.github.token=${GITHUB_TOKEN}

# 連接本地 MCP Server（Quarkus 自身也可啟 MCP server）
quarkus.langchain4j.mcp.local-tools.transport-type=stdio
quarkus.langchain4j.mcp.local-tools.command=java,-jar,/opt/tools/my-mcp-server.jar
Java · 使用 MCP 的 AI Service
import io.quarkiverse.langchain4j.mcp.runtime.McpToolBox;

@RegisterAiService(
    toolProviders = @McpToolBox("github")   // 使用 github MCP 所有工具
)
public interface GitHubAgent {
    @SystemMessage("You are a helpful GitHub assistant. Help users manage their repositories.")
    String help(@UserMessage String task);
    // AI 現在可以 list repos, create issues, review PRs 等
}

AI Observability

Quarkus LangChain4j 自動整合 OpenTelemetry，每次 LLM 呼叫都產生 span 和 metrics：

application.properties
# OTel（第 35 章已設）
quarkus.otel.exporter.otlp.endpoint=http://otel-collector:4317

# LangChain4j 自動曝露的 metrics
# gen_ai.client.token.usage{gen_ai.request.model,gen_ai.operation.name}
#   → input_tokens / output_tokens 分開追蹤
# gen_ai.client.operation.duration{gen_ai.request.model}
#   → LLM 呼叫延遲（P50/P95/P99）

# Dev 模式：記錄完整 prompt 和回應（注意隱私！）
%dev.quarkus.langchain4j.log-requests=true
%dev.quarkus.langchain4j.log-responses=true
# Prod 不要開（PII 風險）
✓
AI Observability Grafana 告警建議
  • Token 用量超預算：sum(gen_ai.client.token.usage) > daily_budget → 告警 + 限流
  • LLM 延遲 P99 > 5s：用戶體感差，考慮 timeout 或換模型
  • Error rate 上升：API key 失效、Rate limit 觸發
  • 成本異常：某個 service 突然 token 暴增 ── 可能是 prompt injection 或程式錯誤

AI 成本控制

  • 模型選型：同任務用最便宜能完成的（GPT-4o-mini 比 GPT-4o 便宜約 15 倍）
  • @RateLimit（ch38）：限制 AI endpoint QPS，防止濫用
  • Token 監控：Grafana 告警 + 月預算上限（LLM provider 端也可設）
  • Caching：相同問題快取回應（語意 cache 或精確 cache）
  • Streaming + 早停：讓用戶可以在回答一半時停止，節省 output token

本章小結

  • 多模型策略：便宜 / 精準 / 離線各有適用場景；modelName 讓不同 AI Service 用不同模型，零程式碼修改。
  • MCP（Model Context Protocol）：2025 標準，讓 AI 透過標準化方式連接 GitHub、Slack 等外部服務。
  • OTel 自動整合：token 用量、LLM 延遲變成 metrics，接進 Grafana 監控。
  • Dev log-requests=true，Prod 必須關閉（PII 隱私風險）。
  • 成本控制：模型選型 + RateLimit + Token 告警 + Caching。
