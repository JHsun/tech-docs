Health：SmallRye Health 與 K8s Probe

Logs、Metrics、Traces 告訴你「過去發生了什麼」── 而 Health 告訴 Kubernetes「現在能不能送流量進來」。 這是 observability 與自動化恢復的交界。一個正確的 health check 設計，可以讓 K8s 在 DB 斷線時 自動停止送流量、在記憶體洩漏時自動重啟 Pod ── 而一個錯誤的設計，則會讓 K8s 把一半的 Pod 在尖峰時間全殺掉。 本章把 Liveness / Readiness / Startup 三種 probe 的語意說清楚，再講 Quarkus 的自動 check、 自訂 HealthCheck、管理端口分離，最後直接給出 K8s 生產級 probe 配置。

三種 Probe 的語意

三種 probe 常被混用，但混用的代價可以是生產事故。先把語意釘清楚：

Probe問的問題失敗的後果應該檢查什麼
Liveness
/q/health/live		 「App 還活著嗎？」 K8s 重啟 Pod App 本身（deadlock、OOM、無限等待）── 不含外部依賴
Readiness
/q/health/ready		 「App 能接受請求嗎？」 K8s 從 Service 移除 Pod ── 不重啟 DB 連線、Kafka 連線、外部服務、暖機狀態
Startup
/q/health/started		 「啟動完成了嗎？」 失敗時阻止 Liveness 開始計時 初始化任務（資料庫 migration 完成、快取預熱完成）

⚠
最常見的致命錯誤：把外部依賴放進 Liveness
如果 Liveness probe 去 ping DB，DB 暫時斷線 → Liveness 回 DOWN → K8s 重啟 Pod。 但重啟完 DB 還是斷的，下一個 Pod 也死 → rolling restart 把所有 Pod 殺光 → 全服務中斷。
外部依賴一律放 Readiness。Liveness 只檢查「App 程式本身是否卡死」。

自訂 Liveness Check：JVM 資源監控

Liveness 不該檢查外部依賴，那能檢查什麼？JVM 自身健康──記憶體、Deadlock 偵測：

Java · JVM memory liveness check
import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Liveness;
import jakarta.enterprise.context.ApplicationScoped;
import java.lang.management.ManagementFactory;
import java.lang.management.MemoryMXBean;

@Liveness
@ApplicationScoped
public class JvmMemoryLivenessCheck implements HealthCheck {

    private static final double HEAP_THRESHOLD = 0.90;  // 90%
    private final MemoryMXBean memBean = ManagementFactory.getMemoryMXBean();

    @Override
    public HealthCheckResponse call() {
        long used = memBean.getHeapMemoryUsage().getUsed();
        long max  = memBean.getHeapMemoryUsage().getMax();
        double ratio = max > 0 ? (double) used / max : 0;

        if (ratio < HEAP_THRESHOLD) {
            return HealthCheckResponse.named("jvm-heap")
                .up()
                .withData("used_mb", used / 1_048_576)
                .withData("max_mb", max / 1_048_576)
                .withData("ratio_pct", (int)(ratio * 100))
                .build();
        }
        return HealthCheckResponse.named("jvm-heap")
            .down()
            .withData("used_mb", used / 1_048_576)
            .withData("max_mb", max / 1_048_576)
            .withData("ratio_pct", (int)(ratio * 100))
            .build();
    }
}

自訂 Readiness Check：外部依賴

如果你有外部 API（Payment gateway、匯率 API）是核心依賴，加進 Readiness：

Java · 外部 URL readiness check
import io.smallrye.health.checks.UrlHealthCheck;
import org.eclipse.microprofile.config.inject.ConfigProperty;
import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.Readiness;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.ws.rs.HttpMethod;

@Readiness
@ApplicationScoped
public class PaymentGatewayCheck {

    @ConfigProperty(name = "payment.gateway.health-url")
    String healthUrl;

    @Readiness
    HealthCheck checkPaymentGateway() {
        return new UrlHealthCheck(healthUrl)
            .name("payment-gateway")
            .requestMethod(HttpMethod.GET)
            .statusCode(200);
    }
}

自訂 DB check（加業務邏輯）

Java · 不只 ping，還要 query
@Readiness
@ApplicationScoped
public class DatabaseReadinessCheck implements HealthCheck {

    @Inject DataSource ds;

    @Override
    public HealthCheckResponse call() {
        try (var conn = ds.getConnection();
             var stmt = conn.prepareStatement("SELECT 1")) {
            stmt.executeQuery();
            return HealthCheckResponse.named("db-connectivity").up().build();
        } catch (Exception e) {
            return HealthCheckResponse.named("db-connectivity")
                .down().withData("error", e.getMessage()).build();
        }
    }
}
⚠
Readiness check 不能太重
K8s 每 10 秒就會來 probe 一次。如果你的 check 耗時 500ms，會壓迫 DB connection pool。 用 輕量 query（SELECT 1），超時設 1–2 秒，避免 cascading failure。

Startup Check：等初始化完成

Quarkus 啟動速度極快，通常不需要 startup probe。但有些場景確實需要：

  • 等待 Flyway / Liquibase migration 完成
  • 等待 預熱快取（把 10 萬筆商品載入 Caffeine）
  • 等待 外部 warm-up call（先呼叫 JIT 熱門路徑）
Java · cache warm-up startup check
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Startup;
import jakarta.enterprise.context.ApplicationScoped;
import java.util.concurrent.atomic.AtomicBoolean;

@Startup
@ApplicationScoped
public class CacheWarmupStartupCheck implements HealthCheck {

    private final AtomicBoolean warmed = new AtomicBoolean(false);

    // 由 ApplicationScoped 的 @PostConstruct 或 Scheduler 觸發
    public void markWarmed() { warmed.set(true); }

    @Override
    public HealthCheckResponse call() {
        if (warmed.get()) {
            return HealthCheckResponse.named("cache-warmup").up().build();
        }
        return HealthCheckResponse.named("cache-warmup")
            .down().withData("status", "warming up").build();
    }
}

AsyncHealthCheck：Reactive 場景

Java · Reactive readiness check
import io.smallrye.health.api.AsyncHealthCheck;
import io.smallrye.mutiny.Uni;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Readiness;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@Readiness
@ApplicationScoped
public class ReactiveDbCheck implements AsyncHealthCheck {

    @Inject io.vertx.mutiny.pgclient.PgPool client;

    @Override
    public Uni<HealthCheckResponse> call() {
        return client.query("SELECT 1").execute()
            .map(rows -> HealthCheckResponse.named("reactive-db").up().build())
            .onFailure().recoverWithItem(e ->
                HealthCheckResponse.named("reactive-db")
                    .down().withData("error", e.getMessage()).build());
    }
}

K8s Probe 完整配置

yaml · Kubernetes Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: catalog-service
        image: example/catalog-service:1.4.2
        ports:
        - containerPort: 8080
          name: http
        - containerPort: 9000        # 管理端口（下一節）
          name: management

        startupProbe:
          httpGet:
            path: /q/health/started
            port: 9000               # 走管理端口
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 30       # 最多等 150s（給 migration 時間）
          timeoutSeconds: 3

        livenessProbe:
          httpGet:
            path: /q/health/live
            port: 9000
          initialDelaySeconds: 0    # startup 完成後立即開始
          periodSeconds: 20
          failureThreshold: 3       # 3 次失敗才重啟（避免瞬間抖動）
          timeoutSeconds: 2

        readinessProbe:
          httpGet:
            path: /q/health/ready
            port: 9000
          initialDelaySeconds: 0
          periodSeconds: 10
          failureThreshold: 3
          successThreshold: 1
          timeoutSeconds: 3
✓
Quarkus Kubernetes 擴充自動生成
如果加了 quarkus-kubernetes 擴充，以上 probe 配置可以直接在 application.properties 設定： quarkus.kubernetes.liveness-probe.period=20s，build 時自動加進 YAML。不需手寫。

管理端口分離：安全最佳實踐

預設 health endpoint 在 :8080/q/health（與業務 API 同一個 port）。 生產建議分離到獨立管理端口：

  • 業務端口可以有 Auth 保護，管理端口讓 K8s 直接訪問
  • 管理端口可以做 network policy 限制只讓 K8s 節點 IP 訪問
  • 隔離後，就算業務端口雪崩，管理端口仍能回報狀態
application.properties
# 開啟管理介面（獨立 port）
quarkus.management.enabled=true
quarkus.management.host=0.0.0.0
quarkus.management.port=9000

# Health check 自動移到管理介面
# 路徑變成：http://host:9000/q/health
# 也可自訂
quarkus.smallrye-health.root-path=/q/health
# 業務 API → port 8080 curl http://catalog-service:8080/api/products # 管理（health）→ port 9000（K8s probe 用） curl http://catalog-service:9000/q/health/ready

DevOps / SRE 視角

✓
生產 Health Probe Checklist
  1. Liveness 不查外部依賴 ── 只查 App 本身（堆記憶體、deadlock）
  2. Readiness 查所有核心依賴 ── DB、Kafka、必要的外部 API
  3. Startup probe + failureThreshold 給足初始化時間（migration 可能 30–120s）
  4. 管理端口分離（:9000）── 業務端口可有 auth，管理端口 K8s 直達
  5. Health check 超時要比 periodSeconds 短（避免 probe 堆積）
  6. Liveness failureThreshold ≥ 3（避免瞬間抖動就重啟）
  7. Readiness check 輕量（SELECT 1 不要複雜 query）
  8. 不要把 Health endpoint 放在 API gateway auth 之後（K8s 過不了 auth）
  9. withData() 補診斷資訊，DOWN 時立即看出原因
  10. Metrics 監控 health check 失敗率（smallrye_health_check_*）

常見陷阱

症狀原因解法
高峰期 Pod 被大量重啟Liveness 查 DB，DB 高負載回應慢 → timeout把 DB check 移到 Readiness，Liveness 只查 JVM
新版部署後流量長時間斷沒設 startup probe，liveness 太快開始、migration 未完成加 @Startup check，並調高 failureThreshold
Health endpoint 403endpoint 在 API gateway auth 之後管理端口分離到 :9000，繞過 gateway
DOWN 時不知道哪個 check 失敗HealthCheckResponse 沒 withData()加診斷資訊：error message、timestamp、config
Kafka check 不生效預設關閉設 quarkus.kafka.health.enabled=true
Health check 本身拖慢 App重量型 check 每 10s 執行用 AsyncHealthCheck、輕量 query、縮短超時
Native build 後 health endpoint 404資源未包進 native image用官方 quarkus-smallrye-health 擴充，非自訂 endpoint

本章小結

  • 三種 probe 語意：Liveness（重啟 Pod）/ Readiness（移出 LB）/ Startup（延遲 Liveness 開始）── 混用會釀成事故。
  • Liveness 絕不查外部依賴，只查 App 自身（JVM 記憶體、deadlock）。
  • 裝 quarkus-smallrye-health，Agroal / Redis / MongoDB / Kafka 的 readiness check 自動接進來。
  • 自訂 check：實作 HealthCheck + @Liveness/@Readiness/@Startup，用 HealthCheckResponse.named().up()/.down().withData() 建回應。
  • Reactive 場景用 AsyncHealthCheck 回傳 Uni<HealthCheckResponse>。
  • Startup probe + failureThreshold 給慢啟動（DB migration、快取預熱）留足時間。
  • 管理端口分離（quarkus.management.port=9000）── 業務端口可有 auth，K8s 直打管理端口。
  • K8s probe 黃金設定：Liveness 20s 週期 3 次 timeout 2s；Readiness 10s 週期 3 次 timeout 3s。
  • withData() 補充診斷資訊，DOWN 時一眼看出原因。
