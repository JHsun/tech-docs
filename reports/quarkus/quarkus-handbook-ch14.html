Chapter 14 · Part III

gRPC 與 GraphQL

REST 不是唯一答案。gRPC用 protobuf 提供強型別、高效能、雙向串流，適合微服務間通訊； GraphQL讓 client 自己決定要取哪些欄位，解決 over-fetching 與 under-fetching。 Quarkus 把這兩個風格都做到「貼上 proto 就跑」、「加註解就成 API」的簡潔程度。

Part 1：gRPC

gRPC 核心觀念

gRPC 的世界觀：

  1. 合約優先：寫 .proto 檔定義 service 與 message

定義 .proto

proto · catalog.proto
syntax = "proto3";

option java_multiple_files = true;
option java_package = "com.example.catalog";

package catalog;

service CatalogService {
  // 1. Unary：一問一答
  rpc GetProduct(GetProductRequest) returns (Product);

  // 2. Server streaming：一問多答
  rpc ListProducts(ListProductsRequest) returns (stream Product);

  // 3. Client streaming：多問一答
  rpc CreateProducts(stream Product) returns (CreateSummary);

  // 4. Bi-directional streaming：多問多答
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}

message GetProductRequest {
  int64 id = 1;
}

message ListProductsRequest {
  int32 page_size = 1;
  string filter = 2;
}

message Product {
  int64 id = 1;
  string name = 2;
  double price = 3;
  string sku = 4;
  repeated string tags = 5;
}

message CreateSummary {
  int32 total_created = 1;
  repeated int64 ids = 2;
}

message ChatMessage {
  string user = 1;
  string text = 2;
}

實作 server

Java · Mutiny 風格實作
import io.quarkus.grpc.GrpcService;
import io.smallrye.mutiny.Multi;
import io.smallrye.mutiny.Uni;

@GrpcService
public class CatalogGrpcService extends MutinyCatalogServiceGrpc.CatalogServiceImplBase {

    @Inject ProductRepository repository;

    // Unary
    @Override
    public Uni<Product> getProduct(GetProductRequest req) {
        return Uni.createFrom().item(() -> {
            var p = repository.findById(req.getId());
            return Product.newBuilder()
                .setId(p.id())
                .setName(p.name())
                .setPrice(p.price().doubleValue())
                .build();
        });
    }

    // Server streaming
    @Override
    public Multi<Product> listProducts(ListProductsRequest req) {
        return Multi.createFrom().iterable(repository.list(req.getPageSize()))
            .map(p -> Product.newBuilder()
                .setId(p.id()).setName(p.name())
                .setPrice(p.price().doubleValue()).build());
    }

    // Bidirectional streaming
    @Override
    public Multi<ChatMessage> chat(Multi<ChatMessage> incoming) {
        return incoming.map(msg -> ChatMessage.newBuilder()
            .setUser("server")
            .setText("echo: " + msg.getText())
            .build());
    }
}
Java · 傳統 StreamObserver 風格
@GrpcService
public class CatalogGrpcService extends CatalogServiceGrpc.CatalogServiceImplBase {

    @Override
    public void getProduct(GetProductRequest req, StreamObserver<Product> obs) {
        var p = repository.findById(req.getId());
        obs.onNext(Product.newBuilder().setId(p.id()).build());
        obs.onCompleted();
    }
}
✓
優先用 Mutiny 風格
Uni / Multi 比 StreamObserver 更清晰、能與其他 reactive API 自然組合、適合 event-loop 執行。 生成的 MutinyXxxImplBase 與 CatalogServiceImplBase 同時存在，挑一個用即可。

HTTP/2 與 K8s

⚠
Ingress 必須支援 HTTP/2
gRPC 強制 HTTP/2。許多 K8s Ingress 預設 HTTP/1.1，需要配置：
  • NGINX Ingress：annotation nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
  • Istio：VirtualService 中允許 HTTP/2
  • Cloud LB：通常需明確選 gRPC mode
若 Ingress 不支援，可內部走 gRPC，邊緣轉 REST。

Part 2：GraphQL

GraphQL 解決什麼問題

REST 兩個經典痛點：

  • Over-fetching：GET /products/42 回了 30 個欄位，但 mobile 只要 name 與 price
  • Under-fetching：要顯示「產品 + 評論 + 評論者」需要 3 次 round-trip

GraphQL 讓 client 用查詢語言精確說明要的資料形狀，server 一次回傳：

graphql · client query
{
  product(id: 42) {
    name
    price
    reviews(limit: 3) {
      rating
      text
      author { name }
    }
  }
}

加擴充

bash
quarkus extension add smallrye-graphql

第一個 @GraphQLApi

Java · 基本 GraphQL endpoint
import org.eclipse.microprofile.graphql.*;
import jakarta.enterprise.context.ApplicationScoped;

@GraphQLApi
@ApplicationScoped
public class CatalogGraphQLApi {

    @Inject ProductService service;

    @Query("product")
    @Description("依 ID 取得單一產品")
    public Product getProduct(@Name("id") Long id) {
        return service.findById(id);
    }

    @Query("products")
    public List<Product> listProducts(
            @Name("limit") @DefaultValue("20") int limit,
            @Name("offset") @DefaultValue("0") int offset) {
        return service.list(limit, offset);
    }

    @Mutation
    public Product createProduct(@Name("input") CreateProductInput input) {
        return service.create(input);
    }

    @Mutation
    public Product updateProductPrice(
            @Name("id") Long id,
            @Name("price") BigDecimal price) {
        return service.updatePrice(id, price);
    }
}

public record CreateProductInput(String name, BigDecimal price, String sku) {}
⚠
@GraphQLApi class 一定要有 @ApplicationScoped
這是新手常見陷阱：沒加 scope 註解，Quarkus 不會把它視為 CDI bean，整個 endpoint 不會註冊。

欄位層級的 resolver：@Source

典型場景：Product 上有個 reviews 欄位，但 reviews 來自不同服務／表。GraphQL 用 resolver 概念：每個欄位由獨立方法解析。

Java · @Source 解析子欄位
@GraphQLApi
public class CatalogGraphQLApi {

    @Inject ReviewService reviewService;

    @Query
    public Product product(Long id) { return service.findById(id); }

    // 補上 Product 上的 reviews 欄位
    public List<Review> reviews(@Source Product product,
                                @Name("limit") @DefaultValue("10") int limit) {
        return reviewService.findByProductId(product.id(), limit);
    }
}

Client 就能查：

graphql
{ product(id: 42) { name reviews(limit: 3) { rating text } } }

N+1 問題與 @Batched 解法

GraphQL 最惡名昭彰的陷阱：查詢 100 個產品，每個都觸發 reviews resolver → 1 + 100 次 DB 查詢。 解法：用 @Source 接收 List，Quarkus 自動聚合：

Java · 批次 resolver 解 N+1
// ❌ N+1：每個 product 一次 query
public List<Review> reviews(@Source Product product) {
    return reviewService.findByProductId(product.id());
}

// ✓ Batched：所有 products 合一次 query
public List<List<Review>> reviews(@Source List<Product> products) {
    Map<Long, List<Review>> byProductId = reviewService.findByProductIds(
        products.stream().map(Product::id).toList());
    return products.stream()
        .map(p -> byProductId.getOrDefault(p.id(), List.of()))
        .toList();
}
✓
效能差異巨大
100 個產品的查詢，N+1 版本可能跑 101 次 SQL，Batched 版本只跑 2 次（products + reviews）。 生產級 GraphQL 服務必定要做這個優化。

Subscriptions：基於 WebSocket 的訂閱

Java · GraphQL Subscription
import io.smallrye.graphql.api.Subscription;
import io.smallrye.mutiny.Multi;
import io.smallrye.mutiny.operators.multi.processors.BroadcastProcessor;

@GraphQLApi
@ApplicationScoped
public class CatalogGraphQLApi {

    private final BroadcastProcessor<Product> productEvents = BroadcastProcessor.create();

    @Mutation
    public Product createProduct(CreateProductInput input) {
        Product created = service.create(input);
        productEvents.onNext(created);
        return created;
    }

    @Subscription
    public Multi<Product> productCreated() {
        return productEvents;
    }
}

Client 用 WebSocket（graphql-transport-ws 協定）訂閱：

graphql
subscription {
  productCreated { id name price }
}

gRPC vs GraphQL：怎麼選

ℹ︎
真實案例的決策
  • 內部微服務 service-to-service ── gRPC。低延遲、強型別、HTTP/2 多工
  • 移動 App / Web 前端 → 後端 BFF ── GraphQL。彈性查詢、避免大量 endpoint
  • 公開 API / 第三方整合 ── REST。生態最廣、開發者最熟悉
  • 即時雙向通訊（瀏覽器） ── WebSocket（第 13 章）或 GraphQL Subscription

DevOps / SRE 視角

gRPC 部署紅線

  1. K8s probe 用 grpc:（1.24+），不要用 HTTP 健康端點偽裝
  2. Ingress 確認 HTTP/2 支援，必要時加 backend-protocol 註解
  3. 不要在公開 API 暴露 reflection（dev/staging 啟用，prod 關閉）
  4. Stork 整合服務發現，搭配 name-resolver=stork
  5. 觀測：每個 RPC 自動產生 metrics（latency、status code）

GraphQL 安全考量

⚠
GraphQL 的獨特安全風險
  • 查詢爆炸：client 可組巨大 nested query 拖垮 server。設 query depth/complexity 限制
  • Introspection 洩漏 schema：prod 考慮關閉 quarkus.smallrye-graphql.events.enabled=false
  • N+1 攻擊：未做 batching 時，惡意 query 可放大 DB load 數百倍
  • Subscription 認證：GraphiQL UI 不會自動帶 Authorization header 到 WebSocket，建議用程式化 client 測試

常見陷阱

症狀原因解法
gRPC build 失敗：找不到 proto-generated 類別 proto 不在 src/main/proto 確認檔案位置正確，跑 mvn clean compile
@GraphQLApi 沒生效 未加 @ApplicationScoped 加上 CDI scope
GraphQL N+1 查詢爆炸 子欄位沒 batched resolver 改 @Source List<T> 簽名
gRPC 從外部呼叫不通 Ingress 不支援 HTTP/2 或 gRPC 配置 backend-protocol GRPC 或改 gRPC-Web
GraphQL Subscription 連上但無事件 BroadcastProcessor 沒在事件發生時 onNext 在 Mutation/Service 層手動 push
GraphiQL 對 secure subscription 不送 token 已知行為，UI 不傳 Authorization 到 WebSocket 用程式化 client（gql、Apollo）測試

本章小結

  • gRPC：合約優先，.proto 編譯為 Java stub，@GrpcService 實作；支援四種 RPC 模式（unary、server stream、client stream、bidi）。
  • 優先用 Mutiny 風格（Uni／Multi），與 Quarkus reactive 生態緊密整合。
  • gRPC client 用 @GrpcClient 注入；可整合 Stork 做服務發現。
  • Quarkus 自動實作 gRPC Health Check，K8s probe 直接用 grpc protocol。
  • GraphQL：@GraphQLApi + @Query / @Mutation / @Subscription，自動產生 schema 與 GraphiQL UI。
  • 用 @Source 寫欄位 resolver；批次 resolver（@Source List<T>）解決 N+1。
  • GraphQL Client 用宣告式介面 @GraphQLClientApi。
  • 三種 API（REST + gRPC + GraphQL）可共存於同一個 Quarkus 應用，共用相同的 service 層。
  • SRE 紅線：gRPC 需 Ingress HTTP/2 支援；GraphQL 需限制 query depth/complexity、注意 N+1、認證 subscription。
