Kafka 進階

第 22 章用 JSON 把訊息送上 Kafka 已經能跑，但生產級事件平台需要更多：Schema Registry 治理欄位演進； Avro／Protobuf 二進位節省頻寬；transactional producer 提供 exactly-once 寫入； Kafka Streams 把消費邏輯升級成串流拓樸；CloudEvents 標準化跨語言事件格式。 本章是真正進入「事件驅動架構」的門檻。

為什麼需要 Schema Registry

回到第 22 章的 JSON 寫法 ── 看似簡單但生產上有三個致命缺陷：

⚠
JSON-on-Kafka 的隱形成本
  1. 無 schema 約束：上游某天把 price 從 number 改成 string，下游全爆炸
  2. 欄位名重複寫進每筆訊息：百萬筆訊息 = 百萬份 "productId": 字串，浪費 30-50% 頻寬與儲存
  3. 無法演進追蹤：「上個月誰加了 discount 欄位？哪些消費者已適配？」無從查起

解法：外部化 schema。訊息只帶 schema ID，schema 本體存在中心化的 Schema Registry。

sequenceDiagram
  participant P as Producer
  participant R as Schema Registry
  participant K as Kafka
  participant C as Consumer

  P->>R: 註冊 schema v1
  R-->>P: schema ID = 42
  P->>K: 訊息 [magic byte + ID:42 + Avro binary]
  C->>K: 拉訊息
  C->>R: 用 ID:42 查 schema
  R-->>C: schema v1 定義
  C->>C: 用 schema 反序列化

面向Apicurio RegistryConfluent Schema Registry

ℹ︎
Apicurio v2 → v3 重大變更
Apicurio Registry 3.x 改 schema ID 從 8-byte（long）變 4-byte（int）。
v2 寫的訊息不能直接被 v3 client 讀，反之亦然 ── 除非顯式配置相容性。
全新專案直接用 v3 預設；既有 v2 訊息要存留則需 apicurio.registry.use-id=contentId 等顯式設定。

加擴充：Avro + Apicurio

bash
quarkus extension add messaging-kafka apicurio-registry-avro

dev 模式下，Kafka + Apicurio Registry 兩個容器都會自動啟動（Dev Services for Apicurio Registry）。零配置。

寫第一份 Avro Schema

json · src/main/avro/order-event.avsc
{
  "type": "record",
  "namespace": "com.example.events",
  "name": "OrderEvent",
  "fields": [
    { "name": "orderId", "type": "string" },
    { "name": "type",    "type": { "type": "enum", "name": "OrderType",
                                    "symbols": ["CREATED", "PAID", "CANCELLED"] } },
    { "name": "total",   "type": { "type": "bytes", "logicalType": "decimal",
                                    "precision": 12, "scale": 2 } },
    { "name": "at",      "type": { "type": "long", "logicalType": "timestamp-millis" } },
    { "name": "userId",  "type": ["null", "string"], "default": null }
  ]
}

Maven 編譯 schema → Java class

xml · pom.xml

Java · 程式碼幾乎不變
import com.example.events.OrderEvent;
import com.example.events.OrderType;

@Path("/orders")
public class OrderResource {

    @Channel("order-events")
    Emitter<OrderEvent> emitter;

    @POST
    public Response create(CreateOrderRequest req) {
        Order o = orderRepo.create(req);
        OrderEvent ev = OrderEvent.newBuilder()
            .setOrderId(o.id())
            .setType(OrderType.CREATED)
            .setTotal(o.total().unscaledValue().toByteArray() /* simplified */)
            .setAt(Instant.now().toEpochMilli())
            .setUserId(o.userId())
            .build();
        emitter.send(ev);
        return Response.accepted().entity(o).build();
    }
}

Schema 演進相容性

Avro schema 改動有四種相容性模式，由 Registry 強制檢查：

模式允許的變更不允許
BACKWARD新版可讀舊版（新增有 default 的欄位、刪除欄位）新加 required 欄位
FORWARD舊版可讀新版（刪除有 default 的欄位）移除 required 欄位
FULLBACKWARD + FORWARD（最嚴格）不向下／向上相容的變更
NONE任何變更（不檢查）（什麼都允許 = 沒保護）
✓
生產推薦：BACKWARD
BACKWARD 最務實：先升 producer（送新格式），再升 consumer（讀新格式），舊 consumer 仍能讀新訊息（忽略新欄位）。 若有舊 consumer 仍要讀新訊息，新增欄位都必須有 default。

schema 演進範例

json · 加新欄位（BACKWARD 相容）
{
  "type": "record",
  "name": "OrderEvent",
  "fields": [
    /* ... 既有欄位 ... */
    { "name": "discount", "type": ["null", "double"], "default": null },
    { "name": "source",   "type": "string", "default": "WEB" }
  ]
}

Registry 在註冊新版時自動 reject 不相容變更。

Transactional Producer：exactly-once 寫入

Kafka 預設 at-least-once。要達到 exactly-once 寫入（producer 端去重）需要 transactional producer：

application.properties
mp.messaging.outgoing.order-events.transactional.id=order-tx-${HOSTNAME}
mp.messaging.outgoing.order-events.enable.idempotence=true
mp.messaging.outgoing.order-events.acks=all
mp.messaging.outgoing.order-events.max.in.flight.requests.per.connection=5
Java · KafkaTransactions API
import io.smallrye.reactive.messaging.kafka.transactions.KafkaTransactions;

@ApplicationScoped
public class OrderService {

    @Channel("order-events")
    KafkaTransactions<OrderEvent> txEmitter;

    @POST @Transactional       // JTA + Kafka 兩階段 commit
    public Order placeOrder(CreateOrderRequest req) {
        return txEmitter.withTransaction(emitter -> {
            Order o = orderRepo.create(req);
            emitter.send(buildEvent(o, "CREATED"));
            emitter.send(buildEvent(o, "ANALYTICS"));
            return Uni.createFrom().item(o);
            // emitter 內所有 send 在同一個 Kafka transaction
            // 若 JTA rollback，Kafka transaction 也 abort
        }).await().indefinitely();
    }
}
⚠
transactional.id 必須每個 Pod 都唯一且穩定
若兩個 Pod 用相同 transactional.id，後啟動者會 fence 掉前者，造成持續切換。 用 ${HOSTNAME}（StatefulSet）或 K8s Downward API 注入唯一 ID。 Deployment 滾動更新時要小心，舊 Pod 結束後新 Pod 才能用同 ID。

Kafka Streams：消費邏輯升級成拓樸

當你的處理邏輯比「收訊息 → 寫 DB」更複雜（聚合、JOIN、視窗、stateful 處理），Kafka Streams 比 Reactive Messaging consumer 更合適。

bash
quarkus extension add kafka-streams
Java · Topology 定義
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.Topology;
import org.apache.kafka.streams.kstream.*;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.inject.Produces;

@ApplicationScoped
public class OrderStreamTopology {

    @Produces
    public Topology buildTopology() {
        StreamsBuilder builder = new StreamsBuilder();

        KStream<String, OrderEvent> orders = builder.stream("order-events");

        // 1. 過濾出 PAID
        KStream<String, OrderEvent> paid = orders.filter(
            (k, v) -> v.getType() == OrderType.PAID);

        // 2. 依 userId 重新分區，並做每分鐘窗口聚合
        KTable<Windowed<String>, Long> paidPerMinute = paid
            .groupBy((k, v) -> v.getUserId().toString())
            .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))
            .count();

        // 3. 輸出到另一個 topic
        paidPerMinute.toStream()
            .map((wk, count) -> KeyValue.pair(wk.key(), count))
            .to("user-paid-counts");

        return builder.build();
    }
}
application.properties
quarkus.kafka-streams.application-id=order-aggregator
quarkus.kafka-streams.bootstrap-servers=${kafka.bootstrap.servers}
quarkus.kafka-streams.topics=order-events

# 整合 Apicurio Avro SerDes
quarkus.kafka-streams.schema-registry-key=apicurio.registry.url
quarkus.kafka-streams.schema-registry-url=http://apicurio:8080/apis/registry/v3
ℹ︎
Streams vs Reactive Messaging consumer
  • Reactive Messaging：訊息 → 業務動作（寫 DB、call 外部 API）
  • Kafka Streams：訊息 → 訊息（過濾、聚合、JOIN、視窗、輸出回 Kafka）
  • 需要 stateful 處理（KTable、Windows）一定是 Streams
  • 同一個應用可以同時用，但通常拆服務更清楚

CloudEvents 標準

跨組織、跨語言交換事件時，CloudEvents 提供統一信封格式（CNCF 標準）。Quarkus Kafka 內建支援：

Java · 寫 CloudEvent
import io.smallrye.reactive.messaging.ce.OutgoingCloudEventMetadata;

@Channel("order-events")
Emitter<OrderEvent> emitter;

public void send(OrderEvent ev) {
    emitter.send(Message.of(ev).addMetadata(
        OutgoingCloudEventMetadata.<String>builder()
            .withId(UUID.randomUUID().toString())
            .withSource(URI.create("/catalog/orders"))
            .withType("com.example.order.created.v1")
            .withSubject(ev.getOrderId().toString())
            .build()));
}
application.properties · 模式選擇
# binary mode（預設）：CloudEvents 屬性放在 Kafka headers，payload 仍是 Avro/JSON
mp.messaging.outgoing.order-events.cloud-events-mode=binary

# structured mode：整個訊息是 application/cloudevents+json
# mp.messaging.outgoing.order-events.cloud-events-mode=structured

貫穿專案進度：catalog-service 升級到 Avro

把第 22 章的 JSON 訊息全部換成 Avro：

  • 新增 src/main/avro/ 目錄，放每個事件的 .avsc
  • CI/CD 加 Apicurio Maven plugin，在 deploy 前驗證 schema 與 registry 中的相容性
  • Registry 部署用 PostgreSQL 後端 + 3 個 replica，HA
  • Consumer 啟用 use-specific-avro-reader=true，用編譯出的型別安全類別
  • 對外（跨團隊）事件包成 CloudEvents 格式，內部事件直接 Avro

DevOps / SRE 視角

Schema Registry 部署

✓
生產配置要點
  • 儲存後端：PostgreSQL（最穩定）；別用 Kafka 後端（雞生蛋）
  • 多 replica：至少 2 個，前面放 Service Load Balancer
  • 身份驗證：OIDC（與第 27 章整合）
  • 備份：DB 端定期備份；schema 是 critical metadata
  • 禁止 auto-register 在生產 ── schema 變更走 CI/CD review
  • 強制 BACKWARD 相容性：Registry 設 global rule

Partition 重新分配

業務成長導致 partition 不夠用時，能加 partition 但要小心：

  • 同 key 的訊息順序會被打破（partition 數變、hash 結果變）
  • 對外發 ApiUpdate 通知所有 consumer 知道
  • 用 kafka-reassign-partitions.sh 工具搬資料
  • 大型 cluster 建議用 Cruise Control 自動化

監控的進階指標

  • Schema Registry：請求延遲、schema 註冊速率、4xx/5xx 比例
  • Streams 應用：commit-latency、poll-latency、stale RocksDB 警告
  • Transactional producer：txn-init-time-ns、txn-commit-time-ns

常見陷阱

症狀原因解法
v2 寫的訊息 v3 讀不到（magic byte 錯） Apicurio v2→v3 ID 格式改變 新環境用 v3 預設；舊資料保留則配置相容模式
升 schema 後 producer 啟動失敗 違反 BACKWARD 相容性 新欄位加 default；不要改既有欄位型別
Kafka Streams 重啟極慢 state store rebuild 用 PVC 保留 state、啟用 standby replica
transactional.id 衝突 多 Pod 用同 ID 每 Pod 唯一 ID（用 ${HOSTNAME} 或 K8s Downward API）
Confluent client 找不到 schema.registry.url Quarkus property 命名不同 顯式設 schema.registry.url，不要靠 Quarkus 短名
specific Avro reader 反序列化得到 GenericRecord 沒設 use-specific-avro-reader=true 顯式啟用

本章小結

  • JSON-on-Kafka 是學習用，生產必上 Schema Registry：治理欄位演進、節省頻寬、防止格式漂移。
  • Quarkus 提供 quarkus-apicurio-registry-avro 與 quarkus-confluent-registry-avro 兩條路。
  • Apicurio Registry v2→v3 schema ID 格式改變（8-byte → 4-byte），跨版本要注意。
  • Avro schema 演進的四種相容性：BACKWARD（最常用）、FORWARD、FULL、NONE。
  • transactional producer 提供 exactly-once 寫入；transactional.id 每 Pod 必須唯一穩定。
  • Kafka Streams 是訊息→訊息的拓樸式處理；Reactive Messaging 是訊息→業務動作。
  • Quarkus 用 @Produces public Topology 注冊 Streams 拓樸。
  • CloudEvents（CNCF 標準）跨語言事件信封：binary 與 structured 兩種傳輸模式。
  • 生產 Registry 部署：PostgreSQL 後端、多 replica、OIDC 驗證、禁 auto-register、強制 BACKWARD。
  • Partition 加減會打破同 key 順序；用工具或 Cruise Control 規劃重新分配。
