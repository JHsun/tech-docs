應用生命週期與初始化

什麼時候適合做快取預熱？什麼時候該關閉連線池？啟動失敗該不該讓 Pod 直接 crash？ Quarkus 提供清晰的生命週期 hook，讓你能在「對的時間做對的事」。 但要注意 ── native image 模式下，某些 hook 的觸發時機與你預期的不同。

圖 7-1 ─ Quarkus 應用完整生命週期與各 hook 觸發時機

⚠
不要在 main 方法塞業務邏輯
Quarkus 自動生成 main 方法，但在它執行的那一刻，CDI 容器尚未初始化。 在 main 裡注入 Bean、讀配置都會失敗。要在啟動時跑邏輯，請用 StartupEvent 或 @Startup。

最常用：StartupEvent / ShutdownEvent

絕大多數啟動／關閉邏輯都用這對事件解決：

Java · 完整範例
import io.quarkus.runtime.ShutdownEvent;
import io.quarkus.runtime.StartupEvent;
import io.quarkus.logging.Log;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Observes;

@ApplicationScoped
public class AppLifecycle {

    void onStart(@Observes StartupEvent ev) {
        Log.info("應用啟動 ── 預熱快取、連線檢查");
        warmupCache();
        verifyExternalServices();
    }

    void onStop(@Observes ShutdownEvent ev) {
        if (ev.isStandardShutdown()) {
            Log.info("正常關閉");
        } else {
            Log.warn("緊急關閉（收到 signal）");
        }
        flushBuffers();
        closeConnections();
    }
}

觸發時機：

  • StartupEvent：所有 CDI Bean 初始化完成、HTTP server 啟動之前
  • ShutdownEvent：收到 SIGTERM/SIGINT，HTTP server 已停止接收新請求
ℹ︎
isStandardShutdown 的用途
ShutdownEvent.isStandardShutdown() 在 SRE 場景很重要：
  • true ── 正常呼叫 Quarkus.asyncExit() 或從應用內部觸發
  • false ── 來自 OS signal（K8s SIGTERM、Ctrl+C），通常代表「外力中斷」
可據此決定 cleanup 的詳細程度（緊急關閉時跳過慢操作，避免 K8s 等不及 SIGKILL）。

@Startup：簡化版的快速啟動

若你只是想在啟動時跑一個方法，不需要寫整個 observer，用 @Startup 註解更簡潔：

Java · @Startup 用法
import io.quarkus.runtime.Startup;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class CacheWarmer {

    @Startup
    void warmup() {
        // 啟動時立即執行，等同於觀察 StartupEvent
    }
}

更厲害的是：類別層級的 @Startup 強制 Bean 在啟動時就建立（而非等到第一次注入）：

Java · 類別層級的 @Startup
@Startup                    // 強制 eager init，不需等到被注入
@ApplicationScoped
public class MetricsRegistry {

    public MetricsRegistry() {
        // 啟動時建立，可在這做初始化（雖然不建議重活在 constructor）
    }
}

Reactive 版本

啟動邏輯若需要非阻塞 I/O（例如 HTTP 健康檢查、發 Kafka 訊息），@Startup 可回傳 Uni：

Java · Reactive 啟動
@ApplicationScoped
public class ReactiveInitializer {

    @Inject @RestClient
    ExternalApiClient client;

    @Startup
    Uni<Void> verifyExternalApi() {
        return client.ping()
            .onItem().invoke(() -> Log.info("外部 API 可達"))
            .onFailure().invoke(t -> Log.warn("外部 API 連線失敗", t))
            .replaceWithVoid();
    }
}

@Shutdown：對稱的關閉註解

對應 @Startup，@Shutdown 標示「應用關閉時要跑的方法」：

Java · @Shutdown 用法
import io.quarkus.runtime.Shutdown;
import io.quarkus.runtime.Startup;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class ConnectionPool {

    private DataSource ds;

    @Startup
    void init() {
        ds = createDataSource();
        Log.info("DataSource 建立");
    }

    @Shutdown
    void cleanup() {
        ds.close();
        Log.info("DataSource 關閉");
    }
}

@Shutdown 等同於 @Observes ShutdownEvent，是語法糖。可用 @Priority 控制執行順序：

Java · 控制關閉順序
@Shutdown(Shutdown.HIGH_PRIORITY)   // 越大越早執行
void closeBackgroundJobs() { /* ... */ }

@Shutdown(Shutdown.LOW_PRIORITY)    // 最後關閉
void closeMetrics() { /* ... */ }

@PostConstruct vs @Startup

很多人混淆這兩者。它們確實都在「啟動初期」執行，但語意不同：

面向@PostConstruct@Startup
觸發時機Bean instance 建立後應用整體 ready 後
適用 Bean任意 scope主要 @ApplicationScoped / @Singleton
能注入其他 Bean？同一個 Bean 內部初始化整個容器都已就緒
失敗影響該 Bean 創建失敗整個應用啟動失敗
典型用途處理 Bean 自己的內部狀態跨服務的整體初始化
ℹ︎
經驗法則
若邏輯只關 Bean 自己的事（例如解析 internal config），用 @PostConstruct。
若邏輯涉及多個 Bean 或外部服務（例如 warmup cache、ping external API），用 @Startup。

小心陷阱：@Initialized 在 Native Image 的不同

傳統 CDI 開發者習慣用 @Observes @Initialized(ApplicationScoped.class) 標示「應用啟動」。在 Quarkus 不要這樣寫：

Java · ❌ 不要這樣寫
// ❌ 在 native image 模式下會在「建構期」執行
void onStart(@Observes @Initialized(ApplicationScoped.class) Object ev) {
    pingDatabase();   // build time 還沒有資料庫！
}

原因：

  • JVM 模式：@Initialized 與 StartupEvent 觸發時機接近，差別不大
  • Native 模式：@Initialized(ApplicationScoped.class) 在 build time 就會被觸發，這時還沒有實際 runtime 資源
⚠
記住這條原則
在 Quarkus 中：啟動邏輯一律用 StartupEvent 或 @Startup， 永遠不要用 @Initialized(ApplicationScoped.class)。

QuarkusApplication：自訂 main 行為

Quarkus 預設生成一個 main 方法，啟動容器後等待關閉信號 ── 適合 server 類應用。 若你要寫命令列工具（跑完任務就退出），用 QuarkusApplication：

Java · CLI 工具
import io.quarkus.runtime.Quarkus;
import io.quarkus.runtime.QuarkusApplication;
import io.quarkus.runtime.annotations.QuarkusMain;

@QuarkusMain
public class ReportGenerator implements QuarkusApplication {

    @Inject
    ReportService service;

    @Override
    public int run(String... args) throws Exception {
        Log.info("產生報表 ── 接收參數: " + Arrays.toString(args));
        service.generate();
        return 0;       // 退出碼，跑完即終止應用
    }
}

與一般 server 應用的差別：

  • 不會 waitForExit：run 方法回傳後立即關閉應用
  • 已完整初始化：到 run 時 DI、配置、所有 Bean 都可用
  • 退出碼可控：回傳的 int 即程序 exit code

若要寫「跑完任務但保持應用運行」，可在 run 中呼叫 Quarkus.waitForExit()：

Java · 跑任務 + 保持 server 模式
@Override
public int run(String... args) throws Exception {
    Log.info("自訂啟動邏輯");
    Quarkus.waitForExit();   // 等待 SIGTERM
    return 0;
}

Init Tasks：分離初始化流程

某些初始化需要在應用啟動前完成，且不該重複執行（例如 schema migration）。 傳統做法是把這些放進 K8s initContainer。Quarkus 提供 Init Tasks 把這類邏輯與正常啟動分離。

application.properties · 啟用 init mode
quarkus.init-and-exit=true     # 跑完 init 任務就退出

典型場景：

  1. K8s Pod 啟動，initContainer 用 quarkus.init-and-exit=true 跑 Flyway migration
  2. 遷移完成、initContainer 退出
  3. 主 container 啟動正常 Quarkus 應用，schema 已就緒
✓
關鍵好處：避免多副本搶 migration
多 Pod 同時啟動時，若把 migration 寫在 StartupEvent，每個 Pod 都會嘗試遷移，可能造成資料庫鎖死或重複執行。 用 initContainer 確保只有一個 Pod 跑 migration，其他 Pod 等待後直接啟動。

K8s deployment 範例

yaml · Deployment 摘錄
spec:
  template:
    spec:
      initContainers:
      - name: db-migration
        image: catalog-service:1.0
        env:
        - name: QUARKUS_INIT_AND_EXIT
          value: "true"
        - name: QUARKUS_DATASOURCE_JDBC_URL
          value: jdbc:postgresql://db:5432/catalog
        envFrom:
        - secretRef:
            name: catalog-secrets

      containers:
      - name: catalog-service
        image: catalog-service:1.0
        envFrom:
        - secretRef:
            name: catalog-secrets

優雅關機（Graceful Shutdown）

在 K8s 環境中，當 Pod 被 terminate 時，kubelet 會：

  1. 把 Pod 從 Service endpoints 移除（停接新請求）
  2. 呼叫 preStop hook（若有定義）
  3. 送出 SIGTERM
  4. 等待 terminationGracePeriodSeconds 秒
  5. 若 Pod 還沒退出，送 SIGKILL 強制結束

Quarkus 預設 graceful shutdown 行為：

  • 收到 SIGTERM 後，停止接收新請求
  • 等待進行中的請求完成（直到 timeout）
  • 觸發 ShutdownEvent 與 @Shutdown 方法
  • 關閉 HTTP server、釋放資源
application.properties · 控制 grace timeout
# 等待進行中請求完成的最長時間，預設 0（立即關閉）
quarkus.shutdown.timeout=30s

# K8s 部署搭配
# terminationGracePeriodSeconds: 35   # 給 Quarkus 30s + 緩衝
⚠
SRE 紅線：兩個 timeout 要對得上
quarkus.shutdown.timeout 必須小於 K8s 的 terminationGracePeriodSeconds， 否則 Quarkus 還在等請求完成時就被 SIGKILL，導致請求失敗、連線中斷。建議差 5 秒緩衝。

完整實戰範例

把所有 hook 整合到一個 catalog-service：

Java · 完整生命週期管理
@ApplicationScoped
public class CatalogLifecycle {

    @Inject ProductRepository repository;
    @Inject @RestClient PricingApiClient pricingApi;
    @Inject Event<ApplicationReady> readyEvent;

    @Startup
    Uni<Void> onStart() {
        Log.info("=== Catalog Service 啟動 ===");
        return verifyDatabase()
            .chain(this::warmupCache)
            .chain(this::pingPricingApi)
            .invoke(() -> readyEvent.fire(new ApplicationReady()))
            .invoke(() -> Log.info("=== Catalog Service Ready ==="));
    }

    @Shutdown(Shutdown.HIGH_PRIORITY)
    void onStop() {
        Log.info("=== Catalog Service 關閉 ===");
        flushMetrics();
    }

    private Uni<Void> verifyDatabase() {
        return Uni.createFrom().item(() -> {
            long count = repository.count();
            Log.infof("資料庫連線正常，共 %d 筆產品", count);
            return (Void) null;
        });
    }

    private Uni<Void> warmupCache() {
        // 預載熱門產品
        return Uni.createFrom().nullItem();
    }

    private Uni<Void> pingPricingApi() {
        return pricingApi.health()
            .onFailure().recoverWithItem(() -> {
                Log.warn("Pricing API 暫時無法存取，將以 fallback 模式運作");
                return null;
            })
            .replaceWithVoid();
    }
}

DevOps / SRE 視角

啟動失敗的策略選擇

啟動時驗證資料庫連線、外部 API 健康狀況，是好習慣。但要決定失敗時該怎麼辦：

策略實作適用場景
快失敗（Fail-fast） 在 @Startup 直接 throw exception 關鍵依賴必須可用（資料庫）
軟降級（Degraded） 記 warn log、設 flag、繼續啟動 非關鍵依賴（cache、metric server）
等待重試（Wait-and-retry） Reactive 配合 retry 邏輯 啟動順序敏感（DB 還沒準備好）

整合 K8s Probes

第 34 章會深入 Health Check，這裡先點出生命週期相關設定：

yaml · K8s Probe 配置
spec:
  containers:
  - name: catalog
    image: catalog:1.0

    # Startup Probe：給應用足夠時間完成 @Startup 邏輯
    startupProbe:
      httpGet: { path: /q/health/started, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2          # 30 × 2 = 60s 啟動緩衝

    # Readiness Probe：StartupEvent 完成後才開始接流量
    readinessProbe:
      httpGet: { path: /q/health/ready, port: 8080 }
      periodSeconds: 5

    # Liveness Probe：應用 hang 住時自動重啟
    livenessProbe:
      httpGet: { path: /q/health/live, port: 8080 }
      periodSeconds: 10

  terminationGracePeriodSeconds: 35   # 對應 quarkus.shutdown.timeout=30s

常見陷阱

症狀原因解法
@PostConstruct 中注入的 Bean 是 null 用了 @Singleton 加 field 注入 改 @ApplicationScoped 或 constructor 注入
啟動邏輯在 native 模式跑兩次 誤用 @Initialized(ApplicationScoped.class) 改用 StartupEvent 或 @Startup
ShutdownEvent 沒被觸發 應用被 SIGKILL 強制結束 確認 terminationGracePeriodSeconds 足夠
K8s rolling update 期間請求 502 沒設 graceful shutdown timeout 設 quarkus.shutdown.timeout=30s + 對應 K8s 設定
@Startup 阻塞太久，K8s 認為失敗 啟動邏輯太重 用 reactive 並調大 startupProbe 容忍度
多 Pod 同時做 DB migration 衝突 migration 在 StartupEvent 改 initContainer 用 quarkus.init-and-exit=true

本章小結

  • 主要 hook：StartupEvent / ShutdownEvent 觀察者，或 @Startup / @Shutdown 註解（語法糖）。
  • 不要在 main 方法寫業務邏輯，那時 CDI 還沒就緒。
  • 不要用 @Initialized(ApplicationScoped.class) ── native 模式會在 build time 觸發。
  • QuarkusApplication + @QuarkusMain 用於 CLI 工具與自訂啟動流程。
  • Init Tasks（quarkus.init-and-exit=true）配合 K8s initContainer 解決 schema migration 等一次性任務。
  • SRE 必須對齊 quarkus.shutdown.timeout 與 K8s terminationGracePeriodSeconds，避免 in-flight 請求被砍。
  • ShutdownEvent.isStandardShutdown() 區分正常／緊急關閉，決定 cleanup 細節。
