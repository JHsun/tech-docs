Metrics（Micrometer）

Logs 告訴你「發生什麼」、metrics 告訴你「有多少 / 多快」。 Quarkus 用 Micrometer（Spring 生態同源的 metrics facade）作為 metric API， 背後可插 Prometheus、Datadog、CloudWatch、Stackdriver 等十幾種 registry。 本章從 4 種 meter 類型（Counter / Timer / Gauge / DistributionSummary）入手， 教你用 @Counted、@Timed 註解快速埋點， 然後談 Tags 的高低基數設計（多數人在這裡踩雷把 Prometheus 撐爆）， 最後接上 RED method 與 Grafana dashboard。

為什麼需要 metrics

✓
Logs 解決不了的問題
Logs 告訴你「user X 下單 timeout」── 但要知道過去 5 分鐘有多少筆 timeout，你得 grep 全部 log，慢且貴。 Metrics 把這類問題壓成固定大小的時序數字：
  • 每秒事件數（rate）
  • P95 / P99 延遲（histogram）
  • 當前活躍連線數（gauge）
  • 錯誤率（counter ratio）
成本低、查詢快、適合做警報。

Micrometer：為什麼選它

Quarkus 早期用 MicroProfile Metrics，3.x 起官方推薦 Micrometer。差別：

面向MicroProfile MetricsMicrometer
來源Jakarta EE 規範Spring / Pivotal 生態
後端 registry 數量少（Prometheus 為主）多（10+ 種：Prometheus、Datadog、CloudWatch、StackDriver、New Relic…）
API 風格annotation 為主annotation + programmatic 並重
Tags 支援有限強大、設計核心
2026 狀態仍能用，但 Quarkus 不再投資主推、持續演進

第一個 metrics endpoint

加擴充

bash
quarkus extension add micrometer-registry-prometheus

這一行加進 quarkus-micrometer（核心）+ micrometer-registry-prometheus（後端）。其他後端對應的擴充名：micrometer-registry-datadog、micrometer-registry-azure-monitor 等。

立刻看到一堆免費 metrics

$ curl http://localhost:8080/q/metrics | head -30 # HELP http_server_requests_seconds # TYPE http_server_requests_seconds summary http_server_requests_seconds_count{method="GET",outcome="SUCCESS",status="200",uri="/orders"} 142.0 http_server_requests_seconds_sum{method="GET",outcome="SUCCESS",status="200",uri="/orders"} 4.823 # HELP jvm_memory_used_bytes # TYPE jvm_memory_used_bytes gauge jvm_memory_used_bytes{area="heap",id="G1 Eden Space"} 8.388608E7 jvm_memory_used_bytes{area="heap",id="G1 Old Gen"} 4.5E7 # HELP system_cpu_usage # TYPE system_cpu_usage gauge system_cpu_usage 0.0234

無需配置，Quarkus 自動把以下 metrics 暴露：

  • HTTP server：每個 endpoint 的請求數 / 延遲 / 狀態碼
  • JVM：heap、GC、thread count、class loading
  • System：CPU、process memory
  • Datasource：connection pool 使用率（接 quarkus-agroal 時）
  • Cache：hit rate（接 quarkus-cache 時）
  • Kafka client：consumer lag、producer 量（接 reactive messaging 時）
ℹ︎
Quarkus 的「自動 binder」哲學
這些 metrics 不是你寫的 ── Quarkus 偵測哪些擴充存在，自動掛上對應 binder。這呼應 Quarkus 「慣例優於配置」── 多數應用不寫一行 metric code 就有觀察基底。

圖 34-1 ─ 四種 meter 對應四種典型問題

Counter：次數

Java · annotation 方式
import io.micrometer.core.annotation.Counted;

@Path("/orders")
public class OrderResource {

    @POST
    @Counted(value = "orders.created", description = "訂單建立次數")
    public Order create(OrderRequest req) {
        // ...
    }
}
Java · programmatic 方式
import io.micrometer.core.instrument.MeterRegistry;

@ApplicationScoped
public class OrderService {

    @Inject MeterRegistry registry;

    public Order place(OrderRequest req) {
        Order o = ...;
        registry.counter("orders.created",
                          "status", o.getStatus().name(),
                          "tier", req.userTier()).increment();
        return o;
    }
}
⚠
Counter 只增不減
Counter 是單調遞增計數器，永遠只能 +1，不能減。要「目前還剩多少」用 Gauge；要「成功率」用兩個 counter 相除。

Timer：延遲分布

Java · annotation
import io.micrometer.core.annotation.Timed;

@GET @Path("/{id}")
@Timed(value = "orders.lookup", description = "訂單查詢延遲",
       histogram = true,                         // 啟用 percentile buckets
       percentiles = {0.5, 0.95, 0.99})
public Order get(@PathParam("id") Long id) {
    return orderRepo.findById(id);
}
Java · programmatic
@Inject MeterRegistry registry;

public Order checkout(Cart cart) {
    return registry.timer("checkout.duration",
                           "payment", cart.paymentMethod())
                    .record(() -> doCheckout(cart));
}

Timer 一次給你三件事：count（次數）、sum（總時間）、max（最慢一筆）。開了 histogram 還有 P50/P95/P99。

✓
不要 count 你能 time 的東西
Timer 已含 count（每次 record 都加 1），所以同一個方法不要同時加 @Counted + @Timed。 Timer 提供更多資訊，counter 是 Timer 的子集。

Gauge：當前狀態

Java · 監控 queue 深度
import io.micrometer.core.instrument.Gauge;

@ApplicationScoped
public class JobProcessor {

    private final Queue<Job> pending = new ConcurrentLinkedQueue<>();

    @Inject MeterRegistry registry;

    @PostConstruct
    void init() {
        Gauge.builder("jobs.pending", pending, Queue::size)
            .description("待處理任務數")
            .register(registry);
    }
}
⚠
Gauge 不能 hold 強引用造成記憶體洩漏
Micrometer 對 gauge 用 weak reference 持有目標物件 ── 物件被 GC 後 gauge 自動消失。 用「對 collection / map 建立 gauge」一定要保留物件的強引用（如成員變數），不然 gauge 變 NaN。

DistributionSummary：非時間數字分布

Java · 監控 payload 大小
@Inject MeterRegistry registry;

public void receiveMessage(Message msg) {
    registry.summary("message.payload.bytes",
                      "topic", msg.topic())
            .record(msg.payload().length);
}

Tags：高基數 vs 低基數

Tags（也叫 labels）讓 metric 多維化：

http_server_requests_seconds_count{method="GET",uri="/orders",status="200"} 1042 http_server_requests_seconds_count{method="GET",uri="/orders",status="500"} 5 http_server_requests_seconds_count{method="POST",uri="/orders",status="201"} 287

每組獨特的 tag 值都是一條獨立 time series。10 個 tag、每個 10 個值 → 10⁰⁰⁰⁰ = 100 億條 time series。Prometheus 直接爆炸。

⚠
絕對禁止當 Tag 的東西
  • userId：每個 user 一條 series，幾百萬使用者直接爆
  • orderId / sessionId / requestId：唯一值無限增長
  • error message：自由文本
  • timestamp：series 開銷在 time，不在 tag
  • full path with id（如 /users/12345）：要用 templated path（/users/:id）
這是 metrics 系統第一大事故源。Prometheus / Datadog 帳單一夜暴漲都源於這個。
✓
合適的 Tag 例子
  • method：GET/POST/PUT/DELETE（<10 值）
  • status_code：200/400/500（<100 值）
  • endpoint_template：/orders/:id（事先列舉）
  • region / tenant：少量列舉
  • user_tier：free/premium/enterprise（3-10 值）
  • outcome：success/client_error/server_error
經驗法則：每個 tag 值不超過 100 個、總 tag 組合不超過 10000。

Common Tags：所有 metric 統一加

application.properties
quarkus.micrometer.binder.http-server.suppress-non-application-uris=true

# 全域 tag
%prod.quarkus.micrometer.export.prometheus.path=/q/metrics
Java · MeterFilter 加 common tags
import io.micrometer.core.instrument.config.MeterFilter;
import io.micrometer.core.instrument.Tag;

@Singleton
public class MetricsConfig {

    @ConfigProperty(name = "deployment.env") String env;
    @ConfigProperty(name = "deployment.region") String region;

    @Produces @Singleton
    public MeterFilter globalTags() {
        return MeterFilter.commonTags(List.of(
            Tag.of("application", "catalog-service"),
            Tag.of("env", env),
            Tag.of("region", region)
        ));
    }
}

所有 metric 都自動帶上 application、env、region ── Grafana 可以快速切分不同環境同個應用的數據。

過濾雜訊：忽略不重要的 URI

每個 K8s liveness probe 都觸發一筆 /q/health metric，會把 Prometheus 塞滿沒用的數字：

application.properties
# 忽略管理 endpoint metrics
quarkus.micrometer.binder.http-server.ignore-patterns=/q/.*

# 忽略特定路徑
quarkus.micrometer.binder.http-server.ignore-patterns=/q/.*,/internal/.*

配 Prometheus scrape

yaml · prometheus.yml scrape 配置
scrape_configs:
  - job_name: 'catalog-service'
    metrics_path: /q/metrics
    scrape_interval: 15s
    scrape_timeout: 10s
    static_configs:
      - targets: ['catalog-service:8080']

K8s 用 ServiceMonitor（Prometheus Operator）

yaml · ServiceMonitor

kind: ServiceMonitor
metadata:
  name: catalog-service
  labels:
    release: prometheus       # ← 匹配 Prometheus Operator 的 selector
spec:
  selector:
    matchLabels:
      app: catalog-service
  endpoints:
    - port: http
      path: /q/metrics
      interval: 15s

RED method：每個服務必看的三個指標

Tom Wilkie 提出的 RED method 給出每個 microservice 該監控的最小集：

指標意義對應 meter
Rate每秒請求數Counter（或 Timer 的 count）
Errors失敗率Counter（按 status 分類）
Duration延遲分布（P50/P95/P99）Timer（with histogram）
promql · catalog-service 的 RED 查詢
# Rate
sum by(uri) (rate(http_server_requests_seconds_count{
  application="catalog-service"
}[5m]))

# Errors (5xx rate)
sum by(uri) (rate(http_server_requests_seconds_count{
  application="catalog-service",
  status=~"5.."
}[5m]))

# Duration P95
histogram_quantile(0.95,
  sum by(le, uri) (rate(http_server_requests_seconds_bucket{
    application="catalog-service"
  }[5m]))
)
ℹ︎
基礎設施有 USE，服務有 RED
USE（Utilization / Saturation / Errors）給 host 用，RED 給應用服務用。 SRE Google book 後續又提出 Four Golden Signals（latency / traffic / errors / saturation）── 概念相通。 記住一個原則就行：每個服務至少要能回答「多快、多忙、多錯」。

貫穿專案進度：catalog-service 業務 metrics

免費的 HTTP/JVM metrics 已夠用，但業務團隊還想看：

  • 每分鐘下單數（依 tier 切）
  • 下單延遲 P99
  • 訂單金額分布
  • 當前購物車活躍數
  • 各支付方式失敗率
Java · 業務 metrics 集中
@ApplicationScoped
public class OrderMetrics {

    @Inject MeterRegistry registry;

    private final AtomicInteger activeCarts = new AtomicInteger();

    @PostConstruct
    void initGauges() {
        Gauge.builder("carts.active", activeCarts, AtomicInteger::get)
            .description("當前活躍購物車")
            .register(registry);
    }

    public void recordOrderPlaced(Order order) {
        registry.counter("orders.placed.total",
                          "tier", order.userTier(),
                          "payment", order.paymentMethod())
                .increment();

        registry.summary("orders.amount",
                          "tier", order.userTier(),
                          "currency", order.currency())
                .record(order.amount().doubleValue());
    }

    public void recordOrderDuration(String stage, long millis) {
        registry.timer("orders.processing.duration",
                        "stage", stage)
                .record(millis, TimeUnit.MILLISECONDS);
    }

    public void cartCreated() { activeCarts.incrementAndGet(); }
    public void cartClosed()  { activeCarts.decrementAndGet(); }
}

把所有業務 metric 集中在單一 bean，好處：

  • metric 名稱有單一來源 ── 不會 typo 出 orders.placed vs order.placed
  • 新增 metric 容易 review
  • 測試容易（mock OrderMetrics）
  • 業務代碼乾淨 ── 只呼叫語意明確的方法

DevOps / SRE 視角

✓
Metrics 上線 checklist
  1. 裝 prometheus registry（多數場景；雲端原生用 cloudwatch / datadog）
  2. 暴露 /q/metrics（內部網路，不要對外）
  3. 裝 ServiceMonitor（K8s + Prometheus Operator 環境）
  4. common tags：application / env / region 一定要有
  5. tag cardinality 警報：Prometheus up 跑太慢、series 數突增就告警
  6. 忽略管理 endpoint：/q/.* 不採集
  7. RED dashboard：每個服務一個，作為公司模板
  8. 業務 metrics：與業務 PM 對齊，每月 review 用了沒
  9. histogram bucket：依場景調（API ms 級、batch 秒級不同）
  10. retention 與成本：高解析度短期（1 週）+ 降採樣長期（1 年）

常見陷阱

症狀原因解法
Prometheus 慢死 / OOM tag cardinality 爆炸 找出哪個 metric 的 series 最多（topk(10, count by (__name__)({__name__=~".+"}))），移掉高基數 tag
@Timed 不生效 同 class 內部呼叫（CDI proxy） 拆到別的 bean
Gauge 值是 NaN weak reference 物件被 GC 確保強引用保留（成員變數）
P99 跟 P95 數字一樣 histogram bucket 太粗 用 serviceLevelObjectives 加細 bucket
多 instance 數字看起來不一致 Prometheus 每個 instance 各自記 用 sum by(application) 聚合；instance 是維度不是 bug
JVM heap metric 沒有 JVM binder 被關 確認 quarkus.micrometer.binder.jvm=true
HTTP metric uri label 是 raw path 帶 ID 沒用 templated path Quarkus REST 預設用 template；REST resource 內訪問非 Quarkus 路由要自己處理
Dev mode metrics endpoint 404 extension 沒加 確認 micrometer-registry-prometheus 在 pom

本章小結

  • Metrics 解答「多少 / 多快 / 多錯」── logs 解答不了的問題。
  • Quarkus 3.x 用 Micrometer（取代舊的 MicroProfile Metrics），支援 10+ 種後端 registry。
  • 裝 micrometer-registry-prometheus 一行即得 HTTP / JVM / DB / Cache / Kafka 自動 metrics。
  • 四種 meter：Counter（次數）、Timer（延遲）、Gauge（瞬時值）、DistributionSummary（非時間分布）。
  • Timer 已含 count，別重複加 @Counted。
  • Gauge 用 weak reference，記得保留強引用避免 NaN。
  • Tags 高基數爆炸是第一大事故源：禁用 userId / orderId / error message 當 tag。
  • Common Tags：application / env / region 用 MeterFilter 統一加。
  • 忽略管理 endpoint：/q/.* 不採集，避免 noise。
  • RED method：Rate / Errors / Duration 是每個 microservice 必看的三個指標。
  • 用 K8s + Prometheus Operator → ServiceMonitor 自動發現。
  • 業務 metrics 集中在單一 bean（OrderMetrics），名稱單一來源、易測、業務代碼乾淨。
  • SRE 重點：series cardinality 警報、retention 分層、histogram bucket 設計、RED dashboard 模板化。
