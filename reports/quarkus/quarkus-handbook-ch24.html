AMQP / MQTT

Kafka 不是萬靈丹。需要點對點佇列、事務、企業整合？AMQP 1.0（ActiveMQ Artemis、Azure Service Bus）才是傳統選擇。 要與 IoT 設備、行動裝置低頻寬通訊？MQTT 是真正為受限環境設計的協定。 本章說明 Quarkus 如何用同一套 Reactive Messaging API 連接這兩個世界，以及與 Kafka 該怎麼取捨。

什麼時候 Kafka 不適合

⚠
Kafka 的設計取捨
Kafka 是分散式 log，不是傳統佇列。它對以下場景不太合身：
  • 需要每筆訊息獨立 ack/reject（Kafka 是 offset-based）
  • 嚴格 FIFO 跨整個 topic（Kafka 只在 partition 內保序）
  • 低訊息量、低延遲企業整合（Kafka cluster 維運成本高）
  • 客戶端是邊緣 IoT 裝置（Kafka client 太重）
  • 傳統 JMS 模式（pub/sub + queue + topic + durable subscription）
這些都是 AMQP / MQTT 的舒適區。

Part 1：AMQP 1.0

加擴充

bash
quarkus extension add messaging-amqp

dev 模式下，Quarkus 自動啟一個 ActiveMQ Artemis 容器（Dev Services for AMQP）。

程式碼幾乎與 Kafka 相同

Java · Producer/Consumer
@Path("/quotes")
public class QuotesResource {

    @Channel("quote-requests")
    Emitter<String> emitter;

    @POST @Path("/request")
    public String createRequest() {
        String id = UUID.randomUUID().toString();
        emitter.send(id);
        return id;
    }
}

@ApplicationScoped
public class QuoteProcessor {

    @Incoming("quote-requests")
    @Outgoing("quotes")
    @Blocking
    public Quote computeQuote(String requestId) {
        return new Quote(requestId, new Random().nextInt(1000));
    }
}

看出來了嗎？跟 Kafka 章節幾乎一模一樣 ── 只有 application.properties 不同：

application.properties
amqp-host=artemis.internal
amqp-port=5672
amqp-username=app
amqp-password=${AMQP_PASSWORD}

mp.messaging.outgoing.quote-requests.connector=smallrye-amqp
mp.messaging.outgoing.quote-requests.address=quote-requests
mp.messaging.outgoing.quote-requests.durable=true

mp.messaging.incoming.quote-requests.connector=smallrye-amqp
mp.messaging.incoming.quote-requests.address=quote-requests
mp.messaging.incoming.quote-requests.durable=true
mp.messaging.incoming.quote-requests.client-options-name=acks-mode

Address 模式：queue vs topic

AMQP 1.0 把所有目的地稱為「address」。在 ActiveMQ Artemis 端可以是 queue（點對點）或 multicast（pub/sub）：

application.properties
# 預設模式：anycast (queue 行為)
mp.messaging.outgoing.orders.address=orders

# 廣播模式：multicast (topic 行為)
mp.messaging.outgoing.events.address=events
mp.messaging.outgoing.events.client-options-name=multicast-config

# Consumer 端可選 durable subscription（重啟後仍保留訂閱）
mp.messaging.incoming.events.address=events
mp.messaging.incoming.events.durable=true
mp.messaging.incoming.events.containerId=catalog-service-sub-01

典型場景：Azure Service Bus

ℹ︎
Azure Service Bus 也是 AMQP 1.0
Microsoft Azure Service Bus 原生支援 AMQP 1.0，所以 smallrye-amqp 可直接連線。 使用 SAS Token 認證：
amqp-username=$ConnectionString
amqp-password=Endpoint=sb://...;SharedAccessKey=...
這讓 Quarkus 應用可以無痛跑在 Azure 上而不需鎖定到 vendor SDK。

Part 2：MQTT（IoT 場景）

MQTT 的獨特之處

  • Topic 階層：用 / 分層（sensors/floor1/room2/temp），訂閱可用萬用字元 +（單層）與 #（多層）
  • QoS 三級：0（最多一次）、1（至少一次）、2（恰好一次）
  • Retained message：broker 為每個 topic 保留最後一則訊息，新訂閱者立即收到
  • Last Will：client 不正常斷線時 broker 替它發布預先設定的訊息
  • 極輕協定：最小 2-byte header，適合低頻寬

加擴充

bash
quarkus extension add smallrye-reactive-messaging-mqtt

發送指令給設備

Java · 送 IoT 指令
@Channel("device-commands")
Emitter<String> commandEmitter;

public void rebootDevice(String deviceId) {
    // MQTT 用 metadata 指定動態 topic
    Message<String> msg = Message.of("reboot").addMetadata(
        OutgoingMqttMessageMetadata.builder()
            .withTopic("devices/" + deviceId + "/commands")
            .withQosLevel(MqttQoS.AT_LEAST_ONCE)
            .withRetain(false)
            .build());
    commandEmitter.send(msg);
}

QoS 三級對照

QoS保證機制適用
0at most oncefire-and-forget感測器讀數（高頻、容忍丟失）
1at least oncePUBACK 回應多數場景的預設
2exactly once4-way handshake計費、關鍵指令
⚠
QoS 2 的代價
QoS 2 需要 4 次網路往返才完成一筆訊息，吞吐顯著下降。
多數實際應用QoS 1 + 應用層去重已經夠用，且效能好得多。

圖 24-2 ─ MQTT 收邊緣訊息、Quarkus 橋接到 Kafka 進行後端處理

Java · 一個 method 完成橋接
@ApplicationScoped
public class MqttToKafkaBridge {

    @Incoming("mqtt-in")
    @Outgoing("kafka-out")
    public Message<SensorEvent> bridge(Message<byte[]> mqttMsg) {
        IncomingMqttMessageMetadata mqttMeta = mqttMsg.getMetadata(
            IncomingMqttMessageMetadata.class).orElseThrow();

        SensorEvent ev = parse(mqttMsg.getPayload());

        // 套上 Kafka metadata，用 topic 路徑當 key 保序
        return Message.of(ev).addMetadata(
            OutgoingKafkaRecordMetadata.<String>builder()
                .withKey(mqttMeta.getTopic())
                .build());
    }
}
application.properties
# 上游：MQTT
mp.messaging.incoming.mqtt-in.connector=smallrye-mqtt
mp.messaging.incoming.mqtt-in.topic=sensors/#
mp.messaging.incoming.mqtt-in.qos=1

# 下游：Kafka
mp.messaging.outgoing.kafka-out.connector=smallrye-kafka
mp.messaging.outgoing.kafka-out.topic=sensor-events
✓
同一份 API 接兩種協定
這就是 Reactive Messaging 的真正威力 ── 一個 Quarkus 應用同時用兩種 connector， 寫一行業務邏輯就把 MQTT 訊息原樣轉發到 Kafka。 生產實務這支橋接器通常有額外邏輯：解析、富化、批次、過濾異常值等。

附帶提醒：RabbitMQ 不適合 smallrye-amqp

⚠
RabbitMQ 用 0.9.1，不是 AMQP 1.0
雖然名字都叫 AMQP，但 RabbitMQ 預設用的是 AMQP 0.9.1，與 smallrye-amqp（AMQP 1.0）不相容。
要連 RabbitMQ 請用專用擴充：
quarkus extension add messaging-rabbitmq
或在 RabbitMQ 端啟用 AMQP 1.0 plugin（較少用）。

貫穿專案進度：catalog-service 補上兩條訊息

catalog-service 第 22 章已用 Kafka 處理核心訂單事件。現在補上：

  • AMQP queue 給「對外通知」（email、SMS）：用點對點佇列、每筆獨立 ack，失敗重試由 broker 端管，不必占用 Kafka topic
  • MQTT 給「實體商店終端機」回報庫存掃描：邊緣 IoT 場景天生適合，且橋接到 Kafka 一條鏈路打通

監控指標

  • AMQP：queue depth（堆積）、consumer count、ack rate、redelivery count
  • MQTT：連線數、訂閱數、retained message 數、QoS 1/2 ack 延遲
  • 橋接器：lag（MQTT 到 Kafka 的延遲）、轉換失敗率

常見陷阱

症狀原因解法
AMQP 連 RabbitMQ 失敗 RabbitMQ 預設用 AMQP 0.9.1 改用 messaging-rabbitmq 擴充
AMQP queue 訊息堆積 consumer 處理太慢或掛了 增 Pod、調整 prefetch、檢查業務邏輯
MQTT 連線數爆炸 單一 Pod 對應太多 IoT 設備 broker 水平擴展、用 MQTT cluster
MQTT 訊息丟失 QoS 0 + 網路不穩 升到 QoS 1
QoS 2 吞吐極差 4-way handshake 開銷 退回 QoS 1 + 應用層去重
MQTT 訂閱萬用字元拿不到訊息 用了 +/+ 但 topic 只有一層 調整訂閱式或測試 broker 端 topic 結構
橋接器積壓 Kafka 寫入比 MQTT 收入慢 增 partition、加 Pod、批次寫入

本章小結

  • Kafka、AMQP、MQTT 是互補而非競爭 ── 不同場景選對工具。
  • AMQP 1.0 適合企業整合：點對點佇列、單筆 ack、ActiveMQ Artemis、Azure Service Bus。
  • MQTT 適合 IoT：超輕協定、QoS 三級、retained message、十萬級並發連線。
  • Quarkus 用 smallrye-amqp 與 smallrye-mqtt 兩個 connector，程式碼幾乎跟 Kafka 相同。
  • RabbitMQ 預設用 AMQP 0.9.1，不能用 smallrye-amqp，要用 messaging-rabbitmq。
  • MQTT QoS：多數用 QoS 1，計費／關鍵指令才 QoS 2，感測讀數可 QoS 0。
  • 經典架構：MQTT 收邊緣 → Quarkus 橋接 → Kafka 處理，一個方法搞定。
  • SRE 重點：AMQP 看 queue depth、MQTT 看連線數、橋接看 lag。
