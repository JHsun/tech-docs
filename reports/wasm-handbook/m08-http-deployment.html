8.2路線一：Serverless 平台

最快上線的選項。把 .wasm 推到平台，剩下的（HTTP routing、TLS、global edge distribution、scaling）都由平台處理。

主要平台對照

平台定位底層 runtime計價模式
Fastly Compute@EdgeCDN 邊緣 Wasm，原 VCL 升級版Wasmtime fork每次請求 + bandwidth
Cloudflare Workers全球 PoP、JS-first 但支援 WasmV8 isolates + Wasm每百萬請求
Fermyon Cloud / AkamaiSpin 應用託管（2025 被 Akamai 收購）Spin / Wasmtime免費層 + 用量
Vercel Edge FunctionsVercel 生態邊緣函式V8 + Wasm請求數 + duration
Akamai EdgeWorkersAkamai CDN 邊緣V8 + Wasm企業合約
CosmonicwasmCloud 商業託管wasmCloud / Wasmtime用量計價
Wasmer EdgeWasmer 商業託管Wasmer用量計價

Serverless 平台的權衡

Lock-in 注意 各家 SDK 不同（Fastly 的 fastly crate、Cloudflare 的 worker crate、Spin 的 spin-sdk）。寫好的 .wasm 不能直接搬到另一家。未來 WASI 0.2 的 wasi:http 介面成熟後，可攜性會大幅提升——目前 Spin 與 wasmCloud 都已用 wasi:http 標準。

適合場景

  • 新創 / MVP：把資源放在產品而非基礎建設
  • 邊緣 function：圖片轉換、A/B test、auth proxy、地理路由
  • 低流量但要全球可用：享受 CDN 級分發
  • 不想管 K8s 的團隊

不適合場景

  • 強烈合規 / 資料主權需求（資料離開你的 region）
  • 有特殊網路拓撲（VPN、固定 IP allowlist）
  • 大型應用，計價可能變貴
  • 需要長執行時間任務（多數平台限 30 秒）

Go + wazero 範例

go 
package main

import (
    "context"
    "io"
    "net/http"
    "os"
    "sync"

    "github.com/tetratelabs/wazero"
    "github.com/tetratelabs/wazero/api"
    "github.com/tetratelabs/wazero/imports/wasi_snapshot_preview1"
)

type WasmPool struct {
    runtime  wazero.Runtime
    module   wazero.CompiledModule
    pool     chan api.Module
}

func NewPool(ctx context.Context, wasmBytes []byte, size int) (*WasmPool, error) {
    r := wazero.NewRuntime(ctx)
    wasi_snapshot_preview1.MustInstantiate(ctx, r)

    compiled, err := r.CompileModule(ctx, wasmBytes)
    if err != nil { return nil, err }

    p := &WasmPool{
        runtime:  r,
        module:   compiled,
        pool:     make(chan api.Module, size),
    }
    // 預熱 N 個 instance
    for i := 0; i < size; i++ {
        inst, _ := r.InstantiateModule(ctx, compiled, wazero.NewModuleConfig())
        p.pool <- inst
    }
    return p, nil
}

func (p *WasmPool) Get(ctx context.Context) api.Module {
    select {
    case inst := <-p.pool:
        return inst
    default:
        inst, _ := p.runtime.InstantiateModule(ctx, p.module, wazero.NewModuleConfig())
        return inst
    }
}

func (p *WasmPool) Put(inst api.Module) {
    select {
    case p.pool <- inst:
    default:
        inst.Close(context.Background())  // 池滿了丟棄
    }
}

func main() {
    ctx := context.Background()
    wasmBytes, _ := os.ReadFile("handler.wasm")
    pool, _ := NewPool(ctx, wasmBytes, 10)

    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        inst := pool.Get(r.Context())
        defer pool.Put(inst)

        // 把 request body 寫到 Wasm 記憶體
        body, _ := io.ReadAll(r.Body)
        // ... 序列化 method, path, headers, body 到 Wasm memory ...

        // 呼叫 Wasm handler
        handle := inst.ExportedFunction("handle")
        result, _ := handle.Call(r.Context())

        // 讀 Wasm 回傳的 response
        // ... 寫到 ResponseWriter ...
        _ = result
    })

    http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
    })

    server := &http.Server{
        Addr: ":8080",
    }

    // graceful shutdown
    go func() {
        if err := server.ListenAndServe(); err != http.ErrServerClosed {
            panic(err)
        }
    }()

    // 等待 signal
    var wg sync.WaitGroup
    wg.Add(1)
    wg.Wait()
}

用 wasi:http 簡化

自己寫序列化太繁瑣。用 Wasmtime 內建的 wasi:http 介面，宿主直接把 HTTP 請求 inject 給 component：

rust 
use wasmtime::component::*;
use wasmtime_wasi_http::{WasiHttpCtx, WasiHttpView};

// 寫一個 HTTP server，每個請求用一個全新 component instance
async fn handle_request(
    req: hyper::Request<hyper::body::Body>,
    engine: Arc<Engine>,
    component: Arc<Component>,
) -> Result<hyper::Response<hyper::body::Body>> {
    let mut store = Store::new(&engine, MyState::default());

    let linker = Linker::new(&engine);
    wasmtime_wasi_http::add_to_linker_async(&mut linker)?;

    let proxy = wasi_http_proxy::bindings::Proxy::instantiate_async(
        &mut store, &component, &linker
    ).await?;

    // wasmtime_wasi_http 自動處理 request 序列化
    let response = proxy.wasi_http_incoming_handler()
        .call_handle(&mut store, req).await?;

    Ok(response)
}

適合場景

  • 需要完全控制 routing、middleware、observability 細節
  • 嵌入 Wasm 到既有 Go / Rust 應用
  • 有特殊網路需求（自訂 protocol、TCP-level 處理）
  • 研究與實驗

8.5路線四：Proxy filter（Envoy / Istio / APISIX）

不是「跑一個服務」而是「在 proxy 中插入邏輯」。Envoy + Proxy-Wasm 是業界事實標準。

典型用途

  • 自訂 authentication / authorization 邏輯
  • 請求 / 回應 transformation（rewrite header、body、URL）
  • rate limiting、circuit breaker
  • A/B testing、canary routing
  • 客製 metrics / logging
  • 跨 service mesh 的政策實施

Proxy-Wasm 介面

Proxy-Wasm 是業界規範（spec），定義 proxy 與 Wasm filter 互動的 ABI。Envoy、Istio、APISIX、Kong、MOSN 等都實作此 spec。

rust 
// Rust Proxy-Wasm filter
use proxy_wasm::traits::*;
use proxy_wasm::types::*;

proxy_wasm::main! {{
    proxy_wasm::set_log_level(LogLevel::Trace);
    proxy_wasm::set_http_context(|_, _| -> Box<dyn HttpContext> {
        Box::new(AuthFilter)
    });
}}

struct AuthFilter;

impl Context for AuthFilter {}

impl HttpContext for AuthFilter {
    fn on_http_request_headers(&mut self, _: usize, _: bool) -> Action {
        // 檢查 Authorization header
        match self.get_http_request_header("authorization") {
            Some(auth) if auth.starts_with("Bearer ") => {
                // 驗證 token
                let token = &auth[7..];
                if validate_token(token) {
                    Action::Continue
                } else {
                    self.send_http_response(401, vec![], Some(b"unauthorized"));
                    Action::Pause
                }
            }
            _ => {
                self.send_http_response(401, vec![], Some(b"missing auth"));
                Action::Pause
            }
        }
    }
}

fn validate_token(token: &str) -> bool {
    // ... JWT 驗證邏輯
    true
}

8.6路線五：邊緣 / 嵌入式裝置

把 Wasm 部署到資源受限的裝置：車載 ECU、工業閘道、smart NIC、IoT sensor。

典型架構

  • WasmEdge：邊緣 + AI 推論強
  • WAMR：超低資源（85KB binary）
  • wasm3：純 interpreter，極小但慢

WAMR on microcontroller

把 WAMR 編進 firmware，OTA 更新只更新 .wasm 而非整個 firmware：

c 
#include "wasm_export.h"

uint8_t *wasm_buf;
uint32_t wasm_size;

int main() {
    // 載入從 OTA 收到的 .wasm
    wasm_buf = load_wasm_from_flash(&wasm_size);

    // WAMR 啟動
    wasm_runtime_init();

    wasm_module_t module = wasm_runtime_load(wasm_buf, wasm_size, ...);
    wasm_module_inst_t inst = wasm_runtime_instantiate(module, ...);

    // 呼叫 handle 函式
    wasm_function_inst_t func = wasm_runtime_lookup_function(inst, "handle");
    wasm_runtime_call_wasm(exec_env, func, 0, NULL);
}

適合場景

  • 車載 ECU、ADAS 邏輯
  • 工業 PLC、SCADA
  • 智慧城市 sensor 閘道
  • Smart NIC / DPU 上的封包處理
  • 區塊鏈節點 / 智能合約

8.7狀態外置：Wasm HA 的硬性要求

Wasm instance 設計為短暫、無狀態、可隨時銷毀。所有需要持久的狀態都得放外部。

Rust SDK 用法

rust 
use spin_sdk::http::{IntoResponse, Request, Response};
use spin_sdk::http_component;
use spin_sdk::key_value::Store;
use spin_sdk::sqlite::Connection;

#[http_component]
async fn handle(req: Request) -> Result<impl IntoResponse> {
    // KV
    let kv = Store::open_default()?;
    kv.set("last-request", req.uri().to_string().as_bytes())?;

    // SQLite
    let db = Connection::open_default()?;
    let result = db.execute(
        "INSERT INTO logs (path) VALUES (?)",
        &[req.uri().to_string().into()],
    )?;

    // 外部 HTTP
    let res = spin_sdk::http::send(
        Request::builder()
            .uri("https://api.example.com/data")
            .build()
    ).await?;

    Ok(Response::new(200, format!("logged {} rows", result.rows_affected)))
}

Spin Factors（Spin 3.0+）

2026 年 Spin 3.0 引入 Factors 架構——把 host capabilities 變成可插拔模組。客戶可以開發自家 factor 提供 Redis、Postgres、自訂 KV 等。

8.8與容器部署的根本差異

Wasm 部署的成本與效能特性，跟傳統容器差很多。

面向容器Wasm
冷啟動數百毫秒到秒級µs 到低毫秒
記憶體 baseline~50MB+~KB（無 OS userspace）
實例密度（單 node）10-100 個1000-10000 個
Image 大小10MB-1GB50KB-5MB
Scale-to-zero有冷啟動成本幾乎無感
沙箱保證OS-level（cgroup、namespace）VM-level（Wasm validation）
HTTP 入口process 開 port宿主提供，process 不開 port
狀態可在 container 內存 ephemeral必須外置
OS 相容性Linux / Windows 各打 image單一 .wasm 跨 OS

密度的實際意義

Fermyon 的測試顯示，單一 m5.large 節點：

  • 跑容器：可同時處理約 50 個獨立應用
  • 跑 Wasm：可同時處理 5000+ 個獨立應用

密度 100 倍意味成本壓縮 100 倍——這是企業導入 Wasm 的主要經濟動機。

冷啟動的實際意義

傳統 Lambda 冷啟動 200-1000ms，要靠 keep-warm 機制隱藏。Wasm 冷啟動 1-10ms，scale-to-zero 真的可用，閒置時零成本。

步驟 3 · 實作 handler
rust 
// src/lib.rs
use spin_sdk::http::{IntoResponse, Request, Response};
use spin_sdk::http_component;
use spin_sdk::key_value::Store;

#[http_component]
async fn handle_request(_req: Request) -> Result<impl IntoResponse> {
    let kv = Store::open_default()?;

    // 取得目前計數
    let count: u64 = kv.get("visit_count")?
        .map(|v| u64::from_le_bytes(v.try_into().unwrap_or([0; 8])))
        .unwrap_or(0);
    let new_count = count + 1;
    kv.set("visit_count", &new_count.to_le_bytes())?;

    // 取得 visitor IP（透過 outbound HTTP）
    let ip_resp = spin_sdk::http::send::<Request, Response>(
        Request::builder()
            .uri("https://api.ipify.org?format=json")
            .build()
    ).await?;
    let body = String::from_utf8_lossy(ip_resp.body());

    Ok(Response::builder()
        .status(200)
        .header("content-type", "application/json")
        .body(format!(r#"{{"count":{},"ip":{}}}"#, new_count, body))
        .build())
}

Module 08 · 10 題自我測驗

Q1.下列「Wasm HTTP 服務最快上線」的路線是？
  • 自架 K8s + 自寫 operator
  • Serverless 平台（Fermyon Cloud、Fastly、Cloudflare）
  • 自架 runtime + 自寫 HTTP server
  • 嵌入式裝置
看解答
答案 · B Serverless 平台上線速度分鐘級，運維幾乎為零。代價是 lock-in 與成本可預期性。
Q2.2026 K8s 跑 Wasm 的事實標準是？
  • Krustlet
  • containerd-wasm-shims + RuntimeClass
  • 把 Wasm 包進普通 container
  • 寫自家 operator
看解答
答案 · B Krustlet 已 archive，B 是事實標準。SpinKube 等 operator 進一步在這之上提供 CRD 抽象。
Q3.Spin 與 SpinKube 的關係是？
  • Spin 是核心 runtime；SpinKube 是 K8s operator 把 Spin app 變成 CRD
  • 兩者等價
  • Spin 是商業產品，SpinKube 開源
  • SpinKube 取代了 Spin
看解答
答案 · A Spin 是 Fermyon 開源的 serverless framework；SpinKube 是 CNCF Sandbox 的 K8s operator，把 Spin 應用以 SpinApp CRD 部署。
Q4.下列關於 Wasm 的「狀態管理」，何者正確？
  • Wasm instance 可以持久化記憶體
  • Wasm instance 設計為短暫無狀態，所有狀態必須外置（Redis、DB、Object Store）
  • Wasm 內建持久化儲存
  • 不能跨請求保持狀態
看解答
答案 · B 這是 Wasm HA 設計的核心原則——instance 可隨時銷毀重建，狀態靠外部 Redis、DB、KV、Object Store 等。Spin 內建 SDK 簡化整合。
Q5.Proxy-Wasm filter 適合哪個場景？
  • 寫一個完整 microservice
  • 在 Envoy / Istio / APISIX 中插入自訂 auth、rate-limit、transformation 邏輯
  • 嵌入式 IoT
  • 瀏覽器內 UI
看解答
答案 · B Proxy-Wasm 是業界 spec，讓 service mesh / API gateway 透過 Wasm 動態擴充邏輯。Envoy、Istio、APISIX、Kong、MOSN 都支援。
Q6.Wasm 部署相對於容器，「實例密度」典型差異是？
  • Wasm 較低，因為沙箱開銷大
  • 大致相同
  • Wasm 可達容器的 10-100 倍密度
  • 差距不明顯
看解答
答案 · C Wasm 無 OS userspace、記憶體 baseline KB 級而非 MB 級。Fermyon 公開測試顯示單 node 跑 Wasm 密度比容器高 100 倍。這是企業導入 Wasm 的主要經濟動機。
Q7.下列敘述 Wasm 的「冷啟動」，何者正確？
  • 與容器類似（數百毫秒）
  • µs 到低毫秒，scale-to-zero 真的可用
  • 必須靠 keep-warm 避免冷啟動
  • 冷啟動慢到不能用於 serverless
看解答
答案 · B Wasm 冷啟動極快是其招牌——讓 scale-to-zero 不再有「冷啟動懲罰」。Fastly、Cloudflare 主推這個賣點。
Q8.把 Spin app 推到 OCI registry 的指令是？
  • docker push
  • spin registry push ghcr.io/me/app:1.0
  • spin deploy --registry
  • kubectl apply
看解答
答案 · B Spin 內建 OCI registry 整合。也可以用 wkg 推單一 component。OCI image spec 已支援 Wasm artifact。
Q9.關於 Wasm HTTP service 與容器的「HTTP 入口」差異？
  • 兩者一樣，process 都會開 port
  • 容器 process 開 port；Wasm 自己不開 port，由宿主 / 平台提供 HTTP entrance
  • Wasm 不能處理 HTTP
  • 兩者都靠 socket
看解答
答案 · B Wasm 沒有 ambient 網路能力，自己不開 port。宿主（Spin、Fastly、Wasmtime serve）提供 HTTP server，把請求轉換為 component 的函式呼叫。
Q10.下列哪個是 2026 年「自架 Wasm K8s 服務」的最穩健組合？
  • Krustlet + 自寫 K8s operator
  • SpinKube + containerd-shim-spin + Spin（含 Wasmtime）
  • 在每個 Pod 啟動腳本內 spawn wasmtime
  • WasmEdge 取代 kubelet
看解答
答案 · B SpinKube + containerd-shim-spin 是 2026 K8s 跑 Wasm 的標準組合：開源、生產驗證、與 K8s 既有 HPA / PDB / Ingress 整合自然。
