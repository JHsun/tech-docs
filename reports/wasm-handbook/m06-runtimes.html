Runtime 比較
與自架方案

runtime 是 Wasm 的「JVM」——選錯會卡死你的部署架構。本章系統比較開源 Wasm runtime 與應用框架的設計取捨，幫你做出 evidence-based 的選型決策。

Practical Level ~4 hours Comparative analysis 5 個主流 runtime

本章學習目標

  • 系統比較 Wasmtime、wazero、WasmEdge、Wasmer、WAMR 等主流開源 runtime 的設計取捨。
  • 分辨應用框架（Spin、wasmCloud、Extism）與 raw runtime 的角色差異。
  • 用宿主語言、目標環境、合規需求三維度做 runtime 選型。
  • 實作 Go + wazero、Rust + Wasmtime 兩種嵌入式整合。
  • 了解 K8s 整合（containerd-wasm-shims、SpinKube）的當前事實標準。
  • 判斷 SaaS 平台（Fastly、Cloudflare、Fermyon）vs 自架的權衡。

6.1Runtime 的兩個層次

「Wasm runtime」這個詞涵蓋兩個層次：核心引擎（執行 .wasm 的 VM 實作）與應用框架（包含引擎再加上 HTTP server、KV store、排程器等高階能力）。混淆這兩層會導致選型錯亂。

Layer 1：核心 Runtime / 引擎

負責「執行 .wasm 模組」的最低層次：

  • 解析 binary、validation、JIT/AOT 編譯到原生碼
  • 管理 linear memory、instance lifecycle
  • 提供 host function 介面、WASI 標準介面實作
  • 暴露 SDK 給宿主應用嵌入

例子：Wasmtime、wazero、WasmEdge、Wasmer、WAMR、wasm3、wasmi。

Layer 2：應用框架 / 平台

建在核心 runtime 之上，提供「Wasm 應用該怎麼長」的更高層抽象：

  • HTTP server、HTTP routing
  • 事件 trigger（HTTP、Redis、cron）
  • KV / SQL / object store 整合
  • 多 instance 管理、排程
  • K8s 整合

例子：Spin（內含 Wasmtime）、wasmCloud（內含 Wasmtime）、Extism（多 runtime backend）、SpinKube（K8s operator）。

6.2主要核心 Runtime 深入比較

Wasmtime — 業界事實標準

背景：Bytecode Alliance 旗艦專案，Rust 寫，最早 2018 年由 Mozilla 啟動。

核心特性：

  • 事實上的 WASI 參考實作，新標準最早實作
  • Cranelift JIT/AOT 編譯器，效能優秀
  • Component Model 與 WASI 0.2 / 0.3 領先支援
  • 豐富的執行控制：fuel、epoch interruption、pooling allocator
  • 多語言綁定：C API、Python、Go、.NET、Ruby
  • 生產驗證：Fastly Compute@Edge、Microsoft Azure、Shopify 都在用

適合場景：生產級伺服器 / 邊緣 / Serverless、Component Model 應用、需要最新標準支援。

不適合：超低資源嵌入式（用 WAMR）、極致 cold start（Cranelift 啟動有開銷，但 pooling 可緩解）。

rust 
// 嵌入 Wasmtime 到 Rust 應用
use wasmtime::*;

fn main() -> Result<()> {
    let engine = Engine::default();
    let module = Module::from_file(&engine, "module.wasm")?;
    let mut store = Store::new(&engine, ());

    // 提供 host function
    let func = Func::wrap(&mut store, |x: i32| x * 2);
    let instance = Instance::new(&mut store, &module, &[func.into()])?;

    let run = instance.get_typed_func::<i32, i32>(&mut store, "compute")?;
    let result = run.call(&mut store, 42)?;
    println!("Result: {}", result);
    Ok(())
}

wazero — Go 生態首選

背景：Tetratelabs 開源（2022），純 Go 寫、零 CGO。

核心特性：

  • 純 Go 實作，編譯出純 Go binary、無 C 依賴、跨平台容易
  • WASI 0.1 支援完整、0.2 進行中
  • 對 Go 宿主整合最自然（context、goroutine 友善）
  • 啟動快、適合 per-request instance 模型
  • 效能略低於 Wasmtime（沒有 Cranelift 級的優化），但對多數應用足夠

適合場景：Go 寫的應用要嵌入 Wasm、需要跨平台單一 binary 部署、CI/CD 嚴禁 CGO 的環境。

不適合：需要 Component Model 完整支援（仍進行中）、極致執行效能。

go 
// 嵌入 wazero 到 Go 應用
package main

import (
    "context"
    "os"
    "github.com/tetratelabs/wazero"
    "github.com/tetratelabs/wazero/imports/wasi_snapshot_preview1"
)

func main() {
    ctx := context.Background()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)

    wasi_snapshot_preview1.MustInstantiate(ctx, r)

    wasmBytes, _ := os.ReadFile("module.wasm")
    mod, _ := r.Instantiate(ctx, wasmBytes)

    fn := mod.ExportedFunction("compute")
    result, _ := fn.Call(ctx, 42)
    println("Result:", result[0])
}

WasmEdge — CNCF 邊緣 / AI 重點

背景：原 Second State 開源，2021 進入 CNCF 沙箱，2024 升 incubating。C++ 寫。

核心特性：

  • AI / ML 整合最強：內建 WASI-NN，支援 PyTorch、TensorFlow、llama.cpp、ggml
  • 支援 Tensorflow Lite、OpenVINO、PaddlePaddle 等推論引擎
  • 對邊緣 / IoT 場景有大量優化
  • JIT（LLVM-based）、AOT 編譯器
  • 豐富的 host extension：HTTP client、TCP socket、KV、image processing
  • 跨 containerd 整合：containerd-shim-wasmedge

適合場景：邊緣 AI 推論、LLM serving on edge、IoT 閘道處理感測資料、CDN 邊緣轉碼。

不適合：Component Model 主流場景（WasmEdge 不是 Component Model 首發實作者）。

Wasmer — 多後端、跨平台

背景：Wasmer Inc. 推出，Rust 寫，2019 起。

核心特性：

  • 三種後端可選：Cranelift（平衡）、LLVM（極致效能）、Singlepass（極致啟動）
  • 多語言嵌入綁定（C、Python、Go、JS、PHP、Ruby、Java、C#）
  • WAPM 套件管理（已被 wkg 部分取代）
  • WASIX：自家擴充 WASI，支援 fork、threads、POSIX-style socket
  • Wasmer Edge：商業託管平台

適合場景：需要 POSIX 相容性（移植大型 C 程式）、跨多種主機語言嵌入。

不適合：強烈關心標準合規與跨 runtime 可攜（WASIX 不是標準）。

WAMR — 極輕量嵌入式

背景：WebAssembly Micro Runtime，Bytecode Alliance 旗下，C 寫。

核心特性：

  • 記憶體佔用可低至 85 KB，適合 RTOS、microcontroller
  • 三種執行模式：interpreter、AOT、JIT（fast / classic）
  • 支援多種 OS：Linux、Zephyr、FreeRTOS、SGX、Nuttx、AliOS、ESP-IDF
  • WASI 0.1 完整、0.2 部分
  • Intel、Sony、Bosch、Continental 等汽車與工業客戶採用

適合場景：IoT、車載、smart NIC、工業 PLC、邊緣裝置上的 Wasm。

wasm3 與 wasmi — 純 interpreter

  • wasm3（C）：< 64KB binary 的 pure interpreter，極小但執行慢（解譯）。MIT 授權。
  • wasmi（Rust）：Parity 為 Polkadot 開發的純 Rust interpreter，適合嵌入 no_std Rust。

適合場景：超低資源環境、安全敏感（pure interpreter 攻擊面小）、區塊鏈 deterministic 執行。

6.3應用框架層

有了核心 runtime，還需要把它包裝成「能跑業務」的應用框架。三個重要的開源框架：

Spin（Fermyon）

定位：Wasm 版的「Vercel + Cloud Functions」——HTTP / Redis / cron 事件驅動 serverless，內含 Wasmtime。

核心特性：

  • 聲明式 spin.toml 描述 trigger + components
  • 內建 HTTP routing、KV store、SQLite、AI inferencing
  • 多語言 SDK：Rust、TypeScript、Go、Python、C#
  • 本地 spin up 開發，spin deploy 上雲
  • 2025 加入 WASIp3 RC 支援
toml 
spin_manifest_version = 2

[application]
name = "my-api"
version = "1.0.0"

[[trigger.http]]
route = "/api/users/..."
component = "users"

[[trigger.http]]
route = "/api/orders/..."
component = "orders"

[component.users]
source = "components/users.wasm"
allowed_outbound_hosts = ["https://auth.example.com"]
key_value_stores = ["default"]

[component.orders]
source = "components/orders.wasm"
sqlite_databases = ["orders-db"]

wasmCloud

定位：CNCF incubating，分散式 actor model，跨雲跨邊緣的 Wasm 平台。

核心特性：

  • Actor model：每個 Wasm component 是無狀態 actor
  • Capability provider：actors 透過抽象 capability 取得 HTTP、KV、messaging 等能力
  • NATS 作為 control plane，hosts 自動加入 lattice
  • 跨 region 分散排程，actors 可在多 host 間自動 failover
  • 2025 加入 WASIp3 RC

Extism

定位：「Wasm 多語言外掛系統 SDK」。不是 serverless framework，而是讓你的應用支援第三方 Wasm 外掛。

核心特性：

  • 底層用 Wasmtime 或 wazero
  • 提供 Go、Python、Node.js、PHP、Ruby、Rust、Zig、Elixir、.NET、C 等宿主端 SDK
  • plug-in 端可用 Rust、Go、JS、AssemblyScript 等寫
  • 適合「我的 SaaS 想讓客戶寫客製邏輯」場景

SpinKube — K8s 整合層

CNCF Sandbox 專案，把 Spin 應用以 K8s CRD 形式管理。底層用 containerd-shim-spin 讓 K8s 直接執行 .wasm。

yaml 
apiVersion: core.spinkube.dev/v1alpha1
kind: SpinApp
metadata:
  name: my-api
spec:
  image: "ghcr.io/me/my-api:1.0"
  replicas: 5
  executor:
    name: containerd-shim-spin

6.4K8s 與容器生態整合

K8s 整合是 2024-2026 期間最快成熟的領域。事實標準已經形成：

containerd-wasm-shims

Microsoft + Fermyon + Docker 共同維護的 containerd shim，讓 K8s 用 runtimeClassName 切換到 Wasm runtime：

yaml 
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: wasmtime-spin-v2
handler: spin
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-wasm-app
spec:
  template:
    spec:
      runtimeClassName: wasmtime-spin-v2  # 用 Wasm shim
      containers:
      - name: app
        image: ghcr.io/me/app:1.0  # 內含 .wasm
        ports: [containerPort: 8080]

支援的 shim

  • containerd-shim-spin：Spin 應用
  • containerd-shim-wasmedge：WasmEdge runtime
  • containerd-shim-wasmtime：原生 Wasmtime
  • containerd-shim-wws：wasm-workers-server
  • containerd-shim-lunatic：Lunatic runtime

OCI image 整合

OCI image spec 已正式支援 Wasm 作為 first-class artifact，可以同時存放容器與 Wasm：

bash 
# 用 docker buildx 建 Wasm image
docker buildx build --platform wasi/wasm \
    -t ghcr.io/me/my-app:1.0 .
docker push ghcr.io/me/my-app:1.0

# 用 wkg 推 component 到 OCI registry
wkg oci push ghcr.io/me/my-component:1.0 component.wasm

Krustlet（已 archive）

歷史記錄：Krustlet 是 2020 年 Microsoft 推出的「把 Wasm 當 K8s first-class workload」的 kubelet 替代品。已被 containerd-wasm-shims 取代，2024 年 archive。新專案不要採用 Krustlet。

6.5SaaS 平台 vs 自架

除了開源 runtime，還有商業 SaaS Wasm 平台。它們的底層多半也是開源 runtime，但提供管理層附加價值。

SaaS 與自架的權衡

面向SaaS自架
上線速度分鐘到小時週到月
全球 PoP 覆蓋內建要自己部署多區
運維負擔幾乎為零K8s、observability、scaling 全自己

Lock-in有（API、SDK 差異）無（用標準 WASI 0.2）

選擇建議

新創 / 快速驗證：用 SaaS，把資源放在產品而非基礎建設。Fermyon Cloud、Fastly 是好選擇。

有 K8s 基礎建設、想統一管理：自架 SpinKube + Wasmtime。融入既有 CI/CD、observability、IAM。

邊緣場景但不想自架全球節點：Cloudflare Workers、Fastly Compute。

合規敏感 / 資料主權：自架。

已採用 wasmCloud actor 模型：Cosmonic 託管 vs 自架 NATS lattice，看團隊運維能量。

LAB動手實作：Wasmtime vs wazero 對照

Lab 6.A · 嵌入式對照

用同一個 .wasm 模組，分別嵌入 Rust + Wasmtime 與 Go + wazero 宿主

步驟 1 · 寫 Wasm 模組（Rust）
bash 
cargo new --lib compute-wasm
cd compute-wasm
echo '[lib]
crate-type = ["cdylib"]' >> Cargo.toml

cat > src/lib.rs << 'EOF'
#[no_mangle]
pub extern "C" fn process(n: i32) -> i32 {
    let mut sum = 0;
    for i in 1..=n {
        sum += i * i;
    }
    sum
}
EOF

cargo build --release --target wasm32-unknown-unknown
cp target/wasm32-unknown-unknown/release/compute_wasm.wasm ../module.wasm
cd ..
步驟 2 · Rust + Wasmtime 宿主
bash 
cargo new wt-host
cd wt-host
echo 'wasmtime = "26"
anyhow = "1"' >> Cargo.toml

cat > src/main.rs << 'EOF'
use std::time::Instant;
use wasmtime::*;

fn main() -> anyhow::Result<()> {
    let engine = Engine::default();
    let module = Module::from_file(&engine, "../module.wasm")?;
    let mut store = Store::new(&engine, ());
    let instance = Instance::new(&mut store, &module, &[])?;
    let process = instance.get_typed_func::<i32, i32>(&mut store, "process")?;

    let t0 = Instant::now();
    for _ in 0..10000 {
        let _ = process.call(&mut store, 1000)?;
    }
    println!("Wasmtime 10000 calls in {:?}", t0.elapsed());
    Ok(())
}
EOF

cargo run --release
cd ..
步驟 3 · Go + wazero 宿主
bash 
mkdir wz-host && cd wz-host
go mod init wz-host
go get github.com/tetratelabs/wazero

cat > main.go << 'EOF'
package main

import (
    "context"
    "fmt"
    "os"
    "time"
    "github.com/tetratelabs/wazero"
)

func main() {
    ctx := context.Background()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)

    wasmBytes, _ := os.ReadFile("../module.wasm")
    mod, err := r.Instantiate(ctx, wasmBytes)
    if err != nil {
        panic(err)
    }
    process := mod.ExportedFunction("process")

    t0 := time.Now()
    for i := 0; i < 10000; i++ {
        process.Call(ctx, 1000)
    }
    fmt.Printf("wazero 10000 calls in %v\n", time.Since(t0))
}
EOF

go run main.go
cd ..
步驟 4 · 觀察結果

典型結果（會因硬體與版本不同）：

  • Wasmtime：10000 calls ~30-80ms（含 JIT 編譯首次）
  • wazero：10000 calls ~150-300ms（純 Go interpreter compiler，稍慢）

Wasmtime 比 wazero 快 2-5 倍是常見現象，因為 Wasmtime 用 Cranelift 編譯到原生碼，wazero 是純 Go 的較簡單 compiler。但 wazero 的優勢是零 CGO 部署。

挑戰
  1. 把模組改成更複雜（例如 1000x1000 矩陣相乘），重新比較。
  2. 用 Wasmtime 啟用 pooling allocator（PoolingAllocationConfig），看 per-call 延遲是否改善。
  3. 用 wasmtime compile 預先 AOT 編譯，再用 Module::deserialize_file 載入，比較與 JIT 的差異。

Q2.哪個 runtime「最適合 Go 寫的宿主應用整合」？

  • wazero（純 Go、零 CGO）
  • WasmEdge（C++）

答案 · B wazero 純 Go、零 CGO，跟 Go 生態無縫整合。其他 runtime 要 CGO 或外部 process 互動，部署複雜度高。
Q3.WasmEdge 的特長是？
  • 最完整的 Component Model 支援
  • 最小的 binary size
  • 邊緣 AI / ML 推論（WASI-NN、LLM 支援）
  • 純 Rust 實作
看解答
答案 · C WasmEdge 是 CNCF 沙箱專案，最知名的特長是邊緣 AI——內建 WASI-NN、支援 PyTorch、TensorFlow、llama.cpp。A 是 Wasmtime 的優勢；B 是 WAMR；D 錯，WasmEdge 是 C++ 寫。
Q4.WAMR 適合什麼場景？
  • 大型 microservice
  • IoT、車載、microcontroller 等資源受限場景
  • 瀏覽器內
  • CI/CD 工具
看解答
答案 · B WAMR 記憶體佔用可低至 85 KB，是嵌入式場景首選。支援多種 RTOS、microcontroller，Bosch、Continental 等汽車供應商採用。
Q5.Wasmer 的 WASIX 與標準 WASI 0.2 的關係是？
  • 兩者等價
  • WASIX 是 Wasmer 自家擴充，提供 POSIX fork/threads/signals 但綁定 Wasmer
  • WASIX 是 WASI 0.2 的官方別名
  • WASIX 比 WASI 0.2 更標準
看解答
答案 · B WASIX 是 Wasmer 在 WASI 進度緩慢時推出的擴充版 Preview 1，加入 POSIX-like 系統呼叫。代價是綁定 Wasmer。WASI 0.2 才是 Bytecode Alliance 推的標準。
Q6.下列何者是現代 K8s 跑 Wasm 的事實標準？
  • Krustlet（取代 kubelet）
  • containerd-wasm-shims + RuntimeClass
  • 手動把 Wasm 包進容器
  • 用 Docker run wasm 直接執行
看解答
答案 · B 2024-2026 事實標準是 containerd-wasm-shims（Microsoft + Fermyon + Docker），透過 K8s 的 RuntimeClass 機制切換。Krustlet 已 archive，不建議採用。
Q7.選 Spin / wasmCloud / Extism，下列何者描述正確？
  • Spin 適合 HTTP serverless，wasmCloud 適合分散式 actor，Extism 適合應用內外掛
  • 三者完全等價，可互換
  • 只有 Spin 是開源
  • 三者都不能跨雲
看解答
答案 · A 三者定位不同：Spin = serverless framework；wasmCloud = 跨雲 actor 平台；Extism = 多語言外掛 SDK。
Q8.SaaS Wasm 平台 vs 自架，哪個說法正確？
  • SaaS 永遠便宜
  • 自架永遠靈活
  • SaaS 上線快、無運維負擔，但有 lock-in 與成本可預期性問題；自架反之
  • 兩者沒差
看解答
答案 · C SaaS（Fastly、Cloudflare、Fermyon）上線快但有平台 API 鎖定、運維外包代價是成本不可預期。自架（SpinKube、wasmCloud）成本可控但要自己經營基礎建設。
Q9.下列關於 runtime 效能，何者敘述較貼近現實？
  • 純 Go 寫的 wazero 比 Rust 寫的 Wasmtime 效能高
  • Wasmtime 用 Cranelift 編譯到原生碼，執行效能通常比 wazero 高，但 wazero 部署更簡單
  • 所有 runtime 效能完全一樣
  • 純 interpreter（wasm3）執行最快
看解答
答案 · B Wasmtime + Cranelift 是業界效能標竿；wazero 是純 Go compiler（無 LLVM），執行較慢但宿主整合最自然。pure interpreter（wasm3）執行最慢（D 錯）。
Q10.2026 年生產級 Wasm 服務，最穩健的「自架」runtime 組合是？
  • Krustlet + 自寫 K8s operator
  • Spin + SpinKube + Wasmtime（含 containerd-shim-spin）
  • 直接用 wasm3 跑 .wasm
  • WASIX + Wasmer
看解答
答案 · B Spin + SpinKube + containerd-shim-spin 是 2026 自架 Wasm K8s 的事實標準組合：標準、開源、生產驗證。A Krustlet 已 archived；C wasm3 是 interpreter 效能不夠；D 綁定 Wasmer 生態。
