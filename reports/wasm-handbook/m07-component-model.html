Component Model
與跨語言組合

Wasm 從「沙箱化的 binary」走向「可組合的元件」的關鍵基礎建設。理解 Component Model，你才能看清 Wasm 為什麼是「Docker moment」而不只是「JS 加速器」。

Advanced Level ~4 hours WIT + wac 2026 Component Model 1.0

本章學習目標

  • 區分 core module 與 component 的差異與動機。
  • 讀寫 WIT 介面定義，理解 record、variant、resource、future、stream 等型別。
  • 用 cargo-component 寫 Rust component；用 TinyGo 寫 Go component；用 jco 寫 JS component。
  • 用 wac compose / wac plug 把不同語言寫的 component 組合起來。
  • 把 component 推到 OCI registry（用 wkg），並從 registry 拉取依賴。
  • 了解 Component Model 1.0（2026 達成）對生產採用的意義。

7.1為什麼需要 Component Model

core Wasm 模組的型別系統極簡——只能在 module 邊界傳遞 i32、i64、f32、f64 與線性記憶體位址。要從一個 Rust 模組傳字串給一個 JS 模組，雙方必須手動約定記憶體布局，然後寫 glue code 把字串序列化、反序列化。每對語言都要重新寫一遍。

Core module 的限制

rust 
// Rust 寫的 core module 想傳字串給宿主
#[no_mangle]
pub extern "C" fn greet(name_ptr: *const u8, name_len: u32) -> u32 {
    // 1. 從 (ptr, len) 還原 &str
    let name = unsafe {
        std::str::from_utf8_unchecked(
            std::slice::from_raw_parts(name_ptr, name_len as usize)
        )
    };

    // 2. 計算回應字串
    let response = format!("Hello, {}!", name);

    // 3. 把回應寫到記憶體
    let bytes = response.into_bytes();
    let ptr = bytes.as_ptr();
    std::mem::forget(bytes);  // 防止 drop
    ptr as u32

    // 但宿主怎麼知道回傳字串多長？要再開一個 export 函式查長度？
    // 還是用 (ptr, len) 兩個值回傳？core module 一次只能回一個！
}

看出問題了嗎？字串傳遞要靠 (ptr, len) idiom，每個語言都要實作一套，記憶體所有權、生命週期、編碼（UTF-8 vs UTF-16）都靠約定。沒有型別系統的保證，靠紀律維護 ABI 一致性。

Component Model 的解答

Component Model 引入 WIT + Canonical ABI，把字串、list、record、variant 變成 first-class 的「介面型別」。同樣的 greet 函式變這樣：

wit 
// greeter.wit
package example:greeter@0.1.0;

interface greeter {
    greet: func(name: string) -> string;
}

world api {
    export greeter;
}
rust 
// Rust 實作 - cargo-component 自動生成的 trait
use bindings::exports::example::greeter::greeter::Guest;

struct Component;

impl Guest for Component {
    fn greet(name: String) -> String {
        format!("Hello, {}!", name)
    }
}

bindings::export!(Component with_types_in bindings);

沒有 ptr、len、unsafe、memory leak——介面型別之間自動轉換、生命週期自動管理。而且這個 component 可以在任何支援 Component Model 的 runtime 跑，無論宿主用什麼語言。

Component Model 帶來的改變

  • 跨語言組合：Rust component 可以匯入 Python component 的功能，或反之。
  • typed interface：介面用 WIT 定義，編譯時就能檢查型別吻合。
  • 記憶體隔離：每個 component 有自己的 linear memory，互相不可見。
  • capability-based composition：component 的 import 是 capability，組合時宿主決定提供什麼。
  • 跨 runtime 可攜：同一個 component 可在 Wasmtime、wasmCloud、Spin、Fastly 跑。
  • component 是部署單位：類似 OCI image，但更輕、有強型別介面。
Component Model 1.0 達成（2026） 截至 2026 年 5 月，Component Model 已達到 1.0 里程碑。WIT、Canonical ABI、wac、wkg 等工具進入穩定狀態，主要 runtime（Wasmtime、wasmCloud、Spin）已可生產採用。這是 Wasm「Docker moment」的核心拼圖。

7.2Module vs Component：兩層抽象

釐清這兩個術語的差異是讀 Wasm 文件的關鍵能力。

面向Core Module（傳統 Wasm）Component（Component Model）
邊界型別i32, i64, f32, f64, v128string, list, record, variant, resource, future, stream
記憶體單一 linear memory（可被宿主直接讀寫）每個 component 有自己的 memory，外部不可見
介面描述無正式定義，靠紀律WIT 介面語言
ABI無標準（每對語言自定義）Canonical ABI（標準）
組合不支援（要靠宿主 wiring）原生支援（wac compose）
典型用途嵌入式、自寫宿主、瀏覽器 JS 整合Serverless、microservice、外掛系統

Component 是 module 的超集

從 binary 層面看，component 包裹了一個或多個 core module，加上 WIT 介面描述與 Canonical ABI 轉換邏輯。你用 wasm-tools component wit my-component.wasm 可以看出 component 的介面：

bash 
$ wasm-tools component wit my-component.wasm
package root:component;

world root {
  import wasi:io/error@0.2.0;
  import wasi:io/streams@0.2.0;
  import wasi:cli/stdout@0.2.0;

  export greet: func(name: string) -> string;
}

判斷一個 .wasm 是 module 還是 component

bash 
# wasm-tools 可以辨識
$ wasm-tools print file.wasm | head -1

# 如果第一行是 (module ...)，是 core module
# 如果第一行是 (component ...)，是 component

7.3WIT 介面定義語言深入

第 4 章已介紹過 WIT 的基本概念。本章深入更進階的特性。

Package、interface、world 的階層

wit 
// 完整 WIT 結構
package myorg:my-package@1.0.0;

// interface 定義一組相關的函式與型別
interface types {
    record user {
        id: u64,
        name: string,
        email: string,
    }

    variant error {
        not-found,
        unauthorized,
        internal-error(string),
    }
}

interface user-service {
    use types.{user, error};

    get-user: func(id: u64) -> result<user, error>;
    list-users: func() -> list<user>;
}

// world 描述 component 的「形狀」
world user-app {
    import wasi:keyvalue/store@0.2.0;
    export user-service;
}

Record：結構化資料

wit 
record address {
    street: string,
    city: string,
    country: string,
    postal-code: option<string>,
}

record person {
    name: string,
    age: u32,
    addresses: list<address>,
}

Variant：tagged union

類似 Rust 的 enum 帶資料，可表達「多種可能的值」：

wit 
variant shape {
    circle(f64),                    // radius
    rectangle(tuple<f64, f64>),     // width, height
    triangle(record { a: f64, b: f64, c: f64 }),
}

variant error-code {
    not-found,                       // 不帶值
    unauthorized,
    bad-request(string),             // 帶錯誤訊息
    internal-error(record {
        code: u32,
        message: string,
    }),
}

Resource：不可拷貝的能力 handle

Resource 是 capability-based 安全的 first-class 表達——對應到第 3 章的 handle 模式，但由型別系統強制。

wit 
interface filesystem {
    // resource 宣告 - 一個不可拷貝的能力物件
    resource file {
        // constructor 由 host 提供
        constructor(path: string);

        // method 是 resource 的操作
        read: func(offset: u64, length: u64) -> result<list<u8>, error>;
        write: func(offset: u64, data: list<u8>) -> result<u64, error>;
        size: func() -> u64;

        // 也可以是 static method（不需要 self）
        max-file-size: static func() -> u64;
    }
}

使用方（Rust）：

rust 
use bindings::myorg::filesystem::filesystem::File;

let f = File::new("/data/log.txt");
let data = f.read(0, 1024)?;
let written = f.write(0, vec![1, 2, 3])?;
let total = f.size();
// f 離開 scope 時自動 drop，呼叫 host 釋放

resource 的關鍵特性：

  • 不可拷貝：只能 borrow 或 move，避免兩處持有同一 handle
  • 不可序列化：handle 無法跨 instance 邊界傳遞
  • 自動清理：離開 scope 觸發 host 的 destructor
  • 跨語言一致：Rust、Go、Python、JS 對 resource 都有對應的語言 idiom

Future / Stream（WASI 0.3 起）

2026 年 WASI 0.3 引入 async 型別：

wit 
interface async-api {
    // future<T> - 單一非同步結果
    fetch-data: func(url: string) -> future<result<list<u8>, error>>;

    // stream<T> - 非同步序列
    tail-log: func(file: string) -> stream<string>;
}

Rust 對應：

rust 
// future<T> 變成 impl Future<Output = T>
async fn fetch_data(url: String) -> Result<Vec<u8>, Error>;

// stream<T> 變成 impl Stream<Item = T>
fn tail_log(file: String) -> impl Stream<Item = String>;

Use 與 include

WIT 支援匯入其他 interface 與 world：

wit 
package myorg:lib@1.0.0;

interface types {
    record point { x: f64, y: f64 }
}

interface geometry {
    use types.{point};    // 匯入 point 型別

    distance: func(a: point, b: point) -> f64;
}

// 一個 world 可以 include 另一個 world
world full-api {
    include wasi:cli/imports@0.2.0;    // 取得 cli 的所有 imports
    export geometry;
}

7.4Canonical ABI：型別轉換的底層機制

WIT 是上層介面語言，Canonical ABI 是它對應到 Wasm 底層的標準。理解 ABI 不是必須，但能解釋為什麼有些 WIT 型別比較貴、為什麼跨 component 呼叫有開銷。

Lift 與 Lower

Canonical ABI 定義兩個方向的轉換：

  • Lower：把 WIT 高階型別「降」到 core Wasm 的 i32/i64/f32/f64。把 string 變成 (ptr, len)、把 record 變成連續 bytes、把 list 變成 (ptr, len) + 元素 lower。
  • Lift：反向——從 core Wasm 的原語「升」成 WIT 高階型別。
sequenceDiagram
    participant A as Component A
Rust
    participant CA1 as Canonical ABI
Lower
    participant CORE as Core Wasm
i32, memory bytes
    participant CA2 as Canonical ABI
Lift
    participant B as Component B
Python

    A->>CA1: call f("hello")
    CA1->>CORE: f(ptr=0x100, len=5) + bytes in memory
    CORE->>CA2: cross boundary
    CA2->>B: f(name: str = "hello")

    B->>CA2: return "Hi!"
    CA2->>CORE: ptr=0x200, len=3
    CORE->>CA1: cross boundary
    CA1->>A: result = "Hi!"
Figure 7.1 · Canonical ABI 的 lift / lower 過程

跨 component 邊界的成本

Canonical ABI 的轉換有成本——複雜型別（巨大 record、深層 list）lift/lower 較貴。實務上：

  • i32/i64 跨邊界幾乎免費（直接傳）
  • string 中等成本（要拷貝 bytes 到接收方記憶體）
  • list of records 較貴（要逐個 lower / lift）
  • resource handle 便宜（只是 i32 + table lookup）

對效能敏感的 hot path 設計時，把資料聚合成大物件一次傳，比多次呼叫傳小資料便宜。

7.5用 wac 組合 Component

有了多個 component，怎麼組起來變一個完整應用？答案是 wac（WebAssembly Compositions）。

wac plug：快速組合

最簡單的場景：A component 匯入 B 的功能，把 B 的 export 接到 A 的 import：

bash 
cargo install wac-cli

# 把 dep.wasm 的 export 接到 main.wasm 的 import
wac plug main.wasm --plug dep.wasm -o composed.wasm

# 多個依賴
wac plug main.wasm \
    --plug auth.wasm \
    --plug logger.wasm \
    -o composed.wasm

結果 composed.wasm 是新的 component：

  • 匯出 main 的 export
  • 不再匯出 deps 的 export（它們被「藏進去」）
  • 仍匯入 deps 自己未被滿足的 import

wac compose：用 .wac 檔聲明複雜組合

對更複雜的依賴圖，用 WAC language（WIT 的超集）聲明：

wit 
// compose.wac
package myapp:composition;

// 實例化 logger component
let logger = new infra:logger { };

// 實例化 auth component，連到 logger
let auth = new infra:auth {
    // 把 auth 對 logger 的 import 接到 logger.log
    log: logger.log,
};

// 實例化 main app
let app = new myapp:main {
    // 連接 auth 與 logger
    "infra:auth/validator": auth.validator,
    "infra:logger/log": logger.log,
};

// 最終匯出 app 的 HTTP handler
export app.handle;
bash 
wac compose \
    --dep infra:logger=./logger.wasm \
    --dep infra:auth=./auth.wasm \
    --dep myapp:main=./main.wasm \
    -o final.wasm \
    compose.wac

composed 的 final.wasm 對宿主來說就是一個普通 component，內部三個語言寫的 component 互相 wire 已經完成。

運行時 linking vs 建置時 composition

除了用 wac compose 在建置時組合，也可以在 runtime 動態 linking：

方式時機特性
Build-time（wac compose）編譯 / 部署前單一 binary、可預先優化、無 runtime overhead
Runtime linking執行時動態替換、A/B 測試、更彈性

wasmCloud 是 runtime linking 的代表，actors（components）動態連到 capability providers。Spin 主要是 build-time composition。

7.6跨語言 Component 實作

本節示範同一個 WIT 介面用三種語言（Rust、TinyGo、JS）各寫一個 component，再用 wac 組合。

共同 WIT 介面

wit 
// shared/wit/world.wit
package example:multilang@0.1.0;

interface number-ops {
    record stats {
        count: u32,
        sum: u64,
        mean: f64,
    }

    calculate-stats: func(numbers: list<u64>) -> stats;
}

world stats-component {
    export number-ops;
}

實作 1：Rust + cargo-component

bash 
cargo component new --lib stats-rust
cp shared/wit/world.wit stats-rust/wit/
rust 
// stats-rust/src/lib.rs
#[allow(warnings)]
mod bindings;

use bindings::exports::example::multilang::number_ops::{Guest, Stats};

struct Component;

impl Guest for Component {
    fn calculate_stats(numbers: Vec<u64>) -> Stats {
        let count = numbers.len() as u32;
        let sum: u64 = numbers.iter().sum();
        let mean = if count > 0 {
            sum as f64 / count as f64
        } else { 0.0 };

        Stats { count, sum, mean }
    }
}

bindings::export!(Component with_types_in bindings);
bash 
cargo component build --release
# 產出 target/wasm32-wasip2/release/stats_rust.wasm

實作 2：Go + TinyGo

bash 
mkdir stats-go && cd stats-go
go mod init stats-go
go install go.bytecodealliance.org/cmd/wit-bindgen-go@latest

# 解析 WIT 依賴
wkg wit build --wit-dir ../shared/wit -o example:multilang.wasm

# 生成 Go 綁定
go tool wit-bindgen-go generate \
    --world stats-component \
    --out internal \
    ./example:multilang.wasm
go 
// stats-go/main.go
package main

import (
    "stats-go/internal/example/multilang/number-ops"
)

func init() {
    number_ops.Exports.CalculateStats = func(
        numbers cm.List[uint64],
    ) number_ops.Stats {
        slice := numbers.Slice()
        count := uint32(len(slice))

        var sum uint64
        for _, n := range slice {
            sum += n
        }

        var mean float64
        if count > 0 {
            mean = float64(sum) / float64(count)
        }

        return number_ops.Stats{
            Count: count,
            Sum:   sum,
            Mean:  mean,
        }
    }
}

func main() {}
bash 
tinygo build -target=wasip2 \
    --wit-package ./example:multilang.wasm \
    --wit-world stats-component \
    -o stats_go.wasm main.go

實作 3：JavaScript + jco

bash 
mkdir stats-js && cd stats-js
npm init -y
npm install --save-dev @bytecodealliance/jco @bytecodealliance/componentize-js
javascript 
// stats-js/source.js
export const numberOps = {
    calculateStats(numbers) {
        const count = numbers.length;
        const sum = numbers.reduce((a, b) => a + b, 0n);
        const mean = count > 0 ? Number(sum) / count : 0;

        return { count, sum, mean };
    }
};
bash 
npx jco componentize source.js \
    --wit ../shared/wit/world.wit \
    --world-name stats-component \
    --out stats_js.wasm

三個 component 跑出同樣結果

bash 
# 都可以用 wasmtime 呼叫
for comp in stats_rust.wasm stats_go.wasm stats_js.wasm; do
    echo "=== $comp ==="
    wasmtime --invoke 'calculate-stats' "$comp" '[1,2,3,4,5]'
done

# 結果都是 { count: 5, sum: 15, mean: 3.0 }

三種語言、三種開發體驗、同一個介面——這就是 Component Model 的承諾。

7.7Component Registry：wkg 與 OCI

有了 component，要怎麼分發？傳統 OCI image 太重、npm 不適合 Wasm、Docker Hub 不支援 component metadata。wkg（wasm-pkg-tools）解決這個問題。

wkg 的角色

wkg 是 Bytecode Alliance 開發的 component 套件管理工具，類似「npm / cargo 之於 component」：

  • 把 component / WIT 推到 OCI registry（GHCR、Docker Hub、ECR、ACR 等）
  • 從 registry 拉取 WIT 依賴自動解析
  • 支援版本管理
  • 整合 cargo-component、wac、tinygo 工具鏈
bash 
cargo install wkg

# 配置 default registry
mkdir -p ~/.config/wasm-pkg/
cat > ~/.config/wasm-pkg/config.toml << 'EOF'
default_registry = "ghcr.io"
EOF

# 把 component 推到 registry
wkg oci push ghcr.io/myorg/stats:0.1.0 stats_rust.wasm

# 拉取 component
wkg oci pull ghcr.io/myorg/stats:0.1.0 -o stats.wasm

# 推 WIT package（讓別人可以依賴你的介面）
wkg publish wit/world.wit

從 registry 解析 WIT 依賴

WIT 可以 import 別的 package，wkg 會自動從 registry 解析：

wit 
// 你的 world.wit 想用 wasi:http
package myorg:my-app@0.1.0;

world my-server {
    import wasi:http/types@0.2.0;
    export wasi:http/incoming-handler@0.2.0;
}
bash 
# wkg 自動從 registry 拉 wasi:http
wkg wit build --wit-dir wit -o my-app.wasm
# 生成的 my-app.wasm 包含所有 WIT 依賴

Component Hub 與生態

2026 年 component registry 生態逐漸成熟：

  • Component Hub：bytecode alliance 維護的公開 component 集
  • Fermyon registry：Spin 應用與 component
  • wasmCloud Hub：actor 與 capability provider
  • GHCR / Docker Hub：通用 OCI registry，支援 Wasm artifact
Component 比 OCI image 輕得多 典型 Wasm component 100KB – 5MB，比同等功能的 OCI image 小 10–100 倍。registry 儲存與傳輸成本大幅降低，這也是 Wasm「Docker moment」的物理基礎。

7.82026 年生產採用考量

Component Model 1.0 達成，但實際採用仍要考量現實限制。

已成熟可生產採用的部分

  • WIT 介面定義語言（穩定）
  • Canonical ABI（穩定）
  • Rust component 開發（cargo-component 成熟）
  • TinyGo component 支援（0.34+）
  • JS component（jco 成熟）
  • wac compose 工具（CLI 穩定）
  • OCI registry 整合（wkg 可用）
  • Wasmtime runtime 支援（完整）
  • Spin、wasmCloud 平台整合（生產級）

仍有挑戰的部分

  • 瀏覽器尚未支援 Component Model：仍是 W3C proposal stage 2/3，瀏覽器內仍要靠 jco transpile 成 JS+core Wasm
  • Python component（componentize-py）：可用但較新
  • Java / Kotlin component：仍在發展
  • 跨 runtime 完全可攜性：理論上可，實務上仍有 quirks（特別在 resource 處理）
  • Debug 工具鏈：跨 component debug 仍困難
  • Component 大小優化：相比 core module 增加 metadata overhead

採用建議

2026 年新建 server-side Wasm 服務：直接用 Component Model，不要回去寫 core module（除非有特殊性能 / 體積需求）。

已有 Wasm 應用：評估遷移 cost——core module 仍可用，但新功能用 component 開發更便利。

瀏覽器內：可以用 jco 把 component 轉成 ES module，但體積會增加。多數情況直接寫 core module + wasm-bindgen 仍更合適。

第三方外掛系統：強烈推薦 component。WIT 介面提供強型別契約，多語言外掛無痛整合。

步驟 1 · 定義介面
wit 
// wit/calculator.wit
package example:calculator@0.1.0;

interface adder {
    add: func(a: u32, b: u32) -> u32;
}

interface multiplier {
    multiply: func(a: u32, b: u32) -> u32;
}

world add-comp {
    export adder;
}

world mul-comp {
    export multiplier;
}

world main {
    import adder;
    import multiplier;
    export wasi:cli/run@0.2.0;
    include wasi:cli/imports@0.2.0;
}
步驟 2 · Rust 加法 component
bash 
cargo component new --lib add-component
# 把 wit/calculator.wit 複製進去，編輯 Cargo.toml 指定 world = "add-comp"

# src/lib.rs
cat > add-component/src/lib.rs << 'EOF'
mod bindings;
use bindings::exports::example::calculator::adder::Guest;

struct Component;
impl Guest for Component {
    fn add(a: u32, b: u32) -> u32 { a + b }
}
bindings::export!(Component with_types_in bindings);
EOF

cd add-component && cargo component build --release
步驟 3 · TinyGo 乘法 component
bash 
mkdir multiply-component && cd multiply-component
# 用 wkg + wit-bindgen-go 生成 binding
# main.go 實作 multiply
# tinygo build -target=wasip2 ...
步驟 4 · Rust CLI main component

從 stdin 讀「a b op」（op 為 add 或 mul），呼叫對應 component 計算後輸出結果。

步驟 5 · 組合三個 component
bash 
wac plug main.wasm \
    --plug add.wasm \
    --plug multiply.wasm \
    -o calculator.wasm

# 執行
echo "3 4 add" | wasmtime calculator.wasm
# 7

echo "5 6 mul" | wasmtime calculator.wasm
# 30
挑戰
  1. 把 add 與 multiply 分別推到 ghcr.io，main 用 wkg 從 registry 拉取依賴。
  2. 加入第四個 component（用 JS 寫除法 division），整合進 CLI。
  3. 把整個 composed component 部署到 Spin，提供 HTTP API。

Module 07 · 10 題自我測驗

Q1.下列關於 core module vs component，何者正確？
  • 兩者完全等價
  • core module 只能傳 i32/i64/f32/f64；component 支援 string、record、resource 等高階型別
  • component 比 core module 慢
  • core module 不能在 Wasmtime 跑
看解答
答案 · B 差異核心在型別系統豐富度。Component 包裹 core module 並加上 WIT 介面 + Canonical ABI。執行效能近似（C 錯），core module 仍可在所有 runtime 跑（D 錯）。
Q2.WIT 中的 resource 型別有什麼特性？（複選）
  • 可拷貝
  • 不可拷貝（只能 borrow 或 move）
  • 不可序列化
  • 離開 scope 時自動 drop
  • 可跨 instance 邊界傳遞
看解答
答案 · B、C、D Resource 是 capability handle 的 first-class 表達，不可拷貝、不可序列化、有自動 drop。它無法跨 instance 邊界（E 錯），這是安全保證的根本。
Q3.Canonical ABI 的「lower」與「lift」是什麼？
  • lower 是壓縮、lift 是解壓縮
  • lower 是把 WIT 高階型別降為 core Wasm 原語；lift 是反向
  • 兩者是同義詞
  • lower 是 little-endian、lift 是 big-endian
看解答
答案 · B Lower / lift 是 Canonical ABI 的兩個方向轉換——lower 把 string、list、record 等降到 i32 + memory bytes；lift 反向。跨 component 邊界時兩端各做一次。
Q4.用 wac plug 組合兩個 component 後，產出的新 component 會？
  • 匯出 main + dep 的所有 export
  • 匯出 main 的 export，不匯出 dep 的（被藏進去）
  • 完全沒匯出
  • 同時匯入兩個 component 的 import
看解答
答案 · B wac plug 把 dep 的 export 接到 main 的 import。結果 component 對外暴露的是 main 的 export，dep 變成內部實作細節，被藏進新 component 內。
Q5.下列哪個工具最適合 Rust 寫 component？
  • wasm-pack
  • cargo-component
  • cargo build --target wasm32-unknown-unknown
  • emscripten
看解答
答案 · B cargo-component 專為 component 設計，自動處理 WIT 綁定生成。wasm-pack 是瀏覽器+JS 整合；普通 cargo build 只能編 core module；emscripten 是 C/C++。
Q6.wkg 工具的主要用途是？
  • 編譯 Wasm
  • 執行 Wasm
  • Wasm component 套件管理（推/拉 OCI registry、解析 WIT 依賴）
  • 優化 Wasm binary size
看解答
答案 · C wkg 是「component 套件管理」——類似 npm 之於 JS、cargo 之於 Rust，但目標是 component 與 WIT package。
Q7.下列哪個語言「目前生產可用」的 component 開發體驗最完整？
  • Rust（cargo-component + wit-bindgen）
  • Java
  • Kotlin
  • PHP
看解答
答案 · A Rust 是 Component Model 的「故鄉」——所有工具都先支援 Rust。Java 沒有官方 WASM target；Kotlin/Wasm 仍 Beta；PHP 仍是 interpreter 模式。
Q8.下列哪個是「Build-time composition」而非「Runtime linking」的特性？
  • 部署後可動態替換 component
  • 產出單一 binary，可預先優化
  • A/B 測試方便
  • component 間有 runtime overhead
看解答
答案 · B wac compose 在 build-time 把多 component 組成單一 binary，可預先做整體優化，無 runtime overhead。動態替換是 runtime linking 特性（wasmCloud 主推）。
Q9.2026 年瀏覽器對 Component Model 的支援是？
  • 已原生支援，可直接載入 component
  • 仍是 W3C proposal stage 2/3，瀏覽器尚未原生支援，需用 jco transpile
  • 永遠不會支援
  • 只有 Chrome 支援
看解答
答案 · B Component Model 在伺服器端（透過 Wasmtime、Spin、wasmCloud）已生產可用，但瀏覽器內仍要靠 jco 等工具把 component transpile 成 ES module + core Wasm。
Q10.2026 年新建一個跨多語言團隊的 microservice 系統，下列何者是最適合的策略？
  • 每個團隊各寫一個 Docker container，用 REST 通訊
  • 用 Component Model + WIT 介面，每個團隊用自己熟悉語言寫 component，用 wac 組合或 runtime linking
  • 統一所有團隊用 Rust
  • 避免使用 Wasm
看解答
答案 · B Component Model 就是為這種跨語言情境設計的——強型別 WIT 介面避免 REST 序列化開銷、組合靈活、部署單位輕、capability-based 安全。Container + REST 在 component 化後可大量取代。

SUMMARY章節總結

本章完成 Component Model 的全景理解，這是 Wasm 從「沙箱化 binary」演進為「可組合元件」的關鍵。你現在應該能：

  • 讀寫 WIT 介面，使用 record、variant、resource、future、stream 等型別。
  • 理解 Canonical ABI 的 lift / lower 機制，判斷跨 component 邊界的成本。
  • 用 wac plug / wac compose 組合多個 component。
  • 用 Rust、TinyGo、JS 各寫一個 component，並用 wac 組合。
  • 用 wkg 把 component 推到 OCI registry、解析 WIT 依賴。
  • 判斷 2026 年生產採用 Component Model 的成熟度與限制。
