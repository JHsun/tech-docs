9.1Wasm 可觀測性的獨特挑戰

傳統 process-based 應用的 observability 是成熟領域——OpenTelemetry SDK 嵌入應用、自動 instrument 框架、thread-local 維護 trace context。但 Wasm 的 host-guest 架構讓這套方法部分失效。

三大支柱在 Wasm 的處境

支柱傳統應用Wasm 應用
MetricsSDK 收集 + Prometheus scrape宿主收集為主、Wasm 內可選
Logsstdout / file / syslogstdout 透過 wasi:cli 或 wasi:logging
TracesSDK + 自動 instrument跨 host-guest 邊界需手動處理 context

三個遙測收集點

2025 Wasm I/O 上 Caleb Schoepp 的演講提出了清晰的分類——Wasm 系統的遙測可在三個層面收集：

  • Layer 1：Host-Guest Telemetry——宿主對 Wasm 模組的呼叫、執行時間、錯誤、資源使用
  • Layer 2：Inter-Guest Telemetry——不同 component 之間的呼叫（透過 import / export）
  • Layer 3：Intra-Guest Telemetry——component 內部自己 emit 的 span / metric / log

挑戰 1：Trace context 不能用 thread-local

傳統 OTel SDK 用 thread-local storage 維護 current span。Wasm 沒有 thread 概念，且每個 instance 是獨立隔離的——thread-local 在 Wasm 內無效。Trace context 必須顯式傳遞。

挑戰 2：OTel SDK 編譯到 Wasm 困難

傳統 OTel SDK 倚賴：

  • 背景 thread 批次 export
  • 網路 socket 直接送 OTLP
  • signal handling、process atexit hook

這些在 Wasm 內都不可用或受限。需要設計新模型：宿主代為處理 export、Wasm 只負責 emit。

挑戰 3：跨 host-guest 邊界的 trace 關聯

HTTP request 進入宿主時開始一個 root span；宿主呼叫 Wasm component；component 呼叫宿主的 outbound HTTP——這條鏈如果不正確處理 trace context，會變成三段斷掉的 trace，無法在 Tempo / Jaeger 中看到完整呼叫。

9.2路線 A：宿主層觀測（最實用）

把 Wasm 當黑盒，由宿主負責所有遙測。這是最成熟、生產級可用的方式，2026 年大多數 Wasm 服務都這樣做。

宿主可量測什麼

  • 每次 Wasm 呼叫的延遲、結果（成功/失敗/trap）
  • Wasm instance 的記憶體用量（linear memory pages × 64KB）
  • CPU 消耗（用 Wasmtime fuel 或 epoch 機制計量）
  • Instance 池狀態（available、in-use、created、destroyed）
  • Module 編譯時間、AOT cache hit rate
  • 跨 component 呼叫的拓撲與延遲

Go + wazero 的宿主埋點

go 
package main

import (
    "context"
    "net/http"
    "time"

    "github.com/tetratelabs/wazero"
    "github.com/tetratelabs/wazero/api"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/attribute"
    "go.opentelemetry.io/otel/metric"
    "go.opentelemetry.io/otel/trace"
)

var (
    tracer        = otel.Tracer("wasm-host")
    meter         = otel.Meter("wasm-host")
    wasmDuration  metric.Float64Histogram
    wasmErrors    metric.Int64Counter
    wasmMemUsage  metric.Int64Gauge
)

func init() {
    wasmDuration, _ = meter.Float64Histogram("wasm.invocation.duration_ms")
    wasmErrors, _ = meter.Int64Counter("wasm.errors.total")
    wasmMemUsage, _ = meter.Int64Gauge("wasm.memory.bytes")
}

func invokeWasm(ctx context.Context, mod api.Module, req *http.Request) error {
    // 開始 span
    ctx, span := tracer.Start(ctx, "wasm.handle_request",
        trace.WithAttributes(
            attribute.String("wasm.module", "my-api"),
            attribute.String("http.method", req.Method),
            attribute.String("http.target", req.URL.Path),
        ))
    defer span.End()

    start := time.Now()
    fn := mod.ExportedFunction("handle")
    _, err := fn.Call(ctx)
    duration := time.Since(start).Seconds() * 1000

    // 記錄 metrics
    attrs := metric.WithAttributes(
        attribute.String("component", "my-api"),
        attribute.Bool("success", err == nil),
    )
    wasmDuration.Record(ctx, duration, attrs)

    // 記憶體用量
    memSize := int64(mod.Memory().Size())
    wasmMemUsage.Record(ctx, memSize, metric.WithAttributes(
        attribute.String("component", "my-api"),
    ))

    if err != nil {
        span.RecordError(err)
        wasmErrors.Add(ctx, 1, attrs)
    }

    return err
}

9.3路線 B：Wasm 內主動回報

宿主層觀測雖然好用，但只看得到「Wasm 進去多久回來」這個外觀。要看內部邏輯（業務 metric、自訂 span），需要 Wasm 自己 emit telemetry。

機制：宿主匯入 telemetry 函式

go 
// 宿主匯入給 Wasm 的 telemetry 函式
func metricInc(ctx context.Context, m api.Module,
                namePtr, nameLen uint32, value float64) {
    name := readStr(m, namePtr, nameLen)
    counter, _ := meter.Float64Counter(name)
    counter.Add(ctx, value)
}

func logMsg(ctx context.Context, m api.Module,
             msgPtr, msgLen, level uint32) {
    msg := readStr(m, msgPtr, msgLen)
    logger := otel.GetLogger("wasm-guest")
    switch level {
    case 0: logger.Trace(msg)
    case 1: logger.Debug(msg)
    case 2: logger.Info(msg)
    case 3: logger.Warn(msg)
    case 4: logger.Error(msg)
    }
}

func spanStart(ctx context.Context, m api.Module,
                namePtr, nameLen uint32) uint32 {
    name := readStr(m, namePtr, nameLen)
    _, span := tracer.Start(ctx, name)
    return registerSpan(span)  // 回傳 handle
}

func spanEnd(ctx context.Context, m api.Module, handle uint32) {
    if span, ok := lookupSpan(handle); ok {
        span.End()
    }
}

// 註冊
r.NewHostModuleBuilder("telemetry").
    NewFunctionBuilder().WithFunc(metricInc).Export("metric_inc").
    NewFunctionBuilder().WithFunc(logMsg).Export("log").
    NewFunctionBuilder().WithFunc(spanStart).Export("span_start").
    NewFunctionBuilder().WithFunc(spanEnd).Export("span_end").
    Instantiate(ctx)

9.4路線 C：WASI-OTel 標準化（2026 仍 phase 0）

WASI-OTel 是把 OTel 變成 first-class WASI 介面的提案。截至 2026 年 5 月仍在 Phase 0（早期討論），但 Spin、wasmCloud 等平台已有實驗實作。

提案的核心構想

定義一組標準 WIT 介面，讓 Wasm component 可以用任何語言的 OTel SDK，由宿主透明地處理 export：

wit 
// 簡化版 wasi:otel/tracing
package wasi:otel@0.1.0;

interface tracing {
    record span-context {
        trace-id: list<u8>,    // 16 bytes
        span-id: list<u8>,     // 8 bytes
        flags: u8,
    }

    record key-value {
        key: string,
        value: string,
    }

    resource span {
        constructor(name: string, parent: option<span-context>);
        set-attribute: func(key: string, value: string);
        add-event: func(name: string, attributes: list<key-value>);
        set-status: func(code: u32, message: option<string>);
        end: func();
    }

    current-context: func() -> option<span-context>;
}

它解決的問題

  • 跨 component 一致介面：所有 component 用同個 wasi:otel，宿主負責橋接到實際 OTel collector
  • 正確的 parent-child 關係：host 啟動 span、傳給 guest、guest 在內部嵌套 child span，全部正確關聯
  • 語言 SDK 透明：Rust、Go、JS 的 OTel SDK 包一層 wasi:otel adapter 後，開發者寫的程式碼跟寫一般 OTel 應用一樣
  • Processor callbacks：onStart、onEnd 讓宿主插入處理邏輯

Spin 的提前實作

Spin 2.x 起內建 OTel 整合，Spin 3.0 進一步完整化。不用寫一行 OTel SDK 程式碼，Spin 自動產生 span 涵蓋 HTTP 入口、Wasm 執行、outbound HTTP 等。

9.5Trace Context 跨邊界傳遞

單一遙測訊號收集只是基礎，讓 trace 在 client → host → wasm → outbound → backend 完整連起來，才是 distributed tracing 的真正價值。本節深入這個關鍵問題。

W3C TraceContext 標準

OTel 用 W3C TraceContext 規範：

text 
# HTTP header
traceparent: 00-{trace-id}-{parent-span-id}-{flags}
tracestate: vendor specific data

# 例
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

關鍵：trace-id 16 bytes（32 hex chars）、span-id 8 bytes（16 hex chars）。

關鍵實作細節

1. 入口層：從 HTTP header 還原 context

go 
import (
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/contrib/propagators/b3"
)

func handler(w http.ResponseWriter, r *http.Request) {
    // 從 HTTP header 還原 context
    ctx := otel.GetTextMapPropagator().Extract(r.Context(),
        propagation.HeaderCarrier(r.Header))

    ctx, span := tracer.Start(ctx, "http.server",
        trace.WithSpanKind(trace.SpanKindServer),
        trace.WithAttributes(
            attribute.String("http.method", r.Method),
            attribute.String("http.target", r.URL.Path),
        ))
    defer span.End()

    invokeWasm(ctx, mod, r)
}

2. 邊界層：把 context 傳給 Wasm

Wasm 不能讀宿主的 context，要把 trace_id / span_id 序列化傳進去。實作方式：

go 
// 宿主匯入 wasm 取得 current trace context 的函式
func getTraceContext(ctx context.Context, m api.Module, outPtr uint32) uint32 {
    sc := trace.SpanContextFromContext(ctx)
    if !sc.IsValid() {
        return 0
    }

    // 寫 32 bytes: 16 bytes trace_id + 8 bytes span_id + 8 bytes flags/padding
    var buf [32]byte
    copy(buf[0:16], sc.TraceID().Bytes())
    copy(buf[16:24], sc.SpanID().Bytes())
    buf[24] = byte(sc.TraceFlags())

    m.Memory().Write(outPtr, buf[:])
    return 32
}

3. Wasm 內：建立 child span

rust 
extern "C" {
    fn get_trace_context(out_ptr: *mut u8) -> u32;
    fn start_span(name_ptr: *const u8, name_len: u32) -> u32;
    fn end_span(handle: u32);
}

fn handle() {
    // 取得 parent context
    let mut ctx_buf = [0u8; 32];
    unsafe { get_trace_context(ctx_buf.as_mut_ptr()) };
    let parent_trace_id = &ctx_buf[0..16];
    let parent_span_id = &ctx_buf[16..24];

    // 開始 child span（隱含繼承 parent trace_id）
    let span_name = b"process_request";
    let span = unsafe {
        start_span(span_name.as_ptr(), span_name.len() as u32)
    };

    // ... business logic

    unsafe { end_span(span) };
}

4. Outbound 層：注入 context 到下游

go 
// 宿主的 outbound HTTP wrapper
func outboundHTTP(ctx context.Context, url string) ([]byte, error) {
    ctx, span := tracer.Start(ctx, "http.client",
        trace.WithSpanKind(trace.SpanKindClient),
        trace.WithAttributes(attribute.String("http.url", url)))
    defer span.End()

    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)

    // 注入 trace context 到 header
    otel.GetTextMapPropagator().Inject(ctx,
        propagation.HeaderCarrier(req.Header))

    resp, err := http.DefaultClient.Do(req)
    if err != nil { return nil, err }
    defer resp.Body.Close()

    return io.ReadAll(resp.Body)
}

    sleep 0.1
done
步驟 4 · 在 Grafana 觀察

打開 http://localhost:3000（Grafana）：

  1. 選 Tempo data source，query {service.name="my-spin-app"}，看到 trace 列表
  2. 點開一條 trace，看到 spin.request → wasm.execute → 其他內部 span 的階層
  3. 切到 Loki，query {service_name="my-spin-app"}，看到對應 log
  4. 切到 Prometheus，query rate(spin_http_requests_total[1m])，看到請求速率
步驟 5 · 加自訂 span

在你的 Spin component 內加 OTel SDK，emit 自訂 span 並驗證在 Tempo 看得到：

rust 
use spin_sdk::http::{IntoResponse, Request, Response};

#[spin_sdk::http_component]
async fn handle(req: Request) -> Result<impl IntoResponse> {
    // Spin SDK 自動關聯 parent context
    let _result = process_business_logic(&req).await;

    Ok(Response::new(200, "OK"))
}

#[tracing::instrument]
async fn process_business_logic(req: &Request) -> String {
    // tracing 自動 emit span
    tracing::info!("processing request");
    // ...
    "done".to_string()
}
挑戰
  1. 加上 outbound HTTP 呼叫，確認 trace 跨服務串接成功。
  2. 注入錯誤（panic、超時），看 trace 是否正確標記 status=error。
  3. 用 tail-sampling 只保留錯誤與慢請求，減少儲存量。
  4. 把 trace 連結到對應 log（透過 trace_id），實作 trace-to-log 跳轉。

Module 09 · 10 題自我測驗

Q1.Wasm 系統的三個遙測收集點是？
  • CPU、記憶體、網路
  • Host-Guest、Inter-Guest、Intra-Guest
  • Metrics、Logs、Traces
  • Browser、Server、Edge
看解答
答案 · B Caleb Schoepp 在 Wasm I/O 2025 提出的清晰分類：Host-Guest（宿主對 Wasm 呼叫）、Inter-Guest（component 之間）、Intra-Guest（component 內部）。C 是 OTel 的三大支柱不同概念。
Q2.為什麼傳統 OTel SDK 直接編譯到 Wasm 困難？（複選）
  • SDK 倚賴背景 thread 批次 export，Wasm 不支援 thread
  • SDK 需要直接 socket 送 OTLP，Wasm 預設無網路
  • SDK 用 thread-local storage 維護 context，Wasm 無
  • Wasm 不能做 metric 計算
看解答
答案 · A、B、C A、B、C 是真實限制。D 錯——Wasm 當然能做 metric 計算，問題在 export 機制。
Q3.WASI-OTel 提案要解決什麼問題？
  • 讓 Wasm 跑得更快
  • 標準化 component 與宿主之間的 telemetry 介面，正確處理 host-guest span 父子關係
  • 取代 OpenTelemetry
  • 減少 binary 大小
看解答
答案 · B WASI-OTel 把 OTel 變成 first-class WASI 介面（資訊 sourced from Wasm I/O 2025）。截至 2026 仍 Phase 0，但 Spin / wasmCloud 已有實驗實作。
Q4.下列「宿主層觀測」可量測的指標，何者「不包含」？
  • 每次 Wasm 呼叫延遲
  • Wasm linear memory 用量
  • Wasm 內部 if 分支執行次數
  • Fuel 消耗
看解答
答案 · C 宿主只能看「黑盒」級別的指標（A、B、D）。Wasm 內部邏輯分支要靠 Layer 3 主動回報才看得到。
Q5.W3C TraceContext 中的 traceparent 結構是？
  • version-trace_id-span_id-flags
  • service-name-timestamp
  • single 64-bit integer
  • JSON object
看解答
答案 · A 格式: 00-{trace-id 16 bytes}-{parent-span-id 8 bytes}-{flags}。這是 OTel propagation 的標準。
Q6.Spin 3.0 的 OTel 整合需要開發者做什麼才能啟用？
  • 寫一大段 OTel SDK 程式碼
  • 設環境變數 OTEL_EXPORTER_OTLP_ENDPOINT 就行
  • 付費購買 Spin Enterprise
  • 改寫 spin.toml 加上 telemetry section
看解答
答案 · B Spin 自動 instrument，只要設環境變數就能 emit 完整 trace（spin.request、wasm.execute、outbound HTTP、KV、SQLite 操作都自動有 span）。
Q7.OTel collector 在 stack 中扮演什麼角色？
  • 儲存遙測資料
  • 取代 Grafana
  • vendor-neutral 中介：接收應用送來的 OTLP，processor 處理（batch、sampling、enrichment），轉送各 backend
  • 提供 UI 介面
看解答
答案 · C OTel collector 是「處理 pipeline」——receivers → processors → exporters。讓應用程式不必直接知道後端是 Tempo、Datadog 還是 Honeycomb。
Q8.下列關於 Wasm 內 trace context 傳遞，何者正確？
  • 用 thread-local storage（跟傳統 OTel 一樣）
  • 由宿主在每次呼叫時序列化 context 傳給 Wasm，Wasm 顯式取得後用於 child span
  • Wasm 不可能參與 trace 鏈
  • 用全域變數共享
看解答
答案 · B Wasm 沒 thread 概念，context 要顯式傳遞。WASI-OTel 提案就是把這個過程標準化。
Q9.tail-sampling 處理器（processor）的作用是？
  • 把所有 trace 都儲存
  • 等 trace 完整後決定取樣（保留錯誤、慢請求、隨機部分），減少儲存成本
  • 取代 Prometheus
  • 壓縮 trace 資料
看解答
答案 · B head-sampling 是進入時隨機取樣，head 看不到完整資訊。tail-sampling 等 trace 完成後做 informed 決策，例如「100% 留錯誤、100% 留 >500ms、隨機 10%」。
Q10.2026 年 Wasm 服務最快上手的可觀測性方案是？
  • 自寫所有 host function instrumentation
  • 用 Spin 或 wasmCloud 內建 OTel，設環境變數連到 collector
  • 每天手動 grep log
  • 等 WASI-OTel 1.0 release
看解答
答案 · B Spin 3.0、wasmCloud 1.0 都內建完整 OTel 整合，幾乎零配置。WASI-OTel 仍是長期方向但 phase 0，等不及。框架的內建整合是 2026 年的實務最佳選擇。
