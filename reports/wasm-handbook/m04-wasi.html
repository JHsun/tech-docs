4.1為什麼需要 WASI

第三章我們學會了自己寫 host function 給 Wasm 模組使用。問題是——如果每個 Wasm runtime 都自己定義一套，模組就無法跨 runtime 移植。Wasm「Write Once Run Anywhere」的承諾就破功了。

沒有 WASI 的世界

想像三個 Wasm runtime 各自定義「讀檔」函式：

wat 
;; Runtime A 的 import
(import "fs" "open_file" (func (param i32 i32) (result i32)))

;; Runtime B 的 import
(import "env" "file_open" (func (param i32) (result i32)))

;; Runtime C 的 import
(import "system" "openat" (func (param i32 i32 i32) (result i32)))

同一個「開檔」概念，三家簽章都不同。Wasm 模組編譯出來綁定其中一個，就無法在另一個 runtime 跑——這跟 Win32 vs POSIX vs Cocoa API 的碎片化沒兩樣。

WASI 的提案

2019 年 Mozilla 提出 WASI（WebAssembly System Interface），目標是：

  • 標準化：所有 Wasm runtime 共通的系統介面。
  • 能力導向：繼承 Wasm 的安全模型，每個能力都是明確 import。
  • 跨平台：抽象 Linux、macOS、Windows、BSD 差異。
  • 模組化：不是一個巨大 API，而是多個獨立 worlds（檔案、網路、HTTP、KV 等）。
  • 不依賴 POSIX：WASI 不是 POSIX 的 wrapper，是重新設計，POSIX 的不安全設計（如 fork、ambient signals）刻意被排除。

類比：POSIX 與 WASI

Preview 1（WASIp1, wasi_snapshot_preview1）

2019 年的首版，POSIX-like 設計，提供基本能力：

  • 檔案系統（pre-opened directories，capability-based）
  • command-line arguments、environment variables
  • clocks（時鐘、計時器）
  • random（亂數）
  • 基本 I/O streams（stdin、stdout、stderr）

注意 Preview 1 沒有網路！這是它最被詬病的限制。要聯網要靠 runtime 自己擴充（例如 Wasmtime 的 -S inherit-network 是非標準擴充）。

介面用 witx（WASI 自訂的 IDL）描述，跟 Wasm 核心緊密耦合。

Preview 2（現名 WASI 0.2）

2024 年釋出，是 WASI 的重新設計，採用 Component Model 與 WIT 介面語言。核心變化：

  • 採 WIT 取代 witx：更現代的介面定義語言，支援 record、variant、resource、list、option 等高階型別。
  • 引入 Worlds 概念：把 API 分成多個獨立 world，模組可以宣告需要哪些 world。
  • 網路 first-class：wasi:sockets、wasi:http 正式標準化。
  • 更多 worlds：wasi:cli、wasi:http、wasi:sockets、wasi:filesystem、wasi:io、wasi:clocks、wasi:random、wasi:keyvalue、wasi:logging。
  • 更明確的 resource 概念：file descriptor、socket 等都是 first-class resource type。

截至 2026 年 4 月，WASI 0.2 最新是 v0.2.11，狀態 stable，可生產採用。

Preview 3（現名 WASI 0.3）

2026 年初進入 Wasmtime 37+ 預覽，預計 2026 上半年完成。核心新增：

  • Native async：在 Component Model 層引入 future<T> 與 stream<T> 型別，async function signature。
  • 可組合的並發：不同語言寫的 component 可以透過 async 邊界自然組合，不必互相 nest event loop。
  • 0.2 介面回頭調整：用 async 重寫部分 0.2 介面（例如 wasi:http 的 streaming）。
  • Thread 支援：thread-spawn 提案漸成熟。

WASI 0.3 的 async 是這次的招牌。過去 Wasm 處理 async 要靠 polling 或 callback，現在可以直接寫 async fn handle(req: Request) -> Response 風格的程式碼。

未來：WASI 1.0

WASI 1.0 是長期穩定版的代號，預期在 0.3 完成後啟動，目標把所有介面凍結，承諾後向相容。時程未定，可能 2027 或更晚。

命名變更 Bytecode Alliance 在 2024 年改了命名規則：「Preview 2」改稱 WASI 0.2，「Preview 3」改稱 WASI 0.3。新文件多用 0.x 名稱，舊文件仍用 Preview。生產採用時要看清楚自己用的 runtime 對應哪個版本。

4.3WIT 介面定義語言

WIT（WebAssembly Interface Types）是 WASI 0.2+ 用來描述介面的 IDL，類似 Protocol Buffers 之於 gRPC、IDL 之於 CORBA、Smithy 之於 AWS。

WIT 的設計目標

  • 高階型別：string、list、record、variant、option、result、resource，不必再用 (ptr, len) idiom。
  • 跨語言可生成綁定：用 wit-bindgen 工具，從 .wit 檔產生 Rust、JS、Python、Go、C# 等綁定。
  • 版本與套件管理：支援 package 命名、版本宣告。
  • 組合性：interface 可組合成 world，world 可繼承 / 包含其他 world。

WIT 基本範例

wit 
// greet.wit
package example:greeter@0.1.0;

interface greet {
    // record 是結構型別
    record person {
        name: string,
        age: u32,
    }

    // variant 是 tagged union
    variant greeting-style {
        formal,
        casual,
        excited,
    }

    // result<T, E> 表示成功 T 或失敗 E
    say-hello: func(p: person, style: greeting-style) -> result<string, string>;
}

world greeter-world {
    import wasi:logging/logging@0.1.0;
    export greet;
}

Resource：不可拷貝的能力 handle

WIT 的 resource 是 capability-based 安全的 first-class 表達：

wit 
interface filesystem {
    resource descriptor {
        read: func(offset: u64, len: u64) -> result<list<u8>, error>;
        write: func(offset: u64, data: list<u8>) -> result<u64, error>;
        close: func();
    }

    open-file: func(path: string) -> result<descriptor, error>;
}

對應到第三章的 handle 模式——descriptor 是 opaque resource，Wasm 拿到後只能呼叫它的 method（read、write、close），無法偽造或從 i32 推導。Wasm runtime 內部仍用 i32 表示 resource，但 WIT 層把這個細節隱藏掉。

4.4主要 WASI Worlds

WASI 0.2 包含一系列 standardized worlds，每個 world 是一組相關介面的集合。生產採用時你只匯入需要的 world，最小化能力授予。

wasi:cli — 命令列程式

類似 main()、argv、env、stdin/out/err 的標準環境。包含介面：

  • wasi:cli/environment — env vars、initial-cwd
  • wasi:cli/exit — 程式結束代碼
  • wasi:cli/run — 入口函式
  • wasi:cli/stdin、stdout、stderr

wasi:http — HTTP 客戶端與伺服器

2026 年最熱門的 world。生產採用的 Spin、Fastly、wasmCloud 都用它。介面：

wit 
// 簡化版 wasi:http
interface incoming-handler {
    handle: func(request: incoming-request,
                 response-out: response-outparam);
}

interface outgoing-handler {
    handle: func(request: outgoing-request,
                 options: option<request-options>)
            -> result<future-incoming-response, error-code>;
}

resource incoming-request {
    method: func() -> method;
    path-with-query: func() -> option<string>;
    headers: func() -> headers;
    consume: func() -> result<incoming-body>;
}

有了這個介面，同一個 Wasm component 可以在 Spin、Fastly、wasmCloud 上跑，因為它們都實作 wasi:http 標準。

wasi:sockets — TCP / UDP socket

提供 BSD socket 的精簡 capability-based 版本。介面：

  • wasi:sockets/tcp — TCP socket、listen、accept、connect
  • wasi:sockets/udp — UDP socket、send、receive
  • wasi:sockets/network — network resource（capability handle）
  • wasi:sockets/ip-name-lookup — DNS 解析

關鍵設計：要建立 TCP listener 必須有 network resource，而 network 是宿主授予的——這就是 capability-based 的物理形式。

wasi:filesystem — 檔案系統

Pre-opened directory 模型——宿主給 Wasm 一個 descriptor 對應某目錄，Wasm 用相對路徑操作。無法存取沒被授予的目錄。

wasi:keyvalue — Key-Value Store

標準化的 KV 介面，宿主決定背後實作（記憶體、Redis、etcd、SQLite-litestream 都可以）。Wasm component 不知道也不需要知道。

wit 
// wasi:keyvalue/store
resource bucket {
    get: func(key: string) -> result<option<list<u8>>, error>;
    set: func(key: string, value: list<u8>) -> result<_, error>;
    delete: func(key: string) -> result<_, error>;
    exists: func(key: string) -> result<bool, error>;
}

open-bucket: func(identifier: string) -> result<bucket, error>;

wasi:logging — 結構化日誌

wit 
interface logging {
    enum level { trace, debug, info, warn, error, critical }
    log: func(level: level, context: string, message: string);
}

wasi:clocks、wasi:random、wasi:io

基礎工具 worlds：時鐘、亂數、串流抽象。多被其他 world 引用。

新興或仍在演進的 worlds

  • wasi:blobstore — Object storage（S3 概念）
  • wasi:messaging — Pub/Sub、queue
  • wasi:sql — SQL 資料庫存取（仍 alpha）
  • wasi:observe / wasi-otel — OpenTelemetry 整合（提案中）
  • wasi:nn — Neural network 推論（WasmEdge 主推）

4.5WASI 0.2 vs WASIX：兩條路線之爭

講 WASI 不能不提 WASIX——這是 Wasmer 在 WASI 進度緩慢時推出的「擴充版 Preview 1」。兩者在 2026 年仍處於並行狀態，採用前要釐清差異。

WASIX 是什麼

WASIX 是 Wasmer 在 2023 年推出的 Preview 1 fork，加入 POSIX-like 的非標準擴充：

  • fork() 與 exec()
  • 完整 BSD-style sockets
  • signals、process groups
  • threads（pthread-compat）
  • 更多 syscall 對應

目標是「讓現有 POSIX 程式（如 PHP、Python、Ruby）以最少改動跑在 Wasm」。實用主義導向。

差異與權衡

面向WASI 0.2WASIX
制定組織Bytecode Alliance（標準）Wasmer 公司
安全模型嚴格 capability-basedPOSIX-like，部分 ambient
移植既有 C 程式困難（fork、signals 都沒有）容易
跨 runtime 可攜性Wasmtime、wazero、WasmEdge、WAMR 都支援實質只有 Wasmer
Component Model原生整合不支援
async0.3 將原生支援polling 模型
未來標準化是（WASI 1.0 終極目標）否（Wasmer 自家擴充）

選型建議

選 WASI 0.2：

  • 從零開始寫 Wasm 服務
  • 需要跨 runtime 可攜性
  • 關心長期標準演進
  • 用 Rust、TinyGo、JS、Python 等支援 component 的語言

選 WASIX：

  • 必須移植大型既有 POSIX 程式（PHP runtime、Python 直譯器等）
  • 強烈依賴 fork、signals 等 POSIX 機制
  • 可接受綁定 Wasmer 生態

絕大多數新案應該選 WASI 0.2。WASIX 適合特定移植需求。

小心生態鎖定 選 WASIX = 綁定 Wasmer。如果三年後另一個 runtime 更適合，你可能要重寫。WASI 0.2 模組可在 Wasmtime、wazero、WasmEdge、WAMR 間自由切換，這個自由度有實質商業價值。

4.6Wasmtime CLI 的 WASI 能力控制

Wasmtime 是 WASI 的參考實作，CLI 提供了豐富的能力授予選項。實務中你會用這些控制本機開發、CI 測試、部分生產場景。

常用旗標

bash 
# 完全沙箱（預設）
wasmtime run program.wasm
# 模組無法讀檔、無法聯網、看不到 env

# 給特定目錄存取（capability-based pre-open）
wasmtime run --dir=/tmp/sandbox program.wasm
# 模組可讀寫 /tmp/sandbox 內檔案，無法 escape

# 給多個目錄 + 重新映射路徑
wasmtime run --dir=/host/data::/app/data program.wasm
# 模組看到 /app/data，宿主對應到 /host/data

# 傳遞環境變數（明確列出）
wasmtime run --env DB_URL=postgres://... --env LOG_LEVEL=info program.wasm

# 繼承全部環境變數（生產不建議）
wasmtime run --env-inherit program.wasm

# 開放網路存取（粗粒度）
wasmtime run -S inherit-network program.wasm

# 開放 DNS 名稱解析
wasmtime run -S allow-ip-name-lookup program.wasm

# 完整繼承（最寬鬆，等同 native process）
wasmtime run -S inherit-network -S allow-ip-name-lookup \
             --dir=. --env-inherit program.wasm

# 限制 CPU（fuel）
wasmtime run --fuel 10000000 program.wasm

# Component Model（WASI 0.2）
wasmtime run --wasm component-model program.wasm

# 預編譯 AOT
wasmtime compile program.wasm -o program.cwasm
wasmtime run --allow-precompiled program.cwasm

能力旗標的設計哲學

注意 wasmtime 對能力控制的設計：

  • 預設拒絕：不加任何旗標時，模組什麼都不能做。
  • 顯式授予：每個能力都要在指令行明確列出，沒有「給我大概的存取」。
  • 粒度可選：細到單一目錄、粗到「整個網路」皆可。
  • 無 root 概念：不論你以什麼 uid 跑 wasmtime，Wasm 內看到的能力都受 CLI 旗標限制。

用 cargo-component

bash 
# 安裝
cargo install cargo-component

# 建立 HTTP server component
cargo component new --reactor my-http
cd my-http

cargo-component 自動產生 wit/world.wit，內含 wasi:http 的 incoming-handler。我們實作 src/lib.rs：

rust 
use wasi::http::types::*;
use wasi::http::proxy::exports::wasi::http::incoming_handler::Guest;

struct MyHandler;

impl Guest for MyHandler {
    fn handle(req: IncomingRequest, response_out: ResponseOutparam) {
        // 讀請求
        let method = req.method();
        let path = req.path_with_query().unwrap_or_default();

        // 建立回應
        let response = OutgoingResponse::new(Fields::new());
        response.set_status_code(200).unwrap();

        let body = response.body().unwrap();
        ResponseOutparam::set(response_out, Ok(response));

        // 寫 body
        let out = body.write().unwrap();
        let greeting = format!("Hello from WASI 0.2! method={:?} path={}\n",
                               method, path);
        out.blocking_write_and_flush(greeting.as_bytes()).unwrap();
        OutgoingBody::finish(body, None).unwrap();
    }
}

wasi::http::proxy::export!(MyHandler with_types_in wasi::http::proxy);
bash 
# 編譯成 component
cargo component build --release

# 用 wasmtime 直接 serve
wasmtime serve \
    target/wasm32-wasip2/release/my_http.wasm

# 另一個 terminal
curl http://localhost:8080/test
# Hello from WASI 0.2! method=GET path=/test

就這樣——一個跨 runtime、capability-based、Component Model 標準的 HTTP service。同一個 .wasm 可以丟到 Spin、wasmCloud、Fastly 都能跑。

給不同團隊的建議

新專案、HTTP 服務：WASI 0.2 + Spin（或 Wasmtime 直接嵌入）。標準、可攜、社群成熟。

邊緣 / Serverless 平台：WASI 0.2 + Wasmtime 嵌入。Fastly、Spin、wasmCloud 內部都這套。

Go 團隊嵌入 Wasm：wazero + WASI 0.1（或等 0.2 完整支援）。零 CGO 部署簡單。

實驗 async：Wasmtime 37+ 啟 0.3 預覽。不要用於生產，介面仍可能變動。

有大量 POSIX 既有程式：評估 WASIX，但要考量生態鎖定。長期可能仍要遷移到 WASI 0.2。

編輯 src/lib.rs：

rust 
#[allow(warnings)]
mod bindings;

use bindings::exports::wasi::http::incoming_handler::Guest;
use bindings::wasi::http::types::*;

struct Component;

impl Guest for Component {
    fn handle(req: IncomingRequest, response_out: ResponseOutparam) {
        let method = req.method();
        let path = req.path_with_query().unwrap_or_else(|| "/".into());
        let headers = req.headers();

        // 建立回應 headers
        let response_headers = Fields::new();
        response_headers.append(&"content-type".into(),
                                &b"text/plain".to_vec()).ok();

        let response = OutgoingResponse::new(response_headers);
        response.set_status_code(200).unwrap();

        let body = response.body().unwrap();
        ResponseOutparam::set(response_out, Ok(response));

        let stream = body.write().unwrap();
        let msg = format!(
            "WASI 0.2 echo service\nmethod: {:?}\npath: {}\n",
            method, path
        );
        stream.blocking_write_and_flush(msg.as_bytes()).ok();
        drop(stream);
        OutgoingBody::finish(body, None).ok();
    }
}

bindings::export!(Component with_types_in bindings);

Module 04 · 10 題自我測驗

Q1.WASI 與 POSIX 的根本差異是？
  • WASI 比 POSIX 慢
  • WASI 採 capability-based 安全模型，POSIX 採 ambient authority
  • 兩者完全等價，只是名稱不同
  • WASI 只支援 Wasm，無法用於原生程式
看解答
答案 · B WASI 雖然概念上類似 POSIX，但安全模型根本不同——所有能力以 capability handle 形式授予，沒有 ambient authority。這也是為什麼 POSIX 的 fork、signals 等不被 WASI 0.2 採用。
Q2.下列何者「不是」WASI Preview 1（0.1）的能力？
  • 檔案系統存取（pre-opened directories）
  • command-line arguments、env vars
  • 網路 socket
  • stdin/stdout/stderr
看解答
答案 · C WASI 0.1 沒有網路！這是它最被詬病的限制。網路是 WASI 0.2 才正式標準化的（wasi:sockets、wasi:http）。Preview 1 時代要聯網要靠 runtime 擴充（如 Wasmtime 的 inherit-network 是非標準）。
Q3.WASI 0.2 引入的關鍵變化是？（複選）
  • 採 WIT 取代 witx 作為 IDL
  • 引入 Component Model 與 Worlds 概念
  • 網路成為 first-class（wasi:sockets, wasi:http）
  • native async 全面支援
看解答
答案 · A、B、C A、B、C 都是 0.2 的核心變化。D 錯——native async 是 0.3 的重點，0.2 仍是 polling 模型。
Q4.WIT 中的 resource 型別對應什麼概念？
  • 普通結構，可隨意拷貝
  • 不可拷貝、不可偽造的能力 handle，類似 file descriptor
  • 字串型別
  • async future
看解答
答案 · B resource 是 WIT 對 capability handle 的 first-class 表達。它不可拷貝（防止 handle 被偽造）、不可序列化（防止 escape），只能透過 method 操作——正是第三章 handle 模式的標準化抽象。
Q5.關於 WASI 0.3，下列敘述何者正確？
  • 已於 2024 年完成標準化
  • 主要新增 native async（future<T>、stream<T> 型別）
  • 是 WASI 0.2 的小幅修正
  • 目標是把 WASI 變成完整 POSIX 替代
看解答
答案 · B WASI 0.3 的核心是 Component Model 層的 native async：future<T>、stream<T>、async function signature。2026 年初進入 Wasmtime 37+ 預覽，預計 2026 H2 完成。
Q6.WASIX 與 WASI 0.2 的主要差異？
  • WASIX 是 Wasmer 推的 Preview 1 擴充，提供 POSIX fork/signals/threads，但綁定 Wasmer 生態
  • WASIX 是 WASI 0.2 的別名
  • 兩者完全相容
  • WASIX 比 WASI 0.2 更標準
看解答
答案 · A WASIX 是 Wasmer 自家擴充，重視「移植既有 POSIX 程式的便利性」，代價是綁定 Wasmer。WASI 0.2 才是 Bytecode Alliance 推的標準路線，跨多個 runtime。
Q7.下列 Wasmtime CLI 旗標，何者「最寬鬆」？
  • wasmtime run program.wasm
  • wasmtime run --dir=/tmp program.wasm
  • wasmtime run -S inherit-network --env-inherit program.wasm
  • wasmtime run --fuel 10000 program.wasm
看解答
答案 · C C 同時開放網路與所有 env vars，能力最多。A 預設拒絕一切；B 只給單一目錄；D 是 CPU 限制，不是能力授予。
Q8.下列 WASI worlds 中，哪個用於 HTTP server 場景？
  • wasi:cli
  • wasi:filesystem
  • wasi:http/incoming-handler
  • wasi:keyvalue
看解答
答案 · C wasi:http 分 incoming-handler（server 接受請求）與 outgoing-handler（client 發起請求）。Spin、Fastly、wasmCloud 都實作這個介面。
Q9.用 cargo component build 編譯的產物與 cargo build --target wasm32-wasip1 有何差異？
  • 兩者完全相同
  • cargo component 產出的是 WASI 0.2 component，有 WIT 介面；後者是 core module
  • cargo component 只是 alias，沒有實質差異
  • 後者不能跑在 Wasmtime
看解答
答案 · B component 是包裹了 WIT 介面、Canonical ABI 的 Wasm 高階抽象。core module 是傳統 Wasm，只有 i32/i64/f32/f64 級型別。cargo-component 工具自動處理介面綁定生成，產出可被 Spin、wasmCloud 等載入的 component。
Q10.2026 年新建一個邊緣 HTTP 服務，最穩健的 WASI 選擇是？
  • WASIX，因為功能最多
  • WASI 0.3 預覽，搶先採用
  • WASI 0.2 + Wasmtime / Spin，stable 且跨 runtime 可攜
  • WASI 0.1，最久最穩
看解答
答案 · C 2026 採用 WASI 的穩健選擇：0.2 stable 且 wasi:http 已成熟，跨 Wasmtime、Spin、wasmCloud、Fastly 等實作。A 綁 Wasmer；B 介面仍可能調整；D 沒網路，不適合新服務。
