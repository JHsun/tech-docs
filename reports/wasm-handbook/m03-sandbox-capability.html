能力導向安全模型

Wasm 最具特色的安全設計，不在加密、簽章、或代碼簽署，而在「能力導向」——一個被學界討論四十年、卻直到 Wasm 才在主流落地的安全模型。本章帶你動手實作。

Core Level ~3 hours Hands-on Lab Go + wazero

本章學習目標

  • 區分傳統授權模型（permission-based）與能力導向（capability-based）的根本差異。
  • 說明 Wasm 預設「無 ambient access」的物理意義。
  • 用 Go + wazero 實作 L7 / L4 proxy 宿主，授予 Wasm 受限的 outbound 能力。
  • 設計 allowlist / denylist 策略，理解粗粒度與細粒度的權衡。
  • 實作 SSRF 防護、配額限制、circuit breaker 等生產級防護。
  • 判斷你的場景該採用 capability-based 還是粗粒度授權。

3.1傳統授權 vs 能力導向

資安模型的本質是「決定誰能做什麼」。傳統作業系統與多數應用採用 permission-based（授權導向）模型——預設給程式很多能力，再用權限檢查擋掉不該做的。Wasm 反過來——預設什麼都不能做，宿主明確賦予具體能力。這個翻轉看似小，後果卻很大。

傳統授權的特徵

典型例子：你的 Linux 程式有讀檔權限（uid 屬於某個 group），那它能讀任何該 group 可讀的檔案。權限是「能力類別」，不綁定具體目標。

  • Ambient authority：程式取得權限後，可以對「該類資源」自由操作，目標由程式內部決定。
  • 事後檢查：每次操作時 kernel / runtime 檢查 ACL、capabilities、SELinux policy。
  • 容易誤用：程式被入侵後，攻擊者繼承所有 ambient authority；SSRF、path traversal 等漏洞利用這個特性。
  • 難以最小化：權限的粒度通常是「全部或全無」，給太多是常態。

能力導向的特徵

Capability-based 安全是 1970 年代由 Dennis 與 Van Horn 提出的概念，後在 KeyKOS、EROS、Capsicum、CloudABI 等系統中嘗試，但都未普及。Wasm 是第一個讓這個模型廣泛落地的主流技術。

  • 無 ambient authority：程式拿不到「讀檔」這個抽象能力，只能拿到「這個目錄的 handle」這種具體物件。
  • 能力即物件：能力是不可偽造的物件參考，傳遞它就是傳遞權力。
  • 事前授予：宿主在實例化時就決定該模組能拿到哪些 handle，之後無法擴大。
  • 最小特權自然達成：模組沒被傳到的 handle，就無法操作；不需要事後 ACL。

用一個生活比喻

傳統授權像「給你大樓的萬能鑰匙，警衛在每間房門口檢查你是不是該進」；能力導向像「只給你 305 號房的鑰匙，其他房門不存在於你的世界裡」。

3.2Wasm 如何實踐能力導向

第二章已經提過 Wasm 的 import / export 機制。本節從安全視角重新檢視這個機制——它就是能力導向的物理實作。

Import 即能力授予

Wasm 模組在 import section 宣告它「需要」什麼。實例化時，宿主決定要不要、以及用什麼版本提供這些 import。

wat 
;; 模組宣告需要這些能力
(module
  (import "env" "log" (func (param i32 i32)))
  (import "env" "http_get" (func (param i32 i32) (result i32)))
  (import "env" "read_file" (func (param i32 i32) (result i32)))
  ;; ...)

關鍵在於：模組無法在執行時動態取得新能力。所有能力清單在 binary 裡明確列出，可在部署前靜態審查。如果宿主沒提供某個 import，實例化會直接失敗（在執行前）。

沒匯入＝指令不存在

這比「事後檢查」更徹底。傳統 sandbox 像 seccomp 是攔截 syscall，模組仍會嘗試呼叫；Wasm 是連對應的呼叫指令都不存在。一個沒有匯入 http_get 的模組，整個 binary 找不到呼叫 http_get 的指令，連表達這個操作的方式都被消除。

Handle 模式

更進階的用法：宿主不直接給「能力」，而是給「能力 handle」。模組拿到一個 handle ID（通常是 i32），透過 handle 操作對應資源。

go 
// 宿主維護一個 handle registry
type handleRegistry struct {
    mu       sync.Mutex
    handles  map[uint32]interface{}  // handle ID → 真實資源
    nextID   uint32
}

// 宿主匯入給 Wasm 的函式：開檔，回傳 handle
func openFile(ctx context.Context, m api.Module, pathPtr, pathLen uint32) uint32 {
    path := readStr(m, pathPtr, pathLen)

    // 1. 檢查 allowlist
    if !isAllowedPath(path) {
        return 0  // 0 = invalid handle
    }

    // 2. 開檔，把 *os.File 存進 registry
    f, err := os.Open(path)
    if err != nil {
        return 0
    }

    registry.mu.Lock()
    registry.nextID++
    id := registry.nextID
    registry.handles[id] = f
    registry.mu.Unlock()

    return id  // 回給 Wasm 一個不透明 ID
}

// Wasm 透過 handle 讀取
func readHandle(ctx context.Context, m api.Module,
                 handle, bufPtr, bufLen uint32) uint32 {
    registry.mu.Lock()
    f, ok := registry.handles[handle].(*os.File)
    registry.mu.Unlock()
    if !ok {
        return 0
    }

    buf := make([]byte, bufLen)
    n, _ := f.Read(buf)
    m.Memory().Write(bufPtr, buf[:n])
    return uint32(n)
}

這個模式的好處：

  • Handle 不可偽造：Wasm 無法從 i32 數字猜出對應的真實物件，registry 是宿主私有的。
  • Handle 可細粒度：每個 handle 對應一個具體目錄 / 連線 / 物件，不是整個系統能力。
  • 生命週期可控：宿主可隨時 close handle，讓對應能力失效。

3.3實作：L7 HTTP Proxy 宿主

我們現在動手寫一個能力導向的 HTTP proxy 宿主——Wasm 模組想呼叫外部 API，必須透過宿主匯入的 proxy_l7 函式，且只能連到 allowlist 內的後端。

架構

sequenceDiagram

    participant H as Host wazero

    H->>H: allowedBackends = {api.example.com}

    W->>H: proxy_l7 url=api.example.com

    H->>H: 檢查 allowlist 拒絕
    H-->>W: DENIED return 0
Figure 3.2 · L7 proxy 的請求路徑

宿主程式碼

go 
// host/main.go
package main

import (
    "context"
    "fmt"
    "io"
    "net/http"
    "os"

    "github.com/tetratelabs/wazero"
    "github.com/tetratelabs/wazero/api"
)

// allowlist：宿主明確列出 Wasm 可以連到的後端
var allowedBackends = map[string]bool{
    "https://httpbin.org":    true,
    "https://api.github.com": true,
}

func main() {
    ctx := context.Background()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)

    // 註冊 host function 到 "env" 命名空間
    _, err := r.NewHostModuleBuilder("env").
        NewFunctionBuilder().
        WithFunc(proxyL7).
        Export("proxy_l7").
        Instantiate(ctx)
    if err != nil {
        panic(err)
    }

    // 載入 Wasm 模組
    wasmBytes, _ := os.ReadFile("module.wasm")
    mod, err := r.Instantiate(ctx, wasmBytes)
    if err != nil {
        panic(err)
    }

    // 呼叫 Wasm 的 handle 函式
    if _, err := mod.ExportedFunction("handle").Call(ctx); err != nil {
        panic(err)
    }
}

// proxy_l7: 接收 Wasm 傳來的 URL，檢查 allowlist 後代為發送 HTTP 請求
func proxyL7(ctx context.Context, m api.Module, urlPtr, urlLen uint32) uint32 {
    buf, ok := m.Memory().Read(urlPtr, urlLen)
    if !ok {
        return 0
    }
    url := string(buf)

    // 能力檢查：allowlist
    if !allowedBackends[url] {
        fmt.Printf("[host] DENIED: %s not in allowlist\n", url)
        return 0
    }

    fmt.Printf("[host] proxying L7 GET %s\n", url)
    resp, err := http.Get(url)
    if err != nil {
        return 0
    }
    defer resp.Body.Close()

    body, _ := io.ReadAll(resp.Body)
    return uint32(len(body))
}

Wasm 模組端（用 TinyGo）

go 
// module/main.go - 編譯時用 tinygo build -target=wasi
package main

import "unsafe"

//go:wasm-module env
//export proxy_l7
func proxyL7(urlPtr, urlLen uint32) uint32

//export handle
func handle() {
    // 嘗試被允許的後端
    url1 := "https://httpbin.org"
    ptr1 := uint32(uintptr(unsafe.Pointer(unsafe.StringData(url1))))
    n1 := proxyL7(ptr1, uint32(len(url1)))
    println("httpbin response length:", n1)

    // 嘗試未授權的後端 - 會被宿主拒絕
    url2 := "https://evil.example.com"
    ptr2 := uint32(uintptr(unsafe.Pointer(unsafe.StringData(url2))))
    n2 := proxyL7(ptr2, uint32(len(url2)))
    println("evil response length:", n2)  // 應該是 0
}

func main() {}

3.4實作：L4 TCP Proxy 宿主

L7 proxy 對 HTTP 場景方便，但有時需要更底層的 TCP 通道（連 Redis、MQ、SQL）。L4 proxy 使用 handle 模式：宿主給 Wasm 一個 connection handle，Wasm 透過 handle 做 read / write。

核心宿主程式碼

go 
// L4 proxy：handle-based 連線管理
type connRegistry struct {
    mu    sync.Mutex
    conns map[uint32]net.Conn
    next  uint32
}

var registry = &connRegistry{conns: map[uint32]net.Conn{}}

// 只允許這些 L4 後端
var allowedL4 = map[string]bool{
    "backend.internal:6379": true,  // Redis
    "queue.internal:5672":   true,  // RabbitMQ
}

// tcp_dial: Wasm 傳入位址，宿主檢查後建立連線，回傳 handle
func tcpDial(ctx context.Context, m api.Module,
              addrPtr, addrLen uint32) uint32 {
    buf, _ := m.Memory().Read(addrPtr, addrLen)
    addr := string(buf)

    if !allowedL4[addr] {
        log.Printf("[host] DENIED L4: %s", addr)
        return 0
    }

    conn, err := net.DialTimeout("tcp", addr, 5*time.Second)
    if err != nil {
        return 0
    }

    registry.mu.Lock()
    registry.next++
    id := registry.next
    registry.conns[id] = conn
    registry.mu.Unlock()

    return id
}

// tcp_write: Wasm 透過 handle 寫資料到連線
func tcpWrite(ctx context.Context, m api.Module,
              handle, ptr, length uint32) uint32 {
    registry.mu.Lock()
    conn := registry.conns[handle]
    registry.mu.Unlock()
    if conn == nil {
        return 0
    }
    buf, _ := m.Memory().Read(ptr, length)
    n, _ := conn.Write(buf)
    return uint32(n)
}

// tcp_read: Wasm 從連線讀資料
func tcpRead(ctx context.Context, m api.Module,
              handle, ptr, maxLen uint32) uint32 {
    registry.mu.Lock()
    conn := registry.conns[handle]
    registry.mu.Unlock()
    if conn == nil {
        return 0
    }
    buf := make([]byte, maxLen)
    n, _ := conn.Read(buf)
    m.Memory().Write(ptr, buf[:n])
    return uint32(n)
}

// tcp_close: 關閉並從 registry 移除
func tcpClose(ctx context.Context, m api.Module, handle uint32) {
    registry.mu.Lock()
    if conn, ok := registry.conns[handle]; ok {
        conn.Close()
        delete(registry.conns, handle)
    }
    registry.mu.Unlock()
}

// 註冊四個 host function
func registerL4(ctx context.Context, r wazero.Runtime) error {
    _, err := r.NewHostModuleBuilder("env").
        NewFunctionBuilder().WithFunc(tcpDial).Export("tcp_dial").
        NewFunctionBuilder().WithFunc(tcpWrite).Export("tcp_write").
        NewFunctionBuilder().WithFunc(tcpRead).Export("tcp_read").
        NewFunctionBuilder().WithFunc(tcpClose).Export("tcp_close").
        Instantiate(ctx)
    return err
}

handle 模式的安全特性

  • Wasm 拿到的 handle 是不透明 i32，無法從中推導真實 socket、目標位址、檔案描述符。
  • handle 只能透過宿主提供的函式操作，沒有「直接呼叫 sys_write(fd, ...)」這種旁路。
  • 宿主可隨時 close handle，例如 quota 超出、安全事件觸發。
  • handle 不可跨實例共享，每個 Wasm instance 有自己的 handle 空間。

3.5粒度選擇：細粒度 vs 開放式

能力導向不一定要「細到每個 URL allowlist」。實務上要依場景調整粒度。

三種粒度

粒度授予方式適用場景
極細每個 URL / 目錄 / IP allowlist已知對象的微服務、安全敏感任務
類別授予「網路存取能力」+ IP/domain 過濾通用 HTTP client、爬蟲
開放授予完整網路存取使用者執行自己的 Wasm 程式

WASI 的分層授權

WASI Preview 2 的 wasi:sockets 介面就是「類別」粒度的範例。Wasmtime CLI 可以這樣控制：

bash 
# 完全禁網（預設）
wasmtime run module.wasm

# 開放網路存取
wasmtime run -S inherit-network module.wasm

# 開放網路 + DNS 解析

SSRF 防護的標準做法

即使選擇「開放式」聯網，仍應加上基本防護，避免 Wasm 模組被攻擊者用來掃描內網或攻擊其他服務。

go 
// 開放網路但加 SSRF 防護
func tcpDialSafe(ctx context.Context, m api.Module,
                  addrPtr, addrLen uint32) uint32 {
    buf, _ := m.Memory().Read(addrPtr, addrLen)
    addr := string(buf)

    host, _, err := net.SplitHostPort(addr)
    if err != nil {
        return 0
    }

    // DNS 解析後檢查 IP，擋掉私有/loopback/link-local
    ips, err := net.LookupIP(host)
    if err != nil {
        return 0
    }
    for _, ip := range ips {
        if ip.IsLoopback() ||
           ip.IsPrivate() ||
           ip.IsLinkLocalUnicast() ||
           ip.IsLinkLocalMulticast() ||
           ip.IsUnspecified() {
            log.Printf("[host] DENIED private/internal: %s", ip)
            return 0
        }
    }

    conn, err := net.DialTimeout("tcp", addr, 5*time.Second)
    if err != nil {
        return 0
    }

    // ... 註冊 handle
    return registerConn(conn)
}
DNS Rebinding 上面的「DNS 解析後檢查 IP」仍有 DNS rebinding 風險——攻擊者 DNS 回應第一次給公開 IP（通過檢查）、第二次給內網 IP。正確做法是：解析後把該 IP 直接用於 dial，不要讓 dial 重新解析 hostname。

3.6更全面的生產級防護

能力導向解決「能不能做」，但還需要「能做多少、做多久」的配額管理。

記憶體配額

go 
// 限制 Wasm 實例最多用 128 MiB
rConfig := wazero.NewRuntimeConfig().
    WithMemoryLimitPages(2048)  // 2048 pages × 64KB = 128 MiB
r := wazero.NewRuntimeWithConfig(ctx, rConfig)

CPU 配額（Wasmtime fuel）

Wasmtime 支援精確的指令配額，每執行一條指令消耗一單位 fuel。fuel 用盡會 trap。

rust 
use wasmtime::*;

fn main() -> Result<()> {
    let mut config = Config::new();
    config.consume_fuel(true);
    let engine = Engine::new(&config)?;
    let mut store = Store::new(&engine, ());

    // 給 10M 單位 fuel
    store.set_fuel(10_000_000)?;

    // ... 載入並執行模組

    let consumed = 10_000_000 - store.get_fuel()?;
    println!("consumed {} fuel units", consumed);
    Ok(())
}

Epoch interruption

Fuel 適合精確計量但每條指令都要扣，有開銷。Wasmtime 還支援 epoch interruption——定期讓 runtime 檢查「該不該中止」，開銷小但精度低。

rust 
let mut config = Config::new();
config.epoch_interruption(true);
let engine = Engine::new(&config)?;
let mut store = Store::new(&engine, ());
store.set_epoch_deadline(1);

// 另一個 thread 定期 increment epoch
std::thread::spawn({
    let engine = engine.clone();
    move || loop {
        std::thread::sleep(Duration::from_millis(100));
        engine.increment_epoch();
    }
});

// Wasm 執行超過 100ms 會 trap

Circuit Breaker

當 Wasm 模組頻繁透過 host 呼叫下游失敗時，host 層加 circuit breaker 保護下游：

go 
type circuitBreaker struct {
    mu        sync.Mutex
    failures  int
    threshold int
    openUntil time.Time
}

func (cb *circuitBreaker) allow() bool {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    if time.Now().Before(cb.openUntil) {
        return false  // circuit is open
    }
    return true
}

func (cb *circuitBreaker) recordResult(success bool) {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    if success {
        cb.failures = 0
        return
    }
    cb.failures++
    if cb.failures >= cb.threshold {
        cb.openUntil = time.Now().Add(30 * time.Second)
        cb.failures = 0
    }
}

// 用在 host function 內
func proxyL7WithBreaker(ctx context.Context, m api.Module,
                         urlPtr, urlLen uint32) uint32 {
    if !breaker.allow() {
        return 0  // circuit open
    }
    // ... do request
    breaker.recordResult(success)
    return uint32(n)
}

3.7能力導向的反模式

實作 capability-based 安全時容易踩的坑，整理如下。

反模式 1：在 Wasm 內做安全檢查

有人會想：「把 allowlist 編譯進 Wasm 模組，模組自己檢查不就好了？」絕對不可以。攻擊者可以修改 Wasm binary、繞過 Wasm 內的檢查。安全邊界必須在宿主，Wasm 內的任何檢查都只是「便利層」，不是安全保證。

反模式 2：把整個系統能力當一個 import 給

例如匯入一個 exec_command(cmd) 函式給 Wasm。這跟「給 shell access」沒區別，capability 粒度太粗，失去意義。

反模式 3：handle 編號可預測

如果 handle 從 1 開始遞增，攻擊者可以猜測其他模組的 handle 編號。handle 應該用隨機數，且每個 instance 獨立 namespace。

反模式 4：信任 Wasm 傳來的字串長度

Wasm 傳 (ptr, len) 給宿主時，宿主必須驗證 len 不會導致讀取越過記憶體邊界，否則 wazero 雖然有 bounds check 但你拿到的 buf 可能是空 byte slice，後續邏輯崩潰。

go 
func badRead(m api.Module, ptr, length uint32) string {
    buf, _ := m.Memory().Read(ptr, length)
    return string(buf)  // 如果越界 buf 是 nil，這裡空字串
}

func goodRead(m api.Module, ptr, length uint32) (string, error) {
    if length > MAX_STRING_LEN {
        return "", errors.New("string too long")
    }
    buf, ok := m.Memory().Read(ptr, length)
    if !ok {
        return "", errors.New("memory read out of bounds")
    }
    return string(buf), nil
}

反模式 5：忘記 Wasm 是「不可信」的

即使 Wasm binary 是你自己編譯的，仍要假設它可能被替換、修改、攻擊。所有從 Wasm 傳來的資料，都當成不可信輸入處理，做完整的驗證、限制、稽核。

最重要的心智模型 Wasm 模組是「不可信的客體」（untrusted guest），宿主才是「可信主體」（trusted host）。所有安全決策都在宿主做，Wasm 內部的任何「保護」都是裝飾性的。

步驟 2 · 完整宿主程式碼

建立 main.go：

go 
package main

import (
    "context"
    "fmt"
    "io"
    "log"
    "net"
    "net/http"
    "os"
    "strings"
    "sync"
    "time"

    "github.com/tetratelabs/wazero"
    "github.com/tetratelabs/wazero/api"
    "github.com/tetratelabs/wazero/imports/wasi_snapshot_preview1"
)

var allowedHosts = map[string]bool{
    "httpbin.org":    true,
    "api.github.com": true,
}

var stats = struct {
    sync.Mutex
    requests int
    denied   int
}{}

func readStr(m api.Module, ptr, length uint32) string {
    if length > 4096 {
        return ""
    }
    buf, ok := m.Memory().Read(ptr, length)
    if !ok {
        return ""
    }
    return string(buf)
}

func proxyL7(ctx context.Context, m api.Module,
              urlPtr, urlLen uint32) uint32 {
    rawURL := readStr(m, urlPtr, urlLen)
    if rawURL == "" {
        return 0
    }

    stats.Lock()
    stats.requests++
    stats.Unlock()

    // 1. 解析 URL
    parsed, err := url.Parse(rawURL)
    if err != nil {
        return denied("invalid url")
    }

    // 2. allowlist 檢查
    host := parsed.Hostname()
    if !allowedHosts[host] {
        return denied(fmt.Sprintf("%s not in allowlist", host))
    }

    // 3. SSRF: 解析 IP, 拒絕私有網段
    ips, err := net.LookupIP(host)
    if err != nil || len(ips) == 0 {
        return denied("dns failed")
    }
    for _, ip := range ips {
        if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() {
            return denied(fmt.Sprintf("private IP: %s", ip))
        }
    }

    // 4. 發送請求（timeout）
    client := &http.Client{Timeout: 5 * time.Second}
    resp, err := client.Get(rawURL)
    if err != nil {
        return 0
    }
    defer resp.Body.Close()

    body, _ := io.ReadAll(io.LimitReader(resp.Body, 1*1024*1024))
    log.Printf("[host] %s ok %dB", rawURL, len(body))
    return uint32(len(body))
}

func denied(reason string) uint32 {
    stats.Lock()
    stats.denied++
    stats.Unlock()
    log.Printf("[host] DENIED: %s", reason)
    return 0
}

func main() {
    ctx := context.Background()
    r := wazero.NewRuntime(ctx)
    defer r.Close(ctx)

    wasi_snapshot_preview1.MustInstantiate(ctx, r)

    _, err := r.NewHostModuleBuilder("env").
        NewFunctionBuilder().WithFunc(proxyL7).Export("proxy_l7").
        Instantiate(ctx)
    if err != nil {
        log.Fatal(err)
    }

    wasmBytes, _ := os.ReadFile("module.wasm")
    cfg := wazero.NewModuleConfig().WithStdout(os.Stdout).WithStderr(os.Stderr)
    mod, err := r.InstantiateWithConfig(ctx, wasmBytes, cfg)
    if err != nil {
        log.Fatal(err)
    }
    _ = mod

    fmt.Printf("Stats: %+v\n", stats)
}

Module 03 · 10 題自我測驗

Q1.下列關於 permission-based 與 capability-based 的敘述，何者正確？
  • 兩者是等價的安全模型，只是術語不同
  • capability-based 預設無 ambient authority，能力以具體 handle 形式授予
  • permission-based 比 capability-based 安全，因為有 ACL 檢查
  • capability-based 只能用於 Wasm，無法套用其他系統
看解答
答案 · B capability-based 的核心特徵就是「無 ambient authority」+「能力即 handle」。A 兩者本質不同；C 兩者各有優勢但 capability-based 對 confused deputy 等問題更穩健；D 錯，KeyKOS、EROS、Capsicum 等 OS 都實作過。
Q2.Wasm 如何在物理層面實踐「能力導向」？
  • 執行時用 syscall filter 攔截不該做的操作
  • 用簽章驗證 Wasm 模組是否被授權
  • 沒有匯入對應 import，模組的 binary 內就找不到該操作的指令
  • 透過 RBAC policy 控制存取
看解答
答案 · C Wasm 能力導向的物理表現是「指令層面的能力限制」——沒匯入該能力，連表達該操作的指令都不存在。這比 A 的「事後攔截」更徹底。
Q3.下列哪種粒度最適合「使用者上傳自己的 Wasm 程式」場景？
  • URL allowlist（極細粒度）
  • 授予「網路存取」能力 + IP 過濾（類別粒度）
  • 給完整網路存取，不做任何限制
  • 禁止任何網路存取
看解答
答案 · B 使用者程式的目標位址不可預知，極細 allowlist 不可行（A 錯）；完全開放容易被當跳板攻擊內網（C 錯）；完全禁止又限制使用案例（D 錯）。授予類別能力 + IP 過濾是最佳平衡。
Q4.handle 模式相對於「直接傳資料」的好處是？（複選）
  • handle 是不透明 i32，Wasm 無法推導真實資源
  • handle 的生命週期由宿主控制，可隨時 invalidate
  • handle 支援細粒度授權（一個 handle 對應一個資源）
  • handle 比直接傳資料更快
看解答
答案 · A、B、C A、B、C 是 handle 模式的安全優勢。D 錯——handle 模式多一層 registry lookup，並沒有更快，採用它是為了安全而非效能。
Q5.下列何者是「DNS rebinding 攻擊」的有效防禦？
  • 解析 DNS 後檢查 IP，把該 IP 直接用於 dial（不讓 dial 重新解析）
  • 用 hostname allowlist 過濾
  • DNS 快取 5 分鐘
  • 用 HTTPS
看解答
答案 · A DNS rebinding 利用「兩次 DNS 解析結果不同」攻擊。如果 dial 重新解析，就會用到第二次的（內網）IP。把第一次解析得到的 IP 鎖死再 dial 才能擋住。B、C、D 都無法防 rebinding。
Q6.關於 Wasmtime 的 fuel 機制，下列何者正確？
  • fuel 用盡時 Wasm 模組會收到通知，可決定是否繼續
  • 每執行一條 Wasm 指令消耗一單位 fuel，用盡時 trap
  • fuel 只能用於 fuel：開放部分指令、限制部分指令
  • fuel 機制沒有任何效能開銷
看解答
答案 · B fuel 是精確的指令計量，用盡直接 trap（不通知）。它對所有指令一視同仁，且每指令扣 fuel 有少量開銷（單位百分比）。
Q7.下列何者是「在 Wasm 內做安全檢查」的問題？
  • Wasm 跑得慢，所以檢查效率低
  • 攻擊者可修改 Wasm binary 繞過內部檢查，安全邊界必須在宿主
  • Wasm 不支援字串比對
  • Wasm 內的檢查無法 log
看解答
答案 · B 這是 capability-based 的核心心智：宿主才是 trusted boundary。Wasm 內部任何檢查都只是「便利層」，不算安全保證。攻擊者可以給你一個沒檢查的 Wasm。
Q8.處理 Wasm 傳來的 (ptr, len) 字串時，正確做法是？
  • 直接信任 len，從記憶體讀取對應 bytes
  • 先檢查 len 不超過合理上限，再讀取並檢查讀取是否成功
  • 先把整個記憶體 dump 出來再從中找字串
  • 忽略 len，讀到 null byte 為止
看解答
答案 · B 所有從 Wasm 來的資料都當不可信。len 要先 validate 上限（避免巨大 alloc）、讀取要檢查回傳值（avoid silent fail）、處理空 string 等邊緣情況。
Q9.Wasmtime --dir=/tmp/sandbox 的行為是？
  • 把 Wasm chroot 到 /tmp/sandbox
  • 給 Wasm 一個對應 /tmp/sandbox 的目錄 handle，無法逃出此目錄
  • 把 /tmp/sandbox 掛載成 Wasm 的根目錄
  • 設定 Wasm 的 working directory
看解答
答案 · B --dir 是 capability-based pre-open——給 Wasm 一個 directory handle 對應該路徑。Wasm 即使呼叫 open("/etc/passwd") 也會失敗，因為它拿到的 handle 根目錄是 /tmp/sandbox，沒有任何方式 escape。
Q10.下列何者「不是」生產級 Wasm 宿主必備的防護？
  • 記憶體配額（限制 linear memory 上限）
  • CPU 配額（fuel 或 epoch interruption）
  • 能力 allowlist / capability handle
  • 把 Wasm 編譯時 -O3 優化
看解答
答案 · D 編譯優化是效能議題，不是安全議題。A、B、C 都是必備的執行時防護。D 雖然會讓 Wasm 更快，但不影響安全保證。
