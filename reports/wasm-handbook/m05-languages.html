5.1語言支援的三類模式

當我們說「某語言支援 Wasm」，這個說法掩蓋了很大的差異。同樣是「跑得起來」，C 寫的 Wasm 可能 5KB、Go 寫的 1MB、Python 寫的 10MB——根本不在同個量級。要把這個差異看清楚，需要分清「語言怎麼抵達 Wasm」這三種路徑。

路徑一：直接編譯（Directly compiled）

編譯器直接把 source code 編譯成 Wasm 指令，沒有「另一層 runtime」存在。代表語言：

  • Rust：rustc + LLVM Wasm backend
  • C / C++：clang + Wasm backend（透過 Emscripten 或 WASI SDK）
  • Zig：內建 Wasm 為一級編譯目標
  • AssemblyScript：TypeScript-like 語法，但設計為直接編譯到 Wasm

產出特性：binary 小（KB 級到百 KB 級）、冷啟動極快、執行效能接近原生。沒有 GC、沒有大型 runtime，記憶體用 malloc/free 手動管理（或 Rust 的 ownership）。

路徑二：帶 GC 的編譯（GC-based）

語言有垃圾回收機制。過去要把整個 GC runtime 編進 .wasm，binary 大；Wasm 3.0 加入 GC 後可以用宿主 GC，binary 變小但仍比直接編譯大。代表語言：

  • Go（標準工具鏈）：含完整 runtime + scheduler + GC
  • Go（TinyGo）：自家精簡 runtime，犧牲部分 Go 語意
  • Kotlin：透過 Wasm GC（experimental），鎖定 Kotlin Multiplatform 場景
  • Dart / Flutter：已 stable 使用 Wasm GC，Flutter Web 主推
  • Java：CheerpJ、TeaVM 等專案把 JVM 轉到 Wasm
  • C#：透過 Blazor + Mono on Wasm，含 .NET runtime
  • Scheme：透過 Guile Hoot，需 Wasm 3.0 的 tail call

產出特性：binary 中等到大（百 KB 到數 MB）、啟動時要載入 runtime、執行效能接近原生但有 GC pause。

路徑三：直譯器移植（Interpreter on Wasm）

不是把你的程式編成 Wasm，而是把整個語言直譯器編成 Wasm。你的程式（.py、.rb、.php）作為輸入資料給 interpreter。代表案例：

  • Pyodide：把 CPython + NumPy + SciPy 全套編成 Wasm，瀏覽器內跑 Python
  • MicroPython on Wasm：輕量級 Python，binary 較小
  • ruby.wasm：CRuby（MRI）編成 Wasm
  • PHP-Wasm / WordPress Playground：在瀏覽器跑完整 WordPress
  • QuickJS-Wasm / Javy：JS 引擎跑在 Wasm 沙箱內，常用於 Fastly Compute
  • Lua-Wasm、Perl-Wasm、Tcl-Wasm 等

產出特性：binary 巨大（5–20MB）、啟動慢、執行效能受 interpreter 限制，但可重用整個語言生態。

三個性能向量

看到「某語言支援 Wasm」時，問三個問題：

向量意義影響
Binary size編出來的 .wasm 體積下載時間、AOT 編譯時間、儲存成本
Runtime overhead內含的 runtime / GC / scheduler 大小記憶體佔用、執行時 CPU 開銷
Cold start從載入到第一行業務邏輯執行的時間Serverless / edge 場景關鍵

5.2Rust：生態最完整的 Wasm 開發選擇

Rust 是目前 Wasm 開發生態最完整、工具鏈最成熟的語言。Bytecode Alliance 的核心工具（Wasmtime、wit-bindgen、cargo-component、wasm-tools）都是 Rust 寫的，受益最大。

Rust 的 Wasm targets

Target定位WASI典型用途
wasm32-unknown-unknown純 Wasm，無 WASI無瀏覽器內、嵌入式宿主
wasm32-wasip1WASI 0.10.1傳統 Wasm 服務、CLI
wasm32-wasip2WASI 0.2 + Component Model0.2現代 component（首選）
wasm32-wasip3WASI 0.3（async）0.3 預覽實驗 async（2026）
wasm32-wasi (legacy)舊名稱，等同 wasip10.1已 deprecated，建議改用 wasip1

三種開發模式

模式 A：純 Wasm module（無 WASI）

最低層次的開發。產出 core module，所有能力都靠宿主自訂 import。適合自寫宿主、嵌入式應用。

toml 
# Cargo.toml
[package]
name = "core-mod"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[profile.release]
opt-level = "s"     # 優化體積
lto = true
strip = true        # 去除 debug
rust 
// src/lib.rs
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[no_mangle]
pub extern "C" fn fib(n: i32) -> i32 {
    if n < 2 { n } else { fib(n - 1) + fib(n - 2) }
}
bash 
cargo build --release --target wasm32-unknown-unknown
ls -la target/wasm32-unknown-unknown/release/core_mod.wasm
# 通常 < 2 KB

模式 B：WASI Preview 1 程式

適合需要檔案、stdin/stdout、env vars 的 CLI 工具。能在任何 WASI runtime 跑。

rust 
// src/main.rs
use std::env;
use std::io::{self, Read, Write};

fn main() {
    let name = env::var("USER").unwrap_or_else(|_| "world".into());
    let mut input = String::new();
    io::stdin().read_to_string(&mut input).ok();
    println!("Hello {}! you typed: {}", name, input.trim());
}
bash 
cargo build --release --target wasm32-wasip1
wasmtime run --env USER=Alice \
    target/wasm32-wasip1/release/my-cli.wasm <<< "hi"
# Hello Alice! you typed: hi

模式 C：WASI 0.2 Component（推薦現代開發）

用 cargo-component 寫 component，符合 WIT 介面，可被 Spin、wasmCloud、Wasmtime serve 等載入。

bash 
cargo install cargo-component

cargo component new --lib my-component
cd my-component
# 編輯 wit/world.wit 定義介面

三套 Rust Wasm 工具

Rust 生態有三套工具負責不同層次的 Wasm 開發，常被混淆：

工具用途產出
cargo build --target wasm32-*原生 cargo 編 Wasmcore module

wasm-bindgen：瀏覽器與 JS 整合

瀏覽器內 Wasm 要跟 JS、DOM、Web API 互動，wasm-bindgen 是主流方案。它自動生成 JS 綁定，讓 Rust 看起來像直接呼叫 JS。

rust 
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub struct Greeter {
    name: String,
}

#[wasm_bindgen]
impl Greeter {
    #[wasm_bindgen(constructor)]
    pub fn new(name: &str) -> Self {
        Self { name: name.to_string() }
    }

    pub fn greet(&self) -> String {
        format!("Hello, {}!", self.name)
    }
}

// 呼叫 JS 全域 console.log
#[wasm_bindgen]
extern "C" {
    #[wasm_bindgen(js_namespace = console)]
    fn log(s: &str);
}

#[wasm_bindgen]
pub fn say_hello() {
    log("Hello from Rust + Wasm!");
}

用 wasm-pack 包成 NPM 套件：

bash 
cargo install wasm-pack
wasm-pack build --target web
# 產出 pkg/ 目錄，含 .wasm + JS glue + .d.ts
# 可直接在前端 import

體積優化技巧

Rust 預設編出的 Wasm 可能比預期大，幾個優化點：

toml 
# Cargo.toml 完整體積優化
[profile.release]
opt-level = "z"         # z 比 s 更激進壓體積
lto = true              # link-time optimization
codegen-units = 1       # 單一編譯單元，較好優化
strip = true            # 去除 symbol
panic = "abort"         # 不要 unwinding code
bash 
# 進一步用 wasm-opt（binaryen 工具）
cargo install wasm-opt
wasm-opt -Oz -o output.wasm input.wasm
# 通常可再減 10-30% 體積

# wasm-tools 也可進一步 strip 沒用到的 section
wasm-tools strip output.wasm -o stripped.wasm

Rust Wasm 的常見坑

  • panic 會 trap：Rust panic 在 Wasm 中變成 trap，整個 instance 死掉。生產用 Result 而非 panic。
  • 沒有 std::thread：Wasm 1.0/2.0 沒原生 thread；要用 thread 要用 wasm32-wasi 的 threads 提案或宿主協助。
  • std::process::exit 行為不同：在 component 內呼叫 exit 會結束整個 instance，不只是當前 invocation。
  • 時間 API 受限：SystemTime::now() 在 WASI 環境會工作，但 Instant::now() 在某些 target 上不可用。
  • 網路庫不通用：tokio、reqwest 等預設不支援 Wasm。WASI 0.2 有 wasi:sockets 但 ecosystem 還在追。

5.3Go / TinyGo：兩條路徑的取捨

Go 是後端 / 雲端原生領域的主力語言，但它編到 Wasm 有兩條路：標準工具鏈與 TinyGo。兩者取捨非常不同。

標準 Go 工具鏈

從 Go 1.11 起，GOOS=js GOARCH=wasm 可編譯到瀏覽器內 Wasm；從 Go 1.21 起，GOOS=wasip1 GOARCH=wasm 編譯到 WASI 0.1；2024 Go 1.24+ 開始支援 //go:wasmexport 標準化匯出。

go 
// main.go - 標準 Go WASI
package main

import (
    "fmt"
    "os"
)

//go:wasmexport add
func Add(a, b int32) int32 {
    return a + b
}

func main() {
    name := os.Getenv("USER")
    if name == "" {
        name = "world"
    }
    fmt.Printf("Hello %s from Go on WASI!\n", name)
}
bash 
# 編譯為 WASI 0.1
GOOS=wasip1 GOARCH=wasm go build -o app.wasm main.go
ls -la app.wasm
# 通常 1.5-3 MB（含完整 Go runtime）

wasmtime run --env USER=Alice app.wasm
# Hello Alice from Go on WASI!

標準 Go 的優劣

優點：

  • 完整 Go 語言相容性——你的 Go 程式幾乎不用改
  • 標準函式庫完整可用（fmt、net/http client、encoding/json 等）
  • goroutine、channel 等並發原語可用
  • GC 行為與原生 Go 一致

缺點：

  • binary 巨大：hello world 就 2MB+，因為要塞 GC + scheduler + runtime
  • 啟動慢：runtime 初始化要時間
  • WASI 0.2 / Component Model 暫不支援：標準工具鏈仍主要綁 WASI 0.1
  • 記憶體佔用高：每個 instance 都帶完整 runtime

TinyGo

TinyGo 是基於 LLVM 的 Go 替代編譯器，專為「小 binary」設計。它支援 Go 語言子集（不是 100% 相容），用更精簡的 runtime 與 GC，編出來的 Wasm 小很多。

bash 
# 安裝 TinyGo (Linux/macOS)
# https://tinygo.org/getting-started/install/

# WASI 0.1
tinygo build -o app.wasm -target=wasi main.go

# WASI 0.2 (component) - TinyGo 0.34+
tinygo build -o app.wasm -target=wasip2 main.go

# 0.41 (2026) 開始有更完整 WASI 支援
tinygo version

TinyGo 0.34+ 的 component model 支援

2024 年 TinyGo 加入 wasip2 target；2026 年 TinyGo 0.41 進一步完善 component 開發體驗。流程：

bash 
# 1. 安裝必要工具
cargo install wasm-tools wkg
go install go.bytecodealliance.org/cmd/wit-bindgen-go@latest

# 2. 撰寫 WIT
mkdir my-comp && cd my-comp
cat > wit/world.wit << 'EOF'
package example:adder@0.1.0;

interface add {
    add: func(x: u32, y: u32) -> u32;
}

world adder {
    include wasi:cli/imports@0.2.0;
    export add;
}
EOF

# 3. 用 wkg 解析依賴
wkg wit build --wit-dir wit -o example:adder.wasm

# 4. 用 wit-bindgen-go 生成 Go 綁定
go tool wit-bindgen-go generate \
    --world adder --out internal ./example:adder.wasm

# 5. 寫 main.go 實作介面
# 6. tinygo build
tinygo build -target=wasip2 \
    -o adder.wasm \
    --wit-package ./example:adder.wasm \
    --wit-world adder \
    main.go
go 
// main.go - 對應上述 WIT
package main

import (
    "example.com/internal/example/adder/add"
)

func init() {
    add.Exports.Add = func(x uint32, y uint32) uint32 {
        return x + y
    }
}

// main 函式即使空也必要
func main() {}

標準 Go 與 TinyGo 對照

選擇建議

選標準 Go：你有複雜的 Go 程式想原封不動編到 Wasm，可接受 2MB+ binary 與長啟動。常見場景：CI 工具、批次處理。

選 TinyGo：你關心 binary size、冷啟動、或需要 component model。常見場景：邊緣 serverless、外掛系統、嵌入式。2026 年 Wasm + Go 主流選擇。

標準函式庫的坑 TinyGo 不支援部分 std 套件，最常見的是 net/http 完整版（client 部分可、server 受限）、reflect 部分功能、encoding/gob 等。實際使用前要查 TinyGo std 支援表。

wazero + 標準 Go 的特殊組合

提醒一個容易混淆的點：wazero 是 Go 寫的 Wasm runtime，跟「用 Go 寫 Wasm 模組」是不同的事。

  • 「用標準 Go 編 Wasm」：把你的 Go 程式編成 .wasm，產出大。
  • 「用 wazero 跑 Wasm」：在 Go 程式裡內嵌一個能執行 .wasm 的 runtime，宿主端用。

實務上常見組合：宿主用 wazero（Go）、Wasm 模組用 Rust 或 TinyGo 寫，兩邊都享受 Go 友好。

5.4C / C++ / Zig：系統語言的 Wasm 之路

C/C++ 是 Wasm 的原始目標語言——2015 年提案時主要使用案例就是「讓 C++ 程式在瀏覽器跑」。Zig 是後起之秀，內建 Wasm 為一級 target。

兩種 C/C++ 工具鏈

Emscripten：最早、最完整的工具鏈，emcc 取代 gcc/clang。主打瀏覽器整合，自動生成 JS glue code、提供 SDL/OpenGL 等 API 模擬。代價：產出綁瀏覽器、binary 較大。

WASI SDK：Bytecode Alliance 提供的「乾淨」C/C++ 工具鏈，基於 clang，產出標準 WASI Wasm，無 JS 綁定。適合伺服器 / 邊緣 / 嵌入式。

EmscriptenWASI SDK
主要場景瀏覽器伺服器、邊緣、嵌入式
libcmusl-derived（含 JS 接口）wasi-libc（純 WASI）
輸出.wasm + .js glue純 .wasm
SDL / OpenGL原生支援（轉 WebGL）無
檔案系統虛擬 FS（emscripten FS API）WASI fd

WASI SDK 範例

c 
// hello.c
#include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    const char *name = getenv("USER");
    if (!name) name = "world";
    printf("Hello %s from C on WASI!\n", name);
    return 0;
}
bash 
# 下載 WASI SDK
# https://github.com/WebAssembly/wasi-sdk/releases

# 編譯
$WASI_SDK_PATH/bin/clang \
    --target=wasm32-wasi \
    --sysroot=$WASI_SDK_PATH/share/wasi-sysroot \
    -O2 -o hello.wasm hello.c

ls -la hello.wasm  # 約 20-30 KB
wasmtime run --env USER=Alice hello.wasm

Emscripten 範例（瀏覽器）

bash 
# 安裝 emsdk
git clone https://github.com/emscripten-core/emsdk
cd emsdk && ./emsdk install latest && ./emsdk activate latest
source ./emsdk_env.sh

# 編譯
emcc hello.c -o hello.html
# 產出 hello.html + hello.js + hello.wasm
# 用 emrun hello.html 開啟瀏覽器測試

把既有 C/C++ 程式編到 Wasm

Emscripten / WASI SDK 都能編譯大型 C/C++ 專案，常見的成功案例：

  • SQLite：sqlite.wasm 可在瀏覽器跑完整資料庫
  • FFmpeg：影音編解碼在瀏覽器
  • ImageMagick：影像處理
  • OpenSSL / BoringSSL：密碼學運算
  • Unity / Unreal 引擎：遊戲
  • Doom、Quake：經典遊戲移植

移植時最常遇到的問題：

  • fork / exec 不支援（除非用 WASIX）
  • 檔案系統行為不同，要 mount 虛擬 FS
  • POSIX signals 受限
  • 多執行緒要靠 SharedArrayBuffer（瀏覽器需 CORS header）
  • 網路要用 Emscripten 的 socket emulation 或 Web API

Zig：新銳系統語言

Zig 把 Wasm 列為一級 target，zig build-exe -target wasm32-wasi 就能編譯，不需第三方工具。Zig 沒有隱含 runtime，編出來的 Wasm 跟 Rust no_std 同等小。

zig 
// hello.zig
const std = @import("std");

pub fn main() !void {
    const stdout = std.io.getStdOut().writer();
    try stdout.print("Hello from Zig on Wasm!\n", .{});
}

export fn add(a: i32, b: i32) i32 {
    return a + b;
}
bash 
# WASI binary
zig build-exe hello.zig -target wasm32-wasi -O ReleaseSmall

# 純 module (無 WASI)
zig build-lib hello.zig -target wasm32-freestanding \
    -dynamic -rdynamic -O ReleaseSmall

Zig 的優勢是無隱藏成本——沒 GC、沒 runtime、明確的記憶體管理、跨編譯非常簡單。劣勢是生態還小，函式庫遠少於 Rust。

5.5AssemblyScript：給 Web 開發者的 Wasm

AssemblyScript 是「TypeScript-like 語法的 Wasm 專用語言」。不是真正的 TypeScript（缺少很多動態特性），但語法相似，是 web 開發者進入 Wasm 的最低門檻。

typescript 
// assembly/index.ts
export function add(a: i32, b: i32): i32 {
    return a + b;
}

export function fib(n: i32): i32 {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}

// 字串支援（靠輕量 runtime）
export function greet(name: string): string {
    return "Hello, " + name + "!";
}
bash 
npm install --save-dev assemblyscript
npx asinit .
npx asc assembly/index.ts -o build/release.wasm -O3
ls -la build/release.wasm  # 通常 1-5 KB

AssemblyScript 的特性

  • 靜態型別嚴格：必須宣告型別，i32 / i64 / f32 / f64 / string 等。
  • 輕量 runtime + 簡易 GC：支援 class、string、array，比 Rust 多但比 Go 少。
  • 無動態特性：沒有 any、沒有 union type、沒有 reflection。
  • 對 web 開發者友善：語法、工具鏈跟 npm 生態整合。
  • 體積小：典型 hello world 數 KB。

適用場景：前端開發者想加速關鍵運算邏輯、做 web 內部分數值/圖形運算、需要 Wasm 但又不想學 Rust。但生態相對小，企業案例不多。

5.6GC 語言：Dart、Kotlin、Java、C#、Scheme

傳統 Java、Dart、Kotlin 等 GC 語言要把整個 runtime + GC 編進 .wasm，binary 巨大（10–30MB）。Wasm 3.0 的 GC 提案改變了這個局面——這些語言可以用宿主提供的 GC，binary 大幅瘦身。

Dart / Flutter Web

2024 年起 Dart 支援 Wasm GC，Flutter Web 主推這個方案：用 Wasm 取代 dart2js 達到「near-native」效能。截至 2026 年 Flutter Wasm 已 stable，binary 比 dart2js 版稍大但執行快很多。

bash 
# Flutter Web with Wasm
flutter build web --wasm
# 產出 build/web/ 含 .wasm 與 JS 載入器

Kotlin / Kotlin Multiplatform

Kotlin/Wasm 仍標示 alpha（2026 年），但已可用於 Kotlin Multiplatform 場景。目標：Kotlin 程式在瀏覽器跑得跟 JVM 一樣快，不再走 Kotlin/JS。

kotlin 
// gradle config
kotlin {
    wasmJs {
        browser()
        binaries.executable()
    }
}

Java：CheerpJ、TeaVM、Bytecode Alliance 提案

Java 的 Wasm 路徑比較分散：

  • CheerpJ：商業產品，把 JVM bytecode 編到 Wasm（含一個 JVM-on-Wasm）
  • TeaVM：把 Java bytecode 編到 JS 或 Wasm
  • GraalVM Native Image + Wasm：透過 Truffle
  • OpenJDK Wasm 提案：原生支援，2026 仍在 incubator

C# / Blazor

.NET 從 5.0 起支援 Wasm（透過 Mono 與 .NET runtime），Blazor 是主要應用。2026 年的 Blazor 仍是 .NET runtime + AOT 編譯到 Wasm，binary 數 MB，但 enterprise 採用率高。

bash 
dotnet new blazorwasm -n MyApp
cd MyApp
dotnet publish -c Release
# 產出 wwwroot/ 含 .wasm + .NET runtime + 你的 DLL

Scheme（GNU Guile Hoot）

Hoot 利用 Wasm 3.0 的 tail call、GC、exception handling，把 Guile Scheme 編到 Wasm。代表 Wasm 3.0 對函式式語言的意義——之前 Scheme 寫的 Wasm 要用 trampoline 模擬 tail call，現在原生支援。

GC 語言的 Wasm 路徑 Wasm 3.0 GC 提案讓 Java、Kotlin、Dart、Scheme 等不必再帶完整 GC runtime，binary 大幅瘦身。但完整商用採用度仍以 Dart/Flutter 領先。Java、Kotlin 仍在追，2026 下半年情況會明朗。

5.7Interpreter on Wasm：Python、Ruby、PHP、JS

這條路徑特別——不是把你的程式編成 Wasm，而是把整個語言直譯器編成 Wasm，你的程式（.py、.rb）作為輸入餵給 interpreter。

Pyodide：Python on Wasm

Pyodide 是把 CPython 完整編到 Wasm 的專案，內建 NumPy、Pandas、Matplotlib、SciPy 等科學運算棧。瀏覽器內可以直接跑 Python，且幾乎所有 PyPI 套件都能跑（純 Python 套件無縫，C 擴充套件部分支援）。

html 
<!-- 瀏覽器內跑 Python -->
<script src="https://cdn.jsdelivr.net/pyodide/v0.27.0/full/pyodide.js"></script>
<script>
async function main() {
    const pyodide = await loadPyodide();
    await pyodide.loadPackage("numpy");

    const result = pyodide.runPython(`
import numpy as np
arr = np.array([1, 2, 3, 4, 5])
arr.mean()
    `);
    console.log("mean:", result);
}
main();
</script>

代價：Pyodide 主 bundle 6–10 MB，首次載入慢。但對「在瀏覽器跑科學運算」場景無可取代。

componentize-py：Python as Component

另一條路徑：把你的 Python 程式跟一個精簡 Python interpreter 一起打包成 WASI 0.2 component。適合伺服器端 Wasm 服務。

bash 
pip install componentize-py
componentize-py componentize app -o app.wasm
wasmtime serve app.wasm

Ruby.wasm

把 CRuby（MRI）編成 Wasm。比 Pyodide 更晚成熟，但 2024 起也漸普及。瀏覽器內、Wasmtime 都能跑。

html 
<script type="text/ruby">
require "js"
JS.global[:document].write("Hello from Ruby!")
</script>
<script src="https://cdn.jsdelivr.net/npm/@ruby/3.3-wasm-wasi@2.6.0/dist/browser.script.iife.js"></script>

PHP-Wasm / WordPress Playground

WordPress Playground 把 PHP 引擎 + WordPress + SQLite 全部編成 Wasm，瀏覽器內跑完整 WordPress。展示 Wasm 在「重型既有應用移植」的極限。

JavaScript on Wasm：Javy 與 QuickJS

有趣的反向案例——把 JS 引擎編成 Wasm，跑在 Wasm 沙箱內。動機：在 Wasm host（如 Fastly Compute）上跑 JS 程式碼，避免 V8 的攻擊面與資源開銷。

  • Javy（Shopify 開源）：QuickJS + 你的 JS code，編成單一 .wasm。Shopify Functions 大量使用。
  • SpiderMonkey-on-Wasm：Fastly 把 SpiderMonkey 編到 Wasm，效能更好但 binary 更大。
bash 
# 用 Javy
cargo install javy-cli
echo 'console.log("Hello from JS in Wasm");' > index.js
javy compile index.js -o index.wasm
wasmtime run index.wasm

Interpreter 模式的取捨

面向說明
優勢可重用整個既有語言生態（套件、框架、文件），無需重寫
體積大（5–20 MB），interpreter 本體不可避免
啟動慢（百毫秒到秒級）
執行效能受 interpreter 限制，比直接編譯慢 5–50 倍
適用場景瀏覽器內跑既有腳本、客戶端腳本系統、移植大型 codebase
不適用場景邊緣 serverless（冷啟動殺手）、效能敏感運算

給不同團隊的具體建議

後端 / 平台工程師：學 Rust，因為生態最完整、官方工具鏈最成熟，且未來 Component Model 進展也以 Rust 為先。

Go 團隊轉 Wasm：用 TinyGo + WASI 0.2 target，享受小 binary 與 component model。標準 Go 留給特殊情境（要 100% Go 相容性）。

前端團隊想加速關鍵運算：兩條路——AssemblyScript（低門檻）或 Rust + wasm-pack（更專業）。

既有大型 C/C++ codebase 移植：Emscripten（瀏覽器）或 WASI SDK（伺服器邊緣）。

SaaS 想讓客戶寫腳本：用 Javy（JS）或 componentize-py（Python），讓客戶用熟悉語言。

LAB動手實作：同一 API、三種語言實作

Lab 5.A · 多語言對比

用 Rust、TinyGo、AssemblyScript 各寫一個 fibonacci 函式，比較體積

共同介面

每個語言都實作一個函式 fib(n: i32) -> i32，計算費氏數列。

Rust 實作
bash 
mkdir rust-fib && cd rust-fib
cargo init --lib

# Cargo.toml
cat >> Cargo.toml << 'EOF'
[lib]
crate-type = ["cdylib"]

[profile.release]
opt-level = "z"
lto = true
strip = true
panic = "abort"
EOF

# src/lib.rs
cat > src/lib.rs << 'EOF'
#[no_mangle]
pub extern "C" fn fib(n: i32) -> i32 {
    if n < 2 { n } else { fib(n - 1) + fib(n - 2) }
}
EOF

cargo build --release --target wasm32-unknown-unknown
ls -la target/wasm32-unknown-unknown/release/rust_fib.wasm
TinyGo 實作
bash 
mkdir tinygo-fib && cd tinygo-fib

cat > main.go << 'EOF'
package main

//go:wasmexport fib
func Fib(n int32) int32 {
    if n < 2 {
        return n
    }
    return Fib(n-1) + Fib(n-2)
}

func main() {}
EOF

tinygo build -o fib.wasm -target=wasi -no-debug main.go
ls -la fib.wasm
AssemblyScript 實作
bash 
mkdir as-fib && cd as-fib
npm init -y
npm install --save-dev assemblyscript
npx asinit . -y

cat > assembly/index.ts << 'EOF'
export function fib(n: i32): i32 {
    if (n < 2) return n;
    return fib(n - 1) + fib(n - 2);
}
EOF

npx asc assembly/index.ts -o build/release.wasm -O3 --runtime stub
ls -la build/release.wasm
標準 Go 對照組
bash 
mkdir go-fib && cd go-fib

cat > main.go << 'EOF'
package main

//go:wasmexport fib
func Fib(n int32) int32 {
    if n < 2 {
        return n
    }
    return Fib(n-1) + Fib(n-2)
}

func main() {}
EOF

GOOS=wasip1 GOARCH=wasm go build -o fib.wasm main.go
ls -la fib.wasm
比較結果

典型結果（會隨工具版本變化）：

實作體積備註
Rust（cdylib + opt-level=z）~ 200 bytes無 runtime
AssemblyScript (runtime=stub)~ 100 bytes類似 Rust
TinyGo (no-debug)~ 100 KB含精簡 runtime
標準 Go~ 2 MB含完整 runtime + GC + scheduler

同樣的邏輯，體積差距達 10000 倍。這就是「選錯語言會讓 .wasm 膨脹十倍以上」的真實樣貌。

挑戰
  1. 把每個版本用 wasmtime --invoke fib N 跑 fib(30)，比較執行時間。
  2. 觀察 wasm-tools dump *.wasm 找出體積差異來自哪些 section。
  3. 用 wasm-opt -Oz 進一步壓縮 Rust 版本，看能壓到多小。

Module 05 · 10 題自我測驗

Q1.下列哪類語言編出的 Wasm 體積最小？
  • 直接編譯類（Rust、C、Zig）
  • GC 語言（標準 Go、Java）
  • Interpreter on Wasm（Pyodide、ruby.wasm）
  • 所有語言都差不多
看解答
答案 · A 直接編譯類無 runtime，體積最小（KB 級）。GC 語言要帶 runtime（百 KB 到 MB）。Interpreter 模式要把整個解譯器塞進來（5-20 MB）。
Q2.「wazero + 標準 Go」這個組合的角色配置是？
  • 用標準 Go 編 Wasm 模組，再用 wazero 跑
  • 用 wazero 作為宿主 runtime，Wasm 模組通常用 Rust 或 TinyGo 寫
  • 兩者完全等價
  • wazero 是 Go 的 Wasm 編譯器
看解答
答案 · B wazero 是 Go 寫的 runtime（執行 .wasm），不是編譯器。常見組合：宿主用 Go + wazero、Wasm 模組用 Rust/TinyGo 寫。
Q3.下列何者「不是」TinyGo 相對標準 Go 的優勢？
  • 較小的 binary
  • 較快的冷啟動
  • 100% Go 標準函式庫相容
  • 支援 WASI 0.2 / Component Model
看解答
答案 · C TinyGo 不支援完整 Go std——這是它最大的缺點。reflect、部分 net、encoding 套件等都受限。A、B、D 都是 TinyGo 真正的優勢。
Q4.下列何者是 Rust Wasm 三大工具的對應關係？
  • cargo build → core module；wasm-pack → 瀏覽器+JS 綁定；cargo-component → WASI 0.2 component
  • 三者完全等價，只是名稱不同
  • cargo build 只能編譯到 wasm32-wasip1
  • cargo-component 只能用於瀏覽器
看解答
答案 · A 三者職責不同：cargo build 是底層 Wasm 編譯；wasm-pack 主要處理瀏覽器 + JS 整合；cargo-component 專做 WASI 0.2 component。
Q5.Emscripten 與 WASI SDK 的主要差異是？
  • Emscripten 較快
  • Emscripten 主打瀏覽器整合（自動生 JS glue），WASI SDK 產出純 WASI Wasm 適合伺服器/邊緣
  • WASI SDK 只支援 C，Emscripten 支援 C++
  • 兩者完全等價
看解答
答案 · B Emscripten 是瀏覽器整合導向（SDL、OpenGL、WebGL、JS API 全模擬），WASI SDK 是純 WASI 導向。兩者場景不同：前者搬遊戲到瀏覽器，後者搬伺服器邏輯到 Wasm。
Q6.Wasm 3.0 的 GC 提案對下列哪些語言意義最大？（複選）
  • Rust
  • Dart
  • Kotlin
  • Java
  • C
看解答
答案 · B、C、D Wasm GC 讓帶 GC 的語言可以用宿主 GC，不必把自家 GC runtime 編進 .wasm。Dart、Kotlin、Java 受益最大。Rust、C 沒 GC，不受影響（A、E 錯）。
Q7.Pyodide 適合哪個場景？
  • 邊緣 serverless（冷啟動要求 µs 級）
  • 瀏覽器內跑 Python 科學運算（NumPy、Pandas）
  • 嵌入式 IoT 裝置
  • 高頻交易系統
看解答
答案 · B Pyodide 體積 6-10 MB、啟動秒級，A、C、D 都不適合。但瀏覽器內跑 Python 科學運算棧是它的招牌場景。
Q8.下列哪個工具用於 JavaScript 編到 Wasm？
  • wasm-pack
  • cargo-component
  • Javy
  • Emscripten
看解答
答案 · C Javy（Shopify 開源）把 JS + QuickJS 引擎打包成單一 .wasm。Shopify Functions 大量採用。A 是 Rust→Wasm；B 是 Rust component；D 是 C/C++→Wasm。
Q9.選擇 Wasm 開發語言時，最該優先考慮的問題是？
  • 這個語言的薪資高不高
  • 場景（serverless 冷啟動、瀏覽器、嵌入式...）、binary 體積要求、團隊熟悉度
  • 語言的人氣排名
  • 是否支援泛型
看解答
答案 · B Wasm 語言選擇是工程決策，要根據場景需求（性能向量）、團隊資源、生態成熟度。
Q10.2026 年新建一個邊緣 HTTP serverless 服務，最佳語言選擇順序通常是？
  • Python（Pyodide） > Java > 標準 Go
  • Rust > TinyGo > AssemblyScript
  • 標準 Go > Java > C#
  • 隨便選都一樣
看解答
答案 · B 邊緣 serverless 場景看重小 binary + 快冷啟動。Rust 生態最成熟、TinyGo 對 Go 團隊友善、AssemblyScript 對前端友善——都是直接編譯類。A、C 的選項冷啟動成本太高。

  • 讀懂「binary size、runtime overhead、cold start」三個性能向量，並用此判斷適用場景。
  • 用 Rust 三套工具（cargo build、wasm-pack、cargo-component）依場景產出不同類型的 Wasm。
  • 知道 TinyGo 與標準 Go 各自的優劣，做出 informed 的選型。
  • 了解 C/C++（Emscripten、WASI SDK）、Zig、AssemblyScript 的定位。
  • 掌握 GC 語言（Dart、Kotlin、Java、C#、Scheme）在 Wasm 3.0 後的進展。
