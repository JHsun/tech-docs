1.1Wasm 是什麼，又不是什麼

在大多數技術介紹文裡，WebAssembly 被描述為「一種可以在瀏覽器中接近原生速度執行的二進位格式」。這個描述沒有錯，但失之片面——它只看到了 2017 年的 Wasm，沒看到 2026 年的 Wasm。要建立穩固的心智模型，我們需要從「它技術上到底是什麼」開始拆解。

正面定義：技術本質

WebAssembly（簡稱 Wasm）是一種低階的二進位指令格式（low-level binary instruction format），設計為可攜帶的編譯目標（portable compilation target）。它的核心技術特徵：

  • Stack-based 虛擬機：採堆疊式虛擬機執行模型，指令操作堆疊上的值，類似 JVM bytecode 但更精簡。
  • 靜態型別、靜態驗證：載入時就能完成型別檢查與記憶體安全驗證，不像動態語言要邊跑邊檢查。
  • 沙箱化執行：每個 Wasm 模組獨占自己的線性記憶體（linear memory），無法直接讀寫宿主環境記憶體。
  • 能力導向（capability-based）安全模型：預設無 ambient access，所有對外能力都必須由宿主（host）明確匯入。
  • 跨語言、跨平台：作為編譯目標，理論上任何系統語言都能編譯到 Wasm；產出的 .wasm 在任何遵循標準的 runtime 都能執行。

反面定義：Wasm 不是什麼

誤解 Wasm 的人通常都把它跟某個既有技術混為一談。逐一釐清：

誤解正確認知
Wasm 是 JavaScript 取代品 Wasm 是「給多語言用的編譯目標」，跟 JS 是互補關係。Wasm 在瀏覽器內需要 JS 來載入，且很多 Web API（DOM、fetch）目前仍要透過 JS 中介。
Wasm 是 OS 執行檔 跟 ELF、PE、Mach-O 不同，你無法直接 ./module.wasm 執行。它永遠需要一個 runtime 來載入、驗證、執行——無論這個 runtime 是瀏覽器、Wasmtime、wazero，還是嵌入應用內的引擎。
Wasm 是容器替代品 容器（OCI image）打包的是「整個 OS userspace + 程式」，Wasm 模組打包的只是「程式邏輯」，作業系統能力來自宿主。兩者粒度不同，更精確地說，Wasm 取代的是 container runtime 中的 process，而不是容器本身。
Wasm 是 JVM 翻版 表面相似（都是 stack VM、都跨平台），但設計哲學差很多。JVM 是 Java 生態為主、為長駐進程設計；Wasm 是語言中立、為輕量沙箱與短生命週期設計，且啟動成本低 2-3 個數量級。
Wasm 只能在瀏覽器跑 這是 2018 年的認知。2026 年的 Wasm 在伺服器、邊緣、IoT、區塊鏈、資料庫 UDF 等場景都已生產採用，瀏覽器反而不是其最活躍的演進前線。

一段話精準定義

WebAssembly 是一種跨語言、跨平台、能力導向的可攜編譯目標。它定義了一個低階虛擬機的二進位格式與執行語意，由宿主提供能力、執行驗證與隔離。它讓任何系統語言寫的程式碼能以「安全、可預測、低開銷」的方式部署到瀏覽器、伺服器、邊緣與嵌入式環境。
記住這幾個關鍵詞 Portable compilation target、stack-based VM、linear memory、capability-based、host-imported abilities。這幾個詞會在後續每一章反覆出現。

階段一：史前時代（2008–2014）

Wasm 不是憑空出現，它解決的是一個由 Google 與 Mozilla 各自摸索十年的問題：「怎麼讓瀏覽器跑非 JS 寫的程式碼，又不失去 Web 的安全模型？」

Google 的答案是 Native Client（NaCl），2008 年推出。NaCl 直接在瀏覽器跑原生 x86 / ARM 二進位，用軟體層 sandboxing 隔離。技術很強，但有兩個致命缺點：跟 CPU 架構綁定（不可攜）、與 Web 安全模型整合困難（其他瀏覽器不買單）。2013 年改良為 PNaCl（Portable NaCl），用 LLVM bitcode 解決可攜性，但仍只有 Chrome 支援。

Mozilla 走另一條路：asm.js（2013）。把 JS 語言子集（只用整數、避免 GC 物件）當成「JIT 友善的 typed assembly」，現有引擎就能跑，新引擎可以針對這個子集做 AOT 編譯。Emscripten 把 C/C++ 編譯到 asm.js 後，Unity、Unreal 引擎就能跑在瀏覽器裡。這證明了概念可行，但 asm.js 仍是文字格式，解析慢、體積大。

階段二：MVP 誕生（2015–2017）

2015 年 6 月，Mozilla、Google、Microsoft、Apple 四大瀏覽器廠商聯合宣布合作開發 WebAssembly。這個聯合宣告是 Web 史上少見的——通常標準制訂過程冗長且各有盤算，Wasm 是少數一開始就達成共識的案例。

共識的基礎是：asm.js 的設計是對的（typed、AOT-friendly），但格式應該是二進位而非文字 JS 子集；目標是所有語言而非只有 C/C++；安全模型要繼承 Web 既有的 same-origin policy 與沙箱。

2017 年 3 月，四大瀏覽器同時宣告 Wasm MVP（Minimum Viable Product）達成。MVP 包含的能力很基礎：

  • i32、i64、f32、f64 四種數值型別。
  • 線性記憶體（linear memory），預設一頁 64KB。
  • 函式匯入匯出（functions、tables）。
  • 結構化控制流（block、loop、if、br）。
  • JS API（在瀏覽器中載入、實例化 Wasm 模組）。

注意 MVP 沒有的東西：沒有字串、沒有 GC、沒有例外處理、沒有多執行緒、沒有 SIMD、沒有 64-bit 位址。這是刻意的——先把最小可用版本做出來、達成跨廠商共識，再慢慢演進。

階段三：W3C 標準化（2018–2019）

2018 年 W3C 成立 WebAssembly Working Group 與 Community Group。前者負責正式標準，後者讓更廣泛社群參與提案。2019 年 12 月 5 日，WebAssembly Core Specification 成為W3C Recommendation，正式成為與 HTML、CSS、JavaScript 平起平坐的 Web 第四個基礎標準。

這個時間點很重要——從那一天起，Wasm 不再是「實驗性瀏覽器功能」，而是與 HTML 同等地位的 Web 基礎建設。

階段四：跳出瀏覽器（2019–2022）

真正讓 Wasm 從「瀏覽器加速器」轉變為「通用 runtime」的關鍵，是 2019 年 3 月 Mozilla 發起的 WASI（WebAssembly System Interface）提案。WASI 定義了一組標準化、能力導向的系統呼叫介面，讓 Wasm 模組能跳出瀏覽器，跟檔案系統、網路、時鐘等資源互動。

WASI 出現後，整個生態才有了「為什麼要在伺服器端用 Wasm」的明確答案。Fastly Compute@Edge（2019 公測）、Cloudflare Workers（陸續加入 Wasm 支援）、Fermyon Spin（2022 開源）、wasmCloud（CNCF Sandbox 2021）等平台陸續出現，把 Wasm 當成比容器更輕的部署單位。

同期 2022 年 4 月，Wasm 2.0 成為 W3C Recommendation，新增：

  • SIMD：128-bit 向量運算指令，對影音編解碼、AI 推論有意義。
  • 多回傳值：函式可以回傳多個值，不必透過記憶體 workaround。
  • Reference types：引入 funcref、externref，為後續 GC 鋪路。
  • Bulk memory：批次記憶體操作指令（memory.copy、memory.fill）。
  • Non-trapping float-to-int conversions：浮點轉整數的安全版本。

階段五：Component Model 與 Wasm 3.0（2023–2026）

2.0 之後，社群把火力放在「讓 Wasm 真正成為通用元件」這個更大的目標上。兩條主線並行推進：

Component Model：核心 Wasm 的型別系統極簡（只有數值與記憶體位址），跨語言互通靠手動序列化，代價高。Component Model 引入 WIT（WebAssembly Interface Types）介面定義語言與 Canonical ABI，讓字串、列表、結構等高階型別變成 first-class。這條線到 2026 年仍未到 1.0，但 Wasmtime、wasmCloud、Spin 等實作已可生產使用。

Wasm 3.0：2025 年 9 月正式 live，是核心規格的重大躍進，把醞釀六到八年的提案一次整合：

  • GC（Garbage Collection）：原生 GC 支援，引入 struct、array、reference type 等 GC-managed 物件。對 Java、Kotlin、Dart、Scheme 等高階語言意義重大——過去它們要把整個 GC runtime 編進 .wasm，現在可以用宿主 GC。
  • Memory64：linear memory 與 table 可用 64-bit 位址，過去 4GB 上限解除。對 AI 推論、大型運算、邊緣 ML 是必要條件。
  • 例外處理（exception handling）：原生 try/catch/throw 指令，C++、Java、Swift 等語言不必再用 setjmp/longjmp 模擬。
  • Tail calls：尾呼叫優化原生支援，函式式語言（Scheme、OCaml、Haskell）的遞迴能常數空間執行。
  • Multiple memories：一個模組可宣告多塊 linear memory，過去只能有一塊。
  • Relaxed SIMD：在極致效能與跨平台可重現性間提供 deterministic profile 選項。
為什麼歷史很重要 理解 Wasm 的設計取捨，要知道它的歷史包袱。「為什麼線性記憶體預設這麼小」「為什麼一開始沒有字串型別」「為什麼能力導向設計」這些問題的答案都在歷史脈絡裡——從 NaCl 的失敗教訓、Web 安全模型的繼承、四大廠商共識的妥協而來。

1.3四種定位光譜

2026 年的 Wasm 有四個並行發展的「定位」，每個定位的技術重點、工具鏈、典型用例都不同。當有人說「我在用 Wasm」，要先問清楚他在哪一個定位上——不然很容易雞同鴨講。

定位一：瀏覽器內

核心命題：在 JS 引擎旁邊提供一個高效能執行通道，讓 CPU 密集工作能近原生速度跑。

技術重點：跟 JS 的互通（透過 WebAssembly JS API）、共享 ArrayBuffer、Web API 整合、源地圖支援。

代表用例：

  • Figma：渲染引擎、向量幾何運算用 Wasm，UI 用 React。
  • Photoshop Web：Adobe 把 30 年的 C++ codebase 用 Emscripten 編到 Wasm，在瀏覽器跑完整 Photoshop。
  • Google Earth：地理資料的渲染與運算。
  • AutoCAD Web：CAD 引擎以 Wasm 形式在瀏覽器執行。
  • 瀏覽器內 AI 推論：MediaPipe、ONNX Runtime Web、transformers.js 等讓模型在瀏覽器跑。
  • WordPress Playground：把整個 PHP 引擎編成 Wasm，瀏覽器內跑 WordPress。

主流引擎：V8（Chrome、Edge、Node.js）、SpiderMonkey（Firefox）、JavaScriptCore（Safari）。

定位二：伺服器 / 邊緣運算

核心命題：用比容器輕一到三個數量級的部署單位、近零冷啟動、能力導向安全，跑 serverless / edge function / microservice。

技術重點：WASI（Preview 1 → 2 → 3）、Component Model、HTTP server abstraction、KV / DB / object store 標準介面。

代表用例：

  • Fastly Compute@Edge：全球 PoP 部署 Wasm，微秒級冷啟動，原本 VCL 的進化版。
  • Cloudflare Workers：原本主跑 V8 isolates，現支援 Wasm，可混用 JS + Wasm。
  • Fermyon Spin / SpinKube：開源 Wasm serverless framework，K8s 原生。
  • wasmCloud：CNCF 沙箱專案，分散式 actor model，跨雲跨邊緣。
  • Vercel Edge Functions、Akamai EdgeWorkers、Netlify Edge Functions：各 CDN 邊緣平台。

主流引擎：Wasmtime、wazero、WasmEdge、Wasmer。

定位三：嵌入式 / IoT

核心命題：在資源受限的裝置上提供安全可更新的執行環境，取代 OTA 風險高的原生 firmware 更新。

技術重點：超低記憶體佔用（KB 級）、interpreter 而非 JIT、AOT 編譯支援、與 RTOS 整合。

代表用例：

  • 車載運算：Bosch、Continental 等汽車供應商用 Wasm 做 ECU 可更新邏輯。
  • 工業閘道：Siemens、ABB 在邊緣裝置上跑 Wasm 處理感測器資料。
  • Smart NIC / DPU：在網卡上跑 Wasm 做封包過濾、流量分析。
  • 區塊鏈節點：Polkadot、NEAR 用 Wasm 跑智能合約。

主流引擎：WAMR（WebAssembly Micro Runtime）、wasm3、WasmEdge。

定位四：應用內外掛系統

核心命題：讓既有應用支援第三方擴展，又不失去 process 隔離與資源控制。

技術重點：嵌入式 SDK（讓宿主應用方便載入 Wasm）、ABI 標準化（讓不同應用的外掛可重用）、生命週期管理。

代表用例：

  • Envoy / Istio filter：用 Wasm 寫 service mesh 的中介邏輯（auth、rate-limit、transform）。
  • Kong / APISIX plugin：API Gateway 的客製化邏輯。
  • 資料庫 UDF：CockroachDB、ScyllaDB、SingleStore 等用 Wasm 跑 user-defined function。
  • 遊戲 mod 系統：Veloren、Mindustry 等用 Wasm 給玩家寫 mod。
  • SaaS 客製化：Shopify Functions、Suborbital 等讓客戶用 Wasm 自訂業務邏輯。
  • Extism：通用多語言 Wasm 外掛框架。
不要混淆定位 Wasm 在不同定位下，能力預期、工具鏈、效能模型都不同。例如「在瀏覽器內」是輔助 JS 跑重運算，「在伺服器」是取代 container process，「在 IoT」是取代 firmware 邏輯。讀任何 Wasm 文章前先問：作者在講哪個定位？

W3C WebAssembly Working Group

負責什麼：制定 Wasm 核心規格的正式 W3C Recommendation。Wasm 1.0（2019）、Wasm 2.0（2022）、Wasm 3.0（2025）的 spec 都是這個 WG 通過的。

成員結構：由各大瀏覽器廠商代表組成，包括 Mozilla、Google、Microsoft、Apple、Intel、ARM、Fastly 等。決策需要跨廠商共識，過程慢但結果穩定。

產出物：

  • Core Specification（核心執行語意、binary format、validation 規則）
  • JavaScript API（瀏覽器內 JS 如何載入、實例化 Wasm）
  • Web API（瀏覽器 DOM、fetch 等如何與 Wasm 互動）

權威性：最高。被 W3C 接受的功能才是真正「標準化」的能力，瀏覽器與所有相容 runtime 都會實作。

W3C WebAssembly Community Group

負責什麼：提案孵化器。所有新功能（GC、Component Model、threads、SIMD、tail calls 等）都先在這裡用「proposal」形式公開，由社群成員協作演進，達到一定成熟度後才進入 Working Group 做最終標準化。

提案階段（共五階段）：

階段名稱含意
0Pre-Proposal初步想法，可能還在 GitHub issue 階段
1Feature Proposal有完整 motivation 文件、初步 spec sketch
2Proposed Spec Text有正式 spec 文字，可開始實作參考實作
3Implementation Phase多個獨立實作完成，跑 test suite
4Standardize the Feature合併進 main spec，準備下一版 W3C Recommendation

如何追蹤：github.com/WebAssembly/proposals 列出所有提案與其階段。當有新聞說「Wasm 加入 X 功能」，可以先去這個列表看 X 在哪個 stage，stage 3 以下的功能不要在生產採用。

Bytecode Alliance

背景：2019 年由 Mozilla、Fastly、Intel、Red Hat 共同創立，2021 年成為非營利組織，定位是「致力於用 Wasm 與 WASI 建構安全、高效、模組化的軟體基礎」。

負責什麼：

  • WASI 提案開發：WASI 雖然有自己的 GitHub 組織，實際開發主力在 Bytecode Alliance 旗下。
  • Component Model 設計與實作：包括 WIT 語言、Canonical ABI、wit-bindgen 工具。
  • Wasmtime 開源 runtime：業界事實標準的 Wasm runtime，Rust 寫的。
  • WAMR：嵌入式場景的輕量 runtime。
  • 工具鏈生態：cargo-component、wasm-tools、jco（JS component tools）等。

成員：超過 35 個組織，包括 Microsoft、Google、Amazon、ByteDance、Arm、NVIDIA、Cisco、Shopify、Fermyon、Fastly、Cloudflare、Adobe 等。

權威性：在「Wasm 在瀏覽器外」的領域，Bytecode Alliance 是事實標準制定者。WASI 與 Component Model 雖然不是 W3C 標準（W3C 只管瀏覽器內），但被廣泛採用。

CNCF（Cloud Native Computing Foundation）

負責什麼：把 Wasm 整合進 cloud-native 生態，作為容器與虛擬機之外的第三種部署單位。

旗下 Wasm 相關專案：

  • wasmCloud（Incubating）：分散式 actor model，跨雲跨邊緣的 Wasm 平台。
  • WasmEdge（Sandbox）：邊緣與 AI 推論場景的 runtime。
  • SpinKube（Sandbox）：把 Spin 應用以 K8s CRD 形式部署。
  • Krustlet（Archived）：早期把 Wasm 當 K8s first-class workload 的 kubelet 替代，已被 containerd shims 取代。

權威性：在 K8s 與 cloud-native 整合層面是主要治理者。CNCF 採用一個專案後，企業採用率明顯提升。

其他重要組織

  • Fermyon：Spin 與 SpinKube 的母公司，由前 Microsoft / Deis Labs 團隊創立，是「Wasm serverless 為主」這個概念的最積極推動者。
  • Cosmonic：wasmCloud 的母公司，提供商業託管版本。
  • Fastly：Compute@Edge 的提供者，對 Wasm 早期生態貢獻巨大，許多核心開發者來自這裡。
  • Cloudflare：Workers 平台支援 Wasm，主推 V8 isolates + Wasm 混合架構。
判斷新聞權威性的小技巧 看到 Wasm 相關新聞時，先看消息源：W3C 公告 > Bytecode Alliance blog > CNCF 公告 > runtime 廠商 blog > 一般技術媒體。新聞中提到的功能要對照 proposal 階段，stage 3 以下都還不能視為穩定。

1.62026 年生態現況與趨勢

本章寫作於 2026 年 5 月。基於 Bytecode Alliance、CNCF、各 runtime 廠商的最新發布，整理三個值得關注的趨勢。

趨勢一：Component Model 邁向 1.0

Component Model 是讓 Wasm 真正成為「跨語言通用元件」的關鍵基礎建設。截至 2026 年 5 月，Component Model 仍未到 1.0，但已有以下進展：

  • Wasmtime、wasmCloud、Spin 都支援 WASIp2 + Component Model 的生產級應用。
  • wit-bindgen 對 Rust、JS、Python、Go（含 TinyGo）的綁定產生器都已 stable。
  • wac（WebAssembly Compositions）工具讓多個 component 可以聲明式組合。
  • OCI registry 開始支援 Wasm component 作為 first-class artifact（透過 wkg）。

Component Model 1.0 預計在 2026 下半年發布，這將是 Wasm「Docker moment」的最後一塊拼圖。完成後，企業可以放心地把跨語言 component 部署到任何遵循標準的 runtime。

趨勢二：WASI Preview 3 與 native async

WASIp2 在 2026 年初進入 stable 狀態，主要 world（wasi:cli、wasi:http、wasi:sockets、wasi:keyvalue、wasi:logging）都已可生產使用。但 WASIp2 仍有一個重要缺口：缺乏 native async 模型。

目前 Wasm component 處理 async 操作要靠 callback、polling、或 host 端的協程。WASIp3 引入 native async + Future / Stream 型別到 Component Model，讓 component 可以直接寫 async/await 風格的程式碼。

WASIp3 在 2025-11 進入 RC，預計 2026 下半年 stable。生產採用建議仍以 WASIp2 為主，密切觀察 WASIp3 對 component 介面的影響。

趨勢三：K8s 整合的標準化

過去把 Wasm 部署到 K8s 有多種做法（Krustlet、各家自訂 CRD），現在事實標準已經形成：

  • containerd-wasm-shims（Microsoft + Fermyon + Docker）讓 containerd 直接執行 .wasm，K8s 用 runtimeClassName 就能切換。
  • runwasi 作為底層共用函式庫，所有 shim 都基於此。
  • SpinKube 與 wasmCloud K8s Operator 各提供高階抽象。
  • OCI image spec 已正式支援 Wasm artifact，registry 可同時存放容器與 Wasm。

這個整合層的成熟，讓「Wasm 在 K8s 上跟容器並存」從實驗變成生產可選方案。CNCF 2025 年的 survey 顯示，有 19% 的 cloud-native 採用者已在生產中跑 Wasm，比 2024 年的 12% 顯著成長。

仍未解決的挑戰

誠實地說，Wasm 在 2026 仍有幾個未解難題：

  • 瀏覽器內 DOM 存取：仍需透過 JS 中介，component model 整合 Web API 的提案還在討論。
  • 跨 runtime 的 component 可攜性：理論上 component 該跨 runtime，實際上 host capabilities 差異仍導致行為不一致。
  • Debug 工具鏈不均：Rust + Wasmtime debug 體驗好，其他組合（Go + wazero、AssemblyScript + 任何 runtime）還有差距。
  • 記憶體共享：threads 提案進度緩慢，Wasm 內部多執行緒模型仍需 host 配合，跨 component 共享記憶體更難。
給生產採用的建議 2026 採用 Wasm 的安全選擇是：使用 Wasmtime 或 wazero、基於 WASIp2 設計、避開 Component Model 中尚在演進的功能、把 Wasm 當「比容器更輕的部署單位」而不是「替代既有架構」。等 Component Model 1.0 與 WASIp3 stable 後，再評估更大膽的整合。

Module 01 · 10 題自我測驗

Q1.下列何者最精準地描述 WebAssembly？
  • 一種比 JavaScript 更快的瀏覽器腳本語言
  • 一種低階二進位指令格式，作為跨語言、跨平台的可攜編譯目標
  • 一種類似 Docker 的容器化技術
  • 一種專為 Rust 設計的虛擬機
看解答
答案 · B Wasm 不是腳本語言（A 錯）、不是容器替代品（C 錯，粒度不同）、也不專屬 Rust（D 錯，是語言中立的目標）。B 是 W3C 官方定義的精神：portable compilation target。
Q2.Wasm 1.0 成為 W3C Recommendation 的年份是？
  • 2015
  • 2017
  • 2019
  • 2022
看解答
答案 · C 2015 是四大瀏覽器聯合宣告合作；2017 是 MVP 達成；2019-12-05 才正式成為 W3C Recommendation；2022 是 Wasm 2.0 成為 Recommendation。
Q3.Wasm 3.0（2025-09）加入下列哪些重要功能？（複選）
  • 原生 GC 支援
  • 64-bit linear memory（memory64）
  • 原生 try/catch 例外處理
  • DOM 直接存取
  • Tail call 優化
看解答
答案 · A、B、C、E Wasm 3.0 加入 GC、memory64、exception handling、tail calls、multiple memories、relaxed SIMD 等。D 錯——DOM 直接存取仍未進入規格，目前仍需透過 JS 中介，且這項是否該屬於 Wasm 本身仍有爭議。
Q4.下列哪個組織負責 W3C Recommendation 級別的 Wasm 標準制定？
  • Bytecode Alliance
  • W3C WebAssembly Working Group
  • CNCF
  • Fermyon
看解答
答案 · B W3C WG 制定正式 Recommendation。Bytecode Alliance 負責 WASI、Component Model、Wasmtime 等開源實作；CNCF 負責 cloud-native 整合；Fermyon 是公司，主推 Spin。
Q5.關於 Wasm 提案（proposals）的階段，下列敘述何者正確？
  • 所有 stage 1 的提案都已可在主流瀏覽器使用
  • stage 4 表示提案合併進 main spec，準備下一版 Recommendation
  • 提案階段共有 10 個
  • 提案不需要多個獨立實作就能進入 stage 4
看解答
答案 · B 提案共 5 個階段（0–4）。stage 4 確實是「合併進 main spec」。stage 1 只是有完整 motivation 文件，離可用還很遠（A 錯）。進入 stage 4 需要多個獨立實作完成（D 錯）。
Q6.WASI 主要解決什麼問題？
  • 讓 Wasm 在瀏覽器跑得更快
  • 為 Wasm 提供標準化、能力導向的系統介面，讓它能跳出瀏覽器
  • 讓 Wasm 取代 JavaScript
  • 讓 Wasm 跟 JVM 互通
看解答
答案 · B WASI（WebAssembly System Interface）2019 年由 Mozilla 提出，目的就是讓 Wasm 跳出瀏覽器，跟檔案、網路、時鐘等系統資源互動，採能力導向設計。
Q7.下列何者「不是」Wasm 在 2026 年的典型生產定位？
  • 瀏覽器內加速 CPU 密集運算（如 Figma、Photoshop Web）
  • 邊緣 Serverless function（如 Fastly Compute）
  • 直接執行 OS 系統呼叫，繞過宿主 runtime
  • 應用內外掛系統（如 Envoy filter）
看解答
答案 · C Wasm 預設無 ambient access，所有系統能力都必須由宿主明確匯入（capability-based），沒有「繞過宿主」這個選項——這正是 Wasm 安全模型的根本。A、B、D 都是當前生產定位。
Q8.下列何者最能說明 Wasm 與容器（Container）的差異？
  • Wasm 比容器更安全，所以容器會被淘汰
  • 兩者粒度不同：容器打包 OS userspace + 程式，Wasm 模組只打包程式邏輯，OS 能力來自宿主
  • Wasm 是容器的子集
  • 兩者完全等價，只是格式不同
看解答
答案 · B 粒度不同是核心差異。實務上 Wasm 通常跑在容器內或取代容器內的 process，而不是取代整個容器層。兩者長期會並存，各有適用場景。
Q9.下列哪個 runtime 是 CNCF 沙箱 / 孵化專案？（複選）
  • Wasmtime
  • wasmCloud
  • WasmEdge
  • wazero
  • SpinKube
看解答
答案 · B、C、E wasmCloud（Incubating）、WasmEdge（Sandbox）、SpinKube（Sandbox）屬於 CNCF。Wasmtime 屬於 Bytecode Alliance；wazero 由 tetratelabs 維護，未加入 CNCF。
Q10.2026 年若要為生產環境採用 Wasm，下列何者是最穩健的選擇？
  • 使用 stage 2 提案的功能，搶先採用
  • 使用 Wasmtime 或 wazero、基於 WASIp2 設計，避開仍在演進的 Component Model 功能
  • 把所有 microservice 立刻改寫為 Wasm
  • 使用 Krustlet 部署到 K8s
看解答
答案 · B 2026 採用 Wasm 的穩健策略：成熟 runtime（Wasmtime / wazero）+ 穩定 WASI 版本（Preview 2）+ 避開仍在 churn 的功能。A 風險太高；C 沒考慮成本與適用性；D Krustlet 已被 archive，請用 containerd-wasm-shims。
