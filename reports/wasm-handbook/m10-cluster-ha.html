10.1HA 設計核心原則

Wasm HA 架構建立在一個原則上：實例本身設計成無狀態、可隨時銷毀重建，狀態外置到共享儲存。這個原則跟 12-factor app 一脈相承，但 Wasm 把它推到極致——instance 的銷毀重建不是「優化」，而是常態操作。

三個基本原則

  1. Stateless instance：每個 Wasm instance 不持有任何「重要」狀態。重要狀態在 Redis、Postgres、S3、KV store。
  2. Idempotent operation：所有對外操作可重試。配合 instance 可隨時被銷毀重建。
  3. Cheap to create：建立新 instance 的成本（µs 級）讓我們可以「per-request instance」——每個請求一個全新 instance，請求結束銷毀。

  • Cloudflare / Fastly：全球 anycast LB
  • AWS ALB / GCP LB：雲端 managed LB

Wasm 特有的 LB 考量

Consistent hashing 對 instance cache 命中率：

Wasm runtime 通常有 module compile cache（AOT 編譯結果）。如果用 round-robin LB，同一個 Wasm app 的請求可能分到不同 node，每個 node 都要重新編譯該 module。用 consistent hashing（基於 Wasm app id）讓同 app 的請求黏在同 node，命中率高。

10.3Instance Pool 模式

Wasm instantiate 即使快，仍有微秒級成本。Instance pool 是 Wasm runtime 常見的優化——預先建一批 instance 等請求使用。

兩種模式

模式說明權衡
Per-request instance每個請求 new 一個 instance，用完丟棄完美隔離、無狀態污染；instantiate cost 高
Reused from pool從 pool 拿、用完歸還低延遲、低 CPU；要小心重置狀態

Go + wazero 實作

go 
type WasmPool struct {
    instances chan api.Module
    runtime   wazero.Runtime
    compiled  wazero.CompiledModule
    config    wazero.ModuleConfig
    maxSize   int

    metrics struct {
        sync.Mutex
        created   int64
        destroyed int64
        gets      int64
        puts      int64
        oversize  int64
    }
}

func NewPool(ctx context.Context, r wazero.Runtime,
              compiled wazero.CompiledModule, size int) *WasmPool {
    p := &WasmPool{
        instances: make(chan api.Module, size),
        runtime:   r,
        compiled:  compiled,
        config:    wazero.NewModuleConfig(),
        maxSize:   size,
    }
    // 預熱
    for i := 0; i < size; i++ {
        inst, _ := r.InstantiateModule(ctx, compiled, p.config)
        p.instances <- inst
        p.metrics.Lock()
        p.metrics.created++
        p.metrics.Unlock()
    }
    return p
}

func (p *WasmPool) Get(ctx context.Context) api.Module {
    p.metrics.Lock()
    p.metrics.gets++
    p.metrics.Unlock()

    select {
    case inst := <-p.instances:
        return inst
    default:
        // 池空，現場建立
        inst, _ := p.runtime.InstantiateModule(ctx, p.compiled, p.config)
        p.metrics.Lock()
        p.metrics.created++
        p.metrics.Unlock()
        return inst
    }
}

func (p *WasmPool) Put(inst api.Module) {
    p.metrics.Lock()
    p.metrics.puts++
    p.metrics.Unlock()

    select {
    case p.instances <- inst:
        // 歸還成功
    default:
        // 池滿，丟棄
        inst.Close(context.Background())
        p.metrics.Lock()
        p.metrics.oversize++
        p.metrics.destroyed++
        p.metrics.Unlock()
    }
}

func (p *WasmPool) Stats() map[string]int64 {
    p.metrics.Lock()
    defer p.metrics.Unlock()
    return map[string]int64{
        "created":   p.metrics.created,
        "destroyed": p.metrics.destroyed,
        "gets":      p.metrics.gets,
        "puts":      p.metrics.puts,
        "available": int64(len(p.instances)),
    }
}

Wasmtime 的 PoolingAllocator

Wasmtime 內建 pooling allocator，比手刻 pool 更高效——直接管理 instance 的記憶體 layout，減少分配 / 釋放開銷。

rust 
use wasmtime::*;

let mut config = Config::new();

// 啟用 pooling allocator
let mut pool_config = PoolingAllocationConfig::default();
pool_config.total_memories(1000);       // 最多同時 1000 個記憶體
pool_config.total_core_instances(1000);
pool_config.max_memory_size(64 * 1024 * 1024); // 每個 instance 上限 64MB

config.allocation_strategy(InstanceAllocationStrategy::Pooling(pool_config));

let engine = Engine::new(&config)?;

狀態污染問題

Reused instance 最大的坑：上次請求遺留的狀態（global、static、heap）可能洩漏到下次請求。處理策略：

  • Wasm 內顯式 reset：每次 invoke 開始呼叫 reset() 函式清空 global state
  • 每 N 次 invoke 銷毀重建：限制 instance 使用次數，超過就 drop
  • 用 component 替代 module：component 每次 invoke 預設邊界清晰，較不易洩漏
  • 關鍵業務用 per-request：對安全敏感場景接受高 cost 換完美隔離

10.4AOT 快取

Wasm runtime 把 .wasm 編譯到原生碼是有成本的——對大模組可能要幾秒。AOT 編譯把這個成本搬到部署前。

Wasmtime AOT 流程

bash 
# 預編譯
wasmtime compile module.wasm -o module.cwasm

# 執行時直接 load .cwasm，跳過 JIT
wasmtime run --allow-precompiled module.cwasm

跨 node 共用 AOT cache

K8s 環境的最佳實踐：

  1. CI/CD pipeline 把 .wasm 編譯成 .cwasm
  2. 把 .cwasm 推到 OCI registry（與 .wasm 一起）
  3. 每個 node 拉 .cwasm，啟動極快
AOT 與 CPU 架構綁定 AOT 編譯的 .cwasm 跟「目標 CPU 架構 + Wasmtime 版本」綁定。x86_64 編的不能跑在 ARM。CI 要為每個目標架構各編一份，或在每個 node 第一次啟動時 lazy compile。

Wasmtime 的 incremental cache

Wasmtime 2.x 起支援 incremental cache——記住已編譯的函式單元，相似 module 共用編譯結果。實務上不必手動管理，runtime 內部處理。

10.5健康檢查兩層設計

K8s 標準的 liveness / readiness probe 仍適用，但 Wasm 要在 process 層之外多一層應用層檢查。

兩層意義

層級K8s 對應檢查什麼
Process layerlivenesshost process 還活著、能回應 HTTP
Runtime layerreadinessWasm pool 可用、AOT cache 載入、能成功 invoke 一個 noop wasm

實作範例

go 
// 兩層 probe
func livenessHandler(w http.ResponseWriter, r *http.Request) {
    // process 還在跑就是 alive
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("alive"))
}

func readinessHandler(pool *WasmPool) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // 1. pool 有可用 instance
        stats := pool.Stats()
        if stats["available"] == 0 {
            http.Error(w, "pool empty", http.StatusServiceUnavailable)
            return
        }

        // 2. 能 invoke noop 函式
        ctx, cancel := context.WithTimeout(r.Context(), 100*time.Millisecond)
        defer cancel()

        inst := pool.Get(ctx)
        defer pool.Put(inst)

        noop := inst.ExportedFunction("noop")
        if noop == nil {
            http.Error(w, "noop not found", http.StatusServiceUnavailable)
            return
        }

        _, err := noop.Call(ctx)
        if err != nil {
            http.Error(w, fmt.Sprintf("noop failed: %v", err),
                       http.StatusServiceUnavailable)
            return
        }

        w.WriteHeader(http.StatusOK)
        w.Write([]byte("ready"))
    }
}

10.6故障處理

OOM 處理

Wasm linear memory 上限可由 runtime 配置強制。超過時 wasm 內 alloc 會回 -1 或 trap。單一 instance 超量不影響 host process，這是 Wasm 隔離的優勢。

go 
// wazero 限制每 instance 最多 128 MiB
config := wazero.NewRuntimeConfig().
    WithMemoryLimitPages(2048) // 2048 × 64KB = 128 MiB
r := wazero.NewRuntimeWithConfig(ctx, config)

// 失敗時 trap，宿主收到錯誤
result, err := fn.Call(ctx, args...)
if err != nil {
    if errors.Is(err, wasmtime.OutOfMemory) {
        // 紀錄 metric、回 503、丟棄 instance、不要 putBack
        metric.Inc("wasm.oom")
        http.Error(w, "out of memory", 503)
        return
    }
}

Fuel 用盡（Wasmtime）

rust 
store.set_fuel(10_000_000)?;

match func.call(&mut store, args) {
    Ok(result) => result,
    Err(e) if e.is_trap() && e.downcast_ref::<Trap>()
                  == Some(&Trap::OutOfFuel) => {
        // CPU 超量
        return Err(StatusCode::TooManyRequests);
    }
    Err(e) => return Err(internal_error(e)),
}

Circuit breaker 在 host 層

Wasm 透過宿主 outbound 呼叫下游時，加 circuit breaker 保護下游：

go 
type Breaker struct {
    mu        sync.Mutex
    failures  int
    threshold int
    openUntil time.Time
    cooldown  time.Duration
}

func (b *Breaker) allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    if time.Now().Before(b.openUntil) {
        return false
    }
    return true
}

func (b *Breaker) record(success bool) {
    b.mu.Lock()
    defer b.mu.Unlock()
    if success {
        b.failures = 0
        return
    }
    b.failures++
    if b.failures >= b.threshold {
        b.openUntil = time.Now().Add(b.cooldown)
        b.failures = 0
    }
}

// 用在 host function
var apiBreaker = &Breaker{threshold: 5, cooldown: 30 * time.Second}

func hostOutboundHTTP(ctx context.Context, m api.Module,
                       urlPtr, urlLen uint32) uint32 {
    if !apiBreaker.allow() {
        return 0 // circuit open
    }

    url := readStr(m, urlPtr, urlLen)
    resp, err := http.Get(url)
    apiBreaker.record(err == nil)

    if err != nil { return 0 }
    // ...
}

Graceful shutdown

SIGTERM 時的標準流程：

sequenceDiagram
    participant K as K8s
    participant H as Host Process
    participant LB as Load Balancer
    participant W as Wasm Instances

    K->>H: SIGTERM
    H->>H: readiness probe → false
    Note over LB: 30s 後移除此 endpoint
    LB->>H: 停止送新請求
    H->>H: 等正在執行的 invoke 完成
timeout 例如 30s
    H->>W: Close all instances
    H->>K: exit 0
Figure 10.2 · Graceful shutdown 流程
go 
func main() {
    pool := NewPool(...)
    ready := atomic.Bool{}
    ready.Store(true)

    mux := http.NewServeMux()
    mux.HandleFunc("/health/ready", func(w http.ResponseWriter, r *http.Request) {
        if !ready.Load() {
            http.Error(w, "shutting down", 503)
            return
        }
        // ... 正常 ready check
    })
    mux.HandleFunc("/", wasmHandler(pool))

    server := &http.Server{Addr: ":8080", Handler: mux}

    // 監聽 SIGTERM
    sigCh := make(chan os.Signal, 1)
    signal.Notify(sigCh, syscall.SIGTERM, syscall.SIGINT)

    go func() {
        if err := server.ListenAndServe(); err != http.ErrServerClosed {
            log.Fatal(err)
        }
    }()

    <-sigCh
    log.Println("received SIGTERM, starting graceful shutdown")

    // 1. readiness 變 false，LB 開始排除
    ready.Store(false)

    // 2. 等 30s 讓 LB 真的把流量切走
    time.Sleep(30 * time.Second)

    // 3. 停止 HTTP server，等 active request 完成（最多 30s）
    shutdownCtx, cancel := context.WithTimeout(
        context.Background(), 30*time.Second)
    defer cancel()
    server.Shutdown(shutdownCtx)

    // 4. 關閉 pool
    pool.Close()

    log.Println("shutdown complete")
}

10.8Wasm HA 相對於容器的優勢

本章最後總結 Wasm HA 的真實效益。

面向容器Wasm
冷啟動數秒微秒到低毫秒
實例密度10-100 / node1000-10000 / node
故障半徑整個 container單一 wasm 實例（µs 級）
Scale-to-zero有冷啟動成本，需 keep-warm幾乎無感
記憶體開銷MB 級 baselineKB 級 baseline
OOM 隔離整個 container OOM kill單一 instance trap，host 繼續
跨 OS 部署每 OS 一個 image單一 .wasm 跨平台
Image size10MB - 1GB50KB - 5MB

密度的真實意義

Fermyon 2025 公開的數據：他們的邊緣平台每秒處理 7500 萬次請求，這個密度在容器架構上不可能達成。密度 100 倍意味著服務同等流量的硬體成本降低 100 倍。

故障半徑的真實意義

當你的應用每 node 跑 1000 個 instance，一個 instance crash 影響的「客戶」少 100 倍。傳統容器一個 OOM 影響該 process 處理的所有流量；Wasm OOM 只影響當下那個 instance。

Scale-to-zero 的真實意義

傳統 serverless 為避免冷啟動懲罰要 keep-warm，閒置時仍有最低成本。Wasm scale-to-zero 真實可用——閒置時零成本，請求進來 µs 級恢復。這對 long tail 應用（每天幾百次請求）特別有意義。

  4. 實作 canary deployment：先 5% 流量到 v2，觀察 metric 後逐步擴大。

QUIZ章末自我評估

Module 10 · 10 題自我測驗

Q1.Wasm HA 設計的核心原則是？
  • 儘量保留 instance 狀態
  • Wasm instance 設計為 stateless、idempotent、cheap to create，狀態外置
  • 用 sticky session 保證同 client 連同 instance
  • 每 node 跑越少 instance 越好
看解答
答案 · B Wasm HA 與 12-factor 一脈相承——stateless、idempotent、可隨時 reschedule。Wasm 把這個原則推到極致：instance 銷毀重建是常態。
Q2.用 consistent hashing 而非 round-robin LB 的好處是？
  • 效能更高
  • 同 Wasm app 的請求黏在同 node，AOT cache 命中率高
  • 負載更均勻
  • 支援更多 client
看解答
答案 · B Wasm runtime 有 module compile cache，consistent hashing 讓同 app 請求黏在同 node，避免每個 node 都要重編譯。
Q3.下列關於「instance pool reuse」，何者正確？
  • 完全無風險
  • 效能高，但要處理「上次請求遺留狀態洩漏」問題
  • 比 per-request instance 更安全
  • 會增加冷啟動時間
看解答
答案 · B Reuse 省了 instantiate cost，但要處理狀態污染：上次留下的 global、static、heap 可能洩漏到下次。處理方式包括 reset 函式、定期銷毀、用 component 替代 module。
Q4.AOT 編譯（wasmtime compile）的好處是？
  • 減少 binary 大小
  • 把 JIT 編譯成本搬到部署前，啟動時直接 load 原生碼
  • 提高執行效能
  • 取代 Wasm runtime
看解答
答案 · B AOT 在 CI/CD 預先編譯成 .cwasm，省 runtime JIT 階段。代價是 .cwasm 跟 CPU 架構 + runtime 版本綁定。
Q5.Wasm host 的「兩層健康檢查」分別檢查什麼？
  • CPU 與記憶體
  • Liveness（host process 還活著）+ Readiness（Wasm pool 可用、能 invoke noop）
  • 入站與出站
  • 同步與非同步
看解答
答案 · B Wasm 多一層應用級檢查——光是 host process 活著還不夠，要確認 runtime 能成功 invoke。
Q6.Wasm instance OOM 的影響是？
  • 整個 host process crash
  • 該 instance trap，host process 繼續服務其他 instance 的請求
  • 整個 node 重啟
  • 資料庫斷線
看解答
答案 · B Wasm 沙箱保證 instance 故障不影響 host——這正是 Wasm 故障半徑小的根本。OOM 的 instance trap，host 紀錄、回 503，丟棄該 instance。
Q7.Graceful shutdown 的正確順序是？
  • 直接 exit
  • readiness 變 false → 等 LB 排除 → 等 active request 完成 → 關閉 pool → exit
  • 先 kill 所有 instance 再退出
  • 關閉 HTTP server → exit
看解答
答案 · B 關鍵：先讓 LB 知道「我要下線」（readiness false），等流量切走，再處理進行中請求，最後清理資源。
Q8.Wasm 相對於容器的「實例密度」典型差異？
  • 差不多
  • 容器較高
  • Wasm 可達容器的 10-100 倍
  • 取決於語言
看解答
答案 · C Fermyon 公開測試證實這個量級差距。Wasm 無 OS userspace、記憶體 baseline KB 級，單 node 跑 1000-10000 instance 可行。
Q9.跨區資料同步建議的選擇是？
  • 手動 rsync 檔案
  • CockroachDB / Spanner / DynamoDB Global Tables 等原生分散式 DB
  • 用單一 SQLite 檔
  • 每個 region 用獨立 DB，不同步
看解答
答案 · B 跨區 active-active 需要原生分散式 DB。CockroachDB、Spanner、DynamoDB Global Tables 都是常見選擇，提供強一致或最終一致保證。
Q10.下列何者是「Wasm scale-to-zero 真正可用」的根本原因？
  • Wasm 比較便宜
  • µs 級冷啟動讓「從零起步」幾乎無感，不需 keep-warm
  • K8s 自動處理
  • runtime 自動快取
看解答
答案 · B 傳統 serverless 為避免數百毫秒冷啟動，必須 keep-warm（無流量也有最低成本）。Wasm 冷啟動 µs 級，scale-to-zero 真的可以「零成本」，長尾流量場景特別有意義。
