2.1Stack Machine vs Register Machine

Wasm 採用 stack-based 虛擬機執行模型，這是它與許多現代 VM（如 Dalvik、LLVM IR）的根本差異。理解這個選擇背後的權衡，能幫你建立對 Wasm 效能特性的正確直覺。

兩種虛擬機模型

Stack machine：所有運算操作堆疊上的值。要做 a + b，先把 a push 上堆疊，再把 b push 上堆疊，然後執行 add——它從堆疊頂部取兩個值、相加、把結果 push 回去。指令本身不需要指定操作對象，因為對象隱含是「堆疊頂部」。

Register machine：所有運算指定虛擬暫存器。要做 a + b，指令長得像 add r3, r1, r2——明確指出從 r1 與 r2 取值、結果放 r3。

為什麼 Wasm 選 stack machine

主要有四個原因：

  1. 更小的編碼：指令不必編碼暫存器號碼，binary 體積較小。對需要透過網路下載的 Wasm 來說，這是關鍵指標。
  2. 解碼速度快：解析器不必處理暫存器分配，啟動時的驗證階段更快。
  3. 易於驗證：堆疊狀態可以靜態追蹤，型別檢查與安全驗證相對單純。
  4. 歷史延續：JVM、CLR 都採 stack machine，社群有大量現成設計與實作經驗。

效能不是問題

有人會擔心 stack machine 是不是比 register machine 慢。實際上不會——現代 Wasm runtime 都會做 JIT 或 AOT 編譯，把 stack machine 指令轉成原生機器碼，編譯時會做暫存器分配。stack 只是 binary 格式的「中間表示」，最終跑在 CPU 上的還是原生程式碼。

關鍵心智模型 Wasm 的 stack 是「source IR 的編碼形式」，不是「執行時的真實 stack」。執行時 stack 會被 runtime 編譯掉，跟著走的是原生暫存器分配。

四種數值型別

Wasm 1.0 / 2.0 原生支援四種數值型別：

Wasm 2.0 加入 v128（128-bit SIMD vector）。Wasm 3.0 加入更多 reference types 與 GC types（後續章節詳述）。注意 Wasm 沒有原生的字串、bool、char、struct 型別——這些都要靠線性記憶體與序列化來實作。

2.2Module 與 Instance 的對應關係

Wasm 有兩個容易混淆的概念：module（模組）與 instance（實例）。理解兩者的差異對寫宿主程式、設計實例池都很重要。

Module：靜態的部署單位

Module 是「編譯後的 .wasm 檔案」對應的概念。它包含：

  • Type section：宣告所有函式簽章（function signatures）。
  • Import section：宣告需要從宿主匯入的函式、記憶體、table、global。
  • Function section：函式定義（指令序列）。
  • Memory section：宣告 linear memory 大小（初始與上限）。
  • Table section:宣告 table（存放函式參考等）。
  • Global section：全域變數。
  • Export section：對外開放給宿主呼叫的函式 / 資源。
  • Start section：選擇性的啟動函式（實例化時自動執行）。
  • Element / Data section：table 與 memory 的初始值。
  • Custom section：自訂資料（如 debug info、name section）。

Module 是不可變的，可以序列化、複製、AOT 編譯後快取。它本身無法執行——它只是執行所需資訊的藍圖。

Instance：執行時的動態實體

Instance 是 module 的「具體執行個案」，由宿主呼叫 instantiate 操作從 module 產生。產生時需要：

  • 提供所有 import 對應的實際值（宿主函式、記憶體、global 等）。
  • 分配 linear memory（一塊新的 byte array）。
  • 初始化 table、global 的值。
  • 執行 start function（如果有）。

一個 module 可以實例化多次，每個 instance 有自己獨立的記憶體、global 狀態，互不影響。這對「per-request instance」這種輕量隔離模型很關鍵。

2.3線性記憶體（Linear Memory）

Wasm 的記憶體模型是這個技術最具特色的設計之一。理解它能幫你判斷「為什麼字串要這樣傳」「為什麼宿主能讀取 Wasm 記憶體」「為什麼 Wasm 模組之間預設無法共享資料」。

什麼是線性記憶體

每個 Wasm instance 配有一塊（Wasm 3.0 後可多塊）連續的位元組陣列，稱為 linear memory。它的特性：

  • 單一連續位址空間：從位址 0 開始，最大 4GB（Wasm 1.0/2.0）或 16EB（Wasm 3.0 with memory64）。
  • 頁式管理：以 64KB 為一頁，可動態 grow（透過 memory.grow 指令）。
  • Instance 獨佔：每個 instance 有自己的記憶體，預設不共享。
  • Wasm 可讀寫：模組內所有 load/store 指令都對這塊記憶體操作。
  • 宿主也可讀寫：宿主拿到 instance 物件後，可以直接讀寫這塊記憶體（這是 import/export 字串時的機制）。
  • Wasm 無法讀宿主記憶體：模組內的指令無法讀取宿主程序的其他記憶體區域——這是沙箱隔離的根本。

頁式增長

記憶體以頁（page）為單位增長，一頁 = 65536 bytes（64KB）。Wasm 指令 memory.grow N 會增加 N 頁，回傳增加前的頁數（如果失敗回傳 -1）。

wat 
;; 宣告 memory，初始 1 頁，上限 10 頁
(memory $mem 1 10)

;; 增加 2 頁
(memory.grow (i32.const 2))
;; 此時記憶體變成 3 頁，stack 上是舊頁數 1

沒有原生指標的指標

Wasm 沒有「指標」這個 first-class 型別。所謂的「指標」就是 i32（或 i64 with memory64）的記憶體位址。C/C++ 編譯到 Wasm 時，指標都被編碼為 i32。

wat 
;; 從位址 100 讀一個 i32
i32.const 100
i32.load
;; stack 上現在是位址 100 處的 4 個 byte 解讀為 i32

;; 把 42 寫到位址 200
i32.const 200
i32.const 42
i32.store

字串怎麼傳？

因為 Wasm 沒有字串型別，字串傳遞要靠約定：

  1. Wasm 模組把字串資料寫到自己的 linear memory（例如位址 100，長度 5）。
  2. 呼叫宿主函式時，傳兩個 i32 參數：指標（100）、長度（5）。
  3. 宿主拿到這兩個值後，從 instance 的記憶體讀取 byte 100 到 104，解碼為 UTF-8 字串。

這就是為什麼很多 Wasm host function 看起來像 func(ptr: i32, len: i32) -> ...——這是傳字串的 idiom。Component Model 把這個 idiom 封裝成 first-class 的 string 型別（後續章節 M07 詳述）。

記憶體訪問安全 Wasm 的記憶體訪問是邊界檢查的（bounds-checked）。如果指令存取超出記憶體範圍的位址，會 trap（中止執行）。這個檢查是 Wasm 安全保證的關鍵——不像 C 的 buffer overflow 可以讀寫任意記憶體。

2.4匯入與匯出

Wasm 模組的「邊界」由匯入（imports）與匯出（exports）定義。這是宿主與 Wasm 互動的唯一管道，也是 Wasm 安全模型的物理基礎。

四種可匯入匯出的東西

類型說明典型用途
Function函式呼叫宿主能力、暴露邏輯給宿主
Memorylinear memory多個模組共享記憶體（少見）
Table函式參考表實作 vtable、function pointer
Global全域變數共享狀態、設定值

命名空間

每個 import 用兩個字串標識：module name（命名空間）與 field name（具體名稱）。例如：

wat 
(import "env" "log" (func $log (param i32 i32)))
(import "wasi_snapshot_preview1" "fd_write"
        (func $fd_write (param i32 i32 i32 i32) (result i32)))

第一段匯入 env 命名空間下的 log 函式（這是 Emscripten 常用的命名）；第二段匯入 WASI Preview 1 的 fd_write，這是寫 stdout 的標準介面。

匯出

匯出讓宿主可以從 instance 取得對應實體。範例：

wat 
(module
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a
    local.get $b
    i32.add)
  (export "add" (func $add)))

宿主取得 instance 後，可以呼叫 instance.exports.add(3, 5)，會得到 8。

能力導向的物理表現

「Wasm 預設無法做任何 I/O」這個性質，物理上就體現在「沒有匯入就無法呼叫」。一個沒有任何 import 的 module 是純函式——只能算數、操作自己的記憶體，無法做任何外部互動。要讓它能讀檔，宿主必須匯入一個 read_file 函式；要讓它能聯網，宿主必須匯入 http_get 之類的函式。沒有 ambient access，所有能力都明確列在 import section 裡——這就是 capability-based security 的物理實現。

各階段做什麼

1. Source → IR

各語言用自家編譯器前端把 source 轉成內部 IR。Rust 用 rustc + LLVM；C/C++ 用 clang + LLVM；Go 標準工具鏈用自家 SSA IR；TinyGo 用 LLVM。

2. IR → .wasm

編譯器後端把 IR 翻成 Wasm 指令。LLVM 有官方 Wasm backend，這是最成熟的路徑。產出是二進位 .wasm 檔。

3. WAT（選擇性）

WAT（WebAssembly Text Format）是 .wasm 的人類可讀文字形式，用 S-expression 語法。debug 與學習時很有用，但生產不會用 WAT 部署。wasm-tools print 可從 .wasm 反組譯為 WAT。

4. Validation

宿主載入 .wasm 後，第一件事是驗證：

  • 所有指令的型別正確（type check）。
  • 記憶體訪問會被 runtime 加邊界檢查。
  • 控制流結構合法（block/loop/br 配對正確）。
  • 呼叫的函式 index 存在。

驗證是 Wasm 安全性的核心——通過驗證的 module，在型別系統內保證不會「亂走」。這個驗證是靜態的，發生在編譯到原生碼之前。

5. JIT 或 AOT 編譯

通過驗證後，runtime 把 Wasm 指令編譯成原生機器碼：

  • JIT（Just-In-Time）：邊執行邊編譯，啟動快、編譯成本攤平。瀏覽器 V8、Wasmtime 預設都是 JIT。
  • AOT（Ahead-Of-Time）：執行前先把整個 module 編譯好。啟動更快、但前置編譯時間長。Wasmtime wasmtime compile、WasmEdge wasmedgec 都支援。

常見編譯器：Wasmtime 用 Cranelift（自家寫的）；V8 用 TurboFan；JavaScriptCore 用 BBQ / OMG；SpiderMonkey 用 BaldrMonkey。

6. Instantiation

編譯完成後，呼叫 instantiate 真正建立 instance：分配 memory、初始化 global、解析 imports、執行 start function。

7. Execution

宿主呼叫 export 的函式，runtime 跳到對應原生碼執行。執行期間任何違反安全的操作（越界記憶體、整數除零、stack overflow、不可達指令）會 trap，中止當前執行。

2.6讀懂 WAT 文字格式

WAT 是 Wasm 二進位的人類可讀對應。雖然生產不會用 WAT 寫程式，但 debug、學習、理解編譯器產出時，能讀 WAT 是基本能力。

S-expression 語法

WAT 用 LISP 風格的 S-expression。基本結構：(關鍵字 參數1 參數2 ...)。整個 module 就是一個大的 S-expression：

wat 
(module
  ;; 註解用兩個分號開始

  ;; 宣告型別（可省略，直接寫在 func 也行）
  (type $sig_i32_i32_to_i32 (func (param i32 i32) (result i32)))

  ;; 定義 add 函式
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a       ;; push 第一個參數
    local.get $b       ;; push 第二個參數
    i32.add)           ;; 從 stack 取兩個值相加

  ;; 匯出 add，外部可呼叫
  (export "add" (func $add)))

函式區域變數（locals）

wat 
(func $sum_to_n (param $n i32) (result i32)
  (local $i i32)      ;; 宣告 local
  (local $sum i32)

  ;; 初始化 sum = 0, i = 1
  i32.const 0
  local.set $sum
  i32.const 1
  local.set $i

  ;; 迴圈 while (i <= n) sum += i; i++;
  (block $exit
    (loop $loop
      local.get $i
      local.get $n
      i32.gt_s
      br_if $exit          ;; if (i > n) break;

      local.get $sum
      local.get $i
      i32.add
      local.set $sum       ;; sum += i

      local.get $i
      i32.const 1
      i32.add
      local.set $i         ;; i++

      br $loop))           ;; continue

  local.get $sum)          ;; 回傳 sum

記憶體操作

wat 
(module
  ;; 宣告 1 頁記憶體，上限 5 頁
  (memory $mem 1 5)

  ;; 把 "Hello" 寫到位址 0
  (data (i32.const 0) "Hello")

  (func $get_byte (param $offset i32) (result i32)
    local.get $offset
    i32.load8_u)           ;; 讀 1 byte 為 unsigned i32

  (export "memory" (memory $mem))
  (export "get_byte" (func $get_byte)))

2.7Trap 與安全保證

當 Wasm 模組做了「不該做的事」，runtime 會觸發 trap——立即中止當前執行、把錯誤回給宿主。trap 是 Wasm 安全模型的最後一道防線。

哪些情況會 trap

  • 越界記憶體訪問：load/store 的位址超過當前記憶體大小。
  • 整數除零：i32.div_s 0 或 i32.rem_s 0。
  • 整數溢位轉換：i32.trunc_f32_s 對 NaN 或超出範圍的浮點數。
  • 未對齊的特定操作：例如 i32.atomic.load 對非 4-byte 對齊的位址。
  • Stack overflow：呼叫深度超過 runtime 限制。
  • 不可達指令：unreachable 指令被執行（編譯器常用來標記理論不該到達的分支）。
  • 呼叫 null function reference：透過 table 呼叫但 entry 是 null。
  • 型別不符的間接呼叫：call_indirect 的型別與目標函式簽章不符。

Wasm 的安全性由三層機制共同保障：

Layer 1 在載入時靜態檢查（不通過就拒絕載入）；Layer 2 在執行時動態檢查（不通過就 trap）；Layer 3 是架構層的保證（沒有 import 對應能力，連對應指令都不存在）。

Trap 不是萬能 Trap 保證「壞事不會發生」，但不保證「程式沒 bug」。例如算錯結果、無限迴圈消耗 CPU、洩漏資料給 host 可訪問的記憶體——這些都不會 trap。生產環境還需要 fuel / epoch limit、timeout、記憶體上限等額外控制。

LAB動手實作：解剖一個 .wasm

Lab 2.A · 從零到解析

用 Rust 編一個 Wasm 模組，再用 wasm-tools 反組譯

本 lab 完整走過：寫 Rust → 編譯為 Wasm → 用 wasm-tools 檢視 → 用 wasmtime 執行的流程。

步驟 1 · 建立 Rust 專案
bash 
cargo new --lib hello_wasm
cd hello_wasm
步驟 2 · 設定 Cargo.toml

編輯 Cargo.toml，加上 cdylib crate type（讓編譯產出 .wasm）：

toml 
[package]
name = "hello_wasm"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]

[profile.release]
opt-level = "s"     # 優化體積
lto = true          # link-time optimization
strip = true        # 去除 debug symbols
步驟 3 · 寫 Rust 程式碼

編輯 src/lib.rs：

rust 
// 用 no_mangle 讓函式名不被混淆
// extern "C" 用 C ABI，方便 host 呼叫
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[no_mangle]
pub extern "C" fn fib(n: i32) -> i32 {
    if n < 2 {
        n
    } else {
        fib(n - 1) + fib(n - 2)
    }
}

#[no_mangle]
pub extern "C" fn sum_to(n: i32) -> i32 {
    let mut sum = 0;
    for i in 1..=n {
        sum += i;
    }
    sum
}
步驟 4 · 編譯為 Wasm
bash 
# 安裝 target（如果還沒裝）
rustup target add wasm32-unknown-unknown

# 編譯
cargo build --release --target wasm32-unknown-unknown

# 找出產出檔
ls target/wasm32-unknown-unknown/release/hello_wasm.wasm

產出的 .wasm 應該不到 2KB。

步驟 5 · 反組譯為 WAT
bash 
wasm-tools print target/wasm32-unknown-unknown/release/hello_wasm.wasm | head -40

你會看到類似這樣的輸出：

wat 
(module
  (type (;0;) (func (param i32 i32) (result i32)))
  (type (;1;) (func (param i32) (result i32)))
  (func $add (type 0) (param i32 i32) (result i32)
    local.get 1
    local.get 0
    i32.add)
  (func $fib (type 1) (param i32) (result i32)
    ...)
  (memory (;0;) 16)
  (export "memory" (memory 0))
  (export "add" (func $add))
  (export "fib" (func $fib))
  (export "sum_to" (func $sum_to)))
步驟 6 · 用 wasm-tools dump 看詳細結構
bash 
wasm-tools dump target/wasm32-unknown-unknown/release/hello_wasm.wasm | head -50

這個指令顯示每個 section 的位元組偏移、大小、內容。對 debug binary size、追蹤大小膨脹來源很有用。

步驟 7 · 用 Wasmtime 直接呼叫
bash 
wasmtime --invoke add target/wasm32-unknown-unknown/release/hello_wasm.wasm 3 5
# 8

wasmtime --invoke fib target/wasm32-unknown-unknown/release/hello_wasm.wasm 10
# 55

wasmtime --invoke sum_to target/wasm32-unknown-unknown/release/hello_wasm.wasm 100
# 5050
步驟 8 · 觀察優化效果

比較 release 與 debug build 的體積：

bash 
cargo build --target wasm32-unknown-unknown   # debug build
ls -la target/wasm32-unknown-unknown/debug/hello_wasm.wasm
ls -la target/wasm32-unknown-unknown/release/hello_wasm.wasm
# debug 通常 100KB+，release 不到 2KB
Lab 2.B · 純手寫 WAT

不用編譯器，直接寫 WAT 並執行

步驟 1 · 寫 WAT

建立 manual.wat：

wat 
(module
  (func $multiply (param $a i32) (param $b i32) (result i32)
    local.get $a
    local.get $b
    i32.mul)

  (func $factorial (param $n i32) (result i32)
    (local $result i32)
    (local $i i32)

    i32.const 1
    local.set $result

    i32.const 1
    local.set $i

    (block $exit
      (loop $loop
        local.get $i
        local.get $n
        i32.gt_s
        br_if $exit

        local.get $result
        local.get $i
        i32.mul
        local.set $result

        local.get $i
        i32.const 1
        i32.add
        local.set $i

        br $loop))

    local.get $result)

  (export "multiply" (func $multiply))
  (export "factorial" (func $factorial)))
步驟 2 · 組譯為 .wasm
bash 
wasm-tools parse manual.wat -o manual.wasm
ls -la manual.wasm
# 大約 100 bytes — 純手寫 binary 極小！
步驟 3 · 執行
bash 
wasmtime --invoke multiply manual.wasm 6 7
# 42

wasmtime --invoke factorial manual.wasm 5
# 120
步驟 4 · 驗證錯誤

故意把 i32.mul 改成 i64.mul，重新組譯看 validation 是否會抓到型別錯誤：

bash 
# 修改 manual.wat，把 i32.mul 改成 i64.mul
sed -i 's/i32.mul/i64.mul/' manual.wat
wasm-tools parse manual.wat -o manual.wasm
# 應該會報錯：type mismatch

# 還原
sed -i 's/i64.mul/i32.mul/' manual.wat

這就是 validation 在發揮作用——靜態型別檢查。

QUIZ章末自我評估

Module 02 · 10 題自我測驗

Q1.Wasm 採用 stack-based VM 的主要原因是？（複選）
  • 執行速度比 register-based 快
  • binary 編碼較小
  • 解碼與驗證較簡單快速
  • 與 JVM、CLR 等成熟 stack VM 共享設計經驗
看解答
答案 · B、C、D 執行速度其實兩者差不多（A 錯），因為現代 runtime 都會 JIT/AOT 到原生碼，stack 只是 IR 編碼形式。B、C、D 才是真正的選擇理由。
Q2.下列關於 module 與 instance 的敘述，何者正確？
  • 一個 .wasm 檔對應一個 instance
  • instance 可以序列化後傳給其他機器
  • 同一個 module 可以實例化多次，每個 instance 有自己的記憶體
  • module 可以直接執行，不需要 instantiate
看解答
答案 · C 一個 module 可實例化多次（A 錯）；instance 包含 runtime 狀態，不易序列化（B 錯）；module 是執行藍圖，不能直接執行（D 錯）。C 是正確的——這是 Wasm「per-request instance」模型的基礎。
Q3.Wasm 線性記憶體的特性，下列敘述何者錯誤？
  • 以 64KB 為一頁，可動態增長
  • 宿主可以讀寫 Wasm instance 的線性記憶體
  • Wasm 模組可以直接讀寫宿主程序的其他記憶體區域
  • 記憶體訪問會做邊界檢查
看解答
答案 · C Wasm 模組無法讀寫宿主程序的其他記憶體——這正是沙箱隔離的根本。A、B、D 都是正確特性。
Q4.Wasm 1.0/2.0 原生支援的四種數值型別是？
  • i8、i16、i32、i64
  • i32、i64、f32、f64
  • int、long、float、double
  • i32、i64、f32、f64、string
看解答
答案 · B i32、i64、f32、f64 是 MVP 就支援的四種數值型別。Wasm 沒有原生 string、bool 等型別——這些要靠線性記憶體與序列化實作。
Q5.Wasm 模組如何把字串傳給宿主函式？
  • 直接傳 string 型別參數
  • 傳一個指標（i32）與一個長度（i32），讓宿主從 instance 記憶體讀取對應 bytes
  • 用 base64 編碼後傳成 i64
  • 序列化為 JSON 字串後傳
看解答
答案 · B 因為 Wasm 沒有原生 string 型別，標準做法是傳 (ptr, len) 兩個 i32，宿主從記憶體讀取 bytes 解碼。Component Model（M07）會把這個 idiom 封裝成 first-class string。
Q6.下列關於編譯流程，何者敘述正確？
  • .wasm 直接由 CPU 執行
  • 所有 runtime 都是 AOT 編譯，沒有 JIT
  • .wasm 載入後先經 validation，然後 JIT 或 AOT 編譯成原生碼執行
  • Wasm 是純 interpreter，不編譯到原生碼
看解答
答案 · C CPU 無法直接執行 .wasm（A 錯）；runtime 多採 JIT，AOT 是選擇性（B 錯）；極輕量 runtime 才用 pure interpreter，多數情況都會編譯（D 錯）。C 是標準流程。
Q7.下列何者會觸發 Wasm trap？（複選）
  • 整數除以零
  • 記憶體越界訪問
  • 無限迴圈
  • 執行 unreachable 指令
  • stack overflow
看解答
答案 · A、B、D、E A、B、D、E 都是標準 trap 來源。C 無限迴圈不會觸發 trap——這需要 runtime 額外的 fuel / epoch / timeout 機制才能中止。這也是為什麼生產環境除了 trap 還要設執行配額。
Q8.「能力導向（capability-based）」在 Wasm 中的物理表現是？
  • 用 ACL 控制 Wasm 模組權限
  • 沒有匯入對應 import 的能力，模組連對應操作的指令都無法表達
  • 用 syscall filter 阻擋 Wasm 的系統呼叫
  • 執行前讀取 manifest 檔案決定權限
看解答
答案 · B 能力導向的核心特性是「沒有 ambient access」——Wasm 模組要做任何 I/O，必須有對應 import；沒有 import 對應，連表達該操作的方式都不存在。這比 A、C 的「事後檢查」模型更安全。
Q9.WAT 中 local.get $x 指令的作用是？
  • 把 local 變數 $x 的值 push 到 stack 頂部
  • 從 stack pop 一個值存到 local $x
  • 宣告一個 local 變數
  • 取得 global 變數的值
看解答
答案 · A local.get 把 local 變數的值 push 到 stack。對應的 local.set 才是 B 的操作。Local 變數宣告用 (local $x i32)；global 用 global.get。
Q10.下列關於 Wasm 三層安全保證，何者敘述正確？
  • validation 在執行時動態進行
  • runtime checks 與 capability boundary 是同一件事
  • validation 是載入時靜態做的，capability boundary 在架構層保證
  • 只要通過 validation，就保證程式沒 bug
看解答
答案 · C validation 是載入時靜態做的（A 錯）；runtime checks 是執行時邊界檢查，capability boundary 是架構層的能力限制，兩者不同（B 錯）；validation 保證型別與記憶體安全，不保證邏輯正確（D 錯）。
