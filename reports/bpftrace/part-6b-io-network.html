CHAPTER 28 I/O 與檔案系統 ⚙️ SRE 🛠 開發

Linux I/O 從應用到磁碟有四層 —— syscall / VFS / page cache / block layer。每層各有觀測點，把它們組合起來就能定位「這個讀為什麼這麼慢」。

28.1 Linux I/O 堆疊地圖

圖 28.1 — Linux I/O 堆疊與 bpftrace 觀測點對應

📌 各層的觀測語意

  • Syscall 層：應用看到的 I/O 行為，含未必觸發磁碟的呼叫（page cache hit）。
  • VFS 層：所有檔案系統共用的抽象。最適合「不分檔案系統觀察讀寫」。
  • Page cache：未命中時才會往下層走。觀察這層可分辨 cache hit vs miss。
  • Block 層：真正觸及磁碟的 I/O。延遲 = 物理 I/O 延遲。

28.2 Block I/O 延遲分布

CASE 28-1

磁碟健檢：biolatency 風格分析

應用報告偶發 I/O 慢，但平均延遲看起來正常 —— 需要看分布找出 outlier。

// biolatency.bt — 量測 block I/O 延遲分布
tracepoint:block:block_rq_issue {
  @start[args.dev, args.sector] = nsecs;
}

tracepoint:block:block_rq_complete
/has_key(@start, (args.dev, args.sector))/ {
  @us = hist((nsecs - @start[args.dev, args.sector]) / 1000);
  delete(@start, (args.dev, args.sector));
}

END { clear(@start); }

  @us[args.dev] = hist((nsecs - @start[args.dev, args.sector]) / 1000);
  delete(@start, (args.dev, args.sector));
}

28.3 哪個 process 在做最多 I/O

CASE 28-2

磁碟 IOPS 異常飆高，找出元兇 process

iostat 顯示 nvme0n1 寫入 IOPS 從平常 200 跳到 5000，但 iotop 沒看到明顯異常 process。

// 從 block layer 倒推回 process — 這比 iotop 精準
tracepoint:block:block_rq_issue {
  @bytes[comm, pid] = sum(args.bytes);
  @count[comm, pid] = count();
}

interval:s:5 {
  printf("\n=== 5s window ===\n");
  printf("%-16s %-8s %12s %8s\n", "COMM", "PID", "BYTES", "OPS");
  print(@bytes, 10);
  print(@count, 10);
  clear(@bytes); clear(@count);
}

⚠️ block_rq_issue 的 comm 不一定是發起者

當 I/O 從kernel thread（如 kworker、flush-*）發出時，comm 會是那個 kernel thread，不是真正寫資料的 application —— 這是 page cache 寫回的特性。要追真正 dirty 的 process，要走 VFS 層或 syscall 層。

28.4 VFS 慢操作溯源

CASE 28-3

應用偶爾卡 200ms，懷疑是檔案 I/O

某 service 的 p99 latency 偶爾飆到 200ms+，CPU 使用率正常，懷疑是應用層感知到的檔案操作問題（含 page cache 等待）。

// vfs_slow.bt — 抓所有 VFS 操作中超過 50ms 的，附 stack
let @start = lruhash(8192);

fentry:vfs_read,
fentry:vfs_write,
fentry:vfs_fsync {
  @start[tid, func] = nsecs;
}

fexit:vfs_read,
fexit:vfs_write,
fexit:vfs_fsync
/has_key(@start, (tid, func))/ {
  let $dur = nsecs - @start[tid, func];
  delete(@start, (tid, func));

  // 量分布
  @lat_us[func] = hist($dur / 1000);

  // 慢事件抓 stack
  if ($dur > 50ms) {
    printf("[SLOW] %s pid=%d %s took %d ms\n",
           comm, pid, func, $dur / 1ms);
    @slow_stacks[func, kstack(8)] = count();
  }
}

END {
  clear(@start);
  printf("\n--- Latency distribution ---\n");
  print(@lat_us);
  printf("\n--- Slow event stacks ---\n");
  print(@slow_stacks);
}

28.5 檔案開啟監控（誰在開哪些檔）

CASE 28-4

資安事件：誰在偷讀 /etc/shadow？

蜜罐警報觸發，有人嘗試讀取機密檔案。需要即時知道是哪個 process。

// fopen_audit.bt
tracepoint:syscalls:sys_enter_openat {
  let $name = str(args.filename);
  if (strcontains($name, "shadow") ||
      strcontains($name, "/proc/self/maps") ||
      strcontains($name, "id_rsa") ||
      strcontains($name, ".aws/credentials")) {
    printf("[AUDIT] [%s] %-16s pid=%d uid=%d -> %s\n",
           strftime("%H:%M:%S", nsecs),
           comm, pid, uid, $name);
  }
}

進階：把命中事件寫到 syslog（用 --unsafe，僅在受控環境）：

tracepoint:syscalls:sys_enter_openat
/strcontains(str(args.filename), "shadow")/ {
  system("logger -t bpftrace-audit \"%s pid=%d read shadow\"",
         comm, pid);
}

28.6 Page cache 命中 vs 未命中

分辨應用看到的read 慢是不是因為 cache miss 觸發磁碟 I/O：

// 量 vfs_read 與 block I/O 的 ratio
fentry:vfs_read {
  @vfs_reads = count();
}

tracepoint:block:block_rq_issue {
  if (args.rwbs == "R" || args.rwbs == "RA") {     // Read 或 Read-Ahead
    @block_reads = count();
  }
}

interval:s:5 {
  printf("vfs_reads=%d, block_reads=%d, cache_hit_ratio=~%d%%\n",
         @vfs_reads,
         @block_reads,
         @vfs_reads > 0
           ? 100 - (@block_reads * 100 / @vfs_reads)
           : 100);
  clear(@vfs_reads);
  clear(@block_reads);
}

📌 ratio 不會 100% 精準

原因：block_reads 含 prefetch、metadata 讀取；vfs_reads 也含對 procfs / sysfs 的讀（沒有 block I/O）。但 ratio 的趨勢有意義 —— 突然從 95% 掉到 60% 就是 working set 變大或 cache 被擠爆的訊號。

28.7 完整腳本：io_diag.bt

#!/usr/bin/env bpftrace
// io_diag.bt — 30 秒 I/O 全景健檢

config = {
  max_map_keys = 16384;
}

let @vfs_start   = lruhash(8192);
let @block_start = lruhash(16384);

BEGIN {
  printf("=== I/O diagnostic for 30s ===\n");
}

// (1) VFS 層延遲
fentry:vfs_read,
fentry:vfs_write,
fentry:vfs_fsync {
  @vfs_start[tid, func] = nsecs;
}

fexit:vfs_read,
fexit:vfs_write,
fexit:vfs_fsync /has_key(@vfs_start, (tid, func))/ {
  let $dur = nsecs - @vfs_start[tid, func];
  delete(@vfs_start, (tid, func));
  @vfs_us[func] = hist($dur / 1000);
}

// (2) Block 層延遲
tracepoint:block:block_rq_issue {
  @block_start[args.dev, args.sector] = nsecs;
  @block_bytes[comm] = sum(args.bytes);
}

tracepoint:block:block_rq_complete
/has_key(@block_start, (args.dev, args.sector))/ {
  let $dur = nsecs - @block_start[args.dev, args.sector];
  delete(@block_start, (args.dev, args.sector));
  @block_us = hist($dur / 1000);
}

// (3) Top file opens
tracepoint:syscalls:sys_enter_openat {
  @opens[comm] = count();
}

interval:s:30 { exit(); }

END {
  printf("\n--- VFS latency (us) ---\n");
  print(@vfs_us);

  printf("\n--- Block I/O latency (us) ---\n");
  print(@block_us);

  printf("\n--- Block I/O bytes by process ---\n");
  print(@block_bytes, 10);

  printf("\n--- Top file openers ---\n");
  print(@opens, 10);

  clear(@vfs_start); clear(@block_start);
}

29.2 TCP 連線生命週期觀察

每個 TCP 連線都會經過幾個 state：CLOSED → SYN_SENT/RECV → ESTABLISHED → FIN_WAIT/CLOSE_WAIT → CLOSED。tcp_set_state 看得最清楚：

CASE 29-1

追蹤所有新建立的連線

// tcp_lifecycle.bt
tracepoint:tcp:tcp_set_state {
  $sk = (struct sock *)args.skaddr;
  $saddr = ntop($sk->__sk_common.skc_rcv_saddr);
  $daddr = ntop($sk->__sk_common.skc_daddr);
  $sport = $sk->__sk_common.skc_num;
  $dport = bswap($sk->__sk_common.skc_dport);

  // TCP states 從 include/net/tcp_states.h
  // 1=ESTABLISHED 2=SYN_SENT 3=SYN_RECV 4=FIN_WAIT1
  // 5=FIN_WAIT2  6=TIME_WAIT 7=CLOSE 8=CLOSE_WAIT 9=LAST_ACK
  if (args.newstate == 1) {       // ESTABLISHED
    printf("[%s] EST %s:%d -> %s:%d (%s)\n",
           strftime("%H:%M:%S", nsecs),
           $saddr, $sport, $daddr, $dport, comm);
  } else if (args.newstate == 7) { // CLOSE
    printf("[%s] CLS %s:%d -> %s:%d (%s)\n",
           strftime("%H:%M:%S", nsecs),
           $saddr, $sport, $daddr, $dport, comm);
  }
}

29.3 連線延遲（connect latency）

CASE 29-2

某下游服務 connect 變慢

應用回報：呼叫某個內部 API 的延遲變高，但實際 HTTP request/response 很快 —— 懷疑是 TCP 連線階段慢。

// tcpconnect.bt — 量 connect 階段延遲
let @start = lruhash(2048);

fentry:tcp_v4_connect {
  @start[tid] = nsecs;
}

fexit:tcp_v4_connect /has_key(@start, tid)/ {
  let $sk = args.sk;
  let $daddr = ntop($sk->__sk_common.skc_daddr);
  let $dport = bswap($sk->__sk_common.skc_dport);
  let $dur_ms = (nsecs - @start[tid]) / 1ms;
  delete(@start, tid);

  printf("%-16s %-15s:%-5d %4d ms\n",
         comm, $daddr, $dport, $dur_ms);

  @lat_ms[$daddr] = hist($dur_ms);
}

29.4 重傳分析

CASE 29-3

大量 TCP 重傳，疑似網路品質問題

netstat -s 顯示 segments retransmitted 在最近一小時暴增 10 倍。

// tcp_retrans.bt — 找出重傳最多的連線
tracepoint:tcp:tcp_retransmit_skb {
  $sk = (struct sock *)args.skaddr;
  $saddr = ntop($sk->__sk_common.skc_rcv_saddr);
  $daddr = ntop($sk->__sk_common.skc_daddr);
  $dport = bswap($sk->__sk_common.skc_dport);

  @[$saddr, $daddr, $dport] = count();
}

interval:s:30 {
  printf("\n=== Top retransmitting connections (30s) ===\n");
  print(@, 10);
  clear(@);
}

@[10.0.0.5, 192.168.10.21, 443]: 892
@[10.0.0.5, 10.0.0.99, 8080]: 12

29.6 封包擷取（無需 tcpdump）

CASE 29-4

特定條件下才擷取封包到 PCAP

想抓「TCP 重傳的封包」並用 Wireshark 分析。tcpdump 無法以 retransmit 為條件抓。

// 用 0.25 的 skboutput 直接寫 PCAP
fentry:tcp_retransmit_skb {
  let $skb = (struct sk_buff *)args.skb;
  skboutput("/tmp/retrans.pcap",
            $skb,
            $skb->len,
            0);
}

interval:s:60 { exit(); }
sudo bpftrace cap.bt
# 60 秒後
tcpdump -nr /tmp/retrans.pcap | head
wireshark /tmp/retrans.pcap

💡 比 tcpdump 強的地方

  • 能抓「kernel 內任意條件」觸發的封包，例如「只有當對應 socket 有特定 cookie 才抓」。
  • 不需要 promiscuous mode，避免雜訊。
  • 能配合 -p PID 只抓單一 process 的網路流量。

29.8 IP 位址過濾的標準寫法

生產環境需要只追特定 IP 的流量。三種對齊技巧：

// 1. 比對單一 IPv4
fentry:tcp_sendmsg
/args.sk->__sk_common.skc_daddr == (uint32)pton("8.8.8.8")/ {
  @[comm] = count();
}

// 2. 比對特定子網（前置位元）
fentry:tcp_sendmsg
/(args.sk->__sk_common.skc_daddr & (uint32)pton("255.255.255.0"))
   == (uint32)pton("10.0.1.0")/ {
  @[comm] = count();
}

// 3. 多個目標 IP
fentry:tcp_sendmsg /
  args.sk->__sk_common.skc_daddr == (uint32)pton("10.0.1.5") ||
  args.sk->__sk_common.skc_daddr == (uint32)pton("10.0.1.6")
/ {
  @[comm] = count();
}

⚠️ skc_daddr 是 network byte order

kernel struct 裡 IPv4 位址是 __be32（big-endian network byte order）。pton() 也回傳 network byte order，所以兩者直接比對是 OK 的。但若要轉成數字 print，記得 bswap()。

29.9 完整網路健檢腳本：net_diag.bt

#!/usr/bin/env bpftrace
// net_diag.bt — 30 秒網路全景健檢

config = { max_map_keys = 16384; }

let @connect_start = lruhash(2048);

BEGIN { printf("=== Network diagnostic for 30s ===\n"); }

// (1) Connection establishment latency
fentry:tcp_v4_connect { @connect_start[tid] = nsecs; }
fexit:tcp_v4_connect /has_key(@connect_start, tid)/ {
  let $sk = args.sk;
  let $daddr = ntop($sk->__sk_common.skc_daddr);
  @connect_us[$daddr] = hist((nsecs - @connect_start[tid]) / 1000);
  delete(@connect_start, tid);
}

// (2) Send / recv volume
fentry:tcp_sendmsg { @sent[comm] = sum(args.size); }
fexit:tcp_recvmsg /retval > 0/ { @recv[comm] = sum(retval); }

// (3) Retransmits
tracepoint:tcp:tcp_retransmit_skb {
  $sk = (struct sock *)args.skaddr;
  @retrans[ntop($sk->__sk_common.skc_daddr)] = count();
}

// (4) RSTs
kprobe:tcp_v4_send_reset {
  @rsts[comm] = count();
}

// (5) State changes
tracepoint:tcp:tcp_set_state {
  if (args.newstate == 1) { @ests = count(); }       // ESTABLISHED
  if (args.newstate == 7) { @clss = count(); }       // CLOSE
}

interval:s:30 { exit(); }

END {
  printf("\n--- Connect latency by destination (us) ---\n");
  print(@connect_us);

  printf("\n--- Sent / Recv bytes ---\n");
  print(@sent, 10); print(@recv, 10);

  printf("\n--- Retransmits by destination ---\n");
  print(@retrans, 10);

  printf("\n--- RST senders ---\n");
  print(@rsts);

  printf("\n--- State transitions ---\n");
  print(@ests); print(@clss);

  clear(@connect_start);
}

💡 解讀流程

  1. Connect latency 看是否有 outlier（>100ms 通常異常）。
  2. Sent/Recv 看哪個 process 流量主導。
  3. Retransmits 集中到單一目的 = 鏈路問題；分散 = 自身 NIC/系統問題。
  4. RST 發起方 是自己時要看 stack 找原因（連線數爆？應用主動關？）。
  5. EST/CLS 比例 嚴重失衡（CLS 遠多於 EST）= 連線耗盡 / 短連線風暴。
