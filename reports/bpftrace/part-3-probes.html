CHAPTER 11 探針總覽與寫法 🔰 初學 🛠 開發

把所有探針類型放在一張地圖上 —— 內核 vs 使用者、靜態 vs 動態、單點 vs 多點。看完這章你能挑對工具，後面四章只是把細節填滿。

11.1 探針的四象限地圖

圖 11.1 — 探針四象限：選擇正確的觀測切入點

💡 選 probe 的優先順序

  1. 有 tracepoint 用 tracepoint（穩定、有型別化 args）。
  2. 有 fentry 用 fentry（比 kprobe 快、有 BTF args、retprobe 也能存 args）。
  3. 沒有以上才退回 kprobe / kretprobe。
  4. 使用者空間 → 先看 USDT，再退回 uprobe。

這個順序適用於 90% 的情境；剩下 10% 的特例會在各章說明。

11.3 多探針綁定與 wildcard

逗號分隔多個探針

tracepoint:syscalls:sys_enter_open,
tracepoint:syscalls:sys_enter_openat,
tracepoint:syscalls:sys_enter_openat2 {
  printf("%s opens %s\n", comm, str(args.filename));
}

Wildcard（受 probe type 支援）

// 所有 vfs_ 開頭的內核函式
kprobe:vfs_* { @hits[probe] = count(); }

// 所有 sched 命名空間下的 tracepoint
tracepoint:sched:* { @[probe] = count(); }

// 用 ? 比對單一字元
kprobe:do_?ad { ... }   // do_bad、do_pad ...

11.4 Listing Probes：探針自我發現工作流程

遇到陌生函式或子系統時，先列再追是最高效的工作流程。

基本列表 -l

# 列出所有 vfs_ 開頭的 kprobe
sudo bpftrace -l 'kprobe:vfs_*'

# 列出所有 syscalls 命名空間的 tracepoint
sudo bpftrace -l 'tracepoint:syscalls:*'

# 列出 fentry 全部（從 BTF 讀取）
sudo bpftrace -l 'fentry:*' | head

# 沒指定 pattern 就列全部（很多）
sudo bpftrace -l | wc -l

詳細列表 -lv（最重要！）

-lv 會顯示每個探針的型別化參數，這是寫腳本前的必備步驟：

sudo bpftrace -lv 'tracepoint:syscalls:sys_enter_openat'
tracepoint:syscalls:sys_enter_openat
    int __syscall_nr;
    int dfd;
    const char * filename;
    int flags;
    umode_t mode;

這告訴你 args.filename、args.flags、args.mode 都可用。

sudo bpftrace -lv 'fentry:vfs_read'
fentry:vfs_read
    struct file * file
    char * buf
    size_t count
    loff_t * pos

💡 一條命令搞定 90% 探索

# 想知道有哪些 tcp 相關 fentry，每個的 args 長什麼樣
sudo bpftrace -lv 'fentry:tcp_*' | less

列出 uprobe / USDT

# 列出二進位內所有可掛 uprobe 的函式
sudo bpftrace -l 'uprobe:/bin/bash:*' | head

# 列出所有 USDT
sudo bpftrace -l 'usdt:/path/to/app:*'

# 對某個正在跑的 process（會搜尋它的 address space）
sudo bpftrace -p 1234 -l 'uprobe:*'

11.5 缺失探針的處理

當你寫了 kprobe:foo* 想用 wildcard 抓一批，但其中某些函式不存在 / 已被 inline，預設行為是掛得上的就掛、其他丟 warning。

透過 missing_probes config 控制：

config = {
  missing_probes = "error";   // 只要有一個掛不上就整個 fail
  // missing_probes = "warn";  // 預設：印 warning，繼續執行
  // missing_probes = "ignore"; // 安靜，當沒事
}

--probe-filter：在 attach 前就排除

當你寫 kprobe:tcp_* 卻有幾個函式特別吃 CPU 不想追，可在執行時 regex 排除：

sudo bpftrace --probe-filter 'tcp_v4_rcv|tcp_recvmsg' script.bt

CHAPTER 12 內建特殊探針 🛠 開發

begin / end / self:signal / interval / profile / hardware / software / test / bench —— 這些不是「掛在某段程式上」，而是 bpftrace 自己給你的 hook。

12.1 begin 與 end

begin / end

begin { ... } end { ... }

觸發時機
begin：bpftrace 啟動、所有探針掛上之前；end：所有探針 detach 之前。
數量限制
可以有多個 begin / end，依宣告順序執行。
作用
程式啟動訊息、表頭、初始化 map、最終報告。
begin {
  printf("%-8s %-6s %-16s %s\n", "TIME", "PID", "COMM", "EVENT");
}

tracepoint:sched:sched_process_exec {
  printf("%-8d %-6d %-16s %s\n",
         elapsed / 1ms, pid, comm, str(args.filename));
}

end {
  printf("\nFinished at %s\n", strftime("%H:%M:%S", nsecs));
}

📌 end 不會阻止預設印 map

即使你寫了 end { ... }，bpftrace 仍然會在程式結束時印出所有非空 map。要避免就在 end 內 clear()，或設定 print_maps_on_exit = false。

12.2 self:signal:SIGUSR1

self:signal:SIGUSR1

self:signal:SIGUSR1 { ... }

觸發時機
bpftrace 進程本身收到 SIGUSR1 時。
典型用途
長跑腳本不結束、但要「中途取一份 snapshot」。
begin {
  printf("Send SIGUSR1 to PID %d for snapshot\n", pid);
}

tracepoint:syscalls:sys_enter_read {
  @reads[comm] = count();
}

self:signal:SIGUSR1 {
  printf("\n=== Snapshot at %s ===\n", strftime("%H:%M:%S", nsecs));
  print(@reads);
  clear(@reads);
}
# 在另一個 terminal
kill -USR1 $(pgrep -x bpftrace)

12.3 interval vs profile

兩者都是定時觸發，差別在「哪幾個 CPU 觸發」：

探針觸發位置典型用途
interval:s:1單一 CPU（任意一顆）計時器、定期 dump map、產生秒級報告
profile:hz:99每顆 CPU 都觸發採樣、繪火焰圖前處理

interval：定期報告

tracepoint:syscalls:sys_enter_read {
  @reads = count();
}

interval:s:1 {
  printf("%s reads/s: %d\n", strftime("%H:%M:%S", nsecs), @reads);
  clear(@reads);
}

profile：採樣

// 99 Hz × 每顆 CPU = 採樣 ustack
profile:hz:99 {
  @[ustack, comm] = count();
}

profile 支援的單位：

  • profile:hz:N — 每秒 N 次
  • profile:s:N — 每 N 秒一次
  • profile:ms:N — 每 N 毫秒一次
  • profile:us:N — 每 N 微秒一次

💡 為什麼採樣用 99 Hz 而不是 100 Hz

避免與內核或應用裡其他 100 Hz 的計時器產生 alias（每次採到的都是同樣相位的 stack），用質數（97、99、997）能均勻採到不同瞬間。這是火焰圖工具鏈的標配做法。

12.4 hardware（PMC）與 software

hardware 與 software 探針綁到 perf_events 提供的事件，每觸發 N 次跑一次 action：

類型常見事件
hardware:*cpu-cycles · instructions · cache-references · cache-misses · branch-instructions · branch-misses · bus-cycles
software:*cpu-clock · task-clock · page-faults · faults · context-switches · cpu-migrations · minor-faults · major-faults · alignment-faults · emulation-faults · dummy · bpf-output
 
// 每 100 萬個 cache miss 取樣一次 stack
hardware:cache-misses:1000000 {
  @miss[ustack] = count();
}

// 每 100 個 page fault 看一次
software:faults:100 {
  @[comm] = count();
}

// 留空使用預設頻率
software:page-faults: { @[comm] = count(); }

12.5 test 與 bench（給腳本作者）

0.25 的 test 與 bench 探針配合 --test / --bench CLI 旗標使用，用來測試/基準你寫的工具：

// 只在 --test 時跑
test:check_basic_arithmetic {
  let $a = 2 + 2;
  if ($a != 4) {
    fail("arithmetic broken");
  }
}

// 只在 --bench 時跑
bench:hash_lookup_perf {
  for ($i : 0..1000) {
    @h[$i] = $i * 2;
  }
}
sudo bpftrace --test myscript.bt
sudo bpftrace --bench myscript.bt

CHAPTER 13 內核動態追蹤：kprobe · fentry · rawtracepoint 🛠 開發 ⚙️ SRE

動態追蹤 = 「想看哪個函式就掛上去」。kprobe 是元老、fentry 是後起之秀且更強。能用 fentry 就用 fentry。

13.1 kprobe / kretprobe

kprobe / kretprobe

kprobe:func_name [+offset] kprobe:0xADDR (需 --unsafe) kretprobe:func_name

機制
內核將 func_name 起點（kprobe）或返回點（kretprobe）的指令替換為 int3 trap，trap 觸發 BPF 程式。
引數
用 arg0、arg1、... argN（型別都是 int64，需自行 cast）。
返回值
kretprobe 用 retval。
限制
kretprobe 看不到 entry 時的 args，需自行用 map 暫存。

基本範例

kprobe:vfs_read {
  // arg0 = struct file *, arg1 = char __user *, arg2 = size_t count
  printf("%s reading %d bytes\n", comm, arg2);
}

kretprobe:vfs_read {
  // retval = ssize_t
  if ((int64)retval < 0) {
    printf("%s read failed: errno=%d\n", comm, -(int64)retval);
  }
}

結合 args entry → retval 的延遲量測

let @start = lruhash(8192);

kprobe:vfs_read {
  @start[tid] = nsecs;
}

kretprobe:vfs_read /has_key(@start, tid)/ {
  @lat = hist((nsecs - @start[tid]) / 1us);
  delete(@start, tid);
}

偏移與 bare address（unsafe）

// 在函式進入後第 32 byte 處掛
kprobe:vfs_read+32 { ... }

// 直接掛在 raw kernel address（0.25 重新支援）
sudo bpftrace --unsafe -e 'kprobe:0xffffffff81234567 { print(probe); }'

⚠️ kprobe 的固有風險

  • 函式名稱依 kernel 版本變化（重命名、被 inline、靜態化）。
  • 引數順序與型別也可能改 —— 沒有 BTF 提示。
  • 傳遞引數方式依 ABI（x86_64 是 RDI、RSI、RDX、RCX、R8、R9 前 6 個；超過這些走 stack，bpftrace 不支援）。

13.2 fentry / fexit（最推薦）

fentry / fexit (kfunc/kretfunc)

fentry:func_name { ... args.* ... } fexit:func_name { ... args.* ... retval ... }

機制
使用 BPF trampoline，不需要 trap、近乎零成本。kernel 5.5+。
引數
args 是型別化 struct，欄位名直接對應 C 函式簽章。fexit 也能取 args！
BTF 依賴
需要 vmlinux BTF（現代 distro 預設都有）。
別名
kfunc / kretfunc 是舊名，0.25 仍支援。

kprobe vs fentry 對照

特性kprobefentry
掛載成本~ 1µs/event~ 0.1µs/event
引數型別資訊需手動 castBTF 自動
retprobe 能取 args❌✅
支援所有 kernel 函式✅需 BTF 收錄
需要 kernel 版本≥ 4.4≥ 5.5

fexit 直接取 args 範例

// 看 vfs_read 真的讀到多少 bytes，並列出檔名
fexit:vfs_read {
  // args.file 是 struct file *
  // args.count 是請求 size
  // retval 是實際讀到的 bytes
  if (retval > 0) {
    printf("read %d/%d bytes from %s\n",
           retval, args.count,
           str(args.file.f_path.dentry.d_name.name));
  }
}

這在 kprobe/kretprobe 寫法上要分兩個 probe + 一個 map 才能實現。

fentry:bpf — 觀測其他 BPF 程式

0.25 支援把 fentry 掛在正在執行的另一個 BPF 程式上：

sudo bpftrace -l 'fentry:bpf:*'
// 在另一個 bpftrace 跑著 uprobe:./test:foo 時
fexit:bpf:uprobe___test_foo_1 {
  print("the other bpftrace just printed something");
}

13.3 rawtracepoint

rawtracepoint / rt

rawtracepoint:event_name { ... }

機制
掛在 tracepoint 的「原始」階段，跳過 tracepoint 對 args 的封裝。
vs tracepoint
效能略高、引數從 raw 結構讀取（更接近 kernel struct）。
使用時機
tracepoint 因 args 包裝開銷影響 hot path 時。
rawtracepoint:sched_switch {
  // args.0 = preempt, args.1 = prev *task_struct, args.2 = next *task_struct
  $next = (struct task_struct *)args.2;
  printf("switching to %s\n", $next.comm);
}

📌 何時用 raw、何時用 normal

初學一律用 tracepoint（args 已封裝、好寫）。當追的 tracepoint 觸發頻率極高（如 sched_switch 在繁忙系統可能 100k/s+）影響系統時，再降級到 rawtracepoint。

CHAPTER 14 內核靜態追蹤：tracepoint · iter 🛠 開發 ⚙️ SRE

靜態追蹤點是 kernel 開發者「承諾會穩定的觀測介面」 —— 寫一次能跑很多版本，是 production 的首選。

14.1 tracepoint

tracepoint / t

tracepoint:category:event_name { ... args.* ... }

機制
kernel 開發時於關鍵點寫死的觀測 hook。
穩定性
視為準 ABI，跨版本變動少。
引數
args 結構，欄位由 tracepoint 定義。
探索方式
bpftrace -lv 'tracepoint:*' 或 /sys/kernel/debug/tracing/events/<category>/<event>/format

常用 tracepoint 類別總覽

命名空間典型事件用途
syscallssys_enter_* / sys_exit_*系統呼叫追蹤
schedsched_switch / sched_wakeup / sched_process_*排程、CPU 分析
blockblock_rq_issue / block_rq_complete磁碟 I/O
tcptcp_set_state / tcp_retransmit_skb網路
kmemkmalloc / kfree / mm_page_alloc記憶體
signalsignal_generate / signal_deliver信號
raw_syscallssys_enter / sys_exit所有 syscall（用 args.id 區分）

實戰：所有 syscall 計數

tracepoint:raw_syscalls:sys_enter {
  // args.id 是 syscall number
  // 0.25 新增 syscall_name() 直接轉成可讀名稱
  @[syscall_name(args.id)] = count();
}

interval:s:5 {
  print(@, 10);
  clear(@);
}

實戰：sched_switch

tracepoint:sched:sched_switch {
  // 看每個 thread 從 runnable 變 running 再變 swapped 的轉移
  @[args.prev_comm, args.next_comm] = count();
}

💡 tracepoint 的「format 檔案」

對應的純文字定義就在：

cat /sys/kernel/debug/tracing/events/syscalls/sys_enter_openat/format

從這裡可確認 args 欄位（field、offset、size、signed 等）。在沒有 BTF 的舊環境特別有用。

14.2 iter（BPF iterator）

iter

iter:task { ... ctx->task ... } iter:task_file { ... ctx->task, ctx->file ... } iter:task_vma { ... ctx->task, ctx->vma ... }

機制
kernel 5.8+ 新增的 BPF program 類型，按需遍歷 kernel 結構（task list、所有 fd、所有 vma）。
觸發時機
不是事件驅動。掛上去時跑一次遍歷整個 list，或 pin 後從 user space 觸發。
典型用途
系統快照（所有 process / 所有開啟檔案 / memory map），不需要等事件發生。

列出所有 task

iter:task {
  printf("%s:%d (parent=%d)\n",
         ctx->task->comm,
         ctx->task->pid,
         ctx->task->real_parent->pid);
}

列出所有開啟的檔案

iter:task_file {
  printf("%s:%d -> %s\n",
         ctx->task->comm,
         ctx->task->pid,
         path(ctx->file->f_path));
}

Pinning：把 iterator 釘到 BPFFS

用 :pin_file 後綴把 iterator 釘到 /sys/fs/bpf，之後可以從 user space 多次觸發：

iter:task:my_tasks {
  printf("%s:%d\n", ctx->task->comm, ctx->task->pid);
}
# bpftrace 跑著時
sudo cat /sys/fs/bpf/my_tasks   # 觸發一次遍歷

⚠️ iter 的 ctx 用 -> 而非 .

注意 iter 探針的 ctx 預設用 -> 存取 —— 因為這是傳入的 BPF program context 而非一般 struct ptr。雖然 0.25 自動 deref 普遍適用，iter ctx 仍習慣用 ->。

CHAPTER 15 使用者空間追蹤：uprobe · usdt 🛠 開發

從 kernel 切到 user space —— 觀察 bash、libc、postgres、node、python 的內部。原則：先試 USDT（穩定），再退回 uprobe（任意點，但脆弱）。

15.1 uprobe / uretprobe

uprobe / uretprobe

uprobe:/path/to/binary:func_name [+offset] uprobe:/path/to/binary:0xOFFSET uretprobe:/path/to/binary:func_name

機制
內核在 user binary 的目標地址插入 trap，process 執行到時觸發 BPF 程式。
引數
用 argN（無 BTF，需手動 cast）。若有 DWARF debug info，bpftrace 0.x 仍保留部分 uprobe args 解析。
觀察範圍
掛上後，所有執行該 binary 的 process 都會觸發。用 -p PID 限定單一 process。

基本範例

uprobe:/bin/bash:readline {
  printf("bash readline triggered by pid=%d\n", pid);
}

uretprobe:/bin/bash:readline {
  // retval 是 char *，是使用者剛輸入的那行
  printf("user typed: %s\n", str(retval));
}

偏移與位址

// 在函式進入後第 16 byte（少見但偶爾用到）
uprobe:./myapp:my_func+16 { ... }

// 直接以 binary 內 offset 指定
uprobe:./myapp:0x401040 { ... }

限定 process

// 用 -p $PID 後，uprobe 自動限定該 process
sudo bpftrace -p 1234 -e '
uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
  @[ustack] = count();
}'

C++ demangle

C++ 函式名在 binary 裡是 mangled 的（如 _ZN4Foo3barEv）。:cpp 前綴會啟用 demangle 比對：

uprobe:./myapp:cpp:Foo::bar { ... }

另外 stack trace 印 C++ 符號時也需要設定：

config = { cpp_demangle = true; }   // 預設就是 true
profile:hz:99 { @[ustack] = count(); }

⛔ Go runtime 與 uretprobe 的衝突

內核實作 uretprobe 的方式是偷偷竄改 user stack 上的 return address。Go runtime 會把這當成 stack corruption 觸發 panic。

追 Go 程式的鐵律：

  • 能用 uprobe（進入點）就絕對不要用 uretprobe。
  • 需要拿返回值時，找呼叫端的 uprobe（在 caller 取得返回值後再掛）。
  • 或改用 USDT、tracepoint，從 Go 的 runtime hook 切入。

⚠️ inline 函式抓不到

編譯器 inline 後的函式不存在獨立位址，uprobe 抓不到。對策：

  • 編譯時加 -fno-inline（適用於除錯版）。
  • 追它的 caller。
  • 檢查 binary 是否被 strip：nm /path/to/bin | grep funcname。

15.2 USDT（User-level Statically Defined Tracing）

usdt / U

usdt:/path/to/binary:provider:probe_name { ... arg0..argN ... } usdt:/path/to/binary:probe_name (省略 provider)

機制
程式編譯時用 SDT macro（STAP_PROBE 等）埋下的使用者層 tracepoint。在執行檔的 .note.stapsdt section 留下中繼資料。
vs uprobe
USDT 點是程式作者明確設計的，名稱與 args 跨版本相對穩定。
常見 provider
postgres、node、python、ruby、redis、mysqld、libpthread、libc（glibc 與部分 musl）。

USDT semaphore 與 file activation

有些 USDT 用 semaphore 機制 —— 程式檢查「有沒有人在追蹤」，沒人在追就跳過 USDT 點以節省成本。bpftrace 啟動時必須做某件事讓 semaphore 開啟：

情境處理方式
內核支援 uprobe refcount（5.6+ 多數 distro 已啟用）自動處理，無需手動操作
限定追特定 PID-p $PID
追蹤系統上所有執行該 binary 的 process--usdt-file-activation
用 -c CMD 啟動 child 並追它-c "/path/to/app args"
 
sudo bpftrace --info 2>&1 | grep "uprobe refcount"
# bcc bpf_attach_uprobe refcount: yes
# uprobe refcount (depends on Build:bcc bpf_attach_uprobe refcount): yes

⚠️ --usdt-file-activation 的限制

  • 只在 attach 當下掃一次。後來才啟動的 process 抓不到。
  • 用檔案路徑比對。容器內的 process 從容器外抓會失敗（路徑不同）—— 對策：把 bpftrace 跑進對應的 mount namespace 裡。

啟動 child process 並追蹤

// 用 -c 啟動程式時，cpid 是該 child 的 PID
usdt:./myapp:my_provider:my_probe /pid == cpid/ {
  printf("child fired probe with arg=%d\n", arg0);
}
sudo bpftrace -c "./myapp arg1 arg2" myscript.bt

CHAPTER 16 進階探針 (watchpoint) 與探針組合策略 🛠 開發 ⚙️ SRE

watchpoint 是 CPU 級的記憶體存取監視；組合策略則決定一支腳本在 production 該掛幾條探針 —— 這是初學與資深的分水嶺。

16.1 watchpoint

watchpoint

watchpoint:ADDRESS:LENGTH:MODE { ... } MODE: r (read) / w (write) / x (execute) / 組合如 rw / rwx

機制
使用 CPU debug register（x86 DR0–DR3、arm64 watchpoint registers），在指定記憶體位址被讀/寫/執行時觸發。
數量限制
x86_64 最多同時 4 個 watchpoint（硬體限制）。
LENGTH
必須是 1 / 2 / 4 / 8（bytes），且位址需對齊。

⛔ 0.25 變更：watchpoint:func+arg 已移除

0.24 之前的 watchpoint:my_func+arg2:8:rw 與 asyncwatchpoint 變體，0.25 起不再支援。需要監視函式參數指向的記憶體，得自己分兩步：先 kprobe 進入函式取位址，再用 watchpoint + 該位址（透過 $1 等位置參數傳入）。

監視 kernel 中的某個全域變數寫入

# 找位址
grep some_global_var /proc/kallsyms
# ffffffff828dd140 B some_global_var

sudo bpftrace -e '
watchpoint:0xffffffff828dd140:8:w {
  printf("%s wrote to some_global_var: %d\n", comm, *(uint64*)0xffffffff828dd140);
}'

典型應用場景

  • 除錯：誰寫到了不該寫的 kernel 結構欄位。
  • 反編譯：追蹤 user binary 內某個全域變數被改的時機。
  • 記憶體損毀：定位寫到不該寫的 heap/stack 區域。

16.2 探針組合策略：寫好 production 腳本的關鍵

同樣是「追 vfs_read 延遲」，三種寫法的成本差異可達 10 倍：

寫法 A — 過於粗糙

// 每次 read 都 push 一筆事件給 user space → 高頻 syscall 機器會吐到 ringbuffer 滿
kprobe:vfs_read {
  printf("%s read %d bytes\n", comm, arg2);
}

寫法 B — 較佳，使用聚合

// 在 kernel 內聚合，user space 只在程式結束時讀一次 map
kprobe:vfs_read {
  @bytes[comm] = sum(arg2);
  @count[comm] = count();
}

寫法 C — production 級，加 predicate + 限定 PID + 用 fentry

// 1. fentry 比 kprobe 快 10 倍以上
// 2. predicate 在 BPF 內就能砍掉不關心的事件
// 3. 用 hist 取代 sum，可看延遲分布
let @start = lruhash(8192);

fentry:vfs_read /pid == $1/ {
  @start[tid] = nsecs;
}

fexit:vfs_read /has_key(@start, tid)/ {
  @lat = hist((nsecs - @start[tid]) / 1us);
  delete(@start, tid);
}

16.3 效能評估清單

每加一個 probe，問自己以下五個問題：

問題典型答案
1. 觸發頻率多高？ perf stat -e 或 perf top 先量。10k/s 以下可放心；>100k/s 要小心。
2. action 多複雜？ 單純 count() < printf << kstack/ustack
3. 用對 probe 類型？ tracepoint > fentry > kprobe（成本由低到高）
4. predicate 能否前置？ 用更窄的 probe（tracepoint:syscalls:sys_enter_openat 比 wildcard kprobe:do_sys_open* 好）
5. 輸出量是否暴衝？ 能聚合就聚合，避免每事件 printf。

16.4 production 腳本必備 8 項

📌 上 production 前的檢查清單

  1. 明確宣告 map type 與容量（let @m = lruhash(N);）。
  2. 限定 PID 或 comm，避免追到 noise。
  3. 用 fentry / tracepoint 而非 kprobe，除非別無選擇。
  4. 聚合在 kernel 內，避免每事件 printf。
  5. retprobe 配合 has_key 檢查，並 delete() 釋放。
  6. 長跑加 interval:s:N 定期 flush，並 clear()。
  7. 設好 missing_probes（production 通常用 warn 而非 error）。
  8. 先在 staging 用 --dry-run 與測試環境跑過。
