📌 排查心法

  • 從症狀出發，不從工具出發。不要看到問題就開所有 probe，先想「我要驗證什麼假設」。
  • 分布比平均重要。p50 健康、p99 爛 → hist 才看得出。
  • 配對追蹤 > 一次採樣。entry+exit 量延遲遠比單點 profile 精準。

事件 1 — 神秘高 CPU：火焰圖找不到熱點

📞 14:32 — 收到告警

監控顯示某 host CPU usage 從平常 30% 漲到 88%，top 指出 api-server 占用 6 核 CPU。但 latency 也只翻倍，看似「就是 CPU 變忙」—— 然而 traffic 沒變、QPS 沒變。

📊 第一輪：採樣熱點函式

標準操作 —— 採樣 30 秒、產生火焰圖：

profile:hz:99 /comm == "api-server"/ {
  @[ustack(perf, 32), comm] = count();
}
interval:s:30 { exit(); }

火焰圖出來 —— 結果一片平坦。沒有任何函式占超過 5%，所有時間散在數百個 worker thread 的 epoll_wait 等等，看不出熱點。

⚠️ 經驗訊號：火焰圖平坦但 CPU 高

這是典型的「看似在跑但實際在等」模式。火焰圖只記錄「那一瞬間正在執行的函式」—— 如果 thread 大部分時間在 spin（busy-wait）、輪詢、或 thrashing，火焰圖會顯示成均勻分布。
下一步要看的是：「這些 thread 是真的在幹活，還是在反覆做沒意義的事？」

📊 第二輪：scheduler 行為觀察

// 量該 process 的 context switch 與 wakeup 頻率
tracepoint:sched:sched_switch /args.prev_comm == "api-server"/ {
  if (args.prev_state == 0) {
    @ctx_invol[args.prev_pid] = count();
  } else {
    @ctx_vol[args.prev_pid] = count();
  }
}

tracepoint:sched:sched_wakeup /str(args.comm) == "api-server"/ {
  @wakeup[args.pid] = count();
}

interval:s:10 { exit(); }
@ctx_invol[12347]:    8421     ← 被搶 8K 次/10秒
@ctx_invol[12348]:    7892
@ctx_vol[12347]:        12     ← 主動 sleep 只有 12 次！
@ctx_vol[12348]:         8
@wakeup[12347]:         34

線索浮現：thread 幾乎不主動 sleep（voluntary 極少）、被 preempt 千次（involuntary 高）。這是thread 一直跑、沒在等任何事件的訊號 —— 通常是busy loop。

📊 第三輪：抓 syscall + futex 行為

// 看 api-server 在做什麼 syscall（高頻 = 線索）

  @[syscall_name(args.id)] = count();
}

每秒 18 萬次 futex！正常情況頂多幾百次。futex 通常用於 mutex / condition variable —— 18 萬次/秒表示嚴重的鎖競爭。

📊 第四輪：抓 futex 上的 stack

Cache::lookup 內的 mutex 是元兇。下一步檢查該 cache 實作：

$ git log --since="1 week ago" -- src/cache.cpp
commit a1b2c3d - "Switch cache to global mutex (was sharded)"

🎯 Root Cause

一週前的 commit 把分片 mutex（256 把鎖）改成單一全域 mutex，理由是「程式碼比較簡單」。流量低時測不出問題，正式環境週中流量峰值期就觸發鎖爭用 —— 所有 worker thread 在 cache 上互搶。

💡 學到什麼

  • 火焰圖平坦不代表沒事，可能是鎖競爭把時間分散到 spin / context switch。
  • voluntary 與 involuntary context switch 比例是判斷 thread 是「真忙」還是「在等」的好信號。
  • syscall 分布看 futex 比例是定位鎖競爭最直接的方法。
  • 修復後可常駐這支腳本當 canary：每分鐘檢查 futex/sec，超過閾值就告警。

事件 2 — 磁碟突然慢：從 application 一路追到 NVMe queue

📞 02:18 — PagerDuty 響

PostgreSQL 主庫 commit latency p99 從 5ms 飆到 100ms+。應用回報 5xx 增加，下游 timeout。

📊 第一輪：iostat 給出粗略訊號

iostat -xz 1 5
Device  r/s  w/s  rkB/s  wkB/s  await  %util
nvme0n1 50  3200   1024  41200   45.2   98.5    ← 異常！

NVMe 居然 await 45ms、util 接近滿。但 iostat 看不出「為什麼」。bpftrace 切入。

📊 第二輪：跨層延遲分布

同時量三層延遲，比較哪一層最先出問題：

// 多層 latency 比較
let @vfs_start = lruhash(8192);
let @blk_start = lruhash(8192);

// VFS write 層
fentry:vfs_write {
  @vfs_start[tid] = nsecs;
}
fexit:vfs_write /has_key(@vfs_start, tid)/ {
  @vfs_us = hist((nsecs - @vfs_start[tid]) / 1000);
  delete(@vfs_start, tid);
}

// Block layer
tracepoint:block:block_rq_issue {
  @blk_start[args.dev, args.sector] = nsecs;
}
tracepoint:block:block_rq_complete
/has_key(@blk_start, (args.dev, args.sector))/ {
  @blk_us = hist((nsecs - @blk_start[args.dev, args.sector]) / 1000);
  delete(@blk_start, (args.dev, args.sector));
}

📊 第五輪：確認 some-batch-job 是誰

tracepoint:sched:sched_process_exec
/strcontains(str(args.filename), "batch")/ {
  printf("[%s] %d %s\n",
         strftime("%H:%M:%S", nsecs),
         pid, str(args.filename));
}
[02:00:01] 28471 /usr/local/bin/log-archive.sh
[02:00:01] 28472 /usr/bin/gzip
[02:00:01] 28473 /usr/bin/tar

🎯 Root Cause

一個 cron 排程在 02:00 啟動的 log archive 腳本，把當天 50GB 的 log 跨硬碟複製打包。沒設 ionice 也沒走 cgroup throttle，把 NVMe 寫頻寬完全占滿，page cache writeback 排隊塞住 PostgreSQL 的 fsync。

💡 學到什麼

  • kworker 在 block_rq_issue 出現大量寫幾乎必然是 page cache writeback —— 真正的元兇在 VFS 層。
  • iostat 看到 await 高只能告訴你「磁碟在排隊」，不能告訴你「誰把它塞滿」。bpftrace 從 block_rq_issue 倒推 process 是黃金第一步。
  • 長期解：把 log-archive 放進獨立 cgroup，限 IO weight；或改成 trickle write（rate-limit）。
  • 偵測解：常駐一支腳本看 kworker bytes/sec，超過閾值就告警，比 iostat 早 30 分鐘預警。
NETWORK SEV-2 持續 ~ 30 分鐘 影響：對外 API 連線間歇失敗

事件 3 — 連線雪崩：TIME_WAIT 與 conntrack 滿表

📞 09:50 — 警報：對下游 API 連線 timeout

應用 log 出現 connect: cannot assign requested address 與 connect: connection timed out 混合，比例約 1:1。兩種錯誤的根因不同 —— 必須分開排查。

📊 觀察 socket 狀態分布

ss -s
# Total: 245
# TCP:   220 (estab 12, closed 198, ...)
# 198 closed!

ss -tan state time-wait | wc -l
# 28473    ← TIME_WAIT 爆量

線索 1：local port 被 TIME_WAIT 用光，所以 cannot assign requested address。

cat /proc/sys/net/netfilter/nf_conntrack_count
# 524288
cat /proc/sys/net/netfilter/nf_conntrack_max
# 524288    ← 滿了！

dmesg | grep conntrack | tail
# nf_conntrack: table full, dropping packet

線索 2：conntrack 表也滿，新封包被 drop → connection timed out。

📊 用 bpftrace 看連線建立速度

tracepoint:tcp:tcp_set_state {
  if (args.newstate == 1) {       // ESTABLISHED
    @new_conn = count();
  }
  if (args.newstate == 7) {        // CLOSE
    @closed = count();
  }
  if (args.newstate == 6) {        // TIME_WAIT
    @time_wait = count();
  }
}

interval:s:5 {
  printf("EST=%d CLS=%d TW=%d\n", @new_conn, @closed, @time_wait);
  clear(@new_conn); clear(@closed); clear(@time_wait);
}
EST=4823 CLS=4801 TW=4792
EST=5102 CLS=5089 TW=5080
EST=4978 CLS=4965 TW=4958

每秒近 5000 連線開／關。極短連線 → 每個 TIME_WAIT 占 ~60 秒 → 每 60 秒累積 30 萬 TIME_WAIT。

📊 找出短連線元兇

let @start = lruhash(16384);

// 連線建立時記時間
tracepoint:tcp:tcp_set_state /args.newstate == 1/ {
  @start[args.skaddr] = nsecs;
  @comm[args.skaddr] = comm;
}

// 連線關閉時量壽命
tracepoint:tcp:tcp_set_state /args.newstate == 7 && has_key(@start, args.skaddr)/ {
  let $life_us = (nsecs - @start[args.skaddr]) / 1000;
  @lifetime[@comm[args.skaddr]] = hist($life_us);
  delete(@start, args.skaddr);
  delete(@comm, args.skaddr);
}

interval:s:30 { exit(); }
END { clear(@start); clear(@comm); }
@lifetime[api-server]:
[256, 512)    412 |@@@@                                                |
[512, 1K)    1247 |@@@@@@@@@@@@@                                       |
[1K, 2K)     8421 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2K, 4K)     2147 |@@@@@@@@@@@@@                                       |

連線壽命中位數 1-2 ms 就關閉 → 每個 request 都 connect/close，沒做 connection pool。

🎯 Root Cause

新部署的 API client 函式庫沒啟用 keep-alive，每個 request 都發起新 TCP 連線。流量擴大後每秒 5000 連線，TIME_WAIT 與 conntrack 表雙雙爆滿。

🔧 緊急止血（buy time）

# 1. 擴大 conntrack 表（立即生效）
sudo sysctl -w net.netfilter.nf_conntrack_max=2097152

# 2. 縮短 TIME_WAIT（注意 — 副作用要評估）
sudo sysctl -w net.ipv4.tcp_fin_timeout=15

# 3. 擴大 ephemeral port 範圍
sudo sysctl -w net.ipv4.ip_local_port_range="10000 65000"

🔧 真正修復

應用端啟用 HTTP keep-alive + connection pool。修復後重跑同腳本：

@lifetime[api-server]:
[1K, 2K)        12 |                                                    |
[1M, 2M)       847 |@@@@@@@@@@                                          |
[2M, 4M)      4218 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
                                       ↑ 連線壽命幾秒 = 正常 keep-alive

💡 學到什麼

  • 連線壽命直方圖是判斷「短連線爛習慣」的最直接指標。
  • TIME_WAIT 與 conntrack 是兩個獨立資源，可以同時爆。診斷要分開看。
  • 調 sysctl 是 band-aid，真正的解永遠是應用端 connection pool。
  • 常駐監控：每分鐘看 TIME_WAIT 數 + conntrack 使用率，超 80% 就告警。

📞 全天間歇性收到 pod restart 告警

K8s pod 每 30-60 分鐘被殺一次。kubectl describe 顯示 OOMKilled，但應用 log 看不出洩漏 —— heap 使用穩定在 1.5G，cgroup limit 設 2G，理論上有餘裕。

📊 第四輪：cgroup memory 事件

# 看該 cgroup 的 memory.events
sudo cat /sys/fs/cgroup/kubepods.slice/.../pod-id.scope/memory.events
# low      0
# high     14523    ← 持續 throttle
# max      0
# oom      6        ← 6 次 OOM
# oom_kill 6

🎯 Root Cause

應用每 30 分鐘 mmap 一個 100GB 大檔做掃描。雖然應用本身的 RSS 不到 2GB，但 mmap + read 觸發 page cache 把該檔案的內容全部塞進 cgroup 的 memory accounting。
cgroup memory limit 包含 RSS + page cache。當 indexing job 跑時 page cache 在這個 cgroup 內快速膨脹，超過 limit → kernel 嘗試 direct reclaim → 失敗 → OOM kill。

💡 學到什麼

  • cgroup OOM 不等於 RSS 過高。Page cache 也算進去；mmap 大檔特別容易踩到。
  • direct reclaim 大量出現是 OOM 將至的明確訊號 —— 監控可從這裡早期預警。
  • 修復方案：
    • 給 indexing job 用 posix_fadvise(POSIX_FADV_DONTNEED) 主動釋放 page cache。
    • 或改用 streaming read 而非 mmap 整個 100GB 檔。
    • 調大 cgroup memory limit（短期 band-aid）。
  • 常駐監控：memory.events 的 high/oom 計數變化 + direct reclaim 頻率。
CROSS-TEAM SEV-3 爭執 ~ 2 天 應用團隊 vs 平台團隊

事件 5 — 跨團隊責任歸屬：「應用慢」還是「底層慢」

背景

應用團隊抱怨：「我們的服務 latency p99 從 200ms 漲到 800ms，是平台問題！」
平台團隊回應：「我們的指標都正常 —— CPU、磁碟、網路都沒滿。是你們的應用問題！」

兩邊吵了兩天沒結論。SRE 介入，目標：用客觀數據確認延遲到底發生在哪一層。

📊 跨層延遲量測腳本

核心方法：在同一個 request 的生命週期裡，量每一層的延遲。串接 syscall → VFS → block 三層。

// cross_layer.bt — 跨層 latency 比較
let @app_start  = lruhash(16384);
let @vfs_start  = lruhash(16384);
let @blk_start  = lruhash(16384);

// (1) Application 層：用 USDT
usdt:/usr/lib/api-server:api:request_start {
  @app_start[tid] = nsecs;
}

// (2) Syscall 層：每個 read/write
tracepoint:syscalls:sys_enter_read,
tracepoint:syscalls:sys_enter_write
/has_key(@app_start, tid)/ {
  @sys_start[tid] = nsecs;
}

tracepoint:syscalls:sys_exit_read,
tracepoint:syscalls:sys_exit_write
/has_key(@sys_start, tid)/ {
  @syscall_us = hist((nsecs - @sys_start[tid]) / 1000);
  delete(@sys_start, tid);
}

// (3) VFS 層
fentry:vfs_read, fentry:vfs_write { @vfs_start[tid] = nsecs; }
fexit:vfs_read, fexit:vfs_write /has_key(@vfs_start, tid)/ {
  @vfs_us = hist((nsecs - @vfs_start[tid]) / 1000);
  delete(@vfs_start, tid);
}

// (4) Block 層
tracepoint:block:block_rq_issue { @blk_start[args.dev, args.sector] = nsecs; }
tracepoint:block:block_rq_complete /has_key(@blk_start, (args.dev, args.sector))/ {
  @block_us = hist((nsecs - @blk_start[args.dev, args.sector]) / 1000);
  delete(@blk_start, (args.dev, args.sector));
}

// (5) Application total
usdt:/usr/lib/api-server:api:request_done /has_key(@app_start, tid)/ {
  @app_ms = hist((nsecs - @app_start[tid]) / 1ms);
  delete(@app_start, tid);
}

interval:s:60 { exit(); }
END { clear(@app_start); clear(@vfs_start); clear(@blk_start); }

🔍 解讀

數字攤開來給雙方看：

  • Application 層 (USDT)：p99 ~ 1.6 秒，慢。
  • Syscall 層：p99 ~ 16µs，正常。
  • VFS 層：p99 ~ 8µs，正常。
  • Block 層：p99 ~ 1ms，NVMe 完全健康。

應用看到的 1.6 秒，扣掉所有 syscall + VFS + block 加總（最壞 ~10ms），剩下 1.59 秒是純應用 CPU 邏輯 —— 不在 kernel、不在磁碟、不在網路。

📊 進一步精準定位應用內部

// 看應用內部哪段邏輯慢 — off-CPU 分析
tracepoint:sched:sched_switch
/args.prev_comm == "api-server" && args.prev_state != 0/ {
  @offcpu[args.prev_pid] = nsecs;
}

tracepoint:sched:sched_switch
/has_key(@offcpu, args.next_pid)/ {
  let $delta_ms = (nsecs - @offcpu[args.next_pid]) / 1ms;
  if ($delta_ms > 100) {
    @slow_waits[kstack(8)] = count();
  }
  delete(@offcpu, args.next_pid);
}

interval:s:30 { exit(); }
@slow_waits[
    futex_wait_queue+...
    ...
    runtime.gopark()           ← Go runtime
    sync.(*Mutex).Lock+...
    cache.(*store).Get+...     ← 應用程式 cache 鎖

🎯 Root Cause

應用程式內部的 cache mutex 競爭。最近的 deploy 增加了 cache 寫入頻率，但 mutex 沒對應改進。慢的不是 kernel、不是磁碟，是應用等自己的鎖。

平台層各層延遲指標都健康 —— 平台真的沒問題。應用團隊一開始的「平台問題」是錯誤歸因。

💡 學到什麼

  • 跨層 latency 比較是仲裁神器：當「應用慢 vs 底層慢」爭論時，把每層數字攤開來，誰也不能耍賴。
  • Application USDT 是必備：沒有應用層的 USDT，就無法區分「應用內部」與「應用呼叫的 syscall」。值得在重要服務埋幾個關鍵 USDT 點。
  • off-CPU + stack是定位「應用在等什麼」的最後一哩 —— 用 stack 直指有問題的程式碼路徑。
  • 用客觀數據而非主觀爭論：bpftrace 給 SRE 跨團隊問題定位的客觀立場。

32.6 五個事件的共通模式

事件第一線症狀關鍵 bpftrace 步驟意外的 root cause
1. 高 CPU火焰圖平坦syscall 分布看到 futex 占 90%Mutex 從分片改全域
2. 磁碟慢iostat util 100%block_rq_issue 看到 kworker 大量寫Cron log archive 沒做 throttle
3. 連線雪崩EADDRNOTAVAIL連線壽命 hist 中位 1msClient lib 沒開 keep-alive
4. OOMRSS 沒爆cgroup page cache 觀察mmap 大檔填滿 cgroup memory
5. 跨團隊各執一詞跨層 latency 比較應用內部鎖競爭（不關平台事）

📌 共通方法論

  1. 從監控告警開始，先用 OS 工具縮範圍（top / iostat / ss / dmesg）。
  2. bpftrace 切入時先量分布（hist），不要單純印事件。
  3. 看到分布不對勁，加 stack trace 找到具體程式碼路徑。
  4. 跨層比對：把症狀層、中間層、根因層的延遲全攤開，誰最慢就找誰。
  5. 修復後常駐 canary 腳本：把這次學到的指標化為長期監控。
