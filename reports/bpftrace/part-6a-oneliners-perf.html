CHAPTER 26 One-liner 速查與設計模式 🔰 初學 ⚙️ SRE

把最常用的觀測場景濃縮成一行 —— 這些 one-liner 是日常排查的「肌肉記憶」，記住後 production 問題第一線處理速度會明顯提升。

26.1 通用設計模式

One-liner 的力量在於「用最少的字元換最多的資訊」。所有 one-liner 都圍繞這四種設計模式：

誰觸發了這個事件最多次？」 key 可換 comm / pid / probe / args.x 最常用、最便宜、可上 production PATTERN B — DISTRIBUTION @ = hist(value); 「分布是什麼樣？有 outlier 嗎？」 value 可換 args.bytes / latency / ret 值 看出長尾分布、雙峰 PATTERN C — ENTRY/EXIT TIMING @s[tid]=nsecs → ret: hist(now-@s[tid]) 量延遲 / 持續時間 需要 has_key + delete PATTERN D — SAMPLED STACK profile:hz:99 { @[ustack]=count(); } 採樣熱點函式呼叫鏈 餵給 FlameGraph 工具產生火焰圖

26.2 Syscall 速查

各 process 的 syscall 次數

sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

各 syscall 的呼叫次數

sudo bpftrace -e '
tracepoint:raw_syscalls:sys_enter { @[syscall_name(args.id)] = count(); }
interval:s:5 { print(@, 15); clear(@); }'

看誰開了什麼檔

sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat {
  printf("%-16s %s\n", comm, str(args.filename));
}'

看誰執行了什麼程式（含參數）

sudo bpftrace -e '
tracepoint:syscalls:sys_enter_execve {
  printf("[%d] ", pid);
  join(args.argv);
}'

read 大小分布

sudo bpftrace -e '
tracepoint:syscalls:sys_exit_read /args.ret > 0/ {
  @ = hist(args.ret);
}'

失敗的 syscall（帶 errno）

sudo bpftrace -e '
tracepoint:raw_syscalls:sys_exit /(int64)args.ret < 0/ {
  @[syscall_name(args.id), -(int64)args.ret] = count();
}'

26.3 Process 與 scheduler 速查

觀察新 process

sudo bpftrace -e '
tracepoint:sched:sched_process_exec {
  printf("[%d] %s\n", pid, str(args.filename));
}'

觀察 process 退出（含 exit code）

sudo bpftrace -e '
tracepoint:sched:sched_process_exit {
  printf("[%d] %s exit\n", pid, comm);
}'

fork 風暴觀測

sudo bpftrace -e '
tracepoint:sched:sched_process_fork {
  @[args.parent_comm] = count();
}'

所有 sched_* 事件分布

sudo bpftrace -e 'tracepoint:sched:sched_* { @[probe] = count(); }'

26.4 I/O 速查

Block I/O 大小分布

sudo bpftrace -e '
tracepoint:block:block_rq_issue { @ = hist(args.bytes); }'

各 process 的 block I/O 量

sudo bpftrace -e '
tracepoint:block:block_rq_issue {
  @bytes[comm] = sum(args.bytes);
}'

VFS 操作頻率

sudo bpftrace -e 'kprobe:vfs_* { @[probe] = count(); }'

26.5 網路速查

新 TCP 連線

sudo bpftrace -e '
tracepoint:tcp:tcp_set_state /args.newstate == 1/ {
  printf("%s -> established\n", comm);
}'

TCP 重傳

sudo bpftrace -e '
tracepoint:tcp:tcp_retransmit_skb { @ = count(); }'

各 process 的 TCP 送出 bytes

sudo bpftrace -e '
fentry:tcp_sendmsg { @bytes[comm] = sum(args.size); }'

26.6 Memory 速查

Page faults by process

sudo bpftrace -e '
software:faults:1 { @[comm] = count(); }'

Major page faults（會 disk read）

sudo bpftrace -e '
software:major-faults:1 { @[comm] = count(); }'

kmalloc 大小分布

sudo bpftrace -e '
tracepoint:kmem:kmalloc { @ = hist(args.bytes_alloc); }'

26.7 信號與 OOM 速查

觀察被發送的信號

sudo bpftrace -e '
tracepoint:signal:signal_generate {
  printf("%s -> pid %d (sig=%d)\n", comm, args.pid, args.sig);
}'

OOM kill 觀測

sudo bpftrace -e '
kprobe:oom_kill_process {
  printf("OOM: %s killed by %s\n", comm, ksym(reg("ip")));
}'

26.8 套用模式：自製 one-liner

有了模式 + builtin 名單，所有 one-liner 都可以即興。三步驟：

  1. 挑問題類型 → 對應 Pattern A/B/C/D。
  2. 挑 probe → 用 bpftrace -l 'tracepoint:<cat>:*' 探索。
  3. 挑 key / value → 從 -lv 看到的 args 挑欄位。

例：「想看哪個 process 觸發最多 page allocation」

  • Pattern A — count by key。
  • probe → tracepoint:kmem:mm_page_alloc。
  • key → comm。
sudo bpftrace -e '
tracepoint:kmem:mm_page_alloc { @[comm] = count(); }'

💡 把常用 one-liner 存成 alias

# ~/.bashrc
alias trace-syscalls='sudo bpftrace -e "tracepoint:raw_syscalls:sys_enter { @[syscall_name(args.id)] = count(); } interval:s:5 { print(@, 15); clear(@); }"'
alias trace-execs='sudo bpftrace -e "tracepoint:syscalls:sys_enter_execve { printf(\"[%d] \", pid); join(args.argv); }"'

CHAPTER 27 系統效能診斷 ⚙️ SRE 🛠 開發

CPU 採樣 · 火焰圖前處理 · page fault · context switch · scheduler latency · off-CPU · run queue —— 把整台機器的效能問題拆成可量化的維度。

27.1 CPU 採樣與火焰圖

CASE 27-1

CPU 使用率突然飆高，誰是元兇？

監控顯示某主機 CPU 從 30% 飆到 95%，但 top 看不出明顯的單一行程。

第一步：採樣 + 統計各 process 的 CPU 時間

profile:hz:99 {
  @[comm] = count();
}

interval:s:30 { exit(); }
@[node]: 287
@[chrome]: 145
@[postgres]: 89
@[bpftrace]: 12
...

看出 node 是首要嫌疑犯。再深入挖：

第二步：採樣該 process 的 user stack

profile:hz:99 /comm == "node"/ {
  @[ustack] = count();
}

第三步：產生火焰圖

# 30 秒採樣 → 產生 stackcollapse 格式
sudo bpftrace -e '
profile:hz:99 /comm == "node"/ { @[ustack(perf), comm] = count(); }
interval:s:30 { exit(); }' > profile.txt

# 用 FlameGraph 工具產出 SVG
git clone https://github.com/brendangregg/FlameGraph
./FlameGraph/stackcollapse-bpftrace.pl profile.txt | \
  ./FlameGraph/flamegraph.pl --title="Node CPU" > flame.svg

# 用瀏覽器開啟 flame.svg
xdg-open flame.svg

💡 容器化環境用 build_id mode

// 0.25 build_id mode 適合在 host 採樣容器內 process
profile:hz:99 { @[ustack(build_id, 32)] = count(); }

採樣後可以拿到 build_id + 位址，再從原始 binary 解析符號（含 debug info），不需要 host 與 container 共用 binary 路徑。

27.2 Off-CPU 分析（為什麼程式在等？）

火焰圖顯示「程式跑在哪」—— 但很多時候問題是「程式沒在跑、在等」。Off-CPU 分析把這個盲區補上。

CASE 27-2

應用 latency p99 不穩，CPU 卻沒滿

服務 latency 偶爾飆到秒級，但機器 CPU 用量只有 40%，看不出明顯 hot path。

追蹤每次 thread 從 sleep 醒來的等待時間 + stack

let @start = lruhash(8192);

// thread 從 running 變 not-running（要去 sleep）
tracepoint:sched:sched_switch
/args.prev_state != 0/ {     // != TASK_RUNNING
  @start[args.prev_pid] = nsecs;
  @stack[args.prev_pid] = kstack;
}

// 同一 thread 被喚醒回 CPU
tracepoint:sched:sched_switch
/has_key(@start, args.next_pid)/ {
  let $delta = nsecs - @start[args.next_pid];
  @offcpu_us[@stack[args.next_pid], args.next_comm] = hist($delta / 1000);
  delete(@start, args.next_pid);
  delete(@stack, args.next_pid);
}

輸出告訴你：每個 thread 平均在哪段 kernel code 等待、等多久。常見模式：

@offcpu_us[
    futex_wait_queue_me+...
    do_futex+...
    __x64_sys_futex+...
    , postgres
]:
[1K, 2K)        342 |@@@@@                                      |
[2K, 4K)       1235 |@@@@@@@@@@@@@@@@                           |
[4K, 8K)       3897 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[8K, 16K)       154 |@@                                         |

看到大量時間花在 futex_wait_queue_me → 鎖競爭。下一步追 lock：用 fentry:__sched_text_start 等 probe 進一步分析。

27.3 Run queue latency（排程延遲）

Process 已 runnable 但還沒拿到 CPU 的時間 —— 通常表示 CPU 飽和或 nice / cgroup CPU limit 在限縮。

CASE 27-3

高 load average 但 CPU 用量低

load1 高達 50，但所有 CPU 加總用量只有 70% —— 有大量 thread 在 run queue 排隊。

量測 run queue 等待時間

let @qtime = lruhash(8192);

// thread 進入 runnable
tracepoint:sched:sched_wakeup,
tracepoint:sched:sched_wakeup_new {
  @qtime[args.pid] = nsecs;
}

// 真正拿到 CPU
tracepoint:sched:sched_switch
/has_key(@qtime, args.next_pid)/ {
  @runqueue_us = hist((nsecs - @qtime[args.next_pid]) / 1000);
  delete(@qtime, args.next_pid);
}
@runqueue_us:
[0]              125 |                                                  |
[1]            12483 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2, 4)          8941 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@               |
[4, 8)          3215 |@@@@@@@@@@@@@                                     |
[8, 16)         1124 |@@@@                                              |
[16, 32)         415 |@                                                 |
[32, 64)         142 |                                                  |
[64, 128)         38 |                                                  |
[128, 256)        12 |                                                  |
[256, 512)         3 |                                                  |
[512, 1K)          1 |                                                  |
[1K, 2K)           1 |                                                  |

p99 約 32-64µs 還算健康；如果出現 [>1ms] 範圍的 bucket，就是嚴重排程延遲。

27.4 Page fault 分析

CASE 27-4

應用啟動後第一次處理請求很慢

服務剛啟動時前幾秒 latency 高，之後就正常 —— 經典的 page fault 模式（lazy memory allocation）。

觀察 minor / major faults 與來源

// minor fault：頁面已在 RAM，只是要建 mapping
software:minor-faults:1 {
  @minor[comm] = count();
}

// major fault：要從磁碟讀
software:major-faults:1 {
  @major[comm] = count();
  @major_stack[ustack] = count();   // 哪段 code 觸發
}

interval:s:5 {
  printf("\n=== 5s window ===\n");
  print(@minor); print(@major);
  clear(@minor); clear(@major);
}

major fault 多 → 可能要 mlock 重要區域、或預先 touch 記憶體（warmup）；minor fault 多但 major 少 → 通常正常的 demand paging。

27.5 Context switch 觀察

每秒 context switch 次數（含類別）

tracepoint:sched:sched_switch {
  // prev_state 0 = preempted, 非 0 = voluntary
  if (args.prev_state == 0) {
    @involuntary[args.prev_comm] = count();
  } else {
    @voluntary[args.prev_comm] = count();
  }
}

interval:s:5 {
  printf("\n--- involuntary (preempted) ---\n");
  print(@involuntary, 10);
  printf("\n--- voluntary (sleeping) ---\n");
  print(@voluntary, 10);
  clear(@involuntary);
  clear(@voluntary);
}

📌 解讀 context switch

  • 大量 voluntary：thread 主動 sleep（等 I/O、等鎖、等 condition variable）。可能是正常 event loop。
  • 大量 involuntary：被排程器強制換下。CPU 飽和或同類 priority thread 太多時會出現。
  • Voluntary 暴增 + 應用 latency 變差：高機率是鎖競爭。

27.6 CPU 跨 NUMA migration

Thread 跨 NUMA node 遷移會導致 cache miss 暴增，是極隱晦的效能殺手。

tracepoint:sched:sched_migrate_task {
  // 同一 NUMA node 內遷移（normal）vs 跨 NUMA
  // 每台機器的 CPU/NUMA 對應不同，可從 /sys/devices/system/cpu/cpuN/topology/physical_package_id 看

27.7 完整效能診斷腳本：cpu_diag.bt

整合本章技巧，做一個 production 級的「CPU 健檢」腳本：

#!/usr/bin/env bpftrace
// cpu_diag.bt - 30 秒系統 CPU 健檢

config = {
  max_map_keys = 16384;
  stack_mode   = perf;
}

let @runq    = lruhash(8192);
let @offcpu  = lruhash(8192);

BEGIN {
  printf("=== CPU diagnostic for 30s ===\n");
}

// (1) On-CPU 採樣
profile:hz:99 {
  @oncpu[comm] = count();
  @oncpu_stack[ustack(perf, 16), comm] = count();
}

// (2) Run queue latency
tracepoint:sched:sched_wakeup,
tracepoint:sched:sched_wakeup_new {
  @runq[args.pid] = nsecs;
}

tracepoint:sched:sched_switch /has_key(@runq, args.next_pid)/ {
  @runq_us = hist((nsecs - @runq[args.next_pid]) / 1000);
  delete(@runq, args.next_pid);
}

// (3) Off-CPU
tracepoint:sched:sched_switch /args.prev_state != 0/ {
  @offcpu[args.prev_pid] = nsecs;
}

tracepoint:sched:sched_switch /has_key(@offcpu, args.next_pid)/ {
  @offcpu_ms[args.next_comm] = hist(
    (nsecs - @offcpu[args.next_pid]) / 1000000);
  delete(@offcpu, args.next_pid);
}

// (4) Context switch
tracepoint:sched:sched_switch {
  if (args.prev_state == 0) {
    @ctxsw_invol[args.prev_comm] = count();
  } else {
    @ctxsw_vol[args.prev_comm] = count();
  }
}

// (5) Page faults
software:major-faults:1 { @majflt[comm] = count(); }

interval:s:30 { exit(); }

END {
  printf("\n--- (1) Top On-CPU processes ---\n");
  print(@oncpu, 15);

  printf("\n--- (2) Run queue latency (us) ---\n");
  print(@runq_us);

  printf("\n--- (3) Off-CPU latency by process (ms) ---\n");
  print(@offcpu_ms);

  printf("\n--- (4) Context switches ---\n");
  printf("Voluntary:\n");   print(@ctxsw_vol, 10);
  printf("Involuntary:\n"); print(@ctxsw_invol, 10);

  printf("\n--- (5) Major page faults ---\n");
  print(@majflt);

  // 清掉 verbose 的中間 map
  clear(@oncpu_stack); clear(@runq); clear(@offcpu);
}

💡 解讀流程

  1. 先看 (1)—哪個 process 占 CPU。
  2. 看 (2)—run queue latency 是否健康（p99 應 < 1ms）。
  3. 看 (3)—哪個 process 在等待，等多久。
  4. 看 (4)—involuntary 高表示 CPU 飽和；voluntary 高表示 I/O 或鎖密集。
  5. 看 (5)—大量 major fault 表示 working set > RAM。

這支腳本能在 30 秒內幫你回答 90% 的「機器為什麼慢」。

27.8 進階：用 fentry 抓特定函式延遲

當 profile + off-CPU 仍指不出明確元兇時，針對嫌疑函式細追：

// 查 vfs_read 的 latency 分布
fentry:vfs_read {
  @start[tid] = nsecs;
}

fexit:vfs_read /has_key(@start, tid)/ {
  let $dur = nsecs - @start[tid];
  delete(@start, tid);

  @lat_us = hist($dur / 1000);

  // 慢 read 抓 stack
  if ($dur > 50ms) {
    printf("[SLOW] %s vfs_read took %d ms\n", comm, $dur / 1ms);
    @slow_stacks[ustack] = count();
  }
}
