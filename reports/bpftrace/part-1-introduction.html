CHAPTER 01 認識 bpftrace 🔰 初學

在動手寫第一支腳本之前，先建立心智模型 —— bpftrace 是什麼、它觀察的是什麼、它與既有工具的分工。

1.1 什麼是 bpftrace

bpftrace（命令列縮寫 bpftrace，副檔名習慣使用 .bt）是一套高階動態追蹤語言，目標是讓 Linux 系統的觀測變得像寫小腳本一樣輕鬆。它的語法靈感來自 Sun 的 DTrace 與其衍生的 D 語言；底層則透過 LLVM 將腳本編譯成 eBPF bytecode，再經由 libbpf 與 bcc 函式庫送進 Linux 核心執行。

簡單一句話：bpftrace 讓你用幾行字，就能在不修改任何程式、不重啟任何服務的前提下，觀察整台機器（內核 + 使用者空間）正在發生什麼事。

📌 0.25 版本重點變更

本手冊以 0.25 為基準。相較 0.24 版有幾項與寫法直接相關的變化：

  • 結構欄位存取自動解參考：. 已能自動 dereference 指標，因此 $p.field 等同於 $p->field。-> 仍可使用，但官方建議改用 .。
  • exit() 不再允許在 for / unroll 等 loop 內呼叫。
  • 新增 Records 型別：類似 struct 的具名 tuple，例如 (color="green", size=2)。
  • 新增 pcomm、build_id stack mode、syscall_name()。
  • Macros、Map declarations 從 unstable 升為 stable。
  • 實驗性 watchpoint:func+arg / asyncwatchpoint:func+arg 已被移除。
  • 新增 CLI --fmt（自動格式化）。

1.2 與 BPF / eBPF / bcc / perf / ftrace 的關係

Linux 的觀測生態系工具繁多，名稱也容易混淆。以下用一張關係圖快速釐清。

圖 1.1 — bpftrace 在 Linux 觀測技術堆疊中的位置
BPF / eBPF
核心提供的「在 kernel 內安全執行受限制 byte code」的機制。早期叫 BPF（Berkeley Packet Filter，僅用於封包過濾），擴展後改稱 eBPF（extended BPF），現在多半混用。bpftrace 跑的就是 eBPF。
bcc
BPF Compiler Collection，較早期的工具集。用 Python/C++ 撰寫，彈性大、能做命令列參數處理與複雜輸出，但程式碼量多很多。bcc 與 bpftrace 是互補關係。
libbpf-tools
bcc 工具集的「CO-RE 純 C 版」。執行時不需編譯 BPF（因有 BTF），啟動快、體積小。
perf / ftrace
內核傳統追蹤工具。perf 善於採樣與 profiling、ftrace 善於 function tracing。bpftrace 可看作「把 perf + ftrace + 自定運算」整合成一種腳本語言。
BTF (BPF Type Format)
內核裡的型別中繼資料。有了 BTF，bpftrace 不需要安裝 kernel headers 就能存取 kernel 資料結構。幾乎所有現代 distro 都已預設啟用。

💡 何時選 bpftrace、何時升級到 bcc？

bpftrace：探索性追蹤、ad-hoc 排查、寫成短腳本長期保存。22 行能解的事不要寫 131 行。

bcc：需要複雜命令列參數（argparse）、客製化輸出格式、整合既有 Python 生態（資料分析、繪圖、寫進 DB）。

一條建議的開發路徑：one-liner → bpftrace 腳本 → 真的需要再升級到 bcc。

1.3 動態追蹤的核心概念

不論 DTrace、SystemTap、bpftrace，動態追蹤的核心觀念都圍繞著三件事：

概念在 bpftrace 裡長什麼樣說明
Probe（探針） kprobe:vfs_read
tracepoint:syscalls:sys_enter_open		 「要在哪個事件上掛勾」。事件可以是 kernel 函式進入、tracepoint、使用者程式函式、定時器、PMC 計數溢出 ⋯
Action（動作） { printf("%s\n", comm); } 探針事件觸發時要執行的 BPF 程式。能存取參數、寫入 map、印出資訊。
Map（聚合儲存） @count[pid] = count(); 跨探針事件共享、累計、聚合資料的容器。bpftrace 結束時預設會自動印出所有 map。

把這三件事串起來，你就能寫出「每次 X 事件發生時、把 Y 資料聚合到 Z map 裡」這種模式，而這正是觀測的本質。

1.4 適用場景與限制

✅ bpftrace 擅長的

  • 系統呼叫頻率、延遲分布、由誰發起。
  • 磁碟 I/O 延遲分布、檔案開啟次數、慢查詢溯源。
  • 網路連線生命週期、retransmit、TCP state 變化。
  • 排程延遲、context switch、CPU 使用率分析。
  • 應用層追蹤（USDT、uprobe），如 PostgreSQL、bash、Python、Node.js。
  • 內核函式行為驗證（修了某個 bug，實際呼叫路徑是否如預期）。

⚠️ 已知限制（這些是 BPF 本身的限制，bpftrace 也跟著繼承）

⚠️ 浮點數不支援

BPF 不允許浮點運算，因此 bpftrace 也沒有 float / double。需要小數時用整數縮放（例如時間用 ns、百分比 ×100）後再除回去。

⚠️ BPF stack 上限 512 bytes

每個探針的 BPF 程式 stack 最多 512 bytes。一旦你在腳本裡塞了大字串、多個 struct 副本、或一堆 local 變數，verifier 會直接拒絕載入。常見對策：

  • 用 pid 而不是 comm（節省 16 bytes）。
  • 降低 BPFTRACE_MAX_STRLEN（預設 1024，多數場景 64 已足）。
  • 把單一大探針拆成多個小探針。
  • 用 on_stack_limit config 把大物件移到 pre-allocated memory。

⚠️ Map 預設大小限制

max_map_keys 預設 4096。需要大量 key（例如以時間戳當 key 取樣 stack）時，要主動調高，但記憶體與啟動時間會跟著增加。

⚠️ uretprobe 與 Go runtime 衝突

內核為了實現 uretprobe，會在使用者函式進入時偷改 return address。Go 等有自己 runtime 的語言會偵測到 stack 異常，導致程式 panic。

實務上：追 Go 程式請優先用 uprobe（進入點），盡量避免 uretprobe，必要時用 stack frame 在進入時保存資訊。

⛔ 觀測也是有成本的

掛上一萬個 kprobe 的後果不是「資訊豐富」而是「機器卡住」。bpftrace 預設限制 max_probes=1024 就是要保護你。每加一個探針都要思考：觸發頻率 × 動作複雜度 = 系統開銷。Production 上線前一定要在測試環境量過。

CHAPTER 02 安裝、執行與第一支腳本 🔰 初學 ⚙️ SRE

2.1 各發行版安裝方式

bpftrace 早已被多數主流 distro 收錄。以下用一個指令列出最常見環境的安裝方式（各 distro 收錄的版本可能落後 upstream，需要最新版時建議用容器或自行編譯）。

Ubuntu / Debian

sudo apt update
sudo apt install -y bpftrace

# 驗證版本
bpftrace --version

Fedora / RHEL / Rocky / Alma

sudo dnf install -y bpftrace

Arch / Manjaro

sudo pacman -S bpftrace

用容器執行（推薦：總是拿到最新版本）

# quay.io 上有官方鏡像
sudo docker run -it --rm \
  --privileged \
  --pid=host \
  -v /sys/kernel/debug:/sys/kernel/debug \
  -v /lib/modules:/lib/modules:ro \
  -v /usr/src:/usr/src:ro \
  quay.io/iovisor/bpftrace:latest \
  bpftrace -e 'kprobe:do_nanosleep { printf("%d sleeping\n", pid); }'

💡 Production 機器選哪個版本？

多數 distro 倉庫的 bpftrace 版本會比 upstream 慢 1~2 個 minor 版本。0.25 包含的 Records、build_id stack mode、syscall_name() 等新功能，Debian/Ubuntu LTS 短期內不會有。如果你需要這些特性，請：

  • 用 quay.io/iovisor/bpftrace 容器；或
  • 從 GitHub Releases 下載 portable static build；或
  • 自行用 nix flake 編譯（官方 release process 與 Nixpkgs 同步）。

2.3 Hello World：one-liner 與腳本檔

One-liner：直接從命令列跑

sudo bpftrace -e 'BEGIN { printf("Hello, bpftrace!\n"); }'

輸出：

Attached 1 probe
Hello, bpftrace!
^C

解釋：-e 後面跟著腳本字串。BEGIN 是內建特殊探針，bpftrace 啟動時會觸發一次。按 Ctrl-C 結束。

稍微實用一點：監控誰在 sleep

sudo bpftrace -e 'kprobe:do_nanosleep { printf("%-6d %-16s sleeping\n", pid, comm); }'
Attached 1 probe
1234   sleep            sleeping
2231   chrome           sleeping
1234   sleep            sleeping
...

寫成腳本檔

建立 open_trace.bt：

#!/usr/bin/env bpftrace

BEGIN {
  printf("Tracing open() & openat() ... Hit Ctrl-C to end.\n");
  printf("%-8s %-6s %-16s %s\n", "TIME", "PID", "COMM", "FILE");
}

tracepoint:syscalls:sys_enter_open,
tracepoint:syscalls:sys_enter_openat {
  printf("%-8d %-6d %-16s %s\n",
         elapsed / 1000000, pid, comm, str(args.filename));
}

執行：

chmod +x open_trace.bt
sudo ./open_trace.bt

幾個要點：

  • #!/usr/bin/env bpftrace 讓腳本可直接執行。
  • 可以用逗號把多個探針綁到同一段 action。
  • args.filename 是 tracepoint 提供的型別化參數，比 argN 更安全。
  • str() 把 kernel pointer 解析成字串。

2.4 程式生命週期

理解 bpftrace 程式的四個階段，能避免一堆「為什麼我的腳本沒輸出」的困惑。

圖 2.1 — bpftrace 程式四階段生命週期
Stage 1 · Compile
bpftrace 在 user space 把 .bt 解析成 AST，經 LLVM 後端產生 BPF bytecode。看到 syntax error 都在這階段。
Stage 2 · Attach
bytecode 透過 bpf() syscall 進到 kernel，verifier 檢查通過後 JIT 編譯，再掛到對應的探針點。掛完後 BEGIN 探針觸發。輸出 Attached N probes 表示這階段完成。
Stage 3 · Run
事件發生 → 對應 action 被執行（在 kernel 內，BPF runtime）。printf、cat、system 等 async helper 會把資料丟到 perf/ring buffer，由 user space bpftrace 取出來印。
Stage 4 · Cleanup
觸發 END 探針 → 預設印出所有非空 map → detach 探針 → bpftrace 進程結束。

📌 預設會自動印 map

很多新手寫 @hits[pid] = count(); 卻看不到輸出，按 Ctrl-C 才發現原來預設要等程式結束才印。如果你不想要這個行為，加上：

config = { print_maps_on_exit = false }

或在 END 用 clear() 把不想印的 map 清掉。

CHAPTER 03 程式結構總覽 🔰 初學 🛠 開發

Preamble、Action Block、Probe、Predicate、Action —— 一支 bpftrace 腳本由這五件事構成。看懂它，往後讀任何官方範例都不會卡。

3.1 Preamble、Action Block、Probe

官方文件用一張結構圖描述每支 bpftrace 腳本：

preamble

actionblock1
actionblock2
...

而每個 action block 又長這樣：

[name=]probe[,probe]
/predicate/ {
  action
}

對照下面這張圖更直覺：

圖 3.1 — bpftrace 腳本完整結構

Preamble（前置區）

位於所有 action block 之前，選用。包含四種元素：

  • Preprocessor 指令：#include、#define。透過 libclang 處理。
  • Type 定義：自訂 struct。沒有 BTF 時特別有用。
  • config block：設定執行期參數，例如 stack_mode=perf、max_map_keys=2。
  • Map 宣告：let @a = lruhash(100); 等，挑選底層 BPF map type 並指定 max entries。

Action Block（動作區塊）

整支腳本可有任意多個 action block，順序執行（同一個事件多個 block 觸發時依宣告順序）。每個 block 的格式：

[name=]probe[,probe]
/predicate/ {
  action
}
name=（選用）
給 probe 起個名字，目前保留給內部使用，一般情境用不到。
probe
必填。指定要掛在哪個事件。可逗號分隔多個 probe，或用 wildcard kprobe:tcp_*。
/predicate/
選用。一個布林運算式。為 false 時不執行 action（但 probe 還是被觸發）。
{ action }
必填。一連串以分號分隔的敘述。

3.2 Predicate 與 Action

Predicate（過濾條件）

用來在事件已觸發後，決定要不要跑 action。常見模式：

// 只追蹤 bash
kprobe:vfs_read /comm == "bash"/ {
  printf("read by bash\n");
}

// 只看大量讀取
kprobe:vfs_read /arg2 > 1024/ {
  printf("big read: %d\n", arg2);
}

// 多條件組合
kprobe:vfs_read /comm == "bash" && arg2 > 1024/ {
  printf("big bash read\n");
}

⚠️ Predicate 不會減少觸發次數

Predicate 是事件觸發後在 BPF 內判斷，不是事先過濾。如果某個 probe 每秒觸發 100 萬次，加 predicate 也救不回 hot path 的成本。當需要更積極的過濾時，請：

  • 用更精確的 probe（例如 tracepoint:syscalls:sys_enter_openat 比 kprobe:do_sys_open 更窄）。
  • 用 -p PID 只追蹤單一 process（uprobe / USDT 自動套用，其他 probe 會在 BPF 內加 pid filter）。
  • 用 --probe-filter regex 在 attach 時就排除某些 probe。

Action（動作主體）

大括號內的程式碼，可以做以下事：

  • 讀取/設置 scratch 變數（$x = ...）與 map 變數（@m = ...）。
  • 呼叫 builtin（pid、comm、nsecs ...）。
  • 呼叫 helper function（printf、str、kstack ...）。
  • 使用 control flow（if、for、三元運算子）。
  • return 結束目前 probe（不結束整個 bpftrace）；exit() 結束整個 bpftrace。

📌 0.25 變更：exit() 不能在 loop 內

0.25 起 exit() 不再允許出現在 for / unroll 等迴圈內，否則會編譯失敗。需要在迴圈內中斷整個程式時，用 break 跳出迴圈後再呼叫 exit()。

3.3 一支完整腳本的拆解

把學到的概念套到一支實用的腳本 —— 統計每個 process 開了哪些檔案、各自的次數，並在程式結束時列出 top 結果。

#!/usr/bin/env bpftrace

// ---- Preamble ----
config = {
  max_map_keys = 8192;          // 預期 key 量大，先放寬
  stack_mode   = perf;
}

let @opens = lruhash(4096);     // 用 LRU 避免長跑記憶體爆掉

// ---- Action Block #1：啟動訊息 ----
BEGIN {
  printf("Tracing file opens by process. Hit Ctrl-C to end.\n");
}

// ---- Action Block #2：紀錄 open / openat ----
tracepoint:syscalls:sys_enter_open,
tracepoint:syscalls:sys_enter_openat
/comm != "bpftrace"/        // 別追到自己
{
  @opens[comm, str(args.filename)] = count();
}

// ---- Action Block #3：每 5 秒印一次 top 5 ----
interval:s:5 {
  printf("\n=== Top 5 file opens (last 5s) ===\n");
  print(@opens, 5);
  clear(@opens);
}

// ---- Action Block #4：結束時的清理 ----
END {
  clear(@opens);              // 不想最後再印一次
  printf("\nDone.\n");
}

逐行解讀：

區塊角色說明
config = { ... } Preamble 把預設 4096 的 map key 上限調到 8192；改用 perf 風格的 stack 輸出。
let @opens = lruhash(4096); Map 宣告 明確選擇 LRU hash type，避免長期執行時 key 撐爆。
BEGIN { ... } Action Block 程式啟動時印一次提示。
兩條 tracepoint 共用同一 action Action Block 同時掛 open 和 openat，避免漏抓。
/comm != "bpftrace"/ Predicate 排除自己，否則 print 行為本身會被計入。
@opens[comm, str(...)] = count(); Action 主體 用 multi-key map 紀錄 (process, filename) → 次數。
interval:s:5 Probe 單 CPU 計時器，每 5 秒觸發一次。
print(@opens, 5); Action 主體 印出 top 5（依 value 排序）。
END { clear(@opens); ... } Action Block 避免預設行為再印一次 map。

💡 從這支腳本可以延伸的方向

  • 把 key 改成 (pid, str(args.filename))，用 cgroup_path() 進一步分群（容器環境）。
  • 加 -p $TARGET_PID 限定觀察某個服務。
  • 把 interval 改 profile:hz:99，做火焰圖前處理。

這些變化我們會在 Part VI（實戰場景手冊）逐一展開。
