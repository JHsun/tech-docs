35.2 verifier reject 的解讀

BPF verifier 是 kernel 內的「靜態分析器」—— 它要在你的 BPF 程式執行前，證明程式不會崩潰、不會無窮迴圈、不會讀寫錯位址。verifier 拒絕 = 你的腳本沒掛上去。

sudo bpftrace -d verifier myscript.bt
libbpf: load bpf program failed: Permission denied
libbpf: -- BEGIN DUMP LOG ---
0: (b7) r6 = 0
1: (bf) r1 = r6
2: (b7) r2 = 4
...
142: (79) r3 = *(u64 *)(r1 +8)
143: (b7) r4 = 1024
144: (85) call bpf_probe_read_kernel#113
math between map_value pointer and unbounded register
processed 145 insns (limit 1000000) ...
-- END DUMP LOG ---

解讀邏輯：

  1. 看最後一行錯誤訊息（最有意義）。
  2. 對應指令編號（144:）找具體那行做什麼。
  3. 映射回 .bt 原始碼 —— -d codegen 能幫你對照。

verifier 常見錯誤對照表

stack/frame size limit exceeded

scratch 變數（特別是字串）總和超過 512 bytes BPF stack 上限。

解法：降 max_strlen 到 64-128；少用 string scratch；複用同一變數。

unbounded loop

用 for 但 verifier 算不出迴圈邊界（key/value 取自 map、又繼續 modify map）。

解法：改用 unroll(N) 編譯期展開；或 range 用 const 上限。

math between map_value pointer and unbounded register

對 map 取值的指標做了 verifier 算不出範圍的算術。

解法：把運算改成 mask（如 x & 0xff）讓 verifier 知道上界；或先存到 scratch 再操作。

invalid access to map value, value_size=N off=M size=K

讀寫 map value 時超出 value 的範圍。常見於 multi-key map 用了錯的 key 結構。

解法：檢查 map 宣告的 value type 與實際使用一致。

R1 type=ctx expected=fp

把 probe context 當成普通 pointer 用了某個只接受 stack pointer 的 helper。

解法：先把資料 copy 到 scratch（stack）再處理。

BPF program is too large. Processed N insn

單一 probe 的 BPF program 超過內核指令上限（通常 100 萬條，v5.2+）。

解法：把單 probe 拆成多個；用 macro 重構但避免過多 inline；簡化邏輯。

35.3 常見執行錯誤對照

ERROR: Could not find BTF

系統沒提供 vmlinux BTF。所有 fentry / 結構欄位存取都不能用。

解法：檢查 ls /sys/kernel/btf/vmlinux。沒有的話：(1) 升 kernel 到 5.4+ 並啟用 CONFIG_DEBUG_INFO_BTF；(2) 安裝 distro 的 kernel-debuginfo；(3) 用 BPFTRACE_BTF 環境變數指向自取的 BTF。

No probes to attach

wildcard 比對到 0 個 probe，或 probe 名稱拼錯。

解法：先用 bpftrace -l 'pattern' 確認；檢查 kernel 版本是否有該 tracepoint / function。

Cannot read /sys/kernel/debug/tracing/...

tracefs 沒掛載，或 bpftrace 不是以 root 跑。

解法：sudo mount -t tracefs nodev /sys/kernel/tracing；用 sudo 執行。

WARNING: lost N events

perf ring buffer 滿，user space 來不及處理。

解法：(1) 減少 hot path async helper（聚合代替 printf）；(2) 調大 perf_rb_pages；(3) 用 -q 抑制次要訊息減負擔。

probe full

attach 的 probe 數超過 max_probes（預設 1024）。

解法：config max_probes = 5000；或用更窄的 wildcard。

Failed to attach uprobe to PID X: No such file

target binary 路徑錯誤、或容器內 binary host 看不到。

解法：檢查 ls -l /proc/<PID>/exe；容器情境用 /proc/<PID>/root/... 路徑。

35.4 BTF 詳解

BTF（BPF Type Format）是 kernel 把 C 型別資訊以 BPF runtime 可讀格式嵌入 vmlinux。沒有 BTF，bpftrace 寫 args.file.f_path.dentry.d_name.name 時根本不知道 struct file 的記憶體佈局。

檢查 BTF 是否可用

# 1. 看 kernel 是否帶 BTF
ls -lh /sys/kernel/btf/vmlinux
# -r--r--r-- 1 root root 4.8M ... /sys/kernel/btf/vmlinux ✅

# 2. bpftrace --info 確認
sudo bpftrace --info 2>&1 | grep -i btf
# btf (depends on Build:libbpf bpf_object__btf): yes
# module btf: yes

# 3. 看 BTF 內含哪些 struct
bpftool btf dump file /sys/kernel/btf/vmlinux | grep -E '^\[\d+\] STRUCT' | head -20

BTF 在 bpftrace 的三個關鍵作用

作用沒 BTF 替代方案有 BTF 寫法
取 struct 欄位 自訂 struct + #include kernel header 直接 $f.f_path.dentry.d_name.name
fentry / fexit 不可用 fentry:vfs_read { args.file ... }
引數型別自動化 arg0 都是 int64，要手動 cast args 已是型別化結構

kernel module 的 BTF（5.11+）

# 各 module 自己的 BTF
ls /sys/kernel/btf/
# vmlinux  ext4  i915  nvme  ...

sudo bpftrace --info 2>&1 | grep 'module btf'
# module btf: yes

有 module BTF 後，fentry:nvme_setup_cmd 這類 module 函式才能被 bpftrace 透過 BTF 解析。

BPFTRACE_HAVE_BTF 預處理巨集

寫跨環境腳本時可以條件編譯：

#ifdef BPFTRACE_HAVE_BTF
fentry:vfs_read {
  printf("read %d bytes from %s\n",
         args.count,
         str(args.file.f_path.dentry.d_name.name));
}
#else
kprobe:vfs_read {
  // 沒 BTF 的環境：手動定義 struct 後 cast arg0
  let $count = (size_t)arg2;
  printf("read %d bytes\n", $count);
}
#endif

35.5 跨 kernel 版本相容性策略

bpftrace 不是 CO-RE（Compile Once - Run Everywhere）—— 它在 當下 kernel 編譯腳本，所以同一支 .bt 在不同 kernel 上跑可能：

  • kprobe：函式不存在或簽章變了 → attach 失敗或拿到錯資料。
  • tracepoint：欄位被改名 → args.field 編譯失敗。
  • helper：新 helper 在舊 kernel 沒有 → 編譯失敗。

三條防禦策略

// 1. 編譯期檢查 helper / function
BEGIN {
  if (!kfunc_exist("tcp_set_state")) {
    fail("tcp_set_state not available on this kernel");
  }
}

// 2. wildcard + missing_probes=warn
config = { missing_probes = "warn"; }
kprobe:tcp_v4_connect, kprobe:__tcp_v4_connect {  // 不同 kernel 名稱不同
  ...
}

// 3. tracepoint 優先（最穩定）
// 而非 kprobe（最不穩定）

📌 寫工具的人遇到 kernel 升級該怎麼辦

大型 fleet 跑多種 kernel 版本時：

  • 用 tracepoint（穩定 ABI）優先，避開 kprobe。
  • fentry args 來自 BTF，比 kprobe argN 穩定很多。
  • 把腳本標記支援的 kernel 範圍（透過 BEGIN { fail() } 主動拒絕）。
  • 在 staging fleet 跑 --dry-run 提早發現問題。

36.1 systemd 整合

當你需要 bpftrace 腳本「跟服務一起啟動、跟服務一起停止、自動 restart」，systemd unit 是首選做法。

基本 service unit

[Unit]
Description=bpftrace - I/O latency monitor
After=network-online.target
Documentation=internal-runbook.example.com/io_lat

[Service]
Type=simple
ExecStart=/usr/local/bin/bpftrace /etc/bpftrace/io_lat.bt
StandardOutput=journal
StandardError=journal
SyslogIdentifier=bpftrace-io-lat

# 失敗自動重啟
Restart=on-failure
RestartSec=10

# 資源限制（避免 bpftrace 自己吃太多）
MemoryMax=256M
CPUQuota=10%

# 安全
User=root              # bpftrace 必須 root
NoNewPrivileges=false  # 但需保留 BPF capability

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now bpftrace-io-lat.service
journalctl -u bpftrace-io-lat -f

Type=notify 與 systemd-run（早期啟動）

需要在系統啟動非常早就掛上 probe（例如追早期 kernel 行為）—— 用 systemd-run + Type=notify：

sudo systemd-run --service-type=notify \
  /usr/local/bin/bpftrace /etc/bpftrace/early_boot.bt

bpftrace 0.24+ 在所有探針 attach 完成後會發送 systemd readiness signal（透過 sd_notify）。配 Type=notify 後，依賴此 service 的其他 unit 會等到 bpftrace 真的開始追蹤才啟動。這對「我想抓某個服務啟動時的行為」極為關鍵。

Early-boot 完整流程：追 systemd 啟動的 open syscall

[Unit]
Description=Trace open() during boot
DefaultDependencies=no
After=local-fs.target
Before=basic.target

[Service]
Type=notify
ExecStart=/usr/local/bin/bpftrace -e '
tracepoint:syscalls:sys_enter_openat {
  printf("[%d] %s opens %s\n", pid, comm, str(args.filename));
}'
StandardOutput=journal

[Install]
WantedBy=basic.target
sudo systemctl enable bpftrace-boot.service
sudo reboot

# 重啟後查看
journalctl -b -u bpftrace-boot.service | head -100

36.2 長跑腳本的記憶體與穩定性

跑 24x7 的 bpftrace 腳本要特別注意：

問題對策
Map 持續成長爆 RAM 用 lruhash 替代 hash；限定明確 max entries；定期 clear()
Per-thread 變數沒清 kretprobe 用 delete()；超時用 interval flush
輸出量隨時間擴大 避免 hot path printf；改用 hist 聚合
Symbol cache 持續累積 用 cache_user_symbols=NONE 或 PER_PROGRAM；限定 PID
跑太久後 BPF prog 占資源 定期 systemd RestartSec 重新載入；外部 watchdog 監控 RSS

長跑腳本範本

#!/usr/bin/env bpftrace
// long_running_safe.bt — 設計給 24/7 跑的安全範本

config = {
  max_map_keys      = 32768;
  max_strlen        = 64;       // 最小化 stack 用量
  perf_rb_pages     = 256;       // 1 MB/CPU 給 hot path
  print_maps_on_exit = false;    // 避免結束時暴量輸出
  cache_user_symbols = "NONE";   // 避免 symbol cache 持續吃 RAM
}

let @lat_us = lruhash(8192);     // ⚠ 必用 lruhash，避免無限成長
let @start  = lruhash(4096);

BEGIN {
  printf("=== Started at %s ===\n", strftime("%Y-%m-%d %H:%M:%S", nsecs));
}

fentry:vfs_read { @start[tid] = nsecs; }

fexit:vfs_read /has_key(@start, tid)/ {
  @lat_us = hist((nsecs - @start[tid]) / 1000);
  delete(@start, tid);          // ⚠ 必 delete，否則 map 會慢慢膨脹
}

// 每 5 分鐘 flush 一次
interval:s:300 {
  printf("\n=== %s ===\n", strftime("%H:%M:%S", nsecs));
  print(@lat_us);
  clear(@lat_us);
  // @start 不 clear（它是 in-flight 量測，clear 會破壞配對）
}

// 每小時也清掉所有 stale @start（沒配對到的孤兒）
interval:s:3600 {
  // BPF 沒辦法看哪個 entry 是 stale，只能整批 clear
  clear(@start);
}

36.3 AOT 編譯展望

傳統 bpftrace 每次啟動都要：

  1. 把 .bt 解析成 AST。
  2. 透過 LLVM 編譯成 BPF bytecode。
  3. 解析 BTF / kallsyms 等。
  4. 送進 kernel verifier。

對 production fleet 來說缺點：每台機器都要裝 LLVM（200+ MB）、啟動慢（編譯期 1-3 秒）、bytecode 不易簽章。

AOT (Ahead-Of-Time) compilation 是 bpftrace 社群長期工作項目，目標：

  • 在 build server 把 .bt 預先編成自包含執行檔。
  • Production 機器只跑 runtime shim（不需 LLVM）。
  • 啟動只需 setup 而非 compile，快非常多。
  • Bytecode 可簽章驗證。

📌 0.25 的 AOT 狀態

0.25 版本已有實驗性 AOT 支援，但仍有限制：部分 helper（如 cgroup_path）AOT 不可用、容器/cgroup 路徑解析等需要 host context 的功能要謹慎使用。production 級 AOT 預計仍要幾個 release 才完備。

需要立即「免 LLVM」部署的方案：

  • 使用 portable static build（GitHub releases 提供）—— 一個 binary 含 LLVM，靜態連結，不依賴 distro。
  • 或用容器化部署（quay.io/iovisor/bpftrace）。

36.4 Portable static build

適用於需在多種 distro / kernel 上跑同一 bpftrace 的情境。

# 從 GitHub releases 下載
ARCH=$(uname -m)
curl -LO https://github.com/bpftrace/bpftrace/releases/download/v0.25.0/bpftrace-v0.25.0-${ARCH}.tar.gz
tar xzf bpftrace-v0.25.0-${ARCH}.tar.gz
sudo install -m 755 bpftrace /usr/local/bin/

# 驗證
bpftrace --version
bpftrace --info | head

36.5 何時該升級到 bcc

bpftrace 適合 90% 的觀測需求，但有些情境 bcc 更適合：

情境建議工具原因
One-liner、ad-hoc 排查 bpftrace ✅ 輸入字數最少
固定腳本、長期維護 bpftrace ✅ .bt 檔簡潔，easy review
複雜命令列參數（> 5 個 named） bcc Python argparse 更清楚
客製化輸出格式（JSON 嵌套、Prometheus expose） bcc Python 完整生態
整合既有 Python 系統（資料分析、繪圖、寫 DB） bcc 同一程序內處理
需要 conditionally maintained per-PID 結構 bcc / libbpf-tools 更精細控制 BPF map life-cycle
長期 metrics agent（取代 node_exporter 模組） libbpf-tools / Cilium Tetragon / Pixie 專業生態系

💡 升級遷移路徑

  1. 先用 bpftrace 寫 prototype 證明可行 + 量出指標。
  2. 達到「不能再進步」時（命令列複雜、輸出格式特殊）再升級到 bcc。
  3. 絕大多數情況不需要這個升級 —— bpftrace 足夠。

36.6 與其他工具的協同

工具用途與 bpftrace 配合
perf 採樣 / PMC / 系統等待事件 bpftrace 採 stack 後 perf script 後處理；perf 拿不到 BPF map
ftrace function trace 全量輸出 ftrace 沒有聚合，bpftrace 有 hist；ftrace 不需 BTF
bcc tools 固定 production 工具（biolatency / opensnoop ...） 許多 bcc tools 已被改寫成 bpftrace；可互相借鑒
FlameGraph 視覺化 stack bpftrace ustack(perf) 是其 input
kubectl-trace K8s 集群跑 bpftrace 把 .bt 包成 Job 排到指定 node
BCC's Pixie / Cilium Tetragon 長跑 observability agent bpftrace 適合 prototype / ad-hoc，agent 適合常駐

36.7 production 部署 checklist

📋 上 production 前的最終檢查

  1. 環境健檢：bpftrace --info 確認 BTF / probe types 都支援。
  2. 腳本驗證：--dry-run 確認能 attach。
  3. Config 顯式設定：max_map_keys / max_strlen / perf_rb_pages 都設好，不依賴預設。
  4. Map 用 lruhash：長跑必備。
  5. Per-thread 配對加 has_key + delete：避免孤兒。
  6. 定期 flush 與 clear：interval probe 控制 map 大小。
  7. missing_probes = warn：避免單一 probe 掛不上整支 fail。
  8. kfunc_exist 檢查：BEGIN 內驗證 kernel 支援。
  9. 輸出 buffer 控制：-B line 適合 streaming，-B full 適合批次。
  10. systemd 包裝：MemoryMax / CPUQuota / Restart=on-failure。
  11. 監控 bpftrace 自己：journald 看 lost events / verifier warnings。
  12. Stage rollout：先在 1 台 → 一個 zone → 全 fleet。
