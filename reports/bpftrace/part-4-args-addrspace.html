CHAPTER 17 取得探針引數（argN vs args） 🛠 開發

bpftrace 提供兩種取引數的途徑 —— 你用哪一種，不是個人偏好，是 probe 類型決定的。挑錯了會編譯失敗或拿到錯資料。

17.1 兩種引數機制的分工

機制適用 probe 類型型別資訊讀法
argN
(arg0, arg1, ...)		 kprobe · uprobe · usdt 無（一律 int64，需自行 cast） 從暫存器原始讀取
args
(args.field)		 tracepoint · rawtracepoint · fentry · fexit · uprobe(有 DWARF 時) 有（從 BTF / tracepoint format / DWARF） 透過 struct 欄位

📌 一句話原則

有 args 就用 args —— 因為它有型別、會自動處理 BTF 結構、且fexit 連 entry args 都還能存取。
只有 kprobe / uprobe（無 DWARF）/ usdt 必須退回用 argN。

17.2 argN：原始暫存器值

arg0、arg1、arg2... 都是 int64，bpftrace不知道真實型別 —— 你得自己查 kernel/user 的函式簽章再 cast。

kprobe 範例

// kernel: ssize_t vfs_read(struct file *file, char __user *buf, size_t count, loff_t *pos)
kprobe:vfs_read {
  $file  = (struct file *)arg0;        // 第一個參數
  $count = (size_t)arg2;                // 第三個參數
  printf("reading %d bytes from %s\n",
         $count,
         str($file.f_path.dentry.d_name.name));
}

uprobe 範例

// libc: void *malloc(size_t size)
uprobe:libc.so.6:malloc {
  printf("malloc(%d) called by pid=%d\n", arg0, pid);
}

// libc: void free(void *ptr)
uprobe:libc.so.6:free {
  printf("free(0x%lx)\n", arg0);
}

USDT 範例

// PostgreSQL: TRACE_POSTGRESQL_QUERY__START(query)
usdt:/usr/lib/postgresql/16/bin/postgres:postgresql:query__start {
  printf("query: %s\n", str(arg0));
}

⚠️ argN 在 kretprobe 不可用

kretprobe 觸發時，原始暫存器已經不是 entry 時的內容（CPU 跑完整個函式了）。要拿 entry args 必須：

  • 用 map 在 kprobe(entry) 暫存。
  • 升級到 fentry/fexit —— fexit 直接用 args.x 就能存取 entry 的所有參數。

17.3 args：型別化結構欄位

對於 tracepoint / fentry / fexit，bpftrace 會在編譯期產生一個 args struct，欄位名與型別來自：

來源適用 probe
Tracepoint format file
/sys/kernel/tracing/events/<cat>/<event>/format		tracepoint
Kernel BTF (vmlinux)fentry / fexit / rawtracepoint
DWARF debug info（如有）uprobe

tracepoint 用 args

// /sys/kernel/tracing/events/syscalls/sys_enter_openat/format 顯示：
//   const char * filename
//   int flags
//   umode_t mode
tracepoint:syscalls:sys_enter_openat {
  printf("%s opens %s (flags=%d, mode=%o)\n",
         comm,
         str(args.filename),
         args.flags,
         args.mode);
}

fentry 用 args（BTF 提供型別）

fentry:vfs_read {
  // args.file 是 struct file * — 直接拿
  // args.buf  是 char __user *
  // args.count 是 size_t
  printf("%s reading %d bytes from %s\n",
         comm,
         args.count,
         str(args.file.f_path.dentry.d_name.name));
}

查 args 有什麼欄位 — verbose listing

sudo bpftrace -lv 'tracepoint:block:block_rq_issue'
tracepoint:block:block_rq_issue
    dev_t dev
    sector_t sector
    unsigned int nr_sector
    unsigned int bytes
    char rwbs[8]
    char comm[16]
    __data_loc char[] cmd
sudo bpftrace -lv 'fentry:tcp_v4_connect'
fentry:tcp_v4_connect
    struct sock * sk
    struct sockaddr * uaddr
    int addr_len

💡 直接 print 整個 args

不確定欄位時，可以一次 dump：

tracepoint:syscalls:sys_enter_openat {
  print(args);     // 印出整個 struct
}

17.5 stack 引數與浮點引數的限制

⛔ 兩種拿不到的情形

  1. 第 7 個以後的整數引數（走 stack）：bpftrace 沒有 arg6、arg7 ...。要拿就得自己用 reg("sp") 算 offset，極少這樣做。
  2. 浮點引數（走 XMM 暫存器）：bpftrace 不支援，且 BPF 也沒浮點。

對策：找呼叫鏈中只用整數參數的封裝函式來掛 probe，或從 caller 取上下文。

檢查函式有幾個整數參數

# 用 fentry verbose listing 看（最快）
sudo bpftrace -lv 'fentry:my_func'

# 用 BTF dump（需 bpftool）
bpftool btf dump file /sys/kernel/btf/vmlinux | grep -A 1 'FUNC_PROTO.*my_func'

17.6 retval 與 fexit args 的妙用

retval 永遠是 int64，需要時 cast 成正確型別：

// 1. read() 返回 ssize_t，可能是負（errno）
kretprobe:vfs_read {
  $ret = (int64)retval;
  if ($ret < 0) {
    printf("%s read failed errno=%d\n", comm, -$ret);
  } else {
    printf("%s read %d bytes\n", comm, $ret);
  }
}

// 2. open() 返回 int (fd)
kretprobe:do_sys_openat2 {
  $fd = (int)retval;
  if ($fd >= 0) {
    @opened_fds = count();
  }
}

// 3. malloc() 返回 void * — 0 = OOM
uretprobe:libc.so.6:malloc {
  if (retval == 0) {
    printf("malloc OOM in pid=%d\n", pid);
  }
}

fexit 的關鍵優勢：同時看 args 和 retval

// 一個 probe 解決：要分配 N bytes，實際分到了哪個位址
fexit:__kmalloc {
  printf("kmalloc(%d) -> 0x%lx (caller=%s)\n",
         args.size, retval, kstack(1));
}

用 kprobe + kretprobe 寫等價邏輯需要兩個 probe + 一個 map，差異很大。

17.7 sargN：USDT 專用

除了 arg0~argN，USDT 還支援 sargN（stack-relative args）。在某些 USDT 點，arg 由 stack 提供而非暫存器；sargN 就是讀對應 stack offset 的值。

usdt:/path/to/myapp:provider:probe {
  // 大多數情況直接用 argN
  printf("%d %s\n", arg0, str(arg1));

  // 偶爾遇到 stack-passed args 才需要 sargN
  // (極少見，視 SDT 編譯時的 inline asm 而定)
}

📌 實務上 USDT 直接用 argN 即可

絕大多數 USDT 點的 args 都會被編譯器排到暫存器，argN 就能讀到。sargN 是極少數特殊情況才用得到，初學階段可暫不深究。

CHAPTER 18 位址空間（Address Spaces） 🛠 開發 ⚙️ SRE

「kernel pointer」與「user pointer」是 bpftrace 裡最隱晦的概念之一 —— 它不會在型別上顯示，但讀錯就拿到垃圾或失敗。

18.1 為什麼有兩個位址空間

Linux 的虛擬記憶體佈局把內核空間與使用者空間分開，BPF 程式跑在內核中，但要讀的 pointer 可能來自其中任一邊。某些架構（如 SPARC）兩邊位址甚至重疊 —— 必須明確告訴 kernel 該用哪種讀法。

圖 18.1 — Kernel / User 位址空間與 BPF 讀取助手

18.2 bpftrace 的自動推斷

多數情況 bpftrace 能根據 probe 類型自動選對 helper：

Probe 類型預設假設 pointer 在
kprobe / kretprobeKernel 空間
fentry / fexitKernel 空間（除非 BTF 標 __user）
tracepoint:syscalls:sys_enter_*User 空間（syscall args 來自 user 呼叫者）
uprobe / uretprobe / usdtUser 空間
iter:*Kernel 空間

正確自動推斷的範例

// kprobe:vfs_read 的 arg0 是 struct file *（kernel ptr）
// → bpftrace 用 probe_read_kernel 讀取結構欄位
kprobe:vfs_read {
  $name = str(((struct file *)arg0).f_path.dentry.d_name.name);
  printf("read from: %s\n", $name);
}

// tracepoint:syscalls:sys_enter_openat 的 args.filename 是 user ptr
// → bpftrace 用 probe_read_user 讀取
tracepoint:syscalls:sys_enter_openat {
  printf("opens: %s\n", str(args.filename));
}

18.3 kptr() 與 uptr()：手動標註

當自動推斷失敗 —— 例如內核函式回傳 user pointer，或腳本邏輯混合兩種來源 —— 用 kptr() / uptr() 強制指定：

// 場景：syscall 進入時 args.filename 是 user ptr，自動推斷正確
tracepoint:syscalls:sys_enter_openat {
  $name = str(args.filename);     // OK
}

// 場景：在 kprobe 內想讀一個明知是 user 空間的指標
kprobe:do_sys_openat2 {
  // arg1 在 do_sys_openat2 是 const char __user * filename
  // 但 kprobe 預設假設 kernel ptr，所以要明確標 uptr
  $name = str(uptr(arg1));
  printf("opens: %s\n", $name);
}

反過來：

// 罕見情境：在 uprobe 內想讀一個 kernel 位址（例如全域 kallsym）
uprobe:./myapp:my_func {
  let $kaddr = kaddr("jiffies");
  let $val   = *kptr($kaddr);     // 強制當作 kernel ptr
  printf("kernel jiffies: %d\n", $val);
}

kptr() / uptr() 的型別保留

這兩個函式只標註位址空間，pointer 本身的型別不變。例如 uptr((struct foo *)arg0) 仍是 struct foo *，可以繼續做 . / ->。

18.4 -k 與 -kk 旗標：把錯誤暴露出來

BPF helper 失敗時預設會被悄悄忽略，你只會看到「資料是 0 或空字串」這種症狀，看不到真正錯誤。-k 與 -kk 把錯誤暴露出來：

旗標行為
(無)BPF helper 錯誤被忽略
-kBPF helper 錯誤會發 warning（除了 probe_read_*）
-kk所有 helper 錯誤都會 warning，包含 probe_read_*
 
# 沒看到輸出？開 -kk 看是不是讀錯空間
sudo bpftrace -kk script.bt
script.bt:5:9-12: WARNING: Failed to probe_read_user: Bad address (-14)
  @=*uptr(kaddr("do_poweroff"))
        ~~~

看到這種訊息就知道：你用 uptr 包了一個實際是 kernel 位址的指標。

💡 除錯流程

  1. 腳本能跑、輸出怪怪的（資料是 0、空字串、亂碼）。
  2. 用 -kk 重跑，看 helper 錯誤訊息。
  3. 看到 probe_read_user 失敗 → 該 ptr 其實是 kernel ptr → 用 kptr() 包。
  4. 看到 probe_read_kernel 失敗 → 該 ptr 其實是 user ptr → 用 uptr() 包。

18.5 probe_read_kernel/user 的對應

底層上，str()、buf()、結構欄位存取都會 lower 成這四個 BPF helper：

場景底層 helper
str(kptr(p)) 或 kernel 推斷下的 str(p)bpf_probe_read_kernel_str
str(uptr(p)) 或 user 推斷下的 str(p)bpf_probe_read_user_str
buf(kptr(p), n)bpf_probe_read_kernel
buf(uptr(p), n)bpf_probe_read_user
結構欄位存取（kernel ptr）bpf_probe_read_kernel
結構欄位存取（user ptr）bpf_probe_read_user

這個拆分自 kernel 5.5 起：在更早的 kernel，bpftrace 會 fallback 到舊 bpf_probe_read。

18.6 實戰：從 syscall arg 讀 user buffer

下列範例覆蓋幾個常見組合，看完應能應對 90% 的位址空間問題。

範例 1 — 從 tracepoint 讀 user 字串（最常見）

tracepoint:syscalls:sys_enter_openat {
  // args.filename: const char __user *
  // bpftrace 自動知道這是 user ptr
  printf("%s opens %s\n", comm, str(args.filename));
}

範例 2 — 從 kprobe 讀 user 字串（要手動標 uptr）

kprobe:do_sys_openat2 {
  // arg1 是 const char __user *
  // kprobe 預設假設 kernel ptr，要強制標 uptr
  printf("opens: %s\n", str(uptr(arg1)));
}

範例 3 — 讀 user buffer 內容（buf + uptr）

// 看 write 寫了什麼到某個 fd
tracepoint:syscalls:sys_enter_write
/comm == "myapp"/ {
  // args.buf 是 user ptr
  // args.count 是要寫的 bytes 數
  printf("write %d bytes: %r\n",
         args.count,
         buf(args.buf, args.count));
}

%r 是 raw bytes 格式，與 buf() 搭配印出二進位內容（含不可印字元 → \xNN）。

範例 4 — fentry 取 kernel struct 內的 user ptr 欄位

// kernel: ssize_t vfs_read(struct file *file, char __user *buf, ...)
fentry:vfs_read {
  // args.file 是 kernel ptr → 直接 . 走 BTF
  // args.buf 是 user ptr → 也由 BTF 標記，bpftrace 知道
  $count_str = str(args.buf, args.count);   // 自動用 probe_read_user_str
  printf("first chars: %s\n", $count_str);
}

範例 5 — kernel 全域變數讀取

interval:s:1 {
  // kaddr() 回傳 kernel symbol 位址 — 是 kernel ptr
  $jp = kaddr("jiffies");
  $j  = *$jp;        // 解參考 → bpf_probe_read_kernel
  printf("jiffies = %lu\n", $j);
}

📌 為什麼這個容易踩

看 bpftrace 程式碼，pointer 的型別沒有任何標記顯示它是 kernel 還是 user 空間。
這個資訊隱藏在「probe 類型」與「BTF 註記」裡，肉眼看不出來。
→ 養成兩個習慣：（1）syscall args 永遠是 user，（2）kernel struct 欄位若標 __user 就是 user。其他預設 kernel。
