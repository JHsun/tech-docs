CHAPTER 30 應用層追蹤 🛠 開發 ⚙️ SRE

從 kernel 切到 user space —— 觀察應用內部的行為。原則：先試 USDT（穩、有設計過的觀測點），再退回 uprobe（任意位址、但脆弱）。

圖 30.1 — 應用層追蹤的標準四步驟

30.2 bash readline：經典開場

追蹤每個 user 在 shell 裡輸入了什麼 —— 安全稽核 / 教學示範必備。

// bash_readline.bt
uretprobe:/bin/bash:readline {
  printf("[%s pid=%d] %s\n",
         strftime("%H:%M:%S", nsecs),
         pid,
         str(retval));
}
[14:23:15 pid=1234] ls -la
[14:23:18 pid=1234] cd /tmp
[14:23:21 pid=1234] cat /etc/passwd

⚠️ 路徑要對

有些 distro 把 bash readline 編進 bash 本身（/bin/bash），有些用 libreadline.so：

# 確認 readline 在哪
ldd /bin/bash | grep readline
# 若有 libreadline → 改 uprobe target
sudo bpftrace -e 'uretprobe:/lib/x86_64-linux-gnu/libreadline.so.8:readline { printf("%s\n", str(retval)); }'

30.3 libc malloc：記憶體洩漏初篩

CASE 30-1

服務記憶體緩慢成長，懷疑 malloc 洩漏

某 C/C++ 服務 RSS 每天漲 100MB 但沒 OOM。tcmalloc / jemalloc 的 profiler 沒裝。先用 bpftrace 快速確認熱點配置呼叫鏈。

方法一：依 ustack 統計呼叫量（最便宜）

// malloc_stacks.bt
uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
  @[ustack(perf, 8), comm] = count();
}

interval:s:60 { exit(); }

方法二：依 size 看分布

uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
  @sizes = hist(arg0);
}

方法三：配對 malloc/free 找未釋放（複雜，注意陷阱）

// 注意：高頻 malloc 服務會把 map 撐爆
let @allocs = lruhash(65536);

uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
  @size[tid] = arg0;
}

uretprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc /@size[tid]/ {
  @allocs[(uint64)retval] = (@size[tid], ustack);
  delete(@size, tid);
}

uprobe:/lib/x86_64-linux-gnu/libc.so.6:free /has_key(@allocs, arg0)/ {
  delete(@allocs, arg0);
}

interval:s:60 {
  printf("currently outstanding: %d allocations\n", len(@allocs));
}

⛔ malloc/free 配對的成本警告

追每次的 malloc/free 是非常高頻的事 —— 在 Web server 等高併發場景每秒可能數十萬次，會嚴重影響應用效能。建議：

  • 先用方法一（ustack 採樣）找熱點 stack。
  • 必要時才用方法三，且限定一個小時間窗（10 秒）並 -p PID。
  • 更專業的洩漏分析請用 jemalloc profiler / valgrind / heaptrack。

30.4 C++ 程式追蹤（demangle）

C++ 函式名在 binary 中是 mangled 的，例如 _ZN3App7HandlerC1Ev。追蹤時用 :cpp: 前綴啟用 demangle 比對：

// 用 demangle 名稱掛 probe
uprobe:./myapp:cpp:App::Handler::process {
  printf("Handler::process called, arg0=0x%lx\n", arg0);
}

// stack 印 demangle 名稱
config = { cpp_demangle = true; }    // 預設就是 true
profile:hz:99 /comm == "myapp"/ {
  @[ustack] = count();
}

📌 找 demangled 名稱

# 列出 binary 內所有 C++ 函式（demangled）
nm -C ./myapp | grep ' T '

# 或用 c++filt 把 mangled 轉回來看
nm ./myapp | grep _ZN | c++filt | head

30.5 USDT 多語言實戰

30.5.1 PostgreSQL — query 延遲與慢查詢

CASE 30-2

找出 PostgreSQL 真正的慢查詢（不依賴 log_min_duration_statement）

DBA 設了 log_min_duration_statement = 1000 只看到部分慢查詢，且影響 log volume；想動態觀察任意門檻。

// pg_slow.bt — usage: sudo ./pg_slow.bt -- --threshold_ms=100
let @start = lruhash(2048);

BEGIN {
  let $threshold = getopt("threshold_ms", 50, "Slow query threshold in ms");
  printf("Tracing pg queries > %d ms ...\n", $threshold);
  @threshold_ms = $threshold;
}

usdt:/usr/lib/postgresql/16/bin/postgres:postgresql:query__start {
  @start[tid] = nsecs;
  @sql[tid]   = str(arg0);
}

usdt:/usr/lib/postgresql/16/bin/postgres:postgresql:query__done
/has_key(@start, tid)/ {
  let $dur_ms = (nsecs - @start[tid]) / 1ms;
  if ($dur_ms > @threshold_ms) {
    printf("[%s] [%d ms] %s\n",
           strftime("%H:%M:%S", nsecs), $dur_ms, @sql[tid]);
  }
  @hist_ms = hist($dur_ms);
  delete(@start, tid);
  delete(@sql, tid);
}

END {
  clear(@start); clear(@sql); clear(@threshold_ms);
}
sudo ./pg_slow.bt -- --threshold_ms=200

30.5.2 Node.js — HTTP request 觀測

Node.js 內建 USDT 但預設關閉，需要 --enable-tracing 或用 -p PID 觸發 USDT semaphore：

// node_http.bt
usdt:/usr/bin/node:node:http__server__request {
  printf("[%s pid=%d] %s %s\n",
         strftime("%H:%M:%S", nsecs),
         pid,
         str(arg5),         // method
         str(arg6));        // url
}
# 必須 -p 限定，否則 USDT semaphore 不會啟用
sudo bpftrace -p $(pgrep -x node) node_http.bt

📌 列出 Node 內所有 USDT

sudo bpftrace -l 'usdt:/usr/bin/node:*' | head
# usdt:/usr/bin/node:node:http__server__request
# usdt:/usr/bin/node:node:http__server__response
# usdt:/usr/bin/node:node:gc__start
# usdt:/usr/bin/node:node:gc__done

30.5.3 Python — function call 追蹤

CPython 3.6+ 有 USDT，但需要 --with-dtrace 編譯（多數 distro 預設沒開）：

# 確認你的 python 有 USDT
readelf -n $(which python3) | grep stapsdt

如果有，可以追：

// python_calls.bt — Python function call/return
usdt:/usr/bin/python3:python:function__entry {
  printf("[%s] %s in %s line %d\n",
         comm,
         str(arg1),         // function name
         str(arg0),         // filename
         arg2);             // line number
}

⚠️ Ubuntu / Debian 預設 Python 沒 USDT

實際情況：Ubuntu 22.04+ 的 python3 沒啟用 USDT。對策：

  • 用 python3-dbg（debug build）—— 部分 distro 有。
  • 自己編 CPython 加 --with-dtrace。
  • 用 libstapsdt + python-bcc 等動態埋 USDT 點。
  • 最務實的做法：在 Python 程式碼內自己加 instrumentation（如 cProfile、OpenTelemetry），不從 bpftrace 切入。

30.5.4 MySQL / Redis

// MySQL: query parse / execute
usdt:/usr/sbin/mysqld:mysql:query__start { @starts[tid] = nsecs; }
usdt:/usr/sbin/mysqld:mysql:query__done /@starts[tid]/ {
  @ms = hist((nsecs - @starts[tid]) / 1ms);
  delete(@starts, tid);
}

// Redis（自 7.0 起內建 USDT；舊版需自行編譯）
usdt:/usr/bin/redis-server:redis:command__start {
  printf("redis cmd: %s\n", str(arg0));
}

30.6 自己埋 USDT（C 程式範例）

如果你有自家 C/C++ 服務、想精準觀測業務語意（如 "user 登入完成"、"訂單已建立"），自己埋 USDT 是最佳方案：

// myservice.c
#include <sys/sdt.h>
#include <stdio.h>

void process_order(long order_id, const char *user) {
    DTRACE_PROBE2(myapp, order_start, order_id, user);
    // ... 業務邏輯 ...
    DTRACE_PROBE2(myapp, order_done, order_id, user);
}

int main() {
    process_order(12345, "alice");
    return 0;
}
# 1. 安裝 SDT header（Debian: systemtap-sdt-dev / Fedora: systemtap-sdt-devel）
sudo apt install -y systemtap-sdt-dev

# 2. 編譯
gcc -O2 myservice.c -o myservice

# 3. 確認 USDT 嵌入了
readelf -n ./myservice | grep -A2 stapsdt
# Provider: myapp
# Name:     order_start

# 4. 追蹤
sudo bpftrace -e '
usdt:./myservice:myapp:order_start {
  printf("order %d started by %s\n", arg0, str(arg1));
}'

💡 USDT 的真正價值在語意觀測

kprobe/uprobe 看「函式呼叫」；USDT 看「業務發生了什麼」。在自家服務埋 order_start / payment_done / cache_miss，比追任意函式名更貼近你真正關心的事。

USDT 點本身在沒人 attach 時幾乎零成本（一個 nop 指令），可以放心常駐。

30.7 Go 程式特殊注意事項

⛔ Go runtime 與 uretprobe 衝突 — 再次強調

Go 的 stack 機制與 uretprobe 互不相容。追 Go 程式絕對不要用 uretprobe。處理方式：

  • 進入點用 uprobe 沒問題。
  • 需要看返回值 → 找 caller 的 uprobe（在呼叫端取 return）。
  • 或在 Go 程式埋 USDT（透過 github.com/iovisor/gobpf 或 cgo）。

Go 程式因為有自己的 stack 管理 + 函式 inline 激進，uprobe 也要小心：

# Go binary 通常 strip 過，先看符號還在不在
nm ./mygo-app | grep main.handleRequest
# 若沒有 → 編譯時加 -gcflags="all=-N -l" 保留符號 + 不 inline

# 或用 go build 預設模式 + 確認沒被 strip
file ./mygo-app
# ELF 64-bit LSB executable, ..., not stripped  ← 有符號才能掛 uprobe

30.8 應用層追蹤腳本範本：app_diag.bt

#!/usr/bin/env bpftrace
// app_diag.bt — 通用應用層健檢範本（PostgreSQL 為例）
// usage: sudo ./app_diag.bt -p $(pgrep postgres | head -1) -- --threshold_ms=100

config = { max_map_keys = 16384; }

let @start = lruhash(8192);
let @sql   = lruhash(8192);

BEGIN {
  @threshold_ms = getopt("threshold_ms", 100, "slow threshold in ms");
  printf("=== App diag (threshold > %d ms) ===\n", @threshold_ms);
}

// (1) Query latency + slow capture
usdt:/usr/lib/postgresql/16/bin/postgres:postgresql:query__start {
  @start[tid] = nsecs;
  @sql[tid]   = str(arg0);
}

usdt:/usr/lib/postgresql/16/bin/postgres:postgresql:query__done
/has_key(@start, tid)/ {
  let $dur = nsecs - @start[tid];
  let $dur_ms = $dur / 1ms;
  @lat_ms = hist($dur_ms);
  if ($dur_ms > @threshold_ms) {
    printf("[SLOW %d ms] %s\n", $dur_ms, @sql[tid]);
  }
  delete(@start, tid);
  delete(@sql, tid);
}

// (2) Resource correlation: malloc 大 size 觀察
uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc /arg0 > 1024 * 1024/ {
  @big_alloc[ustack(perf, 6)] = count();
}

// (3) Disk I/O issued by this process
fentry:vfs_read,
fentry:vfs_write {
  @vfs_us[func] = hist(0);   // placeholder, 實際應做 entry/exit pairing
}

interval:s:60 { exit(); }

END {
  printf("\n--- Query latency (ms) ---\n"); print(@lat_ms);
  printf("\n--- Big allocations (>1MB) ---\n"); print(@big_alloc);
  clear(@start); clear(@sql);
}

CHAPTER 31 容器與 cgroup 環境 ⚙️ SRE 🛠 開發

在 K8s / Docker / containerd 環境下用 bpftrace 有兩個關鍵差異：檔案路徑變了、PID namespace 不一樣。把這兩件事搞懂，整個生態系都能觀測。

31.1 容器環境的核心觀念

圖 31.1 — bpftrace 在 host 跑、觀察容器內事件的架構

💡 永遠在 host 跑 bpftrace

幾乎所有情境下，把 bpftrace 安裝在 host 上、用 cgroup / pid 過濾觀測特定容器是最簡單可靠的做法。在容器內跑 bpftrace 需要 --privileged + 大量 mount，意義不大。

31.2 Cgroup ID 過濾（v2）

Linux 5.0+ cgroup v2 為主流。每個 cgroup 有唯一 cgroup id（即該 cgroup 目錄的 inode 號）。

從 host 看某個容器的 cgroup id

# Docker
sudo cat /proc/$(docker inspect -f '{{.State.Pid}}' <container>)/cgroup
# 0::/docker/abcdef.../

# K8s（某 pod 的某個 container）
sudo crictl inspect <containerID> | jq '.info.pid'
sudo cat /proc/<PID>/cgroup

# 或直接從 cgroup tree 找
sudo find /sys/fs/cgroup -name '<container-id-prefix>*'
# /sys/fs/cgroup/system.slice/docker-abcdef....scope

用 cgroupid() 過濾

// 只追特定容器的 syscall
tracepoint:raw_syscalls:sys_enter
/cgroup == cgroupid("/sys/fs/cgroup/system.slice/docker-abcdef.scope")/ {
  @[syscall_name(args.id)] = count();
}

cgroupid() 是 compile-time helper，啟動時一次性把路徑解析成 inode 號，之後與 cgroup builtin 比較幾乎零成本。

對所有容器分組統計

// 用 cgroup_path() 顯示（async，僅能 print）
tracepoint:syscalls:sys_enter_openat {
  @[cgroup_path(cgroup), comm] = count();
}
@[/system.slice/docker-abc.scope, nginx]: 4521
@[/system.slice/docker-def.scope, postgres]: 1247
@[/user.slice/user-1000.slice/.../session-c1.scope, vim]: 89
...

31.3 K8s pod 的 PID 與 cgroup 對應

CASE 31-1

追蹤特定 K8s pod 的網路流量

想觀察 namespace=production 內 deployment=api-server 某個 pod 的對外連線。

第一步：找到 pod 對應的 cgroup 路徑

# 1. 拿 container ID
kubectl get pod api-server-xyz -n production -o jsonpath='{.status.containerStatuses[0].containerID}'
# containerd://abcdef0123...

# 2. 從 host 找 cgroup（K8s 預設的 systemd cgroup driver）
sudo find /sys/fs/cgroup/kubepods.slice -name '*abcdef0123*'
# /sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/.../cri-containerd-abcdef0123.scope

第二步：用 cgroupid filter 在 host 跑 bpftrace

// pod_net.bt
BEGIN {
  printf("Tracing TCP traffic for pod cgroup ...\n");
}

fentry:tcp_sendmsg
/cgroup == cgroupid(
  "/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/cri-containerd-abcdef0123.scope"
)/ {
  let $sk = args.sk;
  printf("%s -> %s:%d (%d bytes)\n",
         comm,
         ntop($sk->__sk_common.skc_daddr),
         bswap($sk->__sk_common.skc_dport),
         args.size);
}
sudo bpftrace pod_net.bt

31.4 PID namespace 處理

容器內看到的 PID 與 host 看到的 PID 不同。bpftrace 的 pid / tid 預設是當前 namespace 的值（host 跑 bpftrace 就是 host PID）。

同時取得兩種 PID（0.25）

tracepoint:syscalls:sys_enter_read {
  // 預設 = curr_ns（host 看到的 PID）
  // pid(init) 也是 host PID（bpftrace 已在 init ns）
  // 取 container 內 PID 需要從 task_struct 拿
  printf("host_pid=%d, host_tid=%d\n", pid, tid);
}

📌 取 container 內 PID 的進階寫法

// 從 curtask 走 nsproxy → pid_ns → 取 namespace pid
tracepoint:syscalls:sys_enter_read {
  let $task = curtask;
  let $level = $task->nsproxy->pid_ns_for_children->level;
  let $ns_pid = $task->thread_pid->numbers[$level].nr;
  printf("host_pid=%d, container_pid=%d\n", pid, $ns_pid);
}

實務上很少需要這個 —— 用 cgroup 過濾通常更直觀。

31.5 容器內 binary 的 uprobe

容器把應用 binary 放在自己的檔案系統內，host 看到的路徑長這樣：

# 找出 container 的 root
sudo ls /proc/$(docker inspect -f '{{.State.Pid}}' my-container)/root/usr/bin/myapp

# 用該路徑掛 uprobe（注意：path 跟 host 不一樣）
sudo bpftrace -e '
uprobe:/proc/12345/root/usr/bin/myapp:my_func {
  printf("called by pid=%d\n", pid);
}'

⚠️ 容器重啟後 PID 會變

用 /proc/<pid>/root/... 路徑時，pod restart 後 PID 改變，腳本失效。對策：

  • 如果可以：把 binary 鏡像 mount 到 host 的固定路徑（DaemonSet 風格）。
  • 動態場景：用 wrapper script 啟動前先 docker inspect 取 PID 再掛。
  • K8s 大規模：用 kubectl-trace（下節）。

31.6 Stack trace 跨容器：build_id mode（0.25 重點）

傳統 ustack 解析需要在 host 上能讀到對應 binary。容器內 binary 對 host 來說「不在預期路徑」會讓符號解析失敗。0.25 的 build_id mode 解決這個問題：

// 用 build_id 替代位址解析
profile:hz:99 {
  @[ustack(build_id, 32)] = count();
}
@[
    addr: 0x401234, build_id: a1b2c3d4...
    addr: 0x402345, build_id: a1b2c3d4...
    addr: 0x405678, build_id: a1b2c3d4...
]: 1247

輸出帶 build_id 後可以離線解析：

# 從 build_id 找對應 binary
debuginfod-find debuginfo <build_id>

# 或在容器 image 裡查
docker run --rm myimage sh -c '
  find / -type f -executable 2>/dev/null | xargs -I{} sh -c "
    bid=\$(eu-readelf -n {} 2>/dev/null | grep -oE \"Build ID: [0-9a-f]+\")
    [ \"\$bid\" = \"Build ID: a1b2c3d4...\" ] && echo {}
  "'

31.7 kubectl-trace：在 K8s 集群內執行

對大規模 K8s 集群，逐機 SSH 跑 bpftrace 不切實際。kubectl-trace 把 bpftrace 包成 Job 排到指定 node 上：

# 安裝 kubectl 插件
kubectl krew install trace

# 在某 node 上跑 one-liner
kubectl trace run node/worker-1 \
  -e 'tracepoint:syscalls:sys_enter_openat {
       @[comm] = count();
      }
      interval:s:30 { exit(); }'

# 對某個 pod 上的 process 跑 uprobe
kubectl trace run pod/api-server-xyz \
  -f myscript.bt

📌 kubectl-trace 的限制

  • 建立privileged Job，需要對應的 RBAC 與 admission policy。
  • 每次都拉 image、起 pod、跑、結束 —— 不適合需要超低延遲的互動式排查。
  • 結果以 Job log 形式取出。

31.8 完整實戰：跨容器 latency 比較

CASE 31-2

同一 host 上多個容器，比較它們的 syscall latency

某 host 跑了 5 個 pod，懷疑某個 pod 因 cgroup CPU limit 導致 syscall latency 變高。

// per_pod_latency.bt
config = { max_map_keys = 32768; }

let @start = lruhash(16384);

tracepoint:raw_syscalls:sys_enter {
  @start[tid] = nsecs;
}

tracepoint:raw_syscalls:sys_exit /has_key(@start, tid)/ {
  let $dur_us = (nsecs - @start[tid]) / 1000;
  // key = (cgroup_path, syscall_name)
  @lat_us[cgroup_path(cgroup), syscall_name(args.id)] = hist($dur_us);
  delete(@start, tid);
}

interval:s:30 { exit(); }

END { clear(@start); }

輸出可以比較不同 cgroup 的同一 syscall 分布：

@lat_us[/kubepods.slice/.../pod-A/, read]:
[1]   45123 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2,4)  3214 |@@@                                                 |

@lat_us[/kubepods.slice/.../pod-B/, read]:
[1]   12015 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[2,4)   985 |@@@@                                                |
[1K,2K) 124 |@                                                   |  ← outlier!
[2K,4K)  31 |                                                    |

pod-B 出現毫秒級的 syscall outlier → 多半是 cgroup CPU throttle 或 I/O queue 飽和。下一步可看 /sys/fs/cgroup/.../cpu.stat 的 throttled count 確認。
