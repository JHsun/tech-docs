CHAPTER 23 控制與流程函式 🛠 開發 ⚙️ SRE

exit / signal / override / skboutput / reg / offsetof / sizeof / unwatch / debugf / bpf_prog_id —— 不是輸出資料，而是控制行為的函式群。

23.1 結束程式：exit()

exit([code])

結束 bpftrace 程式（觸發 END probe，印出 map，然後退出）。可選 exit code。

// 計時 30 秒後自動結束
BEGIN { printf("Tracing for 30s...\n"); }

tracepoint:syscalls:sys_enter_open {
  @[comm] = count();
}

interval:s:30 {
  exit();           // 觸發 END，印出 @
}

⚠️ 0.25：exit() 不能在迴圈內

0.25 起 exit() 不能出現在 for / unroll 內。要在迴圈內中斷請先 break，跳出迴圈後再 exit()。

23.2 對 process 發送 signal

signal(sig)

對觸發 probe 的 process 發送信號。sig 可以是整數或字串名稱（"SIGTERM"、"SIGKILL"）。

// 自動殺掉 fork 太多 child 的 process
tracepoint:sched:sched_process_fork
/@forks[args.parent_pid]++ > 100/ {
  printf("PID %d forked too many times, killing\n", args.parent_pid);
  signal("SIGKILL");
}

⛔ 用 signal() 前先確認後果

對 init / systemd / 系統關鍵服務發 SIGKILL 會直接搞壞系統。務必加嚴謹 predicate，並先在隔離環境驗證。

23.3 override() — 攔截函式回傳值

override(rc)

unsafe

讓被 probe 的 kernel 函式不執行，直接回傳 rc。需要 CONFIG_BPF_KPROBE_OVERRIDE=y，且僅特定函式可被 override（kernel 標 ALLOW_ERROR_INJECTION）。

// 攔截 id 命令的 getuid，永遠回傳 4194304
sudo bpftrace --unsafe -e '
kprobe:__x64_sys_getuid /comm == "id"/ {
  override(2 << 21);
}'
# 在另一個 terminal:
$ id
uid=4194304 gid=...

⚠️ override 是錯誤注入工具

主要用途是測試系統對函式失敗的反應（chaos engineering 風格）。不要拿來在 production 改變正常行為。

23.4 skboutput — 把封包寫到 PCAP

skboutput(filename, skb, length, offset) → int

把 struct sk_buff 寫到 PCAP 檔案。返回 0 = 成功。

// 把 TCP 重傳的封包都抓下來分析
fentry:tcp_retransmit_skb {
  $skb = (struct sk_buff *)args.skb;
  let $r = skboutput("/tmp/retrans.pcap",
                     $skb,
                     $skb->len,
                     0);
  if ($r != 0) {
    printf("skboutput failed: %d\n", $r);
  }
}
$ tcpdump -nr /tmp/retrans.pcap | head
reading from file /tmp/retrans.pcap
12:34:56.123456 IP 10.0.0.1.443 > 10.0.0.2.54321: Flags [P.], seq ...

23.5 reg() — 直接讀暫存器

reg(name) → uint64

從 probe 上下文讀指定暫存器（"ip"、"sp"、"r12"、"x86" 標準名稱）。

kprobe:do_softirq {
  // ip = 當前 instruction pointer
  // sp = stack pointer
  printf("called from %s, sp=0x%lx\n", ksym(reg("ip")), reg("sp"));
}

多用於除錯 / 特殊場景（如取第 7 個以上 stack 引數）。一般 probe args 不需要它。

23.6 offsetof / sizeof — 編譯期工具

offsetof(struct, field) → uint64

compile-time

取 struct 欄位的 byte offset，類似 C 的 offsetof 巨集。

sizeof(type | expr) → uint64

compile-time

取型別或運算式的 byte 大小。

BEGIN {
  printf("task_struct size: %d\n", sizeof(struct task_struct));
  printf("comm offset:      %d\n", offsetof(struct task_struct, comm));
  printf("nested:           %d\n", offsetof(struct Foo, a.b.c.d));
  exit();
}

多用於：

  • Verifier debugging（看 BPF 指令在算什麼 offset）。
  • 跨 kernel 版本相容性檢查。
  • 手動拼 raw pointer（極少數場景）。

23.7 unwatch — 移除 watchpoint

unwatch(addr)

移除 watchpoint:<addr>。讓 watchpoint 變成「一次性」觸發。

// 第一次寫到該位址後就不再追
watchpoint:0xffffffff828dd140:8:w {
  printf("first write detected by %s\n", comm);
  unwatch(0xffffffff828dd140);
}

23.8 debugf — 寫到 trace_pipe

debugf(fmt, args...)

把訊息透過 bpf_trace_printk 寫到 /sys/kernel/tracing/trace_pipe。純除錯用。

kprobe:vfs_read {
  debugf("got vfs_read pid=%d", pid);
}
# 另一個 terminal 看
sudo cat /sys/kernel/tracing/trace_pipe

📌 何時用 debugf 而非 printf

當你懷疑 bpftrace 自己的 printf 流程出問題（例如 ring buffer 滿、user space 處理慢）時，debugf 走完全不同的 kernel 路徑，能幫助定位是事件沒觸發 還是訊息沒傳到。

23.9 bpf_prog_id — 觀察 BPF 程式

bpf_prog_id() → uint32

當前 BPF 程式自己的 prog id（由內核分配）。配合 fentry:bpf:* 等 meta probe 使用。

BEGIN {
  printf("This bpftrace's BPF prog id: %d\n", bpf_prog_id());
}

CHAPTER 24 Map 函式（聚合） 🔰 初學 🛠 開發 ⚙️ SRE

bpftrace 之所以能在 production 上跑 —— 因為大量計算發生在 kernel 內。Map 函式就是把「每事件操作」轉成「kernel 內聚合」的關鍵。

24.1 為什麼一定要用 map 函式

看下面兩種寫法的差異：

// ❌ 寫法 A：每事件 push 到 user space
kprobe:vfs_read { printf("%d\n", arg2); }

// ✅ 寫法 B：在 kernel 內聚合，user space 只在最後讀一次
kprobe:vfs_read { @ = hist(arg2); }

差異不只「輸出量」—— 寫法 A 在 1M events/sec 的 hot path 上會把 ring buffer 撐爆、bpftrace 進程 OOM、甚至影響 production 服務。寫法 B 則完全在 kernel 跑，幾乎零成本。

24.2 計數類聚合

@m = count()

累計觸發次數。底層用 PERCPU map，避免 CPU 競爭。

@m = sum(n)

累計 n 的總和。也用 PERCPU map。

@m = min(n) / max(n)

追蹤觀察到的最小 / 最大值。

@m = avg(n)

連續呼叫間的滾動平均。

@m = stats(n)

同時得到 count、avg、total。輸出格式：count=N, average=X, total=Y。

tracepoint:syscalls:sys_enter_read {
  @count[comm] = count();
  @bytes[comm] = sum(args.count);
  @max_size[comm] = max(args.count);
  @stats[comm]   = stats(args.count);
}
@count[bash]: 47
@count[chrome]: 1203
...
@bytes[bash]: 4096
@bytes[chrome]: 4915200
...
@stats[chrome]: count 1203, average 4087, total 4916200

⚠️ count() vs ++ 的差異（再次強調）

@x++ 是非 atomic 的 read-modify-write，多 CPU 同時觸發會掉資料。count() 用 PERCPU map，每 CPU 各自累計，sync read 時加總，絕不掉資料。需要精確統計就用 count()。

24.3 分布類聚合

@m = hist(n [, k])

log2 直方圖。k = 每個 power of 2 內再分幾個 bucket（0~5，預設 0）。

@m = lhist(n, min, max, step)

線性直方圖。在 [min, max) 區間以 step 切等寬 bucket，超出範圍另計兩個 bucket。

hist 範例：read 大小分布

tracepoint:syscalls:sys_exit_read /args.ret > 0/ {
  @bytes = hist(args.ret);
}
@bytes:
[1]                    3 |                                                    |
[2, 4)                 0 |                                                    |
[4, 8)                 8 |@                                                   |
[8, 16)               42 |@@@@@@                                              |
[16, 32)              63 |@@@@@@@@                                            |
[32, 64)              71 |@@@@@@@@@                                           |
[64, 128)            134 |@@@@@@@@@@@@@@@@@                                   |
[128, 256)           215 |@@@@@@@@@@@@@@@@@@@@@@@@@@@                         |
[256, 512)           412 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[512, 1K)            331 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@           |
[1K, 2K)              91 |@@@@@@@@@@@                                         |

lhist 範例：精細的延遲區間

// 想看 0-1000us 之間，每 100us 一個 bucket
let @start = lruhash(8192);

kprobe:vfs_read { @start[tid] = nsecs; }

kretprobe:vfs_read /has_key(@start, tid)/ {
  @lat = lhist((nsecs - @start[tid]) / 1000, 0, 1000, 100);
  delete(@start, tid);
}

tseries — 時間序列圖（unstable）

@m = tseries(n, interval_ns, num_intervals [, agg])

unstable

記錄一個值隨時間的變化，繪成終端機可看的時間序列圖。agg: "avg" / "min" / "max" / "sum"，預設 "avg"。

config = { unstable_tseries = enable; }

tracepoint:syscalls:sys_enter_read {
  // 每 100ms 一格，記 60 格 = 6 秒
  @reads = tseries(args.count, 100ms, 60, "sum");
}

24.4 操作類函式

clear(@m)

清空整個 map。

delete(@m, key)

刪除指定 key 的 entry。多 key map 用 tuple：delete(@m, (k1, k2))。

zero(@m)

把所有 value 設為 0，但保留 key 結構（hist / lhist 適用，避免下次需要時重建）。

len(@m) → int

map 內 entry 數量。

has_key(@m, key) → bool

檢查 key 是否存在。scalar map 上呼叫會編譯失敗。

find(@m, key) → ptr

取得 key 對應 value 的指標（不存在則為 NULL）。0.25 起穩定。

let @bytes = lruhash(8192);

kprobe:vfs_read {
  @bytes[tid] += arg2;
}

kretprobe:vfs_read /has_key(@bytes, tid)/ {
  let $total = @bytes[tid];
  delete(@bytes, tid);
  if ($total > 1 << 20) {
    printf("%s read %d MB total\n", comm, $total / (1 << 20));
  }
}

interval:s:30 {
  printf("currently tracking %d threads\n", len(@bytes));
}

24.5 PERCPU map 的 sync read 成本

count() / sum() 等用 PERCPU map：每 CPU 各自累計、sync 讀時把所有 CPU 加總。寫便宜、讀貴。

// 每 100ms 觸發一次
interval:ms:100 { @ = count(); }

// 每 10 秒讀一次（耗時但精確）
interval:s:10 {
  print(@);
  if (@ > 1000) {     // sync read，正確
    printf("rate too high!\n");
  }
  clear(@);
}

📌 async print vs sync read

print(@) 是 async —— 它把 map 引用送到 user space，user space 處理時才讀。期間 BPF 還在更新 map，看到的不是當下值，是 user space 處理那一刻的值。

下面的 if (@ > 1000) 是 sync read，會在當下從所有 CPU 加總，得到精確值，但成本較高。

24.6 Cast PERCPU 值為 array

偶爾需要看每個 CPU 的部分和，可以把 PERCPU map 值 cast 成陣列：

kprobe:vfs_read { @per_cpu = count(); }

interval:s:5 {
  let $arr = (uint64[ncpus])@per_cpu;
  for ($i : 0..ncpus) {
    printf("CPU %d: %d\n", $i, $arr[$i]);
  }
  clear(@per_cpu);
}

CHAPTER 25 同步 vs 非同步（Invocation Mode） 🛠 開發 ⚙️ SRE

25.3 時序滯後實例

下面這支腳本會發生有趣的現象：

interval:ms:100 { @ = count(); }

interval:s:10 {
  print(@);          // async print
  if (@ > 10) {       // sync read
    print(("count exceeded threshold"));
  }
  clear(@);
}

觀察輸出，@ 的值「看起來」每秒都很穩定 —— 因為每次 user space 處理 event 時，kernel 內 map 已被多次更新，總是看到當下值。

25.4 compile-time helper

一些 helper 在編譯期就求值，根本不在 runtime 執行。這類 helper 的結果可當常數使用，且零成本：

helper編譯期做什麼
cgroupid("/path")讀 /sys/fs/cgroup/... 取 inode 號
kaddr("name")從 /proc/kallsyms 找位址
uaddr("sym")從 ELF 找符號位址
offsetof(s, f)從 BTF / 自訂 struct 算 offset
sizeof(t)從 BTF / 自訂 struct 算大小
kfunc_exist / kfunc_allowed檢查 kernel 是否有該函式
fail / errorf編譯期錯誤
is_* 反思系列編譯期型別檢查

25.6 實務指南

💡 三條鐵則

  1. Hot path 不放 async helper。 每秒 100k+ 觸發的 probe 上不要用 printf；用 count() / hist() 聚合。
  2. 需要精確值，用 sync read。 if (@ > threshold) 是 sync，可信賴；print(@) 後查值是 async，可能滯後。
  3. compile-time helper 是免費午餐。 能在 BEGIN 算好的東西，就在 BEGIN 算（如 kfunc_exist 檢查、cgroupid 設定 filter）。

25.7 觀察 ring buffer 是否撐爆

用 perf_rb_pages config 調整 ring buffer 大小（預設 64 pages = 256 KB）：

config = {
  perf_rb_pages = 256;     // = 1 MB per CPU
}

運行時看 bpftrace 是否抱怨 lost events：

WARNING: lost 12345 events

看到 lost events 表示：

  1. Hot path 上 async helper 太多（首要對策：聚合）。
  2. Ring buffer 太小（其次對策：調 perf_rb_pages）。
  3. User space 處理太慢（極少數場景 —— 如 cgroup_path 解析卡住）。
