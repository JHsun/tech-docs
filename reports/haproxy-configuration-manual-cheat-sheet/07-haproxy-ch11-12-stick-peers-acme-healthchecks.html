Ch.11

Stick-tables 宣告

Stick-table 是 HAProxy 最強大的功能之一：在記憶體中維護鍵值對資料庫，用於 session persistence、rate limiting、攻擊防護、狀態追蹤。鍵可以是 IP、字串、整數等。

stick-table 語法

stick-table type { ip | ipv6 | integer | string [len <n>] | binary [len <n>] }
            size <n> [expire <time>]
            [nopurge] [peers <name>]
            store <counter>[,<counter>...]

常用計數器 (store) 完整列表

計數器說明類別
conn_cnt累積連線數連線
conn_cur目前活躍連線數連線
conn_rate(<period>)連線速率（例：10s 內的平均）連線
sess_cnt累積 session 數Session
sess_rate(<period>)Session 速率Session
http_req_cnt累積 HTTP 請求數HTTP
http_req_rate(<period>)HTTP 請求速率HTTP
http_err_cnt累積 HTTP 錯誤（4xx/5xx）數HTTP
http_err_rate(<period>)HTTP 錯誤速率HTTP
bytes_in_cnt累積接收位元組數流量
bytes_out_cnt累積傳送位元組數流量
bytes_in_rate(<period>)接收位元組速率流量
bytes_out_rate(<period>)傳送位元組速率流量
gpc0 – gpc9通用計數器（手動增減）自訂
gpc0_rate(<period>)通用計數器速率自訂
gpt0 – gpt9通用 64-bit 計數器 3.4自訂
glitch_cntGlitch 計數器（協定異常）3.4安全

完整範例：Session Persistence + Rate Limiting

backend app
    # stick-table：1M 條目，30 分鐘過期，跨節點同步
    stick-table type ip size 1m expire 30m peers mycluster \
        store conn_cur,conn_rate(10s),http_req_rate(10s),http_err_rate(10s),gpt0

    # Session persistence — 依來源 IP
    stick on src

    # Rate limiting — 超過 100 req/10s 回 429
    http-request track-sc0 src
    http-request deny deny_status 429 if { sc_http_req_rate(0) gt 100 }

    # 進階：防禦 abusive IP（過多 4xx/5xx）
    http-response sc-inc-gpt0(0) if { status ge 400 }
    http-request deny if { sc_get_gpt0(0) gt 50 }

    server s1 10.0.0.1:80 check
    server s2 10.0.0.2:80 check

常用 Stick-table Actions

Action說明
stick on <fetch>依 fetch 值做 persistence（寫入 stick-table）
stick match <fetch>查詢 stick-table 找到上次使用的 server
track-sc0 <fetch>追蹤 fetch 值到 slot 0（供 sc_* 取樣）
sc-inc-gpc0(0)遞增通用計數器
sc-set-gpt0(0) <expr>設定通用 64-bit 計數器
sc-inc-gpt0(0)遞增通用計數器 3.4

Ch.11

Peers 宣告（跨節點同步）

Peers 讓多台 HAProxy 之間透過專用 TCP 連線同步 stick-table 狀態，實現 HA 架構下的 session persistence 與 rate limiting 一致性。

Peers Section 語法

peers <name>
    bind <addr>[:<port>]
    default-server [opts]
    server <name> <addr>[:port] [opts]
    localpeer <name>
    table <tbl-name> [type ...] [size ...] [expire ...] [store ...]

基本範例

peers mycluster
    peer lb1 192.168.1.10:1024
    peer lb2 192.168.1.11:1024

    # 3.4：可直接在 peers 內宣告 table
    table rate_limit type ip size 1m expire 10m store conn_rate(10s)

backend app
    stick-table type ip size 1m expire 30m peers mycluster
    stick on src

3.4 新功能：Peers 內直接宣告 table

table <name> type ... size ... expire ... store ...

HAProxy 3.4 允許在 peers section 內直接宣告 stick-table，不需在每個 backend 中重複宣告。多個 backend 可共用同一個 peers-level table。

💡 localpeer每台 HAProxy 的 peer 名稱必須與 localpeer 一致（預設為 hostname），可用 -L 命令列參數或 localpeer 指令覆蓋。

12.8

ACME 自動化憑證管理 3.4 強化

HAProxy 3.2 首次引入 ACME（Automatic Certificate Management Environment）支援，3.4 大幅擴充：新增 DNS-PERSIST-01 挑戰、External Account Binding、發行設定檔。

ACME Section 語法

acme <name>
    account-key <path>           # 帳號私鑰路徑
    directory <url>               # ACME 目錄 URL（Let's Encrypt: https://acme-v02.api.letsencrypt.org/directory）
    eab-key-id <id>              # External Account Binding Key ID
    eab-mac-key <key>            # EAB HMAC Key（base64url）
    domains <domain> [...]        # 要申請的域名清單
    challenge <type>              # http-01 / dns-01 / dns-persist-01（3.4 新增）

    # 3.4 新增：發行設定檔 (Issuance Profile)
    keytype <ecdsa-p256|ecdsa-p384|rsa>
    bits <2048|3072|4096>        # RSA key 位元數
    acme-vars <name>             # 變數輸出前綴（供後續使用）

Challenge 類型比較

Challenge說明適用場景
http-01HAProxy 自動回應驗證請求（需 port 80 公開）最簡易、全自動
dns-01透過 DNS TXT 記錄驗證（支援 wildcard）無公開 port 80、wildcard
dns-persist-01 NEW持久性 DNS TXT 記錄（含 CA + account ID），不需每次更新手動管理 DNS 區、wildcard

完整範例

# 1. 定義 ACME section
acme letsencrypt
    account-key /etc/haproxy/acme/account.pem
    directory https://acme-v02.api.letsencrypt.org/directory
    domains example.com www.example.com
    challenge http-01

    # 3.4 發行設定檔
    keytype ecdsa-p256
    acme-vars acme_le

# 2. crt-store 引用 ACME
crt-store web_certs
    load crt example.com.pem acme letsencrypt

# 3. 前端引用
frontend https-in
    bind :443 ssl crt example.com.pem alpn h2,http/1.1
🆕 DNS-PERSIST-01 原理設定一條包含 CA 名稱 + ACME 帳號 ID 的持久 TXT 記錄後，CA 在每次續期時都認可該記錄，不需再更新 DNS。適合 DNS zone 手動管理且不支援自動化 API 的場景。

12.9

Healthchecks 可重用區段 3.4 NEW

HAProxy 3.4 引入 healthcheck section，將 HTTP check 邏輯定義為可重用的命名區段，多個 backend/server 可共享同一份 check 設定。

語法

healthcheck <name>
    http-check send meth GET uri /healthz
    http-check expect status 200
    # 可包含多條 http-check 指令

backend app
    server s1 10.0.0.1:80 check healthcheck mycheck
    server s2 10.0.0.2:80 check healthcheck mycheck

完整範例

# 定義可重用的 health check
healthcheck api_health
    http-check send meth GET uri /healthz hdr Host api.internal
    http-check expect status 200

healthcheck db_health
    option pgsql-check
    # PostgreSQL check 不需額外設定

# backend 引用
backend api_servers
    default-server healthcheck api_health inter 3s fall 3 rise 2
    server api1 10.0.1.1:8080 check
    server api2 10.0.1.2:8080 check

backend db_servers
    default-server healthcheck db_health inter 5s
    server db1 10.0.2.1:5432 check
    server db2 10.0.2.2:5432 check
💡 注意若同時在 backend 層和 healthcheck 區段定義了 http-check 指令，backend 層的設定會覆蓋 healthcheck 區段。healthcheck 區段提供的是「預設值」。

DBE

Dynamic Backends — Runtime API 操作

3.4 最重要的架構功能：後端可透過 Runtime API 動態建立、加入 server、發佈、移除，全程不需要 reload。

Runtime API 命令

命令作用
add backend <name> from <defaults> [mode …]從指定 defaults 繼承設定，建立新 backend
add server <be/srv> <addr> [opts]加入 server
enable server <be/srv>啟用 server
enable health <be/srv>啟用 health check
publish backend <name>發佈 backend（使其可被 frontend 路由到）
unpublish backend <name>取消發佈
del backend <name>刪除 backend（需先 unpublish + 無活躍連線）
set server <be/srv> state maint設為維護模式（優雅下線）

操作流程範例

# 1. 建立 backend
echo "add backend test-app from mydefaults mode http" | socat stdio /run/haproxy/admin.sock
# → New backend registered.

# 2. 加入 server
echo "add server test-app/server1 10.0.0.10:8080 check" | socat stdio /run/haproxy/admin.sock

# 3. 啟用
echo "enable server test-app/server1" | socat stdio /run/haproxy/admin.sock
echo "enable health test-app/server1" | socat stdio /run/haproxy/admin.sock

# 4. 發佈（frontend 現在可以路由到它）
echo "publish backend test-app" | socat stdio /run/haproxy/admin.sock

# 5. 搭配 map file 動態路由
echo "add map virt@routes.map /test test-app" | socat stdio /run/haproxy/admin.sock

刪除流程

# 優雅下線
echo "set server test-app/server1 state maint" | socat stdio /run/haproxy/admin.sock
echo "wait 5s srv-removable test-app/server1; del server test-app/server1" | socat stdio /run/haproxy/admin.sock
echo "unpublish backend test-app" | socat stdio /run/haproxy/admin.sock
echo "del map virt@routes.map /test" | socat stdio /run/haproxy/admin.sock
echo "wait 5s be-removable test-app; del backend test-app" | socat stdio /run/haproxy/admin.sock
⚠ 重要動態 backend 需要 named defaults 區段（defaults mydefaults）供繼承。若不需動態 backend，可設定 tune.defaults.purge on 釋放 defaults 佔用的記憶體。
force-be-switch 可強制使用被 unpublish 或 disabled 的 backend。
JWT

JWT / AES 原生加密操作

JWT 驗證流程

# global 段 — 限制可接受的演算法
global
    jwt.decrypt_alg_list ECDH-ES:RSA-OAEP
    jwt.decrypt_enc_list A128CBC-HS256:A256GCM

# frontend — JWE 解密 + 簽章驗證 + 欄位擷取
frontend api
    bind :443 ssl crt /etc/ssl/api.pem

    # 從 Authorization header 取出 JWT
    http-request set-var(txn.raw_jwt) req.hdr(Authorization),field(2,' ')

    # 若 JWT 是加密的 (JWE)，先用 secret 解密
    http-request set-var(txn.jwt) var(txn.raw_jwt),jwt_decrypt_secret("${JWE_SECRET}")

    # 驗證簽章（HS256）
    http-request deny unless { var(txn.jwt),jwt_verify("${JWT_SECRET}","HS256") }

    # 擷取 payload 欄位供路由決策
    http-request set-var(txn.role) var(txn.jwt),jwt_payload_query('$.role','string')
    http-request set-var(txn.sub)  var(txn.jwt),jwt_payload_query('$.sub','string')

    use_backend admin_api if { var(txn.role) -m str admin }
    default_backend user_api

AES 加解密 Converter

# AES-256-CBC 解密（token 或 session cookie）
http-request set-var(txn.token) req.cook(SESSION),aes_cbc_dec(256,"${AES_KEY}","${AES_IV}")

# AES-GCM 解密（帶認證標籤）
http-request set-var(txn.payload) req.body,aes_gcm_dec(256,"${AES_KEY}","${AES_IV}")
🆕 v3.4 新增jwt_decrypt_cert（ECDH-ES 非對稱解密）、jwt_decrypt_jwk（JWK 格式解密）、jwt.decrypt_alg_list / jwt.decrypt_enc_list（演算法白名單）、AES-CBC/AES-GCM converter。

OpenTelemetry 分散式追蹤

HAProxy 3.4 以 OpenTelemetry 取代已棄用的 OpenTracing filter。3.5 將完全移除 OpenTracing。

設定範例

# global — 載入 OTel addon
global
    otel-config /etc/haproxy/otel.yaml

# frontend / backend — 啟用 OTel filter
frontend api
    filter opentelemetry
    # traces 自動傳送到 OTLP collector

FLT

Filter 重構 & 其他 3.4 重點

filter-sequence — 明確控制 filter 順序

backend app
    filter compression
    filter bwlim-out rate-limit
    # 宣告順序 ≠ 執行順序
    filter-sequence bwlim-out compression  # 先限速再壓縮

壓縮 filter 拆分

舊寫法 (3.0)新寫法 (3.4)
filter compressionfilter comp-req（請求）+ filter comp-res（回應）

http-request set-timeout 擴充

3.4 新增支援動態設定 timeout connect、timeout queue、timeout tarpit（原本僅支援 server/tunnel/client）。

http-request set-timeout connect 2s  if { path_beg /fast/ }
http-request set-timeout queue   50ms if is_bulk
