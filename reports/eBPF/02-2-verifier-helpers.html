5.1 為何 Verifier 是 BPF 的靈魂

把 user 寫的程式塞進 Kernel 執行——這在過去十年聽起來像是場惡夢。Linux Kernel 之所以敢這麼做，唯一的原因就是 Verifier：一個位於 kernel/bpf/verifier.c、約三萬行程式碼的靜態分析器。它在 BPF_PROG_LOAD syscall 流程中執行，把任何可能傷害 Kernel 的程式拒於門外。

有些開發者把 Verifier 比喻成「苛刻但善意的官僚機構」——它經常拒絕看似正常的程式，但每一個拒絕背後都是合理的安全考量。學會與 Verifier 合作，是 BPF 開發的成年禮。

Verifier 在 BPF 中扮演四個角色：

  1. 安全守門員：確保程式不會 crash kernel、不會無限迴圈、不會洩漏 kernel pointer。
  2. 類型檢查器：對每個 register 與 stack slot 維護精準的 type 狀態。
  3. 邊界證明器：對每次記憶體存取，從 instruction 出發，反推目前的 register value range，證明存取在合法範圍內。
  4. 資源清理檢查器：對 acquire/release 配對的 helper（取得 socket、開啟 file 等），確保程式所有路徑都釋放。

5.2 Verifier 的三層分析

5.2.1 Layer 1：Control Flow Graph 檢查

第一層處理「程式結構」。Verifier 把 BPF instructions 視為一張有向圖，做下列檢查：

  • 無無限迴圈：原則上禁止後向跳躍。例外：bounded loop（5.3+，Clang 必須能靜態推斷迭代上限）、bpf_loop helper（5.17+）、iter_* KFuncs（6.4+）。
  • 無無法到達指令：所有 instruction 必須位於至少一條從入口出發的路徑上。
  • 跳躍目標合法：所有 jump offset 不能跳到程式以外。
  • BPF-to-BPF 呼叫的入口正確：subprogram 必須有合法 prologue。

5.2.2 Layer 2：模擬執行

第二層是 Verifier 的核心。它從程式入口出發，模擬執行每一條指令，並追蹤所有 register 與 stack slot 的狀態。遇到 branch 時，它會 fork 出兩個狀態繼續走，直到所有路徑都檢查完。

每個 register 維護一個 struct bpf_reg_state，內容包含：

欄位意義
typeSCALAR_VALUE / PTR_TO_CTX / PTR_TO_MAP_VALUE / PTR_TO_PACKET ... 等
var_offtnum，對 SCALAR 追蹤每個 bit 的「0 / 1 / 未知」狀態
smin_value / smax_valuesigned 解讀下的最小最大值
umin_value / umax_valueunsigned 解讀下的最小最大值
id同一個 pointer 的 fork 標記，用來連結相關 register
ref_obj_id需釋放的 reference 物件 id（如 socket）
off / range對 packet pointer，已驗證的有效偏移與範圍

5.2.3 Layer 3：值約束驗證

每次 program 呼叫 helper / kfunc，Verifier 會檢查：

  • 該 program type 是否被允許呼叫此 helper（白名單）。
  • 每個參數的 register state 是否符合預期（例如 bpf_map_lookup_elem 的 arg1 必須是 ARG_CONST_MAP_PTR）。
  • helper 是否會 acquire reference，若是，後續路徑必須有對應 release。
  • 程式 return value 是否符合 program type 的合約（例如 XDP 必須 return XDP_PASS / XDP_DROP / XDP_TX / XDP_REDIRECT / XDP_ABORTED）。

5.3 Type System 完整對照

Verifier 維護的 register type 多達 30+ 種。理解最核心的 10 種就足以讀懂大部分 verifier log。

類型意義常見來源
NOT_INIT從未寫入過，不可讀進入 program 時的 R2-R5
SCALAR_VALUE普通數值（不可作為 pointer）常數、helper 回傳的 number
PTR_TO_CTX指向 program context（XDP md / sk_buff / pt_regs ...）進入 program 時的 R1
PTR_TO_STACK指向 stack（透過 R10 +/- offset 取得）區域變數位址
PTR_TO_MAP_VALUE指向 map valuebpf_map_lookup_elem 回傳值（已 NULL check）
PTR_TO_MAP_VALUE_OR_NULL同上但可能為 NULL剛從 lookup 拿到、尚未 NULL check
PTR_TO_PACKET指向封包資料XDP/tc 程式的 ctx->data
PTR_TO_PACKET_END封包結束邊界ctx->data_end
PTR_TO_SOCKET指向 socket，refcountedbpf_sk_lookup_tcp
PTR_TO_BTF_ID指向某個 BTF type 的 kernel structfentry/fexit、tp_btf、LSM 程式
CONST_PTR_TO_MAPmap 本身的常數 pointer（非 value）ELF relocation 注入
PTR_TO_MEM普通記憶體 pointer，含已知大小ringbuf 的 reserved buffer

很多類型還可以加上 modifier：

  • _OR_NULL：可能為 NULL，必須先檢查才能 deref。
  • MEM_RDONLY：唯讀記憶體（map flags 設定）。
  • MEM_USER：來自 user space 的記憶體（必須走 bpf_probe_read_user）。
  • MEM_RCU：受 RCU 保護的 pointer，需在 RCU critical section 內使用。

5.3.1 Type 轉換規則範例

每一行的 register state 變化
SEC("xdp")
int example(struct xdp_md *ctx) {
    // R1 = PTR_TO_CTX
    void *data = (void *)(long)ctx->data;
    // R6 = PTR_TO_PACKET (off=0, r=0)  -- r=0 表「尚未證明可讀範圍」

    void *end  = (void *)(long)ctx->data_end;
    // R7 = PTR_TO_PACKET_END

    if (data + 14 > end) return XDP_PASS;
    // 進入 if-false 分支後：
    //   R6 = PTR_TO_PACKET (off=0, r=14)  -- 證明前 14 bytes 可讀

    struct ethhdr *eth = data;
    // R8 = R6 = PTR_TO_PACKET, r=14

    __u16 proto = eth->h_proto;
    // 讀取 R8+12 ~ R8+14，因為 r=14，剛好在合法範圍

    return XDP_PASS;
}

5.4 值追蹤：tnum + interval

Verifier 對 SCALAR 同時維護兩種互補的值表示：

5.4.1 tnum（tristate number）

每個 bit 三種狀態：0 / 1 / unknown。表達「精確的 bit 模式」。例：

tnum意義
tnum(0xff, 0)已知全為 0xff（mask=0、value=0xff）
tnum(0, 0xff)低 8 bits 完全未知
tnum(0x10, 0x0f)高 nibble 是 1，低 nibble 未知（即 0x10–0x1f 之間）

tnum 對位元運算（and、or、xor、shift）追蹤超精準，但對加法之類的運算就會失去精度。

5.4.2 interval（min / max）

對算術範圍的補充：把可能值記成 [smin, smax] 與 [umin, umax] 兩個區間。signed 與 unsigned 各一份是因為比較時邏輯不同（負數處理）。

5.4.3 兩者互補

tnum 擅長 bit 操作、interval 擅長加減。每次 instruction 執行，Verifier 同時更新兩種，最後做交集得到最緊的描述。實務上你看 verifier log 寫 scalar(umin=10,umax=30)，就是 interval 表示；如果出現 scalar(0x...) 形式則包含 tnum 細節。

為什麼要那麼精細？

因為 邊界檢查 必須證明 無論 value 是哪個可能值，存取都在範圍內。例如 map[i] 要證明 0 ≤ i < max_entries，Verifier 必須知道 i 的精確 value range。tnum + interval 是目前 Linux Kernel 找到的「夠精準又能在合理時間內收斂」的折衷方案。

5.5 State Pruning：避免狀態爆炸

「對每個 branch 都 fork」聽起來會炸開：100 個 if 就 2^100 條路徑。Verifier 用 state pruning 技巧避免：

flowchart LR P1["路徑 A 走到指令 #50
state X"] P2["路徑 B 走到指令 #50
state Y"] EQ{{"state Y 是 X 的子集？"}} SKIP["剪枝
路徑 B 不再分析"] GO["繼續分析路徑 B"] P1 --> EQ P2 --> EQ EQ -->|"是"| SKIP EQ -->|"否"| GO

翻譯成大白話：「路徑 A 已經證明過從這條指令出發、用這組 state 的所有後續安全；現在路徑 B 來到同一個指令，state 又是更嚴格的（A 已涵蓋的子集），那就不用再走一次。」

這個機制讓 Verifier 在實務上能處理數萬條 instruction 的程式，但也是「我加了一個變數，程式就過不了 verifier」這類玄學行為的來源——多了一個 register、state 不再被 prune，導致複雜度爆炸。

5.6 Reference Counting：取得即釋放

某些 helper 會回傳需要釋放的 reference，最典型的是 socket lookup：

所有 path 都必須 release
SEC("tc")
int sock_lookup(struct __sk_buff *skb) {
    struct bpf_sock_tuple tuple = { /* ... */ };
    struct bpf_sock *sk = bpf_sk_lookup_tcp(skb, &tuple, sizeof(tuple),
                                            BPF_F_CURRENT_NETNS, 0);
    if (!sk) return TC_ACT_OK;

    // ... 用 sk 做事 ...

    if (some_condition) {
        // ❌ 漏 release！verifier 會拒絕
        return TC_ACT_SHOT;
    }

    bpf_sk_release(sk);     // ✅ 必須在所有 return path 前釋放
    return TC_ACT_OK;
}

Verifier 透過 ref_obj_id 追蹤每個 acquired reference 的去向。任何路徑沒釋放，都會看到：

Unreleased reference id=2 alloc_insn=12

常見需要 release 的 helper / kfunc：

  • bpf_sk_lookup_tcp / udp / bpf_skc_lookup_tcp → bpf_sk_release
  • bpf_ringbuf_reserve → bpf_ringbuf_submit 或 bpf_ringbuf_discard
  • bpf_obj_new（KFunc）→ bpf_obj_drop
  • bpf_iter_*_new（KFunc）→ bpf_iter_*_destroy
  • bpf_dynptr_*（部分變體）

5.7 解讀 Verifier Log

Verifier log 是 BPF 開發最重要的除錯工具。看懂 log 是必修技能。

5.7.1 log notation 全解

每行典型結構：

17: (61) r2 = *(u32 *)(r6 +12)        ; R2_w=scalar(...) R6=pkt(...)
^   ^    ^                             ^
|   |    BPF instruction               instruction 後的 reg state
|   opcode（hex）
instruction 編號

register state 字串的常見組合：

表示意義
R1=ctx()R1 是 PTR_TO_CTX
R2=scalar()R2 是 SCALAR，值未知
R2=42R2 是常數 42
R2=scalar(umin=0,umax=100)R2 範圍 0–100
R6=pkt(off=0,r=14)R6 指向 packet，已驗證可讀 14 bytes
R6=pkt(off=12,r=14)R6 指向 packet+12，整段可讀範圍 14
R0=map_value(off=0,ks=4,vs=8)map value pointer，key 4B、value 8B
R0=map_value_or_null剛從 lookup 拿到，尚未檢查 NULL
R3=fp-8R3 = R10 - 8（指向 stack）
R7_w=...下標 _w 表示「verifier 正在 write 這個 state」（區分 read-only 旁觀記號）
R4=sock(ref_obj_id=2)R4 持有 socket reference id=2，需 release

5.7.2 完整 log 範例：邊界檢查失敗

缺少 bounds check
0: R1=ctx() R10=fp0
0: (61) r2 = *(u32 *)(r1 +0)   ; R1=ctx() R2_w=pkt(off=0,r=0)
1: (61) r3 = *(u32 *)(r1 +4)   ; R3_w=pkt_end()
2: (b7) r0 = 2                 ; R0_w=2
3: (71) r4 = *(u8 *)(r2 +0)
invalid access to packet, off=0 size=1, R2(id=0,off=0,r=0)
R2 offset is outside of the packet
processed 4 insns (limit 1000000) max_states_per_insn 0
total_states 0 peak_states 0 mark_read 0

逐行解讀：

  1. R2_w=pkt(off=0,r=0)：R2 是 packet pointer，r=0 表示尚未證明任何讀取範圍。
  2. 第 3 行 r4 = *(u8 *)(r2 +0) 想讀 1 byte，但 r=0 不夠。
  3. 錯誤訊息：R2 offset is outside of the packet。

修正方式：在 instruction 3 之前加上 if (r2 + 1 > r3) return; ，這會讓 verifier 在 if-false 分支把 r 提升到 1。

5.8 八個經典拒絕案例

每位 BPF 工程師遲早會遇到下面這些。建議先看一遍混個眼熟，真的撞牆時回來查。

5.8.1 案例 1：缺少 NULL check

map lookup 沒檢查 NULL
__u32 key = 0;
__u64 *cnt = bpf_map_lookup_elem(&m, &key);
*cnt += 1;            // ❌ R0 是 PTR_TO_MAP_VALUE_OR_NULL
先 NULL check
__u32 key = 0;
__u64 *cnt = bpf_map_lookup_elem(&m, &key);
if (cnt) {
    *cnt += 1;        // ✅ if-true 分支內 R0 = PTR_TO_MAP_VALUE
}

5.8.2 案例 2：未初始化讀取 stack

helper 收到未初始化 stack
char buf[16];
bpf_perf_event_output(ctx, &m, BPF_F_CURRENT_CPU, buf, sizeof(buf));
// ❌ buf 從未被寫過，verifier 拒絕
先填 0
char buf[16];
__builtin_memset(buf, 0, sizeof(buf));
// 或更新每個欄位後再傳
bpf_perf_event_output(ctx, &m, BPF_F_CURRENT_CPU, buf, sizeof(buf));

5.8.3 案例 3：邊界檢查放錯位置

用變數做邊界，verifier 看不出範圍
__u32 idx = bpf_get_smp_processor_id();
return arr[idx];          // ❌ verifier 不知 idx < ARRAY_SIZE
明確邊界 + AND mask
__u32 idx = bpf_get_smp_processor_id();
if (idx >= 256) return 0;
return arr[idx & 0xff];   // ✅ 雙保險：if 與 mask 都加上

5.8.4 案例 4：迴圈未指定上限

變數上限的迴圈
for (int i = 0; i < n; i++) {   // ❌ n 是變數，verifier 拒絕
    do_thing(i);
}
用編譯期常數或 bpf_loop
// 法 1：常數上限 + 早 break
#pragma unroll
for (int i = 0; i < 32; i++) {  // ✅ 32 是常數
    if (i >= n) break;
    do_thing(i);
}

// 法 2：5.17+ 用 bpf_loop helper
bpf_loop(n, callback, &ctx, 0);  // ✅ 動態上限也 OK

5.8.5 案例 5：嘗試直接讀 Kernel pointer

在 kprobe 直接 deref
struct task_struct *t = (void *)bpf_get_current_task();
pid_t p = t->pid;        // ❌ 不可直接 deref kernel pointer
用 BPF_CORE_READ 或 fentry
// 法 1：kprobe 場景
struct task_struct *t = (void *)bpf_get_current_task();
pid_t p;
BPF_CORE_READ_INTO(&p, t, pid);   // ✅ 走 bpf_probe_read_kernel

// 法 2：用 fentry/fexit/tp_btf（5.5+）
SEC("fentry/__x64_sys_open")
int BPF_PROG(on_open, const char *filename, int flags) {
    // 在 BTF-typed 程式中可直接讀，verifier 知道型別
}

5.8.6 案例 6：忘記 release reference

某條 path 沒 release
struct bpf_sock *sk = bpf_sk_lookup_tcp(...);
if (!sk) return TC_ACT_OK;
if (sk->state == 1) return TC_ACT_SHOT;   // ❌ leak
bpf_sk_release(sk);
return TC_ACT_OK;
所有 path 都 release
struct bpf_sock *sk = bpf_sk_lookup_tcp(...);
if (!sk) return TC_ACT_OK;
int verdict = (sk->state == 1) ? TC_ACT_SHOT : TC_ACT_OK;
bpf_sk_release(sk);   // ✅ 唯一 release point
return verdict;

5.8.7 案例 7：variable map index

struct + offset 越界
struct event ev = {};
ev.fields[user_input] = 1;   // ❌ user_input 範圍未證明
先 mask 再寫
struct event ev = {};
__u32 idx = user_input & (sizeof(ev.fields)/sizeof(ev.fields[0]) - 1);
// 假設陣列大小是 2 的次方，masking 即可保證 in-bounds
ev.fields[idx] = 1;          // ✅

5.9 配合 Verifier 的撰寫技巧

實務上幾條心法能讓你少撞 80% 的 verifier 牆：

  1. 先 NULL check 再用：所有 _OR_NULL 類型，第一件事就是 NULL check。
  2. 邊界 check 寫在最早：拿到 packet pointer 立刻寫 if (data + N > end) return;，後續 verifier 才有 r 範圍可用。
  3. 對 user input 加 mask：idx & (size - 1)（size 為 2 的次方）讓 verifier 一眼看出 in-bounds。
  4. 區域變數初始化：所有 stack buffer 用 __builtin_memset(buf, 0, sizeof(buf))。
  5. helper 配對寫在同個 scope：reserve / release 配對放近一點，方便 verifier 與你自己追蹤。
  6. 常數迴圈搭 #pragma unroll：迴圈次數小（< 64）就 unroll；大或動態用 bpf_loop。
  7. BPF-to-BPF call 拆解大程式：把複雜邏輯拆成 subprogram，每個都通過 verifier 子集分析，總體更快收斂。
  8. Verifier log 看不出原因時調大 log buffer：cilium/ebpf 預設 16K，複雜程式得開 16M+。

5.10 複雜度限制與擴大策略

限制數值備註
單支程式 instruction 數1,000,000（5.2+）之前是 4,096，5.2 大幅放寬
verifier 總 step 上限1,000,000（預設）state pruning 不夠時容易撞
單支程式 stack512 bytes（含 tail call 256）大資料用 PERCPU_ARRAY scratch
tail call 巢狀33（5.10+）之前 32
BPF-to-BPF call 巢狀8—
helper / kfunc 參數數5透過 R1-R5

程式爆 instruction 上限或 verifier step 上限的對策：

  • 拆 program：用 tail call 串接多個 program。
  • 拆 subprogram：把大邏輯拆成 BPF-to-BPF function call，verifier 對 subprogram 獨立分析。
  • 用 KFunc 取代純 BPF 實作：例如字串搜尋走 bpf_strncmp kfunc 比手寫迴圈省太多 verifier 預算。
  • 少寫 trick code：複雜的 register reuse 反而讓 state pruning 失效，擾亂 verifier。寧願多用幾條指令。

5.11 第 5 章小結

  1. Verifier 是 BPF 安全的唯一把關，三層分析：CFG → 模擬執行 → helper / context 約束。
  2. 對每個 register 維護精準 type system 與 tnum + interval 雙重值追蹤。
  3. 遇到 branch 即 fork 狀態，用 state pruning 避免狀態爆炸。
  4. Reference counting 透過 ref_obj_id 確保 acquire/release 配對。
  5. Verifier log notation 是除錯關鍵；八個經典拒絕案例覆蓋 80% 日常情境。
  6. 配合 verifier 的撰寫技巧：早做 NULL check、邊界 check、user input masking、helper 配對。

6.1 為何 BPF 需要 Helper / KFunc

BPF 程式不能呼叫任意 Kernel function——任意呼叫等於把 Kernel 當 library，verifier 無從驗證安全。但完全不呼叫也不行：你需要取得時間、查 Map、輸出 log、操作網路 stack...

解法：Kernel 預先挑選一批安全可呼叫的函式，BPF 程式只能透過這個受控介面與 Kernel 互動。這個介面歷史上分兩代：

  • Helper Functions（2014 起）：固定 ID、白名單管理、UAPI 穩定。
  • KFuncs（Kernel Functions）（2022 起）：用 BTF 函式名呼叫、彈性更高、UAPI 不保證穩定。

6.2 Helper vs KFunc：兩代機制比較

為什麼 KFuncs 是「未來」

新增一個 helper 需要修 UAPI、走 ABI 穩定流程，門檻很高，因此十年下來大概 200 個就停了。KFuncs 透過 BTF 把「Kernel 函式」標記出來即可給 BPF 用，新增成本低、可承擔不穩定。Linux 社群已明確：除非極特殊情況，新功能一律走 KFunc。Helper 數量幾乎不再增加。

docs.ebpf.io 把 helper 依用途分為 14 大類。下面用 helper-card grid 呈現每類的代表 helper（非完整列表，附錄 A 會列全）：

  • bpf_probe_read_user_str

6.4 KFuncs 詳解

KFuncs 是 BPF 與 Kernel 互動的新介面。它有兩個關鍵設計：flags 標記行為、argument suffix 描述參數約束。

6.4.1 KFunc Flags

Flag意義
KF_ACQUIRE會回傳一個需要釋放的 reference；verifier 強制配對 release
KF_RELEASE釋放某個 acquired reference
KF_RET_NULL回傳值可能是 NULL，呼叫方必須先檢查
KF_TRUSTED_ARGS只接受 PTR_TRUSTED 參數（從 program 入口傳下來、未經運算）
KF_RCU可接 RCU-protected pointer，呼叫方需在 RCU critical section
KF_SLEEPABLE可能 sleep，僅 sleepable program 可呼叫
KF_DESTRUCTIVE可能造成 panic / reboot；需 CAP_SYS_BOOT
KF_ITER_NEW / KF_ITER_NEXT / KF_ITER_DESTROYiterator 三步驟，verifier 強制配對

KFunc 的參數透過名稱後綴傳達 verifier 約束資訊：

__k必須是常數，verifier 在 load 時就要知道值void *bpf_obj_new(__u64 local_type_id__k)
__szk常數 size（compile-time）—
__opt該參數可為 NULL（搭 __sz 用）buffer 可省略
__nullablepointer 可為 NULL，但 verifier 不強制 NULL checktask__nullable
__uninit該參數未初始化也 OK（kfunc 自己會初始化）iterator init 用
__ignverifier 忽略該參數的型別檢查少用
__refcounted_kptr必須是 refcounted kernel pointer—

6.5 Dynptr：動態大小指標

BPF 程式長期以來有一個痛點：處理變動長度資料很煩。一段封包可能 14 bytes，也可能 1500 bytes；驗證每個 access in-bounds 寫起來繁瑣。Dynptr 解決這個問題，從 5.19 起逐步成熟。

Dynptr 把「pointer + 大小 + 安全 metadata」打包，verifier 看到 dynptr 就知道是有 metadata 撐腰的安全結構。讀寫時自動檢查邊界。

用 dynptr 處理 XDP 封包
SEC("xdp")
int xdp_with_dynptr(struct xdp_md *ctx) {
    struct bpf_dynptr ptr;
    if (bpf_dynptr_from_xdp(ctx, 0, &ptr) < 0)
        return XDP_ABORTED;

    // 讀前 14 bytes 到 buffer
    __u8 buf[14];
    if (bpf_dynptr_read(buf, sizeof(buf), &ptr, 0, 0) < 0)
        return XDP_PASS;

    // 或直接拿 slice（不複製）
    void *slice = bpf_dynptr_slice(&ptr, 14, NULL, 0);
    if (!slice) return XDP_PASS;

    // ... 處理 ...
    return XDP_PASS;
}

6.6 Iterator KFuncs：迭代器

Kernel 6.4 起引入正式的迭代器機制。透過 KF_ITER_NEW / NEXT / DESTROY 三個 flag，verifier 可以保證迭代器不會洩漏，也允許「動態次數」的有界迴圈。

遍歷系統所有 task
SEC("syscall")
int dump_tasks(void *ctx) {
    struct bpf_iter_task it;
    struct task_struct *task;

    bpf_iter_task_new(&it, NULL, 0);

    while ((task = bpf_iter_task_next(&it))) {
        // 對每個 task 做事
        bpf_printk("pid=%d comm=%s", task->pid, task->comm);
    }

    bpf_iter_task_destroy(&it);   // verifier 會檢查必須呼叫
    return 0;
}

使用 iter_num 取代純數字迴圈，搭 verifier 的迭代器支援可以做動態上限的有界迴圈：

動態 N 次迴圈，取代 #pragma unroll
struct bpf_iter_num it;
int *v;
bpf_iter_num_new(&it, 0, n);     // 範圍 [0, n)
while ((v = bpf_iter_num_next(&it))) {
    process(*v);
}
bpf_iter_num_destroy(&it);

6.7 選用建議

場景建議
需要跨多版本 Kernel 的工具（5.10–6.x）優先用 Helper
新 Kernel 限定的開發（6.4+）放心用 KFunc
存取受 RCU 保護的 kernel object必用 KFunc（Helper 不支援 KF_RCU）
動態長度資料處理用 Dynptr KFunc
動態次數迴圈5.17+ 用 bpf_loop helper；6.4+ 改用 iter KFunc 更乾淨
cgroup / task / fs 統計新 KFunc 比舊 helper 強大很多
32-bit ARM / 老架構只能用 Helper（KFunc 需 JIT）

6.8 第 6 章小結

  1. Helper 與 KFunc 是 BPF 與 Kernel 互動的兩代機制：Helper 穩定但停滯，KFunc 不穩但是未來。
  2. Helper 分 14 大類，~200 個；KFunc 約 150 個且持續成長。
  3. KFunc 透過 flags（KF_ACQUIRE / RCU / SLEEPABLE 等）與 argument suffix（__sz / __k / __nullable 等）描述語意。
  4. Dynptr 解決變動長度資料的 verifier 友善處理。
  5. Iterator KFunc 讓動態次數迴圈第一次成為可能。
  6. 選用原則：跨版本相容用 Helper，新功能無痛用 KFunc。
