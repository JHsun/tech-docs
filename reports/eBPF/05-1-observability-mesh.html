18.2 Continuous Profiling 工作原理

18.2.1 取樣 → 聚合 → 火焰圖

傳統 perf record 只能對某個 process 短時間取樣。eBPF profiler 用常駐取樣器 + map 聚合 + 非同步上傳達成「production-safe always-on profiling」。

sequenceDiagram participant CPU as CPU 0..N participant K as Kernel
perf_event timer participant B as BPF program
(perf_event type) participant M as STACK_TRACE map
+ HASH map count participant A as Profiler agent participant S as Backend
(Parca/Pyroscope server) loop 每 1/19 秒 K->>CPU: 中斷 (per-CPU) CPU->>B: 執行 BPF B->>B: bpf_get_stackid(ctx) B->>M: 紀錄 stack_id B->>M: count++ on (pid, stack_id) end loop 每 N 秒 A->>M: lookup batch dump M-->>A: aggregated samples A->>A: 解析 stack_id → 函式名 A->>S: pprof 上傳 end

18.2.2 為什麼這個架構可以 production always-on

關鍵設計節省的 overhead
取樣（19 Hz / CPU）只看 5% 的 CPU 時間，但統計上代表全部
BPF 寫 map，不直接打 user space無 syscall、無 context switch
Stack trace deduplicate同樣 stack 只存一次，N 次出現只增加 counter
Agent 非同步 dump（每 N 秒）不阻擋 BPF 執行
跨 process 共用 BPF 程式不需要每個 pod 注入

實測 overhead 通常 < 1% CPU，遠低於傳統 perf 的 5-10%。

18.8 自己做：用 STACK_TRACE map 寫火焰圖採樣器

了解原理勝過用工具。下面示範用 BPF_MAP_TYPE_STACK_TRACE 自寫一個簡易 CPU profiler。

18.8.1 BPF C

profile.bpf.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

#define MAX_STACK_DEPTH 127
#define MAX_ENTRIES 16384

struct {
    __uint(type, BPF_MAP_TYPE_STACK_TRACE);
    __type(key, __u32);
    __type(value, __u64[MAX_STACK_DEPTH]);
    __uint(max_entries, MAX_ENTRIES);
} stack_traces SEC(".maps");

struct sample_key {
    __u32 pid;
    __s32 user_stack_id;
    __s32 kern_stack_id;
};

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, struct sample_key);
    __type(value, __u64);
    __uint(max_entries, MAX_ENTRIES);
} counts SEC(".maps");

SEC("perf_event")
int do_sample(struct bpf_perf_event_data *ctx) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;
    if (pid == 0) return 0;

    struct sample_key key = {
        .pid = pid,
        .user_stack_id = bpf_get_stackid(ctx, &stack_traces, BPF_F_USER_STACK),
        .kern_stack_id = bpf_get_stackid(ctx, &stack_traces, 0),
    };

    __u64 zero = 0, *count;
    count = bpf_map_lookup_elem(&counts, &key);
    if (count) (*count)++;
    else bpf_map_update_elem(&counts, &key, &zero, BPF_ANY);

    return 0;
}

18.8.2 Go user space（attach 到 perf event）

main.go（節錄）
package main

import (
    "github.com/cilium/ebpf"
    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/rlimit"
    "log"
    "os"
    "os/signal"
    "syscall"
)

func main() {
    if err := rlimit.RemoveMemlock(); err != nil { log.Fatal(err) }

    var objs profObjects
    if err := loadProfObjects(&objs, nil); err != nil { log.Fatal(err) }
    defer objs.Close()

    /* 對每個 CPU attach 一個 perf event sampler，99 Hz */
    for cpu := 0; cpu < runtime.NumCPU(); cpu++ {
        l, err := link.OpenPerfEventCPU(link.PerfEventOptions{
            CPU:        cpu,
            SampleFreq: 99,
            Type:       link.PerfTypeSoftware,
            Config:     link.PerfCountSWCPUClock,
            Program:    objs.DoSample,
        })
        if err != nil { log.Fatal(err) }
        defer l.Close()
    }

    /* 等待 30 秒，然後 dump */
    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt, syscall.SIGTERM)
    log.Println("Sampling... Ctrl-C 結束")
    <-sig

    dumpFolded(objs.Counts, objs.StackTraces)
}

/* dumpFolded：把 (pid, stack) → count 轉成 folded format（餵 flamegraph.pl 用） */
func dumpFolded(counts *ebpf.Map, st *ebpf.Map) {
    var key profSampleKey
    var val uint64

    iter := counts.Iterate()
    for iter.Next(&key, &val) {
        names := []string{}
        var stack [127]uint64

        /* user stack */
        if key.UserStackId >= 0 {
            st.Lookup(uint32(key.UserStackId), &stack)
            for _, ip := range stack {
                if ip == 0 { break }
                names = append(names, fmt.Sprintf("0x%x", ip))
                /* 真實工具會用 /proc/[pid]/maps 解析 + DWARF/symbol */
            }
        }
        /* kernel stack */
        /* ... */

        fmt.Printf("pid_%d;%s %d\n", key.Pid, strings.Join(names, ";"), val)
    }
}

18.9 eBPF 可觀測性的成本控制

BPF 跑在 kernel 內，每個事件都會觸發。如果不控管，高頻事件（每秒百萬次的網路封包、context switch）會吃掉可觀的 CPU，而且事件量會塞爆 user space。

18.9.1 控管四原則

原則實作方式
① Sampling每 N 個事件取一個（perf_event 用採樣頻率，自寫程式用 bpf_get_prandom_u32() %% N）
② Aggregation in BPFBPF 內聚合（HASH map count），不要每個事件都打到 user space
③ Cardinality 控制label 維度爆炸是觀測系統 #1 殺手；避免把 PID、connection-tuple 當 label
④ Retention 規劃profile 與高 cardinality metric 退場政策；老資料降採樣

18.9.2 BPF 端 sampling 範例

每 100 個事件記一個
SEC("kprobe/tcp_v4_connect")
int sampled_trace(struct pt_regs *ctx) {
    if (bpf_get_prandom_u32() % 100 != 0)
        return 0;     /* 99% 跳過 */
    /* ... 真正記錄 ... */
    return 0;
}

18.10 eBPF vs OpenTelemetry：互補不取代

面向eBPF 擅長OTel 擅長
取得時機事後（不必預先 instrument）事前（明確標記哪是 span）
業務語意看不到「order_id」、「user_id」應用知道，能加 tag
跨服務 trace 串接難（需 context propagation）標準 W3C trace context
核心級事件強（syscall、scheduling、TCP retrans）無法直接看
跨語言一致強（看 binary 不看 SDK）需要每語言 SDK
低 overhead強（kernel 內聚合）視 SDK 與 sampling 設計
最佳實踐：OTel + eBPF 共存

業務語意的 span（含 user_id / order_id / 重要 tag）用 OTel 寫應用層 instrumentation。底層網路與系統指標、profile、L7 trace、kernel event 等用 eBPF 自動採集。兩邊用 trace context（traceparent）關聯。這是 2026 業界共識。

18.11 第 18 章小結

  1. 觀測四支柱：Metrics / Logs / Traces / Profiles；eBPF 在每一支柱都帶來「無感、跨語言、低 overhead」的加值。
  2. Continuous profiling 用「perf_event 採樣 + STACK_TRACE map 聚合 + 非同步上傳」達到 always-on，overhead < 1%。
  3. 主流工具地圖：Pixie（自動 L7 trace）/ Parca / Pyroscope（profiling）/ Hubble（網路）/ Inspektor Gadget（kubectl 工具集）。
  4. Coroot / Beyla / Odigos 走「eBPF + OTel」路線：用 BPF 採集，但輸出標準 OTLP，不綁平台。
  5. 自己用 BPF_MAP_TYPE_STACK_TRACE + perf_event 也能實作 profiler，了解原理勝過用工具。
  6. 四個成本控制原則：sampling / aggregation / cardinality / retention。
  7. eBPF 不取代 OpenTelemetry，兩者互補：業務語意用 OTel、底層細節用 eBPF。

19.1 為何 eBPF 能改寫 K8s 網路

Kubernetes 預設網路三大元件都有 eBPF 替代品的明確理由：

傳統元件痛點eBPF 解法
kube-proxy / iptablesservice 多時 iptables 規則 O(n) 線性掃描，1000 service 延遲明顯Cilium socket-LB（O(1) hash 查詢）
iptables NetworkPolicy基於 IP 的規則難維護、policy 變更需 reloadCilium identity-based policy（基於 label，K8s 原生概念）
Sidecar service mesh每 pod 多一個 Envoy（CPU + memory + latency 三倍負擔）per-node Envoy + eBPF L3/L4，95% 流量不過 sidecar

19.2 Cilium 取代 kube-proxy

19.2.1 kube-proxy 為何慢

flowchart LR POD["Pod sends to
service VIP 10.96.0.1:80"] NETNS["Pod netns"] NSTACK["Host network stack"] IPT["iptables 規則鏈
(KUBE-SERVICES → KUBE-SVC-XXX → KUBE-SEP-YYY)"] DNAT["DNAT to
real pod IP"] OUT["送出"] POD --> NETNS --> NSTACK --> IPT IPT -->|"O(n) 線性掃描"| DNAT --> OUT

每個 service 約 5-7 條 iptables 規則，1000 個 service 就 5000-7000 條。每個封包都要遍歷一次，對 connection-heavy 工作負載是顯著瓶頸。

19.2.2 Cilium socket-LB 怎麼解

Cilium 用 CGROUP_SOCK_ADDR（第 10 章 §10.4）在 connect() 系統呼叫的瞬間就改寫目的地：

flowchart LR POD["Pod connect()
到 service VIP"] SC["CGROUP_SOCK_ADDR
BPF 攔截"] MAP["service map 查詢
(O(1) hash)"] REW["改寫 user_ip4 +
user_port → real backend"] NSTACK["Kernel network stack"] OUT["直送 backend pod"] POD --> SC --> MAP --> REW --> NSTACK --> OUT

結果：

  • O(1) 查詢，不論 service 多少。
  • 改寫發生在 connect() 瞬間，之後封包不再經過 LB（不像 iptables DNAT 每包都要查 conntrack）。
  • 無 conntrack 開銷，無 iptables 規則，10-30% 延遲改善是常見實測數字。

19.5 ClusterMesh 與多叢集

多叢集場景（DR、跨地域、聯邦）傳統靠 Istio multi-cluster（複雜）或 submariner。Cilium ClusterMesh 把它變成 native：

關鍵特性：

  • Global Service：用 annotation: io.cilium/global-service: "true" 標記跨叢集 service。
  • Identity 同步：Cilium identity（基於 K8s label）跨叢集同步。
  • 跨叢集 NetworkPolicy：用 cluster name 維度授權。
  • 傳輸：node IP 直連 + WireGuard / IPsec 自動加密。

19.6 Katran：Meta 的 L4 LB

Katran
定位
Meta 開源的 L4 負載均衡器
主要技術
XDP（NIC ingress）+ Maglev hash + IPIP encapsulation
規模
Meta 內部處理 facebook.com / instagram.com 全部入站流量
性能
單 NIC 10+ Mpps，scale linear with NIC queues

Katran 是典型 XDP_TX 用例：

  1. 封包到 NIC，XDP 程式跑。
  2. 從 5-tuple 算 Maglev hash → 挑 backend。
  3. 用 IPIP 把封包包起來轉給 backend（保留 client src IP）。
  4. XDP_TX 從同一 NIC 送出，完全不進 Linux network stack。

結果：100K req/s 等級的 LB 不需要傳統 LVS / HAProxy 機群。Cilium 的 XDP-based load-balancer mode 借鑑了 Katran 的設計。

19.7 加密：WireGuard 與 IPsec

節點間流量加密是合規常見需求（PCI-DSS、HIPAA）。Cilium 提供兩種模式：

19.8 BIG TCP / SRv6 / IPv6 only

19.8.1 BIG TCP

Linux 5.19 引入 BIG TCP：把 TCP 段的 GSO / GRO 上限從 64 KB 拉到 192 KB（IPv6），減少封包數量、提高 throughput。Cilium 1.13+ 支援啟用：

--set enableIPv6BIGTCP=true

實測對 100 Gbps 工作負載 throughput 提升 30%+，特別適合 AI 訓練、儲存 replication 場景。

19.8.2 SRv6（Segment Routing v6）

SRv6 是 IPv6 上的 source routing：把封包要走的路徑寫進 IPv6 extension header。Cilium 用 BPF（LWT_SEG6LOCAL，第 9 章）支援 SRv6 終端，做到 service chaining、跨叢集 traffic engineering。

19.8.3 IPv6 only Kubernetes

2025-2026 大型雲端開始推 IPv6 only 叢集（雙堆疊 IP 不夠用）。Cilium 是少數 native 支援 IPv6 only 的 CNI，包含 socket-LB、policy、加密都可只走 IPv6。

19.10 第 19 章小結

  1. eBPF 改寫 K8s 網路三大元件：kube-proxy / NetworkPolicy / Service Mesh。
  2. Cilium socket-LB 用 CGROUP_SOCK_ADDR 在 connect() 瞬間改寫，O(1) 取代 iptables 的 O(n)。
  3. Cilium data plane 多層分工：cgroup_sock_addr（LB）+ tcx（policy/encap）+ XDP（早期 drop/LB）+ per-node Envoy（L7）。
  4. Sidecarless 模式比 sidecar 省 5-10 倍 CPU、3-5 倍 memory，已是 Istio Ambient、Cilium、Linkerd 三家共同方向。
  5. ClusterMesh 把多叢集網路變成 native，identity / service / policy 跨叢集同步。
  6. Katran 是 XDP_TX 的標桿：Meta 用它扛全部入站流量。
  7. WireGuard / IPsec 提供節點間透明加密；BIG TCP 把 GSO 上限拉到 192 KB；SRv6 / IPv6 only 是 2026 主流方向。
