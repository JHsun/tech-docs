3.1 eBPF Virtual Machine 架構

eBPF 程式不是直接在 CPU 上跑——它在 Kernel 內部一個特殊的虛擬機（VM）裡執行（Verifier 通過後 JIT 為原生指令，但 ISA 設計依然是 VM 視角）。理解這個 VM 的限制，才能寫得出能通過 Verifier 的程式。

3.1.1 暫存器（Registers）

eBPF VM 有 11 個 64-bit 暫存器，模擬類 RISC 架構：

R0
回傳值（return value）
R1
第 1 個函式參數
R2
第 2 個函式參數
R3
第 3 個函式參數
R4
第 4 個函式參數
R5
第 5 個函式參數
R6
callee-saved 暫存器
R7
callee-saved 暫存器
R8
callee-saved 暫存器
R9
callee-saved 暫存器
R10
read-only frame pointer（指向 stack）

關鍵約定：

  • 程式進入時，R1 一定是 context pointer（隨程式類型不同而不同：tracepoint 是事件結構、XDP 是 xdp_md *、tc 是 __sk_buff *）。
  • 呼叫 helper function 時，前 5 個參數依序放入 R1–R5，回傳值在 R0。這個 ABI 與 x86-64 的 calling convention 對齊，所以 JIT 後的程式碼能高效呼叫 Kernel 內部函式。
  • R10 不能寫，只能讀。所有 stack 存取都透過 R10 - offset 的方式進行。

3.1.2 Stack

每個 BPF 程式擁有 固定 512 bytes 的 stack（使用 tail call 時剩 256 bytes）。沒有 heap、沒有 alloca。所有「區域變數」都來自這 512 bytes。

為何 stack 這麼小？

eBPF 程式必須在有限時間內結束（Verifier 會強制執行），且要在 Kernel 與其他程式共用 stack 空間，故設定上限。如果你的程式需要大型暫存區，正確做法是把資料放進 Map（特別是 BPF_MAP_TYPE_PERCPU_ARRAY 當大型 scratch buffer）。

3.1.3 Context

每個程式類型有自己的 context 結構，由 Kernel 在程式被呼叫時準備好放在 R1。常見幾類：

3.1.4 指令集（ISA）

eBPF 是 fixed-length 64-bit 指令格式，每條指令 8 bytes。主要分類：

  • ALU64 / ALU32：算術與邏輯運算（add、sub、mul、div、mod、and、or、xor、shift）。
  • Load / Store：記憶體讀寫，含原子 atomic operations。
  • Branch：條件跳躍（jeq、jne、jlt、jle、jgt、jge、jset、jsgt 等），含 signed / unsigned。
  • Call：呼叫 helper function 或 BPF-to-BPF function。
  • Exit：程式結束（用 R0 作為 return value）。

以 Hello World 中的 e->pid = bpf_get_current_pid_tgid() >> 32; 這一行為例，會被 clang 編成大致這樣的 BPF 指令：

編譯後的 BPF 指令（簡化示意）
; e->pid = bpf_get_current_pid_tgid() >> 32

call 14            ; 呼叫 helper #14 (bpf_get_current_pid_tgid)
                   ; 回傳 64-bit (tgid<<32) | pid，放在 R0
r0 >>= 32          ; 邏輯右移 32 bit -> 取得 tgid
                   ; (BPF 慣例：tgid 才是 user space 看到的 PID)
*(u32 *)(r1 + 0) = r0   ; 寫入 e->pid (假設 r1 指向 event)
查看實際的 BPF assembly

編譯出 .o 後，用 llvm-objdump -S program.o 可以看到 C 與 BPF 指令並列。bpftool prog dump xlated id <ID> 則能看到 Kernel 載入後（含 verifier 的修正、relocation）的最終 BPF 指令。冊四第 17 章會深入這些除錯工具。

3.3 Verifier 內部運作

Verifier 是 eBPF 安全的核心。它會在 BPF_PROG_LOAD 過程中拒絕任何「可能傷害 Kernel」的程式。它不是 unit test，是靜態分析器——所有檢查都在程式還沒執行時完成。

3.3.2 Step 1：Control Flow Graph 檢查

Verifier 把 BPF instruction 視為 DAG（Directed Acyclic Graph），檢查：

  • 無向後跳躍（無迴圈）—— 但 5.3+ 起可用 bounded loop（編譯器靜態確認 iteration 數量）；5.17+ 起可用 bpf_loop helper。
  • 無 unreachable instruction（沒被任何路徑觸及）。
  • 所有跳躍目標都在程式範圍內。

3.3.3 Step 2：Register State Tracking

Verifier 對每個暫存器與 stack slot 維護一個 bpf_reg_state，記錄：

  • type：NOT_INIT、SCALAR_VALUE、PTR_TO_CTX、PTR_TO_MAP_VALUE、PTR_TO_STACK、PTR_TO_PACKET、PTR_TO_SOCKET 等。
  • 已知範圍：對 SCALAR 維護「最小 / 最大可能值」，對 pointer 維護「最小 / 最大 offset」。
  • refcount：對需釋放的 pointer（如 bpf_sk_lookup_tcp 取得的 socket）追蹤是否在 program 結束前 release。

Verifier 沿著所有可能執行路徑同時推進，遇到分支就分裂狀態。為了避免狀態爆炸，它使用 state pruning：若新路徑的 reg state 是已驗證路徑的子集，就跳過。

3.3.4 經典拒絕案例

會被 Verifier 拒絕：未檢查 NULL
SEC("xdp")
int bad_xdp(struct xdp_md *ctx) {
    void *data     = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    // 沒有檢查 data + 14 是否超出 data_end
    struct ethhdr *eth = data;
    if (eth->h_proto == htons(ETH_P_IP))   // ← Verifier 拒絕：可能讀越界
        return XDP_DROP;

    return XDP_PASS;
}

// 正確寫法：先比對長度
if (data + sizeof(*eth) > data_end) return XDP_PASS;
struct ethhdr *eth = data;
會被 Verifier 拒絕：map value 越界
SEC("kprobe/sys_open")
int bad_kprobe(void *ctx) {
    __u32 key = 0;
    char *val = bpf_map_lookup_elem(&my_array_map, &key);
    if (!val) return 0;     // ← 必要：Verifier 要求

    // map value_size 是 16 bytes
    val[20] = 'X';          // ← Verifier 拒絕：超出 value 範圍
    return 0;
}
會被 Verifier 拒絕：讀取未寫入的 stack
SEC("tracepoint/syscalls/sys_enter_execve")
int bad_tp(void *ctx) {
    char buf[16];           // ← stack 預留 16 bytes，但內容未定義

    // 未先寫入 buf 就傳給 helper
    bpf_perf_event_output(ctx, &events, BPF_F_CURRENT_CPU,
                          buf, sizeof(buf));  // ← Verifier 拒絕

    return 0;
}

// 正確寫法：先 __builtin_memset(buf, 0, sizeof(buf));

3.3.5 Verifier log 解讀

當載入失敗時，Verifier 會輸出詳細 log。一個典型 log 片段：

Verifier log（簡化）
0: R1=ctx() R10=fp0
0: (b7) r2 = 0                  ; R2_w=0
1: (61) r3 = *(u32 *)(r1 + 0)   ; R1=ctx() R3_w=scalar(...)
2: (07) r3 += 14                ; R3_w=scalar(umin=14,umax=...)
3: (2d) if r3 > r2 goto pc+10   ; R2_w=0 R3_w=scalar(...)
4: (71) r4 = *(u8 *)(r3 + 0)    ; R3 ptr access without bounds check

invalid access to packet, off=0 size=1, R3(id=0,off=14,r=0)
R3 offset is outside of the packet

解讀重點：

  • 每行 N: (XX) ... 是 BPF 指令編號 N、opcode XX。
  • R1=ctx()、R3_w=scalar(...) 是 Verifier 推導的 register 狀態。_w 表示這個值是 verifier「正在追蹤」的（write）狀態。
  • 最後一行的 原因 才是真正錯誤訊息。

3.4 JIT 編譯

通過 Verifier 的程式會被 JIT（Just-In-Time）編譯為當前 CPU 的原生機器碼。Linux Kernel 為主要架構都實作了 BPF JIT：

3.5 BTF：BPF Type Format

BTF（BPF Type Format）是 eBPF 生態系最重要的支撐技術。它是一種緊湊的 type 描述格式，靈感來自 Sun 的 CTF（Compact C Type Format）。

3.5.1 BTF 解決什麼問題

過去 eBPF 程式要讀取 Kernel 結構（如 struct task_struct）必須 #include <linux/sched.h>，而這個 header 只反映「編譯時主機的 Kernel 版本」。Kernel 5.4 把某個欄位移到結構尾端，5.10 又新增了一個欄位，傳統 BPF 程式就會在新版本上讀錯偏移、印出垃圾資料。

BTF 的核心想法很簡單：讓 Kernel 自己描述自己的 type，然後讓 BPF loader 在載入時根據目標 Kernel 的 BTF動態調整 BPF 程式裡的欄位偏移。

3.5.4 BTF 的其他用途

BTF 不只是用於 CO-RE，它還支撐多項現代 eBPF 特性：

  • BTF-enabled raw tracepoint：直接用 BTF 推導 tracepoint 參數的型別，免去手動定義。
  • fentry / fexit：替代 kprobe，成本更低、可直接讀 typed 參數。
  • BPF LSM：每個 LSM hook 的參數型別由 BTF 描述。
  • STRUCT_OPS：可程式化的 Kernel ops 介面（如自訂 TCP congestion control、scheduler）。
  • kfuncs：可以由 BPF 程式呼叫的 Kernel function（不是 helper），由 BTF 描述介面。

3.6 CO-RE：Compile Once – Run Everywhere

CO-RE 是「編一次，到處跑」的縮寫。它讓 BPF 物件檔（.o）在 Kernel 5.5、5.10、6.1、6.8... 不同版本之間都能正確執行，無需重新編譯。

3.6.1 為何需要 CO-RE

假設你的 BPF 程式想讀 task_struct 的 pid 欄位。傳統 BPF 程式編譯時 clang 會把欄位偏移寫死（例如 load *(u32 *)(r1 + 1232)，1232 是當前 Kernel 上 pid 的 byte offset）。但 Kernel 5.10 新加了一個欄位，pid 偏移變成 1240。原本的程式在 5.10 上會讀到完全不相干的資料。

  1. Clang 標記欄位存取：每次原始碼寫 task->pid，clang 不直接 emit 一個 hardcoded offset，而是 emit 一條「pseudo instruction」+ 一個 BTF relocation 紀錄：「我要存取 struct task_struct 的 pid 欄位」。
  2. BTF 隨 .o 一起發行：編譯出的 .o 裡面包含程式自己用到的所有 type 的 BTF。
  3. Loader 動態 patch：載入時，loader 比對「程式 BTF 中的 task_struct」與「Kernel BTF 中的 task_struct」，找到 pid 在當前 Kernel 中的真實 offset，把那條 pseudo instruction 改寫成 load *(u32 *)(r1 + 真實偏移)。

3.6.3 CO-RE 巨集（C 端）

實務上你不會手寫 pseudo instruction，而是用 libbpf 提供的巨集：

用 BPF_CORE_READ 安全讀取 Kernel 結構
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>     // CO-RE 巨集

SEC("kprobe/do_open")
int trace_open(struct pt_regs *ctx) {
    // 取得當前 task_struct
    struct task_struct *task = (void *)bpf_get_current_task();

    // 直接 task->pid 在 verifier 那會炸（不可直接 deref kernel pointer）
    // 必須用 BPF_CORE_READ 才能 (1) 走 bpf_probe_read，(2) 套上 CO-RE relocation
    pid_t pid;
    BPF_CORE_READ_INTO(&pid, task, pid);

    // 讀巢狀欄位：task->real_parent->pid
    pid_t ppid = BPF_CORE_READ(task, real_parent, pid);

    // 比對欄位是否存在
    if (bpf_core_field_exists(task->exit_code))
        bpf_printk("has exit_code field");

    return 0;
}

為什麼 ringbuf / hashmap 等 helper 不需要 CO-RE？

CO-RE 解的是「讀寫 Kernel 內部結構的偏移問題」。Helper function 是 ABI-stable 的——它們的 ID 與 prototype 在 Kernel 之間不變，所以呼叫 helper 不需要 relocation。CO-RE 主要影響你 trace 任意 Kernel struct 時的欄位存取。

3.7 Maps：跨空間共享記憶體

Maps 是 BPF 程式與 user space、以及 BPF 程式之間的唯一資料共享機制。BPF 程式沒有 heap、沒有全域 mutable 變數（global static 是唯讀），所有跨函式呼叫保留資料、所有對外輸出都靠 Map。

3.7.1 Map 是什麼

從介面看，Map 是 key-value 容器；從實作看，Map 是 Kernel 中的物件，由 BPF_MAP_CREATE 建立、用 FD 存取。

3.8 Helper Functions 與 KFuncs

BPF 程式不能呼叫任意 Kernel function，那會讓 Verifier 無從驗證安全性。所以 Kernel 提供了一組「已驗證安全的函式」讓 BPF 程式呼叫。這套機制歷史上分兩代：

3.8.1 Helper Functions（傳統）

  • 每個 helper 有固定 ID（如 BPF_FUNC_map_lookup_elem = 1），call 指令直接帶 ID。
  • 每個 program type 有白名單，限制能呼叫哪些 helper（如 XDP 不能呼叫 bpf_get_current_pid_tgid）。
  • 截至 2026 年共有約 200 多個 helper，依用途分類：Map / Probe / Time / Process / Print / Network / Socket / Dynptr...

3.8.2 KFuncs（新一代，5.18+）

  • 不再用固定 ID，而是用 BTF 函式名呼叫。
  • Kernel 開發者標記 __bpf_kfunc，自動公開給 BPF 使用。
  • 可以接受複雜參數型別（pointer、struct、reference-counted 物件）。
  • 已涵蓋 cgroup stat、cpumask、crypto、connection tracking、HID、sched_ext 等大量領域。
Helper vs KFunc 該用哪個？

實作層面：你寫 BPF 程式時通常用 libbpf / aya 提供的 wrapper，不用煩惱底層是 helper 還是 kfunc。但要注意：kfunc 通常需要更新的 Kernel。如果目標環境 Kernel 較老（<5.18），優先使用 helper。完整速查表會在附錄 A、B提供。

3.9 Hooks 與 Attach 機制

BPF 程式必須掛載到某個 Kernel 事件點才會被觸發。掛載過程：

  1. 程式經 BPF_PROG_LOAD 載入，得到 prog_fd。
  2. 用 BPF_LINK_CREATE（或對應 helper API）把 prog 綁到某個 hook，取得 link_fd。
  3. 事件發生時，Kernel 透過 hook 框架呼叫 BPF 程式。
  4. 關閉 link_fd 即解除 attach。

3.10.1 開發者視角的關鍵理解

對開發者而言，這張圖讓你理解三件事：

  1. Verifier 是你最常打交道的對象：不是 Kernel 在排斥你，而是它在保護所有人。學會讀 Verifier log 是 BPF 開發第一技能。
  2. CO-RE 不是免費的：要享受跨 Kernel 移植性，BPF 端必須用 vmlinux.h + 適當的 macro，user space 端必須用支援 CO-RE 的 loader。直接寫 raw offset 等於放棄移植性。
  3. Maps 是溝通的全部：BPF 程式輸出資料、user space 讀取資料、BPF 程式間共享狀態，全靠 Map。設計 BPF 工具時，先想 Map schema 再寫 BPF code 通常更省事。

3.11 本章小結與下一步

3.11.1 本章重點回顧

  1. eBPF VM：11 個 64-bit 暫存器、512 bytes stack、固定指令格式、context 由 program type 決定。
  2. bpf() syscall：單一 syscall 多路複用，分七大類 cmd（建立、Map、Program、Link、發現、Pin、安全）。
  3. Verifier：CFG 檢查 → 模擬執行 → helper 約束驗證。失敗訊息透過 verifier log 解讀。
  4. JIT：通過驗證後，BPF bytecode 翻譯為原生機器碼，效能接近 Kernel C 程式。
  5. BTF：Kernel 自描述 type 的緊湊格式，分 18 個 kind，是 CO-RE / BPF LSM / fentry / kfunc 的基礎。
  6. CO-RE：clang 標記欄位存取 → loader 對照 Kernel BTF → 改寫 instruction 中的 offset，達成跨 Kernel 移植。
  7. Maps：BPF 程式對外溝通的唯一管道，24 種類型對應不同存取模式。
  8. Helper / KFunc：Kernel 預先驗證安全的函式集合，BPF 程式可呼叫。
  9. Hooks：kprobe / tracepoint / XDP / cgroup / LSM 等十多種事件源。
