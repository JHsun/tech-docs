1.1 什麼是 eBPF

eBPF（extended Berkeley Packet Filter）是一種在 Linux Kernel 中執行沙箱化（sandboxed）程式的技術。它讓開發者可以在不修改 Kernel 原始碼、不載入 Kernel Module、不重啟系統的前提下，動態地擴充 Kernel 的行為。

用一句話總結 eBPF：

「讓使用者可以在 Kernel 裡安全地執行自己寫的程式碼，並且即時回應系統內各種事件——封包到達、syscall 進入、函式被呼叫、cgroup 變化⋯⋯。」

這個能力在過去十幾年是不可想像的。傳統上，要在 Kernel 中插入自訂邏輯只有兩條路：

  1. 修改 Kernel 原始碼：得提交 patch、被 kernel maintainer review、等版本釋出，週期常以年計。
  2. 撰寫 Kernel Module（LKM）：能立即生效，但寫錯一行就讓整台機器 panic；安全性、相容性、維運成本都極高。

eBPF 提供第三條路：把程式寫在 user space、編譯成 BPF bytecode、丟進 Kernel 內建的驗證器（verifier）檢查、通過後由 JIT 編譯為原生指令執行。整個流程毫秒等級、零重啟、效能接近原生 Kernel 程式碼。

關鍵術語：Hook（掛載點）

eBPF 程式不會自己亂跑，它必須被掛載到某個 Kernel 事件點才會被呼叫。例如：當網卡收到封包時、當某個 syscall 被呼叫時、當某個 kernel function 被執行時。整本手冊接下來會大量出現「Program Type」「Attach Type」「Hook Point」這些詞，它們指的都是「這支 eBPF 程式要在哪裡被觸發」。

1.2 從 cBPF 到 eBPF：歷史脈絡

要理解 eBPF 的設計取捨，先回頭看它的祖先 cBPF（classic BPF）。

1.2.1 cBPF（1992 – 2014）

BPF 最早由 Steven McCanne 與 Van Jacobson 在 1992 年於 Berkeley 提出，目的非常單純：在 Kernel 中高效率地過濾網路封包，避免每個封包都複製到 user space 才能丟掉。經典應用就是 tcpdump—— 你在命令列下的那串 tcp port 80 and host 1.2.3.4，會被編譯為 cBPF bytecode，由 Kernel 在收到封包當下就決定是否要遞送給 user space。

cBPF 的限制非常多：

  • 只有 2 個 32-bit 暫存器（A、X）。
  • 指令集極小，只能做簡單的算術與比較。
  • 沒有迴圈、沒有函式呼叫、沒有持久化儲存。
  • 幾乎只能用於封包過濾這一個情境。

1.2.2 eBPF 誕生（2014 起）

2014 年，Alexei Starovoitov 把 BPF 大幅擴充，提出了我們今天稱為 eBPF 的版本，並合併進 Linux Kernel 3.18。關鍵變革包括：

名詞釐清：BPF 還是 eBPF

在現代 Linux Kernel 原始碼裡，幾乎所有寫成 BPF_* 的常數、函式、syscall 都指 eBPF。cBPF 已經被當作 eBPF 的子集處理（Kernel 內部會把 cBPF 程式轉譯成 eBPF 執行）。本手冊與多數現代資料中，「BPF」與「eBPF」常被混用，除非特別強調歷史脈絡，否則指的都是 eBPF。

1.3 eBPF 的核心設計哲學

理解 eBPF 為何「能做到那麼多事卻又安全」，要先理解它的四個設計支柱。

1.3.1 安全（Safety）：Verifier 把關

eBPF 程式在進入 Kernel 之前，會由 Verifier（驗證器）進行靜態分析。Verifier 會檢查：

  • 程式不會無窮迴圈（執行步數有上限）。
  • 所有記憶體存取都在合法範圍內（無越界、無未初始化讀取）。
  • 所有指標在使用前都經過 NULL 檢查。
  • 不可呼叫未經許可的 helper function。
  • 程式回傳值符合該 program type 的合約。

沒通過 Verifier 的程式根本進不了 Kernel，這也是 eBPF 與傳統 Kernel Module 最關鍵的差異——你寫錯了，Verifier 拒絕載入，但你的機器不會炸。

1.3.2 效能（Performance）：JIT 編譯

BPF bytecode 通過 Verifier 後，會由 JIT（Just-In-Time）編譯器翻譯成目標 CPU 的原生機器碼（x86-64、aarch64、riscv64...）。執行時直接是原生指令，不是解譯字節碼，效能與 Kernel 內部 C 程式碼幾乎沒有差距。

1.3.3 動態性（Dynamism）：無需重啟

eBPF 程式可以隨時載入、卸載、更新。一個運行中的觀測工具，可以根據需求即時把新的 trace 程式塞進 Kernel；一個正在處理流量的網路節點，可以在不中斷服務的情況下熱換新版的封包處理邏輯。這個特性讓 eBPF 在雲原生（cloud-native）環境裡顯得格外吸引人。

1.3.4 可移植性（Portability）：CO-RE

不同 Kernel 版本之間，內部資料結構（如 struct task_struct）的欄位可能會增減或位移。傳統 Kernel Module 必須對特定 Kernel 版本編譯。eBPF 透過 BTF（BPF Type Format）與 CO-RE（Compile Once – Run Everywhere）機制，讓同一份編譯好的 eBPF 程式可以在不同 Kernel 版本上正確執行。

這四個支柱互相支撐：因為有 Verifier 把關，Kernel 才敢讓不受信任的程式進來；因為有 JIT，這些程式才有實用效能；因為動態載入，eBPF 才能成為平台級工具的基礎；因為 CO-RE，eBPF 工具才能寫一次到處跑。

Safety

Verifier 靜態分析每一個 instruction，拒絕任何可能損害 Kernel 的程式。

Performance

JIT 編譯到原生 CPU 指令，效能接近 Kernel 原生程式碼。

Dynamism

程式可在系統運行中載入、卸載、更新，零停機。

Portability

BTF + CO-RE 讓同一支程式跨 Kernel 版本與發行版執行。

eBPF 的應用範圍極廣，但業界普遍把主要領域歸納為三類，每一類都有對應的成熟產品與工具。

1.4.1 網路（Networking）

這是 eBPF 的「老本行」。在 Kernel 網路堆疊（network stack）的關鍵節點放上 eBPF hook，就能：

  • 封包過濾與 DDoS 緩解：在 XDP（eXpress Data Path）層攔截惡意封包，每秒可達數千萬 pps。
  • 負載平衡：取代 kube-proxy 中的 iptables，實現 hash table-based 的高效率服務轉發。
  • 網路策略執行：以 Pod identity（不是 IP）為基礎執行 L3/L4/L7 policy。
  • Service Mesh 加速：在 socket 層攔截流量，節省 sidecar proxy 的 CPU 與延遲開銷。

代表產品：Cilium（CNCF Graduated）、Katran（Meta 的 L4 負載平衡器）、XDP-based DDoS 防護（Cloudflare）。

1.4.2 可觀測性（Observability）

eBPF 可以在幾乎任何 Kernel 函式、syscall、tracepoint 上掛載 probe，蒐集執行時資訊：

  • 系統呼叫追蹤：誰在打開哪個檔案、哪個 process 在發送網路請求。
  • 效能剖析（profiling）：CPU on-/off-CPU 時間、stack trace、火焰圖（flame graph）。
  • 應用層觀測：透過 USDT 或 uprobes 觀測 user space 應用內部行為。
  • 持續剖析（continuous profiling）：低開銷、長時間蒐集生產環境的效能資料。

代表產品：bcc、bpftrace、Pixie、Parca、Pyroscope、Datadog 與 Dynatrace 的 eBPF agent。

1.4.3 安全（Security）

eBPF 可以在事件發生的當下就進行偵測甚至阻擋，比 user space 的 audit log 解析快得多：

  • Runtime threat detection：偵測異常 process 行為、權限提升、可疑系統呼叫序列。
  • LSM-based policy：透過 BPF LSM hook 實作可程式化的存取控制。
  • Syscall filtering：seccomp-bpf 用 eBPF 限制容器可呼叫的 syscall。
  • Network identity-based policy：以工作負載身份（不是 IP）為單位的 zero-trust 網路。

代表產品：Falco（CNCF Graduated）、Tetragon（Cilium 旗下，CNCF Incubating）、Tracee。

三大領域的共通結構

仔細觀察會發現，三大領域其實都在做同一件事：「在 Kernel 中放一支程式，當某個事件發生時，把它記錄下來、修改它、或拒絕它。」差別只在掛在哪個 hook、要看什麼欄位、輸出到哪裡。理解這個共通模式後，後續所有章節都會變得容易消化。

1.5.1 Layer 1：Kernel eBPF 子系統

整個生態的根基。所有上層工具最終都是透過 bpf() syscall 與 Kernel eBPF 子系統互動。本手冊「冊四」會深入這層。

1.5.2 Layer 2：工具鏈

  • clang / LLVM：把 C 編譯成 BPF bytecode 的標準編譯器。
  • bpftool：Kernel 內建的 eBPF 命令列管理工具，列出 program、map、查看 Verifier log。
  • pahole：產生 BTF 資訊的工具。

1.5.3 Layer 3：Userspace Loader 函式庫

負責「把編譯好的 eBPF 物件檔載入 Kernel、設定 Map、attach 到 hook」。本手冊主要使用：

  • cilium/ebpf：純 Go 函式庫，Cloudflare 與 Cilium 共同維護，無需 cgo、無需 libbpf，是 Go 生態的標準選擇。
  • aya：純 Rust 函式庫，aya-rs 維護，整個 user space 與 BPF kernel space 都可以用 Rust 寫。

1.5.4 Layer 4：開發框架

  • bcc（BPF Compiler Collection）：iovisor 開發，Python 與 C++ 綁定，含大量現成工具（execsnoop、biolatency、tcpconnect 等）。
  • bpftrace：高階 eBPF 腳本語言，類似 awk for Kernel，一行命令就能 trace。
  • libbpf-bootstrap：libbpf + CO-RE 的 C 範本專案。

1.7 為什麼是 2026 年該學 eBPF 的時候

截至 2026 年，eBPF 已經從「實驗性技術」徹底轉為「業界標準」。幾個關鍵指標：

  • 大規模生產採用：Cilium 已是 CNCF Graduated 專案，v1.19 於 2026 年 4 月 15 日發布。Google、Meta、Netflix、Cloudflare、Datadog 都在生產環境大規模部署 eBPF。
  • Kernel 功能持續擴張：BPF Arena（Kernel heap 配置）、BPF Token（受限權限載入）、擴充的 USDT 支援、sched_ext（可程式化 scheduler）等新特性持續被合併進主線。
  • 跨平台延伸：eBPF for Windows 已可用，eBPF 不再侷限於 Linux。
  • OpenTelemetry 整合：OpenTelemetry 社群正在把 eBPF 作為 collector 的官方資料蒐集機制。
  • 標準化推進：eBPF Foundation（Linux Foundation 旗下）持續推動 ISA、BTF、CO-RE 等標準化工作。

對開發者而言，這意味著現在學 eBPF 不會學到一個還在動盪的技術；對 SRE 而言，這意味著你部署的 eBPF 工具會持續被維護、被擴充。

1.8 本章小結與下一步

1.8.1 本章重點回顧

  1. eBPF是讓使用者程式安全地在 Linux Kernel 中執行的技術。
  2. 它由四大支柱支撐：Safety（Verifier）、Performance（JIT）、Dynamism（動態載入）、Portability（BTF + CO-RE）。
  3. 主要應用三大領域：網路、可觀測性、安全。
  4. 生態系分五層：Kernel 子系統 → 工具鏈 → Loader → Framework → End-user Products。
  5. 本手冊以 Go（cilium/ebpf）與 Rust（aya）為範例語言，後續所有章節都會看到這兩種語言並列呈現。

第 2 章將進入動手環節：環境搭建、必要工具安裝、第一支 Hello World eBPF 程式。在那之前，建議你先確認手邊有以下其中之一：

  • 一台 Linux 機器（Ubuntu 22.04+ / Debian 12+ / Fedora 38+，Kernel 5.15 或更新）
  • 一個 Linux VM（VirtualBox、UTM、Multipass 都可以）
  • 一個雲端 Linux 主機（AWS EC2、GCP Compute Engine 等）
macOS / Windows 使用者注意

eBPF 主要是 Linux Kernel 技術，無法直接在 macOS 或 Windows 上原生執行。你需要透過 VM、Multipass、Docker（搭配 Linux Kernel headers）或雲端機器來練習。Windows 上有 eBPF for Windows 但功能子集較小，本手冊主要以 Linux 為實作平台。
