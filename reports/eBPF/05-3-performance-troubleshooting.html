22.1 BPF 效能的四大層次

效能問題很少只有單一原因。要系統化提升 BPF 程式效能，從下到上看四個層次：

map sizing / ring buffer / pinning"] L2["第 2 層：Map 設計

22.1.1 影響量級的概略觀念

層次典型影響量級調校門檻
Program 層演算法2-10×（換 O(n) → O(1)）需要重寫
Map 類型對換2-5×（perf → ringbuf）中等
Cache locality1.2-2×低
JIT 後機器碼1.1-1.5×觀察為主，難主動優化
Kernel 參數避免硬限制（不是 speedup，是不會 fail）低

結論：先看程式邏輯與 map 選型，再看 cache，最後才是 kernel 參數。

22.2 Verifier 友善：寫得讓 verifier 開心

verifier 不只決定「能不能跑」，也影響 instruction 數量（dead code 消除、bounded loop 展開）。寫得 verifier-friendly 的程式 instruction 數可能少 30-50%。

22.2.1 verifier 三個硬限制

限制數值（5.2+）5.2 之前
單支 program instruction 上限1,000,0004,096
complexity（驗證路徑展開）上限1,000,000131,072
單一 program 的 stack size512 bytes同
tail call 深度33同

22.2.2 verifier-friendly 五原則

原則實作
① 用 __always_inline 把小函式 inline避免 BPF-to-BPF call 帶來額外 verifier 路徑
② 早期 return（early bail-out）命中常見 fast path 立刻 return，verifier 也少展開
③ 減少 pointer 共線同一 pointer 經多條分支變成不同 type，verifier 要展開大量狀態
④ bpf_assert 縮小範圍給 verifier 明確 hint：「這個值在 X..Y 之間」
⑤ 用 bpf_for / bpf_repeat5.17+ 的 bounded loop helper，比手寫 unrolled loop 更省 instruction

22.2.3 範例：early return 的威力

所有條件都展開
SEC("xdp")
int xdp_filter(struct xdp_md *ctx) {
    int verdict = XDP_PASS;
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    /* 即使是 IPv6 也走完所有 IPv4 解析路徑 */
    if (data + sizeof(struct ethhdr) <= data_end) {
        struct ethhdr *eth = data;
        if (eth->h_proto == bpf_htons(ETH_P_IP)) {
            /* 100 行 IPv4 處理 */
        }
        if (eth->h_proto == bpf_htons(ETH_P_IPV6)) {
            /* 100 行 IPv6 處理 */
        }
        /* ... 更多協定 */
    }
    return verdict;
}
命中即 return
SEC("xdp")
int xdp_filter(struct xdp_md *ctx) {
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;

    if (data + sizeof(struct ethhdr) > data_end)
        return XDP_PASS;        /* early bail-out */

    struct ethhdr *eth = data;
    __be16 proto = eth->h_proto;

    if (proto == bpf_htons(ETH_P_IP))
        return handle_ipv4(ctx, eth);
    if (proto == bpf_htons(ETH_P_IPV6))
        return handle_ipv6(ctx, eth);

    return XDP_PASS;            /* 其他協定一律放行 */
}

第二種寫法：(a) verifier 對每條 path 獨立分析，complexity 大降；(b) JIT 後執行也少跳轉。

22.3 Map 類型選擇與 sizing

22.3.1 常見場景的最佳 map 類型

場景建議 map type為何
Lookup blacklist / configHASH 或 LPM_TRIE（CIDR）O(1) 查詢
Counter（per-key 計數）PERCPU_HASH + user space aggregate無 lock contention
Connection tracking（會 evict）LRU_HASH容量上限 + LRU evict
固定大小事件 → user spaceRINGBUF（5.8+）多 producer / 1 consumer 高效
Variable-size 事件RINGBUF 配 dynamic 寫同上
Stack trace（profiler）STACK_TRACE + HASH count專為 stack 設計
Tail call 跳轉表PROG_ARRAY唯一支援的方式
巨大 array（millions of entries）ARRAY 或 BLOOM_FILTER（5.16+）O(1)，bloom 適合 set membership
每 CPU 暫存（流水線中介）PERCPU_ARRAY max_entries=1無 lock、無同步
CIDR 比對LPM_TRIElongest prefix match

22.3.2 Sizing 三原則

  • HASH / LRU_HASH：max_entries 設成預期峰值的 1.3-1.5 倍，避免 hash collision degraded。
  • RINGBUF：必須是 2 的次方，建議 16 KB - 16 MB，看 producer 速率與 consumer latency。
  • PERCPU_*：每 CPU 一份，注意 NUMA 大機台。128 核機台 PERCPU_ARRAY size=8KB 等於用掉 1MB lock memory。

22.4 Ring buffer vs perf array：高頻事件設計

面向RINGBUF（5.8+）PERF_EVENT_ARRAY（傳統）
Producer 模型多 CPU 共享一個 buffer每 CPU 一個 buffer
Consumer 模型單 reader（user space）每 CPU 一個 reader
事件順序跨 CPU 全域順序僅 per-CPU 順序
APIbpf_ringbuf_reserve + bpf_ringbuf_submitbpf_perf_event_output

22.4.1 RINGBUF 高效寫入模式：reserve + submit

標準 ringbuf 寫入
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);  /* 256 KB */
} events SEC(".maps");

struct event {
    __u32 pid;
    char comm[16];
    __u64 ts;
};

SEC("tp_btf/sched_process_exec")
int handle_exec(u64 *ctx) {
    /* reserve 一個 entry，避免一次 copy */
    struct event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e) return 0;

    e->pid = bpf_get_current_pid_tgid() >> 32;
    e->ts = bpf_ktime_get_ns();
    bpf_get_current_comm(e->comm, sizeof(e->comm));

    /* submit 後 user space 立即可見（zero-copy） */
    bpf_ringbuf_submit(e, 0);
    return 0;
}

vs bpf_perf_event_output，RINGBUF 的核心優勢：

  1. Zero-copy：BPF 直接寫到 user space 可見的記憶體（mmap）。
  2. 無記憶體膨脹：傳統 perf array 每 CPU 一份，96 核機 96 份。
  3. 跨 CPU 全域順序：debug 易得多。

22.5.1 經典 PERCPU 範例：取代 stack 大 buffer

BPF stack 只有 512 bytes。要做大封包解析、L7 解析常需要更大 scratch buffer：

用 PERCPU_ARRAY 當大暫存
struct scratch {
    char buf[4096];
    __u32 len;
    __u32 state;
};

struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __type(key, __u32);
    __type(value, struct scratch);
    __uint(max_entries, 1);     /* 只要 1 個 entry！ */
} scratch_map SEC(".maps");

SEC("xdp")
int xdp_parse(struct xdp_md *ctx) {
    __u32 zero = 0;
    struct scratch *s = bpf_map_lookup_elem(&scratch_map, &zero);
    if (!s) return XDP_PASS;     /* 不可能，但 verifier 要求檢查 */

    /* 用 s->buf 做大型解析（4 KB > BPF stack 512） */
    /* ... */
    return XDP_PASS;
}

22.6 Tail call、bounded loop 與 BPF-to-BPF call

BPF 程式長度受 1M instruction 限制。寫複雜邏輯有三種拆解方式：

機制支援版本verifier 友善性能適用
Tail call4.2強（每支獨立驗證）每跳一次有 indirect call 開銷邏輯複雜、要 dispatch
BPF-to-BPF call4.16中等（call 進去要展開）direct call，快共用工具函式
Bounded loop5.3看 unroll 量最快（直線）固定迴圈次數
bpf_loop helper5.17強（不展開）有 helper call 開銷但少 instruction大次數迴圈

22.6.1 Tail call 33 層深度限制

避免遞迴爆炸，BPF 限制 tail call 鏈最多 33 層。實務上 5-10 層已經足夠處理多協定 dispatch（例：XDP → IPv4 / IPv6 → TCP / UDP / ICMP → 應用）。

22.6.2 範例：bpf_loop 取代手寫 unrolled loop

unrolled loop（instruction 多）
#pragma unroll
for (int i = 0; i < 64; i++) {
    if (do_work(i, ...) == STOP) break;
}
/* 64 次展開 = ~64×N instructions */
bpf_loop（少 instruction）
static long callback(__u32 i, void *ctx) {
    if (do_work(i, ctx) == STOP)
        return 1;       /* break */
    return 0;
}

bpf_loop(64, callback, ctx, 0);
/* 1 次 helper call + 1 個 callback program = ~N instructions */

22.7 Cache locality 與 struct 排版

BPF 在 hot path 跑（每封包、每事件），每次 cache miss 都是延遲。三個關鍵點：

22.7.1 Map value struct 對齊

大部分 BPF map value 對齊到 8 bytes 即可。但若是 PERCPU 且常被 cross-CPU 讀（罕見），對齊到 64 bytes（cacheline）可避免 false sharing：

cache-aligned struct
struct counters {
    __u64 packets;
    __u64 bytes;
} __attribute__((aligned(64)));   /* 對齊到 cacheline */

struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __type(key, __u32);
    __type(value, struct counters);
    __uint(max_entries, 1024);
} stats SEC(".maps");

22.7.2 把熱欄位放前面

若一個 struct 大、但常用的只有 head 幾個欄位，把熱欄位排在 struct 開頭，每次只讀一個 cacheline。對 connection table 這類常存取的結構意義特別大。

22.7.3 避免 unaligned access

verifier 預設要求對齊存取（除非加 BPF_F_ANY_ALIGNMENT flag）。對齊存取在多數架構上更快，是雙贏。

22.8.2 retpoline 對 indirect call 的影響

Spectre v2 緩解：tail call 與 helper call 用 indirect jump（call *%rax）受影響。retpoline 把 indirect jump 改成保守的 lfence + ret，每次 ~10 cycles 額外開銷。

新 Kernel（5.17+）配新 CPU（Intel eIBRS、AMD branch type retire）可關 retpoline，BPF tail call 與 helper call 可恢復原速：

$ cat /sys/devices/system/cpu/vulnerabilities/spectre_v2
Mitigation: Enhanced IBRS, IBPB: conditional, RSB filling
# 看到 Enhanced IBRS = 不需 retpoline，indirect call 不慢

22.8.3 nocopy 與 inline 的合作

為什麼 helper call 也常被 JIT inline？因為 verifier 把已知 helper（lookup_elem 等）標記為「可內聯」，JIT 會直接展開。但 BPF-to-BPF call 不會，所以 inline 寫法在 instruction 層級更便宜。

22.10 建立效能 baseline 與長期趨勢

「為什麼今天比上週慢 10%」這類問題只能靠 baseline 回答。建議流程：

  1. 每次 release，跑固定 benchmark suite（用 PROG_TEST_RUN + Repeat）。
  2. 記錄每個 program 的 p50 / p99 nanoseconds per invocation。
  3. 記錄 ringbuf drops、verifier 失敗次數、memlock 使用率。
  4. 所有指標進 Prometheus，繪 Grafana dashboard。
  5. 新版本 deploy 後對比 24 hours，p99 退化超過 20% 自動 alert。
CI 流程整合

把 benchmark 跑進 GitHub Actions / GitLab CI：每 PR 跑一次，diff 顯示在 PR comment。Cilium、cilium/ebpf 自己的 CI 都這樣做，避免合併後才發現迴歸。

22.11 第 22 章小結

  1. BPF 效能調校四層：程式邏輯 → map 設計 → resource 配置 → kernel 參數。先看上層演算法。
  2. verifier-friendly 五原則：inline、early return、減少 pointer 共線、bpf_assert hint、bpf_loop helper。
  3. Map 選型對照表記下來：HASH / LRU_HASH / RINGBUF / PERCPU / PROG_ARRAY / LPM_TRIE 各有所長。
  4. RINGBUF（5.8+）是新工具預設，比 PERF_EVENT_ARRAY 省記憶體 + 跨 CPU 順序。
  5. PERCPU_ARRAY max_entries=1 是取代 BPF stack 大 buffer 的標準慣例。
  6. Tail call vs BPF-to-BPF call vs bpf_loop：複雜邏輯首選 tail call，共用工具函式 BPF-to-BPF，迴圈用 bpf_loop。
  7. Cache locality 三點：struct 對齊、熱欄位前置、避免 unaligned。
  8. JIT 觀察用 bpftool prog dump jited；retpoline 在新 CPU + 新 Kernel 已不是負擔。
  9. Kernel sysctl：bpf_stats_enabled / bpf_jit_kallsyms / unprivileged_bpf_disabled 是 production 標配。
  10. 建立 baseline 並讓 CI 跑 benchmark，是長期防止效能迴歸的唯一方式。

23.2.2 「invalid argument」載入失敗

23.3 Verifier 拒絕：常見訊息翻譯

verifier log 是 BPF 開發最常踩的痛點。下表是八個經典訊息與翻譯：

verifier 訊息意思解法
R1 type=ctx expected=fp用了 ctx 當記憶體位址直接寫不能直接寫 ctx；需經 helper
invalid mem access 'inv'對 PTR_TO_PACKET 之類存取超出已知範圍加上 if (data + N <= data_end) bounds check
R2 unbounded memory accessVariable-length read 沒有上界加 if (n < MAX) ... 限制
back-edge from insn N to M有非 bounded loop（5.3 之前完全禁止迴圈）用 bounded loop / bpf_loop / 改 unrolled
BPF program is too large. Processed N insn超過 1M instruction 上限拆 tail call / inline 撤掉
complexity limit exceededverifier 路徑展開超過 1M states同上 + 簡化條件
cannot return stack pointer to the callerBPF function 回傳 stack 上的 pointer改回傳 map value 指標或 by-value
R0 invalid mem access 'scalar'map_lookup 後沒檢查 NULL 就用必須 if (!ptr) return ...;

23.3.1 看 verifier log 的訣竅

設高 LogLevel 後，log 會顯示「verifier 模擬執行的每一步」。錯誤訊息附近的幾行之前就是 verifier 認為的真實狀態，常常是定位問題的關鍵：

; if (data + sizeof(*eth) > data_end)
0: (61) r2 = *(u32 *)(r1 +0)        ; r2 = data
1: (61) r3 = *(u32 *)(r1 +4)        ; r3 = data_end
2: (07) r2 += 14                    ; r2 = data + 14
3: (2d) if r2 > r3 goto pc+8        ; bounds check OK
; eth->h_proto
4: (71) r4 = *(u8 *)(r2 -2)         ; load h_proto byte 0
5: ...
; 假設第 14 行 verifier 拒絕
14: R2 type=invalid expected=...   ← 重點看 14 行前的 r2 是怎麼變成 invalid

23.4 CO-RE relocation 失敗

CO-RE 在載入時對照 Kernel BTF 修正 offset。失敗訊息常見：

訊息意思解法
relo failed: type 'foo' does not exist目標 Kernel 沒有此 type（被 rename / 刪除）用 bpf_core_type_exists 條件包起來
field 'bar' not found in 'struct foo'欄位被 rename / 移除用 flavors（foo___pre_X / foo___post_X）
multiple matches for type 'foo'同名 type 在 vmlinux + module 都存在用更明確的 type name（含 module prefix）
enum value 'BAR' not foundenum 值不存在bpf_core_enum_value_exists
relocation kind 'X' not supportedlibbpf 版本太舊升級 libbpf / cilium-ebpf

23.5 Attach 失敗

訊息場景解法
device or resource busy (EBUSY)該 hook 已有 BPF 程式（XDP, cgroup）先 detach 舊的，或用 link priority（tcx / netkit）
operation not permitted (EPERM)權限不足檢查 cap / SCC / BPF Token

23.6 Map 操作失敗

錯誤原因解法
cannot allocate memory (ENOMEM)memlock 不足；map 太大5.10-：增 RLIMIT_MEMLOCK；5.11+：減 max_entries
map_lookup_elem returned NULL 但 key 該存在BPF 端與 user space 端 byte order 不一致用 network byte order 統一（htonl）
BPF_EXIST update failed (ENOENT)用 BPF_EXIST flag 但 key 不存在第一次用 BPF_NOEXIST 或 BPF_ANY
HASH map 看似漏資料達到 max_entries，新插入失敗用 LRU_HASH 自動 evict 或加大
PERCPU map user space 讀只看到一個 CPU 的值API 用法錯用 PERCPU 專屬 read API（cilium/ebpf map.Lookup 自動處理）

23.7 Runtime 行為錯誤（程式跑了但不對）

verifier 通過、attach 成功，但行為不符預期。最棘手。常見原因：

症狀常見原因
kprobe / fentry 完全不觸發(a) 函式被 inline；(b) symbol name 對不上（kfunc rename）；(c) 某 fastpath 不經過該函式
Counter 數值跳動奇怪(a) 跨 CPU race（沒用 PERCPU 或 atomic）；(b) overflow 被截斷
偶發性 event 不上送(a) ringbuf drop（buffer 太小）；(b) BPF 用了 sampling 但忘了關掉
讀字串只有 1 個字元用了 bpf_probe_read_kernel 而不是 _str 變體；string 不是 NUL-terminated
BPF 程式跑了但 user space 沒看到資料BPF 在 wrong cgroup / wrong namespace 觸發；selectors 過濾掉了

23.7.1 確認 BPF 真有跑：run_count 偵察

$ sudo bpftool prog show id 12
12: kprobe  name myprog  ...
        run_time_ns 12345678  run_cnt 9876

run_cnt 是 0 = 從未被觸發。多數「行為錯」其實是「沒被觸發」。

23.8 效能突降排查

「上週還好，這週慢 30%」。系統化排查：

  1. 看 BPF run_time_ns avg：是 BPF 變慢還是別處變慢？
  2. 看 perf top：哪個函式最熱？是 BPF 程式 still、helper、還是 user space？
  3. 看 ringbuf drop rate：drop 上升 = consumer 慢或 producer 暴增。
  4. 看 map 大小 / hash collision：HASH map 達到飽和會降速。
  5. 看 kernel 版本：升級後 verifier 可能展開不同 instructions。

23.8.1 一個典型 case

案例：HASH map 飽和導致 latency 雙倍

某 BPF connection tracking 工具：max_entries 設 10K。叢集擴張後同時連線數常 8K-12K，達到 max_entries 後新插入失敗，BPF 程式進入 fallback 路徑，慢 2-3 倍。
解法：改用 LRU_HASH，或把 max_entries 加到峰值的 1.5 倍。
偵察線索：run_time_ns avg 從 100ns 跳到 250ns，但 run_cnt 沒變。

23.9 系統異常：OOM / CPU / kernel taint

23.9.1 BPF 引發 OOM

BPF map 是 kernel memory，不會 swap。設太大可能觸發 OOM killer 殺死 user space process。排查：

# 看 BPF 占用了多少
$ sudo bpftool map list | awk '/memlock/ {sum+=$NF} END {print sum/1024/1024" MB"}'

# 個別 map 占用
$ sudo bpftool map list -j | jq '[.[]|{name, memlock: .memlock_bytes}] | sort_by(-.memlock) | .[0:5]'

23.9.2 BPF 引發 CPU 高

BPF program 在 hot path 變成 hot 函式：

# 開啟 stats
$ sudo sysctl -w kernel.bpf_stats_enabled=1

# 30 秒後看
$ sudo bpftool prog show -j | jq '[.[]|{name, run_time_ns, run_cnt, avg_ns: (.run_time_ns / .run_cnt)}] | sort_by(-.run_time_ns) | .[0:10]'

# 用 perf 看 BPF 占多少 CPU
$ sudo perf top --no-children
# BPF 程式名會出現（前提：bpf_jit_kallsyms=1）

23.9.3 Kernel taint：kernel 層級的紅旗

$ cat /proc/sys/kernel/tainted
4096    # 不為 0 表示 kernel 進入「不純淨」狀態

# 解讀
$ awk '{ for (i=0; i<28; i++) if (and($0, lshift(1, i))) print i }' /proc/sys/kernel/tainted

BPF JIT spray 被 spectre 防護擋下會增加 taint bit。注意這代表已有潛在攻擊嘗試，是安全 alert。

23.10 bpftrace：5 分鐘 debug 利器

對於「臨時想看 kernel 在做什麼」，bpftrace 是 awk 級的快速腳本：

常用 one-liner
# 統計每秒 syscall 數
$ sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:1 { print(@); clear(@); }'

# 看哪些 process open 了 /etc/passwd
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { if (str(args->filename) == "/etc/passwd") { printf("%s\n", comm); } }'

# tcp 連線目的地分布
$ sudo bpftrace -e 'kprobe:tcp_v4_connect { @[ntop(((struct sock *)arg0)->__sk_common.skc_daddr)] = count(); }'

# fsync 延遲 histogram
$ sudo bpftrace -e 'kprobe:vfs_fsync { @start[tid] = nsecs; } kretprobe:vfs_fsync /@start[tid]/ { @us = hist((nsecs - @start[tid]) / 1000); delete(@start[tid]); }'
腳本檔（trace-execve.bt）
#!/usr/bin/env bpftrace

BEGIN {
    printf("Tracing execve... Ctrl-C to end\n");
    printf("%-8s %-16s %s\n", "PID", "COMM", "ARGS");
}

tracepoint:syscalls:sys_enter_execve {
    printf("%-8d %-16s %s\n", pid, comm, str(args->filename));
}

END {
    printf("Done.\n");
}

# 執行
$ sudo bpftrace ./trace-execve.bt
產生 histogram + heatmap

'

23.11 第 23 章小結

  1. 故障排查心智模型：BPF 七階段每個階段都可能出問題，先定位哪個階段。
  2. 排查前置 5 行：bpftool prog/map/link list + bpftool cgroup tree + dmesg | grep -i bpf。
  3. Verifier 訊息 8 種經典翻譯背下來，多半都遇得到。
  4. CO-RE relocation 失敗 5 種典型，配 llvm-objdump --section=.BTF.ext 與 bpftool btf dump 排查。
  5. Attach 失敗看 EBUSY / EPERM / ENOENT / EINVAL 錯誤碼分流；XDP 不支援 native 時 fallback 到 GENERIC。
  6. Map 失敗常見：memlock、byte order、flag 用錯、HASH 飽和、PERCPU 讀法錯。
  7. 「Verifier 通過但行為不對」最常見實際是 沒被觸發——先看 run_cnt。
  8. 效能突降系統化看：BPF run_time → perf top → ringbuf drop → map 飽和 → kernel 升版。
  9. BPF 引發 OOM 看 bpftool map list 的 memlock；引發高 CPU 用 bpf_stats_enabled + perf。
  10. bpftrace 是 incident 期間最快的 debug 工具，long-running daemon 仍用 cilium/ebpf。
