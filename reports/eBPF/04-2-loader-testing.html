16.1 Loader 的工作流程鳥瞰

BPF Loader 的工作可以拆成七階段。不論是 cilium/ebpf、aya 還是 libbpf，本質上都做同樣的事，只是抽象封裝不同。

flowchart TB ELF["1. 讀取 BPF ELF
(.o 檔案 / 嵌入 binary)"] PARSE["2. 解析 sections
.text / .maps / .BTF / .rodata / ..."] SPEC["3. 建立 Spec
CollectionSpec / ObjectSpec"] BTF["4. BTF 處理
解析 + 載入"] CORE["5. CO-RE relocation
對照 Kernel BTF
patch instructions"] CREATE["6. Kernel object 建立
BPF_MAP_CREATE × N
BPF_PROG_LOAD × N"] ATTACH["7. Attach 到 hook
BPF_LINK_CREATE"] ELF --> PARSE --> SPEC --> BTF --> CORE --> CREATE --> ATTACH

16.1.1 各階段的關鍵動作

階段動作
① 讀 ELF從磁碟或 embed 取得 .o bytes，做 ELF magic 驗證
② 解析 sections列出所有 section，依名稱分類成 program / map / data / btf
③ 建立 Spec把 section 解析結果組成不可變規格物件，可重複實例化
④ BTF 處理解析 .BTF（local types）；若 Kernel 有 vmlinux BTF 則一併載入
⑤ CO-RE relocation對 .BTF.ext 中每筆 core_relo 計算 target offset，patch instruction 中的 imm 值
⑥ Kernel 建立用 syscall 建立 map 與載入 program；map fd 必須先存在再注入到 program 的 ld_imm64
⑦ Attach建 link 把 program 接到 hook（XDP / tcx / kprobe / cgroup ...）

16.3 cilium/ebpf 三層抽象

cilium/ebpf 把 loading 流程切成三層，對應「不可變規格」與「kernel runtime 物件」的分離：

flowchart LR ELF[".o ELF"] subgraph SPEC["Spec 層（規格、可重複實例化）"] CSP["CollectionSpec"] MS["MapSpec × N"] PS["ProgramSpec × M"] VS["VariableSpec × K"] end subgraph RUNTIME["Runtime 層（kernel objects）"] COL["Collection"] M["Map × N"] P["Program × M"] L["Link × M"] end ELF -->|"LoadCollectionSpec()"| CSP CSP --> MS CSP --> PS CSP --> VS CSP -->|"NewCollection() /
LoadAndAssign()"| COL COL --> M COL --> P P -->|"link.AttachXDP() 等"| L

16.3.1 三層的 Go 對應 API

層核心型別建立方式
① ELF 解析*ebpf.CollectionSpecLoadCollectionSpec(path) / LoadCollectionSpecFromReader(r)
② Spec 細節*MapSpec / *ProgramSpec / *VariableSpec透過 spec.Maps[name] 取得
③ 載入到 Kernel*ebpf.Collection + *Map + *ProgramNewCollection(spec) / NewCollectionWithOptions(spec, opts)
④ 自動 assign 到 struct使用 LoadAndAssign把 *Program / *Map 直接指給 struct field

16.3.2 LoadAndAssign 範例（手寫，不依賴 bpf2go）

手動載入 BPF .o 並 assign
package main

import (
    "github.com/cilium/ebpf"
    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/rlimit"
    "log"
)

type myObjs struct {
    XdpFilter *ebpf.Program `ebpf:"xdp_filter"`   // section 名
    Stats     *ebpf.Map     `ebpf:"stats"`        // map 名
}

func main() {
    if err := rlimit.RemoveMemlock(); err != nil { log.Fatal(err) }

    /* ① 解析 ELF → CollectionSpec */
    spec, err := ebpf.LoadCollectionSpec("/path/to/myprog.o")
    if err != nil { log.Fatal(err) }

    /* ② 預先調整 spec（可選） */
    spec.Maps["stats"].MaxEntries = 1024 * 1024  // 動態改大小

    /* ③ 載入到 Kernel + assign 到 struct */
    var objs myObjs
    if err := spec.LoadAndAssign(&objs, nil); err != nil {
        log.Fatalf("load: %v", err)
    }
    defer objs.XdpFilter.Close()
    defer objs.Stats.Close()

    /* ④ Attach */
    l, err := link.AttachXDP(link.XDPOptions{
        Program:   objs.XdpFilter,
        Interface: 2,
    })
    if err != nil { log.Fatal(err) }
    defer l.Close()

    /* ... 主要邏輯 ... */
}

16.4 bpf2go：compile-time code generation

手寫 LoadCollectionSpec 雖然清楚，但每個專案都要重複 30 行樣板。bpf2go 解決這個問題：編譯期把 BPF .c 編成 .o，並產出對應的 Go code，把 .o 嵌入 binary。

16.4.1 工作流程

flowchart LR GO["main.go
+ //go:generate ..."] BPFC["bpf/myprog.c"] GEN["go generate"] CC["clang -target bpf -g -O2"] O["myprog_bpfel.o
+ myprog_bpfeb.o"] CODE["myprog_bpfel.go
+ myprog_bpfeb.go"] BIN["最終 Go binary
(.o 已 embed)"] GO --> GEN BPFC --> GEN GEN --> CC --> O GEN --> CODE O -->|"go:embed"| BIN CODE -->|"go build"| BIN

16.4.2 generate 註解

generate.go
package main

//go:generate go tool bpf2go -cc clang \
//    -target amd64,arm64 \
//    myprog bpf/myprog.c -- -I./bpf/headers
產生的程式碼（節錄）
// Code generated by bpf2go; DO NOT EDIT.
package main

import (
    "github.com/cilium/ebpf"
    _ "embed"
)

//go:embed myprog_bpfel.o
var _myprogBytes []byte

type myprogObjects struct {
    myprogPrograms
    myprogMaps
}

type myprogPrograms struct {
    XdpFilter *ebpf.Program `ebpf:"xdp_filter"`
}

type myprogMaps struct {
    Stats *ebpf.Map `ebpf:"stats"`
}

func loadMyprogObjects(obj interface{}, opts *ebpf.CollectionOptions) error {
    spec, err := loadMyprog()
    if err != nil { return err }
    return spec.LoadAndAssign(obj, opts)
}

func loadMyprog() (*ebpf.CollectionSpec, error) {
    /* 從 _myprogBytes 解析 */
    return ebpf.LoadCollectionSpecFromReader(bytes.NewReader(_myprogBytes))
}

16.4.3 -target 為何寫 amd64,arm64

bpf2go 需要產生兩份 .o：

  • myprog_bpfel.o：little-endian（amd64 / arm64 / riscv64 / loongarch64）
  • myprog_bpfeb.o：big-endian（s390x / mips 等）

對應的 Go 檔加上 build tag，go build 時自動挑選合適 endianness。

16.5 ELF Relocation 處理

BPF .o 中的 instructions 不能直接送到 Kernel——有幾類「占位」必須在載入時 patch：

relocation 類型內容處理時機
map fdld_imm64 r1, <map symbol> 中的占位 map indexmap 建立後拿到 fd，patch 進 imm[1]
BPF-to-BPF callcall <subprog> 跳到別的 section symbol把 subprog 拼進主 program 後 patch 偏移
CO-RE relocation第 15 章詳述：欄位 offset / type size / enum value 等載入時對照 Kernel BTF
data section referenceld_imm64 r1, .rodata + offset建立 .rodata internal map 後 patch fd
extern symbol（kfunc / kvar）對 KFunc / kernel variable 的引用對照 Kernel BTF 找 id

16.6 Map / Program / Link Lifecycle

cilium/ebpf 對 BPF object 的 lifecycle 採「file descriptor + Go GC」雙層管理。理解這個對寫長期運行的 daemon 很關鍵。

16.6.1 Lifecycle 三條規則

  1. fd 由 Go object 持有：*Program、*Map、link.Link 都封裝一個 fd。Go object 被 GC 時會自動 close fd。
  2. Kernel 用引用計數：fd 是其中一種引用，pin 是另一種，program-uses-map / link-uses-program 也都是引用。
  3. 所有引用清掉，物件才消失。
flowchart LR GO["Go *Program"] FD["Kernel fd"] OBJ["Kernel BPF object"] PIN["bpffs pin"] LINK["bpf_link"] MAP["其他 map 引用"] GO --> FD --> OBJ PIN --> OBJ LINK --> OBJ MAP --> OBJ

16.6.2 常見 lifecycle 陷阱

陷阱後果正確作法
Go application 退出但忘了 pinKernel object 自動清除，hooks 失效長期運行就 retain 物件；短期 CLI 想留下就 pin
Loader 載完就 spec = nil 不存 *CollectionGC 後 fd close，但有些 map 已 attached 到 prog 倒沒事務必把 *Collection 持有到不需要為止
Pin 之後忘了 unpin下次啟動失敗（路徑已存在）啟動時先 os.RemoveAll 或用 bpftool map show 檢查
Program Array 沒 user space 引用所有 tail call target 失效對 PROG_ARRAY 強制要求保留引用

16.7 aya 的 Rust 設計

aya 是 Rust 生態的純 Rust BPF library，不依賴 libbpf。設計與 cilium/ebpf 神似但更 Rust-idiomatic。

16.7.1 對應抽象

cilium/ebpfaya意義
CollectionSpecEbpfLoaderELF → 可調整的 spec
CollectionEbpf已載入 Kernel 的物件集
*ProgramProgram / Xdp / KProbe / TracePoint 等 type-safe wrapperaya 用 Rust enum 區分
*MapHashMap<_, K, V> / PerfEventArray<_> 等 genericaya 把 map type 變成 Rust generic
bpf2gocargo workspace + aya-build都是 compile-time

16.7.2 aya 載入範例

user/src/main.rs
use aya::{
    programs::{Xdp, XdpFlags},
    maps::HashMap,
    Ebpf, EbpfLoader, VerifierLogLevel,
};

fn main() -> anyhow::Result<()> {
    /* ① + ② + ③ 一氣呵成 */
    let mut bpf = EbpfLoader::new()
        .verifier_log_level(VerifierLogLevel::DEBUG)
        .load(aya::include_bytes_aligned!(
            "../../target/bpfel-unknown-none/release/myprog"
        ))?;

    /* ④ 取得 typed Program */
    let prog: &mut Xdp = bpf.program_mut("xdp_filter").unwrap().try_into()?;
    prog.load()?;
    prog.attach("eth0", XdpFlags::default())?;

    /* ⑤ 取得 typed Map */
    let mut blocklist: HashMap<_, u32, u32> =
        HashMap::try_from(bpf.map_mut("BLOCKLIST").unwrap())?;
    blocklist.insert(0x01010101u32, 1, 0)?;

    /* ... */
    Ok(())
}

16.8 libbpf 與 bpftool gen skeleton

C 端的標準 loader 是 libbpf。它的「skeleton」概念是 bpf2go / aya 的靈感來源：

產生 skel.h
# 編 BPF .o
$ clang -O2 -target bpf -g -c hello.bpf.c -o hello.bpf.o

# 用 bpftool 產生 skeleton header
$ sudo bpftool gen skeleton hello.bpf.o > hello.skel.h
使用 skeleton（C）
#include "hello.skel.h"

int main() {
    struct hello_bpf *skel = hello_bpf__open_and_load();
    if (!skel) { fprintf(stderr, "load failed\n"); return 1; }

    if (hello_bpf__attach(skel)) {
        fprintf(stderr, "attach failed\n");
        hello_bpf__destroy(skel);
        return 1;
    }

    /* skel->maps.events 直接是 *bpf_map */
    /* skel->progs.handle_execve 直接是 *bpf_program */
    /* skel->data->some_global = 42; */

    while (running) sleep(1);
    hello_bpf__destroy(skel);
    return 0;
}

16.9 Loader 互通性與選擇

場景建議
Kubernetes / cloud-native daemon（Go）cilium/ebpf + bpf2go
系統工具、CLI（Go）cilium/ebpf + bpf2go
嵌入式、IoT、安全產品（Rust）aya + aya-ebpf
BPF kernel 開發者測試libbpf + bpftool gen skeleton
BCC 風格快速 prototypelibbpf + libbpf-tools
Python 整合 / NotebookBCC（注意 runtime compile 開銷）
關於 BCC：仍有一席之地，但別當預設

BCC（IO Visor）是早期 BPF 工具的代名詞（execsnoop、tcplife 等都來自它）。但 BCC 的執行模型是 runtime compile：每次執行都要 clang + LLVM 編譯。CO-RE 出現後，libbpf-tools 是 BCC 工具的 CO-RE 重寫版，啟動快、不需 LLVM。新工具優先用 libbpf-tools / cilium-ebpf / aya，BCC 留給 prototype。

16.10 第 16 章小結

  1. 所有 Loader 共用七階段流程：ELF → Spec → BTF → CO-RE → Kernel object → Attach。
  2. BPF .o 內有 12+ 個標準 section，.text / .maps / .rodata / .BTF / .BTF.ext 是核心。
  3. cilium/ebpf 三層抽象：CollectionSpec（不可變規格）→ Collection（已載入 kernel 物件）→ Link（attach 後的綁定）。
  4. bpf2go 與 bpftool gen skeleton 都是 compile-time code generation：把 .o 嵌入 binary，產出 typed wrapper。
  5. ELF relocation 五大類：map fd、BPF-to-BPF call、CO-RE、.rodata reference、kfunc。
  6. Lifecycle 用 fd 與 Go GC 雙層管理；長期運行的 daemon 必須持有 Collection，不要讓它 GC。
  7. aya 是 Rust 生態對應，設計神似但 type-safe 程度更高。
  8. Loader 選擇：Go 用 cilium/ebpf、Rust 用 aya、C 用 libbpf；BCC 留給 prototype。

test_helper.go：構造封包
func buildIPv4Packet(src, dst string) []byte {
    eth := &layers.Ethernet{
        SrcMAC: net.HardwareAddr{1, 2, 3, 4, 5, 6},
        DstMAC: net.HardwareAddr{6, 5, 4, 3, 2, 1},
        EthernetType: layers.EthernetTypeIPv4,
    }
    ip := &layers.IPv4{
        Version: 4, IHL: 5, TTL: 64,
        Protocol: layers.IPProtocolTCP,
        SrcIP: net.ParseIP(src), DstIP: net.ParseIP(dst),
    }
    tcp := &layers.TCP{SrcPort: 12345, DstPort: 80, SYN: true}
    tcp.SetNetworkLayerForChecksum(ip)

    buf := gopacket.NewSerializeBuffer()
    opts := gopacket.SerializeOptions{FixLengths: true, ComputeChecksums: true}
    gopacket.SerializeLayers(buf, opts, eth, ip, tcp)
    return buf.Bytes()
}

# 含 coverage（cover bpf2go 產生的 Go code）
$ sudo go test -coverprofile=cover.out ./...

17.2.3 PROG_TEST_RUN 的 Repeat 模式

RunOptions.Repeat 可以叫 Kernel 重跑 N 次同一段邏輯，回傳單次平均時間。簡易 micro-benchmark 神器：

微 benchmark
ret, _, err := objs.XdpFilter.Run(&ebpf.RunOptions{
    Data:   pkt,
    Repeat: 1_000_000,   // 跑一百萬次
})
/* 回傳的 duration 是「平均單次 ns」 */
log.Printf("avg per-packet: %s", duration)
/* 例：avg per-packet: 73ns */

17.3 Layer 2：整合測試（netns + 真實流量）

單元測試確認邏輯正確，但 attach 到真實 hook 後行為對不對是另一回事。整合測試用 network namespace 隔離環境，跑實際的封包流。

17.3.1 一個典型的 netns 測試環境

flowchart LR H["Host (test runner)"] NS1["netns A
(client)"] NS2["netns B
(server)"] V1["veth0 (in A)"] V2["veth1 (in B)"] BPF["BPF 程式 attach
到 veth0 ingress"] H -. "create" .-> NS1 H -. "create" .-> NS2 NS1 --> V1 NS2 --> V2 V1 -. "veth pair" .-> V2 BPF --> V1

17.3.2 用 shell + bpftool 構造

setup.sh
#!/bin/bash
set -e

# 建立兩個 netns
sudo ip netns add ns_client
sudo ip netns add ns_server

# 建立 veth pair
sudo ip link add veth_c type veth peer name veth_s

# 各放一個 netns
sudo ip link set veth_c netns ns_client
sudo ip link set veth_s netns ns_server

# 設定 IP
sudo ip -n ns_client addr add 10.0.0.1/24 dev veth_c
sudo ip -n ns_server addr add 10.0.0.2/24 dev veth_s
sudo ip -n ns_client link set veth_c up
sudo ip -n ns_server link set veth_s up
sudo ip -n ns_client link set lo up
sudo ip -n ns_server link set lo up

# 把 BPF attach 到 server 端 veth ingress
sudo ip -n ns_server link set veth_s xdpgeneric obj /path/to/myprog.o sec xdp
test.sh
#!/bin/bash
# 在 client netns 跑 ping，看 BPF 是否如預期 drop / pass
sudo ip netns exec ns_client ping -c 3 -W 1 10.0.0.2

# 用 tcpdump 觀察 server 端是否收到封包
sudo ip netns exec ns_server timeout 5 tcpdump -i veth_s -nn -c 10 &
sleep 0.5
sudo ip netns exec ns_client curl -m 3 http://10.0.0.2/

# 從 BPF map 確認計數
sudo bpftool map dump pinned /sys/fs/bpf/stats

17.3.3 在 Go test 中自動化 netns

cilium/ebpf 自帶的 testing utility（vishvananda/netns）可以在 Go test 中切換 netns，做完全自動化的整合測試。Cilium 與 Tetragon 的 CI 都基於這個模式。

17.4 Layer 3：負載與壓力測試

確認效能在預期範圍。常見場景：

  • XDP 程式在 10 Gbps line rate 下能否處理？
  • cgroup_skb 在 100K rps 下 CPU 增加多少？
  • 長時間運行（> 24h）有沒有 memory leak？

17.4.1 用 XDP_LIVE_FRAMES 做純 BPF 速度測試

第 14.9.3 節介紹過 XDP_LIVE_FRAMES：把 PROG_TEST_RUN 的封包注入網路堆疊，等同無實體網卡的速度測試。

用 XDP_LIVE_FRAMES 測 throughput
opts := &ebpf.RunOptions{
    Data:   pkt,
    Repeat: 10_000_000,
    Flags:  unix.BPF_F_TEST_XDP_LIVE_FRAMES,
}
ret, _, err := objs.XdpFilter.Run(opts)
/* 從 duration 算出 pps */
log.Printf("avg %s/packet → %.2f Mpps",
    duration, 1e3 / float64(duration.Nanoseconds()))

17.4.2 用 pktgen / TRex 灌真實流量

pktgen（kernel 內建）能產生 100M+ pps 的測試流量，搭配兩台機器 + DPDK / TRex 可以做 100 Gbps 測試。是 Cilium、Katran 等專案的 benchmark 標準。

17.6.3 bpf_trace_printk 與 trace_pipe

BPF 程式內 print 訊息的傳統方式。由於是共享 trace_pipe，所有 BPF 程式都會看到，不適合 production：

BPF 端
SEC("xdp")
int xdp_filter(struct xdp_md *ctx) {
    /* 最多 3 個 % 參數 */
    bpf_printk("pkt len=%d ifindex=%d", ctx->data_end - ctx->data,
               ctx->ingress_ifindex);
    return XDP_PASS;
}
user space 端觀察
# 看 trace_pipe（共享，會收到所有 BPF print）
$ sudo cat /sys/kernel/debug/tracing/trace_pipe
   curl-12345  [001] ...11  3245.12: bpf_trace_printk: pkt len=74 ifindex=2
   ...

# 注意：trace_pipe 是 read-once-and-consumed
# 多個讀者會搶

17.7 BPF stream（6.13+）：現代 stdout/stderr

傳統 bpf_trace_printk 的痛點：

  • 單一全域 trace_pipe，所有 BPF 程式共享。
  • 無法區分哪支程式產生的訊息。
  • 讀取被 consume，多 reader 互搶。
  • 速率有限制，高頻會 drop。

Linux 6.13 引入 BPF stream：每個 program 有自己的 stdout / stderr stream，user space 透過 BPF_PROG_STREAM_READ_BY_FD 讀取，類似 process 的 fd 0/1/2。

BPF 端寫 stream
SEC("xdp")
int xdp_filter(struct xdp_md *ctx) {
    /* 寫到自家 stream，不會與其他程式混 */
    bpf_stream_printk(BPF_STREAM_STDOUT, "pkt len=%d", ctx->data_end - ctx->data);
    if (something_bad)
        bpf_stream_printk(BPF_STREAM_STDERR, "warning: %d", err);
    return XDP_PASS;
}
user space 讀取
/* cilium/ebpf 已開始支援 6.13+ */
buf := make([]byte, 4096)
n, err := objs.XdpFilter.StreamRead(ebpf.StreamStdout, buf)
if err != nil { /* ... */ }
log.Printf("BPF stdout: %s", buf[:n])

17.9 第 17 章小結

  1. BPF 測試分三層：單元測試（PROG_TEST_RUN）→ 整合測試（netns）→ 負載測試（pktgen / XDP_LIVE_FRAMES）。
  2. 單元測試最有效率：用 RunOptions.Repeat 還能順便做 micro-benchmark。
  3. 整合測試靠 netns + veth 做隔離環境模擬。
  4. 負載測試靠 XDP_LIVE_FRAMES（純軟體）或 pktgen / TRex（真實流量）。
  5. 除錯三大利器：bpftool prog dump xlated/jited、verifier log、bpf_trace_printk + trace_pipe。
  6. BPF stream（6.13+）取代 trace_pipe，每支 program 獨立 stdout/stderr。
  7. 上線前檢查 10 項：包含 verifier、CO-RE、記憶體、效能、ref leak、attach/detach 等。
