4.1 為何 Maps 是 eBPF 的核心

讀完冊一你應該已經熟悉一個事實：BPF 程式沒有 heap、沒有 mutable 全域變數、stack 只有 512 bytes。所有跨呼叫保留資料、跨程式共享狀態、跨 user/kernel 邊界傳遞訊息，全靠 Maps。

用一個比喻：

BPF 程式像是一個只能讀寫局部變數的純函式，Maps 就是這個函式存取外部世界的唯一管道。沒有 Maps，BPF 程式只能在 Kernel 裡安靜地跑完然後消失，不留痕跡。

Maps 在 BPF 生態的角色：

  1. BPF → User space 輸出資料：用 ring buffer / perf event array。
  2. User space → BPF 配置參數：用 hashmap / array。
  3. BPF → BPF 共享狀態：例如 XDP 程式統計後，由 tc 程式讀取。
  4. BPF 程式內部跨呼叫保留狀態：例如延遲計算需要存「這次 syscall 的進入時間」。
  5. BPF → BPF 跳轉：用 prog array 做 tail call。
  6. BPF → 網路堆疊重導向：用 sockmap、devmap、cpumap 把封包轉到別處。

4.3 Map 的共通機制

4.3.1 BTF-style 宣告（建議寫法）

過去（<= 2020 年）大家用 struct bpf_map_def 宣告 Map，但這種寫法不帶 BTF type 資訊，因此沒有 CO-RE 支援、bpf2go 也無法產生 typed scaffolding。現代寫法都用 BTF-style：

推薦：BTF-style，放在 .maps section
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

struct event {
    __u32 pid;
    char  comm[16];
};

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, struct event);
    __uint(max_entries, 1024);
} my_hash SEC(".maps");

// 還可以加：
//   __uint(map_flags, BPF_F_NO_PREALLOC);
//   __uint(pinning,   LIBBPF_PIN_BY_NAME);
不推薦：legacy 寫法，放在 maps section
// 缺點：bpf2go 無法產生 typed wrapper、無 CO-RE、IDE 失去型別提示
struct bpf_map_def my_hash SEC("maps") = {
    .type = BPF_MAP_TYPE_HASH,
    .key_size = sizeof(__u32),
    .value_size = sizeof(struct event),
    .max_entries = 1024,
};

4.3.4 Map 的生命週期

sequenceDiagram participant U as User space participant K as Kernel participant M as Map 物件 participant P as BPF Program U->>K: bpf(BPF_MAP_CREATE, ...) K->>M: 配置記憶體 K-->>U: 回傳 map_fd Note over P,M: BPF 載入時持有 map reference U->>K: bpf(BPF_PROG_LOAD, ...)
含 map_fd reference K->>P: 載入 program loop 運行中 P->>M: bpf_map_lookup_elem U->>M: BPF_MAP_LOOKUP_ELEM (syscall) end Note over U,M: User space 關閉 fd U->>K: close(map_fd) Note over P,M: 若 program 也釋放 reference
且未 pin，map 即被回收

Map 的生命週期由所有持有 reference 的物件決定：

  • User space FD
  • BPF Program 載入時的 reference
  • Pinning 在 bpffs 上的 inode

只要還有任何一方持有，Map 就活著。全部釋放後，Kernel 才會回收。

4.3.5 容量計算（重要！）

Map 不是免費的——每個 Map 都會占用 Kernel locked memory。粗略估算公式：

記憶體估算公式

對 HASH：(key_size + value_size + ~50 bytes overhead) × max_entries

對 ARRAY：roundup(value_size, 8) × max_entries（key 不占空間）

對 PERCPU_*：上述 × nr_cpus

對 RINGBUF：max_entries 直接是 bytes（必須是 2 的次方）

例：8-CPU 主機上 PERCPU_HASH，key 4 bytes、value 32 bytes、max_entries 100,000，記憶體約 (4+32+50) × 100000 × 8 ≈ 65 MB。

用 bpftool map show 可以查看實際的 memlock 占用。

4.4 Generic Maps（通用型）

這是日常開發最常用的五種 Map。它們都是「通用 K/V 容器」，差別在於索引方式與是否支援淘汰。

4.4.1 BPF_MAP_TYPE_HASH

BPF_MAP_TYPE_HASH
分類
Generic
Key
任意大小、任意結構
Value
任意大小、任意結構
淘汰
無，滿了之後 update 會回 ENOMEM
支援版本
3.19
典型用途
PID → 統計、IP → metadata、syscall id → 計數

Hash table 是預設選擇——當你不確定要用什麼，先用 HASH。它支援任意大小的 key/value，bpf_map_lookup_elem 回傳指向 value 的指標，所以更新只要在原地修改即可：

原地更新計數
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);          // PID
    __type(value, __u64);        // syscall 計數
    __uint(max_entries, 10240);
} pid_count SEC(".maps");

SEC("tracepoint/raw_syscalls/sys_enter")
int count_syscall(void *ctx) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;

    __u64 *cnt = bpf_map_lookup_elem(&pid_count, &pid);
    if (cnt) {
        // 直接 in-place 加，但併發可能 race
        // 想免 race 改用 __sync_fetch_and_add
        __sync_fetch_and_add(cnt, 1);
    } else {
        __u64 init = 1;
        bpf_map_update_elem(&pid_count, &pid, &init, BPF_NOEXIST);
    }
    return 0;
}
HASH 的 race condition

多 CPU 上同時觸發 BPF 程式時，lookup → modify → update 不是原子操作。要避免 race：(1) 用 __sync_fetch_and_add 等 atomic builtin、(2) 改用 PERCPU_HASH、(3) 用 spin lock（5.1+）。

Array 在建立時就配置好全部 slot 並初始化為 0，無法 delete，只能 update。換來的好處是：JIT 知道 max_entries 是常數，可以把 bpf_map_lookup_elem 內聯掉，極快。

進階用法：開啟 BPF_F_MMAPABLE，user space 可以 mmap map 到 process 記憶體，避免 syscall，效能再上一層樓。常見於儀表板、計數器收集。

Bloom Filter 是機率性資料結構，可能誤判（false positive），但絕不漏報（no false negative）。對於「先 cheap 篩掉九成請求」的場景非常省記憶體。

配合 HASH 做兩階段查詢
struct {
    __uint(type, BPF_MAP_TYPE_BLOOM_FILTER);
    __type(value, __u32);
    __uint(max_entries, 1000000);  // 預期條目數
    __uint(map_extra, 5);          // hash 函式數量（可選）
} suspicious_ips SEC(".maps");

SEC("xdp")
int filter_xdp(struct xdp_md *ctx) {
    __u32 src_ip = /* 解析封包... */;

    // 先用 bloom filter 快速篩
    if (bpf_map_peek_elem(&suspicious_ips, &src_ip) != 0) {
        return XDP_PASS;   // 不在可疑清單，直接放行
    }
    // bloom filter 命中（可能誤判），再走重的精確查表
    // ... 查另一個 HASH map ...
    return XDP_DROP;
}

4.5 Per-CPU 變體

每個基礎 Map 類型多半有 per-CPU 版本。每個 CPU 各自有一份獨立的記憶體，BPF 程式存取時自動取得當前 CPU 的版本，免鎖、零 contention。代價是：

  • 記憶體 = 單份 × nr_cpus。
  • BPF 程式之間無法跨 CPU 共享資料。
  • User space 讀取時會看到「全部 CPU 的陣列」，需要自己 aggregate。

四個 per-CPU 變體：

類型對應普通版支援版本
BPF_MAP_TYPE_PERCPU_HASHHASH4.6
BPF_MAP_TYPE_PERCPU_ARRAYARRAY4.6
BPF_MAP_TYPE_LRU_PERCPU_HASHLRU_HASH4.10
BPF_MAP_TYPE_PERCPU_CGROUP_STORAGECGROUP_STORAGE4.20
什麼時候該用 PerCPU？

三個情境：(1) 高頻計數—— 每秒百萬次計數的 metric 必用。(2) 大型 scratch buffer—— BPF stack 只有 512 bytes，需要大暫存區時用 PERCPU_ARRAY[1] 取得 CPU-private 大塊記憶體。(3) 避免 lock contention—— 任何只在 BPF 程式內聚合、最後由 user space 加總的計數場景。

4.5.1 PerCPU Array 當大型 scratch space

用 PERCPU_ARRAY 取代 stack 大型暫存
struct heavy_ctx {
    char buf[4096];     // 遠超過 512 bytes stack
    __u32 fields[256];
};

struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __type(key, __u32);
    __type(value, struct heavy_ctx);
    __uint(max_entries, 1);     // 每 CPU 只需要 1 個
} heavy_scratch SEC(".maps");

SEC("kprobe/__some_function")
int trace_heavy(struct pt_regs *ctx) {
    __u32 zero = 0;
    struct heavy_ctx *hc = bpf_map_lookup_elem(&heavy_scratch, &zero);
    if (!hc) return 0;

    // 在 hc->buf 等大塊記憶體上工作，不會炸 stack
    // ...
    return 0;
}

Arena 是 eBPF 史上第一個「BPF 程式可動態配置記憶體」的機制。原本 BPF 完全無 heap，所有資料結構都受限於 Map 預定的 schema。Arena 提供一個 user / BPF 兩邊都能 mmap 的記憶體區，BPF 內可以用 bpf_arena_alloc_pages / bpf_arena_free_pages 動態配置。

實務意義：可以在 BPF 內實作自己的 binary tree、linked list、自訂 hash 表，不再受 Map 預定義結構限制。本書冊二第 7 章會展開。

BPF → user space 大量事件流的標準工具。共三類：

Ring Buffer 是 5.8 之後的首選事件輸出機制。優勢：

  • 整機共用一個：不像 perf event array 要每 CPU 建一個。
  • BPF 端 reserve / submit / discard 三步驟：可以先預留空間，發現條件不對再 discard，沒寫完就不會被 user 看到。
  • 支援 epoll wakeup：user space 用 epoll 等待，幾乎零 polling 開銷。
  • 事件保序（per CPU 內）：相比 perf event array 更可靠。

第 2 章 Hello World 就是用 RINGBUF。

4.9 Storage Maps（綁定 Kernel 物件）

這是一類特殊 Map：每個 entry 「綁定到某個 Kernel 物件」（task_struct、socket、inode、cgroup），物件消失時 entry 自動回收。對「per-task / per-socket 上下文」場景無比方便。

類型綁定物件支援版本
BPF_MAP_TYPE_TASK_STORAGEstruct task_struct5.11
BPF_MAP_TYPE_SK_STORAGEstruct sock5.2
BPF_MAP_TYPE_INODE_STORAGEstruct inode5.10
BPF_MAP_TYPE_CGRP_STORAGEstruct cgroup6.2
BPF_MAP_TYPE_CGROUP_STORAGE（舊式）cgroup（綁 program）4.19
BPF_MAP_TYPE_PERCPU_CGROUP_STORAGEcgroup（綁 program，per-cpu）4.20

4.9.1 為何不用普通 HASH？

沒有 storage map 之前，「per-PID 計時器」這類需求要用 HASH<pid, struct timer>。但 process 退出後，這個 entry 不會自動消失，要 user space 自己掃 PID list 清理，麻煩又容易 leak。Storage Map 把 entry 生命週期綁到 Kernel 物件本身，物件死了 entry 跟著走。

4.9.2 範例：用 TASK_STORAGE 計算 syscall 延遲

用 TASK_STORAGE 取代傳統 HASH
struct {
    __uint(type, BPF_MAP_TYPE_TASK_STORAGE);
    __uint(map_flags, BPF_F_NO_PREALLOC);   // 必須
    __type(key, int);                       // 慣例：填 0
    __type(value, __u64);                   // 起始時間戳
} start_ts SEC(".maps");

SEC("tracepoint/raw_syscalls/sys_enter")
int on_enter(void *ctx) {
    struct task_struct *task = (void *)bpf_get_current_task();
    __u64 ts = bpf_ktime_get_ns();
    bpf_task_storage_get(&start_ts, task, &ts,
                         BPF_LOCAL_STORAGE_GET_F_CREATE);
    return 0;
}

SEC("tracepoint/raw_syscalls/sys_exit")
int on_exit(void *ctx) {
    struct task_struct *task = (void *)bpf_get_current_task();
    __u64 *t = bpf_task_storage_get(&start_ts, task, NULL, 0);
    if (!t) return 0;
    __u64 latency = bpf_ktime_get_ns() - *t;
    // ... 將 latency 送出 ...
    bpf_task_storage_delete(&start_ts, task);
    return 0;
}

當 process 結束時，Kernel 自動釋放這個 entry，不需要任何 cleanup 程式碼。

4.11 Map of Maps

「Map 的 value 是另一個 Map 的 reference」。讓 BPF 程式可以根據 outer key 動態決定要操作哪個 inner map。

4.11.1 BPF_MAP_TYPE_ARRAY_OF_MAPS / HASH_OF_MAPS

類型Key支援版本
ARRAY_OF_MAPS4 bytes index4.12
HASH_OF_MAPS任意4.12

典型場景：

  • 多租戶：每個租戶獨立有一個自己的 stats Map，outer key 是 tenant id。
  • 動態切換 routing 表：藍綠部署，atomic 換掉一張 LPM_TRIE。
  • 每網卡獨立 ACL：outer key 是 ifindex，inner 是該介面的 rule HASH。
每網卡獨立 stats
// inner map 範本
struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __type(key, __u32);
    __type(value, __u64);
    __uint(max_entries, 256);
} inner_template SEC(".maps");

// outer map: ifindex -> inner map
struct {
    __uint(type, BPF_MAP_TYPE_HASH_OF_MAPS);
    __type(key, __u32);
    __array(values, struct {
        __uint(type, BPF_MAP_TYPE_ARRAY);
        __type(key, __u32);
        __type(value, __u64);
        __uint(max_entries, 256);
    });
    __uint(max_entries, 32);
} per_dev_stats SEC(".maps");

SEC("xdp")
int xdp_count(struct xdp_md *ctx) {
    __u32 ifindex = ctx->ingress_ifindex;
    void *inner = bpf_map_lookup_elem(&per_dev_stats, &ifindex);
    if (!inner) return XDP_PASS;

    __u32 idx = 0;
    __u64 *cnt = bpf_map_lookup_elem(inner, &idx);
    if (cnt) __sync_fetch_and_add(cnt, 1);
    return XDP_PASS;
}

4.13 完整實作範例（Go + Rust 並列）

下面用一個小工具串起前面所有概念：記錄每個 process 開啟過的檔案數量，使用 HASH<pid, count>。

4.13.1 設計

  1. BPF 程式 attach 到 tracepoint/syscalls/sys_enter_openat。
  2. 每次觸發，取出 PID，更新 HASH map：map[pid]++。
  3. User space 每秒 dump 一次 map，列出 top 10。

4.13.2 BPF C（兩條路線共用）

openat.bpf.c — Go 路線使用
// SPDX-License-Identifier: GPL-2.0
#include "headers/vmlinux.h"
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "GPL";

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, __u64);
    __uint(max_entries, 10240);
} open_count SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_openat")
int count_openat(void *ctx) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;

    __u64 *cnt = bpf_map_lookup_elem(&open_count, &pid);
    if (cnt) {
        __sync_fetch_and_add(cnt, 1);
    } else {
        __u64 init = 1;
        bpf_map_update_elem(&open_count, &pid, &init, BPF_NOEXIST);
    }
    return 0;
}

4.13.3 Go user space

gen.go
package main

//go:generate go tool bpf2go -cc clang -target amd64,arm64 \

main.go
package main

import (
    "log"
    "os"
    "os/signal"
    "sort"
    "syscall"
    "time"

    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/rlimit"
)

type entry struct {
    PID   uint32
    Count uint64
}

func main() {
    if err := rlimit.RemoveMemlock(); err != nil {
        log.Fatal(err)
    }

    objs := openatObjects{}
    if err := loadOpenatObjects(&objs, nil); err != nil {
        log.Fatalf("load: %v", err)
    }
    defer objs.Close()

    tp, err := link.Tracepoint("syscalls", "sys_enter_openat", objs.CountOpenat, nil)
    if err != nil {
        log.Fatalf("attach: %v", err)
    }
    defer tp.Close()

    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt, syscall.SIGTERM)
    tick := time.NewTicker(time.Second)
    defer tick.Stop()

    log.Println("Tracking openat... (Ctrl-C 結束)")
    for {
        select {
        case <-sig:
            return
        case <-tick.C:
            entries := dumpMap(objs.OpenCount)
            sort.Slice(entries, func(i, j int) bool {
                return entries[i].Count > entries[j].Count
            })
            log.Printf("=== Top 10 ===")
            for i := 0; i < len(entries) && i < 10; i++ {
                log.Printf("  PID %-7d  count=%d", entries[i].PID, entries[i].Count)
            }
        }
    }
}

func dumpMap(m *ebpf.Map) []entry {
    var (
        key uint32
        val uint64
        out []entry
    )
    iter := m.Iterate()
    for iter.Next(&key, &val) {
        out = append(out, entry{PID: key, Count: val})
    }
    return out
}

4.13.4 Rust（aya）user space

openat-ebpf/src/main.rs（aya-ebpf）
#![no_std]
#![no_main]

use aya_ebpf::{
    helpers::bpf_get_current_pid_tgid,
    macros::{map, tracepoint},
    maps::HashMap,
    programs::TracePointContext,
};

#[map]
static OPEN_COUNT: HashMap<u32, u64> = HashMap::with_max_entries(10240, 0);

#[tracepoint]
pub fn count_openat(_ctx: TracePointContext) -> u32 {
    let pid = (bpf_get_current_pid_tgid() >> 32) as u32;

    unsafe {
        if let Some(cnt) = OPEN_COUNT.get_ptr_mut(&pid) {
            *cnt += 1;          // BPF 端 unsafe in-place 更新
        } else {
            let _ = OPEN_COUNT.insert(&pid, &1, 0);
        }
    }
    0
}

#[panic_handler]
fn panic(_info: &core::panic::PanicInfo) -> ! { loop {} }

use aya::{maps::HashMap, programs::TracePoint, Ebpf};
use std::{convert::TryInto, time::Duration};
use tokio::{signal, time};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    env_logger::init();

    #[cfg(debug_assertions)]
    let mut bpf = Ebpf::load(include_bytes_aligned!(
        "../../target/bpfel-unknown-none/debug/openat-ebpf"
    ))?;
    #[cfg(not(debug_assertions))]
    let mut bpf = Ebpf::load(include_bytes_aligned!(
        "../../target/bpfel-unknown-none/release/openat-ebpf"
    ))?;

    let prog: &mut TracePoint = bpf
        .program_mut("count_openat").unwrap().try_into()?;
    prog.load()?;
    prog.attach("syscalls", "sys_enter_openat")?;

    let map: HashMap<_, u32, u64> = HashMap::try_from(bpf.map("OPEN_COUNT").unwrap())?;

    let mut interval = time::interval(Duration::from_secs(1));
    println!("Tracking openat... (Ctrl-C 結束)");
    loop {
        tokio::select! {
            _ = signal::ctrl_c() => break,
            _ = interval.tick() => {
                let mut entries: Vec<(u32, u64)> = map.iter()
                    .filter_map(Result::ok).collect();
                entries.sort_by(|a, b| b.1.cmp(&a.1));
                println!("=== Top 10 ===");
                for (pid, count) in entries.iter().take(10) {
                    println!("  PID {:<7}  count={}", pid, count);
                }
            }
        }
    }
    Ok(())
}

4.14.3 常見效能陷阱

  • HASH 預設 pre-alloc 全部 slot：max_entries 設大會吃光記憶體；想 lazy 配置加 BPF_F_NO_PREALLOC。
  • RINGBUF max_entries 必須是 2 的次方：而且建議至少 64 KiB × CPU 核心數，否則高負載下會 drop event。
  • PERCPU 系列在小機器上反而浪費：1-2 CPU 場景效益很低，差距主要在 16+ CPU。
  • iterating HASH 是 O(n)：若每秒掃 10 萬條 entry 會卡 user space。考慮 BPF_MAP_LOOKUP_BATCH（5.6+）。
  • Spin lock 取消支援 mmap：開了 BPF_F_MMAPABLE 的 ARRAY 不能再放 spin lock 結構。
