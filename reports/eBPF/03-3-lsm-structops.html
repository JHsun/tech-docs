12.1 LSM 框架與 BPF LSM 的位置

LSM（Linux Security Module）是 Linux Kernel 從 2.6 開始的安全框架。它在 Kernel 內關鍵安全決策點放置 hook，讓安全模組（SELinux、AppArmor、Smack、Tomoyo、Yama、Lockdown 等）插入自己的策略決策。

傳統 LSM 模組是 編譯期靜態整合到 Kernel 的：

  • SELinux 把策略檔案（policy.conf）編譯後載入 Kernel，修改規則要重啟 / 重載 policy。
  • AppArmor 用 profile 檔，靈活度比 SELinux 高，但仍然非程式化。
  • 要新增自訂安全行為，傳統做法是寫 Kernel module，需要 root + 維護成本極高。

BPF LSM（5.7+）打破這個限制：

把 BPF 程式 attach 到 LSM hook，用 BPF 寫安全策略。
不用重新編 Kernel、不用寫 module，動態載入、動態卸載。

12.1.1 BPF LSM vs 其他類別

規則表達能力靜態 policy 語言固定 syscall 過濾語法圖靈完備（受 verifier 限制）

LSM hook 位置的特性：

  • 在實際操作之前：可以阻止操作發生，不只是事後審計。
  • 多模組鏈式呼叫：所有 attach 的 LSM 模組都會被詢問，任一拒絕即整體拒絕。
  • 看得到 typed kernel 物件：透過 BTF，BPF 程式直接讀 struct task_struct、struct inode、struct sock 等。

12.2 啟用 BPF LSM

BPF LSM 不是預設啟用的。多數發行版需要修改 Kernel boot parameter。

12.2.1 三步驟檢查

12.3 LSM hook 全景

LSM 提供 200+ hook 點，覆蓋：

  • Process / task：fork、exec、setuid、ptrace、signal、kill
  • 檔案系統：open、read、write、mmap、mprotect、unlink、mount
  • 網路：socket_create、socket_bind、socket_connect、socket_listen、socket_accept、socket_sendmsg、socket_recvmsg
  • BPF / 模組 / 核心：bpf、bpf_prog_load、kernel_load_data、kernel_module_request
  • IPC / SysV：msg_queue、shm、sem
  • Capabilities：capable、capset
  • Inode / file：inode_create、inode_unlink、file_permission、file_alloc_security

完整 hook 清單在 Kernel source include/linux/lsm_hook_defs.h。常用的有：

Hook觸發時機典型策略
file_openopen() 時禁止讀某些檔案
file_mprotectmprotect() 時阻止 RWX 記憶體（防 JIT spray）
bprm_check_securityexecve() 前阻擋執行特定二進位
socket_createsocket() 時禁特定 process 開 socket
socket_connectconnect() 時禁止連到特定 IP / port
task_kill發送 signal 時防 SIGKILL 攻擊重要 process
ptrace_access_checkptrace 附加禁止 ptrace 敏感 process
bpf呼叫 bpf() syscall 時限制誰能載入 BPF
kernel_module_request自動載入 kernel module禁止載入未簽章 module

12.4 BPF LSM 程式撰寫

12.4.1 基本骨架

最小 LSM 範例
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

#define EPERM 1

// hook 名稱在 SEC("lsm/<hook_name>")
SEC("lsm/file_open")
int BPF_PROG(my_file_open_check, struct file *file, int ret) {
    /* 「不可覆寫拒絕」原則：若上一個 LSM 已經拒絕，
     * 我們不可改變決定，直接回傳同樣的 ret */
    if (ret != 0) return ret;

    /* 我們可以做進一步檢查並拒絕 */
    /* return -EPERM 拒絕；return 0 允許 */
    return 0;
}

12.4.2 BPF_PROG 巨集的展開

注意 BPF_PROG 巨集的最後一個參數總是 int ret。它代表「前一個 LSM 程式的 return value」（或 0，如果是第一個）。這是 LSM 「cannot override a denial」的實作關鍵，下節會詳解。

12.4.3 typed 參數的優勢

LSM 屬於 TRACING family（與 fentry/fexit 同類），BTF-typed。可以直接讀 kernel struct 欄位，無需 BPF_CORE_READ：

直接讀 typed 參數
SEC("lsm/file_open")
int BPF_PROG(check_open, struct file *file, int ret) {
    if (ret != 0) return ret;

    /* 直接讀 kernel struct，BTF 處理 offset */
    const unsigned char *name = file->f_path.dentry->d_name.name;
    char buf[64];
    bpf_probe_read_kernel_str(buf, sizeof(buf), name);

    /* 簡單比對檔名（實務上應透過 map 查詢黑名單） */
    if (buf[0] == 's' && buf[1] == 'h' && buf[2] == 'a' &&
        buf[3] == 'd' && buf[4] == 'o' && buf[5] == 'w') {
        bpf_printk("blocking open of: %s", buf);
        return -EPERM;
    }
    return 0;
}

12.5 「不可覆寫拒絕」原則

LSM 的設計核心：多個 LSM 模組形成決策鏈，任一拒絕即整體拒絕，且後者不可推翻前者的拒絕。

flowchart LR REQ["請求進入 LSM hook"] M1["LSM 模組 1
SELinux"] M2["LSM 模組 2
AppArmor"] M3["LSM 模組 3
BPF LSM"] OK["允許"] DENY["拒絕"] REQ --> M1 M1 -->|"return 0"| M2 M1 -->|"return -EPERM"| M2 M2 -->|"see ret=-EPERM
必須 return ret"| M3 M2 -->|"return 0 (若前者 0)"| M3 M3 -->|"see ret=-EPERM
必須 return ret"| DENY M3 -->|"return 0 (若前者 0)"| OK

因此每個 BPF LSM 程式的開頭幾乎都長這樣：

if (ret != 0) return ret;   /* 「不可覆寫拒絕」 */

違反這個原則（譬如不檢查 ret 直接 return 0）不會被 verifier 拒絕，但會破壞與其他 LSM 的協作，被視為錯誤的實作。

12.6 BPF_LSM_MAC vs BPF_LSM_CGROUP

BPF LSM 有兩種 attach type，行為差異很大：

Attach type範圍Return 語意用途
BPF_LSM_MAC整機0 = allow，負值 = deny系統級 MAC 政策
BPF_LSM_CGROUP特定 cgroup1 = allow，0 = deny（反向！）容器級政策
CGROUP 模式 return 語意是反的！

BPF_LSM_CGROUP 採「access grantor」模型：每個 attach 在 cgroup 上的 BPF 程式都當作「授權者」，只要任一個 grant（return 1）就允許。這與 MAC 模式相反。寫 cgroup 級 LSM 時要特別注意。

12.7 完整實作範例：阻擋 outgoing 連線

建立一個 BPF LSM 工具：阻擋系統內任何 process 連到 1.1.1.1。

12.7.1 BPF C

lsm_block.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_endian.h>

char LICENSE[] SEC("license") = "GPL";

#define EPERM 1
#define AF_INET 2

/* 黑名單（network byte order） */
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, __u32);
    __uint(max_entries, 1024);
    __uint(pinning, LIBBPF_PIN_BY_NAME);
} blocklist SEC(".maps");

SEC("lsm/socket_connect")
int BPF_PROG(restrict_connect,
             struct socket *sock,
             struct sockaddr *address,
             int addrlen,
             int ret) {
    /* 不可覆寫拒絕 */
    if (ret != 0) return ret;

    /* 只攔 IPv4 */
    if (address->sa_family != AF_INET) return 0;

    struct sockaddr_in *addr = (struct sockaddr_in *)address;
    __u32 dest = addr->sin_addr.s_addr;

    if (bpf_map_lookup_elem(&blocklist, &dest)) {
        bpf_printk("LSM: blocking connect to 0x%x", dest);
        return -EPERM;
    }
    return 0;
}

12.7.2 Go user space（cilium/ebpf）

main.go
package main

import (
    "encoding/binary"
    "log"
    "net/netip"
    "os"
    "os/signal"
    "syscall"

    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/rlimit"
)

//go:generate go tool bpf2go -cc clang -target amd64,arm64 \
//   lsmblock bpf/lsm_block.c -- -I./bpf/headers

func main() {
    if len(os.Args) < 2 {
        log.Fatalf("usage: %s <ip>[,...]", os.Args[0])
    }
    ips := os.Args[1]

    if err := rlimit.RemoveMemlock(); err != nil { log.Fatal(err) }

    objs := lsmblockObjects{}
    if err := loadLsmblockObjects(&objs, nil); err != nil {
        log.Fatalf("load: %v (請確認 BPF LSM 已啟用：cat /sys/kernel/security/lsm)", err)
    }
    defer objs.Close()

    /* attach 到 LSM hook */
    l, err := link.AttachLSM(link.LSMOptions{
        Program: objs.RestrictConnect,
    })
    if err != nil { log.Fatalf("attach LSM: %v", err) }
    defer l.Close()

    /* 加入黑名單 */
    for _, s := range splitCsv(ips) {
        addr, err := netip.ParseAddr(s)
        if err != nil || !addr.Is4() { continue }
        b := addr.As4()
        raw := binary.BigEndian.Uint32(b[:])
        if err := objs.Blocklist.Put(raw, uint32(1)); err == nil {
            log.Printf("blocked %s (network=0x%08x)", s, raw)
        }
    }

    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt, syscall.SIGTERM)
    log.Println("LSM 已 attach。Ctrl-C 結束。")
    <-sig
}

func splitCsv(s string) []string {
    out := []string{}; cur := ""
    for _, r := range s {
        if r == ',' { out = append(out, cur); cur = ""; continue }
        cur += string(r)
    }
    if cur != "" { out = append(out, cur) }
    return out
}

12.8 與 Tetragon / KubeArmor / Falco 的關係

產品主要使用的 BPF 機制定位
Tetragon（Cilium）kprobe + LSM + tp_btfK8s 安全可觀測性 + 行動阻止
KubeArmorBPF LSM + AppArmorK8s policy enforcement
Falco（Sysdig）kprobe / tp_btf（傳統 driver 為主）Runtime 入侵偵測（RID）
Tracee（Aqua）kprobe / LSM容器 runtime 可觀測性

主流產品都在朝 LSM 過渡——它比 kprobe 穩定（有 ABI 保證）、又能阻止而非僅觀察。

12.9 第 12 章小結

  1. LSM 是 Kernel 安全框架，BPF LSM（5.7+）讓我們用 BPF 寫安全策略，無需 Kernel module。
  2. 啟用需要 lsm=...,bpf boot parameter，多數新發行版已預設。
  3. 200+ hook 點覆蓋 process / file / network / IPC / capabilities，靈活度極高。
  4. 「不可覆寫拒絕」原則：每個程式必須先檢查 ret != 0。
  5. BPF_LSM_MAC 系統級、BPF_LSM_CGROUP 容器級，後者 return 語意相反。
  6. LSM 屬於 TRACING family，BTF-typed，可直接讀 kernel struct。
  7. Tetragon、KubeArmor、Falco、Tracee 都使用 BPF LSM 作為新一代安全機制基礎。

13.1 STRUCT_OPS 概念：BPF 作為「實作」

過去你看到的 BPF 多半是「觀察者 / 攔截者」：trace 函式、過濾封包、拒絕 syscall。STRUCT_OPS（5.6+）是一個翻轉視角的 program type：

Kernel 在某些子系統提供了一組「可替換的函式指標」（如 struct tcp_congestion_ops、struct sched_class）。STRUCT_OPS 讓你用 BPF 程式填這些指標，等同實作一個 Kernel module，但不需要 module 機制、不需要重啟。

13.1.1 為何需要 STRUCT_OPS

傳統做法痛點STRUCT_OPS 解法
寫 Kernel module 實作 TCP CCmodule 簽章、發行週期長、debug 不便用 BPF 寫，立即生效
修改 Kernel scheduler幾乎不可能（會破壞 ABI）sched_ext 允許 BPF 取代 fair scheduler
實驗新 HID quirks每個裝置寫 module，難維護hid_bpf_ops 讓使用者輕量自訂

13.2.2 範例骨架（DCTCP）

用 BPF 實作 DCTCP（資料中心專用）
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

char LICENSE[] SEC("license") = "GPL";

extern void tcp_reno_cong_avoid(struct sock *sk, __u32 ack, __u32 acked) __ksym;

SEC("struct_ops/dctcp_init")
void BPF_PROG(dctcp_init, struct sock *sk) {
    /* per-connection 狀態初始化 */
}

SEC("struct_ops/dctcp_ssthresh")
__u32 BPF_PROG(dctcp_ssthresh, struct sock *sk) {
    return 16;  /* 簡化版 */
}

SEC("struct_ops/dctcp_cong_avoid")
void BPF_PROG(dctcp_cong_avoid, struct sock *sk, __u32 ack, __u32 acked) {
    /* 直接借用 reno 算法 */
    tcp_reno_cong_avoid(sk, ack, acked);
}

/* 把 BPF 函式組成「TCP CC 模組」 */
SEC(".struct_ops")
struct tcp_congestion_ops bpf_dctcp = {
    .init        = (void *)dctcp_init,
    .ssthresh    = (void *)dctcp_ssthresh,
    .cong_avoid  = (void *)dctcp_cong_avoid,
    .name        = "bpf_dctcp",
    .flags       = TCP_CONG_NEEDS_ECN,
};

net.ipv4.tcp_available_congestion_control = reno cubic bbr bpf_dctcp

# 也可以 per-socket 設定
# C: setsockopt(sk, IPPROTO_TCP, TCP_CONGESTION, "bpf_dctcp", ...)

13.3 sched_ext_ops — 可程式化 CPU scheduler

struct sched_ext_ops
分類
STRUCT_OPS 熱門
支援版本
6.12（2024-11）
典型用途
遊戲機 / 桌面延遲優化、AI 訓練 GPU 排程、資料中心 workload-aware 排程

sched_ext（簡稱 scx）是 Linux 史上第一次允許 BPF 取代 CPU scheduler。它由 Meta（Tejun Heo）主導，已合併進 6.12。Linux 現在有了 「BPF 可程式化的排程器框架」。

13.3.1 關鍵函式指標（部分）

欄位意義
select_cpu新 task wake 起來，挑哪個 CPU
enqueue把 task 放入 runqueue
dispatch給某 CPU 派 task 執行
tick每個 tick 呼叫
running / stoppingtask 開始 / 停止執行
runnable / quiescenttask 變可執行 / 變閒置
set_weight / set_cpumasknice / affinity 變化
cpu_acquire / cpu_releaseCPU 加入 / 退出（hotplug）

13.3.2 已知 sched_ext schedulers

名稱定位
scx_simple最小範例，純 FIFO
scx_rusty（Meta）多 domain，user space 與 BPF 協作
scx_lavd（Latency-Aware Virtual Deadline）桌面 / 遊戲低延遲
scx_layered（Meta）workload class 分層
scx_bpfland互動式工作流優化（已用於 CachyOS）
scx_central單一 CPU 排程整機（DPDK 風格）

13.3.3 啟用 sched_ext

啟用 scx
# 確認 Kernel 支援
$ grep CONFIG_SCHED_CLASS_EXT /boot/config-$(uname -r)
CONFIG_SCHED_CLASS_EXT=y

# 安裝 scx 工具集
$ sudo apt install scx-scheds   # Ubuntu 24.10+
# 或從原始碼 build：https://github.com/sched-ext/scx

# 跑一個 scheduler
$ sudo scx_lavd
# 它會載入 BPF、註冊到 Kernel，整機 scheduler 切換

# 觀察狀態
$ cat /sys/kernel/sched_ext/state
enabled
$ cat /sys/kernel/sched_ext/root/ops
lavd
為什麼 Meta、Oracle、CachyOS 都跳上來

sched_ext 解決一個長年痛點：「實驗新 scheduler 太困難」。傳統做法要 fork Kernel、合併到 mainline，週期以年計。scx 讓研究員與工程師幾天內就能實作、部署、A/B test。Meta 的內部資料中心已用 scx_layered，CachyOS 等發行版預設 scx_bpfland 提升桌面互動性。

13.4 hid_bpf_ops — HID 裝置 BPF

struct hid_bpf_ops
分類
STRUCT_OPS
支援版本
6.11
典型用途
HID 裝置 quirks（鍵盤 / 滑鼠 / 手把 / 平板的特殊處理）

HID（Human Interface Device）是鍵盤、滑鼠、遊戲手把、繪圖板的標準。每個怪奇裝置可能需要 quirk。傳統做法是進 Kernel module（hid-multitouch.c 等），門檻高。HID-BPF 讓使用者用 BPF 修正自家裝置行為，無需動 Kernel 原始碼。

典型用途：

  • 修正某品牌滑鼠的 scroll wheel 反向。
  • 把廠商奇怪的遙控器按鍵 remap 成標準 keycode。
  • 繪圖板壓力曲線 calibration。

13.5 Qdisc_ops — 自訂 qdisc

struct Qdisc_ops
分類
STRUCT_OPS 最新
支援版本
6.16（2025）
典型用途
用 BPF 實作 traffic control qdisc（取代 fq_codel、cake 等的 module 寫法）

Linux traffic control 的 qdisc 是 packet scheduler 的關鍵。Qdisc_ops 讓 BPF 可以實作 enqueue / dequeue / peek / drop 邏輯，相當於 sched_ext 之於 process scheduler。是最新加入的 STRUCT_OPS。

13.6 EXT — 函式替換 / freplace

BPF_PROG_TYPE_EXT
分類
特殊
支援版本
5.6
典型用途
替換另一個 BPF 程式的 subprogram（freplace）；libxdp 的 hot reload

EXT 是個少見但很巧妙的 program type：它替換另一個已載入 BPF 程式的某個 subprogram（透過 BTF function 名稱對齊）。這讓你能：

  • 熱替換 BPF 邏輯，不用 reload 整支程式。
  • libxdp 用它做「dispatcher」程式 + 多個可掛載的 freplace handlers。

13.7 SYSCALL — 給 BPF 寫的「小 syscall」

BPF_PROG_TYPE_SYSCALL
分類
特殊
支援版本
5.14
典型用途
用 BPF 寫一支「啟動一次性」的小程式來操作 BPF 物件

這是個元用法：寫一支 BPF 程式，它本身可以呼叫 BPF syscall（建立 map、載入 prog、attach）。透過 BPF_PROG_TEST_RUN 觸發即可執行。常見場景：

  • 初始化 BPF iterator
  • 建立巢狀 BPF 物件
  • 把 user space 的 setup 邏輯壓進 BPF（避免 root 條件下做事）

13.8 LIRC_MODE2 — 紅外線解碼

BPF_PROG_TYPE_LIRC_MODE2
分類
特殊
支援版本
4.18
典型用途
紅外線遙控器解碼（LIRC = Linux Infrared Remote Control）

LIRC 子系統處理紅外線輸入（電視盒、空調遙控器）。LIRC_MODE2 讓你用 BPF 寫自訂解碼器，取代傳統的 user space lircd 配置檔。一般工作負載完全不會碰到，這裡列出僅為完整性。

13.10 第 13 章小結

  1. STRUCT_OPS 翻轉了 BPF 的視角：從「觀察 / 攔截」變成「實作 Kernel 子系統」。
  2. 目前 4 個支援的 ops：tcp_congestion_ops（5.6）、hid_bpf_ops（6.11）、sched_ext_ops（6.12）、Qdisc_ops（6.16）。
  3. sched_ext 是近年 Linux Kernel 最重要的革新之一：可程式化 CPU scheduler，已用於 Meta 資料中心、CachyOS、遊戲玩家社群。
  4. EXT（freplace）支援熱替換 BPF subprogram，是 libxdp dispatcher 的基礎。
  5. SYSCALL 讓 BPF 自己呼叫 BPF syscall，常用於 setup 自動化。
  6. LIRC_MODE2 是 niche 的紅外線解碼專用。
  7. 讀完本冊，你已掌握 30+ 種 BPF program type 的全貌。
