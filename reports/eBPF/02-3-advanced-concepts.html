7.1 Concurrency 與 atomic 操作

BPF 程式在 Kernel 中執行時，同一個 program 可能在多個 CPU 上同時被觸發（XDP 在每個 RX queue 一份、tracepoint 在每個觸發 CPU 上獨立執行）。沒有任何同步機制的話，最常見的後果就是計數遺失或 map 內容錯亂。

7.1.1 三條主要對策

策略適用情境成本
Per-CPU map各 CPU 獨立計數，由 user space aggregate記憶體 × CPU 數，但完全免鎖
Atomic builtin（__sync_fetch_and_add）共享計數器，誤差可接受cache line bouncing
BPF spin lock（5.1+）需精確 read-modify-write 的 critical sectionBPF 程式被序列化

7.1.2 Atomic builtins

Clang 把 __sync_fetch_and_add、__sync_fetch_and_sub、__sync_lock_test_and_set、__sync_val_compare_and_swap 編成 BPF atomic instruction。Kernel 5.12+ 起 BPF ISA 加入了完整的 atomic ops（add/and/or/xor/xchg/cmpxchg）。

atomic add 是 BPF 計數的標準寫法
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, __u64);
    __uint(max_entries, 10240);
} counts SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_openat")
int count(void *ctx) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;
    __u64 *c = bpf_map_lookup_elem(&counts, &pid);
    if (c) {
        // ✅ 原子加法，多 CPU 安全
        __sync_fetch_and_add(c, 1);
    } else {
        __u64 init = 1;
        bpf_map_update_elem(&counts, &pid, &init, BPF_NOEXIST);
    }
    return 0;
}

7.1.3 BPF spin lock

對多欄位結構需要原子更新時，spin lock 是必要選擇。例：同時更新 {count, sum, max} 三個欄位。

BPF spin lock 用法
struct stats {
    struct bpf_spin_lock lock;   // 必須是第一個或固定位置
    __u64 count;
    __u64 sum;
    __u64 max;
};

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, struct stats);
    __uint(max_entries, 1024);
} m SEC(".maps");

SEC("kprobe/some_func")
int update(struct pt_regs *ctx) {
    __u32 key = 0;
    struct stats *s = bpf_map_lookup_elem(&m, &key);
    if (!s) return 0;

    __u64 v = PT_REGS_PARM1(ctx);
    bpf_spin_lock(&s->lock);
    s->count += 1;
    s->sum   += v;
    if (v > s->max) s->max = v;
    bpf_spin_unlock(&s->lock);     // verifier 強制配對
    return 0;
}
spin lock 的限制
  • 每個 BPF 程式同時只能持有 一個 spin lock。
  • 持有 lock 期間不能呼叫多數 helper（避免巢狀）。
  • 含 spin lock 的 map 不能再開 BPF_F_MMAPABLE 或 freeze。
  • tracepoint / kprobe 等可被中斷打斷的程式類型須謹慎使用，否則可能死鎖。

7.1.4 RCU 與 BPF

BPF 程式在執行時通常已身處某種「非搶占（non-preemptible）」上下文，這天然提供類似 RCU read-side 的保護。但對明確標記為 RCU-protected 的 kernel pointer（KFunc 帶 KF_RCU），sleepable program 必須顯式呼叫 bpf_rcu_read_lock / unlock。

7.2 Pinning：跨 process 持久化

BPF 物件預設由 user space FD 持有，FD 關閉就會被 Kernel 回收。但很多場景需要：

  • Loader 啟動 BPF，把它放到背景，自己退出。
  • 多個獨立 process 共享同一個 BPF map。
  • K8s DaemonSet 重啟時，希望舊 BPF 不被卸載。

解法：把物件 pin 到 bpffs（一個特殊檔案系統，通常掛在 /sys/fs/bpf）。pin 之後 inode 持有 reference，物件存活到 unpin 為止。

(查詢 map)"] USER3["重啟後新 loader"] USER1 -->|"pin"| BPFFS BPFFS -. "持有 ref" .-> PROG USER1 -. "exit" .-> X((退出)) USER2 -->|"open"| BPFFS USER3 -->|"open existing"| BPFFS

7.2.1 Pin 的三種方式

方式觸發時機適用
BPF C 端宣告 __uint(pinning, LIBBPF_PIN_BY_NAME)載入時自動，路徑為 /sys/fs/bpf/<name>libbpf / cilium-ebpf 都支援
User space 顯式呼叫 pin API程式可控制路徑與時機動態決定要 pin 哪些

7.2.2 範例：在 Go 中 pin map

main.go
// 載入時建立物件，立刻 pin
if err := objs.OpenCount.Pin("/sys/fs/bpf/open_count"); err != nil {
    log.Fatalf("pin: %v", err)
}

// 之後其他 process 取回：
m, err := ebpf.LoadPinnedMap("/sys/fs/bpf/open_count", nil)
if err != nil { ... }

// 解除：
os.Remove("/sys/fs/bpf/open_count")

# 從 pin 取回 program 並 attach

# 移除
$ sudo rm /sys/fs/bpf/my_prog

7.3 Tail Call 與 BPF-to-BPF Call

BPF 程式單支有 1M instruction 上限，Verifier 對複雜邏輯的容忍度也有限。Kernel 提供兩種「拆解大程式」的機制：

7.3.1 Tail Call：跳轉而不返回

Tail call 透過 BPF_MAP_TYPE_PROG_ARRAY 取得目標 program，呼叫 bpf_tail_call 後跳走且不返回。原 program 的 stack frame 被重用，新程式從零開始執行。

flowchart LR A["Program A
main"] PA["PROG_ARRAY
map"] B["Program B
handle TCP"] C["Program C
handle UDP"] D["Program D
handle ICMP"] A -->|"bpf_tail_call idx=6"| PA PA -->|"idx=6 → B"| B PA -->|"idx=17 → C"| C PA -->|"idx=1 → D"| D
protocol dispatcher
struct {
    __uint(type, BPF_MAP_TYPE_PROG_ARRAY);
    __uint(max_entries, 256);
    __type(key, __u32);
    __type(value, __u32);
} progs SEC(".maps");

SEC("xdp")
int xdp_dispatcher(struct xdp_md *ctx) {
    __u8 proto = parse_proto(ctx);
    bpf_tail_call(ctx, &progs, proto);  // 不返回
    // 只有 tail call 失敗才會跑到這裡
    return XDP_PASS;
}

SEC("xdp")
int xdp_handle_tcp(struct xdp_md *ctx) {
    // ...
    return XDP_PASS;
}

限制：

  • 巢狀 33 層（5.10+）。
  • 不能與 BPF-to-BPF call 自由混用（5.10 後限制鬆綁）。
  • 每次 tail call 共用同一塊 stack（256 bytes 而非 512）。

7.3.2 BPF-to-BPF Function Call

從 4.16 起，BPF 程式可以呼叫同一個 ELF 中的 subprogram，行為與 C function call 一樣會返回。Verifier 對每個 subprogram 獨立分析。

把複雜邏輯拆成 subprogram
// 不是 SEC("...")，這是 subprogram
static __always_inline int parse_eth(void *data, void *end, __u16 *proto) {
    // ...
    return 0;
}

// __noinline 強制 verifier 視為獨立 subprogram
static __noinline int complex_logic(struct __sk_buff *skb) {
    // ... 大量邏輯 ...
    return 0;
}

SEC("tc")
int tc_main(struct __sk_buff *skb) {
    return complex_logic(skb);   // BPF-to-BPF call，會返回
}

用 __always_inline 或 __noinline 可以引導 clang 把函式 inline 或保留為獨立 subprogram。

7.4 Bounded Loop / bpf_loop / Iterator

BPF 對迴圈的支援經歷三代：

世代機制支援版本限制
1#pragma unroll所有版本常數迴圈
2Bounded loop（verifier 自動展開）5.3+編譯期可推算上限
3bpf_loop helper5.17+動態次數，但需 callback 寫法
4Iterator KFunc（bpf_iter_num_new...）6.4+最自然的寫法

7.4.1 三種寫法對比

傳統：常數迴圈 + unroll
__u32 sum = 0;
#pragma unroll
for (int i = 0; i < 16; i++) {  // 16 是常數
    sum += arr[i];
}
5.17+：bpf_loop helper（動態次數）
struct ctx {
    __u32 *arr;
    __u32 sum;
};

static long callback(__u32 idx, void *user_ctx) {
    struct ctx *c = user_ctx;
    c->sum += c->arr[idx];
    return 0;   // 0 = 繼續，1 = 提早結束
}

SEC("xdp")
int xdp_prog(...) {
    struct ctx c = { .arr = arr, .sum = 0 };
    bpf_loop(n, callback, &c, 0);  // n 可以是變數
    // c.sum 為結果
    return XDP_PASS;
}
6.4+：iterator KFunc
struct bpf_iter_num it;
int *v;

bpf_iter_num_new(&it, 0, n);     // 範圍 [0, n)
__u32 sum = 0;
while ((v = bpf_iter_num_next(&it))) {
    sum += arr[*v];
}
bpf_iter_num_destroy(&it);  // verifier 強制必須呼叫

7.5 BPF Timer

5.15 起 BPF 程式可以「排程未來執行」。在 map 內定義 struct bpf_timer，呼叫 bpf_timer_init + bpf_timer_set_callback + bpf_timer_start 即可。

用途：

  • 連線 idle timeout 自動清除。
  • 定期統計輸出（不需要 user space 主動 poll）。
  • 限速演算法（token bucket refill）。
每 5 秒清空計數
struct elem {
    __u64 count;
    struct bpf_timer t;        // 必須在 map value 內
};

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);
    __type(value, struct elem);
    __uint(max_entries, 1);
} m SEC(".maps");

static int reset_cb(void *map, __u32 *key, struct elem *e) {
    e->count = 0;
    bpf_timer_start(&e->t, 5000000000ULL, 0);   // 再排 5 秒
    return 0;
}

SEC("tracepoint/syscalls/sys_enter_openat")
int on_openat(void *ctx) {
    __u32 k = 0;
    struct elem *e = bpf_map_lookup_elem(&m, &k);
    if (!e) return 0;

    if (e->count == 0) {   // 首次：初始化 timer
        bpf_timer_init(&e->t, &m, CLOCK_MONOTONIC);
        bpf_timer_set_callback(&e->t, reset_cb);
        bpf_timer_start(&e->t, 5000000000ULL, 0);
    }
    __sync_fetch_and_add(&e->count, 1);
    return 0;
}

7.6 Resource Limit 與 RLIMIT_MEMLOCK

BPF 物件都會占用 locked memory（不能 swap 出去）。Kernel 5.11 之前，每個 BPF 物件都計入 process 的 RLIMIT_MEMLOCK，預設只有 64KB，幾乎做什麼都會撞牆。所以歷史上每個 BPF 工具開頭都要：

5.11 前必加
import "github.com/cilium/ebpf/rlimit"

func main() {
    if err := rlimit.RemoveMemlock(); err != nil {
        log.Fatal(err)
    }
    // ... 載入 BPF ...
}
手動調 ulimit
# 查
$ ulimit -l
65536

# 提高（需 root）
$ ulimit -l unlimited
$ sudo ./my-bpf-tool

5.11 起改為計入 cgroup memcg，RLIMIT_MEMLOCK 不再限制 BPF。新工具不再需要 RemoveMemlock，但保留也不影響——library 會自動偵測 Kernel 版本。

7.7 Trampolines（fentry / fexit）

傳統 kprobe 透過 INT3 軟中斷觸發 BPF 程式，每次呼叫成本約 100ns–1μs。fentry / fexit（5.5+）改用 BPF trampoline：在被 trace 函式的 prologue 直接 patch 一個 jump 到 BPF，成本接近一次 function call。

flowchart LR subgraph KPROBE["kprobe（傳統）"] K1["函式入口插 INT3"] K2["INT3 軟中斷"] K3["跳到 kprobe handler"] K4["觸發 BPF"] K5["返回函式繼續"] K1 --> K2 --> K3 --> K4 --> K5 end subgraph FENTRY["fentry（trampoline）"] F1["函式入口插 jump"] F2["跳到 BPF trampoline"] F3["觸發 BPF"] F4["返回函式繼續"] F1 --> F2 --> F3 --> F4 end

7.7.1 fentry / fexit 範例

trace tcp_v4_connect 進入與返回
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

SEC("fentry/tcp_v4_connect")
int BPF_PROG(on_connect_enter, struct sock *sk) {
    // 直接拿到 typed sock pointer（BTF）
    bpf_printk("connecting from pid %d", bpf_get_current_pid_tgid() >> 32);
    return 0;
}

SEC("fexit/tcp_v4_connect")
int BPF_PROG(on_connect_exit, struct sock *sk, int ret) {
    // fexit 可以拿到原函式的 return value！
    bpf_printk("connect returned %d", ret);
    return 0;
}

fentry / fexit 的優勢：

  • 呼叫成本約是 kprobe 的 1/10。
  • fexit 能拿到 return value，kretprobe 雖然也能但不穩定。
  • 透過 BTF，參數是 typed，不必走 PT_REGS_PARM*。
什麼時候不能用 fentry？

(1) 目標函式被 inline、(2) 目標函式被 livepatch、(3) Kernel 不支援 BTF（極舊版本）、(4) 目標函式不在 ftrace 白名單。撞到時 fallback 到 kprobe。

7.8 BPF Token（6.9+）

長久以來，載入 BPF 是一個 binary 權限：要嘛你有 CAP_BPF + CAP_PERFMON（基本上等同 root），要嘛完全不能。在多租戶環境（K8s 各個 tenant、CI runner、unprivileged container）這就尷尬：要給 XDP 程式跑，就得給整個 tenant 等同 root 的權限，違反最小權限原則。

BPF Token（Linux 6.9，Andrii Nakryiko 主導）解決這個問題：

  • 特權 process（如容器 runtime、systemd）建立一個 bpffs mount，並在其中設定精確的 delegation 規則：可以載入哪些 program type、建立哪些 map type、attach 到哪些 hook。
  • 該 bpffs FD 傳給 unprivileged process。
  • Unprivileged process 在 user namespace 內透過 BPF_TOKEN_CREATE 從 bpffs 取得 token FD。
  • 之後呼叫 BPF_PROG_LOAD 等命令時帶上 token FD，Kernel 只允許在 delegate 範圍內的操作。
sequenceDiagram participant P as Privileged Daemon
(systemd / runtime) participant K as Kernel participant U as Unprivileged Process
(in user namespace) P->>K: fsopen(bpf), fsconfig(delegate_cmds, delegate_progs) K-->>P: bpffs FD (with policy) P->>U: 透過 unix socket 傳 bpffs FD U->>K: bpf(BPF_TOKEN_CREATE, bpffs_fd) K-->>U: token_fd U->>K: bpf(BPF_PROG_LOAD, token_fd=token_fd) K->>K: 檢查 token 是否允許這個 program_type K-->>U: prog_fd（在 delegation 範圍內）

7.8.1 fsconfig 可設定的 delegation

選項意義
delegate_cmds=...允許的 BPF syscall 命令（PROG_LOAD、MAP_CREATE 等）
delegate_maps=...允許建立的 map 類型
delegate_progs=...允許載入的 program 類型
delegate_attachs=...允許的 attach type

7.8.2 實務意義

  • K8s tenant 限定載入 XDP：給某個 namespace delegate XDP-only 權限，租戶可以裝 eBPF 工具但不能 trace 別人。
  • CI runner 限定 socket_filter：build 流程跑 BPF tests 不需要完整 root。
  • 未來 unprivileged BPF 復活：歷史上因為 Spectre / 安全考量，unprivileged BPF 被 disable，BPF Token 提供細粒度替代。

7.9 Dynptr 深入

第 6 章 §6.5 已介紹過 Dynptr 的概念。本節補上幾個進階用法。

7.9.2 兩種讀取方式

read 與 slice 比較
struct bpf_dynptr ptr;
bpf_dynptr_from_xdp(ctx, 0, &ptr);

// 法 1：read 模式（複製到 buffer，安全但有複製成本）
__u8 hdr[14];
bpf_dynptr_read(hdr, sizeof(hdr), &ptr, 0, 0);

// 法 2：slice 模式（直接拿到指向原資料的指標，零複製）
struct ethhdr *eth = bpf_dynptr_slice(&ptr, 0, NULL, sizeof(*eth));
if (!eth) return XDP_PASS;
// 注意：slice 回傳的指標只在當下 dynptr 有效範圍內可用

// 法 3：rdwr slice（可寫的 slice）
struct ethhdr *eth_w = bpf_dynptr_slice_rdwr(&ptr, 0, scratch, sizeof(*eth_w));
eth_w->h_proto = htons(0x0800);    // 修改後可能需要 bpf_dynptr_write 寫回

7.10 AF_XDP（XSK）：Kernel Bypass

XDP 程式可以呼叫 bpf_redirect_map(&xskmap, queue_id, 0)，把封包送到一個特殊 socket family AF_XDP，user space 程式可從中拿到原始封包，跳過整個 kernel network stack。這就是 Linux 的 kernel-bypass 機制，與 DPDK 同等級但天然整合進 Kernel。

7.10.1 AF_XDP 架構

flowchart TB NIC["NIC RX queue"] XDP["XDP 程式
(in driver)"] XSKMAP["XSKMAP"] XSK["AF_XDP socket
(XSK)"] UMEM["UMEM
(user-space allocated buffer)"] RXR["RX ring"] TXR["TX ring"] FILLR["FILL ring"] COMPR["COMPLETION ring"] APP["User space app"] NIC --> XDP XDP -->|"bpf_redirect_map"| XSKMAP --> XSK XSK -. "write packet" .-> UMEM XSK --> RXR APP --> FILLR FILLR -. "提供空 chunk" .-> XSK RXR -. "通知有資料" .-> APP APP -. "讀取 UMEM chunk" .-> UMEM APP --> TXR TXR -. "傳送" .-> NIC NIC --> COMPR --> APP

7.10.2 四個 ring + UMEM

AF_XDP 的精髓在於 4 個 ring buffer + 1 個共享 memory（UMEM）：

Ring方向意義
FILLapp → kernel「這些 UMEM chunk 是空的，可以寫入封包」
RXkernel → app「這些 UMEM chunk 已寫入封包，可讀」
TXapp → kernel「請發送這些 UMEM chunk 內的封包」
COMPLETIONkernel → app「TX 完成的 chunk，可以再用」

UMEM 由 user space 配置一塊大記憶體，切成等大 chunk。所有封包都在 UMEM 內，Kernel 與 user space 透過 ring 傳遞 chunk descriptor，沒有任何複製。

7.10.3 三種模式

模式需求效能
Native zero-copyNIC driver 支援（mlx5、ixgbe、i40e、virtio-net 等）最佳，真正零複製
Native copyNIC driver 支援 XDP 但不支援 zero-copy有一次複製到 UMEM
Genericfallback 到 generic XDP（軟體模擬）最慢，調試用
AF_XDP vs DPDK 差異

DPDK 完全在 user space、自帶 driver；AF_XDP 仍透過 Kernel driver 但走 fast path。實務優勢：(1) 與 Kernel 共用 driver、不需獨佔網卡，(2) 支援多 process 共用，(3) 與 Linux 工具鏈整合（iptables、tc 仍能在 XDP_PASS 路徑運作）。代價是極限效能略低於純 DPDK，但對 95% 應用場景已足夠。

7.11 USDT：User Space 靜態 Tracepoint

USDT（User-level Statically Defined Tracing）是一種「應用程式作者預先定義的 trace 點」，原本由 Solaris DTrace 引入。Linux 的 SystemTap、bpftrace、bcc 都支援讀取 USDT，是觀測 PostgreSQL、MySQL、Java JVM、Python、Node.js、libvirt 等應用內部行為的標準方式。

7.11.1 USDT 與 uprobe 差異

面向uprobeUSDT
誰決定 trace 點BPF 工具作者（任意函式）應用程式作者預先放置
穩定性函式名變、簽名變就壞應用作者承諾穩定
是否需要 debuginfo需要（解析 symbol）不需要（用 ELF note section）
典型用途反向工程、底層除錯應用層觀測

7.11.2 應用程式如何放 USDT

在 C 應用埋 USDT
#include <sys/sdt.h>

void process_request(int req_id, const char *user) {
    // 應用程式預先定義的 trace 點
    DTRACE_PROBE2(myapp, request_start, req_id, user);

    // ... 處理邏輯 ...

    DTRACE_PROBE2(myapp, request_end, req_id, user);
}
BPF 端用 SEC("usdt/...")
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/usdt.bpf.h>

SEC("usdt/myapp:request_start")
int BPF_USDT(on_req_start, int req_id, const char *user) {
    bpf_printk("req=%d user=%s", req_id, user);
    return 0;
}

7.12 BPF Arena（6.9+）：BPF 第一個 Heap

到 6.8 為止，BPF 程式完全沒有「動態配置記憶體」的能力——所有資料結構都受限於 Map 預定義的 schema。Linux 6.9 引入 BPF_MAP_TYPE_ARENA，這是 BPF 史上第一次能在 BPF 內動態 allocate 記憶體。

7.12.1 Arena 的關鍵特性

  • Map 配置一塊線性記憶體區（最大可達數 GB），分成 4KB pages。
  • BPF 程式呼叫 bpf_arena_alloc_pages 取得 pages，bpf_arena_free_pages 釋放。
  • Arena 同時可以被 user space mmap，user 與 BPF 共用同一虛擬位址，零 syscall 互相讀寫。
  • BPF 端可以在 arena 內實作自訂 link list、binary tree、自訂 hashmap 等資料結構。
flowchart LR USER["User space
(mmap arena)"] ARENA[("BPF Arena
共享記憶體")] BPF["BPF Program"] ALLOC["bpf_arena_alloc_pages"] FREE["bpf_arena_free_pages"] USER -. "mmap" .-> ARENA BPF --> ALLOC --> ARENA BPF --> FREE BPF -. "指標讀寫" .-> ARENA

7.12.2 應用情境

  • Cilium 大型 connection tracking 表：原本要拼湊多種 map，現在可以實作自家結構。
  • BPF + user space 高頻交換大量資料：Arena mmap 後是 zero-syscall 的 shared memory。
  • 實作高階資料結構：BTree、跳表、自訂 LRU 替代演算法。

7.12.3 Arena 範例骨架

BPF Arena 用法概念
struct {
    __uint(type, BPF_MAP_TYPE_ARENA);
    __uint(map_flags, BPF_F_MMAPABLE);
    __uint(max_entries, 1 << 20);    // 4 GB（in 4KB pages）
} arena SEC(".maps");

SEC("syscall")
int alloc_node(void *ctx) {
    void *p = bpf_arena_alloc_pages(&arena, NULL, 1, NUMA_NO_NODE, 0);
    if (!p) return -ENOMEM;

    // p 是 arena 內的虛擬位址
    // 可以用普通 pointer 操作（注意是 arena 範圍內）
    *(int *)p = 42;

    // 釋放
    bpf_arena_free_pages(&arena, p, 1);
    return 0;
}
Arena 仍是新技術

Arena 6.9 才合併、語言 / 工具鏈支援還在持續成熟。實務上 cilium/ebpf 與 aya 都已支援，但範例不多、最佳實踐尚未沉澱。要嚐鮮的讀者建議盯緊 LWN 與 cilium blog。

7.13 本章小結

7.13.1 重點回顧

  1. Concurrency：per-CPU map、atomic builtin、spin lock 三種對策；場景對應方法。
  2. Pinning：把 BPF 物件 pin 到 bpffs，跨 process 持久化。
  3. Tail call：透過 PROG_ARRAY 跳到別支 program 不返回；BPF-to-BPF call 是傳統 function call 行為。
  4. 迴圈四代演進：unroll → bounded loop → bpf_loop → iterator KFunc。
  5. BPF Timer：在 Kernel 內排程延遲執行，無需 user space poll。
  6. RLIMIT_MEMLOCK：5.11 前必須處理，現代 Kernel 已自動。
  7. Trampolines（fentry/fexit）：取代 kprobe，10× 低成本，能拿到 typed 參數與 return value。
  8. BPF Token（6.9+）：細粒度權限委派，多租戶與 unprivileged BPF 的解法。
  9. Dynptr：變動長度資料的 verifier-friendly 操作。
  10. AF_XDP（XSK）：4 ring + UMEM 架構，Kernel-bypass 實作。
  11. USDT：應用程式預埋的穩定 trace 點。
  12. BPF Arena（6.9+）：BPF 第一個動態 heap。
