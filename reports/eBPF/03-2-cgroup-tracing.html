10.1 cGroup BPF 整體脈絡

傳統 Linux 對「限制某個容器的網路存取」這個需求，依賴 iptables、tc qdisc、network namespace 等多個元件拼湊。每個元件都有自己的 model 與限制，組合起來既複雜又脆弱。cGroup BPF把策略直接掛在 cgroup v2 階層上：

對某個 cgroup attach 一支 BPF 程式，該 cgroup 內的所有 process觸發網路 / socket / sysctl / device 操作時，BPF 程式會被執行並決定「允許 / 拒絕 / 修改」。

10.1.1 為何需要 cGroup BPF

傳統做法痛點cGroup BPF 解法
iptables 比對 process / cgroupiptables 規則是全機共用，匹配 cgroup 要寫複雜 mark程式直接綁在 cgroup 上，自然隔離
seccomp 過濾 syscall只能 allow/deny，無法改寫參數CGROUP_SOCK_ADDR 可改寫 IP/port
devices cgroup（v1）只能黑白名單無法基於行為動態判斷CGROUP_DEVICE 可程式化
sysctl 只能在 boot 時或 namespace 級設定無法做更精細控制CGROUP_SYSCTL 攔截寫入

10.1.3 cGroup BPF 與 cgroup v2 的關係

cGroup BPF 強烈推薦使用 cgroup v2（Linux 4.5+ 起，6.0+ 後幾乎是各發行版預設）。原因：

  • cgroup v2 採單一階層，BPF 程式 attach 點明確。
  • cgroup v1 各 controller 各有獨立階層，BPF 不易對齊。
  • K8s 1.25+ 預設使用 cgroup v2（cgroupfs / systemd driver）。
確認 cgroup v2
# 看是否掛載 v2（unified hierarchy）
$ mount | grep cgroup2

# 看當前 process 的 cgroup
$ cat /proc/self/cgroup
0::/user.slice/user-1000.slice/session-3.scope

# 列出某 cgroup 路徑下被 attach 的 BPF
$ sudo bpftool cgroup show /sys/fs/cgroup

10.2.2 範例：cGroup egress 計數

每個 cgroup 累計 egress bytes
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __type(key, __u32);
    __type(value, __u64);
    __uint(max_entries, 1);
} bytes SEC(".maps");

SEC("cgroup_skb/egress")
int count_egress(struct __sk_buff *skb) {
    __u32 zero = 0;
    __u64 *p = bpf_map_lookup_elem(&bytes, &zero);
    if (p) (*p) += skb->len;
    return 1;       // pass
}

char LICENSE[] SEC("license") = "GPL";
CGROUP_SKB 不能修改封包

它只能讀 skb 與決定 pass / drop。要改封包請用 tcx / XDP。CGROUP_SKB 的設計理念是「policy decision，不是 packet manipulation」。

10.4 CGROUP_SOCK_ADDR — Socket 位址操作

BPF_PROG_TYPE_CGROUP_SOCK_ADDR
分類
cGroup
觸發位置
process 呼叫 bind / connect / sendto / recvfrom / getsockname / getpeername
Attach types
cgroup/bind4/6、connect4/6、sendmsg4/6、recvmsg4/6、getsockname4/6、getpeername4/6
Context
struct bpf_sock_addr *（含 user_ip4/6、user_port、family、type、protocol）
Return values
0 = block syscall / 1 = allow（5.12+ 第 2 bit 表 bypass CAP_NET_BIND_SERVICE）
支援版本
4.17
典型場景
透明代理、DNS 攔截、port redirect、容器網路重寫

這是 cgroup BPF 中最強大的一個。它能改寫 process 的目的 IP/port，效果類似 iptables 的 DNAT，但精度到 process 級別。GitHub 的 deployment safety、Cilium 的 socket-LB 都靠它。

10.4.1 範例：DNS 重導

改寫所有 DNS 查詢的目的地
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

#define DNS_PROXY_IP   bpf_htonl(0x7F000001)   // 127.0.0.1
#define DNS_PROXY_PORT bpf_htons(5353)

SEC("cgroup/connect4")
int redirect_dns(struct bpf_sock_addr *ctx) {
    if (ctx->type != SOCK_DGRAM) return 1;     // 只攔 UDP
    if (ctx->user_port != bpf_htons(53)) return 1;

    ctx->user_ip4 = DNS_PROXY_IP;
    ctx->user_port = DNS_PROXY_PORT;
    return 1;
}

char LICENSE[] SEC("license") = "GPL";
為什麼比 iptables DNAT 強

iptables NAT 在封包出網卡之後才作用，且不知道 process 身分。CGROUP_SOCK_ADDR 在 process 呼叫 connect 的瞬間就改寫，knows the process，且不需任何 conntrack overhead。Cilium socket-LB（取代 kube-proxy）就是基於此。

10.8 完整實作範例：cGroup egress 黑名單

把第 10 章串起來，做一個能實際運行的「cgroup egress IP 黑名單」工具：對某個 cgroup 內所有 process 的 outgoing 連線，命中黑名單即 drop。

10.8.1 BPF C

cg_block.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

char LICENSE[] SEC("license") = "GPL";

#define ETH_P_IP 0x0800

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);     // IPv4 (network byte order)
    __type(value, __u32);
    __uint(max_entries, 4096);
    __uint(pinning, LIBBPF_PIN_BY_NAME);
} block_ip SEC(".maps");

SEC("cgroup_skb/egress")
int cg_block_egress(struct __sk_buff *skb) {
    if (skb->protocol != bpf_htons(ETH_P_IP))
        return 1;       // 只處理 IPv4

    // CGROUP_SKB 已經拿到完整 sk_buff，直接讀 IP header
    struct iphdr iph;
    if (bpf_skb_load_bytes(skb, 0, &iph, sizeof(iph)) < 0)
        return 1;

    if (bpf_map_lookup_elem(&block_ip, &iph.daddr))
        return 0;       // drop

    return 1;
}

10.8.2 Go user space（cilium/ebpf）

main.go
package main

import (
    "encoding/binary"
    "log"
    "net/netip"
    "os"
    "os/signal"
    "syscall"

    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/rlimit"
)

//go:generate go tool bpf2go -cc clang -target amd64,arm64 \
//   cgblock bpf/cg_block.c -- -I./bpf/headers

func main() {
    if len(os.Args) < 3 {
        log.Fatalf("usage: %s <cgroup-path> <ip>[,...]", os.Args[0])
    }
    cgPath := os.Args[1]
    ips := os.Args[2]

    if err := rlimit.RemoveMemlock(); err != nil { log.Fatal(err) }

    objs := cgblockObjects{}
    if err := loadCgblockObjects(&objs, nil); err != nil {
        log.Fatalf("load: %v", err)
    }
    defer objs.Close()

    // attach 到 cgroup
    l, err := link.AttachCgroup(link.CgroupOptions{
        Path:    cgPath,
        Attach:  ebpf.AttachCGroupInetEgress,
        Program: objs.CgBlockEgress,
    })
    if err != nil { log.Fatalf("attach: %v", err) }
    defer l.Close()

    // 加入黑名單
    for _, s := range splitCsv(ips) {
        addr, err := netip.ParseAddr(s)
        if err != nil || !addr.Is4() { continue }
        b := addr.As4()
        raw := binary.BigEndian.Uint32(b[:])
        if err := objs.BlockIp.Put(raw, uint32(1)); err == nil {
            log.Printf("blocked %s", s)
        }
    }

    sig := make(chan os.Signal, 1)
    signal.Notify(sig, os.Interrupt, syscall.SIGTERM)
    log.Printf("Attached to %s. Ctrl-C 結束。", cgPath)
    <-sig
}

func splitCsv(s string) []string {
    out := []string{}; cur := ""
    for _, r := range s {
        if r == ',' { out = append(out, cur); cur = ""; continue }
        cur += string(r)
    }
    if cur != "" { out = append(out, cur) }
    return out
}

10.10 第 10 章小結

  1. cGroup BPF 把網路與資源策略直接綁在 cgroup v2 階層，比 iptables/seccomp 更精準。
  2. 6 種 program type 涵蓋封包、socket 生命週期、socket 位址、socket option、device、sysctl。
  3. 最強大的是 CGROUP_SOCK_ADDR：能改寫 connect / bind 的目的位址，是 Cilium socket-LB 的基礎。
  4. cgroup v2 是現代環境的預設（K8s 1.25+），cGroup BPF 在其上發揮最大效益。
  5. systemd 的 IPAddressDeny=、Docker/containerd 的 device controller、Cilium 的 kube-proxy 替代方案，都靠 cGroup BPF。

11.2.1 KPROBE 的工作機制

kprobe 是動態探針：在指定 kernel function 入口（或退出）插一個軟中斷（INT3 on x86），中斷處理時執行 BPF 程式。優點是可以 trace 任何 kernel function；缺點是：

  • 每次呼叫成本約 100ns–1μs（軟中斷開銷）。
  • 函式被 inline 後就 trace 不到。
  • 函式名 / 簽名變動就壞，無 ABI 保證。
  • 取得參數要用 PT_REGS_PARM* 巨集，不是 typed。

11.2.2 ELF section 命名

kretprobe/<funcname>kernel function 退出
kprobe.multi/<pattern>multi-kprobe（5.18+）批次 attach 多支函式
ksyscall/<name>syscall wrapper（自動加 arch prefix）
uprobe/<path>:<funcname>user space function 進入
uretprobe/<path>:<funcname>user space function 退出
uprobe.multi/<path>:<pattern>multi-uprobe（6.6+）

11.2.3 範例：trace tcp_v4_connect 的 PID 與目的地

kprobe + kretprobe 配對
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __type(key, __u32);                 // PID
    __type(value, struct sock *);
    __uint(max_entries, 1024);
} sk_in_flight SEC(".maps");

SEC("kprobe/tcp_v4_connect")
int BPF_KPROBE(connect_enter, struct sock *sk) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;
    bpf_map_update_elem(&sk_in_flight, &pid, &sk, BPF_ANY);
    return 0;
}

SEC("kretprobe/tcp_v4_connect")
int BPF_KRETPROBE(connect_exit, int ret) {
    __u32 pid = bpf_get_current_pid_tgid() >> 32;
    struct sock **skp = bpf_map_lookup_elem(&sk_in_flight, &pid);
    if (!skp) return 0;

    if (ret == 0) {
        // 連線成功，讀取目的地
        __be32 daddr = BPF_CORE_READ(*skp, __sk_common.skc_daddr);
        __be16 dport = BPF_CORE_READ(*skp, __sk_common.skc_dport);
        bpf_printk("pid=%d daddr=0x%x dport=%d", pid, daddr, bpf_ntohs(dport));
    }
    bpf_map_delete_elem(&sk_in_flight, &pid);
    return 0;
}

}

11.3 TRACEPOINT — Kernel 預留的穩定 trace 點

BPF_PROG_TYPE_TRACEPOINT
分類
Tracing
觸發位置
Kernel 內預先標註的 trace 點
Context
tracepoint 自訂的 event 結構（void *，需自行 cast）

典型場景
追蹤 syscall、scheduler、IRQ、IO、netif 等預留事件

Kernel 開發者在程式碼中預先放置 TRACE_EVENT(...) 巨集，這些點稱為 tracepoint。它們有穩定的 schema（field 名稱與型別不會隨意變動），是觀測 Kernel 行為的建議起點。

    field:unsigned char common_flags;       offset:2;  size:1;

11.3.2 TRACEPOINT vs KPROBE

面向TRACEPOINTKPROBE
穩定性有 schema 保證，跨 Kernel 版本通常穩函式名/簽名變就壞
覆蓋面只有 Kernel 開發者預留的點幾乎所有 kernel 函式
參數讀取從 event 結構讀（typed）從 pt_regs 讀（手工解析）
性能較快（無軟中斷）有軟中斷開銷
建議有 tracepoint 就用它沒 tracepoint 才退而求其次

11.4 RAW_TRACEPOINT — 原始參數的 tracepoint

BPF_PROG_TYPE_RAW_TRACEPOINT
分類
Tracing
觸發位置
同 TRACEPOINT，但拿到的是原始參數陣列，沒做 schema 整理
Context
struct bpf_raw_tracepoint_args *
支援版本
4.17
典型場景
高頻 tracepoint，省去 schema 整理開銷

RAW_TRACEPOINT 比 TRACEPOINT 快約 30-50%（因為 Kernel 不需要把參數打包成 event 結構）。代價是參數需要自己 cast。BCC、libbpf 的高頻工具（如 execsnoop-bpfcc）多用此型。

11.5 PERF_EVENT — perf 計數取樣

BPF_PROG_TYPE_PERF_EVENT
分類

這是 Brendan Gregg 火焰圖工具的底層機制。每 N ms（或 N 個 hardware event）取一次當前堆疊，最後 aggregate 成火焰圖。用 BPF_MAP_TYPE_STACK_TRACE 儲存堆疊。

11.6 TRACING（fentry / fexit / tp_btf / iter）

BPF_PROG_TYPE_TRACING
分類
Tracing 現代
觸發位置
fentry / fexit（kernel function 入/出）/ tp_btf（BTF-typed tracepoint）/ fmod_ret / iter（迭代器）
Context
BTF-typed，直接讀 typed 參數
支援版本
5.5（fentry/fexit）/ 5.7（fmod_ret）/ 5.8（iter）

11.6.1 為何 TRACING 優於 KPROBE / TRACEPOINT

面向kprobefentry/fexit (TRACING)
呼叫成本~100ns（軟中斷）~10ns（trampoline jump）
參數型別raw pt_regsBTF-typed
fexit 拿 return valuekretprobe 不穩定原生支援，穩定
需要 BTF否是（5.5+ 標配）
現代 BPF tracing 的選擇順序
  1. 有 tracepoint → 用 tp_btf（TRACING 子類）
  2. 需要 trace 任意函式 + Kernel 5.5+ → 用 fentry / fexit
  3. 需要 trace 任意函式 + 老 Kernel → fallback 到 KPROBE
  4. 需要 trace user space → UPROBE / URETPROBE（目前無 fentry 等價物）

11.6.2 fentry / fexit 範例

用 fexit 取代 kretprobe
SEC("fentry/tcp_v4_connect")
int BPF_PROG(connect_enter, struct sock *sk) {
    // 直接拿 typed 參數，無需 BPF_CORE_READ
    bpf_printk("connect from pid %d", bpf_get_current_pid_tgid() >> 32);
    return 0;
}

SEC("fexit/tcp_v4_connect")
int BPF_PROG(connect_exit, struct sock *sk, int ret) {
    // fexit 額外拿到 return value
    bpf_printk("connect ret=%d daddr=0x%x", ret, sk->__sk_common.skc_daddr);
    return 0;
}

11.6.3 iter — 遍歷 Kernel 物件

TRACING 的 iter 子類是個特別的存在：它讓 BPF 程式作為「Kernel 物件迭代器的處理回呼」。常見用途：

  • SEC("iter/task")：遍歷系統內所有 task
  • SEC("iter/tcp")：遍歷所有 TCP socket
  • SEC("iter/bpf_map")：遍歷所有 BPF map
  • SEC("iter/cgroup")：遍歷 cgroup 階層

透過 seq_file 介面，user space 用 read 即可取得 BPF 程式對每個物件的處理結果。是 ss 等系統工具的次世代實作。

11.7 LSM 簡介（前情提要）

BPF_PROG_TYPE_LSM（5.7+）也屬於 tracing 大家族，但它有獨立角色：作為 Linux Security Module 的 hook，能阻止系統呼叫（return 非 0 即拒絕）。本書冊三第 12 章會專章討論。本節僅作前情提要。

11.9 第 11 章小結

  1. Tracing 類有 5 大 program type，各自對應不同 trace 機制與位置。
  2. TRACING（fentry/fexit/tp_btf）是現代首選，比 kprobe 快 10×，且參數 typed。
  3. 有 tracepoint 就用 tracepoint，沒有再考慮 kprobe；user space 一律 uprobe。
  4. RAW_TRACEPOINT 比 TRACEPOINT 略快但要自解析，高頻場景值得。
  5. PERF_EVENT 是 profiling 與火焰圖的底層機制，配合 STACK_TRACE map。
  6. LSM（第 12 章）也是 tracing 家族的一員，但具備阻止能力。
