Cloud-native 安全分四階段，eBPF 是 runtime 階段的核心技術：

20.1.1 為什麼 runtime 不能省

shift-left 抓不到的runtime 才能看到
0-day 漏洞（沒 CVE 編號）異常行為（從未見過的 syscall 序列）
合法工具被惡意使用（curl、wget、kubectl）誰跑了它、從哪個 container、做了什麼
Supply chain 攻擊（合法 image 被植入後門）image 行為與宣告不符
Container escape進程跨 namespace 的瞬間
Lateral movement（橫向移動）跨 pod / 跨 node 的可疑 connect

20.2 Falco / Tetragon / KubeArmor 定位對比

「觀測」與「阻擋」的差別

純觀測（observe）：發現異常就記錄、發告警，事件已經發生。
即時阻擋（enforce）：發現異常的瞬間就拒絕 syscall 或 kill process，傷害不發生。
但 enforce 風險高：誤判會造成業務中斷。實務上通常先 observe → 確認規則無誤 → 切到 enforce。

20.3.1 範例 1：監視寫入 /etc/passwd

monitor-passwd.yaml
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "monitor-passwd-write"
spec:
  kprobes:
  - call: "security_file_permission"
    syscall: false
    return: false
    args:
    - index: 0
      type: "file"
    - index: 1
      type: "int"
    selectors:
    - matchArgs:
      - index: 0
        operator: "Equal"
        values:
        - "/etc/passwd"
        - "/etc/shadow"
      - index: 1
        operator: "Mask"
        values:
        - "2"          # MAY_WRITE

20.3.2 觀察事件

即時看 events
# 套用 policy
$ kubectl apply -f monitor-passwd.yaml

# 即時觀察
$ kubectl exec -n tetragon ds/tetragon -c tetragon -- tetra getevents -o compact

$ kubectl exec -it suspicious-pod -- sh -c 'echo "hacker:x:0:0::/root:/bin/bash" >> /etc/passwd'

# Tetragon 端會輸出

🚧 file_permission default/suspicious-pod /etc/passwd MAY_WRITE
💥 exit    default/suspicious-pod /bin/sh -c ... 0

20.4 進階 selectors 與 in-kernel filtering

Tetragon 一個關鍵設計：filtering 在 kernel 內完成。意思是「不關心的事件不會送到 user space」，避免 event flood。

20.4.1 selectors 的 4 大類

selector作用範例
matchArgs檢查 syscall / function 參數第 0 個 arg 的 path 等於 "/etc/shadow"
matchBinaries檢查觸發的 binary path不是 sshd 才觸發
matchPIDs檢查 PID 範圍排除 PID 1（init）
matchNamespaces檢查 namespace（K8s pod ns 或 pid/net/mnt ns）非預期的 ns ID
matchCapabilities檢查 process capability set有 CAP_SYS_ADMIN 才觸發
matchActions觸發動作（observe / sigkill / override）見 §20.5

20.4.2 範例 2：除了 sshd 外不准讀 /root/.ssh/id_rsa

protect-ssh-key.yaml（LSM 版）
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "protect-ssh-key"
spec:
  lsmHooks:
  - hook: "file_open"
    args:
    - index: 0
      type: "file"
    selectors:
    - matchBinaries:
      - operator: "NotIn"
        values:
        - "/usr/sbin/sshd"
        - "/usr/bin/ssh"
      matchArgs:
      - index: 0
        operator: "Equal"
        values:
        - "/root/.ssh/id_rsa"
      matchActions:
      - action: Sigkill

20.5 Enforcement：sigkill、override

action效果適用
Post（預設）送 event 到 user space純觀測
Sigkill對 process 送 SIGKILL觀察到瞬間就殺
Override讓 syscall 直接回傳指定錯誤碼（不執行原邏輯）讓應用「以為失敗」，常見回傳 -EPERM
FollowFD / UnfollowFD追蹤 fd 的後續使用對 file 操作做精細追蹤
NoPost不送 event（只用於 filter）降噪

20.5.1 Override vs Sigkill

兩種 enforce 的差別

Sigkill：殺死整個 process。當 process 在做正常工作時被殺，影響面廣。
Override：只讓那個 syscall 失敗，process 繼續跑、它會以為是普通的權限錯誤。對應用比較「友善」，但若 process 不處理錯誤就會崩潰。
實務上：對非法 binary 用 Sigkill；對合法應用偶發違規用 Override。

20.6 LSM 路徑：避免 TOCTOU

TOCTOU（Time-Of-Check-Time-Of-Use）是傳統 syscall-based 工具的死穴：

sequenceDiagram participant ATK as Attacker participant K as Kernel participant TOOL as 安全工具
(kprobe-only) participant FS as Filesystem ATK->>K: open("/tmp/safe", O_RDONLY) K->>TOOL: kprobe sys_open: filename ptr TOOL->>K: 讀 filename "/tmp/safe" → OK Note over ATK: 同時間 attacker 改寫
filename buffer K->>FS: 真正解析 filename → 變成 "/etc/shadow" FS-->>ATK: 回傳 /etc/shadow 內容

LSM hook 在kernel 已經把參數複製到 kernel space + 解析完路徑之後才觸發，無 TOCTOU window。這是 BPF LSM（第 12 章）作為 enforcement 機制的核心優勢。

機制TOCTOU 風險
Syscall kprobe（讀 user pointer）有，attacker 可在 kprobe 與真正 use 之間改值
seccomp（採用 syscall args, BPF 看 user pointer）有同類風險（除非用 SECCOMP_RET_USER_NOTIF）
LSM hook（讀 kernel struct）無，參數已驗證過

20.7 經典威脅模式偵測 6 例

20.7.1 Container escape via /proc/sys/kernel/core_pattern

Pre-2024 經典攻擊：在 container 裡寫 /proc/sys/kernel/core_pattern 為 |/tmp/exploit %P，當 host 上有 process crash 時 host 會執行容器準備的 binary。LSM hook file_open + matchArgs path == "/proc/sys/kernel/core_pattern" + Sigkill。

20.7.2 Cryptominer 偵測

抓 execve 的 binary path 含 xmrig / kinsing 等已知挖礦程式名，或連續高 CPU + 連線到挖礦池 port。Tetragon kprobe + matchBinaries Postfix 比對。

20.7.3 Reverse shell 偵測

detect-reverse-shell.yaml
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "detect-reverse-shell"
spec:
  kprobes:
  # 偵測 dup2(socket_fd, 0|1|2) — shell 把 stdin/stdout 接到 socket 的經典 pattern
  - call: "sys_dup2"
    syscall: true
    args:
    - index: 0
      type: "fd"
    - index: 1
      type: "int"
    selectors:
    - matchArgs:
      - index: 1
        operator: "Equal"
        values: ["0", "1", "2"]
      matchBinaries:
      - operator: "In"
        values: ["/bin/sh", "/bin/bash", "/bin/dash"]

20.7.4 敏感檔案存取 fan-out

同一 process 短時間內 open 大量敏感檔案（/etc/shadow、/root/.ssh/*、/etc/kubernetes/admin.conf），通常是 reconnaissance。BPF map 計數 + 閾值告警。

20.7.5 PrivEsc：setuid root

觀察 commit_creds kprobe，攔截 process 的 effective uid 從非 0 變 0。

20.7.6 Network exfiltration

容器對外連線到非預期 IP / port。Tetragon + CiliumNetworkPolicy 雙保險。

20.8 Falco 補充：規則與 sidekick

Falco 的優勢是規則庫成熟。falco-rules（與 stable rules / incubating rules）已有 200+ 條，涵蓋大多數 MITRE ATT&CK 對 cloud-native 的對應。

falco rule 範例
- rule: Detect crypto mining
  desc: detect cryptocurrency miners
  condition: spawned_process and proc.name in (xmrig, ethminer, t-rex, kinsing)
  output: >
    Cryptocurrency miner detected
    (user=%user.name command=%proc.cmdline container=%container.name image=%container.image.repository)
  priority: CRITICAL
  tags: [process, mitre_execution]

20.8.1 Falco Sidekick

Falco 本身只負責偵測 + 寫 stdout。Falco Sidekick 是 forwarder：把 events 轉發到 100+ 種後端（Slack、PagerDuty、Splunk、ES、Loki、SIEM、SNS、Webhook）。

20.10 第 20 章小結

  1. Runtime 安全是 cloud-native 安全的最後一道防線，shift-left 抓不到 0-day 與行為異常。
  2. 三家主流 eBPF 安全工具：Falco（規則庫成熟）/ Tetragon（觀測+enforce 並重）/ KubeArmor（policy-first LSM）。
  3. Tetragon TracingPolicy 由 hook + args + selectors + actions 組成；selectors 在 kernel 內完成 filtering，避免 event flood。
  4. Enforcement 兩主軸：Sigkill（殺 process）與 Override（讓 syscall 失敗）。實務先觀測 → 確認 → 切 enforce。
  5. LSM hook 避免 TOCTOU，是真正可靠的 enforcement 點。
  6. 典型威脅模式 6 例：container escape、cryptominer、reverse shell、sensitive file fan-out、privilege escalation、exfiltration。
  7. Events 透過 perf ring buffer → agent → aggregator → SIEM 流動，最終呈現於 SOC dashboard。

21.1 BPF 工具的 K8s 部署慣例

BPF 是每個 node 一份的東西（kernel 屬於 node），所以 BPF 工具一律用 DaemonSet 部署。標準骨架：

標準 BPF DaemonSet 骨架
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: my-bpf-agent
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: my-bpf-agent
  template:
    metadata:
      labels:
        app: my-bpf-agent
    spec:
      hostPID: true            # 看到 host 上所有 process
      hostNetwork: true        # 看到 host 上所有 network ns
      serviceAccountName: my-bpf-agent
      tolerations:
      - operator: Exists       # 容忍所有 taint，確保每個 node 都跑
      containers:
      - name: agent
        image: ghcr.io/me/my-bpf-agent:v1.0.0
        securityContext:
          privileged: true     # 大部分舊式 BPF 工具還是 privileged
          # 或更細粒度（推薦）：
          # capabilities:
          #   add: ["BPF", "PERFMON", "SYS_RESOURCE", "NET_ADMIN", "SYS_ADMIN"]
        volumeMounts:
        - name: bpffs
          mountPath: /sys/fs/bpf
          mountPropagation: Bidirectional
        - name: cgroup
          mountPath: /sys/fs/cgroup
          readOnly: true
        - name: kernel-debug
          mountPath: /sys/kernel/debug
          readOnly: false
        - name: btf
          mountPath: /sys/kernel/btf
          readOnly: true
        - name: proc
          mountPath: /host/proc
          readOnly: true
      volumes:
      - name: bpffs
        hostPath:
          path: /sys/fs/bpf
          type: DirectoryOrCreate
      - name: cgroup
        hostPath:
          path: /sys/fs/cgroup
      - name: kernel-debug
        hostPath:
          path: /sys/kernel/debug
      - name: btf
        hostPath:
          path: /sys/kernel/btf
      - name: proc
        hostPath:
          path: /proc

21.1.1 為何需要 hostPID / hostNetwork

選項用途替代
hostPID: true看到 host 上所有 process（trace 任意 pod 內 process）無實質替代；agent 必須這樣設
hostNetwork: true能 attach XDP / tcx 到 host interface、看 host 完整網路 ns有些 user space agent 可不用，但 BPF 抓網路必要

21.2 SecurityContext 與 capabilities

21.2.1 必要 capabilities 對照

傳統 privileged: true 等於「所有 caps 開啟」，相當於 root。現代趨勢是給最小集合：

Capability用途BPF 工具是否需要
CAP_BPF呼叫 bpf() syscall（5.8+ 拆出）必要
CAP_PERFMONperf event、tracepoint、kprobe（5.8+ 拆出）多數 tracing 工具需要
CAP_NET_ADMINattach XDP、tc、cgroup_skb網路 BPF 需要
CAP_SYS_RESOURCE調整 RLIMIT_MEMLOCK（5.11+ 不需要）5.10 以下 fallback 用
CAP_SYS_ADMIN萬用槍（loading kernel module 等）5.8 以前舊環境，現代避免
CAP_SYS_PTRACE讀 /proc/[pid]/maps 等敏感資訊profiler 需要

21.2.2 5.8+ 推薦 caps 組合

最小化 capabilities
securityContext:
  privileged: false
  runAsNonRoot: false       # 仍需 root（多數 BPF 工具）
  runAsUser: 0
  capabilities:
    drop: ["ALL"]
    add:
      - "BPF"               # 5.8+ 必須
      - "PERFMON"           # 5.8+ tracing 用
      - "NET_ADMIN"         # 網路類用
      - "SYS_PTRACE"        # 讀 /proc 用
  seccompProfile:
    type: RuntimeDefault    # 仍能用大多數 BPF 場景

21.3 必要的 volume mounts

Mount路徑用途
bpffs/sys/fs/bpfpin BPF 物件、跨 process 共享
btf/sys/kernel/btf讀 vmlinux BTF 做 CO-RE
cgroup/sys/fs/cgroupcgroup BPF attach 點 + cgroup 資訊
kernel-debug/sys/kernel/debugtracing 子系統，bpf_trace_printk
proc/procprocess info、namespace 路徑
kernel-headers（如需 runtime compile）/usr/src/... + /lib/modulesBCC 需要；CO-RE 工具不需要
CO-RE 工具的 mounts 大幅簡化

用 libbpf-tools / cilium-ebpf / aya 寫的 CO-RE 工具，不需要 kernel headers，也不需要 runtime compile 工具鏈。docker image 從 BCC 時代的 100+ MB 降到 20 MB 以下。

21.4 OpenShift SCC 與 PSA

21.4.1 OpenShift SCC（Security Context Constraint）

OpenShift 預設禁止 privileged 容器。要部署 BPF 工具需要明確授予 SCC：

授予 privileged SCC
# 1) 建立 ServiceAccount
$ oc create serviceaccount my-bpf-agent -n kube-system

# 2) 把 privileged SCC 綁到 ServiceAccount
$ oc adm policy add-scc-to-user privileged \
    -z my-bpf-agent -n kube-system

# 3) 確認
$ oc get scc privileged -o yaml | grep my-bpf-agent

# 也可以用 PolicyBinding（更精細）
$ oc create rolebinding bpf-scc-binding \
    --clusterrole=system:openshift:scc:privileged \
    --serviceaccount=kube-system:my-bpf-agent

21.4.2 Pod Security Admission（K8s 1.25+）

K8s 內建的 PSA 取代了 PSP。BPF 工具需要 privileged profile：

namespace 加標籤
# 對 BPF 工具的 namespace 標記為 privileged 等級
apiVersion: v1
kind: Namespace
metadata:
  name: my-bpf-system
  labels:
    pod-security.kubernetes.io/enforce: privileged
    pod-security.kubernetes.io/audit: privileged
    pod-security.kubernetes.io/warn: privileged

21.5 BPF Token：unprivileged BPF 的未來

傳統 BPF 工具必須 root + privileged。BPF Token（Kernel 6.9+）是新的權限模型：

管理員建立一個 BPF Token（pin 在 bpffs），授予「載入特定 program type / 使用特定 helper / 建立特定 map type」的子集權限。
非 root user 在非 init userns 中拿到 token fd，就能載入限定範圍的 BPF，不需要 CAP_BPF / CAP_PERFMON。

21.5.1 工作流程

flowchart LR ADMIN["叢集管理員
(root)"] BPFFS["bpffs:
/sys/fs/bpf/tokens/xdp"] POD["unprivileged pod
(non-root)"] K["Kernel"] ADMIN -->|"BPF_TOKEN_CREATE +
限制範圍"| BPFFS POD -->|"bpf_token_create
從 bpffs 取 fd"| BPFFS BPFFS -->|"token fd"| POD POD -->|"PROG_LOAD +
token_fd"| K K -->|"驗證權限子集"| POD

21.5.2 K8s 上的應用前景

2026 年 BPF Token 仍在 stabilize，但已能看到應用方向：

  • Multi-tenant 叢集：每個租戶能用自己的 BPF profiler，僅授予 perf_event sampling 範圍。
  • Confidential workload：BPF agent 不需 host root，只需 token 限定的權限。
  • CI/CD pipeline：開發者能在 namespace 內部署 BPF 工具測試，不必拿到叢集 admin。

21.6 升級策略：rolling update 與 hot reload

21.6.1 標準 DaemonSet rolling update 的痛點

BPF DaemonSet pod 重啟期間，該 node 上「BPF 程式 detach → 新 pod 起來 → 重新 attach」有 packet drop window。對於關鍵元件（Cilium、kube-proxy 替代）這個 window 可能造成業務中斷。

21.6.2 解法：bpffs pin + LINK_UPDATE

sequenceDiagram participant V1 as Pod v1 participant FS as bpffs participant K as Kernel participant V2 as Pod v2 V1->>K: load BPF + create link V1->>FS: pin program + link Note over V1,FS: 即使 pod 重啟，bpffs 仍持有引用 V1->>V1: SIGTERM V1-->>K: pod 退出，但 program 仍 alive (pinned) Note over K: 流量正常處理（無 drop） V2->>FS: 取回 pinned link fd V2->>K: BPF_LINK_UPDATE 換新 program Note over K: 原子替換，無 drop V2->>FS: 替換 pinned program V2->>V2: 接管 daemon 工作

關鍵動作：

  1. v1 把 program 與 link pin 到 bpffs。
  2. v1 SIGTERM 時不 close link fd（讓它被 bpffs 引用）。
  3. v2 起來，從 bpffs 取回 link fd。
  4. v2 載入新 program，用 BPF_LINK_UPDATE 原子替換。
  5. 整個過程無 detach 空檔。

Cilium 的 hubble、cilium-agent、cilium-envoy 都採用這個模式，能做到「升級期間零封包丟失」。

21.7 ConfigMap-driven config 與 reload

BPF agent 的 policy / threshold / 黑名單 通常是動態的。標準做法是把資料放 ConfigMap，agent watch 後寫進 BPF map。

flowchart LR OPS["Ops 編輯
kubectl apply -f cm.yaml"] CM["ConfigMap"] INF["agent watch"] AGENT["BPF agent"] MAP["BPF Map
(blocklist / threshold)"] KERN["Kernel BPF program"] OPS --> CM CM -->|"informer event"| INF INF --> AGENT AGENT -->|"map update"| MAP MAP -. "即時生效" .-> KERN

這樣不重啟 BPF program 就能更新策略。是 production-grade BPF 工具的標準做法。

21.8 監控 BPF agent 自身健康

BPF agent 也是 production 服務，需要 SRE 級監控。常見指標：

指標意義告警閾值（範例）
BPF program run_count rate每秒觸發次數突降 → BPF 可能 detach
BPF program run_time_ns avg每次執行平均耗時> 1μs → policy 過於複雜
map memlock 使用率BPF map 記憶體佔用> 80% → 需擴容
events/sec 上送產生的事件率突高 → 攻擊或 sampling 失靈
perf ring buffer drops來不及消費被丟棄> 0 → user space 慢
verifier 載入失敗次數policy 載入失敗突增 → 規則錯誤或 Kernel 變動

21.8.1 暴露 metrics

用 cilium/ebpf info API 取得 stats
info, err := objs.MyProg.Info()
if err == nil {
    runCount, ok := info.RunCount()
    runTime, ok2 := info.Runtime()
    if ok && ok2 {
        // 暴露給 Prometheus
        bpfRunCount.WithLabelValues("my_prog").Set(float64(runCount))
        bpfRunTimeNs.WithLabelValues("my_prog").Set(float64(runTime.Nanoseconds()))
    }
}

21.9 CIS Benchmark 對應

CIS Kubernetes Benchmark 針對 K8s 安全性的常見控制項中，與 BPF 工具部署直接相關的：

CIS 控制項BPF 工具影響處理方式
5.2.1 minimize privileged containersBPF 工具一般 privileged限定 namespace、用 PSA 例外、長期遷移到 BPF Token
5.2.2 minimize hostPIDBPF tracing 需要同上，用 namespace 隔離
5.2.4 minimize hostNetworkBPF 網路工具需要同上
5.2.7 minimize NET_RAW不需要明確 drop NET_RAW
5.7.x 一般 PSP / PSA用 privileged profile標籤明確

CIS audit 看到 BPF 工具用 privileged 通常會 flag。實務上要附說明：「BPF 工具是核心級觀測 / 安全工具本身，需要 BPF + PERFMON + NET_ADMIN caps。已用 namespace 隔離 + 唯一 ServiceAccount + image 簽章 + 規則 GitOps 化來控制風險。」這是業界常見答案，多數 audit 接受。

21.10 第 21 章小結

  1. BPF 工具一律用 DaemonSet 部署，配 hostPID + hostNetwork。
  2. SecurityContext 慣例：5.8+ 用 BPF + PERFMON + NET_ADMIN，避免 privileged 全開。
  3. 必要 mounts：bpffs / btf / cgroup / kernel-debug / proc。CO-RE 工具不需 kernel headers。
  4. OpenShift 用 SCC 授權；K8s 1.25+ 用 PSA privileged profile。
  5. BPF Token（6.9+）是 unprivileged BPF 的未來：管理員預先發 token，非 root pod 取 token 後可載入限定 BPF。
  6. 升級用 bpffs pin + LINK_UPDATE 達到零 packet drop。
  7. Policy 動態化用 ConfigMap → BPF map，不重啟 program。
  8. 監控 BPF agent 自身：run_count / run_time_ns / memlock / ring buffer drops / verifier 失敗次數。
  9. CIS audit 對 BPF 工具的 privileged 通常需附說明，已是業界常見實務。
