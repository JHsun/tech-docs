14.2 BPF_PROG_LOAD 全攻略

BPF_PROG_LOAD 是所有 cmd 中最複雜的——它觸發 Verifier、CO-RE relocation、JIT 三件大事。理解它的 attr 欄位等同理解 BPF 載入的全貌。

14.2.1 union bpf_attr 中與 PROG_LOAD 相關的欄位

欄位意義誰會填
prog_typeprogram type（XDP、KPROBE、TRACEPOINT...）必填
insn_cnt / insnsBPF instruction 陣列必填
license授權字串（必須 GPL 相容才可用部分 helper）必填
log_levelverifier log 詳細度（0=無、1=錯誤、2=指令、4=stats）除錯時填
log_buf / log_sizeverifier log 輸出緩衝同上
kern_versionkprobe 程式預期的 Kernel 版本（4.18 後對多數 program type 取消檢查）較舊 kprobe
prog_flagsflags：BPF_F_STRICT_ALIGNMENT、BPF_F_ANY_ALIGNMENT、BPF_F_TEST_RND_HI32、BPF_F_SLEEPABLE...進階情境
prog_name顯示名稱（最多 16 字元）建議填
prog_ifindexHW offload 用的 ifindexSmartNIC offload
expected_attach_type預期的 attach type（影響 verifier 對 helper 與 return 的檢查）多數 program 必填
prog_btf_fd同時提交的 BTF 物件 FDCO-RE 程式必填
func_info_rec_size / func_infoBTF 函式 metadata（subprogram 對應）libbpf / cilium-ebpf 自動處理
line_info_rec_size / line_infoBTF 行號 metadata（除錯用）同上
core_relos / core_relo_rec_sizeCO-RE relocation 資訊同上（第 15 章詳解）
attach_btf_idfentry/fexit/LSM/tp_btf 的目標 BTF IDtracing program
attach_prog_fdEXT (freplace) 的目標 programEXT
attach_btf_obj_fd跨 kernel module 的 BTF 物件module attach
fd_arraymap FD 陣列（BPF_PSEUDO_MAP_IDX 用）libbpf 自動處理
prog_token_fdBPF Token FD（6.9+）受限權限載入

14.2.2 PROG_LOAD 內部流程

sequenceDiagram participant U as User space (loader) participant K as Kernel participant V as Verifier participant C as CO-RE relocator participant J as JIT U->>K: bpf(PROG_LOAD, attr) K->>K: 複製 attr 到 kernel 空間 K->>K: 配置 bpf_prog 結構 K->>V: 開始驗證 V->>V: Layer 1: CFG 檢查 V->>V: Layer 2: 模擬執行 + reg state tracking V->>V: Layer 3: helper / context 約束 V->>C: 對 instruction 套用 CO-RE relocation C->>C: 比對 BTF，改寫 offset / type C-->>V: relocated instructions V-->>K: 通過 K->>J: 編譯為原生機器碼 J-->>K: 完成 K-->>U: 回傳 prog_fd

14.2.3 經典載入錯誤排查

錯誤常見原因解法
EINVAL + verifier log程式違反 verifier 規則讀 verifier log（§14.2.4）
EACCES權限不足用 root 或 setcap CAP_BPF
ENOMEMlocked memory 用盡（<5.11 Kernel）RLIMIT_MEMLOCK unlimit
EAGAINverifier 受 signal 中斷retry
E2BIG程式 instruction 數超 1M用 tail call 或 BPF-to-BPF 拆解

14.2.4 取得詳細 Verifier log

cilium/ebpf 取得 verifier log
opts := &ebpf.CollectionOptions{
    Programs: ebpf.ProgramOptions{
        LogLevel:    ebpf.LogLevelInstruction | ebpf.LogLevelStats,
        LogSizeStart: 64 * 1024 * 1024,
    },
}
if err := loadObjs(&objs, opts); err != nil {
    var ve *ebpf.VerifierError
    if errors.As(err, &ve) {
        fmt.Printf("verifier rejected:\n%+v\n", ve)
    }
    log.Fatal(err)
}
aya 取得 verifier log
use aya::{EbpfLoader, VerifierLogLevel};

let mut bpf = EbpfLoader::new()
    .verifier_log_level(VerifierLogLevel::DEBUG | VerifierLogLevel::STATS)
    .load_file("/path/to/program.o")?;
libbpf 直接呼叫 syscall
#include <linux/bpf.h>
#include <sys/syscall.h>
#include <unistd.h>

char log_buf[64 * 1024 * 1024];
union bpf_attr attr = {
    .prog_type = BPF_PROG_TYPE_TRACEPOINT,
    .insns     = (__u64)insns,
    .insn_cnt  = ARRAY_SIZE(insns),
    .license   = (__u64)"GPL",
    .log_level = 2,                     // 1=err, 2=instr, 4=stats
    .log_buf   = (__u64)log_buf,
    .log_size  = sizeof(log_buf),
};
int prog_fd = syscall(__NR_bpf, BPF_PROG_LOAD, &attr, sizeof(attr));
if (prog_fd < 0) {
    fprintf(stderr, "verifier log:\n%s\n", log_buf);
}

14.3 Map 操作命令

第 4 章已介紹 user space 與 BPF 兩條 map 存取路徑。本節聚焦 user space 端的 syscall 細節，特別是批次操作。

14.3.1 單條 vs 批次 lookup

大量資料時，單條 lookup 每 entry 一次 syscall 過於耗費。BPF_MAP_LOOKUP_BATCH（5.6+）讓你一次取多筆：

cilium/ebpf 批次讀
// 一次讀 1024 筆
const batch = 1024
keys := make([]uint32, batch)
vals := make([]uint64, batch)
var cursor ebpf.MapBatchCursor

for {
    n, err := m.BatchLookup(&cursor, keys, vals, nil)
    if err != nil && !errors.Is(err, ebpf.ErrKeyNotExist) {
        return err
    }
    for i := 0; i < n; i++ {
        fmt.Printf("key=%d val=%d\n", keys[i], vals[i])
    }
    if errors.Is(err, ebpf.ErrKeyNotExist) {
        break   // map 已 iterate 完
    }
}

14.3.2 BPF_MAP_FREEZE：建好後變唯讀

常見場景：user space 建立 array 載入 config 後 freeze，BPF 程式只讀不寫，避免後續手滑改錯。Verifier 在 frozen map 上會把 value 視為 const，啟用更積極的優化。

14.4 BPF_LINK_CREATE：現代 attach 機制

過去 BPF 程式 attach 透過 BPF_PROG_ATTACH（cgroup）、netlink（XDP / tc）、perf event（kprobe / tracepoint）等多套機制，沒有統一介面。BPF_LINK_CREATE（5.7+）統一了所有 attach 路徑：

flowchart LR OLD["傳統路徑（碎片化）"] NEW["BPF_LINK_CREATE
(統一)"] OLD --> O1["BPF_PROG_ATTACH
(cgroup / sockmap)"] OLD --> O2["netlink IFLA_XDP
(XDP)"] OLD --> O3["perf_event_open + ioctl
(kprobe / tracepoint)"] OLD --> O4["setsockopt
(socket filter)"] NEW --> N1["回傳 link_fd
(統一物件)"] N1 --> N2["可 BPF_LINK_UPDATE
原子替換"] N1 --> N3["可 BPF_LINK_DETACH"] N1 --> N4["可 BPF_OBJ_PIN"]

14.4.1 Link 的優勢

  • 統一物件：所有 attach 結果都是 link FD，FD 關閉即 detach。
  • 原子更新：BPF_LINK_UPDATE 可在不中斷的情況下替換 program（zero-downtime）。
  • 可 pinning：link 本身能釘到 bpffs，重啟 loader 不影響 attach。
  • 可發現：用 BPF_LINK_GET_NEXT_ID 列出系統內所有 link。

14.4.2 LINK_CREATE 的 attr 變化最大

不同 program type 用不同欄位。常見組合：

Program Type關鍵欄位
XDPtarget_ifindex + flags（DRV_MODE / SKB_MODE / HW_MODE）
cgrouptarget_fd（cgroup directory FD）+ attach_type
tracing (fentry / fexit / LSM)target_btf_id
tracepointperf_event sub-struct
kprobe.multikprobe_multi sub-struct（syms / addrs / cookies）
uprobe.multiuprobe_multi sub-struct（path / offsets / cookies）
SK_LOOKUP / FLOW_DISSECTORtarget_fd（netns FD）
iteriter_info（指向 union bpf_iter_link_info）
tcx (6.6+)target_ifindex + relative_fd / relative_id + flags

14.5 BPF_PROG_TEST_RUN：在 Kernel 內 dry-run

BPF 程式很難用傳統 unit test 框架測——它得跑在 Kernel。BPF_PROG_TEST_RUN（4.12+，後改名 BPF_PROG_RUN）讓你在 user space 提供假 context + 封包資料，請 Kernel 在受控環境下執行 BPF 程式，回傳結果。

14.5.1 支援的 program type

  • XDP（含 live frame mode，6.0+ 可真正注入封包到網路堆疊）
  • SCHED_CLS（tc）
  • SOCKET_FILTER
  • RAW_TRACEPOINT
  • FLOW_DISSECTOR
  • SOCK_OPS
  • SK_LOOKUP
  • SYSCALL（這是它唯一的執行方式！）

14.5.2 測試 XDP 的範例

cilium/ebpf 跑 XDP test
// 準備一個假封包：Ethernet + IPv4 header
pkt := []byte{
    /* eth dst */ 0xff, 0xff, 0xff, 0xff, 0xff, 0xff,
    /* eth src */ 0x01, 0x02, 0x03, 0x04, 0x05, 0x06,
    /* eth proto IPv4 */ 0x08, 0x00,
    /* IPv4 header */ 0x45, 0x00, 0x00, 0x14,
    0x00, 0x01, 0x00, 0x00, 0x40, 0x06, 0x00, 0x00,
    0x01, 0x02, 0x03, 0x04,    /* src IP 1.2.3.4 */
    0x05, 0x06, 0x07, 0x08,    /* dst IP 5.6.7.8 */
}

// 直接呼叫 BPF_PROG_TEST_RUN
ret, _, err := objs.XdpFilter.Test(pkt)
if err != nil { log.Fatal(err) }

switch ret {
case 1: log.Println("XDP_DROP")
case 2: log.Println("XDP_PASS")
case 3: log.Println("XDP_TX")
}

14.5.3 XDP Live Frame Mode（6.0+）

傳統 TEST_RUN 跑完不會把封包注入網路堆疊；live frame mode 改為「真的把封包送進去」，可作為極簡 traffic generator：

  • 單次 syscall 執行 BPF 數百萬次
  • 每次都是新的封包副本
  • 由 program return code 決定真實命運（drop / redirect / tx）
  • 用 BPF_F_TEST_XDP_LIVE_FRAMES flag 啟用

14.6 BPF Iterator

BPF Iterator（5.8+）是個聰明的 hybrid：BPF 程式擔任「遍歷 Kernel 物件的回呼」，user space 透過讀檔案取得結果。

14.6.1 工作流程

sequenceDiagram participant U as User space participant L as bpf_link participant I as Iterator (kernel) participant P as BPF program U->>U: 載入 BPF program (SEC("iter/task")) U->>L: bpf(LINK_CREATE, iter_info) L-->>U: link_fd U->>L: bpf_iter_create(link_fd) L-->>U: iter_fd (檔案描述子) loop 每次 read U->>I: read(iter_fd, buf, size) I->>P: 對每個 task 呼叫 BPF P->>P: 把資訊寫到 seq_file buffer I-->>U: 回傳 buffer 內容 end

14.6.2 支援的 iterator 類型

Iterator遍歷對象
iter/task系統內所有 task
iter/task_file每個 task 的所有 open file
iter/task_vma每個 task 的記憶體區段
iter/tcp / iter/udp所有 TCP / UDP socket
iter/bpf_map系統內所有 BPF map
iter/bpf_prog系統內所有 BPF program
iter/bpf_link系統內所有 BPF link
iter/cgroupcgroup 階層
iter/sockmapsockmap 內 socket

意義：ss、ps、lsof 等系統工具的下一代實作都可以用 BPF iterator 取代，效能更好、無需 /proc 解析。

14.7 Pinning：BPF_OBJ_PIN / BPF_OBJ_GET

第 7 章 §7.2 已介紹過 pinning 概念。本節補充 syscall 細節：

cmd意義備註
BPF_OBJ_PIN把 program / map / link 釘到 bpffs 路徑該路徑的 inode 持有 reference
BPF_OBJ_GET從 bpffs 路徑取回 FD不論程式類型都可開

Pinning 的細節：

  • 路徑必須在 bpffs（/sys/fs/bpf）下，不可在普通 fs。
  • 同一物件可釘多個路徑，每個路徑各持一份 reference。
  • 解除釘住：rm /sys/fs/bpf/<name> 或 unlink() syscall。
  • libbpf 的 LIBBPF_PIN_BY_NAME 約定：自動釘到 /sys/fs/bpf/<map_name>。

14.8 物件發現：BPF_*_GET_NEXT_ID

Kernel 為每個 BPF 物件分配唯一 ID（prog_id、map_id、link_id、btf_id）。透過 GET_NEXT_ID + GET_FD_BY_ID + GET_INFO_BY_FD 三個 syscall 組合，可以列出系統內所有 BPF 物件。

14.10 第 14 章小結

  1. bpf() syscall 共 40+ 個 cmd，分七大類：建立 / Map / Program / Link / 發現 / Pin / Token。
  2. BPF_PROG_LOAD 是最複雜的 cmd，內含 verifier、CO-RE relocation、JIT 三道處理。
  3. BPF_LINK_CREATE（5.7+）統一 attach 路徑，取代碎片化的 PROG_ATTACH / netlink / perf_event 等老路。
  4. BPF_PROG_TEST_RUN 讓 BPF 程式可以 unit test，6.0+ XDP live frame mode 還能當 traffic generator。
  5. BPF Iterator 用 BPF 寫 Kernel 物件遍歷器，是 ss/ps/lsof 的下一代實作。
  6. 三種 loader（cilium/ebpf、aya、libbpf）內部都是包裝這些 syscall，strace 可看到實際呼叫。

15.1 為何 BTF + CO-RE 是現代 BPF 的命脈

第 3 章已介紹 BTF 與 CO-RE 概念。本章把它們從原理到 wire format 完全攤開，因為這個機制是：

  • 所有現代 BPF 工具跨 Kernel 版本部署的基礎。
  • fentry / fexit / LSM / tp_btf 等 BTF-typed program 的前提。
  • kfunc 機制（用 BTF func name 呼叫）的底層支撐。
  • K8s DaemonSet 部署 BPF 工具不需要在 node 上重新編譯的關鍵。

「沒有 BTF / CO-RE，BPF 只是研究工具；有了它，BPF 才是工程化技術。」

15.2 BTF Wire Format

BTF 是緊湊的 binary 格式，由 pahole --btf_encode 從 DWARF 轉出。整體結構：

flowchart LR H["btf_header
(24 bytes)"] T["Type Section
(btf_type 陣列)"] S["String Section
(\\0 分隔字串池)"] H --> T --> S

15.2.1 btf_header

btf_header 結構（24 bytes）
struct btf_header {
    __u16   magic;       /* 0xeB9F (LE) 或 0x9FeB (BE) */
    __u8    version;     /* 1 */
    __u8    flags;
    __u32   hdr_len;     /* 通常 24 */

    /* type 與 string 兩個 section 的 offset / length */
    __u32   type_off;
    __u32   type_len;
    __u32   str_off;
    __u32   str_len;
};

15.2.2 btf_type

每個 type 都用 struct btf_type 開頭：

btf_type 共用 header（12 bytes）
struct btf_type {
    __u32 name_off;       /* 指向 string section */
    __u32 info;           /* 三段：kind / kind_flag / vlen */
    union {
        __u32 size;       /* 對 INT / STRUCT / UNION / ENUM 等 */
        __u32 type;       /* 對 PTR / TYPEDEF / VOLATILE / CONST 等 */
    };
};

/* info 的 bit layout：
 *   bits  0-15: vlen   （該 type 的 child 數量）
 *   bits 16-23: 未用
 *   bits 24-28: kind   （type 種類）
 *   bit     31: kind_flag （某些 kind 的特殊 flag）
 */
#define BTF_INFO_KIND(info) (((info) >> 24) & 0x1f)
#define BTF_INFO_VLEN(info) ((info) & 0xffff)

每種 kind 後面接的「extra data」不同，下節詳解。

15.2.3 String Section

所有名稱都集中在 string section，用 NUL 分隔。name_off 是該名稱在 section 內的 byte offset。第一個字節保留為 0（空字串）。

15.3 BTF 全部 18 種 kind

每個 kind 有自己的 extra data 格式。下表整理（以 6.16 為基礎）：

Kind編號意義extra data
BTF_KIND_INT1整數型別1 個 u32（bits / encoding / offset）
BTF_KIND_PTR2指標無（用 type 欄位）
BTF_KIND_ARRAY3陣列btf_array（type / index_type / nelems）
BTF_KIND_STRUCT4結構vlen 個 btf_member
BTF_KIND_UNION5聯合同上
BTF_KIND_ENUM6列舉（32-bit）vlen 個 btf_enum
BTF_KIND_FWD7前向宣告無
BTF_KIND_TYPEDEF8type alias無
BTF_KIND_VOLATILE9volatile 修飾無
BTF_KIND_CONST10const 修飾無
BTF_KIND_RESTRICT11restrict 修飾無
BTF_KIND_FUNC12函式定義無
BTF_KIND_FUNC_PROTO13函式 prototypevlen 個 btf_param
BTF_KIND_VAR14全域變數1 個 u32（linkage）
BTF_KIND_DATASEC15data sectionvlen 個 btf_var_secinfo

15.3.1 STRUCT 編碼範例

來看 struct task_struct { int pid; ... }（簡化）的 BTF 編碼：

struct task_struct 的 BTF binary 描述
// type id = 5 (假設)
struct btf_type {
    name_off = 100,                          // string section 中 "task_struct"
    info = BTF_KIND_STRUCT << 24 | 1,        // kind=4, vlen=1
    size = 1024,                             // sizeof(struct task_struct)
};
// 後接 vlen=1 個 btf_member：
struct btf_member {
    name_off = 200,                          // string section "pid"
    type     = 1,                            // type id of 'int'
    offset   = 1232 * 8,                     // bit offset (1232 bytes)
};

15.3.2 為何要這麼設計

  • 所有名稱集中在 string section → 同名重複的 type 共享字串。
  • type 之間用 ID 互相參照 → 無循環指標，避免序列化問題。
  • kind / vlen 編碼在 32-bit info → 固定 12 bytes header，緊湊。
  • extra data 隨 kind 變化 → 每種 kind 只存必要資訊。

15.4 BTF Deduplication

Kernel 編譯時的 DWARF 資訊約 200MB。BTF 透過 deduplication 把它壓到 5MB 以下。為何能這麼小？

15.4.1 為何 DWARF 會這麼大

因為 C 編譯模型，每個 .c 檔都會產生一份完整的 type 描述。struct task_struct 在 kernel/sched.c、kernel/fork.c、kernel/exit.c 等檔案中各被描述一次。Kernel 數千個 .c 檔加起來，重複嚴重。

15.4.2 BTF deduplication 演算法

flowchart TB DWARF["DWARF
(每 .c 檔重複)"] PARSE["pahole 解析"] HASH["每個 type 計算
結構 hash"] MERGE["相同 hash 合併
(僅留一份)"] REWIRE["所有 reference
改指向新 ID"] BTF["BTF
(極度緊湊)"] DWARF --> PARSE --> HASH --> MERGE --> REWIRE --> BTF

關鍵想法：「結構等價的兩個 type（同名 + 同欄位 + 同型別）視為同一個」。pahole 用 hash + struct walking 偵測等價，合併。最後得到去重 type 集合。

15.4.3 數字感受

Kernel ComponentDWARF 大小BTF 大小壓縮比
vmlinux（典型 6.x）~200 MB~5 MB40×
kernel module（中型）~5 MB~150 KB33×
BPF program（典型）數十 KB數 KB10–20×

15.5 CO-RE Relocation 完整 kind 列表

當 Clang 編譯 BPF 程式遇到 task->pid 這類 kernel 結構存取，它不直接 emit 常數 offset，而是 emit 一條「pseudo instruction + CO-RE relocation 紀錄」。Loader 載入時根據目標 Kernel BTF 改寫 instruction。

15.5.2 Relocation 的 wire format

編譯時，clang 把 relocation 紀錄存在 ELF 的 .BTF.ext section：

每筆 relocation
struct bpf_core_relo {
    __u32   insn_off;        /* 程式中對應 instruction 的位元組 offset */
    __u32   type_id;         /* 本地 BTF 中的 type ID */
    __u32   access_str_off;  /* 存取路徑（"0:1:2" 之類） */
    enum bpf_core_relo_kind kind;
};

15.6 CO-RE 巨集背後的機制

libbpf 提供的 BPF_CORE_READ、bpf_core_field_exists 等巨集，本質上是 clang 內建的 builtin 包裝。每個巨集對應一個 builtin call：

bpf_core_field_exists(t->f)__builtin_preserve_field_info(..., 2)FIELD_EXISTS
bpf_core_field_size(t->f)__builtin_preserve_field_info(..., 1)FIELD_BYTE_SIZE
bpf_core_type_exists(T)__builtin_preserve_type_info(..., 0)TYPE_EXISTS
bpf_core_type_size(T)__builtin_preserve_type_info(..., 1)TYPE_SIZE
bpf_core_type_id_local(T)__builtin_btf_type_id(..., 0)TYPE_ID_LOCAL
bpf_core_type_id_kernel(T)__builtin_btf_type_id(..., 1)TYPE_ID_TARGET
bpf_core_enum_value_exists(E, V)__builtin_preserve_enum_value(...)ENUMVAL_EXISTS
bpf_core_enum_value(E, V)__builtin_preserve_enum_value(...)ENUMVAL_VALUE

15.6.1 完整使用範例

用 CO-RE 巨集兼容多版本 Kernel
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>
#include <bpf/bpf_tracing.h>

SEC("kprobe/do_open")
int trace_open(struct pt_regs *ctx) {
    struct task_struct *task = (void *)bpf_get_current_task();

    /* 1. 直接讀 typed 欄位（CO-RE 自動處理 offset） */
    pid_t pid;
    BPF_CORE_READ_INTO(&pid, task, pid);

    /* 2. 巢狀讀取 task->real_parent->pid */
    pid_t ppid = BPF_CORE_READ(task, real_parent, pid);

    /* 3. 條件性讀取：欄位是否存在於目標 Kernel */
    if (bpf_core_field_exists(task->exit_code)) {
        int code = BPF_CORE_READ(task, exit_code);
        bpf_printk("has exit_code=%d", code);
    }

    /* 4. 條件性讀取：type 是否存在 */
    if (bpf_core_type_exists(struct mm_struct)) {
        bpf_printk("kernel has mm_struct");
    }

    /* 5. 取 enum 在目標 Kernel 的真實值 */
    int task_running = bpf_core_enum_value(enum task_state, TASK_RUNNING);

    return 0;
}

15.6.2 為何 CO-RE 巨集這麼重要

沒有 CO-RE 之前，跨 Kernel 的 BPF 工具只有兩條路：

  1. BCC 路線：在 target machine 上用 LLVM 重新編譯。每次啟動慢、需要 LLVM toolchain、極佔資源。
  2. 逐版本維護：為每個 Kernel 版本維護一份 .o，發行時打包數百個版本。極不可行。

有了 CO-RE：一份 .o，跨數百個 Kernel 版本。這是工程化轉折點。

15.8 老 Kernel 的可攜性：BTFhub / BTFGen

CO-RE 的前提是目標 Kernel 提供 BTF。但 Kernel 5.2 之前都沒 BTF；某些早期發行版（CentOS 7、Ubuntu 18.04 等）即使編譯支援，也沒啟用 CONFIG_DEBUG_INFO_BTF。怎麼辦？

15.8.1 BTFhub：補強 BTF 檔案庫

BTFhub（Aqua Security 維護）為已發行但缺 BTF 的 Kernel提供補強：

  • 對 RHEL、CentOS、Ubuntu、Amazon Linux 等發行版的舊版 Kernel，事後生成 BTF 檔案。
  • 從受影響的 distro debug package 抽出 DWARF，用 pahole 轉成 BTF。
  • 已涵蓋 1000+ Kernel 變體，可下載對應檔案。

15.8.2 BTFGen：精簡 BTF

BTFhub 的問題：每個 BTF 檔幾 MB，要支援 300 個 Kernel 變體就是 1+ GB。BTFGen 解法：

「你這個 BPF 程式只用到 task_struct 的 5 個欄位、struct sock 的 3 個欄位 ... 那我只把你需要的那些 type放進 BTF 即可。」

結果：每個 mini-BTF 只有幾 KB，數百個 Kernel 變體合計 1.5 MB，完全可隨工具一起發行。Tetragon、Tracee、Falco 都已採用。

15.9 第 15 章小結

  1. BTF 是 Linux Kernel 與 BPF 程式的緊湊 type 描述格式：5 MB 即可描述整個 Kernel（vs DWARF 200 MB）。
  2. BTF wire format：btf_header + Type Section（btf_type 陣列）+ String Section。
  3. 共 19 種 kind（INT、PTR、STRUCT、UNION、ENUM、ENUM64、TYPEDEF、FUNC、FUNC_PROTO、VAR、DATASEC、DECL_TAG、TYPE_TAG、FLOAT 等），每種 extra data 不同。
  4. BTF deduplication 依結構等價合併重複 type，是 BTF 緊湊的關鍵。
  5. CO-RE relocation 共 11 種 kind，覆蓋欄位 offset / size / 存在性、type 存在性 / size / ID、enum 值等情境。
  6. libbpf 的 CO-RE 巨集是 clang builtin 的 wrapper，每個對應一種 relocation kind。
  7. 對老 Kernel 無 BTF 場景，BTFhub（補完 BTF 檔案）+ BTFGen（精簡為 mini-BTF）是業界標準解法。
