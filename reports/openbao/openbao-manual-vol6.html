Chapter 34排錯手冊（Troubleshooting）

本章按「症狀」整理常見問題與解法。你看到某個錯誤訊息或現象時，直接翻到對應段落。

34.1 症狀：bao status 顯示 sealed

$ bao status
Sealed                  true
Initialized             true
Total Shares            5
Threshold               3
Unseal Progress         0/3

可能原因與解法：

  • 剛重啟 — Shamir seal 必須手動 unseal：bao operator unseal ×3 次。Production 上應改用 auto-unseal。
  • Auto-unseal 但仍 sealed — 通常是 KMS / HSM 連線失敗。看 server log：journalctl -u openbao -e。常見錯誤：
    • could not decrypt seal: AccessDenied → IAM role / Service Account 權限不對。
    • InvalidSignatureException → KMS region 設錯。
    • connection refused → 網路或 firewall 擋住。
  • Cluster 內某些節點 sealed — 可能是 join 失敗或剛重啟。先看 active node 的 log，再 bao operator raft list-peers。

34.2 症狀：bao status 顯示 not initialized

第一次啟動時正常。如果是已運行的 cluster突然 not initialized：

  • 新節點想 join 但連到了空的 storage — 檢查 storage 設定。
  • Storage backend 連不上 — Raft 路徑錯、PG 連線失敗都會這樣。
  • 用了錯的 seal 設定 — 用 KMS A 加密的資料，現在用 KMS B 啟動，OpenBao 認為「我不認識這個 storage」，視同未 init。

在動手「重新 init」之前 — 想清楚：重新 init 會生成新的 root key，原有資料無法解開，等於資料全失。

34.3 症狀：應用收到 403 Forbidden

Error: 1 error occurred:
  * permission denied

排查順序：

  1. 確認 token 有效：bao token lookup。看 ttl 和 policies。
  2. 看 policy 內容：bao policy read <name>。確認對應 path 有正確 capability。
  3. 確認 KV v2 雙路徑都寫了：secret/data/... 與 secret/metadata/...。
  4. 用 -output-policy 反推這次操作真正需要什麼權限：
$ bao kv get -output-policy -mount=secret myapp/db
path "secret/data/myapp/db" {
  capabilities = ["read"]
}

對比實際 policy 跟這個輸出，少哪條 capability 一目了然。

常見子症狀：sudo 路徑

某些路徑（如 sys/audit、sys/leases/revoke-prefix、sys/raw）需要 sudo capability，不是 create/update：

path "sys/audit/*" {
  capabilities = ["create", "update", "sudo"]
}

34.4 症狀：應用 token 不斷過期

典型原因：

  • Token TTL 太短（如 5 分鐘）+ 應用沒實作 renew → 5 分鐘後永遠 403。解：實作 LifetimeWatcher（第 28 章），或用 OpenBao Agent。
  • Token max_ttl 到了 — 不論怎麼 renew 都過期。應用必須重新 login。
  • Token 的 explicit_max_ttl 比你想的短。bao token lookup <tok> 看 explicit_max_ttl。

34.5 症狀：Lease 數量爆炸

Metric vault.expire.num_leases 飆到數萬甚至數十萬：

  • 找出元凶：vault.expire.num_leases_by_mount 看哪個 mount 多。
  • 常見原因：
    • 應用每次 read DB cred 都當新 secret，沒重複用：每次取 lease，造成累積。
    • PKI 發 cert 不必要地 store（no_store=false + 高頻發證）。
    • Token TTL 太長，卻不斷發新 token。
  • 緊急清理：bao lease revoke -prefix <path> 批次撤銷某 mount 的 lease。
  • storage tidy：v2.4+ 提供 sys/leases/tidy 清理 dangling lease entry。但「會做大量 I/O，建議在離峰使用」。
# 看當前 irrevocable lease 統計
$ bao read sys/leases/count type=irrevocable
$ bao write sys/leases/tidy

34.6 症狀：Performance 變慢

系統性排查：

  1. 看 vault.core.handle_request p99 — 是哪個 mount / endpoint 慢？
  2. 看 vault.runtime.heap_objects 與 num_goroutines — 有沒有持續上升？
  3. 看 vault.barrier.put / get 的 p99 — storage 慢嗎？
  4. 看 vault.raft.apply 與 raft.commitTime — Raft replication 健康嗎？
  5. 檢查 leader 與其他節點的 disk I/O（iostat）和 network。

常見性能問題

  • 大 KV value：每寫 1MB value × 10 versions = 10MB 在 storage。瘦身或 archive。
  • Lease 累積：見上一節。
  • PKI 大量簽發：用 ECDSA 而非 RSA-4096；「使用 sign 而非 issue 比較快（client 自己產 key）」；考慮 no_store=true + generate_lease=false。
  • 沒用 performance standby：v2.5.0 起加入 horizontal read scalability。如果你關掉了 disable_standby_reads，所有讀都打 active。

34.7 症狀：Audit log 不寫

  • 確認 audit device 啟用：bao audit list。
  • 確認 file 路徑可寫：ls -la /var/log/openbao/，OpenBao process user 對該目錄有 write 權限。
  • logrotate 後 file 變空：忘記在 postrotate 加 kill -SIGHUP（第 24 章）。
  • Audit 失敗 metric：vault.audit.log_request_failure。如果它 > 0，所有 request 會失敗。

34.8 症狀：Raft cluster 失去 quorum

$ bao operator raft list-peers
Error: cluster does not have quorum

這代表 cluster 已喪失 quorum，無法寫入。可能：

  • 多數節點掛掉（5 節點掛 3）— 救活其中一個就回來。
  • 網路分裂（split brain）— 修復網路。
  • 節點時鐘漂移過大 — Raft 對 clock 敏感，跑 NTP。

最壞情況：只剩一個節點還活著但其他都救不回。可以用peers.json recovery強制重組：

# 在剩下的節點上停 OpenBao，編輯 raft 目錄下的 peers.json
$ cat > /var/lib/openbao/data/raft/peers.json <<EOF
[
  {
    "id": "bao-1",
    "address": "10.0.1.1:8201",
    "non_voter": false
  }
]
EOF

$ systemctl start openbao
# 啟動後它會把這個節點視為唯一 voter，重組 cluster

之後逐一加入新節點。這是危險動作，一定要先有 snapshot。

34.9 症狀：升級後啟動失敗

  • 看 journalctl log，找出第一條 ERROR。
  • 常見：deprecation 移除導致設定失效（如某個被 remove 的 storage backend）。
  • 用 bao operator diagnose（v2.5+）跑配置與 storage 健檢。
  • 跨 minor 升級失敗：回到 pre-upgrade snapshot + 舊版本 binary。
$ bao operator diagnose
Starting diagnose...
[ success ] OpenBao Diagnose
  [ success ] Check Operating System
  [ success ] Parse Configuration
  [ success ] Create Storage Backend
  [ warning ] Check Listener TLS
    Certificate expires in 14 days. Consider renewal.
...

34.10 症狀：應用啟動時取不到 secret（K8s）

用 Agent Injector 時最常見：

  • Annotation 寫錯：vault.hashicorp.com/agent-inject 不是 openbao.org/agent-inject。Injector 仍用 vault.hashicorp.com namespace。
  • vault.hashicorp.com/role 沒設或對不上 OpenBao 的 K8s role。
  • SA 沒對應到 OpenBao 端的 bound_service_account_names。
  • Pod namespace 沒對應到 bound_service_account_namespaces。
  • Init container fail — 看 init container log：kubectl logs <pod> -c vault-agent-init。

34.11 症狀：CLI 連不上 server

$ bao status
Error checking seal status: Get "https://127.0.0.1:8200/v1/sys/seal-status":
  x509: certificate signed by unknown authority
  • 沒設 BAO_CACERT 指向你的 CA 檔。
  • 用了自簽 cert 但 host 上沒 trust。
  • 權宜（非 production）：BAO_SKIP_VERIFY=true。永遠不要在 production 用這個。
$ bao status
Error checking seal status: Get "https://bao.example.com:8200/...":
  context deadline exceeded
  • 網路：firewall、Security Group、VPC peering。
  • DNS：解析錯誤。
  • Server 沒在這個 port listening。

34.12 用 operator diagnose 主動找問題

OpenBao 內建 operator diagnose 指令，「在 server 啟動前或運作中可主動跑」，會檢查 OS、配置、storage、TLS、seal 設定、unseal、auth 等多個面向：

$ bao operator diagnose -config=/etc/openbao/config.hcl

輸出每行前綴：[ success ]、[ warning ]、[ skipped ]、[ failure ]。Production deploy 與升級前都建議跑一次。

34.13 收集 support bundle

遇到難解問題開 issue 時，至少附：

  • OpenBao 版本：bao version
  • Server log（過濾敏感資訊）
  • Config（脫敏 — 移除 token、cert 內容）
  • bao status + bao operator raft list-peers + autopilot state
  • 相關 metric 截圖
  • 復現步驟與預期 vs 實際結果

34.14 ⚙ 動手練習

  1. 故意 stop 一個 Raft 節點，跑 autopilot state 觀察 failure tolerance 變化。
  2. 故意設一個 lease 超短（10 秒），讓 lease 累積 1000 個，跑 sys/leases/tidy 清理。
  3. 跑 bao operator diagnose，把所有 warning 都修好。

Chapter 35治理與貢獻

OpenBao 不是一家公司的產品，是 Linux Foundation / OpenSSF 旗下的開源專案。理解它的治理模式，能幫助你：(1) 評估專案長期穩定性、(2) 提交 bug / feature、(3) 自己 fork 維運。

35.1 OpenBao 的由來

  • 2023 年 8 月，HashiCorp 把 Vault 與其他產品從 MPL 2.0 改成 BSL（Business Source License）。
  • 同年底，社群基於 Vault 1.14（最後一個 MPL 版本）fork 出 OpenBao。
  • 2024 年中，OpenBao 進入 Linux Foundation；後續歸屬 OpenSSF 保護傘下。
  • 由 IBM 工程師 Nathan Phelps、Joe Pearson 等啟動，社群維運（非 IBM 官方產品）。
  • License：MPL 2.0（OSI 認可的真開源）。

35.2 治理結構

  • Technical Steering Committee（TSC）：技術決策最高機構，公開選舉產生。
  • Maintainers：對特定子系統有 commit 權，由 TSC 任命。
  • Contributors：任何提交 PR 的人。
  • Security Team：處理 CVE 與機敏 issue，openbao-security@lists.openssf.org。

所有 governance 文件公開於 openbao/openbao 的 GOVERNANCE.md。

35.3 RFC 流程

對 OpenBao 行為有結構性影響的改動（新功能、API 變更、storage 格式變更）走 RFC 流程：

  1. 提案者在 openbao/openbao 開 RFC issue，描述問題、設計、API 影響、後相容性。
  2. TSC 與相關 maintainer 在 issue 討論。
  3. 達成共識後，提案者進入實作 PR。
  4. PR 通過 review + CI 後合併。
  5. Release notes 寫明這是 RFC #xxx 的實作。

例：第三冊提到的 SSH CA Multi-issuer 就是經由 RFC 流程進入 OpenBao（原 Vault 並無此功能）。

35.4 如何貢獻

① 回報 bug

  • 用 GitHub issue + 完整 support bundle（第 34.13）。
  • 機敏 / 安全相關：寄 openbao-security@lists.openssf.org，不要在 public issue。

② 提交 PR

  • Fork → 建分支 → 開 PR。
  • 遵循 CONTRIBUTING.md（CLA、測試覆蓋率、changelog）。
  • 每個 PR 對應一個 GitHub Issue（除非是純文檔 / typo）。
  • 大改動先開 issue / RFC 討論再寫 code。

③ 改善文檔

OpenBao 文檔在 openbao/openbao repo 的 website/ 子目錄。改錯字、補範例、補翻譯都歡迎。文檔貢獻通常 review 較快。

④ 翻譯

OpenBao 主要文檔仍是英文。中文/日文等社群翻譯仍是早期階段。如果你看完這套手冊覺得「這部分官方文件如果有中文就好了」 — 你可以開個 PR 提這份。

35.5 OpenBao 與 Vault 的關係（持續演進）

截至本手冊撰寫（2026/05）：

  • API 仍大致相容：絕大多數 Vault client library 對 OpenBao 仍可用。
  • OpenBao 開始有 Vault 沒有的功能：Namespaces（OSS）、Performance Standby（OSS）、Declarative Self-Initialization、http audit device、SSH CA Multi-issuer、CEL roles、Inline Auth 等。
  • Vault 也有 OpenBao 沒有的：Disaster Recovery Replication（仍是 Enterprise 專屬）、部分新增 secret engine 與 plugin。
  • 長期可能會逐漸分歧；現在跨平台仍可，未來可能不行。

35.6 從 Vault 遷移到 OpenBao

實務經驗（截至 2026/05）：

  1. 盤點目前用的功能：所有 secret engine、auth method、policy、Enterprise 功能。
  2. 確認 OpenBao 對等支援：對照附錄 D。
  3. 非 production 試：在 staging fresh deploy OpenBao，重建設定。
  4. 客戶端不需改 code：API 相容。
  5. 不要直接 restore Vault snapshot 到 OpenBao：除非已在 staging 測過。
  6. 大多數情境的可行做法是並行運作 + 逐步搬遷：應用一個個從 Vault 切到 OpenBao。

35.7 商業支援與顧問

OpenBao 是社群專案，沒有官方付費支援。但有以下選擇：

  • 多家 systems integrator 提供 OpenBao 諮詢與部署服務。
  • GitLab 已宣布把 OpenBao 整合進 GitLab Premium 的 Secrets Manager。
  • 各大雲端 marketplace 上會有 OpenBao 預封裝映像（社群維護）。

如果你的組織需要付費支援，「想清楚需求 → 選對廠商」比抓最便宜的重要。

35.8 ⚙ 動手練習

  1. 到 openbao/openbao 看一下開放的 issue 與最近的 PR，找一個你能修的「good first issue」。
  2. 閱讀 GOVERNANCE.md 與 CONTRIBUTING.md。
  3. Subscribe security mailing list（即使你不打算貢獻，也能第一時間收到 CVE）。

Appendix ACLI 指令速查表

最常用的 bao 指令，按使用情境分類。每個指令都可加 -help 查完整 flag。

A.1 連線與環境

# 環境變數
export BAO_ADDR=https://bao.example.com:8200
export BAO_CACERT=/etc/openbao/ca.crt
export BAO_TOKEN=<token>
export BAO_NAMESPACE=<ns>

# 確認連線
bao status

# 印 token 環境
bao print token

A.2 認證

# Token 登入（手動輸入）
bao login

# 各種 auth method
bao login -method=userpass username=alice
bao login -method=oidc role=admin
bao login -method=approle role_id=<rid> secret_id=<sid>
bao login -method=kubernetes role=myapp jwt=<jwt>

# Token 操作
bao token create -policy=app-ro -ttl=1h
bao token lookup <tok>
bao token renew <tok>
bao token revoke <tok>
bao token revoke -self                  # 撤銷自己當前 token

A.3 KV v2

# 啟用
bao secrets enable -path=secret kv-v2

# CRUD
bao kv put -mount=secret myapp/db user=alice password=s3cret
bao kv get -mount=secret myapp/db
bao kv get -mount=secret -field=password myapp/db
bao kv get -mount=secret -version=3 myapp/db
bao kv patch -mount=secret myapp/db new_field=val
bao kv delete -mount=secret myapp/db                # 軟刪
bao kv undelete -mount=secret -versions=1 myapp/db
bao kv destroy -mount=secret -versions=1 myapp/db   # 永久毀某版
bao kv metadata delete -mount=secret myapp/db       # 整把毀（含 metadata）

# Metadata
bao kv metadata put -mount=secret -max-versions=5 \
  -delete-version-after=720h myapp/db
bao kv metadata get -mount=secret myapp/db
bao kv list -mount=secret myapp/

A.4 Policy

bao policy list
bao policy read app-ro
bao policy write app-ro app-ro.hcl
bao policy delete app-ro
bao policy fmt app-ro.hcl                    # 格式化檢查

# 反推所需 policy
bao kv get -output-policy -mount=secret myapp/db
bao <cmd> -output-policy ...                # 任何指令都可加

A.5 Auth methods

bao auth list
bao auth enable userpass
bao auth enable -path=jwt-github jwt
bao auth disable userpass/

bao write auth/userpass/users/alice password=<pwd> policies=admin
bao write auth/approle/role/myapp policies=app-ro token_ttl=1h
bao read auth/approle/role/myapp/role-id
bao write -f auth/approle/role/myapp/secret-id

# Tune mount-level 設定
bao auth tune -default-lease-ttl=1h userpass/

A.6 Secret engines

bao secrets list
bao secrets enable kv-v2
bao secrets enable -path=team-a/secret kv-v2
bao secrets disable team-a/secret/
bao secrets move secret/ kv/

# Tune（TTL、audit、response header⋯）
bao secrets tune -default-lease-ttl=1h -max-lease-ttl=24h database/
bao secrets tune -audit-non-hmac-request-keys=common_name pki-int/

A.7 Database engine

# 設定 connection
bao write database/config/my-pg \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@..." \
  allowed_roles="myapp-ro" username=openbao password=...

# Rotate root（強烈建議）
bao write -force database/rotate-root/my-pg

# Dynamic role
bao write database/roles/myapp-ro \
  db_name=my-pg \
  creation_statements="..." default_ttl=1h max_ttl=24h
bao read database/creds/myapp-ro

# Static role
bao write database/static-roles/legacy-app \
  db_name=my-pg username=legacy_app rotation_period=24h
bao read database/static-creds/legacy-app
bao write -force database/rotate-role/legacy-app

A.8 PKI engine

# Setup
bao secrets enable -path=pki-root pki
bao secrets tune -max-lease-ttl=87600h pki-root
bao write pki-root/root/generate/internal common_name="Root CA" ttl=87600h

# Issue / sign
bao write pki-int/issue/example-com common_name=api.example.com ttl=72h
bao write pki-int/sign/example-com csr=@req.csr common_name=api.example.com

# Revoke
bao write pki-int/revoke serial_number=<serial>

# Health check
bao pki health-check pki-int

A.9 SSH engine

# Signed cert mode
bao secrets enable -path=ssh-client-signer ssh
bao write ssh-client-signer/config/ca generate_signing_key=true
bao read ssh-client-signer/config/ca   # 取出 CA pub

# 發 user cert
bao write -field=signed_key ssh-client-signer/sign/dev-role \
  public_key=@~/.ssh/id_ed25519.pub \
  valid_principals=ubuntu > ~/.ssh/id_ed25519-cert.pub

A.10 Transit engine

bao secrets enable transit
bao write -f transit/keys/myapp-data
bao write transit/encrypt/myapp-data plaintext=$(echo -n "hello" | base64)
bao write transit/decrypt/myapp-data ciphertext="vault:v1:..."
bao write -f transit/keys/myapp-data/rotate
bao write transit/rewrap/myapp-data ciphertext="vault:v1:..."

A.11 Operator（cluster 管理）

# 初始化 / unseal
bao operator init -recovery-shares=5 -recovery-threshold=3
bao operator unseal <key>
bao operator seal

# Root token 補發
bao operator generate-root -init
bao operator generate-root -nonce=<n>

B.4 重要 Header

  • X-Vault-Token: <token> — 認證 token（OpenBao 仍用 X-Vault- 前綴以保留 API 相容）
  • X-Vault-Namespace: <ns> — 指定 namespace
  • X-Vault-Wrap-TTL: 5m — 請求 response wrapping
  • X-Vault-Index: <index> — 強一致讀（讓 standby 等到該 index 才讀）
  • X-Vault-Forward: active-node — 強制 forward 到 active
  • X-Vault-Inconsistent: forward-active-node — 容忍不一致時的 fallback

B.5 LIST 動作的 HTTP 等價

OpenBao 用非標準 HTTP verb LIST。也可改用 GET + ?list=true：

LIST /v1/secret/metadata/myapp HTTP/1.1
X-Vault-Token: ...

# 或

GET /v1/secret/metadata/myapp?list=true HTTP/1.1
X-Vault-Token: ...

Appendix DOpenBao vs HashiCorp Vault 對照

截至 2026 年 5 月的兩專案差異速查。本表會隨兩邊各自演進而變動，以官方 release notes 為準。

D.1 基本面

OpenBaoVault CommunityVault Enterprise
LicenseMPL 2.0BSL 1.1（4 年後轉 MPL）商業
主導Linux Foundation / OpenSSF（社群）HashiCorp（IBM 旗下）同左
Fork 起點Vault 1.14（最後 MPL 版）——
API 相容性對 Vault 仍大致相容——
CLI 名稱baovaultvault
環境變數支援 BAO_* 與 VAULT_*VAULT_*VAULT_*

D.2 OpenBao OSS 已具備、但 Vault 須 Enterprise 的

功能說明
Namespaces多租戶隔離；OpenBao 在 OSS 即提供
Performance Standby (read scaling)v2.5.0 起 OpenBao OSS 也有 horizontal read scalability
HSM auto-unseal (PKCS#11)OpenBao OSS；Vault 是 Enterprise
Declarative Self-InitializationOpenBao OSS 獨有：config 直接定義 init 後狀態
config 內定義 audit deviceOpenBao 獨有：第一個 request 起即受 audit

D.3 Vault 有、但 OpenBao 尚無的

功能說明
DR Replication（Disaster Recovery）Vault Enterprise 跨 cluster 自動同步；OpenBao 用 snapshot DR 替代
Performance Replication（PR）跨 region 雙活；OpenBao 無對等功能
Auto-snapshot（內建排程）Vault Enterprise 內建；OpenBao 需外部 cron + script
Sentinel PolicyVault Enterprise；OpenBao 用 CEL 取代部分用例
HSM HA（多 HSM 同步）Vault Enterprise
Control Group需多人核可流程；Vault Enterprise
較新的內部 secret engineVault 後續引入但未 backport 進 OpenBao 的（看版本而定）

D.4 兩邊都有，但語意稍異的

項目差異
Default storageOpenBao 推薦 Raft；Vault 同；但 OpenBao 對 PostgreSQL 的支援更積極（v2.4 起棄用 PG < 9.5）
Audit 端點 typeOpenBao 多了 http type 給 webhook
SSH engineOpenBao 已支援 SSH CA Multi-issuer（Vault 仍單一 CA）
JWT authOpenBao 加了 CEL roles 支援
Inline AuthOpenBao 獨有：在主 request 內附 auth，少一次 round-trip

D.5 從 Vault 遷移到 OpenBao 的注意事項

  1. 盤點 Enterprise 功能：DR Replication、Sentinel、Control Group 等需要替代方案。
  2. 不要直接 restore Vault snapshot 到 OpenBao：先在 staging 測過。
  3. 客戶端 token 通常不用換：API path 相容。
  4. OpenBao fork 起於 Vault 1.14：1.14 之後 Vault 加的功能不會自動進 OpenBao。
  5. 並行運作 + 逐步切換是最穩做法。
  6. 對監控 / SIEM 規則：metric 名稱（vault.*）與 audit log 欄位 OpenBao 沿用 vault 前綴，現有 dashboard 通常可用。

給管理者的話

OpenBao 不是「裝起來就好」的軟體。它是組織信任的中心 — 安全強化要做、稽核要看、policy 要 review、key 持有人要追蹤、災難演練要做。本手冊提供了路線圖，但真正讓 OpenBao 安全的是持續的營運。把第 31 章的清單貼在 wiki 上，每季 review。

給開發者的話

OpenBao 把 secret 從 application 中拿走，讓你的 code 變乾淨。但這個 abstraction 不是免費的 — 你要懂 token、lease、renewal、retry。這套手冊的第 28 章是基礎，但真正寫對 client 是慢慢練。從一個小 service 開始整合，遇到問題回頭翻第 34 章。

給專案發起人的話

把 OpenBao 引進組織不是技術決定 — 是流程決定。技術上 OpenBao 沒問題；難的是讓所有應用團隊接進來、讓 policy review 變成日常、讓 audit log 真的有人看。從一個小 pilot project 開始，做完整套後再擴張。第 35 章對從哪裡開始有明確建議。

致謝

本手冊基於 OpenBao 官方文件與社群文章撰寫，所有命令與 API path 已對照 v2.5.x 官方文件查證。如果在閱讀過程中發現錯誤、過時資訊或想看更多，歡迎依第 35 章貢獻流程提出。

祝你的 secret 永遠安全。
