Chapter 28應用程式整合 OpenBao

第三冊已示範過「用 SDK 寫一個 client」的最簡形式。但 production 應用要面對的不只是「拿到 secret」 — 還有 token 過期、lease 續租、連線重試、零 downtime。本章把這些 pattern 走過一遍，並提供 Go / Python / Java / Node.js / Rust 五種主流語言的入門。

28.1 應用整合的兩種模式

直接整合（用 SDK）

應用內含 OpenBao client SDK，自己處理 login、renew、retry。

  • ✅ 完全控制（cache、超時、重連）
  • ✅ 沒有額外進程
  • ✗ 每個應用都要寫一遍
  • ✗ Legacy app 不易改

中介整合（用 Agent）

OpenBao Agent 跑在 sidecar / host，把 secret 寫成檔案或 env。應用完全不知道 OpenBao 存在。

  • ✅ 應用零侵入
  • ✅ 統一處理 token / lease
  • ✗ 多一個進程要維護
  • ✗ 動態行為（隨需 read 不同 secret）較難

本章重點放在 SDK 直接整合。Agent 模式詳見第四冊第 23 章。

28.3 Go：完整 production-ready 範例

① 初始化 client

$ go get github.com/openbao/openbao/api/v2
package main

import (
    "context"
    "fmt"
    "log"
    "os"
    "time"

    openbao "github.com/openbao/openbao/api/v2"
)

func newClient() (*openbao.Client, error) {
    config := openbao.DefaultConfig()  // 自動讀 BAO_ADDR / BAO_CACERT 等環境變數
    config.Timeout = 30 * time.Second
    config.MaxRetries = 3

    client, err := openbao.NewClient(config)
    if err != nil {
        return nil, fmt.Errorf("init client: %w", err)
    }
    return client, nil
}

② 用 Kubernetes auth method 登入

func loginK8s(client *openbao.Client, role string) error {
    jwt, err := os.ReadFile("/var/run/secrets/kubernetes.io/serviceaccount/token")
    if err != nil {
        return fmt.Errorf("read SA token: %w", err)
    }

    secret, err := client.Logical().Write(
        "auth/kubernetes/login",
        map[string]interface{}{
            "role": role,
            "jwt":  string(jwt),
        },
    )
    if err != nil {
        return fmt.Errorf("login: %w", err)
    }
    if secret == nil || secret.Auth == nil {
        return fmt.Errorf("no auth info returned")
    }

    client.SetToken(secret.Auth.ClientToken)
    return nil
}

③ 讀 KV v2 secret

func readDBConfig(client *openbao.Client) (string, string, error) {
    sec, err := client.KVv2("secret").Get(
        context.Background(),
        "myapp/db",
    )
    if err != nil {
        return "", "", fmt.Errorf("read kv: %w", err)
    }

    user, ok := sec.Data["user"].(string)
    if !ok { return "", "", fmt.Errorf("user missing") }
    pwd, ok := sec.Data["password"].(string)
    if !ok { return "", "", fmt.Errorf("password missing") }

    return user, pwd, nil
}

④ 處理 token / lease 自動續租：LifetimeWatcher

// 取得 dynamic DB credential 並啟動背景 renewer
func getDBCredsAndWatch(client *openbao.Client) (*openbao.Secret, error) {
    sec, err := client.Logical().Read("database/creds/myapp-ro")
    if err != nil {
        return nil, err
    }

    watcher, err := client.NewLifetimeWatcher(&openbao.LifetimeWatcherInput{
        Secret:    sec,
        Increment: 3600,  // 希望 renew 後剩 1h
    })
    if err != nil {
        return nil, err
    }

    go func() {
        defer watcher.Stop()
        go watcher.Start()

        for {
            select {
            case err := <-watcher.DoneCh():
                if err != nil {
                    log.Printf("renew failed: %v", err)
                }
                // Lease 到 max TTL 或 renew 失敗 — 應用該重新取
                return
            case info := <-watcher.RenewCh():
                log.Printf("lease renewed, ttl=%v", info.Secret.LeaseDuration)
            }
        }
    }()

    return sec, nil
}

⑤ 完整啟動流程（推薦 pattern）

func main() {
    client, err := newClient()
    if err != nil { log.Fatal(err) }

    if err := loginK8s(client, "myapp"); err != nil {
        log.Fatal(err)
    }

    // 同時啟動 token 自身的 renewer
    tokenSecret, _ := client.Auth().Token().LookupSelf()
    if tokenSecret != nil {
        watcher, _ := client.NewLifetimeWatcher(&openbao.LifetimeWatcherInput{
            Secret: &openbao.Secret{Auth: &openbao.SecretAuth{
                ClientToken:   client.Token(),
                LeaseDuration: int(tokenSecret.Data["ttl"].(float64)),
                Renewable:     tokenSecret.Data["renewable"].(bool),
            }},
        })
        go watcher.Start()
    }

    // 讀 KV
    user, pwd, err := readDBConfig(client)
    if err != nil { log.Fatal(err) }

    // 連 DB ...
    fmt.Printf("connecting as %s\n", user)
    _ = pwd
}

28.5 Java：Spring Cloud Vault

Spring 應用最簡單的整合方式，application.yaml 加：

spring:
  config:
    import: "vault://"
  cloud:
    vault:
      uri: ${BAO_ADDR}
      ssl:
        ca-cert: file:///etc/myapp/openbao-ca.crt
      authentication: KUBERNETES
      kubernetes:
        role: myapp

28.6 Node.js：node-vault

$ npm install node-vault
// JavaScript — 用 node-vault 連 OpenBao
const vault = require("node-vault")({
  endpoint: process.env.BAO_ADDR,
  // 雖然 API 路徑兼容，模組仍叫 node-vault
});

const fs = require("fs");

async function main() {
  // K8s login
  const jwt = fs.readFileSync(
    "/var/run/secrets/kubernetes.io/serviceaccount/token", "utf8"
  );
  const result = await vault.kubernetesLogin({ role: "myapp", jwt });
  vault.token = result.auth.client_token;

  // KV v2 read
  const kv = await vault.read("secret/data/myapp/db");
  const { user, password } = kv.data.data;

  // Dynamic DB cred
  const dbCred = await vault.read("database/creds/myapp-ro");
  console.log("DB user:", dbCred.data.username);

  // Renew lease
  setInterval(() => {
    vault.write("sys/leases/renew", {
      lease_id: dbCred.lease_id,
      increment: 3600,
    });
  }, 30 * 60 * 1000);  // 每 30 分鐘
}
main().catch(console.error);

28.7 Rust：vaultrs

# Cargo.toml: vaultrs = "0.7"
// Rust — 用 vaultrs 連 OpenBao
use vaultrs::client::{VaultClient, VaultClientSettingsBuilder};
use vaultrs::auth::kubernetes;
use vaultrs::kv2;
use std::fs;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut client = VaultClient::new(
        VaultClientSettingsBuilder::default()
            .address(std::env::var("BAO_ADDR")?)
            .build()?,
    )?;

    let jwt = fs::read_to_string(
        "/var/run/secrets/kubernetes.io/serviceaccount/token"
    )?;
    let auth = kubernetes::login(&client, "kubernetes", "myapp", &jwt).await?;
    client.set_token(&auth.client_token);

    #[derive(serde::Deserialize)]
    struct DbConfig { user: String, password: String }
    let cfg: DbConfig = kv2::read(&client, "secret", "myapp/db").await?;

    println!("DB user: {}", cfg.user);
    Ok(())
}

28.8 機敏值不落盤的設計模式

取得 secret 後最忌諱「順手寫到本機檔案做 cache」。常見的安全 pattern：

  1. 啟動時讀，永久放在記憶體：應用啟動時取一次，存到 struct field；長期 daemon 用 LifetimeWatcher 背景續租。
  2. 每請求重取（high-frequency 慎用）：Each handler 開新 connection 時 re-read DB cred。配 OpenBao Agent caching 才不會打爆 OpenBao。
  3. 用 tmpfs 寫成檔案：應用必須讀檔案（legacy）時，把它寫到 /dev/shm 或 K8s emptyDir(memory)，永遠不落盤。
  4. 用 OS keyring：桌面 / CLI 工具可以用 libsecret / Keychain / Windows DPAPI 加密放 OS keyring。

絕對不要：

  • Secret 寫到 stdout / log（有些 web 框架預設會 dump request body）。
  • Secret 進 process_env 然後被 dump（K8s describe pod、core dump、crash report）。
  • Secret 寫到 K8s ConfigMap / Secret 然後 mount（除非 Sealed Secret 等加密方案）。

28.9 Token Renewal 與重連

實作 token / lease renew 邏輯時的標準 pattern：

  1. Login 取得 token，記下 token_ttl 與 token_max_ttl。
  2. 啟動 background goroutine / async task：每 2/3 × ttl 跑一次 renew-self。
  3. Renew 失敗 → 等待短暫 backoff → 重新 login。
  4. 到 max_ttl 之後 renew 一定失敗，強制重新 login（因為到 max 即使 renew 也沒用）。
  5. 重新 login 失敗 → backoff 重試（不要瞬間打爆 OpenBao）。

OpenBao Go SDK 的 LifetimeWatcher 已內建這套邏輯。其他語言如果無對等元件，建議照這個 pattern 自己實作（或直接走 OpenBao Agent，省事）。

28.10 ⚙ 動手練習

  1. 挑一個你熟的語言，寫一段 client：登入 → 讀 KV → 取 DB dynamic creds → 續租 → 退出時 revoke。
  2. 故意把 token TTL 設成 1 分鐘，觀察 LifetimeWatcher（或自己的 renewer）是否在 40s 左右 renew。
  3. 對 OpenBao server 重啟 / kill -9，看你的應用能否優雅重連。

Chapter 29CI/CD 整合

CI/CD 是機器身份使用 OpenBao 的典型場景：每個 build / deploy 工作要拿到雲端 API key、deploy key、registry credentials。把這些放進 GitHub / GitLab Secrets 不夠 — 那只是把問題換個地方。本章談把 CI/CD 真正接進 OpenBao 的方式。

29.1 CI 取 secret 的三種模式

模式機制安全性適合
① CI 平台原生 secrets 把 secret 存在 CI 平台 (GitHub Actions secrets) 低（platform 共用、難稽核） 小團隊、低風險 secret
② AppRole + 預先放 role_id/secret_id CI 用 AppRole login OpenBao 中 不支援 OIDC 的 CI 平台
③ OIDC federation CI 簽 OIDC JWT，OpenBao JWT auth 驗 高（無長期 credential） 主流推薦

29.2 GitHub Actions + OIDC（推薦模式）

① OpenBao 端設定

OpenBao JWT auth method 信任 GitHub 的 OIDC issuer：

$ bao auth enable -path=jwt-github jwt

$ bao write auth/jwt-github/config \
    bound_issuer="https://token.actions.githubusercontent.com" \
    oidc_discovery_url="https://token.actions.githubusercontent.com"

# 限定只能來自 my-org 的 main branch 工作流
$ bao write auth/jwt-github/role/deploy-prod \
    role_type="jwt" \
    user_claim="actor" \
    bound_audiences="https://github.com/my-org" \
    bound_claims_type="glob" \
    bound_claims='{"repository":"my-org/*","ref":"refs/heads/main"}' \
    policies="deploy-prod" \
    token_ttl=15m token_max_ttl=30m

② Workflow YAML

name: deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write     # 讓 workflow 簽 OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - name: Authenticate to OpenBao
      uses: hashicorp/vault-action@v3
      with:
        url: https://bao.example.com:8200
        method: jwt
        path: jwt-github
        role: deploy-prod
        # OIDC token 由 vault-action 自動取得 GitHub 簽的 JWT
        secrets: |
          secret/data/deploy/aws AWS_ACCESS_KEY_ID | AWS_ACCESS_KEY_ID ;
          secret/data/deploy/aws AWS_SECRET_ACCESS_KEY | AWS_SECRET_ACCESS_KEY ;
          database/creds/deploy-rw username | DB_USER ;
          database/creds/deploy-rw password | DB_PWD ;

    - name: Deploy
      run: ./scripts/deploy.sh

整段流程沒有任何長期 secret存在 GitHub。每次 workflow 都向 GitHub 拿一個 1 分鐘的 OIDC token，向 OpenBao 換 15 分鐘的 BAO token，再用它取 deploy 用的 secret。

注意 vault-action 雖然名字是 vault，但對 OpenBao 完全相容（API 一致）。

29.3 GitLab CI + OIDC

GitLab 17+ 內建 OIDC token 簽發 (id_tokens)：

# OpenBao 端類似設定，bound_issuer 改成 GitLab：
$ bao write auth/jwt-gitlab/config \
    bound_issuer="https://gitlab.com" \
    oidc_discovery_url="https://gitlab.com"

$ bao write auth/jwt-gitlab/role/deploy \
    role_type="jwt" \
    user_claim="user_login" \
    bound_audiences="https://bao.example.com" \
    bound_claims='{"project_path":"my-group/my-project","ref":"main","ref_type":"branch"}' \
    policies="deploy"
# .gitlab-ci.yml
deploy:
  image: alpine:latest
  id_tokens:
    BAO_JWT:
      aud: https://bao.example.com
  script:
    - apk add --no-cache curl jq
    - export BAO_TOKEN=$(curl --silent --request POST \
        --data "{\"jwt\": \"$BAO_JWT\", \"role\": \"deploy\"}" \
        https://bao.example.com:8200/v1/auth/jwt-gitlab/login \
        | jq -r '.auth.client_token')
    - export DB_PWD=$(curl --silent -H "X-Vault-Token: $BAO_TOKEN" \
        https://bao.example.com:8200/v1/database/creds/deploy \
        | jq -r '.data.password')
    - ./deploy.sh
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

29.4 AppRole CI 模式（OIDC 不可用時）

當你的 CI 不支援 OIDC（自架 Jenkins、舊版 Tekton、TeamCity⋯）：

  1. OpenBao 端建立一個 AppRole role，secret_id_num_uses=1 或 2（每 build 一張）。
  2. 長期注入 role_id（公開）到 CI 變數。
  3. 由一個 trusted 排程器 / 控制平面，每次 build 開始前生成新的 secret_id，透過 response wrapping 傳給 build job。
  4. Build job 用 bao unwrap 取出 secret_id，與 role_id 一起 login，得到 token。
  5. Token 完成 build 工作後 revoke。

這個流程稱為 secure introduction，在沒有 OIDC 信任鏈時是可行替代方案，但比 OIDC federation 多一層維運（需要 trusted 控制器）。

Terraform Vault provider 對 OpenBao 完全相容（兩者都遵循 Vault API），可直接用：

provider "vault" {
  address = "https://bao.example.com:8200"
  # token 從環境變數讀

# 把 OpenBao 當「機敏值來源」（讀 secret 提供給其他 resource）
data "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "myapp/db"
}

  password = data.vault_kv_secret_v2.db.data["password"]
  # ...
}

# 把 OpenBao 當「IaC 管控對象」（建立 mount、policy、role）
resource "vault_mount" "kv" {
  path        = "team-a/secret"
  type        = "kv-v2"
  description = "Team A KV"
}

resource "vault_policy" "team_a_ro" {
  name   = "team-a-ro"
  policy = file("${path.module}/policies/team-a-ro.hcl")
}

resource "vault_kubernetes_auth_backend_role" "team_a" {
  backend                          = "kubernetes"
  role_name                        = "team-a-app"
  bound_service_account_names      = ["myapp"]
  bound_service_account_namespaces = ["team-a"]
  token_policies                   = [vault_policy.team_a_ro.name]
  token_ttl                        = 3600
  token_max_ttl                    = 86400
}

注意：

  • Provider 名稱仍是 hashicorp/vault（OpenBao 沒自己的 provider，第三方 fork 也存在但較少維護）。
  • OpenTofu 1.10 起原生支援用 OpenBao 的 Transit 加密 state file，這是另一個 OpenBao + OpenTofu 整合場景。

  • 在 Pipeline 裡用 withVault wrapper 注入：
// Jenkinsfile
pipeline {
  agent any
  stages {
    stage('deploy') {
      steps {
        withVault(configuration: [vaultUrl: 'https://bao.example.com:8200',
                                  vaultCredentialId: 'bao-approle'],
                  vaultSecrets: [
                    [path: 'secret/data/deploy/aws',
                     secretValues: [
                       [vaultKey: 'access_key', envVar: 'AWS_ACCESS_KEY_ID'],
                       [vaultKey: 'secret_key', envVar: 'AWS_SECRET_ACCESS_KEY'],
                     ]],
                  ]) {
          sh './deploy.sh'
        }
      }
    }
  }
}

29.8 ⚙ 動手練習

  1. 把你的某個 GitHub repo 接 OpenBao（OIDC mode），讓 deploy workflow 取得一個短期 secret。
  2. 用 Terraform Vault provider 寫一份 IaC，建立一個 namespace + KV mount + policy + role。
  3. 把該 IaC 放進另一個 GitHub repo，做 plan/apply 兩階段 workflow。

Chapter 30平台整合（Platforms）

不同平台給應用注入 OpenBao secret 有幾種主流模式。本章把 K8s 上的三種常見模式對比清楚，並摘要主要雲平台（AWS / GCP / Azure）整合 OpenBao 的方式。

30.1 K8s 上應用取 secret 的三種模式

第三冊提過 KV / Database engine，第四冊提過 Agent injector。把全部 K8s 取 secret 的選項並列：

模式機制應用感知適合
① Agent Injector（sidecar / init container） Annotation 觸發 sidecar 注入；Agent 把 secret 寫成檔案 讀檔即可 主流推薦，特別是 legacy app
② CSI Provider OpenBao secret 作為 CSI volume 掛載 讀檔即可（路徑固定） Kubernetes-native；多 volume 場景
③ Direct API 應用直接用 SDK 跟 OpenBao 通訊 需要 SDK 整合 需要動態取不同 secret 的應用；非 KV 為主的場景

30.2 模式 ①：Agent Injector（最常見）

已經在第四冊第 23 章詳細介紹過。簡述要點：

  • 安裝方式：Helm chart 內 injector.enabled=true。
  • 用法：在 Pod 上加 annotation：vault.hashicorp.com/agent-inject: "true" + vault.hashicorp.com/role: "myapp"。
  • 輸出：secret 寫到 /vault/secrets/<name>。
  • 動態 cred 自動續租：sidecar 模式下，DB cred lease 自動 renew。

30.3 模式 ②：CSI Provider

K8s Secrets Store CSI Driver 是 CNCF 專案，提供「把外部 secret store 當 volume 掛載」。OpenBao 對應 CSI provider 可掛載 secret 成檔案，跟 Agent Injector 類似但走 CSI 規範。

安裝

$ helm install csi-secrets-store secrets-store-csi-driver/secrets-store-csi-driver \
    -n kube-system

# OpenBao chart 內 csi.enabled=true（與 injector 互斥使用更乾淨）
$ helm upgrade openbao openbao/openbao -f values.yaml \
    --set csi.enabled=true

使用：SecretProviderClass

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: myapp-secrets
  namespace: production
spec:
  provider: vault
  parameters:
    vaultAddress: "https://bao.example.com:8200"
    roleName: "myapp"
    objects: |
      - objectName: "db-pwd"
        secretPath: "secret/data/myapp/db"
        secretKey: "password"
      - objectName: "api-key"
        secretPath: "secret/data/myapp/api"
        secretKey: "key"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      serviceAccountName: myapp
      containers:
      - name: app
        image: myorg/myapp:v1
        volumeMounts:
        - name: secrets
          mountPath: /mnt/secrets
          readOnly: true
      volumes:
      - name: secrets
        csi:
          driver: secrets-store.csi.k8s.io
          readOnly: true
          volumeAttributes:
            secretProviderClass: myapp-secrets

應用就讀 /mnt/secrets/db-pwd 與 /mnt/secrets/api-key 即可。

CSI vs Injector 怎麼選？

  • Injector 更接近原生「Vault 風格」，模板能力更強（可組合多個 secret 渲染成設定檔）。
  • CSI 更 Kubernetes-native，跟其他 Secrets Store（Azure Key Vault、AWS Secrets Manager）走相同 abstraction。
  • 多數環境二者擇一即可，混用會造成認知負擔。

30.4 模式 ③：Direct API

應用本身有 OpenBao client SDK 整合（第 28 章）。優點是動態行為：

  • 運行時根據 user 動態決定要取哪個 secret。
  • 用 Transit engine 加解密（不只是讀 KV）。
  • 需要 cubbyhole / response wrapping 之類進階功能。

缺點是每個應用要自己處理 token / lease，除非搭配 OpenBao Agent 做 API proxy（應用打 localhost:8200，Agent 自動加 token）。

30.5 三種模式組合的實務 pattern

真實 production 通常同時有多種模式：

  • Stateless web app：Injector 把設定檔寫好，啟動即用。
  • Worker / Job：CSI 掛幾個固定 secret，啟動即用。
  • 需要 transit 加密的服務：Direct API + Agent API proxy。
  • 多 namespace 的 platform：Injector，每個 namespace 各自 SA + role。

30.6 主要雲平台整合摘要

① AWS

  • Auto-unseal：AWS KMS（第二冊第 6 章）。
  • Auth：AWS auth method 支援 EC2 instance metadata / IAM role；K8s 上 EKS pods 用 IRSA + AWS auth method。
  • Dynamic AWS keys：aws secret engine 動態產 IAM access key（短期）。
  • Storage：DynamoDB backend（已被 Raft 取代為主流）。
  • EKS Pod Identity：較新的 AWS-native 替代 IRSA 的方式，OpenBao 對應的 role 設定相同邏輯。

② GCP

  • Auto-unseal：GCP Cloud KMS。
  • Auth：GCP auth method 用 IAM signed JWT；GKE 上 Pod 配 Workload Identity → JWT auth method。
  • Dynamic GCP creds：gcp secret engine。
  • Storage：GCS backend（OpenBao 上是否仍維護視版本而定）。

③ Azure

  • Auto-unseal：Azure Key Vault。
  • Auth：Azure auth method 用 MSI（Managed Service Identity）。
  • Dynamic Azure SP：azure secret engine。

④ Oracle Cloud / 阿里雲 / 其他

都有對應的 KMS auto-unseal 與 auth method。詳見官方 seal stanza 文件。

30.7 ⚙ 動手練習

  1. 同一個應用 Deployment，分別用 Injector 模式與 CSI 模式試一次，比較 manifest 與 Pod 內檔案。
  2. EKS（或 GKE / AKS）上配 IRSA + OpenBao auto-unseal，從 OpenBao 端發 dynamic AWS IAM key，跑一個能列 S3 的應用。
✓ 章末重點
  • K8s 三種模式：Injector（主流）、CSI（K8s-native）、Direct API（需動態行為）。
  • Injector 與 CSI 二擇一，避免混用。
  • CI/CD 接 OpenBao 推薦用 OIDC federation；OpenTofu 1.10 原生支援 OpenBao。
  • 三大雲都有對應的 auto-unseal、auth method、dynamic creds engine。

Chapter 31安全強化（Hardening）清單

「我們有 OpenBao 了，所以資料是安全的」是危險錯覺。沒有正確的 hardening，OpenBao 反而把所有 secret 集中變成更大的攻擊目標。本章是上 production 前必須跑過的清單。

31.1 為什麼要特別 hardening

OpenBao 的威脅模型清楚定義：「OpenBao client 與 server 之間沒有相互信任。Storage backend 也是 untrusted 的。」。這意味著 OpenBao 假設：

  • Network 上有人嘗試 MITM → 必須 TLS。
  • Storage 可能被人取得備份 → 已加密，但 unseal key 不能跟 storage 一起放。
  • 內部使用者可能濫用權限 → policy 必須最小化、root token 必須最小化。
  • 稽核紀錄可能被修改 → audit 必須開且外送。

這些假設要靠 hardening 落實。

31.2 必做：TLS Everywhere

① Listener TLS

  • 禁止 tls_disable=true，除非是純內部 metrics listener 綁 127.0.0.1。
  • tls_min_version 至少 tls12，新環境設 tls13。
  • 使用有效 CA 簽過的 cert（內部 CA OK），不要 self-signed 給多人共用。
  • 定期更換 cert，最好 ≤ 90 天 TTL（用 cert-manager 或 ACME 自動化）。

② Cluster 節點之間的 TLS

HA cluster 節點互相通信也需要 TLS。OpenBao 內部 cluster_address 預設用內部產生的 mTLS（每個 cluster 一個 CA，自動旋轉），但初始 join 時需要明確 TLS：

storage "raft" {
  retry_join {
    leader_api_addr     = "https://bao-1.internal:8200"
    leader_ca_cert_file = "/etc/openbao/tls/ca.crt"
    leader_tls_servername = "bao.internal.example.com"
  }
}

③ Storage 後端 TLS

用 PostgreSQL / 其他外部 storage 時，連線必須 SSL：

storage "postgresql" {
  connection_url = "postgresql://user:pwd@pg:5432/openbao?sslmode=verify-full&sslrootcert=/etc/openbao/pg-ca.crt"
}

31.3 必做：Root Token 最小化

官方明確說：「Root token 應該只在初始設定（建立 auth methods 與 policies）或緊急狀況下使用，且使用後立即 revoke」。

標準流程

  1. Init 完成後立刻用 root token 做：(a) 啟用 audit；(b) 建第一批 admin auth method（OIDC / userpass）；(c) 建 admin policy。
  2. 登出 root token，登入 admin 帳號。
  3. Revoke 該 root token：bao token revoke <root_token>。
  4. 之後需要 root 時，用 bao operator generate-root（需要 unseal/recovery key threshold），用完再 revoke。

另一個建議：「使用 root token 時，建議多人見證 — 在 terminal 上至少兩人在場，便於互相確認動作」。

31.4 必做：Audit 必開、且至少兩個

第四冊第 24 章已詳述。重點：

  • Audit 是 OpenBao 唯一可信的事後鑑識來源。
  • 同時啟用 file + syslog（或 socket），避免單一 device 故障導致整體癱瘓。
  • Audit log 必須外送異地（SIEM / Elasticsearch / Loki），本機 log 隨時可能被攻擊者刪。
  • Audit log 必須對應到外部時間源（NTP），事後對時間軸才有意義。

31.5 必做：Network 隔離

  • OpenBao 不該在公網。即使有 TLS，公網暴露增加 brute force / DDoS 攻擊面。
  • 放在內網或 VPC private subnet，透過 LB / Ingress 暴露給特定來源。
  • 用 Security Group / NetworkPolicy 限制：
    • 8200（API）：只允許應用網段。
    • 8201（cluster）：只允許 cluster 內節點互通。
    • 8220（metrics）：只允許 Prometheus 來源。
  • K8s 上配 NetworkPolicy 限制 namespace 之間：
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: openbao-allow
  namespace: openbao
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: openbao
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          openbao-access: "allowed"
    ports:
    - port: 8200
  - from:
    - podSelector:
        matchLabels:
          app.kubernetes.io/name: openbao
    ports:
    - port: 8201   # cluster 內互通

31.6 必做：Seal Key 嚴格保管

不論 Shamir 還是 auto-unseal recovery key，都是「能解整個 OpenBao」的鑰匙：

  • 分散保管：N 份 shares 給 N 個不同人。絕對不要把 N 份都放同一台機器或同一個帳號。
  • 離線儲存：紙本 + 防火保險櫃 / 加密 USB / 可信 vaulting service。
  • 用 PGP 加密：init 時用 -pgp-keys，每個 share 對應收件人公鑰加密，攻擊者拿到 init log 也無用。
  • 定期 rekey：人員變動、定期審計時用 bao operator rekey。
  • 記錄持有人名單：誰有第幾片，離職時要回收 + rekey。

31.7 必做：Memory 保護

  • Bare metal / VM：保留 mlock（OpenBao 預設啟用），禁用 swap 或加密 swap。第一冊第 3 章詳述。
  • Container：給 IPC_LOCK capability；如果 K8s PSS 不允許，至少確保 node --fail-swap-on=true。
  • 禁止 core dump：systemd unit 加 LimitCORE=0，防止 OOM 時把記憶體 dump 落盤。
  • 禁止 ptrace：systemd unit 加 NoNewPrivileges=true、ProtectKernelTunables=yes。

建議的 systemd unit 範本（參考第三方教學）：

[Unit]
Description=OpenBao Secret Management
Documentation=https://openbao.org/docs
Requires=network-online.target
After=network-online.target

[Service]
User=openbao
Group=openbao
ProtectSystem=full
ProtectHome=read-only
PrivateTmp=yes
PrivateDevices=yes
SecureBits=keep-caps
AmbientCapabilities=CAP_IPC_LOCK
CapabilityBoundingSet=CAP_SYSLOG CAP_IPC_LOCK
NoNewPrivileges=yes
ExecStart=/usr/local/bin/bao server -config=/etc/openbao/config.hcl
KillMode=process
KillSignal=SIGINT
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
StartLimitIntervalSec=60
StartLimitBurst=3
LimitNOFILE=65536
LimitMEMLOCK=infinity
LimitCORE=0
MemorySwapMax=0

[Install]
WantedBy=multi-user.target

31.8 必做：Resource Quota

第二冊第 10 章已介紹 rate-limit 與 lease-count quota。Production 強烈建議：

  • 全域 rate limit：根據 cluster 容量設一個 ceiling（例：rate=5000, interval=1s）。
  • 每 namespace lease quota：避免單一團隊 lease 失控（例：max_leases=10000）。
  • Audit 開但別計入 rate：sys/health、sys/seal-status 加進 quota exempt list。

31.9 強烈建議：Mlock + IPC_LOCK + 非 root user

  • OpenBao process 不要用 root 跑（用專用 openbao user）。
  • 但給該 user CAP_IPC_LOCK，這樣 mlock 仍能用。
  • 檔案權限：
    • config 檔：0640 root:openbao 或 openbao:openbao。
    • TLS key：0600 openbao:openbao。
    • data 目錄：0700 openbao:openbao。
  • OpenBao 提供 file permission check：環境變數 VAULT_ENABLE_FILE_PERMISSIONS_CHECK=true 啟用啟動時檢查。

31.10 強烈建議：Disable 不必要的端點

  • Disable unauthed generate-root：v2.5.3 起 disable_unauthed_generate_root_endpoints=true 已是預設。確認你的設定沒有改成 false。
  • Profiling 端點：pprof 預設關，沒事不要開（debug 完關掉）。
  • Metrics 端點：用獨立 listener + 內網綁定，不要開在 public listener 上。

31.11 強烈建議：Backup + DR 演練排程

第四冊第 26 章已詳述。提醒：

  • Snapshot job：至少每 4 小時一次，異地保存，加 KMS 加密。
  • 每月跑一次恢復演練（在 staging 上）。
  • 每年至少一次整 cluster 災難演練。

Chapter 32Policy 與權限治理

Policy 寫得不好，OpenBao 反而成為「什麼都拿得到，卻沒人記得是誰拿的」的災難。本章把 policy 的長期治理 — review、版本控制、break-glass 帳號、定期審計 — 走過一遍。

32.1 Policy as Code 工作流

① 為什麼要 IaC 化

  • Review-able：Policy 改動透過 PR 走過 reviewer，杜絕「root token 偷偷新增權限」。
  • 可追溯：Git history 記錄誰、什麼時候、為什麼改。
  • 可重現：disaster recovery 時整個權限結構能從 git 還原。
  • 環境一致：dev / staging / prod 共用同一份 policy 定義，避免 prod 跟 staging 行為不同。

② 標準 repo 結構

openbao-config/
├── policies/
│   ├── admin.hcl
│   ├── app-myapp-ro.hcl
│   ├── app-myapp-rw.hcl
│   ├── pki-issuer.hcl
│   └── ...
├── auth/
│   ├── kubernetes-roles.tf
│   ├── jwt-github-roles.tf
│   └── userpass-admins.tf
├── secrets/
│   ├── kv-mounts.tf
│   ├── pki-mounts.tf
│   └── database-roles.tf
├── audit/
│   └── audit-devices.tf
└── README.md

Policy 文件用 .hcl，OpenBao 物件（mount / role / auth method）用 Terraform。

③ Pull Request 工作流

  1. 開發者開 PR：「我想要加 secret/data/team-x/* 的 read 權限給 team-x-app role。」
  2. CI 跑：(a) terraform plan；(b) policy syntax 檢查；(c) 自動化規則檢查（見下節）。
  3. Reviewer（security team + 對應團隊負責人）審核。
  4. 合併後 CI 自動 terraform apply 到 staging。
  5. 觀察 24h，再人工觸發 prod apply。

32.2 Policy 自動化檢查

Policy review 時容易疏忽的點，用 CI 自動擋下：

① 禁止 wildcard sudo

# 用 grep 簡單擋
$ if grep -RE '"sudo"' policies/ | grep -v 'admin\.hcl'; then
    echo "ERROR: sudo only allowed in admin policy"; exit 1
  fi

② 禁止 path "*"

$ if grep -E 'path\s+"\*"' policies/; then
    echo "ERROR: wildcard root path not allowed"; exit 1
  fi

③ 強制每個 policy 都有 metadata 註解

# app-myapp-ro.hcl
# Owner: team-platform
# Granted-to: K8s SA myapp in production namespace
# Review-due: 2026-08-01
# Ticket: PLAT-1234

path "secret/data/myapp/*" {
  capabilities = ["read"]
}
...

CI 檢查每個 policy 開頭有 Owner:、Granted-to:、Review-due: 三個 header，否則拒絕合併。

32.3 Policy 審查清單

Reviewer 在批 PR 前對照這個清單：

  • ✅ 最小權限：只給絕對必要的 capability。需要 read 不要給 update；需要 list 不要給 read。
  • ✅ 路徑明確：避免 secret/data/* 這種「整個 mount」grant；改用 secret/data/team-x/*。
  • ✅ 不要混用 mount：一個 policy 不要同時管 KV 和 PKI（職責分離）。
  • ✅ KV v2 雙路徑都要寫：secret/data/... 與 secret/metadata/...。
  • ✅ 危險動作明確 deny：metadata delete、destroy 在 app policy 裡明確 deny。
  • ✅ 引用 templated 而非 hardcode：能用 {{identity.entity.aliases.<mount>.name}} 就用。
  • ✅ 不該有 sudo：除了 admin policy，其他 policy 不該有 sudo。
  • ✅ Token TTL 合理：對應 role 的 token TTL 別超過 8h（人類）/ 24h（機器）。

32.4 Break-Glass 帳號設計

所有 OpenBao operator 帳號都被鎖出去（OIDC provider 掛了、root token revoke 了、admin user 都離職）— 怎麼辦？

解法：break-glass 帳號 — 一個平時不用、緊急時可動用的高權限路徑。

建議模式

  1. 建立一個 auth/userpass-breakglass/ mount，密碼設為複雜隨機值。
  2. 密碼不放任何系統，分成三份用 PGP 加密交給三位 senior（與 unseal key 持有人不同）。
  3. 對應的 policy 有 admin 權限，但每次使用都會觸發 audit alert。
  4. Audit log 配警報：auth/userpass-breakglass/login 出現 → SOC 立刻 page。
  5. 每年至少測試一次（演練 + 換密碼）。

另一個選項：依賴 generate-root 流程（需要 unseal/recovery key threshold），不另設 break-glass 帳號。優點：減少 surface；缺點：需要召集 key holder，較慢。

32.5 定期 Policy Review

Policy 隨時間會「累積」 — 應用退役、團隊重組，但對應 policy 還在。建議：

  • 每季 review 全部 policy 的 Review-due header；過期的 policy 必須 owner 重新確認或關閉。
  • 每年 對 audit log 做使用率分析：哪些 policy 從來沒被 token attach 過 → 提案刪除。
  • 觸發式 review：團隊重組、人員變動、應用下架時，立即 review 受影響 policy。

32.6 Wrap TTL 強制

第二冊第 9 章介紹過 response wrapping。Policy 可以強制某些 path 的 response 必須 wrap：

path "auth/approle/role/+/secret-id" {
  capabilities = ["create", "update"]
  min_wrapping_ttl = "1s"      # 強制必須 wrap
  max_wrapping_ttl = "5m"      # 最久 5 分鐘
}

這保證 secret_id 永遠以 wrap 形式傳遞，避免 plain 的 secret_id 出現在 CI log。

32.7 ⚙ 動手練習

  1. 把現有 policy 全部從 OpenBao 抓出來放進 git，補上 metadata header。
  2. 寫一個 CI script，跑 policy syntax 檢查（bao policy fmt）+ wildcard 檢查。
  3. 建立一個 break-glass userpass，配對應 audit alert 規則。
  4. 挑一個目前的 policy，用 -output-policy 反推它真正需要的最小集，比較與現況。

Chapter 33OpenBao 安全內部運作

本章是給好奇的人、做安全稽核的人、寫 RFC 與 plugin 的人。理解 OpenBao 內部加密層次，能讓你回答稽核員的問題，也能讓你在做進階決策（key import、HSM 整合、cross-cluster 搬遷）時不踩雷。

33.1 加密三層結構

OpenBao 內部其實是三層 key 結構：

33.2 第三層：Barrier Keyring

所有真正的業務資料（KV、token entries、lease、policy 等）寫到 storage 前都先經過 barrier。Barrier 用一組 AES-256-GCM keys（稱 keyring）加密 / 解密：

  • 96-bit nonce，所以同一把 key 用 ~ 2³² 次後就要 rotate（NIST 800-38D）。
  • OpenBao 會自動偵測接近上限並自動 rotate。
  • 每一筆 storage entry 的 ciphertext 開頭包含 key version，讓 OpenBao 在多版本共存時知道用哪把解。

33.3 第二層：Root Key

Root key 用來加密整個 barrier keyring。當你看到 core/keyring 在 storage 裡是加密的，加密用的就是 root key。

Root key 不寫到 storage（只有用 root key 加密過的 barrier keyring 在 storage）。它在 server 啟動時由 unseal 流程注入記憶體。

33.4 第一層：Seal Mechanism

Seal mechanism 負責保護 root key。三種類型：

  • Shamir：root key 用 Shamir 拆分，N 份 shares 存在 N 處（通常人手保管）。Threshold 數量的 shares 才能重組 root key。
  • Auto-unseal (KMS / HSM)：root key 用 KMS / HSM 的 key 包裹後存 storage。Server 啟動時呼叫 KMS 解開。
  • Transit auto-unseal：用另一個 OpenBao/Vault 的 transit key 包裹 root key。

33.5 Key Rotation 詳解

OpenBao 有兩種 rotation：

① rotate/keyring — 換 barrier keyring

產生新的 barrier key，加入 keyring。新寫入用新 key，「舊 keys 保留在 keyring 中以解密舊資料」。這是線上操作，不需要使用者參與。

$ bao operator rotate
Key Term            8
Install Time        2026-05-05T...

# 自動排程
$ bao write sys/rotate/keyring/config \
    interval=2160h \
    max_operations=2000000000

OpenBao 啟動自動追蹤每個 key 的使用次數，接近 2³² 時觸發 rotation。多數 operator 不需要手動跑。

② rotate/root — 換 root key（Shamir rekey）

對 Shamir：產生新 root key，重新拆 shares，舊 unseal keys 失效。需要持有舊 threshold 數量 shares 的人協作完成。

對 auto-unseal：類似流程，但用 KMS 而非人手。

# 啟動 rekey 流程
$ bao operator rekey -init -key-shares=5 -key-threshold=3

# 持有 share 的人各自貢獻
$ bao operator rekey -nonce=<nonce>
Unseal Key (will be hidden): ...

# 達到 threshold 後得到新 shares

什麼時候做：人員變動、定期審計、確認 share 持有人有效。

33.6 Storage 上的 Entry 結構

Storage 中的每筆資料（ciphertext）結構大致：

+-----------------+----------------+-----------------+
| 1 byte version  | 4 byte term    | nonce + ciphertext + tag |
+-----------------+----------------+-----------------+
  • version：barrier 格式版本。
  • term：對應 keyring 內的 key 版本（rotate 後 +1）。
  • nonce + ciphertext + auth tag：AES-GCM 標準輸出。

這就是為什麼 storage 備份本身對攻擊者沒用 — 沒有對應 keyring（在 root key 加密下）就是 random bytes。

33.7 PGP / Keybase / GnuPG 的角色

PGP 在 OpenBao 中只用在三個地方：

  • operator init -pgp-keys：每個 unseal share 用對應收件人公鑰加密。
  • operator init -root-token-pgp-key：把 init 產生的 root token 用 PGP 加密。
  • operator generate-root -pgp-key：補發 root token 時用 PGP 加密結果。

OpenBao 接受三種等價形式：

  • 本機 ASCII-armored PGP key file：alice.asc。
  • Keybase username：keybase:alice（OpenBao 自動下載對應公鑰）。
  • 多個合用：-pgp-keys="alice.asc,keybase:bob,keybase:carol"。

使用 PGP 的好處：init log 即使被人看到（截圖、log aggregator），單份 share 仍是密文。

33.8 Cluster 內部 mTLS

Cluster 節點互相通信用內部生成的 mTLS：

  • 每個 cluster 啟動時生成一個 internal CA。
  • 每個節點生成自己的 cert，由 cluster CA 簽。
  • 所有節點互相驗證對方 cert（mutual TLS）。
  • Internal CA 與 cluster cert 定期自動 rotate。

這保證即使有人在 cluster 網路上攔截，也無法偽裝成 cluster 節點。

33.9 安全模型總結

OpenBao 在做的事可以總結為：

  1. Network 層：強制 TLS，拒絕 MITM。
  2. 身份層：所有操作都需要 token，token 透過 auth method 驗證身份取得。
  3. 授權層：所有操作受 policy 檢查，default deny。
  4. 稽核層：每筆 request/response 寫進 audit log（HMAC 機敏值）。
  5. 傳輸層加密：cluster 內 mTLS、storage 連線 TLS。
  6. 儲存層加密：barrier keyring 加密 → root key 加密 → seal mechanism 保護。
  7. 記憶體保護：mlock 防 swap，core dump 禁用。

每一層都假設前一層可能失守，這就是 defense in depth 的設計哲學。

33.10 ⚙ 動手練習

  1. 跑 bao read sys/key-status 看當前 keyring term。
  2. 手動跑一次 bao operator rotate，再 read 看 term + 1。
  3. 讀完一篇官方 Security Model 文件，把上面 7 條總結對應到文件中的描述。
✓ 章末重點
  • 三層加密：Seal mechanism → Root key → Barrier keyring。
  • Barrier 用 AES-256-GCM；接近 2³² 操作自動 rotate。
  • Storage 上的 ciphertext 包含 term，多版本共存可解舊資料。
  • PGP 用於 init / generate-root，保護 share 與 root token 的初始傳遞。
  • Cluster 內部 mTLS 自動建立與 rotate。
