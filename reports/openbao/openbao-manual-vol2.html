第一冊讓你跑起 OpenBao、寫了第一個 secret。但那是用 root token 暴力解。實際工作中你不會把 root token 給應用、不會用 dev mode、也不會永遠靠記憶體存 secrets。本冊是補上這些「真實世界缺角」的關鍵章節。

Chapter 6Seal/Unseal 與初始化

為什麼 OpenBao 啟動時會「開不了」？為什麼需要好幾個人拿著各自的 key 才能讓它運作？這個設計叫 sealing，是 OpenBao 整套安全模型的根基。理解它，你才能合理地處理 production 的啟動、HA、災難復原。

6.1 為什麼要有 Seal 機制

① 概念導讀

OpenBao 把所有資料用一把 encryption key（barrier key 或 root key）加密後，才寫到 storage backend。這把 key 必須在記憶體裡才能解資料 — 但它不能跟 storage 一起存，否則拿到 storage 備份的人就能解一切。

所以這把 key 必須在 server 啟動後「從外部注入」進來。注入完成前，server 處於 sealed 狀態：可以接受 unseal 請求，但拒絕所有業務請求。注入完成後變成 unsealed，正常服務。

更進一步：OpenBao 不希望這把 key 由「單一人」掌握。所以它用 Shamir's Secret Sharing 把 key 拆成 N 份（shares），需要其中至少 K 份（threshold）才能重組。這就是為什麼 unseal 通常需要多個操作員協同完成。

② Seal 在 OpenBao 中真正保護什麼

嚴謹一點看，OpenBao 內部其實是兩層 key：

  • Barrier keyring：實際拿來加密 / 解密 storage 內容的對稱 key 集（會 rotation）。
  • Root key：用來加密 barrier keyring 本身。

Shamir / auto-unseal 機制保護的是 root key。Server 啟動時：

  1. 從 storage 讀出加密後的 barrier keyring。
  2. 等待 unseal 機制提供 root key。
  3. 用 root key 解出 barrier keyring。
  4. 用 barrier keyring 解開後續所有資料。

6.2 第一次啟動：Initialize

初始化只會做一次，產生 root key、unseal shares、初始 root token。之後即使重啟，也只需要 unseal 不需要重 init。

準備一個非 dev 的 server 設定

建立 config.hcl：

storage "raft" {
  path    = "/var/lib/openbao/data"
  node_id = "node1"
}

listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_disable = true   # ⚠ 僅本機練習，production 必須啟用 TLS
}

api_addr     = "http://127.0.0.1:8200"
cluster_addr = "https://127.0.0.1:8201"
ui           = true
disable_mlock = true   # 練習用；production 應 enable mlock
$ mkdir -p /var/lib/openbao/data
$ bao server -config=config.hcl &

檢查狀態（應為 sealed + uninitialized）

$ export BAO_ADDR=http://127.0.0.1:8200
$ bao status
Key                Value
---                -----
Seal Type          shamir
Initialized        false
Sealed             true
...

初始化（產生 5 份 share，3 份門檻）

$ bao operator init -key-shares=5 -key-threshold=3
Unseal Key 1: PVdC6mKj1...
Unseal Key 2: 7yT2nQB...
Unseal Key 3: x9F5LVm...
Unseal Key 4: t1AbEh...
Unseal Key 5: K8oSrU...

Initial Root Token: s.AbCd1234...
⛔ 這一刻最危險，也最重要

這 5 把 key 與 root token 是 OpenBao 有史以來唯一一次把它們明文輸出給你的機會。立刻：

  1. 把它們複製到不同的安全位置（例如：分發給 5 位 ops 同事，或寫進 5 個離線、加密的 USB；或用 PGP/Keybase 公鑰預先加密）。
  2. 不要把它們留在這台機器上的歷史紀錄、shell history、vim swap、cloud-init log 裡。
  3. 記下 root token，但儘快用它建立兩三個有限權限的人類管理員帳號，然後 revoke 這個 root token。

用 PGP 加密保護 unseal keys（推薦）

OpenBao init 支援用 PGP 公鑰預先加密每份 share，這樣任何人看 init 的輸出都看不到明文：

$ bao operator init \
    -key-shares=5 -key-threshold=3 \
    -pgp-keys="alice.asc,bob.asc,carol.asc,dave.asc,eve.asc" \
    -root-token-pgp-key="ciso.asc"

每份輸出對應的人，只能用自己的 PGP 私鑰解開。Keybase 也支援 keybase:username 形式的快捷寫法。詳見官方 PGP/GnuPG/Keybase 文件。

6.3 Unseal 流程

OpenBao 啟動後，需要重複呼叫 unseal API 三次（threshold=3），每次提供一份不同的 share：

# 操作員 A
$ bao operator unseal
Unseal Key (will be hidden): <貼入 share 1>
...
Unseal Progress  1/3

# 操作員 B
$ bao operator unseal
Unseal Progress  2/3

# 操作員 C
$ bao operator unseal
Unseal Progress  3/3
Sealed           false  ✓

三位 share 持有者甚至可以從不同地點操作，他們只需各自連到 server 一次、貼入自己的 share，不用見面、不用共享任何資訊。這是 Shamir 設計的精髓。

HA cluster 的 Shamir unseal

多節點 Raft cluster 的話：「每個節點都需要獨立 unseal 到 threshold；部分 unseal 不會自動同步到 cluster」。實務上這就是為什麼大家通常選 auto-unseal。

6.4 Auto-Unseal：把麻煩交給 KMS / HSM

Shamir 概念純粹，但運維代價高 — 每次 server 重啟都要找 3 個人按 enter，這在大規模或 K8s 環境是不可接受的。auto-unseal 把 root key 交給外部可信的金鑰管理服務保管：

  • AWS KMS — EKS / EC2 環境最常見。
  • Azure Key Vault — Azure 環境。
  • GCP Cloud KMS — GCP 環境。
  • OCI KMS — Oracle Cloud。
  • AliCloud KMS — 阿里雲。
  • PKCS#11（HSM、SoftHSM、Securosys 等）— on-prem HSM。
  • Transit — 用另一個 OpenBao/Vault 集群作為 unseal 服務（用於完全 self-hosted）。

AWS KMS 範例

seal "awskms" {
  region     = "us-west-1"
  kms_key_id = "alias/openbao-unseal"
  # 認證可走 IAM Role（建議）或 access key
}

Transit auto-unseal 範例（用另一個 Bao 來解這個 Bao）

seal "transit" {
  address    = "https://unsealer.example.com:8200"
  token      = "<agent token>"
  key_name   = "openbao-unseal-key"
  mount_path = "transit/"
}

Auto-unseal 後 init 的差異

用 auto-unseal 時，operator init 不再產生 unseal keys，而是產生 recovery keys：

$ bao operator init -recovery-shares=5 -recovery-threshold=3
Recovery Key 1: ...
Recovery Key 2: ...
...
Initial Root Token: s....
⚠ Recovery key 跟 unseal key 不一樣

「Recovery keys 不能解密 root key，因此單靠它們無法把 OpenBao 從『auto-unseal 機制壞掉』的狀態救回來；它們是純授權機制」。也就是說：

  • Recovery key 用於：generate-root（補發 root token）、rekey、某些手動 seal 後的解封操作。
  • Recovery key 不能取代 KMS — 如果 KMS key 真的被刪除或永久不可用，「就無法恢復對 OpenBao cluster 的存取」，連備份都救不回來。

因此 auto-unseal 用 KMS 時，KMS key 的保護比拿到它更重要：用 SCP（Service Control Policy）禁止刪除、開啟 versioning、跨帳號隔離管理。

6.5 主動 Seal 與重啟

有時候你會想「立刻把 OpenBao 鎖回去」（例如懷疑入侵）：

$ bao operator seal
Success! OpenBao is sealed.

之後所有業務請求都會回 503，直到再次 unseal。「只要有一個 root 等級的操作員就能 seal」。

節點 unsealed 之後會保持 unsealed，直到下列任一發生：

  • 透過 API seal
  • Server 重啟
  • Storage 層發生不可恢復錯誤

6.6 Recovery Mode

當 OpenBao 的設定壞到連 unseal 都跑不起來（例如 storage corruption、auth 模組異常），可以啟動 recovery mode：

$ bao server -recovery -config=config.hcl

Recovery mode 下，OpenBao 只接受極少數的修復用 API（例如刪除錯誤的 mount entry、重置某些 plugin 設定），不處理一般業務請求。詳見第六冊「排錯手冊」。

6.7 Seal Migration（變更 seal 機制）

已經跑起來的 cluster 想從 Shamir 換成 KMS auto-unseal，或反過來，怎麼辦？OpenBao 支援 seal migration：

  1. 規劃短暫的維護視窗（HA Raft 一次只能讓一個節點下線）。
  2. 把 standby 節點停掉，更新它的 seal 設定（保留舊的、加上新的）。
  3. 啟動該節點，用 -migrate flag 提供舊 unseal key：bao operator unseal -migrate
  4. 所有節點輪流做完同樣動作。
  5. 最後在 active 節點 step down，等 standby 接管後再做。
ℹ 限制

遷移過程中新舊兩種 seal 機制都必須可用。例如從 AWS KMS 遷到 Shamir，AWS KMS 在過程中還是要能用。另外，AWS KMS → AWS KMS 的同型 migration 目前不支援，其他同型都支援。

6.8 三套環境的 Seal 部署模式對照

環境建議 seal 模式原因
本機 / dev Shamir 1/1（甚至 dev mode） 學習友善；資料隨時可丟
單機 Linux/Docker production（小團隊） Shamir 5/3，PGP 加密 share 無雲端依賴；定期重啟頻率低
EKS / GKE / AKS 對應雲的 KMS auto-unseal Pod 重啟頻繁；Shamir 不切實際
純地端 K8s 或 OpenShift PKCS#11（HSM）或 Transit auto-unseal 無雲 KMS 可用
高度合規（金融、政府） HSM + Shamir 緊急 fallback（規劃中 RFC #1830） 金鑰不離開 HSM 邊界 + 緊急復原能力

6.9 ⚙ 動手練習

  1. 用 config.hcl 啟動非 dev server，做一次 5/3 的 init。
  2. 把 5 份 share 複製到 5 個檔案，各加密成不同 PGP 收件人。
  3. 故意只貼 2 份 share 嘗試 unseal，觀察「2/3」進度。
  4. 停掉 server 重啟，觀察 sealed 狀態，再做一次 unseal。
  5. bao operator seal 主動鎖回去，看 bao kv get 拿不到資料。
✓ 章末重點
  • Sealed 狀態 = 無法處理請求 + 沒有人能看到 secret 明文，即使有 storage 全量備份。
  • Init 只做一次；unseal 每次重啟都要做。
  • Shamir：人為控制感最高，運維代價最高。Auto-unseal：相反。
  • Auto-unseal 的 recovery key 不能取代 KMS。KMS key 一旦永久遺失，cluster 也救不回來。

Chapter 7認證（Authentication）

Server unseal 之後，第二個問題就是「誰能進來」。OpenBao 把這件事抽象成「auth method」— 各種把外部身份轉換成 OpenBao token 的橋。本章涵蓋官方文件的所有 auth method，並給出在 Linux/Docker、Kubernetes 三套環境下的選擇建議。

7.1 認證在 OpenBao 中的位置

① 概念導讀

OpenBao 自己不存使用者帳密（除了 userpass，且僅限該 mount）。它把「驗證身份」這件事委託給各種 auth method：使用者帶著外部憑據（密碼、JWT、K8s service account token、TLS cert⋯）來，auth method 驗證後，OpenBao 發一個內部 token 給使用者，並把對應的 policies 綁上去。

所有 auth method 都掛在 auth/ 前綴下，可以同型多次掛載。例如 auth/userpass-dev/ 給開發者、auth/userpass-admin/ 給管理員，兩者完全隔離。

② 兩種主流認證流程：Standard vs Inline

Standard Authentication（多數情況）

Client 先 login → 拿到 token → 之後每個請求都帶 X-Vault-Token header。Token 寫進 storage、能 lease、能 renew。

$ bao login -method=userpass username=alice
$ bao kv get secret/foo  # 自動帶 token

Inline Authentication

不先 login，認證資訊用特殊 header 跟主請求一起送。產生的 token 是 ephemeral（不寫 storage）。

POST /v1/secret/data/foo
X-Vault-Inline-Auth-Path: auth/userpass/login/alice
X-Vault-Inline-Auth-Parameter-password: ...

適合 high-throughput、stateless、不需 lease 的查詢場景。不能跑 MFA，不能用於會產生 lease 的請求。

7.2 Token 認證

① 概念

Token 同時是「認證結果」也是「認證方法」。Token 認證 (auth/token/) 是內建且不可關閉的，從第一個 root token 之後的所有 token 操作都走它。

② Token 的種類

類型特性典型用途
Root token 無 TTL，全權限，唯一可在 init 時產生（或 generate-root） 初始設定、災難復原；用完即 revoke
Service token 有 TTL、可 renew、可 revoke、leases 與其綁定。預設類型。 使用者登入、長期服務、會用到 dynamic secrets 的場景
Batch token 不寫 storage、不可 renew、token 本身就是被簽過的訊息 高頻短期、不需 lease，例如 high-throughput 查 KV
Periodic token 每次 renew 都用 period 而非 TTL，「只要持續 renew 就不會過期」 長期 worker / agent，但你想保留「停了就死」的特性
Orphan token 沒有 parent token，parent revoke 不影響它 中介自動化系統發給應用的 token，避免 cascade revoke

③ 動手：建立各種 token

# 建立一個一般的 service token，TTL 1h，max TTL 4h
$ bao token create -policy=app-ro -ttl=1h -explicit-max-ttl=4h

# 建立 batch token（不寫 storage，超快）
$ bao token create -type=batch -policy=app-ro -ttl=10m

# 建立 periodic token（只要 renew 就不會死）
$ bao token create -policy=worker -period=24h

# 建立 orphan token（root/sudo 限定）
$ bao token create -policy=cron -orphan

④ Renew、Revoke、Lookup

# 續租自己手上的 token
$ bao token renew

# 續租指定 token（需要該 token 或更高權限）
$ bao token renew <token>

# 用 accessor 查或撤銷（不需要知道 token 本身）
$ bao token lookup -accessor <accessor>
$ bao token revoke -accessor <accessor>

# 撤銷某 token 但讓它的 children 變 orphan（不 cascade）
$ bao token revoke -mode=orphan <token>
ℹ Accessor 是什麼

每個 token 都有一個對應的 accessor。Accessor 不能用來認證（不能拿來 read secret），但可以用來：lookup、renew、revoke。Accessor 適合放 audit log、放管理介面，因為即使被偷走，攻擊者也無法用它讀資料。「列出 token 的唯一方法是 auth/token/accessors」。

7.3 Userpass — 給開發者用的本機帳密

適用：本機開發、小團隊、人類使用者；不適用：機器對機器、production 服務帳號。

$ bao auth enable userpass

$ bao write auth/userpass/users/alice \
    password=changeme \
    policies=dev-ro

$ bao login -method=userpass username=alice
Password (will be hidden): ...
Key                   Value
---                   -----
token                 s.qJZ...
token_policies        ["default" "dev-ro"]
...

7.4 AppRole — 機器對機器的金標準

① 概念

AppRole 是 OpenBao 為「機器身份」量身設計的 auth method。它把身份拆成兩個 secret：

  • Role ID（公開）— 像 username，可以放在設定檔。
  • Secret ID（私密、可一次性、可有限次數）— 像 password，需要安全分發。

應用同時提供兩者才能登入，避免單一 leakage。

② 動手：設定 AppRole

$ bao auth enable approle

# 建立一個 role，附帶 policy、token TTL、secret_id 限制
$ bao write auth/approle/role/myapp \
    token_policies=app-ro \
    token_ttl=1h \
    token_max_ttl=24h \
    secret_id_ttl=10m \
    secret_id_num_uses=1

# 取出 role_id（公開）
$ bao read auth/approle/role/myapp/role-id
role_id    7c3d1a9b-...

# 產生一個 secret_id（私密）
$ bao write -force auth/approle/role/myapp/secret-id
secret_id           4e8b62f0-...
secret_id_accessor  ...
secret_id_num_uses  1

# 應用用兩者 login
$ bao write auth/approle/login \
    role_id=7c3d1a9b-... \
    secret_id=4e8b62f0-...

③ 安全分發 secret_id：CI/CD 模式

典型 production 模式：

  1. OpenBao 管理員提前建好 role，把 role_id 放進應用設定 / Helm values / ConfigMap。
  2. CI/CD 在部署時，用自己的 token 跟 OpenBao 要一個 secret_id（secret_id_num_uses=1），透過安全管道（K8s Secret、Argo CD sealed-secret）注入到 Pod。
  3. 應用啟動時 login，拿到正式 token，立刻 revoke 那個 secret_id（已經 1 次用完）。

這個流程稱為 secure introduction（安全引入），第 9 章 response wrapping 會有更安全的版本。

7.5 JWT / OIDC — SSO 整合

JWT auth 接受外部 OIDC provider（Keycloak、Okta、Auth0、Azure AD、Google⋯）簽發的 ID token，驗證簽章後映射到 OpenBao policies。

$ bao auth enable jwt

# 設定 OIDC discovery
$ bao write auth/jwt/config \
    oidc_discovery_url="https://keycloak.example.com/realms/main" \
    default_role="developer"

# 建立 role：把 OIDC 的 group claim 對應到 policies
$ bao write auth/jwt/role/developer \
    user_claim="sub" \
    bound_audiences="openbao" \
    role_type="oidc" \
    allowed_redirect_uris="http://localhost:8250/oidc/callback" \
    allowed_redirect_uris="http://127.0.0.1:8200/ui/vault/auth/jwt/oidc/callback" \
    groups_claim="groups" \
    policies="default,dev-ro"

使用者登入時：

$ bao login -method=oidc role=developer
# 瀏覽器自動開啟 → 完成 OIDC 流程 → 拿到 token

7.6 Kubernetes — Pod 取得 token

Kubernetes auth method 信任 K8s 簽發的 service account token，把它換成 OpenBao token。這是 K8s 上應用取得 secret 的主流方式，第四冊與第五冊會再深入。

設定步驟

$ bao auth enable kubernetes

# 設定 K8s API 與其 CA（OpenBao 透過此驗 SA token）
$ bao write auth/kubernetes/config \
    kubernetes_host="https://kubernetes.default.svc" \
    kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
    token_reviewer_jwt="@/var/run/secrets/kubernetes.io/serviceaccount/token"

# 建立 role：哪個 SA 對應到哪些 policies
$ bao write auth/kubernetes/role/myapp \
    bound_service_account_names=myapp \
    bound_service_account_namespaces=production \
    policies=app-ro \
    token_ttl=1h

Pod 內登入

  name: myapp

  name: myapp

$ JWT=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)

7.7 LDAP / Kerberos / RADIUS / TLS Cert

這幾個是企業內部「接既有身份系統」常用的 method：

Method適用備註
LDAP已用 AD/OpenLDAP 的組織把 LDAP group 對應到 OpenBao policy
KerberosWindows AD 環境，整合 SPNEGO/GSSSSO 體驗，無需重新輸密碼
RADIUS整合 RADIUS server（如老 VPN 環境）較少用於現代 K8s 環境
TLS Certificates (cert)mTLS 客戶端認證適合受控的內部 service-to-service，注意 v2.5.3 修復了 token renewal 漏洞 CVE-2026-39388

7.8 MFA 與 User Lockout

OpenBao 支援 Login MFA：在 auth method 完成後再加一道驗證關卡（TOTP、Duo、PingID、Okta）。設定上是建立 MFA method 後，把它附加到 auth method 的 enforcement：

# 建立 TOTP MFA method
$ bao write sys/mfa/method/totp/my-totp \
    issuer="MyOrg" \
    period=30 \
    key_size=20 \
    qr_size=200 \
    algorithm=SHA1 \
    digits=6

# 把 MFA 套到 userpass auth
$ bao write sys/mfa/login-enforcement/admin-mfa \
    mfa_method_ids=<method_id> \
    auth_method_accessors=<userpass_accessor>

User Lockout 是另一個重要安全機制：對 userpass、ldap、approle 等 method，連續失敗一定次數後鎖定來源帳號。預設啟用，可在 mount 設定中調整 lockout_threshold、lockout_duration。

  2. 啟用 approle，做出一個 secret_id_num_uses=1 的 role，模擬 CI/CD 取得 secret_id 然後使用它。
  3. 嘗試 inline auth：用 curl 帶 X-Vault-Inline-Auth-* header，直接讀 KV，不先 login。
  4. 建一個 batch token 跟一個 service token，比較 token lookup 的差異。
✓ 章末重點

  • 三類核心場景：人類 SSO（OIDC）、K8s 應用（Kubernetes）、VM/CI 機器（AppRole）。
  • Token 有 service / batch / periodic / orphan 四種變形，根據壽命與相依性選擇。
  • Accessor 是「能管不能讀」的 token handle，是 audit 與管理的好朋友。

Chapter 8授權 — Policy 與 Identity

「你是誰」是 auth method 的事，「你能做什麼」就是 policy 與 identity 的事。Policy 是 OpenBao 的 ACL 引擎；Identity 系統把不同 auth method 來的同一個人/機器連在一起。本章學完，你就有能力為一整個團隊規劃可維護的權限結構。

8.1 Policy 基礎：HCL 語法與 Capability

① 概念

Policy 用 HCL（或 JSON）撰寫，描述「允許哪些 path 上做哪些操作」。OpenBao 預設拒絕所有操作，policy 是白名單。一個最小例子：

path "secret/foo" {
  capabilities = ["read"]
}

這個 policy 只能讀 secret/foo。其他 path、其他動作都被拒絕。

② Capability 完整清單

Capability對應 HTTP 動作說明
createPOST/PUT在 path 建立資料
readGET讀取 path
updatePOST/PUT更新 path（或執行寫入動作，如 transit/encrypt）
patchPATCH部分更新（如 KV v2 的 patch）
deleteDELETE刪除 path
listLIST列出 path 下的子項
scanSCAN遞迴列出（OpenBao 新增）
sudo—在受保護的 path（如 sys/ 部分端點）取得提升權限
deny—明確拒絕；優先於其他 capability

③ Path 比對規則

Policy path 支援三種比對：

  1. Exact match — "secret/foo" 只配 secret/foo。
  2. Glob suffix — "secret/foo*" 配 secret/foo、secret/foobar、secret/foo/bar，等同 prefix match。「* 只能放在 path 的最後一字元」。
  3. 單層萬用 + — "secret/+/config" 配 secret/myapp/config，但不配 secret/myapp/inner/config。

④ 多 policy 與多 path 的交互

如果同一 token 帶有多個 policy，OpenBao 採「最特定路徑優先」+「同路徑取交集」邏輯：

  • 同一 path pattern 在多個 policy 出現 → capability 取聯集（OR）。
  • 不同 path pattern 都能配到請求 → 取最具體的那個（先看誰 wildcard 出現得最後，再看 path 長度）。
  • 任何 policy 在某 path 上有 deny，整體就是 deny（優先級最高）。

8.2 寫一份實用的 policy

給應用 myapp 一份「能讀自己的 KV，能寫自己的 audit log，不能碰其他人」的 policy：

# app-myapp.hcl

# KV v2 的「資料」端點 — 注意 path 是 secret/data/...
path "secret/data/myapp/*" {
  capabilities = ["read"]
}

# KV v2 的 metadata（列出版本、軟刪除）
path "secret/metadata/myapp/*" {
  capabilities = ["read", "list"]
}

# 自己的 audit log 路徑（範例 transit engine）
path "transit/encrypt/myapp" {
  capabilities = ["update"]
}

# 明確拒絕讀其他 app 的資料（即使其他 policy 開了也不行）
path "secret/data/other-team/*" {
  capabilities = ["deny"]
}

上傳：

$ bao policy write app-myapp app-myapp.hcl
Success! Uploaded policy: app-myapp

# 之後建立 token / role 時 attach 它
$ bao token create -policy=app-myapp -ttl=1h

8.3 KV v2 的 path 雙層結構

初學者最常踩的坑：KV v2 在 API 層其實有兩組 path：

Path 字首內容常見 capability
secret/data/<k>實際機敏資料read、create、update、delete（軟刪）
secret/metadata/<k>版本、created_at、custom_metadataread（看版本）、list（列出 keys）、delete（永久刪整把）
secret/delete/<k>軟刪特定版本update
secret/undelete/<k>還原已軟刪版本update
secret/destroy/<k>永久銷毀某版本（不可逆）update

所以用 CLI 寫 bao kv list secret/myapp（看起來只 list secret/myapp）時，policy 必須允許 list on secret/metadata/myapp，否則會 403。第三冊會展開更詳細的 KV v2 範例。

8.4 Templated Policies — 動態 path

當你想寫「每個使用者只能讀自己的 secret」這種規則，硬編 path 不切實際。OpenBao 支援 policy template：

# self-service.hcl

path "secret/data/users/{{identity.entity.aliases.<auth_accessor>.name}}/*" {
  capabilities = ["create", "read", "update", "delete"]
}

path "secret/metadata/users/{{identity.entity.aliases.<auth_accessor>.name}}/*" {
  capabilities = ["list", "read"]
}

{{identity.entity.aliases.<auth_accessor>.name}} 在 policy 評估時會被替換成當前 token 的使用者名稱。例如 alice 來時，這個 path 變成 secret/data/users/alice/*，bob 來則是 secret/data/users/bob/*。同一份 policy，所有使用者都安全地隔離在自己的子路徑。

常用的 template 變數：

  • identity.entity.id — 當前 entity ID
  • identity.entity.name — entity 名稱
  • identity.entity.aliases.<mount_accessor>.name — alias 名稱（最常用）
  • identity.groups.names.<group_name>.id — 所屬 group 的 ID
  • identity.groups.ids.<group_id>.metadata.<key> — group metadata

8.5 Identity 系統：Entity / Alias / Group

① 概念

同一個「人」可能透過不同 auth method 登入（例如 Alice 在筆電用 OIDC、在 server 用 LDAP、在 CI 用 AppRole）。每個 auth login 都會產生一個 alias（auth method 上的身份），OpenBao 會把屬於同一人的多個 alias 連到一個 entity（內部統一身份）。

② 動手：建立 entity 與綁定 alias

# 建立一個 entity
$ bao write -format=json identity/entity name=alice \
    metadata=team=platform \
    policies=base-user \
  | jq -r .data.id
<entity-id>

# 綁 OIDC alias 到 alice
$ bao write identity/entity-alias \
    name=alice \
    canonical_id=<entity-id> \
    mount_accessor=<oidc accessor>

# 綁 LDAP alias 到同一個 alice
$ bao write identity/entity-alias \
    name=alice \
    canonical_id=<entity-id> \
    mount_accessor=<ldap accessor>

之後 alice 不論用 OIDC 或 LDAP login，都會解析到同一個 entity，繼承 entity 上的 policies 與 metadata。

③ 三層 policy 來源

一個 token 最終的 effective policies 來自三處（取聯集）：

  1. Token 自身 attach 的 policies（由 auth method role 或 token create 指定）。
  2. Entity 上的 policies（管理員手動設定）。
  3. Entity 所屬 Group 的 policies（含 internal group 與 external group）。

8.6 Identity Tokens 與 OIDC Provider 模式

OpenBao 不只能消費 OIDC token，也能當 OIDC Provider。它可以發 ID token 給其他應用驗證使用者身份，這個機制叫做 Identity Tokens。

典型場景

  1. 使用者用 LDAP / OIDC 登入 OpenBao。
  2. 應用 X 要求使用者出示 ID token（短期、可驗簽）。
  3. 使用者向 OpenBao 取得 identity token：bao read identity/oidc/token/myrole。
  4. 把這個 token 拿給應用 X。
  5. 應用 X 用 OpenBao 公開的 JWKS 驗簽，得知是誰、屬於哪些 group。

這把 OpenBao 變成內網的 SSO IdP，特別適合需要簽發短期、跨應用身份斷言的環境。

8.7 Common Expression Language (CEL)

OpenBao 從 v2.5.0 起導入 CEL（Common Expression Language）支援，讓 policy 與 role 條件可以寫更動態的判斷式：例如根據時間、來源 IP、token metadata 動態決定是否允許。CEL 使用情境會在第三冊（PKI、Database role 條件）與第五冊（policy as code）多處用到，本冊先建立認知：

  • CEL 是 Google 開源的小型 expression language，比完整 Sentinel/OPA 輕量。
  • OpenBao 在 PKI、Database 等 engine 的 role 中支援 CEL 表達式做進階條件。
  • 目前 ACL policy 仍以 HCL capability 為主，但未來會擴充。

8.8 用 -output-policy 自動推導需要的 capability

不確定某個操作要哪些 capability？OpenBao CLI 有一個超實用的 flag：

$ bao kv get -output-policy secret/myapp/config
path "secret/data/myapp/config" {
  capabilities = ["read"]
}

$ bao kv list -output-policy secret/myapp/
path "secret/metadata/myapp/" {
  capabilities = ["list"]
}

它會印出「執行這個操作所需的 minimum policy」，是寫 policy 時的好朋友。

8.9 最小權限原則範例集

應用：唯讀某 KV 子樹

path "secret/data/myapp/*" {
  capabilities = ["read"]
}
path "secret/metadata/myapp/*" {
  capabilities = ["list"]
}

應用：能呼叫 transit 加解密但不能管理 key

path "transit/encrypt/myapp" {
  capabilities = ["update"]
}
path "transit/decrypt/myapp" {
  capabilities = ["update"]
}
# 故意不允許 transit/keys/myapp - 應用不該能 rotate / read key 結構

管理員：read-only 全 cluster（用於 SRE 看狀態）

path "sys/health" { capabilities = ["read"] }
path "sys/metrics" { capabilities = ["read"] }
path "sys/seal-status" { capabilities = ["read"] }
path "sys/mounts" { capabilities = ["read", "list"] }
path "sys/auth" { capabilities = ["read", "list"] }
path "sys/policies/acl" { capabilities = ["read", "list"] }
path "+/+" { capabilities = ["read", "list"] }

8.10 ⚙ 動手練習

  1. 用 -output-policy 看 bao kv put secret/foo a=b 需要哪些 capability。
  2. 寫一份 templated policy：路徑 secret/data/users/{{alias.name}}/*，給 alice、bob 各自試試只能看自己的。
  3. 建立兩個 entity（alice、bob），把 OIDC 跟 userpass 的 alias 都綁到 alice 上，觀察 token policies 是否合併。
  4. 建立 group dev，alice、bob 都加入；group 上掛一個 read-only policy，看 alice/bob token 是否都繼承到。
✓ 章末重點
  • Policy 是 path-based 白名單；deny 會勝出。
  • KV v2 有 data/metadata 雙層 path，policy 都要寫到。
  • Templated policy 是 multi-tenancy 自助的關鍵。
  • Entity 統一同一人的多個 alias；Group 給多人共同 policy。
  • -output-policy 是寫 policy 的隱藏神器。

Chapter 9Token、Lease 與 Response Wrapping

Token 是「身份證」、Lease 是「身份證的有效期」、Response Wrapping 是「把機敏值用一次性信封包起來」。這三個機制合起來決定了 OpenBao 的時間軸 — 任何東西都會過期，且過期之後預設清乾淨。

9.1 Token 的 TTL 與 Max TTL

① 概念

每個非 root token 都有 TTL（time-to-live）：

  • TTL（也叫 token_ttl 或 lease duration）：當前這次的有效期，從建立或上次 renew 起算。
  • Max TTL（也叫 explicit_max_ttl）：硬上限，「不可被超過」。即使一直 renew，到 max TTL 時直接 expire。
  • System max：整個 OpenBao 預設 32d，可在 mount 設定中下調。

實際 effective max = min(token explicit max, mount max, system max)。

9.2 Lease：所有「動態事物」的時鐘

① 概念

OpenBao 對「每個 dynamic secret 與 service token 都會建立 lease：包含時長、可否續租等 metadata」。Lease 的存在是為了強制 consumer「定期回來打卡」，這讓 audit 更有意義、key rolling 更容易。

Lease 與 token TTL 的關係：

  • Service token 自身就帶一個 lease。
  • 用 service token 從 dynamic secret engine（Database、PKI、SSH⋯）取得 secret，會產生另一個 lease，並掛在這個 token 之下。
  • 「Token 被 revoke 時，所有用它建立的 lease 也跟著被 revoke」。
  • Batch token 不寫 storage，所以用它建立的 lease 受限於 batch token 的剩餘 TTL，且不能 renew。

② Lease 操作

# 動態取得一個 DB 帳號（會回 lease_id）
$ bao read database/creds/readonly
Key                Value
---                -----
lease_id           database/creds/readonly/abcd-1234
lease_duration     1h
lease_renewable    true
password           ...
username           v-readonly-...

# 續租這個 lease
$ bao lease renew database/creds/readonly/abcd-1234
$ bao lease renew -increment=3600 database/creds/readonly/abcd-1234

# 主動撤銷
$ bao lease revoke database/creds/readonly/abcd-1234

# 緊急批次撤銷（某 prefix 下全部）
$ bao lease revoke -prefix database/creds/readonly

注意：「bao lease renew 的 increment 是『從現在算起希望剩多久』，不是『目前剩餘 + increment』」，這在規劃 renewal 邏輯時很重要。

③ 讓應用自己處理 renew：Lifetime Watcher

Go SDK 內建 LifetimeWatcher，會在 token / lease 到期前自動 renew：

secret, _ := client.Logical().Read("database/creds/readonly")

watcher, err := client.NewLifetimeWatcher(&openbao.LifetimeWatcherInput{
    Secret:    secret,
    Increment: 3600,
})
if err != nil { log.Fatal(err) }

go watcher.Start()
defer watcher.Stop()

for {
    select {
    case err := <-watcher.DoneCh():
        if err != nil { log.Fatal("renew failed:", err) }
        // lease 到期或 max ttl 到了，需要重新取
        return
    case info := <-watcher.RenewCh():
        log.Printf("renewed, ttl=%v", info.Secret.LeaseDuration)
    }
}

在 K8s 環境中，OpenBao Agent（第四冊）能更省事地處理 renew，連應用程式碼都不用改。

9.3 設計合理的 TTL：經驗法則

對象建議 TTL建議 Max TTL備註
人類管理員 SSO4h8h（一個工作天）逼使用者每天重新驗證
K8s Pod token1h24hPod 通常活不過 24h；Agent 自動 renew
CI/CD job15m1hJob 通常 5–30 分鐘完成
長期 daemonperiodic 24h無periodic token，停了 24h 後自動死
Database dynamic creds1h24h避免帳號過多；DB 端 TTL 與 OpenBao 一致
PKI 長期 cert—30d 或更長受限於業務；過短會撞限速

9.4 Response Wrapping — 一次性信封

① 解決什麼問題

場景：CI/CD 系統幫應用建立了一個 secret_id，要怎麼安全地把它傳到應用？

  • 放環境變數？任何能存取容器的人都看得到。
  • 放 K8s Secret？放 etcd 加密只是延後問題。

OpenBao 的解法：把 secret 放進一個一次性的 cubbyhole，回傳一個 short-lived wrapping token。應用拿著 wrapping token 呼叫 unwrap 取出真正的 secret，同一個 wrapping token 不能被使用第二次。如果有人「先到一步」用了這個 token，應用 unwrap 就會失敗 — 你立刻知道有問題。

② 動手

# Operator：產生一個 wrapped secret_id，TTL 5 分鐘
$ bao write -wrap-ttl=300s -force auth/approle/role/myapp/secret-id
Key                              Value
---                              -----
wrapping_token:                  s.wrapToken123...
wrapping_accessor:               ...
wrapping_token_ttl:              5m
wrapping_token_creation_time:    ...
wrapping_token_creation_path:    auth/approle/role/myapp/secret-id

# Operator 把 s.wrapToken123 透過任意管道交給應用
# 應用 unwrap（不需要先 login，可在 wrap token 被 issue 後 5min 內呼叫）
$ BAO_TOKEN=s.wrapToken123 bao unwrap
secret_id           4e8b62f0-...
secret_id_accessor  ...
...

③ 安全屬性

  • 單次使用：unwrap 一次後 cubbyhole 銷毀，wrap token 失效。
  • 過期保險：wrap TTL 到了就算沒用過也消失。
  • 洩漏可偵測：應用 unwrap 失敗 = 有人捷足先登 = 立刻 alert。
  • Auditable：wrap / unwrap 都進 audit log，且 wrap accessor 可以被管理。

9.5 Cubbyhole — 每個 token 的私人空間

Cubbyhole 是 OpenBao 內建的特殊 secret engine（掛在 cubbyhole/），「每個 token 有自己獨立的 cubbyhole，token 死掉時 cubbyhole 內容自動銷毀」。

$ bao write cubbyhole/notes content="my temporary note"
$ bao read cubbyhole/notes
# 換另一個 token 進來看 — 看不到
$ BAO_TOKEN=<other> bao read cubbyhole/notes
No value found at cubbyhole/notes

Response wrapping 內部就是把要傳的資料寫進「一個臨時 token 的 cubbyhole」。Cubbyhole 也適合：

  • Token 私有的設定快取（不希望被別的 token 看到）。
  • SecureIntroduction 三方協議的中介儲存。

9.6 Token 完整生命週期管理範本

把前面的概念串起來，一個 production K8s 應用的 token 生命週期長這樣：

  1. 啟動：Pod 啟動，service account token 透過 Kubernetes auth method 換成 OpenBao token（TTL 1h, max TTL 24h）。
  2. 取 dynamic secret：用這個 token 從 database engine 取 DB 帳號（lease 1h）。
  3. 定期 renew：OpenBao Agent 每 30 分鐘 renew token 與 lease。
  4. 到 max：超過 24h，token 強制 expire；Agent 重新登入取新 token，DB 帳號被新 lease 取代。
  5. 關閉：Pod 收 SIGTERM，Agent revoke 自己的 token；OpenBao 連鎖 revoke 所有相關 lease（DB 帳號立刻消失）。

9.7 ⚙ 動手練習

  1. 建立 TTL 1m, max TTL 5m 的 token，連續 renew 觀察什麼時候到 max 就死。
  2. 建立 batch token，跑 bao token lookup 比較 service token 的差別（有沒有 accessor、storage entry）。
  3. 用 bao write -wrap-ttl=2m 包起一個 KV 值，故意 unwrap 兩次，觀察第二次的錯誤。
  4. 寫進自己 token 的 cubbyhole，登出再登入，看 cubbyhole 是否清空。
✓ 章末重點
  • Token 帶 TTL；TTL 可 renew 但不能跨 max TTL。
  • Lease 是 dynamic secret 的時鐘，掛在 token 之下；token 死 → lease 跟著死。
  • Response wrapping = 一次性信封 + 偵測機制；secure introduction 的標準解。
  • Cubbyhole = token 私人空間，token 死光資料消。

Chapter 10Namespaces、Resource Quotas、Profile

當你的 OpenBao 開始服務多個團隊、多個環境，怎麼確保「Team A 的人不會誤刪 Team B 的東西」、「失控的應用不會打爆 server」？這就是 namespace 與 resource quota 解決的問題。

10.1 Namespaces：原生多租戶

① 為什麼是 OpenBao 的關鍵賣點

在 HashiCorp Vault，Namespaces 是 Enterprise 收費功能。在 OpenBao，「Namespaces 包含在開源版本中，零成本」。對需要為多個團隊或環境隔離 OpenBao 但不想跑多個 cluster 的組織，這是非常顯著的差異。

② 概念

Namespace 在 OpenBao 內形成邏輯隔離的 OpenBao 副本：

  • 每個 namespace 有自己的 secret engine、auth method、policies、token、entity、group。
  • 一個 namespace 的 token 預設無法存取其他 namespace 的資源。
  • Namespace 可以階層巢狀：root → team-a → team-a/staging。
  • 子 namespace 預設不繼承父 namespace 的 mount，但有 identity_token_namespaces 等可控選項。

③ 動手

# 建立 namespace
$ bao namespace create team-a

# 在子 namespace 操作（環境變數）
$ export BAO_NAMESPACE=team-a
$ bao secrets enable -path=secret kv-v2
$ bao kv put secret/app/db pwd=team-a-secret

# 切回 root
$ unset BAO_NAMESPACE
$ bao kv get secret/app/db
Error reading secret/data/app/db: ... 404
# 因為這個 KV 在 team-a namespace 下，root 看不到

在 HTTP 層，namespace 透過 X-Vault-Namespace header 傳遞：

$ curl \
    --header "X-Vault-Token: $TOK" \
    --header "X-Vault-Namespace: team-a" \
    $BAO_ADDR/v1/secret/data/app/db

④ 巢狀

$ BAO_NAMESPACE=team-a bao namespace create staging

# 操作 team-a/staging
$ BAO_NAMESPACE=team-a/staging bao secrets enable -path=secret kv-v2
$ BAO_NAMESPACE=team-a/staging bao kv put secret/svc/cfg ...

⑤ Namespace 的設計建議

  • 用 namespace 做「組織階層」隔離，不是「應用」隔離。應用之間用 path 與 policy 區分就夠了。
  • 典型 pattern：root（共用 PKI / Transit）→ team-{platform,data,billing}（各團隊管理）→ {prod,staging,dev}（環境）。
  • 避免太深：超過 3 層通常變成自己的負擔。
  • 記得：每個 namespace 都要自己掛 audit device（root 的 audit 不會自動接子 namespace）。

10.2 Per-Namespace Sealing（進階）

OpenBao 有一個進行中的 RFC（Per-Namespace Sealing），允許每個 namespace 獨立 seal/unseal，給租戶更強的數據主權。本書撰寫時 (v2.5.3) 部分能力已落地：每個 namespace 可有自己的 barrier key、seal 機制、且不影響其他 namespace 的可用性。詳見官方 RFC 文件。

目前的實際能力：

  • 租戶可以獨立要求 seal 自己的 namespace（不影響其他 namespace）。
  • 每個 namespace 可有自己的 encryption key（namespace barrier key）。
  • Sealed namespace 拒絕業務請求但 cluster 整體仍服務其他 namespace。

10.3 Resource Quotas：保護 server 不被打爆

有些 client 寫得不好（每秒打 1000 次 read），或被惡意攻擊，會把 OpenBao server 打趴。OpenBao 提供兩種 quota：

① Rate Limit Quota（每秒請求數）

# 全域：所有請求每秒不超過 1000
$ bao write sys/quotas/rate-limit/global \
    rate=1000 \
    interval=1s

# 限定某 path：team-a/secret/* 每秒 100
$ bao write sys/quotas/rate-limit/team-a-cap \
    path="team-a/secret/" \
    rate=100 \
    interval=1s

# 限定某 namespace（搭配 BAO_NAMESPACE）
$ BAO_NAMESPACE=team-a bao write sys/quotas/rate-limit/team-a-internal \
    rate=500 \
    interval=1s

超過 rate 的請求會回 429 Too Many Requests。

② Lease Count Quota（總 lease 數）

對 dynamic secret 重度使用的環境（PKI 簽發、Database creds），lease 數量可能爆量導致記憶體 / storage 壓力。Lease quota 會在達到上限時拒絕產生新 lease：

$ bao write sys/quotas/lease-count/pki-cap \
    path="pki/" \
    max_leases=10000

③ 例外名單

某些 path 不該被計入（例如 sys/health 的監控請求），可以加進 quota 例外：

$ bao write sys/quotas/config \
    rate_limit_exempt_paths=["sys/health","sys/seal-status"]

10.4 Profile 系統

OpenBao 在 v2.5 加入 Profile System，讓 operator 可以用「設定模板」批次建立 mount + policy + role，避免每次新團隊上線都手動敲幾十條指令。

典型用途：

  • 新 namespace 上線：自動建立 KV、PKI、所需 policy、預設 role。
  • 環境切換：dev / staging / prod 各有預設組合。

詳見官方 Profile System 文件，因為仍在持續演進，本書只建立認知，實際使用時請對照官方文件最新版本。

10.5 Mount Migration：不停機搬遷

有時你需要把 mount 從一個 path 搬到另一個 path（例如 secret/ → kv/，或從 root 搬到 namespace 之下）。Mount migration 機制允許不停機完成這件事：

$ bao secrets move secret/ kv/
⚠ 注意

Mount move 「會 revoke 所有現有 lease」，因為 lease ID 跟 path 綁定。所以對 dynamic secret engine（DB、PKI）影響大；對純 KV 影響小（KV 不發 lease）。排在維護視窗做，並通知所有相依應用。Mount data 本身會保留。

10.6 多租戶設計範本

把整章串起來，一個服務 5 個團隊的 OpenBao 多租戶設計範例：

# 1. Root namespace 放共用 PKI + Transit
$ bao secrets enable -path=pki pki
$ bao secrets enable transit

# 2. 每個團隊一個 namespace
$ for ns in platform data billing identity infra; do
    bao namespace create $ns
  done

# 3. 全域 rate limit 防止單一團隊打爆
$ bao write sys/quotas/rate-limit/global rate=5000 interval=1s

# 4. 每團隊獨立 lease quota
$ for ns in platform data billing identity infra; do
    BAO_NAMESPACE=$ns bao write sys/quotas/lease-count/team-cap \
      max_leases=5000
  done

# 5. 每個 namespace 各自啟用 audit
$ for ns in platform data billing identity infra; do
    BAO_NAMESPACE=$ns bao audit enable file file_path=/var/log/openbao/$ns.log
  done

# 6. 每個 namespace 啟用各自需要的 secret engine
# 由團隊自助，或由 platform team 用 Profile 批次建立

10.7 ⚙ 動手練習

  1. 建立兩個 namespace team-a 與 team-b，各自掛 KV，互相寫值，確認彼此看不見。
  2. 在 root 建立 token 帶有 app-ro policy，嘗試讀 team-a 的 KV，看 403 錯誤訊息。
  3. 套一個 rate-limit quota（rate=2 interval=10s），用 for loop 連發 10 次 read，看哪幾次被擋。
  4. 在 team-a/staging 建一個巢狀 namespace 並掛 KV。
✓ 章末重點
  • Namespaces 是 OpenBao 對 Vault Enterprise 的關鍵差異化 — OSS 即可使用。
  • 用 namespace 隔離「組織」，用 path + policy 隔離「應用」。
  • Rate limit + lease count quota 是保 server 命的最後一道牆。
  • Mount move 會 revoke lease；排維護視窗做。
