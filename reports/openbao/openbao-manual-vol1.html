Chapter 1OpenBao 是什麼

在開始學習任何工具之前，理解「它要解決什麼問題」比理解「它怎麼用」更重要。本章建立你對 OpenBao 的整體認知：它是什麼、從哪來、能做什麼、什麼情況不適合用它。

1.1 為什麼需要 secrets management

① 概念導讀

現代應用系統需要操作大量 secrets（機敏值）：資料庫帳密、API key、TLS 憑證、SSH 金鑰、雲端服務 access key⋯。當這些 secrets 散落在程式碼、設定檔、CI/CD 變數、甚至 Slack 對話中，會出現幾個典型問題：

  • credential sprawl（憑證蔓延）：不知道有哪些 secrets、誰在用、放在哪，無法統一回收。
  • 無法輪替（key rotation）：每次換密碼都要改 N 個地方，最後乾脆不換。
  • 缺乏稽核：誰在何時用了哪個 secret，沒人說得出來。
  • 明文外洩：commit 到 Git、存在共用文件、貼在 Wiki，造成根本性風險。

OpenBao 把所有 secrets 集中在一個強加密、可稽核、可程式化的中央倉庫，由它扮演「secrets 守門員」：應用要用 secret，先向 OpenBao 認證，由 OpenBao 決定發不發、發多久、發完之後怎麼回收。

② 它具體能做什麼

根據官方對 OpenBao 的定義，官方文件列出五大核心能力：Secure Secret Storage、Dynamic Secrets、Data Encryption、Leasing and Renewal、Revocation。我們把它們轉譯成你會直接看到的場景：

能力說明典型場景
Secure Secret Storage 加密保存 K/V 機敏值，落盤前先用 barrier key 加密。 把資料庫密碼、API key 從程式碼移除，改由應用啟動時向 OpenBao 拉取。
Dynamic Secrets 不存固定憑證，而是「需要時即時產生」短期憑證。 應用要連 PostgreSQL，OpenBao 即時建立一個有效 1 小時的 DB 帳號。
Data Encryption（Encryption as a Service） 提供加解密 API，但金鑰永遠不離開 OpenBao。 應用要加密 PII 寫進 SQL，呼叫 transit/encrypt，存密文，讀取時再呼叫 transit/decrypt。
Leasing & Renewal 每個 secret 都有 lease（租約），到期自動回收，可中途續租。 動態 DB 帳號 lease 1 小時，應用每 30 分鐘 renew 一次；應用掛了，帳號 1 小時內自動消失。
Revocation 支援單筆或整樹 secrets 撤銷。 偵測到入侵，一鍵撤銷某使用者所有發過的 secrets。

1.2 OpenBao 與 HashiCorp Vault 的關係

① 簡史

HashiCorp 於 2023 年 8 月將其產品授權從 MPL 2.0 改為 BSL（Business Source License），這對某些下游使用者與雲端服務商造成商業限制。社群隨後從 Vault 最後一個 MPL 2.0 版本（v1.14.0）派生出 OpenBao，並交由 Linux Foundation 治理；目前隸屬於 LF Edge / OpenSSF Sandbox。OpenBao 採用 OSI 認可的 MPL 2.0，無 BSL 商業限制。

② 對日常使用者的影響

幾乎一致的部分

  • CLI 指令（bao ↔ vault）大多可互換
  • HTTP API path 與 header（仍使用 X-Vault-Token）
  • Policy HCL 語法
  • 大部分 secret engine 與 auth method
  • Storage backend（Raft、PostgreSQL 等）

不同或注意點

  • OpenBao 從 v1.14 後的 Vault 新功能不會自動有
  • OpenBao 的 Namespaces 是 OSS 免費功能（Vault 是 Enterprise）
  • Vault Enterprise 的 DR Replication，OpenBao 目前尚無對等功能
  • 部分過時 secret engine 已在 OpenBao 中移除或標 deprecated

③ 該選哪個？

本手冊聚焦 OpenBao，但下列原則對選型仍有幫助：若你的環境受 BSL 限制（例如要把它包進你自己的 SaaS 賣給客戶）、想要免費 multi-tenancy（namespaces）、傾向 LF 開源治理，OpenBao 是合理選擇；若你已使用 Vault Enterprise 且依賴其 DR Replication、Performance Replication、HSM 整合等企業功能，繼續用 Vault 較直接。兩者並非二擇一，許多組織也會評估漸進式遷移。

1.3 OpenBao 的核心使用情境

把上面五大能力對應到實際工程場景，可以歸納成這四類：

  1. Static secrets store（靜態機敏值集中保管） — 用 KV v2 engine 取代 .env、Jenkins credential、K8s Secret 明文 base64。
  2. Dynamic credentials（動態憑證） — Database engine、AWS engine、PKI engine 等，把長期憑證換成短期、可審計、可自動回收的動態憑證。
  3. Encryption as a Service（加密即服務） — Transit engine 提供 encrypt / decrypt / sign / verify / HMAC，金鑰從不離開 OpenBao，應用無需自己處理 key management。
  4. Identity broker（身份中介） — OIDC Provider 模式，把 OpenBao 當作 SSO 層發放身份 token。

1.4 不適合 OpenBao 的場景

誠實談一下界線。OpenBao 雖然強大，但它不是萬靈丹：

  • 它不是密碼管理員 — 不要把它當 1Password / Bitwarden 給使用者放個人密碼，那是 UX 完全不同的產品。
  • 它不是 KMS 的完全替代 — 雲端 KMS（AWS KMS / GCP Cloud KMS）有 HSM 背書與深度雲端整合，OpenBao 的 Transit 是「應用層的 KMS」，兩者常一起用：用雲 KMS 做 OpenBao 的 auto-unseal。
  • 它不是大量資料加密引擎 — Transit 適合加密敏感欄位（信用卡、身分證），不適合加密整個影片檔；那種場景應用 envelope encryption + 雲端 KMS 才合理。
  • 它不是 secret 唯一解 — Kubernetes 內部短週期、不離開叢集的低風險 secrets，繼續用原生 K8s Secret + RBAC 完全可以；OpenBao 應該保留給「跨團隊、跨環境、需稽核」的高價值 secrets。
✓ 章末重點

OpenBao 是一個「身份為基礎」的中央 secrets 與加密管理系統。它的價值不在於「加密」這個動作本身（你也可以用 GPG），而在於把儲存、取用、輪替、撤銷、稽核整套生命週期收攏到單一可程式化的平面，並透過 lease 機制讓 secrets 預設就會過期。

Chapter 2核心術語與心智模型

OpenBao 的功能像一個由四種可掛載元件拼出來的小型作業系統：路由系統 + 檔案系統 + 認證模組 + 稽核管道。本章介紹這些抽象層，後面五冊都會反覆引用，先把心智模型打穩。

2.1 三層架構：Server / Client / Storage Backend

① 概念導讀

不論是用 bao CLI、curl、Web UI 或自己寫的 Go/Python 程式，所有人都是 client，透過 HTTP API 跟 OpenBao server 對話。Server 把所有資料加密後寫到 storage backend（Raft、PostgreSQL、File⋯）。

② 為什麼這樣分

這個分層的設計有兩個重要意義：

  • Storage 永遠看不到明文。 Server 在寫入前會先用 barrier key 加密，storage backend 拿到的是 ciphertext。所以你可以用 PostgreSQL 當 storage，但不需要擔心 DBA 看到你的 secrets。
  • Server 可以橫向擴展但 storage 是單一真相來源。 HA 情境下會有多個 server node，但 storage（不論是 Raft cluster 內部還是外部 PostgreSQL）只有一份資料，這保證一致性。

2.2 四大可掛載元件：Engine / Auth / Audit / Policy

OpenBao Server 內部其實是個極簡的 router：所有功能都是「掛載（mount）在某個路徑下的模組」。理解這點就解開了 OpenBao 一半的學習曲線。

元件掛在哪做什麼例子
Secret Engine 任意路徑（預設 type 名稱） 儲存 / 產生 / 加密資料 KV、PKI、Database、Transit、SSH⋯
Auth Method auth/ 前綴 驗證身份 → 發 token Userpass、AppRole、JWT/OIDC、Kubernetes、LDAP⋯
Audit Device sys/audit/ 記錄所有請求 / 回應到外部 File、Syslog、Socket
Policy sys/policies/ 規範 token 能存取哪些 path 與動作 HCL 規則檔

每個 engine / auth method / audit device 都可以同型多次掛載。例如：你可以同時把 KV v2 掛在 secret/（給應用用）和 shared/（給跨團隊共用）；也可以把 Userpass 掛在 auth/userpass/（給開發者）和 auth/admin/（給管理員），兩者完全隔離。

2.4 名詞速覽（後面五冊都會深掘）

這節先讓你「看到時不會驚訝」，每個詞都會在後面章節深入。

Path

OpenBao 一切以 path 為單位，類似一個虛擬檔案系統。例如 secret/data/myapp/config 是 KV v2 的一個 secret，auth/userpass/login/alice 是 Userpass auth 的登入端點。Path 是 case-sensitive 的：kv/ 和 KV/ 是兩個不同的 mount。

Mount

把一個 engine 或 auth method 註冊到某個 path。例如 bao secrets enable -path=team-a kv-v2 把一個 KV v2 engine 掛到 team-a/。

Token

OpenBao 的核心通行證。所有操作（除了少數 unauth endpoint 與 inline auth）都需要 token。Token 有 TTL、有對應的 policies、可以續租、可以撤銷。Root token 是最高權限的特例，僅應用於初始設定與災難恢復。

Lease

動態 secret 與 token 的「使用期」。每筆 lease 有 ID、TTL、max TTL；應用可以呼叫 renew 延長，也可以主動 revoke 撤銷。Lease 是 OpenBao 「secrets 自帶過期」的精髓所在。

Seal / Unseal

OpenBao 啟動時是 sealed（封印） 狀態，無法處理任何請求。要把它 unseal，需要拼出 master key — 而 master key 用 Shamir Secret Sharing 拆成 N 份，需要其中 K 份才能重組（預設 N=5、K=3）。這保證「沒有單一管理員可以獨自解開 OpenBao」。

Policy

用 HCL 寫的存取規則檔。例如：

path "secret/data/myapp/*" {
  capabilities = ["read", "list"]
}

path "secret/data/myapp/config" {
  capabilities = ["read", "update"]
}

Token 在 login 時會被 attach 到一個或多個 policies，policies 是白名單（沒明確允許的 path 預設拒絕）。

ℹ 後面會更詳細

本章只需要記得：「OpenBao = 一個會路由請求的 server，內部掛載著各種 engine 和 auth method，所有操作都受 policy 保護，每筆請求都被 audit。」這個一句話心智模型，能撐你看完接下來三章。

3.3 Container 安裝（最快上手）

OpenBao 同時推送 Alpine 與 RHEL UBI 兩套映像到三個 registry：

  • ghcr.io/openbao/openbao（GitHub Container Registry）
  • quay.io/openbao/openbao
  • docker.io/openbao/openbao

對應的 UBI 變體把 openbao 換成 openbao-ubi。

啟動 dev mode container

$ docker run --rm --name openbao \
    -p 8200:8200 \
    -e BAO_DEV_ROOT_TOKEN_ID=dev-only-token \
    -e BAO_DEV_LISTEN_ADDRESS=0.0.0.0:8200 \
    --memory-swappiness=0 \
    docker.io/openbao/openbao:2.5.3 server -dev

容器啟動後會輸出 root token、unseal key 與 listen address。--memory-swappiness=0 是官方建議的安全強化，避免 OS 把記憶體頁換出到 swap，導致 secrets 殘留在磁碟。

⚠ Production container 注意

Production 用 container 部署時，務必：(1) 不要用 dev mode；(2) 掛載 production 設定檔；(3) 提供持久化儲存 volume；(4) 使用固定版本 tag（不要用 latest）。完整 production container 部署在第四冊「在 Kubernetes 上部署」與「OpenBao Agent」章節會詳細展開。

3.4 預編譯 binary

$ VERSION=2.5.3
$ OS=linux
$ ARCH=amd64
$ wget https://github.com/openbao/openbao/releases/download/v${VERSION}/bao_${VERSION}_${OS}_${ARCH}.tar.gz
$ tar xzvf bao_${VERSION}_${OS}_${ARCH}.tar.gz
$ sudo mv bao /usr/local/bin/
$ bao --version

校驗 SHA-256 與 GPG 簽章

正式環境強烈建議至少做 SHA-256 校驗，最好連 GPG 簽章一起驗。先匯入官方 GPG key：

$ wget https://openbao.org/assets/openbao-gpg-pub-20240618.asc
$ gpg --import openbao-gpg-pub-20240618.asc
# fingerprint 應為:
# 66D1 5FDD 8728 7219 C8E1  5478 D200 CD70 2853 E6D0

$ wget https://github.com/openbao/openbao/releases/download/v${VERSION}/checksums-linux.txt
$ wget https://github.com/openbao/openbao/releases/download/v${VERSION}/checksums-linux.txt.gpgsig

# 驗證簽章
$ gpg --verify checksums-linux.txt.gpgsig checksums-linux.txt

# 驗證 binary 雜湊
$ sha256sum --check checksums-linux.txt 2>/dev/null | grep -F "$(basename bao_${VERSION}_${OS}_${ARCH}.tar.gz)"

OpenBao 同時也支援 Cosign + Rekor 的 sigstore 驗章流程，適合在 supply-chain security 嚴格的環境使用。

3.6 安裝後安全強化（Hardening）

OpenBao 把 secrets 都加密在磁碟，但記憶體中需要明文才能處理請求。如果作業系統把這部分記憶體頁換到 swap，magic 就破功了。官方安裝指南明確要求處理這件事：

Linux + systemd

OpenBao 隨附的 systemd unit 預設已經設了 MemorySwapMax=0，等同於告訴 systemd「這個 process 不能用 swap」。確認方式：

$ systemctl cat openbao | grep MemorySwapMax
MemorySwapMax=0

非 systemd 的 Linux

用 cgroup v2 的 memory.swap.max=0，或如果整台機器都跑 OpenBao，可以乾脆 swapoff -a（不是首選）。

Docker

$ docker run --memory-swappiness=0 ...

Windows

Windows 不能完全禁 swap，但可以加密 page file：

> fsutil behavior query encryptpagingfile
encryptpagingfile = 0    # 0=disabled, 1=enabled
> fsutil behavior set encryptpagingfile 1
# 然後重啟

macOS

macOS 預設 swap 已加密，不需要額外設定。

  • ✅ 知道要從哪個 registry / repo 取得官方建構，且能驗證簽章（生產環境）

Chapter 4第一次跑 OpenBao — Dev Server

本章帶你跑起第一個 OpenBao server、寫入第一個 secret、再讀回來。整章只用 dev mode，5 分鐘就能跑通。但 dev mode 永遠不可以上 production，這點本章末會詳細交代邊界。

4.1 什麼是 Dev Server

Dev Server 是官方提供的「拋棄式」啟動模式，目的是讓你不需要設定檔、不需要 init、不需要 unseal，一條指令就能玩。為了達到這個目的，它做了幾件危險的事：

  • 所有資料只放記憶體，server 一停就全部消失。
  • 使用單一 unseal key（而不是 Shamir 的多份），且自動 unseal。
  • 使用 root token（你可以指定固定值），全權限。
  • 明文 HTTP 監聽，沒有 TLS。
  • 啟用 KV v2 engine 在 secret/，方便立刻寫入。
⛔ 三大紅線
  1. Dev mode 永遠不可以對外，bind 0.0.0.0 且開公網等於把所有 secrets 公開展示。
  2. Dev mode 的 root token 絕對不要拿到 production 用。
  3. Production server 啟動時 絕對不會看到 -dev 這個 flag。

4.2 啟動 Dev Server（Linux/macOS）

① 啟動

開一個 terminal（之後叫 Terminal A），執行：

$ bao server -dev -dev-root-token-id="dev-only-token"

你會看到類似的輸出：

==> OpenBao server configuration:
             Api Address: http://127.0.0.1:8200
                     Cgo: disabled

              Listener 1: tcp (addr: "127.0.0.1:8200", ...)
               Log Level: info
                Mlock: supported: false, enabled: false
            Recovery Mode: false
                 Storage: inmem
                 Version: OpenBao v2.5.3

WARNING! dev mode is enabled! ...

Root Token: dev-only-token
...

② 設定 Client 環境變數

開一個新的 terminal（Terminal B），告訴 bao CLI 要連到哪、用什麼 token：

$ export BAO_ADDR='http://127.0.0.1:8200'
$ export BAO_TOKEN='dev-only-token'
ℹ BAO_* 與 VAULT_*

OpenBao 為了相容性，同時接受 BAO_ADDR/BAO_TOKEN 與 VAULT_ADDR/VAULT_TOKEN。HTTP API 的 header 也仍是 X-Vault-Token。這是 OpenBao 與 Vault 工具鏈互通的關鍵。本手冊優先用 BAO_*，遇到 raw HTTP API 時則用 X-Vault-Token（這是固定的）。

③ 確認連線

$ bao status

Sealed: false + Initialized: true 代表一切就緒。

4.3 啟動 Dev Server（Docker）

① 啟動容器

$ docker run --rm -d --name openbao-dev \
    -p 8200:8200 \
    -e BAO_DEV_ROOT_TOKEN_ID=dev-only-token \
    -e BAO_DEV_LISTEN_ADDRESS=0.0.0.0:8200 \
    --memory-swappiness=0 \
    docker.io/openbao/openbao:2.5.3 server -dev

② 主機端設定 client

從 host 機連 container：

$ export BAO_ADDR='http://127.0.0.1:8200'
$ export BAO_TOKEN='dev-only-token'
$ bao status

沒裝 host 端 bao CLI 也沒關係，可以用容器內的：

$ docker exec -it openbao-dev sh
/ # export BAO_ADDR='http://127.0.0.1:8200'
/ # export BAO_TOKEN='dev-only-token'
/ # bao status

4.4 啟動 Dev Server（Kubernetes 簡易版）

正式的 K8s 部署請看第四冊；這裡只示範一個最簡單的 dev pod，讓 K8s 使用者也能 5 分鐘上手。

⚠ K8s dev pod 的限制

IPC_LOCK capability 是給 OpenBao 鎖記憶體不被 swap 用的；在某些受限的 K8s 環境（如 Pod Security Standards "restricted"）會被擋掉，這時可以暫時拿掉，但只限 dev 用。Production 部署一定要走 Helm chart，第四冊會詳述。

4.5 寫入第一個 secret

Dev mode 預設已經把 KV v2 engine 掛在 secret/。我們來寫一個 K/V：

$ bao kv put secret/myapp/config \
    db_user=appuser \
    db_password=s3cret-pa55w0rd \
    api_key=AKIAEXAMPLE
======== Secret Path ========
secret/data/myapp/config

======= Metadata =======
Key                Value
---                -----
created_time       2026-05-05T...
deletion_time      n/a
destroyed          false
version            1

注意輸出的 path 是 secret/data/myapp/config — 多了 data/。這是 KV v2 的 API 結構，但 CLI 會幫你自動處理，所以你下指令時直接寫 secret/myapp/config 就好。

4.6 讀回 secret

$ bao kv get secret/myapp/config
======== Secret Path ========
secret/data/myapp/config

======= Metadata =======
...
version  1

====== Data ======
Key           Value
---           -----
api_key       AKIAEXAMPLE
db_password   s3cret-pa55w0rd
db_user       appuser

只讀單一欄位，加上 -field：

$ bao kv get -field=db_password secret/myapp/config
s3cret-pa55w0rd

JSON 格式輸出（適合接 jq）：

$ bao kv get -format=json secret/myapp/config | jq '.data.data'
{
  "api_key": "AKIAEXAMPLE",
  "db_password": "s3cret-pa55w0rd",
  "db_user": "appuser"
}

4.7 用 Web UI 看一遍

瀏覽器打開 http://127.0.0.1:8200/ui/，用 dev-only-token 登入。你會看到剛才寫入的 secret/myapp/config，可以瀏覽、編輯、查看歷史版本。

UI 重點導覽（後面 Ch5 詳述）

  • Secrets：所有掛載的 secret engines 與其下的 secrets。
  • Access：auth methods、policies、entities、leases、tokens。
  • Tools：unwrap、wrap、random、hash 等工具。
  • Status bar：seal status、cluster info。

Chapter 5CLI、API、Web UI 三種操作介面

OpenBao 提供三種等價的操作管道：CLI、HTTP API、Web UI。三者背後都打到同一組 HTTP endpoint，差別只是「人手介面」與「自動化介面」。本章建立你對三者的完整對照，後面所有章節你都能在這三種模式間切換。

5.1 三種介面的關係

5.2 CLI 結構與常用指令

CLI 動詞家族

OpenBao CLI 子命令大致分成幾個家族：

家族用途例子
bao server啟動 serverbao server -config=cfg.hcl
bao status查看 seal/init 狀態bao status
bao operator運維操作（init、unseal、key rotate）bao operator init
bao secrets管理 secret enginesbao secrets enable kv-v2
bao auth管理 auth methodsbao auth enable userpass
bao policy管理 policiesbao policy write app app.hcl
bao tokentoken 管理bao token create -policy=app
bao kv / bao pki / bao ssh 等各 engine 的捷徑指令bao kv put secret/foo k=v
bao read / bao write / bao list / bao delete低階通用 path 操作bao read sys/health
bao login取得 tokenbao login -method=userpass username=alice
bao path-help查某 path 的 schema 說明bao path-help secret/data/foo

輸出格式

$ bao kv get -format=json secret/myapp/config        # JSON
$ bao kv get -format=yaml secret/myapp/config        # YAML
$ bao kv get -format=table secret/myapp/config       # 預設 table

常用環境變數

變數說明
BAO_ADDR / VAULT_ADDRServer 位址，例：https://bao.example.com:8200
BAO_TOKEN / VAULT_TOKEN當前 token
BAO_NAMESPACE / VAULT_NAMESPACE多租戶 namespace
BAO_CACERT / VAULT_CACERTTLS root CA 路徑
BAO_CLIENT_CERT, BAO_CLIENT_KEYmTLS 客戶端憑證

5.3 HTTP API 基礎

所有 API endpoint 都在 /v1/... 之下，token 透過 X-Vault-Token header 傳遞。

基本骨架

POST /v1/secret/data/myapp/config HTTP/1.1
Host: 127.0.0.1:8200
X-Vault-Token: dev-only-token
Content-Type: application/json

{
  "data": {
    "db_user": "appuser",
    "db_password": "s3cret"
  }
}

用 curl 改寫剛才寫 secret 的指令

$ curl \
    --header "X-Vault-Token: dev-only-token" \
    --request POST \
    --data '{"data": {"db_user": "appuser", "db_password": "s3cret"}}' \
    http://127.0.0.1:8200/v1/secret/data/myapp/config

讀回

$ curl \
    --header "X-Vault-Token: dev-only-token" \
    http://127.0.0.1:8200/v1/secret/data/myapp/config | jq '.data.data'

{
  "db_password": "s3cret",
  "db_user": "appuser"
}

HTTP 動詞 vs OpenBao 動作

OpenBao 的 path 不嚴格遵守 REST 慣例，動作意義由 path 決定：

HTTP 方法多數情況代表備註
GETread
LIST（OpenBao 自訂）list許多 client 用 GET ?list=true
POST / PUTcreate / update視 endpoint 而定
DELETEdeleteKV v2 是 soft delete

Inline Authentication

OpenBao 支援 inline authentication：把認證資訊用特殊 header 帶在主請求裡，省去先 login 拿 token 再用 token 兩步。適合對 lease 不敏感的 high-throughput 場景：

POST /v1/secret/data/foo HTTP/1.1
X-Vault-Inline-Auth-Path: auth/userpass/login/alice
X-Vault-Inline-Auth-Operation: update
X-Vault-Inline-Auth-Parameter-password: <base64url-encoded JSON>
...

注意：「inline auth 創建的 token 是 ephemeral（不寫入 storage），所以涉及 lease 的請求會出錯」。詳情第二冊「認證」章節。

5.4 Web UI 導覽

Web UI 適合：

  • 快速瀏覽某 path 下有什麼
  • 查看 lease 與 token 狀態
  • 新人 onboarding 視覺化理解結構
  • 解開 wrapped response（unwrap）

不適合：

  • 大量批次操作（用 CLI/API）
  • 自動化（用 SDK）
  • 受嚴格 audit 的操作（CLI/API 的 log 較易接 SIEM）

5.6 用 Go SDK 寫一個 client

所有自動化最終都會走 SDK 而非 shell。以下是官方 Go SDK 的最小範例（第五冊會深入講多語言 SDK 與 production 化）：

$ go get github.com/openbao/openbao/api/v2
package main

import (
    "context"
    "fmt"
    "log"

    openbao "github.com/openbao/openbao/api/v2"
)

func main() {
    config := openbao.DefaultConfig()
    config.Address = "http://127.0.0.1:8200"

    client, err := openbao.NewClient(config)
    if err != nil {
        log.Fatalf("init client: %v", err)
    }
    client.SetToken("dev-only-token")

    // 寫入
    _, err = client.KVv2("secret").Put(
        context.Background(),
        "myapp/config",
        map[string]interface{}{
            "db_user":     "appuser",
            "db_password": "s3cret",
        },
    )
    if err != nil { log.Fatal(err) }

    // 讀回
    sec, err := client.KVv2("secret").Get(context.Background(), "myapp/config")
    if err != nil { log.Fatal(err) }

    pwd, _ := sec.Data["db_password"].(string)
    fmt.Printf("password = %s\n", pwd)
}
