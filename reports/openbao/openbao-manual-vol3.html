Preface · 本冊定位從「概念」到「能解決問題」

第二冊讓你會 seal/unseal、會做認證授權、會管 token。但那些都還是 OpenBao 的「內部機制」。本冊的八個章節，是 OpenBao 真正對外服務的入口 — 也就是你的應用真的會打到的 endpoint。

什麼是 Secret Engine

Secret Engine 是「在某個 path 上掛載的小服務」 — 給它輸入、它做某種處理、回傳結果。但根據你選的 engine，「處理」的意義完全不同：

  • 給 KV：寫進去就存起來、讀出來就拿到原樣值。
  • 給 Database：讀它就動態建一個 DB 帳號給你，到期自動回收。
  • 給 PKI：寫 CSR 進去就簽出一張 X.509 憑證。
  • 給 Transit：寫 plaintext 進去得到 ciphertext，但 OpenBao 不存資料 — 它只是加解密服務。
  • 給 SSH：拿你的 SSH public key 寫進去，得到一張有效幾小時的簽證。

Chapter 11Secret Engine 共通機制

所有 Secret Engine 都共享一組生命週期 API（enable / disable / move / tune）以及一個叫做「barrier view」的隔離機制。先把共通的部分學完，後面每一章你會看得更輕鬆。

11.1 Engine 的生命週期

① enable（掛載一個 engine）

# 預設 path 等於 type
$ bao secrets enable kv-v2
Success! Enabled the kv-v2 secrets engine at: kv-v2/

# 自訂 path
$ bao secrets enable -path=team-a/secret kv-v2

# 同一 type 可重複掛在不同 path
$ bao secrets enable -path=team-a/secret kv-v2
$ bao secrets enable -path=team-b/secret kv-v2
⚠ Path case-sensitive

Mount path 嚴格區分大小寫。kv/ 和 KV/ 是兩個不同的 engine，互不影響。看似筆誤的失誤可能讓你的 policy 全部失效。

② disable（關閉 engine）

$ bao secrets disable team-a/secret/
Success! Disabled the secrets engine (if it existed) at: team-a/secret/

Disable 時：

  • 所有相關 lease 自動 revoke（如果是 dynamic engine，現有動態憑證立刻失效）。
  • 該 engine 在 storage 中的所有資料被刪除。
  • 不可逆。 Disable 一個 KV mount 等於永久刪除其下所有 secrets。

③ move（搬遷 path）

$ bao secrets move secret/ kv/
Success! Finished moving auth method secret/ to kv/

Move 會 revoke 所有現有 lease（lease ID 跟 path 綁定），但 mount data 保留。對 KV 影響小，對 Database/PKI 等影響大。

④ tune（調整設定）

# 調整 mount 的預設 / 最大 TTL
$ bao secrets tune -default-lease-ttl=1h -max-lease-ttl=24h database/

# 開啟某些 audit / response header 的傳遞
$ bao secrets tune -allowed-response-headers="Last-Modified" pki/

⑤ list（看現在掛了什麼）

$ bao secrets list
Path          Type         Accessor              Description
----          ----         --------              -----------
cubbyhole/    cubbyhole    cubbyhole_xxx         per-token private secret storage
identity/     identity     identity_xxx          identity store
kv/           kv-v2        kv-v2_xxx             ...
secret/       kv-v2        kv-v2_xxx             ...
sys/          system       system_xxx            system endpoints used for control, ...

11.2 Barrier View — 為什麼 engine 之間互不干擾

每次 enable 一個 engine，OpenBao 會分配一個隨機 UUID 作為它的 storage 根目錄。這個 engine 在 storage 內的所有讀寫都被自動加上這個 UUID 前綴 — 由於 OpenBao storage 不支援 ../ 相對路徑，「即使是惡意 plugin engine 也無法存取其他 engine 的資料」。

這個 chroot-like 的隔離，加上 barrier 加密（每個 engine 寫到 storage 的內容都先加密），就是 OpenBao multi-tenancy 安全性的基礎。

11.3 Mount 路徑衝突規則

Mount path 不能彼此衝突。具體規則：

  • 不能掛在現有 mount 的子路徑下。例如：已有 foo/，就不能再掛 foo/bar。
  • 不能把現有 mount 變成新 mount 的前綴。例如：已有 foo/baz，就不能再掛 foo。
  • 但 foo/bar 與 foo/baz 平行存在可以。

11.4 同一 Engine 多次掛載的時機

幾個典型用例：

場景多 mount 設計原因
多團隊隔離team-a/secret/、team-b/secret/Policy 容易寫；team-a 的 token 完全看不到 team-b 的 mount
分環境secret/dev/、secret/prod/單一 mount + path prefix 也可以，兩種都常見

11.6 ⚙ 動手練習

  1. 啟用同一 KV v2 engine 在三個不同 path：secret/、team-a/、team-b/。
  2. 用 bao secrets list 確認三個都在。
  3. 嘗試掛 secret/sub，觀察衝突錯誤訊息。
  4. 用 bao secrets tune -default-lease-ttl=30m secret/ 調整 TTL，再用 bao secrets list -detailed 看效果。

Chapter 12KV（Key/Value）秘密引擎

KV 是 OpenBao 最常用、最易上手的 engine。但「最簡單」不代表「沒有眉角」— v1 與 v2 的差異、metadata 的特殊地位、versioning 的軟刪/硬刪語意，都是初學者最常掉進去的坑。

12.1 KV v1 vs v2：什麼時候用哪個

① 概念差異

KV v1（簡單儲存）

  • 單純的 key-value，沒有版本
  • 每次 write 直接覆寫
  • Storage 較小，請求較快
  • 沒有 metadata 層
  • 軟刪除沒有（DELETE 就是真刪）

適合：靜態 config、效能敏感的場景。

KV v2（版本化儲存，預設）

  • 每次 write 產生新版本
  • 預設保留 10 版（可調）
  • 支援 check-and-set（CAS）防衝突寫
  • 支援軟刪 → undelete → destroy 三層
  • 有獨立的 metadata 端點

適合：需要 audit、需要回溯、團隊共用的場景（絕大多數情況）。

② Dev mode 預設用 v2

Dev server 啟動時，「KV v2 已預設掛在 secret/」。Production 啟動時則需要自己 enable。本章接下來都以 v2 為主。

12.2 啟用 KV v2 與第一筆寫入

# 啟用 KV v2 在預設 path 'kv-v2/'
$ bao secrets enable kv-v2

# 或啟用在自訂 path
$ bao secrets enable -path=secret -version=2 kv

# 寫入（推薦用 -mount 旗標明確）
$ bao kv put -mount=secret myapp/config \
    db_user=appuser \
    db_password=s3cret

== Secret Path ==
secret/data/myapp/config

======= Metadata =======
Key            Value
---            -----
created_time   2026-05-05T...
custom_metadata 
deletion_time  n/a
destroyed      false
version        1

注意 CLI 輸出的 path 是 secret/data/myapp/config，比你輸入的多了一段 data/。這是 v2 的真實 API 路徑。「path-like 寫法 (secret/myapp/config) 仍可用，但容易和真實 API path 混淆，因此建議用 -mount 旗標」。

12.3 讀取與輸出格式

# 預設 table 輸出
$ bao kv get -mount=secret myapp/config

# 只取單一欄位（適合 shell 命令串）
$ DB_PWD=$(bao kv get -mount=secret -field=db_password myapp/config)

# JSON 輸出
$ bao kv get -mount=secret -format=json myapp/config | jq '.data.data'

# 取特定版本
$ bao kv get -mount=secret -version=2 myapp/config

12.4 Versioning 與 Check-and-Set

① 為什麼需要 CAS

沒有 CAS 的情況下，兩個 client 同時寫 secret/myapp/config，後寫的會覆蓋先寫的（last-write-wins）。在分散式系統這不安全。CAS 讓你說：「我認為現在版本是 N，請只在這個前提下寫入」：

# 第一次寫，CAS 0 表示「這把 key 必須不存在」
$ bao kv put -mount=secret -cas=0 myapp/config password=s3cret

# 之後寫，必須說明你以為的當前版本
$ bao kv put -mount=secret -cas=1 myapp/config password=newer

# 如果 CAS 不對，OpenBao 會拒絕：
$ bao kv put -mount=secret -cas=1 myapp/config password=stale
Error: check-and-set parameter did not match the current version

② 強制全 mount CAS

# 設定整個 mount 強制每次寫都要 CAS
$ bao write secret/config cas_required=true

# 也可在單一 key 級別設定
$ bao kv metadata put -mount=secret -cas-required=true myapp/config

12.5 軟刪、Undelete、Destroy

v2 把「刪除」分成三層，是新人最容易誤操作的地方。

# 軟刪最新版本（可 undelete）
$ bao kv delete -mount=secret myapp/config

# 軟刪指定版本
$ bao kv delete -mount=secret -versions=2 myapp/config

# 還原已軟刪的版本
$ bao kv undelete -mount=secret -versions=2 myapp/config

# 永久銷毀某版本（不可逆！）
$ bao kv destroy -mount=secret -versions=2 myapp/config

# 永久刪除整把 key（含所有版本與 metadata，不可逆！）
$ bao kv metadata delete -mount=secret myapp/config
⛔ kv metadata delete 不可逆

它會把整把 key 的所有版本連同 metadata 一併消失。給對應 path 的 delete capability on secret/metadata/* 等於給「永久刪除」權限。Production 環境應該嚴格限制這個 capability。

12.6 Custom Metadata 與 max_versions

# 為一把 key 加 custom metadata（不會出現在 data 裡）
$ bao kv metadata put -mount=secret \
    -custom-metadata=owner=platform-team \
    -custom-metadata=ticket=PLAT-1234 \
    myapp/config

# 設定這把 key 最多保留 5 版（超過的舊版自動 destroy）
$ bao kv metadata put -mount=secret -max-versions=5 myapp/config

# 設定 7 天後自動刪除版本
$ bao kv metadata put -mount=secret \
    -delete-version-after=168h \
    myapp/config

# 查 metadata
$ bao kv metadata get -mount=secret myapp/config

12.7 Patch — 只更新部分欄位

沒有 patch 的話，更新一把 secret 的單一欄位需要先 read → 修改 → 整把 write 回去。Patch 讓你直接：

$ bao kv patch -mount=secret myapp/config new_field=new_value

注意 patch 也會產生新版本。Policy 上需要單獨給 patch capability。

12.8 KV 對應的 Policy 範例

第二冊已經提到 v2 的雙層 path（data/metadata）。完整的「應用唯讀」policy 如下：

# app-readonly.hcl

# 讀資料
path "secret/data/myapp/*" {
  capabilities = ["read"]
}

# 列出 / 看版本資訊
path "secret/metadata/myapp/*" {
  capabilities = ["read", "list"]
}

「應用可寫」+「但不能永久刪除」：

path "secret/data/myapp/*" {
  capabilities = ["create", "read", "update", "patch"]
}

path "secret/metadata/myapp/*" {
  capabilities = ["read", "list"]
  # 故意不給 delete - 防止 metadata delete 永久刪整把
}

path "secret/delete/myapp/*" {
  capabilities = ["update"]   # 軟刪 OK
}

# 故意不給 destroy - 防止永久銷毀某版本

12.9 三套環境實作

① Linux/Docker：基本流程

# 啟動 dev server (見第一冊)
$ bao server -dev -dev-root-token-id=dev-only-token &
$ export BAO_ADDR=http://127.0.0.1:8200 BAO_TOKEN=dev-only-token

# KV 已預設掛在 secret/，直接寫
$ bao kv put -mount=secret myapp/db url=postgres://...
$ bao kv get -mount=secret myapp/db

② Kubernetes：Pod 透過 Kubernetes auth + KV 取得設定

結合第二冊的 K8s auth：

# 在 OpenBao 端
$ bao auth enable kubernetes
$ bao write auth/kubernetes/config \
    kubernetes_host="https://kubernetes.default.svc" \
    kubernetes_ca_cert=@ca.crt

$ bao policy write app-ro - <<EOF
path "secret/data/myapp/*" { capabilities = ["read"] }
path "secret/metadata/myapp/*" { capabilities = ["read", "list"] }
EOF

$ bao write auth/kubernetes/role/myapp \
    bound_service_account_names=myapp \
    bound_service_account_namespaces=production \
    policies=app-ro \
    token_ttl=1h

# 把要給應用讀的 secret 寫進 KV
$ bao kv put -mount=secret myapp/db \
    url="postgres://prod-db:5432/myapp" \
    user=appuser password=prod-pwd

Pod 端用 sidecar / init container 讀取（完整模式在第四冊 OpenBao Agent 章節展開）：

12.10 Production 注意事項

  • 不要把 KV v2 mount 設太低 max_versions（如 max_versions=2），會在錯誤回滾時懊悔。預設 10 通常夠用。
  • 大的 secret 不要塞 KV。KV value 上限通常是 1MB（受 storage 限制），且每版都會占空間。要存大檔，請用其他方式 + KV 存路徑。
  • KV 不發 lease，所以靠它的 secret 不會自動過期。應用自己要週期性 re-fetch。
  • 稽核 metadata delete：在 audit log 過濾 operation=delete + path=secret/metadata/*，這是 high-risk 動作。
✓ 章末重點
  • KV v2 在 dev mode 預設掛 secret/；production 要自己 enable。
  • 實際 API path 是 secret/data/... 與 secret/metadata/...；CLI 用 -mount 旗標最不會搞錯。
  • delete vs destroy vs metadata delete：三層意義完全不同，policy 要對應分權。
  • CAS 是分散式寫入時的安全網。
  • KV 不發 lease，自動過期靠 max_versions + delete_version_after。

Chapter 13Database 動態憑證

「不要把資料庫密碼寫在程式碼裡」是老話了。但即使用了 KV，密碼還是同一把、所有應用共用、忘記輪替也不會壞。Database engine 把這件事做到極致：每個應用、每次連線可以拿到全新、有過期時間、自動回收的 DB 帳號。

13.1 動態 vs 靜態憑證

① 概念

Dynamic Roles（動態）

  • 每次 read 產生全新帳號
  • 有 lease，到期自動 DROP USER
  • 適合：應用、CI、batch job
  • 缺點：DB 可能短時間累積大量帳號

Static Roles（靜態）

  • OpenBao 託管既存的 DB user
  • 定期自動輪替密碼
  • 適合：不能換 username 的場景（legacy app、共用帳號、SaaS connector）
  • 注意：不要用 root 帳號做 static role！

② 共通設定流程

  1. Enable engine：bao secrets enable database。
  2. Configure DB connection：告訴 OpenBao 怎麼連 DB（包含一個有「建立其他 user」權限的 admin 帳號）。
  3. Define role：設定 SQL 模板（CREATE USER ... GRANT ...）與 TTL。
  4. Application reads /creds/<role>：每次取得一組臨時帳密。
  5. OpenBao 自動 rotate root credentials（建議定期）。

13.2 完整範例：PostgreSQL Dynamic Role

① 準備 Database

用 Docker 跑一個 PostgreSQL：

$ docker run -d --name pg \
    -e POSTGRES_PASSWORD=dev-pwd \
    -p 5432:5432 \
    postgres:16

# 在 PG 內建立一個 OpenBao 用的 admin user
$ docker exec -it pg psql -U postgres -c "
  CREATE ROLE openbao WITH LOGIN PASSWORD 'openbao-init-pwd' SUPERUSER;
"

② OpenBao 端設定

# 1. 啟用 database engine
$ bao secrets enable database

# 2. 配置 PostgreSQL 連線
$ bao write database/config/myapp-pg \
    plugin_name=postgresql-database-plugin \
    allowed_roles="myapp-ro,myapp-rw" \
    connection_url="postgresql://{{username}}:{{password}}@127.0.0.1:5432/postgres?sslmode=disable" \
    username="openbao" \
    password="openbao-init-pwd" \
    password_authentication="scram-sha-256"

# 3. 立刻 rotate 掉初始密碼（OpenBao 把它換成只有自己知道的）
$ bao write -force database/rotate-root/myapp-pg

# 4. 建立 read-only role
$ bao write database/roles/myapp-ro \
    db_name=myapp-pg \
    creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; \
                         GRANT pg_read_all_data TO \"{{name}}\";" \
    revocation_statements="DROP ROLE IF EXISTS \"{{name}}\";" \
    default_ttl=1h \
    max_ttl=24h

# 5. 取得一組動態帳密
$ bao read database/creds/myapp-ro
Key                Value
---                -----
lease_id           database/creds/myapp-ro/abcd-1234
lease_duration     1h
lease_renewable    true
password           A1b2-c3D4-eF5g
username           v-token-myapp-ro-XYZw9-1715000000

每次 read 都是全新的 username/password。Lease 1h 後，OpenBao 自動執行 revocation_statements（DROP ROLE）。如果應用希望延長使用，呼叫 bao lease renew 即可（但不能超過 max_ttl）。

③ Username 模板

預設 username 看起來像 v-token-myapp-ro-XYZw9-1715000000，太長且不易閱讀。可以自訂：

$ bao write database/config/myapp-pg \
    plugin_name=postgresql-database-plugin \
    ... \
    username_template='myapp_{{.RoleName | truncate 8}}_{{random 10}}'

變數參考：.DisplayName、.RoleName、.UnixTime、random N、truncate N 等。受限於 PostgreSQL 63 char 上限。

13.3 Static Role 範例

場景：legacy 應用無法支援動態帳號，必須用固定 username legacy_app，但你想自動輪替它的密碼：

# 預先在 DB 建好 user
$ docker exec -it pg psql -U postgres -c "
  CREATE ROLE legacy_app WITH LOGIN PASSWORD 'temporary';
  GRANT CONNECT ON DATABASE postgres TO legacy_app;
"

# 在 OpenBao 設 static role
$ bao write database/static-roles/legacy-app \
    db_name=myapp-pg \
    username="legacy_app" \
    rotation_period="24h"

# 讀當前密碼（OpenBao 已輪替過）
$ bao read database/static-creds/legacy-app
Key                    Value
---                    -----
last_vault_rotation    2026-05-05T00:00:00Z
password               new-rotated-pwd
rotation_period        24h
ttl                    23h59m...
username               legacy_app

應用每次需要連 DB 都來 read 這個 endpoint，就拿到當前密碼。OpenBao 每 24 小時主動輪替一次，且永遠是 OpenBao 唯一知道密碼。

⛔ 不要把 root 設為 static role

官方明確警告：「不要把你提供給 OpenBao 的 config/ root credentials 交給 static role 管理。OpenBao 不會分辨『一般 user』與『root user』，輪替後 config/ 的密碼就失效了，所有 dynamic / static 帳號都會跟著壞。」

輪替 root 用 database/rotate-root/<name> 端點，不要用 static role。

13.5 MySQL/MariaDB 範例摘要

$ bao write database/config/my-mysql-database \
    plugin_name=mysql-database-plugin \
    connection_url="{{username}}:{{password}}@tcp(127.0.0.1:3306)/" \
    allowed_roles="my-role" \
    username="root" \
    password="mysql"

$ bao write database/roles/my-role \
    db_name=my-mysql-database \
    creation_statements="CREATE USER '{{name}}'@'%' IDENTIFIED BY '{{password}}'; \
                         GRANT SELECT ON *.* TO '{{name}}'@'%';" \
    default_ttl="1h" max_ttl="24h"

$ bao read database/creds/my-role
⚠ MySQL 反引號陷阱

MySQL 的 GRANT 語法常用反引號（`db\_%`）包資料庫名。但 shell 的反引號會被解釋成命令執行。「最簡單的解法是把 creation_statements 用 base64 編碼後傳入」，或用 HEREDOC 寫設定檔再讀。

13.6 在 K8s 給應用用

應用 pod 拿到 K8s auth 換來的 OpenBao token 後，呼叫 read database/creds/myapp-ro 拿動態帳密：

// 在 pod 啟動的初始化邏輯中
client, _ := openbao.NewClient(&openbao.Config{Address: os.Getenv("BAO_ADDR")})
// (透過 K8s SA token 完成 login，省略)

secret, err := client.Logical().Read("database/creds/myapp-ro")
if err != nil { log.Fatal(err) }

dbUser := secret.Data["username"].(string)
dbPwd  := secret.Data["password"].(string)
leaseID := secret.LeaseID
// connect to DB ...

// 啟動背景 lifetime watcher 自動 renew lease
watcher, _ := client.NewLifetimeWatcher(&openbao.LifetimeWatcherInput{
    Secret: secret,
})
go watcher.Start()
defer watcher.Stop()

Pod 結束時應該主動 revoke lease（避免 DB 帳號殘留 1h）：

// SIGTERM handler
client.Sys().Revoke(leaseID)

或者乾脆讓 OpenBao Agent 全自動處理（第四冊）。

13.7 Production 注意事項

  • 初始 root 一定要 rotate。bao write -force database/rotate-root/<name> 會把 OpenBao 連線用的密碼換掉，從此只有 OpenBao 知道。
  • 給 OpenBao 的 admin 帳號權限最小化：只需要 CREATE/DROP USER + GRANT 範圍內的權限，不要直接給 superuser（PG 在某些版本必須）。
  • Lease quota：bao write sys/quotas/lease-count/db-cap path=database/ max_leases=1000，避免某 client 失控產生上千個 DB 帳號。
  • 監控 leasing：metric vault.expire.num_leases、vault.token.creation。
  • 選 dynamic 還是 static：能 dynamic 就 dynamic；只有當應用真的不能換帳號（如某些 SaaS connector）才用 static。

13.8 ⚙ 動手練習

  1. 跑 PostgreSQL container，依本章流程設定 dynamic role，取得帳密後用 psql 直接連線測試。
  2. 觀察 PostgreSQL 端的 \du 列出的 user，等到 lease 過期看是否消失。
  3. 建立 static role，手動觸發一次 bao write -force database/rotate-role/<name>，再 read 看密碼變了沒。
  4. 故意設一個 creation_statements 內含錯誤 SQL，看 OpenBao 回什麼錯。

Chapter 14PKI（企業憑證簽發）

PKI 大概是 OpenBao 中最強大、也最容易踩雷的 engine。它讓你的組織擁有一套可程式化的 CA：可以幾秒鐘內簽發 server / client 憑證、支援 ACME（像 Let's Encrypt 那樣的協議）、可在 Kubernetes 透過 cert-manager 自動取得 internal TLS。

14.1 為什麼用 OpenBao 做 PKI

  • 程式化簽發：service-to-service mTLS 不需要每次手動 CSR + 等簽。
  • 短 TTL：簽出來的 cert 預設只活幾小時或幾天，過期自然死，不需要 CRL 撐起一張長 list。
  • 每個 instance 一張獨立 cert：防止憑證共享、防 lateral movement。
  • 內建 ACME：自動跟 cert-manager、Traefik、Caddy 等整合。

14.2 PKI 階層設計

① Root CA + Intermediate CA

正式環境絕對不要用 root CA 直接簽發 leaf cert。標準做法：

官方建議「Root CA 維護於 OpenBao 之外，並把已簽好的 intermediate CA 提供給 OpenBao」。本章為了教學完整性，會示範整套包含 root 都在 OpenBao 內。

14.3 完整流程：建 Root + Intermediate

① 建立 Root CA mount

# 啟用 PKI 並命名為 pki-root
$ bao secrets enable -path=pki-root pki

# Tune mount，把 max TTL 拉到 10 年（Root CA 的 lifetime）
$ bao secrets tune -max-lease-ttl=87600h pki-root

# 產生 Root CA（在 OpenBao 內部產生 keypair，外部看不到 private key）
$ bao write -field=certificate pki-root/root/generate/internal \
    common_name="Example Internal Root CA" \
    issuer_name="root-2026" \
    ttl=87600h > root-ca.crt

# 設 issuing 與 CRL URL（cert 內會嵌這些）
$ bao write pki-root/config/urls \
    issuing_certificates="https://bao.example.com/v1/pki-root/ca" \
    crl_distribution_points="https://bao.example.com/v1/pki-root/crl"

② 建立 Intermediate CA mount

$ bao secrets enable -path=pki-int pki
$ bao secrets tune -max-lease-ttl=43800h pki-int   # 5 年

# 產生 Intermediate CSR
$ bao write -format=json pki-int/intermediate/generate/internal \
    common_name="Example Internal Intermediate" \
    issuer_name="int-2026" \
  | jq -r '.data.csr' > pki_int.csr

# 用 Root 簽 Intermediate CSR，TTL 5 年
$ bao write -format=json pki-root/root/sign-intermediate \
    csr=@pki_int.csr \
    format=pem_bundle \
    ttl=43800h \
  | jq -r '.data.certificate' > intermediate.cert.pem

# 把已簽好的 Intermediate cert 寫回 Intermediate mount
$ bao write pki-int/intermediate/set-signed \
    certificate=@intermediate.cert.pem

# Intermediate 也要設 URL（讓 leaf cert 有正確的 chain 與 CRL distribution）
$ bao write pki-int/config/urls \
    issuing_certificates="https://bao.example.com/v1/pki-int/ca" \
    crl_distribution_points="https://bao.example.com/v1/pki-int/crl"

③ 建立 Role：規範什麼樣的 cert 可以被簽

$ bao write pki-int/roles/example-com \
    issuer_ref="$(bao read -field=default pki-int/config/issuers)" \
    allowed_domains="example.com,example.local" \
    allow_subdomains=true \
    allow_bare_domains=false \
    allow_glob_domains=false \
    enforce_hostnames=true \
    max_ttl="72h" \
    key_type="ec" \
    key_bits="256"

Role 是 PKI 安全的第一道牆 — 它規定哪些 SAN 可被請求、哪種 key、哪種用途。Production 上要嚴格限縮。

④ 簽發 leaf cert

# Issue：OpenBao 同時生成 keypair 與 cert
$ bao write pki-int/issue/example-com \
    common_name="api.example.com" \
    ttl="48h"

Key                Value
---                -----
ca_chain           [...]
certificate        -----BEGIN CERTIFICATE-----...
expiration         1715250000
issuing_ca         -----BEGIN CERTIFICATE-----...
private_key        -----BEGIN EC PRIVATE KEY-----...
private_key_type   ec
serial_number      ab:cd:...

# 或：用客戶端自己產的 CSR 簽
$ bao write pki-int/sign/example-com \
    csr=@my-csr.pem \
    common_name="api.example.com" \
    ttl="48h"

14.4 ACME — 內網的 Let's Encrypt

OpenBao PKI 支援 ACME 協議，意味著你可以直接讓 cert-manager / Traefik / Caddy 等熟悉 ACME 的工具，從 OpenBao 自動取憑證並自動 renew。

啟用 ACME

# Tune mount 允許 ACME 必要的 response header
$ bao secrets tune \
    -allowed-response-headers="Last-Modified,Replay-Nonce,Link,Location" \
    pki-int

# 設 cluster URL（ACME directory 會用到）
$ bao write pki-int/config/cluster \
    path="https://bao.example.com/v1/pki-int" \
    aia_path="https://bao.example.com/v1/pki-int"

# Enable ACME on this mount
$ bao write pki-int/config/acme \
    enabled=true

使用時，把 ACME directory 指向 https://bao.example.com/v1/pki-int/roles/example-com/acme/directory 即可。

14.5 Cert 撤銷：CRL 與 OCSP

# 用 serial number 撤銷
$ bao write pki-int/revoke serial_number="ab:cd:..."

# 取得當前 CRL（leaf 已 embed 的 crl_distribution_points 會指向這個）
$ curl -s $BAO_ADDR/v1/pki-int/crl/pem

# OpenBao PKI 也支援 OCSP responder
$ curl -s $BAO_ADDR/v1/pki-int/ocsp \
    --request POST \
    --data-binary @ocsp-request.der \
    --header "Content-Type: application/ocsp-request"

但 PKI 哲學是「盡量讓 cert 短命，這樣 CRL 不需要被認真維護」。72h ttl 的 cert 比 90 天並嚴格 OCSP/CRL 監控好得多。

14.6 與 Kubernetes cert-manager 整合

cert-manager 是 K8s 的事實標準 cert 自動化工具，原生支援 OpenBao（透過 vault-style ClusterIssuer）：

apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: openbao-pki
spec:
  vault:
    server: https://bao.example.com:8200
    path: pki-int/sign/example-com
    auth:
      kubernetes:
        role: cert-manager
        mountPath: /v1/auth/kubernetes
        secretRef:
          name: cert-manager-token
          key: token
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: api-tls
  namespace: production
spec:
  secretName: api-tls-cert
  issuerRef:
    name: openbao-pki
    kind: ClusterIssuer
  commonName: api.example.com
  dnsNames:
  - api.example.com
  duration: 72h        # cert lifetime
  renewBefore: 24h     # 24h 前 renew

cert-manager 會：(1) 用 K8s SA login OpenBao；(2) 生成 CSR 送 OpenBao 簽；(3) 把 cert 存進 K8s Secret；(4) 到 renewBefore 時間自動再簽一次。應用只需要掛載這個 K8s Secret 即可。

14.7 PKI Health Check

OpenBao 提供一個內建的 pki health-check 指令，會掃 mount 配置常見問題：

$ bao pki health-check pki-int

它會檢查例如：「Root CA 上是否有不該存在的 leaf 簽發」、「ACME 啟用但缺 response headers」、「Role 設定 allow_localhost=true 是否安全」等等。Production 上線前一定跑一次。

14.8 Production 注意事項

  • Root CA 離線保管最理想。如果一定要在 OpenBao 內，那一定要把 root mount 的 policy 鎖死，禁止 sign / issue endpoint，只允許 sign-intermediate。
  • Role 要嚴格：allowed_domains 明確列出、allow_glob_domains=false、require_cn=true。
  • ext_key_usage 限縮：server cert 不需要 client auth、反之亦然。
  • Audit metadata：bao secrets tune -audit-non-hmac-request-keys=common_name,alt_names pki-int，否則 audit log 看不到 CN 是什麼。
  • Cert TTL 短一點：72h、24h 都很常見；越短越不需要 CRL/OCSP。
  • 監控指標：vault.pki.*.issue、vault.pki.*.sign、vault.pki.*.revoke。

14.9 ⚙ 動手練習

  1. 建立 Root + Intermediate 兩個 mount，並完成 cross signing。
  2. 建立 role internal-svc，限定 SAN 只能在 *.svc.cluster.local，發一張 cert。
  3. 用 openssl x509 -text 檢查發出的 cert，確認 CRL/AIA URL 正確嵌入。
  4. 跑 bao pki health-check pki-int，依照建議改進。

Chapter 15SSH 秘密引擎

用 OpenBao 管理 SSH access 有兩種模式：簽署 SSH 公鑰（推薦）、與 OTP（少用）。前者把 SSH 變成「拿著今天有效的簽證連線，不需要在每台機器佈 authorized_keys」。

15.1 兩種模式比較

Signed SSH Certificates（推薦）OTP
機制OpenBao 當 SSH CA，簽你的 public keyOpenBao 為每次連線發 OTP，目標主機驗
目標主機需要信任 OpenBao 的 CA public key跑 vault-ssh-helper 守護程序
授權檔TrustedUserCAKeys 一次設好不用
適合大規模、靜態主機叢集少量、需嚴格 audit 的情境
離線可用使用者拿到簽證後可離線連不行（每次連線都要打 OpenBao）

本章重點放在 Signed Certificates 模式。

15.2 Signed Certificates：完整流程

① OpenBao 端：建立 SSH CA

# 啟用兩個 SSH mount：一個簽 client key，一個簽 host key
$ bao secrets enable -path=ssh-client-signer ssh
$ bao secrets enable -path=ssh-host-signer ssh

# 在每個 mount 各自產生 CA keypair
$ bao write ssh-client-signer/config/ca generate_signing_key=true
$ bao write ssh-host-signer/config/ca generate_signing_key=true

# 取出 client signer 的 CA public key（給目標主機）
$ bao read -field=public_key ssh-client-signer/config/ca \
    > ssh_client_ca.pub
# 取出 host signer 的 CA public key（給 SSH client 信任）
$ bao read -field=public_key ssh-host-signer/config/ca \
    > ssh_host_ca.pub

② 在目標主機：信任 client CA、用 host CA 簽自己的 host key

# 把 client CA pub 放進 sshd 設定
$ sudo cp ssh_client_ca.pub /etc/ssh/trusted-user-ca-keys.pem
# /etc/ssh/sshd_config 加上：
#     TrustedUserCAKeys /etc/ssh/trusted-user-ca-keys.pem
$ sudo systemctl reload sshd

# 把 host 的 public key 拿給 OpenBao 簽
$ bao write -field=signed_key ssh-host-signer/sign/host-role \
    cert_type=host \
    public_key=@/etc/ssh/ssh_host_ed25519_key.pub \
    > /etc/ssh/ssh_host_ed25519_key-cert.pub

# /etc/ssh/sshd_config 加上：
#     HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
$ sudo systemctl reload sshd

③ OpenBao 端：建立 client 用的 role

$ bao write ssh-client-signer/roles/dev-role \
    key_type=ca \
    algorithm_signer=rsa-sha2-256 \
    allow_user_certificates=true \
    allowed_users="ubuntu,deploy" \
    default_user="ubuntu" \
    default_extensions='{"permit-pty":""}' \
    ttl="8h" \
    max_ttl="24h"

④ 在使用者本機：取得簽證並登入

# 用 OpenBao 簽自己的 SSH public key
$ bao write -field=signed_key ssh-client-signer/sign/dev-role \
    public_key=@$HOME/.ssh/id_ed25519.pub \
    valid_principals="ubuntu" \
    > $HOME/.ssh/id_ed25519-cert.pub

# 用簽證 + 自己的私鑰登入
$ ssh -i ~/.ssh/id_ed25519-cert.pub \
      -i ~/.ssh/id_ed25519 \
      ubuntu@target.example.com

OpenSSH 在 7.0+ 看到同名 cert 會自動把它 attach 到登入請求。簽證在 8 小時後自動失效，使用者需要重新跟 OpenBao 簽 — 這就是「免發、免回收」的精髓。

⑤ 客戶端信任 host CA

讓使用者的 SSH client 信任 OpenBao 的 host CA：

$ cat >> ~/.ssh/known_hosts <<EOF
@cert-authority *.example.com $(cat ssh_host_ca.pub)
EOF

這樣連線時不會再跳出 known_hosts prompt，且能驗證主機真的是被你 CA 簽過的。

15.3 進階：SSH CA Multi-issuer

OpenBao SSH engine 支援單一 mount 多個 issuer（CA），方便進行不停機 CA rotation：

  1. 在現有 mount 中產生第二個 CA：bao write ssh-client-signer/issuers/import ...。
  2. 在所有目標主機的 TrustedUserCAKeys 裡同時放兩個 CA pub。
  3. 把 OpenBao 預設 issuer 切到新的，新發的簽證用新 CA。
  4. 等舊簽證全部 TTL 過期後，再從目標主機移除舊 CA。

15.4 OTP 模式（簡述）

$ bao secrets enable ssh
$ bao write ssh/roles/otp-role \
    key_type=otp \
    default_user=ubuntu \
    cidr_list=10.0.0.0/8

# 取得 OTP（限定使用一次）
$ bao write ssh/creds/otp-role ip=10.0.23.5

# 直接以 OpenBao CLI 包裝 ssh
$ bao ssh -role=otp-role -mode=otp ubuntu@10.0.23.5

目標主機需要先安裝 vault-ssh-helper 並改 PAM 設定。OTP 模式現代環境少用，主要在不能改 sshd_config 但可改 PAM 的 legacy 環境才會考慮。

15.5 Production 注意事項

  • 用 ed25519 / RSA-SHA2-256，不要用 SHA1；OpenBao 預設已避免 ssh-rsa。
  • TTL 短：8h（一個工作天）是常見值。
  • 限 principals：role 上 allowed_users 加 token entity 的 metadata template，做到「只能用自己的 username」。
  • 分離 client/host signer：兩個 mount，policy 完全獨立，避免 client signer 被濫用簽 host cert。
  • 監控簽證量：vault.ssh.*.sign。

15.6 ⚙ 動手練習

  1. 用兩個 Docker container 模擬「OpenBao + 一台 SSH server」，跑通簽證簽發、登入、主機驗證。
  2. 故意把簽證 TTL 設成 1 分鐘，觀察過期後是否被拒。
  3. 在 role 上加 valid_principals_template=true，用 entity metadata 動態限制 principals。

Chapter 16Transit：加密即服務

前面的 engine 都是「OpenBao 存資料、應用來拿」。Transit 反過來：OpenBao 不存應用的資料，只負責加解密。應用把 plaintext 給 OpenBao，得到 ciphertext，存到自家 SQL；要看時把 ciphertext 給 OpenBao，得到 plaintext。金鑰永遠不離開 OpenBao。

16.1 Transit 解決的問題

  • Application-level encryption 不想自己處理 key：應用層加密敏感欄位（信用卡號、身分證、PII），但開發者不該、也不想處理 key generation、storage、rotation。
  • Envelope encryption：加密大量資料時，用 datakey 加密內容、用 OpenBao key 加密 datakey，能兼顧效能與安全。
  • 跨應用一致簽章驗證：用 OpenBao 簽 token / 訊息，多個服務驗證。
  • Searchable encryption：convergent encryption 讓相同 plaintext 永遠對應相同 ciphertext，可在密文上做欄位等值搜尋。

16.2 支援的 Key Type

Type用途支援的操作
aes256-gcm96（預設）對稱加解密encrypt / decrypt / derive / convergent
aes128-gcm96對稱加解密（較弱）同上
chacha20-poly1305對稱加解密（無 AES-NI 環境較快）同上
ed25519簽章sign / verify / derive
ecdsa-p256 / p384 / p521簽章sign / verify
rsa-2048 / 3072 / 4096加解密 + 簽章encrypt / decrypt / sign / verify
hmacHMAChmac / verify_hmac

「所有 key type 也都支援 HMAC」，因為 OpenBao 在創建 key 時會額外生成一把 HMAC key 配對。

16.3 基本：Encrypt / Decrypt

# 啟用 transit
$ bao secrets enable transit

# 建立一把 key
$ bao write -f transit/keys/myapp-data

# 加密（plaintext 必須 base64 編碼）
$ PT=$(echo -n "hello world" | base64)
$ bao write transit/encrypt/myapp-data plaintext="$PT"
Key            Value
---            -----
ciphertext     vault:v1:abc123...
key_version    1

# 解密
$ bao write transit/decrypt/myapp-data \
    ciphertext="vault:v1:abc123..."
Key          Value
---          -----
plaintext    aGVsbG8gd29ybGQ=

# Base64 decode 看明文
$ echo "aGVsbG8gd29ybGQ=" | base64 -d
hello world

Ciphertext 格式

注意 ciphertext 的 prefix vault:v1: — 這是 OpenBao 的 ciphertext envelope，包含 key version 資訊。這讓 key rotation 後仍能正確解開歷史資料。

16.4 Key Rotation：在線輪替

# 輪替 key（生成 v2）
$ bao write -f transit/keys/myapp-data/rotate

# 從現在起，新加密用 v2
$ bao write transit/encrypt/myapp-data plaintext="$PT"
ciphertext     vault:v2:...

# 但舊的 vault:v1:... 仍能解（OpenBao 仍持有 v1 key）

# Rewrap：把舊版本 ciphertext 升級到當前 key 版本
$ bao write transit/rewrap/myapp-data \
    ciphertext="vault:v1:abc123..."
ciphertext     vault:v2:...

# 設定最低可解密版本（舊版本 archive）
$ bao write transit/keys/myapp-data/config \
    min_decryption_version=2 \
    min_encryption_version=2

典型 rotation 流程：

  1. 定期（每 90 天）rotate。
  2. 應用平日寫資料時，自動用新版加密（OpenBao 預設）。
  3. 背景 job 把舊版 ciphertext 用 rewrap 升級到新版（不需要拿到 plaintext，可批次跑）。
  4. 確認沒有舊版資料後，調 min_decryption_version 拒絕舊版本。

16.5 Datakey：Envelope Encryption

當你要加密大檔（影片、log archive），不適合每次都呼叫 transit/encrypt（網路延遲、size 限制）。改用 envelope encryption：

# 跟 OpenBao 要一個 datakey
# - 回傳「明文 datakey」+「用 myapp-data 加密過的 datakey」
$ bao write -f transit/datakey/plaintext/myapp-data
Key            Value
---            -----
ciphertext     vault:v2:wrappedDataKey...
plaintext      randomGeneratedDataKeyBase64

應用收到後：

  1. 用明文 datakey 在本機 AES-GCM 加密大檔（自己做，OpenBao 不參與）。
  2. 把加密過的 datakey ciphertext 存在大檔旁。
  3. 立刻丟掉明文 datakey。
  4. 需要解時：把 ciphertext datakey 給 OpenBao decrypt 拿回明文 datakey；用它解大檔。

這樣 OpenBao 只處理小資料（幾十 byte 的 wrapped datakey），大檔加解密在應用本機完成。

16.6 Convergent Encryption（可搜尋）

正常加密：相同 plaintext 每次加密產生不同 ciphertext（IV 隨機）。Convergent：相同 plaintext + context 永遠對應相同 ciphertext。

# 建立 convergent + derived 的 key
$ bao write transit/keys/email-search \
    type=aes256-gcm96 \
    convergent_encryption=true \
    derived=true

# 加密（必須提供 context）
$ CTX=$(echo -n "users:emails" | base64)
$ bao write transit/encrypt/email-search \
    plaintext=$(echo -n "alice@example.com" | base64) \
    context="$CTX"
ciphertext  vault:v1:xxxxxFixedForSamePlaintextAndContext

# 同 plaintext + 同 context → 相同 ciphertext，可在 SQL WHERE 用來找
⚠ Convergent 風險

因為相同 plaintext 永遠相同 ciphertext，頻率分析變得可能（攻擊者拿到資料表，看哪個 ciphertext 出現得最多）。Convergent 適合「同欄位內值多樣性高」的情境（如 email、phone hash），不適合「值很集中」的（如國籍、性別）。

16.7 Sign / Verify

# 建立簽章用 key
$ bao write transit/keys/api-signing type=ed25519

# 簽
$ bao write transit/sign/api-signing \
    input=$(echo -n "important-message" | base64)
Key            Value
---            -----
key_version    1
signature      vault:v1:abc...

# 驗
$ bao write transit/verify/api-signing \
    input=$(echo -n "important-message" | base64) \
    signature="vault:v1:abc..."
Key      Value
---      -----
valid    true

16.8 BYOK：自帶金鑰

有些合規要求金鑰必須由你自己提供（例如某些雲端搬遷、HSM 出來的 key）。OpenBao Transit 支援 BYOK：

# 1. 先取得 OpenBao 的 wrapping public key（4096-bit RSA）
$ bao read -field=public_key transit/wrapping_key > wrapping.pub

# 2. 用工具 (bao transit import 內建邏輯 / 或 OpenSSL) 把你的 key
#    用 wrapping key 包起來，產生 ciphertext

# 3. 寫進 transit
$ bao transit import transit/keys/imported-key @wrapped-key.bin \
    type=aes256-gcm96 \
    allow_rotation=true

整個過程中，OpenBao 看到的 import payload 是用它自己的 RSA public key 加密過的，外人攔截也無法解。詳情見官方 Key Wrapping Guide。

16.9 Production 注意事項

  • 定期 rotate：AES-GCM 在達到 2^32 次操作前要換，OpenBao 會自動執行；但業務上的 rotation（例如 90 天一次）需要手動或排程。
  • 不要 deletion_allowed=true 留在 production。誤刪 transit key = 對應 ciphertext 全部變磚。
  • 分 key 用途：簽章用 ed25519，加密用 AES，搜尋用 convergent；不要一把 key 多用途。
  • 把 transit/encrypt 的 capability 限到最小：應用只需要 update 在 transit/encrypt/myapp，不需要 read key。
  • Datakey 適合大檔，傳輸成本低；transit/encrypt 適合小資料。

16.10 ⚙ 動手練習

  1. 建一把 AES-256 key，用 Python / Go / curl 各加密一次同一個 plaintext，比較 ciphertext。
  2. 跑一次 rotate，看舊 ciphertext 是否仍可解；用 rewrap 升級到新版。
  3. 建立 convergent key 加密兩次同一段 email，確認 ciphertext 相同。
  4. 產生 datakey，自己用 Go 寫一段 AES-GCM 加大檔，存 wrapped key 旁邊；之後解回。

Chapter 17其他引擎

OpenBao 還內建幾個用得到、但不那麼主流的 engine。本章以速覽方式介紹，遇到再回來查即可。

17.1 Cubbyhole — Token 私人空間

第二冊已經介紹過：每個 token 有自己獨立的 cubbyhole namespace，token 死掉時 cubbyhole 內容自動消失。這是 response wrapping 內部用的機制。

$ bao write cubbyhole/notes content="my private note"
$ bao read cubbyhole/notes
# 換另一個 token 看不到

17.2 Identity Engine

Identity engine 不是給應用用的「儲存 secret」，而是 OpenBao 內部 entity / group / alias 管理的 API 介面。你在第二冊已經用過：

  • identity/entity — 管理 entity
  • identity/group — 管理 group
  • identity/oidc — OIDC provider 模式（簽 identity token）

17.3 Kubernetes Engine — 動態產生 K8s SA token

這是「Kubernetes auth method」的反向：

  • Kubernetes auth：應用拿 K8s SA token，換 OpenBao token。
  • Kubernetes secret engine：應用問 OpenBao 要一個 K8s SA token，用來呼叫 K8s API。
$ bao secrets enable kubernetes
$ bao write kubernetes/config \
    kubernetes_host="https://k8s.example.com:6443"

$ bao write kubernetes/roles/my-role \
    allowed_kubernetes_namespaces="*" \
    service_account_name="default" \
    token_max_ttl="1h"

# 應用呼叫，取得短命 K8s SA token
$ bao read kubernetes/creds/my-role
Key                  Value
---                  -----
service_account_name default
service_account_token eyJhbGciOiJSUzI1NiI...

適合：CI 系統需要短期操作 K8s API、外部工具需要受控的 K8s 存取。

17.4 LDAP Engine — 動態 LDAP 帳號

類似 Database engine，但對 LDAP 操作。可以發給應用一個短期 LDAP user，到期自動刪除。設定的核心是定義 creation_ldif、deletion_ldif。

17.5 RabbitMQ Engine

動態產生 RabbitMQ user + permission。應用啟動時 read /creds/<role>，得到 RabbitMQ 用戶名與密碼，連上 broker，到期自動 revoke。

17.6 TOTP Engine

OpenBao 內建 TOTP（Google Authenticator 那種 6 位數 OTP）的產生與驗證：

$ bao secrets enable totp

# 產生一個 key（OpenBao 端持有）
$ bao write totp/keys/alice generate=true \
    issuer=MyOrg account_name=alice@example.com

# 取得當前 6 位 code
$ bao read totp/code/alice
Key     Value
---     -----
code    123456

# 驗證
$ bao write totp/code/alice code=123456

典型用途：應用想實作自己的 2FA，但不想自己處理 secret 與 time drift；交給 OpenBao。

17.7 Transform — 資料遮罩 / Format-Preserving Encryption

Note：Transform 在某些版本仍有差異性支援。Transform 提供 FPE（保持格式的加密）與 masking：例如把信用卡號 4111-1111-1111-1111 加密後仍然是 16 位數字，可寫入既有 schema。詳見官方文件對應你 OpenBao 版本的章節。

Chapter 18Plugin 系統

所有 secret engine、auth method、database driver 在 OpenBao 內部都是 plugin。多數情況你用的是 built-in plugin，但你也可以註冊外部 plugin（自己寫的或社群提供的）來擴充 OpenBao。

18.1 Built-in vs External Plugin

  • Built-in：編譯進 bao 二進位內，無需另行部署。OpenBao 大部分官方 engine 都屬於這類。
  • External：獨立的 binary，OpenBao 透過 RPC（go-plugin）跟它溝通。需要先註冊 plugin catalog。

18.2 Plugin Directory 設定

Server config 加上：

plugin_directory = "/etc/openbao/plugins"
api_addr         = "https://bao.example.com:8200"

把 plugin binary 放進這個目錄，並確保 OpenBao process 對它有讀取與執行權限。

18.3 註冊 Plugin

# 計算 plugin 的 SHA-256
$ SHA=$(sha256sum /etc/openbao/plugins/myplugin | awk '{print $1}')

# 註冊到 plugin catalog
$ bao plugin register -sha256=$SHA \
    secret myplugin

# 或註冊 auth method plugin
$ bao plugin register -sha256=$SHA \
    auth myauthplugin

SHA-256 是 OpenBao 確認 plugin 沒被竄改的方式 — 啟動 plugin 前會比對。Plugin 自報版本（透過 version interface）也會在 catalog 中顯示。

18.4 啟用外部 Plugin 為 mount

$ bao secrets enable -path=mydata myplugin

18.5 自製 Plugin 概覽

OpenBao 提供 SDK 讓你用 Go 寫自己的 secret / auth / database plugin。基本流程：

  1. go get github.com/openbao/openbao/sdk/v2
  2. 實作對應的 interface（如 logical.Backend、dbplugin/v5.Database）。
  3. 用 OpenBao SDK 提供的 plugin.Serve 包裝 main。
  4. 編譯成 binary、放進 plugin directory、register。

18.6 Plugin Multiplexing

同一個 plugin process 可服務多個 mount（例如多個 Database connection 共用一個 plugin process），「節省記憶體與啟動開銷」。需要 plugin 編譯時呼叫 ServeMultiplex。

18.7 何時該寫自製 Plugin

  • 有內部專屬的資料來源（自家 DB、不對外的服務）需要動態憑證。
  • 需要把 OpenBao 串接非標準的 auth flow（例如自家 SSO 協議）。
  • 需要實作客製業務邏輯的加密 / 簽章流程，但仍想沿用 OpenBao 的 audit、policy、token 體系。

多數情況下 built-in 已經夠用，自製 plugin 是進階場景。Plugin 開發比 application 開發麻煩，安全責任也更重。

✓ 章末重點
  • 所有 engine / auth method 都是 plugin，built-in vs external 只是部署差異。
  • External plugin 要在 plugin directory + register + SHA-256 校驗。
  • SDK 提供 Go 寫 plugin 的框架，但是進階場景。
  • 大多數使用者一輩子不需要寫自己的 plugin。
