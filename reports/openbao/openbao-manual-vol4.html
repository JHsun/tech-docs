Chapter 19配置檔（Configuration）完整參考

Production 模式的 OpenBao 一定要有一份設定檔。config.hcl 是 OpenBao 的「名片」 — 它告訴 server 怎麼監聽、怎麼存資料、怎麼 seal、發 metric 到哪、留多少 log。本章把所有 production 必設、選設、看了會踩雷的欄位走過一遍。

19.1 設定檔結構總覽

一份完整的 production config.hcl 由幾個 stanza 組成：

# 必填
storage "raft" { ... }      # 資料存哪
listener "tcp" { ... }      # 監聽哪
api_addr     = "..."        # 對 client 廣告的位址
cluster_addr = "..."        # 對其他節點廣告的位址

# 強烈建議
seal "awskms" { ... }       # auto-unseal
ui = true                   # 啟用 Web UI

# 選填
telemetry { ... }           # metrics
log_level  = "info"
log_format = "json"
log_file   = "/var/log/openbao/openbao.log"
log_rotate_max_files = 7
plugin_directory = "/etc/openbao/plugins"

19.2 Listener 區塊

① 最簡 production listener

listener "tcp" {
  address     = "0.0.0.0:8200"
  cluster_address = "0.0.0.0:8201"

  tls_cert_file      = "/etc/openbao/tls/cert.pem"
  tls_key_file       = "/etc/openbao/tls/key.pem"
  tls_min_version    = "tls12"

  # 給 mTLS 內部 client（選用）
  tls_client_ca_file = "/etc/openbao/tls/internal-ca.pem"
}

② 多 listener：API + 內網 metrics 各自一個

# Public TLS listener
listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_cert_file = "/etc/openbao/tls/cert.pem"
  tls_key_file  = "/etc/openbao/tls/key.pem"
}

# 純 metrics listener（內網、無 TLS、unauthenticated）
listener "tcp" {
  address     = "127.0.0.1:8220"
  tls_disable = true

  telemetry {
    unauthenticated_metrics_access = true
  }
}

第二個 listener 只給 Prometheus scraping 用，「unauthenticated_metrics_access = true 讓 /v1/sys/metrics 不需要 token 即可存取」。務必綁 127.0.0.1 或內網 IP，否則 metric 端點變成資訊外洩。

③ Listener 重要參數速覽

參數用途
address監聽位址，預設 127.0.0.1:8200
cluster_address給 cluster 節點互傳的位址
tls_cert_file / tls_key_fileTLS cert/key 路徑（PEM）
tls_min_version建議 tls12 起，新環境設 tls13
tls_disable禁用 TLS（僅限本機 dev / unprivileged listener）
tls_client_ca_file啟用 mTLS：要求 client 出示 CA 簽過的 cert
x_forwarded_for_*L7 proxy 場景下保留真實來源 IP
http_idle_timeoutHTTP idle timeout

storage "raft" {
  path    = "/var/lib/openbao/data"
  node_id = "node1"

  # 用 cloud auto-join 自動發現其他節點
  retry_join {
    auto_join        = "provider=aws region=us-west-1 tag_key=Role tag_value=openbao"
    auto_join_scheme = "https"
    auto_join_port   = 8200
  }

  # 進階儲存設定
  performance_multiplier = 1
}

19.4 Seal 區塊（節錄，詳第二冊第 6 章）

seal "awskms" {
  region     = "us-west-1"
  kms_key_id = "alias/openbao-unseal"
}

這只是其中一種，PKCS#11、Transit、static、Azure、GCP、OCI、Aliyun 各有對應寫法。第二冊第 6 章詳述。

19.5 Telemetry 區塊（詳第 25 章）

telemetry {
  prometheus_retention_time = "24h"
  disable_hostname          = true
}

有了這個 + listener 上的 unauthenticated_metrics_access，Prometheus 就能 scrape /v1/sys/metrics?format=prometheus。

19.6 全域必設參數

① api_addr 與 cluster_addr

Cluster 中的節點需要互相廣告自己的可達位址。這是多節點部署時最常踩雷的設定：

  • api_addr：完整 URL，告訴其他節點「client 應該連到我這裡」。例：https://bao-1.internal.example.com:8200。
  • cluster_addr：完整 URL，告訴其他節點「節點間 RPC 應該連到我這裡」。例：https://bao-1.internal.example.com:8201。

如果 節點是動態 IP（Pod 重排、ASG 滾動），用 go-sockaddr 樣板：

api_addr     = "https://{{ GetPrivateIP }}:8200"
cluster_addr = "https://{{ GetPrivateIP }}:8201"

K8s 場景常用環境變數：

api_addr     = "https://${POD_IP}:8200"
cluster_addr = "https://${POD_IP}:8201"

② disable_mlock

Memory locking（mlock）防止記憶體頁被 swap 到磁碟（避免 secret 外洩）。但在容器環境需要 IPC_LOCK capability，許多 K8s PSS（Pod Security Standards）的 "restricted" 模式禁用此 capability。

解法：

  • **Container 環境**：設 disable_mlock = true，但必須在容器層級確保不會 swap（K8s node 設 --fail-swap-on=true，這通常已是預設）。
  • **Bare metal / VM**：保持 disable_mlock = false（預設），給 process CAP_IPC_LOCK。

③ ui

ui = true

啟用後，Web UI 在所有 listener 的 /ui/ 路徑可達。

④ plugin_directory

External plugin 的存放位置（第三冊第 18 章）。

19.7 Log 設定

log_level            = "info"           # trace, debug, info, warn, error
log_format           = "json"            # 推薦 json 給 SIEM 解析
log_file             = "/var/log/openbao/openbao.log"
log_rotate_duration  = "24h"             # 每天輪替
log_rotate_max_files = 7                 # 留 7 天

json 格式對 SIEM、Loki、ELK 等友好，強烈建議 production 用 json。

19.8 Service Registration（K8s 自動服務註冊）

K8s 環境下，OpenBao 可以自動把自己的 active/standby 狀態寫進 Pod 的 label，讓 K8s Service 能用 selector 把流量路到正確 Pod：

service_registration "kubernetes" {}

啟用後 Pod 上會出現：

labels:
  vault-active: "true"     # 只有 active node 是 true
  vault-sealed: "false"
  vault-perf-standby: "false"
  vault-initialized: "true"

這讓你能定義一個 openbao-active Service，selector vault-active=true，流量永遠打到 active node。

19.10 設定檔的部署模式

OpenBao 支援單一檔或整個目錄。指定目錄時，所有 .hcl 與 .json 檔會按字母順序載入合併：

$ bao server -config=/etc/openbao/conf.d/

典型分檔：

  • 00-common.hcl — ui、log、api_addr 等共用
  • 10-listener.hcl — listener stanza
  • 20-storage.hcl — storage stanza
  • 30-seal.hcl — seal stanza（敏感，可能由 secret 注入）
  • 40-telemetry.hcl — telemetry

讓 GitOps 部署能單獨更新某個面向。

19.11 用環境變數覆蓋設定值

OpenBao 支援用環境變數覆蓋特定 config 項：

  • VAULT_API_ADDR → api_addr
  • VAULT_CLUSTER_ADDR → cluster_addr
  • VAULT_UI → ui
  • VAULT_LOG_LEVEL → log_level

並支援在 config 內用 ${VAR} 取環境變數值（適合容器啟動時注入動態 IP）。

19.12 ⚙ 動手練習

  1. 寫一份 production-grade config.hcl，啟動 server 後 bao status 確認啟動成功。
  2. 把 config 拆成 conf.d/ 目錄結構，重啟 server 確認等價。
  3. 故意把 tls_cert_file 路徑寫錯，看 server 啟動的錯誤訊息。
  4. 啟動兩個 listener — 一個對外 TLS、一個對內 metrics — 用 curl 測 /v1/sys/metrics?format=prometheus。

Chapter 20儲存後端（Storage Backend）

Storage backend 決定 OpenBao 把加密過的資料放在哪。選錯不會立刻爆，但會在 cluster 規模成長、需要 HA、需要備份時還回來咬你。本章直接給結論再展開細節。

20.1 直接給結論：選 Integrated Storage (Raft)

對絕大多數情況，答案就是 Raft。理由：

  • OpenBao 官方推薦，第一方支援、文件齊全。
  • 內建 HA：3-5 節點直接 cluster，不需要外部 ZK / Consul / DB。
  • 內建 snapshot：bao operator raft snapshot save 一行備份。
  • 支援 production 級功能：「paginated lists、transactional storage」。
  • Cloud auto-join：節點動態 IP 不是問題。

什麼時候不選 Raft？基本上只有兩種：(1) 你的環境已有大型 PostgreSQL HA 群，且維運單位希望統一管理；(2) 你只跑單機（連 HA 都不需要），在這狀況下 File 也夠。其他狀況都選 Raft。

20.3 Integrated Storage (Raft) 詳解

① Raft 的工作原理

Raft 是一種 consensus algorithm：cluster 中的節點選出一個 leader，由 leader 接收所有寫入並複製到其他 followers。寫入需要超過半數節點確認才算成功（quorum）。

典型部署是奇數節點：

  • 3 節點：可容忍 1 節點掛掉
  • 5 節點：可容忍 2 節點掛掉
  • 7 節點：可容忍 3 節點掛掉，但延遲增加

「OpenBao 官方建議 production 跑 5 個節點」。為什麼不是 3？因為 5 節點允許「升級時 1 節點下線 + 1 節點故障」仍維持 quorum，3 節點則做不到。

② Raft 設定參數

storage "raft" {
  path    = "/var/lib/openbao/data"
  node_id = "bao-1"   # 必須在 cluster 內唯一

  # 加入既有 cluster 的方式（多選一）
  retry_join {
    leader_api_addr = "https://bao-2.internal.example.com:8200"
  }
  retry_join {
    leader_api_addr = "https://bao-3.internal.example.com:8200"
  }
  # 或：cloud auto-join
  # retry_join {
  #   auto_join = "provider=aws region=us-west-1 tag_key=Role tag_value=openbao"
  #   auto_join_scheme = "https"
  #   auto_join_port = 8200
  # }

  # 進階
  performance_multiplier = 1   # 1=最高效能, 5=最節能（測試用）
  max_entry_size         = 1048576    # 單一 raft entry 上限 (1MB)
  max_transaction_size   = 8388608    # 單筆 tx 上限 (8MB)

  autopilot_reconcile_interval = "10s"
  autopilot_update_interval    = "2s"
}

③ Raft 資料目錄結構

$ ls /var/lib/openbao/data/
raft/
  raft.db           # bbolt FSM database
  snapshots/        # 自動 snapshots
  raft-wal/         # WAL（write-ahead log）

整個目錄需要備份，但不要直接複製（會破壞一致性）。用 bao operator raft snapshot save（第 26 章）。

④ 加入新節點的流程

  1. 新節點啟動，但不要 init（cluster 已 init 過）。
  2. 新節點配置中的 storage "raft" 必須有相同的 seal 設定（auto-unseal 才能解開接到的資料）。
  3. 新節點呼叫 bao operator raft join 加入既有 leader。
  4. 如果是 Shamir seal，加入後才 unseal；如果是 auto-unseal，加入即可自動解。
  5. Autopilot 自動把它先加為 non-voter，等同步穩定（server_stabilization_time，預設 10s）後升級為 voter。
$ bao operator raft join https://bao-1.internal.example.com:8200

---       -----
joined    true

# 看 cluster 狀態（需要 token）
$ bao operator raft list-peers

----     -------                                -----       -----
bao-1    bao-1.internal.example.com:8201        leader      true
bao-2    bao-2.internal.example.com:8201        follower    true
bao-3    bao-3.internal.example.com:8201        follower    true

20.4 Raft Autopilot

Autopilot 是 OpenBao 內建的 cluster 自動化系統，預設啟用，但 dead server cleanup 預設關閉。它做三件事：

  1. Server stabilization：新節點先當 non-voter，穩定後才升 voter。防止剛加入的節點立刻投票造成 quorum 抖動。
  2. Dead server cleanup：自動把死掉的節點從 peer set 移除（需手動啟用）。
  3. State API：把 cluster 健康狀態用一支 API 回報。

查 Autopilot 狀態

$ bao operator raft autopilot state
Healthy:                      true
Failure Tolerance:            1
Leader:                       bao-1
Voters:
   bao-1
   bao-2
   bao-3
Servers:
   bao-1
      Name:            bao-1
      Address:         bao-1.internal.example.com:8201
      Status:          leader
      Node Status:     alive
      Healthy:         true
      Last Contact:    0s
      Last Term:       3
      Last Index:      459

Failure Tolerance: 1 表示這個 cluster 還能容忍 1 個節點故障。監控這個值非常重要，掉到 0 是強烈警訊。

啟用 dead server cleanup

$ bao operator raft autopilot set-config \
    cleanup-dead-servers=true \
    dead-server-last-contact-threshold=24h \
    min-quorum=3

20.5 PostgreSQL Backend

當你的組織已有強大的 PG 維運（HA、point-in-time recovery、跨 region），且不想再多一套 Raft cluster 維運，PG backend 是合理選擇。

storage "postgresql" {
  connection_url = "postgresql://openbao:pwd@pg-prod:5432/openbao?sslmode=require"
  table          = "openbao_kv_store"
  ha_enabled     = "true"
  ha_table       = "openbao_ha_locks"
  max_idle_connections = 10
}

注意：

  • 「不再支援 PostgreSQL 9.5 以前」（v2.4 起）。建議 PG 14+。
  • HA 模式靠 PG 的 advisory lock 實現，不需要外部 lock service。
  • OpenBao 啟動時若資料表不存在會自動建立。
  • 跨 region 部署時，PG 端的同步性決定 OpenBao 寫入延遲。

20.6 File Backend

storage "file" {
  path = "/var/lib/openbao/file"
}

適合：本機學習、單機小工具、開發環境。不支援 HA，所以 production 上規模稍大就頂不住。

20.7 Storage 大小規劃

實際儲存大小受幾個因素影響：

  • KV v2 版本數：max_versions × secret 數量 × 平均大小。
  • Lease 數量：每個 dynamic secret 都產生一筆 lease entry。
  • Token 數量：service token 都寫入 storage。
  • Audit log：不在 storage 裡，是另開檔案 / syslog。

典型小組織（<5000 secrets，<50 應用）：Raft 資料目錄 < 1GB。中型組織 < 10GB。如果你看到目錄超過 50GB，通常是 lease 沒清乾淨或 audit 寫錯地方。

20.8 ⚙ 動手練習

  1. 用 Docker compose 跑 3 個 OpenBao 容器，組成 Raft cluster，觀察 leader election。
  2. 停掉 leader 容器，看 autopilot 自動選新 leader 的過程。
  3. 跑 bao operator raft autopilot state，理解 failure tolerance。
  4. 嘗試把第 4 個節點 join 進去，觀察先 non-voter 後 voter 的過程。

Chapter 21高可用性（HA）架構

「節點掛了 OpenBao 還能服務嗎？」這是任何要把 OpenBao 上 production 的人第一個被問的問題。本章把 HA 完整講清楚 — 從 active/standby 模型到跨 AZ / 跨 region 設計。

21.1 OpenBao 的 HA 模型：Active / Standby

① 概念

OpenBao 的 HA 模式叫 Active / Standby：

  • 一個 active node 接收所有 read / write 請求。
  • 其他 standby nodes 不主動處理請求，但會 forward 收到的請求到 active，或把 client redirect 到 active（取決於 listener 的 redirect 設定）。
  • Active 掛掉時，剩下節點重新選舉，產生新 active。

這跟某些「真主主」系統（多節點都能寫）不同。OpenBao 的設計理由：寫入順序必須嚴格，由單一 active 序列化最簡單可靠。

21.2 LB 與 health check 設計

LB 應該只把流量打到 active node。怎麼判斷誰是 active？OpenBao 提供 /v1/sys/health 端點，回傳的 HTTP status code 帶豐富語意：

Status意義LB 該怎麼處理
200已 init、unsealed、active✓ 流量過來
429已 init、unsealed、standby✗ 不要打過來
472Disaster recovery 模式✗
473Performance standby✗（除非設定允許）
501未 init✗
503Sealed✗

大部分 LB 看 200 就放行、其他都當 unhealthy，這正是我們要的行為。

AWS ALB / NLB 範例 health check

HealthCheckPath: /v1/sys/health
HealthCheckProtocol: HTTPS
HealthCheckIntervalSeconds: 5
HealthyThresholdCount: 2
UnhealthyThresholdCount: 2
Matcher:
  HttpCode: "200"

K8s Service：用 service_registration 自動標籤

第 19 章提過，OpenBao 設定 service_registration "kubernetes" {} 後，active pod 會被標 vault-active=true。然後：

apiVersion: v1
kind: Service
metadata:
  name: openbao-active
spec:
  selector:
    app.kubernetes.io/name: openbao
    vault-active: "true"
  ports:
  - port: 8200
    targetPort: 8200

K8s Service 會自動把流量導到 active pod，無需自寫 health check。

節點數Quorum容錯使用情境
110Dev / 學習

不要用偶數節點。4 節點和 3 節點容錯都是 1，但 4 節點 quorum 變 3，反而更脆弱。

21.4 Performance Standby

OpenBao 支援 Performance Standby — standby 節點可處理 read 請求（透過 forwarding 到 active 寫，但 read 自己處理），減輕 active 負擔。需要在 listener 設定允許 PSS 流量。

listener "tcp" {
  address = "0.0.0.0:8200"
  ...
}

# 取消對 PSS 的拒絕
disable_performance_standby = false   # 預設就是 false，即啟用 PSS

請注意：PSS 處理過的 read 可能有少量 staleness（落後 active 幾百毫秒到秒級），對需要 strong consistency 的場景要謹慎，可以在請求加 X-Vault-Index header 強制讀新資料。

21.5 跨 AZ / 跨 region 部署

① 跨 AZ（同 region 不同可用區）— 強烈建議

5 節點分佈在 3 個 AZ，例如 2-2-1 或 3-1-1。Raft latency 在同 region 不同 AZ 通常 1-3ms，幾乎無感。整個 AZ 掉電仍維持 quorum。

② 跨 region — 慎重

跨 region latency 通常 50ms+，每次寫入都要等 quorum 確認，等於每筆寫變慢數十毫秒。處理方法：

  • 不要把 voter 跨 region 散。把多數 voter 放在主 region，遠 region 放 non-voter（備援，不參與 quorum）。
  • 真正需要跨 region active-active 是 enterprise replication 等級的需求，OpenBao 目前無對等功能（DR replication 是 HCV Enterprise 的功能）。
  • 實際做法：跨 region 用定期 snapshot 到另一 region S3，災難時用 snapshot 重建（RTO 數十分鐘 / RPO 數分鐘）。

21.6 Standby 節點轉成 Active 的時機

下列情況會觸發 leader election：

  • Active node crash / 失聯。
  • Active node 主動 step down：bao operator step-down。
  • Active node 升級時主動 step down。

選舉時間通常 5-15 秒（取決於 Raft 設定）。期間所有 client 看到 503 / 5xx，需要應用層 retry。

  1. 用 Docker compose 跑 5-node Raft cluster，配上 nginx 當 LB。
  2. 觀察 bao operator raft list-peers 與 autopilot state。
  3. 強制 stop active node 容器，看新 leader 多久產生、應用看到的 503 持續多久。
  4. 跑 bao operator step-down 主動下台，比較與 crash 的差別。
✓ 章末重點
  • OpenBao 是 active/standby 模型，所有寫入由單一 active 處理。
  • Production 推薦 5 節點 Raft cluster，跨 3 AZ 分佈。
  • LB 用 /v1/sys/health 判斷 active；K8s 用 service_registration + selector 自動處理。
  • Autopilot 監控節點健康並自動穩定，failure tolerance 是必看 metric。
  • 跨 region active-active 不是 OpenBao 強項，用 snapshot DR 取代。

22.6 K8s 部署常踩雷

  • 忘了 PodAntiAffinity：5 個 pod 全部跑在同一 node，等於只有 1 個 pod。
  • storageClassName 用了 hostPath：node 死掉資料就消失。生產用 cloud disk / Ceph / etc。
  • Resource limit 太低：OpenBao 在 lease 大量產生時會 OOM。production 至少 1Gi。
  • readinessProbe path 設錯：寫成 /v1/sys/health（不帶 standbyok），standby pod 永遠 NotReady，K8s 一直重啟。
  • UpdateStrategy 是 RollingUpdate 沒處理 unseal：如果用 Shamir，所有 pod 同時重啟會集體 sealed，需手動 unseal 每個。建議 OnDelete + 自己控制節奏，或一定要用 auto-unseal。
  • Ingress backend protocol 沒設 HTTPS：Nginx 預設用 HTTP 跟 backend 講話，OpenBao 只接 HTTPS，全部 502。

Chapter 23OpenBao Agent 與 Proxy

應用直接呼叫 OpenBao 看似簡單，但會遇到三個重複出現的問題：(1) 怎麼 login？(2) Token 怎麼 renew？(3) 如何把 secret 寫成檔案讓 legacy 應用讀？OpenBao Agent 就是解決這三件事的中介工具。

23.1 Agent vs Proxy：差別在哪

OpenBao Agent

Sidecar / 本機 daemon，幫應用做事：

  • auto-auth（自動 login + renew）
  • 把 secret 寫成檔案（template）
  • 啟動子程序時注入環境變數（exec）
  • API proxy（讓應用透過 Agent 打 OpenBao）
  • Caching

OpenBao Proxy

純粹的 API forwarder：

  • auto-auth + listener
  • 把應用對 Proxy 的請求 forward 給 OpenBao
  • 可選快取
  • 不做 template / exec

適合應用本身有 OpenBao client lib，只想免去 login 邏輯的場景。

本章重點放在 Agent，因為它是大多數場景的選擇。Proxy 是 Agent 功能的子集。

23.2 Agent 三大功能

① Auto-Auth：自動 login + renew

Agent 啟動時用設定的 method 自動 login（K8s SA、AppRole、Cert⋯），把得到的 token 寫到 sink（檔案、env），並背景 renew。Token 過期時自動重新 login。

② Template：把 secret 寫成檔案

用 Consul Template 語法，把 secret 渲染成設定檔給應用讀。應用完全不用改 code。

③ Exec：注入環境變數啟動子程序

Agent 拿到 secret 後，把它們轉成 env 啟動子程序。子程序看到的 env 已經包含 secret，更省事。

23.3 完整範例：K8s Sidecar Agent + Template

① OpenBao 端準備（重複自第 13 章）

$ bao auth enable kubernetes
$ bao write auth/kubernetes/config kubernetes_host="https://kubernetes.default.svc"
$ bao policy write app-ro - <<'EOF'
path "secret/data/myapp/*" { capabilities = ["read"] }
path "database/creds/myapp-ro" { capabilities = ["read"] }
EOF
$ bao write auth/kubernetes/role/myapp \
    bound_service_account_names=myapp \
    bound_service_account_namespaces=production \
    policies=app-ro token_ttl=1h max_ttl=24h

② Agent 設定

# /etc/openbao/agent.hcl

pid_file = "/tmp/agent.pid"

vault {
  address = "https://openbao.bao.svc:8200"
  retry { num_retries = 5 }
}

auto_auth {
  method "kubernetes" {
    config = {
      role       = "myapp"
      token_path = "/var/run/secrets/kubernetes.io/serviceaccount/token"
    }
  }

  sink "file" {
    config = {
      path = "/etc/openbao/agent-token"
    }
  }
}

# Template 1: 把 KV secret 寫成 application.properties
template {
  contents     = <<EOF
db.host={{ with secret "secret/data/myapp/db" }}{{ .Data.data.host }}{{ end }}
db.port=5432
db.username={{ with secret "database/creds/myapp-ro" }}{{ .Data.username }}{{ end }}
db.password={{ with secret "database/creds/myapp-ro" }}{{ .Data.password }}{{ end }}
EOF
  destination = "/etc/myapp/application.properties"
  perms       = "0640"
  command     = "kill -HUP $(pidof myapp) || true"
}

# Template 2: 渲染 PKI cert
template {
  contents     = <<EOF
{{ with pkiCert "pki-int/issue/internal-svc" "common_name=myapp.svc" "ttl=24h" }}
{{ .Cert }}{{ .Key }}
{{ end }}
EOF
  destination = "/etc/myapp/tls.pem"
  perms       = "0600"
}

cache {}   # 啟用 caching

listener "tcp" {
  address     = "127.0.0.1:8200"
  tls_disable = true
}

api_proxy {
  use_auto_auth_token = true
}

③ K8s Pod 配置（Agent + App 在同一 Pod）

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  template:
    spec:
      serviceAccountName: myapp
      containers:
      # OpenBao Agent sidecar
      - name: openbao-agent
        image: docker.io/openbao/openbao:2.5.3
        args:
        - agent
        - -config=/etc/openbao/agent.hcl
        volumeMounts:
        - name: agent-config
          mountPath: /etc/openbao
        - name: shared-secrets
          mountPath: /etc/myapp
      # 應用本體 — 完全不知道 OpenBao 存在
      - name: app
        image: myorg/myapp:v1
        volumeMounts:
        - name: shared-secrets
          mountPath: /etc/myapp
          readOnly: true
      volumes:
      - name: agent-config
        configMap:
          name: openbao-agent-config
      - name: shared-secrets
        emptyDir:
          medium: Memory   # tmpfs，secret 不落盤

應用容器只要讀 /etc/myapp/application.properties，無需任何 OpenBao SDK 整合。Agent 會：

  • 啟動時 K8s SA → OpenBao token；
  • 背景 renew token；
  • 定期 re-render template（DB 動態 cred 過期就重簽）；
  • Cert 接近過期時自動 re-issue；
  • 觸發 command 通知應用重載設定（HUP signal）。

23.4 Vault Agent Injector（K8s 自動 sidecar 注入）

不想每個 Deployment 都手動加 sidecar？Injector 是一個 mutating admission webhook，看 Pod 上的 annotation 自動注入 sidecar：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "myapp"
        vault.hashicorp.com/agent-inject-secret-config: "secret/data/myapp/db"
        vault.hashicorp.com/agent-inject-template-config: |
          {{- with secret "secret/data/myapp/db" -}}
          db_url={{ .Data.data.url }}
          db_user={{ .Data.data.user }}
          db_pwd={{ .Data.data.password }}
          {{- end }}
    spec:
      serviceAccountName: myapp
      containers:
      - name: app
        image: myorg/myapp:v1

Injector 看到 annotation，自動把 init container（一次性取 secret）+ sidecar（持續 renew）插進 Pod。應用容器看到 /vault/secrets/config 已經有 rendered 內容。

Injector 是 K8s 上「對應用零侵入」的最佳實踐。

23.5 OpenBao Proxy 範例（純 API forward）

# /etc/openbao/proxy.hcl

vault {
  address = "https://openbao.bao.svc:8200"
}

auto_auth {
  method "approle" {
    config = {
      role_id_file_path   = "/etc/openbao/role-id"
      secret_id_file_path = "/etc/openbao/secret-id"
      remove_secret_id_file_after_reading = false
    }
  }
  sink "file" {
    config = { path = "/var/run/openbao-token" }
  }
}

api_proxy {
  use_auto_auth_token = "force"
}

cache {}

listener "tcp" {
  address     = "127.0.0.1:8200"
  tls_disable = true
}

啟動：bao proxy -config=/etc/openbao/proxy.hcl。應用直接打 http://127.0.0.1:8200 就好，不用帶 token — Proxy 會自動加。

23.6 Caching 機制

Agent / Proxy 的 cache 機制不是「KV 快取」 — 它是「lease + token」的快取。當應用透過 Agent 取得 dynamic secret，Agent 會：

  • 幫該 secret 維護 lease，到期前自動 renew；
  • 應用如果在 lease 期內再次 read 同一 endpoint，直接回 cached 結果；
  • 應用主動 revoke / drop 時，Agent 對應更新。

這對 「DB cred 在多 worker 共用」 場景特別有用：100 個 worker 透過 Agent 取 DB cred，Agent 內部其實只跟 OpenBao 拿一次。

  2. 加上 template，把 KV secret 寫進設定檔；改 KV 內容，看 Agent 多久 detect 並 re-render。
  3. K8s 上裝 injector，給一個 Deployment 加 annotation，無侵入注入 secret。
  4. 跑一次 Proxy 模式，用 curl http://127.0.0.1:8200/v1/secret/data/foo（不帶 token）試試。

Chapter 24Audit Devices

「每個對 OpenBao 的請求都被完整記錄」是合規與事後鑑識的基礎。Audit device 是 OpenBao 把每個 request/response 寫到外部的機制 — 它預設關閉，但 production 上一定要開。

24.1 為什麼一定要開 audit

  • 合規：SOC2、ISO 27001、PCI-DSS 都要求對機敏存取的 audit。
  • 鑑識：發生事故時，誰在何時讀了什麼，唯一可信的紀錄。
  • 排錯：應用回 403？Audit log 看 deny 的精確 path 與 policy。
  • 用量分析：哪些 secret 被頻繁讀、哪些從來沒人讀（candidate for cleanup）。

24.2 Audit device 種類

類型用途備註
file 寫到本機檔案 最常用；要搭配 logrotate 與外送（Filebeat / Fluentd / Vector）
syslog 寫到本機 syslog 自動跟系統 log 一起轉送；只支援 Unix；大訊息 UDP 會截斷
socket 寫到 TCP/UDP/Unix socket 適合直送 SIEM；socket 中斷會 block 請求！

24.3 啟用 file audit

# 預設 file device，路徑必須 OpenBao process 有寫權限
$ bao audit enable file file_path=/var/log/openbao/audit.log

# 確認啟用
$ bao audit list
Path     Type    Description
----     ----    -----------
file/    file    n/a

HMAC 機敏值處理

Audit log 預設會把 所有 string 用 HMAC-SHA256 雜湊，避免明文 secret 落入 log。但這也讓 log 變得難讀（每個值都是雜湊）。可以用 /sys/audit-hash 反查特定值的雜湊：

# 想知道 'alice' 在 audit log 中對應什麼 hash
$ bao write sys/audit-hash/file/ input=alice
hash    hmac-sha256:5d3...

對特定欄位停用 HMAC

有些欄位不是機敏的（例如 PKI 的 common_name），保留明文反而對 audit 有幫助：

$ bao secrets tune \
    -audit-non-hmac-request-keys=common_name,alt_names \
    pki-int/

# Auth 的 metadata 也類似
$ bao auth tune \
    -audit-non-hmac-request-keys=role,name \
    auth/userpass/

24.4 Audit log 格式

每行是一個 JSON object，type 為 request 或 response。範例（簡化）：

{
  "type": "request",
  "auth": {
    "client_token": "hmac-sha256:abc...",
    "accessor":     "hmac-sha256:def...",
    "display_name": "userpass-alice",
    "policies":     ["default", "app-ro"],
    "metadata":     {"username": "alice"}
  },
  "request": {
    "id":         "ed5e1...",
    "operation":  "read",
    "path":       "secret/data/myapp/db",
    "remote_address": "10.0.1.42",
    "remote_port":    52341,
    "client_id":  "..."
  },
  "time": "2026-05-05T08:30:00Z"
}
{
  "type": "response",
  "request": { ... 同上 ... },
  "response": {
    "data": { "data": "hmac-sha256:..." }
  },
  "time": "2026-05-05T08:30:00.012Z"
}

每個 request 都有 request.id，response 也帶同樣的 ID — 用這個關聯 request 與 response。

24.5 Syslog Audit

$ bao audit enable syslog \
    facility=AUTH \
    tag=openbao
⚠ Syslog 大訊息陷阱

官方明確警告：「audit 訊息可能比單一 UDP 封包大。如果可能，syslog daemon 配 TCP listener；否則改用 file backend，讓 syslog 從 file 讀」。實務上：除非你的 syslog 已用 TCP（如 rsyslog）且 message size 設足，否則直接 syslog audit 並非好選擇。

24.6 Multiple Audit Devices — 高可用

OpenBao 對 audit 有特殊處理：「如果 OpenBao 無法 audit 一個 request 或 response，原 request 會失敗」。也就是說，單一 audit device 故障 = 整個 OpenBao 無法回應請求。

解法：啟用多個 audit device。OpenBao 對成功的判斷是「至少一個 device 寫入成功」。

# 同時啟用 file + syslog
$ bao audit enable -path=file_local file file_path=/var/log/openbao/audit.log
$ bao audit enable -path=syslog_remote syslog facility=AUTH tag=openbao

如此即使 disk 滿、syslog 掛了任一個，OpenBao 仍能服務。

24.7 接到 SIEM

把 audit log 送進 SIEM 的常見模式：

① Filebeat / Fluentd 讀 file

# Filebeat config
filebeat.inputs:
- type: filestream
  paths:
    - /var/log/openbao/audit.log
  parsers:
    - ndjson:
        target: ""
output.elasticsearch:
  hosts: ["elastic:9200"]

② socket audit 直送

$ bao audit enable socket \
    address=siem.internal:5514 \
    socket_type=tcp

但 socket device 有風險：socket 中斷時會 block OpenBao。非必要不要用，file + 外送是更穩的選擇。

24.8 Audit log rotation

OpenBao 不會自己 rotate audit file。必須在外部處理：

logrotate 範例（Linux）

# /etc/logrotate.d/openbao
/var/log/openbao/audit.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    sharedscripts
    postrotate
        kill -HUP $(pidof bao) 2>/dev/null || true
    endscript
}

關鍵：postrotate 必須 SIGHUP OpenBao，否則 OpenBao 會繼續寫到舊的 inode，新檔案永遠空。

24.9 Disable Audit Device

$ bao audit disable file/

注意 disable 是立刻生效。如果你只啟用了一個 device，disable 後下一個請求會失敗（因為沒有 audit 可寫）。永遠保持至少一個 device 啟用。

24.10 ⚙ 動手練習

  1. 啟用 file audit，做幾個操作（read, write, delete），看 log 內容。
  2. 用 sys/audit-hash 反查某個 string 的 hash。
  3. 把 PKI mount 設成 audit-non-hmac-request-keys=common_name，觀察 audit log 變化。
  4. 同時啟用兩個 audit device，停掉其中一個（mv log 檔讓它 inode 失效），看 OpenBao 是否仍能服務。
✓ 章末重點
  • Production 一定要開 audit，且同時開兩個避免 single point of failure。
  • 所有 string 預設 HMAC；可對特定欄位 opt-out。
  • File audit 記得設 logrotate + postrotate SIGHUP。
  • Socket audit 雖直送 SIEM 但有 block 風險；file + Filebeat 較穩。

Chapter 26備份、還原與災難復原

「我有 3 個 Raft 節點，一定不會掉資料」是錯覺。Raft 保護你免於節點故障，不保護你免於誤操作（policy 寫爛、把 root mount 刪了、人為手抖）。也不保護你免於整個基礎設施毀滅（整個 K8s cluster 沒了）。本章談這些災難場景與恢復方法。

26.1 備份策略：定期 snapshot + 異地保存

OpenBao Raft 的備份方式只有一個：snapshot。

# 在 active node 上執行
$ bao operator raft snapshot save backup-2026-05-05.snap

# 用 curl
$ curl -H "X-Vault-Token: $TOK" \
    --output backup.snap \
    $BAO_ADDR/v1/sys/storage/raft/snapshot

Snapshot 是完整 cluster 狀態的快照，可以還原成任何時間點的 cluster。注意：

  • Snapshot 仍然是加密的。沒有對應的 root key（auto-unseal 用的 KMS / unseal keys），snapshot 沒用。
  • Snapshot 不包含 root token（root token 不寫 storage）。要重建 root token 用 generate-root + recovery keys。

26.2 自動排程 snapshot

① 簡易：cron

# /etc/cron.d/openbao-snapshot
0 */4 * * * openbao /usr/local/bin/openbao-snapshot.sh

# /usr/local/bin/openbao-snapshot.sh
#!/bin/bash
set -e
DATE=$(date +%Y%m%d-%H%M)
BAO_TOKEN="$(cat /etc/openbao/snapshot-token)" \
BAO_ADDR=https://localhost:8200 \
  bao operator raft snapshot save \
    /var/backups/openbao/snap-$DATE.bao

# 上傳到 S3 (異地保存)
aws s3 cp /var/backups/openbao/snap-$DATE.bao \
    s3://my-org-backups/openbao/ \
    --sse aws:kms --sse-kms-key-id alias/backup-key

# 保留 30 天
find /var/backups/openbao -name "snap-*.bao" -mtime +30 -delete

② Snapshot 用的 token policy

Snapshot 是 sensitive 操作（包含整個 cluster 資料），對應 token 必須有：

path "sys/storage/raft/snapshot" {
  capabilities = ["read", "sudo"]
}

建議建立一個 periodic token 專門給 snapshot job 用，不要用 root token。

26.3 還原：完整 cluster 重建

① 場景：整個 cluster 沒了，要從 snapshot 還原

  1. 準備一個全新的 OpenBao cluster（同 seal 設定！否則無法解 snapshot 內的資料）。
  2. 啟動 single node（暫不加入其他節點）。
  3. 執行 init（任何 init 即可，會被 snapshot 覆蓋）。
  4. 還原 snapshot：bao operator raft snapshot restore snap.bao。
  5. 還原後，這個節點就是 cluster 的一切；接著按正常流程加入其他節點。
$ bao operator raft snapshot restore /backup/snap-20260505-0800.bao
Snapshot restored. Cluster will rejoin shortly.

② 場景：誤刪某個 mount，想回到 1 小時前

同樣用 snapshot restore，但會把整個 cluster 退回（不是只復原誤刪的 mount）。所以你要評估：「過去 1 小時的其他寫入是否能犧牲？」如果不行，得手動從 audit log 重建。

實務上：policy delete、metadata delete 等高風險動作做之前先 snapshot；做完確認沒事再丟掉。

26.4 補發 root token：generate-root

正常運作時，root token 用一次後就應該 revoke。萬一需要再用（人都離職了、忘了密碼、故障排除），用 generate-root 流程：

# 1. 啟動 generate-root operation（會回 nonce + OTP/PGP）
$ bao operator generate-root -init
A One-Time-Password has been generated for you...
OTP: ...
Nonce: ...

# 2. 持有 unseal/recovery key 的人各自貢獻一份（threshold 之數）
$ bao operator generate-root -nonce=<nonce>
Unseal Key: ...
# ...重複到達 threshold

# 3. 取得 encoded token
$ bao operator generate-root -decode=<encoded> -otp=<otp>
Root Token: s.abc123...

生成後請立刻用它做完該做的事，然後 revoke：

$ bao token revoke -self

26.5 Recovery Mode

當 OpenBao 的設定檔損壞、storage 部分損壞、或某些 mount 啟動時 panic，server 連 unseal 都跑不起來。Recovery mode 啟動極簡 OpenBao，只暴露修復用 API：

$ bao server -recovery -config=/etc/openbao/config.hcl

Recovery mode 下：

  • 只接受 token 認證（用 generate-root 過的 root token）。
  • 可以呼叫部分 sys/raw/* 端點直接修 storage entry。
  • 不執行業務 mount、不 routing 一般請求。

Recovery mode 是最後一道牆，需要對 OpenBao 內部 storage layout 有相當理解才能用對。Production 上會用到的時機：(1) 跟支援團隊一起 debug；(2) 需要強行刪除某個損壞的 mount。

26.6 跨環境搬遷流程

場景：把 production 的 OpenBao 從 EKS A region 搬到 EKS B region。

  1. 在 B region 用相同 seal 設定建立新 cluster。可能需要先把 KMS key 跨 region 複製，或設定新的 KMS。
  2. A region snapshot save → 上傳 S3 → B region 下載。
  3. B region snapshot restore。
  4. 修改 client 的 BAO_ADDR 指向 B region。
  5. 關閉 A region cluster。

注意：

  • snapshot restore 後，所有 lease 仍會被識別，但對應的 dynamic secret（DB 帳號、PKI 簽出去的 cert）實體不在 B region 對應的後端。所以 dynamic 部分會「lease 還在但實際不能用」。實務上做法是 snapshot 後立刻 revoke 所有 dynamic lease，重新發。
  • Token 仍然有效，client 不需要重新 login（前提是 cluster_id 在 token 內仍可解）。

26.7 備份檢查清單

每月至少跑一次：

  • ✅ snapshot job 是否仍正常 (last successful run)。
  • ✅ snapshot 大小是否合理（不該突然變兩倍或變空）。
  • ✅ 異地保存是否仍可下載。
  • ✅ 隨機挑一個 snapshot 在測試環境做完整 restore，確認可恢復。
  • ✅ 文件中記錄的恢復流程（runbook）是否仍正確。
  • ✅ 持有 unseal/recovery key 的人員是否仍在職。

26.8 ⚙ 動手練習

  1. 跑一個 single-node 測試 cluster，寫幾個 KV，做一次 snapshot save。
  2. 把 KV 全部刪掉，跑 snapshot restore，看資料是否回來。
  3. 練習 generate-root 流程（單節點、recovery=1）。
  4. 寫一個 cron script + S3 上傳的 snapshot job。
✓ 章末重點
  • Snapshot 是 OpenBao 唯一備份方式；定期排程 + 異地保存。
  • Snapshot restore 是「整個 cluster」級的退回，不是 selective restore。
  • Recovery mode 是排錯用的最後一道牆，平時不該用。
  • Generate-root 流程需要 unseal/recovery key threshold；用完馬上 revoke。
  • 備份要演練；沒演練過的 DR 不算 DR。

Chapter 27升級指南

OpenBao 約每 3-4 個月一個 minor release，每月可能有 patch release。Production 環境怎麼升級才不會掉服務？本章提供 standalone 與 HA cluster 的標準流程。

27.1 版本相容性政策

  • Patch (2.5.x)：可跨任意 patch 直接升。
  • Minor (2.x)：建議逐 minor 升（2.4 → 2.5），跨多 minor 可能踩到中間版本的 migration。
  • Major (1.x → 2.x)：請仔細閱讀對應 release notes，可能有 breaking changes 與 migration 指南。

檢查 release notes

升級前務必看：

  • 該版本的 Breaking changes 段
  • Deprecation 段（即將被移除的功能）
  • Known issues 段
  • Security advisories（如有）

27.2 升級前檢查清單

每次升級前都跑一次：

  • ✅ 備份：執行一次 fresh snapshot，傳到異地。
  • ✅ 讀 release notes。
  • ✅ 確認 cluster 健康：bao operator raft autopilot state 顯示 healthy。
  • ✅ 確認 audit 正常：log 寫入沒積壓。
  • ✅ 準備回滾計畫：如果新版有問題，怎麼回到舊版？
  • ✅ 下班高峰前不升：至少留 24h 觀察期。

27.3 Standalone 升級

# 1. 備份
$ bao operator raft snapshot save pre-upgrade.bao

# 2. 停服務
$ sudo systemctl stop openbao

# 3. 替換 binary
$ sudo cp /downloads/bao-2.5.4 /usr/local/bin/bao
$ bao --version
OpenBao v2.5.4

# 4. 啟動
$ sudo systemctl start openbao

# 5. unseal（如非 auto-unseal）
$ bao operator unseal ...

# 6. 驗證
$ bao status
$ bao kv get secret/test

Standalone 升級會有幾秒到幾分鐘的 downtime。

27.4 HA Cluster Rolling Upgrade（零停機）

多節點 cluster 可以做 rolling upgrade，整個過程業務不掉：

  1. Snapshot 備份。
  2. 升級所有 standby 節點，一次一個：
    • 停掉一個 standby (systemctl stop)。
    • 升級它的 binary。
    • 啟動，等 unseal、加回 cluster、autopilot 顯示 healthy。
    • 下一個 standby。
  3. 讓 active step down：bao operator step-down。某個剛升級過的 standby 變 active。
  4. 升級原 active（現在已經是 standby）。
  5. 全 cluster 都新版本，完成。

K8s 上的 rolling upgrade

使用 Helm chart 時的標準流程：

# 1. 備份
$ kubectl -n openbao exec openbao-0 -- \
    bao operator raft snapshot save /tmp/snap.bao
$ kubectl -n openbao cp openbao-0:/tmp/snap.bao ./pre-upgrade-snap.bao

# 2. 更新 image tag
$ helm upgrade -n openbao openbao openbao/openbao -f values.yaml \
    --set server.image.tag=2.5.4

# 但因為我們前面設了 updateStrategyType: OnDelete，
# 不會自動 rolling，需要手動：

# 3. 一個個刪 standby pod，K8s 會用新 image 重建
$ kubectl -n openbao get pods -l vault-active!=true
NAME       READY   STATUS    RESTARTS
openbao-1  1/1     Running   0
openbao-2  1/1     Running   0
openbao-3  1/1     Running   0
openbao-4  1/1     Running   0

$ kubectl -n openbao delete pod openbao-1
# 等它 ready 後
$ kubectl -n openbao exec openbao-1 -- bao status
# 確認 healthy 且 join 回 cluster

$ kubectl -n openbao delete pod openbao-2
# ... 重複

# 4. 最後 step down active 並升級
$ kubectl -n openbao exec openbao-0 -- bao operator step-down
$ kubectl -n openbao delete pod openbao-0
⚠ 為什麼推薦 OnDelete 而非 RollingUpdate

Default StatefulSet rolling update 會同時重啟多個 pod（取決於 PodDisruptionBudget）。對 OpenBao 這種需要 quorum 的服務來說，可能瞬間掉到 quorum 之下。OnDelete 讓你掌控節奏：一個 pod 重起後 healthy 才動下一個。

27.5 回滾（Rollback）

OpenBao 不正式支援版本回滾（新版可能寫了舊版不認識的 storage entry 格式）。如果新版本有問題：

  • 同 minor 內回 patch（2.5.4 → 2.5.3）通常 OK。
  • 跨 minor 回滾（2.5 → 2.4）不支援。如果一定要，得從 pre-upgrade snapshot 在舊版本環境 restore。

所以「能不能回滾」 = 「有沒有 pre-upgrade snapshot」。這就是為什麼升級前 step 1 永遠是備份。

27.6 Deprecation 處理

OpenBao 對於將要移除的功能會在 release notes 標 deprecated。流程通常是：

  1. vN：標 deprecated，仍能用，但 server log 會 warn。
  2. vN+1：仍能用，但啟動時 print prominent warning。
  3. vN+2：移除。

升級前務必檢查你目前用的設定是否有 deprecated 項目。例如某些舊的 storage backend 在 v2.x 已被移除（從 Vault fork 過來時保留的）。

27.7 升級後驗證清單

升級完立刻跑：

  • ✅ bao status：所有節點 unsealed、有 active leader
  • ✅ bao operator raft autopilot state：healthy + failure tolerance ≥ 1
  • ✅ bao kv get、bao read database/creds/<role> 各跑一次
  • ✅ Audit log 仍持續寫入
  • ✅ Prometheus metrics 仍可 scrape
  • ✅ 應用層健康（隨機抽幾個服務看是否仍能取到 secret）

升級後觀察 24-48 小時，沒事再做下個升級。

27.8 ⚙ 動手練習

  1. 準備一個 3-node Raft cluster，當前版本 2.5.x（任意）。
  2. 做完整 rolling upgrade 到下個 patch（2.5.x+1），記錄每步驟的 bao status 與 autopilot state。
  3. 故意在 standby 升級到一半 kill 掉看 cluster 狀態。
  4. 從 pre-upgrade snapshot 在另一個全新 cluster 上 restore 練習回滾。
✓ 章末重點
  • 升級前永遠先 snapshot。
  • HA cluster rolling upgrade 順序：先 standby 一個個來，最後 active step-down 後升級。
  • StatefulSet 用 OnDelete 而不是 RollingUpdate，掌控節奏。
  • 跨 minor 不支援回滾，回滾 = 從 snapshot 在舊版本環境 restore。
  • 升級完跑驗證清單，觀察 24-48h 才動下個升級。
