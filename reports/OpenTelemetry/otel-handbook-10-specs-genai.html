29.3 OTLP 1.10 規格摘要

OTLP（OpenTelemetry Protocol）定義了 telemetry 的 wire format。重點：

  • Schema：用 protobuf 定義 ResourceSpans / ResourceMetrics / ResourceLogs / ResourceProfiles 四個 root message
  • 傳輸：gRPC（4317）與 HTTP/protobuf（4318）；兩者語意一致，差別只在傳輸效率與防火牆穿透
  • HTTP/JSON：可選，用於 debugging（瀏覽器 DevTools 可讀）
  • Partial Success：1.0+ 後端可回應「收下這 X 筆，剩下 Y 筆 reject」，client 可選擇是否 retry
  • OTLP/gRPC retry：用 standard gRPC retry header；限制 backoff
  • Compression：gzip 廣為支援，zstd（OTLP 1.5+）效能更佳

Wire 結構簡圖

flowchart LR
  subgraph Resource[ResourceSpans]
    R[Resource
service.name=...
k8s.pod.name=...]
    SS1[ScopeSpans
scope: java-instrumentation 1.0]
    SS2[ScopeSpans
scope: app-business 1.0]
    R --> SS1
    R --> SS2
    SS1 --> S1[Span 1]
    SS1 --> S2[Span 2]
    SS2 --> S3[Span 3]
  end

三層結構：Resource（誰發的）→ Scope（哪個 instrumentation 產生的）→ Spans / Metrics / Logs / Profiles。Scope 層常被忽略，但是後端做 instrumentation 篩選的關鍵。

29.4 OpAMP 規格摘要

OpAMP（Open Agent Management Protocol）規格 2024–2025 穩定。提供 agent fleet management 標準：

能力用途
Remote Configuration從中央 server 下發 config，無需重啟 agent
Effective Config ReportingAgent 回報目前實際生效的 config（含 env var 展開後）
Health StatusAgent 回報健康狀態
Package ManagementAgent 接受 binary 升級
Connection Settings動態調整 OTLP endpoint、TLS 憑證
Custom Messagesvendor-specific 擴充

Collector 的 opamp extension 已實作此協定（在第七篇 21.5 講過）。要 1000+ Collector 規模才會真正需要它。

29.5 規格升級流程與向下相容承諾

OTel 規格遵循 SemVer。明確承諾：

  1. Stable API 不會破壞向下相容：1.x → 1.y 版本切換不需改程式碼
  2. Stable SDK 行為穩定：環境變數名、預設值不會大改
  3. OTLP 嚴格向後相容：新版 client 能跟舊版 server 互通（feature degradation 可接受）
  4. SemConv 提供 stability migration 路徑：屬性 rename 會有 dual-emit 過渡期
  5. Experimental 標籤可破壞性變更：但會在 release notes 提醒

第 30 章 SemConv 完整剖析 開發者架構師#

30.1 SemConv 是什麼，為什麼是 OTel 最大價值

SemConv 定義「當你寫一個 HTTP server span，attribute 應該叫什麼名字、是什麼型別、什麼意思」。沒有它，每個 instrumentation 各自命名（http.method vs method vs request.method），跨服務查詢會崩潰。

SemConv 是 OTel 對業界最大的貢獻——比任何 SDK / Collector 都重要。一個團隊接 OTel 的長期收益，70% 來自 SemConv 帶來的跨服務跨工具一致性。

30.2 屬性命名規則（Attribute Naming）

規則範例
用 . 分層命名空間http.request.method / db.system.name
用 lower snake case 內部單詞error.type 不是 errorType
單複數依語意messaging.batch.message_count（單數）vs http.request.header.<key>（template）
避免縮寫service.namespace 不是 service.ns
業務屬性用獨立 namespaceapp.order.id / acme.tenant.id，不要混進 http.*
Resource 與 Span 屬性各自 namespaceservice.* 是 resource；http.* 是 span

30.3 屬性需求等級（Required / Recommended / Opt-In）

SemConv 對每個屬性標註 requirement level：

Level意義範例
Required合規 instrumentation 必須提供HTTP server span 的 http.request.method
Conditionally Required滿足條件時必須http.response.status_code（response 已 ready 時必須）
Recommended強烈建議，沒提供會降低 telemetry 價值http.route（route template）
Opt-In需顯式啟用（隱私／效能考量）http.request.body.size

讀 SemConv 文件時，這個欄位是首要關注點——告訴你「這個屬性會穩定存在嗎？」

30.4 Stability：Experimental → Stable

SemConv 的每個 group 都有 stability 標籤：

  • Experimental：可能變更名稱、型別、語意
  • Stable：凍結，破壞性變更需走 deprecation 流程
  • Deprecated：即將移除，找 replacement

2024–2026 大量 SemConv group 從 Experimental 進入 Stable，例如 HTTP（2024 stable）、Database（2025 stable）、K8s（2024 stable）。GenAI 截至 2026-05 仍在 Development（即 Experimental）。

30.5 Schema URL 與 Schema 轉換

每個 telemetry 都帶 schema URL，告訴後端「我用的是哪一版 SemConv」：

https://opentelemetry.io/schemas/1.41.0

後端在 ingestion 階段可以做 schema migration：把舊版屬性自動 rename 成新版。例如 HTTP migration（已穩定）：

舊（≤ 1.20）新（≥ 1.24 stable）
http.methodhttp.request.method
http.status_codehttp.response.status_code
http.urlurl.full
http.targeturl.path + url.query
http.schemeurl.scheme
http.hostserver.address + server.port
http.user_agentuser_agent.original

30.6 SemConv migration 三大遷移指南（HTTP、DB、K8s）

OTel 對主要領域的屬性穩定化提供 SemConv stability migration guide。各領域 instrumentation 透過 OTEL_SEMCONV_STABILITY_OPT_IN 環境變數控制 dual-emit 行為：

# 同時 emit 舊版與新版（過渡期）
export OTEL_SEMCONV_STABILITY_OPT_IN=http/dup,database/dup

# 只 emit 新版
export OTEL_SEMCONV_STABILITY_OPT_IN=http,database

# 多領域
export OTEL_SEMCONV_STABILITY_OPT_IN=http,database/dup,gen_ai_latest_experimental
領域狀態（2026-05）關鍵指南
HTTP Stable（2024 起） 已完成大多數命名 rename；舊應用要主動 opt-in 新版
Database Stable（2025 起） db.system → db.system.name；db.statement 處理；新增 db.operation.batch.size
K8s Stable（2024 起） K8s namespace 屬性穩定；增加 k8s.cluster.uid 等補強
RPC 進行中 命名空間統一
GenAI Development 新規格，尚未開始穩定化（見第 31 章）

第 31 章 Generative AI Observability 獨立章節 AI 開發者平台團隊#

31.1 為什麼 GenAI 需要獨立的 SemConv

LLM 應用（直接呼叫 OpenAI / Anthropic、用 LangChain、做 RAG、跑 agent、整合 MCP）有傳統 web 應用沒有的觀察維度：

  • Token 計量：input / output token 直接對應到帳單與效能
  • Cost：每次呼叫都有實際金額
  • Model 版本：同一 prompt 在 GPT-4 vs Claude 3.5 vs Llama 行為差異很大
  • Streaming 行為：first token latency、token rate
  • Tool Calling：function call 是業務關鍵，需要可追蹤
  • Agent 鏈：多步推理、可能非線性、可能含 retry / 自我反思
  • RAG retrieval：embedding、向量搜尋、context 長度
  • Safety：過濾結果、guardrail 觸發

OTel 從 2023 起設計專屬 SemConv，目前狀態 Development（即 Experimental），但社群已實作（OpenAI / Anthropic / AWS Bedrock / Azure AI Inference 都有對應 instrumentation）。

31.3 Model spans：單次 LLM 呼叫

Span 命名與 kind

  • Span name 格式：{operation} {model}，例如 chat gpt-4o / embeddings text-embedding-3-small
  • Span kind：CLIENT（呼叫遠端 API）

Python 範例（OpenAI 直接呼叫）

from opentelemetry import trace
from openai import OpenAI

tracer = trace.get_tracer("com.acme.chatbot")
client = OpenAI()

def chat(user_message: str):
    with tracer.start_as_current_span(
        "chat gpt-4o",
        attributes={
            "gen_ai.system": "openai",
            "gen_ai.operation.name": "chat",
            "gen_ai.request.model": "gpt-4o-2024-08-06",
            "gen_ai.request.temperature": 0.7,
            "gen_ai.request.max_tokens": 1024,
        }
    ) as span:
        try:
            response = client.chat.completions.create(
                model="gpt-4o-2024-08-06",
                messages=[{"role": "user", "content": user_message}],
                max_tokens=1024,
                temperature=0.7,
            )

            span.set_attribute("gen_ai.response.model", response.model)
            span.set_attribute("gen_ai.usage.input_tokens", response.usage.prompt_tokens)
            span.set_attribute("gen_ai.usage.output_tokens", response.usage.completion_tokens)
            span.set_attribute("gen_ai.response.finish_reasons", [response.choices[0].finish_reason])
            span.set_attribute("gen_ai.response.id", response.id)

            return response.choices[0].message.content
        except Exception as e:
            span.record_exception(e)
            span.set_status(trace.StatusCode.ERROR, str(e))
            raise

實務上不會這樣手寫，而是用 instrumentation library（OpenAI / Anthropic SDK 都有官方 OTel 整合 package），但理解屬性定義對 debug 很重要。

31.4 Agent spans：自主代理工作流

Agent 是「能呼叫 tool、自我推理、可能多步」的 LLM 應用。SemConv 為 agent 場景定義了專門 span：

operation.name意義
create_agent建立 agent instance（含 system prompt、tool list）
invoke_agent觸發 agent 執行單一 task
execute_toolAgent 執行某 tool（function calling）

  T1[execute_tool

31.5 GenAI Events：input / output content

GenAI SemConv 把實際的 prompt / response 內容放在 events 而非 attributes 中。原因：內容可能很長、含敏感資料、可能完全不需要送到 backend。

Event內容
gen_ai.user.message使用者輸入訊息
gen_ai.system.messageSystem prompt
gen_ai.assistant.messageAssistant 回應
gen_ai.tool.messageTool 呼叫的回傳結果
gen_ai.choiceFinal choice（含 finish_reason、tool_calls）

Events 是 opt-in：預設不送，需顯式啟用。建議：

  • 開發 / 測試環境：開啟，方便 debug prompt
  • 正式環境：關閉，或只在錯誤情況下 sample 進來
  • 受合規限制：永久關閉

31.6 GenAI Metrics：tokens、duration、cost

Metric類型意義
gen_ai.client.token.usageHistogram每次呼叫的 token 用量分佈（含 token.type=input / output 維度）
gen_ai.client.operation.durationHistogram單次操作 latency 分佈
gen_ai.server.request.durationHistogramServer 端視角的 latency（如自架 LLM 服務）
gen_ai.server.time_to_first_tokenHistogramStreaming 場景的首 token 延遲（極關鍵 UX 指標）
gen_ai.server.time_per_output_tokenHistogram每 output token 平均生成時間

關鍵維度

  • gen_ai.system
  • gen_ai.operation.name
  • gen_ai.request.model
  • gen_ai.response.model
  • gen_ai.token.type（input / output）
⚠️ Cost 不是 standard metric

SemConv 沒有定義 cost metric（因每家定價不同）。實務做法：在 Collector 用 transform processor 從 token usage 衍生 app.gen_ai.cost.usd，乘上對應 model 的單價（hard-code 或從 config 取）。

31.7 Vendor 特化：OpenAI / Anthropic / AWS Bedrock / Azure AI Inference

SemConv 對主流 vendor 有額外 namespace 補充：

Vendor專屬屬性 namespace主要 attribute 範例
OpenAI openai.* openai.request.service_tier、openai.response.service_tier、openai.response.system_fingerprint
Anthropic anthropic.* anthropic.request.beta（beta features）、anthropic.response.cache_creation_input_tokens、anthropic.response.cache_read_input_tokens
AWS Bedrock aws.bedrock.* aws.bedrock.guardrail.id、aws.bedrock.knowledge_base.id
Azure AI Inference azure.ai.inference.* Azure 特定的 deployment / region 屬性

用法：核心欄位（model、tokens、operation）走標準 gen_ai.*，廠商特化部分走對應 namespace。後端可以同時做「跨廠商比較」與「廠商特定 dashboard」。

31.8 Model Context Protocol（MCP）SemConv

MCP 是 Anthropic 在 2024 提出、後成為跨廠商標準的協定，定義 LLM 如何與外部 tool / resource / prompt 互動。OTel SemConv 已加入 MCP namespace（2025 起 Development）：

屬性意義
mcp.method.nameJSON-RPC method（tools/call、resources/read、prompts/get...）
mcp.request.idJSON-RPC request ID
mcp.session.idMCP session ID
mcp.tool.nameTool 名稱（在 tools/call 時）
mcp.resource.uriResource URI（在 resources/read 時）
mcp.prompt.namePrompt 名稱（在 prompts/get 時）

MCP server 與 MCP client 之間的呼叫是獨立的 span，與外層 LLM chat span 用 parent-child 關聯。這讓 RAG / Agent 系統的觀察粒度精細到「哪個 tool 慢、哪個 resource fetch fail」。

31.9 GenAI 隱私與合規

議題對策
使用者 prompt 含 PII events（actual content）預設關閉；只記 metadata（token count、duration）
System prompt 含商業機密 不記錄 system message event；或在 Collector OTTL 過濾
Tool call arguments 含敏感資料 對 tool name 採白名單；arguments 不記
Cost 屬商業敏感 per-team 隔離；不在共用 dashboard 暴露
Token usage 反映使用者行為 個別 user 的 metric 高基數；建議聚合到 team / customer 級別

31.10 GenAI 觀察實戰範本

把上面所有內容綁成一個給 GenAI 應用的 SOP：

  1. 裝對應 instrumentation library（opentelemetry-instrumentation-openai-v2、opentelemetry-instrumentation-anthropic...）
  2. 確認預設關閉 content events（避免 prompt 外洩）
  3. 建立 4 個 dashboard panel：
    • Token usage trend（按 model 分線）
    • Latency p50 / p95 / p99（按 operation 分線）
    • First-token latency（streaming UX）
    • Estimated cost per day（OTTL 衍生 + 單價表）
  4. 建立告警：
    • Error rate > 1%（model 錯誤、rate limit）
    • Cost daily quota 超標
    • Token usage 暴增（疑似濫用 / loop bug）
  5. Trace exemplars 連到 metric：每個慢請求的 metric 點都能跳到 trace
  6. Agent 場景：把 invoke_agent 設為 root span，用 trace 看完整推理鏈
  7. 每月檢視 SemConv 是否有 breaking 變更（GenAI 仍是 Development 狀態）

第 33 章 OTel 的未來：值得追蹤的方向 架構師#

33.1 Profiling 訊號（第四訊號）

2024 OTel 把 Profiles（CPU / memory / lock 分析資料）正式納入規格，與 trace、metric、log 並列為「第四訊號」。OTLP 1.7+ 已支援 profile message。pprof（Go 的標準 profiling 格式）是 reference encoding。

實務應用：當 trace 顯示某 span 異常慢，後端可直接跳到該時段的 profile，看到具體哪個函式佔用 CPU。這把 SRE 的 RCA 流程縮短一個量級。狀態：規格穩定，後端支援逐步擴大（Pyroscope / Parca / Datadog 已生產可用）。

33.2 OBI（OpenTelemetry eBPF Instrumentation）

OBI（前身 Grafana Beyla）是用 eBPF 實現「無需程式碼修改、無需 SDK」的真正 zero-code 觀察。它直接 hook kernel 層 socket / syscall，產生 RED metrics 與分散追蹤——對任何語言、任何框架都通用。

限制：需 privileged 容器或對應 capabilities；對 mTLS 流量無法解密；trace 資訊比 SDK 少。但對遺留系統觀察價值極大。狀態：2025 起進入 OTel 主線，文件在 opentelemetry.io/docs/zero-code/obi/。

33.3 Entities 規格

OTel Spec 1.30+ 引入 Entities 概念。Resource 描述「誰發 telemetry」是一個「平面集合」，但實際上它包含多個重疊實體（Service、Container、Host、K8s Pod、Cloud Region...）。Entities 規格把它們區分開，每個有自己的識別屬性與生命週期。

Entities 解決的痛點：以前 Prometheus 標籤過多時 explosion；後端對「同一 host 上多個 service」這類關係建模困難。Entities 給了清晰的多實體模型。狀態：規格 stable，SDK 與 backend 實作進行中。

33.4 Declarative Configuration GA

Declarative Config（YAML SDK 設定）規格已穩定（2025）。各語言 SDK 從 Beta 走向 GA：Java 已 GA；Python / JS 進行中。當所有主流語言都 GA 後，多語言 OTel 部署的設定一致性會大幅提升。

33.5 GenAI / Agent 演進

GenAI SemConv 2026–2027 預計重點：

  • 從 Development 進入 Stable（部分子規格優先）
  • Agent 與 Multi-agent 的標準化（更多 LangGraph / AutoGen / CrewAI 整合）
  • Streaming / WebSocket 場景的標準化
  • Tool calling 細節屬性（含 retries、parallel calls）
  • Cost metric 規格化（讓跨 vendor 比較更容易）
  • RAG / Vector DB 觀察規範
