入門與基礎概念

OpenTelemetry（簡稱 OTel）是一套廠商中立、開源的可觀測性框架（observability framework）。它幫你在不被綁死於特定後端的前提下，用同一套 API 與規格，產生、收集並導出應用系統的 telemetry 資料。本篇從零講起：可觀測性是什麼、OTel 解決什麼問題、三大訊號的資料模型，以及上下文傳播、Resource、Sampling 等必備概念。

第 1 章 認識 OpenTelemetry 初學者#

1.1 什麼是 OpenTelemetry

OpenTelemetry（縮寫 OTel）是一個由 CNCF（Cloud Native Computing Foundation）託管的開源專案，定位是 observability framework and toolkit，目標是讓你能用一致、廠商中立的方式，產生（generate）、導出（export）、收集（collect）系統的 telemetry data，包含 traces、metrics、logs，以及正在邁入穩定的 profiles。

更具體一點，OTel 提供了下列幾類產出物：

  • 規格（Specification）：定義所有元件的語意、行為、API 形狀。目前最新為 OTel Spec 1.56.0。
  • 協定（Protocol, OTLP）：規範 telemetry 在線上傳輸的資料格式，目前 OTLP 1.10.0。
  • 語意約定（Semantic Conventions）：常見場景（HTTP、DB、K8s、GenAI…）的標準屬性命名，目前 SemConv 1.41.0。
  • 各語言 API 與 SDK：把規格落地成 Java、Go、Python、JavaScript、.NET、Ruby、PHP、Rust、C++、Erlang、Swift 等實作。
  • Instrumentation Libraries：對主流框架（Spring、Express、Django、gRPC…）已預先寫好的 instrumentation。
  • Zero-code Instrumentation：不改程式即可產出 telemetry 的自動化機制（例如 Java agent、eBPF）。
  • OpenTelemetry Collector：廠商中立的 telemetry 收集、處理、導出 proxy。
  • 周邊工具：Kubernetes Operator、Helm Charts、FaaS 資產等。
📌 一句話定義

OTel 是一套幫你「產 telemetry 並送到任何後端」的標準與工具鏈，自己不存資料、不畫圖。後端（儲存）與前端（視覺化）刻意留給其他工具，例如 Jaeger、Prometheus、Grafana，或商業 APM 廠商。

1.2 為什麼需要可觀測性

從 Monitoring 到 Observability

傳統 Monitoring（監控）處理的是「我已知這件事可能會壞，幫我盯著」——這叫 known-unknowns。而 Observability（可觀測性）處理的是「我根本不知道哪裡會壞，但發生時我得能查得出來」——這叫 unknown-unknowns。

Observability 的核心，是從系統的外部輸出（traces、metrics、logs）反推內部狀態，而不需要事先預設要看什麼指標。當應用程式被「正確地 instrument」，工程師遇到問題時，不需要新增 instrumentation 就能 debug，因為手上已經有足夠的脈絡資訊。

Reliability、SLI、SLO

幾個必懂、可觀測性與 SRE 共用的詞：

術語白話定義例子
Telemetry 系統產生、用以描述行為的資料 Traces / Metrics / Logs / Profiles
Reliability（可靠度） 「服務做的事是不是使用者預期的？」 Up 100% 但結帳會把黑鞋變白鞋＝不可靠
SLI Service Level Indicator 從使用者視角測量服務行為的指標 頁面載入時間、API 成功率
SLO Service Level Objective 把 SLI 綁上業務價值後對外承諾的目標 「99.9% 結帳請求 < 500ms」

為什麼這些概念會在 OTel 文件出現？因為 OTel 產出的 traces 與 metrics，正是計算 SLI、追溯 reliability 問題最直接的原料。沒有一致的 telemetry，SLO 只是紙上談兵。

1.3 OTel 解決的核心問題

OTel 把自己的設計準則濃縮成兩條原則：

  1. You own the data that you generate. 你產生的資料屬於你，不被廠商鎖定。
  2. You only have to learn a single set of APIs and conventions. 全公司、跨語言只學一套 API 與命名約定。

這兩條原則背後其實處理了三個老問題：

老問題OTel 怎麼解
每家 APM 廠商都要你裝專屬 agent，換家就重做 應用只跟 OTel API 互動，後端透過 Collector exporter 切換
跨語言、跨團隊命名各搞各的，無法跨服務聚合分析 Semantic Conventions 統一屬性命名（http.request.method、service.name …）
Trace、Metric、Log 三條 pipeline 各自為政，無法 correlate 共用 Context、Resource，並由 OTLP 統一 wire format

1.4 與 OpenTracing、OpenCensus 的歷史淵源

OTel 並非從零開始。它是 2019 年由兩個前身專案合併而成：

  • OpenTracing：CNCF 專案，專注於 distributed tracing 的 vendor-neutral API。
  • OpenCensus：Google 主導，Tracing 與 Metrics 雙軌的函式庫集合。

兩者都在解同一個問題——「如何 instrument 程式碼並把 telemetry 送到後端」——但都各自缺一塊（API vs 實作、tracing vs metrics）。合併後形成了今日的 OpenTelemetry，並把 logs、profiles 也納入。

2019 ~ now]
  OC[OpenCensus
2018 · API + SDK] --> OTel
  OTel --> Traces
  OTel --> Metrics
  OTel --> Logs
  OTel --> Profiles

如果你目前還在用 OpenTracing 或 OpenCensus，OTel 提供了 官方 Migration 文件，這部分我們會在第七篇〈相容性〉再深入。

1.5 OTel 不是什麼

OTel 文件特別強調幾個常見誤解，這對採購、選型、架構設計都很關鍵：

常見誤解事實
OTel 是一個 APM／observability 後端 不是。它不存資料、不畫圖、不告警。後端要自己選（Jaeger、Tempo、Prometheus、Grafana、Datadog、New Relic 等）。
OTel 會取代 Prometheus / Jaeger 不會。它是輸入端標準。Prometheus / Jaeger 都已支援接收 OTLP，可以共存。
OTel 一裝就有圖看 沒有。你需要：①instrument 應用 ②選後端 ③選 UI。OTel 只負責中間的「產生 → 傳輸 → 收集」。
OTel 只做 tracing 三大訊號 traces / metrics / logs 都是公民，第四訊號 profiles 也已有規格。

1.6 OTel 在 CNCF 的位階與成熟度

OTel 是 CNCF 的 Incubating（孵化中）專案，但實質上是 CNCF 內活躍度與貢獻者規模僅次於 Kubernetes 的專案之一。各訊號的穩定度不一，產品決策時請以 OTel 官方的 Status 頁面為準：

訊號／元件規格狀態產品建議
Traces (API/SDK)Stable正式環境可用
Metrics (API/SDK)Stable正式環境可用
Logs (API/SDK)多數語言 Stable，Logs Bridge 已穩定正式環境可用，建議透過 Logs Bridge 接管現有 logger
ProfilesDevelopment（規格 1.x 中演進）實驗階段，不建議全面導入
OTLPStable（1.10.0）跨後端首選 wire format
OTel Collectorcore 元件多為 Stable，contrib 多為 Beta選擇 component 時看個別狀態
⚠️ 版本號別搞混

OTel 內有多個獨立版本號：①Specification（如 1.56.0）②OTLP（如 1.10.0）③Semantic Conventions（如 1.41.0）④各語言 SDK（各自獨立）⑤Collector（各自獨立）。導入時請逐一確認，不要假設「升某個元件其他都會跟著動」。

第 2 章 快速上手 初學者開發者DevOps#

官方把入門路徑明確分成兩條——Dev 路徑（開發者：要把自己應用 instrument 起來）與 Ops 路徑（運維：要把 telemetry 收進來、跑起來、上後端）。本章先給你兩條路徑的最短可行版本，後續章節會分別展開。

最低限度的環境變數設定（任何語言都通用）： 

# 識別這個服務
export OTEL_SERVICE_NAME="my-app"
export OTEL_RESOURCE_ATTRIBUTES="service.version=1.0.0,deployment.environment=staging"

# 預設用 OTLP/gRPC，送到本地 Collector
export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4317"

# 初期可以全送，正式上線再導入 sampling
export OTEL_TRACES_SAMPLER="always_on"
✅ Dev 路徑的捷徑

第一次接觸 OTel 強烈建議先跑 OpenTelemetry Demo（第二篇詳述）。它是一個多語言微服務範例，啟動後就能看到 traces、metrics、logs 三訊號完整 correlate，是學各語言 SDK 的最佳範本。

2.2 維運人員快速體驗路徑（Ops）

對 DevOps / SRE 來說，OTel 的「實體」就是 Collector 這支可獨立部署的程式。最簡 Ops 路徑：

  1. 選 distribution：otel/opentelemetry-collector-contrib（功能最齊全）或 core 版（最小化攻擊面）。
  2. 寫 config.yaml：定義 receivers / processors / exporters / pipelines。
  3. 選部署模式：Agent（每節點一個）、Gateway（集中閘道）、Agent + Gateway（混合）。
  4. 啟動 → 觀察 internal telemetry → 接後端。

最小可行 Collector 設定範例：

# config.yaml — 最小可行版
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:
  memory_limiter:
    check_interval: 1s
    limit_mib: 400

exporters:
  debug:
    verbosity: detailed
  # 之後可改 otlp/prometheus/elasticsearch 等

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]
    metrics:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]
    logs:
      receivers:  [otlp]
      processors: [memory_limiter, batch]
      exporters:  [debug]

啟動：

docker run --rm -p 4317:4317 -p 4318:4318 \
  -v $(pwd)/config.yaml:/etc/otelcol/config.yaml \
  otel/opentelemetry-collector-contrib:latest
📌 為什麼第一站建議 debug exporter？

很多人卡在「我裝好應用了，但後端看不到資料」，原因往往是中間鏈路斷了。先用 debug exporter 印出來確認 Collector 真的有收到資料，再切換到正式後端。第五篇 Collector 章會深入 troubleshooting。

第 3 章 核心概念（上）— 訊號與資料模型 初學者開發者#

3.1 三大訊號總覽

在 OTel 的語言裡，Signal（訊號）指的是「一類具有獨立資料模型與處理 pipeline 的 telemetry」。目前有四類：

Signal回答的問題典型形式規格穩定度
Traces 「這個請求在系統裡走了哪些步驟、各花多久？」 Span 樹狀結構 Stable
Metrics 「系統整體層面的數字趨勢如何？」 時序數值（Counter / Gauge / Histogram） Stable
Logs 「在某個時間點，發生了什麼事件？」 結構化或非結構化的時間戳訊息 Stable
Baggage 「跨服務攜帶業務脈絡」（嚴格說是傳輸機制不是訊號） Key-Value 對 Stable
Profiles 「程式內部哪些函式吃掉了 CPU、記憶體？」 Profile 樣本（pprof 格式） Development
📌 怎麼搭配使用

典型 SRE/Dev 工作流：①先看 Metrics 發現異常（成功率掉、p99 飆）→ ②跳到對應時段的 Traces 找慢的或失敗的請求 → ③下鑽到該 trace 上的 Logs 看具體錯誤訊息。三訊號透過 trace_id / span_id correlate 起來，這正是 OTel 與單一訊號工具的最大差異。

3.2 Traces：Span、Trace 與屬性

Span 是什麼

Span 代表「一個工作單元或操作」——例如一次 HTTP 請求、一次 DB 查詢、一次 RPC 呼叫。它包含：

  • Name：人讀的操作名稱（如 GET /api/orders/:id）。
  • SpanContext：包含 trace_id（128-bit）、span_id（64-bit）、trace_flags、trace_state。
  • Parent Span ID：指向父 span，沒有就是 root。
  • Kind：SERVER、CLIENT、PRODUCER、CONSUMER、INTERNAL。
  • Start / End Timestamp：奈秒精度的起訖時間。
  • Status：Unset、Ok、Error。
  • Attributes：Key-Value 屬性，描述這個 span 的具體內容。
  • Events：span 內部的時間點訊息（結構化的 log）。
  • Links：指向其他 span 的關聯（例：訊息佇列的 batch 處理）。

Trace 則是把所有共享同一個 trace_id 的 spans 組合成的樹狀結構。一條 trace 通常代表「使用者一個請求從進入系統到離開系統」的完整旅程。

Span 屬性（Attributes）— 跟著 SemConv 走

OTel 強烈建議屬性命名要遵循 Semantic Conventions，這樣後端、儀表板、告警規則才能跨服務通用：

Key範例值
http.request.method"GET"
network.protocol.version"1.1"
url.path"/webshop/articles/4"
url.query"?s=1"
server.address"example.com"
server.port8080
http.route"/webshop/articles/:article_id"
http.response.status_code200
client.address"192.0.2.4"
user_agent.original"Mozilla/5.0 ..."

3.3 Metrics：Counter、Gauge、Histogram、Exemplars

Metrics 在 OTel 中的設計目標是「可聚合的、可時序儲存的數值資料」。與 Prometheus 概念高度重合，但加了幾個特色（特別是 Exemplars 與 Multi-dimensional aggregation）。

Instrument 類型

類型用途例子
Counter 單調遞增的累計值 http.server.request.count、db.errors_total
UpDownCounter 可增可減的累計值 佇列長度、進行中連線數
Gauge（含 Asynchronous Gauge） 瞬時量測值 CPU 使用率、記憶體使用量
Histogram 分佈統計（含 Explicit Bucket 與 Exponential） HTTP 延遲分佈、Payload 大小分佈

Synchronous vs Asynchronous

  • Synchronous：在業務程式呼叫處同步記錄，例如 requestCounter.add(1, attrs)。
  • Asynchronous（Observable）：在 metric 收集時 callback 回去取值，適合「想看當下值」的場景，例如記憶體使用量。

Exemplars — Trace 與 Metric 的橋樑

Exemplar 是 OTel Metric 的特色之一：每個 metric data point 可以附帶一筆「當時某個具體 trace 的 trace_id / span_id」，讓你在儀表板上看到「99 百分位高的延遲」時，能直接點進那筆代表性的 trace 看原因。這對排查長尾延遲非常有用。

3.4 Logs：Log Record 與 Trace 關聯

Logs 是三大訊號中最後加入 OTel 的（規格較新），它有一個獨特定位——OTel 不打算取代你現有的 logger，而是提供一個 Logs Bridge，讓你的 log4j、logback、structlog、winston 等可以把 log 轉成 OTel Log Record，搭著 Trace Context 一起送出。

Log Record 資料模型

欄位說明
Timestamp事件發生時間
ObservedTimestamp被收集到的時間
SeverityText / SeverityNumber等級（INFO/WARN/ERROR/...）
BodyLog 主體（可為字串或結構化 AnyValue）
TraceId / SpanId / TraceFlags關聯到的 trace（如果有）
Resource產生這則 log 的服務／主機
Attributes結構化 key-value
✅ 為什麼 Logs 與 Trace 關聯這麼重要

排查問題時，從 trace waterfall 跳到該 span 期間的 logs，比在大海撈針裡 grep 高效一百倍。OTel 自動把當前 SpanContext 寫入 log record，後端就能用 trace_id 篩選相關 logs。

3.5 Baggage：跨服務攜帶業務資訊

Baggage 嚴格來說不是訊號，而是「跨服務傳遞的 Key-Value 對」。它和 Trace Context 走同一條 propagation 路徑（W3C Baggage Header），但內容由你定義。

典型用途

  • 把 tenant.id、user.tier、region 等業務維度傳到下游服務，下游可以拿來標註自己的 spans/metrics/logs，做業務維度的聚合分析。
  • 在多 service 間傳遞 feature flag context，讓下游服務知道「這個請求是 A/B 測試的 B 群」。

用 Baggage 的注意事項

⚠️ 三個常見地雷
  • 不要塞 PII（個資）：Baggage 會跟著 HTTP header 走遍整個系統，可能被上下游 log 下來。
  • 不要塞太大：Baggage 是 HTTP header，多數 reverse proxy 對 header 大小有限制（通常 8KB 內）。
  • Baggage ≠ Span Attributes：Baggage 不會自動成為 span attribute；需要在下游服務手動把 baggage 讀出來、寫進 span 裡。

3.6 Profiles：第四訊號

Profile 回答的是「程式內部哪一行、哪個函式正在吃 CPU/記憶體？」，傳統上由各語言的 profiler（pprof、async-profiler、py-spy…）提供，缺乏跨語言統一格式。

OTel 把 profiles 納為第四訊號，採用業界事實標準 pprof 格式，並透過 OTLP 傳輸。Profile 與 trace 的整合是它的賣點：點 trace 上的某個 span，就能看到那段時間該服務真實的 CPU 火焰圖。

⚠️ Profiles 目前狀態

截至 2026 年初，OTel Profiles 規格仍在 Development（開發中）階段，Collector 已有 otlpreceiver/profiles 與部分後端（如 Pyroscope/Grafana）支援，但 SDK 端尚未全面 GA。生產環境導入請評估風險。

4.1 Context Propagation

分散式 tracing 的核心難題：Service A 發送請求到 Service B，B 怎麼知道自己是 A 那個 trace 的一部分？答案是 Context Propagation（上下文傳播）——把 trace_id、span_id、baggage 等資訊塞進跨服務通訊的載體（headers、message metadata）。

W3C Trace Context 是預設標準

OTel 預設使用 W3C Trace Context 標準，主要兩個 HTTP header： 

# traceparent — 必要欄位
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              ^   ^                                ^                ^
              |   |                                |                +-- trace-flags (sampled?)
              |   |                                +------------------- parent-span-id
              |   +------------------------------------------------- trace-id (128-bit)
              +-------------------------------------------------- version

# tracestate — vendor-specific 補充欄位
tracestate: rojo=00f067aa0ba902b7,congo=t61rcWkgMzE

Propagator 的概念

Propagator 是負責把 context inject（注入）到 carrier、或從 carrier extract（取出）的元件。OTel 內建幾種：

Propagator用途

jaegerJaeger Uber-Trace-Id
xrayAWS X-Ray

通常設定多個 propagator 以求相容：OTEL_PROPAGATORS=tracecontext,baggage。

4.2 Resources

Resource 描述的是「產生這份 telemetry 的實體是誰」——服務名稱、版本、所在主機、雲端區域、容器、Pod 等。所有這個 SDK 產的 traces / metrics / logs 都會被加上同一個 Resource。

必填的 Resource Attribute

Attribute說明範例
service.name服務的邏輯名稱（必填，沒設會是 unknown_service）checkout-api
service.version服務版本1.4.2
service.instance.id實例 ID（同服務多副本時區分用）pod-7f9c
deployment.environment.name環境prod / staging
host.name主機名node-eu-1
k8s.pod.nameK8s pod 名（K8s 環境）checkout-7f9c-x2d

Resource Detector

SDK 通常內建多個 Resource Detector，會自動偵測執行環境並補上對應的 attribute：在 AWS EC2 自動帶 cloud.provider=aws、在 K8s 自動帶 k8s.*。你要做的是設好 service.name 與 service.version，其餘交給 detector。

4.3 Instrumentation Scope

Instrumentation Scope 描述「是哪段 instrumentation 程式碼產生這個 telemetry」——通常對應一個 instrumentation library。例如 io.opentelemetry.instrumentation.spring-webmvc-6.0 表示這個 span 是 Spring WebMVC 6.0 instrumentation 產的。

這個資訊雖然不起眼，但在排查問題時非常有用——「為什麼這個 span 的屬性怪怪的？」往往答案就是「某個 instrumentation library 的 bug 或舊版」。

4.4 Semantic Conventions

Semantic Conventions（語意約定，簡稱 SemConv）是 OTel 的命名標準，目的是「讓不同團隊、不同語言、不同 instrumentation 對同一件事用同樣的 attribute 名稱」。

為什麼這件事如此重要？想像一下：

  • Java 服務記錄 http.method=GET，但 Go 服務記錄 http_method=GET。
  • 後端儀表板想統一查所有 GET 請求 → 你得寫一堆 OR 條件。
  • SemConv 規定大家都叫 http.request.method，這個問題就消失了。

SemConv 涵蓋範圍（節錄）

類別典型 attribute
HTTPhttp.request.method、http.response.status_code、http.route
Databasedb.system.name、db.collection.name、db.query.text
Messagingmessaging.system、messaging.destination.name、messaging.kafka.consumer.group
RPCrpc.system、rpc.service、rpc.method
Cloud / K8scloud.provider、cloud.region、k8s.namespace.name
GenAIgen_ai.request.model、gen_ai.usage.input_tokens（第八篇詳述）
📌 SemConv 也在演進

SemConv 1.41.0（2026 年初最新）相較幾年前的版本有重大改名（最有名的是 http.method → http.request.method）。OTel 提供了 Schema URL 機制，讓 telemetry 自帶版本資訊，後端可以做轉換。導入時請以最新版本為準。

4.5 Sampling

Sampling（取樣）是把 telemetry 體積與成本壓低、又保留代表性的關鍵手段。OTel 把 sampling 分成兩大類：

Head-based Sampling（頭部取樣）

在 trace 開始時就決定「要不要採樣」，後續所有 span 跟隨這個決定。優點是便宜、不用緩存整條 trace，缺點是可能漏掉錯誤的 trace（因為錯誤通常出現在 trace 中後段）。常見實作：

Sampler策略
AlwaysOn全採
AlwaysOff全不採
TraceIdRatioBased依 trace_id hash 取固定比例（如 10%）
ParentBased跟隨上游決定（推薦預設）

Tail-based Sampling（尾部取樣）

等整條 trace 完成後再決定要不要保留。優點是能保留所有錯誤、慢的 trace；缺點是需要在 Collector 緩存所有 spans，記憶體消耗大、有延遲。通常透過 Collector 的 tail_sampling processor 實作。 

flowchart TD
  A[Trace 開始] --> B{Head Sampler
決定要不要採?}
  B -- 不採 --> C[後續 spans 都不送]
  B -- 採 --> D[所有 spans 送出 OTLP]
  D --> E[Collector tail_sampling processor]
  E --> F{policies
例:
error 必收
p99 latency 必收
正常 1% 抽樣}
  F -- 收 --> G[送往後端]
  F -- 丟 --> H[捨棄]

新趨勢：Probability Sampling 與 Consistent Sampling

OTel Spec 1.5x 系列引入了基於 tracestate 的 Probability Sampling 機制，讓不同服務用不同採樣率時也能維持一致性與可計算性（例如後端能正確還原原本的 metric counts）。實作層面這還在演進，但概念上是把 sampling 從「黑魔法」推向「可數學化」。

4.6 Components 與 Distributions

Components（元件）

OTel 整個生態主要由下列元件（Components）組成：

  • Specification：所有元件的行為依據。
  • API：輕量、給應用程式用的介面（例：tracer.Start()）。
  • SDK：API 的實作端，含取樣、批次、Exporter。
  • Instrumentation Libraries：對主流框架預先寫好的 instrumentation。
  • OTel Collector：接收、處理、導出的 proxy。
  • OTel Operator：K8s 上的自動化部署工具。
  • OTel Helm Charts：K8s 部署的 Helm 範本。

Distributions（發行版）

Distribution 是「把 OTel 元件打包成特定組合的客製版本」。為什麼需要？因為 OTel 上游元件追求最小可行、廠商中立，但實務上你可能要：

  • 在 Collector 上加入特定後端的 exporter（例：vendor X 的 exporter）。
  • 移除不會用到的元件，縮小 binary、降低攻擊面。
  • 固定特定版本組合，加上自家 patch。

常見 distribution：

Distribution說明
otelcol（Core）OTel 官方核心版，元件最少
otelcol-contribOTel 官方 contrib 版，包含社群所有 components
各廠商 distributionAWS Distro for OpenTelemetry (ADOT)、Splunk Distribution、Grafana Alloy 等
OCB（OpenTelemetry Collector Builder）讓你自己組裝 distribution 的工具
