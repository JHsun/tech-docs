第 5 章 Demo 應用全景 初學者開發者DevOps#

5.1 Demo 是什麼、為什麼重要

OpenTelemetry Demo（簡稱 Demo）是 OTel 官方維護的「仿真電商應用」，原始碼在 open-telemetry/opentelemetry-demo。它有四個身分：

  • 跨語言參考實作：每個微服務都以不同語言寫成（.NET、Go、Java、JavaScript、Kotlin、PHP、Python、Ruby、Rust、TypeScript、C++、Elixir），是學各語言 OTel SDK 最佳的「活範本」。
  • 三訊號整合 demo：traces / metrics / logs 在同一個應用中同時產出、並透過 trace_id correlate。
  • Feature Flag 故障場景庫：內建可開關的「故障情境」（記憶體洩漏、延遲飆升、廣告失敗等），讓你練習用 OTel 找出問題。
  • 整套 backend stack：附 Jaeger（trace）、Prometheus（metric）、OpenSearch（log）、Grafana（unified UI）、flagd（feature flag），開箱即用、不依賴任何商業 SaaS。
✅ 為什麼第一站推薦這個

多數人剛入門 OTel 最大的卡點是「整條鏈路斷在哪我看不到」。Demo 把所有環節都打通了，你可以：先看到完整成果 → 再去拆每一個元件學原理 → 最後改造成自家系統。本手冊後面所有章節，都可以回來在 Demo 上驗證。

5.2 應用架構與微服務組成

Demo 模擬的是天文望遠鏡與配件電商：使用者瀏覽商品、加入購物車、結帳付款、收信、評論商品。截至 2026 年初，共有約 20 個服務，2025 下半年新增了 Product Reviews Service（Python）與 LLM Service（Python，模擬 GenAI 場景）。資料儲存層也從 Redis 改為 Valkey（Redis fork），佇列為 Kafka，關聯式資料則由 PostgreSQL 提供。

幾個觀察重點：

  • 所有 telemetry 一律先進 Collector：應用不直接寫後端。這是 OTel 推薦的部署形狀，提供緩衝、批次、過濾、轉換、避免應用直接綁後端。
  • Span Metrics Connector：把 traces 轉成 RED metrics（Rate / Errors / Duration），免得你還要另外為每個服務寫 instrumentation。第五篇 Collector 章會深入它。
  • Prometheus 收 OTLP：直接走 OTLP HTTP（/api/v1/otlp/v1/metrics），不需 sidecar exporter。第七篇會講這對 Prometheus 生態的意義。
  • 三個 backend、一個 UI：Jaeger / Prometheus / OpenSearch 各司其職，Grafana 在最上層做 unified observability，這也是業界主流做法。

5.5 系統需求

Demo 不算輕，跑全部服務 + 後端 stack 至少需要：

  • CPU：建議 4 核以上（最低 2 核）。
  • RAM：建議 8 GB 以上（Docker Desktop 設定要一併調高）。
  • Disk：第一次拉映像約 6 GB；含資料卷預留 10 GB。
  • 軟體：Docker 26+ 且支援 docker compose v2，或 Kubernetes 1.27+ + Helm 3.14+。
⚠️ Mac 與 Windows 的 Docker Desktop

預設記憶體配額通常是 2 GB，Demo 會直接 OOM。請到 Docker Desktop → Settings → Resources 把 RAM 調到 8 GB 以上、CPU 調到 4 core 以上。WSL2 也建議在 %USERPROFILE%/.wslconfig 設定 memory=8GB。

第 6 章 Demo 部署與操作 初學者DevOps#

6.1 Docker Compose 部署

最快的方式，三條指令搞定：

# 1. 取得 repo
git clone https://github.com/open-telemetry/opentelemetry-demo.git
cd opentelemetry-demo

# 2. 拉映像 + 啟動所有服務
docker compose up --no-build -d
# 第一次會花一點時間，因為要拉 30+ 映像

# 3. 確認服務都健康
docker compose ps

啟動後可以在瀏覽器打開以下端點：

UI用途網址
Webstore電商前端，可下單http://localhost:8080
Grafana所有 dashboard 入口（含 Jaeger / Prometheus 嵌入）http://localhost:8080/grafana/
Load GeneratorLocust UI，控制流量大小http://localhost:8080/loadgen/
Feature Flag UIflagd-ui，切換故障場景http://localhost:8080/feature/
JaegerTrace UI（也可從 Grafana 進）http://localhost:8080/jaeger/ui/

停掉所有服務：

docker compose down
# 連 volumes 一起清：
docker compose down -v

6.2 Kubernetes / Helm 部署

K8s 環境用官方 Helm chart：

# 1. 加 OTel Helm repo
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

# 2. 安裝 demo（會建立一堆 deployment/svc/configmap）
helm install my-otel-demo open-telemetry/opentelemetry-demo

# 3. port-forward 到本機
kubectl --namespace default port-forward svc/frontend-proxy 8080:8080

之後同樣用 http://localhost:8080 進入。Helm chart 的好處：

  • 所有服務都按 deployment / service / configmap 標準切好，方便客製。
  • 可在 values.yaml 中關閉用不到的服務（例如不想跑 OpenSearch），縮小資源占用。
  • 可以接上自家的 Collector / Backend，把 demo 應用單獨拉出來作為負載源。
📌 在現有 K8s 叢集評估時的小技巧

Demo Helm chart 預設把 Jaeger、Prometheus、Grafana、OpenSearch 都裝起來。如果你叢集已有 observability stack，可以在 values.yaml 裡 disable 這些子 chart，只留應用層，把 OTLP exporter 指向你既有的 Collector。這是評估自家平台是否能正確接收所有訊號的好方法。

6.3 React Native App 行動端

2025 年新增的 React Native App 服務，是行動端的 client-side instrumentation 範例。它示範如何把 RUM（Real User Monitoring）資料一路 trace 到後端服務。

要跑起來需要 Android Studio 或 Xcode 環境。架構上它與 React Native App 之間透過 frontend-proxy 通訊，與其他服務共享 trace context（透過 W3C Trace Context header）。

這個服務對有行動端產品的團隊特別有價值：示範了 mobile span 的命名約定（依照 SemConv mobile namespace）、screen view tracking、network errors 如何 propagate 到後端 trace。第六篇〈平台與環境整合〉會詳述。

6.4 Load Generator 與壓力測試

Load Generator（Python + Locust）是 Demo 的「流量引擎」。它模擬真實使用者：瀏覽商品 → 加入購物車 → 結帳，並隨機混入錯誤情境。沒有它，所有 dashboard 都是死的。

進入 http://localhost:8080/loadgen/ 後可以調整：

  • Number of users：併發使用者數，預設 10–50；要看明顯延遲分佈時可調到 100+。
  • Spawn rate：每秒新增使用者數。
  • Host：通常已預設好為 http://frontend-proxy:8080。

學習時建議的觀察流程：

  1. 啟動 50 user 的負載。
  2. 等 1 分鐘讓 metric 穩定。
  3. 到 Grafana → OpenTelemetry Demo Dashboard 觀察 RED metrics。
  4. 到 Jaeger 找一筆完整 checkout trace，研究跨服務的 span 樹。
  5. 切換到 OpenSearch / Logs 看對應 trace 的所有 logs。

6.5 Forking — 改造為自家測試平台

官方鼓勵 fork Demo 來作為自家 observability 平台的「跨語言驗收測試環境」。常見改造路徑：

  • 替換後端：把 OTLP exporter 指向自家 Collector / 商業 APM，驗證接收完整性。
  • 裁減服務：只留代表性的 3–5 個服務，做為 CI 流程的整合測試素材。
  • 加入自家 instrumentation：把自家公司寫的 instrumentation library 注入 Demo 應用，驗證跨語言支援。
  • 故障情境擴充：用 flagd 加入自家業務常見的故障模式（資料庫連線池耗盡、外部 API 雪崩…）。

Fork 後維持與上游 sync 的最佳實踐：

# 把上游加為 remote
git remote add upstream https://github.com/open-telemetry/opentelemetry-demo.git

# 定期 rebase 上游 main
git fetch upstream
git checkout main
git rebase upstream/main

# 自家修改放在獨立 branch，方便重新 apply
git checkout -b custom/my-org-changes

第 7 章 Demo Telemetry 解讀 開發者DevOpsSRE#

7.1 Collector Data Flow Dashboard

Demo 內建一個叫 Collector Data Flow Dashboard 的 Grafana 儀表板，這是 SRE / DevOps 必看的第一站——它告訴你 Collector 自己的健康狀態：

Panel監測什麼異常代表
otelcol_receiver_accepted_* Collector 接到的 spans / metric points / log records 速率 掉到 0：上游應用斷送或網路斷
otelcol_receiver_refused_* Collector 拒收的數量 非 0：受 memory_limiter 觸發或格式錯誤
otelcol_processor_batch_* 批次處理的延遲與大小 批次飆大：下游慢，可能要擴容
otelcol_exporter_sent_* 送到後端的成功量 遠低於 receiver_accepted：中間有資料流失
otelcol_exporter_send_failed_* 送到後端的失敗量 非 0：後端拒收 / 認證錯 / 格式錯
otelcol_exporter_queue_size 退流隊列大小 持續增長：後端速度跟不上，將觸發背壓
✅ 觀察自家 Collector 也用同一組指標

這份 dashboard 在 Demo 上是學習用，但同一組指標放到 prod 環境就是 SRE 的核心儀表板。第五篇 Collector 章會把這些指標的查詢 PromQL 完整列出。

7.2 Trace Coverage：誰在發 spans？

Demo 文件裡的 Trace Coverage 矩陣告訴你每個服務目前對 trace 的支援程度：是用 zero-code 自動 instrument、還是有 manual span、有沒有用 SDK 的 batch processor 等等。

實作面，每個服務的 span 模式大致分三類：

模式典型代表特徵
純 Zero-code Recommendation（Python opentelemetry-instrument） 不改程式，agent 自動產生 HTTP/gRPC server/client 與 DB span
Library + Manual hybrid Checkout（Go）、Frontend（TS） 用 instrumentation library 接住框架層，再手寫 business span（如 place-order）
純 Manual Currency（C++）、Payment（JavaScript） 每個 span 都是程式碼 tracer.Start() 出來的

  • Email 是 fire-and-forget，會 block 結帳；正式環境通常會改成非同步。

7.3 Metric Coverage：誰在發指標？

Demo 各服務發的 metric 大致分三類：

類別例子來源
HTTP/gRPC server & client http.server.request.duration、rpc.client.duration 由各語言的 instrumentation library 自動產生
Runtime metrics JVM 的 jvm.memory.used、Go 的 process.runtime.go.goroutines 各語言 SDK 內建 Resource Detector + Runtime instrumentation
Business metrics（手寫） app.orders.placed、app.payment.errors 各服務以 OTel API 手寫
Span Metrics（衍生） traces.span.metrics.duration 由 Collector 的 Span Metrics Connector 從 traces 衍生

這對自家系統設計也是個好範本：你的 RED metrics（Rate / Error / Duration）不必每個服務都重寫，可以由 Collector 從 traces 衍生；只有真正業務語義的指標（訂單數、付款失敗率）才需要手寫。

7.4 Log Coverage：誰在發 logs？

Demo 各語言的 log 模式：

  • Java、Python、JavaScript、.NET、Ruby：透過 OTel Logs Bridge 把現有 logger（log4j、logging、winston、Microsoft.Extensions.Logging、ruby-logger）的 log record 轉成 OTLP 送出。
  • Go：使用 OTel Go 的 logs SDK 直接寫（也可橋 slog）。
  • Rust：經 tracing crate 接 OTel exporter。

所有 log record 都會自動帶上當時的 SpanContext（trace_id / span_id），所以在 OpenSearch / Grafana 裡可以這樣查： 

# 在 OpenSearch 查某個 trace 期間的所有 logs
GET _search
{
  "query": {
    "term": { "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736" }
  },
  "sort": [{ "@timestamp": "asc" }]
}

這正是 OTel 三訊號 correlate 的價值——傳統 ELK + APM 兩套系統時，這個查詢非常難做。

7.5 Manual Span Attributes 對照

Demo 文件有一個叫 Manual Span Attributes 的對照表，列出每個服務手動加上 span 的業務維度屬性。它示範一個關鍵原則：

遵循 SemConv 規定的標準屬性（http.*、db.*、rpc.*），這些通常已由 instrumentation library 自動補。但業務屬性（app.cart.items、app.user.id）必須手寫，且應遵循 app.* 命名空間。

服務業務屬性範例用途
Checkoutapp.order.id、app.order.amount查特定訂單的 trace
Cartapp.cart.items.count分析購物車大小與延遲關係
Product Catalogapp.product.id、app.product.name商品熱度分析
Paymentapp.payment.card_type（無敏感資料）不同卡別的付款失敗率
Recommendationapp.recommendation.cache_enabled故障情境用
⚠️ 不要把 PII 放進 attributes

span attributes 會被送到後端、被儲存在搜尋系統、被各種 dashboard 引用。絕對不要放身分證、信用卡號、電話、email 等個資。Demo 故意設計成只放 card_type 而非卡號，是個好範例。第七篇〈安全性〉會深入。

7.6 Feature Flags 與記憶體洩漏實戰

Demo 內建幾個故障情境，最經典的是 recommendationCacheFailure。它示範如何用 metrics + traces 雙視角找出記憶體洩漏。

場景設計

Recommendation Service 是 Python 寫的。當 recommendationCacheFailure flag 打開時，會無限制累積 cache 條目（沒做 eviction），導致：

  1. 記憶體單調上升 → 觸發 OOM 或 GC 風暴。
  2. 對 Recommendation 的 RPC 越來越慢（cache lookup 在大 dict 上 O(n)）。
  3. 連帶拖慢 Frontend 對 Recommendation 的 gRPC 呼叫。

這個流程示範了 OTel 三訊號合作的價值：

  • Metrics 告訴你「壞了」：哪個服務 SLI 異常。
  • Traces 告訴你「在哪裡壞」：跨服務看到瓶頸在哪一個 span。
  • Logs 告訴你「為什麼壞」：具體錯誤訊息、變數值、stack trace。

7.7 Tail Sampling 範例：service.criticality

Demo 也提供一個進階的 Tail Sampling 範例設定，示範如何用 Collector 的 tail_sampling processor，根據服務關鍵性（service.criticality）做不同採樣率的決策： 

# 簡化版的 tail sampling 設定
processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 50000
    expected_new_traces_per_sec: 10
    policies:
      # 1. critical 服務的 trace 一律保留
      - name: critical-services
        type: string_attribute
        string_attribute:
          key: service.criticality
          values: [critical]

      # 2. 有錯誤的 trace 一律保留
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }

      # 3. 慢 trace（>1s）一律保留
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }

      # 4. 其他正常 trace 抽 10%
      - name: probabilistic
        type: probabilistic
        probabilistic: { sampling_percentage: 10 }

這個設定組合的效果是：不漏掉任何問題，但成本可控。是進入正式環境必經的成熟度。第五篇 Collector 章會深入 OTTL 與 sampling policies 寫法。
