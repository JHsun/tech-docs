第 12 章 Go 完整教學 開發者#

12.1 Go OTel 全景與設計哲學

Go OTel 跟其他語言最大的差異：沒有真正成熟的 zero-code agent。Go 沒有 runtime monkey-patch、沒有 bytecode 改寫，所以幾乎所有 Go 服務都走「純 SDK + instrumentation library + 手寫 spans」路線。這也意味著 Go 是 OTel API 設計理念貫徹得最徹底的語言。

套件 module用途
go.opentelemetry.io/otelAPI（介面層）
go.opentelemetry.io/otel/sdkSDK（實作層）
go.opentelemetry.io/otel/exporters/otlp/...OTLP 各種 exporter
go.opentelemetry.io/otel/exporters/stdout/...stdout exporter（debug 用）
go.opentelemetry.io/contrib/instrumentation/...各 framework 的 instrumentation library
go.opentelemetry.io/contrib/propagators/...各種 propagator（B3、Jaeger、AWS X-Ray…）
📌 為什麼 Go 是「functional options」風格

OTel Go 的所有 builder 方法都是 functional options，例如 trace.NewTracerProvider(trace.WithBatcher(exp))。這種風格適合 Go 沒有 method overloading 的語言特性，並能保持 API 向後相容（新增選項不會破壞既有呼叫）。閱讀 OTel Go 程式碼時要習慣這種 pattern。

12.3 SDK 初始化（標準 setupOTelSDK 模板）

OTel Go 官方範本叫 setupOTelSDK。它的設計重點：把所有 shutdown 函式集中管理，回傳一個 closure，呼叫端只要 defer shutdown(ctx)。

// otel.go
package main

import (
	"context"
	"errors"
	"time"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/exporters/otlp/otlplog/otlploggrpc"
	"go.opentelemetry.io/otel/exporters/otlp/otlpmetric/otlpmetricgrpc"
	"go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
	"go.opentelemetry.io/otel/log/global"
	"go.opentelemetry.io/otel/propagation"
	sdklog "go.opentelemetry.io/otel/sdk/log"
	sdkmetric "go.opentelemetry.io/otel/sdk/metric"
	"go.opentelemetry.io/otel/sdk/resource"
	sdktrace "go.opentelemetry.io/otel/sdk/trace"
	semconv "go.opentelemetry.io/otel/semconv/v1.30.0"
)

func setupOTelSDK(ctx context.Context) (shutdown func(context.Context) error, err error) {
	var shutdownFuncs []func(context.Context) error

	shutdown = func(ctx context.Context) error {
		var err error
		for _, fn := range shutdownFuncs {
			err = errors.Join(err, fn(ctx))
		}
		shutdownFuncs = nil
		return err
	}

	handleErr := func(inErr error) {
		err = errors.Join(inErr, shutdown(ctx))
	}

	// Resource: 描述「誰在發 telemetry」
	res, err := resource.Merge(
		resource.Default(),
		resource.NewWithAttributes(
			semconv.SchemaURL,
			semconv.ServiceName("checkout-svc"),
			semconv.ServiceVersion("1.4.2"),
			semconv.DeploymentEnvironmentName("prod"),
		),
	)
	if err != nil {
		handleErr(err)
		return
	}

	// Propagator
	otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
		propagation.TraceContext{},
		propagation.Baggage{},
	))

	// Trace
	traceExporter, err := otlptracegrpc.New(ctx,
		otlptracegrpc.WithEndpoint("collector:4317"),
		otlptracegrpc.WithInsecure(),
	)
	if err != nil {
		handleErr(err)
		return
	}
	tp := sdktrace.NewTracerProvider(
		sdktrace.WithBatcher(traceExporter,
			sdktrace.WithBatchTimeout(2*time.Second)),
		sdktrace.WithResource(res),
		sdktrace.WithSampler(sdktrace.ParentBased(
			sdktrace.TraceIDRatioBased(0.1),
		)),
	)
	shutdownFuncs = append(shutdownFuncs, tp.Shutdown)
	otel.SetTracerProvider(tp)

	// Metric
	metricExporter, err := otlpmetricgrpc.New(ctx,
		otlpmetricgrpc.WithEndpoint("collector:4317"),
		otlpmetricgrpc.WithInsecure(),
	)
	if err != nil {
		handleErr(err)
		return
	}
	mp := sdkmetric.NewMeterProvider(
		sdkmetric.WithReader(sdkmetric.NewPeriodicReader(metricExporter,
			sdkmetric.WithInterval(60*time.Second))),
		sdkmetric.WithResource(res),
	)
	shutdownFuncs = append(shutdownFuncs, mp.Shutdown)
	otel.SetMeterProvider(mp)

	// Log
	logExporter, err := otlploggrpc.New(ctx,
		otlploggrpc.WithEndpoint("collector:4317"),
		otlploggrpc.WithInsecure(),
	)
	if err != nil {
		handleErr(err)
		return
	}
	lp := sdklog.NewLoggerProvider(
		sdklog.WithProcessor(sdklog.NewBatchProcessor(logExporter)),
		sdklog.WithResource(res),
	)
	shutdownFuncs = append(shutdownFuncs, lp.Shutdown)
	global.SetLoggerProvider(lp)

	return shutdown, nil
}

呼叫端：

// main.go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	shutdown, err := setupOTelSDK(ctx)
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		if err := shutdown(context.Background()); err != nil {
			log.Printf("OTel shutdown failed: %v", err)
		}
	}()

	// ... 你的 server 邏輯 ...
}
⚠️ Resource Merge 的 schema URL 衝突

resource.Merge() 要求兩邊的 SchemaURL 一致或一邊為空。如果你使用了多個 resource detector（GCP detector、自家 detector），它們的 SchemaURL 可能不一致，merge 會失敗。解法：統一固定到一個 SemConv 版本，或用 resource.New(...) 重新組裝。

12.4 用 API 寫 Trace

import (
	"context"
	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/attribute"
	"go.opentelemetry.io/otel/codes"
	"go.opentelemetry.io/otel/trace"
)

var tracer = otel.Tracer("github.com/acme/checkout-svc")

func PlaceOrder(ctx context.Context, orderID string) (Order, error) {
	ctx, span := tracer.Start(ctx, "place-order",
		trace.WithSpanKind(trace.SpanKindInternal),
		trace.WithAttributes(
			attribute.String("app.order.id", orderID),
		),
	)
	defer span.End()

	if err := validate(ctx, orderID); err != nil {
		span.RecordError(err)
		span.SetStatus(codes.Error, err.Error())
		return Order{}, err
	}
	if err := charge(ctx, orderID); err != nil {
		span.RecordError(err)
		span.SetStatus(codes.Error, err.Error())
		return Order{}, err
	}

	span.SetStatus(codes.Ok, "")
	return Order{ID: orderID}, nil
}

Go 風格的關鍵點

  • ctx 必須一路傳遞：Go 的 context 是 immutable 樹狀結構，tracer.Start 會回傳新的 ctx，下游函式必須收到這個新 ctx 才能成為 child span。
  • defer span.End()：Go 沒有 try-finally，用 defer 確保結束。
  • Status：error 用 codes.Error，正常完成 codes.Ok（也可省略）。

12.6 用 API 寫 Log（slog 橋接）

Go 1.21+ 內建 log/slog。OTel 提供 bridge 把 slog 寫入的 log 轉成 OTLP：

import (
	"log/slog"
	"go.opentelemetry.io/contrib/bridges/otelslog"
)

logger := otelslog.NewLogger("github.com/acme/checkout-svc")
slog.SetDefault(logger)

slog.InfoContext(ctx, "Order placed",
	"order.id", orderID,
	"amount", amount,
)

關鍵：用 InfoContext 而非 Info，這樣 logger 才能從 ctx 取得 trace_id / span_id 並注入 log record。

12.9 Context Propagation 與 goroutine

Go 的 context 與 goroutine 互動有幾個關鍵原則：

  1. 新 goroutine 必須繼承 ctx：go func() { do(ctx) }()，不能用全域 context.Background()。
  2. 長時間 goroutine 應 detach：用 context.WithoutCancel(ctx) 保留 trace context 但不繼承 cancellation。
// ❌ 錯誤：父 request 結束時 ctx 被 cancel，背景工作炸了
go processInBackground(ctx)

// ✅ 正確：保留 trace context 但取消 cancellation
go processInBackground(context.WithoutCancel(ctx))

跨服務 propagation 已由 instrumentation library 處理

用 otelhttp / otelgrpc 時，W3C Trace Context header 已自動 inject / extract。手寫只在自家 RPC 框架時才需要。

12.10 Go 常見陷阱與最佳實踐

陷阱原因解法
Span 沒送出程式直接 os.Exit() 或 panic 未捕捉main 必 defer shutdown(ctx)
Child span 變 root沒有把 tracer.Start 回傳的 ctx 傳下去嚴格遵守 ctx 鏈
Goroutine 後 trace 斷新 goroutine 沒帶 ctxgo func() { do(ctx) }()
背景工作意外取消父 request ctx 被 cancelcontext.WithoutCancel(ctx)
Logger 沒 trace_id用了 slog.Info 而非 InfoContext一律用 *Context 版本
Resource Merge 失敗多 detector 的 SchemaURL 衝突固定一個 SemConv 版本
Lambda / 短命 process 丟資料Batch processor 還沒送就退出用 SimpleProcessor，或退出前 ForceFlush
✅ Go 最佳實踐 5 條
  1. 用 setupOTelSDK 標準模板，shutdown 集中管理
  2. 所有函式簽名第一參數一律 ctx context.Context
  3. HTTP / gRPC / SQL 一律用 instrumentation library，不要手寫 server / client middleware
  4. 用 otelslog 橋接 slog，InfoContext 取代 Info
  5. 業務 metric 用 app. prefix，避免和 SemConv 衝突

13.2 Node.js SDK 初始化

最簡寫法：用 NodeSDK 一站式初始化。

// instrumentation.ts (TypeScript)
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-grpc';
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-grpc';
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-grpc';
import { PeriodicExportingMetricReader } from '@opentelemetry/sdk-metrics';
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs';
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node';
import { resourceFromAttributes } from '@opentelemetry/resources';
import {
  ATTR_SERVICE_NAME,
  ATTR_SERVICE_VERSION,
} from '@opentelemetry/semantic-conventions';

const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    [ATTR_SERVICE_NAME]: 'payment-svc',
    [ATTR_SERVICE_VERSION]: '1.4.2',
    'deployment.environment.name': 'prod',
  }),
  traceExporter: new OTLPTraceExporter({ url: 'http://collector:4317' }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({ url: 'http://collector:4317' }),
    exportIntervalMillis: 60000,
  }),
  logRecordProcessors: [
    new BatchLogRecordProcessor(
      new OTLPLogExporter({ url: 'http://collector:4317' })
    ),
  ],
  instrumentations: [getNodeAutoInstrumentations({
    // 個別套件可微調
    '@opentelemetry/instrumentation-fs': { enabled: false }, // 太吵
  })],
});

sdk.start();

process.on('SIGTERM', () => {
  sdk.shutdown()
    .then(() => console.log('OTel terminated'))
    .catch(err => console.error('OTel shutdown error', err))
    .finally(() => process.exit(0));
});

# ESM (Node 18+)

13.3 ESM 與 CommonJS 的差異

JS 生態 OTel 最痛的地雷。

環境載入方式OTel 注意
CommonJS（require）--requireOTel hook 用 require-in-the-middle，原生支援
ESM（import）--import（Node 18+）需 import-in-the-middle，OTel 2024 起正式支援
TypeScript（編譯為 CJS）同 CommonJS無問題
TypeScript（編譯為 ESM）同 ESM需注意 import-in-the-middle 版本
⚠️ "type": "module" 專案

package.json 有 "type": "module" 時，必須用 --import 而非 --require，且 instrumentation file 副檔名要是 .mjs（或 .js 配合 "type": "module"）。錯誤組合會讓 instrumentation 無聲失效——應用跑得起來，但什麼 telemetry 都沒有。

13.4 用 API 寫 Trace / Metric / Log

Trace

import { trace, SpanStatusCode, SpanKind } from '@opentelemetry/api';

const tracer = trace.getTracer('com.acme.payment', '1.4.2');

export async function chargePayment(orderId: string, amount: number) {
  return tracer.startActiveSpan('charge-payment',
    { kind: SpanKind.INTERNAL, attributes: { 'app.order.id': orderId, 'app.amount': amount } },
    async (span) => {
      try {
        const result = await callPaymentGateway(orderId, amount);
        span.setStatus({ code: SpanStatusCode.OK });
        return result;
      } catch (e: any) {
        span.recordException(e);
        span.setStatus({ code: SpanStatusCode.ERROR, message: e.message });
        throw e;
      } finally {
        span.end();
      }
    }
  );
}

13.5 Context Propagation 與 async

JS 的 OTel 用 AsyncLocalStorage（Node.js）儲存 context，自動隨 Promise / async function 流動。但兩個常見坑：

  1. EventEmitter：跨 emit 的 listener 不一定保留 context。
  2. setTimeout / setInterval：在 timer callback 內 context 可能丟失。
import { context } from '@opentelemetry/api';

// 顯式綁定 context 到 callback
const ctx = context.active();
setTimeout(() => {
  context.with(ctx, () => {
    // 這裡看得到外層 context
    doWork();
  });
}, 1000);

13.6 Browser SDK

瀏覽器環境的目標是 RUM（Real User Monitoring）：頁面載入、fetch / XHR、使用者互動。

// browser-instrumentation.ts
import { WebTracerProvider, BatchSpanProcessor } from '@opentelemetry/sdk-trace-web';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { ZoneContextManager } from '@opentelemetry/context-zone';
import { registerInstrumentations } from '@opentelemetry/instrumentation';
import { getWebAutoInstrumentations } from '@opentelemetry/auto-instrumentations-web';
import { resourceFromAttributes } from '@opentelemetry/resources';

const provider = new WebTracerProvider({
  resource: resourceFromAttributes({
    'service.name': 'frontend-app',
    'browser.platform': navigator.platform,
  }),
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({ url: 'https://collector.example.com/v1/traces' })
    ),
  ],
});

provider.register({
  contextManager: new ZoneContextManager(),
});

registerInstrumentations({
  instrumentations: getWebAutoInstrumentations({
    '@opentelemetry/instrumentation-document-load': {},
    '@opentelemetry/instrumentation-user-interaction': {},
    '@opentelemetry/instrumentation-fetch': {
      propagateTraceHeaderCorsUrls: [/^https:\/\/api\.example\.com/],
    },
  }),
});
⚠️ CORS 與 Trace Header

跨域 fetch 預設不會送 traceparent header（瀏覽器 CORS 限制）。要：(1) 在 propagateTraceHeaderCorsUrls 列出允許的域名 (2) 後端 API 的 CORS 回應允許 traceparent 與 tracestate headers。沒設好就會出現「RUM 端有 trace、後端 server 端有 trace，但兩邊接不起來」的詭異現象。

13.7 Serverless（Lambda / Cloudflare Workers）

AWS Lambda — 推薦用 OTel Lambda Layer（zero-code）

# serverless.yml
functions:
  myFunction:
    handler: src/handler.main
    layers:
      - arn:aws:lambda:us-east-1:184161586896:layer:opentelemetry-nodejs-0_13_0:1
    environment:
      AWS_LAMBDA_EXEC_WRAPPER: /opt/otel-handler
      OTEL_SERVICE_NAME: my-function
      OTEL_EXPORTER_OTLP_ENDPOINT: https://collector.example.com

Cloudflare Workers / Vercel Edge

Edge runtime 不支援 Node.js API（無 AsyncLocalStorage、無 batch timer）。需用：

  • @microlabs/otel-cf-workers（Cloudflare 專用社群方案）
  • SimpleSpanProcessor 而非 Batch
  • 每個 invocation 獨立 flush

13.8 JS 常見陷阱與最佳實踐

陷阱原因解法
ESM 專案 instrumentation 無效用了 --require改 --import
fs instrumentation 噪音爆量每個檔案讀寫都產 span關掉 @opentelemetry/instrumentation-fs
Lambda 丟資料BatchProcessor 沒送出用 SimpleSpanProcessor 或 lambda layer
Browser 跨域 trace 斷CORS 沒放行 traceparent後端 CORS 設定 + propagateTraceHeaderCorsUrls
setTimeout 後 context 丟失Timer callback 不繼承 AsyncLocalStoragecontext.with(ctx, fn) 包起來
多重 SDK 衝突同時裝多個 framework 的 OTel SDK（如 Next.js + 自家 SDK）只留一個入口
OTel module 版本不一致npm 平行版本用 npm dedupe 或 yarn resolutions
✅ JS 最佳實踐 5 條
  1. 把 instrumentation 集中在一個 instrumentation.{js,mjs,ts} 檔，全程式入口最先載入
  2. 關掉吵的 instrumentation（fs、有時 net）
  3. Browser 端先確認 CORS / propagateTraceHeaderCorsUrls 才能接到後端
  4. Lambda / Workers 用對應的 serverless 模式（layer 或專用套件）
  5. npm dedupe 避免多版本 OTel API 共存

本章對 Java／Python／Go／JS 以外的語言做精簡介紹：每種語言給入門路徑、特色、官方文件入口。實作細節以官方為準。

14.1 .NET（建議 native + 少量 SDK code）

.NET 對 OTel 是「原生最深」的語言。Microsoft 把 OTel 視為 .NET 的標準 telemetry API，新版 ASP.NET Core、HttpClient、SqlClient、StackExchange.Redis 都已 native 支援，無需 instrumentation library wrapper。

// Program.cs (ASP.NET Core 9)
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;
using OpenTelemetry.Metrics;
using OpenTelemetry.Logs;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r
        .AddService("cart-svc", serviceVersion: "1.4.2"))
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("Cart")  // 自家 ActivitySource
        .AddOtlpExporter())
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()
        .AddOtlpExporter())
    .WithLogging(l => l.AddOtlpExporter());

var app = builder.Build();
app.Run();

業務 span 用 System.Diagnostics.ActivitySource（OTel-compatible）：

private static readonly ActivitySource ActivitySource = new("Cart");

public Order PlaceOrder(string orderId)
{
    using var activity = ActivitySource.StartActivity("place-order");
    activity?.SetTag("app.order.id", orderId);
    // ...
}

官方入口：opentelemetry.io/docs/languages/dotnet/

14.2 Ruby

Ruby OTel 的標準路徑：opentelemetry-sdk + opentelemetry-instrumentation-all（一個 meta-gem 包含所有支援的 instrumentation）。

# Gemfile
gem 'opentelemetry-sdk'
gem 'opentelemetry-exporter-otlp'
gem 'opentelemetry-instrumentation-all'
# config/initializers/opentelemetry.rb (Rails)
require 'opentelemetry/sdk'
require 'opentelemetry/instrumentation/all'

OpenTelemetry::SDK.configure do |c|
  c.service_name = 'email-svc'
  c.use_all  # 啟用所有可用的 instrumentation
end

Ruby 的特色是 use_all 自動偵測——它會掃描已 require 的 gem，啟用對應 instrumentation（Rails、ActiveRecord、Redis、Sidekiq、Net::HTTP…）。

14.3 PHP

PHP 的 OTel SDK 經 Composer 安裝；zero-code 經 PHP extension（已在第三篇講過）。Code-based 範例：

composer require \
  open-telemetry/sdk \
  open-telemetry/exporter-otlp \
  open-telemetry/sem-conv
<?php
use OpenTelemetry\API\Globals;
use OpenTelemetry\SDK\Trace\TracerProvider;
use OpenTelemetry\Contrib\Otlp\SpanExporter;
use OpenTelemetry\SDK\Trace\SpanProcessor\BatchSpanProcessor;
use OpenTelemetry\SDK\Common\Time\ClockFactory;

$tracerProvider = TracerProvider::builder()
    ->addSpanProcessor(

        )

    ->build();

$tracer = $tracerProvider->getTracer('com.acme.quote');
$span = $tracer->spanBuilder('get-quote')->startSpan();
try {
    // ...
} finally {
    $span->end();
}

14.4 Rust

Rust OTel 透過 opentelemetry crate 與 opentelemetry_sdk。Rust 的特色是與 tracing crate 深度整合：

# Cargo.toml
[dependencies]
opentelemetry = "0.27"
opentelemetry_sdk = { version = "0.27", features = ["rt-tokio"] }
opentelemetry-otlp = { version = "0.27", features = ["grpc-tonic"] }
tracing = "0.1"
tracing-subscriber = "0.3"
tracing-opentelemetry = "0.28"
use opentelemetry::trace::TracerProvider as _;
use opentelemetry_sdk::trace::TracerProvider;
use tracing_subscriber::layer::SubscriberExt;

let exporter = opentelemetry_otlp::SpanExporter::builder()
    .with_tonic()
    .with_endpoint("http://collector:4317")
    .build()?;

let provider = TracerProvider::builder()
    .with_batch_exporter(exporter, opentelemetry_sdk::runtime::Tokio)
    .build();

let tracer = provider.tracer("shipping");
let telemetry = tracing_opentelemetry::layer().with_tracer(tracer);

tracing_subscriber::registry()
    .with(telemetry)
    .init();

// 之後正常用 tracing
tracing::info!(order_id = "123", "shipping order");

Rust 的成熟度逐年上升，2025 起 tracing-opentelemetry 已是事實標準。

第 15 章 SDK 設定（跨語言通用） 開發者DevOps#

15.1 環境變數標準總覽

OTel 規格定義了一組跨語言一致的環境變數，所有官方 SDK 都支援這套。這是部署 OTel 應用最重要的事——一致的設定方式，跨團隊跨語言。

(A) 一般通用（General SDK）

環境變數說明預設
OTEL_SDK_DISABLED關閉整個 SDK（API 變 no-op）false
OTEL_SERVICE_NAMEservice.name（必填）—
OTEL_RESOURCE_ATTRIBUTES逗號分隔的 resource attributes—
OTEL_LOG_LEVELSDK 自身 log 等級info
OTEL_PROPAGATORS啟用的 propagator，預設 tracecontext,baggagetracecontext,baggage

(B) Trace 相關

環境變數說明
OTEL_TRACES_EXPORTERotlp / console / none
OTEL_TRACES_SAMPLER採樣器類型（如 parentbased_traceidratio）
OTEL_TRACES_SAMPLER_ARG採樣器參數（如 0.1）
OTEL_BSP_*BatchSpanProcessor 各參數（max queue、scheduled delay…）
OTEL_SPAN_ATTRIBUTE_COUNT_LIMIT單一 span 最多多少 attributes
OTEL_SPAN_EVENT_COUNT_LIMIT單一 span 最多多少 events

(C) Metric 相關

環境變數說明
OTEL_METRICS_EXPORTERotlp / prometheus / console / none
OTEL_METRIC_EXPORT_INTERVAL匯出間隔毫秒（預設 60000）
OTEL_METRIC_EXPORT_TIMEOUT匯出 timeout（預設 30000ms）
OTEL_EXPORTER_PROMETHEUS_HOSTPrometheus exporter 監聽 host
OTEL_EXPORTER_PROMETHEUS_PORTPrometheus exporter 監聽 port

(D) Logs 相關

環境變數說明
OTEL_LOGS_EXPORTERotlp / console / none
OTEL_BLRP_*BatchLogRecordProcessor 各參數

15.2 OTLP Exporter 設定細節

環境變數說明預設
OTEL_EXPORTER_OTLP_ENDPOINTCollector 位址http://localhost:4318（HTTP）/ http://localhost:4317（gRPC）
OTEL_EXPORTER_OTLP_PROTOCOLgrpc / http/protobuf / http/jsonhttp/protobuf（規格定義；部分 SDK 預設 grpc）
OTEL_EXPORTER_OTLP_HEADERS逗號分隔的 header（如 api-key=xxx,team=yyy）—
OTEL_EXPORTER_OTLP_TIMEOUTsend timeout 毫秒10000
OTEL_EXPORTER_OTLP_COMPRESSIONgzip / nonenone
OTEL_EXPORTER_OTLP_CERTIFICATETLS CA 憑證路徑—
OTEL_EXPORTER_OTLP_CLIENT_KEYTLS client key—
OTEL_EXPORTER_OTLP_CLIENT_CERTIFICATETLS client cert—

分訊號獨立設定

每個訊號類型可獨立指定 endpoint：

# Traces 走 gRPC，Metrics 走 HTTP
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://collector:4317
export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://prometheus:9090/api/v1/otlp
export OTEL_EXPORTER_OTLP_METRICS_PROTOCOL=http/protobuf
⚠️ gRPC vs HTTP 預設不一致

OTel 規格把 HTTP/protobuf 定為預設 protocol，但歷史上 Java SDK 預設 gRPC、Python / JS 預設 HTTP。如果應用收不到資料，先確認 protocol 與 endpoint 端口是否相符（gRPC 4317、HTTP 4318）。

15.3 Declarative Configuration（YAML）

2024–2025 OTel 推出了新的Declarative Configuration規格（otelcol-config-like 的 YAML 格式），目標是用一份 YAML 檔同時設定所有 SDK 行為，跨語言一致。狀態：規格穩定（2025 後半）；各語言實作 GA 進行中。

# otel-config.yaml
file_format: "0.3"

resource:
  attributes:
    - name: service.name
      value: checkout-svc
    - name: service.version
      value: 1.4.2
    - name: deployment.environment.name
      value: prod

tracer_provider:
  processors:
    - batch:
        exporter:
          otlp:
            protocol: grpc
            endpoint: http://collector:4317
        scheduled_delay: 2000
  sampler:
    parent_based:
      root:
        trace_id_ratio_based:
          ratio: 0.1

meter_provider:
  readers:
    - periodic:
        interval: 60000
        exporter:
          otlp:
            protocol: grpc
            endpoint: http://collector:4317

logger_provider:
  processors:
    - batch:
        exporter:
          otlp:
            protocol: grpc
            endpoint: http://collector:4317

propagators:
  composite:
    - tracecontext
    - baggage

啟用方式：

# Java（透過 OTEL_EXPERIMENTAL_CONFIG_FILE）
export OTEL_EXPERIMENTAL_CONFIG_FILE=/etc/otel/otel-config.yaml
java -javaagent:opentelemetry-javaagent.jar -jar app.jar

# 其他語言：以官方文件為準（成熟度依語言而異）
✅ Declarative Config 為什麼值得關注

當公司的 OTel 部署橫跨 Java / Python / Go / Node.js 時，最大的痛是每種語言的設定 API 都不一樣。Declarative Config 解決這個問題，平台團隊可以發一份 YAML 模板給所有團隊套用。即便 2026 年某些語言實作仍在 Beta，現在開始把它納入內部標準仍是值得的投資。

15.4 跨語言一致性檢查清單

當公司有多語言服務時，這份 checklist 確保所有服務發出的 telemetry 在後端能被正確聚合：

項目檢查重點
Resource attributes每個服務都有 service.name、service.version、deployment.environment.name
SemConv 屬性命名所有 HTTP / DB / Messaging span 屬性遵循同一版 SemConv（建議鎖定 1.41.0+）
Propagator所有服務一律 tracecontext,baggage（不要混 b3 / jaeger 除非有特殊需求）
OTLP Endpoint統一指向同一 Collector
Sampler採樣率一致；用 parent-based 確保上下游一致決策
Time precision全部用 nanosecond 精度（OTel 預設即此）
業務 attribute prefix全公司統一用 app. 或自家 prefix（如 acme.）
Histogram bucket boundaries跨服務的 latency histogram 用相同 bucket 邊界，方便比較
Logs trace correlation每種語言都已啟用 log → trace_id 注入
