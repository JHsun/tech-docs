22.2 Getting Started：從零部署

從乾淨的 K8s 集群開始，到應用發出第一筆 telemetry，可以用四步驟：

步驟 1：安裝 cert-manager（Operator 依賴）

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml

# 等到 webhook 就緒
kubectl -n cert-manager wait --for=condition=Available deployment --all --timeout=180s

步驟 2：安裝 OTel Operator

helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

helm install opentelemetry-operator open-telemetry/opentelemetry-operator \
  -n opentelemetry-operator-system --create-namespace \
  --set manager.collectorImage.repository=otel/opentelemetry-collector-k8s

步驟 3：部署 Agent DaemonSet + Gateway

# agent.yaml
apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: otel-agent
  namespace: observability
spec:
  mode: daemonset
  image: otel/opentelemetry-collector-k8s:0.150.0

  # DaemonSet 需要的 host volume（讀 container log）
  volumes:
    - name: varlogpods
      hostPath: { path: /var/log/pods }
    - name: varlibdockercontainers
      hostPath: { path: /var/lib/docker/containers }
  volumeMounts:
    - name: varlogpods
      mountPath: /var/log/pods
      readOnly: true
    - name: varlibdockercontainers
      mountPath: /var/lib/docker/containers
      readOnly: true

  config:
    receivers:
      otlp:
        protocols:
          grpc: { endpoint: 0.0.0.0:4317 }
          http: { endpoint: 0.0.0.0:4318 }
      hostmetrics:
        collection_interval: 30s
        scrapers: { cpu: {}, memory: {}, disk: {}, network: {}, load: {} }
      kubeletstats:
        collection_interval: 30s
        auth_type: serviceAccount
        endpoint: ${env:K8S_NODE_IP}:10250
        insecure_skip_verify: true
      filelog:
        include: [/var/log/pods/*/*/*.log]
        start_at: end
        include_file_path: true
        operators:
          - type: container
            id: container-parser

    processors:
      memory_limiter:
        check_interval: 5s
        limit_percentage: 80
        spike_limit_percentage: 25
      k8sattributes:
        auth_type: serviceAccount
        passthrough: false
        extract:
          metadata: [k8s.namespace.name, k8s.pod.name, k8s.pod.uid, k8s.deployment.name, k8s.node.name]
        pod_association:
          - sources:
              - { from: resource_attribute, name: k8s.pod.ip }
          - sources:
              - { from: connection }
      batch:
        send_batch_size: 1024
        timeout: 10s

    exporters:
      otlp/gateway:
        endpoint: otel-gateway-collector.observability.svc:4317
        tls: { insecure: true }

    service:
      pipelines:
        traces:
          receivers:  [otlp]
          processors: [memory_limiter, k8sattributes, batch]
          exporters:  [otlp/gateway]
        metrics:
          receivers:  [otlp, hostmetrics, kubeletstats]
          processors: [memory_limiter, k8sattributes, batch]
          exporters:  [otlp/gateway]
        logs:
          receivers:  [otlp, filelog]
          processors: [memory_limiter, k8sattributes, batch]
          exporters:  [otlp/gateway]

22.3 Helm Charts 詳解（Collector / Demo / Operator）

OTel 維護三個官方 Helm chart：

Chart用途適用
opentelemetry-collector部署 Collector（不經 Operator）不用 Operator 的環境，或一次性部署
opentelemetry-operator安裝 Operator + CRDs大規模 / 多 cluster
opentelemetry-demo整套 Demo（17 服務 + Tempo + Prometheus + Grafana + Jaeger）培訓 / Demo / POC

opentelemetry-collector chart 的 mode 參數

helm install otel-agent open-telemetry/opentelemetry-collector \
  --set mode=daemonset \           # daemonset / deployment / statefulset
  --set image.repository=otel/opentelemetry-collector-k8s \
  --set presets.kubernetesAttributes.enabled=true \
  --set presets.hostMetrics.enabled=true \
  --set presets.kubeletMetrics.enabled=true \
  --set presets.logsCollection.enabled=true

那些 presets.* 開關會自動把 receivers / processors / RBAC / volume mounts 一起設好。新手用 preset，熟練後再寫完整 config。

22.4 K8s 重要 receiver 與 processor

元件用途RBAC 需求
k8sattributes processor 從 K8s API 取得 pod / deployment / namespace 元資料附加到 telemetry get/list/watch pods、namespaces、replicasets
kubeletstats receiver 從 kubelet :10250 拿 container / pod / volume 級別 metrics nodes/stats、nodes/proxy
k8s_cluster receiver 從 K8s API 拿 cluster-level 物件數量（pods、nodes 狀態） get/list/watch 大部分 core 資源
k8sobjects receiver 把 K8s 物件變動（events、deployments 變更）轉為 logs get/list/watch 對應資源
k8s_events receiver（已併入 k8sobjects） K8s events events
filelog receiver 讀 /var/log/pods/*/*/*.log 需 hostPath 掛載 + container parser operator
prometheus receiver + Target Allocator 取代 Prometheus server scrape nodes/metrics、ServiceMonitor / PodMonitor 監視

22.5 SemConv：K8s Resource Attributes

OTel SemConv 1.41 對 K8s 環境定義了一組標準 resource attributes：

屬性內容
k8s.cluster.name叢集名稱
k8s.cluster.uid叢集 UID（kube-system namespace 的 UID）
k8s.namespace.name命名空間
k8s.pod.namePod 名稱
k8s.pod.uidPod UID
k8s.pod.ipPod IP
k8s.deployment.nameDeployment 名稱
k8s.replicaset.nameReplicaSet 名稱
k8s.statefulset.nameStatefulSet
k8s.daemonset.nameDaemonSet
k8s.job.name / k8s.cronjob.nameJob / CronJob
k8s.node.name / k8s.node.uidNode 名稱／UID
k8s.container.name容器名稱
k8s.container.restart_count容器重啟次數

這些絕大多數由 k8sattributes processor 自動填，不用應用程式碼處理。

K8s 環境常見陷阱

症狀原因解法
k8sattributes 補不到屬性 RBAC 不足或 pod_association 規則不對 檢查 ClusterRoleBinding；確保 association 用 connection 或 k8s.pod.ip
Agent OOM 重啟 Filelog 抓 log 時把舊檔全讀一次；hostmetrics scrape 太頻繁 Filelog 用 start_at: end；scrape interval 至少 30s；memory_limiter 必設
Helm 升級 chart 失敗 CRD schema 改變但 chart upgrade 不會自動更新 CRD 升級前手動 kubectl apply 新 CRDs
Operator 改 config 後沒生效 Pod 沒重啟（修改 ConfigMap 不會自動 rolling restart） 用 kubectl rollout restart 或 Operator 的 configVersion 註解觸發
Auto-instrumentation 注入後 pod 起不來 init container 拉不到 instrumentation image（air-gapped 環境） Mirror image 到內部 registry
Prometheus scrape 重複 多 Agent 副本各自 scrape 啟用 Operator Target Allocator
Container log 含 ANSI 色碼 應用直接 print 帶顏色的 log Filelog operator 加 regex_parser 移除 ANSI escape

第 23 章 FaaS：AWS Lambda 與其他無伺服器 開發者DevOps#

23.1 FaaS 場景的特殊挑戰

FaaS（Function as a Service，無伺服器）跟一般服務的差異會影響 OTel 設計：

差異對 OTel 的影響
函式短命（毫秒到秒） BatchSpanProcessor 的 batch timeout 沒到就被殺，必須用 SimpleSpanProcessor 或在 handler 結束前 ForceFlush
沒有持久化 host 無法跑本地 Collector Agent
冷啟動敏感 OTel SDK 初始化會增加冷啟動延遲
Concurrency 模型不同 同一函式多 instance 平行跑
計費按用量 SDK overhead 會直接反映在帳單上
網路出口受限 VPC 內 Lambda 出口要走 NAT / VPC Endpoint

OTel 對 Lambda 提供三條路徑：Auto-Instrumentation Layer（最簡）、Manual Instrumentation（最彈性）、Lambda Collector Layer（local sidecar Collector）。

23.2 Lambda Auto-Instrumentation（Layer）

OTel 為 Lambda 各 runtime 發布了官方 Layer，安裝後零程式碼啟用：

# serverless.yml
service: checkout-service

provider:
  name: aws
  runtime: nodejs20.x
  region: us-east-1

functions:
  checkout:
    handler: src/handler.main
    layers:
      # OTel Lambda Layer ARN（按 region 取對應）
      - arn:aws:lambda:us-east-1:184161586896:layer:opentelemetry-nodejs-0_13_0:1
    environment:
      AWS_LAMBDA_EXEC_WRAPPER: /opt/otel-handler
      OTEL_SERVICE_NAME: checkout
      OTEL_RESOURCE_ATTRIBUTES: deployment.environment.name=prod,team=payments
      OTEL_EXPORTER_OTLP_ENDPOINT: https://collector.example.com
      OTEL_EXPORTER_OTLP_HEADERS: "api-key=${env:OTEL_API_KEY}"
      OTEL_TRACES_SAMPLER: parentbased_traceidratio
      OTEL_TRACES_SAMPLER_ARG: "1.0"  # Lambda 通常全採

關鍵：AWS_LAMBDA_EXEC_WRAPPER: /opt/otel-handler。這個環境變數指示 Lambda runtime 用 OTel wrapper 包裹原本的 handler，自動初始化 SDK 並追蹤呼叫。

各 runtime 的 Layer ARN（每 region 不同）

Layer ARN 會隨版本與 region 變動。實際使用時請從 opentelemetry-lambda releases 取得最新值。範本如下：

RuntimeLayer 名稱模式
Node.jsopentelemetry-nodejs-{ver}
Pythonopentelemetry-python-{ver}
Javaopentelemetry-javaagent-{ver}
Java（無 agent，用 Wrapper）opentelemetry-javawrapper-{ver}
Collector（無 SDK）opentelemetry-collector-{arch}-{ver}

23.3 Lambda Manual Instrumentation

當 Auto Layer 不夠彈性（要自家 Distro、預配置額外 instrumentation、特殊 sampler 邏輯）時，用 Manual：

// handler.ts (Node.js, manual)
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { SimpleSpanProcessor } from '@opentelemetry/sdk-trace-base';
import { AwsLambdaInstrumentation } from '@opentelemetry/instrumentation-aws-lambda';
import { AwsInstrumentation } from '@opentelemetry/instrumentation-aws-sdk';
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http';
import { resourceFromAttributes } from '@opentelemetry/resources';

const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    'service.name': process.env.AWS_LAMBDA_FUNCTION_NAME,
    'cloud.provider': 'aws',
    'cloud.region': process.env.AWS_REGION,
    'faas.name': process.env.AWS_LAMBDA_FUNCTION_NAME,
  }),
  // 注意：Lambda 用 SimpleSpanProcessor，不用 Batch
  spanProcessors: [
    new SimpleSpanProcessor(
      new OTLPTraceExporter({ url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT })
    ),
  ],
  instrumentations: [
    new AwsLambdaInstrumentation({
      // 抓 event payload 中特定欄位放 span
      requestHook: (span, info) => {
        span.setAttribute('faas.invocation.event_source', info.event?.source);
      },
    }),
    new AwsInstrumentation(),
    new HttpInstrumentation(),
  ],
});

sdk.start();

export const handler = async (event: any) => {
  // 你的業務邏輯
  return { statusCode: 200 };
};
⚠️ 為什麼 Lambda 不用 BatchSpanProcessor

BatchSpanProcessor 的 batch timeout 預設 5 秒，但 Lambda handler 結束後 runtime 馬上凍結 process（freeze），下次喚醒可能是新的 micro-VM。已收的 spans 在 freeze 中無法送出，下次喚醒時 SDK 狀態不一定保留。SimpleSpanProcessor 在每個 span end 時同步送出，避免這個問題（代價是 latency overhead）。

23.4 Lambda Collector Configuration

方法 3：在 Lambda 內跑 Collector Layer（local sidecar），SDK 送 OTLP 到 localhost:4317，Collector 再送外部後端。

適用：(1) 後端 endpoint 需要複雜 auth（OAuth、SigV4），(2) 想做本地 batch 與 retry，(3) 多函式共用同一 Collector config（透過 Layer）。

# 部署時加兩個 Layer
layers:
  - arn:aws:lambda:us-east-1:184161586896:layer:opentelemetry-nodejs-0_13_0:1
  - arn:aws:lambda:us-east-1:184161586896:layer:opentelemetry-collector-amd64-0_150_0:1

environment:
  AWS_LAMBDA_EXEC_WRAPPER: /opt/otel-handler
  OPENTELEMETRY_COLLECTOR_CONFIG_URI: /var/task/collector-config.yaml
  OTEL_EXPORTER_OTLP_ENDPOINT: http://localhost:4318
  OTEL_EXPORTER_OTLP_PROTOCOL: http/protobuf
# collector-config.yaml（與函式打包在一起）
receivers:
  otlp:
    protocols:
      http: { endpoint: localhost:4318 }

processors:
  decouple:   # Lambda 專用 processor，避免阻塞 handler
  batch:
    timeout: 100ms

exporters:
  otlphttp:
    endpoint: https://collector.example.com
    headers: { x-api-key: ${env:API_KEY} }

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [decouple, batch]
      exporters:  [otlphttp]
📌 decouple processor 是 Lambda 必備

Decouple processor 把 receiver 跟 exporter 解耦，讓 receiver 立刻 ack 給 SDK（handler 可以結束），exporter 在 freeze 之前盡量送出。沒它的話 SDK 會等 exporter 真的送完才返回，handler latency 大幅上升。

第 24 章 Client-side Apps：Web、iOS、Android 前端行動端#

24.1 Client-side Observability 是什麼，為什麼重要

傳統 observability 從 backend 開始。但使用者實際感受到的是端到端：頁面載入、按鈕點擊到回應、app 崩潰。Client-side OTel 把觀察點往前推到瀏覽器與 app。

OTel 對 client-side 提供三條官方路徑：

  1. Web：瀏覽器 JS（在第五篇 13.6 已介紹過架構，本章補完整 RUM 設定）
  2. iOS：OpenTelemetry-Swift
  3. Android：opentelemetry-android（針對 Android 特化）

Demo 中還有 React Native 範本，是混合 web 與行動端的應用模式。

24.2 Web RUM：完整設定

第五篇給過骨架，這裡補上 RUM 場景的完整設定：

// rum-instrumentation.ts
import { WebTracerProvider, BatchSpanProcessor } from '@opentelemetry/sdk-trace-web';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { ZoneContextManager } from '@opentelemetry/context-zone';
import { registerInstrumentations } from '@opentelemetry/instrumentation';
import { resourceFromAttributes } from '@opentelemetry/resources';

// 自動 instrumentation
import { DocumentLoadInstrumentation } from '@opentelemetry/instrumentation-document-load';
import { UserInteractionInstrumentation } from '@opentelemetry/instrumentation-user-interaction';
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch';
import { XMLHttpRequestInstrumentation } from '@opentelemetry/instrumentation-xml-http-request';
import { LongTaskInstrumentation } from '@opentelemetry/instrumentation-long-task';

// 產生 / 取得 session id
const sessionId = sessionStorage.getItem('otel-session-id') || crypto.randomUUID();
sessionStorage.setItem('otel-session-id', sessionId);

const provider = new WebTracerProvider({
  resource: resourceFromAttributes({
    'service.name': 'frontend-app',
    'service.version': process.env.APP_VERSION,
    'browser.platform': navigator.platform,
    'browser.user_agent': navigator.userAgent,
    'session.id': sessionId,
    'deployment.environment.name': process.env.NODE_ENV,
  }),
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({
        url: 'https://otlp.example.com/v1/traces',
        // 用 sendBeacon 在 page unload 時也能送出
        keepalive: true,
      })
    ),
  ],
});

provider.register({
  contextManager: new ZoneContextManager(),
});

registerInstrumentations({
  instrumentations: [
    new DocumentLoadInstrumentation(),
    new UserInteractionInstrumentation({
      eventNames: ['click', 'submit', 'change'],
    }),
    new FetchInstrumentation({
      // 只把 trace header 送給自家 API
      propagateTraceHeaderCorsUrls: [
        /^https:\/\/api\.example\.com\/.*/,
      ],
      // 只記錄業務 API，過濾掉 analytics / static asset
      ignoreUrls: [
        /^https:\/\/(www\.google-analytics\.com|cdn\.example\.com)\/.*/,
      ],
    }),
    new XMLHttpRequestInstrumentation(),
    new LongTaskInstrumentation(),
  ],
});

Android 端有專屬的 SDK opentelemetry-android，提供：

24.6 Session 模型與行動端特殊概念

Web / 行動端有一個 backend 沒有的概念：session（一次 app 使用週期）。SemConv 1.41 提供：

屬性意義
session.id使用者 session 唯一識別碼（通常 30 分鐘 idle 後算新的）
session.previous_id前一個 session id（連結 session 鏈）

Session 與 trace 是正交關係：一個 session 含多個 traces，一個 trace 通常完成在一個 session 內。後端可用 session.id 把同一使用者的所有 traces 串起來分析使用者旅程。

24.7 Client-side 隱私與合規

議題應對
個資（PII） Browser SDK 的 attribute 不要含 email / 真實姓名；使用者 ID 用 hash
GDPR / Cookie 同意 OTel session.id 屬個資；要在 cookie consent banner 同意後才開始送 telemetry
追蹤防禦 Safari ITP / Firefox ETP 會清 sessionStorage；session.id 可能比預期短命
CORS 後端 API 必須允許 traceparent / tracestate header（在第五篇 13.6 已強調）
Bandwidth / Battery 行動端 BatchSpanProcessor timeout 拉長到 30s+；避免 cellular 上傳
App Store / Play Store policies SDK 收什麼資料要在 Privacy Policy 揭露

關鍵設計：

  • K8s 內走 Agent → Gateway（如第六篇 17.4 介紹）。
  • 所有 Collector 最終匯入同一 Gateway，再分發到後端。

25.2 端到端 trace：Browser → Backend → Lambda

跨平台 trace 的關鍵在於 W3C Trace Context 一路傳遞。流程：

sequenceDiagram
  autonumber
  participant Browser
  participant CDN
  participant API as Backend API (K8s)
  participant Q as SQS / Pub/Sub
  participant Lambda
  participant DB

  Browser->>Browser: 開始 trace, 產生 traceparent
  Browser->>CDN: GET /page (帶 traceparent)
  CDN->>API: 轉發 (帶 traceparent)
  API->>DB: 查詢 (帶 traceparent)
  DB-->>API: 結果
  API->>Q: 發訊息 (在 message header 帶 traceparent)
  Q->>Lambda: 觸發 (extract traceparent)
  Lambda->>Lambda: 處理 (link to parent trace)
  Lambda-->>Q: ack
  API-->>CDN: 200
  CDN-->>Browser: 200

  Note over Browser,Lambda: 同一 trace_id, 完整端到端

檢查清單：跨平台 propagation 要對齊

  1. 所有平台的 propagator 設為 tracecontext,baggage（不要混 b3 / jaeger）
  2. Browser SDK 設定 propagateTraceHeaderCorsUrls
  3. 後端 CORS 允許 traceparent 與 tracestate
  4. 非同步邊界（SQS、Kafka、Pub/Sub）用 messaging instrumentation library 在 message header / attribute 自動 inject / extract
  5. Lambda 端的 AwsLambdaInstrumentation 已支援從 SQS / SNS / Kinesis event 中 extract trace context

25.3 統一 Backend 還是分流

多平台會帶來不同 telemetry 特性，是否需要分流到不同後端？

來源典型特性建議
Web / Mobile RUM高量、低結構性、隱私敏感可走獨立 RUM 後端，或用 sampling 大幅降量後與 backend trace 整合
K8s Backend結構化、量大、需詳細採樣主流 trace backend（Tempo / Jaeger / 商業 APM）
Lambda短命、量起伏大同 Backend；用 cold start attribute 標記
Batch Job / CronJob低頻但長同 Backend；可降採樣率

實務建議：能統一就統一，靠 attribute 與 sampling policy 區分；分流要付出 dashboard / 告警 / 教育成本，除非有合規需求（如 EU 與 US 資料分離）。

25.4 平台選型決策清單

問題建議
跑在 K8s？Operator + Agent DaemonSet + Gateway Deployment（標準三件套）
有大量 Lambda？Lambda Layer + 中央 Edge Collector
有 Web 前端？Web SDK + 公開 Edge Collector + CORS 設定
有 iOS / Android？對應 OTel SDK + session.id + 隱私揭露
混合 VM / 容器 / FaaS？每種環境部各自的 Agent，最終 Gateway 集中
Multi-cluster / Multi-cloud？每個 cluster 一個 Gateway；中央可加 super-Gateway 做 cross-cluster aggregation
需要 zero-code 注入？K8s 用 Operator Instrumentation CRD；Lambda 用 Layer
需要 host-level metrics？Agent DaemonSet（K8s）或 systemd service（VM）
大規模管理？OpAMP（500+ Collector 才需要）
強合規要求？OCB 自製 distribution、Edge Collector PII 過濾、persistent queue 落地稽核
