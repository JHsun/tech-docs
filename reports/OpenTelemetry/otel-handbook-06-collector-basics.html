第 16 章 Collector 概論與安裝 DevOpsSRE#

16.1 Collector 是什麼，為什麼需要它

OpenTelemetry Collector（簡稱 OTel Collector，或就叫 Collector）是一個 vendor-agnostic 的獨立程式，職責是接收、處理、匯出 telemetry data。本質上是一條可組合的 pipeline。

不用 Collector 也能讓應用直接送到 backend，所以「為什麼需要 Collector？」是合理問題。答案有六個層次：

角色沒 Collector 時的痛Collector 解決了什麼
應用工程師 每換一次後端就要改 SDK exporter / 重新部署所有應用 應用只送 OTLP 到 Collector，後端隨時可換
SRE 應用得自己處理 retry / batch / 壓縮 / 失敗 buffer Collector 統一管，應用只負責「送出去就好」
Security 無法集中過濾 PII；憑證 / Token 散落各應用 Collector 集中做 redaction、認證；應用不接觸後端 credentials
FinOps 採樣、過濾邏輯散在各語言 SDK，難一致調整 Collector 上一個 config 改完，全公司流量立刻變
多後端整合 同一筆 telemetry 要送到 Jaeger + Datadog + S3 archive 三處 Collector 用 fanout / routing 一次決定
非 OTLP 來源 舊系統發的是 statsd / Fluent Forward / Prometheus scrape Collector 各種 receiver 都收，再轉 OTLP
✅ 一句話判斷

「能讓 Collector 做的事，就不要在應用 SDK 做」——這是 OTel 社群的明確建議。Collector 是團隊治理 telemetry 的中央槓桿點。

OTel 官方對 Collector 列出五個目標：易用性、效能、可觀測性（自身就是 observable service 的範本）、可擴展性、統一性（單一程式碼基底，可作 agent 或 gateway，三訊號都支援）。

16.2 內部架構：Receiver → Processor → Exporter

Collector 內部是一條 pipeline，結構非常清晰：

  subgraph EXT[Extensions]
    HC[health_check]
    PPROF[pprof]
    ZPAGES[zpages]
  end

  subgraph PIPE[Pipeline]
    R1[OTLP Receiver]
    R2[Prometheus Receiver]
    R3[Filelog Receiver]

    P1[memory_limiter]
    P2[batch]
    P3[transform]
    P4[tail_sampling]

    E1[OTLP Exporter]
    E2[Prometheus Exporter]
    E3[OpenSearch Exporter]

    R1 --> P1
    R2 --> P1
    R3 --> P1
    P1 --> P2
    P2 --> P3
    P3 --> P4
    P4 --> E1
    P4 --> E2
    P4 --> E3
  end

  subgraph CONN[Connectors]
    SM[Span Metrics
Connector]
  end

  P3 -.derives.-> SM
  SM -.feeds.-> P2
元件類別職責典型範例
Receiver接收 telemetry（push 或 pull）otlp、prometheus、filelog、kafka、hostmetrics
Processor對流經的資料做過濾、轉換、批次、採樣batch、memory_limiter、resource、transform、tail_sampling、filter
Exporter把資料送出去otlp、otlphttp、prometheus、opensearch、kafka、file
Connector同時是 exporter 也是 receiver，把一條 pipeline 接到另一條spanmetrics、servicegraph、routing、forward
Extension不在資料路徑上，提供管理／健康／除錯能力health_check、pprof、zpages、oauth2client、basicauth
📌 為什麼有 Connector 這個東西

傳統 pipeline 模型只有「receiver → processor → exporter」。但有些需求需要把處理結果重新進入另一條 pipeline，例如「從 traces 衍生 RED metrics」。Connector 就是這座橋，2023 年加入後成為非常常用的工具。第七篇會深入 Span Metrics Connector 的設定。

16.3 Distributions：Core、Contrib、Vendor

Collector 不是「一個 binary」，而是「一系列 distribution」，每個 distribution 包含不同元件組合：

Distribution包含元件適用場景
otelcol（Core） 最小核心：OTLP receiver/exporter、batch、memory_limiter、health_check 嚴格生產環境、要極小攻擊面
otelcol-contrib Core + 全部社群元件（200+ receivers/processors/exporters） 多數情境、評估 / Demo / 中型部署
otelcol-k8s K8s 場景特化（kubeletstats、k8sattributes、k8sobjects 等預載） Kubernetes 內部署
vendor distribution 各 APM 廠商（Datadog、New Relic、Splunk、Elastic、Honeycomb、AWS、Google、Azure…）的客製版 用了該廠商的 backend
自製（OCB） 用 OpenTelemetry Collector Builder 挑選需要的元件 大規模部署、安全合規嚴格

2026-04-14 最新穩定版：v0.150.0。發版頻率約兩週一次，建議生產環境鎖定固定 minor version 並排定每月升級節奏。

⚠️ 不要用 latest 標籤

Docker image 用 otel/opentelemetry-collector-contrib:0.150.0，不要用 :latest。Collector 在 minor 升級偶爾會有 breaking changes（component config schema 變更、deprecated 元件移除），釘版本是必須的。

16.4 Docker 安裝

最簡單的試跑方式：

# 1. 建立最小 config 檔
cat > otelcol-config.yaml <<'EOF'
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch:

exporters:
  debug:
    verbosity: detailed

service:
  pipelines:
    traces:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [debug]
    metrics:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [debug]
    logs:
      receivers:  [otlp]
      processors: [batch]
      exporters:  [debug]
EOF

# 2. 啟動
docker run --rm \
  -v "$(pwd)/otelcol-config.yaml:/etc/otelcol/config.yaml" \
  -p 4317:4317 -p 4318:4318 \
  otel/opentelemetry-collector-contrib:0.150.0

跑起來後，把任何 OTel 應用 endpoint 指向 http://localhost:4317，stdout 就會印出收到的 traces / metrics / logs。這是除錯時最有用的設定。

16.5 Kubernetes 安裝（Helm + Operator）

K8s 環境有兩個官方安裝路徑：Helm Chart（直接部署 Collector workload）與 Operator（CRD 驅動，適合大規模管理）。

(A) Helm Chart

# 加 OTel Helm repo
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update

# 安裝 Collector（預設 deployment 模式）
helm install otel-collector open-telemetry/opentelemetry-collector \
  --set image.repository=otel/opentelemetry-collector-k8s \
  --set mode=deployment \
  --values values.yaml

values.yaml 簡化範例：

mode: deployment   # 或 daemonset / statefulset
replicaCount: 2

config:
  receivers:
    otlp:
      protocols:
        grpc:
          endpoint: 0.0.0.0:4317
        http:
          endpoint: 0.0.0.0:4318
  processors:
    batch: {}
    memory_limiter:
      check_interval: 5s
      limit_percentage: 80
      spike_limit_percentage: 25
  exporters:
    otlp/backend:
      endpoint: tempo.observability.svc:4317
      tls:
        insecure: true
  service:
    pipelines:
      traces:
        receivers:  [otlp]
        processors: [memory_limiter, batch]
        exporters:  [otlp/backend]

resources:
  limits:
    cpu: 1
    memory: 2Gi

(B) Operator（CRD 驅動）

OTel Operator 是 K8s 平台團隊強烈推薦的方式，提供：

  • OpenTelemetryCollector CRD：宣告式管理 Collector 部署
  • Instrumentation CRD：透過 annotation 自動注入 zero-code instrumentation 到應用 Pod
  • Target Allocator：把 Prometheus scrape targets 智能分散到多 Collector 實例
  • Auto-instrumentation 注入（已在第三篇講過）
# 安裝 Operator（用 cert-manager 管 TLS）
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
helm install opentelemetry-operator open-telemetry/opentelemetry-operator
# 用 CRD 部署 Collector
apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: otel-gateway
  namespace: observability
spec:
  mode: deployment
  replicas: 3
  image: otel/opentelemetry-collector-k8s:0.150.0
  config:
    receivers:
      otlp:
        protocols:
          grpc: { endpoint: 0.0.0.0:4317 }
          http: { endpoint: 0.0.0.0:4318 }
    processors:
      batch: {}
    exporters:
      otlp:
        endpoint: tempo:4317
        tls: { insecure: true }
    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [batch]
          exporters: [otlp]

16.6 Binary 安裝（Linux / macOS / Windows）

非容器環境（VM、bare metal、邊緣節點）需要 binary 安裝。三大平台都有官方 release：

Linux（systemd）

# Debian / Ubuntu (.deb)
wget https://github.com/open-telemetry/opentelemetry-collector-releases/releases/download/v0.150.0/otelcol-contrib_0.150.0_linux_amd64.deb
sudo dpkg -i otelcol-contrib_0.150.0_linux_amd64.deb

# RHEL / CentOS (.rpm)
sudo rpm -ivh otelcol-contrib_0.150.0_linux_amd64.rpm

# 啟用 systemd service
sudo systemctl enable --now otelcol-contrib

# 設定檔位置：/etc/otelcol-contrib/config.yaml
# 預設帳號：otelcol-contrib（不可登入）
# 日誌位置：journalctl -u otelcol-contrib

macOS（Homebrew）

brew install opentelemetry-collector
# 設定檔位置：/opt/homebrew/etc/otelcol-contrib/config.yaml

Windows（MSI）

下載 otelcol-contrib_0.150.0_windows_amd64.msi，雙擊安裝，會註冊成 Windows Service。設定檔在 C:\Program Files\OpenTelemetry Collector\config.yaml。

16.7 Status、版本相容性與升級策略

Collector 的 status 是「mixed」——核心元件（OTLP receiver/exporter、batch processor、health_check extension）已 stable，但每個元件有獨立的 stability level。要看每個 component 的 README 確認。

Stability Level意義適合 prod 嗎
StableAPI 凍結、有破壞性變更會走 deprecation flow✅ 是
BetaAPI 大致穩定，但可能微調⚠️ 評估後可
Alphaactive development，會有 breaking changes❌ 不建議
Development還在原型階段❌ 不建議
Deprecated即將移除，找替代方案❌ 立刻換
Unmaintained沒人在維護，下版可能移除❌ 立刻換
✅ 升級節奏建議
  1. Lab／Dev 環境跟 latest（每兩週升一次）
  2. Staging 落後 1–2 個 minor
  3. Production 落後 2–4 個 minor，每月固定升級
  4. 每次升級前讀 CHANGELOG，特別注意 BREAKING CHANGES 區塊
  5. 每個元件的 README 看 stability level，alpha / deprecated 元件要建立替換計畫

第 17 章 部署模式與 Quick Start DevOpsSRE#

17.1 為什麼部署模式重要

Collector 跑哪、跑幾個、誰送給誰，會直接影響：

  • 延遲：應用送 telemetry 的 RTT
  • 可靠性：Collector 掛掉時資料是否丟失
  • 資源消耗：是每個 node 一個 daemon，還是中央集中部署
  • 網路成本：跨 AZ / 跨 region 流量計費
  • 權限隔離：應用是否需要持有後端 credentials

OTel 規格定義了三種主要模式：Agent、Gateway、Agent-to-Gateway，外加一個 No Collector（應用直接送）。

17.2 Agent 模式

Collector 跟應用同 host 跑（K8s 中是 DaemonSet），應用透過 localhost:4317 送出。Collector 做 batch / 壓縮 / retry / resource attribute enrichment 後再送出。

flowchart LR
  subgraph Node1[Node 1]
    A1[App A]
    A2[App B]
    AG1[Collector
DaemonSet]
    A1 -.localhost.-> AG1
    A2 -.localhost.-> AG1
  end
  subgraph Node2[Node 2]
    A3[App C]
    A4[App D]
    AG2[Collector
DaemonSet]
    A3 -.localhost.-> AG2
    A4 -.localhost.-> AG2
  end

  AG1 --> BE[(Backend)]
  AG2 --> BE

優點

  • 低延遲：應用送 telemetry 走 loopback，幾乎無感
  • 可採集 host metrics：DaemonSet 可掛 hostPath，跑 hostmetrics receiver、filelog 抓 node 上的 log
  • K8s 屬性 enrichment：搭配 k8sattributes processor 自動補 k8s.pod.name、k8s.namespace.name 等

缺點

  • 資源開銷：每個 node 都跑一個 Collector（即便該 node 流量不大）
  • 後端 credentials 散落：每個 Collector 都要有後端 token
  • 無法做需要全域決策的事：tail-based sampling、跨服務的 routing 都需要中央集中

17.3 Gateway 模式

Collector 集中跑在獨立節點群（K8s 中是 Deployment 或 StatefulSet），所有應用透過網路送過來。

flowchart LR
  A1[App A]
  A2[App B]
  A3[App C]
  A4[App D]

  subgraph GW[Gateway Cluster]
    G1[Collector 1]
    G2[Collector 2]
    G3[Collector 3]
  end
  LB[Load Balancer]

  A1 --> LB
  A2 --> LB
  A3 --> LB
  A4 --> LB
  LB --> G1
  LB --> G2
  LB --> G3

  G1 --> BE[(Backend)]
  G2 --> BE
  G3 --> BE

優點

  • 集中控制：可做 tail sampling、跨服務 routing、backend 切換、敏感資料 redaction
  • credentials 集中：只有 Gateway 持有後端 token
  • 水平擴充容易：Deployment + HPA

缺點

  • 網路依賴：應用 → Gateway 是網路呼叫，可能跨 AZ 產生流量費
  • SPOF 風險：Gateway 全掛時所有 telemetry 都丟（解法：多副本 + load balancer）
  • 無法做 host 層採集：拿不到 node-level metrics / kubelet stats

17.4 Agent-to-Gateway 模式（推薦正式環境）

把上面兩種混合：每個 node 跑 Agent（DaemonSet），中央跑 Gateway 群。Agent 做本地批次與 enrichment，Gateway 做集中決策與後端送出。

    A2 -.localhost.-> AG2

    A3[App C]
    AG3[Agent]
    A3 -.localhost.-> AG3
  end

  subgraph GW[Gateway Cluster]
    G1[Collector 1]
    G2[Collector 2]
  end

  AG1 --> G1
  AG2 --> G1
  AG3 --> G2

  G1 --> Tempo[(Tempo)]
  G1 --> Mimir[(Mimir)]

  G2 --> Tempo
  G2 --> Mimir
  G2 --> Loki

各層職責切分

層典型職責
Agent
  • OTLP 接收（localhost）
  • memory_limiter（保護 node）
  • k8sattributes 補 K8s 元資料
  • resourcedetection 補 host / cloud 元資料
  • filelog 抓 container log（如有需要）
  • hostmetrics 採 node 指標
  • 初步 batch（小批次，低延遲）
  • 送 OTLP 到 Gateway
Gateway
  • OTLP 接收（從 Agent）
  • tail_sampling（需要看完整 trace 後決策）
  • spanmetrics connector（衍生 RED metrics）
  • servicegraph connector（衍生服務拓撲）
  • filter、transform（OTTL）做 PII 清洗
  • routing connector（按 attribute 路由到不同後端）
  • 大批次 batch（高效送出）
  • 持有後端 credentials
✅ 為什麼 Agent-to-Gateway 是正式環境首選

它兼具兩種模式的優點：應用低延遲、本地 enrichment 完整、又有集中決策能力。代價是多一層元件要維護，但 Helm chart / Operator 已把這件事自動化。絕大多數中大型企業生產環境都採這種模式。

17.5 No Collector 模式

應用直接送 OTLP 到後端，不經 Collector。

flowchart LR
  A1[App A]
  A2[App B]
  A3[App C]

  A1 --OTLP--> BE[(SaaS Backend
Datadog / Honeycomb /
New Relic / ...)]
  A2 --OTLP--> BE
  A3 --OTLP--> BE

適用場景

  • 初期試跑：第一次接 OTel，先不部署 Collector
  • SaaS-only 部署：小團隊、用單一商業 APM、流量不大
  • FaaS：Lambda 等短命環境，沒地方放 Collector

缺點

  • 所有應用都要持有後端 credentials
  • 無集中過濾、採樣、routing
  • 後端切換時要重新部署所有應用
  • 無法統一加 K8s / cloud 元資料

17.7 Quick Start：5 分鐘第一筆 telemetry

給一份完整可跑的設定，覆蓋三個訊號 + 基本 processor + 兩種 exporter（debug + OTLP 到後端）：

# otelcol-quickstart.yaml

# ============== Receivers ==============
receivers:
  # OTLP（最常用）
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

  # 採集 Collector 自身與 host 指標
  hostmetrics:
    collection_interval: 30s
    scrapers:
      cpu: {}
      memory: {}
      disk: {}
      network: {}
      load: {}

# ============== Processors ==============
processors:
  # 1. 防爆機（最關鍵）
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 25

  # 2. 補 host / cloud 元資料
  resourcedetection:
    detectors: [env, system]
    timeout: 2s
    override: false

  # 3. 補環境屬性
  resource:
    attributes:
      - key: deployment.environment.name
        value: dev
        action: upsert

  # 4. 批次（送出前最後一站）
  batch:
    send_batch_size: 1024
    timeout: 10s
    send_batch_max_size: 2048

# ============== Exporters ==============
exporters:
  # 除錯：印到 stdout
  debug:
    verbosity: basic   # 或 normal / detailed

  # 正式：送到後端 OTLP（這裡示意 Tempo / Mimir / Loki）
  otlp/traces:
    endpoint: tempo:4317
    tls:
      insecure: true
    sending_queue:
      enabled: true
      queue_size: 1000
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_interval: 30s
      max_elapsed_time: 5m

  otlphttp/metrics:
    endpoint: http://mimir:9009/otlp
    sending_queue: { enabled: true }
    retry_on_failure: { enabled: true }

  otlphttp/logs:
    endpoint: http://loki:3100/otlp
    sending_queue: { enabled: true }
    retry_on_failure: { enabled: true }

# ============== Extensions ==============
extensions:
  # 健康檢查（K8s readiness/liveness 用）
  health_check:
    endpoint: 0.0.0.0:13133

  # 內部除錯頁面
  zpages:
    endpoint: 0.0.0.0:55679

  # CPU / 記憶體 profile
  pprof:
    endpoint: 0.0.0.0:1777

# ============== Service ==============
service:
  extensions: [health_check, zpages, pprof]

  # 自身 telemetry：Collector 自己也是 observable service
  telemetry:
    logs:
      level: info
      encoding: json
    metrics:
      level: detailed
      readers:
        - pull:
            exporter:
              prometheus:
                host: 0.0.0.0
                port: 8888

  pipelines:
    traces:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, resource, batch]
      exporters:  [debug, otlp/traces]

    metrics:
      receivers:  [otlp, hostmetrics]
      processors: [memory_limiter, resourcedetection, resource, batch]
      exporters:  [debug, otlphttp/metrics]

    logs:
      receivers:  [otlp]
      processors: [memory_limiter, resourcedetection, resource, batch]
      exporters:  [debug, otlphttp/logs]

幾個值得抓出來的設計重點：

  1. memory_limiter 永遠是 pipeline 的第一個 processor：當 Collector 記憶體飆高時，它會主動拒收（receiver 開始 backpressure），保護 Collector 不 OOM。沒有它就是定時炸彈。
  2. batch 永遠是 pipeline 的最後一個 processor：把零散的 spans / metrics 點打包，提升傳輸效率。
  3. resourcedetection + resource 順序很重要：先偵測環境（host name、cloud zone），再覆寫應用層屬性。
  4. 每個 exporter 都有 sending_queue + retry_on_failure：後端短暫不可用時不會丟資料。第七篇會深入 Resiliency。
  5. Service 區塊本身的 telemetry：Collector 自己暴露 Prometheus metrics on :8888，這是觀察 Collector 健康的首要來源。

17.8 Internal Telemetry：監測 Collector 自身

Collector 的口號是「An exemplar of an observable service」——它自身就是個可被觀察的服務。每個 Collector 在 :8888/metrics 暴露一組 Prometheus metrics（OTel 規格命名），值得長期 dashboard：

Metric意義異常指標
otelcol_receiver_accepted_spans / _metric_points / _log_records各 receiver 接收量突降為 0：上游應用斷送
otelcol_receiver_refused_*各 receiver 拒收量非 0：受 memory_limiter 觸發或格式錯
otelcol_processor_batch_send_size實際送出的批次大小分佈偏離設定的 send_batch_size：背壓中
otelcol_exporter_sent_*各 exporter 成功送出量遠低於 receiver_accepted：管線中流失
otelcol_exporter_send_failed_*各 exporter 失敗量非 0：後端拒收 / 認證錯
otelcol_exporter_queue_size持久化佇列當前大小持續增長：後端速度跟不上
otelcol_processor_dropped_*processor 丟棄數量非 0：filter / sampling 丟掉
otelcol_process_runtime_total_alloc_bytesCollector 自身記憶體長期上升：可能有元件記憶體洩漏

建議至少在 Grafana 上建立兩個 dashboard：

  • Pipeline health：每個 pipeline 的 receiver / processor / exporter 流量三線比較
  • Resource usage：CPU、記憶體、queue size、goroutines

這兩個 dashboard 是 Demo 內建 Collector Data Flow Dashboard 的延伸（見第二篇 7.1），是 SRE 標配。

17.9 常見部署陷阱

症狀原因解法
Collector OOM 重啟迴圈 沒設 memory_limiter，或 limit 太接近 container limit memory_limiter 設 80%，container limit 設 1.25 倍以上
應用收不到資料但 Collector 是健康的 endpoint 寫成 localhost 而非 0.0.0.0，K8s 內無法外部接 receiver endpoint 一律用 0.0.0.0:port
資料量被 retry 放大 後端 5xx 大量觸發 retry，Collector queue 越塞越大 設 retry_on_failure.max_elapsed_time 上限，並監測 queue_size
K8s 升級時資料丟失 Collector 沒有 gracefulShutdown 設 terminationGracePeriodSeconds: 60，讓 Collector 把 queue flush 完
跨 AZ 流量費爆增 Gateway 沒有 zone-aware 部署 K8s topology spread / multi-AZ Gateway，或改 Agent-to-Gateway
Tail sampling 結果不對 多個 Gateway 副本各自決策，同一 trace 被切到不同 Collector 用 loadbalancing exporter（trace_id-aware routing）把同一 trace 路由到同一 Collector
memory_limiter 觸發但流量沒減少 應用 SDK 對 backpressure 沒反應，繼續打 SDK 端調整 BatchSpanProcessor 參數；增加 Collector 副本
Collector 升級後啟動失敗 Config schema 在新版有 breaking change 升級前用 otelcol-contrib validate --config=config.yaml 驗證
⚠️ 永遠記得做 config 驗證

Collector 啟動時若 config 有錯，會直接 crash。在 CI / GitOps pipeline 加上：
otelcol-contrib validate --config=/path/to/config.yaml
能在部署前抓到 90% 的設定錯誤。
