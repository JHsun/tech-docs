Instrumentation 策略總論

OTel 給了三條把應用「instrument 起來」的路徑：Zero-code（外掛 agent，零程式碼改動）、Code-based（直接呼叫 SDK／API）、Library（用社群預先寫好的 instrumentation library）。每條路各有適用場景與盲點，本篇幫你建立決策框架，並深入 Zero-code 各語言（Java agent、.NET、Python、JavaScript、Go Auto SDK、PHP、OBI eBPF）的實際操作流程。第四篇才會接著進入 Code-based 的程式碼層細節。

第 8 章 三大 Instrumentation 策略 開發者DevOps#

8.1 為什麼要分這三類

要讓系統可被觀測，code 必須發出 signals。這件事可以透過三條路徑完成，OTel 官方文件把它們明確分成： 

flowchart LR
  subgraph Goal[目標：應用發出 traces / metrics / logs]
    direction TB
  end

  Z[Zero-code
掛 agent / 注 sidecar / eBPF
不改一行 app code] --> Goal
  C[Code-based
直接呼叫 OTel API / SDK
寫 business span] --> Goal
  L[Library
用社群 instrumentation library
或函式庫的 native OTel 支援] --> Goal

這個分法重要在「誰負責產 telemetry」這個責任歸屬：

策略誰寫 instrumentation誰部署它
Zero-code OTel 社群 / Vendor 寫好 agent 運維啟動 app 時掛上去（Java -javaagent、Python opentelemetry-instrument、K8s init container...）
Code-based 應用工程師自己寫 跟著應用程式部署
Library 函式庫作者（如 Spring、Express、gRPC）或 OTel 社群維護的 wrapper 應用工程師 import 或自動載入

8.2 Zero-code 的本質

Zero-code 的核心邏輯：在程式進入點（或執行期）動態插入 instrumentation，不需要改業務程式碼。實作機制依語言而異：

  • JVM 系（Java、Kotlin、Scala）：用 -javaagent 載入 OTel Java Agent，bytecode 動態改寫框架類別。
  • .NET：透過 CLR Profiling API 注入 IL 指令。
  • Python：用 opentelemetry-instrument 啟動命令，monkey-patch 主流套件。
  • Node.js：透過 Node 的 require hook 攔截模組載入。
  • PHP：透過 PHP 擴充模組（C extension）注入。
  • Go：較特殊——Go 沒有 runtime monkey-patch，分兩條路：(a) eBPF 從 kernel 觀察、(b) compile-time 透過 otel-go-auto-instrumentation 注入（實驗性，2025 起改名為 Auto SDK）。
  • 跨語言（OBI）：用 eBPF 從 kernel 觀察，幾乎所有語言都能用，無侵入。

Zero-code 給你什麼，沒給你什麼

免費得到的得不到的
HTTP server 接入點 spans（Spring MVC、Express、Flask、ASP.NET Core...） 業務語意（哪個訂單？哪個 user？哪個 promotion？）
HTTP / gRPC client spans 業務指標（如 orders.placed、payment.failures）
常見 DB driver spans（JDBC、psycopg2、go-sql、mysql2...） 跨業務 domain 的 trace 連續性（特別是非標準的 messaging 方式）
常見 messaging client spans（Kafka、RabbitMQ、SQS...） 對私有協定、自家 RPC 框架、舊版本框架的覆蓋
Runtime metrics（JVM heap、Go goroutines、Python GC...） 程式內部關鍵函式的執行時間（除非該函式剛好在標準框架攔截點上）
Resource detection（host / cloud / k8s） 敏感資料的 redaction policy（要自己加 Processor）
✅ Zero-code 的甜蜜點

「剛開始導入 OTel，想先看到結果」、「幾百個老服務，沒辦法一個個改」、「第三方應用無法改程式碼」這幾種情境，Zero-code 幾乎是唯一答案。覆蓋率通常能在第一週就達到 70% 以上。

8.3 Code-based 的本質

Code-based 的核心邏輯：應用工程師直接呼叫 OTel API。流程上分兩件事：

  1. SDK setup：應用啟動時初始化 TracerProvider、MeterProvider、LoggerProvider，配置 Resource、Sampler、Exporter。這通常只需寫一次。
  2. 呼叫 API：在業務程式碼裡 tracer.startSpan(...)、counter.add(1, attrs)、logger.info(...)。這是日復一日的開發工作。

API vs SDK：別混淆

這是 OTel 設計的精髓——API 與 SDK 是兩個獨立 module：

  • API：輕量、沒有依賴，只定義介面（Tracer / Meter / Logger…）。即使 SDK 沒接上，API 呼叫也是 no-op，不會炸。
  • SDK：API 的執行端，含取樣、批次、Exporter。應用啟動時才綁上。

這個設計讓函式庫作者可以放心依賴 OTel API——使用該函式庫的應用如果沒裝 SDK，也不會壞。這就是下面要講的 Library 模式的基礎。

8.4 Library 的本質與「Native Instrumentation」

Library 模式有兩個變體，常被混為一談：

變體原理例子
OTel-maintained instrumentation library OTel 社群（或 vendor）幫流行框架寫 instrumentation wrapper opentelemetry-instrumentation-flask、@opentelemetry/instrumentation-http
Native instrumentation 函式庫本身依賴 OTel API，「原生支援」OTel 新版 .NET 的 HttpClient、新版 OkHttp、ASP.NET Core、Quarkus、Spring Boot 3 部分組件

Native 是 OTel 長期目標——不需 wrapper，函式庫自己就會發 OTel telemetry。.NET 是目前覆蓋最廣的（Microsoft 把 OTel 視為 .NET 的標準 telemetry API），Java 生態次之（Quarkus、Micronaut、Spring Cloud 都已部分原生支援），Go 生態因為 OTel API 設計與 Go 工程文化高度契合，許多熱門函式庫（如 net/http、database/sql 透過 OTLP wrapper、chi、fiber）也都有原生 OTel hook。

📌 為什麼這個區分對採購／架構決策有意義

「函式庫原生支援 OTel」 vs 「需要外掛 instrumentation library」差別在於版本相容性與維護負擔。Native 不會因為框架升級而 instrumentation 壞掉；外掛 wrapper 必須跟著框架版本走。長期看，盡量選原生支援 OTel 的函式庫。

8.6 混合策略：實務最常用的組合

對應到 Demo 的設計，三種代表性混合方式：

組合典型代表說明
Zero-code 為主 + Code-based 點睛 Demo 的 Ad（Java）、Recommendation（Python） Java agent / Python auto 涵蓋 80%，剩下手寫 business span
Library 為主 + Code-based 補強 Demo 的 Checkout（Go）、Frontend（TS） Go / TS 沒成熟 zero-code，靠 instrumentation library 接住框架，業務語意手寫
純 Code-based Demo 的 Currency（C++）、Payment（JS） 該語言生態沒有現成 zero-code 也沒 library，全部手寫

8.7 共同盲點與限制

三種策略都有共同要注意的事：

  1. Trace context propagation 不會自動發生在自家 RPC 框架上。OTel 只懂標準 HTTP / gRPC / 主流 messaging，自家私有協定要手寫 inject / extract。
  2. Async 邊界容易斷 trace。Thread pool、Goroutine、Promise chain、Callback 都可能丟失 context；多數 SDK 提供「context-aware executor / scope」可解，但要主動使用。
  3. SDK 設定錯誤會 silently drop。OTel SDK 預設「絕不影響應用」——出錯時是丟掉 telemetry 而非拋例外。第一次部署一定要看 internal telemetry 確認真的有送出。
  4. 覆蓋率要持續維護。框架升級、新增程式庫、新增微服務，都會帶來新的「沒被 instrument」的盲區。把這納入 PR template / CI check。
⚠️ 一個常見的災難

「裝了 zero-code agent 就以為大功告成」。Agent 雖然涵蓋了框架邊界，但所有業務語意（哪個 user、哪個訂單、哪個 promotion）都看不見——這恰好是排查業務問題最需要的維度。Zero-code 是地基，不是完成。

9.2 Java Agent — 最成熟的選擇

核心指令

# 1. 下載 agent jar
curl -sLO https://github.com/open-telemetry/opentelemetry-java-instrumentation/releases/latest/download/opentelemetry-javaagent.jar

# 2. 啟動應用時掛上
java -javaagent:./opentelemetry-javaagent.jar \
  -Dotel.service.name=checkout-api \
  -Dotel.exporter.otlp.endpoint=http://collector:4317 \
  -Dotel.resource.attributes=deployment.environment.name=prod \
  -jar app.jar

核心環境變數

變數說明
OTEL_SERVICE_NAME必填，service.name
OTEL_EXPORTER_OTLP_ENDPOINTCollector 位址，預設 http://localhost:4318
OTEL_EXPORTER_OTLP_PROTOCOLgrpc（4317）或 http/protobuf（4318）
OTEL_TRACES_SAMPLER採樣器：always_on / traceidratio / parentbased_*
OTEL_INSTRUMENTATION_<name>_ENABLED個別 instrumentation 開關（如 OTEL_INSTRUMENTATION_LOGBACK_APPENDER_ENABLED）
OTEL_JAVAAGENT_LOGGINGapplication（預設）、simple、none

進階：Spring Boot Starter / Quarkus

如果你用的是 Spring Boot 3 或 Quarkus，OTel 提供更輕量的整合方式：

  • Spring Boot Starter：opentelemetry-spring-boot-starter 直接以 dependency 載入，與 Spring 配置整合（application.yaml）。比 Java Agent 慢一點啟動但無 bytecode 改寫，更可預測。
  • Quarkus：Quarkus 已 native 內建 OTel SDK，application.properties 一行 quarkus.otel.exporter.otlp.endpoint=... 即可。

9.3 .NET Auto-Instrumentation

安裝（Linux／macOS）

# 1. 下載安裝腳本
curl -sSfL https://github.com/open-telemetry/opentelemetry-dotnet-instrumentation/releases/latest/download/otel-dotnet-auto-install.sh -O

# 2. 安裝到 ~/.otel-dotnet-auto/
sh ./otel-dotnet-auto-install.sh

# 3. 啟動前載入環境變數
. $HOME/.otel-dotnet-auto/instrument.sh

# 4. 設定服務名與 endpoint
export OTEL_SERVICE_NAME=cart-svc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317

# 5. 啟動 .NET app
dotnet Cart.dll

容器化（Dockerfile）

FROM mcr.microsoft.com/dotnet/aspnet:9.0
WORKDIR /app
COPY ./publish .

# 安裝 OTel auto-instrumentation
RUN apt-get update && apt-get install -y curl \
 && curl -sSfL https://github.com/open-telemetry/opentelemetry-dotnet-instrumentation/releases/latest/download/otel-dotnet-auto-install.sh -O \
 && sh otel-dotnet-auto-install.sh

ENV OTEL_SERVICE_NAME=cart-svc
ENV CORECLR_ENABLE_PROFILING=1
ENV CORECLR_PROFILER={918728DD-259F-4A6A-AC2B-B85E1B658318}
ENV CORECLR_PROFILER_PATH=/root/.otel-dotnet-auto/linux-x64/OpenTelemetry.AutoInstrumentation.Native.so

ENTRYPOINT ["dotnet", "Cart.dll"]
📌 .NET 的特殊優勢

.NET 對 OTel 的態度是「非常認真的原生支援」。Microsoft 內部把 OTel 視為 .NET 的官方 telemetry API，新版 ASP.NET Core、HttpClient、SqlClient 都已 native 內建，不裝 auto-instrumentation 也會發出 System.Diagnostics.Activity（OTel-compatible）。所以許多 .NET 專案純 SDK setup 即可，不需 auto-instrumentation。Auto-instrumentation 主要補老版本與第三方 NuGet。

9.4 Python Auto-Instrumentation

三步上工

# 1. 安裝 distro + 自動偵測 instrumentation
pip install opentelemetry-distro opentelemetry-exporter-otlp

# 2. 自動掃描已安裝的套件，安裝對應 instrumentation
opentelemetry-bootstrap --action=install

# 3. 啟動：用 opentelemetry-instrument 包裝原本的命令
opentelemetry-instrument \
  --service_name recommendation-svc \
  --exporter_otlp_endpoint http://collector:4317 \
  python recommendation_server.py

關鍵在第 2 步——opentelemetry-bootstrap 會看你目前的 pip list，自動裝對應的 instrumentation 套件（例如有 flask 就裝 opentelemetry-instrumentation-flask）。

環境變數設定法（推薦）

# 用環境變數設定，不要把 CLI 寫死
export OTEL_SERVICE_NAME=recommendation-svc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317
export OTEL_PYTHON_LOG_CORRELATION=true   # 自動把 trace_id 注入 log 格式
export OTEL_LOGS_EXPORTER=otlp            # 啟用 logs export

opentelemetry-instrument python app.py

K8s 上的 Operator 模式

不想自己改 Dockerfile？OpenTelemetry Operator 可以透過 annotation 自動注入：

apiVersion: v1
kind: Pod
metadata:
  annotations:
    instrumentation.opentelemetry.io/inject-python: "default/python-instr"
spec:
  containers:
  - name: app
    image: my-python-app:1.0

第六篇 Kubernetes 篇會深入這個機制。

9.5 JavaScript（Node.js）Auto-Instrumentation

安裝

npm install --save \
  @opentelemetry/api \
  @opentelemetry/auto-instrumentations-node \
  @opentelemetry/exporter-trace-otlp-grpc \
  @opentelemetry/exporter-metrics-otlp-grpc \
  @opentelemetry/sdk-node

啟動方式 A：純 require hook（最 zero-code）

# 設環境變數
export OTEL_SERVICE_NAME=payment-svc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317

# 用 --require 預先載入
node --require @opentelemetry/auto-instrumentations-node/register app.js

啟動方式 B：自家 bootstrap 檔（更可控）

// instrumentation.js — 應用最一開始要載入的檔
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
const { OTLPTraceExporter } = require('@opentelemetry/exporter-trace-otlp-grpc');

const sdk = new NodeSDK({
  serviceName: 'payment-svc',
  traceExporter: new OTLPTraceExporter({ url: 'http://collector:4317' }),
  instrumentations: [getNodeAutoInstrumentations({
    // 個別 instrumentation 微調
    '@opentelemetry/instrumentation-fs': { enabled: false }, // fs 太吵，關掉
  })],
});

sdk.start();
// 啟動
node --require ./instrumentation.js app.js

ESM（ECMAScript Modules）注意事項

⚠️ 用 type: "module" 的專案

ESM 載入時機與 CommonJS require hook 不一致，--require 不一定生效。Node 18+ 要改用 --import：node --import ./instrumentation.mjs app.mjs。OTel 從 2024 起已正式支援 ESM。

9.6 PHP Auto-Instrumentation

PHP 的 zero-code 透過 OTel PHP extension 注入：

# 1. 安裝 PECL extension
pecl install opentelemetry

# 2. 在 php.ini 啟用
echo "extension=opentelemetry.so" >> /etc/php/php.ini

# 3. 安裝 SDK 與 instrumentation 套件
composer require \
  open-telemetry/sdk \
  open-telemetry/exporter-otlp \
  open-telemetry/opentelemetry-auto-laravel  # 視框架而定

# 4. 啟動 (環境變數同其他語言)
OTEL_SERVICE_NAME=quote-svc \
OTEL_PHP_AUTOLOAD_ENABLED=true \
OTEL_EXPORTER_OTLP_ENDPOINT=http://collector:4317 \
php -S 0.0.0.0:8080 -t public

Composer 包名格式：open-telemetry/opentelemetry-auto-<framework>，常見有 auto-laravel、auto-symfony、auto-slim、auto-pdo 等。

9.7 Go — Auto SDK 與 eBPF 兩條路

Go 的 zero-code 是個故事——Go 沒有 runtime monkey-patch、沒有 bytecode 改寫，所以「真正的 zero-code」很難。OTel 提供兩條路：

(A) Auto SDK（compile-time）

2025 年原來的 otel-go-auto-instrumentation 改名為 Auto SDK，定位也從 eBPF 轉為 compile-time 注入：在 build 時把 instrumentation 編譯進 binary。需要：

  1. 用 go.opentelemetry.io/auto 取代直接 import "net/http" 等。
  2. build 時走特定 flag。

對 Go 工程文化（顯式、無魔法）這仍是個半妥協方案，目前 Experimental。多數 Go 專案還是直接走 Code-based + instrumentation library（如 otelhttp、otelgrpc），第四篇 Go 章會詳述。

(B) eBPF（OBI，下節詳述）

OBI 從 kernel 觀察 syscalls，理論上對任何 Go 程式都有效，且不需重新編譯。但因為是「外部觀察」，能拿到的訊號比 SDK-based 少（看不到應用層業務語意）。

9.8 OBI（OpenTelemetry eBPF Instrumentation）

OBI（前身為 Grafana Beyla，2025 年由 Grafana Labs 捐贈給 OTel 並改名）是 OTel 唯一的跨語言、零侵入 zero-code 方案，用 eBPF 從 Linux kernel 觀察應用流量。

OBI 給你什麼

  • HTTP server/client metrics & spans：所有走 socket 的 HTTP 都看得到
  • gRPC metrics & spans
  • Network metrics（含 inter-AZ 流量）
  • Distributed traces：能透過 W3C Trace Context header propagate

OBI 部署模式

模式適用場景
Docker container單機 / Docker Compose 試跑
Kubernetes DaemonSet每個 node 一個 OBI，觀察 node 上所有 pod
Helm chartK8s 標準部署方式
Standalone processVM、bare metal

OBI 跑起來最小設定

# 用 Helm 在 K8s 部署 OBI
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

helm install otel-obi grafana/beyla \
  --set config.data.otel_metrics_export.endpoint=http://collector:4318 \
  --set config.data.discovery.services[0].k8s_namespace=production \
  --set config.data.discovery.services[0].open_ports=8080

多語言環境下要快速建立全公司「哪些服務在跟哪些服務講話、流量多大、誰最慢」的可見性，OBI 是最快的方式。它不取代語言層 instrumentation，但作為「第一層 fallback safety net」非常有效——任何沒被正規 instrument 的服務，OBI 都能補一層基本 metrics。

9.10 Zero-code 常見陷阱與排查

症狀常見原因排查／解法
應用啟動了，但 backend 完全沒資料 endpoint 設錯（gRPC 4317 vs HTTP 4318 弄混） 把 exporter 換成 stdout / debug 確認；檢查 OTEL_EXPORTER_OTLP_PROTOCOL
有 trace 但缺 span（例如缺 DB span） 該 instrumentation 預設關閉，或 DB driver 版本太老 檢查 agent log 裡的 instrumentation X loaded 訊息；查 supported libraries 表
啟動時間明顯變長 Java Agent bytecode 改寫所有 class，第一次啟動會慢 正常現象；可用 AppCDS 緩解；正式環境改用 Spring Starter
記憶體使用上升 Agent 自己有 metric exporter / span batch buffer 調 OTEL_BSP_MAX_QUEUE_SIZE、降低取樣率
Logs 沒有 trace_id Logs Bridge / log correlation 預設未啟用 Java：OTEL_INSTRUMENTATION_LOGBACK_APPENDER_EXPERIMENTAL_LOG_ATTRIBUTES=true；Python：OTEL_PYTHON_LOG_CORRELATION=true
非同步 (thread pool / executor) 後 trace 斷掉 未繼承 context 多數語言 SDK 提供 context-aware executor / wrap；查官方 cookbook
Agent 與既有 APM agent 衝突 同時掛兩個 java agent，bytecode 互相干擾 先停掉舊 APM agent；或用 OTel collector 把 telemetry 送回去舊 APM
K8s pod 被 OOMKilled Agent 占用 + 應用 RSS 超過 limit 調高 memory limit；改用更輕量的 Spring Starter / native instrumentation
