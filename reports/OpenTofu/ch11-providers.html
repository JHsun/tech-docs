1. 什麼是 Provider

Provider 是 OpenTofu 與外部系統之間的橋樑。它把 HCL 設定翻譯成對 AWS API、Azure API、Datadog API、GitHub API... 的呼叫。沒有 provider，OpenTofu 什麼也做不了。

plugin binary"]
    P3["Local Provider
plugin binary"]
    AWS[("AWS API")]
    DD[("Datadog API")]

每個 Provider 都是獨立的 binary

  • Provider 是獨立的執行檔（用 Go 寫成），與 OpenTofu Core 透過 gRPC 通訊
  • 每個 provider 有自己的版本與發佈節奏，可獨立升級
  • OpenTofu Public Registry（registry.opentofu.org）是預設來源，超過 4,000 個 provider 可用
  • Provider 的授權獨立於 OpenTofu：絕大多數 MPL/Apache 授權，少數 BUSL（如 HashiCorp 商業 provider）

Provider 的兩個層次

層次用途位置
required_providers宣告我需要哪個 provider、什麼版本terraform {} block 內
provider block設定如何使用（region、credentials 等）頂層 block

2. required_providers：宣告依賴

required_providers 必須放在 terraform {} block 內，宣告本 module 用到的所有 provider。

HCL · required_providers 完整語法 
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    # 標準形式
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }

    # 第三方 provider（必須宣告 source，不像 hashicorp 命名空間可省略）
    datadog = {
      source  = "DataDog/datadog"
      version = "~> 3.40"
    }

    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.30"
    }

    # 完整來源位址（含 registry hostname，多用於 private registry）
    internal = {
      source  = "registry.example.com/myorg/internal"
      version = ">= 1.0.0, < 2.0.0"
    }

    # 設定別名（區分多個同 provider 設定，第 6 節詳述）
    aws = {
      source                = "hashicorp/aws"
      version               = "~> 5.0"
      configuration_aliases = [aws.tokyo, aws.frankfurt]
    }
  }
}

三大屬性

屬性用途必填？
sourceprovider 來源位址（NAMESPACE/NAME 或完整 hostname/NAMESPACE/NAME）除 hashicorp 命名空間外都建議寫
version版本約束（運算子請見第 10 章）強烈建議寫
configuration_aliasesmodule 接受的 provider alias 清單module 用 alias 才需要

Source 位址完整解析

Plaintext · source 位址結構 
# 完整形式
hostname/namespace/name
registry.opentofu.org/hashicorp/aws

# 簡寫（hostname 預設為 registry.opentofu.org）
hashicorp/aws

# OpenTofu 1.0 之前的舊式（不要再用）
aws    # 隱含 hashicorp/aws，但不建議

永遠寫完整的 source

有些團隊會混用 hashicorp/aws 與 opentofu/aws，後者來自 OpenTofu Registry 的 mirror。在同一專案內保持一致，否則 OpenTofu 會把它們當成兩個不同的 provider，下載兩份 binary 並產生 lock 衝突。建議統一用 hashicorp/aws，OpenTofu Registry 會自動轉導。

版本約束在 reusable module 的設計

HCL · 不同場景的 version 寫法 
# Root module（你執行 tofu apply 的地方）：寫上下限
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.30"   # >= 5.30, < 6.0
    }
  }
}

# Reusable child module（給別人用的）：只寫下限
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0"   # 不寫上限，讓使用者自由選擇
    }
  }
}

3. provider 設定：認證與 region

provider block 設定具體的執行參數（region、credentials、endpoint 等）。每個 provider 的可用屬性不同，由 provider 自己定義。

HCL · provider block 範例 
provider "aws" {
  region = "us-east-1"

  # 預設 tag（套用到此 provider 建立的所有資源）
  default_tags {
    tags = {
      ManagedBy = "OpenTofu"
      Project   = "myapp"
    }
  }

  # 部分 provider 的 retry / timeout 設定
  retry_mode  = "adaptive"
  max_retries = 5
}

provider block 是選用的

如果一個 provider 不需要任何設定（或全部用預設），可以省略 provider block。OpenTofu 會建立空白設定。例如 local provider 通常無需設定：

HCL · 不需 provider block 的情況 
terraform {
  required_providers {
    local = { source = "hashicorp/local", version = "~> 2.5" }
  }
}

# 直接用，不需要 provider "local" {} block
resource "local_file" "test" {
  filename = "/tmp/test.txt"
  content  = "hello"
}

provider block 只在 root module 寫

child module 不該寫 provider block

Provider 設定必須在 root module，由 root 決定 region、credentials 等。Child module 只寫 required_providers 宣告它需要什麼 provider；具體設定由 root 透過 providers map 傳入。這是 module 設計最常被誤解的地方。

不要把認證資訊寫死

HCL · ❌ vs ✅ 
# ❌ 絕對不要這樣寫（credentials 會進 git！）
provider "aws" {
  region     = "us-east-1"
  access_key = "AKIAIOSFODNN7EXAMPLE"
  secret_key = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
}

# ✅ 正確：用環境變數、IAM role、credentials file
provider "aws" {
  region = "us-east-1"
  # AWS_ACCESS_KEY_ID、AWS_SECRET_ACCESS_KEY、AWS_SESSION_TOKEN 由環境提供
  # 或自動從 ~/.aws/credentials、IAM instance profile、IRSA 取得
}

4. Provider 安裝機制

當你跑 tofu init，OpenTofu 會：

    P1 --> P2{有 lock 檔？}

    P2 -->|否| P4[依 version 約束找最新匹配版本]
    P3 --> P5[檢查 source 位址]
    P4 --> P5
    P5 --> P6{安裝方式？}
    P6 -->|direct| Direct["直接從 origin registry 下載

    P6 -->|filesystem mirror| FS["從本地 mirror 目錄複製"]
    P6 -->|network mirror| Net["從 mirror 服務下載"]
    P6 -->|OCI registry| OCI["從 OCI registry 下載 (1.10+)"]
    Direct --> Verify[驗證 SHA256 與簽章]
    FS --> Verify
    Net --> Verify
    OCI --> Verify
    Verify --> Cache[存入 .terraform/providers/]

    Lock --> Done[就緒]

Provider Plugin Cache：節省時間與頻寬

每個專案 init 都重新下載 provider，幾百 MB 不誇張。設定全域 cache 能大幅加速：

HCL · ~/.tofurc 設定 cache 
plugin_cache_dir = "$HOME/.terraform.d/plugin-cache"

# 或用環境變數
# export TF_PLUGIN_CACHE_DIR="$HOME/.terraform.d/plugin-cache"

之後不同專案會共享 cache 中的同版本 provider，tofu init 變得幾乎瞬時完成。

~/.tofurc 與 ~/.terraformrc 的關係

檔名OpenTofu 行為Terraform 行為
~/.tofurc✅ 優先讀取❌ 不認識
~/.terraformrc✅ 後備讀取✅ 主要讀取

同時跑 OpenTofu 與 Terraform 的開發機，建議內容寫一份在 ~/.terraformrc，OpenTofu 也會讀到。

5. .terraform.lock.hcl 完整解析

.terraform.lock.hcl 是 OpenTofu 的provider dependency lock 檔，tofu init 自動產生。

HCL · .terraform.lock.hcl 範例 
# This file is maintained automatically by "tofu init".
# Manual edits may be lost in future updates.

provider "registry.opentofu.org/hashicorp/aws" {
  version     = "5.30.0"
  constraints = "~> 5.30"
  hashes = [
    "h1:abc123...=",
    "h1:def456...=",
    "zh:1234567890abcdef...",
    "zh:fedcba0987654321...",
    # ... 多平台的 hash
  ]
}

provider "registry.opentofu.org/hashicorp/local" {
  version     = "2.5.1"
  constraints = "~> 2.5"
  hashes = [
    "h1:xyz...=",
  ]
}

Lock 檔的核心職責

  1. 鎖定版本：團隊成員、CI/CD 都用同一版 provider
  2. 驗證完整性：每次 init 比對 hash，若被竄改會 error
  3. 跨平台支援：記錄 Linux/macOS/Windows 多平台的 hash

必須 commit 進 git！

.terraform.lock.hcl 是專案的一部分

不像 .terraform/ 目錄該 .gitignore，.terraform.lock.hcl 必須 commit。否則團隊成員可能裝到不同版本的 provider，CI/CD 也可能跑出與本地不同的結果。

升級 provider 版本

Bash · 升級流程 
# 在 version 約束範圍內升到最新
tofu init -upgrade

# 如果改了 version 約束（例如 ~> 5.0 改成 ~> 6.0）
# 一般 init 會偵測到並提示，加 -upgrade 才會升級
tofu init -upgrade

# 升級單一 provider
tofu init -upgrade
# 然後檢查 .terraform.lock.hcl 變動

# CI/CD 中嚴格使用 lock 檔（不允許自動升級）
tofu init -lockfile=readonly

跨平台 lock 檔的問題

若你在 macOS 上 init，lock 檔只記錄 macOS 平台的 hash。當 CI（Linux）跑 init 時會新增 Linux hash 並觸發 lock 變更。解法：用 tofu providers lock 預先寫入多平台 hash：

Bash · 多平台 lock 
tofu providers lock \
  -platform=linux_amd64 \
  -platform=linux_arm64 \
  -platform=darwin_amd64 \
  -platform=darwin_arm64 \
  -platform=windows_amd64

6. Alias：多設定共存

當你需要同一個 provider 但多種設定（多 region、多 account），用 alias 區分：

HCL · 多 region 設定 
# 預設 provider（無 alias）
provider "aws" {
  region = "us-east-1"
}

# 加 alias 區分
provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

provider "aws" {
  alias  = "frankfurt"
  region = "eu-central-1"
}

# 跨 account（同 region 不同 account）
provider "aws" {
  alias  = "audit_account"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::987654321098:role/AuditReadOnly"
    session_name = "OpenTofuAuditSession"
  }
}

使用 alias provider

HCL · 用 provider meta-argument 指定 
# 用預設 provider（us-east-1）
resource "aws_s3_bucket" "primary" {
  bucket = "my-app-primary"
}

# 用 tokyo
resource "aws_s3_bucket" "tokyo_replica" {
  provider = aws.tokyo
  bucket   = "my-app-tokyo"
}

# data 也支援
data "aws_caller_identity" "audit" {
  provider = aws.audit_account
}

module 接受 alias provider 的宣告

HCL · module 端宣告 
# 在 child module 的 versions.tf 內
terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = ">= 5.0"
      configuration_aliases = [aws.replica]   # 宣告本 module 接受 aws.replica alias
    }
  }
}

# module 內可直接用
resource "aws_s3_bucket" "primary" {
  # 用預設 aws
  bucket = "primary"
}

resource "aws_s3_bucket" "replica" {
  provider = aws.replica
  bucket   = "replica"
}

7. Provider for_each（OpenTofu 1.9+）

OpenTofu 1.9 推出強大的 provider for_each 功能：動態產生多個 provider 實例。這是 Terraform 沒有的獨家功能！

傳統痛點：靜態 provider 無法動態化

假設你想為「使用者輸入的每個 region」建立資源。靜態 provider 設定無法應對：

HCL · ❌ 傳統做法的限制 
variable "regions" {
  type    = list(string)
  default = ["us-east-1", "us-west-2", "eu-central-1"]
}

# 必須事先寫死所有 region 的 provider
provider "aws" { alias = "use1", region = "us-east-1" }
provider "aws" { alias = "usw2", region = "us-west-2" }
provider "aws" { alias = "euc1", region = "eu-central-1" }
# 想加新 region 又要改 hcl...

OpenTofu 1.9+ 解法：provider for_each

HCL · ✅ 動態多 region 
variable "regions" {
  type    = set(string)
  default = ["us-east-1", "us-west-2", "eu-central-1"]
}

# 一個 alias provider block，依 var.regions 動態產生實例
provider "aws" {
  alias    = "regional"
  for_each = var.regions
  region   = each.key
}

# 用 instance key 指定要哪個 region
resource "aws_s3_bucket" "regional_logs" {
  for_each = var.regions

  provider = aws.regional[each.key]
  bucket   = "myapp-logs-${each.key}"
}

這讓「N 個 region 各建一份資源」這個常見需求變得乾淨許多。

8. 傳遞 provider 給 module

當父 module 用了 alias provider，child module 也要用，要透過 providers map 傳遞。

HCL · 父 module 傳遞 provider 
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

# Module 用單一 provider
module "primary_infra" {
  source = "./modules/regional"

  # 不指定 providers → child module 用預設 aws（us-east-1）
}

# Module 用替代 provider
module "tokyo_infra" {
  source = "./modules/regional"

  providers = {
    aws = aws.tokyo   # child module 內所有 aws 用法都對應到 aws.tokyo
  }
}

# Module 同時需要兩個 provider（multi-region module）
module "global_replica" {
  source = "./modules/cross-region-replication"

  providers = {
    aws         = aws            # 主 region（us-east-1）
    aws.replica = aws.tokyo      # 副 region（東京）
  }
}

何時需要 providers = {} map

① child module 用了 alias provider；② 父 module 想讓 child 用替代設定。單純 child 用預設 provider 不需要寫 providers map。

9. Provider Mirror：filesystem 與 network

不依賴 public registry 也能裝 provider，常見場景：air-gapped、企業 proxy、加速 CI、合規。

Filesystem Mirror（最簡單）

Plaintext · filesystem mirror 目錄結構 
/opt/providers/
└── registry.opentofu.org/
    └── hashicorp/
        └── aws/
            └── 5.30.0/
                ├── linux_amd64/
                │   └── terraform-provider-aws_v5.30.0_x5
                ├── darwin_arm64/
                │   └── terraform-provider-aws_v5.30.0_x5
                └── windows_amd64/
                    └── terraform-provider-aws_v5.30.0_x5.exe
HCL · ~/.tofurc 啟用 mirror 
provider_installation {
  filesystem_mirror {
    path    = "/opt/providers"
    include = ["*/*"]   # 所有 provider 都從 mirror 找
  }
  direct {
    exclude = ["*/*"]   # 不從 origin registry 找
  }
}

Network Mirror

HCL · network mirror 
provider_installation {
  network_mirror {
    url     = "https://provider-mirror.example.com/"
    include = ["*/*"]
  }
}

Network mirror 服務需實作 Provider Network Mirror Protocol。常見選項：自架 nginx + 靜態檔、Artifactory、Nexus、JFrog。

混合模式：部分 mirror 部分 direct

HCL · 混合策略 
provider_installation {
  # 內部 provider 從本地 filesystem 找
  filesystem_mirror {
    path    = "/opt/providers"
    include = ["registry.example.com/*/*"]
  }
  # 其他 provider 從 origin
  direct {
    exclude = ["registry.example.com/*/*"]
  }
}

10. OCI Registry 提供 provider（OpenTofu 1.10+）

OpenTofu 1.10 推出將 provider 發佈到 OCI registry 的能力（與 module 類似）。同樣是 OpenTofu 獨家功能。

適用場景

  • 企業已用 GHCR / ECR / Harbor，把 provider 也放在這裡統一管理
  • 內部開發 provider，不想架設 registry 服務
  • 把 provider mirror 放在 OCI 取代 filesystem mirror

把 provider 推到 OCI（用 oras + 對應 .zip）

Bash · 推送 provider package 
# 1. 從官方 release 下載 provider .zip（每個平台一份）
TOFU_PROVIDER_VERSION="5.30.0"
ZIP="terraform-provider-aws_${TOFU_PROVIDER_VERSION}_linux_amd64.zip"

curl -LO "https://github.com/hashicorp/terraform-provider-aws/releases/download/v${TOFU_PROVIDER_VERSION}/${ZIP}"

# 2. 推送到 OCI registry
oras push \
  --artifact-type=application/vnd.opentofu.providerpkg \
  ghcr.io/myorg/aws:${TOFU_PROVIDER_VERSION}_linux_amd64 \
  ${ZIP}:archive/zip

# 3. 設定 OpenTofu 從 OCI 拉取（在 ~/.tofurc）
HCL · ~/.tofurc 用 OCI provider mirror 
provider_installation {
  oci_mirror {
    repository_template = "ghcr.io/myorg/${type}"
    include             = ["registry.opentofu.org/hashicorp/*"]
  }
  direct {
    exclude = ["registry.opentofu.org/hashicorp/*"]
  }
}

repository_template 中的 ${hostname}、${namespace}、${type} 會被自動替換成 provider source 的對應欄位。

11. 主流雲端的認證模式

AWS

HCL · AWS 5 種認證方式 
# 方式 1：環境變數（CI/CD 首選）
# export AWS_ACCESS_KEY_ID=...
# export AWS_SECRET_ACCESS_KEY=...
# export AWS_SESSION_TOKEN=...   # 用 STS 時
provider "aws" {
  region = "us-east-1"
}

# 方式 2：~/.aws/credentials profile
provider "aws" {
  region                   = "us-east-1"
  shared_credentials_files = ["~/.aws/credentials"]
  profile                  = "production"
}

# 方式 3：IAM Instance Profile（在 EC2 上）
# 完全不需設定 credentials，自動取用 EC2 metadata
provider "aws" {
  region = "us-east-1"
}

# 方式 4：assume_role（跨 account）
provider "aws" {
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::123456789012:role/OpenTofuRole"
    session_name = "tofu-session"
    external_id  = "uniqueexternalid"
  }
}

# 方式 5：Web Identity（GitHub Actions OIDC、IRSA）
provider "aws" {
  region = "us-east-1"

  assume_role_with_web_identity {
    role_arn                = "arn:aws:iam::123456789012:role/GitHubActionsRole"
    web_identity_token_file = "/var/run/secrets/eks.amazonaws.com/serviceaccount/token"
  }
}

Azure

HCL · Azure 認證 
provider "azurerm" {
  features {}

  # 方式 1：az login（互動式，本地開發）
  # 直接用，不需設 credentials

  # 方式 2：Service Principal + client secret（CI/CD）
  # ARM_CLIENT_ID、ARM_CLIENT_SECRET、ARM_TENANT_ID、ARM_SUBSCRIPTION_ID
  # 從環境變數讀

  # 方式 3：Managed Identity（Azure VM 上）
  use_msi = true

  # 方式 4：OIDC（GitHub Actions 等）
  use_oidc = true
}

GCP

HCL · GCP 認證 
provider "google" {
  project = "my-project"
  region  = "us-central1"

  # 方式 1：Application Default Credentials（gcloud auth application-default login）
  # 不需設 credentials

  # 方式 2：Service Account JSON 檔
  # GOOGLE_APPLICATION_CREDENTIALS=/path/to/sa.json

  # 方式 3：Workload Identity（GKE / GitHub OIDC）
  # 不需在 HCL 設定，由環境提供
}

主流選擇：永遠用短期憑證

2026 年的最佳實踐：OIDC + 短期憑證

本地開發用 SSO（aws sso、az login、gcloud auth login）；CI/CD 用 OIDC（GitHub Actions、GitLab、Atlantis 都支援）取得短期 token。絕對不要在 CI 設定永久 access key。OIDC 設定一次後，後續無 secret 管理負擔，且自動有 token rotation。

12. 常見陷阱與最佳實踐

陷阱 1：lock 檔在不同平台 hash 不一致

第 5 節已說明：用 tofu providers lock -platform=... 預先寫多平台 hash。

陷阱 2：第三方 provider 沒寫 source

HCL · 常見錯誤 
# ❌ 直接用 provider block，沒在 required_providers 宣告
provider "datadog" {
  api_key = var.dd_api_key
}
# Error: provider "datadog" not found

# ✅ 必須先宣告 source
terraform {
  required_providers {
    datadog = {
      source  = "DataDog/datadog"
      version = "~> 3.40"
    }
  }
}

provider "datadog" {
  api_key = var.dd_api_key
}

陷阱 3：alias provider 拼錯導致用了預設 provider

HCL 
provider "aws" {
  region = "us-east-1"
}

provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

# ❌ 拼錯 alias 名稱
resource "aws_s3_bucket" "x" {
  provider = aws.toky    # 多打/少打字 → OpenTofu 直接 error
  bucket   = "x"
}

這算是好事——如果是沒寫 provider 屬性，OpenTofu 會默默用預設 provider，可能造成資源建在錯的 region/account。用 alias 時務必每個 resource 都明確指定。

陷阱 4：同 source 但拼法不同

第 2 節提過：hashicorp/aws、opentofu/aws、registry.opentofu.org/hashicorp/aws 在 OpenTofu 看來可能是不同 provider。整個專案保持一致用 hashicorp/aws。

陷阱 5：在 child module 寫 provider block

OpenTofu 會接受但會警告。Provider 設定該在 root module，由 root 透過 providers map 傳給 child。

最佳實踐速查

主題建議
required_providers每個 module 寫；source + version 都要寫
provider 設定只在 root 寫
認證OIDC / SSO 短期憑證；絕不寫死 key
版本約束（reusable module）只寫下限 >= X
版本約束（root module）寫上下限 ~> X.Y
Lock 檔必須 commit；多平台 hash 用 providers lock -platform
Plugin cache設定 TF_PLUGIN_CACHE_DIR 加速 init
多 region用 alias，OpenTofu 1.9+ 可用 provider for_each
跨 account用 assume_role alias provider
module 端 alias用 configuration_aliases 宣告
內部 providerfilesystem mirror 或 OCI mirror
CI/CD init用 -lockfile=readonly 防止意外更新 lock

13. 本章重點與練習

重點回顧

  • Provider 是 OpenTofu 與外部 API 的橋樑，獨立 binary 用 gRPC 通訊
  • 兩個層次：required_providers（宣告依賴）與 provider block（設定）
  • 每個 source 三段：hostname/namespace/name，hashicorp 命名空間可省略 source
  • Reusable module 只寫 version = ">= X"；root module 寫上下限 "~> X.Y"
  • .terraform.lock.hcl 必須 commit 進 git；用 tofu providers lock -platform 預先寫多平台 hash
  • Alias 區分多設定（多 region / 多 account）；resource 用 provider = aws.alias 指定
  • OpenTofu 1.9+ 獨家：provider for_each 動態產生 provider 實例
  • 傳遞 alias 給 module 用 providers = {...} map
  • OpenTofu 1.10+ 獨家：從 OCI registry 安裝 provider
  • 認證：本地用 SSO，CI/CD 用 OIDC，絕不寫死 access key
⚡ 動手實作 · Hands-on Lab 11

Provider 設定全方位練習

  1. 建立 provider-lab/，用 local 與 random provider，宣告 required_providers 含 source + version
  2. 跑 tofu init，檢視產生的 .terraform.lock.hcl：找出 hash 與 constraints 區段
  3. 跑 tofu providers lock -platform=linux_amd64 -platform=darwin_arm64 -platform=windows_amd64，再次檢視 lock 檔，看到多平台 hash
  4. 練習 A · 全域 cache：在 ~/.tofurc 設 plugin_cache_dir，刪掉 .terraform/ 後再 tofu init，觀察速度差異
  5. 練習 B · alias 與 for_each（OpenTofu 1.9+）：建立 random provider 的多個 alias，用 for_each = toset(["a", "b", "c"]) 動態產生
  6. 練習 C · 第三方 provider：加入 http（hashicorp/http）provider，用它讀取一個 public URL，把回應寫入 local_file
  7. 挑戰題 1：建立一個 child module 接受 random.alt alias，用 configuration_aliases 宣告，從 root 透過 providers = { random = random, random.alt = random.other } 傳遞
  8. 挑戰題 2：建立 filesystem mirror 結構，把已下載的 provider 移過去，設定 ~/.tofurc 從 mirror 安裝，刪 .terraform/ 後 init 確認從 mirror 載入
  9. 挑戰題 3：在 ~/.tofurc 用 credentials block 設定一個假的 private registry token，跑 tofu init 確認沒有 leak
  10. 用 tofu destroy 清掉資源
