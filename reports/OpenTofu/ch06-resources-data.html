1. Resource vs Data Source：管理 vs 讀取

OpenTofu 中所有「跟外部世界打交道的東西」都用兩種 block 表達：

    User["你的
OpenTofu 設定"]

    subgraph Cloud["雲端 / 外部系統"]
        Existing["已存在的資源
（其他團隊管理）"]
        Owned["你管理的資源"]
    end

    User -->|"data 讀取"| Existing
    User <-->|"resource 建立 / 修改 / 銷毀"| Owned

    style Existing fill:#cffafe,stroke:#0891b2
    style Owned fill:#dcfce7,stroke:#16a34a
面向 resource 區塊 data 區塊
正式名稱Managed resource（受管資源）Data source（資料源 / 唯讀資源）
OpenTofu 行為建立 / 修改 / 銷毀只讀取
是否寫入 state是（管理對象的完整快照）是（讀取結果的快照，下次 plan 重讀）
典型用途「我要建立一個 VPC」「我要建立一個 RDS」「找出最新版的 Ubuntu AMI」「讀取另一團隊的 VPC ID」
destroy 時行為銷毀對應資源什麼也不做（沒東西要銷毀）
label 數量2（type + name）2（type + name）

關鍵心智模型

resource 是寫入意圖：「這個東西我要它存在、長這樣」。
data 是讀取意圖：「我要拿到這個東西的資訊，來幫助我寫其他 resource」。
最常見的搭配：用 data 讀別人管的東西（VPC、AMI、Secret），用 resource 建立自己要管的東西（EC2、RDS）。

2. Resource Block 完整語法

每個 resource 由四個部分組成：type、name、arguments、meta-arguments。

HCL · resource block 完整骨架 
resource "" "" {
  # ① 一般 arguments：由 provider 定義
  argument_a = "value"
  argument_b = 123

  # ② nested blocks：由 provider 定義（例如 ingress、network_interface）
  nested_block {
    inner = "value"
  }

  # ③ meta-arguments：由 OpenTofu 定義，所有 resource 通用
  count       = var.instance_count
  for_each    = var.subnets
  provider    = aws.tokyo
  depends_on  = [aws_iam_role.app]

  lifecycle {
    create_before_destroy = true
    prevent_destroy       = false
    ignore_changes        = [tags]
    replace_triggered_by  = [aws_kms_key.this]
  }

  provisioner "local-exec" {  # 一般避免使用，但語法上存在
    command = "echo created"
  }
}

Resource Type 與 Name

  • Type（第一個 label）：由 provider 決定，通常是 <provider>_<object>，例如 aws_instance、google_compute_instance、local_file
  • Name（第二個 label）：你自己取的名字，僅在當前 module 範圍內有意義；用來在 HCL 內部互相引用

同一個 module 內，type + name 的組合必須唯一。但你可以有兩個 name 不同的同 type 資源：

HCL · 命名範例 
resource "aws_instance" "web" { /* ... */ }    # OK
resource "aws_instance" "db"  { /* ... */ }    # OK
resource "aws_instance" "web" { /* ... */ }    # ❌ 錯誤：與第一個 web 衝突

Resource Address（資源位址）

Resource 的位址由 type.name 構成。如果用了 count 或 for_each，會多出索引：

場景位址形式範例
單一資源type.nameaws_instance.web
使用 counttype.name[index]aws_instance.web[0]
使用 for_eachtype.name[key]aws_instance.web["primary"]
子 module 內的資源module.X.type.namemodule.vpc.aws_subnet.public[0]

3. Resource 生命週期（CRUD）

每個 resource 都有四種基本動作，OpenTofu 會自動依設定變化計算該執行哪個。

stateDiagram-v2
    [*] --> Planning
    Planning --> Create: 設定中新增了該資源
    Planning --> UpdateInPlace: 屬性變更（不需重建）
    Planning --> Replace: 屬性變更需重建
    Planning --> Destroy: 設定中刪除該資源
    Planning --> NoOp: 設定無變化

    Create --> Active
    UpdateInPlace --> Active
    Replace --> Active: 先 destroy 後 create
    NoOp --> Active

    Active --> Planning: 下次 plan
    Destroy --> [*]

四種動作對應的 plan 符號

符號 動作 觸發條件 是否中斷服務
+createstate 中沒有，設定中有否（新增）
~update in-place屬性變更但 provider 支援原地修改視 provider 行為
-/+destroy + create（replace）變更了 force-new 屬性是（先銷毀後重建）
+/-create + destroy（搭配 create_before_destroy）同上但開了 lifecycle 設定較小（先建後拆）
-destroy設定中移除是

哪些屬性會觸發 replace？

Provider 為每個屬性決定它是 Optional、Computed 或 ForceNew。ForceNew 屬性變更時無法原地修改，必須重建。例如：

常見 ForceNew 屬性原因
aws_instance.subnet_idEC2 實例不能換 subnet
aws_instance.availability_zone同上
aws_db_instance.engineRDS 不能改引擎類型
aws_s3_bucket.bucketS3 bucket name 不能改
local_file.filename檔名變了等於不同檔案

小心 -/+ 對 production 的影響

每次 plan 看到 -/+（destroy + create）時要特別警覺，這代表服務會中斷。如果該資源有 stateful 資料（資料庫、ElastiCache、ECS task），重建可能造成資料遺失。對策：搭配 create_before_destroy = true 或重新設計，避免變更觸發 replace。

4. 屬性參照（Attribute Reference）

當你建立一個 resource，provider 會回傳該物件的所有屬性（id、arn、計算後的網域名稱等）。這些屬性可以在其他 block 引用，這就是 OpenTofu 自動推導依賴的關鍵。

引用語法

HCL · 屬性參照 
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id              # ← 引用 vpc 的 id
  cidr_block = aws_vpc.main.cidr_block      # 也可引用任何屬性
}

# 用 count 時用索引
resource "aws_instance" "web" {
  count     = 3
  subnet_id = aws_subnet.web.id
  ami       = "ami-abc..."
}

# 引用 count 出來的多個資源（splat 表達式）
output "instance_ids" {
  value = aws_instance.web[*].id            # 取得所有 id 組成 list
}

# 用 for_each 時用 key
resource "aws_instance" "shard" {
  for_each = toset(["a", "b", "c"])
  ami      = "ami-abc..."
}

output "shard_a_id" {
  value = aws_instance.shard["a"].id
}

常見的內建屬性

每個 resource 都有 provider 給的屬性，但有幾個是 OpenTofu 自己提供的「meta-attribute」：

屬性意義
self當前 resource 自身（只能用在 provisioner、postcondition）
count.index使用 count 時的索引（從 0 開始）
each.key / each.value使用 for_each 時的鍵與值
path.module當前 module 的目錄路徑
path.rootroot module 的目錄路徑
path.cwdOpenTofu 執行時的當前工作目錄
terraform.workspace當前 workspace 名稱

5. Data Source 完整介紹

Data source 用 data block 宣告，用來從外部讀取資訊但不管理它。

HCL · data source 範例 
# 範例 1：找出最新的 Ubuntu 22.04 AMI
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]   # Canonical 官方帳號

  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-amd64-server-*"]
  }

  filter {
    name   = "virtualization-type"
    values = ["hvm"]
  }
}

# 範例 2：讀取另一團隊管理的 VPC
data "aws_vpc" "shared" {
  filter {
    name   = "tag:Name"
    values = ["shared-prod-vpc"]
  }
}

# 範例 3：讀取目前 caller 身份
data "aws_caller_identity" "current" {}

# 範例 4：讀取當前 region
data "aws_region" "current" {}

# 引用 data source 結果
resource "aws_instance" "web" {
  ami       = data.aws_ami.ubuntu.id        # ← data 的 id
  subnet_id = data.aws_vpc.shared.default_subnet_id

  tags = {
    Account = data.aws_caller_identity.current.account_id
    Region  = data.aws_region.current.name
  }
}

Data Source 三大用途

  1. 讀取雲端既有資源：找 AMI、找已存在的 VPC、查 IAM role 等
  2. 讀取本地計算資料：local-only data source 例如 local_file（讀本地檔案）、aws_iam_policy_document（產生 IAM 政策 JSON）、archive_file（打包 ZIP）
  3. 跨 stack 讀取：用 terraform_remote_state 從另一個 OpenTofu 專案的 state 讀輸出值

Local-only data source：本地計算工具

HCL · 用 data source 產生 IAM 政策 
data "aws_iam_policy_document" "s3_read" {
  statement {
    sid    = "AllowS3Read"
    effect = "Allow"

    actions = [
      "s3:GetObject",
      "s3:ListBucket",
    ]

    resources = [
      aws_s3_bucket.app.arn,
      "${aws_s3_bucket.app.arn}/*",
    ]
  }
}

resource "aws_iam_policy" "s3_read" {
  name   = "s3-read"
  policy = data.aws_iam_policy_document.s3_read.json
}

這比手寫 JSON 字串安全很多——provider 會幫你驗證語法，IDE 還能 autocomplete。

跨 stack 讀取：terraform_remote_state

HCL · 讀取另一個 stack 的 outputs 
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket = "my-tf-state"
    key    = "network/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_instance" "web" {
  subnet_id = data.terraform_remote_state.network.outputs.public_subnet_id
}

terraform_remote_state 的取捨

方便但形成緊耦合：被讀的 stack 一旦改 output 名稱就會炸。對於穩定 contract（例如「core network stack 永遠輸出 vpc_id」），可以用；對快速演進的 stack，不如用 SSM Parameter Store / data source 查雲端的方式更鬆耦合。

6. Data Source 何時跑、跑幾次

Data source 的執行時機比 resource 更微妙。理解這點能避免一些 plan 階段的錯誤。

flowchart TD
    Start[tofu plan]
    Start --> Q1{data 的 arguments
是否引用了未建立
的 resource？}
    Q1 -->|否| Refresh[在 refresh 階段讀取
plan 中可看到實際值]
    Q1 -->|是| Defer[延遲到 apply 階段才讀取
plan 中顯示為 known after apply]

    Refresh --> Plan2[Plan output 顯示真實值]
    Defer --> Plan3["Plan output 顯示
(known after apply)"]

    style Refresh fill:#dcfce7,stroke:#16a34a
    style Defer fill:#fef3c7,stroke:#d97706

三種觸發 deferred read 的情況

  1. Data source 的 arguments 引用了某個 managed resource 的計算屬性（plan 階段還不知道值）
  2. Data source 透過 depends_on 顯式依賴一個有變更計畫的 resource
  3. Data source 的 arguments 包含其他「至 apply 才知」的值
HCL · 觸發 deferred read 的範例 
# Resource：state 中還沒建立
resource "aws_s3_bucket" "logs" {
  bucket = "my-app-logs-${random_id.suffix.hex}"
}

resource "random_id" "suffix" {
  byte_length = 4
}

# Data source：依賴上面 bucket 的 arn（apply 後才知道）
# 這個 data source 會 defer 到 apply 階段才讀取
data "aws_iam_policy_document" "logs_policy" {
  statement {
    actions   = ["s3:PutObject"]
    resources = ["${aws_s3_bucket.logs.arn}/*"]   # 引用尚未建立的資源
  }
}

Data Source 的 lifecycle

Data source 也支援 lifecycle block，但選項比 resource 少：

HCL · data source lifecycle 
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter { name = "name", values = ["ubuntu-22.04-*"] }

  lifecycle {
    # 1.10+：條件性讀取，false 時當作不存在
    enabled = var.use_dynamic_ami

    # postcondition：apply 後驗證讀到的值
    postcondition {
      condition     = self.architecture == "x86_64"
      error_message = "AMI must be x86_64."
    }
  }
}

7. 依賴關係：implicit vs explicit

OpenTofu 的依賴推導機制是它能正確處理大型基礎設施的核心。

Implicit 隱式依賴：自動推導

當你在 resource A 的 arguments 中引用了 resource B 的屬性，OpenTofu 自動推斷「A 依賴 B」，並在 graph 中建立邊。絕大多數情境用隱式依賴就夠了，且應該優先採用。

HCL · 隱式依賴 
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

# OpenTofu 自動推斷：subnet 必須在 vpc 之後建立
resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id      # ← 隱式依賴點
  cidr_block = "10.0.1.0/24"
}

Explicit 顯式依賴：用 depends_on

當依賴關係不能從 HCL 表達式中推斷時，用 depends_on 強制宣告。常見場景：

  • 資源 A 需要某個 IAM policy 已附加才能正常運作，但 A 的設定中沒直接引用該 policy
  • 資源 A 在 user_data 內呼叫某個 SSM parameter，OpenTofu 看不出依賴
  • 資源建立順序有 cloud API 的最終一致性問題（很罕見）
HCL · 顯式依賴 
resource "aws_iam_role" "lambda" {
  name = "lambda-exec"
  # ...
}

resource "aws_iam_role_policy_attachment" "lambda_logs" {
  role       = aws_iam_role.lambda.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_lambda_function" "app" {
  function_name = "my-app"
  role          = aws_iam_role.lambda.arn
  # ...

  # depends_on：顯式宣告必須先建立 policy attachment
  # 因為 lambda 設定中沒引用到 attachment 資源
  depends_on = [aws_iam_role_policy_attachment.lambda_logs]
}

depends_on 是最後手段

能用隱式依賴就用隱式。depends_on 過度使用會讓 graph 邊數爆增，apply 變慢，且失去屬性級的精確依賴（OpenTofu 只知道「有依賴」但不知道是哪個屬性）。如果你發現自己頻繁用 depends_on，多半是設計可以改進。

8. lifecycle meta-argument 全解

lifecycle 是 resource 內最重要的 meta-argument 區塊，控制 OpenTofu 如何處理該資源的生命週期動作。

四個主要設定

設定用途常見場景
create_before_destroy 需 replace 時，先建立新的再銷毀舊的 Load balancer、ASG 想避免短暫中斷
prevent_destroy 禁止 OpenTofu 銷毀該資源 Production 資料庫、S3 bucket 防呆
ignore_changes 忽略指定屬性的 drift ASG 的 desired_capacity（被 autoscaler 動態調整）
replace_triggered_by 當其他資源變更時，觸發本資源的 replace 當 KMS key 換時，強制重建相關資源

create_before_destroy：避免中斷的關鍵

HCL · 零停機 launch template 更新 
resource "aws_launch_template" "web" {
  name_prefix   = "web-"   # 注意是 prefix 不是固定名（避免衝突）
  image_id      = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  lifecycle {
    create_before_destroy = true
  }
}

注意：開啟 create_before_destroy 時，name 必須能同時存在新舊兩份。AWS 多數資源用 name_prefix 而非固定 name 解決這個問題。

prevent_destroy：production 防呆

HCL · 保護 production DB 
resource "aws_db_instance" "prod" {
  identifier        = "prod-db"
  engine            = "postgres"
  instance_class    = "db.r6g.large"
  allocated_storage = 100

  lifecycle {
    prevent_destroy = true
  }
}

當試圖透過設定變更觸發銷毀時，OpenTofu 會直接 refuse，並顯示明確錯誤訊息。

prevent_destroy 的盲點

它只擋「設定變更引發的 destroy」。它不擋：①直接 tofu destroy；②從設定中整個 resource block 移除（block 都沒了，prevent_destroy 也跟著消失）。要完整保護，配合 IAM 政策、CI/CD approval、backend 的 versioning 才夠。

ignore_changes：忽略外部變動

HCL · ignore_changes 範例 
resource "aws_autoscaling_group" "web" {
  min_size         = 2
  max_size         = 10
  desired_capacity = 2

  lifecycle {
    # autoscaler 會動態調整 desired_capacity，OpenTofu 不要管
    ignore_changes = [
      desired_capacity,
      tag,                        # 整個 tag 屬性
      tags["LastDeployedAt"],     # 只忽略某個 tag key
    ]
  }
}

# 也可以忽略所有屬性（資源建立後完全不管）
resource "aws_iam_user" "managed_externally" {
  name = "external-user"

  lifecycle {
    ignore_changes = all
  }
}

replace_triggered_by：跨資源 replace

有時你想說：「當 X 變了，Y 也要重建」，但這個關聯不在 HCL 表達式裡。

HCL · 強制 replace 
resource "aws_kms_key" "secrets" {
  description = "App secrets"
}

resource "aws_secretsmanager_secret" "db_password" {
  name       = "db-password"
  kms_key_id = aws_kms_key.secrets.arn

  lifecycle {
    # 當 KMS key 重建時，強制重建這個 secret
    # （否則它仍會用舊 key 解密，可能無法讀取）
    replace_triggered_by = [aws_kms_key.secrets]
  }
}

9. precondition / postcondition：守護資源契約

OpenTofu 1.6+ 提供 precondition 與 postcondition，讓你能在 resource 上聲明「我假設什麼為真」「我保證輸出什麼」，並在違反時提早報錯。

HCL · 完整 precondition / postcondition 範例 
data "aws_ami" "app" {
  most_recent = true
  owners      = ["self"]
  filter { name = "name", values = ["app-*"] }
}

resource "aws_instance" "app" {
  instance_type = "t3.micro"
  ami           = data.aws_ami.app.id

  lifecycle {
    # precondition：建立前的假設驗證
    precondition {
      condition     = data.aws_ami.app.architecture == "x86_64"
      error_message = "AMI 必須是 x86_64 架構，目前是 ${data.aws_ami.app.architecture}"
    }

    # postcondition：apply 後的保證驗證
    postcondition {
      condition     = self.public_dns != ""
      error_message = "EC2 實例必須有 public DNS。請確認 VPC 啟用了 DNS hostnames。"
    }
  }
}
區塊檢查時機用途可用 self?
precondition動作執行前檢查依賴的資料是否符合預期否（資源還沒建立）
postcondition動作執行後確保資源最終狀態符合契約是（self 指該資源）

用 condition 把假設變成契約

傳統做法：用 README 寫「請確保 VPC 開了 DNS hostnames」，下個工程師沒看到還是會出錯。改用 postcondition：「VPC 沒開 DNS 我就 fail，並印出明確訊息」。把假設文字化成執行時檢查，是大型團隊降低錯誤的關鍵手段。

10. 特殊資源：terraform_data、null_resource

terraform_data：取代 null_resource 的現代方案

OpenTofu 內建的「黏合劑」資源，沒有真實 cloud 物件對應，純粹用來：

  • 觸發其他資源的 replace（搭配 replace_triggered_by）
  • 儲存任意值到 state 中（之前需用 null_resource + triggers）
  • 橋接 lifecycle 行為到非 resource 的值（local、變數）
HCL · terraform_data 範例 
# 場景：當 var.config_version 變動時，強制 EC2 重建
resource "terraform_data" "config_version" {
  input = var.config_version
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = "t3.micro"

  lifecycle {
    replace_triggered_by = [terraform_data.config_version]
  }
}

null_resource（舊式，仍可用）

來自 hashicorp/null provider，類似但需要額外 provider 宣告。新專案建議用 terraform_data 取代。

11. 常見陷阱與最佳實踐

陷阱 1：誤把 data 用成 resource

常見錯誤：「我想建立一個 IAM role 並讓它能被讀取」，誤寫成 data "aws_iam_role" "x"。data 只讀，不會建立。要建立用 resource。

陷阱 2：data source 找不到對象

當 data 的 filter 找不到符合的物件，OpenTofu 會直接報錯（不會回傳空值）。對應策略：

  • 確保物件確實存在（先用 AWS CLI 驗證）
  • 用 try() 函式包裹（OpenTofu 1.10+ 部分情境支援）
  • 改用 data.aws_xxx_count 這類「找得到才有值」的 data source

陷阱 3：循環依賴

HCL · ❌ 循環依賴 
resource "aws_security_group" "web" {
  ingress {
    security_groups = [aws_security_group.db.id]   # 引用 db sg
  }
}

resource "aws_security_group" "db" {
  ingress {
    security_groups = [aws_security_group.web.id]  # 引用 web sg
  }
}
# Error: Cycle detected

解法：把 ingress 拆成獨立的 aws_security_group_rule 資源（或新版的 aws_vpc_security_group_ingress_rule），讓 sg 本體只負責 group 定義。

陷阱 4：忘了 ignore_changes 導致無止境的 drift

常見於 ASG 與 autoscaler 並存、或 EKS node group 被 cluster autoscaler 動態管理。每次 OpenTofu plan 都顯示要把 desired_capacity 改回去，apply 後 autoscaler 又改回來。永遠的拉鋸戰。

解法：在 lifecycle 加 ignore_changes = [desired_capacity]。

最佳實踐速查

場景建議做法
新建資源用 resource。如果要重用既有的，改用 data 引入
引用其他資源屬性用屬性表達式，避免 depends_on
被 autoscaler 管理的屬性加入 ignore_changes
Production 資料庫、S3 bucket加 prevent_destroy + 配 IAM 政策
無停機更新（LB、ASG launch template）create_before_destroy + name_prefix
跨資源 replacereplace_triggered_by + terraform_data
守護資源契約precondition / postcondition
讀取另一團隊的 VPC / Subnetdata source（避免 hardcode ID）
產生 IAM 政策 JSONdata "aws_iam_policy_document"（不要手寫字串）

12. 本章重點與練習

重點回顧

  • resource 是受管資源（managed），OpenTofu 建立、修改、銷毀；data 是資料源，只讀取
  • Resource 位址格式：type.name，搭配 count 用 [N]，搭配 for_each 用 [key]
  • Resource 生命週期四種動作：create、update in-place、destroy + create（replace）、destroy
  • ForceNew 屬性變更會觸發 replace；對 production 慎重評估，搭配 create_before_destroy 降低中斷
  • 引用 resource 屬性時 OpenTofu 自動建立隱式依賴（implicit），這應該是首選；depends_on 是最後手段
  • Data source 在 plan 階段執行，但若 arguments 引用未建資源，會 defer 到 apply 階段
  • lifecycle 四大設定：create_before_destroy、prevent_destroy、ignore_changes、replace_triggered_by
  • precondition（執行前）與 postcondition（執行後）把假設轉成執行時檢查
  • terraform_data 取代舊式的 null_resource，用作 lifecycle 黏合劑
⚡ 動手實作 · Hands-on Lab 6

用 local provider 練習 resource 與 data source

不需雲端帳號，全程用 local provider 即可完成。

  1. 建立目錄 resources-lab/，先在裡面建立一個檔案 seed.txt，內容隨意
  2. 寫 main.tf：用 data source local_file 讀取 seed.txt 的內容
  3. 用 resource local_file 建立 3 個新檔案，內容包含 seed.txt 的內容（用屬性參照 data.local_file.seed.content）
  4. 跑 tofu init、tofu plan、tofu apply
  5. 練習 A：手動修改 seed.txt，再跑 tofu plan。觀察 OpenTofu 偵測到 data source 內容變了，所有引用該 data 的 resource 都要 replace
  6. 練習 B：在你的某個 local_file 加上 lifecycle { ignore_changes = [content] }，再次修改 seed.txt 跑 plan，確認該資源不再 replace
  7. 練習 C：故意製造循環依賴（兩個 resource 互相引用對方屬性），跑 plan 觀察錯誤訊息
  8. 挑戰題：用 terraform_data 加上 replace_triggered_by，當變數 var.version 變動時，強制全部 local_file 重建。Hint：terraform_data { input = var.version }
  9. 進階挑戰：加上一個 postcondition，驗證每個生成檔案的 content_base64sha256 不為空字串
  10. 用 tofu destroy 清掉資源
