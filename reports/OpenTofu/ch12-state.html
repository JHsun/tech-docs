1. 為什麼 OpenTofu 需要 state

OpenTofu 是宣告式工具——你描述「目標長什麼樣」，工具決定「怎麼做」。但「怎麼做」需要知道「現在長什麼樣」。這個「現在的樣子」就是 state。

State 紀錄了什麼

  • 每個受管資源的唯一 ID（AWS instance 的 i-0abc...、S3 bucket 的 my-bucket）
  • 每個資源的所有屬性值（建立時填入的、雲端產生的、後續變更的）
  • 資源之間的依賴關係
  • 使用的 provider 版本 與 schema
  • State serial 與 lineage（防覆寫機制）
  • output 值（給其他 stack 透過 terraform_remote_state 讀取）

State 含有敏感資料

Provider 取得的所有屬性都會寫進 state，包括資料庫密碼、API token、private key、TLS cert 等。這就是為什麼：① state 絕對不能 commit 進 git；② 團隊環境必須用支援加密的 remote backend；③ OpenTofu 1.7+ 起提供 native state encryption（本章第 7 節詳述）。

JSON · terraform.tfstate（節錄）

  "version": 4,
  "terraform_version": "1.11.6",
  "serial": 7,
  "lineage": "abc-123-def-456",
  "outputs": {
    "vpc_id": {
      "value": "vpc-0abc123",
      "type": "string"
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "aws_vpc",
      "name": "main",
      "provider": "provider[\"registry.opentofu.org/hashicorp/aws\"]",
      "instances": [
        {
          "schema_version": 1,
          "attributes": {
            "id": "vpc-0abc123",
            "cidr_block": "10.0.0.0/16",
            "tags": {
              "Name": "primary"
            }
          },
          "sensitive_attributes": [],
          "dependencies": []
        }
      ]
    }
  ],
  "check_results": null
}

關鍵欄位解析

欄位意義
versionState 檔格式版本（目前是 4）
terraform_version最後寫入時的工具版本
serial遞增計數器，每次 apply 變更時 +1，用於樂觀鎖
lineageUUID，識別這份 state 的「血統」，用於防止意外覆寫不同 state
outputs當前 output 值的快照
resources所有受管資源的清單
resources[].modemanaged（resource）或 data（data source）
resources[].instances使用 count / for_each 時會有多個 instance
resources[].instances[].sensitive_attributes標記哪些屬性是 sensitive（仍以明文儲存，僅控制顯示）
resources[].instances[].dependencies該 instance 依賴的其他資源位址

lineage 防呆機制

lineage 是個 UUID。當 OpenTofu 寫 state 時會檢查目標的 lineage 是否相同；如果不同（代表那是別份 state），會 refuse 寫入。這是防止「把 stack A 的 state 不小心寫到 stack B 的位置」的最後防線。

3. Local backend：起步用

OpenTofu 預設使用 local backend，state 存成 terraform.tfstate（沒錯，仍沿用 terraform 字樣）放在工作目錄。

HCL · 顯式 local backend（通常省略） 
terraform {
  backend "local" {
    path = "terraform.tfstate"   # 預設值，可省略
  }
}

適用場景

  • 個人學習、實驗
  • 單人專案、且資源不重要
  • 剛起步，還沒選定 remote backend

不適用場景

  • 團隊協作：誰在用 state？最新的 state 在誰的筆電上？
  • CI/CD：每次跑都是新環境，state 會遺失
  • Production：state 是公司資產，不能放在個人筆電

第一週可以用 local，第二週開始就該 migrate 到 remote

新專案啟動時 local backend 是合理的快速起步方式，但進入正式開發前必須切到 remote。第 9 節會介紹遷移流程。

4. Remote backend 大全

OpenTofu 內建支援多種 remote backend，分兩大類：

分類Backend特點
雲端物件儲存s3AWS S3，最普及的選擇。OpenTofu 1.10+ 原生支援 S3 lockfile，不需 DynamoDB
azurermAzure Blob Storage，內建 blob lease 鎖定
gcsGoogle Cloud Storage，內建 atomic locking
通用協定http實作 HTTP REST API 的任何服務（GitLab Managed Terraform State、Atlantis 等）
kubernetesstate 存成 K8s Secret，適合 K8s-native 工作流程
ociOCI Object Storage（Oracle Cloud）
資料庫postgresPostgreSQL，內建 advisory lock
consulConsul KV store
cosTencent Cloud Object Storage

2026 年的選擇

① AWS 用戶：S3 backend + native lockfile（1.10+）
② Azure 用戶：azurerm backend + Azure AD auth
③ GCP 用戶：gcs backend
④ K8s-native：kubernetes backend + GitOps
⑤ Multi-cloud / 自架：postgres 或 http
⑥ 不要用：HCP Terraform 的 cloud {} block（OpenTofu 不支援）

backend block 必須在 root module

兩個重要限制

① backend block 不能用 variable（OpenTofu 1.8+ 部分放寬，但仍受限）。要動態設定，用 partial config + -backend-config。
② backend block 只在 root module 有效，child module 寫 backend 會被忽略並警告。

5. S3 backend 完整配置（含 1.10+ native locking）

S3 是最常用的 backend，這裡示範 production 級別的完整配置。

建立 backend 基礎設施（一次性的 bootstrap）

HCL · 用 OpenTofu 建立自己的 backend bucket 
# backend-bootstrap/main.tf
# 一個獨立的小專案，先用 local state 建這些資源，之後就能用它們

resource "aws_s3_bucket" "tofu_state" {
  bucket = "myorg-tofu-state"

  lifecycle {
    prevent_destroy = true   # 防誤刪
  }
}

# 必開：版本控制（萬一 state 被寫壞才能還原）
resource "aws_s3_bucket_versioning" "tofu_state" {
  bucket = aws_s3_bucket.tofu_state.id
  versioning_configuration {
    status = "Enabled"
  }
}

# 必開：server-side encryption（加上 KMS）
resource "aws_kms_key" "tofu_state" {
  description             = "OpenTofu state encryption"
  deletion_window_in_days = 30
  enable_key_rotation     = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "tofu_state" {
  bucket = aws_s3_bucket.tofu_state.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.tofu_state.arn
    }
    bucket_key_enabled = true
  }
}

# 必開：擋掉所有 public access
resource "aws_s3_bucket_public_access_block" "tofu_state" {
  bucket                  = aws_s3_bucket.tofu_state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# 可選：lifecycle 自動清掉舊版本
resource "aws_s3_bucket_lifecycle_configuration" "tofu_state" {
  bucket = aws_s3_bucket.tofu_state.id
  rule {
    id     = "expire-old-versions"
    status = "Enabled"
    noncurrent_version_expiration {
      noncurrent_days = 90
    }
  }
}

使用 S3 backend（OpenTofu 1.10+ 推薦）

HCL · 1.10+ 新式（不需要 DynamoDB） 
terraform {
  backend "s3" {
    bucket = "myorg-tofu-state"
    key    = "production/web/terraform.tfstate"
    region = "us-east-1"

    encrypt    = true       # SSE-S3 / SSE-KMS（雙重保護）
    kms_key_id = "arn:aws:kms:us-east-1:123456789012:key/abc..."

    # OpenTofu 1.10+ 獨家：原生 S3 lockfile，省去 DynamoDB
    use_lockfile = true
  }
}

舊式（仍可用，需 DynamoDB）

HCL · 1.10 之前的傳統做法 
terraform {
  backend "s3" {
    bucket         = "myorg-tofu-state"
    key            = "production/web/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "tofu-state-locks"   # 需要事先建立 DynamoDB 表
  }
}

Partial Config：避免把 bucket 名稱 hardcode

HCL · backend.tf（部分設定） 
terraform {
  backend "s3" {
    # 只放跨環境通用的設定
    encrypt      = true
    use_lockfile = true
  }
}

6. State Locking 機制

當兩個人同時跑 tofu apply，可能造成 state 損毀。Lock 機制確保同時間只有一個人能寫 state。

各 backend 的 lock 實作

Backend鎖定機制
S3（1.10+）S3 lockfile（同 bucket 內 .tflock 檔，用 conditional write）
S3（1.9 以前）外部 DynamoDB 表，conditional put
azurermBlob lease（內建）
gcsGCS object generation 機制（內建）
postgresPostgreSQL advisory lock
consulConsul session
local本地檔案 lock（同一台機器內有效）
http由 server 端實作（PUT /lock、DELETE /unlock）

Lock 的工作流程

sequenceDiagram
    participant U1 as 使用者 1
    participant U2 as 使用者 2
    participant Lock as Lock Mechanism
    participant State as State Storage

    U1->>Lock: tofu apply
取得 lock
    Lock-->>U1: lock 取得（id=ABC）
    U1->>State: 讀取 state

    Note over U2: 同時間
    U2->>Lock: tofu apply
嘗試取得 lock
    Lock-->>U2: ❌ Failed: 已被 ABC 持有

    U1->>State: 寫入新 state
    U1->>Lock: 釋放 lock
    Lock-->>U1: 已釋放

    U2->>Lock: 重試取得 lock
    Lock-->>U2: lock 取得（id=DEF）

解除卡住的 lock

偶爾會發生 OpenTofu 異常退出沒釋放 lock 的情況。解法：

Bash · force-unlock 
# 看 lock 訊息中的 ID
tofu apply
# Error: state is locked
# Lock ID: 12345678-abcd-...

# 強制解鎖（先確認真的沒人在用！）
tofu force-unlock 12345678-abcd-...

force-unlock 是核武器

強制解鎖前務必確認沒有其他人/CI 在執行。同時 unlock 與另一個 apply 並行，會讓 state 進入不可預測狀態。最佳做法：在 Slack/Teams 廣播一下，等 5 分鐘確認沒人在動再 unlock。

7. Native State Encryption（OpenTofu 1.7+ 獨家）

OpenTofu 1.7 推出的原生 state 加密是它最重要的獨家功能之一。state 在離開你的機器之前就已經加密，server 端只看到密文。

Server-side encryption vs Client-side encryption

面向Server-side（如 S3 SSE）Client-side（OpenTofu 1.7+）
加密發生在S3 server你的機器（CLI 或 CI runner）
傳輸時明文（雖有 TLS）密文
誰能看到明文有 S3 access 的人只有持有 encryption key 的人
誰持有金鑰AWS（除非用 customer-managed KMS）你（與你信任的 KMS）
抵禦 backend 被入侵否是

Defense-in-depth：兩種一起用

正確做法是 S3 SSE + OpenTofu native encryption 一起用。SSE 是基線、便宜、無腦；native encryption 是真正的防線。

基本配置（用 PBKDF2 + passphrase）

HCL · encryption block 
terraform {
  required_version = ">= 1.7.0"

  backend "s3" {
    bucket  = "myorg-tofu-state"
    key     = "production/terraform.tfstate"
    region  = "us-east-1"
    encrypt = true
  }

  encryption {
    # 1. 金鑰提供者：從 passphrase 衍生
    key_provider "pbkdf2" "main" {
      passphrase = var.encryption_passphrase
    }

    # 2. 加密方法：AES-GCM
    method "aes_gcm" "state" {
      keys = key_provider.pbkdf2.main
    }

    # 3. 套用到 state
    state {
      method = method.aes_gcm.state
    }

    # 4. 也加密 plan 檔
    plan {
      method = method.aes_gcm.state
    }
  }
}

variable "encryption_passphrase" {
  type      = string
  sensitive = true
}

跑 OpenTofu 時透過環境變數傳入 passphrase：

Bash 
export TF_VAR_encryption_passphrase="$(secret-tool lookup tofu-passphrase main)"
tofu init
tofu apply

Production 等級：用 KMS

HCL · AWS KMS key provider 
terraform {
  encryption {
    key_provider "aws_kms" "main" {
      kms_key_id = "arn:aws:kms:us-east-1:123456789012:key/abc..."
      region     = "us-east-1"
      key_spec   = "AES_256"
    }

    method "aes_gcm" "state" {
      keys = key_provider.aws_kms.main
    }

    state {
      method = method.aes_gcm.state
      enforced = true   # 必須加密，否則 refuse
    }

    plan {
      method = method.aes_gcm.state
      enforced = true
    }
  }
}

三種 key provider 比較

Key Provider金鑰來源適合對象
pbkdf2從 passphrase 衍生個人專案、簡單環境
aws_kmsAWS KMSAWS 環境
gcp_kmsGCP KMSGCP 環境
openbao / vaultHashiCorp Vault / OpenBaomulti-cloud、企業
staticHCL 內 hardcode（測試用）絕不用於 production

從未加密遷移到加密

HCL · 含 fallback 的遷移配置 
terraform {
  encryption {
    key_provider "aws_kms" "main" {
      kms_key_id = var.kms_key_arn
      region     = var.region
    }

    method "aes_gcm" "state" {
      keys = key_provider.aws_kms.main
    }

    # 這個讓 OpenTofu 能讀「未加密的舊 state」
    method "unencrypted" "migration" {}

    state {
      method = method.aes_gcm.state

      fallback {
        method = method.unencrypted.migration   # 暫時容許讀未加密 state
      }
    }
  }
}

遷移流程：

  1. 加上含 fallback 的 encryption block
  2. 跑 tofu init 與 tofu apply -refresh-only（讀未加密、寫加密）
  3. 確認 state 已加密（從 backend 直接 cat 應該看到 binary）
  4. 移除 fallback block
  5. 下一次 apply 開始嚴格加密模式

金鑰輪替

HCL · 兩把金鑰共存做輪替 
terraform {
  encryption {
    key_provider "aws_kms" "old" {
      kms_key_id = var.old_kms_key_arn
      region     = "us-east-1"
    }

    key_provider "aws_kms" "new" {
      kms_key_id = var.new_kms_key_arn
      region     = "us-east-1"
    }

    method "aes_gcm" "rotate" {
      keys = key_provider.aws_kms.new   # 新寫入用 new key
    }

    state {
      method = method.aes_gcm.rotate

      fallback {
        # 讀的時候若是舊 key 加密的也能解
        method = method "aes_gcm" "old_method" {
          keys = key_provider.aws_kms.old
        }
      }
    }
  }
}

8. tofu state 子指令完整介紹

tofu state 系列指令用於檢視與修改 state 內容。修改類指令會直接寫 state，使用前務必備份。

指令用途會修改 state？
tofu state list列出所有 resource address否
tofu state show <addr>顯示單一資源完整屬性否
tofu state pull把遠端 state 印到 stdout否
tofu state push把本地檔案推到遠端 state（高危！）是
tofu state mv <src> <dst>重新命名資源（重構用）是
tofu state rm <addr>從 state 移除（不銷毀雲端資源）是
tofu state replace-provider <old> <new>更換 provider 來源（例如從 hashicorp 換成 opentofu）是

常用實戰範例

Bash · state 子指令實戰 
# 看有哪些資源
tofu state list

# 看某個資源詳情（含敏感屬性）
tofu state show aws_db_instance.main

# 把 state 拉成 JSON（給其他工具吃）
tofu state pull > state.json

# 重新命名資源（不會 destroy + create）
tofu state mv aws_instance.web aws_instance.web_primary

# 把資源從 state 移除（雲端資源還在）
# 例如：把資源轉給另一個 stack 管理時用
tofu state rm aws_instance.legacy

# 一次處理多個（搭配 wildcards）
tofu state list | grep '^aws_subnet\.public' | xargs -L1 tofu state rm

state mv vs moved block

OpenTofu 1.x 提供 moved block 取代 tofu state mv 的命令式做法：

HCL · moved block 的宣告式重構 
# 把 aws_instance.web 改名成 aws_instance.web_primary
moved {
  from = aws_instance.web
  to   = aws_instance.web_primary
}

resource "aws_instance" "web_primary" {
  # ...
}

第 13 章會詳細介紹 moved、removed、import 三個宣告式重構 block。它們應該優先於 tofu state mv/rm 命令式操作。

9. Backend 遷移與 state 移動

Local → Remote 遷移

從 local backend 遷移到 S3：

Bash · backend 遷移 
# 1. 備份本地 state
cp terraform.tfstate terraform.tfstate.backup-$(date +%Y%m%d)

# 2. 在 main.tf 加上 backend block
cat >> main.tf <<'EOF'
terraform {
  backend "s3" {
    bucket       = "myorg-tofu-state"
    key          = "production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
EOF

# 3. 跑 init，OpenTofu 會問是否複製本地 state 到 remote
tofu init
# Initializing the backend...
# Do you want to copy existing state to the new backend? [yes/no]
# 輸入 yes

# 4. 確認
tofu state list
# 應該看到所有資源都在

更換 Remote backend

Bash · 從 backend A 遷移到 backend B 
# 1. 修改 backend block 為新設定

# 2. 先備份遠端 state
tofu state pull > state-backup-$(date +%Y%m%d-%H%M%S).json

# 3. 跑 init -migrate-state
tofu init -migrate-state
# Do you want to copy existing state to the new backend? [yes/no]
# yes

# 4. 確認
tofu plan
# 應顯示 No changes

跨 stack 移動資源

有時你想把某些資源從 stack A 移到 stack B（例如把 IAM 資源從 app stack 抽到 platform stack）。OpenTofu 1.8+ 提供 tofu state mv 支援跨 state 移動：

Bash · 跨 state 移動 
# 在 stack A 目錄
cd stack-a/

# 把 aws_iam_role.app_role 從本 state 移到 stack B 的 state
tofu state mv \
  -state-out=../stack-b/terraform.tfstate \
  aws_iam_role.app_role \
  aws_iam_role.app_role

# 注意：兩個 state 都會有變動，務必各自備份

10. 災難復原與 state 損毀處理

場景 A：state 被意外覆寫

S3 versioning 開啟時可從歷史版本還原：

Bash · S3 versioning 還原 
# 1. 列出版本
aws s3api list-object-versions \
  --bucket myorg-tofu-state \
  --prefix production/terraform.tfstate

# 2. 找到要還原的版本 ID

# 3. 把舊版本複製為當前版本
aws s3api copy-object \
  --bucket myorg-tofu-state \
  --copy-source "myorg-tofu-state/production/terraform.tfstate?versionId=ABC123" \
  --key production/terraform.tfstate

# 4. 跑 plan 確認
tofu plan

場景 B：state 與雲端不同步（drift）

有人在 console 改了東西，state 不知道。處理方式：

Bash · refresh + plan 
# 只更新 state 不變動雲端，看出差異
tofu plan -refresh-only

# 接受 drift 為新基準（apply 並只更新 state）
tofu apply -refresh-only

# 接受並把雲端改回設定檔的樣子（一般 apply）
tofu apply

場景 C：資源在雲端被刪除但 state 還在

OpenTofu 下次 apply 會試圖重建。如果你想接受刪除：

Bash 
tofu state rm aws_instance.removed_externally

場景 D：把現有雲端資源納入 OpenTofu 管理（import）

HCL · import block（OpenTofu 1.5+） 
import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket-name"
}

resource "aws_s3_bucket" "legacy" {
  bucket = "my-existing-bucket-name"
  # ...
}

第 13 章會詳細講 import block 與舊式的 tofu import 指令。

場景 E：state 完全遺失（最壞）

如果連 versioning 都沒有，又沒有任何備份，唯一辦法是：

  1. 用 import block 把每個雲端資源逐一匯入新 state
  2. 對於小 stack 還可行；大 stack（>100 資源）非常痛苦
  3. 所以一定要 backend versioning + 定期備份

11. 常見陷阱與最佳實踐

陷阱 1：把 state commit 進 git

新人最常犯的錯誤。.gitignore 必須有：

Plaintext · .gitignore 
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
crash.log
crash.*.log
override.tf
override.tf.json
*_override.tf
*_override.tf.json
.terraformrc
terraform.rc

陷阱 2：兩個 stack 指向同一個 state

絕對不要同時用兩份 .tf 設定指向同一個 state key。雖然 lock 機制會擋住同時 apply，但兩份設定的差異會互相覆蓋對方的資源。

陷阱 3：忘了 backend bucket 開 versioning

沒 versioning 等於沒備份。第 5 節已強調必開。

陷阱 4：state 包含 sensitive 但 backend 沒加密

S3 SSE 是免費且必開的。再加上 OpenTofu 1.7+ 的 native encryption 形成 defense-in-depth。

陷阱 5：在 child module 寫 backend

會被忽略且警告。Backend 只在 root module 有效。

陷阱 6：直接編輯 state 檔

看到 state JSON 想手動改某個值。幾乎一定會壞掉（serial、checksum、依賴關係很難手動維護一致）。要改用 tofu state 子指令或 moved block。

最佳實踐速查

主題建議
個人學習local backend 即可
團隊 AWSS3 + use_lockfile=true（1.10+）+ KMS encrypt + versioning
團隊 Azureazurerm + use_azuread_auth + versioning
團隊 GCPgcs + customer-managed CMEK
State key 結構{org}/{team}/{env}/{component}/terraform.tfstate
Backend bucket必開 versioning、SSE、block public access、prevent_destroy
Sensitive 保護S3 SSE + OpenTofu native encryption（雙保險）
金鑰管理用 KMS（不用 passphrase）、開 key rotation
state 重構優先用 moved block，避免手動 tofu state mv
納管既有資源用 import block（不用舊式 tofu import 指令）
多環境每環境獨立 state key 與 IAM

備份策略backend versioning + 定期 tofu state pull 異地備份
force-unlock務必確認沒人在用，最好 Slack 廣播

12. 本章重點與練習

重點回顧

  • State 是 OpenTofu 的記憶系統，紀錄所有受管資源的 ID、屬性、依賴
  • State 含明文 secret（即使 variable 標 sensitive 也會明文寫入 state），必須加密保護
  • Local backend 起步用即可，正式專案必須 remote backend
  • OpenTofu 1.10+ S3 backend use_lockfile = true 不再需要 DynamoDB
  • Backend bucket 必備：versioning、SSE、block public access、prevent_destroy
  • State locking 各 backend 機制不同，但 force-unlock 是核武器，務必小心
  • OpenTofu 1.7+ 獨家：native client-side state encryption，用 encryption {} block 配 KMS / passphrase / Vault
  • Defense-in-depth：S3 SSE + OpenTofu native encryption 一起用
  • tofu state list/show/pull 是只讀，mv/rm/push 會修改 state（用前備份）
  • 結構性重構優先用 moved / removed / import block，而非命令式 tofu state mv
  • 災難復原靠 backend versioning：S3 / GCS 啟用 versioning、Azure 啟用 blob versioning
⚡ 動手實作 · Hands-on Lab 12

State 管理全方位演練

  1. 建立 state-lab/，先用 local backend，建立幾個 local_file resource，跑 apply 後檢視 terraform.tfstate 內容（version、serial、lineage 等欄位）
  2. 練習 A · state 檢視：跑 tofu state list、tofu state show <addr>、tofu state pull | jq .，理解輸出
  3. 練習 B · state mv：用 tofu state mv 把某個 resource 改名，再 plan 確認 No changes（state 已知道新名字）
  4. 練習 C · moved block：把另一個 resource 用 moved block 重構而不用命令式 mv，確認 plan 顯示「重新命名」而不是「destroy + create」
  5. 練習 D · state rm：故意手動刪除某個 local_file（用 OS 指令），跑 tofu plan -refresh-only 看 OpenTofu 偵測到 drift；再用 tofu state rm 接受外部刪除
  6. 練習 E · 模擬 backend versioning：把 terraform.tfstate 複製成 tfstate.v1，做幾次 apply 變更，再把舊版蓋回來，跑 plan 看會發生什麼
  7. 挑戰題 1：（如果有 AWS 帳號）建立 S3 bucket + KMS key，把 state 從 local 遷移到 S3 backend with use_lockfile = true（OpenTofu 1.10+）
  8. 挑戰題 2：加上 OpenTofu native encryption block 用 PBKDF2 + passphrase；確認 state 在 S3 上是 binary（不可讀），但本地能正常 plan
  9. 挑戰題 3：模擬金鑰輪替——把 passphrase 從 v1 改成 v2，加 fallback 段保留 v1 的 method，apply 後 state 變成用 v2 加密。再移除 fallback。
  10. 用 tofu destroy 清掉資源
