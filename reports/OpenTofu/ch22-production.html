1. 為什麼 production 不同

Part 1-4 教你「怎麼做」OpenTofu，第 21 章教你「怎麼自動化」。本章是最後一塊拼圖：「在團隊與生產環境怎麼做才不會炸」。

Production 與個人專案的本質差異

① 影響範圍大：一個錯誤可能讓上千用戶斷服；② 無法 Ctrl-Z：state 損毀、資源誤刪都很難回復；③ 多人寫一份 codebase：紀律 > 個人偏好；④ 監管要求：SOC 2 / HIPAA / FedRAMP 等需可審計；⑤ 成本壓力：誤建一條 NAT Gateway 一個月燒 30 美金。本章把這些痛點整理成可操作的最佳實踐。

3. State 拆分策略

單一 state 含 500+ 資源是 production 最大反模式。但拆過頭也痛——關鍵是找到對的切點。

三種錯誤的拆法

Plaintext · 反模式 
# ❌ 太單一（dangerous）：什麼都在一份 state
state/monolith.tfstate
# 一個錯改全部毀

# ❌ 太細（operationally painful）：每個 subnet 一份 state
state/vpc.tfstate
state/subnet-1a.tfstate
state/subnet-1b.tfstate
state/sg-web.tfstate
# 跨 stack output 串接很痛苦

# ✅ 對的切點：依 lifecycle 與 blast radius
state/networking.tfstate    # VPC、subnets（很少改）
state/platform.tfstate      # EKS、RDS（偶爾改）
state/apps/api.tfstate      # API service（每天改）
state/apps/workers.tfstate  # workers（每天改）

拆分原則

原則說明
變動頻率每天改的（app）vs 每週改的（platform）vs 每季改的（network）分開
Blast radius改 A 不該影響 B 的資源就分開
擁有團隊不同 team owns 的資源分開（IAM 該歸 platform team、app 該歸 app team）
合規要求PCI / HIPAA 的資源獨立，方便稽核
plan 時間plan 超過 60 秒考慮拆

跨 stack 共享資料

HCL · 用 terraform_remote_state 串接 
# networking stack 輸出 VPC ID 等
output "vpc_id"      { value = aws_vpc.main.id }
output "private_subnet_ids" { value = aws_subnet.private[*].id }

# platform stack 引用 networking 的 output
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "myorg-tofu-state"
    key    = "production/networking/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_eks_cluster" "main" {
  vpc_config {
    subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids
  }
}

替代：data source 直接查雲端

有時用 data "aws_vpc" { tags = { Name = "main" } } 直接查更乾淨——不依賴另一個 stack 的 output 命名，耦合度更低。但兩種都是合理選項，看團隊偏好。

4. Module 設計：500 行原則

業界經驗：模組大小臨界值

多個 production 團隊報告：

  • 平均 module 成長到 2,400 行才被拆
  • 2,400 行 module：plan 4-7 分鐘、apply 12-20 分鐘
  • 單一 security group 改動 forces plan 200 個無關資源
  • 實施 500 行限制後：plan/apply 速度提升 3 倍，blast radius 大幅降低

兩層 Module 設計

層級定位範例
Resource Module包一個 provider resource type，加上 sensible defaults 與 validationrds-instance、s3-bucket、security-group
Service Module把 resource modules 組合成可部署單位postgres-service（DB + subnet group + parameter group + SG）
Plaintext · 兩層架構範例 
modules/
├── resource/                      # 第一層：薄包裝
│   ├── rds-instance/              # 100-200 行，只管 DB instance
│   ├── rds-subnet-group/
│   ├── rds-parameter-group/
│   └── security-group/
└── service/                       # 第二層：組合
    └── postgres-service/          # 200-300 行，組合上述 resource module
        ├── main.tf                # 呼叫 modules/resource/rds-instance 等
        ├── variables.tf
        └── outputs.tf

# Bad pattern: 把 RDS、subnet group、parameter group、SG、IAM、CloudWatch alarm
# 全塞同一個 1500-line 「rds-everything」module

Resource Module 範例：rds-instance

HCL · modules/resource/rds-instance/main.tf（簡化版） 
variable "identifier" { type = string }
variable "engine_version" { type = string, default = "16.1" }
variable "instance_class" { type = string }
variable "subnet_group_name" { type = string }
variable "security_group_ids" { type = list(string) }

variable "instance_class" {
  type = string
  validation {
    condition     = can(regex("^db\\.(t3|t4g|m6g|r6g)\\.", var.instance_class))
    error_message = "Use t3/t4g/m6g/r6g instance classes only."
  }
}

resource "aws_db_instance" "this" {
  identifier        = var.identifier
  engine            = "postgres"
  engine_version    = var.engine_version
  instance_class    = var.instance_class
  allocated_storage = 100

  db_subnet_group_name   = var.subnet_group_name
  vpc_security_group_ids = var.security_group_ids

  # AWS 管理密碼，永不進 state
  manage_master_user_password = true

  storage_encrypted   = true
  deletion_protection = true
  skip_final_snapshot = false

  backup_retention_period = 30
  backup_window          = "03:00-04:00"
}

output "endpoint"    { value = aws_db_instance.this.endpoint }
output "identifier"  { value = aws_db_instance.this.identifier }

For_each key 穩定性（避免 identity churn）

HCL · 穩定 vs 不穩定 key 
# ❌ 用 list index 當 key（順序變更就 destroy/create）
resource "aws_subnet" "x" {
  count      = length(var.cidrs)
  cidr_block = var.cidrs[count.index]
}

# ✅ 用語意化 key（穩定不變）
resource "aws_subnet" "x" {
  for_each   = var.subnet_config   # map(string)，key 是 "public-1a"、"public-1b"...
  cidr_block = each.value
  tags       = { Name = each.key }
}

5. Secret 管理深入

四大鐵則

  1. 絕不寫進 state：用 manage_master_user_password = true、Secrets Manager data source、Vault dynamic secrets
  2. 絕不寫進 .tf：用 TF_VAR_ 環境變數注入、sensitive = true + 變數來源在 secret store
  3. 絕不出現在 plan output：sensitive 變數 + 不要 print plan JSON 到 PR comment
  4. 用 ephemeral（OpenTofu 1.11+）：真正不寫入 state 的 secret 取得

AWS managed_master_user_password（最推薦）

HCL · 讓 AWS 管 DB 密碼，永不在 state 
resource "aws_db_instance" "main" {
  identifier = "myapp-db"
  engine     = "postgres"

  username = "admin"
  manage_master_user_password = true   # AWS 自動產生、儲存在 Secrets Manager、自動 rotation

  # 不寫 password！
}

# 應用程式從 Secrets Manager 取
output "secret_arn" {
  value     = aws_db_instance.main.master_user_secret[0].secret_arn
  sensitive = true
}

Vault / OpenBao 動態 secret

HCL · OpenTofu 1.11+ ephemeral 取 secret 
ephemeral "openbao_kv_v2_secret" "db_creds" {
  mount = "kv"
  name  = "myapp/db"
}

resource "aws_db_instance" "main" {
  username    = "admin"
  password_wo = ephemeral.openbao_kv_v2_secret.db_creds.data["password"]
  password_wo_version = 1   # 改 version 才會更新密碼

  # password_wo 是 write-only，不寫入 state
}

SOPS：加密 tfvars 檔

有些 secret 必須在 .tfvars 中（例如非 AWS 的 token）。用 SOPS 加密後再 commit：

Bash · SOPS 流程 
# 1. 安裝 sops
brew install sops

# 2. 加密
sops --encrypt --kms arn:aws:kms:us-east-1:...:key/abc \
  --input-type yaml --output-type yaml \
  prod.secrets.yaml > prod.secrets.enc.yaml

# 3. commit prod.secrets.enc.yaml（純文字加密內容）

# 4. CI 中解密注入
sops --decrypt prod.secrets.enc.yaml | yq -r '.[]' | while read line; do
  export TF_VAR_$line
done

tofu apply

避免反模式：random_password + output

HCL · ❌ 經典反模式 
# ❌ 密碼進了 state、output、可能進了 CI log
resource "random_password" "db" {
  length = 32
}

resource "aws_db_instance" "main" {
  password = random_password.db.result
}

output "db_password" {
  value     = random_password.db.result
  sensitive = true   # 只是不顯示，仍寫入 state JSON
}

6. Drift Detection 完整實作

「有人在 console 改了 prod 卻沒人知道」是大型團隊噩夢。產品團隊報告：定期 drift detection 能在 6 小時內發現手動變更，否則可能等到下次 apply 才發現（plan 突然顯示要 destroy 別人在用的資源）。

排程方案：GitHub Actions cron

YAML · .github/workflows/drift-check.yml 
name: Drift Detection

on:
  schedule:
    - cron: '0 6 * * *'   # 每天 06:00 UTC
  workflow_dispatch:

permissions:
  id-token: write
  contents: read

jobs:
  drift-check:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        stack: [networking, platform, apps/api, apps/workers]

    steps:
      - uses: actions/checkout@v4
      - uses: opentofu/setup-opentofu@v2
        with: { tofu_version: 1.11.6 }

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/TofuPlanRole
          aws-region: us-east-1

      - run: tofu -chdir=envs/prod/${{ matrix.stack }} init -lockfile=readonly

      - name: Plan -refresh-only
        id: plan
        run: |
          set +e
          tofu -chdir=envs/prod/${{ matrix.stack }} plan -refresh-only -detailed-exitcode -no-color > drift.txt
          echo "exitcode=$?" >> $GITHUB_OUTPUT
        # 0 = 無 drift，2 = 有 drift，1 = error

      - name: Slack alert on drift
        if: steps.plan.outputs.exitcode == '2'
        uses: slackapi/slack-github-action@v1
        with:
          payload: |
            {
              "text": "⚠️ Drift detected in prod/${{ matrix.stack }}",
              "blocks": [{
                "type": "section",
                "text": { "type": "mrkdwn", "text": "*Drift detected:* prod/${{ matrix.stack }}\nRun ID: ${{ github.run_id }}" }
              }]
            }
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_DRIFT_WEBHOOK }}

處理 drift 的決策樹

flowchart TD
    Detected[偵測到 drift]
    Detected --> Q1{變更內容是？}
    Q1 -->|預期外的人為改動| A["人工調查
找到改動者並協調"]
    Q1 -->|外部自動化（如 ASG 自動 scale）| B["在 .tf 用 lifecycle ignore_changes
把該屬性排除"]
    Q1 -->|實際是合理改動| C["把改動納入 .tf
下次 apply 接受新狀態"]
    Q1 -->|資源被刪| D["用 import block 重建
或 state rm 接受刪除"]

    A --> E[修正 process
限制 console 寫入權限]

    style Detected fill:#fee2e2,stroke:#dc2626
    style E fill:#dcfce7,stroke:#16a34a

不要 auto-remediate

有些工具提供「自動把 drift 修回來」。production 強烈不建議——你不知道為什麼變動發生，自動修回可能讓正在處理 incident 的人被打斷。Drift detection 的目的是通知人類去看，由人決定處理方式。

7. 災難復原

備份策略：三層保險

層級機制RPO
第一層S3 Versioning（自動，每次寫入）0 秒（即時）
第二層S3 Cross-Region Replication 到 DR region分鐘級
第三層每日 tofu state pull 異地備份（S3 → 不同帳號或冷儲存）24 小時

State 損毀的還原流程

Bash · 從 S3 versioning 還原 
# 1. 列出歷史版本
aws s3api list-object-versions \
  --bucket myorg-tofu-state \
  --prefix prod/myapp/terraform.tfstate \
  --max-items 20

# 2. 還原指定版本
aws s3api copy-object \
  --bucket myorg-tofu-state \
  --copy-source "myorg-tofu-state/prod/myapp/terraform.tfstate?versionId=ABC..." \
  --key prod/myapp/terraform.tfstate

# 3. 跑 plan 確認
tofu plan
# 應該看到 No changes（如果還原版本與當前雲端一致）

Partial apply 處理

Apply 跑到一半失敗了，state 紀錄部分資源已建立。處理流程：

  1. 不要 panic 重跑 apply，先看 state 與雲端是否同步
  2. tofu plan 看下一個 apply 會怎麼做（會跳過已建立的、繼續做未完成的）
  3. 如果失敗的資源在雲端有殘留但 state 沒記錄：用 import block 納管
  4. 如果 state 記錄了但雲端沒成功建立：tofu state rm ADDR 移除孤兒紀錄
  5. 修復根本原因（quota、權限、設定錯誤）後再重跑 apply

用 import 重建 state（最壞情境）

state 完全遺失且無備份時：

HCL · 批次 import 
# 對每個雲端既有資源寫 import block
import {
  to = aws_vpc.main
  id = "vpc-0abc..."
}

import {
  to = aws_subnet.public["us-east-1a"]
  id = "subnet-0def..."
}

# 跑 plan 確認 No changes，再 apply
# 大型 stack（>100 資源）這種重建非常痛苦——所以一定要 backend versioning + 備份

8. Cost Estimation 與 FinOps

OpenTofu 沒內建成本估算，主流方案是 Infracost（OSS）。

Infracost CI 整合

YAML · GitHub Actions PR comment with cost 
- name: Setup Infracost
  uses: infracost/actions/setup@v3
  with:
    api-key: ${{ secrets.INFRACOST_API_KEY }}

- name: Generate base cost (main branch)
  run: |
    git checkout ${{ github.event.pull_request.base.ref }}
    infracost breakdown --path . --format json --out-file /tmp/base.json

- name: Generate cost diff (PR branch)
  run: |
    git checkout ${{ github.event.pull_request.head.ref }}
    infracost diff --path . --compare-to /tmp/base.json --format json --out-file /tmp/diff.json

- name: Post cost diff to PR
  run: infracost comment github --path /tmp/diff.json \
       --repo $GITHUB_REPOSITORY --pull-request ${{ github.event.pull_request.number }} \
       --github-token ${{ secrets.GITHUB_TOKEN }} --behavior update

Cost policy：超過閾值 fail PR

Bash · 簡單 threshold 檢查 
DIFF=$(jq -r '.diffTotalMonthlyCost' /tmp/diff.json)
THRESHOLD=500

if (( $(echo "$DIFF > $THRESHOLD" | bc -l) )); then
  echo "❌ Monthly cost diff (\$$DIFF) exceeds threshold (\$$THRESHOLD)"
  echo "Manual review required from FinOps team"
  exit 1
fi

標籤強制（cost allocation）

HCL · default_tags + 強制策略 
provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      Project     = var.project
      Environment = var.environment
      ManagedBy   = "OpenTofu"
      CostCenter  = var.cost_center   # FinOps 用此 attribute 拆帳
      Owner       = var.team_email
    }
  }
}

9. 零停機部署模式

create_before_destroy

關鍵資源升級時不該先 destroy 再 create——會造成短暫斷服。用 lifecycle.create_before_destroy：

HCL · 不可中斷的 launch template 升級 
resource "aws_launch_template" "app" {
  name_prefix   = "app-"   # 用 prefix 讓兩個版本可共存
  image_id      = data.aws_ami.app.id
  instance_type = "t3.medium"

  lifecycle {
    create_before_destroy = true
  }
}

resource "aws_autoscaling_group" "app" {
  launch_template {
    id      = aws_launch_template.app.id
    version = aws_launch_template.app.latest_version
  }

  # 漸進式 instance refresh
  instance_refresh {
    strategy = "Rolling"
    preferences {
      min_healthy_percentage = 90
      instance_warmup        = 300
    }
  }
}

Blue-Green 與 Canary

策略OpenTofu 實作
Blue-Green建立新 ASG / Lambda alias 指向新版本，把 ALB target group 流量切過去，舊的後續 destroy
Canary用 weighted DNS / ALB weighted target group 慢慢加新版流量比例
Lambda用 alias + version + traffic shifting

state 操作零停機

重構時用 moved block（第 13 章）而不是 destroy + create。例如改 resource 名、搬進 module、count 改 for_each，都不該觸發實體重建。

11. 合規與審計

主流框架對 IaC 的要求

框架對 IaC 的要求
SOC 2變更管理（誰改了什麼）、access control、audit log 保留
ISO 27001變更控制、approval workflow、權責分離
FedRAMP嚴格 access control、加密在傳輸與靜態、完整 audit log
HIPAAPHI 資料的加密、access log、災難復原計畫
PCI-DSS網路分段、加密、定期審查設定

Audit Log 三層

  1. Git history：所有 .tf 變更都在 PR、含 reviewer、merge time
  2. CI/CD log：誰觸發了 apply、何時、結果如何（保留 1+ 年）
  3. Cloud audit log：CloudTrail / Azure Activity Log / GCP Audit Log，記錄實際 API 呼叫

Approval Gate 設計

YAML · GitHub Environments protection 
# 在 GitHub repo Settings > Environments > production 設定
required_reviewers: [@platform-team, @security]
wait_timer: 5  # 5 分鐘冷卻期，避免衝動 approve
deployment_branch_policy:
  protected_branches: true
  custom_branch_policies: false  # 只允許 main branch 部署

Tag Policy 強制

Rego · 必填 tag policy 
package main

required_tags := {"Owner", "Environment", "CostCenter", "DataClassification"}

deny[msg] {
  rc := input.resource_changes[_]
  rc.change.actions[_] == "create"

  # 該資源類型支援 tags
  has_tags(rc.type)

  tags := object.get(rc.change.after, "tags", {})
  missing := required_tags - {key | tags[key]}

  count(missing) > 0
  msg := sprintf("%v missing required tags: %v", [rc.address, missing])
}

has_tags(type) {
  taggable_types := {"aws_instance", "aws_s3_bucket", "aws_db_instance", "aws_vpc"}
  taggable_types[type]
}

Sensitive 資源的雙人 approval

對於 KMS key、IAM role、production DB 等高風險資源，CI 中加入額外檢查：

YAML · 偵測 sensitive 變更 
- name: Detect sensitive changes
  id: sensitive
  run: |
    SENSITIVE=$(tofu show -json tfplan.bin | jq '
      [.resource_changes[] |
       select(.type | test("^aws_(kms|iam_role|iam_policy|db_instance)$")) |
       select(.change.actions[] | test("create|delete|replace"))
      ] | length')
    echo "count=$SENSITIVE" >> $GITHUB_OUTPUT

- name: Require security review
  if: steps.sensitive.outputs.count > 0
  uses: actions/github-script@v7
  with:
    script: |
      github.rest.issues.addLabels({
        issue_number: context.issue.number,
        owner: context.repo.owner,
        repo: context.repo.repo,
        labels: ['needs-security-review']
      });

本章重點回顧

  • Production 五大失敗模式：Identity Churn / Secret Exposure / Blast Radius / CI Drift / Compliance Gaps
  • State 拆分依 lifecycle + blast radius，networking / platform / apps 三層常見
  • Module 設計兩層：Resource Module（薄包裝）+ Service Module（組合），500 行原則提升 plan/apply 速度 3 倍
  • Secret 鐵則：絕不寫進 state、絕不寫進 .tf、絕不出現在 plan output、用 ephemeral / managed_master_user_password / Vault
  • SOPS 加密 tfvars 是合規團隊的常見做法
  • Drift Detection 每日跑、用 Slack alert，不要 auto-remediate
  • 三層備份：S3 Versioning + Cross-Region Replication + 異地備份
  • Cost Estimation：Infracost 整合 PR comment + threshold policy + cost allocation tag
  • 零停機部署：create_before_destroy、instance_refresh、blue-green、canary、moved block
  • OpenTofu 1.10+ 內建 OpenTelemetry tracing，搭配結構化 log 完整 observability
  • 合規三層 audit log：Git history + CI/CD log + Cloud audit log
  • Approval gate + tag policy + sensitive 變更雙人 review 是合規必備

建立 production-ready 完整專案

把前面 21 章學的知識全部串起來，從零建立一個 production 級 OpenTofu 專案：

  1. 專案結構：建立 monorepo 含 modules/（resource + service 兩層）、envs/（dev/staging/prod 三環境）
  2. State 拆分：每環境拆 networking / platform / apps 三 stack
  3. Backend：S3 + KMS + native encryption + S3 versioning
  4. Module 設計：實作至少一個 resource module + 一個 service module，遵守 500 行原則、用 for_each 穩定 key
  5. Secret 管理：示範三種方式（managed_master_user_password / Vault ephemeral / SOPS tfvars）
  6. CI/CD pipeline：寫 GitHub Actions workflow 含 fmt → validate → plan → PR comment → manual approve → apply，OIDC + 雙 IAM role
  7. Drift detection：寫 cron workflow 每日跑、Slack 通知
  8. Cost estimation：整合 Infracost，超過閾值 fail PR
  9. Policy as Code：用 Conftest 強制 4 個必填 tag、禁止 public S3
  10. Observability：開啟 OTEL trace、結構化 log，建立 apply 時間 metric
  11. 合規 audit：sensitive 變更（KMS / IAM / DB）自動加上 needs-security-review label
  12. 災難演練：故意刪掉 state，從 S3 versioning 還原；故意造成 partial apply 並修復
  13. Module 發佈：把其中一個 module 用 OCI 發到 GHCR，從另一個專案引用
  14. 文件化：寫 README、ADR（架構決策紀錄）、runbook（incident 處理流程）
  15. 分享：把專案開源（去敏感資料後），跟團隊或社群分享你的 setup
