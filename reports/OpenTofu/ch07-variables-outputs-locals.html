心智模型：把 module 當成函式

變數 = 函式參數、locals = 函式內區域變數、output = 函式回傳值。這個類比能解釋幾乎所有設計問題：什麼該對外（variable / output），什麼是內部實作細節（local），介面長什麼樣（type、description、validation）。

2. Variable 基礎：宣告與七大屬性

Variable block 的標準形式：

HCL · variable block 全屬性 
variable "instance_type" {
  type        = string
  description = "EC2 instance type for the web tier"
  default     = "t3.micro"
  sensitive   = false
  nullable    = false
  ephemeral   = false
  deprecated  = ""

  validation {
    condition     = can(regex("^(t3|t4g|m5|c5)\\.", var.instance_type))
    error_message = "instance_type must start with t3, t4g, m5, or c5."
  }
}

七大屬性詳解

屬性用途建議
type 限制接受值的型別 強烈建議填寫，越具體越好（避免 any）
description 對使用者的說明文件 強烈建議填寫，會自動成為 module docs
default 未提供值時的預設 有 default = optional；無 default = required
sensitive 是否在 CLI 輸出中遮蔽 secret、token、password 一律設 true
nullable 是否允許 null 值 多數情境設 false 較安全
ephemeral（1.10+） 標示為暫存值，不寫入 state 第 13 章詳介紹
deprecated（1.11+） 標示變數為棄用，提醒使用者遷移 module 大改版時用

default 不能引用其他物件

default 必須是字面值（literal），不能是 var.x、data.y.z、local.k。如需動態預設，把邏輯放到 locals，再讓 resource 用 locals 而不是 variable 的值。

required vs optional：default 決定一切

HCL · 必填 vs 選填 
# Required：呼叫方必須提供值，否則 OpenTofu 會互動式詢問
variable "aws_region" {
  type        = string
  description = "AWS region to deploy to"
  # 沒有 default
}

# Optional：呼叫方可省略，會用 default
variable "instance_type" {
  type        = string
  description = "EC2 instance type"
  default     = "t3.micro"
}

Primitive 型別

HCL · primitive 範例 
variable "name" {
  type    = string
  default = "web-server"
}

variable "port" {
  type    = number
  default = 8080
}

variable "enabled" {
  type    = bool
  default = true
}

Collection 型別：同型別元素的集合

型別特性適用場景
list(T)有序、可重複、整數索引availability zones、subnet CIDR 列表
set(T)無序、不重複、無索引for_each 的輸入、tag 集合
map(T)鍵值對、字串 key、同型別 valuetag、環境變數、簡單字典
HCL · collection 範例 
variable "availability_zones" {
  type        = list(string)
  description = "AZs to use, ordered preference"
  default     = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

variable "subnet_cidrs" {
  type    = set(string)
  default = ["10.0.1.0/24", "10.0.2.0/24"]
}

variable "tags" {
  type    = map(string)
  default = {
    Environment = "production"
    Owner       = "platform-team"
  }
}

variable "instance_counts" {
  type    = map(number)   # value 全部是 number
  default = {
    web = 3
    api = 2
    db  = 1
  }
}

Structural 型別：欄位型態各異的複雜結構

Object：類似 struct，每個欄位有名稱與型別。

HCL · object 型別 
variable "database" {
  type = object({
    engine            = string
    version           = string
    instance_class    = string
    allocated_storage = number
    multi_az          = bool
  })

  default = {
    engine            = "postgres"
    version           = "15.5"
    instance_class    = "db.t3.medium"
    allocated_storage = 20
    multi_az          = false
  }
}

# 使用
resource "aws_db_instance" "main" {
  engine            = var.database.engine
  engine_version    = var.database.version
  instance_class    = var.database.instance_class
  allocated_storage = var.database.allocated_storage
  multi_az          = var.database.multi_az
}

Tuple：固定長度、各位置型別不同的有序集合（很少用）。

HCL · tuple 範例 
variable "first_admin" {
  type    = tuple([string, number, bool])  # 必須恰好 3 個值
  default = ["alice", 30, true]
}

optional()：object 中的選填欄位（強大功能）

當 object 中某些欄位想設預設值或可省略時，用 optional() 包起來：

HCL · optional 欄位 
variable "vpc_config" {
  type = object({
    cidr_block            = string
    enable_dns_hostnames  = optional(bool, true)        # 第二參數是預設值
    enable_dns_support    = optional(bool, true)
    instance_tenancy      = optional(string, "default")
    additional_cidr_blocks = optional(list(string), [])
  })
}

# 呼叫方只需給必填欄位，optional 的會自動填入預設
# vpc_config = {
#   cidr_block = "10.0.0.0/16"
#   # 其他欄位省略，自動帶入 optional 預設值
# }

這個語法讓 module 的介面非常乾淨：必填 vs 選填一目了然，且不需在 module 內手寫 fallback 邏輯。

any：通常是錯誤的選擇

慎用 any

any 等於放棄型別檢查，OpenTofu 會試圖推斷實際型別。除非你只是把整個值原封不動傳給 jsonencode() 之類的函式，否則永遠用具體型別。在大型 module 中濫用 any 會讓使用者收到的錯誤訊息變成「在 apply 階段才爆炸」而非「init 時就提醒」。

4. Validation：把契約寫進設定

Type 確保「型別正確」，validation 確保「值合理」。這兩件事不一樣。

基本 validation

HCL · validation 範例集 
# 1. 列舉值檢查
variable "environment" {
  type        = string
  description = "Deployment environment"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be one of: dev, staging, prod."
  }
}

# 2. 正規表示法
variable "ami_id" {
  type = string

  validation {
    condition     = can(regex("^ami-[a-f0-9]{17}$", var.ami_id))
    error_message = "ami_id must be a valid AMI id (e.g., ami-0a1b2c3d4e5f6789a)."
  }
}

# 3. 數值範圍
variable "port" {
  type = number

  validation {
    condition     = var.port >= 1 && var.port <= 65535
    error_message = "port must be between 1 and 65535."
  }
}

# 4. 多重檢查（多個 validation block）
variable "password" {
  type      = string
  sensitive = true

  validation {
    condition     = length(var.password) >= 12
    error_message = "password must be at least 12 characters."
  }

  validation {
    condition     = can(regex("[A-Z]", var.password))
    error_message = "password must contain at least one uppercase letter."
  }

  validation {
    condition     = can(regex("[0-9]", var.password))
    error_message = "password must contain at least one digit."
  }
}

# 5. 集合型別的驗證
variable "subnet_cidrs" {
  type = list(string)

  validation {
    condition     = length(var.subnet_cidrs) >= 2
    error_message = "Need at least 2 subnet CIDRs for high availability."
  }

  validation {
    condition = alltrue([
      for cidr in var.subnet_cidrs : can(cidrhost(cidr, 0))
    ])
    error_message = "All values in subnet_cidrs must be valid CIDR notation."
  }
}

can() 函式：把錯誤轉為布林值

can(expr) 嘗試評估 expr，成功回 true、丟例外則回 false。常與 regex()、cidrhost() 等可能失敗的函式搭配。

condition 必須引用該變數本身

設計限制

OpenTofu 1.9 之前，validation.condition 必須引用該變數本身（例如 var.ami_id），不能引用其他變數。1.9+ 放寬此限制，可引用其他 variable / data source。但跨變數引用會增加 dependency graph 複雜度，建議仍盡量讓 validation 自我封閉。

5. Sensitive 標記與 state 中的 secret

sensitive = true 的效果

HCL · sensitive 範例 
variable "db_password" {
  type        = string
  sensitive   = true
  description = "Database master password"
}

resource "aws_db_instance" "main" {
  identifier = "app-db"
  password   = var.db_password   # 會被遮蔽
  # ...
}

output "db_password_again" {
  value     = var.db_password
  sensitive = true   # 引用 sensitive 變數的 output 也必須標 sensitive，否則 OpenTofu 會 error
}

Plan 中會看到：

Plaintext · plan 輸出 
  + resource "aws_db_instance" "main" {
      + password = (sensitive value)
      + identifier = "app-db"
      + ...
    }

sensitive 不是 encryption

sensitive = true 只控制 CLI 輸出遮蔽，state 檔仍以明文記錄。任何能讀 state 的人都能看到 secret 明文。完整保護需要：①支援加密的 remote backend；②OpenTofu 1.7+ 的 native state encryption（第 12 章）；③或改用 OpenTofu 1.10+ 的 ephemeral 機制（第 13 章），這是真正不寫入 state 的方案。

sensitive 的傳染性

當你把 sensitive 變數的值用在其他地方，那個地方也會被視為 sensitive：

HCL · 傳染範例 
variable "api_token" {
  type      = string
  sensitive = true
}

locals {
  # 因為包含了 var.api_token，整個 url 也會被視為 sensitive
  api_url = "https://api.example.com/v1?token=${var.api_token}"
}

output "api_url" {
  value     = local.api_url
  sensitive = true   # 必須標，否則 OpenTofu 會 error
}

CI/CD 與 secrets 的最佳搭配

在 CI/CD 中傳遞 secret variable 時，用環境變數（TF_VAR_db_password），不要寫進 .tfvars 檔。.tfvars 容易被誤 commit；環境變數可從 secret manager（GitHub Secrets、Vault、AWS Secrets Manager）動態注入。

多環境 tfvars 結構建議

Plaintext · 多環境結構 
my-infra/
├── main.tf
├── variables.tf
├── envs/
│   ├── dev.tfvars
│   ├── staging.tfvars
│   └── prod.tfvars
└── ...

# 切換環境
tofu plan -var-file="envs/dev.tfvars"
tofu plan -var-file="envs/prod.tfvars"

7. Outputs：對外的回傳值

Output 是 module 的對外回傳值。在 root module，它們會印在 tofu apply 結束時；在 child module，它們可被父 module 透過 module.X.output_name 讀取。

Output block 完整屬性

HCL · output block 全屬性 
output "vpc_id" {
  value       = aws_vpc.main.id
  description = "ID of the primary VPC"
  sensitive   = false
  ephemeral   = false
  depends_on  = []   # 較少用，通常隱式即可

  precondition {
    condition     = aws_vpc.main.enable_dns_hostnames
    error_message = "VPC must have DNS hostnames enabled."
  }
}
屬性用途
value（必填）輸出的表達式
description說明文件（強烈建議）
sensitive遮蔽 CLI 輸出；引用 sensitive 來源時必填
ephemeral（1.10+）讓 output 不寫入 state（仍可被父 module 讀到）
depends_on顯式依賴（少用）
precondition輸出前的條件檢查（守護契約）

Output 命名與設計慣例

HCL · 良好的 output 設計 
# 1. 單一資源屬性：清楚命名，不重複 module 上下文
output "vpc_id" {
  value       = aws_vpc.main.id
  description = "ID of the VPC"
}

output "vpc_cidr_block" {
  value       = aws_vpc.main.cidr_block
  description = "CIDR block of the VPC"
}

# 2. 多個資源 → list
output "private_subnet_ids" {
  value       = aws_subnet.private[*].id
  description = "List of private subnet IDs"
}

# 3. map：key 對應某個有意義的識別
output "subnet_ids_by_az" {
  value = {
    for s in aws_subnet.private :
    s.availability_zone => s.id
  }
  description = "Private subnet IDs keyed by AZ"
}

# 4. 整合多個資源資訊到一個 object
output "database" {
  value = {
    endpoint = aws_db_instance.main.endpoint
    port     = aws_db_instance.main.port
    name     = aws_db_instance.main.db_name
  }
  description = "Database connection info"
}

# 5. 引用 sensitive 來源時必須標 sensitive
output "db_password" {
  value     = aws_db_instance.main.password
  sensitive = true
}

output 的 precondition：守護輸出契約

HCL · output precondition 
output "rds_endpoint" {
  value       = aws_db_instance.main.endpoint
  description = "RDS connection endpoint"

  precondition {
    condition     = aws_db_instance.main.endpoint != ""
    error_message = "RDS endpoint must not be empty."
  }
}

當 precondition 失敗，OpenTofu 會：①保留前一次 apply 的 output 值；②印出錯誤訊息；③不破壞 state。這是避免 module 對外輸出 garbage 值的關鍵機制。

8. Locals：內部的暫存與抽象

Locals 是 module 內部的區域變數，用來：

  • 避免在多個地方重複計算同一個值
  • 把複雜表達式拆成有名稱的中間值，提升可讀性
  • 建立 module 內部的「衍生計算」，不需暴露到對外介面

locals block 語法

HCL · locals 範例 
locals {
  # 1. 字串組合
  name_prefix = "${var.project}-${var.environment}"

  # 2. 共用 tags
  common_tags = {
    Project     = var.project
    Environment = var.environment
    ManagedBy   = "OpenTofu"
    Owner       = var.team_email
  }

  # 3. 條件邏輯
  instance_type = var.environment == "prod" ? "m5.large" : "t3.micro"

  # 4. 從 list 計算 map
  subnet_by_az = {
    for s in aws_subnet.private :
    s.availability_zone => s.id
  }

  # 5. 引用其他 local（locals 之間可互相引用）
  full_name = "${local.name_prefix}-${var.component}"
}

# 用 local
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = local.instance_type

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-web"
  })
}

多個 locals block 可並存

同一檔案或多個檔案都可以有 locals { }，OpenTofu 會把它們合併視為一個。但在同一 module 內，不允許重複定義同名 local。

HCL · 多個 locals block 
# locals.tf
locals {
  common_tags = { /* ... */ }
}

# main.tf
locals {
  # OK：不同名
  instance_count = var.environment == "prod" ? 3 : 1
}

locals 不會出現在 plan 輸出中

不像 resource 與 output，locals 純粹是 module 內部抽象，plan 輸出看不到 local 值。Debug 時想看 local 值，可以暫時用 output 把它印出來。

9. 三者選用準則

需求該用什麼
從外部接收值（region、size、tags）variable
把值對外提供給其他 module / 使用者output
把長表達式取個名字提升可讀性locals
多個 resource 共用的 tag 清單locals（不是 variable，因為非外部輸入）
條件邏輯計算（prod vs dev 不同設定）locals 內用三元運算
從 list 推導出 map / 反之locals 內用 for expression
從多個 variable 衍生出的單一值locals（避免使用者要懂內部邏輯）
讓使用者選擇預設行為（可被覆寫）variable 帶 default

反例：什麼時候用錯了

HCL · 反例 1：把計算放進 variable default 
# ❌ 不能這樣寫，default 必須是字面值
variable "name_prefix" {
  type    = string
  default = "${var.project}-${var.environment}"   # ERROR
}

# ✅ 改用 local
locals {
  name_prefix = "${var.project}-${var.environment}"
}
HCL · 反例 2：把純內部值暴露成 output 
# ❌ 不必要的 output（呼叫方根本不需要這個值）
output "internal_subnet_count" {
  value = length(aws_subnet.private)
}

# ✅ 改用 local（如果 module 內部要用）
locals {
  subnet_count = length(aws_subnet.private)
}

10. 常見陷阱與最佳實踐

陷阱 1：list vs set 搞錯

list(string) 與 set(string) 看起來像但行為差很多。for_each 接受的是 set 或 map，不是 list。如果你拿 list 給 for_each，需要先用 toset() 轉換。

HCL 
variable "names" {
  type    = list(string)
  default = ["alice", "bob"]
}

resource "aws_iam_user" "team" {
  for_each = toset(var.names)   # ✅ 用 toset 轉換
  name     = each.key
}

陷阱 2：用 nullable = true 但忘記處理 null

HCL 
variable "tags" {
  type     = map(string)
  default  = null
  nullable = true     # 預設值，但要小心
}

# ❌ 直接用會在 null 時炸
resource "aws_instance" "web" {
  tags = merge(var.tags, { Name = "web" })  # merge(null, ...) ❌
}

# ✅ 用 coalesce 或 try
resource "aws_instance" "web" {
  tags = merge(coalesce(var.tags, {}), { Name = "web" })
}

陷阱 3：tfvars 的型別誤匹配

HCL · variables.tf 
variable "port" {
  type = number
}
Plaintext · 各種傳值的格式差異 
# tfvars 檔（HCL 語法）
port = 8080            # ✅ 不加引號

# 環境變數（字串會被自動轉型）
export TF_VAR_port=8080      # ✅ OpenTofu 會 coerce 成 number

# CLI -var（字串會被自動轉型）
tofu plan -var=port=8080     # ✅

# 但複雜型別在 -var 與環境變數中要用 JSON 字串
export TF_VAR_tags='{"env":"prod"}'    # ✅
tofu plan -var='tags={"env":"prod"}'   # ✅

陷阱 4：在 locals 內形成循環引用

HCL 
locals {
  a = local.b + 1   # ❌
  b = local.a + 1   # ❌ Cycle detected
}

最佳實踐速查

主題建議
每個 variable必填 type、description；預設加 validation
每個 output必填 description
Secret 類變數sensitive = true + 用環境變數傳遞 + 配合 state encryption
複雜結構用 object({...}) 配 optional() 提供乾淨介面
多環境設定用 envs/<env>.tfvars 結構，CI 透過 -var-file 切換
共用 tag放 locals.common_tags，每個 resource 用 merge()
條件邏輯放 locals，不寫在 resource block 中
any 型別避免使用，除非整個值不被內部解析

11. 本章重點與練習

重點回顧

  • Variable / Local / Output 對應「函式參數 / 區域變數 / 回傳值」三種角色
  • Variable 七大屬性：type、description、default、sensitive、nullable、ephemeral、deprecated，並可有多個 validation block
  • 型別系統三大類：primitive（string、number、bool）、collection（list、set、map）、structural（object、tuple）；optional() 讓 object 欄位可選填並有預設值
  • Validation 用 can() 把可能丟例外的表達式轉成布林
  • sensitive = true 只遮蔽 CLI 輸出，不加密 state。Secret 完整保護需 state encryption 或 ephemeral 機制
  • 傳值優先序（低到高）：default → TF_VAR_xxx → terraform.tfvars → *.auto.tfvars → -var-file → -var
  • Output 是對外契約，可用 precondition 守護輸出值
  • Locals 是內部抽象，不出現在 plan 輸出，可互相引用但不能循環
  • 常見錯誤：把計算放進 variable default、把內部值暴露成 output、忘記處理 null
⚡ 動手實作 · Hands-on Lab 7

設計一個完整的 module 介面

  1. 建立目錄 vars-lab/，用 local + random provider，模擬一個會建立多個檔案的「app deployment module」
  2. 定義以下 variables：
    • project：必填 string
    • environment：必填 string，validation 限制為 dev/staging/prod
    • file_count：number，default 3，validation 限制 1~10
    • tags：map(string)，default 空 map
    • db_password：string，sensitive，validation 至少 12 字
    • app_config：object 包含 name(string)、port(optional number, 8080)、debug(optional bool, false)
  3. 用 locals 計算：
    • name_prefix："${var.project}-${var.environment}"
    • common_tags：merge 預設 tag 與 var.tags
  4. 用 resource "local_file" 配 count = var.file_count 建立檔案，每個檔案內容包含 name_prefix 與 app_config 資訊
  5. 定義 outputs：file_paths（list）、config_summary（object 整合多個值）
  6. 建立 terraform.tfvars 與 envs/dev.tfvars、envs/prod.tfvars，分別給不同的值
  7. 練習 A：跑 tofu plan，觀察哪些變數是 required、互動式詢問格式
  8. 練習 B：故意違反 validation（environment 給 "test"），觀察錯誤訊息
  9. 練習 C：用 tofu plan -var-file="envs/dev.tfvars" 與 -var-file="envs/prod.tfvars" 切換環境
  10. 挑戰題：把 db_password 改成從環境變數 TF_VAR_db_password 傳入，並加上 output precondition 確保 file_paths 至少有 1 個元素
  11. 用 tofu destroy 清掉資源
