1. terraform {} block 是什麼

terraform {} 是專門設定 OpenTofu 自身行為的特殊 block。它與 resource、variable、provider 不同：

  • 不對應任何外部資源
  • 不接受 expression 或函式呼叫——所有值必須是字面值（constant）
  • 不能引用 var、local、resource 等任何具名物件
  • 每個 module 可有多個 terraform {} block，OpenTofu 會自動合併

為什麼還叫 terraform？

OpenTofu 從 Terraform 1.5.x fork，故意保留 terraform {} 名稱以維持相容。這是 OpenTofu v1.x 相容性承諾的一部分——讓 Terraform 設定能無縫遷移。官方文件提到「未來可能引入 tofu {} block，但目前尚未存在」。新專案仍應使用 terraform {}。

2. terraform {} block 全貌

HCL · terraform block 完整範例 
terraform {
  # ① OpenTofu 版本約束
  required_version = ">= 1.6.0, < 2.0.0"

  # ② Provider 版本約束
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  # ③ Backend 設定（state 存哪裡）
  backend "s3" {
    bucket       = "myorg-tofu-state"
    key          = "production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }

  # ④ State encryption（OpenTofu 1.7+）
  encryption {
    key_provider "pbkdf2" "main" {
      passphrase = var.encryption_passphrase
    }

    method "aes_gcm" "main" {
      keys = key_provider.pbkdf2.main
    }

    state {
      method = method.aes_gcm.main
    }
  }

  # ⑤ Experimental features（謹慎使用）
  experiments = [example_experiment]
}

3. required_version：版本守門員

required_version 約束哪個版本的 OpenTofu 可以使用本設定。當有人用不符的版本跑 tofu init 或 tofu plan，OpenTofu 會立即 error。

版本約束運算子

運算子意義範例與允許版本
= 1.11.6 或 1.11.6精確等於只允許 1.11.6
!= 1.11.0不等於排除 1.11.0
>= 1.6.0大於等於1.6.0 以上所有版本
< 2.0.0小於1.x.x
~> 1.11悲觀約束（最右一位可變）1.11.x、1.12.x... 但不到 2.0
~> 1.11.0悲觀約束（patch 可變）1.11.x 但不到 1.12.0
>= 1.6.0, < 2.0.0範圍組合1.6.x ~ 1.x.x

Reusable module vs Root module 的不同寫法

HCL · 兩種場景的版本策略 
# Root module（你執行 tofu apply 的地方）：寫上下限
terraform {
  required_version = ">= 1.11.0, < 2.0.0"
}

# Reusable child module（給別人用的）：只寫下限
terraform {
  required_version = ">= 1.6.0"   # 不寫上限，讓使用者自由選擇
}

不要用 ~> 在 reusable module

如果你的 reusable module 寫 required_version = "~> 1.6"，使用者必須維持在 1.6.x 系列，用 1.11.x 就會 error。對 reusable module，只設下限給使用者最大彈性。

Belt-and-suspenders：required_version + .opentofu-version 雙保險

}
EOF

# 2. 在專案根目錄建 .opentofu-version（給 tenv 自動切換）

# - 萬一有人 bypass tenv，required_version 仍會擋下不相容的版本

4. required_providers：複習關鍵點

第 11 章已詳細介紹，這裡摘要核心概念：

HCL · required_providers 完整範例 
terraform {
  required_providers {
    # 標準形式
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }

    # 第三方 provider 必須宣告 source
    datadog = {
      source  = "DataDog/datadog"
      version = "~> 3.40"
    }

    # 接受 alias provider 的 module（搭配 alias 使用）
    aws = {
      source                = "hashicorp/aws"
      version               = "~> 5.0"
      configuration_aliases = [aws.tokyo, aws.frankfurt]
    }
  }
}

Provider 版本約束的 root vs reusable 策略

場景建議寫法原因
Root module~> 5.30鎖在已測試的 minor 系列，避免被動升級
Reusable module>= 5.0下限給最低相容版本，上限由使用者決定
已知有 bug 的版本~> 5.30, != 5.30.5排除特定版本
嚴格鎖定（合規/政府專案）= 5.30.4確切版本，搭配 lock 檔

5. backend 與 encryption block

第 12 章已完整介紹。這裡列出在 terraform {} 中可見的形式：

HCL · S3 backend + encryption 
terraform {
  required_version = ">= 1.11.0"

  backend "s3" {
    bucket       = "myorg-tofu-state"
    key          = "production/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true       # SSE-S3
    use_lockfile = true       # OpenTofu 1.10+ native lockfile
  }

  encryption {                # OpenTofu 1.7+ native encryption
    key_provider "aws_kms" "main" {
      kms_key_id = "arn:aws:kms:us-east-1:..."
      region     = "us-east-1"
    }

    method "aes_gcm" "state" {
      keys = key_provider.aws_kms.main
    }

    state {
      method   = method.aes_gcm.state
      enforced = true
    }

    plan {
      method   = method.aes_gcm.state
      enforced = true
    }
  }
}

6. Experimental Features

OpenTofu 有時會推出實驗性語法或功能，先讓社群試用、回饋，正式化後再加入相容性承諾。要使用實驗特性需明確 opt-in：

HCL · 啟用實驗特性 
terraform {
  experiments = [some_experiment_name]
}

實驗特性的紀律

① 實驗特性不在 v1.x 相容性承諾內，未來版本可能 breaking change 或移除；② 升級 OpenTofu 時，實驗特性可能消失導致設定無法解析；③ 絕對不要在 production module 用實驗特性。在 sandbox 試用、給核心團隊回饋即可。

歷史上的實驗特性已正式化（example）：

  • module_variable_optional_attrs（已正式化為 optional()）
  • config_driven_move（已正式化為 moved block）

7. v1.x Compatibility Promises

OpenTofu 在 1.0 release 時做了正式的 v1.x compatibility promises：在 v1.x 系列內，特定範疇的相容性會被保證。

承諾保護的範圍

項目是否承諾相容
HCL 語法（block、argument、expression）✅
內建函式（除非有重大 bug）✅
CLI 子指令、flag、退出碼✅
state 檔格式（v4 JSON）✅
terraform {} block 名稱✅（沿用，不會改名為 tofu）
Provider plugin protocol✅（保證在 v1.x 內運作）
Module registry protocol✅
Backend protocol✅
Experimental features❌
內部 Go API（internal/ 目錄）❌
未文件化的行為❌

什麼情況下相容性承諾可能不適用？

  • 修正安全漏洞：可能改變既有行為
  • 修正明確的 bug：原本的「正確行為」可能與你的 workaround 衝突
  • 實驗特性：明確標示為 experimental 的功能
  • 跨主版本升級：v2.0 可能會有 breaking change（但目前還未發生）

這個承諾為什麼重要

在企業 IaC 環境，「升級 OpenTofu 後 plan 突然顯示要重建幾百個資源」是惡夢。v1.x 相容性承諾讓你的 .tf 檔在多個小版本間都能正常運作，安心定期升級。這是 OpenTofu 比某些競品更負責任的設計。

9. 升級指南：從 v1.6 / v1.7 / v1.8+ 到最新

升級總原則

  1. 不跳大版本：1.6 → 1.11 直跳風險高，建議經 1.6 → 1.8 → 1.10 → 1.11
  2. 先升 dev / staging：production 是最後一站
  3. 備份 state：升級前 tofu state pull > backup-vX-YYYYMMDD.json
  4. 讀 changelog：每個 minor 都有 release notes，特別注意 deprecation 與 breaking
  5. 跑 plan 確認 No changes：升級後 plan 應顯示無變更（除非你刻意用了新版才有的功能）

required_version建議升到 ">= 1.6.0, < 2.0.0" 預留升級空間

10. 版本管理策略

三層版本鎖定

Plaintext · 三層保險 
第 1 層：required_version（設定檔內，給 OpenTofu 自己擋）
  versions.tf 的 terraform { required_version = ">= 1.11.0, < 2.0.0" }

第 2 層：.opentofu-version（給 tenv / tofuenv 自動切換）
  echo "1.11.6" > .opentofu-version

第 3 層：CI/CD 鎖定（Docker image tag、setup-opentofu 的 tofu_version）
  uses: opentofu/setup-opentofu@v2
    with: tofu_version: 1.11.6

升級節奏建議

環境類型升級節奏
個人 sandbox每週都可試新版
Dev 環境新版釋出 1-2 週後跟上
Staging新版穩定（.x 版本至少 .3）後採用
Production等 staging 穩定 2-4 週才升；安全性 patch 例外（2-3 天內升）
合規環境（金融、醫療）內部 review + 至少一個 minor 系列穩定後

內部 module 的版本策略

對於 reusable module 的版本管理：

  • Module 自身發版用 SemVer：v1.0.0、v1.1.0、v2.0.0
  • Major version 改變：對應 breaking change（變數結構大改、required_version 提升）
  • 使用 deprecated 給遷移期：在 v1.x 標記舊變數為 deprecated，v2.0 才移除
  • 保留至少 2 個 major 版本的 maintenance：v1 與 v2 同時收 bug fix，避免使用者被迫立即升級

11. 常見陷阱與最佳實踐

陷阱 1：在 terraform block 裡用變數

HCL 
# ❌ 早期版本完全不允許
terraform {
  required_version = ">= ${var.min_version}"   # ERROR
}

# ✅ 必須是字面值
terraform {
  required_version = ">= 1.11.0"
}

OpenTofu 1.8+ backend 內放寬了部分變數使用（早期變數評估），但 required_version 與 required_providers 的 version 字串仍必須是字面值。

陷阱 2：用 ~> 寫 reusable module 的 required_version

第 3 節已強調：reusable module 用 ">= X" 給彈性，root module 才用 "~> X.Y" 鎖定。寫反了會讓使用者卡死在某版本。

陷阱 3：升級時忘了同步更新 required_version

升級到 1.11.6 但 required_version 還停在 ">= 1.6.0"？技術上能跑，但新團隊成員裝 1.6.x 也能跑、會錯失新功能限制。建議升級新版時同步抬高下限。

陷阱 4：用了實驗特性 + 忘了寫 experiments 宣告

實驗特性必須明確啟用：

HCL 
terraform {
  experiments = [some_experiment]
}

沒宣告會直接 error。但在 production 用實驗特性本身就是錯誤。

陷阱 5：cloud {} block

從 Terraform Cloud / HCP Terraform 遷移過來的設定可能有：

HCL · OpenTofu 不支援的 block 
terraform {
  cloud {                # ❌ OpenTofu 不支援
    organization = "myorg"
    workspaces { ... }
  }
}

必須改用標準 backend（S3 / GCS / Azure 等）+ Spacelift/env0/Scalr 等 TACOS 平台。第 4 章遷移指南已詳述。

陷阱 6：跳大版本升級

1.6 → 1.11 一次跳，遇到問題很難分辨是哪個版本引入的變化。逐步升級能讓問題範圍可控。

最佳實踐速查

主題建議
Root module required_version">= X.Y.Z, < (X+1).0.0" 格式
Reusable module required_version只設下限 ">= X.Y"
版本鎖定三層：required_version + .opentofu-version + CI tofu_version
多個 terraform blockOK，會自動合併；建議拆檔（versions.tf、backend.tf、encryption.tf）
terraform block 內只用字面值（除 backend 部分情境外）
實驗特性限 sandbox，絕不 production
升級節奏逐版本升、dev → staging → prod、備份 state、看 plan
HCP Terraform 遷移把 cloud {} 換成標準 backend + TACOS 替代
新功能採用1.7+ encryption、1.10+ S3 use_lockfile、1.11+ enabled / ephemeral，依需要逐步採用
向下相容OpenTofu v1.x 內，HCL 與 state 格式承諾不破

12. 本章重點與練習（含 Part 2 總回顧）

本章重點回顧

  • terraform {} 是 OpenTofu 自身設定的特殊 block，內部只接受字面值
  • 五大 sub-block：required_version、required_providers、backend、encryption、experiments；cloud {} 不支援
  • 多個 terraform {} block 會被自動合併，建議拆檔組織
  • required_version：root 寫上下限、reusable 只寫下限；搭配 .opentofu-version 與 CI 三層保險
  • v1.x compatibility promise 保證 HCL、state、CLI、protocol 在 v1.x 內穩定
  • 實驗特性不在承諾內，限於 sandbox 使用

terraform block 與版本管理綜合練習

  1. 建立 settings-lab/，把 terraform {} 拆成 versions.tf、backend.tf、encryption.tf 三個檔案，跑 tofu init 確認自動合併
  2. 練習 A · required_version 防呆：在 versions.tf 寫 required_version = ">= 1.11.0"，然後用 tenv 切到 1.10.x（如果有裝），跑 tofu init 觀察 error 訊息
  3. 練習 B · 版本約束實驗：分別試試 "= 1.11.6"、"~> 1.11.0"、">= 1.6.0, < 2.0.0" 三種寫法，比較行為差異
  4. 練習 C · 三層保險：建立 .opentofu-version 寫 1.11.6；在 versions.tf 寫 required_version = ">= 1.11.0"；如果有 GitHub repo，加 .github/workflows/tofu.yml 用 opentofu/setup-opentofu@v2 鎖 1.11.6
  5. 練習 D · reusable module 版本策略：建立一個 child module，required_version = ">= 1.6.0"（不寫上限）；root module 寫 "~> 1.11.0"。確認從 root 用 1.11.x 跑 child 沒問題
  6. 挑戰題 1：在 root module 把 backend 從 local 切到 S3（如果有 AWS），用 partial config + backend config 檔，跑 tofu init -migrate-state 完成遷移
  7. 挑戰題 2：在 terraform {} 加 OpenTofu 1.7+ 的 encryption block 用 PBKDF2 + passphrase，apply 後從 backend 直接 cat 確認 state 是 binary（無法明文讀取）
  8. 挑戰題 3：故意違反相容性承諾的「保證」，例如試圖在 required_version 用變數，看到具體 error 訊息與排查方法
  9. 用 tofu destroy 清掉資源
