1. 什麼是 workspace

CLI workspace 是在同一個工作目錄、同一個 backend 內，維持多份獨立 state的機制。每個 workspace 對應一份 state 檔，但共用同一份設定檔。

main.tf, variables.tf..."]

    subgraph Backend["同一個 Backend (例如 S3)"]
        S1["state: default"]
        S2["state: dev"]
        S3["state: staging"]
        S4["state: prod"]
    end

    Config -.workspace=default.-> S1
    Config -.workspace=dev.-> S2
    Config -.workspace=staging.-> S3
    Config -.workspace=prod.-> S4

OpenTofu 起步就有 default workspace

每個初始化的工作目錄一開始就有名為 default 的 workspace。如果你從沒下過 tofu workspace 指令，你就在 default 裡。default workspace 不能被刪除。

workspace 不是「環境」（雖然常被當環境用）

官方明確建議：別用 workspace 區分嚴重隔離的環境

OpenTofu 官方文件明確說：「Workspaces 不適合用來隔離需要獨立 credentials 與 access controls 的部署」。多 workspace 共用同一個 backend、同一份設定，無法做到「dev/prod 用不同 cloud account / IAM」。下面第 6、7 節會詳述。

2. workspace 的內部運作機制

state 檔位置

不同 backend 對 workspace state 的存放方式不同：

Backendworkspace state 位置
localterraform.tfstate.d/<workspace_name>/terraform.tfstate
s3s3://<bucket>/env:/<workspace_name>/<key>（default 用 <key>）
gcs<prefix>/<workspace_name>.tfstate
azurerm<key>env:<workspace_name>
postgres同 schema 不同 row

3. workspace 指令完整介紹

指令用途
tofu workspace list列出所有 workspace（當前用 * 標記）
tofu workspace show只顯示當前 workspace 名稱
tofu workspace new NAME建立新 workspace 並切換過去
tofu workspace select NAME切換到既有 workspace
tofu workspace delete NAME刪除 workspace（必須先 select 別的）

實戰範例

Bash · workspace 完整流程 
# 初始化專案
tofu init

# 看現在哪些 workspace（一開始只有 default）
tofu workspace list
# * default

# 建新 workspace（會自動切過去）
tofu workspace new dev
# Created and switched to workspace "dev"!

tofu workspace new staging
tofu workspace new prod

# 列出全部
tofu workspace list
#   default
#   dev
#   prod
# * staging  ← 當前

# 確認當前
tofu workspace show
# staging

# 切換
tofu workspace select dev

# 在 dev workspace 裡跑 plan / apply
tofu plan
tofu apply

# 切到 prod 看（state 完全獨立）
tofu workspace select prod
tofu plan
# 只會看到 prod workspace 的資源變化

# 刪除舊的 workspace（必須先切到別的）
tofu workspace select default
tofu workspace delete old_dev
# 注意：如果 old_dev 還有資源在 state，會 refuse 刪除
# 必須先 destroy 或加 -force（危險）

用環境變數選擇 workspace（CI 友善）

Bash · TF_WORKSPACE 環境變數 
# 不用 select 指令，直接用環境變數
export TF_WORKSPACE=production
tofu plan   # 自動在 production workspace 跑

# CI/CD pipeline 中很實用
TF_WORKSPACE=$ENVIRONMENT tofu apply -auto-approve

TF_WORKSPACE 與 select 衝突時

如果同時設定 TF_WORKSPACE 與用 tofu workspace select，但兩者指向不同 workspace，OpenTofu 會 error。選一種就好，CI 用環境變數、本地用 select。

4. terraform.workspace 在設定中的使用

在 .tf 檔內可以引用 terraform.workspace 取得當前 workspace 名稱，讓設定根據 workspace 變化。

常見用法 1：tag 與命名

HCL · 用 workspace 命名資源 
resource "aws_instance" "web" {
  ami           = "ami-0abc123"
  instance_type = "t3.micro"

  tags = {
    Name        = "web-${terraform.workspace}"  # web-dev、web-staging、web-prod
    Environment = terraform.workspace
  }
}

常見用法 2：變數查表

HCL · 用 workspace 查 map 
variable "instance_size" {
  type = map(string)

  default = {
    default = "t2.micro"
    dev     = "t2.micro"
    staging = "t3.small"
    prod    = "m5.large"
  }
}

resource "aws_instance" "web" {
  instance_type = lookup(var.instance_size, terraform.workspace, "t2.micro")
  # ...
}

常見用法 3：條件邏輯

HCL · 條件啟用功能 
locals {
  is_prod = terraform.workspace == "prod"
}

resource "aws_db_instance" "main" {
  multi_az            = local.is_prod
  backup_retention_period = local.is_prod ? 30 : 7
  deletion_protection = local.is_prod
  # ...
}

# 只在 prod 建立 backup vault
resource "aws_backup_vault" "main" {
  count = local.is_prod ? 1 : 0
  # ...
}

用 console 驗證

Bash · 互動式驗證 
tofu workspace select dev
tofu console
> terraform.workspace
"dev"

> lookup(var.instance_size, terraform.workspace)
"t2.micro"

# 切換 workspace
> exit

tofu workspace select prod
tofu console
> terraform.workspace
"prod"

> lookup(var.instance_size, terraform.workspace)
"m5.large"

6. 何時用 workspace、何時不用

✅ 適合用 workspace 的場景

場景原因
開發者個人 sandbox（每人一個 workspace）同 account、同 backend 內隔離，方便試驗
同一 cloud account 內的多個短暫環境（feature branch、PR preview）不需獨立 credentials，自動化建立/銷毀
多 region 部署（同一份設定服務全球）terraform.workspace 對應 region
多 tenant SaaS（同 codebase 部署到不同 tenant）每個 tenant 一個 workspace
個人學習與實驗簡單方便

❌ 不適合用 workspace 的場景

場景原因
dev / staging / prod 用不同 cloud accountworkspace 共用 backend，無法用不同 IAM
需要嚴格 access control（dev 工程師不能讀 prod state）workspace 共用 backend，IAM 粒度不夠
環境間有結構性差異（prod 多了 DR / WAF / Shield）單一設定難管理大量條件邏輯
合規要求 prod state 與 dev state 物理隔離同 backend 不符合稽核要求
多 cloud（部分環境在 AWS、部分在 GCP）provider 設定差異太大

最重要的反模式：用 workspace 區分 dev/prod

新手最常見的錯誤：「workspace 就是環境，dev workspace、prod workspace」。這是反模式。在同一 backend 中，prod state 與 dev state 並存，誰能讀寫 dev 就能讀寫 prod，且 tofu workspace select 沒有額外確認步驟，極易切錯後 apply 出意外。production 應該用目錄分離。

7. 目錄分離策略：production 推薦

對於 dev / staging / prod 這類正式環境分離，強烈推薦目錄分離。每個目錄是獨立的 root module，有自己的：

  • Backend 設定（指向不同 bucket / account）
  • Provider 設定（用不同 IAM role / credentials）
  • terraform.tfvars（環境專屬變數）
  • .terraform.lock.hcl（環境可獨立升級 provider 版本）

完整目錄結構

Plaintext · production 推薦結構 
myapp-infra/
├── README.md
├── modules/                    # 共用 modules
│   ├── network/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── database/
│   └── app/
└── envs/
    ├── dev/                    # ← 獨立 root module
    │   ├── main.tf             # 呼叫 modules
    │   ├── backend.tf          # dev backend
    │   ├── providers.tf        # dev account
    │   ├── variables.tf
    │   ├── outputs.tf
    │   ├── terraform.tfvars
    │   └── .terraform.lock.hcl # 各 env 獨立 lock
    ├── staging/
    │   └── ... (同 dev 結構)
    └── prod/
        └── ... (同 dev 結構)

每個環境的 main.tf 範本

HCL · envs/prod/main.tf 
module "network" {
  source = "../../modules/network"

  vpc_cidr           = var.vpc_cidr
  availability_zones = var.availability_zones
  environment        = "prod"
}

module "database" {
  source = "../../modules/database"

  vpc_id        = module.network.vpc_id
  subnet_ids    = module.network.private_subnet_ids
  instance_size = "db.r6g.large"   # prod 規格
  multi_az      = true
  backup_days   = 30
}

module "app" {
  source = "../../modules/app"

  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.private_subnet_ids
  db_endpoint = module.database.endpoint
}

每個環境的 backend.tf

HCL · envs/prod/backend.tf 
terraform {
  backend "s3" {
    bucket       = "myorg-prod-tofu-state"   # prod 專屬 bucket
    key          = "myapp/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true

    # 用 prod 的 IAM role 讀寫 state
    role_arn = "arn:aws:iam::PROD_ACCOUNT:role/TofuStateAccess"
  }
}

使用方式

Bash 
# 直接 cd 到對應環境
cd envs/prod
tofu init
tofu plan
tofu apply

# 或用 -chdir 不切目錄
tofu -chdir=envs/prod init
tofu -chdir=envs/prod plan
tofu -chdir=envs/prod apply

為什麼這個結構是 production 黃金標準

① 視覺上強隔離：terminal prompt 看到 envs/prod 一目了然；② backend 與 IAM 獨立，dev 工程師不會誤踩 prod；③ 各環境可獨立升級 provider 版本（lock 檔分離）；④ 結構性差異容易管理（prod 可加 prod-only resource 不影響 dev）；⑤ CI/CD 設計簡單（依 PR 影響的目錄決定要 apply 哪個 env）。

8. OpenTofu 1.8+ 的 Static Evaluation

OpenTofu 1.8 推出 early evaluation of variables and locals（俗稱 static evaluation），讓 backend block 也能用 variable。這大幅改進了「策略 C：backend-config 切換」的體驗。

OpenTofu 1.8+ 在 backend 用變數

HCL · main.tf 
variable "environment" {
  type        = string
  description = "Deployment environment (dev, staging, prod)"
}

terraform {
  backend "s3" {
    bucket       = "myorg-${var.environment}-tofu-state"   # OpenTofu 1.8+ 才能這樣
    key          = "myapp/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
Bash · 用 var 切環境 
# 用環境變數切換
TF_VAR_environment=dev tofu init
TF_VAR_environment=prod tofu init -reconfigure

backend 內能用的變數有限制

OpenTofu 1.8+ backend 內的變數有兩個限制：① 必須是 top-level variable（不能引用其他 resource、output 或 locals）；② 變數值必須在 tofu init 階段就確定（透過 .tfvars、CLI flag、環境變數提供）。仍然不能用 data 或運行時計算的值。

結合 module versioning 的單目錄策略

1.8+ 也允許 module source 用變數（早期 evaluation）：

HCL · 動態 module 版本 
variable "module_version" {
  type        = string
  description = "Version of the shared module to use"
}

module "vpc" {
  source = "git::https://github.com/myorg/terraform-aws-vpc.git?ref=${var.module_version}"
  # ...
}

這讓「dev 用最新 module、prod 用穩定版」變得自然。

9. 命名慣例與管理紀律

workspace 命名規範

場景命名建議
個人 sandboxdev-${USER}，例如 dev-alice、dev-bob
Feature branchfeature-${BRANCH}，例如 feature-PROJ-123
Multi-region${REGION}，例如 us-east-1、eu-central-1
Multi-tenanttenant-${ID}
環境（不推薦）用目錄分離，但若硬要 workspace：dev、staging、prod

避免危險的 workspace 操作

Bash · 安全 wrapper script 
#!/bin/bash
# tofu-safe.sh - 確認 workspace 後才執行 OpenTofu

set -e

EXPECTED_WORKSPACE="$1"
shift

CURRENT=$(tofu workspace show)
if [ "$CURRENT" != "$EXPECTED_WORKSPACE" ]; then
  echo "Error: Current workspace is '$CURRENT', expected '$EXPECTED_WORKSPACE'"
  echo "Run: tofu workspace select $EXPECTED_WORKSPACE"
  exit 1
fi

echo "Workspace confirmed: $CURRENT"
exec tofu "$@"

# 用法：
# ./tofu-safe.sh prod apply
# ./tofu-safe.sh dev plan

shell prompt 顯示當前 workspace

Bash · 加入 .bashrc / .zshrc 
# 在 prompt 顯示當前 OpenTofu workspace
function tofu_ws() {
  if [ -d ".terraform" ]; then
    local ws=$(tofu workspace show 2>/dev/null)
    if [ -n "$ws" ] && [ "$ws" != "default" ]; then
      echo " [tofu:$ws]"
    fi
  fi
}

# bash
PS1='\u@\h:\w$(tofu_ws)\$ '

# zsh（用 prompt subst）
setopt prompt_subst
PROMPT='%n@%m:%~$(tofu_ws)%# '

之後 cd 到專案目錄，prompt 會顯示 [tofu:prod]，避免切錯。

10. 常見陷阱與最佳實踐

陷阱 1：用 workspace 區分 dev/prod 但共用 cloud account

第 6 節已警告。正式環境一定要 cloud account 隔離 + 目錄分離。

陷阱 2：忘了切 workspace 就跑 apply

切到了 prod 改了東西，忘了切回 dev 就 apply。為什麼會發生：

  • workspace 切換無視覺提示
  • 長時間 session 會忘記在哪
  • terminal 多開時更危險

對策：

  • 用 shell prompt 顯示 workspace（第 9 節）
  • 寫 wrapper script 強制確認（第 9 節）
  • 正式環境用目錄分離（cd 到 prod 目錄是強烈視覺提示）

陷阱 3：刪 workspace 之前沒清資源

Bash 
tofu workspace select dev_alice

# ❌ 直接刪會 error（因為 state 還有資源）
tofu workspace delete dev_alice
# Error: Workspace is not empty

# ✅ 先 destroy 再刪
tofu destroy
tofu workspace select default
tofu workspace delete dev_alice

# ⚠️ 強制刪除（state 中的資源還活著但沒人管！）
# tofu workspace delete -force dev_alice    ← 不要用！會留下孤兒資源

陷阱 4：default workspace 與其他 workspace 行為不一

S3 backend 中，default workspace state 在 <key>，其他 workspace 在 env:/<name>/<key>。建議：建立 stack 後立刻切到具名 workspace（如 main），讓 default 永遠是空的。

陷阱 5：terraform.workspace 在 module 內的行為

terraform.workspace 在 child module 中也指向當前 root module 的 workspace，不是 child 自己的。Module 設計時不要假設 workspace 名稱有特殊意義（最好把 environment 當作明確 variable 傳入）：

HCL · 良好的 module 設計 
# ❌ child module 內依賴 terraform.workspace
resource "aws_instance" "web" {
  tags = { Env = terraform.workspace }   # 模組強依賴 workspace 機制
}

# ✅ 接受 environment 變數
variable "environment" {
  type = string
}

resource "aws_instance" "web" {
  tags = { Env = var.environment }   # 模組獨立於 workspace
}

- name: Tofu plan

    TF_WORKSPACE: ${{ github.event.inputs.environment }}

11. 本章重點與練習

重點回顧

  • CLI workspace 是「同一目錄、同一 backend、多份 state」的機制；不是「環境」
  • 每個專案啟動時都有 default workspace，不能刪除
  • state 存放：local backend 在 terraform.tfstate.d/<ws>/、S3 在 env:/<ws>/<key>
  • 5 個指令：list / show / new / select / delete；環境變數 TF_WORKSPACE 可取代 select
  • terraform.workspace 在設定中可用，常見用法：tag 命名、變數 lookup、條件邏輯
  • 三大策略：workspace（限定情境）、目錄分離（production 推薦）、backend-config 切換
  • 絕不用 workspace 區分需要不同 cloud account / IAM 的 dev/prod
  • 適合 workspace 的場景：個人 sandbox、PR preview、多 region、多 tenant、多個短暫環境
  • OpenTofu 1.8+ 的 static evaluation 讓 backend 也能用變數，部分情境讓「策略 C」變得好用
  • 實務紀律：shell prompt 顯示 workspace、wrapper script 確認、CI 用 TF_WORKSPACE
  • module 設計：傳 var.environment，不依賴 terraform.workspace，提升可移植性
⚡ 動手實作 · Hands-on Lab 17

多環境管理綜合練習

  1. 建立 workspace-lab/，main.tf 用 local + random provider 建立帶 terraform.workspace 的資源（檔名含 workspace 名稱）
  2. 練習 A · workspace 基本指令：
    • 跑 tofu init 與 tofu workspace list
    • 用 tofu workspace new dev、tofu workspace new staging、tofu workspace new prod 建三個
    • 各 workspace 跑 tofu apply，觀察 terraform.tfstate.d/ 目錄結構
  3. 練習 B · workspace lookup：在 main.tf 加入 map(string) 變數，依 terraform.workspace 對應不同 file content；切換各 workspace 跑 plan 看差異
  4. 練習 C · TF_WORKSPACE 環境變數：用 TF_WORKSPACE=prod tofu plan 不需要 select 直接切換
  5. 練習 D · 改用目錄分離：把 main.tf 抽出來做成 modules/files/，建立 envs/dev、envs/staging、envs/prod 三個目錄各自呼叫 module，每環境獨立的 terraform.tfvars
  6. 練習 E · 安全 wrapper：寫一個 bash script tofu-safe.sh，先驗證當前 workspace 與預期一致才執行 OpenTofu 指令
  7. 練習 F · shell prompt：在 ~/.bashrc / ~/.zshrc 加入會顯示當前 workspace 的 prompt 函數，cd 到 lab 目錄看效果
  8. 挑戰題 1 · CI 模擬：寫 bash script 模擬 GitHub Actions 流程：
    • 接收 $ENVIRONMENT 參數
    • 用 TF_WORKSPACE 切到對應 workspace
    • 跑 tofu plan -detailed-exitcode
    • 依退出碼決定是否 apply
  9. 挑戰題 2 · static evaluation：(OpenTofu 1.8+) 在 backend 內用 var.environment，跑 TF_VAR_environment=dev tofu init -reconfigure 切換
  10. 挑戰題 3 · 雙模式比較：把 lab 同時做成 workspace 模式與目錄分離模式，分別在兩種上跑 plan / apply / destroy，記錄你的個人偏好與理由
  11. 清掉所有 workspace 與資源
