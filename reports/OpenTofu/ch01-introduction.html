1. 什麼是 Infrastructure as Code（IaC）

在進入 OpenTofu 之前，我們必須先理解它要解決的核心問題：如何讓基礎設施像程式碼一樣可以被版控、審查、重現？

傳統的基礎設施管理多半是「手動操作」——工程師登入雲端 console 點擊滑鼠、SSH 進伺服器執行指令、用 Excel 紀錄誰擁有哪台機器。這種方式有幾個致命缺陷：

  • 無法重現：dev 環境跟 production 環境的設定可能差了二十處你不知道的細節
  • 沒有審計軌跡：誰在什麼時候改了什麼，全靠記憶
  • 無法 rollback：操作錯了只能再手動改回去，沒有 git revert 這種東西
  • 規模化困難：管 5 台機器靠人腦，管 500 台就會崩潰

IaC（Infrastructure as Code，基礎設施即程式碼）的核心理念非常簡單：把整個雲端環境的「樣子」寫成設定檔，這份檔案就是事實的唯一來源（single source of truth）。要建立或變更基礎設施，只要修改這份檔案，由工具自動執行對應的 API 呼叫。

    B -->|git commit| C[版本控制系統]
    C -->|tofu apply| D[OpenTofu 引擎]
    D -->|API 呼叫| E[AWS]
    D -->|API 呼叫| F[Azure]
    D -->|API 呼叫| G[GCP]

採用 IaC 後，你獲得的是：

  • 可版控（versionable）：每次變更都有 git log，可以 review、可以 revert
  • 可重現（reproducible）：同一份設定檔在哪裡跑都能拉出一樣的環境
  • 可審計（auditable）：誰在哪個 PR 改了什麼一清二楚
  • 可協作（collaborative）：團隊成員透過 PR 合作，不會踩到彼此
  • idempotent（冪等）：同一份設定 apply 一次跟 apply 一百次的結果相同

術語小辭典

idempotent（冪等）：執行多次與執行一次的效果相同。這是 IaC 工具最重要的性質之一，意味著你可以反覆執行 tofu apply 而不會造成資源被重複建立或破壞。

2. 宣告式 vs 命令式：兩種 IaC 哲學

IaC 工具有兩大流派：命令式（imperative）與宣告式（declarative）。OpenTofu 屬於後者。理解這兩者的差異是掌握 OpenTofu 心法的關鍵。

命令式：告訴電腦「怎麼做」

命令式工具（例如 Ansible 的 playbook、Chef、Puppet 在某些用法下）讓你描述步驟。你寫的是「先 SSH 進去、再裝 nginx、再開 80 port、再啟動服務」。

YAML · Ansible（命令式範例） 
- name: Install and start nginx
  hosts: webservers
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
    - name: Start nginx
      service:
        name: nginx
        state: started

宣告式：告訴電腦「最後要長什麼樣」

宣告式工具讓你描述結果。你寫的是「我要有一台機器，上面跑 nginx，狀態是 running」——至於要做哪些動作來達到這個狀態，是工具的事，不是你的事。

HCL · OpenTofu（宣告式範例） 
resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"

  tags = {
    Name = "nginx-server"
  }
}

OpenTofu 拿到這份設定後，會自動比對「目前實際狀態」與「設定檔描述的目標狀態」，計算出差異（diff），然後執行必要的動作把差異弭平。這個比對的過程叫做 plan，執行的過程叫做 apply。

面向 命令式（Imperative） 宣告式（Declarative）
你描述的 怎麼做（步驟） 要長什麼樣（結果）
典型工具 Ansible、Chef、Bash 腳本 OpenTofu、Terraform、CloudFormation
學習曲線 較低，邏輯直觀 較高，需理解 state 與 diff
大規模管理 容易失控、執行順序敏感 可預測、可重現
idempotent 需開發者自行保證 原生內建

兩者並非對立

實務上，IaC 與 configuration management 經常並用：用 OpenTofu 提供（provision）虛擬機與網路，用 Ansible 進入機器內部設定軟體。OpenTofu 處理「機器、網路、雲端資源」，Ansible 處理「機器內部的軟體狀態」。

3. OpenTofu 的起源與授權事件

要理解 OpenTofu 為何存在，必須回到 2023 年 8 月那場震撼開源社群的事件。

事件時間軸

2014 · 07

Terraform 0.1 釋出

HashiCorp 推出 Terraform，採用 Mozilla Public License 2.0（MPL-2.0），定位為通用的 IaC 工具。此後十年成為產業事實標準。

2023 · 08 · 10

HashiCorp 變更授權

HashiCorp 突然宣布將旗下所有產品（包含 Terraform）的授權從 MPL-2.0 改為 Business Source License（BUSL/BSL）。BUSL 並非開源授權，明文禁止「對 HashiCorp 商業產品構成競爭」的使用方式。

2023 · 08 · 15

OpenTF Manifesto 發布

短短五天後，社群與多家廠商（Spacelift、env0、Scalr、Harness、Gruntwork）聯合發起 OpenTF 倡議，承諾將 Terraform 留在開源世界。Manifesto 在 GitHub 上迅速累積數萬顆星。

2023 · 09 · 20

捐贈 Linux Foundation，更名 OpenTofu

專案正式加入 Linux Foundation，更名為 OpenTofu，採用中立治理模式。從 BUSL 變更前的最後一個 MPL-2.0 commit 分支（fork）出來，確保授權合法性。

2024 · 01

OpenTofu 1.6.0 首個穩定版

與 Terraform 1.6.x 高度相容，使用者只要把 terraform 指令換成 tofu 即可遷移。

2024 · 04

OpenTofu 1.7：State Encryption 上線

推出 OpenTofu 獨家的 state 檔案加密與 provider-defined functions，這是 Terraform 沒有的功能。專案開始走出自己的路。

2024 · 04

HashiCorp 寄發 cease and desist

HashiCorp 指控 OpenTofu 不當使用 BUSL 授權的 Terraform 程式碼。OpenTofu 否認指控，主張所引用的程式碼皆來自 MPL 授權版本。事件最終未演變為訴訟。

2025 · 12 · 09

OpenTofu 1.11.0：Ephemeral Resources

推出 ephemeral 資源（敏感資料不寫入 state）與 enabled meta-argument（清晰的條件式資源啟用）。

2026 · 04 · 08

當前最新穩定版：1.11.6

下一個主版本 1.12 已進入 beta 階段。OpenTofu 進入穩定發展期。

為什麼授權變更這麼嚴重？

BUSL 授權的核心限制是：「使用本軟體不得構成對 HashiCorp 商業產品的競爭」。這對下列人造成直接衝擊：

  • 建構於 Terraform 之上的廠商：Spacelift、env0、Scalr、Atlantis 等公司的產品本質上就是「跑 Terraform」，BUSL 讓它們的商業模式陷入法律不確定性
  • 大型企業：法務部門通常不允許使用授權條款不明確、可能被單方面變更的軟體
  • 開源生態：BUSL 不被 OSI 認可為開源授權，社群信任受損

授權對比速記

MPL-2.0（OpenTofu 採用）：自由使用、修改、商用、再散布，僅要求修改後的檔案保持 MPL 授權。OSI 認可的開源授權。
BUSL-1.1（Terraform 採用）：源碼可看、可改，但商業使用受限，且通常設定四年後自動轉為其他授權。非開源授權。

四大元件

① OpenTofu Core（核心引擎）

用 Go 撰寫的單一二進位檔（tofu）。負責解析 HCL 設定檔、建構資源依賴圖、計算 plan、執行 apply。它本身不知道如何呼叫任何雲端 API——所有與外部世界的互動都透過 provider 完成。

② Provider（外掛）

每一個 provider 是一個獨立的二進位檔，透過 gRPC 與 OpenTofu Core 通訊。Provider 知道「要建立 AWS EC2 實例需要呼叫哪個 API、傳哪些參數、回傳什麼欄位」。Public OpenTofu Registry 上有超過 4,000 個 provider，涵蓋幾乎所有主流雲端與 SaaS 服務。

③ Resource Graph（資源依賴圖）

OpenTofu 解析設定檔後會建立一張有向無循環圖（DAG），描述資源之間的依賴關係。例如「subnet 依賴 VPC」「EC2 依賴 subnet 與 security group」。執行 apply 時會依拓撲順序處理，無依賴關係的資源會平行建立。

④ State（狀態檔）

OpenTofu 把它管理的每一個資源的目前狀態紀錄在 state 檔（terraform.tfstate，是的，檔名仍沿用 terraform 字樣）。下次 plan 時會比對 state 與設定檔，算出要做的變更。State 檔可以存在本地，也可以放到遠端 backend（S3、GCS、Azure Blob 等）讓團隊共享。

核心工作流程：Write → Plan → Apply

這是 OpenTofu 整個工具的精神。撰寫設定（write）→ 預覽變更（plan）→ 確認後執行（apply）。每次操作前的 plan 步驟會顯示「將新增 X 個資源、修改 Y 個、刪除 Z 個」，是避免意外的關鍵安全網。

5. OpenTofu vs Terraform vs 其他 IaC 工具

OpenTofu vs Terraform

這是最常被問到的問題。簡單版本：2024 年中以後，新專案應該選 OpenTofu。詳細版本則依使用情境而定。

面向 OpenTofu Terraform
授權 MPL-2.0（真正的開源） BUSL-1.1（非開源，商用受限）
治理 Linux Foundation 中立治理 HashiCorp（已被 IBM 收購）
HCL 語法相容性 1.6.x 完全相容；1.7+ 開始有獨家功能 原生
Provider 相容性 所有 MPL 授權的 provider 直接可用（包含 AWS、Azure、GCP） 原生
State 加密 ✅ 原生支援（1.7+） ❌ 需第三方工具
Provider-defined functions ✅ 原生支援 後來也支援，但生態較分裂
Backend 區塊使用變數 ✅ 原生支援 ❌ 不支援
enabled meta-argument ✅ 1.11+ 原生支援 ❌ 需用 count hack
Ephemeral resources ✅ 1.11+ 支援 1.10+ 開始支援
商業產品授權 無限制 受 BUSL 限制
Registry OpenTofu Registry（4,000+ providers） HashiCorp Registry

與其他 IaC 工具比較

工具 定位 語言 適用場景
OpenTofu 多雲、多 provider 的 IaC HCL（宣告式） 跨雲、企業級基礎設施管理
Pulumi 用通用程式語言寫 IaC TypeScript / Python / Go / C# / Java 軟體工程師主導、複雜邏輯需求高的團隊
AWS CloudFormation AWS 原生 IaC JSON / YAML（宣告式） 純 AWS 環境、需要與 AWS 服務深度整合
Azure Bicep / ARM Azure 原生 IaC Bicep DSL / JSON 純 Azure 環境
Ansible configuration management（偏命令式） YAML（playbook） 機器內部設定、應用部署、跑一次性任務
Crossplane K8s-native 的 IaC YAML（CRD） 已重度使用 K8s、想用 K8s API 管基礎設施

選型決策樹

你的環境主要是單一雲且想用原生工具？選 CloudFormation / Bicep。
你想用程式語言寫 IaC，能寫複雜邏輯？選 Pulumi。
你已經 all-in Kubernetes？看看 Crossplane。
你需要跨雲、跨服務、生態最大、社群最廣？選 OpenTofu。

6. 何時該用 OpenTofu？何時不該？

✅ 適合使用 OpenTofu 的場景

  • 多雲（multi-cloud）或混合雲環境：需要同時管 AWS、Azure、GCP，OpenTofu 的 provider 生態無人能敵
  • 跨雲端與 SaaS 整合：例如「在 AWS 開 EC2，同時在 Datadog 建立 monitor、在 PagerDuty 建立 escalation policy、在 GitHub 建立 repo」這類流程
  • 需要長期穩定、團隊協作的基礎設施：版控、PR review、CI/CD 整合這套流程已經非常成熟
  • 產品中需要建立基礎設施的功能：例如 SaaS 平台讓使用者一鍵開出環境，OpenTofu 的 MPL 授權沒有商業使用限制
  • 合規要求高的企業：需要 state 加密、稽核軌跡、明確開源授權

⚠️ 不太適合的場景

  • 機器內部設定：OpenTofu 不適合裝套件、改設定檔、跑 shell script。這類事情交給 Ansible、Chef、cloud-init
  • 頻繁變動的應用部署：「每天 deploy 100 次新版本」這種事情，OpenTofu 不是最好的選擇。用 Helm、ArgoCD、應用層 CI/CD 更適合
  • 一次性的腳本任務：例如「批次重啟 50 台機器」「跑一次資料遷移」，用 bash 或 Ansible 簡單得多
  • 單純的容器編排：用 Kubernetes 原生工具（Helm、Kustomize）通常比用 OpenTofu 管 K8s 資源更方便

常見誤區

有人會試圖用 OpenTofu 管所有東西——包含應用層的設定。這通常是個壞主意。OpenTofu 適合管「變動較少、結構穩定」的東西（VPC、IAM、資料庫實例、DNS）。對於「變動頻繁、生命週期短」的東西（容器化應用），用對應的工具更省事。

7. 本章重點與練習

重點回顧

  • IaC 是把基礎設施寫成程式碼，獲得版控、可重現、可審計的能力
  • OpenTofu 屬於宣告式 IaC：你描述「要長什麼樣」，工具負責計算「怎麼做」
  • OpenTofu 是 2023 年 HashiCorp 變更 Terraform 授權後社群分支出來的專案，採用 MPL-2.0 並由 Linux Foundation 治理
  • OpenTofu 與 Terraform 1.6.x 完全相容，從 1.7 開始有獨家功能（state 加密、ephemeral resources、enabled meta-argument 等）
  • OpenTofu 由 Core、Provider、Resource Graph、State 四大元件組成
  • 適合多雲、跨服務的中長期基礎設施管理；不適合管機器內部或頻繁部署的應用
