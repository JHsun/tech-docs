1. 工作流程全景

OpenTofu 整個工具的精神可以濃縮成一句話：把你想要的基礎設施寫下來，讓工具規劃怎麼做，再執行它。HashiCorp 把這個工作流程稱為 Write → Plan → Apply，這是貫穿 OpenTofu 所有功能的核心思維模型。

實際上的步驟順序是：Write → Init → Plan → Apply。Init 之所以不在三步走的口號裡，是因為它通常在你建立新專案或加入新 provider/module 時才需要——日常迭代開發中你會不斷重複 Plan → Apply。

步驟 動作 是否變動雲端資源 是否變動 state
Write 編輯 .tf 檔 否 否
tofu init 下載 provider、連 backend 否 否
tofu plan 計算 diff、顯示變更 否（只讀取以 refresh state） 否（除非加 -refresh-only）
tofu apply 執行 plan 是 是
tofu destroy 銷毀所有資源 是 是

記住這個區分

在 OpenTofu 中，讀取（read）動作不會改變雲端，但計算 plan之前必須先讀取現狀。寫入（write）動作只發生在 apply 與 destroy。這個分離是 OpenTofu 安全性的核心。

2. Write：撰寫設定檔

Write 階段是你以人類可讀的方式描述「想要什麼」的階段。OpenTofu 使用 HCL（HashiCorp Configuration Language），副檔名為 .tf（也可用 .tofu，OpenTofu 1.6+ 起支援）。

典型專案結構

Plaintext · 標準目錄結構 
my-infra/
├── main.tf              # 主要資源定義
├── variables.tf         # 輸入變數
├── outputs.tf           # 輸出值
├── versions.tf          # OpenTofu 與 provider 版本約束
├── terraform.tfvars     # 變數預設值（通常 .gitignore）
├── .terraform.lock.hcl  # Provider 版本鎖定（要 git commit）
└── .terraform/          # Init 產生的快取（一律 .gitignore）

檔案分割不是強制的

OpenTofu 會把同一目錄下所有 .tf 檔案合併視為一個 module。你可以全部寫在 main.tf，也可以拆成 vpc.tf、iam.tf、rds.tf 等等。怎麼拆是給人類看的組織方式，跟工具行為無關。建議的分法：依資源類型或功能領域拆檔，每檔不超過 200 行。

四大基本 block

HCL 的 block 種類很多，剛入門你只需認識四個：

HCL · 四大基本 block 
# ① terraform block：宣告版本約束（檔名常為 versions.tf）
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

# ② variable block：輸入變數
variable "greeting" {
  type        = string
  description = "問候語"
  default     = "Hello, OpenTofu!"
}

# ③ resource block：你想要 OpenTofu 管理的東西
resource "local_file" "greeting" {
  filename = "${path.module}/greeting.txt"
  content  = var.greeting
}

# ④ output block：執行完想印出來的值
output "file_path" {
  value = local_file.greeting.filename
}

HCL 還有 data（讀取既有資源）、module（呼叫 module）、locals（區域變數）等其他 block，會在 Part 2 系統介紹。

3. tofu init：初始化工作目錄

tofu init 是每個新專案的第一個指令，也是修改 provider 或 backend 設定後必跑的指令。它的工作可以分成幾個階段：

Init 後產生的東西

產物 用途 git 處理

常用 init flag

# 升級 provider 到 required_providers 允許的最新版本

tofu init -reconfigure

# 遷移既有 state 到新 backend
tofu init -migrate-state

# CI/CD 友善：不互動、輸出簡潔
tofu init -input=false -no-color

# 不下載 provider（只做檔案結構初始化）
tofu init -backend=false -get=false

4. tofu plan：基礎設施工具最重要的安全網

tofu plan 是 OpenTofu 整個設計哲學的核心。它做了三件事：

  1. Refresh：呼叫 provider API，讀取目前每個受管資源的真實狀態，更新 state（in-memory）
  2. Diff：比對「設定檔描述的目標」與「state 紀錄的現狀」，計算出差異
  3. Output：把要做的動作以人類可讀格式印出來

plan 不會修改任何雲端資源。它只讀取，不寫入。所以你可以放心地反覆執行，當作「what-if」分析工具。

Plan 的完整生命週期

flowchart TD
    Start[tofu plan]
    Start --> Load[載入 .tf 檔與變數]
    Load --> Validate[驗證設定語法]
    Validate --> InitProv[啟動 provider plugin]
    InitProv --> Refresh{是否 refresh？
預設：是}
    Refresh -->|是| ReadAPI[呼叫雲端 API
讀取每個資源實際狀態]
    Refresh -->|否| UseCache[使用 state 中的快照]
    ReadAPI --> BuildGraph[建立 resource dependency graph]
    UseCache --> BuildGraph
    BuildGraph --> CalcDiff[逐個資源計算 diff]
    CalcDiff --> ShowPlan[輸出 plan 結果]
    ShowPlan --> SaveOpt{有 -out 旗標？}
    SaveOpt -->|是| SaveFile[存成 plan 檔
供 apply 直接用]
    SaveOpt -->|否| Speculative[僅 speculative
顯示後丟棄]

讀懂 Plan 輸出的符號

OpenTofu plan 的輸出用幾個符號表達將要做的事：

符號 意思 對應行為
+ create 新建資源
- destroy 銷毀資源
~ update in-place 原地修改（不會重建）
-/+ destroy and re-create 先銷毀後重建（force replacement）
+/- create then destroy 先建立後銷毀（搭配 create_before_destroy）
<= read 讀取 data source
(known after apply) 未知值 該屬性在 apply 後才會知道（例如雲端產生的 ID）

典型 plan 輸出範例

Plaintext · plan output 
OpenTofu will perform the following actions:

  # local_file.greeting will be created
  + resource "local_file" "greeting" {
      + content              = "Hello, OpenTofu!"
      + content_base64sha256 = (known after apply)
      + filename             = "./greeting.txt"
      + id                   = (known after apply)
    }

  # local_file.config will be updated in-place
  ~ resource "local_file" "config" {
        id      = "abc123..."
      ~ content = "old content" -> "new content"
        # (3 unchanged attributes hidden)
    }

  # local_file.legacy will be destroyed
  - resource "local_file" "legacy" {
      - filename = "./old.txt" -> null
      - content  = "to be removed" -> null
    }

Plan: 1 to add, 1 to change, 1 to destroy.

最後一行 Plan: X to add, Y to change, Z to destroy 是每次 apply 前必看的數字。如果這個數字超出你的預期，先別 apply，回頭找出原因。

Plan 的三種模式

模式 指令 用途
Normal mode tofu plan 預設，計算「要怎麼做才能讓現狀符合設定」
Destroy mode tofu plan -destroy 計算「銷毀所有資源」的計畫
Refresh-only mode tofu plan -refresh-only 只更新 state 來反映實際狀態變動，不變動資源（用於 incident 後 reconcile）

儲存 plan 檔：production 必備工作流程

在 production 環境，最佳實踐是把 plan 存成檔案，然後 apply 那個檔案，確保「審查的內容」與「執行的內容」完全一致：

Bash · plan 檔工作流程 
# 1. 產生 plan 並存成檔案
tofu plan -out=tfplan.binary

# 2. 用人類可讀格式查看（也可以輸出 JSON 給審查工具用）
tofu show tfplan.binary
tofu show -json tfplan.binary > plan.json

# 3. （PR 審查、approval 流程...）

# 4. 直接 apply 那個檔案（不會重新計算 plan）
tofu apply tfplan.binary

Plan 檔含敏感資料

Plan 檔會包含設定中的所有變數值（包括 sensitive 標記的 secrets）以及 provider 認證資訊。絕對不要 commit 進 git，也不要存放在公開地方。CI/CD 中傳遞 plan 檔時，應使用加密的 artifact storage。

5. tofu apply：把 plan 變成現實

tofu apply 接續 plan 計算出的動作，依 dependency graph 順序呼叫 provider API 執行變更，並更新 state 檔。

兩種 apply 模式

Bash · apply 兩種模式 
# 模式 A：互動式（會先顯示 plan、再要求確認）
tofu apply
# 顯示 plan 後問：Do you want to perform these actions? Only 'yes' will be accepted to approve.

# 模式 B：apply 一個事先存好的 plan 檔（CI/CD 標配）
tofu apply tfplan.binary
# 直接執行，不再 plan 也不再詢問

# 模式 C：跳過確認（危險，慎用）
tofu apply -auto-approve

Apply 進行中發生的事

sequenceDiagram
    participant U as 使用者
    participant T as OpenTofu Core
    participant P as Provider Plugin
    participant API as 雲端 API
    participant S as State Backend

    U->>T: tofu apply
    T->>S: 取得 state lock
    S-->>T: lock 成功
    T->>T: 重跑 plan（除非用 plan 檔）
    T->>U: 顯示 plan + 詢問確認
    U->>T: yes

    loop 每個資源（依 dependency 順序）
        T->>P: 呼叫對應 CRUD 操作
        P->>API: API 請求
        API-->>P: 回應
        P-->>T: 結果（含新屬性值）
        T->>S: 更新 state
    end

    T->>S: 釋放 state lock
    T-->>U: Apply complete!

輸出範例

Plaintext · apply output 
local_file.greeting: Creating...
local_file.greeting: Creation complete after 0s [id=abc123...]
local_file.config: Modifying... [id=def456...]
local_file.config: Modifications complete after 0s [id=def456...]
local_file.legacy: Destroying... [id=ghi789...]
local_file.legacy: Destruction complete after 0s

Outputs:

file_path = "./greeting.txt"

Apply 失敗時會發生什麼？

OpenTofu 不是交易型系統——它無法 atomic rollback。如果 apply 跑到一半失敗：

  • 已經建立的資源不會自動回滾，但會被記錄到 state 中
  • State 維持在「部分完成」的真實狀態
  • 你下次 tofu plan 會看到剩餘未完成的動作
  • 修正設定後再 apply，OpenTofu 會接續從失敗點往下做

「tainted」狀態

當資源建立成功但設定動作（provisioner）失敗時，該資源會被標記為 tainted。下次 plan 會將它列為「先銷毀再重建」。可用 tofu untaint <resource> 移除標記，tofu taint <resource> 手動加上標記。

6. tofu destroy：受控的拆除

tofu destroy 會銷毀目前 state 中所有受管資源。它的行為等同於「把所有資源從設定檔刪除，再 apply」。

Bash · destroy 用法 
# 互動式（顯示要銷毀什麼，要求輸入 yes）
tofu destroy

# 預覽 destroy plan（推薦）
tofu plan -destroy
tofu plan -destroy -out=destroy.tfplan
tofu apply destroy.tfplan

# 只銷毀特定資源（emergency 用，正常開發應透過修改設定）
tofu destroy -target=aws_instance.temp_server

# 自動確認（dev/CI 用，production 千萬別這樣做）
tofu destroy -auto-approve

保護重要資源不被誤刪

對於 production 的核心資源（資料庫、S3 bucket 等），務必加上 prevent_destroy lifecycle 規則：

HCL · 防止誤刪 
resource "aws_db_instance" "production" {
  identifier = "prod-db"
  # ...

  lifecycle {
    prevent_destroy = true
  }
}

當有人試圖透過修改設定觸發銷毀，OpenTofu 會直接 refuse 並回報錯誤。

prevent_destroy 不擋直接 destroy

prevent_destroy 只擋「因設定變更而觸發的 replace 或 destroy」，它不會擋住 tofu destroy。要徹底保護，需配合 IAM 政策、CI/CD approval 流程、state lock 與 backup 策略。

Destroy 的替代方案：tofu state rm

如果你只是想讓 OpenTofu「不再管理」某個資源（但保留雲端上的資源），用 tofu state rm：

Bash · 從 state 移除（不銷毀） 
# 把 aws_instance.legacy 從 state 移除
# 雲端上的 EC2 實例會繼續存在，只是 OpenTofu 不再管它
tofu state rm aws_instance.legacy

7. State 初識：OpenTofu 的記憶

State 檔（terraform.tfstate）是 OpenTofu 整個系統的記憶。它紀錄：

  • 每個受管資源的唯一 ID（例如 AWS instance 的 i-0abc123...）
  • 每個資源的所有屬性值（建立時填入的、雲端產生的、後續變更的）
  • 資源之間的依賴關係
  • 使用的 provider 版本
  • State serial 與 lineage（用於版本管理與防止覆寫）

看一眼 state 檔

JSON · terraform.tfstate（節錄） 
{
  "version": 4,
  "terraform_version": "1.11.6",
  "serial": 7,
  "lineage": "abc-123-def-456",
  "outputs": {
    "file_path": {
      "value": "./greeting.txt",
      "type": "string"
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "local_file",
      "name": "greeting",
      "provider": "provider[\"registry.opentofu.org/hashicorp/local\"]",
      "instances": [
        {
          "schema_version": 0,
          "attributes": {
            "id": "5d41402abc...",
            "filename": "./greeting.txt",
            "content": "Hello, OpenTofu!"
          }
        }
      ]
    }
  ]
}

state 子指令速查

指令 用途
tofu state list 列出所有受管資源
tofu state show <addr> 顯示單一資源的所有屬性
tofu state pull 把遠端 state 印到 stdout（除錯用）
tofu state mv 重新命名資源（重構用）
tofu state rm 從 state 移除（不銷毀）
tofu state replace-provider 更換 provider 來源

State 包含敏感資料

Provider 取得的所有屬性都會寫進 state，包括資料庫密碼、API token、private key 等。這就是為什麼：① state 絕對不能 commit 進 git；② 團隊環境必須用支援加密的 remote backend；③ OpenTofu 1.7+ 開始提供原生的 state 加密功能（將在 Part 2 第 12 章詳細介紹）。

8. Resource Graph：依賴關係如何被計算

OpenTofu 解析設定檔後會建立一張有向無循環圖（DAG），描述資源之間的依賴關係。Plan 與 apply 都依此圖的拓撲順序執行。

依賴的兩種形式

HCL · 隱式 vs 顯式依賴 
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

# ① 隱式依賴（implicit）：OpenTofu 從表達式中自動推斷
# 因為這個 subnet 引用了 aws_vpc.main.id，OpenTofu 知道必須先建 VPC
resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

# ② 顯式依賴（explicit）：用 depends_on 強制宣告
# 當 OpenTofu 無法從表達式推斷依賴時使用（例如 IAM policy 必須先存在）
resource "aws_instance" "web" {
  ami           = "ami-0abc..."
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.public.id

  depends_on = [
    aws_iam_role_policy.s3_read,
  ]
}

視覺化你的 graph

OpenTofu 內建指令可以輸出 graph 的 DOT 格式，搭配 Graphviz 視覺化：

Bash · 產生 graph 
# 輸出 DOT 格式
tofu graph

# 轉成 PNG（需先 brew install graphviz 或 apt install graphviz）
tofu graph | dot -Tpng > graph.png

# 不同類型的 graph
tofu graph -type=plan       # plan 階段的 graph（預設）
tofu graph -type=apply      # apply 階段的 graph
tofu graph -type=plan-destroy   # destroy plan 的 graph

OpenTofu 看到這張圖後會：

  1. 第一波並行建立：VPC、IAM policy（彼此無依賴）
  2. 第二波並行建立：subnet、security group（都依賴 VPC，彼此無依賴）
  3. 第三波建立：EC2 instance（依賴所有上述資源）

OpenTofu 預設並行度是 10（可用 -parallelism=N 調整）。對於含上百個資源的大型 module，這個並行能讓整體建立時間從幾十分鐘降到幾分鐘。

9. 完整範例：建立、修改、銷毀一個檔案

把前面所有概念串起來。我們用 local provider 操作本地檔案，不需要任何雲端帳號就能完整體驗整個生命週期。

步驟一：撰寫設定

Bash · 建立專案 
mkdir lifecycle-demo && cd lifecycle-demo
HCL · main.tf 
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

variable "team_name" {
  type        = string
  description = "Team name to greet"
  default     = "Platform"
}

resource "local_file" "greeting" {
  filename = "${path.module}/greeting.txt"
  content  = "Hello, ${var.team_name} team!\nGenerated at: ${timestamp()}\n"

  # 改變 timestamp 不應該觸發 replace
  lifecycle {
    ignore_changes = [content]
  }
}

output "file_path" {
  value = local_file.greeting.filename
}

步驟二：init

Bash 
tofu init

第一次跑會看到 OpenTofu 下載 local provider，並產生 .terraform/ 與 .terraform.lock.hcl。

步驟三：plan + apply（建立）

Bash 
tofu plan
# 看到：Plan: 1 to add, 0 to change, 0 to destroy.

tofu apply
# 輸入 yes
# 看到：Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

# 確認檔案存在
cat greeting.txt

步驟四：修改變數，再 apply

Bash · 用 -var 覆寫 
tofu plan -var="team_name=SRE"

# 因為我們設了 ignore_changes = [content]，content 變動不會觸發 update
# 看到：No changes. Your infrastructure matches the configuration.

有沒有發現？這就是 lifecycle.ignore_changes 的用途：告訴 OpenTofu「這個屬性後續變動我自己會處理，你不用幫我同步」。實務上常用於忽略 ASG 的 desired_capacity（會被 autoscaler 動態調整）。

步驟五：強制 replace

Bash 
# 強制重建（destroy + create）
tofu apply -replace=local_file.greeting

# 看到 -/+ 符號，表示 destroy and re-create

步驟六：destroy

Bash 
# 預覽 destroy
tofu plan -destroy

# 執行 destroy
tofu destroy
# 輸入 yes
# 檔案被刪除，state 清空

檢查 state 變化

Bash · 在 apply 後執行 
tofu state list
# local_file.greeting

tofu state show local_file.greeting
# 印出該資源的所有屬性

cat terraform.tfstate | head -30
# 看到 JSON 格式的完整 state

10. 常見陷阱與最佳實踐

陷阱 1：在 production 用 -auto-approve

-auto-approve 跳過確認，省下一次「yes」的時間，但失去最後一道安全網。在 dev/CI 可以接受，production 應該強制要求 reviewer 審視 plan 才能 apply。

陷阱 2：手動修改雲端資源

雲端 console 點點點直接改設定，這叫 configuration drift。下次 plan 時 OpenTofu 會嘗試把它「改回設定檔的樣子」，可能造成意外。

處理方式：

  • 避免：強制所有變更走 OpenTofu
  • 偵測：定期跑 tofu plan -refresh-only 並監控結果
  • 接受：用 lifecycle.ignore_changes 標示 OpenTofu 不該管的屬性

陷阱 3：plan 看起來沒問題，apply 卻失敗

常見原因：

  • Plan 與 apply 之間有人改了雲端資源（race condition）
  • Provider quota 不足（IAM 權限只夠 read 不夠 write）
  • 資源之間有隱性依賴 OpenTofu 看不出來（例如某些 cloud SDK 的最終一致性問題）
  • 前次 apply 失敗留下 tainted 資源

對策：production 一律用 plan -out + apply tfplan 兩步流程，把 plan 與 apply 之間的時間窗縮短。

陷阱 4：state 損毀或遺失

State 檔損毀後 OpenTofu 會以為「沒管理任何資源」，下次 apply 會試圖重建已存在的資源（並失敗）。預防：

  • 使用支援版本控制的 remote backend（S3 with versioning、GCS with object versioning）
  • 啟用 state lock（DynamoDB、blob lease 等）防止並行寫入
  • 定期備份

最佳實踐速查

場景 建議做法
Local dev tofu plan + tofu apply 互動模式即可
CI/CD pipeline 分兩階段：plan 階段產生 plan 檔上傳 artifact，apply 階段下載並 apply 該檔
Production apply plan 檔 + 至少一名 reviewer + 加 -input=false -no-color
大型 module（>100 resources） 調整 -parallelism，但小心 cloud API rate limit
緊急情境（incident） 用 -target 限縮影響範圍，事後立刻把所有變更納入設定檔

11. 本章重點與練習

重點回顧

  • OpenTofu 工作流程是 Write → Init → Plan → Apply，destroy 是生命週期結束時才用
  • tofu init 下載 provider、設定 backend、產生 lock 檔，每個新專案或 provider/backend 變動時必跑
  • tofu plan 是只讀操作，計算現狀與目標的 diff，用符號（+、-、~、-/+）顯示動作
  • Production 應該plan 存檔 → 審查 → apply 該檔，避免 plan 與 apply 之間的偏移
  • tofu apply 依 dependency graph 順序呼叫 provider API，並更新 state；不是交易型，失敗不會自動 rollback
  • Resource graph 是 DAG，OpenTofu 會把無相依的資源並行處理，預設並行度 10
  • State 是 OpenTofu 的記憶，含敏感資料，絕對不能 commit 進 git
  • prevent_destroy 擋設定變更引發的 destroy，但不擋 tofu destroy
⚡ 動手實作 · Hands-on Lab 3

跑完一輪生命週期，並體驗 plan 安全網

  1. 跟著第 9 節做完一輪 init → plan → apply → modify → destroy
  2. 在 apply 之後，手動編輯 greeting.txt（例如刪掉一行），然後跑 tofu plan，觀察 OpenTofu 偵測到 drift
  3. 跑 tofu apply -refresh-only，看它如何只更新 state 不變動檔案
  4. 跑 tofu graph | head -30，看 graph 的 DOT 輸出（如果裝了 graphviz 可以轉 PNG）
  5. 實驗 tofu state list、tofu state show 兩個指令，理解 state 的內部結構
  6. 挑戰題：在 main.tf 加上第二個 local_file 資源，內容引用第一個檔案的 id 屬性。執行 tofu plan，觀察 OpenTofu 如何正確判斷依賴順序（你會看到 (known after apply)）。完成後 destroy。
