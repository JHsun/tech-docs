1. 為什麼 IaC 需要專屬 CI/CD

把 application code 跑 CI/CD 已是行業標準，但 IaC 的 CI/CD有幾個本質上不同的特性：

面向App CI/CDIaC CI/CD
StateStateless（每次重來）Stateful（state 是事實來源）
並行多個 build 可並行同一 stack 必須序列（state lock）
失敗成本Re-deploy 即可Partial apply，可能讓基礎設施處於奇怪狀態
人工 reviewCode review 即可必須 review plan 輸出（不只看代碼）
權限build runner 權限有限需要 cloud admin 級別權限
影響範圍app 層底層基礎設施（影響所有 app）
Drift 偵測不適用需主動偵測（外部變更 vs 設定）

不要用 app CI/CD 模板套到 IaC

常見錯誤是把 app 的 GitHub Actions YAML 改一改用在 IaC，結果忽略了 state lock、plan-as-artifact、approval gate 等 IaC 專屬考量。本章介紹的模板是 IaC 量身打造的。

3. PR-driven Workflow 標準模式

不論用哪個平台，IaC CI/CD 都遵循同一個基本模式：

sequenceDiagram
    participant Dev as 開發者
    participant Repo as Git Repo
    participant CI as CI/CD Platform
    participant Cloud as Cloud
    participant State as State Backend

    Dev->>Repo: 1. 開 PR 含 .tf 變更
    Repo->>CI: 2. webhook 觸發

    Note over CI: Stage 1: Validate
    CI->>CI: tofu fmt -check
    CI->>CI: tofu validate

    Note over CI: Stage 2: Plan
    CI->>State: 取 lock
    CI->>Cloud: refresh state
    CI->>CI: tofu plan -out=tfplan
    CI->>State: 釋放 lock
    CI->>Repo: 把 plan 輸出貼到 PR comment

    Note over Dev,Repo: 人工 review code + plan

    Dev->>Repo: 3. Approve & Merge

    Note over CI: Stage 3: Apply（觸發於 main branch）
    CI->>State: 取 lock
    CI->>CI: tofu apply tfplan
    CI->>Cloud: 套用變更
    CI->>State: 寫 state、釋放 lock
    CI->>Repo: 通知結果

四個關鍵設計原則

  1. Plan as immutable artifact：plan 階段產生 tfplan.bin，approval 後 apply 階段直接用該檔案，避免「review 看到 A，apply 變 B」
  2. Two-stage with manual gate：Plan 自動跑、Apply 需 human approval（PR merge 或 manual approve）
  3. Least-privilege per stage：Plan 階段只需讀權限；Apply 階段才需寫權限
  4. State locking always-on：所有寫操作必持 lock，CI 中 lockfile=readonly 防止意外更新

4. GitHub Actions 完整實作

標準 PR-driven workflow

YAML · .github/workflows/tofu.yml 
name: OpenTofu

on:
  pull_request:
    paths:
      - '**.tf'
      - '**.tfvars'
      - '.terraform.lock.hcl'
  push:
    branches: [main]
    paths:
      - '**.tf'
      - '**.tfvars'

permissions:
  contents: read
  id-token: write          # OIDC 拿 AWS credentials 必要
  pull-requests: write     # PR comment 必要

env:
  TF_INPUT: "0"
  TF_IN_AUTOMATION: "true"
  TF_PLUGIN_CACHE_DIR: ~/.terraform.d/plugin-cache

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Cache OpenTofu plugins
        uses: actions/cache@v4
        with:
          path: ~/.terraform.d/plugin-cache
          key: tofu-${{ hashFiles('**/.terraform.lock.hcl') }}
          restore-keys: tofu-

      - name: Setup OpenTofu
        uses: opentofu/setup-opentofu@v2
        with:
          tofu_version: 1.11.6

      - name: AWS OIDC（Plan 用 read-only role）
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/TofuPlanRole
          aws-region: us-east-1

      - run: mkdir -p ~/.terraform.d/plugin-cache

      - name: Init
        run: tofu init -lockfile=readonly -no-color

      - name: Format check
        run: tofu fmt -check -recursive -no-color

      - name: Validate
        run: tofu validate -no-color

      - name: Plan
        id: plan
        run: |
          tofu plan -no-color -out=tfplan.bin -detailed-exitcode
        continue-on-error: true

      - name: Upload plan artifact
        if: github.event_name == 'pull_request'
        uses: actions/upload-artifact@v4
        with:
          name: tfplan-${{ github.run_id }}
          path: tfplan.bin
          retention-days: 7

      - name: Plan summary
        run: tofu show -no-color tfplan.bin > plan_output.txt

      - name: PR comment with plan
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('plan_output.txt', 'utf8');
            const truncated = plan.length > 60000 ? plan.slice(0, 60000) + '\n\n... (truncated)' : plan;
            const body = `### OpenTofu Plan 📐\n\n<details><summary>Show plan</summary>\n\n\`\`\`\n${truncated}\n\`\`\`\n\n</details>`;

            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: body
            });

      - name: Fail on plan error
        if: steps.plan.outcome == 'failure'
        run: exit 1

  apply:
    needs: plan
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production    # GitHub Environments 啟用 manual approval

    steps:
      - uses: actions/checkout@v4

      - uses: opentofu/setup-opentofu@v2
        with:
          tofu_version: 1.11.6

      - name: AWS OIDC（Apply 用 read/write role）
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/TofuApplyRole
          aws-region: us-east-1

      - run: tofu init -lockfile=readonly -no-color

      - name: Apply
        run: tofu apply -no-color -auto-approve

關鍵設計重點

設計原因
paths: 只在 .tf 變更觸發避免 README 改動也跑 OpenTofu
OIDC + 兩個 IAM rolePlan 用 read-only、Apply 用 write，最小權限
plugin cache跨 run 共享，加速 init
-lockfile=readonly避免 CI 意外更新 lock 檔
-detailed-exitcode0=無變更、1=錯、2=有變更，CI 可判斷
plan 上傳成 artifact後續 apply job 可下載使用（如需）
environment: production觸發 GitHub Environments 的 manual approval

OIDC IAM trust policy 範例

JSON · AWS IAM role trust policy 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",

        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"

5. GitLab CI 完整實作

YAML · .gitlab-ci.yml 
image: ghcr.io/opentofu/opentofu:1.11.6

variables:
  TF_INPUT: "0"
  TF_IN_AUTOMATION: "true"
  TF_PLUGIN_CACHE_DIR: ${CI_PROJECT_DIR}/.tofu-cache
  # GitLab managed terraform state（每個 project 內建）
  TF_TOKEN_gitlab_com: ${CI_JOB_TOKEN}

cache:
  paths:
    - .tofu-cache/

stages: [validate, plan, apply]

before_script:
  - mkdir -p $TF_PLUGIN_CACHE_DIR
  - tofu init -lockfile=readonly

validate:
  stage: validate
  script:
    - tofu fmt -check -recursive
    - tofu validate

plan:
  stage: plan
  script:
    - tofu plan -out=tfplan.bin -detailed-exitcode
    - tofu show -no-color tfplan.bin > plan.txt
  artifacts:
    name: "tfplan-$CI_COMMIT_SHORT_SHA"
    paths:
      - tfplan.bin
      - plan.txt
    expire_in: 7 days
    when: always

apply:
  stage: apply
  script:
    - tofu apply -no-color tfplan.bin
  needs: ["plan"]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual          # 手動 trigger（GitLab 的 approval gate）
  resource_group: production # 確保同 stack 不會多 pipeline 並行

GitLab CI 特色：resource_group

resource_group: production 是 GitLab 的序列化機制，確保同一 group 內的 job 絕不並行。對 IaC 是天然好搭檔——避免兩個 PR 同時 apply 同 stack。

GitLab Managed Terraform State

GitLab 內建 http backend 服務，每個 project 自動有獨立 state：

HCL 
terraform {
  backend "http" {
    address        = "https://gitlab.com/api/v4/projects/123/terraform/state/myapp"
    lock_address   = "https://gitlab.com/api/v4/projects/123/terraform/state/myapp/lock"
    unlock_address = "https://gitlab.com/api/v4/projects/123/terraform/state/myapp/lock"
    lock_method    = "POST"
    unlock_method  = "DELETE"
    retry_wait_min = 5
  }
}

# 認證透過 TF_TOKEN_gitlab_com 環境變數帶入

6. Atlantis：自架 PR 自動化

Atlantis 是 OSS、自架的 PR-driven OpenTofu 工具。最大特色是把 plan/apply 變成 PR comment 指令。

運作流程

sequenceDiagram
    participant Dev as 開發者
    participant GH as GitHub
    participant Atlantis as Atlantis Server
    participant State as State Backend

    Dev->>GH: 開 PR
    GH-->>Atlantis: webhook
    Atlantis->>Atlantis: 自動跑 tofu plan
    Atlantis->>GH: 回 PR comment with plan

    Dev->>GH: 留言 atlantis apply
    GH-->>Atlantis: webhook
    Atlantis->>State: 取 lock
    Atlantis->>Atlantis: tofu apply
    Atlantis->>State: 釋放 lock
    Atlantis->>GH: 回 PR comment 結果
    Dev->>GH: merge PR

關鍵特性

特性說明
PR comment 指令atlantis plan、atlantis apply、atlantis unlock
內建 lock避免兩個 PR 同時改同 directory
多 directory 支援monorepo 友善，依改動目錄自動偵測
OpenTofu 支援v0.27+ 起原生支援，設定 terraform_version: vX.Y 指向 tofu binary
缺點無 drift detection、policy 限制、需自己維運

atlantis.yaml 範例

YAML · atlantis.yaml（repo-level） 
version: 3
projects:
  - name: prod-network
    dir: envs/prod/network
    terraform_version: v1.11.6
    workflow: opentofu
    autoplan:
      when_modified: ["*.tf", "../../modules/**/*.tf"]
      enabled: true
    apply_requirements: [approved, mergeable]

  - name: prod-app
    dir: envs/prod/app
    terraform_version: v1.11.6
    workflow: opentofu
    autoplan:
      when_modified: ["*.tf", "../../modules/**/*.tf"]
    apply_requirements: [approved, mergeable]

workflows:
  opentofu:
    plan:
      steps:
        - run: tofu init -lockfile=readonly
        - run: tofu plan -out=$PLANFILE
    apply:
      steps:
        - run: tofu apply $PLANFILE

Atlantis 何時適合

  • 已有 K8s 環境可放 Atlantis pod
  • 團隊喜歡 PR-driven workflow，但沒預算用 SaaS
  • 不需要進階 policy / drift detection / cost estimation
  • 有人能 own 維運（webhook 設定、TLS、HA、log）

HCL · 用 Spacelift provider 管理 Spacelift stack 
terraform {
  required_providers {
    spacelift = {
      source  = "spacelift-io/spacelift"
      version = "~> 1.0"
    }
  }
}

resource "spacelift_stack" "prod_network" {
  name             = "prod-network"
  repository       = "myorg/infrastructure"
  branch           = "main"
  project_root     = "envs/prod/network"
  opentofu_version = "1.11.6"
  autodeploy       = false   # production 要 manual confirm

  labels = ["production", "opentofu", "aws"]
}

  stack_id            = spacelift_stack.prod_app.id
  depends_on_stack_id = spacelift_stack.prod_network.id
}

# Cloud integration：Spacelift 透過 OIDC 取得 AWS credentials
resource "spacelift_aws_integration_attachment" "prod" {
  integration_id = data.spacelift_aws_integration.main.id
  stack_id       = spacelift_stack.prod_network.id
  read           = true
  write          = true
}

TACOS 平台值得選的理由

  • Drift detection：自動偵測 console 改動，每 N 小時跑一次
  • Stack dependency：network apply 完自動觸發 app 的 plan/apply（不需 terraform_remote_state 手動串）
  • Policy as Code：plan 階段擋掉違反規範的變更
  • Cost estimation：plan 階段算出每月成本變化
  • Audit log + RBAC：誰在何時對哪個 stack 做了什麼
  • 共享 secret store：Spacelift Context、env0 Variables 等

8. Monorepo 多 stack 策略

大型團隊常把多個 stack 放同一 repo（infrastructure monorepo）。CI/CD 需要「只跑改動到的 stack」否則每次 PR 都跑 N 次 plan 拖慢全公司。

策略 1：Path-based filtering（GitHub Actions matrix）

YAML · 動態偵測改動的 stack 
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      stacks: ${{ steps.filter.outputs.stacks }}
    steps:
      - uses: actions/checkout@v4
      - id: filter
        uses: dorny/paths-filter@v3
        with:
          filters: |
            prod-network:
              - 'envs/prod/network/**'
              - 'modules/network/**'
            prod-app:
              - 'envs/prod/app/**'
              - 'modules/app/**'
            staging-app:
              - 'envs/staging/app/**'
              - 'modules/app/**'

  plan:
    needs: detect-changes
    if: needs.detect-changes.outputs.changes != '[]'
    strategy:
      matrix:
        stack: ${{ fromJson(needs.detect-changes.outputs.changes) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: tofu -chdir=envs/${{ matrix.stack }} init -lockfile=readonly
      - run: tofu -chdir=envs/${{ matrix.stack }} plan -out=tfplan.bin

策略 2：Terramate / Terragrunt 編排

Terramate 與 Terragrunt 提供「change detection」：

  • Terragrunt：run-all plan 配合 --queue-include-dir
  • Terramate：terramate list --changed 列出受影響的 stack

策略 3：用 TACOS 平台處理

Spacelift / env0 都內建 monorepo path-based 觸發，每個 stack 設定 project_root 即可，PR 變更哪個目錄自動觸發對應 stack。

9. 安全與權限管理

OIDC 短期憑證（必選）

2026 年的鐵則：絕不在 CI 設定永久 access key。所有主流 CI 平台都支援 OIDC：

CI 平台OIDC 對 AWSOIDC 對 AzureOIDC 對 GCP
GitHub Actions✅✅✅
GitLab CI✅✅✅
Atlantis透過 IRSA（K8s）或 EC2 Instance Profile類似類似
Spacelift✅（內建）✅✅

分階段權限：Plan-Read / Apply-Write

JSON · 兩個 IAM role 的 IAM policy 對比 
// TofuPlanRole（plan 階段用）：只讀
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "ec2:Describe*",
      "rds:Describe*",
      "iam:Get*",
      "iam:List*",
      "s3:GetObject",
      "s3:ListBucket",
      "dynamodb:GetItem",
      "dynamodb:DescribeTable",
      "kms:Decrypt"
    ],
    "Resource": "*"
  }]
}

// TofuApplyRole（apply 階段用）：完整權限

State 與 plan 檔的 secret 處理

檔案含敏感資料？處理
State是（含所有 sensitive 屬性）S3 SSE-KMS + OpenTofu 1.7+ encryption block
tfplan.bin是（含 state snapshot）artifact retention 短（7 天）+ encryption
terraform.tfstate.backup是同 state
plan_output.txt有 sensitive 但會被遮蔽用 -no-color 簡化、retention 短
.terraform/含 provider binary 與 module cache不 commit、CI 中可 cache

secret 注入：永遠用環境變數

YAML · 從 Secret Manager 動態取 
- name: Get DB password from Secrets Manager
  id: secret
  run: |
    PASS=$(aws secretsmanager get-secret-value \
      --secret-id prod/db/master \
      --query SecretString --output text | jq -r .password)
    echo "::add-mask::$PASS"
    echo "TF_VAR_db_password=$PASS" >> $GITHUB_ENV

- name: Apply
  run: tofu apply -auto-approve
  # 不需要在 .tf 任何地方寫 password

10. Policy as Code 整合

Policy as Code 在 plan 階段檢查「這個變更被允許嗎？」，把規則寫成可版控的程式碼。

主流選項

工具類型整合方式
Open Policy Agent (OPA)通用 policy engine對 plan JSON 跑 Rego 規則
ConftestOPA wrapperCLI 友善，CI 跑 conftest test plan.json
Checkov專為 IaC掃描 .tf 檔，內建上千條規則
tfsec / Trivy專為 IaC類似 Checkov，輕量
SentinelHashiCorp 商業HCP Terraform 限定（OpenTofu 不支援）

Conftest 整合範例

Rego · policy/no_public_s3.rego 
package main

deny[msg] {
  rc := input.resource_changes[_]
  rc.type == "aws_s3_bucket_public_access_block"
  not rc.change.after.block_public_acls
  msg := sprintf("S3 bucket %v: block_public_acls must be true", [rc.address])
}

deny[msg] {
  rc := input.resource_changes[_]
  rc.type == "aws_db_instance"
  rc.change.after.publicly_accessible == true
  msg := sprintf("RDS %v: publicly_accessible must be false", [rc.address])
}
Bash · CI 中 conftest 檢查 plan 
tofu plan -out=tfplan.bin
tofu show -json tfplan.bin > plan.json
conftest test --policy ./policy plan.json

# exit code 0 = 合規，>0 = 違反

11. 常見陷阱與最佳實踐

陷阱 1：Plan 階段就用 write 權限

圖方便給 plan 階段完整 admin 權限，等於每個 PR 都拿 admin token。務必拆兩個 IAM role。

陷阱 2：CI 並行跑同 stack

兩個 PR 同時 plan 還好（都讀），但兩個都觸發 apply 時 state lock 會拒絕一個——但 cancelled job 留下的 lock 可能殘留。對策：GitLab 用 resource_group、GitHub Actions 用 concurrency：

YAML · concurrency 設定 
concurrency:
  group: tofu-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: false   # 不取消正在跑的，避免 partial apply

陷阱 3：plan 檔過期才 apply

Plan 後等 review 一週，cloud 環境可能變了。Apply 該 plan 可能跟現實不符。對策：plan 加上 -detailed-exitcode，apply job 重新 plan 確認 No drift；或設定 plan artifact 短 retention（7 天）。

陷阱 4：CI 拿不到正確 OpenTofu 版本

專案用 1.11，CI 預裝 1.6——deprecated 行為差異會出問題。對策：CI 中 setup-opentofu 明確指定版本，加上 required_version 做雙保險。

陷阱 5：把 .tfplan 上傳成 public artifact

plan 檔含 state snapshot 與 sensitive 值。如果 PR 評論 / artifact 設成 public，等於洩漏。對策：retention 短、加 plan encryption（OpenTofu 1.7+）、PR comment 不貼 sensitive 段落。

陷阱 6：apply job 失敗後沒人發現

Apply 失敗後 cloud 處於奇怪狀態，但沒人盯 CI 通知。對策：apply 失敗自動發 Slack/PagerDuty alert、配 drift detection 自動偵測 state 與雲端不同步。

12. 本章重點與練習

重點回顧

  • IaC CI/CD 與 app CI/CD 本質不同：stateful、序列、partial apply、需 review plan
  • 平台選型：GitHub Actions/GitLab CI（彈性）vs TACOS（開箱即用）；OpenTofu 不支援 HCP Terraform
  • 標準模式：PR-driven、plan as artifact、two-stage with manual gate、least-privilege
  • GitHub Actions 標準模板：fmt → validate → plan → upload artifact → PR comment → manual approve → apply
  • GitLab CI 用 resource_group 序列化、內建 GitLab managed terraform state
  • Atlantis：自架 OSS，PR comment 指令觸發 plan/apply，支援 OpenTofu
  • TACOS（Spacelift / env0 / Scalr）：付費 SaaS，提供 drift detection / policy / stack dependency
  • Monorepo：path-based filtering（matrix job）或用 TACOS 內建的 project_root 機制
  • 安全鐵則：OIDC 短期憑證、Plan-Read 與 Apply-Write 兩個 role、state/plan 加密
  • Policy as Code：Conftest / Checkov / OPA / tfsec，plan 階段擋掉違規變更
  • Concurrency 控制：避免兩個 apply 同時跑（GitHub concurrency、GitLab resource_group）
⚡ 動手實作 · Hands-on Lab 21

建立完整 IaC CI/CD pipeline

  1. 練習 A · 本地 wrapper：寫一個 bash script ci.sh 模擬 CI 流程：fmt-check → validate → plan → 等使用者確認 → apply。把它跑一遍以建立心智模型
  2. 練習 B · GitHub Actions：建立 GitHub repo，加入第 4 節的 workflow YAML；設定 GitHub Environments 「production」啟用 manual approval
  3. 練習 C · OIDC 設定：建立 AWS IAM role 信任 GitHub Actions OIDC，配兩個 role：TofuPlanRole（read-only） 與 TofuApplyRole（write）
  4. 練習 D · Plugin cache：在 workflow 加 actions/cache，跑兩次 init 確認第二次明顯加速
  5. 練習 E · Concurrency 控制：在 workflow 加 concurrency 區塊；同時推兩個 PR 看後者是否被 queue
  6. 練習 F · Conftest policy：寫一個 Rego policy 禁止「沒加 Environment tag 的 EC2」；在 CI 中加 conftest 步驟，故意違反看 fail 訊息
  7. 挑戰題 1 · Monorepo matrix：建立 envs/dev、envs/staging、envs/prod 三目錄，用 dorny/paths-filter 動態偵測；只改 envs/dev 的檔案時 CI 只跑 dev plan
  8. 挑戰題 2 · Atlantis 試裝：用 docker-compose 起一個本地 Atlantis，用 ngrok 暴露讓 GitHub webhook 可達，建立一個 PR 看 atlantis plan 自動跑
  9. 挑戰題 3 · Drift detection：寫一個排程 GitHub Actions（cron: '0 6 * * *'）每天跑 tofu plan -refresh-only，有 drift 就發 Slack 通知
