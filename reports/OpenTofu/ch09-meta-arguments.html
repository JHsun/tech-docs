1. 什麼是 Meta-Argument

Meta-argument 是 OpenTofu 自己定義（不是 provider 定義）的特殊 argument，所有 resource、data、module 都能用。它們不直接設定資源屬性，而是控制「OpenTofu 如何管理這個 block」。

Meta-Argument 用途 適用 block
count產生 N 個編號實例resource、module、data
for_each依 map / set 產生命名實例resource、module、data
enabled（1.11+）條件性建立 0 或 1 個resource、module（在 lifecycle 內）
provider指定使用哪個 provider 設定resource、data
depends_on顯式宣告依賴resource、module、data、output
lifecycle客製生命週期行為resource、data、module、ephemeral
provisioner建立後執行命令（不推薦）resource

為什麼叫 meta

「Meta」意指「關於 argument 的 argument」。一般 argument 設定資源是什麼（AMI、CIDR、port 等，由 provider 定義），meta-argument 設定OpenTofu 如何處理它（要建幾份、何時重建、依賴什麼）。Meta-argument 在 plan / apply 之前就被處理，許多無法引用「未知值」（unknown value）。

2. count：產生 N 個編號實例

count 接受一個整數，OpenTofu 會建立 0 .. count-1 個編號實例。

HCL · count 基本 
resource "aws_instance" "web" {
  count = 3   # 建立 web[0]、web[1]、web[2]

  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"

  tags = {
    Name = "web-${count.index}"   # web-0、web-1、web-2
  }
}

count.index：當前實例的索引

在 count 為非零的 block 內，可使用 count.index（從 0 開始）讓每個實例的設定不同：

HCL · 用 count.index 區分實例 
resource "aws_subnet" "private" {
  count = length(var.availability_zones)

  vpc_id            = aws_vpc.main.id
  availability_zone = var.availability_zones[count.index]
  cidr_block        = cidrsubnet(aws_vpc.main.cidr_block, 4, count.index)

  tags = {
    Name = "private-${var.availability_zones[count.index]}"
  }
}

引用 count 出來的實例

引用形式意義
aws_instance.web[0]第 0 個實例
aws_instance.web[*]所有實例（splat 形式，產 list）
aws_instance.web[*].id所有實例的 id 組成 list
length(aws_instance.web)實例總數

count = 0：不建立任何實例

HCL · 用 count 條件化 
# 舊式條件化（OpenTofu 1.11 之前的標準做法）
resource "aws_eip" "nat" {
  count = var.use_nat ? 1 : 0
  domain = "vpc"
}

# 引用要用 [0]，且要先檢查存在
output "nat_ip" {
  value = length(aws_eip.nat) > 0 ? aws_eip.nat[0].public_ip : null
}

count 的限制

  • count 值在 plan 階段必須已知。不能引用「apply 後才知」的 resource 屬性
  • 無法用 sensitive 變數作為 count（會 leak 資訊）
  • 不能與 for_each 同時使用（兩者互斥）

3. for_each：產生命名實例

for_each 接受 set(string) 或 map，產生命名實例（key 是字串，不是數字索引）。

HCL · for_each 用 map 
variable "users" {
  type = map(object({
    role  = string
    email = string
  }))

  default = {
    alice = { role = "admin",  email = "alice@example.com" }
    bob   = { role = "viewer", email = "bob@example.com" }
  }
}

resource "aws_iam_user" "team" {
  for_each = var.users

  name = each.key                # "alice"、"bob"
  path = "/team/${each.value.role}/"

  tags = {
    Email = each.value.email
  }
}

each.key 與 each.value

輸入型別each.keyeach.value
map(T)map 的 keymap 的 value
set(string)該字串該字串（與 key 相同）

用 set 配 for_each

HCL · for_each 用 set 
variable "names" {
  type    = list(string)
  default = ["web", "api", "db"]
}

resource "aws_iam_user" "team" {
  for_each = toset(var.names)   # list 必須先轉 set

  name = each.key
  # each.key == each.value（set 的特性）
}

引用 for_each 出來的實例

引用形式意義
aws_iam_user.team["alice"]key 為 "alice" 的實例
aws_iam_user.team["alice"].arn該實例的 ARN
values(aws_iam_user.team)所有實例的 list（順序依 key 字典序）
keys(aws_iam_user.team)所有 key 的 list
values(aws_iam_user.team)[*].arn用 splat 取所有 ARN

for_each 的限制

  • 輸入只能是 set(string) 或 map，不能是 list（list 用 toset 轉）
  • key 不可為 sensitive（會出現在 resource address 中）
  • key 不可在 plan 階段未知（與 count 同樣限制）
  • 不能與 count 同時使用

實務的關鍵差異：刪除某個實例會發生什麼

這是最容易踩坑也是最重要的差異：

操作用 count用 for_each
刪除中間第一個 後面所有實例都被重建（索引位移） 只有刪除的實例被銷毀
新增一個 新增到末尾，安全 用新 key 新增，安全
重新排序輸入 所有實例可能重建 不影響（key 是身分）
HCL · count 的位移問題 
variable "users" {
  type    = list(string)
  default = ["alice", "bob", "charlie"]
}

resource "aws_iam_user" "team" {
  count = length(var.users)
  name  = var.users[count.index]
}

# 如果改成 default = ["bob", "charlie"]：
# - team[0]: alice → bob   （原 team[0] 改名 = destroy + create）
# - team[1]: bob   → charlie （改名）
# - team[2]: charlie → 刪除
# → 三個動作 = 服務中斷風險

經驗法則

能用 for_each 就用 for_each。count 只在「實例完全一樣，差異只在索引」（例如「3 個一模一樣的 NAT gateway」）才用。如果你的 list 元素有「身分意義」（user 名稱、AZ 名稱、tenant 名稱），絕對改用 for_each。

5. enabled（OpenTofu 1.11+）

OpenTofu 1.11 推出的全新 meta-argument，專為「條件性建立 0 或 1 個」而生。它放在 lifecycle 內（避開與 provider argument 命名衝突）。

新舊對比：解決 count = ? 1 : 0 的痛點

HCL · ❌ 舊式（仍可用，但繁瑣） 
resource "aws_eip" "nat" {
  count  = var.use_nat ? 1 : 0
  domain = "vpc"
}

# 引用要用 [0]，且要先檢查存在
output "nat_ip" {
  value = length(aws_eip.nat) > 0 ? aws_eip.nat[0].public_ip : null
}
HCL · ✅ OpenTofu 1.11+ 新式 
resource "aws_eip" "nat" {
  domain = "vpc"

  lifecycle {
    enabled = var.use_nat
  }
}

# 直接引用，無需 [0]
# 當 enabled = false 時，aws_eip.nat 為 null
output "nat_ip" {
  value = aws_eip.nat != null ? aws_eip.nat.public_ip : null
}

# 或用 try() 更簡潔
output "nat_ip_v2" {
  value = try(aws_eip.nat.public_ip, null)
}

enabled 的優點

面向count = ? 1 : 0enabled
引用語法需 [0] 索引直接 aws_eip.nat
停用時的值空 list []null
語意清晰度「0 個或 1 個實例」「啟用 / 停用」（更貼近意圖）
與其他 meta 衝突不能同時用 count 與 for_each不能同時用 enabled 與 count、for_each
適用 module是是（同樣放在 lifecycle 內）

實戰：feature flag 模式

HCL · feature flag 配 enabled 
variable "features" {
  type = object({
    waf              = bool
    shield           = bool
    enhanced_logging = bool
    backup           = bool
  })

  default = {
    waf              = true
    shield           = false   # $3000/月，prod 才開
    enhanced_logging = true
    backup           = true
  }
}

resource "aws_wafv2_web_acl" "main" {
  name  = "myapp-waf"
  scope = "REGIONAL"

  lifecycle {
    enabled = var.features.waf
  }

  default_action { allow {} }
  visibility_config {
    cloudwatch_metrics_enabled = true
    metric_name                = "myapp-waf"
    sampled_requests_enabled   = true
  }
}

resource "aws_shield_protection" "main" {
  name         = "myapp-shield"
  resource_arn = aws_lb.main.arn

  lifecycle {
    enabled = var.features.shield
  }
}

resource "aws_backup_plan" "daily" {
  name = "myapp-backup"

  lifecycle {
    enabled = var.features.backup
  }

  rule {
    rule_name         = "daily"
    target_vault_name = aws_backup_vault.main.name
    schedule          = "cron(0 2 * * ? *)"
  }
}

module 也能用 enabled

HCL · module 條件化 
module "monitoring" {
  source = "./modules/monitoring"

  alert_email = var.alert_email

  lifecycle {
    enabled = var.environment == "prod"
  }
}

從 count 自動遷移

當你把現有的 count = var.x ? 1 : 0 改成 lifecycle.enabled = var.x，OpenTofu 會自動處理 state 移動，把 aws_eip.nat[0] 移到 aws_eip.nat，無需 moved block。這是 1.11 設計上很貼心的細節。

向下相容注意

enabled 只在 OpenTofu 1.11+ 可用。如果你的 module 想同時支援 Terraform 與舊版 OpenTofu 使用者，仍要用傳統的 count = ? 1 : 0。新專案無此包袱，建議直接採用 enabled。

6. provider：選擇 provider 設定

當你同一個 provider 配多種設定（例如多 region、多 account），用 provider meta-argument 指定 resource 該用哪個。

定義多個 provider 設定（用 alias）

HCL · 多 region provider 
# 預設 provider（無 alias）
provider "aws" {
  region = "us-east-1"
}

# 加上 alias 區分
provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

provider "aws" {
  alias  = "frankfurt"
  region = "eu-central-1"
}

用 provider meta-argument 指定

HCL · 指定 provider 
# 用預設 provider（us-east-1）
resource "aws_s3_bucket" "primary" {
  bucket = "my-app-primary"
}

# 用 tokyo
resource "aws_s3_bucket" "tokyo_replica" {
  provider = aws.tokyo
  bucket   = "my-app-tokyo-replica"
}

# 用 frankfurt
resource "aws_s3_bucket" "frankfurt_replica" {
  provider = aws.frankfurt
  bucket   = "my-app-frankfurt-replica"
}

# data source 也支援
data "aws_caller_identity" "tokyo" {
  provider = aws.tokyo
}

傳遞給 module

呼叫 module 時用 providers（注意是複數）map：

HCL · module 多 provider 
module "tokyo_infra" {
  source = "./modules/regional"

  providers = {
    aws         = aws.tokyo          # 把 alias 對應給 module 內的預設 aws
    aws.replica = aws.frankfurt      # module 內的 aws.replica 對應給 frankfurt
  }

  region_name = "tokyo"
}

7. lifecycle 全解

lifecycle 是 resource 內最重要的 meta-argument 區塊，控制 OpenTofu 如何處理生命週期事件。第 6 章已介紹過四大設定，這裡完整總結 + 補充細節。

設定型別用途OpenTofu 版本
create_before_destroybool需 replace 時，先建後拆所有版本
prevent_destroybool禁止 destroy所有版本
ignore_changeslist / all忽略指定屬性的 drift所有版本
replace_triggered_bylist of refs跨資源觸發 replace1.x
precondition / postconditionnested block條件檢查1.x
enabledbool條件性建立1.11+

create_before_destroy 連鎖效應

當 resource A create_before_destroy = true，所有依賴 A 的資源也會自動套用此行為。OpenTofu 會在 state 中記錄這個自動套用，且不允許下游覆寫為 false（會造成 graph 循環）。

HCL · 連鎖效應範例 
resource "aws_security_group" "web" {
  name_prefix = "web-"   # 用 prefix 確保新舊可同時存在

  lifecycle {
    create_before_destroy = true
  }
}

# 下面的 instance 會自動繼承 create_before_destroy 行為
resource "aws_instance" "web" {
  vpc_security_group_ids = [aws_security_group.web.id]
  # ...
}

ignore_changes 的進階用法

HCL · ignore_changes 進階 
resource "aws_autoscaling_group" "web" {
  min_size         = 2
  max_size         = 10
  desired_capacity = 2

  lifecycle {
    ignore_changes = [
      desired_capacity,           # 整個屬性
      tag,                        # 整個 tag block
      tags["LastDeployedAt"],     # 只忽略某個 tag key
      vpc_zone_identifier,        # 整個 list
    ]
  }
}

# 完全託管：建立後不再追蹤任何變動
resource "aws_iam_user" "external_managed" {
  name = "managed-by-someone-else"

  lifecycle {
    ignore_changes = all
  }
}

replace_triggered_by：跨資源 replace

HCL · 用 terraform_data 觸發 replace 
resource "terraform_data" "config_version" {
  input = var.config_version
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = "t3.micro"

  lifecycle {
    # 當 config_version 變動，強制重建本資源
    replace_triggered_by = [terraform_data.config_version]
  }
}

8. depends_on：顯式依賴

當 OpenTofu 從表達式中無法推斷出依賴關係，但你知道 A 必須在 B 之後建立時，用 depends_on。這是最後手段——能用隱式依賴就用隱式。

正確使用場景

HCL · 合理的 depends_on 用法 
resource "aws_iam_role" "lambda" {
  name = "lambda-exec"
  # ...
}

resource "aws_iam_role_policy_attachment" "lambda_logs" {
  role       = aws_iam_role.lambda.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_lambda_function" "app" {
  function_name = "my-app"
  role          = aws_iam_role.lambda.arn
  # ...

  # Lambda 設定中沒引用 attachment，但 attachment 必須先存在
  # 否則 Lambda 啟動後第一次寫 log 會失敗
  depends_on = [aws_iam_role_policy_attachment.lambda_logs]
}

module 的 depends_on

整個 module 也能加 depends_on：

HCL · module depends_on 
module "app" {
  source = "./modules/app"

  vpc_id = module.network.vpc_id

  # 確保 IAM module 的所有資源建立完才開始 app
  depends_on = [module.iam]
}

depends_on 的限制

  • 列表內只能放靜態資源 reference（不能是 expression、不能引用 var）
  • 會讓 plan / apply 時間變長（更多 graph 邊）
  • 失去屬性級依賴精度：OpenTofu 只知道「整個資源要等」，看不出哪個屬性產生連動

depends_on 的反信號

如果你發現自己頻繁用 depends_on，多半代表設計可改進。試問自己：能不能把那個被等的東西的某個屬性引用過來？例如「資料庫建好才能跑 init 腳本」這類，把 init 腳本依賴 DB endpoint 屬性，就會自動建立隱式依賴。

9. provisioner（不建議使用）

provisioner 讓你在資源建立後執行命令（local 或遠端 SSH）。OpenTofu 官方文件明確標示為 last resort——除非真的沒辦法，否則別用。

HCL · provisioner 範例（僅示範） 
resource "aws_instance" "web" {
  # ...

  # local-exec：在跑 OpenTofu 的機器上執行
  provisioner "local-exec" {
    command = "echo Instance created: ${self.id}"
  }

  # remote-exec：透過 SSH 在遠端執行
  provisioner "remote-exec" {
    inline = [
      "sudo apt update",
      "sudo apt install -y nginx",
    ]

    connection {
      type        = "ssh"
      user        = "ubuntu"
      private_key = file("~/.ssh/id_rsa")
      host        = self.public_ip
    }
  }
}

為什麼不要用 provisioner

  • 失敗時 resource 變成 tainted，下次 apply 會 destroy + create
  • 運作不穩定（網路、SSH key、防火牆問題很多）
  • 不冪等：重跑可能造成意外結果
  • 本質上違反 IaC 哲學：宣告式工具混入命令式步驟

應改用的替代方案

需求建議方案
裝套件、改設定用 cloud-init / user_data，或 Ansible / Chef 等專業工具
建立後跑一次性 API call用對應 provider 的 resource（例如 AWS provider 多半有對應 resource）
把資源資訊寫到本地檔用 local_file resource
等待某個服務 ready用 health check resource，或在 provider 層用 timeouts

10. 常見陷阱與最佳實踐

陷阱 1：count.index 在 splat 中無法用

HCL 
resource "aws_instance" "web" {
  count = 3
  # ...
}

# ❌ 不能在 splat 引用 count.index
# value = aws_instance.web[*].count.index

# ✅ 用 for 表達式
output "indices" {
  value = [for i, _ in aws_instance.web : i]
}

陷阱 2：把可變排序的 list 給 count

若用 count = length(var.users)，使用者只是改了 list 的順序，所有實例都會位移重建。改用 for_each = toset(var.users)。

陷阱 3：for_each 用了 unknown key

HCL 
# ❌ key 在 plan 階段未知（resource id 是 apply 後才知）
resource "aws_iam_user_policy_attachment" "p" {
  for_each = toset(aws_iam_user.users[*].id)   # ERROR
}

# ✅ 用 user 名稱（已知）作為 key
resource "aws_iam_user_policy_attachment" "p" {
  for_each = aws_iam_user.users
  user     = each.value.name
}

陷阱 4：lifecycle 內參考其他屬性

HCL 
resource "aws_db_instance" "main" {
  # ...

  lifecycle {
    # ❌ ignore_changes 必須是靜態屬性路徑，不能用 var
    # ignore_changes = [var.ignored_field]

    # ✅ 必須直接寫
    ignore_changes = [tags, password]
  }
}

陷阱 5：count = 0 與 enabled = false 行為差異

停用方式表達式型別引用
count = 0空 list []aws_x.y 是空 list；要 length() > 0
enabled = falsenullaws_x.y 是 null；用 != null 或 try()

最佳實踐速查

場景選用
3 個一樣的 NAT gatewaycount = 3
每個 user 不同 rolefor_each = var.users
選擇性建立 WAFOpenTofu 1.11+ lifecycle { enabled = var.use_waf }
跨 region 建立 replicaprovider = aws.tokyo
Production 防誤刪 DBlifecycle { prevent_destroy = true }
ASG 與 autoscaler 並存ignore_changes = [desired_capacity]
無停機更新 LBcreate_before_destroy = true + name_prefix
config 變了強制重建 EC2terraform_data + replace_triggered_by
等 IAM policy 才建 Lambdadepends_on（最後手段）
機器內裝套件用 user_data / Ansible，別用 provisioner

11. 本章重點與練習

重點回顧

  • Meta-argument 是 OpenTofu 自己定義的特殊 argument，控制「OpenTofu 如何管理 block」，不是設定資源屬性
  • count 產生編號實例（[0]、[1]...），對位移敏感，適合「實例完全相同」的場景
  • for_each 產生命名實例（["alice"]、["bob"]...），對位移免疫，是大多數情境的首選
  • OpenTofu 1.11+ 推出 lifecycle.enabled，取代舊式的 count = ? 1 : 0，引用語法更清晰
  • 多 region / 多 account 場景用 provider = aws.alias；module 用 providers = {...} map
  • lifecycle 五大設定：create_before_destroy、prevent_destroy、ignore_changes、replace_triggered_by、enabled（1.11+）
  • depends_on 是最後手段，能用隱式依賴就用隱式
  • provisioner 官方標示為 last resort，違反宣告式 IaC 哲學，應用 cloud-init / Ansible 等替代
