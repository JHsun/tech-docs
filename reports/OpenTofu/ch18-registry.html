2. OpenTofu Public Registry

OpenTofu Public Registry 在 search.opentofu.org，是社群維護的 Terraform Registry mirror，提供 4,000+ provider 與 18,000+ module。

歷史與技術背景

  • OpenTofu 從 fork 之初就需要獨立 registry（HashiCorp 的 registry 不一定服務 OpenTofu）
  • 採用靜態 GitHub repo架構，所有 metadata 在 github.com/opentofu/registry
  • 每個 provider/module 對應 repo 中的 JSON 檔，自動從上游 GitHub repo 抓 release 資訊
  • 不是中央服務，沒有單點故障；provider 仍從原 repo 的 GitHub Release 下載

使用 Public Registry

HCL · 預設就能用 
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"   # 完整：registry.opentofu.org/hashicorp/aws
      version = "~> 5.0"
    }
  }
}

# Module 同樣
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.5"
}

命名空間與 source address 結構

Plaintext · source 完整結構 
# Provider source
<HOSTNAME>/<NAMESPACE>/<NAME>
registry.opentofu.org/hashicorp/aws

# Module source
<HOSTNAME>/<NAMESPACE>/<NAME>/<PROVIDER>
registry.opentofu.org/terraform-aws-modules/vpc/aws

# Module 簡寫（省略 hostname）
terraform-aws-modules/vpc/aws

# Hostname 預設為 registry.opentofu.org

提交自家 module / provider

Public Registry 採 PR 方式收錄。流程：

  1. 準備好你的 module/provider GitHub repo（命名規則：terraform-<PROVIDER>-<NAME> 對 module，terraform-provider-<NAME> 對 provider）
  2. 每個版本打語意化 git tag（如 v1.0.0），透過 GitHub Release 發佈
  3. 到 opentofu/registry 提 PR 加入對應的 JSON 檔
  4. PR 通過後自動同步到 search.opentofu.org

3. 挑選優質 module 與 provider

Registry 上 module 良莠不齊，挑選需有方法。

挑 module 的標準

面向具體檢查
維護活躍度過去 6 個月有 commit、issue 有人回應
版本歷史遵循 SemVer、有清晰 CHANGELOG
下載量registry 顯示的下載統計
文件品質README 含完整 inputs/outputs、至少一個 example
測試覆蓋有 tofu test 或 examples 目錄
授權Apache 2.0 / MPL / MIT 之類允許商用
Issue 處理open issues 數合理、有人 triage
變數設計合理預設值、不過度暴露屬性

2026 年值得認識的 namespace

Namespace提供定位
terraform-aws-modules/*AWS 全家桶（VPC、RDS、EKS、IAM、Lambda、ALB 等）事實標準
terraform-google-modules/*GCP 全家桶Google 官方維護
Azure/*Azure 模組覆蓋率較分散
cloudposse/*含命名規範與 tag 標準觀點性強，需先了解其哲學
Anton Babenkoterraform-aws-modules 主要維護者個人作品

挑 provider 的標準

  • HashiCorp 命名空間（hashicorp/*）通常是「官方」，但仍要看授權——HashiCorp 自家某些 provider 已轉 BUSL，OpenTofu 社群會 fork 後改授權
  • 第三方 provider 看 GitHub stars、issue 處理、release 頻率
  • 注意 BUSL 授權的 provider：Vault、Consul、Sentinel 等 HashiCorp 商業 provider 不能在 OpenTofu 自由使用，社群有 OpenBao（Vault fork）等替代品

4. Private Registry 五大方案對照

企業常需要 private module / provider registry，理由包括合規、自家 module 不公開、air-gapped 環境等。

方案架設成本維護成本moduleprovider2026 評價
OCI Registry（GHCR / ECR / Harbor） 很低（多半已有） 很低 ✅ 1.10+ ✅ 1.10+ 🟢 2026 首選
Spacelift / env0 / Scalr（TACOS） 低（SaaS） 中（要付費） ✅ ✅ 🟡 已用 TACOS 才划算
GitLab Module Registry 低（內建） 低 ✅ 🟡 限定 🟡 已用 GitLab 才方便
JFrog Artifactory 高 高 ✅ ✅ 🟡 大企業常用
自架（Citizen / Mass-Driver） 中 高 ✅ ✅ 🔴 需專人維護

為什麼 OCI Registry 是 2026 年首選

① 多數團隊已有 container registry（GHCR、ECR、ACR、Harbor）；② 相同 registry 統一存放 container image、provider、module、甚至 state；③ 標準 OCI 認證（docker login）即可；④ tag 與 digest 兩種不可變版本鎖定；⑤ 無需專人維護。除非你有特殊原因（已用 TACOS、特定合規），新團隊就直接用 OCI。

5. Module / Provider Registry Protocol

OpenTofu 認識兩個 HTTP 協定，任何實作這些協定的服務都能當 registry。

Service Discovery：起點

一切從 https://<hostname>/.well-known/terraform.json 開始：

JSON · /.well-known/terraform.json 
{
  "modules.v1": "/api/v1/modules/",
  "providers.v1": "/api/v1/providers/",
  "login.v1": {
    "client": "opentofu",
    "grant_types": ["authz_code"],
    "authz": "/oauth/authorization",
    "token": "/oauth/token",
    "ports": [10000, 10010]
  }
}

Module Registry Protocol（核心 endpoints）

Endpoint用途
GET /:namespace/:name/:provider/versions列出可用版本
GET /:namespace/:name/:provider/:version/download取得下載 URL（302 redirect 到 archive 位置）

Provider Registry Protocol

Endpoint用途
GET /:namespace/:type/versions列出可用版本（含支援 platform）
GET /:namespace/:type/:version/download/:os/:arch取得特定平台的下載資訊（含 sha256 與 GPG 簽章）

實作 minimal registry：靜態檔案

因為協定是純 GET，用 nginx + 靜態 JSON 檔就能架。OpenTofu Public Registry 自己也是這樣（GitHub repo 當 storage）。

OpenTofu 對 OCI 的要求

  • OCI Distribution 規範 v1.1+（支援非 container artifact）
  • Module package：artifactType 必須是 application/vnd.opentofu.modulepkg
  • Provider package：artifactType 必須是 application/vnd.opentofu.providerpkg
  • 單一 layer，mediaType 為 archive/zip
  • 每個 platform 一份 artifact（1.2.0_linux_amd64、1.2.0_darwin_arm64...）

支援的 OCI Registry

Registry適合對象
GitHub Container Registry（GHCR）已用 GitHub 的團隊（首選）
AWS ECRAWS 為主
Azure Container Registry（ACR）Azure 為主
Google Artifact RegistryGCP 為主
Harbor自架、合規環境
JFrog Artifactory已有 Artifactory
Docker Hub個人 / 開源

7. 用 OCI 發佈 module 完整流程

Step 1：準備 module repo

Plaintext · 標準 module 結構 
terraform-aws-vpc/
├── README.md
├── main.tf
├── variables.tf
├── outputs.tf
├── versions.tf
├── examples/
│   └── basic/
│       └── main.tf
└── .github/
    └── workflows/
        └── publish-oci.yml

Step 2：手動發佈（理解原理）

Bash · oras 推送 module 
# 1. 安裝 oras CLI
brew install oras   # macOS
# 或 curl 下載 release tarball

# 2. 進到 module 目錄
cd terraform-aws-vpc/

# 3. 打包成 zip（注意：要排除 .git、.terraform 等）
VERSION=1.2.0
zip -r ../vpc-${VERSION}.zip . \
  -x ".git/*" ".terraform/*" "*.tfstate*" ".github/*"

# 4. 登入 OCI registry
echo "$GITHUB_TOKEN" | oras login ghcr.io -u myuser --password-stdin

# 5. 推送
oras push \
  --artifact-type=application/vnd.opentofu.modulepkg \
  ghcr.io/myorg/terraform-aws-vpc:${VERSION} \
  ../vpc-${VERSION}.zip:archive/zip

# 6. 加上多個 tag（可變、固定、digest）
oras tag ghcr.io/myorg/terraform-aws-vpc:${VERSION} 1.2
oras tag ghcr.io/myorg/terraform-aws-vpc:${VERSION} 1
oras tag ghcr.io/myorg/terraform-aws-vpc:${VERSION} latest

Step 3：自動化（GitHub Actions）

YAML · .github/workflows/publish-oci.yml 
name: Publish Module to OCI

on:
  push:
    tags:
      - 'v*.*.*'

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write    # 推送到 GHCR 必要

    steps:
      - uses: actions/checkout@v4

      - name: Install oras
        run: |
          curl -LO https://github.com/oras-project/oras/releases/download/v1.3.0/oras_1.3.0_linux_amd64.tar.gz
          tar -xzf oras_1.3.0_linux_amd64.tar.gz
          sudo mv oras /usr/local/bin/

      - name: Extract version
        id: ver
        run: echo "version=${GITHUB_REF_NAME#v}" >> $GITHUB_OUTPUT

      - name: Login to GHCR
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | oras login ghcr.io \
            --username ${{ github.actor }} --password-stdin

      - name: Package module
        run: |
          zip -r module.zip . -x ".git/*" ".github/*" "*.tfstate*" ".terraform/*"

      - name: Push to OCI
        run: |
          REPO_LOWER=$(echo "${{ github.repository }}" | tr '[:upper:]' '[:lower:]')
          oras push \
            --artifact-type=application/vnd.opentofu.modulepkg \
            ghcr.io/${REPO_LOWER}:${{ steps.ver.outputs.version }} \
            module.zip:archive/zip

          # Tag latest
          oras tag ghcr.io/${REPO_LOWER}:${{ steps.ver.outputs.version }} latest

Step 4：使用者引用

HCL · 引用 OCI module 
module "vpc" {
  source = "oci://ghcr.io/myorg/terraform-aws-vpc?tag=1.2.0"
  # 或用 digest（最不可變）
  # source = "oci://ghcr.io/myorg/terraform-aws-vpc?digest=sha256:abc123..."

  cidr_block = "10.0.0.0/16"
  # ...
}

使用者認證

OpenTofu 會自動讀 docker / podman 的認證檔（~/.docker/config.json）。最簡單：先 docker login ghcr.io 即可。

8. 用 OCI 發佈 provider 完整流程

Provider 比 module 複雜，因為要支援多平台 binary。

Step 1：建立每個平台的 binary

Makefile · 跨平台 build 
PROVIDER_NAME := myprovider
NAMESPACE := mycompany
VERSION := 1.0.0

PLATFORMS := linux_amd64 linux_arm64 darwin_amd64 darwin_arm64 windows_amd64

.PHONY: build package

build:
	@for PLATFORM in $(PLATFORMS); do \
		OS=$${PLATFORM%_*}; ARCH=$${PLATFORM##*_}; \
		echo "Building $$OS/$$ARCH..."; \
		GOOS=$$OS GOARCH=$$ARCH go build \
			-o dist/terraform-provider-$(PROVIDER_NAME)_v$(VERSION)_$$OS_$$ARCH \
			.; \
	done

package: build
	@cd dist && for PLATFORM in $(PLATFORMS); do \
		OS=$${PLATFORM%_*}; ARCH=$${PLATFORM##*_}; \
		zip terraform-provider-$(PROVIDER_NAME)_$(VERSION)_$$OS_$$ARCH.zip \
			terraform-provider-$(PROVIDER_NAME)_v$(VERSION)_$$OS_$$ARCH; \
	done

Step 2：推送各平台 zip 為獨立 OCI artifact

Bash · 推送 provider 
VERSION=1.0.0
REPO=ghcr.io/myorg/myprovider

# 每個平台單獨推送
for PLATFORM in linux_amd64 linux_arm64 darwin_amd64 darwin_arm64 windows_amd64; do
  ZIP="dist/terraform-provider-myprovider_${VERSION}_${PLATFORM}.zip"

  oras push \
    --artifact-type=application/vnd.opentofu.providerpkg \
    "${REPO}:${VERSION}_${PLATFORM}" \
    "${ZIP}:archive/zip"
done

Step 3：使用者設定 oci_mirror

HCL · ~/.tofurc 
provider_installation {
  oci_mirror {
    repository_template = "ghcr.io/myorg/${type}"
    include             = ["registry.example.com/mycompany/*"]
  }
  direct {
    exclude = ["registry.example.com/mycompany/*"]
  }
}
HCL · 設定中引用 
terraform {
  required_providers {
    myprovider = {
      source  = "registry.example.com/mycompany/myprovider"
      version = "~> 1.0"
    }
  }
}

使用者跑 tofu init 時：① OpenTofu 看到 source 匹配 oci_mirror 的 include；② 從 ghcr.io/myorg/myprovider 找對應版本＋當前平台的 artifact；③ 拉下解壓使用。

9. OCI Mirror：把 public registry 映射到內部

常見場景：air-gapped 環境、公司網路無法連 public registry，但又要用 hashicorp/aws 等公開 provider。解法：把 public registry 的 provider「鏡像」到內部 OCI。

架構圖

(public)"]
    CI["公司 CI Job
定期同步"]
    OCI["ghcr.io/myorg/
opentofu-providers"]
    Dev["開發者

    Pub -->|每週拉取最新| CI
    CI -->|oras push| OCI
    Dev -.設定 oci_mirror.-> OCI

    style OCI fill:#dcfce7,stroke:#16a34a
    style Dev fill:#cffafe,stroke:#0891b2

用 tofu providers mirror 同步

Bash · 從 public 拉到本地 
# 1. 在能連 public 的地方準備一個 stack（含所有 required_providers）
mkdir -p mirror-bootstrap && cd mirror-bootstrap
cat > main.tf <<'EOF'
terraform {
  required_providers {
    aws    = { source = "hashicorp/aws",    version = "~> 5.0" }
    random = { source = "hashicorp/random", version = "~> 3.0" }
    local  = { source = "hashicorp/local",  version = "~> 2.5" }
  }
}
EOF

# 2. init 取得最新版本
tofu init -backend=false

# 3. 用 providers mirror 把所有 provider 下載成本地 mirror 結構
tofu providers mirror \
  -platform=linux_amd64 \
  -platform=linux_arm64 \
  -platform=darwin_arm64 \
  /tmp/providers-mirror/

# 4. 推送到內部 OCI
for PROVIDER_DIR in /tmp/providers-mirror/registry.opentofu.org/*/*/; do
  NAMESPACE=$(basename "$(dirname "$PROVIDER_DIR")")
  TYPE=$(basename "$PROVIDER_DIR")

  for VERSION_DIR in "$PROVIDER_DIR"*/; do
    VERSION=$(basename "$VERSION_DIR")

    for ZIP in "$VERSION_DIR"*.zip; do
      PLATFORM=$(basename "$ZIP" .zip | sed "s/.*_${VERSION}_//")

      oras push \
        --artifact-type=application/vnd.opentofu.providerpkg \
        "ghcr.io/myorg/${NAMESPACE}-${TYPE}:${VERSION}_${PLATFORM}" \
        "${ZIP}:archive/zip"
    done
  done
done

定期自動更新（GitHub Actions）

name: Sync Provider Mirror

on:
  schedule:
    - cron: '0 3 * * 1'   # 每週一 03:00 UTC
  workflow_dispatch:        # 也允許手動觸發

      packages: write

          sudo mv oras /usr/local/bin/

      - name: Login GHCR

          echo "${{ secrets.GITHUB_TOKEN }}" | oras login ghcr.io \

          tofu init -backend=false

            -platform=linux_amd64 \
            -platform=linux_arm64 \
            -platform=darwin_arm64 \

      - name: Push to OCI
        run: ./scripts/push-mirror-to-oci.sh /tmp/mirror/ ghcr.io/${{ github.repository_owner }}

10. 簽章與供應鏈安全

OpenTofu 對 provider 的驗證機制

機制用途
SHA256 hash驗證下載的 zip 沒被竄改（記錄在 lock 檔）
GPG 簽章驗證 SHASUMS 檔的真實性（從 trusted key 簽）
.terraform.lock.hcl多平台 hash 鎖定，跨團隊一致
Cosign（OCI）OCI artifact 的簽章驗證（手動串接）

用 cosign 簽章 OCI artifact（進階）

Bash · cosign 簽章流程 
# 1. 安裝 cosign
brew install cosign

# 2. 用 keyless（OIDC）簽章——CI 環境推薦
cosign sign --yes ghcr.io/myorg/terraform-aws-vpc:1.2.0

# 3. 驗證
cosign verify ghcr.io/myorg/terraform-aws-vpc:1.2.0 \
  --certificate-identity-regexp ".*@myorg.com" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

cosign 整合目前是「外掛」

截至 OpenTofu 1.11，cosign 簽章驗證不是 OpenTofu 內建，要自己在 CI 中驗證後才呼叫 OpenTofu。但這是供應鏈安全的明顯方向，未來版本可能原生支援。

Lock 檔 hash 驗證

OpenTofu 自動驗證 .terraform.lock.hcl 中的 hash：

Bash · CI 嚴格 lock 
# 嚴格模式：不允許 lock 檔被修改
tofu init -lockfile=readonly

# 寫多平台 hash（在 dev 機器執行一次，commit 進 git）
tofu providers lock \
  -platform=linux_amd64 \
  -platform=linux_arm64 \
  -platform=darwin_arm64 \
  -platform=darwin_amd64 \
  -platform=windows_amd64

11. 版本管理與升級策略

OCI tag 策略

OCI 不像 npm 有 SemVer 內建支援；要靠你自己的 tag 規範。建議模式：

Tag意義使用場景
1.2.0不可變的具體版本production 鎖定
1.2指向最新 1.2.x容許 patch 自動升級
1指向最新 1.x.x容許 minor 自動升級（謹慎）
latest當前最新dev / sandbox
sha256:abc...digest（最不可變）合規 / 審計需求

使用者引用策略

HCL · 不同環境的 source 鎖定 
# 開發環境：用 floating tag 容許自動升級
module "vpc_dev" {
  source = "oci://ghcr.io/myorg/aws-vpc?tag=1.2"   # 1.2.x 自動升
}

# Production：鎖定 patch
module "vpc_prod" {
  source = "oci://ghcr.io/myorg/aws-vpc?tag=1.2.0"
}

# 合規 / 高安全：鎖定 digest
module "vpc_secure" {
  source = "oci://ghcr.io/myorg/aws-vpc?digest=sha256:abc123..."
}

升級流程

  1. 查看 module / provider 的 CHANGELOG
  2. 在 dev 環境改版本字串
  3. 跑 tofu init -upgrade
  4. 跑 tofu plan 觀察變更
  5. 升級 lock 檔，跑 tofu providers lock -platform=... 補多平台 hash
  6. commit lock 檔變更，PR review
  7. merge 後依序部署 dev → staging → prod

12. 常見陷阱與最佳實踐

陷阱 1：OCI artifactType 寫錯

Bash · 常見錯誤 
# ❌ 用 docker push 而非 oras push（OCI image type 不對）
docker push ghcr.io/myorg/module:1.0.0

# ❌ artifactType 拼錯
oras push --artifact-type=opentofu-module ...

# ✅ 正確的兩個 artifactType
oras push --artifact-type=application/vnd.opentofu.modulepkg ...    # module
oras push --artifact-type=application/vnd.opentofu.providerpkg ...  # provider

陷阱 2：zip 內含多餘目錄包裹

Bash 
# ❌ 解壓後是 my-module/main.tf
zip -r m.zip my-module/

# ✅ 解壓後直接看到 main.tf
cd my-module && zip -r ../m.zip .

陷阱 3：忘了多平台 lock

第 11 章已詳述。本機 init 只記錄當前平台 hash，CI 跑 init 會新增 hash 觸發 lock 變更。解法：用 tofu providers lock -platform=... 一次寫好。

陷阱 4：使用 floating tag 後生產被動更新

用 tag=1.2 在 production 是危險的——上游發 1.2.5 含 bug，下次 init 自動拉到後可能炸掉。Production 永遠用具體版本或 digest。

陷阱 5：OCI registry 的 repository 名稱大小寫

GHCR 要求 repository 名稱全小寫。github.repository 是混合大小寫，要轉小寫：

Bash · GitHub Actions 
REPO_LOWER=$(echo "${{ github.repository }}" | tr '[:upper:]' '[:lower:]')
oras push ghcr.io/${REPO_LOWER}:1.0.0 ...

陷阱 6：Public registry 的 BUSL provider

HashiCorp 把部分 provider 從 MPL 轉成 BUSL（Vault、Consul、Nomad、Boundary、Sentinel 等）。OpenTofu 公開 registry 仍可解析這些 source，但授權限制商用。OpenTofu 社群通常 fork 改授權（如 OpenBao 取代 Vault）。

陷阱 7：artifact 沒設 visibility 為 public（GHCR）

GHCR 預設新建 package 是 private，使用者拉取會 401。要去 GitHub package settings 改成 public，或統一用 PAT 認證。

13. 本章重點與練習（含 Part 3 總回顧）

本章重點回顧

  • Registry 是 OpenTofu 的套件分發機制，分發 module 與 provider 兩類
  • OpenTofu Public Registry 是 community-maintained，採靜態 GitHub 架構
  • 挑 module 看活躍度、文件、SemVer、授權；常用 namespace：terraform-aws-modules、terraform-google-modules、cloudposse
  • Private Registry 五大方案：OCI（首選）、TACOS（Spacelift / env0 / Scalr）、GitLab、Artifactory、自架
  • OpenTofu 認識兩個 protocol：Module Registry Protocol 與 Provider Registry Protocol（純 HTTP GET，可用靜態檔架）
  • OCI Registry（OpenTofu 1.10+）三角色：發佈 module、發佈 provider、當 provider mirror
  • OCI artifactType：module 用 application/vnd.opentofu.modulepkg、provider 用 application/vnd.opentofu.providerpkg
  • OCI 發佈 module：oras push --artifact-type=... <repo>:<tag> <zip>:archive/zip
  • OCI 發佈 provider：每平台一個 artifact，用 ${VERSION}_${OS}_${ARCH} tag 命名
  • OCI Mirror：用 tofu providers mirror + oras push 把 public registry 同步到內部，air-gapped 必備
  • 供應鏈安全：lock 檔 hash + cosign 簽章（外掛）+ 嚴格 -lockfile=readonly
  • Tag 策略：production 用具體版本或 digest，dev 可用 floating tag
