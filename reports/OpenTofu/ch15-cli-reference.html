2. tofu init：初始化

tofu init 是所有專案開工的第一步。它做四件事：

  1. 下載並安裝 required providers 到 .terraform/providers/
  2. 下載 modules 到 .terraform/modules/
  3. 初始化 backend（連到 remote state）
  4. 建立或更新 .terraform.lock.hcl

常用 flag

Flag用途
-upgrade升級 provider 與 module 到 version 約束內的最新
-backend=false跳過 backend 初始化（CI 中只想 validate 時用）
-backend-config=KEY=VAL動態傳入 backend 設定（partial config）
-backend-config=path指向 backend config 檔（如 prod.s3.tfbackend）
-reconfigure強制重新初始化 backend（不問是否遷移 state）
-migrate-state遷移既有 state 到新 backend
-get=false不下載 module（只裝 provider）
-lockfile=readonly嚴格使用 lock 檔，不更新（CI/CD 推薦）
-input=false不互動式詢問（CI/CD 必加）
-no-color關閉顏色（CI log 友善）
Bash · init 實戰範例 
# 第一次初始化
tofu init

# 升級 provider 到最新可用版本
tofu init -upgrade

# 多環境用 backend config 檔
tofu init -backend-config=envs/prod.s3.tfbackend

# CI/CD 標準
tofu init -input=false -no-color -lockfile=readonly

# 從另一個 backend 遷移過來
tofu init -migrate-state

# 在不需要連 backend 的情境（例如只跑 fmt + validate）
tofu init -backend=false

3. tofu validate 與 tofu fmt

tofu validate：靜態檢查

檢查語法、型別、引用合法性。不連雲端、不讀 state。

Bash 
# 基本用法（需先 init，但可用 -backend=false 跳過 backend）
tofu init -backend=false
tofu validate

# CI 機器可讀格式
tofu validate -json

# 不顯示顏色
tofu validate -no-color

tofu fmt：標準格式化

類似 gofmt，把所有 .tf 檔調整成標準縮排、對齊、註解風格。

Flag用途
(無)修改檔案
-recursive遞迴處理子目錄
-check只檢查不修改（CI 用，找出未格式化檔會 exit 1）
-diff顯示前後差異
-list=false不列出檔名
-write=false不寫回（搭配 -diff 預覽）
Bash 
# 格式化當前目錄
tofu fmt

# 遞迴處理整個專案
tofu fmt -recursive

# CI 檢查（沒格式化的話 exit 1）
tofu fmt -check -recursive -diff

4. tofu plan：預覽變更

tofu plan 比對設定（HCL）、state、雲端實際狀態，列出將要執行的動作。它不會改任何東西。

三種 planning mode

Mode啟用 flag用途
Normal（預設）(無)「設定 vs 現實」的差異
Destroy-destroy計畫銷毀所有受管資源
Refresh-only-refresh-only只更新 state 不改設定（drift 處理）

常用 flag

Flag用途
-out=FILE把 plan 存成檔案（之後可給 apply 使用）
-detailed-exitcode詳細退出碼（0=無變更、1=錯誤、2=有變更）
-var=KEY=VAL傳入單一變數值
-var-file=FILE從 .tfvars 檔載入
-target=ADDR只處理特定 resource（其他保持不動）
-exclude=ADDR排除特定 resource（OpenTofu 1.9+）
-target-file / -exclude-file從檔案讀多個 target / exclude
-replace=ADDR強制 replace 該資源
-refresh=false不 refresh state（加速但風險高）
-parallelism=N並行 API call 數（預設 10）
-lock-timeout=DUR取 lock 的等待時間（預設 0s 不等）
-show-sensitive顯示 sensitive 值（debug 用，請小心）
-deprecation=module:none關閉 deprecation 警告
Bash · plan 實戰範例 
# 基本
tofu plan

# 存成檔案，給 apply 直接執行（CI/CD 標準做法）
tofu plan -out=tfplan.bin

# 多環境
tofu plan -var-file=envs/prod.tfvars

# CI 中判斷是否有變更
tofu plan -detailed-exitcode -out=tfplan.bin
# echo $?
# 0 = 無變更 → CI 可直接結束
# 2 = 有變更 → CI 進入 approval 流程

# 只處理某個 module
tofu plan -target=module.network

# 強制重建
tofu plan -replace=aws_instance.web

# 排除某資源
tofu plan -exclude=aws_db_instance.legacy

# Drift detection
tofu plan -refresh-only

-target / -exclude 是緊急工具

官方明確說：-target 與 -exclude 是「例外狀況工具」，用於救火、處理錯誤、暫時繞過 OpenTofu 限制。正常工作流程不該用——它會讓 plan 變得非全面，可能漏掉相依資源的變更。常規部署該整個 stack 一起 plan / apply。

5. tofu apply：執行變更

tofu apply 執行 plan 中的動作。兩種使用方式：

Bash · 兩種 apply 模式 
# 模式 1：互動式（適合本地開發）
tofu apply
# OpenTofu 會跑 plan 然後問 yes/no

# 模式 2：應用已存的 plan 檔（CI/CD 標準）
tofu plan -out=tfplan.bin
# ... 走 review / approval ...
tofu apply tfplan.bin
# 不問就直接執行

常用 flag

Flag用途
-auto-approve跳過互動 yes/no 確認（CI 用）
-input=false不互動式詢問
-parallelism=N並行度
-lock=false不取 lock（危險！僅用於 backend 異常）
-lock-timeout=DUR取 lock 的等待時間
-refresh-only只更新 state 不改雲端
-destroy等同 tofu destroy
-target / -exclude同 plan 的限制
-jsonJSON 格式輸出（CI 解析用）
Bash · CI/CD 標準 apply 流程 
# Stage 1：plan
tofu init -input=false -lockfile=readonly
tofu plan -out=tfplan.bin -input=false -no-color

# Stage 2：human approval（GitHub Environments、Manual gate）

# Stage 3：apply
tofu apply -input=false -no-color tfplan.bin

refresh-only：drift 處理

Bash · 處理外部變更 
# 有人在 console 改了什麼，先看差異
tofu plan -refresh-only

# 接受外部變更為新 baseline（只更新 state，不改雲端）
tofu apply -refresh-only

# 接受並讓雲端回到設定的樣子（一般 apply）
tofu apply

6. tofu destroy：銷毀資源

銷毀當前 workspace 中所有受管資源。本質上等同 tofu apply -destroy。

Bash 
# 互動確認
tofu destroy

# 自動同意（CI 環境清理用）
tofu destroy -auto-approve

# 只銷毀某個 module
tofu destroy -target=module.dev_environment

# 同 plan 的 var-file 機制
tofu destroy -var-file=envs/dev.tfvars -auto-approve

destroy 的核武器警語

① destroy -auto-approve 在 production stack 是不可逆操作；② 配合 lifecycle { prevent_destroy = true } 為關鍵資源（DB、KMS key）加防呆；③ CI/CD 中 destroy job 必須有人工 approval gate；④ 永遠先 tofu plan -destroy 確認影響範圍。

7. tofu state 系列：state 操作

第 12 章已詳述。這裡列出指令速查：

指令用途會修改 state？
tofu state list列出所有 resource address否
tofu state show ADDR顯示單一資源屬性否
tofu state pull把遠端 state 印到 stdout否
tofu state push FILE把本地檔案推到遠端 state是（高危）
tofu state mv SRC DST重新命名 / 跨 state 移動是
tofu state rm ADDR從 state 移除（雲端保留）是
tofu state replace-provider OLD NEW更換 provider source 位址是
Bash · state 實戰 
# 列出資源
tofu state list

# 篩選：只看 module.network 內的
tofu state list 'module.network.*'

# 看詳情
tofu state show 'aws_instance.web[0]'

# 備份（多檔備份策略）
tofu state pull > backup-$(date +%Y%m%d-%H%M).json

# 重新命名（建議用 moved block 取代）
tofu state mv aws_instance.web aws_instance.web_primary

# 移除某資源（不銷毀雲端）
tofu state rm aws_iam_user.legacy

# 替換 provider source（從 hashicorp 換成 opentofu 命名空間）
tofu state replace-provider \
  registry.terraform.io/hashicorp/aws \
  registry.opentofu.org/hashicorp/aws

優先用宣告式 block

第 13 章已詳述：moved / removed / import block 應優先於 tofu state mv/rm 與 tofu import 指令。命令式操作不可版控、不能 plan 預覽、容易出錯。

8. tofu import：匯入既有資源

把雲端既有資源納入 OpenTofu 管理。OpenTofu 1.5+ 後優先用 import block（第 13 章），但傳統指令仍存在：

Bash · 傳統 import 指令 
# 先在 .tf 寫好對應的 resource block
# resource "aws_s3_bucket" "legacy" {
#   bucket = "my-existing-bucket"
# }

# 再 import
tofu import aws_s3_bucket.legacy my-existing-bucket

# 帶 module 路徑
tofu import 'module.network.aws_vpc.main' vpc-0abc123

# 帶 count / for_each
tofu import 'aws_instance.web[0]' i-0abc123
tofu import 'aws_instance.shard["primary"]' i-0def456

import block 自動產生 config（推薦）

Bash · 配 plan -generate-config-out 
# 1. 寫 import block（不寫 resource block）
cat > imports.tf <<'EOF'
import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket"
}
EOF

# 2. 自動產生 resource block
tofu plan -generate-config-out=generated.tf

# 3. 整理 generated.tf 後 apply

12. tofu test：測試框架

OpenTofu 1.6+ 內建 testing framework，讓你能自動化測試你的 module。

基本結構

Plaintext · 專案結構 
my-module/
├── main.tf
├── variables.tf
├── outputs.tf
└── tests/
    ├── basic.tftest.hcl
    └── advanced.tftest.hcl
# 或副檔名 .tofutest.hcl 也可

第一個測試檔

HCL · main.tf 
variable "filename" {
  type    = string
  default = "test.txt"
}

resource "local_file" "test" {
  filename = var.filename
  content  = "Hello world!"
}

output "filename" {
  value = local_file.test.filename
}
HCL · tests/basic.tftest.hcl 
# 測試 1：預設值
run "default" {
  assert {
    condition     = local_file.test.filename == "test.txt"
    error_message = "Default filename should be test.txt"
  }

  assert {
    condition     = local_file.test.content == "Hello world!"
    error_message = "Content should be 'Hello world!'"
  }
}

# 測試 2：自訂變數
run "custom_filename" {
  variables {
    filename = "/tmp/custom.txt"
  }

  assert {
    condition     = local_file.test.filename == "/tmp/custom.txt"
    error_message = "Filename variable not respected"
  }
}

# 測試 3：只 plan 不 apply（適合驗證設定，不真的建資源）
run "plan_only" {
  command = plan

  variables {
    filename = "/tmp/will-not-create.txt"
  }

  assert {
    condition     = local_file.test.content == "Hello world!"
    error_message = "Plan-time check failed"
  }
}

執行測試

Bash 
# 執行所有測試（test/ 目錄與根目錄的 .tftest.hcl）
tofu test

# 只跑特定檔案
tofu test -filter=tests/basic.tftest.hcl

# 詳細輸出
tofu test -verbose

# CI 友善
tofu test -no-color -junit-xml=test-results.xml

進階：mock provider

不想真的呼叫 AWS API？OpenTofu 1.7+ 支援 mock provider：

HCL · 用 mock_provider 
mock_provider "aws" {}

run "test_without_real_aws" {
  command = plan

  assert {
    condition     = aws_instance.web.instance_type == "t3.micro"
    error_message = "Wrong instance type"
  }
}

13. 其他指令

tofu force-unlock：強制解鎖

Bash 
# 從錯誤訊息找 lock ID
# Error: state is locked
# Lock ID: abc123-def456-...

tofu force-unlock abc123-def456-...

# 跳過確認（很危險！）
tofu force-unlock -force abc123-def456-...

force-unlock 前必須確認

務必先在團隊頻道廣播「我要 force-unlock 這個 stack」，等 5 分鐘確認沒人在 apply 才執行。同時 unlock 與另一個 apply 並行會讓 state 不可預測。

tofu login / logout：private registry 登入

Bash 
# 登入 private registry（會開瀏覽器 OAuth flow）
tofu login registry.example.com

# 登入 OpenTofu 自家的 cloud（如有）
tofu login

# 登出
tofu logout registry.example.com

token 會存在 ~/.terraform.d/credentials.tfrc.json。

tofu taint / untaint（已 deprecated）

傳統指令，現在改用 tofu apply -replace=ADDR：

Bash 
# ❌ 舊式
# tofu taint aws_instance.web
# tofu apply

# ✅ 新式
tofu apply -replace=aws_instance.web

# 或 plan 階段就指定
tofu plan -replace=aws_instance.web -out=tfplan.bin
tofu apply tfplan.bin

tofu get：只下載 module

Bash 
# 只下載/更新 module，不碰 provider 與 backend
tofu get
tofu get -update

實務上很少用——tofu init 會自動處理。

14. 全域 flag 與環境變數

全域 flag（放在子指令前）

Flag用途
-chdir=DIR切換工作目錄（取代 cd）
-help顯示說明
-version顯示版本
Bash · -chdir 範例 
# 從專案 root 跑某個 stack 的 plan，不需要 cd
tofu -chdir=envs/prod plan

# 注意：-chdir 在子指令前，不是後

常用環境變數

環境變數用途
TF_VAR_xxx傳變數值（變數名 xxx）
TF_LOG=DEBUG開啟 debug log（TRACE/DEBUG/INFO/WARN/ERROR）
TF_LOG_PATH=filelog 寫到檔案
TF_INPUT=0禁用互動詢問（同 -input=false）
TF_IN_AUTOMATION=true標示為 CI 環境（影響輸出格式）
TF_PLUGIN_CACHE_DIRprovider plugin cache 目錄
TF_DATA_DIR替代 .terraform/ 目錄位置
TF_TOKEN_HOSTNAMEprivate registry token（hostname 用底線）
TF_CLI_ARGS_xxx對 xxx 子指令自動加 flag（如 TF_CLI_ARGS_apply="-auto-approve"）
Bash · debug log 實戰 
# 看 OpenTofu 與 provider 之間發生什麼
TF_LOG=DEBUG tofu apply

# 寫到檔案分析
TF_LOG=TRACE TF_LOG_PATH=tofu-trace.log tofu plan
# trace log 通常很長，dump 後 grep 你關心的部分

CI/CD 模板

Bash · 標準 CI/CD pipeline 
#!/bin/bash
set -euo pipefail

# 環境
export TF_INPUT=0
export TF_IN_AUTOMATION=true
export TF_PLUGIN_CACHE_DIR=$HOME/.terraform.d/plugin-cache

# 1. Init（用 lockfile readonly）
tofu init -lockfile=readonly -no-color

# 2. Format check
tofu fmt -check -recursive -no-color

# 3. Validate
tofu validate -no-color

# 4. Plan
tofu plan -out=tfplan.bin -no-color -detailed-exitcode || EXIT=$?

# 退出碼判斷
case ${EXIT:-0} in
  0) echo "No changes"; exit 0 ;;
  1) echo "Plan failed"; exit 1 ;;
  2) echo "Changes pending approval" ;;
esac

# 5. Apply（生產環境前面有 manual gate）
tofu apply -no-color tfplan.bin

16. 本章重點與練習

重點回顧

  • OpenTofu CLI 約 25 個指令，分四大類：核心工作流程、state 操作、輸出與診斷、其他
  • tofu init 做四件事：裝 provider、抓 module、初始化 backend、建/更新 lock 檔
  • tofu plan 三種 mode：normal、destroy、refresh-only；-detailed-exitcode 在 CI 判斷有無變更
  • tofu apply 兩種模式：互動式 vs 套用已存 plan 檔（CI/CD 推薦後者）
  • -target 與 -exclude 是例外狀況工具，正常工作流程不該用
  • State 操作優先用宣告式 block（moved / removed / import），命令式 tofu state 是備援
  • tofu console 是除錯 expression 最快的方法
  • tofu test 是內建測試框架，配 mock_provider 可離線測試
  • 已 deprecated：tofu refresh（用 apply -refresh-only）、tofu taint（用 apply -replace）
  • 環境變數：TF_VAR_xxx、TF_LOG、TF_PLUGIN_CACHE_DIR、TF_TOKEN_HOSTNAME、TF_IN_AUTOMATION
  • 全域 flag -chdir=DIR 取代 cd，CI 中很實用
⚡ 動手實作 · Hands-on Lab 15

CLI 全方位演練

  1. 建立 cli-lab/，含 main.tf（用 local + random provider 建幾個檔案）、variables.tf、outputs.tf
  2. 練習 A · 工作流程基本功：
    • 跑 tofu init 並觀察 .terraform/ 目錄結構
    • 跑 tofu fmt -check -diff
    • 跑 tofu validate
    • 跑 tofu plan -out=tfplan.bin
    • 跑 tofu apply tfplan.bin
  3. 練習 B · plan 各種 flag：分別試 -detailed-exitcode、-target、-replace、-refresh-only，觀察輸出差異
  4. 練習 C · state 操作：
    • tofu state list 列資源
    • tofu state show ADDR 看詳情
    • tofu state pull > backup.json 備份
    • 用 tofu state mv 改名某個 resource
  5. 練習 D · console：進 tofu console，試算各種表達式（內建函式、變數引用、resource 屬性）
  6. 練習 E · output：試 tofu output、tofu output -json、tofu output -raw NAME
  7. 練習 F · graph：跑 tofu graph > g.dot，如有裝 graphviz 用 dot -Tpng g.dot > g.png 渲染
  8. 挑戰題 1 · 寫測試：建立 tests/basic.tftest.hcl，寫 2 個 run block 驗證資源屬性，跑 tofu test
  9. 挑戰題 2 · CI/CD pipeline：寫一個 bash script 模擬 CI 流程：fmt check → validate → plan -detailed-exitcode → 依退出碼決定是否 apply
  10. 挑戰題 3 · debug log：用 TF_LOG=DEBUG TF_LOG_PATH=trace.log tofu plan，看 trace log 找到 provider 與 OpenTofu Core 之間的 gRPC 通訊
  11. 用 tofu destroy -auto-approve 清掉資源
