1. 為什麼要懂 internals

使用 OpenTofu 不需要懂內部機制——但遇到怪問題時，內部知識是診斷的關鍵。常見會用到 internals 知識的情境：

  • plan 顯示意外的 destroy + create，要追是哪個依賴觸發
  • provider crash，要看 gRPC trace log 找原因
  • 大型 stack apply 很慢，要分析 graph 並行度與 bottleneck
  • state lock 異常，要懂 lock 機制才能正確處理
  • 寫 custom provider 或 backend
  • 面試中被問「OpenTofu 是怎麼做到不破壞的更新」

官方對 internals 的態度

OpenTofu 官方文件明確說：「Knowledge of OpenTofu internals is not required to use OpenTofu」。這章的目標是讓你「不需要 magic」也能信任工具，但不是必修。如果你只是要快速上手，可以跳過本章，直接進 Part 5 實戰。

3. 一次 tofu apply 的完整旅程

以下是 tofu apply 從你按下 Enter 到雲端資源建立完成的完整流程：

sequenceDiagram
    participant U as 使用者
    participant CLI as CLI Layer
    participant BE as Backend
    participant Ctx as tofu.Context
    participant GB as Graph Builder
    participant GW as Graph Walker
    participant PR as Provider (gRPC)
    participant Cloud as Cloud API
    participant SM as State Manager

    U->>CLI: tofu apply
    CLI->>BE: 解析 backend config
    BE->>SM: 連接 state storage
    SM->>BE: 取得 state lock
    BE->>Ctx: 建立 Context（含 config + state）

    Ctx->>GB: BuildPlanGraph()
    GB-->>Ctx: 回傳 graph (DAG)

    Ctx->>GW: Walk graph
    GW->>PR: ConfigureProvider()
    PR-->>GW: ok

    loop 每個 resource node（並行）
        GW->>PR: ReadResource() / PlanResourceChange()
        PR->>Cloud: 查詢當前狀態
        Cloud-->>PR: 當前屬性
        PR-->>GW: 計畫變更
    end

    GW-->>Ctx: Plan 完成
    Ctx-->>CLI: 顯示變更

    U->>CLI: yes（確認）

    Ctx->>GW: Walk apply graph
    loop 每個變更（並行 +依依賴順序）
        GW->>PR: ApplyResourceChange()
        PR->>Cloud: 建立/修改/刪除
        Cloud-->>PR: 新狀態
        PR-->>GW: 結果
        GW->>SM: 寫 state（增量）
    end

    GW-->>Ctx: Apply 完成
    Ctx->>SM: 釋放 lock
    SM-->>BE: 完成
    BE-->>CLI: 結果
    CLI-->>U: 顯示 outputs

關鍵階段

階段主要工作
① 解析讀 .tf 檔、解析 HCL、解析 backend
② 初始化連 backend、取 state lock、載入 state
③ Build Graph從 config + state 建出 dependency DAG
④ Refresh對所有資源呼叫 provider Read，同步當前狀態到 in-memory state
⑤ Plan遍歷 graph，每個 node 呼叫 PlanResourceChange，產生變更清單
⑥ Confirm（互動或 -auto-approve）顯示 plan 給使用者確認
⑦ Apply遍歷 apply graph，依順序與並行度執行變更
⑧ State 寫入每個資源變更立即寫 state（防中途失敗丟失進度）
⑨ 完成釋放 lock、印 outputs

HCL 與 expression 的延遲評估

OpenTofu 的設計哲學：能延遲評估的就延遲。原因是很多 expression 引用了「目前還不知道」的值（resource 屬性需要 apply 後才知道）。

  • Static evaluation：count、for_each、module source、backend 設定等需要在 graph build 階段就確定，OpenTofu 1.8+ 才放寬部分變數使用
  • Dynamic evaluation：resource 內 argument 引用 expression，在 graph 遍歷到該節點時才評估
  • HCL Body / Expression：未評估的部分仍以原始 HCL AST 形式保留，graph walker 視需要才呼叫 Decode()

5. Resource Dependency Graph 詳解

這是 OpenTofu 的核心。所有 plan / apply 行為都基於這張 graph。

Graph 是什麼

OpenTofu 的 graph 是有向無環圖（DAG）：

  • Vertex（節點）：每個節點代表一個 OpenTofu 物件（resource、data、provider、variable、output、module call、本地計算節點）
  • Edge（邊）：邊代表「必須在...之後」的順序關係
  • Acyclic（無環）：建好後若有環會直接 error（你的設定有循環依賴）

節點類型

類型對應
Resource Node每個 resource block 一個
Data Node每個 data block 一個
Provider Configuration Node每個 provider 設定（含 alias）一個
Variable Node每個 input variable 一個
Local Node每個 local value 一個
Output Node每個 output 一個
Module Call Node每個 module 呼叫
Resource Meta Nodecount / for_each 的展開（每個 instance 一個）
Orphan Nodestate 有但設定中已移除的資源（要 destroy）
Root Node合成的「最後一個」節點，所有未被引用的 sink 都連到它

邊的建立規則

  1. Implicit edges（隱式邊）：A 的 argument 引用 B 的屬性 → A 依賴 B
  2. Explicit edges（顯式邊）：A 的 depends_on 列出 B → A 依賴 B
  3. Provider edges：所有 resource 依賴它的 provider 設定節點
  4. Module edges：跨 module 邊由 module 介面（input/output）轉接
  5. create_before_destroy 連鎖：開了該設定的 resource，所有依賴它的 resource 自動繼承

不同操作有不同 graph

每個操作（plan / plan-destroy / plan-refresh-only / apply）都有專屬的 graph builder：

Graph 類型用途來源
Plan Graph產生 plan從 config + state 建
Plan-Refresh-Only Graph只更新 state，不計畫變更同上但不評估 diff
Plan-Destroy Graph計畫銷毀（destroy）從 state 建（反向順序）
Apply Graph執行 plan從 plan 建（不從 config）

6. Graph 遍歷與並行控制

Topological Walk

OpenTofu 用拓撲排序遍歷 graph：

  1. 找出所有入度為 0 的節點（沒有任何依賴）
  2. 並行處理它們
  3. 每完成一個，把它從 graph 「移除」，可能讓其他節點變成入度 0
  4. 重複直到所有節點處理完
flowchart TD
    V["aws_vpc"]
    SG["aws_security_group"]
    S1["aws_subnet[0]"]
    S2["aws_subnet[1]"]
    S3["aws_subnet[2]"]
    EC1["aws_instance[0]"]
    EC2["aws_instance[1]"]
    DB["aws_db_instance"]

    V --> SG
    V --> S1
    V --> S2
    V --> S3

    S1 --> EC1
    S2 --> EC2
    S1 --> DB
    SG --> EC1
    SG --> EC2
    SG --> DB

    style V fill:#cffafe,stroke:#0891b2

上圖會分這幾批執行：

  1. Batch 1：aws_vpc 一個
  2. Batch 2：aws_security_group、aws_subnet[0,1,2] 並行 4 個
  3. Batch 3：aws_instance[0,1]、aws_db_instance 並行 3 個

並行度控制：-parallelism

OpenTofu 用 semaphore 限制同時處理的節點數，預設 10：

Bash 
# 預設 10
tofu apply

# 提高並行（注意 cloud API 限制）
tofu apply -parallelism=20

# 降低並行（debug 或避免 rate limit）
tofu apply -parallelism=1

什麼時候調 parallelism

① 大型 stack（>100 資源）有時提高到 20-30 可加速；② 觸發 cloud API rate limit 時降低；③ debug provider 競態條件時設成 1 讓事件序列化；④ 多數情況下用預設 10 就好，provider 自己會做 retry/backoff。

節點處理失敗的影響

當某節點處理失敗：

  • 該節點及其所有下游（依賴它的）節點都不會執行
  • 但已經並行執行的其他分支會繼續完成
  • 整個操作以非零 exit code 結束
  • State 紀錄已成功的部分（不會 rollback）——這是partial apply

7. Plan 階段內部

Plan 的核心問題

Plan 要回答：「從目前狀態到目標狀態，需要做什麼？」這需要三方比較：

來源內容
Config使用者描述的「目標狀態」
StateOpenTofu 記得的「上次狀態」
Cloud (refresh)雲端的「實際當前狀態」

Plan 的三步驟

flowchart TD
    S1["Step 1: Refresh
對每個資源呼叫 ReadResource
同步雲端實際狀態到 in-memory state"]
    S2["Step 2: Diff Calculation
對每個資源呼叫 PlanResourceChange
provider 比較 config vs prior state
回傳 proposed new state"]
    S3["Step 3: Action Decision
OpenTofu 依 schema 決定 create/update/replace/no-op
含 ForceNew 屬性檢查"]

    S1 --> S2 --> S3

    style S2 fill:#cffafe,stroke:#0891b2

Provider 在 Plan 階段的角色

Provider 不是被動執行 OpenTofu 指令，它實際做 diff 計算：

  • OpenTofu Core 把 config、prior_state 透過 gRPC 傳給 provider
  • Provider 根據自己的 schema 計算「proposed_new_state」
  • Provider 還可加入computed attributes（雲端會產生的值，標為 unknown）
  • OpenTofu Core 收到結果後檢查 ForceNew、unknown 處理、決定最終動作

Plan 檔案內容

當你跑 tofu plan -out=tfplan.bin，這個檔案是 binary 格式，含：

  • 當前 state 的快照（含 sensitive 值，所以 plan 檔本身也是敏感檔！）
  • 變更清單（add / change / destroy / replace）
  • 使用的 provider 版本
  • 變數值
  • OpenTofu 1.7+ 可加密

tfplan.bin 是 sensitive 檔案

plan 檔含 state 完整快照與所有 sensitive 值。絕不能 commit 進 git，CI 上傳成 artifact 時要用短期 retention 並限制下載權限。OpenTofu 1.7+ 的 encryption block 也涵蓋 plan 檔。

8. Apply 階段內部

Apply 與 Plan 的差異

面向PlanApply
Graph 來源從 config + state 建從 plan 建
對 provider 的呼叫PlanResourceChangeApplyResourceChange
對 cloud 的影響無（唯讀）實際變更
State 寫入無每個變更立刻寫
失敗影響整個 plan 中止partial apply（state 保留已完成的）

Apply 的關鍵保證

  1. 順序保證：依依賴 DAG 順序執行
  2. 並行保證：無依賴關係的可並行（受 -parallelism 限制）
  3. State 增量寫入：每完成一個 resource 立刻寫 state，避免中途失敗丟進度
  4. Lock 持有：整個 apply 期間都持有 lock，防止其他人並行寫 state

Replace 的執行順序

Plaintext · 兩種 replace 模式 
# 預設：destroy + create
1. Destroy old aws_instance.web
2. Create new aws_instance.web

# 開了 create_before_destroy
1. Create new aws_instance.web (用新名稱或無衝突屬性)
2. Update 引用該資源的下游
3. Destroy old aws_instance.web

State 寫入策略

OpenTofu 對 state 寫入有三種模式：

模式行為場景
Local backend每變更立即 fsync 到本地檔local state
Remote 增量每變更上傳到 backend（網路成本）S3 / GCS 等
Remote batched批次累積後一次上傳（部分 backend）降低 API call

9. Provider Protocol：gRPC 通訊

OpenTofu Core 與每個 provider 是獨立進程，透過 gRPC 通訊。Provider 是被 OpenTofu Core 啟動的子進程。

Provider 啟動序列

sequenceDiagram
    participant Core as OpenTofu Core
    participant FS as 本機 FS
    participant Plugin as Provider Process

    Core->>FS: 找 .terraform/providers/.../terraform-provider-aws_v5.30.0
    Core->>Plugin: spawn binary
    Plugin->>Plugin: 啟動 gRPC server (loopback)
    Plugin->>Core: stdout 印 handshake JSON
{"protocol_version":6, "address":"127.0.0.1:12345"}
    Core->>Plugin: 透過該 port 連 gRPC

    Note over Core,Plugin: handshake 完成

    Core->>Plugin: GetProviderSchema()
    Plugin-->>Core: schema

    Core->>Plugin: ConfigureProvider(region=us-east-1, ...)
    Plugin->>Plugin: 初始化 AWS SDK client
    Plugin-->>Core: ok

    loop graph walk 期間
        Core->>Plugin: ReadResource / PlanResourceChange / ApplyResourceChange
        Plugin->>Plugin: 呼叫 cloud API
        Plugin-->>Core: 結果
    end

    Core->>Plugin: Stop
    Plugin->>Plugin: cleanup
    Plugin->>Core: exit

Protocol 版本

版本狀態說明
tfplugin5遺留OpenTofu 仍支援，舊 provider 用
tfplugin6主流多數新 provider 用，支援 nested types、ephemeral 等新特性

主要 RPC 方法

RPC用途

10. State Manager 與 Lock

State Manager 介面

OpenTofu 內部把 state 操作抽象成 statemgr package 的多個 interface：

Interface方法
statemgr.ReaderState() — 讀
statemgr.WriterWriteState() — 寫（in-memory）
statemgr.PersisterPersistState() — 持久化（上傳到 backend）
statemgr.RefresherRefreshState() — 從 backend 重新拉
statemgr.LockerLock / Unlock
statemgr.Full以上全部組合

State serial 與 lineage

每次 PersistState：

  1. 檢查 backend 上的 lineage 與本地是否一致
  2. 檢查本地 serial > backend 的 serial（防覆寫舊版）
  3. 遞增 serial，寫入 backend

Lock 機制細節

BackendLock 實作
S3（1.10+）conditional write 一個 .tflock 檔（用 If-None-Match）
S3（舊）DynamoDB PutItem with condition expression
azurermBlob Lease（60 秒，自動 renew）
gcsGCS object generation conditional write
postgresPostgreSQL advisory lock（pg_try_advisory_lock）
localOS file lock（flock 或 LockFileEx）
http由 server 端實作（POST/DELETE 對應 endpoint）

11. 用 internals 知識 debug

場景 1：plan 顯示意外的 destroy + create

追究流程：

  1. 看 plan 輸出找到關鍵字 forces replacement
  2. OpenTofu 會指出哪個屬性觸發了 ForceNew
  3. 用 tofu state show ADDR 看 state 中該屬性目前值
  4. 對比 config 中的值，找出差異原因
  5. 常見原因：data source 結果變了、變數預設值改了、provider 升級改了 schema

場景 2：apply 卡住不動

Bash · 診斷流程 
# 1. 開 trace log
TF_LOG=DEBUG TF_LOG_PATH=apply.log tofu apply

# 在另一個 terminal
tail -f apply.log | grep -E "ApplyResourceChange|ReadResource"

# 看是哪個資源在等
# 通常是雲端 API 慢（DB 建立要 5 分鐘）或 timeout 設太長

# 2. 如果是 lock 卡住
tofu force-unlock LOCK_ID   # 確認沒人在用後

場景 3：provider crash

Bash · 找 crash 原因 
# Provider crash 會留下 crash.log 在當前目錄
cat crash.log

# 或開 trace 重跑
TF_LOG=TRACE TF_LOG_PATH=trace.log tofu plan
grep -i "panic\|crash\|stack trace" trace.log

# 通常 crash 報告該寄到 provider 的 GitHub repo

場景 4：循環依賴

Bash · 視覺化 cycle

場景 5：apply 太慢

12. 本章重點與練習

重點回顧

  • OpenTofu 採五層架構：CLI / Backend / Core Engine / Configuration / Provider Plugin
  • Provider 是獨立進程，OpenTofu Core 啟動子進程後透過 gRPC（tfplugin5 / tfplugin6）通訊
  • 一次 apply 完整旅程：解析 → init backend → 取 lock → build graph → refresh → plan → confirm → apply → 寫 state → 釋放 lock
  • Resource Dependency Graph 是有向無環圖（DAG），所有操作都基於它
  • Edge 三種來源：implicit（屬性引用）、explicit（depends_on）、provider edges
  • 不同操作有不同 graph：plan / plan-destroy / plan-refresh-only / apply
  • Graph 用拓撲排序遍歷，semaphore 控制並行（預設 10，可用 -parallelism 調整）
  • Plan 三步驟：refresh → diff calculation（provider 做） → action decision
  • Apply 對 provider 呼叫 ApplyResourceChange，state 增量寫入避免中途失敗丟進度
  • Lock 機制依 backend 不同：S3 conditional write、DynamoDB conditional put、Azure Blob lease 等
  • Debug 用 TF_LOG=TRACE 看 gRPC 對話、用 tofu graph -draw-cycles 看循環、用 -parallelism 調整並行度
⚡ 動手實作 · Hands-on Lab 19

用 internals 知識深入觀察 OpenTofu

  1. 建立 internals-lab/，含多個有相互依賴的 local_file 資源（A、B、C、D，其中 B 依賴 A、C 依賴 A、D 依賴 B 與 C）
  2. 練習 A · 看 graph：跑 tofu graph -type=plan | dot -Tpng > plan.png（如有 graphviz），對比 apply graph 與 plan-destroy graph
  3. 練習 B · trace log 解析：跑 TF_LOG=TRACE TF_LOG_PATH=trace.log tofu plan，找出：
    • provider 啟動的 handshake
    • 每個 resource 的 PlanResourceChange 呼叫
    • config + prior state 在請求中的形式
  4. 練習 C · parallelism 觀察：用 4 個無相互依賴的 local_file 測試：
    • tofu apply -parallelism=1 觀察序列執行
    • tofu apply -parallelism=4 觀察並行
    • 從 trace log 找出時間戳對比
  5. 練習 D · 故意製造 cycle：寫兩個 resource 互相用 depends_on 形成循環，跑 tofu graph -draw-cycles 找出循環
  6. 練習 E · plan 檔解析：跑 tofu plan -out=tfplan.bin、tofu show -json tfplan.bin | jq，看 plan 檔的結構（resource_changes、prior_state、planned_values）
  7. 挑戰題 1 · 觀察 partial apply：故意讓某個 resource 失敗（例如寫一個會 error 的 path），跑 apply 後看 state，確認其他成功的資源仍被記錄
  8. 挑戰題 2 · provider 啟動原理：用 ps -ef | grep terraform-provider 在 apply 期間找到 spawned 的 provider 進程；查 lsof 看 gRPC 用的 port
  9. 挑戰題 3 · gRPC 細節：抓 trace log 中一次完整的 PlanResourceChange，把 input/output 的 protobuf message 解碼出來
