1. HCL 是什麼，為什麼是它

HCL（HashiCorp Configuration Language）是 HashiCorp 開發的一套設定描述語言。它的設計目標只有一個：讓人類讀寫設定既清楚又愉快，同時讓機器解析既穩定又準確。

OpenTofu 採用 HCL 作為設定語言的原生形式（native syntax），副檔名為 .tf 或 .tofu。OpenTofu 也支援與 JSON 語法等價的 .tf.json / .tofu.json，主要供程式自動產生設定檔時使用。

為什麼不用 YAML 或 JSON？

面向 YAML JSON HCL
人類可讀性 🟡 縮排敏感、空白會出錯 🔴 不利長設定、無註解 🟢 區塊清楚，視覺結構好
表達能力 🟡 純資料結構，無計算能力 🔴 純資料結構 🟢 內建表達式、函式、條件
引用其他值 🔴 需 anchor / alias 🔴 不支援 🟢 原生 aws_vpc.main.id
註解 🟢 # 🔴 不支援 🟢 #、//、/* */
機器可生成 🟢 🟢 🟡（但有 JSON 形式可選）

HCL 的核心設計理念

HCL 的精神是 declarative（宣告式） —— 你描述「最後要長什麼樣」，不描述「先做什麼再做什麼」。每個 block 就是一個物件描述，arguments 就是它的屬性，expressions 是屬性的值。

2. 三大基本元素：Block、Argument、Expression

整個 HCL 設定檔，骨子裡只由三種東西組成：

Block

Block 是容器，用大括號 { } 包起來。每個 block 描述一個物件（一個 resource、一個 variable、一個 module 呼叫等）。

Argument

Argument（也常稱 attribute）是 block 內的鍵 = 值，描述該物件的屬性。

Expression

Expression 是放在等號右邊的值。可以是字面值（literal）、變數參照、函式呼叫、條件判斷、for 迴圈等。第 8 章會專門講 expressions。

三者協同的最簡範例

HCL · 三大元素同框 
resource "local_file" "greeting" {     # 這整個是 block
  filename = "/tmp/hello.txt"          # filename 是 argument，"/tmp/hello.txt" 是 expression
  content  = "Hello, ${var.name}!"     # 右邊也是 expression（含字串內插）
}

3. Block 解剖：Type、Label、Body

每個 block 由三個部分組成：type、labels、body。

resource Type  "local_file" "greeting" Labels (×2) {
  filename = "/tmp/hello.txt"  Argument
  content  = var.name             Expression
} Body 結束

Block Type

第一個關鍵字，例如 resource、variable、output、module、data、terraform、provider、locals。每種 type 由 OpenTofu 或 provider 定義其用途與規則。

Block Labels

跟在 type 後面的字串標籤。不同 type 要求的 label 數量不同：

Block Type Label 數量 範例
resource2（type + name）resource "aws_instance" "web" { }
data2（type + name）data "aws_ami" "ubuntu" { }
variable1（name）variable "region" { }
output1（name）output "url" { }
module1（name）module "vpc" { }
provider1（type）provider "aws" { }
terraform0terraform { }
locals0locals { }
ephemeral（1.10+）2（type + name）ephemeral "random_password" "db" { }

Block Body 與巢狀 block

Body 內可以放 arguments，也可以放巢狀 block（nested blocks）。巢狀 block 通常用來表達 sub-structure。

HCL · 巢狀 block 範例 
resource "aws_instance" "web" {
  ami           = "ami-0abc..."
  instance_type = "t3.micro"

  # 巢狀 block：lifecycle 設定
  lifecycle {
    create_before_destroy = true
    prevent_destroy       = false
    ignore_changes        = [tags]
  }

  # 巢狀 block：root_block_device 設定
  root_block_device {
    volume_size = 30
    volume_type = "gp3"
    encrypted   = true
  }

  # 巢狀 block：網路介面（可有多個）
  network_interface {
    network_interface_id = aws_network_interface.web.id
    device_index         = 0
  }
}

attribute 與 argument 的辭彙差異

HCL 規範書稱「鍵 = 值」這個結構為 attribute。OpenTofu 文件改稱 argument，是為了避免與「resource 屬性（如 id、arn）」混淆——後者也叫 attribute，但是讀的不是寫的。日常溝通兩種說法都通用。

4. 識別字（Identifiers）規則

argument 名稱、block label、變數名、resource 名等等，全部都是識別字。識別字必須遵守以下規則：

  • 由字母、數字、底線 _、連字號 -組成
  • 第一個字元不能是數字（避免與數值字面值混淆）
  • 支援 Unicode 識別字語法（可用非 ASCII 字元，但慣例上仍建議 ASCII）
  • 區分大小寫（my_var 與 My_Var 是不同識別字）

合法 vs 不合法

HCL · 識別字範例 
# ✅ 合法
variable "region" { }
variable "instance_type" { }
variable "primary-vpc" { }      # 連字號合法
variable "_internal" { }         # 底線開頭合法

# ❌ 不合法
variable "1st_region" { }        # 開頭是數字
variable "my var" { }            # 含空白
variable "my.var" { }            # 含 dot

慣例：用 snake_case

雖然連字號合法，但 OpenTofu 社群慣例使用 snake_case（小寫 + 底線）：db_subnet_group_name、availability_zones。Provider 文件也都採此風格，跟著用可避免閱讀斷層。

5. 註解的三種寫法

HCL 支援三種註解形式：

HCL · 三種註解 
# 單行註解（推薦使用，社群最常見）

// 也是單行註解（C 風格，可用但較少見）

/*
 * 多行註解
 * 可以跨多行
 * 但不能巢狀使用
 */

resource "aws_instance" "web" {
  ami           = "ami-0abc..."   # 行尾註解：說明這個 AMI 是什麼
  instance_type = "t3.micro"      // 也可以這樣
}

慣例：用 #

OpenTofu 社群絕大多數使用 #。tofu fmt 會自動把 // 換成 #，所以即使你習慣 C 風格，跑過 fmt 後也會被統一。多行註解 /* */ 在實務上很少用到，通常拆成多個 # 行更清楚。

6. 字串：簡單字串與 heredoc

簡單字串（quoted string）

用雙引號包起，支援標準 escape 字元：

HCL · escape 字元 
name        = "my-server"
description = "Server with \"quoted\" word"  # 跳脫雙引號
path        = "C:\\Windows\\System32"        # 跳脫反斜線
multiline   = "line1\nline2\tindented"       # \n 換行、\t Tab
Escape意義
\n換行
\tTab
\rCarriage return
\"雙引號
\\反斜線
\uNNNNUnicode 字元
$$真正的 $ 字元（避免被當成內插起始）
%%真正的 % 字元（避免被當成模板指令）

Heredoc：多行字串

用 <<EOT 開始，獨立一行 EOT 結束。標籤名（這裡的 EOT）可任取，慣例是 EOT、EOF、SCRIPT 等。

HCL · 標準 heredoc 
user_data = <<EOT
#!/bin/bash
echo "Hello from instance"
yum install -y nginx
systemctl start nginx
EOT

Indented heredoc：保留縮排但不汙染輸出

把 << 換成 <<-，OpenTofu 會自動移除每行共同的前導縮排，讓你能在 HCL 內保持整齊縮排，但生成的字串不帶多餘空白：

HCL · indented heredoc 
resource "aws_iam_policy" "example" {
  name = "example"

  policy = <<-EOT
    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": "s3:GetObject",
          "Resource": "*"
        }
      ]
    }
  EOT
}

輸出的 JSON 字串沒有那層 6 空格縮排，因為它們是「共同前導」，OpenTofu 會幫你 strip 掉。

JSON 內容建議用 jsonencode()

上面範例能跑，但實務上更推薦使用 jsonencode({...}) 函式，讓 HCL 直接幫你產生合法的 JSON，避免手動處理引號跳脫。第 8 章會詳細介紹。

7. 字串內插與模板

字串內可以嵌入運算結果，這是 HCL 最強大的語法之一。共有兩種模板語法：

內插：${ ... }

把表達式的結果插入到字串中當作值：

HCL · 內插語法 
tags = {
  Name        = "${var.environment}-web-server"
  Environment = var.environment              # 整個值就是表達式時，不需 ${}
  Owner       = "${var.team}@example.com"
  CIDR        = "${cidrsubnet(var.vpc_cidr, 4, count.index)}"
}

指令：%{ ... }

用於控制字串生成的條件邏輯與迴圈。最常用於 user-data 或設定檔模板。

條件指令 if / else / endif

HCL · 條件模板 
user_data = <<-EOT
#!/bin/bash
%{ if var.install_nginx }
yum install -y nginx
systemctl enable nginx
%{ else }
echo "Nginx skipped"
%{ endif }
EOT

迴圈指令 for / endfor

HCL · 迴圈模板 
user_data = <<-EOT
#!/bin/bash
%{ for pkg in var.packages ~}
yum install -y ${pkg}
%{ endfor ~}
EOT

Whitespace stripping：~ 修飾符

注意上方範例 %{ for ... ~} 與 %{ endfor ~} 多了 ~。這個修飾符告訴 OpenTofu「移除指令後面的空白與換行」（放前面則是移除前面的）。沒有它的話，每次迴圈會多出一行空白。

寫法效果
%{ if cond }不修剪空白
%{~ if cond }修剪指令前的空白
%{ if cond ~}修剪指令後的空白
%{~ if cond ~}前後都修剪

8. 頂層 block 全集

「頂層 block」（top-level block）是可以直接寫在 .tf 檔案最外層的 block。OpenTofu 的功能基本上由這幾個 block type 撐起來：

Block 用途 本書對應章節
terraformOpenTofu 與 provider 版本約束、backend 設定、required_version第 14 章
providerProvider 設定（region、credentials 等）第 11 章
variableModule 的輸入變數第 7 章
localsModule 內的區域變數（避免重複計算）第 7 章
dataData source：讀取既有資源（不建立、不管理）第 6 章
resource受管資源：要建立、修改、銷毀的對象第 6 章
ephemeral（1.10+）暫存資源：值不寫入 state（適合 secret）第 13 章

一個五臟俱全的最小範例

HCL · 完整範例（main.tf） 
# 1. 版本與 provider 約束
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

# 2. 輸入變數
variable "team_name" {
  type        = string
  description = "Team name to use in resource naming"
  default     = "platform"
}

variable "file_count" {
  type        = number
  description = "Number of files to generate"
  default     = 3
}

# 3. 區域變數
locals {
  base_name = "${var.team_name}-greeting"
  common_tags = {
    Owner       = var.team_name
    ManagedBy   = "OpenTofu"
    Environment = "dev"
  }
}

# 4. random_pet：產生隨機名稱
resource "random_pet" "name" {
  length    = 2
  separator = "-"
}

# 5. local_file：依變數數量產生多個檔案
resource "local_file" "greeting" {
  count = var.file_count

  filename = "${path.module}/output/${local.base_name}-${count.index}.txt"
  content  = <<-EOT
    Hello, ${var.team_name} team!
    File index: ${count.index}
    Random ID: ${random_pet.name.id}
  EOT
}

# 6. 輸出
output "file_paths" {
  value       = local_file.greeting[*].filename
  description = "All generated file paths"
}

output "random_name" {
  value = random_pet.name.id
}

這個範例涵蓋了你日常會用到的 80% 結構。後續章節會逐一深入每種 block。

JSON 形式（.tf.json）長什麼樣

實際上很少手寫 JSON 形式，但你可能在「程式自動產生 IaC」場景會看到。語法 1:1 對應 native：

JSON · main.tf.json 
{
  "terraform": {
    "required_version": ">= 1.6.0",
    "required_providers": {
      "local": {
        "source": "hashicorp/local",
        "version": "~> 2.5"
      }
    }
  },
  "resource": {
    "local_file": {
      "greeting": {
        "filename": "/tmp/hello.txt",
        "content": "Hello!"
      }
    }
  }
}

何時用 JSON 形式？

主要場景是「另一個程式產生 IaC」：例如用 Python / Go 跑出大量類似 resource，把它輸出為 .tf.json 比生成 HCL 字串更穩健（不用處理引號、跳脫、縮排）。如果你是手寫設定，永遠不要用 JSON 形式——可讀性差太多。

檔案合併行為

同一目錄的所有 .tf 檔在 OpenTofu 眼中是一個 module，內容會合併處理。檔案怎麼分純粹是給人類看的組織方式。

10. 格式化與驗證：tofu fmt、tofu validate

tofu fmt：自動格式化

OpenTofu 有官方的格式化工具，作用類似 gofmt：把所有檔案調整成標準格式。

Bash 
# 格式化當前目錄
tofu fmt

# 遞迴處理子目錄
tofu fmt -recursive

# 只檢查不修改（CI/CD 用）
tofu fmt -check

# 顯示 diff
tofu fmt -diff

# 在 CI 失敗時印出哪些檔需要 fmt
tofu fmt -check -diff -recursive

tofu fmt 會自動處理：縮排（2 空格）、等號對齊、註解風格（// → #）、字串內插的多餘 ${ }、移除多餘的空白行等。

tofu validate：語法與型別驗證

檢查設定檔是否語法正確、變數型別是否對得起來、reference 的對象是否存在。不會連到雲端，是 fast feedback。

Bash 
# 必須先 init
tofu init -backend=false

# 驗證
tofu validate

# CI 友善
tofu validate -no-color -json

把這兩個放進 pre-commit hook

實務上強烈建議用 pre-commit-opentofu 或自己寫 git hook，讓 commit 前自動跑 tofu fmt -check 與 tofu validate。可以省下大量 PR review 的時間。

11. 風格慣例與專案結構建議

命名慣例

對象慣例範例
Resource namesnake_case，描述用途，不重複 type✅ resource "aws_instance" "web"   ❌ "web_instance"
Variable namesnake_case，動詞開頭描述條件enable_monitoring、vpc_cidr_block
Output namesnake_case，描述輸出內容vpc_id、db_endpoint
Local 變數snake_casecommon_tags、name_prefix
Module namesnake_case，描述用途module "primary_vpc"
檔名snake_case 或單字main.tf、iam_roles.tf

排版慣例

  • 每個檔案以 terraform {}、provider {}、data {}、resource {}、output {} 的順序排列（人類閱讀友善）
  • Variable 與 Output 的 description 強烈建議填寫，會自動成為 docs
  • Resource block 內，必填參數放上面、選填的放下面、meta-arguments（lifecycle、count、for_each）放最後
  • Block 之間用一個空行隔開，提升可讀性

建議的 resource 內部排列順序

HCL · 內部排序慣例 
resource "aws_instance" "web" {
  # 1. 必填參數
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type
  subnet_id     = aws_subnet.web.id

  # 2. 選填參數
  associate_public_ip_address = true
  monitoring                  = false
  user_data                   = local.user_data

  # 3. 巢狀 block（依重要性排序）
  root_block_device {
    volume_size = 30
  }

  # 4. tags（一般慣例放在 meta-arguments 之前）
  tags = merge(local.common_tags, {
    Name = "${var.environment}-web"
  })

  # 5. meta-arguments 放最後
  count = var.instance_count

  lifecycle {
    create_before_destroy = true
    ignore_changes        = [tags["LastDeploy"]]
  }

  depends_on = [aws_iam_role_policy.web_s3]
}

12. 本章重點與練習

重點回顧

  • HCL 由三大元素組成：block（容器）、argument（鍵值對）、expression（值）
  • 每個 block 由 type、labels、body 構成；不同 type 要求不同數量的 label
  • 識別字遵守「字母/數字/底線/連字號 + 不以數字開頭」規則，社群慣例 snake_case
  • 三種註解：#（推薦）、//（會被 fmt 改寫）、/* */（少用）
  • 字串支援 escape 字元；heredoc（<<EOT）寫多行字串，indented heredoc（<<-EOT）自動移除共同縮排
  • ${...} 內插值，%{...} 控制邏輯（if/for），~ 修飾符控制空白修剪
  • OpenTofu 認識 .tf、.tofu、.tf.json、.tofu.json；同名時 .tofu* 優先
  • 同目錄所有檔案合併為一個 module，分檔僅是組織方式
  • tofu fmt 與 tofu validate 應該放進 pre-commit hook
⚡ 動手實作 · Hands-on Lab 5

HCL 語法綜合練習

  1. 建立目錄 hcl-playground/，把第 8 節「五臟俱全的最小範例」貼進 main.tf
  2. 跑 tofu init 與 tofu fmt -diff，看格式化前後的差異
  3. 跑 tofu validate 確認語法無誤
  4. 跑 tofu apply，觀察 output/ 目錄產生 3 個檔案
  5. 練習 A：把 main.tf 拆成 versions.tf、variables.tf、locals.tf、main.tf、outputs.tf 五個檔案，再次跑 tofu plan，確認 OpenTofu 視為同一 module（plan 顯示 No changes）
  6. 練習 B：把 main.tf 改名為 main.tofu，並建立另一個 main.tf 內容是「destroy 資源」（即不寫任何 resource）。跑 tofu plan，觀察 OpenTofu 仍讀 .tofu（顯示 No changes）；用 terraform plan（如有裝）會看到要 destroy 全部資源
  7. 挑戰題：用 indented heredoc + 模板指令 %{ for ... ~}，產生一個 shell script 字串，內容是依 var.packages list 動態產生 yum install -y <pkg> 多行
  8. 用 tofu destroy 清掉資源
