1. 為什麼需要這些進階特性

前面 12 章涵蓋了「日常 90% 工作」的語言特性。本章的進階特性解決的是剩下 10% 的硬問題——這些問題若處理不當會造成嚴重後果（state 損毀、secret 外洩、生產事故）。

進階特性解決什麼問題
precondition / postcondition / check把「應該為真的條件」寫進設定，讓 OpenTofu 在違反時提早報錯
ephemeral 資源 / 變數 / 輸出secret 真正不進 state，只在執行階段存在於記憶體
Write-only attributes密碼類屬性只在「設定變更時」才存在於 plan，平時不在 state
import block宣告式把雲端既有資源納入 OpenTofu 管理
moved block重構（改名、模組化）不需 destroy + create，state 自動跟著遷移
removed block從設定移除某資源但雲端實體保留（不 destroy）
deprecated 屬性module 改版時優雅地廢棄變數/輸出，給使用者遷移期

這章的 audience

本章內容偏進階，適合已能寫日常 module、開始遇到複雜場景的團隊。新手可以略過，但建議至少看 moved 與 import 兩節（重構與納管既有資源很常用）。

2. Custom Conditions：preconditions、postconditions、check

傳統 IaC 的痛點：很多假設只能寫在 README，下個工程師沒看到就出事。Custom conditions 把這些假設變成執行時的檢查。

三種 condition 比較

機制位置檢查時機失敗時行為
variable.validationvariable block 內變數值傳入時立即 error
lifecycle.preconditionresource / data / output 內該物件動作執行前立即 error
lifecycle.postconditionresource / data / output 內該物件動作執行後立即 error
check block頂層獨立 blockplan / apply 結尾warning 而非 error

precondition：守護「我假設什麼為真」

HCL · precondition 範例 
data "aws_ami" "app" {
  most_recent = true
  owners      = ["self"]
  filter { name = "name", values = ["app-*"] }
}

resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = "t3.micro"

  lifecycle {
    precondition {
      condition     = data.aws_ami.app.architecture == "x86_64"
      error_message = "AMI must be x86_64, got ${data.aws_ami.app.architecture}."
    }

    precondition {
      condition     = var.environment != "prod" || var.instance_type != "t3.micro"
      error_message = "Production must not use t3.micro."
    }
  }
}

postcondition：守護「執行完應該長什麼樣」

HCL · postcondition 範例 
resource "aws_instance" "app" {
  ami           = data.aws_ami.app.id
  instance_type = var.instance_type
  subnet_id     = aws_subnet.app.id

  lifecycle {
    postcondition {
      condition     = self.public_dns != ""
      error_message = "EC2 must have public DNS. Check VPC enable_dns_hostnames."
    }

    postcondition {
      condition     = self.private_ip != ""
      error_message = "EC2 must have a private IP."
    }
  }
}

# Output 也支援 precondition
output "instance_id" {
  value = aws_instance.app.id

  precondition {
    condition     = aws_instance.app.tags["Environment"] != null
    error_message = "Instance must be tagged with Environment."
  }
}

self 是 OpenTofu 提供的特殊變數，只能在 postcondition 內使用，指向當前 resource 的最終狀態。

check block：apply 後的軟驗證

check 是頂層 block（不在 resource 內），檢查整個系統的健康狀態。失敗只發 warning，不會中斷 apply：

HCL · check block 範例 
check "health_check" {
  data "http" "endpoint" {
    url = "https://${aws_lb.main.dns_name}/health"
  }

  assert {
    condition     = data.http.endpoint.status_code == 200
    error_message = "Health check failed: HTTP ${data.http.endpoint.status_code}"
  }
}

check "tag_compliance" {
  assert {
    condition = alltrue([
      for r in [
        aws_instance.web,
        aws_db_instance.main,
      ] : r.tags["Owner"] != null && r.tags["Environment"] != null
    ])
    error_message = "All resources must have Owner and Environment tags."
  }
}

三者選用準則

需求用什麼
限制 input variable 範圍variable.validation
「資源建立前先確認某事為真」precondition
「資源建立後驗證它的最終狀態」postcondition
持續檢查整體健康但不阻擋 applycheck
跨資源的合規檢查check 或 conftest / OPA

3. Ephemeral Values（OpenTofu 1.11+ 獨家完整實作）

這是 OpenTofu 1.11 的旗艦級新功能，徹底解決「secret 寫進 state」這個長年痛點。ephemeral 值只在執行階段存在於記憶體，永不寫入 state、永不寫入 plan 檔、永不出現在輸出中。

ephemeral 是什麼等級的進步？

過去 14 年 Terraform/OpenTofu 的 sensitive 機制只是「不顯示在 CLI」，state 仍以明文紀錄。Ephemeral 是真正的 secret 不寫入 state 的解，等於把 IaC 工具的安全等級從「醫療等級口罩」升級到「N95」。OpenTofu 1.7 的 state encryption 已經很好，搭配 1.11 的 ephemeral，達到 production 級安全標準。

① ephemeral resource：取 secret 不留痕

ephemeral block 的語法與 resource、data 類似，但其值不會被儲存：

HCL · 從 OpenBao 取得短期 AWS 憑證 
terraform {
  required_providers {
    openbao = { source = "openbao/openbao", version = "~> 2.0" }
    aws     = { source = "hashicorp/aws",   version = "~> 5.0" }
  }
}

# 從 Vault/OpenBao 取得短期 AWS credentials
ephemeral "openbao_kv_v2_secret" "aws_creds" {
  mount = "kv"
  name  = "aws/production"
}

# 用這個 ephemeral 值設定 AWS provider
provider "aws" {
  region     = "us-east-1"
  access_key = ephemeral.openbao_kv_v2_secret.aws_creds.data["access_key"]
  secret_key = ephemeral.openbao_kv_v2_secret.aws_creds.data["secret_key"]
}

resource "aws_s3_bucket" "x" {
  bucket = "my-bucket"
}

# ⚠️ 不能直接 output ephemeral 值（除非 output 也標 ephemeral）
# output "creds" { value = ephemeral.openbao_kv_v2_secret.aws_creds }  # ERROR

② ephemeral 輸入變數

HCL · ephemeral variable 
variable "session_token" {
  type        = string
  ephemeral   = true        # 只存在記憶體
  description = "Short-lived session token from CI"
}

# 使用：環境變數傳入仍可
# export TF_VAR_session_token=...

# ⚠️ 不能用在會寫進 state 的位置
resource "aws_iam_user" "x" {
  # ❌ 寫死的話會 leak 到 state
  # tags = { token = var.session_token }
}

# ✅ 只能用在 ephemeral context（provider 設定、其他 ephemeral 值、write-only attr）
provider "vault" {
  token = var.session_token
}

③ ephemeral 輸出

HCL · ephemeral output（給 child module 用） 
output "db_password" {
  value     = ephemeral.openbao_kv_v2_secret.db.data["password"]
  ephemeral = true
  sensitive = true
}

注意：root module 的 ephemeral output 不會顯示在 tofu output。它的用途是給父 module 的 child module 引用。在 root level 用 ephemeral output 沒太大意義，主要是 reusable module 之間傳遞 secret。

ephemeral 的使用限制

Ephemeral 值只能用在特定位置：

位置能用 ephemeral？
provider block 屬性✅
provisioner / connection block✅
另一個 ephemeral 資源/輸出/變數✅
local 值（如果該 local 也只用在上述位置）✅（傳染性）
resource 的 write-only 屬性✅
resource 的一般屬性❌
非 ephemeral output❌
data source 的 arguments❌

4. Write-only Attributes

Write-only 屬性是 ephemeral 的另一面：resource 的某些屬性只在「設定變更時」才存在於 plan，平時也不在 state。最典型用途是初始密碼。

使用範例

HCL · DB 初始密碼用 write-only 
ephemeral "openbao_kv_v2_secret" "db_password" {
  mount = "kv"
  name  = "db/initial-password"
}

resource "aws_db_instance" "main" {
  identifier        = "app-db"
  engine            = "postgres"
  instance_class    = "db.t3.medium"
  username          = "admin"

  # write-only 屬性：只在設定變更時 OpenTofu 才需要看它
  password_wo         = ephemeral.openbao_kv_v2_secret.db_password.data["password"]
  password_wo_version = 1   # 改這個版本號才會觸發更新

  lifecycle {
    ignore_changes = [password]  # 平時忽略
  }
}

使用流程：

  1. 第一次 apply：取出 secret 寫入 DB，但不存進 state
  2. 之後 apply：OpenTofu 不需 secret，state 中 password_wo = null
  3. 需要更新密碼時：把 password_wo_version 從 1 改成 2，OpenTofu 才會再去取一次新 secret

需要 provider 支援

不是所有 resource 都支援 write-only 屬性，需要 provider 為該屬性明確標記為 write-only。撰寫本書時 AWS、Azure、GCP 主流 provider 已大量支援，但仍以官方文件為準（屬性會以 _wo 後綴命名）。

5. Import block：宣告式匯入

當你需要把已存在的雲端資源納入 OpenTofu 管理（例如 console 點出來的、其他工具建立的、或別的 stack 移過來的），有兩種方式：

方式命令式宣告式
指令tofu import <addr> <id>import { ... } block
支援版本所有版本OpenTofu 1.5+
是否能版控否（只是命令）是（HCL 設定）
能否 plan 預覽否（直接寫 state）是
批次匯入難（要寫 script）容易（多個 import block）

import block 基本用法

HCL · 匯入既有 S3 bucket 
# 1. 寫 import block
import {
  to = aws_s3_bucket.legacy
  id = "my-existing-legacy-bucket"
}

# 2. 對應的 resource block 必須存在
resource "aws_s3_bucket" "legacy" {
  bucket = "my-existing-legacy-bucket"
  # ... 把雲端實際的設定寫進來
}

工作流程

    S1[在雲端 console 找到既有資源]
    S2[寫 import block + 對應 resource block]
    S3[tofu plan]
    S4[OpenTofu 顯示「will be imported」]
    S5{差異多嗎？}
    S6[補完 resource 設定
讓 plan 顯示 No changes]
    S7[tofu apply]
    S8[資源納入 state]

    S1 --> S2 --> S3 --> S4 --> S5
    S5 -->|是| S6 --> S3
    S5 -->|否| S7 --> S8 --> S9

進階：用 for_each 批次匯入

HCL · 批次匯入 
variable "legacy_buckets" {
  type    = set(string)
  default = ["bucket-a", "bucket-b", "bucket-c"]
}

import {
  for_each = var.legacy_buckets
  to       = aws_s3_bucket.legacy[each.value]
  id       = each.value
}

resource "aws_s3_bucket" "legacy" {
  for_each = var.legacy_buckets
  bucket   = each.value
}

產生 resource block：tofu plan -generate-config-out

不想手動寫 resource block？OpenTofu 1.5+ 可以自動產生：

Bash · 自動產生 resource block 
# 1. 只寫 import block，不寫 resource block
cat > imports.tf <<'EOF'
import {
  to = aws_s3_bucket.legacy
  id = "my-existing-bucket"
}
EOF

# 2. 跑 plan 自動產生 resource 設定
tofu plan -generate-config-out=generated.tf

# 3. 看產生出來的 generated.tf
cat generated.tf
# 4. 整理該檔（移除不必要的屬性、加 lifecycle 等）
# 5. 跑 apply

6. Moved block：重構不破壞 state

當你想改名 resource、把 resource 搬進 module、重構 module 結構，用 moved block。OpenTofu 會自動把 state 中的舊 address 改成新 address，不會觸發 destroy + create。

三種典型重構

① 改 resource name

HCL · 改名 
# 之前
resource "aws_instance" "web" { /* ... */ }

# 之後
resource "aws_instance" "web_primary" { /* ... */ }

moved {
  from = aws_instance.web
  to   = aws_instance.web_primary
}

② 從 count 改成 for_each

HCL · count → for_each 
# 之前
resource "aws_instance" "web" {
  count = 3
  ami   = "ami-..."
  tags  = { Name = "web-${count.index}" }
}

# 之後
resource "aws_instance" "web" {
  for_each = toset(["a", "b", "c"])
  ami      = "ami-..."
  tags     = { Name = "web-${each.key}" }
}

moved {
  from = aws_instance.web[0]
  to   = aws_instance.web["a"]
}
moved {
  from = aws_instance.web[1]
  to   = aws_instance.web["b"]
}
moved {
  from = aws_instance.web[2]
  to   = aws_instance.web["c"]
}

③ 把 resource 搬進 module

HCL · 提取到 module 
# 之前（在 root module）
resource "aws_vpc" "main" { /* ... */ }

# 之後（搬進 module "network"）
module "network" {
  source = "./modules/network"
  # ...
}

# module 內仍有 aws_vpc.main resource
moved {
  from = aws_vpc.main
  to   = module.network.aws_vpc.main
}

moved 之後可以保留還是該移除？

moved block 在 apply 完成後仍可保留——它只是「告訴未來的 OpenTofu 也認識舊 address」。建議的策略：

  • Reusable module 內：保留 moved block，避免使用者升級時 state 跳掉
  • 內部專案、所有環境都已 apply 過：可以移除以保持設定乾淨

7. Removed block：從設定移除但保留實體

有時你想「不再用 OpenTofu 管理某資源」，但不想銷毀雲端實體（例如要交給其他 stack 管理、或人為托管）。傳統做法是 tofu state rm，但這是命令式操作。OpenTofu 1.7+ 提供 removed block：

HCL · removed block 
# 從本 stack 移除 aws_s3_bucket.legacy（但 S3 bucket 在雲端保留）
removed {
  from = aws_s3_bucket.legacy

  lifecycle {
    destroy = false   # 不 destroy（這是 removed block 的精神）
  }
}

# 注意：對應的 resource block 必須移除！
# resource "aws_s3_bucket" "legacy" { ... }   ← 這個要刪掉

使用流程

  1. 從設定中刪掉對應的 resource block
  2. 加上 removed block 並設 destroy = false
  3. 跑 tofu plan 確認顯示「will be removed from state」（而非 destroy）
  4. 跑 tofu apply
  5. 確認後可移除 removed block（OpenTofu 已忘記該資源）

removed vs tofu state rm

面向tofu state rmremoved block
方式命令式宣告式
能 plan 預覽否是
能版控否是（PR review）
能在 CI/CD 自動執行需額外腳本跟普通 apply 一樣
建議使用版本OpenTofu 1.0+OpenTofu 1.7+（推薦）

destroy = true 也支援

removed 也能用來「確實 destroy 但不需保留 resource block」（少見場景）：

HCL · removed + destroy 
# 不再需要 aws_lb.old，destroy 它
removed {
  from = aws_lb.old

  lifecycle {
    destroy = true   # 預設行為
  }
}

但這個用法很少見——直接刪掉 resource block 就會自動 destroy 了，不需 removed。removed 的核心價值是 destroy = false。

8. Variable / Output 的 deprecated（OpenTofu 1.11+）

當你維護 reusable module 並要做 breaking change，希望給使用者遷移期。OpenTofu 1.11+ 推出 deprecated 屬性：

HCL · deprecated 範例 
# 舊變數標記為 deprecated
variable "instance_size" {
  type        = string
  description = "Old name for instance class. Use instance_class instead."
  default     = null
  deprecated  = "Use instance_class instead. instance_size will be removed in v3.0.0."
}

# 新變數
variable "instance_class" {
  type        = string
  description = "EC2 instance class"
  default     = "t3.micro"
}

locals {
  # 內部處理向下相容
  effective_size = var.instance_size != null ? var.instance_size : var.instance_class
}

使用者如果還傳了 instance_size，OpenTofu 會印出 warning：

Plaintext · 警告訊息 
Warning: Variable marked as deprecated by the module author

  on main.tf line 5:
   5:   instance_size = "t3.micro"

Use instance_class instead. instance_size will be removed in v3.0.0.

output 的 deprecated

HCL · output deprecated 
output "vpc_arn" {
  value      = aws_vpc.main.arn
  deprecated = "Use vpc_id instead. vpc_arn will be removed in v3.0.0."
}

output "vpc_id" {
  value = aws_vpc.main.id
}

9. 5 種 state 操作 block 對照

本章介紹了 5 種會影響 state 的 block，這個對照表幫你選用：

resource建立/管理資源新增條目建立資源
import納管既有資源新增條目（不重建）無變化
moved重新命名 / 重構條目改 address無變化
removed (destroy=false)不再管理但保留移除條目無變化
removed (destroy=true)銷毀移除條目銷毀資源

10. 常見陷阱與最佳實踐

陷阱 1：postcondition 用了 self 之外的屬性

self 只在 postcondition 內有意義（不能在 precondition）。要引用其他資源的屬性時，記得加上完整路徑。

陷阱 2：ephemeral 用在錯誤位置

HCL 
ephemeral "secret_x" "y" { /* ... */ }

# ❌ 把 ephemeral 值用在會寫進 state 的位置
resource "aws_instance" "x" {
  user_data = ephemeral.secret_x.y.value   # ERROR: 會寫進 state
}

# ✅ 正確：只能用在 provider 設定、其他 ephemeral、write-only attr
provider "aws" {
  secret_key = ephemeral.secret_x.y.value   # OK
}

陷阱 3：import 後忘了補設定

Import 後若 resource block 設定與雲端實際不符，下次 apply 會「修正」雲端去符合設定，可能造成意外。務必跑 plan 確認 No changes 才 apply。

陷阱 4：moved 寫錯方向

HCL 
# ❌ from 是新名、to 是舊名
moved {
  from = aws_instance.web_primary   # 新名
  to   = aws_instance.web           # 舊名
}

# ✅ from 是舊名、to 是新名
moved {
  from = aws_instance.web           # 舊（state 中的）
  to   = aws_instance.web_primary   # 新（設定中的）
}

記憶法：「從哪裡 → 到哪裡」就是 from → to。

陷阱 5：removed 沒設 destroy = false 結果真的炸了

removed 預設 destroy = true。如果你的目的是「保留實體只移除 state」，務必明確寫 destroy = false。

陷阱 6：check block 的 warning 被忽略

check 失敗只發 warning，CI/CD 預設不會 fail。如果你想讓 check 失敗變成阻擋部署，需在 CI 中 grep warning 文字並判斷 exit code。

11. 本章重點與練習

重點回顧

  • Custom conditions 把假設轉成執行時檢查：variable.validation、precondition、postcondition、check
  • self 只能用在 postcondition，指向當前 resource 的最終狀態
  • check block 失敗只 warning 不中斷，適合持續監控但不阻擋部署
  • OpenTofu 1.11+ 完整實作 ephemeral：四類（resource、variable、output、write-only attr），值不寫入 state / plan 檔
  • Ephemeral 只能用在 provider 設定、其他 ephemeral、write-only 屬性等特定位置
  • import block 是宣告式納管的新方式（OpenTofu 1.5+），可版控、可 plan 預覽，比舊式 tofu import 指令好用太多
  • tofu plan -generate-config-out 可自動產生 resource block，搭配 import 極為方便
  • moved block 處理重構（改名、搬進 module、count→for_each），state 自動跟著遷移不需 destroy + create
  • removed block + destroy = false 是「不再管理但保留實體」的宣告式做法（OpenTofu 1.7+），優於 tofu state rm
  • OpenTofu 1.11+ 的 deprecated 屬性讓 module 改版可優雅地廢棄變數/輸出
  • 原則：宣告式 block 永遠優先於命令式 tofu state 指令
