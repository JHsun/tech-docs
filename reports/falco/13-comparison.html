同類工具
完整比較

Falco 不是唯一選擇。本章對比五個主要的 runtime security 工具—— Falco、Tracee、Tetragon、KubeArmor、Wazuh、Sysdig Secure—— 從偵測機制、效能、enforcement 能力、生態、學習曲線到商業版差異全面解析。

⏱ 預估閱讀 45 分鐘 📚 本手冊原創章節 選型參考 SRE

13.1為什麼要做工具比較

雲端原生 runtime security 市場百花齊放，光開源項目就有 Falco、Tracee、Tetragon、KubeArmor 等。 商業版還有 Sysdig Secure、CrowdStrike、Aqua、Lacework… 沒有單一工具滿足所有需求，理解差異才能組合或選對。

三大評估維度

  1. 偵測 vs Enforcement：純偵測（Falco/Tracee）、偵測+阻擋（Tetragon/KubeArmor）
  2. 資料來源：syscall-only、syscall+plugin、audit log、LSM hooks
  3. 整合面：與 K8s 整合度、與 SIEM/CSPM 整合、商業 support

13.2Falco（基準參照）

🦅 FalcoCNCF GRADUATED

創立 2016 (Sysdig) · 捐贈 CNCF 2018 · graduated 2024 · v0.43 · ~8.7k stars

雲端原生 runtime security 的事實標準。核心定位：偵測 (detection)。 強項是成熟的 rule engine、最大的社群、最完整的 plugin 生態。

✓ 優點
  • CNCF 畢業；最成熟、最大社群
  • YAML rule，學習曲線平緩
  • 豐富的 default rules (~70)
  • Plugin 生態最完整（k8saudit、cloudtrail、okta…）
  • falcosidekick 60+ integration
  • EKS Add-on、Helm、Operator 多種部署
✗ 缺點
  • 只偵測不阻擋（需搭配其他工具做 enforcement）
  • 較舊 process injection / 高階攻擊偵測較弱
  • 規則太多時 CPU 開銷高
  • 沒有原生 K8s label selector（要寫 condition）

13.3Tracee（Aqua Security）

🐍 TraceeCNCF SANDBOX

創立 2019 (Aqua) · v0.27+ · ~3.7k stars

更深的 eBPF tracing。Tracee 比 Falco 鉤更多 kernel 事件點， 提供更豐富的 forensic context。但代價是 CPU 與 RAM 開銷較高。

與 Falco 的主要差異

面向FalcoTracee
規則語言YAML（直觀）Go-based signatures（程式化）
偵測深度syscallsyscall + tracepoint + uprobe
Forensic 能力基本 metadata強，含 capture file
CPU overhead低-中中-高（2-4x Tetragon）
Memory低較高
學習曲線易需 Go 知識
社群大小大 (CNCF graduated)中 (CNCF sandbox)
✓ 適合用 Tracee
  • 需要深度 forensic 證據（incident response team）
  • 研究攻擊行為（red team / security research）
  • 已熟悉 Go 語言
  • 不缺 CPU 預算
✗ 不適合
  • 主流生產偵測（用 Falco 更簡單）
  • CPU 受限環境
  • 純 SRE team（沒 Go 開發能量）

13.4Tetragon（Cilium）

🦖 TetragonCNCF INCUBATING

創立 2022 (Isovalent/Cilium) · v1.x · ~4.0k stars

偵測 + Enforcement。Tetragon 是 Cilium 生態的 runtime security 元件， 最大差異化是能在 kernel 內阻擋行為——透過 bpf_send_signal() 殺 process。

與 Falco 的關鍵差異：可阻擋

實例：偵測到非 nginx 寫入 /etc，Falco 只能告警，Tetragon 可以直接 SIGKILL：

yaml · Tetragon TracingPolicy
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: block-etc-write
spec:
  kprobes:
    - call: "fd_install"
      syscall: false
      args:
        - index: 0
          type: int
        - index: 1
          type: file
      selectors:
        - matchArgs:
            - index: 1
              operator: Prefix
              values: ["/etc"]
          matchActions:
            - action: Sigkill        # ← 直接殺！
✓ 適合用 Tetragon
  • 需要 enforcement 而非單純告警
  • 已用 Cilium 做網路（生態整合好）
  • 追求極低 overhead（< 1% CPU）
  • 需要原生 K8s label selector
✗ 不適合
  • 不熟 Cilium 生態
  • 需要豐富 default rules（Tetragon 較少）
  • 需要 plugin 生態（CloudTrail、Okta）
  • 怕誤殺 (kernel-level kill 不可逆)
💡
最佳組合：Falco + Tetragon。Falco 提供成熟的 detection 與 SIEM 整合； Tetragon 處理需要 enforcement 的少數高優先場景。兩者用 eBPF 但 hook 不同點，可共存。

13.5KubeArmor（AccuKnox）

🛡 KubeArmorCNCF SANDBOX

v1.x · ~1.7k stars

Enforcement-first。比 Tetragon 更強調預防——利用 Linux LSM （AppArmor、SELinux、BPF-LSM）做 zero-trust workload hardening。

主要差異

  • 用 LSM 而非僅 eBPF：能比 eBPF kill 更乾淨地阻擋
  • 政策 schema 偏 K8s native：用 KubeArmorPolicy CRD，能 select pod labels
  • 支援 file/process/network/capability 四類限制
  • 非容器環境也支援：VM、bare metal
✓ 適合
  • 已用 AppArmor / SELinux 的環境
  • 需要白名單模式（zero-trust）
  • VM/bare metal 為主
  • 合規嚴格（強制執行而非僅偵測）
✗ 不適合
  • 偵測（社群、規則庫小於 Falco）
  • 事件 forensic（不如 Tracee）
  • 較高 latency（15-176ms vs Falco ~10ms）

13.6Wazuh（傳統 SIEM 路線）

🪐 WazuhSIEM + EDR

v4.x · ~12k stars

完全不同的取徑。Wazuh 是整套 SIEM 平台——agent + manager + Elastic Stack。 Linux 端用 auditd hook、檔案 integrity、log analysis； 不用 eBPF，所以 visibility 比 Falco 淺，但是個完整方案。

主要差異

面向FalcoWazuh
定位runtime 偵測工具完整 SIEM + EDR 平台
偵測機制eBPF syscallauditd + file integrity + log
偵測深度kernel level（深）userspace + audit（淺）
K8s 原生是適配中（DaemonSet 模式）
內建 UI / Dashboard無有，完整
合規報表需自建內建 PCI-DSS、HIPAA、GDPR…
Endpoint coverageLinux onlyLinux + Windows + macOS
✓
互補組合：Falco + Wazuh。Falco 提供 deep runtime detection， 把 alert 透過 falcosidekick → Wazuh API，Wazuh 做集中管理、合規報表與跨平台關聯。

13.7Sysdig Secure（商業 CNAPP）

💼 Sysdig SecureCOMMERCIAL CNAPP

Sysdig 公司商業產品

Falco 的商業母品牌。Sysdig 是 Falco 的原始作者， Sysdig Secure 是「Falco + 商業增值」的整套 CNAPP（Cloud-Native Application Protection Platform）。

商業版加了什麼

  • 500+ 規則（OSS ~70）+ ML-based 異常偵測
  • CSPM / Posture：雲端 misconfig 掃描
  • Image scanning：build-time + runtime CVE 整合
  • 合規模板：SOC 2、PCI-DSS、HIPAA、CIS 等內建
  • SOC dashboard：完整 web UI、incident workflow
  • Captures-on-alert：自動錄製 alert 觸發時的 syscall 流
  • 商業 SLA：24x7、固定 response time

什麼時候選商業版

  • 組織需要 audit-ready 合規報表
  • 有 SOC 但缺 cloud-native expertise
  • 需 image-to-runtime 完整可視（Trivy 不夠）
  • 需要單一 vendor 負責整個 cloud security stack
💡
OSS + 商業共存：多數 Sysdig Secure 客戶同時跑 OSS Falco——技術 team 用 OSS 做 dev/staging detection 與客製化； SOC 用商業版做集中監控與合規。

三種典型組合

組合 A — Pure OSS 起步（成本敏感）

Falco + falcosidekick + Loki + Grafana

  • 適合：新創、中小規模、技術 team 主導
  • 成本：純人力
  • 限制：無 enforcement、無內建合規報表

組合 B — Defense in Depth（中大型生產）

Falco（偵測）+ Tetragon（關鍵 enforcement）+ Wazuh（合規 + 跨平台）

  • 適合：金融、醫療、需合規的中大型
  • 成本：仍是 OSS 為主，但運維複雜度高
  • 優勢：多層防護 + 合規舉證

組合 C — 商業 CNAPP（單一 vendor）

Sysdig Secure（或 Prisma Cloud、Wiz）+ 內部 OSS Falco for dev

  • 適合：有 SOC、要 24x7 支援、不想自建 stack
  • 成本：依 cluster 數計費
  • 優勢：一站式、SOC 友善、合規快速 onboard

13.10為什麼本手冊選 Falco

讀到這你可能想問：「既然有 Tetragon 能 enforcement，為何整本手冊還是教 Falco？」 這節給答案。

三個理由

  1. 成熟度：CNCF graduated 是市場接受度最高的訊號。 多數企業採用 Falco 的問題能 google 到答案；Tetragon 較新，問題較難找。
  2. 生態：Falco 的 plugin 與 falcosidekick 整合無人能及。 要做 cloud audit、K8s audit、Okta 等多源 detection，Falco 是唯一答案。
  3. 學習曲線：YAML rule 簡單；TracingPolicy（Tetragon）需要對 kprobe / tracepoint 有理解。 組織內非 kernel 專家也能上手寫 Falco rule。

但 Falco 不夠的地方

誠實面對 Falco 的限制：

  • 無法阻擋 → 搭 Tetragon / KubeArmor 處理少數需 enforcement 的場景
  • process injection 偵測弱 → 用 Tracee 補
  • 無內建 UI / dashboard → 用 falcosidekick-ui 或 Grafana
  • 合規報表需自建 → 接 Wazuh / Sysdig Secure / 自寫 Loki query
✓
結論：Falco 不是「最完美」的 runtime security 工具，但它是最適合作為起點的工具。 組織採用後再依需求補其他工具，比一開始就追完美方案實際得多。
