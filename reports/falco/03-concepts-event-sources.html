Event Sources
事件來源

Falco 之所以「看得到」異常行為，是因為它從多個 event sources 接收事件。本章深入兩大來源： kernel syscalls（透過 driver）與 plugin events（雲端 API）， 以及如何選擇正確的 driver。

⏱ 預估閱讀 45 分鐘 📚 對應 docs/concepts/event-sources/ SRE 開發者

3.1Event Sources 總覽

Falco 把每一筆事件統稱為 event，無論來自 kernel 或 plugin。每個 event 屬於某個 source， rules 可以指定只在特定 source 上運行。預設 source 是 syscall。

3.2Kernel Events（最主要來源）

90% 的 Falco 偵測力來自 kernel events——也就是 Linux syscalls。理解 syscall 怎麼被捕獲、被解析， 才能寫出高效能、低 false positive 的 rules。

什麼是 syscall

System call (syscall) 是 user space 程式與 kernel 互動的唯一管道。 開檔案要呼叫 open、執行新程式要呼叫 execve、建網路連線要呼叫 connect。 幾乎所有有趣的安全事件——讀取 /etc/shadow、容器內開 shell、權限提升—— 背後都有對應的 syscall pattern。

進入 / 退出事件 (Enter / Exit Events)

每個 syscall 在 kernel 層其實有兩個事件：進入 (enter, >) 與 退出 (exit, <)。 從 v0.42 起的 drop-enter initiative，Falco 預設只處理 < 事件（exit），效能更好。

⚠️
遺留 rule 警告：若你的 rule 寫過 evt.dir = > 來抓 enter event， v0.42 之後它會匹配不到任何東西、v0.43 會 emit warning。 evt.dir 整個欄位族會在未來版本移除——請盡早改寫。

事件方向欄位 (evt.dir) 的演進

Falco 版本evt.dir = >evt.dir = <
≤ 0.41匹配 enter 事件匹配 exit 事件
0.42不匹配（已棄用）匹配所有
0.43+不匹配 + warning匹配所有 + warning
未來欄位移除，rules 載入失敗欄位移除

3.3Driver 選擇深入

Driver 是把 syscall 從 kernel 傳到 userspace 的橋樑。Falco 支援三種 driver，但實務上只剩一個推薦—— Modern eBPF。

Modern eBPF Probe推薦 · 預設

原理：用 CO-RE (Compile Once, Run Everywhere) 技術編譯的 eBPF 程式， 啟動時自動載入 kernel，零依賴。

  • 需求：Linux kernel 5.8+ 且編譯時 CONFIG_DEBUG_INFO_BTF=y（主流 distro 都有）
  • 優點：無需 kernel headers、無需 DKMS、跨核心 portable、效能優
  • 缺點：太舊的 kernel (< 5.8) 不支援

Kernel Module (kmod)備用

原理：傳統 .ko module，靠 DKMS 在主機上動態編譯。

  • 需求：kernel headers (linux-headers-$(uname -r)) + 編譯工具
  • 優點：能跑在舊 kernel；某些情況比 eBPF 略快
  • 缺點：每次 kernel 升級需重編譯；對 immutable OS（如 Talos、Bottlerocket）不友善

Legacy eBPF Probe⚠ Deprecated v0.43

原理：舊式 eBPF，需要在主機上預先放置 .o 檔。

  • 狀態：v0.43 已標 deprecated，未來版本移除
  • 建議：盡快遷移到 Modern eBPF（多數環境一鍵切換）

切換 driver 實作

Linux host (systemd)：

bash · systemd 切換
# 停掉現用的
sudo systemctl disable --now falco-bpf.service     # legacy eBPF
sudo systemctl disable --now falco-kmod.service    # kmod

# 啟用 Modern eBPF
sudo systemctl enable --now falco-modern-bpf.service
sudo systemctl status falco-modern-bpf.service

Kubernetes (Helm)：

values.yaml · driver kind
driver:
  enabled: true
  kind: modern_ebpf
  # modern_ebpf | kmod | ebpf (legacy, deprecated)

  # 若選 kmod 並需要在啟動時自動安裝 driver
  loader:
    enabled: true
    initContainer:
      enabled: true
bash · 套用
helm upgrade falco -n falco -f values.yaml falcosecurity/falco
kubectl rollout restart ds/falco -n falco
kubectl rollout status ds/falco -n falco

驗證 driver 真的有跑起來

bash · 確認 driver kind

sudo journalctl -u falco-modern-bpf.service | grep -i "engine\|probe"

# k8s pod

3.4Container Metadata 補強

Raw syscall 只有 PID、UID 等基礎資訊。Falco 透過 container plugin 自動 enrich 容器與 Kubernetes context——這是 alert 能直接告訴你「哪個 pod 觸發」的關鍵。

container plugin 的角色

自 Falco 0.41 起，container metadata 改由獨立 plugin（plugins/container）處理， 而非內建在 binary。這讓 enrichment 邏輯能獨立更新、修 bug 不用重 release Falco 本體。 v0.43.1 對齊 container plugin 0.6.4。

⚠️
沒裝 container plugin 的後果：所有 container.* 與 k8s.* 欄位都會是空的。 官方預設 ruleset 大量依賴這些欄位（如 container.image.repository）， 沒 plugin = 多數 default rules 失效。Helm chart 與 Operator 預設都會裝； 手動裝 Falco 時要記得也裝 plugin。

支援的 container runtime

RuntimeSocket 路徑備註
containerd/run/containerd/containerd.sockk8s 主流
CRI-O/var/run/crio/crio.sockOpenShift / RHEL
Docker/var/run/docker.sock非 k8s 環境
Podman透過 CRI socket需設定

Helm 中設定 container plugin（Helm chart 預設行為）

values.yaml · collectors
collectors:
  enabled: true

  containerd:
    enabled: true
    socket: /run/containerd/containerd.sock

  crio:
    enabled: false
    socket: /run/crio/crio.sock

  docker:
    enabled: false                 # 多數 k8s 用 containerd 即可

  kubernetes:
    enabled: true                  # 啟用 K8s metadata 補強
    apiAuthTokenPath: /var/run/secrets/kubernetes.io/serviceaccount/token
    apiUrl: "https://kubernetes.default"

3.5Plugin Events（雲端與第三方來源）

Falco 不只看 kernel。透過 plugin 機制，它能把任何能轉成 event stream 的東西當成 source—— AWS CloudTrail、K8s Audit Logs、Okta、GitHub Audit、自訂 JSON…

三大官方 plugin sources

① k8s_audit — Kubernetes Audit Logs

觀察 K8s API server 的審計日誌。能抓到所有對 API 的呼叫—— kubectl exec 進 pod、建立 ClusterRoleBinding、修改 ConfigMap… 這是偵測 K8s 內部威脅的關鍵 source。

yaml · 範例 k8s_audit rule
- rule: Attach to cluster-admin Role
  desc: Detect any role binding to cluster-admin
  condition: kevt and rolebinding and rolebinding_subject="cluster-admin"
  output: >
    ClusterRole/Role binding to cluster-admin
    (user=%ka.user.name binding=%ka.target.name)
  priority: WARNING
  source: k8s_audit
  tags: [k8s, mitre_privilege_escalation]

② aws_cloudtrail — AWS CloudTrail

持續輪詢 S3 bucket 中的 CloudTrail logs。能觀察 IAM、EC2、S3、Lambda 等 API。 典型偵測：root account 登入、Console 異常地理位置、CloudTrail 自身被停用。

③ okta — Identity Events

輪詢 Okta System Log API。能抓 MFA bypass、suspicious login、admin 操作。 需要 Okta API token。

啟用 k8saudit plugin（範例）

values.yaml · k8saudit plugin
falco:
  load_plugins: [k8saudit, json]
  plugins:
    - name: k8saudit
      library_path: libk8saudit.so
      init_config:
        ""
      open_params: "http://:9765/k8s-audit"   # 或 file path
    - name: json
      library_path: libjson.so
      init_config: ""

  rules_files:
    - /etc/falco/falco_rules.yaml
    - /etc/falco/k8s_audit_rules.yaml         # 來自 plugins repo

services:
  - name: k8saudit-webhook
    type: NodePort
    ports:
      - port: 9765
        nodePort: 30007
        protocol: TCP

然後在 K8s API server 加上 audit policy webhook 指向 http://<node>:30007/k8s-audit。 生產環境 EKS/GKE/AKS 的接法略不同，詳見 Ch.08 · Specific Environments。

3.6Dropped Events（事件流失）

當 syscall 量超過 Falco 處理速度，kernel 端的 ring buffer 會滿，事件被丟棄。這是生產環境最常見的問題。

怎麼發現有 drop

Falco 啟動 log 與定期狀態 log 會印 dropped count：

bash · 觀察 drop
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco | \
  grep -i "drop"

# 期望輸出：
# Detected 0 dropped events     ← OK
# Detected 12345 dropped events ← 嚴重，需要調校

常見原因與對策

原因對策對應 config
規則太多、太複雜 啟用 base syscall set；停用不必要的 rule base_syscalls.custom_set
ring buffer 太小 放大 buffer engine.kind.modern_ebpf.cpus_for_each_buffer
單一 buffer 應對多 CPU 多 buffer 並行 同上
I/O 密集 workload 排除 I/O 密集 syscall base_syscalls.repair
CPU 不夠 升 limit / pin 到性能 core k8s resources / nodeSelector

action on drop（drop 時要做什麼）

Falco 提供四種 drop action：

falco.yaml · syscall_event_drops
syscall_event_drops:
  threshold: 0.1                # 1 分鐘內 drop 比例超過 10% 就觸發
  actions:
    - log                       # log 一筆訊息
    - alert                     # 產出 falco alert (priority: critical)
    # - exit                    # 退出 process (慎用！會觸發 pod restart)
    # - ignore                  # 不做事
  rate: 0.03333                 # token bucket 補充速率（每秒）
  max_burst: 1                  # token bucket 容量
💡
實務建議：生產環境同時開 log 與 alert，把 drop 視為一級告警。 不要用 exit，會在 noisy node 上造成 pod 不斷重啟。 drop 調校細節見 Ch.09 · SRE 維運手冊。

3.7進階：Base Syscalls 與最小化集合

Falco 預設追蹤幾百種 syscall，但實際上只有部分被 default rules 用到。 透過 base_syscalls 把追蹤集合縮到最小，能大幅降 CPU 與 drop 率。

falco.yaml · 最小化 syscall 集合
base_syscalls:
  # repair: 自動修補你 rule 需要但沒列的 syscall
  repair: true

  # custom_set: 額外要包含的 syscall
  custom_set:
    - execve
    - execveat
    - openat
    - openat2
    - open
    - connect
    - accept
    - accept4
    - setns
    - setuid
    - setgid

repair: true 是新手友善的選項——它會分析載入的 rules，自動補上必要 syscall。 手動列 custom_set 適合知道自己在做什麼的進階用戶。

查看目前載入的 syscall 集合

bash · 查看載入的 syscalls
kubectl exec -n falco $(kubectl get pod -n falco -l app.kubernetes.io/name=falco -o name | head -1) \
  -c falco -- falco --list-syscalls

3.8本章心智模型

  • Falco 的 event 來自兩大世界：kernel syscalls（用 driver）與 plugin events（用 .so）。
  • Driver 三選一，實務只選 Modern eBPF。其他兩個各有遺留場景。
  • Container plugin 是讓 alert 帶 k8s context 的關鍵，務必裝。
  • Plugin events 讓 Falco 從「容器安全」擴展為「雲端全棧 detection」。
  • Dropped events 是生產第一大殺手——監控、調校 base_syscalls 與 ring buffer。
