4.1Rule 的三要素

每條 Falco rule 都是一個 YAML object，至少包含 rule、condition、output、 priority 四個必填欄位。理解這個最小結構，後面所有變化都圍著它轉。

yaml · 最小可用 rule
- rule: Shell in Container
  desc: 在容器內偵測 shell 啟動，可能是攻擊者進入容器的訊號
  condition: spawned_process and container and proc.name in (shell_binaries)
  output: >
    Shell spawned in container
    (user=%user.name container=%container.name shell=%proc.name
     cmdline=%proc.cmdline parent=%proc.pname)
  priority: WARNING
  tags: [container, shell, mitre_execution, T1059]
  source: syscall

欄位逐一解析

欄位必填說明
rule✓規則名稱（大寫開頭，首字母大寫）
desc✓人類可讀的描述，建議寫成 2-3 句
condition✓布林運算式，true 時觸發
output✓alert 文字模板，可嵌欄位
priority✓嚴重度（Emergency~Debug）
tags建議分類標籤；常用 MITRE ATT&CK ID
source建議來源 source（預設 syscall）
enabled選true/false；v0.37 後建議改用 override
exceptions選例外清單，見 4.8 節
override選覆寫現有 rule，見 4.7 節
💡
Style 慣例：規則名首字母大寫並用空格分隔（Shell in Container）； macros 與 lists 全小寫並用底線（shell_binaries、spawned_process）。 這不是強制，但官方所有 rules 都遵循。

4.2Condition 語法深入

Condition 是布林運算式，由欄位、運算子、值三者組成， 可用 and or not 與括號組合。

基本結構

yaml · condition 基本範例
condition: >
  evt.type = execve
  and container.id != host
  and proc.name in (bash, sh, zsh)
  and not user.name = root

常用運算子

運算子用途範例
= / !=等於 / 不等於user.name = root
< > <= >=數值比較fd.num > 1024
in在 list / set 中proc.name in (bash, sh)
contains字串包含子字串fd.name contains "passwd"
startswith字串起始於fd.name startswith "/etc/"
endswith字串結尾於fd.name endswith ".sh"
pmatch路徑前綴匹配（高效）fd.name pmatch (/etc, /usr/bin)
intersects兩 set 有交集ka.target.subjects intersects (...)
exists欄位有值container.id exists
✓
效能建議：startswith 與 endswith 比 contains 快。 多個前綴比對改用 pmatch（內部用 trie，O(log n)）。能用 = 就不用 contains。

欄位 (Fields) 分類

Falco 提供數百個欄位，可分幾大類：

類別常用欄位用途
事件evt.type, evt.time, evt.cpu哪種 syscall、何時發生
程序proc.name, proc.cmdline, proc.pname, proc.aname[N]程序資訊與祖先鏈
使用者user.name, user.uid, user.loginuid觸發者身分
檔案描述子fd.name, fd.type, fd.directory開檔 / 網路連線
檔案路徑fs.path.name, fs.path.source, fs.path.targetv0.36+ 統一路徑欄位
網路fd.sip, fd.sport, fd.sip.name對端 IP/port、反解 DNS
容器container.id, container.image.repository, container.name容器資訊
K8sk8s.ns.name, k8s.pod.name, k8s.pod.label.XK8s context
K8s Auditka.verb, ka.target.resource, ka.user.nameplugin: k8saudit 專用
能力 (caps)thread.cap_effective, thread.cap_permittedLinux capabilities

完整欄位清單見 Ch.11 · Reference 或官方 supported-fields。

路徑欄位：fs.path.*（v0.36+）

過去寫路徑相關 rule 很痛——open 用 fd.name、rename 用 evt.args、 mkdir 又不一樣。v0.36 統一引入 fs.path.* 系列欄位，同一個 rule 就能涵蓋多種 syscall。

yaml · 統一路徑欄位範例
- rule: Modify Files Below /etc
  desc: 偵測任何對 /etc 下檔案的寫入、移動、刪除、symlink
  condition: >
    evt.type in (write, mkdir, rename, unlink, symlink, link, openat)
    and fs.path.name startswith "/etc/"
    and not proc.name in (apt, dpkg, yum, dnf, kubelet)
  output: >
    Modification below /etc
    (path=%fs.path.name syscall=%evt.type proc=%proc.name user=%user.name)
  priority: WARNING
  tags: [filesystem, mitre_persistence]

網域名稱解析：fd.sip.name

需要 rule 比對「連到了什麼網域」而不只是 IP 嗎？fd.sip.name（與 fd.cip.name / fd.rip.name / fd.lip.name） 會做反向 DNS lookup，把 IP 轉成主機名。

⚠️
注意：反解需要 Falco 看得到 getaddrinfo 等呼叫的結果（兩階段比對）， 所以對 IP-only 連線無效。詳見官方 fd-sip-name 文件。

Transformer（轉換器）

可在欄位上套用簡單函式，常用 %toupper(...)、%tolower(...)、%basename(...)：

yaml · 使用 transformer
condition: >
  evt.type = connect
  and tolower(fd.sip.name) endswith ".onion"

output: >
  Suspicious Tor connection
  (host=%toupper(fd.sip.name) cmd=%proc.cmdline)

4.3Macros 與 Lists：可重用的零件

寫 rule 寫到「condition 越來越長、好幾條 rule 重複同樣邏輯」時，就該把它抽成 macro 或 list。 這兩者是 Falco rules 的 DRY 工具。

List：值的集合

yaml · list 定義與使用
- list: shell_binaries
  items: [bash, sh, zsh, ksh, csh, tcsh, dash, ash]

- list: sensitive_files
  items:
    - /etc/shadow
    - /etc/passwd
    - /etc/sudoers
    - /root/.ssh/authorized_keys

# 使用
- rule: Read Sensitive File
  condition: >
    evt.type in (open, openat)
    and fd.name in (sensitive_files)
  output: ...
  priority: WARNING

Macro：可重用的子運算式

Macro 是一段 condition 片段，可在多個 rule 之間共用：

yaml · macro 定義與使用
- macro: spawned_process
  condition: evt.type in (execve, execveat) and evt.dir = <

- macro: container
  condition: container.id != host

- macro: shell_procs
  condition: proc.name in (shell_binaries)

# 使用——非常清爽
- rule: Shell in Container
  condition: spawned_process and container and shell_procs
  output: Shell spawned (proc=%proc.name container=%container.name)
  priority: WARNING

Macro vs List：何時用哪個？

情境用
「一群值」（檔名、process 名、IP 範圍）list
「一段邏輯片段」（含 condition + 運算）macro
「會被多條 rule 共用」都可，看內容
「想讓使用者覆寫」多用 macro（因為含邏輯）

巢狀引用

Macro 可以引用其他 macro，list 也可以；無限巢狀：

yaml · 巢狀引用
- list: shell_binaries
  items: [bash, sh, zsh]

- list: scripting_binaries
  items: [python, perl, ruby, php]

- macro: interactive_command
  condition: >
    proc.name in (shell_binaries)
    or proc.name in (scripting_binaries)

- macro: in_production_ns
  condition: k8s.ns.name in (production, prod-payment, prod-checkout)

- rule: Interactive Command in Production
  condition: spawned_process and container and interactive_command and in_production_ns
  ...

官方提供的「待覆寫」macros

官方 ruleset 為環境差異預留了幾個 macro，明確要求使用者覆寫。 最常見的有：

Macro用途預設值
user_trusted_containers允許 privileged 跑的容器很有限
user_known_shell_spawn_activities允許開 shell 的程式never_true
allowed_clear_log_files允許 truncate log 的工具never_true
known_ssh_ports允許的 SSH port22
user_known_write_below_etc_activities允許寫 /etc 的程式never_true

完整清單見官方 Macros to Override。

4.4Output 模板與欄位插值

Output 是 alert 顯示文字，用 %欄位名 嵌入 runtime 值。寫得好的 output 能讓 SOC 不用查兩次就知道發生什麼事。

基本插值

yaml · output 模板
output: >
  Suspicious shell launch
  (user=%user.name shell=%proc.name parent=%proc.pname
   container=%container.name image=%container.image.repository
   k8s_ns=%k8s.ns.name k8s_pod=%k8s.pod.name
   cmd=%proc.cmdline)

未設定的欄位

若某個欄位在當下事件中沒有值（例如非容器環境的 container.image.repository）， Falco 會顯示 <NA>。可用 transformer 改變顯示，但不能徹底隱藏。

Output 內也能用 transformer

yaml · output transformer
output: >
  Disallowed SSH Connection
  (cmd=%proc.cmdline conn=%fd.name
   user=%toupper(user.name) image=%container.image.repository)

Output 撰寫原則

  • 第一行先寫明發生什麼，括號裡才放 context。SOC 一眼掃 log 用
  • 包含觸發者（user / process）、對象（file / connection）、環境（container / k8s_ns）
  • 避免只放 %proc.pid——PID 對人類沒意義，但 cmdline 有
  • 不要太長——超過一行的 alert 在 Slack 上很難讀
💡
過去的舊寫法 %container.info 已棄用（v0.39 移除）。 改用具體欄位如 %container.id、%container.image.repository、%container.name。 若你看到舊範例還在用 %container.info，請改寫。

4.5Priority 與 Tags

Priority 決定告警的緊急程度與後續分流；Tags 用來分類、批次啟用/停用，以及對應 MITRE ATT&CK。

Priority 八等級對照（同 Ch.02）

Priority典型情境建議告警通道
EMERGENCY系統幾乎不能用PagerDuty + Phone
ALERT需立即處理PagerDuty
CRITICAL嚴重情境（root 異常）PagerDuty
ERROR錯誤或可疑Slack #security-alerts
WARNING需注意Slack #security-warnings
NOTICE應留意SIEM + 每日彙整
INFORMATIONAL一般訊息SIEM only
DEBUG除錯用勿在 prod 啟用

Tags：分類與管理利器

tags 是字串陣列，常見命名慣例：

  • 領域：container, network, filesystem, process, k8s
  • MITRE ATT&CK tactic：mitre_persistence, mitre_privilege_escalation, mitre_defense_evasion
  • MITRE Technique ID：T1059, T1098
  • Maturity：maturity_stable, maturity_incubating, maturity_sandbox, maturity_deprecated
  • 適用情境：host, workload, cloud
✓
實務用法：把 SOC 分析師關心的 tags（MITRE）放第一個，內部分流用的 tags 放後面。 在 falco.yaml 可用 tag 一鍵 enable/disable 整組 rules（見 4.9）。

4.6Default vs Local Rules 與載入順序

Falco 會依序載入多個 rules 檔，後載入的會覆蓋先載入的。理解載入順序，才能正確 override。

典型載入順序（falco.yaml）

falco.yaml · rules_files 順序
rules_files:
  - /etc/falco/falco_rules.yaml          # 1. 官方 default rules（勿動）
  - /etc/falco/falco_rules.local.yaml    # 2. 你的自訂 / override
  - /etc/falco/rules.d                   # 3. 其他額外 rule 檔（按字典序）

圖 4.1 · Rules 載入順序與覆蓋邏輯

Rule Matching 模式：first-match vs all

當多條 rule 都匹配同一個 event 時，Falco 預設只觸發第一個（first match wins）。 這是 v0.36 起可調的：

falco.yaml · rule_matching
rule_matching: first   # 預設；第一個 match 就停，效能好
# rule_matching: all   # 全部 match 都觸發；CPU 較高，適合稽核完整性要求

4.7Overriding（覆寫現有 rule）

99% 的客製化情境是「我想改一條官方 rule 的條件 / output / priority」， 而不是從零寫新 rule。這時用 override 區塊最乾淨。

⚠️
append 已 deprecated：過去常用的 append: true 將在 Falco 1.0 移除。 所有新 rule 一律改用 override。本節範例都採新語法。

Override 的三種模式

模式意義適用
append把內容加到原本欄位後面（針對 condition / output / tags）加例外
replace整個替換大改
extension僅特定欄位用少見

範例 1：在條件上加排除

yaml · 用 override 加排除
# falco_rules.local.yaml
- rule: Terminal shell in container
  override:
    condition: append
  condition: and not k8s.ns.name = ci-builders
  # 上面這句會被附加到原始 condition 後面變成：
  # (原始條件) and not k8s.ns.name = ci-builders

範例 2：完全替換 output

yaml · replace output
- rule: Terminal shell in container
  override:
    output: replace
  output: >
    [INTERNAL] Shell detected in container
    pod=%k8s.pod.name ns=%k8s.ns.name
    image=%container.image.repository user=%user.name
    cmdline=%proc.cmdline

範例 3：調 priority（降噪 / 升級）

yaml · replace priority
- rule: Terminal shell in container
  override:
    priority: replace
  priority: ERROR   # 從預設 NOTICE 升到 ERROR

範例 4：啟用 / 停用 rule

過去用 enabled: true 直接覆寫；v0.37 起會 warning。新寫法：

yaml · 啟用 disabled 的 rule
- rule: Some Default Disabled Rule
  override:
    enabled: replace
  enabled: true

範例 5：擴充 macro

yaml · override macro
# 加入你的可信容器
- macro: user_trusted_containers
  override:
    condition: append
  condition: >
    or container.image.repository startswith "myregistry.example.com/"
    or container.image.repository = "datadog/agent"

範例 6：擴充 list

yaml · override list
- list: shell_binaries
  override:
    items: append
  items: [pwsh, fish, nushell]
🚨
常見陷阱：append condition 時，原始 condition 與你加的之間會用空白接，運算優先序可能出乎意料。 若原始 condition 含 or，append and not X 可能只對最後一個 or 分支生效。 解法：用括號明確指定原 macro 邊界，或乾脆 replace 重寫。

4.8Exceptions（結構化例外）

Exceptions（v0.28+）是「允許清單」的官方做法。比起 and not ... 寫一堆排除條件， exceptions 更易讀、更易維護。

基本結構

yaml · exceptions 結構
- rule: Write below binary dir
  desc: 偵測寫入 /usr/bin、/usr/sbin、/bin、/sbin
  condition: >
    bin_dir and evt.dir = < and open_write
    and not package_mgmt_procs
  output: >
    File below a known binary directory opened for writing
    (user=%user.name file=%fd.name proc=%proc.name)
  priority: ERROR

  exceptions:
    - name: known_bin_writers
      fields: [proc.name, fd.name]
      comps: [=, contains]
      values:
        - [nginx, /usr/bin/nginx]
        - [apache2, /usr/sbin/apache2]
        - [docker-init, /usr/local/bin]

欄位解釋

欄位用途
name例外群組名稱，供 audit 與 override 用
fields要比對的 Falco field 清單
comps對應的運算子（= / in / contains / pmatch 等）
valuestuple 清單。每個 tuple 與 fields 一一對應

三種簡化寫法

官方支援幾種快捷方式來減少 boilerplate：

① comps 預設為 = 或 in

單一 field 不寫 comps 時，自動用 in；多 field 用 =：

yaml · 省略 comps
exceptions:
  - name: trusted_users
    fields: user.name
    values: [root_helper, ci_robot, deploy_bot]
    # comps 省略 → 等同 user.name in (...)

② 用 list 引用

把 values 改成 list 引用，方便管理：

yaml · 用 list 當 values
- list: trusted_image_repos
  items:
    - myregistry.example.com/prod
    - gcr.io/my-project

- rule: Some Rule
  ...
  exceptions:
    - name: trusted_images
      fields: container.image.repository
      comps: startswith
      values: trusted_image_repos     # 引用 list 名

③ 暫不給 values，留給之後覆寫

官方 rule 常先定義 exception schema，把 values 留空讓使用者填：

yaml · 兩階段定義
# 官方 falco_rules.yaml
- rule: Read sensitive file untrusted
  ...
  exceptions:
    - name: known_sensitive_file_readers
      fields: proc.name
      values: []                       # 預留

# 你的 local rules
- rule: Read sensitive file untrusted
  exceptions:
    - name: known_sensitive_file_readers
      values: [sshd, openvpn, my_app]  # 填入你的清單

Exceptions vs and not ...：何時用哪個

情境推薦原因
大量「允許清單」式排除exceptions結構化、可用 list、易增刪
邏輯複雜（OR/AND 組合）and not (...)布林表達自由
跨多 rule 重用macro + and notmacro 較重用
使用者要能輕鬆覆寫exceptions有明確的 name + values 介面

4.9Controlling Rules：批次啟停與分組管控

在 falco.yaml 用 rules.enabled_rules / rules.disabled_rules 與 rules.tags 可以不改 rule 檔本身、由 config 端控制誰啟用、誰停用。

用 rule 名稱

falco.yaml · 依名稱啟停
rules:
  - enable:
      rule: Run shell untrusted
  - disable:
      rule: Read sensitive file untrusted

用萬用字元

falco.yaml · 用 wildcard
rules:
  - disable:
      rule: "Read *"        # 停用所有 Read 開頭的 rule
  - enable:
      rule: "* shell *"     # 啟用所有名含 shell 的 rule

用 tags

falco.yaml · 依 tag 啟停
rules:
  - disable:
      tag: maturity_sandbox       # 停用所有 sandbox 等級 rule
  - enable:
      tag: mitre_persistence      # 啟用所有 persistence tactic 的 rule

命令列覆蓋

啟動 Falco 時可用 -T / -t 一次性覆蓋設定：

bash · CLI 覆蓋
# 只跑帶 container tag 的 rule
falco -t container

# 停用某 tag
falco -T maturity_sandbox

4.10從零撰寫 Custom Ruleset：完整流程

把上面所有元素整合起來，這節示範一個完整的「為公司微服務客製化偵測規則」的工作流。

情境

假設你有一組 K8s workload，命名空間 production，image registry myregistry.example.com/。 你想加偵測：

  1. 非 trusted image 跑進 production namespace
  2. 容器內執行了 curl（這些 image 不應該有 curl）
  3. 連線到非預期的外部網域

STEP 1 — 建立 lists 與 macros

custom-rules.yaml · 共用零件
# ============ Lists ============
- list: trusted_image_prefixes
  items:
    - myregistry.example.com/prod/
    - myregistry.example.com/baseline/
    - gcr.io/myproject/

- list: forbidden_tools
  items: [curl, wget, nc, ncat, netcat, socat, nmap, tcpdump]

- list: allowed_external_domains
  items:
    - api.stripe.com
    - hooks.slack.com
    - cdn.myapp.example.com

# ============ Macros ============
- macro: in_production
  condition: k8s.ns.name = production

- macro: trusted_image
  condition: container.image.repository startswith (trusted_image_prefixes)

- macro: outbound_connection
  condition: >
    evt.type = connect
    and evt.dir = <
    and fd.l4proto != icmp
    and fd.type in (ipv4, ipv6)

STEP 2 — 撰寫三條 rule

custom-rules.yaml · rules
# ============ Rule 1 ============
- rule: Untrusted Image in Production
  desc: 在 production namespace 偵測到非可信來源的 image
  condition: >
    spawned_process
    and in_production
    and not trusted_image
  output: >
    Untrusted image running in production
    (image=%container.image.repository pod=%k8s.pod.name
     ns=%k8s.ns.name proc=%proc.name)
  priority: CRITICAL
  tags: [container, supply_chain, custom, mitre_initial_access]
  source: syscall

# ============ Rule 2 ============
- rule: Forbidden Tool in Production
  desc: production 容器內執行了不應該存在的工具
  condition: >
    spawned_process
    and in_production
    and proc.name in (forbidden_tools)
  output: >
    Forbidden tool launched in production container
    (tool=%proc.name parent=%proc.pname cmd=%proc.cmdline
     pod=%k8s.pod.name image=%container.image.repository)
  priority: ERROR
  tags: [container, lateral_movement, custom, T1105]
  source: syscall

# ============ Rule 3 ============
- rule: Outbound to Unexpected Domain
  desc: production pod 連到了未在允許清單的外部網域
  condition: >
    outbound_connection
    and in_production
    and not fd.sip.name in (allowed_external_domains)
    and not fd.sip in (rfc_1918_addresses)
  output: >
    Unexpected outbound connection
    (dest=%fd.sip.name:%fd.sport proc=%proc.name
     pod=%k8s.pod.name)
  priority: WARNING
  tags: [network, exfiltration, custom, T1041]
  source: syscall

  exceptions:
    - name: allow_deps_during_startup
      fields: [proc.name, fd.sip.name]
      comps: [=, endswith]
      values:
        - [npm, ".npmjs.org"]
        - [pip, ".pypi.org"]

4.11Style Guide：撰寫規範要點

官方 Style Guide（適用 v0.36+）總結了多年實戰心得。沒遵循的 rule 在 PR 階段會被退； 遵循的 rule 也通常更快、更穩。

YAML key 推薦順序

  1. rule:
  2. desc:
  3. condition:
  4. output:
  5. priority:
  6. tags:
  7. 其他選用 keys（無特定順序）

命名規則

  • Rule：大寫開頭，空格分隔。例：Shell in Container
  • Macro / List：全小寫，底線分隔。例：kernel_module_load

Condition 效能要點

  • 一定包含 evt.type 篩選——是 Falco 內部 bucketing 的前提
  • 把 evt.type 放最前——讓 engine 能早期剔除無關事件
  • 正向 expression 為主——避免 evt.type != open 這種寫法
  • 排除條件擺最後——讓正向 filter 先做大量篩選
  • 用 and not 來否定正向子運算式，避免雙重否定
  • 能用 startswith / endswith 就不要用 contains
  • 不要混用太多無關的 evt.type，會吃 CPU

常見反例

yaml · 反例 vs 正例
# ❌ 反例
- rule: Bad Example
  condition: not user.name = root and evt.type = execve

# ✓ 正例
- rule: Good Example
  condition: evt.type = execve and user.name != root


# ❌ 反例：用 contains 比對前綴
- macro: in_etc
  condition: fd.name contains "/etc/"

# ✓ 正例：用 startswith
- macro: in_etc
  condition: fd.name startswith "/etc/"


# ❌ 反例：雙重否定
condition: not fd.snet not in (rfc_1918_addresses)

# ✓ 正例
condition: fd.snet in (rfc_1918_addresses)

4.12Rule Versioning 與 Maturity Framework

官方 ruleset 有自己的 semver（如 falco-rules-5.0.0），與 Falco binary 解耦。 每條 rule 還有 maturity level 標明成熟度。

四個 maturity 等級

Maturity意義建議用法
stable低 FP、廣泛驗證生產直接啟用
incubating較新但已測試生產 staging 試跑
sandbox實驗性內測用，預設 disabled
deprecated準備淘汰找替代方案

啟用對應 maturity 的 rules

falco.yaml · 依 maturity tag 控制
rules:
  - enable:
      tag: maturity_stable
  - disable:
      tag: maturity_sandbox
  - disable:
      tag: maturity_deprecated

Default ruleset 版本

本手冊對齊 default ruleset v5.0，與 Falco v0.43 同期發布。 透過 falcoctl 可拉到指定版本：

bash · 用 falcoctl 拉 rules
falcoctl artifact install falco-rules:5
falcoctl artifact list

4.13驗證與測試

寫完 rule 不能直接丟到 production。Falco 有幾個工具讓你在離線環境驗證 syntax 與效果。

1. falco --validate

bash · 驗證 syntax
falco --validate /etc/falco/falco_rules.local.yaml
# Ok: my-rules.yaml

falco --validate broken.yaml
# Error: ... (對應行號)

2. Dry-run 對歷史 capture 重播

用 capture feature（v0.42+）錄一段 .scap，然後對它跑 rule：

bash · capture + replay
# 錄製 1 分鐘
falco --capture-file=/tmp/sample.scap --capture-duration=60s

# 用同一份 scap 測試新 rule
falco -r my-new-rules.yaml -e /tmp/sample.scap

3. event-generator 觸發 default rules

bash · 全 rule 觸發測試
# 跑所有官方 default rule scenario
docker run -it --rm \
  falcosecurity/event-generator run syscall --all

4. CI 自動化（範例 GitHub Actions）

yaml · .github/workflows/falco-rules.yaml
name: Falco Rules CI
on: [pull_request]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Validate rules
        run: |
          docker run --rm \
            -v $PWD/rules:/rules:ro \
            falcosecurity/falco:0.43.1 \
            falco --validate /rules/custom-rules.yaml

5. IDE Support（flycheck）

官方 Emacs extension flycheck-falco-rules 提供寫 rule 時的即時 syntax 檢查。 VSCode 端目前沒官方 plugin，但社群有 YAML schema 可用。

4.14本章心智模型總結

  • Rule = condition（什麼算異常）+ output（怎麼說）+ priority（多嚴重）+ tags（怎麼分類）
  • 用 lists 與 macros 抽取共用零件，DRY 原則
  • 客製化優先順序：exceptions（加白名單）→ override（改現有）→ 自寫 rule
  • append: true 已 deprecated → 全改用 override
  • evt.dir 與 enter event 已 deprecated → 不要再寫
  • 寫 condition 時，evt.type 放最前、排除放最後，效能差很多
  • load 順序：falco_rules.yaml → local.yaml → rules.d/
  • 用 CI falco --validate、capture replay、event-generator 三層驗證
