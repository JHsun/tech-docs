12.1進階 Rule 撰寫技巧

幾個官方文件提到、但容易被忽略的進階主題。

特殊字元逃逸 (Escaping)

YAML 加上 Falco condition 的雙層解析，遇到特殊字元（單引號、雙引號、反斜線、空白、底線）容易踩坑：

yaml · 特殊字元逃逸範例
# ❌ 錯：含空白與引號的字串沒包好
condition: proc.cmdline contains rm -rf /tmp

# ✓ 對：用雙引號 + 整段
condition: proc.cmdline contains "rm -rf /tmp"

# 路徑含反斜線（罕見但 Windows path 場景）
condition: fd.name = "C:\\Users\\admin"

# 含單引號要 escape 或改用雙引號外層
condition: proc.cmdline contains "user='admin'"

# 含中文字元
condition: container.name = "我的服務"

FS Path 統一欄位（複習 Ch.04）

寫跨 syscall 的路徑 rule，一律用 fs.path.* 系列，而非個別 syscall 的 fd.name / evt.args。

yaml · 一條 rule 涵蓋多 syscall
- rule: Any Operation Below /etc
  desc: 涵蓋 open/mkdir/rename/unlink/symlink 等對 /etc 的所有操作
  condition: >
    evt.type in (openat, openat2, open,
                 mkdir, mkdirat,
                 rename, renameat,
                 unlink, unlinkat,
                 symlink, symlinkat,
                 link, linkat,
                 chmod, fchmod)
    and fs.path.name startswith "/etc/"
  output: >
    Op below /etc (syscall=%evt.type path=%fs.path.name
     source=%fs.path.source target=%fs.path.target
     proc=%proc.name)
  priority: NOTICE
  tags: [filesystem, fs.path, custom]

Domain Name 反解 (fd.sip.name)

v0.36+ 引入。給你寫「連到了哪個網域」而非「連到了哪個 IP」的能力。但有兩個重要限制：

  • 只在 connect 後才會解析——需要 Falco 看到對應的 getaddrinfo 或 gethostbyname 呼叫
  • 對 hardcoded IP 連線無效——攻擊者繞 DNS 直連 IP 你抓不到
yaml · 用 fd.sip.name 過濾
- rule: Connection to Crypto Pool
  desc: 偵測連到已知 mining pool
  condition: >
    evt.type = connect and evt.dir = <
    and (fd.sip.name endswith ".minexmr.com"
         or fd.sip.name endswith ".pool.supportxmr.com"
         or fd.sip.name endswith ".moneroocean.stream")
  output: >
    Mining pool connection
    (dest=%fd.sip.name:%fd.sport proc=%proc.name)
  priority: CRITICAL
  tags: [network, mitre_impact, T1496]

用 proc.aname[N] 抓 process 祖先

有時候你不在乎當下 process 是誰，而是它的祖父。例如：誰啟動了這個 shell？

yaml · ancestry 偵測
- macro: web_server_proc
  condition: proc.aname[2] in (nginx, httpd, apache2, node)

- rule: Shell from Web Server
  desc: web server 啟動 shell — 常見的 command injection 跡象
  condition: spawned_process and container and shell_procs and web_server_proc
  output: >
    Shell from web server (shell=%proc.name grandparent=%proc.aname[2]
     cmdline=%proc.cmdline pod=%k8s.pod.name)
  priority: CRITICAL
  tags: [shell, web, mitre_initial_access]

核心工具速覽

📦 falcoctlcore

Plugin / rules 的 package manager。從 OCI registry 拉 artifact、自動更新、管理本地版本。

已在 Ch.06 & Ch.08 深入介紹。repo

📡 falcosidekickrouting

把 Falco HTTP alert 扇出到 60+ 種下游（Slack、PagerDuty、Loki、SIEM…）。生產必裝。

已在 Ch.05 深入介紹。repo

🖥 falcosidekick-uivisualization

本地 web UI，即時看 alert 並提供搜尋、過濾。配 Redis 暫存歷史 alert。

適合：dev 環境快速查看、無需架 SIEM 的小團隊。repo

🧪 event-generatortesting

容器化的事件產生器，自動觸發 default rules 中的場景。用來：

  • 驗證部署後 Falco 正常運作
  • 壓力測試 rule engine 處理能力
  • 培訓 SOC 認識常見 alert
bash
# 觸發單一場景
docker run -it --rm falcosecurity/event-generator run \
  syscall.WriteBelowEtc

# 觸發所有場景
docker run -it --rm falcosecurity/event-generator run syscall --all

# K8s 場景（需 kubectl 權限）
docker run -it --rm \
  -v ~/.kube/config:/.kube/config:ro \
  falcosecurity/event-generator run k8saudit --all

repo

🦈 Stratosharkforensics

Wireshark 的 syscall 版本——用 Wireshark 介面分析 .scap capture 檔。

  • 事後鑑識：Falco 觸發 critical alert，錄製 capture，用 Stratoshark 深入分析
  • 支援 SocketShark 模式：即時觀察 syscall 流

stratoshark.org · repo

🌐 k8s-metacollectork8s

v0.41+ 引入的獨立元件。集中收集 K8s metadata（pod、deployment、namespace label）並推送給 Falco， 避免每個 Falco pod 都對 API server 發 query，大叢集省成本。

repo

📊 Falco Operatork8s

12.3SIEM 整合模式

把 Falco 串進 SOC 的 SIEM 是大型組織標配。下面是四種常見模式。

模式 A：Falco → falcosidekick → SIEM（直送）

最簡單。透過 falcosidekick 內建 outputs（Elasticsearch、Splunk HEC、QRadar、Sentinel…）直接送。

flowchart LR
    F[Falco] -->|HTTP JSON| S[falcosidekick]
    S -->|HEC| Splunk[Splunk]
    S -->|Bulk API| ES[Elasticsearch]
    S -->|Webhook| Sentinel[Azure Sentinel]

適合：< 1000 events/s、SIEM 端能直接收 JSON。

模式 B：Falco → 中介 queue → SIEM（解耦）

用 Kafka / NATS 當 buffer，下游慢不會壓力傳到 Falco。

flowchart LR
    F[Falco] --> S[falcosidekick]
    S -->|topic: falco-events| K[Kafka]
    K -->|consumer 1| Splunk[Splunk]
    K -->|consumer 2| DL[Data Lake S3/GCS]
    K -->|consumer 3| ML[ML pipeline]
    style K fill:#cffafe,stroke:#0891b2,color:#0c2b35

適合：高 throughput、多消費者、需 replay 能力。

模式 C：Falco → Loki/OTel collector → 多端

用 OpenTelemetry collector 處理 Falco log（從 stdout 收），轉發到多目的地：

yaml · otel-collector config
receivers:
  filelog:
    include:
      - /var/log/pods/falco*/falco/*.log
    operators:
      - type: json_parser
    start_at: beginning

processors:
  batch:
    timeout: 5s
  attributes:
    actions:
      - key: source
        value: falco
        action: insert

exporters:
  loki:
    endpoint: http://loki:3100/loki/api/v1/push
  splunk_hec:
    endpoint: https://splunk:8088
    token: ${SPLUNK_TOKEN}
  awss3:
    s3uploader:
      region: us-east-1
      s3_bucket: falco-archive

service:
  pipelines:
    logs:
      receivers: [filelog]
      processors: [batch, attributes]
      exporters: [loki, splunk_hec, awss3]

模式 D：Falco → Data Lake → 批次分析

為了長期保存 + 跑 ML/Threat hunting，把 alert 落地到 data lake：

flowchart LR
    F[Falco] --> S[falcosidekick]
    S -->|S3 output| S3[(S3 bucket
Parquet)]
    S3 --> A[Athena / Trino]
    S3 --> ML[ML training
Spark / Databricks]
    A --> H[Threat hunting
SQL query]

適合：合規長期保存（90~365 天）、需歷史 trend 分析。

12.4Adoption of Falco Rules in Production（最佳實踐）

官方 adoption 頁是寫給生產採用者的「政策建議」。本節整理重點。

採用前 vs 採用後

階段應做不應做
初部署跑全 default + 蒐 baseline第一天就大改 default rules
第 1~2 週分析 noise pattern大量 disable rules 求安靜
第 3~4 週加 exceptions 與 override直接改官方 rule 檔（會在升級丟失）
持續新環境/服務先在 staging 試把所有 priority 都當 critical

Maturity 規劃

不同 maturity 規則的對應策略：

  • maturity_stable → 預設啟用，期望低 FP
  • maturity_incubating → 啟用但密切觀察
  • maturity_sandbox → 預設關閉；在 staging 試
  • maturity_deprecated → 找替代方案，預設關閉

共享 custom rule 給社群

寫了好用的 rule？官方鼓勵分享！送 PR 到 falcosecurity/rules。 流程：

  1. 確認沒重複（搜現有 rule）
  2. 遵循 Style Guide (Ch.04 § 4.11)
  3. 提供 example trigger 與 expected alert
  4. 放適當的 maturity tag（新 rule 通常從 sandbox 起步）
  5. 等 maintainer review

12.5多叢集統一管理模式

當你管 10+ Kubernetes cluster，每個都跑 Falco，怎麼讓 rules / config 保持一致？

三層策略

flowchart TB
    A[Central git repo
falco-config] --> B[ArgoCD ApplicationSet]
    B --> C1[Cluster A: dev]
    B --> C2[Cluster B: staging]
    B --> C3[Cluster C: prod-us]
    B --> C4[Cluster D: prod-eu]
    C1 --> AGG[Central Aggregator
Loki / Splunk]
    C2 --> AGG
    C3 --> AGG
    C4 --> AGG
    AGG --> SOC[SOC view
cross-cluster]
    style AGG fill:#cffafe,stroke:#0891b2,color:#0c2b35

實作要點

  1. 單一 source of truth：把所有 rules / values 放一個 git repo，按環境分子目錄
  2. GitOps 散播：用 ArgoCD ApplicationSet 或 Flux Kustomization 一鍵 deploy 多 cluster
  3. 環境差異最小化：用 kustomize overlay 處理叢集 specific 設定
  4. 中央聚合 alerts：所有叢集 alerts → 同一個 Loki / SIEM，SOC 看 global view
  5. static_fields 標記叢集：每筆 alert 帶 cluster / region / env

ArgoCD ApplicationSet 範例

yaml · ApplicationSet
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: falco-multi-cluster
spec:
  generators:
    - list:
        elements:
          - cluster: prod-us-east
            url: https://k8s-prod-us-east.example.com
            env: prod
          - cluster: prod-eu-west
            url: https://k8s-prod-eu-west.example.com
            env: prod
          - cluster: staging
            url: https://k8s-staging.example.com
            env: staging
  template:
    metadata:
      name: falco-{{cluster}}
    spec:
      source:
        repoURL: https://github.com/yourorg/falco-config
        path: envs/{{env}}
        helm:
          valueFiles: [values.yaml]
          parameters:
            - name: falco.static_fields.cluster
              value: "{{cluster}}"
      destination:
        server: "{{url}}"
        namespace: falco
      syncPolicy:
        automated: { prune: true, selfHeal: true }

12.6與 CSPM / CNAPP 平台整合

商業 CSPM（Wiz、Orca、Lacework）/ CNAPP（Sysdig Secure、Prisma Cloud）通常需要 runtime detection 訊號。 Falco 是這類平台最常見的 OSS 上游。

典型整合方式

  • Sysdig Secure：用商業版 Sysdig agent（Falco 商業 fork），與 OSS Falco 高度兼容
  • Wiz：透過 webhook 收 falcosidekick 輸出
  • Prisma Cloud：原生支援 ingest Falco JSON alerts
  • SUSE NeuVector：與 Falco 互補（NeuVector 偏 enforcement，Falco 偏 detection）

OSS Falco vs 商業 Sysdig Secure

很多人把 Falco 與 Sysdig Secure 混為一談，其實 differences：

面向OSS FalcoSysdig Secure
授權Apache 2.0 開源商業
偵測引擎同樣 libsinsp 為基礎同樣 libsinsp 為基礎
規則庫~70 default rules~500+ Sysdig 規則 + ML
UI無（用 sidekick-ui）完整 SOC dashboard
Posture (CSPM)無有
Image scan無內建 Trivy 整合
合規報表需自製內建 SOC2/PCI/HIPAA 報表
SLA 支援社群24x7 commercial
💡
選擇建議：OSS Falco 對技術 team 足夠；若組織需要合規證明、SOC 等級服務、image-to-runtime 完整可視， 則需考慮 Sysdig Secure 或其他商業 CNAPP。兩者可以同時跑（OSS Falco for engineers, 商業版 for SOC）。

12.7心智模型總結

  • 進階 rule 重點：fs.path.*、fd.sip.name、proc.aname[N] 三大法寶
  • 生態系工具：falcosidekick (路由)、falcoctl (套件管理)、event-generator (測試)、Stratoshark (鑑識)、k8s-metacollector (擴展性)
  • SIEM 整合四模式：直送 / Kafka / OTel / Data Lake，依規模選
  • 多叢集用 GitOps + ApplicationSet 統一管理
  • OSS Falco 與商業 Sysdig Secure 共享同 detection engine，差別在規則庫、UI、合規、支援
