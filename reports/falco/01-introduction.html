1.2Falco 是什麼

一句話：Falco 是雲端原生執行期安全 (Cloud Native Runtime Security) 工具， 它「即時觀察 Linux 核心事件流」與「比對使用者撰寫的規則」，發現異常行為時發出告警。

它的三個核心動作

  1. 觀察 (Observe)：透過 eBPF probe 或 kernel module，攔截系統呼叫 (syscalls)、 以及來自 plugin 的雲端事件 (CloudTrail、K8s Audit、Okta…)。
  2. 豐富 (Enrich)：把 raw event 補上 container、Kubernetes pod、namespace、image 等 context。
  3. 告警 (Alert)：條件符合 rule 時，透過 stdout、HTTP、syslog 等 channel 送出 alert。

1.3Falco 不是什麼

比起認識「它能做什麼」，搞清楚「它不做什麼」更能避免誤用。

✓ Falco 做的事
  • 即時偵測異常行為 (detection)
  • 對 syscalls 與 cloud event 出 alert
  • 用 Kubernetes metadata 補強事件
  • 把 alert 轉發到外部系統
  • 可由 plugin 擴充新事件來源
✗ Falco 不做的事
  • 不阻擋 (no enforcement)——它只偵測，不殺 process
  • 不是 admission controller（那是 OPA/Kyverno 的工作）
  • 不掃 image（那是 Trivy/Grype 的工作）
  • 不做 IDS/IPS 網路封包深度檢測
  • 不取代 SIEM——它是 SIEM 的資料來源之一
⚠️
常見誤解：「Falco 會自動 kill 攻擊者的 process。」 它不會。Falco 是 detection-only。若需 enforcement，請看 Ch.13 · 同類工具比較中 Tetragon 一節，或結合 falcosidekick 與外部 webhook 做 incident response。

1.4Falco 在雲端原生安全棧中的位置

1.5Falco 由哪些元件組成

Falco 不是單一 binary 而是一套元件群。理解元件邊界，後續調校與排錯才能下對藥。

🖥️

Userspace 程式

就是 falco CLI 本身。負責讀 config、載入 rules、處理事件流、產出 alert。

⚙️

Configuration

falco.yaml——指定 driver、輸出 channel、規則檔路徑、metrics 啟用等。

🔌

Driver

把 syscall 從 kernel 傳到 userspace。Modern eBPF 為預設； legacy eBPF / kmod 仍可用但前者已 deprecated。

🧩

Plugins

動態載入的 .so 檔，擴充 event source 與 field。例如 container、k8saudit、cloudtrail。

📦

falcoctl

管理規則與 plugin 的 CLI 工具，從 OCI registry 拉 artifact，與 Falco 一起打包。

📜

Rules

YAML 撰寫的偵測邏輯。Falco 內建 default ruleset；本手冊 Ch.04 會深入教你怎麼寫。

1.6Falco 能偵測什麼

開箱即用的 default ruleset (v5.0) 涵蓋大部分常見的 container 入侵情境。以下是幾個典型例子。

容器與權限類

  • 容器內啟動 shell (sh、bash、zsh)
  • 使用 setns 切換 namespace（容器逃逸前兆）
  • 啟動了 privileged container 或掛載敏感目錄
  • 權限提升 (sudo、setuid binary 觸發)

檔案系統類

  • 寫入 /etc、/usr/bin、/usr/sbin 等系統目錄
  • 建立 symlink 指向敏感檔案
  • 改變敏感檔案的 owner 或 mode
  • 修改 shadow、passwd、SSH 相關設定

網路與程序類

  • 非預期的 outbound 連線（連到 IRC、Tor、礦池等）
  • 容器內執行 SSH client (ssh、scp、sftp)
  • 使用 execve 啟動可疑 binary
  • 修改 coreutils 或 login 相關工具

雲端 API 類（需 plugin）

  • AWS：透過 CloudTrail plugin 偵測 IAM 異常、root 帳號登入
  • Kubernetes：透過 k8saudit plugin 偵測 exec 進入 pod、配置變更
  • Okta：偵測異常登入位置、MFA bypass
✓
實務建議：第一次部署時，先用 default ruleset 跑 1-2 週、收集 noise， 然後再開始 tune。不要第一天就大改規則，那會掩蓋真正的 baseline。 詳見 Ch.09 · SRE 維運手冊 的「Production Adoption」一節。

1.7v0.43 重要變化（給已用過舊版的讀者）

若你之前用過 Falco 但已隔一段時間，以下這些變動值得特別注意。

變動影響建議行動
Legacy eBPF probe 標為 deprecated 未來版本將移除 遷移到 Modern eBPF（已是預設）
gVisor engine 標為 deprecated gVisor 整合將不再維護 若有用，評估改用其他方案或 ignore
gRPC API 整段 deprecated 原本透過 gRPC 拉 alert 的客戶端 改用 HTTP / falcosidekick
capture feature (新功能) 可錄製 .scap 檔做事後重播 排錯與測試 rule 的利器
drop-enter initiative 預設僅處理 syscall exit event，效能更好 若 rule 用了 evt.dir = >（enter 事件），會看到 warning
GPG key rotation (2026-01) DEB/RPM 簽章金鑰已輪替 舊節點需手動匯入新 key，否則 apt update 會失敗
Falco Operator 0.2.0 production-ready Kubernetes 部署多一種官方選擇 k8s 環境建議優先考慮，見 Ch.08
🚨
升級 chocking point：若你的舊節點是 2026-01-17 前安裝、且用 apt 或 yum 管理， 升級前必須匯入新 GPG key，否則 apt update 會因 signature 驗證失敗而中斷。 操作步驟見 Ch.08 · 安裝部署。

1.8心智模型總結

讀完本章，你心中應該已經能回答這幾個問題：

  • Falco 觀察 syscalls 與 plugin events，比對 YAML rules，產出 alerts。
  • 它 只偵測不阻擋。若要 enforcement，需搭配 falcosidekick + webhook 或改看 Tetragon。
  • 它在縱深防禦中位於 runtime 層，與 image scan、admission control、network policy 互補不重複。
  • 典型部署是 Kubernetes DaemonSet，每節點一個 pod；非 k8s 環境可直接裝在 host。
  • 核心元件：falco binary + falco.yaml + rules.yaml + driver + plugins + falcoctl。
