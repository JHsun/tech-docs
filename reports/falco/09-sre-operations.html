9.1SRE 視角的 Falco

Falco 對 SRE 而言不只是「安全工具」，更是跑在每個 production node 上的高敏感 daemon。 它與 kernel 緊密耦合，與 workload 共享資源，告警會吵醒 on-call。 把它當成 production-tier service 來對待。

Falco 的 SLO 設計

建議用三層 SLO 度量 Falco 的健康：

SLO定義目標
Availability有多少 % 時間 Falco 在處理事件99.9%
Event Processingdrop rate 低於 threshold 的時間比例99.5% < 0.1% drop
Detection Latency從 syscall 發生到 alert 抵達 SIEM 的延遲p99 < 30s

三個關鍵錯誤模式

  1. Silent failure：Falco 還活著但 driver 沒在工作 → 你以為有偵測，其實沒有
  2. Dropping：事件流失 → 偵測有 gap，攻擊可能漏掉
  3. Alert fatigue：太多 false positive → on-call 麻木，真威脅被忽略
🚨
最致命的問題是 silent failure——它沒有任何 alert（因為 Falco 自己不會 alert 自己）， 只能靠 metrics 偵測。所以 Ch.07 的四條核心 metric alert 是必設。

9.2監控 Falco 自身（SLO 實作）

把 Ch.07 的 metrics 落實成具體的 SLO 監控。

SLO 1：Availability

promql · availability
# 30 天滾動視窗
- record: slo:falco_availability:ratio_30d
  expr: |
    sum_over_time(up{job="falco"}[30d])
    /
    count_over_time(up{job="falco"}[30d])

# Burn rate alerting（28天 budget）
- alert: FalcoSLOFastBurn
  expr: |
    (
      sum(rate(up{job="falco"}[5m])) by (cluster)
      < 0.99 * count(up{job="falco"}) by (cluster)
    )
  for: 2m
  labels: { severity: critical }
  annotations:
    summary: "Falco availability SLO fast burn on {{ $labels.cluster }}"

SLO 2：Event Processing

promql · drop rate
- record: slo:falco_drop_rate:5m
  expr: |
    rate(falcosecurity_falco_n_drops_total[5m])
    /
    (rate(falcosecurity_falco_n_evts_total[5m]) +
     rate(falcosecurity_falco_n_drops_total[5m]))

- alert: FalcoDropRateHigh
  expr: slo:falco_drop_rate:5m > 0.001
  for: 10m
  labels: { severity: warning }
  annotations:
    summary: "Falco drop rate > 0.1% on {{ $labels.instance }}"
    runbook: "https://wiki/runbooks/falco-dropping"

SLO 3：Detection Latency

這個比較難用 metrics 直接量。實務做法是定期注入「測試 syscall」， measure 從觸發到 alert 出現在 SIEM 的時間：

bash · synthetic test (cronjob)
#!/bin/bash
# 每 5 分鐘跑一次，注入測試事件並 measure latency
TS=$(date +%s%N)
sudo touch /etc/falco_synthetic_test_${TS}

# 等 30 秒讓事件流經整個 pipeline
sleep 30

# 從 SIEM 查找這個 timestamp 的 alert
ELAPSED=$(curl -s "https://siem/api/search?q=falco_synthetic_test_${TS}" | \
  jq '.first_seen - ('${TS}' / 1000000000)')

# 推到 Prometheus pushgateway
echo "falco_synthetic_latency_seconds ${ELAPSED}" | \
  curl --data-binary @- http://pushgateway/metrics/job/falco-synthetic

9.3Troubleshooting Playbook

生產上最常遇到的六大問題，每個都附 symptom → diagnosis → fix 三段。

🚨 Problem 1 · Falco Pod 不停 CrashLoopBackOff
kubectl get pod -n falco → STATUS = CrashLoopBackOff

診斷：

bash · diagnose
kubectl describe pod -n falco <pod> | grep -A 10 "Last State"
kubectl logs -n falco <pod> -c falco --previous

# 常見訊息：
# "Failed to find a usable BPF probe" → driver 問題
# "Permission denied" → privileged 不足
# "rules content compilation error" → custom rules 語法錯

對策：

  1. BPF probe failed：kernel < 5.8 → 改用 kmod。設 driver.kind: kmod 並確認 driver-loader init container 跑成功
  2. Permission denied：DaemonSet 沒設 privileged: true，或被 PodSecurityPolicy / PSA 擋。檢查 securityContext
  3. Rules error：先 falco --validate 你的 custom rules；errors 會印行號
🚨 Problem 2 · 啟動 OK 但沒有任何 alert
pod Running，但故意 trigger 事件後 logs 沒 alert

診斷：

bash · diagnose
# 1. driver 真的有跑？
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco | \
  grep -i "Starting capture\|driver"
# 期望：Starting capture with modern_bpf driver

# 2. 規則有載入？
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco | \
  grep -i "Loaded \|Reading rules"

# 3. 事件有流入？看 metrics
curl -s http://localhost:8765/metrics | grep n_evts_total
# 若數字一直 0，driver 失效

對策：

  1. Driver 沒 attach：通常是 kernel feature 不足。換 driver kind
  2. 規則沒載入：檢查 rules_files 路徑、ConfigMap mount
  3. priority 過濾掉了：把 falco.priority 暫設為 debug 重啟看看
  4. 用 event-generator 驗證：kubectl run eg --image=falcosecurity/event-generator --restart=Never -- run syscall
🚨 Problem 3 · Dropping Syscall Events
log 出現 "Detected N dropped events"，N 持續增長

診斷層級：先量級分類

  • 偶發 < 0.01% — 多半是 burst，可忽略
  • 持續 0.1% ~ 1% — 需要調校
  • 持續 > 1% — 嚴重，可能漏威脅

對策（按順序試）：

  1. 啟用 base_syscalls.repair（自動最小化 syscall set）
  2. 停用 noisy rules：找出命中量極大的 rule，disable 或加 exception
  3. 放大 ring buffer：engine.kind.modern_ebpf.buf_size_preset: 6（預設 4）
  4. 多 buffer：cpus_for_each_buffer: 1（每 CPU 一個 buffer）
  5. 排除 noisy namespace：在 default rule 加 and not k8s.ns.name = noisy-ns
  6. 升 CPU limit：1000m 不夠就 2000m
values.yaml · 調 ring buffer
falco:
  engine:
    kind: modern_ebpf
    modern_ebpf:
      buf_size_preset: 6                # 1~10, 預設 4
      cpus_for_each_buffer: 1           # 每 CPU 一個 ring buffer
      drop_failed_exit: true            # 失敗的 syscall 不重要
🚨 Problem 4 · Alert flood（告警洪水）
某次部署後 alert 數量 100x 暴漲，Slack 被淹

診斷：

bash · 找罪魁
# 用 metrics 找命中最多的 rule
curl -s http://localhost:8765/metrics | \
  grep falcosecurity_falco_rules_matches_total | \
  sort -t' ' -k2 -nr | head -10

對策：

  1. 立刻止血：暫時 disable 該 rule（在 falcosidekick 端 minimumpriority 拉高，或 helm upgrade 加 rules.disabled_rules）
  2. 分析誤觸來源：找出 noisy 來自哪個 pod / image / process
  3. 加 exception 或 override：精準排除合法行為（見 Ch.04 § 4.7-4.8）
  4. 用 GitOps 提 PR：把調校放進 git，code review
🚨 Problem 5 · falcosidekick / Webhook 故障
Falco 有 alert 但 Slack / SIEM 沒收到

診斷：

bash · 順著管線查
# 1. Falco 端真的有送嗎？
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco | \
  grep -i "http_output\|webhook"

# 2. Sidekick 有收到嗎？
kubectl logs -n falco -l app.kubernetes.io/name=falcosidekick

# 3. Sidekick 送下游成功嗎？
kubectl logs -n falco -l app.kubernetes.io/name=falcosidekick | \
  grep -iE "error|fail|timeout"

對策：

  1. 網路：用 kubectl exec ... -- curl -v http://falco-falcosidekick:2801/ 測連通
  2. 下游 webhook URL 過期 / 撤銷：rotate webhook
  3. Rate limit：Slack/PagerDuty 有 rate limit；高 priority 走 PD、其餘走 SIEM
🚨 Problem 6 · Missing fields in alert
alert 中 container.* / k8s.* 全是 <NA>

原因：container plugin 沒裝、或沒能連到 container runtime socket

對策：

  1. 確認 collectors.containerd.enabled: true（或對應 runtime）
  2. 確認 socket 掛載：kubectl exec ... -- ls /run/containerd/containerd.sock
  3. K8s metadata：確認 collectors.kubernetes.enabled: true + SA 有 nodes/pods read 權限

9.4效能調校（Performance Tuning）

Falco 在大型 cluster 可能成為 CPU / 記憶體大戶。系統化調校能把資源使用降一個量級。

調校層級

flowchart TD
    A[效能問題] --> B{CPU or RAM?}
    B -->|CPU 高| C[查 syscall throughput]
    B -->|RAM 高| D[查 threads/containers cache]
    C --> C1[減 syscall set
base_syscalls]
    C --> C2[減 rule 數
disable noisy]
    C --> C3[exception 精簡 condition]
    D --> D1[限制 cached threads]
    D --> D2[限制 cached containers]
    C1 --> E[Verify with metrics]
    C2 --> E
    C3 --> E
    D1 --> E
    D2 --> E
    style E fill:#cffafe,stroke:#0891b2
圖 9.1 · 效能調校決策流

四大調校槓桿

① base_syscalls 最小化

最有效。default 監聽幾百個 syscall，多半用不到。

falco.yaml · base_syscalls
base_syscalls:
  repair: true        # 推薦：自動分析 rules 用到哪些 syscall

  # 或進階手動指定：
  custom_set:
    - execve
    - execveat
    - openat
    - openat2
    - connect
    - accept4
    - setns
    - setuid

② 停用 noisy rules

values.yaml · 停 noisy
falco:
  rules:
    - disable: { tag: maturity_sandbox }
    - disable: { rule: "Read sensitive file untrusted" }

③ Cache 大小

falco.yaml · cache 限制
engine:
  kind: modern_ebpf
  modern_ebpf:
    cpus_for_each_buffer: 2
    buf_size_preset: 4
    drop_failed_exit: true

④ NodeSelector pin 到效能 node

不是所有 node 都需要監控（例：dedicated build / batch node 可降 priority）。 用 taint / nodeSelector 控制 Falco DaemonSet 範圍。

調校後驗證

  1. 看 CPU：kubectl top pod -n falco
  2. 看 drop：curl /metrics | grep n_drops
  3. 看 alert 仍會觸發：跑 event-generator
  4. 對比 baseline：tune 前後跑同樣 workload 看 latency 變化
✓
實測經驗：啟用 base_syscalls.repair 通常能把 CPU 降 50-70%； 再加上停用 sandbox rules 與 noisy default rules，能再降 20-30%。 生產 baseline 應該是每節點 < 100m CPU、< 300Mi RSS。

9.5Production Adoption 策略

新部署 Falco 到生產 cluster 是 漸進過程，不是 day-1 切換。 下面是經過實戰驗證的 4 階段 rollout plan。

Phase 1（Week 1-2）— Observation only

  • 部署 Falco 到 staging cluster，跑全部 default rules
  • 所有 alert 只送 Loki/Elasticsearch，不送 Slack/PagerDuty
  • 收集 baseline noise：哪些 rule 最常觸發、誤觸來源

Phase 2（Week 3-4）— Tuning

  • 針對 baseline 結果寫 exceptions 與 override
  • 調 user_known_* 等待覆寫 macros
  • 停用 sandbox / 不適用 rule
  • 持續收集 alert volume，目標：critical/error < 5/day/cluster

Phase 3（Week 5-6）— Production rollout

  • 部署到 production cluster，仍只送 SIEM
  • 觀察 1 週的 alert pattern
  • 確認 SLO 達標（drop rate < 0.1%、CPU < 100m）

Phase 4（Week 7+）— Active response

  • 打開 Slack / PagerDuty 路由
  • 設定 priority 分流
  • 建立 SOC playbook for top 10 alert types
  • 進入 BAU 維運

name: Falco Rules CI
on:
  pull_request:
    paths: [ 'rules/**', 'envs/**' ]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Validate all rule files
        run: |
          for f in rules/*.yaml; do
            echo "Validating $f"
            docker run --rm -v "$PWD/$f:/rule.yaml:ro" \
              falcosecurity/falco:0.43.1 \
              falco --validate /rule.yaml
          done

      - name: Lint values.yaml
        run: |
          for f in envs/*/values.yaml; do
            helm template falco -f "$f" falcosecurity/falco | \
              kubeval --strict
          done

      - name: Replay test against capture
        run: ./tests/ci-validate.sh

9.7Noise Reduction 系統化方法

新部署 Falco 必經之路。沒做這步直接上 prod，第二天就會被 alert 洗到關機。

四步法

  1. Identify：用 metrics 找 top 10 rule by match count（一週數據）
  2. Analyze：每條 rule 抽 sample alert，分析觸發來源
  3. Decide：對每個 noise source 決定處理方式
  4. Apply：用 exception / override / disable 套用

決策矩陣

來源類型處理方式技術手段
合法系統工具（apt, kubectl）白名單override user_known_* macro
單一工作負載特例per-rule exceptionexceptions:
整個 namespace 無關add and not k8s.ns.nameoverride condition
整個 image 來源trusted_image_repositoriesoverride list
規則本身不適用停用rules.disable

抽樣分析的查詢（Loki）

logql · 找 top noisy
topk(10,
  sum by (rule) (
    count_over_time(
      {app="falco"} | json | __error__="" [7d]
    )
  )

SOC 收到 Falco alert 的標準動作

  1. Triage（5 分鐘）：看 rule、container、pod、command line。是否明顯 FP？
  2. Enrich（15 分鐘）：拉同 pod / node 周邊 alert、image scan 結果、相關 audit log
  3. Decide：FP（回饋 rule team）/ Possible（觀察）/ Confirmed（升級）
  4. Contain：confirmed → 隔離 pod / cordon node / 通知 owner
  5. Document：寫成 incident ticket，5w1h 紀錄

9.9合規舉證

SOC 2、ISO 27001、PCI-DSS、HIPAA 等稽核都會問「你有 runtime detection 嗎？」 Falco + 標準化證據蒐集 = 即時可用的合規舉證材料。

合規 mapping（高層）

框架條款Falco 對應證據
SOC 2CC7.1 detect anomalous eventsalert log + drop rate metrics
ISO 27001A.12.4 logging & monitoringSIEM 中的 Falco alerts
PCI-DSS 4.010.6 review of logs每日 alert 彙整報告
HIPAA164.312(b) audit controlsk8s_audit + syscall logs
NIST CSFDE.CM-1 monitoring整套 Falco 運作證據

三類稽核會要的證據

  1. Coverage（覆蓋率）：所有 production node 都跑 Falco
    → 用 kubectl get pods -n falco -o wide + DaemonSet desired vs ready
  2. Availability（可用性）：Falco 持續運作
    → Prometheus up{job="falco"} 30 天圖表
  3. Response（響應時效）：critical alert 在 SLA 內被處理
    → PagerDuty acknowledgement time / incident ticket 時間軸

自動生成合規 report

bash · 月報 cron
#!/bin/bash
# 每月 1 號跑，產出合規 evidence
MONTH=$(date -d "last month" +%Y-%m)

# 1. Coverage report
kubectl get ds falco -n falco -o jsonpath='{.status}' \
  > evidence/${MONTH}/coverage.json

# 2. Uptime（從 Prometheus）
curl -s "https://prom/api/v1/query_range?query=avg_over_time(up{job=\"falco\"}[30d])&start=...&end=..." \
  > evidence/${MONTH}/uptime.json

# 3. Alert summary（從 Loki）
logcli query '{app="falco"}' --since=720h --output=jsonl \
  | jq -s 'group_by(.rule) | map({rule: .[0].rule, count: length})' \
  > evidence/${MONTH}/alerts-summary.json

# 4. 上傳 evidence vault
gsutil cp -r evidence/${MONTH} gs://compliance-evidence/falco/

9.10災難復原與 BCP

Falco 自己掛了怎麼辦？所有偵測會 gap。需要設計快速恢復機制與 fallback。

失敗模式分析

失敗影響復原策略
單一 Falco pod crash該 node 短暫無偵測K8s 自動重啟
整個 namespace 損毀全 cluster 偵測停擺從 git 重新 sync（GitOps）
升級 break 大量 node大規模 gaphelm rollback
kernel 升級後 driver 不相容事件 0driver kind 切 kmod 應急
falcosidekick 掛alert 不送出但 Falco 仍跑2+ replica；Loki 透過 stdout 也能收
SIEM 滿 / 不可用長期儲存 gapsecondary forwarder（如 S3）

建議 RTO / RPO

  • RTO（恢復時間）：< 15 分鐘（Falco 重啟 / Helm rollback）
  • RPO（資料遺失）：< 5 分鐘（透過 sidekick 多目的地）

Backup 該備什麼

  • Custom rules（在 git，天然有 backup）
  • values.yaml（在 git）
  • Secret（webhook URL 等）— 用 sealed-secret / external-secrets
  • 歷史 alert（在 SIEM，依政策保存 90~365 天）

9.11On-call Runbook

把上面所有內容濃縮成一頁 on-call 速查。半夜被叫醒時翻這頁。

初步 triage 三問

  1. 這 alert 是 critical 嗎？ → 看 priority 與 tags
  2. 影響範圍：單一 pod 還是 cross-cluster？ → 看 k8s_ns / cluster 欄位
  3. 是 FP 嗎？ → 查 image、namespace 是否常見

10 分鐘標準動作

bash · oncall first 10 mins
# 1. 看 alert 全文
kubectl logs -n falco -l app.kubernetes.io/name=falco -c falco --tail=200 | \
  grep -i <rule_name>

# 2. 看相關 pod 的整體日誌
NS=<namespace>; POD=<pod>
kubectl logs -n $NS $POD --tail=300

# 3. 看該 pod 的部署來源
kubectl describe pod -n $NS $POD | head -50

# 4. 看周邊 Falco 事件（過去 30 分鐘）
logcli query '{app="falco"}' --since=30m | grep -i $POD

# 5. 若可疑：cordon node、隔離 pod
kubectl cordon <node>
kubectl label pod -n $NS $POD quarantine=true

# 6. 通知 SOC / 工作負載 owner
# 7. 寫 incident ticket

常見 FP（白名單前可確認的）

  • System update 期間的 "Write below /etc"（apt-get / yum）
  • kubectl exec 觸發 "Terminal shell"（從合法 user）
  • Logrotate 觸發 "Clear log"
  • cert-manager 寫 /etc/letsencrypt
