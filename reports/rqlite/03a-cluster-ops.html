CH. 12叢集基礎

DevOps Developer

第一部第 2 章你已經啟動過 3 節點叢集。本章帶你完整理解 rqlite 叢集的運作原則、實際運維中會遇到的各種狀況，以及最關鍵的災難復原流程。

📌 v10.0.0 版本說明

本批文件以 rqlite v10.0.0（2026-04-28 釋出）為對應版本。第一、二批以 v9.3.0 為基準的 API、shell、客戶端內容仍然有效（v10 沒有 breaking API 變更，也沒有改變 clustering 行為）。v10 主要變更：移除 -on-disk-path flag、新增內建 /console web app、Leader snapshot 解耦於 follower snapshot 串流。v9 升 v10 注意：不支援把 v10 節點 join 到 v9 叢集，必須整套升上去。

12.1 為什麼要組叢集（或不組）

單節點 rqlite 完全能用，許多人把它當作「網路化 SQLite」就跑單節點。但單節點掛了你就得重啟，沒有高可用。

組叢集得到的：

  • Fault tolerance（容錯）：部分節點掛掉系統仍在
  • High availability（高可用）：最少停機時間
  • 持續可用：意外故障時資料庫仍可服務

付出的代價：

  • Network latency：每次寫入要等 quorum 確認
  • 運維複雜度：多節點要管理
  • 寫入吞吐降低：相較單節點顯著降低

12.2 Quorum 與容錯：實用節點數

Raft 的鐵律：N 個節點的叢集，要有 (N/2)+1 個節點在線且能互相聯絡，叢集才能繼續服務寫入。

叢集 NQuorum容錯能力建議
110 節點單節點 / 邊緣 / 開發
220 節點無意義，不如單節點
321 節點最常見的生產配置
431 節點不如 3 節點，純粹增加成本
532 節點高可用需求
642 節點不如 5 節點
743 節點大規模 HA
954 節點極端 HA，operationally heavy
⚠ 為什麼偶數節點沒意義

4 節點叢集的 quorum 是 3，所以也只能容忍 1 節點掛掉 — 跟 3 節點一模一樣，但你多付 33% 硬體成本，且 leader 寫入時要等更多節點 ack。永遠用奇數節點：1、3、5、7、9。

節點太多也是負擔：每次寫入都要 quorum 確認，節點越多網路 round-trip 越多。實務上 3、5、7 是甜蜜點，9 已經偏多，超過就要考慮 read-only nodes 而不是繼續加 voter。

Read-only nodes 不算進 N

唯讀節點（non-voting）不參與 Raft 投票，不計入 N、不影響 quorum，可以無痛擴張到任意數量（詳見第 14 章）。

12.3 手動建立叢集（不用 auto-discovery）

三台機器 host1、host2、host3，每台都能解析到對方且能通訊。

Step 1: 啟動初始 leader（host1）

bash
# 在 host1 上跑
rqlited -node-id 1 \
        -http-addr host1:4001 \
        -raft-addr host1:4002 \
        ~/node

此時 host1 是個單節點叢集，它自選為 Leader。-http-addr 是 HTTP API port、-raft-addr 是 Raft 內部通訊 port。兩者都必須是其他節點可達的位址，因為節點 join 時會把它們廣播給對方。

Step 2: host2 加入

bash
# 在 host2 上跑
rqlited -node-id 2 \
        -http-addr host2:4001 \
        -raft-addr host2:4002 \
        -join host1:4002 \
        ~/node
📌 -join 可以指向任何節點

不必指向 leader。如果 host2 嘗試 join 的對象不是 leader，該節點會自動 redirect。也可以給多個 -join 位址（逗號分隔），rqlite 會依序嘗試直到成功。

Step 3: host3 加入

bash
# 在 host3 上跑
rqlited -node-id 3 \
        -http-addr host3:4001 \
        -raft-addr host3:4002 \
        -join host1:4002 \
        ~/node

重啟 vs 重新 join

  • 只是重啟一個既有節點：不需要再帶 -join，節點會從本地 Raft log + cluster config 恢復
  • 節點 ID 或 Raft 位址有變：必須帶 -join。Leader 會先移除舊紀錄，再加入新的
  • 都沒變：即使帶 -join 也會被 Leader 忽略（idempotent）

12.4 Node ID 與廣播位址

Node ID

  • -node-id 是任意字串，只要在叢集內唯一
  • 一旦選定，不應變更。改了會破壞叢集
  • 生產環境一定要顯式設定（不要靠自動產生）

監聽全網路介面：0.0.0.0

-http-addr 和 -raft-addr 可以設成 0.0.0.0:PORT 監聽所有介面。但此時必須額外設定 -http-adv-addr 與 -raft-adv-addr，因為節點要把實際可達位址廣播給其他節點，0.0.0.0 不是可達位址。

bash
rqlited -node-id 1 \
        -http-addr 0.0.0.0:4001 \
        -raft-addr 0.0.0.0:4002 \
        -http-adv-addr rqlite1.example.com:4001 \
        -raft-adv-addr rqlite1.example.com:4002 \
        ~/node

跨防火牆的場景（AWS EC2 等）

節點的 內部 IP 從外部不可達，必須走外部 IP / public hostname。同樣用 -http-adv-addr 與 -raft-adv-addr 廣播可達位址。

12.5 擴增與縮減叢集

擴增

任何時候都可以加新節點：挑一個從沒用過的 node ID、用 -join 指向叢集任一節點，新節點會自動拿到完整資料。

✅ 加新節點 ≠ 重平衡

rqlite 不分片（no sharding），所以加新節點不會「分配某些 row 到新節點」。新節點會拿到完整 SQLite 副本，跟其他節點一樣。

變更節點的 Raft 位址

節點重啟時可以換 Raft address。流程：傳入新位址 + -join。Leader 會先移除舊紀錄、再加入新的。

🚨 不能同時改所有節點的網路識別

因為更新 cluster config 本身需要 Raft consensus，而 consensus 需要至少 quorum 個節點能互相聯絡。如果你一次重啟全部節點且每個都換新位址，所有節點都聯絡不到「以前的對方」，叢集會 lock 住。每次只能改少數節點。

縮減

要從 3 縮到 1？不能直接關掉 2 個節點，因為剩下的單節點失去 quorum，整個叢集會卡住。正確流程：

  1. 從 leader 執行 .remove <node-id>，把要關的節點正式移除
  2. 關閉該節點
  3. 重複至剩下你要的節點數

12.6 移除節點

shell 操作

text
127.0.0.1:4001> .remove 2
Node removed

HTTP API

bash
curl -XDELETE http://host1:4001/remove -d '{"id": "2"}'

前提：叢集仍有 leader（有 quorum）。如果失敗節點已經破壞 quorum，.remove 也會失敗 — 此時要走第 12.9 節的災難復原流程。

關機時自動移除

啟用 -raft-cluster-remove-shutdown=true，節點收到 SIGTERM 等優雅停機訊號時，會先聯絡 leader 把自己移除、再退出。對 Kubernetes 等動態環境特別有用。

12.7 自動 reap 失聯節點

當節點失聯一段時間後自動移除：

Flag對象建議值
-raft-reap-node-timeoutvoting node保守：48h ↑
-raft-reap-read-only-node-timeoutread-only node30m ~ 2h
bash
rqlited -node-id 1 \
        -raft-reap-node-timeout=48h \
        -raft-reap-read-only-node-timeout=30m \
        data
⚠ Reap 機制的兩個重要規則
  • 必須設在每個 voter 上：因為任一 voter 都可能變 leader，-raft-reap-*-timeout 必須在「所有可能成為 leader 的節點」上設定一致。Read-only 節點上設也沒問題（會被忽略）
  • Leader 換人時，計時器歸零：新 leader 上任時，所有失聯計時重新算。所以實際 reap 時間可能比設定值更長

12.8 一般失效處理

節點 crash

直接重啟即可。節點會從本地 Raft log 接著跑，並從 leader 拉取錯過的 entry。

網路分區（network partition）

多數分區（majority partition）繼續服務；少數分區（minority partition）的節點變成 followers 但無法寫入。網路恢復後自動合併。

磁碟壞掉、節點無法挽救

  1. 用 .remove 從叢集移除該節點
  2. 替換硬體
  3. 用新的 node-id 重新 -join（不要重用舊 ID）

12.9 災難復原：peers.json

「多個節點同時死亡 + 失去 quorum」是最嚴重的情況。可能有資料遺失（因為部分 commit 資訊可能還沒同步出去）。

圖 12-2 · 失去 quorum 的災難復原決策樹

peers.json 格式

在每個要復原的節點的 data/raft/peers.json 中放入相同內容：

json
[
  {
    "id": "1",
    "address": "10.1.0.1:8300",
    "non_voter": false
  },
  {
    "id": "2",
    "address": "10.1.0.2:8300",
    "non_voter": false
  },
  {
    "id": "3",
    "address": "10.1.0.3:8300",
    "non_voter": false
  }
]
  • id：必須沿用原 node-id（無法變更）。可在啟動 log 中找到自動產生的 ID
  • address：Raft 位址（可改、可用 hostname）
  • non_voter：是否為唯讀節點，預設 false

步驟

  1. 停止所有節點
  2. 確認你不打算復原的節點是永久掉了（不能再回來）
  3. 在每個要復原的節點寫入相同的 peers.json
  4. 啟動所有要復原的節點
  5. 復原完成後，peers.json 會被 rename 成 peers.info（保留紀錄，不再觸發復原）
🚨 終極 fallback

如果 peers.json 復原失敗，最穩當的做法是：單節點復原 + 取備份 + 全新建立叢集。詳見第 19 章 Backup & Restore。

這個流程隱含的問題

復原過程會隱式 commit 所有未 commit 的 Raft log entries。這意味著：在故障前還沒被 quorum commit 的寫入，可能會在復原後出現在資料庫裡。對於關鍵業務資料這是隱憂，必須有定期備份當作 fallback。

🔵 開發者重點
  • 奇數節點（3、5、7）；偶數無意義
  • 客戶端打任何節點都行，writes 自動 forward
  • 節點數變多 ≠ 寫入更快（其實更慢）
🟡 DevOps / SRE 重點
  • 0.0.0.0 必配 -*-adv-addr
  • 動態環境啟用 -raft-cluster-remove-shutdown=true
  • reap timeout 保守設（voter 48h+，read-only 30m+）
  • 失去 quorum 走 peers.json 復原 — 定期演練
  • v10 不能 join v9 叢集，要整套升

CH. 13自動 Clustering

DevOps

手動 clustering 要一個個用 -join 指向 seed，部署腳本要區分「初始 leader」vs「後續節點」。自動 clustering 讓你同一個啟動命令套到所有節點，節點自己找對方、組叢集。對 IaC / Helm / Compose 部署友善度大幅提升。

13.1 核心特性：idempotent

✅ 所有 auto-clustering 模式都是 idempotent

如果節點已經是叢集成員（包含已是單節點），auto-clustering 的 flag 會被忽略，不會做任何事。這代表：

  • 部署時不必判斷「這是初次部署還是擴增」
  • 所有節點用同樣的命令
  • 節點重啟也沒事

13.2 Automatic Bootstrapping（已知節點位址）

最直接的自動模式。前提：你事先知道每個節點的 Raft 位址。

bash
# 三個節點通通用這個格式啟動
# 唯一差異：-node-id 和 -http-addr/-raft-addr 換成自己的

# 節點 1
rqlited -node-id=1 -http-addr=$HOST1:4001 -raft-addr=$HOST1:4002 \
  -bootstrap-expect=3 \
  -join=$HOST1:4002,$HOST2:4002,$HOST3:4002 data

# 節點 2、3 同樣模式
rqlited -node-id=2 -http-addr=$HOST2:4001 -raft-addr=$HOST2:4002 \
  -bootstrap-expect=3 \
  -join=$HOST1:4002,$HOST2:4002,$HOST3:4002 data

關鍵點

  • -bootstrap-expect=N：等到看到 N 個節點就一起 bootstrap
  • -join：列出全部節點的 Raft 位址（包括自己）
  • 每個節點的 -bootstrap-expect 和 -join 值必須一致
  • 之後想擴增？同樣命令再多跑一台 — 新節點會嘗試 join，自動成為 follower

Docker 範例

bash
docker run rqlite/rqlite \
  -bootstrap-expect=3 \
  -join=$HOST1:4002,$HOST2:4002,$HOST3:4002

13.3 DNS / DNS SRV 發現

不用事先傳 -join，節點透過解析一個 DNS hostname 學到對方位址。

DNS A records

建立 rqlite.cluster，A record 指向叢集中所有 IP：

dns
rqlite.cluster.  60  IN  A  10.0.1.1
rqlite.cluster.  60  IN  A  10.0.1.2
rqlite.cluster.  60  IN  A  10.0.1.3

啟動：

bash
rqlited -node-id=1 \
  -http-addr=$HOST1:4001 -raft-addr=$HOST1:4002 \
  -disco-mode=dns \
  -disco-config='{"name":"rqlite.cluster"}' \
  -bootstrap-expect=3 data

每個節點假設其他節點用相同的 Raft port（這裡是 4002）。

DNS SRV（節點 port 不同時）

bash
rqlited -node-id=$ID \
  -http-addr=$HOST:4001 -raft-addr=$HOST:4002 \
  -disco-mode=dns-srv \
  -disco-config='{"name":"rqlite.local","service":"rqlite-raft"}' \
  -bootstrap-expect=3 data

會去查 _rqlite-raft._tcp.rqlite.local 的 SRV records，從每筆紀錄拿到 host + port。Consul / etcd 能自動產生這類 SRV。

💡 K8s 天然搭配

K8s 的 headless Service（clusterIP: None）對 StatefulSet 自動提供 A records 與 SRV records。rqlite 在 K8s 部署的標準作法就是 -disco-mode=dns + headless service。第 16 章詳述。

13.4 Consul KV

用 Consul 作為協調中介。節點不必事先知道彼此，啟動後自動透過 Consul 找對方。

bash
rqlited -node-id $ID1 \
  -http-addr=$HOST1:4001 -raft-addr=$HOST1:4002 \
  -disco-key=rqlite1 \
  -disco-mode=consul-kv \
  -disco-config='{"address":"example.com:8500"}' data

運作機制

  • Leader 持續把自己的位址寫到 Consul KV
  • 新節點透過 Consul 讀 leader address → join
  • Leader 變更時自動更新 Consul：後續節點仍能找到新 leader
  • -disco-key 是 KV 的 prefix，多叢集隔離靠它

Docker

bash
docker run rqlite/rqlite \
  -disco-mode=consul-kv \
  -disco-config='{"address":"example.com:8500"}'

Consul 需要 HTTPS、ACL、自訂 timeout 等，完整 JSON schema 在 rqlite-disco-clients/consul/config.go。

13.5 etcd KV

幾乎與 Consul 一模一樣，只是 backend 改成 etcd：

bash
rqlited -node-id=$ID1 \
  -http-addr=$HOST1:4001 -raft-addr=$HOST1:4002 \
  -disco-key=rqlite1 \
  -disco-mode=etcd-kv \
  -disco-config='{"endpoints":["example.com:2379"]}' data

完整 schema：rqlite-disco-clients/etcd/config.go。

13.6 多叢集隔離與 disco-config 進階用法

多叢集共用 Consul / etcd

一個 Consul / etcd 可以協調多個 rqlite 叢集，靠 -disco-key 區分：

bash
# 叢集 A
rqlited -disco-key=cluster-a -disco-mode=consul-kv ...

# 叢集 B（同一個 Consul）
rqlited -disco-key=cluster-b -disco-mode=consul-kv ...

DNS 模式則用不同 domain name 區分。

disco-config 可以放外部檔

大型設定可放 JSON 檔，-disco-config 給檔案路徑而非 inline JSON：

bash
rqlited -disco-mode=consul-kv -disco-config=/etc/rqlite/consul.json ...

環境變數展開

JSON 字串內以 $ 開頭的字會自動展開為環境變數（避免在 command line 暴露秘密）：

json
{
  "address": "$CONSUL_ADDR",
  "token": "$CONSUL_TOKEN"
}

不同方式比較

-bootstrap-expect + -join✓—固定 IP、IaC
dns✗（用 hostname）DNSK8s headless
dns-srv✗DNS（含 SRV）異質 port、Consul DNS
consul-kv✗Consul已有 Consul 基礎建設

🔵 開發者重點
  • K8s 部署最便利：-disco-mode=dns + headless service
  • 所有節點同命令同 flag，idempotent
🟡 DevOps / SRE 重點
  • 每節點 -bootstrap-expect 必須一致
  • 多叢集靠 -disco-key prefix 隔離
  • $VAR 環境變數展開避免 secret 暴露
  • Read-only 節點不能 bootstrap（-bootstrap-expect 不能設 >0）

CH. 14唯讀節點（Read-only Nodes）

DevOps Developer

唯讀節點（又稱 non-voting node）是 rqlite 的 read scaling 機制。它持續接收 leader 的寫入串流並 apply 到本地 SQLite，但不參與 Raft 投票：不計入 quorum、不能選為 leader、不影響容錯計算。

14.1 用途與該不該用

⚠ 預設不要加

單一 rqlite 節點預設一致性下能處理數千 QPS 讀取。"Don't add read-only nodes unless you are sure you need them." 加了反而增加運維複雜度、leader 多了寫入串流的開銷。

真正需要 read-only nodes 的場景

  • 網路邊緣（network edge）：邊緣站到 voter 叢集的連線可能慢或斷續，本地 read-only 節點即使在斷網時仍能服務查詢（接受 stale data）
  • 地理分散讀取：把 read-only 節點放到不同 region，使用者就近查詢
  • 大流量分析型 query：把 heavy SELECT 隔離到專用節點，不影響 voter 寫入

14.2 啟用：-raft-non-voter

bash
rqlited -node-id=4 \
        -http-addr host4:4001 \
        -raft-addr host4:4002 \
        -join host1:4002 \
        -raft-non-voter=true \
        ~/node

加入流程與 voter 相同；移除流程也相同（.remove）。

🚨 read-only nodes 不能 bootstrap

啟動時設 -bootstrap-expect=N（N > 0）+ -raft-non-voter=true 會讓 rqlited 直接 exit。Bootstrap 必須由 voter 完成。

14.3 查詢一致性配合

read-only 節點收到查詢時，必須使用 level=none 或 level=auto。否則該節點會轉送到 leader — read-only 的意義就喪失了。

bash
# ✗ 錯：weak 會被 forward 到 leader
curl -G 'http://read-only-node:4001/db/query' \
  --data-urlencode 'q=SELECT * FROM foo'

# ✓ 對：none + freshness 控制 staleness
curl -G 'http://read-only-node:4001/db/query?level=none&freshness=5s' \
  --data-urlencode 'q=SELECT * FROM foo'

# ✓ 更簡單：用 auto，read-only 自動套 none
curl -G 'http://read-only-node:4001/db/query?level=auto&freshness=5s' \
  --data-urlencode 'q=SELECT * FROM foo'

第 9 章已有完整 freshness / freshness_strict 說明，重點：

  • freshness=Ns：節點距上次聯絡 leader 超過 N 秒就回錯，避免讀到極舊資料
  • freshness_strict：額外檢查最後接收到的資料是否在 N 內收到，需要時鐘同步

14.4 失效處理與自動 reap

read-only 節點失聯時，leader 會持續嘗試重連（與 voter 行為一致）— 但因為不參與投票，read-only 失效不影響 quorum，叢集寫入照常。

不想讓死掉的 read-only 一直霸佔 cluster config？啟用自動 reap：

bash
# 失聯 30 分鐘自動移除 read-only 節點
# （此 flag 設在 voter 上，read-only 不負責 reap）
rqlited -node-id=1 \
        -raft-reap-read-only-node-timeout=30m \
        data

    balance roundrobin
    option httpchk GET /readyz?noleader
    server edge1 edge-eu-1:4001 check
    server edge2 edge-eu-2:4001 check backup

注意 /readyz?noleader — read-only 節點本來就不可能是 leader，要用 noleader 才不會被 health check 永遠視為不可用。

🔵 開發者重點
  • 查詢 read-only 節點時務必加 ?level=none&freshness=Ns 或 ?level=auto

🟡 DevOps / SRE 重點
  • 不要為了「分散讀取」而盲加 read-only — 多數情境 weak 就夠快
  • 邊緣節點啟用 NTP 同步，避免 freshness_strict 失準
  • health check 用 /readyz?noleader
  • 啟用 -raft-reap-read-only-node-timeout 處理掉死掉的邊緣節點

💡 為何要有「不對 client 開放」的 service

節點啟動時還沒 ready（還在 join leader、catching up），不應被當作可服務的端點。但節點間發現需要彼此能解析出對方 IP，這時就不能等 ready。Headless service 列所有 Pod IP（含尚未 ready），用於 discovery；ClusterIP 只列 ready 的，用於 client。

yaml

  - "-http-addr=0.0.0.0:4001"
  - "-raft-addr=0.0.0.0:4002"

rqlite 透過解析 rqlite-svc-internal 拿到所有 Pods 的 IP，等到看見 3 個就 bootstrap。注意 bootstrap-expect=3 只影響「初次組叢集」，之後擴展不需要動它。

16.5 擴增與縮減

擴增

bash
# 3 → 9
kubectl scale statefulsets rqlite --replicas=9

新節點啟動時，-disco-mode=dns + -bootstrap-expect 的 idempotent 設計會讓它嘗試 join 既有叢集而非重新 bootstrap。不要改 -bootstrap-expect。

🚨 擴增的兩個前提
  • 現有叢集 healthy 且 leader 存在
  • DNS 正常運作（headless service 解析得出新 Pod）

否則新 Pod 可能變成「獨立的單節點叢集」 — 而不是 join 既有的，造成資料分裂。

縮減

絕對不要直接 --replicas=1（從 3 縮到 1），會失去 quorum，剩下的單一節點服務不了寫入。

正確做法二選一：

方法 1：手動逐個移除

  1. scale down 一個（如 3 → 2）
  2. 用 .remove <node-id> 從 leader 顯式移除剛被砍的節點
  3. 確認叢集 healthy，再繼續

方法 2：啟用自動移除（推薦）

啟動時加 -raft-cluster-remove-shutdown=true。K8s 砍 Pod 時會送 SIGTERM，rqlite 收到後自動聯絡 leader 把自己移除、再退出。

啟動與驗證

bash
docker compose up -d

# 等 5 秒讓 cluster 形成
sleep 5

# 確認叢集狀態
curl -s localhost:4001/nodes | jq
# 預期看到 3 個節點，1 個 leader
⚠ Docker Compose 限制
  • 單機跑：失去「節點分散在不同機器」的容錯本質 — 整台機器掛全部都掛
  • 適合開發測試，不適合 production HA
  • 正式跑 cluster 用 K8s 或多台機器跑單獨的 docker
🔵 開發者重點
  • K8s 連線目標：rqlite-svc（自動選 ready Pod）
  • 開發環境 Docker Compose 跑 3 節點最方便驗證 cluster 行為
🟡 DevOps / SRE 重點
  • K8s 部署優先用 Helm chart
  • StatefulSet + 兩個 Service 是標準模式
  • StorageClass 用 fast SSD（如 gp3 / Premium SSD）
  • 啟用 -raft-cluster-remove-shutdown=true 配合 K8s
  • scale down 用方法 2（自動 remove），不要直接砍 replicas
