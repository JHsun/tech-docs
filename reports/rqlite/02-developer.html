CH. 05API 基礎

Developer Beginner

rqlite 的核心介面是 HTTP / JSON。本章完整解析三個主要端點、參數化查詢、回應格式、BLOB 處理、錯誤模式、PRAGMA 限制、以及進階的 Raft Index 追蹤與 forwarding 控制。

5.1 三大端點概觀

每個 rqlite 節點對外都暴露三個資料端點：

端點用途接受的 SQL推薦情境
/db/execute寫入INSERT / UPDATE / DELETE / DDL明確的寫入請求
/db/query讀取只允許 SELECT；透過此端點嘗試改變資料庫會回錯明確的讀取請求
/db/request混合（Unified Endpoint）讀寫皆可讀寫混在同一批；批次自動判斷
💡 該選哪一個端點？

官方建議：如果事先知道是讀還是寫，就用專屬端點（/db/execute 或 /db/query），因為你可以精準預期 response 格式，程式邏輯最穩。/db/request 的回應格式會依 statement 類型動態變化，需要在解析時多花一步檢查。

所有端點都可以送到叢集的任一節點，rqlite 會自動把寫入請求 forward 到 leader（詳見 5.12）。

5.2 /db/execute — 寫入

所有變更資料的請求都走這裡。Body 是 JSON array，每個元素是一個 SQL statement：

bash
curl -XPOST 'localhost:4001/db/execute?pretty&timings' \
  -H "Content-Type: application/json" \
  -d '[
    "CREATE TABLE foo (id INTEGER NOT NULL PRIMARY KEY, name TEXT, age INTEGER)"
  ]'

也可以把純 SQL 放在 plain text body（不推薦正式環境）：

bash
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: text/plain" \
  -d 'CREATE TABLE foo (id INTEGER NOT NULL PRIMARY KEY, name TEXT, age INTEGER)'

典型 INSERT 回應：

json
{
    "results": [
        {
            "last_insert_id": 1,
            "rows_affected": 1,
            "time": 0.00886
        }
    ],
    "time": 0.0152
}

time 單位為秒；?timings 啟用後才會回傳。?pretty 啟用後 JSON 會 pretty-print（適合人類除錯）。

⚠ plain/text vs JSON

plain/text 模式適合快速原型，但正式環境一律用 JSON。JSON 結構化避免 escape 錯誤、支援參數化、可以放多個 statement。

5.3 /db/query — 讀取

單一查詢用 HTTP GET，把 SQL 放在 query parameter q：

bash
curl -G 'localhost:4001/db/query?pretty&timings' \
  --data-urlencode 'q=SELECT * FROM foo'

預設回應格式（tabular）：

json
{
    "results": [
        {
            "columns": ["id", "name", "age"],
            "types": ["integer", "text", "integer"],
            "values": [
                [1, "fiona", 20]
            ],
            "time": 0.0150043
        }
    ],
    "time": 0.0220043
}
📌 declared type vs storage class

types 欄位回傳的是 SQLite 的 declared column type（CREATE TABLE 宣告的型別），不是storage class（實際儲存的物理型別）。SQLite 是動態型別系統，兩者可能不同。

POST 形式

查詢也可以用 POST + JSON body，這在需要批次或參數化時必要：

bash
curl -XPOST 'localhost:4001/db/query?pretty' \
  -H "Content-Type: application/json" \
  -d '["SELECT * FROM foo"]'

Associative response form

預設的 columns + values 結構效能好但解析麻煩；加上 ?associative 可改成「每個 row 是一個 dict」：

bash
curl -G 'localhost:4001/db/query?pretty&associative' \
  --data-urlencode 'q=SELECT * FROM foo'
json
{
    "results": [
        {
            "types": {"id": "integer", "age": "integer", "name": "text"},
            "rows": [
                { "id": 1, "age": 20, "name": "fiona"},
                { "id": 2, "age": 25, "name": "declan"}
            ],
            "time": 0.000173
        }
    ]
}

大多數語言可以直接把 rows 載入成 array-of-maps，省去人工 zip columns 跟 values 的步驟。

5.4 /db/request — Unified Endpoint

同一個請求中混合讀寫，rqlite 透過 SQLite 提供的 sqlite3_stmt_readonly() 自動判斷每個 statement 是讀還是寫。

bash
curl -XPOST 'localhost:4001/db/request?pretty&timings&associative' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name, age) VALUES(?, ?)", "fiona", 20],
    ["INSERT INTO foo(name, age) VALUES(?, ?)", "declan", 30],
    ["SELECT * FROM foo"],
    ["SELECT * FROM bar"]
  ]'

回應會混合「INSERT 結果」與「SELECT 結果」，並把存取不存在 table 的錯誤也包進來：

json
{
  "results": [
    { "last_insert_id": 1, "rows_affected": 1, "rows": null },
    { "last_insert_id": 2, "rows_affected": 1, "rows": null },
    {
      "types": { "age": "integer", "id": "integer", "name": "text"},
      "rows": [
        {"age": 20, "id": 1, "name": "fiona"},
        {"age": 30, "id": 2, "name": "declan"}
      ]
    },
    { "error": "no such table: bar" }
  ]
}

Unified Endpoint 支援：transactions、associative、Read Consistency、Parameterized Statements。
不支援：Queued Writes（?queue 在 /db/request 無效）。

5.5 參數化查詢（防 SQL Injection）

把 SQL 與值放在同一個 JSON sub-array 即啟用 prepared statement，rqlite 會做 binding，不會字串串接：

5.5.1 位置參數（?）

bash
# 寫入
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name, age) VALUES(?, ?)", "fiona", 20]
  ]'

# 查詢
curl -XPOST 'localhost:4001/db/query?pretty' \
  -H "Content-Type: application/json" \
  -d '[
    ["SELECT * FROM foo WHERE name=?", "fiona"]
  ]'

5.5.2 命名參數（:name）

bash
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name, age) VALUES(:name, :age)", {"name": "fiona", "age": 20}]
  ]'
🚨 一定要用參數化查詢

下面這個請求看起來像 SQL injection 攻擊：

bash
curl -XPOST 'localhost:4001/db/query' \
  -H "Content-Type: application/json" \
  -d '[
    ["SELECT * FROM foo WHERE name=?", "fiona; DROP TABLE foo"]
  ]'

但由於走 parameterized statement，"fiona; DROP TABLE foo" 整個被當成 name 欄位的字串處理，DROP TABLE 永遠不會被執行。如果改用字串拼接寫成 SELECT * FROM foo WHERE name='fiona; DROP TABLE foo'，雖然在語法上不會立刻 drop（單一 statement 仍只執行第一句），但這個模式在任何其他資料庫都是嚴重漏洞，應該完全避免。

5.6 回應格式選項

URL 參數效果使用場景
prettyJSON pretty-print人類除錯
timings每個 statement 與整體執行時間（秒）效能 profiling

5.7 Transaction 參數

加上 ?transaction，整個 request 中的所有 statement 會包在 implicit transaction 內；任一失敗整批 rollback：

bash
curl -XPOST 'localhost:4001/db/execute?pretty&transaction' \
  -H "Content-Type: application/json" \
  -d '[
    "INSERT INTO foo(name) VALUES(\"fiona\")",
    "INSERT INTO foo(name) VALUES(\"sinead\")"
  ]'
🚨 不要手動下 BEGIN / COMMIT

rqlite 不支援跨 HTTP request 的手動 BEGIN ... COMMIT / SAVEPOINT / RELEASE。「the behavior of a cluster if it fails while such a manually-controlled transaction is not yet defined」。一定要透過 ?transaction URL 參數來控制原子性。

5.8 BLOB 資料

寫入 BLOB

方式 1：X'..' 字面值（hex string）

bash
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d '[
    "CREATE TABLE foo (data BLOB) STRICT"
  ]'

# X'53514C697465' = "SQLite" 的 hex
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d "[
    \"INSERT INTO foo(data) VALUES(x'53514C697465')\"
  ]"

方式 2：參數化 byte array

bash
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(data) VALUES(?)", [83, 81, 76, 105, 116, 101]]
  ]'

讀取 BLOB

預設 BLOB 以 base64 string 回傳：

json
{"values": [["3q2+7w=="]]}

加上 ?blob_array 可拿到 byte array：

json
{"values": [[[222, 173, 190, 239]]]}
💡 STRICT table 消除歧義

建議 BLOB 欄位使用 STRICT table（CREATE TABLE foo (...) STRICT），這樣型別不會被 SQLite 動態轉換，與 ?blob_array 搭配能完全消除「base64 字串 vs 普通字串」的歧義。

5.9 錯誤處理

rqlite 的錯誤有兩層：

  1. HTTP 層：4xx / 5xx 表示請求格式或叢集層級錯誤
  2. SQL 層：即使回應 HTTP 200，個別 statement 仍可能失敗，會在 results[i].error 中標示

範例：

bash
curl -XPOST 'localhost:4001/db/execute?pretty' \
  -H "Content-Type: application/json" \
  -d "[\"INSERT INTO nonsense\"]"
json
{
    "results": [
        { "error": "near \"nonsense\": syntax error" }
    ],
    "time": 2.478862
}
⚠ 一定要檢查 results[].error

HTTP 200 不等於每個 SQL 都成功。客戶端必須 iterate results array，檢查每個元素有沒有 error 欄位，才能正確判斷整體成敗。

5.10 查詢 Timeout

預設 SQL 查詢沒有 timeout。可透過 ?db_timeout 設定：

bash
curl -XPOST 'localhost:4001/db/execute?db_timeout=2s' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name, age) VALUES(?, ?)", "fiona", 20]
  ]'

注意：db_timeout 是每個 SQL statement 的 timeout，不是整個 HTTP request。若 request 包含 5 個 statement、每個 timeout 2 秒，最壞情況可能跑 10 秒。

5.11 PRAGMA

SQLite 的 PRAGMA 大部分都能用。只讀 的 PRAGMA（例如 PRAGMA compile_options、PRAGMA foreign_keys）永遠安全。但以下 PRAGMA 會破壞 rqlite 的運作：

禁用 PRAGMA為什麼
PRAGMA journal_moderqlite 強制使用 WAL，不允許更改
PRAGMA wal_checkpointrqlite 獨佔 WAL 管理權
PRAGMA wal_autocheckpoint=N同上
PRAGMA synchronous=Nrqlite 自己管理 fsync 策略

rqlite 會在請求進入時 檢查 所有 PRAGMA，遇到禁用清單會直接回錯。

查詢編譯選項

bash
curl -G 'localhost:4001/db/query?pretty' \
  --data-urlencode 'q=PRAGMA compile_options'

可以看到該節點 SQLite 內建啟用了哪些 feature（FTS3、JSON1、RTREE、DBSTAT_VTAB、…）。對排查「為什麼某個 SQLite 函式不能用」非常有用。

5.12 Raft Index 與 Request Forwarding

追蹤 Raft Index

加 ?raft_index 可知道某個寫入落到哪個 Raft log entry：

json
{
    "results": [{ "last_insert_id": 3, "rows_affected": 1 }],
    "raft_index": 6
}

用途：你寫了一筆資料，想等到所有 follower 都套用後再讀；可以先拿到 raft_index，再 poll /status 確認 follower 的 applied_index ≥ 該值。

Forward Timeout

follower 把請求轉送給 leader 時，預設等 30 秒。可改：

bash
curl -XPOST 'localhost:4001/db/execute?timeout=2m' ...

停用 Forwarding：要 redirect 還是 forward？

預設 follower 會透明 forward 給 leader，客戶端不需要關心。但有些情況你會想拿到「leader 在哪」這個資訊（例如 client-side load balancer 想直接打 leader）。加 ?redirect 改成 HTTP 301：

text
HTTP/1.1 301 Moved Permanently
Location: http://leader-host:4001/db/query?...

Retry 機制

節點互相聯絡失敗時可自動重試，加 ?retries=N：

bash
curl -XPOST 'localhost:4001/db/execute?retries=2' ...

🟢 初學者重點
  • 三個端點：/db/execute（寫）、/db/query（讀）、/db/request（混合）
  • Body 永遠是 JSON array
  • ?pretty 是除錯好朋友
🔵 開發者重點
  • 一律使用 parameterized statement，不要字串拼 SQL
  • associative 形式對 application code 最友善
  • 檢查 results[i].error，HTTP 200 ≠ 全部成功
  • ?transaction 提供 atomicity；不要手動 BEGIN/COMMIT
🟡 DevOps / SRE 重點
  • ?db_timeout=5s 防止 runaway queries（預設無 timeout）
  • ?raft_index 是排查「為什麼某筆資料還沒在 follower 看到」的利器
  • 禁用 journal_mode / synchronous / wal_* PRAGMA
  • 透明 forward 簡化客戶端；?redirect 給需要可見性的場景

CH. 06連線到叢集

Developer DevOps

當你跑的是叢集（不是單節點），你的應用程式該怎麼連？這章涵蓋四種主流策略：static round-robin、DNS 發現、Load Balancer、API 自動發現。每種都有不同的權衡。

6.1 rqlite 如何路由請求

選策略之前必須先理解 rqlite 內部如何處理請求：

  • 叢集隨時都有單一 Leader，其他是 Follower（或 read-only）
  • 所有寫入必須由 Leader 處理（Raft 的本質）
  • 讀取預設也走 Leader，但可依 level 設定改變
  • Follower 收到寫入時會透明 forward 給 Leader，client 不需要知道誰是 leader
🎯 核心觀點

大多數連線策略下，client 可以打叢集中任一節點，rqlite 會做對的事。策略的差異主要在於：(1) client 怎麼發現節點，(2) 怎麼處理節點故障。

6.2 Static 清單 + Round-Robin

最簡單：寫死節點清單，輪流打。

python
# 概念性示意（用 requests 與 itertools.cycle）
import requests
from itertools import cycle

nodes = [
    "http://node1:4001",
    "http://node2:4001",
    "http://node3:4001",
]
ring = cycle(nodes)

def query(sql):
    for _ in range(len(nodes)):
        node = next(ring)
        try:
            r = requests.get(f"{node}/db/query", params={"q": sql}, timeout=5)
            r.raise_for_status()
            return r.json()
        except requests.RequestException:
            continue
    raise RuntimeError("all rqlite nodes unreachable")

優點：簡單、零依賴、不需額外權限。
缺點：叢集拓樸變更時必須手動更新清單。適合節點集合穩定的場景。

目前 Go 的 rqlite-go-http client 採用的就是這個策略。

6.3 DNS-based 發現

A records 多 IP

讓 DNS 名稱解析到多個 IP，client 端 DNS resolver 多半會 round-robin：

dns
rqlite.example.com.  60  IN  A  10.0.1.1
rqlite.example.com.  60  IN  A  10.0.1.2
rqlite.example.com.  60  IN  A  10.0.1.3

Kubernetes 的 headless Service（clusterIP: None）就是這個機制。Pod 的 IP 直接解析在 DNS 結果中，不經過任何 proxy。

SRV records

當節點 port 不一致時用 SRV record，可同時編碼 hostname + port。Consul / etcd 可自動生成 SRV records。

權衡：

  • Client 只需要記住一個 DNS 名稱
  • DNS TTL 短（10-60s）能快速跟上拓樸變化，但增加 DNS 查詢負擔
  • 需要對 DNS 有控制權，或在 K8s / 雲平台託管

6.4 Load Balancer

HAProxy、nginx、雲端 LB、Kubernetes Service 都可以。因為 rqlite 透明 forward 寫入給 leader，任何普通 LB 策略都能用，不需要 leader-aware。

HAProxy 範例設定

haproxy
frontend rqlite_front
    bind *:4001
    default_backend rqlite_back

backend rqlite_back
    balance roundrobin
    option httpchk GET /readyz
    server node1 10.0.1.1:4001 check
    server node2 10.0.1.2:4001 check
    server node3 10.0.1.3:4001 check

/readyz 是 rqlite 內建的 readiness probe，回 HTTP 200 代表節點 healthy 且可服務請求。健康檢查就用它。

權衡：

  • Client 只需要單一 endpoint，組態最簡單
  • LB 可自動把 unhealthy 節點移除，韌性最佳
  • LB 本身是 SPOF（single point of failure），通常要跑兩台 + floating IP / DNS failover
  • 多一跳（一個 extra hop），有小幅延遲

6.5 透過 /nodes API 發現

rqlite 暴露 /nodes 端點，回傳所有節點的位址與角色：

bash
curl -s 'localhost:4001/nodes?pretty&ver=2'
json
{
    "node1": {
        "api_addr": "http://10.0.1.1:4001",
        "addr": "10.0.1.1:4002",
        "reachable": true,
        "leader": true,
        "voter": true
    },
    "node2": {
        "api_addr": "http://10.0.1.2:4001",
        "addr": "10.0.1.2:4002",
        "reachable": true,
        "leader": false,
        "voter": true
    }
}

這也是 Go 的 gorqlite 採用的策略。連到一個 seed node、呼叫 /nodes 學習拓樸、追蹤誰是 leader、把寫入直接送 leader（省略 forwarding 那一跳）：

go

CH. 07批次寫入（Bulk Writes）

Developer

Bulk Writes 是 rqlite 提供的「一次寫多筆」機制。它的賣點不是語法糖，而是實際的效能 + atomicity 保證。

7.1 為什麼 Bulk 快

  • 節點間 round-trip 數量為 1（而不是 N）
  • 磁碟 fsync 數量為 1
  • leader 與 follower 之間的 commit 確認也只發生 1 次

7.2 Bulk 寫入語法

非參數化（純 SQL 字串）

bash

curl -XPOST 'localhost:4001/db/execute?pretty&timings' \

    ["INSERT INTO foo(name) VALUES(?)", "sinead"]
  ]'
🚨 不能混用

單一 Bulk request 中不能把參數化與非參數化 statement 混在一起。要嘛全部 parameterized，要嘛全部 raw string。

7.3 原子性與 Transaction

Bulk operation 在單一 Raft log entry 內，而 rqlite 每次只處理一個 log entry，所以Bulk 永遠不會與其他請求交錯。

不過同 batch 內前一個成功、後一個失敗的情況仍可能發生（沒加 ?transaction 時）。加上 ?transaction 就能保證 all-or-nothing：

bash
curl -XPOST 'localhost:4001/db/execute?transaction' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name) VALUES(?)", "alice"],
    ["INSERT INTO foo(name) VALUES(?)", "bob"]
  ]'

如果你已經有預先準備好的資料（SQLite binary 或 SQL dump），直接 restore 比一筆一筆寫快非常多。詳見第三部 第 19 章 Backup and Restore。

Python 範例：分批匯入 100,000 筆

python
import requests
import itertools

BATCH = 500
NODE = "http://localhost:4001"

def chunks(iterable, n):
    it = iter(iterable)
    while chunk := list(itertools.islice(it, n)):
        yield chunk

records = ((i, f"user-{i}", i % 100) for i in range(100_000))

for batch in chunks(records, BATCH):
    body = [
        ["INSERT INTO foo(id, name, age) VALUES(?, ?, ?)", *row]
        for row in batch
    ]
    r = requests.post(
        f"{NODE}/db/execute?transaction",
        json=body,
        timeout=30,
    )
    r.raise_for_status()
    results = r.json()["results"]
    errors = [r for r in results if "error" in r]
    if errors:
        raise RuntimeError(f"{len(errors)} failed: {errors[:3]}")

print("100,000 records inserted")

batch size 怎麼挑？從 500 開始實測。太大會撐爆 HTTP body / 增加單筆延遲；太小失去 bulk 效益。多數情境 500-2000 之間最佳。

CH. 08佇列寫入（Queued Writes）

Developer DevOps

Queued Writes 是 rqlite 提供的「以 durability 換 throughput」高速寫入模式。它讓 client 把單筆寫入快速送進來，rqlite 自己做 batching，再一次性寫入 Raft log。

8.1 概念與權衡

一般寫入流程：client → leader → append Raft log → quorum commit → fsync → 套用到 SQLite → 回應 client。整個流程的 critical path 上有一次 disk fsync + 一次 quorum 確認，這就是延遲下限。

Queued Writes 把流程改成：

  1. Client 送請求
  2. 節點把請求加入記憶體中的 queue
  3. 節點立刻回 200 OK + sequence_number（此時資料還沒進 Raft log）
  4. 背景：等到 batch size 滿、或 timeout 到，rqlite 把 queue 內全部請求合併成一個 Bulk write，正常走 Raft 流程

API 回 200 只代表已進 queue，不代表已 commit 到 Raft log。節點此時 crash，queue 內未 flush 的請求會掉。可透過調小 batch size / timeout 縮小視窗，但會降低 throughput。

8.2 啟用：加上 ?queue

bash
curl -XPOST 'localhost:4001/db/execute?queue' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name) VALUES(?)", "fiona"],
    ["INSERT INTO foo(name) VALUES(?)", "sinead"]
  ]'

回應：

json
{
    "results": [],
    "sequence_number": 1653314298877648934
}

注意 results 是空陣列—因為實際的 INSERT 還沒執行，沒有 last_insert_id 也沒有 rows_affected 可回。

🚨 不能與 /db/request 並用

Unified Endpoint（/db/request）不支援 Queued Writes。?queue 只能用在 /db/execute。

8.3 wait 與 timeout

需要確保「真的進到 Raft log 才回應」？加 ?wait：

bash
curl -XPOST 'localhost:4001/db/execute?queue&wait&timeout=10s' \
  -H "Content-Type: application/json" \
  -d '[
    ["INSERT INTO foo(name) VALUES(?)", "bob"]
  ]'

wait 會 block 到 queue 全部 flush 為止；timeout（預設 30s）超過則回錯。

使用情境：批次匯入結束時送一個 queue&wait 當作 barrier，確保前面所有 queued 寫入都已落地，再繼續下個步驟。

8.4 sequence_number

每個 queued 請求都會得到一個單調遞增的 sequence number。可透過 /status 查當前節點「已成功寫入 Raft 的最大 sequence number」：

bash
curl -s http://localhost:4001/status | jq .store.queue.sequence_number
📌 sequence_number 是 node-local

每個節點各自產生自己的 sequence 序列，無法跨節點比較。如果你的 client 會輪流打不同節點，記得 sequence 比較只在同一個節點內有意義。

8.5 佇列調校

啟動 rqlited 時的 flag 可以調整 queue 行為：

Flag意義
-write-queue-capacity=Nqueue 最大容量（記憶體上限）
-write-queue-batch-size=N達到此筆數立刻 flush
-write-queue-timeout=T超過此時間即使未滿也 flush
-write-queue-txflush 時用 transaction 包裝（預設 off）

具體預設值請執行 rqlited -h 確認你跑的版本。調校原則：

  • batch size 大、timeout 長 → throughput 高、視窗大、延遲高
  • batch size 小、timeout 短 → throughput 中、視窗小、延遲低

CH. 09讀取一致性（Read Consistency）

Developer DevOps

rqlite 提供五個讀取一致性等級：weak（預設）、linearizable、none、auto、strong。理解差異對正確使用和避免效能問題都很關鍵。rqlite 也跑過 Jepsen-style 測試（參考），可信度高。

9.1 為什麼讀取需要分等級

單看 Raft，讀取本身不需要共識（不改變狀態）。但如果不做任何檢查就直接讀本地 SQLite，會有兩個風險：

  1. 接到請求的節點雖然還在叢集中，但落後 leader
  2. 節點已脫離叢集，不再接收 Raft log 更新

不同等級就是「在這兩個風險與效能之間取捨」的不同策略。

9.2 weak（預設，幾乎你都該用這個）

流程：

  1. 節點檢查自己是否是 Leader（檢查 local state，極快）
  2. 是 → 直接讀本地 SQLite
  3. 否 → forward 給 Leader，等 Leader 做完 weak read 回傳

已知缺陷：節點以為自己是 Leader 時，可能其實已被 deposed（<1 秒視窗），這時讀到的資料可能 stale。技術上，weak 不是 linearizable。實務上極罕見。

✅ 大多數應用：用 weak

除非有明確的線性化（linearizable）需求，weak 是正確答案。

9.3 linearizable

實作 Raft dissertation 第 6.4 節的 "Processing read-only queries more efficiently"。流程：

  1. 節點記錄當前 Raft commit index
  2. 檢查 local state 是否是 Leader
  3. Leader 對 Followers heartbeat，等到收到 quorum 回應
  4. 關鍵：Leader 等到先前記錄的 commit index 對應的寫入已 apply 到 SQLite
  5. 執行讀取

每次讀取至少反映「在讀取發起後某個瞬間」的系統狀態，保證讀到最新 committed write。比 weak 慢（多了 quorum heartbeat），但 Raft log 沒被涉入，純粹網路延遲。

9.4 none + freshness

節點直接讀本地 SQLite，不做任何 leadership 或叢集連通性檢查。即使節點完全脫離叢集也能成功回傳。最快的查詢，但有 stale data 風險。

📍 restart 後 none 是救命符

節點重啟後，如果無法聯絡到 Leader，使用任何除了 none 以外的一致性等級都會回錯。none 讓你至少能在「斷網但有資料」的情境下提供服務。

freshness：限制最大 staleness

單純 none 沒有任何時間保證；加上 ?freshness=1s 後，節點會檢查「自己最後一次與 Leader 聯絡」距今不超過 1 秒，否則回錯：

bash
curl -G 'localhost:4001/db/query?level=none&freshness=1s' \
  --data-urlencode 'q=SELECT * FROM foo'

freshness_strict：更嚴格的 staleness

freshness 僅檢查「最後聯絡 Leader 時間」。freshness_strict 額外檢查「最後收到的資料是否在 freshness 區間內」。注意這依賴節點與 Leader 的時鐘同步（clock skew 會影響準確性）。

bash
curl -G 'localhost:4001/db/query?level=none&freshness=1s&freshness_strict' \
  --data-urlencode 'q=SELECT * FROM foo'
📌 freshness 規則
  • 節點是 Leader 時 → freshness 被忽略（Leader 永遠最新）
  • 非 none 等級 → freshness 被忽略
  • 設為 0 → 被忽略

典型搭配：read-only nodes + none + freshness，可以擴張讀取能力又控制 staleness。

9.5 auto（讓 rqlite 決定）

auto 不是真的等級，而是「請節點自選最合適的等級」：

  • 節點是 read-only（non-voting） → 選 none
  • 節點是 voter → 選 weak

適合 client 不想（或不能）事先知道目標節點類型的情境。可同時帶 freshness。

bash
curl -G 'localhost:4001/db/query?level=auto&freshness=1s' \
  --data-urlencode 'q=SELECT * FROM foo'

9.6 strong（測試專用）

讀取請求透過 Raft log 處理，確保所有 committed entries 都已 apply。代價：Leader 必須聯絡 quorum、寫一個 log entry、做 disk IO。

🚨 不要在 production 用 strong

官方明確說："Strong consistency has little use in production systems, as the reads are costly, consume disk space, and do not offer any benefit over Linearizable reads. Don't use Strong in production code."

strong 的唯一用途：測試「committed 與 applied 之間沒有差異」的場景。實務上一律用 linearizable 取代。

  • 監控 leader 變更頻率；頻繁切換時 weak 的 stale 風險變高
  • read-only 節點要設 NTP 同步，否則 freshness_strict 不準
  • linearizable 增加 leader 的 heartbeat 負擔，注意 CPU 與網路

CH. 10非確定性函式（Non-deterministic Functions）

Developer

rqlite 是 statement-based replication，意思是每個 SQL statement 通常會以原樣存進 Raft log，每個節點各自 replay。如果 statement 包含 RANDOM() 或 datetime('now') 這類非確定性函式，每個節點獨立執行會產生不同結果，叢集就會 diverge。

10.1 問題本質

考慮這個 statement：

sql
INSERT INTO foo (n) VALUES(random());

三個節點分別 replay 時，random() 各算各的：node 1 拿到 12345、node 2 拿到 67890、node 3 拿到 11111。結果三個節點的 SQLite 就不一致了，雖然 Raft log 完全一致。這違反 rqlite 的基本承諾。

10.2 rqlite 的改寫機制

第一個收到請求的節點會在寫入 Raft log 之前，掃描 SQL 中的非確定性函式，當下計算結果，替換成字面值，然後再進 log。所有節點看到的 log entry 都是相同的字面值。

哪些情況會改寫

  • 寫入請求（/db/execute）的所有 statement
  • 讀取請求（/db/query）且使用 strong read consistency
  • HTTP 請求沒帶 norwrandom 或 norwtime

哪些情況不會改寫

  • 非 strong 的查詢（weak / linearizable / none）— 因為查詢的結果不會寫進 Raft log
  • RANDOM() 出現在 ORDER BY（純排序用，不會產生確定性問題）
  • 明確指定 ?norwrandom / ?norwtime

10.3 RANDOM() 與 RANDOMBLOB(N)

會被改寫的範例

bash
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d '[
    "INSERT INTO foo(id, age) VALUES(1234, RANDOM())"
  ]'

# RANDOMBLOB 也會：
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d '[
    "INSERT INTO bar(uuid) VALUES(hex(RANDOMBLOB(16)))"
  ]'

顯式停用改寫

bash
curl -XPOST 'localhost:4001/db/execute?norwrandom' \
  -H "Content-Type: application/json" \
  -d '[
    "INSERT INTO foo(id, age) VALUES(1234, RANDOM())"
  ]'
# ⚠ 結果：各節點寫入不同 row，資料會 diverge

不會被改寫的範例（ORDER BY 內）

sql
-- 排序用途，每次結果順序不同，但插入的資料相同 → 不改寫
INSERT INTO foo (x) SELECT x FROM bar ORDER BY RANDOM();
⚠ ORDER BY RANDOM() 仍可能讓資料 diverge

雖然 rqlite 不改寫 ORDER BY RANDOM()，但這個 statement 在每個節點的插入順序不同，所以即使 x 的值集合相同，rowid 或表內順序可能不同。對某些應用而言這已經是不一致。如果你需要嚴格一致，避免在會修改資料的 statement 內使用 RANDOM()。

10.4 日期與時間函式

SQLite 的 datetime('now')、unixepoch('now') 等都是非確定性的（每次執行結果不同）。rqlite 在改寫時會把 'now' 替換成「節點收到請求的當下時間」字面值。

會被改寫

bash
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d "[
    \"INSERT INTO datetime_text (d1) VALUES(unixepoch('now'))\"
  ]"

停用

bash
curl -XPOST 'localhost:4001/db/execute?norwtime' \
  -H "Content-Type: application/json" \
  -d "[
    \"INSERT INTO datetime_text (d1) VALUES(unixepoch('now'))\"
  ]"

本來就確定的不會改寫

sql
-- 字面日期，已經確定，無需改寫
INSERT INTO datetime_text (d1) VALUES(date('2020-01-01'));

CURRENT_TIMESTAMP 等預設值的坑

🚨 column DEFAULT CURRENT_TIMESTAMP 會 diverge

如果 schema 寫 created_at DATETIME DEFAULT CURRENT_TIMESTAMP，當 INSERT 沒明確帶 created_at 時，每個節點 replay 該 INSERT 時會各自取自己的時間，導致資料不一致。rqlite 的改寫機制不能處理 column default。

解法：永遠在應用程式端明確產生 timestamp，把它放在 INSERT statement 中：

python
import time
ts = int(time.time())
requests.post("/db/execute", json=[
    ["INSERT INTO logs(msg, created_at) VALUES(?, ?)", "hello", ts]
])

11.2 Go: gorqlite（API 自動發現）

gorqlite 自動透過 /nodes 學習叢集拓樸、追蹤 leader、提供 database/sql 風格的 API。

安裝

bash
go get github.com/rqlite/gorqlite

完整 CRUD 範例

go
package main

import (
    "fmt"
    "log"

    "github.com/rqlite/gorqlite"
)

func main() {
    // 連線到 seed node；之後自動透過 /nodes 學叢集
    conn, err := gorqlite.Open("http://localhost:4001")
    if err != nil {
        log.Fatal(err)
    }
    defer conn.Close()

    // 1. 設定一致性等級（per-connection）
    conn.SetConsistencyLevel("weak")

    // 2. 建表（write 走 leader）
    _, err = conn.WriteOne(
        "CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT, age INTEGER)",
    )
    if err != nil {
        log.Fatal(err)
    }

    // 3. 參數化批次寫入
    results, err := conn.WriteParameterized([]gorqlite.ParameterizedStatement{
        {
            Query:     "INSERT INTO users(name, age) VALUES(?, ?)",
            Arguments: []interface{}{"alice", 30},
        },
        {
            Query:     "INSERT INTO users(name, age) VALUES(?, ?)",
            Arguments: []interface{}{"bob", 25},
        },
    })
    if err != nil {
        log.Fatal(err)
    }
    for i, r := range results {
        fmt.Printf("stmt %d: last_id=%d, rows=%d\n",
            i, r.LastInsertID, r.RowsAffected)
    }

    // 4. 參數化查詢
    rows, err := conn.QueryOneParameterized(gorqlite.ParameterizedStatement{
        Query:     "SELECT id, name, age FROM users WHERE age > ?",
        Arguments: []interface{}{20},
    })
    if err != nil {
        log.Fatal(err)
    }

    for rows.Next() {
        var id, age int64
        var name string
        if err := rows.Scan(&id, &name, &age); err != nil {
            log.Fatal(err)
        }
        fmt.Printf("%d %s %d\n", id, name, age)
    }
}

切換一致性等級（per query）

go
// 此查詢用 linearizable
conn.SetConsistencyLevel("linearizable")
rows, _ := conn.QueryOne("SELECT COUNT(*) FROM users")

// 切回 weak
conn.SetConsistencyLevel("weak")

11.3 Go: rqlite-go-http（thin client）

官方近期推的輕量版，提供最小抽象：盡量貼近 HTTP API，自帶 retry / fallback hosts，但不做 /nodes 自動發現。

安裝

bash
go get github.com/rqlite/rqlite-go-http

使用範例（簡化）

go
package main

import (
    "context"
    "fmt"
    "log"

    rqhttp "github.com/rqlite/rqlite-go-http"
)

func main() {
    // 多 host 做 client-side round-robin fallback
    client, err := rqhttp.NewClient([]string{
        "http://node1:4001",
        "http://node2:4001",
        "http://node3:4001",
    }, nil)
    if err != nil {
        log.Fatal(err)
    }

    ctx := context.Background()

    // 寫入
    execRes, err := client.ExecuteSingle(ctx,
        "INSERT INTO users(name, age) VALUES(?, ?)",
        "charlie", 28,
    )
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println("inserted, last_id=", execRes.LastInsertID)

    // 查詢
    qRes, err := client.QuerySingle(ctx,
        "SELECT id, name FROM users WHERE age > ?", 20,
    )
    if err != nil {
        log.Fatal(err)
    }
    for _, row := range qRes.Rows {
        fmt.Println(row)
    }
}

from fastapi import FastAPI

app = FastAPI()
conn = rqdb.connect_async(hosts=["127.0.0.1:4001"])

@app.on_event("startup")
async def startup():
    await conn.__aenter__()

@app.on_event("shutdown")

    await conn.__aexit__(None, None, None)

    await cur.execute("SELECT name, age FROM users WHERE id = ?", (user_id,))
    row = await cur.fetchone()

        return {"error": "not found"}
    return {"name": row[0], "age": row[1]}

11.6 Python: sqlalchemy-rqlite（ORM 整合）

把 rqlite 接到 SQLAlchemy ORM。對既有 SQLAlchemy app 平移特別有用。

安裝

bash
pip install sqlalchemy sqlalchemy-rqlite

使用

python
from sqlalchemy import create_engine, Column, Integer, String
from sqlalchemy.orm import declarative_base, sessionmaker

# rqlite:// 走 HTTP；rqlite+https:// 走 HTTPS
engine = create_engine("rqlite+http://localhost:4001/")
Base = declarative_base()

class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    name = Column(String)
    age = Column(Integer)

Base.metadata.create_all(engine)
Session = sessionmaker(bind=engine)

with Session() as s:
    s.add(User(name="alice", age=30))
    s.commit()
    for u in s.query(User).all():
        print(u.id, u.name, u.age)
⚠ ORM 與 rqlite 限制

SQLAlchemy 的某些 transaction pattern（begin() 上下文管理器）對應到 rqlite 的 ?transaction URL 參數，但跨多個 statement 的 explicit transaction（BEGIN ... COMMIT 自己控制）在 rqlite 是 undefined behavior。檢查 dialect 文件確認你的使用模式。

11.7 連線池與最佳實踐

共通建議

  • 連線復用：rqlite 客戶端基本上都基於 HTTP keep-alive。建立 connection / client 物件並在程式生命週期中重用，不要每個請求都重建
  • Timeout 永遠設：HTTP request timeout（client 側）+ db_timeout（server 側）兩者都該明確設定
  • Retry 策略：寫入失敗時可重試，但要注意非冪等寫入（如 INSERT 沒 unique constraint）重試可能造成重複資料；可用 INSERT OR IGNORE 或 ON CONFLICT 確保 idempotent
  • 錯誤分級：4xx（請求問題，重試無用）vs 5xx（leader 切換中，可重試）vs 200 + results[].error（SQL 錯誤，重試無用）

Idempotent 寫入範例

sql
-- 用 ON CONFLICT 確保重試安全
INSERT INTO users (id, name, age) VALUES (?, ?, ?)
ON CONFLICT(id) DO UPDATE SET name = excluded.name, age = excluded.age;

import asyncio
import rqdb

                "SELECT name FROM users WHERE id=?", (uid,)

            *(read_one(i) for i in range(1, 101))
