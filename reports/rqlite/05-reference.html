CH. 25設計與實作原理

Developer DevOps

rqlite 自 2014 年開始開發，至今超過 10 年。共識系統、API、自動 clustering、節點發現都經歷了重大演進。本章解析當前實作的設計決策，理解這些有助於更深入地調校與排錯。

每個子系統的職責：

  • HTTP API Layer：接收外部請求、處理 auth、CORS、TLS、URL 參數解析
  • Store Layer：路由邏輯（哪些 query 要 forward 到 leader、應用哪種一致性）
  • Raft Module：選舉、append log、quorum 確認、snapshot 觸發
  • SQLite Module：實際的 SQLite 引擎，rqlite 直接 link 進 binary（不需另裝）
  • CDC Subsystem（9.0+）：每個節點都記事件到本地 queue；只有 leader 對外發送

25.2 Raft 在 rqlite

rqlite 用 Hashicorp Raft 函式庫實作共識（5.0 起改用 Hashicorp Raft v1）。

Raft Log = Authoritative Record

Raft layer 永遠會建立一個檔案 — Raft log。它儲存所有 committed SQLite 命令，依執行順序。這個 log 是系統發生過的所有變更的權威紀錄。

有時 read-only queries 也會進 log（當你用 level=strong，雖然官方建議避免）。

所有節點以完全相同的方式 apply log entries，這是「為何每個節點的 SQLite 相同」的根本保證。

Statement-based Replication

rqlite 是 statement-based 而非 row-based replication：

  • 每個 SQL statement以原文形式進 Raft log
  • 每個節點 replay 該 statement → 套用到本地 SQLite
  • 因為「相同 SQL 在相同 SQLite 上產生相同結果」是確定性的，所有節點達到相同狀態

這個設計簡單，但需要處理非確定性函式（RANDOM()、datetime('now')）。rqlite 在第一個收到請求的節點上把這些函式預先計算成字面值，再進 log。詳見第 10 章。

讀取的多種模式

讀取不必進 Raft log（state 不變），所以可以走多種路徑：

  • weak：節點檢查自己是 leader → 讀本地 SQLite
  • linearizable：leader 對 quorum heartbeat、等之前的 entry apply 完成、再讀
  • none：完全跳過共識檢查，直接讀本地
  • strong：把讀也送進 Raft log（測試用）

25.3 SQLite 的特殊配置

rqlite 對 SQLite 做了兩個關鍵配置以最大化寫入效能：

  • WAL mode：而非預設 rollback journal
  • SYNCHRONOUS=off：寫入後不自動 fsync

意義：SQLite 寫入超快，因為跳過 fsync 開銷。但這也代表如果機器突然斷電，SQLite 檔可能損毀。

rqlite 如何處理這個風險

rqlite 週期性把 SQLite 切到 SYNCHRONOUS=FULL、fsync 全資料庫、然後切回 OFF。這保證了「最近一次 fsync 之後的狀態」是確定持久的。

重啟時的策略

rqlite 重啟時：

  1. 嘗試使用最後一次成功 fsync 的 SQLite 副本當起點
  2. 不存在或有疑慮？完全從 Raft log replay 重建 SQLite

這就是「為什麼 Raft log 是 authoritative」— 即使 SQLite 完全毀掉，只要 Raft log 完整，整個資料庫可以重建。

📌 v9.2+ 大資料集快速重啟

9.2 引入「fast restarts with GB datasets」優化：對於大型 SQLite 檔，重啟時不必每次都從 Raft log 完整 replay。詳見 9.2 blog post。

25.4 Snapshot 與 Log Compaction

沒有壓縮機制的話，Raft log 會無限增長 — 磁碟最終會滿。rqlite 自動做 log compaction：

  1. 達到設定門檻（-raft-snap entries 或 WAL 超過 -raft-snap-wal-size）
  2. 建立 snapshot：把 SQLite 整個複製為 snapshot
  3. 截斷 Raft log：snapshot 之前的 entries 可以丟棄
  4. 之後新節點加入 / 落後節點 catch-up 時，先傳 snapshot、再從 snapshot point 後的 entries 重放
✅ v10 改進：Snapshot 解耦

v9 及更早版本中，Leader 在傳輸舊 snapshot 給落後 follower時，不能建立新 snapshot。如果有持續慢的 follower 不斷需要 snapshot，會餓死 leader 的 snapshot 建立 → log 持續增長 → 磁碟用量失控。

v10 起兩件事完全解耦，不再有這個飢餓問題。這是 v10 主要的可靠性改進。

25.5 自動 Clustering 內部

第 13 章介紹了使用方式，這裡看內部如何運作：

Automatic Bootstrapping

每個節點啟動後，不斷通知所有其他節點自己存在。第一個收到「-bootstrap-expect 個節點通知」的節點觸發 bootstrap。其他節點之後嘗試 bootstrap 會失敗，於是成為 follower。

Consul / etcd KV-based

所有節點對共享的 KV store（Consul 或 etcd）atomic CAS 寫入一個 "leader" key。Key 的 value 是該節點的 HTTP + Raft 位址。CAS 失敗的節點則去讀 key，找到 leader 然後 join。

Leader 變更時，新 leader 也會用 CAS 更新該 key。後來加入的節點可以隨時找到當前 leader。

DNS-based

所有節點解析同一個 DNS hostname。回傳的 IP 數量 ≥ -bootstrap-expect 時觸發 bootstrap。bootstrap 過程就像把那些位址用 -join 傳進來一樣。

📌 多種方法殊途同歸

不管哪種 auto-clustering 方法，最終都是「找到該叢集的其他節點、形成 quorum、選 leader」。Hashicorp 的 Raft 函式庫不關心你怎麼發現節點，只負責找到之後的共識。

CH. 26FAQ & 常見誤解

Beginner Developer DevOps

本章彙整 rqlite 最常被問到的問題，按主題分組。內容主要基於官方 FAQ 頁面（2026-01-29 更新），補充本手冊各章節的交叉參考。

26.1 rqlite 是什麼 / 不是什麼

Q：rqlite 究竟做什麼的？

A：把透過 SQL 寫入的資料複製到多個節點。複製的目的是容錯（資料分散在不同地方）、可用性（部分機器掛了仍能查詢），或兩者皆有。複製的範圍可以是同機架不同機器、同建築不同樓、不同城市、甚至不同大陸。

在複製之上，rqlite 用 Raft 共識協定保證「相對於一個特殊節點 Leader，所有副本的狀態都是嚴格定義的」。Raft 防止資料 diverge，永遠有一份權威的、一致的副本。

Q：什麼時候該用 rqlite？

A：需要容易使用、容錯、高可用的關聯式資料庫的應用。輕量特性適合：

  • 邊緣高可用部署（即使在單台設備也提供可靠儲存）
  • 雲端應用需要簡單可管理的複製式關聯資料庫
  • 需要可靠保存最重要資料的核心服務

Q：和其他分散式資料庫比？為什麼用這個？

Complexity is your enemy.

A：rqlite 極其簡單部署、執行、管理 — operational simplicity 是核心設計目標。單一 binary、丟到機器上、跑就對了。組叢集只要幾秒。

但反過來說，它可能對你需求來說太簡單了。對於需要 sharding、複雜分散式 transaction、多 region active-active 寫入的場景，rqlite 不是合適選擇。

26.2 vs SQLite

Q：rqlite 是 SQLite 的 drop-in 替代品嗎？

A：不是。rqlite 用 SQLite 當儲存引擎，但你必須透過 HTTP API 寫入。也就是說，原本直接 open SQLite file 的 app 必須改成發 HTTP request。不過讀取上 SQLite 的能力幾乎全保留（FTS、JSON、虛擬 table 等）。

Q：可以用 rqlite 把我的 SQLite 複製到第二個節點嗎？

A：不能簡單地這樣用。rqlite 不是「SQLite 複製工具」。雖然每個節點確實有 SQLite 完整副本，但 rqlite 不只是複製那個資料庫 — 它取代你直接存取 SQLite 的需求。

Q：底層 SQLite serializable isolation 維持嗎？

A：是的，rqlite 保留 SQLite 的 serializable isolation level。

26.3 vs dqlite / Litestream / LiteFS

專案性質定位適用
rqlite獨立 RDBMS serverHA 分散式關聯資料庫需要高可用 + 容錯 + 簡單運維
dqliteC 函式庫嵌入式分散式 SQLite整合進你自己的 app（要 C 程式設計）
LitestreamSQLite 備份工具把 SQLite 連續備份到 S3單節點 + 災難復原（非 HA）
LiteFSFUSE 檔案系統SQLite 複製（read replicas）讀取規模化、有 primary-replica 概念

rqlite vs dqlite

dqlite 是 C 函式庫，你必須整合到自己的程式碼（需要程式設計）。rqlite 是獨立 application，直接跑就好，有完整的 read/write/backup/maintain/monitor 能力。兩者完全獨立專案，rqlite 不使用 dqlite。事實上 rqlite 出現得比 dqlite 早。

rqlite vs Litestream

Litestream 為 SQLite 提供可靠性（透過定期備份到 S3）。如果你失去執行 SQLite 的節點，必須從備份還原。不改變 application 與 SQLite 的互動，這是其優雅之處。但有極小機率資料遺失，Litestream 讓你能依需求權衡。

rqlite 同時提供可靠性與高可用（透過 clustering）。app 不會察覺單一節點故障，因為其他節點自動接手。對資料遺失的防護顯著更強。但 rqlite 不是 SQLite drop-in 替代。

rqlite vs LiteFS

LiteFS 是另一個 SQLite 複製系統，方法與 Litestream 不同，但和 rqlite 的差異類似 — rqlite 是高可用分散式資料庫解決方案，不是 SQLite 複製系統。

26.4 CAP 定位

Q：rqlite 在 CAP 定理中的定位？

A：Raft 是 CP（Consistency-Partition tolerance）協定。叢集發生網路分區時：

  • 持有多數節點的那側仍可服務（保持一致性）
  • 少數節點側無法處理寫入
  • 分區恢復時自動 reconcile，繼續提供一致的結果

Q：rqlite 接受寫入前都需要共識嗎？

A：是的，這是 Raft 的本質。Leader 需要兩輪 round-trip 給 quorum（雖然平行進行）。

例外：Queued Writes（?queue）— 用 durability 換 throughput，不等共識立刻回應。詳見第 8 章。

Q：客戶端如何偵測叢集分區？

A：如果 client 在 quorum 那側，沒事。如果在少數側：

  • 可能被 redirect 到 leader，但聯絡 leader 失敗 → timeout
  • 可能直接收到 no leader 錯誤

官方說「未來版本可能讓分區情境對 client 更明顯」。

26.5 單節點與多節點議題

Q：可以跑單一節點嗎？

A：可以，很多人這樣用（喜歡用 HTTP 存取 SQLite）。但沒有冗餘、沒有容錯，節點掛了就要重啟。

重要區分：「單一節點」是叢集大小為 1，不是「3 節點掛了兩個」。後者仍是 3 節點叢集（quorum 不夠處於 offline 狀態），不能當單節點用。

Q：如何把多節點叢集改成單節點系統？

A：不能直接把多數節點關掉留一個 — quorum 不夠會卡死。兩種正確做法：

  1. 備份再啟新單節點：/db/backup 拿到 SQLite 檔，.boot 到新的單節點。最簡單、最快
  2. peers.json 強制單節點復原：依照第 12.9 節 走災難復原流程，peers.json 只列一個節點

Q：最大叢集大小？

A：沒有明確上限，但實務上 voting 節點建議 ≤ 11。需要更多請改加 read-only 節點（不計入 N，不影響 quorum）。

26.6 Transaction 限制

Q：rqlite 支援 transaction 嗎？

A：支援某種形式。可以把 bulk update 包成 transaction（all-or-nothing）— 用 ?transaction URL 參數。但顯式 BEGIN / COMMIT / ROLLBACK 是 undefined behavior。

原因：不是這些 SQL 語法不能執行（它們能執行），而是如果節點 / 叢集在 transaction 進行中失效，系統可能進入難以恢復的狀態。在 rqlite 對「失效當下的 transaction」能提供嚴格保證之前，BEGIN/COMMIT/ROLLBACK 官方不支援。

⚠ 不適合某些應用

這個限制意味著 rqlite 不適合需要跨多個 HTTP request 的長 transaction 的應用（如複雜的交易系統）。若你的應用每筆操作可以 self-contained 在單一 request 內，rqlite 沒問題。

26.7 邊緣場景與大型節點群

Q：rqlite 適合「節點頻繁來去（如數千個邊緣設備）」嗎？

A：不太適合。雖然 read-only 節點讓 rqlite 能擴張到很多節點，但 Raft 共識的核心要求是 voting 節點不能頻繁變動。不會 break，但實務不好用。

但是 — 如果這些節點只需要保持資料同步並服務查詢（不寫入），用 read-only nodes 可能很好。

Q：可以用 rqlite 廣播變更到大量節點（如數百個 read-only）？

A：可以！這正是 read-only 節點的設計用途。詳見第 14 章。

Q：read-only 節點上的 client 想寫入怎麼辦？

A：必須把寫入請求送到 leader。如果可達 leader，這實際上提供了一個「邊緣節點向所有其他節點廣播訊息」的方式。

26.8 Isolation 與並發

Q：並發寫入會互相 block 嗎？

A：在這方面 rqlite 與 SQLite 的語意相同。每個 HTTP write 請求在 leader 上使用同一個 SQLite 連線，所以 HTTP 寫入會互相 block（SQLite 本身的限制）。

更根本的原因：Raft log 對所有寫入序列化，所以即使 SQLite 支援並行寫入，Raft 也會阻止這種優化。

Q：並發讀取會互相 block 嗎？

A：讀取不會 block 其他讀取，也不會 block 寫入 — 只要不用 level=strong。

但有個例外：Raft 系統需要週期性 snapshot SQLite（需要獨佔存取）。讀取可以 block snapshot，而 snapshot 期間寫入無法進行，所以理論上讀取可以間接 block 寫入。snapshot 通常數毫秒完成，實務上不是問題。

26.9 依賴與相容性

Q：跑 rqlite 需要什麼特殊軟體或依賴？

A：依 OS 不同，可能需要 libc。Linux 上 glibc ≥ 2.34。版本不夠 rqlited 可能直接啟動失敗：

text
./rqlited: /lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.33' not found
            (required by ./rqlited)

解決方法：升 OS / distribution、或下載 -musl 版本（靜態 link，無 glibc 依賴）。

SQLite 不需要安裝 — 已經編譯進 rqlite release。

Q：怎麼存取資料庫？

A：主要透過HTTP API。可以直接用，也可以用 client library。隨意使用可用 CLI。rqlited 透過 cmdline flag 提供 CORS 支援（瀏覽器端 app）。

也可以直接讀 SQLite 檔（但風險高，詳見第 24 章）。

Q：直接修改 SQLite 檔可以嗎？

A：不行。會破壞 rqlite。詳見第 24 章。

Q：直接讀 SQLite 檔可以嗎？

A：可以，但未經過完整測試，務必遵守第 24 章的三道防線（OS ACL + mode=ro + 不用 EXCLUSIVE）。

🟢 初學者重點
  • rqlite 不是 SQLite drop-in；要透過 HTTP 寫入
  • 單節點也能跑，但失去 HA
  • 跨大陸複製是真的，且 latency 由網路決定
🔵 開發者重點
  • 讀寫都可送任一節點，自動 forward
  • BEGIN/COMMIT 不支援；用 ?transaction URL 參數
  • 並發寫入會 serialize
  • 讀取看 read consistency 等級
🟡 DevOps / SRE 重點
  • CP 系統：分區時少數側無法寫
  • voting 節點實務上 ≤ 11；更多用 read-only
  • 不適合節點頻繁來去的 voter 場景
  • Linux 需 glibc ≥ 2.34，否則用 -musl 版本

參數用途

附錄 D · 錯誤訊息對照

HTTP 層

HTTP code意義可重試
200 OK請求成功處理；但 results[].error 仍可能有 SQL 錯—
301 Moved Permanently?redirect 模式下 follower 告訴你 leader 位址跟著 Location 跳
400 Bad RequestSQL 語法錯、JSON 格式錯、URL 參數錯否（修 code）
401 Unauthorized需要 credentials 但沒帶或錯誤否
403 Forbiddencredentials 對，但缺權限否
404 Not Found端點不存在（檢查路徑）否
500 Internal Server Error節點內部錯誤可重試
503 Service Unavailable節點啟動中、leader 切換中等backoff 後重試

SQL 層（在 results[i].error）

錯誤訊息原因
near "...": syntax errorSQL 語法錯誤；最常見
no such table: NAMEtable 不存在；用 .tables 確認
no such column: NAME欄位不存在；schema 變更時容易遇到
UNIQUE constraint failed: TABLE.COL違反 UNIQUE constraint
FOREIGN KEY constraint failed違反 FK；rqlite 需 -fk 啟用才會檢查
database is locked並發寫入競爭；通常自動解決
cannot ROLLBACK - no transaction is active嘗試手動 transaction；不支援

叢集層

錯誤訊息原因處理
no leader叢集失去 quorum，或客戶端在分區的少數側檢查 /nodes
not leader非 leader 收到須 leader 處理的請求且 forwarding 失敗檢查網路
node is shutting downgraceful shutdown 進行中連其他節點
read only節點是 read-only 但收到寫入請求送 leader
store has not been opened節點還在啟動初期等待 + /readyz

啟動失敗

訊息原因解
GLIBC_2.34 not found系統 glibc 太舊升 OS 或用 -musl 版
extension failed to loadextension 載入失敗檢查路徑、權限、平台相容
permission denied 在 data 路徑權限不足chown 或 chmod
address already in useport 已被佔用換 port 或 fuser/lsof 找占用者
failed to bootstrap cluster不夠 -bootstrap-expect 數量等其他節點啟動
💡 排查順序
  1. HTTP code → SQL error → 叢集 error，逐層往下
  2. 4xx 不要重試（除非錯誤已修）
  3. 5xx 可 backoff 重試
  4. results[].error 是 SQL 層，不要當 HTTP 5xx 處理
  5. 看不出來時 journalctl -u rqlited -n 200 或 stdout log

升級規則

  • v7+ → v10：無縫滾動升級
  • v10 + v9 混叢集：不支援。要嘛整套升、要嘛整套不升
  • v10 → v9 (downgrade)：不支援。升級前務必備份
  • v6 及更早 → v10：建議先升到 v8 或 v9，再升 v10（中間版本驗證）

升級檢查清單

  1. 備份：/db/backup?compress&vacuum
  2. 查 release notes：CHANGELOG.md 看 breaking change
  3. 移除過時 flag：如 -on-disk-path
  4. staging 先試：用 production 備份還原一個 staging 叢集走完升級
  5. 滾動升級：follower → leader（最後）
  6. 每節點等 /readyz?sync
  7. 升級後驗證：smoke test query + 業務驗證
