CH. 17安全（Security）

DevOps

rqlite 的安全性涵蓋 SQLite 層、檔案系統、網路、HTTP API、節點間通訊。本章逐層說明，並提供完整可跑的安全叢集範例。

17.2 檔案系統與網路

檔案系統

  • data 目錄：Raft log、snapshot、SQLite 檔。不該有任何其他 user 存取。chmod 700 或 systemd StateDirectory 隔離
  • 不要讓任何應用直接寫 SQLite 檔（會造成 rqlite 損壞）
  • 敏感資料考慮放在加密 FS（LUKS、ZFS encryption）
  • TLS 憑證、private key 的權限也要嚴格管理（chmod 600，root 或 rqlite user only）
🚨 直接讀寫 SQLite 檔的風險

rqlite 預期獨佔 SQLite WAL，外部寫入會破壞一致性。需要直接讀 SQLite 檔？參考第 24 章 Direct Access，只能讀取且要小心處理 WAL。

網路

每個節點有 2 個 TCP port：HTTP（4001）與 Raft（4002）。

  • Raft port 只給叢集內：用防火牆 / Security Group / NetworkPolicy 限制只能由其他 rqlite 節點存取
  • HTTP port 只給 application：限制源 IP / 子網
  • 有條件的話，Raft 走獨立網卡 / VLAN

AWS EC2 範例

text
Security Group: rqlite-cluster
  Inbound:
    - Port 4001 (HTTP)  from sg-application-tier
    - Port 4002 (Raft)  from sg-rqlite-cluster (self-reference)
  Outbound:
    - default allow all

17.3 HTTPS + Mutual TLS

啟用 HTTPS

提供 cert + key，rqlited 自動切到 HTTPS：

bash
rqlited -node-id 1 \
        -http-cert /etc/rqlite/server.crt \
        -http-key /etc/rqlite/server.key \
        data

啟用 mutual TLS

加 -http-ca-cert（信任的 CA）+ -http-verify-client。只有持有 CA 簽發證書的 client 能連線：

bash
rqlited -node-id 1 \
        -http-cert /etc/rqlite/server.crt \
        -http-key /etc/rqlite/server.key \
        -http-ca-cert /etc/rqlite/ca.crt \
        -http-verify-client \
        data

客戶端怎麼連

bash
# 一般 HTTPS（驗證 server cert）
curl --cacert ca.crt https://rqlite.example.com:4001/db/query?q=...

# mTLS（client 也帶 cert）
curl --cacert ca.crt \
     --cert client.crt --key client.key \
     https://rqlite.example.com:4001/db/query?q=...

17.4 Basic Auth — 使用者帳密

rqlite HTTP API 支援 Basic Auth。每個節點接受 JSON 設定檔，定義使用者與密碼：

json
[
  {
    "username": "bob",
    "password": "secret1",
    "perms": ["all"]
  },
  {
    "username": "mary",
    "password": "secret2",
    "perms": ["query", "backup", "join"]
  }
]

啟用：

bash
rqlited -auth=/etc/rqlite/auth.json ... data
⚠ 不同節點可以有不同的設定檔

auth 設定是 per-node 的。意味著理論上不同節點可以接受不同帳密 — 但這樣設計運維會很亂。標準作法：保持所有節點的 auth 檔內容一致（用 K8s Secret、Ansible 等同步）。

17.5 User-level permissions

每個使用者可以擁有多個權限：

權限允許操作
all所有操作（admin）
execute/db/execute 寫入
query/db/query 查詢 + /db/sql 改寫觀察
load/db/load 與 /boot 載入
backup/db/backup 備份
snapshot/snapshot 觸發 Raft snapshot
status/status、/nodes、expvar、pprof 等診斷
ready/readyz 健康檢查
join節點加入叢集
join-read-only僅可作為 read-only 加入
remove從叢集移除節點。auto-remove on shutdown 時 -join-as user 需要此權限
leader-ops/leader 相關操作（強制選舉等）
📌 Unified Endpoint 需要兩個權限

呼叫 /db/request 的使用者必須同時擁有 execute 與 query 權限。

萬用使用者 *

username = * 是特殊條目，代表「所有使用者（含匿名）」。常用於開放健康檢查：

json
{
  "username": "*",
  "perms": ["status", "ready", "join-read-only"]
}

這樣 health check / 監控不用帶帳密；read-only 節點可匿名加入。

節點 join 的認證

當叢集啟用 auth，新節點要 join 時也得帶 credentials。用 -join-as：

bash
rqlited -auth=/etc/rqlite/auth.json \
        -join host1:4002 \
        -join-as bob \
        data

節點會從 auth 檔讀 bob 的密碼來認證。避免把密碼放在 command line（會被 ps 看到）。

17.6 節點間通訊 TLS

rqlite 節點間（Raft consensus、forwarding、snapshot 傳輸）的通訊也可以 TLS 加密。必須整個叢集啟用或都不啟用，不能混合。

bash
# 啟用單向 TLS（server cert verify）
rqlited -node-cert /etc/rqlite/node.crt \
        -node-key /etc/rqlite/node.key \
        ...

# 啟用節點間 mutual TLS
rqlited -node-cert /etc/rqlite/node.crt \
        -node-key /etc/rqlite/node.key \
        -node-ca-cert /etc/rqlite/node-ca.crt \
        -node-verify-client \
        ...

單一 hostname 跨叢集使用

如果想讓全部節點共用一張證書（簡化 cert management），用 -node-verify-server-name 指定預期的 hostname：

bash
rqlited -node-cert rqlite.crt -node-key rqlite.key \
        -node-ca-cert ca.crt -node-verify-client \
        -node-verify-server-name rqlite.internal \
        ...

17.7 安全叢集啟動範例

整合所有層級的完整範例：HTTPS + Basic Auth + node TLS。

節點 1（leader / bootstrap）

bash
rqlited -node-id 1 \
        -auth /etc/rqlite/auth.json \
        -http-cert /etc/rqlite/server.crt \
        -http-key /etc/rqlite/server.key \
        -node-cert /etc/rqlite/node.crt \
        -node-key /etc/rqlite/node.key \
        ~/node.1

節點 2（join）

bash
rqlited -node-id 2 \
        -auth /etc/rqlite/auth.json \
        -http-addr localhost:4003 \
        -raft-addr :4004 \
        -http-cert /etc/rqlite/server.crt \
        -http-key /etc/rqlite/server.key \
        -node-cert /etc/rqlite/node.crt \
        -node-key /etc/rqlite/node.key \
        -join localhost:4002 \
        -join-as bob \
        ~/node.2

使用 mary 帳號查詢

bash
curl -G 'https://mary:secret2@localhost:4001/db/query?pretty&timings' \
  --data-urlencode 'q=SELECT * FROM foo'

注意：把密碼放在 URL 會被 access log 紀錄。production 端應該用 -u flag 或 client library 內帶 credentials。

SQL 層 query 限制

rqlite 對 /db/query 使用 SQLite read-only connection，就算 SQL 中混入寫入語句也不會生效。這是額外的縱深防禦 — 把某使用者限制為 query 權限，就絕對無法改資料庫。

17.8 證書輪替（rotation）

rqlite 會持續監控憑證檔變化，自動載入新版本，不必重啟。但有兩個例外：

檔案類型變更後
HTTP cert + key（-http-cert / -http-key）✅ 自動 reload
節點 cert + key（-node-cert / -node-key）✅ 自動 reload
CA cert（-http-ca-cert / -node-ca-cert）❌ 必須重啟節點

實務輪替流程：

  1. 產生新 server cert + key（用同樣 CA 簽）
  2. 用 mv -f atomic 替換檔案
  3. rqlite 在數秒內感知並 reload
  4. 用 curl -v 驗證新證書生效

需要換 CA 時則做 rolling restart（每次重啟一個節點，等 ready 再下一個）。

🟡 DevOps / SRE 重點
  • 分層防禦：FS、網路、HTTPS、Auth、節點間 TLS 各層都要做
  • data dir chmod 700；TLS key chmod 600
  • auth 檔在所有節點保持一致
  • RBAC 細分：監控用 status+ready、app 用 execute+query、管理用 all
  • 節點間 TLS 必須全叢集啟用或不啟用
  • cert 輪替自動 reload；CA 變更要重啟
  • -join-as 用 auth 檔避免密碼洩漏 process list

CH. 18效能調校

DevOps Developer

rqlite 為了 HA 引入分散式架構，吞吐量必然低於單機 SQLite。但實務上幾十到數百筆/秒的寫入，加上幾千筆/秒讀取，已足夠多數應用。本章解析效能瓶頸與調校手段。

18.1 效能的兩個主要因素

  1. 磁碟效能（Disk IO）
  2. 網路延遲（Network latency）

寫入吞吐視機器而定，10 到數百筆 QPS都有可能。

18.2 磁碟與網路

磁碟

低延遲網路時，disk fsync 是效能瓶頸。每次寫入都進 Raft log + fsync 確保持久。

  • NVMe SSD：fsync 延遲 ~0.1ms，最理想
  • SATA SSD：~1ms
  • HDD：~10ms，不適合生產 rqlite
  • 雲端區塊儲存：AWS gp3 / Azure Premium SSD / GCP pd-ssd 都堪用；標準 / cold 等級避免

網路

寫入時 leader 要與其他節點通訊兩次（雖然平行）：

  1. AppendEntry 送 log → 等 quorum 回 ack（commit）
  2. 下一輪 heartbeat 通知 follower apply

網路延遲高時，吞吐瓶頸從磁碟轉移到網路。跨 AZ / 跨 region 的部署要特別注意。

18.3 Snapshotting 機制

Raft log 會無限增長。Snapshot 定期把 SQLite 當前狀態固定下來，並截斷舊 log。

⚠ Snapshot 期間會 block 寫入

Snapshot 過程中所有寫入會被 block。所以：

  • 頻繁 snapshot = 啟動快、log 短，但常 block 寫入、CPU/IO 高
  • 稀疏 snapshot = 寫入順暢，但 log 長、新節點 catch-up 慢、節點啟動慢

三個關鍵 flag：

Flag意義
-raft-snap未 apply log entries 超過此數觸發
-raft-snap-wal-sizeWAL 超過此 bytes 觸發（預設 4MB）；設 0 停用
-raft-snap-int檢查是否需 snapshot 的間隔
✅ v10 改進：snapshot 解耦

v10 以前，Leader 在傳輸舊 snapshot 給落後 follower 時，不能建立新 snapshot。慢 follower 持續需要 snapshot 會餓死 leader 的 snapshot 流程。v10 起兩件事解耦，不再有飢餓問題。

18.4 VACUUM

SQLite VACUUM 重建資料庫、釋放碎片，可能改善 query 效能。

手動 VACUUM

bash
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d '["VACUUM"]'

自動 VACUUM

bash
rqlited -auto-vacuum-int=24h ...
🚨 VACUUM 的三大坑
  • 過程中寫入完全 block，大資料庫可能要分鐘級
  • 暫時需要兩倍磁碟空間（先複製、再交換）
  • 可能改變 rowid 等行為，事先讀 SQLite VACUUM 文件

18.5 PRAGMA optimize

SQLite 的 PRAGMA optimize 分析 table、生成統計、改善 query plan。SQLite 建議定期執行。rqlite 預設每天自動跑一次。

bash
# 改成每 6 小時
rqlited -auto-optimize-int=6h ...

# 完全停用（不推薦）
rqlited -auto-optimize-int=0h ...

18.6 Batching 的影響

單一 request 包越多 statement，寫入效能越好 — 常見的 2 個數量級差距。

Bulk API（單 request 多 statement）+ transaction（atomicity）= 最佳組合。詳見第 7 章。

18.7 Queued Writes（吞吐 vs durability）

能容忍極小機率資料遺失？啟用 Queued Writes（?queue），數量級 throughput 提升，無需改 client。詳見第 8 章。

18.8 記憶體型檔案系統（tmpfs / ramdisk）

把 rqlite data 目錄放到 tmpfs，實測 100× 效能提升。

bash
# 建立 512MB tmpfs
mount -t tmpfs -o size=512m tmpfs /mnt/ramdisk

# rqlite 用此 dir
rqlited -node-id 1 /mnt/ramdisk/rqlite-data
🚨 整個叢集斷電 = 全部資料消失

因為 Raft log + SQLite 都只在記憶體。適用情境：

  • 你能容忍災難性故障時的完全資料遺失
  • 有外部恢復來源（其他資料庫、備份、可重建的衍生資料）
  • 純追求吞吐效能，可接受復原成本

18.9 記憶體用量與 GO GC 調校

rqlite 用 Go 寫，靠 garbage collector 管理記憶體。大型重複 request 可能造成 memory spike，GC 來不及釋放。極端情境下 OOM。

處理：調整 GOGC 環境變數：

bash
# 預設 GOGC=100；降到 50 → GC 觸發頻率加倍
# CPU 上升、記憶體峰值下降
export GOGC=50
rqlited ...

# 或設 GOMEMLIMIT 限制總記憶體
export GOMEMLIMIT=2GiB
rqlited ...

「大」是多大？官方參考：給 rqlited 1GB memory，> 25MB 的 request 就算大。詳細參考 Go GC Guide。

🔵 開發者重點
  • Bulk + transaction，效能差數百倍
  • 讀取可選 weak / none / linearizable，看一致性需求
🟡 DevOps / SRE 重點
  • NVMe SSD 是 rqlite 最佳硬體投資
  • 監控 fsync 延遲（iostat -x 看 w_await）
  • 同 region / 同 AZ 部署 voter，降低網路延遲
  • snapshot 預設值通常 OK，除非有大量資料
  • tmpfs 模式只用於可重建場景
  • OOM 風險高的場景設 GOMEMLIMIT

CH. 19備份與還原

DevOps

rqlite 支援熱備份（hot backup）—不停機就能取得完整 SQLite 副本。本章涵蓋手動備份、自動上傳雲端、從 SQLite 還原叢集等所有運維場景。

19.1 手動熱備份

shell 方式

text
127.0.0.1:4001> .backup bak.sqlite3
backup file written successfully

HTTP API

bash
curl -s -XGET http://localhost:4001/db/backup -o bak.sqlite3

取出的檔案是標準 SQLite 檔，可直接用 sqlite3 開啟檢視。

WAL 模式 vs DELETE 模式

預設備份是 WAL 模式。要 DELETE 模式（標準 SQLite，無 WAL）：

bash
curl -s -XGET 'http://localhost:4001/db/backup?fmt=delete' -o bak.sqlite3

DELETE 模式會在 server 端先複製一份（變更 journal mode），需要兩倍磁碟空間，注意空間。

備份來源：leader vs 本節點

  • 預設：請求自動 forward 到 leader 取資料（保證最新）
  • ?noleader：取本節點的副本（不 forward）
  • ?redirect：follower 回 301 + Location 給 leader
💡 大型備份直接打 leader

備份檔超過 100MB，建議客戶端先呼叫 /leader 找到 leader 位址，直接打 leader 的 backup 端點。否則資料要跨節點傳兩次（leader → follower → client）。

19.2 SQL dump（文字格式）

純文字 SQL，可 diff、grep、人工檢查。

text
127.0.0.1:4001> .dump bak.sql
SQL text file written successfully
bash
curl -s -XGET 'http://localhost:4001/db/backup?fmt=sql' -o bak.sql

# 只 dump 特定 table
curl -s -XGET 'http://localhost:4001/db/backup?fmt=sql&tables=users,orders' -o partial.sql

19.3 VACUUM & 壓縮

備份前先 VACUUM（最小化檔案大小）：

bash
curl -s -XGET 'http://localhost:4001/db/backup?vacuum' -o bak.sqlite3

GZIP 壓縮備份：

bash
curl -s -XGET 'http://localhost:4001/db/backup?compress' -o bak.sqlite3.gz

# 兩者合用 — 最小體積
curl -s -XGET 'http://localhost:4001/db/backup?compress&vacuum' -o bak.sqlite3.gz
⚠ 一定要測試備份

定期用 sqlite3 bak.sqlite3 "PRAGMA integrity_check;" 驗證備份檔可開、無損毀。沒測試過的備份等於沒備份。

19.4 自動備份到 S3

rqlite 內建自動定期備份到雲端儲存。只有 leader 執行備份；新 leader 上任接手。為節省流量，SQLite 沒變化就不上傳。

S3 設定檔範例

json
{
  "version": 1,
  "type": "s3",
  "interval": "5m",
  "vacuum": false,
  "sub": {
    "access_key_id": "$ACCESS_KEY_ID",
    "secret_access_key": "$SECRET_ACCESS_KEY_ID",
    "region": "$BUCKET_REGION",

19.7 進階選項：timestamp / 不壓縮

  • "no_compress": true：停用 gzip 壓縮（預設啟用）
  • "timestamp": true：path 最後一段前自動加上 YYYYMMDDHHMMSS_（UTC），每次備份產生新檔。對 point-in-time recovery 有用
  • 環境變數展開：JSON 內字串以 $ 開頭會被替換成環境變數值

完整範例：每 5 分鐘上傳一份未壓縮、帶 timestamp 的備份

  "no_compress": true,

    "secret_access_key": "$SECRET_ACCESS_KEY_ID",
    "region": "$BUCKET_REGION",
    "bucket": "$BUCKET_NAME",
    "path": "backups/db.sqlite3"

}

19.8 還原：Boot vs Load

rqlite 提供兩種還原機制：

方式速度單節點 only記憶體開銷適用
Boot (/boot)非常快✓ 是低災難復原、初次大資料載入
Load (/db/load)慢可送叢集較高（>100MB 記憶體爆量）運行中的叢集小資料載入

Boot — 單節點專用

專為「快速從 SQLite 建立 rqlite 節點」設計。多 GB 檔都能應付。

bash
curl -XPOST http://localhost:4001/boot \
     -H "Transfer-Encoding: chunked" \
     --upload-file largedb.sqlite
text
127.0.0.1:4001> .boot largedb.sqlite
Node booted successfully

Boot 後是單節點叢集，可後續 join 新節點變多節點。

Load — 可送叢集

兩種輸入格式：SQLite 二進位檔（快）或 SQL 文字 dump（慢）。

bash
# 1. 從 SQLite 檔（推薦）
curl -XPOST localhost:4001/db/load \
     -H "Content-type: application/octet-stream" \
     --data-binary @restore.sqlite

# 2. 從 SQL dump
curl -XPOST localhost:4001/db/load \
     -H "Content-type: text/plain" \
     --data-binary @restore.dump

shell：

text
127.0.0.1:4001> .restore mydb.sqlite
Database restored successfully
⚠ 100MB+ 用 Boot

Load 對大檔案會 CPU + 記憶體爆量。檔案 > 100MB 建議改用 Boot。

還原後處理 Foreign Keys

SQL dump 預設禁用 FK 約束。如果你正常運作時有開 -fk，還原完要重新啟用：

bash
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d '["PRAGMA foreign_keys = 1"]'

19.9 自動還原（auto-restore）

節點啟動時自動從雲端拉備份初始化。前提：節點 data dir 沒有舊資料。
bootstrap 一個新叢集時，只有變成 leader 的節點會真正下載；其他節點透過 Raft 自然同步。

S3 auto-restore 設定

json
{
  "version": 1,
  "type": "s3",
  "timeout": "60s",
  "continue_on_failure": false,
  "sub": {
    "access_key_id": "$ACCESS_KEY_ID",
    "secret_access_key": "$SECRET_ACCESS_KEY_ID",
    "region": "$BUCKET_REGION",
    "bucket": "$BUCKET_NAME",
    "path": "backups/db.sqlite3.gz"
  }
}

continue_on_failure：下載失敗時是否繼續啟動。預設 false（失敗即 exit）；想要寬鬆設 true。

bash
rqlited -auto-restore=/etc/rqlite/restore-s3.json \
        -node-id=1 \
        ...
⚠ 大檔記憶體警告

auto-restore 內部走 Load 機制，所以對 > 100MB 檔有記憶體爆量風險。大資料的災難復原請單節點 Boot + 之後 join 新節點。

19.10 還原最佳實踐

  • 新叢集還原：永遠在乾淨節點還原，不要在有資料的叢集 load — 行為 undefined
  • 停止寫入：還原期間應暫停應用寫入，否則結果不可預期
  • 大檔走 Boot：> 100MB 用 Boot；小檔用 Load
  • 復原後驗證：用 SQL count、checksum、業務驗證 query 等確認資料完整
  • 定期演練：每季從備份還原一次到 staging，記錄耗時

20.5 /readyz — 健康檢查

bash
curl localhost:4001/readyz
text
[+]node ok
[+]leader ok
[+]store ok

HTTP 200 = 全部 ok；否則 5xx + 列出失敗項目。

noleader 變體

只想知道「節點本身活著、回得了 HTTP」？用 ?noleader：

bash
curl localhost:4001/readyz?noleader

對 read-only 節點與啟動初期特別有用。

sync flag — 確認跟上 leader

?sync 會 block 直到節點 catch up 到 leader 的 commit index（透過最新一次 heartbeat 拿到）：

bash
curl 'localhost:4001/readyz?sync&timeout=5s'
text
[+]node ok
[+]leader ok
[+]store ok
[+]sync ok

適合滾動升級時等候新節點完全 sync 才繼續下一步。Leader 收到此請求時 sync 永遠 ok。

📌 readyz 的承諾範圍

readyz ok 表示：可服務所有寫入、所有 weak / strong 一致性的讀取。但 level=none 的讀取任何時候都能服務（只要本地 SQLite 在），結果可能 stale。

20.8 Prometheus 整合範例

rqlite 不原生 暴露 Prometheus 格式，但 expvar JSON 可以靠 exporter 轉換。常見作法：

選項 1：用社群 expvar-exporter

把 expvar JSON 轉成 Prometheus metrics 的小型轉接器（社群有多個實作）。當 sidecar 跑在每個 rqlite 節點旁邊。

選項 2：自寫簡單 sidecar（更靈活）

go
package main

import (
    "encoding/json"
    "net/http"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    queries = prometheus.NewGauge(prometheus.GaugeOpts{
        Name: "rqlite_queries_total",
        Help: "Total queries served",
    })
    executions = prometheus.NewGauge(prometheus.GaugeOpts{
        Name: "rqlite_executions_total",
        Help: "Total write executions",
    })
    leaderState = prometheus.NewGauge(prometheus.GaugeOpts{
        Name: "rqlite_is_leader",
        Help: "1 if this node is Leader",
    })
)

func scrape() {
    resp, err := http.Get("http://localhost:4001/debug/vars")
    if err != nil {
        return
    }
    defer resp.Body.Close()
    var v map[string]any
    json.NewDecoder(resp.Body).Decode(&v)

    if db, ok := v["db"].(map[string]any); ok {
        queries.Set(db["queries"].(float64))
        executions.Set(db["executions"].(float64))
    }

    statusResp, _ := http.Get("http://localhost:4001/status")
    defer statusResp.Body.Close()
    var s map[string]any
    json.NewDecoder(statusResp.Body).Decode(&s)
    if store, ok := s["store"].(map[string]any); ok {
        if raft, ok := store["raft"].(map[string]any); ok {
            if raft["state"] == "Leader" {
                leaderState.Set(1)
            } else {
                leaderState.Set(0)
            }
        }
    }
}

func main() {
    prometheus.MustRegister(queries, executions, leaderState)
    http.HandleFunc("/metrics", func(w http.ResponseWriter, r *http.Request) {
        scrape()
        promhttp.Handler().ServeHTTP(w, r)
    })
    http.ListenAndServe(":9090", nil)
}

Prometheus scrape config：

yaml
scrape_configs:
  - job_name: rqlite
    scrape_interval: 15s
    static_configs:
      - targets:
        - rqlite1:9090
        - rqlite2:9090
        - rqlite3:9090

20.9 告警關鍵指標

指標告警條件意義
/readyz HTTP 200連續 30s 非 200節點壞了
有 leader（任一節點 /leader 回有效）連續 30s 無 leader叢集失去 quorum
leader 切換頻率1 小時內 > 3 次網路抖動 / 過載
applied_index 落後 commit_index持續 > 1000節點追不上
db.execution_errors單位時間激增應用層 SQL 錯誤
Go memstats HeapInuse逼近 GOMEMLIMITOOM 風險
磁碟使用率> 80%snapshot 或 VACUUM 失敗
fsync 延遲（OS 層）p99 > 50ms磁碟有問題

Prometheus 範例告警規則

yaml
groups:
- name: rqlite
  rules:
  - alert: RqliteNoLeader
    expr: max(rqlite_is_leader) by (cluster) == 0
    for: 30s
    annotations:
      summary: "rqlite cluster has no leader"

  - alert: RqliteLeaderFlapping
    expr: changes(rqlite_leader_id[1h]) > 3
    annotations:
      summary: "Leader changed more than 3 times in 1h"

  - alert: RqliteHighExecErrors
    expr: rate(rqlite_executions_errors_total[5m]) > 1
    annotations:
      summary: "rqlite execution errors spiking"

  • K8s liveness 用 /readyz?noleader；readiness 用 /readyz
  • 滾動升級用 /readyz?sync 等候新節點 catch up
  • 三個必看：是否有 leader、follower 是否落後、execution errors
  • cert + auth 啟用後，監控 user 需要 status + ready 權限
  • pprof 線上拉時注意 CPU 增加

  jq 'to_entries[] | "\(.key): reachable=\(.value.reachable) leader=\(.value.leader)"'

echo "=== Check 4: applied 與 commit index 差距 ==="
for n in "${NODES[@]}"; do
  curl -s "$n/status?pretty" | \
    jq '.store.raft | {state, applied_index, commit_index, lag: (.commit_index - .applied_index)}'
done

echo "=== Check 5: 自動備份運作中（leader 上）==="
# 假設備份檔在 S3 路徑 backups/db.sqlite3.gz

詳細步驟（systemd 環境為例）

bash
### Step 1: 拍快照當備份
curl -s -XGET 'http://rqlite1:4001/db/backup?compress&vacuum' \
  -o /backups/preupgrade-$(date +%Y%m%d-%H%M%S).sqlite3.gz

### Step 2: 對 follower 之一執行升級（假設 rqlite2 是 follower）
ssh rqlite2 '
  sudo systemctl stop rqlited
  # 換 binary（或更新 deb / rpm）
  curl -fsSL https://rqlite.io/install.sh -o /tmp/install.sh
  RQLITE_VERSION=v10.0.0 INSTALL_DIR=/usr/local/bin sudo sh /tmp/install.sh
  sudo systemctl start rqlited
'

### Step 3: 等到 rqlite2 catch up 才繼續
curl -s 'http://rqlite2:4001/readyz?sync&timeout=120s'
# 應該回 [+]sync ok

### Step 4: 重複 step 2-3 對 rqlite3

### Step 5: 處理 leader（最後再升）— 先 stepdown 到已升級的 follower
curl -XPOST http://rqlite1:4001/leader \
  -H "Content-Type: application/json" \
  -d '{"id": "2"}'

### Step 6: 等幾秒，確認 leader 已轉移
sleep 5
curl -s http://rqlite2:4001/leader | jq .id  # 應該是 2

### Step 7: 升級 rqlite1（已是 follower）
ssh rqlite1 '... 同 step 2 ...'
curl -s 'http://rqlite1:4001/readyz?sync&timeout=120s'

### Step 8: 驗證
curl -s 'http://rqlite1:4001/status?pretty' | jq .build.version
# 預期回 "10"
🚨 v9 → v10 特別注意
  • 不能讓 v10 節點 join 仍是 v9 的叢集 — 整套要升完
  • 升級期間不要同時做 schema 變更或大量寫入
  • 有用 -on-disk-path 的舊腳本，升 v10 前要先移除
  • 升級過程中如果某節點啟動失敗，停手；先排查再繼續

21.3 Leader Stepdown / 換 Leader

運維中經常需要把 leader 轉到某個特定節點：升級維護、leader 機器要重開機、leader 機器負載太重等。

方式 1：自動換（不指定目標）

bash
curl -XPOST http://leader:4001/leader

Raft 內部觸發 stepdown，會選出新 leader。但不保證是哪個。

方式 2：指定目標（推薦）

bash
curl -XPOST http://leader:4001/leader \
  -H "Content-Type: application/json" \
  -d '{"id": "node2"}'

方式 3：shell

text
127.0.0.1:4001> .stepdown

關機時自動 stepdown（預設啟用）

啟動 flag -raft-shutdown-stepdown（預設 true）：leader 收到 SIGTERM 等優雅停機訊號時，會先把 leadership 轉到其他節點再退出，最小化叢集無 leader 的時間。

21.4 強制 Snapshot

正常情況下 rqlite 會依 -raft-snap 等規則自動 snapshot。手動觸發的時機：

  • 大量寫入後，想立刻把 Raft log 截斷
  • 新節點要加入前，先強制 snapshot 縮短 catch-up 時間
  • 備份前讓 SQLite 處於最新狀態
bash
# 對任一節點呼叫；會 forward 到 leader
curl -XPOST http://localhost:4001/snapshot

shell：.snapshot。需要 snapshot 權限。

⚠ snapshot 期間 block 寫入

大資料庫的 snapshot 可能要數秒到數十秒，期間寫入會 block。不要在高峰期手動 snapshot。
