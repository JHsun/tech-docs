CH. 22Change Data Capture（CDC）

Developer DevOps

CDC 在 9.0 引入（2025-09-15），讓 rqlite 把每筆 INSERT / UPDATE / DELETE 的變更串流到外部系統。它解鎖了「以 rqlite 為事件源」的整類應用：data lake 同步、搜尋索引重建、cache invalidation、跨系統複製、稽核日誌。本章涵蓋啟用、設定、事件格式、運維。

22.1 CDC 是什麼

每次 commit 後，rqlite 把該次寫入產生的變更打包成 JSON、POST 到你指定的 HTTP webhook。傳輸由叢集 leader負責。

POST| W[Webhook
endpoint]:::ext W -.no transmit.- F1 W -.no transmit.- F2 F1 -.local disk FIFO.- F1 F2 -.local disk FIFO.- F2
圖 22-1 · CDC 由 Leader 傳送；Follower 仍將事件記錄到本地磁碟 queue，以便接任 Leader 後不漏

關鍵設計決策：所有節點都把事件寫進本地磁碟 FIFO queue，但只有 leader 傳出。這樣即使 leader 變更，新 leader 仍能從自己的 queue 補送。

22.2 設計與保證

面向承諾
傳送語意at-least-once（webhook 回 200 / 202 算成功）
傳送來源只有 Leader；Followers 保留事件但不送
順序同一 Raft log index 內保序；跨 index 可能重送
持久性事件先進磁碟 queue，不靠 Raft log replay
重複處理每事件有單調遞增 index，下游可去重

High-Water Mark（HWM）

Leader 持續廣播「已成功送達的最大事件 Raft index」給其他節點。其他節點看到後會把 queue 中 ≤ HWM 的事件丟棄。當新 leader 上任時：

  • 從自己的 queue 讀事件
  • 跳過所有 index ≤ HWM 的（因為前 leader 已送過）
  • 從 HWM+1 開始繼續

HWM 廣播間隔可調（high_watermark_interval）。越短的間隔 = leader 切換時重複事件越少 + 跨節點網路流量越多。

⚠ At-least-once = 下游必須能處理重複

正常運作下重複很罕見，但 leader 切換、網路抖動、webhook 暫時無法回應都會造成重送。下游消費端要嘛idempotent，要嘛追蹤 index 做去重。

22.3 啟用 CDC

透過 -cdc-config 啟用。可以傳 URL 字串或 JSON 設定檔路徑。

最簡單：直接給 URL

bash
rqlited -cdc-config="http://localhost:8000/my-cdc-endpoint" ~/node-data

debug 用：印到 stdout

bash
# 把 CDC 事件直接印到 console，方便看 schema
rqlited -cdc-config="stdout" ~/node-data

設定檔（推薦）

最小設定檔：

json
# cdc.json
{
  "endpoint": "https://example.com/webhook"
}
bash
rqlited -cdc-config=/etc/rqlite/cdc.json ~/node-data
💡 設定檔 vs URL

正式部署都用設定檔（便於版本管理、可加 TLS / 過濾 / 重試策略）。URL 模式適合快速試驗。

22.4 完整設定參考

endpoint 與身份

欄位說明
endpoint（必填）HTTP URL，或 "stdout"
service_id（選填）每筆事件帶上此 ID，下游可區分多個 rqlite 來源

事件內容控制

欄位說明
row_ids_only（預設 false）只送 primary key + 操作類型；省 before/after
table_filter（regex，選填）只送名稱符合的 table 的事件

TLS（HTTPS webhook）

json
"tls": {
  "ca_cert_file": "/path/ca.pem",
  "cert_file": "/path/client.crt",
  "key_file": "/path/client.key",
  "insecure_skip_verify": false,
  "server_name": "webhook.example.com"
}

insecure_skip_verify: true 只用於測試。

Batching 與傳送

欄位說明
max_batch_size單筆 POST 最多幾個事件
max_batch_delaybatch 未滿時最多等多久就送（Go duration）
high_watermark_intervalLeader 廣播 HWM 給其他節點的間隔
transmit_timeout每次 HTTP request timeout；超時整批 retry
transmit_max_retries最多重試次數。不設 = 無限重試
transmit_retry_policyLinearRetryPolicy（預設）或 ExponentialRetryPolicy
transmit_min_backoff初始 backoff（預設 100ms）
transmit_max_backoffexponential policy 的最大 backoff
🚨 無限重試 + endpoint 掛掉 = 磁碟爆滿

當 webhook 長時間不可用且 transmit_max_retries 未設定（= 無限），事件會一直堆在本地 disk queue 直到磁碟滿。務必監控 rqlite data 目錄空間，或設定有限的 transmit_max_retries。

    "key_file": "/etc/certs/client.key",
    "insecure_skip_verify": false,
    "server_name": "webhook.example.com"

22.5 事件格式

每個 HTTP POST body 是一個 JSON object，包含 payload array，每個 entry 對應一個 Raft log index（一次 transaction），其中含多個獨立操作事件：

json
{
  "node_id": "127.0.0.1:4002",
  "service_id": "prod-eu-cluster",
  "payload": [
    {
      "index": 3,
      "commit_timestamp": 1757892884812603,
      "events": [
        {
          "op": "INSERT",
          "table": "users",
          "new_row_id": 7,
          "before": null,
          "after": { "id": 7, "name": "fiona" }
        }
      ]
    }
  ]
}

欄位逐項

欄位說明
node_id送出此事件的 Leader 的 Raft 位址
service_id對應設定檔（識別來源叢集）
payload[].index該 transaction 的 Raft log index — 去重用
payload[].commit_timestampcommit 微秒級 timestamp
events[].opINSERT / UPDATE / DELETE
events[].table變更的 table 名
events[].new_row_id新 rowid 或 PK 值
events[].before變更前該 row 內容；INSERT 為 null
events[].after變更後該 row 內容；DELETE 為 null

row_ids_only: true 時 before 與 after 完全省略，只剩 op + table + new_row_id。適合「下游只需要知道哪些 row 變動，自己去 SELECT 完整資料」的場景，省大量網路流量。

22.6 下游 De-duplication

at-least-once 不保證恰一次，下游要自處理。兩個策略：

策略做法適用
追蹤最大 indexpersist last_processed_index，每筆 payload 進來檢查 index > last 才處理順序敏感、需嚴格 exactly-once
讓 handler 冪等同樣的事件多次處理結果一致（如 UPSERT、SET 而非 INCREMENT）多數場景；實作較簡單

追蹤 index 範例（Go webhook）

go
type Payload struct {
    NodeID    string     `json:"node_id"`
    ServiceID string     `json:"service_id"`
    Payload   []Group    `json:"payload"`
}

type Group struct {
    Index           int64     `json:"index"`
    CommitTimestamp int64     `json:"commit_timestamp"`
    Events          []Event   `json:"events"`
}

func handle(w http.ResponseWriter, r *http.Request) {
    var p Payload
    json.NewDecoder(r.Body).Decode(&p)

    last := loadLastIndex(p.ServiceID)
    for _, g := range p.Payload {
        if g.Index <= last {
            continue  // 已處理過
        }
        for _, e := range g.Events {
            processEvent(e)
        }
        saveLastIndex(p.ServiceID, g.Index)
        last = g.Index
    }
    w.WriteHeader(http.StatusOK)
}
📌 service_id 是去重的 partition key

如果你有多個 rqlite 叢集送到同一個 webhook，必須分 service_id 各自追蹤 index。不同叢集的 index 不可比較。

22.7 Webhook 端範例：用 rqlite 作事件源寫入 Elasticsearch

典型架構：rqlite 作 system of record，CDC 把每筆變更 push 到輕量級 Go service，這個 service 把資料轉換後寫進 Elasticsearch / OpenSearch 提供搜尋。

service]:::relay Relay -->|bulk index| ES[Elasticsearch]:::sink ES -.search query.-> AppSearch[Search UI]
圖 22-2 · 典型 CDC 應用：rqlite + search index
go
package main

import (
    "encoding/json"
    "fmt"
    "net/http"
    "sync"
)

type Event struct {
    Op       string                 `json:"op"`
    Table    string                 `json:"table"`
    NewRowID interface{}            `json:"new_row_id"`
    Before   map[string]interface{} `json:"before"`
    After    map[string]interface{} `json:"after"`
}

var (
    mu        sync.Mutex
    lastIndex = make(map[string]int64)
)

func main() {
    http.HandleFunc("/cdc", func(w http.ResponseWriter, r *http.Request) {
        var p struct {
            ServiceID string `json:"service_id"`
            Payload   []struct {
                Index  int64   `json:"index"`
                Events []Event `json:"events"`
            } `json:"payload"`
        }
        if err := json.NewDecoder(r.Body).Decode(&p); err != nil {
            http.Error(w, err.Error(), 400)
            return
        }

        mu.Lock()
        last := lastIndex[p.ServiceID]
        mu.Unlock()

        for _, g := range p.Payload {
            if g.Index <= last {
                continue
            }
            for _, e := range g.Events {
                switch e.Op {
                case "INSERT", "UPDATE":
                    esIndex(e.Table, e.NewRowID, e.After)
                case "DELETE":
                    esDelete(e.Table, e.NewRowID)
                }
            }
            mu.Lock()
            lastIndex[p.ServiceID] = g.Index
            mu.Unlock()
        }
        w.WriteHeader(http.StatusOK)
    })
    fmt.Println("listening :8080")
    http.ListenAndServe(":8080", nil)
}

func esIndex(table string, id interface{}, doc map[string]interface{}) {
    // PUT /index/_doc/<id> with doc as body
}

func esDelete(table string, id interface{}) {
    // DELETE /index/_doc/<id>
}

正式版需要加：

  • 把 lastIndex persist 到 DB / Redis（記憶體中的 map 重啟就丟了）
  • bulk index 而非逐筆呼叫 ES
  • 失敗回非 2xx 讓 rqlite 重送
  • 處理 ES 不可用時的 buffering 邏輯

22.8 運維建議

  • 盡早設 table_filter：只追蹤需要的 table，節省 queue 與網路
  • 降 high_watermark_interval 減少 leader 切換時的重送，代價是節點間流量小幅增加。寫入量大時值得
  • 調 max_batch_size 與 max_batch_delay：吞吐 vs 延遲取捨。寫入量大時兩者都該調大
  • 選對 retry policy：穩定 endpoint 用 Linear；不穩定（如雲端 API gateway）用 Exponential
  • 監控本地 queue size + 磁碟用量：infinite retries + endpoint 掛 = 磁碟爆滿
  • 用 TLS + 驗證 server cert；高安全需求加 mTLS
  • webhook handler 要快：重活丟給內部 queue / worker，避免長期 block 住 CDC 線程
  • 用 service_id 區分多叢集；同 webhook 接多源時必設
⚠ CDC 9.0 才有

CDC 在 rqlite 9.0（2025-09-15）才引入。如果你還在 v8 或更早，需先升級。如果跑 v9.0.1 之前的 v9 早期版本，部分設定欄位可能尚未支援，以你跑的版本的 source code 為準（cdc/config.go）。

🔵 開發者重點
  • at-least-once：handler 必須冪等或追 index 去重
  • row_ids_only 模式省流量，但 handler 要自己再 SELECT
  • 同事件可能來自不同 leader，但 index 始終單調
🟡 DevOps / SRE 重點
  • 務必設定有限 transmit_max_retries 或監控磁碟
  • table_filter 早設、service_id 必設（多叢集）
  • 監控 webhook 失敗率、queue depth、local disk
  • 正式環境用 mTLS

CH. 23SQLite Extensions

Developer DevOps

rqlite 支援 SQLite 的 Run-Time Loadable Extensions 機制。你可以載入自編或第三方 extension 來新增資料型別、自訂函式、向量搜尋、正則表達式、ICU 等能力。

23.1 為什麼要 extensions

SQLite 核心刻意精簡。許多進階能力以 extension 提供：

  • Sqlean：精選的實用函式集（regex、stats、UUID、time、crypto、math 等）
  • sqlite-vec：向量相似度搜尋（embeddings、RAG 應用必備）
  • sqliteai-vector：另一個 vector 引擎實作
  • SQLite ICU：Unicode-correct 字串比對、大小寫、正規化
  • SQLite Misc：rot13、carray、uuid、json1 之外的雜項函式
  • 你自編的 C extension

23.2 Docker 內建

rqlite 官方 Docker image 已經預編譯常用 extensions，啟用即可：

Extension用途Key
Sqlean實用函式集sqlean
sqlite-vec向量搜尋sqlite-vec
sqliteai-vector向量搜尋（另一實作）sqliteai-vector
SQLite ICUICU 國際化icu
SQLite Misc雜項函式（rqlite 選用子集）misc

啟用

用 SQLITE_EXTENSIONS 環境變數，逗號分隔 keys：

bash
# 同時啟用 sqlean + icu
docker run \
  -e SQLITE_EXTENSIONS='sqlean,icu' \
  -p 4001:4001 \
  rqlite/rqlite

啟用 vector 範例

bash
docker run \
  -e SQLITE_EXTENSIONS='sqlite-vec' \
  -p 4001:4001 \
  rqlite/rqlite

# 驗證
curl -G 'localhost:4001/db/query' \
  --data-urlencode 'q=SELECT vec_version()'

23.3 載入自編 extension

用不到 Docker、或內建 extension 沒你要的、或要用自己寫的 — 三步驟：

  1. 編譯 extension 為 shared library（.so / .dylib / .dll）
  2. 把編好的檔案放到 rqlite 機器
  3. 啟動 rqlited 時加 -extensions-path

編譯範例：rot13 與 carray

兩者皆來自 SQLite Misc。

bash
# 建立 extension 目錄
mkdir ~/extensions

# 編譯 .so
gcc -g -fPIC -shared rot13.c -o ~/extensions/rot13.so
gcc -g -fPIC -shared carray.c -o ~/extensions/carray.so

# （選用）打包成 zip — 方便傳輸
zip -j ~/extensions.zip \
  ~/extensions/rot13.so ~/extensions/carray.so
📌 平台依賴

Extension 是原生編譯產物，必須與 rqlite 跑的 OS / CPU 架構一致。Linux x86_64 編的 .so 不能拿到 macOS arm64 用。Docker 容器內跑要在容器內編，或用 cross-compile。

23.4 -extensions-path 用法

支援逗號分隔的多路徑，每個路徑可以是：

  • 單一 extension 檔（.so / .dylib / .dll）
  • 目錄（會把目錄裡所有檔當作 extension 嘗試載入）
  • Zip 檔（.zip）
  • Gzipped tarball（.tar.gz）
⚠ 壓縮檔必須 flat

Zip 與 tarball 內必須是扁平結構：解壓後檔案直接在根層、不能有子目錄。

三種啟動方式

bash
# 1. 整個目錄
rqlited -extensions-path=~/extensions data

# 2. Zip 檔
rqlited -extensions-path=~/extensions.zip data

# 3. 個別檔逗號分隔
rqlited -extensions-path=~/extensions/rot13.so,~/extensions/carray.so data
🚨 目錄模式會 "整個吃掉"

用目錄路徑時，rqlite 把目錄裡的每個檔案都當作 extension 載入。只放 extension 進去，別放 README、原始碼、log 檔。任一個檔載入失敗，整個 rqlited 會 exit。

驗證載入

啟動後在 rqlite shell 用 .extensions：

text
127.0.0.1:4001> .extensions
carray.so
rot13.so
127.0.0.1:4001> SELECT rot13("abc")
+--------------+
| rot13("abc") |
+--------------+
| nop          |
+--------------+

23.5 叢集一致性

🚨 叢集所有節點必須載入相同 extensions

多節點叢集中，如果某些節點有 extension X、其他沒有，當使用 X 函式的 SQL 透過 Raft 同步到所有節點時，沒載入 X 的節點會執行失敗，導致資料 diverge — undefined behaviour。

解法：

  • 把 extension 包進 Docker image 或 K8s ConfigMap，所有節點吃同一份
  • 用 Ansible / Puppet / Chef 確保每節點 /etc/rqlite/extensions/ 同步
  • 升級 extension 時做滾動部署，每節點重啟前先換好檔

23.6 應用範例：向量搜尋（sqlite-vec）

RAG / 語意搜尋現在很常見。用 rqlite + sqlite-vec 提供分散式的向量儲存：

啟動

bash
docker run -e SQLITE_EXTENSIONS='sqlite-vec' \
  -p 4001:4001 rqlite/rqlite

建立向量 table

bash
# 384 維 embedding（如 sentence-transformers/all-MiniLM-L6-v2）
curl -XPOST 'localhost:4001/db/execute' \
  -H "Content-Type: application/json" \
  -d '[
    "CREATE VIRTUAL TABLE docs_vec USING vec0(embedding float[384])"
  ]'

Python 端：用 sentence-transformers 產 embedding 並寫入

python
import requests
import json
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")

texts = [
    "rqlite 是分散式的 SQLite",
    "Raft 是共識演算法",
    "Kubernetes 用 StatefulSet 跑有狀態服務",
]

for i, txt in enumerate(texts, start=1):
    emb = model.encode(txt).tolist()
    requests.post(
        "http://localhost:4001/db/execute",
        json=[
            ["INSERT INTO docs_vec(rowid, embedding) VALUES(?, ?)",
             i, json.dumps(emb)]
        ],
    )

# 相似度搜尋（找 top 3 接近某個 query 的）
query = model.encode("分散式資料庫").tolist()
r = requests.post(
    "http://localhost:4001/db/query",
    json=[["SELECT rowid, distance FROM docs_vec "
            "WHERE embedding MATCH ? AND k = 3 "
            "ORDER BY distance", json.dumps(query)]]
)
print(r.json())

由於走 rqlite，自動有 HA + 容錯，比純 SQLite 部署多了分散式特性。注意：向量比較是 CPU 重的操作，大資料集還是該考慮專用 vector DB（Qdrant、Weaviate 等）。

23.7 Troubleshooting

載入失敗時的排查順序：

  1. 檢查 OS + 架構：file 指令確認 .so 是當前平台
  2. 用純 SQLite 驗證：先用 sqlite3 ":memory:" + .load /path/to/ext.so 試 — 連 SQLite 都載不起來，問題在 extension 本身或編譯
  3. 檔案權限：rqlite 跑的 user 要能讀 extension 檔（chmod 644 通常夠）
  4. 看 rqlite logs：journalctl -u rqlited -f 或 stdout，找 extension、load、dlopen 等關鍵字
  5. 檢查目錄內容：用目錄模式時，ls /path/to/dir/ 確認只有 extension 檔
  6. 還是不行？到 GitHub issues 提問
bash
# 純 SQLite 驗證 extension 能載
sqlite3 :memory:
sqlite> .load /home/me/extensions/rot13.so
sqlite> SELECT rot13('hello');
uryyb
🔵 開發者重點
  • Docker 跑時用 SQLITE_EXTENSIONS 環境變數最快
  • 向量搜尋：sqlite-vec 是首選
  • regex / ICU 等用 sqlean 或 icu
🟡 DevOps / SRE 重點
  • 叢集所有節點必須有一模一樣的 extensions，否則 undefined behaviour
  • extension 用 Docker image 或 ConfigMap 統一發布
  • 目錄模式只放 extension 檔，不放雜物
  • 升級先用純 SQLite 驗證新版 extension 能載

CH. 24Direct Access — 直接存取 SQLite 檔

DevOps

這是進階且危險的章節。多數應用應該完全只透過 rqlite HTTP API。但少數情境（例如本機跑 sqlite3 工具看資料、用 grafana SQLite datasource 直接讀某個節點），你會想直接讀 SQLite 檔。本章說明安全的做法，以及為何絕對不能直接寫。

24.1 為什麼這章標 ⚠️

🚨 違反本章規則 = 資料遺失

SQLite 不知道有 rqlite 存在；rqlite 預期它獨佔 SQLite 檔的某些控制權（WAL 模式、checkpointing、locking）。任何第三方寫入或某些「正常」的讀取行為（例如關閉連線時自動 checkpoint）都可能讓 rqlite 進入未定義狀態，導致：

  • 節點間資料 diverge
  • SQLite 檔損毀
  • Raft snapshot 失敗
  • 最壞情況：整叢集需要復原

24.2 永遠不能直接寫

所有資料變更必須透過 /db/execute 或 /db/request。不可：

  • 用 sqlite3 CLI 打開檔案下 INSERT / UPDATE / DELETE
  • 用任何 SQLite library（Python sqlite3、Go database/sql）開啟連線並寫入
  • 修改 journaling mode（rqlite 鎖定 WAL）
  • 手動 checkpoint WAL（PRAGMA wal_checkpoint）

違反任一項，行為 undefined。不會立刻爆炸，但下次 snapshot 或 leader 切換時很可能會出問題 — 屆時排查源頭極困難。

24.3 可以直接讀，但要遵守這些規則

規則 1：作業系統層強制 read-only

把 SQLite 檔的目錄權限設成「該 user 不能寫」。多保險：

bash
# 假設 rqlite data 在 /var/rqlite/data/db/
# 監控 / 讀取 user = grafana

# 把 SQLite 主檔 + WAL + SHM 設成 grafana 可讀不可寫
setfacl -m u:grafana:r /var/rqlite/data/db/db.sqlite
setfacl -m u:grafana:r /var/rqlite/data/db/db.sqlite-wal
setfacl -m u:grafana:r /var/rqlite/data/db/db.sqlite-shm
📌 三個檔案都要保護

SQLite WAL 模式下有三個檔案：

  • 主資料庫檔（如 db.sqlite）
  • WAL 檔（.sqlite-wal）
  • SHM 檔（.sqlite-shm，shared memory）

第三方只需要讀；任一檔被誤寫都會傷叢集。

規則 2：SQLite client 必須開 read-only 連線

OS 層權限是「最後一道防線」。但應用層也要明確開 read-only，避免 client library 嘗試取 write lock 或 close 時 checkpoint。

SQLite C API

用 sqlite3_open_v2 + SQLITE_OPEN_READONLY。

filename URI

更通用的做法是用 SQLite filename URI 配 mode=ro：

python
import sqlite3

# Python 標準庫；uri=True 啟用 URI 模式
conn = sqlite3.connect(
    "file:/var/rqlite/data/db/db.sqlite?mode=ro&immutable=1",
    uri=True,
)
try:
    rows = conn.execute("SELECT COUNT(*) FROM users").fetchall()
    print(rows)
finally:
    conn.close()

mode=ro 強制 read-only；immutable=1 進一步告訴 SQLite 「假設此檔不會被任何人修改」— 但要謹慎使用，rqlite 一直在實際修改檔，immutable=1 可能讓你的 client 看到 stale snapshot。

go
// Go (mattn/go-sqlite3)
import (
    "database/sql"
    _ "github.com/mattn/go-sqlite3"
)

db, err := sql.Open(
    "sqlite3",
    "file:/var/rqlite/data/db/db.sqlite?mode=ro&_journal=WAL",
)

規則 3：不要用 EXCLUSIVE locking

絕對不要 PRAGMA locking_mode = EXCLUSIVE。這會獨佔 SQLite 檔，block rqlite 自己的存取，叢集會卡住。

🚨 為什麼讀取也可能搞砸

SQLite client 即使沒寫任何資料，關閉連線時可能會 checkpoint WAL。Checkpoint 改變 db 狀態，rqlite 對它的 WAL state 計算就錯了。所以「規則 1 + 規則 2 + 規則 3」三道防線都要做：權限禁止 + ro mode + 不 EXCLUSIVE。

⚠ 在 production 直接讀並非「extensively tested」

官方文件原話："while direct reads in production are a known use case, it has not been extensively tested"。這是一個 documented 但 lightly tested 的能力，使用時自己承擔風險。

24.4 長查詢的衝擊

rqlite 會週期性對 SQLite 取 exclusive access 做 snapshot。如果有第三方 read transaction 拿著 lock（很長的 SELECT、未 close 的 cursor），snapshot 可能被 block。

  • 偶爾遇上：rqlite 自動 retry，沒事
  • 持續遇上：snapshot 不能完成 → Raft log 不斷增長 → 磁碟用量、查詢效能變差

實務上 snapshot 通常數毫秒完成，衝突機率不高，但要監控：

  • store.raft.last_snapshot_index 是否定期推進
  • log 是否有 snapshot 重試訊息
  • 磁碟用量是否異常增長

24.5 範例：Grafana 直接讀 rqlite 節點做監控儀表板

常見場景：你已經有 Grafana 跑在同一台 / 鄰近機器，想直接用 SQLite datasource 撈 rqlite 的某張統計 table，避免再多寫 HTTP API consumer。

選哪個節點

  • 不要打 leader：leader 已忙著 Raft consensus + 寫 SQLite，加上 read 流量會搶 IO
  • 選一個 follower 或 read-only 節點
  • 該節點的 data 目錄要 grafana 可達（local file 或 NFS/CIFS 共享）

權限設定

bash
# 加 ACL 給 grafana user，只給 read
setfacl -m u:grafana:r /var/rqlite/data/db/db.sqlite{,-wal,-shm}

# 確認
getfacl /var/rqlite/data/db/db.sqlite

Grafana datasource 設定

Grafana SQLite 外掛允許自訂連線字串。確保填上 ro mode：

text
# 連線字串範例
file:/var/rqlite/data/db/db.sqlite?mode=ro

建議 query 模式

  • 短而頻繁的 query（每幾秒拉幾筆計數）
  • 避免 SELECT * 掃大表
  • 避免長 transaction
  • 用 cursor / fetchmany 而非一次撈進記憶體（但 query 還是要快）

替代方案

如果這套設定讓你不安，更穩妥的做法：

  1. 用 read-only node 在邊緣，client（含 Grafana）只打 http://read-only:4001/db/query?level=none&freshness=5s
  2. 透過正常 HTTP API 取資料，無風險
  3. Grafana 用 JSON datasource / SimpleJson + 一個輕量 proxy 把 HTTP 結果轉成 Grafana 喜歡的格式
🟡 DevOps / SRE 重點
  • 絕對不能直接寫 SQLite 檔，包括 PRAGMA 等元命令
  • 讀取必須三道防線：OS read-only ACL + client mode=ro + 禁用 EXCLUSIVE
  • 三個檔都要保護：主 db + WAL + SHM
  • 選 follower / read-only 節點直讀，不選 leader
  • 長查詢可能 block snapshot — 監控 last_snapshot_index 推進
  • 有疑慮就走 HTTP API + level=none&freshness
