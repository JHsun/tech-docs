Chapter 07

Volume Snapshot 與 Volume Group Snapshot

Volume Snapshot 讓你在不停止應用程式的前提下，對 PV 建立時間點快照（point-in-time snapshot）。 快照可用於備份、複製（clone）測試資料，或快速還原生產事故後的狀態。

7.1　三元組資源架構

資源類比建立者說明
VolumeSnapshotClass 類似 StorageClass 管理員 定義哪個 CSI driver 處理 snapshot、deletionPolicy（Delete / Retain）
VolumeSnapshot 類似 PVC 開發者 申請建立一個快照，指向來源 PVC；namespace-scoped
VolumeSnapshotContent 類似 PV 系統自動（動態）或管理員（靜態） 代表底層實際的 snapshot 物件；cluster-scoped

7.2　動態 Snapshot 建立與還原全流程

7.3　完整 YAML 範例（建立 → 驗證 → 還原 → 刪除）

snapshot-class.yaml · VolumeSnapshotClass 
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata:
  name: ebs-vsc
  annotations:
    # 設為 default snapshot class
    snapshot.storage.kubernetes.io/is-default-class: "true"
driver: ebs.csi.aws.com
deletionPolicy: Delete         # Retain = 刪 VolumeSnapshot 時保留底層 snapshot
parameters:
  # AWS 特定：snapshot 描述
  csi.storage.k8s.io/snapshotter-secret-name: aws-secret
  csi.storage.k8s.io/snapshotter-secret-namespace: kube-system
snapshot-create.yaml · 建立 VolumeSnapshot 
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: postgres-snap-20260516
  namespace: production
spec:
  volumeSnapshotClassName: ebs-vsc
  source:
    persistentVolumeClaimName: postgres-data   # 來源 PVC
bash · 監控 snapshot 狀態 
# 等待 snapshot 就緒
kubectl wait volumesnapshot postgres-snap-20260516 \
  -n production \
  --for=jsonpath='{.status.readyToUse}'=true \
  --timeout=5m

# 查看詳情（含 snapshot handle 與大小）
kubectl describe volumesnapshot postgres-snap-20260516 -n production

# 查看底層 VolumeSnapshotContent
kubectl get volumesnapshotcontent \
  -o custom-columns="NAME:.metadata.name,HANDLE:.status.snapshotHandle,READY:.status.readyToUse"
pvc-from-snapshot.yaml · 從 Snapshot 還原新 PVC 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data-restored
  namespace: production
spec:
  storageClassName: aws-gp3
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 50Gi             # 必須 >= 原始 snapshot 大小
  dataSource:
    name: postgres-snap-20260516
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io

7.4　Volume Group Snapshot Beta

Volume Group Snapshot 讓你對多個 PVC同時建立一致性快照（crash-consistent group snapshot）。 這對需要跨多個 volume 保持資料一致性的場景（如：database data + wal + config 各自是獨立 PVC）非常重要。

volume-group-snapshot.yaml · 多 PVC 一致性快照 
apiVersion: groupsnapshot.storage.k8s.io/v1beta1
kind: VolumeGroupSnapshot
metadata:
  name: postgres-group-snap
  namespace: production
spec:
  volumeGroupSnapshotClassName: ebs-group-vsc
  source:
    selector:
      matchLabels:
        app: postgres           # 同時快照所有帶此 label 的 PVC
⚠

external-snapshotter v8.4 重要變更：validation webhook 已自 v8.0 起完全移除；Group Snapshot 功能需透過 feature gate 啟用（--feature-gates=CSIVolumeGroupSnapshot=true）；VolumeGroupSnapshot v1beta1 API 已標記為 deprecated，預計遷移至 v1beta2。升級前請確認版本相容性。

7.5　Distributed Snapshotting（Local Volume 專用）

Local volume 的 snapshot 需要 snapshot sidecar 部署在每個節點（而非集中式 StatefulSet）， 讓每個節點只管理自己本地的 snapshot 操作：

bash · 啟用 distributed snapshotting 
# 在 Node DaemonSet 的 csi-snapshotter sidecar 加入以下 args：
# --enable-distributed-snapshotting=true
# --node-deployment=true
# 並設定 NODE_NAME 環境變數指向所在節點名稱

# 同時在 snapshot-controller 加入：
# --enable-distributed-snapshotting=true
# 讓 controller 知道 distributed mode 已啟用

8.2　PVC Clone

PVC Clone 讓你直接從一個現有 PVC 建立另一個內容完全相同的新 PVC， 常用於建立測試環境的資料副本。

pvc-clone.yaml · 從現有 PVC 複製 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data-clone          # 新 PVC
  namespace: staging
spec:
  storageClassName: aws-gp3          # 必須與來源 PVC 相同 StorageClass
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 50Gi                  # 必須 >= 來源 PVC 容量
  dataSource:
    name: postgres-data              # 來源 PVC 名稱（必須同 namespace）
    kind: PersistentVolumeClaim
!

Clone 限制：來源 PVC 與目標 PVC 必須在同一個 namespace（除非使用 Cross-namespace DataSource），且 StorageClass 必須相同。Clone 是 CSI driver 層面的實作，不同 driver 的實作方式不同（有些用 snapshot + restore、有些直接 copy-on-write）。

8.3　Cross-namespace Volume DataSource

預設 PVC 的 dataSource 只能指向同 namespace 的資源。 Cross-namespace DataSource 透過 ReferenceGrant（Gateway API 的概念）讓跨 namespace 的 PVC Clone 和 Snapshot 還原成為可能。

cross-ns-datasource.yaml · 跨 namespace 還原範例 
# Step 1：在來源 namespace（production）建立 ReferenceGrant
# 授權 staging namespace 的 PVC 可以引用 production 的 VolumeSnapshot
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-staging-snapshot-access
  namespace: production              # 授權者所在的 namespace
spec:
  from:
    - group: ""
      kind: PersistentVolumeClaim
      namespace: staging             # 被授權的 namespace
  to:
    - group: snapshot.storage.k8s.io
      kind: VolumeSnapshot

---
# Step 2：在 staging namespace 建立引用 production snapshot 的 PVC
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-from-prod-snap
  namespace: staging
spec:
  storageClassName: aws-gp3
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 50Gi
  dataSourceRef:                     # 使用 dataSourceRef（非 dataSource）支援跨 ns
    apiGroup: snapshot.storage.k8s.io
    kind: VolumeSnapshot
    name: postgres-snap-20260516
    namespace: production            # 來源 namespace

Chapter 09

主流 CSI Driver 實戰（雲端）

9.1　AWS EBS CSI Driver

AWS EBS CSI Driver 是 EKS 叢集的標準區塊儲存方案，支援 gp3、io2（Block Express）、sc1、st1 等多種磁碟類型。 2026 年建議使用 gp3 作為預設（比 gp2 更彈性、更便宜），io2 Block Express 用於高效能資料庫。

bash · EKS 安裝 EBS CSI Driver（Add-on 方式） 
# 方法一：EKS Managed Add-on（建議）
aws eks create-addon \
  --cluster-name my-cluster \
  --addon-name aws-ebs-csi-driver \
  --service-account-role-arn arn:aws:iam::123:role/AmazonEKS_EBS_CSI_DriverRole

# 方法二：Helm
helm repo add aws-ebs-csi-driver \
  https://kubernetes-sigs.github.io/aws-ebs-csi-driver
helm upgrade --install aws-ebs-csi-driver \
  aws-ebs-csi-driver/aws-ebs-csi-driver \
  --namespace kube-system \
  --set controller.serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=\
arn:aws:iam::123:role/AmazonEKS_EBS_CSI_DriverRole
aws-storageclasses.yaml · gp3 + io2 StorageClass 
# gp3：一般用途（預設）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: aws-gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
reclaimPolicy: Delete

allowVolumeExpansion: true

---
# io2 Block Express：高效能資料庫（Postgres、MySQL primary）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: aws-io2-block-express
provisioner: ebs.csi.aws.com
parameters:
  type: io2
  iops: "64000"              # 最高 256,000（Block Express）
  encrypted: "true"
  blockExpress: "true"       # 啟用 Block Express 模式
reclaimPolicy: Retain        # 生產資料庫用 Retain 保險

9.2　GCP Hyperdisk CSI Driver

GCP Hyperdisk 是 GKE 的新世代區塊儲存，支援 VolumeAttributesClass 動態調整 IOPS/throughput， 不需重建 PVC 即可變更效能等級。

gcp-hyperdisk-setup.yaml · Hyperdisk + VolumeAttributesClass 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gcp-hyperdisk
provisioner: pd.csi.storage.gke.io
parameters:
  type: hyperdisk-balanced
  replication-type: none
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true

---
apiVersion: storage.k8s.io/v1
kind: VolumeAttributesClass
metadata:
  name: hd-silver
driverName: pd.csi.storage.gke.io
parameters:
  provisioned-iops: "3000"
  provisioned-throughput: "150"

---
apiVersion: storage.k8s.io/v1
kind: VolumeAttributesClass
metadata:
  name: hd-gold
driverName: pd.csi.storage.gke.io
parameters:
  provisioned-iops: "10000"
  provisioned-throughput: "500"

---
# PVC 使用 Hyperdisk，初始 silver，可無停機切換到 gold
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-db
spec:
  storageClassName: gcp-hyperdisk
  volumeAttributesClassName: hd-silver
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 200Gi

9.4　NFS CSI Driver（on-prem / 跨雲 RWX）

NFS CSI Driver（nfs.csi.k8s.io）是最通用的 ReadWriteMany 解決方案， 適合需要多個 Pod 同時讀寫同一目錄的場景（如：共享 model weights、media files）。

nfs-csi-install.yaml · NFS CSI Driver 安裝與設定 
# Helm 安裝 NFS CSI Driver v4.13
helm repo add csi-driver-nfs \
  https://raw.githubusercontent.com/kubernetes-csi/csi-driver-nfs/master/charts
helm install csi-driver-nfs csi-driver-nfs/csi-driver-nfs \
  --namespace kube-system \
  --version v4.13.0
nfs-storageclass.yaml · NFS 動態 Provisioning（subdir） 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-rwx
provisioner: nfs.csi.k8s.io
parameters:
  server: 10.0.0.5                    # NFS server IP
  share: /exports/k8s
  subDir: ${pvc.metadata.namespace}/${pvc.metadata.name}
  onDelete: retain                    # 保留子目錄（delete = 直接刪）
  mountPermissions: "0777"
reclaimPolicy: Delete
volumeBindingMode: Immediate
allowVolumeExpansion: false
mountOptions:
  - nfsvers=4.1
  - hard
  - timeo=600
  - retrans=3

Chapter 10

Rook-Ceph：K8s Native 分散式儲存

Rook 是 CNCF Graduated 專案，讓 Ceph 這個企業級分散式儲存系統以 Kubernetes-native 的方式運作—— 用 CRD 宣告式管理整個 Ceph 叢集，operator 負責部署、監控、自癒、升級。 對需要 on-prem 自建儲存的團隊，Rook-Ceph 是 2026 年最主流的選擇。

版本基準：Rook v1.18 · 最低 K8s v1.30 · 最低 Ceph v19.2.0（Squid）

10.1　核心元件架構

10.5　生產注意事項

  • OSD 記憶體：每個 OSD 建議 4GiB request，8GiB limit。記憶體不足時 OSD 會被 OOM-killed，導致資料重新平衡（rebalancing），影響效能與資料安全。
  • PG Autoscaler：務必啟用 pg_autoscaler module，避免手動計算 Placement Group 數量。PG 數量不對會嚴重影響效能與容量利用率。
  • 儲存使用率警戒線：Ceph 在使用率超過 80% 時效能顯著下降，超過 85% 時會拒絕寫入（nearfull），超過 95% 時完全停寫（full）。建議 70% 時就開始擴容。
  • 裸磁碟：OSD 節點的磁碟必須是未格式化的裸磁碟（raw device）。Rook 會跳過已有 filesystem 或 partition table 的磁碟。
  • MON 跨 failure domain：3 個 MON 必須分布在 3 個不同節點（ideally 不同機架），避免單節點故障導致 quorum 喪失。
Chapter 11

OpenEBS：Container-Native 本機儲存

OpenEBS 採用 Container-Native 架構，所有儲存邏輯以容器形式運行在 Kubernetes 內部， 不依賴外部儲存陣列。v4.4 引入統一的 umbrella chart 和 kubectl openebs plugin， 讓多種引擎的管理更加一致。

11.1　四大引擎選型

L1 · 最簡單
LocalPV HostPath
  • 直接掛載節點本機目錄
  • 零配置，最低延遲
  • 無 HA，節點掛掉資料不可用
  • 適合：CI/CD、開發環境、暫存資料
L2 · 本機 Block
LocalPV LVM
  • LVM Volume Group 管理 block device
  • 支援 thin provisioning、Snapshot Restore（v4.4）
  • CSIStorageCapacity 感知容量
  • 適合：高效能單節點 DB、SSD 資料
L2 · 本機 Block
LocalPV ZFS
  • ZFS pool 管理，內建 snapshot、clone、壓縮
  • 支援加密 ZFS pool 的 backup/restore
  • 資料完整性驗證（checksums）
  • 適合：需要 snapshot 的本機儲存
L3 · 複製儲存
Replicated PV Mayastor
  • NVMe-oF（NVMe over TCP / RDMA）複製儲存
  • N-way 同步複製（跨節點 HA）
  • DiskPool Expansion、at-rest encryption（v4.3+）
  • 適合：需要 HA 的高效能資料庫

設計模式、故障診斷與最佳實踐

12.1　StorageClass 設計模式

模式一：分層儲存（Tiered Storage）

針對不同工作負載的效能需求設計不同 tier，讓開發者透過 StorageClass 名稱選擇合適層級， 不需要瞭解底層細節。

TierStorageClass後端適用場景
🥉 Bronzehdd-bulkAWS st1 / Azure HDD / Ceph HDD OSD日誌歸檔、備份、冷資料（低 IOPS 容忍）
🥈 Silverssd-standardAWS gp3 / GCP Hyperdisk / Ceph SSD OSDWeb 應用、API server、一般 DB replica
🥇 Goldssd-fastAWS io2 / GCP Hyperdisk high IOPS / Azure Premium SSD v2DB Primary（Postgres、MySQL）
💎 Platinumnvme-ultraAWS io2 Block Express / OpenEBS Mayastor NVMe-oF高頻交易、時序資料庫、OLAP

模式二：Read-heavy vs Write-heavy 拓撲

  • Read-heavy（如：報表、分析）：考慮 CephFS RWX + ReadOnlyMany，讓多個 Pod 共享同一份資料。
  • Write-heavy（如：OLTP 主庫）：單一 RWO volume，最小化複製開銷；搭配 WAL 獨立 volume 減少 IO 競爭。
  • 混合型：主庫用 RWO 高效能 volume，replica 用 snapshot 建立，replica 的 PVC 用成本較低的 StorageClass。

StorageClass RBAC

限制哪些 namespace 可以使用哪些 StorageClass，避免開發者誤用高成本的生產用 StorageClass：

storageclass-rbac.yaml · 限制 StorageClass 使用權限

  name: use-platinum-storageclass
rules:
  - apiGroups: ["storage.k8s.io"]
    resources: ["storageclasses"]
    resourceNames: ["nvme-ultra"]
    verbs: ["get", "list"]

---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: allow-platinum-sc
  namespace: finance-production        # 只有這個 namespace 可以使用
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: use-platinum-storageclass
subjects:
  - kind: ServiceAccount
    name: default
    namespace: finance-production

Encryption at Rest

三種加密方案，依成熟度排序：

  • CSI driver 原生加密（最簡單）：AWS EBS encrypted: "true"、GCP Disk CMK、Azure SSE。直接在 StorageClass parameters 設定，零額外組件。
  • OpenEBS Mayastor at-rest encryption（v4.3+ GA）：DiskPool 層級加密，key 由使用者管理。
  • Vault CSI Provider（最彈性）：透過 Vault Agent Injector 和 Secrets Store CSI Driver，從 HashiCorp Vault 動態取得加密 key，支援 key rotation，適合合規要求嚴格的場景。

12.6　可觀測性：Prometheus 告警規則

prometheus-storage-alerts.yaml · 關鍵儲存告警 
groups:
  - name: kubernetes-storage
    rules:
      # PVC 容量使用率過高
      - alert: PVCAlmostFull
        expr: |
          (kubelet_volume_stats_used_bytes /
           kubelet_volume_stats_capacity_bytes) > 0.80
        for: 5m
        labels:
          severity: P2
        annotations:
          summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} 使用率超過 80%"
          description: "目前使用率：{{ $value | humanizePercentage }}"

      # PVC 容量即將耗盡（預測 24h 內滿）
      - alert: PVCFillingUp
        expr: |
          (predict_linear(
            kubelet_volume_stats_available_bytes[6h], 24*3600
          ) < 0) and
          (kubelet_volume_stats_used_bytes /
           kubelet_volume_stats_capacity_bytes > 0.70)
        for: 1h
        labels:
          severity: P1
        annotations:
          summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} 預測 24 小時內耗盡"

      # PVC 進入 Pending 狀態過久（動態 Provisioning 失敗）
      - alert: PVCPendingTooLong
        expr: |
          kube_persistentvolumeclaim_status_phase{phase="Pending"} == 1
        for: 15m
        labels:
          severity: P2
        annotations:
          summary: "PVC {{ $labels.namespace }}/{{ $labels.persistentvolumeclaim }} Pending 超過 15 分鐘"

      # Ceph 叢集健康警告（透過 Rook metrics）
      - alert: CephClusterHealthWarning
        expr: ceph_health_status == 1
        for: 5m
        labels:
          severity: P2
        annotations:
          summary: "Ceph 叢集進入 HEALTH_WARN 狀態"

      # Ceph 儲存使用率接近警戒線
      - alert: CephOSDNearFull
        expr: |
          (ceph_osd_stat_bytes_used / ceph_osd_stat_bytes) > 0.75
        for: 10m
        labels:
          severity: P1
        annotations:
          summary: "Ceph OSD {{ $labels.ceph_daemon }} 使用率超過 75%"
