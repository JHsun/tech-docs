Chapter 01

Kubernetes 儲存體系概覽

容器天生是無狀態的：Pod 重啟後，寫入本機檔案系統的資料全數消失。 對資料庫、訊息佇列、日誌收集器這類有狀態工作負載（stateful workloads）而言， 這是致命限制。Kubernetes 透過 Persistent Volume 子系統解決這個問題—— 把儲存資源的供應（由叢集管理員負責）與消費（由開發者負責）完全解耦。

1.1　四層儲存抽象

資源角色由誰建立版本狀態
PersistentVolume 代表一份實體儲存（NFS mount、EBS volume、Ceph RBD image…） 管理員（靜態）或 StorageClass（動態） GA
PersistentVolumeClaim 開發者「申請」儲存的方式，描述容量與 access mode 需求 開發者 / StatefulSet GA
StorageClass 定義動態 provisioning 的參數（provisioner、reclaim policy、parameters） 管理員 GA
VolumeAttributesClass 定義 PV 的可動態修改屬性（IOPS、throughput） 管理員 v1.34 GA

1.2　靜態 vs 動態 Provisioning

靜態 Provisioning 適合管理員已預先知道儲存規格的場景（例如：on-prem NFS、特定 LUN）。 動態 Provisioning 是雲端環境的主流，透過 StorageClass 讓 PVC 自動觸發底層儲存建立， 開發者無需瞭解底層細節。

1.3　In-tree Plugin 淘汰與 CSI 遷移

Kubernetes 早期把儲存驅動直接寫進核心（in-tree）。隨著雲廠商數量爆增，維護成本過高， 社群決定全面遷移至 CSI（Container Storage Interface）——一個獨立於核心的標準化介面。

Plugin遷移版本狀態（2026/05）
AWS EBSv1.17 alpha → v1.23 GA預設使用 CSI，in-tree 已移除
GCE PDv1.17 alpha → v1.23 GA預設使用 CSI，in-tree 已移除
Azure Diskv1.19 alpha → v1.24 GA預設使用 CSI，in-tree 已移除
portworxVolumev1.31 預設開啟遷移遷移進行中
NFS無 in-tree 遷移（原本就是 out-of-tree）直接用 nfs.csi.k8s.io

設計哲學：PV 是叢集資源（不屬於任何 namespace），PVC 是namespace 資源。這個隔離讓管理員可以統一管理底層儲存，同時讓各 namespace 的開發者自行申請使用，互不干擾。

Chapter 02

PersistentVolume（PV）深度解析

PV 是叢集層級的儲存資源，生命週期獨立於任何使用它的 Pod。 理解 PV 的各個欄位與生命週期狀態，是正確設計持久化儲存的基礎。

2.1　PV 生命週期六階段

1
Provisioning — 供應
靜態（管理員手動 kubectl apply）或動態（StorageClass + CSI Provisioner 自動建立）。
2
Binding — 綁定
Control loop 找到符合條件的 PVC，將 PV 與 PVC 一對一綁定（status.phase: Bound）。動態 Provisioning 的 PV 必定綁定觸發它的 PVC。
3
Using — 使用中
Pod 透過 PVC 掛載 PV，資料讀寫正常進行。kubelet 呼叫 CSI NodeStageVolume / NodePublishVolume 完成掛載。
4
Releasing — 釋放中
PVC 被刪除後，PV 進入 Released 狀態。此時 PV 已不再綁定，但底層資料尚未清除。
5
Reclaiming — 回收
依 persistentVolumeReclaimPolicy 決定後續：Delete（自動刪除底層儲存）或 Retain（保留資料，需人工清理）。
6
Deleting — 刪除
Delete policy 時，CSI DeleteVolume 呼叫後底層資源釋放，PV 物件從 etcd 移除。Retain policy 時，PV 物件留存，需管理員手動刪除。

2.2　Access Modes

RWO
ReadWriteOnce
只能被單一節點掛載為讀寫。最常見模式，EBS、Azure Disk 預設支援。
ROX
ReadOnlyMany
可被多個節點同時掛載，但僅限唯讀。適合靜態資源（config、image）共享。
RWX
ReadWriteMany
可被多個節點同時掛載為讀寫。需要 NFS、CephFS、Azure Files 等支援；EBS 不支援。
RWOP
ReadWriteOncePod
只能被單一 Pod掛載（比 RWO 更嚴格）。v1.29 Beta，確保跨節點也只有一個 Pod 能寫入。

2.3　Reclaim Policy 比較

PolicyPVC 刪除後 PV 狀態底層資料適用場景
Delete（預設） PV 自動刪除 自動清除（EBS volume、GCE PD 等） 雲端動態 Provisioning，資料不需保留
Retain PV 進入 Released，需手動清理 保留，需管理員手動刪除或重新綁定 生產環境重要資料，避免意外刪除
Recycle ⚠️ 已廢棄（deprecated），勿使用
⚠

Retain 後的手動重新綁定：PV 進入 Released 後，即使容量與 access mode 完全相符，也不會自動重新綁定新 PVC，因為 spec.claimRef 仍殘留舊 PVC 的資訊。必須手動移除 claimRef 欄位後，PV 才會回到 Available。

2.4　volumeMode：Filesystem vs Block

volumeMode掛載方式適用場景
Filesystem（預設） 格式化後掛載為目錄，容器透過標準 POSIX I/O 存取 一般應用程式、Web server、log 儲存
Block 原始 block device 直接掛載，不格式化 資料庫（自管 I/O buffer）、虛擬機磁碟、需要最低延遲的場景

2.5　lastPhaseTransitionTime v1.31 Stable

v1.31 Stable 後，PV 的 .status 包含 lastPhaseTransitionTime， 記錄 PV 最後一次切換 Phase 的時間戳。對監控和 audit 非常有用：

bash · 查看 PV Phase 切換時間 
kubectl get pv pv-postgres-data \
  -o jsonpath='{.status.lastPhaseTransitionTime}'
# 輸出範例：2026-05-16T14:32:00Z

# 找出所有在過去 1 小時內 phase 改變的 PV（Released 可能是 PVC 意外刪除）
kubectl get pv -o json | jq -r '
  .items[] |
  select(.status.lastPhaseTransitionTime > "2026-05-16T13:00:00Z") |
  "\(.metadata.name) \(.status.phase) \(.status.lastPhaseTransitionTime)"
'

2.6　靜態 Provisioning 完整範例（NFS）

pv-nfs-static.yaml · 靜態 PV 建立 
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-postgres
  labels:
    app: postgres
    env: production
spec:
  capacity:
    storage: 100Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: nfs-retain           # 對應 PVC 的 storageClassName
  mountOptions:
    - hard
    - nfsvers=4.1
    - timeo=600
  nfs:
    path: /exports/postgres-data
    server: nfs.internal.example.com
  # v1.31+：Phase 切換時間由系統自動填入 status.lastPhaseTransitionTime

2.7　Local Volume 與 Node Affinity

Local volume 讓 PV 直接對應節點上的本機磁碟（SSD、NVMe），提供最低延遲。 但因為資料只在特定節點，必須設定 nodeAffinity，否則 Pod 可能被調度到沒有該磁碟的節點。

pv-local.yaml · Local PV 含 nodeAffinity 
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-local-nvme-worker01
spec:
  capacity:
    storage: 500Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Delete
  storageClassName: local-nvme        # 需搭配 WaitForFirstConsumer
  local:
    path: /mnt/nvme0n1                # 節點上的本機路徑
  nodeAffinity:                       # 必填！限制只有這個節點可以使用
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - worker-01
Chapter 03

PersistentVolumeClaim（PVC）與 Binding 機制

PVC 是開發者與儲存系統之間的合約——開發者描述「我需要什麼」， Kubernetes 負責找到或建立符合條件的 PV 來滿足。 理解 Binding 的四項條件和 WaitForFirstConsumer 機制， 能避免許多生產環境中 PVC 無法綁定的問題。

3.1　PVC Spec 全欄位解析

pvc-annotated.yaml · 完整欄位說明 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
  namespace: production
spec:
  # ── 存取模式（必須與 PV 相容）
  accessModes:
    - ReadWriteOnce

  # ── 容量請求（PV 容量必須 >= 此值）
  resources:
    requests:
      storage: 50Gi

  # ── StorageClass 名稱（空字串 "" = 禁止動態 Provisioning）
  storageClassName: fast-ssd

  # ── volumeMode：Filesystem（預設）或 Block
  volumeMode: Filesystem

  # ── Selector：靜態 Provisioning 時用來篩選特定 PV
  selector:
    matchLabels:
      env: production
    matchExpressions:
      - key: tier
        operator: In
        values: [gold, platinum]

  # ── VolumeAttributesClass（v1.34 GA）：初始 QoS profile
  volumeAttributesClassName: gold-iops

  # ── DataSource：從 Snapshot 或另一個 PVC 建立（Clone）
  dataSource:
    name: postgres-snapshot-20260516
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io

3.2　Binding 四項條件

PVC 要與 PV 綁定，必須同時滿足：

條件說明常見誤區
Capacity PV capacity >= PVC 請求量 PV 100Gi 可綁 PVC 50Gi；PV 30Gi 不能綁 PVC 50Gi
Access Modes PV 支援的 access modes 必須包含 PVC 要求的 PVC 要 RWX，但 PV 只有 RWO → 無法綁定
StorageClass PV 與 PVC 的 storageClassName 必須完全相同 PVC 未設 storageClassName 會綁 default StorageClass（若啟用 admission plugin）
Selector 若 PVC 有 selector，PV 必須符合 label 條件 靜態 Provisioning 常見問題：PV label 忘記加

3.4　WaitForFirstConsumer — 拓撲感知排程

預設的 volumeBindingMode: Immediate 會在 PVC 建立當下立刻找 PV（或觸發 Provisioning）。 對於 Local Volume 或跨 AZ 情境，這可能造成 Pod 被迫調度到「有 PV 但不適合」的節點。

WaitForFirstConsumer 讓 Binding（或動態 Provisioning）延遲到 Pod 被調度後才發生， Scheduler 可以同時考慮 Pod 的 affinity、resource、topology 等約束，再選擇合適的節點和 PV。

sc-local-wait.yaml · WaitForFirstConsumer 範例 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local-nvme
provisioner: kubernetes.io/no-provisioner   # Local volume 無動態 provisioner
volumeBindingMode: WaitForFirstConsumer     # 等 Pod 排程後再綁定
reclaimPolicy: Delete
!

CSIStorageCapacity 整合：WaitForFirstConsumer 搭配 CSIStorageCapacity 物件，讓 Scheduler 在選節點時能感知各節點的可用儲存容量，避免把 Pod 調度到儲存空間不足的節點。需要 CSI driver 的 external-provisioner 啟用 --enable-capacity 旗標。

3.5　StatefulSet volumeClaimTemplates

StatefulSet 的每個 replica 都需要獨立的持久化儲存，透過 volumeClaimTemplates 自動為每個 Pod 建立獨立 PVC（命名規則：{template-name}-{pod-name}）。

statefulset-postgres.yaml · volumeClaimTemplates 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: production
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
            - name: wal
              mountPath: /var/lib/postgresql/wal
  volumeClaimTemplates:
    # PVC 命名：data-postgres-0, data-postgres-1, data-postgres-2
    - metadata:
        name: data
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: fast-ssd
        resources:
          requests:
            storage: 50Gi
    # 獨立 WAL volume，使用更高效能的 StorageClass
    - metadata:
        name: wal
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: ultra-ssd
        resources:
          requests:
            storage: 20Gi
v1.32

Orphaned PVC 自動清理（v1.32）：StatefulSet 縮減副本數時，之前遺留的 PVC（orphaned PVCs）現在可以自動刪除，不再需要手動清理。這個行為由 persistentVolumeClaimRetentionPolicy 欄位控制（whenDeleted / whenScaled）。

3.6　PVC Protection Finalizer 與 Terminating 卡住

Kubernetes 在 PVC 上自動加入 kubernetes.io/pvc-protection finalizer， 防止正在被 Pod 使用的 PVC 被意外刪除。若刪除 PVC 後卡在 Terminating：

bash · PVC Terminating 排查與強制清理 
# 確認是否有 Pod 仍在使用該 PVC
kubectl get pods -n production -o json | jq -r '
  .items[] |
  select(.spec.volumes[]?.persistentVolumeClaim.claimName == "postgres-data") |
  .metadata.name'

# 若 Pod 已刪除，但 PVC 仍 Terminating：手動移除 finalizer
kubectl patch pvc postgres-data -n production \
  -p '{"metadata":{"finalizers":[]}}' \
  --type=merge

# 注意：強制移除 finalizer 前請確認 Pod 已完全終止，
# 否則可能造成資料損壞
Chapter 04

StorageClass 設計與實作

StorageClass 是動態 Provisioning 的核心配置物件， 定義了「用哪個 provisioner」、「用什麼參數」、「如何回收」。 設計良好的 StorageClass 體系，能讓整個叢集的儲存管理清晰且可維護。

4.1　核心欄位解析

storageclass-annotated.yaml · 完整欄位說明 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    # 設為 default StorageClass（整個叢集只建議一個）
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com           # CSI driver 名稱
parameters:                            # 傳給 provisioner 的參數（各 driver 不同）
  type: gp3
  iops: "3000"
  throughput: "125"
  encrypted: "true"
  kmsKeyId: arn:aws:kms:us-east-1:123:key/xxx
reclaimPolicy: Delete                  # Delete（預設）或 Retain
volumeBindingMode: WaitForFirstConsumer  # 或 Immediate
allowVolumeExpansion: true             # 允許 PVC 擴容（需 CSI driver 支援）
mountOptions:                          # 掛載時傳給 OS 的選項
  - noatime
  - nodiratime
allowedTopologies:                     # 限制 PV 只能在特定拓撲建立
  - matchLabelExpressions:
      - key: topology.kubernetes.io/zone
        values:
          - us-east-1a
          - us-east-1b

4.2　allowVolumeExpansion — PVC 線上擴容

設定 allowVolumeExpansion: true 後，可以直接 patch PVC 的 spec.resources.requests.storage 來觸發線上擴容，無需重建 PVC 或停機。

bash · PVC 線上擴容（50Gi → 100Gi） 
# 方法一：kubectl patch
kubectl patch pvc postgres-data -n production \
  -p '{"spec":{"resources":{"requests":{"storage":"100Gi"}}}}' \
  --type=merge

# 方法二：kubectl edit（互動式）
kubectl edit pvc postgres-data -n production

# 監控擴容進度
kubectl get pvc postgres-data -n production -w
# 先看到 FileSystemResizePending，待 Pod 掛載後自動完成 FileSystem resize

# 確認擴容完成
kubectl get pvc postgres-data -n production \
  -o jsonpath='{.status.capacity.storage}'
# 輸出：100Gi
⚠

只能擴大，不能縮小：PVC 的儲存請求只支援增加，不支援減少（無論底層 CSI driver 是否支援）。縮小需要建立新 PVC 並搬移資料。
Filesystem resize：Block device 擴大後，Filesystem（ext4、xfs）的 resize 會在 Pod 重新掛載或 Pod 重啟時自動觸發（NodeExpandVolume），不需要手動操作。

4.3　Default StorageClass 管理

叢集中只建議設一個 default StorageClass。 若有多個 default，PVC 沒指定 storageClassName 時行為不確定。

bash · Default StorageClass 管理 
# 列出所有 StorageClass，確認哪個是 default
kubectl get sc
# NAME      PROVISIONER       RECLAIMPOLICY   BINDINGMODE      DEFAULT
# gp2       ebs.csi.aws.com   Delete          WaitForFirst
# gp3       ebs.csi.aws.com   Delete          WaitForFirst     true  ← default

# 移除舊的 default 標記
kubectl patch sc gp2 \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"false"}}}'

# 設定新的 default
kubectl patch sc gp3 \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'

Chapter 05

VolumeAttributesClass v1.34 GA

傳統上，K8s volume 有兩個特性：StorageClass（不可變的 provisioning 規格）和 capacity（可透過 resize 修改）。 但 IOPS、throughput 這類效能屬性既不在 StorageClass（不可變），也不是容量。 這造成一個痛點：要調整 IOPS，必須重建 PVC——意味著停機。

VolumeAttributesClass（VAC） 就是為此而生。它在 v1.29 Alpha、v1.31 Beta， 並在 v1.34 正式 GA，讓管理員定義可動態修改的 volume 屬性「profile」， 使用者只需更新 PVC 的 volumeAttributesClassName，底層 CSI driver 就會即時調整。

5.1　與 StorageClass 的核心差異

StorageClassVolumeAttributesClass
用途定義 Provisioning 規格（type、encryption…）定義可動態修改的 runtime 屬性（IOPS、throughput）
可變性一旦 PV 建立後不可修改PVC 建立後可以切換不同 VAC
觸發動作CreateVolume（建立時一次）ModifyVolume（動態修改，隨時可觸發）
需要停機?更換 StorageClass 需重建 PVC（停機）切換 VAC 不需重建 PVC（無停機）
CSI 支援所有 CSI driver需要 driver 實作 ModifyVolume RPC

5.3　VAC 資源定義與 PVC 使用範例

vac-gcp.yaml · VolumeAttributesClass（GCP Hyperdisk） 
apiVersion: storage.k8s.io/v1
kind: VolumeAttributesClass
metadata:
  name: silver
driverName: pd.csi.storage.gke.io
parameters:
  provisioned-iops: "3000"
  provisioned-throughput: "150"   # MiB/s

---
apiVersion: storage.k8s.io/v1
kind: VolumeAttributesClass
metadata:
  name: gold
driverName: pd.csi.storage.gke.io
parameters:
  provisioned-iops: "10000"
  provisioned-throughput: "500"   # MiB/s

---
# PVC 初始使用 silver，可隨時切換到 gold
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  storageClassName: gcp-hyperdisk-balanced
  volumeAttributesClassName: silver      # 初始 QoS profile
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 100Gi
bash · 動態切換 QoS（silver → gold，無需停機） 
# 流量尖峰時，把 PVC 從 silver 升級到 gold
kubectl patch pvc app-data -n production \
  -p '{"spec":{"volumeAttributesClassName":"gold"}}' \
  --type=merge

# 監控修改狀態
kubectl get pvc app-data -n production \
  -o jsonpath='{.status.modifyVolumeStatus}'
# InProgress → Complete

# 查看完整狀態
kubectl describe pvc app-data -n production | grep -A5 "Volume Attributes"

5.4　適用場景

  • HPC / 批次工作負載：工作執行期間臨時提升 IOPS，完成後降回，節省成本。
  • 資料庫 Tier 動態調整：離峰時段用 silver，促銷期間切換到 gold，不重建 PVC。
  • Multi-tenant 環境：不同租戶共用同一 StorageClass，但各自使用不同 VAC 控制 QoS。
⚠

限制：VAC 只能與 CSI 儲存搭配，且 CSI driver 必須實作 ModifyVolume RPC。2026/05 支援狀況：GCE PD CSI（Hyperdisk）✓、AWS EBS CSI（gp3/io2）✓、大多數 on-prem driver 尚未支援。使用前請確認 driver 版本。

Chapter 06

CSI 架構與 Sidecar 容器

CSI（Container Storage Interface）是一個標準化的 gRPC 介面規範， 讓任何儲存廠商都可以實作自己的 CSI driver，而不需要修改 Kubernetes 核心。 理解 CSI 架構，是排查儲存問題、部署 CSI driver、甚至自行開發 driver 的必備基礎。

6.1　CSI 三大 Service 與 RPC 分工

Service部署位置主要 RPC職責
Identity Controller + Node 都要有 GetPluginInfo GetPluginCapabilities Probe 回報 driver 名稱、版本、支援的功能
Controller Deployment（通常 1–3 副本） CreateVolume DeleteVolume ControllerPublishVolume CreateSnapshot ControllerExpandVolume ModifyVolume 管理 volume 生命週期；需要存取雲端 API；不需在每個節點執行
Node DaemonSet（每個節點一個） NodeStageVolume NodePublishVolume NodeUnpublishVolume NodeExpandVolume 在節點上掛載/卸載 volume；需要節點層級的系統呼叫（mount、格式化）

6.2　部署架構圖

6.3　五大官方 Sidecar 容器

external-provisioner
動態建立 / 刪除 Volume
監聽 PVC 事件，觸發 CSI CreateVolume / DeleteVolume。搭配 StorageClass 及 VolumeAttributesClass 使用。
external-attacher
將 Volume 附加 / 卸離節點
監聽 VolumeAttachment 物件，觸發 ControllerPublishVolume / ControllerUnpublishVolume，完成 block device 附加。
external-snapshotter
管理 Volume Snapshot
監聽 VolumeSnapshotContent 事件，觸發 CreateSnapshot / DeleteSnapshot。v8.4 起支援 VolumeGroupSnapshot。
external-resizer
擴容 Volume / 修改屬性
監聽 PVC resize 與 VAC 切換事件，觸發 ControllerExpandVolume 和 ModifyVolume（VAC 支援）。
node-driver-registrar
向 kubelet 註冊 CSI driver
部署在每個節點的 DaemonSet 中，透過 kubelet plugin registration 機制讓 kubelet 知道如何呼叫該節點的 CSI driver。

6.4　完整 CSI Driver Deployment 範例

csi-controller.yaml · Controller StatefulSet（精簡版） 
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: my-csi-controller
  namespace: kube-system
spec:
  replicas: 2                          # HA：2 副本，leader election 選出 1 個 active
  selector:
    matchLabels:
      app: my-csi-controller
  template:
    spec:
      serviceAccountName: my-csi-controller-sa
      containers:
        # ── 主要 CSI driver 容器（儲存廠商提供）
        - name: my-csi-driver
          image: vendor/my-csi-driver:v1.5.0
          args:
            - --endpoint=unix:///var/lib/csi/sockets/pluginproxy/csi.sock
          volumeMounts:
            - name: socket-dir
              mountPath: /var/lib/csi/sockets/pluginproxy/

        # ── external-provisioner sidecar
        - name: csi-provisioner
          image: registry.k8s.io/sig-storage/csi-provisioner:v5.1.0
          args:
            - --csi-address=$(ADDRESS)
            - --leader-election              # HA 部署必須啟用
            - --leader-election-namespace=kube-system
            - --feature-gates=Topology=true
            - --enable-capacity             # 啟用 CSIStorageCapacity
          env:
            - name: ADDRESS
              value: /var/lib/csi/sockets/pluginproxy/csi.sock
          volumeMounts:
            - name: socket-dir
              mountPath: /var/lib/csi/sockets/pluginproxy/

        # ── external-attacher sidecar
        - name: csi-attacher
          image: registry.k8s.io/sig-storage/csi-attacher:v4.7.0
          args:
            - --csi-address=$(ADDRESS)
            - --leader-election
          env:
            - name: ADDRESS
              value: /var/lib/csi/sockets/pluginproxy/csi.sock
          volumeMounts:
            - name: socket-dir
              mountPath: /var/lib/csi/sockets/pluginproxy/

        # ── external-resizer sidecar（含 ModifyVolume 支援）
        - name: csi-resizer
          image: registry.k8s.io/sig-storage/csi-resizer:v1.12.0
          args:
            - --csi-address=$(ADDRESS)
            - --leader-election
          env:
            - name: ADDRESS
              value: /var/lib/csi/sockets/pluginproxy/csi.sock
          volumeMounts:
            - name: socket-dir
              mountPath: /var/lib/csi/sockets/pluginproxy/

      volumes:
        - name: socket-dir
          emptyDir: {}
csi-node.yaml · Node DaemonSet（精簡版） 
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: my-csi-node
  namespace: kube-system
spec:
  selector:
    matchLabels:
      app: my-csi-node
  template:
    spec:
      hostNetwork: true
      containers:
        # ── 主要 CSI Node driver
        - name: my-csi-driver
          image: vendor/my-csi-driver:v1.5.0
          securityContext:
            privileged: true             # 需要掛載 volume（mount syscall）
          volumeMounts:
            - name: plugin-dir
              mountPath: /csi
            - name: kubelet-dir
              mountPath: /var/lib/kubelet
              mountPropagation: Bidirectional  # 讓掛載傳遞到主機
            - name: device-dir
              mountPath: /dev

        # ── node-driver-registrar sidecar（必須在 Node daemonset）
        - name: node-driver-registrar
          image: registry.k8s.io/sig-storage/csi-node-driver-registrar:v2.12.0
          args:
            - --csi-address=/csi/csi.sock
            - --kubelet-registration-path=/var/lib/kubelet/plugins/my-csi/csi.sock
          volumeMounts:
            - name: plugin-dir
              mountPath: /csi
            - name: registration-dir
              mountPath: /registration

      volumes:
        - name: kubelet-dir
          hostPath:
            path: /var/lib/kubelet
            type: Directory
        - name: plugin-dir
          hostPath:
            path: /var/lib/kubelet/plugins/my-csi/
            type: DirectoryOrCreate
        - name: registration-dir
          hostPath:
            path: /var/lib/kubelet/plugins_registry/
            type: Directory
        - name: device-dir
          hostPath:
            path: /dev
            type: Directory

6.5　Leader Election 與 HA 部署

Controller 端的 sidecar（external-provisioner、external-attacher 等）都支援 Leader Election， 讓多個副本中只有一個 active，其餘等待。Leader 死亡後約 15 秒重新選舉。

!

Node DaemonSet 不需要 Leader Election：每個節點只有一個 Node plugin 副本，它只負責自己節點的 volume 掛載，天生無競爭。Leader Election 只需要在 Controller StatefulSet 的 sidecar 上啟用。

6.6　CSIStorageCapacity — Scheduler 感知儲存容量

啟用 --enable-capacity 後，external-provisioner 會定期建立 CSIStorageCapacity 物件， 告知 Scheduler 每個節點/拓撲的可用儲存容量。 搭配 WaitForFirstConsumer，Scheduler 就不會把 Pod 調度到儲存空間不足的節點。

bash · 查看 CSIStorageCapacity 
# 查看叢集中各拓撲的可用儲存
kubectl get csistoragecapacities -A

# 範例輸出
# NAMESPACE     NAME                        STORAGECLASS   CAPACITY
# kube-system   csc-us-east-1a-fast-ssd    fast-ssd       4.8Ti
# kube-system   csc-us-east-1b-fast-ssd    fast-ssd       3.2Ti
# kube-system   csc-us-east-1c-fast-ssd    fast-ssd       6.1Ti

6.7　CSI Driver 開發三原則

  • Follow the CSI spec：實作所有 required RPC，遵循錯誤碼規範（gRPC status codes），避免自行定義行為。
  • Idempotent 操作：CreateVolume 被呼叫兩次（相同參數）應回傳相同結果，而非建立兩個 volume。這對 retry 和 failover 場景至關重要。
  • Graceful failure handling：操作失敗時清理已建立的資源，回傳適當的 gRPC error code，讓 sidecar 的 retry 機制能正確判斷是否重試。
