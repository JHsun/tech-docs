Topic 與 Partition 基礎設定組合

🗂
情境 1-A：單一 Partition Topic（序列保證）
partition=1replication-factor=1

所有訊息進入同一個 Partition，全域有序。寫入吞吐量受限於單一 Broker，Consumer 也只能有一個實例真正消費。適合對順序極度敏感但量不大的場景（如帳務流水）。

flowchart LR
  P([Producer]) -->|append| T0[Topic-A Partition 0]
  T0 -->|consume in order| C([Consumer])
  • 全域 ordering 保證，offset 嚴格遞增
  • Consumer Group 中同時只有 1 個 Consumer 能工作，多餘的閒置
  • 無水平擴展能力
⚠ replication-factor=1 表示 Broker 故障時資料遺失，生產環境務必設為 ≥ 3。
⚡
情境 1-B：多 Partition Topic（高吞吐）
partition=3replication-factor=3

Partition 數決定最大並行消費數與寫入吞吐量上限。3 個 Partition 跨 3 個 Broker 分散 Leader，每個 Broker 同時持有其他 Partition 的 Follower 副本，提升可用性。

flowchart TD
  Producer([Producer])
  subgraph Broker1[Broker 1]
    P0L[P0 Leader]
    P1F[P1 Follower]
  end
  subgraph Broker2[Broker 2]
    P1L[P1 Leader]
    P2F[P2 Follower]
  end
  subgraph Broker3[Broker 3]
    P2L[P2 Leader]
    P0F[P0 Follower]
  end
  Producer -->|P0| P0L
  Producer -->|P1| P1L
  Producer -->|P2| P2L
  P0L -.->|replicate| P0F
  P1L -.->|replicate| P1F
  P2L -.->|replicate| P2F
  • 只有 Leader Partition 接受讀寫；Follower 非同步複製（ISR 機制）
  • 同一 Partition 內有序；跨 Partition 無全域序
  • Partition 數設定後只能增加，不能減少
💡 建議 Partition 數設為預期 Consumer 數的整數倍，避免負載不均。
🗜
情境 1-C：Log Compaction Topic（鍵值最新狀態）
cleanup.policy=compactchangelog / state store

Kafka 只保留每個 key 的最新訊息，舊版本被 compaction 刪除。適合儲存實體最新狀態（如用戶設定、庫存數量），也是 Kafka Streams KTable 底層機制。

sequenceDiagram
  participant P as Producer
  participant K as Kafka compacted topic
  participant C as Consumer
  P->>K: key=u1 val=A offset=0
  P->>K: key=u2 val=X offset=1
  P->>K: key=u1 val=B offset=2
  Note over K: Compaction 執行，刪除 offset=0
  C->>K: fetch
  K-->>C: u1=B, u2=X
  • value=null 的墓碑訊息可徹底刪除一個 key
  • 不適合只需要事件流水的場景
  • Kafka Streams changelog topic 預設使用此策略

Producer 策略組合

🔄
情境 2-A：無 key — Sticky Partitioner
key=null均勻分散

訊息不帶 key，Producer 預設使用 Sticky Partitioner（Kafka 2.4+）：在一個 batch 完成前黏在同一個 Partition，batch 結束後換一個，可減少小 batch 數量、提升吞吐量。

flowchart LR
  P([Producer key=null])
  P -->|batch 1| P0[Partition 0]
  P -->|batch 2| P1[Partition 1]
  P -->|batch 3| P2[Partition 2]
  P -->|batch 4| P0
  • 同一批次訊息有序，跨批次無序
  • 適合日誌類、無需排序的事件
🔑
情境 2-B：指定 key — murmur2 hash 路由
key=user_id同 key 有序

Producer 對 key 做 murmur2(key) % numPartitions，同一 key 永遠落在同一 Partition，確保該 key 的訊息全域有序。常用於用戶行為流、訂單狀態更新。

flowchart LR
  P([Producer])
  P -->|"key=u1 hash%3=0"| P0[Partition 0]
  P -->|"key=u2 hash%3=1"| P1[Partition 1]
  P -->|"key=u3 hash%3=0"| P0
⚠ Partition 數變更後 hash 結果改變，同一 key 可能落到不同 Partition，破壞順序性。
  • Hot partition 問題：某些 key 活躍度遠高於其他，需自訂 Partitioner 分流
  • 可搭配 Kafka Streams 的 KTable 做 key-level 狀態聚合
自訂 Partitioner 範例（Java）
public class UserIdPartitioner implements Partitioner {
  @Override
  public int partition(String topic, Object key, byte[] keyBytes,
                       Object value, byte[] valueBytes, Cluster cluster) {
    int num = cluster.partitionsForTopic(topic).size();
    // 取 uid 後兩碼做 bucket，避免熱點
    String uid = key.toString();
    return Integer.parseInt(uid.substring(uid.length() - 2)) % num;
  }
}
🔒
情境 2-C：Idempotent Producer / 交易性寫入
enable.idempotence=trueexactly-once

Idempotent Producer 透過 producer_id + sequence_number 讓 Broker 去重，避免網路重試造成重複寫入。Transactional Producer 進一步跨 Partition、跨 Topic 保證 exactly-once 語意。

sequenceDiagram
  participant P as Idempotent Producer
  participant B as Broker
  P->>B: send msg seq=1
  B-->>P: ack OK
  P->>B: send msg seq=1 retry
  B-->>P: DuplicateSequenceException
  Note over B: Broker 只存一份，冪等去重成功
  • acks=all + enable.idempotence=true 才能確保 exactly-once
  • 交易性寫入需設定 transactional.id，Consumer 端設 isolation.level=read_committed
  • 適合金融交易、庫存扣減等不能重複的操作
✓ Kafka 3.0+ 預設開啟 idempotence，不再需要手動設定。

Consumer 消費情境組合

📉
情境 3-A：Consumer 數 < Partition 數
2 consumers4 partitions

Group Coordinator 自動將多個 Partition 分配給同一個 Consumer，該 Consumer 需依序消費多條 log，吞吐量下降。

flowchart LR
  subgraph Topic[Topic-X 4 Partitions]
    P0[P0] & P1[P1] & P2[P2] & P3[P3]
  end
  subgraph CG[Consumer Group A]
    C1([Consumer-1 P0 P1])
    C2([Consumer-2 P2 P3])
  end
  P0 --> C1
  P1 --> C1
  P2 --> C2
  P3 --> C2
  • RangeAssignor：按 Partition 編號切段，Consumer 少時前幾個多分一個
  • RoundRobinAssignor：輪流分配，較均勻
  • StickyAssignor（推薦）：rebalance 時盡量保留既有分配，降低遷移成本
⚖
情境 3-B：Consumer 數 = Partition 數（最佳並行）
1:1 對應partition=3, consumers=3

每個 Consumer 恰好負責一個 Partition，是並行消費的最佳狀態。每個 Partition 的序內有序保證完整，Consumer 間不需要協調。

flowchart LR
  P0[Partition 0] --> C0([Consumer-0])
  P1[Partition 1] --> C1([Consumer-1])
  P2[Partition 2] --> C2([Consumer-2])
  • 最大化並行度，同時保有 per-key 有序保證
  • 擴充吞吐量：同步增加 Partition 數與 Consumer 數
🪑
情境 3-C：Consumer 數 > Partition 數（有閒置）
閒置 Consumerpartition=2, consumers=4

Kafka 強制每個 Partition 同一時刻只能被同一個 Consumer Group 中的一個 Consumer 消費。多出來的 Consumer 完全閒置，不會提升吞吐量，但可作為快速接管的熱備份。

flowchart LR
  P0[Partition 0] --> C0([Consumer-0 active])
  P1[Partition 1] --> C1([Consumer-1 active])
  C2([Consumer-2 idle])
  C3([Consumer-3 idle])
⚠ 閒置 Consumer 仍消耗資源（連線、心跳）。Kubernetes 部署時浪費算力，建議先增加 Partition 數。
⏪
情境 3-D：Seek to Offset / 時間戳定位重播
consumer.seek()重播 / 修復

Consumer 可在任意時間呼叫 seek() 跳至指定 offset，或用 offsetsForTimes() 以時間戳定位。常用於資料修復、重算或除錯。

sequenceDiagram
  participant App as Application
  participant C as Consumer
  participant B as Broker
  App->>C: assign TopicPartition
  App->>C: seek partition=0 offset=100
  C->>B: fetch partition=0 from offset=100
  B-->>C: records 100 to 120
  App->>C: commitSync
程式碼範例（Java）
// 用時間戳找 offset
Map<TopicPartition, Long> tsMap = new HashMap<>();
TopicPartition tp = new TopicPartition("my-topic", 0);
tsMap.put(tp, Instant.parse("2025-01-01T00:00:00Z").toEpochMilli());

Map<TopicPartition, OffsetAndTimestamp> result =
    consumer.offsetsForTimes(tsMap);

long targetOffset = result.get(tp).offset();
consumer.seek(tp, targetOffset);

多群組與廣播情境

👥
情境 4-A：同群組消費同一 Topic 多 Partition（水平擴展）
group-id=same負載分散

同一個 Consumer Group 的成員分攤 Topic 的所有 Partition，每筆訊息只由 Group 中的一個 Consumer 處理。等同於傳統的 Competing Consumers pattern。

flowchart TD
  subgraph Topic[Topic: orders 3 Partitions]
    P0[P0] & P1[P1] & P2[P2]
  end
  subgraph CG[Consumer Group: order-processor]
    C0([Consumer-0]) & C1([Consumer-1]) & C2([Consumer-2])
  end
  P0 --> C0
  P1 --> C1
  P2 --> C2
  • 每筆訊息只被處理一次（在 Group 層級）
  • 新增 Consumer 觸發 rebalance，自動重新分配 Partition
  • 同 Partition 的訊息仍保有順序
📡
情境 4-B：不同群組消費同一 Topic（廣播 / Pub-Sub）
group-id=different每組獨立 offset

不同 Consumer Group 各自擁有獨立的 offset 指針，可以同時消費同一個 Topic 的相同訊息。每個 Group 相當於一個獨立的訂閱者，互不干擾。這是 Kafka 與傳統 MQ 最大的架構差異。

flowchart LR
  subgraph T[Topic: user-events]
    P0[P0] & P1[P1]
  end
  subgraph G1[Group: analytics offset at 850]
    A0([Consumer-A0]) & A1([Consumer-A1])
  end
  subgraph G2[Group: notifications offset at 999]
    N0([Consumer-N0]) & N1([Consumer-N1])
  end
  subgraph G3[Group: audit-log offset at 200]
    L0([Consumer-L0]) & L1([Consumer-L1])
  end
  P0 --> A0
  P1 --> A1
  P0 --> N0
  P1 --> N1
  P0 --> L0
  P1 --> L1
  • analytics group 消費速度慢，不影響其他 Group
  • audit-log group 正在重播舊資料，不阻塞生產者
  • Kafka 保留訊息至 retention 期限，各 Group 可獨立決定消費進度
✓ 這是 Kafka 最大的架構優勢：一份資料，多個下游服務獨立訂閱，無需複製資料。
🔀
情境 4-C：多群組各自含多 Consumer（混合架構）
N groupsM consumers per group

實務上最常見的大規模架構：多個下游系統各自建立 Consumer Group，每個 Group 內水平擴展 Consumer 來提升吞吐量，達成廣播 + 並行處理的結合。

flowchart TD
  Topic[Topic: payment-events 6 Partitions]
  subgraph G1[Group: fraud-detector 6 consumers]
    F0([C0]) & F1([C1]) & F2([C2]) & F3([C3]) & F4([C4]) & F5([C5])
  end
  subgraph G2[Group: ledger-service 3 consumers]
    L0([C0]) & L1([C1]) & L2([C2])
  end
  subgraph G3[Group: notification 2 consumers]
    N0([C0]) & N1([C1])
  end
  Topic --> G1
  Topic --> G2
  Topic --> G3
  • fraud-detector 為 1:1 最大並行；ledger 每 Consumer 負責 2 個 Partition
  • 各 Group 消費速度、offset 完全獨立
  • Consumer 數可隨流量動態調整，不影響其他 Group

Rebalance 與故障情境

🔃
情境 5-A：Consumer 加入或離開觸發 Rebalance
Stop-the-worldStickyAssignor 可降低影響

當 Consumer 加入、離開、崩潰或超過 session.timeout.ms 沒有心跳，Group Coordinator 觸發 rebalance。期間所有 Consumer 暫停消費，等待新的分配結果。Kafka 3.1+ 引入 Incremental Cooperative Rebalance 改善此問題。

sequenceDiagram
  participant GC as Group Coordinator
  participant C0 as Consumer-0
  participant C1 as Consumer-1
  participant C2 as Consumer-2 new

  C2->>GC: JoinGroup Request
  GC-->>C0: Rebalance notify
  GC-->>C1: Rebalance notify
  Note over C0,C1: 暫停消費，revoke Partitions
  C0->>GC: JoinGroup follower
  C1->>GC: JoinGroup follower
  GC->>C0: SyncGroup leader assigns
  GC-->>C0: assign P0
  GC-->>C1: assign P1
  GC-->>C2: assign P2
  Note over C0,C2: 恢復消費
  • max.poll.interval.ms：業務處理超時觸發離組，預設 5 分鐘
  • session.timeout.ms：心跳超時，預設 45 秒
  • StickyAssignor 盡量保留 Consumer 原有的 Partition，減少遷移
ℹ Kafka 3.1+ Incremental Cooperative Rebalance：Consumer 只 revoke 被奪走的 Partition，繼續消費其他 Partition，大幅降低停頓。
🏆
情境 5-B：Broker 故障 — Partition Leader 重新選舉
ISRunclean.leader.election

Broker 故障後，Controller（KRaft 架構）從 ISR（In-Sync Replicas）中選出新的 Leader。若 ISR 為空且 unclean.leader.election.enable=true，則可選 out-of-sync replica，但可能導致資料遺失。

sequenceDiagram
  participant Ctrl as Controller KRaft
  participant B1 as Broker-1 Leader
  participant B2 as Broker-2 ISR Follower
  participant B3 as Broker-3 ISR Follower

  B1->>B1: crash
  Ctrl->>Ctrl: detect B1 offline
  Ctrl->>B2: elect as new P0 Leader
  B2-->>Ctrl: confirm Leader
  B3->>B2: sync from new Leader
  Ctrl->>Ctrl: update cluster metadata
  • ISR 越大，可用性越高；min.insync.replicas=2 可避免只剩一個副本時的寫入風險
  • 生產建議：replication-factor=3, min.insync.replicas=2, acks=all

Topic 資料查詢方式分類

📥
方式 A：直接 Consumer API 查詢
Consumer APIAdminClient低延遲

最直接的方式，應用程式透過 Kafka Client 訂閱 Topic 或指定 offset 查詢。適合事件驅動處理、即時消費，以及 offset/lag 監控。

flowchart LR
  App([Application])
  App -->|subscribe or assign| KC[Kafka Consumer]
  KC -->|poll| Broker[Broker Leader]
  Broker -->|records| KC --> App
  Monitor([Monitor App])
  Monitor -->|listOffsets / groupOffsets| Admin[AdminClient]
  Admin --> Broker
四種 seek 策略
策略API用途
指定 offsetseek(tp, offset)精確跳到某筆訊息
時間戳定位offsetsForTimes()查某個時間點之後的資料
從頭重播seekToBeginning()重跑全量資料
只讀最新seekToEnd()跳過歷史，只要新訊息
🗄
方式 B：Sink 到外部儲存後查詢
Kafka ConnectElasticsearch / RDBMS

Kafka 本身不支援複雜查詢。透過 Kafka Connect Sink Connector 將資料同步到外部系統，再用該系統的查詢能力（SQL、全文搜尋）操作。

flowchart LR
  Topic[Kafka Topic]
  Topic -->|Sink Connector| ES[Elasticsearch]
  Topic -->|Sink Connector| PG[PostgreSQL]
  Topic -->|Sink Connector| Redis[Redis]
  App([Application])
  App -->|full-text search| ES
  App -->|SQL| PG
  App -->|GET key| Redis
目標系統適合場景延遲
Elasticsearch全文搜尋、多欄位 filter秒級
PostgreSQL / MySQL複雜 SQL join、報表秒級
Rediskey-level 最新值查詢毫秒
ClickHouse / BigQuery大規模分析、聚合分鐘
MongoDB文件查詢、巢狀結構秒級
🌊
方式 C：串流處理引擎查詢
Kafka StreamsksqlDBFlink / Spark

在資料流動時即時做聚合、join、視窗統計，結果可寫回 Topic 或暴露為查詢介面。

flowchart TD
  TIn[input-topic] & TRef[ref-topic]
  subgraph Streams[Kafka Streams App]
    KS[KStream per-record] --> KT[KTable latest state]
    KT --> AGG[Aggregate Window]
  end
  subgraph KS2[ksqlDB]
    SQL[SELECT FROM topic WHERE key=x]
  end
  TIn --> KS
  TRef --> KT
  AGG -->|sink| TOut[output-topic]
  TIn --> SQL
  SQL -->|push or pull query| App([Application])
ksqlDB 查詢類型
查詢類型語法行為
Push QuerySELECT … EMIT CHANGES持續推送新事件，長連線
Pull QuerySELECT … FROM table WHERE key='x'查一次返回，類似 REST
Materialized ViewCREATE TABLE AS SELECT …預計算的聚合，供 pull query 查詢
Kafka Streams KTable Interactive Query 範例（Java）
KTable<String, OrderState> orderTable = builder
    .table("order-events", Consumed.with(Serdes.String(), orderSerde));

// 直接從本地 state store 查詢，不需要額外 round-trip
ReadOnlyKeyValueStore<String, OrderState> store =
    streams.store(StoreQueryParameters.fromNameAndType(
        "order-state-store", QueryableStoreTypes.keyValueStore()));

OrderState latest = store.get("order-12345");
🔁
方式 D：Change Data Capture（CDC）雙向整合
DebeziumDB binlog to Kafka

CDC 將資料庫的每一筆 insert/update/delete 變更捕捉為 Kafka 事件。應用程式查詢資料庫，資料庫的寫入同時透過 CDC 廣播到下游 Kafka 消費者，形成讀寫分離的事件驅動架構。

flowchart LR
  App([Application]) -->|WRITE| DB[(PostgreSQL binlog)]
  DB -->|Debezium CDC| KT[Kafka Topic db.orders]
  KT -->|consume| Search[Elasticsearch]
  KT -->|consume| Cache[Redis Cache]
  KT -->|consume| DW[Data Warehouse]
  App -->|READ| Search
  • 資料源唯一（DB），查詢從下游專屬系統進行，讀寫分離
  • Debezium 支援 PostgreSQL、MySQL、MongoDB、SQL Server
  • Kafka 作為事件 backbone，確保所有下游系統最終一致
