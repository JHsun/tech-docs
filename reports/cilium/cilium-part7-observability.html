可觀測性

沒有 Hubble 等於閉著眼睛開飛機。本章把 Hubble CLI、UI、Exporter、Prometheus / Grafana metrics、L7 protocol visibility、IP 封包追蹤一次講透，讓你看得到 cluster 內每一個 flow 的 identity、verdict、L7 內容，並把這些資料串到既有 SRE 工具鏈。

對應官方文件：Observability 全章 Cilium 版本：1.19.x 主要對象：SRE / DevOps / 應用開發者

關鍵性質：

  • 無 sidecar、零應用改動：資料來自 eBPF datapath（pod 不知不覺）
  • K8s 識別：每個 flow 都帶 namespace、pod name、label、service name
  • L3/L4/L7：HTTP method/path、DNS query name、gRPC service/method 都看得到
  • Policy verdict：被誰擋的、為什麼擋（這個 traditional tcpdump 看不到）
  • Ring buffer 容量有限：預設每 node 約 4095 個最近 flow，過了就 evict（要持久化需 Exporter）

2. Hubble 啟用

大部分情境用 cilium CLI 一鍵搞定。生產建議直接走 Helm + values，方便版控：

方式 A：cilium CLI（最快）

bash
cilium hubble enable --ui

cilium status | grep -i hubble
# 預期:
# Hubble Relay:       OK
# Hubble UI:          OK

方式 B：Helm（生產建議）

yaml
# cilium-values.yaml (節錄)
hubble:
  enabled: true                         # 每 node agent 啟用 Hubble
  relay:
    enabled: true
    replicas: 2                         # 生產建議 ≥ 2
  ui:
    enabled: true
  metrics:
    enableOpenMetrics: true             # 推薦：OpenMetrics format with exemplars
    enabled:                            # 預設啟用的 metric 集
      - dns:query;ignoreAAAA
      - drop
      - tcp
      - flow
      - port-distribution
      - icmp
      - httpV2:exemplars=true;labelsContext=source_ip,source_namespace,source_workload,destination_ip,destination_namespace,destination_workload,traffic_direction
    serviceMonitor:
      enabled: true                     # Prometheus Operator 環境必開
  tls:
    auto:
      enabled: true                     # 自動產生 TLS 憑證
      method: helm                      # 用 helm hook 產證

安裝 Hubble CLI（本機）

bash
HUBBLE_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/hubble/master/stable.txt)
HUBBLE_ARCH=amd64
[ "$(uname -m)" = "aarch64" ] && HUBBLE_ARCH=arm64
curl -L --fail --remote-name-all \
  "https://github.com/cilium/hubble/releases/download/${HUBBLE_VERSION}/hubble-linux-${HUBBLE_ARCH}.tar.gz"{,.sha256sum}
sha256sum --check hubble-linux-${HUBBLE_ARCH}.tar.gz.sha256sum
sudo tar xzvfC hubble-linux-${HUBBLE_ARCH}.tar.gz /usr/local/bin
rm hubble-linux-${HUBBLE_ARCH}.tar.gz{,.sha256sum}

# 透過 port-forward 連上 Relay
cilium hubble port-forward&

# 驗證
hubble status
# Healthcheck (via localhost:4245): Ok
# Current/Max Flows: 4095/4095 (100.00%)
# Flows/s: 4.50
# Connected Nodes: 3/3

3.3 verdict 解讀

Hubble verdict 是排查 policy 的關鍵欄位。完整對照：

Verdict意義排查方向
FORWARDED 正常通過 無需處理
DROPPED 被 drop（看 reason） 看 reason 進一步處理
ERROR datapath 異常（罕見） 看 cilium-agent log
AUDIT policy audit mode（記錄但不執行） policy 試行階段
REDIRECTED 導去 L7 proxy（Envoy） L7 policy 介入中
TRACED Trace event 診斷模式

當 verdict 是 DROPPED，附帶的 reason 才是真正答案：

Drop Reason典型原因
Policy deniedL3/L4 policy 擋下，最常見
Stale or unroutable IP目的 pod 已被刪除
CT: Map insertion failedconntrack table 滿（大 cluster 需調整）
Invalid source IPspoofing 或 misconfig
Unsupported L3 protocolIPv6 沒啟用卻收到 IPv6 封包
Authentication requiredmTLS 失敗
Service backend not foundService 存在但 endpoints 為空

3.4 輸出格式（自動化）

bash
# JSON Lines (適合 grep / jq)
hubble observe --output json --last 100 | jq 'select(.verdict=="DROPPED")'

# JSON Protobuf (Hubble 原生格式，給工具吃)
hubble observe --output jsonpb --last 1000 > flows.jsonl

# 簡潔表格
hubble observe --output compact

# 含 latency 的詳細表格
hubble observe --output dict --print-raw-filters

實用 one-liners：

bash
# 列出最常被擋的 src → dst pair
hubble observe --verdict DROPPED --last 5000 --output json | \
  jq -r '"\(.source.namespace)/\(.source.pod_name) -> \(.destination.namespace)/\(.destination.pod_name)"' | \
  sort | uniq -c | sort -rn | head

# 計算 HTTP 4xx / 5xx 比例
hubble observe --http-status "[45].." --last 5000 --output json | \
  jq -r '.l7.http.code' | sort | uniq -c

# 列出 DNS 解析最多的域名
hubble observe --type l7 --protocol dns --last 5000 --output json | \
  jq -r '.l7.dns.query' | sort | uniq -c | sort -rn | head

4. Hubble UI（Service Map）

Hubble UI 提供互動式 service map：哪些 pod 跟哪些 pod 講話、走什麼 port / protocol、是否被 deny。對 onboarding 與 incident 時很直覺。

bash
# 開 UI
cilium hubble ui
# 自動打開瀏覽器，預設 http://localhost:12000

# 或手動 port-forward
kubectl -n kube-system port-forward svc/hubble-ui 12000:80

UI 重點用法

  • 左上 namespace 下拉：切換要看的 namespace
  • 節點之間箭頭：粗細代表 traffic 量；紅色代表 drop
  • 點箭頭 → 看具體 flow（含 HTTP method/path）
  • 右上「Show Filters」可即時加 verdict / port / pod 過濾
  • 有「Forwarded only」「Dropped only」快速切換
  • Save filter as URL：存常用 view 給 team 用
💡 onboarding / incident review 利器

新人 onboard 不確定 service 之間關係 → Hubble UI 看一眼就懂。Incident 後復盤想知道「攻擊路徑」→ Hubble UI 直接看 drop 與 forward 軌跡。

5. Hubble Exporter（持久化 flow log）

Hubble 預設 flow 存在每 node 的 ring buffer（預設 4095 個），這對即時觀察足夠，但無法做歷史回溯或長期審計。要把 flow 持久化到外部，啟用 Hubble Exporter：把 flow 寫到 file / stdout，再讓 fluentd、Loki、SIEM 接走。

啟用

yaml
# Helm values
hubble:
  export:
    static:
      enabled: true
      filePath: /var/run/cilium/hubble/events.log
      fileMaxSizeMb: 100        # 單檔大小
      fileMaxBackups: 5         # rotation 保留份數
      # 過濾哪些事件要 export（可選）
      allowList:
        - '{"verdict":["DROPPED","ERROR"]}'
        - '{"event_type":[{"type":1}]}'    # type 1 = L4 flow
      fieldMask:
        - source
        - destination
        - verdict
        - traffic_direction

典型 pipeline：Hubble Exporter → Fluent Bit → Loki / Elasticsearch

動態 Exporter Config（1.17+）

1.17+ 提供 CiliumHubbleFlowExporter CRD，允許運行時動態切換 export 設定（例如 incident 時改抓全部 verdict、平時只抓 DROPPED 節省空間）：

yaml
apiVersion: cilium.io/v1alpha1
kind: CiliumHubbleFlowExporter
metadata:
  name: incident-mode
spec:
  filePath: /var/run/cilium/hubble/incident.log
  allowList:
    - '{}'                     # all
  fileMaxSizeMb: 500

6.3 ServiceMonitor 接到 Prometheus Operator

大多數叢集裝了 kube-prometheus-stack。打開 serviceMonitor.enabled=true 後，Cilium 會自動建好 ServiceMonitor 物件。但 Prometheus 操作員有 selector，你的 label 要對得上：

bash
# 查 Prometheus selector 是什麼
kubectl get prometheus -A -o jsonpath='{.items[*].spec.serviceMonitorSelector}'
# 例: {"matchLabels":{"release":"prometheus"}}

# 對應 values.yaml 設 label
# prometheus:
#   serviceMonitor:
#     labels:
#       release: prometheus

# 驗證 target 真的被 scrape
kubectl -n monitoring port-forward svc/prometheus-operated 9090:9090
# 開 http://localhost:9090/targets，搜尋 cilium，全部 UP

6.4 高基數陷阱

⚠ 大叢集 metric 爆炸

幾個指標會產生每對 (src_pod, dst_pod, port) 一條 time series，cluster 5000 pod 可能爆 100 萬 series。Prometheus OOM、查詢崩。

務必排除的高基數 metric（大 cluster）：

  • cilium_node_connectivity_status — 每對 node 一條，O(n²)
  • cilium_node_connectivity_latency_seconds — 同上
  • port-distribution — 每個非標準 port 都產生 series
  • httpV2 含 source_ip / destination_ip 在 labelsContext 內 — pod IP 變動會炸

排除方法：

yaml
prometheus:
  metrics:
    - "-cilium_node_connectivity_status"
    - "-cilium_node_connectivity_latency_seconds"

# httpV2 labelsContext 用 namespace/workload，不要用 IP
hubble:
  metrics:
    enabled:
      - httpV2:exemplars=true;labelsContext=source_namespace,source_workload,destination_namespace,destination_workload,traffic_direction

7. 重要 metric 速查 + PromQL 範例

cilium-agent 健康

Metric意義
cilium_agent_bootstrap_secondsagent 啟動耗時，異常拉長代表 cluster 大或卡 K8s API
cilium_endpoint_state{state=...}endpoint 各狀態數量（ready / waiting / disconnected）
cilium_endpoint_regeneration_time_stats_secondsendpoint 重生時間，policy 改動時看這個
cilium_identitycluster 內 identity 數量
cilium_policy_count已套用 policy 數量
cilium_drop_count_total{reason=...}各 drop 原因計數
cilium_bpf_map_pressureBPF map 用量比例，>0.8 要警告

Hubble flow

Metric意義
hubble_flows_processed_total{verdict=...}處理過的 flow，verdict 拆分
hubble_drop_total{reason=...}被 drop 的 flow（reason 標籤）
hubble_dns_queries_totalDNS query 總數

常用 PromQL 範例

promql
# 1. 每秒 dropped flow 數（cluster 整體）
sum(rate(hubble_drop_total[5m]))

# 2. 哪個 namespace 的 drop 最多
topk(5,
  sum by (source_namespace) (rate(hubble_drop_total[5m]))
)

# 3. 每秒 HTTP 5xx 比例
sum(rate(hubble_http_requests_total{status=~"5.."}[5m]))
  /
sum(rate(hubble_http_requests_total[5m]))

# 4. DNS NXDOMAIN spike alert
sum by (source_namespace) (
  rate(hubble_dns_response_types_total{rcode="3"}[5m])
) > 10

# 5. BPF map pressure 警告
max by (name, node) (cilium_bpf_map_pressure) > 0.85

# 6. Endpoint 狀態異常
sum by (node) (cilium_endpoint_state{state!="ready"}) > 0

# 7. P99 HTTP latency
histogram_quantile(0.99,
  sum by (le, source_namespace) (
    rate(hubble_http_request_duration_seconds_bucket[5m])
  )
)

8. L7 Protocol 可視性

看到 HTTP method、DNS query 這些 L7 細節，前提是 Cilium 攔截 L7 流量到 Envoy。有兩種啟用方式：

方式 A：寫 L7 policy（自然開啟）

第六部 A 寫過 rules.http 的 policy，這會讓對應流量自動 redirect 到 Envoy，Hubble 就看得到 HTTP method/path。沒寫 L7 policy 的 port → 只看得到 L3/L4。

方式 B：用 visibility annotation（不執行政策，只觀察）

有時候不想加 enforcement 但想看 L7。用 pod annotation：

yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
  annotations:
    # 格式: ///
    io.cilium.proxy-visibility: "<Ingress/80/TCP/HTTP>,<Egress/53/UDP/DNS>"
spec: ...

常用組合：

  • <Ingress/80/TCP/HTTP> — 進入 80/TCP 解析 HTTP
  • <Egress/53/UDP/DNS> — 出向 53/UDP 解析 DNS
  • <Egress/9092/TCP/Kafka> — Kafka 可視性
⚠ L7 可視性的安全與效能取捨
  • 性能：流量過 Envoy 增加 latency（多 μs 到 ms）；不要對高 throughput 大流量無腦開
  • 安全：Envoy 也是攻擊面，雖然 Cilium 限制過權限
  • 合規：解析 HTTP body 涉及隱私，請與資安/法遵確認

9. IP 封包追蹤（連線層級除錯）

Hubble 看的是 flow 級別。有時候你需要看單一封包真實旅程：經過哪些 BPF program、哪個 verdict、被哪個 BPF map lookup 處理？這就是 cilium-dbg monitor 與 cilium-dbg policy trace 的用武之地。

cilium-dbg monitor：看 BPF datapath event

bash
# 進到目標 node 的 cilium-agent
kubectl -n kube-system exec -ti ds/cilium -- bash

# 看所有 event (verbose)
cilium-dbg monitor -v

# 只看 drop
cilium-dbg monitor --type drop

# 只看 policy verdict
cilium-dbg monitor --type policy-verdict

# 過濾特定 endpoint
cilium-dbg monitor --related-to 1234
cilium-dbg monitor --from 1234
cilium-dbg monitor --to 5678

輸出範例（drop event）：

output
xx drop (Policy denied) flow 0x1234567 to endpoint 0, identity 12345->67890: 10.0.1.5:43210 -> 10.0.2.8:8080 tcp SYN
xx drop (Policy denied) flow 0x1234568 to endpoint 0, identity 12345->67890: 10.0.1.5:43210 -> 10.0.2.8:8080 tcp SYN

裡面有具體的 identity ID（可對應你的 pod label）、drop reason、5-tuple。

policy trace：模擬一個請求看會不會通

不需要實際送 request，模擬 source / destination 看 Cilium 會怎麼決定：

bash
# 假設要驗證 frontend (identity 12345) 能不能連到 backend (identity 67890):80
kubectl -n kube-system exec -ti ds/cilium -- \
  cilium-dbg policy trace \
    --src-identity 12345 \
    --dst-identity 67890 \
    --dport 80/TCP

# 輸出顯示哪些 policy match、最終決議 (ALLOWED / DENIED)

endpoint list：看 pod 的 identity 與已套用 policy

bash
kubectl -n kube-system exec -ti ds/cilium -- cilium-dbg endpoint list

# 詳細
kubectl -n kube-system exec -ti ds/cilium -- cilium-dbg endpoint get <endpoint-id>

# 看 endpoint 對應的所有 allow rule
kubectl -n kube-system exec -ti ds/cilium -- cilium-dbg policy selectors

# 看 DNS proxy 學到了哪些 FQDN
kubectl -n kube-system exec -ti ds/cilium -- cilium-dbg fqdn cache list

10. Hubble / Metrics 故障排除

症狀原因排查
Hubble UI 開啟但 service map 空 Relay 還沒連到所有 agent hubble status 看 Connected Nodes: N/N
flow 出現很少 (Flows/s 很低) cluster 流量本來就少 / Hubble ring buffer 太小被 evict 調 hubble.eventBufferCapacity
L7 visibility 沒出現 (HTTP path 空) 沒寫 L7 policy 或 visibility annotation 確認 §8 設定
Prometheus 沒收到 metric ServiceMonitor label 跟 Prometheus selector 不符 查 kubectl get prometheus -A -o yaml | grep serviceMonitorSelector

11. 本章重點回顧

  • Hubble 三件式：Hubble in agent（資料來源）+ Hubble Relay（cluster 中央）+ Hubble UI（service map）。生產加上 Exporter / Prometheus。
  • Hubble CLI 核心：hubble observe + filters。verdict 是排查 policy 的關鍵；FORWARDED / DROPPED / REDIRECTED 各有意義。
  • Hubble UI 的 service map 是 onboarding 與 incident review 的利器，紅色箭頭代表 drop。
  • Flow 預設只在 ring buffer（4095/node）。要長期保留必啟 Exporter → file → Fluent Bit → Loki/ES。
  • 四個 metric 來源：prometheus.enabled / operator.prometheus.enabled / hubble.metrics.enabled / clustermesh.apiserver.metrics.enabled。OpenMetrics + httpV2 exemplars 是現代寫法。
  • 大叢集務必排除 高基數 metric：cilium_node_connectivity_status/_latency、IP-based label。
  • L7 visibility 兩條路：寫 L7 policy（連帶 enforcement）或 visibility annotation（純觀察）。注意 latency 開銷。
  • 單封包追蹤用 cilium-dbg monitor、policy trace、endpoint list、fqdn cache list。
  • Grafana dashboard ID 16611–16614 可直接 import。
