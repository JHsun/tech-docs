網路功能 · 基礎

這一章是 Cilium 網路的核心，講 Pod 封包怎麼跑、IP 怎麼配、kube-proxy 怎麼被取代。讀完你會看懂 cilium status 每一行、選對 routing mode、知道 NodePort 流量怎麼到 backend pod。後續第四部 B 處理 BGP、ClusterMesh、Egress 等進階主題。

對應官方文件：Networking → Concepts / Kubernetes（除 BGP、ClusterMesh、Egress、Service Mesh） Cilium 版本：1.19.x 主要對象：DevOps / SRE，開發者選讀

1. Pod 封包旅程：宏觀視角

關鍵點：

  • 每個 Pod 有一對 veth pair，一端在 Pod netns，一端在 host netns
  • Cilium 在 host 端 veth 的 TC ingress hook 掛 BPF program，這是政策、observability、service LB 真正發生的地方

2. Routing Mode：跨 node 流量怎麼走

Cilium 有兩種主要 routing mode，選哪一個取決於底層網路能不能路由 Pod CIDR：

ModeHelm valuePod IP 怎麼跨 node
Tunnel（預設）routingMode: tunnelVXLAN/Geneve 封裝後用 node IP 走 underlay
NativeroutingMode: native直接用 Pod IP 走 underlay 路由表

2.1 Tunnel mode（封裝）

所有 cluster node 之間建立 n × n 隧道網狀，封包離開 source node 前包一層 VXLAN 或 Geneve header，外層 IP 是 node IP；對端 node 收到後拆封，把內層 Pod 封包送進 BPF 處理。

封裝協定差異

協定UDP PortHeader 大小特點
VXLAN（預設）8472（Cilium）或 4789（IANA）50 bytes業界主流，broad kernel support
Geneve608150–60 bytes支援 TLV option，可放 metadata；DSR / 跨 CNI 共存場景常用
⚠ MTU 注意

封裝會吃掉 ~50 bytes，預設 1500 MTU 的網路會把 inner packet 限制到 1450。應用層大流量場景請開 jumbo frame（host MTU 9000，相對開銷比例從 3.3% 降到 0.6%）。

2.2 Native routing（直接路由）

沒有封裝，Pod IP 直接走 underlay。需要 underlay router / switch 知道每個 Pod CIDR 怎麼到，方法有三種：

  • 同 L2：開 autoDirectNodeRoutes=true，Cilium 自動在每個 node 加 host route「Pod CIDR via Node IP」
  • 不同 subnet：用 BGP（第四部 B 詳述）讓路由器學到 Pod CIDR
  • 雲端：用 ENI / Azure / GKE 模式，IP 由 cloud VPC 直接管理
yaml
# native routing values
routingMode: native
ipv4NativeRoutingCIDR: "10.0.0.0/8"   # 哪些 IP 範圍視為 cluster 內，不做 masquerade
autoDirectNodeRoutes: true            # 同 L2 域自動寫 route
bpf:
  masquerade: true                    # BPF SNAT（出 cluster 才做）

2.3 對照與選擇

Tunnel mode

選它如果：
  • 多雲、雲端 VPC 無法路由 Pod CIDR
  • Pod 數量很大、要彈性 CIDR 規劃
  • 跨多個 L2 / L3 域，topology 複雜
代價：
  • ~50 bytes overhead / packet
  • MTU 要算清楚
  • 對 underlay 觀察工具不透明（tcpdump 看到的是 outer IP）

Native routing

選它如果：
  • 地端、自有 underlay 可掌控路由
  • 追求極致效能、低延遲
  • 有 BGP fabric 或同 L2 域
  • 雲端用 ENI / Azure / GKE 整合
代價：
  • 需要與網路團隊協調路由
  • 不能自由規劃 Pod CIDR

3. IPAM：Pod IP 怎麼配

IPAM 決定「新 Pod 建立時，從哪裡拿到 IP」。Cilium 支援多種模式，差異在「誰負責管 IP pool」：

Mode誰負責典型場景
cluster-pool（預設）Cilium Operator 切大 CIDR 給 node地端、自建
kubernetesK8s controller-manager 給 node CIDRGKE、需要與 K8s 預設一致
multi-pool多個 CiliumPodIPPool CRD多資料中心、不同 namespace 用不同 CIDR
eniAWS ENI API 配發 VPC IPEKS, native VPC routing
azureAzure VNET 配發 IPAKS BYOCNI
delegated-plugin外部 IPAM plugin特殊需求（cloud delegated）
⚠ 一旦選定不要中途切換

官方明確警告：不要在 live cluster 改 IPAM mode。切 mode 等於整個 IP 系統重做，現有 Pod 連線會大量中斷。最安全的路徑是建新 cluster + 應用遷移。

3.1 Cluster Pool（預設）

運作邏輯：

  1. 你給 Cilium 一個「大 CIDR」（如 10.244.0.0/16）+ 每 node 的 mask size（如 /24）
  2. Operator 為每個 node 從大 CIDR 切一個 /24，寫到 CiliumNode CRD
  3. Agent 在 node 上看到 CiliumNode，就從自己的 /24 配給新 Pod
yaml
ipam:
  mode: cluster-pool
  operator:
    clusterPoolIPv4PodCIDRList:
      - "10.244.0.0/16"
    clusterPoolIPv4MaskSize: 24   # 每 node 一個 /24，最多 254 個 Pod IP
bash
# 驗證每 node 拿到的 CIDR
kubectl get ciliumnodes -o json | \
  jq '.items[] | {name: .metadata.name, podCIDRs: .spec.ipam.podCIDRs}'

# 預期:
# { "name": "cilium-lab-control-plane", "podCIDRs": ["10.244.0.0/24"] }
# { "name": "cilium-lab-worker",        "podCIDRs": ["10.244.1.0/24"] }
# { "name": "cilium-lab-worker2",       "podCIDRs": ["10.244.2.0/24"] }
⚠ clusterPoolIPv4MaskSize 不能事後改

已配出去的 CIDR 不能變。如果你只是 pool 用完了，新增 CIDR 到 clusterPoolIPv4PodCIDRList 是 OK 的。

3.2 Kubernetes Host Scope

把 IPAM 交給 K8s controller-manager 的 --node-cidr-mask-size 機制。Cilium 只是讀 node.spec.podCIDR。優點是跟其他 cluster 觀察工具一致，缺點是規模/彈性不如 cluster-pool。

yaml
ipam:
  mode: kubernetes
# 不需要 clusterPool* 設定，看 kube-controller-manager 的 --cluster-cidr 與 --node-cidr-mask-size

3.3 Multi-Pool（1.19 升 stable）

1.19 把 Multi-Pool IPAM 從 Beta 升為 Stable。它讓你在同一個 cluster 內維護多個 CiliumPodIPPool，再用 namespace annotation 或 node label 分配。

用途：

  • 多資料中心：DC1 用 10.1.0.0/16，DC2 用 10.2.0.0/16，靠 node label 選
  • 合規切割：production / development namespace 拿不同 CIDR
  • SNAT 控制：某些 pool 不做 masquerade，讓 firewall 用 Pod IP 識別

Lab：建立額外 pool 並用 namespace annotation 切換

yaml
# 啟用 multi-pool（注意：要 fresh cluster，無法 in-place 切）
ipam:
  mode: multi-pool
  operator:
    autoCreateCiliumPodIPPools:
      default:
        ipv4:
          cidrs: ["10.10.0.0/16"]
          maskSize: 27
yaml
# 建立額外 pool "mars"
apiVersion: cilium.io/v2alpha1
kind: CiliumPodIPPool
metadata:
  name: mars
spec:
  ipv4:
    cidrs:
      - "10.20.0.0/16"
    maskSize: 27
bash
# 把 namespace 綁到 mars pool
kubectl create namespace mars-app
kubectl annotate namespace mars-app ipam.cilium.io/ip-pool=mars

# 新 pod 會從 mars CIDR 拿 IP
kubectl run -n mars-app test --image=nginx
kubectl get pod -n mars-app test -o jsonpath='{.status.podIP}'
# 預期: 10.20.x.x

# 或者只給特定 Deployment 用 mars pool（template annotation）
kubectl apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-mars
spec:
  selector: { matchLabels: { app: nginx-mars } }
  replicas: 2
  template:
    metadata:
      labels: { app: nginx-mars }
      annotations:
        ipam.cilium.io/ip-pool: mars
    spec:
      containers:
      - name: nginx
        image: nginx
EOF

3.4 雲端 IPAM 模式

AWS ENI

Pod 用 VPC IP（從 ENI secondary IP 配），完全 native routing，跟 EC2/RDS 直連不用穿 overlay。

yaml
ipam:
  mode: eni
eni:
  enabled: true
  awsEnablePrefixDelegation: true       # 1 ENI 一次拿 /28，提升每 node Pod 上限
ipam:
  operator:
    eniMinAllocate: 8                   # 預先保持 8 個 IP 可用
    eniMaxAllocate: 30                  # 上限
routingMode: native

EC2 instance type 決定 ENI 數量上限與每 ENI 可附 IP 數，m5.large 大約 30 個 Pod，m5.4xlarge 大約 234 個。開 prefix delegation 後可大幅提升。

Azure

yaml
ipam:
  mode: azure
azure:
  enabled: true
  resourceGroup: my-aks-rg
  subscriptionID: xxx
  tenantID: xxx
  clientID: xxx                          # 給 Cilium operator 用的 SP

3.5 IPAM 調校（pre-allocation）

新 Pod 建立時若要等 IP 配置，會增加啟動延遲。Cilium 提供 pre-allocation：預先在每個 node 保留 N 個可用 IP。

yaml
# 適用於 cluster-pool / multi-pool / 雲端模式
# 寫在 CiliumNode（CRD）的 spec.ipam，或用 Helm 設預設值
spec:
  ipam:
    min-allocate: 10           # 每 node 至少保留 10 個可用 IP
    pre-allocate: 16           # 預先 allocate 16 個（高 churn 環境提高）
    max-above-watermark: 8     # 超過 watermark 多 8 個就停止 allocate
    max-allocate: 250          # 每 node 上限
bash
# 監控 IP 用量
cilium status --verbose | grep -A 10 "IPAM"

# 看各 node 剩多少
for n in $(kubectl get ciliumnodes -o name); do
  echo "=== $n ==="
  kubectl get $n -o jsonpath='{.status.ipam.used}{"\n"}'
done

# IP 枯竭警報（events）
kubectl get events --all-namespaces | grep -i "IP allocation failed"

4. Masquerading（SNAT）

Pod 連到 cluster 外部（網際網路、企業內網）時，Pod IP 通常不能被外部路由，必須做 SNAT 把 src IP 改成 node IP。Cilium 提供兩種 masquerading 實作：

實作Helm value說明
iptables-based預設關閉傳統方式，靠 host iptables NAT 表
BPF-based（推薦）bpf.masquerade: trueBPF 在 datapath 直接 SNAT，繞過 netfilter

誰會被 SNAT、誰不會的判斷依據：

  • 目的 IP 落在 ipv4NativeRoutingCIDR（或 default cluster CIDR）→ 不做 SNAT（cluster 內部流量）
  • 目的 IP 不在範圍內 → 做 SNAT，src IP 改成 egress NIC 的 IP

1.19 進階：per-pool 與跨 subnet 客製

1.19 新增能力：

  • 對「往其他 IP subnet 的 node」流量做不同 masquerade 設定
  • 用 --only-masquerade-default-pool，排除非預設 IPAM pool 不做 SNAT，讓某些 pool 的 Pod IP 在 underlay 可見
  • 個別 pool 加 annotation ipam.cilium.io/skip-masquerade="true"
bash
# 驗證 BPF masquerade 啟用
cilium config view | grep -i masq
# 預期:
# enable-bpf-masquerade            true
# enable-ip-masq-agent             false  (除非你用 ip-masq-agent ConfigMap)

# 看 iptables 還有沒有 NAT 規則（BPF masquerade 啟用後幾乎沒有）
docker exec cilium-lab-control-plane iptables-save -t nat | grep -i masq

5. Fragment Handling

網路封包可能因為 MTU 不匹配被 fragment。Cilium 的 BPF datapath 在處理 fragment 時要特別小心：第二個之後的 fragment 沒有 L4 header，無法決定屬於哪個連線。

Cilium 用 fragment tracking BPF map 記住「第一個 fragment 的 5-tuple」，後續 fragment 用 IP ID 比對。預設啟用：

yaml
# 預設值（通常不用改）
enable-ipv4-fragments-tracking: true
bpf:
  fragments-map-max: 8192        # 同時追蹤的 fragment 數量上限

大量 fragment 環境（如 IPsec、雙重封裝）可能需要把 fragments-map-max 提高。

6. kube-proxy 替換

6.1 為什麼要換

傳統 kube-proxy 有兩種模式，都有 scaling 痛點：

模式查找痛點
iptablesO(n) 線性掃 chain1000 services → 上萬條規則，每個封包都要過；rule 更新要全部 reload
IPVShash 表 O(1)還是要過 netfilter / conntrack；不支援 L7

Cilium 用 BPF map 取代上面兩者，從根本上把 service lookup 從 netfilter 抽離：

  • O(1) hash lookup：不管 service 數量，查詢時間幾乎不變
  • Socket-level LB：cluster 內部呼叫，在 connect() syscall 時就把 ClusterIP 改成 backend pod IP，連 conntrack 都不用
  • XDP 加速：外部進來的 LoadBalancer / NodePort 流量可在 NIC driver 層做 LB，極致吞吐

  algorithm: maglev             # random / maglev
  dsrDispatch: opt              # opt / geneve / ipip

6.4 Maglev consistent hashing

預設 LB 算法是 random，每個連線隨機挑 backend。Maglev（Google 論文的變體）提供consistent hashing：

  • 同一個 5-tuple 永遠選同一個 backend（無 state 同步需求）
  • backend 加減時，最多 1% 連線會被重分配到不同 backend（vs random 100%）
  • Memory 用量比 random 高（lookup table）
  • 主要用於 north-south 外部流量；east-west 內部走 socket-LB 直連

# 預期: 0 （或極少數，因為其他 controller 可能也會寫）

# 5. 部署一個 Service 驗證 LB 還是運作
kubectl create deployment nginx --image=nginx --replicas=3
kubectl expose deployment nginx --port=80

# 從另一個 pod 試
kubectl run -it --rm curl --image=curlimages/curl --restart=Never \
  -- curl -s nginx | head -5
# 預期: 看到 nginx welcome page
✓ 觀察重點

同樣的 Service 概念（ClusterIP、NodePort、LoadBalancer）在 application 端完全沒變，但 datapath 從成千上萬條 iptables 規則變成幾個 BPF map lookup。這也是為什麼大型 cluster 升級到 Cilium 後，CPU 用量明顯下降。

7. K8s 網路整合

7.1 Cilium 自家 CRD 全集

Cilium 安裝時會建立一組 CRD，這是與 K8s 互動的主要介面：

CRD用途
CiliumNode每個 K8s node 對應一個，記錄 PodCIDR、health endpoint、IPAM 狀態
CiliumEndpoint每個 Pod 對應一個，記錄 identity、IP、policy verdict
CiliumEndpointSlice大型 cluster 用，把 CiliumEndpoint 聚合成 slice 減少 etcd 壓力
CiliumIdentityidentity ID → labels 對照表（cluster scope）
CiliumNetworkPolicy (CNP)namespace scoped network policy（取代 / 擴充 K8s NP）
CiliumClusterwideNetworkPolicy (CCNP)cluster scope，所有 namespace 適用
CiliumCIDRGroup把多個 CIDR 命名打包，給 policy 引用
CiliumPodIPPoolMulti-Pool IPAM 用
CiliumLoadBalancerIPPool給 Service.type=LoadBalancer 配 external IP
CiliumNodeConfig對特定 node label 套用不同配置（漸進式 rollout 用）
CiliumBGPClusterConfig 系列BGP control plane（第四部 B 詳述）
CiliumEgressGatewayPolicyEgress Gateway（第四部 B 詳述）
CiliumL2AnnouncementPolicyL2 ARP / ND announcement
CiliumLocalRedirectPolicy把 Service 流量導到 local node Pod

7.2 EndpointSlice 與 CiliumEndpointSlice

每個 Pod 一個 CiliumEndpoint，大 cluster（5000+ Pod）就會 etcd 壓力大。1.10+ 提供 CiliumEndpointSlice：

yaml
# 啟用 (大型 cluster 建議)
ciliumEndpointSlice:
  enabled: true

啟用後，Operator 會把多個 CiliumEndpoint 打包成一個 CiliumEndpointSlice 物件（類似 K8s EndpointSlice 對 Endpoint 的關係），大幅減少 watch event。

7.3 Bandwidth Manager

Cilium 支援 Pod-level 頻寬限制（egress），靠 BPF + EDT (Earliest Departure Time) 實作，比 traditional traffic shaping 精準很多。

yaml
# Helm 啟用
bandwidthManager:
  enabled: true
  bbr: true              # BBR congestion control（建議）
yaml
# Pod 加 annotation 限速
apiVersion: v1
kind: Pod
metadata:
  name: rate-limited
  annotations:
    kubernetes.io/egress-bandwidth: "10M"   # 10 Mbps egress 上限
spec:
  containers:
  - name: app
    image: nginx

7.4 Local Redirect Policy

用途：把 Pod 連到某個 Service 的流量，強制導去同 node 上的本地 Pod，而非 cluster 範圍 LB。典型場景：

  • Node-local DNS cache（每 node 一個 dnscache，pod 永遠連自家 node 的 dnscache）
  • Per-node sidecar（metric agent、log shipper）
yaml
# Cilium 必須開啟支援
localRedirectPolicy: true

# 套用：把 kube-dns 流量導去本地 nodelocaldns
apiVersion: "cilium.io/v2"
kind: CiliumLocalRedirectPolicy
metadata:
  name: "nodelocaldns"
  namespace: kube-system
spec:
  redirectFrontend:
    serviceMatcher:
      serviceName: kube-dns
      namespace: kube-system
  redirectBackend:
    localEndpointSelector:
      matchLabels:
        k8s-app: node-local-dns
    toPorts:
      - port: "53"
        protocol: UDP
      - port: "53"
        protocol: TCP

7.5 Identity Management Mode

Cilium 1.16+ 提供新的 Identity Management Mode，控制 identity 在 kvstore 中的儲存與分配方式：

Mode說明適用
crd（預設）identity 存在 K8s CRD（CiliumIdentity）大多數 cluster
kvstoreidentity 存在 external etcd超大規模 cluster，避免 K8s API 壓力
yaml
identityAllocationMode: crd          # 或 kvstore
identityChangeGracePeriod: "5s"      # identity 變更前等待時間

8. 本章重點回顧

  • Pod 封包旅程：app → veth pair → host TC BPF → routing → NIC → underlay。BPF 在 host 端 veth 的 TC ingress hook 是核心。
  • Routing mode 二選一：tunnel（封裝 VXLAN/Geneve） vs native（underlay 直接路由）。tunnel 開銷 ~50 bytes，native 需要 underlay 知道 Pod CIDR。
  • IPAM 五種主要模式：cluster-pool（預設）/ kubernetes / multi-pool（1.19 stable）/ 雲端模式（eni / azure）。不要在 live cluster 切換 IPAM mode。
  • BPF masquerade 取代 iptables NAT，搭配 ipv4NativeRoutingCIDR 控制誰要 SNAT。
  • kube-proxy 替換有三層機制：socket-LB（cluster 內） + XDP（外部進來，極致快）+ TC BPF（fallback）。
  • LB mode 三選一：snat（最相容）/ dsr（保留 client IP）/ hybrid（TCP DSR + UDP SNAT，折衷）。
  • Maglev consistent hashing：backend 加減時最多 1% 連線重分配，主要用 north-south。
  • 記住主要 CRD：CiliumNode、CiliumEndpoint、CiliumIdentity、CiliumNetworkPolicy。大型 cluster 開 CiliumEndpointSlice。
  • Bandwidth Manager 用 EDT + BBR 做 Pod 級 egress 限速；Local Redirect Policy 把 Service 導到 local Pod，典型用法是 node-local DNS。
