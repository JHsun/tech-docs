實戰安全與 Threat Model

6A 把 policy 語法武器交給你，6B 用這些武器解真實問題：DNS 鎖定、TLS 流量檢視、Kafka 與 gRPC 防護、AWS metadata 攻擊面、host firewall、Transparent Encryption（含 1.19 strict mode），最後從 threat model 視角審視整個 cluster 並給出強化清單。

1. 實戰場景一：Identity-Aware HTTP 政策（Star Wars 進階版）

第二部已經跑過 Star Wars demo，這裡再加碼，把它做成「production-grade」政策樣板，可直接套用到自家 microservice：

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: deathstar-production-grade
  namespace: empire
spec:
  description: "Production-grade ingress policy for deathstar"
  endpointSelector:
    matchLabels:
      app: deathstar
      env: prod          # 只對 prod 生效

  ingress:
    # 1) 只允許 tier=control-tower 的 pod 連
    - fromEndpoints:
        - matchLabels:
            tier: control-tower
            org: empire
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http:
              # 允許 landing：GET 與 POST 都接受
              - method: GET
                path: "/v1/healthz"
              - method: POST
                path: "/v1/request-landing"
                headers:
                  - "x-empire-token: .+"      # header 必須帶 token

    # 2) Prometheus 可 scrape /metrics
    - fromEndpoints:
        - matchLabels:
            app: prometheus
            "k8s:io.kubernetes.pod.namespace": monitoring
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]
          rules:
            http:
              - method: GET
                path: "/metrics"

  egress:
    # 1) DNS 必須允許
    - toEndpoints:
        - matchLabels:
            "k8s:io.kubernetes.pod.namespace": kube-system
            "k8s:k8s-app": kube-dns
      toPorts:
        - ports: [{ port: "53", protocol: UDP }]
          rules:
            dns: [{ matchPattern: "*" }]

    # 2) 連自家 fleet API (FQDN)
    - toFQDNs:
        - matchPattern: "*.fleet.empire.internal"
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]

樣板要點：

  • 聲明式 description：未來別人 review 時知道意圖
  • env=prod 限縮：staging 用其他 policy
  • 明確列出 Prometheus 例外：observability 不會被誤殺
  • egress 永遠先 allow DNS：常被忘記，忘了就所有外部呼叫失敗
  • FQDN 加 wildcard：API 改 IP 不用改 policy

2. 實戰場景二：DNS 鎖定

場景：你不想 cluster 內 pod 隨意呼叫 internet。傳統 firewall 寫 IP 沒用（IP 一直變）。Cilium DNS-aware policy 解這個。

2.1 攔截 DNS + 用 FQDN allow list

核心觀念：Cilium agent 內建 DNS proxy，攔截 pod 的 DNS query，看到 response 後把 IP 寫進 BPF map，給後續封包 lookup 用。

sequenceDiagram participant P as Pod participant DP as Cilium DNS Proxy
(per-node) participant KD as kube-dns participant API as registry.io participant BPF as BPF policy map P->>DP: DNS query: registry.io DP->>DP: 檢查 rules.dns matchPattern DP->>KD: 轉發 query KD-->>DP: A 1.2.3.4 DP->>BPF: 寫入：1.2.3.4 屬於 registry.io DP-->>P: A 1.2.3.4 P->>BPF: TCP connect 1.2.3.4:443 BPF->>BPF: 確認該 IP 對應 allowed FQDN BPF-->>API: 放行

策略範例（全 cluster 預設只能 DNS + 特定域名）：

yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: global-egress-default
spec:
  endpointSelector:
    matchExpressions:
      # 跳過 kube-system / cilium 自己的 pod
      - { key: "k8s:io.kubernetes.pod.namespace", operator: NotIn,
          values: ["kube-system"] }
  egress:
    # 1) DNS（必要）
    - toEndpoints:
        - matchLabels:
            "k8s:io.kubernetes.pod.namespace": kube-system
            "k8s:k8s-app": kube-dns
      toPorts:
        - ports: [{ port: "53", protocol: UDP }]
          rules:
            dns:
              - matchPattern: "*.internal"
              - matchPattern: "*.svc.cluster.local"
              - matchPattern: "*.googleapis.com"
              - matchPattern: "*.amazonaws.com"
              - matchPattern: "registry.example.com"
              # 沒列在這的域名連解析都不行

    # 2) 對 allow 的 FQDN 開 https
    - toFQDNs:
        - matchPattern: "*.internal"
        - matchPattern: "*.googleapis.com"
        - matchPattern: "*.amazonaws.com"
        - matchName: "registry.example.com"
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]

    # 3) cluster 內部全允許（不用透過 FQDN）
    - toEntities:
        - cluster

2.2 Standalone DNS Proxy 1.18+

內建 DNS proxy 跟 cilium-agent 綁在一起：agent 重啟 / 升級 → DNS proxy 重啟 → 短暫的 DNS 解析延遲 / 失敗。1.18+ 提供 Standalone DNS Proxy，把 DNS proxy 拆成獨立 DaemonSet，跟 agent 升級解耦。

yaml
# Helm
standaloneDNSProxy:
  enabled: true
  image:
    repository: quay.io/cilium/dns-proxy
    tag: v1.19.3
💡 何時用 Standalone DNS Proxy

DNS query 量大、對解析延遲敏感、或定期升級 Cilium 不想短暫影響 DNS 的環境，建議啟用。一般 cluster 用內建 proxy 即可。

3. 實戰場景三：TLS Visibility（流量檢視）

傳統 IDS 看不到 HTTPS 內容。Cilium 提供兩種看清 TLS 流量的方式：

方式機制能看到什麼
SNI policy 讀 ClientHello SNI，不解密 目的 hostname
TLS termination + HTTP policy Envoy 解密、檢查、再加密 完整 HTTP method / path / headers

方式一：SNI（最常用，不需提供憑證）

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: tls-sni
spec:
  endpointSelector:
    matchLabels: { app: my-service }
  egress:
    - toPorts:
        - ports: [{ port: "443", protocol: TCP }]
          serverNames:
            - "api.openai.com"
            - "*.googleapis.com"
            - "registry.example.com"
        # 不在這份名單的 SNI 立刻 reset

方式二：TLS 攔截（需要 CA 與 server cert）

讓 Cilium 對 egress 流量做 MITM（man-in-the-middle），需要提供：

  • cluster 內 trusted CA（讓 client 信任）
  • 對應目標的 server cert
yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: tls-inspect
spec:
  endpointSelector:
    matchLabels: { app: my-service }
  egress:
    - toFQDNs:
        - matchName: "api.example.com"
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]
          terminatingTLS:
            secret:
              namespace: cilium-secrets
              name: api-example-com-tls
          originatingTLS:
            secret:
              namespace: cilium-secrets
              name: ca-cert
          rules:
            http:
              - method: GET
                path: "/v1/users/.*"
              - method: POST
                path: "/v1/orders"
⚠ TLS 攔截的合規顧慮

MITM 自家 service 沒問題；但對外部 SaaS 解密通常違反 ToS 與隱私規範。實作前先確認合規。多數場景用 SNI policy 已足夠。

4. 實戰場景四：Kafka / gRPC / Elasticsearch 防護

4.1 Kafka 已 deprecated

Cilium 早期支援原生 Kafka L7 rule（rules.kafka），1.18+ 已標記 deprecated。建議改用：

  • L4 + SNI：限定能連 Kafka broker 的 pod，搭配 broker 的 SASL/mTLS
  • K8s 原生 mTLS：Kafka 自己的 SASL_SSL，Cilium 只管 L4 layer
yaml
# L4 寫法：只允許 producer-app / consumer-app 連 kafka
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: kafka-l4
spec:
  endpointSelector:
    matchLabels: { app: kafka-broker }
  ingress:
    - fromEndpoints:
        - matchLabels: { role: kafka-producer }
        - matchLabels: { role: kafka-consumer }
      toPorts:
        - ports:
            - { port: "9093", protocol: TCP }   # SASL_SSL

4.2 gRPC（HTTP/2 path）

第六部 A 講過：gRPC 跑在 HTTP/2 上，path 為 //，用 HTTP rule 寫即可。實戰範例：限制 UserService 只允許 Read 類方法給某些 caller。

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: grpc-userservice
spec:
  endpointSelector:
    matchLabels: { app: user-service }
  ingress:
    - fromEndpoints:
        - matchLabels: { role: readonly-client }
      toPorts:
        - ports: [{ port: "50051", protocol: TCP }]
          rules:
            http:
              - method: POST
                path: "/myapp\\.UserService/Get.*"
              - method: POST
                path: "/myapp\\.UserService/List.*"
              # CreateUser / DeleteUser 因為不符合 Get* List* 被擋

    - fromEndpoints:
        - matchLabels: { role: admin-client }
      toPorts:
        - ports: [{ port: "50051", protocol: TCP }]
          rules:
            http:
              - method: POST
                path: "/myapp\\.UserService/.*"   # 所有方法

4.3 Elasticsearch（HTTP API）

Elasticsearch 是 REST API，用 HTTP rule 限制能呼叫哪些 endpoint：

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: elasticsearch-readonly
spec:
  endpointSelector:
    matchLabels: { app: elasticsearch }
  ingress:
    # 一般應用只允許讀（_search 等）
    - fromEndpoints:
        - matchLabels: { role: app }
      toPorts:
        - ports: [{ port: "9200", protocol: TCP }]
          rules:
            http:
              - method: GET
                path: "/_search.*"
              - method: GET
                path: "/.*/_search.*"
              - method: POST
                path: "/.*/_search.*"
              # 任何 DELETE / PUT 寫操作都被擋

    # admin pod 才允許寫
    - fromEndpoints:
        - matchLabels: { role: admin }
      toPorts:
        - ports: [{ port: "9200", protocol: TCP }]

5. 實戰場景五：Cloud Metadata 鎖定（SSRF 防護）

三大雲端都有 instance metadata endpoint（如 AWS 的 169.254.169.254），裡面有 IAM credentials。如果 pod 應用有 SSRF 漏洞，攻擊者可以叫 pod 去打這 endpoint 偷 token，提權到雲端帳號。

標準防護：cluster-wide 擋掉所有 pod 連 metadata IP（特例放行 cloud-controller-manager / node-problem-detector 等真正需要的 component）：

yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: deny-cloud-metadata
spec:
  endpointSelector:
    matchExpressions:
      # 排除 kube-system 的合法用途
      - { key: "k8s:io.kubernetes.pod.namespace",
          operator: NotIn, values: ["kube-system"] }
  egressDeny:
    - toCIDR:
        - "169.254.169.254/32"     # AWS IMDS, Azure IMDS, GCP metadata
        - "fd00:ec2::254/128"      # AWS IMDSv6
        - "169.254.170.2/32"       # AWS ECS task metadata
⚠ AWS 額外建議

EKS 環境同時要把 EC2 強制改成 IMDSv2（要求 PUT token），這在 Cilium policy 之外多一層保護。Cilium policy 與 EC2 instance metadata options 兩個一起做。

6. 實戰場景六：Host Firewall 鎖住 bastion / DB node

6A 介紹過 host policy 概念，這裡給生產樣板。場景：bastion / jump box 是進 cluster 的唯一管道，要嚴格控制。

yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: bastion-host-firewall
spec:
  nodeSelector:
    matchLabels:
      role: bastion

  ingress:
    # 1) SSH 只開給辦公 IP
    - fromCIDRSet:
        - cidrGroupRef: corp-office-networks
      toPorts:
        - ports: [{ port: "22", protocol: TCP }]

    # 2) K8s 內部 (kubelet metric scrape, cluster traffic)
    - fromEntities:
        - remote-node
        - host
        - kube-apiserver
      toPorts:
        - ports:
            - { port: "10250", protocol: TCP }   # kubelet
            - { port: "9100",  protocol: TCP }   # node-exporter

    # 3) ICMP（讓 ping 還能用，debug 方便）
    - fromCIDR: ["0.0.0.0/0"]
      icmps:
        - fields: [{ type: 8, family: IPv4 }]

啟用前務必先在 staging 測完整，並開 hubble 持續觀察 verdict，確認沒有預期內的流量被誤殺。

7. 從 Hubble Verdict 反向產生 Policy

實務上，你接手一個已運行的 cluster，沒人知道哪些 pod 跟哪些 pod 講話。怎麼開始寫 policy？答案：先觀察、再 codify。

步驟一：監聽 cluster 全 flow，存 JSON

bash
# 1. 先確保 hubble enabled
cilium hubble enable --ui

# 2. 持續觀察至少幾天（涵蓋 batch job、cron、weekly task）
hubble observe \
  --namespace my-app \
  --verdict FORWARDED \
  --output jsonpb \
  > observed-flows.jsonl &

# 等夠久後（建議 1 週以上）
kill $!

步驟二：用社群工具產生 policy 草稿

幾個社群工具能讀 hubble flow 自動產 CNP：

  • hubble-flow2policy（社群工具）：讀 hubble JSON 產 CNP YAML
  • Cilium Network Policy Editor：圖形介面，editor.networkpolicy.io
  • Tetragon（Cilium 姊妹專案）：基於 eBPF 的 runtime security，也能做行為 baseline

步驟三：產出後務必人工審核

⚠ 機器產出 ≠ 直接套用

自動產的 policy 反映「觀察期內的實際流量」，包含可能的攻擊 / 不該存在的呼叫。生產採用前一定要：

  • review 每一條 rule 的合理性
  • 移除明顯不該存在的流量（如生產 pod 連到 dev DB）
  • 先 default 模式試跑一週看 hubble drop log，確認沒誤殺
  • 再用 always mode 完全 enforce

8. Transparent Encryption

很多合規要求「data in transit must be encrypted」。應用層 TLS 確實滿足，但維運成本高（每個服務要管 cert）。Cilium Transparent Encryption 給你在 datapath 層面加密所有 pod 間流量的選擇，零應用改動。兩種實作：

WireGuard（推薦）

  • kernel 5.6+ 原生支援
  • 4000 行 code，易審計
  • 無需管理 cert，agent 自動配 keypair
  • UDP port 51871
  • FIPS 140-2 compliance ?（看 distro）

IPsec

  • 傳統業界標準
  • FIPS 完整支援
  • 需要管理 PSK 或 cert (xfrm)
  • kernel module 較複雜
  • 1.19 起支援 BPF Host Routing 加速

8.1 WireGuard 啟用

bash
# 前置：確認 kernel 支援 WireGuard
modprobe wireguard 2>/dev/null && echo "Kernel WireGuard OK"

# 啟用
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --reuse-values \
  --set encryption.enabled=true \
  --set encryption.type=wireguard \
  --set encryption.nodeEncryption=true        # 1.10+ 也加密 node 流量

kubectl -n kube-system rollout restart ds/cilium

# 驗證
cilium status | grep Encryption
# 預期: Encryption: Wireguard [cilium_wg0 (Pubkey: , Port: 51871, Peers: N-1)]

# 每個 node 自動產 keypair 並寫到 CiliumNode CRD
kubectl get ciliumnodes -o yaml | grep -A1 "wg-pub-key"

WireGuard 細節

  • 每 node 建立對所有其他 node 的 WireGuard tunnel mesh
  • 同 node 內 pod-to-pod 不加密（理由：能進 node 就能看封包，加密無意義）
  • 預設不加密 control-plane node 與 worker 之間的 host network 流量，避免 key 換新時 worker 連不到 API server。可用 node-encryption-opt-out-labels ConfigMap 改
  • ClusterMesh 場景：所有 cluster 都要開 WireGuard（不支援 mixed），UDP 51871 要跨 cluster 允許

8.2 IPsec 啟用

bash
# 1. 產 PSK secret
kubectl create -n kube-system secret generic cilium-ipsec-keys \
  --from-literal=keys="3+ rfc4106(gcm(aes)) $(echo $(dd if=/dev/urandom count=20 bs=1 2> /dev/null | xxd -p -c 64)) 128"

# 2. Helm 開啟
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --reuse-values \
  --set encryption.enabled=true \
  --set encryption.type=ipsec

kubectl -n kube-system rollout restart ds/cilium

# 驗證
cilium status | grep Encryption
# 預期: Encryption: IPsec

1.19 IPsec 改進：BPF Host Routing 加速 IPsec，相同 throughput 下 CPU 用量降低（詳見第八部）。

8.3 1.19 Strict Mode 1.19

傳統 transparent encryption 有個微妙問題：endpoint 資訊在 cluster 內最終一致，不是即刻一致。新 pod 建立後，遠端 node 還沒拿到「這個 IP 屬於 cluster 內 endpoint」的資訊，會把該 IP 當外部處理，不加密就送出去。這個 race window 可能洩漏初始幾個封包的明文。

1.19 提供 Strict Mode，要求「到指定 CIDR 的所有流量必須加密，否則 drop」：

yaml
encryption:
  enabled: true
  type: wireguard
  nodeEncryption: true

  strictMode:
    enabled: true
    cidr: "10.244.0.0/16"           # 整個 Pod CIDR
    allowRemoteNodeIdentities: true  # 暫時允許 node IP 不加密

Strict Mode 限制（必讀）：

  • 必須是 IPv4（IPv6 不受保護）
  • 建議用 direct routing mode 並讓 node CIDR 與 Pod CIDR 不重疊
  • 若不能達成上面條件，allowRemoteNodeIdentities: true 暫時允許 node IP 明文（會留下小範圍 leak window）
  • 新 pod 建立後仍需 endpoint 資訊傳播完成，期間連線可能被 strict mode drop 直到 propagation 完成

8.4 Lab：驗證流量真的被加密

bash
# 在 worker 1 上跑
docker exec -it cilium-lab-worker bash

# 安裝 tcpdump
apt-get update && apt-get -y install tcpdump

# 監聽 WireGuard 介面（解密前）
tcpdump -n -i cilium_wg0 -c 5

# 監聽實體網卡（加密後）
tcpdump -n -i eth0 udp port 51871 -c 5
# 預期: 看到 UDP/51871，內容是 random bytes (加密過)
exit

# 同時在另一個 terminal 觸發跨 node 流量
kubectl exec pod-a -- curl -s pod-b-service

對比：cilium_wg0 介面看到的是明文 HTTP（這是 kernel 內 WireGuard module 已解密的視角），eth0 看到的是不可讀的 UDP/51871 payload。確認加密真的發生。

9. 限制特權 Cilium Pod 的存取

Cilium agent 必須跑在 privileged 模式（要存取 kernel BPF / netlink）。這代表如果 attacker 從 application pod 跳到 cilium-agent pod，等於拿到 node root。預設 cilium-agent 還有對 K8s API 的廣泛權限（要 list secrets、CRDs、watch pods…）。

強化建議：

  • RBAC 最小化：跑 cilium status --output yaml 後審視 cluster role，移除不需要的 verb
  • OPA / Kyverno 限制：禁止其他 service account 跨到 cilium-agent SA
  • PodSecurityStandard：把 cilium namespace 設為 privileged，其他 namespace 全 restricted，明確切割
  • Runtime detection：用 Tetragon / Falco 偵測 attacker 嘗試 access /var/run/cilium/cilium.sock
  • 避免 multi-tenant cluster：cilium-agent 拿到 root 等同 cluster root，多租戶風險高

11. 整體強化清單

把以上整理為一份「新 cluster 上線安全檢核表」：

基礎

  • ✅ policyEnforcementMode 從 default 開始，目標 always
  • ✅ 每個 namespace 都有 default-deny CNP（empty ingress/egress）
  • ✅ 每個 workload 有對應 allow list CNP
  • ✅ 所有 namespace 設定 PodSecurityStandard restricted，cilium namespace 例外

網路層

  • ✅ kube-proxy 完全替換（kubeProxyReplacement=true）
  • ✅ WireGuard 或 IPsec 啟用（生產合規幾乎必要）
  • ✅ 高安全要求環境啟用 1.19 Strict Mode
  • ✅ Cloud Metadata 全 cluster deny
  • ✅ 跨 cluster (ClusterMesh) policy 明確指定 cluster scope（1.19 預設只 local）

應用層

  • ✅ 所有對外 egress 用 FQDN allow list
  • ✅ TLS egress 至少加 SNI policy
  • ✅ Ingress / Gateway API Two-stage policy 完整（world→ingress, ingress→app）
  • ✅ 對外 Service / Ingress 都有 rate limit（CEC）

節點層

  • ✅ Bastion / DB nodes 啟用 Host Firewall
  • ✅ Cilium agent RBAC 最小化
  • ✅ EKS 全 node 強制 IMDSv2

可觀測 / 偵測

  • ✅ Hubble Relay + Metrics 啟用
  • ✅ Hubble flow log 持久化（export 到 SIEM）
  • ✅ Drop event 設 alert（policy denied 異常增加 → 攻擊或設定變動）
  • ✅ 考慮加 Tetragon 做 process / file / network runtime detection

變更管理

  • ✅ Policy 都進 Git，PR review 後才套用
  • ✅ Helm values 入版控
  • ✅ 升級走完整 pre-flight check（第三部 §3.4）
  • ✅ 1.19 升級前用 cilium clustermesh inspect-policy-default-local-cluster 預檢

12. 本章重點回顧

  • 實戰六場景：identity-aware HTTP、DNS 鎖定（含 Standalone DNS Proxy）、TLS visibility（SNI / 攔截）、Kafka/gRPC/Elasticsearch L4-L7、Cloud Metadata SSRF 防護、Host Firewall。
  • 沒人寫過 policy？用 Hubble JSON flow → 社群工具產 CNP 草稿，但務必人工 review。
  • Transparent Encryption：WireGuard（推薦，簡單、kernel native）vs IPsec（傳統 FIPS）。同 node pod-to-pod 不加密是設計。
  • 1.19 Strict Mode 補上「endpoint propagation 期間明文 leak window」這個歷史問題，但只 IPv4 + 建議 direct routing。
  • Cilium agent 是特權 pod，從應用 pod 跳到 agent = node root，RBAC / namespace 切割不能少。
  • 用 STRIDE 對應 Cilium 對策：identity policy（Spoofing）、encryption（Tampering）、FQDN allow list（Info Disclosure）、metadata deny（EoP）。
  • 11 章的強化清單當 cluster 上線安全 checklist 用。
