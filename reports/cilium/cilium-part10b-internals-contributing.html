關鍵設計

  • Hubble Server embedded in agent：與 cilium-agent 同 process，零 IPC 開銷接 datapath event
  • Userspace ring buffer：固定容量（power of 2，預設 4095 events），無鎖設計用 atomic ops，舊事件被新事件 override
  • 兩個 gRPC service：Observer（GetFlows 等查詢）/ Peer（Relay 用，回報這個 cluster 有哪些 Hubble instance）
  • Hubble Relay 是獨立 Deployment，連所有 cilium-agent 的 Hubble Server，提供「multi-node cluster-wide view」

為什麼 Relay 是必要的

  • Hubble Server 每個 node 一份，只看到自家 flow
  • UI / CLI 不想連 N 個 endpoint（複雜、TLS 一堆）
  • Relay 做聚合 fan-out：把 client query 同時送到所有 Hubble Server，收集結果
  • Peer 服務讓 Relay 知道 cluster 內現在有哪些 instance（pod 來去自動更新）

Source 入口

  • Server in agent：pkg/hubble/
  • Relay：hubble-relay/
  • Observer gRPC service：pkg/hubble/observer/
  • Ring buffer：pkg/hubble/container/
  • Peer service：pkg/hubble/peer/

Identity ID 區段配置

Range用途
1 ~ 16777215（cluster-pool）動態分配給 pod label set
0 ~ 255（reserved）系統保留 identity（world=2, cluster=8, host=1 等）
local scopenode-local 分配（沒被 cluster identify 出去的 entity）

Allocation 流程（CRD 模式，預設）

  1. 新 pod 起來，agent 觀察到 label set
  2. 過濾掉「不參與 identity 的 label」（namespace 一些自動加的 label）
  3. 查 local cache 有沒有對應 identity
  4. 沒有就建 CiliumIdentity CRD（K8s API 唯一性靠 conflict + retry 保證）
  5. 更新 ipcache 把 IP → identity ID 寫入
  6. 透過 K8s watch，所有 cluster node 都得知這個 mapping

5. Hive 框架

Cilium 從 1.13 起逐步把 codebase 改用 Hive 組織。Hive 是Cilium 團隊自寫的 Go dependency injection (DI) framework（基於 uber/dig），現在獨立成 github.com/cilium/hive。

5.1 為什麼要 DI

Cilium 早期是一大坨 main() 手動配線，問題：

  • 初始化順序錯亂
  • 全域變數到處都是，難測試
  • 新元件難加入（要找出在 main 哪行加 init）
  • shutdown 時 leak goroutine

Hive 的解法：每個元件描述為一個 Cell（包含建構函數與依賴），Hive 自動：

  • 解析依賴圖、決定建構順序
  • 調用每個 Cell 的 Start / Stop hook（lifecycle）
  • 暴露 CLI flag（每個 Cell 可以宣告自己的 flag）
  • 產出依賴圖（dot graph，視覺化）

5.2 Cell 範例

go
// pkg/foo/cell.go
package foo

import (
    "github.com/cilium/hive/cell"
    "github.com/cilium/hive/job"
)

// Cell 定義一個元件
var Cell = cell.Module(
    "foo-service",                 // 唯一 ID
    "Foo service that does X",     // 描述

    cell.Provide(newFooService),   // 構造函數
    cell.Config(defaultConfig),    // 配置（自動暴露 CLI flag）
    cell.Invoke(registerHandler),  // 啟動時呼叫
)

type Config struct {
    FooEnabled bool   `mapstructure:"foo-enabled"`
}

var defaultConfig = Config{ FooEnabled: true }

func (Config) Flags(flags *pflag.FlagSet) {
    flags.Bool("foo-enabled", true, "Enable foo service")
}

type FooService struct {
    log  *slog.Logger
    cfg  Config
    deps SomeDependency        // Hive 自動注入
}

// 由 Hive 自動呼叫，參數從依賴圖找
func newFooService(
    log *slog.Logger,
    lc cell.Lifecycle,         // 生命週期 hook
    cfg Config,
    deps SomeDependency,
) *FooService {
    s := &FooService{ log: log, cfg: cfg, deps: deps }
    lc.Append(cell.Hook{
        OnStart: s.start,
        OnStop:  s.stop,
    })
    return s
}

6. StateDB

StateDB 是 Cilium 為了管理 control-plane state 自寫的 in-memory database（也已獨立成 github.com/cilium/statedb）。它解決：

  • state 與 controller 分離：state 在 DB 內，controller 是 reconciler 訂閱 DB 變動
  • MVCC（Multi-Version Concurrency Control）：reader 不會 block writer
  • 有索引：複合條件查詢不用 linear scan
  • 可觀察：每張表都能訂閱變動，自然支援 reactive 設計
  • Persistent Adaptive Radix Tree：高效不可變樹結構

關鍵規矩

  • 每個 commit DCO sign-off：git commit -s，CLA 透過 DCO 替代
  • Commit message 格式：第一行 ≤ 75 字，subsystem: short summary；body 解釋為什麼、附 fixes # 編號
  • Label：PR 標題用前綴（fix(network):、feat(security):）讓 release note generator 抓得到
  • 不要混重構 + 功能：拆成多個 PR / 多個 commit
  • 每個改動有對應 test：unit / integration / E2E 至少一層
  • release-note 標籤：bug fix 標 release-note/bug，新功能標 release-note/major 或 minor

第一次貢獻怎麼起步

  1. 找 good-first-issue 或 help-wanted 標籤的 issue
  2. 留言「I'll work on this」避免撞單
  3. 動手前先進 Slack #development 問設計方向
  4. 送 draft PR 早點拿 feedback，別憋一個月才送

11. Release Management & Backport

11.1 Release cycle

Cilium minor release（1.X.0）大約每 4 個月一次。流程：

  1. Feature freeze：release 前 ~6 週，停收新 feature PR
  2. Release candidate：rc1、rc2... 公開測試
  3. Release：tag v1.X.0，發 blog、release note
  4. 後續 patch release（1.X.1, 1.X.2...）每 2–4 週
  5. 每個 minor 維護 ~1 年（依社群決定）

11.2 Backport 流程

bug fix 通常先 merge 到 main，再 backport 到 active minor。流程：

1

PR 標記要 backport

主 PR 上加 needs-backport/1.18 / needs-backport/1.19 標籤，maintainer 看到會列入 backport queue。

2

自動產 backport PR

Cilium 有 contrib/backporting/ 腳本（社群常用 create-backport-pr.sh）自動 cherry-pick 並建 PR：

bash
./contrib/backporting/start-backport.sh v1.19 12345
# 12345 = 原 PR 編號

# 解 conflict 後送 PR，標題: "Backport: 1.19: ..."
3

Backport PR 規矩

  • 原則上只接 bug fix 與 security fix
  • 新 feature 不 backport，避免引入回歸
  • conflict 一定要在 PR 中說明怎麼解
  • backport 的 commit 在原 commit 後加 [ upstream commit abcdef1 ]

11.3 Security release

發現 security vulnerability：

  1. 不要發 GitHub issue，先寄 security@cilium.io（embargo）
  2. Security committee 評估、產 CVE、寫 fix
  3. 所有 active minor 同時發 patch + advisory
  4. 公開 disclosure（通常 7–14 天後）

    "fmt"
    "log"

    flowpb "github.com/cilium/cilium/api/v1/flow"
    observerpb "github.com/cilium/cilium/api/v1/observer"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
)

func main() {
    conn, err := grpc.NewClient(
        "localhost:4245",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
    )
    if err != nil { log.Fatal(err) }
    defer conn.Close()

    client := observerpb.NewObserverClient(conn)
    stream, err := client.GetFlows(context.Background(), &observerpb.GetFlowsRequest{
        Number: 100,
        Follow: false,
        Whitelist: []*flowpb.FlowFilter{{
            Verdict: []flowpb.Verdict{flowpb.Verdict_DROPPED},
        }},
    })
    if err != nil { log.Fatal(err) }

    for {
        resp, err := stream.Recv()
        if err != nil { break }
        flow := resp.GetFlow()
        fmt.Printf("%s: %s -> %s [%s]\n",
            flow.Time.AsTime(),
            flow.Source.PodName, flow.Destination.PodName,
            flow.Verdict)
    }
}

12.4 Compatibility

API 遵守 semver-ish：

  • 同一 minor 內欄位只加不刪
  • 跨 minor 可能 deprecate（保留 release cycle 後移除）
  • major 變動（如 v2）會有獨立 proto 包

13. 本章重點回顧

  • Cilium repo 頂層三大關鍵：bpf/（C 寫的 datapath）、pkg/（Go 商業邏輯）、daemon/（agent main + Hive cells）。
  • Operator 跑 cluster-wide 任務（IPAM 切 CIDR、Identity GC、LB IPAM、BGP NodeConfig）。多 replica leader election。
  • Hubble Server embedded in agent（無 IPC 開銷）→ userspace ring buffer（無鎖）→ Observer/Peer gRPC → Relay 聚合多 node → UI / CLI / Metrics。
  • Identity 是 label hash → 16-bit numeric ID → 存 CiliumIdentity CRD（or kvstore）→ 透過 ipcache 傳到所有 node。
  • Hive 是 Cilium 自家 DI framework：每個元件 = Cell（Provide / Config / Invoke / Lifecycle）；自動解析依賴圖。Agent root cell tree 分 Infrastructure / ControlPlane / Datapath。
  • StateDB 是 in-memory MVCC DB，control-plane state 放這、reconciler 訂閱變動。基於 Persistent Adaptive Radix Tree。
  • Datapath 主要 BPF source：bpf_xdp.c / bpf_host.c（NIC）、bpf_lxc.c（veth）、bpf_sock.c（socket-LB）、bpf_overlay.c（tunnel）。
  • 開發環境：make kind 一鍵起 3-node 環境；LVH 在 QEMU 跑特定 kernel 版本的 BPF unit test。
  • 貢獻流程：DCO sign-off + subsystem: summary commit message + release-note label。第一次貢獻找 good-first-issue，Slack #development 問設計。
  • 測試四層：unit（Go testing）/ integration（Hive harness + scripttest）/ BPF unit（LVH）/ E2E（cilium connectivity test）。
  • Release ~4 個月一個 minor，每 minor 維護 ~1 年。Backport 用 needs-backport/X.Y label + start-backport.sh 腳本；只接 bug/security fix，不接 feature。
  • 三套 API：REST (agent) / gRPC (Flow/Observer/Peer/Relay/SDP) / cilium-cli 包裝。Go 程式直接呼叫 Hubble 用 observerpb.NewObserverClient。
