Service Mesh

Cilium 的 Service Mesh 不靠 sidecar，靠 per-node 的 Envoy。這代表你 cluster 內 1000 個 pod，只需要 N 個 Envoy（N = node 數），不是 1000 個 sidecar。這章從基礎概念到完整 lab，把 Ingress、Gateway API、L7 traffic management、mTLS、與 Istio 整合一次講完。

對應官方文件：Networking → Service Mesh 全章 Cilium 版本：1.19.x（Ztunnel Beta） 主要對象：所有讀者

1. 為什麼需要 Service Mesh

傳統 K8s 提供 Service VIP、DNS、Ingress 這些L4 為主的能力。當應用變成微服務後，光 L4 不夠用，你會想要：

  • L7 流量管理：canary、A/B testing、按 header 路由、fault injection、retry/timeout
  • 基於身份的安全：不靠 IP，靠 SPIFFE / certificate 互相驗證身份
  • 可觀測性：每個 HTTP/gRPC 呼叫的 latency、error code、tracing
  • 對應用透明：上面這些不需要改應用代碼

過去這些功能由 Istio、Linkerd 等 Service Mesh 提供，架構上靠 sidecar（每個 pod 旁邊塞一個 Envoy/proxy 容器）。這引入新的問題。

2. Cilium 的無 sidecar 架構

Sidecar Mesh（Istio 經典模式）

  • 每個 pod 注入 Envoy container
  • 每個 envoy 大約 50–100MB 記憶體
  • cluster 1000 pod = 1000 個 Envoy
  • 連線多兩跳：app → local sidecar → remote sidecar → app
  • 應用 startup 變慢（等 sidecar）
  • certificate 管理複雜

Cilium Service Mesh

  • 每個 node 一個 Envoy（DaemonSet cilium-envoy）
  • L4 工作完全在 BPF 內，不過 Envoy
  • L7 工作（HTTP、gRPC 解析）才 transparent redirect 到本地 Envoy
  • 沒有 sidecar，pod 不用 inject
  • 記憶體開銷 ~N 個 Envoy（N = node 數）

2.1 三條主要路徑

Cilium Service Mesh 的所有 L7 功能都共用 per-node Envoy，但 Envoy 接收流量的來源有三條：

路徑觸發用途
L7 NetworkPolicyCNP 內含 rules.http/dns/kafka第六部會詳述

L7 Traffic Management建立 CiliumEnvoyConfig本章 §5

3. Kubernetes Ingress

Cilium 內建 Ingress Controller，ingressClassName: cilium 就用它。背後是 per-node Envoy。

3.1 啟用

bash
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --reuse-values \
  --set ingressController.enabled=true \
  --set ingressController.loadbalancerMode=shared \
  --set ingressController.default=true \
  --set kubeProxyReplacement=true \
  --set l7Proxy=true

kubectl -n kube-system rollout restart deploy/cilium-operator
kubectl -n kube-system rollout restart ds/cilium

3.2 Shared vs Dedicated loadbalancer mode

Mode說明適用
shared 所有 Ingress 共用一個 LoadBalancer Service（名稱 cilium-ingress） 節省 LB IP，大多數情境
dedicated 每個 Ingress 各拿一個 LoadBalancer Service / IP 多租戶、不同 SLA、不同 IP segment 要求

Service 怎麼配 IP？看你選哪個曝光方案：

  • 雲端：用雲端內建 LB
  • 地端：搭配第四部 B 的 LB IPAM + BGP 或 L2 Announcements

3.3 Lab：建一個 Ingress

bash
# 1. 部署 demo bookinfo（從 Istio sample）
kubectl apply -f https://raw.githubusercontent.com/cilium/cilium/1.19.3/examples/kubernetes/servicemesh/bookinfo.yaml

# 2. 建 Ingress
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: bookinfo
spec:
  ingressClassName: cilium
  rules:
    - http:
        paths:
          - path: /details
            pathType: Prefix
            backend:
              service:
                name: details
                port:
                  number: 9080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: productpage
                port:
                  number: 9080
EOF

# 3. 看 Ingress 與 underlying LoadBalancer Service
kubectl get ingress bookinfo
kubectl -n kube-system get svc cilium-ingress

# 4. 用 EXTERNAL-IP 測（地端要先準備 LB IPAM）
INGRESS_IP=$(kubectl -n kube-system get svc cilium-ingress -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
curl -s http://$INGRESS_IP/details/0
# 預期: 看到 JSON details
curl -s http://$INGRESS_IP/ | grep title
# 預期: 看到 productpage HTML

3.5 重要：Source IP 與 Policy enforcement

💡 不用設 externalTrafficPolicy: Local

官方文件明確說：Cilium Ingress 與 Gateway API 都會自動透過 TPROXY 把原始 source IP 保留下來，並寫入 X-Forwarded-For / X-Envoy-External-Address header。不需要為了保留 client IP 而設 externalTrafficPolicy: Local。

進入 Envoy 的流量會被指派特殊 identity ingress。從外部進來的流量原本是 world identity，過 Envoy 後變 ingress，再到 backend pod。這代表撰寫 policy 時要考慮兩段：

sequenceDiagram participant Client as 外部 Client participant Envoy as cilium-envoy
(per-node) participant Pod as Backend Pod Client->>Envoy: 1. world → ingress 需 policy 允許 Note over Envoy: 處理 L7（HTTP routing、TLS、retry） Envoy->>Pod: 2. ingress → app 需 policy 允許 Pod-->>Envoy: response Envoy-->>Client: response (X-Forwarded-For 加進去)

4. Gateway API Stable

4.1 為什麼換掉 Ingress

K8s Ingress API 從 2017 就停在 Beta，後來 GA 後也沒擴充能力。真實需求（path-based routing、header match、流量分流、TLS passthrough、gRPC）只能靠 annotation 補。每個 Ingress controller 寫的 annotation 還不一樣，遷移無望。

Gateway API 是 SIG-Network 提的新標準：

  • Role-Oriented：分 GatewayClass（雲端商提供）/ Gateway（平台維運）/ HTTPRoute（應用 owner），權責清楚
  • Expressive：原生支援 header/method/queryParam match、流量加權、HTTP rewrite
  • Extensible：協定不限於 HTTP，TLS / gRPC / TCP / UDP routes 都有
  • Portable：不同 implementation（Cilium、Envoy Gateway、Kong、NGINX Gateway Fabric）共用同樣 API

4.2 啟用

bash
# Step 1: 先裝 Gateway API CRD（Cilium 不會自動裝）
GATEWAY_API_VERSION=v1.2.0
kubectl apply -f \
  https://github.com/kubernetes-sigs/gateway-api/releases/download/${GATEWAY_API_VERSION}/standard-install.yaml

# Step 2: 啟用 Cilium Gateway API
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --reuse-values \
  --set gatewayAPI.enabled=true \
  --set kubeProxyReplacement=true \
  --set l7Proxy=true

kubectl -n kube-system rollout restart deploy/cilium-operator
kubectl -n kube-system rollout restart ds/cilium

# 確認 GatewayClass 'cilium' 已建立
kubectl get gatewayclass cilium
# 預期: ACCEPTED=True

4.3 HTTPRoute / TLSRoute / GRPCRoute

建一個 Gateway + HTTPRoute：

yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
  namespace: default
spec:
  gatewayClassName: cilium
  listeners:
    - name: http
      protocol: HTTP
      port: 80
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - kind: Secret
            name: bookinfo-cert
yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: bookinfo-route
spec:
  parentRefs:
    - name: my-gateway          # 綁到上面的 Gateway
  hostnames:
    - "bookinfo.example.com"
  rules:
    # path 開頭是 /details
    - matches:
        - path: { type: PathPrefix, value: "/details" }
      backendRefs:
        - name: details
          port: 9080

    # 含特定 header 才走 v2
    - matches:
        - headers:
            - name: "x-version"
              value: "v2"
      backendRefs:
        - name: reviews-v2
          port: 9080

    # default
    - backendRefs:
        - name: productpage
          port: 9080

4.4 Lab：流量分流（80 / 20 canary）

Gateway API 內建 backend weight，不需要任何 annotation就能做 canary：

yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: canary-route
spec:
  parentRefs:
    - name: my-gateway
  rules:
    - matches:
        - path: { type: PathPrefix, value: "/" }
      backendRefs:
        - name: my-app-stable
          port: 80
          weight: 80          # 80% 走 stable
        - name: my-app-canary
          port: 80
          weight: 20          # 20% 走 canary
bash
# 驗證
GW_IP=$(kubectl get gateway my-gateway -o jsonpath='{.status.addresses[0].value}')

for i in $(seq 1 50); do
  curl -s http://$GW_IP/ | grep "version"
done | sort | uniq -c
# 預期: 大約 40 stable / 10 canary（80/20 比例）

4.5 TLSRoute（SNI 路由不解密）

有些後端要自己處理 TLS（如某些 gRPC 庫）。Gateway 可以根據 SNI 做 L4 級轉發，不解密：

yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: tls-gateway
spec:
  gatewayClassName: cilium
  listeners:
    - name: tls
      protocol: TLS
      port: 443
      tls:
        mode: Passthrough          # 不解密
      hostname: "*.example.com"
---
apiVersion: gateway.networking.k8s.io/v1alpha2
kind: TLSRoute
metadata:
  name: passthrough
spec:
  parentRefs:
    - name: tls-gateway
  hostnames:
    - "secure.example.com"
  rules:
    - backendRefs:
        - name: my-tls-backend
          port: 443

5. L7 Traffic Management（東西向）

§3 §4 處理的是南北向（外部進 cluster）。如果你要對東西向（cluster 內 service 互呼）做 L7 處理（rate limit、retry、circuit breaking），用 CiliumEnvoyConfig。

⚠ CEC 是「進階逃生口」

CiliumEnvoyConfig 讓你直接寫 Envoy 原生 config，幾乎沒有抽象。優點是能用上所有 Envoy 功能；缺點是你的 Envoy 知識決定一切，schema 變動沒有 K8s 通常的優雅升級。建議優先用 Gateway API，CEC 是 escape hatch。

5.1 啟用 envoyConfig

bash
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --reuse-values \
  --set envoyConfig.enabled=true \
  --set loadBalancer.l7.backend=envoy

5.2 Lab：對某 Service 做 rate limit

yaml
apiVersion: cilium.io/v2
kind: CiliumEnvoyConfig
metadata:
  name: rate-limit-config
  annotations:
    cec.cilium.io/use-original-source-address: "false"   # 東西向必加
spec:
  services:
    - name: my-app
      namespace: default
  resources:
    - "@type": type.googleapis.com/envoy.config.listener.v3.Listener
      name: my-app-listener
      filter_chains:
        - filters:
            - name: envoy.filters.network.http_connection_manager
              typed_config:
                "@type": type.googleapis.com/envoy.extensions.filters.network.http_connection_manager.v3.HttpConnectionManager
                stat_prefix: my-app
                http_filters:
                  # local rate limit filter
                  - name: envoy.filters.http.local_ratelimit
                    typed_config:
                      "@type": type.googleapis.com/envoy.extensions.filters.http.local_ratelimit.v3.LocalRateLimit
                      stat_prefix: my-app-rl
                      token_bucket:
                        max_tokens: 100
                        tokens_per_fill: 100
                        fill_interval: 1s   # 每秒 100 req
                      filter_enabled:
                        runtime_key: local_rate_limit_enabled
                        default_value: { numerator: 100, denominator: HUNDRED }
                      filter_enforced:
                        runtime_key: local_rate_limit_enforced
                        default_value: { numerator: 100, denominator: HUNDRED }
                  - name: envoy.filters.http.router
                route_config:
                  name: local_route
                  virtual_hosts:
                    - name: my-app
                      domains: ["*"]
                      routes:
                        - match: { prefix: "/" }
                          route: { cluster: my-app }

除了 rate limit，CEC 可用來實作 retry、circuit breaking、外部 authz、custom filter（lua / wasm）等。

6. mTLS（Mutual TLS）

Cilium 對 service-to-service mTLS 有兩種策略：

6.1 Transparent Encryption（節點間加密，不是 mTLS）

第六部會深入講。簡單說：WireGuard / IPsec 在 node 對 node 之間加密所有流量，對應用透明。優點是零應用改動；缺點是不是 service 身份級的 mTLS，只是 node 之間。

6.2 Cilium Service-to-Service Auth（基於 SPIFFE）早期

Cilium 提出 mTLS 基於 SPIFFE / SPIRE 的方案，但目前 GA 度與 Istio Ambient 還有距離。多數團隊在「需要 service identity mTLS」時，傾向：

  • 用 Cilium 做 CNI + L4 與 L7 policy
  • 把 mTLS / service identity 交給 Istio（ambient 模式）
  • 兩者用 CNI chaining 整合（§7）

1.19 把 Ztunnel 整合升 Beta，正是這條整合路線（見 §7.2）。

7. 與 Istio 整合

7.1 與 Istio sidecar 模式並用

Cilium 1.13 後完整支援 Istio sidecar 並存。注意事項：

  • 用 Cilium overlay 模式（VXLAN / Geneve）時，istiod 必須 hostNetwork: true 才能被 API server reach 到
  • Istio-managed pod 之間是 mTLS 加密的，Cilium 看不到 L7 內容（也就是看不到 HTTP path）
  • Cilium L4 policy 仍然有效（基於 pod identity），但 L7 policy 對 Istio mTLS 流量會失效
  • 建議分工：Istio 管 Istio 流量的 policy；Cilium 管「進出 Istio mesh 邊界」的 policy

7.2 Ztunnel 整合（1.19 Beta）Beta

Istio Ambient Mode 用 ztunnel（per-node DaemonSet）取代 sidecar。1.19 起 Cilium 可整合 ztunnel 做 L4 mTLS，同時保留 Cilium 的 CNI、policy、observability 能力。

啟用步驟概覽（細節依 Istio 版本變動，請以官方文件為準）：

bash
# 1. 裝 Cilium 開啟 Ztunnel 模式
helm install cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --set ipv4NativeRoutingCIDR=10.0.0.0/8 \
  --set kubeProxyReplacement=true \
  --set bpf.masquerade=true \
  --set ztunnel.enabled=true                # 1.19 Beta key

# 2. 裝 Istio ambient（用 istioctl）
istioctl install --set profile=ambient -y

# 3. 把要加入 mesh 的 namespace label
kubectl label namespace my-app istio.io/dataplane-mode=ambient

得到什麼

  • L4 mTLS 由 ztunnel 處理（pod 對 pod 加密、service identity）
  • L7 流量管理 仍可用 Istio waypoint proxy
  • L3/L4/L7 policy 與 observability 仍由 Cilium 處理
  • 沒有 sidecar，記憶體開銷 = N 個 cilium-envoy + N 個 ztunnel
⚠ Beta 狀態實務坑

社群回報過 ztunnel 憑證過期、VM 暫停/恢復後 mTLS 失效等問題。生產採用前務必做完整 chaos / power failure 驗證。對大多數 cluster，2026 仍建議先用「Cilium L7 policy + WireGuard 節點加密」滿足合規，再評估是否需要完整 service identity mTLS。

8. Policy 編排重要注意

啟用 Ingress / Gateway API 後撰寫 Network Policy 一定要記得：進來的流量會經過兩個 identity 階段

yaml
# 對 backend 開放：必須允許 ingress identity 進來
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-from-ingress
spec:
  endpointSelector:
    matchLabels:
      app: productpage
  ingress:
    - fromEntities:
        - "ingress"               # 關鍵：Envoy 出來的流量 identity
      toPorts:
        - ports:
            - port: "9080"

# 對 Envoy 本身開放：必須允許 world 進來
---
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: allow-world-to-ingress
spec:
  endpointSelector:
    matchLabels:
      reserved.ingress: ""        # ingress identity 對應的 endpoint
  ingress:
    - fromEntities:
        - "world"
      toPorts:
        - ports:
            - port: "80"
            - port: "443"

少寫一段，外部就連不進來；或者 Envoy 能進但連不到 backend。第六部會講 policy 完整章節。

9. Service Mesh 故障排除

症狀常見原因排查指令
Ingress IP 一直 <pending> 沒設 LB IPAM（地端）或雲端 LB 未配 kubectl -n kube-system get svc cilium-ingress；看 LB IPAM pool
GatewayClass 顯示 NotAccepted Gateway API CRD 沒裝 kubectl get crd gateways.gateway.networking.k8s.io
HTTPRoute 訪問 404 hostname / path 寫錯、Gateway 沒 attach kubectl describe httproute <name> 看 status.parents
外部 403 但 backend 沒收到 缺 world → ingress 的 policy 用 hubble 看 verdict
backend 收到請求但回 connection refused 缺 ingress → backend 的 policy hubble observe --pod backend --verdict DROPPED
L7 traffic management 沒生效 沒開 envoyConfig.enabled / CEC 寫錯 kubectl logs ds/cilium-envoy 看 Envoy 配置 reload 是否成功
cilium-envoy DaemonSet 不存在 1.14- 是 embedded 模式；1.15+ 預設 external 確認版本與 envoy.enabled value

10. 本章重點回顧

  • Cilium Service Mesh 無 sidecar：用 per-node 的 cilium-envoy DaemonSet，N node = N 個 Envoy，不是 N 個 pod = N 個 sidecar。
  • 進入 Envoy 的三條路徑：L7 NetworkPolicy / Ingress(Gateway API) / CiliumEnvoyConfig。
  • Kubernetes Ingress：ingressClassName: cilium，shared / dedicated 兩種 loadbalancer mode。Source IP 自動透過 TPROXY 保留，不需要 externalTrafficPolicy=Local。
  • Gateway API：Stable，推薦新專案直接用。GatewayClass cilium + Gateway + HTTPRoute/TLSRoute/GRPCRoute。canary、header-based routing 全部原生支援，無 annotation。
  • CiliumEnvoyConfig：對東西向流量做 L7 控制（rate limit、retry、circuit breaking）。寫的是 Envoy 原生 config，是「進階逃生口」。記得加 cec.cilium.io/use-original-source-address: "false"。
  • mTLS：Cilium 自家 SPIFFE-based mTLS 還在早期；想要完整 service identity mTLS，主流做法是 Cilium + Istio Ambient（Ztunnel 整合 1.19 Beta）。
  • Policy 兩段式：外部 → Envoy 是 world → ingress；Envoy → backend 是 ingress → app。少寫一段就斷。
  • 故障排除靠 cilium-dbg envoy admin、Hubble 看 verdict、kubectl describe 看 Gateway/HTTPRoute 的 status。
