1. 什麼是 Cilium

Cilium 是一套 用 eBPF 實作的 Kubernetes 網路、安全與可觀測性平台。在最常見的部署形態下，它扮演三個角色：

  1. CNI (Container Network Interface) Plugin：負責給 Pod 配 IP、處理跨 Node 封包傳輸、做 Service 負載平衡（取代 kube-proxy）。
  2. Network Policy Enforcement：實作 K8s NetworkPolicy 與自家擴充的 CiliumNetworkPolicy / CiliumClusterwideNetworkPolicy，支援 L3、L4 與 L7（HTTP、gRPC、Kafka、DNS）規則。
  3. Observability Backend：搭配 Hubble 提供 service map、flow log、Prometheus metrics、L7 protocol decode。

更廣義來看，Cilium 還能做 ClusterMesh（跨叢集網路）、Egress Gateway（出向流量集中與 SNAT）、BGP control plane、Service Mesh（Ingress、Gateway API、L7 traffic management）、Transparent Encryption（IPsec/WireGuard），近期甚至加入 Ztunnel 整合（Beta）與 IPv6-only 場景優化。

1.1 它解決什麼問題？

傳統 Kubernetes 網路堆疊存在三個結構性痛點：

痛點傳統作法Cilium 的解法
kube-proxy 用 iptables/IPVS，Service 數量一多就慢 iptables 線性比對，O(n) eBPF map 直接 lookup，O(1)，可完全取代 kube-proxy
NetworkPolicy 只到 L4，無法理解 HTTP 動詞或 DNS 名稱 用 sidecar proxy 補（Istio/Linkerd） 原生支援 L7 policy，不需要 sidecar
傳統 tcpdump / iptables log 看不出「哪個 Service 拒絕了誰」 仰賴第三方 APM Hubble 直接從 eBPF datapath 抓 flow，附 K8s identity（namespace / pod / label）

1.2 為什麼是 eBPF？

eBPF（extended Berkeley Packet Filter）讓使用者可以把受沙箱檢查的程式掛到 Linux Kernel 的各種 hook 上（封包進出網卡、syscall、tracepoint…），不需要改 kernel 原始碼、不需要 kernel module。對網路堆疊而言，這代表：

  • 性能：直接在 TC ingress/egress 或 XDP 處理封包，跳過大半個 Linux netfilter stack。
  • 觀測力：可以在 datapath 中即時 emit metric / event，不用 mirror 流量。
  • 動態更新：政策變更只需重新編譯並 reload BPF program，不影響其他流量。

後續第十部會深入 BPF program 與 map，這一章先建立直覺即可。

2. 什麼是 Hubble

Hubble 是 Cilium 的可觀測性元件。Cilium 在 datapath 處理封包時，可以把每一個 flow（連線）的資訊送到 Hubble；Hubble 再對外提供 CLI、Web UI、gRPC API、Prometheus metrics 四種介面，讓你可以用 K8s identity（namespace / pod label / service name）的視角，看「誰在連誰、走什麼協定、是否被 policy 拒絕」。

Hubble 與其他 APM/Tracing 工具最大的差別：

  • 無需 application 改碼，也不用裝 sidecar，所有資料來自 eBPF datapath。
  • 看得到 L3 / L4 / L7 三層資料，包含 HTTP method、status code、gRPC service、DNS query name。
  • 看得到 policy verdict（被誰、根據哪條 rule、allow 還是 deny），這對排錯 NetworkPolicy 是無可取代的。

2.1 三個 Hubble 子元件

Hubble (in agent)

內嵌在 cilium-agent 內，從 eBPF datapath 收 flow，是資料來源。每個 node 一份。

Hubble Relay

叢集中央元件，把所有 node 上的 Hubble 彙整成一個 cluster-wide gRPC API。

Hubble UI

Web 介面，提供 service map 與互動式 flow 查詢，背後連 Hubble Relay。

3.1 Cilium Agent

cilium-agent 是 Cilium 的核心，以 DaemonSet 形式在每個 node 上跑一個。職責：

  • 從 K8s API 監聽 Pod、Service、NetworkPolicy、Endpoint 等資源變化
  • 把這些資源編譯成 BPF program 與 BPF map，並 attach 到 host 與 Pod 的網路介面
  • 實作 cilium CLI 的 daemon side（cilium endpoint list、cilium policy get 等）
  • 暴露 Prometheus metrics 與 Hubble gRPC API

它是有狀態的：每個 agent 都維護自己 node 上所有 endpoint 的 BPF state，掛了會造成新 Pod 拿不到網路（但已存在的連線通常不受影響，因為 BPF program 還在 kernel）。

3.2 Cilium Operator

cilium-operator 是無狀態的 Deployment，負責那些「整個叢集只該做一次」的事情：

  • IPAM：管理 Cilium 自帶的 PodCIDR 配置（cluster-pool / multi-pool 模式）
  • 同步 K8s heartbeat 給 Cilium agent
  • 清理孤兒 CiliumEndpoint、CiliumIdentity
  • 跨雲端整合：AWS ENI mode、Azure IPAM、GKE 整合

Operator 短暫掛掉不會中斷流量，但長時間掛掉會導致新 Pod 拿不到 IP（IPAM 模式為 cluster-pool 時）。

3.3 CNI Plugin

當 kubelet 要建立 Pod 時，會呼叫 CNI binary（/opt/cni/bin/cilium-cni）。這個 binary 只是個薄薄的 RPC client，它會 unix socket 連到本機 cilium-agent，請 agent 幫忙做 IP 配置與 BPF 設定。所以 agent 掛了，新 Pod 就建不起來。

3.4 Hubble 三件式

已在第 2 節介紹，這裡再強調部署形態：Hubble in agent 隨 cilium-agent DaemonSet 開啟即可；Hubble Relay 是 Deployment，需要 TLS 與 service account；Hubble UI 是另一個 Deployment，背後連 Relay。預設安裝下三者通常一次性開啟（cilium install --set hubble.relay.enabled=true --set hubble.ui.enabled=true）。

3.5 eBPF Datapath

嚴格說，eBPF program 與 map 不是「元件」，而是 cilium-agent 動態載入到 Linux Kernel 的實際 datapath。當 Pod 建立時，agent 會：

  1. 在 host namespace 與 Pod namespace 各建立一個 veth pair
  2. 把編譯好的 BPF program attach 到 veth 上（TC ingress / egress hook）
  3. 把 Pod 對應的 identity、policy、route 寫進 BPF map
  4. 封包進來時，BPF program 在 kernel 內直接決定 forward / drop / redirect

3.6 Data Store

Cilium 需要儲存「跨 node 共享的狀態」（identity、endpoint 列表等）。它支援兩種儲存：

  • K8s API as kvstore（預設）：用 CRD（CiliumIdentity、CiliumEndpoint…）直接存在 K8s etcd，零外部依賴。
  • External etcd：另開一組 etcd 給 Cilium 用，適合超大規模叢集，避免衝擊 K8s API server。

選哪一種會在第三部詳述。一般情況預設的 K8s API 模式就夠用，超過 1000 node 才需要考慮外部 etcd。

4. 核心術語

Cilium 文件大量使用以下術語，搞混就讀不下去。請務必先弄清楚。

4.1 Labels

Labels 是標識一個資源的 key=value pair，跟 K8s label 概念一致，但 Cilium 會把多個來源的 label 合在一起當作身份依據。常見來源：

  • k8s: 前綴：來自 Pod metadata（如 k8s:app=frontend）
  • k8s:io.kubernetes.pod.namespace：namespace 自動轉成 label
  • reserved: 前綴：Cilium 保留標記（reserved:host、reserved:remote-node、reserved:world）
  • container: 前綴：來自 container runtime（少用）

4.2 Endpoint

Endpoint 是 Cilium 的網路抽象單位。對 K8s Pod 來說，一個 Pod = 一個 Endpoint（Pod 內所有 container 共用一個網路 namespace，所以共用一個 endpoint）。Endpoint 由 cilium-agent 管理，可以用 cilium endpoint list 查看：

bash
# 在 cilium-agent Pod 內執行
cilium endpoint list

                                            k8s:io.kubernetes.pod...
5678       Enabled    Disabled   58         k8s:app=backend              10.0.1.6     ready

4.3 Identity

這是 Cilium 整個架構的核心發明。傳統防火牆規則寫的是 IP；但 K8s Pod 的 IP 是動態的，今天的 10.0.1.5 可能跟明天的不是同一個 Pod。Cilium 不用 IP 當識別，改用 identity。

identity 的本質是「一組 label 的雜湊」。所有 label 完全相同的 Pod，會被分配到同一個 identity ID（numeric）。Network Policy 在 BPF map 內存的是 identity ID，不是 IP，所以 Pod 重啟換 IP 完全不影響 policy。

💡 直覺

把 identity 想成「身份證」，label 是「個人特徵」。同樣特徵的人（app=frontend, env=prod, version=v1）就是同一個身份；換了名字（IP）不重要。

4.4 Node

Node 在 Cilium 文件中指的就是 K8s Node。Cilium 會把每個 node 的資訊（內部 IP、外部 IP、PodCIDR、health endpoint）同步到所有其他 node，這個機制叫 Node Discovery。Node 也有自己的 identity（reserved:host 或 reserved:remote-node），可以被 NetworkPolicy 引用。

4.5 Security Identity

Cilium 內部有幾個保留 identity，務必認得：

Reserved Identity意義
reserved:host本機 host（node 上不在任何 Pod 內的程式）
reserved:remote-node叢集中其他 node 的 host
reserved:world叢集外部一切（網際網路）
reserved:cluster叢集內所有 Pod 與 node
reserved:kube-apiserverK8s API server（自動偵測）
reserved:unmanagedCilium 沒接管的 Pod（hostNetwork 等）
reserved:healthCilium 自己用來測 node 間連通性的 health endpoint

5. eBPF 基礎觀念導讀

讀到這裡你應該已經感覺到 eBPF 無所不在。本節不深入 BPF 程式碼（第十部會寫一份完整的 BPF Reference），只建立四個必懂的直覺。

5.1 BPF Program 與 BPF Map

BPF 世界的兩個主角：

  • BPF Program：一小段 sandboxed code，由 verifier 檢查過後 attach 到 kernel hook。常見 hook：TC (Traffic Control) ingress/egress、XDP (eXpress Data Path)、socket、tracepoint、kprobe。
  • BPF Map：kernel 與 user space 都能讀寫的共享資料結構，常見類型有 hash map、array、LRU、LPM trie。Cilium 大量用 map 存 identity → policy verdict、Service backend list、connection tracking 等。

5.2 為什麼 verifier 很重要

每段 BPF program 在被 load 前，kernel 內的 verifier 會做靜態分析，確保：

  • 不會無窮迴圈（有指令數上限）
  • 不會存取未初始化記憶體
  • 不會越界存取 map 或封包

這代表 BPF program 是受信任的擴充點，不會 panic kernel；同時也代表寫起來限制很多，Cilium 用 LLVM C 寫 BPF 並大量倚賴巨集展開來達到 verifier 友善。

Cilium 預設 主力用 TC（功能完整）、選用 XDP（極高吞吐場景，例如 LoadBalancer 前置 LB）。XDP 在封包進 kernel network stack 前就攔截，速度極快，但能存取的資訊較少。

5.4 BPF 取代了什麼？

Cilium 啟用後，iptables 規則會大幅減少（kube-proxy free 模式下幾乎為零）。實際上 Cilium 並不會把 iptables 完全刪掉，因為 K8s 還有其他元件會寫（如 kubelet、第三方 CNI plugin），但Service / NetworkPolicy 的判斷都改在 BPF 內完成。在第八部會有 iptables-save 對照範例。

6. Lab：第一次觀察 eBPF

本章 lab 目的：在不安裝 Cilium的情況下，先確認你的環境有 eBPF 工具鏈，並感受一下 BPF program 是什麼。完整 Cilium lab 留到第二部。

6.1 環境需求

  • Linux Kernel ≥ 5.10（建議 5.15+ 以獲得 1.19 進階功能）
  • 已安裝 Docker 與 kind
  • 已安裝 kubectl
  • 建議安裝 bpftool（多數發行版在 linux-tools-* 套件內）

7. 本章重點回顧

  • Cilium 是用 eBPF 實作的 K8s 網路 + 安全 + 可觀測性平台，扮演 CNI、Policy enforcement、Hubble backend 三角色。
  • 核心元件：cilium-agent（每 node 一個 DaemonSet，有狀態）、cilium-operator（無狀態 Deployment）、CNI plugin binary、Hubble 三件式（agent 內嵌 + Relay + UI）。
  • Identity 取代 IP是 Cilium 最重要的設計：所有 label 相同的 Pod 共享同一個 numeric identity，policy 寫的是 identity。
  • 記住 reserved:* 系列 identity，policy 經常會用到。
  • eBPF 兩主角：BPF program（受 verifier 檢查的 kernel 內程式）+ BPF map（kernel/userspace 共享資料）。Cilium 主用 TC hook，極高吞吐場景才用 XDP。
  • 1.19 重要新功能：IPsec/WireGuard strict mode、Multi-Pool IPAM stable、IPv6 underlay、多層級 DNS wildcard、ICMPv4 deny response、ClusterMesh 預設 local-only。
