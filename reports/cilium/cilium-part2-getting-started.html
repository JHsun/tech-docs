快速上手

把 Cilium 真的裝到 K8s 叢集上、跑完 Star Wars demo、感受 L3/L4/L7 policy 的差異，再用 Hubble 看實際 flow。這是「成為 Cilium 使用者」的最短路徑，預計 60 分鐘可以走完。

對應官方文件：Getting Started（k8s-install-default、demo、terminology、gettinghelp） Cilium 版本：1.19.x 實作環境：kind（3-node cluster）

2. 安裝 Cilium CLI

Cilium CLI（cilium 指令）是本機工具，不是 cluster 內元件。它的角色：

  • 把 Cilium 安裝到 cluster（背後其實是套 Helm chart）
  • 查狀態（cilium status）
  • 跑 connectivity test（cilium connectivity test）
  • 啟停功能（Hubble、ClusterMesh）
  • 收集 sysdump 給故障回報
💡 CLI 版本 vs Cilium 版本

Cilium CLI 是獨立版號（如 v0.19.x），跟 Cilium 本體版號（1.19.x）不同。CLI 通常向下相容近幾個 Cilium 版本，建議保持最新。

2.1 安裝 Linux / macOS / WSL

bash
# Linux (amd64 / arm64 都支援)
CILIUM_CLI_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/cilium-cli/main/stable.txt)
CLI_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then CLI_ARCH=arm64; fi
curl -L --fail --remote-name-all \
  "https://github.com/cilium/cilium-cli/releases/download/${CILIUM_CLI_VERSION}/cilium-linux-${CLI_ARCH}.tar.gz"{,.sha256sum}
sha256sum --check cilium-linux-${CLI_ARCH}.tar.gz.sha256sum
sudo tar xzvfC cilium-linux-${CLI_ARCH}.tar.gz /usr/local/bin
rm cilium-linux-${CLI_ARCH}.tar.gz{,.sha256sum}

# macOS（Homebrew 最快）
brew install cilium-cli

# 驗證
cilium version --client

預期輸出類似：

output

cilium image (default): v1.19.3
cilium image (stable): v1.19.3

3.2 用 cilium install 一鍵部署

因為 kind 環境是 Docker 跑的，cilium-agent 容器內讀不到 host kernel module 路徑，要傳 --set 處理。另外因為叢集沒裝 kube-proxy，要叫 Cilium 開 kubeProxyReplacement：

bash
cilium install \
  --version 1.19.3 \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=cilium-lab-control-plane \
  --set k8sServicePort=6443 \
  --set image.pullPolicy=IfNotPresent \
  --set ipam.mode=kubernetes

4.2 connectivity test

Cilium 內建一組 90+ 個測試案例，會建測試 namespace 跑 pod-to-pod、pod-to-service、egress、L7 等驗證。

bash
cilium connectivity test

整個測試大約跑 5–10 分鐘，結束預期看到：

output
📋 Test Report
✅ 95/95 tests successful (0 warnings)
⚠ 部分測試 skip 是正常的

在 kind 或單機環境，跨 node 的 NodePort、外部 LoadBalancer、IPv6 等測試可能被自動 skip，這是預期行為。只要沒有 failed，安裝就 OK。

4.3 觀察 BPF 變化（vs 第一部）

第一部我們進 kind node 看 BPF 程式，當時很乾淨。現在 Cilium 裝完，再看一次：

bash
docker exec -it cilium-lab-control-plane bash

# 在 node 內列出 BPF program
bpftool prog list | wc -l
# 預期: 數十個（vs 第一部的個位數）

# 看 BPF map
bpftool map list | head -20
# 預期看到 cilium_lxc, cilium_policy_*, cilium_ipcache, cilium_lb4_services_v2 ...

# 看 cilium_lb4_services_v2 (Cilium 自己的 Service map，取代 kube-proxy)
bpftool map dump name cilium_lb4_serv

exit

看到 cilium_lb4_services_v2、cilium_lxc（endpoint）、cilium_ipcache（IP → identity 對照表）這幾個 map，就是 Cilium 在 kernel 內運作的證據。

Death Star 提供以下 API：

  • GET /v1/ — 取得規格
  • POST /v1/request-landing — 請求降落（合法操作）
  • PUT /v1/exhaust-port — 對排氣口下指令（會讓 Death Star 爆炸的危險 API）

我們會逐步套用三個層次的政策，看到傳統 firewall 做不到的事：

  1. 無 policy：所有人都能呼叫所有 API（基準）
  2. L3/L4 policy：只允許 org=empire 連 deathstar 80 port → xwing 被擋
  3. L7 policy：在 L3/L4 之上限制 tiefighter 只能 POST /v1/request-landing → 排氣口被擋

5.3 無 policy 基準

bash
# tiefighter 請求降落（合法）
kubectl exec tiefighter -- curl -s -XPOST deathstar.default.svc.cluster.local/v1/request-landing
# 預期: Ship landed

# xwing 也能請求降落（這是問題！）
kubectl exec xwing -- curl -s -XPOST deathstar.default.svc.cluster.local/v1/request-landing
# 預期: Ship landed

# tiefighter 炸排氣口（這是大問題！）
kubectl exec tiefighter -- curl -s -XPUT deathstar.default.svc.cluster.local/v1/exhaust-port
# 預期: Panic: deathstar exploded ...

這就是「沒有 policy」的真實 K8s — 任何 pod 都能呼叫任何 pod 的任何 API。

5.4 套用 L3/L4 policy：擋掉 xwing

這條政策只允許 org=empire 的 pod 連 deathstar 的 TCP/80：

yaml
# sw_l3_l4_policy.yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: "rule1"
spec:
  description: "L3-L4 policy to restrict deathstar access to empire ships only"
  endpointSelector:
    matchLabels:
      org: empire
      class: deathstar
  ingress:
    - fromEndpoints:
        - matchLabels:
            org: empire
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
bash
kubectl apply -f https://raw.githubusercontent.com/cilium/cilium/1.19.3/examples/minikube/sw_l3_l4_policy.yaml

# 再測一次
kubectl exec tiefighter -- curl -s -XPOST \
  deathstar.default.svc.cluster.local/v1/request-landing
# 預期: Ship landed

# xwing 現在被擋
kubectl exec xwing -- curl -s --max-time 5 -XPOST \
  deathstar.default.svc.cluster.local/v1/request-landing
# 預期: 無回應，5 秒後 timeout (exit code 28)

# 但 tiefighter 還是能炸排氣口（L4 看不到 path）
kubectl exec tiefighter -- curl -s -XPUT \
  deathstar.default.svc.cluster.local/v1/exhaust-port
# 預期: Panic: deathstar exploded ...
⚠ L3/L4 的根本限制

傳統 K8s NetworkPolicy 與 firewall 只能做到這層。它能擋「誰可以連」，但擋不了「連進來後做什麼」。tiefighter 是 empire 的合法 pod，但它呼叫排氣口 API 就會炸 Death Star — 這是應用層級的權限問題，L4 看不到。

5.5 升級到 L7：只允許 POST /v1/request-landing

關鍵差別：在 toPorts 下加 rules.http。Cilium 收到這條 rule，會自動把該 endpoint 的 ingress 流量導到內建 Envoy proxy 做 L7 inspection：

yaml
# sw_l3_l4_l7_policy.yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: "rule1"
spec:
  description: "L7 policy to restrict access to specific HTTP call"
  endpointSelector:
    matchLabels:
      org: empire
      class: deathstar
  ingress:
    - fromEndpoints:
        - matchLabels:
            org: empire
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
          rules:
            http:
              - method: "POST"
                path: "/v1/request-landing"
bash
kubectl apply -f https://raw.githubusercontent.com/cilium/cilium/1.19.3/examples/minikube/sw_l3_l4_l7_policy.yaml

# tiefighter 請求降落 - 依然允許
kubectl exec tiefighter -- curl -s -XPOST \
  deathstar.default.svc.cluster.local/v1/request-landing
# 預期: Ship landed

# tiefighter 炸排氣口 - 現在被擋（同樣 pod，同樣 port，但 path 不對）
kubectl exec tiefighter -- curl -s -XPUT \
  deathstar.default.svc.cluster.local/v1/exhaust-port
# 預期: Access denied
✓ 這就是 L7 policy 的價值

同一個 pod、同一個 port，根據HTTP method 與 path做差異化決策。這在傳統 iptables 或 K8s NetworkPolicy 是做不到的（K8s NP 只到 L4）。Cilium L7 規則靠內建 Envoy 實現，不需要 sidecar。

5.6 用 Hubble 觀察實際 flow

Hubble 是看「政策實際運作」最直觀的方法。先 port-forward Hubble Relay：

bash
# 在背景跑 port-forward
cilium hubble port-forward&

# 等一兩秒，確認 Hubble CLI 連得到
hubble status
# 預期:
# Healthcheck (via localhost:4245): Ok
# Current/Max Flows: 4095/4095 (100.00%)
# Flows/s: 4.50

觀察 deathstar 收到的 flow（再跑一次 curl 測試）：

bash
# Terminal A: 持續 follow 進入 deathstar 的 flow
hubble observe --pod default/deathstar --follow

# Terminal B: 觸發兩種請求
kubectl exec tiefighter -- curl -s -XPOST \
  deathstar.default.svc.cluster.local/v1/request-landing
kubectl exec tiefighter -- curl -s -XPUT \
  deathstar.default.svc.cluster.local/v1/exhaust-port
kubectl exec xwing -- curl -s --max-time 5 -XPOST \
  deathstar.default.svc.cluster.local/v1/request-landing

Terminal A 預期看到類似輸出（節錄）：

output
... default/tiefighter:54320 -> default/deathstar-xxxxx:80    http-request FORWARDED (HTTP/1.1 POST /v1/request-landing)
... default/tiefighter:54320 <- default/deathstar-xxxxx:80    http-response FORWARDED (HTTP/1.1 200 0ms)

... default/tiefighter:54322 -> default/deathstar-xxxxx:80    http-request DROPPED   (HTTP/1.1 PUT /v1/exhaust-port)

... default/xwing:54324      -> default/deathstar-xxxxx:80    Policy denied DROPPED (TCP Flags: SYN)

注意三種 verdict 的差別：

來源請求Hubble verdict解讀
tiefighter POST request-landing http-request FORWARDED L7 規則允許，看得到 HTTP method/path
tiefighter PUT exhaust-port http-request DROPPED L7 規則拒絕，Cilium 回 Access denied 而非 timeout
xwing POST request-landing Policy denied DROPPED (TCP SYN) L3/L4 直接擋下，封包根本沒到 deathstar pod

也可以開 Hubble UI 看 service map（互動式網路圖）：

bash
cilium hubble ui
# 瀏覽器自動開 http://localhost:12000
# 在 namespace 下拉選 default，會看到 tiefighter / xwing / deathstar 的連線圖
# 紅色連線代表 dropped，可點進去看 HTTP 細節

6. 常見初次安裝錯誤

症狀原因解法
cilium-agent CrashLoopBackOff，log 含 too many open files host inotify 限制不足 sysctl fs.inotify.max_user_watches=524288 與 max_user_instances=512
cilium status 卡在 Operator Pending 單節點 kind 預設啟兩個 operator replica 單節點 demo 改 --set operator.replicas=1
所有 connectivity test fail with timeout kind node 與 host 之間 MTU 過小，VXLAN encapsulation 後超 MTU 裝時加 --set MTU=1450 或在 kind config 設定 docker MTU
Pod 啟動但拿不到 IP，cilium-agent 顯示 operator unreachable operator pod 還沒 ready 等 60 秒；超過就 kubectl logs -n kube-system deploy/cilium-operator 排查
kubeProxyReplacement=true 但 NodePort 不通 kind 沒把 cgroup namespace 隔開，Socket LB 無法 attach 檢查 docker exec kind-control-plane ls -al /proc/self/ns/cgroup 與 host 不同；新版 kind 預設 OK
Hubble UI 打開後 service map 空白 Hubble Relay 還沒連到全部 agent hubble status 看 Connected Nodes: 3/3 才算 ready

7.1 回報問題前必跑：cilium sysdump

不論是內部排錯還是 GitHub issue，提交資訊時請附 sysdump，這會把所有 pod log、配置、BPF map 內容打包：

bash
cilium sysdump --output-filename cilium-sysdump
# 產出: cilium-sysdump.zip
# 內含: cilium-agent / operator log、cilium status、bpftool prog/map list、k8s 資源 YAML 等
⚠ sysdump 可能含敏感資訊

內含叢集所有 namespace 名稱、pod label、service IP。對外 share 前請確認你公司政策允許。私人對接 Cilium maintainer 通常可以 share；公開 GitHub issue 建議先過濾。

8. 本章重點回顧

  • Cilium CLI 是本機工具，獨立版號（v0.19.x），背後其實是 Helm。
  • kind 安裝記得 --set kubeProxyReplacement=true（因為 kind config 把 kube-proxy 關了）。
  • 驗證三件事：cilium status 全綠 → nodes Ready → cilium connectivity test 95+/95+ 通過。
  • Star Wars demo 三層演進：無 policy → L3/L4（擋 xwing）→ L7（擋特定 HTTP path）。
