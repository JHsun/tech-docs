A. 社群資源

A.1 治理結構

Cilium 是 CNCF Graduated 專案（2023 年畢業，與 K8s、Prometheus、Envoy 同級）。整個專案的治理：

  • Steering Committee：技術方向、release 重大決策；公開選舉產生
  • Technical Committee：架構與 API 設計把關
  • Special Interest Groups (SIGs)：分領域維護，下面細列
  • Maintainers：對特定 sub-system 有 merge 權限的 contributor
  • Code of Conduct Committee：社群行為準則執行

正式治理文件在 github.com/cilium/community。

A.2 Special Interest Groups (SIGs)

每個 SIG 負責一個 sub-system，有自己的 maintainer、weekly meeting、roadmap。當你的 PR / issue 落在某個範圍，SIG 就是要找的人：

SIG領域
sig-agentcilium-agent 核心邏輯
sig-datapathBPF program、kernel 互動
sig-policyNetwork Policy 引擎、CRD
sig-servicemeshIngress、Gateway API、Envoy 整合
sig-clustermesh跨叢集功能
sig-encryptionWireGuard / IPsec / mTLS
sig-hubbleHubble server / Relay / CLI / UI
sig-ipamIPAM 各模式
sig-bgpBGP Control Plane
sig-loadbalancingkube-proxy replacement、Service handling
sig-scalability大規模、效能
sig-docs文件、website
sig-releaseRelease management、backport

每個 SIG 的 meeting 時間、note、Slack channel 在 cilium/community sigs.yaml。任何人可以參加，不需先註冊。

  • 架構討論 / RFC：GitHub Discussions 或對應 SIG meeting

  • 商業支援需求：Isovalent（Cisco 收購）提供企業級 support，自家 cluster 規模大就找

A.4 Roadmap 與發版節奏

Cilium roadmap 不在單一文件，分三層追蹤：

  • 長期方向：主 repo 的 roadmap.rst + Community Meeting demo
  • 下個 minor 計畫：每個 SIG 在自家 issue tracker 開 milestone，標 milestone/1.20 之類
  • Release Note 草稿：release candidate 前產出，github.com/cilium/cilium/releases 的 draft

節奏（截至 1.19）：

  • Minor release ~4 個月一次
  • Patch release ~2-4 週一次
  • 單一 minor 維護 ~12 個月
  • 每兩年（左右）一次 KubeCon co-located 的 CiliumCon

B.2 該選哪個

沒有絕對的「最好」，只有「最適合場景」。粗略指南：

情境推薦理由
初學者、小 cluster、homelab Flannel 最輕、零學習；要 policy 再加 Calico = Canal
地端 BGP fabric、Windows 工作負載多 Calico BGP 是其招牌；Windows agent 較成熟
K8s-only、追求 L7 policy、觀測、Service Mesh Cilium L7 + Hubble + 無 sidecar mesh 一站式
VMware / NSX-T 既有環境 Antrea 原生 OVS 整合、tier policy 模型
跨混合雲、合規 / 多 OS Calico 跨平台支援廣（K8s + OpenShift + VM + bare metal）
HFT / 微秒級延遲 Cilium eBPF 直接在 kernel 處理，繞過 iptables
規模 1000+ node、想要單一 CNI 處理多 cluster Cilium ClusterMesh + KVStoreMesh + CiliumEndpointSlice
⚠ 別輕易切 CNI

換 CNI 不是滑動開關：要 drain 所有 node、清掉舊 CNI 狀態、重灌、重啟所有 pod。生產 cluster 通常是建新 cluster 跑 Cilium，把 workload 搬過去。第三部 §5 的 cilium-cni-migration 工具可以漸進式遷移，但仍是高風險操作。

B.3 雲端託管預設

雲端預設 CNI支援 Cilium
GKE Dataplane V2（基於 Cilium） 預設啟用 原生整合
AKS Azure CNI（傳統）/ Azure CNI Powered by Cilium（Linux node pool） 官方選項
EKS AWS VPC CNI 可單獨裝或 chaining 模式並用
OpenShift OVN-Kubernetes（4.x 預設） 可替換為 Cilium（社群支援）
K3s / RKE2 Flannel（預設）/ Canal / Cilium 可選 用 --flannel-backend=none 換 Cilium
💡 GKE Dataplane V2 ≠ 完整 Cilium

GKE Dataplane V2 是內嵌、簡化版的 Cilium，部分 advanced feature（如 BGP Control Plane、Hubble UI 自訂、ClusterMesh）不開放使用者控制。要完整 Cilium 體驗，可以在 GKE 上自己安裝 Cilium（停用 Dataplane V2）或選 Isovalent Enterprise 整合方案。

C. 常見錯誤對照表

On-call 時看到陌生錯誤字串，直接 grep 這份。錯誤分五類：

C.1 Pod / Endpoint 啟動

FailedCreatePodSandBox: ... failed to allocate IP
IPAM 枯竭（pool 用完）。擴 CIDR / 換 instance type / 開 prefix delegation。詳見第八部 B §10.9。
Endpoint stuck in "waiting-for-identity"
Identity allocation 卡住，通常 K8s API server 慢或 kvstore 不可達。看 cilium-operator log。
Endpoint in "init" state, never becomes ready
Cilium agent 在該 node 異常（panic / OOM / crash loop）。kubectl logs ds/cilium。
Unmanaged pod (no Cilium endpoint)
Pod 是 hostNetwork: true，或在 Cilium 部署前就建立。重啟 pod 或用 Host Policy 處理。
Endpoint regeneration failed: too many open files
系統 FD 上限不夠（大量 endpoint）。調 LimitNOFILE 或 sysctl fs.file-max。

C.2 Policy / Hubble

Verdict: DROPPED, reason: Policy denied
L3/L4 policy 把流量擋了。用 cilium-dbg policy trace 模擬決策定位。
Verdict: DROPPED, reason: Stale or unroutable IP
目的 pod 已被刪但連線還在試。可忽略，除非大量持續出現（代表 endpoint propagation 慢）。
Verdict: DROPPED, reason: Authentication required
mTLS 失敗。檢查 SPIFFE 憑證、Ztunnel 連線。
Verdict: DROPPED, reason: Service backend not found
Service 存在但 endpoints 空（pod 都沒 ready）。
Verdict: DROPPED, reason: No node ID found (code 197)
IPsec 模式下，目的 node 的 CiliumNode 物件還沒到。新加 node 或重啟過會短暫出現，可自癒。
Verdict: DROPPED, reason: Local cluster only (1.19+)
ClusterMesh policy 沒指定 cluster scope，1.19 預設只允許 local。執行 cilium clustermesh inspect-policy-default-local-cluster 找出 policy 並加 io.cilium.k8s.policy.cluster label。
Hubble Relay: context deadline exceeded
port-forward 斷了或 Relay 沒到達。cilium hubble port-forward 重連。

C.3 Datapath / BPF

CT: Map insertion failed
Conntrack 表滿。調 bpf.ctTcpMax / ctAnyMax，或加快 GC --conntrack-gc-interval=10s。詳見第八部 B §10.4。
BPF program load failed: invalid argument
通常 verifier reject。Cilium log 會印 verifier message，搜「verifier」找具體 register 狀態。可能 kernel 太舊。
BPF program load failed: cannot allocate memory
memlock rlimit 不夠。設 LimitMEMLOCK=infinity 或調大 ulimit -l。
Failed to mount bpffs at /sys/fs/bpf
bpffs 沒掛或被卸載。第八部 A §5 的 systemd unit / fstab 設定。
Drop reason: Invalid source IP
封包 src IP 不符合預期（spoofing 或 host firewall misconfig）。
Drop reason: Unsupported L3 protocol
IPv6 流量但沒開 ipv6 support。
Failed to attach BPF program to interface eth0
TC / XDP 衝突（其他工具佔用），或 driver 不支援 XDP（fallback 到 generic XDP 或關閉 acceleration）。

C.4 Encryption (WireGuard / IPsec)

XfrmInNoStates ever-increasing
IPsec key rotation 不同步，新舊 key 在不同 node 還沒收斂。等 1-2 分鐘；ClusterMesh 環境調大 encryption.ipsec.keyRotationDuration。
XfrmInStateProtoError
key 改了但SPI 沒換。重做正確的 key rotation（遞增 KEYID）。詳見第十部 A §9.4。
XfrmOutPolBlock ever-increasing
已知 issue #26954；多數情況下封包仍正常送出，counter 累積但無實際 drop。升 1.19 最新 patch 確認版本修復。
WireGuard: cilium_wg0 interface missing
kernel 沒 WireGuard module。modprobe wireguard，確認 kernel 5.6+。
Encryption status: Enabled (Wireguard) but no traffic encrypted
同 node pod-to-pod 不加密是設計；跨 node 才加密。用 tcpdump 在 eth0 看 UDP 51871 確認。

C.5 ClusterMesh

clustermesh-apiserver: Lease lost / leader election failed
apiserver 內嵌 etcd 失去 quorum 或網路斷。檢查 apiserver pod 數量與 Service 連線。
Failed to connect to remote cluster "c2"
tunnel 不通、clustermesh-apiserver LB IP 對方連不到、TLS 憑證不匹配。跑 cilium-dbg troubleshoot clustermesh。
Global service has no remote backends
兩 cluster 的 Service 不同名 / namespace、annotation 沒設 service.cilium.io/global: "true"、cluster.id 重複。
CiliumIdentity allocation failed: conflict
兩 cluster 的 cluster.id 設一樣，identity 範圍撞。改 cluster.id 並重建。

D. 三大角色學習檢查清單

不同角色不需要看完所有 14 部。下面是各角色的建議路徑與檢核點，每項可勾掉。

D.1 初學者 / K8s 應用開發者

目標：知道 Cilium 在你 cluster 內做什麼、寫得出基本 Network Policy、會看 Hubble 看流量

基礎概念（前 3 章）

  • 能說明「CNI 是什麼、為什麼 K8s 需要 CNI」
  • 能解釋「Cilium 的 identity 取代 IP」核心理念
  • 能畫出 Cilium 三件組架構（agent / operator / Hubble）
  • 能說明 routing mode tunnel vs native 差異
  • 能在 kind 環境完整跑完 Star Wars demo

實作 Network Policy

  • 能寫一份 K8s NetworkPolicy 控管同 namespace 流量
  • 能寫一份 CiliumNetworkPolicy 控管 HTTP method/path
  • 能寫 FQDN allow list 讓 pod 只能連特定外部域名
  • 能用 deny rule 擋掉 cluster 內某個方向
  • 知道「default 模式 vs always 模式」差異與漸進採用

觀察與除錯

  • 能用 hubble observe 看自家 pod 流量
  • 能解讀 verdict（FORWARDED / DROPPED / REDIRECTED）
  • 能在 Hubble UI 看 service map
  • 知道 sysdump 怎麼產、何時要產

建議閱讀：第一部 → 第二部 → 第六部 A → 第七部

D.2 開發者 / Contributor

目標：看懂 Cilium 原始碼、能送 PR、了解 eBPF 與 Cilium datapath 關係

底層基礎

  • 能畫出 eBPF VM、verifier、JIT 三階段
  • 能說明 BPF map 主要類型（LPM_TRIE / LRU_HASH / PROG_ARRAY）
  • 了解 Cilium 用到的主要 program type（XDP / TC / cgroup BPF）
  • 能用 bpftool 看 cluster 內 BPF 狀態
  • 知道 bpffs pinning 的目的（不會手刪 /sys/fs/bpf）

Cilium 架構

  • 能在 repo 內找到主要功能對應目錄
  • 了解 Hive DI framework 的 Cell 結構
  • 能讀懂一個 Cell 的 Provide / Config / Invoke / Lifecycle
  • 知道 StateDB 用途與基本 API
  • 能在 kind 跑本機 build 的 dev image

貢獻流程

  • 能跑通 make unit-tests 與 make lint
  • 知道 DCO sign-off + commit message 規矩
  • 能用 LVH 跑特定 kernel 的 BPF unit test
  • 能跑 cilium connectivity test 對自家 build
  • 送過至少一個 good-first-issue PR 並 merge

建議閱讀：第一部 → 第十部 A → 第十部 B + 跟著 SIG meeting

D.3 DevOps / SRE / 平台工程師

目標：負責 Cilium 在生產的可靠運維，含安裝、升級、效能、故障排查、安全強化

部署能力

  • 能用 Helm 自訂 values 部署 Cilium（不只 cilium install）
  • 能配置 routing mode、IPAM、kube-proxy replacement
  • 能在地端用 BGP + LB IPAM 對外曝光 Service
  • 能設定 ClusterMesh 跨叢集
  • 能啟用 WireGuard / IPsec encryption（含 1.19 Strict Mode）

觀測與告警

  • 能配 Prometheus 收齊 4 個 metric 來源（agent / operator / hubble / clustermesh）
  • 知道高基數 metric 並能排除
  • 能寫 Hubble drop alert（針對 namespace 級異常）
  • 能把 Hubble flow log export 到 Loki / SIEM
  • 會用官方 Grafana dashboard（ID 16611-16614）

運維與升級

  • 會跑 pre-flight check 並解讀結果
  • 能完整執行 minor 升級（無 reuse-values）
  • 知道哪些 Helm values 變動會觸發 agent restart 還是 endpoint regen
  • 遇到問題能跑 cilium sysdump 並過濾敏感資訊
  • 能調 BPF map 大小應對大 cluster scaling

故障排查（核心戰力）

  • 看到 verdict DROPPED 能立即用 policy trace 定位
  • 看到 CT Map insertion failed 知道調哪個 BPF value
  • 看到 LB / Ingress 不通能依序檢查 Service / endpoints / Envoy
  • 看到 ClusterMesh 斷會用 troubleshoot clustermesh
  • 看到 XFRM error 能對照表找根因
  • 熟悉 §C 錯誤對照表前 20 條

安全強化

  • 實作 cluster-wide deny cloud metadata
  • 實作 default-deny per namespace + allow list
  • 啟用 Host Firewall 保護 bastion node
  • RBAC 最小化 cilium-agent 權限
  • 對外 Service 加 SNI policy 或 TLS 攔截

建議閱讀：全 14 部，重點放第三部、第六部、第七部、第八部

D.5 30 / 60 / 90 天進階建議

  • 若有跨地需求，建 ClusterMesh PoC（第四部 B）
  • 讀第六部 B 把 threat model 對應到自家環境，產出強化清單
  • 進 Cilium Slack，挑 SIG 加入 weekly meeting
  • 把 monthly cilium-config diff 寫 cron 監測，建立變更可審計性
  • 讀第十部 A，至少熟悉 BPF / XFRM 概念，能用 bpftool 看狀態
