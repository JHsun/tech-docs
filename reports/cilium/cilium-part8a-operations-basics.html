運維基礎

把 Cilium 跑起來只是開始，長期運維才是真正的工程挑戰。本章把系統需求（kernel / OS / firewall / port）、升級流程（pre-flight、rollback、版本特定注意）、Configuration ConfigMap 變更與偵測機制一次講透，讓 SRE 有完整 runbook。

對應官方文件：Operations → System Requirements / Upgrade / Configuration Cilium 版本：1.19.x 主要對象：DevOps / SRE

5. BPF Filesystem 與 Routing Table

5.1 BPF Filesystem

Cilium 需要 /sys/fs/bpf 是 bpffs 類型且持久化。沒掛或被卸載，agent 重啟時所有 BPF map 會掉光，造成所有連線中斷。多數發行版預設已掛，自建環境要確認：

bash
# 檢查
mount | grep /sys/fs/bpf
# 應該看到: bpffs on /sys/fs/bpf type bpf (rw,nosuid,nodev,noexec,relatime)

# 若沒掛，手動掛
sudo mount bpffs -t bpf /sys/fs/bpf

# 永久化：寫進 /etc/fstab
echo "bpffs /sys/fs/bpf bpf defaults 0 0" | sudo tee -a /etc/fstab

# 用 systemd 管理 kubelet 的環境（如 kubeadm）建議用 unit
# /etc/systemd/system/sys-fs-bpf.mount
[Unit]
Description=Mount BPF filesystem
DefaultDependencies=no
Before=local-fs.target umount.target
After=swap.target

[Mount]
What=bpffs
Where=/sys/fs/bpf
Type=bpf
Options=rw,nosuid,nodev,noexec,relatime,mode=700

[Install]
WantedBy=multi-user.target

5.2 Routing Table 衝突

Cilium 內部用 routing table 2004、2005（IPsec）。如果你的系統已有 table id 衝突（罕見），需要錯開。檢查：

bash
# 看 routing rule
ip rule list

# 看 cilium 用到的 table
cat /etc/iproute2/rt_tables 2>/dev/null
ip route show table 2004
ip route show table 2005

6. Privileges & Key-Value Store

6.1 必要 capability

cilium-agent 必須跑成 privileged container，需要的 capability：

  • CAP_SYS_ADMIN — 載入 BPF program、配 net namespace
  • CAP_NET_ADMIN — 設網卡、routing、iptables
  • CAP_BPF（5.8+）— BPF program load / map ops
  • CAP_PERFMON（5.8+）— BPF profiling 與 verification

標準 DaemonSet 安裝會自動給。OpenShift / 限制嚴格的環境要在 SCC（Security Context Constraint）放行（第三部 §6.4）。

6.2 KV Store 選擇

選項適用備註
identityAllocationMode: crd預設，< 1000 node所有 identity 存 K8s CRD（CiliumIdentity）
identityAllocationMode: kvstore超大叢集 (1000+ node)用獨立 etcd，避免衝擊 K8s API server

外部 etcd 設定見第三部 §8。預設用 CRD 對 99% 的 cluster 都夠用。

7. 升級指南

7.1 升級準備清單

動手前先打勾：

  • ✅ 讀完目標版本的 Upgrade Guide（docs.cilium.io/en/stable/operations/upgrade/）
  • ✅ 讀完目標版本的 Release Notes（特別是 breaking changes 段落）
  • ✅ 確認 K8s 版本與目標 Cilium 相容（compatibility table）
  • ✅ 確認 kernel 滿足目標 Cilium 需求（§2 對照表）
  • ✅ 把目前 Helm values 匯出並備份（後面要用）
  • ✅ 在 staging cluster 完整跑過一遍
  • ✅ 排定維護視窗（即使是 graceful upgrade，仍會短暫 pod 啟動延遲）
  • ✅ 監控就緒：Prometheus alert、Hubble drop event dashboard

7.2 Pre-flight check（minor 升級必跑）

pre-flight 的工作：

  1. 在每個 node 把新版 image pre-pull，避免升級時拉不到 image 卡住
  2. 驗證現有 CRD（CNP、CCNP）能被新版本解析
  3. 檢查 BPF map 大小是否需要調整
bash
# Step 1: 部署 pre-flight DaemonSet（不取代現有 agent）
helm install cilium-preflight oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  --set preflight.enabled=true \
  --set agent=false \
  --set operator.enabled=false

# Step 2: 等所有 node pre-pull 完成
kubectl get ds cilium-pre-flight-check -n kube-system -w
# 等 DESIRED == READY == NODES 數量

# Step 3: 看 CiliumPreFlightConfig 結果
kubectl get ciliumpreflightconfigs -o yaml | grep -A10 status
# 預期: status.cnpStatus 全部 OK，沒有 incompatible
# 若顯示 incompatible policy，要先改舊 policy 再升級

# Step 4: 移除 pre-flight
helm uninstall cilium-preflight -n kube-system

7.3 執行升級

1

匯出現有 values

bash
helm get values cilium -n kube-system -o yaml > current-values.yaml
cp current-values.yaml current-values.yaml.bak     # 備份原檔
2

檢查 deprecated 欄位

Release Notes 會列出 removed 與 deprecated values。手動審視 current-values.yaml 比對；最近一次 1.19 移除 ToRequires / FromRequires，Kafka rule 也已 deprecated。

3

套用升級

bash
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 \
  --namespace kube-system \
  -f current-values.yaml \
  --set upgradeCompatibility=1.18      # 從哪一版升上來

# 重要: 不要用 --reuse-values，因為 chart 預設值可能變動
4

逐 node 觀察 rollout

bash
kubectl -n kube-system rollout status ds/cilium --timeout=10m
kubectl -n kube-system rollout status deploy/cilium-operator
kubectl -n kube-system rollout status deploy/hubble-relay

# 持續觀察 cilium-agent log
kubectl -n kube-system logs ds/cilium -f --max-log-requests=10
5

升級後驗證

bash
cilium status --wait
cilium connectivity test
cilium version

# 抽查現有 pod 流量仍正常
kubectl exec -n my-app deploy/my-app -- curl -s https://api.internal.example.com/healthz
# 觀察 Hubble drop event 數量
hubble observe --last 1000 --verdict DROPPED | wc -l

7.4 1.18 → 1.19 重點注意

變更影響動作
Encryption Strict Mode 新功能，啟用後未加密流量會被 drop 選用，但生產加密環境推薦評估
ClusterMesh policy 預設 local-only 不指定 cluster 的 selector，只允許 local cluster 升級前用 cilium clustermesh inspect-policy-default-local-cluster 找出受影響 policy
Multi-Pool IPAM 升 Stable 無 breaking 不必動，但可考慮採用
Multi-Level DNS Matches 新 wildcard 行為（**） 檢查既有 FQDN policy 是否有 ** 寫法
ICMPv4 Destination unreachable for deny 選用，啟用後 deny 流量會回 ICMP 需要時開 enableICMPReplyForDenyPolicy: true
Ztunnel Beta 新功能，需配合 Istio Ambient 選用，第五部詳述
Kafka rule deprecated 仍可運作但未來會移除 規劃改用 L4 + SASL/mTLS
ToRequires / FromRequires 已移除 用到的 policy 會 reject 改寫成 toEndpoints / fromEndpoints
K8s 1.35、Envoy 1.35、Gateway API 1.4、GoBGP 3.37 內部依賴升版 確認你的 cluster K8s 版本相容

7.5 Rollback 策略

⚠ Rollback 比想像中複雜

Cilium 升級會動到 BPF map schema，向後降版時舊版 agent 可能讀不懂新版寫的 map。官方建議「不要降版」，遇到問題優先 patch 修；真的要降版，需要完整重灌 cilium。

真的需要 rollback 的流程：

bash
# 1. helm rollback（嘗試，可能不完全乾淨）
helm rollback cilium -n kube-system

# 2. 若失敗，完整重灌
helm uninstall cilium -n kube-system

# 等所有 cilium-agent 真的下線
kubectl -n kube-system get pods -l k8s-app=cilium
# 應該為空

# 清掉每個 node 的 BPF map（在 host 上跑）
for node in $(kubectl get nodes -o name); do
  echo "cleaning $node"
  # 用 nsenter 或 DaemonSet job 跑：
  # rm -rf /sys/fs/bpf/tc/globals/cilium_*
done

# 重新裝舊版
helm install cilium oci://quay.io/cilium/charts/cilium \
  --version 1.18.x \
  --namespace kube-system \
  -f current-values.yaml.bak

整個過程會中斷 cluster 網路，這就是為什麼要 staging 先測。

8. Configuration 詳解

8.1 cilium-config ConfigMap 結構

所有 cilium-agent 與 cilium-operator 的 runtime 配置都來自單一 ConfigMap：kube-system/cilium-config。agent 啟動時讀它，並監聽變動。

bash
kubectl -n kube-system get configmap cilium-config -o yaml | head -50

# 範例（節錄）:
# data:
#   cluster-name: my-prod-cluster
#   cluster-id: "1"
#   kube-proxy-replacement: "true"
#   routing-mode: tunnel
#   tunnel-protocol: vxlan
#   identity-allocation-mode: crd
#   enable-bgp-control-plane: "true"
#   ...

ConfigMap 的 key 跟 Helm value 不是一對一，Helm 會自動轉換。例如 Helm 寫 routingMode: tunnel，ConfigMap 對應 key 是 routing-mode: tunnel。

8.2 變更流程（標準做法）

變動] E --> F{需要重啟

三種變更類別：

類別例子套用方式
立即生效（hot reload）policy enforcement mode、log level改 ConfigMap，agent 自動載入
需 agent 重啟routing-mode、kube-proxy-replacement、encryption改 + kubectl rollout restart ds/cilium
需 endpoint 重生MTU 變更、large 規模 policy 變動agent 重啟後逐 endpoint regenerate
⚠ 不要直接 kubectl edit ConfigMap

下次 helm upgrade 你的 manual 改動會被覆蓋。所有變更都走 values.yaml + helm upgrade。緊急時可以暫時 edit，事後務必同步回 values.yaml。

8.3 偵測未套用的 ConfigMap 變動

Cilium 提供工具檢查「ConfigMap 已改但 agent 還沒讀」的情況：

bash
# 看 cilium agent 目前 in-memory 配置 vs ConfigMap
kubectl -n kube-system exec ds/cilium -- cilium-dbg config

# 對比 ConfigMap 內容（看 diff）
kubectl -n kube-system get cm cilium-config -o yaml

# Helm 看當前發布的 values
helm get values cilium -n kube-system

# 觸發 agent 重新讀 config（不重啟）
kubectl -n kube-system exec ds/cilium -- kill -HUP 1

# 或乾脆 rollout restart
kubectl -n kube-system rollout restart ds/cilium

在 metric 上，Cilium 暴露 cilium_config_sources 與 cilium_config_changes_total 可以做 alert：

promql
# ConfigMap 在過去 10 分鐘有改動，但 agent 沒重啟
increase(cilium_config_changes_total[10m]) > 0
  and on() (time() - cilium_agent_bootstrap_seconds > 600)

8.4 CiliumNodeConfig：對特定 node 群套不同設定

傳統 ConfigMap 是 cluster 全域。但你可能想對特定 node 群套不同配置（漸進式 rollout、不同 hardware、跨 rack 不同）。CiliumNodeConfig CRD 解這個：

yaml
apiVersion: cilium.io/v2
kind: CiliumNodeConfig
metadata:
  name: enable-bbr-on-edge
  namespace: kube-system
spec:
  nodeSelector:
    matchLabels:
      node-role: edge      # 只對 edge node
  defaults:
    enable-bandwidth-manager: "true"
    enable-bbr: "true"

第三部 §5.3 的 CNI 遷移就用了這個機制，逐 node 切換 CNI conf。

9. 日常運維檢核

給 on-call 與 SRE 用的快速健康檢查清單：

每日

  • cilium status 全綠
  • cilium connectivity test 在低風險時段跑（每日 cron）
  • Hubble drop rate 沒異常 spike
  • Prometheus alert 沒 firing
  • cilium_bpf_map_pressure < 0.8

每週

  • 查 Cilium GitHub Releases 是否有新 patch（特別是 security advisory）
  • 看 cilium-agent 與 cilium-operator restart 次數，異常重啟要查
  • 稽核 Hubble drop event 是否有可疑模式（同一 src 大量打不同 dst port）
  • 看 cilium-config ConfigMap 改動歷史

每月

  • 確認 K8s / kernel / Cilium 三者版本仍在 compatibility window 內
  • 確認 staging cluster 有跑 latest patch，準備上 prod
  • 跑一次 sysdump 留檔：cilium sysdump --output-filename cilium-sysdump-$(date +%F)
  • 檢查 BPF map sizing 是否需要調整（隨 cluster scale）

每季

  • 規劃下個 minor 升級（如 1.19 → 1.20）
  • 檢視 deprecated feature 使用情況
  • 跑 chaos test：殺 cilium-operator、模擬 node 故障，看恢復

10. 本章重點回顧

  • Cilium 1.19 推薦 kernel 5.10+，5.15+ 解鎖 BPF Host Routing，6.x 可享受 BIG TCP 與 IPv6 underlay。
  • Ubuntu 22.04+ 務必設 ManageForeignRoutes=no，否則 systemd-networkd 會搶 Cilium 的 routing rule。
  • 必開 kernel config：BPF / FIB_RULES / NET_CLS_BPF；L7 加 NETFILTER_XT_*；WireGuard 加 CONFIG_WIREGUARD=m。
  • Port 速記：node 互通 4240 / 4244 / 8472 (VXLAN) / 6081 (Geneve) / 51871 (WireGuard) / ESP。Prometheus scrape 9962 / 9963 / 9965。
  • BPF FS 必須持久化：/sys/fs/bpf 用 systemd unit 或 fstab，重啟後仍掛載。
  • 升級流程：讀 release notes → pre-flight check → 匯出 values 並檢查 deprecated → helm upgrade（不要 reuse-values）→ rollout 觀察。
  • 1.19 升級重點：ClusterMesh policy 預設 local-only、Multi-Pool stable、ToRequires/FromRequires 已移除、Kafka rule deprecated、依賴升 K8s 1.35 / Envoy 1.35。
  • Rollback 複雜且風險高，能 patch 就 patch、不要降版。真的需要 rollback 要清 BPF map 重灌。
  • 所有 runtime 配置在 cilium-config ConfigMap，不要直接 edit，走 Helm。三類變更：immediate / agent restart / endpoint regen。
  • CiliumNodeConfig CRD 給特定 node 群套不同配置，漸進式 rollout 利器。
