效能與 Troubleshooting

這一章是 SRE 的工具箱：先把所有效能旋鈕（host routing、netkit、XDP、BIG TCP、BBR）一次盤點，再用 symptom library 把生產上 10 種典型問題的「症狀 → 排查指令 → 根因 → 處置」拆給你。最後是 cilium-bugtool / sysdump / debug 模式。

對應官方文件：Operations → Performance / Troubleshooting Cilium 版本：1.19.x 主要對象：SRE / on-call

1. 效能調校總覽

Cilium 預設配置在大多數場景已經很好，但下面這些進階旋鈕能進一步壓 latency 與提升 throughput。先看全景：

調校項需要 kernel效益1.19 狀態
eBPF Host Routing5.10+跳過 iptables hooks，吞吐+15-30%Stable
netkit 設備模式6.8+取代 veth，更快 namespace switchBeta
XDP for NodePort/LB4.18+，且 NIC 支援 native XDP外部 LB 流量在 driver 層處理Stable
IPv6 BIG TCP6.3+GSO/GRO 從 64k 提升到 192kStable
IPv4 BIG TCP6.3+同上，需 IPv4Stable
Bandwidth Manager + EDT5.1+Pod 級頻寬限制（精準）Stable
BBR congestion control5.1+長 RTT 場景 throughput 大幅提升Stable
Native Routing（無 tunnel）—省下 50 bytes 封裝開銷Stable
💡 調校順序建議

不要一次開全部，逐項驗證：(1) 確認 kernel ≥ 5.15 → 開 BPF Host Routing；(2) 確認 NIC 支援 → 開 XDP；(3) 高吞吐場景再考慮 BIG TCP；(4) 想做 Pod 級頻寬限制再開 Bandwidth Manager。每開一個都跑 connectivity test 與壓測比對。

2. eBPF Host Routing（必開）

Cilium 從 1.9 起提供「eBPF host-routing」，完全 bypass iptables 與 Linux upper stack，封包進 host 後直接由 BPF 程式 forward 到目的 endpoint。

啟用 + 驗證：

bash
# 啟用（搭配 kube-proxy 替換）
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 --namespace kube-system --reuse-values \
  --set kubeProxyReplacement=true \
  --set bpf.masquerade=true

kubectl -n kube-system rollout restart ds/cilium

# 驗證
cilium status | grep "Host Routing"
# 預期: Host Routing:           BPF
# 如果是 Legacy 代表 kernel 太舊或某些條件沒滿足

3. netkit 設備模式（kernel 6.8+）Beta

1.19 預設仍用 veth pair 連接 Pod netns 與 host。kernel 6.8 引入新設備類型 netkit，專為 BPF 設計：

  • L3 device 模式，pod 流量在沒有 BPF program 時被 blackhole
  • BPF program 直接掛在 netkit peer 上，無 veth 的 redirect 開銷
  • 支援 BIG TCP
  • 啟用後，非 netkit 介面自動切到 tcx（更高效的 BPF link）

啟用：

yaml
# 需要 kernel 6.8+ 與 BPF host routing
bpf:
  hostRouting: true
bpfNetkit:
  enabled: true              # 1.19 Beta key
bash
# 驗證
cilium status | grep "Device Mode"
# 預期: Device Mode:            netkit

當社群多數 kernel 升到 6.8+，veth 模式會被 deprecate。目前 Beta 階段，生產採用前做完整 PoC。

4. XDP 加速 NodePort / LoadBalancer

當外部請求進來打 NodePort / LoadBalancer，傳統路徑是封包進 kernel network stack → BPF (TC) → 處理。對「本 node 不是 backend」的情況，封包要轉到別的 node，多繞一圈 stack 浪費。

XDP（eXpress Data Path）讓 BPF program 在 NIC driver 層就攔截封包，極致 scale-out。前提：NIC 支援 native XDP（mlx5、ixgbe、i40e、ice、sfc 等主流）。

yaml
# Helm 啟用
loadBalancer:
  acceleration: native        # native / disabled
  algorithm: maglev           # 搭 maglev 一致性 hash
kubeProxyReplacement: true
bash
cilium status | grep "XDP Acceleration"
# 預期: XDP Acceleration:       Native [eth0]
# 若顯示 Disabled，可能是 NIC driver 不支援，可改用 generic（fallback）
⚠ XDP 與 Egress Gateway 互斥

官方明確指出：Egress Gateway reply 流量在 XDP Acceleration 開啟時不會被加密。同時用 Egress GW + Encryption + XDP 要驗證行為，必要時關閉 XDP。

5. BIG TCP（100Gbit/s 場景）

傳統 Linux 網路 stack 處理單一 TCP packet 上限是 64KB GSO/GRO。在 100 Gbit/s+ 環境，每秒要處理上百萬個 packet，每個都要過完整 stack 一次，CPU 直接打滿。

BIG TCP 把 GSO/GRO 上限拉到 192KB，每個 syscall 處理更大的 batch，CPU 用量大降。

項目傳統BIG TCP
GSO/GRO max64 KB192 KB
每 packet stack traversal多少
CPU 用量高低
是否需要改 MTU—否
kernel 需求—5.19+（IPv6）/ 6.3+（IPv4）

IPv6 BIG TCP（先有）

yaml
routingMode: native
bpf:
  masquerade: true
ipv6:
  enabled: true
enableIPv6BIGTCP: true
kubeProxyReplacement: true

IPv4 BIG TCP（kernel 6.3+）

yaml
enableIPv4BIGTCP: true
💡 啟用後要重啟 Pod

切換 BIG TCP 後，K8s pod 必須重啟才生效（kernel 為新 pod 設更大的 GSO/GRO limit）。

6. Bandwidth Manager & BBR

第四部 A §7.3 介紹過 Bandwidth Manager 的 Pod annotation 用法，這裡補充底層機制與 BBR 搭配。

EDT（Earliest Departure Time）

傳統 traffic shaping 用 token bucket，限速精度不高且需要 buffer queue。Bandwidth Manager 改用 EDT：每個 packet 標記「最早可發送時間」，BPF 在 egress 時根據時間決定送或排隊，精準度高得多。

BBR 啟用

BBR（Bottleneck Bandwidth and RTT）是 Google 提出的 congestion control 算法，長 RTT、有 packet loss 的場景（跨地連線）throughput 顯著提升。Cilium 1.13+ 支援讓 Pod 流量也用 BBR：

yaml
bandwidthManager:
  enabled: true
  bbr: true                  # 對 Pod TCP 流量啟用 BBR
bash
cilium status | grep BandwidthManager
# 預期: BandwidthManager:       EDT with BPF [BBR] [eth0]

7. CNI Performance Benchmark

Cilium 官方有一份標準 benchmark 套件（社群可重現），對照 Cilium 與其他 CNI（Calico、Flannel、Antrea）。重點結論：

  • Throughput (TCP_STREAM)：Cilium + Native + BPF Host Routing ≈ 接近 host networking
  • Latency (TCP_RR)：Cilium 約 50% 低於 iptables-based CNI
  • kube-proxy iptables vs Cilium BPF：service 數量 ≥ 1000 時 Cilium 領先 5-10x
  • XDP NodePort LB：scale-out 接近 line rate（100 Gbit/s）

自己跑 benchmark

bash
# Cilium 內建 perf test
cilium connectivity perf

# 對指定 node pair 跑 throughput / latency
cilium connectivity perf \
  --duration 30s \
  --report-output json \
  --output-file perf-result.json

# 工具會 deploy netperf 系列 pod，跑 TCP_STREAM / TCP_RR / UDP_RR
# 完成後產出比較表
cat perf-result.json | jq '.results[] | {test, throughput_mbps, p99_latency_us}'
⚠ Benchmark 數字陷阱

真實 cluster 的 throughput 受 NIC、kernel、CPU pinning、其他 sidecar、cluster 規模影響大。不要直接抄官方數字當 SLA，自家環境跑出來才算數。

8. 大規模 Scalability 實務

cluster 規模從 100 node 跨到 1000+ node，Cilium 的瓶頸通常出現在三個地方：

  1. K8s API server 壓力：每個 Pod 一個 CiliumEndpoint，每個 identity 一個 CiliumIdentity
  2. BPF map 大小：CT、policy、service map 都有預設上限
  3. Agent CPU / Memory：identity allocation、policy recomputation

8.1 CiliumEndpointSlice（必開）

大 cluster 一定要開：

yaml
ciliumEndpointSlice:
  enabled: true

8.2 BPF Map 大小

Map預設大 cluster 建議備註
bpf-ct-global-tcp-max5242881-2MConnection tracking TCP
bpf-ct-global-any-max2621440.5-1MCT 非 TCP（UDP/ICMP）
bpf-nat-global-max5242881-2MNAT 表
bpf-policy-map-max1638465536每 endpoint 的 policy entry 上限
bpf-lb-map-max65536262144Service backend lookup
bpf-fragments-map-max819232768fragment tracking
yaml
# 一次調整
bpf:
  ctTcpMax: 1048576
  ctAnyMax: 524288
  natMax: 1048576
  policyMapMax: 65536
  lbMapMax: 262144

# 每個 map 多用記憶體（線性增加），預估每百萬 entry 大約 80-200 MB

8.3 K8s API client rate limit

大 cluster 內 cilium-agent / operator 要 watch 大量資源，default rate limit 會卡：

yaml
k8sClientRateLimit:
  qps: 200          # 預設 5 / 50
  burst: 400        # 預設 10 / 100

# operator 也要調
operator:
  extraArgs:
    - --k8s-api-qps=100
    - --k8s-api-burst=200

8.4 External etcd（≥1000 node）

第三部 §8 詳述。把 identity 從 K8s CRD 搬到獨立 etcd，避免衝擊 K8s API server。

8.5 KVStoreMesh（ClusterMesh ≥ 5 cluster）

ClusterMesh 1.16+ 預設啟用 KVStoreMesh，把跨 cluster 同步從「每 agent 連所有 remote clustermesh-apiserver」改成「每 cluster 內一個聚合 etcd」，連線數從 N×M 降到 M。

10. Symptom Library（10 種典型問題）

實戰中最常見的 10 種 symptom，每一個給「症狀 → 排查 → 根因 → 處置」。

10.1 Pod 連不上任何東西

症狀：新建 pod 拿到 IP，但連任何外部 / 內部都 timeout

排查：

bash
kubectl -n kube-system exec ds/cilium -- cilium-dbg endpoint list | grep <pod-ip>
# 看該 endpoint 是否在 ready 狀態
# 看 POLICY (ingress/egress) 欄位是 Disabled 還是 Enabled

# 看詳細狀態
ID=<endpoint-id-from-above>
kubectl -n kube-system exec ds/cilium -- cilium-dbg endpoint get $ID

# 看 ipcache 有沒這 IP
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf ipcache list | grep <pod-ip>

常見根因：

  • Pod 是 unmanaged（hostNetwork=true 或 Cilium 還沒接管）
  • 該 namespace 有 default-deny 卻沒對應 allow policy
  • cilium-agent 在該 node CrashLoop

10.2 同 node pod 互通，跨 node 不通

症狀：node1 上 pod 可連同 node1 其他 pod；連 node2 的 pod 全 timeout

排查：

bash
# node 互通 health
kubectl -n kube-system exec ds/cilium -- cilium-health status --verbose

# tunnel 表 (VXLAN/Geneve)
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf tunnel list
# 應該看到所有其他 node

# 在 node 上抓封裝流量
docker exec node1 tcpdump -i eth0 udp port 8472 -c 5

# 監聽 drop
kubectl -n kube-system exec ds/cilium -- cilium-dbg monitor --type drop

常見根因：

  • Underlay firewall 沒開 UDP 8472 (VXLAN) 或 6081 (Geneve)
  • MTU 不一致（tunnel 加 50 bytes 超過 underlay MTU）
  • Native routing 下 router 沒學到 Pod CIDR
  • encryption 啟用但部分 node key 沒同步

10.3 Policy 沒套用

症狀：寫了 deny policy 但流量還是通的，或寫了 allow 但流量被擋

排查：

bash
# 確認 policy 存在
kubectl get cnp,ccnp -A

# 看 agent 看到的 policy
kubectl -n kube-system exec ds/cilium -- cilium-dbg policy get | head -50

# 模擬決策
kubectl -n kube-system exec ds/cilium -- \
  cilium-dbg policy trace --src-identity 12345 --dst-identity 67890 --dport 80/TCP

# Hubble 看實際 verdict
hubble observe --pod default/myapp --verdict DROPPED --last 50

常見根因：

  • Pod 是 unmanaged（hostNetwork=true → policy 不套）
  • Pod 在 Cilium 部署前就建立（沒被 inject）
  • endpointSelector 寫錯，沒選到目標 pod
  • 跨 namespace 忘加 namespace label
  • 1.19 ClusterMesh policy 沒指定 cluster scope（預設 local-only）

10.4 大量 drop：CT Map insertion failed

症狀：cilium monitor 看到 xx drop (CT: Map insertion failed) 持續出現

排查：

bash
# 看 CT 用量
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf ct list global | wc -l

# Prometheus 看 BPF map pressure
# cilium_bpf_map_pressure{name="ct_global"} 接近 1.0

# 看 GC 頻率
kubectl -n kube-system exec ds/cilium -- cilium-dbg metrics list | grep ct

根因 + 處置：

  • CT 表滿：典型大流量場景。提高上限：
yaml
bpf:
  ctTcpMax: 1048576       # 1M
  ctAnyMax: 524288

# 或加快 GC
extraArgs:
  - --conntrack-gc-interval=10s

10.5 偶發 packet 丟失（intermittent loss）

症狀：99% 流量正常，偶爾少數連線 timeout 或 RST

排查：

bash
# 看 drop 是否與特定 pod 變動相關（restart、scale）
hubble observe --since 1h --verdict DROPPED --output json | \
  jq -r '"\(.time) \(.drop_reason) \(.source.pod_name) -> \(.destination.pod_name)"' | sort

# 看 NIC errors
docker exec <node> ip -s link show eth0
# 看 RX/TX errors, drops

# WireGuard 偶發 drop（issue 33159）
cilium status | grep Encryption
# 升級到最新 1.19.x patch 通常修了

# host kernel log
docker exec <node> dmesg | tail -100

常見根因：

  • endpoint 重生時短暫 drop（policy 變動、新 pod）
  • BPF map pressure 接近 max 時 GC 跟不上
  • WireGuard 配置變動時的已知 race（看官方 issue 33159）
  • NIC drop（hardware buffer 不足）

10.6 LoadBalancer / NodePort 連不到

症狀：Service 顯示 EXTERNAL-IP，外部連這 IP timeout 或 connection refused

排查：

bash
# 1. Service backend 有 endpoint?
kubectl get endpoints <svc-name>

# 2. Cilium BPF LB 表
kubectl -n kube-system exec ds/cilium -- cilium-dbg service list
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf lb list

# 3. BGP / L2 announcement 有宣告 VIP?
cilium bgp routes advertised ipv4 unicast
# 或 kubectl get ciliuml2announcementpolicy

# 4. kube-proxy-replacement 是否啟用
cilium status | grep KubeProxyReplacement

常見根因：

  • LB IPAM pool 沒設或耗盡
  • BGP session down，VIP 沒宣告出去
  • backend pod readinessProbe 失敗，endpoints 為空
  • 外部 firewall 擋 NodePort range

10.7 ClusterMesh 跨叢集服務斷

症狀：local cluster pod 連 remote cluster global service timeout

排查：

bash
# 確認 mesh 狀態
cilium clustermesh status --wait
# 看 Cluster Connections: N/N connected

# 看 cilium 看得到 remote endpoints
kubectl -n kube-system exec ds/cilium -- cilium-dbg bpf ipcache list | grep "cluster=<remote-name>"

# 看 service backends 是否含 remote
kubectl -n kube-system exec ds/cilium -- cilium-dbg service list | grep <svc-name>
# 應該看到 backend IP 來自 remote cluster CIDR

# 1.19 policy 預設 local-only 檢查
cilium clustermesh inspect-policy-default-local-cluster --all-namespaces

10.8 Ingress / Gateway API 不通

症狀：建 Ingress 後 EXTERNAL-IP pending，或得到 IP 但連不上

排查：

bash
# Ingress / Gateway 狀態
kubectl describe ingress <name>
kubectl describe gateway <name>
kubectl describe httproute <name>     # 看 status.parents

# Cilium Envoy
kubectl -n kube-system get pods -l k8s-app=cilium-envoy
kubectl -n kube-system logs ds/cilium-envoy --tail=100

# 看 Envoy admin
NODE_AGENT=$(kubectl -n kube-system get pod -l k8s-app=cilium -o name | head -1)
kubectl -n kube-system exec $NODE_AGENT -- \
  cilium-dbg envoy admin --address 127.0.0.1:9901 listeners

# 開 debug
kubectl -n kube-system edit cm cilium-config
# 設 debug: "true", debug-verbose: "flow"
kubectl -n kube-system rollout restart ds/cilium

常見根因：

  • 缺 LB IPAM pool（地端）或雲端 LB 沒設好
  • Gateway API CRD 沒裝
  • policy 缺 world→ingress 或 ingress→app 一段（第五部 §8）
  • HTTPRoute hostname / parentRefs 寫錯

10.9 IPAM 枯竭

症狀：新 pod 起不來，event 顯示 FailedCreatePodSandBox: failed to set up pod network: failed to allocate IP

排查：

bash
# 看 cluster pool 使用率
kubectl get ciliumnodes -o json | jq '.items[] |
  {name: .metadata.name,
   used: (.status.ipam.used | length),
   available: .spec.ipam.podCIDRs}'

# AWS ENI / Azure 模式
kubectl get ciliumnodes -o yaml | grep -A5 "ipam:"

# 看 operator log
kubectl -n kube-system logs deploy/cilium-operator | grep -i ipam

處置：

  • cluster-pool：擴大 clusterPoolIPv4PodCIDRList 或加新 pool（不要動 maskSize）
  • AWS ENI：升 instance type（更多 ENI）或開 prefix delegation
  • Azure：擴 VNET subnet
  • Multi-Pool：建額外 CiliumPodIPPool

10.10 etcd / kvstore 問題（外部 etcd 模式）

症狀：cilium agent 報 kvstore not ready、identity allocation 慢

排查：

bash
cilium status | grep -A5 "KVStore"
# 預期: etcd: 3/3 connected, has-quorum=true

# 從 cilium-agent 內測 etcd
kubectl -n kube-system exec ds/cilium -- \
  etcdctl --endpoints=https://etcd1:2379,https://etcd2:2379 \
  endpoint health

常見根因：

  • etcd 失去 quorum（>1 etcd member down）
  • TLS cert 過期
  • etcd disk IOPS 不足
  • 網路斷

11. cilium-bugtool & sysdump（回報問題必跑）

11.1 cilium-bugtool（單 node）

跑在單一 cilium-agent內，收集該 node 的所有 debug 資訊：BPF map dump、agent log、host kernel info、iptables、ip route、netstat...

bash
POD=$(kubectl -n kube-system get pod -l k8s-app=cilium -o name | head -1)

# 進 pod 跑
kubectl -n kube-system exec $POD -- cilium-bugtool

# 預期輸出最後一行類似:
# ARCHIVE at /tmp/cilium-bugtool-20260513-093045.tar.gz

# 複製出來
kubectl cp kube-system/${POD##*/}:/tmp/cilium-bugtool-20260513-093045.tar.gz \
  ./cilium-bugtool.tar.gz

# 解開檢視
tar xzvf cilium-bugtool.tar.gz
ls cilium-bugtool-*/

11.2 cilium sysdump（全 cluster）

cilium CLI 提供更高層的 sysdump，自動收集所有 node 的 bugtool + K8s 資源 YAML，是回報 GitHub issue 與聯絡 support 的標準格式：

bash
cilium sysdump --output-filename cilium-sysdump-$(date +%F)
# 產出: cilium-sysdump-2026-05-13.zip

# 內含:
# - 每 node 的 cilium-bugtool
# - cilium agent / operator pod 描述與 log
# - K8s 資源 YAML (CNP, CCNP, CiliumNode, CiliumEndpoint, services, deployments)
# - kube-system 內所有 pod 狀態
# - cilium connectivity test 結果
# - Hubble status

# 從特定 node 收
cilium sysdump --node-list node1,node2

# 限制大小（避免 log 太大）
cilium sysdump --logs-since=2h
⚠ sysdump 含敏感資訊

內含所有 namespace 名稱、pod label、Service IP、policy。對外 share 前確認公司政策；公開 GitHub issue 建議先 grep -v 過濾敏感字串。

12. Debug 模式與 log 等級

12.1 暫時開 debug

bash
# 對單一 agent 開（不重啟）
kubectl -n kube-system exec ds/cilium -- cilium-dbg config Debug=true

# 看 monitor verbose
kubectl -n kube-system exec ds/cilium -- cilium-dbg monitor -v
# 加 datapath 訊息
kubectl -n kube-system exec ds/cilium -- cilium-dbg config debug-verbose=datapath

# 對單一 endpoint 開 debug
kubectl -n kube-system exec ds/cilium -- cilium-dbg endpoint config <id> Debug=true

12.2 全 cluster 開 debug（生產要小心）

yaml
# Helm
debug:
  enabled: true
  verbose: "flow datapath"   # flow / datapath / kvstore
⚠ debug=true 影響效能與 log 量

會產生大量 log，可能撐爆 logging system。排查完務必關掉。

12.3 監聽特定 endpoint 的 datapath event

bash
# 進該 node 的 agent
kubectl -n kube-system exec -it ds/cilium -- bash

# 看 endpoint id
cilium-dbg endpoint list | grep mypod

# follow 該 endpoint event
cilium-dbg monitor --related-to 1234
# 或只看 drop
cilium-dbg monitor --related-to 1234 --type drop

13. 本章重點回顧

  • 效能調校順序：BPF Host Routing（最低門檻，kernel 5.10+）→ XDP for LB（需 native XDP NIC）→ BIG TCP（100Gbit/s+）→ BBR + Bandwidth Manager（長 RTT 場景）→ netkit（kernel 6.8+, Beta）。
  • 大規模調校三件事：ciliumEndpointSlice.enabled=true、BPF map 上限調大（CT/NAT/policy/lb）、K8s client rate limit 提高。≥1000 node 考慮 external etcd。
  • Troubleshooting 5 步起手式：cilium status → agent pods → endpoint list → hubble drop → cilium-health。先把全景理清再深入。
  • 10 個典型 symptom：unmanaged pod、跨 node 不通、policy 沒套、CT map 滿、偶發 drop、LB 不通、ClusterMesh 斷、Ingress/Gateway、IPAM 枯竭、etcd。
  • 三個必背指令：cilium-dbg endpoint list、cilium-dbg policy trace、hubble observe --verdict DROPPED。
  • cilium sysdump 是回報問題的標準格式（含所有 node bugtool + K8s 資源），share 前過濾敏感資訊。
  • Debug 模式排查完務必關掉，避免 log 爆炸。
