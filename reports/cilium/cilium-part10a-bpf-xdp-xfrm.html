BPF / XDP / XFRM Reference

這一章給想看懂 Cilium 內部運作、開發 BPF program、或除錯 IPsec 的開發者。涵蓋 BPF 架構（VM、verifier、JIT、map）、9 種 program type 與對應 hook、開發工具鏈（LLVM、bpftool、bpftrace），以及 Cilium IPsec 底層的 XFRM 子系統。日常運維讀者可以略過，需要時再翻。

1. BPF 架構

eBPF 是 Linux Kernel 一個通用、安全、可程式化的擴充機制。從 4.x 開始大量擴充，到 6.x 已經是 Linux 觀測與網路堆疊的核心。Cilium 整個 datapath 就建在它上面。先把整個架構看清楚：

1.1 BPF Virtual Machine

eBPF 是一個 RISC-like 64-bit virtual machine，有：

  • 11 個 64-bit 暫存器（R0–R10，R10 是 frame pointer）
  • 固定 stack 大小 512 bytes
  • 受限的指令集（算術、跳轉、load/store、function call）
  • 不能任意呼叫 kernel function，只能透過 helper functions
  • 沒有 loop（4.x），5.3+ 有 bounded loop，5.17+ 有更彈性的 iter

1.2 編譯流程：C → BPF bytecode → native

Cilium 的 BPF program 寫在 bpf/ 目錄下，是 C source。流程：

  1. cilium-agent 啟動時用內嵌的 clang/LLVM編譯 BPF C → ELF object
  2. 每個 endpoint 都有個別客製化的 BPF object（label、IP、policy 編進去）
  3. 透過 bpf() syscall load 進 kernel
  4. kernel verifier 驗證後 JIT 編譯為 native instruction
  5. attach 到對應 hook
💡 為什麼 Cilium 要在 agent 內帶 clang

傳統 BPF program 是「固定編譯好」load 進去。但 Cilium 要對每個 endpoint 把 identity、IP、policy 用 #define 編進 BPF code，產出最佳化版本。這需要動態編譯，因此 cilium-agent image 內含 clang/LLVM 工具鏈。

1.3 Verifier（成敗關鍵）

Verifier 是 kernel 內的靜態分析器，BPF program load 進來會被它檢查：

  • 會不會無窮迴圈：早期不允許 loop；5.3+ bounded loop；5.17+ iter
  • 會不會 unbounded recursion：tail call 限制鏈深度（5+ 一般是 33）
  • 會不會 access 越界記憶體：load/store 都要先檢查 bound
  • 會不會 access 未初始化記憶體：每個 register 都追蹤狀態
  • map access 是否合法：lookup 結果可能是 NULL，必須先檢查再用
  • 指令數上限：早期 4096，現在 1M（與 privileges 有關）

沒過 verifier 的 program 直接被拒絕 load，運行時不可能 panic kernel。這是 BPF 安全性的核心保證。

1.4 JIT Compiler

verifier 通過後，kernel 用 JIT 把 BPF bytecode 編譯成對應 CPU 架構的 native instruction（x86_64、arm64、ppc64、s390x、riscv 等）。執行時直接跑 native，沒有解釋器開銷。

啟用 JIT：

bash
# 確認 kernel 有 BPF JIT 編進去
zcat /proc/config.gz | grep BPF_JIT
# CONFIG_BPF_JIT=y

# 看是否啟用（多數發行版預設啟用）
sysctl net.core.bpf_jit_enable
# net.core.bpf_jit_enable = 1

# JIT 強化（unprivileged BPF）
sysctl net.core.bpf_jit_harden
# 0 = off, 1 = unpriv, 2 = all

2. BPF Maps

BPF map 是 kernel 與 userspace 共享的 key-value store。BPF program 透過 helper（bpf_map_lookup_elem、bpf_map_update_elem、bpf_map_delete_elem）讀寫，cilium-agent 從 userspace 也能讀寫。

Cilium 用了非常多 map 類型，幾個重要的：

3. Program Types & Hooks

BPF 不只是「網路 BPF」，現在已有 30+ 種 program type，掛到 kernel 各角落。Cilium 用到的主要幾種：

3.1 XDP（eXpress Data Path）

掛在 NIC driver 層，封包進來時最早的 hook 點。重要性質：

  • 速度極快：還沒進 kernel network stack 就執行
  • 程式回傳值決定動作：XDP_PASS（給 stack）/ XDP_DROP（丟）/ XDP_TX（送回同 NIC）/ XDP_REDIRECT（送去別的 NIC）
  • 能存取的封包資料較限制（沒 sk_buff，只有原始 frame）
  • 三種模式：Native XDP（driver 內，最快）/ Generic XDP（generic stack，較慢但相容）/ Offloaded XDP（SmartNIC 硬體執行）

Cilium 用 XDP 做：

  • NodePort / LoadBalancer Service 加速（loadBalancer.acceleration: native）
  • DDoS 防護的 prefilter
  • 1.19 的 BGP packet 處理也部分用到

3.2 TC (cls_bpf) — Cilium 主力

掛在 Traffic Control 子系統，每個 network device 都有 ingress / egress queue：

  • 能存取完整 sk_buff（含 socket、route info）
  • 能修改 packet（NAT、redirect、header insert）
  • 回傳值：TC_ACT_OK（繼續）/ TC_ACT_SHOT（丟）/ TC_ACT_REDIRECT（轉發）
  • kernel 6.6+ 引入 tcx，取代舊 cls_bpf API，1.19 已支援

Cilium 把 TC BPF program 掛到每個 veth peer（host 端）與 host NIC 的 ingress/egress hook，這是 datapath 主力。

3.3 cgroup BPF（Socket-LB 核心）

掛在 cgroup 層級，攔截特定 syscall：

  • BPF_CGROUP_INET4_CONNECT / INET6_CONNECT：connect() 時改 dst IP/port
  • BPF_CGROUP_INET4_SENDMSG / INET6_SENDMSG：UDP sendto() 時改 dst
  • BPF_CGROUP_INET4_GETSOCKNAME：應用 query 對端 IP 時還原

Cilium 用這個實作 socket-LB：cluster 內 pod 連 ClusterIP 時，connect() 在 syscall 階段就被改寫成直接連 backend pod IP。連 conntrack 都不用，零 datapath 開銷。

3.4 Socket Filter / SO_ATTACH_BPF

舊式（classic BPF 時代），用於 socket layer 的 packet filter（tcpdump 用）。Cilium 主要不依賴這個。

3.5 Tracing 類（Tetragon / 觀測用）

Cilium 本身 datapath 不直接用，但姊妹專案 Tetragon 大量使用：

  • kprobe：掛 kernel function entry
  • kretprobe：掛 kernel function return
  • tracepoint：kernel 預定義事件點
  • uprobe / uretprobe：使用者空間 binary 函數
  • perf_event：CPU 計數器、profiling
  • LSM (Linux Security Module)：5.7+ 用 BPF 寫 LSM hook

看現在 attach 了什麼

bash
# 列所有 attach 點
bpftool net show
# 預期看到 tc / xdp 掛點

bpftool cgroup tree
# 看 cgroup BPF attach

4. Tail Calls & BPF-to-BPF Calls

BPF program 受 verifier 限制不能 unbounded 函數調用。但 Cilium 邏輯複雜（policy + service + observability），需要拆成多個小 program 串接：

4.1 Tail Calls

把 program ID 放進 BPF_MAP_TYPE_PROG_ARRAY，呼叫 bpf_tail_call(ctx, prog_map, index) 跳轉到對應 program。

  • 跳轉 = 替代：當前 program 結束，新 program 重新開始（不會 return 回來）
  • 最大 chain 深度 33（5+ kernel）
  • 動態：map 內容可以動態改，不需要 reload program

Cilium 用 tail call 把 datapath 拆成多段（from-container、to-container、handle-policy…），編譯快、verifier 友善。

4.2 BPF-to-BPF Function Calls

5.0+ 引入，正常的函數呼叫（return 回來繼續）。比 tail call 更接近一般 C 函數，但有 stack 深度限制。Cilium 用它組織 helper 邏輯。

5. Helper Functions

BPF program 不能呼叫任意 kernel 函數。kernel 提供一組受控的 helper functions，每個 helper 都有對應 ID，由 verifier 確認 program 有權使用。

網路 BPF 常用 helper：

Helper用途
bpf_map_lookup_elem查 map

bpf_redirect_neigh5.10+，根據 dst IP 自動找 neighbour
bpf_redirect_peer送到對端 netns peer device（netkit 用）
bpf_skb_change_head / change_tail插入 / 移除 packet header

6. Object Pinning & bpffs

預設 BPF map 與 program 的生命週期綁定載入者：load 它的 process 退出，object refcount 降為 0，kernel 自動清掉。對 Cilium 不好：cilium-agent 重啟一次就清光所有 map，所有連線斷。

解法：pinning，把 map / program pin 到 bpffs（一種特殊 pseudo filesystem，掛在 /sys/fs/bpf）：

bash
# 看 bpffs 內的 pinned object
ls -la /sys/fs/bpf/
# 應該有 tc/globals/, ip/, ... 一堆 cilium_* 開頭

ls -la /sys/fs/bpf/tc/globals/ | head
# cilium_lxc, cilium_ipcache, cilium_lb4_services_v2, ...

# bpftool 看
bpftool map list pinned

Cilium 的所有 datapath map 都 pin 到 bpffs，所以 cilium-agent 重啟時 BPF map 完整保留，現有連線不會斷（被 verifier 檢查過的 BPF program 也還在 kernel 內運行）。

⚠ 別動 /sys/fs/bpf

手動刪 bpffs 內的 cilium_* 檔案 = 強制清 BPF map = 所有 datapath state 消失 = cluster 大斷網。除非你確切知道在做什麼，不要 touch。

7. 開發工具鏈

7.1 LLVM / clang（編譯）

BPF C source 用 clang -target bpf 編譯。要支援 BTF（BPF Type Format）以利 CO-RE：

bash
# 編譯 BPF source
clang -O2 -g -Wall -target bpf \
  -D__TARGET_ARCH_x86 \
  -I/usr/include/bpf \
  -c hello.bpf.c -o hello.bpf.o

# 看產出的 BTF info
bpftool btf dump file hello.bpf.o

7.2 bpftool（瑞士刀）

kernel 內建（package linux-tools-*），是看/改 BPF 狀態的標準工具：

bash
# 主要 subcommands
bpftool prog list                    # 所有 BPF program
bpftool prog show id 123             # 單一 program
bpftool prog dump xlated id 123      # 看 disassembled
bpftool prog dump jited id 123       # 看 JIT 後 native code

bpftool map list                     # 所有 map
bpftool map dump name cilium_lxc     # dump 內容
bpftool map update id 123 key 0x01 0x02 value 0x03 0x04

bpftool net show                     # 看 TC / XDP attach
bpftool cgroup tree                  # cgroup BPF
bpftool btf list                     # 載入的 BTF

# Feature probing：這個 kernel 支援什麼 BPF feature
bpftool feature probe full

7.3 iproute2 與 bpftrace

iproute2：傳統 attach TC BPF 的工具（tc filter add ... bpf da obj hello.o sec ingress）。Cilium 現在直接走 libbpf API，不依賴 iproute2 load，但 host 仍需要 iproute2 做其他 routing 操作。

bpftrace：類似 awk 的 BPF 腳本語言，快速寫一次性追蹤：

bash
# 追蹤所有 connect()
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_connect {
  printf("%s -> family %d\n", comm, args->uservaddr->sa_family);
}'

# 統計 conntrack lookup 結果
sudo bpftrace -e 'kprobe:nf_conntrack_in {
  @[comm] = count();
}'

8. Debug & Test

BPF program log

BPF 內無 printf，但有 bpf_printk()（helper）把訊息寫到 kernel trace pipe：

bash
# BPF 程式內
bpf_printk("packet src=%pI4 dst=%pI4\n", &src_ip, &dst_ip);

# Host 上看
sudo cat /sys/kernel/debug/tracing/trace_pipe
# 或
sudo bpftool prog tracelog

BPF testing

5.x 起 BPF 提供 BPF_PROG_TEST_RUN syscall：對 program 灌入指定封包，看回傳值與封包修改結果。Cilium 內部 test framework 基於這個。

bash
# bpftool 提供 wrapper
bpftool prog run id 123 \
  data_in test_packet.bin \
  data_out result.bin

# 看回傳值
echo $?

verifier log

load 失敗時最有用的 debug：

bash
# load 時加上 -d

9. XFRM Reference（IPsec 底層）

XFRM 是 Linux kernel 的 IPsec 框架，名字來自「transform」。Cilium IPsec encryption 完全靠 XFRM；理解它對排查 IPsec 問題不可少。WireGuard 路徑不用 XFRM。

9.1 概念：State 與 Policy

概念意義
XFRM State (SA, Security Association) 實際的加密參數：算法、key、SPI（Security Parameter Index）、source/destination、模式（tunnel / transport）
XFRM Policy (SP, Security Policy) 「哪些封包要走加密」的規則：source/destination CIDR、protocol、方向（in/out/fwd）、要綁哪些 state（template）
SPI 32-bit 識別碼，受方靠它找到對應 state 解密
ESP / AH IPsec 兩種 protocol：ESP 加密+完整性，AH 只完整性。Cilium 用 ESP

典型 Cilium 環境的 ip xfrm 輸出

bash
# 進 node host namespace（kind 環境用 docker exec）
sudo ip xfrm state list
sudo ip xfrm policy list

# 範例 state:
# src 192.168.1.10 dst 192.168.1.20
#   proto esp spi 0x00000003 reqid 1 mode tunnel
#   replay-window 0
#   mark 0xd00/0xf00
#   aead rfc4106(gcm(aes)) 0xa1b2c3d4... 128
#   anti-replay context: seq 0x0, oseq 0x0, bitmap 0x00000000

# 範例 policy:
# src 0.0.0.0/0 dst 10.1.0.0/16
#   dir out priority 0
#   mark 0xe00/0xf00
#   tmpl src 192.168.1.10 dst 192.168.1.20
#     proto esp reqid 1 mode tunnel

9.4 XFRM Errors 對照表

XFRM 錯誤計數器在 /proc/net/xfrm_stat，要先開 CONFIG_XFRM_STATISTICS。每個錯誤都代表一個 packet drop。

Error意義常見原因
XfrmInError kernel 內部錯誤（記憶體配置失敗、route lookup 失敗） memory pressure / 對端 pod 已刪除但 packet 還在
XfrmInBufferError 解密期間 buffer 配置失敗 memory pressure
XfrmInHdrError 外層 IP header 或 SPI 格式錯 傳輸過程封包損壞
XfrmInNoStates 找不到對應 state（最常見錯誤） Key rotation 時新舊 key 不同步、SPI 不匹配
XfrmInStateProtoError protocol 不對 / checksum 失敗 / decrypt 失敗 Key 改了但SPI 沒換，做正確的 key rotation 修
XfrmInStateModeError tunnel vs transport mode 不一致 配置錯誤
XfrmInStateSeqError anti-replay window 之外 網路嚴重亂序、key rotation 沒重置 seq
XfrmInStateExpired state 過期 Cilium 一般不設過期，不該出現
XfrmInTmplMismatch state 不符 policy template 配置不一致
XfrmInNoPols 找不到對應 policy policy 沒裝、reqid 不對
XfrmInPolBlock policy 顯式 block 配置有 deny policy
XfrmOutStateSeqError OUT state sequence 達上限 state 用太久沒 rotate
XfrmOutPolBlock OUT 方向 policy block 常見大量出現，已知 Cilium issue #26954，多數情況下無害但要看 Release Note 確認版本修復
XfrmFwdHdrError decrypt 後 route lookup 失敗 對端 pod 已刪、CiliumNode 資訊還沒到
⚠ 哪些可忍受、哪些要修

官方建議：XfrmFwdHdrError 與 XfrmInError 在正常運維下可能少量出現（pod 剛刪 / 資訊還沒同步）。其他 XFRM error 通常代表 Cilium bug 或配置錯誤，要看版本與 release notes。XfrmOutPolBlock 是知名 issue，1.13+ 多次修補，務必跑最新 patch。

# cilium 包裝

Key Rotation 正確流程

升級或定期 rotate IPsec key 時，必須增加 SPI，否則會大量 XfrmInStateProtoError：

bash
# 1. 取得現有 secret 與 SPI（KEYID）
kubectl -n kube-system get secret cilium-ipsec-keys -o jsonpath='{.data.keys}' | base64 -d
# 範例: 3+ rfc4106(gcm(aes)) ABCD...DEF 128

# 2. 產新 key（SPI +1，注意第一個數字）
NEW_KEY="4+ rfc4106(gcm(aes)) $(echo $(dd if=/dev/urandom count=20 bs=1 2>/dev/null | xxd -p -c 64)) 128"

# 3. 更新 secret（保留舊 key，agent 會自動切換）
kubectl -n kube-system patch secret cilium-ipsec-keys --type='json' \
  -p='[{"op":"replace","path":"/data/keys","value":"'$(echo "$NEW_KEY" | base64 -w0)'"}]'

# 4. 等所有 agent 套用（預設 1 分鐘內）
sleep 90
kubectl -n kube-system exec ds/cilium -- cilium-dbg encrypt status

# ClusterMesh 環境 key rotation 跨多 cluster，default 5 分鐘 cleanup window 可能不夠：
helm upgrade ... --set encryption.ipsec.keyRotationDuration=30m

10. 本章重點回顧

  • eBPF 三件套：受 verifier 檢查的 sandboxed program、與 userspace 共享的 BPF maps、kernel 提供的 helper functions。verifier 是安全核心。
  • Cilium agent 內含 clang/LLVM，因為每個 endpoint 都需要客製化編譯（identity / IP / policy 編進 BPF）。
  • 三大 BPF map 用途：LPM_TRIE（ipcache CIDR 比對）/ LRU_HASH（conntrack）/ HASH_OF_MAPS（per-endpoint policy）。
  • 四大 Program Type：XDP（極速 LB / DDoS）/ TC（cls_bpf / tcx）（Cilium 主力）/ cgroup BPF（socket-LB）/ tracing 類（Tetragon 用）。
  • Tail call 拆 program 串接（不 return）；BPF-to-BPF call 是正常函數呼叫（5.0+）。
  • bpffs pinning 讓 Cilium agent 重啟時 BPF map 與 program 保留，連線不斷。絕對不要手動刪 /sys/fs/bpf/cilium_*。
  • 三大工具：clang -target bpf（編譯）、bpftool（看狀態）、bpftrace（快速腳本）。
  • debug 工具：bpf_printk → /sys/kernel/debug/tracing/trace_pipe；verifier reject → 加 -d verbose 看 register state。
  • XFRM 是 Linux IPsec 框架。state = SA（實際加密參數）/ policy = SP（哪些封包要加密）。SPI 是收方找對應 state 的 32-bit ID。
  • XFRM 錯誤定位：XfrmInNoStates = key rotation 不同步；XfrmInStateProtoError = key 改了沒換 SPI；XfrmFwdHdrError = pod 剛刪（可忍受）；XfrmOutPolBlock = 知名 issue 看 release notes。
  • IPsec key rotation 務必遞增 SPI（KEYID），並考慮 ClusterMesh 需要更長的 cleanup window。
