Network Policy 全解

所有 Cilium 安全功能的核心就是這份政策語言。本章一次把 L3 / L4 / L7、deny、host policy、entities、FQDN、CIDR、selector、policy enforcement mode 講透。下一章（6B）用這些武器解實戰問題：DNS lockdown、TLS visibility、Kafka 防護、AWS metadata 鎖定、整體 threat model。

對應官方文件：Security → Policy 全章 Cilium 版本：1.19.x 主要對象：所有人，特別是 DevOps / SRE / Security

1. 安全模型基礎：Identity 取代 IP

第一部講過：Cilium policy 的關鍵不是 IP，是 identity。先把這個直覺再強化一次，因為後面所有 rule 都繞著它轉。

規則含意：

  • 所有 label 完全相同的 Pod 共享一個 identity ID
  • Policy 在 datapath 用 identity 比對，不查 IP
  • Pod 重啟換 IP → identity 不變 → policy 無感知
  • 新增 Pod、deployment scale up，新 Pod 自動繼承 identity

2. 三種 Policy 資源

Cilium 支援三種寫 policy 的物件，混用沒問題：

資源Scope能力
networking.k8s.io/v1 NetworkPolicy Namespace K8s 原生標準，L3/L4。Cilium 完全相容，但少了 L7、entities、deny 等
CiliumNetworkPolicy (CNP) Namespace Cilium 擴充版，本章主角
CiliumClusterwideNetworkPolicy (CCNP) Cluster 同樣語法，但全 cluster 適用，常用於：host firewall、全域 DNS 攔截、跨團隊規則

本章範例都用 CNP/CCNP。K8s 原生 NetworkPolicy 對應寫法在 §11。

3. Policy Enforcement Mode

Cilium 整體有三種 enforcement mode，用 Helm value policyEnforcementMode 設定：

Mode意義適用
default（預設） 有匹配的 policy 才執行；沒 policy 選到的 endpoint 全 allow 逐步導入 zero-trust 的過渡期
always 每個 endpoint 都強制要有 policy 才能通；沒被 policy 選到的全部 deny 已完成 policy coverage 的成熟環境
never 所有 policy 全失效，allow-all 遷移 CNI 期間、debug

實務建議流程：

  1. 新 cluster 從 default 開始
  2. 逐步補 policy，先做「default deny」逐 namespace（允許 list 列出來的，剩下擋）
  3. 用 Hubble 觀察哪些流量被 dropped
  4. 所有重要 namespace 都有完整 policy 後，再考慮全 cluster 換 always

怎麼做「default deny」？最簡單的方法：在每個 namespace 加一條空 ingress/egress 規則，再用其他 policy allow list：

yaml
# 對 dev namespace 啟用 default deny
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: default-deny
  namespace: dev
spec:
  endpointSelector: {}            # 選全部 pod in this namespace
  ingress: []                     # 空陣列 = 全擋
  egress: []                      # 空陣列 = 全擋

4. Rule 的基本結構

所有 CNP 都長這樣：

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: example
  namespace: my-ns
spec:
  # 1) 對誰生效（subject）
  endpointSelector:
    matchLabels:
      app: backend

  # 2) 進來的規則
  ingress:
    - fromEndpoints:               # 從哪些 endpoint 來
        - matchLabels: { app: frontend }
      fromEntities:                # 或從哪些 entity 來
        - "world"
      fromCIDR:                    # 或從哪些 CIDR 來
        - "203.0.113.0/24"
      toPorts:                     # 在哪些 port 上
        - ports:
            - port: "80"
              protocol: TCP
          rules:                   # L7 規則（可選）
            http:
              - method: GET
                path: "/api/.*"

  # 3) 出去的規則（語法對稱）
  egress:
    - toEndpoints:
        - matchLabels: { app: database }
      toPorts:
        - ports: [{ port: "5432", protocol: TCP }]

關鍵概念：

  • EndpointSelector 決定規則套用於哪些 Pod（subject）
  • ingress / egress 是 array，同一個 array 內多個 rule 是 OR（任一條 match 即可）
  • 同一條 rule 內 fromXxx + toPorts 是 AND（兩個條件都要 match）
  • rules.http / rules.dns / rules.kafka 是 L7 子句，必須有 toPorts 才能寫

5. L3 Policy：選誰 vs 對誰 L3

5.1 EndpointSelector（基於 Pod label）

最基本的 L3 規則：「allow frontend → backend」。不限定 port。

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: l3-allow-frontend
  namespace: dev
spec:
  endpointSelector:
    matchLabels:
      role: backend
  ingress:
    - fromEndpoints:
        - matchLabels:
            role: frontend

常見變化：

yaml
# 允許 same namespace 任何 pod
ingress:
  - fromEndpoints:
      - {}                             # 空 selector = 同 namespace 任何 pod

# 用 matchExpressions
ingress:
  - fromEndpoints:
      - matchExpressions:
          - { key: tier, operator: In, values: [frontend, gateway] }
          - { key: env,  operator: NotIn, values: [test] }

# 多條 fromEndpoints 是 OR
ingress:
  - fromEndpoints:
      - matchLabels: { app: frontend }
      - matchLabels: { app: admin-tool }

5.2 跨 namespace

⚠ 預設只選 same namespace

CNP 內的 endpointSelector 與 fromEndpoints 預設只看 policy 自己的 namespace。要跨 namespace 必須明確標出 namespace label。

yaml
# 允許 monitoring namespace 的 prometheus 連進來
ingress:
  - fromEndpoints:
      - matchLabels:
          app: prometheus
          k8s:io.kubernetes.pod.namespace: monitoring   # 關鍵

5.3 Entities（保留 identity）

除了 pod label，Cilium 提供一組「entity」當捷徑：

Entity意義典型用途
worldcluster 外一切（網際網路）egress 對外
clustercluster 內所有 endpoint、node、unmanaged。1.19 起 ClusterMesh 不含其他 cluster內部寬鬆規則
host本機 host processnode-local DNS、metric agent
remote-nodecluster 其他 node 的 host跨 node host 流量
kube-apiserverK8s API server（自動偵測）允許 pod call API
ingressCilium Envoy 的 ingress identity第五部講過
healthCilium health endpoint內部監控
init啟動中還沒解析 identity 的 endpoint非 K8s 環境
unmanagedCilium 不管的 pod（hostNetwork）很少直接用
all以上全部debug 用
yaml
# Pod 可以連 kube-apiserver 與外網
spec:
  endpointSelector:
    matchLabels:
      app: my-app
  egress:
    - toEntities:
        - kube-apiserver
        - world                  # 對外網
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]

5.4 CIDR 與 CiliumCIDRGroup

⚠ CIDR 只匹配 unmanaged endpoint

CIDR 規則只對 Cilium 不管的 IP 生效。你以為 10.0.0.0/8 會包含 Pod IP，但 Pod 是 managed endpoint，CIDR 規則對它無效。要用 endpoint selector。

yaml
# 允許特定外部 IP 範圍進來
ingress:
  - fromCIDR:
      - "203.0.113.0/24"
    fromCIDRSet:                       # 排除特定子網
      - cidr: "198.51.100.0/24"
        except:
          - "198.51.100.128/25"

多個 policy 反覆寫 CIDR 列表很亂。1.16+ 提供 CiliumCIDRGroup 把 CIDR 命名打包，給多個 policy 引用：

yaml
# 一次定義
apiVersion: cilium.io/v2alpha1
kind: CiliumCIDRGroup
metadata:
  name: corp-networks
spec:
  externalCIDRs:
    - "10.100.0.0/16"               # 辦公網
    - "10.200.0.0/16"               # 資料中心
    - "172.16.0.0/12"
---
# 多個 policy 重用
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: { name: corp-ingress }
spec:
  endpointSelector:
    matchLabels: { exposed: "true" }
  ingress:
    - fromCIDRSet:
        - cidrGroupRef: corp-networks

5.5 Service 與 FQDN

toServices：用 K8s Service 名稱當目的

yaml
egress:
  - toServices:
      - k8sService:
          serviceName: my-database
          namespace: production
⚠ toServices 限制

toServices 不能同時搭配 toPorts。要嘛用 service identity，要嘛限制 port，二選一。混用會引入安全風險（你以為的限制其實沒套上）。

toFQDNs：用域名（DNS 解析）

對 SaaS / 外部 API（IP 會變）非常實用。Cilium 用內建 DNS proxy 攔截 DNS query，學到「我們允許的域名解析出哪些 IP」，再把這些 IP 動態寫進 BPF policy map：

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-api-fqdn
spec:
  endpointSelector:
    matchLabels: { app: my-app }
  egress:
    # 必須先允許 DNS 解析（53/UDP）並啟用 DNS rules
    - toEndpoints:
        - matchLabels:
            "k8s:io.kubernetes.pod.namespace": kube-system
            "k8s:k8s-app": kube-dns
      toPorts:
        - ports: [{ port: "53", protocol: UDP }]
          rules:
            dns:
              - matchPattern: "*.api.cloud.example.com"
              - matchName: "registry.cilium.io"

    # 對解析出來的 IP，允許 TCP/443
    - toFQDNs:
        - matchPattern: "*.api.cloud.example.com"
        - matchName: "registry.cilium.io"
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]

細節：

  • 必須同時允許 DNS 查詢（53/UDP）並寫 rules.dns，否則 Cilium 沒看到 DNS 回應就沒 IP 可學
  • toFQDNs 規則不能與 toEndpoints / toCIDRs 同一個 egress entry，要拆兩條
  • matchPattern 用 glob 語法（*.example.com）
  • 1.19 新功能：Multi-Level DNS Matches — ** 可跨多層子域名（a.b.c.example.com）

6. L4 Policy：限制 port 與 protocol L4

在 L3 之上加 toPorts：

yaml
ingress:
  - fromEndpoints:
      - matchLabels: { role: frontend }
    toPorts:
      - ports:
          - port: "80"
            protocol: TCP
          - port: "443"
            protocol: TCP
        # 端口範圍 (Cilium 1.10+)
          - port: "8000"
            endPort: 8999
            protocol: TCP

常用模式：

yaml
# 「allow all from frontend on 80/TCP」
- fromEndpoints: [{ matchLabels: { role: frontend } }]
  toPorts: [{ ports: [{ port: "80", protocol: TCP }] }]

# 「allow ICMP only」(ping)
- fromEndpoints: [{ matchLabels: { role: monitoring } }]
  icmps:
    - fields:
        - type: 8           # ICMP Echo
          family: IPv4

# 「allow all TCP egress」
egress:
  - toEntities: [world]
    toPorts: [{ ports: [{ port: "0", protocol: TCP }] }]   # port 0 = any

1.19 新功能：對 deny 規則回 ICMPv4 Destination unreachable，client 立刻知道被擋而不是 timeout。可在 helm 啟用：

yaml
# Helm values
enableICMPReplyForDenyPolicy: true

7. L7 Policy L7

L7 規則寫在 toPorts.rules 下面，必須有對應的 L4 port（因為要先指定哪個 port 走 Envoy 解析）。一旦寫了 L7 rule，Cilium 自動把該 port 的流量 transparent redirect 到 per-node Envoy。

7.1 HTTP

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: http-fine-grained
spec:
  endpointSelector:
    matchLabels: { app: myService }
  ingress:
    - toPorts:
        - ports: [{ port: "80", protocol: TCP }]
          rules:
            http:
              # 只允許 GET /products
              - method: GET
                path: "/products"

              # 允許 PUT /path2 但必須帶特定 header
              - method: PUT
                path: "/path2$"
                headers:
                  - 'X-My-Header: true'

              # 用正則
              - method: GET
                path: "/api/v[12]/users/.*"

              # 限定 Host header
              - method: GET
                host: "^api\\.example\\.com$"

能匹配的欄位：

  • method — HTTP method（regex）
  • path — URL path（regex，建議加 ^...$ 錨點）
  • host — Host header（regex）
  • headers — header 必須包含某條 key:value（多個 header 是 AND）
  • headerMatches — 1.14+ 細緻 header 比對

7.2 SNI（TLS 不解密的 hostname 匹配）

對 egress TLS 流量，不解密但根據 ClientHello 的 SNI 決定允不允許：

yaml
egress:
  - toPorts:
      - ports: [{ port: "443", protocol: TCP }]
        serverNames:
          - "one.one.one.one"
          - "*.example.com"

嘗試連 cilium.io 會被擋（SNI 不符），TLS handshake 階段直接被 reset。Client 看到 SSL error 立即失敗，不會 timeout。

7.3 gRPC

gRPC 跑在 HTTP/2 上，path 是 /，所以直接用 HTTP rules 寫：

yaml
ingress:
  - toPorts:
      - ports: [{ port: "50051", protocol: TCP }]
        rules:
          http:
            - method: POST
              path: "/myapp.UserService/(GetUser|ListUsers)"
              headers:
                - 'content-type: application/grpc'
⚠ Kafka rule deprecated

Cilium 早期有原生 Kafka rule（rules.kafka），1.18+ 已標記 deprecated 並會在未來版本移除。生產建議用 mTLS + auth 取代，或第六部 B 會講 alternative。

8. Deny Policy Deny

K8s 原生 NetworkPolicy 沒有顯式 deny（只能 allow list）。Cilium 提供 ingressDeny / egressDeny：

⚠ Deny 比 Allow 高優先級

Cilium 的 evaluation 順序：deny 先比，命中就 drop；deny 沒命中再看 allow。即使有 100 條 allow，只要任何一條 deny 命中，就是 deny。寫 deny 一定要明確且有意識。

典型用途

場景 1：保護敏感 service 不被任何 batch job 連

yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: protect-coreapi
  namespace: tenant-jobs
spec:
  endpointSelector:
    matchLabels: { app: coreapi }
  ingressDeny:
    - fromEndpoints:
        - matchLabels:
            "k8s:io.kubernetes.pod.namespace": jobs    # 整個 jobs namespace 全擋
  ingress:
    - fromEndpoints:
        - matchLabels: { app: web-api }
      toPorts:
        - ports: [{ port: "8080", protocol: TCP }]

場景 2：cluster-wide 擋 AWS metadata（避免 SSRF 取得 IAM credential）

yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: deny-aws-metadata
spec:
  endpointSelector: {}              # 全 cluster
  egressDeny:
    - toCIDR:
        - "169.254.169.254/32"      # AWS / Azure / GCP 通用 metadata IP

Deny 限制

  • Deny rule 只能 L3/L4，不能寫 L7（rules.http 之類）
  • 對 deny 流量 cilium 預設 silently drop；1.19 起可開 ICMP reply 讓 client 立即得知
  • 不要寫太籠統的 deny（如 fromEntities: [cluster]），會很難 debug

9. Host Policy（Node Firewall） Host

傳統 NetworkPolicy 只管 Pod。Cilium Host Policy 把同樣語法擴到整個 node 本身，等於把 Cilium 變成 node firewall。

啟用

bash
helm upgrade cilium oci://quay.io/cilium/charts/cilium \
  --version 1.19.3 --namespace kube-system --reuse-values \
  --set hostFirewall.enabled=true \
  --set devices='{eth0}'                # 在哪些介面攔

kubectl -n kube-system rollout restart ds/cilium

用 nodeSelector 取代 endpointSelector

Host Policy 必須是 CCNP（cluster-wide），且 spec 用 nodeSelector：

yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: lock-down-bastion-nodes
spec:
  nodeSelector:                          # 選 node，不是 pod
    matchLabels:
      role: bastion
  ingress:
    # 只允許辦公網 SSH
    - fromCIDR:
        - "10.100.0.0/16"
      toPorts:
        - ports: [{ port: "22", protocol: TCP }]
    # 允許 K8s control plane 內部通訊
    - fromEntities:
        - remote-node
        - kube-apiserver
      toPorts:
        - ports:
            - { port: "10250", protocol: TCP }     # kubelet
⚠ Host policy 一發即難改

如果寫錯 deny 把自己鎖在外（連 SSH 都進不去），復原很麻煩。務必先在 staging 完整測過。可先用 deny 之外的 allow list 看 hubble verdict，確認沒誤殺再 enforce。

10. Disk-based / Static Policy

Cilium 也支援把 policy 放在 node 檔案系統，不走 K8s API。優點是：node 啟動時即刻有 policy，不用等 K8s API 可達。缺點是要自己同步到每個 node。

啟用

yaml
# Helm value
extraArgs:
  - --static-cnp-path=/var/lib/cilium/policies/
bash
# 把 CNP YAML 放到 node 上
sudo mkdir -p /var/lib/cilium/policies
sudo cp my-static-policy.yaml /var/lib/cilium/policies/

# Cilium agent 啟動時自動載入；改檔案後要 SIGHUP 或重啟 agent

典型用法：bootstrap 階段的最低限度 policy（允許 cilium-agent 連 API server、允許 kubelet 拉 image），確保最壞情況下節點還能 ready。

11. 與 K8s NetworkPolicy 對照

Cilium 完整實作 K8s 原生 NetworkPolicy，所以你用 Calico/原生 K8s 的 YAML 直接拿來貼也會生效。對照表幫你決定何時用哪個：

能力K8s NPCilium CNP/CCNP
L3 endpoint selector✅✅
L4 ports/protocol✅✅
Port range✅ (k8s 1.25+)✅
Namespace selector✅✅
L7 HTTP / gRPC❌✅
DNS / FQDN❌✅
SNI 比對❌✅
Entities（world / host / kube-apiserver）❌✅
Deny rule❌✅
Cluster-wide❌✅ (CCNP)
Host firewall❌✅
ICMP / SCTP有限✅
跨 cluster (ClusterMesh)❌✅

建議：簡單 L4 zoning 可以繼續用 K8s NP（與其他 CNI 通用、團隊已熟）；任何 L7 / DNS / deny 需求一律走 CNP/CCNP。

12. Endpoint Lifecycle 與 Policy 套用時機

Pod 從建立到能跑流量會經歷幾個階段：

sequenceDiagram participant K as kubelet participant CNI as cilium-cni participant A as cilium-agent participant E as Envoy/BPF K->>CNI: create pod, give netns CNI->>A: ADD endpoint Note over A: 從 K8s API 取 pod labels A->>A: 計算 identity（hash labels） Note over A: 從 K8s API 找出 policy A->>E: 寫 BPF policy map A->>E: 若有 L7 rule，配置 Envoy listener A-->>CNI: endpoint ready CNI-->>K: pod IP 配發完成 Note over K: pod 開始接收流量

關鍵點：

  • Pod 啟動瞬間到 policy 套上有微秒到毫秒級延遲（看 cluster 大小與 policy 數量）
  • 這段「policy enforcement lag」期間，預設行為由 policyEnforcementMode 決定（default 模式下沒被任何 policy 選到的 pod 全 allow）
  • 1.19 改進：identity sync optimization 加快這個過程，特別是大型 cluster
  • 對極敏感 workload，可以用 cilium.io/no-track-port annotation 或 init container 等技巧確保 policy 就位才開始服務

13. 常見陷阱（生產踩過的）

陷阱症狀解
用 CIDR 試圖 match Pod IP 規則沒生效 CIDR 只匹配 unmanaged，Pod 要用 endpointSelector
跨 namespace 忘加 namespace label flow 被 drop 加 k8s:io.kubernetes.pod.namespace
toFQDNs 與 toEndpoints 寫在同一 egress policy schema error 拆兩條 egress entry
L7 rule 沒寫 toPorts policy 被拒 L7 必須掛在 toPorts 下
toServices 同時寫 toPorts policy 不如預期 兩者擇一，不能同時用
1.19 升級後跨 cluster policy 失效 flow 被 drop 用 cilium clustermesh inspect-policy-default-local-cluster 找出受影響 policy；明確加 io.cilium.k8s.policy.cluster
寫了 deny 結果連 DNS 都掛 所有 egress 慢 deny 優先級高於 allow；檢查 deny 是否誤殺 kube-dns 流量
L7 policy 對加密流量（如 Istio mTLS）無效 HTTP rule 沒套上 Cilium 看不到加密內容；Istio 整合場景參考第五部 §7
policyEnforcementMode=always 後新 pod 全斷 新 pod 連不出去 確保所有 namespace 都有 baseline policy 才切 always

14. 本章重點回顧

  • Cilium policy 不查 IP，查 identity（label hash）。
  • 三種資源：K8s NetworkPolicy（標準 L3/L4）、CiliumNetworkPolicy（namespace, 含 L7）、CiliumClusterwideNetworkPolicy（全 cluster, host policy 用）。
  • Enforcement mode：default（過渡用）→ always（成熟環境）。逐 namespace 加 default-deny + allow list 才換 always。
  • L3 寫 endpointSelector / fromEndpoints；跨 namespace 必須明寫 namespace label。
  • Entities 速記：world（外部）、cluster（本 cluster 內）、host（本機 host）、kube-apiserver。1.19 起 cluster 不含其他 cluster。
  • CIDR 只匹配 unmanaged endpoint，別拿來圈 Pod。多 policy 用 CiliumCIDRGroup 重用。
  • FQDN policy：必須先 allow DNS（53/UDP + rules.dns），再寫 toFQDNs；兩者不能同一 egress entry。1.19 支援 multi-level wildcard。
  • L4 寫 toPorts + ports 陣列，1.10+ 支援 port range；1.19 可對 deny 回 ICMP Destination unreachable。
  • L7 寫在 toPorts.rules.http/dns。SNI 規則用 serverNames。Kafka rule 已 deprecated。
  • Deny 優先級最高，務必精確。典型用法：保護敏感 service、cluster-wide 擋 cloud metadata IP。
  • Host Policy 用 CCNP + nodeSelector，把 Cilium 變 node firewall。
  • Disk-based policy 給 bootstrap baseline，避免 K8s API 不可用就無 policy。
