Chapter 01

Chaos Engineering 原理

2011 年，Netflix 的工程師把 Chaos Monkey 放進 production——一隻隨機殺掉 EC2 instance 的程式。理由很簡單：「如果我們不先打破它，客戶會替我們打破。」這個決定催生了整個 Chaos Engineering 學門。

Amazon CTO Werner Vogels 有句名言："Everything fails all the time." Chaos Engineering 把這句話從警告變成實踐——主動製造失敗，學習系統真實的容錯邊界，而不是等到凌晨三點讓客戶替你發現。

1.1　什麼是 Chaos Engineering

Chaos Engineering 是在系統上進行實驗的學門，目的是建立對系統在 turbulent conditions 下承受能力的信心（Principles of Chaos Engineering 官方定義）。它不是壞掉東西，而是在受控條件下測試假設。

!

Chaos Engineering ≠ 隨機破壞。核心差別在於：Chaos Engineering 有明確的 hypothesis（假設）、blast radius（爆炸半徑）控制、abort condition（中止條件），以及事後的觀察與學習。沒有這些的就只是在搞破壞。

1.3　五大核心原則

01
建立穩態行為的假設（Steady-State Hypothesis）
先定義「正常」長什麼樣——p99 latency、error rate、throughput。實驗前後都要量測穩態，偏離即代表失敗。
02
模擬真實世界事件（Real-World Events）
注入的故障要對應真實發生過的事：pod crash、network latency、磁碟滿、雲端 AZ 中斷。不要注入「絕對不會發生」的場景。
03
在 Production 執行（Run in Production）
Staging 不等於 Production。流量模式、資料量、第三方整合都不同。最終目標是在 production 做，但要漸進式、blast radius 受控。
04
持續自動化（Automate Experiments to Run Continuously）
一次性的 chaos 實驗沒有意義，因為系統持續演進。把實驗納入 CI/CD pipeline，讓它隨每次部署自動執行。
05
最小化爆炸半徑（Minimize Blast Radius）
從小開始。先在 namespace、再到 staging、再到 production 低流量時段。隨著信心增加逐步擴大範圍。
Chapter 02

Steady-State Hypothesis 與實驗設計

每一個 chaos 實驗都從一個可量測的假設開始。沒有假設的 chaos 就只是觀光——你在看系統壞掉，但沒有學到任何東西。

2.1　Steady-State Hypothesis 格式

一個好的 SSH（Steady-State Hypothesis）包含三個元素：

元素說明範例
Observable可量測的系統指標Payment API p99 latency
Baseline正常狀態下的值200ms 以下
Tolerance允許的最大偏差實驗期間不超過 500ms
steady-state-hypothesis.yaml · LitmusChaos 
steadyStateHypothesis:
  title: "Payment API 在 pod 刪除時維持可用性"
  probes:
    # HTTP probe：確認 API 持續回應
    - name: api-availability
      type: http
      tolerance: 200          # 期望 HTTP 200
      url: "http://payment-api.prod.svc/health"
      timeout: 5

    # Prometheus probe：確認 p99 latency 在容忍範圍內
    - name: p99-latency
      type: prometheus
      tolerance:
        type: range
        range:
          min: 0
          max: 500            # ms，不超過 500ms
      query: |
        histogram_quantile(0.99,
          sum(rate(http_request_duration_seconds_bucket{
            service="payment-api"
          }[1m])) by (le)
        ) * 1000

2.2　Blast Radius 控制

Blast radius（爆炸半徑）是「這個實驗最多能傷害多少東西」的度量。控制 blast radius 的四個維度：

  • Scope：限定 namespace、特定 label selector、單一 deployment。
  • Percentage：只影響 X% 的 pods，不是全部。
  • Duration：最長 N 分鐘，到期自動恢復。
  • Time Window：只在低流量時段執行（例如 UTC 02:00–04:00）。

2.3　Abort Condition 設計

每個實驗都必須有中止條件：當某個指標超過紅線，立即停止並自動恢復。

abort-condition · Chaos Mesh schedule 
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: payment-pod-kill
  namespace: chaos-testing
spec:
  action: pod-kill
  mode: fixed-percent
  value: "20"             # 最多殺 20% 的 pods
  selector:
    namespaces: [production]
    labelSelectors:
      app: payment-api
  duration: "5m"          # 5 分鐘後自動恢復

  # Chaos Mesh 2.x 支援 abort via StatusCheck
  # 若 error rate 超過 1%，自動中止實驗

Chapter 03

Kubernetes 上的 Chaos Engineering 概觀

Kubernetes 是目前最適合跑 chaos 實驗的平台。原因是它本身就是宣告式的——你用 YAML 描述期望狀態，chaos 實驗也用 YAML 描述，兩者天然對齊。加上 CRD（Custom Resource Definition）機制，可以直接把 chaos 實驗當成 K8s 原生資源管理。

3.1　Chaos Mesh vs LitmusChaos 架構比較

CNCF Incubating
Chaos Mesh
  • 架構：Controller Manager + DaemonSet (chaos-daemon) + Dashboard
  • 故障注入：eBPF + Linux 命名空間，不修改應用程式
  • 特色：IOChaos（磁碟）、NetworkChaos（eBPF 層）、HTTPChaos（HTTP proxy）
  • 安全模型：Namespace 隔離、admission webhook 驗證
  • 適合：K8s-only、需要精細網路/IO 控制
CNCF Incubating
LitmusChaos
  • 架構：Chaos Operator + ChaosCenter UI + ChaosHub
  • 故障注入：Go runner pods，跨環境（K8s、VM、雲端、bare metal）
  • 特色：ChaosHub（公開實驗市集）、Probes（自動驗證）、MCP Server（2026 新）
  • 安全模型：RBAC + SSO、多專案多租戶
  • 適合：跨環境、需要 ChaosHub 生態、AI 工作流整合

4.2　PodChaos：殺 pod

pod-kill.yaml · 殺掉 20% 的 payment-api pods 
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: payment-pod-kill
  namespace: chaos-testing
spec:
  action: pod-kill
  mode: fixed-percent
  value: "20"                   # 殺掉 20% 符合條件的 pods
  selector:
    namespaces: [production]
    labelSelectors:
      app: payment-api
  duration: "5m"                # 5 分鐘後自動恢復
  scheduler:
    cron: "@hourly"             # 每小時自動執行一次

4.3　NetworkChaos：注入網路延遲

network-latency.yaml · 對 payment-api 注入 200ms 延遲 
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: payment-network-delay
  namespace: chaos-testing
spec:
  action: delay
  mode: one                     # 只影響一個 pod
  selector:
    namespaces: [production]
    labelSelectors:
      app: payment-api
  delay:
    latency: "200ms"
    correlation: "25"           # 延遲有 25% 相關性（更真實）
    jitter: "50ms"              # ±50ms 抖動
  direction: to                 # 只影響進入流量
  target:
    selector:
      namespaces: [production]
      labelSelectors:
        app: payment-db
  duration: "10m"

4.4　StressChaos：CPU / Memory 壓力

stress-chaos.yaml · CPU hog 測試 HPA 反應 
apiVersion: chaos-mesh.org/v1alpha1
kind: StressChaos
metadata:
  name: payment-cpu-hog
  namespace: chaos-testing
spec:
  mode: fixed-percent
  value: "50"
  selector:
    namespaces: [production]
    labelSelectors:
      app: payment-api
  stressors:
    cpu:
      workers: 4                # 4 個 goroutine 占滿 CPU
      load: 80                  # 80% CPU 負載
    memory:
      workers: 2
      size: "256MB"             # 每個 worker 佔 256MB
  duration: "5m"

4.5　IOChaos：磁碟延遲

io-chaos.yaml · 對 Postgres 注入 100ms IO 延遲 
apiVersion: chaos-mesh.org/v1alpha1
kind: IOChaos
metadata:
  name: postgres-io-latency
  namespace: chaos-testing
spec:
  action: latency
  mode: one
  selector:
    namespaces: [production]
    labelSelectors:
      app: postgres
  delay: "100ms"                # 每次 IO 操作延遲 100ms
  volumePath: /var/lib/postgresql/data
  path: "**/*"                  # 影響所有檔案
  percent: 50                   # 影響 50% 的 IO 操作
  duration: "5m"

4.6　Schedule：定時實驗

schedule.yaml · 每小時執行一次 network chaos 
apiVersion: chaos-mesh.org/v1alpha1
kind: Schedule
metadata:
  name: hourly-network-chaos
  namespace: chaos-testing
spec:
  schedule: "5 * * * *"         # 每小時第 5 分鐘
  historyLimit: 5               # 保留最近 5 次紀錄
  concurrencyPolicy: Forbid     # 不允許同時執行多個
  type: NetworkChaos
  networkChaos:
    action: delay
    mode: one
    selector:
      namespaces: [staging]
      labelSelectors:
        tier: backend
    delay:
      latency: "100ms"
    duration: "12m"
⚠

RBAC 最小權限：Chaos Mesh 的 chaos-daemon 需要 privileged access 才能做 eBPF 注入。生產環境務必用 namespace 隔離、設定 allowedNamespaces，避免 chaos 實驗跨越邊界影響不該影響的服務。

5.2　三大核心 CRD

CRD職責由誰建立
ChaosEngine 連結目標應用與實驗；定義 scope、probe、execution 使用者 / GitOps
ChaosExperiment 實驗定義：runner image、env 參數、RBAC Operator（從 ChaosHub 拉取）

5.3　完整 ChaosEngine 範例（含 Probes）

chaos-engine.yaml · pod-delete with HTTP probe 
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine
metadata:
  name: payment-pod-delete
  namespace: production
spec:
  engineState: active
  appinfo:
    appns: production
    applabel: "app=payment-api"
    appkind: deployment
  chaosServiceAccount: litmus-admin
  experiments:
    - name: pod-delete
      spec:
        components:
          env:
            - name: TOTAL_CHAOS_DURATION
              value: "30"            # 30 秒
            - name: CHAOS_INTERVAL
              value: "10"            # 每 10 秒殺一次
            - name: FORCE
              value: "false"         # 優雅終止
            - name: PODS_AFFECTED_PERC
              value: "50"            # 影響 50% pods
        probe:
          # HTTP probe：持續確認 API 可用
          - name: api-health-check
            type: httpProbe
            mode: Continuous
            httpProbe/inputs:
              url: "http://payment-api.production.svc:8080/health"
              method:
                get:
                  criteria: "=="
                  responseCode: "200"
            runProperties:
              probeTimeout: 5
              interval: 5
              retry: 3
              probePollingInterval: 2

          # Command probe：確認至少 2 個 pods Running
          - name: pod-count-check
            type: cmdProbe
            mode: Edge
            cmdProbe/inputs:
              command: >
                kubectl get pods -l app=payment-api
                -n production --no-headers
                | grep Running | wc -l
              comparator:
                type: int
                criteria: ">="
                value: "2"
            runProperties:
              probeTimeout: 10
              interval: 5
              retry: 2

5.4　四種 Probe 類型

Probe用途Mode
httpProbeHTTP endpoint 健康確認SOT / EOT / Edge / Continuous
cmdProbeShell 指令輸出驗證SOT / EOT / Edge
k8sProbeK8s 資源狀態確認（pod count、deployment ready）SOT / EOT / Edge
promProbePrometheus query 結果驗證SOT / EOT / Edge / Continuous
!

Mode 說明：SOT（Start Of Test）= 實驗開始前跑；EOT（End Of Test）= 結束後跑；Edge = 前後都跑；Continuous = 整個實驗期間持續跑。監控服務可用性用 Continuous，驗證前後狀態用 Edge。

Chapter 06

工具選型決策

Chaos Mesh 和 LitmusChaos 都是 CNCF 的優質工具，選錯不會致命，但選對可以省很多力氣。

6.1　決策矩陣

場景建議工具理由
純 Kubernetes 環境、需要 network/IO 精細控制 Chaos Mesh eBPF 注入不需改 app、NetworkChaos/IOChaos 最完整
跨環境（K8s + VM + 雲端 + bare metal） LitmusChaos Litmus 支援非 K8s 目標，Chaos Mesh 僅限 K8s
需要 ChaosHub 生態、快速上手 LitmusChaos 數百個預建實驗，ChaosHub 是最大的 chaos 市集
多團隊、多租戶、需要 SSO LitmusChaos ChaosCenter 原生支援多專案、RBAC、SSO
已有 Grafana/Prometheus 觀測棧、輕量部署 Chaos Mesh 無狀態 controller、資源消耗低
AI 工作流整合（MCP client） LitmusChaos 2026 推出 MCP Server，Chaos Mesh 尚無

6.2　雙工具策略

成熟的 SRE 團隊常見的做法：Chaos Mesh 做底層網路/IO 故障注入，LitmusChaos 做 workflow 編排與 ChaosHub 實驗。兩者可以在同一個 ChaosWorkflow 中混用（如 Ch5.5 的範例）。

6.3　切換成本評估

!

兩個工具都用 CRD + YAML，語法不互通但概念可遷移。切換成本主要是：重新寫實驗 YAML（1–2 週）、重新調整 CI/CD 流程（3–5 天）、重新培訓團隊（1–2 天）。如果實驗數量少於 20 個，切換成本不高；超過 50 個則建議謹慎評估。

Chapter 07

GameDay 規劃

GameDay 是有劇本、有角色、有觀察的 chaos 演練。它結合了 chaos engineering 的技術實驗與 incident management 的流程演練——是驗證系統韌性與團隊反應能力的最有效手段。

7.1　GameDay vs Tabletop vs Chaos Experiment

活動有真實故障?有角色扮演?目標
Tabletop Exercise否（虛構情境）是測試流程與決策
Chaos Experiment是否測試系統韌性
GameDay是是同時測試系統與團隊

7.2　GameDay 流程

T-2週：規劃

  • 決定 GameDay 主題（例如：「database failover」、「network partition」）。
  • 定義目標系統、blast radius、abort condition。
  • 撰寫 SSH（Steady-State Hypothesis）。
  • 通知利害關係人（主管、客服、on-call 排班人員）。

T-1週：準備

  • 在 staging 跑一次 dry run，確認實驗語法正確。
  • 準備 rollback plan：每個故障注入都要有對應的 abort 指令。
  • 確認 observability：Grafana dashboard、Prometheus alert 都就位。

GameDay 當天流程

gameday-runbook.md · 當天流程 
## GameDay Runbook：Database Failover · 2026-05-20

**時間**：10:00–14:00 UTC
**環境**：Production（低流量時段）
**Facilitator**：@alice（SRE Lead）
**IC**：@bob（Incident Commander）

| 10:35 | 注入：模擬 DB connection pool 耗盡（停止 primary DB） |
| 11:00 | 停止所有故障注入，恢復期 |
| 11:30 | 確認穩態恢復 |
| 12:00 | Debrief 開始 |

### Abort 條件
- Payment error rate > 5%：立即停止所有 chaos，執行 rollback
- 任何 data integrity 問題：立即停止並呼叫 DBA

7.3　Debrief 問題框架

  • 系統層面：哪些 failure 是我們沒預期到的？哪些 circuit breaker 沒有觸發？
  • 團隊層面：決策有沒有延誤？IC 的指令清楚嗎？runbook 有沒有缺口？
  • 流程層面：通知節奏夠嗎？observability 能讓團隊快速找到問題嗎？
  • 學習層面：這次最重要的三個教訓是什麼？Action items 是什麼？

8.2　GitHub Actions 整合範例

.github/workflows/chaos-gate.yaml 
name: Chaos Engineering Gate

on:
  push:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build and unit test
        run: make test

  deploy-staging:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to staging
        run: kubectl apply -f k8s/staging/ --context staging

      - name: Wait for rollout
        run: |
          kubectl rollout status deployment/payment-api \
            -n staging --timeout=5m

  chaos-gate:
    needs: deploy-staging
    runs-on: ubuntu-latest
    steps:
      - name: Apply ChaosEngine
        run: |
          kubectl apply -f chaos/staging-pod-delete.yaml \
            --context staging

      - name: Wait for experiment
        run: |
          kubectl wait chaosresult/payment-pod-delete-pod-delete \
            -n staging \
            --for=jsonpath='{.status.experimentStatus.verdict}'=Pass \
            --timeout=5m

      - name: Check verdict
        run: |
          VERDICT=$(kubectl get chaosresult \
            payment-pod-delete-pod-delete \
            -n staging \
            -o jsonpath='{.status.experimentStatus.verdict}')
          echo "Chaos experiment verdict: $VERDICT"
          if [ "$VERDICT" != "Pass" ]; then
            echo "Chaos gate FAILED — blocking deploy"
            exit 1
          fi

      - name: Cleanup
        if: always()
        run: |
          kubectl delete chaosengine payment-pod-delete \
            -n staging --ignore-not-found

  deploy-production:
    needs: chaos-gate
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to production
        run: kubectl apply -f k8s/production/ --context production

9.3　與 APM / Tracing 整合

把 chaos 實驗的時間窗口和 distributed tracing 結合，可以看到故障注入如何影響 request 路徑：

  • 在 Jaeger/Tempo 搜尋實驗期間的 error traces，找到真正的 failure point。
  • 確認 circuit breaker、retry、fallback 是否在 trace 中正確觸發。
  • 找出「ghost latency」——某些 request 因為 retry 而時間拉長，但最終成功。
Chapter 10

從測試環境到生產環境

大多數團隊卡在「永遠只在 staging 跑」的階段。Staging 的問題是：流量模式不一樣、依賴的第三方可能是 mock、資料量可能是生產的 1/100。只在 staging 跑的 chaos 實驗給你的是錯誤的信心。

10.3　Stakeholder Buy-in 策略

工程師已經相信 chaos 的價值，但主管和其他團隊還沒有。推進 production chaos 需要：

  • 先秀成果：在 staging 找到一個真實的 bug，展示「沒有 chaos 實驗，這個 bug 會在凌晨三點爆給客戶」。
  • 量化風險：「過去 12 個月有 3 次事故是這類 failure 造成的，合計影響 N 小時 SLA」。
  • 清楚的 abort 機制：讓主管知道「一旦錯誤率超過 1%，chaos 自動停止，不需要人工介入」。
  • 第一次 GameDay 邀請主管觀摩：親眼看到系統在受控故障下正常運作，比任何 slide 都有說服力。
✓

結語：Chaos Engineering 的終極目標不是找到 bug，而是建立對系統的信心。當你的團隊說「我們可以部署這個，因為 chaos 實驗證明它能承受 pod failure 和 network partition」，這才是 chaos engineering 真正帶來的價值。這份信心，是任何靜態測試、code review、staging 環境都給不了的。
