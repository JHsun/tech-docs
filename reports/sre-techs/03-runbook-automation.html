Chapter 01

Runbook 基礎

Runbook 是 SRE 工具箱裡最容易被低估、也最容易腐爛的東西。寫得好的 Runbook 讓新進工程師在凌晨三點也能獨立處理事故；沒人維護的 Runbook 比沒有 Runbook 更危險——它給了錯誤的信心。

1.1　Runbook vs Playbook vs SOP

名詞粒度目的典型長度
SOP（Standard Operating Procedure） 最粗 定義整個操作流程的框架與原則 數頁～數十頁
Playbook 中 針對特定情境的決策框架（if X then Y） 1–5 頁
Runbook 最細 針對特定任務的逐步操作指南，可直接執行 0.5–2 頁
!

一句話記法：Playbook 告訴你「遇到資料庫問題要怎麼決策」；Runbook 告訴你「執行資料庫 failover 的步驟 1、2、3」。一個事故可能對應一個 Playbook（決策框架）和多個 Runbook（各種具體操作）。

1.2　三種自動化等級

等級名稱說明適用場景
L1 Procedural / Manual 純文字步驟，人工執行每個指令 新流程、高風險、需要人類判斷
L2 Executable / Semi-automatic 部分步驟自動執行，關鍵節點需人工確認 成熟流程、有驗證機制、降低人為失誤
L3 Fully Automated 全程自動執行，僅在異常時呼叫人 高度重複、低風險、有完整 rollback

1.3　為什麼 Runbook 能降低 MTTR

MTTR（Mean Time To Resolve）由三段組成：detect → triage → remediate。Runbook 主要壓縮 triage 和 remediate 兩段：

  • Triage 加速：Runbook 提供「先看哪裡、問哪些問題」的決策路徑，不需要工程師從零開始思考。
  • Remediate 加速：有驗證過的步驟和指令，不需要現場查文件或記指令。
  • 知識民主化：不需要 oncall 碰巧是「知道這個系統」的那個人。
  • 一致性：每次以相同方式處理相同問題，避免「今天有效、明天沒效」。
Chapter 02

Runbook 設計原則

2.1　Concise but Self-contained

Runbook 最常見的失敗模式有兩種：太短（「重啟服務」，但沒說怎麼確認成功）和太長（把整份架構文件貼進去）。 好的 Runbook 必須在不需要跳出去查其他文件的前提下，讓執行者完成任務。

  • 每個步驟只做一件事。
  • 每個指令後面有「預期輸出」或「如何確認成功」。
  • 把架構背景放在 Runbook 的 header，不要讓人中途去查另一份文件。
  • 連結到相關 dashboard、log query、escalation contact——但不要把它們的內容整個搬進來。

2.2　先手動跑一次，再自動化

Google SRE 和 SolarWinds 的建議一致：在自動化一個步驟之前，至少手動執行過一次。理由：

  • 手動執行會發現「指令在 production 和 staging 行為不同」的問題。
  • 手動執行能確認 validation 步驟（「如何知道這個步驟成功」）。
  • 自動化後很難發現「automation 在某個邊緣案例靜默失敗」。

  • 決策樹：幫助 oncall 在多個選項間快速選擇。

  • 預期輸出範例：「成功時 terminal 應該顯示 X」比「確認成功」具體。
Chapter 03

Runbook 模板與結構

3.1　標準模板欄位

runbook-template.md · 標準模板 
# RB-042 Payment API — DB Connection Pool 耗盡

| 欄位 | 值 |
|---|---|
| ID | RB-042 |
| 服務 | payment-api |
| 版本 | 1.3.0 |
| 觸發條件 | Alert: PaymentDBPoolExhausted |
| 嚴重度 | P1 / P2 |
| 預估執行時間 | 10–15 分鐘 |
| Owner | @alice (Platform SRE) |
| 上次更新 | 2026-04-15 |
| 下次審核 | 2026-07-15 |

## 背景
Payment API 使用 PgBouncer connection pooler，pool size 預設 50。
在流量尖峰期 pool 耗盡時，新請求會排隊或 timeout。

## 相關連結
- Dashboard: https://grafana.example.com/d/payment-api
- Alert rule: https://prom.example.com/alerts#PaymentDBPoolExhausted
- 架構文件: https://wiki.example.com/payment-arch

## 前置條件 (Pre-conditions)
- [ ] 確認你有 payment-api namespace 的 kubectl 存取權限
- [ ] 確認 Slack channel #inc-xxx 已建立
- [ ] 通知 DBA 待命（如果需要 DB 層操作）

## 症狀
- Payment API p99 latency 超過 1s
- Prometheus alert `PaymentDBPoolExhausted` 觸發
- Log 出現 `too many connections` 或 `connection pool exhausted`

## 診斷步驟

### Step 1：確認 pool 狀態
```bash
kubectl exec -n production deploy/pgbouncer -- \
  psql -p 6432 pgbouncer -c "SHOW POOLS;"
```
預期：`cl_active` 欄位接近或等於 `pool_size` 的值

### Step 2：查看目前連線數
```bash
kubectl exec -n production deploy/payment-api -- \
  curl -s localhost:9090/metrics | grep db_pool
```

### Step 3：確認流量尖峰
在 Grafana 確認 payment-api QPS 是否異常升高。

## 修復步驟

### 選項 A：暫時增加 pool size（立即生效）
```bash
kubectl exec -n production deploy/pgbouncer -- \
  psql -p 6432 pgbouncer -c "SET pool_size=100;"
# 注意：重啟後會恢復，需同時更新 ConfigMap
```

### 選項 B：更新 ConfigMap 並 rolling restart
```bash
# 編輯 pool_size
kubectl edit configmap pgbouncer-config -n production
# 找到 pool_size=50，改為 pool_size=100

# Rolling restart
kubectl rollout restart deploy/pgbouncer -n production
kubectl rollout status deploy/pgbouncer -n production --timeout=3m
```

## 驗證
```bash
# 確認 pool 可用連線增加
kubectl exec -n production deploy/pgbouncer -- \
  psql -p 6432 pgbouncer -c "SHOW POOLS;"
# 確認 payment API 錯誤率恢復正常
curl -s https://api.example.com/health | jq .db
```
預期輸出：`{"db": "connected", "pool_available": true}`

## Rollback
```bash
# 若 pool size 增加後反而造成 DB 過載，恢復預設
kubectl edit configmap pgbouncer-config -n production
# pool_size 改回 50
kubectl rollout restart deploy/pgbouncer -n production
```

## 升級條件
若以上步驟 15 分鐘內無法解決，請呼叫 DBA oncall。

3.2　命名與版本管理

  • ID 格式：RB-{service}-{sequence}，如 RB-PAYMENT-042。
  • 語意化版本：major.minor.patch — major 代表流程有根本改變，minor 代表新增步驟，patch 代表文字修正。
  • Changelog：每次更新附上一行說明（為什麼改、改了什麼）。
  • 下次審核日期：強制每季檢視，過期 Runbook 自動標記為 STALE。
Chapter 04

三世代演進

Runbook 自動化不是一步到位的，而是隨著團隊成熟度漸進演進。2026 年 incident.io 把這個演進分為三個世代。

Gen 1 · 2010s
Static Runbook
  • Confluence / Notion / Wiki 靜態頁面
  • 人工閱讀、人工執行每個步驟
  • 容易過期、在壓力下常被跳過
  • 沒有執行紀錄、沒有版本控制
Gen 2 · 2018–2023
Executable Runbook
  • Shell script / Ansible / Terraform
  • 部分步驟自動化，關鍵點仍需確認
  • 有執行 log，但沒有 context
  • 與 incident 流程脫節
Gen 3 · 2024–now
Intelligent Runbook Execution
  • Context-aware：知道哪個 service、哪個 team
  • Human-in-the-loop：自動處理例行步驟，人類做判斷
  • 與 incident management 深度整合
  • AI 建議下一步；audit trail 自動生成

4.1　Gen 3 的核心特徵

2026 年的 Intelligent Runbook Execution（IRE）有幾個標誌性能力：

  • Service Catalog 整合：alert → service → team → oncall → 對應 runbook，全部自動串聯，不需要人工判斷「要跑哪個 runbook」。
  • Slack-native 執行：在 incident channel 內直接 /runbook run payment-db-failover，不需要開另一個 terminal 或 web console。
  • Immutable audit trail：每個步驟的執行時間、執行者、輸出都自動寫入 incident timeline，SOC 2 稽核直接用。
  • AI 協作：根據 incident 的症狀、歷史相似事故、當前系統狀態，AI 建議最可能有效的 runbook 和參數。
Chapter 05

自動化五大設計原則

5.1　Idempotence（冪等性）

Idempotent：執行一次和執行 N 次的結果相同。這是自動化 Runbook 最重要的設計原則，因為在 incident 壓力下，runbook 常常被重複執行。

bash · idempotent vs non-idempotent 
# BAD：非冪等，執行兩次會建立兩個資源
kubectl create namespace chaos-testing

# GOOD：冪等，exists 就略過
kubectl create namespace chaos-testing --dry-run=client -o yaml \
  | kubectl apply -f -
# 或
kubectl get namespace chaos-testing 2>/dev/null \
  || kubectl create namespace chaos-testing

# BAD：非冪等，每次執行都增加 replicas
kubectl scale deploy/payment-api --replicas=+2

# GOOD：冪等，設定絕對值
kubectl scale deploy/payment-api --replicas=6

# BAD：非冪等的 DB migration
ALTER TABLE orders ADD COLUMN retry_count INT DEFAULT 0;

# GOOD：冪等的 DB migration
ALTER TABLE orders ADD COLUMN IF NOT EXISTS retry_count INT DEFAULT 0;

5.2　Parameterization（參數化）

避免把環境名稱、namespace、服務名稱寫死在 Runbook 裡。用參數讓同一個 Runbook 可以跨環境重用：

runbook-high-memory.yaml · 參數化範例 
apiVersion: runbooks/v1
kind: Runbook
metadata:
  name: high-memory-pod-remediation
  version: "1.2.0"
  owner: platform-team

# 可在執行時覆寫的參數
parameters:
  - name: namespace
    type: string
    required: true
    description: "目標 namespace"
  - name: deployment
    type: string
    required: true
    description: "目標 deployment 名稱"
  - name: memory_threshold_mb
    type: integer
    default: 512
    description: "觸發補救的記憶體閾值 (MB)"
  - name: max_restarts
    type: integer
    default: 3
    description: "最大 rolling restart 次數"

# 觸發條件
trigger:
  type: alert
  alertName: PodMemoryHigh
  # 只自動跑在非關鍵 namespace
  conditions:
    - field: namespace
      operator: notIn
      values: ["production-critical", "payment-processing"]

steps:
  - id: check-memory
    name: "確認記憶體用量"
    action: kubectl-exec
    params:
      command: "kubectl top pods -n {{ namespace }} -l app={{ deployment }}"

  - id: rolling-restart
    name: "Rolling restart"
    action: kubectl-rollout-restart
    params:
      namespace: "{{ namespace }}"
      deployment: "{{ deployment }}"
    approval:
      required: "{{ namespace == 'production' }}"  # production 需要審批

  - id: verify
    name: "驗證重啟後記憶體正常"
    action: wait-and-check
    params:
      wait_seconds: 60
      check: "kubectl top pods -n {{ namespace }} | grep {{ deployment }}"

5.3　Auditability（可稽核性）

每次 Runbook 執行都必須留下不可竄改的執行紀錄：

  • 執行者：誰觸發（人工 or 系統）、何時觸發。
  • 參數：當次執行使用的確切參數值。
  • 步驟輸出：每個步驟的 stdout/stderr。
  • 結果：成功、失敗、或人工中止。

這份 audit trail 不只是合規需求（SOC 2、ISO 27001、DORA 都要求），也是事後 postmortem 的重要素材——「runbook 第三步執行了什麼、輸出是什麼」往往能解釋為什麼問題惡化或解決。

5.4　Observability（可觀測性）

自動化 Runbook 本身也需要被監控：

prometheus-metrics · runbook 執行監控 
# 關鍵 metrics
runbook_executions_total{runbook, status}   # 總執行次數（success/failure/aborted）
runbook_duration_seconds{runbook}           # 執行時間分布
runbook_step_failures_total{runbook, step}  # 哪一步最常失敗
runbook_approval_wait_seconds{runbook}      # 等待人工審批的時間

# Alert 範例：runbook 成功率低於 80%
- alert: RunbookHighFailureRate
  expr: |
    rate(runbook_executions_total{status="failure"}[1h])
    /
    rate(runbook_executions_total[1h]) > 0.2
  for: 30m
  labels:
    severity: P2
  annotations:
    summary: "Runbook {{ $labels.runbook }} 失敗率超過 20%"

5.5　Failure Handling（失敗處理）

自動化 Runbook 的失敗處理策略：

失敗類型策略範例
暫時性失敗 Retry with exponential backoff API 暫時 503，等 5s/10s/20s 後重試
步驟失敗（可回滾） 自動 Rollback 到上一個已知良好狀態 Deployment rollback
步驟失敗（不可回滾） 暫停並呼叫人類介入 資料遷移到一半
超時 Abort + 通知 + 保留中間狀態供人工確認 Rolling restart 超過 10 分鐘

6.2　Approval Gates（審批關卡）

不是所有步驟都需要審批，但某些操作必須有人確認才能執行：

approval-config.yaml 
approvals:
  # Production rolling restart 需要 primary oncall 批准
  - name: production-restart-approval
    trigger:
      step: rolling-restart
      conditions:
        - "context.environment == 'production'"
    workflow:
      type: sequential
      timeout: 15m                # 15 分鐘沒人批，自動升級
      escalation:
        - after: 5m
          notify: ["oncall-secondary"]
        - after: 10m
          notify: ["engineering-manager"]
    approvers:
      - type: role
        value: oncall-primary
        required: true
      - type: team
        value: platform-team
        minApprovals: 1
    channels:
      - type: slack
        channel: "#incidents"
    actions:
      approve:
        - label: "Approve Restart"
          style: primary
      reject:
        - label: "Reject - Investigate First"
          requiresComment: true

  # 緊急狀況：允許 SRE Admin 繞過審批
  - name: emergency-bypass
    type: override
    permissions:
      - role: runbook-admin
    audit:
      required: true
      justification: true        # 必須填寫理由

6.3　Secret 管理

Runbook 執行時常需要存取 credential，不能把 secret 硬寫在 Runbook 裡：

bash · Secret 存取範例（Vault / K8s Secret） 
# BAD：把 credential 寫死
DB_PASSWORD="super-secret-123"
psql -h db.example.com -U admin -p "$DB_PASSWORD" ...

# GOOD：從 Vault 動態取得短期 credential
DB_CRED=$(vault read -format=json database/creds/payment-role)
DB_USER=$(echo $DB_CRED | jq -r .data.username)
DB_PASS=$(echo $DB_CRED | jq -r .data.password)
psql -h db.example.com -U "$DB_USER" -p "$DB_PASS" ...
# Vault lease 到期後 credential 自動失效

# GOOD：從 K8s Secret 取得
DB_PASS=$(kubectl get secret payment-db-creds \
  -n production -o jsonpath='{.data.password}' | base64 -d)
⚠

Principle of Least Privilege：Runbook 執行所用的 service account 只應有執行該 Runbook 所需的最小權限。如果 failover runbook 只需要 restart deployment，它的 SA 就不應該有 delete namespace 的權限。每個 Runbook 用獨立的 SA。

7.2　Service Catalog 映射

Service Catalog 是 Gen 3 Runbook 的核心——它建立了 alert → service → team → runbook 的映射：

service-catalog.yaml · 服務目錄範例 
services:
  - name: payment-api
    tier: P1                        # 服務重要性
    owner: payment-team
    oncall_schedule: payment-primary
    runbooks:
      - alert: PaymentAPIHighLatency
        runbook: RB-PAYMENT-001
        auto_trigger: false         # 需人工確認才執行
      - alert: PaymentDBPoolExhausted
        runbook: RB-PAYMENT-042
        auto_trigger: true          # 自動觸發（低風險）
        conditions:
          - "environment != 'production-critical'"
      - alert: PaymentPodCrashLoop
        runbook: RB-PAYMENT-055
        auto_trigger: false
    dashboards:
      - name: "Payment Overview"
        url: "https://grafana/d/payment-overview"
    dependencies:
      - postgres-primary
      - redis-cache
      - stripe-api

7.4　PagerDuty / incident.io 整合

pagerduty-webhook.py · 自動觸發 runbook 
import json
import requests

def handle_pagerduty_webhook(event):
    """PagerDuty webhook handler — 根據 alert 自動觸發 runbook"""
    alert_name = event.get("alert", {}).get("summary", "")
    service = event.get("service", {}).get("name", "")

    # 查詢 Service Catalog
    runbook = lookup_runbook(service, alert_name)
    if not runbook:
        return

    # 若是低風險、設定了 auto_trigger，自動執行
    if runbook.get("auto_trigger") and not is_production_critical(service):
        trigger_runbook(
            runbook_id=runbook["id"],
            params={
                "namespace": get_namespace(service),
                "deployment": service,
            },
            triggered_by="pagerduty-automation",
            incident_id=event["id"],
        )
        post_to_slack(
            channel=f"#inc-{event['id']}",
            message=f"Auto-triggered runbook `{runbook['id']}` "
                    f"for alert `{alert_name}`"
        )
    else:
        # 否則只推薦，不自動執行
        post_to_slack(
            channel=f"#inc-{event['id']}",
            message=f"Suggested runbook: `{runbook['id']}` "
                    f"({runbook['name']})\n"
                    f"Run with: `/runbook run {runbook['id']}`"
        )

實作範例

8.1　範例一：K8s High Memory Pod 自動補救

最常見的 Runbook 自動化情境——pod 記憶體過高時自動重啟：

runbook-high-memory.yaml · 完整自動化範例 
apiVersion: runbooks/v1
kind: Runbook
metadata:
  name: high-memory-pod-remediation
  version: "1.2.0"
  owner: platform-team
  lastUpdated: "2026-01-30"
  tags: [kubernetes, memory, auto-remediation]

trigger:
  type: alert
  source: prometheus
  alertName: PodMemoryHigh
  conditions:
    - field: namespace
      operator: notIn
      values: ["production-critical", "payment-processing"]

parameters:
  - name: namespace
    type: string
    required: true
  - name: deployment
    type: string
    required: true
  - name: maxRestarts
    type: integer
    default: 3

steps:
  - id: check-current-memory
    name: "查看目前記憶體用量"
    action: shell
    command: |
      kubectl top pods -n {{ namespace }} \
        -l app={{ deployment }} --no-headers
    onFailure: continue          # 失敗了繼續跑，只是記 log

  - id: check-restart-count
    name: "確認重啟次數未超標"
    action: shell
    command: |
      COUNT=$(kubectl get pods -n {{ namespace }} \
        -l app={{ deployment }} \
        -o jsonpath='{.items[0].status.containerStatuses[0].restartCount}')
      echo "Current restart count: $COUNT"
      [ "$COUNT" -lt "{{ maxRestarts }}" ]
    onFailure: abort             # 超標就不自動重啟，升級給人

  - id: rolling-restart
    name: "Rolling restart"
    action: kubectl-rollout-restart
    approval:
      required: "{{ namespace == 'production' }}"
    params:
      namespace: "{{ namespace }}"
      deployment: "{{ deployment }}"
    onFailure: rollback

  - id: wait-and-verify
    name: "等待並驗證記憶體恢復"
    action: shell
    command: |
      kubectl rollout status deploy/{{ deployment }} \
        -n {{ namespace }} --timeout=3m
      sleep 60
      kubectl top pods -n {{ namespace }} -l app={{ deployment }}
    onFailure: escalate

rollback:
  steps:
    - action: kubectl-rollout-undo
      params:
        namespace: "{{ namespace }}"
        deployment: "{{ deployment }}"

escalation:
  notify: ["oncall-primary", "platform-team"]
  message: "Runbook high-memory-pod-remediation 失敗，需人工介入"

8.3　範例三：資料庫 Failover Runbook

RB-DB-010-postgres-failover.sh · 半自動化 
#!/usr/bin/env bash
# RB-DB-010 · PostgreSQL Primary Failover
# 執行前提：已確認 primary 不可恢復，replica 同步狀態正常
set -euo pipefail

NAMESPACE="${NAMESPACE:-production}"
PRIMARY="${PRIMARY:-postgres-primary}"
REPLICA="${REPLICA:-postgres-replica-0}"

echo "[1/5] 確認 replica 同步落後量..."
kubectl exec -n "$NAMESPACE" "$REPLICA" -- \
  psql -U postgres -c "SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn();"

echo ""
read -r -p "Replica 落後量可接受？繼續 failover？(yes/no): " CONFIRM
[ "$CONFIRM" != "yes" ] && { echo "已取消"; exit 1; }

echo "[2/5] 停止 primary（若尚可連線）..."
kubectl scale deploy/"$PRIMARY" --replicas=0 -n "$NAMESPACE" 2>/dev/null || true

echo "[3/5] 將 replica 提升為 primary..."
kubectl exec -n "$NAMESPACE" "$REPLICA" -- \
  pg_ctl promote -D /var/lib/postgresql/data

echo "[4/5] 更新 Service selector 指向新 primary..."
kubectl patch svc postgres-service -n "$NAMESPACE" \
  -p '{"spec":{"selector":{"role":"replica-0"}}}'

echo "[5/5] 驗證連線..."
kubectl exec -n "$NAMESPACE" deploy/payment-api -- \
  psql "$DATABASE_URL" -c "SELECT 1;"

echo ""
echo "Failover 完成。請："
echo "  1. 更新 postmortem 記錄 failover 時間與原因"
echo "  2. 監控 replication lag（若後續需設 replica）"
echo "  3. 通知 DBA 確認資料完整性"

  pull_request:
    paths: ["runbooks/**"]

9.3　合規對接（SOC 2 / ISO 27001 / DORA）

現代合規框架都要求有文件化且可測試的事故回應流程：

  • SOC 2：需要「incident response procedures documented and tested」。Runbook 執行的 audit trail + 季度 GameDay 演練記錄，直接作為 evidence。
  • ISO 27001：A.16 Incident Management 要求回應程序文件化。Runbook repo + 執行記錄 = 符合要求。
  • DORA（EU）：要求 ICT incident management policy，Runbook 是最直接的落地方式。

Chapter 10

量測與持續改進

10.1　Runbook 健康指標

Execution Success Rate
success / total
Runbook 執行成功率。低於 80% 代表 Runbook 本身有問題，需要修。
MTTR Impact
MTTR_after - MTTR_before
引入 Runbook 後 MTTR 的改善量。量化 Runbook 的業務價值。
Toil Reduction
manual_mins - auto_mins
每次事故節省的人工操作時間。目標：讓工程師從重複勞動中解放。
Staleness Rate
stale / total
超過審核日期未更新的 Runbook 比例。理想 < 10%。
Coverage
alerts_with_rb / alerts_total
有對應 Runbook 的 alert 比例。從 P1/P2 開始，目標 100%。
Approval Latency
approve_ts - request_ts
人工審批等待時間。過長代表審批流程設計不合理。

10.2　七天快速啟動計畫

如果你的團隊還在 Gen 1（Wiki 靜態頁面），以下是七天把 Runbook 推進到 Gen 2 的實用計畫（來自 SRE School 2026）：

天任務

10.3　GameDay 驗證 Runbook

每季用 GameDay 驗證 Runbook（詳見 Vol. 02 Ch. 7）。重點是：

  • 真實執行 Runbook，不只是「走讀」步驟。
  • 讓沒寫過這份 Runbook 的工程師執行，才能發現文字不清楚的地方。
  • 計時每個步驟，找出瓶頸。
  • 執行後強制更新 Runbook（即使內容沒變，也更新「上次驗證日期」）。
