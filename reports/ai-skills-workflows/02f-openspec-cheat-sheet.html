overview.md — 核心概念一頁通

五大概念（整個心智模型）

#概念說明
1Specs 是真相openspec/specs/ 描述系統現在的行為，按領域組織（auth/、payments/）。由 requirement（SHALL 描述）+ scenario（given/when/then 實例）組成
2一個 change = 一個工作單位openspec/changes/ 下每資料夾就是一件事：proposal、design、tasks、delta specs
3Delta specs 描述「改變」不重寫整份 spec，只寫 ADDED/MODIFIED/REMOVED 的差異——這是 OpenSpec 擅長既有系統的關鍵
4Artifacts 彼此疊加proposal(why) → specs(what) → design(how) → tasks(steps) → implement。隨時可回頭改任何一份
5歸檔把 change 摺回真相archive 後 delta specs 合併回主 specs，change 移到 changes/archive/（附日期戳）
一句話總結：先取得共識，再有信心地動手（agree first, then build confidently）。

Artifact 依賴鏈

proposal→specs→design→tasks→implement

依賴是「enabler（啟用器）」不是「gate（閘門）」——缺依賴只代表還沒準備好，不阻擋你回頭修改已完成的文件。

explore.md — 先探索再承諾

/opsx:explore 是什麼（與不是什麼）

Explore 是對話，不是產生器。

它會做

  • 讀取並搜尋程式碼庫回答真實問題
  • 比較選項並點出各自取捨
  • 畫圖讓設計可讀
  • 把模糊想法收斂成具體、可實作的範圍
  • 準備好時轉入 /opsx:propose

它不會做

  • 建立 change 資料夾
  • 寫任何 artifact（proposal/specs/design/tasks）
  • 寫或改程式碼
探索不花成本、不綁定承諾。你可以探索三個死路、各自學到東西，最後只提出存活的那條路。核心 profile 已預設安裝。
writing-specs.md — 寫好規格

核心原則

  • Spec 是行為，不是程式碼——描述系統「做什麼」，不描述「怎麼實作」。
  • 好 requirement：用 MUST/SHALL，可測試、無歧義（例：系統 SHALL 在 30 分鐘後讓 session 過期）。
  • 好 scenario：GIVEN / WHEN / THEN 三要素，具體可重現。
### Requirement: Session Timeout
The system SHALL expire sessions after 30 minutes.

#### Scenario: Inactivity timeout
- GIVEN a logged-in user
- WHEN no activity for 30 minutes
- THEN their session expires

選對 Delta 類型・控制變更大小

  • 依變更性質選 ADDED/MODIFIED/REMOVED/RENAMED（不要一律 ADDED）。
  • Right-size：一個 change 聚焦單一可審查的工作，太大就拆。
  • 讓 AI 先起草，你再引導收斂——不是直接接受第一版。
editing-changes.md — 編輯與迭代變更

兩種編輯方式

方式做法
直接編輯檔案修改 openspec/changes/<name>/ 下的 proposal/spec/design/tasks 檔案
指令式修訂用 /opsx:update 讓 AI 修訂 artifacts 並保持彼此一致

常見問題

情境解法
開始後想改 proposal/specs直接編輯檔案，或用 /opsx:update 修訂
實作後想回頭再審查用 /opsx:verify 檢查完成度/正確性/一致性
手動改了程式碼回填/更新 tasks 勾選與 delta specs，讓規格反映實作現實
對 proposal 不滿意就地反覆修，不必另開新 change
何時「更新既有 change」vs「另開新 change」：當範圍根本改變、或與另一項工作無關時，才另開新 change。
reviewing-changes.md — 審查變更

兩個審查時機

  • 規劃時（寫完 proposal/specs/tasks，尚未實作）：判斷「對的問題」與「對的完成定義」。
  • 程式碼後（實作完）：用 /opsx:verify 驗證。

閱讀順序 + 兩分鐘檢查清單

依序讀：proposal（這是不是對的問題？）→ spec deltas（「完成」定義是否正確？）→ tasks（工作計畫是否合理？）。

  • 問題選對了嗎？「完成」有客觀定義嗎？
  • delta 操作（ADDED/MODIFIED/REMOVED）用對了嗎？
  • task 有涵蓋所有 scenario 的測試嗎？
  • review 要 right-size：小變更走快速檢查，大變更才逐條深讀。
規劃階段推翻很便宜（只是文字）；實作後才推翻很貴。審查要趁早。
team-workflow.md — 團隊協作

一條鐵律：OpenSpec 不碰 git

OpenSpec 只在 openspec/ 下讀寫純 Markdown，絕不 commit、branch、push、pull，也絕不自行 clone/sync store。

  • openspec/ 像原始碼一樣納入版本控制（commit 整個資料夾）。
  • 一個 change 就是一個可版本化的資料夾，在分支上就是一堆檔案。
  • 以下流程全是「慣例」不是「強制」——OpenSpec 不會逼你。

日常循環・PR 審查・並行

  • 日常循環：開 change → 實作 → archive，每天合併規格。
  • PR 審查：把 delta specs 的 diff 當 PR 的一部分審。
  • 並行變更：兩人各開各的 change，archive 時若碰同一份 spec 需合併。
  • 規劃超出單一 repo：改用 store（見下方 stores-beta）。
existing-projects.md — 既有專案導入

Delta-first 是整個訣竅

OpenSpec 專為 brownfield（既有程式碼庫）設計：你不需要回頭把整份系統寫成 spec，只要在每次變更時寫差異（delta）。規格隨開發自然成長。

  • 30 秒版：openspec init → 開第一個 change → 寫 delta → 實作 → archive。
  • 想有人帶路：用 /opsx:onboard（約 15 分鐘互動式教學，用真實程式碼庫）。
  • 已有需求文件：不用全搬，從「下一個變更」開始寫 delta 即可。
誠實提醒：大程式庫組織 specs 需要紀律；monorepo 跨 repo 的工作考慮 store。別想一次把全部系統規格化——漸進。

troubleshooting.md・glossary.md・faq.md

常見問題（troubleshooting.md 精選）

問題解法
openspec: command not found確認全域安裝、PATH 指向正確版本（舊版可能 shadowing）
「Requires Node.js 20.19.0」升級 Node；用 nvm/fnm 時告知版本管理器而非自行改 PATH

FAQ 重點

  • 一定要用 OpenSpec 做所有事嗎？ 不用——小改動可直接做，重要變更再走 spec。
  • 只能在專案 repo 內用嗎？ 可跨 repo，用 store（beta）。
  • 一定要跑 /opsx:sync 嗎？ 通常不用——/opsx:archive 會自動幫你合併；只有長期變更想先合併時才手動 sync。
  • skill 與 command 差別？ skill 是通用 workflow 描述；command 是工具專屬斜線指令。
  • 推薦模型：Codex 5.5 與 Opus 4.7（規劃與實作皆宜），並保持乾淨的上下文視窗。

Glossary 核心名詞

  • Spec：系統行為的單一真實來源（requirements + scenarios）。
  • Change：一個工作單位（proposal + delta specs + design + tasks）。
  • Delta：描述「改變」的差異（ADDED/MODIFIED/REMOVED/RENAMED）。
  • Archive：把完成的 change 摺回 specs，移入 archive/。
  • Schema：自訂 workflow 的定義（artifacts + 依賴 + templates）。
  • Store：獨立的規劃 repo（beta）。
stores-beta/user-guide.md — 在獨立 repo 規劃

Stores：規劃大於單一 repo 時

OpenSpec 通常內嵌在程式碼 repo 的 openspec/ 資料夾。當規劃跨多個 repo、或規劃先於程式碼存在時，用 store：一個以規劃為唯一任務的獨立 repo，同樣是 openspec/ 結構（specs + changes）加一份識別檔。

  • 在本機註冊一次，之後用 --store <id> 從任何位置讓 list/show/status/validate/archive 等指令作用於它。
  • 搭配 references（引用其他 store）、working context（openspec context 組裝 root + 參考 store）、worksets（openspec workset 個人命名的工作資料夾檢視）。
Stores / references / worksets 皆為 Beta——指令名、旗標、檔案格式、JSON 輸出可能在版本間變動，升級後請重讀本指南。
