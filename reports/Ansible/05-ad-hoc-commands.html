第 5 章 — Ad-hoc 命令

Ad-hoc 是 Ansible 的「指尖功夫」——不寫 playbook、不開 YAML 檔，直接從命令列對著一群主機發送單一任務。它是新人初遇 Ansible 時最容易上手的入口，也是老手日常維運中用最頻繁的工具。本章帶你走過完整 CLI 語法、最常用的 8 個模組（command / shell / raw / script / copy / file / package / service / setup）、—-become / --check / --diff 等關鍵 flag、何時用 ad-hoc 何時該升級到 playbook 的決策準則。

本章覆蓋官方文件對應：Command Guide · Intro to Ad-hoc
初學者必讀（5.1–5.5） 開發者必讀（全章） DevOps / SRE 必讀（5.6–5.9 維運實戰）

5.1什麼是 Ad-hoc 命令？

Ad-hoc 來自拉丁文「為特定目的而做」。在 Ansible 語境下，一條 ad-hoc 命令 = 一個 task——它對指定的 host pattern 執行單一模組、回傳結果，然後結束。

bash · Ad-hoc 的標準語法 
$ ansible [host-pattern] -m [module] -a "[module-args]"
           ↑ 第 4 章學的       ↑ 任何模組    ↑ 模組參數

# 三個經典範例
$ ansible all -m ping
$ ansible webservers -m ansible.builtin.service -a "name=nginx state=restarted" --become
$ ansible db01 -a "uptime"   # 不寫 -m 時預設用 command 模組

5.1.1Ad-hoc vs Playbook 的決策準則

Figure 5.1 — Ad-hoc 與 Playbook 的選擇樹

5.1.2Ad-hoc 的三大典型用途

  • 健康檢查與資訊查詢：ping、uptime、df -h、setup 收集 facts
  • 緊急救火與一次性操作：重啟某個服務、清掉某個檔案、批次踢掉 stuck process
  • 新環境的 bootstrap：在 playbook 跑得起來之前，先用 raw / script 把 Python 裝好

5.2三劍客：command / shell / raw

三個都是「在遠端執行命令」，但行為差異巨大。選錯模組是新手最常見的踩雷點。

模組 是否走 shell 需要遠端 Python 支援 pipe / redirect 典型用途
command 否（直接 exec） 是 否 預設模組，安全簡單命令
shell 是（/bin/sh） 是 是 需要 pipe、redirect、變數展開
raw 是（最低層 SSH） 否 是 遠端無 Python 的 bootstrap、網路設備

5.2.1command 模組（預設）

當你 ansible all -a "..." 不指定 -m，Ansible 預設用 command。它不走 shell，所以管線、重導、變數展開、glob 全部不生效。這是特性而非 bug——避開了 shell injection 風險。

bash · command 模組正確使用 
# 簡單的單一命令 — 完美
$ ansible all -a "uptime"
$ ansible all -a "df -h /var"
$ ansible all -a "systemctl status nginx"

# 切到指定目錄再執行（chdir 是 command 模組的內建選項）
$ ansible appservers -a "git pull chdir=/opt/myapp"

# 條件式執行：creates / removes
# creates=path 表示「path 已存在則跳過」
$ ansible all -a "./setup.sh creates=/opt/.setup_done"

# removes=path 表示「path 存在才執行」
$ ansible all -a "rm -rf /tmp/cache removes=/tmp/cache"
⚠ command 模組不能做的事

下面這些不會如你預期：

ansible all -a "echo $HOME" → 印出字串 $HOME 而非展開

ansible all -a "ps aux | grep nginx" → | 被當成 ps 的參數

ansible all -a "ls *.log" → glob 不會展開

需要這些功能就改用 shell 模組。

5.2.2shell 模組

shell 模組在遠端 host 上以 /bin/sh -c "..." 執行命令——所有 shell 特性都生效。代價是稍微高一點的安全與可移植性風險，但日常維運完全可接受。

bash · shell 模組典型用法 
# Pipeline：找出佔用 80 port 的 process
$ ansible webservers -m shell -a "netstat -tlnp | grep ':80'" --become

# Redirect：把 disk usage 報告寫到檔案
$ ansible all -m shell -a "df -h > /tmp/disk_report.txt"

# 環境變數展開（變數在「遠端」host 解析）
$ ansible all -m shell -a 'echo $HOSTNAME - $USER'

# 多命令串接
$ ansible appservers -m shell -a "cd /opt/app && git log --oneline -5"

# Glob 展開：找最近 30 天的 log 檔數量
$ ansible all -m shell -a "find /var/log -name '*.log' -mtime -30 | wc -l"
ⓘ 引號雙層問題

如果你的命令本身有單引號，包裝外層命令時要記得 escape 或用 double quote。最簡單的做法：外雙、內單——ansible all -m shell -a "echo 'hello'"。這個小細節常讓新手搞半天。

5.2.3raw 模組

raw 是底層中的底層——不經 Ansible 模組系統、不打包 Python 程式碼，純粹把字串透過 SSH 連線丟到遠端 shell 執行。遠端不需要 Python。

bash · raw 模組的核心場景 
# 場景 1：在新 host 上裝 Python（雞生蛋問題的解法）
$ ansible newservers -m raw -a "apt-get install -y python3" --become

# 場景 2：管理沒 Python 的網路設備
$ ansible cisco_switches -m raw -a "show version"

# 場景 3：診斷 — 連 Python 都壞了，先用 raw 看看遠端能不能跑命令
$ ansible problem-host -m raw -a "which python3 || which python"
⚠ raw 不具備 idempotency

raw 沒有 changed/ok 概念——每次執行都被視為「changed」。它純粹把字串塞到 SSH 那一端執行，不檢查狀態、不冪等、不安全。除了 bootstrap 和網路設備，請優先用 command 或 shell。

5.3檔案操作：copy / file / fetch

這三個模組覆蓋了 90% 的 ad-hoc 檔案操作需求。

5.3.1copy — 從 control node 推檔到遠端

bash · copy 模組 
# 最簡用法：把 control node 上的檔案推到所有 webservers
$ ansible webservers -m copy \
    -a "src=./nginx.conf dest=/etc/nginx/nginx.conf" --become

# 同時設定權限與擁有者
$ ansible webservers -m copy \
    -a "src=./app.conf dest=/etc/app/app.conf owner=root group=root mode=0644" --become

# 不從檔案來，直接用 content 參數寫入內容
$ ansible all -m copy \
    -a 'content="MAX_CONNECTIONS=200\n" dest=/etc/sysctl.d/99-app.conf' --become

# 推整個目錄（注意 src 結尾的斜線）
$ ansible webservers -m copy \
    -a "src=./configs/ dest=/etc/app/" --become
#  src=./configs/   → 複製目錄的「內容」到 dest
#  src=./configs    → 複製整個 configs 目錄到 dest 下

5.3.2file — 管理檔案／目錄／權限／symlink

bash · file 模組 
# 建立目錄
$ ansible all -m file \
    -a "path=/opt/myapp state=directory mode=0755 owner=deploy" --become

# 確保檔案存在（不存在則建空檔）
$ ansible all -m file \
    -a "path=/var/log/myapp/app.log state=touch mode=0640" --become

# 刪除檔案／目錄（state=absent 是冪等的）
$ ansible all -m file -a "path=/tmp/old_cache state=absent" --become

# 建立 symlink
$ ansible all -m file \
    -a "src=/opt/myapp/current dest=/usr/local/bin/myapp state=link" --become

# 只改權限不動內容
$ ansible all -m file \
    -a "path=/etc/sudoers.d/ansible mode=0440" --become

5.3.3fetch — 從遠端拉檔回 control node

copy 是「推」，fetch 是「拉」。維運時常用 fetch 集中收集 log、設定檔做比對。

bash · fetch 模組 
# 從每台 host 拉一份 nginx.conf 回 control node 比對
$ ansible webservers -m fetch \
    -a "src=/etc/nginx/nginx.conf dest=./fetched/"

# 結果結構：
# ./fetched/web01.example.com/etc/nginx/nginx.conf
# ./fetched/web02.example.com/etc/nginx/nginx.conf
# 自動以 hostname 分目錄，避免多台同檔案覆蓋

# flat=yes 拍平路徑（會被同名檔覆蓋，慎用）
$ ansible web01 -m fetch \
    -a "src=/var/log/app.log dest=./logs/web01.log flat=yes"

5.4套件、服務、使用者管理

三個模組組成日常維運最常見的「裝、跑、開帳號」三件套。

5.4.1package — 跨平台套件管理

ⓘ 為什麼用 package 而不是 apt / yum / dnf？

ansible.builtin.package 是泛型 wrapper，會根據 host 的 OS 自動呼叫 apt（Debian 系）、dnf（RHEL 系）、apk（Alpine）等。寫一條命令跨平台通吃。不過進階參數（如 apt 的 update_cache）才有的話，還是要用具體模組。

bash · package / apt / dnf 
# 跨平台：確保 htop 已安裝
$ ansible all -m ansible.builtin.package \
    -a "name=htop state=present" --become

# 安裝多個套件（list 形式）
$ ansible all -m ansible.builtin.package \
    -a 'name=["git","vim","tmux"] state=present' --become

# Debian / Ubuntu 專屬：先 update apt cache
$ ansible all -m ansible.builtin.apt \
    -a "name=nginx state=latest update_cache=yes cache_valid_time=3600" --become

# RHEL 系：用 dnf 模組
$ ansible all -m ansible.builtin.dnf \
    -a "name=nginx state=latest" --become

# 移除套件
$ ansible all -m ansible.builtin.package \
    -a "name=telnet state=absent" --become

5.4.2service / systemd — 服務管理

bash · service 模組 
# 啟動服務並設為開機自動啟動
$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=started enabled=yes" --become

# 重啟服務
$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=restarted" --become

# Reload（不中斷現有連線）
$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=reloaded" --become

# 停止並停用
$ ansible all -m ansible.builtin.service \
    -a "name=apache2 state=stopped enabled=no" --become

# systemd 專屬參數（如 daemon_reload）用 systemd 模組
$ ansible all -m ansible.builtin.systemd \
    -a "name=myapp daemon_reload=yes state=restarted" --become

5.4.3user / group — 帳號管理

bash · user 模組 
# 建立基本使用者
$ ansible all -m ansible.builtin.user \
    -a "name=alice shell=/bin/bash state=present" --become

# 加入群組（append=yes 表示「附加」而不是「取代」現有群組）
$ ansible all -m ansible.builtin.user \
    -a "name=alice groups=sudo,docker append=yes" --become

# 為使用者建立 SSH 金鑰並抓出公鑰（generate_ssh_key）
$ ansible all -m ansible.builtin.user \
    -a "name=deploy generate_ssh_key=yes ssh_key_type=ed25519" --become

# 用 authorized_key 模組部署公鑰
$ ansible all -m ansible.posix.authorized_key \
    -a 'user=deploy state=present key="{{ lookup(\"file\", \"~/.ssh/deploy.pub\") }}"' --become

# 刪除使用者（含 home 目錄）
$ ansible all -m ansible.builtin.user \
    -a "name=alice state=absent remove=yes" --become

5.5script 與 setup：兩個特殊但常用的模組

5.5.1script — 把本地腳本送到遠端執行

遇到複雜邏輯不適合一行 shell 寫完、又懶得拆成 playbook 時，script 模組是甜點：它把 control node 上的腳本送到遠端、執行、把 stdout 收回來。遠端不需要先有這個腳本。

bash · script 模組 
# 把本地的健康檢查腳本送到所有 host 跑一次
$ ansible all -m script -a "./scripts/health_check.sh"

# 帶參數
$ ansible webservers -m script \
    -a "./scripts/deploy.sh --env production --version 2.5.0"

# 用 creates / removes 達到 idempotency
$ ansible all -m script \
    -a "./scripts/initial_setup.sh creates=/opt/app/.setup_complete"

# 跑 Python 腳本（會用 #!/usr/bin/env python3 之類的 shebang）
$ ansible all -m script -a "./scripts/gather_metrics.py"

5.5.2setup — 收集 facts

setup 是收集 host metadata 的模組。Playbook 預設第一個 task 自動跑它（除非 gather_facts: no）。Ad-hoc 中也常用來查詢主機資訊。

bash · setup 模組 
# 收集所有 facts（輸出量大，建議搭配 grep / less）
$ ansible web01 -m setup | less

# 用 filter 只看 OS 相關
$ ansible web01 -m setup -a "filter=ansible_distribution*"

# 看記憶體
$ ansible all -m setup -a "filter=ansible_memtotal_mb"

# 看網卡 IP
$ ansible all -m setup -a "filter=ansible_default_ipv4"

# 把所有 facts 存成 JSON 給其他工具用
$ ansible all -m setup --tree /tmp/facts/
ⓘ 常用的 facts

ansible_distribution（Ubuntu / RHEL...）、ansible_distribution_version、ansible_kernel、ansible_processor_count、ansible_memtotal_mb、ansible_default_ipv4.address、ansible_hostname、ansible_fqdn、ansible_python_version。第 7 章會深入介紹 facts 在 playbook 中的用法。

5.6關鍵 CLI Flags 完整對照

除了 -m、-a 兩大金剛，還有十幾個常用 flag。下面表格按功能分類：

5.6.1權限與認證

Flag說明範例
-b / --become啟用 sudo 提權ansible all -m apt -a "name=htop state=present" -b
--become-user提權後切到指定使用者--become-user=postgres
-K / --ask-become-pass互動式詢問 sudo 密碼-b -K
-k / --ask-pass互動式詢問 SSH 密碼金鑰未部署時用
-u USER指定 SSH 使用者-u deploy
--private-key指定 SSH 私鑰路徑--private-key=~/.ssh/prod_key

5.6.2目標選擇與並行控制

Flag說明範例
-i INV指定 inventory 路徑-i inventories/staging
--limit進一步收斂目標 host--limit "web01,web02"
-f N / --forks並行 host 數（預設 5）-f 50
-l / --list-hosts只列出會打到的 host，不執行確認 pattern 正確再實際跑

5.6.3安全與除錯

Flag說明範例
-C / --checkDry-run，只看會做什麼，不實際改所有破壞性命令的救命符
-D / --diff顯示變更前後 diff常與 --check 組合使用
-v / -vv / -vvv / -vvvvverbose 等級遞增-vvvv 顯示完整 SSH 命令
--one-line每 host 結果壓成一行批次掃描時看得清楚
-e VAR=VALextra-vars，覆蓋變數-e "ansible_port=2222"

5.6.4幾個實用組合

bash · 常用 flag 組合 
# 1) Dry-run + diff：在改設定前先預演（最重要的安全網）
$ ansible webservers -m copy \
    -a "src=./nginx.conf dest=/etc/nginx/nginx.conf" \
    --become --check --diff

# 2) 一行式 + 高並行：批次掃描 100 台 host
$ ansible all -m shell -a "uname -r" --one-line -f 50

# 3) 限定範圍 + 互動密碼：對特定一台緊急操作
$ ansible all --limit web01 -m ansible.builtin.service \
    -a "name=nginx state=restarted" --become -K

# 4) 列出將打到的 host（驗證 pattern 正確）
$ ansible 'webservers:&production' --list-hosts

# 5) 連線 debug：完整 SSH 命令 + 模組 JSON
$ ansible problem-host -m ping -vvvv 2>&1 | grep "SSH:"

5.7輸出格式與結果解讀

Ad-hoc 命令的輸出格式有固定結構，看懂它就能在 100 台 host 中快速找出有問題的那台。

5.7.1四種狀態：SUCCESS / CHANGED / FAILED / UNREACHABLE

狀態顏色意義典型場景
SUCCESS綠色命令成功，但沒有改變狀態ping、查詢類；冪等模組發現「已是期望狀態」
CHANGED黃色命令成功，且改變了狀態裝套件、改設定、重啟服務
FAILED紅色命令執行了但失敗權限不足、套件名打錯
UNREACHABLE紅色連 host 都連不到SSH 失敗、網路 / 防火牆問題

5.7.2JSON 結構解讀

json · 一個典型 SUCCESS 輸出 
web01.example.com | SUCCESS => {
    "changed": false,           // 沒有改變狀態
    "cmd": "uptime",
    "delta": "0:00:00.012",    // 命令執行時間
    "end": "2026-05-07 11:23:15.882",
    "rc": 0,                  // return code (0 = 成功)
    "start": "2026-05-07 11:23:15.870",
    "stderr": "",
    "stdout": "11:23:15 up 12 days, 4:33, 0 users, load average: 0.10, 0.05, 0.01"
}
✓ 看懂這幾個 key

changed：true 代表狀態被改變了。冪等模組第二次跑會回 changed: false，這就是 Ansible 安全可重跑的核心。
rc：return code，0 是成功。
stdout / stderr：原始命令輸出。
delta：執行時間，效能調校時看這個。

5.7.3--one-line 壓縮輸出（批次掃描）

bash · --one-line 範例 
$ ansible all -m shell -a "uname -r" --one-line

# 輸出每 host 一行：
web01.example.com | CHANGED | rc=0 | (stdout) 6.8.0-49-generic
web02.example.com | CHANGED | rc=0 | (stdout) 6.8.0-49-generic
db01.example.com  | CHANGED | rc=0 | (stdout) 5.14.0-432.el9.x86_64
old-server        | UNREACHABLE! => ...

# 用 grep 快速挑出異常
$ ansible all -m shell -a "systemctl is-active nginx" --one-line | grep -v active

5.8實戰維運場景集

把前面所有零件組合起來，下面是 SRE 日常會碰到的真實場景。

5.8.1場景：所有 webservers 緊急重啟 nginx

bash · 場景 1 
# 1) 先確認哪些 host 會被打到
$ ansible webservers --list-hosts

# 2) 先用 --check 預演（service 模組支援）
$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=restarted" --become --check

# 3) 滾動重啟（一次只重啟 5 台，避免全部斷線）
$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=restarted" --become -f 5

# 4) 確認所有 host 的 nginx 是 active
$ ansible webservers -m shell \
    -a "systemctl is-active nginx" --one-line

5.8.2場景：批次健康檢查 dashboard

bash · 場景 2 
# 一行掃出所有 host 的：核心版本 + 記憶體 + 開機時間
$ ansible all -m setup \
    -a "filter=ansible_kernel,ansible_memtotal_mb,ansible_uptime_seconds" \
    --one-line

# 找出 disk 使用率超過 80% 的 host
$ ansible all -m shell \
    -a "df -h / | awk 'NR==2 {print \$5}' | tr -d '%'" --one-line \
  | awk -F'(stdout) ' '$2 > 80 {print $1}'

# 找出 nginx 沒在跑的 host
$ ansible webservers -m shell \
    -a "systemctl is-active nginx" --one-line | grep -v active

5.8.3場景：一次性 patch 部署

bash · 場景 3 
# 緊急 CVE 出來，所有 Ubuntu host 升級 openssl

# 1) 先看哪些 host 會被影響
$ ansible all -m setup \
    -a "filter=ansible_distribution" --one-line | grep Ubuntu

# 2) Dry-run 確認
$ ansible all -m ansible.builtin.apt \
    -a "name=openssl state=latest update_cache=yes" \
    --become --check --limit "ubuntu_hosts"

# 3) 滾動更新（一次 10 台）
$ ansible all -m ansible.builtin.apt \
    -a "name=openssl state=latest update_cache=yes" \
    --become --limit "ubuntu_hosts" -f 10

# 4) 驗證版本
$ ansible all -m shell -a "openssl version" --one-line --limit ubuntu_hosts

5.8.4場景：抽 log 集中分析

bash · 場景 4 
# 把所有 webserver 最近 1 小時的 nginx error log 抓回 control node
$ ansible webservers -m shell \
    -a "journalctl -u nginx --since '1 hour ago' > /tmp/nginx-1h.log" --become

$ ansible webservers -m fetch \
    -a "src=/tmp/nginx-1h.log dest=./logs/"

# 結果在 ./logs/web01.example.com/tmp/nginx-1h.log 等
# 接下來可以用 grep / awk 集中分析
$ grep -h "error" ./logs/*/tmp/nginx-1h.log | sort | uniq -c | sort -rn

5.9Ad-hoc 的限制與升級到 Playbook 的時機

Ad-hoc 強大但不是萬能。下列徵兆出現時，該升級到 playbook 了。

!

命令長度超過一行

當你的 ad-hoc 命令參數寫到 80 字元以上、要靠 \ 換行才不會錯位，已經失去 ad-hoc 該有的「快」。

!

需要多步驟有先後依賴

「先停服務、改設定、重啟、驗證」——這四步要寫四條 ad-hoc，中間還要肉眼確認。Playbook 一個檔搞定。

!

需要條件判斷或 loop

when:、loop:、register、handlers——這些是 playbook 的核心能力，ad-hoc 都做不到。

!

會重複執行的任務

「我又要做同樣的事」就是訊號。Playbook 進 git，下次別人接手能直接 review、可重現、可審計。

!

需要把結果傳給下一個 task

register: result + 後續 task 用 {{ result.stdout }}——這個 pipeline ad-hoc 沒有。

!

變更跨越多個環境

要在 staging 驗證、在 production 部署，且兩邊參數不同——應該用 playbook + 不同 inventory，不是兩條 ad-hoc。

ⓘ 一個實用習慣

當你寫的 ad-hoc 「跑一次成功」，還有點價值的話，順手 把它存成一個小 playbook（tasks/quick-fix-2026-05-07.yml），加一行 commit 進 git。半年後類似問題再次出現，你會感謝過去的自己。

5.10本章重點回顧

01

標準語法

ansible [pattern] -m [module] -a "[args]"。不指定 -m 預設用 command。pattern 即第 4 章學的 inventory 群組與 host pattern。

02

三劍客選擇

command（簡單 + 安全）、shell（pipe / redirect / 變數）、raw（無 Python / 網路設備）。預設用 command，需要 shell 特性才升級。

03

檔案三件套

copy（推檔到遠端）、fetch（拉檔回本地）、file（管理權限與目錄／symlink）。

04

維運三件套

package（跨平台套件）、service / systemd（服務管理）、user / authorized_key（帳號與金鑰）。

05

--check 與 --diff 救命組合

所有破壞性命令先 dry-run。--check --diff 顯示「會改什麼、改成什麼樣」，看完無誤才實際執行。

06

--one-line 批次掃描

對 100+ 台 host 跑 ad-hoc 時，預設輸出冗長。加 --one-line 每 host 一行，搭配 grep / awk 快速定位異常。

07

setup 模組查 facts

ansible host -m setup -a "filter=..." 是查詢系統資訊最快的 ad-hoc 工具。OS 版本、記憶體、IP、kernel、Python 版本一鍵到手。

08

升級到 Playbook 的訊號

命令超過一行、要重複執行、需條件判斷、需要結果傳遞——不要 把 ad-hoc 拉長成怪物，直接寫成 playbook。

練習題

  1. 初學者：用 ping 模組對你 inventory 內所有 host 跑健康檢查。改用 --one-line 看輸出有何不同。
  2. 初學者：用 command 模組跑 echo $HOME，觀察輸出。再用 shell 模組跑同樣命令，比較結果。
  3. 初學者：用 setup 模組搭配不同 filter 查詢：① 所有 host 的 OS 與版本、② 記憶體、③ IPv4 位址。
  4. 開發者：用 copy 模組把一個本地設定檔推到 webservers，先用 --check --diff 確認 diff，再實際執行，最後用 fetch 抓一台回來驗證。
  5. 開發者：寫一個 bash 腳本 healthcheck.sh，用 script 模組推到所有 host 執行，輸出每台 host 的 disk / memory / load 狀態。
  6. 開發者：用 user + authorized_key 兩個模組，為新成員 alice 在所有 webservers 建立帳號並部署她的公鑰。
  7. DevOps / SRE：寫一條 ad-hoc 命令，找出 inventory 中 disk 使用率超過 80% 的所有 host，輸出 host 名稱清單。
  8. DevOps / SRE：用 ansible.builtin.apt 模組對所有 Ubuntu host 升級 openssl，必須 先用 --check 看清楚會升級什麼版本，再實際執行 + -f 10 滾動。
  9. DevOps / SRE：把你過去手動 SSH 到每台機器跑的某個操作（例如清 nginx cache、看 log 等），改寫成一條 ad-hoc 命令。如果寫起來超過 80 字元，把它再轉成 playbook（這就是第 6 章的內容）。

本章詞彙表

Ad-hoc command
從命令列直接執行的單一 Ansible task，不寫 playbook。語法 ansible [pattern] -m [module] -a [args]。
command 模組
Ansible 預設模組，直接 exec 命令，不走 shell。不支援 pipe、redirect、變數展開。安全但功能受限。
shell 模組
透過 /bin/sh 執行命令，支援所有 shell 特性（pipe、redirect、glob、變數）。日常維運主力。
raw 模組
最低層 SSH 命令，不需要遠端 Python。用於 bootstrap、網路設備、診斷。沒有 idempotency。
script 模組
把 control node 上的腳本送到遠端執行，遠端不需要先有腳本。適合複雜邏輯但不想寫 playbook 時。
setup 模組
收集 host facts（系統資訊）。Playbook 預設第一個 task 自動跑，ad-hoc 中常用 filter 查詢特定欄位。
copy 模組
從 control node 推檔到遠端 host。支援 src 檔案、content 內容、權限／擁有者參數。
fetch 模組
從遠端 host 拉檔回 control node。預設按 hostname 分目錄避免覆蓋。
file 模組
管理檔案／目錄／symlink，含建立、刪除、權限、擁有者、touch 等操作。
package 模組
跨平台套件管理 wrapper，自動辨認 OS 後呼叫 apt / dnf / apk 等具體模組。
service / systemd 模組
管理服務狀態（started / stopped / restarted / reloaded）與開機啟動（enabled）。systemd 模組多了 daemon_reload 等專屬參數。
--check (dry-run)
讓 Ansible 假裝執行命令，回報「會做什麼」但不實際變更。所有破壞性操作的安全網。
--diff
顯示變更前後的差異（如設定檔的 line-by-line diff）。常與 --check 組合。
idempotency（冪等性）
同一命令重複執行結果一致。冪等模組第二次跑會回 changed: false。command / shell / raw 不冪等，其他大多數模組冪等。
chdir / creates / removes（command 系列模組共用參數）
chdir 切換工作目錄；creates=path 表示 path 已存在則跳過；removes=path 表示 path 存在才執行。三者讓 command/shell 也能達到冪等。
--one-line
把每 host 的輸出壓成一行。批次掃描 + grep / awk 過濾異常時的必備 flag。
