第五篇 — 網路與雲端自動化

第 21 章 — 容器與 Kubernetes

第 18 章用 docker_exec connection plugin 對容器內部跑 task；第 20 章用 cloud collection 起雲端 VM。本章把這兩端的「中段」補上：用 Ansible 管理容器本身與 Kubernetes 資源。涵蓋四個層級——① Docker / Podman host 端管理（裝 daemon、跑 container）；② 容器內配置（用 docker connection plugin）；③ K8s resource 宣告式管理（kubernetes.core.k8s 模組）；④ Helm chart 部署。會釐清 Ansible 與 kubectl / Helm / Kustomize / GitOps（ArgoCD）這四個 K8s 工具的位置與分工——不是取代 kubectl，而是補上「IaC + 跨雲 + post-deployment 配置」的缺口。本章實戰會建一個完整的 K8s app stack：namespace + secret + configmap + deployment + service + ingress + Helm-installed Redis。讀完這章你能用 Ansible 從 EC2 起 K8s cluster 一路部署到 prod-ready 的應用環境。

21.1.2Ansible 在 K8s 生態的定位

ⓘ Ansible 不取代 kubectl 或 Helm

Ansible 是這些工具的外殼與整合層。它能呼叫 kubectl / Helm 並把結果整合到更大的 workflow 裡：「先建 EKS cluster（雲端 collection）→ 套 ingress controller（helm 模組）→ 部署應用（k8s 模組）→ 配置 DNS（cloud collection）→ 通知 Slack（callback plugin）」這種跨領域整合是 kubectl + bash 寫不漂亮的場景。

21.3層級 ①：Docker host 端管理

21.3.1裝 Docker daemon

yaml · roles/docker_install/tasks/main.yml — Ubuntu 
---
- name: 裝必要套件
  ansible.builtin.apt:
    name:
      - ca-certificates
      - curl
      - gnupg
    update_cache: yes

- name: 加入 Docker GPG key
  ansible.builtin.get_url:
    url: https://download.docker.com/linux/ubuntu/gpg
    dest: /etc/apt/keyrings/docker.asc
    mode: "0644"

- name: 加入 Docker repository
  ansible.builtin.apt_repository:
    repo: "deb [arch={{ arch }} signed-by=/etc/apt/keyrings/docker.asc] 
           https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable"
    filename: docker

- name: 裝 Docker engine
  ansible.builtin.apt:
    name:
      - docker-ce
      - docker-ce-cli
      - containerd.io
      - docker-buildx-plugin
      - docker-compose-plugin
    update_cache: yes
  notify: restart docker

- name: 啟動 docker
  ansible.builtin.service:
    name: docker
    state: started
    enabled: yes

- name: 把使用者加進 docker group
  ansible.builtin.user:
    name: "{{ ansible_user }}"
    groups: docker
    append: yes

21.3.2跑 container

yaml · 用 docker_container 起服務 
- name: 建立 docker network
  community.docker.docker_network:
    name: app_net
    driver: bridge
    ipam_config:
      - subnet: 172.20.0.0/16

- name: PostgreSQL container
  community.docker.docker_container:
    name: postgres
    image: postgres:16-alpine
    state: started
    restart_policy: unless-stopped
    env:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: "{{ vault_db_password }}"
      POSTGRES_DB: appdb
    volumes:
      - pg_data:/var/lib/postgresql/data
    networks:
      - name: app_net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 10s
      retries: 5

- name: App container
  community.docker.docker_container:
    name: app
    image: myorg/app:{{ app_version }}
    state: started
    restart_policy: unless-stopped
    ports: ["8080:8080"]
    env:
      DB_HOST: postgres
      DB_PASSWORD: "{{ vault_db_password }}"
    networks:
      - name: app_net
    depends_on: [postgres]

21.3.3Podman 對應

ⓘ Podman 與 Docker 99% 相同

把 community.docker.docker_* 換成 containers.podman.podman_* 即可。Podman 主要差異：rootless 友善（不需 daemon、不需 root）、systemd 整合（podman generate systemd）、預設無 docker socket 暴露風險。RHEL / Fedora 預設容器運行環境是 podman。

- kubernetes.core.k8s:

        labels:
          env: prod

# 方式 ② — 從檔案載入
- kubernetes.core.k8s:
    state: present

- kubernetes.core.k8s:

21.4.4Deployment 範例

yaml · 部署 webapp 完整範例 
- name: 建立 namespace
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: Namespace
      metadata: { name: myapp }

- name: 建立 ConfigMap
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: ConfigMap
      metadata:
        name: app-config
        namespace: myapp
      data:
        log_level: info
        feature_flags: "dark_mode=true,beta_search=false"

- name: 建立 Secret（DB password）
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: Secret
      metadata:
        name: db-secret
        namespace: myapp
      type: Opaque
      stringData:
        password: "{{ vault_db_password }}"

- name: 部署 Deployment 並等就緒
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: webapp
        namespace: myapp
      spec:
        replicas: 3
        selector:
          matchLabels: { app: webapp }
        template:
          metadata:
            labels: { app: webapp }
          spec:
            containers:
              - name: webapp
                image: "myorg/webapp:{{ app_version }}"
                ports: [{ containerPort: 8080 }]
                envFrom:
                  - configMapRef: { name: app-config }
                env:
                  - name: DB_PASSWORD
                    valueFrom:
                      secretKeyRef: { name: db-secret, key: password }
                resources:
                  requests: { cpu: 100m, memory: 128Mi }
                  limits: { cpu: 500m, memory: 512Mi }
                livenessProbe:
                  httpGet: { path: /health, port: 8080 }
                  initialDelaySeconds: 10
    wait: true
    wait_timeout: 300
    wait_condition:
      type: Available
      status: "True"

- name: 建立 Service
  kubernetes.core.k8s:
    state: present
    definition:
      apiVersion: v1
      kind: Service
      metadata: { name: webapp, namespace: myapp }
      spec:
        selector: { app: webapp }
        ports: [{ port: 80, targetPort: 8080 }]
        type: ClusterIP
✓ wait + wait_condition 是關鍵

K8s API 建立成功不等於 應用就緒。Deployment apply 後 pod 還在 pull image / starting / readiness check。wait: true + wait_condition 讓 Ansible 等到真正可用才算完成——CI/CD pipeline 必備。

21.5查詢與診斷：k8s_info / k8s_log / k8s_exec

21.5.1查狀態

yaml · 查 deployment 狀態 
- name: 查 webapp deployment
  kubernetes.core.k8s_info:
    api_version: apps/v1
    kind: Deployment
    name: webapp
    namespace: myapp
  register: dep

- name: 確認 ready replicas
  ansible.builtin.fail:
    msg: "deployment not ready"
  when:
    - dep.resources | length == 0
    - (dep.resources[0].status.readyReplicas | default(0)) < 3

# 列 namespace 內所有 pod
- kubernetes.core.k8s_info:
    kind: Pod
    namespace: myapp
    label_selectors:
      - "app=webapp"
  register: pods

- debug:
    msg: "{{ item.metadata.name }} = {{ item.status.phase }}"
  loop: "{{ pods.resources }}"

21.5.2取 log / 進 pod 跑命令

yaml · debug 用工具 
# 取 pod 最近 100 行 log
- kubernetes.core.k8s_log:
    name: webapp-7d4b8c-xyz12
    namespace: myapp
    tail_lines: 100
  register: log_out

- debug:
    var: log_out.log

# 對 pod 跑命令
- kubernetes.core.k8s_exec:
    namespace: myapp
    pod: webapp-7d4b8c-xyz12
    command: cat /etc/myapp/config
  register: exec_out

21.5.3scale 與 rollback

yaml · 動態 scale 與 rollback 
# 突然要擴容到 10 個
- kubernetes.core.k8s_scale:
    api_version: apps/v1
    kind: Deployment
    name: webapp
    namespace: myapp
    replicas: 10
    wait: true

# 部署有問題 — rollback 到上一版
- kubernetes.core.k8s_rollback:
    api_version: apps/v1
    kind: Deployment
    name: webapp
    namespace: myapp

21.6層級 ④：Helm chart 部署

Helm 是 K8s 的「套件管理器」——把多個 manifest 打包成 chart、用 values 客製化。Ansible 不取代 Helm，是把 Helm 包進 IaC workflow。

21.6.1裝 Bitnami Redis

yaml · 用 Helm 裝 Redis 範例 
- name: 加 Bitnami Helm repo
  kubernetes.core.helm_repository:
    name: bitnami
    repo_url: https://charts.bitnami.com/bitnami

- name: 部署 Redis
  kubernetes.core.helm:
    name: cache-redis
    chart_ref: bitnami/redis
    chart_version: "21.2.5"          # 鎖版本（生產必要）
    release_namespace: myapp
    create_namespace: true
    values:
      auth:
        password: "{{ vault_redis_password }}"
      master:
        resources:
          limits: { cpu: 250m, memory: 256Mi }
          requests: { cpu: 100m, memory: 128Mi }
      replica:
        replicaCount: 2
    wait: true
    wait_timeout: 5m0s

21.6.2從 values 檔載入

yaml · 把 values 抽到外部檔 
# values 比較複雜時抽到 yaml 檔
- kubernetes.core.helm:
    name: prometheus
    chart_ref: prometheus-community/kube-prometheus-stack
    release_namespace: monitoring
    create_namespace: true

    # 用 Jinja2 template 動態算 values（最強大）
    values: "{{ lookup('template', 'prometheus-values.yaml.j2') | from_yaml }}"

    # 或用 values_files 載入靜態檔案
    # values_files:
    #   - /opt/values/prom-base.yaml
    #   - /opt/values/prom-{{ env }}.yaml

21.7Ansible vs kubectl / Helm / GitOps 的位置

K8s 工具生態太多 — Ansible 在哪裡？對照常見工具看分工：

工具強項弱項該何時用
kubectl 互動性最強、debug 最快 不適合 IaC 探索、debug、一次性 ops
Helm 套件化、values 客製化、版本管理 純 K8s 範圍 第三方套件部署、模板化內部 chart
Kustomize 覆寫式 YAML 客製、無模板語言 表達能力比 Helm 弱 純內部 manifest 客製化
ArgoCD / Flux（GitOps） git 是真相、自動 reconcile cluster 創建前的事做不了 cluster 已存在後的應用部署
Ansible 跨領域整合、provisioning + post-config 單純 K8s 操作不及 GitOps 工具 cluster 創建、第一次 bootstrap、雲端 + K8s 混合

ⓘ Ansible 在 K8s 的甜蜜點

① Day 0 bootstrap——cluster 還沒建好、ArgoCD 還沒裝；② 跨領域——同時動 cloud（AWS）+ K8s + DNS + monitoring；③ 跨集群一次性 ops——「所有 50 個 cluster 都裝這個 secret」④ 配置 K8s 之外的東西——cluster node 的 OS / kernel / kubelet config。純 K8s 內、長期維運就讓 ArgoCD / Flux 接手。

21.8業界最佳實踐

①

image tag 不用 latest

永遠寫明確版本（myapp:1.2.3 / image digest）。latest 在 K8s 不會自動拉新版（因為 imagePullPolicy）且爆炸時不知道哪版。

②

Helm chart_version 鎖死

Helm install 一定指定 chart_version。不鎖版本下次跑可能拉到 breaking change。

③

wait + wait_condition

K8s 是 declarative async — apply 成功不等於應用 ready。CI 部署要 wait: true + wait_condition 等真正就緒。

④

resource requests / limits 必設

沒設 resource 的 pod 會被 K8s scheduler 當「最低優先級公民」。生產 deployment 一定有 requests + limits。

⑤

liveness + readiness probe

沒 probe，K8s 不知道你的 pod 是 hung 還是還在 startup。沒 readiness probe，traffic 會在 pod startup 時打進去 502。

⑥

用 namespace 隔離

同個 cluster 多應用 / 多環境用 namespace 區分。配 NetworkPolicy + RBAC 加固。

⑦

secret 從 vault / KMS 取

K8s Secret 預設 base64 編碼不算加密。用 ansible-vault 存、執行時用 stringData 注入；或裝 ESO（External Secrets Operator）+ AWS SSM。

⑧

namespace + labels 標一切

每個 resource 都有 app / env / version / managed-by labels。debug、cleanup、監控規則都靠它。

01

練習題

  1. 初學者：用 community.docker.docker_container 在本機起一個 nginx container，map port 8080。確認瀏覽器連 localhost:8080 看到 nginx 頁面。
  2. 初學者：用 kubernetes.core.k8s 在本機 K8s（kind / minikube / k3s）建一個 namespace 並部署 nginx Deployment（3 replica）+ Service（ClusterIP）。用 k8s_info 確認 pod 狀態。
  3. 初學者：對上題 Deployment 跑 k8s_scale 改成 5 個 replica，確認 kubectl get pod -n <ns> 看到 5 個 pod。
  4. 開發者：實作本章 21.4.4 的完整 webapp stack（namespace + ConfigMap + Secret + Deployment + Service）。wait_condition: Available 等就緒。
  5. 開發者：擴展上題加 Ingress resource（用 nginx ingress controller）。配本機 hosts 檔測試 hostname-based routing。
  6. 開發者：用 kubernetes.core.helm 裝 cert-manager 與 ingress-nginx 兩個 chart，鎖具體版本，wait: true。
  7. DevOps / SRE：寫一個跨集群部署 playbook — 在 inventory 列 dev/staging/prod 三個 cluster（不同 kubeconfig），對所有 cluster 同步同一份應用 Deployment。
  8. DevOps / SRE：寫個 K8s health-check playbook — 用 k8s_info 列所有 namespace 內 Deployment，readyReplicas != desiredReplicas 的 fail 並觸發 callback plugin（Slack 通知）。
  9. DevOps / SRE：設計一個 Day 0 bootstrap playbook — ① 用 amazon.aws 建 EKS cluster；② 取得 kubeconfig；③ 裝 ingress-nginx + cert-manager + ArgoCD（Helm）；④ 部署一個 ArgoCD ApplicationSet 從 git 同步 production manifest。

本章詞彙表

community.docker collection
Ansible 的 Docker 管理 collection。提供 docker_container / docker_image / docker_network / docker_volume 等 host 端管理模組與 docker connection plugin。
containers.podman collection
Ansible 的 Podman 管理 collection。podman_container 等模組。RHEL / Fedora 預設容器運行環境。
kubernetes.core collection
Ansible 官方 K8s collection。提供 k8s / k8s_info / k8s_exec / k8s_log / k8s_scale / k8s_drain / k8s_rollback / helm / helm_repository 等模組。
k8s 模組
萬用 K8s resource 管理模組。能管 Deployment / Service / Ingress / CRD 等任何 K8s object。三種寫法：inline definition / src / template。
k8s_info 模組
查詢 K8s resource。register 後判斷 readyReplicas / status.phase 等做後續決策。
k8s_exec 模組
對 pod 執行命令。等同 kubectl exec。
k8s_log 模組
取 pod log。等同 kubectl logs。
k8s_scale 模組
調整 Deployment / StatefulSet replica 數。
k8s_drain 模組
drain / cordon / uncordon node。升級維護用。
k8s_rollback 模組
把 Deployment rollback 到上一個 revision。
helm 模組
裝 / 升級 / 刪除 Helm release。chart_ref + chart_version + values。
helm_repository 模組
管理 Helm repo（helm repo add 等價物）。
wait + wait_condition
k8s / helm 模組的選項。wait: true + wait_condition: type: Available, status: "True" 等資源真正就緒才算完成。
kubeconfig
K8s 認證設定檔。預設 ~/.kube/config。可用 KUBECONFIG env 或模組的 kubeconfig: 參數指定。
label_selectors
k8s_info 的選項。用 K8s label 過濾 resource。app=webapp。
namespace
K8s 的虛擬隔離空間。生產建議每個應用 / 每個環境一個 namespace。
ConfigMap / Secret
K8s 的設定 / secret 物件。Ansible 用 k8s 模組建立，secret 用 stringData 直接寫文字（K8s 自動 base64）。
Deployment / StatefulSet / DaemonSet
K8s 的應用工作負載類型。Deployment 最常見（無狀態），StatefulSet 有狀態（DB），DaemonSet 每 node 一個（log agent）。
Service / Ingress
K8s 的網路抽象。Service 在 cluster 內 routing；Ingress 對外暴露 HTTP/HTTPS。
Helm
K8s 套件管理器。把多個 manifest 打包成 chart，用 values 客製化。
chart / chart_ref / chart_version
Helm chart 識別。bitnami/redis 是 chart_ref，21.2.5 是 chart_version。生產務必鎖版本。
values_files / values
Helm release 的客製參數。values 是 yaml dict 直接寫；values_files 從檔案載入；最強大用 lookup('template', 'x.j2') | from_yaml 動態產生。
GitOps (ArgoCD / Flux)
K8s 應用部署 pattern — git 是真相，工具持續 reconcile cluster 狀態與 git 一致。Day 1+ 應用部署的主流。
Day 0 / Day 1 / Day 2
運維生命週期。Day 0 = bootstrap（cluster 建立）；Day 1 = 上線；Day 2 = 維運（升級、scale、debug）。Ansible 強在 Day 0 + Day 2，GitOps 強在 Day 1+。
