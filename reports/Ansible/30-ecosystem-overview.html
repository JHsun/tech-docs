30.1為什麼需要 Platform

CLI 的 ansible-playbook 解決「能不能跑」；platform 解決「能不能規模化跑」。本節給五個 CLI 撐不住的場景。

30.1.1CLI 撐不住的五個場景

📅

Scheduling

「每週日 02:00 跑 patch」CLI 靠 cron。但 cron 不會留歷史、不會通知、不會 retry、不會跨團隊看見。

🔐

RBAC + Secret 管理

「DBA 能跑 DB 維護 playbook、不能跑網路設備」。CLI 沒辦法分權；vault 只能解部分問題。

📜

Audit trail

「誰在何時對哪些 host 跑了什麼」要寫進合規日誌。CLI 沒記錄。

👥

多人協作 + 自助式

非 Ansible 工程師（DBA / 客服 / SRE on-call）按按鈕就能執行受信任 playbook。CLI 要他們學 SSH key + git 不現實。

🌐

跨網路分區

Control node 在 office、被管 host 在 datacenter / cloud / edge — 中間有 firewall。SSH 不能直連的拓撲需要 mesh。

30.1.2從 CLI 升級到 platform 的訊號

ⓘ 你的團隊到了該升級的時機嗎？

出現以下三個或以上就該升級了：① 同一個 playbook 多個工程師都會跑、彼此 git push 衝突；② 主管問「上週對 prod 做了什麼維護」答不出來；③ 想讓 DBA / 安全團隊跑某些 playbook 但不給他們 SSH key；④ 部署排程從 git push hook 退化到「Slack 喊一聲手動跑」；⑤ 跨地區 / 跨雲 host 從 control node SSH 不過去。

30.2AAP vs AWX vs Tower — 三者關係

新人最困惑的就是這三個名字。一張圖講清楚：

Figure 30.1 — Tower、AWX、AAP 的關係

30.2.1三個名詞速查

名稱是什麼狀態
Ansible Tower 2017-2021 的商業 web UI 產品（Red Hat 收購後維持品牌） 已停產 — 改名 AAP
AWX Tower / AAP 的開源上游專案。功能與 AAP Controller 幾乎一致 活躍 — Apache 2.0、Red Hat 維護
AAP（Ansible Automation Platform） Red Hat 商業版訂閱產品。AWX + Hub + Mesh + 認證 collection + 24/7 support 活躍 — 2.5 / 2.6 是 2026 主流版本
Automation Controller AAP 內負責 web UI / job / scheduling 的元件 = AWX 的商業版 活躍
✓ 簡記

「AWX 是 free 的、AAP 是 paid 的、Tower 是舊名字」。功能 90% 相同，AAP 多的是企業要的（cert collection / support / private hub / fail-over）。Automation Controller = AAP 內的 AWX，因此本書談「Controller」與「AWX」時多數情況可互換。

30.3整體架構 — 三大組件

Figure 30.2 — AAP 三大組件 — Controller / Hub / Mesh

30.3.1三組件分工

🎛

Controller (AWX)

大腦。Web UI、REST API、job / inventory / project 管理、RBAC、audit log、scheduling、notification。多數用戶日常接觸的就是這個。

📦

Hub（Automation Hub）

私有 Galaxy + EE 容器 registry。團隊內部 collection / role 不上 public Galaxy 而上 Hub。配 SSO 與 cert 管控。

🕸

Mesh（Automation Mesh）

基於 receptor（CNCF 專案）的 overlay 網路。讓 control plane 與 execution node 跨防火牆 / 跨地區可達。傳統 Ansible 痛點之一。

30.4Execution Environment（EE）— venv 的進化

EE 是 AAP 2 / AWX 19+ 引入的核心架構變化。理解 EE 等於理解 modern Ansible。

30.4.1從 venv 到 EE

Figure 30.3 — venv vs EE 演進

30.4.2EE 解決什麼 venv 解不了

能力venvEE
Python 套件隔離會會
Ansible 版本鎖定會會
Collection 鎖定部分完整
系統工具（ssh、sshpass、curl、CLI tools）打包不會會
跨機器一致每台要重做image pull 即可
CI/CD 一致性難CI 跟生產用同 image
Air-gapped 環境難同 image 複製到隔離區

30.4.3EE 內部結構

ⓘ EE 是 OCI 標準容器 image

EE = OCI 容器 image，內含 ① ansible-core 某版本（2.16 / 2.18 等）② ansible-runner Python lib（負責執行）③ 你聲明的 collections + Python 套件 + 系統工具。Podman / Docker 都能跑。2026 主流：AAP 2.5 / 2.6 預設 EE 含 ansible-core 2.16 或 2.18。官方 EE 在 catalog.redhat.com，社群在 quay.io/ansible/awx-ee。

30.5ansible-navigator — 本機跑 EE

EE 不只是 AAP / AWX 用——你的 dev laptop 也可以跑 EE。ansible-navigator 是專為此設計的 CLI + TUI 工具。

30.5.1navigator 在 stack 的位置

工具角色
ansible-playbook傳統 CLI — 直接在 host venv 跑
ansible-navigator新 CLI + TUI — 把 playbook 跑在本地 EE 容器內
ansible-runnerPython lib — 程式內呼叫 Ansible（navigator 內部就是用這個）
AAP / AWXWeb UI 觸發 runner 跑 playbook

30.5.2navigator 基本用法

bash · ansible-navigator 上手 
# 安裝
$ pip install ansible-navigator

# 對 playbook 執行 — 自動拉 EE image 並在容器裡跑
$ ansible-navigator run site.yml \
    --eei "quay.io/ansible/awx-ee:latest" \
    -i inventory/

# 進 TUI 模式 — 可視化 inventory / collection / config
$ ansible-navigator
# 在 TUI 內可瀏覽：
#   :collections   — 列當前 EE 含哪些 collection
#   :doc apt       — 看 apt module 文件
#   :inventory     — 列 inventory
#   :run site.yml  — 跑 playbook

# 用自製 EE
$ ansible-navigator run site.yml \
    --eei "registry.example.com/myorg/network-ee:2.1"

30.5.3navigator 配置檔

yaml · ansible-navigator.yml — 專案級配置 
---
ansible-navigator:
  execution-environment:
    image: registry.example.com/myorg/network-ee:2.1
    pull:
      policy: missing            # missing / always / never / tag
    container-engine: podman     # podman / docker
    enabled: true

  playbook-artifact:
    enable: true
    save-as: "./logs/{playbook_name}-{time_stamp}.json"

  logging:
    level: info

30.6ansible-runner — 程式內呼叫 Ansible

當你想在 Python 程式裡呼叫 Ansible（如自寫 web app、CI 整合、orchestrator 工具）——直接 subprocess 呼 ansible-playbook 是反模式。ansible-runner 是官方 Python lib。

30.6.1用法範例

python · 用 ansible-runner 程式化跑 playbook 
import ansible_runner

# 簡單跑 playbook
r = ansible_runner.run(
    private_data_dir='/tmp/ansible_demo',
    playbook='site.yml',
)

print("狀態:", r.status)        # successful / failed
print("rc:", r.rc)
print("stats:", r.stats)

# 用 EE container 跑
r2 = ansible_runner.run(
    private_data_dir='/tmp/demo2',
    playbook='site.yml',
    container_image='quay.io/ansible/awx-ee:latest',
    container_runtime='podman',
    extravars={'app_version': 'v1.2.3'},
)

# 串流事件（debug / 即時 log）
for event in r2.events:
    if event['event'] == 'runner_on_failed':
        print("task 失敗:", event['event_data'])

30.6.2誰會用 ansible-runner

ⓘ ansible-runner 的真實使用者

① AWX / AAP Controller 自己——controller 觸發 job 時就是呼 ansible-runner；② 自寫 orchestration 工具——Python web app 透過 form 觸發 deployment；③ CI/CD plugin——Jenkins / GitLab plugin 整合 Ansible；④ Molecule（Ch28）—— Molecule 內部也是 runner。一般日常 ops 通常用 ansible-navigator，不必直接碰 runner。

30.7ansible-builder — 自建 EE

官方 EE 通常缺你需要的 collection / Python 套件 / CLI 工具。ansible-builder 是聲明式建 EE 的工具。

30.7.1execution-environment.yml — 聲明檔

yaml · execution-environment.yml — 完整範例 
---
version: 3            # 用最新 schema

images:
  base_image:
    name: quay.io/ansible/awx-ee:latest

dependencies:
  ansible_core:
    package_pip: ansible-core==2.18.*

  ansible_runner:
    package_pip: ansible-runner

  galaxy: requirements.yml     # Ansible collection 依賴
  python: requirements.txt       # Python 套件
  system: bindep.txt             # 系統 pkg（rpm / apt）

# 額外自訂步驟（罕用）
additional_build_steps:
  append_final: |
    RUN echo "Built: $(date)" > /etc/build-info
    USER root
yaml · requirements.yml — collection 依賴 
---
collections:
  - name: community.general
    version: ">=8.0.0"

  - name: cisco.ios
    version: ">=5.0.0"

  - name: amazon.aws

  - name: community.kubernetes
text · requirements.txt — Python 套件 
boto3>=1.28.0
botocore>=1.31.0
kubernetes>=27.0.0
hvac>=1.0.0          # HashiCorp Vault client
netaddr>=0.10.0
jmespath>=1.0.0
text · bindep.txt — 系統套件

git

30.7.2build / push / 用

bash · 完整 build & deploy 流程 
# 1) 安裝 builder
$ pip install ansible-builder

# 2) build image
$ ansible-builder build \
    --tag "registry.example.com/myorg/myapp-ee:1.0" \
    --container-runtime podman

# 3) 本機測試 — 跑 navigator 看 collection 都進去了沒
$ ansible-navigator collections \
    --eei "registry.example.com/myorg/myapp-ee:1.0"

# 4) push 到 registry
$ podman push registry.example.com/myorg/myapp-ee:1.0

# 5) 在 AAP / AWX UI 加 EE entry 指向此 tag
# 6) Job Template 選此 EE — 之後 job 都用這個 image 跑

30.8Automation Mesh — 跨網路執行

傳統 Ansible 痛點：control node 必須能 SSH 到所有被管 host。跨地區 / 跨雲 / 跨防火牆通常做不到。Automation Mesh 用 receptor 解決這個。

30.8.1三種 node 角色

Figure 30.4 — Automation Mesh 三種 node 角色

30.8.2三角色說明

🎛

Controller node

Control plane — web UI / scheduler / job dispatcher。不直接跑 playbook，只做派發。

⚡

Execution node

真正跑 playbook 的 node。透過 EE container 跑、SSH 到被管 host。靠近被管網路（cross firewall 友善）。

🔀

Hybrid node

同時是 controller + execution。小規模部署可不分；大規模 mesh 通常分開。

✓ Mesh 解決的真實場景

「公司在 Tokyo + Singapore + Frankfurt 各有 datacenter，每地一堆 host，office 在 SF」。沒 mesh：要在每地各架 controller，麻煩到爆。有 mesh：SF 一個 controller、各地各放 1-2 個 execution node、receptor 自動找最佳路徑。job 從 SF 觸發 → mesh 派到對應地區 execution → SSH 到 host。

30.9業界選擇建議

30.9.1四種規模對照

規模建議理由
個人 / 小團隊（< 5 人） 純 CLI + git 沒 RBAC / scheduling 需求 — platform 過度
中型團隊（5-50 人） AWX（自架） 免授權費、95% 功能、社群維護
大型組織（50+ 人） 先 AWX 試 → 升 AAP 需要認證 collection、24/7 support、cert pipeline
跨國 / 跨地區 AAP + Mesh 跨網路執行 mesh 必要、合規 audit 必要

30.9.2常見的 8 條業界實踐

①

EE 一律用容器、別用 venv

新專案直接 EE。venv 是過渡期解法，跨團隊一致性差。

②

本機開發用 navigator

開發測試與生產 AAP 用同一 EE — 「在我電腦能跑」變成真的。

③

EE 含版本 tag

myapp-ee:2.1 而非 :latest。job template 鎖版本、CVE 修補時只升那個版本。

④

private registry

Hub 或 Harbor / Quay。內部 EE 不上 public registry。

⑤

job template 是黑箱

讓 DBA / 安全團隊只看「按按鈕跑」介面，git 內細節對他們透明。

⑥

credential 走 secret store

AWX 內建 vault / SSM / HashiCorp Vault credential plugin。不要把 secret 放 inventory。

⑦

Survey 取代命令列參數

Job template 加 survey（web 表單問參數），非工程師也能跑。

⑧

Mesh 跨網路

多地區 / 跨防火牆別硬 SSH 全打通。Mesh execution node 部署到目標網路內、簡化網路規則。

30.10本章重點回顧

01

CLI 撐不住的五場景

scheduling / RBAC / audit / 多人協作 / 跨網路。出現三個就該升級 platform。

02

Tower / AWX / AAP 三者

Tower 已停產；AWX 開源 free；AAP 商用 paid（含 cert 與 support）。Controller = AWX = AAP 內的 web UI 元件。

03

三大組件

Controller（web UI / job）+ Hub（私有 Galaxy / EE registry）+ Mesh（跨網路 overlay）。

04

Execution Environment

OCI 容器 image — 含 ansible-core + collections + Python pkg + 系統工具。venv 的進化、跨環境一致。

05

ansible-navigator

本機跑 EE 的 CLI + TUI。--eei 指定 image。dev 與 prod 用同一 EE。

06

ansible-runner

Python lib — 程式內呼叫 Ansible。AWX / Molecule 內部都是用它。一般 ops 不必直接碰。

07

ansible-builder + execution-environment.yml

聲明式建 EE — base image + collection + Python + 系統 pkg。build → push → AAP UI 配置。

08

三 node 角色 mesh

Controller / Execution / Hybrid。Receptor 為底。跨網路友善。

練習題

  1. 初學者：用一頁紙寫「為什麼我們團隊（要 / 不要）AWX」。列出 5 個 CLI 撐不住的場景中你們有遇到幾個。
  2. 初學者：用 docker compose 或 minikube 部署一個 AWX 開發實例。瀏覽 web UI 找出 organization / project / inventory / job template 四個概念。
  3. 初學者：在 AWX 內建一個簡單 job template — project 指向某 git repo、playbook 指向 hello.yml。跑一次、看 audit log 記錄了什麼。
  4. 開發者：本機裝 ansible-navigator，navigator run 一個 playbook、用官方 EE。比較與直接 ansible-playbook 的差別。
  5. 開發者：寫一個 execution-environment.yml — 含 community.general / amazon.aws / boto3。ansible-builder build 產 image，用 navigator 確認 collection 有進去。
  6. 開發者：寫一段 Python 用 ansible-runner 程式化跑 playbook，串流 events 印出每個 task 結果。
  7. DevOps / SRE：對你公司目前的 Ansible 用量做評估 — 寫一頁 AWX vs AAP 採用分析（人數、地區、合規需求、預算）。給出 6 個月路線建議。
  8. DevOps / SRE：把現有 venv 設定轉成 EE — 寫 execution-environment.yml + requirements.yml + bindep.txt。在 CI 自動 build + push。
  9. DevOps / SRE：規劃多 region mesh 拓撲 — 1 controller + 3 region 各 2 execution node。畫架構圖、列各 node 的 receptor 配置要點。

Ansible Tower
Red Hat 早期的商業 Ansible web UI 產品（2017-2021）。已改名為 Ansible Automation Platform。文件中遇到 Tower 字樣多半是舊資料。
AWX

AAP 內的 web UI / API / job 引擎元件。等同 AWX 的商業認證版。多數時候「Controller = AWX」可互換。

Receptor
CNCF / Ansible 開源的 mesh networking framework。Automation Mesh 的底層協定。
Controller node
Mesh 中的 control plane node — 跑 web UI、scheduler、job dispatcher。不直接執行 playbook。
Execution node
Mesh 中真正跑 playbook 的 node。配 EE 容器、SSH 到被管 host。
Hybrid node
同時是 controller + execution 的 node。小規模單機部署用。
Execution Environment (EE)
OCI 容器 image，內含 ansible-core + ansible-runner + collections + Python pkg + 系統工具。venv 的容器化進化。
OCI image
Open Container Initiative 標準容器 image。Podman / Docker 都能跑。EE 是 OCI 標準的特殊化用途。
ansible-navigator
新一代 CLI + TUI。本機跑 playbook 在 EE container 內。--eei 指定 image。漸取代 ansible-playbook。
TUI（Text User Interface）
navigator 的文字介面模式。可瀏覽 collection / inventory / config 等。:doc / :run 等命令。
ansible-runner
Python library — 程式內呼叫 Ansible。AWX / AAP / Molecule 內部都靠它。一般 ops 不直接碰。
ansible-builder
build EE image 的 CLI。讀 execution-environment.yml 聲明檔產 OCI image。
execution-environment.yml
EE 聲明檔。指定 base_image / dependencies (ansible-core / galaxy / python / system) / 額外步驟。版本 3 是 2026 主流。
bindep.txt
系統套件聲明檔（rpm / dpkg）。openssh-clients [platform:rpm] 格式。

requirements.txt (Python)

quay.io/ansible/awx-ee

catalog.redhat.com
Red Hat 官方 EE 與 cert content registry。AAP 客戶用。
Job Template
AWX / AAP 中的 job 範本 — 綁 project + inventory + EE + credential。使用者按按鈕跑。
Survey
Job template 的互動表單。讓非工程師輸入參數（如 release version）後跑 job。
Project (AWX)
git repo 與 playbook 集合的抽象。AWX 從 git pull 得到 playbook。
Credential (AWX)
AWX 的 secret 抽象。SSH key / cloud key / vault password 都是 credential type。可整合外部 secret store。
Air-gapped
無網路連外的隔離環境（金融 / 軍工 / 醫療）。EE 容器 + private Hub 是 air-gapped 部署的標準解。
