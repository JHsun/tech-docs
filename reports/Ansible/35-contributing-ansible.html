35.1開源生態圖 — 哪個 repo 該貢獻到

「我想對 Ansible 貢獻」的第一個障礙：不知道該對哪個 repo 提 PR。Ansible 是 mono-name、multi-repo 生態。

35.1.1四大 repo 群

Figure 35.1 — Ansible 生態的四大 repo 群

35.1.2repo 對照表

Repo內容適合誰貢獻
ansible/ansible ansible-core 引擎 + builtin module（apt / copy / template / file 等） 核心引擎變更 / 修 builtin module bug
ansible-collections/community.general 最大社群 collection — 上百個跨類別 module 修 community module bug / 加新 module（最常見起步點）
ansible-collections/<X> 特定主題 collection（amazon.aws / cisco.ios / kubernetes.core 等） 該領域 expert 改 / 新增功能
ansible/ansible-documentation 主站 docs（除了 module reference 自動產出之外） 修 typo / 加教學 / 翻譯
ⓘ 找對 repo 的口訣

① 看 ansible-doc <module> 顯示的 collection 名 → 對該 collection repo 提 PR；② builtin（如 ansible.builtin.copy）→ ansible/ansible；③ 文件typo 看頁面右上角「Edit on GitHub」連結直接導去對的 repo。

35.2三種貢獻管道

「貢獻」≠「寫 code」。社群同樣需要文件、測試、用戶體驗回饋。

💻

Code 貢獻

修 bug、新增 module / plugin、改善效能、補 test。需 Python + Ansible 知識。本章主軸。

📚

Docs 貢獻

修 typo、補例子、翻譯、寫教學、整理 FAQ。非 coder 最佳入口——35.10 詳述。

🤝

Community 貢獻

review 別人 PR、回答 forum / Matrix 問題、triage issue、寫 blog post、辦聚會。沒寫一行 code 也能成 maintainer。

✓ Reviewer 是社群最缺的角色

大多數 PR 不缺人寫、缺人 review。即使你不會 Python — 用 user 角度看「這 module 文件清楚嗎？預設值合理嗎？例子能跑嗎？」每個 PR 都需要這層 review。Ansible 多位資深 maintainer 是從 review 起家的、不是從 code。

35.3找你的第一個 PR

35.3.1三步驟挑選

①

從你真的有用的 collection 開始

你日常用 amazon.aws → 對它貢獻最自然。對沒用過的 collection 提 PR 很難寫好。

②

在 GitHub 找 good-first-issue

各 repo 都標有 good_first_issue 或 easyfix label。明確 scope、maintainer 已預備指引。

③

選範圍小的（一個 module 一個 bug）

第一個 PR 不要碰大 refactor 或新 module。範圍小 → 容易過 review → 有信心做下一個。

35.3.2避開三大新人坑

⚠ 三個新人最常踩的坑

① 沒先開 issue 直接寫大 feature PR — maintainer 拒絕浪費你心血。先 issue 討論 scope；② 一個 PR 包多個變更（修 bug + refactor + 加 feature）— 拆 PR、單一 concern；③ 沒讀 collection 的 CONTRIBUTING.md — 每個 collection 規則略有不同（如 community.general 用 antsibull-nox / pre-commit），先讀。

35.4開發環境設置

35.4.1標準 fork + clone 流程

bash · 設置 community.general 開發環境 
# 1) 在 GitHub 上 fork 該 repo（按 Fork button）

# 2) clone 到正確路徑 — 必須是 collection 規範路徑
#    ansible_collections/<namespace>/<name>/
$ mkdir -p ~/ansible_collections/community
$ cd ~/ansible_collections/community
$ git clone git@github.com:YOUR_GH/community.general.git general
$ cd general

# 3) 加 upstream remote
$ git remote add upstream https://github.com/ansible-collections/community.general.git
$ git remote -v
# origin   ...your fork...
# upstream ...official...

# 4) 確認 default branch（通常 main）是最新
$ git checkout main
$ git fetch upstream
$ git merge upstream/main
$ git push origin main

35.4.2用 devcontainer（推薦）

bash · community.general 12.2.0+ 內建 devcontainer 
# 在 VS Code 內：
# 1) 開啟 community.general 目錄
# 2) 右下角會跳出「Reopen in Container」
# 3) 點下去 — VS Code 自動拉 image、安裝 ansible-core / nox / pre-commit / lint

# 不用 VS Code 也可以手動：
$ podman build -t devcontainer .devcontainer/
$ podman run -it --rm -v $(pwd):/workspace devcontainer bash

# container 內已裝好：
# - ansible-core（最新 stable）
# - antsibull-nox（formatter / lint / test 統一入口）
# - pre-commit（自動 ruff format）
# - 各種 dev tool
ⓘ 不用 devcontainer 的後備

沒 Docker / Podman 也能 dev。只要本機有 Python 3.10+ + ansible-core + 該 collection 規範的 dev tool（看 CONTRIBUTING.md）。但 devcontainer 解決「我電腦上能跑、PR 上 CI 跑不過」的痛——強烈推薦。

35.4.3分支命名與 commit 規範

bash · 開新 branch + commit signed 
# 開 feature/fix branch
$ git checkout -b fix/postgresql_db-encoding-utf8

# 改 code ...

# commit — ansible/ansible 強制要求 signed commit
$ git commit -S -m "postgresql_db: 修正 encoding 預設值未套用 UTF8"
# -S 用 GPG 簽（也可用 SSH key 或 S/MIME）

# 多數 collections 用 DCO（Developer Certificate of Origin）
# commit message 結尾加 Signed-off-by:
$ git commit -s -m "postgresql_db: 修正 encoding bug"
# -s 自動加 Signed-off-by: Your Name <email@example.com>

35.5.2PR description 範本

text · 好的 PR description 結構 
## SUMMARY
<一句話說明這 PR 做什麼>

修正 postgresql_db module 在指定 encoding=UTF8 時實際套用 LATIN1 的問題。

## ISSUE TYPE
- Bugfix Pull Request

## COMPONENT NAME
postgresql_db

## ADDITIONAL INFORMATION
Fixes #1234.

### 重現步驟（修前）
```yaml
- community.postgresql.postgresql_db:
    name: mydb
    encoding: UTF8
```
跑完後 `\l` 顯示 db 是 LATIN1。

### Root cause
src/.../postgresql_db.py L150 字串拼接寫死了 LATIN1，沒讀 encoding 參數。

### 改動
讀取 `module.params['encoding']` 帶入 SQL。
新增 integration test 涵蓋 UTF8 / LATIN1 / SQL_ASCII 三案例。

## CHANGELOG
新增 changelogs/fragments/1234-postgresql_db-encoding-fix.yml。

35.5.3Ansibot — 自動 triage

ⓘ Ansibot 是什麼

ansible/ansible repo 用 Ansibot bot 自動 triage PR — 分配 label、ping 對應 maintainer、提醒缺什麼（test / changelog）。社群 collection 多用 Ansibullbot（仿 Ansibot）。bot 會留 comment 告訴你下一步、跟著做就好。

35.6Changelog fragment — 每個 PR 都要

幾乎每個 collection 都要求每個 PR 附 changelog fragment。沒附 = CI fail = 不會 merge。

35.6.1fragment 檔規範

yaml · changelogs/fragments/1234-postgresql_db-encoding-fix.yml 
---
bugfixes:
  - postgresql_db - 修正 encoding 參數未正確套用導致 db 永遠是 LATIN1 的 bug
    (https://github.com/ansible-collections/community.postgresql/pull/1234).

35.6.2fragment 五大 type

Type用途例
bugfixes修 bug修正 encoding 參數套用
minor_changes非破壞性改善新增可選參數 / 改善錯誤訊息
major_changes大改動但不 breaking升級 SDK 版本影響整 collection
breaking_changes破壞性 — 只能 major releasemodule 預設行為變了使用者要改 playbook
deprecated_features標記要廢棄的功能某參數將在 X.0 移除
trivial無 user-facing 影響（infra / refactor）不會出現在 changelog
✓ fragment 寫法格式

① scope - 描述 格式（scope 通常是 module / plugin name）；② 開頭小寫、結尾句點；③ 結尾掛 PR / issue link；④ 新增 module / plugin 不需 fragment（changelog 工具會自動偵測 version_added）。

35.7三層 test

35.7.1三層 test 對照

層級檢查什麼典型命令
Sanity 程式碼風格、import、PEP 8、文件 schema、ansible-doc 能 parse ansible-test sanity --docker
Unit module 內部邏輯（用 pytest mock 外部依賴） ansible-test units --docker
Integration module 真的對某環境跑、確認結果正確 ansible-test integration foo --docker

35.7.2跑 test 範例

bash · 三層 test 完整流程 
# 用 nox（community.general 12+）— 一鍵跑常用 test set
$ nox -Re formatters         # formatter 與 lint
$ nox -Re sanity              # sanity test
$ nox -Re unit                # unit test

# 直接用 ansible-test（可細粒度控制）
$ ansible-test sanity --docker plugins/modules/postgresql_db.py
$ ansible-test units --docker tests/unit/plugins/modules/test_postgresql_db.py

# integration test — 需要 docker / podman
$ ansible-test integration --docker postgresql_db

# 跑單一測試案例
$ ansible-test integration --docker postgresql_db -v

# 看哪些 sanity 規則可以跳（罕用）
$ ansible-test sanity --list-tests

35.7.3寫 unit test 範例

python · tests/unit/plugins/modules/test_xxx.py 結構 
import pytest
from unittest import mock
from ansible_collections.community.general.plugins.modules import xxx

def test_normal_case():
    # 設參數
    args = {"name": "foo", "state": "present"}

    with mock.patch("some.external.api") as mock_api:
        mock_api.return_value = {"status": "ok"}
        result = xxx.do_something(args)

    assert result["changed"] is True
    assert result["name"] == "foo"

def test_invalid_input_raises():
    with pytest.raises(ValueError):
        xxx.do_something({"name": ""})

@pytest.mark.parametrize("input_val,expected", [
    ("UTF8", "UTF8"),
    ("utf8", "UTF8"),
    ("LATIN1", "LATIN1"),
])
def test_encoding_normalization(input_val, expected):
    assert xxx.normalize_encoding(input_val) == expected

35.8Code review 文化

35.8.1當 PR 作者

🎯

耐心等

maintainer 多半是志工。typical review SLA 是幾天到幾週。一週沒回再禮貌 ping。

💬

把 review comment 當禮物

review 有人花時間看你的 code 是好事。即使要改、即使語氣冷——對事不對人。

🔄

每條 comment 回應

同意改 → 改完 reply「Done」。不同意 → 解釋為何、討論。不要默默改 + push，maintainer 不知道你回應了。

🧹

conflict / rebase 自己處理

main branch 變了 → git fetch upstream && git rebase upstream/main 後 force push。不要丟給 maintainer。

35.8.2當 reviewer

✅

從 user 角度看

不必懂 Python 內部也能 review。「這 module 文件清楚嗎？例子能跑嗎？預設值合理嗎？」就有價值。

🚫

避免 bikeshedding

不要為「縮排該 4 還 2」「變數名 foo 還 bar」這種小事爭辯。CI 強制 lint 已處理風格問題。

🌱

對新手友善

看到新 contributor → 多解釋、給連結 / 例子。第一次貢獻體驗決定他會不會回來。

🏷

明確 verdict

用 GitHub「Approve / Request changes / Comment」三選一。不要曖昧 — 「應該改但我不確定」要說清楚。

35.9與 maintainer 健康互動

35.9.1四個常見溝通通路

通路用途
GitHub issue / PR正式提案 / bug report / code 討論。所有決策都要落到這裡。
Matrix（#ansible-community:ansible.com）即時討論、找人、quick question。但 decision 要回到 GitHub。
forum.ansible.com長篇討論、社群提案、新手 Q&A。漸取代 mailing list。
Working Group meeting各 collection 有定期 video meeting（看 wiki / forum 公告）。新人也可參加。

35.9.2避免三種反模式

⚠ 三種會讓 maintainer 退避的行為

① Ghost：開 PR → maintainer review → 你再也沒回。半年後再開新 PR、信任度歸零；② 催：「為何還沒 merge」每天問一次。maintainer 是志工、不是員工；③ 戰略式 hijack：別人 PR 開到一半你開類似但更大的 PR 想搶。先在原 PR 留 comment 表達意見、邀作者合作。

35.10文件貢獻 — 非 coder 的入口

不會 Python 也能對 Ansible 大有貢獻。文件常常是新手挫折的源頭——你最知道哪些不清楚。

35.10.1三個層次

⚡

Quick fix — Edit on GitHub

docs.ansible.com 每頁右上角有 Edit on GitHub。typo / 缺例子 / 連結壞 直接點 → GitHub 編輯器 → propose change → 自動產 PR。5 分鐘搞定。

📖

Module description 改善

每個 module 的文件其實是 module Python 檔內 DOCUMENTATION 區塊（YAML）。改它 = 對 collection 提 PR。改善 description / 加 example / 補 note 都很歡迎。

📚

Tutorial / how-to / FAQ

整篇新教學或大改 — 對 ansible/ansible-documentation 提 PR。寫 reStructuredText（rST），格式類似 Markdown。

35.10.2好文件貢獻 PR 的特徵

text · 好文件 PR 的 3 個特徵 
① 具體問題 — 不是「文件有點不清楚」、是「第 3 段第 2 句的 example 缺 quotes 跑會錯」

② 改進對比 — PR description 寫
   修前：<貼原文>
   修後：<貼新版>
   為何：<reader 看不懂的點>

③ 維持風格 — 新增章節用既有風格，不要混入個人習慣
   reStructuredText 慣例：標題用 = - ~ 三層、code block 用 .. code-block::

35.11本章重點回顧

01

四大 repo 群

ansible/ansible（核心）/ ansible-collections/*（100+ 主題）/ ansible-documentation（站文件）/ Galaxy NG（Hub）。找對 repo 是第一步。

02

三種貢獻管道

code（修 bug / 加 module）/ docs（改 typo / 寫教學）/ community（review / 答問）。沒 code 也能成 maintainer。

03

找第一個 PR

從用過的 collection 開始 / good_first_issue label / 範圍小單一 concern。避免大 feature PR 初次嘗試。

04

devcontainer 是友善起點

community.general 12+ 內建。VS Code 一鍵啟動完整 dev 環境。「我電腦能跑、CI 不過」基本消失。

05

PR 9 步驟

fork → branch → 改 + test + changelog → 本機 nox → signed commit → push → PR → CI → review → merge。

06

Changelog fragment

每 PR 都要（除新 module）。scope - description 格式、結尾掛 PR link。沒附 = CI fail。

07

三層 test

sanity（lint + schema）/ units（pytest mock）/ integration（真環境）。本機 nox 或 ansible-test 都能跑。

08

溝通與互動

GitHub 落結論 / Matrix 即時 / forum 長文 / WG meeting 視訊。避免 ghost、催單、hijack 三反模式。

練習題

  1. 初學者：對 docs.ansible.com 任意一頁找出一個 typo / 不清楚的句子。用「Edit on GitHub」流程提 PR。觀察 GitHub bot 自動加哪些 label。
  2. 初學者：找 community.general repo 的 good_first_issue label issues。看 5 個、判斷哪個你能在 1-2 小時搞定。記下選擇理由。
  3. 初學者：對某個你常用 module 找官方 doc → 寫一份「我覺得不清楚的 3 點」筆記。如果有信心 → 提 doc PR。
  4. 開發者：fork community.general、用 devcontainer 開起來、確認能跑 nox -Re sanity 通過（不改任何 code）。記下耗時。
  5. 開發者：選一個你用過的 module、看其 source。挑一個小改善（如增加錯誤訊息細節）→ 寫 PR。包含 test + changelog fragment。觀察 CI 結果。
  6. 開發者：對某個 PR 做 review — 不必你的 PR、找一個 open 的別人 PR、留至少 3 個有建設性的 comment（用戶角度即可）。
  7. DevOps / SRE：研究你公司用的某個 collection 的 release cycle — 看過去 12 月發了多少版、哪些是 major / minor / patch、哪些 PR 是社群外貢獻。寫 1 頁分析。
  8. DevOps / SRE：對你公司常用的 5 個 collection 列出各自 maintainer 與 working group。確認你 follow 它們的 release announcement（forum / GitHub release）。
  9. DevOps / SRE：把公司內 N 年累積的 internal Ansible 工具 review 一遍 — 哪些可以開源捐回社群（變 collection）？寫一頁提案含 scope / 法務考量 / 維運承諾。

本章詞彙表

ansible/ansible repo
Ansible 核心引擎與 builtin module 的 GitHub repo。修 builtin（apt / copy / template / file 等）對這裡提 PR。
ansible-collections org
GitHub organization，下含 100+ 個社群維護的 collection（community.general / community.postgresql / 等）。多數 module bug 修這邊。
ansible/ansible-documentation
Ansible 主站 docs（docs.ansible.com）的 source。除了 module reference 是自動產的、其餘都這裡改。
community.general
最大社群 collection。涵蓋跨類別 module（系統 / 通訊 / 雲端 / DB / 監控 / 等）。新手第一個 PR 常選這裡。
good_first_issue / easyfix label
GitHub issue label。標記「適合新手」的小範圍 issue。新手第一個 PR 從這裡找。
CONTRIBUTING.md
每個 repo 根目錄的貢獻指引。必讀。各 repo 規則略有不同（test 工具、lint 規則、changelog 格式）。
devcontainer
VS Code 的 development container 標準。community.general 12.2.0+ 內建。.devcontainer/ 目錄定義。一鍵啟動完整 dev 環境。
fork + clone 規範路徑
collection 必須 clone 到 ansible_collections/<namespace>/<name>/ 路徑、ansible-test 等工具才能正確找到 module。
upstream remote
Git 慣例 — 你的 fork 是 origin、官方 repo 是 upstream。git fetch upstream 同步官方變更。
DCO (Developer Certificate of Origin)
commit 簽署聲明 — 你有權貢獻此 code。多數 collection 用 DCO 而非 CLA。git commit -s 自動加 Signed-off-by: 結尾即可。
Signed commit (ansible/ansible)
對 ansible/ansible repo 強制要求所有 commit GPG / SSH / S/MIME 簽章。比 DCO 更嚴。
devel branch
ansible/ansible repo 的開發 branch。所有 PR 對這裡開、不對 stable branch。
main / master branch (collections)
多數 collection 用 main / master 為開發 branch。所有 PR 對這裡開。
Ansibot
ansible/ansible repo 的 triage bot。自動分配 label、ping maintainer、提醒缺漏（test / changelog）。
Ansibullbot
社群 collection 用的 bot（如 community.general 用過）。功能類似 Ansibot。
Patchback
GitHub bot — 自動 backport PR 到 stable branch。maintainer 加 backport label 即觸發。
Changelog fragment
每 PR 在 changelogs/fragments/ 加一個 yaml 檔，描述本 PR 對使用者的影響。檔名通常 <PR#>-<短描述>.yml。
Fragment type
fragment 內可用 key：bugfixes / minor_changes / major_changes / breaking_changes / deprecated_features / trivial。
antsibull-nox / nox
community.general 等 collection 的統一 dev tool 入口。nox -Re sanity / nox -Re unit 跑各層 test。
ansible-test
ansible-core 的 official test 工具。ansible-test sanity / units / integration 三大命令。collection 開發必裝。
Sanity test
輕量靜態檢查 — pylint / pep8 / 文件 schema / import 規則 / module 結構。秒級 to 分鐘級。
Unit test
用 pytest 寫的 module 內部邏輯測試。mock 外部 API。檔在 tests/unit/plugins/。
Integration test
對真環境執行 module。需要 docker / podman / VM。檔在 tests/integration/targets/<module>/。
pre-commit hook
git commit 前自動跑的 lint / format。community.general 用 ruff format。pre-commit install 後 git commit 會自動跑。
ruff format
新一代 Python formatter（替代 black + isort + flake8 部分功能）。Rust 寫的、極快。
Code review three verdicts
GitHub PR review 三選一：Approve（同意 merge）/ Request changes（要求改）/ Comment（觀察 / 提問、不投票）。
Bikeshedding
軟體文化詞 — 為瑣碎風格爭辯（縮排空格 / 變數命名等）而忽略真正重點。code review 該避免。
Matrix（社群即時通訊）
Ansible 社群官方即時通訊（替代 IRC）。主 channel #ansible-community:ansible.com。但決策仍要落 GitHub。
forum.ansible.com
Ansible 社群 Discourse forum。長篇討論 / 提案 / 新手 Q&A。漸取代 mailing list。
Working Group (WG)
各 collection / 主題的工作小組。定期 video meeting。社群決策的場域。
Edit on GitHub
docs.ansible.com 每頁右上角的連結。直接導去對應 GitHub source 編輯器、5 分鐘提 typo PR。文件貢獻最快入口。
reStructuredText (rST)
Ansible 主站文件用的標記語言。類 Markdown 但更結構化。標題用 = - ~ 表示三層、code block 用 .. code-block::。
module DOCUMENTATION block
module Python 檔內的 YAML 區塊。模組文件來源（ansible-doc 與 docs.ansible.com module reference 都讀這個）。改文件 = 改這個。
version_added
module / option 的 metadata。標記「此功能從哪版開始有」。新增 module 不需 changelog fragment、changelog 工具會自動從 version_added 抓。
