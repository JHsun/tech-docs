6.1Blocks — Task 分組

當 playbook 內 5–10 個 task 邏輯上屬於同一群（都做 nginx 設定、都需要相同的 sudo / when / tags），逐個重複寫這些 directive 既冗長又易錯。Block 解決這個問題——把相關 task 包在一起，共用 directive。

6.1.1Block 的基本語法

yaml · 沒用 block 與用 block 的對照 
# ─── 沒用 block：每個 task 都要重複 become / when / tags ───
tasks:
  - name: 安裝 nginx
    ansible.builtin.apt: { name: nginx }
    become: true
    when: ansible_os_family == "Debian"
    tags: [nginx]

  - name: 部署 nginx 設定
    ansible.builtin.copy: { src: nginx.conf, dest: /etc/nginx/nginx.conf }
    become: true
    when: ansible_os_family == "Debian"
    tags: [nginx]

  - name: 啟動 nginx
    ansible.builtin.service: { name: nginx, state: started }
    become: true
    when: ansible_os_family == "Debian"
    tags: [nginx]

# ─── 用 block：directive 寫一次，內部 task 全部繼承 ───
tasks:
  - name: 部署 nginx
    block:
      - name: 安裝 nginx
        ansible.builtin.apt: { name: nginx }

      - name: 部署 nginx 設定
        ansible.builtin.copy: { src: nginx.conf, dest: /etc/nginx/nginx.conf }

      - name: 啟動 nginx
        ansible.builtin.service: { name: nginx, state: started }
    become: true                                # ← 整個 block 共用
    when: ansible_os_family == "Debian"           # ← 整個 block 共用
    tags: [nginx]                              # ← 整個 block 共用
ⓘ Block 可繼承的 directives

become、become_user、when、tags、vars、environment、delegate_to、run_once、ignore_errors、any_errors_fatal 等。Task 層級若再寫同名 directive，會覆蓋從 block 繼承的值。

6.2錯誤處理：rescue 與 always

Block 真正威力在於它的三段式錯誤處理，類似程式語言的 try / catch / finally。當 block 內任一 task 失敗，自動跳到 rescue: 區塊救援；無論成敗，always: 區塊都會執行。

6.2.2實際範例：資料庫遷移失敗自動回滾

yaml · 三段式錯誤處理 
- name: 執行資料庫遷移（含失敗回滾）
  block:
    - name: 備份資料庫
      ansible.builtin.shell: "pg_dump myapp_db > /backup/before-migration.sql"
      become_user: postgres

    - name: 執行 schema 變更
      ansible.builtin.command: "psql myapp_db -f /tmp/migration.sql"
      become_user: postgres

    - name: 驗證新 schema
      community.postgresql.postgresql_query:
        db: myapp_db
        query: "SELECT version FROM schema_versions ORDER BY id DESC LIMIT 1"
      register: schema_check
      failed_when: "schema_check.query_result[0].version != '2.5.0'"

  rescue:
    - name: 遷移失敗 — 自動回滾
      ansible.builtin.shell: "psql myapp_db < /backup/before-migration.sql"
      become_user: postgres

    - name: 通知 PagerDuty
      ansible.builtin.uri:
        url: "{{ pagerduty_webhook }}"
        method: POST
        body_format: json
        body:
          message: "DB migration failed on {{ inventory_hostname }}, rolled back"

  always:
    - name: 無論成敗都記錄
      ansible.builtin.lineinfile:
        path: /var/log/migrations.log
        line: "{{ ansible_date_time.iso8601 }} - migration attempted on {{ inventory_hostname }}"
        create: true
✓ Rescue 救回後 task 視為成功

如果 block 失敗、rescue 成功救回，原本失敗的 task 在 PLAY RECAP 中算是 rescued，整體 play 仍會繼續執行後面的 tasks。但 PLAY RECAP 仍會顯示 rescued=N 提醒你發生過救援。

6.2.3rescue 內可用的特殊變數

變數意義
ansible_failed_task失敗的 task 物件（含 name、action 等）
ansible_failed_result失敗 task 的完整 result（msg、stderr、rc 等）
yaml · 在 rescue 中使用失敗資訊 
  rescue:
    - name: 記錄是哪個 task 失敗
      ansible.builtin.debug:
        msg: |
          失敗的 task: {{ ansible_failed_task.name }}
          錯誤訊息: {{ ansible_failed_result.msg }}
          return code: {{ ansible_failed_result.rc | default('N/A') }}
⚠ rescue 不會救所有錯誤

rescue 只救「task 執行時失敗」（如命令 rc != 0、模組回報失敗）。不會救：① YAML 語法錯誤、② 模組名打錯、③ 主機 unreachable（連 SSH 都連不上）。後面這些是「playbook 結構問題」而非 runtime 錯誤。

6.3Tags — 外科手術式選擇執行

大型 playbook 完整跑一次可能要 30 分鐘。但 90% 情況你只想跑「設定檔更新」那 2 分鐘的部分。Tags 就是這個外科刀——給 task 加標籤，執行時用 --tags 只跑特定標籤的 task。

6.3.1基本用法

yaml · 給 task 加 tags 
tasks:
  - name: 安裝 nginx 套件
    ansible.builtin.apt: { name: nginx, state: present }
    tags:
      - install
      - packages

  - name: 部署 nginx 設定檔
    ansible.builtin.copy: { src: nginx.conf, dest: /etc/nginx/nginx.conf }
    tags:
      - configure
      - nginx

  - name: 部署 SSL 憑證
    ansible.builtin.copy: { src: site.crt, dest: /etc/ssl/certs/ }
    tags:
      - configure
      - tls
bash · 用 tags 選擇執行 
# 只跑設定相關
$ ansible-playbook site.yml --tags configure

# 跑多個 tag (OR 邏輯)
$ ansible-playbook site.yml --tags "install,configure"

# 跳過某個 tag (跑全部 except packages)
$ ansible-playbook site.yml --skip-tags packages

# 列出 playbook 內所有定義的 tags
$ ansible-playbook site.yml --list-tags
# 輸出範例：
#   playbook: site.yml
#       play #1 (webservers): Configure web servers TAGS: []
#           TASK TAGS: [configure, install, nginx, packages, tls]

6.3.2內建特殊 tag：always 與 never

Tag行為典型用途
always 不管你選什麼 tag，這個 task 都會跑（除非用 --skip-tags always） 前置檢查、變數設定、fact 收集
never 預設不會跑，只在 --tags never 或明確指定其他 tag 才會跑 破壞性操作、清理腳本、debug 工具
yaml · always 與 never 範例 
tasks:
  - name: 前置驗證 — 永遠先跑
    ansible.builtin.assert:
      that: "ansible_distribution_major_version is version('20', '>=')"
    tags: [always]                  # 不管 --tags 選什麼都會執行

  - name: 部署應用
    ansible.builtin.copy: { src: app, dest: /opt/app }
    tags: [deploy]

  - name: 破壞性 — 清空資料庫
    community.postgresql.postgresql_db:
      name: myapp
      state: absent
    tags: [never, wipe-db]      # 只有明確 --tags wipe-db 才執行

6.3.3Tag 繼承：block / play / role

除了 task 層，tags 也能加在 block、play、import_role 層。所有 tag 會向下繼承到子 task。

yaml · 不同層級加 tag 
- hosts: webservers
  tags: [web]                       # Play 層 — 此 play 內所有 task 都繼承 web tag
  tasks:
    - name: 部署 nginx 套裝
      block:
        - name: 裝套件
          ansible.builtin.apt: { name: nginx }
        - name: 部署設定
          ansible.builtin.copy: { src: nginx.conf, dest: /etc/nginx/ }
      tags: [nginx]                  # Block 層 — 兩個子 task 同時擁有 web + nginx

    - name: 部署監控 agent
      ansible.builtin.apt: { name: node_exporter }
      tags: [monitoring]              # Task 層 — 此 task 擁有 web + monitoring

6.3.4Tag 設計策略

①

分類維度，不要混雜

挑 2–3 種維度堅持：例如 component（nginx / postgres / app）、phase（install / configure / deploy）、action（rolling-restart / cleanup）。team 內共識比 tag 細節更重要。

②

每 task 不要超過 3 個 tag

tags: [nginx, web, packages, install, apt, server, infra] 是反例——tag 太多反而沒人能預測 --tags X 會跑到什麼。

③

Handler 也要加 tag

用 --tags configure 跑時，notify 的 handler 如果沒有 matching tag，不會執行。最簡單做法：給 handler 加 tags: [always]，或對應 tag 的同名 tag。

④

列出再執行

跑前先 --list-tags 看實際定義了哪些 tag、--list-tasks --tags X 看會跑到哪些 task。比直接執行安全得多。

6.4.5實用組合

bash · 生產環境的標準執行流程 
# 1) CI: syntax check（merge 前）
$ ansible-playbook site.yml --syntax-check

# 2) Staging: 完整 dry-run + diff
$ ansible-playbook -i inventories/staging site.yml --check --diff

# 3) Staging: 真實執行
$ ansible-playbook -i inventories/staging site.yml

# 4) Production: 滾動部署 + 限制目標
$ ansible-playbook -i inventories/production site.yml \
    --limit "webservers" \
    --tags configure

# 5) 失敗從中斷處續跑
$ ansible-playbook site.yml \
    --start-at-task "部署 nginx 設定檔"

# 6) 連線層 debug
$ ansible-playbook site.yml -vvvv 2>&1 | tee debug.log

6.5多 Play 編排

一個 playbook 可以包含多個 play，每個 play 對不同 hosts 做不同的事。多 play 是表達「跨主機編排」的核心機制。

6.5.1典型場景：多層應用部署

yaml · 多 play 部署 web + db 
---
# Play 1: 先處理資料庫層
- name: 設定 PostgreSQL 資料庫
  hosts: databases
  become: true
  tasks:
    - name: 安裝 postgresql
      ansible.builtin.apt: { name: postgresql, state: present }

    - name: 建立應用 DB 與 user
      community.postgresql.postgresql_db:
        name: myapp_db
        state: present
      become_user: postgres

# Play 2: 再部署應用層 (依賴 db 已就緒)
- name: 部署應用伺服器
  hosts: webservers
  become: true
  vars:
    db_host: "{{ groups['databases'][0] }}"     # 跨 host 取得 db hostname
  tasks:
    - name: 安裝 web 服務
      ansible.builtin.apt: { name: nginx, state: present }

    - name: 部署應用設定 (連到 db_host)
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/myapp/app.conf

# Play 3: 最後做整體健康檢查 (任何一台 control 上)
- name: 部署後健康檢查
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: 驗證 web 端點回應
      ansible.builtin.uri:
        url: "https://api.example.com/health"
        status_code: 200

6.5.2Play 間共享資訊：hostvars 與 groups

ⓘ Magic variables 預覽

多 play 場景常用兩個 magic variables：groups['groupname'] 取得某群組的 host 清單；hostvars['hostname'] 跨 host 取得另一台的變數或 facts。第 7 章會深入講變數系統。

yaml · 跨 play 取資訊 
# 在 webservers 的 play 中，取得 databases 群組第一台的 IP
- name: 產生應用設定檔
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/myapp/app.conf
  vars:
    db_primary_host: "{{ hostvars[groups['databases'][0]]['ansible_default_ipv4']['address'] }}"

6.6Include 與 Import — 切分大檔案

Playbook 寫到 200 行以後就該考慮切檔。Ansible 提供兩種切分機制：include_* 與 import_*。它們看似相同但行為差異關鍵。

6.6.1核心差異：靜態 vs 動態

類型import_*include_*
展開時機 Playbook 解析階段（靜態，跑之前就展開） 執行到那一行才展開（動態，runtime）
--list-tasks 看得到 是 否（runtime 才知道）
支援 loop / when 動態決定 否（when 變成繼承給每個內部 task） 是（真正動態決定要不要 include）
tags 套用範圍 傳遞給內部所有 task 只套用到 include 這個動作本身
handler 支援 能 notify 內部 handler 只能 notify 已知名稱

6.6.2主要的 include / import 變體

用途動態（推薦多數場景）靜態
引用一組 tasksinclude_tasksimport_tasks
引用一個 roleinclude_roleimport_role
引用整個 playbook（不存在）import_playbook

6.6.3實際範例

yaml · 用 include_tasks 切分 
# playbooks/site.yml ─ 主入口
- name: 完整部署
  hosts: webservers
  become: true
  tasks:
    - name: 引用安裝相關 tasks
      ansible.builtin.include_tasks: tasks/install.yml

    - name: 引用設定相關 tasks
      ansible.builtin.include_tasks: tasks/configure.yml

    - name: 依 OS 不同引用不同 tasks（動態）
      ansible.builtin.include_tasks: "tasks/{{ ansible_os_family | lower }}.yml"

# tasks/install.yml ─ 子檔案（不是完整 playbook，只是 tasks 列表）
- name: 安裝 nginx
  ansible.builtin.apt: { name: nginx, state: present }

- name: 安裝 logrotate
  ansible.builtin.apt: { name: logrotate, state: present }
yaml · 用 import_playbook 串聯多個 playbook 
# site.yml ─ 主入口，把多個 playbook 串成完整流程
---
- ansible.builtin.import_playbook: infrastructure.yml
- ansible.builtin.import_playbook: database.yml
- ansible.builtin.import_playbook: webservers.yml
- ansible.builtin.import_playbook: monitoring.yml

# 注意：import_playbook 必須在 playbook top-level，不能放在 tasks: 內

6.6.4選擇指南

ⓘ 怎麼選？

預設用 include_*——尤其當引用前需要動態決定（loop / when 條件依賴前面的結果）。用 import_* 當你要 --list-tasks 看得到全貌、或 tags 要繼承給內部 task。2026 業界共識：寫 role 時 main.yml 用 include_tasks 切分子檔案，主 playbook 用 import_playbook 串聯多個 playbook。

6.7實戰範例：完整可用的部署 Playbook

把第 6 章上下兩篇所有概念熔成一份能直接用的部署 playbook：

yaml · playbooks/deploy.yml — 生產級範例 
---
- name: 部署 web 應用 (含錯誤處理 / tags / 滾動部署)
  hosts: webservers:&production
  become: true
  serial: "25%"
  max_fail_percentage: 10

  vars:
    app_version: "2.5.0"

  pre_tasks:
    - name: 前置檢查 — disk 空間
      ansible.builtin.assert:
        that: "item.size_available > 1073741824"
        fail_msg: "剩餘空間不足 1GB"
      loop: "{{ ansible_mounts | selectattr('mount', 'equalto', '/') | list }}"
      tags: [always]

  tasks:

    # ─── 套件安裝 (block) ───
    - name: 安裝相關套件
      block:
        - name: 更新 apt cache
          ansible.builtin.apt: { update_cache: true, cache_valid_time: 3600 }

        - name: 安裝 web 套件
          ansible.builtin.apt:
            name: [nginx, python3-certbot-nginx]
            state: present
      tags: [install, packages]

    # ─── 部署應用 (含錯誤回滾) ───
    - name: 部署應用 (失敗自動回滾)
      tags: [deploy]
      block:
        - name: 備份目前版本
          ansible.builtin.copy:
            src: /opt/myapp/
            dest: /opt/myapp.bak/
            remote_src: true

        - name: 部署新版本
          ansible.builtin.unarchive:
            src: "https://releases.example.com/myapp-{{ app_version }}.tar.gz"
            dest: /opt/myapp/
            remote_src: true

        - name: 部署設定檔
          ansible.builtin.template:
            src: app.conf.j2
            dest: /etc/myapp/app.conf
          notify: restart myapp

      rescue:
        - name: 部署失敗 — 還原備份
          ansible.builtin.copy:
            src: /opt/myapp.bak/
            dest: /opt/myapp/
            remote_src: true

        - name: 通知告警
          ansible.builtin.uri:
            url: "{{ alert_webhook }}"
            method: POST
            body: '{"text": "Deploy failed and rolled back on {{ inventory_hostname }}"}'

  post_tasks:
    - name: 健康檢查
      ansible.builtin.uri:
        url: "http://localhost/health"
        status_code: 200
      retries: 5
      delay: 5
      delegate_to: "{{ inventory_hostname }}"
      tags: [always, healthcheck]

  handlers:
    - name: restart myapp
      ansible.builtin.service:
        name: myapp
        state: restarted
      listen: restart myapp

6.8本章重點回顧

01

Block 共享 directives

把相關 task 包進 block，become / when / tags / vars 等 directive 寫一次、所有子 task 繼承。減少重複也提高可讀性。

02

rescue / always 是 try/catch/finally

Block 內失敗 → rescue 救援；無論成敗 → always 收尾。Rescue 內可用 ansible_failed_task / ansible_failed_result 取錯誤資訊。

03

Tags 是外科刀

30 分鐘的 playbook 用 --tags configure 縮成 2 分鐘。設計時挑 2–3 個維度（component / phase / action），每 task 不超過 3 個 tag。

04

always 與 never tag

tags: [always] 永遠跑（前置檢查必備）。tags: [never] 預設不跑（破壞性操作的安全網）。

05

Handler 也要加 tag

用 --tags configure 跑時，notify 的 handler 若無 matching tag 不會觸發。最簡解：handler 加 tags: [always]。

06

多 play 編排跨主機

一份 playbook 多個 play，依序對 db / web / monitoring 等不同 hosts 做不同事。用 hostvars[] 與 groups[] 跨 play 取資訊。

07

include vs import

include_* = runtime 動態（支援 loop/when 真正分流）。import_* = 解析時靜態（--list-tasks 看得見、tags 繼承給內部）。預設 include，特殊情況才 import。

08

標準執行流程五步

--syntax-check → --list-tasks → --check --diff → 實際執行 → 失敗用 --start-at-task 續跑。

練習題

  1. 初學者：把第 6 章 上 你寫的 playbook 用 block 重構：把相關 task 分組，把重複的 become: true 提到 block 層。
  2. 初學者：給 playbook 內每個 task 加 tags。執行 ansible-playbook --list-tags 看你定義了哪些 tag。
  3. 初學者：用 --tags configure 只跑設定相關 task，觀察 PLAY RECAP 看跳過了多少 task。
  4. 開發者：寫一個 block 含 rescue，故意讓 block 內某個 task 失敗（如執行不存在的命令），確認 rescue 內的 task 確實被觸發。
  5. 開發者：在 rescue 內用 debug 印出 ansible_failed_task.name 與 ansible_failed_result.msg，確認你能取到失敗詳情。
  6. 開發者：把 200+ 行的 playbook 用 include_tasks 拆成 3–4 個子檔案。比較 --list-tasks 的輸出（會看到 include 但不會展開），改用 import_tasks 觀察差異。
  7. DevOps / SRE：寫一個 multi-play playbook，先在 db host 上做 schema migration，再在 web host 上 rolling restart。確認失敗時 db 的 rescue 會觸發回滾，web 部分不會啟動。
  8. DevOps / SRE：用 tags: [never] 給某個破壞性 task（如 wipe-cache），確認預設執行不會 跑到它，只在 --tags wipe-cache 才執行。
  9. DevOps / SRE：把 6.7 完整範例 deploy.yml 套用到你的 staging 環境，先 --check --diff dry-run，確認回滾邏輯後再實際執行。

本章詞彙表

Block
把多個 task 包成一組的容器。共享 become / when / tags 等 directive，並支援 rescue / always 錯誤處理。
rescue
Block 內任一 task 失敗時自動執行的救援區塊。類似 try/catch 的 catch。
always
無論 block 成敗都會執行的區塊。類似 try/catch/finally 的 finally。
ansible_failed_task / ansible_failed_result
rescue 內可用的兩個 magic variables，分別含失敗的 task 物件與其執行結果（msg、stderr、rc 等）。
force_handlers
Play 層 directive 或 CLI flag --force-handlers。即使 play 中途失敗也強制執行所有 notify 過的 handlers。
Tags
給 task / block / play / role 加標籤。執行時用 --tags / --skip-tags 選擇執行哪些。
always tag (內建)
特殊 tag。標記了它的 task 永遠執行，無論 --tags 選什麼。
never tag (內建)
特殊 tag。標記了它的 task 預設不 執行，只在明確 --tags 指定時才執行。
--list-tasks / --list-tags / --list-hosts
三大「列出但不執行」flag。執行 playbook 前的安全網。
--start-at-task
從指定名稱的 task 開始執行。失敗後從中斷處續跑用。
--step
互動模式：每個 task 執行前都暫停詢問。緊張部署時用。
--check / --diff
Dry-run + 顯示變更前後差異。重大變更前必須走這一步。
multi-play
一個 playbook 內含多個 play，每個 play 對不同 hosts 做不同事。表達跨主機編排的核心機制。
hostvars / groups (magic variables)
多 play 跨 host 取資訊用。groups['db'] 取得 db 群組成員清單；hostvars['db01'].ansible_default_ipv4.address 取得 db01 的 IP。
include_tasks / include_role
動態（runtime）展開的引用機制。支援 loop / when 真正動態決定是否執行。
import_tasks / import_role / import_playbook
靜態（解析時）展開的引用機制。--list-tasks 看得到完整內部，tags 會繼承給內部 task。
delegate_to
Task 層 directive，讓這個 task 在指定的另一台 host 上執行（而非當前 host）。常用於 health check、跨主機觸發等場景。
