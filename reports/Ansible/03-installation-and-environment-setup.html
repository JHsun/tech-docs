第 3 章 — 安裝與環境準備

本章是動手章節。讀完後你會擁有：可運作的 control node（包含 ansible-core 2.20）、設定好的 SSH 金鑰、一個能 ping 通的 managed node，以及第一個 ad-hoc 命令的成功回應。我們從 Linux/macOS/WSL 三條路徑開始，著重 2026 年 Ubuntu 24.04 / Debian 12 / RHEL 9 帶來的 PEP 668 「externally-managed-environment」陷阱與 pipx 解法。Windows 不能直接當 control node，但可以是 managed node，本章末會說明 WSL 路徑。

3.1.1四種主要安裝方式的取捨

方式 優點 缺點 建議使用情境
pipx 隔離 venv、不污染系統 Python、CLI 自動加 PATH 需要先裝 pipx；inject 第三方套件比 pip 複雜 2026 年最推薦，個人 / 開發機

ⓘ 我在生產環境用哪個？

個人開發機用 pipx；CI/CD pipeline 用 Execution Environment（容器）；多人共用的中央 control node 用 venv 加上 requirements.txt 與 collections-requirements.yml 鎖版本。三套組合涵蓋 95% 場景。

3.2Linux / macOS 安裝實戰

截至 2026 年 5 月，ansible-core 2.20.4 是最新穩定版（ansible community package 也是當月發布），需要 Python ≥ 3.12。下面分平台給出可直接複製貼上的命令。

3.2.1Ubuntu 24.04 / Debian 12（PEP 668 環境）

這兩個發行版預設啟用 PEP 668 「externally-managed-environment」保護，pip install --user 會直接被擋下來。強烈建議走 pipx。

bash · Ubuntu 24.04 / Debian 12 — pipx 路徑（推薦） 
# ① 系統依賴：Python 3.12 + pipx + venv 模組
$ sudo apt update
$ sudo apt install -y python3 python3-pip python3-venv pipx

# ② 確保 ~/.local/bin 在 PATH
$ pipx ensurepath
$ source ~/.bashrc   # 或開新終端

# ③ 安裝完整 ansible community package（注意 --include-deps 不可省）
#    沒加 --include-deps 只會裝 ansible 一個 CLI，缺 ansible-playbook、ansible-galaxy 等
$ pipx install --include-deps ansible

# ④ 驗證
$ ansible --version
ansible [core 2.20.4]
  config file = None
  configured module search path = ['~/.ansible/plugins/modules', ...]
  ansible python module location = ~/.local/share/pipx/venvs/ansible/lib/python3.12/...
  python version = 3.12.x

# ⑤ 額外：注入 cloud / dnspython 等可選相依套件到同一個 venv
$ pipx inject ansible dnspython jmespath netaddr passlib
⚠ 常見錯誤：error: externally-managed-environment

如果你忽略警告硬要 pip install ansible，會看到：

This environment is externally managed... 解法不是加 --break-system-packages（會破壞系統套件管理），而是改用 pipx 或 venv。臨時測試可加 --user，但不推薦長期使用。

3.2.2RHEL 9 / Rocky Linux 9 / AlmaLinux 9

bash · RHEL 9 系列 — dnf 路徑（簡單） 
# 方式 A：透過 EPEL 倉儲安裝
$ sudo dnf install -y epel-release
$ sudo dnf install -y ansible-core
# 注意：EPEL 通常落後 1–2 個 ansible-core 主版本

# 方式 B：透過 pip 安裝最新版（建議走 venv 避免污染系統 Python）
$ sudo dnf install -y python3.12 python3.12-pip
$ python3.12 -m venv ~/ansible-venv
$ source ~/ansible-venv/bin/activate
(ansible-venv) $ pip install --upgrade pip ansible
(ansible-venv) $ ansible --version
ⓘ Red Hat Ansible Automation Platform 的差異

如果你的組織有 AAP 訂閱，control node 通常透過 RHEL 內建的 ansible-automation-platform-2.x 倉儲安裝，會給你對齊 AAP 預設版本 的 ansible-core（目前是 2.18 / 2.16）。這跟 PyPI 最新版有意保守的落差，第 24 章 Execution Environment 會展開細節。

3.2.3macOS（Homebrew + pipx）

bash · macOS 安裝 
# ① 確保 Homebrew 已安裝（若沒裝先到 brew.sh）
$ brew --version

# ② 安裝 Python 3.12+ 與 pipx
$ brew install python@3.12 pipx
$ pipx ensurepath
$ source ~/.zshrc

# ③ 裝 ansible
$ pipx install --include-deps ansible

# ④ 提高 file handle 上限（macOS 預設太低，forks > 15 容易撞上限）
$ sudo launchctl limit maxfiles unlimited

# ⑤ 驗證
$ ansible --version

3.2.4Windows — 使用 WSL2

Windows 原生不支援 Ansible 當 control node，這是架構性限制而非懶得做：Ansible 大量依賴 POSIX 介面（fork、signal、SSH socket）。最佳路徑是在 Windows 上裝 WSL2 + Ubuntu，然後在 WSL 內依照 3.2.1 的步驟安裝。

powershell · Windows 11 安裝 WSL2 
# 以系統管理員身分執行 PowerShell
PS> wsl --install -d Ubuntu-24.04

# 重開機後，從開始功能表打開 Ubuntu，建立帳號，
# 然後在 Ubuntu 終端機內依照 3.2.1 的步驟安裝 ansible

3.3.1準備一台 managed node 的最小檢查清單

從 control node 開始 SSH 過去之前，managed node 上要先確認下列項目：

  • SSH daemon 運行中：sudo systemctl status ssh 或 sshd
  • Python 已安裝且在 PATH 上：python3 --version 顯示 3.9 以上
  • 建立非 root 的 ansible 專用使用者（強烈建議）：
bash · 在 managed node 上建立 ansible 帳號 
# 在每台 managed node 上執行（一次性 bootstrap）
$ sudo useradd -m -s /bin/bash ansible
$ sudo passwd ansible          # 設一個臨時密碼，後面用金鑰取代

# 給予無密碼 sudo（讓 unattended playbook 不會卡在密碼提示）
$ echo 'ansible ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/ansible
$ sudo chmod 0440 /etc/sudoers.d/ansible
$ sudo visudo -c                # 驗證 sudoers 語法正確
⚠ NOPASSWD 的安全考量

給 ansible 帳號 NOPASSWD 等於讓任何能登入該帳號的人擁有 root 權限。生產環境建議：① ansible 帳號的 SSH 金鑰嚴格控管（不可有 passphrase 為空 + 放在多人共用機器）；② 限制可登入該帳號的 IP（在 sshd_config 用 Match）；③ 用 auditd 記錄所有 sudo 命令。第 28 章「安全性與合規」會深入。

3.4SSH 金鑰設定（控制 node ↔ managed node 認證）

Ansible push 模式靠 SSH 金鑰認證。雖然能用密碼，但每個 task 都會卡認證 prompt，無法 unattended 執行。務必設定金鑰。

3.4.1產生 Ed25519 金鑰

2026 年新建金鑰一律用 Ed25519（除非要管理 OpenSSH 7.8 之前的老系統，那才退而用 RSA 4096）。Ed25519 比 RSA 短、快、強、抗量子化研究進度也較佳。

bash · 在 control node 產生金鑰 
# 產生專用於 ansible 的金鑰（與你個人 SSH 金鑰分開存放）
$ ssh-keygen -t ed25519 -C "ansible@$(hostname)" -f ~/.ssh/id_ansible

# 系統會問 passphrase：
#   - 個人開發機建議設一個（搭配 ssh-agent 快取）
#   - 自動化 CI runner 通常設空（接受對應風險）

# 產生兩個檔案：
#   ~/.ssh/id_ansible      ← 私鑰，權限 600，永遠不要外流
#   ~/.ssh/id_ansible.pub  ← 公鑰，貼到 managed node 的 authorized_keys

$ ls -l ~/.ssh/id_ansible*
-rw-------  1 you  staff   411  May  7 09:00 /home/you/.ssh/id_ansible
-rw-r--r--  1 you  staff   105  May  7 09:00 /home/you/.ssh/id_ansible.pub

3.4.2把公鑰部署到 managed node

bash · 用 ssh-copy-id 部署 
# 最簡方式：ssh-copy-id（內建於大多數 Linux/macOS）
$ ssh-copy-id -i ~/.ssh/id_ansible.pub ansible@web01.example.com

# 會被要求輸入 ansible 帳號的密碼（首次認證）
# 之後 SSH 就改用金鑰了

# 驗證金鑰登入成功（不應再要求密碼）
$ ssh -i ~/.ssh/id_ansible ansible@web01.example.com 'whoami'
ansible

# 多台主機批次部署：用 for loop（首次 bootstrap 限定）
$ for h in web01 web02 db01; do
>     ssh-copy-id -i ~/.ssh/id_ansible.pub ansible@$h.example.com
> done

3.4.3用 ssh-agent 快取 passphrase（個人機推薦）

bash · 啟動 ssh-agent 並載入金鑰 
# macOS：keychain 已內建整合，重啟也能保留
$ ssh-add --apple-use-keychain ~/.ssh/id_ansible

# Linux：手動啟動 agent
$ eval "$(ssh-agent -s)"
$ ssh-add ~/.ssh/id_ansible

# 列出已載入金鑰
$ ssh-add -l

3.4.4~/.ssh/config — 把連線細節集中管理

與其每次跑 ansible 都要記住 user、port、key 路徑，不如在 ~/.ssh/config 一次寫清楚。Ansible 會自動讀取這個檔案。

ini · ~/.ssh/config 
# 對所有 *.example.com 主機統一使用 ansible 帳號 + ed25519 金鑰
Host *.example.com
    User ansible
    IdentityFile ~/.ssh/id_ansible
    IdentitiesOnly yes
    ServerAliveInterval 60
    ConnectTimeout 10

# 透過跳板機 (bastion) 連到內網主機
Host bastion
    HostName 203.0.113.10
    User ansible
    IdentityFile ~/.ssh/id_ansible

Host 10.10.*.*
    ProxyJump bastion
    User ansible
    IdentityFile ~/.ssh/id_ansible

3.5第一個 Ad-hoc 命令：ansible -m ping

萬事俱備。我們要跑 Ansible 的「Hello World」——對 managed node 發出一個 ping 模組命令。注意：這不是 ICMP ping，而是 Ansible 的健康檢查模組，會驗證：① SSH 認證 OK、② 遠端 Python 可用、③ ansible 帳號有執行模組的權限。

3.5.1建立第一個 inventory

ini · ~/ansible-lab/inventory.ini 
# 最簡 inventory：列出主機 + 群組

[webservers]
web01.example.com
web02.example.com

[databases]
db01.example.com  ansible_user=postgres   # 個別 host 覆寫使用者

[all:vars]
ansible_user=ansible
ansible_ssh_private_key_file=~/.ssh/id_ansible

3.5.2跑 ping

bash · 第一個 Ansible 命令 
$ cd ~/ansible-lab
$ ansible all -i inventory.ini -m ping

# 預期成功輸出：
web01.example.com | SUCCESS => {
    "ansible_facts": {
        "discovered_interpreter_python": "/usr/bin/python3.12"
    },
    "changed": false,
    "ping": "pong"
}
web02.example.com | SUCCESS => {...}
db01.example.com  | SUCCESS => {...}
✓ 看到 "ping": "pong" 代表什麼？

三件事都成功了：① SSH 連得進去、② 遠端有可執行的 Python、③ ansible 帳號能執行模組並把結果寫回 stdout。這個 5 秒的小測試之後會幫你省下無數小時的 debug 時間——任何 playbook 失敗時，第一步都應該是用 ansible all -m ping 確認連線層正常。

3.5.3常見 ping 失敗的排除流程

Figure 3.2 — Ping 失敗的排除決策樹
bash · ping 失敗時的 debug 黃金組合 
# 1. 先用 -vvvv 看 Ansible 跑了什麼 SSH 命令
$ ansible web01 -i inventory.ini -m ping -vvvv 2>&1 | grep "SSH:"

# 2. 把那段 SSH 命令拷貝出來手動跑，看真正的錯誤
$ ssh -vvv -i ~/.ssh/id_ansible ansible@web01.example.com 'echo OK'

# 3. 強制使用密碼認證（如果你還沒部署金鑰）
$ ansible web01 -i inventory.ini -m ping --ask-pass

# 4. 顯式指定 Python 解譯器（如果遠端 Python 不在預設位置）
$ ansible web01 -i inventory.ini -m ping \
    -e "ansible_python_interpreter=/usr/bin/python3.9"

# 5. 清掉舊的 SSH ControlPersist socket（卡死的話）
$ rm -rf ~/.ansible/cp/*

3.5.4更多 Ad-hoc 命令範例

趁這個機會，看一下 ansible CLI 的常見用法。後面章節會有完整介紹，這裡先讓你嚐鮮。

bash · 實用 ad-hoc 命令 
# 收集所有主機的 facts（系統資訊）
$ ansible all -i inventory.ini -m setup

# 在所有 webservers 上跑 uptime
$ ansible webservers -i inventory.ini -a "uptime"

# 用 sudo 安裝套件
$ ansible webservers -i inventory.ini -b -m ansible.builtin.package \
    -a "name=htop state=present"

# 把 control node 上的檔案複製到所有 webservers
$ ansible webservers -i inventory.ini -m ansible.builtin.copy \
    -a "src=/etc/hosts dest=/tmp/hosts.backup"

# 限制只跑前兩台（測試用）
$ ansible webservers -i inventory.ini -m ping --limit "web01,web02"

# 並行度提高到 50（預設 5 太慢）
$ ansible all -i inventory.ini -m ping -f 50

3.6建立第一個專案目錄結構

跑通 ad-hoc 後，下一步是建立可長期使用的專案目錄。下面是 2026 年業界主流的最小可行結構，後面所有章節都會以這個結構為基礎延伸。

text · ~/ansible-lab/ 目錄結構 
~/ansible-lab/
├── ansible.cfg                # 專案設定（取代全域 /etc/ansible/）
├── inventory/
│   ├── production.ini         # 生產環境主機
│   ├── staging.ini            # 測試環境主機
│   ├── group_vars/
│   │   ├── all.yml            # 所有主機共用變數
│   │   └── webservers.yml     # 群組層級變數
│   └── host_vars/
│       └── web01.example.com.yml  # 個別 host 變數
├── playbooks/
│   ├── site.yml               # 主入口 playbook
│   └── deploy.yml             # 部署用 playbook
├── roles/                     # 自訂 roles（第 10 章詳述）
├── collections/               # 專案內 collections
├── requirements.yml           # 鎖定 collections 版本
└── .gitignore                 # 排除 *.retry、vault 密碼檔等

3.6.1第一個 ansible.cfg

專案根目錄下的 ansible.cfg 會自動覆蓋系統預設值。下面是融合本書前兩章建議的「黃金預設」：

ini · ansible.cfg 
[defaults]
# 預設 inventory 路徑（用相對路徑指向專案內）
inventory      = ./inventory/production.ini

# 預設並行 host 數（預設 5 太慢）
forks          = 50

# 不要在 ~/ 留 retry 檔
retry_files_enabled = false

# 預設不檢查 host key（首次連線會自動接受）
# 生產環境建議改 True 並維護 known_hosts
host_key_checking = false

# 啟用 fact caching，加速跨 playbook 執行
fact_caching          = jsonfile
fact_caching_connection = .ansible-cache
fact_caching_timeout    = 3600

# 強制 FQCN（提早把規範立起來）
collections_path = ./collections

[ssh_connection]
# 第 2 章重點：開啟 pipelining 與 ControlPersist
pipelining = True
ssh_args   = -o ControlMaster=auto -o ControlPersist=10m
transfer_method = smart

[privilege_escalation]
become      = false      # 預設不 sudo，需要時 task 個別 opt-in
become_method = sudo
become_user  = root

3.7本章重點回顧

01

四種安裝路徑

2026 年首選 pipx（個人）、venv + pip（CI）、OS package（內網求穩）、EE 容器（生產）。Ubuntu 24.04 / Debian 12 / RHEL 9 全部進入 PEP 668 時代，pip 直接裝會被擋。

02

--include-deps 不可省

用 pipx 裝 ansible 一定要加 --include-deps，否則只會裝到 ansible 一個 CLI，缺 ansible-playbook、ansible-galaxy、ansible-vault 等。

03

Python 雙線需求

ansible-core 2.20：control node 需 Python ≥ 3.12，managed node 需 ≥ 3.9。舊 RHEL 7、Ubuntu 18.04 必須升級或淘汰。

04

Ed25519 是新標準

新建金鑰一律用 ssh-keygen -t ed25519。配合 ssh-agent 快取 passphrase、用 ~/.ssh/config 集中管理連線細節。

05

"ping": "pong" 是黃金信號

任何 playbook 失敗，第一步 跑 ansible all -m ping。它確認連線層、認證層、Python 層全部正常，才能往應用層 debug。

06

專案結構與 ansible.cfg

用專案內的 ansible.cfg + requirements.yml 取代全域設定。Pipelining、ControlPersist、forks=50 列入預設。新人 clone 後跑兩條命令就能上工。

練習題

  1. 初學者：在你電腦上用本章 3.2 的方式裝好 ansible-core 2.20，跑 ansible --version 確認版本與 Python 路徑。截圖保存。
  2. 初學者：用 VirtualBox / Multipass / Lima 開一台 Ubuntu 24.04 VM 當 managed node，依 3.3.1 建立 ansible 帳號，從你的本機 ping 通它。
  3. 初學者：故意把 inventory 中的 hostname 改錯（例如改成 web99），觀察 ansible -m ping 的錯誤訊息，再用 -vvvv 看完整 SSH 命令。
  4. 開發者：建立兩個 venv，一個裝 ansible-core 2.18、一個裝 2.20，比較 ansible-doc -l | wc -l 看模組數量差異。練習在不同 venv 之間切換。
  5. 開發者：寫一個 bash 腳本 bootstrap.sh，能在乾淨的 Ubuntu 24.04 上自動完成「安裝 ansible + 產生金鑰 + 部署到 N 台 managed nodes」的全流程。
  6. DevOps / SRE：用 3.6 的目錄結構建立你的 ansible-lab，把它推到 git。確認 .gitignore 有效阻止 vault 密碼意外進 commit。
  7. DevOps / SRE：在你的 CI（GitHub Actions / GitLab CI）建立一個 job，能在每次 push 時自動執行 ansible-galaxy collection install -r requirements.yml 並跑 ansible-playbook --syntax-check。
  8. DevOps / SRE：盤點公司目前的 managed node Python 版本分布，找出最舊的那台。決策：升級 / 隔離（用較舊 ansible-core 版本管它）/ 淘汰。

本章詞彙表

PEP 668 / externally-managed-environment
Python 包裝管理規範，允許 OS 發行版標記其 Python 為「由系統管理」，讓 pip 預設拒絕安裝套件到系統路徑。Ubuntu 24.04+、Debian 12+、RHEL 9 都採用。對策：用 venv 或 pipx。
pipx
把 Python CLI 應用裝在獨立 venv 並把 entry point 連到 ~/.local/bin，使用上像系統工具但不污染系統 Python。pipx install --include-deps ansible 是 2026 年的推薦做法。
venv (virtual environment)
標準函式庫的 python3 -m venv 建立的隔離 Python 環境。每個專案一個 venv 是業界共識。
ssh-copy-id
OpenSSH 自帶工具，把本地公鑰附加到遠端的 ~/.ssh/authorized_keys，並設好權限。首次部署金鑰最常用。
Ed25519
基於 Curve25519 的數位簽章演算法，2014 年發表。比 RSA 4096 更快、更短、安全性同等。OpenSSH 6.5+ 全面支援，2026 年新建金鑰的首選。
ssh-agent
OpenSSH 的金鑰快取常駐程式，在 session 期間記住已解鎖的私鑰 passphrase，避免每次都要輸入。macOS 用 --apple-use-keychain 整合 Keychain 持久化。
~/.ssh/config
OpenSSH 客戶端設定檔，支援萬用字元（Host *.example.com）、ProxyJump（跳板機）等。Ansible 預設讀取這個檔案。
NOPASSWD（sudoers）
sudoers 設定，讓特定使用者執行 sudo 不需密碼。Ansible unattended 執行的必要條件，但有安全成本。
ansible_python_interpreter
Inventory 變數，指定 managed node 上要使用的 Python 路徑。當預設 auto-discovery 找錯版本時用它強制指定。
Ad-hoc command
不寫 playbook、直接從命令列執行的 Ansible 指令。格式 ansible <pattern> -m <module> -a <args>。適合一次性任務、debug、health check。第 5 章詳述。
ping module（不是 ICMP）
Ansible 內建模組 ansible.builtin.ping，做 SSH + Python 端到端健康檢查，回傳 pong 表示連線層完全正常。
fact_caching
把 setup 模組收集到的 facts 快取到磁碟，跨 playbook 重用。可大幅縮短 playbook 啟動時間。第 25 章詳述。
