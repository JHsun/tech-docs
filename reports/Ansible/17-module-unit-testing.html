第 17 章 — 模組單元測試

寫了 module（Ch14）、plugin（Ch15）、inventory plugin（Ch16）後，下個問題：怎麼知道改 code 沒把它弄壞？答案是單元測試。Ansible 模組測試比一般 Python 測試難一點——模組設計上會 sys.exit 結束程序、會打外部 API 或執行 shell command、會直接讀 stdin 拿參數。本章教你怎麼把這些「副作用」一一馴服：用 set_module_args 注入參數、用 AnsibleExitJson / AnsibleFailJson 攔截 exit、用 mock / Moto / Localstack 偽裝外部世界。然後示範對 Ch14 的 feature_flag 模組寫完整測試，最後整合到 collection 結構與 GitHub Actions CI。讀完這章你能對所有自定模組做安全的重構與發版。

本章覆蓋官方文件對應：Unit Testing Ansible Modules · Adding unit tests to a collection
開發者必讀（全章） DevOps / SRE 必讀（全章 — 特別 17.8 collection 內測試結構與 17.9 CI 整合）

17.1為什麼測試自定模組

Ansible 模組常被視為「腳本」——能跑就好。但實際上它們是長期維護的程式碼資產，理由如下：

🛡

抓 regression

新版 ansible-core 釋出、Python 升級、依賴 library bump——任何上游變動都可能砸壞既有模組。沒測試就要靠跑 playbook 才發現。

🔧

安全重構

自家模組會慢慢長成 500+ 行的怪物。沒測試誰敢動它？有測試你能放心抽 helper、改流程、優化效能。

📋

文件即測試

「state=absent 但物件不存在時 changed 應該是什麼？」這類設計決策最好寫在測試裡——既驗證行為又解釋意圖。

🚀

CI 整合與發版信心

Collection 要進 Galaxy / Automation Hub 都要求測試覆蓋。CI 跑通才能 merge / release，這是專業團隊的最低標準。

17.3三大測試模式

Ansible 模組測試的核心難題是「我怎麼讓模組可測試」。實務上分三種模式應對：

模式適用場景特點
① set_module_args + Exit 攔截 純檔案 / 純運算邏輯模組 注入參數、用 exception 取代 sys.exit。最常用。
② Mock 外部依賴 呼叫 run_command / API / file I/O 的模組 用 unittest.mock 把 socket / requests / subprocess 等替換成假物件。
③ 假 cloud 環境 呼叫雲端 SDK（boto3 等）的模組 Moto 偽造 AWS API、Localstack 跑整套假 AWS。

本章詳述模式 ① 與 ②（覆蓋 90% 場景），模式 ③ 在 17.10 補充說明。

17.4set_module_args helper

所有 Ansible 模組測試的起點都是這個 helper。它解決最基本問題：怎麼在 pytest 裡把 task 參數傳進模組？

17.4.1問題

正常情況下，Ansible 把 task 參數寫進一個臨時 JSON 檔，模組從 stdin 讀。pytest 環境沒有這個機制。set_module_args 偷偷在 Python 層面把 JSON 寫到 basic._ANSIBLE_ARGS——AnsibleModule 建構時會優先檢查這裡。

17.4.2標準 helper code

python · tests/unit/conftest.py — 共用 helper 
from __future__ import absolute_import, division, print_function
__metaclass__ = type

import json
import pytest
from ansible.module_utils import basic
from ansible.module_utils.common.text.converters import to_bytes


def set_module_args(args):
    """把 task args 注入到模組會讀到的位置。"""
    payload = json.dumps({'ANSIBLE_MODULE_ARGS': args})
    basic._ANSIBLE_ARGS = to_bytes(payload)


class AnsibleExitJson(Exception):
    """當模組 module.exit_json() 時 raise 此例外，
    讓測試碼 catch 並讀取結果。"""


class AnsibleFailJson(Exception):
    """當模組 module.fail_json() 時 raise 此例外。"""


def exit_json(*args, **kwargs):
    """模擬 exit_json — 把 kwargs 包成 exception args 拋出。"""
    if 'changed' not in kwargs:
        kwargs['changed'] = False
    raise AnsibleExitJson(kwargs)


def fail_json(*args, **kwargs):
    """模擬 fail_json — 把 kwargs 包成 exception args 拋出。"""
    kwargs['failed'] = True
    raise AnsibleFailJson(kwargs)


@pytest.fixture
def patch_ansible_exits(mocker):
    """自動把 exit_json / fail_json 替換成上面的 raise 版本。"""
    mocker.patch(
        'ansible.module_utils.basic.AnsibleModule.exit_json',
        side_effect=exit_json,
    )
    mocker.patch(
        'ansible.module_utils.basic.AnsibleModule.fail_json',
        side_effect=fail_json,
    )

17.5第一個測試：feature_flag 模組

用 Ch14 的 feature_flag 模組為例，寫一份完整測試。模組功能回顧：管理 JSON 設定檔內的 feature flag，三個參數 config_path / flag_name / enabled，支援 idempotency 與 check_mode。

17.5.1測試檔骨架

python · tests/unit/plugins/modules/test_feature_flag.py 
from __future__ import absolute_import, division, print_function
__metaclass__ = type

import json
import pytest

from ansible_collections.myorg.internal.plugins.modules import feature_flag
from ...conftest import (
    set_module_args, AnsibleExitJson, AnsibleFailJson, patch_ansible_exits,
)


class TestFeatureFlag:

    def test_missing_required_args(self, patch_ansible_exits):
        """漏 required 參數應該 fail。"""
        set_module_args({})        # 空參數
        with pytest.raises(AnsibleFailJson) as exc:
            feature_flag.main()
        result = exc.value.args[0]
        assert result['failed'] is True
        assert 'missing required' in result['msg'].lower()

17.5.2測 idempotency — 沒變化的情況

python · 模組值已是期望值時 changed=False 
    def test_idempotent_no_change(self, tmp_path, patch_ansible_exits):
        """flag 已經是期望值 → changed=False。"""
        # 1) 準備檔案 — 已含目標值
        cfg = tmp_path / 'config.json'
        cfg.write_text(json.dumps({'dark_mode': True}))

        # 2) 設參數呼叫
        set_module_args({
            'config_path': str(cfg),
            'flag_name': 'dark_mode',
            'enabled': True,
        })

        with pytest.raises(AnsibleExitJson) as exc:
            feature_flag.main()

        result = exc.value.args[0]
        assert result['changed'] is False
        assert '已是' in result['msg']

        # 3) 額外驗證 — 檔案內容沒被改
        assert json.loads(cfg.read_text()) == {'dark_mode': True}
ⓘ tmp_path fixture

pytest 內建 tmp_path fixture 提供每個測試獨立的臨時目錄，測試結束自動清掉。寫測試模組讀寫真實檔案的最佳工具——不要 mock open()，直接給真檔案測。

17.5.3測 changed — 真的有變化的情況

python · 值不同會更新 
    def test_changed_when_value_differs(self, tmp_path, patch_ansible_exits):
        """flag 值不同 → changed=True 且檔案被更新。"""
        cfg = tmp_path / 'config.json'
        cfg.write_text(json.dumps({'dark_mode': False}))     # 現況 false

        set_module_args({
            'config_path': str(cfg),
            'flag_name': 'dark_mode',
            'enabled': True,                        # 期望 true
        })

        with pytest.raises(AnsibleExitJson) as exc:
            feature_flag.main()

        result = exc.value.args[0]
        assert result['changed'] is True
        assert result['previous_value'] is False
        assert result['current_value'] is True

        # 確認檔案真的被改
        assert json.loads(cfg.read_text()) == {'dark_mode': True}

17.5.4測 check_mode

python · check_mode 應該回報 changed 但不寫檔 
    def test_check_mode_does_not_write(self, tmp_path, patch_ansible_exits):
        """check mode 下回報 changed=True 但不實際寫檔。"""
        cfg = tmp_path / 'config.json'
        cfg.write_text(json.dumps({'dark_mode': False}))
        original = cfg.read_text()

        set_module_args({
            'config_path': str(cfg),
            'flag_name': 'dark_mode',
            'enabled': True,
            '_ansible_check_mode': True,         # ← 觸發 check_mode
        })

        with pytest.raises(AnsibleExitJson) as exc:
            feature_flag.main()

        result = exc.value.args[0]
        assert result['changed'] is True            # 報告會 changed
        assert cfg.read_text() == original          # 但檔案沒被動

17.5.5測錯誤處理

python · 損壞的 JSON 應該 fail_json 
    def test_malformed_json_fails(self, tmp_path, patch_ansible_exits):

17.6Mock 外部依賴

上節範例的 feature_flag 模組只跟檔案系統互動，能用 tmp_path 給真檔案。但其他模組常呼叫 shell command、打外部 API、查 DNS——這些必須 mock，否則測試會：① 慢、② 不可重現、③ 在 CI 跑不過。

17.6.1Mock run_command（shell 命令）

模組透過 module.run_command() 跑 shell。測試時把它 patch 掉。

python · 假設模組呼叫 systemctl 檢查服務 
# 假想模組：plugins/modules/check_service.py
# def main():
#     module = AnsibleModule(...)
#     rc, stdout, stderr = module.run_command(['systemctl', 'is-active', name])
#     module.exit_json(active=(rc == 0), status=stdout.strip())


def test_service_is_active(mocker, patch_ansible_exits):
    mock_run = mocker.patch(
        'ansible.module_utils.basic.AnsibleModule.run_command',
        return_value=(0, 'active\n', ''),       # rc, stdout, stderr
    )

    set_module_args({'name': 'nginx'})
    with pytest.raises(AnsibleExitJson) as exc:
        check_service.main()

    result = exc.value.args[0]
    assert result['active'] is True
    assert result['status'] == 'active'

    # 驗證 mock 確實被呼叫且帶對的參數
    mock_run.assert_called_once_with(['systemctl', 'is-active', 'nginx'])


def test_service_is_inactive(mocker, patch_ansible_exits):
    # systemctl is-active 對停止的 service 回 rc=3
    mocker.patch(
        'ansible.module_utils.basic.AnsibleModule.run_command',
        return_value=(3, 'inactive\n', ''),
    )
    set_module_args({'name': 'nginx'})
    with pytest.raises(AnsibleExitJson) as exc:
        check_service.main()
    assert exc.value.args[0]['active'] is False

def test_ticket_create_happy_path(mocker, patch_ansible_exits):

17.7.1fixture：共用 setup

python · 用 fixture 抽出共用準備 
@pytest.fixture
def cfg_with_flags(tmp_path):

17.7.2parametrize：表格驅動測試

python · 一份 test 跑多組情境 
@pytest.mark.parametrize('initial, target, expected_changed', [
    # initial flag 值, 期望值, 預期 changed
    (False, True,  True),     # 從 false 改 true
    (True,  False, True),     # 從 true 改 false
    (True,  True,  False),    # 一樣不變
    (False, False, False),    # 一樣不變
])
def test_idempotency_table(
    tmp_path, patch_ansible_exits,
    initial, target, expected_changed,
):
    cfg = tmp_path / 'config.json'
    cfg.write_text(json.dumps({'flag': initial}))

    set_module_args({
        'config_path': str(cfg),
        'flag_name': 'flag',
        'enabled': target,
    })

    with pytest.raises(AnsibleExitJson) as exc:
        feature_flag.main()

    assert exc.value.args[0]['changed'] is expected_changed
✓ parametrize 是測試品質的力量倍增器

一份 test 函式自動跑 4 個案例。新加 case 只需多一行 tuple。pytest 輸出會把每個 case 當成獨立 test 顯示，失敗時清楚指出哪個組合掛了。對 idempotency / boundary case / 各種輸入組合的覆蓋特別有用。

17.9CI 整合：GitHub Actions

把測試自動化跑在每次 PR / push。下面是 collection 的標準 GitHub Actions workflow，跨多個 Python 版本與 ansible-core 版本測試。

yaml · .github/workflows/tests.yml 
---
name: Collection Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  sanity:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
        with:
          path: ansible_collections/myorg/internal
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - name: Install ansible-core
        run: pip install ansible-core
      - name: Run sanity tests
        working-directory: ansible_collections/myorg/internal
        run: ansible-test sanity --local --python ${{ matrix.python }}

  units:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
        with:
          path: ansible_collections/myorg/internal
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python }}
      - name: Install dependencies
        run: pip install ansible-core pytest pytest-mock
      - name: Run unit tests
        working-directory: ansible_collections/myorg/internal
        run: ansible-test units --local --python ${{ matrix.python }}

17.9.1測試矩陣設計

①

跨 Python 版本

3.10 / 3.11 / 3.12 — 涵蓋目前主流版本。版本不同的 syntax / library 行為差異常常踩雷。

②

跨 ansible-core 版本

關鍵——你的模組要在 stable / devel 都能跑。matrix 加 ansible: ['stable-2.18', 'devel']。

③

fail-fast: false

matrix 設 fail-fast: false，讓所有組合都跑完，一次看到全部失敗的 cell，不要一掛就停。

④

cache pip

setup-python 加 cache: pip 大幅加速 — 從 30 秒裝套件壓到 3 秒。

17.10進階：Moto / Localstack 偽造雲端

如果你的模組打 AWS / GCP / Azure SDK，前面的 mock 方式會變很冗長（要 mock 一堆 boto3 client method）。業界用兩種更專業的工具：

17.10.1Moto — 純 Python 的假 AWS

python · 用 Moto 測 boto3-based 模組 
import boto3
from moto import mock_ec2


@mock_ec2
def test_create_ec2_instance(patch_ansible_exits):
    # Moto 啟用後 boto3 會被 hook 進假環境
    # 你的模組裡的 boto3.client('ec2') 自動連到 Moto

    set_module_args({
        'name': 'test-instance',
        'ami_id': 'ami-12345678',
        'instance_type': 't3.micro',
        'region': 'us-east-1',
    })

    with pytest.raises(AnsibleExitJson) as exc:
        my_ec2_module.main()

    result = exc.value.args[0]
    assert result['changed'] is True

    # 直接用 boto3 驗證 instance 真的被建立
    ec2 = boto3.client('ec2', region_name='us-east-1')
    instances = ec2.describe_instances()
    assert len(instances['Reservations']) == 1

17.11本章重點回顧

01

set_module_args 是起點

標準 helper 把 args 注入 basic._ANSIBLE_ARGS，讓 AnsibleModule 建構時讀到。所有測試的第一步。

02

AnsibleExitJson / AnsibleFailJson

把 exit_json / fail_json 替換成 raise exception，讓測試碼能用 pytest.raises 接住並讀結果。

03

tmp_path 給檔案模組真環境

不要 mock open()；用 pytest 內建 tmp_path fixture 給每個測試獨立目錄。讀真檔測真行為。

04

mock 外部依賴

run_command / requests / socket 等都 mock。用 mocker.patch（pytest-mock）或 mocker 裝飾器。

05

必測四件事

① required 參數缺失 → fail；② idempotency（值相同不變）；③ 真變更（changed=True）；④ check_mode（report 但不寫）。

06

parametrize 表格驅動

同一個邏輯多種輸入時用 @pytest.mark.parametrize。新加 case 只多一行 tuple，pytest 自動展開成獨立 test。

07

collection 結構鏡射

tests/unit/plugins/modules/test_X.py 對應 plugins/modules/X.py。conftest.py 放共用 fixtures。

08

CI matrix 跨 Python + ansible-core

GitHub Actions 矩陣測試 3 個 Python 版本 + stable/devel ansible-core。fail-fast: false。

練習題

  1. 開發者：把 17.4 節的 helper code 抄到自己的 conftest.py，跑 pytest --collect-only 確認 fixture 能載入。
  2. 開發者：對 Ch14 的 feature_flag 模組實作本章 17.5 全部 5 個 test。跑 pytest -v 確認 5 個全綠。
  3. 開發者：故意把 feature_flag.py 的 idempotency 邏輯改壞（例如永遠 changed=True），跑測試確認對應 test 立刻 fail。
  4. 開發者：用 17.7 節的 parametrize 寫一個 8 種組合的 idempotency 測試（含 flag 不存在 / 設定檔不存在等 edge case）。
  5. 開發者：寫一個會呼叫 module.run_command(['ping', '-c', '1', host]) 的 ping_check 模組，並寫測試 mock run_command 測「成功 ping」與「ping 失敗」兩個 case。
  6. DevOps / SRE：對 Ch14 練習題 7 寫的內部 ticketing 模組（ticket_create）寫完整測試。包含：成功建立、API 401（auth 失敗）、API timeout、duplicate ticket（API 回 409）四個 case。
  7. DevOps / SRE：寫 GitHub Actions workflow 跑你的 collection 測試。matrix 至少含 Python 3.10/3.11/3.12 + ansible-core stable-2.18 與 devel。
  8. DevOps / SRE：加上 coverage 報告。pytest-cov 跑 --cov=plugins --cov-report=xml，把報告 upload 到 codecov.io 或 GitHub Actions artifact。設目標 coverage > 80%。
  9. DevOps / SRE：研究你最近寫過的某個自定模組。問自己：① 沒測試的話下次重構你會怕嗎？② 列出該模組需要的最少 5 個 test case。③ 若實作這 5 個花多少時間？比較與「不寫測試但 production 出 bug」的 cost。

本章詞彙表

Unit test
對單一函式 / 單一模組的測試，外部依賴全 mock。快速、隔離、可重現。本章主題。
Integration test
對模組組合的測試，可能含真環境（DB、容器等）。比 unit test 真實但慢。Ch28 Molecule 章主題。
pytest
業界標準 Python 測試框架。Ansible 模組測試用它。提供 fixture、parametrize、強大的 assertion。
pytest-mock
pytest 的 mock 整合套件。提供 mocker fixture，比 unittest.mock 更易用。
set_module_args(args)
標準 helper function，把 task args 注入 basic._ANSIBLE_ARGS。所有 Ansible 模組測試的第一步。
basic._ANSIBLE_ARGS
AnsibleModule 內部模組變數。AnsibleModule 建構時優先讀此處而非 stdin。set_module_args 利用此機制注入。
AnsibleExitJson
自定 exception class，取代 module.exit_json 行為。讓測試碼能 catch 並讀結果。
AnsibleFailJson
自定 exception class，取代 module.fail_json 行為。
monkeypatch / mocker.patch
把 module function 暫時換掉的工具。最常用：把 exit_json/fail_json 換成 raise exception。
pytest.raises
Context manager，預期區塊內會 raise 指定 exception。with pytest.raises(AnsibleExitJson) as exc:。
tmp_path fixture
pytest 內建 fixture，提供每個測試獨立的臨時目錄。測完自動清理。
conftest.py
pytest 的「共用 fixture」檔案。放同目錄或父目錄會自動被所有 test_*.py 看到。
@pytest.fixture
裝飾器，把 function 標記為 fixture。可被多個 test 注入使用。
@pytest.mark.parametrize
裝飾器，給 test 不同輸入跑多次。表格驅動測試的核心工具。
module.run_command()
AnsibleModule 提供的 shell 執行 helper。回傳 (rc, stdout, stderr)。測試時必須 mock。
ansible-test units
Collection 測試的官方 runner。用法：ansible-test units --local --python 3.11。
pytest-ansible
讓 pytest 直接跑 collection 內單元測試的 plugin。簡化 import path 處理。
Moto
Python 庫，偽造 AWS API。@mock_ec2 裝飾器讓 boto3 的呼叫被攔截到假環境。
Localstack
Docker 內跑的 AWS 模擬環境。比 Moto 更完整，適合 integration test。
coverage / pytest-cov
測量 test 涵蓋多少 source code。CI 中常設目標如 > 80%。
