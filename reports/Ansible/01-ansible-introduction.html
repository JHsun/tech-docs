第 1 章 — Ansible 是什麼

在動手寫第一行 YAML 之前，先搞懂 Ansible 在 IT 自動化版圖上的位置、為什麼它在 2026 年仍是 greenfield 專案的首選 configuration management 工具，以及 ansible-core、ansible community package、Red Hat Ansible Automation Platform（AAP）三者的關係。這一章不寫 code，但決定你後續所有技術選型的底層認知。

1.1IT 自動化與 Configuration Management 的歷史脈絡

要理解 Ansible 為何長成今天這個樣子，必須先看它解決的是什麼問題。把時間軸往回拉二十年，你會看到 IT 自動化從手動 SSH 腳本一路演化到聲明式組態管理（declarative configuration management）的痕跡。

Figure 1.1 — Configuration Management 工具的演化里程碑

四個關鍵轉折值得記住：

  • 從 imperative 到 declarative：早期腳本講「怎麼做」（先 mkdir、再 chmod、再啟動服務），CM 工具講「應該是什麼樣子」（這個目錄該存在、權限是 0755、服務是 running）。差別在於失敗後可重跑、結果可預測。
  • 從 agent 到 agentless：Puppet 與 Chef 都需要在每台 managed node 安裝 agent，這在 2012 年是嚴重的 onboarding 摩擦。Ansible 用已經存在的 SSH當傳輸層，把「裝什麼都不用裝」變成它最強的 selling point。
  • 從 Ruby/DSL 到 YAML：Chef 要會 Ruby、Puppet 要學自家 DSL。Ansible 賭的是「讀 YAML 像讀英文」，把 CM 的學習曲線從「會寫程式的 SRE」拉低到「會寫設定檔的 sysadmin」。
  • 從 monorepo 到 Collections：2020 年 ansible-core 2.10 把所有模組從主 repo 拆出去，模組生態進入 Collections 時代，由 Galaxy 與 Automation Hub 分發。這個架構決定改變了你今天寫 Playbook 的所有 import 寫法。
📜 命名小史

「Ansible」這個字本身來自 Ursula K. Le Guin 1966 年的科幻小說《Rocannon's World》，指不受光速限制的瞬間通訊裝置。Michael DeHaan 在創立專案時刻意用這個典故，呼應「無遠弗屆地控制遠端系統」的設計意圖。

1.2.1什麼時候 不 該用 Ansible

Ansible 雖然是首選，但下列情境另選工具會更合適：

  • 10 K+ 節點且需要即時事件響應：Salt 的 ZeroMQ + Reactor 架構在這個規模仍領先。Ansible 需要靠 Event-Driven Ansible（EDA）+ Automation Controller 才能補上，但複雜度顯著提高。
  • 強合規需求（HIPAA、PCI-DSS、SOC 2 連續稽核）：Chef InSpec 在連續合規（continuous compliance）這塊仍有結構性優勢。Ansible 可整合 OpenSCAP，但屬於「組合拳」而非開箱即用。
  • 純基礎設施 provisioning（建 VM、VPC、Load Balancer）：Terraform / OpenTofu 的 state 管理與 plan/apply 工作流更適合。Ansible 雖然也有雲端模組，但建立資源不是它的強項，設定資源才是。
✓ 黃金組合

2026 年最常見的生產組合是 Terraform / OpenTofu 負責 provisioning + Ansible 負責 configuration + GitOps（Argo CD / Flux）負責 K8s workload。這三層各司其職，比硬要用一套工具吃下全部更穩。

1.3Ansible 的設計哲學

Ansible 的所有設計決策都可以追溯到四個核心原則。理解這四個原則，等於拿到一把通用鑰匙——後面遇到任何「為什麼 Ansible 要這樣設計」的疑問，幾乎都能用它們解釋。

⊘

Agentless

Managed node 不需要安裝任何 Ansible 專屬 agent。Control node 透過已經存在的 SSH（Linux/Unix）或 WinRM（Windows）連線，把 Python 腳本臨時推送過去執行。零安裝、零維護。

↻

Idempotent

同一個 Playbook 跑一次與跑一百次，最終狀態必須相同。模組內部會先檢查當前狀態，只在需要時才執行變更。這是「desired state」模型的具體實作。

≡

Declarative

你描述「要變成什麼樣子」，不描述「怎麼做」。模組內部處理 OS 差異——同一個 package 任務在 Ubuntu 用 apt、在 RHEL 用 dnf、在 Alpine 用 apk，使用者不必管。

▤

Human-readable

YAML 設計成「即使不會 Ansible 的人也能讀懂九成意圖」。這讓 Playbook 同時是執行腳本和系統文件——code that reads like documentation 是 Ansible 官方的口號，不是行銷話術。

1.3.1Idempotent 的實際樣貌

Idempotency 是 Ansible 的核心承諾，但很多人對它有誤解。它不是「Ansible 自動幫你做 idempotent」，而是「每個正規模組都必須自己實作 idempotency」。下面這個對比讓你看清楚差別。

YAML · 反例（非冪等） 
# ✗ 反例：用 shell 跑命令，沒有檢查狀態，每次執行都會重複動作
- name: 確保 nginx 安裝
  shell: apt-get install -y nginx

- name: 確保有寫入 hosts
  shell: echo "10.0.0.1 db" >> /etc/hosts
  # 跑兩次會出現兩行重複
YAML · 正例（冪等） 
# ✓ 正例：用正規模組，內部會檢查狀態，重跑不會產生副作用
- name: 確保 nginx 安裝
  ansible.builtin.package:
    name: nginx
    state: present

- name: 確保有寫入 hosts
  ansible.builtin.lineinfile:
    path: /etc/hosts
    line: "10.0.0.1 db"
    state: present
    # lineinfile 內部會檢查該行是否已存在
⚠ 開發者陷阱

當你用 command 或 shell 模組時，Ansible 沒辦法保證 idempotency——這是兩個模組的本質限制。如果非用不可，請搭配 creates:、removes: 參數讓 Ansible 知道何時該跳過，或用 changed_when: 自行定義變更條件。第 5 章會詳細展開。

1.4ansible-core 與 Ansible Community Package

從 2.10 版開始，Ansible 的官方發行品其實有兩個獨立的軟體包，搞清楚差別才能在安裝、CI/CD、版本鎖定上少踩坑。

Figure 1.2 — ansible-core 與 community package 的組成關係

1.4.1該裝哪一個？

套件 包含內容 適合對象 典型使用情境
ansible-core 引擎 + 約 100 個 ansible.builtin.* 模組 需要精準控制版本的開發者、CI/CD、Execution Environment 容器化執行、自選 Collections、企業 lockfile 嚴格
ansible
（community package）		 ansible-core + 85+ 個常用 Collections 一次到位 初學者、單機操作、快速 onboarding pip install ansible 後立即可用，不必煩惱 Collections

1.4.22026 年版本現況

截至本書撰寫時（2026 年 5 月）：

  • ansible-core 最新穩定版：2.20.4（2026/3/23 發布），需 Python ≥ 3.12。下一個主版本 2.21 正在 RC 階段。
  • ansible community package 最新版：2026/4 發布的版本（隨 ansible-core 主版本約二週內跟進）。
  • ansible-core 維護政策：同時維護當前版本與前 兩個 主版本，每四週釋出一個小版本（patch release）。
  • community package 維護政策：只維護當前主版本，新主版本一發布、舊版本立刻 EOL。這是與 ansible-core 最大的差別，企業在版本選擇上要特別注意。
ⓘ 版本確認指令

裝完之後用以下指令確認你裝的是哪個版本：

bash · 版本檢查 
$ ansible --version
# 看 "ansible [core 2.20.4]" 那行 → 這是 ansible-core 版本

$ ansible-community --version
# 看 "Ansible community version 12.x.x" → 這是 community package 版本
# 若只裝 ansible-core，這個指令會找不到

$ ansible-galaxy collection list
# 列出當前環境裝了哪些 Collections

1.5與 Red Hat Ansible Automation Platform 的關係

當你的組織從「個人 / 小團隊 用 Ansible」進化到「全公司在用 Ansible」，就會撞上以下問題：誰能跑哪些 Playbook？跑完的結果存在哪？大型 Inventory 怎麼集中管理？怎麼排程？怎麼讓非工程人員也能觸發自動化？這正是 Red Hat Ansible Automation Platform（AAP）要解決的層次。

Figure 1.3 — Ansible 開源層、工具層、AAP 三者的關係

1.5.1三個層次的取捨

  • 純開源（ansible-core + AWX）：免費、彈性、自己維運。適合技術自主的小團隊、學習階段、與不想付訂閱費的組織。代價是你要自己處理升級、HA、備份、權限模型。
  • AAP 訂閱：付費、開箱即用、Red Hat 提供 SLA 等級的支援。適合需要稽核 / 合規 / 跨團隊協作的中大型企業。AAP 文件已經移到 docs.redhat.com，與社群 docs 分流。
  • AAP 預設搭配的 ansible-core 版本：AAP 2.5 與 2.6 預設使用 ansible-core 2.16 / 2.18，比 PyPI 上的最新版保守。這是企業環境刻意求穩的取捨——你的本地開發環境可能跑 2.20，但 production AAP 跑的是 2.16/2.18，第 24 章談 Execution Environment 時會深入這個落差。
ⓘ AWX vs Automation Controller

AWX 是 Tower（後改名 Automation Controller）的上游開源版，類似 Fedora 之於 RHEL 的關係。AWX 沒有官方 SLA、沒有 Red Hat 技術支援，但功能與 Controller 幾乎同步。本書第 33 章會分別介紹兩者。

1.6本章重點回顧

01

Ansible 是 declarative agentless CM 工具

用 SSH/WinRM 連線、用 YAML 寫劇本、靠模組保證 idempotency。讀起來像文件、跑起來能重現。

02

2026 年仍是 greenfield 首選

學習曲線最低、生態最完整、網路自動化最強。對手 Puppet 開源版已 deprecated、Salt 在 Broadcom 後不確定性增加。

03

三個層次要分清

ansible-core（引擎）、ansible（community package）、AAP（企業訂閱）。新專案多半用 community package 起步、CI/CD 用 ansible-core、企業規模再上 AAP。

04

它不是萬靈丹

10 K+ 節點即時響應找 Salt、強合規找 Chef InSpec、純 provisioning 找 Terraform。Ansible 在configuration 與orchestration 才是最強。

練習題

  1. 初學者：到 docs.ansible.com 主頁，找出 Ansible「Users / Developers / Maintainers」三條閱讀路徑各對應哪些章節，記下來作為你後續查文件的索引。
  2. 初學者：用一段 200 字內的話，向一位沒寫過程式的同事解釋什麼是 idempotency，並給一個非 IT 領域的類比（例如：自動門開關按鈕、電梯按樓層按鈕）。
  3. 開發者：列出三個你公司目前用 shell script 做的維運任務，思考改用 Ansible 模組重寫後，哪些任務會自動獲得 idempotency、哪些仍需要手動加 creates: / changed_when:。
  4. 開發者：到 PyPI 查 ansible-core 的 release history，比較 2.16 / 2.18 / 2.20 三個版本對 Python 最低版本的要求差異，思考你公司目前的 Python 版本能用到哪一版。
  5. DevOps / SRE：盤點你目前管理的節點規模（小於 100、100–1000、1000+），參考 1.2.1 節的決策原則，判斷單純 Ansible 是否夠用，或需要搭配 Terraform、AAP、EDA。
  6. DevOps / SRE：找出你公司 CI/CD pipeline 中最頻繁失敗的維運步驟，評估用 Ansible Playbook 改寫的 ROI（時間節省、錯誤降低、可重現性）。

本章詞彙表

Idempotent / Idempotency
冪等性。同一操作重複執行 N 次，結果與執行 1 次相同。Ansible 模組的核心承諾。
Declarative
聲明式。描述「應該變成什麼狀態」，不描述「怎麼做」。對立面是 imperative（命令式）。
Agentless
無代理人架構。Managed node 上不安裝 Ansible 專屬常駐程式，靠 SSH/WinRM 即時連線執行。
Control node
控制節點。執行 ansible / ansible-playbook 命令的機器。需要 Python 3.12+。
Managed node
受管節點。被 Ansible 操作的目標機器。Linux/Unix 需要 SSH + Python（部分模組可 raw 執行），Windows 需要 WinRM 或 SSH。
Playbook
劇本。用 YAML 撰寫的自動化任務描述檔，包含一或多個 Plays。
Collection
集合。從 ansible-core 2.10 起的模組分發單位，命名格式為 namespace.collection（例如 amazon.aws）。
FQCN
Fully Qualified Collection Name。模組的完整命名，例如 ansible.builtin.package。2026 年的最佳實踐是永遠 寫 FQCN，避免命名衝突。
ansible-core
Ansible 的引擎部分。只含核心執行邏輯與 ansible.builtin.* 模組，不含外部 Collections。
Ansible Community Package（package ansible）
= ansible-core + 約 85 個常用 Collections 的整合包。pip install ansible 安裝的就是這個。
AAP — Red Hat Ansible Automation Platform
Red Hat 的企業級 Ansible 訂閱產品。包含 Automation Controller、Automation Hub、EDA、Mesh、Analytics 等元件。
AWX
Automation Controller（前 Ansible Tower）的開源上游專案。功能對等但無商業支援。
Execution Environment（EE）
容器化的 Ansible 執行環境。封裝 ansible-core 版本、Python 相依套件、Collections，讓 Playbook 在所有地方跑出一致行為。
