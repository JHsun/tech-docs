第四篇 — 模組／Plugins 生態

第 14 章 — Modules 概論

前 13 章用了上百次 ansible.builtin.copy、community.general.timezone 等模組——但模組到底是什麼？它怎麼跑？參數怎麼傳？我能寫一個自己的嗎？本章從模組是 Ansible 的「動作單位」講起，揭開模組執行的真實流程（control node 把 Python 檔送到 managed node 執行）、AnsibleModule 框架（5 行 boilerplate 換來完整的 argument 驗證 / check_mode / 錯誤處理）、寫一個生產級自定模組的最小範例（feature flag 管理）、放哪裡（library/）、用 ad-hoc 與 playbook 測試的方式。讀完這章你會知道 Ansible 並不神祕——它就是一個在遠端執行 Python 的 RPC 框架，而你完全有能力擴展它。

本章覆蓋官方文件對應：Module Architecture · Developing Modules
初學者選讀（14.1–14.2 概念） 開發者必讀（全章） DevOps / SRE 必讀（全章特別 14.7 idempotency 與 14.8 check_mode）

14.1什麼是模組？

Ansible 的核心是一個 RPC 框架——control node 把「動作」打包成一個檔案，丟到 managed node 上執行，再把結果用 JSON 收回來。這個被執行的檔案就是模組。

14.1.2JSON 介面

模組的 contract 簡單又嚴格：從 stdin / argfile 讀 JSON 參數，把 JSON 結果印到 stdout。所有模組都遵守這個介面。

text · 模組的輸入輸出範例 
# Ansible 提供的 JSON 輸入
{
  "path": "/etc/myapp/config.json",
  "key": "dark_mode",
  "value": "true",
  "state": "present",
  "_ansible_check_mode": false,
  "_ansible_no_log": false
}

# 模組必須印出的 JSON 結果
{
  "changed": true,
  "msg": "Set dark_mode=true",
  "previous_value": "false",
  "current_value": "true"
}
ⓘ 模組原則上可用任何語言

模組契約只是「讀 JSON 印 JSON」，理論上 bash / Ruby / Go / Rust 都能寫模組。但 Python 是唯一一等公民——AnsibleModule helper、module_utils 共用程式、官方文件、IDE 支援、CI 測試框架全部圍繞 Python。沒有特殊理由就用 Python。

Ansible 提供的 800+ 模組大致分以下幾類：

類別用途典型模組

14.2.1什麼時候該寫自定模組？

▶

內部 API 操作

公司內部的 ticketing / inventory / billing API。沒人會寫公開模組。包成 company.create_ticket 比每次寫 uri 模組好多了。

▶

複雜的 idempotent 邏輯

「如果 X 不存在就建立、若版本舊就升級、否則跳過」這類邏輯用 shell + when 寫起來脆弱。寫成模組封裝邏輯。

▶

跨多個 task 的整合操作

「呼叫 LB 拔掉、部署、健康檢查、加回 LB」這種 atomic 操作寫成單一模組更可靠。

▶

商業設備 / 軟體控制

商業 firewall / load balancer / 認證系統等沒有官方 collection 時，自己寫對應模組。

⚠ 寫自定模組前的檢查點

① 是否已有 collection 模組可用？先逛 galaxy.ansible.com。② 用 command + changed_when 能否搞定？簡單情境不必動到 Python。③ 寫成 role 而非模組是否更合適？只是組合既有模組則 role 較佳。真正需要新增「動作」才寫模組。

14.3第一個模組：Hello World

看一個最小可運作的自定模組。建立檔案 library/hello.py：

python · library/hello.py — 最小範例 
#!/usr/bin/python
# -*- coding: utf-8 -*-

from ansible.module_utils.basic import AnsibleModule


def main():
    # 1) 定義模組接受的參數
    module = AnsibleModule(
        argument_spec=dict(
            name=dict(type='str', required=True),
            greeting=dict(type='str', default='Hello'),
        ),
        supports_check_mode=True,
    )

    # 2) 取出參數值
    name = module.params['name']
    greeting = module.params['greeting']

    # 3) 做該做的事（這個範例不改變任何狀態）
    result = {
        'changed': False,
        'message': f'{greeting}, {name}!',
    }

    # 4) 回傳結果
    module.exit_json(**result)


if __name__ == '__main__':
    main()

14.4AnsibleModule 框架核心

剛剛的範例用了 AnsibleModule——一個 100 行內就有完整 argument 驗證、check_mode、錯誤處理、JSON 輸出的框架。深入了解它的核心方法：

14.4.1argument_spec — 參數定義

python · 完整參數規範 
module_args = dict(
    # 基本：型別 + required
    name=dict(type='str', required=True),

    # 含預設值
    state=dict(type='str', default='present', choices=['present', 'absent']),

    # 數字
    timeout=dict(type='int', default=30),
    cpu_ratio=dict(type='float', default=0.75),

    # Boolean
    enabled=dict(type='bool', default=True),

    # List / Dict
    tags=dict(type='list', elements='str', default=[]),
    config=dict(type='dict', default={}),

    # Path 自動處理 ~/ 展開
    path=dict(type='path', required=True),

    # 敏感資訊 — log 中遮罩
    password=dict(type='str', no_log=True),
)

14.4.2參數型別速查

type=說明
str字串（最常用）
int整數
float浮點數
bool布林（接受 yes/no/true/false/1/0）
listlist；用 elements= 指定子型別
dictdict
path路徑；自動 expanduser / abspath
raw不驗證型別
jsonJSON 字串會自動 parse
jsonarg序列化成 JSON 字串
bytes / bits含單位的數量（如 1G、512Mb）

14.4.3進階驗證選項

python · 進階驗證選項 
module = AnsibleModule(
    argument_spec=module_args,
    supports_check_mode=True,

    # 互斥 — 不能同時提供
    mutually_exclusive=[
        ['password', 'ssh_key'],
        ['state_present', 'state_absent'],
    ],

    # 必須一起 — 提供 A 就必須提供 B
    required_together=[
        ['username', 'password'],
    ],

    # 至少要一個
    required_one_of=[
        ['name', 'id'],
    ],

    # 條件性 required — state=present 時 name 必填
    required_if=[
        ['state', 'present', ['name']],
        ['auth_type', 'password', ['password']],
    ],
)

14.4.4退出方法：exit_json / fail_json

python · exit / fail 兩種退出 
# 成功 — 包含結果回傳給 Ansible
module.exit_json(
    changed=True,
    msg='Configuration updated',
    previous_value='false',
    current_value='true',
    # 任何 key 都會送回 playbook（被 register 的變數可以訪問）
)

# 失敗 — Ansible 會把 task 標為 failed
module.fail_json(
    msg='Connection timeout',
    error_code=504,
    target_host='api.example.com',
)
# 注意 fail_json 會立刻 exit，後面 code 不會跑到

14.5實戰：Feature Flag 模組

看一個更接近生產的範例——管理 JSON 設定檔內的 feature flag。

python · library/feature_flag.py 
#!/usr/bin/python
# -*- coding: utf-8 -*-

DOCUMENTATION = r'''
---
module: feature_flag
short_description: 管理應用 feature flag
description:
    - 讀寫 JSON 設定檔內的 feature flag
    - 全程 idempotent，狀態相同不變更
version_added: "1.0.0"
options:
    config_path:
        description: JSON 設定檔路徑
        required: true
        type: path
    flag_name:
        description: feature flag 名稱
        required: true
        type: str
    enabled:
        description: 是否啟用
        required: true
        type: bool
'''

EXAMPLES = r'''
- name: 啟用 dark mode
  feature_flag:
    config_path: /etc/myapp/config.json
    flag_name: dark_mode
    enabled: true
'''

RETURN = r'''
previous_value:
    description: 變更前的值
    type: bool
    returned: when changed
current_value:
    description: 變更後的值
    type: bool
    returned: always
'''

from ansible.module_utils.basic import AnsibleModule
import json
import os


def main():
    module = AnsibleModule(
        argument_spec=dict(
            config_path=dict(type='path', required=True),
            flag_name=dict(type='str', required=True),
            enabled=dict(type='bool', required=True),
        ),
        supports_check_mode=True,
    )

    path = module.params['config_path']
    name = module.params['flag_name']
    desired = module.params['enabled']

    # 1) 讀現況
    if os.path.exists(path):
        try:
            with open(path) as f:
                config = json.load(f)
        except json.JSONDecodeError as e:
            module.fail_json(msg=f'設定檔 JSON 格式錯誤: {e}')
    else:
        config = {}

    previous = config.get(name)

    # 2) 比對 — 相同則不動作（idempotency）
    if previous == desired:
        module.exit_json(
            changed=False,
            current_value=desired,
            msg=f'{name} 已是 {desired}',
        )

    # 3) Check mode — 只報告會發生的變更，不實際寫
    if module.check_mode:
        module.exit_json(
            changed=True,
            previous_value=previous,
            current_value=desired,
            msg=f'(check mode) 會把 {name} 從 {previous} 改為 {desired}',
        )

    # 4) 實際寫入
    config[name] = desired
    try:
        os.makedirs(os.path.dirname(path), exist_ok=True)
        with open(path, 'w') as f:
            json.dump(config, f, indent=2)
    except OSError as e:
        module.fail_json(msg=f'寫入失敗: {e}')

    # 5) 回傳結果
    module.exit_json(
        changed=True,
        previous_value=previous,
        current_value=desired,
        msg=f'{name} 已更新為 {desired}',
    )


if __name__ == '__main__':
    main()

yaml · 在 playbook 中用

14.7Idempotency — 模組設計的最高準則

第 6 章已多次強調 idempotent 是 Ansible 哲學。寫模組時這個準則更重要——沒有 idempotency 的模組就不是 Ansible 模組，只是 shell 腳本。

14.7.1三步驟法則

Figure 14.2 — Idempotent 模組三步驟：讀 → 比對 → 動作
⚠ 反面教材：不是 idempotent 的模組

「跑兩次造成不同結果」就是非 idempotent。例如：每次跑都 append 一行到檔案、每次跑都 increment 計數、每次跑都建立新記錄（不檢查是否已存在）。這種模組會在第二次執行時 PLAY RECAP 錯誤地報 changed=true 或副作用累積。

14.7.2idempotency 自我測試

bash · 連跑兩次驗證 idempotency 
# 第一次（應該 changed=true）
$ ansible-playbook test.yml
# PLAY RECAP : ok=2 changed=1 ...

# 第二次（必須 changed=0！）
$ ansible-playbook test.yml
# PLAY RECAP : ok=2 changed=0 ...

# 如果第二次仍是 changed=1，模組就不 idempotent — bug！

14.8Check Mode — Dry Run 支援

使用者用 --check 跑 playbook 時要看到「會發生什麼變化」但不真正改動。模組必須主動支援這個。

14.8.1啟用 check_mode 支援

python · 三步驟支援 check_mode 
# 1) AnsibleModule 建構時宣告
module = AnsibleModule(
    argument_spec=module_args,
    supports_check_mode=True,        # ← 必設
)

# 2) 在實際變更前檢查並提早回傳
if module.check_mode:
    module.exit_json(
        changed=True,                # 報告會 changed
        msg='(check mode) 會修改 X 從 A 到 B',
    )

# 3) 後面才是真正的變更操作
do_actual_change()
module.exit_json(changed=True, ...)

14.8.2業界規則：check_mode 必須支援

✓ check_mode 是模組的基本要求

沒支援 check_mode 的模組在 --check run 時會被自動 skip——使用者完全看不到 dry run 結果，產生「不知道會發生什麼」的恐懼。發布到 Galaxy 的模組必支援 check_mode。內部用的也建議支援，cost 很低（多寫 5-10 行）但 value 很高。

14.9module_utils — 共用程式

多個模組常有共用邏輯——連同一個 API、共用的 helper function、共用的 exception 處理。這些放module_utils。

14.9.1結構

text · 含 module_utils 的 collection 結構 
collections/ansible_collections/myorg/internal/
├── plugins/
│   ├── modules/
│   │   ├── ticket_create.py     # import myorg.internal.api
│   │   └── ticket_update.py     # import myorg.internal.api
│   └── module_utils/
│       └── api.py               # 共用的 API client

python · plugins/module_utils/api.py 
# 共用的 API client
import requests


class TicketAPI:
    def __init__(self, base_url, token):
        self.base_url = base_url
        self.session = requests.Session()
        self.session.headers['Authorization'] = f'Bearer {token}'

    def create_ticket(self, title, body):
        return self.session.post(
            f'{self.base_url}/tickets',
            json={'title': title, 'body': body},
        ).json()

    def update_ticket(self, ticket_id, **kwargs):
        return self.session.patch(
            f'{self.base_url}/tickets/{ticket_id}',
            json=kwargs,
        ).json()
python · plugins/modules/ticket_create.py 
from ansible.module_utils.basic import AnsibleModule
from ansible_collections.myorg.internal.plugins.module_utils.api import TicketAPI


def main():
    module = AnsibleModule(
        argument_spec=dict(
            base_url=dict(type='str', required=True),
            token=dict(type='str', required=True, no_log=True),
            title=dict(type='str', required=True),
            body=dict(type='str', required=True),
        ),
        supports_check_mode=True,
    )

    api = TicketAPI(module.params['base_url'], module.params['token'])

    if module.check_mode:
        module.exit_json(changed=True, msg='(check) would create ticket')

    result = api.create_ticket(module.params['title'], module.params['body'])
    module.exit_json(changed=True, ticket_id=result['id'])


if __name__ == '__main__':
    main()

14.10本章重點回顧

01

模組是 Ansible 的「動作單位」

Ansible 把模組打包送到遠端執行，透過 stdin / stdout 用 JSON 通訊。原則上任何語言可寫，實務上 Python。

02

放 library/ 即生效

專案根目錄 / role 內的 library/ 自動被掃描。不需註冊，不需安裝，丟 .py 進去就能用。

03

AnsibleModule 是核心框架

提供 argument_spec 驗證、check_mode 支援、退出方法、log 處理。from ansible.module_utils.basic import AnsibleModule 開始所有模組。

04

argument_spec 是模組 API

定義所有可接受參數。型別自動驗證、required 自動檢查、互斥組合自動處理。寫得好的 spec 等於完整 API 文件。

05

idempotency 是必須

讀現況 → 比對期望 → 相同則 changed=False 不動作 → 不同才執行變更。連跑兩次第二次必須 changed=0。

06

check_mode 必須支援

supports_check_mode=True + 在實際變更前檢查 module.check_mode 並提早 exit_json 報告會發生的變化。

07

三大文件區塊

DOCUMENTATION / EXAMPLES / RETURN。配 ansible-doc 查詢。寫到 collection / Galaxy 必須有。

08

module_utils 共用程式

多個模組共用的 API client / helper 放 plugins/module_utils/。避免重複、易維護。

練習題

  1. 初學者：建立 library/hello.py（複製本章 14.3 範例），用 ansible localhost -m hello -a "name=World" 執行確認輸出。
  2. 初學者：閱讀任一個 ansible.builtin 模組原始碼（例如 GitHub 上的 file.py），找出 argument_spec 與 main() 函式。
  3. 初學者：用 ansible-doc copy / ansible-doc community.general.timezone 看官方模組文件，理解 DOCUMENTATION / EXAMPLES / RETURN 結構。
  4. 開發者：實作本章 14.5 的 feature_flag 模組。寫一個 playbook 測試：第一次跑、第二次跑、用 --check 跑、改設定再跑，觀察四種情況的 changed 狀態。
  5. 開發者：擴展 feature_flag 模組支援 state: absent（移除 flag）。考量 idempotency：flag 不存在時 absent 該 changed=False。
  6. 開發者：寫一個 etc_hosts_entry 模組，管理 /etc/hosts 檔內單一 entry（IP + hostname）。支援 state present/absent + check_mode + idempotency。
  7. DevOps / SRE：寫一個內部 API 模組（如 ticket_create），呼叫公司內部 ticketing 系統 API。包含 retry 邏輯、適當的錯誤訊息、敏感參數加 no_log=True。
  8. DevOps / SRE：把上題的 ticketing 模組重構，把 API client 抽到 module_utils/ticket_api.py，主模組瘦身。實作另一個 ticket_update 模組共用同一個 API client。
  9. DevOps / SRE：給你的自定模組寫完整的 DOCUMENTATION / EXAMPLES / RETURN 三大區塊，跑 ansible-doc -M ./library <module_name> 確認文件正確顯示。

AnsibleModule
Ansible 提供的模組開發框架類別。處理 argument 解析、check_mode、退出、log 等通用邏輯。
argument_spec
傳給 AnsibleModule 的 dict，定義模組接受哪些參數。Ansible 自動依此做型別驗證、required 檢查、互斥處理。
library/ 目錄
Ansible 自動掃描的自定模組路徑。專案根目錄、role 內、ansible.cfg 設定皆可。放 .py 即生效，無需註冊。
module_utils
多個模組共用的 Python 程式碼。Collection 結構下放 plugins/module_utils/。
exit_json()
模組成功時的退出方法，傳入結果（含 changed、msg 與其他自訂 key）。Ansible 會把所有 key 回傳給 playbook。
fail_json()
模組失敗時的退出方法，傳入錯誤訊息。Task 會被標為 failed。
changed
所有模組必須回傳的 key。True = 改變了狀態、False = 沒變。是 idempotency 的具體表現。
check_mode
Ansible 的 dry-run 模式。--check 啟用。模組需 supports_check_mode=True 並在實際變更前判斷 module.check_mode。
idempotency / 冪等性
相同輸入跑多次結果相同。Ansible 模組的最高設計準則。模組要做到：第一次跑 changed=true、第二次跑 changed=false。
no_log
argument_spec 內的選項。no_log=True 讓該參數的值在 log 中遮罩，避免密碼洩漏到輸出。
DOCUMENTATION block
模組頂部的 YAML 字串，定義模組描述、所有參數的詳細說明。被 ansible-doc 解析顯示。
EXAMPLES block
模組頂部的 YAML 字串，提供使用範例。直接 copy 即可用。
RETURN block
模組頂部的 YAML 字串，定義模組可能回傳的所有 key 與其結構。
mutually_exclusive / required_together / required_one_of / required_if
AnsibleModule 的進階驗證選項，宣告參數間的相依關係。Ansible 自動驗證，違反時自動 fail。
