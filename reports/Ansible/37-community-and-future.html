37.1Ansible 社群核心價值

每個開源專案都有「氣質」。Ansible 社群的氣質可用三個字總結：radically simple、radically open、radically respectful。

37.1.1三個社群價值

🎯

Radically simple

「最簡單的 IT automation」是專案 tagline。每個提案問：能更簡單嗎？YAML 而非 DSL、SSH 而非 agent、declarative 而非 imperative — 都是這個價值的具現。

🌐

Radically open

所有決策落 GitHub / Forum、所有會議公開（Matrix + 定期 video）、所有 roadmap 公佈。沒有「Red Hat 內部會議神秘決定方向」這回事。

🤝

Radically respectful

有完整 Code of Conduct（CoC）並嚴格執行。codeofconduct@ansible.com 受理檢舉。對新人友善是文化、不是口號。

37.1.2Code of Conduct 五大要點

ⓘ 你必讀的 5 條 CoC 精神

① 包容：不分性別 / 種族 / 宗教 / 經驗水平歡迎參與；② 專業：對事不對人、批評代碼不批評人；③ 耐心：async 通訊不是即時客服、給人 24-72 小時回覆時間；④ 歸因：別人作品被你修了、保留作者署名；⑤ 檢舉機制：遇到不當行為直接寄 codeofconduct@ansible.com 或聯絡 Matrix mod。

37.2兩條 release stream

新人最困惑：ansible 跟 ansible-core 是不同東西、版本號也不同。

37.2.1兩個 package 的關係

Figure 37.1 — ansible-core 是引擎、ansible package 是 batteries-included 包

37.2.2release 節奏對照

項目ansible-coreansible package
內容引擎 + builtin module（apt / copy / template / file 等）core + 100+ curated collection
2026 主流版本2.18 / 2.2011.x（內含 core 2.18）
major release 節奏每年一次（2.x → 2.x+2）每年兩次
minor / patch 節奏4 週 patch（2.18.0 → 2.18.1）4 週 minor（11.0 → 11.1）
SemVer嚴格嚴格
Deprecation 週期4 個 feature release跟 collection 各自 deprecation
Release candidatemajor release 前至少一個 RC（5 工作日）同上
EOL 政策當下 + 前一個 minor 才支援只支援最新 major
⚠ 你的環境用哪個？

① 個人 / 小團隊 → 裝 ansible（package、內含一切常用 collection）；② EE / CI / 嚴控環境 → 裝 ansible-core 然後在 EE 內精準指定 collection 版本（control 強）；③ AAP 客戶 → 用 Red Hat 認證版本，跟 AAP 的 EE 一致。

37.3Working Group + Forum + Matrix

37.3.1三個主要溝通通路

💬

Forum (forum.ansible.com)

預設起點。Discourse 平台。Q&A / 提案 / 公告 / events。比 mailing list 友善、比 Matrix 適合長文。新手第一個帳號該開這。

⚡

Matrix (chat.ansible.im)

即時通訊。general support / dev / community / 各 working group 各有 channel。但決策仍要落 GitHub / Forum——Matrix 是聊天、不是紀錄。

🐙

GitHub

所有 code / issue / PR / 大多數正式 proposal。決策最終的「真相」（source of truth）。

ⓘ IRC 不再是官方通路

歷史上 Ansible 用 IRC（Libera.chat）。現在已停用為官方通路。新人請去 Forum 與 Matrix。網上看到的 IRC channel 教學多半是舊資料。

37.3.2主要 Matrix channel

Matrix channel用途
#users:ansible.com一般使用問題（最熱鬧）
#devel:ansible.com開發 / code 討論
#community:ansible.com社群事務、collection 相關
#meeting:ansible.im定期社群會議
#docs:ansible.com文件貢獻
#social:ansible.com閒聊、Bullhorn newsletter 投稿

37.3.3Working Group — 找你的部落

Working Group（WG）是社群成員圍繞特定主題自組的小組。多數圍繞某個 collection 或主題。

✓ 找你的 WG 三步驟

① 看 Forum「Groups」頁面 — 列出所有 WG（Network / Containers / Cloud / Security / Docs / 等）；② 加入你日常用的 collection 對應 WG；③ 看會議行事曆（多數每 2 週一次 Matrix video）— 旁聽就好、不必發言。一個月後你會自然理解該領域怎麼運作、哪些人是 maintainer。

37.4Roadmap — 提早看路線

不要等 release note 才知道「哦、這版改了 X」。看 roadmap 提早 6-12 月了解走向。

37.4.1三個 roadmap 來源

Roadmap內容頻率
Community Roadmap 整體社群方向（治理 / 工具鏈 / 新計畫） 每年一次（年初 CfgMgmtCamp 後發）
ansible-core roadmap 引擎本身計畫（每個 2.x.0 release） 每個 major 前 2-3 月
Collection 個別 roadmap 各 collection 自有計畫（不一定都有） 變化大 — 看各 repo

37.4.2跟讀 roadmap 的方法

📌

Pin Forum 「Project Discussions」

roadmap 公告都貼這裡。bell 訂閱 → 新貼自動通知。

📅

關注 CfgMgmtCamp（每年 2 月，Ghent）

歐洲最大 Ansible 年度活動。Contributor Summit 在這辦、roadmap 通常這時公佈。線上轉播多有錄影。

📰

訂 Bullhorn newsletter

社群週訊。摘要重要 PR / WG 動向 / 即將 release。Forum 自動發。

🔭

Watch 你關心的 repo

GitHub 「Watch → Releases only」設定。重大 release 自動 email 通知。

37.7Ansible 職涯路徑

37.7.1三個常見職涯軌跡

Figure 37.2 — 三條典型職涯軌跡都會匯到 platform engineer

37.7.2四個技能差異點

🪜

L1 sysadmin → L2 automation eng

關鍵：從「對 1 台」到「對 N 台一致」。掌握 inventory、role、CI 整合。本書 Ch1-Ch22 涵蓋。

🏗

L2 → L3 platform eng

關鍵：從「自己用」到「給整公司用」。掌握 AAP / RBAC / EE pipeline / mesh。本書 Ch23-Ch34。

🌐

L3 → L4 staff / principal

關鍵：從「給公司用」到「影響業界 / 社群」。常見：對 community collection 持續貢獻、寫獨立 collection、給 conference talk、mentor。本書 Ch35-Ch37。

📈

薪資

每個 level 跳通常 +25% to +50%。「Ansible 專家」標籤本身在 2026 美國中位市場約 $130-180k base、亞洲視市場差異大。看你提供的 leverage。

37.8EX374 / RHCE 認證

不是必要、但對某些公司 / 客戶 / 求職場景有顯著幫助。

37.8.1主要認證對照

認證內容適合
RHCE（EX294） Red Hat Certified Engineer — Ansible automation 為核心。RHEL 環境 RHEL sysadmin、IT generalist
EX374 Red Hat Certified Specialist in Developing Automation with Ansible Automation Platform — AAP 進階 AAP 實際運維者、想專業認證
EX447（已被 EX374 替代） 舊版 AAP 認證 歷史版本、已 EOL

37.8.2準備建議

✓ EX374 準備 4 步驟

① 讀官方 exam objectives（Red Hat training site 公開）；② 有 AAP / AWX 實機練 2-3 個月（自架 AWX 也算）；③ 跑官方 RH295 / RH374 課程（or 等價自學）；④ 做 mock exam。重點不是死背 module 名 — 是真的能在限時內產出 working playbook。本書 Ch10-32 已涵蓋大部分 objective。

37.9給未來貢獻者的話

①

從你用的開始

對 amazon.aws 抱怨某 bug → 去修它。對使用過的 collection 貢獻最自然 — 你已經是 user，知道 pain point 在哪。

②

第一個 PR 不必完美

會被 review 改 2-3 輪是正常。每個 maintainer 第一個 PR 都被 review 過。不要因為怕被批評就不做。

③

Reviewer 比 author 缺

不會 Python 也能 review。從 user 角度看「文件清楚嗎、example 能跑嗎」就有價值。Maintainer 多半從 reviewer 起家。

④

耐心與 async 並存

maintainer 多是志工。一週沒回是常態、不是冷處理。給時間、別 ping 太勤。

⑤

分享你學到的

寫 blog / 給內部 talk / 教 onboarding 同事。 「教會別人」是你掌握知識最強驗證、也讓社群知識複利成長。

37.10.3結語

📖 結語：致讀者

本書 37 章 + 6 附錄、約 35 萬字、~150 個 mermaid 圖、超過 600 個程式碼範例。從 2026 年初動筆到現在，每一章都對照那個時點官方文件最新狀態查證撰寫——但 Ansible 演進不會停。讀完這本書你會發現：基礎概念百分之九十不會變（inventory / playbook / role / module），但工具鏈會持續更新（EE / Navigator / EDA 都還在快速進化）。

所以最後一個建議：把這本書當地圖、不當聖經。地圖告訴你大致方向、但走進去之後仍要看路標、問路人、調整步調。Ansible 的真正價值在用它把繁瑣 IT 工作變優雅自動化——讓人類專注在判斷與創造上。

  6. 開發者：選 1 個你常用的 community collection、找 good_first_issue label、選 1 個提 PR（即使 typo 也算）。記下從找 issue 到 merge 的全過程體驗。

  9. DevOps / SRE：規劃下個季度給內部團隊一場 30 min 的 Ansible talk — 主題自選（「我們為何選 AWX」「EE 遷移經驗」「EDA 試水溫」）。寫 outline、找日期、執行。

Ansible 專案 tagline 與核心價值。每個提案問「能更簡單嗎」。YAML / SSH / declarative 都源自此。
Forum (forum.ansible.com)
Discourse 平台。Ansible 社群預設起點。Q&A / 提案 / 公告 / events 都在這。比 mailing list 友善、比 Matrix 適合長文。
Matrix (chat.ansible.im)
Ansible 即時通訊（取代 IRC）。#users / #devel / #community 等多 channel。決策仍要落 GitHub / Forum。
IRC（已停用）
歷史上 Ansible 用 Libera.chat IRC。2026 已不是官方通路。新人請去 Forum 與 Matrix。
Working Group (WG)
社群成員圍繞特定主題自組的小組（Network / Cloud / Containers / Docs 等）。多數每 2 週一次 Matrix video meeting。
Contributor Summit
年度社群貢獻者聚會。通常在 CfgMgmtCamp（每年 2 月、Ghent）週三舉辦。Roadmap 與重大方向多在此公佈。
CfgMgmtCamp
歐洲最大配置管理 conference。每年 2 月在 Ghent 比利時舉辦。Ansible 是主要 track 之一。
AnsibleFest
Red Hat 主辦的年度 Ansible 大會。線上 + 線下混合。商業用戶比例較高。
Community Roadmap
整體社群方向計畫。每年初由 community team 在 Forum「Project Discussions」公佈。CfgMgmtCamp 後通常有更新。
ansible-core roadmap
引擎本身的 release 計畫。每個 2.x.0 major release 前 2-3 個月公佈。
Release candidate (RC)
正式 release 前的候選版。ansible-core / ansible package 每個 major release 前至少一個 RC、tag 後通常 5 工作日。
Feature freeze
release 前的鎖定期。core 開發者 focus 在 release candidate、不接新 feature 與不相關 fix。
Deprecation cycle (ansible-core)
標準 4 個 feature release。2.10 標 deprecation → 2.13 移除。視 use / urgency 可調整。
EOL (End of Life)
停止維護版本的時間點。新版發後舊版多可發一次最終 maintenance release。
Bullhorn newsletter
社群週訊。Forum 自動發布。摘要重要 PR / WG 動向 / 即將 release / 公告。新人必訂。
RHCE (EX294)
Red Hat Certified Engineer — Ansible 為核心。RHEL 環境配置自動化。考試需在 RHEL 上實作。
EX374
Red Hat Certified Specialist in Developing Automation with AAP。AAP 進階運維。取代舊版 EX447。
Patchback
GitHub bot — 自動 backport PR 到 stable branch。maintainer 加 backport label 觸發。community.general 等 collection 有用。
ansible-build-data
ansible package 構建的 metadata repo。指定每個 ansible 版本內含的 collection 與 core 確切版本。reproducible build 的源頭。
Ansible Community Podcast
社群非官方 podcast。不定期、訪談 maintainer 或重大 PR 作者。Forum 通常會公告新集數。
Jeff Geerling
知名 Ansible 社群人物。維護 docker test image（geerlingguy/docker-*-ansible）、寫《Ansible for DevOps》、有 YouTube 頻道。新手生態必接觸。
Platform Engineer
較新職稱。從 SRE / DevOps 演進。負責建內部 platform 給其他工程師用（IDP — internal developer platform）。Ansible AAP 是主要工具之一。
RH295 / RH374 課程
Red Hat 官方 Ansible 課程。RH295 對應 RHCE / EX294；RH374 對應 EX374。線上自學或 instructor-led 兩種模式。
Async-first communication
非同步優先的溝通文化。Forum / GitHub issue 預期幾天到幾週回應、不是即時客服。給 maintainer 24-72 小時 SLA 是合理期待。
Bikeshedding
軟體文化詞——為瑣碎風格爭辯（縮排空格 / 變數命名）而忽略真正重點。code review 與 community discussion 都該避免。
Source of truth
「真相之源」。Ansible 社群中：code 在 GitHub / 決策在 GitHub PR 與 Forum。Matrix 聊天記錄不算數、需總結到 GitHub / Forum 才有效。
maintainer 志工性質
多數 collection maintainer 不是 Red Hat 員工 — 是志工貢獻者。response SLA 是「best effort」、別用商業 support 的標準要求。
radically open
Ansible 開放治理原則。所有決策落公開管道（GitHub / Forum）、所有會議公開（Matrix + 視訊）、所有 roadmap 公佈。沒有「神秘內部會議」。
