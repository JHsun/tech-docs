第三篇 — 進階組織與重用

第 12 章 — Includes 與 Imports

前面章節已多次出現 include_tasks、import_tasks、include_role、import_role、import_playbook、include_vars。這六個 directive 各有微妙的語意差異，是業界最容易混淆、bug 最隱蔽的一組——尤其在「tags 為何沒生效」、「import 為什麼比 include 早報錯」這類問題上。本章把 include / import 的核心二分法（動態 vs 靜態）講清楚，逐一比對每對 directive 的差異，給出選擇指南：哪個情境用哪個、tags 與 conditional 怎麼互動、handler / variable 跨檔案行為。讀完這章你能看一眼 playbook 就知道為什麼某個 task 沒跑、某個 tag 沒被尊重。

本章覆蓋官方文件對應：Reusing Playbook Content · include_* · import_*
初學者必讀（12.1–12.3） 開發者必讀（全章） DevOps / SRE 必讀（特別 12.4 tags 行為與 12.7 選擇指南）

12.1核心二分法：靜態 vs 動態

所有 include / import 的差異，都源自一個根本問題：Ansible 是什麼時候讀取那個外部檔案？答案分兩種——解析時（靜態）或執行時（動態）。

Figure 12.1 — 靜態 import 在解析期讀檔；動態 include 在執行期才讀

12.1.1從這個差異衍生出的所有行為

行為import_* 靜態include_* 動態
外部檔案讀取時機 解析期（執行前） 執行期（跑到才讀）
檔名能用 inventory 變數 否（解析期還沒有 host 概念） 是
能配 loop: 否 是
tags 行為 tag 套用到內部每個 task tag 只套用到 include 動作本身
when 條件行為 copy 給內部每個 task 只判斷一次決定要不要進入
--list-tasks 顯示 看得到內部 task 看不到內部 task（runtime 才知道）
--start-at-task 可以從內部 task 開始 不能
內部錯誤發現時機 解析期就會抓到語法錯誤 跑到才會發現

12.1.2同名檔案 import vs include 行為對比

yaml · 範例：故意有語法錯誤的 tasks 檔 
# tasks/broken.yml — 故意有錯
- name: 這個 task 是好的
  ansible.builtin.debug:
    msg: "hello"

- name: 這個 task 有語法錯
  ansible.builtin.command: ls
  badparam: "oops"            # task 層不允許這個 key
yaml · 用 import 一開始就 fail 
tasks:
  - name: 先印一行          # ← 這個都跑不到
    ansible.builtin.debug:
      msg: "start"

  - ansible.builtin.import_tasks: tasks/broken.yml
  # 解析期讀到 broken.yml 就 fail，整個 play 不會啟動
yaml · 用 include 會跑前面 task 才 fail 
tasks:
  - name: 先印一行          # ← 這個會跑（印出 start）
    ansible.builtin.debug:
      msg: "start"

  - ansible.builtin.include_tasks: tasks/broken.yml
  # 跑到 include 才讀檔，這時才 fail
ⓘ 心智模型

import 像 C 的 #include — 編譯期就把檔案內容貼到原位。include 像 Python 的 import — 執行期才載入。聽起來相反，但這就是 Ansible 的命名約定。記住：import_* = 靜態 / 編譯期、include_* = 動態 / 執行期。

12.2六大 directive 全覽

Directive用途能否 loop常見場景
import_playbook 靜態引入整個 playbook（含多個 play） 否 主入口 site.yml 串聯各專屬 playbook
import_tasks 靜態引入 task 檔（拆 role 內 main.yml） 否 切分 role 主流程（install/configure/service）
include_tasks 動態引入 task 檔 是 依變數動態選檔（如 OS 檔名）、loop 同 task 多次
import_role 靜態引入 role（同 roles: keyword） 否 在 task 流中間插入 role，要 tag 繼承
include_role 動態引入 role 是 條件式或 loop 引用 role
include_vars 動態載入變數檔（無 import_vars 對應物） 是 依 OS 載入 vars/<family>.yml
⚠ 沒有 include_playbook

Playbook 層級只能用 import_playbook。理由：playbook 入口必須在解析期就確定整個執行計畫，動態載入 playbook 會破壞 Ansible 的執行模型。

12.3import_playbook — 串聯主入口

大型專案的主入口 site.yml 通常是「多個 playbook 串聯」的結構。第 10 章 10.7.1 已示範。

yaml · playbooks/site.yml 
---
# 主入口 — 用 import_playbook 串聯各專屬 playbook
# 內含的每個 playbook 各有自己的 hosts 與 tasks

- ansible.builtin.import_playbook: infra-bootstrap.yml
- ansible.builtin.import_playbook: webservers.yml
- ansible.builtin.import_playbook: databases.yml
- ansible.builtin.import_playbook: monitoring.yml

# 跑整套：ansible-playbook -i inv site.yml
# 跑某段：ansible-playbook -i inv playbooks/webservers.yml（直接跑單一 playbook）

# 進階：傳變數與 tag 給被引入的 playbook
- ansible.builtin.import_playbook: monitoring.yml
  vars:
    monitoring_intensity: verbose
  tags: [monitoring]
  when: env == 'production'      # ⚠ 這 when 是 group 層的，行為與 task when 不同
ⓘ 從 collection 引用 playbook

2.11+ 的功能：可以引用 collection 內的 playbook，import_playbook: namespace.coll.playbook_name。讓 collection 成為「可分享的部署 workflow」單位。

12.4import_tasks vs include_tasks — 業界最常踩雷

12.4.1tags 行為差異（最關鍵）

yaml · 被引入的檔案：tasks/deploy.yml 
- name: 拉 git
  ansible.builtin.git:
    repo: https://github.com/example/app.git
    dest: /var/www/app
  tags: [code]

- name: 裝 deps
  ansible.builtin.pip:
    requirements: /var/www/app/requirements.txt
  tags: [deps]

- name: 跑 migration
  ansible.builtin.command: python manage.py migrate
  tags: [migrations]
yaml · 用 import_tasks — tags 正常運作 
- name: 部署
  hosts: webservers
  tasks:
    - ansible.builtin.import_tasks: tasks/deploy.yml

# 解析期把三個 task 直接展開到 play 中，每個 task 各自帶自己的 tag
# 跑 ansible-playbook playbook.yml --tags migrations 會「正確」只跑 migration task
yaml · 用 include_tasks — tags 行為陷阱 
- name: 部署
  hosts: webservers
  tasks:
    - ansible.builtin.include_tasks: tasks/deploy.yml

# 跑 ansible-playbook playbook.yml --tags migrations
# 結果：什麼都不跑！（因為 include_tasks 自己沒帶 migrations tag）
# Ansible 連 include_tasks 都跳過，根本沒讀檔，就算讀了也只看 include 自己有沒有 tag

12.4.2解法：apply 子句

yaml · include_tasks 用 apply 給內部 task 傳 tag 
- ansible.builtin.include_tasks:
    file: tasks/deploy.yml
    apply:
      tags: [deploy, code, deps, migrations]
  tags:
    - deploy            # ← include 自己也要有 tag，否則整個 include 不會被觸發
    - code
    - deps
    - migrations

# 重點：
# 1) 外層 tags: 控制 include 動作要不要執行
# 2) apply.tags: 把 tag 傳給內部所有 task
# 3) 內部 task 自己的 tag 也仍然有效
⚠ 簡單規則：tags 重要的場景優先用 import_tasks

如果你常用 --tags / --skip-tags 控制執行範圍，預設用 import_tasks，行為直觀正確。只有需要 loop / 動態檔名等動態能力時才改 include_tasks，並且記得加 apply。

12.4.3動態檔名（include_tasks 的招牌場景）

yaml · 依 OS 動態載入 
- name: 引入 OS 特定 task
  ansible.builtin.include_tasks: "tasks/{{ ansible_distribution | lower }}.yml"
# 動態解析後可能是 tasks/ubuntu.yml 或 tasks/rocky.yml
# 用 import_tasks 會 fail — 解析期 ansible_distribution 還未知

12.4.4loop — 唯有 include_tasks 能用

yaml · 對多個 user 引用同一段 task 流 
- name: 為每個 user 跑一遍 setup-user task 流
  ansible.builtin.include_tasks: tasks/setup-user.yml
  loop: "{{ users }}"
  loop_control:
    loop_var: user             # 內部用 user 而非 item
    label: "{{ user.name }}"

12.5import_role vs include_role

第 10 章 10.6 已比較過。本節聚焦對比 task 層 import / include 引用 role 的差異。

12.5.1tags 行為（與 import_tasks vs include_tasks 一致）

yaml · import_role — tag 自動繼承內部 task 
- ansible.builtin.import_role:
    name: nginx
  tags: [webserver]

# nginx role 內部所有 task 都自動帶 webserver tag
# 跑 --tags webserver 會跑整個 role
yaml · include_role — tag 只給 include 自己 
- ansible.builtin.include_role:
    name: nginx
  tags: [webserver]

# 跑 --tags webserver 時 include_role 會被觸發
# 但 nginx role 內部 task 沒有 webserver tag，依各自的 tag 執行
# 同樣可以加 apply 解決：

- ansible.builtin.include_role:
    name: nginx
    apply:
      tags: [webserver]
  tags: [webserver]

12.5.2動態 role 名（include_role 的招牌）

yaml · 依變數選 role 
- name: 依設定選擇 web server role
  ansible.builtin.include_role:
    name: "{{ webserver_type }}"      # 可能是 nginx, apache, caddy

- name: 用 loop 部署多個應用實例
  ansible.builtin.include_role:
    name: app_instance
  vars:
    app_name: "{{ item.name }}"
    app_port: "{{ item.port }}"
  loop:
    - { name: api,   port: 8080 }
    - { name: admin, port: 8081 }

12.6include_vars — 動態變數載入

第 7 章已介紹過。回顧三大典型場景：

12.6.1OS 特定變數

yaml · 依 OS family 載入 
- name: 載入 OS 特定變數
  ansible.builtin.include_vars: "{{ ansible_os_family }}.yml"
# 動態解析為 Debian.yml 或 RedHat.yml

- name: 含 fallback 的版本
  ansible.builtin.include_vars:
    file: "vars/{{ ansible_distribution }}-{{ ansible_distribution_major_version }}.yml"
  failed_when: false     # 找不到對應檔不要 fail

12.6.2整個目錄載入

yaml · 載入整個目錄的變數檔 
- name: 載入 vars/secrets/ 下所有 yml
  ansible.builtin.include_vars:
    dir: vars/secrets
    extensions: [yml, yaml]
    depth: 1                # 不遞迴進子目錄

12.6.3把結果存成 named variable

yaml · 載入結果存成自訂變數 
- name: 載入額外設定但不污染全域命名空間
  ansible.builtin.include_vars:
    file: extra-config.yml
    name: extra_config           # 結果都包進 extra_config dict

# 用法：{{ extra_config.some_key }}

12.7.2業界默契：預設用 import，必要才 include

①

import 是「程式員心智模型」

解析期把內容貼進主流程，行為跟普通 task 一樣。Tags、conditional、handler、--list-tasks 都正常運作。

②

include 帶有 runtime 魔法

動態能力強大但行為微妙。tags 的「半隔離」是新手最常遇到的 bug。

③

除非你需要動態能力

否則一律用 import_*。需要 loop / 變數檔名 / runtime 條件時才換 include_*，並用 apply 補回 tag 行為。

④

不要混用 import 與 include 同一檔

同一個檔有時 import 有時 include 行為會混亂。整個 role 或專案統一用同一種模式較好維護。

12.8實戰：完整 role 內 task 拆分模式

整合本章與第 10 章的最佳實踐，看一個生產級 role 的 tasks/ 拆分。

text · roles/myapp/tasks/ 結構 
roles/myapp/tasks/
├── main.yml              # 入口 — 只放 import_tasks
├── preflight.yml         # 前置檢查
├── install.yml           # 安裝套件
├── configure.yml         # 配置檔
├── service.yml           # 服務管理
├── ubuntu.yml            # Ubuntu 特定
├── rhel.yml              # RHEL 特定
└── verify.yml            # 部署後驗證
yaml · roles/myapp/tasks/main.yml — 整合 import 與 include 
---
# 1) include_vars — 動態載入 OS 變數（必須 include）
- name: 載入 OS 特定變數
  ansible.builtin.include_vars: "{{ ansible_os_family }}.yml"
  tags: [always]

# 2) import_tasks — 靜態 task 群（tags 行為直觀）
- name: 前置檢查
  ansible.builtin.import_tasks: preflight.yml
  tags: [preflight]

- name: 安裝套件
  ansible.builtin.import_tasks: install.yml
  tags: [install]

# 3) include_tasks — 動態檔名（依 OS）
- name: OS 特定設定
  ansible.builtin.include_tasks: "{{ ansible_distribution | lower }}.yml"
  tags: [configure]

# 4) import_tasks — 通用設定
- name: 通用設定
  ansible.builtin.import_tasks: configure.yml
  tags: [configure]

- name: 服務管理
  ansible.builtin.import_tasks: service.yml
  tags: [service]

# 5) 條件式 — 部署後驗證（只在不是 quick mode 才跑）
- name: 部署後驗證
  ansible.builtin.import_tasks: verify.yml
  when: not (myapp_quick_mode | default(false))
  tags: [verify]
✓ 這個結構的好處

① tag 行為直觀——--tags configure 跑兩個檔內所有 task。② 解析期錯誤早期發現——任何子檔有 yaml 錯誤都在 play 啟動前報。③ 清楚的職責切分——每個檔做一件事。④ OS 動態能力保留——只在必要的 1 個地方用 include_tasks。

12.9本章重點回顧

01

import = 靜態 / include = 動態

import 在解析期讀檔（執行前），include 在執行期才讀。所有行為差異都從這裡推導。

02

六大 directive

import_playbook（無 include 對應）、import_tasks/include_tasks、import_role/include_role、include_vars（無 import 對應）。

03

tags 行為差異最關鍵

import 的 tag 自動繼承給內部 task。include 的 tag 只給 include 自己。這是業界 #1 踩雷點。

04

include 的 apply 子句

用 apply: tags: [...] 把 tag 傳給內部所有 task，模擬 import 的行為。

05

動態能力只有 include 有

檔名含變數、loop、runtime 條件——必須用 include。import 解析期就要確定，無法支援這些動態能力。

06

沒有 include_playbook

Playbook 層級只能用 import_playbook。Ansible 設計上不允許動態載入 playbook。

07

沒有 import_vars

變數載入只有 include_vars。OS 特定變數、目錄載入、命名空間隔離都靠它。

08

業界默契：預設 import

除非有動態需求，否則一律 import_*。需要動態時才用 include_* 並補上 apply 處理 tag。

練習題

  1. 初學者：建立 tasks/hello.yml 含 2 個 debug task，分別在主 playbook 用 import_tasks 與 include_tasks 引用，跑兩次觀察 PLAY RECAP 是否相同。
  2. 初學者：在被引用的 hello.yml 內故意打錯 yaml 語法（如多一個冒號），分別用 import 與 include 跑，觀察錯誤什麼時候 發生。
  3. 初學者：寫一個 playbook 用 import_playbook 串聯 webservers.yml 與 databases.yml 兩個子 playbook。
  4. 開發者：用 include_tasks 配 loop 對一個 user list 重複跑同一段 setup-user.yml task 流，並用 loop_control.loop_var 改變數名避免衝突。
  5. 開發者：用 include_tasks 依 ansible_distribution 動態載入對應檔（ubuntu.yml / rhel.yml / debian.yml）。確認對應檔名缺失時 fallback 行為。
  6. 開發者：故意在被 include_tasks 引用的檔案內各 task 加 tag，主 playbook 跑 --tags X 觀察是否如預期執行。試著加 apply: tags: 修復行為。
  7. DevOps / SRE：把第 10 章的 nginx role tasks/main.yml 改造成本章 12.8 的「整合 import + include」結構，跑 --tags install、--tags configure 等驗證 tag 行為。
  8. DevOps / SRE：把一個既有的扁平 playbook（200+ 行的 monolithic 檔案）依職責拆成 6 個子 task 檔，用 import_tasks 串聯。確認 --list-tasks 能完整顯示所有 task 名。
  9. DevOps / SRE：寫一個用 include_role 配 loop 部署多個應用實例的 playbook（每個 item 含 app_name + app_port）。比較若改成多次 import_role 寫死，哪種較好維護？

本章詞彙表

Static / 靜態
解析期就讀檔展開的處理方式。import_* 是靜態。Ansible 在執行前已知道完整 task 結構。
Dynamic / 動態
執行期才讀檔的處理方式。include_* 是動態。支援 loop / 變數檔名 / runtime 條件。
import_playbook
靜態引入整個 playbook（含其 hosts / vars / tasks）。常見於主入口 site.yml 串聯各專屬 playbook。沒有 include_playbook 對應物。
import_tasks
靜態引入 task 檔。內部 task 直接展開到主流程，tags 自動繼承。預設首選。
include_tasks
動態引入 task 檔。支援 loop、變數檔名、runtime 條件。需要動態能力時才用。
import_role
靜態引入 role。等同 roles: keyword 的行為，但寫在 task 層。tags 自動繼承內部 task。
include_role
動態引入 role。支援 loop、條件、動態 role 名。
include_vars
動態載入變數檔／目錄／命名空間。沒有 import_vars 對應物。
apply 子句
include_* 的可選參數，把 tags / when 等 directive 套用到內部 task。模擬 import 的繼承行為。
--list-tasks
命令列旗標，列出 playbook 將執行的所有 task。import 引入的 task 看得到，include 引入的看不到（因為 runtime 才知道）。
--start-at-task
命令列旗標，從指定 task 開始執行（跳過前面）。對 import 引入的 task 有效，對 include 引入的無效。
--tags / --skip-tags
命令列旗標，依 tag 過濾要執行的 task。對 import 行為直觀；對 include 需要配 apply 才正確。
