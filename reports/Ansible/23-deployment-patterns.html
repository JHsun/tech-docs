第 23 章 — 部署模式

第六篇進入「實戰工程師」最重要的領域——把前 22 章學的東西組合成生產級部署 workflow。本章是這篇的基礎：部署模式（deployment patterns）。三個核心問題決定一次部署的好壞——downtime（停機時間）、blast radius（爆炸半徑）、rollback（回滾能力）。Ansible 用三大武器解決：serial 控制每批處理的 host 數、max_fail_percentage 是自動 circuit breaker、block / rescue 提供事務式錯誤處理。本章帶你走過：① 部署的核心問題；② 三大模式對比（rolling / blue-green / canary）；③ serial 完整用法（整數 / 百分比 / progressive list）；④ max_fail_percentage 與 any_errors_fatal 的差異；⑤ 從 LB drain 到 health check 到自動 rollback 的完整 pattern；⑥ symlink-based releases 實作 blue-green；⑦ DB migration 與應用部署的協調；⑧ 業界 8 條最佳實踐。讀完這章你能寫一個能安全部署到 100 個 host的 playbook——失敗自動停止、不會炸掉服務。

23.1部署的三個核心問題

所有部署模式都在解決同一組問題。Ansible 在每個問題上都有對應 keyword：

⏱

Downtime — 停機時間

使用者看得到的服務中斷。zero-downtime 部署的目標是「整個過程任何時刻服務都可用」。Ansible 用 serial 分批 + LB drain 達成。

💥

Blast Radius — 爆炸半徑

一個 bug 部署上去後影響多少使用者。如果 100 host 全裝壞版本，blast = 100%；如果先 1 host 試水溫，blast = 1%。Ansible 用 serial 的 progressive list 控制。

↩

Rollback — 回滾能力

部署炸了多快能恢復。理想是「一個指令就回到上一版」。Ansible 用 block / rescue、symlink-based releases、deployment 模組支援 rollback。

ⓘ 部署模式的選擇是 trade-off

沒有「最好」的部署模式——只有「適合你 SLA、host 規模、資源預算」的模式。本章會釐清三大模式（rolling / blue-green / canary）的優劣，讓你做出適合的選擇。

23.3serial 完整用法

serial 是 Ansible rolling deployment 的核心。它告訴 Ansible：「不要一次對所有 host 跑這 play，分批跑」。

23.3.1三種寫法

yaml · serial 三種寫法 
# 寫法 ① — 整數：每次處理 N 個
- hosts: webservers     # 假設 20 台
  serial: 5              # 每批 5 台 → 共 4 批
  tasks: [...]

# 寫法 ② — 百分比：每次處理 N%
- hosts: webservers
  serial: "25%"          # 每批 25% → 4 批
  tasks: [...]

# 寫法 ③ — Progressive list（最強大）
- hosts: webservers
  serial:
    - 1                  # 第 1 批：1 台 canary
    - 5                  # 第 2 批：5 台
    - "25%"              # 第 3 批：剩下的 25%
    - "100%"             # 第 4 批：剩下全部
  tasks: [...]

23.3.2Progressive serial 是 canary 的核心

ⓘ 為什麼從 1 開始

第一批設 1 台 canary 是業界鐵律。一台炸不死服務（如果 LB 後面有 19 台健康），但能告訴你「這個版本能不能跑」。第一批不要設 5、設 1——blast radius 最小化。確認 canary 健康後再放大批次。

23.3.3linear vs free strategy

strategy 與 serial 是不同維度。前者控制同一 task 在不同 host 之間的同步，後者控制每批多少 host。

strategy行為用法
linear（預設）每個 task 等所有 host 完成才走下一個 task部署、配置（必須同步進行）
free每個 host 自己一路跑到 play 結束批次維護、互相獨立的 task
debug互動模式 task-by-task pause除錯

23.3.4throttle — task 級別併發控制

yaml · throttle vs serial 
# serial 是 play 級別 — 整批 host 限制
- hosts: webservers
  serial: 5
  tasks:

    # throttle 是 task 級別 — 單一 task 限制併發
    - name: 打 rate-limited API
      ansible.builtin.uri:
        url: https://api.example.com/notify
      throttle: 3           # 即使 batch 5 個，這 task 同時只 3 個跑

23.4max_fail_percentage — 自動 circuit breaker

單 serial 不夠安全。如果第一批 5 個全失敗，預設行為是繼續往下推（除非 100% 失敗）。max_fail_percentage 是 circuit breaker：超過閾值就停止整個 play。

23.4.1基本用法

yaml · 基本 circuit breaker 
---
- name: 安全的 rolling deploy
  hosts: webservers          # 假設 20 台
  serial: 5
  max_fail_percentage: 20     # 任一批 >20% 失敗就停整個 play
  tasks:
    - name: 部署
      ansible.builtin.include_role:
        name: deploy_app

# 數學：
# serial: 5 + max_fail_percentage: 20
# 5 × 20% = 1 — 一批 5 個只要 >1 個失敗（即 ≥2 個），停止
# 注意：Ansible 會 round down — 5 × 20% = 1，所以閾值是「> 1 才停」

23.4.2max_fail_percentage vs any_errors_fatal

選項行為典型場景
預設（無設定） 所有 host 都失敗才停 不要用（生產不安全）
max_fail_percentage: N 失敗超過 N% 停整個 play 多數 rolling deployment（推薦）
any_errors_fatal: true 任何 host 失敗即停 關鍵 task（DB migration / pre-flight）
max_fail_percentage: 0 等同 any_errors_fatal — 任何失敗即停 嚴格 canary 模式
⚠ any_errors_fatal 覆蓋 max_fail_percentage

兩個都設時 any_errors_fatal 勝出。要混合使用——pre-flight play 用 any_errors_fatal: true（不允許任何失敗），rolling deploy play 用 max_fail_percentage: 20（允許少量失敗）。

23.5LB drain pattern

Rolling deployment 的關鍵不是 serial，是處理 host 期間怎麼讓 traffic 不打進去。標準做法：部署前從 load balancer 移除、部署後再加回。

23.5.1delegate_to: localhost 模式

yaml · 標準 LB drain pattern 
- name: Rolling deployment with LB drain
  hosts: webservers
  serial: 2
  max_fail_percentage: 20

  pre_tasks:
    # 1) 通知 LB 把這台 host 移出 — 注意 delegate_to: localhost
    - name: 從 LB 移除 {{ inventory_hostname }}
      ansible.builtin.uri:
        url: "http://lb.internal:8080/api/backends/{{ inventory_hostname }}/disable"
        method: POST
      delegate_to: localhost      # 在 control node 跑 — 不是在 webserver 上

    # 2) 等現有連線 drain
    - name: 等連線 drain
      ansible.builtin.pause:
        seconds: 15
      delegate_to: localhost

  tasks:
    - name: 部署新版本
      ansible.builtin.include_role:
        name: deploy_app

    - name: 健康檢查 — 重試 10 次
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/health"
        status_code: 200
      register: health
      retries: 10
      delay: 3
      until: health.status == 200

  post_tasks:
    # 3) 健康後加回 LB
    - name: 加回 LB
      ansible.builtin.uri:
        url: "http://lb.internal:8080/api/backends/{{ inventory_hostname }}/enable"
        method: POST
      delegate_to: localhost

23.6健康檢查與自動 rollback

健康檢查不只是 pass/fail——失敗時應該自動 rollback 而非繼續推。block / rescue 是事務式錯誤處理的核心。

23.6.1block / rescue / always 三段式

yaml · 自動 rollback pattern 
- name: 部署 + 健康檢查 + 失敗自動 rollback
  hosts: webservers
  serial: 2
  max_fail_percentage: 20

  tasks:
    - name: 事務式部署
      block:
        # 主流程
        - name: 部署新版本
          ansible.builtin.include_role:
            name: deploy_app

        - name: 健康檢查
          ansible.builtin.uri:
            url: "http://{{ inventory_hostname }}:8080/health"
            status_code: 200
          register: h
          retries: 10
          delay: 3
          until: h.status == 200

      rescue:
        # 失敗才跑
        - name: log 失敗
          ansible.builtin.debug:
            msg: "⚠ 部署在 {{ inventory_hostname }} 失敗 — 自動 rollback"

        - name: 回滾到上一版
          ansible.builtin.include_role:
            name: rollback_app

        - name: 通知值班
          community.general.slack:
            token: "{{ vault_slack_token }}"
            msg: "🚨 {{ inventory_hostname }} rollback - 看 log"
          delegate_to: localhost

        # 仍要把 host 標為失敗，讓 max_fail_percentage 計入
        - ansible.builtin.fail:
            msg: "部署失敗"

      always:
        # 無論成敗都跑 — 例如 cleanup 暫存檔
        - ansible.builtin.file:
            path: /tmp/deploy.lock
            state: absent

23.6.2rescue 的意義

✓ Block / rescue 給你事務語意

不像傳統 shell script「失敗就停在那裡」，block / rescue 讓你能在每個 host 上做本地 rollback——即使 max_fail_percentage 觸發整個 play 停止，那些已經失敗的 host 也已經被 rollback 回上一版。最終狀態是「要嘛全新版、要嘛維持舊版」，沒有「半新半舊的混亂狀態」。

23.7Symlink-based releases — Blue-Green 簡化版

Blue-green 完整實作需要兩套基礎設施很貴，但用 symlink-based releases 在單台 host 內可以模擬類似效果——舊版仍在硬碟上，切回只是改 symlink。

23.7.1目錄結構

text · 標準 release 目錄結構 
/opt/myapp/
├── current -> releases/20260508-1430/    # symlink — 永遠指當前 release
├── releases/
│   ├── 20260507-0900/                    # 上上版
│   ├── 20260508-1100/                    # 上一版（rollback target）
│   └── 20260508-1430/                    # 當前版（current 指向）
└── shared/                               # 共用 — log / 上傳檔 / config
    ├── config/
    └── logs/

23.7.2切換邏輯

yaml · symlink-based release 
- name: 產生 release timestamp
  ansible.builtin.set_fact:
    release_id: "{{ ansible_date_time.iso8601_basic_short }}"

- name: 建新 release 目錄
  ansible.builtin.file:
    path: "/opt/myapp/releases/{{ release_id }}"
    state: directory
    mode: "0755"

- name: 解壓新 artifact
  ansible.builtin.unarchive:
    src: "/tmp/myapp-{{ app_version }}.tar.gz"
    dest: "/opt/myapp/releases/{{ release_id }}"
    remote_src: yes

- name: link shared resources（config / logs）
  ansible.builtin.file:
    src: "/opt/myapp/shared/{{ item }}"
    dest: "/opt/myapp/releases/{{ release_id }}/{{ item }}"
    state: link
  loop: ["config", "logs"]

- name: 記下舊 release（為 rollback 準備）
  ansible.builtin.command:
    cmd: readlink /opt/myapp/current
  register: old_release
  changed_when: false
  failed_when: false            # 第一次部署可能還沒 current

- name: 存舊 release path 到檔案（給 rollback 用）
  ansible.builtin.copy:
    content: "{{ old_release.stdout }}"
    dest: /opt/myapp/.previous_release
  when: old_release.stdout != ""

- name: ⭐ 切換 symlink — atomic！
  ansible.builtin.file:
    src: "/opt/myapp/releases/{{ release_id }}"
    dest: /opt/myapp/current
    state: link
    force: yes

- name: restart 應用
  ansible.builtin.systemd:
    name: myapp
    state: restarted

- name: 清理太舊 release（保留 5 個）
  ansible.builtin.shell:
    cmd: |
      cd /opt/myapp/releases && \
      ls -t | tail -n +6 | xargs -r rm -rf
  changed_when: false

23.7.3Rollback playbook

yaml · rollback.yml — 一個指令回到上一版 
---
- name: Rollback 到上一版
  hosts: webservers
  serial: 5          # rollback 也分批 — 別一次全切
  tasks:
    - name: 讀上一版 path
      ansible.builtin.slurp:
        src: /opt/myapp/.previous_release
      register: prev

    - name: 把 symlink 切回上一版
      ansible.builtin.file:
        src: "{{ prev.content | b64decode | trim }}"
        dest: /opt/myapp/current
        state: link
        force: yes

    - name: restart 應用
      ansible.builtin.systemd:
        name: myapp
        state: restarted

    - name: 驗證 rollback 健康
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/health"
        status_code: 200
      retries: 10
      delay: 3

# 跑：ansible-playbook -i inventory rollback.yml

23.8DB migration 與應用部署的協調

應用部署 + schema 變更是部署最棘手的場景。「應用 vN+1 需要新 column」但「應用 vN 跑著時不能加 column 否則炸」。標準解法：DB migration 在獨立 play 跑 once + serial。

23.8.1協調 pattern

yaml · DB migration + rolling app deploy 
---
# Play 1: pre-flight checks（嚴格）
- name: Pre-deployment 驗證
  hosts: webservers
  any_errors_fatal: true      # pre-flight 一個失敗就停
  gather_facts: true
  tasks:
    - name: 確認硬碟空間 > 2GB
      ansible.builtin.shell: df --output=avail / | tail -1
      register: disk
      changed_when: false
      failed_when: disk.stdout | int < 2097152

    - name: 確認當前服務健康（部署前狀態 baseline）
      ansible.builtin.uri:
        url: "http://localhost:8080/health"
        status_code: 200


# Play 2: DB migration（一次性、單一 host）
- name: Schema migration
  hosts: db_primary
  any_errors_fatal: true
  tasks:
    - name: 跑 migration script
      ansible.builtin.command:
        cmd: "/opt/myapp/bin/migrate up --target {{ app_version }}"
      register: migration
      run_once: true             # 即使 db_primary 多台也只跑一次
      changed_when: "'no changes' not in migration.stdout"


# Play 3: Rolling app deploy
- name: Rolling 應用部署
  hosts: webservers
  serial: [1, "25%", "100%"]   # progressive canary
  max_fail_percentage: 10
  tasks:
    - name: 部署
      block:
        - ansible.builtin.include_role:
            name: deploy_app
        - ansible.builtin.uri:
            url: "http://{{ inventory_hostname }}:8080/health"
            status_code: 200
          retries: 10
          delay: 3
      rescue:
        - ansible.builtin.include_role:
            name: rollback_app
        - ansible.builtin.fail:

23.8.2backward-compatible schema 原則

ⓘ Schema 變更的黃金法則

Migration 一定 backward-compatible——意即「跑了 migration 後、舊版應用仍能繼續運作」。實作：① 加 column 用 nullable / 有 default；② 刪 column 分兩個 release（先讓 app 不再用、下次 release 才刪）；③ 重命名分三步（加新 column → 同寫雙方 → 刪舊 column）。違反這條，rolling deploy 期間就會炸——舊 app 看到新 schema 整個壞掉。

23.9業界最佳實踐

①

Pre-flight 用 any_errors_fatal

磁碟空間 / 服務基線健康 / 配置驗證等 pre-check 任一失敗就停。any_errors_fatal: true 而非 max_fail_percentage。

②

Rolling 用 progressive serial

每個 production deploy 都從 1 開始：serial: [1, 5, "25%", "100%"]。Canary 是免費的保險。

③

max_fail_percentage 必設

沒設 = 99 個失敗 1 個成功也繼續推。生產 deploy 永遠設一個合理閾值（通常 10–20%）。

④

block / rescue 自動 rollback

失敗的 host 在原處 rollback 而非留下半新半舊狀態。配 Slack 通知值班。

⑤

LB drain 一定要 delegate_to: localhost

從 LB 移除動作要在 control node 跑，不是在被部署的 host 上（那 host 即將下線怎麼跟 LB 說？）。

⑥

Health check until 重試

App 起來不是瞬間——用 retries: 10 + delay: 3 + until 給 30 秒 startup window。沒重試直接 fail = 大量 false alarm。

⑦

Symlink-based releases

結合 rolling + 瞬間 rollback 能力。current symlink + 5 個歷史 release 是 80% 場景的甜蜜點。

⑧

DB migration 永遠 backward-compatible

新 schema 對舊 app 不能 breaking。重命名分三 release、刪 column 分二 release。違反這條 rolling deploy 期間必炸。

23.10本章重點回顧

01

三個核心問題

Downtime（停機）、blast radius（爆炸半徑）、rollback（回滾速度）。所有部署模式都在解這三個。

02

三大部署模式

Rolling（預設、80% 場景）、blue-green（嚴格 SLA、2x 資源）、canary（traffic-routing 場景）。

03

serial 三種寫法

整數 / 百分比 / progressive list。第三種最強——從 1 canary 開始逐批放大。

04

max_fail_percentage 是 circuit breaker

沒設這個 = 沒安全網。配 serial 用，失敗超閾值整個 play 停。any_errors_fatal 是更嚴格版本。

05

LB drain 模式

從 LB 移除（delegate_to: localhost）→ 等 connection drain → 部署 → health check → 加回 LB。

06

block / rescue 自動 rollback

失敗 host 本地 rollback、不留半新半舊狀態。配 Slack 通知。

07

Symlink-based releases

current symlink + 多個歷史 release。瞬間 rollback、保留歷史。

08

DB migration 三 play 結構

Pre-flight（any_errors_fatal）→ DB migration（run_once）→ rolling app deploy。Schema 變更必 backward-compatible。

練習題

  1. 初學者：用 serial: 2 對 4 台 web server 部署簡單 nginx 配置變更。觀察 PLAY RECAP 看出 task 是分批執行（不是 4 台同時）。
  2. 初學者：把上題改成 serial: [1, 2, "100%"] progressive list。觀察三個批次大小與順序。
  3. 初學者：故意讓某台 web server 的 deploy task 失敗（如 copy 不存在的檔案）。設 max_fail_percentage: 25，跑 4 台。第一批 1 台失敗會發生什麼？
  4. 開發者：實作本章 23.5 的 LB drain pattern。用 docker 起一個簡單 HAProxy + 3 個 nginx backend，寫 playbook drain → 改 nginx config → enable。確認 drain 期間 traffic 不打進去。
  5. 開發者：實作本章 23.6 的 block / rescue rollback pattern。手動讓 health check 失敗（return 503），觀察 rescue 區塊執行 + Slack 通知。
  6. 開發者：實作本章 23.7 的 symlink-based release。建 /opt/myapp/{current,releases,shared} 結構、寫 deploy + rollback playbook。
  7. DevOps / SRE：寫一個生產級 deploy playbook，整合所有功能：① pre-flight；② DB migration；③ rolling deploy（progressive serial）；④ LB drain；⑤ health check；⑥ block/rescue rollback。對 6 台 web server fleet 測試。
  8. DevOps / SRE：研究你的服務目前怎麼部署。哪一個模式（rolling / blue-green / canary）最適合？downtime / blast radius / rollback 三個維度比一比。寫一份 1 頁的部署策略文件。
  9. DevOps / SRE：模擬真實 incident — 部署到一半（第 2 批）發現問題。寫 incident playbook：①立即停止部署；② rollback 已部署批次；③ 通知值班。確認可在 30 秒內執行完。

本章詞彙表

Deployment pattern
把新版本應用送到生產環境的策略。三大主流：rolling、blue-green、canary。
Downtime
使用者看得到的服務中斷時間。zero-downtime 部署 = 整個過程 0 downtime。
Blast radius
一次部署 bug 影響的使用者比例。canary 部署 1% blast、blue-green 是 0 或 100%。
Rollback
從新版本回到上一版的能力與速度。symlink-based / blue-green / database point-in-time recovery 等實作方式。
Rolling deployment
逐批替換 host 的部署模式。配 serial 控制批次大小。Ansible 最自然支援的模式。
Blue-green deployment
準備兩套完全獨立的環境（blue 與 green），瞬間切流量。資源 2x 但 rollback 瞬間。
Canary deployment
新版本先給小部分流量（5%），觀察無異常後逐步放大。需 traffic routing 能力（service mesh / API gateway / LB weighted routing）。
serial keyword
Ansible play 層級的選項。控制每批處理的 host 數。三種寫法：整數、百分比字串、progressive list。
Progressive serial
serial 的 list 寫法 — serial: [1, 5, "25%", "100%"]。從小批次開始逐步放大，是 canary in Ansible 的經典實作。
max_fail_percentage
play 層級的 circuit breaker。失敗比例超過閾值整個 play 停止。Round down — 5 × 20% = 1。
any_errors_fatal
play 或 task 層級的選項。任一 host 失敗就停。比 max_fail_percentage 嚴格（後者允許少量失敗）。
strategy: linear
預設 strategy。每個 task 等所有 host 完成才開下一個 task — 同步執行。
strategy: free
每個 host 各自跑到 play 結束、不互相等。維護任務適用。
throttle
task 層級的併發上限。即使 batch 5 個 host，可單一 task 限制同時 N 個（rate-limited API 等場景）。
delegate_to: localhost
把 task 交付給 control node 執行的 keyword。LB drain / cloud API call / 通知服務等用 — 不能在被部署的 host 自己跑。
LB drain pattern
從 LB 移除 host → 等 connection drain → 部署 → health check → 加回 LB。zero-downtime rolling 的標準步驟。
Health check
部署後驗證應用能正常服務。uri 模組 + retries + until 給 startup window。
block / rescue / always
Ansible 的事務式錯誤處理。block 是主流程、rescue 失敗時跑、always 必跑。實作自動 rollback 的核心。
Symlink-based release
用 current symlink 指向當前 release 目錄。切換 = 改 symlink。瞬間切換 + 保留歷史 + 容易 rollback。
shared directory
跨 release 共用的資源目錄（config / logs / 上傳檔）。每個 release 透過 symlink 連到 shared。
run_once: true
task 層級選項。即使有多個 host 在 group 內、這 task 只在第一個 host 跑一次。DB migration 等場景。
flush_handlers
Ansible meta task — 強制立即執行已 notify 的 handlers。用於需在後續 task 前確保 service restart 完成的場景。
Backward-compatible migration
新 schema 對舊應用不 breaking。rolling deploy 期間舊 app + 新 schema 必須能共存運作。重命名分三步、刪除分兩步。
Circuit breaker
故障保護機制。電流超載時切斷電路，類比 Ansible 的 max_fail_percentage — 失敗超閾值停止整個 play、防止繼續惡化。
