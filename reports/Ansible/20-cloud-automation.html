第 20 章 — 雲端自動化：AWS / GCP / Azure

前面章節聚焦對既存 host 做事——但雲端時代有個前置問題：host 從哪來？本章兩條軸線並進：① provision 軸——用 Ansible 建立雲端資源（EC2 / VPC / S3 / RDS、Azure VM / AKS、GCP Compute / GKE）；② config 軸——用 cloud inventory plugin 動態發現雲端 host 並做後續設定。會釐清 Ansible 與 Terraform 該怎麼分工——Terraform 適合 stateful 基礎設施 lifecycle、Ansible 適合 provisioning + post-provisioning configuration。實戰部分以 AWS 為主軸（市占最大），Azure / GCP 給對照範例，多雲策略給設計指引。Credential 管理、cost 控制、環境隔離（dev / staging / prod）等業界實踐也會涵蓋。讀完這章你能用 Ansible 從零建立一個跨可用區、含負載均衡、自動擴展、配置完成的應用環境。

20.1.3Ansible vs Terraform 該怎麼分工

ⓘ 業界共識

Terraform 強在 provision、Ansible 強在 configure。Terraform 有 state file 追蹤資源（drift detection、destroy 完整 cleanup），Ansible 是 stateless 但對 SSH-based 配置遠遠勝出。大團隊典型分工：Terraform 建 VPC / VM / DB / IAM → 把 instance 資訊輸出到 inventory → Ansible 接手做 OS 配置與應用部署。

①

純 Ansible 場景

小團隊、簡單環境、不想多學工具。Ansible 涵蓋 provision + configure。

②

純 Terraform 場景

純 cloud-native（Lambda、Fargate、managed DB）。沒 VM 配置需求，用 Terraform + cloud-init 即可。

③

混合場景（最常見）

Terraform 建基礎設施 → ansible 做 OS / 應用配置。兩者透過 inventory 銜接。

20.3.2EC2 provision 完整範例

yaml · playbooks/provision_ec2.yml 
---
- name: 建立完整 AWS web server stack
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    region: us-east-1
    env: dev
    app_name: myapp
  tasks:

    # --- 1) VPC ---
    - name: 建立 VPC
      amazon.aws.ec2_vpc_net:
        name: "{{ app_name }}-{{ env }}-vpc"
        cidr_block: 10.0.0.0/16
        region: "{{ region }}"
        tags: { Environment: "{{ env }}", App: "{{ app_name }}" }
      register: vpc

    - name: 建立 subnet
      amazon.aws.ec2_vpc_subnet:
        vpc_id: "{{ vpc.vpc.id }}"
        cidr: 10.0.1.0/24
        az: "{{ region }}a"
        region: "{{ region }}"
        map_public: true
        tags: { Name: "{{ app_name }}-{{ env }}-subnet" }
      register: subnet

    - name: 建立 internet gateway
      amazon.aws.ec2_vpc_igw:
        vpc_id: "{{ vpc.vpc.id }}"
        region: "{{ region }}"
        state: present
      register: igw

    # --- 2) Security group ---
    - name: web SG — 開 80 / 443 / 22
      amazon.aws.ec2_security_group:
        name: "{{ app_name }}-{{ env }}-web-sg"
        description: Allow web + SSH
        vpc_id: "{{ vpc.vpc.id }}"
        region: "{{ region }}"
        rules:
          - { proto: tcp, ports: [22],  cidr_ip: '10.0.0.0/8' }
          - { proto: tcp, ports: [80, 443], cidr_ip: '0.0.0.0/0' }
      register: sg

    # --- 3) EC2 instances ---
    - name: 啟動 EC2
      amazon.aws.ec2_instance:
        name: "{{ app_name }}-{{ env }}-web-{{ item }}"
        key_name: my-keypair
        instance_type: t3.small
        image_id: ami-0c7217cdde317cfec     # Ubuntu 22.04 us-east-1
        vpc_subnet_id: "{{ subnet.subnet.id }}"
        security_group: "{{ sg.group_id }}"
        network: { assign_public_ip: true }
        tags:
          Environment: "{{ env }}"
          Role: webserver
          App: "{{ app_name }}"
          ManagedBy: ansible
        wait: yes
        state: running
      loop: ["01", "02"]
      register: ec2_results

    # --- 4) 把新 instance 加進 in-memory inventory，下個 play 接手配置 ---
    - name: 註冊到 inventory（in-memory）
      ansible.builtin.add_host:
        name: "{{ item.instances[0].public_ip_address }}"
        groups: launched_web
        ansible_user: ubuntu
        ansible_ssh_private_key_file: ~/.ssh/my-keypair.pem
      loop: "{{ ec2_results.results }}"

    - name: 等 SSH 起來
      ansible.builtin.wait_for:
        host: "{{ item.instances[0].public_ip_address }}"
        port: 22
        delay: 5
        timeout: 120
      loop: "{{ ec2_results.results }}"


# --- 5) 第二個 play — 配置剛建好的 host ---
- name: 設定 web servers
  hosts: launched_web
  become: true
  tasks:
    - ansible.builtin.apt:
        name: nginx
        update_cache: yes
    - ansible.builtin.service:
        name: nginx
        state: started
        enabled: yes

20.4動態 inventory：cloud inventory plugin

AWS 跑了 50 台 EC2，怎麼讓 Ansible 知道？答案是 cloud inventory plugin（Ch16 自定 plugin 那章已介紹概念）。本節用 AWS 範例。

20.4.1aws_ec2 inventory 設定

yaml · inventory/aws_ec2.yml 
---
plugin: amazon.aws.aws_ec2

regions:
  - us-east-1
  - us-west-2
  - eu-west-1

# 過濾 — 只列出我關心的
filters:
  instance-state-name: running
  tag:ManagedBy: ansible

# 自動依 tag 分群
keyed_groups:
  - key: tags.Environment             # env_dev / env_staging / env_prod
    prefix: env
    separator: "_"
  - key: tags.Role                    # role_webserver / role_db
    prefix: role
  - key: placement.region             # aws_region_us_east_1
    prefix: aws_region

# 條件式群組
groups:
  production_critical: "tags.Environment == 'prod' and tags.Critical == 'true'"
  large_instances: "instance_type.startswith('m5') or instance_type.startswith('m6')"

# 設定 ansible_host 用 private IP
compose:
  ansible_host: private_ip_address
  ansible_user: "'ubuntu'"

# 用 Name tag 當 hostname（容易識別）
hostnames:
  - tag:Name
  - private-ip-address

# Cache — 避免每次跑都打 AWS API
cache: true
cache_plugin: ansible.builtin.jsonfile
cache_connection: /tmp/ansible_aws_cache
cache_timeout: 600

不少團隊面臨多雲現實——production 在 AWS、災備在 Azure、AI 訓練用 GCP。Ansible 因為跨雲 collection 都 in-tree，是統一管理的好工具。

20.7.1多雲設計模式

Figure 20.2 — 多雲抽象：playbook 一份、cloud-specific role 三份

20.7.2跨雲 dispatcher 範例

yaml · roles/provision_vm/tasks/main.yml

    file: "{{ cloud_provider }}.yml"      # aws.yml / azure.yml / gcp.yml

vm_size_map:
  small:  { aws: t3.small,  azure: Standard_B1s, gcp: e2-small }
  medium: { aws: t3.medium, azure: Standard_B2s, gcp: e2-medium }
  large:  { aws: t3.large,  azure: Standard_B4ms, gcp: e2-standard-4 }

20.7.3多雲設計建議

①

抽象 vs 客製化

不要過度抽象——強行讓 AWS / Azure / GCP 共用同個 role 通常痛苦。每雲一個 role、共用變數定義。

②

用 tags / labels 跨雲統一

所有資源都打 Environment / App / ManagedBy 標籤。inventory plugin 用同樣 keyed_groups 規則。

③

地區命名規則統一

內部命名 us-east / eu-west / asia-east，再 map 到各雲的 region（us-east-1 / eastus / us-east1）。

④

config management 階段共用

VM 建好後跑同一份 nginx role / app deploy role。不分 AWS / Azure / GCP——都是 Linux + SSH。

20.8Credential 管理進階

20.8.1三大原則

🔒

不寫死 credential

絕對不在 playbook、inventory、git repo 任何地方寫死 access key / password。

🎯

最小權限

給 Ansible 用的 IAM role / service principal 只給必要權限。Ansible 創建 EC2 不需要 Lambda 權限。

🔄

定期輪換

長期 access key 每 90 天輪換。最好用 OIDC / IAM role 短期 token 取代長期 key。

20.8.2CI 中的 credential — GitHub Actions OIDC

yaml · .github/workflows/deploy.yml 
---
jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write          # OIDC 必要
      contents: read
    steps:
      - uses: actions/checkout@v4

      # 用 OIDC 換取臨時 AWS credential — 沒有任何 secret 存在 GitHub
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-ansible
          aws-region: us-east-1

      - name: Run Ansible
        run: |
          pip install ansible-core boto3
          ansible-galaxy collection install amazon.aws
          ansible-playbook -i inventory/aws_ec2.yml site.yml

20.8.3secret 從 SSM / Secrets Manager 取

yaml · 不寫 vault 直接從雲端 secret 服務取 
# AWS SSM Parameter Store
- name: 取 DB password
  amazon.aws.aws_ssm_parameter_store:
    name: /myapp/prod/db/password
  register: db_pwd
  no_log: true

# 用 lookup 直接取（更精簡）
vars:
  db_password: "{{ lookup('amazon.aws.aws_ssm', '/myapp/prod/db/password') }}"

# Azure Key Vault
vars:
  db_password: "{{ lookup('azure.azcollection.azure_keyvault_secret',
                       'db-password',
                       vault_url='https://myvault.vault.azure.net') }}"

20.9業界最佳實踐

①

Tag / label 一切資源

Environment / Owner / App / ManagedBy / CostCenter / Project — 至少這 6 個。沒 tag 的資源在 cost report 是黑洞、cleanup 也找不到。

②

環境隔離用獨立帳號 / subscription

dev / staging / prod 用不同 AWS account / Azure subscription / GCP project。比靠 IAM 區隔強太多——權限錯配也炸不到 prod。

③

用 cloud inventory 而非靜態

動態 inventory 永遠是當前事實。靜態 inventory 在雲端只會 drift。每次跑都從 AWS API 拉。

④

cache inventory 結果

大型部署 inventory 查詢可能 30 秒以上。cache: true + cache_timeout: 600 把第二次跑壓到秒級。

⑤

CI 用 OIDC 不用長期 key

GitHub Actions / GitLab CI 都支援 OIDC 與雲端身分對接。徹底擺脫 secrets store 的 access key。

⑥

Cost 守門人 — budget alert

每個帳號設 budget alert（AWS Budgets / Azure Cost Management / GCP Billing）。Ansible 跑錯把 100 台 instance 起起來時你會感謝。

⑦

State drift 處理

Ansible stateless — 重跑會 reconverge。但純 Terraform-managed 資源被 Ansible 改可能造成 drift。約定哪些資源由誰管。

⑧

用 prefix 命名一致

所有資源 {{ app }}-{{ env }}-{{ purpose }}。例：myapp-prod-web-01、myapp-prod-db-master。看名字就知道用途。

20.10本章重點回顧

01

雲端自動化兩階段

Provision（建立資源、跑 localhost 對 API）+ Configure（設定既存 host、SSH 進去做事）。同一個 playbook 可串兩階段。

02

Ansible vs Terraform 分工

Terraform stateful 適合 provision；Ansible stateless 適合 configure。混合用——Terraform 建設施 + Ansible 配置。

03

三大雲 collection

amazon.aws（200+ 模組）、azure.azcollection（270+）、google.cloud（150+）。配 boto3 / azure SDK / google-auth Python lib。

04

Cloud inventory plugin

每雲一個（aws_ec2 / azure_rm / gcp_compute）。keyed_groups 用 tag 自動分群、compose 設 ansible_host、cache 加速。

05

Credential 三條路

環境變數（dev）→ ~/.aws/credentials profile（multi-account）→ IAM role / OIDC（CI / production，最安全）。

06

多雲設計

每雲獨立 role + 共用變數定義 + 統一 tag / 命名。不要強行讓三雲共用同個 role。

07

從 SSM / Key Vault 取 secret

不用 vault 也行——用 lookup 直接從 cloud secret service 拉。最佳結合：vault 存 vault-password、lookup 取 secret。

08

業界 8 條最佳實踐

tag 一切 / 環境用獨立帳號 / 動態 inventory / cache / OIDC / budget alert / state drift 約定 / 命名一致。

練習題

  1. 初學者：在 AWS free-tier 用 Ansible 啟一台 t3.micro EC2，給它打 Environment: dev tag。用 ansible-inventory 確認 aws_ec2 plugin 能看到它。
  2. 初學者：對上一題的 EC2 寫 playbook 安裝 nginx，用同一個 playbook 兩 play 結構（provision + configure）。
  3. 初學者：用 amazon.aws.s3_bucket 建一個加密、版本、阻擋 public 的 S3 bucket。用 amazon.aws.aws_s3 模組上傳檔案。
  4. 開發者：實作本章 20.3.2 的完整 EC2 stack（VPC + subnet + IGW + SG + 2 instances）。確認 instance 跑起來且 nginx 能透過 public IP 訪問。
  5. 開發者：寫 aws_ec2 inventory 設定，用 keyed_groups 依 Environment + Role + Region 三個維度分群。配 cache 跑兩次測時間差。
  6. 開發者：寫一個 cleanup playbook — 列出所有 ManagedBy: ansible 的資源，依 prompt 確認後依序刪除（EC2 → SG → subnet → VPC）。
  7. DevOps / SRE：用 Terraform 建一個 VPC + subnet + EC2，輸出 instance public IP。用 Ansible 接手做 OS 配置。寫一個 GitHub Actions 串 Terraform plan/apply → Ansible deploy。
  8. DevOps / SRE：實作多雲 dispatcher pattern — 寫一個 provision_vm role，依 cloud_provider 變數對 AWS / Azure / GCP 起 small VM。共用同一份 vars 但實際呼不同 collection。
  9. DevOps / SRE：把 production 帳號改用 OIDC + IAM role 從 GitHub Actions 跑 Ansible。撰寫 IAM trust policy 限制只有指定 repo + branch 能 assume。寫 ansible.cfg 與 GitHub workflow 完整跑通。

本章詞彙表

Provision vs Configure
雲端自動化兩階段 — provision 建立資源（VM / VPC / DB）、configure 設定既存資源（OS / app）。Ansible 都能做。
Infrastructure as Code (IaC)
用程式碼描述基礎設施。Terraform / CloudFormation / Pulumi 是 IaC 主流。Ansible 在 provision 部分也屬於 IaC。
Stateful vs Stateless
Terraform stateful — 有 state file 記錄資源狀態。Ansible stateless — 每次重跑只看當下狀態。各有優劣。
amazon.aws collection
Ansible 官方 AWS collection。提供 200+ 模組（ec2_instance / s3_bucket / rds_instance 等）與 aws_ec2 inventory plugin。
community.aws collection
amazon.aws 的補充 collection。較邊緣的 AWS service 模組放這。
azure.azcollection
Ansible 官方 Azure collection。270+ 模組覆蓋 Azure 主要資源。
google.cloud collection
Ansible 官方 GCP collection。150+ 模組。
boto3
AWS 官方 Python SDK。amazon.aws 模組底層依賴。pip install boto3。
aws_ec2 inventory plugin
amazon.aws 的動態 inventory plugin。從 AWS API 列 EC2 instance 並依 tag 自動分群。
azure_rm inventory plugin
Azure 的動態 inventory plugin。從 resource group 列 VM。
gcp_compute inventory plugin
GCP 的動態 inventory plugin。從 project / zone 列 instance。
keyed_groups (inventory)
動態 inventory 的功能 — 依 host 屬性自動建群組。tag.Environment → env_prod / env_staging。
compose (inventory)
動態 inventory 的功能 — 用 Jinja2 表達式設 host 變數。常設 ansible_host 為 private_ip_address。
IAM role
AWS 的身分容器。EC2 instance profile / GitHub OIDC 等不需長期 access key 的方式都用 IAM role。
OIDC (OpenID Connect)
身分驗證標準。GitHub Actions / GitLab CI 與 AWS / Azure / GCP 對接後，CI 不需存任何長期 secret 即可拿短期 token。
SSM Parameter Store / Secrets Manager
AWS 的 secret 管理服務。Ansible 用 aws_ssm lookup 直接取，不用存在 vault。
Azure Key Vault
Azure 的 secret 管理服務。Ansible 用 azure_keyvault_secret lookup 取。
add_host module
Ansible builtin 模組。把 host 動態加進當前執行的 inventory。常用於 provision 後的 host 配置 handoff。
wait_for module
Ansible builtin 模組。等 port / 檔案 / condition 達成。常用於等 EC2 SSH port 起來再跑 configure play。
Multi-cloud / Hybrid cloud
同時用多家雲端的策略。Ansible 跨雲 collection 都 in-tree，是統一管理工具的好選擇。
