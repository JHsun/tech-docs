第 19 章 — 網路自動化

前 18 章的範例都是 Linux server 自動化——遠端有 Python、有 shell、有 SSH server。但網路設備（Cisco 交換器、Juniper 路由器、Arista 葉節點）什麼都沒有：沒 Python、沒一般 shell、有的只是 vendor CLI（show running-config、configure terminal）或 NETCONF / REST API。Ansible 怎麼處理？答案是 Ch18 介紹的三大網路 connection plugin（network_cli / httpapi / netconf）配合各廠商 collection。本章帶你完整走過：網路自動化與 server 自動化的三大根本差異、三種連線方式的選擇與設定、Cisco IOS / Juniper Junos / Arista EOS 三大平台 collection、cli_command vs cli_config 的取捨、配置備份與 drift detection、跨廠商抽象的 resource modules、完整的「BGP 配置 + 配置備份 + 部署回滾」生產級 playbook。讀完這章你能用 Ansible 管理一個多廠商 (multi-vendor) 網路。

19.1網路自動化的三大根本差異

在動手寫 playbook 前，先理解網路設備跟 Linux server 的本質差異——這些差異決定了 inventory、connection、module 都要不同寫法。

19.1.1差異對照

面向Linux server網路設備
遠端 Python有無
一般 shell（bash / sh）有無 — 只有 CLI
檔案系統訪問完整受限 — 不能 copy 檔案執行
連線方式SSHSSH+CLI / REST API / NETCONF
典型廠商OS 大同小異（Debian / RHEL / Ubuntu）差異巨大（Cisco IOS 與 Juniper Junos 命令完全不同）
Module 在哪跑在 managed node在 control node（local execution）

19.1.2關鍵差異：module 跑在 control node

Figure 19.1 — Module 執行位置：server 在遠端、網路在 control node
ⓘ 為什麼這麼設計

網路設備沒 Python，Ansible 不能像對 Linux server 那樣把 module 檔案傳過去執行。改成module 在 control node 跑、透過 CLI/API 對遠端送命令。這就是「persistent connection」的概念——connection plugin 維持與設備的 SSH session，module 透過它送 show interfaces、configure terminal 等命令。

19.2三大網路 connection plugin

第 18 章已介紹過。本節聚焦三者的選擇邏輯。

19.2.1三種選擇

Connection協定適用場景
ansible.netcommon.network_cli SSH + CLI 最廣泛。Cisco IOS / IOS-XE / NX-OS、Juniper Junos（部分）、Arista EOS、VyOS 都支援。送 show ... / configure terminal 命令。
ansible.netcommon.httpapi REST API（HTTPS） Arista eAPI、Cisco NX-API、Fortinet、F5、Palo Alto。比 SSH+CLI 快、結構化資料（JSON）、支援併發。
ansible.netcommon.netconf NETCONF / XML（SSH port 830） Juniper Junos 首選、Cisco IOS-XR、IETF YANG model 設備。事務式配置、原子化變更。

19.2.3三種連線的 inventory 寫法

yaml · inventory/network.yml — 混合三種連線 
---
all:
  children:

    # Cisco IOS — network_cli
    cisco_switches:
      hosts:
        sw01:
          ansible_host: 10.1.1.1
      vars:
        ansible_connection: ansible.netcommon.network_cli
        ansible_network_os: cisco.ios.ios
        ansible_user: admin
        ansible_password: "{{ vault_cisco_password }}"
        ansible_become: true
        ansible_become_method: enable          # Cisco enable mode
        ansible_become_password: "{{ vault_enable_password }}"

    # Arista EOS — httpapi (eAPI 走 REST)
    arista_switches:
      hosts:
        leaf01:
          ansible_host: 10.2.1.1
      vars:
        ansible_connection: ansible.netcommon.httpapi
        ansible_network_os: arista.eos.eos
        ansible_user: admin
        ansible_password: "{{ vault_eos_password }}"
        ansible_httpapi_use_ssl: true
        ansible_httpapi_validate_certs: false     # lab 用

    # Juniper Junos — netconf
    juniper_routers:
      hosts:
        rtr01:
          ansible_host: 10.3.1.1
      vars:
        ansible_connection: ansible.netcommon.netconf
        ansible_network_os: junipernetworks.junos.junos
        ansible_user: admin
        ansible_password: "{{ vault_junos_password }}"
        ansible_port: 830                          # NETCONF 標準 port
⚠ ansible_network_os 必設

網路設備的 ansible_network_os 是 connection plugin 識別「我在跟哪種設備說話」的關鍵。沒設會 fail。值是 collection FQCN：cisco.ios.ios、arista.eos.eos、junipernetworks.junos.junos 等。

19.4查詢狀態 — facts 與 show 命令

19.4.1網路 facts

跟 server 的 ansible.builtin.setup 類似，每個網路平台 collection 都有 *_facts 模組收集設備資訊。

yaml · 各平台收 facts 
- name: 收集 Cisco IOS facts
  hosts: cisco_switches
  gather_facts: false
  tasks:
    - cisco.ios.ios_facts:
        gather_subset:
          - '!all'             # 排除預設大集合
          - hardware
          - interfaces
        gather_network_resources:
          - interfaces
          - l2_interfaces
          - vlans

    - debug:
        msg:
          - "Hostname: {{ ansible_net_hostname }}"
          - "Version: {{ ansible_net_version }}"
          - "Serial: {{ ansible_net_serialnum }}"
          - "Interfaces: {{ ansible_net_interfaces.keys() | list }}"

- name: Junos / Arista / NX-OS 對應
  tasks:
    # junipernetworks.junos.junos_facts
    # arista.eos.eos_facts
    # cisco.nxos.nxos_facts
    # 用法都類似

19.4.2送 show 命令 — cli_command

yaml · 跨廠商通用的 cli_command 
- name: 查 Cisco 接口狀態
  ansible.netcommon.cli_command:
    command: show ip interface brief
  register: brief

- debug:
    var: brief.stdout_lines

# 多命令一次跑（cli_command 不支援，用 ios_command）
- cisco.ios.ios_command:
    commands:
      - show version | include Software
      - show ip int brief
      - show vlan brief
  register: multi_out

19.4.3結構化輸出 — gather_facts 派生變數

yaml · 用 facts 結構化資料 
- name: 列出所有 up 的接口
  debug:
    msg: "{{ item.key }} -> {{ item.value.ipv4 | default('') }}"
  loop: "{{ ansible_net_interfaces | dict2items }}"
  when: item.value.operstatus == 'up'

19.5配置變更：三種模式

送配置變更的方式從低階到高階三種：

模式抽象層級跨廠商idempotent
cli_command / *_command 低 — 送 raw CLI 否 否 — 你自己處理
cli_config / *_config 中 — 送 config block 部分 部分 — 比對既有 running-config
Resource modules（ios_interfaces 等） 高 — 宣告期望狀態 是 — 跨廠商一致 schema 是

19.5.1模式 ①：cli_config（多行配置）

yaml · cli_config 跨廠商 NTP 設定 
- name: 設定 NTP（跨廠商通用）
  hosts: all_network
  gather_facts: false
  tasks:
    - ansible.netcommon.cli_config:
        config: |
          ntp server 10.0.0.1
          ntp server 10.0.0.2
          clock timezone UTC 0
      register: cfg_result

    - debug:
        msg: "Diff: {{ cfg_result.diff }}"
      when: cfg_result.changed

19.5.2模式 ②：平台專屬 *_config

yaml · cisco.ios.ios_config — 含進階控制 
- cisco.ios.ios_config:
    lines:
      - description {{ if_desc }}
      - ip address {{ if_ip }} {{ if_mask }}
      - no shutdown
    parents: "interface {{ if_name }}"     # 進入 interface 模式

    # 進階：配置塊比對與插入位置
    match: line                           # line / strict / exact / none
    replace: line                         # line / block

    # 比對檢查
    before:
      - "no spanning-tree portfast default"
    after:
      - "do write memory"                   # 配置完存 startup-config

    # 失敗就 rollback（IOS 有 transactional 支援的話）
    save_when: modified

19.5.3模式 ③：Resource modules（推薦）

Resource modules 用宣告式表達期望狀態。跨廠商共用同一 schema——同一份 vars 套到 IOS / NX-OS / EOS / Junos 都能跑。

yaml · resource module — 設 interface 
- name: 用 resource module 配置 interfaces
  cisco.ios.ios_interfaces:
    config:
      - name: GigabitEthernet0/1
        description: Uplink to core
        enabled: true
        mtu: 9000
      - name: GigabitEthernet0/2
        description: Server uplink
        enabled: true
    state: merged             # merged / replaced / overridden / deleted / gathered / rendered / parsed

# Arista EOS 同樣 schema：
- arista.eos.eos_interfaces:
    config:
      - name: Ethernet1
        description: Uplink to core
        enabled: true
    state: merged

19.5.4resource module 的六種 state

state行為
merged把指定設定合併到既有 config（預設）
replaced對列出的 resource 完全替換為指定值
overridden把所有 resource 改成指定值（沒列的會被刪）
deleted刪除指定的 resource 設定
gathered只讀目前狀態（不改）
rendered只產生對應 CLI 但不送（dry-run）
parsed把 raw CLI 輸出解析成 structured data

19.6實戰：BGP 配置

把上面整合，看一個多廠商 BGP 配置 playbook。

19.6.1變數定義

yaml · group_vars/all/bgp.yml 
---
bgp_as: 65001
bgp_router_id: "{{ ansible_host }}"
bgp_neighbors:
  - peer: 10.0.0.1
    remote_as: 65002
    description: "To core router"
  - peer: 10.0.0.2
    remote_as: 65003
    description: "To peer leaf"
bgp_networks:
  - prefix: 10.1.0.0
    masklen: 16

19.6.2Cisco IOS playbook

yaml · playbooks/bgp_cisco.yml 
---
- name: 配置 BGP on Cisco IOS
  hosts: cisco_switches
  gather_facts: false
  tasks:
    - name: 部署前備份 running-config
      cisco.ios.ios_config:
        backup: yes
        backup_options:
          filename: "{{ inventory_hostname }}-{{ ansible_date_time.iso8601 }}.cfg"
          dir_path: ./backups/
      tags: [backup]

    - name: 套用 BGP 設定
      cisco.ios.ios_bgp_global:
        config:
          as_number: "{{ bgp_as }}"
          bgp:
            router_id: "{{ bgp_router_id }}"
          neighbor:
            - address: "{{ item.peer }}"
              remote_as: "{{ item.remote_as }}"
              description: "{{ item.description }}"
        state: merged
      loop: "{{ bgp_neighbors }}"
      register: bgp_result

    - name: 驗證 BGP session 已建立
      cisco.ios.ios_command:
        commands: show ip bgp summary
      register: bgp_summary

    - name: 展示
      debug:
        var: bgp_summary.stdout_lines

19.7配置備份 / drift detection

網路自動化的核心應用之一：定期備份、比對配置變化。

19.7.1定期備份

yaml · playbooks/network_backup.yml 
---
- name: 備份所有網路設備
  hosts: all_network
  gather_facts: false
  tasks:
    # Cisco IOS
    - name: 備份 IOS
      cisco.ios.ios_config:
        backup: yes
        backup_options:
          filename: "{{ inventory_hostname }}.cfg"
          dir_path: "./backups/{{ ansible_date_time.date }}/"
      when: ansible_network_os == 'cisco.ios.ios'

    # Arista EOS
    - name: 備份 EOS
      arista.eos.eos_config:
        backup: yes
        backup_options:
          filename: "{{ inventory_hostname }}.cfg"
          dir_path: "./backups/{{ ansible_date_time.date }}/"
      when: ansible_network_os == 'arista.eos.eos'

    # Junos
    - name: 備份 Junos
      junipernetworks.junos.junos_config:
        backup: yes
        backup_options:
          filename: "{{ inventory_hostname }}.cfg"
          dir_path: "./backups/{{ ansible_date_time.date }}/"
      when: ansible_network_os == 'junipernetworks.junos.junos'

19.7.2把備份推到 Git

yaml · 備份 + commit + push 
# 備份完後在 control node 跑 git ops
- name: 推備份到 git
  hosts: localhost
  connection: local
  tasks:
    - ansible.builtin.command:
        cmd: "{{ item }}"
        chdir: ./backups
      loop:
        - git add .
        - git commit -m "Auto backup {{ ansible_date_time.iso8601 }}" --allow-empty
        - git push origin main
      changed_when: true      # 簡化處理

19.7.3Drift detection

yaml · 偵測配置漂移 
- name: 用 check mode 偵測 drift
  cisco.ios.ios_config:
    src: "./expected/{{ inventory_hostname }}.cfg"
  check_mode: yes           # 不真改、只回報 diff
  register: drift

- name: 有 drift 就告警
  debug:
    msg: "⚠ Config drift detected on {{ inventory_hostname }}: {{ drift.diff }}"
  when: drift.changed

# 進階：fail 整個 play 觸發 CI alert
- fail:
    msg: "Drift on {{ inventory_hostname }}"
  when: drift.changed and strict_drift_check | default(false)

19.8業界最佳實踐

①

vault 所有設備密碼

網路設備密碼 = 整個網路的鑰匙。所有 ansible_password / enable password 進 vault（Ch13）。CI 用 SSH key 或 vault password file。

②

變更前先備份

每個 *_config 模組都有 backup: yes。在 CI 流程中先備份 → 套變更 → 驗證 → 失敗 rollback。

③

盡量用 resource modules

跨廠商一致 schema、宣告式、idempotent、check_mode 友善。比 cli_config / 命令類型強太多。

④

分階段部署 — serial

大型網路用 serial: 25% 或 serial: 1 分批部署。失敗就停止，不要一次全部炸。

⑤

變更後驗證

不只 check task 結果——再下 show ip bgp summary / show interface 等驗證實際狀態符合期望。

⑥

persistent connection 加速

網路 connection plugin 自動維持 SSH session（ANSIBLE_PERSISTENT_COMMAND_TIMEOUT 控制）。同一 host 跨 task 不重連，效能差距 10×。

⑦

用 ansible-vault edit 手動審計

網路設備密碼絕不寫死在 .env 或 inventory plain。每次取出時 git log 看誰改的，責任明確。

⑧

雙人 review + dry run

網路變更影響面廣。CI 跑 --check --diff 給 reviewer 看 diff，確認無誤才 merge 套用。

19.9本章重點回顧

01

網路設備沒 Python

Module 跑在 control node、透過 connection plugin 對遠端送 CLI / API。與 server 自動化的本質差異。

02

三大 connection plugin

network_cli（SSH+CLI 最廣）、httpapi（REST API 快）、netconf（事務式 Junos 首選）。ansible_network_os 必設。

03

collection 生態

ansible.netcommon 提供基礎；cisco.ios / cisco.nxos / arista.eos / junipernetworks.junos / vyos.vyos 等是各廠商實作。

04

Facts 與 show 命令

*_facts 收結構化資訊；cli_command / *_command 送 raw CLI。

05

配置變更三模式

cli_command（raw）→ cli_config（block）→ resource modules（宣告式 + 跨廠商）。優先用最後者。

06

Resource module 七種 state

merged / replaced / overridden / deleted / gathered / rendered / parsed。覆蓋從套用到 dry-run / 解析的所有需求。

07

備份 / drift detection

backup: yes + git 集中存放 + check_mode 比對 = 完整的 config-as-code 流程。

08

業界 8 條最佳實踐

vault 密碼 / 變更前備份 / 用 resource modules / serial 分批 / 變更後驗證 / persistent connection / 手動審計 / 雙人 review + dry run。

練習題

  1. 初學者：用 GNS3 / EVE-NG 起一台 Cisco IOSv，裝 cisco.ios collection，寫 inventory.yml + playbook 跑 cisco.ios.ios_facts 確認能連上並看到 hostname / version。
  2. 初學者：對 Cisco IOSv 跑 cisco.ios.ios_command 送 show ip int brief，把 stdout_lines 用 debug 印出。
  3. 初學者：寫 playbook 用 cli_config 對 Cisco IOSv 設定 NTP server，跑兩次確認第二次 changed=False（idempotency）。
  4. 開發者：建多廠商 lab — Cisco IOSv + Arista cEOS（Docker）+ vMX。用同一個 inventory 三個 group + 三種 connection plugin。寫 playbook 對所有三廠商備份 running-config。
  5. 開發者：用 resource module（cisco.ios.ios_interfaces + arista.eos.eos_interfaces）寫一個跨 IOSv + Arista cEOS 的 interface 配置 playbook。共用同一份 vars。
  6. 開發者：對同一個 resource module 試四種 state：merged → replaced → overridden → deleted。觀察每種 state 對既有配置的影響。
  7. DevOps / SRE：把第 4 題備份 playbook 接 cron / GitHub Actions 排程，每天備份所有設備並 commit + push 到 git repo（用 SSH deploy key）。
  8. DevOps / SRE：實作 drift detection — 把 ./expected/ 目錄存標準配置，跑 --check 用 ios_config 比對，drift 觸發 Slack 通知（用 Ch15 的 callback plugin）。
  9. DevOps / SRE：寫一個生產級 BGP 部署 playbook：① 部署前備份；② 套設定（用 resource module）；③ 等 30 秒；④ 跑 show ip bgp summary 驗證 session up；⑤ session 沒 up 就 fail + 回滾。

本章詞彙表

Network automation
用程式化方式管理網路設備（交換器、路由器、防火牆）。Ansible 透過 connection plugin + collection 實現。
ansible.netcommon collection
Ansible 網路自動化基礎 collection。提供 network_cli / httpapi / netconf 三大 connection plugin 與 cli_command / cli_config / netconf_config 等通用模組。
network_cli connection
ansible.netcommon.network_cli。透過 SSH 連設備並送 CLI 命令。最廣泛支援。
httpapi connection
ansible.netcommon.httpapi。透過 HTTPS REST API 連設備。Arista eAPI / Cisco NX-API / 防火牆等支援 REST 的設備。
netconf connection
ansible.netcommon.netconf。透過 NETCONF 協定（XML / SSH 830）連設備。Juniper Junos 首選、IETF YANG 設備。
ansible_network_os
必設的 inventory 變數，告訴 connection plugin 在跟哪種設備說話。值是 collection FQCN 如 cisco.ios.ios。
Persistent connection
網路 connection plugin 的特性 — 維持與設備的 session，多個 task 重用同一連線。ANSIBLE_PERSISTENT_COMMAND_TIMEOUT 控制。
Platform collection
各廠商的 Ansible collection — cisco.ios / cisco.nxos / cisco.iosxr / arista.eos / junipernetworks.junos / vyos.vyos 等。
cli_command 模組
ansible.netcommon.cli_command。送單一 raw CLI 命令，回傳 stdout。最低階用法。
cli_config 模組
ansible.netcommon.cli_config。送多行 config block，含 idempotency 與 diff 支援。
*_command 模組
平台專屬的 command 模組（ios_command / eos_command / junos_command）。比 cli_command 多平台特定功能（多命令、wait_for 等）。
*_config 模組
平台專屬 config 模組（ios_config 等）。支援 backup / parents / save_when 等進階選項。
Resource modules
跨廠商共用 schema 的宣告式模組（ios_interfaces / eos_interfaces / junos_interfaces）。同份 vars 跨廠商可用。
state: merged / replaced / overridden
resource module 的三種變更模式。merged 加進去；replaced 完全替換指定 resource；overridden 替換所有 resource（沒列的會被刪）。
state: deleted / gathered / rendered / parsed
resource module 其他 state。deleted 刪除；gathered 只讀；rendered 產生 CLI 但不送（dry-run）；parsed 把 CLI 輸出解成 structured。
backup: yes 選項
*_config 模組的選項，套變更前先把 running-config 存到本地。網路自動化必備。
Config drift
實際設備配置與期望（git 中的）不一致的狀態。用 check_mode + diff 偵測。
enable mode
Cisco 設備的特權執行模式。Ansible 用 ansible_become_method: enable + ansible_become_password 進入。
NETCONF
IETF RFC 6241 標準的網路設備管理協定。XML over SSH（port 830）。事務式、原子化、支援 candidate config + commit。
YANG model
NETCONF 用的資料建模語言。定義網路配置的結構 schema。
