第 26 章 — 雲端進階模式

第 20 章教 Ansible 如何 provision 雲端資源；本章談大型雲端架構特有的進階模式。四個主題：① Mutable vs Immutable infrastructure——傳統 SSH 配置 vs 替換式 image-based 部署的根本差異；② Golden image with Packer——Ansible 不再連 SSH 配置 host，改成build image 提供給 ASG / 雲端啟動；③ Auto-Scaling Group 整合——instance refresh 機制 + Ansible 觸發；④ Multi-region 與 DR——主備區架構、failover 自動化、Route 53 切換。本章把 Ansible 的角色從「配置工具」拓展成「image builder + DR 編排器」——讀完這章你能設計一個跨 region、自動 scale、image-based 不可變、可在 5 分鐘內 failover 的 production 架構。

26.1Mutable vs Immutable infrastructure

傳統 Ansible 使用方式是 mutable — 你升級既有 host。雲端時代有了新選項：immutable — 你替換 host。差別比想像中大。

26.1.1對照

Figure 26.1 — Mutable 升級 host vs Immutable 替換 host

26.1.2差異對照

面向Mutable（傳統）Immutable（雲原生）
升級方式SSH 進去改build 新 image、launch 新 instance、replace 舊的
Configuration drift必然發生不存在 — 每台都從同 image 出生
Boot 時間VM 起來 + Ansible 配置 ~10 分鐘VM 起來 ~3 分鐘（image 預烘好）
RollbackAnsible 重跑舊版（需測試）切回舊 AMI（瞬間）
Ansible 的角色runtime 配置工具image build 工具 + 觸發部署
適合場景少數長期 host、stateful 服務、傳統 ITcloud-native、ASG、stateless 服務
ⓘ 業界共識

Stateless tier（web / app / worker）→ immutable。Stateful tier（DB / cache）→ mutable。混用是常態——你的 web tier 用 ASG + AMI、DB 用傳統 Ansible 配置。不要強迫所有東西都 immutable（DB 替換成本太高）。

26.2Golden image — Packer + Ansible

Immutable infrastructure 的核心是 golden image——pre-baked 的 OS image，含好所有依賴與應用。Packer + Ansible 是業界標準組合：Packer 啟動暫時 VM、Ansible 配置、Packer 拍 snapshot 變 AMI。

26.2.2Packer template — HCL2

hcl · packer/webapp.pkr.hcl 
packer {
  required_plugins {
    amazon = {
      version = ">= 1.3.0"
      source  = "github.com/hashicorp/amazon"
    }
    ansible = {
      version = ">= 1.1.0"
      source  = "github.com/hashicorp/ansible"
    }
  }
}

variable "app_version" {
  type    = string
  default = "latest"
}

source "amazon-ebs" "webapp" {
  ami_name      = "webapp-{{ var.app_version }}-{{timestamp}}"
  instance_type = "t3.medium"
  region        = "us-east-1"

  # 從 Ubuntu 24.04 LTS 開始
  source_ami_filter {
    filters = {
      name                = "ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"
      root-device-type    = "ebs"
      virtualization-type = "hvm"
    }
    most_recent = true
    owners      = ["099720109477"]   # Canonical
  }
  ssh_username = "ubuntu"

  tags = {
    Name        = "webapp"
    Version     = "{{ var.app_version }}"
    BuiltBy     = "packer"
    BuildDate   = "{{timestamp}}"
  }
}

build {
  sources = ["source.amazon-ebs.webapp"]

  # Provisioner ① — Ansible
  provisioner "ansible" {
    playbook_file   = "../ansible/playbooks/build_image.yml"
    extra_arguments = [
      "--extra-vars", "app_version=${var.app_version}",
      "--extra-vars", "env=production",
    ]
  }

  # Provisioner ② — Testinfra 驗證
  provisioner "shell" {
    inline = ["py.test --connection=ansible /tmp/tests/"]
  }
}

26.2.3Ansible playbook — 為 image 建構而設計

yaml · ansible/playbooks/build_image.yml 
---
- name: Build webapp golden image
  hosts: all            # Packer 會把暫時 instance 加進來
  become: true
  tasks:
    # OS 級設定
    - ansible.builtin.apt:
        name:
          - nodejs
          - nginx
          - awscli
          - jq
        update_cache: yes

    # 應用程式 — 把 release artifact 烘進 image
    - ansible.builtin.get_url:
        url: "https://artifacts.example.com/webapp-{{ app_version }}.tar.gz"
        dest: /tmp/webapp.tar.gz

    - ansible.builtin.unarchive:
        src: /tmp/webapp.tar.gz
        dest: /opt/webapp/
        remote_src: yes

    # systemd unit 但不啟動 — 由 cloud-init 在運行時啟動
    - ansible.builtin.template:
        src: webapp.service.j2
        dest: /etc/systemd/system/webapp.service

    - ansible.builtin.systemd:
        name: webapp
        enabled: yes
        state: stopped     # 不要在 build 期啟動

    # 清理 — 確保 image 乾淨
    - ansible.builtin.shell: |
        apt-get clean
        rm -rf /var/log/* /tmp/*
        cloud-init clean
        history -c
      changed_when: false

26.2.4Cloud-init 處理 runtime config

⚠ 哪些東西 build-time、哪些 runtime

Build-time（烘進 image）：OS 套件、應用 binary、systemd unit、不變的設定檔。
Runtime（cloud-init 或 user data）：環境變數（DB host / Redis URL）、secret（從 SSM 拉）、實例特定設定（hostname / instance role）。不要把 runtime 東西烘進 image——同一 image 應該能跑 dev / staging / prod 三環境。

yaml · cloud-init.yml.j2 — 啟動時跑 
#cloud-config
write_files:
  - path: /etc/webapp/app.env
    permissions: '0600'
    content: |
      NODE_ENV={{ environment }}
      DB_HOST={{ db_endpoint }}
      REDIS_URL=redis://{{ redis_endpoint }}

runcmd:
  # 從 SSM 拉 secret
  - aws ssm get-parameter --name /webapp/{{ environment }}/db-password
      --with-decryption --query Parameter.Value --output text
      >> /etc/webapp/app.env
  - chmod 600 /etc/webapp/app.env

  # 啟動服務
  - systemctl start webapp
  - systemctl start nginx

26.3Auto-Scaling Group 整合

Image 烘好後怎麼送出去？AWS ASG 的 instance refresh 機制可以自動逐批替換 instance。Ansible 觸發。

26.3.1flow

Figure 26.3 — ASG instance refresh 流程

26.3.2Ansible 觸發 instance refresh

yaml · 對 ASG 發起 instance refresh 
---
- name: 部署新 AMI 到 ASG
  hosts: localhost
  connection: local
  vars:
    ami_id: "{{ new_ami_id }}"           # Packer 輸出的 AMI id
    asg_name: webapp-prod-asg
    lt_name: webapp-prod-lt
  tasks:

    # 1) 更新 launch template 指向新 AMI
    - name: 建新版本 launch template
      amazon.aws.ec2_launch_template:
        name: "{{ lt_name }}"
        image_id: "{{ ami_id }}"
        instance_type: t3.medium
        user_data: "{{ lookup('template', 'cloud-init.yml.j2') | b64encode }}"
        tag_specifications:
          - resource_type: instance
            tags:
              Name: webapp-prod
              AMIVersion: "{{ ami_id }}"

    # 2) 觸發 instance refresh — community.aws 模組
    - name: 啟動 ASG instance refresh
      community.aws.autoscaling_instance_refresh:
        name: "{{ asg_name }}"
        state: started
        preferences:
          min_healthy_percentage: 75          # 至少 75% 健康才繼續換
          instance_warmup: 300                # 給 5 分鐘 warm up
      register: refresh

    # 3) 等 refresh 完成（poll）
    - name: 等 refresh 完成
      community.aws.autoscaling_instance_refresh_info:
        name: "{{ asg_name }}"
        ids:
          - "{{ refresh.instance_refresh_id }}"
      register: refresh_status
      until: refresh_status.instance_refreshes[0].status in ['Successful', 'Failed', 'Cancelled']
      retries: 60          # 60 × 30s = 30 分鐘最長
      delay: 30

    # 4) 驗證
    - name: 確認成功
      ansible.builtin.fail:
        msg: "Instance refresh failed: {{ refresh_status }}"
      when: refresh_status.instance_refreshes[0].status != 'Successful'

26.4Multi-region 與 disaster recovery

單 region 部署有 region-wide outage 風險。生產級服務需要 multi-region active/standby（簡單）或 active/active（複雜）架構。

26.4.1active/standby 架構

Figure 26.4 — Active/standby multi-region 架構

26.4.2DR tier 定義

TierRTORPO架構成本
Tier 1 — 任務關鍵 < 5 分鐘 ≤ 1 分鐘 active/active 多 region 2x（雙跑）
Tier 2 — 業務重要 < 1 小時 < 15 分鐘 active/standby 預啟動 ~1.3x
Tier 3 — 一般業務 < 4 小時 < 1 小時 pilot light（最小 standby） ~1.1x
Tier 4 — 開發測試 < 24 小時 < 24 小時 backup + restore from scratch 1x

26.4.3跨 region 部署 playbook

yaml · playbooks/deploy_multi_region.yml 
---
- name: 同時部署到 primary 與 DR region
  hosts: localhost
  connection: local
  vars:
    regions:
      - { name: us-east-1, role: primary, asg: webapp-use1-asg }
      - { name: us-west-2, role: dr,      asg: webapp-usw2-asg }
    app_version: "v1.2.3"
  tasks:

    # Build 一次 image，跨 region 複製
    - name: build AMI in primary region
      ansible.builtin.command:
        cmd: "packer build -var=app_version={{ app_version }} packer/webapp.pkr.hcl"
      register: packer_out

    - name: 複製 AMI 到 DR region
      amazon.aws.ec2_ami_copy:
        source_image_id: "{{ primary_ami_id }}"
        source_region: us-east-1
        region: us-west-2
        name: "webapp-{{ app_version }}-usw2"
        wait: true
      register: dr_ami

    # 對兩個 region 各自更新 ASG
    - name: 更新所有 region 的 ASG
      community.aws.autoscaling_instance_refresh:
        name: "{{ item.asg }}"
        region: "{{ item.name }}"
        state: started
      loop: "{{ regions }}"
      register: refreshes

26.4.4Failover playbook — 切到 DR

yaml · playbooks/failover_to_dr.yml 
---
- name: DR Failover — primary region 掛了
  hosts: localhost
  connection: local
  vars_prompt:
    - name: confirm
      prompt: "確認要 failover 到 us-west-2？此操作不可逆 (yes)"
      private: false
  tasks:
    - ansible.builtin.fail:
        msg: "取消 failover"
      when: confirm != 'yes'

    # 1) 把 RDS replica promote 為 primary
    - name: promote DR RDS replica
      amazon.aws.rds_instance:
        id: webapp-dr-replica
        region: us-west-2
        read_replica: false          # promote
        wait: true

    # 2) Scale up DR ASG（如果是 pilot light 模式）
    - name: scale up DR ASG to production size
      amazon.aws.autoscaling_group:
        name: webapp-usw2-asg
        region: us-west-2
        desired_capacity: 10
        min_size: 5
        max_size: 20

    # 3) 等 instance 健康
    - name: 等 DR instance ready
      ansible.builtin.uri:
        url: "https://dr-alb.example.com/health"
        status_code: 200
      retries: 60
      delay: 10

    # 4) Route 53 切流量到 DR
    - name: DNS failover
      amazon.aws.route53:
        zone: example.com
        record: api.example.com
        type: A
        alias: true
        alias_hosted_zone_id: "{{ dr_alb_zone_id }}"
        value: "{{ dr_alb_dns }}"
        state: present
        overwrite: true

    # 5) 通知
    - name: 通知 incident channel
      community.general.slack:
        token: "{{ vault_slack_token }}"
        msg: "🚨 已 failover 至 us-west-2 DR region — Route 53 已切換"
        channel: "#incidents"

26.5Terraform + Ansible 進階整合

第 20 章談過分工原則。本節談實作模式。

26.5.1整合模式對照

模式機制適合
① Terraform local-exec Terraform 跑 Ansible 作為 provisioner 小專案、緊耦合、不推薦
② 兩階段 pipeline CI: Terraform → 輸出到 Ansible inventory → Ansible 主流做法、清楚分工
③ Dynamic inventory Ansible aws_ec2 plugin 直接從 AWS 拉 Terraform 與 Ansible 完全解耦（推薦）

26.5.2模式 ② — 兩階段 CI

yaml · .github/workflows/full_deploy.yml 
---
jobs:
  # --- 階段 1: Terraform provision ---
  terraform:
    runs-on: ubuntu-latest
    outputs:
      db_endpoint: ${{ steps.tf.outputs.db_endpoint }}
      redis_endpoint: ${{ steps.tf.outputs.redis_endpoint }}
    steps:
      - uses: actions/checkout@v4

      - name: Terraform apply
        id: tf
        run: |
          terraform init
          terraform apply -auto-approve
          echo "db_endpoint=$(terraform output -raw db_endpoint)" >> $GITHUB_OUTPUT
          echo "redis_endpoint=$(terraform output -raw redis_endpoint)" >> $GITHUB_OUTPUT

  # --- 階段 2: Ansible 配置 ---
  ansible:
    runs-on: ubuntu-latest
    needs: terraform            # 等 Terraform 完成
    steps:
      - uses: actions/checkout@v4

      - name: Ansible deploy
        env:
          DB_ENDPOINT: ${{ needs.terraform.outputs.db_endpoint }}
          REDIS_ENDPOINT: ${{ needs.terraform.outputs.redis_endpoint }}
        run: |
          # 用 aws_ec2 inventory plugin 動態拉 host
          ansible-playbook -i inventory/aws_ec2.yml playbooks/configure.yml \
            -e "db_endpoint=$DB_ENDPOINT" \
            -e "redis_endpoint=$REDIS_ENDPOINT"

26.6業界最佳實踐

①

Stateless tier 用 immutable

Web / app / worker 用 AMI + ASG。stateful tier（DB / cache）保持 mutable。混用最常見。

②

Build-time vs runtime 分清楚

OS 套件 / 應用 binary / 不變設定 → 烘進 image。環境變數 / secret / 實例特定設定 → cloud-init。

③

image tag 含版本與時間

webapp-v1.2.3-20260508。版本看部署、時間看是否需重新 build（CVE 修補）。

④

ASG instance_warmup 設好

應用 startup 需要時間。min_healthy_percentage: 75 + instance_warmup: 300 是常見起點。

⑤

定義 DR tier

不同服務 RTO/RPO 不同。Tier 1 任務關鍵 active/active；Tier 4 開發測試 backup-restore 即可。

⑥

定期 DR drill

Failover playbook 寫了不練 = 沒有。每季模擬切到 DR、量測 RTO 是否達標。

⑦

Terraform + Ansible 解耦

用 dynamic inventory 而非 local-exec。Terraform 跑完輸出，Ansible 自己從 AWS API 拉 host。

⑧

Image 過期清理

每次 build 一個 AMI，幾個月就累積上百個。寫 cleanup playbook 保留最近 N 個、其餘刪除。

26.7本章重點回顧

01

Mutable vs Immutable

傳統 SSH 升級 vs image-based 替換。Stateless 用 immutable、Stateful 用 mutable，混用最常見。

02

Packer + Ansible 黃金組合

Packer 啟暫時 VM、Ansible 配置、Packer 拍 snapshot 變 AMI。Ansible 換角色為 image builder。

03

Build-time vs runtime

套件 / binary / 不變設定 → image；環境 / secret / 實例特定 → cloud-init。同 image 跑多環境。

04

ASG instance refresh

更新 launch template AMI → 觸發 instance refresh → 等完成 → 驗證。Ansible 用 community.aws 模組。

05

Multi-region 架構

Active/standby 用 Route 53 health-checked DNS + RDS cross-region replica + ASG 兩 region。

06

DR tier 分類

Tier 1（< 5 分鐘 RTO，active/active）→ Tier 4（< 24 小時，backup-restore）。每服務分配適合 tier。

07

Failover playbook 五步驟

Confirm → promote DB replica → scale up ASG → wait healthy → Route 53 切換。配 Slack 通知。

08

Terraform + Ansible 解耦

不要用 Terraform local-exec。用兩階段 CI 或 dynamic inventory。Terraform 管基礎設施、Ansible 管配置。

練習題

  1. 初學者：寫一頁文字描述你的某個服務目前是 mutable 還是 immutable。如果改成另一種，trade-off 是什麼？
  2. 初學者：在 AWS free-tier 用 Packer 啟動一個 t3.micro Ubuntu instance、用 Ansible 裝 nginx、build 成 AMI。看 EC2 console 確認新 AMI 出現。
  3. 初學者：對上題 AMI 啟動一個 EC2 instance，確認 nginx 已預裝並 enabled。用 user-data 注入「歡迎訊息」到 index.html。
  4. 開發者：實作 26.2 的完整 Packer + Ansible pipeline。variable 接 app_version、build 完輸出 AMI id。
  5. 開發者：建一個 ASG（min 2 / max 5 / desired 3）用上題 AMI。改 Ansible role + 重新 build → 觸發 instance refresh，觀察 instance 逐批替換。
  6. 開發者：寫 cleanup playbook — 列出 webapp- 開頭的 AMI、保留最近 5 個、刪除其餘（含 EBS snapshot）。
  7. DevOps / SRE：對你的某個 production 服務分配 DR tier。寫 1 頁文件說明 RTO/RPO/架構/成本。manager 認得這個 tier 嗎？
  8. DevOps / SRE：實作 active/standby 架構（即使是 lab 規模）— 兩 region 的 ASG + RDS replica + Route 53 health check + failover playbook。模擬 primary 掛掉、確認 5 分鐘內切到 DR。
  9. DevOps / SRE：把你目前 Terraform + Ansible 整合方式從 local-exec 改成 dynamic inventory（如果適用）。寫 GitHub Actions 兩階段 workflow（Terraform → Ansible）。

本章詞彙表

Mutable infrastructure
傳統 host 管理模式 — 同一台 host 持續被升級配置。Ansible 用 SSH 進去改是典型 mutable。
Immutable infrastructure
雲原生模式 — host 啟動後不再修改，要升版就替換成新 host。從 image 出生、消滅後再建。
Configuration drift
實際 host 狀態與期望不一致。Mutable 必然發生（手動 hotfix / 不一致升級）；Immutable 不會（每台從同 image 出生）。
Golden image
pre-baked OS image，含 OS / 套件 / 應用 / 配置。從這 image 啟動的 instance 可立即運作（無需 SSH 配置）。
Packer
HashiCorp 的 image builder。啟動暫時 VM、跑 provisioner（如 Ansible）、拍 snapshot 變 AMI。multi-cloud 支援。
Packer provisioner
Packer 用來在暫時 VM 內配置的工具。最常見 ansible / shell / file。Ansible provisioner 直接跑 playbook。
HCL2
HashiCorp Configuration Language。Packer 與 Terraform 用同一種 DSL。
Build-time vs Runtime
image 的兩個生命階段。Build-time 是用 Packer 配置時；Runtime 是 instance 啟動後。靜態東西進 build-time、動態東西進 runtime。
cloud-init
Linux 啟動時跑的初始化系統。Read user-data，執行 runtime 配置。雲端 VM 啟動標配。
user-data
啟動 instance 時注入的 cloud-init 設定。在 launch template 設定，每 instance 啟動跑一次。
Auto-Scaling Group (ASG)
AWS 的 instance group 自動擴縮。配 launch template 指定 AMI / instance type / user-data 等。
Launch template
ASG 啟動 instance 用的範本。指定 AMI ID、instance type、user-data、tags。新版 launch template = 觸發 instance refresh 機制的關鍵。
Instance refresh
ASG 的逐批替換機制。把舊 instance 換成新 launch template 對應的新 instance。min_healthy_percentage 控制速度。
min_healthy_percentage
instance refresh 的關鍵參數。期間至少多少 % instance 必須健康才繼續換。75% 是常見值。
instance_warmup
新 instance 起來後，等多少秒才視為「已健康」。給應用 startup 時間。
Multi-region deployment
把同一服務部署到多個雲端 region。三種策略：active/active（雙跑）、active/standby（主備）、pilot light（最小 standby）。
RTO (Recovery Time Objective)
災難後恢復服務的最大可接受時間。Tier 1 通常 < 5 分鐘，Tier 4 可能 24 小時。
RPO (Recovery Point Objective)
災難後可接受的資料遺失量。Tier 1 通常 < 1 分鐘，Tier 4 可能 24 小時。
Pilot light
DR 模式 — DR region 維持最小規模（例如 1 instance），需要時 scale up 到 production 規模。比 active/standby 便宜，比 cold backup 快。
Active/standby
DR 架構 — DR region 預啟動且 ready（不接流量）。failover 只需 DNS 切換 + DB promote。RTO 分鐘級。
Active/active
DR 架構 — 兩個 region 同時服務流量。最高可用、最高成本。需處理 cross-region 一致性。
Route 53 health check
AWS DNS 服務的健康檢查。primary 端點掛了自動切到 secondary。常用於 multi-region failover。
Cross-region replication
把 RDS / S3 / DynamoDB 資料跨 region 同步。DR 必備。多數 AWS 服務原生支援。
DR drill
定期演練 failover 是否能達 RTO。playbook 寫了不演練 = 緊急時刻失敗。建議每季一次。
Terraform local-exec
Terraform 的 provisioner 機制 — 跑本地命令（含 ansible-playbook）。緊耦合、難 debug，業界不推薦。
