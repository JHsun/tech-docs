第 11 章 — Collections 生態

第 1 章提過 ansible-core 與 community package 的拆分。本章揭曉這背後的核心機制——Collection。Ansible 2.10 起，所有非核心模組／plugin／role／playbook 都搬進 collection 中，由獨立的版本週期維護。今天當你寫 community.general.timezone 而非 timezone，就是在用 collection。本章帶你理解：什麼是 collection、FQCN 怎麼讀、ansible-galaxy 安裝管理、五個你 80% 時間會用到的核心 collection、requirements.yml 業界規範、私有 Galaxy server 概念、以及怎麼自己做一個 organization-internal collection。

本章覆蓋官方文件對應：Collections Guide · Galaxy · Building Collections
初學者必讀（11.1–11.4） 開發者必讀（全章） DevOps / SRE 必讀（全章特別 11.6 requirements 與 11.8 私有 collection）

11.1什麼是 Collection？

2020 年之前，Ansible 是一個單體：所有模組（裝套件、雲端、網路設備、資料庫⋯⋯）都跟 ansible-core 一起維護、一起發版。問題：① 主庫越來越大，難以維護；② 任何模組更新都要等下個 Ansible release。

2020 年的 Ansible 2.10 重大重構：把模組拆成 ansible-core（最小核心，僅 ~70 個模組）與數百個獨立的 collection（如 community.general、amazon.aws、cisco.ios）。每個 collection 有自己的 git repo、版本、release cycle。

11.1.1Collection 內含什麼？

Figure 11.1 — Collection 是模組／plugin／role／playbook 的打包單位

11.1.2Collection vs Role 對照

面向RoleCollection
主要內容tasks / templates / handlersmodules / plugins / roles / playbooks
能定義新模組否是（plugins/modules/）
能定義 filter / lookup plugin部分（plugins 目錄但較不規範）是（標準位置）
能包含多個 role否是（roles/ 內可多個）
命名空間無（單一名稱）namespace.collection
用 FQCN 引用否是
主要分發管道Ansible GalaxyAnsible Galaxy / Automation Hub
ⓘ 簡單記法

Role 是「組合既有模組來做某件事」（如部署 nginx）。Collection 是「提供新模組的單位」（如新增管理 ZeroTier 網路的 ZeroTier 模組）。一個 collection 可以內含多個 role，但一個 role 不能內含 collection。

11.2FQCN — Fully Qualified Collection Name

第 6 章已多次出現 FQCN。本節從 collection 角度理解它。

11.2.1FQCN 結構

yaml · FQCN 三段式 
# namespace . collection . plugin_or_role_name
#    ↓           ↓                ↓
ansible.builtin.copy
# namespace=ansible（廠商）, collection=builtin（核心）, plugin=copy（模組）

community.general.timezone
# namespace=community（社群）, collection=general（通用）, plugin=timezone

amazon.aws.ec2_instance
# namespace=amazon, collection=aws, plugin=ec2_instance

cisco.ios.ios_config
# namespace=cisco, collection=ios, plugin=ios_config

11.2.2為什麼用 FQCN 是 2026 年硬規範

①

避免命名衝突

ansible.builtin.copy 與 community.general.copy 可以同時存在不衝突。短名稱 copy 一旦兩個 collection 都定義就出問題。

②

明確的版本來源

看到 amazon.aws.ec2_instance 立刻知道這是 amazon.aws collection 提供。debug 時可直接查該 collection 文件。

③

linter 與 IDE 完整支援

ansible-lint、VS Code Ansible 擴充對 FQCN 有完整支援；短名稱會發 deprecation warning。

④

對應 Collections 生態

Ansible 已經完全 collection 化，FQCN 是設計初衷。短名稱是「歷史相容」，未來會逐漸淘汰。

11.2.3collections: keyword（過渡性，不推薦）

yaml · 不推薦：用 collections keyword 省略前綴 
# 過渡時期的捷徑語法（業界已不推薦）
- hosts: all
  collections:                       # 設定搜尋路徑
    - community.general
    - amazon.aws

  tasks:
    - timezone:                       # Ansible 在上面 collection 裡找
        name: UTC
    - ec2_instance:
        name: my-vm

# 為什麼不推薦：
# 1. role 不會繼承 play 的 collections，造成不一致
# 2. lookup / filter 等仍要寫 FQCN — 半套不徹底
# 3. 短名稱在 review 時讀者不知道來自哪
# 4. 官方明確建議用 FQCN

11.3核心 Collections — 80% 時間用到的

Ansible community package 預裝了上百個 collection，但實務上你 80% 時間會用到的就是這 5–8 個。

Collection用途典型模組
ansible.builtin 核心模組（內建在 ansible-core） copy, file, template, service, package, apt, dnf, user, command, shell, debug, set_fact, ...
ansible.posix POSIX 系統工具 authorized_key, sysctl, mount, firewalld, selinux, synchronize
community.general 社群通用大雜燴（500+ 模組） timezone, ufw, htpasswd, hashicorp.vault, github.repository, ldap_*, snap, ...
community.crypto 加密 / TLS / 憑證 openssl_certificate, x509_certificate, openssl_privatekey, acme_certificate
community.docker Docker / OCI 容器 docker_container, docker_image, docker_compose_v2, docker_swarm
community.postgresql PostgreSQL 管理 postgresql_db, postgresql_user, postgresql_query, postgresql_privs
amazon.aws AWS（EC2 / S3 / IAM 等） ec2_instance, s3_object, iam_role, rds_instance, route53, vpc_*
kubernetes.core Kubernetes k8s, helm, k8s_info, k8s_scale
ansible.netcommon 網路設備通用 cli_command, network_cli, telnet, restconf_get
cisco.ios / arista.eos / junipernetworks.junos 網路設備廠商特定 各家 *_config / *_l3_interfaces / *_vlans
ⓘ 用 community package 還是手動裝？

第 3 章學的 pipx install --include-deps ansible 安裝的是 community package，預裝上述大部分 collection。用這個就好。如果用 pipx install ansible-core（最小核心），則只有 ansible.builtin，其他都要手動 ansible-galaxy collection install。

11.4.2安裝 collection

bash · 安裝 collection 各種方式 
# 從 Ansible Galaxy（預設 server）安裝最新版
$ ansible-galaxy collection install community.general

# 指定特定版本
$ ansible-galaxy collection install community.general:10.0.0

# 版本範圍
$ ansible-galaxy collection install 'community.general:>=9.0.0,<11.0.0'

# 一次裝多個
$ ansible-galaxy collection install community.docker community.crypto kubernetes.core

# 裝到專案本地（推薦 — 對 CI/CD 友善）
$ ansible-galaxy collection install community.general -p ./collections

# 強制重裝
$ ansible-galaxy collection install community.general --force

# 升級到最新
$ ansible-galaxy collection install community.general --upgrade

# 從本地 tarball 安裝（離線環境）
$ ansible-galaxy collection install community-general-10.0.0.tar.gz

# 從 git 直接安裝
$ ansible-galaxy collection install git+https://github.com/example/coll.git,main

ⓘ 推薦：專案本地安裝

大型專案或 CI/CD 場景，把 collection 裝到 ./collections/ 而非 ~/.ansible/collections/。優點：專案隔離（不同專案可用不同版本）、git ignore 後可重現安裝、CI 可 cache。

11.5collection 的版本管理

Collection 版本是 SemVer（semantic versioning），格式 MAJOR.MINOR.PATCH。理解 collection 版本對 production 部署至關重要。

11.5.1SemVer 規則

版本變化意義升級風險
10.0.0 → 10.0.1PATCH — bug fix低 通常安全
10.0.0 → 10.1.0MINOR — 新功能（向後相容）中 通常安全但要看 changelog
10.0.0 → 11.0.0MAJOR — 破壞性變更高 必須 看 changelog 與測試

11.5.2版本範圍語法

yaml · 版本範圍寫法 
# requirements.yml 中的版本指定
collections:
  # 鎖定確切版本（最嚴格，最可重現）
  - name: community.general
    version: "10.0.0"

  # 鎖定主版本（接受 MINOR + PATCH 升級）
  - name: community.docker
    version: ">=4.4.0,<5.0.0"

  # 不指定 — 永遠裝最新（不建議生產用）
  - name: community.crypto

  # 只接受 PATCH 升級（最保守）
  - name: amazon.aws
    version: ">=9.0.0,<9.1.0"
⚠ 生產環境必 pin 版本

不 pin 版本意味著「下次 CI 跑可能裝到不同 collection 版本」——當行為改變時你不知道是 playbook 改的還是 collection 升級造成的。業界規範：production 用確切版本（"X.Y.Z"），dev 可用範圍。

11.6requirements.yml 業界規範

第 10 章已介紹 requirements.yml。本節聚焦 collection 部分的最佳實踐。

11.6.1完整範例

yaml · requirements.yml — 生產級 
---
# 角色依賴（從 Ansible Galaxy / git）
roles:
  - name: geerlingguy.docker
    version: "7.4.0"

  - src: git@github.com:my-org/internal-role.git
    name: internal-role
    version: v1.5.0

# Collection 依賴
collections:
  # 標準 community collections — pin minor 版本
  - name: community.general
    version: "10.0.0"

  - name: community.crypto
    version: "2.22.0"

  - name: community.docker
    version: "4.4.0"

  - name: community.postgresql
    version: "3.11.0"

  - name: amazon.aws
    version: "9.0.0"

  - name: kubernetes.core
    version: "5.0.0"

  # 從私有 Galaxy server 拉取
  - name: myorg.internal_tools
    source: https://galaxy.internal.company.com
    version: "2.0.1"

  # 從 git 直接拉
  - name: my_namespace.my_collection
    source: git@github.com:my-org/my-collection.git
    type: git
    version: main

11.6.2一鍵安裝

bash · 安裝 requirements.yml 
# 同時安裝 roles + collections（推薦）
$ ansible-galaxy install -r requirements.yml
$ ansible-galaxy collection install -r requirements.yml

# 一行串接
$ ansible-galaxy install -r requirements.yml && \
  ansible-galaxy collection install -r requirements.yml

# 安裝到專案本地路徑
$ ansible-galaxy collection install -r requirements.yml -p ./collections

# 升級已安裝的
$ ansible-galaxy collection install -r requirements.yml --upgrade

11.6.3CI/CD 整合範例

yaml · GitHub Actions 範例片段 
# .github/workflows/ansible.yml 片段
- name: Cache Ansible collections
  uses: actions/cache@v4
  with:
    path: ./collections
    key: ansible-collections-${{ hashFiles('requirements.yml') }}

- name: Install collections
  run: |
    ansible-galaxy collection install -r requirements.yml -p ./collections

- name: Run playbook
  env:
    ANSIBLE_COLLECTIONS_PATH: ./collections
  run: ansible-playbook site.yml

11.7Galaxy Server 概念

Ansible Galaxy（galaxy.ansible.com）是預設的 collection / role 公開分發平台。但企業環境常需要私有 server。

11.7.1三種 Galaxy server

Server類型典型用途
Ansible Galaxy 公開（galaxy.ansible.com） 預設來源、開源 collection、社群分享
Red Hat Automation Hub 商業（cloud.redhat.com） Red Hat 認證 collection、企業支援
私有 Galaxy（如 Pulp / Galaxy NG） 自建 內部 collection 分發、air-gapped 環境

11.7.2多 server 設定

ini · ansible.cfg — 配置多個 server 
[galaxy]
server_list = private_hub, automation_hub, galaxy

[galaxy_server.private_hub]
url = https://galaxy.internal.company.com/api/galaxy/content/published/
token = {{ env "PRIVATE_HUB_TOKEN" }}

[galaxy_server.automation_hub]
url = https://cloud.redhat.com/api/automation-hub/content/published/
auth_url = https://sso.redhat.com/auth/realms/redhat-external/protocol/openid-connect/token
token = {{ env "AH_TOKEN" }}

[galaxy_server.galaxy]
url = https://galaxy.ansible.com/

# 安裝時 Ansible 按 server_list 順序找 collection
# 第一個找到就用，不繼續搜其他 server

11.8建立自家 Collection

當組織內部有 5+ 個重複用到的 role / 自定模組，就值得包成 internal collection。

11.8.1Collection 標準結構

text · myorg.internal_tools collection 結構 
myorg-internal_tools/
├── galaxy.yml                # 必要 — collection metadata
├── README.md
├── meta/
│   └── runtime.yml           # 模組命名空間遷移、Python 需求
│
├── plugins/                  # 自定 plugin（核心價值所在）
│   ├── modules/              # 自定模組（Python）
│   │   └── my_module.py
│   ├── filter/               # Jinja2 filter
│   │   └── my_filters.py
│   ├── lookup/               # lookup plugin
│   ├── inventory/            # 動態 inventory plugin
│   └── module_utils/         # 模組共用 Python 程式
│
├── roles/                    # 內含 role（一個 collection 可多個 role）
│   ├── deploy/
│   │   └── tasks/main.yml
│   └── hardening/
│       └── tasks/main.yml
│
├── playbooks/                # 可被 import_playbook 引用的 playbook
│   └── bootstrap.yml
│
├── docs/                     # 額外文件
└── tests/                    # 測試

11.8.2galaxy.yml — Collection 的 manifest

yaml · galaxy.yml 
---
namespace: myorg
name: internal_tools
version: "1.0.0"
readme: README.md
authors:
  - Platform Team <platform@company.com>

description: Internal automation tools and roles for MyOrg infrastructure
license:
  - MIT

tags:
  - internal
  - infrastructure
  - myorg

# 此 collection 的依賴
dependencies:
  "ansible.posix": ">=1.5.0"
  "community.general": ">=9.0.0"

repository: https://github.com/myorg/ansible-internal_tools
documentation: https://docs.internal.company.com/ansible/
homepage: https://github.com/myorg/ansible-internal_tools
issues: https://github.com/myorg/ansible-internal_tools/issues

# 不要打包進 tarball 的檔案
build_ignore:
  - .github
  - tests
  - "*.tar.gz"

11.8.3build / publish workflow

bash · 建置與發布 collection 
# 在 collection 根目錄
$ cd ~/myorg-internal_tools

# 1) build — 產生 tarball
$ ansible-galaxy collection build
# 輸出 myorg-internal_tools-1.0.0.tar.gz

# 2) 本地測試 install 該 tarball
$ ansible-galaxy collection install \
    myorg-internal_tools-1.0.0.tar.gz \
    -p ./test_collections

# 3) publish 到 Galaxy（需有 token）
$ ansible-galaxy collection publish \
    myorg-internal_tools-1.0.0.tar.gz \
    --api-key YOUR_TOKEN

# 4) 發布到私有 Galaxy server
$ ansible-galaxy collection publish \
    myorg-internal_tools-1.0.0.tar.gz \
    --server private_hub

11.8.4使用方

yaml · 從 collection 引用內容 
# 引用 collection 內的 role
- hosts: all
  roles:
    - myorg.internal_tools.deploy      # FQCN 引用
    - myorg.internal_tools.hardening

# 用 task 層方式
- hosts: all
  tasks:
    - name: 用 collection 提供的自定模組
      myorg.internal_tools.my_module:
        option1: value

    - name: 引用內含的 playbook
      ansible.builtin.import_playbook: myorg.internal_tools.bootstrap

11.9Collection 開發 vs Role 開發 — 何時選哪個？

▶

單一服務、組合既有模組

例：「在 ubuntu 上裝設 nginx + 設定」。用 role。Role 結構簡單，門檻低。

▶

有自定模組（Python）

例：「呼叫 internal API 建立 customer」。用 collection。Role 不能裝模組，必須在 collection 裡。

▶

多個相關 role 共享 plugin

例：「3 個 role 都用同一個 internal lookup plugin」。用 collection，把 role + plugin 一起包。

▶

跨組織分享

需要發到 Ansible Galaxy / Automation Hub 公開？用 collection。Galaxy 對 collection 是一等公民。

▶

單一 team 內用

3 個 role 給內部 team 用？放專案 roles/。不需要打包成 collection 的額外複雜度。

▶

5+ role 共用 + 跨專案

內部多個專案會用到的 role 群？包成 internal collection，發到私有 Galaxy server，所有專案 requirements.yml 拉取。

11.10本章重點回顧

01

Collection 是 Ansible 的模組分發單位

2.10 後 Ansible 完全 collection 化。ansible-core 只剩 ~70 個核心模組，其他全在 collection。

02

FQCN 三段式

namespace.collection.plugin。例：community.general.timezone。2026 年硬規範，所有 task 都該用。

03

Role vs Collection

Role 是「組合既有模組」、Collection 是「提供新模組」。Collection 內可包多個 role。

04

核心 5–8 個 collection

ansible.builtin / ansible.posix / community.general / community.crypto / community.docker / community.postgresql / amazon.aws / kubernetes.core 涵蓋 80% 場景。

05

專案本地安裝最佳

-p ./collections 把 collection 放專案內。CI 友善、可重現、可獨立版本管理。

06

requirements.yml + pin 版本

Production 環境必 pin 確切版本（"X.Y.Z"）。Dev 可用範圍。Supply chain 安全的基本要求。

07

Galaxy server 三種

公開 Ansible Galaxy、商業 Automation Hub、自建私有（Pulp / Galaxy NG）。企業環境通常多個並用。

08

建立自家 collection 的時機

有自定模組、5+ role 共用、跨專案使用、需要分享。否則放 roles/ 即可，避免過度工程化。

練習題

  1. 初學者：執行 ansible-galaxy collection list，列出本機已裝的所有 collection 與版本。
  2. 初學者：用 ansible-doc community.general.timezone 看該模組的完整文件，找出它支援的所有參數。
  3. 初學者：在 playbook 中用 FQCN（如 community.general.timezone）設定 host 時區為 UTC。
  4. 開發者：建立一個專案 my-infra/ 含 requirements.yml，列出 5 個 collection 並 pin 版本。執行 ansible-galaxy collection install -r requirements.yml -p ./collections。
  5. 開發者：寫一個 playbook 使用 community.crypto.x509_certificate 自簽 TLS 憑證，再用 community.docker.docker_container 把該憑證掛載進容器使用。
  6. 開發者：把第 10 章寫的 nginx role 與另一個 role（如 monitoring）整合進一個 internal collection 結構。建立 galaxy.yml 並 ansible-galaxy collection build 產出 tarball。
  7. DevOps / SRE：給你的 CI 加 collection cache（如 GitHub Actions 範例），測試 cache 命中時是否大幅加速。
  8. DevOps / SRE：嘗試從一個 collection 的不同版本（如 community.general 9.x → 10.x）升級。先讀 changelog，找出 breaking changes，調整 playbook 後測試。
  9. DevOps / SRE：研究你的組織是否該建私有 Galaxy server。評估：① 內部 collection 數量、② air-gapped 需求、③ 維運成本。給出建議報告。

Ansible Galaxy
公開 collection / role 分發平台（galaxy.ansible.com）。預設來源。
Red Hat Automation Hub
Red Hat 商業版 Galaxy server，提供認證 collection 與企業支援。
私有 Galaxy server
自建的 collection 分發平台，常用 Pulp 或 Galaxy NG。常見於 air-gapped 或受監管環境。
galaxy.yml
Collection 的 manifest 檔，定義 namespace / name / version / dependencies / metadata。
ansible-galaxy collection build
從 collection 原始碼產生 .tar.gz 發布包。產物可 publish 或本地安裝。
