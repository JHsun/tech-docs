第 25 章 — 配置管理進階

Ch4 介紹 inventory 基礎、Ch7 介紹變數與 facts、Ch24 介紹生產級應用部署——這章把這些放大到 100 host 以上的真實規模，並處理「跨 host 協調」這個高階問題。本章五個主題：① 大規模 inventory 設計——multiple sources（static + dynamic + CMDB）合併、群組組合、scale 到 1000+ host；② magic variables 進階——hostvars / groups / group_names / inventory_hostname 的實際用法；③ 跨 host 協調——Web tier 怎麼知道 DB 的 IP？delegate_facts + hostvars 解決；④ custom facts——facts.d 機制讓 host 自報 metadata；⑤ scale 性能調優——fact caching / forks / strategy / smart gathering。讀完這章你能寫一份能跑 1000 host 的 playbook，並讓 web/db/cache 三層自動發現彼此的 IP（不需手寫進 group_vars）。

本章把第 4 章 inventory + 第 7 章 vars/facts 放大到 1000+ host 的工程規模
初學者選讀（25.1–25.2 inventory 與 magic variables） 開發者必讀（特別 25.3 跨 host + 25.4 custom facts） DevOps / SRE 必讀（全章）

25.1大規模 inventory 設計

50 個 host 可以單檔 inventory.yml；500 個 host 不行。本節給工程化的 inventory 結構。

25.1.1multiple sources 合併

真實大規模環境的 inventory 通常來自多個來源：

Figure 25.1 — Inventory 多 source 合併
text · inventory/ 目錄結構 
inventory/
├── 01-static.yml            # bastion / DNS / DC — 不變的
├── 02-aws_ec2.yml           # AWS dynamic plugin 設定
├── 03-gcp_compute.yml       # GCP dynamic plugin 設定
├── 04-cmdb.py               # 自寫 script 從 CMDB 拉
├── group_vars/
│   ├── all.yml
│   ├── webservers.yml
│   └── dbservers.yml
└── host_vars/
    └── db-primary.yml
bash · 用整個目錄 
# 把整個 inventory/ 目錄當 inventory — 自動合併所有 source
$ ansible-playbook -i inventory/ site.yml

# 數字前綴控制載入順序（按 alphabetical）
# static 先載 → dynamic 後補 → CMDB 最後
# 同名 host 後者覆蓋前者

# 看完整 inventory（合併後）
$ ansible-inventory -i inventory/ --graph
$ ansible-inventory -i inventory/ --list

# 看單一 host 的 vars（從哪來）
$ ansible-inventory -i inventory/ --host web01-prod

25.1.2群組組合：children groups

大規模環境的 host 通常屬於多個維度——region、role、env、tier。用 children groups 組合：

yaml · 多維度 group 組合 
---
all:
  children:

    # 維度 1: 環境
    production:
      children:
        prod_us_east: { hosts: { web-prod-use1-01: null } }
        prod_eu_west: { hosts: { web-prod-euw1-01: null } }

    staging:
      children:
        staging_us_east: { hosts: { web-stg-use1-01: null } }

    # 維度 2: 角色
    webservers:
      hosts:
        web-prod-use1-01:
        web-prod-euw1-01:
        web-stg-use1-01:

    dbservers:
      hosts:
        db-prod-use1-primary:
        db-prod-use1-replica1:

    # 維度 3: 區域
    us_east_1:
      children:
        prod_us_east:
        staging_us_east:

# 同一個 host (web-prod-use1-01) 同時屬於：
#   production / prod_us_east / webservers / us_east_1 / all
# 變數從多 group 合併，Ch7 的優先級規則決定誰勝出

25.1.3限制 inventory 範圍：--limit

bash · --limit 用法 
# 只跑 production + webservers 交集
$ ansible-playbook -i inventory/ site.yml \
    --limit "production:&webservers"

# production 但排除 staging（雖然不太合理範例）
$ ansible-playbook -i inventory/ site.yml \
    --limit "production:!staging"

# 只跑特定 region
$ ansible-playbook -i inventory/ site.yml \
    --limit "us_east_1:&webservers"

# 限定單一 host（debug 用）
$ ansible-playbook -i inventory/ site.yml \
    --limit "web-prod-use1-01"

25.2Magic variables 進階

Magic variables 是 Ansible 內建的特殊變數，包含 inventory 與 host 的 metadata。學會四個關鍵 magic variables 等於拿到跨 host 協調的鑰匙。

25.2.1四大 magic variables

變數內容典型用途
hostvars 所有 host 的所有變數的 dict 取其他 host 的 IP / 設定（跨 host 協調）
groups group → host list 的 dict 遍歷某 group 內所有 host
group_names 當前 host 屬於的 group list 條件判斷：「我是哪種 host？」
inventory_hostname 當前 host 在 inventory 的名稱 每 host 各自做事的 key（log file 名等）

25.2.2實用範例：產生 nginx upstream 配置

典型場景：nginx 反向代理需要列出所有 app server 的 IP。不要寫死在 group_vars——用 groups + hostvars 動態產生。

text · templates/nginx-upstream.conf.j2 
# 產生 upstream block — 自動列出所有 app server
upstream app_backend {
{% for host in groups['app_servers'] %}
    server {{ hostvars[host]['ansible_default_ipv4']['address'] }}:{{ hostvars[host]['app_port'] | default(3000) }};
{% endfor %}
}

server {
    listen 80;
    location / {
        proxy_pass http://app_backend;
    }
}
⚠ Facts 必須先 gather 過

用 hostvars[host]['ansible_default_ipv4'] 之前必須先對該 host 跑過 setup（gather facts）。如果 nginx host 跟 app host 是不同 group、且 nginx play 中沒包到 app host——facts 不會有。解法：① 用 fact caching；② 用 delegate_facts（25.3 詳述）；③ 把 facts 從 inventory 變數塞進去（如 app_ip: 寫在 host_vars/）。

25.2.3group_names 動態判斷

yaml · 用 group_names 條件處理 
- name: 統一基礎設定 — 但依角色微調
  hosts: all
  tasks:
    # 所有 host 都裝 monitoring agent
    - name: 裝 monitoring agent
      ansible.builtin.package:
        name: datadog-agent
        state: present

    # 只有 dbservers 多裝 DB 監控插件
    - name: DB host 加裝插件
      ansible.builtin.package:
        name: datadog-postgres-integration
      when: "'dbservers' in group_names"

    # 只有 production 收集 trace 等級 log
    - name: prod 加 trace
      ansible.builtin.lineinfile:
        path: /etc/datadog-agent/datadog.yaml
        line: "log_level: TRACE"
      when: "'production' in group_names"

25.2.4取 group 第一個 host（master/primary 模式）

yaml · 取 group[0] 當 primary 
# Cluster bootstrap — 第一個 host 是 leader
- name: bootstrap cluster
  hosts: "{{ groups['cluster_nodes'][0] }}"      # 第一個 = leader
  tasks:
    - ansible.builtin.command: cluster-init
      register: init

- name: 其餘 node join
  hosts: cluster_nodes:!{{ groups['cluster_nodes'][0] }}
  tasks:
    - ansible.builtin.command:
        cmd: "cluster-join {{ hostvars[groups['cluster_nodes'][0]]['ansible_default_ipv4']['address'] }}"

25.3跨 host 協調 — Web 怎麼知道 DB 的 IP？

這是配置管理的經典難題。Web tier 的 nginx 要連 DB host，但 DB IP 不應該寫死。三種解決方式：

25.3.1三種方案對照

方案機制優劣
① 寫死在 group_vars db_host: 10.0.2.20 簡單；DB 換 IP 要改 vars 檔
② DNS / service discovery app 連 db.internal 標準解；需 DNS 基礎設施
③ Ansible hostvars 動態取 從 inventory + facts 推 不需外部依賴；需 facts 已 gather

25.3.2方案 ③ 的實作：delegate_facts

場景：你只跑 --limit webservers（不對 db host 跑），但 web role 需要 DB 的 IP。預設情況下 dbservers 沒被 setup 過，hostvars['db-primary'] 是空。delegate_facts 解決：

yaml · delegate_facts 跨 host gather 
---
- name: 配置 webservers — 需要 DB 資訊
  hosts: webservers
  gather_facts: true
  tasks:

    # Pre-task — 先去 gather DB host facts，存到 db host 的 hostvars
    - name: 主動 gather DB facts
      ansible.builtin.setup:
      delegate_to: "{{ item }}"
      delegate_facts: true      # 關鍵 — 把 facts 存到 delegated host 的 hostvars
      loop: "{{ groups['dbservers'] }}"
      run_once: true              # 不需每個 webserver 都跑一遍

    # 現在 hostvars['db-primary'] 有完整 facts
    - name: 產生 app config 含 DB IP
      ansible.builtin.template:
        src: app.env.j2
        dest: /etc/myapp/app.env
      vars:
        db_host_ip: "{{ hostvars[groups['dbservers'][0]]['ansible_default_ipv4']['address'] }}"
✓ delegate_facts 的精髓

沒設 delegate_facts: true：facts 存到「執行 task 的 host」（即 webserver）的 hostvars——錯誤的 host！你看到的 hostvars[db-primary] 是空的。設了：facts 存到「被 delegated 的 host」（即 db-primary）的 hostvars——對的位置。

25.3.3跨 play 共享自定 facts

yaml · 用 set_fact 跨 play 傳資料 
---
# Play 1: DB host 跑 migration、把版本記到 hostvars
- name: DB migration
  hosts: db_primary
  tasks:
    - name: 跑 migration
      ansible.builtin.command: /opt/myapp/migrate.sh
      register: migration_out

    - name: 記下 schema 版本
      ansible.builtin.set_fact:
        db_schema_version: "{{ migration_out.stdout | regex_search('v(\\d+)') }}"


# Play 2: webservers 用 hostvars 取 DB 的 schema 版本
- name: 部署 app 版本對應 schema
  hosts: webservers
  tasks:
    - name: 確認 app 版本與 DB schema 對得起來
      ansible.builtin.assert:
        that:
          - "app_version_min_schema | int <= hostvars[groups['db_primary'][0]]['db_schema_version'] | int"
        fail_msg: "app 需要 schema {{ app_version_min_schema }}，但 DB 是 {{ hostvars[...]['db_schema_version'] }}"

25.4Custom facts — facts.d

除了 Ansible 自動 gather 的 facts，可讓 host 端自報 metadata。facts.d 機制讓你放可執行腳本到 /etc/ansible/facts.d/，每次 setup 自動跑、結果進 facts。

25.4.1機制

bash · 部署 custom fact script 
# 在 host 上建 /etc/ansible/facts.d/myapp.fact
# 必須可執行、輸出 JSON 或 INI 格式

$ sudo mkdir -p /etc/ansible/facts.d
$ sudo tee /etc/ansible/facts.d/myapp.fact <<'EOF'
#!/bin/bash
# 輸出 JSON
cat <<END
{
  "app_version": "$(cat /opt/myapp/VERSION 2>/dev/null || echo unknown)",
  "deployed_at": "$(stat -c %y /opt/myapp/current 2>/dev/null || echo unknown)",
  "instance_role": "$(curl -s http://169.254.169.254/latest/meta-data/tags/instance/Role || echo unknown)"
}
END
EOF

$ sudo chmod +x /etc/ansible/facts.d/myapp.fact

# 試跑（手動）
$ /etc/ansible/facts.d/myapp.fact
# {"app_version": "v1.2.3", "deployed_at": "2026-05-08 10:30:00", "instance_role": "webserver"}

25.4.2從 Ansible 取 custom facts

yaml · 取用 ansible_local.myapp 
- name: 確認 app 版本
  hosts: webservers
  tasks:
    - ansible.builtin.debug:
        msg:
          - "當前版本：{{ ansible_local.myapp.app_version }}"
          - "部署時間：{{ ansible_local.myapp.deployed_at }}"

    - name: 如果版本不是預期 — fail
      ansible.builtin.fail:
        msg: "預期 {{ expected_version }}，實際 {{ ansible_local.myapp.app_version }}"
      when: ansible_local.myapp.app_version != expected_version
ⓘ 為什麼用 facts.d 而非直接執行

① 自動快取——配 fact_caching 後 facts 跨 playbook run 共用，比每次 shell 重跑快；② 結構化——回 JSON 直接變 dict，比 register + parse 乾淨；③ host 自治——host 自己知道要報什麼資訊，control side 不必硬編碼；④ 給其他工具用——CMDB / monitoring 也能看 facter / ansible setup 結果。

25.5Performance — 從 50 到 1000 host

50 個 host 跑 5 分鐘的 playbook，1000 個 host 不調優可能跑2 小時。本節給工程化調優。

25.5.1四大調優手段

①

forks

並行 host 數。預設 5 太小。生產通常 50–100。control node 規模決定上限（每個 fork 是個 Python process）。

②

fact caching

Facts 跨 playbook run 快取。第二次跑就跳過 setup（節省 host 數秒至 10 秒）。對 1000 host = 省下 minutes。

③

SSH ControlPersist

Ch18 的招式 — SSH 連線多工。100 個 task 從 100 次 TCP handshake 變 1 次。

④

strategy: free

同 play 內各 host 獨立跑（不必同步）。批次維護 task 適用。

25.5.2生產級 ansible.cfg

ini · 給 1000+ host 用的 ansible.cfg 
[defaults]
# 並行 host 數 — 從預設 5 提到 50
forks = 50

# Fact caching — 跨 run 共用
gathering = smart                    # cache hit 就不 re-gather
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts
fact_caching_timeout = 86400           # 24 小時

# 用 redis 做 fact cache（多 control node 共用）
# fact_caching = redis
# fact_caching_connection = redis.example.com:6379:0

# 進階 — 只 gather 必要的 facts
gather_subset = !all,!min,network,distribution

# Output 友善
stdout_callback = yaml
callbacks_enabled = timer, profile_tasks, profile_roles

# 預設 strategy（per play 還可覆蓋）
strategy = linear

[ssh_connection]
pipelining = True
ssh_args = -C -o ControlMaster=auto -o ControlPersist=60s -o PreferredAuthentications=publickey
control_path_dir = /tmp/ansible-cp
retries = 3

[persistent_connection]
command_timeout = 60

25.5.3調優前後實測

場景預設調優後加速
100 host × 30 task ~25 分鐘 ~3 分鐘 ~8×
1000 host × 30 task ~4 小時 ~25 分鐘 ~10×
第二次跑（fact cache 命中） 每 host 額外 8 秒（gather） 0 秒 無限

25.6ARA — 部署觀察工具

1000 host 部署的 stdout 太長根本看不完。ARA（Ansible Records Ansible）把每次 run 存進 SQLite/PostgreSQL，提供 web UI 查詢。

bash · 安裝 ARA 
# 安裝
$ pip install "ara[server]"

# 啟用 callback plugin（ansible.cfg）
$ export ANSIBLE_CALLBACKS_ENABLED="ara_default"

# 跑 playbook — ARA 自動把 task / play / host 結果存進 SQLite
$ ansible-playbook site.yml

# 啟動 web UI（預設 localhost:8000）
$ ara-manage runserver

# 看：
# - 哪個 task 在哪個 host 失敗
# - 部署歷史（哪個 release 何時部署誰執行）
# - 跨 run 比較

25.7業界最佳實踐

①

inventory 用目錄而非單檔

50+ host 就改用目錄。多 source 自然合併、static + dynamic 並存。-i inventory/ 而非 -i hosts.yml。

②

多維度 children groups

環境 × 角色 × 地區 × 層級。同一 host 可屬多 group。--limit "production:&webservers" 取交集。

③

fact caching 必開

gathering = smart + fact_caching = jsonfile/redis。第二次跑省下整個 setup 階段。

④

forks 50–100

預設 5 太小。50–100 是大型部署常見值。control node 太弱可考慮 ansible-pull 反過來讓 host 拉。

⑤

跨 host 用 hostvars + delegate_facts

不要寫死 IP / 配置。用 facts 動態取。delegate_facts 是 setup 跨 host 的關鍵。

⑥

Custom facts 用 facts.d

app version / 部署狀態 / instance metadata 放 /etc/ansible/facts.d/。host 自報。

⑦

profile_tasks 找瓶頸

跑慢時不要瞎調 — 開 callback 看哪 task 吃時間。優化前先測量。

⑧

ARA / AWX 觀察平台

大規模一定要工具看 run 結果。stdout 看不過來。ARA 開源、AWX/AAP 商用 enterprise 版。

25.8本章重點回顧

01

多 source inventory

static 檔 + AWS / GCP plugin + 自寫 CMDB script。用目錄當 inventory，數字前綴控制順序。

02

多維度 children groups

環境 × 角色 × 區域。同 host 屬多 group。--limit 取交集 / 排除。

03

四大 magic variables

hostvars（跨 host 取資料）、groups（遍歷 group）、group_names（自我判斷）、inventory_hostname（自身 ID）。

04

跨 host 協調

nginx 取 app IP / web 取 DB IP。用 hostvars + delegate_facts 動態 gather。

05

delegate_facts: true 的關鍵

沒設就把 facts 存錯位置。設了才存到 delegated host 的 hostvars。

06

facts.d custom facts

放 /etc/ansible/facts.d/myapp.fact 可執行腳本。輸出 JSON。ansible_local.myapp 取用。

07

四大 scale 調優

forks 50+、fact caching、ControlPersist、strategy 選擇。1000 host 從 4 小時壓到 25 分鐘。

08

觀察工具

profile_tasks 找瓶頸；ARA / AWX 看 run 歷史。1000 host 不能靠 stdout。

練習題

  1. 初學者：把單檔 inventory.yml 改成 inventory/ 目錄結構（含 01-static.yml + group_vars/ + host_vars/）。ansible-inventory --graph 確認結構正確。
  2. 初學者：對 inventory 加環境 × 角色雙維度群組。用 --limit "prod:&webservers" 確認只跑交集。
  3. 初學者：寫一個小 playbook 用 group_names 判斷當前 host 屬於 webservers 還是 dbservers，分別印不同訊息。
  4. 開發者：寫 nginx upstream 模板用 {% for host in groups['app_servers'] %} 遍歷產生。確認新增 app server 後重跑能自動加進 upstream。
  5. 開發者：實作 25.3 的 delegate_facts pattern — 只跑 webservers 的 playbook 也能取到 dbservers 的 IP。確認沒設 delegate_facts: true 時 hostvars 為空。
  6. 開發者：寫一個 facts.d script（bash 或 Python），輸出 app version + git commit hash + 部署時間。部署到 host，ansible-doc 確認 ansible_local.myapp 內容正確。
  7. DevOps / SRE：對你的 ansible.cfg 加上 25.5.2 的調優設定。對某個 50+ host 的 playbook 量測前後耗時、寫成短報告。
  8. DevOps / SRE：開 profile_tasks，找出 playbook 中 top 5 慢 task。各想一條優化方法（cache / async / delegate / 拆分）。
  9. DevOps / SRE：裝 ARA、跑 3 次 playbook（一次成功、一次部分失敗、一次完整失敗）。在 web UI 比較三次的結果差異，寫出你會用 ARA 找出哪些 incident 模式。

本章詞彙表

Multi-source inventory
同時用多個 inventory source（static + dynamic + custom script）。Ansible 自動合併。實作上把它們放同一個目錄、用 -i inventory/。
Children groups
群組內含其他群組。production: { children: { prod_us_east: {...} } }。允許多維度組合。
--limit pattern
命令列限制執行 host 範圍。支援交集（:&）、聯集（:）、排除（:!）。
Magic variables
Ansible 內建特殊變數，包含 inventory 與 host metadata。最常用四個：hostvars / groups / group_names / inventory_hostname。
hostvars
所有 host 的所有變數的 dict。hostvars['db-primary']['ansible_default_ipv4']['address'] 取其他 host 的 IP。需先 gather 該 host facts。
groups
group 名 → host list 的 dict。groups['webservers'] 是 webservers group 內所有 host 名。
group_names
當前 host 所屬 group 的 list。用於 host 自我判斷：when: "'production' in group_names"。
inventory_hostname
當前 host 在 inventory 中的名稱。每 host 各自做事的 key。注意被 delegate 不影響此值。
delegate_to
把 task 交給另一台 host 執行。但 facts 預設仍歸 inventory_hostname（執行 task 那台），需配 delegate_facts 改變。
delegate_facts: true
把 delegate 後 gather 的 facts 存到「被 delegated 的 host」的 hostvars，而非執行 task 的 host。跨 host 協調的關鍵。
set_fact
運行時建立變數的模組。delegate_facts: true 配它能把資料寫到其他 host 的 hostvars。
facts.d / 本地 facts
host 上 /etc/ansible/facts.d/ 目錄。每個 *.fact 檔（可執行、輸出 JSON 或 INI）會在 setup 時自動跑、結果進 ansible_local。
ansible_local
magic 變數，包含該 host 的 custom facts。ansible_local.myapp.app_version。
fact_caching
把 facts 跨 playbook run 快取的機制。jsonfile / redis / memcached 後端。配 gathering = smart 自動跳過已快取 host。
gathering: smart
fact gathering 模式。第一次 gather、之後 cache hit 就跳過。比 implicit（每次都 gather）快。
gather_subset
限制 gather 哪些 facts 子集。!all,!min,network,distribution 表示「不要全套，但要 network 與 distribution」。減少 setup 時間。
forks
並行 host 數。預設 5、生產通常 50–100。每個 fork 是獨立 Python process，control node 規模決定上限。
strategy: linear / free
linear（預設）— 每 task 等所有 host 完成才走下一個 task；free — 每 host 各自跑到 play 結束。維護任務適用 free。
profile_tasks callback
內建 callback。playbook 結尾列出 top N 慢 task。優化前必開。
profile_roles callback
類似但以 role 為單位。看哪個 role 整體耗時。
ARA (Ansible Records Ansible)
開源觀察工具。callback plugin 把每次 run 存 DB，提供 web UI 查詢。1000+ host 部署必備。
ansible-pull
反向部署模式。host 自己定期從 git pull playbook 並執行（不是 control 推）。適合很大規模或無中央 control node 場景。
CMDB (Configuration Management DataBase)
內部資產管理系統。常作為 inventory source — 寫 script 從 CMDB API 拉 host 列表。
