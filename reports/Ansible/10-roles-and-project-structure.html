第 10 章 — Roles 與專案結構

當 playbook 從 50 行長到 500 行、3 個 task 變成 30 個 task、團隊從一個人擴大到五個人，扁平結構就撐不住了。Roles 是 Ansible 給出的「程式工程化」答案——把相關的 tasks、handlers、變數、templates、files 包成一個有標準目錄結構的單位，可重用、可分享、可獨立測試。本章從「為什麼要 role」開始，逐一介紹 8 個標準目錄各自的職責、role 內的變數設計（defaults vs vars 差異 = 業界 #1 困惑點）、role 依賴、引用 role 的三種方式（roles keyword / import_role / include_role）、業界推崇的目錄結構，最後給出生產級的 role 開發 checklist。

本章覆蓋官方文件對應：Roles · Ansible Galaxy 結構規範
初學者必讀（10.1–10.4） 開發者必讀（全章） DevOps / SRE 必讀（全章特別 10.7 大型專案結構與 10.9 開發 checklist）

10.1為什麼需要 Role？

第 6 章 下已介紹 include_tasks / import_tasks 切分大檔。Role 在這之上更進一步——不只切 tasks，還把變數、templates、files、handlers、metadata都包進一個有標準結構的單位。

10.1.1沒用 role vs 用了 role

text · 沒用 role 的扁平結構（會變成噩夢） 
my-project/
├── inventory/
├── ansible.cfg
└── playbooks/
    ├── site.yml                # 1500 行的怪物
    ├── nginx.conf.j2           # 散落在 playbook 旁
    ├── postgres.conf.j2
    ├── redis.conf.j2
    ├── app.crt                 # 各種雜檔混雜
    ├── deploy.sh
    └── ...

# 問題：
# - 找東西要靠 grep
# - 想複用某段 nginx 設定到別的專案？只能手動 copy paste
# - 一個變更影響哪些 tasks 不清楚
# - 兩個人同時修改同一份 playbook 經常衝突
text · 用 role 的結構（清晰、可重用） 
my-project/
├── inventory/
├── ansible.cfg
├── site.yml                    # 主入口，僅 30 行
└── roles/
    ├── nginx/                  # 一切 nginx 相關都在這
    │   ├── tasks/
    │   ├── templates/
    │   ├── handlers/
    │   ├── defaults/
    │   ├── vars/
    │   ├── files/
    │   ├── meta/
    │   └── README.md
    ├── postgres/
    ├── redis/
    └── monitoring/

# 好處：
# - 找東西看目錄就知道
# - 想複用 nginx role？整個目錄複製到別的專案就好
# - 模組化、可獨立測試
# - 多人協作衝突大幅減少

10.1.2Role 的設計原則

①

單一職責

一個 role 做一件事 — nginx role 就只裝設 nginx，不要混入 mysql 或 application code。職責分清楚才能組合。

②

參數化

所有「使用者可能想調」的選項放 defaults/main.yml，附詳細註解。內部常數放 vars/main.yml。

③

跨平台支援

用 facts（ansible_os_family）做分流，把 OS 特定變數放 vars/Debian.yml / vars/RedHat.yml，動態 include。

④

有 README

列出 role 用途、所有可調變數（含預設值）、依賴的其他 role、支援的 OS 平台、執行範例。

10.3tasks / handlers / templates / files

10.3.1tasks/main.yml — 入口

yaml · roles/nginx/tasks/main.yml 
---
# 入口 — Ansible 從這裡開始執行

- name: 載入 OS 特定變數
  ansible.builtin.include_vars: "{{ ansible_os_family }}.yml"

- name: 引用安裝相關 task
  ansible.builtin.include_tasks: install.yml

- name: 引用設定相關 task
  ansible.builtin.include_tasks: configure.yml

- name: 引用 vhost 設定（條件式）
  ansible.builtin.include_tasks: vhosts.yml
  when: nginx_vhosts | length > 0
ⓘ 把 main.yml 當「目錄」

大型 role 的 tasks/main.yml 通常只放幾個 include_tasks，把實際 task 拆到 install.yml、configure.yml、service.yml 等子檔。一個 main.yml 不應超過 50 行，否則就該再切。

10.3.2handlers/main.yml

yaml · roles/nginx/handlers/main.yml 
---
- name: restart nginx
  ansible.builtin.service:
    name: "{{ nginx_service_name }}"
    state: restarted
  listen: "restart nginx"      # 對外的事件名（其他 role 也能 notify）

- name: reload nginx
  ansible.builtin.service:
    name: "{{ nginx_service_name }}"
    state: reloaded
  listen: "reload nginx"

10.3.3templates/ 與 files/

ⓘ 自動查找路徑

在 role 內使用 template 模組時，src: nginx.conf.j2 會自動到 roles/nginx/templates/nginx.conf.j2 找；copy 模組的 src 自動到 roles/nginx/files/ 找。不需要寫完整路徑，這是 role 給你的便利。

yaml · 在 role 內引用檔案的簡寫 
# roles/nginx/tasks/configure.yml
- name: 部署 nginx.conf
  ansible.builtin.template:
    src: nginx.conf.j2          # Ansible 自動找 roles/nginx/templates/nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: restart nginx

- name: 部署預設首頁
  ansible.builtin.copy:
    src: default-index.html      # 自動找 roles/nginx/files/default-index.html
    dest: /var/www/html/index.html

10.4defaults vs vars — 業界 #1 困惑點

第 7 章 上的 22 層優先序中提過：defaults/main.yml 是第 2 層（最低之一），vars/main.yml 是第 15 層（高優先序）。這個差異決定了使用者能不能「輕易覆蓋」這些變數。

10.4.1defaults/ — 給人覆蓋的

yaml · roles/nginx/defaults/main.yml 
---
# 使用者可調的設定 — 這裡的值是 sane defaults
# 任何地方覆蓋（group_vars / host_vars / play vars）都會勝出

# 服務基本設定
nginx_listen_port: 80
nginx_worker_processes: auto
nginx_worker_connections: 1024

# SSL（預設關閉）
nginx_ssl_enabled: false
nginx_ssl_cert_path: ""
nginx_ssl_key_path: ""

# Virtual hosts (空 list 預設)
nginx_vhosts: []

10.4.2vars/ — 不希望被亂改的

yaml · roles/nginx/vars/main.yml 
---
# 內部使用的常數 — 高優先序，難以從外部覆蓋
# （只有 -e 命令列才蓋得過）

__nginx_default_config_path: /etc/nginx
__nginx_required_packages:
  - nginx
  - openssl

# 注意：用 __ 前綴強調「這是內部用，請勿從外部設定」

10.4.3OS 特定變數放 vars/<OS_family>.yml

yaml · 多檔 OS 變數 
# roles/nginx/vars/Debian.yml
---
nginx_package_name: nginx
nginx_service_name: nginx
nginx_user: www-data
nginx_log_dir: /var/log/nginx

# roles/nginx/vars/RedHat.yml
---
nginx_package_name: nginx
nginx_service_name: nginx
nginx_user: nginx          # RHEL 是 nginx user 不是 www-data
nginx_log_dir: /var/log/nginx

# roles/nginx/tasks/main.yml 開頭動態載入
- name: 載入 OS 特定變數
  ansible.builtin.include_vars: "{{ ansible_os_family }}.yml"

10.4.4defaults vs vars 一覽表

面向defaults/main.ymlvars/main.yml
優先序層級第 2 層（最低）第 15 層（高）
目的使用者可調的設定內部常數、不希望被亂改
能被輕易覆蓋的層級幾乎所有層（含 inventory）只有 task vars / set_fact / extra_vars
命名建議nginx_X（公開）__nginx_X（雙底線）
適合放什麼port、版本、開關、可選功能固定路徑、必要套件清單、OS map

10.5meta/main.yml — 依賴與 Metadata

10.5.1基本結構

yaml · roles/nginx/meta/main.yml 
---
galaxy_info:
  role_name: nginx
  author: your-team
  description: Install and configure nginx web server
  license: MIT
  min_ansible_version: "2.18"
  platforms:
    - name: Ubuntu
      versions: [jammy, noble]
    - name: Debian
      versions: [bookworm]
    - name: EL
      versions: ["9", "10"]
  galaxy_tags:
    - webserver
    - nginx
    - proxy

# Role 依賴 — 跑這個 role 之前先跑下面的 role
dependencies:
  - role: common
  - role: firewall
    vars:
      firewall_allowed_ports:
        - "{{ nginx_listen_port }}"
  - role: ssl_certs
    when: nginx_ssl_enabled

10.5.2依賴執行順序

Figure 10.2 — Role 依賴的執行順序
⚠ 依賴是「前置條件」非「真依賴」

Ansible 的 role dependency 不是程式語言的 import — 它的語意是「跑這個 role 之前先跑那些 role」。如果同一份 playbook 多個 role 都依賴 common，common 預設只會跑一次（除非設 allow_duplicates: true）。把 dependencies 想成「automatic prerequisites」較精確。

10.6引用 Role 的三種方式

第 6 章 下已介紹過 import vs include 的概念。本節聚焦 roles: keyword 與兩個 task 層的引用方式。

10.6.1roles: keyword（play 層）

yaml · 用 roles: 在 play 層引用 
- name: 部署 web 服務
  hosts: webservers
  become: true

  pre_tasks:
    - name: 前置檢查
      ansible.builtin.ping:

  roles:                                      # 簡單寫法
    - common
    - nginx

  post_tasks:
    - name: 健康檢查
      ansible.builtin.uri:
        url: http://localhost/health

# 進階寫法：傳 vars / tags / when 給 role
- name: 同主機部署兩個應用
  hosts: webservers
  roles:
    - role: app_instance
      vars:
        app_name: api
        app_port: 8080
      tags: [api]

    - role: app_instance
      vars:
        app_name: admin
        app_port: 8081
      tags: [admin]

10.6.2import_role（task 層 — 靜態）

yaml · import_role 範例 
tasks:
  - name: 先做某些事
    ansible.builtin.debug:
      msg: "準備引用 nginx role"

  - name: 引用 nginx role 在 task 流中插入
    ansible.builtin.import_role:
      name: nginx
    vars:
      nginx_listen_port: 8080

  - name: role 跑完後做某事
    ansible.builtin.debug:
      msg: "nginx role 完成"

10.6.3include_role（task 層 — 動態）

yaml · include_role 配 loop 
tasks:
  - name: 為每個應用部署 app_instance role
    ansible.builtin.include_role:
      name: app_instance
    vars:
      app_name: "{{ item.name }}"
      app_port: "{{ item.port }}"
    loop:
      - { name: api,   port: 8080 }
      - { name: admin, port: 8081 }
      - { name: job,   port: 8082 }
    # import_role 不能配 loop！只有 include_role 可以

  - name: 條件式引用 role
    ansible.builtin.include_role:
      name: monitoring
    when: env == 'production'

10.6.4三種引用方式對照

方式位置展開時機支援 loop支援 vars
roles:play 層play 開始前否是
import_roletask 層解析時（靜態）否是
include_roletask 層runtime（動態）是是
ⓘ 何時用哪一個

絕大多數情況用 roles:（play 層引用最簡潔）。需要在 task 流中間插入 role、或對 role 做 loop / 條件，用 include_role。import_role 較少用——當你要 tag 繼承給 role 內所有 task 時才有理由。

10.8完整 Role 範例：nginx

把以上所有概念整合成一個生產級的 nginx role：

yaml · roles/nginx/defaults/main.yml 
---
# 服務設定
nginx_listen_port: 80
nginx_worker_processes: auto
nginx_worker_connections: 1024

# Virtual hosts (空 list 表示不部署任何 vhost)
nginx_vhosts: []
# 範例：
# nginx_vhosts:
#   - server_name: api.example.com
#     listen: 80
#     proxy_pass: http://backend

# SSL
nginx_ssl_enabled: false

# Service state
nginx_service_state: started
nginx_service_enabled: true
yaml · roles/nginx/tasks/main.yml 
---
- name: 載入 OS 特定變數
  ansible.builtin.include_vars: "{{ ansible_os_family }}.yml"
  tags: [always]

- name: 引用安裝任務
  ansible.builtin.include_tasks: install.yml
  tags: [install]

- name: 引用設定任務
  ansible.builtin.include_tasks: configure.yml
  tags: [configure]

- name: 引用 vhost 任務
  ansible.builtin.include_tasks: vhosts.yml
  when: nginx_vhosts | length > 0
  tags: [configure, vhosts]

- name: 服務管理
  ansible.builtin.service:
    name: "{{ nginx_service_name }}"
    state: "{{ nginx_service_state }}"
    enabled: "{{ nginx_service_enabled }}"
  tags: [service]
yaml · roles/nginx/tasks/install.yml 
---
- name: Debian 系 — 更新 apt cache
  ansible.builtin.apt:
    update_cache: true
    cache_valid_time: 3600
  when: ansible_os_family == "Debian"

- name: 安裝 nginx 套件
  ansible.builtin.package:
    name: "{{ nginx_package_name }}"
    state: present
yaml · roles/nginx/tasks/configure.yml 
---
- name: 部署主設定檔
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: "{{ __nginx_config_path }}/nginx.conf"
    owner: root
    group: root
    mode: "0644"
    validate: "nginx -t -c %s"
  notify: reload nginx
yaml · roles/nginx/tasks/vhosts.yml 
---
- name: 部署各 vhost 設定
  ansible.builtin.template:
    src: vhost.conf.j2
    dest: "{{ __nginx_config_path }}/conf.d/{{ item.server_name }}.conf"
    mode: "0644"
  loop: "{{ nginx_vhosts }}"
  loop_control:
    label: "{{ item.server_name }}"
  notify: reload nginx
yaml · 使用方：playbooks/webservers.yml 
---
- name: 部署 webservers
  hosts: webservers
  become: true

  roles:
    - role: nginx
      vars:
        nginx_listen_port: 80
        nginx_vhosts:
          - server_name: api.example.com
            listen: 80
            proxy_pass: http://backend
          - server_name: admin.example.com
            listen: 80
            root: /var/www/admin

10.9Role 開發 Checklist

✓

使用 ansible-galaxy init

不要手動建目錄。ansible-galaxy role init roles/X 自動產生標準結構，省事且不會漏東西。

✓

所有變數加 role 名前綴

nginx_X 而非 X。Role 之間命名不衝突，code review 時也一眼看出歸屬。內部變數用 __ 前綴。

✓

defaults 全部含註解

每個變數都註解「這是什麼、合理範圍、預設用意」。Defaults 是 role 對外的 API 文件。

✓

所有 task 用 FQCN

ansible.builtin.apt 而非 apt。明確、無歧義、與 collection 生態對齊。

✓

OS 分流用 vars/<family>.yml

避免到處寫 when: ansible_os_family == X。動態 include_vars 載入 OS 特定值，主 task 保持乾淨。

✓

tasks 切多檔

main.yml 只放 include。實際 task 拆 install.yml / configure.yml / service.yml 等。每個檔案 < 50 行。

✓

每個 task 加 tag

install / configure / service 三維度。使用方可用 --tags 選擇執行範圍。

✓

handler 用 listen

handler 加 listen: "service-name action" 對外暴露事件主題，其他 role 也能 notify。

✓

關鍵 template 加 validate

nginx.conf / sshd_config / sudoers 等改壞會炸的設定檔，務必加 validate: "..." 安全網。

✓

README 說明清楚

列出：用途、變數（含預設值）、依賴、支援平台、使用範例。Role 是給人用的，文件比程式更重要。

✓

requirements.yml pin 版本

外部 role / collection 依賴務必 pin 版本。否則一週後別人 clone 跑出來結果不同就難以追蹤。

✓

Idempotent 是底線

Role 跑兩次 PLAY RECAP 第二次的 changed 應該是 0。任何不冪等的 task（command/shell）都要加 creates/removes/changed_when。

10.10本章重點回顧

01

Role = 程式工程化的單位

把 tasks / vars / templates / files / handlers 包成一個有標準目錄結構的單位。可重用、可分享、可獨立測試。

02

單一職責

一個 role 做一件事。nginx 就只裝設 nginx。要組合多個服務用 playbook 串多個 role。

03

標準目錄

tasks / handlers / defaults / vars / templates / files / meta 是核心七目錄。ansible-galaxy role init 自動產生骨架。

04

defaults 是 role API

第 2 層優先序，使用者輕易覆蓋。所有「可調」設定放這，每個含詳細註解。

05

vars 是內部常數

第 15 層優先序，難覆蓋。OS 特定值放 vars/<family>.yml，內部用 __ 前綴變數放 main.yml。

06

meta/main.yml 兩件事

① Galaxy metadata（作者、平台、tag）。② dependencies: 列出前置 role —— 這個 role 跑前先跑那些。

07

三種引用方式

roles: play 層最簡潔。include_role task 層動態（支援 loop）。import_role task 層靜態（tag 繼承）。

08

大型專案結構

inventories/<env>/ 多環境、playbooks/site.yml 主入口、roles/ 自家 role、requirements.yml 外部依賴 pin 版本。

練習題

  1. 初學者：用 ansible-galaxy role init roles/myrole 建一個新 role，觀察自動產生的目錄結構。
  2. 初學者：把第 6 章寫過的某個 nginx playbook，改寫成一個 nginx role + 一個引用它的 site.yml。執行確認與原本行為一致。
  3. 初學者：給 role 的 defaults/main.yml 加 5 個變數（含註解），在使用方 playbook 用 roles: - role: X vars: ... 覆蓋其中一個，確認生效。
  4. 開發者：把 role 的 tasks/main.yml 拆成 install.yml + configure.yml + service.yml 三個子檔，主 main.yml 只放 include_tasks。
  5. 開發者：給 role 加跨 OS 支援 — 建立 vars/Debian.yml 與 vars/RedHat.yml，在 main.yml 動態 include_vars: "{{ ansible_os_family }}.yml"。
  6. 開發者：給 role 寫完整 README.md，列出：用途、所有可調變數（含預設值與用途）、依賴 role、支援平台、最小使用範例。
  7. DevOps / SRE：建立 requirements.yml 引用 geerlingguy.docker（pin 版本），執行 ansible-galaxy install -r，並在 playbook 中使用它。
  8. DevOps / SRE：給 role 加 meta/main.yml dependencies — 例如 nginx role 依賴 common role 與 firewall role（後者帶 nginx_listen_port 參數）。觀察執行順序。
  9. DevOps / SRE：把 role 用 include_role + loop 同時部署多個應用實例（不同 app_name + app_port），確認每個 role 實例獨立運作不互相影響。

本章詞彙表

Role
Ansible 的可重用單位，把 tasks / vars / templates / files / handlers / metadata 包成一個有標準目錄結構的目錄。
tasks/main.yml
Role 的入口檔，Ansible 從這裡開始執行 role 的 task。
handlers/main.yml
Role 內的 handler 定義。可被本 role 或其他 role notify 觸發。
defaults/main.yml
Role 的預設變數值，第 2 層優先序（最低之一）。「歡迎使用者覆蓋」的設定都放這。
vars/main.yml
Role 的內部變數，第 15 層優先序（高）。OS 特定常數、內部 path 等不希望被亂改的值放這。
vars/<OS_family>.yml
OS 特定變數檔，配 include_vars 動態載入。常見 Debian.yml / RedHat.yml / Alpine.yml。
templates/
Role 的 Jinja2 模板目錄。template 模組的 src 自動到這裡找。
files/
Role 的靜態檔案目錄。copy / script 模組的 src 自動到這裡找。
meta/main.yml
Role 的 metadata 與依賴宣告。含 galaxy_info 與 dependencies 兩大區。
dependencies
meta/main.yml 內的前置 role 列表。Ansible 跑該 role 前會先跑這些 role。
allow_duplicates
meta/main.yml 設定。預設同 role 在同 playbook 只跑一次；設 true 可跑多次。
roles: keyword
Play 層引用 role 的最簡寫法。在 pre_tasks 之後、tasks 之前執行。
import_role
Task 層靜態引用 role。解析時展開，tag 會繼承給內部 task，不支援 loop。
include_role
Task 層動態引用 role。runtime 展開，支援 loop / when 真正動態決定，tag 只套用於 include 動作本身。
ansible-galaxy role init
命令列工具，自動產生 role 標準目錄骨架。ansible-galaxy role init roles/myrole。
requirements.yml
列出外部 role 與 collection 依賴的檔案。配 ansible-galaxy install -r 安裝。生產專案必 pin 版本。
library/ / filter_plugins/ / lookup_plugins/
Role 內的進階目錄，分別放自定模組、Jinja2 filter、lookup plugin。Role 啟用時自動加入搜尋路徑。
