第 2 章 — 架構與運作原理

把 Ansible 拆開來看，它由五個核心要素組成：control node、managed node、inventory、modules、playbook。這一章從最高層的架構藍圖往下鑽到「一個 task 在 SSH 層發生了什麼事」，包括 Ansiballz 模組打包、SSH pipelining、ControlPersist、idempotency 的內部實作，以及 Collections 架構。理解這些，你才能讀懂 -vvvv 的輸出、判斷哪些行為可優化、設計大規模執行時取捨在哪。

本章覆蓋官方文件對應：Getting Started · Installation Guide · Developer Guide › Module Architecture
初學者必讀（2.1–2.2） 開發者必讀（全章） DevOps / SRE 必讀（2.3–2.5）

2.1五個核心要素

Ansible 的所有功能、所有複雜性、所有效能調校手段，最終都圍繞這五個元素之間的關係。先把五個元素的定位釐清，後面任何進階主題都能找到落腳點。

Figure 2.1 — Ansible 五大元素與連線關係
①

Control Node

執行 ansible / ansible-playbook 的機器。需安裝 ansible-core 與 Python 解譯器，2.20 版起最低需 Python 3.12。可以是你的 laptop、CI runner、跳板機、或是 EE 容器。Windows 不能直接當 control node，需透過 WSL。

②

Managed Node

被自動化的目標機器。Linux/Unix 需要 SSH + Python（2.20 起最低 Python 3.9），Windows 需要 WinRM 或 OpenSSH。網路設備例外——透過 network_cli / netconf 連線，遠端不需要任何 Python。

③

Inventory

定義「要管哪些機器」的清單。可以是一個 INI/YAML 檔（static），也可以是動態腳本或外掛（dynamic，如 AWS EC2、K8s pods）。Inventory 同時定義主機分組（groups）與主機/群組變數。

④

Module

實際做事的程式單元，是一段 Python 腳本（或 PowerShell）。Ansible 把它動態傳到 managed node 執行、收回 JSON 結果、自己消失。ansible.builtin.package、ansible.builtin.copy 都是模組。

⑤

Playbook

用 YAML 寫的劇本。一個 Playbook 含一或多個 play；每個 play 指定對哪些 hosts 跑哪些 tasks。這是你日常 95% 時間在寫的東西。

+

輔助：Plugins & Collections

Plugins 擴充引擎本身（callback、connection、filter 等）。Collections 是模組與 plugins 的分發單位，從 Galaxy / Automation Hub 安裝。第 11 章會深入。

⚠ 升級陷阱

當你的 control node 升到 ansible-core 2.20，但有些古老的 RHEL 7 / Ubuntu 18.04 managed node 還在跑 Python 3.6，那邊執行模組會失敗。對策：在 inventory 為這些主機指定較舊的 Python 路徑（ansible_python_interpreter=/usr/bin/python3.6），但長遠仍應升級或淘汰這些主機。

2.2SSH / WinRM 連線模型

Ansible 的 agentless 是在傳輸層 實現的：它不發明新通訊協定、不裝常駐服務，而是借用每台 OS 已經有的東西——Linux 的 SSH、Windows 的 WinRM、網路設備的 SSH/NETCONF。

2.2.2Push 模式 vs Pull 模式

Ansible 預設是 push 模式——control node 主動連到 managed node。但它也支援 pull 模式（ansible-pull），由 managed node 主動拉取 playbook 自己跑，適合超大規模或無法主動連入的場景（例如客戶端裝置）。

Figure 2.2 — Push 與 Pull 兩種運作模式
ⓘ Pull 模式的場景

常見 pull 模式應用：① 防火牆只允許出向流量的環境；② 大量短期主機（auto-scaling 群組成員啟動時自己拉設定）；③ 工作站／桌機管理（員工筆電不開 SSH 入站）。Pull 模式設定方法在第 3 章會展示。

2.3Task 執行流程深入

這是本章最關鍵的一節。執行 ansible-playbook site.yml 後，每個 task 在背後到底發生了什麼？理解這個流程，你才能讀懂 -vvvv 的 verbose 輸出、判斷效能瓶頸、寫出能 debug 的自訂模組。

2.3.1從 Playbook 到 Task：執行引擎的拆解

ansible-core 內部的執行引擎由三個關鍵元件組成（自 v2 起的架構）：

  • TaskQueueManager：總指揮。負責協調 plays 的執行、管理 worker processes、收集結果。
  • PlayIterator：迭代器。負責決定下一個要跑的 task 是哪個，處理 block / rescue / always、handler、條件判斷。
  • Strategy Plugin：策略。決定 tasks 在多 host 之間如何平行。預設 linear（同一個 task 等所有 host 跑完才換下一個 task）；free 模式則讓每個 host 自己跑自己的進度。
Figure 2.3 — Playbook 執行的內部流程

2.3.2Ansiballz：模組是怎麼打包送到遠端的？

當一個 task 要在 managed node 執行 ansible.builtin.package 這類「new-style Python module」時，Ansible 並不是把 Python 程式碼以純文字傳過去那麼簡單。實際機制叫 Ansiballz framework，步驟如下：

  1. Control node 把目標模組原始碼 + 相依的 module_utils 子模組 + 一段 boilerplate（含參數注入），組成一個 ZIP。
  2. 整個 ZIP 用 Base64 編碼，包進一個小 Python wrapper 腳本。
  3. 這個 wrapper 透過 SSH 傳到 managed node。在遠端執行時，wrapper 會：
    • 解 Base64 → 暫存 ZIP 到 ~/.ansible/tmp/
    • 把 ZIP 路徑加入 PYTHONPATH
    • 用 __main__ 名稱 import 真正的模組（讓 Python 認為它是被「執行」而非「import」）
  4. 模組執行完，把結果以 JSON 印到 stdout。Wrapper 退出，回到 control node 解析。
ⓘ 為什麼要這樣搞？

單檔自包含的 ZIP wrapper 解決了三個問題：①相依問題 ——module_utils 在遠端也能找到；②環境隔離 ——不會污染遠端的 site-packages；③跨網路單次傳輸——一次 SSH 帶完，不必往返。代價是：每次 task 執行都要重新打包傳送，這正是 pipelining 要解決的問題。

2.3.3沒有 pipelining 的預設流程（4 次 SSH 操作）

用 ansible-playbook -vvvv 跑一個簡單 task，你會看到類似下面的日誌。預設模式每個 task 需要四次 SSH 操作：

text · -vvvv 輸出（簡化） 
# ① 建立遠端暫存目錄
<web01> ESTABLISH SSH CONNECTION FOR USER: ansible
<web01> SSH: EXEC ssh ... '/bin/sh -c "mkdir -p ~/.ansible/tmp/ansible-tmp-XXX"'

# ② SFTP 傳模組過去
<web01> SSH: EXEC sftp -b - ansible@web01
<web01> PUT /tmp/local-AnsiballZ_package.py TO ~/.ansible/tmp/.../AnsiballZ_package.py

# ③ 設定執行權限
<web01> SSH: EXEC ssh ... '/bin/sh -c "chmod u+x ~/.ansible/tmp/.../AnsiballZ_package.py"'

# ④ 真正執行 + 清掉暫存
<web01> SSH: EXEC ssh ... '/bin/sh -c "/usr/bin/python3 ~/.ansible/tmp/.../AnsiballZ_package.py && rm -rf ..."'

50 個 tasks × 100 hosts × 4 次 SSH ＝ 20,000 次連線操作。光是 SSH handshake 在 LAN 內每次 50–100ms，WAN 上可達 300–500ms，這會吃掉 playbook 執行時間的 50–70%。

2.3.4SSH Pipelining：把 4 次操作壓成 1 次

啟用 pipelining 後，Ansible 不再把模組寫到遠端檔案系統，而是直接把模組原始碼透過 stdin 餵給遠端 Python 解譯器。這把每個 task 的 SSH 操作壓縮到 1 次。

Figure 2.4 — Pipelining 開關前後的 SSH 操作數量對比
ini · ansible.cfg 
# 開啟 pipelining 與持久化 SSH 連線（最常見的兩個性能調校）
[ssh_connection]
pipelining = True
ssh_args  = -o ControlMaster=auto -o ControlPersist=120s
⚠ Pipelining 的常見坑：requiretty

許多 RHEL / CentOS 的 /etc/sudoers 預設有 Defaults requiretty。Pipelining 走的是 stdin pipe 而不是真正 TTY，遇到 requiretty 就會失敗，錯誤訊息：sudo: sorry, you must have a tty to run sudo。對策：移除該設定，或為 ansible 使用者加例外。

2.3.5ControlPersist：複用 SSH 連線

SSH 還有另一個正交優化：ControlPersist。它讓第一次連入後的 SSH master socket 保留在 control node 本機 ~/.ansible/cp/，後續同一主機的連線直接借用，省掉 TCP/TLS handshake。Ansible 預設就會啟用，但可調整持續時間：

ini · ansible.cfg 完整效能組合 
[defaults]
# 預設並行執行的 host 數，預設 5 太少，建議 25–100
forks = 50

# 啟用 fact caching，跨 playbook 重用 facts，省下 setup 時間
fact_caching          = jsonfile
fact_caching_connection = ~/.ansible/factcache
fact_caching_timeout    = 7200

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=10m -o PreferredAuthentications=publickey

# 啟用 transfer_method 自動選擇 sftp/scp，遇到舊系統不會失敗
transfer_method = smart
✓ 效能基準

實測經驗值：開啟 pipelining + ControlPersist（10 分鐘）+ forks=50，相較預設值，在 100 host × 50 task 的 playbook 上大約能拿到 2–3 倍速度，CPU 使用率也下降一半。第 25 章會更深入「大規模執行調校」的細節。

2.4Idempotency 的內部實作

第 1 章說 idempotency 是 Ansible 的核心承諾，但怎麼做到？答案是：每個正規模組必須自己實作三步驟「檢查 → 比較 → 變更」。讓我們拆 ansible.builtin.copy 模組來看。

Figure 2.5 — copy 模組的 idempotency 三步驟

2.4.1用 --check 與 --diff 觀察

Ansible 提供兩個旗標讓你不執行真實變更 也能看到模組的判斷：

  • --check（dry-run / Check Mode）：模組只跑「檢查 + 比較」，到要做變更時跳過，回報「假如執行了會有變化」。
  • --diff（Diff Mode）：對於支援的模組（copy、template、lineinfile 等），把差異內容 也印出來，類似 git diff。
bash · check + diff 實際操作 
# 執行第一次：實際變更，回傳 changed
$ ansible-playbook site.yml
PLAY RECAP ************************
web01    : ok=3  changed=2  unreachable=0  failed=0

# 執行第二次：所有 task 已是 desired state，回傳 ok 但 changed=0
$ ansible-playbook site.yml
web01    : ok=3  changed=0  unreachable=0  failed=0  ← 冪等性驗證

# Check + Diff 模式：不真的改、但顯示「會改什麼」
$ ansible-playbook site.yml --check --diff
--- before: /etc/nginx/nginx.conf
+++ after:  /etc/nginx/nginx.conf
@@ -10,7 +10,7 @@
-worker_processes auto;
+worker_processes 4;
⚠ 並非所有模組都支援 check mode

command 與 shell 模組預設跳過 check mode（因為 Ansible 不知道任意 shell 命令會不會有副作用）。如果你的自訂模組要支援 check mode，必須在程式碼內檢查 module.check_mode 並避開實際變更——這在第 16 章撰寫自訂模組會仔細展開。

2.4.2「changed」與「ok」是模組決定的

常被誤解的點：changed/ok 不是 Ansible 自動判斷的，是模組自己回報的。模組執行完會在 JSON 裡放 "changed": true 或 "changed": false。這帶來兩個推論：

  1. 非冪等模組（command/shell/raw）預設永遠回 changed=true，因為它們不知道命令是否真的改變了什麼。需要用 changed_when: 自定義條件，或 creates: / removes: 控制執行條件。
  2. handlers 由 changed 觸發。第 6 章會展開：handler 只在它監聽的 task 真的 changed 時才執行，這是 Ansible 條件式重啟服務的機制。
yaml · 控制 command 的 changed 行為 
# 用 changed_when 自定義「什麼算改變」
- name: 檢查 service 是否需要重啟
  ansible.builtin.command: /usr/local/bin/needs-restart
  register: restart_check
  changed_when: restart_check.rc == 1  # exit code 1 才算 changed
  failed_when: restart_check.rc > 1   # exit code 0 或 1 都不算 failed

# 用 creates 讓 command 自帶 idempotency
- name: 初始化 DB（只在首次執行）
  ansible.builtin.command: /usr/bin/db-init
  args:
    creates: /var/lib/db/.initialized  # 此檔存在則跳過

2.5Collections 架構（自 2.10 起）

2020 年的 ansible-base 2.10（後改名 ansible-core）做了一個傷筋動骨的改動：把絕大多數模組從主 repo 移到獨立的 Collections。這個架構決策影響了你今天寫 playbook 的所有 import 寫法、CI/CD 流程、版本管理策略。

2.5.12.9 之前 vs 2.10 之後

面向 2.9 及之前 2.10 之後
模組來源 全部在 ansible/ansible monorepo 分散在 100+ 個 Collections
模組命名 短名稱：copy、yum、ec2_instance FQCN：ansible.builtin.copy、amazon.aws.ec2_instance
釋出節奏 Ansible 主版本一起釋出（半年） Collections 獨立釋出（可週級）
安裝套件數 1 個（ansible） 2 種選擇：ansible-core 或 ansible（含 ~85 collections）
第三方擴充 需 PR 進主 repo 自己發 Collection 到 Galaxy

2.5.2FQCN（Fully Qualified Collection Name）

Collection 命名格式為 namespace.collection_name，模組命名為 namespace.collection_name.module_name。範例：

yaml · FQCN 寫法 vs 短名稱 
# ✓ 推薦：完整 FQCN，明確指定來源、避免命名衝突
- name: 安裝 nginx
  ansible.builtin.package:
    name: nginx
    state: present

- name: 建立 EC2 instance
  amazon.aws.ec2_instance:
    name: web-01
    image_id: ami-xxx

# ✗ 不建議：短名稱（仍可用，但有命名衝突風險）
- name: 安裝 nginx
  package:    # 沒寫 namespace，Ansible 會去 collections_path 找第一個 match
    name: nginx
✓ 2026 年的最佳實踐

「新寫的 playbook 與 role 永遠用 FQCN」是業界共識。理由：① 明確、② 程式碼搜尋容易、③ ansible-lint 規則 fqcn 會檢查、④ Automation Controller 在 EE 內可能裝多個有同名模組的 collections，FQCN 是唯一可靠的指定方式。

2.5.3Collection 的查找路徑

當你寫 amazon.aws.ec2_instance 時，Ansible 怎麼找到這個 collection？查找順序如下（前面找到就停）：

  1. Adjacent collections：playbook 旁邊的 collections/ 子目錄
  2. ANSIBLE_COLLECTIONS_PATH 環境變數定義的路徑（多個用 : 分隔）
  3. ~/.ansible/collections/：使用者層級
  4. /usr/share/ansible/collections/：系統層級
  5. 內建：ansible.builtin.*、ansible.legacy.* 在 ansible-core 套件內
bash · collection 操作 
# 列出當前環境裝了哪些 collections
$ ansible-galaxy collection list

# 從 Galaxy 安裝
$ ansible-galaxy collection install amazon.aws

# 安裝特定版本
$ ansible-galaxy collection install amazon.aws:==7.6.0

# 從 requirements.yml 批次安裝（推薦的版本鎖定方式）
$ ansible-galaxy collection install -r requirements.yml

# 查模組屬於哪個 collection
$ ansible-doc -l | grep ec2_instance
yaml · requirements.yml 範例 
# 此檔案放在專案根目錄，CI/CD 透過它鎖定 collection 版本
collections:
  - name: amazon.aws
    version: ">=7.0.0,<8.0.0"
  - name: community.general
    version: "==9.5.0"          # 完全鎖死
  - name: kubernetes.core
    version: ">=4.0.0"

# 也可從非 Galaxy 來源
  - name: git+https://github.com/myorg/private-collection.git
    type: git
    version: main

2.6本章重點回顧

01

五大要素

Control node、managed node、inventory、modules、playbook。架構圖牢記，後續所有章節都圍繞這五個元素的關係展開。

02

Python 雙線政策

2.20 版起 control node 需 Python 3.12+，managed node 需 Python 3.9+。升級時先盤點兩邊版本，舊系統用 ansible_python_interpreter 過渡。

03

Ansiballz + Pipelining

模組以 ZIP+Base64+wrapper 形式 push 到遠端執行。預設每 task 4 次 SSH，啟用 pipelining 後變 1 次 — 這是最重要的單一效能調校。

04

Idempotency 由模組實作

模組自己跑「檢查 → 比較 → 變更」三步、自己回報 changed/ok。command/shell 沒這保證，要用 creates: 或 changed_when: 補強。

05

FQCN 為新標準

2.10 起模組移到 collections，命名為 namespace.collection.module。新 code 永遠寫 FQCN，舊 code 用 ansible-lint 漸進遷移。

06

讀懂 -vvvv

四個 v 才會印出 SSH 細節：mkdir、SFTP PUT、chmod、execute。看見這些代表 pipelining 沒開或無法用——這是 debug 第一層工具。

練習題

  1. 初學者：在你電腦上裝 ansible，跑 ansible localhost -m setup，觀察 Ansible 收集了哪些 facts。再用 -vvvv 跑 ansible localhost -m ping，跟著輸出對照本章 2.3.3 的 4 步驟。
  2. 初學者：用一句話跟同事解釋 changed=0 為什麼是「好消息」（提示：與 idempotency、與目標狀態的關係）。
  3. 開發者：在你的環境啟用 pipelining 與 ControlPersist=10m，用 profile_tasks callback 量測同一個 playbook 開關前後的執行時間，記錄差異。
  4. 開發者：寫一個只用 ansible.builtin.command 模組的 task，搭配 creates: 與 changed_when:，使其重跑時 changed 變為 0。驗證它是否真正具備冪等性。
  5. DevOps / SRE：盤點目前 playbook 中所有非 FQCN 的模組呼叫，用 ansible-lint（規則 fqcn）找出來，評估改寫的工作量與風險。
  6. DevOps / SRE：在 inventory 中為一台舊 RHEL 7 主機加上 ansible_python_interpreter=/usr/bin/python3.6，驗證它能與 ansible-core 2.18 共存（注意：2.20 對舊 Python 已不支援）。
  7. DevOps / SRE：建立 requirements.yml 鎖定你專案用到的所有 collections 版本，並把 ansible-galaxy collection install -r 加入 CI 第一步。

負責決定下一個要執行的 task，處理 block/rescue/always、handler、條件判斷。
Strategy
決定多 host 的平行策略。linear（同步）為預設，free 讓每 host 各跑各的。第 25 章詳述。
Connection Plugin
實作「如何連到 managed node」的外掛。常見：ssh、local、winrm、psrp、network_cli、docker、kubectl。
SSH Pipelining
把模組 stdin pipe 給遠端 Python，省去 SFTP 傳輸與檔案落盤。每 task 從 4 次 SSH 降為 1 次。需注意 requiretty。
ControlPersist
OpenSSH 功能，讓首次連線後的 master socket 保留一段時間，後續連線重用。Ansible 預設啟用、可調整持續時間。
Check Mode
用 --check 啟用的 dry-run 模式。模組只跑檢查、不做實際變更，回報「假如執行會發生什麼」。
Diff Mode
用 --diff 啟用，對支援的模組顯示變更前後的差異，類似 git diff。
changed_when / failed_when
覆寫模組的 changed/failed 判斷，常用於 command/shell 模組讓它具備偽冪等性。
creates / removes
command 模組的兩個參數：指定一個檔案路徑，存在/不存在時跳過執行。讓不可冪等的指令可以條件式執行。
FQCN（Fully Qualified Collection Name）
模組的完整命名 namespace.collection.module。例如 ansible.builtin.copy、amazon.aws.ec2_instance。
ANSIBLE_COLLECTIONS_PATH
環境變數，控制 collection 的查找路徑。多個路徑用 : 分隔。
