第 29 章 — 故障排查與除錯

第六篇收尾章。前 5 章教你怎麼正確做事；本章教你事情出錯時怎麼快速定位。Ansible 的 stack 跨控制端 / SSH / Python / 遠端模組——故障可能藏在五個層次之間。本章建立系統化排查流程：① 除錯心智模型——從哪邊開始查；② verbosity 四級—— -v / -vv / -vvv / -vvvv 各看什麼；③ debug 模組——精確 inspect 變數；④ dry-run 三件套—— --check / --diff / --syntax-check；⑤ 互動 debugger——失敗時不退出、現場 fix；⑥ 常見錯誤分類——連線 / 認證 / Jinja2 / module / SELinux 五大類；⑦ 效能瓶頸找法—— profile_tasks / async / 並行；⑧ SOS report 收集——回報 bug 給 Anthropic / Red Hat 用；⑨ 業界除錯紀律。讀完這章你會看到 FAILED! 不會慌——能在 5 分鐘內定位是哪層、為什麼、怎麼修。

本章是第六篇 SRE 實戰收尾 — 從預防（前 6 章）轉到應變
初學者必讀（29.1–29.4 心智模型 + 基本工具） 開發者必讀（特別 29.5 debugger + 29.6 錯誤分類） DevOps / SRE 必讀（全章 — 排查紀律）

29.1除錯心智模型

看到紅字第一反應不該是「重跑試試」。Ansible 失敗有五個可能來源，按發生順序排查最快。

29.1.1五層排查模型

Figure 29.1 — Ansible 故障的五個層次（由近到遠排查）

29.1.2排查步驟

①

看完整錯誤訊息

不要只看「FAILED!」。完整訊息含 module_stderr / msg 欄位通常已有答案。讀整段 JSON。

②

看是哪個 task 哪個 host

多 host run 時看 host name。可能只是某一台特例（連線 / 設定異常）。

③

適度 verbose

從 -v 開始加。-vvv 才看連線細節、-vvvv 看 SSH 協定。不是越多越好——資訊太多反而難找。

④

用 debug 模組鎖定

在可疑變數附近加 debug: var: xxx。比 verbose 精準。

⑤

--start-at-task 跳到出錯點

已知哪個 task 失敗時用。免重跑前面所有成功的 task。

⑥

單獨手動驗證

SSH 進 host 手動跑 task 對應命令。確認是 Ansible 問題還是環境問題。

29.2verbosity 四級

29.2.1四級對照

等級flag看到什麼用於
1 -v task 結果 + module 輸出 哪個 task 為何失敗
2 -vv + 輸入參數 變數有沒有正確展開
3 -vvv + 連線細節 / Python interpreter / 暫存路徑 連線 / 認證 / 權限問題
4 -vvvv + raw SSH 命令 / plugin 內部 SSH 協定層、custom plugin 除錯
ⓘ 從低到高漸進

不要一開始就 -vvvv——資訊洪水反而擋住關鍵訊息。建議：① 先 -v 看 task 失敗原因；② 變數沒展開對 → -vv；③ 連線 / 認證 → -vvv；④ -vvvv 留給 plugin 開發或 SSH 協定 debug。

29.2.2verbose 也能控制 debug 模組

yaml · debug 模組的 verbosity 選項 
# 預設 — 永遠顯示
- ansible.builtin.debug:
    msg: "處理 {{ inventory_hostname }}"

# 只在 -v 時顯示
- ansible.builtin.debug:
    msg: "trace info"
    verbosity: 1

# 只在 -vv 時顯示（細節 vars dump）
- ansible.builtin.debug:
    var: hostvars[inventory_hostname]
    verbosity: 2

# 跑：
# ansible-playbook play.yml          # 只看第一個
# ansible-playbook play.yml -v       # 看前兩個
# ansible-playbook play.yml -vv      # 三個都看

29.3debug 模組精準 inspect

29.3.1三大用法

yaml · debug 模組三種寫法 
# 用法 1: var — 印變數值
- ansible.builtin.debug:
    var: my_variable

# 用法 2: msg — 印訊息（含 Jinja2 展開）
- ansible.builtin.debug:
    msg: "App {{ app_name }} 部署到 {{ inventory_hostname }}"

# 用法 3: 多行訊息
- ansible.builtin.debug:
    msg: |
      Host: {{ inventory_hostname }}
      IP:   {{ ansible_default_ipv4.address }}
      OS:   {{ ansible_distribution }} {{ ansible_distribution_version }}
      RAM:  {{ ansible_memtotal_mb }}MB

29.3.2register 看 task 結果

yaml · register + debug 看 task 完整輸出 
- name: 跑命令並 register 結果
  ansible.builtin.command: df -h /
  register: df_out
  changed_when: false

- name: 看完整結構（rc / stdout / stderr / start / end / delta）
  ansible.builtin.debug:
    var: df_out

# 輸出範例：
# df_out:
#   changed: false
#   cmd: [df, -h, /]
#   rc: 0
#   start: '2026-05-08 10:30:01'
#   end: '2026-05-08 10:30:01'
#   delta: '0:00:00.012345'
#   stdout: 'Filesystem  Size  Used Avail ...'
#   stderr: ''
#   stdout_lines: [...]

# 只看特定欄位
- ansible.builtin.debug:
    var: df_out.stdout_lines

29.3.3常用 debug 變數

變數看到什麼
vars當前 task 範圍內所有變數
hostvars[inventory_hostname]當前 host 所有 facts + 變數
ansible_factsgather_facts 的所有 OS/硬體 facts
group_names當前 host 屬於哪些 group
groups整個 inventory 的 group → host 對應
play_hosts當前 play 涵蓋的 host list

29.4dry-run 三件套

29.4.1三個必學選項

選項做什麼用於
--syntax-check 只檢查 YAML 語法 commit 前 sanity check
--check dry-run — 不真改 看「會改什麼」（敏感環境必用）
--diff 顯示檔案 / template 變更前後 config 變更 review
bash · 經典三連發 
# 1) 先 syntax check（毫秒級）
$ ansible-playbook site.yml --syntax-check

# 2) dry-run + diff — 完整看會改什麼
$ ansible-playbook site.yml --check --diff

# 範例輸出：
# TASK [Configure nginx] *********
# --- before: /etc/nginx/sites-available/default
# +++ after: dynamically generated
# @@ -1,3 +1,4 @@
# server {
#     listen 80;
# +    server_name myapp.example.com;
#     root /var/www/html;

# 3) 限制 task 範圍 — debug iteration 加速
$ ansible-playbook site.yml --check --diff --tags nginx
$ ansible-playbook site.yml --check --diff --start-at-task "Deploy app"

29.4.2--step 互動逐步執行

bash · --step 模式 — 每 task 確認一次 
$ ansible-playbook site.yml --step

# 每個 task 之前會問：
# Perform task: TASK: Install nginx (y/n/c): 
#   y — 跑這個
#   n — 跳過
#   c — 繼續且不再問（取消 step 模式）

# 用途：第一次跑某 playbook、想逐步確認；事後 diff 太晚的場景

29.5互動 task debugger

最強大但最少用的工具。task 失敗時不退出，停在現場讓你 inspect / fix / re-run。等同 IDE 的 breakpoint。

29.5.1三種啟用方式

yaml · 三種啟用 debugger 的方式 
# 方式 1: task / play / role 級別 keyword（最精準）
- name: 可疑 task
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/app/config.yml
  debugger: on_failed     # 失敗時進 debugger
  # 選項：always / never / on_failed / on_unreachable / on_skipped


# 方式 2: ansible.cfg 全域
# [defaults]
# enable_task_debugger = True


# 方式 3: 整個 play 用 debug strategy（每個失敗都進 debugger）
- name: debug 整個 play
  hosts: webservers
  strategy: debug
  tasks:
    - ansible.builtin.command: /bin/false

# 命令列：
# ANSIBLE_STRATEGY=debug ansible-playbook play.yml

29.5.2debugger 互動 prompt 命令

命令做什麼
p task印當前 task 物件
p task.args印 task 的 module 參數（看實際傳了什麼）
p task_vars印該 task 範圍內所有變數
p task_vars['my_var']印特定變數
task.args['arg'] = value修改 task 參數（試新值）
task_vars['x'] = value修改變數
r / redo用更新後的參數 / 變數重跑該 task
c / continue繼續往下個 task
q / quit放棄 playbook
h / help列所有命令

29.5.3實際 debugger session

text · 實際 debugger 對話 — 查 typo 變數 
TASK [Deploy config from template] *********
fatal: [web-01]: FAILED! => {
    "msg": "AnsibleUndefinedVariable: 'app_vesion' is undefined"
}
Debugger invoked
(debug) p task.args
{'src': 'app.conf.j2', 'dest': '/opt/myapp/config.yml'}

(debug) p task_vars['app_version']
'2.5.1'

# 啊 — 變數叫 app_version、template 寫成 app_vesion typo
# 暫時 workaround 讓 playbook 跑完
(debug) task_vars['app_vesion'] = task_vars['app_version']

(debug) redo
ok: [web-01]
# Task 過了，繼續往下

# 真正修法：去 template 改 typo
(debug) c

29.6常見錯誤五大類

29.6.1錯誤分類速查

🔌

連線錯誤

UNREACHABLE / Connection refused / timed out。網路、SSH service、firewall 三大可能。

🔑

認證錯誤

Permission denied / Authentication failure。SSH key / password / sudo 設定。

📝

Jinja2 錯誤

UndefinedError / TemplateSyntaxError。typo / 變數沒設 / 嵌套展開錯。

⚙

Module 錯誤

Python 缺套件、API 認證錯、檔案權限不足、host 不支援該 module。

🛡

SELinux / AppArmor

看似 root 也不能寫某檔案 — Linux MAC 機制擋下。RHEL / Fedora 常踩。

29.6.2連線錯誤排查

bash · 連線錯誤排查 checklist 
# 1) ICMP 通嗎
$ ping web-01

# 2) SSH port 開嗎
$ nc -zv web-01 22
# Connection to web-01 22 port [tcp/ssh] succeeded!

# 3) 手動 SSH 試
$ ssh -vvv deploy@web-01

# 4) Ansible ad-hoc ping（最低層測試）
$ ansible web-01 -m ping -vvv

# 5) 看 known_hosts 有沒有 stale entry
$ ssh-keygen -R web-01

# 6) Ansible host_key_checking 暫時關（lab only）
$ ANSIBLE_HOST_KEY_CHECKING=False ansible-playbook site.yml

29.6.3認證錯誤排查

bash · 認證錯誤檢查清單 
# SSH key 對嗎
$ ssh-add -l                              # 看 agent 有什麼 key
$ ansible-playbook site.yml --private-key=~/.ssh/specific_key

# key 權限對嗎（必須 600）
$ chmod 600 ~/.ssh/id_rsa
$ chmod 700 ~/.ssh

# Sudo 密碼？
$ ansible-playbook site.yml --ask-become-pass

# 用 password 而非 key（lab）
$ ansible-playbook site.yml --ask-pass

# 看 inventory 的認證設定
$ ansible-inventory --host web-01 -i inventory/

29.6.4Jinja2 錯誤

yaml · 三大常見 Jinja2 陷阱 
# 陷阱 1: undefined 變數 — 用 default 防呆
# ❌ {{ app_version }}              — 沒設就 fail
# ✓  {{ app_version | default('latest') }}


# 陷阱 2: 嵌套變數 — 用 vars 字典
# ❌ {{ {{ env }}_db_password }}     — Jinja2 不支援雙層
# ✓  {{ vars[env + '_db_password'] }}


# 陷阱 3: 字串 vs 數字
- ansible.builtin.assert:
    that:
      # ❌ "{{ port == 8080 }}"            — 比錯
      - "port | int == 8080"            # ✓ 顯式轉型


# 陷阱 4: list / dict 操作
- ansible.builtin.debug:
    # 取 list 第一個
    msg: "{{ my_list | first }}"

    # 取 dict 的 key
    # msg: "{{ my_dict.keys() | list }}"

    # 連接 list
    # msg: "{{ list_a + list_b }}"

    # filter
    # msg: "{{ ports | select('match', '^8') | list }}"

29.6.5SELinux 陷阱

⚠ RHEL / Fedora SELinux 必踩

「root 也寫不進 /var/www 某些路徑」這類詭異情況通常是 SELinux。檢查：① getenforce 看是否 enforcing；② ls -Z file 看 SELinux context；③ audit2allow -a 解析 audit log 找原因；④ 用 community.general.sefcontext + file: state: file 在 Ansible 設 context 而不是手動關 SELinux。

29.7找效能瓶頸

「跑得慢」也是 bug。Ch25 介紹了 forks / fact_caching 等預防；本節給已經慢了怎麼定位的方法。

29.7.1profile_tasks callback

bash · 啟用 profile 看誰最慢 
# 命令列暫時開
$ ANSIBLE_CALLBACKS_ENABLED="timer,profile_tasks,profile_roles" \
    ansible-playbook site.yml

# ansible.cfg 永久開
# [defaults]
# callbacks_enabled = timer, profile_tasks, profile_roles

# 跑完輸出尾段（top 慢 task）：
# =============================================================================
# Run system updates  ----------------------- 215.32s
# Install dependencies  --------------------- 88.45s
# Configure nginx  -------------------------- 12.10s
# ...
# Playbook run took 0 days, 0 hours, 5 minutes, 30 seconds

29.7.2常見效能瓶頸與解法

症狀原因解法
Gathering Facts 慢 每次 run 都重 gather fact_caching = jsonfile/redis + gathering = smart
SSH 重複 handshake 沒開 ControlPersist ssh_args = -o ControlPersist=60s
每 task 都是新 SSH 沒開 pipelining pipelining = True
單一 task 鎖整 play 等 linear strategy 用 async + poll / 換 strategy: free
並行不足 forks 太低（預設 5） 提到 50–100
整體 task 太多 該 cache 的沒 cache 把不必每次跑的 task 加 tags 或 when 條件

29.7.3async 跑長 task

yaml · async 不阻擋整 play 
# 跑可能很久的 task — 不阻擋
- name: 執行緩慢更新
  ansible.builtin.shell: /opt/myapp/long_running_migration.sh
  async: 3600             # 最多 1 小時
  poll: 10                # 每 10 秒 poll 一次

# fire-and-forget — 完全不等
- ansible.builtin.shell: /opt/myapp/cleanup.sh
  async: 0
  poll: 0

# 之後查狀態
- ansible.builtin.async_status:
    jid: "{{ result.ansible_job_id }}"
  register: job_status
  until: job_status.finished
  retries: 30
  delay: 10

29.8SOS report — 回報 bug

確定是 Ansible 本身 bug 時，要附完整環境資訊回報。

bash · 收集 bug report 資訊 
# 1) 版本資訊
$ ansible --version
$ ansible-config dump --only-changed       # 看你改過哪些設定

# 2) Collection / role 版本
$ ansible-galaxy collection list
$ ansible-galaxy role list

# 3) 最小可重現範例（minimal reproducer）
#    把問題減到最簡單還能重現的 playbook + inventory

# 4) 完整 verbose log
$ ansible-playbook reproducer.yml -vvv 2>&1 | tee bug.log

# 5) 系統資訊（remote host 端）
$ uname -a
$ python3 --version

# 6) RHEL 用 sosreport — 完整系統 dump
$ sudo sosreport --all-logs                # 商業環境 RH support 必要

# 把 1-5 整理進 GitHub issue / Red Hat support ticket

29.9業界除錯紀律

①

讀完整錯誤訊息

不要只看第一行。module_stderr / stderr / msg 通常已含答案。讀整段 JSON。

②

從低 verbose 漸進

-v → -vv → -vvv。一開始就 -vvvv 是資訊洪水。每升一級看是否答案在這。

③

-vv 看變數展開

「為何變數值不對」是常見問題。-vv 看到 module 真實收到的 args。比腦補快。

④

--check --diff 改動先看

對 prod 永遠先 --check --diff dry-run。不確定就不要 apply。

⑤

--start-at-task 加速迭代

反覆 debug 同個 task 時用，不必重跑前面成功的部分。

⑥

debugger 處理 typo / 變數錯誤

debugger: on_failed 比每次「改 → 重跑」快。直接在現場改 task_vars + redo。

⑦

SSH 連線層自己手動驗

排除 Ansible 因素 — 直接 ssh -vvv user@host 試。能進去再回 Ansible 排查。

⑧

profile_tasks 找慢瓶頸

不要憑感覺優化。先測量 top 5 慢 task、再決定 cache / async / 拆分等手段。

練習題

  1. 初學者：故意寫一個會失敗的 task（如 copy 不存在的檔案）。分別用 -v、-vv、-vvv 跑、比較三層輸出差異。
  2. 初學者：對某 host 寫 5 個 debug task — 印 inventory_hostname / OS / IP / RAM / 所屬 groups。確認都能正常展開。
  3. 初學者：用 --check --diff 對某 playbook 跑 dry-run。觀察 diff 顯示的 template 變更前後。
  4. 開發者：故意製造變數 typo（template 寫 app_vesion），開啟 debugger: on_failed。在 debugger 互動 prompt 用 task_vars 修復、redo 通過。
  5. 開發者：故意關掉某 host 的 SSH service，跑 ansible ad-hoc ping。一步步用 ping / nc / ssh -vvv 確認問題定位。
  6. 開發者：對某個跑很慢的 playbook 開 profile_tasks。找出 top 3 慢 task、寫一頁分析（為什麼慢、改善方法）。
  7. DevOps / SRE：寫個「Ansible debugging cheatsheet」內部文件 — 列你團隊最常見的 5 個 Ansible 錯誤模式 + 各自的排查 SOP。
  8. DevOps / SRE：對某長 task（如 system update）改用 async + async_status。比較同步 vs async 的整體 playbook 耗時。
  9. DevOps / SRE：模擬 SELinux 檔案無法寫入問題 — 在 RHEL 上設 enforcing、寫個 task 寫到非標準路徑、觀察錯誤、用 community.general.sefcontext 修復。寫成 incident 報告。

本章詞彙表

五層排查模型
控制端（YAML / 變數）→ 連線層（SSH）→ Python interpreter → 模組執行 → 業務邏輯。Ansible 故障可能藏在任一層，由近到遠排查最快。
Verbosity flag (-v / -vv / -vvv / -vvvv)
四級 verbose。1 = task 結果；2 = + 輸入參數；3 = + 連線細節；4 = + raw SSH 命令。從低到高漸進。
debug 模組
ansible.builtin.debug。用 var（印變數）、msg（印訊息）、verbosity（控制顯示等級）三選項。
register 與 task result
register: x 後 x 含 rc / stdout / stderr / start / end / delta / changed 等欄位。debug task 看完整結構。
--syntax-check
只檢 YAML 語法，毫秒級。commit 前快速 sanity。
--check
dry-run。不真的對 host 改任何東西。配 --diff 看具體變更。生產敏感操作必先跑。
--diff
顯示 template / config 檔案變更前後內容。配 --check 看會改什麼、不變更狀態。
--step
互動逐步執行。每 task 執行前問 y/n/c。新 playbook 第一次跑時用。
--start-at-task
從指定名稱的 task 開始跑。--start-at-task "Deploy app"。debug 反覆同 task 時加速。
--tags / --skip-tags
限制只跑 / 跳過某 tag 的 task。重 debug 用。
debugger keyword
task / play / role 級別選項。debugger: on_failed 失敗時進 debugger。值：always / never / on_failed / on_unreachable / on_skipped。
strategy: debug
play 級別 strategy。每 task 失敗自動進 debugger。整 play 都需 debug 時用。
debugger 互動命令
p task / p task.args / p task_vars / r redo / c continue / q quit / h help。在 prompt 用。
task.args 修改
debugger 內 task.args['arg'] = value 修改 task 參數。redo 用新值重跑。
task_vars 修改
debugger 內 task_vars['x'] = value 修改變數。處理 typo 變數的 workaround。
UNREACHABLE
Ansible 連不上 host 的錯誤類別（與 FAILED 不同）。網路 / SSH / firewall 三大可能。
UndefinedError (Jinja2)
變數沒定義就引用。預防：| default('x')、strict_undefined 配置。
SELinux context
RHEL / Fedora 的 MAC 標籤。ls -Z 看；community.general.sefcontext 用 Ansible 設。寫不進某路徑常因 context 不對。
audit2allow
解析 SELinux audit log 找出被擋原因，產生對應 policy 建議。ausearch -m avc | audit2allow。
profile_tasks callback
內建 callback。playbook 結尾列出 top N 慢 task。優化前必開。callbacks_enabled = profile_tasks。
profile_roles callback
類似 profile_tasks 但以 role 為單位。看哪個 role 整體耗時。
async + poll
長 task 不阻擋 play 的方式。async: 3600 最大時長、poll: 10 每 10 秒檢查。poll: 0 = fire-and-forget。
async_status 模組
查 async task 完成狀態。register + until: job.finished + retries 配合。
ANSIBLE_DEBUG
環境變數。=1 開啟 Ansible 內部 debug 訊息（比 -vvvv 還詳細）。回報 bug 才用。
ANSIBLE_KEEP_REMOTE_FILES
環境變數。=1 保留遠端暫存檔（預設執行完刪）。debug 模組執行細節用。
SOS report
RHEL 系統的整體 dump 工具（sosreport）。回報 Red Hat support 用。商業環境必備。
ansible-config dump --only-changed
列出你改過的 Ansible 設定（與預設不同的）。回報 bug 時提供。
Minimal reproducer
把問題減到最簡單還能重現的 playbook + inventory。回報 bug 的關鍵 — 沒這個 maintainer 重現不了。
