第 13 章 — Vault 進階

前面章節提及多次「secret 一律進 vault」。本章把 ansible-vault 系統性講清楚——AES-256 加密引擎、檔案 vs 字串兩種粒度、單一 vault password 入門到 multi-environment vault IDs、密碼來源（prompt / file / 環境變數 / client script）、CI/CD 整合模式、以及進階主題：rekey 密碼輪替、與外部 secret manager（HashiCorp Vault / AWS Secrets Manager）的整合策略。Vault 是 Ansible 內建的「夠用就好」secret 解決方案——零基礎設施、AES-256 加密、git 友善——但真正的安全來自於密碼管理流程，本章重點放在那。

本章覆蓋官方文件對應：Ansible Vault Guide · Encrypting Content
初學者必讀（13.1–13.4） 開發者必讀（全章） DevOps / SRE 必讀（特別 13.6 multi-vault、13.7 CI/CD 與 13.9 外部 secret manager 整合）

13.1為什麼需要 Vault？

Ansible 專案最敏感的「秘密三件套」幾乎都會出現在 git repo 裡：

🔑

連線憑證

SSH private keys、ansible_password、API token、cloud provider credentials。一旦洩漏 = 整個基礎設施失守。

🔐

應用密碼

DB password、Redis password、admin user passwords。寫死在 group_vars 等於把生產 DB 密碼公開。

📜

TLS 私鑰

HTTPS certificate 的 private key 部分絕對不能進 git plaintext。Vault 加密後可以安心放 repo。

13.1.1Vault 的核心提案

ⓘ Vault 的提案

「用一個密碼加密 secret，把加密後的內容放 git」。Ansible 跑 playbook 時提供解密密碼，Ansible 自動解密讀取。整個流程對 git 友善、對 diff 友善、對程式員流暢。底層是 AES-256 加密，密碼學上夠強——剩下就看你怎麼管理那把密碼。

13.1.2能加密什麼？

粒度用法場景
整檔加密 ansible-vault encrypt vars/secrets.yml vars 檔全部都是 secret、TLS 私鑰檔案、SSH key 檔案
單字串加密 ansible-vault encrypt_string 10 個變數中只有 1-2 個是 secret，其他保持 plaintext 可讀

13.2檔案層級加密

13.2.1建立加密檔案

bash · ansible-vault create 
# 從零建立加密檔（會打開編輯器）
$ ansible-vault create group_vars/production/vault.yml
# New Vault password: ●●●●●●●●●
# Confirm New Vault password: ●●●●●●●●●
# [編輯器打開 — 在裡面寫 yaml，存檔後自動加密]

# 寫進去的內容範例：
# vault_db_password: "SuperSecret123!"
# vault_api_key: "sk-abc123def456"

13.2.2加密既有檔案

bash · 對既存檔案加密 
# 把現有 plaintext 檔加密（會就地覆寫）
$ ansible-vault encrypt vars/database.yml

# 同時加密多個
$ ansible-vault encrypt vars/db.yml vars/redis.yml vars/jwt.yml

# 看內容（不修改）
$ ansible-vault view vars/database.yml

# 編輯（自動解密 → 編輯 → 重新加密）
$ ansible-vault edit vars/database.yml

# 永久解密（謹慎使用）
$ ansible-vault decrypt vars/database.yml

⚠ Diff 不友善是檔案加密的限制

整檔加密後，git diff 看到的是「整大塊 hex 字串改變」，看不出實際改了什麼。對需要 review 的場景（如改 production 設定）這是缺點。解法：用「字串級加密」（13.3 節）讓 plain 部分仍可 diff。

13.3字串層級加密 — encrypt_string

把 vars 檔大部分維持 plaintext，只把少數 secret 值用 !vault tag 包成加密字串內嵌進去。Diff 友善，可讀性高。

13.3.1產生加密字串

bash · encrypt_string 三種寫法 
# 方式 ① 直接傳值（會出現在 shell history — 不推薦）
$ ansible-vault encrypt_string 'SuperSecret123!' --name 'db_password'

# 方式 ② 從 stdin（推薦，不留 shell history）
$ ansible-vault encrypt_string --stdin-name 'db_password'
# Reading plaintext input from stdin. (ctrl-d to end input):
# SuperSecret123!  ← 輸入後 Ctrl-D 結束

# 方式 ③ 從變數展開（CI 場景）
$ echo -n "$DB_PASSWORD" | ansible-vault encrypt_string --stdin-name 'db_password'

13.3.3整檔 vs 字串加密的選擇

面向整檔加密字串加密
Git diff 可讀否是（明文部分）
Code review 友善否是
整批 rekey 換密碼支援 rekey否（要逐個重加密）
適合場景檔內所有內容都是 secret少數 secret 混在大量 plain 設定中
業界推薦vault.yml 純 secret 檔secret 不多時的權衡選擇

13.4業界推薦：vars + vault 雙檔模式

整檔與字串加密各有優劣，業界最普遍的折衷模式是「明文 vars 引用加密 vault」。

13.4.1結構

text · 雙檔結構 
inventories/production/group_vars/all/
├── main.yml          # 明文 — 引用 vault_ 變數
└── vault.yml         # 整檔加密 — 含 vault_X 開頭的真實密碼

13.4.2main.yml — 明文，引用 vault

yaml · group_vars/all/main.yml 
---
# 明文檔 — 完整可讀，git diff 友善
db_host: db.production.internal
db_port: 5432
db_user: appuser
db_password: "{{ vault_db_password }}"      # ← 引用 vault

api_endpoint: https://api.example.com
api_key: "{{ vault_api_key }}"                # ← 引用 vault

jwt_secret: "{{ vault_jwt_secret }}"           # ← 引用 vault

13.4.3vault.yml — 整檔加密的 secret 來源

yaml · group_vars/all/vault.yml（解密後內容） 
---
# 整檔加密 — 業界慣例所有變數加 vault_ 前綴
vault_db_password: "SuperSecret123!"
vault_api_key: "sk-abc123def456789"
vault_jwt_secret: "my-very-long-jwt-secret-key-2026"
✓ 為何這個模式是業界共識

① main.yml 完整可讀——code review 看得到所有設定的「形狀」（哪些 var 從哪來、引用什麼 vault）；② vault.yml 統一管理——所有 secret 集中、整批 rekey 容易；③ 命名隔離清晰——vault_ 前綴讓變數歸屬一目瞭然；④ 輪替友善——換密碼時只要重 rekey vault.yml 即可。

13.5密碼來源：四種方式

跑 playbook 時 Ansible 怎麼拿到 vault password？四種方式，從互動到全自動。

13.5.1四種來源對照

來源命令列場景
互動 prompt --ask-vault-pass 本地手動執行
密碼檔 --vault-password-file ~/.vault_pass 本地常用、CI 寫入暫存檔
環境變數 ANSIBLE_VAULT_PASSWORD_FILE 環境變數 本地預設、CI 場景
Client script --vault-password-file ./get-pass.sh 從 keyring / 1Password / HashiCorp Vault 等動態取

13.5.2密碼檔（最常用）

bash · 密碼檔設定 
# 1) 建立密碼檔（單行純文字）
$ echo 'MyVaultPassword2026' > ~/.vault_pass
$ chmod 600 ~/.vault_pass        # 嚴格權限

# 2) 用法
$ ansible-playbook site.yml --vault-password-file ~/.vault_pass

# 3) 在 ansible.cfg 設預設
#    [defaults]
#    vault_password_file = ~/.vault_pass
⚠ 絕不把密碼檔進 git

密碼檔絕對不能進 git repo（這樣等於把 vault 解密能力公開）。.gitignore 必加：

gitignore · .gitignore 
# Vault 密碼檔 — 永遠別進 git
.vault_pass
.vault_pass.txt
*.vault_pass
.ansible-vault-pass

13.5.3Client script — 動態密碼來源

bash · ./scripts/get-vault-pass.sh — 從 macOS keychain 取 
#!/usr/bin/env bash
# 一個簡單的 client script — 從 macOS keychain 取 vault password
security find-generic-password \
    -a "$USER" \
    -s "ansible-vault-prod" \
    -w # 直接印密碼到 stdout

# Linux 可用 secret-tool（GNOME keyring）：
# secret-tool lookup ansible vault-prod

# 或從 1Password CLI：
# op item get "Ansible Vault Prod" --fields password
bash · 使用 
$ chmod +x scripts/get-vault-pass.sh
$ ansible-playbook site.yml --vault-password-file scripts/get-vault-pass.sh

# Ansible 把這個 file 偵測為「executable」就當 script 跑，吃 stdout 第一行當密碼

13.6Multi-Vault：環境隔離

單一密碼適合小團隊或單一環境。一旦你有 dev / staging / production 多環境，應該每個環境用不同密碼——這樣 dev 工程師拿到的密碼洩漏，production 仍然安全。

13.6.1Vault ID 概念

ⓘ Vault ID 是「密碼的標籤」

每個加密 vault 可以加一個 vault ID label（如 dev、prod）。Header 會記錄 $ANSIBLE_VAULT;1.2;AES256;prod。執行時提供多個 vault password 與對應 ID，Ansible 用 ID 找對的密碼解密。

13.6.2用不同 ID 加密

bash · 多環境加密 
# 建立 dev 環境的 vault（用 dev 密碼）
$ ansible-vault create --vault-id dev@prompt \
    inventories/dev/group_vars/all/vault.yml

# 建立 prod 環境的 vault（用 prod 密碼）
$ ansible-vault create --vault-id prod@prompt \
    inventories/production/group_vars/all/vault.yml

# 從密碼檔來源（無互動）
$ ansible-vault encrypt --vault-id prod@~/.vault_pass_prod \
    inventories/production/group_vars/all/vault.yml

# 加密字串時也帶 ID
$ ansible-vault encrypt_string --vault-id prod@prompt \
    --stdin-name 'vault_db_password'

13.6.3跑 playbook — 提供多 vault

bash · 同時提供 dev + prod 密碼 
# 跑會接觸 dev 與 prod vault 的 playbook
$ ansible-playbook site.yml \
    --vault-id dev@~/.vault_pass_dev \
    --vault-id prod@~/.vault_pass_prod

# Ansible 看到 vault 含 ID 標籤就用對應密碼解
# 不含 ID 的舊 vault 會逐一試所有密碼

# 嚴格模式 — 強制 ID 必須匹配（避免錯把 dev 密碼用在 prod vault）
$ export ANSIBLE_VAULT_ID_MATCH=true
$ ansible-playbook site.yml --vault-id prod@~/.vault_pass_prod

13.7CI/CD 整合

互動 prompt 在 CI 不可行。CI 必須用密碼檔或環境變數方式。

13.7.1GitHub Actions 範例

yaml · .github/workflows/deploy.yml 
name: Ansible Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install Ansible
        run: pip install ansible

      - name: Write vault password
        env:
          VAULT_PASSWORD: ${{ secrets.ANSIBLE_VAULT_PROD_PASS }}
        run: |
          echo "$VAULT_PASSWORD" > /tmp/.vault_pass
          chmod 600 /tmp/.vault_pass

      - name: Deploy
        run: |
          ansible-playbook -i inventories/production site.yml \
            --vault-password-file /tmp/.vault_pass

      - name: Cleanup
        if: always()
        run: rm -f /tmp/.vault_pass

13.7.2GitLab CI 範例

yaml · .gitlab-ci.yml 片段 
deploy_production:
  stage: deploy
  script:
    - echo "$ANSIBLE_VAULT_PROD" > /tmp/.vault_pass
    - chmod 600 /tmp/.vault_pass
    - ansible-playbook -i inventories/production site.yml --vault-password-file /tmp/.vault_pass
  after_script:
    - rm -f /tmp/.vault_pass
  variables:
    ANSIBLE_VAULT_PROD: ${ANSIBLE_VAULT_PROD}      # GitLab CI/CD variable (masked)
⚠ 暫存密碼檔的安全細節

① 用 chmod 600 限制只有 owner 能讀；② after_script / cleanup 步驟一定要清掉；③ Job 失敗也要清，if: always()；④ 別把 password echo 到 log 中（set +x 或不要 print）。

13.8Rekey — 密碼輪替

密碼學最佳實踐是定期換密碼。Ansible vault 的 rekey 命令支援這個。

13.8.1單一密碼換新

bash · rekey 簡單情境 
# 互動式
$ ansible-vault rekey vars/secrets.yml
# Vault password: ●●●● (舊密碼)
# New Vault password: ●●●●● (新密碼)
# Confirm New Vault password: ●●●●●

# 一次 rekey 多個
$ ansible-vault rekey vars/dev.yml vars/staging.yml vars/prod.yml

# 從檔案來源（無互動）
$ ansible-vault rekey vars/secrets.yml \
    --vault-password-file ~/.vault_pass.old \
    --new-vault-password-file ~/.vault_pass.new

13.8.2含 vault ID 的 rekey

bash · rekey 多環境 
# 把 prod 環境 vault rekey 到新密碼
$ ansible-vault rekey \
    --vault-id prod@~/.vault_pass_prod_old \
    --new-vault-id prod@~/.vault_pass_prod_new \
    inventories/production/group_vars/all/vault.yml

# 也可以把 ID 一起換（從 prod_v1 換到 prod_v2）
$ ansible-vault rekey \
    --vault-id prod_v1@~/.vault_pass_v1 \
    --new-vault-id prod_v2@~/.vault_pass_v2 \
    inventories/production/group_vars/all/vault.yml
⚠ encrypt_string 字串無法 rekey

rekey 只能對整檔加密的 vault 做。!vault 內嵌字串得逐一手動重新 encrypt_string。這也是「整檔加密 vs 字串加密」抉擇的考量點之一。

13.9外部 Secret Manager 整合

Ansible Vault 是內建、零基礎設施的 secret 解法。但企業規模或合規要求高的場景常需要更專業的 secret manager。

13.9.1對照

面向Ansible VaultHashiCorp VaultAWS Secrets Manager
成本免費免費 / 商業每秘密付費
整合內建community.hashi_vaultamazon.aws collection
動態 secret否支援（DB credentials 自動產生）支援（rotation）
稽核 log否是是
權限模型密碼分群policy-basedIAM
適合小團隊、簡單環境大型團隊、複雜權限AWS-native

13.9.2HashiCorp Vault 整合範例

yaml · 用 community.hashi_vault lookup 
- name: 從 HashiCorp Vault 取 DB password
  community.postgresql.postgresql_user:
    name: appuser
    password: "{{ lookup('community.hashi_vault.vault_kv2_get', 'secret/database', url='https://vault.internal:8200').secret.password }}"
  # Ansible 在 control node 即時連 HashiCorp Vault 取值
  # 不寫進任何 git 檔案，secret 流動全程加密

13.9.3AWS Secrets Manager 整合

yaml · 用 amazon.aws lookup 
- name: 從 AWS Secrets Manager 取 secret
  ansible.builtin.set_fact:
    db_credentials: "{{ lookup('amazon.aws.aws_secret', 'prod/db/credentials') | from_json }}"

- name: 用取到的 secret
  community.postgresql.postgresql_db:
    login_user: "{{ db_credentials.username }}"
    login_password: "{{ db_credentials.password }}"
    name: myapp

13.9.4混合策略：Vault + 外部 secret manager

✓ 業界混合模式

Ansible Vault 存「bootstrap secret」（連到外部 secret manager 所需的 token / credentials）；外部 secret manager 存「真正的應用 secret」（DB password、API key 等）。Ansible Vault 解決「雞生蛋」問題（怎麼安全把第一個 token 放進專案），外部 manager 提供 audit / rotation / dynamic credentials 等高階能力。

13.10本章重點回顧

01

Vault 是 git 友善的 secret 解法

AES-256 加密、零基礎設施、內建在 ansible-core。所有 secret 加密後可安全進 git。

02

兩種粒度

整檔加密（rekey 友善但 diff 不友善）vs 字串加密（diff 友善但無法整批 rekey）。各有權衡。

03

業界推薦：vars + vault 雙檔

明文 main.yml 引用 {{ vault_X }}，加密 vault.yml 內所有變數加 vault_ 前綴。完整可讀 + 集中管理 + 易輪替。

04

密碼來源四種

prompt（互動）、密碼檔、環境變數、client script。本地常用密碼檔、CI 用密碼檔（從 secret 寫暫存）、企業整合用 client script。

05

Multi-Vault 環境隔離

Vault ID 是「密碼的標籤」，每個環境用不同密碼。dev 工程師拿不到 prod 密碼，信任邊界對齊組織結構。

06

密碼檔絕不進 git

.gitignore 必加 .vault_pass*。權限 chmod 600。CI 從 secret 寫暫存檔，job 結束清理。

07

Rekey 定期輪替

ansible-vault rekey 換密碼。整檔加密支援；字串加密要逐一手動重 encrypt。

08

外部 secret manager 共生

大規模或高合規場景配合 HashiCorp Vault / AWS Secrets Manager。Ansible Vault 存 bootstrap secret，外部 manager 存應用 secret。

練習題

  1. 初學者：用 ansible-vault create test-vault.yml 建立加密檔，內含 my_secret: "hello world"，跑 ansible-vault view 確認能讀取。
  2. 初學者：寫一個 playbook 用 vars_files 載入加密 vault.yml，用 debug 印出 my_secret。執行時用 --ask-vault-pass 互動輸入。
  3. 初學者：把密碼存到 ~/.vault_pass（含 chmod 600），改用 --vault-password-file 跑同一個 playbook。把該檔加進 .gitignore。
  4. 開發者：用 encrypt_string 加密一個字串，把結果貼進普通 vars 檔，跑 playbook 印該變數確認解密成功。比較整檔加密與字串加密的 git diff 體驗。
  5. 開發者：建立 vars + vault 雙檔結構（13.4 模式）。明文檔含 db_password: "{{ vault_db_password }}"，加密檔含 vault_db_password: "real-secret"。確認執行流程順暢。
  6. 開發者：用 ansible-vault rekey 把上題的 vault.yml 換新密碼。觀察 git diff 看到的是「整大塊 hex 變化」。
  7. DevOps / SRE：建立 dev 與 prod 兩個 vault（不同密碼），用 vault ID 標籤。寫一個 playbook 同時引用兩個環境的 secret，跑 ansible-playbook --vault-id dev@... --vault-id prod@... 驗證。
  8. DevOps / SRE：寫一個 GitHub Actions workflow（或 GitLab CI），從 CI secret 讀 vault password，跑 ansible-playbook 部署，job 結束清理暫存密碼檔。
  9. DevOps / SRE：研究你的組織該用哪個 secret 策略。評估：① 團隊規模、② 環境數量、③ 合規要求、④ 是否已有 HashiCorp Vault / AWS Secrets Manager。給出採用 Ansible Vault / 外部 manager / 混合模式的建議。

本章詞彙表

Ansible Vault
Ansible 內建的 secret 加密功能。AES-256 對稱加密，密碼學上夠強，安全性取決於密碼管理。
ansible-vault 命令
管理加密內容的 CLI 工具。子命令含 create / encrypt / decrypt / view / edit / rekey / encrypt_string。
整檔加密
用 ansible-vault encrypt 把整個 yaml 檔加密。檔案開頭以 $ANSIBLE_VAULT 標記。Diff 不友善但 rekey 容易。
encrypt_string
對單一字串加密，輸出可貼進 yaml 檔內混合明文使用。Diff 友善但無法整批 rekey。
!vault YAML tag
encrypt_string 產出的 yaml tag，告訴 Ansible 該值是加密內容需要解密。
vault password
解密 vault 的密碼。本身不加密，必須妥善保管（password manager / keyring / CI secret）。
--ask-vault-pass
命令列旗標，跑 playbook 時互動式輸入 vault password。本地手動執行用。
--vault-password-file
命令列旗標，從檔案讀 vault password。檔案是 plaintext 或 executable script（後者印 stdout）。
ANSIBLE_VAULT_PASSWORD_FILE
環境變數，預設密碼檔路徑。設了之後不必每次加 --vault-password-file。
Vault ID
密碼的 label，加在加密內容 header 中。多環境場景用以對應正確密碼（dev / staging / prod）。
--vault-id
命令列旗標，指定 vault ID 與密碼來源。格式 ID@SOURCE，如 prod@~/.vault_pass。
DEFAULT_VAULT_ID_MATCH
config 選項。預設 false（任何密碼會試所有 vault）；true 強制只用 ID 匹配的密碼解密。
rekey
把加密 vault 換新密碼的命令。需提供舊密碼與新密碼。只對整檔加密支援。
vault password client script
可執行檔，印 vault password 到 stdout。Ansible 自動偵測 --vault-password-file 是 script 就執行它。常配合 keyring / 1Password / HashiCorp Vault 動態取密碼。
vault_ 前綴慣例
業界慣例，加密檔內的變數一律加 vault_ 前綴（如 vault_db_password），明文檔引用如 db_password: "{{ vault_db_password }}"。命名隔離清晰。
外部 secret manager
專業的 secret 管理平台（HashiCorp Vault / AWS Secrets Manager / Azure Key Vault）。提供 audit / rotation / dynamic secret 等 Ansible Vault 沒有的能力。
