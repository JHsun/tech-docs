第 27 章 — 監控與告警整合

部署完成不是結束——「沒監控就等於沒部署」。本章把 SRE 的三大支柱（metrics / logs / traces）整進 Ansible 部署流程：① 整體架構——Prometheus 拉 metrics、Loki 收 logs、Tempo 收 traces、Grafana 統一視覺化、AlertManager 出告警；② 部署 Prometheus 完整 stack——server / node_exporter / cAdvisor 三 role；③ 應用層 metrics endpoint——Node.js / Python 暴露 /metrics；④ PromQL alert rules——CPU / RAM / 5xx 比例 / 延遲；⑤ AlertManager 路由——Slack / PagerDuty / 分級；⑥ Grafana 自動配置——datasource + dashboard provisioning；⑦ Loki + Promtail 收 logs；⑧ OpenTelemetry Collector 預覽——統一 telemetry pipeline；⑨ SLI / SLO 與最佳實踐。讀完這章你能用 Ansible 在 30 分鐘內把一個沒監控的服務變成完整 observability stack 監控對象。

27.1SRE 三大支柱與整體架構

27.1.1三大支柱

📊

Metrics（指標）

數值時間序列。CPU 使用率 / RPS / p99 延遲 / DB 連線數。用於：警報、容量規劃、儀表板。代表工具：Prometheus。

📝

Logs（日誌）

事件文字記錄。應用 stdout / nginx access log / audit log。用於：debug 個案、稽核、複雜事件追溯。代表工具：Loki（cost-effective）/ ELK。

🔗

Traces（追蹤）

單一請求跨服務的完整路徑。從 LB 到 web → app → DB 的耗時分段。用於：找微服務瓶頸、定位高延遲。代表工具：Tempo / Jaeger / Zipkin。

ⓘ 三者搭配，不是替代

Metrics 告訴你「出事了」（5xx 暴增）；Logs 告訴你「為何出事」（exception stack trace）；Traces 告訴你「在哪一步出事」（payment service 慢 8 秒）。三者搭配才是完整 observability。

27.2.2node_exporter role

yaml · roles/node_exporter/tasks/main.yml 
---
- name: 建立 node_exporter user
  ansible.builtin.user:
    name: node_exporter
    shell: /sbin/nologin
    system: yes

- name: 下載 node_exporter
  ansible.builtin.unarchive:
    src: "https://github.com/prometheus/node_exporter/releases/download/v{{ node_exporter_version }}/node_exporter-{{ node_exporter_version }}.linux-amd64.tar.gz"
    dest: /tmp/
    remote_src: yes
    creates: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64"

- name: 複製 binary
  ansible.builtin.copy:
    src: "/tmp/node_exporter-{{ node_exporter_version }}.linux-amd64/node_exporter"
    dest: /usr/local/bin/node_exporter
    mode: "0755"
    remote_src: yes
    owner: node_exporter
  notify: restart node_exporter

- name: 部署 systemd unit
  ansible.builtin.template:
    src: node_exporter.service.j2
    dest: /etc/systemd/system/node_exporter.service
  notify: restart node_exporter

- name: 啟動 node_exporter
  ansible.builtin.systemd:
    name: node_exporter
    state: started
    enabled: yes
    daemon_reload: yes

- name: 放行 9100 port（從 monitoring server）
  community.general.ufw:
    rule: allow
    port: "9100"
    proto: tcp
    src: "{{ monitoring_server_ip }}"

27.3應用層 metrics endpoint

OS metrics（node_exporter）只是基礎。業務 metrics 才是價值核心——RPS、latency、業務 KPI（訂單數 / 註冊數）。應用要自己暴露 /metrics。

27.3.1三大應用語言範例

javascript · Node.js — prom-client 
// npm install prom-client
const express = require('express');
const client = require('prom-client');

// 自動收集預設 metrics（process / GC / event loop）
client.collectDefaultMetrics();

// 業務 metrics
const httpRequests = new client.Counter({
  name: 'http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'route', 'status'],
});

const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration',
  labelNames: ['method', 'route'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 5],   // p50/p95/p99 用
});

const app = express();

// 中介層：對每個 request 記錄
app.use((req, res, next) => {
  const end = httpDuration.startTimer({ method: req.method, route: req.path });
  res.on('finish', () => {
    httpRequests.labels(req.method, req.path, res.statusCode).inc();
    end();
  });
  next();
});

// /metrics endpoint — Prometheus scrape
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', client.register.contentType);
  res.end(await client.register.metrics());
});
python · Python / Flask — prometheus_client 
# pip install prometheus_client flask
from flask import Flask, request
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST
import time

app = Flask(__name__)

REQUESTS = Counter('http_requests_total', 'Total HTTP requests',
                   ['method', 'endpoint', 'status'])
DURATION = Histogram('http_request_duration_seconds', 'Latency',
                     ['method', 'endpoint'])

@app.before_request
def before():
    request.start_time = time.time()

@app.after_request
def after(response):
    elapsed = time.time() - request.start_time
    DURATION.labels(request.method, request.path).observe(elapsed)
    REQUESTS.labels(request.method, request.path, response.status_code).inc()
    return response

@app.route('/metrics')
def metrics():
    return generate_latest(), 200, {'Content-Type': CONTENT_TYPE_LATEST}

27.3.2四個黃金訊號 — Google SRE Book

⚡

Latency

請求耗時。p50 / p95 / p99 分位數比 mean 重要。失敗請求的 latency 與成功請求要分開看。

📈

Traffic

系統承受的需求量。RPS / QPS / 並發 connection。

❌

Errors

失敗率。HTTP 5xx 比例、應用層 exception 數。

📊

Saturation

系統「飽滿」程度。CPU 90%+、queue 積壓、連線池接近上限。早於 latency / errors 顯現。

27.4PromQL alert rules

有 metrics 沒 alert 等於沒監控。Alert rules 是 PromQL 表達式 + 閾值 + 持續時間。

27.4.1實用 alert rules

yaml · roles/prometheus/files/rules/app_alerts.yml 
---
groups:
  - name: app_alerts
    rules:
      # 1) Host 掛了
      - alert: HostDown
        expr: up{job="node-exporter"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Host {{ $labels.instance }} is down"
          description: "node_exporter on {{ $labels.instance }} 掛 2 分鐘了"

      # 2) CPU 持續高
      - alert: HighCPU
        expr: (1 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]))) * 100 > 85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} CPU > 85% 已 10 分鐘"

      # 3) 磁碟即將爆
      - alert: DiskAlmostFull
        expr: 100 - (node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"} * 100) > 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.instance }} 磁碟使用率 > 85%"

      # 4) 應用 5xx 比例高 — SLO 警報
      - alert: High5xxRate
        expr: |
          (
            sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
            /
            sum by (job) (rate(http_requests_total[5m]))
          ) > 0.01
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} 5xx 比例 > 1%"

      # 5) 高 p99 延遲
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            sum by (job, le) (rate(http_request_duration_seconds_bucket[5m]))
          ) > 1.0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.job }} p99 延遲 > 1s"
⚠ for 子句的重要

for: 5m = 條件「持續成立 5 分鐘」才觸發。沒這個就會被瞬時 spike 噪訊轟炸。持續時間 + 閾值 + 嚴重級別 三者缺一不可。

27.5AlertManager 路由

Alert 觸發後要送到對的人。AlertManager 用 routing tree + receiver 處理。

yaml · roles/alertmanager/templates/alertmanager.yml.j2 
global:
  resolve_timeout: 5m

# 路由樹 — top-down 匹配
route:
  receiver: slack-default          # 沒匹配到 child 時的 fallback
  group_by: ['alertname', 'instance']
  group_wait: 30s                  # 30 秒內同 group 一起送
  group_interval: 5m
  repeat_interval: 4h                # 沒解就 4 小時重發一次

  routes:
    # critical → PagerDuty 叫值班
    - match:
        severity: critical
      receiver: pagerduty
      continue: true             # 繼續往下匹配（也送 Slack）

    # warning → 只送 Slack
    - match:
        severity: warning
      receiver: slack-warnings

receivers:
  - name: slack-default
    slack_configs:
      - api_url: "{{ vault_slack_webhook }}"
        channel: "#alerts"
        title: "{{ '{{ .GroupLabels.alertname }}' }}"
        text: "{{ '{{ range .Alerts }}{{ .Annotations.summary }}\n{{ end }}' }}"

  - name: slack-warnings
    slack_configs:
      - api_url: "{{ vault_slack_webhook }}"
        channel: "#alerts-warning"
        send_resolved: true

  - name: pagerduty
    pagerduty_configs:
      - routing_key: "{{ vault_pagerduty_key }}"
        severity: critical

# Inhibition — 告警壓制（避免噪訊）
inhibit_rules:
  - source_match:
      severity: critical
      alertname: HostDown
    target_match:
      severity: warning
    equal: ['instance']                # 同 instance HostDown 觸發時，壓制其他 warning

27.7Loki + Promtail 日誌

Loki 是「Prometheus for logs」——cost-effective、用 label 而非全文索引。Promtail 是 agent。

yaml · roles/promtail/templates/promtail.yml.j2 
server:
  http_listen_port: 9080

positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://{{ loki_server }}:3100/loki/api/v1/push

scrape_configs:
  # systemd journal logs
  - job_name: journal
    journal:
      max_age: 12h
      labels:
        job: systemd-journal
        host: "{{ inventory_hostname }}"
    relabel_configs:
      - source_labels: ['__journal__systemd_unit']
        target_label: unit

  # 應用 log 檔
  - job_name: app
    static_configs:
      - labels:
          job: webapp
          env: "{{ env }}"
          host: "{{ inventory_hostname }}"
          __path__: /var/log/webapp/*.log
    pipeline_stages:
      - json:
          expressions:
            level: level
            msg: message
      - labels:
          level:                       # 把 JSON 內的 level 提升為 label
ⓘ Logs 的關鍵：結構化 + 適度 label

① 應用輸出 JSON log（不是文字 prose）— 容易 parse；② label 數量適度—Loki 性能依賴 label cardinality。把 user_id 變 label 會炸；放 level / service / env 才合理。

原本 metrics / logs / traces 各自有 agent + protocol。OpenTelemetry（OTel）是統一 vendor-neutral 標準。趨勢：以 OTel Collector 取代 node_exporter / Promtail / 各家 trace agent。

OTel 已成熟、生產就緒。但已穩定運作的 Prometheus + Promtail stack 不必急著換——OTel 的價值是新專案 / 微服務 traces。建議 ① 新服務直接用 OTel SDK；② 既有 stack 維持但對 traces 用 OTel；③ 大規模統一遷移要規劃時間（多數團隊歷時數月）。

27.9SLI / SLO 與業界最佳實踐

27.9.1SLI / SLO / SLA 三件事

術語意義例子
SLI Service Level Indicator 能測量的服務質量指標 5xx 比例、p99 延遲、可用性 %
SLO Service Level Objective 對 SLI 設的內部目標 99.9% 可用、p99 < 500ms
SLA Service Level Agreement 對客戶承諾、違反有罰則 99.5% 可用、否則退款
✓ Error budget 概念

SLO 99.9% = 每月可有 ~43 分鐘不可用。剩餘的「不可用 quota」叫 error budget。budget 沒用完 → 可冒風險快速發布；budget 將近耗盡 → 暫停 risky 改動、focus stability。把 SLO 當產品決策工具而非單純 dashboard 數字。

27.9.2業界 8 條最佳實踐

①

三大支柱缺一不可

Metrics 警報、Logs 除錯、Traces 找瓶頸。少一項 incident 排查就卡關。

②

node_exporter 必裝在所有 host

OS metrics 是基礎。沒 CPU / RAM / 磁碟 metrics 連最基本警報都做不了。Ansible role 確保所有 host 都有。

③

應用層 /metrics 暴露

業務 metrics（RPS / latency / error rate）比 OS 指標重要。新應用一開始就裝 prometheus client lib。

④

四個黃金訊號

Latency / Traffic / Errors / Saturation。任何服務先確保這四個有監控、有警報。

⑤

Alert 必有 for 子句

for: 5m 防止 spike 噪訊。沒 for 子句的 alert 等於垃圾訊息產生器。

⑥

severity 分級 + AlertManager 路由

critical → PagerDuty 叫人；warning → Slack channel。不要全部送同一處。

⑦

Grafana provisioning

datasource + dashboard 用 IaC。不要點手動加。重建環境也是同份 code。

⑧

SLO + error budget

監控不只是 dashboard。SLO 數字驅動「能不能加快發布」「該不該專注 stability」的決策。

27.10本章重點回顧

01

三大支柱

Metrics（出事）/ Logs（為何）/ Traces（在哪）。三者搭配才是完整 observability。

02

整體架構

Prometheus + node_exporter + cAdvisor + AlertManager + Grafana + Loki + Promtail。OTel 是新趨勢。

03

Ansible 三 role

node_exporter（所有 host）、cadvisor（container host）、prometheus 系列（monitoring server）。

04

動態 targets

用 inventory + Jinja2 模板產生 prometheus.yml 的 targets。新增 host 重跑 playbook 即更新。

05

應用 /metrics

prom-client / prometheus_client 各語言函式庫。四個黃金訊號（latency / traffic / errors / saturation）。

06

PromQL alert + AlertManager 路由

HostDown / HighCPU / DiskFull / 5xx / latency 5 大常見 alert。critical 走 PagerDuty、warning 走 Slack。

07

Grafana provisioning

datasource yaml + dashboard json。grafana.com 1860 / 14282 / 3662 是常見 dashboard。

08

SLI / SLO / Error budget

SLI 可測、SLO 是目標、error budget 驅動發布節奏決策。

練習題

  1. 初學者：對某台 Linux host 用 Ansible 裝 node_exporter。瀏覽 http://host:9100/metrics 確認 metrics 暴露。
  2. 初學者：在 monitoring server 裝 Prometheus（從 binary 或 docker），手動寫 prometheus.yml scrape 上題的 node_exporter。在 Prometheus UI（9090）查 node_cpu_seconds_total。
  3. 初學者：裝 Grafana、加 Prometheus datasource、import dashboard 1860（Node Exporter Full）。看到 host 指標儀表板。
  4. 開發者：把 27.3 的 Node.js 或 Python /metrics 整合到一個 hello-world app。確認 /metrics 回傳 Prometheus 格式，Prometheus 能成功 scrape。
  5. 開發者：寫 Ansible role 把 node_exporter 部署到所有 host、Prometheus 自動產生 targets（用 inventory 的 groups）。新加一台 host 重跑 playbook，Prometheus 自動加進 target list。
  6. 開發者：寫 5 條 alert rules（27.4 範例），手動觸發其中 2 條（如停掉 node_exporter、跑 stress-ng 拉高 CPU）、看 AlertManager UI 確認 alert 出現。
  7. DevOps / SRE：實作 27.5 AlertManager 路由 — critical 送 PagerDuty 測試 channel、warning 送 Slack 測試 channel。觸發各一個 alert、確認落地正確 channel。
  8. DevOps / SRE：用 Ansible 部署 Loki + Promtail、把所有 host 的 systemd journal + 應用 log 收集進來。在 Grafana 查 LogQL {job="systemd-journal"} |= "error"。
  9. DevOps / SRE：對你的某個 production 服務定義 1 個 SLI + 1 個 SLO（如「99.5% 5xx 以下」）。寫 PromQL 計算當前 SLO 達成率與剩餘 error budget。

開源時間序列資料庫 + 監控系統。pull 模式 — 定期 scrape target 的 /metrics。Kubernetes 生態事實標準。
PromQL
Prometheus 的查詢語言。rate() / histogram_quantile() / sum by() 是 alert rule 與 dashboard 的核心函式。
node_exporter
Prometheus 官方 exporter — 收集 OS / 硬體 metrics（CPU / RAM / 磁碟 / 網路）。port 9100。所有 host 必裝。
cAdvisor
Google 開發的容器 metrics 收集器。port 8080。跑 container 的 host 必裝。
Application /metrics endpoint
應用自己暴露的 Prometheus 格式 metrics。各語言有 prom-client / prometheus_client / micrometer 等 library。業務 metrics 必經之路。
Counter / Gauge / Histogram
Prometheus 三種 metric type。Counter 只增（如 request 數）；Gauge 可增可減（如 CPU 使用率）；Histogram 是分桶（用於計算 p95 / p99）。
Four Golden Signals
Google SRE Book 提的四個必監控指標 — Latency / Traffic / Errors / Saturation。任何服務先確保這四個有 metrics + alert。
Alert rule
Prometheus rule file 定義的告警條件。expr（PromQL）+ for（持續時間）+ labels（severity）+ annotations（人讀訊息）。
for 子句
alert 必設選項。條件「持續成立」for 多久才觸發。沒設 = spike 噪訊轟炸。
AlertManager
Prometheus 生態的告警分發。group / route / inhibit / receiver 四大概念。port 9093。
Receiver
AlertManager 的告警目的地配置。slack_configs / pagerduty_configs / email_configs / webhook_configs 等。
Inhibit rule
告警壓制規則。Host 掛了時，壓制該 host 所有相關 warning（避免噪訊）。
Grafana
視覺化 dashboard。連接 Prometheus / Loki / Tempo 等 datasource。port 3000。
Grafana provisioning
用 yaml 檔自動配置 datasource 與 dashboard。把 Grafana 配置變成 IaC。/etc/grafana/provisioning/ 路徑。
Loki
Grafana Labs 開發的 log 聚合系統。「Prometheus for logs」— 用 label 而非全文索引。cost-effective。port 3100。
LogQL
Loki 的查詢語言。語法類似 PromQL。{job="webapp"} |= "error"。
Promtail
Loki 的 log 收集 agent。讀取 file / journal、push 到 Loki。port 9080。
Grafana Alloy
Promtail 的後繼 agent。同時支援 metrics / logs / traces，也支援 OpenTelemetry。在新部署中漸取代 Promtail。
Tempo / Jaeger / Zipkin
分散式 tracing backend。儲存與查詢請求的跨服務追蹤。Tempo 是 Grafana 系、Jaeger 是 CNCF 老牌。
OpenTelemetry (OTel)
vendor-neutral 的 observability 標準。SDK + Collector + protocol（OTLP）。是 metrics / logs / traces 統一未來。port 4317（gRPC）/ 4318（HTTP）。
OTel Collector
OTel 的中央收集器。三段式架構：receivers（多協定收集）→ processors（過濾 / 改 label）→ exporters（送到 Prometheus / Tempo / Loki）。
SLI (Service Level Indicator)
能測量的服務質量指標。例如：「5xx 請求比例」、「p99 延遲」、「可用性 %」。
SLO (Service Level Objective)
對 SLI 設的內部目標。「p99 latency < 500ms」「99.9% 可用」。
SLA (Service Level Agreement)
對外承諾的契約。違反通常有財務罰則（退款 / credit）。SLO 必須嚴於 SLA。
Error budget
SLO 允許的「不可用配額」。99.9% SLO = 每月 ~43 分鐘 budget。budget 將盡 = 暫停 risky 發布；budget 充裕 = 可加速 ship。
