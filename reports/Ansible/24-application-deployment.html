第 24 章 — 應用部署實戰

第 23 章談模式（rolling / blue-green / canary），但實際應用怎麼長？production app 從來不只是「一個 process」——通常是 load balancer + web tier + app tier + DB + cache + 後台 worker。這章把第 10 章（roles）、第 23 章（部署模式）、第 21 章（容器）整合成一份真實可用的 production playbook。本章建一個典型 web app stack（nginx + Node.js + PostgreSQL + Redis）並走完一次完整 release：① stack 結構與 role 拆分；② 變數分層（defaults / vars / vault）；③ 設定檔模板化；④ artifact 管理（build vs pull）；⑤ 跨環境部署（dev / staging / prod 用同份 playbook）；⑥ 應用 lifecycle（first deploy / upgrade / rollback / decommission）；⑦ 整合 CI/CD 預覽（為 Ch28 鋪路）；⑧ 業界 8 條最佳實踐。讀完這章你能用 ~5 個 role + 3 個 group_vars 環境檔涵蓋一個應用的完整部署需求。

本章把第 10 章 Roles + 第 23 章模式 + 第 21 章容器整合成生產級實戰
初學者選讀（24.1–24.3 stack 結構與基礎 deploy） 開發者必讀（全章 — 寫應用部署 playbook 的範本） DevOps / SRE 必讀（全章）

24.1.2為什麼這樣分層

🌐

LB

SSL 終端、流量分發、健康路由。Ch23 的 LB drain pattern 在這層動。

⚙

Web App tier

無狀態（stateless），可 horizontal scale。Rolling deploy 主戰場——這層升版用 serial。

💾

DB

有狀態（stateful），不能任意重啟。primary + replica 配置、schema migration 用 run_once。

⚡

Cache

易揮發，但要 graceful 處理。Redis 也常兼任 job queue。

🔄

Worker

處理背景任務（email / 報表 / image processing）。sidekiq / celery / bull。也是 stateless 可 rolling。

24.2.2site.yml — 主入口

yaml · playbooks/site.yml — 一檔涵蓋全 stack 
---
# Play 1: 所有 host 共用的基礎設施
- name: 基礎設施
  hosts: all
  become: true
  roles:
    - common          # user / firewall / monitor agent

# Play 2: DB 層
- name: PostgreSQL
  hosts: db
  become: true
  roles:
    - postgres

# Play 3: Cache 層
- name: Redis
  hosts: cache
  become: true
  roles:
    - redis

# Play 4: Web tier — rolling + canary
- name: Web app + nginx
  hosts: webservers
  become: true
  serial: "{{ web_serial | default([1, '50%', '100%']) }}"
  max_fail_percentage: 10
  roles:
    - app
    - nginx

# Play 5: Worker 層
- name: Background worker
  hosts: workers
  become: true
  serial: "50%"
  roles:
    - worker

24.3變數分層策略

變數放哪是大型專案的核心設計問題。第 7 章學過 22 個優先級——這節給實際 layout。

24.3.1三層變數模型

位置內容會 commit 嗎
roles/<role>/defaults/main.yml role 內合理預設（最低優先） 是
group_vars/all.yml 跨環境共用（如 app_name / 標準 port） 是
group_vars/<env>.yml 環境差異（image tag / replica 數 / DB host） 是
group_vars/all/vault.yml secret（密碼 / API key） 是 — 但加密
host_vars/<host>.yml 個別 host 差異（primary vs replica） 是
-e command line 本次部署一次性 override（如 app_version） 否

24.3.2實際範例

yaml · roles/app/defaults/main.yml — role 預設 
---
# 合理預設 — 任何環境都能跑（雖然可能不適合 prod）
app_name: myapp
app_user: myapp
app_dir: /opt/{{ app_name }}
app_port: 3000
app_env: production
app_log_level: info
app_image_registry: "registry.example.com"
app_image_repo: "{{ app_name }}"
app_image_tag: latest            # 應在 group_vars 或 -e 覆蓋
app_releases_keep: 5
app_node_workers: 2

# 健康檢查預設
app_health_path: /health
app_health_retries: 10
app_health_delay: 3
yaml · group_vars/all.yml — 跨環境共用 
---
app_name: myapp
app_user: myapp
app_image_registry: "registry.example.com"

# 共用標準 port
app_port: 3000
db_port: 5432
redis_port: 6379
yaml · group_vars/prod.yml — prod 專屬 
---
env: prod
app_env: production
app_log_level: warn          # prod 不要 info 級別
app_node_workers: 8          # prod 機器更大
app_image_tag: "{{ release_version | default('stable') }}"

web_serial:
  - 1                        # prod canary 從 1 開始
  - "25%"
  - "100%"

db_replica_count: 2
redis_maxmemory: "4gb"
nginx_workers: 8
yaml · group_vars/all/vault.yml — 加密 secret 
---
# 用 ansible-vault edit group_vars/all/vault.yml 編輯
vault_db_password: "super-secret-pwd-here"
vault_redis_password: "redis-secret"
vault_jwt_secret: "jwt-signing-key"
vault_api_keys:
  stripe: "sk_live_..."
  sendgrid: "SG..."
vault_registry_password: "docker-registry-pwd"
ⓘ vault_ prefix 慣例

把 vault 變數命名為 vault_xxx，在 role / playbook 中用「非 vault」變數引用：db_password: "{{ vault_db_password }}"。好處：① debug 時看 vars 馬上知道是 secret；② 想換成從 SSM / Key Vault 取 secret 時，只改一行 mapping 而非 role 內所有引用。

24.4.2main.yml — orchestrator

yaml · roles/app/tasks/main.yml 
---
- name: 確保系統依賴
  ansible.builtin.include_tasks: dependencies.yml
  tags: [deps]

- name: 取得 artifact
  ansible.builtin.include_tasks: artifact.yml
  tags: [artifact]

- name: 部署（含 LB drain + symlink）
  block:
    - ansible.builtin.include_tasks: deploy.yml
    - ansible.builtin.include_tasks: healthcheck.yml
  rescue:
    - ansible.builtin.include_tasks: rollback.yml
    - ansible.builtin.fail:
        msg: "deploy 失敗，已 rollback to {{ previous_release | default('unknown') }}"
  tags: [deploy]

24.4.3artifact 取得：build vs pull

策略機制優劣
git pull + 本地 build 每台 host 各自 git pull + npm ci 簡單；但每台都消耗 build 時間 + 可能 build 出不同 artifact
tarball pull 從 artifact server 拉 app-1.2.3.tar.gz 單一 artifact 來源（一致性）；需 artifact server
Docker image pull 從 registry 拉 image 最一致 + 整合 dev container；需 docker daemon
S3 / GCS cloud storage 拉 免維運 server；需雲端認證
yaml · roles/app/tasks/artifact.yml — tarball 模式 
---
- name: 產生 release id
  ansible.builtin.set_fact:
    release_id: "{{ ansible_date_time.iso8601_basic_short }}"
    release_dir: "{{ app_dir }}/releases/{{ ansible_date_time.iso8601_basic_short }}"

- name: 建立 release 目錄
  ansible.builtin.file:
    path: "{{ release_dir }}"
    state: directory
    owner: "{{ app_user }}"
    mode: "0755"

- name: 下載 artifact
  ansible.builtin.get_url:
    url: "{{ artifact_url }}/{{ app_name }}-{{ app_image_tag }}.tar.gz"
    dest: "/tmp/{{ app_name }}-{{ app_image_tag }}.tar.gz"
    checksum: "sha256:{{ artifact_checksum }}"     # 驗 SHA256
    mode: "0644"

- name: 解壓到 release dir
  ansible.builtin.unarchive:
    src: "/tmp/{{ app_name }}-{{ app_image_tag }}.tar.gz"
    dest: "{{ release_dir }}"
    remote_src: yes
    owner: "{{ app_user }}"

- name: link shared 資源
  ansible.builtin.file:
    src: "{{ app_dir }}/shared/{{ item }}"
    dest: "{{ release_dir }}/{{ item }}"
    state: link
  loop: ["logs", "uploads", "config"]

24.5跨環境部署 — 一份 playbook 三個環境

24.5.1透過 inventory 切環境

bash · 同一份 playbook 跑不同環境 
# Dev — 一鍵升級
$ ansible-playbook -i inventory/dev.yml playbooks/site.yml \
    -e "release_version=v1.2.3-rc1"

# Staging — 同份 playbook、不同 inventory + 不同 vars
$ ansible-playbook -i inventory/staging.yml playbooks/site.yml \
    -e "release_version=v1.2.3-rc1" \
    --ask-vault-pass

# Prod — 加 --check --diff 預覽 dry-run
$ ansible-playbook -i inventory/prod.yml playbooks/site.yml \
    -e "release_version=v1.2.3" \
    --check --diff --vault-password-file=~/.vault_pass

# Prod — 真正部署（先 staging 驗證過才跑）
$ ansible-playbook -i inventory/prod.yml playbooks/site.yml \
    -e "release_version=v1.2.3" \
    --vault-password-file=~/.vault_pass

24.5.2環境差異該長怎樣

🟢

Dev

serial: 100%、app_log_level: debug、單機 DB、無 cache HA。速度優先。

🟡

Staging

結構與 prod 一致但規模小。serial: [1, "100%"]、有 LB、有 replica。真實性優先。

🔴

Prod

serial: [1, "25%", "100%"]、max_fail_percentage: 10、replica + cache HA、--check --diff dry-run。安全優先。

24.6.3deploy_app.yml — 最常用的入口

yaml · playbooks/deploy_app.yml — 只升 app tier 
---
# Pre-flight — 不允許任何失敗
- name: 部署前驗證
  hosts: webservers
  any_errors_fatal: true
  tasks:
    - name: 確認 release_version 已指定
      ansible.builtin.assert:
        that:
          - release_version is defined
          - release_version | length > 0
        fail_msg: "必須用 -e release_version=vX.Y.Z 指定版本"

    - name: 確認當前服務健康（baseline）
      ansible.builtin.uri:
        url: "http://localhost:{{ app_port }}/health"
        status_code: 200

    - name: 確認硬碟空間 > 2GB
      ansible.builtin.shell: df --output=avail / | tail -1
      register: disk
      changed_when: false
      failed_when: disk.stdout | int < 2097152


# Rolling deploy — 配 max_fail_percentage
- name: 部署 app
  hosts: webservers
  become: true
  serial: "{{ web_serial }}"
  max_fail_percentage: 10
  vars:
    app_image_tag: "{{ release_version }}"
  roles:
    - app
    - nginx


# Post-deploy — 集中 smoke test
- name: 部署後驗證
  hosts: localhost
  connection: local
  tasks:
    - name: 對 LB 跑 smoke test
      ansible.builtin.shell: ./scripts/smoke_test.sh {{ env }}
      register: smoke

    - name: 通知 Slack
      community.general.slack:
        token: "{{ vault_slack_token }}"
        msg: "✅ {{ env }} 部署成功 {{ release_version }}"

24.7.2GitHub Actions 範例

yaml · .github/workflows/deploy.yml 
---
name: Deploy to staging

on:
  push:
    tags: ['v*']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install Ansible
        run: |
          pip install ansible-core
          ansible-galaxy collection install -r collections/requirements.yml

      - name: Setup SSH key
        env:
          SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_KEY" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519

      - name: Setup vault password
        env:
          VAULT_PASS: ${{ secrets.ANSIBLE_VAULT_PASS }}
        run: echo "$VAULT_PASS" > ~/.vault_pass

      - name: Deploy to staging
        run: |
          ansible-playbook -i inventory/staging.yml playbooks/deploy_app.yml \
            -e "release_version=${{ github.ref_name }}" \
            --vault-password-file=~/.vault_pass

24.8業界最佳實踐

①

Role per service

每個服務一個獨立 role（postgres / redis / app / nginx / worker）。dependencies 用 role 的 meta/main.yml 表達。

②

三層變數模型

defaults（最低）+ group_vars/all（共用）+ group_vars/<env>（環境差異）+ vault（secret）。每個變數只應該在一個地方定義。

③

vault_ prefix 慣例

所有 secret 在 vault 裡命名 vault_xxx，role 中用 mapping 引用。換 secret store 時改一處即可。

④

單一 artifact 來源

不要每台 host 各自 build。從 registry / artifact server / S3 拉同一份 — 含 SHA256 校驗。一致性勝於 build 速度。

⑤

release_version 不要寫死

-e release_version=v1.2.3 在 CLI 傳入。CI 自動帶 git tag。沒指定就 fail（assert 起來）。

⑥

多個 playbook 入口

site.yml（從零）、deploy_app.yml（升版）、rollback.yml、decommission.yml。每個入口名字 = 操作意圖，避免一個 playbook 包山包海。

⑦

--check --diff dry-run prod

真正部署 prod 前永遠先 --check --diff 看會改什麼。怪怪的就停。reviewer 也 review 這個 diff。

⑧

部署完 smoke test

不只是 task PASS — 對 LB 跑端對端 smoke test。失敗就 rollback + 通知。

24.9本章重點回顧

01

典型 stack 五層

LB / Web / Worker（無狀態）+ DB / Cache（有狀態）。各自部署策略不同。

02

Role per service

roles/postgres/、roles/redis/、roles/app/、roles/nginx/、roles/worker/、roles/common/。site.yml 串起來。

03

變數三層

defaults（role 內）→ group_vars/all（共用）→ group_vars/<env>（環境差異）+ vault（secret）。每個變數一個出處。

04

app role 7 段式

dependencies → artifact → deploy → healthcheck → rollback。block / rescue 串起 deploy + healthcheck + rollback。

05

artifact 四種來源

git pull / tarball / Docker image / cloud storage。生產建議 tarball 或 image 確保一致性。

06

跨環境一份 playbook

同 site.yml + 不同 inventory + 不同 group_vars。dev / staging / prod 共用一份 deploy 邏輯。

07

Lifecycle 四操作

site.yml（從零）、deploy_app.yml（升版）、rollback.yml、decommission.yml。每個入口名字 = 意圖。

08

業界 8 條最佳實踐

role per service / 三層變數 / vault_ prefix / 單一 artifact / release_version / 多入口 / dry-run / smoke test。

練習題

  1. 初學者：為一個簡單 hello-world Node.js app 寫單一 role（roles/app/）。能在一台 Ubuntu host 上跑起來。
  2. 初學者：把該 role 拆成 dependencies / artifact / deploy / healthcheck 四個 sub-task 檔案。觀察 main.yml 變得多乾淨。
  3. 初學者：建 inventory/dev.yml 與 inventory/prod.yml，分別放不同 host。同一份 playbook 跑兩個 inventory，觀察結果。
  4. 開發者：實作本章 24.4 的完整 app role（含 7 個檔案 + templates + handlers）。對 3 台 web server 部署 sample app。
  5. 開發者：寫 group_vars 三層結構：all.yml + dev.yml + prod.yml + all/vault.yml。確認 prod 部署用 prod 的 image_tag、log_level、worker 數。
  6. 開發者：對 24.4 的 app role 加 block / rescue 自動 rollback。手動讓 health check 失敗，觀察 rescue 觸發。
  7. DevOps / SRE：把所有 5 個 role（postgres / redis / app / nginx / worker）寫齊，在 site.yml 串起來。對 staging 環境一鍵 from-zero 部署。
  8. DevOps / SRE：寫 GitHub Actions workflow — push tag 觸發、build artifact → push 到 registry → SSH 到 control node 跑 ansible-playbook。end-to-end CD 流程。
  9. DevOps / SRE：對你公司的某一個應用，畫出第 24.1 圖的 stack 結構。每層的 host 數、scale 策略、是否 stateful。如果用 Ansible 重構部署 playbook，role 會怎麼切？

Application stack
應用所需的全部元件 — load balancer / web tier / app tier / DB / cache / worker。每層 scale 策略不同。
Stateless tier
無狀態的服務層（web / worker）— 可任意 scale、任意替換、任意重啟。Rolling deployment 主戰場。
Stateful tier
有狀態的服務層（DB / cache / queue）— 不能任意重啟、scale 需要 sharding / replication。部署時需特別處理。
Role per service
設計慣例 — 每個服務（postgres / redis / app / nginx）一個獨立 role。互相獨立、清楚的 dependency 關係。
site.yml
慣例的主入口 playbook 名稱 — 涵蓋整個 stack 從零建立。第一次部署用。
deploy_app.yml
慣例的「只升版 app tier」playbook。最常用的入口（80% 部署都是只升 app）。
rollback.yml
回滾 playbook。切 symlink 到上一版（Ch23）。
decommission.yml
下架 playbook。停 service / 移 LB / 釋放雲端資源 / 清資料。
Three-layer variables
變數三層模型 — defaults（role 內最低）+ group_vars/all（跨環境共用）+ group_vars/<env>（環境差異）+ vault（secret）。
vault_ prefix 慣例
所有 secret 在 vault 內命名 vault_xxx，role 中用 mapping 變數（db_password: "{{ vault_db_password }}"）引用。debug 友善 + 換 secret store 容易。
Artifact
build 產物。tarball / Docker image / .jar / .deb 等。生產建議從單一 source 拉、SHA256 校驗。
Build vs pull
artifact 取得策略對立。build = 每台 host 各自 build（簡單但不一致）；pull = 從 artifact server / registry 拉同一份（一致但需基礎設施）。
Release directory pattern
Ch23 介紹的 symlink-based release。每次部署新的 release dir、current symlink 切換。瞬間 rollback。
Shared directory
跨 release 共用的目錄（logs / uploads / config）。新 release 透過 symlink 連到 shared，避免每次重新部署 logs 散落。
app.env
慣例的應用環境變數檔。Jinja2 模板產生、放在 shared/config/、systemd unit 透過 EnvironmentFile= 載入。
systemd unit
應用的 service 定義（.service 檔）。Ansible 用 template 產生、systemd module 啟用。生產加 NoNewPrivileges / ProtectSystem 等強化。
release_version
慣例的部署參數。CLI -e release_version=v1.2.3 傳入。CI 自動帶 git tag。assert 確保有指定。
--check --diff
Ansible 的 dry-run 旗標。--check 不真改、--diff 顯示差異。Prod 部署前 review 用。
Smoke test
部署後對應用做端對端最小測試。從 LB / public endpoint 打過去看是否回 200。比逐 host healthcheck 更可靠。
environment / env
慣例變數，標明當前部署的環境（dev / staging / prod）。group_vars 依此分檔、playbook 與 task 用 when 判斷。
artifact_url / artifact_checksum
artifact 的 URL 與 SHA256 校驗碼。get_url 模組支援 checksum: sha256:xxx，下載完自動驗證。防止傳輸中 corruption。
