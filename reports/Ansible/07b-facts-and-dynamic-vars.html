第 7 章 下 — Facts 與動態變數

第 7 章 上講的是「你定義的變數」。本下半章換一個視角——「從 host 自動取得的變數」與「運行時動態產生的變數」。Facts 是 Ansible 在每個 play 開始時透過 setup 模組從遠端 host 收集的系統資訊（OS 版本、IP、記憶體、磁碟等），register 把任意 task 的執行結果存成變數，set_fact 在 runtime 動態建立新變數。這三個機制加上 magic variables（hostvars、groups、inventory_hostname）讓 playbook 可以「依現實狀況彈性調整」——OS 不同走不同分支、跨主機取資訊、條件式執行等。

初學者必讀（7.1–7.3） 開發者必讀（全章） DevOps / SRE 必讀（全章特別 7.5 fact caching、7.6 magic variables）

7.1Facts 是什麼？

當你跑 ansible-playbook，第一個 task 通常是 Gathering Facts——這是 Ansible 自動執行的 setup 模組，到每台 managed node 收集系統資訊：OS、kernel、CPU、記憶體、網路介面、掛載點、virtual / cloud metadata、Python 版本……將近 1000 個欄位。

這些資訊在 playbook 中以變數形式可用，前綴 ansible_。例如：

yaml · 直接使用 facts 
- name: 顯示系統資訊
  ansible.builtin.debug:
    msg: |
      Hostname: {{ ansible_hostname }}
      OS: {{ ansible_distribution }} {{ ansible_distribution_version }}
      Kernel: {{ ansible_kernel }}
      CPU 核心: {{ ansible_processor_vcpus }}
      記憶體: {{ ansible_memtotal_mb }} MB
      主要 IP: {{ ansible_default_ipv4.address }}

7.1.1常用 Facts 速查表

Fact說明範例值
ansible_distributionOS 發行版名稱Ubuntu / RHEL / Debian
ansible_distribution_versionOS 版本24.04 / 9.4
ansible_distribution_major_version主版本24 / 9
ansible_os_familyOS 系列（用於跨發行版條件）Debian / RedHat
ansible_kernelkernel 版本6.8.0-49-generic
ansible_architectureCPU 架構x86_64 / aarch64
ansible_processor_vcpusvCPU 數8
ansible_memtotal_mb總記憶體（MB）16384
ansible_hostname短主機名web01
ansible_fqdn完整域名web01.example.com
ansible_default_ipv4主介面 IPv4 資訊（dict）含 address / gateway / interface
ansible_interfaces所有網路介面名稱（list）['lo', 'eth0', 'eth1']
ansible_mounts所有掛載點（list of dict）含 mount / size_total / fstype 等
ansible_python_version遠端 Python 版本3.12.3
ansible_virtualization_type虛擬化類型kvm / docker / NA
ansible_date_time當前時間（dict）含 iso8601 / epoch / tz 等

7.1.2看一台 host 的全部 facts

bash · 探索 facts 
# 用 ad-hoc 看完整 facts（輸出量大，建議搭配 less）
$ ansible web01 -m setup | less

# 用 filter 篩特定 fact
$ ansible web01 -m setup -a "filter=ansible_distribution*"
$ ansible web01 -m setup -a "filter=ansible_default_ipv4"

# 在 playbook 內 dump 所有 facts
- name: 看全部 facts
  ansible.builtin.debug:
    var: ansible_facts

7.2ansible_facts 與舊風格變數

同一份 fact 資料 Ansible 提供兩種訪問方式，這是新手常見的混淆來源。

7.2.1新風格：ansible_facts dict

yaml · 新風格訪問 
# 走 ansible_facts dictionary
- ansible.builtin.debug:
    msg: "{{ ansible_facts['distribution'] }}"
    # 注意：key 是 distribution 而非 ansible_distribution

# 巢狀資料
- ansible.builtin.debug:
    msg: "{{ ansible_facts['default_ipv4']['address'] }}"

7.2.2舊風格：ansible_ 前綴的頂層變數

yaml · 舊風格訪問（預設啟用） 
# 直接用 ansible_ 前綴的變數
- ansible.builtin.debug:
    msg: "{{ ansible_distribution }}"

# 巢狀也支援 dot notation
- ansible.builtin.debug:
    msg: "{{ ansible_default_ipv4.address }}"
ⓘ INJECT_FACTS_AS_VARS 設定

舊風格的存在是因為 ansible.cfg 預設 inject_facts_as_vars = true——把 ansible_facts.X 自動注入成 ansible_X 頂層變數。在大型專案如果想避免命名空間污染，可以在 ansible.cfg 設 inject_facts_as_vars = false，那樣就只能透過 ansible_facts['X'] 訪問。2026 業界共識：保持預設啟用，舊風格較易讀。

7.3Facts 的條件式運用

Facts 真正的威力在跨平台條件分支——一份 playbook 同時支援 Ubuntu、RHEL、Alpine。

7.3.1OS 分流

yaml · 依 OS 安裝不同套件 
- name: 安裝 nginx (Debian 系)
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: true
  when: ansible_os_family == "Debian"

- name: 安裝 nginx (RedHat 系)
  ansible.builtin.dnf:
    name: nginx
    state: present
  when: ansible_os_family == "RedHat"

- name: 處理舊版 (RHEL 7 之前)
  ansible.builtin.fail:
    msg: "不再支援 {{ ansible_distribution_major_version }}"
  when:
    - ansible_os_family == "RedHat"
    - ansible_distribution_major_version | int < 8

7.3.2Hardware 分流

yaml · 依硬體規格做不同設定 
- name: 大記憶體機器用 high-memory 設定
  ansible.builtin.template:
    src: high-memory.conf.j2
    dest: /etc/app/config.conf
  when: ansible_memtotal_mb >= 16384

- name: 小記憶體加 swap
  ansible.builtin.include_tasks: setup-swap.yml
  when: ansible_memtotal_mb < 4096

- name: VM 跳過硬體相關工具
  ansible.builtin.command: "/opt/hardware-tool"
  when: ansible_virtualization_type == "NA"

- name: 處理 ARM 架構
  ansible.builtin.set_fact:
    binary_arch: "{{ 'arm64' if ansible_architecture == 'aarch64' else 'amd64' }}"

7.3.3關掉 fact gathering 加速

每個 play 預設都先收集 facts，這會花 1–3 秒。如果該 play 用不到 facts（例如純粹複製檔案、重啟服務），可以關掉以加速。

yaml · 關閉 fact gathering 
- name: 這個 play 不需要 facts
  hosts: webservers
  gather_facts: false            # ← 關掉
  tasks:
    - name: 重啟服務
      ansible.builtin.service:
        name: nginx
        state: restarted
⚠ 全 play 關 facts 會導致魔法變數失效

關了 fact gathering 後，ansible_distribution 等 facts 變數就不存在，但 inventory_hostname、groups 等 magic variables 仍可用。如果只想關「部分」收集，可用 gather_subset 細粒度控制：

yaml · gather_subset 細粒度控制 
- hosts: all
  gather_facts: true
  vars:
    ansible_facts_modules:
      - ansible.builtin.setup
  tasks:
    # 也可以在 play 開始用 setup 模組指定 subset
    - ansible.builtin.setup:
        gather_subset:
          - "!all"            # 預設不收
          - "network"         # 只收網路相關
          - "distribution"    # 與 OS 資訊

7.4register — 把 task 結果存成變數

除了 facts，任何 task 的執行結果都能存成變數，靠的是 register。它讓 task 之間能傳遞資料。

7.4.1基本用法

yaml · register 與後續使用 
- name: 查詢服務狀態
  ansible.builtin.command: "systemctl is-active nginx"
  register: nginx_status
  changed_when: false           # 純查詢，不要顯示為 changed
  failed_when: false            # 不要因為 inactive 而 fail

- name: 看 register 結果結構
  ansible.builtin.debug:
    var: nginx_status

- name: 使用 stdout
  ansible.builtin.debug:
    msg: "nginx 狀態 = {{ nginx_status.stdout }}"

- name: 依結果做不同事
  ansible.builtin.service:
    name: nginx
    state: started
  when: nginx_status.stdout != "active"

7.4.2Register 結果的標準結構

Key說明
changed是否改變狀態（true / false）
failed是否失敗（true / false）
skipped是否被 when 跳過
rcreturn code（command / shell 模組）
stdout標準輸出（command / shell 模組）
stderr標準錯誤輸出
stdout_linesstdout 已切成 list
msg模組回傳的訊息（fail / debug 等）
start / end / delta執行時間資訊

7.4.3register + loop 的特殊結構

yaml · 在 loop 中 register 
- name: 逐一檢查多個 service
  ansible.builtin.command: "systemctl is-active {{ item }}"
  register: multi_status
  loop:
    - nginx
    - postgresql
    - redis
  changed_when: false
  failed_when: false

# multi_status.results 是 list of dict，每個 item 一筆
- name: 列出每個 service 的結果
  ansible.builtin.debug:
    msg: "{{ item.item }} = {{ item.stdout }}"
  loop: "{{ multi_status.results }}"

7.4.4changed_when 與 failed_when

ⓘ command 不冪等的解法

command / shell 模組永遠回 changed: true（除非 creates / removes 條件成立）。但「查詢狀態」並不是真的 changed，這時用 changed_when: false 抑制誤報。failed_when 同理可控制何時算失敗。

yaml · 自定 changed/failed 判定 
- name: 查 disk 使用率
  ansible.builtin.shell: "df / | awk 'NR==2 {print $5}' | tr -d '%'"
  register: disk_usage
  changed_when: false                        # 純查詢
  failed_when: disk_usage.stdout | int > 90      # 超過 90% 才算 fail

7.5set_fact — 動態建立變數

set_fact 在 runtime 動態建立或修改變數。常見用途：① 從 register 結果加工出新變數；② 在某個 task 計算後設定 flag 給後續 task 用；③ 跨 play 共享資訊（搭配 caching）。

7.5.1基本用法

yaml · set_fact 三種典型用法 
# ① 簡單設值
- name: 設定 deploy ID
  ansible.builtin.set_fact:
    deploy_id: "{{ ansible_date_time.iso8601_basic }}"
    deploy_user: "{{ lookup('env', 'USER') }}"

# ② 從 register 結果加工
- name: 取得 git commit
  ansible.builtin.command: "git rev-parse HEAD"
  register: git_commit
  changed_when: false
  delegate_to: localhost

- name: 把短 hash 設成 fact
  ansible.builtin.set_fact:
    app_version_short: "{{ git_commit.stdout[:7] }}"

# ③ 條件式 fact
- name: 依環境決定 log level
  ansible.builtin.set_fact:
    log_level: "{{ 'DEBUG' if env == 'staging' else 'INFO' }}"

7.5.2cacheable 模式

yaml · cacheable: true 
- name: 把 deploy_id 存進 fact cache 跨 playbook 重用
  ansible.builtin.set_fact:
    deploy_id: "{{ ansible_date_time.iso8601_basic }}"
    cacheable: true            # 寫入 fact cache
⚠ cacheable 後優先序變回 facts 等級

當前 playbook 執行時 set_fact 還是第 19 層（高優先序）。但下次 playbook 啟動，從 cache 讀回的值變成第 11 層（host facts）——比 group_vars 高、但比 play vars 低。這是常見踩雷點：cacheable: true 不適合用來「強制覆蓋」變數，只適合「持久化計算過的不變值」（如固定的 deploy ID、組織內網 IP map）。

7.5.3set_fact vs vars vs register 對照

機制作用域動態性優先序典型場景
vars play / block / task 範圍 靜態（lazy 評估） 第 12 / 16 / 17 層 常數設定
register play 範圍（每 host） task 結束後可用 第 19 層 取得 task 執行結果
set_fact play 範圍（每 host） 立刻 evaluate 為靜態值 第 19 層（cacheable 後變第 11） 動態計算後的固定值

7.6Magic Variables — Ansible 內建的「魔法」

除了 facts，Ansible 自動提供一組「關於 Ansible 自己」的變數，稱為 magic variables。它們的名字是保留的——你不能設同名變數。

7.6.1四大常用 magic variables

變數含義典型用途
inventory_hostname 當前 host 在 inventory 中的名稱 產生 host 專屬檔名 / 訊息
groups 所有群組與成員的 dict 跨 host 列舉（產生 nginx 後端清單）
group_names 當前 host 所屬群組的 list 條件式執行（屬於哪個 group 就做什麼）
hostvars 所有 host 的變數 dict 跨 host 取另一台的 fact / 變數

7.6.2inventory_hostname 範例

yaml · 用 inventory_hostname 
- name: 為每台 host 產生個別 log 檔
  ansible.builtin.copy:
    content: "Deploy on {{ inventory_hostname }} at {{ ansible_date_time.iso8601 }}"
    dest: "/var/log/deploy-{{ inventory_hostname }}.log"

- name: 用 inventory_hostname 抓對應的 host_vars
  ansible.builtin.debug:
    msg: "{{ hostvars[inventory_hostname]['ansible_default_ipv4']['address'] }}"

7.6.3groups 範例：列舉群組成員

yaml · 用 groups 產生後端清單 
# 在 nginx upstream 設定中列出所有 webservers
- name: 產生 nginx upstream 設定
  ansible.builtin.template:
    src: upstream.conf.j2
    dest: /etc/nginx/conf.d/upstream.conf

# 在 upstream.conf.j2 模板內：
# upstream backend {
# {% for host in groups['webservers'] %}
#     server {{ hostvars[host]['ansible_default_ipv4']['address'] }}:8080;
# {% endfor %}
# }

7.6.4group_names 範例：依群組成員身份分流

yaml · 用 group_names 
- name: 把 host 分類加入正確的 firewall zone
  ansible.builtin.set_fact:
    fw_zone: "{{ 'public' if 'webservers' in group_names else 'internal' }}"

- name: 只對 production 群組做某事
  ansible.builtin.command: "backup-now"
  when: "'production' in group_names"

7.6.5hostvars 範例：跨 host 取資訊

yaml · 用 hostvars 跨 host 取資料 
- name: 在 webserver 上產設定，連到 db 群組第一台
  ansible.builtin.template:
    src: app.conf.j2
    dest: /etc/myapp/app.conf
  vars:
    db_primary_ip: "{{ hostvars[groups['databases'][0]]['ansible_default_ipv4']['address'] }}"

# 寫長一點的拆解：
#   groups['databases']                     → ['db01.example.com', 'db02.example.com']
#   groups['databases'][0]                  → 'db01.example.com'
#   hostvars['db01.example.com']            → db01 的所有變數 + facts (需先收集)
#   hostvars['db01.example.com']['ansible_default_ipv4']['address']  → '10.0.1.30'
⚠ hostvars 取另一台的 facts 需要先收集

如果 db host 的 facts 還沒被收集（例如該台還沒在任何 play 中跑過），hostvars['db01']['ansible_default_ipv4'] 會 undefined。解法：① 在 db 群組的 play 中先 gather_facts，再進到 web 群組；② 啟用 fact caching（下節）讓 facts 跨 playbook 持久化。

7.7Fact Caching — 跨 playbook 重用 facts

Ansible 預設用 memory cache plugin，facts 只在當前 playbook 執行期間有效。如果你管理上千台 host，每次都重新收集 facts 不只慢，跨 playbook 取資料也不便。Fact caching 把 facts 持久化到磁碟、Redis、或外部系統。

7.7.1典型架構

Figure 7.3 — Fact Caching 的典型架構

7.7.2啟用 fact caching

ini · ansible.cfg 
[defaults]
# jsonfile 是最簡單的 cache plugin — 寫到本機磁碟
fact_caching = jsonfile
fact_caching_connection = .ansible-cache
fact_caching_timeout = 86400          # 24 小時過期

# 規模大選 redis（需要 redis server）
# fact_caching = redis
# fact_caching_connection = localhost:6379:0

# memcached、yaml、mongodb 等也是選項

7.7.3夜間預收 + 日間重用模式

yaml · facts-only playbook 
# gather-facts.yml — cron 排夜間執行
---
- name: 收集所有 host 的 facts 到 cache
  hosts: all
  gather_facts: true
  tasks: []                          # 不需 task — 光 gather 就會寫 cache

# cron: 0 3 * * * cd /opt/ansible && ansible-playbook gather-facts.yml
✓ Caching 帶來的兩大效益

① 性能——日間 deploy playbook 不用每次重收 facts，節省 1000 host × 2 秒 = 30+ 分鐘；② 跨 host 取資料——deploy webservers 時可以直接 hostvars['db01'].ansible_default_ipv4.address，不用先在 db 群組跑一次 play。

7.8自定 Facts（facts.d）

內建的 1000 個 fact 涵蓋系統通用資訊，但你可能還想暴露應用層資料：「目前部署版本」、「DB 連線狀態」、「業務 metric」等。facts.d 機制讓你在 managed node 上放靜態 / 動態檔案，setup 模組會自動讀進來。

7.8.1靜態 .fact 檔（INI 格式）

ini · /etc/ansible/facts.d/myapp.fact 
[deployment]
version=2.5.0
deployed_at=2026-05-07T10:00:00Z
deployed_by=alice

[features]
new_billing=true
cdn_enabled=true
yaml · 在 playbook 中讀取 
- name: 看自定 facts
  ansible.builtin.debug:
    msg: "目前版本: {{ ansible_local.myapp.deployment.version }}"

# ansible_local 是自定 facts 的命名空間
# myapp 是檔名（去掉 .fact 副檔名）
# deployment / features 是 INI section

7.8.2動態 .fact 腳本（輸出 JSON）

bash · /etc/ansible/facts.d/app_status.fact (executable script) 
#!/usr/bin/env python3
# 必須 chmod +x，必須輸出 JSON 到 stdout
import json, subprocess

facts = {
    'running_services': [],
    'db_alive': False,
}

# 查跑中的 myapp service
try:
    result = subprocess.run(
        ['systemctl', 'list-units', 'myapp*', '--no-pager', '--plain'],
        capture_output=True, text=True
    )
    facts['running_services'] = [
        line.split()[0] for line in result.stdout.split('\n') if line
    ]
except Exception:
    pass

# 查 DB 連線
try:
    facts['db_alive'] = subprocess.run(
        ['pg_isready', '-h', 'localhost'], capture_output=True
    ).returncode == 0
except Exception:
    pass

print(json.dumps(facts))
yaml · 使用動態 fact 
- name: 確保 DB alive 才繼續
  ansible.builtin.assert:
    that: ansible_local.app_status.db_alive
    fail_msg: "DB 連不上，停止部署"

7.9本章重點回顧

01

Facts 是 setup 模組的產出

每個 play 開始時自動執行 setup 模組，收集 1000+ 系統資訊。ansible_distribution、ansible_default_ipv4 等以 ansible_ 前綴可用。

02

兩種訪問方式

ansible_facts['key'] 是新風格；ansible_key 是舊風格頂層變數。預設兩者都可用，2026 年保持兩者相容是業界標準。

03

條件式分流

Facts 配 when 是 Ansible 跨平台支援的核心。ansible_os_family == "Debian"、ansible_memtotal_mb >= 16384 等。

04

register 取 task 結果

標準結構含 changed、failed、rc、stdout 等。command/shell 配 changed_when: false 抑制誤報。loop 中 register 結果在 .results list。

05

set_fact 是 runtime 寫變數

第 19 層優先序。從 register 結果加工出新變數的主要方式。cacheable: true 後寫入 fact cache，下次讀回變第 11 層。

06

Magic Variables 四大金剛

inventory_hostname（自己是誰）、groups（所有群組與成員）、group_names（自己屬於哪些群組）、hostvars（跨 host 取變數）。

07

Fact Caching 解決規模問題

1000+ host 規模時用 jsonfile / redis / memcached 持久化 facts。夜間預收 + 日間重用 是業界標準模式。

08

facts.d 加自定 facts

在 managed node 上的 /etc/ansible/facts.d/ 放 .fact 檔（INI 靜態或可執行 JSON 動態），透過 ansible_local 命名空間讀取。

練習題

  1. 初學者：用 ansible <host> -m setup 看你 inventory 中某台 host 的全部 facts，找出 OS、IP、記憶體、CPU 數的 fact 名稱。
  2. 初學者：寫一個 playbook 用 debug 印出當前 host 的 hostname、OS family、kernel、主 IP 與總記憶體。
  3. 初學者：寫一個 playbook 依 ansible_os_family 安裝對應的套件管理工具（Debian 系裝 apt-utils、RedHat 系裝 dnf-plugins-core）。
  4. 開發者：用 register 抓 systemctl is-active nginx 的結果，依結果判斷是否需要啟動服務。記得加 changed_when: false。
  5. 開發者：用 register + loop 同時查 nginx、postgresql、redis 三個服務狀態，把結果整理印出來。
  6. 開發者：用 set_fact 把 git commit short hash 設為 fact，搭配 cacheable: true 讓下次 playbook 不需重新計算。
  7. DevOps / SRE：用 groups['webservers'] 與 hostvars 在一個 controller host 上產生包含所有 webserver IP 的 nginx upstream 設定檔。
  8. DevOps / SRE：在 ansible.cfg 啟用 jsonfile fact caching，跑兩次 ansible-playbook gather.yml，第二次觀察 Gathering Facts task 應該變很快（從 cache 讀）。
  9. DevOps / SRE：在你某台 managed node 的 /etc/ansible/facts.d/ 放一個 app_version.fact INI 檔，記錄目前部署版本。寫一個 playbook 透過 ansible_local.app_version 讀取它。

本章詞彙表

Facts
Ansible 在 play 開始時透過 setup 模組從 managed node 收集的系統資訊。ansible_ 前綴可用，含 OS、硬體、網路等近 1000 個欄位。
setup 模組
收集 facts 的模組。gather_facts: true（預設）會自動執行；ad-hoc 用 ansible host -m setup。
ansible_facts
所有 facts 的 dict 容器。ansible_facts['distribution'] 是新風格訪問。
inject_facts_as_vars
ansible.cfg 設定，預設 true。把 ansible_facts.X 自動注入成頂層 ansible_X 變數。
gather_subset
setup 模組參數，細粒度控制收集哪些 facts 子集（all、network、virtual、hardware、distribution、min 等）。
register
Task 層 directive，把模組執行結果存成變數。標準結構含 changed / failed / rc / stdout 等。第 19 層優先序。
changed_when / failed_when
Task 層 directive，自定何時算 changed / failed。常用於 command/shell 模組抑制誤報。
set_fact
動態建立或修改變數的模組。第 19 層優先序，per-host 範圍。cacheable: true 後寫入 fact cache，下次讀回降為第 11 層。
Magic Variables
Ansible 內建保留變數，提供關於 Ansible 自身的資訊。名稱不可被覆蓋。
inventory_hostname
當前 host 在 inventory 中的名稱（可能是別名而非實際 hostname）。
groups
所有群組與其成員的 dict。groups['webservers'] 取得 webservers 群組的 host list。
group_names
當前 host 所屬群組的 list。常用 'production' in group_names 做條件分流。
hostvars
所有 host 的變數 dict（含 facts）。hostvars['db01'].ansible_default_ipv4.address 跨 host 取資訊。
Fact Caching
把 facts 持久化到磁碟 / Redis / Memcached 等。常用於大規模環境的「夜間預收 + 日間重用」模式。
fact_caching plugin
cache 後端實作。內建 memory（預設）、jsonfile、redis、memcached、yaml、mongodb、pickle 等。
facts.d
Managed node 上的目錄（預設 /etc/ansible/facts.d/），放靜態 .fact 檔（INI）或可執行腳本（輸出 JSON）。透過 ansible_local 命名空間訪問。
ansible_local
自定 facts 的訪問入口。ansible_local.<filename>.<section>.<key>。
