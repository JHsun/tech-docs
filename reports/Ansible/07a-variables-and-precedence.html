第 7 章 上 — 變數系統與優先順序

變數讓 playbook 從「死板的命令清單」變成「可重用的範本」——同一份 playbook 用不同變數值，可以部署到 staging 也可以 production。但 Ansible 的變數系統有 22 個層級的優先順序，這是業界 #1 的踩雷源。本上半章建立完整心智模型：變數從哪裡來（10+ 種定義方式）、誰會贏（22 層完整對照）、命名怎麼取（合法性與慣例）、變數的作用域（per-host vs per-play）。讀完這篇，往後再也不會被「我明明設了 var=X，為何 task 看到 Y」的鬼故事困擾。

本章覆蓋官方文件對應：Using Variables · Variable Precedence
初學者必讀（7.1–7.4） 開發者必讀（全章） DevOps / SRE 必讀（特別 7.5 優先順序與 7.7 變數除錯）

7.1為什麼需要變數？

來看一個沒用變數的「壞範例」與用了變數的「好範例」對照。

yaml · 沒用變數 — 寫死的版本 
tasks:
  - name: 下載 myapp 2.5.0
    ansible.builtin.get_url:
      url: "https://releases.example.com/myapp-2.5.0.tar.gz"
      dest: /opt/myapp-2.5.0.tar.gz

  - name: 解壓到 /opt/myapp-2.5.0
    ansible.builtin.unarchive:
      src: /opt/myapp-2.5.0.tar.gz
      dest: /opt/myapp-2.5.0/
      remote_src: true

# 想升級到 2.6.0？要改 4 個地方，且兩台 host 不同版本就完全沒辦法
yaml · 用了變數 — 範本化版本 
vars:
  app_version: "2.5.0"

tasks:
  - name: 下載 myapp
    ansible.builtin.get_url:
      url: "https://releases.example.com/myapp-{{ app_version }}.tar.gz"
      dest: "/opt/myapp-{{ app_version }}.tar.gz"

  - name: 解壓
    ansible.builtin.unarchive:
      src: "/opt/myapp-{{ app_version }}.tar.gz"
      dest: "/opt/myapp-{{ app_version }}/"
      remote_src: true

# 升級到 2.6.0：
# 方式一：改 vars 值
# 方式二：執行時 -e "app_version=2.6.0"
# 兩台 host 不同版本：透過 host_vars 個別覆蓋

7.1.1變數值的型別

YAML 變數可以是任何型別——string、int、boolean、null、list、dict（巢狀無限）。Ansible 處理時會自動依場景轉型，但有些陷阱要避開。

yaml · 各種變數型別 
vars:
  # String
  app_name: "myapp"
  env: production          # 不加引號也是 string

  # Integer / Float
  port: 8080
  cpu_quota: 0.75

  # Boolean (注意 yes/no/on/off 都會被解讀為 true/false)
  enabled: true
  debug_mode: false

  # Null
  backup_path: null

  # List
  allowed_users:
    - alice
    - bob

  # Dict / 巢狀
  tls:
    cert: /etc/ssl/site.crt
    key: /etc/ssl/site.key
    protocols: [TLSv1.2, TLSv1.3]
⚠ YAML 1.1 的「Norway 問題」

Ansible 用的 PyYAML 預設是 YAML 1.1，NO、OFF、FALSE、N、NORWAY（這個真的）等字串會被自動轉成 boolean。國家代碼挪威 NO 變成 False 是著名 bug。對策：所有 string 都用引號包起來，特別是看起來像 boolean / 數字的字串。

7.2變數的命名規則與慣例

7.2.1合法字元

規則範例合法？
必須以字母或底線開頭app_port / _internal✓
後續可含字母 / 數字 / 底線app_v2_port✓
不能用連字號（dash）app-port✗
不能以數字開頭2nd_attempt✗
不能用 Python 保留字class / import✗
不能用 Ansible 保留字name / environment✗

7.2.2業界命名慣例

①

snake_case

app_version、tls_cert_path、nginx_worker_connections。Python 風格、Ansible 內部變數一致。不要 用 camelCase 或 PascalCase。

②

Role 內變數加角色前綴

Role nginx 的內部變數命名 nginx_worker_processes、nginx_listen_port。避免 role 之間的命名衝突。第 10 章詳述。

③

內部變數用雙底線

Role 內不應外部使用的變數加 __ 前綴：__nginx_compute_workers。同事 review 時看到就知道「這不是給我設定用的」。

④

避開 ansible_ 前綴

ansible_ 是 Ansible 自己的保留前綴，用於連線變數（ansible_user）與 facts（ansible_distribution）。自定變數絕對不要用這前綴。

7.3.1Inventory 範圍（第 4 章已學）

第 4 章 4.5 節已經介紹過。重點回顧：

yaml · Inventory 變數定義方式 
# inventory.yml — host 與 group 直接內嵌變數
all:

    web01.example.com:
      app_port: 8080     # inventory file 內的 host vars
  vars:
    company: ACME            # inventory file 內的 group vars (all)

# inventory/group_vars/webservers.yml — 群組變數

# inventory/host_vars/web01.example.com.yml — 個別 host 變數
datacenter_rack: A07

7.3.2Play / Task 範圍

yaml · Play 與 Task 層的 vars 
- name: 部署應用
  hosts: webservers

  # ① play 層 vars — 整個 play 都看得到
  vars:
    app_version: "2.5.0"

  # ② vars_files — 從外部檔案載入
  vars_files:
    - vars/common.yml
    - vars/secrets.yml            # 通常是 vault 加密檔

  # ③ vars_prompt — 互動式詢問
  vars_prompt:
    - name: deploy_password
      prompt: "輸入部署密碼"
      private: true

  tasks:
    # ④ block 層 vars — 整個 block 內 task 共用
    - block:
        - name: 用 block 變數的 task
          ansible.builtin.debug:
            msg: "{{ block_only }}"
      vars:
        block_only: "only inside block"

    # ⑤ task 層 vars — 只有這個 task 看得到
    - name: task 自己的變數
      ansible.builtin.debug:
        msg: "{{ task_only }}"
      vars:
        task_only: "only here"

    # ⑥ include_vars — runtime 動態載入
    - name: 依 OS 載入不同變數檔
      ansible.builtin.include_vars: "vars/{{ ansible_os_family }}.yml"

7.3.3Role 範圍（第 10 章詳述）

yaml · Role 內的兩種變數位置 
# roles/nginx/defaults/main.yml — 預設值（最低優先序，使用者可輕易覆蓋）
nginx_worker_processes: auto
nginx_listen_port: 80

# roles/nginx/vars/main.yml — 內部常數（高優先序，難覆蓋）
__nginx_config_path: /etc/nginx/nginx.conf
__nginx_pid_file: /run/nginx.pid

7.3.4動態產生（set_fact / register — 第 7 章 下詳述）

yaml · 動態產生變數 
# register — 把 task 結果存成變數
- name: 查詢服務狀態
  ansible.builtin.command: "systemctl is-active nginx"
  register: nginx_status

# set_fact — 在 play runtime 設新變數（後續所有 task 都看得到）
- name: 設定 deploy 時間戳
  ansible.builtin.set_fact:
    deploy_id: "{{ ansible_date_time.iso8601_basic }}"

7.3.5CLI 範圍：extra_vars

bash · -e / --extra-vars 
# 單一變數
$ ansible-playbook site.yml -e "app_version=2.6.0"

# 多個變數
$ ansible-playbook site.yml -e "app_version=2.6.0 env=staging"

# JSON 形式（傳遞複雜結構）
$ ansible-playbook site.yml -e '{"app_version":"2.6.0", "ports":[80,443]}'

# 從檔案載入（@ 前綴）
$ ansible-playbook site.yml -e "@vars/release.yml"

7.4變數引用與 Jinja2 表達式

定義完變數，怎麼用？Ansible 透過 Jinja2 模板引擎 處理變數展開，標準語法是 {{ var_name }}。

7.4.1基本引用

yaml · 三種引用情境 
vars:
  app_name: myapp
  app_version: "2.5.0"
  database:
    host: db01.example.com
    port: 5432

tasks:
  # ① 字串中嵌入變數
  - name: "部署 {{ app_name }} v{{ app_version }}"
    ansible.builtin.debug:
      msg: "連到 {{ database.host }}:{{ database.port }}"

  # ② 整個值就是一個變數（特例：要加引號）
  - name: "變數展開為值"
    ansible.builtin.debug:
      msg: "{{ database }}"            # 整個 dict

  # ③ 巢狀屬性訪問（兩種等價語法）
  - name: "巢狀屬性"
    ansible.builtin.debug:
      msg: "{{ database.host }}"          # dot notation
  - name: "巢狀屬性 (字典存取)"
    ansible.builtin.debug:
      msg: "{{ database['host'] }}"       # subscript
⚠ 整個值是變數時必須加引號

YAML 把以 { 開頭的字串當成 inline dict，所以 msg: {{ var }} 會壞掉。對策：msg: "{{ var }}" 用引號包起來。在字串中間嵌入則不必（msg: "hello {{ name }}" 自動正確）。

7.4.2Jinja2 表達式：filters / tests / 運算

yaml · 常用 Jinja2 表達式 
vars:
  name: myapp
  version: "2.5.0"
  users: [alice, bob, charlie]

tasks:
  # Filters — 用 | 串接
  - name: "轉大寫: {{ name | upper }}"           # MYAPP
    ansible.builtin.debug: { msg: "{{ name | upper }}" }

  - name: "預設值: {{ undef | default('fallback') }}"
    ansible.builtin.debug: { msg: "{{ undef_var | default('fallback') }}" }

  - name: "List 長度: {{ users | length }}"      # 3
    ansible.builtin.debug: { msg: "{{ users | length }}" }

  - name: "List 連接: {{ users | join(', ') }}"   # alice, bob, charlie
    ansible.builtin.debug: { msg: "{{ users | join(', ') }}" }

  # 運算與比較
  - name: "條件判斷"
    ansible.builtin.debug: { msg: "new" }
    when: version is version('2.0.0', '>=')

  # 三元運算 (ternary)
  - name: "環境判斷"
    ansible.builtin.debug:
      msg: "{{ 'prod URL' if env == 'production' else 'staging URL' }}"
ⓘ Filters 是 Ansible 變數操作的核心

Ansible 內建幾百個 filter（upper、default、length、join、map、select、regex_replace、to_json、b64encode...）。第 9 章會專門介紹 Templates 與 Jinja2 進階用法。

7.522 層變數優先順序（核心）

本章最關鍵的部分。當同一個變數在多個地方定義，誰會贏？Ansible 有 22 個層級的優先順序，由低到高如下：

1
command line values（如 -u USER，注意不是 -e）
2
role defaults — roles/x/defaults/main.yml
3
inventory file or script group vars
4
inventory group_vars/all
5
playbook group_vars/all
6
inventory group_vars/<group>
7
playbook group_vars/<group>
8
inventory file or script host vars
9
inventory host_vars/<host>
10
playbook host_vars/<host>
11
host facts / cached set_fact
12
play vars（play 層 vars:）
13
play vars_prompt
14
play vars_files
15
role vars — roles/x/vars/main.yml
16
block vars（block 層 vars:）
17
task vars（task 層 vars:）
18
include_vars
19
set_fact / registered vars
20
role parameters / include_role vars
21
include_tasks / import_tasks 的 vars:
22
extra vars（-e / --extra-vars）— 永遠贏

7.5.1該記住的關鍵法則

!

extra_vars 永遠贏

第 22 層。-e 是「強制覆寫」的指令，CI / CD pipeline 與緊急覆蓋專用。即使 host_vars / set_fact 都不能蓋過。

!

role defaults 是「給人覆蓋」的

第 2 層，幾乎是最低。Role 設計者把使用者「應該可以調」的變數放這裡——任何 group_vars / host_vars / play vars 都能覆蓋。

!

role vars 是「內部常數」

第 15 層，比 play vars 還高。Role 內部的「不希望使用者亂改」的常數放這裡。例：模組依賴的 path、固定 URL 等。

!

set_fact 蓋過 group/host_vars

第 19 層。runtime 動態取得的值（如查 API 拿到的最新 token）會壓過 inventory 變數。

!

host_vars 比 group_vars 高

「越具體越優先」是核心原則。同 host 屬於多個 group 時，子群組變數覆蓋父群組變數。

!

cached set_fact 變回 facts 等級

用 set_fact: ... cacheable: true 存到 fact cache 後，下次 playbook 執行時優先序變回第 11 層（facts），不再 是 19 層。

7.5.2實戰：層級對打

來看一個實際對打的例子，假設我們在五個地方定義了 app_port：

yaml · 多層級同變數定義 
# inventory/group_vars/all.yml — 第 4 層
app_port: 8000

# inventory/group_vars/webservers.yml — 第 6 層
app_port: 8080

# inventory/host_vars/web01.example.com.yml — 第 9 層
app_port: 8888

# playbooks/site.yml 的 play vars — 第 12 層
vars:
  app_port: 9000

# task 中 set_fact — 第 19 層
- ansible.builtin.set_fact:
    app_port: 9999

# 命令列 -e — 第 22 層
# $ ansible-playbook site.yml -e "app_port=12345"
場景web01 上 app_port 最終是？
不下任何 -e 也沒 set_fact9000（play vars 第 12 層）
set_fact 跑了，沒下 -e9999（set_fact 第 19 層）
下了 -e "app_port=12345"12345（extra_vars 永遠贏）
沒 play vars，沒 set_fact，沒 -e8888（host_vars 第 9 層）
連 host_vars 也沒，只有 group_vars8080（webservers 第 6 層 蓋過 all 第 4 層）

7.6變數合併行為：覆蓋 vs 合併

當同名變數是 dict 或 list 型別 時，預設是「整個替換」而非「合併」。這是踩雷重災區。

7.6.1預設行為：替換

yaml · 預設：高優先序整個取代低優先序 
# group_vars/all.yml
tls:
  cert: /etc/ssl/site.crt
  key: /etc/ssl/site.key
  protocols: [TLSv1.2, TLSv1.3]

# host_vars/web01.yml — 想只覆蓋 cert path
tls:
  cert: /etc/ssl/web01.crt

# 結果：web01 上的 tls 變成只有 cert 一個 key！
# key 與 protocols 都不見了，因為整個 tls 字典被 host_vars 取代

7.6.2啟用 hash_behaviour: merge

ini · ansible.cfg 
[defaults]
hash_behaviour = merge
⚠ hash_behaviour: merge 是已不建議的設計

雖然 merge 模式聽起來方便，Ansible 官方明確不建議使用——它會讓變數行為變得不直觀，跨團隊協作時更難追蹤值是怎麼來的。正確做法：手動用 combine filter 合併：

yaml · 用 combine filter 顯式合併 
# 在需要合併的地方明確使用 combine
vars:
  final_tls: "{{ default_tls | combine(host_specific_tls, recursive=True) }}"

# 範例：
# default_tls = {cert: /a.crt, key: /a.key, protocols: [TLSv1.2]}
# host_specific_tls = {cert: /b.crt}
# 結果 final_tls = {cert: /b.crt, key: /a.key, protocols: [TLSv1.2]}

7.6.3List 變數合併

ⓘ List 也是「替換」非「附加」

List 同名變數同樣是高優先序整個替換低優先序。如果你要「累加」，請用 + 運算符或 union filter：

yaml · List 累加技巧 
# group_vars/all.yml
base_packages: [vim, tmux, git]

# group_vars/webservers.yml
extra_packages: [nginx, curl]

# tasks 中合併
- name: 安裝套件
  ansible.builtin.apt:
    name: "{{ base_packages + extra_packages }}"
    state: present
  # 也可以：name: "{{ base_packages | union(extra_packages) }}"

7.7變數除錯：當值不對時怎麼查

新手最常遇到「我明明設了變數，task 看到的值卻不對」。這時不要靠猜，用工具看真相。

7.7.1三大除錯工具

bash · 變數除錯黃金組合 
# 1) ansible-inventory --host —— 看單一 host 上「最終生效」的所有變數
$ ansible-inventory -i inventory/ --host web01.example.com
# 輸出 JSON，包含所有 inventory 範圍變數合併結果

# 2) debug 模組 —— 在 playbook 內任何位置印出變數
# 寫成一個 task：
- name: 看現在 app_port 是什麼
  ansible.builtin.debug:
    var: app_port

# 3) -vvv —— 跑 playbook 時看完整變數展開過程
$ ansible-playbook site.yml -vvv 2>&1 | grep -A2 app_port

7.7.2debug 模組的兩種寫法

yaml · debug var vs msg 
# 方式 1：var — 顯示「變數名 + 值」
- name: 看變數結構
  ansible.builtin.debug:
    var: tls
# 輸出：
# tls: {cert: /etc/ssl/site.crt, key: ..., protocols: [...]}

# 方式 2：msg — 自定訊息（要加 {{}} 引用）
- name: 人讀格式
  ansible.builtin.debug:
    msg: "TLS cert path is {{ tls.cert }}"

# 進階：印 dict 結構用 to_nice_yaml / to_nice_json
- name: 優雅顯示
  ansible.builtin.debug:
    msg: "{{ tls | to_nice_yaml }}"

7.8變數設計實踐建議

①

用對「層級」傳達意圖

role defaults（第 2 層）= 「歡迎覆蓋」；role vars（第 15 層）= 「請勿亂改」；group_vars（中間）= 「環境配置」。設計時讓層級對應職責。

②

secret 一律進 vault

密碼、API key、TLS 私鑰絕不寫在 plain YAML。放在 group_vars/<env>/vault.yml 用 ansible-vault 加密。第 13 章詳述。

③

變數命名同步 role 名

Role nginx 的所有變數都以 nginx_ 起頭。避免命名衝突，code review 時一眼看出歸屬。

④

避免 hash_behaviour: merge

官方建議保持預設「替換」行為，需要合併時手動用 combine filter 顯式表達意圖。

⑤

extra_vars 留給 CI / 緊急

常用變數放 group_vars / host_vars 進 git 可追蹤；-e 留給 CI pipeline（注入版本號）與緊急覆蓋（如關閉某個 feature flag）。

⑥

所有 string 都加引號

避開 YAML 1.1 的 Norway 問題、避免「看似數字實為 string」歧義。port: "8080" 比 port: 8080 安全。

7.9本章重點回顧

01

變數讓 playbook 範本化

同一份 playbook 用不同變數值跨環境部署。Jinja2 語法 {{ var_name }} 是統一引用方式。

02

10+ 種定義位置

Inventory（file / group_vars / host_vars）、play 層（vars / vars_files / vars_prompt）、role 層（defaults / vars）、動態（set_fact / register / include_vars）、CLI（extra_vars）。

03

22 層優先序心智模型

由低到高大致：role defaults < group_vars < host_vars < play vars < role vars < block / task vars < set_fact < extra_vars 永遠贏。

04

越具體越優先

host_vars 比 group_vars 高（host 比 group 具體）；task vars 比 play vars 高（task 比 play 具體）。設計時讓「特例」放在更具體的層。

05

extra_vars 是核武

第 22 層永遠贏。CI / CD pipeline 注入版本號、緊急覆蓋使用。日常配置不應依賴 -e。

06

Dict / List 預設替換

同名變數是 dict / list 時，高優先序「整個取代」低優先序。要合併用 combine filter 顯式表達；不要開 hash_behaviour: merge。

07

命名用 snake_case + role 前綴

nginx_worker_processes 而非 nginxWorker。Role 內變數加 role 名前綴避免衝突。內部變數用 __ 前綴標記。

08

除錯三件套

ansible-inventory --host 看最終值、debug 模組在 task 中印、-vvv 看完整展開過程。

練習題

  1. 初學者：在 playbook 中定義 app_name、app_port 兩個變數，用 debug 印出 "Deploy {{ app_name }} on port {{ app_port }}"。
  2. 初學者：把同一個變數 greeting 定義在 group_vars/all.yml 與 play 層 vars 裡，跑 playbook 確認 play 層的值贏（第 12 vs 第 4 層）。
  3. 初學者：在 playbook 中用 vars_prompt 互動式詢問使用者輸入版本號，並在 task 中使用該變數。
  4. 開發者：在 group_vars/all.yml、group_vars/webservers.yml、host_vars/web01.yml 三層都定義 http_port。用 ansible-inventory --host web01 確認 host_vars 的值最終勝出。
  5. 開發者：執行 ansible-playbook site.yml -e "http_port=9999"，觀察該變數在所有層的值都被覆蓋（extra_vars 永遠贏）。
  6. 開發者：定義一個 dict 變數 tls 含 cert / key / protocols，在 host_vars 中只想覆蓋 cert。先觀察預設行為（其他 key 消失），再用 combine filter 在 playbook 中達到部分合併。
  7. DevOps / SRE：故意製造一個變數值不如預期的場景（如同時在 5 個地方定義同變數），用第 7.7 節的診斷流程找出最終值來自哪層。
  8. DevOps / SRE：寫一個 playbook，用 set_fact 動態組出 deploy_id（含時間戳），然後在後續 task 中使用。試著用 -e "deploy_id=manual" 覆蓋它——觀察 extra_vars（第 22 層）確實覆蓋 set_fact（第 19 層）。
  9. DevOps / SRE：建立一個 role myapp，在 defaults/main.yml 設 myapp_port: 8080，在 vars/main.yml 設 __myapp_internal_path: /opt/myapp。play 中試著覆蓋兩者，觀察 vars/main.yml 的內部變數無法被簡單覆蓋（只有 -e 蓋得過）。

本章詞彙表

Variable（變數）
在 playbook / inventory / 命令列等處定義的鍵值對。可以是 string / int / boolean / list / dict 等型別。
Variable precedence（優先順序）
當同名變數在多個地方定義時，Ansible 決定誰生效的規則。共 22 層，extra_vars 永遠在最上層。
Jinja2
Ansible 使用的模板引擎。{{ var }} 引用變數、{% %} 控制結構、{# #} 註解。第 9 章詳述。
Filter
Jinja2 的資料轉換工具，用 | 串接：{{ name | upper }}、{{ users | length }}。Ansible 內建幾百個。
extra_vars
命令列 -e / --extra-vars 傳入的變數。優先順序最高（第 22 層），永遠贏過所有其他來源。
vars_prompt
Play 層 directive，互動式詢問使用者輸入。常用於密碼或部署版本號。
vars_files
Play 層 directive，從外部 YAML 檔載入變數。常配合 vault 加密的密碼檔。
role defaults
Role 內 defaults/main.yml。預設值，第 2 層（最低之一），歡迎使用者覆蓋。
role vars
Role 內 vars/main.yml。內部常數，第 15 層，不期望使用者隨意覆蓋。
set_fact
動態設定變數的模組。第 19 層優先序。第 7 章 下詳述。
register
Task 層 directive，把模組執行結果存成變數。第 19 層優先序。第 7 章 下詳述。
include_vars
Runtime 動態載入變數檔的模組。第 18 層優先序。常用於依 OS / 環境載入不同變數。
hash_behaviour
ansible.cfg 中的設定，控制 dict 變數合併行為。預設 replace（整個替換），可改 merge（深度合併）但官方不建議。
combine filter
Jinja2 filter，明確合併兩個 dict。{{ a | combine(b, recursive=True) }} 是替代 hash_behaviour: merge 的官方推薦做法。
YAML 1.1 Norway 問題
YAML 1.1 把 NO、OFF、FALSE 等字串自動轉 boolean。國家代碼 NO（挪威）變成 false 是著名 bug。對策：所有 string 加引號。
snake_case
變數命名慣例：全小寫 + 底線分隔。app_listen_port。Ansible / Python 風格。
