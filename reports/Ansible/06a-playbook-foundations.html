第 6 章 上 — Playbook 基礎結構

Playbook 是 Ansible 的主要自動化單位。它把多個 task 組成有名字、可進 git、可審計、可重跑的 YAML 檔。本章帶你從一個 hello-world playbook 開始，逐層解剖 play / task / handlers 等核心元素，理解 playbook 的執行模型——為什麼 task 是「橫向逐步」（一個 task 跑遍所有 host 才下一個 task），以及 FQCN、become 提權、pre_tasks / post_tasks 等基礎結構。下半章（第 6 章 下）會接著講 blocks、tags、ansible-playbook CLI 等進階組織技巧。

6.1從 Ad-hoc 到 Playbook

第 5 章末已預告 ad-hoc 的 6 個訊號——當你的指令需要重複執行、多步驟、條件判斷、結果傳遞時，該升級到 playbook 了。

6.1.1同樣的任務，兩種寫法

看一個對照組——「在所有 webservers 上裝 nginx、放設定檔、開機啟動、必要時重啟」這個任務：

bash · Ad-hoc 寫法（要敲 4 條命令） 
$ ansible webservers -m ansible.builtin.apt \
    -a "name=nginx state=present update_cache=yes" --become

$ ansible webservers -m ansible.builtin.copy \
    -a "src=./nginx.conf dest=/etc/nginx/nginx.conf" --become

$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=started enabled=yes" --become

$ ansible webservers -m ansible.builtin.service \
    -a "name=nginx state=restarted" --become

# 問題：
# 1) 設定檔沒變也會無條件重啟（破壞 idempotency）
# 2) 中間任一步失敗，後面照跑（沒有錯誤處理）
# 3) 沒進 git，下次就忘了順序與細節
yaml · 同樣任務的 Playbook 寫法 
# playbooks/nginx.yml
---
- name: 部署 nginx
  hosts: webservers
  become: true

  tasks:
    - name: 安裝 nginx 套件
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: 部署 nginx 設定檔
      ansible.builtin.copy:
        src: ./nginx.conf
        dest: /etc/nginx/nginx.conf
        mode: "0644"
      notify: restart nginx     # 只有檔案有變才會觸發 handler

    - name: 啟動並啟用 nginx 服務
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
✓ Playbook 解決了什麼

任務有名字（自我文件化）、handler 只在必要時重啟（保留 idempotency）、失敗自動停止（錯誤處理）、進 git（可審計、可回放）、可加變數與條件（後續章節）。一條 ansible-playbook playbooks/nginx.yml 重跑 100 次結果都一致。

6.2Playbook 的三層結構

每個 playbook 是一個 YAML 檔，從上到下有三層巢狀關係：

Figure 6.1 — Playbook / Play / Task 三層結構

6.2.1三層的職責

層級關鍵字職責
Playbook 整個 YAML 檔 包含一或多個 play。一份 playbook 通常代表一個明確目的，如「部署 web 服務」或「初始化新主機」
Play hosts: + tasks: 把一組 task 套用到特定的 hosts。同一份 playbook 可以有多個 play 對不同主機做不同事
Task name: + 模組名 + 模組參數 單一動作——呼叫一個 Ansible 模組。是執行的最小單位

6.2.2YAML 起手式

yaml · 最小可運行 playbook 
---                                  # YAML document 開始標記
- name: 我的第一個 playbook      # 這是「Play 的名字」（可選但強烈建議）
  hosts: all                     # 這個 play 套用到哪些 host
  tasks:                            # 這個 play 包含的 tasks
    - name: 確認連線
      ansible.builtin.ping:        # task 名稱 + 模組名 (FQCN)
# 注意：
# - 整個檔案開頭的 --- 是 YAML 慣例（document 起始標記）
# - 兩個空格縮排是 YAML 標準
# - 一個 play 是一個 list item（前面有 -）
# - 一個 task 也是一個 list item，縮排在 tasks: 底下

6.3Play 層：定義作用範圍

Play 的核心是「指定一組 hosts，並對它們套用一組 tasks」。除了 hosts: 與 tasks:，play 層還有許多重要關鍵字。

6.3.1Play 層常用關鍵字

關鍵字說明範例值
nameplay 的人類可讀名稱"部署 nginx 到 production"
hosts適用範圍 host patternwebservers / all:!staging
become整個 play 啟用 sudotrue
become_user提權後切到的使用者postgres
gather_facts是否收集 facts（預設 true）false 加速 play
varsplay 範圍變數見下例
vars_files從外部檔載入變數[group_vars/prod.yml]
tasks主要 task 列表見下例
pre_taskstasks 之前執行見 6.7
post_taskstasks 之後執行見 6.7
handlers被通知才執行的特殊 tasks見 6.6
roles引用 role（第 10 章）[common, webserver]
serial滾動並行度5 或 "20%"
strategy執行策略linear（預設） / free

6.3.2實際範例

yaml · 含多個 play 層關鍵字的範例 
---
- name: 部署 web 服務到生產環境
  hosts: webservers:&production      # 只跑生產環境的 webservers
  become: true                          # 整個 play 用 sudo
  gather_facts: true                    # 收集系統資訊
  serial: "25%"                          # 一次只更新 25% 的 host (滾動部署)

  vars:
    app_version: "2.5.0"
    app_port: 8080

  vars_files:
    - vars/secrets.yml                 # 外部變數檔（可能是 vault 加密過的）

  tasks:
    - name: 部署應用程式
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/myapp/app.conf
      notify: restart app

  handlers:
    - name: restart app
      ansible.builtin.service:
        name: myapp
        state: restarted

6.4Task 層：呼叫模組執行動作

Task 是 Ansible 的執行單位。一個 task 呼叫一個模組，把模組參數寫成 YAML key-value。

6.4.1Task 的標準寫法

yaml · Task 的解剖學 
tasks:
  - name: 這是 task 的名字（自我文件化）
    ansible.builtin.apt:                  # ← 模組名稱 (FQCN)
      name: nginx                       # ← 模組參數開始
      state: present
      update_cache: true
    become: true                            # ← Task 層級的 directive
    when: ansible_os_family == "Debian"    # ← 條件（第 8 章）
    tags:                                  # ← 標籤（第 6 章 下）
      - install
      - packages
    register: apt_result                 # ← 把結果存成變數（第 8 章）

6.4.2FQCN — Fully Qualified Collection Name

從 Ansible 2.10 開始，所有模組都建議用完整名稱呼叫：collection.namespace.module_name。這個規範叫做 FQCN。

寫法範例2026 年建議
短名稱copy:不建議 多個 collection 可能定義同名模組
FQCNansible.builtin.copy:建議 明確指定來源 collection
ⓘ FQCN 結構解析

ansible.builtin.copy 拆解：ansible = namespace（廠商／組織）、builtin = collection 名稱、copy = 模組名稱。常見 collection 還有 ansible.posix（POSIX 系統工具）、community.general（社群通用模組）、amazon.aws（AWS 雲端）等。第 11 章會深入講 Collections。

6.4.3命名 Task 的好處

name: 是可選的，但強烈建議每個 task 都寫。原因：

  • 執行時的 log 可讀性——沒名字就只看到模組名 + 參數，難以對應到「在做什麼」
  • --start-at-task 從特定 task 開始——失敗後重跑時非常有用
  • --list-tasks 列出將執行的 task——靠 name 才認得出來
  • code review 時的「程式碼註解」
bash · name 的實際效益 
# 列出 playbook 內所有 task（靠 name）
$ ansible-playbook site.yml --list-tasks

# 從特定 task 開始重跑（debug 神器）
$ ansible-playbook site.yml --start-at-task "部署 nginx 設定檔"

# 執行時 log 對齊：
PLAY [部署 web 服務] *********************
TASK [Gathering Facts] ********************
ok: [web01]
TASK [安裝 nginx 套件] ********************      ← 這就是 name 的價值
changed: [web01]

6.5Playbook 的執行模型

Playbook 怎麼跑？這是新手最容易誤解的地方——它不是「每台 host 從頭執行到尾」，而是「每個 task 跑遍所有 host 後，才進到下一個 task」。

6.5.1橫向 vs 縱向：Ansible 是橫向的

Figure 6.2 — 預設 linear 策略：task 為主迴圈，hosts 為內迴圈

6.5.2為什麼要橫向？

橫向執行（linear strategy）有幾個關鍵好處：

  • 失敗發現得早——如果某個 task 在 100 台 host 中 50 台失敗，可以馬上停止 play，不會等所有 host 跑完才發現問題
  • 狀態同步——確保所有 host 都完成 Task 1 才開始 Task 2，避免「我這台已經改完設定 + 重啟了，那台還在裝套件」這種混亂狀態
  • 並行度好控制——forks 控制同 task 同時跑幾台，CPU / 網路壓力可預測

6.5.3失敗如何傳播？

⚠ 預設行為：失敗的 host 從後續 tasks 中被剔除

當某 host 在 task N 失敗，它會從該 play 後續所有 task中被踢出，但其他 host 繼續跑。Play 結束後，PLAY RECAP 會顯示哪些 host 失敗了。如果所有 host 都失敗，play 就停止。

bash · 控制失敗行為的 directives 
# Task 層級：失敗也繼續
- name: 這個失敗也沒關係
  ansible.builtin.command: /bin/false
  ignore_errors: true

# Play 層級：任何 host 失敗就立即停止整個 play
- hosts: webservers
  any_errors_fatal: true
  tasks: ...

# Play 層級：超過 30% 失敗就停止
- hosts: webservers
  max_fail_percentage: 30
  tasks: ...

6.5.4strategy: free（非預設，少用）

ⓘ free strategy 的存在

strategy: free 讓每台 host 跑自己的 task 序列、不互相等待。一台跑完 task 1 就直接進 task 2，不等其他 host。聽起來更快，但會破壞同步性，除非極特殊情況不建議使用。99% 的場景用預設 linear 就好。

6.6Handlers — 條件式重啟的優雅機制

Handlers 是 playbook 中最有 Ansible 特色的設計之一。它解決一個經典問題：「只有在設定檔真的變更時，才重啟服務」。

6.6.1Handler 的工作原理

Figure 6.3 — Handler 的觸發機制

6.6.2三個關鍵特性

①

只在 task 回傳 changed=true 時觸發

這是 idempotent 設計的核心——若設定檔內容沒變，copy 模組回傳 changed=false，handler 不會被通知。重複執行 playbook 不會無謂重啟服務。

②

同一個 handler 多次通知只跑一次

如果有 5 個 task 都 notify 同一個 handler，那個 handler 在 play 結束時只會執行一次。這在「改 10 個設定檔，最後重啟一次服務」場景特別好用。

③

等所有 tasks 跑完才執行

Handler 不是被通知就立刻跑，而是等該 play 的所有 tasks 都結束後才依序執行。例外：meta: flush_handlers 可強制立即觸發。

6.6.3Handler 的完整範例

yaml · 多個 task 通知同一個 handler 
---
- name: 部署 nginx 多檔設定
  hosts: webservers
  become: true

  tasks:
    - name: 主設定檔
      ansible.builtin.copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
      notify: restart nginx

    - name: virtual host 設定
      ansible.builtin.template:
        src: vhost.conf.j2
        dest: /etc/nginx/sites-available/default
      notify: restart nginx

    - name: SSL 憑證
      ansible.builtin.copy:
        src: site.crt
        dest: /etc/ssl/certs/site.crt
      notify: restart nginx

  handlers:
    # 即使三個 task 都 notify，nginx 也只會重啟一次
    - name: restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted

6.6.4Handler 的進階技巧

yaml · listen + flush_handlers 
tasks:
  - name: 改 SSL 憑證
    ansible.builtin.copy:
      src: site.crt
      dest: /etc/ssl/certs/site.crt
    notify: tls reload          # 通知一個「事件主題」

  - name: 強制立即執行已通知的 handlers
    ansible.builtin.meta: flush_handlers

  - name: 這個 task 跑時 nginx 已經 reload 過了
    ansible.builtin.uri:
      url: https://localhost/health

handlers:
  # 用 listen 讓多個 handler 訂閱同一個事件主題
  - name: restart nginx
    listen: tls reload
    ansible.builtin.service:
      name: nginx
      state: restarted

  - name: 記錄 TLS 變更時間
    listen: tls reload
    ansible.builtin.lineinfile:
      path: /var/log/tls-changes.log
      line: "TLS reloaded at {{ ansible_date_time.iso8601 }}"
      create: true
⚠ Play 中途失敗時 handlers 不會跑

預設行為：如果 play 中途有 task 失敗，原本被 notify 的 handlers 不會執行——避免在不一致狀態下重啟服務。要強制執行可加 --force-handlers 或在 play 內設 force_handlers: true。

6.7pre_tasks / tasks / post_tasks 的執行順序

除了 tasks:，play 還可以定義 pre_tasks: 與 post_tasks:——前置與後置工作。它們的執行順序是固定的：

Figure 6.4 — 一個 play 內的執行順序

6.7.1典型用法

yaml · pre_tasks / post_tasks 範例 
---
- name: 部署應用
  hosts: webservers
  become: true

  pre_tasks:
    - name: 確認最低 disk 空間
      ansible.builtin.assert:
        that: "ansible_mounts | selectattr('mount', 'equalto', '/') | list | first | json_query('size_available') > 1000000000"
        fail_msg: "/ 剩餘空間不足 1GB，無法部署"

    - name: 備份目前設定
      ansible.builtin.copy:
        src: /etc/myapp/app.conf
        dest: /etc/myapp/app.conf.bak
        remote_src: true

  tasks:
    - name: 部署新設定
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/myapp/app.conf
      notify: restart app

  post_tasks:
    - name: 驗證服務有回應
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/health"
        status_code: 200
      register: healthcheck
      retries: 5
      delay: 10

    - name: 通知 Slack 部署完成
      ansible.builtin.uri:
        url: "{{ slack_webhook }}"
        method: POST
        body: '{"text": "Deploy completed on {{ inventory_hostname }}"}'

  handlers:
    - name: restart app
      ansible.builtin.service:
        name: myapp
        state: restarted

6.8Become — Privilege Escalation

大多數系統管理任務需要 root 權限（裝套件、改 /etc 下的檔、重啟服務）。Ansible 用 become 機制處理提權。

6.8.1四個層級的 become

yaml · Become 的四個設定位置 
# 1) 命令列：影響整次執行
# $ ansible-playbook site.yml --become --ask-become-pass

# 2) Play 層：整個 play 都用 sudo
- name: 部署 web
  hosts: webservers
  become: true                # ← 這裡
  tasks:
    - name: 裝 nginx
      ansible.builtin.apt: { name: nginx, state: present }

# 3) Block 層：一組 tasks 共用提權（第 6 章 下會講 block）
  tasks:
    - block:
        - name: block 內的 task 都會 sudo
          ansible.builtin.command: ...
      become: true            # ← 整個 block 提權

# 4) Task 層：只有這一個 task 提權
  tasks:
    - name: 這個 task 才需要 sudo
      ansible.builtin.copy:
        src: app.conf
        dest: /etc/app/app.conf
      become: true            # ← 只這個 task

6.8.2切到非 root 的使用者

yaml · become_user 範例 
# 用 sudo 但切到 postgres 帳號跑某個任務
- name: 建立 PostgreSQL 資料庫
  community.postgresql.postgresql_db:
    name: myapp_db
    state: present
  become: true
  become_user: postgres     # 不切 root，切到 postgres
ⓘ Become method 的選擇

預設 become_method: sudo，但 Ansible 還支援 su、pbrun、doas、pfexec、runas（Windows）等多種提權方式。一般 Linux 用 sudo 即可，無密碼 sudo 在 inventory 用 NOPASSWD 設定（第 3 章 3.3.1 已介紹）。

6.9第一次跑 Playbook

把第 6 章學的所有概念串起來，建立並執行一個完整的 playbook。

6.9.1建立檔案結構

bash · 設定專案結構 
$ mkdir -p ~/ansible-lab/playbooks
$ cd ~/ansible-lab

# 建立 inventory（第 4 章學的）
$ cat > inventory.ini <<EOF
[webservers]
web01.example.com
web02.example.com

[webservers:vars]
ansible_user=ansible
EOF

# 建立 ansible.cfg（第 3 章學的）
$ cat > ansible.cfg <<EOF
[defaults]
inventory = ./inventory.ini
forks = 25
host_key_checking = False
EOF

6.9.2建立 playbook

yaml · playbooks/first.yml 
---
- name: 第一個正式 playbook — 部署 nginx
  hosts: webservers
  become: true

  vars:
    nginx_user: www-data
    worker_connections: 1024

  pre_tasks:
    - name: 確認是 Debian / Ubuntu 系統
      ansible.builtin.fail:
        msg: "此 playbook 只支援 Debian / Ubuntu"
      when: ansible_os_family != "Debian"

  tasks:
    - name: 安裝 nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: 部署 index.html
      ansible.builtin.copy:
        content: "<h1>Hello from {{ inventory_hostname }}</h1>\n"
        dest: /var/www/html/index.html
        mode: "0644"

    - name: 確保 nginx 啟動且開機自動啟動
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  post_tasks:
    - name: 驗證 nginx 回應 HTTP 200
      ansible.builtin.uri:
        url: "http://localhost"
        status_code: 200
      delegate_to: "{{ inventory_hostname }}"

6.9.3執行

bash · 跑 playbook 的標準流程 
# 1) 語法檢查（不執行，只看 YAML 結構是否正確）
$ ansible-playbook playbooks/first.yml --syntax-check

# 2) 列出將執行的所有 tasks（確認沒打錯）
$ ansible-playbook playbooks/first.yml --list-tasks

# 3) 列出將打到的所有 host
$ ansible-playbook playbooks/first.yml --list-hosts

# 4) Dry run（看會做什麼，但不實際執行）
$ ansible-playbook playbooks/first.yml --check --diff

# 5) 正式執行
$ ansible-playbook playbooks/first.yml

# 6) 看完整 SSH debug
$ ansible-playbook playbooks/first.yml -vvvv

6.9.4看 PLAY RECAP

text · 執行結束的 PLAY RECAP 
PLAY RECAP **************************************************
web01.example.com  : ok=6    changed=3    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
web02.example.com  : ok=6    changed=3    unreachable=0    failed=0    skipped=0    rescued=0    ignored=0
欄位意義
ok成功完成（含未變更的）
changed實際改變狀態的 task 數
unreachable連 SSH 都連不上的 host 數
failed失敗的 task 數
skipped因 when 條件不符跳過的 task 數
rescued失敗但被 rescue block 救回（第 6 章 下）
ignored失敗但被 ignore_errors 忽略

6.10本章重點回顧

01

三層結構

Playbook（YAML 檔）→ Play（hosts + tasks）→ Task（呼叫一個模組）。一個 playbook 可有多個 play，一個 play 可有多個 task。

02

FQCN 是 2026 年標準

所有模組用 collection.namespace.module 完整名稱。ansible.builtin.copy 而非短名稱 copy。明確、無歧義、與 Collections 生態對齊。

03

每個 task 都要寫 name

--list-tasks、--start-at-task、執行 log 全部依賴 name。把 name 當註解寫，未來的你會感謝。

04

橫向執行模型

預設 linear strategy：每個 task 跑遍所有 host 後才下一個 task。失敗發現得早、狀態同步、並行度可控。

05

Handlers 解決條件式重啟

notify 只在 task changed 才觸發；同 handler 多次 notify 只跑一次；play 結束才執行。維持 idempotency 的核心設計。

06

pre_tasks → tasks → post_tasks → handlers

固定順序。前置做檢查 / 備份，主 tasks 做核心，後置做驗證 / 通知，handlers 最後重啟。

07

Become 四層級

命令列、play、block、task 任一層都能設 become: true。生產環境通常 play 層級啟用，特殊 task 用 become_user 切到非 root。

08

執行前的安全網

順序：--syntax-check → --list-tasks → --check --diff → 實際執行。重大變更必走完這四步。

練習題

  1. 初學者：把第 5 章你寫過的某個 ad-hoc 命令改寫成一個最小的 playbook（含 name、hosts、tasks），跑 --syntax-check 確認語法正確。
  2. 初學者：寫一個 playbook 在 webservers 上裝 htop、tmux、git 三個套件。執行兩次，第二次觀察 PLAY RECAP 中的 changed 數字應為 0。
  3. 初學者：在你的 playbook 中故意拼錯一個模組參數名（如 nme 代替 name），用 --check 看 Ansible 報的錯訊。
  4. 開發者：寫一個 playbook 部署 nginx 設定檔 + 重啟服務。第一次執行確認 handler 觸發；第二次執行確認 handler 沒觸發（因為設定沒變）。
  5. 開發者：寫一個含三個 task 的 playbook，每個都 notify 同一個 handler。確認最終只重啟服務一次。
  6. 開發者：用 pre_tasks 加一個 disk 空間檢查（assert 模組），故意設不可能達成的條件，確認 playbook 會在 pre_tasks 階段就停下來。
  7. DevOps / SRE：寫一個 playbook，用 serial: "20%" 對 10 台 host 滾動部署，觀察執行 log 確認確實是分批跑。
  8. DevOps / SRE：寫一個 playbook，用 become_user: postgres 在 db servers 上執行某個 PostgreSQL 命令，驗證 sudo 切換有效。
  9. DevOps / SRE：把 any_errors_fatal: true 加到一個 multi-host playbook，故意讓一台失敗，確認其他 host 也會立即停止。

本章詞彙表

Playbook
YAML 檔案，Ansible 自動化的主要容器。包含一或多個 play。
Play
把一組 task 套用到指定 hosts 的單位。每個 play 至少要有 hosts: 與 tasks:。
Task
單一執行動作——呼叫一個 Ansible 模組。語法：name: + 模組名 + 參數。
FQCN (Fully Qualified Collection Name)
模組的完整名稱，格式 namespace.collection.module。例：ansible.builtin.copy。2026 年標準寫法。
linear strategy
Ansible 預設執行策略：每個 task 跑遍所有 host 後才下一個 task。確保狀態同步。
free strategy
另一種執行策略：每台 host 各自跑自己的 task 序列、不同步。極少用。
Handler
特殊 task，只在被 notify 通知時才執行。play 結束才跑。同 handler 多次通知只執行一次。
notify
Task 層的 directive，當該 task changed=true 時觸發指定的 handler。
flush_handlers
強制立即執行所有累積的 handlers，不等到 play 結束。語法 meta: flush_handlers。
pre_tasks / post_tasks
Play 層的 hook：pre_tasks 在 roles / tasks 之前執行，post_tasks 在之後執行。常用於前置檢查與後置驗證。
become / become_user / become_method
Privilege escalation 三件套。become: true 啟用提權，become_user 指定切換到的使用者（預設 root），become_method 指定方式（預設 sudo）。
gather_facts
Play 層 directive，控制是否在第一個 task 之前自動跑 setup 模組收集 facts。預設 true，加速 play 可設 false。
serial
Play 層 directive，控制滾動並行度。可寫具體數字（5）或百分比（"20%"）。
any_errors_fatal / max_fail_percentage
失敗傳播控制。前者：任何 host 失敗就立即終止整個 play。後者：失敗比例超過閾值才終止。
PLAY RECAP
Playbook 執行結束的統計表。每行一個 host，顯示 ok / changed / failed / unreachable 等計數。
--syntax-check / --list-tasks / --list-hosts / --check / --diff
ansible-playbook 的五大安全網 flags。執行重大變更前依序使用。
