34.1傳統 Ansible 的兩個天花板

Figure 34.1 — 傳統 Ansible 的兩個天花板與對應解法

34.1.1三個典型痛點

🌍

跨地區部署

Tokyo / Singapore / Frankfurt 各 datacenter，每地一堆 host，control 在 SF。SSH 跨海延遲 + firewall 規則複雜。Mesh 解。

🏭

邊緣設備 / 工廠 / 零售

製造機台 / POS 終端 / IoT。設備在 NAT 後、不主動讓 cloud SSH 進來。Mesh 解（execution node 部署在邊緣、phone home 模式）。

⏰

2:00 AM 告警

磁碟滿了、服務掛了、cert 將過期。傳統流程：alert → PagerDuty 叫人 → 人 SSH → 跑 playbook 修。MTTR 30 分鐘。EDA 解（直接 alert → playbook 自動修，30 秒）。

34.2Mesh 四種 node

Automation Mesh 用四種 node role 組成有彈性的網路。理解這四種是後續設計拓撲的基礎。

34.2.1四種角色

🎛

Control node

跑 controller 服務（web UI / scheduler / project sync / inventory update）。不執行 playbook。

⚡

Execution node

真正跑 playbook 的 node。透過 EE container 跑、SSH 到被管 host。靠近被管網路。

🔀

Hop node

純「中繼」node — 像 bastion / jump host。不執行 playbook、只 forward 訊息到 execution node。穿越網路分區用。

🔁

Hybrid node

同時是 control + execution。小規模部署省機器。大型 mesh 通常分開以便獨立 scale。

34.2.2四 node 對照

角色控制職責執行 playbook適用場景
Control是否大型部署 / 控制與執行分離
Execution否是大多數 mesh node — 執行的勞力
Hop否否網路中繼 / 跨 firewall 跳板
Hybrid是是小規模 / 單機部署

34.3Receptor — Mesh 底層

Mesh 的引擎是 Receptor——獨立 open source 專案、CNCF 友善、peer-to-peer 訊息傳遞框架。

34.3.1Receptor 三大特性

🔗

P2P 連線

node 之間 peer 連線形成 overlay。任意 node 可發訊息、Receptor 自動找最短路徑（含經 hop node）。

🔐

TLS / mTLS

所有連線可開 TLS。mTLS 雙向身份驗證 — 沒對的證書連不進來。job data / inventory / log 全程加密。

🛡

抗網路抖動

連線斷了會自動重連、訊息有 buffering。job 跑到一半網路掛、回來繼續。

34.4典型 Mesh 拓撲設計

34.4.1三個常見場景

🌐

場景 A：跨地區

3 個 region 各放 2 execution node、SF 一個 control。Region 間用 hop node 中繼。Receptor TLS。

🏠

場景 B：DMZ / 內外網

Control 在內網、被管 host 在 DMZ。中間加 hop node — DMZ → hop → control（hop 是唯一可雙向通的 node）。

📡

場景 C：邊緣 / IoT / 零售

邊緣設備在 NAT / 4G 後。execution node 部署在每個 site、主動連回 control。phone home pattern。

34.5Instance Group — 把 job 派到對的 node

node 都連起來了——但 job 要怎麼決定跑在哪？答案是 Instance Group。

34.5.1三個典型 instance group 設計

text · 典型 instance group 命名與用途 
Instance Group 設計：

ig_tokyo
  └── exec1.tokyo, exec2.tokyo
  用途：所有 Tokyo region 的 job

ig_frankfurt
  └── exec1.frankfurt, exec2.frankfurt
  用途：所有 EU region 的 job

ig_default
  └── 包含全部 execution node
  用途：fallback — 不限地區的 job

# Job template 配置：
# Tokyo deployment job → instance group: ig_tokyo
# EU GDPR 相關 job → instance group: ig_frankfurt
# 一般 job → ig_default

# Inventory 也可指定（更精確）：
# Tokyo inventory → instance_group: ig_tokyo
# 任何 job 對該 inventory 都派到 Tokyo execution
✓ 設計原則 — locality + 分權

① Locality：execution node 與被管 host 同 region — SSH 延遲 / 流量成本最佳化；② 分權：DBA team 的 job 派到 ig_dba（只 DBA 可控），Network team 派 ig_network。同個 mesh 多 team 共用、彼此不干擾。

34.6EDA — 從 ops 到事件驅動

Mesh 解規模問題；EDA 解時延問題。「人介入」是自動化的最大瓶頸——EDA 把這個瓶頸消除。

34.6.1傳統 vs EDA 流程對照

Figure 34.3 — 傳統 ops vs EDA 流程比較

34.6.2EDA 三大組件

📥

Event Source

事件來源 plugin。webhook / Kafka / journal / Alertmanager / file watch / CloudWatch / ServiceNow / Dynatrace 等。負責把事件送進 EDA。

📜

Rulebook

YAML 檔聲明「event + condition → action」。類 playbook 但不是 task list、是事件規則。

⚡

Action

事件匹配後做什麼。最常見是 run_playbook（觸發 AAP job template / 本地 playbook）。也可 post_event、debug、noop。

34.6.3EDA 引擎 — Drools 規則引擎

ⓘ EDA 為何依賴 Java？

EDA 內部用 Drools（Java 寫的成熟規則引擎）做事件比對。所以 EDA controller 需要 Java 17+ runtime（2026 推薦 Java 21 LTS）。ansible-rulebook 1.2.x 是 2026 主流版本、配 ansible.eda collection 2.11+。

34.7Rulebook — 完整解析

34.7.1Rulebook 三段式結構

yaml · rulebook 範例 — 收 webhook 觸發 playbook 
---
- name: 監聽 webhook 觸發部署
  hosts: all

  # ① Sources — 事件從哪來
  sources:
    - ansible.eda.webhook:
        host: 0.0.0.0
        port: 5000

  # ② Rules — 事件如何比對 + 比對到要做什麼
  rules:
    - name: 收到 deploy 事件
      condition: event.payload.message == "deploy-triggered"
      action:
        run_playbook:
          name: playbooks/deploy.yml
          extra_vars:
            version: "{{ event.payload.version }}"
            env: "{{ event.payload.environment }}"

    - name: 收到 rollback 事件
      condition: event.payload.message == "rollback"
      action:
        run_playbook:
          name: playbooks/rollback.yml

34.7.2跑 rulebook

bash · 安裝 + 跑 rulebook 
# 1) 裝 ansible-rulebook（注意 Java 21+）
$ sudo dnf install -y java-21-openjdk        # Rocky Linux
$ pip install ansible-rulebook
$ ansible-galaxy collection install ansible.eda

# 2) 跑 rulebook（會 listen 5000）
$ ansible-rulebook --rulebook deploy-listener.yml -i inventory/

# 3) 另一 terminal 觸發 — POST webhook
$ curl -X POST http://localhost:5000/endpoint \
    -H "Content-Type: application/json" \
    -d '{"message": "deploy-triggered", "version": "v1.2.3", "environment": "staging"}'

# 4) 觀察 rulebook 終端 — 自動跑 deploy.yml

34.7.3condition 語法

語法例
等於event.payload.severity == "critical"
不等於event.payload.status != "resolved"
數值比較event.payload.disk_usage > 90
邏輯 ANDevent.payload.severity == "critical" and event.payload.team == "infra"
邏輯 ORevent.payload.severity == "critical" or event.payload.severity == "high"
巢狀欄位event.payload.alert.labels.alertname == "DiskFull"
字串包含event.payload.message is match("error.*timeout")
欄位存在event.payload.host is defined

34.7.4action 種類

yaml · 五種常用 action 
# 1) run_playbook — 跑本地 playbook
action:
  run_playbook:
    name: playbooks/fix.yml
    extra_vars: { target: "{{ event.payload.host }}" }

# 2) run_job_template — 觸發 AAP job template（生產推薦）
action:
  run_job_template:
    name: "Disk Cleanup"
    organization: "MyOrg"
    job_args:
      extra_vars:
        host: "{{ event.payload.host }}"

# 3) post_event — 重新發出事件給其他 rule 處理
action:
  post_event:
    event:
      type: "escalation"
      original: "{{ event }}"

# 4) debug — 印事件出來（測試用）
action:
  debug:
    msg: "收到事件: {{ event }}"

# 5) noop — 故意不做事（用於規則測試）
action:
  noop: {}

34.8主流 source plugin

🌐

ansible.eda.webhook

HTTP POST 接收。最通用 — 任何系統能 POST JSON 都能整合。

🚨

ansible.eda.alertmanager

Prometheus AlertManager webhook 專門。直接收 alert 結構。

📜

ansible.eda.journald

Linux journal 監聽。某 service 出特定 log 觸發。

📁

ansible.eda.file_watch

監聽檔案 / 目錄變化。config 改動觸發 reload。

📨

ansible.eda.kafka

Kafka topic 消費。與 event-driven 平台整合（Confluent / Strimzi）。

⏱

ansible.eda.range

定時產生事件（類 cron）。「每 5 分鐘觸發」這種需求。

☁

第三方

dynatrace.event_driven_ansible / cisco.* / aws.* / servicenow.* / pagerduty.*。各家 vendor 都有。

🔌

自寫 plugin

Python class 實作 main() + 事件 generator。任何資料源都能變 EDA source。

34.9自動補救實戰

本節給三個常見場景的完整 rulebook + playbook。

34.9.1場景 1：磁碟滿自動清

yaml · disk-cleanup.yml — rulebook 
---
- name: 磁碟滿自動補救
  hosts: all
  sources:
    - ansible.eda.alertmanager:
        host: 0.0.0.0
        port: 5001

  rules:
    - name: 磁碟使用率 90%+ 自動清
      condition: |
        event.alert.labels.alertname == "DiskAlmostFull" and
        event.alert.status == "firing"
      action:
        run_job_template:
          name: "Disk Cleanup"
          organization: "Platform"
          job_args:
            limit: "{{ event.alert.labels.instance }}"
            extra_vars:
              target_host: "{{ event.alert.labels.instance }}"
              disk_usage: "{{ event.alert.annotations.disk_usage }}"

    # 第二條規則：清完還沒解、升級告警
    - name: 清完還沒解 → 升級
      condition: |
        event.alert.labels.alertname == "DiskAlmostFull" and
        event.alert.labels.severity == "critical"
      action:
        run_job_template:
          name: "PagerDuty Escalation"
          organization: "Platform"

34.9.2場景 2：服務掛了自動重啟

yaml · service-restart.yml — 用 journald source 
---
- name: 服務 crash 自動重啟
  hosts: all
  sources:
    - ansible.eda.journald:
        match:
          SYSTEMD_UNIT: myapp.service

  rules:
    - name: 看到 service crash 重啟
      condition: |
        event.message is match(".*crashed.*") or
        event.message is match(".*segfault.*")
      throttle:
        once_within: "5 minutes"     # 5 分內最多動一次（防 flapping）
      action:
        run_playbook:
          name: playbooks/restart-service.yml
          extra_vars:
            service_name: myapp

34.9.3場景 3：證書到期自動 renew

yaml · cert-renew.yml — 定時觸發 
---
- name: 每天檢查證書到期
  hosts: all
  sources:
    - ansible.eda.range:
        limit: 1                    # 每次跑 1 個 event
        # 配合 cron-like：每天 02:00 跑（從 systemd / cron 觸發 rulebook）

  rules:
    - name: 觸發 cert check + renew
      condition: event.i is defined     # 任何 range event
      action:
        run_job_template:
          name: "Cert Renewal Check"
          organization: "Security"

34.10業界實踐 + 第七篇總結

34.10.1Mesh + EDA 業界 8 條最佳實踐

①

Mesh 一律 mTLS

不是 TLS、是 mTLS。雙向身份驗證。沒對的證書連不進來。

②

execution node 靠近被管 host

同 region / 同 VPC。SSH 跨海延遲是百倍差距。

③

Instance group + Inventory locality

Inventory 直接指定 instance_group。job 不用每次手動選。

④

Hop node 部署在邊界

DMZ / 雲 / 邊緣的網路邊界。比直接打洞 SSH 規則安全。

⑤

EDA action 用 run_job_template 不用 run_playbook

透過 AAP 跑：① 集中 audit；② RBAC；③ EE 一致；④ 可觀察。run_playbook 只在 lab。

⑥

EDA 必加 throttle

once_within: "5 minutes" 防 flapping 觸發無限循環。

⑦

從非破壞性事件起步

第一條 rule 寫「debug 印出 event」、不要直接「自動關 prod」。觀察一週、確認規則對、再開 action。

⑧

Rulebook 進 git + code review

跟 playbook 同等對待。EDA 規則改錯可以「自動把 prod 關了」——比 playbook 更危險。PR 必 review。

34.11本章重點回顧

01

傳統 Ansible 兩天花板

SSH 直連限制（拓撲）+ 人觸發限制（時延）。Mesh 解前者、EDA 解後者。

02

Mesh 四種 node

Control（管不執行）/ Execution（執行不管）/ Hop（純中繼）/ Hybrid（單機部署用）。

03

Receptor 是引擎

P2P peer 連線、TLS / mTLS、抗網路抖動。底層 CNCF 友善 open source。

04

三典型拓撲

跨地區 / DMZ 內外網 / 邊緣 IoT。execution node 靠近被管 host。

05

Instance Group

把 job 派到對的 node。可在 job template 或 inventory 層級指定。Locality + 分權。

06

EDA 三組件

Source（事件來源）+ Rulebook（condition + action）+ Action（多半 run_job_template）。底層 Drools 規則引擎、需 Java 21+。

07

主流 source plugin

webhook（最通用）/ alertmanager（Prometheus 整合）/ journald（log）/ kafka（event-bus）/ range（cron-like）。

08

三場景自動補救

磁碟滿清掃 / 服務掛重啟（含 throttle）/ 證書定期 renew。EDA 把 ops MTTR 從 30 min 降到 30 sec。

練習題

  1. 初學者：畫一張你公司的 Ansible 拓撲圖 — 標出哪些 host 需要哪種 node 角色（control / execution / hop / hybrid）。寫一段「為何選這個拓撲」的說明。
  2. 初學者：在 lab 環境（4 VM）部署最簡 mesh — 1 control + 2 execution + 1 hop。awx-manage list_instances 確認都連上、receptor_ctl ping 測連通。
  3. 初學者：建 2 個 instance group（ig_west / ig_east）各含一個 execution node。建兩個 inventory 各分配對應 ig。觸發 job 觀察派到對的 node。
  4. 開發者：寫第一個 rulebook — webhook source、收到 {"action": "ping"} 觸發 debug action 印出。curl POST 測試 → 終端看到 event。
  5. 開發者：擴充上題 — condition 內 event.payload.action == "deploy" 才觸發、其他事件 noop。用兩種 payload 測試確認規則正確。
  6. 開發者：寫場景 1 的完整版 — Prometheus AlertManager 設 webhook 指向 EDA、磁碟使用率 > 90 觸發、EDA 跑 cleanup playbook。stress 工具拉滿磁碟測試。
  7. DevOps / SRE：對你公司現有 5 個常見 PagerDuty alert 寫對應 EDA rulebook（先全用 debug action 跑一週、確認規則正確再切 run_job_template）。
  8. DevOps / SRE：規劃跨 3 region mesh — 含完整 inventory 檔、TLS 證書策略、mTLS 設定。寫一份內部 mesh 架構文件含維運 SOP（怎麼加 node / 換 cert / 故障排查）。
  9. DevOps / SRE：對「服務 crash 自動重啟」rulebook 設計安全 throttle — 5 分內最多 3 次 / 1 小時內最多 10 次、超過就 PagerDuty 升級。寫測試方案驗證 throttle 行為對。

本章詞彙表

Automation Mesh
AAP 的 overlay 網路功能。讓 control plane 與 execution node 跨防火牆 / 跨地區連通。底層基於 Receptor。
Receptor
Mesh 的底層協定與引擎。Open source、CNCF 友善。P2P peer 連線、TLS 加密、抗網路抖動。
Control node
跑 controller 服務（web UI / scheduler / inventory update）的 node。不執行 playbook。
Execution node
真正執行 playbook 的 node。配 EE container、SSH 到被管 host。
Hop node
純中繼 node、像 jump host / bastion。不執行 playbook、只 forward 訊息。穿越網路分區用。
Hybrid node
同時是 control + execution。小規模部署省機器。大型 mesh 通常分開以便獨立 scale。
Peering
Receptor node 間建立連線。peer-to-peer、可多 hop、自動找最短路徑。
peers (config)
installer inventory 中設定 — 「我這個 group 連到哪個 group」。controller peers=hop_nodes。
mTLS (mutual TLS)
雙向 TLS — 雙方都要出示有效證書。沒對的 cert 連不進來。Mesh 生產必開。
Instance Group
execution node 的命名集合。Job template / inventory 可指定派到哪個 group。Locality + 分權設計用。
awx-manage list_instances
AAP 命令 — 列 mesh 中所有 node 的狀態（hostname / type / version / health）。
awx-manage receptor_ctl
AAP 命令 — 控制 receptor。status 看拓撲、ping <node> 測連通。
Event-Driven Ansible (EDA)
事件驅動自動化。事件 → 規則 → 動作。把 ops 從「人觸發」變「事件觸發」。
EDA Controller
AAP 中專責跑 rulebook 的元件（與 Automation Controller 分離）。需 Java 21+ runtime。
ansible-rulebook
EDA 的 CLI 工具。讀 rulebook YAML、啟 source、執行 rule、觸發 action。獨立可跑（不一定要 EDA Controller）。2026 版本 1.2.x。
Rulebook
EDA 的核心 YAML 檔。包含 sources / rules（含 condition + action）三段。類 playbook 但是事件規則。
Drools
EDA 內部的規則引擎（Java 寫的成熟 open source）。負責事件比對。所以 EDA 需 Java runtime。
Source / Event Source
Rulebook 中的事件來源。webhook / Alertmanager / Kafka / journald / file_watch / range / 第三方等。
Condition
Rulebook 中的事件比對條件。支援 ==, !=, <, >, and, or, is match, is defined 等。
Action
事件匹配後的動作。run_playbook / run_job_template / post_event / debug / noop 五大類。生產推薦 run_job_template（透過 AAP）。
throttle
Rule 的節流選項。once_within: "5 minutes" 表示 5 分內最多執行一次。防 flapping 事件無限觸發。
ansible.eda collection
EDA 官方 collection。提供 webhook / alertmanager / journald / kafka / file_watch / range 等內建 source plugin。
ansible.eda.webhook
最通用 source。listen HTTP POST。任何系統 POST JSON 都能整合。
ansible.eda.alertmanager
Prometheus AlertManager 整合 source。直接收 alert 結構（含 labels / annotations）。
ansible.eda.journald
Linux journald 監聽 source。某 service / 某 log 模式觸發。
ansible.eda.kafka
Kafka topic consumer source。整合 event-bus 平台（Confluent / Strimzi）。
ansible.eda.range
定時產生事件的 source。類 cron 場景。
ansible.eda.file_watch
監聽檔案 / 目錄變化的 source。config 改了觸發 reload 之類。
Decision Environment
EDA Controller 用的容器 image（類比 Execution Environment 之於 AAP）。包含 ansible-rulebook + collection + Python pkg + Java runtime。
run_job_template (action)
EDA action 之一。透過 AAP API 觸發 job template。生產推薦（集中 audit / RBAC / EE 一致 / 觀察性）。
NoOps（vs DevOps）
「無 ops」 — ops 工作完全自動化（事件 → 規則 → 補救）。EDA 是達到 NoOps 的關鍵工具。
MTTR (Mean Time To Resolve / Recovery)
故障平均恢復時間。傳統流程 30+ 分鐘（含人介入）；EDA 下到 30 秒。SRE 核心 KPI 之一。
