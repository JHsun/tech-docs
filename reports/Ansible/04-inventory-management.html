第二篇 — 基礎使用

第 4 章 — Inventory 庫存管理

Inventory 是 Ansible 的路由表——它告訴 ansible-core「世界上有哪些主機、怎麼連、屬於什麼群組、各自的 metadata 是什麼」。Playbook 邏輯設計得再漂亮，inventory 寫錯就會把對的命令打到錯的機器上。本章從最簡單的 INI 起步，進到推薦的 YAML 主力寫法，再帶你走過 group_vars/host_vars 目錄結構、多環境管理、動態 inventory（AWS / Azure / K8s），最後用 ansible-inventory CLI 驗證一切如預期。

本章覆蓋官方文件對應：Inventory Guide · Inventory Plugins · Variable Precedence (簡介)
初學者必讀（4.1–4.5） 開發者必讀（4.6–4.7） DevOps / SRE 必讀（4.8–4.9 動態 inventory + 多環境）

4.1Inventory 是什麼？為什麼它是核心

當你執行 ansible webservers -m ping，ansible-core 第一件事就是解析 inventory——把 webservers 這個字串對應到具體的主機清單，連同每台主機的 ansible_user、ansible_host、SSH 金鑰路徑、應用層變數等。沒有 inventory，Ansible 一行 task 都動不了。

Figure 4.1 — Inventory 在 Ansible 執行流程中的位置

4.1.1Inventory 解決的三個核心問題

  • 有哪些主機？——明確列出（靜態）或動態查詢（從 AWS/Azure/K8s API）。
  • 怎麼分群？——按角色（webservers、databases）、環境（production、staging）、地區（us-east、ap-east）、團隊歸屬等多維度切。
  • 每台/每群的 metadata 是什麼？——SSH 連線資訊（host、port、user、key）、應用層變數（http_port、db_password）、行為控制（ansible_python_interpreter）。

4.1.2三種主流 Inventory 形式

形式 優點 缺點 2026 年使用建議
靜態 INI 最簡單、純文字、新人 5 秒讀懂 巢狀群組難看、不支援結構化變數 少於 12 台 host 的小專案、demo、實驗室
靜態 YAML 支援巢狀、型別化變數、可分檔 縮排敏感、初學者要先學 YAML 2026 年靜態 inventory 主力推薦
動態 Inventory
（plugin / 腳本）		 自動同步雲端實例、零維護 API 失效就斷掉、需要額外 caching 雲原生環境、auto-scaling 群組、多環境
ⓘ 2026 年常見組合

多數團隊是混合架構：核心穩定主機（bastion、DNS、CI runner）走靜態 YAML，應用層動態實例（K8s nodes、ASG members）走 dynamic plugin。一份 ansible.cfg 透過 inventory = ./inventory/ 指向整個目錄，Ansible 會自動合併。

4.2INI 格式（最簡入門）

INI 是 Ansible 從 0.x 時代延續至今的格式，沒有任何外部依賴，純文字編輯器秒打開。先用它建立心智模型，再進到 YAML。

4.2.1最小可用 INI

ini · inventory.ini — 完整範例 
# 1) 不屬於任何群組的 host（會自動進 'all' 與 'ungrouped' 群組）
monitor.example.com   ansible_user=admin

# 2) 普通群組
[webservers]
web01.example.com     ansible_host=10.0.1.20  http_port=80
web02.example.com     ansible_host=10.0.1.21  http_port=8080

[databases]
db01.example.com      ansible_host=10.0.1.30
db02.example.com      ansible_host=10.0.1.31

# 3) 範圍寫法 — 自動展開 web03 ~ web10
[webfarm]
web[03:10].example.com

# 4) 群組變數（套用到該群組所有 host）
[webservers:vars]
ansible_ssh_private_key_file=~/.ssh/web_key
max_clients=200

[databases:vars]
ansible_ssh_private_key_file=~/.ssh/db_key
postgres_max_connections=100

# 5) 巢狀群組 — production 包含 webservers + databases
[production:children]
webservers
databases

# 6) all 全域變數
[all:vars]
ansible_user=ansible
ansible_python_interpreter=/usr/bin/python3

4.2.2主機別名與實際連線地址分離

Inventory 中的「主機名」只是標籤，實際 SSH 連到的位置由 ansible_host 決定。這個區別讓你可以用有意義的別名取代 IP：

ini · 別名 vs 實際位址 
[webservers]
# 「web-prod-1」是別名，Ansible 內部用它做 inventory_hostname
# SSH 實際連到 10.42.7.13:2222
web-prod-1   ansible_host=10.42.7.13  ansible_port=2222

# Cloud 場景常見：別名穩定但 IP 變動
api-eu-1     ansible_host=ec2-1-2-3-4.eu-west-1.compute.amazonaws.com

4.2.3INI 的限制

⚠ INI 不擅長的事

INI 格式不支援 list / dict 型別變數。如果你想寫 users: [alice, bob, charlie] 或巢狀字典，INI 會把它當成字串。一旦變數結構複雜起來，就該轉 YAML。另外 INI 也不支援 inline vault 加密——只能透過外部 vars 檔。

4.3YAML 格式（推薦主力寫法）

YAML inventory 把同樣的資訊寫成階層式結構。學習曲線比 INI 高一點，但10 台以上的 host 一律建議 YAML。

4.3.1YAML 的階層結構

Figure 4.2 — YAML inventory 的樹狀結構

4.3.2把 4.2.1 的 INI 翻成 YAML

yaml · inventory/production.yml 
# 重要：YAML inventory 必須以 'all' 開頭，all 是隱含的根群組
all:
  vars:
    ansible_user: ansible
    ansible_python_interpreter: /usr/bin/python3
  hosts:
    monitor.example.com:
      ansible_user: admin
  children:

    webservers:
      hosts:
        web01.example.com:
          ansible_host: 10.0.1.20
          http_port: 80
        web02.example.com:
          ansible_host: 10.0.1.21
          http_port: 8080
      vars:
        ansible_ssh_private_key_file: ~/.ssh/web_key
        max_clients: 200

    databases:
      hosts:
        db01.example.com:
          ansible_host: 10.0.1.30
        db02.example.com:
          ansible_host: 10.0.1.31
      vars:
        ansible_ssh_private_key_file: ~/.ssh/db_key
        postgres_max_connections: 100

    # 巢狀群組：production 包含其他群組
    production:
      children:
        webservers:
        databases:

4.3.3YAML 的型別優勢

YAML 直接支援 list / dict / boolean / int / null 等原生型別，不像 INI 全部變字串：

yaml · 型別化變數範例 
webservers:
  vars:
    # list — playbook 中可直接 loop
    allowed_users:
      - alice
      - bob
      - charlie
    # dict — 巢狀資料結構
    tls_config:
      cert_path: /etc/ssl/certs/site.crt
      key_path: /etc/ssl/private/site.key
      protocols: [TLSv1.2, TLSv1.3]
    # boolean / int / null — 真正的型別，不是字串
    enable_caching: true
    cache_ttl_sec: 3600
    backup_dir: null

4.4主機群組與巢狀群組

群組是 Ansible「打靶」的基本單位。設計群組就是設計你能用什麼角度去切割主機集合。

4.4.1群組設計的三條黃金原則

①

按功能（function）切，不按團隊切

對的：webservers、databases、load_balancers。錯的：team_alpha、cost_center_42——團隊歸屬用變數記錄就好，做為 group 切分太脆弱（人員異動時要重組）。

②

多維度群組可以共存

同一台 host 能屬於多個 group。web01 同時是 webservers（功能）+ production（環境）+ us_east（地區）。Playbook 可以用 hosts: webservers:&production 取交集。

③

巢狀（children）取代重複列舉

production 是 webservers + databases 的父群組。當你新增 cache_servers 到 production，自動套用所有 production 變數，不用每個檔案改。

4.4.2多維度切分實例

yaml · 多維度群組設計 
all:
  children:

    # 維度 1：依功能
    webservers:
      hosts:
        web01.example.com: {}
        web02.example.com: {}
        web-staging.example.com: {}
    databases:
      hosts:
        db01.example.com: {}
        db-staging.example.com: {}

    # 維度 2：依環境（與維度 1 交叉）
    production:
      hosts:
        web01.example.com: {}
        web02.example.com: {}
        db01.example.com: {}
    staging:
      hosts:
        web-staging.example.com: {}
        db-staging.example.com: {}

    # 維度 3：依地區
    us_east:
      hosts:
        web01.example.com: {}
        db01.example.com: {}
    ap_east:
      hosts:
        web02.example.com: {}

4.4.3主機 patterns（模式）— playbook 中的目標選擇

有了多維度群組，playbook 的 hosts: 就能組合出精準目標：

Pattern 寫法 意義 範例命中
all所有 host每一台
webservers單一群組web01, web02, web-staging
webservers:databases聯集（A 或 B）所有 web + 所有 db
webservers:&production交集（A 且 B）web01, web02
webservers:!staging排除（A 但不在 B）web01, web02
web*.example.com萬用字元web01, web02, web-staging
web0[1-2]*正則式web01, web02
bash · 用 pattern 限縮目標 
# 只跑 production 環境的 web
$ ansible 'webservers:&production' -i inventory.yml -m ping

# 跑所有 web 但排除 staging
$ ansible 'webservers:!staging' -i inventory.yml -m ping

# 用 --limit 在 playbook 命令時進一步收斂
$ ansible-playbook site.yml -i inventory.yml --limit "production:&us_east"

4.5group_vars / host_vars 目錄結構

當變數開始膨脹（每個群組 10+ 變數、每台 host 也有特殊變數），把全部塞在 inventory 檔內會變得難讀難維護。Ansible 的解法是「把變數從 inventory 拆到獨立檔案」——這就是 group_vars/ 與 host_vars/ 目錄的設計。

4.5.1標準目錄結構

text · 推薦目錄佈局 
inventory/
├── production.yml             # inventory 主檔（只有 hosts + groups，不含變數）
├── group_vars/
│   ├── all.yml                # 套用到所有 host
│   ├── webservers.yml         # 套用到 webservers 群組
│   ├── databases.yml          # 套用到 databases 群組
│   └── production.yml         # 套用到 production 群組（含其下所有子群組）
└── host_vars/
    ├── web01.example.com.yml  # 只套用到 web01 這一台
    └── db01.example.com.yml   # 只套用到 db01
✓ 自動載入機制

Ansible 解析 inventory 時，會自動 在 inventory/ 同層的 group_vars/ 與 host_vars/ 找對應檔案——檔名必須與群組／主機名稱一致。你不用 import、不用 include、不用任何宣告，放對位置就會自動套用。這是 Ansible 最優雅的設計之一。

4.5.2實際範例

yaml · group_vars/all.yml 
# 全公司共用的設定
timezone: Asia/Taipei
ntp_servers:
  - tw.pool.ntp.org
  - time.cloudflare.com
company_domain: example.com
monitoring_endpoint: https://prometheus.example.com
yaml · group_vars/webservers.yml 
# 只給 webservers 群組
nginx_version: "1.27"
nginx_worker_processes: auto
nginx_worker_connections: 1024
tls_protocols: [TLSv1.2, TLSv1.3]
deploy_user: deploy
app_root: /var/www/app
yaml · host_vars/web01.example.com.yml 
# 只給 web01 這一台 — 通常用於記錄該台的特殊性
role: primary
datacenter_rack: A07
custom_kernel_params:
  net.core.somaxconn: 65535
  vm.swappiness: 10

4.6多 Inventory 與多環境管理

真實專案至少有 production / staging 兩套環境，常見還有 development / qa / pre-prod 等。如何優雅地管理？2026 年的業界主流是「每個環境一個獨立 inventory 目錄」。

4.6.1推薦目錄結構

text · 多環境專案結構 
ansible-project/
├── ansible.cfg
├── inventories/
│   ├── production/
│   │   ├── hosts.yml
│   │   ├── group_vars/
│   │   │   ├── all.yml          # prod 專屬全域變數
│   │   │   └── webservers.yml
│   │   └── host_vars/
│   ├── staging/
│   │   ├── hosts.yml
│   │   ├── group_vars/
│   │   │   ├── all.yml          # staging 專屬全域變數
│   │   │   └── webservers.yml
│   │   └── host_vars/
│   └── development/
│       └── hosts.yml
├── playbooks/
│   └── site.yml
└── roles/

4.6.2切換環境的呼叫方式

bash · 切換 inventory 
# Production 環境
$ ansible-playbook -i inventories/production playbooks/site.yml

# Staging 環境（同一個 playbook，不同 inventory）
$ ansible-playbook -i inventories/staging playbooks/site.yml

# 在 ansible.cfg 設預設 inventory（避免每次都打 -i）
$ cat ansible.cfg
[defaults]
inventory = ./inventories/production
⚠ 預設 inventory 的雙面刃

把 inventory = ./inventories/production 寫死在 ansible.cfg 是常見陷阱——你習慣不打 -i，某天要跑 staging 卻忘了加，整個 production 就被 staging 的 playbook 改了。建議：不要在 ansible.cfg 設預設 inventory，每次 -i 明確指定，或用 direnv 設環境變數 ANSIBLE_INVENTORY。

4.6.3同時載入多個 inventory（混合靜態 + 動態）

把 -i 指向整個目錄，Ansible 會合併目錄內所有 inventory 來源（INI、YAML、可執行 plugin 腳本都行）：

text · 混合 inventory 目錄 
inventory/
├── 01_static.yml          # 靜態 host（bastion、CI）
├── 02_aws_ec2.yml         # AWS 動態插件設定
├── 03_k8s.yml             # K8s 動態插件設定
├── group_vars/
└── host_vars/

# 命令列：
# $ ansible-playbook -i inventory/ site.yml
# Ansible 會按檔名字母順序載入並合併（後者覆蓋前者的衝突變數）

4.7常用 Inventory 變數（連線控制）

Inventory 中的變數有兩類：① 應用層變數（playbook 中自由命名）、② 連線控制變數（以 ansible_ 開頭，影響 Ansible 如何連到 host）。下面是後者最常用的清單。

變數 說明 範例值
ansible_host實際連線的 IP / hostname（與 inventory 別名分離）10.0.1.20
ansible_portSSH port2222
ansible_userSSH 使用者ansible
ansible_ssh_private_key_file私鑰路徑~/.ssh/id_ansible
ansible_connection連線 plugin 名稱ssh / local / winrm / network_cli
ansible_python_interpreter遠端 Python 路徑（auto-discovery 找錯時手動指定）/usr/bin/python3.9
ansible_become是否 sudo / privilege escalationtrue
ansible_become_user提權後的使用者root
ansible_ssh_common_args額外 SSH 參數（ProxyJump 等）-o ProxyJump=bastion
ansible_winrm_transportWindows WinRM 認證方式ntlm / kerberos / credssp
ⓘ 完整清單

還有幾十個 ansible_* 變數，含網路設備專屬（ansible_network_os）、容器專屬（ansible_docker_extra_args）。完整列表見官方文件「Connecting to hosts: behavioral inventory parameters」。

4.8動態 Inventory 與 Inventory Plugins

當你的雲端實例每小時新增/銷毀數十台，手動維護靜態 inventory 不切實際。動態 inventory 在 ansible-playbook 執行的當下，去 cloud API 即時拉取主機列表。

4.8.1Inventory Plugin 演進史

ⓘ 為什麼是 plugin 不是 script？

2.4 版以前，動態 inventory 是「任何輸出特定 JSON 格式的可執行檔」（通常是 Python 腳本），稱為 inventory script。從 2.4 起 Ansible 引入 inventory plugin 機制，提供標準化的 caching、變數混合、auth 處理。2026 年新建的動態 inventory 一律用 plugin，不要再寫 script。

4.8.3AWS EC2 Plugin 完整範例

yaml · inventory/aws_ec2.yml 
# 檔名必須以 _aws_ec2.yml / _aws_ec2.yaml 結尾，
# 或者是 aws_ec2.yml / aws_ec2.yaml — 否則 plugin 不會認
plugin: amazon.aws.aws_ec2

# 要查的 AWS region（不寫的話用 boto 預設）
regions:
  - us-east-1
  - ap-east-1

# 過濾條件 — 只抓有特定 tag 的 instance
filters:
  tag:Environment: production
  instance-state-name: running

# 用 Tag 自動分群
keyed_groups:
  # tag:Role=web → 群組名 role_web
  - key: tags.Role
    prefix: role
  # availability-zone → 群組名 az_us_east_1a 等
  - key: placement.availability_zone
    prefix: az

# 用 PrivateDnsName 當 inventory hostname（避免短名稱衝突）
hostnames:
  - private-dns-name

# 啟用 caching — 在 CI 中可大幅降低 API 呼叫次數
cache: true
cache_plugin: jsonfile
cache_connection: /tmp/ansible_cache
cache_timeout: 300
bash · 使用 AWS 動態 inventory 
# 確保有 boto3 + 正確的 AWS 認證（環境變數、IAM role 或 ~/.aws/credentials）
$ pip install boto3 botocore

# 安裝 amazon.aws collection
$ ansible-galaxy collection install amazon.aws

# 跑 inventory 看結果（不執行 playbook）
$ ansible-inventory -i inventory/aws_ec2.yml --list

# 跑 ping 測試
$ ansible all -i inventory/aws_ec2.yml -m ping

4.8.4動態 Inventory 的快取與效能

⚠ 沒開 caching 的後果

單 region AWS 查詢 1–5 秒，多 region 5–20 秒。如果你 CI 每個 job 都跑一次 inventory，又每個 playbook 都不快取，CI 一天可能多撞 1000+ 次 EC2 DescribeInstances API，很容易撞上 rate limit。對策：① cache: true、② CI runner 共享 cache 目錄、③ 用 tag filter 縮小查詢範圍。

4.9ansible-inventory CLI — 驗證一切如預期

寫完 inventory，跑 playbook 之前一定先驗證。ansible-inventory 是專門檢查 inventory 解析結果的工具，比直接跑 playbook 安全 100 倍。

4.9.1三種輸出模式

bash · ansible-inventory 用法 
# 1. --list：JSON 格式列出全部
$ ansible-inventory -i inventory/production.yml --list

# 2. --list --yaml：YAML 格式（人讀比較舒服）
$ ansible-inventory -i inventory/production.yml --list --yaml

# 3. --graph：樹狀圖（最快檢查群組結構）
$ ansible-inventory -i inventory/production.yml --graph
@all:
  |--@ungrouped:
  |--@webservers:
  |  |--web01.example.com
  |  |--web02.example.com
  |--@databases:
  |  |--db01.example.com
  |--@production:
  |  |--@webservers:
  |  |--@databases:

# 4. --host：看單一 host 最終的所有變數（含 group_vars 合併後）
$ ansible-inventory -i inventory/production.yml --host web01.example.com

4.9.2把驗證納入 CI

yaml · GitHub Actions / GitLab CI 片段 
# 每次 PR 自動驗證 inventory 不會 broken
- name: Validate inventory
  run: |
    ansible-inventory -i inventories/production --list > /dev/null
    ansible-inventory -i inventories/staging --list > /dev/null
    # 也檢查 playbook 語法
    ansible-playbook -i inventories/production --syntax-check playbooks/site.yml

4.10本章重點回顧

01

YAML 是主力

10 台以上 host 一律用 YAML inventory。型別化變數、巢狀群組、可分檔的支援都遠優於 INI。INI 留給最簡單的 demo 與實驗室。

02

主機別名 ≠ 連線位址

Inventory 中的「主機名」只是標籤，ansible_host 才是真正連線的目標。這個區別讓你能用穩定別名搭配變動的 cloud IP。

03

多維度群組

同一台 host 可同時屬於 webservers + production + us_east 等多個群組。Playbook 用 : :& :! 組合，精準打靶。

04

group_vars/host_vars 自動載入

Inventory 旁的 group_vars/<name>.yml 與 host_vars/<name>.yml 會自動套用，不用 import。從具體（host）到一般（all）優先序遞減。

05

每環境一個 inventory 目錄

production / staging / dev 各一個獨立目錄，跑 playbook 時用 -i inventories/staging 切換。不要 在 ansible.cfg 寫死預設 inventory 避免誤跑。

06

動態 inventory 用 plugin 不用 script

2.4 版起的 plugin 機制有 caching、auth、變數混合等優勢。AWS / Azure / GCP / K8s / vSphere 都有官方 plugin，記得啟用 cache: true。

07

ansible-inventory 是黃金驗證工具

--graph 看群組結構、--host name 看單一 host 變數。CI 一定加上 --list > /dev/null 當作 syntax check。

08

群組設計原則

按功能切（webservers），不按團隊切（team_alpha）。團隊歸屬用變數記錄。巢狀（children）取代重複列舉。

練習題

  1. 初學者：把第 3 章的 INI inventory 改寫成 YAML，用 ansible-inventory --graph 確認結構正確。
  2. 初學者：在 inventory 中為某台 host 加上 ansible_host=錯誤IP，觀察 ping 失敗的錯誤訊息，再改回正確 IP 驗證。
  3. 初學者：建立 group_vars/all.yml 設一個變數 company_name: ACME，再用 ansible all -m debug -a "var=company_name" 確認所有 host 都能取到。
  4. 開發者：把同一個 host 放進三個群組（webservers + production + us_east），用 ansible 'webservers:&production:&us_east' -m ping 驗證交集 pattern 能正確命中。
  5. 開發者：在 group_vars/all.yml、group_vars/webservers.yml、host_vars/web01.yml 三處設同名變數 app_version，用 ansible-inventory --host web01 確認誰最後勝出，理解優先順序。
  6. DevOps / SRE：建立 inventories/production/ 與 inventories/staging/ 兩個目錄，各有自己的 hosts.yml + group_vars，驗證可用 -i 切換而不互相污染。
  7. DevOps / SRE：如果你有 AWS 帳號，依 4.8.3 寫一份 aws_ec2.yml，用 tag:Environment 篩選你的 instance，跑 ansible-inventory --graph 確認 keyed_groups 自動分群。
  8. DevOps / SRE：在你的 CI pipeline 加上 inventory 驗證步驟，故意把 inventory 弄壞（如刪掉一個逗號）確認 CI 會抓到並擋下 merge。

本章詞彙表

Inventory
定義 Ansible 要管理哪些 host、怎麼分群、各自變數的清單。可以是 INI 檔、YAML 檔或動態 plugin。
Static inventory
以檔案形式手動維護的 inventory（INI / YAML）。適合穩定環境。
Dynamic inventory
透過 plugin 或腳本在執行時即時生成的 inventory。適合雲端 / auto-scaling 環境。
Inventory plugin
Ansible 2.4+ 引入的標準化動態 inventory 機制，支援 caching、變數混合、auth。取代舊式 inventory script。
Group
主機分組。Playbook 用 group 名稱當作目標。同一 host 可屬於多個 group。
Children group / 巢狀群組
包含其他群組的群組。父群組的變數會繼承到所有子群組成員。INI 用 [parent:children]，YAML 用 children: key。
all / ungrouped
兩個自動存在的內建群組。all 包含所有 host；ungrouped 只包含沒被加入任何群組的 host。
inventory_hostname
Magic variable，host 在 inventory 中的名稱（別名）。與 ansible_host（實際連線地址）區別。
group_vars/
放群組變數的目錄。檔名與群組名一致時自動套用，無需 import。
host_vars/
放單一主機變數的目錄。檔名與 inventory_hostname 一致時自動套用。
Host pattern
選擇目標 host 的字串。支援 :（聯集）、:&（交集）、:!（排除）、*（萬用）。
keyed_groups（dynamic plugin）
動態 inventory plugin 的設定項，依 instance metadata（tag、region 等）自動產生群組。
ansible-inventory
專門檢查 inventory 解析結果的 CLI 工具。--graph、--list、--host 是三大常用參數。
Behavioral inventory parameters
以 ansible_ 開頭、控制 Ansible 連線行為的特殊變數（ansible_host、ansible_user、ansible_port 等）。
